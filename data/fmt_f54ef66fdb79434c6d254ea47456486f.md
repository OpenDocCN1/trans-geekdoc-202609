
如果数据已预先检查过完整性，考虑在执行批量更新时（例如，从操作数据库加载数据仓库）停用约束检查。你也可以将昂贵的约束检查推迟到执行批量更新之后。虽然大多数数据库应用程序可以完全使用 4GL 开发，但考虑用 3GL（例如 C#）编写某些模块，以加速关键方面或实现更好的控制（例如，在 3GL 中检查非循环约束通常比在 SQL 中使用递归并集更快）。

对于极少数特定应用，关系 DBMS 系统可能无法提供所需的性能，可能需要另一种类型的 DBMS（例如，对象数据库）。

由于实际应用通常要求用户通过外部接口（例如，屏幕表单）而不是直接在基表上执行数据更新，因此需要决定在表级进行多少约束检查，在表单级进行多少。对于客户端-服务器网络，我们需要决定在客户端完成多少工作，在服务器端完成多少。约束通常同时在用户界面和 DBMS 中实现。

在屏幕表单上实现约束可以尽早检测数据录入错误。在 DBMS 上实现约束可确保无论用户界面如何，都会对其进行检查。对于非集中式数据库系统，在决定如何复制数据以减少通信开销时需要极大的谨慎。对这些问题的适当讨论超出了本书的范围。

如果在执行前述内部模式优化后，系统性能仍然不可接受，可能需要对基本关系模式进行**反规范化**。通常，这涉及引入**受控冗余**，以减少聚焦查询所需的表连接数量。这会降低更新速度（必须保持冗余事实的一致性），并使系统更难维护，但可以显著减少查询的响应时间。

任何反规范化决策都应仔细记录，并必须强制执行适当的子集约束或相等约束来控制冗余，除非反规范化版本仅用于查询而不用于更新（例如数据仓库）。

作为一个简单示例，考虑以下关系子模式，它是从我们的软件零售商示例中提取的。

![](img/u14-12-9780443237904.jpg)

假设我们经常需要列出指定发票的行项目，包括项目标题。使用前面给出的模式，这需要连接两个表。如果表非常大，仅为了获取项目标题而访问第二个表可能会使速度过慢。为了避免这种情况，我们可以通过在 `LineItem` 表中插入 `title` 的额外副本来进行反规范化。这意味着事实类型 `Item has Title` 现在映射到两个表。为了控制这种**表间冗余**，我们在表之间添加了一对子集约束，如下所示：

![](img/u14-13-9780443237904.jpg)

新的 `LineItem` 表被反规范化为 1NF，因为它包含函数依赖 `itemCode → itemTitle`，而 `itemCode` 只是其主键的一部分。尽管约束模式更复杂，但查询现在可能仅通过访问 `LineItem` 表来执行。带星号的唯一性约束和函数依赖都由其他约束隐含（为什么？），因此无需指定。主键和备选键约束开销较小，但成对子集约束可能开销较大。它不是外键约束，但在 SQL 标准中，可以将其声明为以下断言：

```
create assertion LineItem_itemCode_itemTitle_pair in_Item
check (not exists
                 (select * from LineItem
                  where itemCode not in
                      (select itemCode from Item
                       where itemTitle = LineItem.itemTitle)))
```

在大多数 DBMS 中，不支持断言，因此此约束通常使用触发器编码。每当从 `Item` 表中删除或重命名（代码或标题）项目，或在 `LineItem` 表中插入或重命名项目时，都需要检查子集约束。由于项目很少被删除或重命名，子集约束的主要开销涉及验证对 `LineItem` 表的插入。对于某些应用程序，额外的更新开销可能是提高查询性能值得付出的代价。

前面的示例通过在不同表中存储两次项目标题事实来进行反规范化。另一种反规范化技术是嵌入函数依赖于非键属性的事实，从而违反 3NF。例如，图 14.75(a) 中的概念模式默认映射到 图 14.75(b) 中的规范化关系模式。

从 `roomNr` 到 `phoneNr` 的函数依赖由 `Room` 表中的主键约束高效强制执行，但列出员工电话号码的查询需要连接。为了加速此查询，我们可以通过将电话事实嵌入 `Employee` 表来反规范化为 2NF，如 图 14.75(c) 所示。

由于许多员工可能共用同一个房间，这种反规范化模式容易出现**表内冗余**。例如，如果员工 1 和 2 共用房间 200，该房间电话号码为 4251234567，则房间 200 拥有该电话号码的事实被存储了两次。为了控制这种冗余，我们需要强制执行函数依赖 `roomNr → phoneNr`。因为这不再由键约束强制执行，我们需要单独指定它。在 SQL 标准中，可以使用以下断言：

```
create assertion eachRoomHasAtMostOnePhoneNr
check( not exists
            (select roomNr from Employee
             group by roomNr
             having count(distinct phoneNr) > 1))
```

如果不支持断言（这很可能），嵌入的函数依赖可以通过 `Employee` 表上的插入和更新触发器来强制执行。

正如这些示例所示，反规范化可以加速查询，但可能会减慢更新。因此，存在性能权衡。一般来说，除非这是获得所需性能的唯一途径，否则不要进行反规范化。如果你决定进行反规范化，并且数据库将用于更新，那么请确保通过编写相关约束来控制反规范化。

现实世界的应用程序有时会使用非常糟糕的数据库设计。特别是，新手建模者引入不受控冗余的情况并不少见（例如，忽略上述反规范化模式中的成对子集约束和嵌入式函数依赖）。下一节将讨论一个重构示例，说明（除其他事项外）如何通过应用概念建模技术来改进此类糟糕的设计。

如果你使用的是对象关系或面向对象 DBMS，你可以选择使用复杂类型反规范化为 NF²。例如，SQL:1999 及以后版本允许将数组类型和行类型用作列，它们本身可以作为外层列使用的数组或行结构的组件进行嵌套。SQL:2003 及以后版本支持多重集。回顾前面章节中的 `Voter` 表示例。一些 DBMS 已经支持这些集合类型。这为你提供了更广泛的映射选择，需要审慎使用。

作为一个简单示例，图 14.76(a) 使用两个规范化表来建模关于书籍的详细信息，使用 `position` 列显式存储每位作者在书籍作者列表中的位置。一本书最多允许 10 位作者，其中一些或全部可能未被记录。

![图 14.76 使用 (a) 规范化表或 (b) NF² 表建模作者列表。](img/f14-76-9780443237904.jpg)

通过对作者列表使用数组值列，图 14.76(b) 中的反规范化表方案允许在一个表中捕获所有详细信息。尽管此解决方案似乎更可取，但需要额外小心来强制执行约束。例如，数组中的条目必须唯一。最佳选择取决于应用程序的查询/更新模式。例如，规范化解决方案使列出给定作者的所有书籍变得更容易。

在表设计中使用集合类型时需要格外小心，尤其是在约束实施方面。我们将在后面的章节中对此多做几句说明。鉴于商业 DBMS 目前缺乏统一的方法来处理此类对象-关系扩展，我们在此不再赘述对象-关系 DBMS。

除了反规范化之外，一种称为 `fragmentation`（分片/碎片化）的技术常用于提升超大表的性能。例如，一个包含全美数据的 `PhoneBook` 表将包含数亿行记录。为了提高速度，我们可以将该表分区为 50 个较小的表，每个州一个（如有需要，可进一步划分为更小的区域）。这些较小的表具有相同的结构，表名本身提供了州的信息。

如果这个过程听起来耳熟，那不足为奇。这只是谓词特化的一个例子，正如本章前面所讨论的。无论如何，如果你只想查询或更新某个州的电话详情，可以直接在该州的表上操作。这比在全国性的大表上操作性能好得多。如果你需要同时处理多个州的数据，可以基于这些小表的并集创建一个视图。

某些 DBMS 能够使此类视图获得良好的性能。例如，如果在每个表中包含一个 `statecode` 列，并添加一个检查约束以确保 `statecode` 正确，SQL Server 就可以在并集视图中利用此信息，仅考虑查询中提到的那些州所对应的基表。关于基于按月分区交易数据的此技术的详细讨论，请参见 Seidman (2000)。

物理优化技术在不同 DBMS 间差异很大。例如，Oracle 的 `materialized view`（物化视图）支持与 Microsoft SQL Server 的 `indexed views`（索引视图）支持有所不同。不同系统支持不同种类的 `indexing schemes`（索引方案）（如聚簇索引、哈希表），甚至 Microsoft SQL Server 还提供了一个调优向导，可基于大量事务样本做出最佳索引选择。针对您特定 DBMS 的详细物理优化建议，应可在其在线文档中找到。

## 14.8 重构工程

虽然概念建模是开发新应用的最佳方法，但它也可用于重塑现有系统，以更好地满足需求。更换或修订（可能是剧烈地）现有信息系统主要有三个原因。

首先，当前系统可能提供了一个 `incorrect`（不正确）的 UoD 模型，要么是因为 `inaccurate`（不准确）（信息错误），要么是因为 `incomplete`（不完整）（信息缺失）。错误或缺失的事实类型、约束和导出规则可能源于最初的糟糕建模。例如，模式可能断言行星绕月球运行、允许一个人拥有多个出生日期，或用一个忽略闰年多出一天的简单公式来推导年龄。

如果模型未能跟上 UoD 的变化，也会出现此类错误。例如，一个基于七点数字评分制记录学业成绩的系统，如果评分方案改为五级字母等级，就会过时。

其次，现有系统可能 `inefficient`（低效）。它可能太慢（例如，查询需要太多的表连接）、太大（例如，过多的空值占用空间），或难以演进（例如，过时的规则硬编码在程序代码中，而非建模为表中的数据）。也许硬件平台本身已过时需要更换，或者外部界面对用户来说很别扭。

最后，现有系统可能 `unclear`（不清晰）。这也使其难以维护或演进。如今现存的许多遗留系统是在逻辑层面甚至物理层面设计的，并未为其制定概念模式。它们可能完全用 3GL（第三代语言）开发，没有底层设计方法，文档极少或质量差，且充满了误导性或晦涩难懂的标识符。

通常，这三个原因的组合会导致信息系统需要进行 `reengineered`（重构/再造）或重组，以使其所有者（如公司）在当今的市场中保持竞争力。公司甚至可能重构其经营业务的方式。尽管重组需求有时被用作裁员的借口，但对这一需求的创造性回应可以显著提升业务质量和效率及其支持信息系统。在此，我们仅探讨数据库系统重构的问题。该过程可分为四个阶段，如 图 14.77 所示。

![图 14.77 数据库重构的四个步骤。](img/f14-77-9780443237904.jpg)

图 14.77 数据库重构的四个步骤。

第一阶段，`conceptualization`（概念化）或 `reverse engineering`（逆向工程），涉及从原始数据库开发应用的初始概念模式。这可以通过将 CSDP 应用于数据库来完成，将其视为一组输出报表。大部分口语化阶段通常很简单，因为表是最容易解释的输出报表类型。通常，数据库至少有一个不完整的逻辑模式可用，该模式中的约束（如主键和外键约束）可用于以相当自动化的方式帮助推导出一些约束。

如果数据库不是关系型的，某些表间连接可能需要口语化为事实类型。通常，在领域专家的协助下，会识别出一些未被指定的额外约束。

第二阶段，`transformation`（转换），涉及修改原始概念模式，以适应原始数据库中未建模的 UoD 变化，和/或优化概念模式（如前几节所述）。

第三阶段，`mapping`（映射）或 `forward engineering`（正向工程），带我们进入逻辑模式。如果要使用关系数据库系统，可使用 Rmap 过程来完成此步骤。第四阶段，`data migration`（数据迁移），将原始数据库中存储的事实复制到新数据库。这涉及转换和复制，因为某些涉及的事实类型将被分组到不同的表结构中（回顾 第 14.1 节 中的患者数据示例）。如果最后两个阶段更新的是原始数据库（而非仅生成新数据库），整个重构过程称为往返工程或简称“往返工程”。

### 重构过程概述

重构过程的大部分可以实现自动化，特别是如果在第 1 阶段提供了非常详细的数据库模式。然而，也需要人工交互以确保结果完整且优雅。虽然我们的讨论仅限于逻辑层和概念层，但重构应用程序还涉及外部层（例如，修订用户界面）和物理层（例如，重新调优）的工作。
