
在为 `n` 个客户端托管聊天会话时，该程序运行 `2*n+2` 个并发通信的 goroutine，却不需要任何显式的锁操作（§9.2）。`clients` map 被限制在单个 goroutine（即 broadcaster）中，因此无法被并发访问。由多个 goroutine 共享的变量只有通道和 `net.Conn` 的实例，它们都是*并发安全*的。我们将在下一章更多地讨论封闭、并发安全以及跨 goroutine 共享变量的影响。

**练习 8.12：** 让 broadcaster 在每个新客户端到达时宣布当前的客户端集合。这要求 `clients` 集合以及 `entering` 和 `leaving` 通道也记录客户端名称。

**练习 8.13：** 让聊天服务器断开空闲客户端的连接，例如那些在过去五分钟内未发送任何消息的客户端。提示：在另一个 goroutine 中调用 `conn.Close()` 会解除活动的 `Read` 调用阻塞，例如 `input.Scan()` 所做的调用。

**练习 8.14：** 更改聊天服务器的网络协议，使每个客户端在进入时提供其名称。在用发送者身份为每条消息添加前缀时，使用该名称代替网络地址。

**练习 8.15：** 任何客户端程序若未能及时读取数据，最终都会导致所有客户端卡死。修改广播器，使其在客户端写入器未准备好接收消息时，跳过该消息而非等待。或者，为每个客户端的传出消息通道增加缓冲，以便大多数消息不被丢弃；广播器应对此通道使用非阻塞发送。

# 9. 共享变量的并发

在上一章中，我们展示了几个使用 goroutine 和 channel 以直接自然方式表达并发的程序。然而，在这样做的过程中，我们略过了程序员编写并发代码时必须牢记的许多重要且微妙的问题。

在本章中，我们将更深入地探讨并发的机制。特别是，我们将指出在多个 goroutine 间共享变量所带来的一些问题、识别这些问题的分析技术以及解决它们的模式。最后，我们将解释 goroutine 与操作系统线程之间的一些技术差异。

## 9.1 竞态条件

在顺序程序中，即只有一个 goroutine 的程序，程序的步骤按照由程序逻辑决定的熟悉执行顺序发生。例如，在一系列语句中，第一条发生在第二条之前，依此类推。在拥有两个或更多 goroutine 的程序中，每个 goroutine 内部的步骤按熟悉的顺序发生，但通常我们无法知道一个 goroutine 中的事件 `x` 是发生在另一个 goroutine 中的事件 `y` 之前、之后，还是与其同时发生。当我们无法确信某个事件*先于*另一个事件发生时，则称事件 `x` 和 `y` 是*并发*的。

考虑一个在顺序程序中能正确工作的函数。如果该函数在被并发调用时（即从两个或更多 goroutine 调用且无额外同步）仍能继续正确工作，则称该函数是*并发安全*的。我们可以将这一概念推广到一组协作函数，例如某个特定类型的方法和操作。如果一个类型的所有可访问方法和操作都是并发安全的，则该类型是并发安全的。

我们可以在不使程序中每个具体类型都并发安全的情况下，使程序并发安全。事实上，并发安全类型是例外而非规则，因此只有当其类型的文档说明这样做是安全时，你才应并发访问变量。我们通过将大多数变量*限制*在单个 goroutine 中，或者维护更高层级的*互斥*不变量，来避免对它们的并发访问。我们将在本章中解释这些术语。

相反，导出的包级函数*通常*期望是并发安全的。由于包级变量无法被限制在单个 goroutine 中，修改它们的函数必须强制实施互斥。

函数在并发调用时可能无法工作的原因有很多，包括死锁、活锁和资源饥饿。我们没有空间讨论所有这些，因此将重点关注最重要的一个：**竞态条件**。

竞态条件是指在多个 goroutine 的操作以某些交错顺序执行时，程序无法给出正确结果的情况。竞态条件具有隐蔽性，因为它们可能潜伏在程序中并不频繁出现，也许仅在高负载下，或使用特定编译器、平台或架构时才显现。这使得它们难以复现和诊断。

通常通过金钱损失的隐喻来解释竞态条件的严重性，因此我们将以一个简单的银行账户程序为例。

点击此处查看代码图像

```go
// Package bank implements a bank with only one account.

package bank

var balance int

func Deposit(amount int) { balance = balance + amount }

func Balance() int { return balance }
```

（我们本可以将 `Deposit` 函数体写为 `balance += amount`，这二者等价，但较长的形式将简化解释。）

对于这样一个简单的程序，我们一眼就能看出，对 `Deposit` 和 `Balance` 的任何调用序列都会给出正确答案，即 `Balance` 将报告之前所有存款金额的总和。然而，如果我们不是按顺序而是并发地调用这些函数，`Balance` 就不再保证给出正确答案。考虑以下两个 goroutine，它们代表联名银行账户上的两笔交易：

点击此处查看代码图像

```go
// Alice:

go func() {
    bank.Deposit(200)                // A1
    fmt.Println("=", bank.Balance()) // A2
}()

// Bob:

go bank.Deposit(100)                 // B
```

Alice 存入 200 美元，然后查询余额，而 Bob 存入 100 美元。由于步骤 `A1` 和 `A2` 与 `B` 并发发生，我们无法预测它们发生的顺序。直觉上，似乎只有三种可能的顺序，我们称之为“Alice 优先”、“Bob 优先”和“Alice/Bob/Alice”。下表显示了每一步之后 `balance` 变量的值。带引号的字符串代表打印出的余额单。

点击此处查看代码图像

```
Alice 优先              Bob 优先        Alice/Bob/Alice

          0                      0                      0

  A1    200              B     100              A1    200

  A2 "= 200"             A1    300              B     300

  B     300              A2 "= 300"             A2 "= 300"
```

在所有情况下，最终余额都是 300 美元。唯一的变化在于 Alice 的余额单是否包含 Bob 的交易，但客户无论哪种方式都会满意。

但这种直觉是错误的。存在第四种可能的结果，即 Bob 的存款发生在 Alice 存款的中间，在读取了余额（`balance + amount`）之后、但更新余额（`balance = ...`）之前，导致 Bob 的交易丢失。这是因为 Alice 的存款操作 `A1` 实际上是两个操作的序列，一个读和一个写；称它们为 `A1r` 和 `A1w`。以下是有问题的交错执行：

点击此处查看代码图像

```
数据竞争

         0

A1r      0          ... = balance + amount

B      100

A1w    200          balance = ...

A2  "= 200"
```

在 `A1r` 之后，表达式 `balance + amount` 评估为 200，因此尽管中间插入了存款，`A1w` 期间写入的值仍是 200。最终余额只有 200 美元。银行以 Bob 的损失为代价多赚了 100 美元。

该程序包含一种特定类型的竞态条件，称为*数据竞争*。每当两个 goroutine 并发访问同一变量，且至少其中一次访问是写入时，就会发生数据竞争。

如果数据竞争涉及的变量类型大于单个机器字（如接口、字符串或切片），情况会变得更糟。以下代码并发地用两个不同长度的切片更新 `x`：

点击此处查看代码图像

```go
var x []int

go func() { x = make([]int, 10) }()

go func() { x = make([]int, 1000000) }()

x[999999] = 1 // 注意：未定义行为；可能导致内存损坏！
```

最后一条语句中 `x` 的值未定义；它可能是 nil，也可能是长度为 10 的切片，或者是长度为 1,000,000 的切片。但请回顾一下，切片由三部分组成：指针、长度和容量。如果指针来自第一次对 `make` 的调用，而长度来自第二次，`x` 就会变成一个“怪胎”，即一个名义长度为 1,000,000 但底层数组只有 10 个元素的切片。在这种情况下，向元素 999,999 存值会破坏一个任意的遥远内存位置，其后果无法预测，也难以调试和定位。这种语义雷区被称为 *未定义行为*，C 语言程序员对此深有体会；幸运的是，在 Go 语言中它很少像在 C 语言中那样麻烦。

即使“并发程序是几个顺序程序的交织”这一概念也是一种错误的直觉。正如我们将在 9.4 节 中看到的，数据竞争可能产生更奇怪的结果。许多程序员——甚至一些非常聪明的程序员——偶尔会为其程序中已知的数据竞争辩护：“互斥的成本太高了”，“这段逻辑只是用于日志记录”，“我不介意丢失一些消息”，等等。在特定编译器和平台上没有出现问题，可能会给他们带来虚假的信心。一个好的经验法则是 *不存在良性的数据竞争*。那么我们如何在程序中避免数据竞争呢？

我们将重复这个定义，因为它非常重要：每当两个 goroutine 并发访问同一变量，且至少其中一次访问是写入时，就会发生数据竞争。根据这个定义，避免数据竞争有三种方法。

第一种方法是不写入该变量。请看下面的 map，它会在每个键首次被请求时惰性填充。如果 `Icon` 是顺序调用的，程序运行正常，但如果 `Icon` 是并发调用的，则会发生对 map 的数据竞争。

点击此处查看代码图像

```go
var icons = make(map[string]image.Image)

func loadIcon(name string) image.Image

// 注意：非并发安全！

func Icon(name string) image.Image {
    icon, ok := icons[name]
    if !ok {
        icon = loadIcon(name)
        icons[name] = icon
    }
    return icon
}
```

如果我们在创建额外的 goroutine 之前，用所有必要的条目初始化 map，并且此后不再修改它，那么任意数量的 goroutine 都可以安全地并发调用 `Icon`，因为每个 goroutine 只是读取 map。

点击此处查看代码图像

```go
var icons = map[string]image.Image{
    "spades.png":   loadIcon("spades.png"),
    "hearts.png":   loadIcon("hearts.png"),
    "diamonds.png": loadIcon("diamonds.png"),
    "clubs.png":    loadIcon("clubs.png"),
}

// 并发安全。

func Icon(name string) image.Image { return icons[name] }
```

在上面的示例中，`icons` 变量在包初始化期间赋值，这 *发生在* 程序的 `main` 函数开始运行 *之前*。一旦初始化完成，`icons` 就不再被修改。从不修改或不可变的数据结构天生就是并发安全的，不需要同步。但显然，如果更新是必不可少的（如银行账户），我们就无法使用这种方法。

避免数据竞争的第二种方法是避免从多个 goroutine 访问该变量。这是上一章许多程序采用的方法。例如，并发网页爬虫（§8.6）中的主 goroutine 是唯一访问 `seen` map 的 goroutine，聊天服务器（§8.10）中的 `broadcaster` goroutine 是唯一访问 `clients` map 的 goroutine。这些变量被 *限制* 在单个 goroutine 中。

由于其他 goroutine 无法直接访问该变量，它们必须使用信道向限制该变量的 goroutine 发送请求，以查询或更新该变量。这正是 Go 语言格言“不要通过共享内存来通信；而要通过通信来共享内存”的含义。使用信道请求来协调对受限变量的访问的 goroutine 被称为该变量的 *监控 goroutine*。例如，`broadcaster` goroutine 监控对 `clients` map 的访问。

下面是将 `balance` 变量限制在名为 `teller` 的监控 goroutine 中的银行示例重写版本：

点击此处查看代码图像
gopl.io/ch9/bank1

```go
package bank

var deposits = make(chan int) // 发送存款金额
var balances = make(chan int) // 接收余额

func Deposit(amount int) { deposits <- amount }
func Balance() int       { return <-balances }

func teller() {
    var balance int // balance 限制在 teller goroutine 中
    for {
        select {
        case amount := <-deposits:
            balance += amount
        case balances <- balance:
        }
    }
}

func init() {
    go teller() // 启动监控 goroutine
}
```

即使一个变量不能在其整个生命周期内被限制在单个 goroutine 中，限制仍然可能是解决并发访问问题的办法。例如，在流水线中通过信道将变量的地址从一个阶段传递到下一个阶段，从而在 goroutine 间共享变量，这是很常见的。如果流水线的每个阶段在将变量发送到下一阶段后不再访问它，那么对该变量的所有访问就是顺序的。实际上，该变量先被限制在流水线的一个阶段，然后被限制在下一个阶段，依此类推。这种规范有时称为 *串行限制*。

在下面的示例中，`Cake` 先被串行限制在 `baker` goroutine 中，然后被限制在 `icer` goroutine 中：

点击此处查看代码图像

```go
type Cake struct{ state string }

func baker(cooked chan<- *Cake) {
    for {
        cake := new(Cake)
        cake.state = "cooked"
        cooked <- cake // baker 再也不碰这个 cake 了
    }
}

func icer(iced chan<- *Cake, cooked <-chan *Cake) {
    for cake := range cooked {
        cake.state = "iced"
        iced <- cake // icer 再也不碰这个 cake 了
    }
}
```

避免数据竞争的第三种方法是允许多个 goroutine 访问该变量，但同一时刻只能有一个。这种方法称为 *互斥*，是下一节的主题。

**练习 9.1：** 向 `gopl.io/ch9/bank1` 程序添加一个 `Withdraw(amount int) bool` 函数。其结果应指明交易是成功还是因资金不足而失败。发送给监控 goroutine 的消息必须同时包含取款金额和一个新信道，监控 goroutine 可通过该信道将布尔结果发回给 `Withdraw`。

## 9.2 互斥：`sync.Mutex`

在 8.6 节 中，我们使用带缓冲的信道作为 *计数信号量*，以确保不超过 20 个 goroutine 同时发起 HTTP 请求。利用同样的思路，我们可以使用容量为 1 的信道，确保同一时刻最多只有一个 goroutine 访问共享变量。只能计数到 1 的信号量称为 *二元信号量*。

点击此处查看代码图像
gopl.io/ch9/bank2

```go
var (
    sema    = make(chan struct{}, 1) // 一个保护 balance 的二元信号量
    balance int
)

func Deposit(amount int) {
    sema <- struct{}{} // 获取令牌
    balance = balance + amount
    <-sema // 释放令牌
}

func Balance() int {
    sema <- struct{}{} // 获取令牌
    b := balance
    <-sema // 释放令牌
    return b
}
```

这种*互斥*模式非常有用，以至于 `sync` 包中的 `Mutex` 类型直接支持它。其 `Lock` 方法获取令牌（称为*锁*），而 `Unlock` 方法释放它：

点击此处查看代码图片
gopl.io/ch9/bank3

```go
import "sync"

var (
    mu      sync.Mutex // 保护 balance
    balance int
)

func Deposit(amount int) {
    mu.Lock()
    balance = balance + amount
    mu.Unlock()
}
```
