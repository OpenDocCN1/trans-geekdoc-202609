### 特权程序

在 UNIX 和 Linux 系统中，普通用户无法编辑密码文件（`/etc/passwd`）和影子文件（`/etc/shadow`），它们分别存储账户信息和加密密码。但用户需要能够更改他们的密码（从而更改这些文件）。如果他们不能（直接）更改这些文件，如何更改密码呢？

答案是 `setuid`（设置用户 ID）程序。`Setuid` 是一种 Linux 和 UNIX 文件权限，它使可执行文件以文件所有者的权限运行，而不是以运行用户的权限运行。`Setgid`（设置组 ID）程序以文件所属组的权限运行。

图 4.15 显示了用于设置和更改密码的 Linux 命令 `/usr/bin/passwd` 的权限。它是 `setuid` root（该文件由 root 用户所有，且所有者的执行位设置为“s”，表示 `setuid`），这意味着它以 root（超级用户）权限运行，无论运行用户是谁。

![Fig. 4.15 Linux setuid root program /usr/bin/passwd.](img/f04-15-9780443187346.jpg)

图 4.15 Linux `setuid` root 程序 `/usr/bin/passwd`。

“passwd”程序以 root 身份运行，允许任何用户更改其密码，从而更改 `/etc/passwd` 和 `/etc/shadow` 的内容。`Setuid` 程序必须经过严格审查以发现安全漏洞：攻击者可能会试图欺骗 `passwd` 命令以修改其他文件。应密切监控系统上所有 `setuid` 和 `setgid` 程序的完整性。

### 虚拟化、云计算和分布式计算

虚拟化和分布式计算彻底改变了计算世界，给应用程序、服务、系统数据和数据中心带来了彻底的变革。昨天的最佳实践可能不再适用。当数据在云端时，DMZ 在哪里？你的 NIDS 能否监控单个主机上从一个客户机发送到另一个客户机的数据？你的物理防火墙还重要吗？

#### 虚拟化

*虚拟化*在操作系统和底层计算机硬件之间增加了一个软件层。这允许多个“客户机”操作系统在一台物理“主机”计算机上同时运行。流行的透明虚拟化产品包括 VMware、QEMU 和 Xen。

虚拟化有两种基本类型：透明虚拟化（有时称为完全虚拟化）和半虚拟化。透明虚拟化将标准操作系统（如 Windows 11 或 Ubuntu Linux 22.04）作为虚拟客户机运行。无需更改客户机操作系统。半虚拟化运行专门修改过的操作系统，具有修改过的内核系统调用。半虚拟化可能更高效，但需要更改客户机操作系统。对于闭源操作系统（如 Microsoft Windows 系列）来说，这可能是不可能的。

##### 管理程序

虚拟化安全的关键在于*管理程序*，它控制虚拟客户机与主机硬件之间的访问。类型 1 管理程序（也称为裸金属）是直接运行在主机硬件上的操作系统的一部分。类型 2 管理程序作为普通操作系统（如 Windows 10）上的应用程序运行。例如：VMware ESX 是类型 1 管理程序，VMware Workstation 是类型 2。

许多虚拟化漏洞利用针对管理程序，包括主机与客户机之间、客户机与客户机之间共享的由管理程序控制的资源。这些包括剪切粘贴、共享驱动器和共享网络连接。

##### 虚拟化优势

虚拟化提供了许多优势，包括降低整体硬件成本、硬件整合，以及降低电力和冷却需求。快照允许管理员创建操作系统镜像，只需点击鼠标即可恢复，使备份和恢复变得简单快捷。测试新操作系统、应用程序和补丁可以非常简单。虚拟客户机集群比直接运行在硬件上的操作系统集群要简单得多。

##### 虚拟化安全问题

虚拟化软件复杂且相对较新。如前所述，复杂性是安全的敌人：虚拟化软件的极高复杂性可能导致安全问题。

将多个客户机合并到一台主机上也可能引发安全问题。虚拟化不能替代防火墙：切勿将具有不同安全需求的客户机（如 DMZ 和内部）合并到一台主机上。虚拟化逃逸（称为 VMEscape，攻击者从一个客户机利用主机操作系统或另一个客户机）的风险是近期研究的热门话题。Network World 报道：“在 Cisco 的企业 NFV 基础设施软件 (NFVIS) 中发现了多个漏洞。最严重的漏洞可能允许攻击者从客户机虚拟机 (VM) 逃逸到主机，Cisco 披露。另外两个问题涉及允许恶意行为者注入在根级别执行的命令，以及允许远程攻击者将主机的系统数据泄露给 VM” [[15]](#Ch004_107-223_B9780443187346000076_2.xhtml#bb0080)。已知的虚拟化逃逸漏洞已修补，但新问题可能会出现。

许多基于网络的安全工具（如网络入侵检测系统）可能因虚拟化而“失明”。连接到物理 SPAN 端口或分流器的传统 NIDS 无法看到同一主机上从一个客户机传递到另一个客户机的流量。NIDS 厂商开始提供虚拟 IDS 产品，这些产品作为软件运行在主机上，能够检查主机-客户机和客户机-客户机流量。防火墙也正在发生类似的从物理到虚拟的转变。

#### 云计算

##### 公有云计算

公有云计算将 IT 基础设施、存储或应用程序外包给第三方提供商。云也意味着计算资源的地理多样性。云计算的目标是让大型提供商利用其规模经济，向其他公司提供计算资源，这些公司通常根据使用量为这些服务付费。

##### 云服务层级

云提供商提供的三种常见服务层级是**基础设施即服务**、**平台即服务**和**软件即服务**。

*   **基础设施即服务**提供完整的虚拟化操作系统，由客户从操作系统层面开始进行配置。
*   **平台即服务**提供预配置的操作系统，由客户配置应用程序。
*   **软件即服务**从操作系统到应用程序均已完全配置，客户只需使用该应用程序即可。

在以上三种情况下，云提供商均负责管理硬件、虚拟化软件、网络、备份等。各类型的典型示例请参见表 4.2。

###### 表 4.2 云服务层级示例

| 类型 | 示例 |
| :--- | :--- |
| 基础设施即服务 | Linux 服务器托管 |
| 平台即服务 | Web 服务托管 |
| 软件即服务 | Web 邮件 |

##### 云部署模型

**私有云**存放单个组织的数据，可由第三方运营，也可由组织自行运营。**政府云**旨在将数据和资源在地理上限制在一个国家的边界内，专为相应国家的政府设计。

##### 优势与安全考量

云计算的优势包括降低前期资本支出、降低维护成本、提供稳健的服务级别以及总体运营成本节约。

从安全角度来看，利用公有云计算服务需要严格的服务级别协议，并了解新的风险来源。一个担忧是多个组织的客户机运行在同一宿主机上。一家云客户的遭受攻破可能导致其他客户也被攻破。

此外，许多云提供商提供预配置的系统镜像，这可能因不安全的配置而引入风险。例如，设想一个包含操作系统、Web 服务和博客软件且均已预配置的博客服务镜像。与预配置镜像相关的任何漏洞都可能给使用该镜像的每个组织带来风险。

###### 实例学习：预置镜像

2011 年，亚马逊向部分 **EC2 (Elastic Cloud Compute，弹性云计算)** 客户发送邮件，警告称：“我们最近注意到，美国东部区域的一个公共 **AMI** 附带分发了一个 SSH 公钥，这将允许发布者以 root 身份登录” [[16]](#Ch004_107-223_B9780443187346000076_2.xhtml#bb0085)。

**AMI** 代表 **Amazon Machine Image（亚马逊机器镜像）**，即预配置的虚拟客户机。TippingPoint 的 DVLabs 描述了发生的情况：“受感染的镜像由 Ubuntu 10.4 服务器组成，运行着 Apache、MySQL 和 PHP……该镜像似乎是在……6 个月前发布的，而我们直到现在才听说这个问题。究竟发生了什么？一位名为 guru 的 EC2 用户创建了这个镜像，其中包含他最常用的软件栈，然后将其发布到 Amazon AMI 社区。如果不是一个简单的事实，这一切本来都很好。该镜像在发布时仍然保留着他的 SSH 密钥。这意味着镜像发布者（本案中为 guru）可以作为 root 用户登录任何运行其镜像的服务器实例。密钥被遗留在 `/root/.ssh/authorized_keys` 和 `/home/ubuntu/.ssh/authorized_keys` 中。我们将生成的镜像称为‘官方翻新’。发布者声称这纯属意外，只是其缺乏经验的结果。无论这说法是否属实，该事件暴露了 EC2 社区内的一个重大安全漏洞” [[16]](#Ch004_107-223_B9780443187346000076_2.xhtml#bb0085)。

组织必须分析与预配置云系统相关的风险，并考虑从“基础”开始配置系统的选项，即从基础操作系统着手。

组织在与云计算提供商签订合同前，还应协商具体权利。这些权利包括审计权、漏洞评估权，以及对放置在云中的数据和系统进行渗透测试（包括电子和物理测试）的权利。

最后，你知道你的数据在哪里吗？公有云可能会将数据移动到任何国家，可能超出组织所在国的司法管辖范围。例如，基于美国的法律，如**《健康保险流通与责任法案》**或**《格雷姆-里奇-比利雷金融服务现代化法案》**，在美国境外不生效。在这些情况下，应考虑使用私有云或政府云。

##### 共享责任

在云计算出现之前的世界里，责任划分更简单。正如我们稍后将讨论的，**分界点**描述了客户（其路由器及其后方的所有设备）和 ISP（ISP 的路由器及其后方的所有设备）各自的责任。共享责任实际上就是连接这两个路由器的一根电缆。“责任”描述了谁负责配置、维护和保护分界点两侧的系统。它也反映了对可用性（正常运行时间）和法律责任的双重承担。

#### 微服务、容器和无服务器

云计算革命持续发展并演化出新技术，包括微服务、云和无服务器。这些技术的目标之一是降低计算成本。最初我们有运行在裸机硬件上的计算机。随后虚拟化技术允许多个操作系统在一个管理程序上运行。云为虚拟化带来了规模。每一步都降低了成本。这一过程随着微服务、容器和无服务器的出现而继续，我们接下来将进行讨论。

##### 微服务

想象一家 20 年前在线销售玩具的公司。一年中的大部分时间使用量（相对）较低，但在促销和圣诞节期间会激增。该公司日常运营需要 100 台服务器。在高峰期（圣诞购物季），使用量会激增，公司需要 1000 台服务器来满足需求。

直接构建在硬件上（虚拟化之前）将非常昂贵：900 台服务器将在大半年内闲置。虚拟化改善了情况，但公司仍需要一个能运行 1000 台虚拟机的管理程序。云提供了真正的突破；玩具公司可以利用 **Amazon AWS**、**Microsoft Azure**、**Google Compute**（以及许多其他云提供商）按需配置虚拟系统，并在高峰期过后将其关闭。

###### 微服务架构

微服务在降低成本的同时，提供了额外的扩展机会。服务器在历史上是单体式的：一台服务器提供一系列服务。以上面的玩具公司为例，每台服务器可能提供一系列服务：身份验证、库存、搜索、购物车、信用卡验证、配送等。微服务通过 API（应用程序编程接口）将这些服务拆分出来，并使用容器和无服务器等技术来提供所需功能。Amazon 对微服务的描述如下：

> 采用单体架构时，所有进程都紧密耦合并作为单个服务运行。这意味着，如果应用程序的某个进程遇到需求激增，则必须扩展整个架构。随着代码库的增长，添加或改进单体应用程序的功能变得更加复杂。这种复杂性限制了实验，并使实施新想法变得困难。单体架构增加了应用程序可用性的风险，因为许多依赖且紧密耦合的进程增加了单个进程故障的影响。
>
> 采用微服务架构时，应用程序作为独立组件构建，每个应用程序进程作为一个服务运行。这些服务通过定义良好的接口使用轻量级 API 进行通信。服务是为业务能力而构建的，每个服务执行单一功能。因为它们是独立运行的，所以每个服务都可以更新、部署和扩展，以满足应用程序特定功能的需求 [[18]](#Ch004_107-223_B9780443187346000076_2.xhtml#bb0095)。

##### 容器

容器是一项（相对）较老但持续改进的技术。它们源自 BSD 的“chroot”（更改根目录）功能，该功能将进程锁定在一个目录中。该进程（如 Bind 域名服务器守护进程）只能访问其目录中的文件，而无法访问目录外部的文件。例如：如果 Bind 被 chroot 到 `/var/bind`，它就无法读取该目录及其子目录（如 `/var/bind/conf`）之外的任何内容。这样做是为了将受损服务对操作系统其余部分的风险降至最低：例如，无法访问 `/etc/passwd` 和 `/etc/shadow` 等文件。

BSD jails（BSD 监狱）建立在 chroot 概念之上，同时也隔离了网络：例如，每个 jail 都有自己的 IP 地址。同一系统上需要传输数据的两个 jail 需要通过网络进行通信。

BSD 操作系统称此概念为 jail，而 Linux 使用术语 container（容器）。Docker 是最流行的容器技术之一，专注于大规模编排。Docker 对容器的描述如下：

> 容器是一种标准的软件单元，它将代码及其所有依赖项打包在一起，以便应用程序能够从一个计算环境快速可靠地运行到另一个计算环境。Docker 容器镜像是一种轻量级、独立、可执行的软件包，包含运行应用程序所需的一切：代码、运行时、系统工具、系统库和设置 [[19]](#Ch004_107-223_B9780443187346000076_2.xhtml#bb0100)。

###### 容器与虚拟化

您可能会想：容器与虚拟化有何不同？关键区别在于：每个虚拟系统运行自己的内核。运行三台虚拟机的管理程序意味着有四个内核在运行：一个用于管理程序，每个 VM 一个。运行三个容器的宿主系统意味着只有一个内核在运行：宿主系统的内核。每个容器也使用宿主系统的内核。这意味着容器比 VM 需要更少的资源，但也意味着它们（从安全角度来看）不如 VM 那样隔离。图 4.17 来自美国能源部阿贡国家实验室，展示了容器和虚拟机之间的区别 [[20]](#Ch004_107-223_B9780443187346000076_2.xhtml#bb0105)。

##### 无服务器

无服务器是一个容易让人误解的技术名称：它确实使用服务器，但这些服务器属于别人。“别人的服务器”是个更好的名字，尽管承认不那么朗朗上口。它也被称为函数即服务，这更准确。无服务器简单来说就是将代码发送到另一台服务器，由其返回结果。流行的无服务器技术包括 AWS（Amazon Web Services）Lambda、Azure Functions 和 Google Cloud Functions。

下面是一个简单的“Hello World!”风格的函数 [[21]](#Ch004_107-223_B9780443187346000076_2.xhtml#bb0110)，使用 Python 和 JSON（JavaScript 对象表示法）。请注意，Python 编程和 JSON 结构不在考试范围内；此处仅用于提供无服务器代码的简单示例。

```
import json

print('Loading function')
def lambda_handler(event, context):
    print("value1 = " + event['key1'])
    print("value2 = " + event['key2'])
    print("value3 = " + event['key3'])
```

匹配的 JSON：

```
{
    "key1": "Pass",
    "key2": "the",
    "key3": "CISSP!"
}
```

图 4.18 显示了通过 AWS Lambda 控制台输出的结果。

![图 4.18 无服务器输出。](img/f04-18-9780443187346.jpg)

图 4.18 无服务器输出。

我们已经在自己的 CPU 上运行此类函数几十年了。在这种情况下，函数被发送到 AWS，由 AWS 的 CPU 执行该函数并返回结果。AWS 按执行该函数所需的 CPU 周期收费。这比在物理主机或虚拟机上运行代码高效得多（物理主机或虚拟机上运行着数百个其他进程并消耗 CPU 周期），也比容器高效（容器使用的 CPU 周期比物理主机或 VM 少，但比无服务器多）。

##### 高性能计算（HPC）和网格计算

高性能计算（HPC）和网格计算都旨在通过大量计算机实现高计算性能。关键区别在于：高性能计算系统（也称为超级计算机）利用单一位置的并行计算机（通常都在处理同一任务），而网格计算则利用大量分布式计算机（处理各种任务）。

HPC 系统利用海量 CPU 实现每秒千万亿次浮点运算（FLOPs）。常见的 HPC 应用包括 DNA 测序、自动驾驶、天气预测等。HPC 系统的主要目的是通过规模经济实现性能提升。HPC 系统的一个关键安全问题是确保数据完整性在整个处理过程中得以维护。HPC 系统通常会利用一定程度的共享内存进行操作。如果管理不当，这种共享内存可能会暴露潜在的竞争条件，从而引入完整性挑战。
