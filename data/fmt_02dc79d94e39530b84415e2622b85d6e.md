
# 构建安全的 ML 管道

在本章中，我们首先将讨论在 Google Cloud Platform 上管理数据的安全策略，涵盖从存储、处理到 ML 模型开发的全过程。我们还将简要介绍如何使用身份和访问管理 (IAM) 最佳实践，为数据科学团队提供对 `Vertex AI` 环境的安全访问。

此外，我们将讨论用于管理敏感数据（如个人身份信息 (PII) 和受保护的健康信息 (PHI)）的 Google Cloud 服务和最佳实践。我们还将介绍一种使用 `Google Cloud Data Loss Prevention (DLP) API` 大规模管理 PII 数据的架构。

## 离线批量预测

当您以批次形式获取数据并运行指向已训练模型的批处理作业以进行离线预测时，您执行的是离线或批量预测。离线或批量处理的一些用例包括推荐、需求预测、细分分析，以及对大批量文本进行分类以确定其所属主题。您可以使用 `Vertex AI batch prediction` 为存储在 `BigQuery` 或 `Google Cloud Storage` 中的数据运行批量预测作业。

## 在线预测

当您向已部署的模型端点发送请求并获得预测响应时，这种预测会近乎实时地发生。这可以是一个部署到 HTTPS 端点的模型，您可以使用微服务架构从 Web 应用程序或移动应用程序调用此端点。在进行 ML 预测时需要近乎实时响应的用例包括实时竞价和对 Twitter 源的实时情感分析。

有两种方式可以进行在线预测，具体说明如下：

### 同步

在这种方式中，调用者会等待，直到从 ML 服务接收到预测，然后再执行后续步骤。您可以使用 `Vertex AI online predictions` 将模型部署为实时 HTTPS 端点。您还可以使用 `App Engine` 或 `GKE` (`Google Kubernetes Engine`) 作为 ML 网关，在从客户端应用程序发送请求之前执行一些特征预处理，如图 5.4 所示。

![FIGURE 5.4 Google Cloud architecture for online prediction](img/c05f004.png)

**图 5.4** 用于在线预测的 Google Cloud 架构

### 异步

在这种方法中，最终用户可能不会直接查询模型端点。最终用户可能会收到通知，或者轮询特征存储或数据存储以实时获取预测。这可以通过以下两种方法发生：

#### 推送

模型生成预测并将它们作为通知推送给最终用户。例如，在欺诈检测中，当识别出潜在的欺诈交易时，如果您想通知其他系统采取行动，则会使用此方法。请参阅图 5.5 以供参考。

#### 轮询

模型生成预测并将它们存储在低延迟读取数据库中，例如 NoSQL 数据存储。最终用户定期轮询数据库以获取可用的预测。一个例子是定向营销，系统会实时检查活跃客户的预测倾向评分，以决定是否发送带有促销或挽留优惠的电子邮件。

### 在模型层面最小化延迟

您需要最小化模型在收到请求时进行预测所需的时间。您可以通过构建更小的模型来最小化延迟，因为它将拥有更少的神经网络层，并且处理预测所需的计算量更少。

您可以使用 Cloud GPU 和 `TPU` 等加速器来提供模型端点服务。通常，只有当您拥有大型深度学习模型和大批次大小时，才会使用 `TPU`。

### 在服务层面最小化延迟

这是您最小化系统在收到请求时提供预测所需时间的地方。这包括将输入特征存储在低延迟读取查找数据存储中，在离线批量评分作业中预计算预测，以及缓存预测。

1.  您在一家在线旅行社工作，该公司还向其他公司出售其网站上的广告位。您被要求预测用户接下来应该看到的最相关网页横幅。安全性对您的公司很重要。模型延迟要求为 `300ms@p99`，库存有数千个网页横幅，您的探索性分析表明导航上下文是一个很好的预测因子。

    您想要实现最简单的解决方案。应该如何配置预测流水线？

    1.  在网站上嵌入客户端，然后在 Vertex AI 平台预测上部署模型。
    2.  在网站上嵌入客户端，在 `App Engine` 上部署网关，然后在 Vertex AI 平台预测上部署模型。
    3.  在网站上嵌入客户端，在 `App Engine` 上部署网关，在 `Cloud Bigtable` 上部署数据库以写入和读取用户的导航上下文，然后在 Vertex AI Prediction 上部署模型。
    4.  在网站上嵌入客户端，在 `App Engine` 上部署网关，在 `Memorystore` 上部署数据库以写入和读取用户的导航上下文，然后在 Google Kubernetes Engine (`GKE`) 上部署模型。

2.  您正在使用 `TensorFlow` 训练一个模型，该模型基于存储在多个 `CSV` 文件中的 1000 亿条记录的结构化数据集。您需要提高输入/输出执行性能。应该怎么做？

    3.  将 `CSV` 文件转换为 `TFRecords` 分片，并将数据存储在 Google Cloud Storage 中。
    4.  将 `CSV` 文件转换为 `TFRecords` 分片，并将数据存储在 Hadoop 分布式文件系统 (`HDFS`) 中。

3.  您是一名数据工程师，正在为基于登录用户信息的电子商务网站产品推荐系统构建 ML 模型。您将使用 `Pub/Sub` 处理传入请求。您想存储结果以进行分析和可视化。应该如何配置流水线？

    `Pub/Sub` -> `预处理(1)` -> `ML 训练/服务(2)` -> `存储(3)` -> Data studio/Looker studio 进行可视化

    1.  `1 = Dataflow`，`2 = Vertex AI 平台`，`3 = Cloud BigQuery`

### 8. 基于 GCS 新数据自动触发 Kubeflow 训练

你与一个数据工程团队合作，该团队开发了一个管道来清理数据集并将其保存在 `Google Cloud Storage` 存储桶中。你已经创建了一个 ML 模型，并希望在新数据可用时立即使用该数据刷新模型。作为 CI/CD 工作流的一部分，你希望在 `Google Kubernetes Engine (GKE)` 上自动运行 `Kubeflow Pipelines` 训练作业。应如何设计此工作流架构？

1.  配置带有 `Dataflow` 的管道，将文件保存在 `Google Cloud Storage` 中。文件保存后，在 `GKE` 集群上启动训练作业。
2.  使用 `App Engine` 创建一个轻量级 Python 客户端，持续轮询 `Google Cloud Storage` 以查找新文件。一旦文件到达，立即启动训练作业。
3.  配置 `Google Cloud Storage` 触发器，在存储桶中有新文件可用时向 `Pub/Sub` 主题发送消息。使用由 `Pub/Sub` 触发的 `Cloud Function` 在 `GKE` 集群上启动训练作业。
4.  使用 `Cloud Scheduler` 按固定时间间隔调度作业。作为作业的第一步，检查 `Google Cloud Storage` 存储桶中对象的时间戳。如果自上次运行以来没有新文件，则中止作业。
