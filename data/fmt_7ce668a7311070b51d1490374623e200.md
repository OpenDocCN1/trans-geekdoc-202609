模糊器（Fuzzers）并不总是从零开始生成随机输入。众所周知，纯随机生成是测试系统的一种低效方法。相反，它们通常从一个非常接近正常的输入开始，然后进行大量细小的修改，以观察哪些修改更能有效地暴露漏洞。最终，某个输入会触发目标中的一个有趣状态，此时安全团队需要一种工具来确定漏洞所在以及如何利用该漏洞（如果存在漏洞的话）。这种观测和分析工具通常与模糊器捆在一起，因为没有其中一个，另一个几乎是毫无用处的。

## 压力测试

另一种尝试破坏软件系统的测试类型，是通过创建系统在正常情况下不被预期会遇到的条件来实现的。`压力测试`（Stress testing）通过提出远超软件规划阈值的极端需求，来确定其健壮性。这里的重点是尝试通过创建`DoS`条件来破坏系统的可用性。

最常见的压力测试类型是尝试给系统`过多的`某些东西（例如并发连接或数据）。在开发期间，团队会构建软件以处理特定数量的活动或数据。这种数量可能被指定为非功能性需求，也可能由团队根据经验任意决定。通常，该值是通过衡量或预测系统可能面临的最大负载来确定的。为了根据该值对系统进行压力测试，团队只需在不同条件下超过该值并观察会发生什么。进行这些测试的最常用方法是使用脚本生成数千个模拟连接，或上传极大量的数据（无论是许多大文件，还是少数几个巨型文件）。

并不是所有的压力测试都是为了压垮软件；也可能是让其负载过低。这种类型的压力测试为系统提供`太少`某些东西（例如网络带宽、CPU 周期或内存）。这里的想法是看系统如何处理一种被称为`资源饥饿`（resource starvation）的威胁，在这种情况下，攻击者故意导致系统消耗资源，直到资源耗尽为止。一个健壮的系统在发生此类事件期间会优雅地降低其功能，而不会完全崩溃。资源不足测试也有助于确定系统正常性能所需的绝对最小配置。

## 资源饥饿

资源饥饿攻击试图通过耗尽信息系统运行所需的资源来破坏其可用性。这种类型攻击的三种最常见变体列于此处：

- **网络带宽**：这种类型可能是最广为人知的，因为分布式拒绝服务（`DDoS`）攻击会每秒用数十亿数据包淹没目标。
- **内存**：如果系统存在内存泄漏（即最终未被系统回收的内存分配），那么耗尽系统的内存是很容易的。如果你能导致程序产生无限数量的递归过程调用，或者对在线购物车中可以添加的项目数量没有限制，这也是可能的。
- **CPU**：CPU 饥饿攻击通常更难实施，因为你需要利用系统中的某个漏洞，该漏洞会长时间占用 CPU。例如，某些非对称加密程序（如密钥对生成）是 CPU 密集型的。如果攻击者能够导致系统生成大量的密钥对，它最终将无法执行任何其他功能。

## 最佳实践

也许最重要的原则是质量。`质量`（Quality）可以被定义为适用性。换句话说，某物对于它旨在完成的任何事情有多好。一辆高质量的汽车适合交通。我们不需要担心它会故障、在碰撞中无法保护乘客，或者易于被小偷偷走。当我们需要去某个地方时，只需回到我们停放的地方，并指望它带我们去任何我们需要去的地方。同样，我们不需要担心高质量软件会崩溃、在意外情况下损坏我们的数据，或易于被他人破坏。遗憾的是，许多开发者在考虑质量时仍然首先（或只）考虑功能性。当我们从整体角度观察问题时，我们应该看到质量是开发安全软件时最重要的概念。

当然，这并不是一个新问题。安全软件开发几十年来一直是一项挑战。意料之中的是，已经有一套既定的最佳实践，可以尽可能地减少我们代码中的缺陷和漏洞。你应该熟悉一些最著名的安全编码倡导者所建议的内容，这些建议将在下介绍。

## OWASP

开放 Web 应用安全项目（`OWASP`）是一个专门处理网络安全问题的组织。除了提供长系列开发者可以遵循以创建安全软件的工具、文章和资源外，它在世界范围内设有个人成员会议（分会）。该小组提供开发指南、测试程序和代码审查步骤，但它最广可能是因其维护的十大 Web 应用安全风险列表而闻名。在本书编写时，该小组识别出的顶级风险如下：

* A1: 注入
* A2: 破坏的身份验证和会话管理
* A3: 跨站脚本 (XSS)
* A4: 不安全的直接对象引用
* A5: 安全配置错误
* A6: 敏感数据泄露
* A7: 功能级访问控制
* A8: 跨站请求伪造 (CSRF)
* A9: 使用已知漏洞的组件
* A10: 未验证的重定向和转发

此列表代表了基于 Web 软件中最常见且经常被利用的漏洞。你可以在[`www.owasp.org/index.php/Top_10_2013-Top_10`](https://www.owasp.org/index.php/Top_10_2013-Top_10) 获取更多关于这些漏洞的信息。

## SANS

SANS 学院信息安全和网络安全培训领域最受尊敬的机构之一。其关注领域之一是应用安全 (`AppSec`)，并定期在其网页上提供资源（[`software-security.sans.org/resources`](https://software-security.sans.org/resources)）。SANS 扩展了其流行的“安全人类”（Securing the Human）计划，该计划关注用户安全意识，并包含了一个针对开发者的专门主题。其中，SANS 列出了大量的建议和最佳实践，许多许多已在本章中介绍。以下是你应该了解的其他额外建议：

* 显示通用的错误信息。
* 实现锁定机制。
* 限制敏感数据。
* 使用 HTTPS。
* 使用参数化查询。
* 自动化应用部署。

## 互联网安全中心

互联网安全中心（`CIS`）是一个非营利组织，目标是增强所有公共和私立组织的网络安全。`CIS`的独特之处在于，其核心是协作。多州信息共享与分析中心（`MS-ISAC`）执行类似的功能，但它专注于州、地方和领土 (`SLTT`) 政府。

### 系统设计建议

`CIS`通过关注小组和成员之间的共识建立来识别系统设计的最佳实践。网络安全分析师特别感兴趣的是`20 CIS Controls`，这些措施通常被认为可以提高组织的安全态势。除了识别这些控制措施，`CIS`还提供了关于如何在任何信息系统中实施这些措施的具体指导。

## 基准

如果说`20 CIS Controls`提供了全球性的系统设计建议，那么`CIS Benchmarks`则是保护特定平台（例如`Windows 10 企业版`或`Ubuntu 16.04`）的详细指南。这些基准等同于由政府实体（如国防信息系统局 (`DISA`)）发布的安全技术实施指南 (`STIGs`)，用于保护联邦信息系统。除了详细的基准外，`CIS`还提供了开源平台的预加固镜像。

## 本节总结

尽管你可能不会花时间（或者根本不花时间）开发软件，但作为安全分析师，你必须处理任何不安全编码实践带来的后果。最好的办法是熟悉流程和问题，并成为解决方案的一部分。仅仅是参加会议、提问和分享你的想法，可能就是避免由于程序员没有意识到其决策的潜在后果而导致灾难性破坏的关键。理想情况下，你是一个具有凝聚力的 DevSecOps 团队的一员，持续开发高质量的代码。

至于`CSA+`考试，你应该对开发安全代码的主要问题有所认识。你将被要求知道网络安全分析师如何主动地或在需要时响应地处理自定义软件中的漏洞。这里的一些关键概念是你可以运行的安全测试，例如 Web 应用漏洞扫描、压力测试和模糊测试。

### 防火墙

`Firewalls` 是根据特定规则集限制网络数据流的系统，从而强制执行组织的安全策略。组织安全策略针对保护关键资产的方面，对可接受和不可接受的操作提供高层指令。防火墙拥有的更详细的安全策略，除了其他内容外，它还规定了允许哪些`IP`地址和范围，以及可以访问哪些端口。防火墙策略或规则集通常被称为`access control list (ACL)`。一个简单的规则（如下所示）可以用于允许 SMTP 流量从系统`10.1.1.2`传输到系统`172.1.1.2`：

```
permit tcp host 10.1.1.2 host 172.1.1.2 eq 25
```
