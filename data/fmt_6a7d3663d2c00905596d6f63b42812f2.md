# 16 基于访问控制的云端可信信息共享

DOI: [10.1201/9781003081845-27](https://doi.org/10.1201/9781003081845-27)

## 16.1 简介

云计算的出现以及向软件即服务（`SaaS`）范式的持续转变，使得云端作为服务的可信信息共享（`AIS`）需求日益增长。2011 年 4 月，美国国家安全局（NSA）首席信息官（CIO）Lonny Anderson 在描述该机构专注于采用“以云为中心”的方法与其他机构共享信息时，表达了这一需求的紧迫性 [[NSA2011]](#ch16.xhtml#ref16_46)。同样，美国国防部（DoD）也一直在采纳云计算范式，以更高效、经济、灵活和可扩展的方式，实现其“提供信息力量，通过敏捷企业确保任务成功，并在信息环境中拥有机动自由”的愿景 [[DoD]](#ch16.xhtml#ref16_22)、[[DoD2007]](#ch16.xhtml#ref16_23)。此外，医疗和金融等大多数行业也迫切需要在云端安全且及时地共享信息。

云计算范式能够安全高效地共享大量数据。此外，`云计算`的出现以及向 `SaaS` 范式的持续转变，使得云端作为服务的 `AIS` 需求日益增长。为满足联盟组织以云为中心的 `AIS` 需求，迫切需要开发一个在云端运行的 `AIS` 框架。

尽管近年来已开发出许多基于策略的信息共享 `AIS` 工具 [[AWAD2010]](#ch16.xhtml#ref16_5)、[[FINI2009]](#ch16.xhtml#ref16_25)、[[THUR2008]](#ch16.xhtml#ref16_57)、[[RAO2008]](#ch16.xhtml#ref16_48)（这些工具基于控制对数据的访问），但据我们所知，这些工具均不在云端和大数据环境中运行，因此无法提供支持大量用户（如涉及包含文本、图像和视频的海量数据的社交媒体用户）所需的可扩展性。我们开发的用于支持基于云的 `AIS` 的原型系统，应用了以云为中心的查询引擎（例如第 15 章讨论的 `SPARQL` 查询优化器 Chapter 15），利用基于令牌的策略引擎或强制执行用 `XACML` 表达的策略的引擎 [[THUR2010]](#ch16.xhtml#ref16_58)、[[THUR2011]](#ch16.xhtml#ref16_59)，在关系数据库和语义 Web 数据库中查询大量数据。虽然这比之前的工作有了显著改进（并让我们深入了解了基于云的解决方案的实现），但仍存在一些局限性。首先，基于 `XACML` 的策略规范表达能力不足，无法支持医疗和国防等 `AIS` 应用所需的许多复杂策略。其次，为满足关键任务的可扩展性和效率要求，策略引擎需要在云端运行。例如，虽然第 15 章 Chapter 15 讨论的策略引擎托管在云端，但它们并未充分利用云提供的所有特性。

### 系统设计与实现概述

为了安全高效地共享大量数据，云端社交媒体的策略管理器与数据管理器必须实现无缝集成。因此，为满足以云为中心的 AIS 需求，我们需要：(i) 一个驻留在云端的策略管理器，它使用语义丰富的语言来表达和强制执行信息共享策略；(ii) 一个驻留在云端的数据管理器，它能安全地存储和检索数据，并与策略管理器无缝集成。据我们了解，目前不存在这样的系统。因此，本项目为社交媒体用户设计并开发了基于云的 AIS 系统。我们的策略引擎和数据均使用语义 Web 技术表示，因此能够对社交媒体数据进行表示和推理。也就是说，我们开发了一个以云为中心的策略管理器，强制执行用 RDF 指定的策略；以及一个以云为中心的数据管理器，用于存储和管理数据（如社交图谱及其关联数据），这些数据也用 RDF 指定。该 RDF 数据管理器本质上是一个用于 SPARQL 的查询引擎，SPARQL 是语义 Web 社区广泛用于查询 RDF 数据的语言。此外，我们的策略管理器和数据管理器将实现无缝集成，因为它们都管理 RDF 数据。

我们设计并开发了一系列处理海量数据的基于云的 AIS 系统。也就是说，我们本质上将大数据管理技术应用于 AIS。本章概述了我们的设计和实现验证工作。特别是，我们详细描述了语义云中 AIS 的设计与实现。即，我们利用语义 Web 技术提供基于云的语义 Web 服务，这些服务实现了信息共享。我们的框架采用三层架构，包括用户界面层、策略引擎层和数据连接层，后者集成了云中的多数据源。值得注意的是，要在云端存储关键数据，我们需要对数据进行加密，并在加密数据上执行信息共享操作。这对于公有云尤为重要。然而，我们之前的 AIS 工作并未对云中的数据进行加密。这将成为我们未来研究的一部分。

本章的组织结构如下。第 16.2 节讨论整体系统设计。第 16.2.1 节讨论我们的设计理念。特别是，我们将讨论两个 AIS 系统的设计：CAISS（基于云的 AIS 系统）和 CAISS++（更高级的 CAISS）。第 16.3 节讨论实现细节。第 16.4 节讨论相关工作。第 16.5 节总结本章。图 16.1 展示了本章内容。我们工作的详细信息也可参考文献 [THUR2012]。

## 16.2 系统设计

### 16.2.1 设计理念

我们的设计分两个阶段进行。第一阶段，我们设计并实现了一个以云为中心的可靠信息共享系统（CAISS）概念验证原型，该原型利用了我们自主设计的技术组件以及开源工具。CAISS 由两个组件组成：一个以云为中心的策略管理器，强制执行用 RDF（资源描述框架）指定的策略；一个以云为中心的数据管理器，存储和管理同样用 RDF 指定的数据。该 RDF 数据管理器本质上是一个用于 SPARQL（SPARQL 协议和 RDF 查询语言）的查询引擎，SPARQL 是语义 Web 社区广泛用于查询 RDF 数据的语言。RDF 是一种语义 Web 语言，在指定和推理策略方面比 XACML 具有更强的表达能力。此外，我们的策略管理器和数据管理器将实现无缝集成，因为它们都管理 RDF 数据。我们在第一阶段选择这种基于 RDF 的以云为中心的 AIS 方法，是因为它满足上一段所述的两个必要条件，而且我们已经开发了基于 RDF 的非云中心策略管理器 [CADE2011a] 和用于 AFOSR 的基于 RDF 的云中心数据管理器 [HUSA2011]。拥有构建有用的以云为中心的 AIS 系统所需的两个关键组件的部分功能，使我们能够构建一个有用的概念验证演示系统 CAISS。具体而言，我们正在增强基于 RDF 的策略引擎使其在云上运行，扩展云中心的 RDF 数据管理器以与策略管理器集成，并为 CAISS 构建一个集成框架。我们的目标是将 CAISS 扩展到社交媒体环境。

虽然我们最初的 CAISS 设计和实现将是第一个支持以云为中心的 AIS 的系统，但它仅在单个受信任云上运行，因此不支持跨多云的信息共享。此外，虽然 CAISS 基于 RDF 的形式语义策略规范方法比基于 XACML 的方法具有显著更强的表达能力，但它不支持增强的内容机器可解释性，因为 RDF 没有提供足够丰富的词汇（例如，对类和属性的支持）。因此，第二阶段将开发一个功能完善且健壮的 AIS 系统 CAISS++，以解决这些不足。CAISS++ 的初步设计已完成，将在本章后面讨论。CAISS 是通向 CAISS++ 的重要垫脚石，因为 CAISS 可作为基准框架，从存储模型效率和基于 OWL 的策略表达能力等多个性能维度与 CAISS++ 进行比较。此外，由于 CAISS 和 CAISS++ 共享相同的核心组件（策略引擎和查询处理器），从 CAISS 中这些组件的实现和集成中获得的经验教训，在 CAISS++ 的开发过程中将极其宝贵。最后，对 CAISS 的评估和测试将为我们提供关于 CAISS 缺陷的重要见解，这些缺陷随后可在 CAISS++ 的实现中系统地解决。

我们还将对策略规范及强制执行它们的软件级保护机制进行形式化分析，为生成的系统提供极高保障的安全保证。我们设想 CAISS++ 将用于高度关键任务的应用中。因此，必须保证策略以可证明正确的方式得到执行。我们在形式化策略分析 [JONE2010, JONE2011] 及其通过机器认证的内联参考监视器 [HAML2006a, HAML2006b, SRID2010] 强制执行方面拥有丰富的专业知识。这些分析将被用于建模和认证 CAISS++ 可信计算基中核心软件组件所强制执行的安全属性。

CAISS++ 将成为信息共享的突破性技术，因为它采用了一种新颖的组合：以云为中心的策略规范与强制执行，以及以云为中心的数据存储和高效的查询评估。CAISS++ 将使用本体（Web 本体语言 OWL 的一个子语言）来构建策略。此类本体与基于语义 Web 的规则语言（如 SWRL）相结合，便于对策略进行分布式推理以强制执行安全。此外，CAISS++ 将包含一个 RDF 处理引擎，该引擎基于信息共享策略为评估 SPARQL 查询提供基于成本的优化。

### 16.2.2 CAISS 设计

# 16.2.2 开发 CAISS 的增强措施

我们正在增强为 AFOSR 开发的工具，包括 (i) 面向语义 Web 数据的安全云查询处理，以及 (ii) 基于语义 Web 的策略引擎，以开发 CAISS。我们工具的详细信息见 第 16.4 节（相关工作部分）。在本节中，我们将讨论为开发 CAISS 而对工具进行的增强。

首先，我们基于 RDF 的策略引擎可对表示为 RDF 图的数据强制执行访问控制、编辑和推理控制策略。其次，我们用于 RDF 数据的云 SPARQL 查询引擎使用 Hadoop/MapReduce 框架。请注意，Hadoop 是 Apache 分布式文件系统，而 MapReduce 运行在 Hadoop 之上并执行作业调度。与我们基于云的关系查询处理器原型 [THUR2010] 类似，我们的 SPARQL 查询引擎也处理用 XACML 指定的策略，且策略引擎实现了 XACML 协议。将 XACML 用作策略语言需要深入了解 XACML 设计中使用的通用概念。因此，XACML 策略编写需要陡峭的学习曲线，因而成为一项留给经验丰富的管理员的任务。使用 XACML 的第二个缺点与性能有关。目前的 XACML 实现要求针对系统中的每个策略评估访问请求，直到有策略适用于传入的请求。这种策略对于用户和策略相对较少的系统已足够。然而，对于拥有大量用户和大量访问请求的系统，上述策略会成为性能瓶颈。最后，XACML 的表达能力不足以捕捉信息共享策略的语义。先前的研究表明，基于语义 Web 的策略具有更强的表达能力。这是因为语义 Web 技术基于描述逻辑，具有表示知识和推理知识的能力。因此，我们的第一步是用基于语义 Web 的策略引擎替换基于 XACML 的策略引擎。由于我们已为第一阶段原型拥有基于 RDF 的策略引擎，我们将增强该引擎并将其与 SPARQL 查询处理器集成。由于我们的策略引擎基于 RDF，而查询处理器也管理大型 RDF 图，因此数据与策略之间不会存在阻抗失配。

#### 16.2.2.1 增强的策略引擎
