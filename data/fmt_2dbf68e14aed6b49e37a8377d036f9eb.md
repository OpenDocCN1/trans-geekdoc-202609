### 第 13 章  

#### 维护机器学习解决方案

在前几章中，您学习了模型训练、部署策略以及已部署模型的监控。在本章中，我们将讨论之前未涉及但对于创建成熟的机器学习解决方案并对其进行维护至关重要的一些概念。

这包括重训练策略、MLOps 成熟度（第 0、1、2 级），以及一种常见的设计模式，它解决了随着 MLOps 成熟而频繁出现的问题。

MLOps 是将 DevOps 原则应用于机器学习运营。这为管理运营的 ML 工程师提供了架构和策略指导。在本章中，您将了解到 MLOps 并非“一刀切”的方法，而是一种基于组织采用机器学习成熟度的分级方法。

稍后我们还将讨论 ML 工程师在实施 MLOps 时面临的两个重要问题。首先，确定 ML 模型的重训练策略并使其与组织目标保持一致，随后介绍一种用于模型版本控制的有用约定。其次，组织在特征工程上投入巨大，将机器学习扩展到内部多个团队所面临的复杂性。这两个问题均可通过我们描述为设计模式的解决方案来解决。

#### MLOps 成熟度

组织会经历一个历程：从尝试机器学习技术开始，然后逐步将持续集成/持续部署（CI/CD）的概念引入机器学习。将 DevOps 原则应用于机器学习被称为 MLOps。

虽然 MLOps 和 DevOps 之间存在相似之处，但也存在一些关键差异。

我们发现，组织首先通过手动训练模型来尝试机器学习，然后使用流水线为该过程带来自动化；随后，随着完全实现自动化，它们进入转型阶段。它们经历的这三个阶段使用不同的技术，并反映了其“AI 就绪度”。

在详细了解这些阶段之前，让我们先看看 ML 的步骤：

1.  数据 

    1.  **提取：** 从不同来源收集数据，聚合数据，并使其可供下游 ML 流程使用。

    2.  **分析：** 对收集的数据执行探索性数据分析（EDA），以了解模式、统计分布和关系。确定将要执行的特征工程和数据准备要求。

    3.  **准备：** 对数据应用转换和特征工程。将数据拆分为训练集、测试集和验证集，用于 ML 任务。

2.  模型 

    1.  **训练：** 使用输入数据设置 ML 训练，并预测输出。尝试不同的算法和超参数，以确定表现最佳的模型。

    2.  **评估：** 使用保留集评估模型，并根据预定义的指标评估模型质量。

    3.  **验证：** 验证模型是否符合部署条件，即指标是否满足特定的基线性能标准。

3.  部署 

    1.  **服务：** 部署模型以提供在线或批量预测。对于在线预测，为模型创建并维护 RESTful 端点，并根据需求配置扩展。这也可能包括进行批量预测。

    2.  **监控：** 部署后持续监控模型，以检测异常、漂移和偏差。

我们在前几章中已经了解了所有这些步骤，因此您应该对它们很熟悉。这些步骤的自动化程度定义了 MLOps 的成熟度。Google 将 MLOps 定义为具有三个级别：MLOps 第 0 级（手动阶段）、MLOps 第 1 级（战略自动化阶段）和 MLOps 第 2 级（CI/CD 自动化，转型阶段）。

##### MLOps 第 0 级：手动/战术阶段

开始尝试 ML 的组织处于此阶段。在此阶段，重点是构建概念验证并测试一些 AI/ML 用例。其目的是验证一些关于如何利用 ML 改进业务的想法。

在此阶段，通常有一个个人或团队在进行实验和训练模型。他们工作的成果是模型，该模型通过模型注册表（如图 13.1 所示）移交给发布或部署团队。然后部署团队获取该模型并将其部署以提供预测服务。

###### 第 0 级的关键特性

让我们看看此战术阶段流程的关键点：

1.  **手动：** 所有步骤均无自动化。每个任务均为手动执行，包括数据分析、准备、训练和验证。其中大部分步骤在数据科学家的 Jupyter Notebook 中完成，这并不奇怪。

2.  **ML 与 MLOps 之间的分离：** 服务模型的数据科学家和工程师完全分离，唯一的联系点是模型移交。即使是移交，也可能只是将模型文件存储在存储位置供部署团队获取，或者稍成熟的团队可能会使用模型注册表进行移交。这种分离对检测训练-服务偏差产生负面影响。

3.  **手动迭代：** 由于此阶段训练是手动进行的，因此重新训练没有规律性，导致该流程无法扩展到几个以上的模型。

4.  **持续集成：** 测试通常仅作为 Jupyter Notebooks 的一部分进行，除此之外，CI 甚至不在考虑范围内。

5.  **持续部署：** 这些模型不经常更新，因此 CD 没有得到太多重视。

6.  **预测服务部署：** 此处的部署通常是模型的微服务，通过 REST API 进行调用，而不是部署整个 ML 系统。

7.  **监控：** 通常，此流程不考虑监控或模型退化。

###### 挑战

此阶段最重要的挑战是模型退化。由于训练数据与真实数据之间的差异，训练良好的模型在现实生活中经常表现不佳。缓解这些问题的唯一方法是主动监控预测质量，频繁重新训练模型，并频繁尝试新的算法或模型实现，以利用技术改进带来的优势。

##### MLOps 第 1 级：战略自动化阶段

处于此阶段的组织通常已确定业务目标，并将 ML 确定为解决某些问题的优先事项。此阶段涉及使用流水线来自动化模型的持续训练和模型预测服务的持续交付。实现这一点需要新的服务，包括自动化的数据和模型验证步骤、流水线触发器、特征存储和元数据管理，如图 13.2 所示。

![图 13.2 MLOps 第 1 级或战略阶段](img/c13f002.png)

**图 13.2** MLOps 第 1 级或战略阶段

在此阶段，有基础设施支持团队间共享工件，并且开发环境和生产环境有明确的区分。ML 模型的开发发生在编排环境中。数据流水线的源代码存储在中央代码库中，模型训练实现了自动化。

###### MLOps 第 1 级的关键特性

此阶段具有一些独特的特性，使其比第 0 级更成熟，我们将在此列出：

1. **实验：** 实验阶段的每个步骤都经过编排。由于步骤之间的转换是自动化的，因此加快了实验迭代的速度。

2. **持续训练：** 模型在生产环境中自动训练，由新数据触发。

3. **实验-运营对称性：** 用于创建实验流水线的代码也用于生产环境，这与统一 MLOps 的最佳实践非常吻合。

4. **模块化组件：** 用于创建流水线的每个组件都应可复用、可组合且可共享。

5. **持续交付：** 由于生产流水线是自动化的，因此可以基于新数据构建新模型并交付用于预测服务。

6. **流水线部署：** 在第 1 级，你部署的是一个通过执行来创建模型的流水线。

###### 挑战

在此阶段，预期团队仅管理少量流水线。此外，新流水线是手动部署的。流水线主要在数据发生变化时触发。当你基于新的 ML 思路部署模型时，这并不理想。例如，此方法适合使用新特征重新训练模型。然而，如果你想使用现有流水线中不包含的技术，则必须手动部署。要做到这一点，你需要创建 CI/CD 设置来自动化 ML 流水线的构建/测试/部署。

##### MLOps 第 2 级：CI/CD 自动化，变革阶段

这是处于变革阶段的组织所期望的成熟度级别，此时组织利用 AI 进行创新并提供敏捷性。通常，你可以期望 ML 专家成为产品团队的一部分，并分布在各个业务单元中。数据集通常可跨孤岛访问，ML 项目在产品组之间共享。如图 13.3 所示，整个流水线都经过 CI/CD 自动化（不仅仅是模型）。因此，如果你想将库从 TensorFlow 2.1 更新到 TensorFlow 2.5，它将自然地经过 CI/CD 自动化步骤，而无需手动操作。

###### 第 2 级的关键特性

进入第 2 级的显著特征是完全采用 CI/CD 模型。让我们详细了解一下一些特性：

1. **流水线：** 第一阶段是新 ML 算法的开发和实验，可能使用新库。输出是通过代码库共享的流水线源代码。从那时起，自动化接管一切，从构建流水线代码、对流水线代码运行各种测试、创建流水线代码的工件（如包、可执行文件等），随后部署此流水线并生成模型工件。训练好的模型自动部署以实现持续交付。部署后启用监控，收集监控数据以创建更多训练数据并自动触发训练。

2. **测试：** 测试是流水线持续集成的必要条件，从测试特征工程逻辑、模型训练收敛性检查、检查模型输出中的错误（如 NaN 值）、验证每个阶段创建的工件，以及流水线组件之间的集成测试开始。

3. **交付：** 为了实现持续交付，你需要验证模型与服务环境中的软硬件基础设施的兼容性。测试预测服务是否符合 API 模式、负载测试等。此外，根据特定模型的需求，你还可以在完全推出之前使用蓝绿部署、金丝雀部署或影子部署策略。

总之，维护 ML 解决方案不仅仅是训练模型并在 API 后面部署单个模型。它意味着自动化模型的重新训练、测试和部署的能力。由于机器学习领域几乎每天都在见证技术的快速进步，因此拥有管理这种变化的能力非常重要。

然而，并非每个组织在旅程开始时都必须达到第 2 级。这取决于组织使用 AI/ML 的成熟度，随着组织思维的成熟，自动化也随之而来。

在前面的章节中，我们详细讨论了重新训练模型，甚至持续训练和部署方法论。在这一过程中存在一些常见场景和实际问题，我们将在下一节中将其中两个作为设计模式进行解决。

#### 重新训练和版本控制模型

你已经部署了一个模型，并正在监控预测偏移。现在，我们知道模型性能会随时间退化，这可以从监控数据中测量出来。然而，在什么时间点重新训练模型？这不仅仅是一个出于好奇的问题，而是一个必须回答的问题，以便配置持续训练流水线。

Vertex AI 模型监控为你提供了监控偏移检测和训练-服务偏差的能力。在监控性能时，收集这些真实数据也很重要。这将用于模型评估以及创建新的训练数据集。那么，我们何时使用这个训练数据集来训练新模型？或者我们的重新训练频率是多少？

##### 重新训练的触发器

#### 模型性能与重新训练策略

模型性能通常会随时间推移而下降。为了解决这个问题，我们需要重新训练模型。其思路是根据策略触发重新训练流水线。以下是几种可用的策略：

*   **绝对阈值：** 您可以设置一个用于重新训练的绝对阈值。例如，每当准确率降至 90% 以下时，即可触发重新训练。确定该绝对阈值取决于您的用例。

*   **降级速率：** 每当性能突然下降时，您可以触发重新训练。例如，如果您发现一天内准确率下降超过 2%，则可以触发重新训练。

现在考虑到上述策略，有几个主要要点需要考量：

*   **训练成本：** 训练模型是有成本的。频繁训练模型可能代价高昂。因此，重要的是确保策略不会频繁触发重新训练。

*   **训练时间：** 有些模型只需几分钟即可训练完成，但其他模型可能需要数周。在等待新训练模型的过程中，已部署的模型可能会进一步降级。

*   **延迟训练：** 如果阈值设置得太低，在新模型部署之前，模型可能已经降级太多。这不仅会影响机器学习服务的性能，还会显示出机器学习性能的不一致性，而最终用户可能无法容忍这一点。

*   **定时训练：** 一种简单得多的策略是按固定时间表进行重新训练。这将定期纳入新数据，且成本可预测。

##### 模型版本控制

当您构建多个模型并与其他团队共享时，拥有某种查找它们的方法非常重要。一种方法是使用元数据来识别工件；然而，组织外部的用户通过 API 访问已部署的模型，对他们来说，元数据存储可能不可访问。这就是版本控制可以发挥作用的地方。

拥有多个模型的问题在于，当用户通过 API 访问时，他们期望模型具有特定的性能和行为。如果同一 API 的行为突然发生变化，会导致意外的中断。然而，模型更新或变更是必要的。例如，假设有一个模型用于识别图像中的物体和人类，并能准确检测所有人脸。后来，假设您更新了该模型，使其现在也具备检测狗和其他宠物的能力；这可能会导致中断。在这种情况下，用户需要有能力选择旧模型。

解决方案是使用模型版本控制。模型版本控制允许您将额外的模型部署到现有模型中，并能够使用版本 ID 进行选择。在这种情况下，最终用户可以通过指定版本来访问这两个模型。这解决了向后兼容性问题；即，这非常适用于具有相同输入和输出的模型。

对于行为方式不同的模型（例如具有提供模型解释能力的模型），它们可以作为新模型部署（而不是作为现有模型的新版本）。

在这两种情况下，都应该能够使用 REST 端点单独且方便地访问这些模型。在所有已部署的模型版本上启用监控，使您能够比较不同版本。

#### 特征存储

特征工程是构建优秀机器学习模型能力的重要因素。然而，观察发现，实际上特征工程比尝试机器学习模型更加耗时。因此，一个经过精心设计的有价值特征为整个机器学习解决方案提供了巨大价值。

因此，特征工程是任何组织的一项巨大投资。为了优化模型，许多团队致力于创建新特征。有时这些特征对其他团队也很有价值。不幸的是，共享这些特征很棘手，因此相同的特征工程任务会一遍又一遍地重复进行。这会产生几个问题：

*   **不可复用：** 特征是临时创建的，并非旨在供他人使用。每个团队创建特征的目的仅在于自用。这些临时特征未在流水线中自动化，有时源自其他昂贵的数据预处理流水线。

*   **治理：** 创建这些特征的方法来源多样，给数据治理带来了非常复杂的局面。

*   **跨团队协作：** 由于这些特征具有临时性且不共享，团队之间产生了更多隔阂，并继续各自为政。

*   **训练与服务差异：** 当特征临时构建且未自动化时，会导致训练数据和服务数据之间存在差异，从而降低机器学习解决方案的有效性。

*   **特征产品化：** 虽然这些临时特征在实验期间很有用，但由于缺乏自动化以及对特征低延迟检索的需求，它们无法实现产品化。

##### 解决方案

解决方案是拥有一个中心位置来存储特征以及关于特征的元数据，以便在数据工程师和机器学习工程师之间共享。这还允许将软件工程的版本控制、文档编制和访问控制原则应用于这些特征。

特征存储还有两个关键特性：快速处理大型特征集的能力，以及以低延迟访问特征以进行实时预测、以及批量访问以进行训练和批量预测的能力。
