
# 数字签名与公钥基础设施

## 数字签名流程

1. Alice 使用密码学上可靠的哈希算法（如 `SHA3-512`）生成原始明文消息的消息摘要。
2. Alice 然后仅使用她的私钥加密消息摘要。这个加密后的消息摘要就是数字签名。
3. Alice 将签名后的消息摘要附加到明文消息后。
4. Alice 将附加后的消息发送给 Bob。

当 Bob 接收到数字签名消息时，他会反向执行该过程，步骤如下：

1. Bob 使用 Alice 的公钥解密数字签名。
2. Bob 使用相同的哈希函数为从 Alice 接收到的完整明文消息创建一个消息摘要。
3. Bob 然后将从 Alice 接收到的解密消息摘要与他自己计算的消息摘要进行比较。如果两个摘要匹配，他可以确信收到的消息是由 Alice 发送的。如果不匹配，则消息不是由 Alice 发送的，或者消息在传输过程中被修改过。

请注意，数字签名过程本身不提供任何隐私保护。它仅确保满足完整性、认证和不可否认性这些加密目标。然而，如果 Alice 想要确保发给 Bob 的消息的隐私，她可以在消息创建过程中增加一个步骤。在将签名后的消息摘要附加到明文消息后，Alice 可以用 Bob 的公钥加密整条消息。当 Bob 收到消息时，他会先用自己的私钥解密，然后再遵循上述步骤。

### HMAC

哈希消息认证码（`HMAC`）算法实现了部分数字签名——它保证消息在传输过程中的完整性，但不提供不可否认性。

`HMAC` 可以通过使用共享密钥与任何标准消息摘要生成算法（如 `SHA-3`）结合。因此，只有知道密钥的通信双方才能生成或验证数字签名。如果接收者解密了消息摘要，但无法将其与从明文消息生成的消息摘要成功比较，则意味着消息在传输过程中被篡改。

因为 `HMAC` 依赖于共享密钥，所以它不提供任何不可否认性功能（如前所述）。然而，它的运行效率比下一节描述的数字签名标准更高，可能适用于对称密钥密码学适用的场景。简而言之，它代表了未加密使用消息摘要算法与基于公钥密码学的计算成本高昂的数字签名算法之间的一个折中点。

### 数字签名标准

美国国家标准与技术研究院在联邦信息处理标准（`FIPS`）186-4 中规定了联邦政府可用的数字签名算法，该标准也称为数字签名标准（`DSS`）。该文件规定，所有联邦批准的数字签名算法必须使用 `SHA-3` 哈希函数。

`DSS` 还规定了可用于支持数字签名基础设施的加密算法。目前有三种批准的标准加密算法：

* `FIPS 186-4` 中规定的数字签名算法（`DSA`）
* `ANSI X9.31` 中规定的 Rivest、Shamir、Adleman（`RSA`）算法
* `ANSI X9.62` 中规定的椭圆曲线 DSA（`ECDSA`）

## 公钥基础设施

公钥加密的主要优势在于其促进相互未知各方之间通信的能力。这得益于 `public key infrastructure (PKI)` 信任关系层级。这些信任关系允许将非对称密码学与对称密码学相结合，并辅以哈希和数字证书，从而实现混合密码学。

在以下章节中，您将了解公钥基础设施的基本组件以及使全球安全通信成为可能的加密概念。您将学习数字证书的组成、证书颁发机构的作用，以及生成和销毁证书的过程。

### 证书

`Digital certificates`（数字证书）为通信双方提供保证，确认他们正在通信的人确实是他们声称的那个人。数字证书本质上是个人公钥的背书副本。当用户验证证书是由受信任的 `Certificate Authority (CA)`（证书颁发机构）签名时，他们就知道该公钥是合法的。

数字证书包含特定的标识信息，其构建遵循国际标准——`X.509`。符合 `X.509` 的证书包含以下证书属性：

* 证书符合的 `X.509` 版本
* 序列号（来自证书创建者）
* 签名算法标识符（指定证书颁发机构用于对证书内容进行数字签名的技术）
* 颁发者名称（颁发证书的证书颁发机构的标识）
* 有效期（指定证书有效期间的日期和时间——起始日期/时间和过期日期/时间）
* 主体的 `Common Name (CN)`（通用名称），清晰描述证书所有者（例如 `certmike.com`）
* 证书可选地包含 `Subject Alternative Names (SAN)`（主体替代名称），允许您指定受单个证书保护的其他项目（IP 地址、域名等）。
* 主体的公钥（证书的核心——证书所有者用于建立安全通信的实际公钥）

`X.509` 的当前版本（版本 3）支持证书扩展——由证书颁发机构插入证书中的包含数据的自定义变量，用于支持证书跟踪或各种应用程序。

证书可针对多种目的颁发。这些包括为以下对象的公钥提供保证：

* 计算机/机器
* 个人用户
* 电子邮件地址
* 开发人员（代码签名证书）

证书的主体名称中可能包含通配符，表示该证书对子域名同样有效。通配符由星号字符指定。例如，颁发给 `*.certmike.com` 的通配符证书对以下所有域名均有效：

* `certmike.com`
* `www.certmike.com`
* `mail.certmike.com`
* `secure.certmike.com`

### 证书颁发机构

`Certificate Authorities (CAs)`（证书颁发机构）是将公钥基础设施粘合在一起的关键。这些中立组织为数字证书提供公证服务。要从信誉良好的 CA 获取数字证书，您必须向 CA 证明您的身份。以下列表包含一些提供广泛接受的数字证书的主要 CA：

* Symantec
* IdenTrust
* Amazon Web Services
* GlobalSign
* Comodo
* Certum
* GoDaddy
* DigiCert
* Secom
* Entrust
* Actalis
* Trustwave

没有任何东西能阻止组织直接开展 CA 业务。然而，CA 颁发的证书仅取决于对颁发该证书的 CA 的信任程度。在接收第三方的数字证书时，这是一个重要的考量因素。如果您不认识或不信任颁发证书的 CA 的名称，则完全不应信任该证书。PKI 依赖于信任关系的层级结构。如果您将浏览器配置为信任某个 CA，它将自动信任该 CA 颁发的所有数字证书。浏览器开发商预先将浏览器配置为信任主要 CA，以避免将此负担强加给用户。

`Registration Authorities (RAs)`（注册机构）协助 CA 在颁发数字证书前验证用户身份。它们不直接颁发证书，但在认证过程中发挥着重要作用，允许 CA 远程验证用户身份。

证书颁发机构必须仔细保护其自身的私钥以维护信任关系。为此，它们通常使用 `offline CA`（离线 CA）来保护其 `root certificate`（根证书），即其整个 PKI 的顶级证书。该离线 CA 与网络断开连接并关机，直到需要时才启用。离线 CA 使用根证书创建从属的 `intermediate CAs`（中间 CA），它们作为 `online CAs`（在线 CA）用于日常颁发证书。

在 CA 信任模型中，使用一系列中间 CA 称为 `certificate chaining`（证书链）。要验证证书，浏览器首先验证中间 CA 的身份，然后沿着信任路径追溯到已知的根 CA，验证信任链中每个环节的身份。

证书颁发机构不必是第三方服务提供商。许多组织运营内部 CA，为组织内部使用提供 `self-signed certificates`（自签名证书）。这些证书不会被外部用户的浏览器信任，但内部系统可配置为信任内部 CA，从而节省从第三方 CA 获取证书的费用。

### 证书生成与销毁

公钥基础设施背后的技术概念相对简单。在以下章节中，我们将介绍证书颁发机构用于创建、验证和吊销客户端证书的过程。

#### 注册

当您想要获取数字证书时，首先必须以某种方式向 CA 证明您的身份；此过程称为 `enrollment`（注册）。如前一节所述，这有时涉及携带适当的身份证明文件亲自出现在认证机构代理人面前。一些证书颁发机构提供其他验证方式，包括使用信用报告数据和受信任的社区领袖进行身份验证。

一旦您满足了证书颁发机构对身份的要求，您便以 `Certificate Signing Request (CSR)`（证书签名请求）的形式向其提供您的公钥。CA 随后创建一个包含您标识信息和公钥副本的 `X.509` 数字证书。CA 然后使用 CA 的私钥对证书进行数字签名，并向您提供一份签名后的数字证书副本。您随后可以安全地将此证书分发给任何您想要安全通信的人。

证书颁发机构根据其执行的身份验证级别颁发不同类型的证书。最简单、最常见的是 `Domain Validation (DV) certificates`（域名验证证书），CA 仅验证证书主体对域名的控制权。`Extended Validation (EV) certificates`（扩展验证证书）提供更高级别的保证，CA 在颁发证书前会采取措施验证证书所有者是否为合法企业。

#### 验证

当您从想要通信的对象处收到数字证书时，您需使用 CA 的公钥检查 CA 的数字签名来 `verify`（验证）该证书。接下来，您必须检查并确保证书未被吊销，方法是使用 `Certificate Revocation List (CRL)`（证书吊销列表）或 `Online Certificate Status Protocol (OCSP)`（在线证书状态协议）。此时，前提是满足以下要求，您可以假设证书中列出的公钥是真实的：

* CA 的数字签名是真实的。
* 您信任该 CA。
* 证书未列在 CRL 中。
* 证书实际包含您所信任的数据。

最后一点是一个微妙但极其重要的项目。在信任某人身份的识别信息之前，请确保该信息实际包含在证书中。如果证书包含电子邮件地址（`billjones@foo.com`）但不包含个人姓名，你只能确定其中包含的公钥与该电子邮件地址相关联。CA 并不对 `billjones@foo.com` 电子邮件账户的实际身份做任何断言。但是，如果证书包含姓名 Bill Jones 以及地址和电话号码，CA 也将为该信息担保。

数字证书验证算法内置于许多流行的 Web 浏览器和电子邮件客户端中，因此你不常需要深入了解该过程的细节。然而，深入理解幕后发生的技术细节对于为你的组织做出适当的安全判断非常重要。这也是购买证书时选择一个广受信任的 CA 的原因。如果一个 CA 不包含在主流浏览器信任的 CA 列表中，或稍后被从中移除，将极大地限制你的证书的实用性。

2017 年，数字证书行业发生了一起重大安全故障。Symantec 通过一系列关联公司签发了多个不符合行业安全标准的数字证书。作为回应，Google 宣布 Chrome 浏览器将不再信任 Symantec 证书。结果，Symantec 最终将其证书签发业务出售给了 DigiCert，后者同意在签发前妥善验证证书。这证明了妥善验证证书请求的重要性。一系列看似微小的程序疏忽可能会摧毁一家 CA 的业务！

*证书固定* 方法指示浏览器将证书与主体关联一段延长的时间。当站点使用证书固定时，浏览器将该站点与其公钥关联。这允许用户或管理员在证书意外变更时察觉并介入。

#### 吊销

有时，证书颁发机构需要*吊销*证书。这可能因以下原因之一发生：

* 证书被泄露（例如，证书所有者意外泄露了私钥）。
* 证书被错误签发（例如，CA 在未进行适当验证的情况下错误签发了证书）。
* 证书详细信息发生变更（例如，主体名称变更）。
* 安全关联发生变更（例如，主体不再受雇于赞助该证书的组织）。

你可以使用三种技术来验证证书的真实性并识别已吊销的证书：

* **证书吊销列表** 证书吊销列表（CRL）由各个证书颁发机构维护，包含已由 CA 签发并已吊销的证书的序列号，以及吊销生效的日期和时间。证书吊销列表的主要缺点是必须定期下载和交叉引用，在证书被吊销和最终用户收到吊销通知之间引入了一段延迟期。

* **在线证书状态协议 (OCSP)** 该协议通过提供实时证书验证的手段，消除了使用证书吊销列表固有的延迟。当客户端收到证书时，它向 CA 的 OCSP 服务器发送 OCSP 请求。服务器随后响应有效、无效或未知的状态。浏览器使用此信息确定证书是否有效。

* **证书装订** OCSP 的主要问题是它给证书颁发机构运营的 OCSP 服务器带来了巨大负担。这些服务器必须处理来自网站每个访问者或数字证书其他用户的请求，验证证书是否有效且未被吊销。

    *证书装订* 是在线证书状态协议的一个扩展，它减轻了原始协议给证书颁发机构带来的部分负担。当用户访问网站并发起安全连接时，网站将其证书发送给最终用户，后者通常负责联系 OCSP 服务器以验证证书的有效性。在证书装订中，Web 服务器联系 OCSP 服务器本身，并从 OCSP 服务器接收签名并加盖时间戳的响应，然后将其附加或装订到数字证书上。然后，当用户请求安全 Web 连接时，Web 服务器将带有装订 OCSP 响应的证书发送给用户。用户的浏览器随后验证证书是否真实，并验证装订的 OCSP 响应是否真实且近期。由于 CA 对 OCSP 响应进行了签名，用户知道它来自证书颁发机构，时间戳向用户保证 CA 最近验证了该证书。从那里，通信可以照常继续。

    时间节省体现在下一位用户访问网站时。只要时间戳足够近期，Web 服务器只需重复使用装订的证书，无需再次联系 OCSP 服务器。通常装订证书的有效期为 24 小时。这将 OCSP 服务器的负担从每天处理每个用户一个请求（可能达数百万请求）减少到每天处理每个证书一个请求。这是巨大的减少。

### 证书格式

数字证书存储在文件中，这些文件有多种不同的格式，包括二进制和基于文本的格式：

* 最常见的二进制格式是 **Distinguished Encoding Rules (DER)** 格式。DER 证书通常存储在扩展名为 `.DER`、`.CRT` 或 `.CER` 的文件中。
* **Privacy Enhanced Mail (PEM)** 证书格式是 DER 格式的 ASCII 文本版本。PEM 证书通常存储在扩展名为 `.PEM` 或 `.CRT` 的文件中。
* **Personal Information Exchange (PFX)** 格式通常由 Windows 系统使用。PFX 证书可以二进制形式存储，使用 `.PFX` 或 `.P12` 文件扩展名。
* Windows 系统也使用 **P7B** 证书，以 ASCII 文本格式存储。

## 非对称密钥管理

在公钥基础设施中工作时，遵守若干最佳实践要求以维护通信安全非常重要。

首先，明智地选择你的加密系统。正如你之前所学，“通过隐蔽实现安全”不是一种合适的方法。选择一种算法处于公共领域且已由行业专家彻底审查的加密系统。警惕那些使用“黑盒”方法并坚持其算法的机密性对密码系统完整性至关重要的系统。

### 密钥管理最佳实践

你必须以适当的方式选择密钥。使用能够在安全需求与性能考量之间取得平衡的密钥长度。此外，确保你的密钥真正随机，或者用密码学术语来说，具有足够的熵。密钥中的任何可预测性都会增加攻击者破解加密并降低密码系统安全性的可能性。你还应了解加密算法的局限性，并避免使用任何已知的弱密钥。

使用公钥加密时，务必保管好私钥！在任何情况下，都不允许其他人访问你的私钥。请记住，即使只允许他人访问一次，也会永久性地危害使用该密钥进行的所有通信（过去、现在或未来）的安全性，并允许第三方成功冒充你。

在密钥完成其使命后将其弃用。许多组织都有强制性的密钥轮换要求，以防止未被发现的密钥泄露。如果你没有必须遵循的正式策略，请根据密钥的使用频率选择合适的轮换间隔。持续重复使用密钥会产生更多加密材料，这些材料可能被用于密码分析攻击。如果切实可行，你可能需要每隔几个月更换一次密钥对。

备份你的密钥！如果因数据损坏、灾难或其他情况导致包含私钥的文件丢失，你肯定希望有可用的备份。你可以自行创建备份，也可以使用由第三方维护备份的密钥托管服务。无论哪种情况，都要确保备份得到安全处理。

**硬件安全模块（HSM）** 也提供了一种有效的加密密钥管理方式。这些硬件设备以一种安全的方式存储和管理加密密钥，防止人类需要直接处理密钥。HSM 的范围和复杂程度各不相同，从非常简单的设备（如 `YubiKey`，将加密密钥存储在 USB 驱动器上供个人使用）到驻留在数据中心的更复杂的企业级产品。云服务提供商（如 Amazon 和 Microsoft）也提供基于云的 HSM，为 IaaS 服务提供安全的密钥管理。

## 密码学攻击

如果时间教会了我们什么，那就是人们经常做别人认为不可能的事。每当发明一种被认为无法破解的新代码或新流程时，总有人会想出破解它的方法。

让我们看看一些常见的破解技术。

### 暴力破解

这种方法只是尝试所有可能的密钥。它保证能成功，但可能耗时极长，以至于根本不可行。例如，要破解凯撒密码，只有 26 个可能的密钥，可以在极短时间内尝试完毕。但即使是拥有相对较弱密钥的 DES，也需要 2⁵⁶ 次不同的尝试。那是 72,057,594,037,927,936 个可能的 DES 密钥。为了更直观地理解，如果你每秒尝试 100 万个密钥，尝试完所有密钥需要略超过 46,190,765 年。

### 频率分析

**频率分析** 涉及查看加密消息的分组，以确定是否存在任何常见模式。最初，分析师不试图破解代码，而是查看消息中的模式。在英语中，字母 *e* 和 *t* 以及 *the*、*and*、*that*、*it* 和 *is* 等单词非常常见。句子中独立存在的单个字母通常仅限于 *a* 和 *I*。
