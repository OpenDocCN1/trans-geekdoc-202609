
因此，关注点转向了使用虹膜图案作为识别基础的可能性。虹膜位于眼睛外部，并且可以从远处扫描。最终，研究人员希望能够使计算机扫描一个人的面部，并以与人类大致相同的方式识别它。然而，如果机器要能够考虑不同的光照条件、面部角度、化妆的使用等，这将需要相当高的复杂性。

提供指纹进行检查的想法，如同视网膜扫描一样，可能会遇到一些抵制，因为在公众心目中，指纹与警察逮捕嫌疑人时遵循的程序有关。更可接受的替代方案是使用手部几何形状，手部放在平面上并测量其尺寸。还可以使用个人签名，以正常方式书写但在特殊敏感板上。在这种情况下，重要的是记录笔的运动模式，而不仅仅是签名的形状，否则该方法很容易通过传统的伪造而被滥用。

即使使用常规键盘也可以提供一些身份识别的线索，尽管这对于访问控制目的来说并不太实用。因为每个人在键盘上工作都会形成一定的风格和节奏，所以可以通过分析击键记录来识别用户。这在检查已登录的人是否确实是他们声称的人时很有用。

![Figure 4.4 Picture of fingerprint reader with keypad](img/fig4_4_B.jpg)

图 4.4 指纹读卡器带键盘的图片

总之，以下方法可用于生物特征识别：

1. 被动测试（用户无需采取任何行动）：
    * 视网膜图案；
    * 虹膜图案；
    * 人脸识别；
2. 主动测试（用户必须以某种方式参与）：
    * 手部几何形状；
    * 指纹；
    * 语音模式；
    * 手写签名；
    * 击键模式

### 4.2.3 适用于所有识别方法的补充措施

无论使用何种识别方法（或方法组合），都可以应用某些措施来加强对用户 ID 滥用的保护。重点可以放在旨在`预防`的控制上，或`反馈`控制上，后者有助于在滥用发生后检测到它。

#### 预防

* **终端超时**。如果用户已登录，但一段设定的时间内未发生任何活动，系统将断开用户连接。这降低了其他人发现终端无人看管并阅读显示内容，或利用终端在无人看管时仍运行的访问权限的风险。类似的效果可以通过使用“屏幕保护程序”来实现，其工作原理大致相同：如果似乎没有人使用计算机，屏幕上的材料将被图案或图片替换，只有输入屏幕保护程序密码后才能移除。

* **访问与工作模式绑定**。通常员工只需要在正常工作时间或从自己工作区域的终端访问系统。如果是这样，系统可以设置为将访问限制为例如某个特定办公室的终端，周一至周五上午 8:00 至下午 6:00。

#### 反馈

* **有关先前登录的信息**。每当用户登录时，系统应回复一条消息，说明该用户 ID 上次使用的时间。这使用户可以检查日期和时间是否与其回忆或其正常工作模式一致。明显的问题示例是，如果系统声称该 ID 在周末凌晨办公室关闭时被使用。用户应立即提醒系统管理员该 ID 很可能已被泄露。

* **对 ID 使用情况的分析**。某些情况明显可疑，例如，如果同一 ID 在同一时间被用于两个不同地点的登录。可以使用分析软件浏览系统登录记录，突出显示任何不应该发生的情况。这种分析也可以在“实时”进行，使可疑登录在发生时被阻止或质询，从而将其从反馈型控制转变为预防型控制。

其他形式的反馈和预防性控制在第 5.1 节中讨论。

## 4.3 系统范围的访问控制

许多组织中发现的 IT 格局是多年添加、扩展和修改各种系统混合的结果。随着部门合并，或各自为政地进行 IT 采购，或因无法负担更换而勉强使用过时的软件，结果形成了一片凌乱的 IT 拼凑物。（唯一大家通常能达成一致的是，如果能重新开始，他们几乎肯定会做得不一样）。

这种来自过去的遗留问题也可能使 IT 系统难以与当前的组织结构和边界非常精确地保持一致。这一点所带来的一些影响已经有所涉及（参见第 1.6 节和第 3.3 节）。不幸的是，整个访问控制的概念都依赖于能够在被保护的实体和未被保护的实体之间做出明确区分。这迫使必须非常精确地决定系统的边界在哪里，以及谁被允许使用它们。如果以往的做法是设施以非正式方式共享，或者对于一些较老旧或使用频率较低的系统而言“开放访问”一直是常态，那么这可能会证明特别困难。

传统上，访问控制的边界设定在两个层级。第一层标志着`通用控制`的适用点。理想情况下，这些控制涵盖组织中使用的所有 IT 设施。有时，考虑一个较小的单元可能是合适的，例如一个单独的办公地点或一家公司的部门。在第二层级，`应用控制`用于在人们开始使用单个设施（此处的“应用”指基于特定软件的服务，例如会计或计算机辅助设计）后调节访问和使用。许多组织中 IT 的拼凑式演进意味着该模型在实践中往往无法非常完美地契合；然而，它有助于探讨访问控制最好如何以及在何处进行管理的一些问题。

在通用边界上的访问控制可以类比为使用共享办公楼外门的钥匙。这是获得你想要使用的设施访问权限的第一步。给予你这种“通用”访问并不意味着你被允许在建筑物内自由漫游。一旦被准入系统，你会发现自己被限制在被认为与你的需求相关的应用范围内。这可以类比为能够进入一栋办公楼，但被迫使用只能停在你工作楼层的电梯。这种控制模型在图 4.5 中有所描述。

![Figure 4.5 General and application controls](img/fig4_5_B.jpg)

Figure 4.5 General and application controls

在业务系统中，一些应用（如电子邮件）将对几乎每个人开放。其他应用（如研究与开发或市场营销使用的数据库）则包含具有相当商业价值的数据，因此其使用将受到更严格的限制。理想情况下，通用访问控制应为每个人呈现系统的“逻辑”视图，给人一种印象，即除了该用户被授权的应用之外没有其他应用。因此用户 A 和用户 B 在首次登录时可能会看到两套截然不同的选项（参见图 4.6）。以这种方式隐藏应用对用户来说很方便，因为他们不会浪费时间尝试进入被禁止的应用，同时也使有志于黑客攻击和欺诈的人的生活变得更加困难。

## 4.4 应用控制：多重与单点登录

一旦用户获得了对应用的合法访问，是否需要施加进一步的访问控制取决于应用的性质。例如，每个电子邮件用户都需要大致相同的标准功能；使用市场数据库的人希望能够浏览其中包含的所有数据。在这些情况下，对应用的访问意味着可以自由使用而无需任何进一步限制。

在其他情况下，需要引入额外的控制层级。例如，一名初级职员可能被允许访问会计系统，但仅限于录入订单或发票。而他的主管则被允许执行更敏感的任务，例如在系统中录入新客户和核销坏账。同样，对于跟踪仓库货物情况的应用，某些人仅限于查询库存状况，而其他人则被允许在货物进出时记录变更。在医院，初级员工可能能够使用患者管理系统查找患者的所在位置，但不能浏览其他患者详情。应用层级控制的增加在图 4.8 中有所说明。

如果以这种方式为应用创建单独的访问控制制度，则存在一些优缺点，如下所示。

### 优点

* **接近性**。如果有某个部门是应用的主要使用者，访问控制的责任可以分配给其高级员工之一。该人员将处于了解应用使用方式的良好位置，因此可以判断部门不同成员可能需要的访问类型。

* **响应性**。将责任移交给驻用户部门的人员意味着用户请求更新和更改，以及报告他们对控制工作方式的任何担忧应该会更容易。

### 缺点

* **登录的复杂性**。以最常见的情况为例，即使用密码，创建完全独立的访问控制制度意味着用户必须先输入一个密码进行通用访问，然后再输入另一个密码进入应用。用户可以理解地不愿使用多个密码。可以安排使用相同的密码用于两种情况（该过程称为`同步`密码）。然而，这意味着本地密码管理员与中心之间需要不断联络。此外，并非总能对不同软件包中的密码格式和用户 ID 应用相同的约定。如果使用任何令牌或生物识别方法，复杂性会倍增。

* **划分职责**。设置和维护访问控制的责任现在分散在两个地方，用户可能会觉得烦人且令人困惑，尤其是当他们试图解决紧急问题时。

解决“多重密码”问题的一种方法是采用基于 `single sign-on` 的方法。要使其发挥作用，必须在控制两个不同层级的软件之间建立安全链接。一旦用户通过了通用访问控制，其信息就会自动转发给应用程序软件。应用程序软件随后将此作为身份证明。

单点登录可以通过两种不同的方式实现：

* `Scripting`。通用访问控制软件存储应用程序软件会识别的用户 ID 和密码。这些信息以模拟用户在屏幕上输入相应登录序列的效果的方式传递给应用程序软件。

* `Authentication server`。所有访问控制都移交给一台专门的服务器机器。该服务器对每个用户进行初始检查。与应用程序交换专门编码的信号以传递用户身份。对于这种方法能够发挥作用，每个应用程序必须嵌入特殊代码，以处理并响应来自身份验证服务器的信号。

`Scripting` 实现起来容易得多，但很难做到完全安全。如果脚本不够正确，可能会出现不可预测的结果，并且应用程序可能会返回令人困惑的消息。身份验证服务器是控制的更好手段，但需要付出相当多的努力来设置和管理。在任何一种情况下，单点登录都应仅作为覆盖整个组织的协调良好的努力来进行 Hardy 1996。

## 4.5 构建和实施访问控制规则

访问控制设施通常作为软件包的标准功能提供。作为此类功能，它们应与其他任何方面一样彻底地进行审查。例如，在比较会计产品时，接受供应商的保证说外币处理或报告生成“只是小儿科”会被视为天真。会立即要求提供文件和演示来支持此类说法。

此外，购买者通常期望发现某些软件包比其他软件包更适合，只是因为它们与业务需求的“契合度”更好。同样原则适用于访问控制。评估这一方面可能相关的一些标准包括：

* 控制所需的 `granularity` 程度。例如，在控制对数据的访问时，是否需要能够区分到单个数据项的级别，还是更概括的控制就足够了？

* 创建 `ACT` 条目时的 `user-friendliness`。从头开始构建 `ACT` 非常耗时。产品应提供有效的帮助和快捷方式。

* 控制的 `sharing` 和 `delegation`。例如，受保护文件的拥有者是否希望自行决定授予其他用户访问权限，而无需向安全管理员请示？

* 与组织 `standards` 的一致性。示例包括公司要求所有密码在设定的时间间隔后更改，或是否使用单点登录。

* `specific to the organisation` 的要求。也许需要能够将访问权限与位置、终端标识符或一天中的时间相关联？

为了使访问控制易于操作，一些供应商将其简化为最基本的功能。例如，他们可能会创建有限数量的预定访问“级别”。这让人想起分层/军事化安全方法。每位员工被分配一个数字，例如一到九之间：数字越高，可访问的设施范围越大。问题在于，在给定级别上的设施组合可能与任何特定员工的工作说明书不完全匹配。因此，在一款面向小型企业的会计软件包中，所选级别将决定员工在 *所有* 设施上的权限范围，从分类账、库存和税务记录到折扣、价格和报告格式的设置。这不允许出现例如员工仅需要对销售分类账具有较高访问级别的情况。系统坚持必须在整个设施范围内授予同样高的访问级别。

信誉良好的软件包通常在分配访问权限方面提供更大的灵活性。例如，应该能够定义用户将被允许执行的任务类型的精确列表。理想情况下，每个任务都可以链接到用户为执行它而选择的特定图标或菜单选项。其效果是使其中一些保持为“活动”功能，而其他功能则拒绝执行，或根本从屏幕上呈现的选项中消失。

## 4.6 对数据库和聚合数据的访问

`Databases` 最初被设想为集中管理的、可供组织中每个人使用的中央数据存储库。在“真正的”数据库中，所有数据都由一个名为 `Database Management System (DBMS)` 的软件管理。任何从数据库读取或写入的数据都必须通过 `DBMS`，后者强制执行数据编码和组织的标准方法。目标是确保存在单一、可靠的数据来源，该来源独立于使用它的应用程序。`DBMS` 的这种“托管”角色使其成为强制执行某些类型访问控制的有用位置。`DBMS` 的功能在 Figure 4.12 中示意性地显示

![Figure 4.12 ](img/fig4_2_B.jpg)

Figure 4.12 

不幸的是，`database` 已被证明是一个有用的词，用来描述任何类型的庞大数据集合。即使已经安装了数据库软件产品（现在已有数款可在普通 PC 上运行），也无法保证它实际上被用作 DBMS。它可能只是以一种方便的方式保存一个大型文件，该文件需要以各种相当复杂的方式进行搜索。在这种情况下，数据库没有系统范围的作用，实际上与任何其他应用程序没有什么不同。

如果数据库 *确实* 对整个组织使用的数据拥有保管权，那么访问权限的控制就成为一个关键问题。尽管某些应用程序可能会定期向数据库输入数据，但严格来说，这些数据并不‘属于’它们。数据现在已成为整个组织拥有的资源。

因此，有必要仔细查看数据库的每个用户被允许做什么。对数据的访问权限可分为以下五大类：

* **READ**。用户可以读取数据并复制，但不能以任何方式更改它。
* **WRITE**。用户可以输入新数据。这通常适用于 *预期* 的数据，即已经为其创建了空字段。
* **UPDATE**。用户可以更改现有数据。例如，薪水可能会从每年 £15,000 更新为 £16,000。在此上下文中，删除现有条目也等同于更新。
* **CREATE**。用户可以建立新的记录或文件。例如，可以为新员工创建记录，或建立一个新文件来保存来年的销售信息。
* **DELETE**。用户可以删除现有记录或文件。

在每种情况下，‘用户’可能是使用查询程序（基于诸如结构化查询语言之类的搜索语言）的人，也可能是依赖数据库获取数据的应用程序。当然，该应用程序最终也会响应来自‘用户’的命令。

数据库的 ACT 往往很复杂，因为它必须为每个用户-应用程序指定可访问的数据以及允许的使用类型。在某些情况下，访问需要指定到单个数据字段的级别。

例如，员工记录可能包含多个字段。Figure 4.13 仅显示了张先生的六个字段。前三个字段显示姓名和出生日期，不应更改，因此对大多数用户应为 *只读*。然而，一个或多个用户将需要能够 *更新* 接下来的两个字段，因为哈罗德在公司的发展过程中会有所进步。评估字段也需要在未来某个时间点 *写入* 等级。哈罗德的记录将在他加入公司时 *创建*，并在离职时 *删除*（至少从当前员工文件中删除）。

![Figure 4.13 ](img/fig4_13_B.jpg)

由于数据库旨在成为广泛使用的资源，通常会发现只读访问被广泛提供。存在一种危险，即关注点集中在对数据完整性构成潜在威胁的更活跃的访问权限上。例如，在错误的人手中，更新或创建记录的能力在实施各种欺诈时可能非常有用。然而，即使是只读访问权限也应谨慎审查。这尤其适用于数据库包含个人身份信息（例如上面引用的 H. Chang 的记录）或具有商业敏感性（例如显示按产品和地区划分的销售明细）的情况。
