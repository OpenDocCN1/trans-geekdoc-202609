
一些作者列出了容易与聚合混淆但不应建模为聚合的关联种类，例如拓扑包含、分类包含、属性化、附着和所有权（[Martin and Odell, 1998；Odell, 1998]）。例如，“手指属于手”是聚合，但“戒指属于手指”则不是。作者们对于该列表应包含什么存在一些分歧。例如，一些人将属性化视为聚合的一种特例，即一个类与其属性的类之间的组合（Rumbaugh et al., 1999）。

对于概念建模目的而言，为这些区别纠结可能不值得。对于聚合应如何（如果有的话）包含在概念建模阶段，你可以采取不同的立场。你可以决定什么最适合你。章节注释对此提供了进一步的讨论。

现在让我们看看*初始值*的概念。如图所示，UML 中属性规范的基本语法包含六个组成部分。此处方括号和花括号按字面意义用作定界符（而非用于指示可选组成部分的 BNF 符号）。

*   `visibililty name` \[`multiplicity`\]: `type-expression` = `initial-value` {`property string`}

如果显示属性，其名称是必须显示的唯一内容。可见性标记（`+`、`#`、`−`、`~` 分别表示 public、protected、private、package）是实现关注点，将在我们的讨论中忽略。多重性前面已讨论过，对于属性，它在方括号中指定，例如 `1..*`。

对于属性，默认多重性为 1，即 `1..1`。类型表达式指示属性所基于的域（例如 `String`、`Date`）。初始值和属性字符串声明可以选择性地声明。属性字符串可用于指定诸如可变性之类的方面（见后文）。

可以通过在属性声明中“=”后包含值来为属性分配初始值（例如 `diskSize = 9`；`country = USA`；`priority = normal`）。编写值所用的语言是实现关注点。

在图 9.48(a) 中，`nrColors` 属性基于一个简单域（例如 `PositiveInteger`）并被赋予了初始值 1。`resolution` 属性基于一个复合域（例如 `PixelArea`）并被分配了初始值 `(640, 480)`。

![图 9.48 在 (a) UML 和 (b) ORM 扩展中分配了初始值的属性。](img/f09-48-9780443237904.jpg)

图 9.48 在 (a) UML 和 (b) ORM 扩展中分配了初始值的属性。

除非被另一个初始化过程（例如构造函数）覆盖，否则声明的初始值会在创建该类的对象时被赋值。这类似于数据库中*默认值*的概念，即在插入元组时，如果用户未提供值，则属性可能会被赋予预先声明的默认值。然而，UML 仅在其他语境中使用“默认值”一词（例如模板和操作参数），且一些作者声称默认值不是 UML 模型的一部分（Rumbaugh et al., 1999，第 249 页）。

SQL 标准将**null**视为默认值的一种特殊实例，UML 支持这一点，因为规范指出“0..1 的多重性提供了 null 值的可能性：值的缺失”。因此，UML 中的可选属性可用于建模一种特性，当映射到关系数据库时，它将表现为一个默认值为 null 的列。推测，对于任意 *n* > 1，多重性 `[0..*]` 或 `[0..*n*]` 也允许多值属性为 null，尽管也可以使用空集合代替。

目前，ORM 没有对初始/默认值的显式支持。一个可能的扩展可以允许为 ORM 角色指定默认值。在元层面，我们添加事实类型 `Role has default-Value`。在外部层面，该事实类型的实例可以在谓词属性表上指定，或在图表上输入（例如，通过将注解 `d: value` 附加到角色上，并最好允许切换此显示的开/关）。例如，图 9.48(b) 中 `NrColors` 扮演的角色被分配了默认值 1。当映射到 SQL 时，这应在 `ClipArt.nrColors` 的列定义中添加声明“default 1”。

为了支持 UML 允许的复合初始值，可以为由复合标识的对象类型（共引用或嵌套）扮演的 ORM 角色指定复合默认值。当共引用涉及由相同或兼容对象类型扮演的至少两个角色时，需要一个顺序来消除复合值含义的歧义。例如，在图 9.48(b) 中，`Resolution` 扮演的角色被分配了默认复合值 `(640, 480)`。为确保 640 应用于水平像素计数，480 应用于垂直像素计数（而不是反过来），此顺序需要应用于外部唯一性约束的定义角色。ORM 工具通常根据输入此约束时选择角色的顺序来确定此顺序。

如果一个对象类型扮演的所有或大多数角色具有相同的默认值，则允许为对象类型本身指定默认值可能很有用。这可以通过在 ORM 中添加元事实类型 `ObjectType has default-Value` 并提供一些表示法来实例化它来实现（例如，通过对象类型属性表中的条目，或通过用 `d: value` 注解对象类型形状）。这对应于 SQL 标准中 `create-domain` 语句允许的默认子句。请注意，对象类型默认值总是可以用基于角色的默认值来表示，但反之则不然（因为默认值可能随角色而异）。

默认值的规范并不涵盖关于一般默认信息可能出现的所有情况。Halpin and Vermeir (1997) 中讨论了一个为 ORM 提供更多默认信息支持的提议，但这超出了 UML 或 SQL 中内置的默认支持范围。默认信息可以通过使用谓词来非正式地建模，以向人类传达这一意图。例如，我们可以使用 1:n 事实类型 `Medium is default preference for SoftProduct` 来指定软产品（如音乐、视频、软件）交付的默认媒介（如“CD”、“DVD”）偏好。

在默认值与实际值重叠的情况下，我们可能还希望将相关事实类型的实例分类为实际或默认（例如 `Shipment used Medium`）。对于唯一性约束跨越 *n* **−** 1 个角色的典型情况，这可以通过包含指示默认状态的事实类型来实现（例如 `Shipment was based on Choice {actual, default}`），从而在数据库中产生额外的列来记录状态。虽然这种方法是通用的，但它要求建模者和用户承担全部责任来区分实际值和默认值。

在 UML 中，除了二元关联的角色（端点）外，还可以对属性的*可变性*施加限制。不清楚可变性是否可以应用于 *n*-元关联的端点。UML 2 识别以下四种可变性值，在给定时间只能应用其中一种：

*   `unrestricted`
*   `readOnly`
*   `addOnly`
*   `removeOnly`

默认可变性是“unrestricted”（允许任何更改）。值“unrestricted”以前称为“changeable”，而“changeable”以前称为“none”。其他设置可以在大括号中显式声明。对于属性，大括号放在属性声明的末尾。对于关联，大括号放在关联的另一端，远离约束所应用的对象实例。

回想一下，在 UML 中，“链接”是关联的实例。术语“`readOnly`”（以前称为“frozen”）意味着一旦插入了属性值或链接，就不能更新或删除它，也不能向该属性/关联添加额外的值/链接（针对受约束的对象实例）。

术语“`addOnly`”意味着虽然原始值/链接不能被删除或更新，但可以向该属性/关联添加其他值/链接（针对受约束的对象实例）。显然，只有当属性/关联角色的最大多重性超过其最小多重性时，`addOnly` 才有意义。术语“`removeOnly`”意味着对现有属性值或链接允许的唯一更改是删除它。

作为一个简单但不切实际的示例，请参见图 9.49。此处 `Employee` 的员工编号、出生日期和出生国均为 `readOnly`，因此它们不能从原始值更改。例如，如果我们给员工分配员工编号 007，并输入其出生日期为 02/15/1946、出生国为“Australia”，那么我们永远无法对此进行任何更改或添加。

![图 9.49 属性和关联角色的可变性](img/f09-49-9780443237904.jpg)

图 9.49 属性和关联角色的可变性。

对于每个员工，语言集合和访问过的国家集合均为 `addOnly`。假设对于员工 007，我们最初将其语言设为 {Latin, Japanese}，访问过的国家设为 {Japan}。只要数据库中引用了员工 007，这些事实就不能被删除。但是，我们可以对此进行添加（例如，稍后我们可能添加员工 007 会说 German 且访问过 India 的事实）。

默认情况下，其他属性是可变的。例如，员工 007 可能合法地将其姓名从“Terry Hagar”改为“Hari Seldon”，并将想访问的国家从 {Ireland, USA} 改为 {Greece, Ireland}。

### 可变性限制与派生数据

#### 可变性限制

一些传统的数据建模方法也提到了一些可变性限制。Barker ER 表示法包含一个菱形，用于将关系标记为不可转移的（一旦实体类型的一个实例与一个对象扮演了某个角色，它就不能与另一个对象扮演该角色）。虽然可变性限制可能很有用，但在实践中，它们在数据库环境中的应用是有限的。

其中一个原因是，输入数据库的事实可能需要更改。对于快照数据，这是常态，但即使对于历史数据，也可能发生更改。最常见的情况是允许纠正错误，这可能是因为我们最初被告知了错误的信息，或者因为我们在录入数据时粗心大意导致了拼写错误或笔误。

在特殊情况下，我们可能要求将某种错误保留在数据库中（例如，出于审计目的），但通过录入后续事实来纠正该错误。这种方法对于银行交易很有意义（参见图 9.50）。例如，如果一笔 100 美元的存款交易被错误地录入为 1000 美元，该错误记录会被保留，但一旦发现错误，就可以通过一笔 900 美元的银行取款来补偿。余额既是派生的又是存储的，其 `readOnly` 状态通常由基本属性上的 `readOnly` 设置连同派生规则共同暗示。

![Fig. 9.50 Transaction 的所有属性均为 readOnly。](img/f09-50-9780443237904.jpg)

图 9.50 Transaction 的所有属性均为 readOnly。

一些作者允许为类指定可变性，作为为其所有属性和相反关联端声明此项的缩写（Booch et al., 1999，第 184 页）。例如，图 9.50 中所有的 `{readOnly}` 约束可能被替换为“Transaction”名称下方的单个 `{readOnly}` 约束。虽然这种表示法更整洁，但很少使用。即使在这个例子中，我们可能仍希望允许稍后添加非冻结信息的可能性（例如，一笔交易可能由零个或多个审计员审计）。

可变性设置在程序代码设计中很有用。虽然可变性设置在 ORM 中尚不受支持，因为 ORM 侧重于静态约束，但它们正在被考虑纳入扩展以支持动态约束（见下一章）。从更广泛的角度来看，能够完整建模安全问题（例如，谁有权更改什么）将提供额外价值。

#### 有序集合与集合类型

UML 允许为多值属性和关联端指定 `{ordered}` 和 `{unique}` 属性。因为 `{unique}` 默认为 true，所以使用 `{ordered}` 表示有序集合（一个无重复项的序列）。例如，图 9.51(a) 展示了在 UML 中建模论文作者身份的一种方式。每篇论文都有一个作者列表，每位作者在该列表中最多只能出现一次。

![Fig. 9.51 (a) UML 和 (b) ORM 中建模的有序集合。](img/f09-51-9780443237904.jpg)

图 9.51 (a) UML 和 (b) ORM 中建模的有序集合。

这可以通过使用 `Position` 对象类型来存储作者在列表中的顺序位置，在平面 ORM 中建模，如图 9.51(b) 所示。前两个角色上的唯一性约束声明了对于每篇论文，一位作者最多占据一个位置；覆盖第一和第三个角色的约束表明对于任何论文，每个位置最多由一位作者占据。文本约束指出列表位置从 1 开始按顺序编号。

虽然这种三元表示法看起来可能笨拙，但它易于填充，并且便于任何涉及位置的讨论（例如，论文 21 的第二作者是谁？）。从实现角度来看，仍可选择有序集合结构。

有序集合是集合类型的一个例子。正如第 10 章所述，某些版本的 ORM 允许以类似 UML 的方式将集合指定为映射注解，某些 ORM 版本允许将集合直接建模为一等对象。

#### 关联重定义

UML 2 引入了*关联重定义*的概念。此概念适用于泛化以及关联。其主要用途之一是指定对涉及超类型的关联进行特化的关联的更强约束。例如，在图 9.52(a) 中，`executiveCar` 角色重定义了 `assignedCar` 角色，应用了仅适用于高管的更强的多重性约束。实际上，关联“高管被分配公司汽车”被视为“员工被分配公司汽车”关联的一个特化。更强的多重性约束可以通过文本约束在 ORM 中表示，如图 9.52(b) 所示，或通过涉及子类型链接的子集约束表示（见第 10.8 节）。

#### 派生数据

现在让我们考虑*派生数据*。在 UML 中，派生元素（例如属性、关联或关联角色）通过在其名称前加前缀“/”来指示。也可以选择性地指定*派生规则*。派生规则可以表示为约束或注释，通过虚线连接到派生元素。这条线实际上是依赖箭头的简写，可选择性地用构造型名称 `«derive»` 标注。

### ORM 处理推导规则方法的一个优势

ORM 处理推导规则方法的一个优势在于其更加稳定，因为它不受模式变更的影响，例如属性后来被重构为关联。
