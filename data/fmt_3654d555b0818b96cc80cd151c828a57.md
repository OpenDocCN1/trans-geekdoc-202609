
# 鸟类物种的学名

鸟类物种的学名实际上是一个包含两个组成部分的语义名称。例如，在 `dacelo gigas` 中，“dacelo”是属名，“gigas”是种名。单独的种名（如“gigas”或“americana”）并不能标识一个物种。例如，`certhia americana`（褐旋木雀）与 `parula americana`（北美林莺）是不同的鸟类物种。

如果我们希望查询属名或种名，应将命名语义解包为双部分引用方案，如图 5.28 所示；否则可以使用图 5.27(b)所示的简单引用方案。

# 复合引用方案与实体标识

简单的 1:1 命名方案将实体直接关联到值（例如，主题到主题代码）。在现实生活中，我们有时通过将实体与其他实体建立 1:1 关系来标识实体（例如，“1992 年举办的奥运会”、“位于‘布里斯班’市的仓库”、“领导‘销售’部门的总监”）。此类标识方案可被选为主要引用，并描绘为强制性 1:1 二元事实（例如，“奥运会 举办于 年份 (CE:)”）。这些二元事实随后被视为引用类型，而非基本事实类型。

这种做法很少见。相反，此类二元关联通常被建模为基本事实类型，并选择其他主要引用方案，例如 `Olympics(.SequenceNr)`、`Warehouse(.Nr)`。或者，通过使用合适的描述性谓词来移除相关实体类型。例如，断言“2020 年奥运会举办地为‘东京’市”可描绘为 Year 和 City 实体类型之间的二元关联。如果不需要原始的引用语义，另一种选择是使用简单值引用，但这通常是最后的手段。例如，`Warehouse(.Name) 'Brisbane'` 丢失了该仓库位于布里斯班市这一语义。

# 析取引用

在大多数复合引用方案中，每个引用谓词都是强制性的，因此同类型的每个实体都使用相同数量的值来标识。然而在现实世界中，我们有时会遇到只有部分引用角色是可选的，但它们的析取仍然是强制性的标识方案。这称为**析取引用**。在这些情况下，同类型的不同实体可能通过不同数量的值来引用。例如，考虑图 5.29 中描绘的植物学标识方案。

![图 5.29 植物学标识中，某些引用角色是可选的](img/f05-29-9780443237904.jpg)

图 5.29 植物学标识中，某些引用角色是可选的。

某些植物仅通过属名即可标识（例如 `agrostis`）。许多其他植物品种通过属名和种名的组合来引用（例如 `acacia interior`）。还有一些通过属名、种名和亚种名的组合来标识，其中亚种本身由等级和亚种名标识（例如 `Eucalyptus fibrosa` ssp. `nubila`）。因此，根据植物种类的不同，标识它可能需要一、二或四个值。

跨三个角色的外部唯一性约束表明每个（属、种、亚种）元组最多指代一种植物。在 PlantKind 引用方案中，只有属名是强制性的。唯一性约束符号中的“o”表示应用**外连接语义**（参见第 10.1 节），因此对于每个属，最多只有一种仅凭属名的植物；对于每个属-种组合，最多只有一种无亚种的植物。在关系数据库中，每种植物映射到一个包含四个值的序列，其中三个可能为空，且每个四元组都是唯一的（将空值视同其他值处理）。另一个外部唯一性约束声明（等级、亚种名）对标识亚种。

从 Plant has Infraspecies 的第一个角色指向 Plant has SpeciesName 的第一个角色、带有子集符号的箭头，表示**子集约束**：仅当记录了种名时，才记录亚种。子集约束将在下一章详细讨论。图 5.29 的引用方案是植物学实际使用的标识方案的简化版本，实际方案还需照顾杂交种和栽培品种等复杂情况。现实世界很复杂！

## 避免使用析取引用作为首选引用

实践中，**应尽量避免将析取引用方案用作首选引用**。以当前示例为例，我们应考虑引入替代的简单标识符（例如 `PlantkindNr`）。如果用户同意在日常交流中使用它，可在概念模型中做此更改。如果不同意，我们仍可考虑在逻辑设计中使用它。若如此，我们仍需将析取信息建模为“次要引用”方案。虽然实现起来仍然麻烦，但将析取从主要引用移至次要引用，可简化并提升大多数实现的性能。

避免析取引用的另一种方法是将引用组件连接成单个名称。但这会导致难以针对单个组件发出查询，因此在当前示例中不太可行。

避免析取引用的另一种方法是在标识方案中使用特殊默认值。例如，若使用“--”或“#”等符号表示“不存在”，则所有引用角色均变为强制性，且该特殊值在强制唯一性时视同其他值处理。虽然此法在某些情况下可行，但它几乎不具备概念性，且若要求用户群体使用特殊值，或需要同一符号适配不同数据类型（如数字和字符串），则可能不切实际。

# 引用链与同义词

有时引用链可能很长。值由常量标识。每个实体直接使用一个或多个对象序列来引用，这些对象可能是值或实体。在后一种情况下，引用链递归继续，直到引用对象最终全为值。这样，每个对象最终都由一个或多个值引用，这些值作为输出报告或数据库表中命名列的条目出现。

同一实体的候选标识符被称为*同义词*。有些人用“*同名词*”来指代指向多个实体的标签。例如，相同的姓氏“Jones”可能指代不止一个人。由于“同名词”有不同的语法含义，因此“非标识标签”等其他术语更为合适。无论如何，“同名词问题”要么通过扩充参考模式直到实现标识（例如，结合姓氏和首字母缩写）来解决，要么通过使用完全不同的首选标识模式（例如，社会安全号码）来解决。

“(mm:)”后面的星号“*”表示毫米是*派生单位*，这与作为*标准单位*的米不同。图 5.30(b) 显示了单位参考模式的展开形式，每个单位都基于相同的*单位维度*（长度）。它还显示了单位之间的*换算规则*，派生单位位于“=”号的左侧。我们使用术语“维度”来包含派生维度（例如，体积 = 长度³）。换算规则等式的两边必须具有相同的维度（例如，长度）或维度表达式（例如，质量/体积）。

ORM 2 认为具有相同基于单位的参考模式的对象类型是兼容的。因此，如果长度和压力出现在同一个模型中，使用参考模式 `Length(mm:)` 和 `Pressure(mm:)` 将是不正确的，因为这暗示长度和压力基于相同的语义域。为避免此问题，我们需要重命名其中一个参考模式，例如 `Pressure (mmHg:)`。

## 元数据降级

作为一种更抽象的方法，我们可以将表 5.11 中的元数据（长度等）建模为数据，如图 5.31 所示的填充模型。表 5.11 中的第一个事实可以用以下事实来表示：`LumberSize “A4” has Attribute “length” of NumericValue 3`；`Attribute “length” has Unit “m”`。单位换算规则仍然是必需的。这种技术称为*元数据降级*，因为它将元数据（关于数据的数据）降级为领域数据。虽然这种方法非常强大，但对大多数用户来说通常不自然。如果使用，通常应将其转换为更简单的外部模式以供用户交互。

![图 5.31 将元数据降级为数据。](img/f05-31-9780443237904.jpg)

图 5.31 将元数据降级为数据。

作为将不同单位视为值的一个更简单的例子，涉及多种货币的金融应用可能会使用复合参考模式 `MoneyAmount(is in Currency(.code), has NumericValue())` 来建模货币金额。

将元数据（类型）降级为数据（实例）有助于最大程度地减少随时间推移对模式的更改。像图 5.31 这样的抽象模型可用于允许添加新属性而无需更改数据库模式。例如，医疗应用可能使用关联 `Patient has Attribute of Value` 来预测稍后要添加的新患者检测项目。在这种情况下，通常需要额外的关联来控制单位在其上下文中的使用。

有时，我们可能需要处理多个单位制。例如，随着用户逐渐从一个单位制迁移到另一个单位制，或合并独立的应用程序，我们可能同时需要公制和非公制度量。除了提供在不同单位之间转换的换算规则外，我们还必须小心地向与系统交互的人类暴露单位（回想一下火星气候轨道飞行器的命运）。

# 5.4 案例研究：一家激光唱片零售商

以下小型案例研究旨在巩固 CSDP 步骤 1-5 的主要思想。为了获得最大收益，你应该尝试自己解决该问题，然后再查看解决方案。该业务领域涉及一家激光唱片（CD）零售商，其使用信息系统来协助账户和库存控制，并为寻求特定音乐作品和艺术家信息的客户提供专门服务。

每张激光唱片以 CD 编号作为其首选标识符。虽然此处未显示，但不同唱片可能具有相同的名称。此处，“CD”用于通用意义上，类似于目录库存项。零售商库存中可能有许多张 CD `654321-2`，但就我们的目的而言，这些都被视为同一张 CD。在某些应用中（如汽车销售），你确实需要区分同一型号的不同副本，但对于我们的应用，这不是要求。

艺术家是一个人或一群人。对于给定的 CD，当且仅当该唱片上的大多数曲目都是由该艺术家演奏时，才列出主要艺术家（此约束由数据录入员强制执行，而非系统）。假设每个艺术家都有一个标识名称，我们使用事实类型 `CompactDisc(CDNr) has main- Artist(.Name)`；否则我们必须用 `ArtistName` 替换 `Artist`，即 `CompactDisc(CDNr) has main- ArtistName()`。

必须记录发行该唱片的唱片公司。

该应用程序一个具有挑战性的方面是理解“曲目”的含义并确定其标识方案。为了澄清术语，你通常需要咨询领域专家。“曲目”一词通常有两种含义：激光唱片上的 `物理曲目` 和录制在该曲目上的音乐作品或 `作品`。

在给定 CD 的上下文中，曲目由其曲目编号或在唱片上的顺序位置来标识。但该领域中有许多 CD，因此我们需要 CD 编号和曲目编号两者来标识一个曲目。使用“曲目”的物理意义，第一张 CD 报表中涉及“Maya’s Dance”的事实可以这样口头化：

|  |

| --- |

| `CD 编号为 ‘654,321–2’ 的激光唱片上的、曲目编号为 1 的曲目` |

| `存储一个标题为 ‘Maya’s Dance’ 的作品。` |

这使用了复合参照方案：`Track(is on CompactDisc, has TrackNr)`。请注意，事实谓词说的是“*一个*该标题的作品”，而不是“*该*作品”。不同的音乐作品可能具有相同的标题。虽然物理曲目仅出现在一张 CD 上，但同一作品可能出现在许多唱片上。例如，CD `654321-2` 的曲目 5 和 CD `925838-2` 的曲目 2 具有相同的标题，且很可能是同一作品。也有两个标题为“Sultans of Swing”的曲目，但它们的时长不同，因此不是同一作品。在极少数情况下，同一张 CD 上可能出现两个标题相同的曲目（此处未显示）。

之前的口头化未将 `Work` 作为实体类型包含在内。我们应该包含它吗？我们需要知道一张唱片上的作品是否与另一张唱片上的作品完全相同吗？只有领域专家能告诉我们他/她是否想知道这一点。对于我们的解决方案，假设该问题的答案为“否”。

然而，如果答案是“是”，我们将需要 `Work` 的 1:1 标识方案。`Work` 的自然参照方案很难找到（即使标题、艺术家和时长的组合可能也不够）。我们可能会使用人工标识符（如 `WorkNr`），但这可能难以强制执行，因为人类负责强制执行首选参照方案中的约束。

曲目的时长是指播放所需的时间。每个曲目恰好有一个时长，以秒为单位。大多数曲目有一个或多个歌手。某些曲目可能没有歌手（这些是器乐曲目而非声乐曲目）。

## 销售报告做得怎么样？
