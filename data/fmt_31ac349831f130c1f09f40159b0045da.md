
您可以通过在 `Model` 资源上调用 Vertex AI `deploy` 函数来部署模型。`deploy` 方法将创建一个端点，并将您的模型部署在该端点上。您需要提供流量分配、机器类型、GPU 和最小节点数来设置 `deploy` 方法。以下 `deploy` 函数返回一个 `Endpoint` 对象。

```
Endpoint = model.deploy(
     deployed_model_display_name=DEPLOYED_NAME,
     traffic_split=TRAFFIC_SPLIT,
     machine_type=DEPLOY_COMPUTE,
     accelerator_type=DEPLOY_GPU.name,
     accelerator_count=DEPLOY_NGPU,
     min_replica_count=MIN_NODES,
     max_replica_count=MAX_NODES,
 )
```

上述 Vertex AI 函数接受以下参数：

*   `deployed_model_display_name`：已部署模型的可读名称。
*   `TRAFFIC_SPLIT`：流向该模型的端点流量百分比，以一个或多个键值对字典的形式指定。
    *   如果只有一个模型，则指定为 `{ "0": 100 }`，其中 `"0"` 指代正在上传的此模型，100 表示 100% 的流量。
    *   如果端点上存在现有模型且流量将被分配，则使用 `model_id` 指定为 `{ "0": percent, model_id: percent, ... }`，其中 `model_id` 是已部署端点上现有模型的模型 ID。百分比之和必须为 100。
*   `machine_type`：用于训练的机器类型。
*   `accelerator_type`：硬件加速器类型。
*   `accelerator_count`：附加到每个工作副本的加速器数量。
*   `starting_replica_count`：最初预配的计算实例数量。
*   `max_replica_count`：扩缩的最大计算实例数量。在本教程中，仅预配一个实例。

您可以使用上述 API 或 Google Cloud 控制台来部署模型。

### 模型不同版本的 A/B 测试

A/B 测试对比机器学习中两个版本模型的性能，以查看哪一个更吸引访问者/观看者。它测试对照版本 (A) 与变体版本 (B)，根据您的关键指标衡量哪一个最成功。

#### 将两个模型部署到同一端点

将两个模型部署到同一端点，可让您逐步用一个模型替换另一个模型。在 A/B 测试场景中，如果您不想在应用中造成突发性变化，可以将新模型添加到同一端点，为其分配一小部分流量，然后逐渐增加新模型的流量分割比例，直到其承载 100% 的流量。

#### 使用流量分割进行 A/B 测试

对于 Vertex AI 中的 A/B 测试，我们在部署模型时介绍了 `traffic-split` 参数。您可以在将两个模型托管到同一端点时，向此 `traffic-split` 参数提供 `model_id` 和分割值，以拆分流量。以下是在 Cloud Shell 中使用 `gcloud` 命令的示例：

```
gcloud ai endpoints update <Endpoint> --region=us-central1 \
  --traffic-split=[DEPLOYED_MODEL_ID=Value] --service-account=<Service account> \
  --project=<Project> \
  --traffic-split=[DEPLOYED_MODEL_ID=VALUE,…]
```

在上述代码中，`traffic-split` 参数接受一个已部署模型 ID 列表，并将其值设置为 `traffic-split`。请查看此链接以了解有关部署模型参数的更多信息：

`https://cloud.google.com/sdk/gcloud/reference/ai/endpoints/update`

由于资源与模型相关联而非端点，因此您可以将不同类型的模型部署到同一端点。然而，最佳实践是将特定类型的模型（例如 AutoML 文本、AutoML 表格、自定义训练）部署到一个端点。这种配置更易于管理。

开箱即用方面，除了使用 `traffic-split` 之外，Vertex AI 并不具备您通常用于 A/B 测试的所有功能，例如控制模型流量、实验、跟踪结果、对比等。

不过，您可以结合 Vertex AI 模型评估功能与 Vertex AI 模型监控来创建一套 A/B 测试方案。此功能目前处于实验性版本。

Vertex AI 模型评估功能允许您运行模型评估作业（在测试数据集上衡量模型性能），而无论使用哪种 Vertex 服务来训练模型（AutoML、托管流水线、自定义训练等），并可在 Vertex AI 模型注册表中跨多个模型存储和可视化评估结果。凭借这些功能，Vertex AI 模型评估使用户能够决定哪些模型可以进入在线测试或投入生产，以及一旦投入生产后，何时需要重新训练模型。

#### 取消部署端点

如果您没有关键业务需求，仅需在一天中的几个小时或工作日期间让端点保持运行，则需要取消部署这些端点。运行中的端点会产生费用。因此，最好在不使用时取消部署它们。您可以使用 `undeploy` 函数来取消部署，如以下 Python 代码片段所示：

```
deployed_model_id = endpoint.list_models()[0].id
endpoint.undeploy(deployed_model_id=deployed_model_id)
```

## 在 Google Cloud 上托管第三方流水线 (`MLflow`)

在本节中，我们将介绍在 Google Cloud 上托管特定于 MLflow 的第三方流水线的各种方式。MLflow (`https://mlflow.org/docs/latest/concepts.html`) 是一个用于管理端到端机器学习生命周期的开源平台。它与库无关，您可以将其与任何机器学习库以及任何编程语言配合使用。它主要解决四大功能：

*   **MLflow Tracking** 用于实验跟踪，以及记录和对比参数与结果。您可以将其视为类似于 Vertex AI Experiments，后者用于在 Vertex AI 中跟踪实验。我们将在即将到来的第 14 章中介绍实验。
*   **MLflow Projects** 用于以可重用、可复现的形式打包 ML 代码，以便与其他数据科学家共享或迁移至生产环境。
*   **MLflow Models** 用于管理和部署来自各种 ML 库的模型，以适配各种模型服务和推理平台。
*   **MLflow Model Registry** 用于提供一个中央模型存储，协作管理 MLflow Model 的完整生命周期，包括模型版本控制、阶段转换和注解。这类似于 Vertex AI Model Registry，后者是一个集中存储模型、支持版本控制和注解的场所。

您可以单独使用这些组件中的每一个。例如，您可能只想使用 MLflow 来跟踪实验，而不使用 MLflow Model Registry 或 Projects。

您会在 Google Cloud 上使用 MLflow，以利用 Google Cloud Vertex AI 平台为模型训练和托管提供的可扩展性和可用性。您可以访问 GPU、TPU 和 CPU 等高性能计算资源，在 Google Cloud 上运行 MLflow 训练和托管工作负载。

要在 Google Cloud 上运行或安装 MLflow：

*   创建一个 PostgreSQL 数据库，用于存储模型元数据。
*   创建一个 Google Cloud Storage 存储桶，用于存储工件。
*   创建一个 Compute Engine 实例来安装 MLflow 并运行 MLflow 服务器，或者您可以在 Kubernetes 上使用 Docker 环境运行 MLflow Projects。

### 您还可以使用 Google Cloud 插件运行 MLFlow，而无需安装 MLFlow 提供的 Docker 镜像。有关插件详情，请参阅此链接：

`https://pypi.org/project/google-cloud-mlflow`

## 配置触发器和流水线计划

对于本节，您需要知道如何根据用例在 Vertex AI 平台上触发训练或预测作业。

例如，要触发实时预测作业，您可以在 Google Cloud App Engine 上设置预测端点，以创建无服务器 ML 网关。我们在本章前面的“服务（在线、批量和缓存）”一节中介绍了该架构模式。

以下是一些有助于创建触发器并在 Vertex AI 上安排训练或预测作业的服务：

*   `Cloud Scheduler` 可帮助您设置 cron 作业计划，以安排 Vertex AI 训练或预测作业。
*   使用 `Vertex AI managed notebooks`，您可以使用 Jupyter Notebook 执行和安排 Vertex 训练和预测作业。请参阅此链接了解详情：`https://cloud.google.com/vertex-ai/docs/workbench/managed/schedule-managed-notebooks-run-quickstart`。
*   `Cloud Build` 是 GCP 上的 CI/CD 产品。如果您想重新训练模型、构建 `Dockerfile` 并将其推送用于自定义训练，请使用 `Cloud Build` 启动它。`Cloud Run` 是用于部署容器的托管产品。假设您部署的容器是一个包含您模型的 Flask 或 FastAPI 应用。您可以使用 `Cloud Build` 将应用部署到 `Cloud Run`。
*   您还可以使用事件驱动的无服务器 `Cloud Functions` 和 `Cloud Pub/Sub`。`Cloud Functions` 是无服务器且无状态的函数即服务，而 `Pub/Sub` 实现了发布者-订阅者模式。您可以为 `Cloud Function` 使用基于事件的 `Cloud Storage` 触发器，以便在存储桶中添加新版本的模型时，激活 `Cloud Function` 以启动部署。

当有多个 `Cloud Functions` 执行多项任务时，使用 `Cloud Function` 和 `Pub/Sub` 具有挑战性。例如，`Cloud Function A` 触发数据转换，然后 `Cloud Function B` 触发模型训练，最后 `Cloud Function C` 部署模型。在这种情况下，您需要一个编排器来在流水线中编排这些事件。要使用 `Cloud Functions` 编排数据清洗、数据转换、模型部署和模型训练，您可以使用 `Cloud Workflows`。

**Cloud Workflows** 将多个基于 HTTP 的服务编排为持久且有状态的工作流。工作流非常适合将微服务链接在一起、自动化基础设施任务（如启动或停止 VM）以及与外部系统集成。工作流连接器还支持 Google Cloud 服务（如 `Cloud Storage` 和 `BigQuery`）中的简单操作序列。

如果您不想使用 `Cloud Function` 进行编排，请使用 `Cloud Scheduler` 和 `Workflows`。

Vertex AI 提供了编排选项，例如表 10.3 中列出的 Vertex AI 流水线，我们将在下一章（第 11 章，“设计 ML 训练流水线”）中详细介绍。
