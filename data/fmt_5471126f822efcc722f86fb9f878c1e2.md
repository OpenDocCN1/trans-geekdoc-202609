## 15.11 总结

ORM 提供了一种强大的方法论和符号，用于在概念层面（即与实现无关的层面）捕获信息结构。从 ORM 模型中，可以推断出信息动态方面的某些偏序关系。例如，与主对象类型关联的强制事实类型的信息，必须在该对象类型实例化时刻之前可用。主事实类型之间的引用必须以维护引用完整性的方式排序——在数据库系统中，这些通常表现为外键引用。

然而，这些有限的约束远未达到流程定义的程度。需要其他形式的表达来明确定义企业执行其活动的意图。业务流程模型提供了一种方式；状态模型提供了另一种。ORM 也不提供任何表达流程元素其他方面（如涉及的资源）的方式。这并非对 ORM 的批评：只是企业的描述除了它所使用的信息结构外，还涉及许多其他方面。

显然，从许多不同视角考察企业可能是适当的，但这些不同的观点必须协调一致，因为它们最终表达的是同一个业务系统。试图仅用 ORM 建模这些不同视角，就像试图用 UML 建模面向对象系统却只能使用类图一样。这意味着业务建模需要采用多视角方法。然而，结合不同视角并不意味着使用独立的模型，因为我们实际上是在谈论对一个公共模型的不同视图。

流程模型和状态模型都可用于表达行为方面。它们所体现的技术演变方式相似，因为它们回应了相同的压力，例如处理大量复杂活动集的需求。UML 包含活动建模和状态建模，但其在业务建模中的应用因其主要面向定义软件工件而受到影响。

标准在流程建模中变得越来越重要。非正式标准（如广泛引用的工作流模式）有助于建立对业务流程重要特征的更好理解。更官方的标准（如 `BPMN` 和 `DMN`）正在帮助各类企业推广流程建模的应用。

## 16.1 外部数据结构

前几章隐含地假设数据将存储在某种数据库系统中，例如关系数据库。在本章中，我们将探讨如何以独立于特定类型数据存储的方式来表示数据。当我们需要在不同系统之间传输数据时，这可能是必要的。如果传输发生在同类的两个系统之间，我们可以利用系统内置的任何功能。例如，我们可以使用服务器到服务器的复制机制，或将一台服务器上制作的备份恢复到另一台不同的服务器上。但这些方法通常不适用于两个不同类型的系统之间，即使它们属于同一大类。例如，在 `SQL Server` 上制作的备份副本无法在 `Oracle` 系统上恢复。我们还需要注意不同种类系统之间可能进行的交换，例如数据库管理系统和电子表格之间。

一种广泛使用且由来已久的方法是使用逗号分隔值，通常称为“CSV 文件”。这是一种简单的文件格式，用于以纯文本格式存储表格数据。在 CSV 文件中，每一行文本代表一条记录，每条记录中的字段由逗号分隔。这种结构大致相当于关系数据库中单个表中的值。制表符分隔值是其近亲；顾名思义，这里字段之间的分隔符是制表符而非逗号。如果数据本身包含分隔符（逗号、制表符、换行符），则需要采取额外措施，如加引号或转义。

CSV 文件的主要优势在于其简单性。该文件可以用任何文本编辑器打开和编辑，结构易于理解，只有行和列（尽管由于不同行的字段长度不同，列可能不太明显）。CSV 文件被各种应用程序广泛支持，包括电子表格、编程语言和数据库。它们非常紧凑，因为主要由数据组成，仅包含极少量的分隔符。因为它们不包含关于数据如何存储的信息，所以它们是不同种类系统之间进行直接数据传输的常用选择。此类文本文件在配合适当的查询工具（如 UNIX 环境中经典的 `AWK` 语言）时，也可用作简单的数据库。

然而，这种相同的缺乏结构限制了该格式的表达能力。没有内置方式来包含关于数据或文件本身的元数据。没有定义数据类型的方法。最重要的是，没有表达即使是中等复杂度的结构或关系的方法。

解决这些问题的需求促使人们对更复杂的表示法产生了兴趣。出现了两种主要替代方案：可扩展标记语言 (`XML`) 和 JavaScript 对象表示法 (`JSON`)。两者都被广泛使用，特别是用于系统间结构化数据的传输，尽管它们本身也可以用作信息存储。它们有一些共同特征。

1.  **它们基于文本。** 与 CSV 文件一样，`XML` 和 `JSON` 文件可以用简单的文本编辑器打开和编辑。然而，结构的复杂性会使这成为一项艰巨的任务。很容易犯编辑错误导致结构无效，并且除非适当地布局，否则很难直观地展现结构。因此，通常使用对符号约定敏感的专用编辑器。不过，结果仍然只是文本，可以使用标准工具进行存储和检索。

2.  **它们是分层的。** 元素可以包含其他元素（递归地），这导致数据被包含在一个树状结构中。即使原始数据不是天然的层次结构，也是这种情况。一个不可避免的后果是数据重复的可能性，这需要在数据存储中或使用数据的应用程序中进行管理。

3.  **它们使用“括号”表示法。** 数据元素包含在一对匹配的开始和结束定界符中，例如 `< x >`、`( x )`、`[ x ]` 或 `{ x }`。嵌套元素必须完全包含，因此 `< x < y >>` 可能是有效的，但 `<x < > y >` 肯定不是。

4.  **它们是非确定性的**，意思是相同的数据结构可以用不同但同样有效的方式表示。例如，在 `XML` 中，一个数据项可以作为属性的值或元素的内容出现。在这两者之间的选择可以由一些高层的非具体策略或数据的预期用途来指导，但这不受任何语言约束或工具的强制。这与关系场景中规范化规则的应用不同。

虽然 `XML` 和 `JSON` 都是基于文本的，但在结构化查询语言 (`SQL`) 术语中，它们也可以被视为复杂数据类型，与 `BLOB`、`DATETIME` 等并列，并且两者都已作为此类类型被 `SQL` 标准采纳。`XML` 在 `SQL:2003` 中作为数据类型被添加。`JSON` 通过 `SQL:2016` 中的文本操作引入，并在 `SQL:2023` 中作为数据类型引入。与文本相比，使用内置数据类型有一些优势。验证更简单，某些操作更高效，并且当输入或输出需要以 `XML` 或 `JSON` 形式呈现时，可以避免转换的开销。在本章中，我们将主要关注 `XML` 和 `JSON` 如何用于结构化数据的表示。

## 16.2 XML

`XML` 是万维网联盟 (`W3C`) 制定的一系列标准中的关键成员。1.0 版本首次出现于 1998 年，1.1 版本于 2004 年随之推出。随后的几次修订修正了勘误并提供了澄清。使用 `HTML`（本身于 1993 年推出）的 `WWW` 系统的增长暴露了对一种语言的需求，该语言提供了一种更强有力的方式来表示结构化数据，以支持跨不同系统和平台的无缝数据交换、转换和互操作性，并允许扩展以针对特定应用定制语言。

还有其他几个与 `XML` 相关的标准。除了 `XML` 本身（及其与 `SQL` 的关系）外，我们将在本章将主要讨论限制在以下内容：

**XPath**。这是一种表达式语言，提供了一种对 `XML` 树中的节点进行层次寻址的方法。除了对 `XML` 的树结构建模外，数据模型还包括原子值、函数项和序列。

**XQuery**。这是一种查询语言，旨在广泛适用于多种类型的 `XML` 数据源，包括结构化和半结构化文档、关系数据库和对象存储库。`XQuery` 智能地利用 `XML` 的结构来表达跨所有这些类型数据的查询，无论数据是物理存储在 `XML` 中，还是通过中间件视为 `XML`。

这两者反过来都依赖于 *XQuery 和 XPath 数据模型*。该模型定义了查询处理器输入中包含的信息，以及 `XQuery` 和 `XPath` 语言中表达式的所有允许值。这两种语言都已扩展以支持 `JSON` 以及 `XML`。

特定论域（UoD）的数据结构可以通过模式来定义。`XML Schema` 标准提供了一种定义 `XML` 文档的结构、内容和语义的方法。它取代了早期用于定义结构的文档类型定义（`DTD`）。可以针对模式验证 `XML` 文档，以确保其结构一致。与 `SQL` 一样，`XML` 定义了多种数据类型，尽管这些类型并不完全对应。`SQL` 规范（第 14 部分）定义了 `XML Schema` 与 `SQL` 数据类型之间的映射，但 `XML Schema` 是一个复杂的主题，我们将不会在本章中详细探讨。
