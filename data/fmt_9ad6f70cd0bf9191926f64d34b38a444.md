
# 跨站脚本的解决办法是什么？

在创建允许任何类型用户输入的 Web 应用程序时，开发人员必须确保执行输入验证。在最基本的层面上，应用程序绝不应允许用户在反射输入字段中包含 `<SCRIPT>` 标签。然而，这并不能完全解决问题；对于勤奋的 Web 应用程序攻击者来说，有许多巧妙的替代方案可用。最好的解决方案是确定应用程序将允许的输入类型，然后验证输入以确保其与该模式匹配。例如，如果应用程序有一个允许用户输入年龄的文本框，它应该只接受一到三位数字作为输入。应用程序应拒绝任何其他输入作为无效输入。

## 存储型/持久型 XSS

跨站脚本攻击通常利用反射输入，但这并不是攻击发生的唯一途径。另一种常见技术是将跨站脚本代码存储在远程 Web 服务器上，这种方法称为**存储型 XSS**。这些攻击被称为持久型，因为即使攻击者没有主动发动攻击，它们仍会保留在服务器上。

作为一个例子，考虑一个允许用户发布包含 HTML 代码消息的留言板。这非常普遍，因为用户可能想使用 HTML 为其帖子添加强调效果。例如，用户可能在留言板帖子中使用以下 HTML 代码：

```html
<p>Hello everyone,</p>
<p>I am planning an upcoming trip to <A HREF=
'https://www.mlb.com/mets/ballpark'>Citi Field</A> to see the Mets take on the
Yankees in the Subway Series.</p>
<p>Does anyone have suggestions for transportation? I am staying in Manhattan 
and am only interested in <B>public transportation</B> options.</p>
<p>Thanks!</p>
<p>Mike</p>
```

## 请求伪造

请求伪造攻击利用信任关系，试图让用户在不知情的情况下针对远程服务器执行命令。它们有两种形式：跨站请求伪造和服务端请求伪造。

### 跨站请求伪造（CSRF/XSRF）

跨站请求伪造攻击，缩写为 XSRF 或 CSRF 攻击，与跨站脚本攻击相似，但利用的是不同的信任关系。XSS 攻击利用用户对网站的信任在用户的计算机上执行代码。XSRF 攻击利用远程网站对用户系统的信任，代表用户执行命令。

XSRF 攻击基于一个合理的假设：用户通常同时登录到许多不同的网站。攻击者随后在一个网站中嵌入代码，该代码向第二个网站发送命令。当用户点击第一个网站上的链接时，他们在不知情的情况下向第二个网站发送了命令。如果用户恰好登录了第二个网站，该命令可能会成功。

例如，考虑一个在线银行网站。想要从用户账户窃取资金的攻击者可能会访问一个在线论坛并发布一条包含链接的消息。该链接实际上直接指向资金转账网站，发出一条将资金转入攻击者账户的命令。攻击者随后将链接留在论坛上，等待毫无戒心的用户前来点击该链接。如果用户恰好登录了银行网站，转账就会成功。

开发人员应保护其 Web 应用程序免受 XSRF 攻击。一种方法是创建使用安全令牌的 Web 应用程序，攻击者无法知道该令牌以将其嵌入链接中。另一种保护措施是网站检查从最终用户接收到的请求中的引用 URL，并且只接受源自其自身网站的请求。

### 服务端请求伪造（SSRF）

服务端请求伪造（SSRF）攻击利用类似的漏洞，但它们不是诱骗用户的浏览器访问 URL，而是根据用户提供的输入诱骗服务器访问 URL。当 Web 应用程序接受来自用户的 URL 作为输入，然后从该 URL 检索信息时，SSRF 攻击就成为可能。如果服务器有权访问非公开 URL，SSRF 攻击可能会无意中将该信息泄露给攻击者。

# 应用程序安全控制

尽管影响应用程序的众多漏洞是网络安全专业人员极为关注的重大问题，但好消息是，有许多工具可用于协助开发纵深防御安全方法。通过安全编码实践和安全基础设施工具的结合，网络安全专业人员可以构建强大的防御体系来抵御应用程序攻击。

## 输入验证

网络安全专业人员和应用程序开发人员手头有多种工具，可帮助防范应用程序漏洞。其中最重要的是 `input validation`（输入验证）。允许用户输入的应用程序应对该输入执行验证，以降低其包含攻击代码的可能性。不当的输入处理实践会使应用程序面临注入攻击、跨站脚本攻击和其他攻击。

最有效的输入验证形式是 `input whitelisting`（输入白名单），即开发人员描述预期从用户处接收的确切输入类型，然后在将输入传递给其他进程或服务器之前，验证该输入是否符合该规范。例如，如果输入表单提示用户输入年龄，输入白名单可以验证用户提供的值是否为 0–120 范围内的整数。应用程序随后会拒绝该范围之外的任何值。

由于许多允许用户输入的字段的性质，执行输入白名单验证通常很困难。例如，设想一个分类广告应用程序，允许用户输入待售产品的描述。要编写描述该字段所有有效提交且同时防止恶意代码插入的逻辑规则是很困难的。在这种情况下，开发人员可能会使用 `input blacklisting`（输入黑名单）来控制用户输入。采用这种方法时，开发人员不尝试显式描述可接受的输入，而是描述必须阻止的潜在恶意输入。例如，开发人员可能会限制用户输入中 HTML 标签或 SQL 命令的使用。执行输入验证时，开发人员必须注意字段中可能出现的合法输入类型。例如，完全禁止使用单引号（`'`）可能有助于防范 SQL 注入攻击，但也可能导致包含撇号的姓氏（如 O’Brien）难以输入。

## Web 应用程序防火墙

`Web application firewalls (WAFs)`（Web 应用程序防火墙）在保护 Web 应用程序免受攻击方面也发挥着重要作用。虽然开发人员应始终依靠输入验证作为抵御注入攻击的主要防线，但现实是应用程序有时仍会包含注入缺陷。这可能发生在开发人员测试不足，或供应商未及时为易受攻击的应用程序提供补丁时。

WAF 的功能类似于网络防火墙，但它们工作在应用层。WAF 位于 Web 服务器前方，如图 6.18 所示，并接收所有发往该服务器的网络流量。然后，它会仔细检查发往应用程序的输入，在将输入传递给 Web 服务器之前执行输入验证（白名单和/或黑名单）。这可以防止恶意流量到达 Web 服务器，并作为针对 Web 应用程序漏洞的分层防御的重要组成部分。

## 数据库安全

安全的应用程序依赖于安全的数据库，以提供支持业务运营所需的内容和事务处理。关系型数据库构成了大多数现代应用程序的核心，保护这些数据库不仅仅是防范 SQL 注入攻击。网络安全专业人员应深入了解安全的数据库管理实践。

### 规范化

`Database normalization`（数据库规范化）是数据库设计人员在构建和修改数据库时应遵循的一组设计原则。遵循这些原则的数据库被称为符合范式，范式按遵循原则的程度递增编号。最简单的范式是第一范式（1NF），更高级的范式依次递增（2NF、3NF 等）。

数据库社区就数据库设计人员应多严格地遵循范式进行着积极而健康的讨论。在切实可行的范围内尽可能实施这些原则的一些优势包括：规范化设计可做到以下几点：

*   防止数据不一致
*   防止更新异常
*   减少重构现有数据库的需求，以及
*   使数据库模式更具信息量

### 参数化查询

参数化查询提供了另一种保护应用程序免受注入攻击的技术。在参数化查询中，客户端不会直接将 SQL 代码发送给数据库服务器。相反，客户端将参数发送给服务器，服务器再将这些参数插入预编译的查询模板中。这种方法可防范注入攻击，还能提高数据库性能。

`Stored procedures`（存储过程）是某些数据库平台使用的参数化查询的一种实现示例。

### 混淆与伪装

在数据库中维护敏感个人信息会使组织面临风险，一旦该信息被攻击者窃取。数据库管理员应采取措施防范 `data exposure`（数据泄露）。

*   `Data minimization`（数据最小化）是最佳防御。组织不应收集不需要的敏感信息，并应在收集的敏感信息不再用于合法业务目的时尽快销毁。数据最小化可降低风险，因为你无法失去对你原本就没有掌握的信息的控制！
*   `Tokenization`（令牌化）使用查找表用唯一标识符替换可能直接揭示个人身份的个人标识符。例如，我们可以用一个随机生成的 10 位数字替换广为人知的值（如学生 ID）。然后我们维护一个查找表，以便在需要确定某人身份时将这些数字转换回学生 ID。当然，如果使用这种方法，你需要保护好查找表的安全！
*   `Hashing`（哈希）使用加密哈希函数将敏感标识符替换为不可逆的替代标识符。在哈希之前用随机数对这些值进行 `Salting`（加盐），可使这些哈希值能抵抗一种称为彩虹表攻击的攻击类型。你将在 第 7 章“密码学和公钥基础设施”中了解更多关于哈希、加盐和彩虹表攻击的内容。

## 代码安全

软件开发人员还应采取措施，保护其代码的创建、存储和交付。他们通过多种技术来实现这一点。

### 代码签名

`Code signing`（代码签名）为开发人员提供了一种向最终用户确认其代码真实性的方法。开发人员使用加密函数以其私钥对代码进行数字签名，然后浏览器可以使用开发人员的公钥来验证该签名，确保代码合法且未被未经授权的人员篡改。在缺乏代码签名的情况下，用户可能会无意中运行非真实代码。

### 代码复用

许多组织不仅在内部复用代码，还通过使用第三方软件库和软件开发工具包（SDK）来复用代码。第三方软件库是开发人员之间共享代码的常用方式。

#### 库和 SDK

库由执行相关功能的共享代码对象组成。例如，软件库可能包含一系列与生物学研究、金融分析或社交媒体相关的函数。开发人员无需编写代码来执行他们所需的每一个详细功能，只需找到包含相关函数的库，然后调用这些函数即可。

试图让库更易于开发人员使用的组织通常会发布软件开发工具包（SDK）。SDK 是软件库的集合，结合了文档、示例和其他资源，旨在帮助程序员在开发环境中快速上手。SDK 通常还包括专用工具，旨在帮助开发人员设计和测试代码。

当组织将代码开发外包给其他组织时，也可能将第三方代码引入其环境。安全团队应确保外包代码接受与内部开发代码同等级别的测试。

安全专业人员应熟悉其组织中使用第三方代码的各种方式，以及其组织向他人提供服务的方式。共享代码中出现安全缺陷的情况相当普遍，因此了解这些依赖关系并对安全更新保持警惕极为重要。

### 软件多样性

安全专业人员致力于避免其环境中的单点故障，以防止单个组件出现问题时引发可用性风险。这对软件开发同样适用。安全专业人员应留意组织中依赖单一源代码、二进制可执行文件或编译器的地方。虽然可能无法消除所有这些依赖，但跟踪它们是维护安全代码库的关键部分。

### 代码仓库

`代码仓库` 是用于存储和管理应用程序源代码的中心位置。代码仓库的主要目的是将软件开发中使用的源文件存储在一个中心位置，该位置允许安全存储并协调多个开发人员之间的变更。

代码仓库还执行 `版本控制`，允许跟踪变更并在需要时将代码回滚到早期版本。基本上，代码仓库执行软件开发的内务工作，使许多人能够以有组织的方式共同完成大型软件项目。它们还满足了安全和审计专业人员的需求，他们希望确保软件开发包含变更的自动审计和日志记录。

通过向组织中的所有开发人员公开代码，代码仓库促进了代码重用。寻求执行特定功能代码的开发人员可以在仓库中搜索现有代码并重用它，而不必从零开始。

代码仓库还有助于避免 `僵尸代码` 问题，即代码在组织中正在使用，但没有人负责维护该代码，事实上，甚至没人知道原始源文件驻留在何处。

### 完整性度量

代码仓库是应用程序安全的重要组成部分，但只是代码管理的一个方面。网络安全团队还应与开发人员和运维团队通力合作，确保应用程序通过组织批准的发布管理流程以安全的方式进行预配和取消预配。

此过程应包括代码完整性度量。代码完整性度量使用加密哈希函数来验证发布到生产环境的代码与之前批准的代码是否匹配。哈希值的任何偏差都表明代码被修改过，无论是有意还是无意，都需要在发布前进行进一步调查。

### 应用弹性

在设计应用程序时，我们应使其能够在不断变化的需求面前保持弹性。我们通过应用两个相关原则来实现这一点：

*   `可扩展性` 意味着应用程序的设计应使其所需的计算资源可逐步增加，以支持不断增长的需求。
*   `弹性` 进一步超越了可扩展性，它意味着应用程序应能在必要时自动预配资源以进行扩展，然后在不再需要时自动取消预配这些资源，以减少容量（和成本）。

# 安全编码实践

创建应用程序可能涉及多种开发风格、语言、框架和其他变量，但无论使用哪种，许多安全问题都是相同的。事实上，尽管许多开发框架和语言提供了安全功能，但相同的安全问题仍不断出现在应用程序中！幸运的是，许多通用的最佳实践可供你使用，以帮助确保组织的软件安全。

## 源代码注释

注释是优秀开发人员工作流程的重要组成部分。注释被战略性地放置在代码中，它们记录设计选择、解释工作流程，并提供对稍后可能被要求修改或排查代码的其他开发人员至关重要的细节。掌握在正确的人手中时，注释至关重要。

然而，注释也可能为攻击者提供解释代码如何工作的路线图。在某些情况下，注释甚至可能包含应保密的关键安全细节。开发人员应采取措施确保其代码的注释版本保密。对于编译型代码，这没有必要，因为编译器会自动从可执行文件中移除注释。然而，暴露其代码的 Web 应用程序可能允许远程用户查看代码中留下的注释。在这些环境中，开发人员应在部署前从生产版本的代码中移除注释。在归档的源代码中保留注释作为未来开发人员的参考是可以的——只是不要让它们在互联网上被未知人员访问！

## 错误处理

攻击者善于利用代码中的错误。开发人员必须理解这一点，并编写代码使其能抵御攻击者为测试代码边界而可能创建的意外情况。例如，如果 Web 表单请求年龄作为输入，仅验证年龄是否为整数是不够的。攻击者可能在该字段中输入一个 50,000 位的整数，试图执行整数溢出攻击。开发人员必须预判意外情况，并编写 `错误处理` 代码以安全的方式介入并处理这些情况。不当的错误处理可能使代码面临不可接受的风险水平。

从错误处理的另一面来看，过于冗长的错误处理例程也可能带来风险。如果错误处理例程解释了过多关于代码内部工作原理的信息，它们可能允许攻击者找到利用代码的方法。例如，图 6.19 显示了一个出现在法国网站上的错误消息，其中包含用于创建网页的 SQL 查询的详细信息。你不需要懂法语就能理解这可能允许攻击者确定表结构并尝试 SQL 注入攻击！

## 硬编码凭据

在某些情况下，开发人员可能会在源代码中包含用户名和密码。此错误有两种变体。首先，开发人员可能会为应用程序创建一个硬编码的维护账户，即使身份验证系统发生故障，也允许开发人员重新获得访问权限。这被称为 `backdoor`（后门）漏洞，之所以成问题，是因为它允许任何知道后门密码的人绕过正常身份验证并访问系统。如果后门被公开（或私下！）知晓，生产环境中的所有代码副本都将受到威胁。

硬编码凭据的第二种变体发生在开发人员在其源代码中包含其他服务的访问凭据时。如果该代码被有意或意外泄露，这些凭据就会为外部人员所知。当开发人员意外将包含 API 密钥或其他硬编码凭据的代码发布到公共代码仓库（如 `GitHub`）时，这种情况经常发生。

## 内存管理

应用程序通常负责管理其自身的内存使用，在这种情况下，不良的内存管理实践会破坏整个系统的安全性。

### 资源耗尽

我们需要关注的关于内存或系统上任何其他有限资源的问题之一是 `resource exhaustion`（资源耗尽）。无论是有意还是无意，系统可能会消耗掉其可用的所有内存、存储、处理时间或其他资源，导致系统瘫痪或无法用于其他用途。

`Memory leaks`（内存泄漏）是资源耗尽的一个例子。如果应用程序向操作系统请求内存，最终将不再需要该内存，并应将内存返还给操作系统供其他用途使用。在存在内存泄漏的应用程序中，应用程序未能返还其不再需要的部分内存，可能只是丢失了对已写入内存保留区域的对象的跟踪。如果应用程序长期持续这样做，会慢慢耗尽系统可用的所有内存，导致系统崩溃。重启系统通常能重置问题，将内存返还给其他用途，但如果内存泄漏未得到修正，循环将重新开始。

### 指针解引用

`Memory pointers`（内存指针）也可能导致安全问题。指针是应用程序开发中常用的概念。它们只是存储内存中另一位置地址的内存区域。
