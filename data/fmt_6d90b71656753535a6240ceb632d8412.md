
*   **计划**：指定所需功能，称为用户故事。它们用于确定迭代（时间线）并驱动详细规格说明。
*   **结对编程**：程序员以团队形式工作。
*   **四十小时工作周**：预测的迭代应足够准确，以预测完成项目所需的工时。如果程序员必须加班，则说明迭代规划有缺陷。
*   **全程客户参与**：客户随时可用，并密切监控项目。
*   **详细测试程序**：称为单元测试[[13]](#Ch009_459-508_B9780443187346000088.xhtml#bb0070)。

> **注意**
>
> XP 开发模型不应与 Microsoft Windows XP 混淆：极限编程对首字母缩写词“XP”的使用早于微软。

### 螺旋模型

螺旋模型是一种旨在控制风险的软件开发模型。Barry W. Boehm 创建了该模型，并在其 1986 年的论文《软件开发与改进的螺旋模型》中进行了描述（参见 [`portal.acm.org/citation.cfm?id=12948`](http://portal.acm.org/citation.cfm?id=12948)）。Boehm 指出：“螺旋模型的主要显著特征是它创造了一种风险驱动的软件过程方法，而非主要的文档驱动或代码驱动过程。它融合了其他模型的许多优点，并解决了它们的许多困难”[[8]](#Ch009_459-508_B9780443187346000088.xhtml#bb0045)。

螺旋模型重复项目的步骤，从适度的目标开始，以不断扩大的螺旋向外扩展（称为轮次）。螺旋的每一轮构成一个项目，每一轮可以遵循传统的软件开发方法，如修改的瀑布模型。每一轮都会进行风险分析。项目或过程中的根本缺陷更有可能在早期阶段被发现，从而导致更简单的修复。这降低了项目的整体风险：大型风险应被识别并缓解。

Boehm 使用螺旋模型开发了 TRW 软件生产力系统（TRW-SPS），这是一个复杂的软件项目，产生了 1,300,000 条计算机指令。“第零轮”是一项可行性研究，一个旨在确定 TRW-SPS 项目是否对组织具有重大价值、从而值得承担风险的小型项目。可行性研究表明该项目值得进行（低风险），项目随之向外螺旋扩展。后续轮次的交付物包括：

1.  操作概念（COOP）
2.  软件需求
3.  软件产品设计
4.  详细设计[[8]](#Ch009_459-508_B9780443187346000088.xhtml#bb0045)

每一轮包含多个重复步骤，包括原型开发，最重要的是风险分析。Boehm 的螺旋模型如图 9.5 所示。

![图 9.5 螺旋模型。来源：https://upload.wikimedia.org/wikipedia/commons/e/ec/Spiral_model_%28Boehm%2C_1988%29.svg。图片遵循 Creative Commons 许可。](img/f09-05-9780443187346.jpg)

### 快速应用开发（RAD）

**快速应用开发**（RAD）通过使用原型、“虚拟”GUI、后端数据库等快速开发软件。RAD 的目标是快速满足系统的业务需求；技术顾虑居于次要地位。客户深度参与整个过程。

根据医疗保险和医疗补助服务中心（参见 [`www.cms.gov/Research-Statistics-Data-and-Systems/CMS-Information-Technology/XLC/Downloads/SelectingDevelopmentApproach.pdf`](http://www.cms.gov/Research-Statistics-Data-and-Systems/CMS-Information-Technology/XLC/Downloads/SelectingDevelopmentApproach.pdf)），RAD“旨在快速生成高质量系统，主要通过迭代原型（在开发的任何阶段）、积极的用户参与和计算机辅助开发工具。这些工具可能包括图形用户界面（GUI）构建器、计算机辅助软件工程（CASE）工具、数据库管理系统（DBMS）、第四代编程语言、代码生成器和面向对象技术”[[14]](#Ch009_459-508_B9780443187346000088.xhtml#bb0075)。

### 原型法

原型法是一种迭代方法，将项目分解为较小的任务，创建系统设计特性的多个模型（原型）。这通过允许客户在最终产品完成前很久就看到逼真的结果来降低风险。与其他现代开发方法一样，客户参与度很高：客户检查原型以确保项目按计划进行并达到其目标。

“原型”一词可能有点误导：后期阶段的原型可能被用作实际的最终产品。原型可以被视为“工作模型”。原型法不是一个成熟的软件开发方法论：它被螺旋模型或 RAD 等其他迭代方法所使用。

### DevOps

传统软件开发是在开发人员、质量保证团队和生产团队之间严格分离职责的情况下进行的。开发人员拥有镜像生产模型的硬件和测试数据。他们将代码移交给质量保证团队，后者也拥有镜像生产模型的硬件以及测试数据。质量保证团队随后将测试过的代码移交给生产团队，后者拥有生产硬件和真实数据。

在旧的（不那么敏捷的）模型中：开发人员与生产环境没有直接接触，实际上通过职责分离被严格隔离在生产环境之外。

DevOps 是一种更敏捷的开发和支持模型，呼应了我们在本章前面了解到的敏捷编程方法，包括 Sashimi 和 Scrum。DevOps 是“运维和开发工程师共同参与整个服务生命周期的实践，从设计、开发过程到生产支持”[[15]](#Ch009_459-508_B9780443187346000088.xhtml#bb0080)。

### DevSecOps

DevSecOps 是一种将信息安全集成到开发过程中的敏捷方法。安全贯穿每一步。DevSecOps 宣言概述了目标：

*   **主动介入** 胜过 **总是说“不”**
*   **数据与安全科学** 胜过 **恐惧、不确定性和怀疑**
*   **开放贡献与协作** 胜过 **仅限安全需求**
*   **带有 API 的可用安全服务** 胜过 **强制安全控制与文书工作**
*   **业务驱动的安全评分** 胜过 **橡皮图章式安全**

#### 核心安全原则

*   **红蓝对抗渗透测试** 胜过 依赖扫描与理论漏洞
*   **7 × 24 主动安全监控** 胜过 在被告知事件后才被动响应
*   **共享威胁情报** 胜过 独自掌握信息
*   **合规运营** 胜过 靠记事板与核对清单 [¹⁶]

##### 持续集成与持续交付

持续集成与持续交付（CI/CD）是一种敏捷方法论，专注于通过流水线快速部署代码更新。它是核心 DevSecOps 实践之一。NIST 对 CI/CD 的描述如下：

> DevSecOps 在流程工作流中引入的一个独特概念是“流水线”的概念。有了流水线，就无需为启动/执行流程的每个阶段单独编写作业。取而代之的是，只有一个作业从初始阶段开始，自动触发与其他阶段（无论是顺序还是并行）相关的活动/任务，并创建一个无错误的智能工作流。
>
> DevSecOps 中的流水线根据其完成的总体任务和所包含的两个单独阶段，被称为 CI/CD 流水线。CD 可以表示持续交付或持续部署阶段。根据后一阶段的不同，CI/CD 可能涉及以下任务：
>
> *   **构建、测试、安全防护和交付**——经过测试的修改代码被交付到预发布区域。
> *   **构建、测试、安全防护、交付和部署**——预发布区域中的代码被自动部署 [¹⁷]。

#### 安全编排、自动化与响应

安全编排、自动化与响应（SOAR）是一种敏捷方法论，用于集中管理安全运营，包括事件处理与响应、漏洞扫描、安全信息与事件管理（SIEM）以及其他运营活动。其目标是将过去手动执行的任务自动化。它利用编排通过应用程序编程接口（API）来协调 SIEM、IDS/IPS、防火墙和威胁情报源的管理。这种安全设备的编排被称为 `软件定义安全`（SDSec），这类似于软件定义网络（详见第 5 章，领域 4：通信与网络安全）。

自动化包括诸如在自动漏洞扫描确定系统存在漏洞后为其打补丁等步骤。它利用人工智能识别安全事件，并执行事件响应剧本以采取具体行动，例如从用户收件箱中移除恶意邮件或隔离受感染的系统。

#### 软件配置管理

软件配置管理（SCM）是一种敏捷方法，可自动化系统管理任务，包括服务器部署和配置管理。SCM 实现了 `基础设施即代码`，允许通过 PowerShell、Python 等脚本语言构建和配置系统。Ansible、Chef、Puppet 和 Salt Stack 是流行的 SCM 工具。

#### SDLC

**系统开发生命周期**（**SDLC**，也称为**软件开发生命周期**或简称**系统生命周期**）是一种系统开发模型。SDLC 在 IT 行业广泛使用，但在考试语境下，SDLC 侧重于安全。可将“我们的” SDLC 视为“*安全*系统开发生命周期”：安全是隐含的。

在考试中，SDLC 关注每个阶段的安全性。该模型比许多应用开发模型更宽泛，关注整个系统，从选择/开发、运营需求到安全废弃。SDLC 有许多变体，但大多数遵循（或基于）美国国家标准与技术研究院（NIST）的 SDLC 流程。

NIST 特别出版物 800-14 指出：“安全与 IT 系统的其他方面一样，如果在整个 IT 系统生命周期中进行规划，则管理得最好。IT 系统生命周期有许多模型，但大多数包含五个基本阶段：启动、开发/获取、实施、运行和废弃” [¹⁸]。通常会增加额外步骤，其中最关键的是安全计划，它是任何 SDLC 的第一步。以下概述摘自 NIST SP 800-14：

*   **制定安全计划**：确保在 IT 系统生命周期的所有阶段都考虑到安全性，并且在每个阶段都完成安全活动。
*   **启动**：表达对系统的需求并记录系统的目的。
    *   **实施敏感性评估**：审视系统的安全敏感性及待处理信息。
*   **开发/获取**：对系统进行设计、采购、编程或开发。
    *   **确定安全需求**：确定技术特性（如访问控制）、保证措施（如对系统开发人员的背景调查）或运营实践（如安全意识和培训）。
    *   **将安全需求纳入规格说明**：确保前面收集的信息已纳入项目计划。
    *   **获取系统及相关安全活动**：可能包括开发系统的安全功能、监控开发过程本身的安全问题、响应变更和监控威胁。
*   **实施**：对系统进行测试和安装。
    *   **安装/启用控制**：系统通常带有被禁用的安全功能。这些需要被启用和配置。
    *   **安全测试**：用于认证系统；可能包括测试安全管理、物理设施、人员、程序、商业或内部服务（如网络服务）的使用以及应急计划。
    *   **授权**：授权（管理）官员对系统运行的正式授权，并明确接受风险。
*   **运行/维护**：系统通过硬件和软件的添加以及其他事件进行修改。
    *   **安全运营与管理**：示例包括备份、培训、管理加密密钥、用户管理和打补丁。
    *   **运营保障**：检查系统是否按照其当前的安全需求进行运行。
    *   **审计与监控**：系统审计是一次性或定期的事件，用于评估安全。监控是指持续进行的活动，检查系统或用户。
*   **废弃**：系统的安全退役。
    *   **信息**：信息可能被移至另一系统、归档、丢弃或销毁。
    *   **介质清理**：清除介质有三种通用方法：覆写、消磁（仅适用于磁性介质）和销毁 [¹⁸]。

请注意，“安全”或“保障”一词出现在 NIST SDLC 的每一个步骤中，从项目启动到废弃：这是 SDLC 的核心。

> **注意**
>
> 在考试中，“安全” SDLC 的每一步都包含安全。任何遗漏安全的步骤都是“错误答案”。此外，任何遗漏安全废弃作为最终生命周期步骤的 SDLC 计划也是“错误答案”。

#### 考试警告

不要求背诵每个 SDLC 的具体步骤，但务必理解 SDLC 流程的逻辑（安全）流向。

*   **启动：** 当发起人识别出需求或机会时开始。创建概念建议书。
*   **系统概念开发：** 定义概念的范围或边界。包括系统边界文档、成本效益分析、风险管理计划和可行性研究。
*   **规划：** 制定项目管理计划和其他规划文档。为获取实现解决方案所需的资源提供基础。
*   **需求分析：** 分析用户需求并开发用户需求。创建详细的功能需求文档。
*   **设计：** 将详细需求转化为完整、详细的系统设计文档。侧重于如何交付所需功能。
*   **开发：** 将设计转化为完整的信息系统。包括获取和安装系统环境；创建和测试数据库/准备测试用例步骤；准备测试文件；编码、编译、优化程序；执行测试就绪评审和采购活动。
*   **集成与测试：** 证明开发的系统符合功能需求文档中规定的需求。由质量保证人员和用户执行。生成测试分析报告。
*   **实施：** 包括实施准备、将系统部署到生产环境，以及解决在集成与测试阶段发现的问题。
*   **运行与维护：** 描述在生产环境中运行和维护信息系统的任务。包括实施后评审和过程评审。
*   **处置：** 描述系统生命周期结束的活动。重点在于数据的妥善保存 [[19]](#Ch009_459-508_B9780443187346000088.xhtml#bb0100)。

#### 集成产品团队

集成产品团队 (IPT) 是一个以客户为中心的团队，关注项目的整个生命周期：

> 集成产品团队 (IPT) 是一个由多学科人员组成的团队，他们共同负责交付定义明确的产品或流程。IPT 由负责规划、执行和实施被采购系统生命周期决策的人员组成。它包括来自与产品相关的所有职能领域的授权代表（利益相关者）——所有在项目成功中拥有利益的人员，如设计、制造、测试与评估 (T&E) 和后勤人员，尤其是客户 [[20]](#Ch009_459-508_B9780443187346000088.xhtml#bb0105)。

与传统的层级团队相比，集成产品团队是一种更敏捷的方法：“……摆脱层级决策模式，转向由集成产品团队跨组织结构进行决策的过程。这意味着我们正在打破体制障碍。这也意味着我们的高级采购人员处于接收模式——而不仅仅是传输模式。目标是对来自一线的想法保持开放态度，以获得认同和持久的变革” [[21]](#Ch009_459-508_B9780443187346000088.xhtml#bb0110)。

#### 软件托管

软件托管是指让第三方存储计算机软件归档副本的过程。这通常作为与专有软件供应商签订合同的一部分进行协商。供应商可能希望保守软件源代码秘密，但客户可能担心供应商倒闭（可能导致软件无人维护）。没有可用源代码的孤儿软件将无法获得未来的改进或补丁。

软件托管将源代码置于托管状态，由中立的第三方控制。合同严格规定了将源代码发布给客户的条件，通常是由于软件供应商的业务失败。

#### 代码仓库安全

私有/内部代码仓库的安全性主要归属于前文讨论的其他企业安全控制：纵深防御、安全认证、防火墙、版本控制等。

公共第三方代码仓库（如 GitHub ([`www.github.com`](https://www.github.com))）引发了额外的安全担忧。除了代码托管提供商本身的安全性之外，最重要的控制措施之一是利用双因素认证的安全认证。开发人员常犯的一个错误是意外将私有代码发布为公开。这包括意外发布包含密码或私钥的代码。许多犯罪分子拥有针对此类内容的自动化搜索工具。

##### 实例学习

###### 泄露密钥导致 6500 美元亚马逊账单

2015 年，Carlo van Wyk 通过 Microsoft Visual Studio 2015 将代码发布到其私有 GitHub 账户，“Visual Studio 中的一个简单 bug 导致本应发布到安全私有源代码仓库的源代码被发布到了公共仓库。随后发生的一系列事件让我背上了 6500 美元的账单” [[22]](#Ch009_459-508_B9780443187346000088.xhtml#bb0115)。
