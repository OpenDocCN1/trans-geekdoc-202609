
```
create sequence sequence-name [ as data-type | start with start-value | increment by increment-value | maxvalue value | no maxvalue | minvalue value | no minvalue | cycle | no cycle [ ,... ] ]
```

数据类型必须是标度为零的数值类型（例如 `integer`）。这些选项与前面讨论的标识列选项类似。序列的一个额外功能是，某些实现还允许零增量，使序列实际上成为一个全局常量值。

从序列获取下一个值的标准语法是：

```
next value for sequence-name
```

但某些实现可能对此有变体。它们也可能提供某种方式来访问最后生成的序列号而不生成新序列号，例如：

```
previous value for sequence-name
```

SQL 还定义了 `drop sequence` 和 `alter sequence` 命令，但因为这些命令的工作方式显而易见，我们在此不再讨论。

# 索引

*索引* 通常是键值的有序二叉树，带有指向存储数据的完整记录位置的指针。因为索引仅与物理建模相关，而与逻辑建模无关，所以 SQL 标准从未提及它们。然而，大多数商业系统允许用户使用诸如 `create [ unique ] index indexname on tablename ( index-column [ asc | desc ] [,...] )` 和 `drop index indexname` 之类的语法显式地创建和删除索引。优化器使用索引来提高性能，并可能自行创建和删除索引。如果受支持，唯一索引选项提供了一种强制唯一性约束的方法。然而，大多数唯一性约束最好使用 `primary key` 或 `unique` 声明来定义，尽管可选列上的唯一性约束通常需要触发器。索引通常会为主键和外键自动创建。

索引可以显著提高查询性能，尤其是对于大表，因为索引通常允许在主存中随机访问，而不是顺序磁盘访问。某些商业系统还可能允许将选定的索引指定为 *clustered*（聚集）。这会在索引列的值的逻辑顺序与行的物理存储顺序之间创建对齐，从而可能提高检索行数据的性能。显然，如果一个表有多个索引，只能选择一个作为聚集的基础；通常这将是主键列上的索引。

虽然索引可以提高查询效率（从而可能提高约束强制执行的性能），但也需要付出代价。索引可能会降低表的更新速度，因为对数据的任何更改不仅涉及基本表的更改，还涉及已定义的任何索引的更改。不过，根据具体情况，这种权衡可能仍然是可以接受的。各个 DBMS 可能提供多种不同类型的索引，选择索引的策略也可能因 DBMS 而异。由于本书主要关注概念和逻辑建模，因此不再进一步讨论索引策略。

## 游标

游标本质上是一种机制，用于为预先指定的 `select` 语句的结果提供逐行访问。只要正在使用游标（在此期间游标被称为 *open*（打开）），结果就会被保留。使用游标是一个四阶段过程。

1.  游标被 *声明*，这定义了 `select` 语句和游标的操作模式。
2.  游标被 *打开*，此时执行关联的 `select` 语句并形成临时结果表。
3.  应用程序浏览结果表，通常逐行进行，以 *提取* 任何所需操作所需的数据。
4.  当应用程序完成工作时，游标被 *关闭*，这将导致原始 `select` 语句的结果被删除。

直接从应用程序控制这些步骤是相当常见的做法。这是游标以运行迟缓著称的原因之一，稍后将更详细地讨论。

大多数供应商支持用于游标声明的基本 SQL-92 语法，如下所示。后续版本的标准中添加了一些细节，但这些并未影响基本的 SQL 游标概念。

*   ```
    declare cursor-name [ sensitive | insensitive ] [ scroll | no scroll ] cursor
    ```
*   ```
    for select_statement
    ```
*   ```
    [ for { read only | update [ of column_name [ ,... ] ] } ]
    ```

可选地，游标可以声明为 `for read only`（如果不需要更新，这能提高性能）或 `for update`，并可限制为特定列。声明为 `insensitive` 的游标会创建所用数据的临时副本，所有数据请求都从该临时表中应答。因此无法对基本表进行修改。如果省略 `insensitive` 或选择了 `sensitive` 选项，则对底层表所做的更改可能会反映在后续的提取中。`scroll` 选项指定应为游标启用一系列导航操作。如果省略，或选择了 `no scroll` 选项，则游标仅限于提取结果的下一行。一旦定义了游标，就可以将其打开。语法简直再简单不过了：

*   ```
    open cursor-name
    ```

`open` 子句没有更改 `select` 语句的选项；它只是执行关联游标声明中已定义的语句。它还将游标定位在结果集第一行之前。给定一个打开的游标，可以从 `select` 语句产生的结果中提取数据。

## 13.7 事务与并发

影响 DBMS 中数据的操作包含在事务中。一个事务可能由许多单独的动作组成，从某种意义上说，这些动作可以被视为一个原子活动单元。为了保持数据库的完整性，我们可以对是否接受一个活动单元的结果做出明确的决定。相应的数据库操作是 `commit`（提交），它使结果永久生效；以及 `rollback`（回滚），它中止活动并移除事务的结果，使数据库保持在事务开始前的状态。在某些情况下，`commit` 或 `rollback` 会隐式执行，具体取决于程序是正常终止还是异常终止。

如果数据库系统一次只处理一个事务，这种机制足以维护完整性。我们可以称这种理想情况为*串行*执行。然而，一个现实的数据库系统可能会有许多并发用户，每个用户执行他们自己的单独事务。因此，极有可能有多个用户在数据库的同一部分工作，例如，向同一张表读写数据。虽然我们可能期望事务内部的完整性，但当事务重叠时会出现一些潜在问题。可能出现以下情况。

### 脏读（也称为未提交读）

`Transaction1` 修改表中的一行。`Transaction2` 在 `Transaction1` 执行 `commit` 之前读取了该行。如果 `Transaction1` 随后执行 `rollback`，`Transaction2` 将读取到一行实际上从未真正存在过的数据。

### 不可重复读

`Transaction1` 从表中读取一行。`Transaction2` 修改了该行，或者可能将其删除，然后执行 `commit`。如果 `Transaction1` 尝试再次读取该行，会发现它已被更改，甚至可能完全消失！

### 幻读

`Transaction1` 读取满足搜索条件的某些行。`Transaction2` 随后创建了一些满足 `Transaction1` 所用搜索条件的行。如果 `Transaction1` 尝试使用相同的搜索条件再次读取这些行，将获得原始结果加上一些现在神秘出现的额外行。

可以通过资源上的*锁*来控制事务之间的交互。想要使用资源（如行或表）的事务可以获取一个锁，使其成为该资源的临时所有者。其他事务必须等待，直到第一个事务释放锁，然后才能竞争同一资源。典型序列如图 13.3 所示。

应用程序可以指定连接所需的隔离级别。如果未指定级别，DBMS 将假定一个默认值，例如 `READ COMMITTED`，这代表了隔离性和性能之间的合理折衷。有时也适合临时切换到不同的隔离级别以提高隔离性或性能。例如，从只读表读取数据的应用程序可以暂时降级到 `READ UNCOMMITTED` 级别以提高性能——在这种情况下不会损害隔离性，因为不会并发更新只读表，所以不会发生脏读。

实际的 DBMS 还必须处理锁的许多副作用。其中之一是*死锁*情况。`Transaction1` 需要资源 `A` 和 `B`，并成功获取了 `A` 的锁。同时，需要相同两个资源的 `Transaction2` 已获取了 `B` 的锁。结果是 `Transaction1` 因等待 `B` 而无法继续，`Transaction2` 因等待 `A` 而无法继续。大多数 DBMS 都有内置的后台进程来检测死锁情况。通常，通过回滚其中一个事务来自动解决死锁。另一个潜在问题是设计不良的应用程序获取锁并保留过长时间。同样，可以包含自动进程来检测此类情况并回滚有问题的事务。

## 13.8 安全性与元数据

本节简要介绍数据库管理员需要熟悉的两个主题：SQL 中的安全性和元数据。首先从安全性开始。当且仅当数据库上的操作只能由授权用户执行时，该数据库才是*安全*的。每个系统用户被分配一个用户标识符（`AuthID`）。"拥有"或创建数据库的用户拥有其所有访问权限，并可以向其他用户授予和撤销访问权限。SQL 提供了*授权语句* 以向用户授予各种权限。SQL-92 语法如下：

```
grant all privileges | select | insert [ (col) ] | update [ (col) ] | delete | usage | references [ (col) ] [,...] on object to user-list [ with grant option ]
```

其中 `object` 可以是 `[table] tablename`、`domain domainname` 等。用户列表可以包含 `public`，表示所有用户。SQL:1999 扩展了该语句以支持“角色”（用户组）。如果包含 `with grant option`，用户列表将拥有将相同权限授予他人的能力。例如，以下语句授予所有用户对 `Stock` 表的读取访问权限：`grant select on Stock to public`。以下语句授予授权 ID 为 "Mgr" 的用户对 `Stock` 表的读取访问权限以及更新 `price` 列中值的权限：`grant select, update(price) on Stock to Mgr`。可以使用*撤销语句* 移除权限：

```
revoke [ grant option for ] privilege-list on object from user-list [ restrict | cascade ]
```

例如，要撤销之前授予的更新权限，使用 `revoke update ( price ) on Stock from Mgr`。`grant` 或 `revoke` 语句中的表名可以是基表或视图的名称。授予视图访问权限而非基表是实施安全性的一种便捷方式。`restrict` 和 `cascade` 选项尚未被广泛支持。

除了数据库权限外，商业系统还提供对数据库服务器和 DBMS 实例相关操作的控制。一台服务器可能包含多个实例，一个实例可能支持许多单独的数据库。通常，角色按层次结构排列，层次结构较低级别的权限少于较高级别。例如，较低级别的管理员可能能够执行维护和实用程序操作，但无法访问存储在数据库中的数据。

现在，让我们转到*元数据*（关于数据的数据）。SQL 系统自动维护一组*系统表*，保存关于数据库模式本身的信息（例如基表、视图、域、约束和权限）。在商业 DBMS 中，这些表统称为各种名称，如“系统目录”。SQL-92 在不同意义上使用术语“catalog”（指环境中模式的集合）。商业系统的系统表还包括优化器使用的物理信息（例如关于索引的信息）。有权访问系统表的用户可以使用 SQL 查询它们（就像查询应用表一样）。

从 SQL-92 开始，SQL 标准通过名为 `DEFINITION_SCHEMA` 的特殊模式中的表和断言来定义元数据。这为元数据提供了参考模型，但不打算在任何商业实现中以这种方式实现——模拟其存在即可。预期的元数据访问是通过名为 `INFORMATION_SCHEMA` 的另一个模式中定义的*视图* 进行的。`INFORMATION_SCHEMA` 中的视图是根据 `DEFINITION_SCHEMA` 中的模型定义的。大多数视图定义了授予 `public` 的 `select` 权限，但未授予其他权限，因此这些视图无法更新。随着 SQL 后续版本中添加触发器等新功能，这些模式已得到扩展。

为了符合标准，DBMS 应支持这些视图，许多流行的 DBMS 至少正在着手支持。商业系统可能仍使用其特定的名称（例如 `SysTables`、`SysCatalog` 等）和结构来存储元数据。这些通常提供与标准模式等效的功能，但在详细语法上有所不同。

作为一个简单示例，以下查询使用标准的 `Columns` 视图请求 `Customer` 表中的列数：

```
select count ( * ) from Columns where table_name = 'CUSTOMER'
```

为了展示商业系统间的差异，SQL Server 中的等效查询可能如下：

*   ```
    select count ( * ) from sys.Columns
    ```
*   ```
    where object_id = object_id ( 'CUSTOMER', 'U' )
    ```

而在 DB2 中可能如下：

*   ```
    select count ( * ) from sysibm.Columns
    ```
*   ```
    where table_name = 'CUSTOMER'
    ```

## 13.9 总结

基本表模式可以使用*建表语句* 定义，其主要语法如下：

*   ```
    create table tablename (
    ```
*   ```
    colname data-type [ not null ]
    ```
*   ```
    [ default literal | null | user ]
    ```
*   ```
    [ primary key | unique ]
    ```
*   ```
    [ references tablename ]
    ```
*   ```
    [ check (col-condition-on-same-row) ]
    ```
*   ```
    [,...]
    ```
*   ```
    [, primary key ( col-list ) ]
    ```
*   ```
    [, unique ( col-list ) ]
    ```
*   ```
    [, foreign key ( col-list ) references tablename [ ( unique-col-list ) ] [,...] ]
    ```
*   ```
    [, check (table-condition-on-same-row) [,...] ] )
    ```

除了通过定义创建表（如刚才所示）外，表也可以**像**另一个表一样创建，或**作为**select 查询的结果创建。其他 SQL 语句用于修改和删除表等任务，其他类型的数据库对象也有相应的 alter 或 drop 语句。

视图可以使用*create-view 语句*创建，语法如下：

```
create view viewname [ ( col-list ) ] as select-query [ with check option ]
```

视图定义用于将针对视图的查询转换为针对基表的等效查询。某些视图是不可更新的（例如涉及连接的视图）。

触发器用于响应给定表或视图上下文中的特定事件。当检测到指定事件时，将执行触发器中的代码主体。触发器可以检查导致事件的数据，以确定适当的处理方式。创建触发器的基本语法是：

*   ```
    create trigger triggername
    ```
*   ```
    { before | after } { insert | delete | update [ of col-list ] } on tablename
    ```
*   ```
    [ referencing { old | new } [row] [ as ] correlation-name |
    ```
