### 15. Joe 从他的家用电脑访问公司网站 www.anybusi.com，看到一个包含令人不安图片的被篡改网站。他打电话给 IT 部门报告网站黑客攻击，他们他们没有看到网站有任何问题——文件没有被更改，而且从他们的终端（公司内部）访问时，网站显示正常。Joe 通过 VPN 连接到公司网站，发现网站显示正常。以下哪项可能解释这个问题？

**A.** DNS 投毒（DNS poisoning）

**B.** 路由投毒（Route poisoning）

**C.** SQL 注入（SQL injection）

**D.** ARP 投毒（ARP poisoning）

![Image](img/r.jpg)**A.** DNS 投毒在这里是最合理的解释。在许多情况下（例如我目前在家里办公的办公室里），连接到公司的 VPN 将会迫使你使用公司 DNS 而不是本地解析。在这个示例中，Joe 从家里进行的连接所使用的 DNS 查询服务器与业务网络使用的 DNS 服务器不同。完全可能有人更改了他本地服务器中的缓存条目，将其指向一个与托管真实网站不同的 IP 地址——这个 IP 是黑客设置的，用来提供被篡改的版本。网页文件没有发生变化，且从网络内部看网站显示正常，这一事实也证明了这一点。如果结果 Joe 的 DNS 修改是唯一的变动，那么极有可能是 Joe 正在被针对性地作为攻击目标——这一点 Joe 应该非常认真地对待。最后，`HOSTS` 和 `LMHOSTS` 文件在此类情况下也可能起着很大作用；然而，如果攻击者已经拥有了访问 Joe 计算机的这种权限，他面临的问题就比公司网站大得多了。

![Image](img/w.jpg)**B** 是错误的，因为路由投毒（route poisoning）与此毫无关系。路由投毒用于距离矢量路由协议，以防止路由表中的路由环路。

![Image](img/w.jpg)**C** 是错误的，虽然 SQL 注入确实是一种攻击攻击，但它与此无关。网页文件保持完整且未更改的事实证明了，通过 SQL 漏洞访问网站并非此处发生的情况。

![Image](img/w.jpg)**D** 是错误的，因为 ARP 投毒在特定的子网内部有效，而不是在子网外部（诚然，你可以通过配置了相应的路由器进行 ARP 转发，但这并不符合本题的情况）。ARP 投毒会将请求从同一子网内的一个机器重定向到另一台机器，与此处描述的场景几乎没有关系。虽然你可以从技术角度论证 ARP 投毒在这种场景下可能有效，但关键点在于关注显式的网段 DNS 设置。换句话之，Joe 的家庭网络极不可能成为 ARP 投毒的受害者，更有可能的答案是他的 ISP 的 DNS 被投毒了。

### 19. traceroute 使用什么方法来映射数据包通过的路由？

**A.** 通过在载荷中携带 hello 包，强制主机响应

**B.** 通过在每个跳处使用 DNS 查询

**C.** 通过操作生存时间 (`TTL`) 参数

![Image](img/r.jpg) **C.** Traceroute（至少在带有 `tracert` 命令的 Windows 机器上）通过在每次命中跳点并返回时将发送的每个数据包的 TTL 加 1 来跨越互联网跟踪数据，确保响应显式地从该跳点返回并返回其名称和 IP 地址。这提供了路由路径和传输时间。它通过使用 `ICMP ECHO` 包来报告从源到目的地之间每个“跳点”（路由器）的信息。顺带一提，Linux 机器默认使用一系列 UDP 包来执行 traceroute 的相同功能。
