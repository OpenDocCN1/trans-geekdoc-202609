## Performing On-Demand Debug Logging

If debug logging introduces an unacceptable burden on your application under normal operation, or if the sheer amount of debug log data overwhelms your available storage space, you might want the ability to enable debug logging on demand. One technique is to use a semaphore file to enable debug logging. A *semaphore file* is an empty file whose existence is meant as a signal to the logger to change its behavior. If the semaphore file is present, the logger outputs debug-level logs. Once you remove the semaphore file, the logger reverts to its previous log level.

Let’s use the `fsnotify` package to allow your application to watch for filesystem notifications. In addition to the standard library, the `fsnotify` package uses the `x/sys` package. Before you start writing code, let’s make sure our `x/sys` package is current:

```
$ go get -u golang.org/x/sys/...
```

Not all logging packages provide safe methods to asynchronously modify log levels. Be aware that you may introduce a race condition if you attempt to modify a logger’s level at the same time that the logger is reading the log level. The Zap logger allows you to retrieve a `sync/atomic`-based leveler to dynamically modify a logger’s level while avoiding race conditions. You’ll pass the atomic leveler to the `zapcore.NewCore` function in place of a log level, as you’ve previously done.

The `zap.AtomicLevel` struct implements the `http.Handler` interface. You can integrate it into an API and dynamically change the log level over HTTP instead of using a semaphore.

Listing 13-12 begins an example of dynamic logging using a semaphore file. You’ll implement this example over the next few listings.

*--snip--*

```go
func Example_zapDynamicDebugging() {
	tempDir, err := ioutil.TempDir("", "")
	if err != nil {
		log.Fatal(err)
	}
	defer func() { _ = os.RemoveAll(tempDir) }()

	debugLevelFile := filepath.Join(tempDir, "level.debug")
	atomicLevel := zap.NewAtomicLevel()
	zl := zap.New(
		zapcore.NewCore(
			zapcore.NewJSONEncoder(encoderCfg),
			zapcore.Lock(os.Stdout),
			atomicLevel,
		),
	)
	defer func() { _ = zl.Sync() }()
```

To do that, you need a new atomic leveler 2. By default, the atomic leveler uses the info level, which suits this example just fine. You pass in the atomic leveler 3 when creating the core as opposed to specifying a log level itself.

			}

		}
	}

## Scaling Up with Wide Event Logging

*Wide event logging* is a technique that creates a single, structured log entry per event to summarize the transaction, instead of logging numerous entries as the transaction progresses. This technique is most applicable to request-response loops, such as API calls, but it can be adapted to other use cases.

When you summarize transactions in a structured log entry, you reduce the logging overhead while conserving the ability to index and search for transaction details.

One approach to wide event logging is to wrap an API handler in middleware. But first, since the `http.ResponseWriter` is a bit stingy with its output, you need to create your own response writer type (Listing 13-15) to collect and log the response code and length.

*--snip--*

```go
package ch13

import (
	"io"
	"io/ioutil"
	"net"
	"net/http"
	"net/http/httptest"
	"os"

	"go.uber.org/zap"
	"go.uber.org/zap/zapcore"
)

type wideResponseWriter struct {
	http.ResponseWriter
	length, status int
}

func (w *wideResponseWriter) WriteHeader(status int) {
	w.ResponseWriter.WriteHeader(status)
	w.status = status
}

func (w *wideResponseWriter) Write(b []byte) (int, error) {
	n, err := w.ResponseWriter.Write(b)
	w.length += n
	if w.status == 0 {
		w.status = http.StatusOK
	}
	return n, err
}
```

*Listing 13-15: 创建一个 ResponseWriter 以捕获响应状态码和长度 (`wide_test.go`)*

新类型嵌入了一个实现 `http.ResponseWriter` 接口的对象 1。此外，你还添加了 `length` 和 `status` 字段，因为这些值最终是你想要记录的响应内容。你重写了 `WriteHeader` 方法 2 以便轻松捕获状态码。同样，你重写了 `Write` 方法 3 以保持已写入字节数的准确计数，并在调用方在 `WriteHeader` 之前执行 `Write` 时可选地设置状态码。

## 使用 Lumberjack 进行日志轮转

如果你决定将日志输出到文件，可以使用像 `logrotate` 这样的应用来防止日志占用所有可用的硬盘空间。

使用第三方应用管理日志文件的缺点是，该第三方应用需要向你的应用发送信号以重新打开日志文件句柄，否则应用会继续向已轮转的日志文件写入。

一个更不侵入且更可靠的选项是直接在 logger 中添加日志文件管理，使用像 `Lumberjack` 这样的库。Lumberjack 以透明的方式处理日志轮转，因为你的 logger 将 Lumberjack 视为任何其他 `io.Writer`。同时，Lumberjack 会为你跟踪日志条目计数并管理文件轮转。

Listing 13-18 在典型的 Zap logger 实现中添加了日志轮转。

*--snip--*

```go
func TestZapLogRotation(t *testing.T) {
	tempDir, err := ioutil.TempDir("", "")
	if err != nil {
		t.Fatal(err)
	}
	defer func() { _ = os.RemoveAll(tempDir) }()

	zl := zap.New(
		zapcore.NewCore(
			zapcore.NewJSONEncoder(encoderCfg),
			zapcore.AddSync(
				&lumberjack.Logger{
					Filename:   filepath.Join(tempDir, "debug.log"),
					Compress:   true,
					LocalTime:  true,
					MaxAge:     7,
					MaxBackups: 5,
					MaxSize:    100,
				},
			),
			zapcore.DebugLevel,
		),
	)
	defer func() { _ = zl.Sync() }()

	zl.Debug("debug message written to the log file")
}
```

*Listing 13-18: 使用 Lumberjack 在 Zap logger 中添加日志轮转 (`zap_test.go`)*

与 Listing 13-9 中的 `*bytes.Buffer` 类似，`*lumberjack.Logger` 2 不实现 `zapcore.WriteSyncer`，也不提供 `Sync` 方法。因此，你需要调用 `zapcore.AddSync` 1 将其包装。

Lumberjack 包含多个字段来配置其行为，尽管默认值是合理的。它使用进程名称格式 `<processname>-lumberjack.log` 保存在临时目录中，除非你明确指定日志文件名 3。你也可以选择压缩已轮转的日志文件以节省硬盘空间 4。默认情况下，每个轮转日志文件使用 UTC 时间戳，但你可以指示 Lumberjack 使用本地时间 5。最后，你可以配置在日志文件达到特定年龄后进行轮转（6），保留的轮转文件最大数量（7），以及在日志文件达到特定大小（以兆字节为单位）时进行轮转（8）。

你可以像直接向标准输出或 `*os.File` 写入一样继续使用 logger，只是 Lumberjack 会智能地管理日志文件。

### Histograms and Summaries

一个 *histogram（直方图）* 将值放入预定义的桶中。每个桶对应一个数值范围，并以其最大值命名。当观察到一个值时，直方图会为最小能容纳该值的桶的最大值的计数加 1。因此，直方图跟踪每个桶中观察到的值的频率。

让我们看一个快速示例。假设您有三个桶，分别为 0.5、1.0 和 1.5。如果直方图观察到值 0.42，它会为 0.5 桶的计数加 1，因为 0.5 是能容纳 0.42 的最小桶。它覆盖 0.5 及更小的值。如果直方图观察到值 1.23，它会为 1.5 桶的计数加 1，该桶覆盖 1.0 到 1.5 之间的值。自然，1.0 桶覆盖 0.5 到 1.0 之间的值。

您可以利用直方图观察到的值的分布来估算百分比或平均值。例如，您可以使用直方图计算服务中观察到的请求大小或响应大小的平均值。

一个 *summary（摘要）* 是带有少量差异的直方图。首先，直方图需要预定义桶，而摘要会自行计算桶。其次，指标服务器从直方图中计算平均值或百分比，而您的服务则从摘要中计算平均值或百分比。因此，您可以在指标服务器上对直方图进行聚合，但无法对摘要进行聚合。

一般建议是使用摘要在您不知道预期值的范围时使用，但我建议在可能的情况下使用直方图，以便在指标服务器上对直方图进行聚合。让我们用直方图来观察请求持续时间（参见 Listing 13-22）。
