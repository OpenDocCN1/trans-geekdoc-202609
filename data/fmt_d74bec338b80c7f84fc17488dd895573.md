
请注意 `City` 如何在此查询中用作连接对象类型。如果改用属性，查询构建会变得更加繁琐。如果允许复合属性，我们可能会使用 `List Employee.empNr where Employee.city = Branch.city and Branch.branchNr = 52`。如果不允许，我们可能不得不采用 `List Employee.empNr where Employee.cityName = Branch.cityName and Employee.stateCode = Branch.stateCode and Employee.country = Branch.country and Branch.branchNr = 52`。除了笨拙之外，这两种基于属性的方法都违反了**语义相关性**原则。因为 `City` 的标识方案与问题无关，所以不应强迫用户显式处理它。

即使我们有一个工具允许我们直接在 ER 或 OO 模型中构建查询，并且该工具显示当前对象类型的属性以便可能同化到查询中（类似于 `ActiveQuery` 显示高亮对象类型的角色），这也不会像 ORM 那样暴露直接连接。例如，检查 `Employee.city` 并不能告诉我们它与 `Branch.city` 存在某种连接。

在关系层面，我们有两个表：`Employee`（`empNr`、`countryCode`、`stateCode`、`cityName`……）和 `Branch`（`branchNr`、`countryCode`、`stateCode`、`cityName`……）。因为这些表中的城市属性之间没有外键引用来关联，自由文本查询工具依赖于连接被显式预先输入到字典中，这是一个有风险的假设。自动揭示所有连接可能性的唯一方法是将域本身作为连接性的基础，这是 ORM 的显著特征之一。

由于 `ConQuer` 查询基于 ORM，只要其含义持续存在，它们就会继续产生预期的结果。换句话说，如果问题的英文含义仍然适用，你永远不需要更改 `ConQuer` 查询。特别是，`ConQuer` 查询不受应用程序典型变更的影响，例如新事实类型的添加、约束的变更或某些特性相对重要性的变化。这确保了**语义独立性**（即，当底层结构的变更对含义没有影响时，概念查询独立于这些变更）。与基于属性的方法相比，这带来了更高的**语义稳定性**。

作为一个简单的例子，假设在我们的模型中，每个员工由员工编号标识，且恰好有一个性别和至多一个头衔。在现实世界中，一名员工可能有多个头衔（例如，“博士”、“教授”、“爵士”），但我们决定最多只记录其中一个。

现在假设我们想列出有头衔的员工及其性质。图 18.6(a) 显示了用于此目的的 ORM 模式和 `ConQuer` 查询。从 `Employee` 发出的两个分支之间存在一个隐含的**和**。图的其余部分显示了等效的 UML 类图、关系模式和 SQL 查询。SQL 代码不仅是亚概念的（空值是实现细节），而且是不稳定的，因为对头衔关系的一个简单概念约束变更也要求更改代码。

例如，假设我们更改业务规则，允许为同一员工记录多个头衔，并且我们还决定记录列出头衔所需的任何顺序（例如，“Prof. Dr.” 这一组合应按该方式列出，而不是 “Dr. Prof.”）。从 ORM 的角度来看，这种新情况如图 18.7(a) 所示。头衔关联上的唯一性约束从 `n:1` 放宽为 `m:n`，并添加了一个头衔优先级事实类型。这些模式变更对 `ConQuer` 查询没有影响，因为其含义仅与阴影部分的事实类型有关，而不涉及它们的约束，也不涉及额外的事实类型。由于阴影路径具有不变的语义，原始 `ConQuer` 查询的含义保持不变，因此可以重用。

对于基于属性的方法，业务变更要求对模型和查询进行重大更改。图 18.7 的其余部分显示了新的 UML 模式、新的关系模式和新的 SQL 查询。需要进行大量更改，因为关于头衔的事实现在存储在一个关联中，而不是一个属性中。第 10.1 节讨了另一种情况，即强制将用头衔甚至性别属性建模的事实重新建模为关联，以记录某些头衔（例如“爵士”）对特定性别的限制。相比之下，`ConQuer` 查询保持有效；唯一变化的是从查询自动生成的 SQL 代码。

面向对象的查询方法通常比 ER 或关系方法更成问题，因为关于事实如何分组为结构有许多额外的选择，并且用户必须接触这些结构才能提出问题。此外，随着业务领域的发展，这些结构可能会发生剧烈变化以维持性能。

在现实世界中，UoD 变更经常发生，需要更改数据库结构。修改存储查询的代码需要更多的工作。如果我们在逻辑层面工作，维护工作量可能非常巨大。我们可以通过在概念层面使用 ORM 工作，并让工具处理较低层面的转换，从而将变更对模型和查询的影响降至最低。

`ActiveQuery` 工具尽可能利用 ORM 约束的知识生成**语义优化**的 SQL 查询，以产生更高效的代码。例如，如果头衔角色实际上是强制性的，则前面的 `ConQuer` 查询在两种情况下生成的 SQL 都会简化为 `select empNr, gender from Employee`。该工具还可以为不同的后端生成不同的代码，以适应它们对 SQL 标准的不同支持，有时会生成针对临时表的查询链，以使查询能够运行。

刚才给出的简单示例说明了 `ConQuer` 如何实现语义清晰性、相关性和稳定性。让我们简要地看一下它的语义强度或表达能力。该语言支持常用的比较符（`=`、`<`、`in`、`like` 等）、逻辑运算符（`and`、`or`、`not`）和包函数（`count`、`sum` 等），以及用于概念左外连接的模态运算符（`possibly`）。子类型/超类型连接显示为 “`is`” 谓词。

在关系层面，需要两张表：`Employee`( empNr, branchNr, …); `Achieves`( empNr, rating )。此查询的 SQL 如下所示。这很棘手，特别是分支机构编号之间的最终相关性，甚至经验丰富的 SQL 程序员也可能难以应对。对于即使只有最少语言经验的大多数最终用户来说，等效的 `ConQuer` 查询将很容易。这表明了像 `ConQuer` 这样一种语言赋能最终用户的潜力。

```
select max(X1.branchNr), X2.empNr
from   Employee as X1, Achieves as X2
where X1.empNr = X2.empNr
group by X2.empNr
having max(X2.rating) >
              (select avg(X4.rating)
           from  Employee as X3, Achieves as X4
           where X3.empNr = X4.empNr
    and X3.branchNr = X1.branchNr)
```

`ActiveQuery` 允许你定义派生谓词并存储这些定义。这些派生谓词（或“宏”）随后可像基础谓词一样在其他查询中使用。子类型可被视为一种派生对象类型，其定义由 `ConQuer` 查询提供。例如，子类型 `MalePatient` 的实例总体可通过执行以下 `ConQuer` 查询获得：**Find each** Patient **who** is of Gender ‘M’。鉴于其通用性，`ConQuer` 可改编为一种极高层语言，用于指定派生规则。

约束可视为一种检查：即搜索违反该约束的查询返回空集。因此，约束也可用查询来表达。语言中可提供各种高层构造，使其比 SQL 提供的 not-exists-check-query 形式更自然。尽管此处无法详述，但很明显这种方法非常强大。

ORM 丰富的图形约束符号仍需辅以文本语言，以完整覆盖业务领域中发现的各类约束和派生规则。虽然 ORM 的图形约束可自动语言化，但像 `ConQuer` 这样的输入文本语言可用于定义其他业务规则，并自动映射到 SQL。尽管 `ActiveQuery` 工具目前已不再可用，但 `NORMA` 工具的相关工作正在进行中，旨在将 `FORML` 文本语言用于 ORM，并赋予其 `ConQuer` 的表达能力。这将产生一种极高层的文本语言，既适用于概念建模（包括事实类型、约束和派生规则），也适用于概念查询。

## 18.4 Schema Abstraction Mechanisms

有时，我们可能会觉得 ORM 模式图（甚至 UML、ER 或关系模式）所捕获的细节层级几乎令人窒息。然而，在开发、转换或映射模式时，这些细节至关重要。ORM 符号的设计旨在促进这些任务。正如我们所见，这些图表可自然地语言化并填充事实实例，其基于对象角色的符号允许直观地表达许多约束，而其对象类型揭示了将模式粘合在一起的语义域。所有这些有助于建模者获得完整正确的图景，并以严谨的方式转换模型，从而正式控制信息的损失或增加。

然而，一旦模式开发完成，我们有时可能希望隐藏部分信息，以获得快速概览或专注于某些方面。如果模式庞大且复杂，情况尤为如此。因此，需要**抽象机制**来从直接考量中移除不需要的细节。本节概述了几种较有用的方法。章节注释提供了进一步研究的参考。

一个显而易见的抽象策略是**模块化**。在此策略下，完整模式被“划分”为若干大小适宜的模块或子模式。一种方法是为不同的建模**视角**使用不同的模式。例如，UML 使用类图和对象图作为数据视图，使用状态图和活动图作为行为视图，等等。此外，你可能会使用纯概念模式进行分析，使用带注解或修改过的概念模式作为设计视图。

在给定的建模视角内，全局模式仍可能过大，无法一次性方便地检查，尽管墙面大小的模式有时对于查看深远联系非常有用。将全局模式图划分为独立单元格的一种简单方法是叠加网格。

然而，允许模块重叠通常更有用，这样例如同一对象类型可能出现在多个模块中。此技术还允许基于语义分组来构建模块，从而获得更大的灵活性。一种有用的技术是将全局模式划分为**可复用子模式**，稍后可将其导入其他模式或项目。最流行的技术是将给定模式划分为**页面**。每个页面应赋予有意义的名称，并包含适量的紧密耦合建模元素。

可使用多种方式指定模块间的连接，如超链接、注解和边界重叠（参考公路地图册）。电子浏览比硬拷贝浏览提供了更多可能性（如滚动、缩放、超文本导航），但也需照顾到标准页面的打印文档。

对于大型应用，原始模式可能由不同团队作为独立模块开发，稍后再集成。这对**模式集成**过程提出了额外要求。特别是，必须确保全局一致性，要么通过统一术语、约束和规则的处理方式达成一致，要么通过指定适当的翻译。理想情况下，应在开发早期就商定基本架构框架，并通过解决同义词和同形异义词问题，使所有建模者对词汇赋予相同含义。

例如，如果同一对象类型在一个模块中称为“Subject”，在另一个模块中称为“Course”，则将二者之一选为标准术语，另一个术语由其替代。如果不同模块中的不同对象类型或事实类型被赋予相同的名称或读法，则必须修改其中之一。只要它们能唯一引用，替代名称和读法可作为别名存储。

应就全局标识方案和约束达成一致。在必要时，可通过子类型支持上下文标识，并可添加文本约束以加强特定上下文的全局约束（例如，受限强制角色约束和受限唯一性约束）。对于某些应用（如联邦数据库），可能倾向于相关模块间的部分集成，而非全局集成。

另一个有用的抽象机制由**显示切换**或**分层**提供。例如，当角色名称和选定类别的约束或派生规则非当前关注点时，可将其显示切换关闭，以获得更简洁的图景。在 ORM 模式上，例如，我们可能切换关闭值列表、环约束、频率约束、集合比较约束、文本约束和派生规则，以专注于唯一性约束和强制角色约束。每个约束类别可视为一个约束层，建模者可随时选择查看哪些层。一种极端选项是切换关闭所有约束。

子类型显示可通过多种方式抑制。我们可以隐藏子类型定义规则或图形约束（如排斥约束和全覆盖约束）。我们可以仅隐藏部分子类型，最好以某种方式指示其他子类型的存在（如使用省略号或第 9 章中讨论的 UML 注解之一）。我们也可以将子类型折叠到其顶层超类型中。视模型类型而定，可隐藏各种其他建模元素（如引用方案或属性）。当需要额外细节层时，可再次切换开启其显示。虽然这种分层概念可适配硬拷贝（如使用一系列叠加透明胶片或渐进式详细打印输出），但理想情况下应结合计算机辅助软件工程（CASE）工具以交互方式加以利用。

## 18.5 进一步的设计层面

另一种抽象机制是**对象类型缩放**。在此，建模者选择一个感兴趣的对象类型，使显示聚焦于该对象类型及其直接**邻域**。对象类型将连同其所有事实类型一起显示。通过为缩放指定**逻辑半径**（例如，以谓词单位计），邻域可扩展以包含第一级缩放中对象类型的事实类型，依此类推。

`ActiveQuery` 使用此机制逐步向用户展开视野，为当前高亮的对象类型显示一谓词半径的邻域。`NORMA` 工具也为此提供了一个上下文窗口，允许扩展至三个谓词长度。

另一种在大型 ORM 模式中特别有用的抽象机制是基于**主要对象类型**的**细化层级**。这可以结合**属性抽象**使用，以提供 ER 模式或 UML 类图。

在开发概念模式时，平等对待所有对象类型很有用，因为对象类型的相对重要性取决于它在全局模式中扮演的所有角色。然而，一旦模式完成，该信息即可获得，并可用于确定哪些是最重要的或**主要对象类型**。Campbell 和 Halpin (1993) 开发了一种确定 ORM 模式中主要对象类型的程序，并将其作为生成外部用户界面默认屏幕窗体的基础（因为应用屏幕基本上使用户能够对主要对象执行操作）。

一旦确定了主要对象类型，ORM 图即可提升到更高的抽象层级。例如，我们可以选择仅显示**主要事实类型**（即至少有两个角色由主要对象类型扮演的事实类型）。对于大型模式，此图本身可接受相同的程序，产生更高层级的抽象，依此类推，直到获得顶层视图。只要完整的详细模式可访问，这种自底向上的抽象即可逆转，允许顶层视图逐步细化至详细的底层。

图 18.8 中的详细模式图有六个对象类型：`Movie`、`MovieTitle`、`Person`、`MoneyAmount`、`Country` 和 `Date`。直观上，这些在该领域中并非同等重要。哪些是主要对象类型？除了凭直觉判断，你还可以利用约束模式来辅助决定。特别是强制角色约束和唯一性约束相关。如果一个对象类型具有**显式**强制角色，则它是主要的。通常，扮演函数角色的对象类型也是主要的，但这并不总是成立（例如，即使 `MovieTitle` 的角色是函数式的，它仍是次要对象类型；其角色仍只是隐式强制的）。
