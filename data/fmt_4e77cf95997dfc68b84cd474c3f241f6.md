
NGFW 的功能已远远超出防火墙的传统范围，包含传统上在独立产品中才有的安全功能。潜在的扩展功能集，包括 Web 内容过滤、沙箱、反恶意软件、威胁情报和 HTTPS 解密等能力，可使组织潜在地降低在单独设备中维护这些功能的总体成本。

### 端点防火墙

防火墙的主要关注点历来是部署用于保护网络上系统集合的资产。虽然防火墙对于实现网络分段的重要性依然存在，但部署在单个端点上的防火墙提供了实质性的额外收益。在任何防火墙上执行的最基本配置涉及定义与各种网络相关的信任级别。历史上，这意味着信任内部资产并将所有非内部资产视为不受信。不幸的是，对手越来越多地利用横向移动（MITRE ATT&CK® 企业矩阵中的 TA0008 [[6]](#Ch008_361-457_B9780443187346000064_2.xhtml#bb0035)）降低了将内部等同于受信这一做法的有效性。

值得庆幸的是，端点防火墙为我们提供了一种技术上简单的方法来应对这种过度慷慨的内部信任区。端点防火墙有时被称为桌面防火墙或基于主机的防火墙，作为安装在单个系统上的软件运行。只有安装了端点防火墙的系统需要被隐性信任，这使得在对手从受损内部资产的有利位置发起攻击时，能够获得极大增强的保护和检测能力。

## 基础防火墙设计

防火墙设计多年来不断演进，从简单扁平的设计（如双宿主主机和屏蔽主机）发展到分层设计（如屏蔽子网）。虽然这些术语不再常用，且扁平设计已逐渐淡出使用，但了解基础防火墙设计仍然很重要。这种演进融合了网络纵深防御，从而导致了 DMZ 和更安全网络的使用。

### 堡垒主机

`堡垒主机` 是指放置在互联网上且未受其他设备（如防火墙）保护的任何主机。堡垒主机必须自我保护，并经过加固以抵御攻击。堡垒主机通常提供特定服务，所有其他服务都应被禁用。

### 双宿主主机

`双宿主主机` 拥有两个网络接口：一个连接到受信网络，另一个连接到不受信网络（如互联网）。双宿主主机不进行路由：如图 8.8 所示，希望从互联网访问受信网络的用户，会先登录到双宿主主机，然后从那里访问受信网络。这种设计在 1990 年代现代防火墙出现之前更为常见，有时仍用于访问遗留网络。

![图 8.8 双宿主主机。](img/f08-08-9780443187346.jpg)

### 屏蔽主机架构

`屏蔽主机架构` 是一种较旧的扁平网络设计，使用一台路由器通过访问控制列表 (`ACL`) 过滤进出 `堡垒主机` 的外部流量。堡垒主机可以访问其他内部资源，但路由器 `ACL` 禁止直接的内部/外部连接，如图 8.9 所示。

![图 8.9 屏蔽主机网络。](img/f08-09-9780443187346.jpg)

图 8.9 屏蔽主机网络。

双宿主主机与屏蔽主机设计的区别在于，屏蔽主机使用屏蔽路由器，该路由器过滤发往其他内部系统的互联网流量。屏蔽主机网络设计不采用网络纵深防御：堡垒主机的故障会使整个受信网络面临风险。屏蔽子网架构应运而生，通过使用 DMZ 网络实现了网络纵深防御。

### DMZ 网络与屏蔽子网架构

`DMZ` 是 `非军事区` 网络；该名称基于现实世界的军事 DMZ，如朝鲜和韩国之间的 DMZ。DMZ 是一个危险的“无人区”：这对军事 DMZ 和网络 DMZ 皆适用。

任何从不受信源（如互联网）接收流量的服务器都面临被攻陷的风险。我们使用纵深防御缓解策略来降低这种风险，包括打补丁、服务器加固和 `NIDS`，但总会残留一些风险。

出于这个原因，从不受信网络（如互联网）接收流量的网络服务器应放置在 DMZ 网络上。DMZ 的设计假设任何 DMZ 主机都可能被攻陷：DMZ 旨在遏制攻陷，防止其蔓延到内部受信网络。DMZ 上的任何主机都应经过加固。加固应考虑来自不受信网络的攻击，以及来自被攻陷的 DMZ 主机的攻击。

“经典” DMZ 使用两个防火墙，如图 8.10 所示。这称为 `屏蔽子网` 双防火墙设计：两个防火墙屏蔽 DMZ 子网。

![图 8.10 屏蔽子网双防火墙 DMZ 设计。](img/f08-10-9780443187346.jpg)

图 8.10 屏蔽子网双防火墙 DMZ 设计。

单防火墙 DMZ 使用一个防火墙，如图 8.11 所示。这有时被称为“三足式” DMZ。

![图 8.11 单防火墙 DMZ 设计。](img/f08-11-9780443187346.jpg)

图 8.11 单防火墙 DMZ 设计。

单防火墙设计要求防火墙能够过滤所有接口上的流量：不受信、受信和 DMZ。双防火墙设计更复杂，但被认为更安全。如果因防火墙故障导致攻陷，双防火墙 DMZ 需要两个防火墙同时故障，受信网络才会暴露。单防火墙设计仅需一次故障。

> **注意**
>
> 单独使用“DMZ”一词即暗示双防火墙 DMZ。

## Web 应用防火墙 (WAF)

Web 应用防火墙 (WAF) 并非仅仅是另一种类型或代的通用网络防火墙，而是一种完全独立且独特的控制措施。顾名思义，WAF 的唯一重点是提升组织在 Web 应用方面的安全态势，最常见的是组织自行开发的 Web 应用。WAF 的部署方式使其能够审查发往组织控制的 Web 应用的应用层流量。名称中的“防火墙”清楚地表明 WAF 通常旨在作为一种预防性控制使用。然而，即使配置为完全不阻断任何内容，它们也能提供实质性的检测收益。

组织最常为面向公众的应用程序部署 WAF，但也可用于增强面向内部的 Web 应用的安全性。WAF 可以通过多种方式部署，包括云托管、作为部署在托管应用的 Web 服务器前面的反向代理的本地部署，甚至作为运行在托管目标应用的 Web 服务器上的服务。这些第 7 层控制措施只需内联部署，使 Web 应用流量流经 WAF，以便其能够阻断公然恶意的流量或对可疑活动发出警报。

## 沙箱技术

基于签名的恶意内容预防方法存在一个主要的固有弱点；签名从根本上依赖于先验知识来创建。如果您的组织是首个遇到新型漏洞利用或技术的组织，基于签名的方法必然会失效。沙箱技术试图通过专注于识别可疑行为而非主要依赖签名来填补这一空白。

沙箱技术采用的总体思路是渲染或执行潜在的恶意内容，并分析在一个被充分理解、严格控制、专门用于此目的的牺牲系统上发生的变化。通过测量该虚拟系统上发生的行为和状态变化，沙箱工具可以判断被测文件是恶意、可疑还是良性。虽然沙箱技术既不完美也不充分，但对于与通过基于 Web 的下载或电子邮件获取的恶意内容相关的客户端利用，沙箱技术证明特别有用。

意图是以内联方式部署恶意软件沙箱，从而阻止被判定为恶意或过度可疑的内容的传递。然而，特别是对于基于 Web 的内容，沙箱工具行为分析引入的延迟可能会使其无法配置为阻止内容传递。即使在这种情况下，沙箱工具也能快速检测可疑内容，但需要采取自动或手动的纠正措施来响应警报。

## 端点安全

虽然大多数组织早已部署了边界防火墙、入侵检测系统（`IDS`）以及许多其他以网络为中心的预防和检测对策，但纵深防御要求采用额外的保护层。当防火墙、`IDS`、Web 内容过滤器等被绕过时，端点可能会被攻破。

由于端点是攻击的目标，端点本身的预防和检测能力提供了超越以网络为中心的安全设备的一层防护。现代端点安全套件通常包含除简单防病毒软件之外的无数产品。这些套件能将安全对策的深度提升到远超网关或网络边界的程度。

虽然纵深防御本身是一个值得称道的目标，但端点安全套件为现代组织提供的显著优势远不止安全深度的增加。即使设备超出了组织的边界，这些工具也能帮助提升设备的安全态势，无论是因为设备物理移动，还是因为用户将内部设备连接到了 Wi-Fi 或蜂窝网络。端点安全产品提供的另一项优势是，即使通信一直加密到相关端点，它们也能提供预防和检测控制。与端点安全相关的典型挑战在于容量考量：必须管理大量的产品/系统；必须分析并可能保留大量数据。

许多端点产品可被视为整体端点安全套件的一部分。其中最重要的包括防病毒、应用程序白名单、可移动介质控制、磁盘加密、主机入侵防御系统和桌面防火墙。

> **注意**
>
> 有关主机入侵检测系统（`HIDS`）和主机入侵防御系统（`HIPS`）的详细信息，请参阅下文的“HIDS 和 HIPS”部分。有关桌面防火墙的详细信息，请参阅上文的“防火墙”部分。

### 反恶意软件/防病毒

部署最广泛的端点安全产品是反恶意软件，仍普遍称为防病毒软件。许多功能齐全的端点安全套件都是从最初仅提供基于特征码的防病毒产品逐渐演变而来的。防病毒产品常因持续无法阻止恶意软件传播而受到诟病。然而，反对防病毒的大多数论点似乎都在抱怨这些产品单独使用不足以阻止恶意软件。遗憾的是，没有能阻止恶意软件的灵丹妙药，在出现之前，防病毒或反恶意软件产品将继续是必要的，尽管它们并不充分。防病毒是端点安全纵深防御中的一层（众多层之一）。

虽然防病毒供应商通常采用启发式或统计方法进行恶意软件检测，但检测恶意软件的主要手段仍然是基于特征码的。基于特征码的方法要求防病毒供应商拥有恶意软件样本以创建特征码。这是应用程序黑名单的一个例子，现在有时称为阻止列表（请参阅下文的“应用程序白名单/应用程序控制”部分）。对于快速变异的恶意软件或以前未遇到过的恶意软件，基于特征码的检测成功率要低得多。

### 应用程序白名单/应用程序控制

应用程序白名单，也称为应用程序控制，是端点安全套件中较新增的功能。应用程序白名单的主要重点是预先确定哪些二进制文件被认为可以在给定系统上安全执行。一旦建立了这个基线，任何不在已知良性二进制文件列表中、试图运行的二进制文件都将被阻止执行。这种方法的一个弱点是，当攻击者利用“已知良性”二进制文件并将其用于恶意目的时。

白名单技术包括允许运行以下二进制文件：

*   通过受信任的代码签名数字证书签名的
*   与已知良性的加密哈希匹配的
*   具有受信任的完整路径和名称的

最后一种方法最弱：攻击者可以用恶意版本替换受信任的二进制文件。

应用程序白名单优于应用程序黑名单（后者禁止已知的恶意二进制文件）。

### 可移动介质控制

另一个进入大型套件的较新端点安全产品协助进行可移动介质控制。对更好地控制可移动介质的需求在两个方面尤为强烈。首先，将感染恶意软件的可移动介质插入组织计算机，一直是攻破原本相当安全的组织的一种方法。其次，指甲盖大小的介质能容纳惊人的存储量，并被用于秘密窃取敏感数据。

恶意软件传播的常见载体是许多较新版 Microsoft 操作系统的 `Autorun`（自动运行）功能。如果将格式正确的可移动驱动器插入支持 `Autorun` 的 Microsoft Windows 操作系统，介质根目录下 `Autorun.inf` 文件引用的任何程序都将自动执行。许多形式的恶意软件会向所有驱动器的根目录写入恶意的 `Autorun.inf` 文件，试图在驱动器被移除并连接到另一个系统时病毒式传播。

最佳实践是在 Microsoft 操作系统上禁用 `Autorun`。请参阅 Microsoft 文章“如何在 Windows 中禁用 Autorun 功能”（[`support.microsoft.com/kb/967715`](https://support.microsoft.com/kb/967715)）以获取禁用 `Autorun` 的信息。

主要由于这些问题，组织被迫对可连接到设备的可移动介质类型实施更严格的控制。可移动介质控制产品是与禁止未经授权使用可移动介质的策略授权等管理控制相匹配的技术控制。

### 磁盘加密

另一个越来越常见的端点安全产品是磁盘加密软件。组织通常强制要求使用全盘加密产品，以防止落入未经授权之手的硬盘上的敏感数据泄露，尤其是移动设备，因为它们面临更高的被盗风险。

#### 全盘加密 (FDE)

全盘加密 (FDE)，也称为整盘加密，可加密整个磁盘。这优于部分加密解决方案，例如加密卷、目录、文件夹或文件。后一种方法的问题在于存在将敏感数据留在磁盘未加密区域的风险。例如，将文件从未加密目录拖放到加密目录可能会留下作为未分配数据的未加密数据。

## 持续监控

威胁、漏洞和资产形势在不断变化。组织历来最关注季度扫描、年度审计，甚至临时审查期间的安全性。虽然定期检查很有价值，但对手的 24×7 特性始终存在。持续监控的一个目标是迁移到内联模式。从架构上讲，主动响应 `NIPS` 类似于图 8.12 中的 `NIDS`；区别在于监控接口是读/写的。主动响应 `NIPS` 可通过多种方法“拦截”恶意流量，包括向源、目的（或两者）伪造 TCP RST 段，或向源发送 ICMP 端口、主机或网络不可达消息。

`Snort` 是一款流行的开源 `NIDS` 和 `NIPS`（参见 [www.snort.org](http://www.snort.org)），具有以下主动响应规则：

*   `reset_dest`：向目的发送 TCP RST
*   `reset_source`：向源发送 TCP RST
*   `reset_both`：向源和目的均发送 TCP RST
*   `icmp_net`：向源发送 ICMP 网络不可达
*   `icmp_host`：向源发送 ICMP 主机不可达
*   `icmp_port`：向源发送 ICMP 端口不可达
*   `icmp_all`：向源发送 ICMP 网络、主机和端口不可达

内联 `NIPS` 处于流量“内联”位置，通过放行或允许流量发挥第 3-7 层防火墙的作用，如图 8.13 所示。

### HIDS 和 HIPS

基于主机的入侵检测系统（`HIDS`）和基于主机的入侵防御系统（`HIPS`）是 `NIDS` 和 `NIPS` 的基于主机的对应物。它们处理主机内部的信息。它们可能会在网络流量进入主机时进行处理，但考试的重点通常在于文件和进程。

一个著名的 `HIDS` 是开源 Tripwire®，在该公司扩展其商业产品之前，它仅被称为 Tripwire（参见 [`github.com/Tripwire/tripwire-open-source`](https://github.com/Tripwire/tripwire-open-source)）。开源 Tripwire® 通过检测关键操作系统文件的变更来保护系统完整性。变更通过多种方法进行检测，包括加密哈希的比较。

### 模式匹配

模式匹配 `IDS` 通过将事件与静态特征码进行比较来工作。关于前面提到的 Log4Shell 漏洞，Crowdstrike 指出：“可以通过检查日志文件中是否存在特征 URL 模式 `${jndi:ldap://` 来检测利用尝试” [[7]](#Ch008_361-457_B9780443187346000064_2.xhtml#bb0040)。基于该信息，可以使用以下模式来检测此类尝试性的 Log4Shell Log4j2 利用。如果字符串 `${jndi:ldap://` 出现在发往组织 Web 服务器的流量中：警报。

模式匹配非常适合检测已知攻击，但通常在面对新攻击时表现不佳。

### 协议行为

协议行为 `IDS` 对协议应有的工作方式建模，通常通过分析 RFC（征求意见稿）来实现。RFC 793（TCP，参见 [`datatracker.ietf.org/doc/html/rfc793`](https://datatracker.ietf.org/doc/html/rfc793)）描述了 TCP 标志。SYN 表示同步，FIN 表示结束。一个标志用于创建连接，另一个用于终止连接。

基于对 RFC 793 的分析，生成的协议行为规则可以是“如果单个数据包中同时设置了 SYN/FIN 标志：警报。”根据 RFC，单个段尝试同时开始和结束连接是讲不通的。

攻击者会构造此类“损坏”的段，因此协议行为确实能检测到恶意流量。问题在于汉隆剃刀，这是一条格言，内容为：“永远不要将恶意归因于那些用愚蠢即可充分解释的事物” [[8]](#Ch008_361-457_B9780443187346000064_2.xhtml#bb0045)。协议行为还会检测“愚蠢的”（损坏的）流量：由未阅读或遵循 RFC 的开发人员设计的应用程序产生的流量。这相当常见：应用程序“能用”（流量流动），但违背了 RFC 的初衷。

> **注意**
>
> 所有信息安全专业人员都应理解汉隆剃刀。我们的世界充满了恶意：蠕虫、网络钓鱼攻击、身份盗窃等。但愚蠢和破坏更多：大多数灾难都是由用户错误引起的。

### 异常检测

异常检测 `IDS` 通过建立正常流量的基线来工作。异常检测 `IDS` 随后忽略该流量，报告不符合基线的流量。

与模式匹配不同，异常检测可以检测新攻击。挑战在于建立“正常”的基线：这在小型可预测的网络上通常很简单，但在大型复杂的网络上可能非常困难（甚至不可能）。

## 出站监控

历史上，对入侵和对手活动的检测主要专注于进入我们更受信任的内部网络的攻击流量；入侵检测系统（`IDS`）天然契合这一范式。出站监控采取相反的方法，专注于通过监视离开我们网络的内容来进行检测。许多利用后活动，包括命令与控制（`C2`）和数据渗漏，自然必然会导致可能通过监控流出我们网络的流量来辨别的流量模式。利用出站监控成功检测对手的一个经典示例是，通过观察源自预期内部邮件服务器以外的系统且目标为 TCP 25 端口的流量，识别出发送垃圾邮件的受感染主机。

## 安全信息和事件管理

入侵检测系统（`IDS`）长期以来一直是组织使用的主要技术侦查控制手段。尽管 `IDS` 的重要性并未减弱，但组织现在认识到，除了 `IDS` 之外，更多数据源可以提供有价值的信息。这些不同的信息源可以提供各自有价值的数据；组织越来越看重能够更高效地关联来自多个来源的数据。

安全信息和事件管理（`SIEM`）是用于简化跨不同来源数据关联的主要工具。关联安全相关数据是 `SIEM` 提供的主要效用。数据关联的目标是更好地理解背景，从而因跨各种安全平台记录的活动而更深入地了解组织内部的风险。虽然 `SIEM` 通常带有一些内置警报，用于查找特定的关联数据，但可以创建自定义关联规则以增强内置功能。
