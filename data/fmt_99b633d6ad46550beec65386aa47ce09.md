声明模式的过程通常称为数据定义，专门为此任务设计的语言组件称为`数据定义语言`（DDL）。我们的示例足够简单，关系模式可以在标准 SQL 的 DDL 组件中完全指定。然而，通常有些约束必须单独编码。

关系模式可能包含表定义、约束和派生规则。概念模式中的大多数派生规则可以通过在关系 DBMS 中定义视图（虚拟表）或计算列，或通过编写触发器或存储过程来指定。如果某类查询常用且需要派生，则会在概念模式的派生规则部分显式包含它。相比之下，临时查询则通过在查询语言本身中包含派生函数和运算符来处理，以便用户可以在查询构建本身中表达所需的派生规则。

在 SQL 等关系数据库语言中，表达许多数学和逻辑派生规则相当容易（例如，平均值，或从父母关系派生的祖父母关系）。一些难以在 SQL 中表达的派生规则可以用其他语言轻松表达。例如，以下 Prolog 规则以父母关系为基础递归地定义了祖先关系：

```
X is an ancestor of Y if X is a parent of Y. X is an ancestor of Y if X is a parent of Z and Z is an ancestor of Y.
```

SQL 标准支持递归查询，但商业 SQL 产品对该特性的支持程度各异。不直接支持递归的商业 SQL 产品通常支持从 SQL 调用其他语言（如 C# 或 Prolog）以执行所需的递归或其他期望任务。

Prolog 等语言用于某些 AI 应用。过去，AI 系统倾向于处理大量复杂事实类型的小规模总体，而数据库系统处理少量简单事实类型的大规模总体。下一代技术的目标之一是将强大的推理能力与高效的数据库管理相结合。

一旦定义了模式，就可以开始`数据操作`。最初为空的表将填充数据（即`插入`行）。随后可以`删除`或`修改`行。如果一行的一个或多个值发生变化，则该行被修改：在 SQL 的上下文中这有时称为“更新”，但我们笼统地使用“更新”一词来包含插入、删除和修改操作。这三种操作统称为`数据维护`。如果约束指定得当，当发生维护操作时，DBMS 会自动强制执行它们。

从概念上讲，关系型 DBMS 的行修改操作只是添加或删除基本事实。例如，将图 2.6 中 `Employee` 表第三行的“Adams, Ann”改为“Smith, Ann”，只是删除了员工 006 名为“Adams, Ann”这一事实，并添加了员工 006 名为“Smith, Ann”这一事实。当然，在外部层面，用户只需修改表单的屏幕版本（如图 2.5 所示）或表行（如图 2.6 所示）中的值。

数据操作的另一个方面是`数据检索`。这通常涉及三个步骤：用户请求信息；系统搜索数据库和/或模式以定位相关信息并利用它获得所需结果；然后系统输出该结果。第二阶段可能涉及对数据进行排序和/或派生结果（例如平均值）。与维护操作不同，检索操作不会改变数据库。

`数据呈现`是指在屏幕上显示信息（屏幕显示）或生成格式化打印输出（报表编写）的特殊技术。我们笼统地使用“`输出报表`”一词来包括屏幕报表和硬拷贝报表。

通常，关系数据库应用程序的用户不会直接与存储数据的关系表进行交互。通常，他们通过 `forms interface`（表单界面）输入和访问数据。诸如屏幕表单的设计与管理、以及 `security`（安全性）实施等问题，往往构成了应用程序开发的主要部分。

出于正确性、清晰性、完整性和可移植性等原因，数据库设计应首先被指定为概念模式，然后再映射到实际的数据库模式。

## 2.4 开发框架

信息系统开发至少涉及 `four worlds`（四个世界）：主题世界、系统世界、使用世界和开发世界 (Jarke et al., 1992)。`subject world`（主题世界）即 UoD（论述域），或业务领域，通常是现实世界的一部分。`system world`（系统世界）是信息系统对 UoD 的模型，因此是一种形式化的抽象。

`usage world`（使用世界）是系统运行所在的组织世界，包括系统的用户群体、他们与系统的用户界面、相关活动等。这有时被称为论述环境。`development world`（开发世界）涵盖用于开发系统的环境和过程，包括建模人员和程序员、他们的设计方法和基本原理、项目进度安排等。

系统世界有时被称为 `information system in the narrow sense`（狭义信息系统），而四个世界的组合被称为 `information system in the broad sense`（广义信息系统），因为它包含了所有相关的人为因素。专注于系统世界的专家被称为 `dry`（干派，他们处理形式化方面），而专注于其他三个世界的专家被称为 `wet`（湿派，他们愿意亲自处理非形式化的、较软性的方面）。在实践中，干派和湿派方法都是必要的。

确定 `automation boundaries`（自动化边界，即主题世界中有多少将由系统世界管理）是一项关键决策。我们首先应确定业务要提供的服务（即基本业务流程）。然后，针对这些服务中的每一项，我们需要决定是将其完全自动化、半自动化，还是人工操作。

为业务领域开发信息系统本质上是一个 `problem-solving`（问题求解）过程。这一通用过程可分解为四个主要阶段：(1) 定义问题，(2) 制定计划，(3) 执行计划，(4) 评估结果。最通用的两种问题求解策略是：将问题分解为若干 `subproblems`（子问题）并单独处理，以及先尝试问题的一个 `simpler`（更简单）版本。

当问题求解过程涉及软件开发时，它被细化为图 2.8 所示的五阶段 `software life cycle`（软件生命周期）：`specify`（规格说明，说明软件要做什么）、`design`（设计，决定怎么做）、`implement`（实现，编写代码）、`test`（测试，检查是否工作）、`maintain`（维护，保持运行）。在天真的“瀑布”版本中，这五个阶段的路径是一个简单的序列。然而在实践中，该过程通常具有 `cyclic`（循环）性质，如虚线箭头所示。

*   需求分析

*   生产版本实现
*   测试与验证
*   软件、文档和培训发布
*   维护

在实践中，这些阶段往往重叠，反馈循环很常见，且某些阶段可能被省略。存在许多详细程序来充实这些阶段。

**可行性研究** 确定拟议信息系统的主要目标，并判断哪些组件可利用已知资源（如预算分配和人员）实施。它考察替代方案的成本效益，并为各个系统组件分配优先级。成本/效益分析可能揭示某些目标不切实际，或者某些目标通过改进人工程序而非使用计算机能更好地实现。

假设项目获批，将进行详细的 **需求分析**，以确定系统具体需要做什么。系统组件被划定界限，并对熟悉相关应用领域的人员进行访谈，包括领域专家、预期用户和决策者。访谈可辅以问卷调查。需检查相关文档（如表单、报表、图表、政策手册，甚至待重构的遗留系统代码）。

在无此类文档可用的情况下，会请求领域专家编造要记录的信息种类的示例。常使用简单图表来说明信息系统如何与业务环境交互。识别并确定要支持的主要操作或事务的优先级，并估算其预期数据量、频率和所需响应时间。

这一需求收集与分析阶段的输出是一份 `requirements specifications`（需求规格说明）文档，详细说明功能性需求、非功能性需求（如性能）和维护信息（如预期变更）。

该文档应当 `unambiguous`（无歧义）、`complete`（完整）、`verifiable`（可验证，即有办法检查需求是否得到满足）、`consistent`（一致，需求之间不相互矛盾）、`modifiable`（可修改，可轻松安全地进行更改）、`traceable`（可追踪，需求可追溯到其来源，并在文档的不同版本中被识别）以及 `usable`（可用，供文档的当前和未来用户使用）。

各种文本和图形符号用于需求规格说明的不同方面。一些面向过程的符号（如用例图、上下文图、数据流图）将在后续章节讨论。对于大型复杂项目，需求分析阶段可能耗时数月。由于面向事实的建模利用熟悉示例的口语化来阐明 UoD，其概念设计方法也适用于数据需求分析。

衡量需求活动进度的一种方法采用需求工程的以下三个维度：`specification`（规格说明：不透明、一般、完整）、`representation`（表示：非正式、半形式化、形式化）和 `agreement`（共识：个人观点、共同观点）。在这些维度上推进得越远越好 (Pohl, 1994)。

### 概念设计

在理解各阶段可能重叠的前提下，信息系统生命周期的下一阶段是**概念设计**。这有时简称为“*分析*”，以区别于后续的逻辑设计和物理设计阶段。对于大型应用，可能会选择更易管理规模的子问题或组件，指定用于耦合组件的*架构*，并为每个组件设计一个概念*子模式*。这些子模式随后可在一个*全局*概念模式中*集成*。在本书中，讨论的问题规模足够小，我们可以设计整个概念模式，而无需先设计子模式。然而，主要设计过程本身被分解为多个阶段。例如，在添加约束之前先识别事实类型。

经验丰富的建模者经常会注意到新应用与他们或他人之前设计的应用之间的相似之处。在这种情况下，通过审慎地**复用**早期模型中采用的策略，可显著节省设计工作量。例如，如果我们已经建模了一个大学图书馆系统，现在需要建模一个视频租赁业务，则早期模型的许多特性均可复用。我们可以选择以类似方式识别对象类型 `Loan`，并采用或改编早期应用中的若干事实类型。通过将相似的具体概念（如“书籍”、“光盘”）抽象为更通用的概念（如“可租赁物品”），更容易识别出新应用与早期应用的关联。

近年来，关于*设计模式*和*最佳实践*的大量且不断增长的研究成果已形成，以促进复用。有许多资源为各种业务领域提供基本设计模式和模板。用于企业资源规划（ERP）的大型商业软件包可改编以处理企业的各种职能（如订单处理、薪资管理）。为扩大复用范围，此类软件包通常在极高的抽象层级建模实践，这可能使其难以应用于具体案例。组件技术、设计模式和 ERP 包的兴起，使得策略从“自建或购买”转向了“自建、购买和复用”。

多年来，已提出许多维度或视角来捕捉信息系统设计的不同方面。一项关于信息系统设计方法的经典调查确定了三种设计视角：数据、过程和行为（Olle et al., 1991）。

- **面向数据的视角**关注数据库中存储何种数据、这些数据适用何种约束，以及何种数据可被导出。
- **面向过程的视角**考察为帮助理解特定业务运作方式而执行的过程或活动。除描述过程及其代理外，还描述过程与其他组件之间的信息流。
- 复杂过程常被细化为若干子过程。**面向行为的视角**关注*事件*如何触发动作。通常，活动分析可改述为事件分析，反之亦然。

指定进程执行或“触发”所需的信息及充分条件非常重要。例如，检索账户余额的过程可能由客户请求账户余额的事件触发，并需要来自客户的输入信息（如客户编号和账户类型）以及相关数据库表的信息。由于过程与行为之间的界限往往模糊不清，我们将遵循一种通用做法，将关于过程、事件、操作、活动等的讨论归入单一视角，称为“过程”。从该观点看，仅有*两个主要视角*：数据和过程。各种技术（如*工作流模型*）已开发出来以支持*业务流程建模*，详见第 15 章。

几十年前，系统设计主要基于过程视角，但这在许多情况下被证明是低效且不可靠的。数据视角因更基础且稳定得多，成为信息系统开发的主导视角。业务流程不断变化，但底层数据相比之下仅发生微小变化。近来，面向对象建模提供了一种结合数据和过程视角的方法，对象封装数据和操作。遗憾的是，这种结合常在次概念层级指定，因此这种集成并不像看起来那样完美。

如果设计得当，概念模式提供了 UoD 结构的形式化模型。完成这种语义建模后，我们将执行概念设计到**逻辑设计**的*映射*，用实现目标的通用数据模型术语表达。例如，我们可能将概念模式映射为关系模式。CASE 工具可自动执行此映射。

确定逻辑设计后，可进行**基本物理设计**。逻辑设计将适配所用的特定 DBMS 或编码语言，并指定各种策略（如索引或聚类）以提高物理设计的效率。

信息系统的**基本外部设计**涉及确定哪些数据和操作可供哪些用户组访问，并为这些组设计适当的人机界面。通常，会为不同用户类型构建访问权限表，决定不同屏幕表单支持何种功能，并确定屏幕表单和菜单的布局。外部设计可包含对内部设计的交叉引用（如显示哪些表单访问哪些表或类）。

除微不足道的应用外，生命周期的下一阶段通常涉及**原型设计**。原型是预期产品的简化版本，用于从用户处获得关于设计质量的早期反馈。其旨在覆盖需求规格说明中的主要功能，但通常省略最终版本所需的大部分错误检查和细节，且仅使用少量样本数据。因早期反馈在此阶段比效率更重要，原型可能用比最终版本更高级的语言编码。对于用户界面设计，初始原型可能仅绘制在纸上：称为“纸原型”。原型向客户演示，其反馈用于在必要时修订需求和设计。

原型被接受后，将着手（希望是）产品或组件的**最终设计**。现在通过为生产版本编写实际代码，完成内部和外部设计的**实现**。产品随后接受广泛的**测试和验证**（也称为*质量保证*）。使用精心挑选的数据和操作运行软件，以检查其是否按预期运行。随后可向选定用户发放预发布版本（如 alpha 版和一个或多个 beta 版），以帮助发现其他错误。通常，预发布版本越先进，测试用户受众越广。对于某些关键应用（如军事安全系统），可能开发正确性证明以验证系统是否满足规格说明。最后，产品的**发布**版本连同大量*文档*和*培训*材料向公众提供。

### 软件维护与开发因素

软件**维护**涉及软件在初始发布后的修改。维护主要分为三种类型：*纠正性*（消除错误）；*适应性*（修改软件以适应环境或 UoD 的变化）；以及*完善性*（增加改进）。只要产品可用，维护就会持续进行。整体开发过程通常是*迭代*的，即一次将开发周期应用于一个主要组件，而不是试图一次性构建整个产品。在开发周期中越早发现错误，修复起来就越容易。在实现阶段纠正错误的成本可能比在分析阶段修复它的成本高出几个数量级。

开发信息系统的重要因素包括：实用性（自动化真的可取吗？）、正确性、清晰性（设计和代码应具有可读性且文档完善）、效率（内存需求、速度、生产成本）、可移植性、可维护性、适应性、用户防错性和支持性。

### 信息模式层级与框架

本章前面我们了解到，信息模式可以存在于四个不同的层级（概念、逻辑、物理和外部）。逻辑层级的加入完善了国际标准组织制定的最初的三模式架构。这种层级概念提供了一种垂直划分信息系统架构的方式。提供水平划分也很有用。一种方法是使用鲁德亚德·吉卜林在其 1902 年的故事《象宝宝》中提到的“六个朋友”：“我养着六个诚实的仆人……他们的名字叫什么、为什么、何时、怎么、哪里和谁”。如果我们为这六个问题各设一列，并将四个层级各作为一行显示，就能得到一个包含 24 个单元格的表格化*层级/视角框架*。

结合垂直和水平划分最具影响力的框架是约翰·扎克曼的信息系统架构框架（Zachman, 1987）。它使用六个焦点列对应吉卜林的疑问词，但有五个视角行而不是四个层级。因此，*扎克曼框架*有 30 个单元格，如表 2.2 所示。任何系统工程项目都需要考虑这些单元格中哪些是相关的，以及如何在层级间进行映射。

### 其他行业框架

业界还提出了许多其他用于构建信息系统架构的框架。下面简要提及其中四种。更多细节可参阅章节注释中列出的参考文献。

#### 对象管理组模型驱动架构 (MDA)

对象管理组模型驱动架构 (MDA) 方法包含三个层级：计算无关模型 (CIM)、平台无关模型 (PIM) 和平台相关模型 (PSM)。CIM 层部分属于概念层，PIM 层属于逻辑层，PSM 层属于物理层。

#### 开放组架构框架 (TOGAF)

开放组架构框架 (TOGAF) 包含四个层级或域（业务、应用、数据、技术），并提供了详细的架构开发方法 (ADM)，可根据组织需求进行裁剪，并用于管理架构规划活动的执行。
