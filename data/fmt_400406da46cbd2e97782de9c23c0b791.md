### 映射对象化关联

现在让我们讨论一些涉及 `objectification`（也称为 `nesting`）的情况。在图 11.22 中，关联 Employee worked on Project 被对象化为 Work。这个对象化类型扮演一个强制角色和一个可选角色，两者都是函数的。与其他对象类型一样，我们*最初将对象化关联视为“黑盒”，在脑海中擦除其标识方案*。

![图 11.22 具有函数角色的活动对象化关联。](img/f11-22-9780443237904.jpg)

图 11.22 具有函数角色的活动对象化关联。

从这个角度来看，概念模式似乎只有两个事实类型，两者都有连接到对象类型 Work 的函数角色。*事实类型现在按常规方式分组*。因此，这两个事实类型被分组到同一个表中。将嵌套对象类型 Work 可视化为黑盒 "▪"，得到表 `Work(▪, startdate, [enddate])`。最后，我们将 ▪ *解包为其组成属性*（empNr 和 projectName），得到 `Work(empNr, projectName, startdate, [enddate])`。

图 11.22 中的值约束表述为：**对于每个** Work，**现存的** enddate >= startdate。值约束被违反当且仅当其求值为 false（就像 SQL 检查子句一样）。此处关系模式上的脚注注释对应 SQL 检查子句 `check (enddate >= startdate)`。

现在考虑图 11.23 的 ORM 模式。在这里，员工可能在其实际开始日期已知之前就被分配到项目。因此，对象化的 Assignment 关联的一些实例可能被记录下来，但在（某些数据库状态下）不扮演任何连接的角色。在本例中，因为即使连接角色的析取也是可选的，所以嵌套对象类型是*独立的*——这由 "Assignment !" 中的感叹号标记。与此形成对比的是前一个例子（图 11.22），其中嵌套对象类型 Work 是活动的，且关系模式中的 startdate 列不是可选的。

![图 11.23 映射具有函数角色的独立对象化关联。](img/f11-23-9780443237904.jpg)

图 11.23 映射具有函数角色的独立对象化关联。

无论嵌套与否，独立对象类型在映射时都需要特殊处理，如下所示。

*   • 将每个独立对象类型及其扮演函数角色的事实类型（如果有）映射到一个单独的表，以该对象类型的标识符作为主键，所有其他属性为可选。从每个映射自独立对象类型非函数角色（如果有）的列序列，向该主键添加一个子集约束。

如果我们只想记录某员工被分配到特定项目这一事实，我们只需输入 empNr 和 projectName 的值。关于项目工作的开始和结束日期的细节，可以在已知时稍后添加。因为开始日期和结束日期都是可选的，值约束现在表述为：**对于每个** Assignment，**现存的** enddate >= **现存的** startdate。

图 11.24 展示了建模此 UoD 的另一种方式。独立对象类型没有连接的函数角色，并单独映射到一个表。`m:n` 事实类型映射到另一个表。一个子集约束捕获其可选性。如果我们尝试将所有内容映射到一个表，这将违反实体完整性（为什么？）。

![图 11.24 映射无函数角色的独立对象化关联。](img/f11-24-9780443237904.jpg)

图 11.24 映射无函数角色的独立对象化关联。

如果已知某分配的开始日期和结束日期，则结束日期必须晚于或等于开始日期这一约束，现在在概念层面和关系层面都更难表述了。此外，图 11.24 的方法将信息分散在更多表中，并要求表间约束。这通常是不可取的，因为它往往会降低查询和更新的执行速度。基于这些原因，通常首选图 11.23 的方法，而非图 11.24 的方法。

图 11.23 和 11.24 中的模式允许我们在没有开始日期的情况下记录结束日期。在实际应用中，我们有时允许这种情况，因为我们的信息可能是不完整的。例如，我们可能想记录某人结束项目的日期，但不知道 `know` 该人何时开始。

在这种情况下，概念模式有时比理想世界所建议的强制角色更少，因此关系模式可能比完整知识所允许的可选列更多。

然而，假设如果我们知道结束日期，那么我们 `do` 知道开始日期。要在图 11.23 中强制执行此约束，请在 ORM 模式上添加一个子集约束，从“结束于”谓词的第一个角色到“开始于”谓词的第一个角色。

此约束可通过使用 `nested option brackets`（嵌套可选括号）在关系模式中声明。在这里，我们将 `enddate` 的可选括号括在 `startdate` 的可选括号 *内部*，得到 `Assignment`( `empNr`, `projectName`, \[ `startdate`, \[`enddate`\] \] )。这表明仅当记录了 `startdate` 的值时，才为 `enddate` 记录（非空）值。

要向图 11.24 添加此约束并不容易。在概念层面和关系层面都需要一个文本约束，以声明对于每个员工、项目组合，仅当记录了阶段“结束”时，才记录阶段“开始”。

第 14 章 详细探讨了“等价”概念模式的概念，并提供了将概念模式转换以提高从 Rmap 获得的关系模式效率的指南。

如果记录了员工在项目上的开始和结束日期，可以指定一个派生规则来计算工作时长（通过用结束日期减去开始日期，如果已知的话）。因为每个计算机系统都有一个内部时钟，概念上存在一种一元事实类型，形式为“日期是今天”。因此，对于仍在项目上工作的人，我们也可以通过用“今天”的当前值减去开始日期来派生迄今为止在项目上花费的时间。

默认情况下，派生事实不存储。因此，`by default, derived columns are excluded from the base tables`（默认情况下，派生列从关系模式的基表（即存储表）中排除）。例如，派生规则可以使用视图或存储过程来实现。

在某些情况下，效率考虑可能会导致我们在更新时 `derive on update` 派生，而不是在查询时派生，并存储派生信息。在这种情况下，概念模式图上的派生事实类型标记为“\*\*”。在关系映射期间，该事实类型映射到基表，派生规则映射到由派生规则中引用的基表更新触发的规则。

例如，我们可以通过声明适当的生成列或表触发器来实现派生规则（回顾前面的净工资示例）。除了派生规则外，`all`（所有）概念约束都应该映射（不仅仅是唯一性和强制约束）。

SQL 标准包含对子类型的有限支持，但当前的关系系统通常不直接支持这一概念。尽管如此，在当前系统中实现子类型主要有三种方法：吸收、分离和分区。采用 `absorption`（吸收）方法时，我们将 `absorb the subtypes back into the (top) supertype`（将子类型吸收回（顶层）超类型）（得到 `qualified optional roles`（限定可选角色）），`group the fact types as usual`（像往常一样对事实类型分组），然后 `add the subtyping constraints as textual qualifications`（将子类型约束作为文本限定添加），如图 11.25 所示。

为了最好地理解这个例子，请在概念模式上将子类型吸收回超类型 Patient，并将子类型角色作为限定可选角色附加到 Patient。附加到 Patient 的所有角色都是函数式的，因此事实类型都映射到同一个表，如图所示。`phone`、`prostateStatus` 和 `nrPregnancies` 属性都是可选的，但后两个是限定的。

在限定条件中，`exists` 意味着值非空。限定条件 1 是一个纯子类型约束，表示仅当该行 `gender` 的值为“M”时，才记录前列腺状态的非空值。有些男性这里可能记录为空。限定条件 2 既表达了一个子类型约束（仅当 `gender` 为“F” 时记录怀孕次数），又表达了一个强制角色约束（如果 `gender` 为“F” 则记录 `nrPregnancies`）。回想一下，`iff` 是“if and only if”（当且仅当）的缩写。

因为这个例子只涉及函数式事实类型，吸收方法导致的表基本上与原始输出报表匹配（大多数关系系统只支持一种空值除外）。这种方法的主要优点是将子类型家族的所有函数式谓词映射到单个表中。这通常使相关查询和更新更高效。其主要缺点是会产生空值。

第二种主要方法 `separation`（分离）为具有子类型特定函数角色的事实创建单独的表。采用这种方法，图 11.25 的概念模式映射到三个表：一个用于通用事实，一个用于男性特有事实，一个用于女性特有事实。

第三种主要方法 `partition`（分区）可用于子类型构成其超类型的一个分区时。因为 MalePatient 和 FemalePatient 是互斥且穷尽的，所以此处可使用此方法，结果得到两个表：一个包含男性患者的事实，另一个包含女性患者的事实。

下一节讨论这三种方法的相对优劣，并考虑子类型使用不同于超类型的首选标识方案的映射情况。然而，我们的默认方法是在分组前吸收子类型。

### 关系映射中的非功能性事实类型

即使采用这种方法，**任何由子类型扮演非功能性角色的事实类型都会映射到单独的表中，其子类型定义通过以主超类型表为目标的限定子集约束来表达**。

例如，图 11.26 中的 ORM 模式增加了一个可选的 `m:n` 事实类型 `FemalePatient attended prenatal clinic on Date`。如图所示，该事实类型映射到一个带有限定子集约束“**only where** gender = ‘F’”的单独表中。如果新事实类型对 `FemalePatient` 是强制性的，限定条件将显示为“**exactly where**”而不是“**only where**”。
