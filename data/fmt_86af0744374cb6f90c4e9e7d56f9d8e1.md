
管理员授权是由管理员策略蕴含的授权，回顾一下，其目的是授权用户指定访问控制或过滤策略。因此，管理员策略蕴含两类授权：指定访问控制策略的授权，我们简称为 `管理员授权`；以及指定过滤策略的授权，即 `管理员禁止`。一般来说，管理员授权可以表示为一个三元组（`u`，`p`，`o`），表明用户 `u` 被授权为对象 `o` 上的权限 `p` 指定访问控制策略。因此，与授权和禁止类似，管理员授权也可以表示为 `Person` 和 `Resource` 类之间的一个对象属性。根据这种建模，我们可以定义对象属性 `AdminRead`，其实例表明给定用户被授权表达授予特定对象读取权限的访问控制策略。考虑实例 `<Bob,URI1>:`AdminRead`，它表明 Bob 被授权指定授予 URI1 对象读取权限的访问控制策略。

与访问控制授权类似，只需定义子属性，即可指定管理员授权如何传播。让我们声明前面提到的属性 `AdminRead`，并进一步创建属性 `AdminWrite` 和 `AdminAll`。我们声明 `AdminAll` 为 `AdminWrite` 和 `AdminRead` 两者的子属性。考虑我们的运行示例，Alice 拥有一张照片。假设这授予了她该照片的 `AdminAll` 授权。如果 Alice 试图允许 Bob 读取该照片，而该动作仅限拥有 `AdminRead` 属性的个体执行，则通过 `AdminAll` 属性即可允许此操作。

相反，管理员禁止可以表示为一个元组（`s`，`t`，`o`，`p`），这意味着用户 `s`（监管者）被授权为目标用户 `t` 和对象 `o` 上的权限 `p` 指定过滤策略。与之前的授权不同，管理员禁止不能表示为属性，因为它们不表示二元关系。因此，我们决定将管理员禁止建模为一个 OWL 类 `Prohibition`。这使我们能够将禁止的所有组成部分指定为类属性。更确切地说，给定一个管理员禁止（`s`，`t`，`o`，`p`），我们可以将授权监管者建模为 `Prohibition` 和 `Person` 类之间的一个对象属性 `Supervisor`。类似地，目标用户可以表示为 `Prohibition` 和 `Person` 类之间的一个对象属性 `TargetUser`，目标对象表示为 `Prohibition` 和 `Resource` 类之间的一个对象属性 `TargetObject`。相反，监管者被授权声明过滤策略的权限不表示为对象属性。确实，为了自动传播管理员禁止，我们倾向于直接将权限指定为类名。因此，作为示例，`ProhibitionRead` 类的实例表示授权为读取权限指定过滤策略的管理员禁止。通过妥善定义子类，可以自动推断新的管理员禁止。

假设，我们有一个通用的 `Prohibition` 类，带有子类 `PRead` 和 `PView`。然后我们为它们各自创建另一个子类 `PAll`。假设我们有两个个体，John 和 Jane，John 是 Jane 的父亲。在这种情况下，John 应被允许过滤其女儿能观看的视频。即，我们有一个禁止（“John”，“Jane”，Video，`PAll`）。现在，对于任何视频和任何权限，John 都可以禁止他希望禁止的内容。

## 17.5.3 安全规则

所提框架将每个安全策略转换为一条 SWRL 安全规则，其中前件编码策略中指定的条件（例如，表示主体和对象规范的条件），而后件编码蕴含的授权或禁止。特别地，由于我们将安全规则建模为 SWRL 规则，SWRL 规则体陈述了针对 SNKB 的策略条件，即第 17.3 节中引入的本体上的条件，而 SWRL 规则头蕴含 SAKB 的新实例，即第 17.3 节中引入的本体的实例。因此，SWRL 安全规范的制定严格受限于 OSN 为建模 SN 和 SA 知识库所支持的本体。这意味着无法提供通用 SWRL 规则的形式化，因为这些规则会因所考虑的本体而异。相反，在本节中，我们旨在展示一些基于我们框架中采用的本体定义的有意义的 SWRL 安全规则示例。

我们首先考虑管理员策略，该策略规定对象的所有者有权为该对象指定访问控制策略。根据前几节介绍的本体定义的相应 SWRL 规则如下：

```
Owns(?grantor, ?targetObject) ⇒ AdminAll(?grantor, ?targetObject)
```

对上述规则的求值结果是为每一对用户及其拥有的相应资源生成一个不同的对象属性 `AdminAll` 实例。值得注意的是，这种授权是根据对 SAKB 进行建模的本体进行传播的。因此，由于框架利用了第 17.5.1 节介绍的本体，上述授权也会传播到 `AdminRead` 和 `AdminWrite`。

社交网络中另一个有意义的管理员策略是：如果用户在照片中被标记，则她有权为该照片的读取权限指定访问控制策略。这可以通过以下 SWRL 安全规则进行编码：

```
Photo(?targetObject) ∧ photoOf(?grantor, ?targetObject) ⇒ AdminRead(?grantor, ?targetObject)
```

上述规则是有趣的例子，强调了在所提出的框架中，可以轻松指定管理员策略，而在非基于语义的访问控制机制中实现这些策略将需要复杂的策略管理。确实，为 OSN 提供对用户和资源之间关系（例如建模所有权或标记关系）进行建模的本体，使得 SA 能够通过简单地对所需关系类型提出条件来指定管理员策略。相反，在传统访问控制机制中强制执行这些管理员策略将需要实现复杂的策略管理功能，因为这将要求首先确定用户和资源之间所有可能的关系，然后为所有这些关系指定管理员授权。而在所提出的框架中，这项任务由推理器执行。

表 17.1 展示了一些 SWRL 安全规则的示例。第一条安全规则编码了一条过滤策略，规定 Bob 的孩子不能访问视频。一旦对该规则进行求值，就会为 Bob 的每个孩子和视频资源创建一个禁止实例。相反，第二条安全规则对应 Bob 陈述的一条访问控制策略，将对其照片的读取访问限制为仅限其直接朋友，而第三条规则编码了一条访问控制策略，规定 Alice 被标记的照片可以被她的直接朋友访问。最后，第四条规则规定如果一个人拥有一张照片，那么他们朋友的朋友（一种间接关系）可以查看该照片。

### 表 17.1 SWRL 安全规则示例

| # | SWRL 规则 |
|---|---|
| (1) | `Video(?targetObject) ∧ ParentOf(Bob, ?controlled) ⇒ PRead(?controlled, ?targetObject)` |
| (2) | `Owner(Bob, ?targetObject) ∧ Photo(?targetObject) ∧ Friend(Bob, ?targetSubject) ⇒ Read(?targetSubject, ?targetObject)` |
| (3) | `Photo(?targetObject) ∧ photoOf(Alice, ?targetObject) ∧ Friend(Alice, ?targetSubject) ⇒ Read(?targetSubject, ?targetObject)` |

## 17.6 安全规则执行

### 17.6.1 我们的方法

我们的框架的作用类似于传统的访问控制机制，其中 `reference monitor`（参考监视器）通过查找授予或拒绝请求的授权来评估请求。在所提出的框架中利用这一原则意味着通过查询 SAKB 本体来检索授权/禁止。因此，例如，要验证用户 `u` 是否有权为对象 `o` 的读取权限指定访问控制策略，有必要验证实例 `AdminRead(u, o)` 是否在本体中，即执行实例检查。这意味着在评估任何可能的请求之前，必须先评估所有编码安全策略的 SWRL 规则，从而推断出所有访问控制/管理员授权以及所有禁止。因此，在策略执行之前，需要执行一个称为 `policy refinement`（策略细化）的初步阶段。该阶段旨在通过执行所有编码安全策略的 SWRL 规则，用推断出的授权/禁止来填充 SAKB。

一旦推断出授权/禁止，就可以进行安全策略执行。特别是，访问控制和过滤策略在提交 `access request`（访问请求）时进行评估，而管理员策略在提交 `admin request`（管理员请求）时进行评估。在下文中，我们将展示这两种请求评估，说明相应策略是如何执行的。

### 17.6.2 管理员请求评估

管理员请求包含两部分信息：`grantor`（授予者）的名称，即提交管理员请求的用户；以及授予者想要指定的访问控制或过滤策略，编码为 SWRL 规则，即 `submitted SWRL`（提交的 SWRL）。仅当 SAKB 中存在针对授予者的管理员授权时，提交的 SWRL 才能被插入系统。例如，如果提交的规则要求为 `targetObject` 的读取权限指定访问控制策略，则必须存在 `<grantor, targetObject>: Read` 的实例。请注意，关于权限和 `targetObject` 的信息可以直接从提交的 SWRL 中检索。因此，要决定上述请求是否可以被授权，一种可能的方法是查询 SAKB 以检索相应的管理员授权（如果有）。如果存在实例，则可以评估提交的 SWRL，否则框架将拒绝授予者的管理员请求。另一种方法是通过在其主体中添加条件来重写提交的 SWRL，以验证 SAKB 中是否存在授权指定该规则的管理员授权。以下示例将阐明这一基本思想。

假设系统收到以下管理员请求：`{Bob, SWRL[1]}`，其中 `SWRL[1]` 如下：

```
SWRL[1]: Owns(Bob, ?targetObject) ^ Photo(?targetObject) ^ Friend(Bob, ?targetSubject) ⇒ Read(?targetSubject, ?targetObject)
```

为了确定管理员请求的结果，框架必须验证 SAKB 中 `<Bob, targetObject>: AdminRead` 实例的存在性。可以通过简单地修改 `SWRL[1]` 将此检查合并到其主体中，如下所示：

```
New_SWRL[1]: AdminRead(Bob, ?targetObject) ^ Owns(Bob, ?targetObject) ^ Photo(?targetObject) ^ Friend(Bob, ?targetSubject) ⇒ Read(?targetSubject, ?targetObject)
```

然后对 `New_SWRL[1]` 进行求值，其结果是只有当 Bob 根据管理员策略被授权指定这些授权时，读取访问控制授权才会被插入 SAKB。

如果管理员请求提交的是过滤策略，为了决定授予者是否有权指定该策略，需要在 `Prohibitions` 类（即过滤策略要求禁止的动作对应的子类）中进行搜索，寻找一个实例，其 `Grantor` 属性等于授予者，`Controlled` 和 `TargetObject` 属性分别等于提交的 SWRL 规则头部指定的受控者和 `TargetObject`。在这种情况下，我们也可以采用基于 SWRL 重写的方法。

假设框架接收到以下管理员请求：`{Bob, SWRL[2]}`，其中 `SWRL[2]` 如下：

`SWRL[2] : Video(?targetObject) ^ ParentOf(Bob,?controlled) ⇒ PRead(?controlled,?targetObject)`

然后，系统可以修改提交的 SWRL 为：

`New_SWRL[2]: PRead(?p) ^ Grantor(?p,Bob) ^ Controlled(?p,?controlled) ^ TargetObject(?p,?targetObject) ^ Video(?targetObject) ^ ParentOf(Bob,?controlled) ⇒ PRead(?controlled,?targetObject)`

其求值效果是仅当存在管理员禁止策略（`Bob, *c, o*, Read`）时，才插入 `PRead` 属性实例（即读取禁止），其中 `c` 是 Bob 的子女，`o` 是视频资源。注意，即使提交的 SWRL 显式指定了受控用户的名称（例如 `…. ⇒ PRead(Alice,?targetObject)`），这也是有效的。

### 17.6.3 访问请求求值

一般来说，访问请求可以建模为一个三元组（`u`, `p`, `URI`），表示用户 `u` 请求在位于 `URI` 的资源上执行权限 `p`。为了评估该请求，框架必须验证是否存在访问控制授权，将 `URI` 上的权限 `p` 授予请求者 `r`。然而，由于所提系统也支持过滤策略，此类授权的存在并不一定意味着 `r` 被授权访问 `URI`，因为可能存在一条禁止策略拒绝该用户访问该资源。因此，要评估是应授予还是拒绝访问请求，有必要对 SAKB 执行两个查询。第一个用于检索授权，第二个用于检索禁止。更确切地说，如果 `u` 需要读取权限 `Read`，系统必须查询对象属性 `Read` 和 `PRead` 的实例。特别是，这两个查询都寻找实例 `<u, URI>`（即 `<u, URI> : Read` 和 `<u, URI> : PRead`）。如果第一个查询返回实例且第二个查询返回空集，则授予访问；否则拒绝。

再次考虑 17.3 节 和 17.4 节 中的示例，并增加一个名为“Susan”的人。Susan 是 Jane 的朋友，并发布了一个她允许所有朋友查看的视频。然而，Jane 的父亲禁止她观看视频。当 Jane 请求查看 Susan 的视频时，将执行授权和禁止查询。授权查询返回 `Read` 权限，但禁止查询返回 `PRead`。这意味着 Jane 将无法观看该视频。

## 17.7 访问控制框架的实现

在前几节中，我们提供了一个使用语义 Web 技术的社交网络访问控制框架。在这里，我们展示了在合成数据上对该框架的初步实现结果。如前所述，我们设计了一个基于语义 Web 技术的可扩展、细粒度的 OSN 访问控制模型。我们的主要思想是通过本体编码社交网络相关信息。具体而言，我们建议使用语义 Web 本体对 OSN 的以下五个重要方面进行建模：（1）用户配置文件，（2）用户间关系（例如，Bob 是 Alice 的密友），（3）资源（例如，在线相册），（4）用户与资源间的关系（例如，Bob 是相册的所有者），（5）动作（例如，在某人的墙上发布消息）。通过构建此类本体，我们对社交网络知识库（SNKB）进行建模。然后，我们的访问控制执行机制通过利用这些知识来实现。具体而言，思路是将安全策略定义为规则，其前件陈述 SNKB 上的条件，后件指定授权动作。我们假设由社交网络管理器托管的集中式参考监视器将强制执行所需策略。我们的架构具有可扩展性，因为我们可以添加模块来执行诸如推理控制之类的功能。此外，我们还可以扩展策略以包含信息共享策略，而不仅仅是访问控制策略。有关语义技术在在线社交网络中应用的详细讨论，请参阅我们的工作文献 [CARM2009a]。在这里，我们将讨论局限于那些影响我们在在线社交网络中实现资源访问控制机制的特定主题。

在最近的过去，Facebook 对其定义网络上朋友关系的方法进行了重大更改。以前，如果我们有两个是朋友的 Facebook 用户，例如 John 和 Jane，他们中的任何一方都可以选择 Facebook 允许的预选友谊类型之一，另一方则需要确认或拒绝这一友谊标签。随后，John 或 Jane 的任何朋友都能看到应用于这段友谊的定义。然而现在，每个人都有能力创建有意义的列表，而不是定义对他人可见的链接类型。然后，朋友可以被添加到用户选择的任意数量的列表中。这些列表随后可用于控制状态更新、墙贴等的可见性。但是，无法定义这些列表的层次结构。例如，如果创建了“高中同学”列表和“大学同学”列表，则无法创建“同学”列表，除非将每个人单独添加到该第三个列表中。

我们使用 W3C [WWW1999] 指定的 n 元关系模式来表示友谊。这意味着每个友谊都是一个类的实例，我们称之为 `FriendshipRelation`。这使我们能够维护关于每个友谊的独立信息。具体而言，我们为每个友谊维护一个 `TrustValue`。这使我们能够确定友谊的特定强度，即使与同一类中的友谊相比也是如此。我们的实现支持访问控制策略，以调节在线社交网络成员如何访问资源。特别是，支持的访问控制策略是基于我们之前的工作 [CARM2009b] 定义的。在这里，授权用户是根据网络中节点间关系的类型和/或信任级别来表示的。例如，访问控制策略可以规定，唯一被授权访问给定资源的 OSN 参与者是那些与资源所有者具有直接友谊关系的人，前提是该关系也具有特定的信任级别。

然而请注意，使用语义推理可以带来一些超出 [CARM2009b] 中讨论能力的改进。这一优势源于我们能够针对 OSN 中的语义概念指定访问控制策略。例如，作为默认设置，Facebook 可能规定照片只能由直接朋友查看。在个别用户未定义策略的情况下，推理将默认采用这一通用策略。我们为 OSN 提供安全性的方法设计在 第 19 章 中讨论。主要方面包括过滤策略、安全规则执行、管理策略评估和访问请求评估。在下一节中，我们将描述我们的实现框架。

## 17.8 框架架构

### 社交网络访问控制框架
