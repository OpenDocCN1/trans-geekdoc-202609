
需要一个额外的文本约束，以确保每个设备项目最多由一个 `Department` 拥有（如脚注约束所示）。为了允许以后添加任何种类的所有权事实类型，我们不添加文本约束来确保只有员工拥有汽车，只有部门拥有设备。如果需要，可以添加此类额外的文本约束。

在这种情况下，我们应该泛化互斥的对象类型吗？除非我们想为通用类型的所有成员提出一个共同问题（例如，列出所有所有者及其资产），否则不应该。如果对象不需要在输出报告的同一列中一起列出，则无需对它们进行泛化。共同属性越多，此类查询被制定的可能性就越大。

例如，在银行或保险等许多应用中，客户可能是个人或公司。因为需要在同一查询中访问它们的共同信息，所以将 `Person` 和 `Company` 泛化为 `Customer`（或 `Party`，或适合该应用的某个术语）是值得的。当然，我们仍保留 `Person` 和 `Company` 作为子类型，以记录特定于它们的细节。

如果两个事实类型具有相同的谓词读法和对象类型名称序列，则将它们视为同一事实类型。然而，不同的谓词可以具有相同的名称。这在诸如“has”和“is of”这样的平凡谓词中经常发生。如果我们不泛化共享公共角色的对象类型，也可能发生这种情况。例如，在图 6.57 中有两个称为“owns”的谓词。我们可以通过它们包含的事实类型来区分这些谓词（例如，`Employee owns Car` 与 `Department owns Equipment` 不同）。在 CASE 工具中，具有相同读法的谓词可能通过代理或扩展名称在内部加以区分（例如，`P56`、`P57`，或“owns1”、“owns2”）。然而，除了“has”和“is of”等显而易见的情况外，如果我们在模式上复制了一个谓词读法，我们应该问自己是否应该进行泛化。

到目前为止的示例都是互斥子类型。*重叠类型* 又如何呢？回想一下，概念模式上的原始实体类型是互斥的。允许不同实体类型重叠的唯一方法是使它们成为子类型。因此，一般来说，如果我们发现两个确实重叠的原始实体类型，则应该为它们引入一个超类型。然而，在极少数情况下，我们可能会将现实中重叠的实体类型在模型中描绘为互斥的，因为我们根本不关心了解任何重叠情况。

请考虑图 6.59 所示的模式。这可能是大学模式的一部分。学生由学号标识，大学员工由员工编号标识。员工被分类为教学人员、行政人员或普通员工。只有教学人员可以教授科目，只有学生可以学习科目。除了各自的特定角色外，学生和员工的性别和出生日期都会被记录。在全局模式中，学生的其他具体细节（例如，注册模式）和员工的其他具体细节（例如，部门）以及其他共同属性（例如，姓名、地址、电话号码）都会被记录。

![Fig. 6.59 Students and employees have some details in common.](img/f06-59-9780443237904.jpg)

图 6.59 学生和员工有一些共同细节。

如果你将图 6.59 垂直地从中间切开，但在两边都复制 Gender、Date 和 Subject，左侧子模式处理学生记录，右侧子模式处理员工记录。过去，独立开发此类子系统是常见做法。如今，许多组织正在将子系统集成到一个通用系统中，以提供对更多信息的访问，并强制执行原本独立模式之间的约束。

假设 `Student` 和 `Employee` 是互斥的。尽管它们有共同的角色，但我们不太可能想在同一查询中为学生和员工列出此类信息。在这种情况下，我们可以保持模式原样。

现在，假设在现实中 `Student` 和 `Employee` 存在重叠，因此一名学生可能也是一名员工。如果我们想对这种可能性建模，就必须引入一个超类型（例如 `Person`）。但如果我们不关心某学生是否为员工，且这两种类型没有共同的问题需要处理，那么可以保持模式原样。不过，我们的模型在这一点上现在与现实世界有所不同。

通过将 `Student` 和 `Employee` 表现为原始类型，我们的模型宣称这两种类型是互斥的，而现实中它们是重叠的。为避免误解，模型与现实之间的任何此类分歧都必须在技术手册和用户手册中明确记录，以便人们充分了解这一决策。

此类决策不应轻率做出，因为通常有充分的理由想要知道某个实例是否同时属于这两种类型。例如，假设我们要强制执行这样一个约束：任何教师都不能选修自己教授的课程。如果我们希望信息系统为我们强制执行此约束，就必须为其提供一种检测某学生是否为员工的方法。为此，我们必须引入一个超类型（例如 `Person`），最好带有一个全局标识方案（例如 `PersonNr`）。

此外，我们可能想为学生员工记录特定数据（例如休学假）。在这种情况下，我们还需要引入 `StudentEmployee` 作为 `Student` 和 `Employee` 的共同子类型。图 6.60 描绘了这种情况的子类型图。作为练习，请通过添加事实类型和子类型定义将此图扩展为完整模式。性别和出生日期事实类型连接到 `Person`。如果包含在内，关于教师的约束应以文本形式指定。

![图 6.60 泛化与进一步特化后的子类型图。](img/f06-60-9780443237904.jpg)

图 6.60 泛化与进一步特化后的子类型图。

在之前的案例中，子类型图中的所有子类型都继承了其顶层超类型的标识方案。例如，在图 6.60(a)中，所有人，无论是否为学生和/或员工，都由人员编号标识。

然而在实践中，我们有时会遇到某个子类型拥有首选标识方案，且该方案不同于其直接超类型的情况。在这种情况下，我们拥有一个*上下文相关引用方案*，因为对象的首选标识符取决于其被考察的上下文。

假设在学生档案的上下文中，我们想用 `StudentNr` 标识学生；而在员工档案的上下文中，我们想用 `EmployeeNr` 标识员工。我们可以通过在子类型节点本身引入*上下文相关标识符*来在子类型图上指示这一选择。

例如，在图 6.60(b)中，`Student` 由 `StudentNr` 标识，`Employee` 由 `EmployeeNr` 标识。如果某子类型未引入其首选标识符，则必须从其某个超类型（直接或间接）继承标识符。

*实线子类型箭头*提供了一条通往子类型首选标识符的路径，使用该路径上找到的第一个标识符。*虚线子类型箭头*不提供通往子类型首选标识符的路径，因此该子类型要么引入自己的标识符，要么必须通过另一条通往超类型的路径来继承其标识符。

例如在图 6.60(b)中，`Student` 和 `Employee` 引入了自己的标识符，因此它们仅与 `Person` 有虚线子类型连接。`StudentEmployee` 有两个超类型，并由 `EmployeeNr` 标识（由实线子类型连接显示），而非由 `StudentNr` 标识（虚线连接）。

泛化对象类型的过程总结如下。此处 `A` 和 `B` 最初被分别描绘为没有共同超类型的实体类型。

| | |
| --- | --- |
| | **泛化过程 (GP)：** |
| | **如果** |
| | `A` 和 `B` 重叠，或可被比较（例如计算比率） |
| | **且** 我们希望对此建模 |
| | **或** |
| | `A` 和 `B` 互斥。 |
| | **且** 为两者记录了共同信息。 |
| | **且** 我们希望就此信息将 `A` 和 `B` 一起列出。 |
| | **那么** |

必须强调的是，泛化或特化的决策是一个概念层面的决策。这并不意味着我们承诺以特定方式将生成的子类型图映射到逻辑数据库模式。存在多种映射选项（例如，子类型可被吸收进与其超类型相同的表中，或映射到单独的表中）。第 11 章将详细讨论这些映射选项。

## 6.7 总结

**集合**由其成员决定，因此顺序和重复不重要，例如 `{3, 6} = {6, 3, 6}`。**包**或**多重集**使重复变得重要，例如 `[3, 6] = [6, 3]` 但 `[3, 6] ≠ [3, 6, 6]`。**序列**是有序的包，例如 `(3, 6) ≠ (6, 3)`。集合 *A* 是 *B* 的**子集**（写作 *A* ⊆ *B*），当且仅当 *A* 的每个成员都属于 *B*；在这种情况下 *B* 是 *A* 的**超集**。*A* 是 *B* 的**真子集**当且仅当 *A* ⊆ *B* 且 *A* ≠ *B*。*A* 和 *B* **互斥**或**不相交**，当且仅当它们没有共同成员，即它们的**交集** *A* ∩ *B* = {}。如果集合有共同成员，则它们**重叠**；如果每个集合也有额外的成员，则属于**真重叠**情况。

**CSDP 步骤 6** 添加任何值、集合比较（子集、相等、排除）和子类型约束。**值约束**为值类型或角色指定可能的值。它可能提供所有值的**完整列表**或**枚举**，例如 `{"M", "F"}`；**子范围定义**，例如 `{1..7}`、`{"A".."E"}`；或列表和范围的组合。

值约束也可能指示语法数据类型（例如，最多 20 个 Unicode 字符的变长文本）。如果底层数据类型是实数（例如 `float` 或 `decimal`），方括号/圆括号表示端值的包含/排除。例如，`"(0..100]"` 表示不超过 100 的正实数（含 100）。

**独立对象类型**是一种原始对象类型，其实例可以独立于扮演任何事实角色而存在（事实角色共同是可选的）。独立对象类型在其名称后附加“!” 。例如，我们可以用所有现有国家的名称填充“Country!”的参考表，即使其中一些国家不参与任何基本事实。原则上，引用独立对象类型成员的值可以改为在值约束中声明；但是，如果值可能发生变化，或有许多无法指定为范围的值，这样做会很别扭。

**集合比较约束**限制一个角色或角色序列的总体与另一个角色序列总体的关联方式。设 `rs1` 和 `rs2` 为由兼容对象类型扮演的角色序列（包含一个或多个角色）。从 `rs1` 到 `rs2` 的**子集约束**用指向该方向的箭头表示，包含一个圆圈“⊆”符号。这表示 `pop(rs1) ⊆ pop(rs2)`。

**相等约束**等同于双向的子集约束。它用带圆圈“=”符号的虚线表示，要求 `pop(rs1) = pop(rs2)`。**排除约束**通过虚线将两个或多个角色序列连接到“⨂”；这意味着它们的总体必须是不相交的（互斥）。

如果一组角色是析取强制且互斥的，这可以用救生圈符号表示。这种**异或约束**符号就是包含约束符号 ⨀ 叠加在排除约束符号 ⨂ 上。

如果每个角色序列有两个角色，我们称之为**对子**子集、对子相等和对子排除约束。元组子集约束蕴含简单子集约束。简单排除约束蕴含元组排除。定理 NXS 表明，没有排除约束可以拥有与子集约束完全相同的参数。

对象类型 *A* 是 *B* 的（真）子类型，当且仅当（A ≠ *B* 且）对于每个数据库状态，`pop(A) ⊆ pop(B)`。我们用从 *A* 到 *B* 的**箭头**表示这一点。如果 *A* 是 *B* 的子类型，且 *B* 是 *C* 的子类型，则可传递地推断出 *A* 是 *C* 的子类型；这种间接的子类型连接通常不应显示。

一个对象类型可以有多个子类型和多个超类型。一组兼容对象类型之间的子类型连接显示在一个有向、无环的**子类型图**中。该图恰好有一个根节点（或顶点），它必须是一个原始对象类型（或在极少数情况下是对象化关联）。

在 ORM 中，引入子类型通常是为了声明某些角色仅由该子类型扮演。引入子类型的过程称为**特化**。子类型继承其超类型的所有角色，且通常至少有一个特定角色。默认情况下，子类型继承直接超类型的首选引用方案，因此引用方案不显示在子类型上。有了子类型（和对象化关联），任何强制角色必须显式显示。

子类型可以是派生的、断言的或半派生的。每个**派生子类型**必须使用其超类型的一个或多个角色，在等价派生规则中正式定义，例如，**Each** `FemalePerson` **is a** `Person` **who** is of Gender ‘F’。派生子类型标记为“*”。对于派生子类型，必须声明定义谓词上的所有相关约束；这确保了任何存在的子类型排除“⨂”或全覆盖“⨀”约束都是隐含的。互斥对象类型（例如 `Man`、`Woman`）不能有共同子类型。**断言子类型**只是在没有任何派生规则的情况下被断言。**半派生子类型**可能同时拥有派生和断言实例；这些罕见的子类型标记为“^+”并具有条件派生规则。

输出报表通常有缺失值或空值。如果缺失值意味着“**不予记录**”（即因其他记录数据而不适用），则表明存在子类型化。本书为此使用减号“−”。如果输出报表相对于子类型图是重要的，我们可以通过检查“−”标记的模式来确定该图。然而，需要背景知识来确定子类型定义，从而得到有意义的子类型名称。输入表单通常提供指示，说明在什么条件下需要表单上的特定条目。此类指示可用于推断子类型约束。有时报表已经根据子类型分离，其报表标题提供了子类型方案的线索。

如果没有完整的输出报表集，我们可能会错误地将对象类型声明为原始类型。然后我们需要引入超类型；这个过程称为对象类型**泛化**，是特化的逆过程。如果对象类型重叠且我们想知道这一点，则引入超类型。如果对象类型互斥但有共同角色，且我们想将它们列在一起以获取这些共同信息，也会引入超类型。如果原始对象类型有特定角色，它们必须保留为子类型。

在某些情况下，子类型需要具有不同于其超类型的首选引用方案。这种**上下文相关引用**通过在相关子类型上显示首选引用方案来指示。如果子类型箭头提供了通往子类型首选标识符的路径，则显示为**实心箭头**；否则显示为**虚线箭头**。

### 章节注释

并非所有 ORM 版本都允许独立实体类型。完全面向通信的信息建模（**FCO-IM**）（Bakema et al., 1994）通过将实体类型视为一元谓词的对象化来处理此问题。

大多数 ER 版本不允许在模式图中包含角色序列之间、或属性之间的子集、相等或排除约束（参见第 8 章）。统一建模语言（UML）仅包含整个关联之间的子集约束的图形符号，以及仅在角色之间的异或约束上下文中的排除约束的图形符号（参见第 9 章）。实体关系建模（ER）的最新版本以及 UML 为子类型化提供了基本支持，但忽略了对形式化子类型定义或上下文相关引用的需求（参见第 8 章和第 9 章）。

某些版本的 ORM 将子类型限制为派生的、活动子类型。某些版本不支持上下文相关引用。PSM 变体采用了一种不同的泛化方法，其中超类型使用其子类型的标识方案的析取（例如，参见 ter Hofstede 等人, 1993）。尽管这在对重叠子类型执行通用查询时引发了额外的实现问题，但这确实提供了另一种可行的方法。
