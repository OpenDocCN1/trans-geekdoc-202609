## 14.9 数据迁移与查询转换

数据迁移是重构的第四阶段，有时可能具有挑战性。当原始数据库填充了海量数据时，通常不切实际去手动转换并重新录入数据到新的数据库模式中。虽然大多数 DBMS 都提供了协助数据迁移的工具，但这些工具通常只能处理简单的数据转换，因此对于更复杂的情况，你需要编写自己的转换程序。此类数据转换通常用 SQL 编写，不过如果数据以 XML 形式提供，也可以使用 XSLT。

数据迁移完成后，原数据库上的任何存储查询都需要重新编码，以便在新数据库上执行等效的查询。本节通过一个小型重构示例来说明数据迁移和查询转换的任务。本节末尾的练习提供了一个更大的示例供你自行尝试。

图 14.82(a) 显示了一个关于武术俱乐部的关系模式片段。在武术（如柔道和空手道）中，段位严格分为两种：段（黑带等级）和级（黑带以下）。`ClubNrRankedPlayers` 表存储关于特定俱乐部拥有多少段和级选手的事实。例如，元组（“KDK”，段，300）和（“KDK”，级，250）意味着俱乐部代码为“KDK”的俱乐部拥有 300 个段位选手和 250 个级位选手。

图 14.82 (a) 原始关系模式和 (b) 重构后的关系模式。

假设原始数据库有一个存储查询，用于列出每个俱乐部的代码和名称，以及黑带选手的数量（如果已知）。该查询可用 SQL 表示为查询 Q1。

```
Q1: select Club.clubCode, clubName, nrPlayers as nrDanGrades
from Club left outer join ClubNrRankedPlayers

and ClubNrRankedPlayers.rankType = 'dan'
```

假设原始模式称为 `MartialArts1`，新模式称为 `MartialArts2`。我们现在可以使用以下 SQL 命令将数据从原始的两个表迁移到新表中。

```
insert into MartialArts2.Club

```

```
Q2: select clubCode, clubName, nrDanGrades
```

## 14.10 总结

如果两个概念模式建模的是同一个 UoD（论述域），则它们是*等价*的。可以执行各种*模式转换*，将概念模式重塑为等价的模式，或可接受的替代模式。

**谓词特化**将一个谓词分解为两个或多个特殊情况，通常通过*吸收*一个枚举对象类型来实现。例如，关联“Person is of Gender {‘M’,’F’}”（人具有性别 {‘M’,’F’}）可以通过吸收 Gender（性别）特化为“Person is male”（人是男性）和“Person is female”（人是女性）。

逆向转换**谓词泛化**通常涉及从谓词中*提取*一个枚举对象类型。谓词特化/泛化 (PSG) 也可以通过考虑具有频率约束 *n* 或 ≤*n* 的角色的 *n* 种情况来执行。例如，关联“Person is a parent of Person”（人是人的父母）在其第二个角色上具有频率约束 2，可以特化为“Person is parent1 of Person”（人是人的父母 1）和“Person is parent2 of Person”（人是人的父母 2）。

**嵌套**对象类型可以使用嵌套/共引用转换 (N/CR) 与**共引用**对象类型互换。任一表示均可通过*扁平化*替换为一个或多个事实类型。例如，考虑嵌套“Enrollment(Student enrolled in Subject) results in Rating”（注册[学生选修科目]产生评分）。如果结果是强制的，这可以扁平化为三元事实类型“Student for Subject scored Rating”（学生针对科目获得评分）。如果结果是可选的，扁平化方法需要一个额外的二元事实类型（Student enrolled in Subject），并由来自三元事实类型的配对子集约束作为目标。

**重叠算法**指示了如何根据兼容子谓词之间的约束（子集、相等、排斥等）执行嵌套。请参见图 14.35。还存在其他模式转换。转换可能将图形约束转换为文本约束（反之亦然）。

尽管嵌套和共引用方法具有相同的关系映射，但许多其他等价概念模式在经过标准 Rmap 过程时，会产生不同的关系模式。将概念模式转换为另一个能产生更高效关系映射的概念模式的过程称为**概念模式优化**。

许多优化举措旨在减少关系表的数量，通常通过将非函数谓词特化为函数谓词，使其能与另一个函数事实类型分组在同一表中，或通过使用嵌套（或共引用）来统一兼容的复合键。这对于减少聚焦查询所需的表连接数量特别有用。谓词特化有时用于启用同一表中行之间的比较被替换为同一行中列之间的比较，从而消除了执行查询所需的自连接。

对正确设计的概念模式进行 Rmap 映射，会自动产生一个安全、无冗余的关系模式，通过将具有相同键的函数事实类型分组在一起，减少了表的数量。与此去概念化方法相反，**规范化**提供了一组规则，通过处理属性间的依赖来实现合理的表设计。

**综合法规范化**输入一组属性和一些基本依赖，并将属性分组到表中，旨在最小化满足这些依赖所需的表数量。**分解法规范化**应用规则将设计不佳的表分割为两个或多个表，以努力确保某些基本依赖由表键约束隐含。

这种分解方法识别出多种**范式**。如果一个表具有固定数量的列，且所有值均为原子值，则它符合第一范式 (*1NF*)。**非键属性**既不是键也不是键的一部分。在 *2NF* 表中，每个非键属性都完全函数依赖于整个键。在 *3NF* 表中，非键属性之间不存在函数依赖 (FD)。

如果 *X* 包含 *Y*，则 FD *X* → *Y* 是平凡的；如果该 FD 需要整个 *X* 而不仅仅是其一部分，则是完全的。**基本 FD** 是完全且非平凡的。**基本键**对某个其他属性具有基本 FD。在 *EKNF* (基本键范式) 表中，每个基本 FD（如果有）都来自整个键或终止于基本键内部。在 *BCNF* (Boyce-Codd 范式) 表中，每个基本 FD 都始于整个键。

如果表中 *Y* 值的集合仅依赖于 *X*，则存在**多值依赖** (MVD) *X* ↠ *Y*。如果 *X* 包含 *Y*，或者 *X* 和 *Y* 共同包含表中的所有属性，则 MVD *X* ↠ *Y* 是平凡的。*4NF* 表是一个 BCNF 表，其所有非平凡依赖均为 FD。因此，每个非函数 MVD 都需要一个单独的表。为了正确地将此概念应用于表模式，我们将其强化为**语义 4NF**，其中语义 MVD *X* ↠ *Y* 适用的条件是：对于底层事实类型的所有可能实例，*Y* 值的集合仅依赖于 *X*。

如果一个表等价于其某些投影的连接，则该表具有**连接依赖** (JD)。如果其中一个投影是表本身，则该 JD 是平凡的。如果对于每个非平凡 JD，每个投影都包含原表的一个键，则该表符合 5NF。5NF 通常称为“PJNF”（投影-连接范式），尽管这两个概念之间存在一些细微差别。

如果一个事实类型是基本的，则其所有 FD 均源自其 UC（唯一性约束）。如果存在另一个 FD，其背后隐含另一个事实类型，该事实类型是原事实类型元组子集约束的目标，这进而要求角色移除（参见图 14.72）。

如果一个表的唯一约束是域约束和键约束，则该表符合**域键范式** (*DKNF*)。如果关系模式的所有表都符合 DKNF，且表间约束要么不存在，要么很简单（例如包含依赖，通常是外键约束），则该关系模式符合 DKNF。在实践中，被建模的 UoD 中通常存在更复杂的约束，因此 DKNF 对于完整模型往往是不够的。

当且仅当一个表的所有连接依赖均为平凡时，该表符合 6NF。6NF 表的每一行恰好存储一个原子事实。

这九种范式可按范式程度递增的顺序列出：1NF、2NF、3NF、EKNF、BCNF、4NF、5NF、DKNF 和 6NF。高级范式满足所有低级范式。一般来说，规范化忽略了我们在概念和关系层面考虑的各种约束。

一旦完成概念优化和映射，物理模式应进行*调优*（例如，通过添加索引、工作表或物化视图）。还需做出各种选择，以确定强制实施约束的最佳位置（例如，在数据库中和/或在屏幕表单中）。如果性能仍然不佳，可能需要通过*受控冗余*对某些基表进行*反规范化*，以减少对连接的需求。

如果现有的数据库应用程序不令人满意，可能需要对其进行`reengineer`（重构）。这种重塑可能涉及四个主要步骤：将现有数据库模式概念化（或`reverse engineer`[逆向工程]）为概念模式；通过转换来`optimize`（优化）该模式；将其`map`（映射，或`forward engineer`[正向工程]）为改进后的数据库模式；并迁移原始数据以填充新数据库。一旦完成`data migration`（数据迁移），通常需要进行`query transformation`（查询转换），以将基于旧模式的存储查询转换为新模式上的等价查询。

### 章节注释

大多数关于模式优化的工作集中在亚概念层面。Date (2000)清晰地讨论了关系层面的各种优化方面。关于一种通过在随机生成的等价内部模式上评估适应度函数来进行模式优化的方法，请参见 van Bommel and van der Weide (1992)。
