
我们的 provenance 推理控制器（详见 [THUR2014]）随后可提供关于知识库分类的信息。例如，我们可能关心为什么一组 RDF 三元组被分类为敏感，或者为什么一个概念被视为敏感。这些问题的答案留给解释服务层。该层建立在 Pellet 解释服务之上，并显示用于推导出被另一个类包含的概念的那组公理。

解释服务层使用 `pellet` 服务，为每个敏感的 provenance 片段提供理由（也称为依据）。解释服务层可向应用设计师提供反馈。解释使用低层描述显示，可能会揭示内部分类工作原理的细节。这可能是系统的一个缺点，因为应用用户可能不理解描述逻辑或 OWL。尽管如此，该服务提供了一个期望的特性，即应用设计师可以查看其策略是如何被低层推理服务解释的。例如，由于高层描述逻辑规则的应用方式可能与作者意图不同，策略设计师现在有机会调整高层策略以获得期望的结果。解释服务层如图 18.8 所示。

## 18.7 生成器

我们现在解释将知识添加到 provenance 存储的过程。我们构建一组生成器。其中有一组后台生成器，负责提取通常可在线获取的背景信息。还有一组杂项生成器，用于构建关于疾病、药物、检查和治疗的合成数据。杂项生成器利用在线资源指导其将疾病与相关检查、治疗和疾病关联起来，因此这些杂项生成器也会产生额外的背景信息。最后，我们讨论生成实际 provenance 的工作流生成器。工作流生成器产生在线不可用的合成 provenance 数据。正是这些 provenance 数据包含我们必须隐藏的子集。

### 18.7.1 选择背景信息

我们使用当前网页上实际存在的真实信息，以便演示推理控制器相对于查询代理的先验知识集的有效性。我们确定美国的一个城市和州。针对该城市，我们选定一组邮政编码。信息从黄页、白页等免费网站下载。我们爬取这些网站，通过设置常用名和姓的种子列表，提取各个个体的姓名、地址、电话号码、年龄、性别、亲属等信息。这使我们能够为玩具医院中的每个患者捕获相似的属性值。对于医院，我们仅选择患者邮政编码范围内的医院。每家医院都有名称、地址和电话号码。由于许多医院不公开其员工姓名，我们在相同邮政编码范围内搜索医生及其专业。这很正常，因为大多数专家都隶属于其执业地附近的特定医院。一些保险公司网站确实提供医生名单及其隶属关系，但许多此类网站需要登录 ID，或每次访问都需要不同的验证码。鉴于这些障碍，我们只能接受对实际医院情况不那么准确的描绘。此外，由于我们的系统是用户驱动的，自动化和效率成为更高优先级。这并不妨碍客户使用自己的数据填充知识库。以这种方式生成数据比使用完全合成的数据使系统更真实。查询用户可以将系统的响应与可访问的背景信息结合起来进行推理。然后查询用户可以发出新查询，以验证他们对知识库中数据的猜测。

### 18.7.6 生成工作流

如前所述，在我们的玩具医院示例中，为每位患者发起更新患者记录的工作流。记录的溯源是我们在系统中假设的唯一机密数据。其目的是给查询用户一个机会，去猜测与记录相关的患者疾病、药物或检查。溯源带来的挑战比传统数据更大。控制器不仅要预测涉及用户先验知识的推理，还要考虑数据项之间因果关系以及溯源实体相关的推理（算法 18.2）。

### 18.7.7 数据库中的不完整信息

我们从各种网页生成数据，每个网页为知识库贡献了一部分。这代表了我们的知识库包含部分或不完整信息的一个典型案例。

不完整数据库由一组约束和一个部分数据库实例定义。在不完整数据库上回答结合查询是一项重要的计算任务，它是信息集成、数据交换和数据仓储等许多问题的核心。关系数据库上部分信息的一个常见例子是视图。视图可以被定义为隐藏底层数据库中的重要数据，从而限制用户的访问。这通常是为了满足某些约束而进行的；例如，财务部门的员工可以查看会计记录，但不能查看人力资源记录。给定一个查询和一个不完整数据库，任务是计算确定答案的集合。确定答案是在符合部分实例并满足约束的每个数据库实例中都满足查询的元组。在一般约束下回答查询是不可判定的。因此，通常会限制所考虑的约束语言的表达能力，以实现可判定性。数据库中不完整信息的一个类比是 OWL 本体。在 OWL 本体中，TBox 可以被视为包含约束集合的概念模式，而 ABox 则可以被视为模式的某些部分实例。

不完整数据库具有一项重要特性，推理控制器在回答 RDF 数据库上的查询时可以利用该特性。当查询返回否定响应时，用户必须判断该查询是试图访问机密信息，还是该查询在 RDF 数据库中并不蕴含。

## 18.8 用例：医疗示例

在本节中，我们提供溯源查询的示例。这些查询可用于识别策略的资源或识别用户查询的答案。

图 18.18 中的溯源图展示了一个工作流，该工作流更新了一位在医院经历三个医疗阶段的患者的虚构记录。在第一阶段，医生对患者进行了检查。检查期间，医生查阅了患者记录中的病史 `med:Doc1_1`，并执行了记录患者笔记的任务。检查结束时，医生更新了患者记录，生成了一个更新版本 `med:Doc1_2`。在第二阶段，应医生要求，患者返回进行随访。在此次就诊中，医生查阅患者记录以回顾病史，随后对患者进行了一系列检查。此次就诊结束时，医生再次更新患者记录，生成了更新版本 `med:Doc1_3`。在第三阶段，患者返回接受心脏手术。此手术由患者主治医师下令，由住院医师实施。手术开始前，主治医师和外科医生均对患者记录进行了仔细审查。手术过程中，外科医生执行了记录心脏手术各阶段结果的任务。手术结束时，外科医生更新了患者记录，生成了更新版本 `med:Doc1_4`。

## 18.9 实现约束

约束通常是规则，但也可能包含附加条件。这些条件可能规定应用规则的情形（例如，某些时间或位置标准）。

我们的方法之一是使用正则表达式来编写约束。因此，我们可以通过正则表达式指定规则的左侧（LHS），以便在溯源图中存在某种模式时强制执行约束。我们研究了以下约束处理方法。我们将讨论查询修改过程。

*   DL 概念
*   查询实现
*   SWRL 规则
*   图文法/图重写

### 18.9.1 用于强制执行约束的查询修改

我们提出了两种修改 SPARQL 查询中图模式的方法。这些方法使用 SPARQL 过滤器和属性函数。为了根据安全类型（或标签）确定三元组的类型，推理引擎将使用领域本体来确定三元组主语或对象中找到的每个数据项的概念，或 TBox 中找到的属性的分类。然而，当三元组模式仅包含变量和字面量时，此方法会失效。我们假设图模式中任何三元组的主语、谓语或宾语均为 URI。可以为三元组宾语中出现的各种字面量的安全类型确定做出特殊规定；例如，识别九位数的 SSN 或十六位数的信用卡号。

#### 18.9.1.1 查询过滤器

图模式匹配产生一个解序列，其中每个解包含一组变量到 RDF 术语的绑定。SPARQL FILTER 将解限制为使过滤器表达式评估为 TRUE 的那些。SPARQL 规范 [PRUD2006] 提供了修改图模式的不同技术。

*   **SPARQL FILTER 可使用 regex 限制字符串的值。**

    ```
    PREFIX dc: <http://purl.org/dc/elements/1.1/>
    SELECT ?title
    WHERE { ?x dc:title ?title
    FILTER regex(?title, "^SPARQL")
    }
    ```

*   **SPARQL FILTER 可限制算术表达式。**

    ```
    PREFIX dc: <http://purl.org/dc/elements/1.1/>
    PREFIX ns: <http://example.org/ns#>
    SELECT ?title ?price
    WHERE { ?x ns:price ?price.
    FILTER (?price < 30.5)
    ?x dc:title ?title. }
    ```

*   可选模式匹配中的约束，例如。

    ```
    PREFIX dc: <http://purl.org/dc/elements/1.1/>
    PREFIX ns: <http://example.org/ns#>
    SELECT ?title ?price
    WHERE { ?x dc:title ?title.
    OPTIONAL { ?x ns:price ?price. FILTER (?price < 30) }
    }
    ```

## 18.10 下一代推理控制器

社交媒体数据以及高度链接的数据均可表示为 RDF 图。因此，前几节提出的思想适用于此类社交图。安全策略也可表示为 RDF 或 SWRL 等语言。这些策略包括访问控制策略和信息共享策略。例如，如果一个人透露了其宗教信仰，则其政治倾向会被推断出来。因此，如果一个人想保持其政治倾向私密，则不应在其社交媒体网站上发布其宗教信仰。

我们可以在第 15 章中描述的访问控制架构之上构建推理控制器。图 18.19 展示了这样一个推理控制器。推理引擎本质上是控制访问并通过推理处理未授权访问的策略引擎。社交媒体数据表示为 RDF 图，而策略和知识可以使用 SWRL、RDF 和 OWL 的组合来指定。当用户发起查询（例如使用 SPARQL）时，策略引擎会检查知识库（可能包含溯源数据、策略）并修改查询。修改后的查询针对基于 RDF 的社交媒体数据库执行。前几节中的大部分讨论以及推理控制器的实现均适用于基于 RDF 的社交媒体数据。

最近，用于表示和推理知识的知识图谱概念变得非常流行。正如[FENS2020]所述：“自 Google 首创以来，知识图谱已成为一个近期无处不在使用的术语，但尚无公认的明确定义。”知识图谱本质上是从 20 世纪 70 年代和 80 年代的语义网络和概念图演变而来的。它们将语义网络和概念图与语义网和本体方面的最新成果相结合。这些知识图谱捕获知识，并利用内置的各种推理技术对知识进行推理。

就安全性和隐私而言，挑战在于：能否聚合不同的知识图谱并推断出高度机密或私密信息？我们在 20 世纪 90 年代初利用语义网络和概念图进行了大量研究并开发了工具来解决这一问题[THUR1991]。也就是说，我们使用这些网络和图来表示知识，随后应用推理技术来确定是否可以推断出敏感信息。当时我们的大部分工作集中在逻辑推理上，例如如果 A 蕴含 B，B 蕴含 C，且 C 是敏感的，那么 A 是否应该敏感？如果知识分类不正确，则旨在通知应用设计师可能存在通过推理导致的潜在安全违规。

虽然 20 世纪 70 年代和 80 年代的表示和推理技术有限，但随着语义网和本体的出现，加上传统的知识表示和推理方案（如语义网络），造就了强大的知识图谱。因此，我们的挑战是表示知识并对其进行推理，以确定是否可能存在安全和隐私违规。更多细节见[THUR2020]。
