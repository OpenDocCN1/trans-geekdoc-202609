### Document AI

当您想要从文档中提取详细信息时，例如旧印刷文档、书籍或表格的数字化扫描图片，可以使用 Document AI。这些页面可能包含段落格式的文本，也可能包含表格和图片。其中部分文本可能是印刷体，有时也可能是手写体。这也是政府办公室（如车管所 DMV）常见的文档类型，人们需要在表格上填写信息。

表格包含印刷文本和供人们填写详细信息的空白栏。这些内容可能用不同类型的墨水书写（蓝笔或黑笔等），且人们书写时有时会出错。因此，ML 模型需要理解文档的结构（在哪里期望出现“姓名”和“地址”），并对手写文本具有一定的容错能力。

另一个例子是政府文件，如护照、驾驶执照和纳税申报单。这些文档结构较好，但仍存在一些差异。

如果我们能从表格中提取重要详细信息（如“名”、“姓”、“地址”等），就得到了结构化数据，这些数据现在可以存储在数据库中并进行分析。这就是提取阶段。

Document AI 是一个理解文档并帮助您执行以下操作的平台：

*   检测文档质量。
*   矫正倾斜。
*   提取文本和布局信息。
*   识别并提取键值对。
*   提取并规范化实体。
*   拆分和分类文档。
*   审核文档（人工介入）。
*   存储、搜索和整理文档（Document AI Warehouse）。

Document AI 有两个重要概念：`processors` 和 `Document AI Warehouse`。

Document AI 处理器是文档与机器学习模型之间的接口，用于执行相关操作。有通用处理器、专用处理器（采购、身份、贷款和合同文档）和自定义处理器。您可以通过提供训练数据集（标记过的文档集）来训练自定义处理器以满足您的自定义需求。有关处理器类型的完整列表，请访问 `https://cloud.google.com/document-ai/docs/processors-list`。

Document AI Warehouse 是一个用于存储、搜索、整理、治理和分析文档及其结构化元数据的平台。

### 自定义训练

当您选择自定义训练时，您可以完全灵活地选择各种硬件选项来训练模型。

图形处理单元 (GPU) 可以加速深度学习模型的训练过程。用于自然语言、图像和视频的模型需要计算密集型操作（如矩阵乘法），这些操作可通过在 GPU 等大规模并行架构上运行而受益。

如果在单个 CPU 上训练深度学习模型，可能需要数天、数周甚至数月才能完成。但是，如果您能将繁重的计算卸载到 GPU，可以将时间缩短一个数量级。以前需要数天的任务可能只需几小时即可完成。

为了了解专用硬件的优势，让我们先看看 CPU 的工作原理。

#### CPU 的工作原理

CPU 是一种可以运行通用工作负载的处理器，包括软件应用、数据应用等。CPU 设计得非常灵活，支持大量操作。

CPU 从内存加载数据，对值执行某些操作，然后将结果存回内存，每个操作都如此。这种架构非常适合通用软件应用。然而，CPU 串行执行计算，当需要进行数万亿次计算时（这在使用大型数据集训练 ML 模型时非常典型），这种方式效率极低。

#### GPU

GPU 提供了额外的强大算力。图形处理单元 (GPU) 是一种专用芯片，旨在快速处理内存中的数据以创建图像；它最初用于处理电影和渲染视频游戏中的图像。GPU 不单独工作，它是一个协助 CPU 完成某些任务的协处理器。

### GPU 和 TPU 硬件加速

GPU 在单个处理器中包含数千个算术逻辑单元（ALU）。因此，GPU 不会为每次操作都访问内存，而是加载一块内存，并利用数千个 ALU 并行应用某些操作，从而使其更快。将 GPU 用于大型矩阵乘法和微分运算，可将速度提高一个数量级。

要使用 GPU，必须使用 A2 或 N1 机器系列。目前 GPU 提供以下类型：

*   `NVIDIA_TESLA_T4`
*   `NVIDIA_TESLA_K80`
*   `NVIDIA_TESLA_P4`
*   `NVIDIA_TESLA_P100`
*   `NVIDIA_TESLA_V100`
*   `NVIDIA_TESLA_A100`

在 `WorkerPoolSpec` 中，在 `machineSpec.acceleratorType` 字段中指定要使用的 GPU 类型，在 `machineSpec.acceleratorCount` 字段中指定工作池中每个 VM 要使用的 GPU 数量。

尝试使用实例类型配置 GPU 时，基于实例类型、实例内存等存在若干限制。部分限制如下：

*   所选 GPU 类型必须在执行自定义训练的位置可用。并非所有类型的 GPU 在所有区域都可用。
    列出可用位置的页面：`cloud.google.com/vertex-ai/docs/general/locations`。
*   存在每个实例的 GPU 数量限制。例如，可在 VM 上使用两个或四个 `NVIDIA_TESLA_T4` GPU，但不能使用三个。Google 提供了完整的参考表，随着更多实例类型和 GPU 的推出，该表可能会发生变化；请参阅下方提示中的链接。
*   GPU 配置必须具有与之匹配的机器类型相比足够的虚拟 CPU 和内存。例如，如果在工作池中使用 `n1-standard-16` 机器类型，则每个 VM 拥有 16 个虚拟 CPU 和 60 GB 内存。由于每个 `NVIDIA_TESLA_V100` GPU 最多可提供 12 个虚拟 CPU 和 76 GB 内存，因此每个 `n1-standard-16` VM 必须至少使用 2 个 GPU 以满足其要求。（一个 GPU 资源不足，且无法指定 3 个 GPU。）

#### TPU

随着 ML 工程师使用 GPU 训练超大型神经网络，他们开始注意到下一个瓶颈。GPU 仍是一种半通用处理器，必须支持包括视频处理软件在内的许多不同应用。因此，GPU 与 CPU 存在相同的问题。对于数千个 ALU 中的每次计算，GPU 都必须访问寄存器或共享内存以读取操作数并存储中间计算结果。为将性能提升到新水平，Google 设计了 TPU。

张量处理单元（TPU）是 Google 专门为机器学习工作负载设计的专用硬件加速器。请参阅图 4.5 了解 TPU-v4 的系统架构。

![图 4.5 TPU 系统架构](img/c04f005.png)

**图 4.5 TPU 系统架构**

CPU 中的 ALU 一次执行一项操作，而每个 TPU 拥有多个矩阵乘法单元（MXU）。

每个 MXU 拥有 128 × 128 个乘累加器。每个 MXU 每个周期可使用 `bfloat16` 数字格式执行 16,000 次乘累加运算。

TPU 的主要任务是矩阵处理，这是乘法和累加运算的组合。TPU 包含数千个直接相连的乘累加器，形成一个大型物理矩阵。

TPU 可对巨大矩阵执行海量运算，而这正是神经网络训练循环的核心。

##### 如何使用 TPU

TPU 可组成称为 Pod 的群组，只需极少或无需代码更改即可扩展工作负载。

Cloud TPU 提供以下 TPU 配置：

*   单个 TPU 设备
*   TPU Pod（由高速互连连接的一组 TPU 设备）
*   TPU 切片（TPU Pod 的一个细分）
*   TPU VM

##### TPU 的优势

TPU 将计算速度提升到超越 GPU 的水平。在 CPU 上需数月训练的模型，在 GPU 上可能仅需数天，而在 TPU 上可能只需数小时。简单来说，TPU 相较于 GPU 可提供一个数量级的性能提升。

##### 何时使用 CPU、GPU 和 TPU

TPU 适合特定工作负载，但在某些情况下，使用 GPU 甚至 CPU 可能更好。以下是为您的用例选择合适硬件的指南：

**CPU**

*   需要灵活性的快速原型设计
*   训练速度快的模型
*   适用小批量的小型模型
*   使用 C++ 编写的自定义 TensorFlow 操作
*   受限于主机的可用 I/O 或网络带宽

**GPU**

*   源代码不存在或更改过于繁琐的模型
*   包含大量自定义 TensorFlow 操作、因此至少需部分在 CPU 上运行的模型
*   包含 TPU 上不可用的 TensorFlow ops 的模型
*   中大型模型搭配中等批量

**TPU**

*   以矩阵计算为主的模型
*   无自定义 TensorFlow 操作的模型
*   训练时间长达数周或数月的模型
*   具有超大有效批量的大型和超大型模型

Cloud TPU **不**适合以下工作负载：

*   需要频繁分支（if/else 或条件判断）或以元素级代数为主的程序。TPU 非为执行条件判断而设计，而是为大规模矩阵乘法而设计。
*   稀疏数据（包含大量零值、仅极少非零值的数据），会导致稀疏内存访问，不适用。
*   高精度场景不适合 TPU。勿期望双精度运算。
*   包含使用 C++ 编写的自定义 TensorFlow 操作的深度神经网络，特别是主要训练循环中的自定义操作不适合 TPU 的情况。

要有效发挥 TPU 优势，应在 TPU 上运行训练循环的多次迭代。这非理论要求，而是为消除否则将导致的显著低效而提出的实际要求。您可在 `https://cloud.google.com/tpu/docs/tpus` 文档中找到这些指南及更多 TPU 信息。

###### Cloud TPU 编程模型

使用 TPU 时的主要瓶颈是 Cloud TPU 与主机内存之间的数据传输。该数据传输通过 PCIe 总线进行，其速度远慢于 TPU 互连和片上高带宽内存（HBM）。若使用模型的部分编译（部分在 TPU 上执行，其余在主机上执行），TPU 将处于空闲等待数据状态。正确的编程模型是在 TPU 上执行训练循环的大部分，理想情况下是全部。

### 预测阶段的资源预配

上一节探讨了训练阶段的硬件预配方面。本节将探讨预测阶段。

预测工作负载与训练工作负载截然不同。训练期间，我们将预配置在特定时长内使用、完成后释放的资源。

预测可通过两种方式进行：在线和批量。在线预测是指模型部署在服务器上，可通过 REST 等便捷接口查询。此处预期响应时间接近实时。批量预测是指大量输入数据已就绪并存储，预测作为“批量作业”启动。此处用户预期作业在合理时间内完成（非实时），但重点关注预测成本。

与训练工作负载相比，预测（尤其是在线预测）是一种持续性工作负载，也需要根据需求持续地扩容或缩容。批量预测工作负载与这两者也有显著差异。

在此背景下，为预测配置资源时最重要的两个考量因素是扩缩容行为和寻找理想的机器类型。让我们详细了解这两个考量因素。

#### 扩缩容行为

如果您使用自动扩缩容配置，`Vertex AI` 会在现有节点的 `CPU` 使用率变高时自动扩容以使用更多预测节点。如果您使用的是 `GPU` 节点，请务必配置适当的触发器，因为有三种资源（`CPU`、内存和 `GPU`）需要监控其使用情况。

#### 寻找理想的机器类型

要从成本角度确定自定义预测容器的理想机器类型，请将该容器作为 `docker` 容器直接部署到 `Compute Engine` 实例，然后通过调用预测接口对实例进行基准测试，直到实例达到 90% 以上的 `CPU` 利用率。确定不同机器类型的*每秒查询数成本（QPS cost per hour）*。例如，如果自定义容器包含一个只能有效利用 1 个核心的 `Python` Web 服务器进程，而该进程调用的是多线程 `ML` 模型（如大多数 `XGBoost` 实现），随着 `QPS` 增加，Web 服务器将开始“阻塞” `XGBoost`，因为每次 `XGBoost` 预测都将等待 Web 服务器进程。如果部署到 2 核或 4 核机器规格上，容器将触及 `QPS` 限制且 `CPU` 利用率会很高，因此该容器部署到 `Vertex AI` 后将能有效地自动扩缩容。

请注意自定义容器中单线程 Web 服务器的局限性；即使部署在 32 核机器规格上，它也可能无法扩容。

因此，您需要综合考虑模型类型、自定义模型情况下的服务封装代码、资源（`CPU`、内存、 `GPU`）的有效利用率、延迟和吞吐量要求以及价格，以确定要使用的实例类型。

您可以选择使用 `GPU` 来加速预测，但存在一些限制。限制如下：

*   `GPU` 只能用于 `TensorFlow SavedModel`，或用于经过设计可利用 `GPU` 的自定义容器。您不能将 `GPU` 用于 `scikit-learn` 或 `XGBoost` 模型。
