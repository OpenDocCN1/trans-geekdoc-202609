
相关的 XML 标准正在通过 W3C 推进。完整详情，包括标准本身的当前版本，可在 [www.w3c.org](http://www.w3c.org) 找到。标准文档并不特别容易阅读，但有大量更易读的教程信息可用。XQuery 对许多数据库从业者来说仍然相对陌生，但它似乎很可能在利用异构数据方面变得越来越重要。有用的介绍可参见 Walmsley (2015) 和 Melton and Buxton (2006)。

JSON 作为一种数据格式比 XML 出现得晚，但它现在已确立为数据管理中的基本组成部分。JSON 的简短介绍可参见 Basset (2015)。由于其起源于 JavaScript，其标准化工作归 ECMA 负责，该机构也负责 JavaScript 语言的规范（现在有时称为 ECMAScript）。JavaScript 的全面描述见 Flanagan (2020)。标准副本和更多详情可在 [www.ecma-international.org](http://www.ecma-international.org) 找到。JavaScript 和 JSON 分别涵盖在标准 `ECMA-262` 和 `ECMA-404` 中。后者也已被采纳为 ISO 标准 (`ISO/IEC 21778`)。JSON Schema 仍在进行中，但最新状态可在 [www.json-schema.org](http://www.json-schema.org) 找到。关于 JSONPath 的更多详情，请参见 Gössner and Bormann (2021)。

XML 和 JSON 功能现在已包含在主要关系数据库中，但由于不同实现之间存在差异，供应商的文档通常是最有用的资源。大多数商业系统提供可通过多种方式搜索的在线帮助。

## 17.1 NoSQL 运动的兴起

继 E.F. Codd 于 1970 年发表开创性的关系论文 (Codd, 1970) 之后，直到 1980 年代商业关系数据库系统才广泛可用。从那时起，它们就成为了主导的数据存储模型。其他数据资源用于较小规模，如电子表格、文本文件等，但对于大规模数据，关系系统一直占据统治地位。

NoSQL 运动始于 2010 年代，这是对关系方法中感知到的缺陷的回应 (Leavitt, 2010)。值得注意的是，“NoSQL” 并不是一个特别好的名称选择。关键问题并不在于结构化查询语言 (SQL) 本身。事实上，一些 NoSQL 供应商非常努力地提供尽可能类似于 SQL 的语言。相反，NoSQL 方法依赖于非关系数据模型来提供其独特功能。有人建议将 "NoSQL" 解释为 "Not Only SQL"（不仅仅是 SQL），但这将包括各种数据库，使其完全失去意义。

推动这一运动的驱动力，并非源于关系模型本身的失败，而是源于技术总体演进所暴露出的新挑战与新机遇。以下趋势尤为相关：

*   **数据存储成本大幅下降。** 20 世纪 80 年代，由于硬件昂贵，人们极力追求最小化存储需求。如今，消费者普遍可获得包含数 GB 免费存储空间的服务，这在早期是不可想象的。存储最小化的激励减弱，导致数据库规模持续增长。
*   **对数据价值的认知显著提升。** 即使是人与其电子邮箱地址之间经过验证的简单关系，也具有现金价值。这促使组织尽可能多地收集数据，即使该信息暂无直接用途。
*   **架构演进带来的互操作需求。** 关系型数据库诞生于“客户端-服务器”作为主导架构的时代，天然服务于有限的内部利益群体。如今组织普遍认识到在异构系统间传输数据（内部及与客户、供应商、合作伙伴等外部交互）的优势。`XML`（eXtensible Markup Language）和 `JSON`（JavaScript Object Notation）等交换格式促进了这一过程，详见第 16 章。
*   **互联网规模的指数级增长。** 自 1990 年面世以来，互联网规模增长了数个数量级。快速可靠的网络连接已普及，大多数地区视连接为理所当然。许多网站（及其支撑数据库）拥有数百万用户，而 20 世纪 80 年代数百用户即属大规模用户群。
*   **组织运营对 IT 平台的深度依赖。** 绝大多数组织的日常运营依赖某种 IT 平台以实现组织内外的数据交换。数据使用量呈爆发式增长，很大程度上得益于智能手机的普及。即大多数人随身携带计算和通信设备，无需拴系于静态业务系统。例如，街道地图出版几乎崩溃，因为人们现在通过手机（访问远程数据库）获取地图。

随着这些趋势演进，数据库系统面临新挑战与机遇。应对这些问题引发了关于组织数据资源最佳方式的思考，或许需要偏离长期作为标准的关系模型。

深入探讨 NoSQL 之前，回顾一些数据库特性将为后续讨论提供背景。本章假设安全性、安装便捷性、文档质量、供应商声誉、技术支持等选择数据库方案的重要因素在所有候选方案中均衡。我们将聚焦于区分关系型与非关系型数据库的关键方面。

### 关系模型

显而易见，起点是关系模型。许多 NoSQL 拥护者将其描述为定义特定类型的数据库系统，但这不完全准确。建模的是**信息结构**，而非系统结构。关系型数据库是为满足关系结构需求而演进的，而非相反。关系模型以自然、逻辑的方式捕获信息集合内的关系（详见本书前几章）。关系模型的表达通常称为关系**模式**（schema）。

有个特性值得特别关注。关系模式捕获信息的内在结构，但不涉及信息将如何（或能否）被使用。这种中立立场引导关注信息**是什么**，而非**能做什么**。视视角不同，这可视为优势或劣势。

假设模式已正确规范化，则可确保避免不必要的冗余，因为每条信息仅出现一次。这在考虑信息可能用途时提供了最大灵活性，因为它未针对任何特定用法方向进行优化。我们随后可能为优化特定方向性能而偏离纯规范化模式。遗憾的是，在给定场景下优化某因素通常会使其他因素反优化，因此中立立场是有用的起点。

反规范化关系模式最常见的原因是改善特定使用场景下的性能。不同关系的值可组合得出任意结果，但这涉及连接操作，计算代价相对较高。通过合并相关关系（实际上是预连接而非查询时连接）可避免连接。然而，虽然这降低了查询成本，却因反规范化引入重复信息而使更新更昂贵。

确定最佳策略需要预知预期数据流量。例如，在线目录可能更新不频繁但查询量大，而日志应用可能更新频繁但极少查询。性能顾虑在 NoSQL 数据库中占重要地位，稍后将见到。

许多 NoSQL 平台宣称“无模式”为主要优势。定义任何类型的数据库模式确实可能涉及大量工作，如识别待容纳数据、理解其业务相关性、协调竞争需求等。NoSQL 厂商网站常展示无需考虑这些问题即可创建任意数据结构的示例。

然而，关系型数据库亦可如此。我们可创建数据库，再随意添加任意列的任意表，无需参考模式。标准方法（先搞定模式再推进）反映了构建真实系统的宝贵经验。

为何定义数据模式对潜在企业系统可能很重要，有以下几个理由。界定系统职责范围可能需要协调企业内部不同观点。最好在投入可能浪费的时间精力前预先解决此类问题。

使用数据库的应用始终需知晓信息结构。编写能以绝对任意结构或格式处理所需数据的应用完全不切实际。现实中，应用程序必须针对某个定义好的结构编写。

模式也是企业视为重要的信息的便捷摘要。这便于在数据库及其应用负责人间形成共享文化。

### 分布式数据库

#### 分布式系统

分布式系统在现代计算中发挥着至关重要的作用。分布式数据库系统并非将数据仅存储在单个节点上，而是同时使用多台物理或虚拟机器。这些分布式机器共享同一状态并并发运行。

分布式系统提供三项重要特性：可扩展性、可用性和容错性。这些关注点之间存在一定重叠，但可扩展性尤其成为 NoSQL 运动的关键驱动因素之一。

可扩展性的两种主要方法可概括为**垂直扩展**或**水平扩展**。前者随着需求增加使用性能逐步更强的服务器；后者将数据库拆分为不同部分，可随着需求增加挂载到越来越多的服务器上。

垂直扩展的一种方式是将数据库迁移到更强大的机器上，但这显然存在限度。另一种选择是使用共享公共数据存储的服务器集群。这显然会引入额外的复杂性，且迟早也会达到无法进一步扩展的临界点。

NoSQL 数据库更侧重于水平扩展策略，这能应对比垂直扩展大得多的数据库。关键步骤是确定一种合适的数据库分区方法。分区可通过两种方式实现：垂直分区或水平分区。请参考图 17.1 所示示例。

#### CAP 定理

CAP 定理由 Brewer 于 2000 年首次提出，是分布式系统设计中广泛使用的概念（Gilbert and Lynch, 2002）。其核心在于理解构建分布式系统时必须做出的权衡。具体而言，它指出分布式系统不可能同时提供以下三项保证：

*   **一致性**：分布式系统中的每个节点在同一时间看到相同的数据，意味着每次读操作必须返回最近一次写操作的数据值。
*   **可用性**：对系统发出的每个请求都能在合理时间内收到响应，无论系统中的节点是否故障或遇到问题。
*   **分区容错性**：即使发生网络分区（由于网络故障或其他问题导致系统中的节点相互分离），分布式系统也应继续运行。

换句话说，CAP 定理表明在任意时刻只能满足三项保证中的两项。这意味着：高可用且分区容错的系统必须牺牲一致性；高一致且分区容错的系统必须牺牲可用性；高可用且高一致的系统必须牺牲分区容错性。

如果数据库未分区，则可以同时具备一致性和可用性（有时称为 CA 数据库）。这正是采用大型中央服务器（即单节点系统）的传统数据库的情况。如果数据库已分区，则可优先保证一致性（CP）或优先保证可用性（AP）。请考虑图 17.4 所示的分布式系统；仅两个节点即足以说明问题。

![图 17.4 简单分布式系统](img/f17-04-9780443237904.jpg)

图 17.4 简单分布式系统。

在一个节点上进行的更新可通过网络连接以一定延迟传输到另一个节点。两组用户最终都能看到一致的数据。但如果发生故障（如节点 1 和节点 2 之间的网络连接丢失），则有两种可能性：

1.  **防止访问其中一个节点**。这保证了工作节点上的一致性，但移除了另一节点上用户的可用性（CP 选项）。
2.  **允许访问两个节点**。系统对所有用户保持可用，但一个节点上的更新无法到达另一个节点，从而丧失一致性（AP 选项）。

此示例显然很简单，但说明了分布式系统中必须考虑的平衡。没有唯一的正确答案，因为选择取决于应用程序的预期用途。金融系统可能倾向于一致性，而社交媒体平台可能倾向于可用性。不同的分布式系统可能会在牺牲部分一致性与牺牲部分可用性之间探索不同的折中方案。

#### ACID 与 BASE

传统数据库通常遵循一组称为 ACID 的原则，该首字母缩写源自 Atomic（原子性）、Consistent（一致性）、Isolated（隔离性）和 Durable（持久性）四个术语（Gray and Reuter, 1993）。

*   **原子性**：事务中的所有操作必须要么全部成功完成，要么全部不执行。如果事务执行期间任何操作失败，整个事务将中止并回滚到其之前的状态。
*   **一致性**：每次成功事务后，数据库必须从一个一致状态转换到另一个一致状态。所有数据完整性约束必须在每次事务前后均得到维护。
*   **隔离性**：并发事务互不干扰彼此的执行。每个事务应表现得如同独立执行，不影响其他正在进行的事务。
*   **持久性**：一旦事务成功完成（“提交”），对数据库所做的任何更改应持久保存，即使发生系统故障也是如此。

ACID 观点非常看重一致性，使其非常适合对数据可靠性要求至关重要的传统事务型数据库系统。分布式系统的兴起促进了对另一种观点的关注，即 BASE，该首字母缩写词源自 **基本可用**、**软状态** 和 **最终一致性** 这三个术语（Pritchett, 2008）。

*   **基本可用** 意味着系统应始终可用于处理请求，即使系统正经历某种故障或中断。
*   **软状态** 指的是数据的不同副本不需要在所有时间都处于完全一致的状态。
*   **最终一致性** 意味着给予足够时间后，数据的差异最终会得到协调。

BASE 观点通过允许数据副本之间存在临时不一致，强烈倾向于可用性而非一致性。这显然比 ACID 要求宽松，但对于分布式系统更具相关性。

## CP 数据库中的一致性机制

数据库可以通过采用各种技术和机制来同步分布式系统中多个节点间的数据，从而确保一致性。CP 数据库常用的方法包括以下几种：

*   **共识协议**：CP 数据库通常利用共识协议（如 `Paxos` 或 `Raft`）就数据更新的顺序和有效性在节点间达成一致。这些协议通过在提交更改前要求多数派或一致同意，确保系统中所有节点达到一致状态。
*   **两阶段提交**：在分布式事务中，可使用两阶段提交协议来协调跨多个节点的更改提交或回滚。它确保所有参与节点同意提交事务或中止事务，从而保证系统范围内的一致性。
*   **法定人数与副本**：CP 数据库通常使用复制在不同节点间维护数据的多个副本。法定人数用于确定读或写操作所需达成一致的最小节点数，以确保一致性。通过要求一定数量的副本参与操作，CP 数据库可在返回结果前确保所有副本保持一致。
*   **同步与锁定**：CP 数据库可能使用同步机制（如分布式锁或乐观并发控制）来防止对共享数据的并发访问和修改。这些技术确保冲突的更改被串行化并按一致的顺序应用。
*   **数据版本控制与冲突解决**：CP 数据库通常采用数据版本控制或时间戳来跟踪更改，并在发生并发更新时解决冲突。通过为数据分配唯一版本或时间戳，可基于预定义的规则或策略检测并解决冲突。

当然，实现一致性可能会引入延迟并降低可用性，尤其是在网络分区或故障期间。CP 数据库采用的具体机制和权衡取决于其设计以及应用程序所需的一致性级别。

## 可用性

分布式系统中的可用性是指系统响应客户端请求的能力，即使系统的某些部分已经发生故障。这很重要，因为采用分布式架构的主要原因之一就是提高可用性和容错能力。

在分布式数据库中，可以采用多种方法来提供高可用性，确保系统即使在发生故障或网络分区时仍保持运行和可访问。以下是实现高可用性的一些常用技术：

*   **复制**，涉及在分布式数据库的不同节点间创建数据的多个副本。通过在不同位置拥有副本，即使某些节点发生故障，系统仍可继续提供读写请求服务。复制还能提高容错能力，因为即使一个或多个节点变得不可用，数据副本仍然可用。
*   **数据分区**，或分片，涉及将数据集划分为较小的子集并分布到多个节点上。每个节点负责特定的数据分区。通过分发数据，系统可以并行处理更大量的请求，从而提高可用性和可扩展性。
