
一些面向对象特性源自语义数据建模，正如我们所知，它用对象及其关系来建模现实，并包含子类型等概念（如 ORM、UML 和扩展实体关系 (ER) 建模）。各种思想也借鉴了逻辑数据模型（网状、层次、关系，特别是嵌套关系模型）的研究成果。最后，一些概念改编自人工智能领域，那里使用框架等结构进行知识表示。

DBMS 必须具备哪些特性才能算作“面向对象”？对此没有普遍公认的答案。一篇经典论文（“OODBMS 宣言”）在第一届面向对象与演绎数据库国际会议上发表 (Atkinson et al., 1990)。为了将 ODBMS 与面向对象编程语言区分开来，确定了 DBMS 的五个基本特性，然后增加了面向对象特性，其中八个被认为是必需的，五个是可选的（见表 17.3）。让我们简要了解一下该提案中的基本面向对象特性。

**复杂对象** 由更简单的对象通过构造器构建而成。该宣言提议这些构造器至少应包括集合、列表和元组，并且应是正交的（即可以按任意顺序递归应用）。例如，一个对象可能是元组的集合的集合的列表。在关系模型中构造器不是正交的（仅允许原子值的元组集合），嵌套关系模型中也不是（例如，顶层构造必须是集合）。复杂对象的概念被认为很重要，因为它允许我们以直接、自然的方式对复杂结构进行建模。

**对象标识** 的基本思想是对象应由系统生成的对象标识符（OID）来标识，而不是由其属性的值来标识。这与关系模型形成鲜明对比，在关系模型中，例如元组由其主键的值来标识。

除其他作用外，OID 还有助于跟踪那些基于外部值的标识可能随时间变化的对象。这可能因简单的重命名而发生。例如，电视频道 0 变为频道 10，或女性婚后改姓。更极端的情况是，引用方案本身可能发生变化（例如，由学号标识的学生变为由工号标识的员工）。

面向对象意义上的对象标识符一定程度上克服了这个问题，因为它们是刚性标识符（即始终指代同一对象）。它们由系统生成、不可重用、不可变，且通常是隐藏的。在 ODB 系统中，它们可能被实现为代理（逻辑标识符或自增计数器，通过索引映射到物理地址）、类型化代理（这使得类型间的迁移变得困难）或结构化地址。

**封装** 涉及将对象的操作和数据捆绑在一起，正常情况下通过其操作接口访问对象，实现细节被隐藏。例如，雇佣、解雇和晋升员工被视为 `Employee` 上的操作，并与其封装在一起。操作的实现通常称为“方法”。

封装包含这样的思想：正如在概念模式中一样，对象应按**类型**或**类**进行分类。此外，应提供某种形式的**继承**机制（例如，使子类型可继承其超类型的数据和操作）。子类型可能拥有与其超类型函数同名的特化版本函数。在这种情况下，当在子类型上调用该操作时，特化版本通常会**覆盖**更通用的版本。

例如，彩色等边三角形的显示过程可能不同于多边形的通用显示过程。存在各种覆盖选项。

**计算完备性** 要求数据操作语言能表达任何可计算函数（如有必要，可通过调用编程语言）。**可扩展性** 要求用户可定义自己的类型，且系统应像支持内置类型一样支持它们。

### “第三代 DBMS 宣言”

部分作为对 OODB 宣言的回应，一群学术界和工业界的研究人员提出了另一种“第三代 DBMS 宣言”(Stonebraker et al., 1990)。在此方案中，他们将层次和网络系统称为第一代，关系系统称为第二代。按此划分，第三代 DBMS 被视为下一代。

该宣言规定了下一代 DBMS 应遵循的三条基本原则和 13 条详细提案（见表 17.4）。该提案本质上主张用面向对象特性扩展现有关系系统，并有效地为当今的对象-关系数据库系统奠定了基础，我们稍后将讨论。

### 演绎数据库系统

请注意，OO 类对应于从概念模式抽象出的主要对象类型。因此，它们为构建应用程序的屏幕表单提供了有用的基础。封装涉及添加通用操作以及特定类型的操作（例如，可能会向 `Student` 添加 graduate 操作）。

ODB 方法的一个问题是它将太多层级混合在一起——OO 模式包含概念、逻辑和物理元素。它还涉及关联的冗余规范。例如，考虑事实类型 `Student takes Subject`。在 OO 模式中，这被指定了两次：一次在 `CurrentStudent` 上，另一次在 `Subject` 上。

在指定 OO 模式时，使用了逆向引用来声明 `CurrentStudent` 与 `Subject` 之间以及 `Subject` 与 `Lecture` 之间的双向对象链接。这使得可以使用路径表达式指定任一方向的查询。如果链接变为单向，这种通用性就会丧失。请注意，在关系模型中不存在此类导航问题，尽管当然许多查询将需要连接。虽然连接可能会降低速度，但对其使用没有限制，因为它们不需要预先建立链接。相比之下，ODB 方法通过“硬连线”查询中使用的链接来获得效率。这使得难以优化临时查询。

依赖模式本身中预先声明的访问路径来实现效率的问题，在模式演变时会加剧。届时我们可能不得不重置导航路径以针对新情况进行优化，而不能像当前的关系系统那样，仅依赖系统优化器来完成这项工作。

这并不是说 ODB 是个坏主意，或者复杂对象不应在实现层面建模为复杂对象。许多复杂结构用关系术语建模很别扭。然而，我们应该能够以一种清晰的方式指定此类结构，而不必求助于低级机制。

与 ODB 不同，关系数据库基于单一数据模型，该模型正式基于谓词逻辑。此外，关系 DBMS 现在占据主导地位，并且许多正在被扩展以解决前面提到的几个缺陷。这种扩展的关系数据库系统通常称为*对象-关系数据库*（ORDB）系统。这些本质上是通过添加对许多 OO 特性的支持来扩展的关系 DBMS，例如额外的数据类型（空间、图像、视频、文本……）、构造器（数组、集合……）和继承。一些主要的商业系统通过允许插入模块来支持扩展数据类型。此类模块可能由供应商或第三方开发。这些模块被称为“关系扩展器”、“数据刀片”或“数据盒”。

SQL 标准已大幅逐步扩展，以包含若干面向对象特性（例如，用户定义类型和函数、封装、对 oid 的支持、子类型、触发动作和计算完备性）以及演绎特性（例如，递归并）。

鉴于关系 DBMS 庞大的安装基础、这些产品的持续扩展、将应用程序移植到新数据模型的成本，以及 SQL 标准的广泛采用，下一代 DBMS 很可能会从当前的关系产品中演变而来。正如印度教吸收了威胁其存在的其他宗教的特性一样，关系模型很可能会吸收面向对象信仰的有趣特性，而不会被其取代。

SQL 基础 DBMS 中发生的所有变革是否真正可取，这是有争议的。虽然扩展数据类型（空间、视频等）的使用显然是一个进步，但在许多情况下，构造器（数组、多重集等）的使用是值得商榷的，因为它们可能使为临时查询和更新设计高效数据库变得更难，并使编写优秀优化器的任务复杂化。

关于许多 OO 特性如何被移植到关系模型上的详细评论，请参见 Date (2000) 和 Date and Darwen (1998)。无论如何，关系和对象-关系系统目前在商业上占据主导地位，而其他竞争者如对象数据库系统正努力争取任何有意义的市场份额。

SQL 包括数组、行类型和多重集。一个挑战是对这些集合建模并提供映射算法以高效实现它们。各种构造器（例如用于集合、包、序列和模式）已被添加到某些版本的 ORM 和 ER 中。此外，ORM 和 UML 都允许将某些类型的集合表示为概念模式上的映射注解。虽然在概念模型中使用集合类型有利于映射到等效的实现结构，但直接在概念层面建模复杂对象通常要困难得多，并且通过口头化和填充实例来验证它们极其别扭。复杂对象也倾向于被过度使用，而更简单的解决方案被忽视。关于集合类型的进一步讨论，请参见第 10 章。

如今，许多应用程序使用第三代语言（3GL），如 `C#` 或 `Java` 来指定用于瞬态内存存储的对象模型，并使用 SQL 来指定用于持久存储的关系或对象-关系数据库。由于数据必须在对象模型和关系模型之间移动，因此在*对象-关系映射*上花费了大量精力。使用诸如 `NORMA` 之类的工具从 ORM 模型生成对象模型和关系模型，简化了创建对象-关系映射过程的任务。

### 演绎数据库系统

*逻辑编程语言*（如 `Prolog`）是基于一阶谓词逻辑的声明性语言。事实和推导规则（包括递归规则）可以简洁地声明，并具有内置的回溯支持。

`Datalog` 结合了关系数据库系统的特性和逻辑编程语言的一个安全子集。与 `Prolog` 不同，`Datalog` 中的查询保证在有限时间内执行完毕。`Datalog` 已被用于自然语言处理，并作为演绎数据库系统的查询语言。

*演绎数据库*为以声明方式管理复杂数据提供了优雅而强大的方法，特别是对于通过递归推导出的信息。这赋予了它们强大的规则强制机制，具有内置的回溯和对递归规则的优秀支持。例如，`isanAncestorOf` 关系可以从基本的 `parent` 关系和以下两条霍恩子句规则中推导出来：

*    `X isanAncestorOf Y :- X isaParentOf Y.`（基础子句）
*    `X isanAncestorOf Y :- X isaParentOf Z, Z isanAncestorOf Y.`（递归子句）。

此处，规则头部和主体之间的“:-”表示“**如果**”，规则主体中的逗号“,”表示“**且**”。规则头部中的个别变量假定为全称量化，而在主体中引入的变量假定为存在量化，因此这些规则等价于谓词逻辑中的以下公式：

*    `∀x,y ( x isanAncestorOf y  if  x isaParentOf y )`
*    `∀x,y [ x isanAncestorOf y  if  ∃z(x isaParentOf z and z isanAncestor of y) ]`

相比之下，`SQL-92` 完全无法表达递归查询。`SQL:1999` 引入了递归并运算符，但其语法更复杂，且其执行不享有内置的回溯功能。

各种基于或受 Prolog 或 Datalog 影响的演绎数据库系统已被开发，例如 LogiQL (Halpin and Rugaber, 2015) 和 Soufflé ([`github.com/souffle-lang`](https://github.com/souffle-lang))。LogiQL 由 LogicBlox 开发，但自 2014 年 12 月 LogicBlox 被 Predictix 收购后不再可用。Soufflé 是一种[开源](https://en.wikipedia.org/wiki/Open_source)、[并行](https://en.wikipedia.org/wiki/Parallel_computing)、[逻辑编程语言](https://en.wikipedia.org/wiki/Logic_programming)，包含一个解释器和一个以并行 C++ 为目标的编译器。

RelationalAI ([`relational.ai`](https://relational.ai)) 正在开发一种极其强大的编程语言，该语言支持演绎数据库功能以及知识图谱，预计发布日期在 2024 年中左右。该系统称为 `RAI`，基于云，其语言称为 `Rel`，因为其数据结构以关系（有序元组的集合）为中心。

祖先关系的递归规则 ∀x,y \[ x isanAncestorOf y if ∃z(x isaParentOf z and z isanAncestor of y) \] 可以通过以下定义在 `Rel` 中表达：`def isanAncestorOf (x, y): exists((z) | isaParentOf(x, z) and isanAncestorOf(z, y))`。

作为 `Rel` 强大功能的一个迹象，RelationalAI 程序员团队编写了一个 `Rel` 程序，可自动将免费公共领域版 NORMA 工具中捕获的 ORM 模型转换为 `Rel` 中的结构。此转换能够映射极其复杂的 ORM 模型，并可捕获 ORM 中本质上所有的真值约束。撰写时，道义约束尚不支持。

假设 ORM 事实类型 Country has CountryName 已使用二元谓词 `hasCountryName` 在 `Rel` 中声明，ORM *强制角色* 约束 **Each** Country has **some** CountryName 可表示如下：

```
ic (c) { Country(c) implies hasCountryName(c, _) }
```

头变量 `c` 是全称量化的，下划线字符“`_`”表示匿名变量，因此约束表达式等价于以下谓词逻辑公式：

*    ∀x \[Country(x) → ∃y(x hasCountryName y)\]。

Country 在 Country has CountryName 中的角色的*内部唯一性约束*可通过声明谓词为*函数式*来声明，如下所示：

```
ic () requires function(hasCountryName)
```
