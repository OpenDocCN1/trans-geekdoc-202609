## RESTful 方法简述

正如我们在简介中提到的，REST 是一组约束，而 RESTful API 是满足 REST 约束的 API。让我们强调一下：REST 是一种风格，而不是像 HTTP 这样的协议。REST 和 HTTP 之间存在常见的混淆。Roy Fielding 允许使用任何首选协议来实现 REST。虽然此选项可用，但大多数 RESTful API 使用 HTTP 协议，这是 Roy 推荐的首选协议，但并非强制要求。其他类型的协议可以是 FTP、SMTP、IMAP 等。流行的表述类型（REST 中的 RE）是 JSON（代表 JavaScript 对象表示法），同样，这也不是约束。RESTful API 可以使用其他表述，如 XML、HTML、CSV、纯文本、PDF 等。

根据我们的选择、需求和业务约束，有多种方式来构建 RESTful API。最终，每个 RESTful API 都满足 REST 约束，但方式各异。

![](img/Figure-7.2.jpg)

**图 7.2：** REST 约束

REST 有六个约束。最终，我们可以随心所欲地编写代码。REST 风格旨在指导我们构建更合理的系统。实施这些约束旨在提高客户端性能、服务端的稳定性和可扩展性。这些约束相结合，旨在解决和修复大多数系统已遇到并深受其害的常见熟悉问题。

### 资源与表述

我们已经多次提到资源和表述。这两个术语是 REST 风格的核心。

*   **资源：** 资源是一条信息，代表作为单一单元的功能性数据。例如，资源可以是一个对象（账户、用户、椅子）、对象集合、文档、图片等。我们可以通过所谓的资源方法来改变资源的状态，这些方法需要是统一的（作为统一接口约束的一部分）。例如，HTTP 方法如 `GET`、`POST`、`PUT`、`DELETE` 等充当资源方法。
*   **表述：** 资源表述指的是资源的状态，包括数据、元数据和超链接。

### 约束

以下是六个约束。

#### 客户端-服务端

该约束也是微服务架构的核心原则。它鼓励我们保持客户端和服务端松耦合。客户端和服务端之间不得共享任何依赖。组件需要独立、分别开发；客户端仅知道服务端暴露的 URI。

#### 统一接口

这是最复杂的约束，由其他四个子约束组成。URI 代表统一资源标识符，是一串字符，Web 技术可识别并关联特定资源。

![](img/Figure-7.3.jpg)

**图 7.3：** URI 组成

与前面提到的协议和表述不同，URI 不是可选的。REST 强制我们使用 URI 来确定资源的唯一性。在服务端和客户端之间存在一个接口。该约束旨在通过四个子约束创建统一性，同时建立该接口：

*   **资源标识：** 它涉及确保每个 URI 对特定资源都是唯一的。这种唯一性至关重要，可防止从不同接口操作同一资源。
*   **通过表述操作资源：** 服务端需要暴露的表述是期望的修改。此表述需要尽可能明确。

    例如，像 `DELETE + URI` 这样的 HTTP 方法用于特定资源（`DELETE https://domain:port/api/account/{accountId}`）表示客户端请求 API 删除一个具有 `accountId` Account ID 的账户。开发人员必须能够轻松理解 URI，而无需进一步的文档（至少在大多数情况下）。
*   **自描述消息：** 消息必须包含所需资源上所有的“指令”。服务器应仅从消息中获取所有必要信息，而无需进一步的询问或信息。
*   **超媒体作为应用状态引擎：** 超媒体指电影、图片、文件等所有形式的媒体。当客户端请求 RESTful API 服务器获取资源数据时，它期望获得该资源的数据。部分数据可以是超媒体，REST 旨在提供指向媒体数据的链接，而不是以某种形式直接提供数据本身。

#### 无状态

每个从客户端到服务器的请求都是隔离的。服务器绝不能以任何方式依赖之前的请求，也不能依赖服务器的本地动态上下文。客户端请求必须包含执行请求所需的所有必要数据。

#### 分层系统

每个从客户端到服务器的请求都会经过各层。客户端与业务逻辑之间从不存在直接连接。这些层可以是认证、缓存、负载均衡等。此约束鼓励我们在客户端和服务器之间创建分离的层，例如微服务架构中那样。客户端对其与服务器之间的不同层是不可知的。大多数层通常存在于 API 网关中——正如上一章所述。

#### 可缓存

此约束强制服务器返回一个响应，其中包含指示数据是否来自缓存的数据。

#### 按需代码

此约束不常见，也不是必需的。服务器可以通过下载小程序或脚本为客户端提供额外功能。例如，客户端想要将 JPEG 转换为 PDF，因此它向服务器请求一个执行此操作的脚本。客户端获取脚本并执行它。

## 设计 API

在着手编写服务之前，第一步是了解产品需求、工程约束以及可能影响决策的任何因素。定义它将是什么样子、必要的能力是什么、什么不是、以及如何实现它。决定可用资源及其对应的表现形式。

### 能力

RESTful API 的标准能力如下：

*   文档
*   认证和授权（可以在 API 网关层）
*   RBAC（可以在 API 网关层）
*   分页
*   限流
*   缓存
*   过滤
*   排序
*   监控和可观测性
*   功能开关
*   告警
*   错误处理
*   自动生成代码客户端

每个 API 可能不需要所有这些能力，也可能需要此处未提及的其他能力。在构建微服务架构时，每个 API 都希望实现这些能力的一部分或更多，且实现方式可能与其他 API 相同。如果我们为每个 API 重复实现相同的能力（即使我们为每个能力使用一个包），最终将得到大量略有差异的样板代码。

为了解决这个问题，我们需要创建共享基础设施。实现共享基础设施的一种方式是通过共享代码（使用单体仓库时）。在 Go 中，这些代码将位于名为 `pkg` 的目录中。另一种实现共享基础设施的方式是使用 SDK（使用多仓库时）；每个 API 将导入并使用此 SDK 以满足其自身需求。

### 文档：Swagger 和 OpenAPI

构建 API 最关键的部分是记录 API 规范。记录 API 规范的行业标准是使用 Swagger 和 OpenAPI。

OpenAPI 是一种用于标准化 API 文档的规范的官方名称。它具有独特的语法，可以用 JSON 或 YAML 编写。

Swagger 是一组帮助实现 OpenAPI 的工具。大多数 Swagger 工具可在开源项目中获取；付费是获取高级工具的一种选择。

*   **Swagger Editor**：允许我们在线编辑 Swagger YAML 并查看变更的工具。
*   **Swagger UI**：为 OpenAPI 规范生成 UI 的工具。
*   **Swagger Codegen**：通过 OpenAPI 规范，Swagger Codegen 可以用多种编程语言生成各种 API 客户端和服务端。
*   其他可以帮助满足各种需求的工具，此处不一一列举。

![](img/Figure-7.4.jpg)

**图 7.4：** Swagger editor（https://editor.swagger.io/）

Swagger 因其简单的语法而成为功能最强大、应用最广泛的工具集，但它有许多描述 API 的选项。客户端和服务端之间的约定是使用集中式文档。很多时候，负责 API 服务端的开发人员/团队与负责客户端的开发人员/团队是不同的。

在每个类别目录中，每个资源都有一个不同的目录。请注意，单个资源可以包含多个端点。例如，`GET /api/fruits/apple/:id, POST /api/fruits/apple, UPDATE /api/fruits/apple/:id, DELETE /api/fruits/apple/:id` —— 这四个端点都与同一个资源相关 —— apple。在每个资源目录中，可以有四个文件：

*   `controller.go`：这是主要处理程序，请求在通过所有中间件后从此处开始。它解析请求，向客户端通知错误（4XX 状态码），并按 OpenAPI 约定返回数据。
*   `db.go`：这有时命名为 `repository.go`。该文件包含针对数据库的所有操作，无论是什么数据库。这种结构的威力在于我们可以切换数据库，而我们只需要处理 `db.go` 文件。请注意，该文件本身不应包含模型/实体。通常有一个单独的机制来管理数据库，如 ORM 和迁移工具（`gorm` 是实现 ORM 的标准且广泛使用的工具）。
*   `routes.go`：定义资源的所有端点。请注意，单个资源可以包含多个端点。该文件将包含如下函数：

```
func RegisterRoutes(group *gin.RouterGroup) {
    group.GET("/fruits/apple/search", gin.HandlersChain{ProcessRequestSearch}…)
    group.GET("/fruits/apple/:id", gin.HandlersChain{ProcessRequestID}…)
}
```

*   `service.go`：它包含所有业务逻辑。

### 资源方法

如前所述，REST 并不强制我们使用特定协议，但 HTTP 方法目前作为使用最广泛的 REST 协议占据主导地位。本节将专注于 HTTP；然而，我们可以在其他协议上实现相同的行为。

*   `GET`：它仅用于检索信息；它不会以任何方式改变状态。此方法代表读取操作。每次使用 `GET` 方法，我们都应获得相同的结果，除非另一个 HTTP 方法的请求修改了该资源。此类请求可以被缓存，且有长度限制。示例：
    `GET https://www.example.com/accounts`
    `GET https://www.example.com/accounts/search?name=john`
    `GET https://www.example.com/accounts?page=5`
*   `POST`：它为特定资源创建新数据 —— 单行或多行。此类请求不可缓存，且无长度限制。通常，数据在请求体中发送，而不在 URI 中。`POST` 和 `GET` 方法是 HTTP 方法中使用最广泛的。示例：
    `POST https://www.example.com/accounts`
    `POST https://www.example.com/accounts/myaccount_id/users`
*   `PUT`：它通常用于更新现有资源状态。然而，它也可以像 `POST` 方法一样创建新数据。`POST` 和 `PUT` 的主要区别在于 `PUT` 是幂等的，而 `POST` 不是。这种差异意味着多次调用 `PUT` 方法将给出相同的结果，而 `POST` 由于潜在的副作用不保证这一点。示例：
    `PUT https://www.example.com/accounts/{myaccount_id}`
*   `DELETE`：它用于删除特定资源。
*   **其他**：`PATCH`、`OPTIONS`、`HEAD`、`CONNECT` 和 `TRACE` 是我们可以使用的其他 HTTP 方法，但不如前面的方法常用。

让我们简要概览标准 HTTP 状态码（X 代表任意数字，`1XX` 表示 100-199）：

*   **1XX**：信息响应。不常用。
*   **2XX**：成功响应，我们希望看到的状态码。
    *   `200 OK`：通常由 `GET` 方法用于确定数据已成功检索。
    *   `201 Create`：通常由 `POST`/`PUT` 使用。
*   **3XX**：重定向消息，通常用于将请求重定向到其他服务器、端点、域名等。
*   **4XX**：客户端错误响应，意味着请求有问题，这是客户端的责任。这类响应在中间件或控制器中捕获。
    *   **400 Bad Request**：客户端未提供处理请求所需的正确/恰当信息。
    *   **401 Unauthorized**：服务器无法识别客户端。
    *   **403 Forbidden**：客户端已被识别，但无法访问请求的数据。
    *   **404 Not Found**：它是最流行的状态码之一，表示请求未被识别。
*   **5XX**：服务器错误响应，意味着服务器本身有问题，用户通常对此无能为力。
    *   **500 Internal server error**：服务器进入了一个我们不知道如何处理的场景。

## 打造服务器
