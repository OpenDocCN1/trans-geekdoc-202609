### 19.2.4.4 计算 `R[01].m_col`

这是列混合（Mix Columns）步骤，无疑是最复杂的：

- 这实际上是 GF(2⁸) 上的计算，即系数为 7 次的多项式。
- 但不用担心，它也可以表示为固定矩阵 `C` 的乘积。假设移行后的 `R[01].s_row` 是按列写入的：

| C | `R[01].s_row` |
| --- | --- |
| `02 03 01 01` | `d4 e0 b8 1e` |
| `01 02 03 01` | `bf b4 41 27` |
| `01 01 02 03` | `11 98 dd 52` |
| `03 01 01 02` | `ae f1 e5 30` |

该乘法的结果是另一个 4×4 矩阵。再次按列读取将得到 `R[01].m_col`。然而，这些乘法是在 GF(2⁸) 或 mod 256 下进行的，可以使用“对数表”（见 Rijmen and Daemen 2001, pp. 221–222）来简化计算。事实上，代码中使用简短函数 `mul`：

```
logtable[(Logtable[a] + Logtable[b]) mod 255]
```

### 19.2.4.6 最后一步——密钥调度

在密钥调度中，我们使用上一个密钥，将其与上一个密钥的其他部分进行异或运算，通过 S 盒并加上计数器。这次，我将只计算密钥的字（即 4 个字节）。

取上一个密钥的前 4 个字节：`2b 7e 15 16`。将最后 4 个字节左移一次：`09 cf 4f 3c → cf 4f 3c 09`。将这最后部分通过 S 盒：`SubByte(cf 4f 3c 09) = 8a 84 eb`。这就是新密钥的前 4 个字节：`2b 7e 15 16 ⊕ 8a 84 eb ⊕ a0 fe 17 = c9 9a f9`。

### 19.3 密钥管理问题

尽管 AES 或几乎所有加密方法都有其优缺点，但它们共同的一个问题是密钥管理。这种问题在于密钥必须被发送方和接收方共享，这以导致了 AES 或几乎所有的加密方法被统称为“对称加密”。

### 19.4 对称加密或公钥加密

无论 AES 的优缺点如何，它无法解决的问题就是密钥管理问题。假设我们有一个六个用户的网络，每个用户都需要与其他五个用户通信一个独立的密钥。因此，对于六个用户，我们需要（如图所示）：

```
\frac{6 \times 5}{2} = 15\text{ 个密钥}
```

通常情况下，会有 1000 个用户的网络，因此我们需要

```
\frac{1000 \times 999}{2} = 499500\text{ 个密钥。
```

遗憾的是，我们无法使用这个网络来分发密钥，因为在分发密钥之前网络是不安全的。

### 19.5 用于密钥管理的公钥密码学模型

现在考虑以下方法。对于 1000 个用户中的每一个，选择一个密钥 `ki = (kpi, ksi)`，`i = 1, …, 1000`。在全局公共目录中列出所有的“公”密钥 `kpi`，`i = 1, …, 1000`。然后，向用户 `j` 发送消息，选择公钥 `kpi` 并应用加密变换 `c = T(kpi, m)`。

发送密文 `c`。

只有用户 `j` 拥有解密所需的剩余密钥：

```
T((kp[i], ks[i]), c) = m
```

因此，与其在 n 个用户的网络中管理 O(n2) 个密钥的秘密分发，只需要 n 个密钥，而且它们不需要秘密分发。

### 19.6 身份验证

此外，公钥概念还可以用于消息的身份验证，这是密钥系统无法解决的问题。

考虑一个基于传统对称密钥加密系统。同样考虑它被用于银行网络中的资金转账。某天，系统管理员收到一封来自 X 的消息。管理员使用 X 与自己之间约定的密钥对消息进行解密。消息内容是：“从我的账户转账 1,000,000 美元到系统管理员的账户。”经理尽职执行了操作。

X 向当局投诉，称该消息是伪造的，是由经理本人（她）发送的。当从塔希提通过长途电话联系管理员评论时，他表示该消息是真实的，且 X 已经撤回了转账意愿。

由于 X 和经理都必须知道该密钥，使用该加密系统没有办法解决这一纠纷。
