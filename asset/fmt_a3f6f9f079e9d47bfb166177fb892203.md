
# 管道安全与配置安全

## 第 5 章：管道安全

传输数据从一处到另一处的“管道”，乍看之下似乎很简单——一端数据进，另一端数据出。现实则更复杂。

设想两座城镇之间的铁轨。最简单形式下，它只是从一座城镇延伸到另一座城镇的连续钢轨。但要将人员和货物从一座城镇运到另一座，光有钢轨是不够的——必须有车厢承载不同种类的内容：供人乘坐的客车、集装箱车、专门装化学品或牛奶的液体罐车、散货车、轨道检查车等多种类型。其中一些可自行移动（如轨道车），但其他必须由机车牵引。列车通过将这些部件组装成编组，作为一个整体沿轨道行驶，因此一端必须有空间集结它们，另一端有空间解编重组。必须有办法检测列车是否未到达目的地（因脱轨或机车故障）。有时列车会在不属于同一组织甚至不同国家的轨道上运行，而不一定知情。

网络空间中的“管道”情况相同。管道承载着混合的、具有不同需求的流量，且由于分组交换，这些不同种类的流量被交织在一起。管道本身没有智能，因此关于异常情况下发生什么的所有决定，都是双端的责任，双端因此必须能够达成一致。

### 协议层级与网络通信

定义流量外观及流动方式的规则集称为**协议**。它们构成了每根管道所连接节点的交战规则。

人类交谈时也存在类似的交战规则。在最底层，语音只是一系列振动。在更高一层，我们将短时振动片段归类为音素。再往上，将音素组合归类为单词。最上层则涉及语言、演讲或对话等概念。电话能传输语音，但它仅将语音视为振动。语音识别系统（如许多自动话务员）必须在音素和单词的更高层级理解语音。智能代理或聊天机器人则必须将语音理解为对话。

同理，协议按层级排列，对应不同抽象层次。通信底层仅通过光纤、导线或无线电信号将比特从一端移动到另一端（比特流本身不包含任何揭示其“含义”的结构）。上一层理解比特集合作为通信单元的含义。更高层管理更复杂的通信过程（类似对话），包括处理两端不同步的情况。

### 5.1 IP 协议

在最底层（仅移动比特之上）是一种描述数据如何以单元移动的协议，但仅限简单单元。这就是**互联网协议**，即 `IP`。它负责将单个信息块（以**数据包**为单位）从源 `IP` 地址（发送计算机）传递到目标 `IP` 地址（接收计算机）。

这两台计算机通常不会直接相连，因此该协议不仅负责将数据从管道一端移至另一端，还负责通过一系列管道将其导向正确位置。它利用每个中间节点的路由表引导每个数据包，使其在每一步都更接近目的地。

现实类比是寄送实体邮件。邮局在一地收到信件，尽力投递到另一地。途中会经过分拣办公室，每个办公室将其发往旅程的正确下一阶段。

正如实体邮件一样，`IP` 传递是尽力而为的，发送方不会收到数据包已送达的通知。

在 `IP` 中，每个数据包独立于其他所有数据包处理，因此即使从同一来源发往同一目的地的数据包，也不一定遵循相同路径，也不保证按发送顺序到达。实体邮件也存在这种情况。

某个数据包在旅程各阶段可能经过的管道，其容量不一定相同。特别是数据包可能遇到只能处理较小数据包尺寸的管道（类似开车走捷径却遇到限高桥）。`IP` 拥有将大数据包分割成小数据包并在目的地重组的机制。这类似于将包裹切成薄片，使其看起来像一堆信件即可发送。遗憾的是，`IP` 拆分和重组数据包的机制过于简陋——它依赖每个片段仅记录其距原始数据包开头的距离——这给轻易篡改创造了机会。

### 5.2 TCP 协议

尽管我们使用实体邮政服务已超一个世纪，但它作为网络空间数据传输模型有明显缺陷。两个更抽象的协议构建在 `IP` 之上。使用这些高层协议的流量被分割成 `IP` 数据包并通过 `IP` 传输，但它们无需知晓具体实现方式。它们不再将管道视为简单的比特移动连接器，而是视为 `IP` 流量传输器。这些高层协议提供了 `IP` 缺失的功能，如保证交付和流速管理。

最重要且作为互联网标准的协议是**传输控制协议**，即 `TCP`。它太常见了，以至于常与 `IP` 连用称为 `TCP/IP`。`TCP` 提供了 `IP` 缺失的以下功能：

*   **端点间的有状态连接，创建会话**（而非单向单数据包投递）。会话类比对话：有始有终，存在期间双方均负责管理。
    建立连接要求一端发送控制**段**。
*   **数据包到达确认**，以便通过超时检测丢失的段，并由会话另一端的发送方重发。
    因双方知晓会话存在，均预期来自对方的流量。段到达后，接收方必须在约定时间内确认（双方可协商调整）。若发送方未收到确认，则假定段丢失并重传。
*   **按发送顺序向目标节点交付数据**，利用每个段携带的**序列号**。当某段延迟或丢失时，目标节点接收到的后续段会被保留，直到缺失片段到达。因此，目标端必须预留大量空间用于重组。
*   **拥塞控制**，通过信号告知发送方何时停止发送以便接收方追赶进度。
*   **更复杂的寻址方案**，发送方和接收方均使用 `IP` 地址和**端口号**的组合。节点上运行的每个预期与外界交互的软件使用特定端口。某些常用软件的端口号预先确定且广为人知——例如 Web 流量用端口 `80`，邮件用端口 `25`，域名服务用端口 `53`。其他软件每次启动时选择端口号。这些 `IP` 地址和端口号的组合标识了节点及其上运行的特定软件，确保数据来自并送达正确位置。

`TCP` 为互联网上两设备提供稳健通信，但若路径上某些管道较小、发生拥塞、或两端传输时间长，速度会相对较慢。

### 5.3 UDP 协议

在交付速率至关重要的场景下，还有一种可用的高层协议。它称为**用户数据报协议**，即 `UDP`，提供与 `IP` 同类功能——尽力而为交付，无排序或错误控制——但具备 `IP` 地址 + 端口寻址。因此 `UDP` 以牺牲可靠交换换取快速端到端交付。

`UDP` 用于延迟比偶尔丢包更重要的应用。此类应用通常主要单向流式传输数据。例如网络电话（`VOIP`）、视频传输（`Skype`、`Netflix`）。有时也用于可假设高可靠性的局域网（如远程桌面协议），因其避免了 `TCP` 的开销。

### 5.4 利用协议的攻击

所有这些协议设计之初环境更受信任，面对的系统性能约束比当今大多数系统更大。因此它们极易受到攻击。

以下是涉及管道的一些常见攻击：

#### 网络安全威胁与对策

##### 窃听

数据包和段的全部内容均可读，除非载荷部分在到达 `TCP` 协议前已被加密。即使载荷已加密，数据流向的所有细节及流量大小在网络中仍完全可见。

这需要访问流动中的网络流量。可通过物理窃听流量（点对点管道）、监听无线网络，或诱导网络接口硬件将其本地区域内所有流量复制到节点（该功能原用于故障检测，但仍普遍存在）。

网络空间中大量流量未加密，易被捕获读取。加密流量的协议头仍可见，因节点需知晓各段/包的发送去向。流量分析可揭示端点对间的流量大小及时间；`TCP`/`UDP` 端口号常关联特定应用，从而推断通信应用；即便单一流涉及多应用，包大小分布也可能泄露所用应用，进而推断计算机功能（如 Web 服务器、打印服务器具有特征流量模式）。

##### 地址欺骗

因数据包和段头部的 `IP`（及端口号）字段无保护，伪造流量可随意发送，合法流量可被重定向。修改目的地址可将流量发送至错误位置（如冒充真实计算机的主机）；修改源地址可生成恶意流量并伪装来源（这也是网络攻击溯源困难的原因之一，因隐藏流量来源极其容易）。

##### 篡改内容

若载荷未加密，可在不留痕迹的情况下篡改或替换内容。若操作得当，部分流量内容可被不可检测地替换。

段头部部分字段含校验和，源自内容的简单函数。这些远非数字哈希；设计初衷是捕获传输错误，而非刻意篡改。若内容被篡改，对应校验和只需重新计算修改即可匹配，过程简单。

此三协议通用缺陷，或许是全流量加密普及的主因。

##### IP 分片攻击

`IP` 可将大包分片为小片段，以便穿越无法承载典型包的细链路。每片段含字段描述其距初始大载荷起始处的偏移。全部分片到达目的地（可能不到达）时，`IP` 利用这些字段作为偏移量重组。然而，这些偏移量未经过合理性检查。攻击者若在途篡改偏移量，重组过程可能导致载荷部分被其他部分覆盖，最终包载荷与原始形态毫无相似。

此攻击非直接损坏包（可直接实施），而是使携带分片的包在防火墙等设备前显得无害，重组后却成防火墙本会拦截的包。

##### 拒绝服务

`TCP`（及 `UDP` 程度较轻）的端点交互含状态，存在利用此状态的攻击。最简单是 `SYN` 洪水攻击。因 `TCP` 会话建立需三步交互，攻击者可执行第一步——请求会话——并忽略目标响应。目标须跟踪所有建立中会话。分配空间满时，无法接受新连接请求（含合法请求），且攻击填满的进行中连接表槽位永不解决。这类似反复致电餐厅用不同名字预订同一时段却从不赴约。

其他拒绝服务攻击令目标过忙而无法做有用工作。单一攻击者系统难产生足够流量，但攻击者可向大量其他系统发送伪装成来自目标系统的流量，这些系统随即同时响应目标。

接收 `UDP` 包导致接收方检查对应端口是否有应用等待流量；若无，发回“地址无此用户”响应。拒绝服务攻击可向大量系统发送目标为罕见端口地址的段，伪造发送者地址为待攻击目标系统。响应随即涌向目标并将其淹没。

##### 序列号预测与插入

攻击者可篡改 `TCP` 段内容，即“中间人”攻击。但插入额外流量较难，因会话各方向连续段具有递增序列号。序列号使目的地跟踪已收段并正确确认，亦使其按正确顺序重组。这增加了插入额外段（从而有限接管流量）的难度。若攻击者能猜测序列号（并可能通过如拒绝服务攻击阻止真实源系统发送），可伪装成源。早期 `TCP` 生成初始序列号方案极简，现代实现则致力于使其随机。攻击仍可能但需更多工作。

##### 协议栈指纹识别

协议官方协议规范不足，致使各实现可在最高效（或最简）处自由发挥。不同厂商（或 `Windows`、`Linux`、`Mac` 等操作系统家族）实现略有差异。虽在关键处必须一致，但段头部仍留有痕迹泄露生成该协议的特定实现。这类似人类言语口音——虽能听懂不同口音（大多），但口音透露与所言无关的信息。

攻击者可观察流量，通过不同实现选择的痕迹或后果，推断特定节点运行何种软件。这可能因暴露已知弱点而使攻击规划更易，揭示哪些节点为良好目标。

### 5.5 对策

因数据移动机制被视为“幕后”且高技术活动，效率成关键设计标准，安全鲜被考量。故针对这些攻击的对策寥寥。

核心问题在于管道须“说同一语言”以连接异构节点并承载混合流量。协议变更须向后兼容，致使安全弱点即使在坚定改进努力下仍存续多年。

解决协议弱点的主要方法是对传输的数据进行加密（但这无法防止流量分析），并使用工作在更高层级的协议来查找并修正 `TCP` 层面的问题和缺陷。这些协议被称为*应用层协议*，它们对待 `TCP` 的方式正如 `TCP` 对待 `IP` 一样。它们假定存在一种建立会话并用于传输数据的方法（这正是 `TCP` 所做的），但它们会在数据传输上施加自己的检查，以确保传输正确发生。

一个重要的高层协议是*虚拟专用网络*（VPN），它将来自某个节点的所有流量视为单一的加密流，传输至另一个受信节点，在那里解包后正常传输至目的地。这保护了数据在 VPN 传输过程中的安全，并防止了在该段旅程中的窃听。通常，一端节点是个人或企业计算机，另一端节点归 VPN 提供商所有。

由于*所有*流量在 VPN 中混合在一起，因此从流量分析中获取有用信息或针对某个特定会话进行攻击变得困难得多。当然，这仅能保护使用 VPN 的那段通信，因此这只是对互联网中特别不可信部分的一种保护。VPN 的工作原理有点像船只组成船队航行以寻求保护。

使用 VPN 会产生一个副作用，即流量看起来似乎源自受信节点而非其真实源头。这被用于规避针对流媒体视频服务等的国家特定限制，也被异见人士用于在不被政府发现或干扰的情况下使用网络空间。

不幸的是，攻击者已利用 VPN 牟利，他们冒充 VPN 提供商，诱使用户注册使用其 VPN，随后在流量通过所谓的“受信”节点时进行监视。

节点应对管道固有不安全性的另一个关键方式是使用*防火墙*。防火墙可以是独立的交换机，也可以是现有交换机中包含的软件。它们包含一组关于允许何种流量通过的规则；所有其他流量均被丢弃。规则通常应用于 `TCP` 流量层面，因此它们可以描述哪些源 `IP` 地址、目的 `IP` 地址和端口的组合是可接受的，同时阻止所有其他组合。

由于某些端口与特定类型的流量强相关，这也意味着可以允许某些类型的流量而禁止其他类型。不幸的是，虽然端口 `80` 保留给 Web 流量，但由于可以使用 Web 浏览器执行许多不同的操作，因此在防火墙中允许端口 `80` 流量就会为许多不同类型的活动打开方便之门。

一些防火墙独立处理每个段，仅检查其是否满足允许进入的规则。更复杂的防火墙会跟踪会话（因为它们能看到建立会话的段），并确保所有其他方面可接受的流量也属于某个会话。

防火墙可以存在于各个规模——从隔离整个政府或跨国企业，到单个局域网。

那些检查并阻断由应用层协议承载的流量的防火墙通常被称为*入侵检测系统*。运行在个人电脑和手机上的杀毒和反恶意软件应用程序就是以这种方式工作的。它们检查传入的文件，如电子邮件附件或网页内容，以查看是否包含恶意软件。换句话说，它们等待来自低层的流量被组装成完整的对象，然后检查这些对象以判断是否允许通过。

因为它们更了解流量的目的，且能负担更多时间和资源，入侵检测系统在检测方面比防火墙可以更复杂。

两个系统之间的管道可以是点对点的，也可以涉及向多个系统广播。例如，有线网络使用交换机将计算机相互连接，这使得攻击者更难潜伏在网络上窃听。无线网络至少在潜在层面上，会使所有传输对网络上的每个其他设备可见，因此窃听变得简单直接。

对于手机，拦截流量最简单的方法是让用户安装一个拥有广泛访问手机应用权限的应用程序，并在流量仍在手机内部时捕获它。第二种策略是创建一个*伪基站*，诱使手机连接到它，记录流量，再将其转发给真实的基站。由于手机通常连接信号最强的基站，这只要求伪基站比真实基站更近即可。拦截使用标准电话网络发送的语音通话和短信非常简单，相关产品可购买，且使用所需专业知识极少。

拦截无线网络流量也很简单，但取决于具体的网络配置。网络接口（无论是交换式还是无线）都能向其本地区域内的所有节点广播，攻击者往往可以隐蔽地开启此功能。

最后，管道可能被物理切断（通常是因在错误地点挖掘），一旦发生这种情况，可能会导致大规模混乱。

## 第 6 章：配置安全

构成网络空间的节点和管道必须能够相互通信，因此交互规则、诸如 `IP` 和 `TCP` 等协议使这成为可能。但节点和管道的系统必须作为一个整体协同工作，以应对不断变化的环境——节点和管道的消失或出现、拥塞等瞬态效应——即使该系统是去中心化的，并由许多不同的实体拥有和管理。这需要一种管理整个系统的方法，即使在去中心化的情况下也能发挥作用。

这种组织反映了最初的阿帕网（Arpanet）是为在核攻击中生存而设计的，因此采用了去中心化设计。互联网的所有基本运行都继承了这种去中心化设计，因此很少有可以直接控制互联网属性的节点。

### 6.1 互联网控制报文协议

互联网必须有一种方法来维护每个交换机上的路由表，并发现何时出现故障并加以处理。该机制使用*互联网控制报文协议*（ICMP）。该协议运行在与 `IP` 相同的层级，可被视为一种并行协议。用户无需感知它，因为它在后台处理配置，但它包含可被用于攻击的漏洞，因此为了全面理解网络安全，必须了解它。

### 6.2 域名服务

另一个在网络空间幕后运行的系统是 **域名服务**，它负责处理人类可读的计算机名称与 `IP` 地址之间的映射。它是一组分布式的数据表，记录着当前的映射关系。

`DNS` 服务器的进出流量使用 `UDP`，但这种流量对用户不可见——它嵌入在 Web 浏览器、邮件客户端以及其他需要将名称解析为 `IP` 地址的应用程序中。

**域** 是名称空间的一部分，之所以存在是因为计算机名称具有层级结构。例如，`.uk` 是英国所有计算机的域，`gov.uk` 是英国所有政府计算机的集合，而 `data.gov.uk` 是存放英国政府开源数据的系统的域。

在互联网的每个子区域中，至少有一台计算机，即 **本地 DNS 服务器**，将保存名称到 `IP` 地址的映射，通常是与本地计算机正在执行的任务相关的映射。例如，这些本地服务器可能保存属于同一企业或机构的所有计算机（无论本地还是远程）的映射，因为本地计算机很可能与它们通信；也可能保存用户通常使用的热门新闻或社交媒体网站的映射。

如果设备请求的映射不在其本地 DNS 服务器中，该服务器会将请求发送到更高级别的 DNS 服务器。如果该服务器知道答案，它将返回映射，该映射会被发送回原始请求计算机，并**同时存储在本地 DNS 服务器中**。之所以这样做，是因为一旦一台本地计算机请求某个映射，它或其他本地计算机在不久的将来也很可能想要知道该映射。如果 DNS 服务器映射存储空间耗尽，它将删除近期最少使用的映射。

如果更高级别的服务器也不知道该映射，它会将请求发送给下一级更高的服务器，或者可能跳过某些级别直接发送给 **顶级 DNS 服务器**。顶级 DNS 服务器知道如何找到 `.com`、`.uk` 以及所有最高级域的 DNS 服务器。

层级结构中的某些 DNS 服务器是特定域的 **权威 DNS 服务器**，它们永远不会删除该域的映射。因此，`.uk` 有其权威 DNS 服务器，其他 DNS 服务器总能通过询问每个子域的权威服务器来找到 `.uk` 内的子域。换句话说，权威 DNS 服务器持有域名与 `IP` 地址之间的**权威映射**，而较低级别的 DNS 服务器持有此类映射的**副本**。

DNS 系统因 **区域** 的定义而变得复杂，区域横跨域和子域的层级结构。例如，一家企业可能在不同国家拥有域名，如 `fredmart.com`、`fredmart.co.uk` 和 `fredmart.com.au`，并希望将访问其任何网站的访问者重定向到适合其国家的版本。它们可以为所有 `fredmart.*` 域名设置一个权威 DNS 区域服务器来实现这一点。
