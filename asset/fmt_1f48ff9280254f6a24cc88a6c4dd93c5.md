
等式约束等同于两个子集约束，并用于替代它们。至多只能在两个（完整）角色序列之间声明一个集合比较约束。然而，可在角色序列的不同部分之间声明不同的集合比较约束，例如，在第一个角色之间声明子集约束，在第二个角色之间声明排斥约束。两个角色序列之间的子集或等式约束意味着各个角色之间存在类似的约束。相反，单个角色之间的排斥约束意味着包含这些角色的所有序列之间都存在排斥约束。

这些约束蕴含结果在图 6.29 中针对角色对进行了描绘，使用“⇨”表示“必然蕴含”。在每种情况下，蕴含仅在一个方向上成立。等式约束的结果与子集约束的结果类似。在排斥示例中，如果简单排斥约束在右侧角色之间，则成立类似结果。隐含约束通常应从模式中省略。作为练习，您可能希望证明这些结果。如果您在此处遇到困难，请尝试构造一些反例来反驳等价性声明。例如，如果 `pop(r[1], r[2]) = {(a1, b1), (a2, b2)}` 且 `pop(r[3], r[4]) = {(a1, b2), (a2, b1)}`，则 `pop(r[1]) = pop(r[3])` 且 `pop(r[2]) = pop(r[4])`，但 `pop(r[1], r[2]) ≠ pop(r[3], r[4])`。

![图 6.29 隐含约束不应显示。](img/f06-29-9780443237904.jpg)

图 6.29 隐含约束不应显示。

本书后面还会提到其他约束蕴含定理。一个重要的结果是：配对子集约束的目标包含函数角色的情况。例如，图 6.29(a) 中的左侧模式具有一个从下部角色对到顶部角色对的配对子集约束。如果我们在顶部角色对的左侧角色上添加一个简单唯一性约束，这对下部角色对的左侧角色意味着什么？如果下部谓词是二元的，则该角色也必须是唯一的！作为练习，请证明这一点。该结果的一个重要推论是：如果下部谓词长于二元（即元数大于 2），则在这种情况下它必须拆分，因为将存在一个从第一个角色到第二个角色的隐含函数依赖 (FD)。当我们在第 14.6 节讨论规范化时，将说明这一结果。

## 6.5 子类型化

如果一个对象类型的实例被归类为更具体的类型，则该特化类型称为**子类型**。考虑图 6.30 中所示的 Person 类型。为便于讨论，该类型填充了八个人，以剪贴画形状表示。记录了每个人的性别和出生国家。Gender 的两个实例用生物学上的男性和女性符号表示。国家用其地图形状表示（此处仅显示澳大利亚、意大利和墨西哥）。

![图 6.30 根据性别或出生地将 Person 归类为子类型。](img/f06-30-9780443237904.jpg)

图 6.30 根据性别或出生地将 Person 归类为子类型。

根据性别，我们可以将 `Person` 分类为子类型 `MalePerson` 和 `FemalePerson`。我们在图 6.30 中将男性放在左侧，女性放在右侧，这样你就可以直观地看到通过垂直划分 `Person` 类型来创建这些子类型。我们也可以根据出生国将人员分类为子类型。在图 6.30 中，这通过将 `Person` 水平划分为 `Australian`、`Italian`、`Mexican` 等来表示。对于所示的人口，有三个澳大利亚人、两个意大利人和三个墨西哥人，其他国籍位于下方的各个层中（此处简标为“等”）。为简化起见，忽略归化问题，因此此处“Australian”用于“澳大利亚出生者”之意，以此类推。

在建模中使用子类型的主要原因是*声明类型约束*（在本例中，是*声明一个或多个特定角色仅由给定子类型扮演*）。例如，医疗数据库可能会记录患者是否受过割礼，但这仅针对男性患者记录。

子类型化的第二个原因是*鼓励模型组件的复用*。例如，如果我们已经拥有一个描述对象类型 `Employee` 的详尽子模式，并想讨论经理，我们可以将 `Manager` 声明为 `Employee` 的子类型，并仅添加特定于经理的额外细节。

如果 `Employee` 在参考模型中定义，它可以被导入到许多不同的模型中，并根据每种情况适当地进行特化。如果为对象类型定义了行为，这也可以连同数据方面一起复用。在编程应用中，这可以显著减少代码重复。

子类型化的第三个原因是揭示 UoD 中使用的*分类法*或分类方案。然而，在 ORM 中，我们通常避免仅为暴露分类方案而引入子类型。为什么？首先，分类法通常可以用更经济的方式建模。例如，要表明有两种性别，我们只需在 `Gender` (`.code`) 上添加一个值约束，如 `{"M", "F"}`。除非我们在应用领域中有一些特定角色需要它们扮演，否则无需引入 `Male` 和 `Female` 子类型。

其次，如果我们纯粹为分类法使用子类型，子类型的数量会迅速失控。例如，假设我们希望根据出生国对人员进行分类。我们只需要事实类型：`Person was born in Country`。如果我们改为引入 `Person` 的子类型，每个国家一个，这将导致模式中出现近 200 个子类型！

这太疯狂了。如果这些子类型中的某一个扮演特定角色，那么我们应该引入它；但如果不扮演，我们就没有必要引入。例如，假设我们想记录 `Australians` 是否希望他们的国家成为共和国，但对其他国籍没有特定内容要记录。在这种情况下，`Australian` 是我们应该引入的唯一子类型。

本章前面使用欧拉图来描绘一个集合作为另一个集合的子集。在设计概念模式时，我们经常需要引入子类型，并明确说明什么是什么的子类型。对于简单情况，例如图 6.31(a)中 *B* 和 *C* 是 *A* 的子类型，可以使用欧拉图。

![图 6.31 欧拉图适用于简单的子类型化 (a)，但不适用于复杂情况 (b)。](img/f06-31-9780443237904.jpg)

图 6.31 欧拉图适用于简单的子类型化 (a)，但不适用于复杂情况 (b)。

将其解释为假设的欧拉图，问题是 *A* 是否包含不在 *B* 或 *C* 中的元素。如果 *A* 确实有更多元素，可以通过在 *B* 和 *C* 外部区域添加星号来表示。正如第 8.2 节所讨论的，ER 的 Barker 表示法为此目的使用一种称为“Other”的特殊类型。

欧拉图的优点是通过将一个集合或类型在空间上放置在另一个内部，直观地显示包含关系。这对简单情况效果很好。然而在实践中，一个对象类型可能有许多子类型，它们可能重叠，且一个子类型可能有许多超类型。

例如，图 6.31(b) 中的子类型模式描绘了以下信息：*B*、*C* 和 *D* 是 *A* 的子类型，而 *E* 是 *C* 和 *D* 共同的子类型。此外，*B* 与 *C* *重叠*（即它们可能有共同实例），*C* 与 *D* *重叠*，但 *B* 和 *D* 是*互斥的*（不能有共同实例）。例如，*A* = `Person`；*B* = `Asian`；*C* = `Consultant`；*D* = `American`；*E* = `TexanConsultant`。

对于这种情况，欧拉图变得无望地复杂。此外，个别子类型可能有许多特定细节需要记录，如果子类型节点挤在其超类型节点内部，根本没有空间附加这些细节。

基于这些原因，非平凡的子类型化不采用欧拉图。我们需要一种简单的表示法，无论情况多大或多复杂，都能用来显示子类型关系和子类型角色。这通过将子类型显示在其超类型*外部*，并通过*箭头*描绘子类型-超类型连接来实现。

基本思想如图 6.32 所示。这里，*A* 和 *B* 是对象类型。假设 *A* = `Employee` 而 *B* = `Manager`。实体类型 `Employee` 是可能记录事实的所有员工的集合。子类型 `Manager` 是可能记录事实的所有经理的集合。在任何给定的数据库状态下，`pop(Employee)` 和 `pop(Manager)` 分别是数据库中实际引用的员工集合和经理集合。

![图 6.32 B 是 A 的真子类型。](img/f06-32-9780443237904.jpg)

图 6.32 *B* 是 *A* 的真子类型。

一般来说，当且仅当 `pop(B)` 始终是 `pop(A)` 的子集，且 *A* ≠ *B* 时，*B* 是 *A* 的**真子类型**。在这种情况下，*A* 是 *B* 的*真超类型*。如果 *A* = *B*，我们不指定任何子类型连接。基于此理解，我们在谈论子类型和超类型时通常省略“真”。

形容词“真”适用于类型关系，但不一定适用于*人口*关系。可能存在一种数据库状态，其中 `pop(A)` = `pop(B)`。例如，如果尚未录入关于 *A* 的事实，则 `pop(A)` 和 `pop(B)` 都等于 {}；以我们的例子为例，我们可能选择先录入关于经理的信息，再录入其他员工。

这种表示法不如欧拉图直观，因为子类型显示在其超类型“外部”，尽管子类型内的每个对象实例也必须包含在超类型内。此外，除非我们添加某种方式来捕获，否则关于子类型重叠的信息就会丢失。

这是用箭头而非空间包含来描绘子类型连接的后果。然而，这种劣势远远被以下优势抵消：能够方便地表示任意复杂度的子类型模式，同时仍在每个节点周围留出足够空间以附加细节。

使用这种表示法，图 6.31(b) 的欧拉图中所示的复杂子类型模式可以建模为图 6.33 所示。此处，`A` 是 `B`、`C` 和 `D` 的 `公共超类型`，而 `E` 是 `C` 和 `D` 的 `公共子类型`。一般来说，公共超类型至少是其子类型的并集；如果它是其子类型的并集，则称其子类型 `穷尽` 它。在我们的例子中，`B`、`C` 和 `D` 不穷尽 `A`。请注意，图 6.33(a) 仅描绘了子类型连接。

![图 6.33 这是对图 6.31b 中子类型连接的另一种建模方式。](img/f06-33-9780443237904.jpg)

图 6.33 这是对图 6.31b 中子类型连接的另一种建模方式。

图 6.31(b) 包含额外信息：`B` 与 `C` 重叠，`C` 与 `D` 重叠，而 `B` 和 `D` 互斥。因此，如果使用子类型箭头表示法，必须用其他某种方式来传达子类型是否互斥。在 ORM 中实现这一点的一种方法是通过虚线将 `排除` 符号“⨂”附加到相关的子类型链接上。

没有排除符号表示这些类型的总体可能重叠。有了这个附加符号，图 6.33(b) 现在传达了图 6.31(b)中欧拉图的排除/重叠信息。

要表明两个或多个子类型对其超类型是 `穷尽` 的（即它们的并集等于该超类型），需用虚线将 `包含性或` 约束符号“⨀”连接到相关的子类型链接上，如图 6.34(b) 所示。此约束既适用于总体也适用于类型。超类型总体中的每个实例必须出现在至少一个子类型的总体中。

![图 6.34 B 和 C 互斥 (a)、穷尽 (b) 或两者兼具 (c)。](img/f06-34-9780443237904.jpg)

图 6.34 `B` 和 `C` 互斥 (a)、穷尽 (b) 或两者兼具 (c)。

如果我们结合这两个约束，就会得到一个 `异或` 约束，表明超类型被 `划分` 为其子类型，如图 6.34(c) 所示。

隐含地，每个子类型箭头下面都有一个派生的、实例级的 1:1 二元关联“is/is”。子类型排除约束和穷尽约束分别对应于超类型在这些关联中所扮演角色上的排除约束和包含性或（析取性强制）约束——因此选择这些符号来表示这些约束。

从这个角度来看，图 6.34 中的约束可以分别口头化为：**没有** `A` **同时** 是 `B` **和** `C`；**每个** `A` **是某个** `B` **或** `C`；**每个** `A` **恰好是** `B` **或** `C` **之一**。

子类型之间可能重叠，特别是当它们基于不同的分类方案时。例如，在图 6.35 中，子类型 Australian 和 Female 重叠。因为重叠的子类型拥有共同元素，所以可以从它们交集中的一个或多个元素形成一个公共子类型。例如，子类型 FemaleAustralian 既是 Australian 的子类型，也是 Female 的子类型。

![图 6.35 间接子类型连接是隐含的，因此应省略。](img/f06-35-9780443237904.jpg)

图 6.35 间接子类型连接是隐含的，因此应省略。

子类型关系具有 `传递性`：如果 `A` 是 `B` 的子类型，且 `B` 是 `C` 的子类型，则 `A` 是 `C` 的子类型。在这种情况下，称 `A` 是 `C` 的 `间接子类型`。例如在图 6.35 中，FemaleAustralian 是 Australian 的直接子类型，而 Australian 是 Person 的直接子类型。因此，FemaleAustralian 是 Person 的间接子类型。为了说明目的，该间接链接在图中用星号标记以显示其派生性质。然而，为了避免混乱，间接子类型链接应从图中省略，因为它们是传递隐含的。

如果一个子类型有两个或更多直接超类型，这称为 `多重继承`。例如，在图 6.35 中，FemaleAustralian 同时继承自 Australian 和 FemalePerson。一般来说，一个子类型至多是其超类型的交集。如果一个子类型只有一个直接超类型，这称为 `单一继承`。

一个超类型可以有多个直接子类型，一个子类型也可以有多个直接超类型，因此一般来说我们得到的是一个 `子类型图` 而不是树。超类型和子类型被称为图的 `节点`。因为箭头提供了方向，所以我们得到的是一个有向图。
