### 动态链接库注入

动态链接库 (DLL) 注入发生在程序被强制在其地址空间中加载 DLL 并运行 DLL 代码时。DLL 中的代码可能是黑客想要在系统上执行的恶意代码。

### 轻量级目录访问协议注入

轻量级目录访问协议 (LDAP) 注入是指黑客填写一个 Web 表单，该表单通常使用表单数据通过 LDAP 调用查询数据库，但由于应用程序开发人员未验证任何输入，黑客可以将任何内容插入页面，且该内容将由服务器执行。

### 可扩展标记语言注入

可扩展标记语言 (XML) 注入类似于 SQL 注入和 LDAP 注入，不同之处在于黑客将 XML 代码插入应用程序。如果应用程序开发人员未验证输入，黑客可能会利用注入的 XML 数据操纵应用程序的流程。

您可以通过清理输入和验证输入来防止所有不同类型的注入攻击。

### 跨站脚本

跨站脚本 (XSS) 是一种流行的攻击形式，涉及黑客将脚本代码插入网页上的表单中，并将脚本代码提交给服务器。这里的目的不是攻击服务器，而是让服务器将该脚本提供给另一个客户端，由该客户端解析并执行该脚本。跨站脚本可能发生的一个简单示例是：黑客将脚本代码提交到存储在数据库中的字段中。当另一个人访问该站点时，Web 服务器将返回数据库中的数据并将其发送给客户端浏览器——这段代码随后将被客户端解析并执行。

跨站脚本攻击有不同类型：

*   **反射型** 反射型 XSS 攻击是指脚本代码被插入表单并提交给服务器进行处理。服务器即时处理该脚本，而不是像前面描述的那样将其存储在数据库中。

### 存储型/持久型

存储型 XSS 攻击，也称为持久型 XSS，就是前面描述的那种情况：黑客提交脚本，服务器在后台将其存储在数据库中（例如讨论论坛网站）。当有人访问该网站时，网站从数据库检索数据，然后将 HTML 页面中的内容发送给用户。用户的浏览器读取 HTML 以创建页面，当遇到脚本代码时，会在客户端系统上执行。

为防止 XSS 攻击，开发人员可以执行以下操作：

- **验证输入** 开发人员应验证用户提供的所有输入，因为这些输入会进入应用程序，并拒绝无效数据或对其进行清理。

- **显示时对数据进行编码** 接收数据时，开发人员可以对数据进行编码，使其在页面上显示，而不会作为代码执行。

#### 跨站请求伪造

跨站请求伪造（简称 CSRF 或 XSRF）是一种针对已通过网站身份验证的用户的攻击，例如用于网上银行的银行网站。随后，黑客会诱骗用户运行一个网页；例如，黑客向用户发送电子邮件或短信，诱使用户点击链接。该链接会执行恶意网页加载，并向用户已登录的银行网站发送命令（如表单提交）。在这种情况下，最终结果是用户在不知情的情况下可能会向黑客的账户转账。

为防止 CSRF 攻击，应用程序开发人员应在对其自身逻辑的每次调用中使用同步令牌。同步令牌是一个只有开发人员知道的秘密字符串值，他们会在每个调用页面逻辑的 HTTP 请求中检查同步令牌（一个字符串值）。这样，如果 HTTP 请求到达但请求中不存在同步令牌，应用程序就会知道不处理该请求，因为它不是来自应用程序或网站中的链接。

#### 传递哈希

传递哈希攻击是指攻击者能够从系统中获取密码哈希值，这可能是由于利用了该系统上的漏洞。一旦他们从系统中获取了密码哈希值，攻击者就会尝试使用用户名和在前一次攻击中获得的密码哈希值连接到网络上的其他服务器（而不是尝试破解密码哈希值）。

#### 权限提升

权限提升攻击是指攻击者利用系统漏洞，在该系统中仅拥有最低权限——通常是用户级权限。随后，攻击者使用权限提升技术提升其权限级别，从而获得对系统的管理员级访问权限。例如，黑客可能利用系统上运行的服务，但意识到他们只有用户级访问权限。利用成功后，黑客可以迁移或跳转到另一个以提升权限运行的进程，从而获得这些特权。

#### SSL 剥离

SSL 剥离攻击是指黑客能够将自己置于受害者和受害者使用的安全 HTTPS 网站之间。当用户向安全网站发送请求时，黑客拦截该请求，并实质上与目标网站建立自己的安全连接。受害者与黑客之间的通信被降级为不安全的 HTTP 通信（允许黑客查看所有数据），但受害者的流量随后会由黑客使用 HTTPS 发送到安全网站。

#### 驱动程序操纵与重构

遵循持续代码改进的思维模式，我们一直在寻找改进代码的更好方法。当应用程序在环境中运行出现问题时，可以创建并应用一个 Shim（垫片/兼容层）来修复兼容性问题。就 `driver manipulation` 而言，可以创建一个 Shim 来允许驱动程序在该驱动程序存在兼容性问题的操作系统上运行。从安全角度来看，对应用程序进行 Shim 处理可能会创建新的攻击载体，因为在 Shim 中重写函数并将其应用于应用程序或驱动程序可能会意外引入缺陷——如果创建 Shim 的人是黑客，则可能是故意引入。驱动程序重构是指用恶意驱动程序替换原装驱动程序。当应用程序调用重构后的驱动程序时，它们实际上是在执行恶意代码。

#### 其他应用程序攻击

对于 Security+ 考试，您还需要熟悉许多其他应用程序攻击。以下列出了其他类型的应用程序攻击：

- **竞争条件** 竞争条件是一种软件编程问题，线程（线程是工作单元）执行的代码必须按特定顺序完成，然后另一个线程才能执行相同的逻辑。例如，假设银行账户存款操作有三个步骤：(1) 读取账户余额，(2) 增加存款金额，(3) 将新余额保存回账户余额。如果两个线程或进程执行该逻辑，我们会假设每个步骤都按顺序完成，然后下一个线程才执行该逻辑；否则，账户余额将不准确。例如，假设银行账户中有 100 美元。如果逻辑执行顺序错误（发生竞争条件），线程 1 可能读取账户余额（100 美元），线程 2 也读取账户余额（100 美元）。然后每个线程都增加 50 美元并将值保存回去。最终余额只有 150 美元，而不是预期的 200 美元。这是因为发生了竞争条件，我们需要每个线程在下一个线程或进程执行相同逻辑之前完成所有三个步骤。这被称为 `time of check/time of use (TOCTOU)` 软件缺陷，要修复此问题，代码应检查正在访问的对象以确保其未被其他代码访问，然后最小化对象的使用时间并将其释放，以便其他代码可以访问它。

- **重放攻击** 重放攻击，或会话重放攻击，是指攻击者拦截受害者的流量并能够从该流量中获取其会话 ID。攻击者随后可以向目标重新提交流量，实质上冒充受害者，因为攻击者拥有会话 ID。

- **应用程序编程接口 (API) 攻击** API 是程序员创建的函数库，提供某种功能。API 攻击是指黑客试图将该 API 用于恶意目的——通常通过调用函数并对这些函数执行注入攻击。

- **资源耗尽** 人力不足无法妥善完成工作是一种漏洞类型。例如，程序员不足可能导致偷工减料，跳过输入验证等重要任务。同样，过度劳累的程序员更容易出错。

- **内存/缓冲区漏洞** 有许多内存漏洞或缓冲区漏洞需要注意：

  - **内存泄漏** 内存泄漏是指程序在使用完内存后，不释放内存供其他进程使用。如果每个程序用完内存后都不释放，系统将耗尽内存并崩溃。

## 整数溢出

当数据存储在内存中时，会被分配一个特定大小的内存块。当创建了一个内存块来存储整数值，但算术运算的结果超过了所分配整数类型的最大尺寸时，就会发生整数溢出错误。据发现，该应用程序在处理整数溢出时会产生意外响应，从而构成安全问题。

### 缓冲区溢出

当软件向其分配区域之外的内存区域写入数据时，就会发生缓冲区溢出。

### 指针/对象解引用

指针是程序员用来引用内存区域的工具。当程序员想要读取内存内容时，他们会`解引用指针`。从安全角度来看，请确保阻止不可信或注入代码的执行，以防止黑客读取这些内存区域。

#### 应用程序漏洞存在的原因

您可能会问为什么这些攻击会得逞。原因有很多，但关键要记住的是，黑客学习技术是为了弄清如何破坏它们或将其用于恶意目的。

以下是应用程序攻击得逞的关键原因：

### 输入处理不当

输入处理是软件程序员的另一项工作。每当数据传入应用程序时，程序员都应验证该数据，并确保其适合当前任务。如果数据无效，应向用户显示错误，而不是处理该信息。如果程序员不验证输入，黑客就可以将恶意数据注入应用程序，以非预期的方式控制软件。

### 错误处理不当

错误处理也是软件程序员的工作之一，包括确保应用程序捕获发生的任何错误，并适当处理这些错误，以免应用程序崩溃。测试软件时，开发人员会寻找错误的存在。错误处理不当可能导致程序被利用。

### 默认配置

安装软件或系统时，请务必尽可能更改默认配置。黑客了解产品的默认配置，并学习如何根据默认配置利用系统。您应更改默认值，使黑客更有可能放弃并寻找更容易攻击的目标。

### 错误配置/弱配置

大多数漏洞的存在是因为软件或操作系统被管理员错误配置，从而处于非安全状态。请检查任何新部署系统的配置，并遵循这些系统的加固程序。

### 弱密码套件和实现

当今系统中另一个常见漏洞是使用弱加密技术或协议。例如，您可能会发现某个应用程序正在使用 `DES` 或 `3DES` 对称算法加密数据。这被视为弱加密，您应升级到更强的算法，如 `AES`。另一个例子是将较弱的加密协议（如 `TLS 1.0` 和 `TLS 1.1`）替换为较新的实现 `TLS 1.3`。

### 新威胁/零日

需要注意的最大类型漏洞之一是零日威胁，这是一种未披露或未知的漏洞，供应商尚不知情，或刚刚知情，因此没有机会提供补丁来修复它。

### 认证目标 15.02

##### 安全应用程序开发概念

安全中一个被忽视的方面是我们日常使用的应用程序的安全性。了解黑客如何通过公司系统上运行的应用程序入侵系统非常重要。这里的关键教训是要理解：作为网络管理员，您可以完成自己的工作，加固系统并确保其通过补丁保持最新，但如果系统上安装的一个应用程序不遵循安全编码概念，该系统就很容易被攻破。在本节中，您将了解用于防范应用程序攻击的安全编码概念。

#### 安全编码概念

如前所述，保护系统的很大一部分是确保在系统上运行的应用程序是以安全方式开发的。这取决于应用程序开发人员——他们需要学习安全的应用程序开发方法，以防止黑客通过应用程序入侵并获取系统访问权限。

##### 开发生命周期模型

`软件开发生命周期 (SDLC)` 概述了开发应用程序的主要阶段。软件开发生命周期有六个阶段：

### 需求收集与分析

第一阶段涉及收集应用程序的需求。

### 设计

收集需求后，您将根据需求着手设计应用程序。

### 实现（编码）

实现阶段也称为编码阶段。在此阶段，您编写应用程序的代码。

## 测试

编码阶段结束后，您必须测试代码，以验证其是否按预期工作。

### 部署

测试完成后，您就可以将应用程序安装（部署）到需要该应用程序的系统上。

### 维护

在维护阶段，您通常会收到使用应用程序人员的反馈。您需要在此阶段修复应用程序出现的任何问题。

有不同的软件开发生命周期模型可供选择。其中两个较流行的模型是瀑布模型和敏捷模型。它们具有相同的阶段，但在如何从一个阶段移至另一个阶段方面有所不同：

### 瀑布模型

采用瀑布模型时，您将依次完成 `SDLC` 的每个阶段，且无法在任何时候返回之前的阶段。关键在于您必须确保充分完成每个阶段，以免需要返回（在该模型创建时，返回被视为成本高昂）。

### 敏捷模型

采用敏捷模型时，您可以采取更迭代的方法，如果发现遗漏或需要重工，可以返回之前的阶段。例如，您可以进行一些需求收集、一些设计，然后实现一个原型供客户审查。然后，根据客户的反馈，您可能需要重新审视前几个阶段，以完成需求收集和应用程序设计。在测试期间，您可能会发现需要更改设计或代码。敏捷模型将返回某个阶段的能力视为应用程序开发的关键。

#### 应用程序环境

让新创建的软件经过大量测试以确保其遵循安全编程概念进行开发至关重要。这意味着应用程序在其生命周期内要经历不同的阶段或环境。应用程序经历的环境顺序如下：

1. **开发** 开发环境是创建应用程序并调试以修复任何应用程序错误的地方。

2. **测试** 应用程序开发完成后，应将其部署到测试环境，该环境拥有应用程序运行所需的所有基本要素，如测试数据库服务器。

3. **预发布** 测试完成后，应用程序进入预发布环境，该环境尽可能接近生产环境（可将其视为“模拟生产”环境）。这实质上是应用程序进入生产前的最后一个测试环境。

## 4. 生产

一旦应用程序已在所有环境中经过测试，包括预发布环境，您就可以将应用程序部署到生产环境——这意味着应用程序已上线并准备好供使用！

质量保证 (QA) 环境用于测试应用程序是否满足客户期望。质量保证环境是进行所有 QA 测试的地方。

### 版本控制与变更管理

拥有开发团队创建应用程序的大型组织将受益于使用版本控制功能，这些功能标识开发人员正在处理的应用程序版本。这是通过版本号或修订号来完成的。版本号可帮助您跟踪哪些文件代表了对文档所做的最近更改。版本控制软件可自动跟踪更改，并允许您在任何给定时间轻松恢复到之前的版本（如果您愿意）。

变更管理是您实施变更应遵循的流程。大多数公司都有变更管理策略，规定了如何进行变更。变更管理流程通常涉及变更规划、变更测试、变更应用，然后验证变更。变更管理还包括变更管理审批流程，即在实施变更之前必须获得批准，通常由 `变更咨询委员会 (CAB)` 批准。

### 供应与取消供应

在计划部署应用程序时，重要的是确保您已制定流程来供应将运行该应用程序的系统。`供应` 是设置新系统的过程。这是当今应用程序安全的关键部分，因为应用程序复杂且通常涉及使用多台服务器。您可能需要供应一台应用程序服务器、一台 Web 服务器和一台数据库服务器来部署应用程序。请确保供应系统以支持应用程序，但同时要确保遵循安全最佳实践，例如加固系统。供应的目标是确保系统合规，从而减少遭受攻击的漏洞。作为供应流程的一部分，您将授予用户对应用程序的访问权限。

`取消供应` 系统是将系统从应用程序环境中移除的过程。在取消供应应用程序或系统时，您首先会更改访问控制，以确保用户无法访问该系统或应用程序。重要的是要注意，如果您不取消供应（或移除）网络中的旧系统，它们最终可能无法打补丁，这会使这些系统容易受到攻击。

另一个例子是取消供应离职员工的用户账户。作为离职流程的一部分，您应该取消供应离职员工使用的账户，并确保他们不再有权访问这些系统。

### 完整性度量

完整性度量是一种用于验证文件是否已被系统上的软件修改的技术。完整性度量系统将关键操作系统文件的文件哈希存储在一个中央列表中，以便稍后可以通过将每个文件的当前文件哈希与文件哈希列表进行比较来验证。

## 安全编码技术

开发安全代码的两个重要部分是编写良好的异常处理例程和验证传递给应用程序的所有数据。

### 适当的错误处理

当应用程序开发人员创建应用程序时，他们有时无法预见不同情况下可能发生的错误。例如，创建“文件打开”对话框时的一个常见错误是，未计划用户在系统中未放置 DVD 时选择从 DVD 设备打开文件。这通常会导致 `运行时错误`——即直到应用程序运行时才会发生的错误——这意味着开发人员在创建应用程序时没有任何迹象表明该错误会存在。

运行时错误会发生，因为开发人员无法强制某人在浏览该资源之前将 DVD 放入 DVD 托架。因此开发人员必须做的是捕获此时发生的错误。`捕获` 错误意味着错误不会实际发生，而是程序员拦截该错误并显示友好的警告消息或采取某种纠正措施，而不是让应用程序崩溃（运行时错误会导致应用程序崩溃）。

异常处理是一种更高级的错误处理方法。`异常` 是运行时错误的一个花哨术语，诸如 .NET 或 Java 开发人员之类的程序员将实现异常处理代码。异常处理代码使用所谓的 `try/catch` 块——意思是“尝试这段代码并捕获任何错误”。以下代码是 `try/catch` 块的示例：

### 适当的输入验证

开发人员需要遵循这样一个理念：当有人将信息输入应用程序并单击“保存”、“查找”或“执行”等按钮时，开发人员必须在应用程序的某处使用该输入之前对其进行验证。`验证输入` 意味着开发人员检查以确保用户键入应用程序的信息对于预期的输入类型是合适的。任何未通过验证测试的输入都应被丢弃且不予处理。

![Image](img/exam.jpg)

**针对 Security+ 考试，请记住安全的内部应用程序必须从开发人员验证输入开始。您肯定会在 Security+ 考试中看到关于输入验证的问题！**

例如，在应用程序的登录屏幕上，用户需要键入用户名和密码。用户名和密码在大多数情况下是包含少于 14 个字符的短单词。程序员应该测试此输入，并确保用户名不超过 14 个字符，密码也不超过 14 个字符。此外，密码中没有空格，因此程序员应检查空格是否被用作字符之一——如果是，则应取消处理该信息，因为它可能是恶意的。要注意的其他字符示例包括破折号和撇号。它们通常不用于密码，但黑客会将它们输入登录屏幕以操纵软件的执行方式。
