
# 作为基于键的连接依赖示例

`Employee(empNr, birthdate, gender)` 等价于投影 `Emp1(empNr, birthdate); Emp2(empNr, gender)` 的连接。原表以及两个较小的表都处于 5NF。因为如果关系模式的表模式都处于某个范式，则该关系模式处于该范式，所以仅包含 Emp1 和 Emp2 表的关系模式是一个 5NF 模式。这说明 5NF 本身并不保证模式在表数量上是最小的。

非基于键的非平凡连接依赖很少见，因此 4NF 表几乎总是也处于 5NF。5NF 检验的底层理论包含在 CSDP 步骤 4 的投影-连接检查中，因此我们在此仅作简要讨论。一个用于讨论该概念的经典示例呈现在图 14.69(a) 的 `SellsFor` 表中。提供了一个小样本填充以表明唯一的唯一性约束是最弱的可能约束（请自行验证）。

![图 14.69 (a) 这是一个 5NF 表吗？ (b) 映射到模式 (c) 的可能 ORM 模式。](img/f14-69-9780443237904.jpg)

图 14.69 (a) 这是一个 5NF 表吗？ (b) 映射到模式 (c) 的可能 ORM 模式。

从概念上讲，这种三元事实类型可表示为：代理人为公司销售车型。三个二元投影背后的事实类型可表示为：代理人销售车型；代理人代表公司；公司制造车型。任何将此三元事实类型拆分为*两个*二元事实类型的尝试都会导致信息丢失。例如，从“Smith 是 Foord 的代表”以及“Foord 制造四轮驱动车 (4WD)”这两个事实中，并不能推断出“Smith 销售 4WD”。

然而，`SellsFor` 表的数据内容确实等于这三个二元投影的连接（请自行验证）。因此，我们可以在不丢失信息的情况下，将这个特定的表数据内容拆分为三个二元表数据内容。

但由于数据库内容是持续更新的，如果我们要将表模式拆分为三个二元表模式，我们需要知道这种连接依赖适用于所有可能的完整数据内容。换句话说，该样本数据内容在这方面是否具有代表性？如果是，则图 14.69(b) 中所示的推导规则适用。

检查这是否为实际业务规则的唯一方法是询问领域专家。假设它*不是*一条规则。例如，现在可以仅删除图 14.69(b) 中 `SellsFor` 表的第一行。请自行检查，如果该规则适用，则应拒绝此删除操作。在这种情况下，该三元事实类型是基本的，应保持原样。如果推导规则不适用，则 `SellsFor` 表*模式*已经是 5NF。

如果推导规则*确实*适用，如图 14.69(b) 所示，则需要强制执行此规则，但 `SellsFor` 三元表中的键约束无法做到这一点（例如，它允许删除第一行）。为避免此问题，应将 4NF 三元表拆分为三个 5NF 二元表，如图 14.69(c) 所示。如果 ORM 模式中的某些角色是强制的，则需要添加一些表间约束。原始三元表也可以定义为从新表连接派生出的视图。

有人认为（例如 Kent 认为），当图 14.69(a) 中的 `SellsFor` 等关系模式是基本的时，存在一种“不可避免的冗余”。例如，“代理人 ‘Jones E’ 销售轿车”这一“事实”在行 1 和行 3 中重复出现。然而，这种“冗余”是无害的，因为它是派生的而非存储的。虽然元组（“Jones E”，“轿车”）被存储了两次，但“代理人 ‘Jones E’ 销售轿车”这一事实只能通过推导规则“代理人销售车型 **当且仅当** 代理人为公司销售车型”来获得。

迄今讨论的七种范式是严格有序的。每种高级范式都满足低级范式。回顾一下，“⊂”表示“是……的真子集”。设“5NF-rels”表示所有第五范式关系的集合，以此类推。严格排序现可列出如下（按范式程度递减顺序）：

*   5NF-rels ⊂ 4NF-rels ⊂ BCNF-rels ⊂ EKNF-rels ⊂ 3NF-rels ⊂ 2NF-rels ⊂ 1NF-rels

本质上，通过 5NF 的规范化通过确保三种依赖（函数依赖 FD、多值依赖 MVD 和连接依赖 JD）将由键约束（即每个表内的唯一性约束）自动强制执行，从而简化了表更新。FD 是 MVD 的特例，而 MVD 又是 JD 的特例。正如 Fagin 所指出的，BCNF 确保所有 FD 由键约束蕴含，4NF 确保所有 MVD 由键约束蕴含，而 5NF 确保所有 JD 由键约束蕴含。

# 域键范式 (DKNF)

我们接下来要考虑的范式是**域键范式**（**DKNF**），由 Fagin (1981) 提出。当且仅当表模式的所有约束都可表示为域依赖或键依赖时，该表模式即属于 DKNF。域依赖为给定属性指定一组可能的值。这基本上是为属性声明一种数据类型（例如 `varchar(20)`）或值约束（例如 {"M", "F"}）。键依赖是跨越表模式中一个或多个属性的唯一性约束。如果所有域均为无限域，则任何 DKNF 表模式也属于 5NF。

要使关系数据库模式符合 DKNF，其每个表模式都应符合 DKNF，并且不应存在表间约束，或仅存在易于强制执行的“简单”表间约束，例如包含依赖（子集约束）。

DKNF 设计易于理解，其约束通常可由 DBMS 高效强制执行。遗憾的是，现实并非如此简单。实际应用中常出现许多其他类型的约束，即使将其纳入关系模式会违反 DKNF，也仍需强制执行。

作为一个简单示例，图 14.70 显示了一个概念模式及其关系映射。表模式 `Person` 不符合 DKNF，因为它包含除域依赖和键依赖之外的两个约束。首先，从 `manager` 到 `personNr` 的子集约束是一个表内包含依赖。其次，“`personNr ≠ manager`”约束强制汇报关联的非自反性。由于其 `Person` 模式不符合 DKNF，且存在排除约束（没有人既撰写又审阅同一本书），因此整体模式不符合 DKNF。

![图 14.70 关系模式不符合 DKNF。](img/f14-70-9780443237904.jpg)

图 14.70 关系模式不符合 DKNF。

尽管图 14.70 中的关系模式不符合 DKNF，但其每个表模式均符合 5NF。这些额外约束不包含在 5NF 的定义中，因此不违反 5NF。如果使用我们的 `Rmap` 过程进行映射，任何断言事实类型均为原子的有效 ORM 模式都将生成一个 5NF 关系模式。

正如该示例所示，ORM 通过支持其他类型的约束，实际上超越了 5NF。尽管这种对约束表达和映射的丰富支持可能导致违反 DKNF 的模式，但这是优势而非劣势，因为捕获相关业务规则需要这种违反。

# 第六范式 (6NF)

我们讨论的最后一个范式是**第六范式**（**6NF**），它由 Chris Date 等人在 20 世纪 90 年代末提出，主要是为了简化时态数据库的实现。当且仅当一个关系模式不满足任何非平凡连接依赖时，它才符合 6NF。6NF 表模式自动符合 5NF 和 DKNF。

直观上，6NF 表模式包含主键和至多一个其他属性。因此，6NF 表的每一行仅包含一个原子事实。回想一下，原子事实要么是基本事实，要么是存在性事实。

例如，5NF 表模式 `Person(name, gender, height, weight, maritalStatus)` 可以分解为以下 6NF 表模式：`Person(name, gender)`；`Person(name, height)`；`Person(name, weight)`；`Person(name, maritalStatus)`。这使得存储时态信息变得更加容易，例如一个人具有特定身高、特定体重或特定婚姻状况的时间段。

作为一个平凡的例子，表模式 `Person(name)` 也符合 6NF，因为它的每一行仅包含一个存在性事实（例如，存在一个名为“Joseph Robinette Biden Jr.”的人）。

可以发明更多的范式来满足更多的约束，但最好还是专注于在概念层面清理设计缺陷，因为在那里人类可以更容易地利用他们对 UoD 的语义理解。

正如下一节所讨论的，有时有必要对关系模式进行反规范化以获得可接受的性能。这对于当前示例是一个可能的选择。请注意，表间约束的实施成本很高，不像键约束那样。例如，实施外部唯一性约束实际上要求每次向任一表插入一行时都进行表连接。此外，列出谁教谁什么的查询也需要表连接。

通过将图 14.71(a) 中的原始 ORM 模式映射得到图 14.74(a) 所示的关系模式，可以获得另一种设计。配对子集约束暗示了三元事实类型在 (lecturer, student) 上的另一个键约束，因此可以省略该约束。尽管三元事实类型被反规范化了，但它是安全的，因为其有问题的 FD 由配对子集约束和二元事实类型中的键约束强制执行。我们现在可以列出谁教谁什么，而无需表连接。如果这是应用程序的重点查询，则可能首选此设计。

# 反规范化与底层优化

如果规范化的双表设计性能不佳，我们可能会将设计反规范化为单表，即它们的自然连接，如图 14.74(b)所示。将图 14.71(a)的子集约束替换为等值约束后，分配事实可以通过在三元事实类型的前两个角色上投影来检索，但分配二元事实类型上的唯一性约束仍需处理。在反规范化的三元事实类型中，该约束无法作为唯一性约束来强制执行，因此需要一个单独的约束来强制执行函数依赖 `lecturer → course`。只要强制执行此额外约束（例如，作为 SQL 中的用户定义约束），单表设计就是安全的。如前所述，备选键约束是隐含的，因此省略了。

关系语言的进步使得指定非基于键的约束（如函数依赖）变得更加容易。然而，在选择最终的关系设计时，必须考虑强制执行此类约束的开销。一般来说，我们应该首先尝试完全规范化的设计，在相关的地方使用概念优化来改进它。如果性能仍然不可接受，受控反规范化是一种选择。

# 14.7 反规范化与底层优化

应用概念优化过程并遵循 `Rmap` 过程可确保一个无冗余的关系模式，其效率应当相当合理。要测试此逻辑模式的性能，应使用真实的数据量将其作为内部模式在目标 DBMS 上实现。在此阶段，通常应为所有主键和外键以及在聚焦查询中起重要作用的任何其他列创建 `indexes`（索引）。

对于大表，索引可以显著提高性能，因为它们通常可以部分或整体地加载到主存中，且其条目被排序进允许快速检索的结构中（例如，二叉树）。有时，索引可能会减慢更新速度，因为当相关更改发生在基表上时，索引必须更新；但即使有更新，索引也能加快许多种约束检查（例如，确保键的唯一性）。索引有多种类型（例如，聚簇、非聚簇），且索引方案在不同供应商之间往往有所不同。

为了加速或促进某些复杂查询，可以使用 `working tables`（工作表，预先声明或临时创建均可）（例如，用于保存中间结果，这些结果可能通过连接多个表获得，在基础值更新前可能被重用多次）。预先声明的工作表在会话开始时填充，用于保存该会话中可视为稳定的中间结果；这些临时表在会话结束时删除。临时创建的工作表类似，但在会话期间创建，并且一旦不再需要，可在会话结束前随时删除。

另一个流行的选项是使用 `materialized views`（物化视图）——这些视图根据其定义自动填充数据，并在其基表更新时根据需要自动更新。对物化视图的支持因 DBMS 而异；在 SQL Server 中，它们称为索引视图。

不同的 DBMS 提供其他调整内部模式的方法（例如，聚簇存储相关数据）。此外，由于没有查询优化器是完美的，实际查询本身的形式也会影响（有时严重影响）性能。对于某些较旧的优化器，仅更改连接条件中列出表的顺序就可能导致响应时间发生显著变化。在大多数情况下，你可以使用 DBMS 提供的性能调优辅助来比较执行计划并选择最佳方案。
