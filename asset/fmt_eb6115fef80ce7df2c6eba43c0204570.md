
```go
// writeString writes s to w.
// If w has a WriteString method, it is invoked instead of w.Write.
func writeString(w io.Writer, s string) (n int, err error) {
    type stringWriter interface {
        WriteString(string) (n int, err error)
    }
    if sw, ok := w.(stringWriter); ok {
        return sw.WriteString(s) // avoid a copy
    }
    return w.Write([]byte(s)) // allocate temporary copy
}

func writeHeader(w io.Writer, contentType string) error {
    if _, err := writeString(w, "Content-Type: "); err != nil {
        return err
    }
    if _, err := writeString(w, contentType); err != nil {
        return err
    }
    // ...
}
```

为了避免重复代码，我们将检查移到了工具函数 `writeString` 中，但它非常有用，以至于标准库将其作为 `io.WriteString` 提供。这是向 `io.Writer` 写入字符串的推荐方式。

这个例子有趣的是，没有标准接口定义 `WriteString` 方法并指定其所需行为。此外，具体类型是否满足 `stringWriter` 接口仅由其方法决定，而不由它与接口类型之间的任何声明关系决定。这意味着上述技术依赖于这样一个假设：*如果*一个类型满足下面的接口，*那么* `WriteString(s)` 必须与 `Write([]byte(s))` 具有相同的效果。

点击此处查看代码图片

```go
interface {
    io.Writer
    WriteString(s string) (n int, err error)
}
```

虽然 `io.WriteString` 记录了它的假设，但调用它的函数极少会记录它们也做了同样的假设。为特定类型定义方法被视为对某种行为契约的隐式同意。Go 语言的新手，特别是那些有强类型语言背景的人，可能会觉得这种缺乏显式意图的做法令人不安，但在实践中这很少是个问题。除了空接口 `interface{}` 之外，接口类型极少会因无意的巧合而被满足。

上面的 `writeString` 函数使用类型断言来查看通用接口类型的值是否也满足更具体的接口类型，如果满足，则使用该具体接口的行为。无论被查询的接口是标准的（如 `io.ReadWriter`）还是用户定义的（如 `stringWriter`），这种技术都很有用。

这也是 `fmt.Fprintf` 区分满足 `error` 或 `fmt.Stringer` 的值与所有其他值的方式。在 `fmt.Fprintf` 内部，有一个步骤将单个操作数转换为字符串，大致如下：

点击此处查看代码图片

```go
package fmt

func formatOneValue(x interface{}) string {
    if err, ok := x.(error); ok {
        return err.Error()
    }
    if str, ok := x.(Stringer); ok {
        return str.String()
    }
    // ...所有其他类型...
}
```

如果 `x` 满足这两个接口中的任意一个，那就决定了该值的格式化方式。如果不满足，默认情况会使用反射或多或少统一地处理所有其他类型；我们将在 第 12 章 了解具体如何做。

同样，这假设任何拥有 `String` 方法的类型都满足 `fmt.Stringer` 的行为契约，即返回一个适合打印的字符串。

## 7.13 类型开关

接口有两种截然不同的使用风格。第一种风格，以 `io.Reader`、`io.Writer`、`fmt.Stringer`、`sort.Interface`、`http.Handler` 和 `error` 为例，接口的方法表达了满足该接口的具体类型之间的相似性，但隐藏了这些具体类型的表示细节和内在操作。重点在于方法，而非具体类型。

第二种风格利用了接口值可以容纳多种具体类型值的能力，将接口视为这些类型的*联合*。使用类型断言在这些类型中动态区分，并区别对待每种情况。在这种风格中，重点在于满足接口的具体类型，而非接口的方法（如果确实有方法的话），并且不隐藏信息。我们将这种使用方式的接口描述为*可辨识联合*。

如果你熟悉面向对象编程，你可能会将这两种风格分别认作*子类型多态*和*特设多态*，但你不必记住这些术语。在本章剩余部分，我们将展示第二种风格的示例。

Go 语言用于查询 SQL 数据库的 API，与其他语言一样，让我们能够清晰地将查询的固定部分与可变部分分离开来。一个示例客户端可能如下所示：

点击此处查看代码图片

```go
import "database/sql"

func listTracks(db sql.DB, artist string, minYear, maxYear int) {
    result, err := db.Exec(
        "SELECT * FROM tracks WHERE artist = ? AND ? <= year AND year <= ?",
        artist, minYear, maxYear)
    // ...
}
```

`Exec` 方法会用表示相应参数值的 SQL 字面量替换查询字符串中的每个 `'?'`，参数值可以是布尔值、数字、字符串或 `nil`。以这种方式构建查询有助于避免 SQL 注入攻击，这种攻击利用输入数据引用不当，让攻击者控制查询。在 `Exec` 内部，我们可能会找到一个如下所示的函数，它将每个参数值转换为其 SQL 字面量表示法。

点击此处查看代码图片

```go
func sqlQuote(x interface{}) string {
    if x == nil {
        return "NULL"
    } else if _, ok := x.(int); ok {
        return fmt.Sprintf("%d", x)
    } else if _, ok := x.(uint); ok {
        return fmt.Sprintf("%d", x)
    } else if b, ok := x.(bool); ok {
        if b {
            return "TRUE"
        }
        return "FALSE"
    } else if s, ok := x.(string); ok {
        return sqlQuoteString(s) // (未显示)
    } else {
        panic(fmt.Sprintf("unexpected type %T: %v", x, x))
    }
}
```

`switch` 语句简化了执行一系列值相等性测试的 `if`-`else` 链。类似地，*类型开关*语句简化了类型断言的 `if`-`else` 链。

在最简单的形式中，类型开关看起来像一条普通的 switch 语句，其操作数是 `x.(type)`——这就是字面上的 `type` 关键字——并且每个 case 有一个或多个类型。类型开关基于接口值的动态类型实现多路分支。`nil` case 在 `x == nil` 时匹配，`default` case 在没有其他 case 匹配时匹配。`sqlQuote` 的类型开关将包含以下 case：

```go
switch x.(type) {
case nil:       // ...
case int, uint: // ...
case bool:      // ...
case string:    // ...
default:        // ...
}
```

与普通的 switch 语句一样（§1.8），case 按顺序考虑，当找到匹配时，执行该 case 的主体。当一个或多个 case 类型是接口时，case 顺序变得重要，因为此时存在两个 case 都匹配的可能性。`default` case 相对于其他 case 的位置无关紧要。不允许使用 `fallthrough`。

注意在原始函数中，`bool` 和 `string` case 的逻辑需要访问类型断言提取出的值。由于这很典型，类型开关语句有一种扩展形式，它将提取的值绑定到每个 case 内的一个新变量：

点击此处查看代码图片

```go
switch x := x.(type) { /* ... */ }
```

这里我们也将新变量命名为 `x`；与类型断言一样，重用变量名很常见。像 `switch` 语句一样，类型开关隐式创建一个词法块，因此名为 `x` 的新变量声明不会与外部块中的变量 `x` 冲突。每个 `case` 也隐式创建一个单独的词法块。

使用类型开关的扩展形式重写 `sqlQuote` 使其清晰得多：

点击此处查看代码图片

```go
func sqlQuote(x interface{}) string {
    switch x := x.(type) {
    case nil:
        return "NULL"
    case int, uint:
        return fmt.Sprintf("%d", x) // x 在这里的类型是 interface{}。
    case bool:
        if x {
            return "TRUE"
        }
        return "FALSE"
    case string:
        return sqlQuoteString(x) // (未显示)
    default:
        panic(fmt.Sprintf("unexpected type %T: %v", x, x))
    }
}
```

在这个版本中，在每个单类型 case 的块内，变量 `x` 具有与该 case 相同的类型。例如，`x` 在 `bool` case 中类型为 `bool`，在 `string` case 中类型为 `string`。在所有其他情况下，`x` 具有 `switch` 操作数的（接口）类型，在本例中为 `interface{}`。当多个 case 需要相同的动作时，如 `int` 和 `uint`，类型开关使组合它们变得容易。

虽然 `sqlQuote` 接受任意类型的参数，但只有当参数的类型与类型开关中的某个 case 匹配时，函数才会正常完成；否则它会因“unexpected type”（意外的类型）而 panic。虽然 `x` 的类型是 `interface{}`，但我们将其视为 `int`、`uint`、`bool`、`string` 和 `nil` 的*可辨识联合*。

## 7.14 示例：基于 Token 的 XML 解码

第 4.5 节 展示了如何使用 `encoding/json` 包中的 `Marshal` 和 `Unmarshal` 函数将 JSON 文档解码为 Go 数据结构。`encoding/xml` 包提供了类似的 API。当我们想要构建文档树的表示时，这种方法很方便，但对于许多程序来说这是不必要的。`encoding/xml` 包还提供了一个用于解码 XML 的低级*基于 Token* 的 API。

在基于 Token 的风格中，解析器消费输入并产生一个 Token 流，主要分为四种——`StartElement`、`EndElement`、`CharData` 和 `Comment`——每种都是 `encoding/xml` 包中的一个具体类型。每次调用 `(*xml.Decoder).Token` 都会返回一个 Token。

API 的相关部分如下所示：

```go
package xml

type Name struct {
    Local string // 例如 "Title" 或 "id"
}

type Attr struct { // 例如 name="value"
    Name  Name
    Value string
}

// Token 包含 StartElement、EndElement、CharData、
// 和 Comment，以及一些晦涩的类型（未显示）。
type Token interface{}
type StartElement struct { // 例如 <name>
    Name Name
    Attr []Attr
}
type EndElement struct { Name Name } // 例如 </name>
type CharData []byte                 // 例如 <p>CharData</p>
type Comment []byte                  // 例如 <!-- Comment -->

type Decoder struct{ /* ... */ }

func NewDecoder(io.Reader) *Decoder
func (*Decoder) Token() (Token, error) // 返回序列中的下一个 Token
```

`Token` 接口没有任何方法，也是一个判别联合的例子。像 `io.Reader` 这样的传统接口的目的是隐藏满足它的具体类型的细节，以便可以创建新的实现；每个具体类型都被统一对待。相比之下，满足判别联合的具体类型集合是由设计固定并暴露的，而不是隐藏的。判别联合类型只有很少的方法；操作它们的函数被表示为一组使用类型开关的情况，每种情况有不同的逻辑。

下面的 `xmlselect` 程序提取并打印 XML 文档树中特定元素之下的文本。使用上述 API，它可以在一次遍历输入的过程中完成任务，而无需实例化树。

```go
// Xmlselect 打印 XML 文档中选定元素的文本。
package main

import (
    "encoding/xml"
    "fmt"
    "io"
    "os"
    "strings"
)

func main() {
    dec := xml.NewDecoder(os.Stdin)
    var stack []string // 元素名称栈
    for {
        tok, err := dec.Token()
        if err == io.EOF {
            break
        } else if err != nil {
            fmt.Fprintf(os.Stderr, "xmlselect: %v\n", err)
            os.Exit(1)
        }
        switch tok := tok.(type) {
        case xml.StartElement:
            stack = append(stack, tok.Name.Local) // 入栈
        case xml.EndElement:
            stack = stack[:len(stack)-1] // 出栈
        case xml.CharData:
            if containsAll(stack, os.Args[1:]) {
                fmt.Printf("%s: %s\n", strings.Join(stack, " "), tok)
            }
        }
    }
}

// containsAll 报告 x 是否按顺序包含 y 的元素。
func containsAll(x, y []string) bool {
    for len(y) <= len(x) {
        if len(y) == 0 {
            return true
        }
        if x[0] == y[0] {
            y = y[1:]
        }
        x = x[1:]
    }
    return false
}
```

`main` 中的循环每遇到一个 `StartElement`，就将元素名称压入栈，每遇到一个 `EndElement` 就从栈中弹出名称。API 保证 `StartElement` 和 `EndElement` Token 的序列将正确匹配，即使在格式不良的文档中也是如此。`Comment` 被忽略。当 `xmlselect` 遇到 `CharData` 时，只有当栈包含命令行参数指定的所有元素且顺序一致时，才会打印该文本。
