
最后，Kerberos 旨在缓解恶意网络：嗅探器将几乎没有价值。Kerberos 无法缓解恶意本地主机：明文密钥可能存在于内存或缓存中。恶意的本地用户或进程可能能够窃取本地缓存的凭据。

### Kerberos 攻击利用

Kerberos 作为许多企业环境中的主要凭据守门人，意味着针对该生态系统的攻击无处不在且应在预料之中。针对 Kerberos 最常见的攻击涉及对手仅仅获取并冒充已认证的安全主体。严格来说，这并不真正涉及对 Kerberos 的利用，而只是利用账户之前颁发的服务票据。在 Kerberos 生态系统中，利用用户当前已验证的服务票据将允许对手访问用户已在访问的资源。

也存在更明显的以 Kerberos 为中心的攻击模式。MITRE 的 ATT&CK® 企业矩阵包含技术 1558 (T1558)：窃取或伪造 Kerberos 票据，这还强调了特定的攻击模式，如黄金票据、白银票据和 Kerberoasting [\[13\]](#Ch006_295-335_B9780443187346000052.xhtml#bb98)。在每种情况下，总体目标都是让对手破坏 Kerberos 认证，以合法用户的身份出现，这可以实现对手的横向移动，并允许在受害环境中进行一般性访问。

## 访问控制协议和框架

集中式和分布式模型都可能支持远程用户向本地系统进行身份验证。许多协议和框架可用于支持这一需求，包括 `RADIUS`、`Diameter`、`TACACS/TACACS+`、`PAP` 和 `CHAP`，以及 Microsoft Active Directory。

### RADIUS

*远程认证拨号用户服务* 协议是一种第三方认证系统。`RADIUS` 在 RFC 2865 和 2866 中有描述，并使用用户数据报协议（`UDP`）端口 1812（认证）和 1813（计费）。`RADIUS` 以前使用（非官方分配的）端口 1645 和 1646 用于相同的目的；某些实现仍继续使用这些端口。

`RADIUS` 被视为一个“AAA”系统，由三个组件组成：认证、授权和计费。它根据认证数据库验证主体的凭据。它通过允许特定用户访问特定数据对象来授权用户。它通过为每个建立的 `RADIUS` 连接创建日志条目来记录每个数据会话。

`RADIUS` 请求和响应数据以属性值对（`AVPs`）的形式承载。根据 RFC 2865 ([`datatracker.ietf.org/doc/html/rfc2865`](https://datatracker.ietf.org/doc/html/rfc2865))，`RADIUS` 支持以下代码：

*   `Access-Request`
*   `Access-Accept`
*   `Access-Reject`
*   `Accounting-Request`
*   `Accounting-Response`
*   `Access-Challenge`
*   `Status-Server`（实验性）
*   `Status-Client`（实验性） [\[14\]](#Ch006_295-335_B9780443187346000052.xhtml#bb0065)

### Diameter

*Diameter* 是 `RADIUS` 的继任者，旨在提供改进的认证、授权和计费（`AAA`）框架。`RADIUS` 提供的问责功能有限，且在灵活性、可扩展性、可靠性和安全性方面存在问题。`Diameter` 也使用属性值对，但支持更多：`RADIUS` 对 `AVP` 字段使用 8 位（允许总共 256 个可能的 `AVPs`），而 `Diameter` 对 `AVP` 字段使用 32 位（允许数十亿个潜在的 `AVPs`）。这使得 `Diameter` 更加灵活，例如允许支持移动远程用户。

`Diameter` 使用单个服务器来管理许多服务的策略，而 `RADIUS` 则需要许多服务器来处理所有安全连接协议。与 `RADIUS` 一样，`Diameter` 提供 `AAA` 功能，但此外，它通过使用传输控制协议（`TCP`）变得更加可靠。`Diameter` 在 RFC 6733 ([`datatracker.ietf.org/doc/html/rfc6733`](https://datatracker.ietf.org/doc/html/rfc6733)) 中有描述。

### TACACS 和 TACACS+

`终端访问控制器访问控制系统 (TACACS)` 是一种集中式访问控制系统，要求用户发送 ID 和静态（可重用）密码进行身份验证。TACACS 使用 UDP 端口 49（也可能使用 TCP）。可重用密码是一种漏洞：改进的 `TACACS+` 通过允许双因素强身份验证提供了更好的密码保护。

重要的是要注意，TACACS+ 不与 TACACS 向后兼容。TACACS+ 使用 TCP 端口 49 与 TACACS+ 服务器进行身份验证。实际的身份验证功能与 RADIUS 非常相似，但存在一些关键差异。

RADIUS 仅加密密码（用户名等其他数据保持未加密状态）。而 TACACS+ 则加密 TACACS+ 头部以下的所有数据。这是对 RADIUS 的改进，安全性更高。

### PAP 和 CHAP

`密码认证协议 (PAP)` 由 RFC 1334 定义（[`datatracker.ietf.org/doc/html/rfc1334#section-22`](https://datatracker.ietf.org/doc/html/rfc1334#section-22)），被称为“非强身份验证方法” [\[15\]](#Ch006_295-335_B9780443187346000052.xhtml#bb0070)。用户输入密码，然后以明文形式通过网络发送。当 PAP 服务器接收到密码后，会对其进行认证和验证。嗅探网络可能会泄露明文密码。嗅探是指监控网络通信并捕获原始 TCP/IP 流量。

`质询握手认证协议 (CHAP)` 由 RFC 1994 定义（[`datatracker.ietf.org/doc/html/rfc1994`](https://datatracker.ietf.org/doc/html/rfc1994)），可防范重放攻击。它使用一个中心位置对远程用户发起质询。正如 RFC 中所述，“CHAP 依赖于仅认证方和对等方知道的‘密钥’。密钥不会在链路上发送。虽然认证仅是单向的，但通过双向协商 CHAP，同一组密钥可轻松用于双向认证” [\[16\]](#Ch006_295-335_B9780443187346000052.xhtml#bb0075)。

与 PAP 相比，使用 CHAP 的优势在于质询和响应过程中使用共享密钥提供的额外安全性：查看整个质询/响应过程的嗅探器将无法确定共享密钥。

### Microsoft Active Directory 域

Microsoft Windows Active Directory 使用 `域` 的概念作为控制访问的主要手段。出于身份验证目的，Microsoft 基于 RFC 1510（Kerberos 认证协议）建立其信任关系认证，并自 Windows 2000 起已集成到 Microsoft Windows 操作系统中。每个域都有独立的身份验证过程和空间。每个域可能包含不同的用户、不同的网络资产和数据对象。由于 Microsoft Windows 也使用组的概念来控制用户对数据对象的访问，因此每个组可能被授予对系统内各个域的访问权限。如果在域之间创建了双向信任，则属于任一域的组均可访问对方域中的数据对象。

正如 Microsoft 所述，“特定信任如何传递身份验证请求取决于其配置方式；信任关系可以是单向的，提供从受信域到信任域中资源的访问，也可以是双向的，提供从每个域到另一个域中资源的访问。信任也可以是非传递的，即信任仅存在于两个信任伙伴域之间；或是传递的，即信任自动扩展到任一伙伴信任的任何其他域”[\[17\]](#Ch006_295-335_B9780443187346000052.xhtml#bb0080)。

> **考试警告**
>
> Microsoft 信任关系分为两类：非传递性和传递性。非传递性信任仅存在于两个信任伙伴之间。传递性信任存在于两个伙伴及其所有伙伴域之间。例如：如果 A 信任 B，在传递性信任中，A 将信任 B 以及 B 的所有信任伙伴。

## 访问控制模型

现在我们已经回顾了基石般的访问控制概念，可以讨论不同的访问控制模型了：主要模型包括 `自主访问控制 (DAC)`、`强制访问控制 (MAC)` 和 `基于角色的访问控制 (RBAC)`，以及最近定义的 `基于属性的访问控制 (ABAC)` 和 `基于风险的访问控制`。

不要认为某个模型优于另一个模型。相反，请记住每个模型都用于特定的信息安全目的。例如，如果你有一个需要立即更新数据的天气网站，但信息本身可能包含微小错误（天气数据以不可靠著称），其数据完整性模型将不同于包含核发射代码的绝密数据库（核发射代码数据**既**必须可靠，**又**必须高度机密）。

### 自主访问控制 (DAC)

`自主访问控制 (DAC)` 赋予主体对其创建或被授权访问的对象的完全控制权，包括与其他主体共享对象。主体被赋予权力并控制其数据。标准的 UNIX 和 Windows 操作系统对文件系统使用 DAC：主体可以授予其他主体访问其文件的权限、更改其属性、修改或删除它们。

如果主体犯了错误，例如将错误的文件作为附件发送到公共邮件列表，可能导致机密性丧失。错误和恶意行为也可能导致数据完整性或可用性丧失。

### 强制访问控制 (MAC)

`强制访问控制 (MAC)` 是基于主体的许可级别和对象的标签的系统强制访问控制。主体和对象分别具有许可级别和标签，如机密、秘密和绝密。仅当主体的许可级别等于或高于对象的标签时，主体才能访问该对象。主体无法与缺乏适当许可的其他主体共享对象，也无法将对象“写入”较低的分类级别（如从绝密到秘密）。MAC 系统通常专注于保护数据的机密性。

强制访问控制的实施成本高昂且困难，尤其是在尝试在同一个互联 IT 系统中分离不同的机密性级别（安全域）时。对用户进行许可审查是一个昂贵的过程；详见第 3 章“许可”部分，领域 2：资产安全。具体的 MAC 模型（如 Bell-LaPadula）将在第 4 章讨论，领域 3：安全架构与工程。

### 基于角色的访问控制

`基于角色的访问控制 (RBAC)` 根据主体的角色定义如何在系统上访问信息。角色可以是护士、备份管理员、服务台技术人员等。主体被分组为角色，每个定义的角色基于角色而非个人拥有访问权限。

根据 NIST，RBAC 具有以下规则：

1.  **角色分配：** 仅当主体选择或被分配了角色时，才能执行事务。识别和认证过程（如登录）不被视为事务。系统上的所有其他用户活动均通过事务进行。因此，所有活跃用户都必须具有某个活跃角色。

2.  **角色授权：** 主体的活跃角色必须经主体授权。结合上述规则 (1)，此规则确保用户只能承担其被授权的角色。

3.  **事务授权：** 只有当事务通过主体的角色成员资格获得授权，并受限于可能应用于用户、角色和权限之间的任何约束时，主体才能执行该事务。结合（1）和（2），此规则确保用户只能执行其被授权执行的事务 [18]。

即使是强大的角色也有限制；例如，许多组织不允许系统管理员在使用管理员账户时浏览网页。这使得系统上的每个角色保持独立，并减少了更敏感账户的暴露风险。表 6.1 显示了基于用户在系统上的角色而具有不同数据访问权限的示例。

**表 6.1 RBAC**

| 角色 | 示例数据访问 |
| --- | --- |
| 基本用户 | 桌面应用程序：电子邮件、电子表格、网页访问 |
| 审计员 | 系统安全日志、认证服务器日志 |
| 网络工程师 | 路由器日志、防火墙日志、VPN 集中器日志 |

#### 基于任务的访问控制

*基于任务的访问控制*提供了一种与 RBAC 紧密相关的访问控制模型。基于任务的访问控制基于每个主体必须执行的任务，例如开具处方、从备份磁带恢复数据或打开服务台工单。它试图解决 RBAC 解决的同一个问题，但侧重于特定任务，而非角色。请注意，任务也可以作为一种属性，用于指导本章后面讨论的基于属性的访问控制（ABAC）。

### 基于规则的访问控制

正如预期的那样，*基于规则的访问控制*系统使用一系列定义好的规则、限制和过滤器来访问系统内的对象。规则采用“如果/那么”语句的形式。基于规则的访问控制设备的一个例子是代理防火墙，它仅允许用户使用预定义的已批准内容浏览网页（“如果用户被授权浏览网页，且该站点在批准列表中，则允许访问”）。其他站点被禁止，且此规则在所有经过认证的用户中强制执行。

### 基于属性的访问控制（ABAC）

基于属性的访问控制（ABAC）代表了一种促进现代信息系统访问控制的较新方法。在 ABAC 中，将审查主体和/或客体的属性，以确定其值是否满足授予或拒绝访问的预期要求。要评估的特定属性实际上可以是任何可以编码进 ABAC 生态系统的内容。ABAC 中常见的属性包括：是否采用了 MFA，以及最近一次满足 MFA 质询的时间；请求访问的位置（例如，本地部署与远程）；请求访问的系统（例如，公司拥有的笔记本电脑与员工自有的移动设备）；用于访问的接口（例如，API 与 Web 门户）。上述列表中的大多数属性都是面向主体的属性。基于对象的属性，例如正在被访问的内容类型，同样也可以在 ABAC 访问决策中发挥重要作用。

虽然绝非专门与云服务相关，但面向 ABAC 的方法在云服务中被广泛采用，作为一种现代且灵活的生态系统，与传统的 MAC、DAC 甚至 RBAC 生态系统相比，它能提供更动态的访问控制方法。

#### 基于内容和上下文的访问控制

基于内容和*上下文的访问控制*本身并非成熟的访问控制方法，但可以发挥纵深防御的支持作用。历史上，它们可能作为额外的控制被添加，通常添加到 DAC 系统中，但现在这些方法通常被用作 ABAC 生态系统中的重要属性。

*基于内容的访问控制*在身份识别和认证之外增加了额外标准：主体试图访问的实际内容。组织的所有员工可能都有权访问 HR 数据库以查看其累积的病假和休假时间。如果某员工试图访问 CIO 的 HR 记录内容，则会被拒绝访问。

基于上下文的访问控制在授予访问权限前应用额外的上下文。常用的上下文是时间。在身份识别和认证后，一名周一至周五上午 9 点至下午 5 点工作的服务台人员，将在周二中午获得访问权限。基于上下文的访问控制系统可能会在周日凌晨 1:00 拒绝访问（时间错误，因此上下文错误）。

### 基于风险的访问控制

尽管命名使基于风险的访问控制听起来相当笼统，但其现实影响却十分重大。经典的访问控制范式涉及确定是应授予还是拒绝主体对客体的访问。虽然这听起来很简单，但当前的威胁形势涉及对手以用户及其关联系统为目标，以获取对受损用户或系统可访问资源的访问权限。一个重要的访问控制问题变成了：寻求访问的主体是否实际上是已获得对该主体一定程度控制权的对手。

基于风险的访问控制的目标是在确定必要时和地点，采取动态或自适应的访问控制措施。基于风险的访问控制方法的两种表现形式包括自适应认证和逐级认证。这两种方法都涉及在特定情况下，要求在允许主体访问客体之前对其进行额外的审查。

> **考试警告**
>
> 在 CISSP® 考试中，RBAC 代表基于角色的访问控制。请小心不要将 RBAC 缩写与基于规则的访问控制或基于风险的访问控制混淆。在考试中，基于规则的访问控制和基于风险的访问控制将始终拼写全称。

#### 逐级认证

逐级认证要求用户在被允许继续访问先前定义为更敏感或关键的数据或功能之前，通过额外的验证。涉及逐级认证的常见场景是要求用户在被允许执行关键事务之前重新验证其 MFA。逐级认证可被视为一种基于风险的访问控制，因为它关注的是一旦被攻破将导致更重大影响的资产。

#### 自适应认证

自适应认证代表了一种不同的方法，同样具有基于风险的访问控制的特征。通过自适应认证，应用程序或信息系统识别出与主体相关的可疑行为或特征，并将在授予访问权限前要求进一步验证。例如，用户可能试图访问其从未访问过的数据，或从以前未见过的位置进行访问。这种与其正常配置文件的偏差可能会触发应用程序要求用户在提供所请求的访问权限前，再次成功通过 MFA 质询。

## 身份与访问配置生命周期

### 访问供应生命周期

一旦选择并部署了适当的访问控制模型，就必须维护并保障访问供应生命周期的安全。虽然许多组织遵循授予访问权限的最佳实践，但许多组织缺乏正式流程，以确保在员工和承包商在组织内部流动时，访问权限的整个生命周期始终保持安全。身份与访问生命周期包含诸如身份注册与审核、定义逻辑角色、安全地供应和取消供应账户及访问权限等考量因素。限制账户及其关联访问权限暴露的操作控制也同样相关，包括访问评审、即时供应和权限提升机制等组件。

始终将账户撤销作为访问供应生命周期中的必需步骤。此流程应与人力资源部门紧密协调，不仅要跟踪离职情况，还要跟踪组织内部的横向和纵向调动或晋升。此外，如前所述，不活跃账户应作为撤销目标。

#### 注册、审核与身份建立

当考虑对个人进行审核和验证时，许多安全专业人员在思维上会直接跳到认证环节，但逻辑上的前置步骤涉及一个健壮的身份识别组件流程。简单来说，在我们能够认证某个个体之前，我们需要实际了解并收集与该个体相关的信息。为此，在信息系统中建立身份涉及身份注册和审核的过程。

注册（也可称为入册）涉及在系统中请求或申请身份，并提供系统所需的、允许唯一识别的信息。一旦提供了必要的识别属性，就需要对这些属性进行验证。审核涉及对注册/入册过程中提供的属性进行验证和确证。将审核明确作为一个单独流程提出的原因之一，是因为某些场景在身份验证过程中会利用第三方处理器。身份审核验证过程的范围，与大多数事物一样，由风险管理原则决定。

#### 角色定义

组织及其信息系统会定期发生变化。随着组织内部新职能的定义，显然也将需要以定义角色的形式来表达这些职能的访问控制要求。然而，即使员工继续从事同一份工作，其职能随时间推移也可能发生重大变化。工作性质的变化同样可能导致访问控制系统中需要新的角色定义。前文讨论的基于角色的访问控制（RBAC）和利用角色作为属性的基于属性的访问控制实现的有效性，取决于定义清晰且被充分理解的角色。
