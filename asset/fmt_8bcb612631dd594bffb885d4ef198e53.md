
### 10.7.2 下载包

使用 `go` 工具时，包的导入路径不仅指示在本地工作区中何处可以找到它，还指示在互联网上何处可以找到它，以便 `go get` 能够检索和更新它。

`go get` 命令可以下载单个包，也可以使用 `...` 表示法下载整个子树或仓库，如前一节所示。该工具还会计算并下载初始包的所有依赖项，这就是为什么上一个示例中 `golang.org/x/net/html` 包会出现在工作区中的原因。

`go get` 下载包后，会构建它们，然后*安装*库和命令。我们将在下一节查看详细信息，但一个示例将展示该过程有多简单。下面的第一个命令获取 `golint` 工具，它用于检查 Go 源代码中的常见风格问题。第二个命令在 `gopl.io/ch2/popcount`（来自第 2.6.2 节）上运行 `golint`。它有帮助地报告我们忘记为包编写文档注释：

```
$ go get github.com/golang/lint/golint

$ $GOPATH/bin/golint gopl.io/ch2/popcount

src/gopl.io/ch2/popcount/main.go:1:1:
  package comment should be of the form "Package popcount ..."
```

`go get` 命令支持 GitHub、Bitbucket 和 Launchpad 等流行的代码托管网站，并能向其版本控制系统发出适当的请求。对于不太知名的网站，你可能必须在导入路径中指明使用哪种版本控制协议，如 Git 或 Mercurial。运行 `go help importpath` 查看详情。

`go get` 创建的目录是远程仓库的真实客户端，而不仅仅是文件副本，因此你可以使用版本控制命令查看本地编辑的差异，或更新到不同的版本。例如，`golang.org/x/net` 目录是一个 Git 客户端：

```
$ cd $GOPATH/src/golang.org/x/net

$ git remote -v

origin  https://go.googlesource.com/net (fetch)

origin  https://go.googlesource.com/net (push)
```

注意，包导入路径中的表观域名 `golang.org` 与实际 Git 服务器的域名 `go.googlesource.com` 不同。这是 `go` 工具的一项功能，它允许包在导入路径中使用自定义域名，同时由通用服务（如 `googlesource.com` 或 `github.com`）托管。`https://golang.org/x/net/html` 下的 HTML 页面包含如下所示的元数据，可将 `go` 工具重定向到实际托管网站的 Git 仓库：

```
$ go build gopl.io/ch1/fetch

$ ./fetch https://golang.org/x/net/html | grep go-import

<meta name="go-import"
      content="golang.org/x/net git https://go.googlesource.com/net">
```

如果指定 `-u` 标志，`go get` 将确保其访问的所有包（包括依赖项）在构建和安装前都更新到最新版本。如果没有该标志，本地已存在的包将不会更新。

`go get -u` 命令通常会获取每个包的最新版本，这在入门时很方便，但对于已部署的项目可能不合适，因为精确控制依赖项对于发布卫生至关重要。通常的解决方案是 *vendor* 代码，即制作所有必要依赖项的持久本地副本，并谨慎、刻意地更新此副本。在 Go 1.5 之前，这需要更改这些包的导入路径，因此我们的 `golang.org/x/net/html` 副本将变为 `gopl.io/vendor/golang.org/x/net/html`。更新版本的 `go` 工具直接支持 vendoring，尽管此处没有空间展示细节。请参阅 `go help gopath` 命令输出中的 *Vendor Directories*。

**练习 10.3：** 使用 `fetch http://gopl.io/ch1/helloworld?go-get=1`，找出哪个服务托管了本书的代码示例。（来自 `go get` 的 HTTP 请求包含 `go-get` 参数，以便服务器将其与普通浏览器请求区分开。）

### 10.7.3 构建包

`go build` 命令编译每个参数包。如果包是库，则丢弃结果；这仅检查包是否没有编译错误。如果包名为 `main`，`go build` 将调用链接器在当前目录中创建可执行文件；可执行文件的名称取自包导入路径的最后一段。

由于每个目录包含一个包，每个可执行程序（或 Unix 术语中的 *command*）都需要自己的目录。这些目录有时是名为 `cmd` 的目录的子目录，例如 `golang.org/x/tools/cmd/godoc` 命令，它通过 Web 界面提供 Go 包文档（§10.7.4）。

包可以通过其导入路径指定（如上所示），或通过相对目录名指定，后者必须以 `.` 或 `..` 段开头，即使通常不需要这样做。如果未提供参数，则假定为当前目录。因此，以下命令构建相同的包，尽管每个命令都在运行 `go build` 的目录中写入可执行文件：

```
$ cd $GOPATH/src/gopl.io/ch1/helloworld

$ go build
```

和：

```
$ cd anywhere

$ go build gopl.io/ch1/helloworld
```

和：

```
$ cd $GOPATH

$ go build ./src/gopl.io/ch1/helloworld
```

但不能：

```
$ cd $GOPATH

$ go build src/gopl.io/ch1/helloworld

Error: cannot find package "src/gopl.io/ch1/helloworld".
```

包也可以指定为文件名列表，尽管这通常仅用于小程序和一次性实验。如果包名为 `main`，可执行文件名来自第一个 `.go` 文件的基本名称。

```
$ cat quoteargs.go

package main

import (
    "fmt"
    "os"
)

func main() {
    fmt.Printf("%q\n", os.Args[1:])
}

$ go build quoteargs.go

$ ./quoteargs one "two three" four\ five

["one" "two three" "four five"]
```

特别是对于这种一次性程序，我们希望在构建后立即运行可执行文件。`go run` 命令将这两个步骤合二为一：

```
$ go run quoteargs.go one "two three" four\ five

["one" "two three" "four five"]
```

第一个不以 `.go` 结尾的参数被视为 Go 可执行文件参数列表的开始。

默认情况下，`go build` 命令构建请求的包及其所有依赖项，然后丢弃除最终可执行文件（如果有）之外的所有编译代码。依赖分析和编译都非常快，但随着项目增长到数十个包和数十万行代码，重新编译依赖项的时间可能变得明显，甚至达数秒，即使那些依赖项根本没有改变。

`go install` 命令与 `go build` 非常相似，不同之处在于它保存每个包和命令的编译代码，而不是丢弃它们。编译后的包保存在 `$GOPATH/pkg` 目录下，对应源码所在的 `src` 目录，命令可执行文件保存在 `$GOPATH/bin` 目录下。（许多用户将 `$GOPATH/bin` 加入可执行文件搜索路径。）此后，如果这些包和命令未更改，`go build` 和 `go install` 将不再为它们运行编译器，从而使后续构建快得多。为方便起见，`go build -i` 会安装构建目标的依赖包。

由于编译后的包因平台和架构而异，`go install` 将它们保存在名称包含 `GOOS` 和 `GOARCH` 环境变量值的子目录下。例如，在 Mac 上，`golang.org/x/net/html` 包被编译并安装在 `$GOPATH/pkg/darwin_amd64` 下的 `golang.org/x/net/html.a` 文件中。

*交叉编译* Go 程序非常简单，即构建针对不同操作系统或 CPU 的可执行文件。只需在构建期间设置 `GOOS` 或 `GOARCH` 变量。`cross` 程序打印其构建目标的操作系统和架构：

```
gopl.io/ch10/cross

func main() {
    fmt.Println(runtime.GOOS, runtime.GOARCH)
}
```

以下命令分别生成 64 位和 32 位可执行文件：

```
$ go build gopl.io/ch10/cross

$ ./cross

darwin amd64

$ GOARCH=386 go build gopl.io/ch10/cross

$ ./cross

darwin 386
```

某些包可能需要为特定平台或处理器编译不同版本的代码，以处理低级可移植性问题或提供重要例程的优化版本。如果文件名包含操作系统或处理器架构名称，如 `net_linux.go` 或 `asm_amd64.s`，则 `go` 工具仅在为该目标构建时编译该文件。称为 *build tags* 的特殊注释提供了更细粒度的控制。例如，如果文件包含此注释：

```
// +build linux darwin
```

在包声明（及其文档注释）之前，`go build` 将仅在为 Linux 或 Mac OS X 构建时编译它，而此注释表示永远不要编译该文件：

```
// +build ignore
```

有关更多详细信息，请参阅 `go/build` 包文档的 *Build Constraints* 部分：

```
$ go doc go/build
```

### 10.7.4 文档化包

Go 风格强烈鼓励对包 API 进行良好的文档记录。每个导出的包成员的声明以及包声明本身都应紧跟在一个解释其目的和用法的注释之前。

Go *文档注释* 始终是完整的句子，第一句通常是一个以声明名称开头的摘要。函数参数和其他标识符在提及时不加引号或标记。例如，这是 `fmt.Fprintf` 的文档注释：

```
// Fprintf formats according to a format specifier and writes to w.
// It returns the number of bytes written and any write error encountered.
func Fprintf(w io.Writer, format string, a ...interface{}) (int, error)
```

`Fprintf` 的格式化细节在与 `fmt` 包本身关联的文档注释中解释。紧接在 `package` 声明之前的注释被视为整个包的文档注释。必须只有一个，尽管它可以出现在任何文件中。较长的包注释可能需要单独的文件；`fmt` 的注释超过 300 行。此文件通常称为 `doc.go`。

良好的文档不必详尽，文档也不能替代简洁性。事实上，Go 的约定倾向于在文档中也保持简洁和简单，因为文档像代码一样也需要维护。许多声明可以用一个措辞得当的句子来解释，如果行为确实显而易见，则不需要注释。

全书中，在空间允许的情况下，我们在许多声明前加上了文档注释，但浏览标准库时你会找到更好的示例。两个工具可以帮助你做到这一点。

`go doc` 工具打印命令行指定实体的声明和文档注释，该实体可以是一个包：

```
$ go doc time

package time // import "time"
Package time provides functionality for measuring and displaying time.
const Nanosecond Duration = 1 ...
func After(d Duration) <-chan Time
func Sleep(d Duration)
func Since(t Time) Duration
func Now() Time
type Duration int64
type Time struct { ... }
...many more...
```

或一个包成员：

```
$ go doc time.Since

func Since(t Time) Duration
    Since returns the time elapsed since t.
    It is shorthand for time.Now().Sub(t).
```

或一个方法：

```
$ go doc time.Duration.Seconds

func (d Duration) Seconds() float64
    Seconds returns the duration as a floating-point number of seconds.
```

该工具不需要完整的导入路径或正确的标识符大小写。此命令从 `encoding/json` 包打印 `(*json.Decoder).Decode` 的文档：

```
$ go doc json.decode

func (dec *Decoder) Decode(v interface{}) error
    Decode reads the next JSON-encoded value from its input and stores
    it in the value pointed to by v.
```

第二个工具，令人困惑地命名为 `godoc`，提供交叉链接的 HTML 页面，提供与 `go doc` 相同的信息以及更多内容。`godoc` 服务器 `https://golang.org/pkg` 涵盖标准库。图 10.1 显示了 `time` 包的文档，在第 11.6 节中我们将看到 `godoc` 对示例程序的交互式显示。`godoc` 服务器 `https://godoc.org` 拥有数千个开源包的可搜索索引。

![The time package in godoc.](img/godoc-time.png)

**图 10.1.** `time` 包在 `godoc` 中的显示。

如果你想浏览自己的包，也可以在工作区运行一个 `godoc` 实例。在运行此命令时访问浏览器中的 `http://localhost:8000/pkg`：

```
$ godoc -http :8000
```

其 `-analysis=type` 和 `-analysis=pointer` 标志用高级静态分析的结果增强文档和源代码。

### 10.7.5 内部包

包是 Go 程序中封装的最重要机制。未导出的标识符仅在同一个包内可见，而导出的标识符对全世界可见。

不过，有时中间地带会很有帮助，一种定义标识符的方式，使其对一小组受信任的包可见，但不对所有人可见。例如，当我们将一个大包拆分为更易管理的部分时，我们可能不想向其他包公开这些部分之间的接口。或者我们可能想在项目的几个包之间共享工具函数，而不想更广泛地暴露它们。又或者我们只是想通过将一个新包“置于试用期”并限制其客户端集合，来在过早承诺其 API 之前对其进行试验。

为了满足这些需求，如果包的导入路径包含名为 `internal` 的路径段，`go build` 工具会对该包进行特殊处理。此类包称为 *内部包*。内部包只能由位于 `internal` 目录父级为根的树内的另一个包导入。例如，给定下面的包，`net/http/internal/chunked` 可以从 `net/http/httputil` 或 `net/http` 导入，但不能从 `net/url` 导入。然而，`net/url` 可以导入 `net/http/httputil`。

```
net/http
net/http/internal/chunked
net/http/httputil
net/url
```

### 10.7.6 查询包

`go list` 工具报告可用包的信息。在最简单的形式下，`go list` 测试包是否存在于工作区中，如果存在则打印其导入路径：

```
$ go list github.com/go-sql-driver/mysql

github.com/go-sql-driver/mysql
```

`go list` 的参数可能包含 `...` 通配符，它匹配包导入路径的任何子字符串。我们可以用它来枚举 Go 工作区内的所有包：

```
$ go list ...

archive/tar
archive/zip
bufio
bytes
cmd/addr2line
cmd/api
...many more...
```

或特定子树内的包：

```
$ go list gopl.io/ch3/...

gopl.io/ch3/basename1
gopl.io/ch3/basename2
gopl.io/ch3/comma
gopl.io/ch3/mandelbrot
gopl.io/ch3/netflag
gopl.io/ch3/printints
gopl.io/ch3/surface
```

或与特定主题相关的包：

```
$ go list ...xml...

encoding/xml
gopl.io/ch7/xmlselect
```
