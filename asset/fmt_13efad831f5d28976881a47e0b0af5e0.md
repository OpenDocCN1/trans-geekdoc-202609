
# 证书颁发机构与公钥基础设施

*证书颁发机构*（CAs）是将公钥基础设施粘合在一起的关键。这些中立组织为数字证书提供公证服务。要从信誉良好的 CA 获得数字证书，您必须向 CA 证明您的身份，令其满意。以下列表包含一些提供广泛接受的数字证书的主要 CA：

*   Symantec
*   IdenTrust
*   Amazon Web Services
*   GlobalSign
*   Comodo
*   Certum
*   GoDaddy
*   DigiCert
*   Secom
*   Entrust
*   Actalis
*   Trustwave

没有任何东西能阻止任何组织直接开张当 CA。然而，CA 颁发的证书只有在该 CA 受到信任的情况下才可靠。当从第三方接收数字证书时，这是一个需要考虑的重要事项。如果您不认识也不信任颁发证书的 CA 的名称，则完全不应信任该证书。PKI 依赖于信任关系的层级结构。如果您将浏览器配置为信任某个 CA，它将自动信任该 CA 颁发的所有数字证书。浏览器开发商预先将浏览器配置为信任主要 CA，以避免将此负担强加给用户。

*注册机构*（RAs）协助 CA 在颁发数字证书之前验证用户身份的负担。它们不直接颁发证书，但在认证过程中发挥着重要作用，允许 CA 远程验证用户身份。

## 证书生成和销毁

公钥基础设施背后的技术概念相对简单。在以下章节中，我们将介绍证书颁发机构用于创建、验证和撤销客户端证书的过程。

### 注册

当您想要获取数字证书时，首先必须以某种方式向 CA 证明您的身份；这个过程称为*注册*。如前一节所述，这有时涉及携带适当的身份证明文件亲自出现在认证机构代理人面前。一些证书颁发机构提供其他验证方式，包括使用信用报告数据和由受信任的社区领袖进行身份验证。

一旦您让证书颁发机构对您的身份感到满意，您就向他们提供您的公钥。CA 接下来创建一个包含您身份信息和公钥副本的 X.509 数字证书。然后，CA 使用 CA 的私钥对证书进行数字签名，并向您提供一份已签名的数字证书副本。然后，您可以安全地将此证书分发给任何您想要安全通信的人。

### 验证

当您收到某人提供的数字证书并想与其通信时，您可以通过使用 CA 的公钥检查 CA 的数字签名来*验证*该证书。接下来，您必须检查并确保该证书未被撤销，方法是使用*证书吊销列表*（CRL）或*在线证书状态协议 (OCSP)*。此时，如果满足以下要求，您可以假设证书中列出的公钥是真实的：

*   CA 的数字签名是真实的。
*   您信任该 CA。
*   该证书未列在 CRL 上。
*   证书实际包含您所信任的数据。

最后一点是一个微妙但极其重要的项目。在您信任关于某人的身份识别信息之前，请确保它实际包含在证书内。如果证书包含电子邮件地址（`billjones@foo.com`）但不包含个人姓名，您只能确定其中包含的公钥与该电子邮件地址相关联。CA 对 `billjones@foo.com` 电子邮件账户的实际身份不做任何断言。但是，如果证书包含姓名 Bill Jones 以及地址和电话号码，CA 也在为该信息担保。

数字证书验证算法内置于许多流行的 Web 浏览和电子邮件客户端中，因此您通常不需要深入了解该过程的细节。然而，对幕后发生的技术细节有扎实的理解对于为您的组织做出适当的安全判断非常重要。这也是为什么在购买证书时，您要选择一个广受信任的 CA。如果一个 CA 不在主流浏览器信任的 CA 列表中，或稍后被从中移除，将极大地限制您证书的用处。

2017 年，数字证书行业发生了一起重大安全故障。Symantec 通过一系列关联公司颁发了几个不符合行业安全标准的数字证书。作为回应，Google 宣布 Chrome 浏览器将不再信任 Symantec 证书。结果，Symantec 最终将其证书颁发业务出售给了 DigiCert，后者同意在颁发前妥善验证证书。这证明了妥善验证证书请求的重要性。一系列看似微小的程序疏忽可能会摧毁一个 CA 的业务！

### 撤销

有时，证书颁发机构需要*撤销*证书。这可能由于以下原因之一发生：

*   证书被泄露（例如，证书所有者意外泄露了私钥）。
*   证书被错误颁发（例如，CA 在未进行适当验证的情况下错误地颁发了证书）。
*   证书详细信息发生变更（例如，主体名称已更改）。
*   安全关联发生变更（例如，主体不再受雇于赞助该证书的组织）。

您可以使用两种技术来验证证书的真实性并识别已撤销的证书：

#### 证书吊销列表

证书吊销列表（CRL）由各个证书颁发机构维护，包含已由 CA 颁发并已被撤销的证书的序列号，以及撤销生效的日期和时间。证书吊销列表的主要缺点是必须定期下载和交叉引用，这在证书被撤销的时间和最终用户收到撤销通知的时间之间引入了一段延迟期。然而，CRL 仍然是目前最常用的检查证书状态的方法。

#### 在线证书状态协议 (OCSP)

该协议通过提供实时证书验证的手段，消除了使用证书吊销列表固有的延迟。当客户端收到证书时，它向 CA 的 OCSP 服务器发送 OCSP 请求。服务器随后响应有效、无效或未知的状态。

## 非对称密钥管理

在公钥基础设施中工作时，遵守若干最佳实践要求以维护通信安全非常重要。

首先，明智地选择您的加密系统。正如您之前所学，“通过隐匿实现安全”不是一种合适的方法。选择一种算法处于公共领域且已由行业专家彻底审查的加密系统。警惕那些使用“黑盒”方法并坚持其算法的保密性对密码系统的完整性至关重要的系统。

### 密钥管理最佳实践

您还必须以适当的方式选择密钥。使用一种在安全需求与性能考量之间取得平衡的密钥长度。此外，确保您的密钥真正随机。密钥中的任何模式都会增加攻击者破解您加密的可能性，并降低密码系统的安全性。

使用公钥加密时，请务必保管好您的私钥！在任何情况下，都不允许其他人访问您的私钥。请记住，即使仅允许他人访问一次，也会永久性地危害使用该密钥进行的所有通信（过去、现在或未来）的安全，并允许第三方成功冒充您。

在密钥完成其使用寿命后将其弃用。许多组织都有强制性的密钥轮换要求，以防止未被发现的密钥泄露。如果您没有必须遵循的正式策略，请根据您使用密钥的频率选择一个合适的间隔。如果切实可行，您可能希望每隔几个月更换一次密钥对。

备份您的密钥！如果您因数据损坏、灾难或其他情况丢失了包含私钥的文件，您肯定希望有可用的备份。您可以自行创建备份，也可以使用由第三方为您维护备份的密钥托管服务。无论哪种情况，都要确保以安全的方式处理备份。毕竟，它与您的主密钥文件同等重要！

`硬件安全模块 (HSM)` 也提供了一种管理加密密钥的有效方式。这些硬件设备以安全的方式存储和管理加密密钥，防止人类需要直接处理密钥。HSM 的范围和复杂程度各不相同，从非常简单的设备（如 `YubiKey`，将加密密钥存储在 USB 驱动器上供个人使用）到驻留在数据中心的更复杂的企业级产品。云服务提供商（如 Amazon 和 Microsoft）也提供基于云的 HSM，为 IaaS 服务提供安全的密钥管理。

## 应用密码学

到目前为止，您已经学习了大量关于密码学基础、各种加密算法内部工作原理，以及利用公钥基础设施通过数字证书分发身份凭据的知识。您现在应该对密码学基础感到得心应手，并准备好继续学习这项技术的更高层级应用，以解决日常通信问题。

在以下章节中，我们将探讨使用密码学保护静态数据（如存储在便携设备上的数据）以及传输中的数据，所用技术包括安全电子邮件、加密 Web 通信和网络加密。

### 便携设备

笔记本电脑、上网本、智能手机和平板电脑现在无处不在，这给计算领域带来了新的风险。这些设备通常包含高度敏感的信息，一旦丢失或被盗，可能会给组织及其客户、员工和关联方造成严重损害。因此，许多组织转向使用加密来保护这些设备上的数据，以防设备遗失。

当前版本的主流操作系统现在都包含磁盘加密功能，使得在便携设备上应用和管理加密变得容易。例如，Microsoft Windows 包含 `BitLocker` 和 `加密文件系统 (EFS)` 技术，Mac OS X 包含 `FileVault` 加密，而 `VeraCrypt` 开源套件允许在 Linux、Windows 和 Mac 系统上对磁盘进行加密。

有各种各样的商业工具可用，它们提供额外的功能和管理能力。这些工具的主要区别在于它们如何保护存储在内存中的密钥、是提供全盘加密还是仅卷加密，以及是否与基于硬件的 `可信平台模块 (TPM)` 集成以提供额外的安全性。任何选择加密软件的工作都应包括对备选方案在这些特性上竞争表现的分析。

### 电子邮件

我们多次提到安全应具有成本效益。就电子邮件而言，简单性是最具成本效益的选择，但有时密码学功能提供了您不得不使用的特定安全服务。既然确保安全也是具有成本效益的，以下是关于加密电子邮件的一些简单规则：

*   如果您发送电子邮件时需要**机密性**，请加密该消息。
*   如果您的消息必须保持**完整性**，您必须对消息进行哈希处理。
*   如果您的消息需要**认证**、**完整性**和/或**不可抵赖性**，您应该对消息进行数字签名。
*   如果您的消息要求**机密性**、**完整性**、**认证**和**不可抵赖性**，您应该对消息进行加密并数字签名。

发送方始终有责任采取适当机制，以确保消息或传输的安全性（即机密性、完整性、真实性和不可抵赖性）得以维持。

密码学最热门的应用之一是电子邮件的加密和签名。直到最近，加密电子邮件还需要使用复杂、笨拙的软件，而这些软件又需要人工干预和复杂的密钥交换过程。近年来对安全性的重视程度提高，导致主流电子邮件软件包中实现了强加密技术。接下来，我们将了解一些当今广泛使用的安全电子邮件标准。

#### 优良隐私协议

Phil Zimmerman 的优良隐私协议 (PGP) 安全电子邮件系统于 1991 年出现在计算机安全领域。它将本章前面描述的 CA 层级结构与“信任网”概念相结合——也就是说，您必须获得一个或多个 PGP 用户的信任才能开始使用该系统。然后您接受他们对其他用户有效性的判断，并由此延伸，信任一个从您最初的信任判断衍生出的多层级用户“网络”。

PGP 最初遇到了广泛使用的许多障碍。最难克服的阻碍是美国政府的出口管制，该管制将加密技术视为军火，并禁止向美国境外分发强加密技术。幸运的是，这一限制现已废除，PGP 可自由分发给大多数国家。

PGP 有两个版本。商业版使用 `RSA` 进行密钥交换，使用 `IDEA` 进行加密/解密，使用 `MD5` 生成消息摘要。免费版（基于极其相似的 OpenPGP 标准）使用 `Diffie-Hellman` 密钥交换、Carlisle Adams/Stafford Tavares (CAST) 128 位加密/解密算法和 `SHA-1` 哈希函数。

许多商业提供商还提供基于 PGP 的电子邮件服务，形式包括基于 Web 的云电子邮件产品、移动设备应用程序或 Webmail 插件。这些服务吸引管理员和最终用户，因为它们消除了配置和维护加密证书的复杂性，并为用户提供托管的安全电子邮件服务。此类产品包括 `StartMail`、`Mailvelope`、`SafeGmail` 和 `Hushmail`。

#### S/MIME

安全/多用途互联网邮件扩展 (S/MIME) 协议已成为加密电子邮件的事实标准。S/MIME 使用 `RSA` 加密算法，并获得了包括 RSA Security 在内的主要行业参与者的支持。S/MIME 已被纳入大量商业产品中，包括：

*   Microsoft Outlook 和 Office 365
*   Mozilla Thunderbird
*   Mac OS X Mail
*   GSuite 企业版

S/MIME 依赖 X.509 证书来交换加密密钥。这些证书中包含的公钥用于数字签名，以及用于较长通信会话的对称密钥交换。`RSA` 是 S/MIME 支持的唯一公钥加密协议。该协议支持 `AES` 和 `3DES` 对称加密算法。

尽管业界对 S/MIME 标准有强有力的支持，但技术限制阻碍了其广泛采用。虽然主流桌面邮件应用程序支持 S/MIME 邮件，但主流基于 Web 的电子邮件系统并不原生支持它（需要使用浏览器扩展）。

### Web 应用程序

加密被广泛用于保护 Web 事务。这主要是因为电子商务的强劲发展，以及电子商务供应商和消费者都希望通过 Web 安全地交换财务信息（如信用卡信息）。我们将介绍两项技术，它们是 Web 浏览器中小锁图标的由来——安全套接字层（`SSL`）和传输层安全性（`TLS`）。

`SSL` 由 Netscape 开发，旨在为 Web 流量提供客户端/服务器加密。超文本传输安全协议（`HTTPS`）使用端口 `443` 在 Web 服务器和浏览器客户端之间协商加密通信会话。虽然 `SSL` 起源于 Netscape 浏览器的标准，但 Microsoft 也将其作为其流行的 Internet Explorer 浏览器的安全标准予以采纳。这两款产品都纳入了 `SSL`，使其成为事实上的互联网标准。

`SSL` 依赖服务器数字证书的交换，在浏览器和 Web 服务器之间协商加密/解密参数。`SSL` 的目标是创建安全通信通道，在整个 Web 浏览会话期间保持打开状态。它依赖对称和非对称加密的组合。涉及以下步骤：

1.  当用户访问网站时，浏览器检索 Web 服务器的证书并从中提取服务器的公钥。
2.  然后浏览器创建一个随机对称密钥，使用服务器的公钥对其进行加密，并将加密的对称密钥发送给服务器。
3.  服务器随后使用其自己的私钥解密对称密钥，两个系统使用对称加密密钥交换所有未来的消息。

这种方法使 `SSL` 能够利用非对称加密的高级功能，同时使用更快的对称算法加密和解密交换的绝大多数数据。

1999 年，安全工程师提出 `TLS` 作为 `SSL` 标准的替代品，当时 `SSL` 处于第三版。与 `SSL` 一样，`TLS` 使用 TCP 端口 `443`。基于 `SSL` 技术，`TLS` 结合了许多安全增强功能，并最终在大多数应用程序中被采纳为 `SSL` 的替代品。早期版本的 `TLS` 支持在双方均不支持 `TLS` 时将通信降级到 `SSL v3.0`。然而，在 2011 年，`TLS v1.2` 取消了这种向后兼容性。

2014 年，一种称为填充神谕攻击降级遗留加密（`POODLE`）的攻击演示了 `TLS` 的 `SSL 3.0` 回退机制中存在的重大缺陷。为了修补此漏洞，许多组织完全放弃了 `SSL` 支持，现在仅依赖 `TLS` 安全性。

### 隐写术和水印

`隐写术` 是利用加密技术将秘密消息嵌入另一条消息中的艺术。隐写算法通过更改构成图像文件的众多位中最低有效位来工作。这些更改非常微小，以至于对查看的图像没有可感知的影响。该技术允许通信双方在显而易见的地方隐藏消息——例如，他们可能将秘密消息嵌入到一个原本无害的网页的插图中。

隐写者通常将秘密消息嵌入图像或 `WAV` 文件中，因为这些文件通常非常大，即使是最敏锐的检查员也容易忽略秘密消息。隐写术技术常用于非法或可疑活动，如间谍活动和儿童色情。

然而，隐写术也可用于合法目的。通过隐写术向文档添加数字水印以保护知识产权。隐藏信息仅为文件创建者所知。如果有人稍后创建了内容的未授权副本，水印可用于检测该副本（如果向每个原始接收者提供唯一水印的文件），并将违规副本追溯到源头。

### 数字版权管理

`数字版权管理`（`DRM`）软件使用加密来对数字媒体强制执行版权限制。在过去十年中，出版商尝试在各种媒体类型中部署 `DRM` 方案，包括音乐、电影和书籍。在许多情况下，特别是音乐方面，反对者对 `DRM` 部署尝试进行了强烈抵制，认为使用 `DRM` 侵犯了他们自由享受和制作合法授权媒体文件备份副本的权利。

#### 音乐 DRM

音乐行业多年来一直在与盗版作斗争，可以追溯到自制磁带复制的时代，并延续到光盘和数字格式。音乐分发公司尝试使用各种 `DRM` 方案，但大多数在消费者压力下放弃了该技术。

当苹果公司面对这种反对意见，撤回了通过 iTunes Store 销售的音乐所使用的 `FairPlay DRM` 时，购买音乐使用 `DRM` 的情况大幅放缓。苹果联合创始人史蒂夫·乔布斯在 2007 年致音乐行业的一封公开信中预示了这一举措，呼吁他们允许苹果销售无 DRM 音乐。信中部分写道：

> 第三种选择是彻底废除 DRM。想象一个世界，每个在线商店都销售采用开放可授权格式编码的无 DRM 音乐。在这样的世界里，任何播放器都可以播放从任何商店购买的音乐，任何商店都可以销售可在所有播放器上播放的音乐。这显然是对消费者最好的选择，苹果会毫不犹豫地接受。如果四大音乐公司愿意在不要求 DRM 保护的情况下将音乐授权给苹果，我们将在 iTunes 商店只销售无 DRM 音乐。每一款 iPod 都能播放这种无 DRM 音乐。

完整文章不再在苹果网站上提供，但可在 [`bit.ly/1TyBm5e`](http://bit.ly/1TyBm5e) 找到存档副本。

目前，`DRM` 技术在音乐中的主要用途是基于订阅的服务，如 Napster 和 Kazaa，它们使用 `DRM` 在用户订阅期结束时撤销用户对已下载音乐的访问权限。

#### 电影 DRM

电影行业多年来使用了各种 `DRM` 方案来遏制全球性的电影盗版问题。用于保护大规模分发媒体的两项主要技术如下：

##### 高带宽数字内容保护 (HDCP)

为通过数字连接（包括 HDMI、DisplayPort 和 DVI 接口）发送的内容提供 DRM 保护。虽然该技术仍广泛应用于许多实现中，但黑客于 2010 年发布了 HDCP 主密钥，使该保护完全失效。

##### 高级访问内容系统 (AACS)

保护存储在蓝光和 HD DVD 媒体上的内容。黑客已演示了检索 AACS 加密密钥并将其发布到互联网上的攻击手段。

行业出版商与黑客之间的“猫鼠游戏”至今仍在继续；媒体公司试图保护其内容，而黑客则寻求持续获取未加密副本的途径。
