
这可能导致语义上的胡扯，例如比较人和城市，或比较身高和体重。SQL 标准现在允许属性定义在用户定义的语法域上，这些域指定底层数据类型，并可选择性地指定值列表和/或默认值。标准 SQL 中的底层数据类型支持字符串、数字、日期、时间和位串，但不支持 `Money`，后者是用数值数据类型定义的，例如 `decimal(9,2)`。SQL:1999 引入了用户定义类型，可用作语义域。然而，许多商业 SQL 仍不支持用户定义的域或类型，因此从这一点开始，我们通常会忽略域的细节。

### 关系模式中的约束表示法

现在让我们考虑关系模式中用于指定**约束**的主要表示法。后续章节将讨论如何将事实类型分组到表模式中，以及如何更详细地映射约束和规则。

使用水平布局时，关系列上的**唯一性约束**通过下划线表示。表的**超键**（superkey）是一个或多个列的集合，其条目必须唯一，从而提供了一种识别表中行的方法。**候选键**（candidate key）是**最小**超键。换句话说，如果从复合键中移除一个属性，剩余属性不再受唯一性约束约束。如果只有一个候选键，它自动成为**主键**（primary key）。例如，我们可以指示 `empNr` 是 `Employee` 表的主键，如下所示：

```
Employee ( empNr, salary, tax )
```

如果存在多个候选键，必须选择其中一个作为主键。其他的则称为“**备选键**”（alternate keys）或“**次要键**”（secondary keys）。

如果存在备选键，主键用双下划线标记。例如，假设我们还记录每个员工的姓名和部门，且员工姓名与部门的组合是唯一的。主键和次要键可以如下所示：

```
Employee ( empNr, empName, deptCode, salary, tax )
```

列出列的顺序在语义上无关紧要，因为每个列都有一个在其表中唯一的名称。如果复合键中的列未连续列出，则用虚线连接下划线，以表明应用的是单个复合唯一性约束，而不是多个简单约束。例如，前面的 `Employee` 表模式也可以如下显示：

![](img/u11-20-9780443237904.jpg)

不允许空值的列被称为**强制性**的（针对其表）。允许空值的列被称为*可选*的。对于水平布局，本书采用以下惯例：可选列用*方括号*括起；除非标记为可选，否则列在其表中是强制性的。这种做法与著名的巴科斯-诺尔范式（BNF）表示法一致。例如，因为纳税是可选的，前面的 ORM 模式映射为以下表模式，其中 `tax` 列为可选（允许空值）：

```
Employee ( empNr, salary, [tax] )
```

### 映射强制角色约束

图 11.3(a) 在 图 11.1 的基础上增加了两个事实类型。现在记录每位员工的性别以及员工驾驶的汽车。仅当对象类型 *O* 扮演的每个其他角色的总体必须是角色 *r* 总体的子集时，角色 *r* 对对象类型 *O* 才是强制的。因此，一个对象类型的每个可选角色都对该对象类型的每个强制角色有一个*隐含子集约束*。图 11.3(b) 显示了从 `Employee` 的每个可选角色到 `Employee` 的一个强制角色的隐含子集约束（绿色标注）。强制角色之间隐含相等约束，但与我们的讨论无关。

![图 11.3 子集约束由强制角色约束隐含。](img/f11-03-9780443237904.jpg)

图 11.3 子集约束由强制角色约束隐含。

如果一个对象类型扮演的所有角色都映射到同一张表，其强制角色只需指定为强制列即可。然而，关系模型通常要求关于同一对象的不同事实存储在不同的表中。一般来说，*强制角色约束通过使其列在各自的表中成为强制列来捕获，并从包含该对象类型事实的其他表（如果有）运行子集约束*。

正如下一节所讨论的，*m:n* 性质的 `drives` 事实类型要求将其映射到不同于其他三个事实类型的关系表中。因此，`Employee` 的信息分散在 图 11.3(c) 所示的两个关系表中。在这里，强制角色约束仅被部分捕获——没有任何机制阻止我们在 `Drives` 表中输入 `Employee` 表中不存在的员工编号。

那么我们如何映射概念层面的强制角色约束呢？

`salary`、`gender` 和 `tax` 这三个 *n*:1 事实类型被归组到 `Employee` 表中。强制的 `salary` 和 `gender` 谓词映射为强制列，而 `tax` 角色上的子集约束通过使 `tax` 成为 `Employee` 表中唯一的可选列来捕获。`drives` 事实类型映射到一个单独的表。

为了捕获来自 `drives` 角色的子集约束，我们向关系模式添加一个从 `Drives` 表的 `empNr` 列到 `Employee` 表的 `empNr` 列的子集约束。在水平布局中，该子集约束描绘为虚线箭头，如 图 11.3(c) 所示。这确保了任何被列为驾驶汽车的员工也列在 `Employee` 表中，在那里 `gender` 和 `salary` 被强制记录。

在关系术语中，该子集约束是一个*参照完整性约束*，`Drives` 表的 `empNr` 属性是一个*外键*，它*引用* `Employee` 表的 `empNr` 属性。在标准关系模型中，外键只能引用主键，但 SQL 也允许外键以候选键为目标。

关系模型有两条基本完整性规则。*实体完整性规则*要求主键不包含空值（即主键中的每一列都是其表的强制列）。*参照完整性规则*基本上规定外键的每个非空值必须匹配某个主键的值。关系模型还允许用户定义约束和派生规则。

```

## 11.3 关系映射过程

上一节介绍了一种用于列出关系模式的通用符号，并讨论了从概念模式映射到关系模式的简单示例。现在我们讨论执行此类映射的通用过程的主要步骤。该过程的高级方面将在第 11.4 节中探讨。

对于给定的概念模式，可能会选择几种不同的关系设计。理想情况下，所选的关系模式应*正确、高效且清晰*。正确性要求关系模式等同于概念模式（在关系结构允许的完整性范围内）。效率意味着对更新和查询有良好的响应时间，且对存储空间的要求合理。清晰性意味着模式应相对易于理解和使用。

由于数据的正确性通常比快速响应时间更重要，而正确性需要充分的约束强制执行，因此通常高度重视简化更新时的约束强制执行。实现这一点的主要方法是*避免冗余*。这种策略可能导致设计中包含更多表，如果现在需要额外的表连接，可能会降低查询和更新的速度。为提高效率，我们应尝试将表的数量保持在可接受的限度内。

### Rmap 过程概述

考虑到这些标准，**Rmap** (*R*elational *map*ping) 过程保证了无冗余的关系设计，并包含限制表数量的策略。Rmap 扩展并改进了一个称为“最优范式” (ONF) 算法的旧映射过程。Rmap 的完整版本包括将所有图形概念约束完全映射的细节，超出了本书的范围。然而，该过程的核心步骤将在本节和下一节中介绍。

正如后续章节所讨论的，如果在应用 Rmap 之前，概念模式经过优化算法的转换，可能会产生表更少、效率更高的关系设计；有时为了满足关键性能要求，可能需要使用受控冗余进行低级优化。

即使没有进一步的优化，Rmap 过程也极其宝贵，因为它保证了一种安全、合理高效、规范化的设计。幸运的是，该过程的基本步骤很简单。
