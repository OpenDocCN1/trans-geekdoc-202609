
作为安全专业人员参与 SDLC，为提高应用程序安全性提供了重要机会。首次协助软件安全的机会出现在需求收集和设计阶段，此时安全可以作为需求的一部分内置其中，然后基于这些需求进行设计。随后，在开发过程中，安全编码技术、代码审查和测试可以提高所开发代码的质量和安全性。

在测试阶段，可以使用 Web 应用安全扫描器或渗透测试技术等工具对完全集成的软件进行测试。这还为持续的安全运营奠定了基础，通过为未来的安全扫描以及补丁和更新期间的回归测试建立基线。贯穿这些步骤，了解开发人员面临、制造和发现的常见安全问题会有所帮助。

#### 安全编码实践

安全编码实践的最佳资源之一是开放 Web 应用安全项目（OWASP）。OWASP 是一个广泛的开发人员和安全从业者社区的家园，它托管了许多社区开发的标准、指南和最佳实践文档，以及大量开源工具。OWASP 提供了定期更新的主动控制清单，不仅作为一套有用的最佳实践供审查，也作为了解 Web 应用安全威胁逐年变化的一种方式。

以下是 OWASP 2018 年的顶级主动控制措施及其简要说明：

*   **定义安全需求** — 在整个开发过程中实施安全。
*   **利用安全框架和库** — 预先存在的安全功能可以使保护应用程序更容易。
*   **安全数据库访问** — 预构建 SQL 查询以防止注入，并为安全访问配置数据库。
*   **编码和转义数据** — 移除特殊字符。
*   **验证所有输入** — 将用户输入视为不可信并进行适当过滤。

##### OWASP 主动控制措施

*   **实施数字身份** — 使用多因素认证、安全的密码存储与恢复以及会话处理。
*   **强制执行访问控制** — 要求所有请求都经过访问控制检查，默认拒绝，并应用最小权限原则。
*   **保护无处不在的数据** — 在传输中和静态时使用加密。
*   **实施安全日志记录和监控** — 这有助于检测问题，并允许事后进行调查。
*   **处理所有错误和异常** — 错误不应提供敏感数据，且应测试应用程序以确保其能妥善处理问题。

您可以在 `www.owasp.org/index.php/OWASP_Proactive_Controls` 找到 OWASP 的主动控制措施列表，在 `www.owasp.org/index.php/OWASP_Secure_Coding_Practices_-_Quick_Reference:Guide` 可获取一份有用的安全编码实践快速参考指南。

##### API 安全

*应用程序编程接口* (API) 是客户端与服务器之间，或应用程序与操作系统之间的接口，它们定义了客户端应如何向服务器请求信息以及服务器将如何响应。这一定义意味着用任何语言编写的程序都可以实现 API 并发起请求。

API 对于构建系统间的接口非常有用，但如果未妥善保护，它们也可能成为脆弱点。API 安全依赖于认证、授权、适当的数据范围界定（以确保不会发布过多数据）、速率限制、输入过滤，以及适当的监控和日志记录来保持安全。当然，保护底层系统、配置 API 端点服务器或服务，以及提供正常的网络层安全性以保护服务也很重要。

许多安全工具和服务器提供 API，安全专业人员通常需要编写脚本或程序来访问 API 以提取数据。

#### 代码审查模型

审查为应用程序编写的代码具有诸多优势。它有助于共享代码知识，且编写代码获得的经验优于单纯的文档，因为它提供了对代码及其功能的个人理解。它还有助于在开发周期中通过让代码接受审查来发现问题，同时强制执行编码最佳实践和标准。最后，它确保团队的多名成员知晓代码的预期功能及其实现方式。

存在许多常见的*代码审查*流程，包括正式和敏捷流程，如结对编程、过肩审查和 Fagan 代码审查。

##### 结对编程

*结对编程* 是一种敏捷软件开发技术，让两名开发人员共用一个工作站。一名开发人员编写代码，而另一名开发人员在编写过程中审查其代码。这旨在提供实时代码审查，并确保多名开发人员熟悉所编写的代码。在大多数结对编程环境中，开发人员需要频繁轮换角色，使他们都能花时间在键盘前思考代码，并在审查时思考设计及代码中存在的任何问题。

结对编程增加了开发成本，因为它需要两名全职开发人员。同时，它为代码的审查和分析提供了额外机会，并将更多经验直接应用于编码问题，从而有可能提高代码质量。

##### 过肩审查

*过肩代码审查* 同样依赖于一对开发人员，但它不要求持续的互动和交接，而是要求编写代码的开发人员向另一名开发人员解释代码。这种方法允许对代码进行同行评审，还能帮助开发人员理解代码如何工作，且没有结对编程相对较高的成本。

##### 传阅代码审查

*传阅代码审查*，有时称为电子邮件传阅代码审查，是一种通过将完成的代码发送给审查人员来检查代码问题的手动同行评审形式。传阅审查可能涉及多名审查人员，允许具有不同专业知识和经验的审查人员做出贡献。虽然传阅审查在*发生时间*上比过肩审查更灵活，但它们不像过肩审查和结对编程那样提供从编写代码的开发人员那里轻松了解代码的机会，这使得文档变得更加重要。

##### 工具辅助审查

*工具辅助代码审查* 依赖基于正式或非正式软件的工具来进行代码审查。Atlassian 的 Crucible 协作代码审查工具、Codacy 的静态代码审查工具和 Phabricator 的 Differential 代码审查工具等，都是为了改进代码审查流程而设计的。用于代码审查的各种工具不仅反映了软件开发生命周期选项的多样性，也反映了组织如何建立其设计和审查流程。

##### Fagan 检查

*Fagan 检查* 是一种结构化的正式代码审查，旨在在开发过程中发现各种问题。Fagan 检查为流程指定了进入和退出标准，确保在执行适当的尽职调查之前不启动流程，并确保有已知的标准用于进入下一阶段。

图 6.6 所示的 Fagan 检查流程展示了典型流程的六个阶段：

1.  **规划**，包括材料、与会人员和地点的准备
2.  **概览**，通过审查材料和分配角色（如编码人员、阅读人员、审查人员和主持人）来准备团队
3.  **准备**，涉及审查被检查的代码或其他项目，并记录他们可能存在的任何问题或疑问
4.  **会议**，根据准备阶段的记录识别缺陷
5.  **重构以解决问题**
6.  **版主跟进以确保所有已识别的问题均已发现，且在解决过程中未产生新缺陷**

#### 软件安全测试

无论应用程序的开发团队多么优秀，代码中总会存在某种形式的缺陷。Veracode 2019 年基于其测试得出的应用程序指标显示，他们扫描的应用程序中有 83% 在测试过程中至少表现出一个安全问题。这一数字表明，迫切需要将软件安全测试更好地集成到软件开发生命周期中。

安全专业人员和开发人员可使用各种各样的手动和自动测试工具及方法。幸运的是，自动化工具不断改进，提供了一种更简便的方式来验证代码的安全性。在接下来的几页中，我们将回顾当今可用的一些关键软件安全测试方法和工具。

##### 分析和测试代码

作为每个应用程序和程序基础的源代码可能包含各种错误和缺陷，从编程和语法错误到业务逻辑、错误处理以及与其他服务和系统集成方面的问题。能够分析代码以了解代码的功能、执行任务的方式以及程序本身中可能出现缺陷的位置非常重要。这通常通过`静态`或`动态代码分析`以及`模糊测试`等测试方法来完成。一旦对代码进行更改并部署，必须进行`回归测试`，以确保修复措施没有产生新的安全问题！

###### 静态代码分析

*静态代码分析*（有时称为源代码分析）是通过审查应用程序的代码来进行的。由于静态分析使用应用程序的源代码，因此它可以被视为一种`白盒测试`，测试人员拥有完全可见性。这使测试人员能够发现其他测试可能遗漏的问题，原因可能是逻辑未暴露给其他测试方法，或者是由于内部业务逻辑问题。

与许多其他方法不同，静态分析不运行程序；相反，它专注于理解程序是如何编写的以及代码旨在做什么。静态代码分析可以使用自动化工具进行，也可以通过人工审查代码来进行——这一过程有时称为“代码理解”。自动化静态代码分析在查找已知问题方面非常有效，而人工静态代码分析有助于识别程序员引入的错误。

###### 动态代码分析

*动态代码分析*依赖于在提供输入以测试软件的同时执行代码。与静态代码分析非常相似，动态代码分析可以通过自动化工具或手动完成，但由于大多数动态代码测试过程中需要进行大量测试，因此强烈倾向于自动化测试。

###### 模糊测试

*模糊测试*或*模糊测试*，涉及向应用程序发送无效或随机数据，以测试其处理意外数据的能力。系统会监控应用程序，以确定其是否崩溃、失败或以不正确的方式响应。由于模糊测试涉及大量数据，因此通常是自动化的，它对于检测输入验证和逻辑问题以及内存泄漏和错误处理特别有用。不幸的是，模糊测试往往只能识别简单的问题——它不考虑复杂的逻辑或业务流程问题，并且如果不监控其进度，可能无法提供完整的代码覆盖率。

#### 注入漏洞

现在您已经很好地理解了安全代码开发和测试实践，让我们将注意力转向建立这些机制的动力：攻击者可能利用的漏洞，以破坏我们的安全。在本章中，我们将探讨许多不同的漏洞类别。

*注入漏洞*是攻击者用来突破 Web 应用程序并访问支持该应用程序的系统的主要机制之一。这些漏洞允许攻击者向 Web 应用程序提供某种类型的代码作为输入，并诱使 Web 服务器执行该代码或将其提供给另一台服务器执行。

### SQL 注入攻击

Web 应用程序通常接收来自用户的输入，并使用它来构建数据库查询，将结果返回给用户。例如，考虑电子商务网站上的搜索功能。如果用户在搜索框中输入**橙色老虎枕头**，Web 服务器需要知道目录中哪些产品可能与该搜索词匹配。它可能会向后端数据库服务器发送如下所示的请求：

```
SELECT ItemName, ItemDescription, ItemPrice
FROM Products
WHERE ItemName LIKE '%orange%' AND
ItemName LIKE '%tiger%' AND
ItemName LIKE '%pillow%'
```

此命令检索可包含在返回给最终用户的结果中的项目列表。在 SQL 注入攻击中，攻击者可能会向 Web 服务器发送一个看起来非常异常的请求，例如搜索：

```
orange tiger pillow'; SELECT CustomerName, CreditCardNumber FROM Orders; -- 
```

如果 Web 服务器只是将此请求传递给数据库服务器，它将执行以下操作（为便于查看稍作重新格式化）：

```
SELECT ItemName, ItemDescription, ItemPrice
FROM Products
WHERE ItemName LIKE '%orange%' AND
ItemName LIKE '%tiger%' AND
ItemName LIKE '%pillow';
SELECT CustomerName, CreditCardNumber
FROM Orders;
--%'
```

如果成功，此命令将运行两个不同的 SQL 查询（由分号分隔）。第一个将检索产品信息，第二个将检索客户姓名和信用卡号码的列表。

在我们刚才描述的基本 SQL 注入攻击中，攻击者能够向 Web 应用程序提供输入，然后监控该应用程序的输出以查看结果。虽然这是攻击者的理想情况，但许多存在 SQL 注入缺陷的 Web 应用程序并不提供让攻击者直接查看攻击结果的方法。然而，这并不意味着攻击不可能；这只是使其更加困难。攻击者使用一种称为*盲目 SQL 注入*的技术，即使无法直接查看结果也能实施攻击。我们将讨论两种形式的盲目 SQL 注入：基于内容和基于时间。

###### 基于内容的盲目 SQL 注入

在基于内容的盲目 SQL 注入攻击中，攻击者向 Web 应用程序发送输入，在尝试实施攻击之前测试应用程序是否正在解释注入的代码。例如，考虑一个要求用户输入账户号码的 Web 应用程序。此 Web 页面的一个简单版本可能如图 6.7 所示。

当用户在该页面输入账户号码时，接下来将看到与该账户关联的信息列表，如图 6.8 所示。

支持此应用程序的 SQL 查询可能类似于以下内容：

```
SELECT FirstName, LastName, Balance
FROM Accounts
WHERE AccountNumber = '$account'
```

其中 `$account` 字段的值取自 图 6.7 中的输入字段。在此场景下，攻击者可以通过在账号字段中输入以下内容来测试标准的 SQL 注入漏洞：

```
52019' OR 1=1;--
```

如果成功，这将导致以下查询被发送到数据库：

```
SELECT FirstName, LastName, Balance
FROM Accounts
WHERE AccountNumber = '52019' OR 1=1
```

此查询将匹配所有结果。然而，Web 应用程序的设计可能会忽略第一行以外的任何查询结果。如果是这种情况，查询将显示与 图 6.8 所示相同的结果。尽管攻击者可能无法看到查询结果，但这并不意味着攻击失败。然而，由于对应用程序的可见性有限，很难区分防御完善的应用程序和成功的攻击。

攻击者可以通过使用已知会产生结果的输入来执行进一步测试，例如提供 图 6.8 中的账号 52019，并使用可修改该查询以返回*无*结果的 SQL 语句。例如，攻击者可以向该字段提供以下输入：

```
52019' AND 1=2;--
```

如果 Web 应用程序容易受到盲目 SQL 注入攻击，它将向数据库发送以下查询：

```
SELECT FirstName, LastName, Balance
FROM Accounts
WHERE AccountNumber = '52019' AND 1=2
```

当然，此查询永远不会返回任何结果，因为 1 永远不等于 2！因此，Web 应用程序将返回一个无结果的页面，如 图 6.9 所示。如果攻击者看到此页面，他们可以合理地确定该应用程序容易受到盲目 SQL 注入攻击，随后便可尝试更多恶意查询，以篡改数据库内容或执行其他非预期操作。

###### 基于时间的盲目 SQL 注入

除了利用应用程序返回的内容来评估其对盲目 SQL 注入攻击的易感性外，渗透测试人员还可以利用处理查询所需的时间作为从数据库检索信息的通道。

这些攻击依赖于不同数据库平台提供的延迟机制。例如，Microsoft SQL Server 的 Transact-SQL 允许用户指定如下命令：

```
WAITFOR DELAY '00:00:15'
```

此命令将指示数据库在执行下一个操作前等待 15 秒。试图验证应用程序是否容易受到基于时间的攻击的攻击者，可能会向账户 ID 字段提供以下输入：

```
52019'; WAITFOR DELAY '00:00:15'; --
```

立即返回 图 6.8 所示结果的应用程序，很可能不容易受到基于时间的攻击。然而，如果应用程序在 15 秒延迟后返回结果，则很可能存在漏洞。

这看起来可能像是一种奇怪的攻击，但它实际上可用于从数据库中提取信息。例如，假设前面示例中使用的 Accounts 数据库表包含一个名为 `Password` 的未加密字段。攻击者可以使用基于时间的攻击，通过逐个字母检查来发现密码。

执行基于时间的攻击的 SQL 语句有点复杂，考试不要求你掌握它。相反，这里有一些伪代码，从概念上说明该攻击的工作原理：

```
For each character in the password
 For each letter in the alphabet
 If the current character is equal to the current letter, wait 15
 seconds before returning results
```

通过这种方式，攻击者可以遍历所有可能的密码组合，逐个字符地推导出密码。这看起来可能很繁琐，但像 `SQLmap` 和 `Metasploit` 这样的安全工具可以自动执行基于时间的盲目攻击，使其变得非常简单。

##### 代码注入攻击

SQL 注入攻击是一类被称为*代码注入*攻击的通用攻击的具体示例。这些攻击旨在将攻击者编写的代码插入到 Web 应用程序开发人员创建的合法代码中。任何将用户提供的输入插入到应用程序开发人员编写的代码中的环境，都可能容易受到代码注入攻击。
