
图 6.3(a) 显示*相等*或*同一性*（例如，`A = B = {1,2}`）。在图 6.3(b)中，`A` 和 `B` 是*不相交*或*互斥*的；即它们没有共同成员（例如，`A = {1}`，`B = {2}`）。在图 6.3(c)中，`A` 是 `B` 的*子集*（等价地，`B` 是 `A` 的超集）。在图 6.3(d)中，`A` 是 `B` 的*真子集*（因此 `B` 是 `A` 的真超集）。例如，`A = {1}`，`B = {1, 2}` 和 `A = {1}`，`B = {1}` 都是子集关系的实例，但只有前者是真子集关系的实例。图 6.3(e) 显示*重叠*：集合有一些共同成员。图 6.3(f) 显示*真重叠*：集合既有共同成员又有额外成员。例如，`A = {1, 2}`，`B = {2,3}` 和 `A = {1}`，`B = {1, 2}` 都是重叠的实例，但只有前者是真重叠的情况。

#### 集合形成运算

现在让我们考虑**集合形成运算**，其结果是一个集合。给定任意集合 `A` 和 `B`，我们定义 `A ∪ B`（即 `A` 并 `B`）为 `A` 或 `B` 中所有元素的集合，这里的“或”指包含性或。`A ∩ B`（即 `A` 交 `B`）是 `A` 和 `B` 共有的所有元素的集合。这些运算中的每一个都是可交换的，因此操作数的顺序无关紧要。即 `A ∪ B = B ∪ A` 且 `A ∩ B = B ∩ A`。

**集合差集**（或相对补集）运算定义如下：`A − B`（即 A 减 B）是属于 `A` 但不属于 `B` 的所有元素的集合。该运算不可交换（即可能出现 `A − B ≠ B − A` 的情况）。如果令 U = **全集**（即考虑范围内的所有元素的集合），我们定义 `A` 的**补集**为 `A′ = U − A`。`A` 和 `B` 的**对称差集**是仅属于 `A` 或 `B` 中的一个的元素集合（即并集减去交集）。

最重要的三个集合形成运算是并集、交集和差集。这些通过**文氏图**在图 6.4 中描绘，以其发明者、英国逻辑学家约翰·文（John Venn，1834–1923 年）命名。在这里，阴影表示运算的结果。

## 6.3 值约束与独立类型

图 6.4 三种集合形成操作的 Venn 图。

与 Euler 图不同，Venn 图椭圆总是重叠。与 HED 类似，Venn 图采用假设视角。作为这些操作的示例，如果 `A = {1, 2}` 且 `B = {2, 4}`，则 `A ∪ B = {1, 2, 4}`，`A ∩ B = {2}`，`A − B = {1}`，且 `B − A = {4}`。

Venn 图有时用于讨论两个集合之间的比较。例如，图 6.5(a) 使用线填充和“*”分别表示空区域和非空区域，指示 `A ⊂ B`。然而，一旦集合数量超过三个，Venn 图就会变得极其难以驾驭——请考虑 图 6.5(b) 中四个集合的 Venn 图。Euler 图有类似的可扩展性问题。第 6.5 节 引入了一种用于绘制子类型连接的有向图表示法，它能够关联许多兼容的对象类型，而不会产生 Euler 图和 Venn 图在这类情况下的线条交叉混乱。

![图 6.5 (a) A 是 B 的真子集，以及 (b) 四个集合的 Venn 图。](img/f06-05-9780443237904.jpg)

图 6.5 (a) A 是 B 的真子集，以及 (b) 四个集合的 Venn 图。

**值约束** 指示值类型或角色中允许的值，有时称为“域约束”。只有当值列表至少相当 *稳定* 时，才应声明值约束；否则，随着值列表的变化，我们将需要不断更改约束，从而更改模式。

值类型可以通过将其外延（可能值的集合）声明为一个或多个用大括号（花括号）括起来的枚举或范围来定义。在模式图上，*对象类型值约束* 通过在值类型本身或由该值类型引用的实体类型旁边显示外延来声明。

图 6.6 显示了几个示例。如果我们列出或枚举所有可能的值，这就是一个 *枚举*，如 图 6.6(a) 所示。如果这些值可以从第一个到最后一个按连续列表（无间隙）排序，我们只需在首尾值之间用“..”列出即可，因为我们知道如何填充中间值（见 图 6.6(b) 中的前两个示例）。这称为 *范围*。

![图 6.6 对象值约束列出值类型的可能值。](img/f06-06-9780443237904.jpg)

图 6.6 对象值约束列出值类型的可能值。

如果范围在一端是 *无界* 的，则该端不出现值。例如，如果我们以整年数来度量 Age，则值约束为 `{0..}`。默认情况下，范围假定为闭区间，因此包含端点值。例如，`{50..100}` 包括 50 和 100 以及它们之间的数字。*在起始值前插入左括号“(”可排除该值*，*在结束值后追加右括号“)”可排除该值*。如果需要，可使用方括号显式表示包含（默认情况）。例如，“`(0..100`”和“`(0..100]`”均表示大于 0 且小于等于 100 的正数范围。也可以将枚举和/或范围组合成单个约束，如 图 6.6(c) 所示。

如果值约束表达式较短，可在图上完整显示。如果值列表很长，我们可以在对象角色建模（ORM）工具中输入所有值，但选择仅显示部分前导值。尾部的省略号“…”则表示后续值的显示被抑制。例如，对于对象类型 WeekDay，我们可能指定值列表 `{"Sunday", "Monday", "Tuesday", "Wednesday", "Thursday", "Friday", "Saturday"}`，但选择仅显示前两个（见 图 6.7）。虽然列表在图上被压缩了，但需要时仍可完整以文本形式显示（例如，通过访问对象类型的属性表）。

![图 6.7 后续值的显示被抑制。](img/f06-07-9780443237904.jpg)

图 6.7 后续值的显示被抑制。

现在考虑 图 6.8，这是之前讨论的奥运会示例的修改版，连同 1988 年在韩国首尔举行的第 24 届夏季奥运会最终结果的样本数据（按国家按字母顺序排序）。对于此应用，仅允许三种奖牌：金、银、铜，分别用代码“G”、“S”和“B”表示。该约束通过在实体类型 MedalKind 旁列出可能值集合 `{"G", "S", "B"}` 来指定。

![图 6.8 为 MedalKind 和 Quantity 角色声明了值约束。](img/f06-08-9780443237904.jpg)

图 6.8 为 MedalKind 和 Quantity 角色声明了值约束。

在 1988 年奥运会上，共有 237 个项目，每个项目颁发一枚金、银、铜牌（假设无并列）。同一国家赢得某类奖牌的所有奖牌是可能的（尽管极不可能）。因此，此处 Quantity 所扮演的角色（我们可以将此角色命名为“奖牌种类数量”）的最大可能值为 237，假设我们将其他运动会（可能有更多项目）排除在域之外。

奖牌种类数量的最小可能值是多少？如果我们想记录某国家未赢得某类奖牌，则最低奖牌种类数量为 0。为减小数据库规模，我们可以仅存储实际获奖的事实——我们的样本数据建议采用这种方法。在这种情况下，奖牌种类数量的下限为 1。采取封闭世界假设，某国家赢得 0 枚金牌这一事实，则可从该国赢得一些金牌的断言事实不存在这一情况推导得出。因此，此值约束的值范围为 `{1..237}`。

由于 Quantity 很可能在全局模式中扮演其他角色，`{1..237}` 值约束仅适用于 Quantity 在该事实类型中的角色，而非 Quantity 本身。我们称之为 *角色值约束* 而非对象类型值约束。角色值约束通过虚线连接到其适用的角色上显示，如 图 6.8 中 `{1..237}` 所示。

另一种方法是引入更具体的对象类型（例如 MedalKindQuantity）并将值约束放在其上；然而，这种做法可能导致口语化表达别扭，因此角色值约束非常方便。

作为一个细节，显示在带有参照模式的实体类型旁边的对象值约束，实际上是值类型所扮演的参照角色上的角色值约束。在 NORMA 工具中，您可以通过将 `ExpandRefMode` 切换为 True 来以这种方式显式显示。

### 独立对象类型

在本例中，“Country”（国家）表示地球上所有国家的集合，或者可能仅指参加奥运会的国家。我们应该为 Country 或 Country 的角色添加值约束吗？这不切实际，因为国家名称列表太长（例如，161 个国家参加了 1988 年夏季奥运会）且不稳定（例如，1991 年前苏联解体为 15 个国家）。如果模式被复用于多届比赛，此值约束将需要持续更新。

由于国家列表既庞大又不稳定，我们不会将 `CountryName` 的值列表指定为*约束*（稍后我们将看到提供此类列表的另一种方式）。但是，我们可以声明一个语法*数据类型*作为“值约束”的一种弱形式。例如，我们可能要求每个国家名称最多为 30 个字符的字符串。

虽然选择语法数据类型不是建模中最具概念性或最令人兴奋的方面，但这是在实现模型之前必须完成的工作。否则，你将得到系统提供的任何默认数据类型，而这并不总是你想要的。

### 回答关于参赛情况的查询

现在假设我们的奥运会信息系统需要回答以下问题：*哪些国家参赛了？哪些国家没参赛？* 第一个问题可以通过向 图 6.8 中的 Country 添加一元谓词“competed”（参赛）来解决。然后，所有参赛国家都将被录入该一元事实类型的单列表中。或者，我们可以为每个未获得特定奖牌的参赛国家显式记录零值。

但第二个问题怎么办？这实际上是在问：哪些国家存在但未参赛？此列表通常很小，但也可能很大（例如，因抵制）。因此，我们需要一种方法来记录所有现存的国家，无论它们是否参赛。正如之前讨论的，将此国家列表放入约束中是不明智的，因为列表庞大且不稳定。虽然模式经常演变，但我们通常试图将其设计得尽可能稳定。一种经典策略是对特性进行建模，使变化发生在数据库填充中，而不是模式本身。我们如何在当前示例中做到这一点？

你可能想给 Country 添加一元谓词“exists”（存在）。但这种谓词将适用于模式中的所有对象类型。此外，将“exists”（存在量词）视为谓词在形式上存在问题。原则上，我们可以通过为 Country 添加另一个一元谓词“did not compete”（未参赛）并将非参赛国存储于此来解决该问题。但这种方法很别扭——Country 可能扮演多个角色（出生地、地点等），且任意否定其中某个角色以涵盖其余国家可能显得随意。

### 参考表与独立性

一种更简洁的方法是将所有现存国家列在 Country 的*参考表*中。一个国家可以出现在此表中，而不在模式中扮演任何基本事实角色。这样的国家被称为*独立*的，因为它在我们的模型中独立于做任何事情而存在。**独立实体类型**是指其基本事实角色（如果有）共同为可选的*基本实体类型*。一个*独立值类型*可能包含一些不参与任何事实（基本或存在性）的值。

“独立”一词不用于子类型。如果一个独立对象类型扮演某些事实角色，则其角色的析取不是强制的（无论是隐式还是显式）。

为了表示对象类型是独立的，在其名称后附加一个*感叹号*“!”。图 6.9 将 Country 描绘为独立的。其参考表列出了所有现存国家。为节省空间，仅列出前六个国家。第一项可以口头化为“名为‘Afghanistan’的 Country 存在”；这是一个参考或存在性事实。

![图 6.9 在此模式中，Country 是一个独立对象类型。](img/f06-09-9780443237904.jpg)

图 6.9 在此模式中，Country 是一个独立对象类型。

包含了零胜场数。三元事实类型中的第一个角色是可选的，因为有些国家不参赛（此处数据为�构）。如果排除零胜场（如图 6.8 所示）并添加一元谓词“competed”，则该角色与胜场角色的析取将是可选的（且将从胜场角色到参赛角色运行一个子集约束——子集约束稍后讨论）。因此，*隐含强制角色规则不适用于独立对象类型*。

独立实体类型的参考方案是强制的，因此除非某国家记录在 Country 的填充中，否则不得记录其参赛或获胜。用所有国家的列表完整填充 Country 是一项繁琐的任务；然而，一旦完成，可根据需要导入许多应用程序。实际上，大多数独立对象类型的实例较少。作为一个次要点，Quantity 角色上的值约束可能需要更新以适应更多事件。

如果我们不想了解不参赛的国家，则作为添加一元谓词“competed”的替代方案，我们可以将 Country 的含义限制为“参赛国家”，将其标记为独立，并仅记录非零胜场。

### 灵活性与 FCO-IM

使用独立对象类型或一元谓词代替值约束增加了灵活性，因为数据可以在不重新编译模式（以及相关窗体等）的情况下更改。然而，这种责任现在掌握在录入数据的人手中，而不是模式设计者手中。通常，此类参考表的写入权限仅授予数据库管理员。

一种称为完全面向通信的信息建模（FCO-IM）的荷兰版 ORM 将所有实体类型（无论是否独立）视为对象化谓词。例如，在图 6.12 中，实体类型 Country 被描绘为 CountryName 这一值类型所扮演角色的对象化。实体类型的概念随后可被视为派生构造，而非基础构造。
