
## The Text Record

The `Text (TXT) record` allows the domain owner to return arbitrary text.

These records can contain values that prove domain ownership, values that remote mail servers can use to authorize email, and entries to specify which IP addresses may send mail on behalf of the domain, among other uses.

Listing 2-7 shows the text records associated with `google.com`.

```text
$ dig google.com. txt
-- snip --
;QUESTION
google.com. IN TXT
;ANSWER
google.com. 299 IN TXT "facebook-domain-verification=22rm551cu4k0ab0bxsw536tlds4h95"
google.com. 299 IN TXT "docusign=05958488-4752-4ef2-95eb-aa7ba8a3bd0e"
google.com. 299 IN TXT "v=spf1 include:_spf.google.com ~all"
google.com. 299 IN TXT "globalsign-smime-dv=CDYX+XFHUw2wml6/Gb8+59BsH31KzUr6c1l2BPvqKX8="
-- snip --
```

*Listing 2-7: DNS answer of the google.com TXT resource records*

The domain queries and answers should start to look familiar by now. The last field in a TXT record is a string of the TXT record value 1. In this example, the field has a Facebook verification key, which proves to Facebook that Google’s corporate Facebook account is who they say they are and has the authority to make changes to Google’s content on Facebook. It also contains `Sender Policy Framework` rules 2, which inform remote mail servers which IP addresses may deliver email on Google’s behalf.

> **NOTE** The Facebook for Developers site has more information about domain verification at <https://developers.facebook.com/docs/sharing/domain-verification/>.

## Multicast DNS

`Multicast DNS` (*mDNS*) is a protocol that facilitates name resolution over a local area network (LAN) in the absence of a DNS server. When a node wants to resolve a domain name to an IP address, it will send a request to an IP multicast group. Nodes listening to the group receive the query, and the node with the requested domain name responds to the IP multicast group with its IP address. You may have used mDNS the last time you searched for and configured a network printer on your computer.

## Privacy and Security Considerations of DNS Queries

DNS traffic is typically unencrypted when it traverses the internet. A potential exception occurs if you’re connected to a virtual private network (VPN) and are careful to make sure all DNS traffic passes through its encrypted tunnel. Because of DNS’s unencrypted transport, unscrupulous ISPs or intermediate providers may glean sensitive information in your DNS queries and share those details with third parties. You can make a point of visiting HTTPS-only websites, but your DNS queries may betray your otherwise secure browsing habits and allow the DNS server’s administrators to glean the sites you visit.

Security is also a concern with plaintext DNS traffic. An attacker could convince your web browser to visit a malicious website by inserting a response to your DNS query. Considering the difficulty of pulling off such an attack, it’s not an attack you’re likely to experience, but it’s concerning nonetheless. Since DNS servers often cache responses, this attack usually takes place between your device and the DNS server it’s configured to use. RFC 7626 (<https://tools.ietf.org/html/rfc7626/>) covers these topics in more detail.

## Domain Name System Security Extensions

Generally, you can ensure the authenticity of data sent over a network in two ways: authenticating the content and authenticating the channel.

`Domain Name System Security Extensions` (*DNSSEC*) is a method to prevent the covert modification of DNS responses in transit by using digital signatures to authenticate the response. DNSSEC ensures the authenticity of data by authenticating the content. DNS 服务器对资源记录进行加密签名，并使这些签名可供你使用。你可以验证来自权威 DNS 服务器的响应是否与签名一致，以确保响应不是欺诈性的。

DNSSEC 不解决隐私问题。DNSSEC 查询仍然会在网络中以未加密的方式传输，从而允许被动观察。

## DNS over TLS

`DNS over TLS (DoT)`，详见 RFC 7858 (<https://tools.ietf.org/html/rfc7858/>)，通过使用 `Transport Layer Security` (`TLS`) 在客户端和其 DNS 服务器之间建立加密连接，解决了安全和隐私问题。TLS 是一种常用的协议，用于在网络节点之间提供加密安全的通信。使用 TLS 后，DNS 请求和响应在传输过程中完全加密，攻击者无法窃听或篡改响应。DoT 通过验证通道的真实性来确保数据的真实性，无需像 DNSSEC 那样依赖于数字签名，因为整个 DNS 服务器与客户端之间的通信均已加密。

DoT 使用的网络端口与常规 DNS 流量不同。

## DNS over HTTPS

`DNS over HTTPS (DoH)`，详见 RFC 8484 (<https://tools.ietf.org/html/rfc8484/>)，旨在在广泛使用的 TCP 端口上解决 DNS 安全和隐私问题。与 DoT 类似，DoH 通过加密连接发送数据并验证通道的真实性。DoH 使用常见端口，并将 DNS 请求和响应映射为 HTTP 请求和响应。通过 HTTP 传输的查询可以利用 HTTP 的所有特性，如缓存、压缩、代理和重定向。

## PART II: SOCKET-LEVEL PROGRAMMING

### 3 RELIABLE TCP DATA STREAMS

TCP 允许你可靠地在网络节点之间流式传输数据。本章深入探讨该协议，重点关注通过我们编写的代码来建立 TCP 连接并通过这些连接传输数据的各个方面。这些知识将帮助你调试程序中的网络相关问题。

我们首先介绍 TCP 握手过程、序列号、确认、重传以及其他特性。随后，我们在 Go 中实现 TCP 会话的步骤，从建立、监听、接受到会话终止。接着讨论超时和临时错误，如何检测它们以及如何利用它们保持用户满意。最后，我们将讲解不可靠网络连接的早期检测。Go 标准库让你能够编写稳健的基于 TCP 的网络应用，但它不会手把手地帮助你；如果不注意处理 incoming data 或正确关闭连接，你会在程序中遇到隐蔽的错误。

#### What Makes TCP Reliable?

TCP 之所以可靠，是因为它克服了数据包丢失或按顺序接收的问题。`Packet loss` 发生在数据未能到达目的地时，通常是由于传输错误（如无线网络干扰）或网络拥塞导致的。`Network congestion` 发生在节点尝试发送的数据量超过连接容量时，导致节点丢弃多余的数据包。

例如，你不能在 10 Mbps 的连接上以 1 Gbps 的速率发送数据。10 Mbps 连接会迅速饱和，参与数据流的节点会丢弃超出其容量的数据。

TCP 会根据网络状况调整数据传输速率，使其在尽可能快的速度发送数据的同时尽量减少丢包，即使网络条件发生变化（例如 Wi-Fi 信号减弱或目的节点因数据量过大而被淹没）。这一过程称为 `flow control`，它尽力弥补底层网络介质的不足。

TCP 无法在差网络上传输高质量数据，它受限于网络硬件。

TCP 还会跟踪已收到的数据包，并在必要时重新传输未确认的数据包。接收端也可能收到乱序的数据包，例如在传输过程中数据被重新路由。请回顾第 2 章（`#index_split_000.html#p39`）中提到的，路由协议使用度量值决定数据包的路由方式，这些度量值会随网络状况变化。在 TCP 会话期间，你无法保证所有发送的数据包都走相同的路径。好在 TCP 会对乱序数据包进行组织并按顺序处理。

结合流控和重传，这些特性使得 TCP 能够克服数据包丢失并保证数据成功送达接收端。因此，你无需担心这些错误，只需专注于发送和接收的数据。

#### Working with TCP Sessions

一个 `TCP session` 使你能够向接收端发送任意大小的数据流并获得接收端已成功接收数据的确认。这避免了大量数据在网络中传输后才发现接收端未收到的低效情况。

正如人们偶尔点头表示在倾听说话者，流式传输让你在传输进行过程中即时收到接收端的反馈，从而能够实时纠正错误。事实上，你可以把 TCP 会话看作是两个节点之间的对话：先有问候，接着是对话，最后是告别。

在讨论 TCP 的具体细节时，我想让你明白 Go 会帮你处理实现细节。你的代码会利用 `net` 包的接口来使用 TCP 连接。

#### Establishing a Session with the TCP Handshake

TCP 连接使用三次握手来介绍客户端和服务器，并建立会话。图 3-1 展示了握手过程中发送的三条消息。

```text
Client                            Server
  |  Dial                         |  Listen
  |                               |  Accept
  |----------- SYN -------------->|
  |<-------- SYN/ACK -------------|
  |----------- ACK -------------->|
  |  Established                  |  Established
```

*Figure 3-1: The three-way handshake process leading to an established TCP session*

在建立 TCP 会话之前，服务器必须先监听 incoming connections。（本章使用 `server` 表示监听节点，`client` 表示发起节点，尽管 TCP 本身没有明确的客户端和服务器概念，但一个节点主动向另一个节点发起会话。）

握手的第一步，客户端发送带有 `synchronize (SYN)` 标志的数据包给服务器。该 SYN 包告知服务器客户端的能力以及后续通信的首选窗口设置。我们稍后会讨论接收窗口。接下来，服务器回复一个带有 `acknowledgment (ACK)` 和 `SYN` 标志的数据包。`ACK` 标志告诉客户端服务器已收到它的 SYN 包；服务器的 SYN 包则告知客户端它已同意的会话参数。最后，客户端发送 `ACK` 完成握手。

回复服务器的 SYN 包，发送 ACK 包确认，完成三次握手。

三次握手过程完成后，建立 TCP 会话，双方即可交换数据。TCP 会话保持空闲，直到任一端有数据需要传输。未管理的、持续时间较长的空闲 TCP 会话会导致内存的浪费。本章后面会介绍如何在代码中管理空闲连接。

在代码中发起连接时，Go 会返回一个连接对象或错误。如果收到连接对象，则说明三次握手成功。你无需自行管理握手过程。

#### 使用序列号确认收到数据包

每个 TCP 数据包都包含 `序列号`，接收端使用该序列号确认已收到数据包，并按顺序排列，以便向 Go 应用程序呈现（见图 3-2）。

```text
客户端                             服务器
  |--- SYN (Seq = X) ------------>|
  |                               | 已收到，客户端 Seq = X
  |<-- SYN (Seq = Y), ACK (Seq = X + 1) --|
  |                               | 已收到，服务器 Seq = Y
  |--- ACK (Seq = Y + 1) -------->|
```

*图 3-2：客户端和服务器交换序列号*

客户端操作系统确定初始序列号（图 3-2 中的 `X`），并在握手时将其封装在 SYN 包中发送给服务器。服务器在其 ACK 包中包含该序列号，以确认已收到该数据包。同样，服务器在其 SYN 包中发送自己生成的序列号 `Y` 给客户端，客户端随后回复 ACK。

ACK 包使用序列号告知发送方：“我已收到并包括该序列号的数据包在内的所有数据包”。一个 ACK 包可以确认发送方的一个或多个数据包。发送方利用 ACK 包中的序列号判断是否需要重新传输数据包。例如，若发送方发送了序列号一直到 100 的多个数据包，随后收到序列号为 90 的 ACK，发送方知道需要重新传输序列号 91 到 100 的数据包。

在编写和调试网络程序时，常需要查看代码发送和接收的流量。为了捕获并检查 TCP 数据包，强烈建议你熟悉 Wireshark（<https://www.wireshark.org/>）。该工具能极大帮助你理解代码如何影响网络数据的传输。

如需进一步学习，可参考 *Practical Packet Analysis*，第 3 版，作者 Chris Sanders（No Starch，2017）。
