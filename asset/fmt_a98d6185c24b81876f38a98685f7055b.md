
CountryName 在 Country has CountryName 中的角色的唯一性约束可声明如下：

```
ic (c1, c2, n) requires (hasCountryName(c1,n) and hasCountryName(c2,n) implies c1 = c2
```

假设三元事实类型已声明，其复合唯一性约束可声明如下：

```
ic (c, y, p1, p2) requires (inYearHadPopulation(c, y, p1) and inYearHadPopulation(c, y, p2)) implies p1 = p2
```

State 的复合参考方案中的外部唯一性约束可声明如下：

```
ic (s1, s2, c, sc) requires (isInCountry(s1,c) and hasStateName(s1,sc) and isInCountry(s2,c) and hasStateName(s2,sc)) implies s1 = s2
```

图 17.18 中的 ORM 模式包含其他几种约束。示例 (a) 中的包含或约束确保每个求职者要么合格，要么有推荐人（或两者皆有）。这可在 `Rel` 中表示为：

![图 17.18 更多约束。](img/f17-18-9780443237904.jpg)

图 17.18 更多约束。

```
ic (p) requires JobApplicant(p) implies (isQualified(p) or hasaReference(p))
```

示例 (b) 中的排他或约束确保我们太阳系中的每颗行星要么是内行星，要么是外行星，但不能两者皆是。这可在 `Rel` 中表示为：

```
ic (p) requires Planet(p) implies (isAnInnerPlanet(p) xor isAnOuterPlanet(p))
```

示例 (c) 中的值约束限制底层引用类型 Gender has GenderCode 中 GenderCode 的值。示例 (d) 中的值约束将 IQ 值限制在 0..300 范围内。这些约束可制定如下：

```
ic (g, gc) requires hasGenderCode(g,gc) implies (gc = “M” or gc = “F”)
ic (x, y) requires hasIQNr(x,y) implies (x >= 0 and x <=300)
```

示例 (e) 和 (f) 中的排除约束规定：没有人可以同时撰写和评审同一本书；没有人可以评审由在同一所大学任教的人撰写的论文。图 (f) 中关于连接路径上的排除约束的图表是 NORMA 工具的屏幕截图。这些约束可制定如下：

```
ic (p, b) requires reviews(p, b) implies not authors(p, b)
ic (p1, p2, u, pr) requires (authors(p1, pr) and lecturesAt(p1, u) and reviews(p2, pr)) implies not lecturesAt(p2,u)
```

图 17.19 中的 ORM 模式包含更多约束。示例 (a) 中的等值约束确保患者有舒张压读数当且仅当患者有收缩压读数。这可在 `Rel` 中使用匿名变量表示如下：

![图 17.19 一些等值和频率约束。](img/f17-19-9780443237904.jpg)

图 17.19 一些等值和频率约束。

```
ic (p) requires hasDiastolicBP(p, _) iff hasSystolicBP(p,_)
```

示例 (b) 中的内部频率约束确保每个评审人最多被分配三篇论文进行评审。可制定如下：

```
ic (r, n) requires isAssignedNrPapers(r, n) implies n <= 3
```

示例 (c) 中的复合频率约束确保没有学生可以在同一课程中注册超过两次。这可制定如下。此处，“def” 前置 `inCourseHasNrEnrollments` 关系的定义或推导规则，该规则使用内置的 `count` 函数。该约束利用了派生的三元关系。

##### 示例代码

```
def inCourseHasNrEnrollments(s, c, n): n = count[(e): isanEnrollmentByStudent(s, e) and isanEnrollmentInCourse(e, c)]
ic (s, c, n) requires inCourseHasNrEnrollments(s, c, n) implies n <= 2
```

示例 (d) 中的外部频率约束确保对于每个国家，其政府成员中同时担任共治者的政治家最多有两位。此约束可使用 count 函数制定，也可简单地这样表述：

```
ic (p1, p2, p3, c) requires (isaCoregent(p1) and servesOnGovtOf(p1, c) and isaCoregent(p2) and servesOnGovtOf(p2, c) and isaCoregent(p3) and servesOnGovtOf(p3, c)) implies p1 = p2 or p1 = p3 or p2 = p3
```

环约束 在 `Rel` 中很容易指定。人认识他们自己的自反环约束可表达为：`ic(p) requires Person(p) implies knows(p, p)`。没有人是其自己的父母这一非自反环约束可表达为：`ic (p) requires not isaParentOf(p, p)`。兄弟姐妹关系的对称约束可这样指定：`ic (p1, p2) requires isaSiblingOf(p1, p2) implies isaSiblingOf(p2, p1)`。没有人是其自己父母这一非对称环约束可这样表达：`ic (p1, p2) requires isaParentOf(p1, p2) implies not isaParentOf(p2, p1)`。

`isOlderThan` 关系的传递性质可按如下方式制定：`ic (p1, p2, p3) requires (isOlderThan(p1, p2) and isOlderThan(p2, p3)) implies isOlderThan(p1, p3)`。直接优先关系的非传递约束可按如下方式制定：`ic (e1, e2, e3) requires (directlyPrecedes(e1, e2) and directlyPrecedes(e2, e3)) implies not directlyPrecedes(e1, e3)`。

祖先关系可按如下方式定义：`def isanAncestorOf(p1, p2): isaParentOf(p1, p2) or isaParentOf(p1, p3) and isanAncestorOf(p3, p2)`。祖先关系的无环约束可这样指定：`ic (p) requires not isanAncestorOf(p, p)`。

图 17.20(a) 中的成对子集约束确保每个通过课程的学生也选修了该课程。这在 `Rel` 中可表达为：`ic (s, c) requires passedCourse(s, c) implies enrolledInCourse(s, c)`。

图 17.20 中的连接路径上的子集约束确保每个在某国任职的顾问必须至少会说该国使用的一种语言。此约束可按如下方式表达：

![图 17.20 一些子集约束。](img/f17-20-9780443237904.jpg)

图 17.20 一些子集约束。

```
ic (a, c) requires servesInCountry(a, c) implies (speaksLanguage(a, l) and isaLanguageUsedBy(l, c))
```

这些简单示例展示了 `Rel` 在建模 ORM 约束方面的表达能力。大型、高度复杂的 ORM 模型也可映射为 `Rel` 结构。

### 其他数据库种类

有时会调用专用数据库种类来处理特定类型的应用。空间数据库 需要对空间数据进行高效管理，例如地图（道路、土地等）、二维设计（电路、城镇规划等）和三维设计（医疗手术可视化、分子结构、飞行路径等）。它们为空间数据类型（点、线、多边形等）、空间操作符（重叠、包含、相交等）和空间索引（R 树、四叉树等）提供内置支持。这允许高效地构建和处理空间查询，例如：拟建购物中心 5 公里范围内有多少房屋？哪些航班飞越大洛杉矶地区？哪些图表与图表 37 相似？

以前，空间数据使用专用系统，而字母数字数据使用关系 DBMS。当前的趋势是在一个系统中同时管理标准数据和空间数据。地理信息系统 (GIS) 的典型应用可能按如下方式进行：输入交通事故的标准数据；显示道路地图以突出事故地点；然后用于确定需要采取额外预防措施的区域（例如雷达测速陷阱）。

历史上，GIS 厂商采用了三种主要方法：混合式（空间文件存储中的地理关系对象被赋予可在关系表中引用的标识符）；集成式（空间和非空间数据存储在关系表中）；面向对象（所有数据存储在 ODB 中）。最近，许多空间数据库应用以及其他使用非标准数据的应用已使用对象关系技术实现。

虽然时间只有一个维度，不像空间有三个维度，但时间信息的高效管理并非易事。如果需要维护关于对象的历史记录而非快照记录，时间将在建模中占据重要地位。

正如第 10 章所讨论的，建模时间可采用多种方法。在某些情况下，我们只需在概念模式中包含 Time 和 Period 等对象类型，并像映射其他对象类型一样映射它们。可能需要区分事务时间（系统记录事实的时间）和有效时间（事实在被建模的 UoD 中为真的时间）。通常，我们需要利用时间关系（如前、后）和时间操作（例如计算两个时间点之间的间隔）。

SQL 标准目前仅包含对时间数据的基本支持，有时普通关系数据库无法高效实现时间方面的功能。对于此类应用，有时会使用称为“时间数据库系统”的专用 DBMS；这些系统为自动时间戳和各种时间操作符提供内置支持。

大多数时间数据库的工作侧重于随时间维护应用对象的相关历史，前提是概念模式本身是固定的。上升一层，如果我们允许概念模式本身随时间变化，问题会变得更复杂。这是模式演化问题的一个方面。

再上升一层，我们可能允许概念元模式本身随时间变化（例如，我们可能在后期决定允许在概念模式语言中使用复杂对象类型的构造器）。此类高阶演化的管理已在不断演化的信息系统研究中得到解决。这一主题为第 18 章中关于元建模的讨论提供了一个动机。

本章前面讨论了集中式和分布式数据库。联邦数据库 提供了另一个维度。它们处理在几个不同的数据库系统之间（可能是异构的，例如有的关系型、有的列式、有的键值型等）需要共享数据的情况。在此框架中，每个单独的系统保持其局部自主性，并按需与其他系统通信。由于异构性问题要求在不同数据模型之间进行转换，联邦系统的控制是非同小可的。

云计算的出现加速了对联邦数据库的兴趣。大多数组织发现管理一组异构数据库可能是一场噩梦，但通过将功能外包给云服务提供商，这可以大大缓解。通常提供三级服务：

基础设施即服务 提供基于专用或虚拟硬件的基本处理、存储和网络功能。这本质上是在云服务中复制了一个内部数据中心。用户仍负责标准管理功能。

### 平台即服务

平台即服务 将管理基础设施资源的责任转移给云服务提供商。用户无需再担心操作系统更新、硬件维护等问题。可以从服务提供商处轻松且增量地获取额外容量，使用户能够专注于安装和维护应用程序。

### 软件即服务

软件即服务 包含前述所有功能，同时也承担了软件应用程序的责任，包括许可、软件更新等。在这种情况下，云服务提供商控制应用程序，用户只需为访问权限付费。

### 基于云的方法

基于云的方法开启了其他几个重要的可能性。其中之一是无服务器数据库的概念。数据库可以按常规方式定义，但服务器硬件被融合进广泛的云能力中。这提供了在服务器上安装传统数据库的所有功能，外加一些额外优势。这些优势包括更强的弹性、自动扩展以满足需求、更简单的资源管理以及按需付费的定价模式。

#### 数据湖

组织通常在数据仓库中存储大量数据，以便进行后续处理。在云环境下，这一概念可扩展为数据湖。该名称源于一个类比：一湖未经处理的水，可随时取用并以各种方式处理，使其适合饮用。数据湖是一个存储库，用于以原始“原始”形式存储大量数据。这与数据仓库不同，因为它没有模式，任何必要的模式都可根据待满足的需求按需创建。可使用软件工具开发必要的功能，例如从数据湖中的 CSV 文件和电子表格创建新的 SQL 数据库。

#### 文件格式

已创建多种文件格式以适应特定条件，未来无疑还会定义更多。Avro 是一种面向行的格式示例，适用于压缩数据。文件中的每条记录包含二进制数据以及一个定义如何解析二进制数据以提取各个字段的 JSON 头部。Parquet 是一种面向列的格式示例，适用于包含嵌套值的大型数据集。同一列的值存储在一起，并组织成行组以实现高效处理。同样，文件包含元数据以便高效定位数据。

#### 低代码开发

通过低代码开发，在云环境中创建数据库变得轻而易举。创建者无需编写代码（可能是 SQL）来定义结构，只需从一系列选项中选择即可。构建必要结构的详细操作可实现自动化并对用户隐藏。有用的字段，如创建记录的用户、最后修改日期等，可自动添加到表中。这种方法的一个例子是 Microsoft Dataverse，它是一个基于云的数据平台。它允许用户使用 Microsoft 的 Power Platform 工具创建数据相关应用程序，而无需技术知识。

#### 数据库中的 XML 和 JSON

正如第 16 章所述，XML 和 JSON 是支持以系统化方法描述结构化数据的表示法，两者都有可能为数据库系统提供基础。正如我们已经看到的，JSON 提供了文档数据库方法的基础。已经开发出一些 XML 数据库 的示例，但这些并未被广泛采用。XML 的通用用法是单个 XML 文档的形式，特别是用于不同系统之间结构化数据的交换。XML 现在作为一种数据类型被包含在 SQL 中，XML 数据的处理可以在关系框架内进行，降低了专门为 XML 而设的独立数据库的吸引力。

虽然 XML 和 JSON 都是文本表示法，但文本不太适合人类直观地查看业务领域的信息。在这两种情况下，最好先使用 ORM 等高级语言进行建模，然后将模型映射到所需的低级表示法来开发模式。关于将 ORM 映射到 XML 模式的讨论，请参阅 Bird et al. (2000)。

### 人工智能

自 20 世纪 50 年代首次提出该术语以来，人工智能 (AI) 一直被宣传为一项可能彻底改变技术的突破。早期的 AI 方法主要基于这样一种观点：知识可以用逻辑表达式来表示，通过系统化的过程使用数据值。尽管报告了一些成功案例，但构建此类系统被证明很困难，且生成的系统通常不够健壮，无法处理现实世界的数据。

20 世纪 90 年代，关注点开始转向“连接主义”方法。系统不再通过以人为中心的数据分析来识别逻辑关系，而是在应用领域的数据上进行训练。这开发出了训练数据中模式的内部模型，随后可部署到新数据上。这种方法的一个特点是，可能不容易解释系统是如何得出特定结果的。但这与人类的运作方式并无不同。例如，大多数语言的母语使用者能产生语法正确的结果，即使该人无法解释所遵循的语法“规则”。

当这些想法应用于超大型数据集时，发生了一次重大飞跃。这为健壮性问题提供了解决方案：如何应对各种各样的情况。不再是费力地试图分析可能出现的每一种情况，超大型数据集可以包含可能出现的所有情况的示例。复杂的学习算法可应用于数据，以构建一种有时被称为“通用 AI”的能力。所需的大量计算由超大型数据库（包括本章前面讨论的类型）和专用处理器支持，以高效地执行许多重复操作。

尽管通用 AI 潜力巨大，但它尚未成为数据库创建和管理的常规功能。所有主要供应商除许多专注于特定功能的初创公司外，都在大力投资其应用。在此，我们将仅限于描述 AI 具有明显相关性的一些领域，在某些情况下已开始应用。

#### AI 应用领域

**模式设计**。根据给定领域的自然语言描述生成初始模式设计。在关系型情况下，可强制执行严格的规范化。

**查询设计**。针对给定的数据库类型和模式，用适当的技术语言编写查询，以返回用自然语言表达的结果。

**应用设计**。根据给定的数据库模式，为用自然语言描述的应用程序生成设计。这可能包括桌面端和移动端两种变体。

**数据库管理**。 自动化数据库管理员 (DBA) 通常执行的例行操作。这些任务可包括索引创建和更新、针对不断变化的使用情况的查询调优、性能评估和优化等。

**数据清洗**。历史数据常因原始数据采集的相关问题而备受困扰，这些问题会阻碍后续分析。通过典型问题的训练可用于避免或修复这些问题。

**代码创建**。可根据非技术语言的意图描述，生成技术代码（采用某种给定语言）。这已在某些开发环境中作为“副驾驶”功能投入运行。

**模式迁移**。随着数据库用途的演变，可能会发现最初设想的模式不再合适。迁移到备选模式是一个复杂的过程，可以通过自动化来辅助。

**高级分析**。数据中与业务相关的信息可以被处理，以发现通过传统查询不易察觉的模式和趋势。

上述提到的各类 AI 应用通常依赖于对提示词的响应，该提示词定义了 AI 所需的关注焦点。创建合适的提示词目前是一项技能，但这项技能本身必然会随着时间的推移而变得适合由 AI 来完成。有一个领域是 AI 无法确定的，即什么与用户相关或不相关（在 ORM 上下文中常被称为 `UoD`），以及用户对 `UoD` 中对象如何关联的看法。在某种意义上，`UoD` 可被视为终极提示词，它无法简化为其他任何事物，也无法在没有用户知识的情况下定义。显然，AI 代理必须理解 `UoD` 才能有效工作，但该信息如何提供？一个显而易见的解决方案是由 `ORM` 模式提供。当然可以通过非正式论述来描述 `UoD`，但这类描述饱受众所周知的歧义之苦。创建 `ORM` 模式有时对企业来说是一个痛苦的过程（内部政治、方向不明等），但最终的回报是对业务意图的明确描述。一旦被企业采纳，它就可作为后续 AI 处理许多方面的基础。
