## 结果沟通

我们讨论了许多回归和分类的指标；然而，在与业务部门或利益相关者沟通时，这些指标并不总是对利益相关者具有业务意义。此外，你的模型生成的输出对终端用户可能没有直接的实用价值。举个例子来说，你训练了一个预测房价的模型，并且它能够准确地做到这一点。但对于销售代理来说，他们可能感兴趣的是影响价格的因素；例如，房屋的位置、建筑商详情等。同时，基于即将开展的项目房价预测可以被开发商用于锁定合适的目标客户群体。通过这种方式，同一个模型可以被不同的相关者以不同的方式消费，因此根据要求沟通结果至关重要。

另一个例子是客户流失问题，我们预测客户流失的概率。在每个与客户打交道的业务中，由于各种原因总会产生流失。因此，对于营销人员来说，他们想了解利润率最高的客户（这可能是其他机器学习模型的结果），并且他们想尝试阻止这些客户流失。同时，并不是每个客户都能被阻止流失，因此这应该是流失概率和盈利能力之间的最佳组合。

上述示例只是为了说明，训练一个良好的机器学习模型只是其中之一，人们需要理解利益相关者并据此沟通结果。这可能涉及整合多个模型，或仅分享部分结果。最终目标始终应该是基于所分享的洞察产生某些可操作的结果。

## 注意事项

- 性能指标应该根据手头的问题和数据进行选择。
- 向利益相关者沟通机器学习模型的性能是机器学习项目成功的关键。
- 将机器学习模型的性能与业务目标相关联可以使利益相关者的达成更加一致。
- 指标能够对同一个问题的多个机器学习模型进行比较。

# 第 8 章：特征存储 (Feature Store)

在之前的章节中，我们涵盖了机器学习模型的训练和测试，以及衡量模型性能的 KPI。我们还看到数据很少以可以直接被机器学习算法消费的格式。为了将数据准备成可消费的格式，我们需要从原始数据中提取特征。特征工程还涉及将业务知识嵌入数据中，这是一项创造性任务，并且不断演进。特征工程是机器学习训练中最耗时的任务之一，它涉及数据科学家与不同的利益相关者合作，从数据中提取出有用的特征。

在组织中，同时有多个机器学习项目在进行，负责这些项目的数据科学家处于孤立工作状态。由于很多时候特征工程的工作是重复的。为了避免这种情况，建立一个中央仓库是一个好主意，其中存储所有创建的特征，任何需要训练的机器学习模型都应该从特征存储获取特征。另一个用途是为评分模型提供现成的新数据，同时保持一致性。

我们将在本章介绍 `Feast`，这是一个用于管理和提供模型训练及推理特征的开源特征存储。`Feast` 由 Google 和 Gojek 创建。我们将介绍 `Feast` 以及相关的最佳实践。

- `Feast`

## 概述

在企业层面，许多问题将机器学习作为解决方案不可或缺的一部分。在训练和推理时，机器学习模型需要相同的特征集；通常在模型确定到准备好推理之间存在巨大的延迟。大多数情况下，这是由于为了获取持续预测而创建了与训练相同的数据流水线。特征存储解决的问题之一是在新数据方面从训练到推理的平滑过渡。

另一个挑战是大量的重复工作，并且没有单一的地方可以查看为特定实体创建的特征。这导致了工作的浪费，有时会导致信息的丢失。这是特征存储试图通过为特定实体（如客户、产品等）建立集中仓库来解决的另一个问题。

`Feast` 通过提供一致的数据访问和实时（point-in-time correct）的数据来尝试解决所有问题。`Feast` 还允许特征的可重用，并使新特征的部署变得顺畅。我们将在后续章节中介绍 `Feast` 架构以及如何使用 `Feast` 创建特征仓库。

## 实体 (Entity)

实体类似于主键，特征从多个特征视图中聚合此处。在我们的案例中，`CustomerID` 是我们需要创建的实体，因为所有特征都是针对由该标识标识的单个客户。要创建实体，我们将使用以下代码：

```python
## 为 Customer 定义一个实体。
customer = Entity(
  # 实体的名称。必须在项目内是唯一的
  Name = "CustID",
  # 实体的连接键描述了可以查找特性的存储层字段/列。
  # 连接键在构建特征向量时也用于连接特征表/视图
  join_key = "CustomerID",
  # 实体的存储层类型
  value_type = ValueType.STRING,
)
```

在此段代码中，我们正在创建一个实体，我们给实体的 `Name` 是名称，而 `join_key` 是用于查找该实体的源表。你可以为实体提供任何喜欢的名称，但要确保在特征视图中正确使用该名称。`value_type` 是实体对应的数据类型。根据业务问题，实体可以是多个键的组合，例如 `CustomerID` 和 `Department` 等。一旦创建了实体，下一步是创建数据源。

## 数据源 (Data source)

数据源定义为获取特征值的文件或表格。由于我们正在使用 GCP，对于我们来说，源将是之前讨论过的 Bigquery 表格。在 feast 中创建数据源，我们将使用以下代码：

```python
## 客户连接详情
cust_conn_details_source = BigQuerySource(
  # 可以在其中找到特性的 BigQuery 表
  table_ref="project_name.dataset.cust_conn_det",
  # 事件时间戳用于点点连接 (point-in-time joins) 
  # 并确保只返回 TTL（生存时间）范围内的特征
  event_timestamp_column="feature_creation_date",
  created_timestamp_column="record_creation_date",
)
```

我们在前面的代码中创建的连接是用于连接详情表的。我们提供了表格名称，如果你为表格指定了其他名称，则需要进行替换。`project_name` 和 `dataset` 名称应该替换为 GCP 项目和 Bigquery 数据集名称。这将形成源表名。

`event_timestamp_column` 有两个用途：一个用于对特征进行点点连接，另一个用于理解它在在线存储中应持有多少信息（在下一节中讨论）。对于我们的示例，我们在数据中使用 `feature_creation_date` 作为。

另一个日期列 `created_timestamp_column` 不是强制字段，但我们在案例中使用了它。它用于去重。

## 特征视图 (Feature view)

特征视图是实际存储数据的模式。离线数据用于训练，在线数据用于评分。以下代码重点突出了创建特征视图的方法：

```python
## 连接特征视图
cust_conn_fv = FeatureView(
  name="customer_conn_det",
  entities=["CustID"],
  ttl=timedelta(days=365),
  features=[
    Feature(name="Tenure"),
    Feature(name="PhoneService"),
    Feature(name="MultipleLines"),
    Feature(name="InternetService"),
    Feature(name="OnlineSecurity"),
    Feature(name="OnlineBackup"),
    Feature(name="DeviceProtection"),
    Feature(name="TechSupport"),
    Feature(name="StreamingTV"),
    Feature(name="StreamingMovies"),
  ],
  input=cust_conn_details_source,
)
```

`name` 是我们给特征视图的名称，`entities` 是该视图对应的实体，`ttl` 定义了生存时间。`features` 包含了特征列表，每个特征都有自己的名称。`input` 是该视图对应的数据源。

## 访问数据

我们从特征存储（feature store）中访问数据有两个目的：首先用于训练模型，其次用于新数据进行评分。我们需要使用 `feast` API 中的 `FeatureStore` 和 `RepoConfig` 模块来配置特征存储。测试 feastian 特征存储的代码在共享的 GitHub 链接 `test_feature_store.py` 脚本中。配置完成后，我们现在需要导入数据来训练模型。你还需要定义想要从特征存储中导入的特征，这可以配置为一个列表。命名规范例如，对于前一节中创建的特征视图中的 `Tenure` 特征，命名为 `customer_conn_det:Tenure`。
