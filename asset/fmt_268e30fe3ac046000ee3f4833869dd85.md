# 第 9 章：ICS 安全评估

## 简介

在上一章中，您了解了网络安全策略生成过程以及风险管理过程。回顾一下，在组织的网络资产已被识别和评估，且针对其的潜在漏洞和威胁已被识别后，制定网络安全计划的下一步是执行风险评估。

在威胁已被识别且风险已被量化后，流程中的下一步是对网络进行实际的漏洞测试，以确定其对这些威胁的易感程度。这是通过一个称为 **安全评估** 的过程来完成的。

在本章中，您将了解与规划和实施安全评估相关的常用术语、工具、技术和流程。这包括渗透测试（或称 **渗透测试**）的介绍，即针对网络（及其可能的管理和支持人员）进行测试，以达到风险识别的目的。

## 安全评估

在 IT 和 OT 网络环境中，安全评估涉及执行一系列练习，旨在定位组织网络和计算环境中的漏洞。然后，组织利用从评估中获得的结果来帮助评估其安全态势。这是在风险评估早期识别出的潜在威胁和漏洞得到验证的地方。

正如您稍后在本章中将看到的，有许多可用于实施安全评估的参考资料和指南。然而，所有这些方法论通常都遵循四阶段流程执行。

### 1. 发现阶段（识别）

识别企业或 OT 网络中正在使用的系统和流程。

1.  检查组织的网络安全实践。收集有关其网络安全策略、程序和实践的信息。此外，收集可能在关键数字资产（如计算机和网络设备）的网络安全中发挥作用的资源信息。
2.  识别待评估的资产。对每个已识别的关键资产执行初步后果分析，以确定如果该资产遭到破坏，对组织可能造成的后果。

### 2. 漏洞扫描阶段（评估）

紧随发现阶段之后，使用自动化工具搜索网络中的安全问题。

1.  对已识别的数字资产进行桌面推演审查和验证测试。这应包括物理检查以及电子测试（扫描已识别的关键资产）。

### 3. 漏洞评估阶段（缓解）

建立在发现阶段和漏洞扫描阶段的基础上，识别漏洞并验证组织因发现的漏洞而面临的风险敞口级别。评估结果生成的背景信息可用于帮助管理层了解其网络中风险的严重程度。

1.  实施易感性评估。利用桌面推演审查和验证测试的结果，评估每个关键资产遭受网络攻击的易感性。该阶段的产出是对每个 **关键数字资产 (CDA)** 总体易感性级别的估算。
2.  实施风险评估活动。重新评估初步后果分析，并结合易感性评估的结果，估算每个资产遭受网络攻击的风险。
3.  实施风险管理活动。这些活动包括识别和表征可实施的潜在新对策，以增强网络安全。
4.  将这些对策的收益与实施和运营这些对策的成本进行比较。
5.  识别具有成本效益的风险管理选项，并为管理层准备建议。

### 4. 报告阶段（预防）

使组织能够从潜在攻击者的角度全面审视其网络安全态势。组织可以利用报告中的建议来实施工具和流程，根据评估的威胁和漏洞降低其风险敞口。通常，安全评估报告将包含以下主题：

1.  执行摘要
2.  项目范围描述
3.  评估方法论描述
4.  信息安全优势
5.  网络漏洞
    *   开放的 TCP 端口
    *   开放的 UDP 端口
6.  网络修复建议

在这四个阶段中，安全评估应仔细调查 `ISA/IEC-62443-3-X` 系列功能安全评估中定义的 **工业自动化与控制系统 (IACS)** 安全七大基础要求的各个方面，列表如下：

*   访问控制
*   使用控制
*   系统完整性
*   数据保密性
*   受限数据流
*   及时响应事件
*   网络资源可用性

## ICS 设备测试

在 IT 网络环境中，有大量关于保护不同网络设备的信息可用。企业网络管理员和安全管理员通常非常清楚其网络中计算和连接设备的优势和潜在弱点。然而，在 ICS 网络环境中，这种情况尚未被证实。历史上，OT 网络设备被认为通过默默无闻以及缺乏与企业网络和互联网相关的外部攻击向量而保持安全。

数据通信已成为大多数 ICS 系统的重要组成部分。随着向基于以太网的网络迁移以构建其通信基础设施的趋势，OT 网络变得越来越容易受到网络安全威胁。

## 漏洞

目前，连接到组织 IT 网络的 ICS 和 SCADA 网络面临着许多漏洞挑战。最普遍的挑战包括以下内容：

*   继续运行的过时或失效的 ICS 技术
*   不安全的接口
*   不存在或不充分的监控
*   不存在或过时的软件补丁
*   缺乏针对 OT 系统的病毒防护工具
*   不安全的网络连接
*   软件溢出漏洞
*   因缺乏访问控制导致的远程访问漏洞
*   缺乏设备和软件供应商的安全参与
*   来自第三方供应商的其他硬件/软件漏洞

定位和纠正（或补偿）这些漏洞涉及两个方面：

*   **ICS 供应链**（硬件和软件供应商的安全保证和支持）
    *   应监控并评估来自供应商和其他适当来源的漏洞通知，涵盖与企业和 OT 网络环境相关的所有系统和应用程序。
*   基于 ICS 设备测试和网络渗透测试的 **组织安全评估**

## 漏洞评估

*   在将所有新的 IT 和 OT 设备及系统（或正在进行重大变更的设备及系统）投入使用前，必须对其执行漏洞评估。此类活动通常在沙箱环境中进行，因为在运行中的生产网络中执行可能会影响可用性和生产力。
*   还必须定期对 OT 网络和设备执行漏洞评估，以便采取适当措施应对已识别漏洞相关的风险。

## 供应链

为了弥补 OT 网络环境中出现的威胁向量和攻击面增加的问题，OT 设备制造商已升级其漏洞测试程序，纳入以下活动：

*   端口扫描测试
*   网络泛洪活动
*   漏洞扫描
*   协议模糊测试

制造商进行这些测试是为了审查并确保设备在面对常见网络攻击手段时，维持运行性能和 `安全保障等级`（`SALs`）的能力。然而，ICS 领域充斥着晦涩且有时已过时的技术，这些技术无法提供任何可靠的 `SALs`。

`ISA99` 委员会编制了一系列文件，如图 9.1 所述，旨在解决 ICS 网络安全的不同方面。对于从事安全评估的人员而言，文件底部组别中的两个项目尤为重要。这些文件侧重于 OT 网络中单个组件的技术安全要求：硬件、软件和系统的信息组件。

![图 9.1 ISA/IEC-62443 文件系列](img/c09f001.png)

**图 9.1** ISA/IEC-62443 文件系列

`ISA/IEC-62443` 计划的一部分是为 ICS 设备制造商在开发产品时遵循提供一套一致性认证计划。`ISASecure`（`www.isasecure.org`）计划已开发完成，旨在为行业提供一套可认证的 ICS 设备和系统一致性评估方案。它认证商用现货（COTS）ICS 产品和系统，解决如何保障 ICS 供应链安全的问题。目前，该计划提供两种 COTS 认证。

*   嵌入式设备安全保障（ISASecure-EDSA），依据 IEC 62443-4-2 标准认证 IACS 产品
*   系统安全保障（ISASecure-SSA），依据 IEC 62443-3-3 标准认证 IACS 系统

还有一种第三方认证，即安全开发生命周期保障（SDLA），依据 IEC 62443-4-1 标准认证 IACS 开发组织。该认证旨在保证供应商组织已将网络安全制度化并融入其产品开发实践中。

由于 OT 环境中缺乏漏洞研究，无法提供更好的工具来扫描 OT 设备和网络，ISASecure 计划包含一个测试工具认可流程，以确保工具满足执行所有必需产品测试所需的充要功能要求，并确保认可工具之间的测试结果一致。

尽管这些计划正在上线推行，但网络的 OT 侧尚不具备一套健全的系统来提高其设备和系统的安全性。在企业网络环境中，有许多可用的工具来扫描网络漏洞，产品供应商会积极追踪并修复发现和报告的漏洞。在企业网络中打补丁是一项惯例的、被接受的且持续的活动。

ICS 领域的情况并非如此。有来源估计，每台 OT 计算机平均存在 1,800 多个未被发现的漏洞。此外，针对 OT 操作系统发布的补丁中，有 15% 到 25% 是不正确的，会导致崩溃、死机、数据中断和安全问题增加，从而对最终用户产生不利影响。

### 设备测试风险

如前所述，许多组织抵制升级到新 OT 设备的压力，因为这样做可能会干扰其运营流程。因此，设备测试成为 ICS 安全评估的重要组成部分。然而，现场 OT 设备测试的相关风险还包括：在 ICS 或 SCADA 设备上使用扫描工具和技术，确实可能导致流程停机（或中断）。如前所述，此类任务通常在数字孪生或沙箱环境中执行，然后再引入运营环境。

### 设备关键性

术语 `criticality`（关键性）是指具有最高重要性的质量、状态或程度。应对每个 OT 网络设备执行关键性评估和分析流程，以确定其故障或功能丧失的后果。当组织开展 ICS 安全评估、风险缓解和安全策略生成计划时，必须解决以下可能的风险领域：

*   人员安全
*   设备安全
*   环境影响
*   生产损失
*   数据丢失
*   不利的商业影响

这些关注点在第 8 章“ICS 安全治理与风险管理”中描述的 `危险与可操作性`（`HAZOP`）研究中得以解决。特别是该研究中的 `失效模式、影响及关键性分析`（`FMECA`）部分，分析流程设备以识别其可能的失效方式，并评估其对组织的相对影响。顾名思义，`FMECA` 涉及三个主要领域：

*   `失效模式` 涉及对设备或系统可能失效的方式（模式）进行分类。此部分分析识别组件功能失效的具体方式。
*   `影响分析` 是指对这些失效的后果进行分类。此部分分析识别每种模式对组织的严重影响程度，并为每种模式生成一个严重度（`S`）评级。它还为每种模式生成一个发生频度（`O`）评级，以估算失效发生的概率。
*   `关键性分析` 涉及根据严重度和发生频度（`S x O`）计算，确定应处理潜在失效的优先顺序。

由此产生的 `关键性评估` 可用于识别系统中最可能失效的组件。这反过来使组织能够采取行动，缓解可能的失效事件及其频率。这可能涉及用可靠性评级更高的组件替换现有组件、增加冗余组件以补偿潜在故障，或降低关键设备的运行应力水平。根据漏洞的严重程度，组织可能希望对产生高 `关键性排名` 的设备和系统实施额外的监控活动。

## 攻击面分析

术语 `attack surface`（攻击面）用于定义设备或系统中攻击者可能借以获得访问权限或提取数据的所有不同点。`攻击面分析` 流程旨在明确设备或系统的哪些方面构成漏洞，以便组织了解与该特定设备或系统相关的风险。随后，组织可以确定其愿意为将这些风险降至最低而投入的精力程度和资源类型。

### 攻击面分析流程

该过程始于识别可用于访问目标的所有攻击向量（路径、通道或手段）。这包括记录物理访问路径、远程访问路径以及与外部系统的接口（特别是与互联网连接的路径），如图 9.2 所示。与每个通道相关的协议的相对安全性也在分析中予以考虑。

![图 9.2 攻击面](img/c09f002.png)

**图 9.2** 攻击面

分析过程还涉及识别保护每条路径的所有防护措施——连接和控制设备、认证和授权工具，以及数据活动日志系统和数据编码系统。

接下来，必须将授予不同类型用户的各种角色和权限（访问权限）纳入分析。特别是，必须评估高权限用户（如管理员和安全人员）以及未经授权和匿名用户（来宾账户）。

最后，应将每个攻击向量按风险类型（面向外部或面向内部）、目的、实现和技术进行分组。然后统计与每个组相关的攻击向量数量，以便从每组中检查案例，并将评估活动集中在被指定为高风险区域的地方。此类分析过程通常由红队成员（如网络安全人员和 渗透测试人员（pentesters））在内部执行。

攻击面分析可用于识别以下内容：

*   组织需要审查或测试安全漏洞的网络层面
*   需要纵深防御保护策略的网络高风险区域
*   设备或网络的攻击面何时发生变化，从而需要进行新的威胁评估

## 通信鲁棒性测试

鲁棒性 测试是指测试以确定设备处理错误和故障的能力。嵌入式设备通常在现场运行数年，在其生命周期内可能需要经受多次技术变革。如果设备在发生断电等事件后能继续运行，则被认为具有鲁棒性。

针对嵌入式设备的 通信鲁棒性测试（CRT） 基于向设备发送协议消息，然后检查其通信状态。如果设备无法继续提供系统控制和报告功能，则表明存在漏洞。通常测试三类消息：

*   格式正确的消息
*   错误消息
*   格式错误的消息

设备应能充分维持基本服务，例如过程控制/安全回路的运行、命令功能和过程报警。

## 模糊测试

模糊测试 是一种自动化的黑盒数据注入技术，将格式错误的数据注入软件结构，以检测软件结构、配置和实现中的故障。因此，模糊测试常用于暴露软件中可被攻击者利用的漏洞（攻击向量或 模糊向量）。它通常是通信鲁棒性测试程序的一部分。典型的模糊向量类别包括：

*   SQL 注入
*   跨站脚本攻击 (XSS)
*   LDAP 注入
*   XML 注入
*   缓冲区溢出 (BFO)
*   格式字符串错误
*   整数溢出

模糊测试过程始于建立通往目标设备的通信通道。然后使用称为 模糊器 的软件工具将格式错误的数据注入目标的软件结构中，旨在创建前面列出的任何条件。这些测试旨在创建从不稳定到完全故障的各种条件，可通过简单观察来检测。如果设备发生故障或表现异常，则表明存在漏洞条件，必须为该设备制定风险缓解计划。

协议模糊测试 涉及向协议引入故障（格式错误的消息），以测试目标设备的鲁棒性。格式错误的消息就是语法不正确的协议消息。有多种不同的协议，如 `SIP`、`SCADA`、`IPv6`、`Wi-Fi`、`Bluetooth`、`ARP`、`DHCP` 和 `Modbus`，均可通过模糊测试进行测试。

协议模糊测试需要了解协议的头部/数据包格式，以及用于创建/操作头部和消息的工具。图 9.3 描绘了典型的 TCP/IP 头部。通过向不同字段注入各种值，特别是为将来使用保留的未定义值，可以向目标发送数据包，尝试让其进行处理。

当目标设备接收到意外值时，例如长度不正确的字段（特别是零长度、过短或过长的载荷），它会变得“困惑”，并可能以多种不同方式做出反应，包括进入无限程序循环、缓冲区溢出条件，或直接崩溃。 基于状态的模糊测试 涉及操纵消息的顺序，而不是消息的内容。

前面列出的故障条件是每个软件程序员都能识别的典型软件相关条件。程序员可以轻松创建消息来触发它们。然而，渗透测试人员可用的商业和开源模糊测试包有几个：

*   **W3af** (`https://docs.w3af.org`)：W3af 是一个用于构建漏洞发现/利用工具的灵活框架。该框架允许用户将其他工具（插件）集成到包中，用于利用或监控目的。该实用程序在 Kali Linux 和 Windows 中均可用。
*   **Wapiti** (`https://wapiti-scanner.github.io`)：Wapiti 旨在通过查找可注入数据的脚本和表单来审计 Web 应用程序的安全性。在创建潜在漏洞列表后，它将载荷注入脚本（模糊测试）以确定是否真正存在漏洞。
*   **Wfuzz** (`https://github.com/xmendez/wfuzz`)：Wfuzz 模糊器旨在对 Web 应用程序进行暴力破解攻击。特别是，它可用于定位未链接的资源，如可被利用的目录、脚本等。此外，它可用于不同类型的注入攻击（SQL、XSS、LDAP 等）以及模糊测试/暴力破解用户/密码参数。Wfuzz 在 Kali Linux 和基于 Windows 的实用程序中均可用。
*   **Peach** (`https://github.com/MozillaSecurity/peach`)：Peach 模糊器旨在配合不同的测试定义（称为 Peach Pits）运行，这些定义包含有关特定目标类型的具体信息。只需选择目标类型，使用基于 Web 的 GUI 配置参数，然后开始测试。该工具将自动生成一份按优先级排序的报告，列出它遇到的每个问题。
*   **Sulley** (`https://github.com/OpenRCE/sulley`)：除了所有模糊器提供的数据生成功能外，基于 Python 的 Sulley 模糊器框架还监控网络和目标设备的健康状况，并将操作恢复到“良好状态”。一般来说，Sulley 设置和使用所需的编码工作比其他模糊器少。
