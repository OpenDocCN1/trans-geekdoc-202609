
它们具有执行复杂任务和做出一致决策的能力。它可以帮助操作系统选择适用于打开特定文件的应用程序。

### 专家系统

它们可以协助系统进行决策，就像该领域的专家一样。系统诊断问题、提出解决方案并提供替代方案。它在内存管理和操作系统崩溃中可能起关键作用[[5]]。专家系统[[5]]也可用于构建更好的用户界面。

### 自然语言处理

它可以用于用人类语言与机器通信。

#### 模糊逻辑系统

模糊逻辑系统的方法模仿人类的决策过程。即使输入不准确或不，它也能提供接受的确定输出，从而使系统能够在确定和不定的条件下工作。

#### 神经网络

它在为操作系统提供增强安全性方面将证明是有用的，因为它有助于模式识别，而模式识别可用于语音和脸部识别。

## 7.2 学习配置

设置与时间相关的配置，例如 CPU 核心的中断频率 [6, 7\]（用于线程调度）、后台交换的调用频率（用于内存分页）、缓冲区缓存的刷新频率（用于存储）以及 CPU 时钟频率的采样率（用于能量和性能），是非常困难的，因为这些涉及到各种权衡。例如，频繁的 CPU 中断会导致性能开销（通过抢占和上下文切换线程），最终降低有效 CPU 的利用率 [\[8\]](#c07.xhtml#ref8)。

手动设置这些配置需要大量的工程工作，涉及反复试错和离线实验。因此，机器学习（ML）可能是该任务的良好候选方案。良好的机器学习模型可以根据过去的负载和操作系统/硬件环境进行训练，以动态生成新配置来适应负载和环境的变化。

此外还有尺寸配置，例如缓冲区缓存大小（用于存储缓存）、交换预取量（用于内存分页）和磁盘预取量（用于存储访问）。设置这些与尺寸相关的配置也是困难的，特别是当不同尺寸之间存在权衡时。例如，较大的缓冲区缓存可以提高存储系统的性能，但会减少用户应用程序的可用内存。

机器学习可以生成的 OS 策略：空间分配 [9, 10]、调度和缓存管理，目前这些都由预定义的固定算法完成，例如最佳拟合策略、公平份额调度和最久未使用（LRU）缓存访问。

## 7.3 构建机器学习模型

尽管基于机器学习的操作系统开发前景广阔，但在许多应用中，选择合适的模型是一个难题。虽然我们可以通过评估应用模型后的应用程序性能来估计特定算法的有效性，但其他变量（如负载的变化或同一操作系统上运行的其他进程）可能会影响我们的结果。因此，为了更准确地确定某个模型的效果，我们应该寻求更好、更本地化的评估目标。细粒度模型可以通过更多的定制和专门化实现更准确的预测，但需要更多资源，如内存空间、训练 CPU 时间 [\[11\]](#c07.xhtml#ref11) 等。操作系统中的不同进程相互关联，一个进程的变化会影响另一个。因此，我们必须联合优化相关任务以获得最佳结果。此类机器学习模型可以使用大型细粒度数据集进行离线训练，而在在线训练时低频率使用粗粒度数据，且不干扰前端应用程序的性能。这些模型可以针对理论最优（如果存在）进行验证，例如用于线程调度的最短作业优先，或让机器学习使用强化学习为这些需求寻找最佳解决方案。

## 7.4 在改进进程调度方面完成的工作

CPU 使用调度算法为进程分配时间片；这些算法不使用进程之前的执行历史。对需要极短 CPU 时间的进程进行抢占会增加上下文切换次数、缓存和流水线的失效、缓冲区交换等，最终增加程序的周转时间。这个问题可以通过使用适当的机器学习技术来识别程序，以理解其之前的执行历史并预测其资源需求来缓解。这样做是有收益的。为了让机器学习算法或分类器成功，它们需要对适合预测的程序属性进行合适的刻画。

Suranuwarat 和 Taniguchi [\[1\]](#c07.xhtml#ref1) 的工作研究了在各种相似状态下某些已知程序的运行时间。程序流序列（PFS）的知识是一种根据其过去执行历史计算的度量，用于确定进程是否需要额外时间。

Smith *et al.* [\[2\]](#c07.xhtml#ref2) 论文的作者使用了遗传算法技术，通过使用队列、负载、均衡脚本、参数等特征来寻找特定负载下两个应用程序之间的相似性。

在 Fredrik *et al.* [\[3\]](#c07.xhtml#ref3) 的论文中，作者描述了一种应用程序签名模型，用于预测在给定网格资源上的应用程序性能。在该模型中，他们引入了“应用程序内在行为”的概念，将运行时系统的性能影响与应用程序本身内在的行为隔离开。应用程序内在指标是指那些完全取决于应用程序代码和问题参数的指标。

Atul Negi 和 Kishore Kumar P *et al.* [\[4\]](#c07.xhtml#ref4) 的论文中作者修改了 Linux 内置的 O(1) 调度器。使用这个修改后的调度器运行不同的程序，并发现了它们的 STS（最佳特殊时间片）。这为我们提供了最小周转时间。由此获得的运行轨迹的程序静态和动态特性知识库，并使用 C4.5 决策树算法进行训练。如果出现新程序，则对其进行分类并使用预测的 `STS` 运行程序。如果程序不在知识库中，我们使用修改后的调度器运行程序。作者得出结论，C4.5 决策 \[12\]](#c07.xhtml#ref12) 树算法实现了良好的预测（91% - 94%），这表明当使用合适的属性（在这种情况下为输入大小、程序大小、bss、text、rodata 和输入类型）时，已知程序确实存在某种可预测性。他们实现了周转时间减少 1.4% 到 5.8%。

### 7.4.1 OS 代理

论文 [\[5\]](#c07.xhtml#ref5) 的作者讨论了 OS 代理（OS agents）的概念，这是一种面向目标的操作系统命令行接口方法，通过决定如何完成来满足高级用户请求。用户只需指定必须做的事。代理能够合成一系列 OS 命令 [13, 14]、程序调用或系统调用来完成广泛的用户目标。它们可以执行这些命令，从任何意外故障中恢复，并在时自动尝试替代方法完成任务。它们必须被视为类似于 shell 脚本的命令扩展机制。然而，它们具有更大的力量，即根据不同的条件、资源和用户喜好进行适应。

这种方法允许用户请求虽然表达简单但使用标准命令可能难以执行的动作。通常，此类需求涉及跟踪状态或遵守限制。其中一个例子是“`/papers/sosp` 中的所有文件对组均可读”。这可以翻译为正确的语法结构，如下：

```
(maintain (forall ?file (parent-directory ?file /papers/sosp)
(protection ?file group.readable)))
```

为了实现此类任务，作者将此类代理的结构分为两个模块：规划器（planner）和管理员（clerk）。

规划器将用户的请求映射到相应的 OS 命令序列。它根据用户的请求生成目标，这些目标无非量化原子命题的合取，称为子目标。例如，规划器的目标可能是从远程站点检索所有 1994 年的技术报告并在本地打印，表达如下：

```
(forall ?file (machine ?file stanford.edu)
(parent-directory ?file /pub/trs)
(creation-date ?file ?date)
(year ?date 1994)
(printed ?file ?printer))
```

为了实现这一目标，OS 代理必须访问远程机器、检索所需文件、对其进行重新格式、选择合适的本地打印机并打印文件。

这些代理的基本规划和执行流程如下：规划器维护一个表示其计划的数据结构，该计划包含了一组与原始输入目标相对应的未满足的子目标。为了推导出计划，规划器会反复选择一个需要满足的子目标，并搜索一个后置条件与该子目标统一的动作。一旦选择了此类动作，规划器就会将其插入计划，并将其先决条件添加到“待满足”子目标列表中。然后，规划器开始其循环的下一次迭代，选择一个新的子目标来满足，以此此类推。某些子目标可以通过当前系统状态或已插入计划的动作来满足。规划器通过维护一个系统状态模型、检查子目标是否已经满足并记录这一事实来察觉这一点。如果某些情况进展不顺利，规划可能需要回溯。当规划器得到一个每个动作的先决条件都已满足、且能使系统处于输入目标已满足的状态的计划时，规划完成。

他们描述了 OS 代理的哲学、设计和实现，OS 代理是一种面向目标的操作系统命令机制，它利用 AI 规划技术来满足其目标。通过 OS 代理，用户可以请求系统执行复杂的动作，系统将自动确定执行该请求所需的步骤。由于规划是动态完成的，代理能够响应状态和配置的变化。他们在 Unix 上实现了相同的功能 [[14]](#c07.xhtml#ref14)]，但在一个分布式且可能是异构的环境的框架下实现。他们成功地将广为人知的 AI 规划算法整合到我们的代理中，产生了一个灵活且可扩展的系统。规划算法和算符表示语言的精确描述，结合他们论文中的讨论，足以复制其实现和实验结果。此外，OS 代理的正常运行充满了学习机会。已经存在算法，可以通过分析过去的成功与失败来学习控制种控制启发式方法，并基于实验和观察人类用户自动生成动作的逻辑模型。他们还描述了 OS 代理功能在 Unix 中的集成。OS 代理服务器负责与系统接口、发布命令、调用系统调用以及对感兴趣的内部系统事件设置触发器。他们在 Unix 内提供了一些特权支持，以便代理表达对特定状态的兴趣而无需轮询或特权访问。该机制还允许信任人员动态向系统添加额外的事件类型，以支持 OS 代理查询。我们相信，像 OS 代理这样的设施将允许用户发出日益强大的请求。随着经验的积累，用户将想象出新类型的查询和请求，这些可能需要系统设计者最初未预到的信息或事件信号。因此，未来旨在支持此类设施的操作系统设计者应该认真考虑信息和事件信号的需求，并预测支持用户请求的扩展需求。

## 7.5 分布式操作系统中的人工智能

无处不在可以通过大型分布式系统架构中情感渗透式智能的交互来实现，在这些架构中，富传感器的嵌入设备能够感知它们与用户以及环境中其他设备的关系，并且允许这些设备自主运行，从而减少人类的参与。传统 AI 拥有大量此类算法，允许快速搜索数据以实现从分布式数据中学习，并便于利用大量信息进行快速规划，这些信息可用于优化资源管理、增加容错性、自动化安全、自动化资源发现、提供更自然的用户界面等。

AI 搜索技术，如遗传算法、模拟退火、爬山算法、贝叶斯网络和包括 A* 搜索在内的启发搜索，可以用于分布式操作系统，以改进对处理器、文件和内存等资源的管理。至关重要的一点是，只需更改每个算法中的几个参数，整个分布式操作系统的行为可能会改变，而不需要任何额外的设计考虑或开发。例如，遗传算法（GA）的适应度函数和终止标准可以随时更改，将系统从满足实时需求转向更具容错性。目前，这些解决方案大多是独立评估的，而不是作为大型分布式操作系统的一部分。这些策略中的某些也可能实现在虚拟机（Hypervisors）中，允许操作系统虚拟化，尽管其收益不如在微内核或单体内核中实现那样明显。目前还没有足够的统计数据来评估和对比这些真实的优缺点，因为这些策略尚未部署在经过良好测试的分布式操作系统上。

决策树可以用于资源管理，对机器通信统计数据进行分类，然后用于将数据快速分发到网络的不同部分。强化学习可能也用于类似的目标，特别是当系统状态可以表示为离散状态时。分布式操作系统还可以用于建模，通过动态学习开发系统模型，以检测和应对资源或通信问题。神经网络可以在已知的安全漏洞上进行训练并实现在分布式操作系统上。由于神经网络可能具有泛化能力，它可能处理已知的和此前未预见的攻击。命名（Naming）是在分布式系统中分配并唯一地标识用户、服务、文件、打印机、组、主机和其他对象的过程。基于某些属性搜索已识别资源就是资源发现的核心。模型学习算法非常适合这项任务，因为它们寻求构建和维护一个可以用多种方式的系统模型。在这种情况下，基于模型的算法（如基于惊讶度的学习）可以使用。

SBL 可以通过定期查询分布式系统来自主创建和维护模型。通常，该模型由许多规则组成，每条规则都包含一组情况、一个操作以及一组预测规则。学习者必须为所有可能的操作做好准备，这些操作可能包含一系列合法的 系统命令。查询是某个命令的执行，例如带有特定次数的 `ping`。SBL 会监控所有的系统活动，并将它认为是由命令执行触发的任何变化作为规则记录在模型中。SBL 有一个预测，它在下一次发出相同命令时可能会进行测试；如果预测准确，说明其模型是正确的；否则，它将拆分并精炼规则，直到模型符合系统的实际状态。如果学习到了良好的模型，并且添加了新主机、旧主机故障或添加了新用户，学习者最终会发现并相应地更新模型，即使学习者没有立即收到报警。因此，分布式操作系统可以轻松采用这种范式来执行资源管理和容错。自然地，查询过程能够处理字面的资源发现；然而，因为模型可以检测冲突，它可能被用于某种程度上解决命名难题。此外，可以采用分层模型分布的方法，为不同主机上的子系统保留较小的模型。正如 SBL 所示，可以使用逻辑来描述分布式系统的知识。作为逻辑规则，可以收集并存储大量关于系统的信息。在这种情况下，分布式操作系统可能会利用各种 AI 规划方法做出有效判断。包括约束满足在内的命题逻辑规划、一阶逻辑推理、框架系统和语义网络是分布式操作系统可以使用的几种著名的 AI 规划技术，用于确保并发、防止死锁等。

## 7.6 现状进展

Cognition 是一种基于 AIOS 的操作系统，被设计用作智能助手、电子顾问、推荐引擎和聊天机器人。基于人工神经网络的操作系统 NeurOS 正在开发中。模式学习与识别、工作记忆、感知、预测、上下文启动、想象力、注意力、抽象、分类、联想思维和行为等是它的某些功能之一。NeurOS 程序在设计上是可移植、可扩展、可网络化、可扩展和可嵌入的。目前还有其他创建 AIOS 的工作，例如 Jarvis。AI 也被应用于助手程序，如亚马逊的 Alexa、苹果的 Siri、Google Now 和微软的 Cortana。此外，Windows Metro 交付了 AIOS 特性。然而，其用户界面仅显示文件夹，无法提供下一代 AIOS 体验。

在本节中，我们的重点是 KMLib，这是一个尝试针对内核空间组件的轻量级且高效 ML 引擎。在他们的论文中，该引擎的创建者讨论了针对操作系统 I/O 调度器的初始原型。开发这样的系统需要从零实现甚至是标准的数学浮点操作，如 `logarithm` 和 `power`。该库遵循机器学习社区中流行库的做法，使用张量表示矩阵和模型参数。用于操作这些矩阵和张量的函数（如加法和乘法）也是从零实现的。此外，库中使用的神经网络层使用无锁数据结构实现，以便在可能的情况下分解计算 `DAG` 来允许并行处理。该库实现了反向模式自动微分来计算梯度，然后使用 `gradient descent` 等基于梯度的学习算法来更新模型权重。

### 适应新工作负载

我们必须不断训练模型，以适应现代操作系统不断变化的工作负载。这意味着在适应能力和计算效率之间存在权衡。对于低维问题，模型可以在极少数几轮（epochs）内实现收敛，我们仅当最近 `k` 个批次（batches）的分类准确率至少比这 `k` 个批次中最频繁的标签高 `p[margin]` 时才进行推理。`k` 和 `p[margin]` 是可调的，否则我们可以使用这种简单的反馈机制本身。

理想情况下，人们会部署一种训练时间最短且使用训练实例最少的机器学习算法，这在适用时可以通过少样本学习（few shot learning）来实现。人们还希望执行“主动学习”，即仅使用那些有望提高模型性能的训练实例来训练数据模型。有效利用解决这两个问题的方法，可以产生在训练上花费时间最短且更多用于推理的模型。

许多操作系统任务必须在亚微秒级时间内完成，否则会发生严重的性能下降。正如我们上面提到的，KMLib 可以同时在用户空间和内核空间中工作。为了减少计算开销和内存消耗，我们应该利用低精度训练。由于 Linux 内核中不允许浮点操作，调用 `kernel-fpu-begin` 模块，并在完成操作后调用 `kernel-fpu-end` 模块。浮点启用代码块的大小是因为 KMLib 在浮点启用区域花费的时间越长，被切换上下文的可能性就越大。当浮点单元启用时，内核必须保存浮点寄存器，并产生额外的开销。所设计的引擎通过将计算卸载到库线程，能够在底层操作系统运行时执行训练和推理操作。KMLib 唯一的干扰是保存输入数据和用于训练的预测。

使用无锁环形缓冲区存储训练数据。这些缓冲区的大小由用户配置。缓冲区可以在两种模式中运行：阻塞和丢弃。阻塞模式有助于用户处理每一个输入数据块，但如果计算请求频率很高，这种阻塞模式可能会因为阻塞额外的输入而产生额外开销。丢弃模式会忽略未处理的输入数据：它不会产生额外开销，但 KMLib 因此会丢失数据，可能会影响训练质量。通过这些功能，用户可以根据其 ML 需求限制内存开销。尽管 KMLib 使用无锁数据结构来减少多线程通信和同步开销，但计算 `DAG` 中可能存在依赖关系，这可能会导致延迟。这就是为什么用户可以选择使用多少线程用于训练和推理。所有这些与卸载训练/推理计算相关的功能都可以禁用，并在原始线程上下执行。

KMLib 有两种部署方式：(i) 内核模式，训练和推理都在内核空间进行；(ii) 内核-用户内存映射共享模式。在后者中，KMLib 从内核空间收集数据并使用用户空间线程进行训练。对于推理，KMLib 仍在内核空间中运行操作以减少延迟。但由于 KMLib 线程以轮询方式工作，只有在它们被调度时，才能提取训练请求。

开发了一个 KMLib 的示例应用程序用于微调“mq-deadline”I/O 调度器。为了预测 I/O 请求是否能满足截止日期，我们训练了一个线性回归模型。该回归模型使用归一化块编号和序化操作类型作为特征，预测给定 I/O 请求的发射时间。然后对预测的发射时间进行阈值处理，预测 I/O 请求是否应该提前拒绝。我们观察到，阈值化的回归输出可以以 74.62% 的准确率预测 I/O 请求是否错过截止日期：这使得整体 I/O 延迟降低了 8%，考虑到 I/O 远慢于内存或 CPU（因此 I/O 应该是优先优化的），这是一个非常有前景的结果。
