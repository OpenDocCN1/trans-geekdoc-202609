
试图关闭一个已经关闭的 channel 会导致 panic，关闭 nil channel 也是如此。关闭 channel 还有一种用作广播机制的用途，我们将在 8.9 节中介绍。

### 8.4.3 单向 Channel 类型

随着程序的增长，将大型函数拆分为较小的部分是很自然的。我们之前的示例使用了三个 goroutine，通过两个作为 `main` 局部变量的 channel 进行通信。该程序自然地划分为三个函数：

```go
func counter(out chan int)
func squarer(out, in chan int)
func printer(in chan int)
```

处于管道中间的 `squarer` 函数接受两个参数，即输入 channel 和输出 channel。两者类型相同，但预期用途相反：`in` 仅用于接收，`out` 仅用于发送。参数名 `in` 和 `out` 传达了这一意图，但仍然无法阻止 `squarer` 向 `in` 发送或从 `out` 接收。

这种安排很典型。当 channel 作为函数参数提供时，几乎总是打算专门用于发送或专门用于接收。

为了记录这一意图并防止误用，Go 的类型系统提供了*单向* channel 类型，它们仅暴露发送和接收操作中的一种。类型 `chan<- int` 是一种*只发送*的 `int` channel，允许发送但不允许接收。相反，类型 `<-chan int` 是一种*只接收*的 `int` channel，允许接收但不允许发送。（`<-` 箭头相对于 `chan` 关键字的位置是一个助记符。）对此规则的违反会在编译时被检测出来。

由于 `close` 操作断言不再会有发送操作发生在 channel 上，因此只有发送 goroutine 有资格调用它，因此试图关闭一个只接收 channel 会导致编译时错误。

这里再次展示平方管道，这次使用了单向 channel 类型：

点击此处查看代码图像

`gopl.io/ch8/pipeline3`

```go
func counter(out chan<- int) {
    for x := 0; x < 100; x++ {
        out <- x
    }
    close(out)
}

func squarer(out chan<- int, in <-chan int) {
    for v := range in {
        out <- v * v
    }
    close(out)
}

func printer(in <-chan int) {
    for v := range in {
        fmt.Println(v)
    }
}

func main() {
    naturals := make(chan int)
    squares := make(chan int)

    go counter(naturals)
    go squarer(squares, naturals)
    printer(squares)
}
```

调用 `counter(naturals)` 会隐式地将 `naturals`（一个 `chan int` 类型的值）转换为参数类型 `chan<- int`。`printer(squares)` 调用执行类似的隐式转换为 `<-chan int`。允许在任何赋值中从双向 channel 类型转换为单向 channel 类型。但是无法逆向操作：一旦你拥有了一个单向类型的值，如 `chan<- int`，就无法从中获得一个引用相同 channel 数据结构的 `chan int` 类型的值。

### 8.4.4 缓冲 Channel

缓冲 channel 拥有一个元素队列。队列的最大容量是在创建时由 `make` 的 capacity 参数决定的。下面的语句创建了一个能容纳三个 `string` 值的缓冲 channel。图 8.2 是 `ch` 及其引用的 channel 的图形化表示。

```go
ch = make(chan string, 3)
```

![一个空的带缓冲通道。](img/emptychannel.png)

**图 8.2。** 一个空的带缓冲通道。

在带缓冲通道上的发送操作会在队列尾部插入一个元素，而接收操作则会从队列头部移除一个元素。如果通道已满，发送操作会阻塞其所在的 goroutine，直到另一个 goroutine 执行接收操作腾出空间。反之，如果通道为空，接收操作会阻塞，直到另一个 goroutine 发送一个值。

我们可以在此通道上发送多达三个值而不会导致 goroutine 阻塞：

```go
ch <- "A"
ch <- "B"
ch <- "C"
```

此时，通道已满（图 8.3），第四条发送语句将会阻塞。

![一个满的带缓冲通道。](img/fullchannel.png)

**图 8.3。** 一个满的带缓冲通道。

如果我们接收一个值，

```go
fmt.Println(<-ch) // "A"
```

通道既不满也不空（图 8.4），因此发送操作或接收操作都可以在不阻塞的情况下进行。通过这种方式，通道的缓冲解耦了发送和接收的 goroutine。

![一个部分填满的带缓冲通道。](img/nonemptychannel.png)

**图 8.4。** 一个部分填满的带缓冲通道。

在极少数程序需要知道通道缓冲容量的情况下，可以通过调用内置的 `cap` 函数获得：

```go
fmt.Println(cap(ch)) // "3"
```

当应用于通道时，内置的 `len` 函数返回当前缓冲的元素数量。由于在并发程序中，该信息一旦获取很可能就已过时，因此其价值有限，但在故障诊断或性能优化时可能会有用。

```go
fmt.Println(len(ch)) // "2"
```

再执行两次接收操作后，通道再次变空，第四次接收将会阻塞：

```go
fmt.Println(<-ch) // "B"
fmt.Println(<-ch) // "C"
```

在本例中，发送和接收操作均由同一个 goroutine 执行，但在实际程序中，它们通常由不同的 goroutine 执行。新手有时会被带缓冲通道简洁优雅的语法所吸引，试图在单个 goroutine 内将其用作队列，但这是一个错误。通道与 goroutine 调度有着深层联系，如果没有另一个 goroutine 从通道接收，发送者——甚至整个程序——都面临永远阻塞的风险。如果你只需要一个简单的队列，请使用切片来实现。

下面的示例展示了带缓冲通道的一个应用。它向三个*镜像站点*发起并行请求，即功能等价但地理位置分布不同的服务器。它将响应发送到一个带缓冲通道，然后接收并仅返回第一个响应，也就是最快到达的那个。因此 `mirroredQuery()` 甚至在两个较慢的服务器响应之前就已返回结果。（顺便提一下，多个 goroutine 并发向同一通道发送值，如本例所示，或从同一通道接收值，都是很正常的情况。）

点击此处查看代码图像

```go
func mirroredQuery() string {
    responses := make(chan string, 3)
    go func() { responses <- request("asia.gopl.io") }()
    go func() { responses <- request("europe.gopl.io") }()
    go func() { responses <- request("americas.gopl.io") }()
    return <-responses // 返回最快的响应
}

func request(hostname string) (response string) { /* ... */ }
```

如果我们使用无缓冲通道，那两个较慢的 goroutine 会因试图在一个永远不会有 goroutine 接收的通道上发送响应而卡住。这种情况称为 *goroutine 泄漏*，属于 Bug。与垃圾变量不同，泄漏的 goroutine 不会被自动回收，因此确保 goroutine 在不再需要时自行终止非常重要。

在无缓冲和带缓冲通道之间进行选择，以及带缓冲通道容量的选择，都可能影响程序的正确性。无缓冲通道提供更强的同步保证，因为每个发送操作都与其对应的接收操作同步；而带缓冲通道则将这些操作解耦。此外，当我们知道将要发送到通道的值的数量上限时，创建一个该大小的带缓冲通道并在第一个值被接收前完成所有发送，这并不罕见。未能分配足够的缓冲容量会导致程序死锁。

通道缓冲也可能影响程序性能。想象蛋糕店里有三位厨师，分别负责烘焙、抹糖霜和装饰，每位厨师完成一个蛋糕后将其传递给流水线上的下一位。在空间狭小的厨房里，完成蛋糕的厨师必须等待下一位厨师准备好接收；这种会合类似于无缓冲通道上的通信。

如果每位厨师之间有一个蛋糕的放置空间，厨师可以将完成的蛋糕放在那里，然后立即开始制作下一个；这类似于容量为 1 的带缓冲通道。只要厨师们的平均工作速率大致相同，大多数交接都能快速进行，从而平滑各自速率的瞬时差异。厨师之间更大的空间——更大的缓冲——可以在不停滞流水线的情况下平滑更大的瞬时速率变化，例如某位厨师短暂休息后又赶工补进度的情况。

另一方面，如果流水线的前一阶段持续比后一阶段快，它们之间的缓冲区大部分时间将处于满载状态。反之，如果后一阶段更快，缓冲区通常将是空的。在这种情况下，缓冲区不提供任何益处。

流水线隐喻对于理解通道和 goroutine 很有帮助。例如，如果第二阶段更复杂，单个厨师可能无法跟上第一位厨师的供应速度，也无法满足第三位厨师的需求。为了解决这个问题，我们可以雇佣另一位厨师协助第二阶段，执行相同的任务但独立工作。这类似于创建另一个通过相同通道通信的 goroutine。

由于篇幅限制，此处不展示代码，但 `gopl.io/ch8/cake` 包模拟了这个蛋糕店，包含若干可调参数。其中包含了上述几种场景的基准测试（§11.4）。

## 8.5 并行循环

在本节中，我们将探讨一些在并行执行循环所有迭代时的常见并发模式。我们将研究从一组全尺寸图像生成缩略图的问题。`gopl.io/ch8/thumbnail` 包提供了一个 `ImageFile()` 函数，可缩放单张图像。我们不会展示其实现，但可从 `gopl.io` 下载。

点击此处查看代码图像

`gopl.io/ch8/thumbnail`

```go
package thumbnail

// ImageFile 从 infile 读取图像并将其缩略图版本写入同一目录。
// 它返回生成的文件名，例如 "foo.thumb.jpg"。
func ImageFile(infile string) (string, error)
```

下面的程序遍历图像文件名列表，为每个文件生成一张缩略图：

点击此处查看代码图像

`gopl.io/ch8/thumbnail`

```go
// makeThumbnails 为指定文件生成缩略图。
func makeThumbnails(filenames []string) {
    for _, f := range filenames {
        if _, err := thumbnail.ImageFile(f); err != nil {
            log.Println(err)
        }
    }
}
```

显然，我们处理文件的顺序无关紧要，因为每个缩放操作都独立于其他所有操作。这类完全由相互完全独立的子问题组成的问题被称为**尴尬并行**（*embarrassingly parallel*）。尴尬并行问题是最容易并发实现的，且其性能随并行度线性扩展。

让我们并行执行所有这些操作，从而隐藏文件 I/O 的延迟，并利用多个 CPU 进行图像缩放计算。我们的第一个并发版本尝试仅添加一个 `go` 关键字。我们暂时忽略错误，稍后再处理。

点击此处查看代码图像

```go
// NOTE: incorrect!
func makeThumbnails2(filenames []string) {
    for _, f := range filenames {
        go thumbnail.ImageFile(f) // NOTE: ignoring errors
    }
}
```

这个版本运行得非常快——快得离谱，事实上，即使文件名切片只包含单个元素，它也比原版耗时更短。如果没有并行性，并发版本怎么可能运行得更快？答案是 `makeThumbnails` 在完成预期工作之前就返回了。它为每个文件名启动了一个 goroutine，但不等待它们完成。

没有直接的方法来等待 goroutine 完成，但我们可以通过在共享通道上发送事件，让内部 goroutine 向外部 goroutine 报告完成情况。既然我们知道正好有 `len(filenames)` 个内部 goroutine，外部 goroutine 只需计数那么多事件即可返回：

点击此处查看代码图像

```go
// makeThumbnails3 makes thumbnails of the specified files in parallel.
func makeThumbnails3(filenames []string) {
    ch := make(chan struct{})
    for _, f := range filenames {
        go func(f string) {
            thumbnail.ImageFile(f) // NOTE: ignoring errors
            ch <- struct{}{}
        }(f)
    }

    // Wait for goroutines to complete.
    for range filenames {
        <-ch
    }
}
```

注意，我们将 `f` 的值作为显式参数传递给字面量函数，而不是使用外层 `for` 循环中 `f` 的声明：

点击此处查看代码图像

```go
for _, f := range filenames {
    go func() {
        thumbnail.ImageFile(f) // NOTE: incorrect!
        // ...
    }()
}
```

回顾 第 5.6.1 节 中描述的匿名函数中循环变量捕获的问题。上面，单个变量 `f` 为所有匿名函数值所共享，并由连续的循环迭代更新。当新 goroutine 开始执行字面量函数时，`for` 循环可能已经更新了 `f` 并开始了另一次迭代，或者（更有可能）已经完全结束，因此当这些 goroutine 读取 `f` 的值时，它们都会观察到它具有切片最后一个元素的值。通过添加显式参数，我们确保使用的是执行 `go` 语句时 `f` 的当前值。

如果我们想从每个工作 goroutine 向主 goroutine 返回值怎么办？如果调用 `thumbnail.ImageFile` 创建文件失败，它会返回一个错误。下一个版本的 `makeThumbnails` 返回从任何缩放操作中接收到的第一个错误：

点击此处查看代码图像

```go
// makeThumbnails4 makes thumbnails for the specified files in parallel.
// It returns an error if any step failed.
func makeThumbnails4(filenames []string) error {
    errors := make(chan error)

    for _, f := range filenames {
        go func(f string) {
            _, err := thumbnail.ImageFile(f)
            errors <- err
        }(f)
    }

    for range filenames {
        if err := <-errors; err != nil {
            return err // NOTE: incorrect: goroutine leak!
        }
    }

    return nil
}
```

这个函数有一个微妙的 bug。当它遇到第一个非 nil 错误时，它将错误返回给调用者，导致没有 goroutine 排空 `errors` 通道。每个剩余的工作 goroutine 在尝试向该通道发送值时将永远阻塞，且永远不会终止。这种情况称为 **goroutine 泄漏**（§8.4.4），可能导致整个程序卡住或耗尽内存。

最简单的解决方案是使用一个具有足够容量的缓冲通道，这样工作 goroutine 在发送消息时就不会阻塞。（另一种解决方案是创建另一个 goroutine 来排空通道，而主 goroutine 立即返回第一个错误而不延迟。）

下一个版本的 `makeThumbnails` 使用缓冲通道返回生成的图像文件名以及任何错误。
