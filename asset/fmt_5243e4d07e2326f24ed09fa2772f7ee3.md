## CI/CD

CI/CD 代表持续集成和持续交付（或持续部署），它不仅仅是一组工具；更是一种文化变革，赋能团队更快、更可靠地交付更好的软件。

在 DevOps 时代之前，应用程序和软件的发布周期是按月、按季、按年，甚至更长。在 DevOps 时代，得益于 CI/CD 文化，集成新代码的生命周期快得多——一天内可以发布几个版本，甚至每小时发布几个版本。作为开发者，我们将代码交付并集成到真实世界（生产环境）的速度越快，就能获得更快的反馈循环，从而更快地发现 Bug、修复问题和改进。

*   **持续集成 (CI)：** 侧重于频繁的代码集成和自动化测试。
*   **持续交付 (CD)：** 增加了自动化打包部署到生产、预发布等环节。
*   **持续部署 (CD)：** 无需人工干预，直接将变更发布到生产环境。

![Figure 9.1: CI/CD lifecycle](img/Figure-9.1.jpg)

**图 9.1：** CI/CD 生命周期

上图描述了 CI/CD 流水线的生命周期及其中包含的通用步骤。

具体而言，CI 指的是将代码部署到生产环境之前的过程。图中用蓝色表示（计划、编码、构建和测试）。CI 的主要工作是打包和测试代码。如果 CI 充分通过，将继续进入 CD 阶段。CD 指的是将代码部署到其他环境（主要是生产环境）。CD 过程力求完全自动化，无需任何人工干预。

市场上有各种工具可帮助创建 CI/CD 流水线，例如 `Jenkins`、`GitHub Actions`、`CircleCI` 等。作为开发者，我们不会创建这些流水线，但必须了解它们，并确保我们的代码能按预期进行测试、构建和部署。

在微服务架构中使用 CI/CD 流水线至关重要，主要有两个原因：

*   **保持一致性：** 一致且自动化的部署流程确保所有服务能继续无缝协作。
*   **可扩展性：** 随着系统增长，服务数量会增加。通常，服务数量的增加会线性增加工作量。然而，得益于 CI/CD，增加更多服务时的工作量会少得多。

## 故障设计

将应用程序部署到生产环境时，关于其如何表现存在迷雾和不确定性。尽管我们的代码通过了单元测试甚至冒烟测试，但应用程序遇到 Bug 和错误是可能且常见的。我们需要为这些场景做好准备。我们将在微服务架构的 RESTful API 服务中，发现几种处理故障的有价值的方法和设计模式。

### 超时

对于任何需要向另一个服务发送请求，或需要为某段软件设定有限执行时间的服务来说，超时都是必不可少的。我们在从一个服务向另一个服务发送请求时经常会用到超时。使用超时，我们可以避免不必要的在途请求导致服务过载。超时时间因服务而异，通常在 10 到 60 秒之间，平均为 30 秒，但这取决于具体场景，基本上可以是任何选定的时间限制。让我们看看如何在 Golang 中实现超时。

> **免责声明** —— 超时值是任意的，我给出的数字是基于我作为工程师的视角。它可能不同，最长 5 秒，或持续几分钟。

以下示例演示了如何在 Go 中使用通道实现超时。在第一个示例中会发生超时，而在第二个示例中不会。我们首先创建一个容量为 1 的通道，然后启动一个 goroutine 来模拟延迟并向通道发送消息。启动 goroutine 后，我们使用 `select` 语句：如果在超时前收到通道的结果则打印该结果，如果先达到超时则打印 "`Timeout`"：

```go
// 发生超时的示例
resultCh := make(chan string, 1)
go func() {
    time.Sleep(3 * time.Second)
    resultCh <- "Received before timeout"
}()
select {
case res := <-resultCh:
    println(res)
case <-time.After(2 * time.Second):
    println("Timeout")
}
// 输出: Timeout

// 未发生超时的示例
resultCh = make(chan string, 1)
go func() {
    time.Sleep(1 * time.Second)
    resultCh <- "Received before timeout"
}()
select {
case res := <-resultCh:
    println(res)
case <-time.After(2 * time.Second):
    println("Timeout")
}
// Output: Received before timeout
```

在这些示例中，`select` 语句用于处理计时，检查来自通道的结果是否在指定的超时时间内被接收。

我们也可以使用 context 实现超时。让我们看看如何实现：

```go
ctx, _ := context.WithTimeout(context.Background(), 2*time.Second)
go func() {
    select {
    case <-ctx.Done():
        println("Timeout")
        os.Exit(1)
    }
}()
time.Sleep(3 * time.Second)
fmt.Println("Done")
```

与前面的示例类似，我们在此示例中也实现了超时机制，但我们使用了 `context.WithTimeout` 和 `Done()` 函数。在此示例中，当超时发生时，`Done()` 函数会向通道发送一个信号。

### 重试

正如前几章所讨论的，在微服务架构中，服务间通信的常用方式是通过 API 调用。最终，API 调用会失败，我们必须处理这些失败。简单的重试通常可以解决问题，并显著降低错误率（除非这是无论如何都会发生的 Bug）。一个好的做法是执行大约两次重试（除了第一次尝试之外）。重试次数仍取决于用例，可以是 0 次或更多。

另一个好的做法是使用指数退避算法在每次重试之间等待。指数退避算法是一种策略，用于在发生故障时逐渐增加重试尝试之间的延迟，从而减少系统负载并提高成功通信的机会。

例如，每次重试之间的等待时间为 1、2、4、8、16，依此类推。让我们看看 Golang 中指数退避重试的实际示例。

```go
func main() {
	err := Retry(3, time.Second, func() error {
		fmt.Println("trying...")
		return fmt.Errorf("some error")
	})
	if err != nil {
		fmt.Printf("error: %s\n", err)
	}
}

func Retry(attempts int, sleep time.Duration, f func() error) (err error) {
	currentAttempt := 1
	for {
		err = f()
		if err == nil {
			return nil
		}
		if currentAttempt >= attempts {
			return fmt.Errorf("after %d attempts, last error: %w", attempts, err)
		}
		time.Sleep(sleep)
		sleep *= 2
		currentAttempt++
	}
}
```

输出：

```
trying...
trying...
trying...
error: after 3 attempts, last error: some error
```

在前面的示例中，有一个指数退避重试的具体实现。我们可以用许多其他形式实现重试。例如，我们也可以为服务间的请求编写特定的重试机制。

### 降级

在可能发生故障的场景中，我们必须处理该故障。我们可以尝试执行重试，如上一节所示。然而，它并不总能解决问题，我们需要一个可信赖的降级方案。降级是一个无任何错误即可执行的已知函数，或是一个我们可以信任的先前功能。在最坏的情况下，`fallback` 会通知用户出了问题。

```go
func main() {
	result, err := performOperation()
	if err != nil {
		// 发生错误时的降级操作
		result = fallbackOperation()
	}
	fmt.Println("Result:", result)
}

func performOperation() (string, error) {
	return "", fmt.Errorf("Operation failed")
}

func fallbackOperation() string {
	return "Fallback result"
}
```

在前面的示例中，我们展示了一种执行降级的简单方法。我们尝试使用 `performOperation()` 函数。不幸的是，它返回了一个错误，所以我们使用了一个名为 `fallbackOperation()` 的降级函数，它返回一个固定结果。

### 熔断器

熔断器是一种设计模式，用于增强分布式系统的弹性和稳定性，在我们的例子中是微服务架构。它通过以受控方式检测和处理故障，有助于防止级联故障（一个服务的故障导致许多服务故障，像多米诺骨牌一样）。

熔断器监控服务的可用性，如果检测到一定阈值的故障，就会“打开”熔断器，阻止对故障服务的进一步调用。这使系统能够优雅地处理故障，减轻有问题服务的负载，并防止整个系统性能下降。实现熔断器有几种方法，但建议使用现有的库，如 [`github.com/sony/gobreaker`](https://github.com/sony/gobreaker)。

让我们深入了解该模式的逻辑和行为。熔断器可以有三种状态：关闭、打开和半打开。

#### 关闭

这也是熔断器的初始状态。

![](img/Figure-9.2.jpg)

**图 9.2：** 熔断器处于关闭状态

在此状态下，熔断器允许来自服务 A 到服务 B 的请求。同时，熔断器按定义的周期监控故障数量（例如每分钟 10 次故障）。如果某个周期内的故障数量超过定义的阈值，状态将变为打开。

#### 打开

图 9.3 显示了打开状态：

![](img/Figure-9.3.jpg)

**图 9.3：** 熔断器处于打开状态

在此状态下，熔断器将阻止来自服务 A 的任何请求，并向服务 A 返回错误响应。同时，服务 B 不会收到任何请求。熔断器将保持打开状态，直到定义的超时周期结束。然后，它将进入半打开状态。

#### 半打开

图 9.4 描绘了半打开状态：

![](img/Figure-9.4.jpg)

**图 9.4：** 熔断器处于半打开状态

在此状态下，熔断器将允许有限的请求从服务 A 发往服务 B。如果这些有限数量的请求成功，熔断器将再次切换到关闭状态。

### 舱壁模式

与熔断器模式一样，舱壁模式旨在保持系统弹性并避免级联故障。该模式受船舶舱壁的启发，舱壁将舱室隔离以防止漏水。

![](img/Figure-9.5.jpg)

**图 9.5：** 船舶舱壁

在软件中，舱壁模式隔离组件或服务，限制一个服务中的故障对其他服务的影响。该模式在并发系统（服务级别）或分布式系统（系统级别）中发挥重要作用，通过隔离和控制不同服务内的故障，有助于维持系统稳定性，最大限度地降低级联故障的风险。

我们通过为每个工作负载部署多个副本来在系统级别实现舱壁模式。拥有尽可能多的真正隔离的服务实例至关重要。以缓存为例；我们倾向于为每个副本配备独立的缓存，而不是让所有副本共享单个缓存。现在，一个副本引起的问题将会通过缓存影响所有其他副本。

在服务级别，我们希望 goroutine 之间的依赖尽可能小。此外，我们通常希望限制并发 goroutine 的数量，以避免给服务带来过大负载，导致其崩溃。我们已经看到了使用 `sync.WaitGroup` 等待并发 goroutine 完成的用法。然而，我们并未强制规定并发 goroutine 最大数量的硬性限制。限制 goroutine 数量的一个好的实现是使用名为 `sizedwaitgroup` 的包 - [`github.com/remeh/sizedwaitgroup`](https://github.com/remeh/sizedwaitgroup)。让我们看看如何使用它。

```go
package main

import (
	"fmt"
	"time"
	"github.com/remeh/sizedwaitgroup"
)

func main() {
```
