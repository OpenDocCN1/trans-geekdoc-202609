
我们将从节点 Q 开始导航，它为我们的路径表达式提供了“上下文”。节点 Q 可能位于我们所考虑的层级结构的顶部，在这种情况下，它可以代表我们整个 XML 文档。除了这种特殊情况外，我们总是可以从 Q 向上一级到达节点 P，即 Q 的 `parent`（父节点）。如果 Q 有 `siblings`（兄弟节点，即也具有父节点 P 的节点），我们可以横向导航。如果 Q 有 `children`（子节点），则可以向下导航。向上/横向/向下移动的某些组合可以将我们带到一个新节点。一旦到达那里，新选中的节点可以成为其他导航的上下文。

大多数情况下，我们关心的是 XML 元素之间的关系，因此，例如，我们可能想了解所有“包含在”元素 Q 中的元素（即节点 Q 的后代节点）。但我们可能也想了解所有具有特定属性的元素、与特定命名空间相关的所有元素，等等。在 XPath/XQuery 中，所有这些可能的维度被称为 `axes`（轴），这些语言提供了复杂的符号，用于精确定义沿各种轴组合进行导航。遗憾的是，完整的符号有点繁琐。幸运的是，存在涵盖主要可能性的简写符号，我们将重点关注这些简写形式。

在 XML 中，节点或“元素”通过一对命名标签（开始标签和结束标签）来标识。节点可以有零个或多个属性，这些属性列在开始标签中。每个开始标签必须在该标签的所有内容列出后最终被关闭。以下 XML 表达式显示了一个示例：

```
<movie movieNr="1"> <title> Cosmology </title> </movie>
```

这里，我们有一个名为“movie”的标签，带有一个包含数据的属性 `movieNr`。它包含另一个名为 `title` 的标签，后者本身包含一些数据。结束标签重复标签名称，前面加上一个斜杠字符。可选地，不包含其他元素的元素可以仅用一个紧跟在任何属性后的斜杠字符来关闭，如下所示。

```
<movie movieNr="1" />
```

关于选择属性还是元素内容作为数据位置的指导原则有点模糊。广义上讲，属性应该用于节点的内在属性，但这留有解释空间。可以肯定的是，以下表示在语法上与第一种同样有效。

```
<movie title="Cosmology"> <movieNr> 1 </movieNr> </movie>
```

在许多情况下，找到通往相关节点或节点的路径就是从 XML 中提取相关数据所需的一切。所需路径可以使用 XPath 表达式指定。为了提供一些具体示例，我们将回到第 1 章中的 *Movies* 示例。在那里，我们看到了如何将报告的内容捕获为关系表。清单 16.1 显示了类似的信息（数据与第 1 章中的示例略有不同）。初始标签仅标识这是一个 XML 文档。该清单比 CSV 文件等效渲染冗长得多，但这是为了实现表示复杂数据结构所需的表达能力而必须付出的代价。

![Listing 16.1 Movie information in XML.](img/f16-06-9780443237904.jpg)

### XQuery：查询 XML 数据

既然我们已经对如何在 XML 层级结构中移动有了一些了解，接下来我们可以考虑如何查询 XML 数据。在简单的情况下，路径表达式的结果可能已经足够，但通常我们需要更强大的表达式。这一需求由 XQuery 来满足，XQuery 是一种用于操作 XML 值的语言。粗略地说，XQuery 与 XML 数据的关系，正如 SQL 与关系数据的关系一样。与 SQL 类似，XQuery 是声明式的。它指明数据源以及要应用的处理规则，但不指定生成结果的显式过程。

#### 函数式语言特性

XQuery 是一种*函数式*语言，因此我们必须用函数式术语来指定要做什么。大多数软件开发人员都熟悉函数的概念。函数有一个名称、零个或多个输入参数，以及一个计算并返回某个结果的主体。从函数式编程的角度来看，传递给函数的参数可以是常量，也可以是其他函数产生的结果（即参数可以是对另一个函数的调用）。现在，我们有了另一种层级结构：提供结果给其他函数的函数，后者又提供结果给……以此类推。这种*函数*层级可以动态建立，并且可能与*数据*层级没有直接关系。函数层级的顶层计算我们所寻求的结果；较低层级的函数向其父函数提供结果，以（最终）支持顶层计算。XQuery 定义了一百多个内置函数，但商业系统可能尚未实现所有这些函数。

#### FLWOR 表达式

XQuery 允许从多个来源组合信息并重构以生成新结果。XQuery 中此类最常见的表达式称为 FLWOR 表达式，其名称取自表达式中可能出现的子句类型的首字母：`for`、`let`、`where`、`order by` 和 `return`。FLWOR 表达式是 XQuery 中对应 SQL `select` 语句的结构。

FLWOR 表达式中的子句是基于*元组*定义的。元组通过在 `for` 和/或 `let` 子句中将变量绑定到值来创建，因此每个 FLWOR 表达式必须至少包含一个 `for` 或 `let` 子句。两者的区别在于：`for` 会遍历表达式中的各个项，为每一项生成一个元组；而 `let` 则为整个表达式结果生成一个元组。

##### 简单 FLWOR 示例

作为一个简单示例，以下 FLWOR 表达式产生的结果与表 16.2 中最后一个路径示例的结果相同。美元符号“$”在 XQuery 中表示变量。

```
for $m in movie
where $m/star = "Tom Hanks"
return $m/released
```

##### 复杂 FLWOR 示例：反转层级

作为一个稍微复杂的示例，假设我们想要反转源 XML 的层级结构。对于我们的 Movies XML 片段，我们可以在每个演员下列出其主演的电影，而不是在每部电影下列出主演演员。实现此功能的 XQuery 表达式可能如下所示：

```
for $s in distinct-values(movie/star)
order by $s descending
return
  <starring>
    <actor> { $s } </actor>
    <movies> { for $m in movie where $m/star = $s return $m/title } </movies>
  </starring>
```

这里，我们使用了 `distinct-values()` 函数以确保每个演员只出现一次，并按演员名称降序排序结果。查询包含*构造器*，由内部表达式外围的大括号表示，用于构建元素内容。对该查询求值将产生以下结果：

```
<starring>
  <actor>Tom Hanks</actor>
  <movies>
    <title>The Da Vinci Code</title>
    <title>Cast Away</title>
  </movies>
</starring>
<starring>
  <actor>Stephen Chow</actor>
  <movies>
    <title>Kung Fu Hustle</title>
  </movies>
</starring>
…等。
```

#### 连接多个 XML 来源

当然，我们不限于使用单个 XML 文档或片段。假设我们有一些包含电影评论的 XML 数据，如清单 16.2 所示。

![清单 16.2 XML 格式的电影评论。](img/f16-07-9780443237904.jpg)

清单 16.2 XML 格式的电影评论。

评论通过唯一的 `movieNr` 引用与电影相关联。在标准 SQL 中，如果我们想显示电影标题及每部电影的评分，可以使用连接。我们在 XQuery 中可以做同样的事情。

##### 内连接等价写法

下面是实现内连接等价功能的一种方法。

```
for $m in movie
where some $r in review satisfies ($m/@movieNr = $r/movieNr)
return
  <reviewscore>
    { $m/title, $m/released }
    { for $r in review where $m/@movieNr = $r/movieNr return $r/rating }
  </reviewscore>
```

查询中包含了发行年份和标题，以避免同名电影之间的歧义。`where some ... satisfies (...)` 结构是一个存在量词测试，因此我们只会得到有评论的电影的结果。该查询产生以下结果：

```
<reviewscore>
  <title>The Secret Garden</title>
  <released>1993</released>
  <rating>4</rating>
</reviewscore>
<reviewscore>
  <title>The Da Vinci Code</title>
  <released>2006</released>
  <rating>4</rating>
  <rating>5</rating>
  <rating>1</rating>
</reviewscore>
```

要获得外连接的等价写法（这也将包含没有评论的电影），我们只需省略查询第二行中的存在量词测试即可。

#### 聚合函数

作为最后一个 XQuery 示例，我们将展示 SQL 中*聚合*或*包*函数的等价写法，这些函数包括 `sum()`、`count()`、`avg()`、`max()` 和 `min()`。假设我们想为每部电影生成一个汇总元素，将评论总数和平均分作为属性显示。以下查询是生成所需结果的一种方式。

```
for $m in movie
return <reviewsummary total = "{ count ( review [ movieNr = $m/@movieNr ] ) }"
  avg = "{ avg ( review [ movieNr = $m/@movieNr]/rating ) }" >
  { $m/title, $m/released }
</reviewsummary>
```

这里，我们使用了 XQuery 函数 `count()` 和 `avg()`，它们的工作方式类似于其 SQL 对应函数。对于空元素列表（在本例中为没有评论的电影），`count()` 函数返回零，而 `avg()` 函数返回空结果。运行查询将产生以下 XML 片段：

```
<reviewsummary total="0" avg="">
  <title>Cosmology</title>
  <released>2006</released>
</reviewsummary>
<reviewsummary total="0" avg="">
  <title>Kung Fu Hustle</title>
  <released>2004</released>
</reviewsummary>
<reviewsummary total="0" avg="">
  <title>The Secret Garden</title>
  <released>1987</released>
</reviewsummary>
<reviewsummary total="1" avg="4">
  <title>The Secret Garden</title>
  <released>1993</released>
</reviewsummary>
<reviewsummary total="3" avg="3.33333333333333">
  <title>The Da Vinci Code</title>
  <released>2006</released>
</reviewsummary>
<reviewsummary total="0" avg="">
  <title>Cast Away</title>
  <released>2000</released>
</reviewsummary>
```

XQuery 还有许多其他特性，更完整的描述需要单独成书。章节注释中包含了一些进一步参考资料的来源。

我们还可以使用标准编程语言来处理 XML 值。大多数语言都提供库函数，允许将 XML 处理器合并到程序中。有两种类型可用。第一种通常称为 DOM 处理器，它将完整的文档对象模型加载到内部程序结构中。随后，可以使用各种函数浏览该模型，以将标签和属性作为单个项或列表提取到程序中。由于整个 DOM 都在内存中，这既方便又相当高效，但能够加载的 XML 文件大小会有一定的上限。

另一种通常称为 SAX 处理器（用于 XML 的简单 API）。它采用一种不同的基于事件的策略来处理 XML 文件。在读取 XML 文档时，每个重要项（如开始标签）都会被发送到程序中，以便存储供后续使用或立即处理。重要的区别在于，不需要将整个文档存储在内存中，因此文档大小没有上限。缺点是，很难执行那些需要在模型的各个部分之间来回引用的操作。

### SQL/XML

SQL:2003 将 XML 作为一种新的内置数据类型引入。XML 数据是强类型的，因为 XML 值被假定为树状数据结构，这与其文本字符串形式的表示截然不同。XML 类型可用于允许其他 SQL 类型的任何地方，例如表列、例程参数、变量等。尽管关系数据和 XML 数据都是结构化的，但它们之间存在一些显著差异。表 16.3（重复自表 16.1）列出了一些关键点。

XML 数据可以存储在数据库的文本列（即 `char`、`varchar` 或 `clob`）中，也可以存储在 `xml` 数据类型的列中。如果保留文档的文本保真度很重要（这可能包含与数据结构无关的文本），或者 XML 始终作为完整文档输入和检索，则可能首选文本表示形式。然而，将数据存储在 XML 列中，可以在数据库中高效处理 XML 数据，而不是在中间层应用程序中处理。

除了 XML 数据类型，SQL:2003 标准还引入了一些相关特性，例如新的 XML 运算符、函数，以及 SQL 概念与 XML 概念之间映射的规则。大多数厂商广泛支持这些特性或其等效功能，但将额外的 XML 特性集成到不同的预先存在的框架中，不可避免地导致了一些语法细节上的差异。XML 支持是厂商竞争的热点领域这一事实，也可能产生各种非标准扩展。由于需要与其他标准（如 XQuery）互操作，情况变得更加复杂。幸运的是，这种竞争仅限于为将 XML 与 SQL 集成而提供的各种运算符、函数等。XML 数据结构的标准是在 SQL 之外定义的，因此 XML 值本身在不同数据库系统之间具有相当好的一致性。

2006 年，处理 XML 的 SQL 标准部分（第 14 部分）经过修订和扩展，以整合 SQL/XML 的特性（正如它后来被称为的那样）。（该标准有时被称为 SQL:2006，尽管这有点误导性，因为只有 XML 部分在 2006 年进行了修订。）在这里，我们将在必要时使用 SQL/XML:2006 来专门区分更新的版本。

在 SQL/XML:2006 中，`xml` 数据类型基于 XQuery 数据模型。^(¹⁷)

一个恰好包含一个文档节点的序列称为 *XML 内容*，带有类型修饰符 `xml(content)`。一种特殊的内容是文档节点恰好包含一个元素节点（加上可能的注释和处理指令节点），这称为 *XML 文档*，带有类型修饰符 `xml(document)`。

可以为 `xml(content)` 和 `xml(document)` 添加辅助修饰符，以指示内容或文档是既可以包含类型化和非类型化元素（`any`），还是仅包含非类型化元素（`untyped`），或包含由模式定义的元素（`schema` 名称）。如果定义了模式，则保证元素和属性节点根据该模式是有效的。这些区别总结在图 16.3 中。如果指定类型 `xml` 时不带修饰符，则关于这些更专业子类型的任何默认假设均取决于实现。

![图 16.3 XML 数据类型修饰符。](img/f16-03-9780443237904.jpg)

图 16.3 XML 数据类型修饰符。

SQL:2003 标准引入了谓词 `is document`，用于测试 XML 表达式是否为文档。基本语法为：

```
xmlexpression is [ not ] document
```

尽管该谓词的语法从 SQL:2003 保持不变，但由于 SQL/XML:2006 与 XQuery 数据模型的重新对齐，其含义发生了一些变化。又增加了三个谓词：`is content`、`xmlexists` 和 `is valid`。`is content` 谓词用于测试 XML 表达式是否为合法的 XML 内容，语法如下：

```
xmlexpression is [ not ] content
```

要测试表达式是否包含有效的 XML，可以使用 `xmlexists` 谓词。简化后的语法如下：

```
xmlexists ( XQuery-expression  [ passing value-expression  [ as identifier ] [ { by ref | by value } ] ] [,...] )
```
