
*   • “提高开发人员生产力。`SSO` 为开发人员提供了一个通用的认证框架。事实上，如果 `SSO` 机制是独立的，那么开发人员根本不必担心认证问题。他们可以假设，一旦对应用程序的请求附带了用户名，认证就已经完成了。”

*   • “简化管理。当应用程序参与单点登录协议时，管理用户账户的管理负担得以简化。简化的程度取决于应用程序，因为 `SSO` 只处理认证。因此，应用程序可能仍需要设置特定于用户的属性（如访问权限）。”

`SSO` 的劣势如下，在系统上实施 `SSO` 之前必须考虑这些因素：

*   • “难以改造。`SSO` 解决方案对于现有应用程序来说可能难以改造、耗时且昂贵。”

*   • “无人看管的桌面。实施 `SSO` 减少了一些安全风险，但增加了其他风险。例如，如果用户离开座位且保持登录状态，恶意用户可能会访问该用户的资源。虽然这是安全方面的普遍问题，但对于 `SSO` 来说更严重，因为所有授权资源都会受到威胁。至少使用多重登录时，用户可能一次只登录一个系统，因此只有一个资源受到威胁。”

*   • “单点攻击。使用单点登录时，所有应用程序都使用单个中央认证服务。这是黑客进行拒绝服务攻击的诱人目标” [\[9\]](#Ch006_295-335_B9780443187346000052.xhtml#bb0050)。

#### 单点登录的会话管理

权力越大，责任越大：`单点登录` 使用户能够通过一次认证访问大量信息。恶意访问这些资源的风险可能随 `SSO` 而增加，必须降低这种风险。请参阅上一节中引用自“构建和实施单点登录解决方案”的“无人看管的桌面”部分。

`SSO` 应始终与 `MFA`（多因素认证）结合使用，但这仍然无法消除现有会话被恶意利用的潜在风险。因此：应使用会话超时和自动锁定工作站的屏幕保护程序。用户离开工位时也应接受锁定工作站的培训。

### 联合身份管理

`联合身份管理`（`FIM`）在更大范围内应用 `单点登录`：范围从跨组织到互联网规模。

根据 EDUCAUSE 的定义，“身份管理是指建立用户身份并强制执行关于数字资源访问规则的策略、流程和技术。在校园环境中，许多信息系统——如电子邮件、学习管理系统、图书馆数据库和网格计算应用程序——要求用户进行身份验证（通常使用用户名和密码）。随后，授权流程决定经过身份验证的用户被允许访问哪些系统。借助企业身份管理系统，用户无需为每个系统维护单独的凭据，而是可以使用单一的数字身份来访问其有权访问的所有资源。联合身份管理允许将这种方法扩展到企业级别之上，在多个组织之间建立数字身份的可信授权机构。在联合系统中，参与机构基于商定的标准共享身份属性，便于联邦其他成员进行身份验证，并授予对在线资源的适当访问权限。这种方法在简化数字资产访问的同时保护了受限资源” [\[10\]](#Ch006_295-335_B9780443187346000052.xhtml#bb0055)。

### SAML

`SAML`（安全断言标记语言）2.0 是当前版本，它提供了一种在系统之间传输身份数据的标准化方式。`SAML` 通过 XML 格式的断言传输这些数据，这些断言可以传达有关识别、身份验证，以及可能还有授权的详细信息。`SAML` 的一个目标是实现互联网规模的基于 Web 的 SSO。

`SAML` 涉及三个角色：身份提供者（`IdP`）、服务提供者（`SP`）和主体/用户。主体通常通过用户代理（即 Web 浏览器）向 `SP` 请求资源。`SP` 提供可由受信任主体利用的应用程序/资源，但依赖 `IdP` 来验证主体身份并为其担保。`IdP` 作为身份的可信来源，负责对用户/主体进行身份验证，并将验证结果传达给 `SP`。从高层来看，`SAML` 通过身份提供者（`IdP`）创建的 XML 格式断言进行操作，以向服务提供者（`SP`）传达有关主体/用户识别和身份验证状态的详细信息。

`SAML` 原生主要关注身份验证。虽然在某些用例中基本 `SAML` 可用于简单的授权，但它可以扩展以支持传输更强大的授权详细信息。要集成复杂的授权详细信息，`SAML` 可以利用基于 XML 的可扩展访问控制标记语言（`XACML`）协议或 JSON 格式的 `OAuth`，后者将在下文讨论。

### OAuth

`OAuth` 提供了一个授权框架，允许以标准化方式向应用程序传达和委派授权，而无需用户透露其凭据。请注意，`OAuth` 的重点和目的是促进授权，而非身份验证。`OAuth` 的一个主要用例是用户授权客户端应用程序代表其行事，而无需将用户凭据暴露给该客户端应用程序。`OAuth` 通过使用访问令牌来实现这一点，客户端应用程序使用该令牌来证明用户已批准其代表用户行事。

`OAuth` 2.0 在 `OAuth` 1.0 发布不久后推出，解决了原始规范中的安全缺陷。

### OIDC (OpenID Connect)

`OIDC`（OpenID Connect）构建在 `OAuth` 2.0 授权框架之上，并扩展了功能以促进身份验证，为 FIM 或 SSO 实现提供了 `SAML` 的替代方案。如前所述，`OAuth` 旨在用于授权而非身份验证。对于开发人员而言，`OIDC` 的流程很大程度上反映了常用的 `OAuth` 2.0 框架，但现在它也可以传达身份和身份验证详细信息，而不仅仅是授权。`SAML` 传达 XML 格式的断言，而 `OIDC` 则通过 ID Token 传达声明，该令牌采用 RFC 标准的 `JWTs`（JSON Web Tokens）结构进行格式化。

### 身份即服务 (IDaaS)

鉴于身份是有效管理机密性、完整性和可用性的必要前提条件，显然身份在安全中发挥着关键作用。身份即服务（`IDaaS`），或称云身份，允许组织利用云服务进行身份管理。利用公共云服务进行身份管理的想法可能令人不安。然而，与所有安全事务一样，云身份也存在既能增加风险也能降低风险的因素。

利用 `IDaaS` 最重要的理由之一源于组织持续采用并集成云托管应用程序及其他面向公众的第三方应用程序。许多 `IDaaS` 供应商可以直接与这些服务集成，从而实现更流畅的身份管理和单点登录。组织在内部身份管理方面已举步维艰，尤其棘手的是账户/访问权限撤销。当组织还必须考虑到员工利用的公开可访问的关键应用程序时，这些挑战变得更加复杂。与云身份提供商集成所带来的其他常见安全收益包括：更容易部署和集成双因素或多因素身份验证、自助账户管理和密码重置、更好地支持移动设备集成，以及集中审计能力。

`IDaaS` 一个显而易见的安全顾虑在于组织关键身份和身份验证信息可能面临的更大暴露风险。使用传统的本地部署身份管理解决方案时，企业可自行控制平台本身的安全防护。而采用云身份时，如果身份提供商遭遇泄露，客户组织可能因此遭受毁灭性打击。

Microsoft Accounts（前身为 Live ID）是越来越多企业内部采用的云身份示例。

> **考试警告**
>
> 考试中，切勿将 `IaaS`（基础设施即服务，详见第 4 章，领域 3：安全架构与工程）与 `IDaaS`（身份即服务）混淆。

### 结合第三方服务的联合身份

历史上，联合身份管理（FIM）专注于企业内部，并预期身份提供者和应用程序托管在本地。基于云的身份解决方案日益普及，以及云服务（特别是软件即服务 `SaaS` 应用程序）采用率的普遍上升，增加了 FIM 部署和服务模型的多样性。虽然本地部署的 FIM 仍在企业中广泛使用，但完全托管在云端的 FIM 解决方案以及整合了本地和云托管组件的混合解决方案的采用率也在不断提高。

尽管云身份（即 `IDaaS`）的采用率在上升，但并非所有应用程序和服务都能与 `IDaaS` 提供商集成。此外，从架构上讲，许多内部应用程序的部署方式使其难以轻松与面向公众的云身份提供商对接。虽然这并非解决上述挑战的完美方案，但缓解其中部分问题的一种方法是部署本地第三方身份服务。利用企业托管的第三方身份服务实现，可以解决纯公共云身份服务所带来的部分安全性和物流挑战。

第三方身份服务的本地部署实现可以允许内部应用程序与云身份集成。这甚至可能无需从根本上改变应用程序的安全架构即可实现。虽然这取决于实现细节，但转向集成第三方身份服务的另一个好处是，它可能允许组织的传统本地身份解决方案具有更大的可移植性。

部署企业托管的身份服务实例远非与第三方身份服务集成的唯一途径。另一种方法是部署解决方案，允许现有的传统本地身份提供者与云身份提供者集成。这种模式是联合本地组织身份的一种方式，并且可以允许使用典型的组织凭据，即使最终用户毫不知情，这些凭据也会与云身份集成，从而允许用户身份具有更大的可移植性。

### 凭据管理系统

尽管进行了许多值得称赞的尝试试图超越它们，密码仍然是运营痛点的来源和攻击的常见目标。虽然 MFA（多因素认证）和/或无密码认证系统的采用似乎正在增加，但静态密码依然存在。合法凭据代表了对手的高价值目标。在初始利用之后，对手经常会寻找并破坏可用于在受损网络中横向移动的凭据。组织为降低凭据泄露的可能性或限制凭据泄露的影响所做的任何努力，对安全性都是巨大的裨益。

凭据管理系统可以通过有意义的方式帮助强化用户凭据。凭据管理系统可能提供的功能包括：安全密码生成、安全密码存储、凭据签入与签出、自动密码轮换、减少用户必须记住的凭据数量、用于解锁凭据的多因素认证，以及所有交互的审计日志记录。能够实现高效且安全的凭据访问和使用的凭据管理系统，可以增加用户为每个凭据利用不同的随机生成密码的可能性，并减少密码重用的发生。虽然功能各异，但凭据管理系统在帮助更好地保护这些高价值目标方面可以发挥至关重要的作用。

### LDAP

`轻量级目录访问协议 (LDAP)` 为网络操作系统提供的目录服务信息提供了一种通用的开放协议，用于接口和查询。`LDAP` 广泛用于绝大多数内部身份服务，最著名的是 `Active Directory`。目录服务在许多应用程序中发挥着关键作用，通过 `LDAP` 暴露关键用户、计算机、服务和其他对象以供查询。

`LDAP` 是一种应用层协议，通过 `TCP` 或 `UDP` 使用端口 `389`。`LDAP` 查询可以以明文传输，并且根据配置，可能允许匿名查询部分或全部数据。自然地，`LDAP` 确实支持经过身份验证的连接，也支持利用 `TLS` 的安全通信通道。

### Kerberos

`Kerberos` 是一种第三方认证服务，可用于支持 `单点登录 (Single Sign-On)`。`Kerberos` ([`www.kerberos.org/`](https://www.kerberos.org/)) 这个名字源自希腊神话中守护哈迪斯（也称刻耳柏洛斯）入口的三头犬。神话中 `Kerberos` 的三头意在象征 `AAA` 系统的三个“A”：认证、授权和审计。实际上，最初的 `Kerberos` 主要提供认证。现在有人认为 `Kerberos` 的三头代表客户端、`密钥分发中心 (Key Distribution Center, KDC)` 和服务器。

**考试警告**

`Kerberos` 是在 `麻省理工学院 (MIT)` 的 `Project Athena` 项目下开发的。`Kerberos` 极易成为考点；最好学会 `Kerberos` 的工作原理。

`Kerberos FAQ`（参见 [`www.faqs.org/faqs/kerberos-faq/user/`](http://www.faqs.org/faqs/kerberos-faq/user/)）指出：“`Kerberos` 是一种用于物理上不安全网络的网络认证系统，基于 Needham 和 Schroeder 提出的密钥分发模型。它允许通过网络通信的实体相互证明身份，同时防止窃听或重放攻击。它还使用诸如 `DES (数据加密标准)` 之类的密码系统，提供数据流完整性（检测修改）和保密性（防止未经授权的读取）” [\[11\]](#Ch006_295-335_B9780443187346000052.xhtml#bb0060)。

#### Kerberos 特性

`Kerberos` 使用对称加密，并提供客户端和服务器的双向认证。它可防止网络嗅探和重放攻击。`Kerberos` 的当前版本是版本 5，由 `RFC 4120` 描述 [\[12\]](#Ch006_295-335_B9780443187346000052.xhtml#bb97)。

`Kerberos` 具有以下组件：

*   **主体**：客户端（用户）或服务
*   **域**：一个逻辑 `Kerberos` 网络
*   **票据**：验证主体身份的数据
*   **凭据**：一张票据和一个服务密钥
*   **KDC**：`密钥分发中心`，用于认证主体
*   **TGS**：`票据授予服务`
*   **TGT**：`票据授予票据`
*   **C/S**：`客户端/服务器`，关于两者之间的通信

#### Kerberos 操作步骤

一个 `Kerberos` 主体，由用户 Alice 运行的客户端，希望访问一台打印机。Alice 可以在完成以下五个（简化）步骤后进行打印：

1.  `Kerberos` 主体 Alice 联系 `KDC`（`密钥分发中心`，充当认证服务器），请求认证。
2.  `KDC` 向 Alice 发送一个会话密钥，该密钥使用 Alice 的密钥加密。`KDC` 还发送一个 `TGT`（`票据授予票据`），该票据使用 `TGS` 的密钥加密。
3.  Alice 解密会话密钥，并用它向 `TGS`（`票据授予服务`）请求打印权限。
4.  `TGS` 看到 Alice 拥有有效的会话密钥（因此证明了她的身份声明），向 Alice 发送一个 `C/S` 会话密钥（第二个会话密钥）供打印使用。`TGS` 还发送一张服务票据，该票据使用打印机的密钥加密。
5.  Alice 连接到打印机。打印机看到有效的 `C/S` 会话密钥，知道 Alice 有权打印，也知道 Alice 是真实的。

图 6.8 步骤 2 中的会话密钥使用 Alice 的密钥加密（表示为“{Session Key}Key^(Alice)”）。另请注意，`TGT` 使用 `TGS` 的密钥加密：Alice 无法解密 `TGT`（只有 `TGS` 可以）；她只是将其发送给 `TGS`。`TGT` 包含许多项目，包括 Alice 会话密钥的副本。这就是 `TGS` 知道 Alice 拥有有效会话密钥的方式（这证明了 Alice 已通过认证）。

**注意**

许多站点在一台系统上同时运行 `KDC` 和 `TGS` 服务，但它们也可以在单独的系统上运行。对于考试来说，将它们视为独立的系统会有所帮助。

TGT 适用于站点选定的特定生命周期，通常设置为 10 小时（工作日的长度，再加上几个小时）。这允许典型用户进行一次身份验证，并在票据的生命周期内访问网络资源。Kerberos 因此是无状态的：一旦 Alice 拥有了 TGT，她就可以在其生命周期内使用它，即使 KDC 离线也没关系。此外，TGS 可以允许 Alice 打印而无需咨询 KDC：TGS 所需了解的一切都包含在 Alice 发送的流量中，包括 TGT 和第一个认证器。

Alice 发送给打印机的服务票据也是如此。它是用打印机的密钥加密的，并包含一份客户端/服务器会话密钥的副本。Alice 无法解密它，只是将其原封不动地传回给打印机。这使得打印机能够完全根据 Alice 发送的内容做出决定，而无需咨询 KDC 或 TGS。

> **注意**
>
> 本节（以及考试）描述的是“原生” Kerberos，而非特定供应商的实现，例如 Microsoft Windows Active Directory 中的 Kerberos。

#### Kerberos 的优势

Kerberos 提供客户端和服务器的相互认证。我们已经了解到 TGS 和服务器（如打印机）如何知道主体 Alice 已通过认证。Alice 也知道 KDC 是真正的 KDC。真正的 KDC 同时知道 Alice 和 TGS 的密钥。如果一个流氓 KDC 假装成真正的 KDC，它将无法访问这些密钥。图 6.9 展示了 Alice 尝试通过流氓 KDC 进行认证的步骤 1 和 2。

![图 6.9 流氓 KDC。](img/f06-09-9780443187346.jpg)

图 6.9 流氓 KDC。

流氓 KDC 不知道 Alice 或 TGT 的密钥。因此它提供垃圾密钥（`Key^(garbage)`）。当 Alice 尝试解密会话密钥时，她将得到垃圾数据，而不是有效的会话密钥。Alice 就会知道该 KDC 是伪造的。

Kerberos 通过使用时间戳来缓解重放攻击（攻击者嗅探 Kerberos 凭据并在网络上重放它们）。认证器包含一个时间戳，请求的服务将拒绝任何过旧的认证器（通常为 5 分钟）。使用 Kerberos 的系统上的时钟需要同步，原因就在于此：时钟偏差会使认证器失效。

除了相互认证外，Kerberos 还是无状态的：由 KDC 或 TGS 颁发的任何凭据在其生命周期内均有效，即使 KDC 或 TGS 宕机也是如此。

#### Kerberos 的弱点

Kerberos 的主要弱点在于 KDC 存储了所有主体（客户端和服务器）的密钥。KDC 遭到攻破（物理或电子方式）可能导致 Kerberos 领域中每个密钥的泄露。

KDC 和 TGS 也是单点故障：如果它们宕机，将无法颁发新凭据。现有凭据仍可使用，但新的身份验证和服务授权将停止。

在认证器的生命周期内，重放攻击仍然可能发生。攻击者可以嗅探认证器，针对客户端发起拒绝服务攻击，然后冒充或欺骗客户端的 IP 地址。

在 Kerberos 4 中，任何用户都可以为另一个用户请求会话密钥。因此 Eve 可以说：“嗨，我是 Alice，我想进行身份验证。”然后 KDC 会发送一个用 Alice 的密钥加密的 TGT 和会话密钥给 Eve。Eve 随后可以对加密的会话密钥发起本地密码猜测攻击，尝试猜出 Alice 的密钥。Kerberos 5 增加了一个额外步骤来缓解此攻击：在图 6.8 的步骤 1 中，Alice 用她的密钥加密当前时间并将其发送给 KDC。KDC 知道 Alice 是真实的（拥有她的密钥），然后继续执行步骤 2。
