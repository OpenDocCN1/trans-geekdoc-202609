
一些软件即服务（SaaS）供应商通过云提供安全服务。例如，Barracuda Networks 包含类似于下一代防火墙和 UTM 设备的基于云的解决方案。例如，他们的 Web Security Service 充当 Web 浏览器的代理。管理员配置代理设置以访问基于云的系统，并根据组织需求执行 Web 过滤。同样，他们拥有基于云的 Email Security Gateway，可执行入站垃圾邮件和恶意软件过滤。它还可以检查出站流量，以确保其符合组织的数据丢失防护策略。

### 渗透测试

`渗透测试`是组织用来应对攻击的另一种预防措施。渗透测试（通常简称为`pentest`）模拟实际攻击，试图识别攻击者可用于绕过应用程序、系统、网络或组织安全性的技术。它可能包括漏洞扫描、端口扫描、数据包嗅探、DoS 攻击和社会工程学技术。

安全专业人员在执行渗透测试时会尽量避免停机。然而，渗透测试具有侵入性，可能会影响系统的可用性。因此，安全专业人员在执行任何测试之前，获得高级管理层的书面批准极为重要。

定期进行的渗透测试是评估组织内部安全控制有效性的好方法。渗透测试可能会揭示补丁或安全设置不足的领域、新漏洞出现或暴露的领域，以及安全策略无效或未被遵循的领域。攻击者可以利用这些漏洞中的任何一个。

渗透测试通常包括漏洞扫描或漏洞评估以检测弱点。然而，渗透测试更进一步，尝试利用这些弱点。例如，漏洞扫描器可能会发现一个带有后端数据库的网站未使用输入验证技术，容易受到 SQL 注入攻击。渗透测试随后可能会使用 SQL 注入攻击来访问整个数据库。同样，漏洞评估可能会发现员工未接受过社会工程学攻击教育，渗透测试可能会使用社会工程学方法进入安全区域或从员工处获取敏感信息。

以下是渗透测试的一些目标：

*   确定系统承受攻击的能力
*   识别员工实时检测和响应攻击的能力
*   识别可实施的额外控制措施以降低风险

#### 渗透测试的风险

渗透测试的一个重大危险是某些方法可能导致停机。例如，如果漏洞扫描发现基于互联网的服务器易受缓冲区溢出攻击，渗透测试利用该漏洞可能导致服务器关闭或重启。

理想情况下，渗透测试应在造成实际损害前停止。不幸的是，测试人员通常直到采取该步骤才知道哪一步会造成损害。例如，模糊测试器向应用程序或系统发送无效或随机数据以检查响应。模糊测试器可能会发送导致缓冲区溢出并锁定应用程序的数据流，但测试人员直到运行模糊测试器才会知道会发生这种情况。经验丰富的渗透测试人员可以最大限度地降低测试造成损害的风险，但无法消除风险。

只要可能，测试人员会在测试系统上而非实时生产系统上执行渗透测试。例如，在测试应用程序时，测试人员可以在沙箱等隔离环境中运行和测试应用程序。如果测试造成损害，仅影响测试系统，而不影响实时网络。挑战在于测试系统通常无法提供生产环境的真实视图。测试人员可能能够在测试环境中测试不与其他系统交互的简单应用程序。然而，大多数需要测试的应用程序并不简单。当使用测试系统时，渗透测试人员通常会限定其分析，并声明测试是在测试系统上完成的，因此结果可能无法提供对生产环境的有效分析。

#### 获取渗透测试许可

渗透测试应仅在仔细考虑并获得高级管理层批准后执行。许多安全专业人员坚持以书面形式获得此批准，并明确列出风险。执行未经批准的安全测试可能导致生产力损失并触发应急响应团队。

### 恶意员工与渗透测试

意图破坏 IT 环境安全的恶意员工可依据现有法律受到惩罚。同样，如果内部员工在未经授权的情况下对系统进行非正式的未授权测试，组织可能会将其行为视为非法攻击，而非渗透测试。这些员工极有可能失去工作，甚至面临法律后果。

#### 渗透测试技术

组织聘请外部顾问执行渗透测试是常见做法。组织可以控制提供给这些测试人员的信息，而提供给他们的知识水平决定了他们执行的测试类型。

##### 零知识团队的黑盒测试

`zero-knowledge team`（零知识团队）除了公开可用的信息（如域名和公司地址）外，对目标站点一无所知。这就像他们透过黑盒观察目标，在开始探测之前完全不知道盒子里有什么。零知识团队的攻击非常类似于真实的外部攻击，因为关于环境的所有信息都必须从头获取。

##### 全知识团队的白盒测试

`full-knowledge team`（全知识团队）拥有对目标环境所有方面的完全访问权限。他们知道安装了哪些补丁和升级，以及所有相关设备的确切配置。如果目标是应用程序，他们将拥有源代码访问权限。全知识团队执行白盒测试（有时称为水晶盒测试或透明盒测试）。白盒测试普遍被认为在定位漏洞方面更高效、更具成本效益，因为所需的发现时间更少。

##### 部分知识团队的灰盒测试

拥有目标部分知识的 `partial-knowledge team`（部分知识团队）执行灰盒测试，但他们并未获得所有信息的访问权限。他们可能会被提供网络设计和配置详情等信息，以便他们将重点放在针对特定目标的攻击和漏洞上。

常规负责保护渗透测试目标的安全管理人员可被视为全知识团队。然而，他们并不是执行渗透测试的最佳人选。他们在对某些安全主题的理解、评估或能力方面往往存在盲点或差距。如果他们知道某个可被利用的漏洞，他们很可能早已建议采取控制措施将其降至最低。全知识团队知道什么已被保护，因此可能会因依赖错误假设而无法妥善测试所有可能性。零知识或部分知识测试人员不太可能犯这些错误。

渗透测试可能采用自动化攻击工具或套件，也可能使用常见网络实用工具手动执行。自动化攻击工具范围广泛，从专业漏洞扫描器和渗透测试工具，到攻击者在互联网上共享的地下工具。有多种开源和商业工具（如 `Metasploit`）可用，安全专业人员和攻击者都在使用这些工具。

社会工程学技术常用于渗透测试中。根据测试目标，测试人员可能会使用技术突破组织的物理边界，或诱导用户泄露信息。这些测试有助于确定员工对熟练社会工程师的脆弱程度，以及他们对旨在挫败此类攻击的安全策略的熟悉程度。

### 保护报告

渗透测试人员将提供一份记录其结果的报告，该报告应作为敏感信息受到保护。报告将概述具体漏洞以及如何利用这些漏洞。报告通常还会包含关于如何缓解漏洞的建议。如果这些结果在组织实施建议之前落入攻击者手中，攻击者可利用报告中的细节发动攻击。

同样重要的是要认识到，渗透测试团队提出建议并不意味着组织就会实施该建议。管理层可以选择实施建议以缓解风险，或者如果认为建议控制措施的成本无法得到合理解释，则选择接受风险。换句话说，一年前的报告可能列出了一个至今未缓解的特定漏洞。这份一年前的报告应像昨天刚完成的报告一样受到严密保护。

### 道德黑客

`Ethical hacking`（道德黑客）常被用作渗透测试的另一个名称。`ethical hacker`（道德黑客）是指了解网络安全和突破安全的方法，但不将此知识用于个人谋利的人。相反，道德黑客利用这些知识帮助组织了解其漏洞并采取行动防范恶意攻击。道德黑客始终在法律范围内行事。

第 14 章提到了破解者、黑客和攻击者之间的技术区别。黑客的原始定义是无恶意的技术爱好者，而破解者或攻击者则是恶意的。由于“hacker”一词常被用作“attacker”的同义词，其原始含义已变得模糊。换句话说，大多数人将黑客视为攻击者，给人的印象是道德黑客是一个自相矛盾的术语。然而，“ethical hacking”一词中的“hacker”使用的是其原始含义。

道德黑客将学习并经常使用攻击者使用的相同工具和技术。然而，他们不使用这些工具攻击系统。相反，他们仅在组织明确授予许可后，使用这些工具测试系统的漏洞。

### 日志记录、监控与审计

日志记录、监控和审计程序有助于组织预防事件，并在事件发生时提供有效响应。以下部分涵盖日志记录和监控，以及用于评估访问控制有效性的各种审计方法。

### 日志记录与监控

日志记录将事件记录到各种日志中，监控则审查这些事件。二者结合使组织能够跟踪、记录和审查活动，提供整体问责制。

这有助于组织检测可能对系统的机密性、完整性或可用性产生负面影响的不良事件。它在事件发生后重建活动以确定发生了什么，有时还能起诉责任人方面也很有用。

##### 日志记录技术

`Logging`（日志记录）是将有关事件的信息记录到日志文件或数据库的过程。日志记录捕获事件、更改、消息和其他描述系统上发生的活动的数据。日志通常会记录诸如发生了什么、何时发生、在哪里发生、谁做的，有时还包括如何发生的等详细信息。当你需要查找近期发生的事件信息时，日志是一个很好的起点。

###### 常见日志类型

有许多不同类型的日志。以下是 IT 环境中可用的常见日志简要列表。

**安全日志** 安全日志记录对资源（如文件、文件夹、打印机等）的访问。例如，它们可以记录用户何时访问、修改或删除了文件，如前文 图 17.5 所示。许多系统会自动记录对关键系统文件的访问，但要求管理员在其他资源上启用审核后才记录访问。例如，管理员可能会为专有数据配置日志记录，但不对网站上发布的公共数据进行记录。

**系统日志** 系统日志记录系统事件，例如系统何时启动或关闭，或服务何时启动或停止。如果攻击者能够关闭系统并使用 CD 或 USB 闪存驱动器重新启动，他们可以在没有任何数据访问记录的情况下窃取系统数据。同样，如果攻击者能够停止监控系统的服务，他们可能会在日志未记录其行为的情况下访问系统。记录系统重启或服务停止时间的日志可以帮助管理员发现潜在的恶意活动。

**应用程序日志** 这些日志记录特定应用程序的信息。应用程序开发人员选择在应用程序日志中记录什么内容。例如，数据库开发人员可以选择记录任何人何时访问特定的数据对象，如表或视图。

**防火墙日志** 防火墙日志可以记录与到达防火墙的任何流量相关的事件。这包括防火墙允许的流量和防火墙阻止的流量。这些日志通常记录关键数据包信息，如源和目标 IP 地址、源和目标端口，但不记录数据包的实际内容。

**代理日志** 代理服务器可以提高用户的互联网访问性能，并能控制用户可以访问的网站。代理日志包括记录详细信息的能力，例如特定用户访问了哪些网站以及在这些网站上花费了多少时间。它们还可以记录用户何时尝试访问已知的禁止网站。

**变更日志** 变更日志记录变更请求、批准以及作为整体变更管理过程一部分的系统实际变更。变更日志可以手动创建，也可以通过内部网页在人员记录与变更相关的活动时创建。变更日志可用于跟踪已批准的变更。它们作为灾难恢复计划的一部分也很有帮助。例如，灾难发生后，管理员和技术人员可以使用变更日志将系统恢复到最后已知状态，包括所有已应用的变更。

日志记录通常是操作系统以及大多数应用程序和服务的原生功能。这使得管理员和技术人员配置系统以记录特定类型的事件变得相对容易。应在任何日志记录计划中包含来自管理员和 root 用户账户等特权账户的事件。这有助于防止恶意内部人员的攻击，并在必要时为起诉记录活动。

###### 保护日志数据

组织内部人员可以使用日志重现事件发生前和发生期间的情况，但前提是日志未被修改。如果攻击者可以修改日志，他们可以抹除自己的活动，从而有效地使数据失去价值。这些文件可能不再包含准确信息，并且可能无法作为起诉攻击者的可采纳证据。考虑到这一点，防止未经授权的访问和未经授权的修改来保护日志文件非常重要。

通常会在中央系统（如 `SIEM`）上存储日志副本以保护它们。即使攻击修改或损坏了原始文件，人员仍可使用副本查看事件。保护日志文件的一种方法是分配权限以限制其访问。

组织通常有严格的政策，强制要求备份日志文件。此外，这些政策还定义了保留时间。例如，组织可能会保留归档日志文件一年、三年或任何其他时长。某些政府法规要求组织无限期保留归档日志。安全控制措施（如将日志设置为只读、分配权限和实施物理安全控制）可保护归档日志免受未经授权的访问和修改。在日志不再需要时销毁它们很重要。

美国国家标准与技术研究院（`NIST`）发布了大量关于 IT 安全的信息，包括*联邦信息处理标准（`FIPS`）出版物*。*联邦信息和信息系统的最低安全要求（`FIPS 200`）* 将以下内容指定为审计数据的最低安全要求：

> 创建、保护和保留信息系统审计记录，程度应足以支持对非法、未经授权或不当的信息系统活动进行监控、分析、调查和报告。
>
> 确保能将各个信息系统用户的行为唯一地追溯到这些用户，以便让他们对自己的行为负责。

##### 监控的作用

监控为组织提供多种益处，包括增加问责性、协助调查和基本故障排除。以下部分将更深入地描述这些益处。

###### 审计跟踪

*审计跟踪* 是当有关事件和发生情况的信息存储在一个或多个数据库或日志文件中时创建的记录。它们提供系统活动的记录，并可重现安全事件发生前和发生期间的活动。安全专业人员从审计跟踪中提取有关事件的信息，以证明或反驳过错等。审计跟踪允许安全专业人员按正序或逆序检查和追踪事件。这种灵活性在追踪问题、性能问题、攻击、入侵、安全漏洞、编码错误和其他潜在策略违规时很有帮助。

使用审计跟踪是一种被动的侦察型安全控制。它们的威慑作用方式与闭路电视（`CCTV`）或保安相同。如果人员知道他们正被监视且其活动正被记录，他们就不太可能从事非法、未经授权或恶意活动——至少在理论上是这样。有些罪犯过于粗心或无知，导致这并不总是一致适用。然而，越来越多的高级攻击者会花时间定位并删除可能记录其活动的日志。这已成为许多高级持续性威胁的标准做法。

审计跟踪作为起诉罪犯的证据也至关重要。它们提供资源、系统和资产状态的前后对比图景。这反过来有助于确定某项更改或变更是用户、操作系统（`OS`）或软件的行为导致的，还是由其他来源（如硬件故障）导致的。由于审计跟踪中的数据非常有价值，因此确保日志受到保护以防止修改或删除非常重要。

###### 监控与问责制

### 监控

监控是一项必要的功能，旨在确保主体（如用户和员工）对其行为和活动负责。用户声明身份（如使用用户名）并证明其身份（通过认证），审计追踪记录他们在登录期间的活动。监控和审查审计追踪日志可为这些用户提供问责制。

这直接促进了积极的用户行为和对组织安全策略的遵守。知晓日志正在记录其 IT 活动的用户，不太可能试图绕过安全控制或执行未经授权或受限的活动。

一旦发生安全策略违规或违规事件，应确定违规的来源。如果能够识别出责任人，应根据组织的安全策略追究其责任。严重案例可能导致解雇或法律起诉。

立法通常要求特定的监控和问责实践。这包括《2002 年萨班斯-奥克斯利法案》、《健康保险流通与责任法案》（HIPAA）以及许多组织必须遵守的欧盟（EU）隐私法。

#### 监控与调查

审计追踪赋予调查人员在事件发生很久之后重构事件的能力。它们可以记录访问滥用、特权违规、入侵尝试以及多种不同类型的攻击。在检测到安全违规后，安全专业人员可以通过仔细检查审计追踪，重构事件发生前、发生期间和发生后的条件及系统状态。

一个重要的考量因素是确保日志具有准确的时间戳，并且这些时间戳在整个环境中保持一致。一种常用方法是设置一个内部网络时间协议（NTP）服务器，并将其与受信任的时间源（如公共 NTP 服务器）同步。然后，其他系统可以与此内部 NTP 服务器同步。

NIST 运营多台支持认证的时间服务器。一旦 NTP 服务器正确配置，NIST 服务器将响应加密且经过认证的时间消息。该认证提供了响应来自 NIST 服务器的保证。

#### 监控与问题识别

审计追踪提供了关于已记录事件的详细信息，这对管理员很有用。除了恶意攻击外，它们还可以记录系统故障、操作系统漏洞和软件错误。某些日志文件甚至可以在应用程序或系统崩溃时捕获内存内容。这些信息有助于确定事件原因，并排除其作为可能攻击的嫌疑。例如，如果系统因内存故障频繁崩溃，转储文件有助于诊断问题。

将日志文件用于此目的通常称为问题识别。一旦识别出问题，执行问题解决所涉及的工作仅仅是跟进所披露的信息。

#### 监控技术

**监控**是审查信息日志以查找特定内容的过程。人员可以手动审查日志，或使用工具实现自动化。监控对于检测主体的恶意行为、入侵尝试和系统故障至关重要。它有助于重构事件、为起诉提供证据并创建分析报告。

重要的是要理解监控是一个持续的过程。持续监控确保记录所有事件，以便日后必要时进行调查。许多组织在发生事件或疑似事件后会增加日志记录，以收集关于攻击者的更多情报。

**日志分析**是一种详细且系统的监控形式，其中对记录的信息进行分析以发现趋势和模式，以及异常、未经授权、非法和违反策略的活动。日志分析不一定是对事件的响应，而是一项定期任务，可检测潜在问题。

在手动分析日志时，管理员只需打开日志文件并查找相关数据。这可能非常繁琐且耗时。例如，即使使用内置搜索工具，在 10 个不同的归档日志中搜索特定事件或 ID 代码也需要一些时间。

在许多情况下，日志会产生大量信息，导致重要细节淹没在海量数据中，因此管理员通常使用自动化工具分析日志数据。例如，入侵检测系统（IDS）主动监控多个日志，以实时检测恶意入侵并做出响应。IDS 可帮助检测和追踪来自外部攻击者的攻击，向管理员发送警报，并记录攻击者对资源的访问。

多家供应商销售运维管理软件，该软件主动监控网络中各系统的安全性、健康状况和性能。该软件自动查找表明存在问题（如攻击或未经授权的访问）的可疑或异常活动。

##### 安全信息与事件管理

许多组织使用集中式应用程序来自动监控网络上的系统。有多个术语用于描述这些工具，包括安全信息与事件管理（SIEM）、安全事件管理（SEM）和安全信息管理（SIM）。这些工具提供对组织内各系统发生事件的实时分析。它们包括安装在远程系统上的代理，用于监控称为警报触发器的特定事件。触发器发生时代理将事件报告回中央监控软件。

例如，SIEM 可以监控一组邮件服务器。每当某台邮件服务器记录一个事件，SIEM 代理就会检查该事件以确定其是否为关注项。如果是，SIEM 代理会将事件转发给中央 SIEM 服务器，并根据事件类型，可为管理员触发警报。例如，如果邮件服务器的发送队列开始积压，SIEM 应用程序可在问题变得严重之前检测到该问题并提醒管理员。
