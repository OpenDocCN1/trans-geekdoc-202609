
# 参考约束与表修改

## references 子句语法

```
references table [ (col-list) ][ match { full | partial | simple } ][ delete-action [ update-action ] | update-action [ delete-action ] ]
```

其中 `delete-action` 的语法为：

`on delete` { `no action` | `cascade` | `set null` | `set default` }

`update-action` 的语法为：

`on update` { `no action` | `cascade` | `set null` | `set default` }

如果尝试通过插入、删除或更新操作更改数据库，且该操作会违反参照约束，默认的 `no action` 选项将拒绝该更改。其他三个参照动作选项接受该更改，但也会采取一些补偿措施以保持数据库一致性。`cascade` 选项将更改传播到所有引用的外键值；`set null` 将相关外键值设为 null；`set default` 将相关外键值设为列默认值。例如，考虑以下关系模式：

这里有一个包含两个子集约束的链。假设为两个约束都声明了 `on delete cascade`。如果我们尝试从 `CarModel` 表中删除车型 "Ford T"，该删除操作会被接受。但如果 `Car` 表中存在车型为 "Ford T" 的行，它们也会被删除，进而导致 `Drives` 表中注册号匹配的行也被删除。

SQL-92 引入了 `match` 操作符作为布尔运算符，用于测试元组是否属于一个元组集合，即 `(*a*[1], …, *a*[n])` ∈ `{(*b*[1], …, *b*[n]), …}`？除布尔特性外，它是 `in` 操作符的推广，可用于以下形式的搜索条件：`(*a*[1], …, *a*[n])` **match** [`unique`] [`full` | `partial` | `simple`] `(*subquery*)`。**unique** 选项要求元组恰好匹配一行。默认情况下，或声明了 **simple** 时，如果所有值 `*a*[1]`..`*a*[n]` 都匹配或*部分*为 null，匹配操作返回 True；否则返回 False。如果指定了 **full**，当所有值 `*a*[1]`..`*a*[n]` 都匹配或*全部*为 null 时，匹配操作返回 True；否则返回 False。如果指定了 **partial**，当所有*非空*值都匹配时，匹配操作返回 True；否则返回 False。**match** 操作符也可用于 **references** 子句中，方式类似。虽然 SQL-89 的 **references** 子句语法被广泛支持，但大多数 SQL 方言对 SQL-92 或 SQL:1999 中进一步的参照语法支持较少。

## 修改表定义

创建并填充基表后，我们可能希望更改其定义。这在 SQL-89 中是不可能的，但 SQL-92 允许使用 `alter table` 语句更改表模式。SQL:1999 稍微扩展了此功能以适应列作用域。每项更改需要单独的语句。基本语法如下：

```
alter table tablename add [ column ] col-defn  | alter [ column ] colname set default-defn | drop default | drop [ column ] colname restrict | cascade | add table-constraint-defn  | drop constraint constraint-name restrict | cascade
```

如果指定了 `restrict` 且该列在约束或视图定义中被引用，则不允许删除该列。`cascade` 选项会导致其他定义也被删除。商业 SQL 通常不支持删除列或约束的 `restrict` 或 `cascade` 选项。

尽管标准禁止更改列的数据类型，但某些方言允许将列的数据类型更改为“更大的类型”，例如将 `roomNr` 列从 `char(2)` 改为 `char(4)`。许多供应商不支持某些 alter 操作，例如 `drop column`。为简化自动建表，某些供应商倾向于在 `alter table` 语句中添加大多数表约束。以下示例不言自明：

```
alter table Person add column email_address varchar(20)
alter table Person add foreign key starsign references starsignPeriod
```

SQL-92 允许使用 `drop table` 语句从数据库中删除表（包括其数据）。虽然 SQL-89 不允许这样做，但所有供应商都支持该功能。语法如下：

```
drop table tablename cascade | restrict
```

如果指定了 `restrict` 且该表在约束或视图定义中被引用，则不允许删除该表。`cascade` 选项会导致其他定义也被删除。大多数商业 SQL 此处不要求 cascade/restrict。

作为迈向用户定义类型的第一步，SQL-92 引入了用于创建、修改和删除语法 **域** 的语句。定义域后，可在列定义中使用它。例如：

```
create domain Money as decimal ( 9, 2 )
```

```
create domain Gendercode as char
constraint ValidGendercode check ( value in ( 'F' , 'M' ) )
```

```
create domain Centimeters as smallint check ( value > 0 )
```

```
create domain Kilograms as smallint check ( value > 0 )
```

```
create table Employee (
    empNr            smallint                    not null primary key,
    gender           Gendercode                  not null,
    ...
)
```

# SQL: 视图

除了定义基本表之外，SQL 还允许我们定义**视图**，或称为“虚拟表”，它们本质上是*命名的派生表*。它们的定义会被存储，但其内容不会。通过视图定义，对视图的查询和更新会自动转换为对基本表的等效查询/更新。因此，与你可能创建用于临时存储结果的工作表不同，视图始终是最新的。

视图有许多用途。出于安全原因，可以通过允许特定用户组访问视图而非其底层基本表来使用视图。它们还可以用于隐藏不需要的细节、简化查询或更新、实施派生规则，并允许以最小影响重构基本表。它们的主要局限性在于某些视图无法更新，且对视图的查询有时会降低性能。关于使用视图和生成列实现派生规则的进一步讨论，请参阅随书附带的网站。

视图是使用 `create view` 语句创建的。SQL-89 语法如下：

```
create view viewname [ (col-list) ] as
    select-query
    [ with check option ]
```

因为视图的结果是一个派生表，所以视图中的 `select` 语句可以引用其他视图以及基本表。事实上，从 `select` 语句的角度来看，对表的查询和对视图的查询几乎没有区别。

SQL-92 允许将检查选项限定为 local（本地）或 cascaded（级联），而 SQL:1999 允许视图为递归的并基于用户定义类型。虽然 SQL-89 不允许删除视图，但 SQL-92 可以，语法如下：

```
drop view viewname { restrict | cascade }
```

如果指定了 `restrict` 选项，当视图被另一个视图或约束引用时，该视图不会被删除。如果指定了 `cascade` 选项，该视图以及引用它的任何视图或约束都将被删除。许多方言（包括 SQL Server）尚不支持这两个选项。虽然标准未提供 `alter view` 语句，但某些方言（包括 SQL Server 的 T-SQL）提供了该语句。修改视图而不是删除并重新创建它的一个优势是，与视图关联的任何权限得以保留。

用于定义视图的 `select` 查询适用某些限制，尽管细节取决于 SQL 方言。通常，不允许使用 `order-by` 子句或任何 `union`、`intersect` 或 `except` 运算符。*可更新视图*可用于插入、删除或修改行。针对可更新视图适用更多限制（稍后讨论）。

考虑用于存储教职工详细信息的表模式 `Academic` ( empNr, empName, dept, [ gender ], grade )。表 13.1 包含部分数据。dept 列存储教职工的部门代码（例如，CS = 计算机科学，MA = 数学），grade 列是教职工的职级（例如，Lec = 讲师，Prof = 教授）。例如，要检索计算机科学系的女教授，我们请求：

```
select empNr, name from FemaleCompScientist
where rank = ‘Prof’ → Rolland, C
```

以下语句可用于创建一个仅包含女性计算机科学家的视图。存储该定义后，我们可以像视图对应的表真实存在一样进行操作，如 表 13.2 所示。

```
create view FemaleCompScientist ( empNr, name, rank ) as
select empNr, empName, grade from Academic
where dept = ‘CS’ and gender = ‘F’
```

处理此查询时，会访问视图定义并用于自动将查询转换为以下针对底层基本表的等效查询。然后处理基本表查询以生成结果：

```
select empNr, empName
from  Academic
where dept = ‘CS’ and gender = ‘F’
and grade = ‘Prof’ → Rolland, C
```

该视图仅基于单个表的投影和选择。让我们看一个基于连接的更复杂的例子。考虑表模式 `ParentOf` ( parent, child )。图 13.2 显示了一个示例数据。为简单起见，假设人员由其名字标识。

现在考虑查询：谁是 Fred 的祖父母？为了便于回答该问题，图 13.2 包含一个图，其中从一个节点到另一个节点的虚线箭头表示前者是后者的父母。从 Fred 开始，我们可以轻松找到 Chris 作为 Fred 唯一记录在案的父母，然后向上移动到 Chris 的父母。因此，答案是集合 {Ann, Bill}。我们也可以使用表遵循此过程。该查询使用成员资格子查询在 SQL 中很容易表述，如下所示：

```
select parent from ParentOf
where child in
    ( select parent from ParentOf
    where child = ‘Fred’ )
```

但现在假设我们经常想在不同场合列出不同人的祖父母。我们可以通过为 `GrandparentOf` ( grandparent, grandchild ) 关系定义一个视图来节省一些工作，如下所示：

## 视图定义与更新

```sql
create view GrandparentOf ( grandparent, grandchild ) as
select A.parent, B.child
from ParentOf as A join ParentOf as B
on A.child = B.parent
```

此视图定义涉及自连接上的投影，其中将祖父母的 child 与孙辈的 parent 进行匹配。表 13.3 显示了虚拟填充内容，可使用命令 `select * from GrandParentOf` 列出。

可使用 `select * from GrandparentOf where grandchild = 'Fred'` 列出 Fred 的祖父母。通过用其他人名替换 "Fred"，可查询任意人的祖父母。虽然该视图对查询显然有用，但它也可用于更新吗？

正如上一章所讨论的，可使用 `insert` 命令向基表插入行。假设我们尝试向视图插入一行：

```sql
insert into GrandparentOf values ( 'Bernie', 'Selena' )
```

视图上的更新必须转换为基表上的等价更新。但因我们不知道中间父母（即 Selena 的父母），此时最多只能向 `ParentOf` 表添加以下两行：

```
ParentOf: parent child
        -------------
        Bernie   ?
        ?     Selena
```

这是不可接受的，因为这并未真正表明 Bernie 是 Selena 的祖父母。事实上，这两行无论如何都不满足视图定义，因为它们不满足连接条件 `A.child = B.parent`。此处两值均为 null，条件评估为 unknown，导致行 ("Bernie", "Selena") 被视图排除。因此，`GrandparentOf` 视图是**不可更新**的。

SQL-92 对可更新视图的类型施加了许多限制（多于逻辑要求）。特别是，可更新视图不得包含连接、并集（或交集、差集）、`distinct` 选项和 `group by` 子句。SQL Server 通过在视图上使用 `instead-of` 触发器绕过了许多此类限制（见后文）。

即使没有连接，若视图排除了其搜索条件中使用的列，也会出现类似的 null 问题。例如，假设我们在 `FemaleCompScientist` 视图上尝试以下插入：

```sql
insert into FemaleCompScientist values ( 105, 'Bird, L', 'Lec' )
```

若允许此更新，"Bird, L" 是否包含在结果中？根据之前的视图定义，若接受该更新，将转换为向 `Academic` 表插入以下行：(105, "Bird, L", **null**, **null**, "Lec")。新行因条件 ( dept = 'CS' **and** gender = 'F' ) 评估为 unknown 而不满足视图定义。因此，若接受更新，它并不属于该视图！

最好拒绝任何不满足视图定义的更新。这通过在视图定义后附加 "**with check option**" 实现。例如，以下视图可用于计算机科学教授：

```sql
create view CSProfessor ( empNr, name, dept, rank ) as
select empNr, empName, dept, grade
from Academic
where grade = 'Prof' and dept = 'CS'
with check option
```

以下尝试更新此视图将产生所示结果。

```sql
insert into CSProfessor
values ( 106,'Wirth N','CS','Prof' )  →  accepted
```

```sql
insert into CSProfessor
values ( 107,'Russell B','MA','Prof' )  →  rejected
```

```sql
update CSProfessor
set rank = 'Lec'
where empNr = 103  →  rejected
```

迄今考虑的视图类型本质上是对一个或多个基表的预定义查询。查询结果不存储在视图中，仅存储查询定义。对视图的后续查询将与视图定义中的查询结合，组合查询针对基表运行。这确保结果始终与基表内容同步，但若频繁查询视图可能效率低下。

另一种选择是执行视图定义的查询并缓存结果。此时视图代表物理存储中实际的数据结构，而非仅数据结构的定义。这称为**物化视图**。此类视图在效率上有明显优势，但基表数据的后续更改可能导致视图越来越不代表“真实”数据。支持物化视图的商业系统通常提供定期刷新它们的机制。

SQL:2003 向 `create table` 语句添加了新选项，允许基于 `select` 语句结果创建表。这提供了与物化视图类似的功能。基本语法为：

```sql
create table tablename as select-statement { with data | with no data }
```
