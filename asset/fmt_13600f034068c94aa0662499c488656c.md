
*Sequences*（有序包），如奖项列表，可在 ORM 中使用键中的位置类型建模（例如：`Lottery awarded prize of Rank to Person`），在 UML 中使用 `{ordered, nonunique}` 设置建模。*Arrays*（索引序列）的建模方式类似。

*Nominalization*（名词化）将动词重构为名词短语。在信息建模中，关系的对象化通常是*情境名词化*，即生成的对象是一种事态（如事件或活动），它与被对象化的关系一一对应，但不等同于该关系。例如：`Person sings Song`；**that** `Singing is delightful`。

在对象化情况下，ORM 会在底层创建*链接事实类型*（例如：`Singing is by Person`，`Singing is of Song`）。在极少数情况下，对象化是*命题名词化*，即讨论的对象是一个命题；这是 UML 中定义关联类的方式。在信息建模中，命题名词化通常可用情境名词化替代。

ORM 2 允许一元事实类型（例如：`President died`）被对象化（例如：`Death`），并包含对象化指南以帮助决定何时对象化（例如：除非 `n:1` 关联可能演变为 `m:n` 关联，或对象化类型有多个直接关联的事实类型，否则不要对象化 `n:1` 关联）。带有跨越唯一性约束的事实类型也可被对象化（例如：`Person speaks Language`，且 `Person visited Country in Year`）。ORM 2 还允许对象化恰好有一个跨越 `n−1` 个角色的唯一性约束的事实类型（`n ≥ 1`），但此类情况最好用其他方式建模。

`CWA` 假定所有相关事实均已知（在模型中作为断言事实或派生事实出现），并蕴含*失败即为假*（找不到或无法证明某命题即意味着它为假）。`OWA` 允许某些相关事实未知，并蕴含*经典否定*（找不到或无法证明某命题即意味着其真值未知）。

`SWA` 允许某些相关事实作为派生事实未知，但作为断言事实则已知，并蕴含*半正否定*（断言事实类型的缺失实例为假，但无法派生出某事实实例或其否定即意味着其真值未知）。`OWN` 允许某些相关事实未知，但也允许断言否定；作为 `OWA` 的特例，它蕴含经典否定。

目前正在考虑为 ORM 2 的一元事实类型提供图形符号以区分不同的封闭/开放世界风味（例如：虚线表示开放）。即使没有这些符号，也可通过引入否定谓词的一元类型或转换为二元类型来建模不同方法。实践中，`CWA` 和 `OWN` 是最有用的方法，分别可在 UML 和关系模式中用强制性布尔属性和可选布尔属性来体现。

*First-order logic*（一阶逻辑）仅对个体量化，不对谓词量化。高阶逻辑对个体和谓词均量化。*Higher-order type*（高阶类型）包含本身即为类型的实例。*Categorization type*（分类类型，如 `Gender`）用于将另一类型（如 `Person`）分类为子类型。UML 允许称为“powertypes”（幂类型）的高阶类型用作分类类型。

例如，在 UML 中，子类型 `Oak` 可被视为等同于幂类型 `TreeSpecies` 的一个实例，后者用于对类型 `Tree` 进行分类。高阶类型有时也用于直接建模元结构，并允许跨层级/元层级的规则。

高阶逻辑的高效实现比一阶逻辑复杂得多。实践中，通常在信息建模中避免使用高阶构造（且我们建议如此）。例如，分类类型的实例可视为个体，信息性事实类型可用于分类，不同层级可在不同模型中处理。然而，若在信息建模中使用高阶逻辑，我们建议使用受限 Henkin 语义。

从子类型指向超类型的箭头显示了一种类型层级关系，它蕴含连接子类型和超类型实例的实例层级同一性关系。*Inclusive-or constraints*（包含或约束）、*exclusion constraints*（排斥约束）和*subset subsets*（子集子集）可应用于*实例层级链接事实类型*的*超类型角色*。

通常，包含或约束应用于由同一对象类型承载的两个或多个角色。然而，*包含或约束也可应用于由不同类型承载的角色*，只要这些类型兼容即可。

## 11.1 实现概念模式

大多数数据库建模工具允许您使用一种或多种高层表示法（例如 ER、IDEF1X、ORM 或 UML）以及逻辑层表示法（例如关系模型）来录入数据模型。通常，高层（概念或半概念）模式必须映射到逻辑模式，然后再映射到物理模式，以便对数据库进行填充和查询。假设您首先在概念层进行建模，实现数据模型的主要步骤如下。

*   设计概念模式
*   根据需要使用映射选择标注概念模式
*   将设计映射到逻辑模式（例如关系或对象-关系）
*   根据需要微调逻辑模式（例如重命名或重排某些列）
*   生成物理模式（例如在 Microsoft SQL Server 或 IBM DB2 中）
*   创建外部模式（例如窗体、报表）
*   根据需要实施安全级别
*   填充数据库
*   发出查询和更新
*   根据需要更新模式

前几章讨论了如何设计概念模式。本章重点介绍将概念模型映射到逻辑模型。由于关系数据库系统被广泛使用，因此关系模型被用作逻辑模式。第 1 章 和 第 2 章 介绍了关于关系数据库的基本概念。第 11.2 节 总结了这些要点并简要加以扩展。第 11.3 节 讨论了将 ORM 模式映射到关系模式的基本过程。这可以很容易地调整以涵盖从其他表示法（如 ER 或 UML）的映射。正如 第 8 章 所讨论的，从 IDEF1X 到关系模型的映射是微不足道的。

第 11.4 节 讨论了关系映射的高级方面，包括使用概念标注来覆盖默认映射选择（例如，控制子类型如何映射）。自动映射完成后，可能需要对表名和列名进行一些微调以满足命名标准，并可能需要对列重新排序以提高性能。

一旦确定了逻辑模式（如果不是在此之前），就会选择目标数据库管理系统 (DBMS)。然后为该特定平台生成物理模式。调整物理模型以提高性能的某些方面将在后面的 第 14 章 中介绍（例如索引选择和反规范化）。

更新和查询倾向于在逻辑查询语言（例如 SQL 或 QBE）中进行，或通过定义在逻辑模式之上的外部窗体和报表界面进行。外部模式设计的某些方面将在后面的章节中介绍。对于多用户应用程序，不同用户组对表、窗体和报表的访问权限应由数据库管理员强制执行。第 12 章 和 第 13 章 指出了如何在 SQL 中声明表更新、查询和访问权限。

所有主要的关系 DBMS 要么直接支持 SQL，要么提供与 SQL 互译的工具。一些更高层的查询语言允许用户直接用维度（用于数据仓库）甚至概念模式构造来构建查询。其中一些将在后面的章节中讨论。

下一节将使用通用表示法总结关系数据库模式中的基本构造。随后的两节将讨论概念模式到关系模式的基本和高级映射。最后一节提供本章小结。

## 11.2 关系模式

### 关系模式

**关系模式**（relational schema，或关系数据库模式）是一组关系表定义、约束，或许还有推导规则。您可能希望回顾第 1.3 节和第 2.3 节，那里讨论了基本概念。单个关系表的结构称为**表模式**（table scheme）或关系变量。这基本上是一组命名的**属性**（列），它们的值取自数据**域**。每个表模式可以由一组未命名的数据**元组**（行）填充，但填充内容不是表模式本身的一部分。

### 表模式的表示法

存在许多用于表模式的**表示法**。`NORMA`工具使用垂直布局，其中列名垂直列出。为了节省空间并便于讨论填充内容，本书通常使用**水平布局**，即表名位于一个用逗号分隔的括号列名列表之前。如果需要，可以在列名后使用冒号分隔符显示域名。

例如，忽略约束，图 11.1(a) 中的 ORM 概念模式映射为表模式 `Employee( empNr: EmployeeNr, salary: Money, tax: Money )`。此处表名为“Employee”，属性 `empNr` 基于域 `EmployeeNr`，属性 `salary` 和 `tax` 均基于域 `Money`。

![图 11.1 将 ORM 模式映射为关系模式（省略约束）。](img/f11-01-9780443237904.jpg)

图 11.1 将 ORM 模式映射为关系模式（省略约束）。

因为基于单位的参考模式 USD 基于单位维度 `Money`，所以 ORM 模式也可以像图 11.1(b) 那样显示。

我们采用的惯例是：表名和域名以大写字母开头，属性名以小写字母开头。这种大小写惯例类似于 UML，且相当流行。无论您选择哪种大小写惯例，坚持使用它都将有助于使您的模式更具可读性。

使用水平布局时，我们通常用斜体书写表名。我们也倾向于连接名称组件，后续组件首字母大写（例如 `empNr`），而不是使用下划线或空格等分隔符（例如 `emp_nr` 或“emp nr”）。正如下一章所讨论的，SQL 标准要求包含空格字符的名称必须用双引号括起来。

建模工具通常允许您控制此类名称的生成方式。例如，`NORMA`工具允许您声明“Employee”在列名中缩写为“Emp”但不在表名中缩写，并且它可以利用角色名来确定列名。您可以选择自己的风格并坚持使用。为了紧凑，列出表模式时通常省略域名，例如 `Employee( empNr, salary, tax )`。

理论上，关系模型支持语义域，这基本上对应于 ORM 概念对象类型。1992 年之前，SQL 标准要求每个属性必须直接定义在数值或字符串数据类型上。例如：

```
Person ( surname: varchar(20), city: varchar(20), height: smallint, weight: smallint )
```
