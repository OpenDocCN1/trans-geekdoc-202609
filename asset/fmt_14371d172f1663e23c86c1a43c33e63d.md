
# NIST 指南将 `post-incident activities` 的 `lessons learned` 和改进步骤确定为事件响应生命周期中最重要的部分

这些步骤帮助组织在预期新威胁和改进技术方面不断发展。所有参与重大事件的各方应在响应工作结束后参与经验教训会议，以确定发生了什么、做了什么、本可以做却没做的事，以及响应计划的执行效果如何。

## 根因分析

实施遏制措施后，CSIRT 必须将注意力转向定位事件的根本原因。这是通过 `root-cause analysis` (`RCA`) 来完成的。RCA 是一种问题解决方法，用于将促成因素与根本原因区分开来。**促成因素** 是指移除后会提供改进条件但不能防止事件再次发生的任何条件。`root cause` 是指移除或中和后能防止事件再次发生的条件或项目。

应将所有收集到的事件数据汇总并彻底分析。对事件特征的分析可能会显示出需要解决的系统性安全问题，或者指出必须缓解的单一漏洞。无论哪种情况，该分析都可用于更新 IRP，并建议需要采取的任何额外控制措施，以加强组织的网络安全态势。

## 记录/报告

上一节列出的所有程序（包括响应期间采取的行动）都必须记录在案。如果有必要，可以请求联邦当局（如 CISA 或 NERC）协助进行更深入的分析。至少应分享经验教训，并调整公司安全策略以防止类似的后续攻击。

请回顾，最初的事件处理人员负责为处理可能成为证据的事件信息建立 `chain of custody`。这包括创建证据保管链文档。证据保管链文档应明确指定“谁、什么、哪里、何时，以及可能的原因”，以防证据成为法律要求。

完成 IRP 流程后，应生成事件报告并分发给所有受影响的利益相关者。该报告应包括根因分析结果、采取的修复行动和实施的恢复活动。报告的目的是教育管理团队了解使网络更安全所需/曾经需要的工作。

`Cybersecurity & Infrastructure Security Agency` (`CISA`) 为政府机构制定了指南，规定联邦、州、地方和部落政府组织如何向 `National Cybersecurity and Communications Integration Center` (`NCCIC`) 和 `United States Computer Emergency Readiness Team` (`US_CERT`) 提交事件通知。

指南要求组织在其 CSIRT 团队成员、安全运营中心 (SOC) 或 IT 部门验证事件后一小时内，报告信息系统 CIA 遭到破坏的信息安全事件。报告必须包含以下三类信息：

*   影响和严重性类别
*   攻击向量
*   事件属性

### 影响和严重性类别

NCCIS 收集事件影响和严重性信息，以分析国家网络事件评分系统 (NCISS) 的事件属性。收集的信息还用于计算由 NCISS 开发的严重性评分。严重性评分类别范围从基线（白级或蓝级）到低（绿级）、中（黄级）、高（橙级）、严重（红级）再到紧急（黑级）。NCISS 所需的影响和严重性类别数据包括以下内容：

*   `Functional impact`——这是对业务功能或提供服务能力影响程度的衡量。分配的严重性级别包括：无影响、最小非关键影响、最小关键影响、重大非关键影响、非关键服务中断、重大关键服务影响、关键服务中断及控制丧失。
*   `Information impact`——此条目描述丢失、泄露或损坏的信息类型。影响报告选项包括：无影响、疑似但未识别、隐私数据泄露、专有信息泄露至非关键系统破坏、关键系统数据泄露、核心凭证泄露、关键系统破坏。

### 可恢复性

此条目用于确定从事件中恢复所需资源的范围。选项包括常规、补充、扩展和不可恢复。

### 攻击向量

SP800-61r2 指南还要求识别、跟踪和报告与网络事件相关的攻击向量。该文档描述了用于创建统一报告系统的术语及其之间的关系。它列出了以下攻击向量定义：

*   **未知**——原因不明，但可能在后续报告中被识别。
*   **消耗**——一种用于破坏、降级或摧毁系统的暴力攻击。这可能是 DoS/DDoS 攻击或针对认证机制的攻击。
*   **Web**——从网站或 Web 应用程序发起的攻击。
*   **电子邮件/网络钓鱼**——通过电子邮件或附件执行的攻击。
*   **外部可移动介质**——从可移动介质源发起的攻击。
*   **冒充/欺骗**——涉及替换合法内容/服务的攻击。
*   **不当使用**——因授权用户违反组织政策而导致的任何事件。
*   **丢失或盗窃**——组织计算设备或介质的丢失或被盗。
*   **其他**——不属于上述任何列出类别的任何攻击。

### 事件属性

与报告事件相关的属性也由 NCISS 进行跟踪。它们定义其属性类别如下：

*   **观测活动位置**——此类别描述检测到观测活动的位置。标准属性定义包括业务 DMZ、业务网络、业务网络管理、关键系统 DMZ、关键系统管理、关键系统、安全系统和未知。
*   **行为主体表征**——此类别用于描述涉及事件的行为主体类型。
*   **跨部门依赖性**——此条目是由国土安全部 (DHS) 关键基础设施分析办公室 (OCIA) 进行的跨部门分析确定的加权因子。
*   **潜在影响**——此条目是因受影响实体而导致的总体国家影响的估计值。

完整的指南副本及其定义可从 `www.cisa.gov/uscert/sites/default/files/publications/Federal_Incident_Notification_Guidelines.pdf` 获取。

## NERC CIP 008-6

在电力生产和分配市场中，NERC CIP 008-6《网络安全事件响应计划规范》为 BES 运营商提供了生成网络安全事件处理程序的指导。

这些指南包括为网络安全事件响应团队和个人建立角色和职责。它还规定了事件处理程序的要求，如前文所述的四阶段模型中所述。与其他 CIP 标准一样，CIP 008 标准规定了进行 IRP 测试（每 15 个日历月）的条件和时间，以及报告要求。

# 第 11 章：灾难恢复与业务连续性

## 简介

灾难可定义为造成组织流程运作中断、对其生产力和盈利能力产生不利影响并需要恢复工作以纠正的事件。组织必须能够在各类小型紧急情况和大型灾难发生时继续运营，以确保组织的健康发展和持续经营。

现代企业极度依赖其通信基础设施，因此“网络”是任何组织连续性计划中最重要的组成部分之一。数据丢失会转化为系统停机、生产浪费、客户不满以及公司收益减少。

尽管预防措施始终是应对潜在灾难的首选工具，但它们无法保证永远不需要系统恢复。因此，应设计灾难恢复流程，以便在因意外、盗窃、蓄意破坏或自然灾害导致关键故障时，恢复组织网络的全部或部分功能。

正如第 8 章“ICS 安全治理与风险管理”中所述，组织依赖三种相互关联的计划来应对这些可能性：*事件响应计划*（*IRP*）、*业务连续性计划*（*BCP*）和*灾难恢复计划*（*DRP*）。这些计划通常具有重叠的功能，但它们是不同的。*BCP* 旨在预判并为组织业务流程中断期间持续运营所需的关键组件、目标和流程提供指导。因此，当中断或灾难发生时，*BCP* 更多是被参考而非被触发执行。*DRP* 通常在运营或数据丢失发生时被激活。*IRP* 在检测到或报告事件或潜在事件时被触发。了解每个计划的设计目的、它们之间的关联以及何时触发每个计划，是有效保障组织运营和职能的关键。

*IRP* 在第 8 章中介绍，并在第 10 章“ICS 安全监控与事件响应”中详细阐述。在本章中，重点将转移到阐述业务连续性计划和灾难恢复计划的目的与功能。

## 业务连续性计划

业务连续性计划是一份文档，旨在描述组织在发生任一类破坏性事件时的准备工作、增长计划和未来规划。

*BCP* 被设计为统领性计划，指导其他计划的设计与实施。因此，它将与事件响应计划和灾难恢复计划建立联系。

*BCP* 的首要任务是识别关键业务功能，并必须针对组织风险分析和业务影响评估与分析所指出的事件，提供应对和恢复业务中断的流程与程序，以实现最具成本效益的运营持续。*BCP* 适用于整个组织的每个内部业务单元及其外部供应商。正如您所能想象的，在这一组织层级制定的计划由高管团队开发。

*BCP* 的另一功能是尝试识别所有可能阻碍或停止组织各项业务功能的灾难场景。这通常包括潜在自然灾害、公用设施中断（如电力或网络资源中断）或人为中断（如黑客或恐怖活动）等项目。

连同 *DRP*，一个可靠的 *BCP* 包括风险分析、业务影响分析、计划维护、培训和集成流程，以及计划验证。这些项目通常由组织的企业资源规划（*ERP*）或信息安全（*infosec*）团队创建。对于 *BCP* 要取得成功，获得高层管理人员的认可至关重要。

### 系统冗余

*冗余* 是指投入额外硬件以维护系统和网络资源的做法。通过增加额外设备，可以将代表单点故障的组件从运行中移除。*故障点* 是网络中任意一旦失效就会导致关键进程关闭的要素。*故障点* 的一个例子是：*OT* 网络中唯一的数据历史服务器发生故障。在这种情况下，组织将无法记录生产数据，直到数据历史服务器功能恢复。

*系统冗余* 是在运营中创建并行系统以提供替代路径、维持组织运营的过程。创建此类冗余通常涉及通过备用站点提供安全恢复、安装高可用性容错网络资源，以及实施数据备份系统和方法以提供冗余数据源。

#### 备用站点

为冗余目的创建和维护备用站点属于 *BCP* 冗余选项的最高端。建立备用站点使组织能够在重大灾难期间及整个恢复期内临时继续运营。灾难结束后，组织可能能够将运营迁回主站点。在主站点重新建立运营时，应从最不关键的流程开始。可能有必要暂时在两个站点同时工作，直到主站点完全恢复。

备用站点是灾难情况下可使用的设施：

*   热站点
*   温站点
*   冷站点
*   云站点

这些不同设施类型的主要目的均在于恢复安全数据并维持组织的持续功能性运营。对于处理机密或秘密数据的组织而言，`安全恢复`至关重要。特别是在灾难发生时，能够在备用站点继续安全运营，且不损害数据完整性或机密性，这点极为关键。在规划可能影响网络的灾难应对方案时，安全恢复和持续运营应作为首要目标。

`热站点` 提供在灾难发生时继续运营所需的几乎所有资源。这些站点可能是主站点的缩减版。在某些情况下，热站点配备最少人员并同步运行，同时提供备份和容错功能。

在主站点创建的数据库可同步备份至热站点，或在数小时内完成备份。若无人值守，人员抵达备用站点后通常几分钟内即可投入运营。这些站点通常包含当前的数据备份以及在主站点发生灾难时立即运行所需的所有设备。计算机、线缆、网络外设、电力、气候控制和连接在热站点均可即刻投入使用。

当所有设备随时可用时，在灾难演练中测试热站点会容易得多。然而，由于成本极高，大多数组织要么创建热站点的缩减版——即 `温站点`，要么改用 `冷站点`。

与热站点不同，`温站点` 可能配备陈旧设备，且极有可能在真正的灾难发生前处于无人值守状态。温站点也可能将备份数据存放在安全保险库或保险柜中，但灾难发生后恢复关键运营所需时间会更长。

`冷站点` 通常仅提供最有限的功能，直到投入额外资源。关键电话和便携式笔记本电脑将在该备用站点启动运营。这种类型的异地设施在真实紧急情况下功能性不强，但可提供额外存储空间，并在安全室或保险柜中存放备份数据。无论建立哪种类型的备用站点，都应定期测试该站点以确保持续功能性。

在冷站点，设备通常仅限于基本设施功能，包括地板、墙壁、电力、照明和空调。网络计算机通常不安装在冷站点。不过，某些组织可能选择在其冷站点配备非运行状态的设备。决定因素在于投资成本与非生产性设备包预期回报的权衡。

从逻辑上讲，冷站点最难测试，因为它们缺乏日常运营所需的大多数设备。仅拥有冷站点而不进行测试会带来虚假的安全感。当真正的灾难降临时，冷站点可能无法满足恢复需求。

`基于云的灾难恢复站点` 使组织能够安全地将其数据、操作系统和软件工具迁移至云端，以利用相较于其他站点类型的成本优势。基于云的服务运营可根据需求在 `云服务提供商` (`CSP`) 的虚拟服务器上弹性扩展或收缩。由于数据始终可通过互联网访问，组织指定成员随时随地均可从单一位置访问数据。通过利用高网络带宽和服务的可持续扩展性，云确保了恢复过程的效率和可靠性。

`私有云服务` 日益普及，因此越来越多地由内部 IT 员工提供支持。`公有云服务` 通常极少需要本地支持，但软件即服务产品可能要求启用特定防火墙规则以实现最佳使用。`混合云服务` 则结合了公有云和私有云环境，其集成程度可以非常无缝，以至于用户可能忘记其数据并非完全存储在本地。

#### 高可用性/容错系统

要使生产设施取得成功，必须具备生产产品的能力。分钟级的停机通常意味着收入损失；因此，组织在维持其 OT 环境高可用性方面投入巨大。容错是确保这种高可用性的一种方法。

在小型组织中，一台服务器可能专门用于提供由多个物理磁盘驱动器组成的阵列，以实现容错。这种数据可用性的实现方式称为 `独立磁盘冗余阵列` (`RAID`)。如果其中一个物理驱动器发生故障，可将其更换，并从 RAID 阵列中的其他磁盘重新生成数据。

虽然 RAID 有多种类型，但其中一些并非旨在提供容错。相反，它们用于增加可用空间或卷以存储更大量的数据。然而，`RAID 1` 和 `RAID 5` 解决方案确实提供容错。`RAID 1` 提供主磁盘的镜像，通常用于保护操作系统免受故障影响。RAID 1 可采用单控制器加两个物理磁盘（称为 `镜像`），或双控制器加两个物理磁盘（称为 `磁盘双工`），后者比磁盘镜像更安全。

`RAID 5` 要求至少三个物理磁盘，且分区大小相似才能实现。数学奇偶校验元素在磁盘间生成容错，类似简单的代数方程：A + B + C = D。若任一分区元素故障，均可重新生成。例如，若上式中 A 发生故障，因 A = D – (B + C)，故 A 可被重新生成。

RAID 总体上是大多数操作系统维护数据的一种相当有效的方法，也是一种支持高可用性的技术解决方案。然而，若 RAID 阵列将恶意代码复制并损坏其他磁盘，则会失效，数据仍可能丢失。鉴于此潜在威胁，备份仍然必要。
