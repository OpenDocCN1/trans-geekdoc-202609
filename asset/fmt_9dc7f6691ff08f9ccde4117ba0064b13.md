
# 用于 OLAP 的多维结构

用于 OLAP 的多维结构通常被称为**立方体**。在几何学中，立方体是一种三维盒状结构。在 OLAP 理论中，立方体可以拥有任意数量的维度。立方体提供了一种直观的方式来可视化和浏览数据，并能快速访问聚合数据。

让我们考虑一个简单的例子。参考图 18.3 中的星型模式，假设我们想列出 2020 年至 2022 年每个地理区域和每个商品类别的销售单位数量。作为练习，你可以尝试为其编写 SQL 查询。你需要对四张表执行自然连接；按 `saleYear`、`region` 和 `category` 分组；并计算 `sum(qty)`。表 18.1 显示了可能结果的一个摘录，假设只有两个类别（SW = 软件，HW = 硬件）和四个区域（N = 北，S = 南，E = 东，W = 西）。该表的基础事实类型是：年份在区域中销售了类别为某项的若干单位商品。完整的结果表将包含 24 行（每年 8 行）；此处仅显示前 9 行。

OLAP 立方体可能比这个例子复杂得多。对于任意一组独立维度，可能存在多个度量（例如，销售单位数和收入）。这些不同的度量通常统称为**度量维度**。此外，每个独立维度通常都有一个**层级**的**级别**。例如，位置维度的顶层可能是区域，第二层由州组成，第三层是城市，第四层是门店。同样，时间维度可以分解为年、季度、月和日。最后，商品维度可以分解为类别和具体商品。

因此，我们的数据集市示例可以用来构建一个具有三个独立层级维度（位置、时间和商品）以及一个用于 UnitsSold 和 Revenue 度量的因变维度的立方体。立方体结构的妙处在于，它能够高效地存储和访问层级中所有级别的度量聚合值。

### 立方体操作

在分析立方体时，你可以选择合并或**上卷**这些聚合值（例如，将城市的销售数字上卷为区域销售数字）。你也可以**下钻**到更细粒度的级别。此外，你可以通过获取其子立方体，以任何你喜欢的方式对立方体进行**切片和切块**。例如，如果你将图 18.4 中的商品类别限制为软件，你将得到立方体的前部切片。

由于这些优势，数据集市中的星型模式常被用于创建各种立方体以便于分析。SQL Server 提供了向导来简化立方体创建任务，并支持用于查询立方体的**多维表达式 (MDX)** 语言。

### MDX 查询语言

在 MDX 中，**select** 语句指定一个结果集，该结果集包含从立方体返回的多维数据的一个子集。select 子句指定查询轴（允许 0 到 128 个轴），from 子句确定将查询哪个立方体，可选的 where 子句确定在切片轴上使用哪些成员或元组来限制返回的数据。

作为一个简单的例子，假设 `SalesCube` 基于前面讨论的层级位置、时间和商品维度。以下 MDX 查询将生成一个二维网格，列出 2020 年前三个季度华盛顿州的软件销售单位数和收入。

```
select { [Measures].[UnitsSold], [Measures].[Revenue] } on columns,
       { [Time].[2020].[Q1] : [Time].[2020].[Q3] } on rows
from SalesCube
where ( [Item].[SW], [Location].[N].[WA] )
```

在 MDX 中，大括号用于定界序列，方括号可用于定界标识符或值。点符号用于向下遍历层级。请注意，时间下钻到了季度，位置下钻到了州。冒号 `:` 用于表示范围（类似于英语中的 `..`）。上述查询的结果网格有两列（销售单位数和收入）和三行（2020 年前三个季度）。

不同的 OLAP 工具工作方式不同。SQL:1999 及以后版本包含对立方体和上卷的支持，因此希望未来某些 OLAP 功能能变得更加标准化。全面介绍 MDX 还需要一两章的篇幅，因此此处不再深入。有关 SQL Server 2022 MDX 的详细介绍，请参阅 [MDX Language Reference (MDX) - SQL Server | Microsoft Learn](https://learn.microsoft.com/en-us/sql/mdx/mdx-language-reference-mdx?view=sql-server-ver16)。

MDX 查询可能非常复杂，Microsoft SQL Server 提供了一种称为**英语查询**的高级语言，最终用户可用它来生成 MDX 查询。基于自然语言的查询将在下一节讨论。

## 18.3 概念查询语言

信息系统可以在四个层级中的任意一个进行建模：概念、逻辑、物理和外部。原则上，也可以在任意这些层级对其进行**查询**。然而在实践中，虽然概念建模被广泛使用，但系统在概念层级被查询的情况却相对较少。相反，查询通常是在外部层级使用表单、在逻辑层级使用 SQL 等语言、或在物理层级使用编程语言来构建的。

在外部层级，**表单查询 (QBF)** 允许用户通过在表单字段中输入适当的值或条件，直接在屏幕表单上输入查询。这种基于表单的界面非常适合简单查询，即查询范围可见于单个表单且不涉及复杂操作的场景。然而，它无法用于表达复杂查询。此外，随着外部接口的演进，已保存的 QBF 查询可能会迅速过时。出于这些原因，QBF 对于严肃的工作来说过于受限。

### 查询语言与概念查询方法

#### 关系与面向对象查询语言

对于关系型数据库，SQL 和 示例查询 更具表达力。然而，复杂查询甚至用自然语言很容易表达的查询（例如：谁不会说超过一种语言？）对于非技术用户来说，用这些语言表达起来可能很困难。此外，即使查询的含义未变，如果概念模式或内部模式的相关部分发生变化，SQL 或 QBE 查询通常也需要修改。最后，关系查询优化器忽略了许多源于约束知识的语义优化机会。

面向对象和对象关系 DBMS 的查询语言也面临类似问题。它们额外的结构（例如：集合、数组、包和列表）往往导致用户编写和系统优化的复杂性都更高。例如，对象查询语言 (OQL) 通过各种导航函数以及组合和扁平化结构的函数扩展了 SQL，从而迫使用户直接处理信息在内部的存储方式 (Cattell and Barry, 2000)。在物理层面，编程语言可用于直接访问内部结构（例如：使用指针和记录），但这种非常低层次的查询编写方法完全不适合最终用户。

#### 商业 SQL 查询构建器工具

现在有几款商业 `SQL query builder tools` 可供用户轻松创建 SQL 查询，而无需任何 SQL 知识。它们提供拖放或点击式界面，使非技术用户能够快速构建 SQL 查询。有些还提供图表环境，用于将 SQL 查询结果保存为图表、报表和仪表板。有关其中几款工具的详细信息，可访问 [9 Best SQL Query Builder & Generator Tools (2023) (guru99.com](https://www.guru99.com/best-sql-query-builders.html)) 和 [www.activequerybuilder.com/](http://www.activequerybuilder.com/)。

#### 自然语言查询工具

一些商业工具允许用户直接用英语输入查询，然后将其翻译成 SQL 或 MDX 等数据库查询语言。此类早期工具常受困于歧义性和表达能力问题，以及生成的 SQL 代码的正确性问题。我们所考察的大多数自然语言输入工具都要求你花费大量精力建立字典，以将概念术语关联到底层数据库结构，而且它们大多在处理自然语言输入方面做得不完美。考虑到自然语言固有的歧义性和复杂性，这并不令人惊讶。

##### English Query 方法

解决歧义问题的一种方法是采用 `English Query`，它多年前曾包含在 Microsoft SQL Server 中，但现已不再提供。当你用英语输入一个问题时，它会被重述以指示所采用的理解。有时会给出不止一种重述，你可以选择能传达你预期含义的那一个。

当然，能被理解的问题类型是有限的，而且你需要花时间建立语义模型与数据库结构之间的连接。例如，如果你想要在除外键引用主键以外的表之间建立连接，你需要预先显式添加此连接。此外，生成的 SQL 可能不如你自己编写的那样高效。

然而，一旦完成所有这些工作，你就可以让非技术最终用户用通俗易懂的英语查询数据库。虽然常见的、可预测的查询最好通过预写过程提供，但 `English Query` 对于特设查询特别有用。例如，参考上一节中的数据集市模式，并假设已进行充分设置，问题“哪个区域拥有最多的商店？”可能会生成以下 SQL 代码：

```
select top 1 with ties dbo.Store.region as “Region”, count(*) as “count”
from   dbo.Store
where dbo.Store.region is not null
group by dbo.Store.region
order by 2 desc
```

除了返回拥有最多商店的区域外，该查询还返回这些区域中的商店数量，这可能不是我们想要的。此外，`where` 子句和 `order by` 子句都是冗余的。但对于无法编写 SQL 查询的非技术用户来说，这些都是小问题。对于 OLAP 应用，`English Query` 也被用于生成 MDX 查询。例如，参考上一节讨论的 SalesCube，问题“列出单位销量最多的三个商品”可能会导致重述“显示总单位销量最高的三个商品”以及以下 MDX 查询：

```
select { Measures.[UnitsSold] } on columns,topcount([Item].[ItemCode].members, 3, Measures.[UnitsSold] ) on rowsfrom [SalesCube]
```

正如这些示例所示，自然语言的自由输入极大地拓展了数据库的受众范围，使任何会写字的人都能使用数据库。随着语言识别技术的成熟，它也将使任何会说话的人都能使用数据库。然而，在该技术变得完全可靠之前，我们还有很长的路要走。

### 概念查询语言

已经提出了几种 `conceptual query languages`，允许用户直接在概念模式上编写查询。这些语言提案大多是学术研究项目，充其量只有原型工具支持，且通常基于 ER 模式（例如：ERQL、Super、Hybris）或演绎模型（例如：CBQL）。这些对于初学者来说通常具有挑战性，而且它们对属性的使用使查询面临不稳定性，因为随着应用模型的演进，属性可能会演变为实体或关系。

#### 基于概念模式的查询

通过采用一种不同的方法：`conceptual-schema-based queries`，可以一举消除歧义和繁琐的字典准备问题。在这里，用户通过选择现有概念模式中的路径来发出查询，而不是使用自由文本输入，因此不会产生歧义。正如稍后讨论的，如果使用 ORM 概念模式，则无需预先声明任何连接路径，因为 ORM 对象类型是所有连接所基于的语义域。由于 ORM 在其基本概念模型中不包含属性，它还避免了基于属性的查询的不稳定性问题，后者在属性演变为关系时需要重新编写（见后文示例）。此外，ORM 的唯一数据结构是关系类型，提供了一个简单的、基于句子的框架。基于这些原因，我们认为 ORM 概念查询技术是现有所有方法中潜力最大的。

#### 参考与构想语言 (RIDL)

第一个重要的基于 ORM 的查询语言是参考与构想语言 (RIDL)，一种兼具声明式和过程式特点的混合语言 (Meersman, 1982; Meersman et al., 1984)。RIDL 是一种文本语言，用于定义、填充和查询 NIAM 模型，NIAM 是面向事实建模的早期版本。它是在布鲁塞尔大学的 Control Data 研究实验室开发的，是有史以来第一个真正被实现的概念查询语言。让我们看一些 RIDL 示例。考虑一个包含以下事实类型的军事概念模式：军官 拥有 军衔；军官 出生于 年份。在 RIDL 中，这些事实类型通常会被声明为 Officer having Rank；Officer born-in Year。要查找 1950 年前出生的中士，可以使用以下 RIDL 查询：

```
LIST Officer (having Rank ‘sergeant’ AND born-in Year < 1950)
```

在 RIDL 中，保留字为大写。为了说明 RIDL 的过程式一面，以下查询列出了军衔相同且出生于 1950 年前的军官对：

#### RIDL 和 LISA-D

```
FOR EACH o1, o2 IN Officer born-in Year < 1950 DO
    IF Rank OF o1 = Rank OF o2
        THEN LIST o1, o2
    END-IF
END-FOR
```

最初的 RIDL 软件将 RIDL 查询映射为内部语句，这些语句可直接在一些早期的 Control Data 计算机上执行。在后来的几年里，RIDL 的数据定义部分在 RIDL* 工具中以图形方式实现，但查询组件不受支持。

另一种 ORM 查询语言是信息结构和访问描述语言（LISA-D）。尽管它非常有表现力，但对最终用户来说在技术上具有挑战性，且目前缺乏工具支持（ter Hofstede et al., 1996）。

#### OSM-QL

与 ORM 一样，面向对象系统建模（OSM）方法避免将属性作为基本构造。基于这种方法，开发了用于图形查询语言 OSM-QL 的学术原型（Embley et al., 1996）。对于任何给定的查询，用户选择概念模式的相关部分，并用限制条件注释生成的子模式图来构建查询。通过添加频率约束“0”来处理否定，并通过子类型联合运算符引入析取。通过单击相关的对象节点，然后单击标记为输出按钮来完成投影。

#### ConQuer 和 ActiveQuery

另一种 ORM 查询语言是 **ConQuer**（名称源于“CONceptual QUERy”）。ConQuer 比 OSM-QL 更有表现力，且对新手用户更容易。其工具实现将概念查询转换为各种后端 DBMS 的 SQL 查询，并且不要求用户熟悉概念模式或 ORM 图符号。ConQuer 的第一个版本在 InfoAssistant 中发布（Bloesch and Halpin, 1996）。该版本的反馈导致对语言和用户界面进行了重新设计，以提高表现力和可用性，从而产生了一个名为 ActiveQuery 的工具（Bloesch and Halpin, 1997）。典型查询只需单击鼠标选择对象并添加条件即可构建。ActiveQuery 技术后来被微软收购。

对 ConQuer 技术的基本了解将有助于深入了解概念查询环境。ConQuer 语言及其工具支持的设计旨在实现表现力、清晰度、简洁性、语义稳定性和语义相关性。这些设计原则在 Section 3.1 中进行了解释。ConQuer 查询只能应用于 ORM 模式。使用软件工具，可以直接输入 ORM 模式，或者从现有的逻辑模式（例如关系或对象关系模式）反向工程生成。虽然反向工程是自动的，但人工的某些改进可以提高可读性（例如，为谓词生成的默认名称并不总是像人工提供的那样自然）。

尽管 ConQuer 查询基于 ORM，但用户不需要熟悉 ORM 或其符号。ConQuer 查询以文本（大纲）形式（基本上作为连接对象的谓词树）列出，底层约束被隐藏，因为它们不影响查询的含义。

使用 ActiveQuery，用户可以在不了解模式的情况下构建查询。打开模型时，会向用户显示一个对象选取列表。当将对象类型拖动到查询窗格时，另一个窗格会显示该对象在模型中扮演的角色。用户拖动感兴趣的任何关系。单击这些关系中的对象类型会显示其角色，用户可以拖动感兴趣的角色，依此类推。通过这种方式，用户可以快速声明穿越信息空间的查询路径，而无需任何底层数据结构的先验知识。用户也可以最初拖动多个对象类型。然后利用底层模型的结构自动推断出穿越信息空间的合理路径，这称为 **point-to-point query**。

要显示的项目用勾选标记“✓”指示。这些勾选标记可根据需要切换开/关。查询路径可以通过使用运算符和条件以各种方式进行限制。作为一个简单的例子，假设一家公司在世界各地的几个城市设有分支机构。现在，考虑查询：列出居住在 52 号分支机构所在城市的每位员工。这可以在 ConQuer 中这样列出：
