##### 计算机辅助软件工程 (CASE)

*计算机辅助软件工程* (CASE) 使用程序来协助其他计算机程序的创建和维护。编程历来由（人类）程序员或团队执行：CASE 将软件添加到编程“团队”中。

CASE 软件有三种类型：

1.  **工具**：仅支持软件生产过程中的特定任务。
2.  **工作台**：通过在单个应用程序中集成多个工具，支持一个或几个软件过程活动。
3.  **环境**：通过工具和工作台的集合，支持软件生产过程的全部或至少一部分 [\[5\]](#Ch009_459-508_B9780443187346000088.xhtml#bb0030)。

第四代计算机语言、面向对象语言和 GUI 通常被用作 CASE 的组件。

#### 自顶向下与自底向上编程

程序员的任务是开发能够播放 MP3 音乐文件的软件。程序员应如何开始构思将文件中的比特转化为我们可听到的音乐这一挑战？程序员是应该从“顶层”开始，思考音乐听起来会怎样，以及 MP3 播放器的外观和行为？还是应该从“底层”开始，思考接收比特流并将其转换为音频波形所需的低级设备驱动程序？

**自顶向下 (TD) 编程** 从最广泛和最高层级的需求（最终程序的概念）开始，逐步深入到低级技术实现细节。**自底向上编程** 则相反：它从低级技术实现细节开始，逐步构建到完整程序的概念。

这两种方法都存在风险：如果自顶向下的方法对低级设备的性能做出了错误假设，会怎样？另一方面，自底向上方法冒着浪费时间的风险，可能会为最终产品中可能不需要或未实现的功能编写大量代码。

过程式语言（如 C）历来采用自顶向下风格编程：从主程序开始，定义过程，然后逐步向下进行。面向对象编程通常使用自底向上设计：定义对象，并利用它们构建最终程序。

#### 公开发布软件的类型

编程完成后，公开发布的软件可能以不同形式出现（例如附带或不附带源代码），并根据各种许可证发布。

##### 开源与闭源软件

**闭源** 软件通常以可执行形式发布：源代码保密。示例包括 Oracle 和 Microsoft Windows 11。**开源** 软件公开发布源代码。示例包括 Ubuntu Linux 和 Apache Web 服务器。**专有软件** 是受知识产权保护（如专利或版权）的软件。“闭源软件”和“专有软件”有时被用作同义词，但这并不总是正确的：某些开源软件也是专有的。

##### 免费软件、共享软件和残废软件

**免费软件** 是一个有争议的术语，不同群体对其定义不同。“免费”可能意味着免费使用（有时称为“免费如啤酒”），也可能意味着用户可以自由以任何方式使用软件，包括修改它（有时称为“自由如言论”）。这两种类型分别称为 **gratis**（免费）和 **libre**（自由）。这种混淆源于英语中 "free" 一词具有多重含义。既是 gratis 又是 libre 的软件有时称为 free [\[2\]](#Ch009_459-508_B9780443187346000088.xhtml#bb0015)（free squared，即完全免费）。

**免费软件** 是“免费如啤酒”(gratis) 的软件，可免费使用。**共享软件** 是功能完整的专有软件，最初可免费使用。如果用户继续使用共享软件的时间超过许可证规定的特定期限（如 30 天），共享软件许可证通常要求付费。**残废软件** 是功能部分受限的专有软件，通常禁用关键功能。用户通常需要付费以解锁全部功能。

##### 软件许可

软件可能被发布到公共领域，意味着它（明确地）没有版权或许可。这不对软件用户施加任何知识产权限制。某些免费软件属于此类。大多数软件（无论闭源还是开源）都受软件许可保护。

专有软件通常受版权保护（也可能受专利保护，详见 第 2 章，领域 1：安全与风险管理，了解更多关于版权和专利的信息）；软件用户通常必须同意软件许可协议的条款才能使用软件。这些协议通常称为 **EULA**（最终用户许可协议），可以是纸质或电子形式，后者通常在用户安装软件时点击“我同意”即表示同意。

开源软件可能受多种许可协议保护，包括 **GNU 通用公共许可证 (GPL)**、**BSD**（Berkeley Software Distribution，伯克利软件发行版）和 **Apache**（以 Apache Software Foundation，Apache 软件基金会命名）许可证。

最流行的开源许可证是 GPL，它专注于自由软件，允许用户自由使用、修改和共享软件。GPL 的核心是“copyleft”（版权许可/反版权）一词，这是对 copyright（版权）的谐音：copyleft 旨在确保自由软件保持自由。《GPLv3 快速指南》（见 <http://www.gnu.org/licenses/quick-guide-gplv3.xhtml>) 指出：“没有人应该受到其所使用软件的限制。每个用户都应享有四项自由：

*   为任何目的使用软件的自由，
*   修改软件以满足您需求的自由，
*   与朋友和邻居分享软件的自由，以及
*   分享您所做更改的自由” [\[6\]](#Ch009_459-508_B9780443187346000088.xhtml#bb0035)。

GPL copyleft 要求对 GPL 软件的修改必须保持自由：您不能获取 GPL 代码，修改它，然后将修改后的代码变为专有。其他自由许可证（如 BSD）允许许可代码变为专有。

## 应用程序开发方法

计算机编程可追溯到 1940 年代末电子计算机的诞生。程序员最初使用机器码或汇编语言；第一种高级编程语言是 Fortran，于 1954 年首次亮相。早期的计算机程序员通常独自工作，独立创建完整程序。在这种情况下，项目管理方法简单或非必要：程序员有时可以在（人脑）记忆中构想整个项目，然后直接编写代码。随着软件复杂性的增加，软件编程越来越成为一项团队工作。基于团队的项目需要项目管理：提供包含交付物和里程碑的项目框架、分配任务、团队沟通、进度评估和报告，以及（希望）最终交付产品。

最终，大型应用程序开发项目可能与与软件无关的项目非常相似，比如制造零件或建造桥梁。应用程序开发方法（如瀑布模型和螺旋模型）通常是非编程模型的近亲。这些方法可以被视为项目管理方法，并具有支持代码创建的附加功能。

### 瀑布模型

`Waterfall Model`（瀑布模型）是一种线性的应用开发模型，使用严格的阶段；当一个阶段结束时，下一个阶段开始。瀑布模型早于软件设计，最早用于制造业。1969 年，它首次被用于描述软件开发过程，当时大型软件项目已变得过于复杂，无法使用非正式方法进行设计。步骤按顺序发生，未修改的瀑布模型不允许开发人员返回之前的步骤。之所以称之为瀑布，是因为它模拟水流向下：无法回流向上。

Winston W. Royce 博士在《大型软件系统开发管理》（"Managing the Development of Large Software Systems"）中首次结合软件开发描述了瀑布模型（参见 [`leadinganswers.typepad.com/leading_answers/files/original_waterfall_paper_winston_royce.pdf`](http://leadinganswers.typepad.com/leading_answers/files/original_waterfall_paper_winston_royce.pdf)）。Royce 的未修改瀑布模型（无迭代，有时称为“阶段式”）如图 9.2 所示，包含以下步骤：系统需求、软件需求、分析、程序设计、编码、测试和运维。

![图 9.2 未修改的瀑布开发模型 [7]。](images/B9780443187346000088/f09-02-9780443187346.jpg)

图 9.2 未修改的瀑布开发模型 [[7]](#Ch009_459-508_B9780443187346000088.xhtml#bb0040)。

Royce 的论文未使用“瀑布”一词，但描述了该过程。未修改的瀑布模型不允许迭代：即返回之前的步骤。这给早期步骤带来了沉重的规划负担。此外，由于每个后续步骤要等到前一步骤结束才能开始，早期步骤的任何延迟都会级联传递到后续步骤。

具有讽刺意味的是，Royce 的论文是在批评该模型。关于图 9.2 所示模型，“上述实现充满风险，招致失败” [[7]](#Ch009_459-508_B9780443187346000088.xhtml#bb0040)。在现实世界中，需要迭代：通常不现实禁止返回之前的步骤。Royce 提出了在测试阶段发现根本设计错误的问题：“测试阶段发生在开发周期末尾，这是首次将时序、存储、输入/输出传输等作为实际体验而非分析对象的事件。这些现象无法精确分析……然而，如果这些现象未能满足各种外部约束，则不可避免地需要进行大规模重新设计” [[7]](#Ch009_459-508_B9780443187346000088.xhtml#bb0040)。许多后续的软件设计模型被称为迭代模型：它们明确设计为允许迭代，即返回之前的步骤。

> **考试警告**
>
> Royce 未修改瀑布模型的具体阶段名称不可考：请掌握整体流程。此外，Royce 遗漏了一个关键的最终步骤：销毁。任何导致包含敏感生产数据的操作系统投入运行的开发过程，在该系统退役、数据归档、以及这些物理系统上剩余数据被安全销毁之前，都不算真正完成。

Royce 描述了一个修改后的瀑布模型，允许返回前一阶段进行验证或确认，理想情况下仅限于相邻步骤。Barry Boehm 的论文《软件开发与改进的螺旋模型》（"A Spiral Model of Software Development and Enhancement"，见下文“螺旋模型”部分）展示了一个基于 Royce 论文的修改后瀑布模型，如图 9.3 所示。

![图 9.3 修改后的瀑布开发模型 [8]。](images/B9780443187346000088/f09-03-9780443187346.jpg)

图 9.3 修改后的瀑布开发模型 [[8]](#Ch009_459-508_B9780443187346000088.xhtml#bb0045)。

### 敏捷软件开发

`Agile Software Development`（敏捷软件开发）是作为对瀑布模型等僵化软件开发模型的反应而演变而来的。敏捷方法包括 `Scrum`（Scrum）和 `Extreme Programming`（极限编程，XP）。敏捷宣言（参见 [`agilemanifesto.org/`](http://agilemanifesto.org/)）指出：

> “我们通过实践并帮助他人实践，发掘出更好的软件开发方法。通过这项工作，我们开始重视：
>
> *   **个体和互动** 高于 流程和工具
> *   **可工作的软件** 高于 详尽的文档
> *   **客户协作** 高于 合同谈判
> *   **响应变化** 高于 遵循计划” [[11]](#Ch009_459-508_B9780443187346000088.xhtml#bb0060)

敏捷体现了许多现代开发概念，包括更大的灵活性、以较小里程碑实现快速周转、团队内部的强沟通以及更多的客户参与。

#### Scrum

`Scrum` 开发模型（以橄榄球运动中的“争球”命名）是一种敏捷模型，最早由 Hirotaka Takeuchi 和 Ikujiro Nonaka 在《新新产品开发游戏》（"The New New Product Development Game"）中结合产品开发进行描述；他们指出：“停止接力赛，改打橄榄球” [[12]](#Ch009_459-508_B9780443187346000088.xhtml#bb0065)。“接力赛”指瀑布模型，即团队在步骤完成后将工作移交给其他团队。他们建议：“相反，整体或‘橄榄球’式方法——团队作为一个整体尝试全程推进，来回传球——可能更好地满足当今的竞争要求” [[12]](#Ch009_459-508_B9780443187346000088.xhtml#bb0065)。

Peter DeGrace（因 Sashimi 而知名）结合软件开发描述了（并命名了）Scrum。Scrum 包含小型开发团队，称为 `Scrum Team`（Scrum 团队）。`Scrum Master`（Scrum 主管）是组织中的资深成员，像教练一样为团队提供支持。最后，`Product Owner`（产品负责人）是业务部门的代言人。

#### 极限编程（XP）

极限编程（XP）是一种敏捷开发方法，采用成对的程序员基于详细规格说明进行工作。客户参与度极高。“极限编程在五个关键方面改进了软件项目：沟通、简洁、反馈、尊重和勇气。极限程序员与客户及同行程序员保持持续沟通。他们保持设计简洁清晰。从第一天起就通过测试软件来获取反馈。他们尽早将系统交付给客户，并实施建议的变更”[[13]](#Ch009_459-508_B9780443187346000088.xhtml#bb0070)。XP 核心实践包括：
