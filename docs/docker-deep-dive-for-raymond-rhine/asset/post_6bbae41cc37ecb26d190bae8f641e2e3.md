Congratulations. You've just completed a zero-downtime rolling update of a live containerized application.

If you run a `docker service inspect --pretty` command against the service, you'll see the `update parallelism` and `update delay` settings have been merged into the service's definition. # Service logs

You can inspect a service's logs with the `docker service logs` command. It gathers the logs from every replica and displays them in a single output.

If you've been following along, you'll have a service called **uber-svc** with 12 replicas mapped to port `8080` on every cluster node. Open a browser tab to the IP address of any cluster node on port `8080` and refresh the page a few times.

Now run a `docker service logs` command to see any log messages generated by the service.

```
docker service logs uber-svc
uber-svc.8.r33cra80eeut@wrk1
uber-svc.2.vid8752oj48@wrk1
uber-svc.7.jv67x3zfkyar@wrk2
uber-svc.1.zlmvo5k156@wrk2
uber-svc.3.kleeiyovue5@wrk2  | {"level":"info","message":"/"}
| {"level":"info","message":"/"}
| {"level":"info","message":"/"}
| {"level":"info","message":"/"}
| {"level":"info","message":"/"}
```

The output shows five lines relating to five requests serviced by five different replicas. The long string on the left of each line is the name of the replica which Docker creates by concatenating the service name, replica number, replica ID, and the name of the node it's scheduled on. The following table maps the names of the five replicas that requested services.

| Service name | Replica number | Replica ID | node |
|---|---|---|--- |
| uber-svc | 8 | r33cra80eeut | @wrk1 |
| uber-svc | 2 | vid8752oj48 | @wrk1 |
| uber-svc | 7 | jv67x3zfkyar | @wrk2 |
| uber-svc | 1 | zlmvvo5k156 | @wrk2 |
| uber-svc | 3 | kleeiy0vuue5 | @wrk2 |

Notice how Swarm balanced the requests across five different replicas. In the real world, your requests probably won’t be as evenly balanced as this due to the way browsers and different tools create and handle requests. However, if you refresh enough times, you’ll eventually see the requests being serviced by different replicas.

By default, Docker configures services to use the `json-file log driver`, but other drivers exist, including:

- awlogs
- gelf
- journald (only works on Linux hosts running systemd)
- splunk
- syslog

**json-file** and **journald** are the easiest to configure, and they both work with the **docker service logs** command. However, other drivers don't always work with the native Docker commands and you may have to use the logging platform’s native tools.

The following snippet is from a **daemon.json** configuration file on a Docker host configured to use the **syslog** driver. The **daemon.json** file is usually located in **/etc/docker/daemon.json**, but sometimes it doesn’t exist unless you create it manually for custom settings.

```
{
  "log-driver": "syslog"
}
```

You can force new services to use specific log drivers by starting them with the **--log-driver** and **--log-opts** flags. Doing this will override anything set in the **daemon.json** file.

Service logs expect applications to run as PID 1 and send logs to STDOUT and errors to STDERR. The logging driver then forwards the logs to the locations configured via the logging driver.

# Docker Swarm – The Commands

- docker swarm init creates a new swarm. The node you run the command on becomes the first manager and the Docker Engine on that node switches into swarm mode.
- docker swarm join-token reveals the commands and tokens you need to join workers and managers to the swarm. You add manager to the command to get the manager join token and worker to get the worker token. Be sure to keep your join tokens secure!
- docker node ls lists managers and workers, including which manager is the leader.
- docker service create creates a new service.
- docker service ls lists running services and gives basic information on their state and the number of replicas they’re running.
- docker service ps <service> gives more detailed information about individual service replicas.
- docker service inspect gives very detailed information on a service.
- docker service scale scales the number of replicas.
- docker service update updates the properties of a service.
- docker service logs shows logs.
- docker service rm deletes a service.

Swarm is Docker’s native technology for clusters. It is similar to Kubernetes but easier to use. The orchestration component deploys and manages microservices.
