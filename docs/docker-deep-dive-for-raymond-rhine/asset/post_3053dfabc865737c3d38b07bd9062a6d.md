# Rollouts

Application updates are a fact of life, and for the longest time they were painful. I've personally lost more than enough

weekends to major application updates and I've no intention of doing it again.

Fortunately, thanks to Docker services, updating well-designed microservices apps is easy.

**Terminology:** We use terms rollouts, updates, and rolling updates to mean the same thing — updating a live application.

You're about to deploy a new service to help demonstrate a rollout. However, before doing that, you'll create a new overlay network for the service. This isn't necessary, but I want you to see how to attach services to networks.

Run the following two commands to create a new overlay network called **uber-net** and then check if it exists.

```
$ docker network create -d overlay uber-net
43wp6pzea470et4d57udn9ws
```

```
$ docker network ls
| NETWORK ID | NAME | DRIVER | SCOPE |
| 43wp6pzea47 | uber-net | overlay | swarm |
| <Snip> | | | |
```

The new network exists and was successfully created as an overlay network scoped to the entire swarm. You’ll learn about overlay networks in a later chapter, but for now, it’s enough to know that they span all swarm nodes and that all containers in the same overlay network can communicate, even if they’re deployed on different nodes.

Figure 10.5 shows four swarm nodes connected to two underlay networks connected by a layer 3. The overlay network spans all four nodes and creates a single flat 2 network abstracting the underlying networks. All container replicas are connected to the overlay and can communicate with each other. (img/ae0230bf8529bd8076c4c780dca8d3_277_0.png) Figure 10.5

Let’s create a new service and attach it to the uber-net network.

```
$ docker service create --name uber-svc \
  --network uber-net \
  -p 8080:8080 --replicas 12 \
  nigelpton/ddd-book:web0.0
```

```
overall progress: 12 of 12 tasks
1/12: running [====================================]
2/12: running [====================================]
3/12: running [====================================]
<Snip>
12/12: running [====================================]
verify: Service converged
```

Let’s step through what happened. On the first line, you named the service uber-svc. You then used the **--network** flag to tell Docker to attach all service replicas to the new uber-net. Then, you mapped 8080 on every swarm node to port 8080 in all 12 replicas. Finally, you told Docker which image to base the replicas on. This mode of publishing a service on every swarm node, including nodes not running replicas, is called **ingress mode** and is the default. The alternative is **host mode**, which only publishes a service on nodes running.

Run docker service ls and a docker service ps to verify the state of the service and each replica.
