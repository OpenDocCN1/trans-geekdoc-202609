
The number at the end of the container names allows each service to have multiple replicas. For example, if the web-fe service had three replicas they would be called multi-container-fe-1, multi-container-fe-2, and multi-container-fe-3.

$ docker volume ls

With the application deployed, you can point a web browser at your Docker host on port 5001 to view it. You can connect to localhost:5001 if you're running Docker Desktop (img/ae0230bf8529bd076c8d237_0.png).

Refreshing the page will cause the counter to increment. This is because the app counts hits and stores the counter in the Redis service. If you followed along and brought the application up in the foreground, you'll see response codes in your terminal for every refresh. You won't see this if you used the `--detach` flag to bring it up in the background.

## Managing apps with Compose

In this section, you'll see how to stop, restart, delete, and get the status of Compose apps. Run the following command to shut down the app. If you started it in the foreground, you'll see messages requesting the app to gracefully quit.

$ docker compose down
- Container multi-container-redis-1 Removed
- Container multi-container-fe-1 Removed
- Network multi-container-counter-net Removed

The output shows Docker removing both containers and the network. However, it doesn't mention the volume. Run a `docker volumes` command to see if the volume still exists.

$ docker volume ls
local multi-container-counter-vol

The volume still exists, including the counter data stored in it. This is because Docker knows we store important information in volumes and might not want to delete them with other resources. With this mind, Docker decouples the lifecycle of volumes from the rest of the application. Docker also keeps the images built and pulled when it started the app. This makes future deployments faster. Feel free to run a `docker images` command to verify the images still exist.

Let's explore a few other `docker compose` sub-commands. Run the following command to redeploy the app.

$ docker compose up --detach
[+] Running 2/3
- Network multi-container-counter-net Created 0.2s
- Container multi-container-redis-1 Started 0.2s
- Container multi-container-fe-1 Started 0.2s

Notice how it started much faster this time. This is because the volume and both images already exist. Check the current state of the app with the `docker compose ps` command.

| NAME | COMMAND | SERVICE | STATUS |
| :--- | :--- | :--- | :--- |
| multi-container-redis-1 | "docker-entrypoint.sh" | redis | Up |
| multi-container-fe-1 | "python app/app.py" | web-fe | Up |

The output shows both containers, the commands they're executing, their current state, and the network ports they're listening on. Run a `docker compose top` to list the processes inside each container.

$ docker compose top
multi-container-redis-1
UID PID PPID ... CMD
lxd 12023 11980 redis-server :6379

multi-container-fe-1
UID PID PPID ... CMD
root 12024 12002 0 python app/app.py python app.py
root 12085 12024 0 /usr/local/bin/python app/app.py python

The PID numbers returned are the PID numbers as seen from the Docker host (not from within the containers). You’re about to stop and restart the app. However, before doing this, connect your browser to the app again and refresh the page few times. Make a note of the counter value before continuing. Run the following commands to stop the app and recheck its status.

$ docker compose stop
[+] Running 2/2
- Container multi-container-redis-1 Stopped
- Container multi-container-fe-1 Stopped

$ docker compose ps
NAME COMMAND SERVICE STATUS PORTS

The app is down, but Docker hasn't deleted any of its resources. Verify this by checking if the containers still exist.
