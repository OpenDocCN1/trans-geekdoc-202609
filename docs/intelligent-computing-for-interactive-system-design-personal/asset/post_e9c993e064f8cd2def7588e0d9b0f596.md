
## Personal Context from Mobile Phones—Case Study 5
Jason Wiese

Mobile phones are prime platforms for inferring personal context; many people carry their phone with them throughout the day and use it for a diverse set of personal tasks in many different situations. These characteristics mean that phones can provide numerous types of data from which personal context can be inferred. Similarly, the very fact that phones are used in so many situations throughout the day can make accurate contextual inferences especially valuable. However, for all of the potential value that personal context inferences can offer, there are many pitfalls and challenges when inferring personal context and when applying those inferences in user-facing systems.

This chapter describes two projects that illustrate different aspects of the process of inferring personal context from mobile devices: one project that infers phone placement, and another that infers social context from communication behavior. Next, we use the experiences illustrated in these examples to highlight some common patterns and challenges for inferring personal context from mobile phones.

### 9.1 What Is Personal Context?

When we say personal context, we are talking about any piece of information that is relevant to a person's current situation. Dourish points out some issues with this [Dourish 2004]. Specifically, he notes that there are endless potential pieces of context in a given situation, but the vast majority of contextual information is not relevant at any given moment in time. Furthermore, information can go from contextually relevant to irrelevant or vice versa very quickly and fluidly. Thus, a more common interpretation is to say “any piece of information that is *potentially relevant* to a person’s current situation.” Dey makes this a bit more concrete by identifying some common categories: location (where), identity (who), time (when), and activity (what) [Dey 2010]. However, other categories can be considered personal context, for example, the social context of an interpersonal relationship.

For now, rather than obsessing over a precise definition, we’ll just establish some guidelines to help you identify instances of personal context. Personal context is personal: it relates to an individual. It changes on some time scale, whether that is on the order of milliseconds, hours, weeks, or even years. For our purposes, it should also be plausibly useful: inferring context doesn’t matter if nobody can come up with a reason that having that context is helpful or important in some way.

Within these guidelines, there remain many different possibilities for personal context. For example, time is not simply restricted to clock time, it could be something much more relative, such as “breakfast time.” *Breakfast time* might be a more useful piece of context for a particular application than, say specifying a clock time when we expect the user to be eating breakfast. It even has a pretty straightforward definition “the time during which the user is eating breakfast in the morning.” However, this doesn’t mean that inferring this piece of context from phone sensors is as straightforward: how do we know from the available sources of data that the user is actually eating breakfast? On an even more basic level, what are the available sources of context?

### 9.1.1 A Continuum of Personal Data

While it can be useful to think about “types” of personal context as noted, another way to think about context is to think about levels of abstraction within personal data. Personal context is a type of personal data—it is data about an individual. Personal data is also what fuels personal context inferences. Figure 9.1 shows a continuum of personal data, ranging from low level streams on the far left side all the way up to a holistic understanding on the far right side. In general, the process of inferring personal context means taking data at some point on this continuum (often more on the left side) and developing a model or inference to move it up the continuum toward the right side. For example, it is possible to use accelerometer and gyroscope data (far left side) to infer step count. Step count could then be used (perhaps in combination with other things) to infer physical activity, which could be used as an input to an inference about clinical depression. See Wiese et al. [2017] for a more thorough exploration of these ideas.

### 9.1.2 Questions to Consider Before Developing a New Personal Context Inference

The two examples described in the sections below demonstrate two very different opportunities for inferring personal context from mobile devices. The process of completing each of those projects was not simple: it required considerable planning and forethought. It can be tempting to jump right in and start training models right away. However, just as human–computer interaction (HCI) tells us we should think about design before starting to code an application, some forethought and planning is very important when inferring personal context. Some of those questions are listed below.

### 9.1.2.1 Q1: What Am I Actually Inferring?

Having a clear description of the specific thing that will be inferred is an important first step. Let's say you want to develop an “Are people nearby?” inference. Is that a binary (yes/no) classifier, or is it guessing how many people are nearby? What does “nearby” actually mean? Within a certain distance? In the same room? How frequently will this inference change? Having a specific statement of what the inference really is will be essential background for answering the remaining questions.

### 9.1.2.2 Q2: What Is the End Goal for this Classifier?

It is important to identify the purpose for developing the classifier. Is the goal to show that it that it is possible and establish how well it might work? Or is the classifier going to be used in a production environment as a part of an application? If it will be deployed, is the inference going to be available programmatically to third-party developers, or only used within your own application? Understanding the end goal has implications for other aspects of development, such as the pipeline for collecting data from sources and the robustness of the resulting classifier. It can also have implications for tuning the model, for example, trading off between precision and recall.

### 9.1.2.3 Q3: What Data Do I Need, What Data Do I Want?

Next, it is important to consider what data source(s) you will use for the classification. There are many possible data sources: inertial measurement unit (IMU) sensors, location, phone state, app usage, and log data from many apps as well. Will the inference depend on having a long history of data in order to calculate features, or is an instantaneous measurement alright? For example, the tie strength and life facet classifiers described in Section 9.3 require having enough data in the call and SMS logs that features can be calculated from them. Without a minimum amount of data, the classifiers simply cannot function. By contrast, the phone placement model in Section 9.2 needed only instantaneous data.

### 9.1.2.4 Q4: Where Will My Training Data Come from, and Is It Good Enough?

Many ideas for inferring personal context break down when it comes to this question. Unlike many other types of inferences, personal context classifiers can seldom be calculated from an existing “big data” style dataset. A major reason for this is that the data labels can often be difficult to come by. For example, in the hypothetical “are people nearby?” classifier above, where does the data label come from? You could have the user label the data *in situ*, as we did in the work described in Section 9.2. In other situations, such as the relationship classifiers in Section 9.3, you could have the user label these *post hoc*. The challenge with inferring personal context is in the name: it’s *contextual*, which means that the data label depends on the individual *person* and the situation they are in. In some cases data labels might be able to come from someone other than the user (which can be costly and can introduce other issues), but much of the time they cannot.

Another important aspect to consider for training data is its coverage. One way to think about coverage is to consider the question “What percentage of unique real-world situations does my training data cover?” In practice this is a very difficult question to answer, but breaking it down can make it a bit more tractable.
