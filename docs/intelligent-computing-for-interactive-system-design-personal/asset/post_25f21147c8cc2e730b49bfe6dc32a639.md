## 9.3.5 Q5: What Are the Privacy and Ethical Implications of Developing this Classifier?

One of the issues with developing these classifiers was the sheer volume of sensitive data we were asking for from our participants. While we had institutional review board (IRB) approval from our university's IRB, ultimately we were asking for our participants to trust us with their communication records.

There are also some serious implications to consider if the classifier ends up working well. Having this kind of contextual information about a person's relationships can be very valuable for certain types of social engineering attacks. Another issue is that, depending on how this classifier was used, it might be possible to be gamed. For example, if the classifier is used to automatically determine privacy and sharing preferences, an adversary could potentially communicate with a target in such a way that the classifier is fooled into thinking the adversary should get access to data that they should not.

Finally, there are potential ethical implications to knowing about an individual's social support, especially if they do not have much support. For example, if someone is socially isolated they might be at risk for depression or self-harm behaviors. Or they might just have multiple phones, and so the data we have access to is an incomplete picture of the user's social interaction. What responsibility does a developer or researcher have in this situation? Should they solicit help? Suggest that the user seek help? Simply ignore this information? While we were not planning to deploy this classifier, these concerns are real and complex.

## 9.3.6 Q6: A General Classifier or Personal Classifiers?

In the case of these classifiers, a personal classifier doesn't make much sense, because these (life facet and tie strength) are things that are not likely to change, and if they do they will probably change slowly over a long period of time. Thus, having a personalized classifier to tell me who my four closest people are makes no sense—I know who those people are, and once I provide that training data to the classifier the classifier does not need to classify those contacts again. The value of this classifier is in a user never having to tell the phone, but the phone automatically inferring this information, and thus a general classifier makes more sense here.

## 9.3.7 Q7: What Happens When the Classifier Is Wrong?

Again, because the purpose of developing these models is for research, rather than for a production system, the cost of a wrong classification is fairly low in an immediate sense. However, the answer to Q5 clearly shows that if we are not careful with how the classifier is used, it could end up exposing information that the user did not want to be exposed. This risk, combined with the relatively low likelihood that tie strength and life facet will change suggests that one strategy for dealing with wrong classifications is to make it easy for the user to confirm that a classification is correct, or to correct it if it is wrong. Because it is unlikely to change frequently, correcting wrong classifications manually takes a relatively small amount of effort.

## 9.3.8 How Well Do the Classifiers Perform?

Now that we've considered these questions, how do the classifiers perform?

### 9.3.8.1 Life Facet Classification

To evaluate the life facet classification, we built a model with SVMs (polynomial kernel; d = 2). Since an SVM is originally a binary classifier, we composed three pairwise SVMs (family-vs.-work, family-vs.-social, and work-vs.-social) and combined their outputs with a maximum voting method. We also compared the result with two different models using WEKA [Hall et al. 2009]: a rule-based model (decision tree C4.5) and probabilistic model (naïve Bayes [NB]).
We also split the data into three different categories and trained models for each dataset:

- all includes all contacts on the 70-person list
- contactlist includes only contacts from the 70-person list who appear in the user's phonebook
- somecomm includes only contacts from the 70-person list with at least one logged SMS or call

For the 70-contact list data set, the SVMs showed 65.5% accuracy with survey features and increased to 81.0% when using all features (see Table 9.5). Note that half of the contacts in the 70-contact list were online friends, that is, the profile and mobile-communication features did not contain their data. Nevertheless, this approach achieves a 13.2% improvement in accuracy in using the survey feature. The SVMs yielded 68.5% accuracy on the in-phonebook list using the profile and mobile-communication features together. Accuracy went up to 88% for contacts that users actually communicated with (the communication list set).

This is because the profile variables that strongly correlated with the family facet, like last name and Is-starrer, were missing on many contacts or only associated with a few strongest ties. On the other hand, we could classify family and social contacts correctly by using mobile communication features while many of the work-type contacts were confused as social because of no communication logs.

The combination of profile and communication features failed to classify the work facet, shown in Table 9.5. We have two possible explanations. First, the number of the profile features (17) was much smaller than the number of the communication features (136), and thus might be less influential within the combined feature vector. Second, the profile features had many missing values and SVM does not handle missing data well. To address these issues, we need a feature selection scheme or classifier combination approach with two different models built on each type of feature.

### 9.3.8.2 Tie Strength Classification

We trained the tie-strength models using the Weka Toolkit's [Hall et al. 2009] implementation of an SVM. We conducted a leave-one-participant-out cross-validation (each fold contained data from one participant). This prevents any anomalies within a particular participant's data from causing a performance overestimate. We trained nine models, varying two aspects of input data. First we varied what the model was classifying (as described in Q1 between a ternary classifier and two different binary classifiers (first column of Table 9.6). Second, similarly to the life facet models, we also varied the input data for the classifier (second column of Table 9.6).

Classification results vary considerably (Table 9.6), ranging from 46.28% (κ = 0.179), to 91.55% (κ = 0.361). The κ statistic measures the agreement between predicted and observed categorizations, correcting for agreement that occurs by chance. Table 9.6 reveals clear trends. First, within each of the class conditions, classifiers perform best for all, second best for contactlist and worst for somecomm. Most of the contacts who are not in the contact list (thus excluded from contactlist models) or who have no communication history (thus excluded from the somecomm models) are not strong ties, and thus are easier to classify. As a result, the models that include them perform better.
