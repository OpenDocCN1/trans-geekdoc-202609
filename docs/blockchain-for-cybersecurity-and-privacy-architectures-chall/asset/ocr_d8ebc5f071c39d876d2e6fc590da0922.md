The part of the system relies on the PHP Laravel framework. The prototype is implemented simply and does not benefit the security features of the Laravel system, such as Laravel Authentication System. However, by default, it benefits from protections for vulnerabilities, as cross-site request forgery and cross-site scripting, which Laravel provides. Relying on a platform such as Laravel for the web part of smart applications would result in better security for these applications and may allow quick improvement in the overall system by integrating other features of Laravel in the production environment.

Being a distributed application, and by running on a specific platform, blockchain brings additional vulnerabilities to the smart contract applications. Primitive codes caused by either development languages/platforms or lack of experience in distributed application design result in problems that may cause important security issues. Lu et al. (2016) proposed a system called OYENTE, which investigates the smart contract for vulnerability. OYENTE provides an output as a result of this investigation, pointing out possible vulnerabilities as integer overflow, underflow, parity인지 bug, stack depth attack vulnerability, transaction ordering, timestamp dependency, and re-entrance vulnerability for smart contract applications. This application was used during the case study, resulting in no significant security-related bug of the used types.

The business logic of retention payment is not complex. Event-ordering vulnerabilities and time-dependency are commonly seen business logic-oriented vulnerabilities in smart contract applications. The proposed smart application does not take any action on timestamps. Thus, it is not prone to the latter vulnerability. However, in order to examine the existence of event-ordering vulnerability, it is necessary to investigate the order of events for this specific use case. Later, there is a list that summarizes these orders of events, where each activity can be followed by activity 4.1 or 4.2.

+   1. Contractor uses MS Project add-in to claim the partial completion of project activity(s).
2. Contractor uses DApp to submit to the client.
3. Client sees a connection request on his/her screen.
4. Client checks the request and approves or rejects.
4.1 Once the request is approved, the retention amount of approved activities is transferred to the contractor's wallet.
4.2 If rejected, a pop-up appears on the contractor's screen, and the contractor makes the necessary changes.
