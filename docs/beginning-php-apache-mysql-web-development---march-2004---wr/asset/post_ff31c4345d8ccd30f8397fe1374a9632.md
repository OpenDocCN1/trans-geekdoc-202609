We also have left out the id from the insert, and inserted values into the zip_id and lair_addr columns only. MySQL treats ignored columns as if you had attempted to insert NULL into them. We need to specify every column when doing an insert. If you need to modify your SQL statement, having all the columns in the INSERT query gives you a nice placeholder so all you have to modify the insert.

The following is a little function. Assuming the insert worked properly ($result returned), the mysql_insert_id() function will return the value of the last auto_increment from the last query. This only works after running a query on a table with an auto_increment column. In this case we just inserted into the char_id table. We will need that value to insert into the char_main table.

```php
if ($result) $laidid = mysql_insert_id($conn);
```

The the connection is optional, but we think it's a good idea to always include it. If you omit it, it will use the most recently opened connection. In a simple application like ours, that's not a problem; in a more complex application where you might have more than one connection, it could get confusing.

There are a couple of concerns here. First, if there is already a power for this user (there shouldn't be; a new character, but always be prepared), we need not to insert the row. We already know how to take care of this by using the IGNORE keyword.

Second, we insert multiple rows of data with one query. Easy enough; all we have to do is supply a comma-separated list of value groupings that matches up to the column grouping in the query. For example:

```sql
INSERT INTO table (col1, col2) VALUES (val1, val2), (val3, val4)
```

When it comes to the char_good_bad_link link, we have a little bit of referential integrity that we have to handle (what MySQL does for us). We don't want to have a good_id/bad_id combination to match a bad_id/good_id combination. For the purposes of a relational database, that isn't bad, but for our purposes is considered a duplication. We will handle this contingency when updating a character, because this is a new character (with a new id), we don't have to worry about that just yet.

We don't really need to put the results of the mysql_query in a variable. We like to do this as a matter of habit if we need the return value later, then it will be available for use. In the case of a DELETE, you don't get a result set, you get a return value of either TRUE or FALSE.

Remembering that our char_good_bad_link need to maintain what we call “reverse” referential integrity (1, 3 matches 3), we remove all rows that contain the character's id in either column:

This brings us to the Enemies, where not only do we have to maintain referential integrity, but have to worry about updating rows where our id can be present in either of the two columns. We must maintain our own "reverse" referential integrity.

How did we deal with referential integrity? It turns out that it takes care of itself when we follow the same method we employed when updating the char_power_link table. By simply running the DELETE query we ran when deleting a character, and then immediately running the INSERT query when we are creating a new character, we ensure that only one set of rows matches to each character enemy. It's simple, elegant, and it works!

By this time, queries should seem quite familiar to you. The DELETE query is one of the simplest of the SQL statements. In DELETE queries, we need to delete each power that was selected on the Add/Delete Power page. We do this not only in the char_power table but in the char_power_link table as well (In our application, if a power is removed, we remove power from the characters as well). In order to perform a DELETE on multiple rows, we use the IN keyword, which with each id in the supplied comma-separated list of power IDs is matched against the id, and each matching row is deleted.


```php
$sql = 'DELETE FROM char_power WHERE id IN ($powerlist)';
```
