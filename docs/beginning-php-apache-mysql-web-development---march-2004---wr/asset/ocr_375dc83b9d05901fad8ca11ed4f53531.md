# Chapter 9

It may seem bit nitpicky, but you still have some duplicate data that you can take care of in the character. It is possible for more than one character to be in the same lair, as is the case with Clean Freak and Soap Stud. Let's create a table, and link it to the character with keys. Let's also add a new column to the character table for alignment. See the two tables that follow.

| id* | lair_id | name | real name | align |
|---|---|---|---|---|
| 1 | 1 | Clean Freak | John Smith | Good |
| 2 | 1 | Soap Stud | Efram Jones | Good |
| 3 | 2 | The Dustmite | Dustin Hare | Evil |

| id* | lair address | city | st | zip |
|---|---|---|---|---|
| 1 | 123 Poplar Avenue | Tompkins | OH | 45293 |
| 2 | 452 Elm Street #3D | Burgtown | OH | 45201 |

We might add the alignment column to illustrate a point. If you are in the middle of the normalization process, and discover there is some other data you need to add, it isn't difficult to do so. You could add a completely new table if you need to. That is the geist thing about relational design.

The City and State fields are not only duplicates, but they are redundant with the ZIP Code (which is in itself a representation of the City/State). City and State are also not directly related to the lairs (because other lairs exist in the same city). For these reasons, the ZIP Code is numeric, and a direct representation of City/State, we will make the ZIP Code a primary key. This is pass "three," in the three tables that follow.

| id* | lair_id | name | real name | align |
|---|---|---|---|---|
| 1 | 1 | Clean Freak | John Smith | Good |
| 2 | 1 | Soap Stud | Efram Jones | Good |
| 3 | 2 | The Dustmite | Dustin Hare | Evil |

| id* | zip_id | lair address |
|---|---|---|
| 1 | 45293 | 123 Poplar Avenue |
| 2 | 45201 | 452 Elm Street #3D |

| id* | city | st |
|---|---|---|
