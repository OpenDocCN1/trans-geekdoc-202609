# Chapter 9

There are further requirements for database normalization, but Third Normal Form is generally accepted as good enough for most business applications. The next step is Boyce-Codd Normal Form, followed by Fourth Normal Form and Fifth Normal Form. In our case, the Forms don't apply—the database is as normalized as it needs to. All tables are easily modifiable and updateable, without affecting data in the other tables.

We know there are some database gurus out who would tell you that in order to completely satisfy the Forms of normalization, the align column should be put into its own table and linked with a foreign key. While that may be true in the strictest sense of the rules, we think of normalization as a guideline. In this case, we have only two values, good and evil. Those values will never change, and they will be the only values available to the user. Because of this, we can create a column with the enum datatype. Because the values evil will be hardcoded into the table definition, and we don't ever see a need to change the values in the future, there is no problem keeping those values in the char_main table.

# Standardization

When designing a application, it is a very good idea to come up with standards, or design rules, that you adhere to in all cases. such as the standards published by the W3C for XML, and others. They can be very short, but very strict, such as the list of standards brought from a mountain by an old bearded man. For now we'll standardize our table structure. For this application, we came up with the following tables:

+   **Table names:** Table names should be descriptive, but relatively short. Table names will be in lowercase. They should describe what main function, and what application they belong to. All of our tables should start with "char," to show that they belong to the character set.

+   **Column names:** Table columns are similar to table names. All column names will be in lowercase. They will be kept short, but multiple words (such as address and list) will be separated by an underscore "_" (like_addr).

+   **Primary keys:** Single primary keys will always be called "id". Except in special cases, primary keys will be an integer datatype that is automatically incremented. If they consist of a single column, they will always be the first column of the table.

+   **Foreign keys:** Foreign keys will be "id". They will start with the table descriptor. For example, in the char_lair table, the foreign key for the char_zipcode table will be called zip_id.

# Finalizing the Database Design

One thing we like to do during the database design process is to put the datatypes into the empty cells of each table. We can print these and easily refer to them when we are writing the SQL code. You might want to do this yourself (or just use the tables provided).

If you don't understand datatypes, you can learn about them in Chapter 3, and we discuss datatypes in more detail later in this chapter. For now, just understand that datatypes are the type of data stored in each column, such as INT (integer), VARCHAR (variable-length string), or ENUM (enumerated list). Appropriate, for example, varchar(100) is a character column that can contain up to 100 characters.
