# How It Works

Your first file, config.php, contains just five lines:

```
define('SQL_HOST','yourhost');
define('SQL_USER','youruser');
define('SQL_PASS','yourpass');
define('SQL_DB','yourdatabase');
define('ADMIN_E_MAIL','your@e-mailaddress.com');
```

These constants are created separately so that in the event that you make a change as moving the application to another server, or changing the password, it can be done in only one location. If this data were in each file, any change would require modification of several files.

# Chapter 13

Take notice of the CREATE DATABASE statement. There are a couple of things you should be aware of when creating databases. If you already have a database (one that you created in another chapter, or if your site is already using a database), it's better to create your mailing list tables in that. You do not need to create extra databases if your Web site spans multiple databases, and that is extra overhead that is just not necessary.

In addition, if there are any relationships between your tables from one application and tables from other apps, they need to be in the same database. For example, if you have a user table that stores your registered users for all applications, all of the applications that rely on that user should reside in the same database.

If you need to create a new database, the CREATE DATABASE command may still work if your site is hosted by an Internet service provider (ISP). Some ISPs don't allow programmed creation of databases. If this is, you may need to go through your ISP to create the database (through PHPMyAdmin for example) and run sql.php. Just sure to put the proper database name in the code. See Chapter 9 for more information about creating databases.

This SQL is used to create the tables in your database:

```
$sql1 = <<EOS
CREATE TABLE IF NOT EXISTS ml_lists (
ml_id int(11) NOT NULL auto_increment,
lastname varchar(255) NOT NULL default '',
PRIMARY KEY (ml_id)
) TYPE=MyISAM;
EOS;

$sql2 = <<EOS
CREATE TABLE IF NOT EXISTS ml_subscriptions (
ml_id int(11) NOT NULL default '0',
user_id int(11) NOT NULL default '0',
pending tinyint(1) NOT NULL default '1',
PRIMARY KEY (ml_id,user_id)
) TYPE=MyISAM;
EOS;

$sql3 = <<EOS
CREATE TABLE IF NOT EXISTS ml_users (
user_id int(11) NOT NULL auto_increment,
firstname varchar(255) default '',
lastname varchar(255) NOT NULL default '',
e_mail varchar(255) NOT NULL default '',
PRIMARY KEY (user_id)
) TYPE=MyISAM;
EOS;
```

Note there are three tables: ml_lists, ml_users, and ml_subscriptions. The ml_lists table contains two columns: the unique ID (ml_id) and the name of the mailing list (lastname). The ml_users table contains four columns: the unique ID (user_id), first name (firstname), last name (lastname), and e-mail address (e-mail).

The ml_subscriptions table where most of the "work" is done when it comes to mailing lists, contains three columns: ml_id, user_id, and pending. The combination of ml_id and user_id must be unique (You don't want to have the same user in the same mailing list than once, right?). The pending column is used to determine whether or not a user has finished subscribing. We describe the use of the pending column in this chapter.

The following lines simply run the SQL queries to create the tables. As long as all three tables are created (or already exist), you will see "Done" on the screen. Otherwise, you will see an error message.

```
$res = mysql_query($sql1) or die(mysql_error());
$res = mysql_query($sql2) or die(mysql_error());
$res = mysql_query($sql3) or die(mysql_error());
echo "Done.";
```

Let's pause for a moment and talk about form submission. A common practice is to post a form back to itself, but that certainly could go disastrous. When your page contains data that needs to be inserted into a database, you need to think twice about self-posting forms. If the user were to refresh or reload the page, all of your database functions would run and you would end up with duplicate data or records you didn't mean to delete.

Obviously, you don't want that to happen, so in order to minimize the probability, post a separate form called admin_transact.php. This page handles all of the necessary database transactions and then redirects back to the page from which you came. If the user reloads the page, no harm will come to your database.

```
<form method="post" action="admin_transact.php">
```

You might notice that all of your buttons have the same name, "action", each with a different value. When posting the form, you are accessing the $_POST['action'] variable to set which button was pressed and perform the action. This allows you to use one script for multiple transactions rather than having to create a multiple page with each form, allowing posting to a different transaction page.

```
<input type="submit" name="action" value="Add New Mailing List">
```
