You can tell Keras not to convert your Python functions by setting dynamic=True when creating a custom layer or a model. Alternatively, you can set eager=True when calling the model's compile() method.

TF Function generates a graph for every unique set of input shapes and data types, and it creates for subsequent calls. For example, if you call tf_cube(tf.constant(10)), a graph will be generated for int32 tensors of shape []. If you call tf_cube(tf.constant(20)), the same graph will be reused. If you then call tf_cube(tf.constant([10, 20])), a new graph will be generated for int32 tensors of shape [2]. However, this is only true for tensor arguments (i.e.- varying argument types and shapes). If you pass numerical values to a TF Function, a new graph will be generated for every distinct value: for example, calling tf_cube(18) and tf_cube(28) will generate two graphs.

If you call TF many times with different Python values, then many graphs will be generated, slowing down your program and using up a lot of RAM. Python values should be reserved for arguments that have few unique values, such as hyperparameters the number of neurons per layer. This allows TensorFlow to optimize each variant of your model.

# Autograph and Tracing

So how does TensorFlow generate graphs? First, we start by analyzing the Python function's source code to capture all the control flow statements, as for loops and while loops, if statements, as well as break, continue and return statements. This first step is called autograph. The reason TensorFlow has to analyze the source code is that Python does not provide any other way to capture control flow statements: __add__() or __mul__() to capture operators like + and *, but there are no __while__() or __if__() methods. After analyzing the function's code, autograph outputs an upgraded version of that function in which all the control flow statements are replaced by the appropriate TensorFlow operations, such as tf.while_loop() for loops and tf.cond() for if statements. For example in Figure 12-4, autograph analyzes the source code of the sum_squares() Python function, and it generates the tf_sum_squares() function. In this function, the loop is replaced by the definition of loop_body() function (containing the body of the original loop), followed by a call to the tf_stmt() function. This will build the appropriate tf.while_loop() operation in the computation graph.

![](img/0684d2da98e09085c0a622d4fd69aaad_424_0.png)

Next, TensorFlow calls this "upgraded" function, but instead of passing the actual argument, it passes a symbolic tensor, meaning a tensor without any actual value, only a name, a data type, and a shape. For example, if you call sum_squares(tf.constant(18)), then the tf_sum_squares() function will actually be called with a symbolic tensor of int32 and shape []. The function will run in graph mode, meaning that each TensorFlow operation will add a node to the graph to represent itself and its output(s) (as opposed to the regular mode, called eager execution, eager mode). In graph mode, TF operations do not perform any actual computations. This will feel familiar if you know TensorFlow 1, as graph mode was the default mode. in Figure 12-4, you can see the tf_sum_squares() function being called with a symbolic tensor as argument (in this case, an int32 tensor of shape []), and the final graph generated during tracing. The ellipses represent operations, and the arrows represent tensors (both the generated function and the graph are simplified).

To view the generated function's source code, you can call tf.autograph.to_code(sum_squares.python_function). The code is not meant to be pretty, but it can sometimes help for debugging.

# TF Function Rules

Most of the time, converting a Python function that performs TensorFlow operations into a TF Function is trivial: just decorate it with @tf.function or let Keras care of it. However, there are a few rules to respect:

- If you call any external library, including NumPy or even the standard library, this call will run only during tracing, will not be part of the graph. Indeed, a TensorFlow graph can only include TensorFlow (constructors, operations, variables, datasets, and so on). Make sure to use tf.reduce_sum() instead of np.sum(), and tf.sort() instead of the built-in sorted() function, and so on (unless you really want the code to run only during tracing).
- For example, if you define a TF function f(x) that returns np.random.rand(), a random number will only be generated when the function is traced, so f(tf.constant(2)) and f(tf.constant(3)) will return the same number, but f(tf.constant([2,3])) will return a different. One should replace np.random.rand() with tf.random.uniform(), then a new random number will be generated upon every call, since the operation will be part of the graph.
- If your non-TensorFlow code has side-effects (such as logging or updating a Python counter), you should not expect side-effect to occur every time you call the TF Function, as it will only occur when the function is traced.
- If you wrap arbitrary Python code in tf.py_function() operation, but this will help performance, TensorFlow will not be able to draw any graph optimization on this code, and it will also reduce portability, as the graph will only run on platforms where Python is available (and the right libraries installed).
- You can call other Python functions or TF Functions, but they should follow the same rules, as TensorFlow will also capture their operations in the computation graph. Note that these other functions do not need to be decorated with @tf.function.
- If the function creates a TensorFlow variable (or other TensorFlow object, such as a dataset or queue), it must do so upon the first call, and only then, else you will get an exception. It is usually preferable to create variables outside of the TF Function (e.g., in the build(shape) method of custom layer).
- The source code of your Python function should be available to TensorFlow. If the source code is unavailable (for example, if you define your function in the Python shell, which does not give access to the source code, or if you deploy only the compiled files .pyc to production), then the graph generation process will fail or have limited functionality.
- TensorFlow will only capture loops that iterate over a tensor or a Dataset. So make sure you use i in tf.range(10) rather than i in range(10), or else the loop will not be captured in the graph. Instead, it will run during tracing. This may be what you want, if the loop is meant to build the graph, for example to create each layer in a neural network.
- And as always, for performance reasons, you should prefer a vectorized implementation whenever you can, rather than using loops.
