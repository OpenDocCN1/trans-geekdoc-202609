# Randomized Search

The grid search approach is when you are exploring relatively few combinations, like in the previous example, but when the hyperparameter search space is large, it is often preferable to use RandomizedSearchCV instead. This can be used in the same way as the GridSearch class, but instead of trying out all possible combinations, it evaluates a given number of random combinations by selecting a random value for each hyperparameter at every iteration. This has two main benefits:

- If you let the randomized search run for, say, 1,000 iterations, this approach will explore 1,000 different values for each hyperparameter (instead of just a few values per hyperparameter with the grid search approach).
- You have control over the computing budget which you want to allocate to hyperparameter search, simply by setting the number of iterations.

# Evaluate Your System on the Test Set

After tweaking your models for a while, eventually have a system that performs sufficiently well. Now is the time to evaluate the final model on the test set. There is nothing special about this; just get the predictors and the labels from your test set, run your final_pipeline to transform the data (call transform(), do not want to fit the test set!), and evaluate the final model on the test set:

```python
final_model = grid_search.best_estimator_

X_test = strat_test_set.drop('median_value', axis=1)
y_test = strat_test_set['median_value'].copy()

X_test_prepared = full_pipeline.transform(X_test)

final_predictions = final_model.predict(X_test_prepared)

final_mse = mean_squared_error(y_test, final_predictions)
final_rmse = np.sqrt(final_mse)  # evaluates to 47738.2
```

In some cases, the estimate of the generalization error will not be enough to convince you that it is 1% better than the model in product? For this, you can compute a 95% confidence interval for the generalization error using scipy.stats.interval().

```python
>>> scipy import stats
>>> confidence = 0.95
>>> squared_errors = (final_predictions - y_test) ** 2
>>> np.sqrt(stats.interval(confidence, len(squared_errors) - 1,
            loc=squared_errors.mean(),
            scale=stats.sem(squared_errors)))

```

The performance will usually be slightly worse than what you measured using cross-validation if you did a lot of hyperparameter tuning (when your system ends up to perform on the validation data and will likely not as well on unknown datasets). It is not the case in this example, but when this happens you must resist the temptation to tweak the hyperparameters to make the numbers look good on the test set; the improvements would be unlikely to generate new data. Now comes the prelaunch phase: you need to present your solution (highlighting what you have learned, what worked and what did not, what assumptions were made, and what your system’s limitations), document everything, and create nice presentations with clear visualizations and easy-to-read statements (e.g., “the median income is the number one predictor of housing prices”). In this California example, the final performance of the system is not better than the experts’, but it may still be a good idea to launch it, especially if this frees some time for the experts so they can work on more interesting and productive tasks.

# Launch, Monitor, and Maintain Your System

Perfect, you got approval to launch! You need to get your solution ready for production, in particular by plugging the production input data sources into your system and writing tests.

You also need to write monitoring code to check your system’s live performance at regular intervals and trigger alerts when it drops. This is important to catch not only sudden breakage, but also performance degradation. This is quite common because models tend to “rot” as data evolves over time, unless the models are regularly trained on fresh data.

Evaluating your system’s performance will require sampling the system’s predictions and evaluating them. This will generally require a human analysis. These analysts may be field experts, or workers on a crowdsourcing platform (such as Amazon Mechanical Turk or CrowdFlower). Either way, you need to plug the human evaluation into your system.

You should also make sure you evaluate the system’s input data quality. Sometimes performance will degrade slightly because of a poor quality signal (e.g., a malfunctioning sensing random values, or another team’s output becoming stale), but it may take a while before your system’s performance degrades enough to trigger an alert. If you monitor your system’s inputs, you may catch this earlier. Monitoring the inputs is particularly important for online learning systems.

Finally, you will generally want to train your models on a regular basis using fresh data. You should automate this process as much as possible. If you are likely to refresh your model only every six months (at best), and your system’s performance may fluctuate over time. If your system is an online learning system, you should make sure you save snapshots of its state at regular intervals so you can easily roll back to a properly working state.
