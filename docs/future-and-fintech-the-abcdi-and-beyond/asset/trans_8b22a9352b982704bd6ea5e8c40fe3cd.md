
# MLOps：整合 DevOps 与机器学习

传统上，在整个软件开发生命周期（SDLC）中，不同群体的人员独立工作。例如，在完成软件开发后，开发人员将其移交给质量保证（QA）测试人员，后者再将软件包移交给运维部门进行发布和生产支持。由于不同群体的人员必须等待彼此完全完成各自的工作，这种流程因协作低效而需要漫长的交付时间。因此，鉴于市场的快速变化，迫切需要开发更快的响应机制以满足市场需求，并实现敏捷产品交付。

在现实世界中，ML 生命周期是一个复杂的过程，如[图 14.1](#chap14.xhtml#fig14-1)所示。数据科学的 ML 代码仅占生产环境中 ML 生命周期的一小部分，而生命周期的大部分与工程组件相关（见谷歌指出的[图 14.2](#chap14.xhtml#fig14-2)[[1]](#chap14.xhtml#rref1)），如特征工程和模型运维。事实上，在 ML 生命周期的设计、开发、测试、部署和维护阶段，存在许多与工程相关的痛点。

首先，职能角色（见附录[表 14.8](#chap14.xhtml#tab14-8)）通常分布在不同部门，协作有限。跨职能谈判在许多情况下会导致延迟。此外，不同职能的员工不共享相同的思维模式和理解。[图 14.3](#chap14.xhtml#fig14-3)展示了 ML 生命周期中不同角色之间的典型交互。开发人员和测试人员通常持有不同的观点和视角。数据科学家更关注数据异常值、概念漂移和偏见，并以此为基础构建模型。然而，测试人员可能更关注风险，以确保不会出现严重问题。这可能导致一种场景：开发人员制造了一件防弹背心，但测试人员却瞄准腿部射击。此外，精通 ML 算法和数学模型的优秀数据科学家未必是优秀的软件工程师，因为他可能缺乏编写端到端应用程序的经验。再者，负责生产环境软件管理的运维人员可能不理解 AI 和 DS 模型，从而导致部署延迟、误解和对模型的误读。

专业知识的不匹配总是导致这种“神话” —— 数据科学家花费一个月开发模型；而直到第 10 个月末，模型才出现在生产环境中；业务最终用户一年后才开始使用它。一项调查显示，87% 的 ML 项目从未上线[[1]](#chap14.xhtml#fn1)，主要归因于上述的复杂性。当企业 ML 开发依附过多工具和框架时，其开发速度缓慢，难以标准化和扩展。这些因素往往导致流程延迟、团队摩擦和资源浪费。

其次，ML 开发的本质通常是持续且迭代的。万物皆在流变 —— 新数据、算法、库和框架持续影响模型性能，从而改变测试、验证和监控的方式。

第三，内部治理流程往往相互孤立，通常是手动且低效的。特别是由于金融机构（FIs）的严格监管，数据和模型验证及治理程序通常繁文缛节、手动且缓慢。在许多公司，没有配备自动化工具的专门 ML QA 团队。此外，ML 开发有一些特殊要求，例如：生产数据可能用于开发环境；IT 团队的开发人员可能阅读未标记的业务数据以了解其实际含义；模型需要频繁重新训练以保持性能等。

第四，AI 生产的依赖关系通常很复杂，不仅体现在人员、技术和工具上，还体现在数据变更和业务需求的转变或增加上。例如，某些复杂模型（如深度神经网络）具有高计算复杂度且训练时间长，这推动了对加速器（如 GPU、TPU 和 FPGA）的高需求。此外，大量精力常用于处理数据并从原始数据中寻找最佳特征集以进行最佳建模。然而，往往缺乏合适的自动化流水线。同时，ML 模型应具备可扩展性，例如，模型能从小规模平滑过渡到大规模，在部署和维护中无痛苦。

最后但同样重要的是，外部客户提出了更高要求，监管机构施加了更严格的要求。我们可以看到该领域实施了更多新法规和实践，例如 AI 伦理（见[第 4 章](#chap4.xhtml)）。模型资产不应隐匿于暗处。所有模型都应妥善保管并在组织内可见。例如，在风险应用中，客户需要明确的理由说明他们为何受到决策的不利影响，例如信用卡或贷款申请。

在这方面，构建高效的 ML 生命周期流程成为行业的一个挑战。现在 DevOps（见[第 12 章](#chap12.xhtml)）应运而生以解决这一问题。特别是，DevOps 与 ML 的整合产生了一个名为 MLOps 的新概念（见[图 14.4](#chap14.xhtml#fig14-4)）。

## 14.1.1 特征

MLOps 通常应表现出一些特殊特征，如[表 14.1](#chap14.xhtml#tab14-1)所列：可复现性、可审计性（问责制）、验证、自动化、可观测性、协作性和可扩展性。例如，可复现性对于 ML 模型的容错、迭代筛选和适当审计至关重要。它需要阐明以下方面的变异来源：(i) 模型架构；(ii) 超参数；(iii) 初始化方法，如层权重（随机初始化/梯度）；(iv) 数据集打乱；(v) 训练策略，如轮数和误差容忍度；(vi) ML/DL 框架和库；(vii) CPU 设置，如多线程；(viii) GPU 设置，如浮点数、混合精度。

请注意，MLOps 的概念应与 ML 框架、编程语言、平台和基础设施无关。然而，实际实现可能是特定的。作为最佳实践，MLOps 应在开始时具有明确的业务目标和 ML 靶标、经过验证的高质量数据集、一个紧密协作的团队（见附录[表 14.8](#chap14.xhtml#tab14-8)），具备高效沟通和互补技能、适合 ML 实验的正确开发环境，以及使用流水线进行复现。

## 14.1.2 优势

实施这些特征后，MLOps 平台能以可复用或可复现的方式，更快、更轻松、更频繁地开发和部署 ML 产品：

*   集中管理特征或模型的跟踪、版本控制和监控
*   整合不同技术，如不同类型的 ML/DL 平台、模型格式、算法组件等
*   减少科学与工程之间的摩擦，增强各角色间的协作，如数据科学团队和 IT/运维团队
*   最小化偏见并提高可解释性，如可将 XAI 组件嵌入框架
*   降低风险，如自动化可审计流水线
*   以组织良好且高效的方式比较模型质量和性能
