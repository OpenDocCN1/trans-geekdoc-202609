

这四个角色之间可能存在许多重叠，但可以说数据科学家可以同时承担机器学习工程师、数据分析师和数据工程师的工作职责，反之则不然。在本章中，我们的观点是收集、存储、分析和呈现数据以创造价值是团队的责任。团队成员需要就其职责达成共识，每个角色都有其自身的贡献和重要性。一个关键点是确保管理层拥用所有可用信息以进行协调一致的决策，并且机器学习产品能够以高效的方式交付到市场。

## 14.2.4 CI/CD

CI/CD 是软件工程 DevOps 中的一个关键概念（参见[第 12 章](#chap12.xhtml)和[[4](#chap14.xhtml#rref4), [5](#chap14.xhtml#rref5)]）。通常，CI/CD 流程利用流水线，每当代码发生变更时（例如 `git push` 或 `merge`）触发，以自动构建软件资产、运行测试并部署编译后的包。

然而，通用的软件 CI/CD 流水线与 ML 流水线截然不同（参见[表 14.2](#chap14.xhtml#tab14-2)）。除了响应代码变更的通用操作外，ML 流水线还经常因模型和数据变更，以及环境和配置变更，而按请求或计划触发运行。另一方面，CI 组件在 MLOps 中具备测试和验证数据模式、数据及模型的能力，而 CD 组件支持模型部署和最终的模型服务（可能与应用程序一起）。有时，另一个术语——持续测试（CT）——用于指代在原始 CI/CD 框架内的自动模型重新训练和优化。

## 14.2.5 对比

MLOps 工作流利用 DevOps 原则，并可应用于 ML 运维。例如，MLOps 中的数据或模型版本控制是除通用 DevOps 中的代码版本控制之外的额外需求。模型可复现性与软件复用截然不同，因为前者需要基于场景和数据进行调优。此外，可复现性应同时针对计划任务和按需任务实现，因为模型会随时间衰减，部分原因是数据漂移和概念漂移。

**表 14.2.** CI 与 CD 的对比

| | **持续集成** | **持续交付** |
| --- | --- | --- |
| 阶段 | ML 开发术语和工作流 | ML 运维（部署、监控、维护、诊断）术语和工作流（有时也可能包含 CI） |
| 目标 | 生成一个准备好部署到服务器或机器上的打包制品 | 安全且可重复地将制品交付到生产环境 |
| 通用操作 | 开发、合并冲突、管理代码、检查代码完整性、检查库/包版本、代码审查、测试代码（单元测试/集成测试）、安全检查 | 发布、部署和监控应用程序 |
| ML 专用操作 | 检查数据/元数据/模式完整性，测试和验证模型（UAT/预发布、常规特征工程）；持续训练（CT） | 监控模型性能；触发模型重新训练 |

除了 MLOps，还有一些源自 DevOps 且具有独特特性的其他概念。DataOps 工作流基于类似的原则构建，例如协作和自动化，作为数据管理工作流。这些工作流可以消除源自数据层面的孤岛。ModelOps 涵盖 ML 实验。在此，DataOps 和 ModelOps 被视为 MLOps 的一部分，尽管某些文献将 MLOps 狭义地定义为 ModelOps。[图 14.9](#chap14.xhtml#fig14-9) 展示了 DataOps、ModelOps 和 DevOps 之间的联系，它们形成了 MLOps 流程以集成和复用现有的 IT 资源。GitOps 是一种特定的 MLOps，以 Git 为核心组件，通过 Git 请求（如 `pull` 和 `merge`）完成 CI/CD 动作。[表 14.3](#chap14.xhtml#tab14-3) 对比了 DevOps、DataOps 和 MLOps 之间的差异。

另一个概念 DevSecOps（参见[第 13 章](#chap13.xhtml)），将开发、安全和运维原则统一到一个统一框架中。该工作流通常通过持续反馈循环实现自动化。这确保开发人员将时间花在关键任务上，并持续改进和保障代码安全。这一理念也可以融入 MLOps，因为如果代码安全性和模型鲁棒性不足，ML 数据和模型可能容易受到某些攻击（参见[第 3 章](#chap3.xhtml)）。MLOps 与安全的结合（MLSecOps）可用于从一开始就防止漏洞进入 ML 项目。

目前的 MLOps 以模型为中心的方法为主导。特别是，ML 实验几乎聚焦于模型选择、超参数调优和模型验证。然而，一些研究人员认为以数据为中心的方法可能更适合未来的 MLOps。通用的格言“垃圾进，垃圾出”以及“数据科学家约 80% 的时间花在清洗数据上”说明数据实际上是 ML 生命周期中最重要的组成部分之一。这与 Andrew Ng 的观点“不管是数据，都是 AI 的食物”不谋而合。^([3](#chap14.xhtml#fn3)) 以模型为中心的方法将 ML 平台与关键数据流水线和生产环境分离开来，导致 MLOps 操作通常分散在多个不同的平台上。由于以数据为中心的方法试图从“固定”模型中榨取最佳性能，数据流水线和模型流水线应当无缝集成。这意味着带有流水线工具的数据和 ML 平台应重新设计和重新开发，以满足新的集成需求。
