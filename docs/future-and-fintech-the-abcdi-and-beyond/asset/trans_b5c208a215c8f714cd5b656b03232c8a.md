

## 4. 特征工程与模型构建

对于特征工程，数据科学家可能会在 `Feature Store` 或 `Databricks` 的工作台中进行处理。特征可以在 `Feature Store` 内进行版本控制。^([9](#chap14.xhtml#fn9)) 对于初始模型构建，数据科学家可能会选择一些典型模型，例如 `ARIMAS`、`LightGBM`、`Extra tree`、`LSTM`、`AutoEncode` 等，作为候选模型。`Optuna` 被用作模型的超参数调优器。为了降低为每台 ATM 调优模型的计算成本，首先根据 EDA（探索性数据分析）识别出一些典型的 ATM 使用场景。^([10](#chap14.xhtml#fn10)) 然后，调优过程仅应用于选定样本的典型场景。`MLflow` 的内置函数和自定义 Python 脚本均用于流程中以记录工件。训练结果存储在 `MLflow` 跟踪服务器中，我们可以从那里为每个场景选择最佳算法或候选模型。一旦某个场景的调优过程完成，调优后的模型结构将应用于同组中的 ATM，除非发生某些事件触发器。ML 实验由 ML 工程师优化为流水线。

## 5. 模型服务

`MLflow` 的服务功能可用于生成 RESTful 端点。然而，它通常是一模型一 API，这可能不适合本案例。相反，它可用于测试阶段，面向一小组 ATM。在生产阶段，会编写内部函数以批量加载模型进行预测。

## 6. 用户界面与监控

基于 `Django` 的 Web 服务用作运营人员的用户界面，以获取预测信息和一些补钞报表。实现了一个后台性能监控功能，用于发现模型性能下降和数据漂移，这可以根据预定义的控制规则，自动使用 ML 实验流水线为特定 ATM 触发模型重新训练过程。^([11](#chap14.xhtml#fn11))

## 14.4.2 基于 Kubeflow + Github 的案例研究

### 14.4.2.1 简介

`Kubeflow` 最初由 `Google` 开发，并于 2018 年作为开源项目发布，旨在用于在 `Kubernetes` 之上使用 `Tensorflow` 的 AI/ML 应用，以最大程度地减少 MLOps 工作量。`Google` 一直在使用基于 `TFX` (`Tensorflow Extended`) 的流水线，通过基于 `Kubernetes` 的基础设施部署生产环境中的 ML 模型。如今，`Kubeflow` 已扩展至其他现代 AI/ML 框架，例如 `PyTorch`、`MXNet` 和 `Chainer`，这使得开发人员能够在 `Kubernetes` 中快速创建、训练和调优 ML 模型，以实现动态资源配置。`Kubeflow` 有助于改进 AI/ML 模型的部署、可移植性和管理，如[图 14.14](#chap14.xhtml#fig14-14)所示。

### 14.4.2.2 场景

我们继续使用前面的 ATM 现金流预测示例，但将部署范围从单一市场扩展到全球市场。IT 基础设施因市场而异；因此，我们需要开发一种高效的方法，在有限时间内实现这一目标。

### 14.4.2.3 实施

`Kubernetes` 有几种不同的变体，例如 `Google Kubernetes Engine (GKE)`、^([12](#chap14.xhtml#fn12)) `Amazon Elastic Kubernetes Service (EKS)`、^([13](#chap14.xhtml#fn13)) 和 `Microsoft Azure Kubernetes Service (AKS)`。^([14](#chap14.xhtml#fn14)) 因此，用户可以选择带有特定工具包的相应云平台；或使用原始 `Kubernetes` 的本地部署设置，甚至是本地 `Minikube` 集群。

虽然 `Kubeflow` 功能强大，足以包含我们在[表 14.4](#chap14.xhtml#tab14-4)中列出的许多工具，但我们仅考虑一个主要包含 `Kubeflow` 和 `Gitlab` 的简化案例。示例流程如下：

1.  数据科学家在目标开发环境（通常是 `Jupyter lab`）中，基于从历史数据衍生出的特征，开发用于训练 ML 模型的源代码。
2.  平台或某些特定代码将每次训练的工件记录为实验中的一次运行。
3.  数据科学家查询 ML 实验，获取所有运行记录的指标。如果指标不满足期望标准，则回到步骤 1 并迭代以优化模型。
4.  数据科学家或 ML 工程师可将标准和阈值形式化为测试（流水线）代码。特征可连同相应的处理代码和设置存储在 `Feature Store` 中（如果有）。
5.  一旦找到满意的运行，数据科学家将持久化模型并在模型注册表中注册。还应开发流水线的评分脚本。
6.  数据科学家或 ML 工程师将 ML 实验代码形式化，并开发模型推理阶段的源代码。
7.  数据科学家或 ML 工程师将代码提交到自己的分支，提交带有变更描述的 Pull/Merge Request，并请求合并到主仓库的（master）分支。该请求可能伴随自动化构建和测试；有时，也会在流水线中包含代码质量和安全检查。
8.  指定的审查员或批准人（例如高级数据科学家/ML 工程师）将审查代码和模型变更（以及自动化构建（如有）和测试输出），并对变更发表评论和提供反馈。如果最终满足所有条件，他们可能会批准合并。
9.  成功合并（或新版本发布）将触发 CI/CD 平台中向 `Kubeflow` 部署新代码，即执行一条流水线，或可能按计划执行。这通常发生在开发环境或用户验收测试（UAT）环境中。
10. 可能会生成新的模型工件（例如配置文件、评估指标、模型分布等），并复制到中央仓库（或单独的模型注册表、git 等）。有时，对于计算密集型案例，可能直接使用存储在任何工件仓库中的数据科学家训练模型。
11. 流水线将自动更新仓库中相应配置的模型信息，提交变更，并创建合并请求，以便发布版本包含所有变更。
12. 指定的审查员或批准人（例如首席数据科学家或数据科学负责人）将评估模型，以确保模型满足部署的所有要求（例如性能、风险、伦理等）。
13. 合并批准将触发另一次 CD 部署到 UAT、预发布或生产环境。“推理”应用（链接和模型）将被更新。通常，在首次生产部署之前，需要进行 UAT。这需要业务利益相关者的批准，并结合主题领域专家（SME）的反馈。生产环境的重新部署可能需要 UAT，也可能不需要。
14. 由 DevOps 工程师维护的监控和诊断流水线将在 ML 在生产环境中运行后执行。应定义模型退役和模型重训的标准，以便事件触发相应的通知和流水线来处理棘手情况。
