
在本地电子产品商店，你可以买到集打印机、扫描仪、复印机、传真机于一体的多功能设备。与单独购买这四个组件的成本相比，它的价格很有优势，因为这四种功能的实现有相当大的重叠。此外，多功能设备体积小巧，你只需在系统上安装一个设备，而不是四个。但如果其中任何部分发生故障，你会一次性失去大量功能。因此，多功能机器代表了我们在任何系统设计中都要在功能性、经济性和可用性之间做出的权衡。

关于这类设备的架构决策，与上文关于模块化、信息隐藏以及软件组件复用或互换性的论点有关。基于这些原因，一些人建议在系统架构中采用异构性或“基因多样性”：让系统的许多组件来自单一来源，或依赖单个组件，都是有风险的。

然而，许多系统在这方面实际上相当同质化。出于便利性和成本考虑，我们经常设计使用单一供应商的软件或硬件（或两者兼有）的系统。例如，在计算机早期，从单一供应商处购买“捆绑”的硬件和软件非常方便。买家需要做的决定更少，如果出了问题，只需一个电话就能启动故障排查和维护。Daniel Geer 等人 [[GEE03a](#bib01.html#bib_220)] 考察了由单一制造商主导的计算单一文化，其特征通常是：今天由 Apple 或 Google 主导，昨天由 Microsoft 或 IBM 主导，明天未知。他们研究了农业中类似的情况，即整个作物可能易受单一病原体的侵害。在计算领域，病原体的等价物可能是从 Morris 蠕虫到 Code Red 病毒的恶意代码；这些“感染”造成的危害特别大，因为世界上很大比例的计算机因运行相同版本的操作系统而瘫痪（Morris 蠕虫针对 Unix，Code Red 病毒针对 Windows）。

多样性为攻击者创造了一个移动的目标。正如 Per Larson 及其同事所解释的 [[LAR14](#bib01.html#bib_361)]，自动引入多样性是可能的，但很棘手。编译器可以从一个源文件生成不同但功能等价的目标代码；重排语句（在功能上不依赖顺序的地方）、使用不同的存储布局，甚至添加无用但无害的指令，都有助于保护一个版本免受可能影响另一个版本的危害。然而，不同的输出目标代码可能会给代码维护带来噩梦。

**多样性减少了易受某一类攻击的目标数量。**

***

2014 年，许多计算机和网站受到所谓的 Heartbleed 恶意软件的影响，该软件利用了广泛使用的 `OpenSSL` 软件中的漏洞。SSL（安全套接层）是一种加密技术，用于保护浏览器的 Web 通信安全，例如保护银行交易的隐私。（我们将在 [第 6 章](#ch06.html#ch06) 中介绍 SSL。）`OpenSSL` 实现被大多数网站使用；两个使用 `OpenSSL` 的主要软件包占使用 SSL 的网站的 66% 以上。由于 `OpenSSL` 的采用范围极广，这一漏洞影响了大量网站，使大多数互联网用户面临风险。关于软件缺乏多样性的警告在此尤为相关。然而，密码学是一个微妙的主题；即使编写正确的代码也可能泄露敏感信息，更不用说代码可能出错的许多微妙方式了。因此，有充分的理由让少数密码学实现接受分析师的严格审查。但通用代码呈现了大规模故障的单一或共同故障点。

此外，多样性成本高昂，大型用户（如公司或大学）必须维护多种系统，而不能将精力集中在仅一种系统上。此外，大量竞争产品将大幅增强多样性，但市场经济使得许多供应商难以获得足够的利润维持生存。Geer 在 [[GEE03](#bib01.html#bib_219)] 中完善了这一论点，该论点引发了 James Whittaker [[WHI03b](#bib01.html#bib_656)] 和 David Aucsmith [[AUC03](#bib01.html#bib_36)] 的辩论。对于这一困境，没有显而易见的正确解决方案。

产品的紧密集成也是一个类似的担忧。`Windows` 操作系统与 `Internet Explorer`、`Office` 套件和 `Outlook` 电子邮件处理程序紧密关联。其中一个组件的漏洞也可能影响其他组件。由于紧密集成，修复一个子系统中的漏洞可能会影响其他子系统。另一方面，采用更多样化（从供应商角度）的架构，另一供应商浏览器中的漏洞（例如）只会在两个系统通过定义良好的接口通信的范围内影响 `Word`。

当程序被加载到内存中执行时，会发生另一种形式的变化。**地址空间布局随机化** 是一种技术，它使模块在不同的时间加载到不同的位置（使用类似于基址寄存器和界限寄存器的重定位设备，详见 [第 5 章](#ch05.html#ch05)）。然而，当整个模块作为一个单元被重定位时，获得一个真实地址就给了攻击者计算该模块所有其他部分地址的关键。

接下来我们从产品转向过程。如何生产出好的软件？与代码属性一样，这些过程方法不是配方：做这些事情并不能保证代码好。然而，就像代码特性一样，这些过程倾向于反映成功开发安全软件的人们的方法。

### 测试

测试是一个关注产品质量的过程活动：它旨在在潜在产品故障实际发生之前找到它们。测试的目标是使产品无故障（消除故障的可能性）；但现实地讲，测试只能降低故障的可能性或限制故障的影响。每个软件问题（尤其是与安全相关的问题）不仅可能导致软件故障，还可能对业务或生命造成不利影响。一个控制的失效可能会暴露出一个漏洞，而任何数量的正常运行的控制都无法缓解该漏洞。测试人员通过尽可能多地发现故障，并仔细记录其发现，以便开发人员能够定位原因并在可能的情况下修复问题，从而提高软件质量。

测试说起来容易做起来难，Herbert Thompson 指出安全测试尤其困难 [[THO03](#bib01.html#bib_613)]。James Whittaker 在 2010 年 8 月 20 日的 Google Testing Blog 中指出：“开发者种树；测试者管森林”，意思是测试者的工作是探索许多因素的相互作用。副作用、依赖关系、不可预测的用户以及有缺陷的实现基础（语言、编译器、基础设施）都增加了这种难度。但安全测试的本质复杂性在于，我们不能只关注程序做对的那一个行为；我们还必须寻找程序可能出错的成百上千种方式。
