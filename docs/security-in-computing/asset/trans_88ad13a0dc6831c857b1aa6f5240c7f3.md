

# IaaS 产品与云作为安全控制

## IaaS 标准化与迁移

IaaS 产品是三种服务模型中最标准化的，因为它们必须保持与常见操作系统和网络协议的兼容性。（[侧边栏 8-1](#ch08.html#ch08sb01) 描述了一种利用这一事实的巧妙方法。）API 挑战与 PaaS 模型中的大致相同，尽管在这种情况下，这些 API 侧重于对 IaaS 虚拟机 (VM) 的控制和交互。VM 本身通常易于迁移，因为有工具可将 VM 从几乎任何标准文件格式转换为另一种格式。然而，某些 VM 可能会导致问题：IaaS 提供商提供具有独特功能的专用 VM（例如，原本仅作为集成设备提供的防火墙产品），并且他们可能拥有这些产品的独家权利。根据客户网络配置的广泛程度，复杂性也可能成为切换 IaaS 提供商时的一个问题。

## 云作为安全控制

虽然将数据和功能迁移到云端确实存在风险，但云服务在许多方面可以成为有价值的安全工具。最明显的是，云服务通常擅长缓解单点故障。这种优势体现在几种形式中。

> **云计算可缓解单点故障的风险。**

### 地理多样性

如果您只有一个数据中心，您将面临各种本地化威胁：自然灾害、火灾和互联网中断，仅举几例。除了安全问题，仅拥有一个数据中心可能会不可接受地增加长距离通信的网络延迟。云服务可能是一种实现地理多样化的具有成本效益的方式。一些提供商甚至允许客户从数据中心列表中选择一个来托管其功能和数据；如果您有此选项，请务必选择一个距离主数据中心足够远的辅助数据中心，使其面临不同的风险。

### 侧边栏 8-1：云 RAID

2010 年，康奈尔大学的三位研究人员设计了一种巧妙的方法来对抗云存储的供应商锁定：与多个云存储提供商合作，并将每个提供商视为巨大 RAID 阵列中的单个硬盘驱动器。在提交给 ACM 云计算研讨会的一篇论文中 [[ABU10](#bib01.html#bib_01)]，Hussam Abu-Libdeh、Lonnie Princehouse 和 Hakim Weatherspoon 描述了一种在各种云提供商之间对数据进行条带化存储的方法，同时跨提供商保持足够的冗余，以便在某个提供商不可用时重建所有数据——这与 RAID 5 在小得多的规模上使用的方法类似。

研究人员的原型工具 `Redundant Array of Cloud Storage (RACS)` 充当云存储请求的代理，然后智能地将用户的请求分配给许多不同的提供商。为了帮助缓解该工具成为单点故障的担忧，多个 `RACS` 实例可以协调并代表单个客户行事。研究人员估计，与传统云存储相比，这种方法的成本将高出约 11%——主要归因于冗余所需的额外数据——但比在单独的存储提供商处维护两份完整的数据副本要便宜得多。此外，它极大地降低了供应商锁定的担忧，因为从一个提供商迁移出去将意味着仅移动您的一小部分数据。

虽然这项研究可能尚未准备好进行商业部署，但它为管理各种云迁移风险指明了一个有趣且潜在富有成效的方向。

### 平台多样性

本书讨论的许多网络攻击都是针对特定应用程序、操作系统或协议的。您的云提供商很可能运行与您不同的操作系统、应用程序和协议，此外，这些提供商部署和配置它们的方式也不同。这意味着它们拥有与您不同的一组漏洞，从而降低了您的系统和云提供商的系统同时遭受相同攻击的可能性。

### 基础设施多样性

除了软件栈，您和您的云提供商之间许多其他潜在的脆弱点也可能不同，包括硬件、网络配置、安全控制、安全人员素质、IP 地址和供应商。

许多迁移到云服务的公司不会妥善考虑单点故障的风险。他们不会利用云服务来缓解该风险，反而会使云服务成为他们的单点故障（有关这有多危险的示例，请参见[侧边栏 8-2](#ch08.html#ch08sb02)）。即使云提供商在多个地理位置分散的数据中心复制您的服务，您仍然必须担心这些数据中心共享许多共同漏洞，以及提供商倒闭的风险。如果您决定通过外包给两个云提供商而不是一个来缓解这些风险，您将多出一个需要注意的问题：许多云提供商本身就是更大云提供商的客户。如果您的一个云提供商正在向另一个销售服务，您可能并没有您想象中的那种冗余。

### 侧边栏 8-2：一个人的单点故障

2012 年 8 月，记者 Mat Honan 的数字生活被彻底颠覆。他正陪女儿玩耍，突然他的 Apple iPhone 关机了。手机重启后，他的所有数据都不见了。幸运的是，Honan 设置手机定期备份到他的 Apple 笔记本电脑上，所以他当时并不担心。不久后他打开笔记本电脑，屏幕变灰，他意识到遇到了真正的麻烦。不久之后，Honan 发现，除了手机，他的笔记本电脑和 Apple iPad 也被远程擦除了，而且他的 Gmail 和 Twitter 账户也被黑了。

以下是事件的简略版本 [[HON12](#bib01.html#bib_273)]：黑客从最初的目标——Honan 的 Twitter 账户（“@mat”）入手。该 Twitter 账户链接到他的个人网站，网站上列出了他的 Gmail 地址。当黑客前往 Gmail 尝试重置 Honan 的账户密码时，Gmail 向他们显示了 Honan 模糊处理的备用紧急邮箱地址：`m****n@me.com`。`me.com` 归 Apple 所有。黑客正确地猜测该 `me.com` 地址将是 Honan 用于 Apple iCloud 的用户名，iCloud 是一项将用户的所有 Apple 设备与存储在 Apple 数据中心的数据联系在一起的服务。

因为黑客以前实施过此类攻击，他们知道入侵 iCloud 账户所需的唯一额外信息就是 Honan 的邮寄地址和信用卡号后四位。邮寄地址很容易获取：他们只需搜索 Honan 网站的 whois 记录。为了获取信用卡后四位数字，黑客去了 Amazon。他们正确地假设 Honan 的 Amazon 用户名将是他的 Gmail 地址，并凭借这一点以及他们已掌握的信息，成功诱骗 Amazon 显示了该账户关联信用卡的后四位数字（有关攻击这一部分的详细信息，请参阅 *Wired* 文章 [[HON12](#bib01.html#bib_273)])。

一旦黑客掌握了那四位数字，他们就拥有了让 Apple 客服允许他们进入 Honan iCloud 账户所需的一切。得益于一项非常有用的 iCloud 安全功能——允许用户在设备被盗时远程擦除 Apple 设备——攻击者能够在几分钟内删除 Honan 所有设备上的数据。

也许这个故事最令人惊讶的部分是 Honan 了解攻击经过的方式：黑客告诉他的。其中一名黑客联系了他，作为不提起诉讼的承诺交换，详细讲述了整个事件。
