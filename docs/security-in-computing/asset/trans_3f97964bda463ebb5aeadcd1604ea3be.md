
在这个简单的例子中，只要同时打开的问题不超过 99 个，程序就可能长时间正确运行，但添加第 100 个问题会导致程序失败。当过程编辑或重新格式化输入时，会出现类似的问题，这可能会将单字符序列变为两个或更多字符（例如，某些字体中可用的单字符省略号符号“...”被文字处理器转换为三个连续的句点，以适应功能更有限的字体）。这些未预料到的大小变化会导致更改后的数据不再适合原本存储它的空间。更糟糕的是，错误似乎是偶发的，仅当数据量超过分配空间的大小时才会发生。

遗憾的是，防范这些错误的唯一手段是正确编程：始终检查以确保容器足够大，能容纳它所要包含的数据量。

### 整数溢出

**整数溢出** 是一种特殊类型的溢出，因为其结果与其他类型的溢出略有不同。**整数溢出** 发生的原因是存储位置具有固定、有限的大小，因此只能容纳不超过特定限制的整数。是否发生溢出取决于数据值是否为有符号数（即是否保留一位来指示数字是正还是负）。[表 3-1](#ch03.html#ch03tab01) 给出了几种内存位置（字）大小的有符号和无符号值的范围。

![Image](graphics/03tab01.jpg)

**表 3-1** 按字长划分的值范围

当计算导致值超过 [表 3-1](#ch03.html#ch03tab01) 中的某个限制时，多余的数据不会溢出到相邻的数据项中去影响它们。这是因为算术运算是在处理器的硬件寄存器中执行的，而不是在内存中。相反，要么发出硬件程序异常或故障条件信号，导致转移到错误处理例程，要么丢失数据项最高有效端的多余数字。因此，对于 8 位无符号整数，`255 + 1 = 0`。如果程序使用 8 位无符号整数作为循环计数器，而循环的停止条件是 `count = 256`，那么该条件永远不会为真。

检查这种类型的溢出很困难，因为只有当结果发生溢出时，程序才能确定溢出发生了。例如，使用 8 位无符号值，程序可以确定第一个操作数是 `147`，然后检查第二个操作数是否大于 `108`。这种测试需要双倍的工作：首先确定在范围内的最大第二个操作数，然后计算总和。某些编译器会生成代码来测试整数溢出并引发异常。

### 未终止的以空字符结尾的字符串

长字符串是许多缓冲区溢出的根源。有时攻击者会故意将过长的字符串输入处理程序，以观察程序是否以及如何失败，拨号程序就是这种情况。其他时候，漏洞是意外造成的：程序错误地覆盖了字符串的一部分，导致字符串被解释为比实际更长。这些错误实际上如何发生取决于字符串如何存储，而这取决于所涉及的编程语言、应用程序和操作系统。

如 [图 3-15](#ch03.html#ch03fig15) 所示，变长字符（文本）字符串有三种定界方式。最简单的方法由 Basic 和 Java 使用，即为声明的最大字符串长度分配空间，并将当前长度存储在独立于字符串数据的表中，如 [图 3-15](#ch03.html#ch03fig15)(a) 所示。

![Image](graphics/03fig15.jpg)

**图 3-15** 变长字符串表示法

某些系统和语言（特别是 Pascal）在字符串前面加上一个整数来表示字符串的长度，如 [图 3-15](#ch03.html#ch03fig15)(b) 所示。在这种表示法中，字符串“Hello”将表示为 `0x0548656c6c6f`，因为 `0x48`、`0x65`、`0x6c` 和 `0x6f` 分别是字符“H”、“e”、“l”和“o”的内部表示。字符串的长度是第一个字节 `0x05`。有了这种表示法，字符串缓冲区溢出很少见，因为处理程序首先接收长度，并可以验证是否存在足够的空间来容纳该字符串。（这种表示法容易受到我们前面描述的问题的影响，即在规划字符串空间时未能包含长度元素。）即使长度字段被意外覆盖，读取字符串的应用程序也只会读取写入长度字段中指定数量的字符。但因此字符串长度的限制就变成了能放入长度字段的最大数字，对于 1 字节长度可达 `255`，对于 2 字节长度可达 `65,535`。

表示字符串的最后一种模式，通常用于 C 语言，称为**以空字符结尾**，意味着字符串的结尾由一个空字节（即 `0x00`）表示，如 [图 3-15](#ch03.html#ch03fig15)(c) 所示。在这种形式下，字符串“Hello”将是 `0x48656c6c6f00`。以这种方式表示字符串可能导致缓冲区溢出，因为处理程序只有在接收完整个字符串后，才能通过确定字符串的结尾来确定其长度。这种格式容易被误解。假设一个错误的进程碰巧覆盖了字符串的结尾及其终止空字符；在这种情况下，读取字符串的应用程序将继续读取内存，直到碰巧出现一个空字节（来自其他某个数据值），这可能在字符串末尾之后的任意距离处。因此，应用程序可能会多读取 `1`、`100` 到 `100,000` 个或更多额外字节，直到遇到一个空字节。

缓冲区溢出问题也出现在计算中。移动和复制字符串的函数在将参数传递给这些函数时，可能会导致栈或堆中的溢出。

### 参数长度、类型和数量

数据长度错误的另一个来源是过程参数，来自 Web 或传统应用程序。问题的来源包括：

*   **参数过多**。例如，即使应用程序只接收三个传入参数，该应用程序也可能通过使用调用栈帧中传入的合法参数旁边的杂散数据，错误地写入四个传出结果参数。（相反的问题，即输入多于应用程序预期的情况，问题较小，因为被调用应用程序的输出将保持在调用者分配的空间内。）
*   **错误的输出类型或大小**。调用过程和被调用过程需要就交换的数据值的类型和大小达成一致。如果调用者为两字节整数提供空间，但被调用例程产生四字节结果，那多余的两个字节会去往某处。或者调用者可能期望以 1970 年 1 月 1 日后的天数作为数字形式的日期结果，但产生的结果却是“dd-mmm-yyyy”形式的字符串。
*   **字符串过长**。过程接收的输入字符串可能比它能处理的要长，或者它在输出时可能产生过长的字符串，这两种情况都会导致溢出条件。

过程通常拥有或分配临时空间来操作参数，因此临时空间必须足够大以容纳参数的值。如果传递的参数是以空字符结尾的字符串，则在找到尾随空字符之前，过程无法知道字符串有多长，因此非常长的字符串会耗尽缓冲区。
