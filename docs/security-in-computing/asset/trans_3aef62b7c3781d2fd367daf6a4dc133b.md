
公共云客户为准备事件检测和响应所能做的最重要的事情，是在与提供商编写 SLA 时解决日志记录和取证问题。SLA 可以包含事件通知、证据保存和证据访问的要求；它们还可以指定可用的日志类型和其他潜在的证据来源 [[CSA13](#bib01.html#bib_137)]。相关数据可能包括来自 Web 服务器、应用程序、数据库、操作系统、虚拟机监视器、网络设备、安全设备和云计算平台的日志，以及网络流量捕获。

然而，仅仅使日志可用是不够的。将日志发送到 SIEM 进行存储和分析，并极其小心地将 SIEM 及其存储从云服务中隔离出来，隔离程度以实际可行的范围为准。为了使 SIEM 发挥作用，它需要来自云服务的近实时日志数据流，但它也需要受到保护，免受可能已渗透云服务的攻击者的恶意影响。识别并消除任何潜在路径，这些路径可能允许云系统中的入侵者删除或修改来自您的 SIEM 或其底层存储的数据。

### 8.4 云身份管理

组织在迁移到公共云服务时面临的常见挑战之一是身份管理。云客户通常将敏感数据和功能移入云环境，因此他们需要一种方法来对访问云中这些资源的用户进行身份验证和授权。身份管理也保护云提供商：他们需要确保访问其服务的用户是客户组织的合法成员，而不是冒名顶替者。

解决云身份管理问题的显而易见的方法是让每个用户单独在每个云提供商处注册一个用户账户。不幸的是，这种方法充满了问题。一个问题是它创造了新的漏洞机会。云提供商像许多公司一样，有时会被黑客攻击，并且不一定擅长保护用户的密码和个人信息。要求用户在许多不同的云提供商处创建新账户会增加这些用户个人信息被盗的几率，而且如果这些用户重复使用其他服务的密码，这种做法会使他们面临更大的危害。正如我们在[第 2 章](#ch02.html#ch02)所述，许多用户不擅长选择和管理密码，给他们更多的密码来管理，特别是在敏感数据和功能面临风险时，是一个危险的主张。当用户为其 Facebook 和 Twitter 账户设置相同的弱密码时，他们只让自己处于危险之中。但当开发人员在涉及不同公司、不同合作伙伴和不同敏感数据的四个不同软件开发项目上使用相同的弱密码时，情况就完全不同了。

依赖云提供商进行身份管理也限制了组织为保护基于云的用户账户所能施加的控制：许多云提供商允许用户选择弱密码，或使用基本个人信息轻松重置密码（回想[第 2 章](#ch02.html#ch02)中描述的对 Sarah Palin 电子邮件的攻击）。很少有云提供商提供多因素认证选项，即使这变得更普遍，用户也理所当然地会反对为了各种云服务而不得不随身携带一口袋访问令牌。

除了这些问题之外，还有一个管理问题：一旦用户不再需要访问权限（无论是由于离开组织还是职责变更），组织如何禁用该用户的所有账户？正如我们在[第 2 章](#ch02.html#ch02)所述，在单个组织内分配和撤销访问权限就很难管理；有了多个云提供商，问题变得更具挑战性。大型组织可能使用数十甚至数百个云服务提供商，跟踪所有这些提供商，以及哪些用户拥有或需要哪些提供商的账户，可能是一场物流噩梦。云计算的一大优势是计算运营的管理责任转移给了云提供商。然而，随之而来的是一种诱惑，即忽视或忘记只有组织才能提供的身份管理需求。

如果让用户创建个人账户是一个糟糕的选择，那么让整个组织使用共享账户则是更糟的选择。让多个用户共享一个密码会大大增加该密码被盗的几率。更糟的是，在用户不当行为的情况下，无法辨别谁用哪些数据做了什么。最糟的是，每当用户离开组织或更换角色时，都必须更改密码，因为这是防止前授权用户继续访问账户的唯一方法。

这些问题的解决方案是一个称为**联合身份管理**（FIdM，我们在[第 2 章](#ch02.html#ch02)中介绍过）的概念。FIdM“使身份信息能够在多个实体之间以及跨信任域进行开发和共享……为已识别的个人、身份提供商和信赖方提供‘**单点登录**’的便利和效率。”[[GAR14](#bib01.html#bib_216)] 简而言之，FIdM 允许一个组织或系统向另一个组织或系统证明用户的身份和权限。

有了 FIdM，一个系统维护用户的身份信息，其他系统在需要时查询该系统。例如，假设你在一家将其电子邮件系统外包给云提供商的公司工作。要访问你的电子邮件，你访问云提供商的网站并输入你的公司登录凭证——很可能就是你用于登录工作电脑的相同凭证。网站不再自行检查你的凭证，而是参考你公司的身份管理服务器来验证你的身份。因为你公司的身份管理服务器知道你的身份，它可以确认你的凭证并向云提供商发送一条授权你访问电子邮件的消息。[图 8-4](#ch08.html#ch08fig04) 描绘了此信息流，其中步骤 3 和 4 描绘了在传输登录凭证时绕过第三方提供商的替代方案（从安全角度来看这是首选方案）。

**图 8-4** FIdM 概念视图

FIdM 有效地解决了我们上面概述的所有云身份挑战。借助 FIdM 解决方案，用户可以使用访问公司系统的相同凭证访问公司的所有云服务提供商。因为云客户控制身份验证过程，他们可以指定适合他们的身份验证要求：例如最小密码长度、多因素认证或生物识别。FIdM 还极大地简化了治理问题，确保只有一个系统拥有创建、修改或删除用户账户的权限：客户的身份管理系统（通常是 LDAP 或 Microsoft Active Directory）。

虽然我们是在使用云服务的背景下介绍 FIdM，但我们在此介绍的联合技术并不局限于云场景。它们对于跨网络飞地或单个企业内部的安全上下文，或企业群组之间管理身份同样有价值。如果用户身份在一个环境中被提供、维护和认证，但需要这些身份的服务在单独的环境中运行，那么 FIdM 可能是个好主意。
