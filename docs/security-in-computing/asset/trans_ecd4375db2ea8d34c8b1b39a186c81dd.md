### 数据丢失防护

数据丢失防护（Data Loss Prevention，简称 DLP）正如[第 6 章](#ch06.html#ch06)所述，在云存储环境中可能难以实施。DLP 产品保护公司免受敏感数据丢失的部分方式，是提供设备在网络边界监控并阻断流量。当公司将数据和服务迁移至公有云时，用户可以从公司网络外部访问它们，从而完全绕过这些网络边界。

在迁移至公有云时保持 DLP 能力的一种方法，是强制用户通过公司网络进行访问。许多云服务为客户公司提供按源 IP 地址限制用户的选项。如果用户尝试在没有与公司网络建立开放 VPN 连接的情况下（即没有公司拥有的源 IP 地址）从家中或其他地方登录云服务，登录将失败。某些 VPN 提供主机扫描功能，用于检查尝试登录的主机。这些主机扫描器可配置为确保近期运行过恶意软件扫描、存在公司证书以及正在运行特定应用程序。对于依赖软件代理进行 DLP 的公司而言，此功能非常有用，因为主机扫描器可以阻止未启用 DLP 代理的系统登录。

迁移至云后保持 DLP 能力的另一种解决方案，是在云环境的网络边界部署 DLP 功能。此解决方案通常仅适用于 IaaS 部署，因为它们通常足够灵活，允许客户将 DLP 作为 VM 部署，并配置其 VM 网络，使所有出站流量必须路由通过该 DLP VM。

### 云应用安全

在云环境中编写安全软件与在任何其他环境中并无不同，因此[第 3 章](#ch03.html#ch03)是该主题的绝佳切入点。事实上，在许多方面，编程是安全社区在云领域最具经验的方面。Web 托管——一种允许客户在服务提供商的硬件和软件栈之上构建自定义 Web 应用程序的服务——早在 1990 年代初就成为了第一个 PaaS，远在“云”一词被创造出来之前。自那以后，开发人员就不得不学会在共享环境中保护应用程序。

为云部署编写应用程序时，你需要做出的最大调整是了解威胁是如何变化的。不幸的是，并没有一份你需要担心的具体威胁的综合清单，因为这些威胁在很大程度上取决于你的云环境的具体实现：云计算平台、配置、库等。然而，由于云计算范式，有几个普遍的威胁会随之出现：

* **针对共享资源的攻击**。即使你没有与恶意用户共享云环境，你也几乎肯定会与存在漏洞的应用程序共享。例如，如果多个应用程序共享一个数据库即服务，其中一个应用中的 SQL 注入漏洞可能会影响所有应用 [[SUL13](#bib01.html#bib_598)]。一项 2012 年的研究发现，在现代硬件和现代管理程序上运行的恶意 VM，在给定几小时的情况下，能够利用侧信道攻击推断出部署在同一系统上的受害者 VM 所使用的私钥 [[ZHA12](#bib01.html#bib_669)]。**加密侧信道攻击**是一种复杂的数学运算，攻击者通过仔细观察加密操作的副作用（如处理器产生的热量、处理器响应时间等）来推断受害者的加密密钥。

* **不安全的 API**。使用云服务和第三方网站暴露的 API 是构建云应用程序的必要部分。不幸的是，一项针对 2008 年 1 月至 2012 年 2 月云安全事件的调查发现，29% 的云服务中断是由“不安全的接口和 API”引起的 [[KO13](#bib01.html#bib_338)]。一项 2012 年的研究发现，包括亚马逊和 PayPal 在内的多家主要供应商面向云的 API 中的 SSL 证书验证“完全损坏”，导致通往这些 API 的 SSL 连接容易受到中间人攻击 [[GEO12](#bib01.html#bib_222)]。

不幸的是，除非对云提供商和合作伙伴进行广泛的安全测试，否则你几乎无法保护自己免受这些问题的影响。最好的准备方式是认识到：你依赖的产品迟早会出现重大漏洞，并确保到那时你已做好响应准备。这可能意味着能够快速打补丁；准备好切换云提供商；或拥有依赖不同产品集和云服务的冗余系统。

### 日志记录与事件响应

在公有云中检测和响应发生的安全事件带来了有趣的挑战。SOC 分析师识别和调查安全事件的主要方式是利用系统日志数据。在普通企业中，安全相关的日志来自多个来源，包括操作系统、恶意软件扫描器、漏洞扫描器、IDS、防火墙和业务应用程序。部分日志数据包含潜在恶意行为的警报，而其他日志数据则帮助分析师围绕潜在安全事件建立上下文感知——谁登录了、运行了什么应用程序以及其他此类有用信息。

如果安全事件特别值得关注——可能是因为后果严重或手法新颖——受害者可能希望通过计算机取证进行更深入的调查。取证调查的主要目标是尽可能可靠地保留尽可能多的相关证据，并以法庭信服的方式进行。这可能意味着在关闭系统电源或将其从网络中移除之前，对内存和硬盘进行快照；妥善保存物理驱动器；并保护缺乏存储空间的设备上的日志文件。

你现在可能已经猜到了，当你在公有云中遭受攻击时，执行上述所有操作的问题在于：你可能无法访问大量必要的数据和功能。在这些场景中，SaaS 产品通常帮助最小，因为它们通常仅向用户提供有限的应用层日志，且无法洞察或控制底层系统和网络。PaaS 稍好一些，因为客户可以完全控制其应用程序生成的日志，有时还可以配置运行时环境日志记录。然而，与 SaaS 一样，PaaS 客户无法控制底层系统 [[BIR11](#bib01.html#bib_72)]。IaaS 服务为日志记录和取证提供了最灵活的选项，因为它们赋予客户对操作系统、应用程序和虚拟网络的完全控制权。客户可以在这些控制范围内启用任何所需的日志记录，并可以使用 VM 快照——在某一时刻保存和恢复 VM 的确切状态的能力——来实现强大的取证分析和证据保全能力。然而，即使使用 IaaS，许多日志对客户而言也可能不可用，包括由管理程序、底层物理系统和提供商网络生成的日志。
