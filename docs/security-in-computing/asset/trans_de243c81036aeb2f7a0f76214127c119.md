
The three aspects of computer security—integrity, confidentiality, and availability—are closely related to database management systems (DBMS). As we have described, integrity applies to each separate element of a database and to the database as a whole. Integrity is also a property of database structure (elements in one table correspond one-to-one with elements in another) and database relationship (records with the same unique identifier, called a key, are related). Thus, integrity is a primary concern in the design of database management systems. We look more closely at integrity issues in the next section.

Confidentiality is likewise a key issue for databases because databases are often used to implement controlled sharing of sensitive data. Access to data can be direct (you request a record and the database provides it) or indirect (you request some records and infer or intuit other data from those results). Controlling direct access uses the access control techniques we described in [Chapter 2](#ch02.html#ch02) and [Chapter 5](#ch05.html#ch05). However, indirect access is more difficult to control, and we examine it in more depth later in this chapter.

Finally, availability is important because it is the basis for the motivation to develop shared access to databases. However, availability conflicts with confidentiality. The last few sections of this chapter explore availability issues in environments where confidentiality is also important.

## 7.3 Reliability and Integrity

Databases integrate data from multiple sources, and users expect the DBMS to provide access to data in a reliable way. When software engineers say that software has **reliability**, they mean that the software runs for very long periods of time without failure. Users certainly expect a DBMS to be reliable because data is usually critical to business or organizational needs. In addition, users entrust data to a DBMS and reasonably expect it to protect the data from loss or corruption. Concern for reliability and integrity is a general security issue, but it is more pronounced in databases.

DBMSs protect against loss or corruption in several ways, which we study in this section. However, the controls we consider are not absolute: no control can prevent an authorized user from inadvertently entering an acceptable but incorrect value.

Concern for database reliability and integrity can be viewed from three dimensions:

*   **Database integrity:** Concern that the database as a whole is protected against damage, such as a disk drive failure or corruption of the master database index. These problems are addressed by operating system integrity controls and recovery procedures.
*   **Element integrity:** Concern that the value of a specific data element is written or changed only by authorized users. Proper access controls protect the database against corruption by unauthorized users.
*   **Element accuracy:** Concern that only correct values are written into a database element. Checks on element values help prevent the insertion of improper values. In addition, constraints can detect incorrect values.

### Operating System Protection Features

In [Chapter 5](#ch05.html#ch05), we discussed the protection that an operating system provides for its users. A responsible system administrator backs up database files regularly, along with other user files. During normal execution, the operating system's standard access control mechanisms protect files from outside access. Finally, the operating system performs certain integrity checks on all data as part of normal I/O device read and write operations. These controls provide basic security for a database, but the database administrator must augment them.

### Two-Phase Update

A serious problem facing a database manager is the failure of the computing system during a data modification. If the data item to be modified is a long field or a record consisting of multiple attributes, only part of the new data may have been written to permanent storage. Thus, the database file will contain incorrect, partially updated data. Even if such errors are easy to detect (and they are not), a more subtle problem arises when multiple fields are updated and no single field shows an obvious error. The solution to this problem, first proposed by Lampson and Sturgis ([LAM76](#bib01.html#bib_357)) and adopted by most DBMSs, is to use a **two-phase update**.

#### Update Technique

In the first phase, called the **intent phase**, the DBMS gathers the resources necessary to perform the update. It may gather data, create virtual records, open files, lock out other users, compute final results; in short, it does everything to prepare for the update but makes no changes to the database. The first phase can be repeated indefinitely because it takes no permanent action. If the system fails during execution of the first phase, no harm is done because all these steps can be restarted and repeated after system recovery processing.

The last event of the first phase is called the **commit**, which involves writing a **commit flag** to the database. The commit flag means the DBMS has passed the point of no return: after the commit, the DBMS begins to make permanent changes.

The second phase makes the permanent changes. In the second phase, the precommit actions cannot be repeated, but the update activities of the second phase can be repeated as many times as necessary. If the system fails during the second phase, the database may contain incomplete data, but the system can repair these data by executing all the activities of the second phase. After the second phase is complete, the database is once again in a consistent state.

#### Two-Phase Update Example

Consider a database containing a company's inventory of office supplies. The company's central storeroom stocks paper, pens, paper clips, and so on, which departments requisition as needed. The company buys in bulk to get the best price. Each department has a budget for office supplies, so there is a chargeback mechanism to recover the cost of supplies from the departments. In addition, the central storeroom monitors inventory levels so that new supplies can be ordered when stocks run low.

Suppose the process begins when the Accounting department requests 50 boxes of paper clips. Suppose there are 107 boxes in stock, and a new order is placed if the stock level falls below 100 boxes. The storeroom receives the requisition and follows these steps:

**1.** The storeroom checks the database to verify that 50 boxes of paper clips are in stock. If not, the requisition is denied and the transaction ends.

**2.** If paper clips are in stock, the storeroom deducts 50 from the inventory count in the database (107 – 50 = 57).

**3.** The storeroom deducts the cost of 50 boxes of paper clips from the Accounting department's supply budget in the database.

**4.** The storeroom checks its remaining stock level (57) to determine whether it is below the reorder point. Because it is, a notification to order more paper clips is generated, and the item is marked "on order" in the database.

**5.** A shipping order is prepared to send 50 boxes of paper clips to the Accounting department.

All five of these steps must be completed in the order listed for the database to be accurate and the transaction to be processed correctly.
