
这个表格的一个棘手特性是最后一列。该列中的条目是学位的集合。请措辞你的句子，使其每次只包含一个学位。将步骤 1 应用于第一行，会产生四个事实，可陈述如下。

1.  34. 姓名为“Adams JB”的**讲师** *出生于* 1946 年（CE）。
2.  35. 姓名为“Adams JB”的**讲师** *拥有* 年龄 42 岁。
3.  36. 姓名为“Adams JB”的**讲师** *持有* 代码为“BSc”的**学位**。
4.  37. 姓名为“Adams JB”的**讲师** *持有* 代码为“PhD”的**学位**。

此处，实体类型和参考模式为 `Lecturer (.Name)`、`Year (CE:)`、`Age (y:)` 和 `Degree (.Code)`。共有三种事实类型：讲师 *出生于* 年份；讲师 *拥有* 年龄；以及讲师 *持有* 学位。实体类型 Year 和 Age 在语义上是不同的。Year 涉及一个时间起点，而 Age 仅仅是一段时间长度（在本例中，以年为单位衡量）。

示例的口语化涉及解释，因此示例的类型对我们或协助我们执行步骤 1 的领域专家来说必须是 *熟悉* 的。由于领域专家通常缺乏建模方面的技术专长，我们不应指望他们独自完成步骤 1 的所有工作。只要他们能用自己的术语正确地口语化表达信息即可。这是 **步骤 1a**：*口语化表达信息*（或许是非正式的）。

作为建模者，我们经常需要通过确保事实是基本的且对象被良好标识来完善他们的口语化表达。这是 **步骤 1b**：*将信息口语化为基本事实*。例如，领域专家可能通过以下方式执行步骤 1a，口语化表达该报告首行的信息：

*   辅导组 A 在周一下午 3 点于 CS-718 室上课。
*   学号 302156 的学生属于 A 组，名为“Bloggs FB”。

我们随后可能通过将这些非正式句子完善为以下四个基本句子来执行步骤 1b：

1.  38. 代码为“A”的**辅导组** *在* 代码为“Mon 3 p.m.”的**时间** *上课*。
2.  39. 代码为“A”的**辅导组** *在* 房间号为“CS-718”的**教室** *上课*。
3.  40. 学号为 302156 的**学生** *属于* 代码为“A”的**辅导组**。
4.  41. 学号为 302156 的**学生** *拥有* 学生姓名“Bloggs FB”。

此示例中的许多特性都依赖于解释。例如，我们假设 `StudentNr` 和 `StudentName` 指代学生，并且同一行上的学生编号和学生姓名指代同一个学生。我们还将关联填充为“在……上课”、“在……上课”、“属于”和“拥有”。报告本身并未告诉我们这些。我们利用对该情境的背景知识做出此类假设。还做出了关于实体类型和参考方案的决定，例如，我们将 Time 视为由日-时代码标识的实体类型，而不是引入 Day 和 Hour 实体类型。类似的评论也适用于 Room 和 StudentName。

选择 `StudentNr` 而非 `StudentName` 来标识 Student。报告在此有所帮助，因为 `StudentNr` 出现在最前面（最左侧），而“Bloggs FB”出现了两次且对应不同的学生编号，这表明可能有多个学生同名。然而，我们仍在做假设（例如，学生只有一个学号，或者学生只属于一个小组）。

另一个假设是每个辅导组每周只上一次课。我们需要这一点来证明对时间和教室使用单独的事实是合理的（而不是将其口语化为“辅导组在时间于教室上课”）。报告中 A 组未重复出现这一事实有助于此决策，但这仍假设样本在这一方面具有代表性。因为初始步骤总是涉及解释，如果我们不熟悉该示例，应通过向领域专家提问来消除疑虑，并使用他们熟悉的示例。

虽然我们作为建模者可能擅长在形式化的类型层面上表达，但并非所有领域专家都能做到这一点。通过使用领域专家熟悉的示例进行工作，我们可以利用他们对 UoD（关注域）的隐性理解，而无需强迫他们进行抽象和表达，从而可能错误地表达我们所寻求的相关结构。

句子 (41) 表达了一个实体（一个学生）与一个值（一个姓名）之间的关系。在口语化事实时，**值类型** 紧跟在值之前陈述（例如，StudentName “Bloggs FB”）。与实体术语不同，值术语没有参考方案。
