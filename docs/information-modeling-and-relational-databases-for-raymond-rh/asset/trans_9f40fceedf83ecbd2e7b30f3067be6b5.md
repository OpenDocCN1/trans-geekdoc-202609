
最初的三个范式是由 E. F. “Ted” Codd 提出的，他奠定了数据的关系模型基础。其他范式后来被引入以适应更多情况。这些改进归功于包括 Codd、R. Boyce、R. Fagin、A. Aho、C. Beeri 和 J. Ullman 在内的多位研究人员的工作。也提出过其他范式（例如水平范式和嵌套范式），但此处不作讨论。

当且仅当表的属性是单值且固定时，该表才是规范化的，或者说处于**第一范式**（**1NF**）。换句话说，`1NF` 表具有固定数量的列，并且行列交叉位置的每个条目都是一个简单值（可能为 null）。本书迄今为止所见的几乎每个表都处于 `1NF`。

如果表具有多值属性（例如，条目为集合，如集合、数组甚至关系），或者允许不同行具有不同数量的属性，则该表可能违反 `1NF`（因此成为 `NF²` 表）。

作为第一种违反情况的示例，请考虑[表 14.7](#Ch014_681-771_B9780443237904000189.xhtml#t0040)。虽然该 Student 表的前两列仅存储原子值，但 Car 列存储值的集合，而 Result 列存储 (course, rating) 对的集合。

要在关系数据库中对其建模，我们需要将结构展平为三个表：`Student`( studentNr, gender )；`Drives`( studentNr, car )；以及 `Scores`( studentNr, course, rating )。因此，`1NF` 关系通常被称为*扁平关系*。

然而，可以通过使用不在第一范式中的关系直接对该结构建模。例如，我们可以使用以下*嵌套关系*模式：`Student`( studentNr, gender, `Car`( regNr ), `Result`( course, rating ) )。

此处，第三列中的条目本身就是一个关系（此处为汽车注册号的集合）。同样，Result 列中的每个条目也是一个关系（具有 course 和 rating 属性）。因为这种方法的底层逻辑数据模型允许关系嵌套在关系内部，所以称为*嵌套关系模型*。

因为嵌套表不在 `1NF` 中，所以它不是关系表（即不符合数据的关系模型）。尽管纯嵌套关系系统尚未产生任何显著的商业影响，但许多主要的关系 DBMS 已演变为支持 `NF²` 表的对象关系系统，这将在下一节讨论。虽然不在 `1NF` 的表可能处于其他奇特的“范式”中，但通常习惯将它们称为“非规范化”。

[表 14.7](#Ch014_681-771_B9780443237904000189.xhtml#t0040) 中像 Car 这样的集合值字段有时称为“重复属性”，而像 Result 这样存储分组值集合的字段有时称为“重复组”。通过允许只有一个值的退化组，该术语可用于包含重复属性的概念。使用这种略显误导的术语，我们可以说 `1NF` 表没有重复组。

非规范化表的另一个例子是 Pascal 和 Modula 等语言中使用的“变体记录类型”。此处，同一记录类型中的不同“行”可能包含不同的字段。例如，[图 14.57](#Ch014_681-771_B9780443237904000189.xhtml#f0290) 中的 figure 记录类型旨在存储有关彩色几何图形的详细信息。其中包含了示例数据填充。记录类型包含 figureId、color 和 shape（圆形、菱形、三角形）的公共字段。

![Fig. 14.57 A variant record type, with a sample population.](images/B9780443237904000189/f14-57-9780443237904.jpg)

根据 shape 的不同，记录类型具有不同的其余字段（圆形的 radius；菱形的 side 和 angle；三角形的三条 side）。这提供了一种实现受限子类型概念的方法，而无需使用现代面向对象编程语言中常见的子类。

表的*键*是由显式唯一性约束跨越的一组一个或多个属性。此处，“显式”排除了由其内部较短的 UC 隐含的任何 UC；因此，键由“最小” UC 跨越。对于给定的关系，当且仅当属性属于该关系的某个键（主键或备选键）时，它才是*键属性*。*非键*属性既不是键，也不是复合键的一部分。

例如，考虑关系模式 `City`( cityNr, cityname, statecode, population, \[mayor\] )。此处，cityNr 是主键，(cityname, statecode) 是备选键。因此 cityNr、cityname 和 statecode 是键属性。尽管 mayor 属性是唯一的，但它不是键，因为它是可选的。因为它们不属于键，population 和 mayor 是非键属性。

虽然范式及相关依赖的定义通常以关系（固定元组集合）的术语给出，但我们应该以*关系模式*的术语来定义它们，因为我们希望表结构对于每种可能的填充都表现出所需的质量（这要求修订某些高级范式的定义）。考虑到这一点，我们按如下方式定义关系模式上的 FD。给定关系模式的属性 `X` 和 `Y`，`X` 函数决定 `Y`（`X` → `Y`）当且仅当，*给定表模式的任何可能填充*，对于 `X` 的每个值，`Y` 只有一个值。属性 `X` 和 `Y` 可以是复合的。判断某填充是否为业务领域所允许，需要领域专家的理解（这是一个非形式语义问题，而非语法问题）。

当且仅当表模式处于 `1NF` 且每个非键属性都（函数）依赖于键的整体（而不仅仅是其一部分）时，该表模式处于**第二范式**（**2NF**）。如果表已规范化，则它至少处于 `1NF`。例如，[图 14.58](#Ch014_681-771_B9780443237904000189.xhtml#f0295)(a) 中的表处于 `2NF`，因为 gender 和 birthdate 都是 student number 的函数。此处，从 studentNr 出发的 FD 以箭头表示。
