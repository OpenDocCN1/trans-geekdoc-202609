
# SQL/JSON Construction Functions

It's possible to include data from different levels of the JSON text by using "nested" columns. In our data, the names of any stars of a movie are at a level below the title of the movie. The following example shows how these levels can be combined.

```
select jt.* from videos as v, json_table(v.movies, '$.movies[*]' columns(
    Title varchar(20) path '$.title',
    Released int path '$.released',
    nested path '$.stars[*]' columns (
        Starring varchar(20) path '$.name'
    )
)) as jt order by Released
```

Again, this produces a standard SQL result table.

![u16-07-9780443237904](images/B9780443237904000207/u16-07-9780443237904.jpg)

Tables produced in this way can participate in all the usual table operations such as join operations with other (non-JSON) tables in the database. A possible use of `json_table` is to create views that allow the JSON origins of the data to be hidden from SQL developers.

There is one more SQL/JSON retrieval function, and that is `json_serialize`. This takes a JSON value as input and returns JSON text in one of the SQL character data types (typically `varchar`). This is useful if the "raw" JSON value is in a binary form, which is not intended for human readability. Some implementations may also include a "pretty" option to produce nicely formatted text.

The operations we have considered so far assume that we have some JSON value stored in the database and want to extract some or all of it, in various ways. SQL/JSON also defines construction functions that build SQL/JSON items from non-SQL/JSON values.

The most obvious of these is `json_parse`, which takes a text input and converts it to a JSON sequence. This is essentially the reverse operation to `json_serialize`. If the input text is not well-formed JSON, an error will be returned. The `json_scalar` function is simple: it creates a JSON value from a non-JSON value. For example, an SQL value of data type `int` would be converted to a JSON number.

More interesting are the functions to construct JSON structural elements, objects and arrays. The constructors can be nested, so we can build JSON values of arbitrary complexity. These functions are summarized in [Table 16.8](#Ch016_831-873_B9780443237904000207.xhtml#t0045).

Creating objects is straightforward. The following query defines an object structure with members for employee number and office, which is then applied to each row of the Agent table.

```
select json_object('empNr' value nr, 'office' value office) from Agent
```

**Result:**

```
{"empNr": 101, "office": "Boston"}
{"empNr": 232, "office": "Portland"}
{"empNr": 397, "office": "Durham"}
{"empNr": 468, "office": null}
```

Some implementations of `json_object` replace the `value` keyword with a comma. An ugly feature of the result is the `null` in the last object. A more natural JSON representation would omit this member entirely. SQL/JSON defines an optional `absent on null` clause to effect this, but it's not supported in all implementations. We may be able to find a workaround by providing something more meaningful based on domain knowledge. For instance, if we know that the reason for Dave Dunk having no office recorded is that he is mobile, so his office varies, we can replace the `null`.

```
select json_object(
    'empNr', nr,
    'office', case when office is not null then office else 'varies' end
) from Agent
```

**Result:**

```
{"empNr": 101, "office": "Boston"}
{"empNr": 232, "office": "Portland"}
{"empNr": 397, "office": "Durham"}
{"empNr": 468, "office": "varies"}
```

It's obvious how this query could be extended to include separate members for `givenName` and `familyName`, but an alternative would be to create a `name` member containing objects for each of the name components. This can be done by nesting additional `json_object` constructors within the `name` member.

Phone information is a little more complex because the member is not single-valued. We'll assume that a list of numbers is required, each represented by an object. This can be produced by nesting object constructors inside an array constructor in the following way.

```
select json_array(
    json_object('type' value 'home', 'number' value homePhone),
    json_object('type' value 'work', 'number' value workPhone)
) from Agent
```

**Result:**

```
[{"type": "home", "number": "222-9876"}, {"type": "work", "number": "222-1234"}]
[{"type": "home", "number": null}, {"type": "work", "number": "555-6789"}]
[{"type": "home", "number": "777-6789"}, {"type": "work", "number": "777-4321"}]
[{"type": "home", "number": null}, {"type": "work", "number": null}]
```

To integrate this information, we can introduce a `phones` member into our earlier object, with the array construct above nested inside it. We have the same issue as before with `null`s. If the `absent on empty` clause is not available, we could create a more complex SQL query to remove the `null` members from the JSON result, but for our current purposes, we'll just accept the `null`s.

The functions not covered so far are the object aggregate and array aggregate constructors. We can illustrate these with the Project table. The `json_objectagg` function requires a key-value pair, as in the following example:

```
select empNr, json_objectagg(projName, rate)
from Project group by empNr
```

**Result:**

```
101     {"Grebe": 2, "Mallard": 1}
232     {"Grebe": 3, "Plover": 1, "Bittern": 2}
```

Here, the resulting object for each group has a member for each item in the group. This differs from `json_object`, which would give a separate object for each item.

Creating an aggregating array works similarly but requires only the identification of the value to be listed. This gives an array with an element for each item in the group.

```
select empNr, json_arrayagg(projName)
from Project group by empNr
```

**Result:**

```
101     ["Mallard", "Grebe"]
232     ["Grebe", "Plover", "Bittern"]
```

To meet our aim of a comprehensive Agent object, the `json_arrayagg` constructor looks the most appropriate. This can be integrated into the larger query by nesting it within a `projects` member of the main object structure.
