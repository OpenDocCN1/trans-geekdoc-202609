

# 语义代码与引用方案

语义代码常用于遗留系统中，但并未尝试将其语义作为单独的组件暴露出来。如果这些遗留系统必须保持当前形式，则可以构建一个单独的系统（例如数据仓库），以更好地支持对组件的查询。在将数据从遗留系统复制到新系统时，代码会被转换为单独的组件字段。

在概念模式中应暴露多少承载信息的名称背后的语义，取决于我们希望发出的查询。

## 暴露楼层语义

现在假设我们希望查询系统关于楼层的信息；例如，“楼栋 67 的第 3 层有多少个房间？”为了便于此操作，我们可以将引用方案扩展为三个组件以暴露楼层语义。建模此方案的一种方式如[图 5.26](#Ch005_159-209_B9780443237904000098.xhtml#f0135)(a)所示。这将之前的房间号（例如 `301`）分为 `FloorNr`（例如 `3`）和一个序列号（例如 `01`）。

![图 5.26 暴露房间三部分引用方案的两种方式。](images/B9780443237904000098/f05-26-9780443237904.jpg)

[图 5.26](#Ch005_159-209_B9780443237904000098.xhtml#B-f0135) 暴露房间三部分引用方案的两种方式。

如果我们想考虑楼层本身，而不仅仅是楼层号，最好将 `Floor` 建模为一个实体类型，如[图 5.26](#Ch005_159-209_B9780443237904000098.xhtml#f0135)(b)所示。在这里，`Floor` 在 `Room` 的复合引用方案中发挥作用，并且拥有自己的复合引用方案。

虽然不太方便，但可以使用派生函数来构建关于引用组件*单个实例*的查询，而无需实际存储该组件。例如，要列出楼栋 67 第 3 层的房间数量，我们可以使用以下 SQL 查询：

```
select count(*) from Room where roomNr like ‘67–3%.’
```

尽管这种方法可行，但我们仍建议暴露语义。如果不确定是否暴露某些语义，通常最好暴露出来。

如果您希望查询其实例的*组*，则应始终存储引用组件；例如，“*对于*楼栋 67 的*每个*楼层，有多少个房间？”使用[图 5.26](#Ch005_159-209_B9780443237904000098.xhtml#f0135)(b)的模式，这可以在 ORM 中通过选择从 `Room` 到 `Building` 的路径（即 Room 位于**一个** Floor **该** Floor 位于 Building）来表述，为 `Building` 添加条件“= 67”（隐式应用于 `BuildingNr`），然后请求 `Floor` 和 `count(Room)` **针对每个** `Floor`。

在关系层面，该查询可以使用 SQL 的 group-by 子句来表述；例如：

```
select floorNr, count(*) from Room where buildingNr = 67 group by floorNr
```

SQL 语言在[第 12 章](#Ch012_539-646_B9780443237904000268_1.xhtml)和[第 13 章](#Ch013_647-679_B9780443237904000049.xhtml)中有详细讨论。

## 引用方案指南

为实体类型选择引用方案是建模的一个重要方面。作为一条严格准则，*实体类型的首选标识方案必须将该类型的每个实体 1:1 映射到一个由一个或多个值组成的元组*（直接或间接）。因此，每个首选引用方案都提供了一个*单射*（强制性的 1:1 映射）。例如，在[图 5.26](#Ch005_159-209_B9780443237904000098.xhtml#f0135)中，每个楼栋直接映射到一个唯一的楼栋号，每个房间通过引用谓词（间接地）映射到一个唯一的三元组值（楼栋号、楼层号、序列号）。

在日常生活中，某些场合会使用较弱的标识方案。例如，有些人有识别性的绰号（例如，“大白鲨”指代高尔夫球手格雷格·诺曼）。然而，在典型应用中，并非每个人都有绰号，因此绰号不用于首选引用（它们不是强制性的）。

有时会使用 1:多 引用方案。例如，一种动植物类型可能有多个识别性的通用名称。例如，学名为 *dacelo gigas* 的鸟类物种，也可能通过以下任一通用名称来识别：“kookaburra”、“laughing jackass”、“great brown kingfisher”或“bushman’s clock”。作为一个植物学例子，“gorse”和“furze”指代同一种植物。

在[图 5.27](#Ch005_159-209_B9780443237904000098.xhtml#f0140)(a)中，通用名称被用作鸟类物种的首选标识符。这种选择由双唯一性约束杠标志。包含了一个示例种群来说明这种引用类型的 1:多 性质。您能发现该引用方案的问题吗？

![图 5.27 关联 (a) 不是 1:1，因此不应用于首选引用。](images/B9780443237904000098/f05-27-9780443237904.jpg)

[图 5.27](#Ch005_159-209_B9780443237904000098.xhtml#B-f0140) 关联 (a) 不是 1:1，因此*不*应用于首选引用。

该关联*绝不*能用于首选引用，因为它不是 1:1。想象一下，如果我们在数据库的一个部分用“kookaburra”来标识一种鸟类，在另一个部分用“laughing jackass”来标识，会出现什么问题。在缺乏学名等标准标识符的情况下，我们如何知道我们谈论的是同一种鸟类？

对于首选引用，我们必须选择一个强制性的 1:1 方案。这种方案可能已经存在，例如[图 5.27](#Ch005_159-209_B9780443237904000098.xhtml#f0140)(b)中的 `ScientificName`。如果不存在，我们在领域专家的帮助下创建一个。这可能部分是人工的（例如标准通用名称）或完全人工的（例如 `BirdkindNr`）。无论我们选择什么，都需要让信息系统的用户达成一致。
