
# Nesting

Now, let’s consider *nesting*. In [Fig. 4.23](#Ch004_111-158_B9780443237904000232.xhtml#f0120), the subject ratings example was set out in flattened form. Suppose instead we use a nested approach, as shown in [Fig. 4.30](#Ch004_111-158_B9780443237904000232.xhtml#f0155). Here each (Person, Subject) enrollment is treated as an object that may result in a rating. For example, the enrollment of Adams in CS112 results in a 7.

![Fig. 4.30 The enrollment association is objectified as a nested object type.](images/B9780443237904000232/f04-30-9780443237904.jpg)

[Fig. 4.30](#Ch004_111-158_B9780443237904000232.xhtml#B-f0155) The enrollment association is objectified as a nested object type.

[Fig. 4.23](#Ch004_111-158_B9780443237904000232.xhtml#f0120) is not actually equivalent to [Fig. 4.30](#Ch004_111-158_B9780443237904000232.xhtml#f0155) unless a further constraint is added that a rating must be known for each enrollment. Such mandatory role constraints are discussed in the next chapter.

The `Enrollment` entity type in [Fig. 4.30](#Ch004_111-158_B9780443237904000232.xhtml#f0155) is called an objectified association, an objectified relationship type, an objectified predicate, a nested entity type, or a nested object type. Most objectified associations are spanned by a `UC` (as in [Fig. 4.30](#Ch004_111-158_B9780443237904000232.xhtml#f0155)). This spanning `UC` indicates that each person may enroll in many subjects, and the same subject may be enrolled in by many people. The simple `UC` on the binary predicate indicates that each (Person, Subject) enrollment resulted in at most one rating.

[Section 10.5](#Ch010_401-479_B9780443237904000244.xhtml#s0050) includes a discussion of objectification of associations with nonspanning `UCs` (e.g., 1:1 associations and *n*:1 associations). While currently allowed in ORM, such cases can violate elementarity, and are better modeled in other ways.

# 4.4 External Uniqueness Constraints

The `UCs` discussed so far are *internal* (intrapredicate) `UCs`, as each applies to one or more roles in a single predicate. **External** (interpredicate) **uniqueness constraints** *apply to roles from different predicates*. To understand these constraints, the *conceptual join* operation is first discussed.

Consider the schema and sample population in [Fig. 4.31](#Ch004_111-158_B9780443237904000232.xhtml#f0160). The left-most fact table indicates that employee 15 drives cars with registration numbers `PKJ123` and `ABC000`. The right-most fact table indicates that car `PKJ123` is imported from Italy. The ternary fact table indicates that employee 15 drives the car `PKJ123` imported from Italy. The asterisk after the mixfix predicate reading indicates that the ternary fact type is *derived*. The derivation rule is preceded by an asterisk.

![Fig. 4.31 A compound ternary derived from a conceptual inner join of the binaries.](images/B9780443237904000232/f04-31-9780443237904.jpg)

[Fig. 4.31](#Ch004_111-158_B9780443237904000232.xhtml#B-f0160) A compound ternary derived from a conceptual inner join of the binaries.

The instance diagram in [Fig. 4.32](#Ch004_111-158_B9780443237904000232.xhtml#f0165) may help clarify things. The binary facts appear as lines connecting two dots. The ternary fact corresponds to the continuous path from `Employee` to `Country`. Starting at the `Car` type, this path may also be verbalized as the conjunction Car is driven by Employee **and** was imported from Country.

![Fig. 4.32 An instance diagram for the model shown in Fig. 4.31.](images/B9780443237904000232/f04-32-9780443237904.jpg)

[Fig. 4.32](#Ch004_111-158_B9780443237904000232.xhtml#B-f0165) An instance diagram for the model shown in [Fig. 4.31](#Ch004_111-158_B9780443237904000232.xhtml#f0160).

The derivation rule shows how the ternary is derived by combining the binaries, with `Car` as the connecting or join object type. The defining expression “Employee drives **some** Car **that** was imported from Country” is a formal verbalization of the conceptual path from `Employee`, through the drives predicate, `Car` type, and import predicate, to `Country`. The keyword “**that**” declares that the driven car must be *the same* as the imported car. In other words, if an employee drives a car, we must use the very same car to continue the path to `Country`.

A fact type resulting from a join is a *compound fact type*, not an elementary fact type because it is essentially the conjunction of at least two simpler fact types. For this reason, *join fact types are normally excluded from ORM schema diagrams*. If included for discussion purposes, they may be *shaded,* as in [Fig. 4.31](#Ch004_111-158_B9780443237904000232.xhtml#f0160), to indicate that they are just views. Unlike elementary derived fact types, their compound nature can lead to redundancy unless each join role is covered by a simple `UC`.

For example, if we add the row `(16, PKJ123)` to the drives table in [Fig. 4.31](#Ch004_111-158_B9780443237904000232.xhtml#f0160), then row `(16, PKJ123, IT)` is added to the ternary and is now contained twice in the ternary. Although join fact types are never used as asserted fact types, join paths are often involved in constraints and queries, as discussed later.

In an ORM schema, to navigate from one predicate to another, we must pass through an object type, performing a *conceptual join* (or *object join*) on that object type. By default, the join condition is that the object instance remains the same as we pass through. This is called a *conceptual inner join*. This is similar to a relational natural inner join (see later chapter), except that conceptual joins require the conceptual objects to be the same, instead of matching attribute names and values. ORM object types are conceptual domains, not attributes. Conceptual joins still apply if we declare different role names (cf. attribute names) for the join roles.

In terms of the fact tables, the column value of the role entering the join object type must equal the column value of the role that exits the object type. [Fig. 4.33](#Ch004_111-158_B9780443237904000232.xhtml#f0170) depicts two predicates, *R* and *S*, sharing a common object type, *B*. From a fact table perspective, the conceptual inner join of *R* and *S* is obtained by pairing rows of *R* with rows of *S* where the *B* column values match, and arranging for the final *B* column to appear just once in the result.

![Fig. 4.33 Joining on B requires the values in the two B columns to match.](images/B9780443237904000232/f04-33-9780443237904.jpg)

[Fig. 4.33](#Ch004_111-158_B9780443237904000232.xhtml#B-f0170) Joining on *B* requires the values in the two *B* columns to match.

The dotted lines show how the rows are paired together. For example, row `(a1, b1)` is paired with rows `(b1, c1)` and `(b1, c3)` to give rows `(a1, b1, c1)` and rows `(a1, b1, c3)`. [Fig. 4.34](#Ch004_111-158_B9780443237904000232.xhtml#f0175) shows the result of this join operation. The final *B* column is the intersection of the original *B* columns. The natural inner join of any tables *R* and *S* is denoted by “*R* ⋈ *S*” or “*R* natural join *S*”. The “inner” is often omitted and assumed by default.

![Fig. 4.34 Table resulting from the natural inner join of the tables in Fig. 4.33.](images/B9780443237904000232/f04-34-9780443237904.jpg)
