
如果 *m:n* 关系是环关联，则可以在迁移外键的名称前加上角色名以区分它们。例如，在 [图 8.40](#Ch008_309-346_B9780443237904000177.xhtml#f0205)(a) 中，角色名“subPartNr”和“superPartNr”被加在“partNr”前面，以消除 Containment 主键属性的歧义。

![图 8.40 角色名可用于 (a) IDEF1X 和 (b) ORM。](images/B9780443237904000177/f08-40-9780443237904.jpg)

[图 8.40](#Ch008_309-346_B9780443237904000177.xhtml#B-f0205) 角色名可用于 (a) IDEF1X 和 (b) ORM。

虽然 IDEF1X 标准在角色名后使用点号，但某些 CASE 工具不支持这种点号表示法。不过，仅使用角色名（例如，用“subPartNr”代替“subPartNr.partNr”）即可轻松实现区分，无需点号。无论哪种情况，角色名都应显示为名词短语，即使不附加被引用主键的名称也能识别该属性。在 ORM 中，对这种情况建模更自然的方式是将包含关联对象化，如 [图 8.40](#Ch008_309-346_B9780443237904000177.xhtml#f0205)(b) 所示。

在 IDEF1X 中，实体类型可分类为一个或多个互斥的*类别*（子类型）簇。超类型称为*泛型*实体（类型）。每个子类型继承其超类型的主键，因此是标识符依赖的。子类型联系称为“*分类关系*”。

与 ORM 子类型相比，这种子类型版本受限得多。ORM 子类型允许“簇”内有重叠类型，以及上下文依赖引用。实际上，IDEF1X 的子类型方法将实体类型视为表，“分类关系”仅仅是外键引用。相比之下，ORM 子类型纯粹是概念性的，在实现时可选择不同的映射策略（参见 [第 11 章](#Ch011_481-537_B9780443237904000141.xhtml)）。

然而，IDEF1X 的子类型方法有两个方面表达的不仅仅是简单的外键引用。它们是完整性声明和判别器声明。子类型联系显示为一条线，在超类型端有一个带下划线的圆圈。*单下划线*表示该簇是*不完整*的（即，超类型不仅仅是其子类型的并集）。这意味着超类型的实例可能包含不属于其任何子类型的实例。

例如，在 [图 8.41](#Ch008_309-346_B9780443237904000177.xhtml#f0210)(a) 中，子类型 TallPerson 和 ShortPerson 互斥，但不详尽。一个人可能是中等身高，而不被归类为高或矮。与 IDEF1X 相反，ORM 常使用派生子类型，必须根据其超类型所扮演的角色来定义。[图 8.41](#Ch008_309-346_B9780443237904000177.xhtml#f0210)(b) 显示了在 ORM 中建模这种情况的一种方式。

![图 8.41 (a) IDEF1X 和 (b) ORM 中的不完整且互斥的子类型簇。](images/B9780443237904000177/f08-41-9780443237904.jpg)

[图 8.41](#Ch008_309-346_B9780443237904000177.xhtml#B-f0210) (a) IDEF1X 和 (b) ORM 中的不完整且互斥的子类型簇。

这里，一个人的身高用于确定他或她是否属于 TallPerson 或 ShortPerson。子类型定义和 Height 上缺乏值约束表明这些子类型是互斥但不详尽的。这也可以通过显式的隐含排除约束来描述。作为使用身高的替代方案，可以将可选且互斥的一元角色“是高个子”和“是矮个子”附加到 Person，并提供显而易见的定义。

在 IDEF1X 中，超类型端的*双下划线*表示该簇是*完整*的。这意味着超类型是其子类型的并集。由于 IDEF1X 簇的成员也是互斥的，这意味着我们有一个分区。例如，在 [图 8.42](#Ch008_309-346_B9780443237904000177.xhtml#f0215)(a) 中，Person 被分区为 MalePerson 和 FemalePerson。

![图 8.42 (a) IDEF1X 和 (b) ORM 中的完整、互斥子类型簇。](images/B9780443237904000177/f08-42-9780443237904.jpg)

[图 8.42](#Ch008_309-346_B9780443237904000177.xhtml#B-f0215) (a) IDEF1X 和 (b) ORM 中的完整、互斥子类型簇。

超类型的一个强制属性可用作*判别器*，并写在圆圈旁边以指示子类型划分的依据。例如，在 [图 8.42](#Ch008_309-346_B9780443237904000177.xhtml#f0215)(a) 中，gender 被用作判别器将 Person 分类为 MalePerson 和 FemalePerson。相应的 ORM 模式如 [图 8.42](#Ch008_309-346_B9780443237904000177.xhtml#f0215)(b) 所示。此处显式显示的分区约束由子类型定义和其他约束隐含。

好了，这基本涵盖了 IDEF1X 表示法。虽然它是一种广泛使用的标准，特别是在国防工业中，但我们发现它不如 Barker 或 IE 表示法适合概念建模。要在 IDEF1X 中捕获任何细节甚至基本约束，必须将模型解析为本质上是关系模型的东西。此外，IDEF1X 的概念集及其表示法不必要地复杂且难记。对于概念分析和验证，它还受制于基于属性方法的弱点。

尽管存在这些缺点，经验丰富的建模者仍可有效使用 IDEF1X，他们通常将连接关系与迁移而来的概念关系联系起来。然而，即使对于这类经验丰富的建模者，在 IDEF1X 中建模的最佳方式也是先做一个 ORM 模型，然后将其映射到 IDEF1X，将任何额外的 ORM 约束表示为补充文本或实现代码。一些 ORM 建模工具可以自动执行此映射。

## 8.5 从 ORM 映射到 ER

完全属性化的 IDEF1X 模式本质上是用不同表示法显示的关系模式。因此，Microsoft 的 ORM 源模型解决方案将 IDEF1X 视为仅仅是一种不同的关系风格。如果您使用该工具，可以通过自动生成关系模式、将绘图风格设置为 IDEF1X，然后将任何额外的 ORM 规则记为文本注释，从 ORM 模式生成 IDEF1X 模式。

如果您需要手动从 ORM 生成 IDEF1X 模式，请遵循 [第 11 章](#Ch011_481-537_B9780443237904000141.xhtml) 中讨论的关系映射（Rmap）过程以获得关系模式，然后以 IDEF1X 重绘。从 ORM 映射到真正的 ER 取决于 ER 方言（例如，是否支持 *n* 元关联、多值属性、任何形式的对象化或派生属性/关联？）。工业界的 ER 方言通常不支持这些选项。[表 8.2](#Ch008_309-346_B9780443237904000177.xhtml#t0015) 中的 *ERmap* 过程为将 ORM 映射到 Barker ER 或 IE 提供了基本指导。
