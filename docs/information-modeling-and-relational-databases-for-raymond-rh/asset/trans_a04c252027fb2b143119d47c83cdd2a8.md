

## 非标识关系

在非标识关系中，子实体的*非键*属性（即不在主键中的属性）包含一个引用父实体主键的外键。如果该外键是强制的（其每个组成部分均非空），则每个子实例恰好关联一个父实例。这被称为*强制*关系，但其真实含义是：在迁移之前产生该外键引用的概念关系中，子角色是强制的。

[图 8.33(a)](#Ch008_309-346_B9780443237904000177.xhtml#f0170) 更详细地描绘了这种情况。此处，*a* 和 *b* 为简单或复合属性。如果外键是可选的（其组成部分可能全为空），则每个子实例至多关联一个父实例。[图 8.33(b)](#Ch008_309-346_B9780443237904000177.xhtml#f0170) 描绘了这种情况。在 IDEF1X 中，这被称为*可选*关系。

![图 8.33 “强制”(a) 和 “可选”(b) 非标识 “关系”。](images/B9780443237904000177/f08-33-9780443237904.jpg)

[图 8.33](#Ch008_309-346_B9780443237904000177.xhtml#B-f0170) “强制”(a) 和 “可选”(b) 非标识 “关系”。

在强制和可选两种情况下，子实体外键的每个无空值组成部分的实例都必须作为父实体主键的一个实例出现。这是结构化查询语言（SQL）中外键约束的默认含义。当然，对于强制情况，不允许有空值组成部分。

[图 8.34(a)](#Ch008_309-346_B9780443237904000177.xhtml#f0175) 展示了一个强制非标识连接关系的示例。在此，每个雇员由雇员编号标识，必须有姓名，且必须为某个部门工作。每个部门由其代码标识，且必须有唯一名称。

![图 8.34 同一示例的 (a) IDEF1X、(b) IE、(c) 关系和 (d) ORM 表示。](images/B9780443237904000177/f08-34-9780443237904.jpg)

[图 8.34](#Ch008_309-346_B9780443237904000177.xhtml#B-f0175) 同一示例的 (a) IDEF1X、(b) IE、(c) 关系和 (d) ORM 表示。

某雇员为某部门工作这一事实（概念关系）通过实例化 `Employee` 的 `empNr` 和 `deptCode` 属性来存储（例如 `empNr = 101`，`deptCode = "HR"`）。该连接“关系”仅是一个外键引用，指示雇员的每个部门代码必须是某个部门的部门代码。

同一示例在 [图 8.34(b)](#Ch008_309-346_B9780443237904000177.xhtml#f0175) 中以 IE 表示法展示，在 [图 8.34(d)](#Ch008_309-346_B9780443237904000177.xhtml#f0175) 中以 ORM 表示法展示。此处，关联“雇员为部门工作”被概念性地描绘，而非将 `deptCode` 作为 `Employee` 的属性包含在内。Barker 表示法也是这种情况。[图 8.34(c)](#Ch008_309-346_B9780443237904000177.xhtml#f0175) 以关系表示法描绘了该情况。在此，关于谁为哪个部门工作的事实存储在 `Employee` 表中，该表包含一个引用 `Department` 表的 `deptCode` 属性。将其与 [图 8.34(a)](#Ch008_309-346_B9780443237904000177.xhtml#f0175) 中的 IDEF1X 表示法比较，应能清楚地看出它们只是同一结构的两种符号变体。在基于键和全属性视图中，IDEF1X 表示法本质上是一种逻辑表示法，而非概念表示法。

作为非标识关系的另一个示例，[第 1.2 节](#Ch001_1-25_B9780443237904000062.xhtml#s0015) 和 [第 8.2 节](#Ch008_309-346_B9780443237904000177.xhtml#s0015) 中考虑的会议室调度示例在 [图 8.35(a)](#Ch008_309-346_B9780443237904000177.xhtml#f0180) 中以 IDEF1X 建模。该情况的 ORM 模型（不含事实实例）在 [图 8.35(b)](#Ch008_309-346_B9780443237904000177.xhtml#f0180) 中复现。IDEF1X 模式中的主键和备选键约束对应于 ORM 模型中的唯一性约束。虽然 IDEF1X 模式捕获了所有约束，但它是一种逻辑而非概念表示，且不像 ORM 那样通过口头化和实例化来便于验证。

在 ER 视图或“实体级图”中，所有实体类型均用实线矩形描绘，并允许非特定（`m:n`）关系。每条非特定关系线必须以一个点结束，该点可能带有基数标记。若无标记，则假定基数恰好为一。在转向基于键或全属性视图时，每个 `m:n relationship` 必须解析为一个带有两个 `n:1` 关系的“`intersection entity type`”（交集实体类型）。[图 8.39](#Ch008_309-346_B9780443237904000177.xhtml#f0200) 展示了 IDEF1X 和 ORM 中的示例。

![图 8.39 (a) 在 IDEF1X 中，`m:n` 关系必须解析为 `n:1` 关系。(b) 同一示例的 ORM 表示。](images/B9780443237904000177/f08-39-9780443237904.jpg)

[图 8.39](#Ch008_309-346_B9780443237904000177.xhtml#B-f0200) (a) 在 IDEF1X 中，`m:n` 关系必须解析为 `n:1` 关系。(b) 同一示例的 ORM 表示。

交集实体类型有时称为“`associative entity type`”（关联实体类型）。尽管概念上这对应于 ORM 中的共引用对象类型，但在 IDEF1X 中，标识属性必须被“迁移”以成为交集实体类型主键内的外键，因此交集实体类型必须是标识符依赖的，显示为虚线矩形。这种外键描绘有效地将表示层级降低到了关系层级。

尽管这种解析通常不自然，但它确实允许向曾经的关系添加属性。例如，我们可能希望为 `Play` 记录技能等级。在 ORM 和 UML 中，也可以通过简单地允许关系被对象化（作为对象化关联或关联类）来实现这一目标，但 IDEF1X 不允许这种概念替代方案。
