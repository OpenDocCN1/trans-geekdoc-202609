
虽然关系模型禁止这样做，但大多数关系数据库系统（允许没有主键的表）都支持这种情况，相关的唯一性约束可以通过过程或断言来强制执行。然而，通过修改概念模式以非析取引用替换析取引用，通常可以获得更简单的实现。在步骤 0.6 中，我们将考虑此类替换。

替换析取引用方案有三种基本方法：人工标识符、连接标识符或使用特殊默认值。让我们简要地看看这三种替代方案，以植物学示例为例。第一种选择是为 `PlantKind` 引入一个新标识符（例如 `PlantKindNr`），从而得到以下关系模式。

![](images/B9780443237904000141/u11-11-9780443237904.jpg)

这种方法有两个主要优点：主键没有空值，且表连接更快（现在仅基于 `plantKindNr`）。人工标识符选项并非全是好消息。`PlantKind` 中的辅助键仍然包含可选字段。此外，由于该辅助键使用自然引用方案，这通常是用户想要看到的（而不是人工的 `PlantKindNr`）。例如，要查找博物馆展示了哪些植物种类，我们现在需要连接表，因为我们想查看自然植物名称。

一个更简单的解决方案是将标识符原本分开的部分连接成一个单一名称。这导致了非常简单的关系模式：

![](images/B9780443237904000141/u11-12-9780443237904.jpg)

如果我们不需要列出或分组标识符原本分开的部分，这种简单模式是最佳解决方案。然而，如果我们想发出诸如“哪个物种拥有最多的植物种类？”之类的查询，现在就没有简单的方法可以做到这一点。

第三种选择是保持引用方案的原始组件分离，但通过在没有实际值存在时使用*特殊默认值*使它们每一个都成为强制性的。例如，植物种类 *acacia interior* 可以存储为元组（“acacia”、“interior”、“nil”、“nil”），使用“nil”作为特殊默认值（不同于 null）来指示该植物种类在 `infraRank` 和 `infraName` 上没有实际值。[图 11.48](#Ch011_481-537_B9780443237904000141.xhtml#f0245) 中的概念模式通过使 `PlantKind` 的 `species` 和 `infraspecies` 谓词成为强制性的、删除子集约束，并向 `Rank` 的任何值列表添加“nil”（例如 {“ssp”、“var”、“forma”、“n-ssp”、“n-var”、“n-forma”、“nil”}）进行了修改。获得了以下关系模式（省略了值列表）：

![](images/B9780443237904000141/u11-13-9780443237904.jpg)

在这种情况下，默认值“nil”不太可能与实际值混淆。然而，在某些情况下，可能会出现这种混淆（例如，默认分数为 0），用户可能因此承担区分默认值和实际值的责任。此外，忽略 null 的包函数不会忽略 nil。

映射过程步骤 0 的最终细化（步骤 0.7）处理了对象化谓词未被唯一性约束跨越的情况。某些 ORM 版本禁止这种情况，因为它违反了元素性。正如[第 10.5 节](#Ch010_401-479_B9780443237904000244.xhtml#s0025)所讨论的，我们也倾向于避免此类情况。

然而，如果允许这种情况，则在执行过程的分组部分之前需要一些预处理。

在嵌套 1:1 的情况下，应在分组时决定偏向其中一个角色。例如，假设[图 11.49](#Ch011_481-537_B9780443237904000141.xhtml#f0250) 中的模式用于模拟一夫一妻制社会中的当前婚姻。该模式违反了元素性。它可以分裂为两个事实类型：一个关于婚姻，一个关于婚姻年份。如果 `Person` 不扮演其他函数角色，我们可能将其映射到[图 11.49](#Ch011_481-537_B9780443237904000141.xhtml#f0250) 中所示的任一表方案。对于这种 1:1 情况，必须做出选择（例如，通过选择其中一个唯一性约束作为主键）。

![图 11.49 对象化 1:1 关联的两种可能映射。](images/B9780443237904000141/f11-49-9780443237904.jpg)

[图 11.49](#Ch011_481-537_B9780443237904000141.xhtml#B-f0250) 对象化 1:1 关联的两种可能映射。

如果对象化谓词中的只有一个角色是函数性的，它会自动被选为主键。例如，在一夫多妻制社会中，一个男人最多只能娶一个女人，但反之不然，`husband` 列将被选为主键（而 `wife` 将不再是键）。

尽管有步骤 0.7 的规定，没有跨越唯一性约束的对象化关联通常应通过无嵌套的重建模来避免。回顾[图 10.52](#Ch010_401-479_B9780443237904000244.xhtml#f0265)，它展示了针对讨论中的婚姻案例的两种无嵌套重建模方法。[图 10.54 和 10.55](#Ch010_401-479_B9780443237904000244.xhtml#f0275) 说明了如何在不使用对象化的情况下重建模其他一些案例。

一旦在关系映射中确定了列和约束，您可能希望考虑更改表内的*列顺序*。虽然关系模型将列顺序视为无关紧要，但在实践中，列顺序会影响可读性和性能。CASE 工具会为您选择一种排序，但您可以覆盖它。

通常，最好将主键列放在前面，并将组合标识的对象类型的组成部分或具有强语义亲和力的列分组在一起。在这种情况下，通常首选自顶向下的顺序（例如 `buildingNr`、`roomNr` 而不是 `roomNr`、`buildingNr`）。对于此类组合情况，将取值较少的属性放在前面在某些情况下有助于加快连接速度。类似的观点也适用于组合索引。如果将可选列放在最后，某些系统的性能也会更好。
