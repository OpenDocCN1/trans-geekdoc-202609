

# IDEF 建模语言

20 世纪 70 年代，美国空军启动了一个集成计算机辅助制造（ICAM）项目。这标志着 `IDEF 建模语言` 家族的诞生。首字母缩写词 "IDEF" 最初代表 "ICAM DEFinition"（ICAM 定义），但现在代表 "Integration DEFinition"（集成定义），反映了其可用于在不同建模语言之间交换信息。ICAM 项目并未规定一种通用的建模语言，而是为不同任务定义了以下语言：

*   `IDEF0` 活动建模
*   `IDEF1` 概念数据建模
*   `IDEF2` 仿真建模

后来，又增加了其他语言，包括：

*   `IDEF1X` 逻辑数据建模
*   `IDEF3` 过程建模
*   `IDEF4` 面向对象软件设计
*   `IDEF5` 企业本体的知识工程
*   `IDEF1X[97]` 具有面向对象扩展的逻辑数据建模

名称 "`IDEF1X`" 代表 "IDEF1 eXtended"（IDEF1 扩展）。尽管基于概念 `IDEF1` 语言，`IDEF1X` 进行了更改以专注于逻辑数据建模。尽管有人对此表示遗憾，但 `IDEF1X` 的引入实际上宣告了 `IDEF1` 的终结。随着时间的推移，`IDEF3` 在很大程度上吸收了 `IDEF2` 和 `IDEF5`。如今，`IDEF1X` 是最流行的 `IDEF` 语言，受到许多 CASE 工具的支持，并广泛应用于美国政府部门，特别是国防领域。其他 `IDEF` 语言也在使用，尽管程度较低。

## IDEF1X 概述

`IDEF1X` 是一种混合语言，结合了一些概念概念（如实体、关系）与关系数据库构造（如外键）。它于 1993 年被美国国家标准与技术研究院（NIST，1993）接受为标准。一个名为 `IDEF1X[97]` 的后继版本（也称为 `IDEF[object]`）于 1998 年经 IEEE 批准，并于 2012 年进一步完善，成为目前仍在使用的版本（[https://www.iso.org/standard/60614.html](https://www.iso.org/standard/60614.html)）。该版本为 `IDEF1X` 增加了面向对象特性，以便于在面向对象数据库和编程语言中实现，同时保持与用于关系数据库实现的 `IDEF1X` 的兼容性。这种向后兼容性使 `IDEF1X[97]` 在美国政府部门的采用方面比 UML 具有一项优势。

然而，`IDEF1X[97]` 的面向对象扩展不如 UML 中的全面。虽然 UML 尚未广泛用于数据库设计，但它迄今为止是设计面向对象代码最广泛使用的语言，并受到许多 CASE 工具的支持。在撰写本文时，只有少数 CASE 工具支持 `IDEF1X[97]`。相比之下，`IDEF1X` 语言的原始（1993）版本继续被广泛用于数据库设计，并受到许多建模工具的支持。基于这些原因，本节其余部分我们将关注原始 `IDEF1X`。

## 建模构造

为了对事实建模，`IDEF1X` 使用了 ER 的三个主要构造：实体、属性和关系。遗憾的是，`IDEF1X` 标准使用术语 "entity"（实体）来表示 "entity type"（实体类型），而非 "entity instance"（实体实例）。更遗憾的是，一些从业者采用了这种误用。因此，你可能不得不比你想要的更频繁地使用 "instance"（实例）一词，仅仅是为了确保不被误解。每个实体类型具有一个或多个基于域的属性。域是一组具有相同数据类型的命名数据值集合。关系仅限于实体类型之间的二元关联。

`ER 视图` 可在分析早期使用，但与真正的 ER 相比表达能力非常弱。未为实体类型指定标识方案，且无需声明属性。如果指定了属性，则不为它们声明约束（如强制性）。

`IDEF1X` 中的 ER 视图基本上是 ER 模型的一个不完整草图。原则上，它可以细化为真正的 ER 模型。遗憾的是，`IDEF1X` 并未在概念层面进行细化，而是降至逻辑层面以添加额外细节。任何 ER 视图都必须解析为基于键的视图，并最终解析为完全属性视图以完成模型。基于键的视图和完全属性视图在许多方面类似于关系模型。一些支持 `IDEF1X` 的 CASE 工具不支持其 ER 视图，因此我们从这一点起忽略 ER 视图。

*在基于键和完全属性视图中，IDEF1X 实体类型基本上是关系表，而 "关系" 是外键到主键的引用*。回想一下，外键是一组一个或多个属性，其值（可能是复合的）必须作为某个主键的值出现。源或引用实体（类型）称为 `child`（子实体），目标或被引用实体（类型）称为 `parent`（父实体）。关系可以像概念关联或子类型链接一样被赋予正向和反向读法。然而，它们最终代表子集约束。实际事实全部存储在属性中，就像在关系模型中一样。

### 实体类型

实体类型分为标识符独立和标识符依赖两类。当且仅当实体类型的标识符不依赖于其他实体类型时，它才是 `identifier independent`（标识符独立）的。换句话说，其标识方案不包含与另一个实体类型的概念关系。就键而言，这意味着 *当且仅当实体类型的主键没有任何组件是（完整的）外键时，该实体类型才是标识符独立的*；不过，其主键可能包含仅是外键一部分的属性。否则，该实体类型就是 `identifier dependent`（标识符依赖）的。术语 "identifier independent" 和 "identifier dependent" 常简称为 "independent"（独立）和 "dependent"（依赖）。这种 "independent" 的概念与 ORM 中独立对象类型的概念无关。

### 属性

实体类型的 `Attributes`（属性）列在其矩形内部。`Primary key`（主键）属性出现在顶部区间。这些提供实体类型的主要标识方案。`Alternate keys`（备选键）通过附加 "(AK*n*)" 来标记，其中 *n* > 0。这些提供备选标识方案。如果备选键是复合的，则其每个组件具有相同的 *n* 值。不同的备选键必须具有不同的 *n* 值。`Foreign keys`（外键）通过附加 "(FK)" 来指示。属性 `默认为强制性`。要显示属性为 `可选`，则附加 "(O)"。所有属性均为单值。

在 [图 8.27](#Ch008_309-346_B9780443237904000177.xhtml#f0140) 中，`empNr` 是 `Employee` 的主键。`bldgNr`、`roomNr` 对为 `Room` 提供了复合主键。社会安全号码属性（`ssn`）是 `Employee` 的备选键。在 `Employee` 中，`bldgNr`、`roomNr` 对是一个外键（引用 `Room` 的主键）。在 `Room` 中，`bldgNr` 是一个外键（引用此处未显示的 `Building` 实体类型的主键）。除 `fax` 和 `phoneNr` 标记为可选外，所有属性均为强制性。
