
# 数据库与概念模式

数据库存储来自业务领域的事实实例，而其概念模式对该领域的*结构*进行建模。[图 18.29](#Ch018_935-1005_B9780443237904000104.xhtml#f0150) 回顾了我们对信息系统的基本视图，其中数据库遵循概念模式中规定的规则。从本质上讲，DBMS 是一个用于管理各种数据库的系统；对于建模某个 UoD 的每个数据库，它都会检查每个数据库状态是否与该 UoD 的概念模式中指定的结构一致。

![图 18.29 数据库必须符合概念模式的结构。](images/B9780443237904000104/f18-29-9780443237904.jpg)

[图 18.29](#Ch018_935-1005_B9780443237904000104.xhtml#B-f0150) 数据库必须符合概念模式的结构。

除其他功能外，概念建模工具还是一个用于管理概念模式的系统。本书中的每个有效模式图都可被视为该系统的一个输出报告。关键在于将模式视为这一高层系统的一个实例。只要我们能将图表口语化为原子事实，就可以使用 CSDP 为这种概念模式开发概念模式。我们将得到一个概念*元模式*（关于模式的模式）。

在这种情况下，[图 18.29](#Ch018_935-1005_B9780443237904000104.xhtml#f0150) 中的信息系统架构仍然适用，但用户是信息建模者，数据库存储概念模式，UoD 关乎概念模式，概念信息处理器通过检查它们是否满足元概念模式中指定的结构，确保只有有效的概念模式被放入数据库。

与其为 ORM 概念模式开发一个完整的元模式，不如将我们的讨论限制在简单示例上，例如[图 18.30](#Ch018_935-1005_B9780443237904000104.xhtml#f0155)，忽略嵌套、子类型、派生以及除唯一性约束和强制角色约束之外的所有约束。如果你是元建模新手，起初可能会觉得有点奇怪。作为一个挑战，请使用[图 18.30](#Ch018_935-1005_B9780443237904000104.xhtml#f0155)作为示例报告，执行 CSDP 步骤 1。

元建模类似于普通建模，不同之处在于被建模的事物本身就是一个模型。你可以先粗略描述[图 18.30](#Ch018_935-1005_B9780443237904000104.xhtml#f0155)，例如“它有两个实体类型和一个值类型”。谓词“was directed by”的第一个角色是强制的且具有唯一性约束，等等。这种口语化传达了信息，但我们需要用原子事实来表达它。例如，使用“ObjectKind”表示“对象类型的种类”，我们可以说：“名为‘Movie’的 ObjectType 属于名为‘Entity’的 ObjectKind”。

在前几章中，我们看到同一个 UoD 可以用不同的方式建模。这在这里也适用，因为[图 18.30](#Ch018_935-1005_B9780443237904000104.xhtml#f0155)中的信息可以用许多不同的方式口语化为原子事实。例如，考虑谓词“starred”的两个角色都被同一个唯一性约束跨越这一信息。你会如何用原子事实来表达这一点？

对于像这样的图形化应用，你经常会发现想谈论一个对象（如约束），但它在图表上*没有名称*。你自然会通过*指向*它来向身边的人标识它，但这无法帮助你通过电话向他人传达信息。

在这种情况下，引入一个人工名称或*代理*来标识该对象通常很方便。这在[图 18.31](#Ch018_935-1005_B9780443237904000104.xhtml#f0160)中有所体现，其中每个约束都被赋予了一个标识约束编号。为方便起见，我们还引入了角色编号和谓词编号（尽管我们本可以通过角色在谓词中的位置来标识角色，通过展开的事实类型读法来标识谓词）。

![图 18.31 添加代理以标识约束、角色和谓词。](images/B9780443237904000104/f18-31-9780443237904.jpg)

[图 18.31](#Ch018_935-1005_B9780443237904000104.xhtml#B-f0160) 添加代理以标识约束、角色和谓词。

如果使用读法来标识谓词，我们需要用对象类型名称扩展它们（例如，为了区分 `Movie starred Person` 中的 starred 谓词与 `Play starred Person` 中的谓词，或 `Horse runs Race` 中的 runs 谓词与 `Person runs Barbershop` 中的谓词）。在这些示例中，两个“starred”谓词含义相同，而两个“runs”谓词含义不同。我们可以扩展元模型来捕捉这种区别，但为简单起见，我们在此忽略此问题。

[图 18.32](#Ch018_935-1005_B9780443237904000104.xhtml#f0165)所示的元模式只是众多可能解决方案中的一个。为辅助理解，它填充了与[图 18.31](#Ch018_935-1005_B9780443237904000104.xhtml#f0160)所示概念模式对应的数据库或事实集合。此处，“UC”和“MR”分别代表“唯一性约束”和“强制角色”。

![图 18.32 概念元模式，填充了图 18.31 的模式。](images/B9780443237904000104/f18-32-9780443237904.jpg)

[图 18.32](#Ch018_935-1005_B9780443237904000104.xhtml#B-f0165) 概念元模式，填充了[图 18.31](#Ch018_935-1005_B9780443237904000104.xhtml#f0160)的模式。

唯一性约束是内部还是外部，可通过检查其角色是否来自同一谓词来推导。强制约束是简单还是析取性的（包含性或），可通过检查它是否跨越多个角色来推导。为简单起见，图表省略了这些推导。

回顾一下，本讨论忽略其他约束。为简单起见，每个谓词仅存储一种读法，且忽略嵌套。该解决方案还忽略了参考模式隐含的隐式引用类型。如果你开发了另一种元模式，别忘了进行填充检查。

[图 18.32](#Ch018_935-1005_B9780443237904000104.xhtml#f0165)中的元模式实际上包含原始示例中不存在的特性（例如子类型和其他种类的约束）。因此它不够丰富，无法捕捉自身。作为一个非平凡的练习，你可能希望扩展元模式，直到它能捕捉任何 ORM 模式。例如，你可以通过添加事实类型 `ObjectType is a subtype of ObjectType` 来捕捉子类型链接。要测试一个完整的 ORM 元模式，你应该能够用它自身来填充它。
