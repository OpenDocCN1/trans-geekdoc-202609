
# Temporal Concepts in Data Modeling

Different facts may be recorded with different `granularities of time` (e.g., second, day). Time may be measured using different `calendars` (e.g., Gregorian, Julian) and different `time zones` (e.g., coordinated universal time (UTC), Mountain Standard Time). For most modeling tasks, calendar and time zone choices are taken to be implicitly understood.

Temporal extensions have been proposed for the relational model as well as higher-level data modeling approaches such as ER, ORM, and UML. Basic `temporal object types` (e.g., `Date` or `Period`) may be used just like other object types in the business model, with basic temporal operators (e.g., `−`) assumed to be predefined. *For the rest of this section, time is understood as valid time*, not transaction time.

## Classification of Temporal Object Types

Temporal object types may be classified into two kinds: once only and repeatable.

### Once-Only Temporal Objects

A `once-only temporal object` is either a single `instant` or a single `period` of time, measured to a specified temporal granularity (relative to an assumed calendar and time zone). Some simple examples are depicted in [Fig. 10.9](#Ch010_401-479_B9780443237904000244.xhtml#f0050)(a).

For example, Albert Einstein was born in the year 1879 CE. In this sense, a year is a 12-month period in the time stream. Likewise, a date is a period of 1 day in the time stream (e.g., 2023 June 5), a month is a period of approximately 30 days in the time stream (e.g., 2023 June), an hour is a period of 60 minutes (e.g., 2023 June 5, 9–10 a.m.).

![Fig. 10.9 Examples of (a) once-only and (b) repeatable temporal object types.](images/B9780443237904000244/f10-09-9780443237904.jpg)

[Fig. 10.9](#Ch010_401-479_B9780443237904000244.xhtml#B-f0050) Examples of (a) once-only and (b) repeatable temporal object types.

A `time` is an instant in the time stream measured to a specified granularity, such as a second, for example, 2023-06-05 14:35:27 (i.e., 2023 June 5, 14 h 35 m 27 s). Object types such as these are useful for recording when an individual event happened or will happen (e.g., the birth of Einstein, or the next Olympic Games).

### Repeatable Temporal Objects

Each `repeatable temporal object` corresponds to a set of instants or time periods, measured to a specified granularity (relative to an assumed time zone). Some simple examples in ORM notation are depicted in [Fig. 10.9](#Ch010_401-479_B9780443237904000244.xhtml#f0050)(b).

Here, a `weekday` is a day slot of any week excluding the weekend (e.g., Monday), a `MonthOfYear` instance is a month slot of any year (e.g., January, or Month 1), and an `hour slot` is a 1-h slot of a day. Object types such as these are useful when modeling schedules (e.g., a workout routine or a conference program).

## Classification of Fact Types by Temporal Behavior

As a business domain changes over time, the set of facts describing it also changes. Regardless of how we represent fact types in a model (e.g., as relationships or as attributes), for the purpose of making decisions about how they are impacted by time, it is convenient to distinguish at least `three kinds of fact types`:

*   `Definitional` (truth of instances is a matter of definition, independent of events)
*   `Once-only` (each instance corresponds to a single event)
*   `Repeatable` (instances may correspond to multiple events)

### Definitional Facts

`Definitional facts` have no temporal aspect. They are necessarily true by definition, rather than depending on any event in the business domain. [Fig. 10.12](#Ch010_401-479_B9780443237904000244.xhtml#f0065)(a) shows an ORM diagram for the definitional fact type `PolygonShape has NrSides` along with a sample fact population. [Fig. 10.12](#Ch010_401-479_B9780443237904000244.xhtml#f0065)(b) shows the same fact type as a UML class diagram.

### Once-Only Facts

Each `once-only fact` corresponds to a single event. Its truth derives from an event that can never be repeated in that business domain. For example, Einstein was born in Germany. This is true because of his birth event, a state of affairs that happened in 1879 CE.

Whether or not reincarnation is possible, let us ignore such possibilities for the business domain modeled in [Fig. 10.13](#Ch010_401-479_B9780443237904000244.xhtml#f0070), where each employee has exactly one birth event. [Fig. 10.13](#Ch010_401-479_B9780443237904000244.xhtml#f0070)(b) depicts this as a many:1 association in UML, and [Fig. 10.13](#Ch010_401-479_B9780443237904000244.xhtml#f0070)(c) depicts this as a single-valued attribute in UML.

### Repeatable Facts

Each `repeatable fact` corresponds to a set of events, in the sense that its truth is determined by any one of a set of repeatable events. For example, suppose employee 101 visited Belgium many times. The fact that he/she visited Belgium is made true by any one of those visits. Because the same employee may visit the same country repeatedly, the fact type `Employee visited Country` is said to be repeatable.
