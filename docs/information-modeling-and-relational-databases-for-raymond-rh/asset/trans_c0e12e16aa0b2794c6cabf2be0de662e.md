
现在，假设在现实中 `Student` 和 `Employee` 存在重叠，因此一名学生可能也是一名员工。如果我们想对这种可能性建模，就必须引入一个超类型（例如 `Person`）。但如果我们不关心某学生是否为员工，且这两种类型没有共同的问题需要处理，那么可以保持模式原样。不过，我们的模型在这一点上现在与现实世界有所不同。

通过将 `Student` 和 `Employee` 表现为原始类型，我们的模型宣称这两种类型是互斥的，而现实中它们是重叠的。为避免误解，模型与现实之间的任何此类分歧都必须在技术手册和用户手册中明确记录，以便人们充分了解这一决策。

此类决策不应轻率做出，因为通常有充分的理由想要知道某个实例是否同时属于这两种类型。例如，假设我们要强制执行这样一个约束：任何教师都不能选修自己教授的课程。如果我们希望信息系统为我们强制执行此约束，就必须为其提供一种检测某学生是否为员工的方法。为此，我们必须引入一个超类型（例如 `Person`），最好带有一个全局标识方案（例如 `PersonNr`）。

此外，我们可能想为学生员工记录特定数据（例如休学假）。在这种情况下，我们还需要引入 `StudentEmployee` 作为 `Student` 和 `Employee` 的共同子类型。[图 6.60](#Ch006_211-271_B9780443237904000025.xhtml#f0305) 描绘了这种情况的子类型图。作为练习，请通过添加事实类型和子类型定义将此图扩展为完整模式。性别和出生日期事实类型连接到 `Person`。如果包含在内，关于教师的约束应以文本形式指定。

![图 6.60 泛化与进一步特化后的子类型图。](images/B9780443237904000025/f06-60-9780443237904.jpg)

在之前的案例中，子类型图中的所有子类型都继承了其顶层超类型的标识方案。例如，在[图 6.60](#Ch006_211-271_B9780443237904000025.xhtml#f0305)(a)中，所有人，无论是否为学生和/或员工，都由人员编号标识。

然而在实践中，我们有时会遇到某个子类型拥有首选标识方案，且该方案不同于其直接超类型的情况。在这种情况下，我们拥有一个*上下文相关引用方案*，因为对象的首选标识符取决于其被考察的上下文。

假设在学生档案的上下文中，我们想用 `StudentNr` 标识学生；而在员工档案的上下文中，我们想用 `EmployeeNr` 标识员工。我们可以通过在子类型节点本身引入*上下文相关标识符*来在子类型图上指示这一选择。

例如，在[图 6.60](#Ch006_211-271_B9780443237904000025.xhtml#f0305)(b)中，`Student` 由 `StudentNr` 标识，`Employee` 由 `EmployeeNr` 标识。如果某子类型未引入其首选标识符，则必须从其某个超类型（直接或间接）继承标识符。

*实线子类型箭头*提供了一条通往子类型首选标识符的路径，使用该路径上找到的第一个标识符。*虚线子类型箭头*不提供通往子类型首选标识符的路径，因此该子类型要么引入自己的标识符，要么必须通过另一条通往超类型的路径来继承其标识符。

例如在[图 6.60](#Ch006_211-271_B9780443237904000025.xhtml#f0305)(b)中，`Student` 和 `Employee` 引入了自己的标识符，因此它们仅与 `Person` 有虚线子类型连接。`StudentEmployee` 有两个超类型，并由 `EmployeeNr` 标识（由实线子类型连接显示），而非由 `StudentNr` 标识（虚线连接）。

泛化对象类型的过程总结如下。此处 `A` 和 `B` 最初被分别描绘为没有共同超类型的实体类型。

|  |  |
| --- | --- |
|  | **泛化过程 (GP)：** |
|  | **如果** |
|  | `A` 和 `B` 重叠，或可被比较（例如计算比率） |
|  | **且** 我们希望对此建模 |
|  | **或** |
|  | `A` 和 `B` 互斥。 |
|  | **且** 为两者记录了共同信息。 |
|  | **且** 我们希望就此信息将 `A` 和 `B` 一起列出。 |
|  | **那么** |
|  | 引入其超类型 `A` ∪ `B` 及其自身的标识方案； |
|  | 向超类型添加谓词以将成员分类为 `A`、`B`； |
|  | 将共同角色连接到超类型； |
|  | **如果** `A`（或 `B`）扮演某些特定角色 |
|  | **那么** 将其定义为子类型并连接这些角色 |

必须强调的是，泛化或特化的决策是一个概念层面的决策。这并不意味着我们承诺以特定方式将生成的子类型图映射到逻辑数据库模式。存在多种映射选项（例如，子类型可被吸收进与其超类型相同的表中，或映射到单独的表中）。[第 11 章](#Ch011_481-537_B9780443237904000141.xhtml)将详细讨论这些映射选项。
