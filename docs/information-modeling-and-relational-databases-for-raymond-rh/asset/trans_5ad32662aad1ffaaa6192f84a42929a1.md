[图 14.63](#Ch014_681-771_B9780443237904000189.xhtml#B-f0320) 函数依赖 `countryCode → population` 是一个无害的传递依赖。

设 *X* 和 *Y* 为同一张表的属性（可能是复合属性）。当且仅当 *X* 包含 *Y* 时，函数依赖 *X* → *Y* 为*平凡*依赖。例如，表模式 `Student(studentNr, gender)` 有六个平凡函数依赖：`studentNr → studentNr`、`(studentNr, gender) → studentNr` 等。当且仅当不存在从 *X* 的仅一部分到 *Y* 的函数依赖时，函数依赖 *X* → *Y* 为*完全*依赖（而非部分依赖）。

一个完全、非平凡的函数依赖被称为*基本函数依赖*。请看 [图 14.64](#Ch014_681-771_B9780443237904000189.xhtml#f0325) 中关于美国城市人口的表（2023 年数据）。该表有三个以主键 `cityNr` 为起点的基本函数依赖，以及两个以备选键 `(cityname, stateCode)` 为起点的基本函数依赖。该表中的一些非基本函数依赖有 `cityNr → cityNr` 和 `(cityName, stateCode) → cityName`。我们通常避免显示非基本函数依赖，因为它们显然由基本函数依赖隐含。

![图 14.64 五个基本函数依赖：三个来自 cityNr，两个来自 (cityName, stateCode)。](images/B9780443237904000189/f14-64-9780443237904.jpg)

[图 14.64](#Ch014_681-771_B9780443237904000189.xhtml#B-f0325) 五个基本函数依赖：三个来自 `cityNr`，两个来自 `(cityName, stateCode)`。

如果从某键到表中某属性存在基本函数依赖，则该键为*基本键*。如果某属性属于某个基本键，则该属性为基本键属性。例如，[图 14.64](#Ch014_681-771_B9780443237904000189.xhtml#f0325) 中的城市表有两个基本键：`cityNr` 和 `(cityName, stateCode)`。现在我们可以定义下一个更强的范式，它作为对 3NF 的改进而被提出（[Zaniolo, 1982](#Ch014_681-771_B9780443237904000189.xhtml#bb1330)）。

当且仅当表模式的所有基本函数依赖都始于完整的键，或终于基本键属性时，该表模式处于**基本键范式**（**EKNF**）。换句话说，对于形式为 *X* → *Y* 的每一个完全、非平凡函数依赖，*X* 要么是一个键，*Y* 要么是（某个）基本键（的一部分）。例如，[图 14.64](#Ch014_681-771_B9780443237904000189.xhtml#f0325) 中的 City 表处于 EKNF。如果一张表的主键包含其所有列，则该表自动处于 EKNF，因为它没有基本函数依赖；例如：`Enrollment(studentNr, subjectCode)`。

现在考虑 [图 14.65](#Ch014_681-771_B9780443237904000189.xhtml#f0330)(a) 中的 OfficialLanguage 表，它记录各国官方使用的语言。国家可通过其代码或名称来标识。该表有两个复合键：`(countryCode, language)`；`(countryName, language)`。主键用双下划线标示；因为其属性不相邻，所以添加了一条虚线连接符，以表明这是一个单一的复合键，而不是两个简单键约束。次键用单下划线标示。

![图 14.65 (a) 处于 3NF 但非 EKNF 的表。(b) Rmap 提供了正确的模式。](images/B9780443237904000189/f14-65-9780443237904.jpg)

[图 14.65](#Ch014_681-771_B9780443237904000189.xhtml#B-f0330) (a) 处于 3NF 但非 EKNF 的表。(b) Rmap 提供了正确的模式。

因为 OfficialLanguage 表没有非键属性，所以它自动处于 3NF。然而，它存在明显的问题（例如，代码为“CA”的国家名为“Canada”这一事实被重复了）。

发现这种糟糕设计的一种方法是注意到该表不在 EKNF 中。存在从 `countryCode` 到 `countryName` 的函数依赖，以及从 `countryName` 到 `countryCode` 的函数依赖（由表上方的箭头描绘）。这些基本函数依赖来自键的一部分而非完整的键，且它们不终于基本键属性，因为这两个复合键都不是基本键。因此，该表不在 EKNF 中。

通过将表拆分为两个 EKNF 表（如 [图 14.65](#Ch014_681-771_B9780443237904000189.xhtml#f0330)(b) 所示）来避免冗余：`Country(countryCode, countryName)`；`LanguageUse(countryCode, language)`。原表模式中缺失的两个函数依赖现在由 Country 表中的键约束捕获，冗余也被消除。通过对所示 ORM 模式进行 Rmap 映射可获得相同的设计。如果语言事实类型对 Country 不是强制的，则在关系模式中用从 `LanguageUse.countryCode` 到 `Country.countryCode` 的简单子集约束替换等值约束。

下一个范式以 Raymond Boyce 和 Edgar Codd 命名，他们将其作为对 3NF 的改进而提出。[Heath (1971)](#Ch014_681-771_B9780443237904000189.xhtml#bb9050) 更早给出了一个等价定义。当且仅当表模式的*所有基本函数依赖都始于完整的键*时（即，给定任意完全、非平凡函数依赖 *X* → *Y*，*X* 必须是一个键），该表模式处于**Boyce-Codd 范式**（**BCNF**）。例如，关系模式 `Student(studentNr, gender, birthdate)` 处于 EKNF，因为其所有基本函数依赖都始于 `studentNr` 键。关系处于 3NF（或 EKNF）但不处于 BCNF 的唯一情况是：它至少有两个相互重叠的候选键（[Vincent and Srinivasan 1994](#Ch014_681-771_B9780443237904000189.xhtml#bb1305)）。

该表不在 BCNF 中，因为表上方所示的函数依赖并不始于完整的键。例如，存在函数依赖 `countryCode → countryName`，但 `countryCode` 只是 `(countryCode, language)` 键的一部分。通过将表拆分为两个 BCNF 表（如 [图 14.66](#Ch014_681-771_B9780443237904000189.xhtml#f0335)(b) 所示）来避免冗余。

通过对所示 ORM 模式进行 Rmap 映射可自动获得此设计。和以前一样，如果语言使用事实类型是可选的，则将等值约束改为子集约束。

前面的范式仅考虑函数依赖。下一个范式由 Ronald [Fagin (1977)](#Ch014_681-771_B9780443237904000189.xhtml#bb0405) 提出，它考虑*多值依赖*（MVD）。对于具有属性 *X*、*Y* 和 *Z*（可能是复合的）的给定关系，*X 多重决定 Y*（记作 *X* ↠ *Y*）当且仅当 *Y* 值的*集合*仅是 *X* 的函数（独立于 *Z* 的值）。在这种情况下，称 *Y* 多值依赖于 *X*，或 *Y* 多重依赖于 *X*；在这种情况下，*Z* 也将多重依赖于 *X*。函数依赖是多值依赖的一种特殊情况，即当依赖值的集合为单元集时。当且仅当 *X* 包含 *Y*，或 *X* 和 *Y* 共同包含关系中的所有属性时，多值依赖 *X* ↠ *Y* 为平凡依赖。
