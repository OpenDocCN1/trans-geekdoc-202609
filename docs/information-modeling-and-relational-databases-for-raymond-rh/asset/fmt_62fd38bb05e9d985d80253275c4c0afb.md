
# JSON Support and SQL/JSON

JSON support is available in many languages, not just JavaScript. Once a JSON file is loaded into the language of choice, the standard facilities of that language can be used to carry out operations on the data in the usual way, such as iterating over the members of a collection. Extracting data from the object structure created by loading the JSON file requires code in JavaScript, Python, C#, or whatever host language is being used. Strictly speaking, JSON refers to the text format, so once it has been loaded, it is no longer JSON but a structure of the kind appropriate to the language. The syntax may vary by language, there may be different conventions for single versus double quotes, and so on. Data operations are normally carried out on this internal structure, not on the JSON text. Each language will also provide some function to carry out the reverse process to output a textual representation of the inner structure. Different languages may change the format slightly by introducing extra whitespace characters into the output. This does not change the data, but it means that results may not be identical if moving from one programming language to another.

## JSON Schema

Like XML, a JSON file can be described precisely with a schema. The JSON Schema specification describes the structure, constraints, and validation rules for JSON documents. JSON Schema is itself written in a JSON format. It uses JSON objects to describe the structure of the data it validates. This means that JSON Schema documents themselves can be validated. The expected properties of an object can be defined, each property with its own validation rules and data types. This includes maximum and minimum values for numeric properties, maximum and minimum lengths for strings, regular expression patterns, and special formats such as email or URL. Array properties can be specified with data types and maximum and minimum numbers of items. JSON Schema includes many other features that we will not cover here. The specification is constantly reviewed and updated and is freely available. There are many tools available for validation of JSON against a specific schema, generating a JSON schema, generating code from a schema, and so on. As with XML Schema, we will not delve into the full details here.

In some respects, a JSON file (and a corresponding program to load and process the file) could be considered a small database in its own right, though perhaps lacking many features expected in a complete database system such as transactions, concurrency, and so on. However, the JSON format has proved so useful that it has been used as the basis for full database systems, commonly referred to as *Document Databases*. These are usually classified as a type of "NoSQL" database and are discussed in more detail in [Chapter 17](#Ch017_875-933_B9780443237904000050.xhtml).

## SQL/JSON

Given the widespread use of JSON, the SQL standard needed to be extended to accommodate it in the same way that it had previously accommodated XML. SQL:2016 provided support for JSON stored as text in a character-based column (typically `varchar`). Time pressures did not allow the full definition of JSON as a data type, but this was completed in SQL:2023, so data can be stored in a column of data type `json`. This had already been anticipated by several vendors, but their solutions are not necessarily compatible with each other or with the SQL:2023 standard. However, all vendors consistently adhere to the standard definition of JSON. There are two immediate advantages of a `json` data type.

1.  Values can be automatically validated as correctly formed JSON. A data type such as `varchar` has no intrinsic understanding of JSON structure, so an additional function is required for text to establish that it represents a valid JSON value.
2.  Values can be processed more efficiently by converting JSON text into a binary form for internal operations, avoiding relatively expensive string processing. The binary versions also require less storage.

The SQL/JSON data model covers SQL/JSON items and SQL/JSON sequences. A sequence is an ordered list of items. An item is any of the following:

*   An SQL/JSON object: an unordered collection of members, where each member is a key-value pair, the value component being an SQL/JSON item.
*   An SQL/JSON array: an ordered list of elements, where each element is an SQL/JSON item.
*   An SQL/JSON scalar: a nonnull value with a type that is one of the standard JSON types (character string, numeric, or Boolean) or datetime.
*   An SQL/JSON null (different from an SQL null).

Because the structural items (object and array) can be nested, JSON text can represent data with any required degree of complexity.

Values can be inserted into a `json` column in the usual way. Assume we have the following table definition:

```
create table movies (
    movienr int primary key,
    moviedata json
)
```

The primary key column here is included simply as a convenience. We could enter JSON data using one row for each movie in a similar way to any other SQL data type.

```
insert into movies values (3,
    '{ "title": "The Secret Garden",
         "released": "1987",
         "director": "Alan Grint",
         "stars": [
             { "name": "Gennie James", "gender": "F" },
             { "name": "Barret Oliver", "gender": "M" }
         ]
    }')
```
