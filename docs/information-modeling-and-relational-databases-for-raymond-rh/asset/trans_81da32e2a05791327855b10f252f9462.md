上述建表语句声明了 `Employee` 和 `Drives` 表的模式。非空子句表明某列在其表中是强制性的。主键通过主键子句声明。唯一子句指定备选复合键。表间子集约束通过引用子句声明。检查子句用于声明值约束和频率约束。下一章将进一步解释 SQL 语法。

尽管上述 SQL 语法多年来一直是合法的，但某些商业 SQL 方言尚不支持所有这些语法。在实践中，关系模式的某些特性可能需要指定为过程代码，而非声明式地指定。

概念模式包含三个部分：事实类型、约束和*推导规则*。概念推导规则可使用适当的语言，采用关系式或属性式符号进行指定。

例如，在[图 11.6](#Ch011_481-537_B9780443237904000141.xhtml#f0035)(a)所示的模式中，员工的实发工资是通过以下 ORM 规则推导的：**对于每个**员工，**如果**税款**存在则**实发工资 = 薪资 – 税款，**否则**实发工资 = 薪资。

![Fig. 11.6 Making tax paid optional (a) or mandatory with a zero default (b).](images/B9780443237904000141/f11-06-9780443237904.jpg)

[图 11.6](#Ch011_481-537_B9780443237904000141.xhtml#B-f0035) 使缴税成为可选项 (a) 或具有零默认值的强制项 (b)。

如[图 11.6](#Ch011_481-537_B9780443237904000141.xhtml#f0035)(b)所示，如果我们使税款成为强制项并设默认值为 0（在上述税款列的 SQL 代码后追加“`not null default` = 0”）或假设减法运算将 null 视为零，则推导规则可简化为简单的减法。下一章将详细讨论 SQL 如何处理 null 值。

将推导规则映射到关系层存在多种选项。一种选项是在*视图*（虚拟表）中声明推导规则，例如，`create view NetSalary( empNr, netPay ) as select empNr, salary – tax from Employee`。

第二种选项是在相关基表中包含一个*生成列*。在 SQL 标准中，这可以通过在前面给出的表定义中包含以下定义来完成：`netPay generated always as (salary – tax)`。

并非所有 DBMS 都支持生成列，且某些支持该特性的 DBMS 使用不同的语法。例如，在 SQL Server 中，我们可以简单地声明 `netPay as (salary – tax)`。

第三种选项是在相关基表中包含一个*触发列*。正如[第 13 章](#Ch013_647-679_B9780443237904000049.xhtml)所讨论的，表上的触发器指定当相关列以特定方式更改时自动采取的操作。触发器的语法因 DBMS 而异。假设 Employee 表包含 netPay 列，则可在 SQL Server 中使用以下触发器来推导实发工资：

```
create trigger DeriveNetPay on Employeeafter insert, update asif update(salary) or update(tax)beginupdate Employeeset netpay = salary – taxend
```

第四种选项是将推导规则包含在按需调用的*存储过程中*（参见[第 13 章](#Ch013_647-679_B9780443237904000049.xhtml)）。前面给出的 SQL 示例仅用于概述目的。接下来两章将详细解释 SQL。

一旦声明了关系模式，初始数据定义阶段即告结束。随后我们通过添加或删除基本事实，或许还有一些存在性事实（通过插入、删除和修改数据行）来执行数据维护。然后可以进行数据检索，以列出感兴趣的基本或推导事实（例如，通过构建适当的 SQL select 语句）。

数据呈现和数据安全任务通常也通过创建输入屏幕和输出报表，以及向各用户组分配数据访问权限来解决。这些操作将在接下来两章中详细讨论。

## 11.3 关系映射过程

上一节介绍了一种用于列出关系模式的通用符号，并讨论了从概念模式映射到关系模式的简单示例。现在我们讨论执行此类映射的通用过程的主要步骤。该过程的高级方面将在[第 11.4 节](#Ch011_481-537_B9780443237904000141.xhtml#s0055)中探讨。

对于给定的概念模式，可能会选择几种不同的关系设计。理想情况下，所选的关系模式应*正确、高效且清晰*。正确性要求关系模式等同于概念模式（在关系结构允许的完整性范围内）。效率意味着对更新和查询有良好的响应时间，且对存储空间的要求合理。清晰性意味着模式应相对易于理解和使用。

由于数据的正确性通常比快速响应时间更重要，而正确性需要充分的约束强制执行，因此通常高度重视简化更新时的约束强制执行。实现这一点的主要方法是*避免冗余*。这种策略可能导致设计中包含更多表，如果现在需要额外的表连接，可能会降低查询和更新的速度。为提高效率，我们应尝试将表的数量保持在可接受的限度内。
