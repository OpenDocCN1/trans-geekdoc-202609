为了解决这个问题，我们可以要求在注解中包含角色名称，或者采用 ORM 提供正式子类型定义的做法。类型 `Employee`、`ParttimeEmployee` 和 `FulltimeEmployee` 是时间指示性的，因为它们的含义部分取决于其术语被表述/记录的时间。

UML 允许泛化注解包含泛化集的名称（当涉及幂类型时，推测是作为幂类型名称的前缀，但 UML 规范并未阐明这种可能性）。然而，此类名称被视为非正式注释。没有正式要求将这些名称关联回超类型的属性（属性或远端角色），就像那些使用判别器来指示子类型依据的数据库建模技术所做的那样。

如果我们要在模型中允许高阶类型，什么样的高阶逻辑是合适的？目前的 ORM 形式化仅使用一阶逻辑、基本算术和包推导。一旦我们采用高阶逻辑，就需要允许任意阶（而不仅仅是二阶），因为原则上，人们总可能引入新类型来对现有类型进行分类，无论这些类型是否为一阶。如果我们采用高阶逻辑的标准语义，其中量词可以遍历任何可想象的谓词，我们将失去一阶逻辑的一些有用性质（例如完备性和紧致性）。

此外，需要小心避免一些著名的悖论。`Russell’s paradox`（罗素悖论）考虑的是所有不包含自身的集合的集合：这个集合是否包含自身？如果是，则不是；如果不是，则是，从而导致矛盾。

`Grelling’s paradox`（格雷林悖论）处理自谓或自指性质（适用于自身的性质）。例如，我们可能会争辩说，非人的性质本身是非人的（因此是自谓性质），而人的性质本身不是人（因此是非自谓性质）。如果谓词可以实例化自身，那么用 `N` 和 `H` 分别表示非人和人的性质，我们可能将其形式化为 `NN` 和 `~HH`。但那么非自谓性质本身如何？它是自谓的还是非自谓的？如果它是，那么它不是；如果它不是，那么它是。无论哪种方式，我们都会得到矛盾。

为了避免此类悖论，伯特兰·罗素发展了一种类型论，其中类型按层级排序，只有当第二个类型位于层级的下一层时，说一个类型是另一个类型的实例才有意义。同样，高阶谓词仅适用于较低阶的谓词或对象。特别是，没有谓词可以适用于同阶的任何谓词。因此，没有谓词可以适用于自身。本质上，通过禁止谓词适用于自身，采用类型只能拥有较低层级实例的层级体系，从而避免了悖论。

虽然这似乎是采用高阶逻辑的合理方法，但其他一些版本的高阶逻辑并不采用这种方法。例如，知识交换格式（`KIF`）和 ISO Common Logic 标准都允许谓词实例化自身，因此允许诸如 `(R R)` 之类的表达式。

为了使高阶逻辑的实现更易处理，似乎最好采用非标准语义（类似于 Henkin 语义），以限制我们可以量化的谓词/函数范围，从而保留一阶逻辑的有用性质（如完备性）。在标准语义下，一元一阶谓词可以遍历个体域（对象：词汇或非词汇）的幂集。

对于我们希望断言实例为类型的分类类型（例如 `AccountType`），似乎我们超越一阶逻辑所需的唯一扩展，是允许对已声明分类类型的实例对象类型进行量化（无论这些实例是否已显式声明为子类型）。

作为一个单独的决定，如果我们希望允许在同一模型中跨越元层级（见后文），我们应该允许对模式中显式声明的任何阶的对象类型（原始或派生）进行量化。如果我们允许这一点，似乎没有令人信服的理由允许对多元谓词进行量化，因此这种放宽可被视为 Henkin 语义的一个受限情况。

我们现在概述一种保持一阶的分类方法。考虑 [图 10.66](#Ch010_401-479_B9780443237904000244.xhtml#f0335) 中的 ORM 模式，这是一个经典案例，高阶逻辑支持者会要求 `CarModel` 是一个二阶类型，其实例是 `Car` 的子类型（例如丰田卡罗拉 2022、道奇大黄蜂 2023、雪佛兰科尔维特 2025）。

![图 10.66 子类型（或任何类型）的总体通常随时间变化。](images/B9780443237904000244/f10-66-9780443237904.jpg)

[图 10.66](#Ch010_401-479_B9780443237904000244.xhtml#B-f0335) 子类型（或任何类型）的总体通常随时间变化。

当我们想到 `Person` 和 `Car`（具体概念）的实例时，我们想到的是实际的人或车。当我们想到 `CarModel`（抽象概念）的实例时，我们通常想到的是一种本质上是汽车设计的抽象——一种可能由示意图表示的汽车*结构或规格*。

对于任何给定的业务域，我们将*类型*定义为*一组可能的实例，对于业务域的任何给定状态，该类型恰好有一个子集是该类型在该状态下的总体*。

在任何给定时间，类型的*总体*是该类型在该时间存在于业务域中的实例集合。需要时间维度来区分那些具有相同*随时间变化的外延*但在*某一时刻的外延*可能不同的类型（例如 `HumanPerson` 和 `HumanBaby`）。

根据外延性原则，集合由其外延定义。因此，除非我们诉诸非良基集合论，否则必须将集合视为固定的——它们不会随时间改变。对于任何给定的业务域，类型（例如 `Person` 或 `Country`）的当前总体可能随时间变化，但类型本身不会。

鉴于上述类型定义，不将汽车模型的实例视为该模式下可能汽车的集合（子类型）似乎是合理的。每个 `CarModel` 实例都与这种子类型（隐式或显式）存在 1:1 对应关系，但它不等同于子类型。我们认为这种区别总是可以做出的。如果是这样，我们可以将此类“分类类型”的实例视为非类型的普通个体，因此一阶逻辑就足够了。

假设我们如 [图 10.66](#Ch010_401-479_B9780443237904000244.xhtml#f0335) 所示显式引入一个名为 `DodgeHornet2023` 的汽车子类型。子类型定义提供了子类型与汽车模型实例之间的正式联系。使用 ORM 的标准参考模式语义，定义中的表达式 `CarModel ‘DodgeHornet2023’` 简写为 `CarModel **that** has CarModelName ‘DodgeHornet2023’`。

假设我们在生产任何该型号汽车之前，将存在性事实**存在一个** `CarModel` **具有** `CarModelName` ‘DodgeHornet2023’ 添加到信息库中。此时，汽车子类型 `DodgeHornet2023` 的总体是空集。假设稍后生产了 1000 辆该型号汽车。在那个较晚的时间，汽车子类型 `DodgeHornet2023` 的总体包含 1000 辆汽车。
