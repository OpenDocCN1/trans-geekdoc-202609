

## 流程-信息桥接（PIB）

另一种方法是在 BPMN 模型和 ORM 模型之间引入一个中间阶段，形成**流程-信息桥接（Process-Information Bridge，PIB）**。然后，数据存储引用可以指向一个包含相关 ORM 链接的 PIB 元素。一个数据项可以在一个流程的多个活动中使用，因此这也提供了一个解决一对多关系的位置。[图 15.37](#Ch015_773-830_B9780443237904000190.xhtml#f0190) 显示了相关的图形符号。

![图 15.37 活动链接到 PIBRef。](images/B9780443237904000190/f15-37-9780443237904.jpg)

[图 15.37](#Ch015_773-830_B9780443237904000190.xhtml#B-f0190) 活动链接到 PIBRef。

接下来，我们可以转向关系的 ORM 端。在 ORM 中（与实体-属性模型相反），实体的属性（特性）被拆解，并可以用单独的事实类型来寻址。“实体”是通过映射过程从事实类型的集合中形成的，该过程生成一种由映射定义的类型的新模型（例如，关系模型）。

尽管 ORM 中实体的拆解潜在地提供了活动与信息之间更细粒度的关系定义，但对于我们正在考虑的这种交叉引用类型来说，这并不一定方便。一个活动很可能要求将关于一个实体的所有信息作为一个整体来处理，而不是作为孤立的事实。例如，更新存储的人员数据的代理人可能希望同时看到关于特定员工的所有相关信息。与其引用单个事实类型，不如将事实类型按与主要实体类型相关的便捷包进行组织，这要简单得多。

实现这一点的一个直接方法是将事实类型分组为 `relations`（关系），这是指 Codd 最初提出的意义上的关系。ORM 中已经存在通过 `Rmap` 过程从 ORM 模型生成规范化关系的功能。在概念模型中，没有预先承诺采用关系数据库解决方案，但这无关紧要，因为规范化关系可以在其他类型的数据结构中实现，例如 `XML` 和 `JSON`；详见[第 16 章](#Ch016_831-873_B9780443237904000207.xhtml)。

因此，可以通过简单地使用关系的（唯一）名称，来方便地引用信息模型中的一组事实类型。在流程执行期间访问特定数据项，将需要关系名称加上该关系内唯一的键值。同一个活动在流程的不同实例（执行）中可能访问同一关系的不同实例。然而，仅需关系名称即可定义流程模型与信息模型之间的链接。

这种方法将在流程模型和信息模型之间创建一组层级链接，如[图 15.38](#Ch015_773-830_B9780443237904000190.xhtml#f0195) 所示。

### PIBRef 组件

每个 PIBRef 将包含以下内容：

*   **CRUD 访问指示符**：指示在此情况下预期的 CRUD 访问类型的指示符。通常的访问将是只读（Read-only），即活动不期望更改数据；或完全访问（Full），即活动可以查看数据并可能更改数据。这些可以用单个字母表示（`R` 或 `F`，其中 `F` 是 CRUD 的简写）。在极不可能需要更具体的情况下，可以使用 CRUD 的单个字母。
*   **ORM 元素标识**：使用关系名称标识在此情况下涉及的 ORM 元素。同一个 PIBRef 中可以使用多个关系。例如，一个活动可能涉及从一个关系读取并更新另一个关系。

每组 PIBRef 访问/关系值很可能只出现在一个 PIBRef 中——同一个 PIBRef 可以在流程模型中重用，因此无需重复。然而，如果意外引入了重复，也不会有害，只是略显浪费。总体方案总结在[图 15.39](#Ch015_773-830_B9780443237904000190.xhtml#f0200) 中。

### 示例：投诉处理流程

为了说明其中的一些要点，我们可以看一个示例流程模型。[图 15.40](#Ch015_773-830_B9780443237904000190.xhtml#f0205) 使用 BPMN 说明了一个简单的投诉处理流程。记录投诉后，联系客户确认收到，并联系相关部门评估投诉。评估后，要么以某种方式补偿客户，要么发送标准信函解释解决结果。案件详情归档以备将来查询，流程终止。

![图 15.40 一个简单的投诉处理流程。](images/B9780443237904000190/f15-40-9780443237904.jpg)

[图 15.40](#Ch015_773-830_B9780443237904000190.xhtml#B-f0205) 一个简单的投诉处理流程。

为了提供流程与信息之间关系的具体示例，我们将查看 `SendStandardLetter`（发送标准信函）活动；其他活动也可以绘制相应的图示。我们假设该活动拥有适当的资源和人工服务，如打印、装信、加盖邮资，并专注于信息使用。[图 15.41](#Ch015_773-830_B9780443237904000190.xhtml#f0210) 显示了一个信息模型片段，包括可能与 `SendStandardLetter` 活动相关的事实类型。

![图 15.41 与 SendStandardLetter 信息相关的 ORM 模型片段。](images/B9780443237904000190/f15-41-9780443237904.jpg)

[图 15.41](#Ch015_773-830_B9780443237904000190.xhtml#B-f0210) 与 SendStandardLetter 信息相关的 ORM 模型片段。

我们在此假设信函主要由“模板”文本组成，在适当位置插入客户信息、案件参考和日期。为了识别相关事实，该活动需要识别两个主要对象：一个 `Case`（案件）和一个 `LetterType`（信函类型）。从 `Case` 中，我们可以唯一标识 `Client`（客户），从而获得客户的称谓、姓名和地址。从 `LetterType` 中，我们可以识别形成信函正文的适当文本。当前日期假定可从活动的环境中获得。这些信息足以让活动创建并发送标准信函。

[图 15.42](#Ch015_773-830_B9780443237904000190.xhtml#f0215) 显示了信息的关系视图。这可以作为定义流程与信息之间必要桥接的基础。

![图 15.42 SendStandardLetter 信息的关系视图。](images/B9780443237904000190/f15-42-9780443237904.jpg)

[图 15.42](#Ch015_773-830_B9780443237904000190.xhtml#B-f0215) SendStandardLetter 信息的关系视图。

从流程角度来看，必要的链接由[图 15.40](#Ch015_773-830_B9780443237904000190.xhtml#f0205) 的流程模型中的 `SendLetter` 数据存储引用提供。`SendStandardLetter` 活动需要对 `LetterType`、`Client` 和 `Case` 关系进行读取访问（`R`），但需要对 `ClientWasSentLetterTypeOnDate` 关系进行完全访问（`F`）。相关的 PIB 可以在合适的编辑工具中定义，如[图 15.43](#Ch015_773-830_B9780443237904000190.xhtml#f0220) 所示。这显示了四个关系，最后一个关系被展开以显示其属性。该特定工具还允许在流程上下文中使用替代名称。
