
在这里，这两个集合分别包含一个 `Course` 文档列表和一个 `Student` 文档列表。学生和课程之间的关系通过 `Student` 文档中对 `Course` 文档标识符的引用来记录。这避免了前一个示例中的数据冗余，但引入了其他问题。例如，如果我们想获取某学生获得的学分总值，我们必须读取额外的 `Course` 文档以获取必要信息。这大致相当于关系型系统中的连接操作。

`Courses` 和 `Students` 之间的关系是多对多的（因此在上面的示例中，一个 `Student` 文档需要包含对多个 `Course` 文档的引用）。我们可以通过创建一种新的 `Course-Student` 文档来解决这个问题，这相当于关系型系统中的链接表。然而，这可能会被视为一种不自然的人为构造而被拒绝。如果考虑现实世界中基于纸质的对应物，`Course` 文档和 `Student` 文档很可能存在，但 `Course-Student` 文档则不太可能存在。

在设计文档数据库时，嵌入与引用的选择取决于在多个相互竞争的因素之间找到恰当的平衡。

首先，我们需要识别重要的文档类型。如果我们是从零开始，可以开发一个对象-角色模型（ORM）来理清与我们关注点相关的信息结构。由此，我们可以使用关系映射（如 [第 11 章](#Ch011_481-537_B9780443237904000141.xhtml) 所述）推导出一组候选文档类型，这些类型可以用适当的 JSON 格式表示。或者，我们可能希望基于预先存在的文档进行设计，如果它们采用其他形式（CSV、XML 等），则将其重新指定为 JSON 格式。

下一组决策高度依赖于文档的预期用法。广义上讲，我们希望文档的大小恰好满足需求，但不应过大。这可能表明应拆分某些候选文档以提高性能（数据库可能会对单个文档施加大小限制，但通常该限制足够大，不必担心）。在考虑文档间的关系时，我们需要了解数据上常见的创建、读取、更新、删除（CRUD）操作的相对频率。读取操作占主导地位的情况很常见，但并非总是如此。

如果我们考虑两种以某种方式相关的文档类型 A 和 B，以下是一些可能相关的场景。

*   如果 A 和 B 经常一起被查询，请考虑将 A 嵌入 B，或将 B 嵌入 A（以性能最优者为准）。
*   长列表效率低下，因此如果将 B 嵌入 A 会导致 B 的长列表，请考虑改用引用。
*   如果 B 很少被单独查询，请考虑将 B 嵌入 A。
*   如果 B 嵌入在 A 中，但 B 与许多其他文档类型相关联，请考虑改用引用。
*   如果 B 嵌入在 A 中，且 B 的更新频率远高于 A，请考虑改用引用。

### 分区

文档数据库中的分区通常指水平分区。通过拆分文档类型以创建两个新的文档类型，每个类型包含原始文档字段的不同子集，可以实现类似垂直分区的效果，但这属于原始数据库设计的内在部分。水平分区可以基于文档的任何部分，但选择取决于数据库的预期用法。每个分区或“分片”可以容纳一个集合中文档的子集，并且在物理上与其他分片截然不同。一个关键决策是选择用作分发依据的字段或字段组合。与其他方面一样，这将取决于数据库的预期使用模式。例如，如果查询经常聚焦于某一特定年份内的数据，则为每一年分配一个单独的分片，并使用相关的日期字段作为分发依据可能是合适的。

集合中的每个文档根据相关字段被分配一个 `shard key` 值。`shard key` 的选择应能将数据均匀地分布在各分片上，以防止热点并确保性能均衡。数据库中的每个分片都维护元数据，将 `shard key` 值的范围映射到特定的分片。执行操作时，数据库客户端会在发送给集群的查询或命令中包含 `shard key` 值。这由专用路由器处理，路由器检查 `shard key`，确定哪些分片需要参与执行该操作，然后制定在相关分片上执行查询的计划。

假设查询涉及多个分片，路由器会根据分片负责的 `shard key` 范围，将查询的各部分发送到相应的分片。每个分片在本地执行其部分查询，并将包含该特定分片特定的整体结果子集的部分结果返回给路由器。一旦路由器收到来自所有分片的结果，它会将它们合并以形成完整的结果集。这可能涉及排序、合并以及应用任何额外的查询操作（例如过滤）以匹配原始查询条件。最后，路由器将合并后的结果集发送回客户端应用程序，提供统一的查询结果视图，就好像它是在单个非分片数据库上执行的一样。

分布式结果的收集和合并显然会带来性能损耗，因此 `shard key` 的选择需要慎重考虑。理想情况下，分区设计应使大多数查询能够路由到集群中的单个分片。

### 索引

与关系型数据库一样，文档数据库可以通过创建允许高效数据检索的数据结构来使用索引以提高查询性能。与模式设计的其他方面一样，拥有清晰的索引策略很重要。虽然索引可以提高查询性能，但也会影响写入性能并增加存储需求。

应检查使用数据库的应用程序的查询类型及其相对频率。根据操作的数量和类型，可以确定合适的索引类型。有几种类型可用，包括：

*   单字段索引：最基本的索引类型，查询基于单个字段。
*   复合索引：在多个字段上创建，将它们组合成单个索引。
*   多键索引：单独为数组的元素建立索引。

还有其他类型的索引用于更专业的应用，如文本、地理空间和哈希索引。

索引是通过指定要索引的集合和字段以及可能需要的任何其他选项（例如在后台创建索引以最大程度减少干扰）的操作来创建的。例如，我们可以在 `Courses` 集合的 `courseName` 字段上创建一个单字段索引，如下所示：

```
db.Courses.createIndex( { courseName: 1 } )
```

这里，数字 `1` 表示索引应按升序排列；降序将由 `− 1` 参数表示。

在文档数据库中，小心处理更新和删除也很重要。与关系型数据库不同，文档数据库不强制执行引用完整性或级联删除。由开发人员负责确保正确执行更新和删除，而不留下孤立数据或破坏关系。
