
UCs may often be determined simply by background knowledge of the UoD. Real world UCs usually determine the weakest UCs to be considered for the actual database. If we know the fact table is significant, then we can generate the constraints from it.

Usually, however, we won’t know in advance that the table is significant, and we will have to use some of our background knowledge. If we lack such knowledge, we should consult the domain expert about any doubtful constraints, posing the relevant questions while adding concrete examples of facts to violate the constraints and asking whether such updates may be accepted.

With a ternary fact type, a spanning constraint is always implied because no whole row may be repeated. This constraint should be specified if and only if no shorter UC holds. So, for our current example, we mark just the constraint for the column 1–3 pair, indicating that each (Person, Subject) pair is assigned at most one rating.

Because the two role boxes involved are not adjacent, a `divided constraint bar` is used, as shown in [Fig. 4.23](#Ch004_111-158_B9780443237904000232.xhtml#f0120). A `dotted line` connects the two active parts of the constraint bar, indicating that the constraint excludes the role under the dotted line. If we omitted the dotted line, the bars would instead denote two separate constraints, one for each end role. If we reordered the fact type instead as “Person for Subject scored Rating”, there would be two contiguous roles spanned by an undivided constraint bar.

The term `n-role constraint` denotes a constraint that spans `n` roles. A UC that spans just one role is a `simple` UC. The constraint in [Fig. 4.23](#Ch004_111-158_B9780443237904000232.xhtml#f0120) is a two-role constraint because it spans two of the three roles involved in the fact type. A binary fact type has three possible basic constraints (two one-role and one two-role), which give rise to four possible cases. A later section demonstrates that no (elementary) ternary fact type can have a simple UC. So a ternary fact type has four basic UCs to be considered: three two-role constraints and one three-role constraint, as shown in [Fig. 4.24](#Ch004_111-158_B9780443237904000232.xhtml#f0125).

![Fig. 4.24 Allowed basic uniqueness constraints for a ternary.](images/B9780443237904000232/f04-24-9780443237904.jpg)

[Fig. 4.24](#Ch004_111-158_B9780443237904000232.xhtml#B-f0125) Allowed basic uniqueness constraints for a ternary.

In practice, ternaries usually have just a single UC either over one role pair or over all three roles. As an example of the latter, a politician travel example is modeled in [Fig. 4.25](#Ch004_111-158_B9780443237904000232.xhtml#f0130). Here, many politicians may visit many countries in many years. Such a fact type is said to be “many to many to many”. Because no whole row can be repeated, we cannot use this fact type to record multiple visits to the same country by the same politician in the same year. If you want to record this, use a different model (e.g., replace Year by Date, or add Quantity).

![Fig. 4.25 A ternary with a spanning uniqueness constraint.](images/B9780443237904000232/f04-25-9780443237904.jpg)

[Fig. 4.25](#Ch004_111-158_B9780443237904000232.xhtml#B-f0130) A ternary with a spanning uniqueness constraint.

With a ternary fact type, we should systematically test each of the three two-role UCs to see which ones hold. Only if no two-role constraints hold should the three-role constraint be specified. As an exercise, check for yourself that the sample data is significant for this constraint.

For a ternary association, there is only one way to have a three-role UC. There are three ways of having precisely one two-role constraint, and three ways of having exactly two two-role constraints. Finally, there is one way of having three two-role constraints. Thus, there are eight different UC patterns that may arise with a ternary fact type. Four of these involve just one constraint ([Fig. 4.24](#Ch004_111-158_B9780443237904000232.xhtml#f0125)) and four involve combinations (see [Fig. 4.26](#Ch004_111-158_B9780443237904000232.xhtml#f0135)).

![Fig. 4.26 Allowed uniqueness constraint combinations for a ternary.](images/B9780443237904000232/f04-26-9780443237904.jpg)

[Fig. 4.26](#Ch004_111-158_B9780443237904000232.xhtml#B-f0135) Allowed uniqueness constraint combinations for a ternary.

This general approach for specifying UCs applies to fact types of any arity. [Fig. 4.28](#Ch004_111-158_B9780443237904000232.xhtml#f0145) shows a template for a quaternary predicate with a UC spanning roles 1, 3, and 4. This indicates that each `acd` combination must be unique to the fact table, where `a`, `c`, and `d` occur in the first, third, and fourth columns, respectively, on the same row of this table. A small but significant population of the fact table is shown. Verify for yourself that this is consistent with the indicated UC.

It is shown later that any UCs on a quaternary must span at least three roles. As an exercise, you might like to explore all the possible cases. Or maybe not! Because elementary fact types are rarely longer than quaternaries, no examples of quinaries or longer fact types are discussed here.

To visualize the connection between roles and columns of the fact table, think of the role boxes as the holes in which the objects get placed to complete the fact. No matter what the arity of the fact type, a UC across a combination of role boxes means that any instance of that column combination that does appear in the table must occur on one row only, and hence can be used to identify that row.

Because a role combination governed by a UC provides a “key to unlock” any row of the fact table, this combination is referred to as a `key` for that table. This notion will be elaborated later in the context of the (often nonelementary) tables used in relational databases.
