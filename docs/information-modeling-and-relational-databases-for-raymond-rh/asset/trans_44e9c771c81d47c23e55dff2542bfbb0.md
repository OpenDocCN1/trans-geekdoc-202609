
请注意，类型所扮演的*任何*角色都可用作对其进行分类的基础。因此，将此类 is-of 关联标记为分类关系的主要原因，是为了强制执行此类关系的形式化属性。我们现在可以形式化此类分类关系。[图 10.62](#Ch010_401-479_B9780443237904000244.xhtml#f0315)(a) 描述了一般情况，假设始终使用相同的谓词读法 "is of:"（如果并非如此，则不失一般性，首先将每个读法替换为 "is of:"）。我们使用 "~" 表示否定（"并非……"），"&" 表示合取（"且"），"→" 表示实质蕴涵（"蕴含"）。与局部同质性不同，非对称性和非传递性属性可以独立于对象类型进行声明。

![图 10.62 分类关系 "is of:"。](images/B9780443237904000244/f10-62-9780443237904.jpg)

[图 10.62](#Ch010_401-479_B9780443237904000244.xhtml#B-f0315) 分类关系 "is of:"。

对于*一阶逻辑解释*，所有类型均为一阶，因此其实例为个体，而非类型。我们使用小写字母（可能带下标）来遍历个体。对于*高阶逻辑解释*，我们使用大写字母（斜体）表示任意阶的类型变量。任何类型的阶（1, 2, 3, …）均为隐含的，因为它可以通过检查完整模式来推导。如果需要显式显示类型的阶，可使用前上标（例如，²B 表示 B 为二阶类型）。

后上标通常用于表示元数，后下标常用于区分同类型的变量。忽略跨越元层级的情况，将类型的阶指定为 1，加上以该类型为终点的、包含零个或多个分类关系的连续链中的关系数量。

使用 ∃¹ 表示"存在唯一"量词，我们现在可以形式化 [图 10.62](#Ch010_401-479_B9780443237904000244.xhtml#f0315)(b) 中分类关系的约束，该约束具有强制性和唯一性约束。一阶形式化将 `AccountType` 视为个体类型。

| *一阶形式化* |
| --- |
| ∀*xy* \[*x* is of: *y* → ~ (*y* is of: *x*)\] | \-- 非对称性 |
| ∀*xyz* \[*x* is of: *y* & *y* is of: *z* → ~ (*x* is of: *z*)\] | \-- 非传递性 |
| ∀*xy* \[AccountType *y* & *x* is of: y → Account *x*\] | \-- 局部同质性 |
| ∀*x* \[Account *x* → ∃¹*y* (AccountType *y* & *x* is of: *y*)\] | \-- 强制性和唯一性 |

高阶形式化将 `AccountType` 视为一阶类型的类型，因此它用 "`Y`" 和 "`Z`" 替换上述表述中的 "`y`" 和 "`z`"。或者，高阶形式化可将形式为 `α is of: β` 的任何表达式（其中 `β` 为类型变量）替换为 `βα`，因为它认为在这种情况下 `α is of: β` 蕴含 `α` 实例化了 `β` 谓词。

区分此类分类关系的一个动机，是为了便于转换到或来自包含所谓*幂类型* 的 UML 模型，UML 专门引入幂类型来建模此类分类方案。在 UML 1.4 中，幂类型使用 «powertype» 标注声明为刻板印象类，但该符号在 UML 2 中已废弃。在 UML 2 中，判断一个类是否为幂类型的唯一方法，是查看它是否在泛化约束中被引用。

[图 10.63](#Ch010_401-479_B9780443237904000244.xhtml#f0320) 显示了一个常用于说明幂类型必要性的示例的简化版本，采用 UML 2 符号。这种对树的分类方式在植物学上是错误的，但这与该问题无关。假设树可以简单地分类为橡树、榆树和柳树等物种。此处，`TreeSpecies` 是一个类，类似于 [图 10.61](#Ch010_401-479_B9780443237904000244.xhtml#f0310) 中的对象类型 `AccountType`。

![图 10.63 UML 2 符号下的 TreeSpecies 幂类型示例。](images/B9780443237904000244/f10-63-9780443237904.jpg)

[图 10.63](#Ch010_401-479_B9780443237904000244.xhtml#B-f0320) UML 2 符号下的 TreeSpecies 幂类型示例。

如果 "powertype" 这个名称源自幂集的概念（集合 *A* 的幂集是 *A* 的所有子集的集合），那么该术语具有误导性，因为 `TreeSpecies` 幂类型排除了树的幂集中的许多实例（例如空集、所有树的集合以及许多其他树的集合）。因此，术语"*高阶类型*"比"幂类型"更为恰当。

无论如何，该图并未显式包含成员关联，如 `Tree is a member of TreeSpecies`（类似于 `Account is of AccountType`）。我们可以在此将此关联视为隐式的，但在实践中，通常需要该关联的显式版本，因为我们通常想知道任何给定树的物种，而有数百个树种时，为所有物种引入子类型在图表上过于繁琐。

在 UML 2 中，冒号 ":" 前置幂类型名称（例如 ": TreeSpecies"），以标注属于基于将超类型与幂类型相关联的关联所提供的分类方案的、所有可能泛化关系集合（称为 *GeneralizationSet*）中所显示的子类型-超类型连接集合。

如果子类型使用不同的箭头连接到超类型，则幂类型标注放置在穿过相关子类型连接的虚线旁边（参见 [图 10.63](#Ch010_401-479_B9780443237904000244.xhtml#f0320)(a)）。

如果使用公共箭头，则标注放置在该箭头旁边（参见 [图 10.63](#Ch010_401-479_B9780443237904000244.xhtml#f0320)(b)）。

如果一个类的名称用于泛化集约束，我们就可以知道它是一个幂类型。我们不能假设从一个类到幂类型的任何二元关联都具有这种性质。例如，除了 `Tree is a member of TreeSpecies`，我们可能还有 `Person named TreeSpecies` 等事实类型。

[图 10.64](#Ch010_401-479_B9780443237904000244.xhtml#f0325) 显示了一个来自 UML 2 规范的示例，它提供了一种不同的方式来建模我们早先账户示例的一个变体。此处，`AccountType` 被建模为幂类型而非枚举，事实类型 `Account is of AccountType` 被建模为关联而非属性。可以在*不显式引入任何子类型*（如 `SavingsAccount` 等）的情况下在模型中包含此关联。在这种情况下，*无法正式捕获该关联的分类语义，也无法声明 `AccountType` 为幂类型*。

![图 10.64 来自 UML 2.0 超结构规范的幂类型示例。](images/B9780443237904000244/f10-64-9780443237904.jpg)

[图 10.64](#Ch010_401-479_B9780443237904000244.xhtml#B-f0325) 来自 UML 2.0 超结构规范的幂类型示例。

虽然角色名称 "account classifier" *非正式地* 暗示了这些额外的语义，但这没有任何形式效力（UML 规范中的其他示例使用不同的角色名称，如 "vehicle category" 等）。因此，*我们需要区分分类关联本身*，例如，通过在关系读法（如 "is of:"）和/或相关关联角色名称后附加冒号。

即使泛化关系用相关幂类型名称标注，也并不总是能正式保证所需的语义。例如，假设我们将员工分类为兼职或全职，并记录其首选雇佣状态（兼职或全职）（如果有）。[图 10.65](#Ch010_401-479_B9780443237904000244.xhtml#f0330) 中的 UML 模型在 `Employee` 和 `EmployeeType` 之间有两个关联，但没有正式的方法知道哪个关联被用作子类型成员资格的基础。
