
# Constraints in Graph Databases

We also need to consider the constraints specified in the ORM model. This is potentially problematic because of the very limited constraint options available in the graph database equivalent. Some workaround possibilities exist through careful framing of statements that modify the structure, but this may not always be possible.

Mandatory constraints can be enforced to some extent by requiring that, for example, a property of a label is not null, but this can be a nuisance if the property value is not known when the relevant node is created.

Uniqueness constraints are available in `Neo4j` and can be used where appropriate. In the model above, the identifying properties for `Company`, `Channel`, `Survey`, and `Program` can be defined as unique. This means that, for example, there will only be one node with the label “Channel” and a `ChannelNumber` property equal to “1”. However, this should not be done in the case of `Suburb`, `Department`, or `TimeSlot` because these labels can have multiple nodes with the same property, as can be seen in [Fig. 17.14](#Ch017_875-933_B9780443237904000050.xhtml#f0075). These nodes can be distinguished from each other by having different instances of their relations with other nodes.

The external uniqueness constraint between the `Channel` role and the `TimeSlot` role is more difficult. We need to ensure that a `TimeSlot` can only relate to one `Program` for a given `Channel`, although the same `TimeSlot` can be used by other channels for their own programs. There is no constraint in `Neo4j` to express this, but we could specify the creation of the `IS_SHOWN_IN` relation between a specific `Program` and a specific `TimeSlot` using the following strategy:

1.  Use a query to find the `Channel` that shows the specified `Program`.
2.  Use a query to find any `Program` shown by that `Channel` in the specified `TimeSlot`.
3.  If the result is null, create the `IS_SHOWN_IN` relation between `Program` and `TimeSlot`.

ORM has a very rich constraint language, and it may not be worthwhile to try to write complex `Cypher` code to capture the full intent of the ORM model. In such cases, it may be better to delegate the constraint to the application code instead of trying to enforce it in the database.

It’s clear from this example that there is a close affinity between ORM and graph databases, which is perhaps not surprising because an ORM model is itself a graph. Graph databases offer a useful alternative to relational systems in applications that are focused more on relationships than data processing. They share many of the same issues on scalability as relational systems, but can provide high availability by replicating servers.

Translating an ORM model into a graph database can be done in a systematic way that preserves most of the intent of the ORM model, though some creativity may be required in dealing with constraints. For a specific graph database system, it would be feasible to automate a `Gmap` procedure to generate a schema design, possibly including some code (in the appropriate language) to deal with issues such as constraints.

Probably the most important feature of graph databases is their ability to follow links through a connected network of data, perhaps extending over long chains of connections.

Many common problems can be expressed in terms of searches through data space, and there are well-known algorithms to perform this in an efficient way. These capabilities make graph databases a popular choice in application areas such as the following:

*   Modeling and querying social network data and other interpersonal relationships.
*   Creating recommendations for users of a system by analyzing their preferences and activities.
*   Identifying patterns of fraudulent behavior by analyzing connections between entities.
*   Building knowledge graphs that represent semantic relationships between entities.
*   Analyzing connections between individuals, organizations, and events in criminal investigations.

# 17.6 Other Nonrelational Databases

A conceptual schema may be mapped to various logical data models. The `Rmap` procedure discussed in [Chapter 11](#Ch011_481-537_B9780443237904000141.xhtml) assumes that the application platform is a centralized, relational DBMS. It is a fairly simple task to specify other procedures for mapping to other types of DBMSs, as we’ve seen earlier in this chapter.

Although relational DBMSs have long been dominant in the commercial marketplace, many alternatives exist. These include older systems based on the hierarchic or network data model as well as newer alternatives such as those discussed previously. While purely relational DBMSs suit most business applications, they may not be the ideal match for some specialized applications such as computer-aided software engineering (CASE) tools, computer-aided design tools (e.g., VLSI design, mechanical engineering, architecture), document processing, spatial databases, expert systems, scientific databases (e.g., genetic engineering), and communications management. Note that most of these applications involve complex objects and probably account for at most 10% of database applications.

Many reasons are cited for dissatisfaction with *purely* relational DBMSs for complex applications. They may be too slow–they don’t perform well with complex objects mainly because they require too many table joins. They often model objects in an unnatural way (e.g., information about a single object such as a person may be spread over several tables–this gets worse with complex objects). They are dependent on value-based identifiers. They don’t facilitate reuse (e.g., they have no direct support for subtyping). They require access to a procedural language for difficult tasks (e.g., special rules and behavior), which leads to an “impedance mismatch” with the declarative, set-based, relational query language. They might not support binary large objects (BLOBs) such as images (icons, pictures, maps etc.), sound tracks, video, and so on.

## Object Orientation

An *object database* (ODB), or *object-oriented database* (OODB), incorporates various object-oriented features. Historically, ODB research drew upon related developments in four areas: programming languages, semantic data models, logical data models, and artificial intelligence.

With programming languages, the need was seen for user-definable abstract data types and for persistent data. The object-oriented programming paradigm began with `Simula` in 1962 and `Smalltalk` in 1972. Nowadays, many object-oriented programming languages exist (e.g., `Eiffel`), and many traditional programming languages have been given object-oriented extensions (e.g., `C++` and `C#`).

Some object-oriented features were taken from semantic data modeling, which as we know models reality in terms of objects and their relationships and includes notions such as subtyping (e.g., ORM, UML, and extended entity-relationship (ER) modeling). Various ideas were also borrowed from work on logical data models (network, hierarchic, relational, and especially the nested relational model). Finally, some concepts were adapted from artificial intelligence, where structures such as frames are used for knowledge representation.

What features must a DBMS have to count as “object-oriented?” There is no commonly agreed-upon answer. A classic paper (“The OODBMS Manifesto”) on this issue was presented at the first international conference on object-oriented and deductive databases ([Atkinson et al., 1990](#Ch017_875-933_B9780443237904000050.xhtml#bb0020)). To distinguish ODBMSs from OO programming languages, five essential features of a DBMS were identified, and then object-oriented features were added, of which eight were considered essential and five optional (see [Table 17.3](#Ch017_875-933_B9780443237904000050.xhtml#t0020)).
