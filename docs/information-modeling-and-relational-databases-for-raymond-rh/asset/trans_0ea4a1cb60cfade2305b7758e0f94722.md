
# 标识符栏的使用

标识符栏的使用提供了ORM中外部唯一性约束所提供的部分功能。例如，[图 8.9](#Ch008_309-346_B9780443237904000177.xhtml#f0050)中的模式是等价的。Room和Building的任何其他属性在ORM中都将建模为关系。对我们而言，ORM的外部唯一性符号似乎更直观地传达了每个`RoomNr`、`Building`组合都是唯一的这一概念（即最多引用一个房间）。但也许我们有偏见。无论如何，该约束（以及任何其他图形约束）都可以自动用自然语言表达。

![图 8.9 (a) Barker ER和(b) ORM中的复合标识。](images/B9780443237904000177/f08-09-9780443237904.jpg)

[图 8.9](#Ch008_309-346_B9780443237904000177.xhtml#B-f0050) (a) Barker ER和(b) ORM中的复合标识。

有些人会将复合标识的栏符号误读为“1”，因为在许多其他ER符号中，该符号代表此含义。但栏和“#”符号的主要问题是，它们不能用于声明不用于主引用的唯一性约束（见后文）。第二个问题源于将某些事实类型建模为属性而将其他事实类型建模为关系的做法，导致对同一基本概念（唯一性）使用了两种截然不同的符号。

[第 1.2 节](#Ch001_1-25_B9780443237904000062.xhtml#s0015)使用了一个房间调度示例，说明了ORM与ER和UML等建模方法之间的几个根本差异。您可能还记得，[图 8.10](#Ch008_309-346_B9780443237904000177.xhtml#f0055)中所示的模式曾用于在Barker符号中建模该示例。如果您跳过了[第 1.2 节](#Ch001_1-25_B9780443237904000062.xhtml#s0015)，建议现在阅读，因为它详细讨论了该示例。该模型中属性的使用和二元关系限制使得难以通过表达和填充模式来进行验证。此外，至少缺少一个约束。

![图 8.10 Barker符号中的房间调度模型。](images/B9780443237904000177/f08-10-9780443237904.jpg)

[图 8.10](#Ch008_309-346_B9780443237904000177.xhtml#B-f0055) Barker符号中的房间调度模型。

该示例的填充ORM模式复现于[图 8.11](#Ch008_309-346_B9780443237904000177.xhtml#f0060)（不包括[第 1.2 节](#Ch001_1-25_B9780443237904000062.xhtml#s0015)中讨论的反例行）。在此，事实自然地被表达为一个三元和一个二元，并且可以使用表达和样本数据轻松检查约束。对于ER模型，无法在任一事实类型上指定右侧的唯一性约束，因为Barker符号无法捕获属性或关系上的唯一性约束，除非它们用于主标识。

![图 8.11 房间调度的填充ORM模型。](images/B9780443237904000177/f08-11-9780443237904.jpg)

[图 8.11](#Ch008_309-346_B9780443237904000177.xhtml#B-f0060) 房间调度的填充ORM模型。

以免看起来我们只是在抨击基于属性的方法（如ER），让我们重申一下，我们认为基于属性的模型对于紧凑的概览和更接近实现模型很有用。然而，我们通过从ORM映射来生成这些模型，ORM被我们专门用于初始概念分析。这使得首次建模更容易做到正确，并且随着底层领域的演变更容易修改模型。

与ER（以及UML）不同，ORM是基于语言学基础构建的，其图形符号经过精心选择，旨在利用样本填充的潜力。为了利用表达和填充的优势，与领域专家进行沟通和验证，最好使用一种为此设计的语言。

ORM的一个额外好处是，其图形符号可以捕获比流行ER符号多得多的业务规则。虽然不如ORM丰富，但Barker符号比许多ER符号更具表现力。本节其余部分讨论其对高级约束和子类型的支持。

在Barker符号中，跨两个或多个角色的排除约束显示为一个连接到角色的“排他弧”，连接处带有一个小点或圆圈。例如，[图 8.12](#Ch008_309-346_B9780443237904000177.xhtml#f0065)(a)包含这样一个约束：任何员工不得同时分配有公交卡和停车位。在ORM中，该约束通过虚线将“⊗”连接到相关角色来描绘，如[图 8.12](#Ch008_309-346_B9780443237904000177.xhtml#f0065)(b)所示。

![图 8.12 (a) Barker符号和(b) ORM中的简单排除约束。](images/B9780443237904000177/f08-12-9780443237904.jpg)

[图 8.12](#Ch008_309-346_B9780443237904000177.xhtml#B-f0065) (a) Barker符号和(b) ORM中的简单排除约束。

要声明两个或多个角色既互斥又析取强制，Barker符号使用排他弧，但每个角色显示为强制（实线）。例如，在[图 8.13](#Ch008_309-346_B9780443237904000177.xhtml#f0070)(a)中，每个账户由一个人或一家公司拥有，但不能两者兼有。

![图 8.13 (a) Barker符号和(b) ORM中的异或约束。](images/B9780443237904000177/f08-13-9780443237904.jpg)

[图 8.13](#Ch008_309-346_B9780443237904000177.xhtml#B-f0070) (a) Barker符号和(b) ORM中的异或约束。

这种符号容易误导，因为它违反了语言设计中的正交性原则。单独来看，关联“Account owned by Person”的第一个角色似乎是强制的，因为使用了实线。但该角色实际上是可选的，因为叠加排他弧改变了实线的语义，使其表示该角色属于一个析取强制的角色集。

将其与[图 8.13](#Ch008_309-346_B9780443237904000177.xhtml#f0070)(b)所示的等价ORM模型进行对比。在这里，排除约束`⊗`与析取强制（包含性或）约束`⊙`正交组合，产生异或约束，此处通过将一个约束符号叠加在另一个之上形成的“救生圈”符号显示。

ORM符号清楚地表明每个角色单独来看都是可选的，并且异或约束是包含性或约束和排除约束的组合。假设我们修改业务，使得同一个账户可以同时由一个人和一家公司拥有。仅从模型中移除排除约束，就会留下包含性或约束`⊙`，即每个账户由一个人或公司拥有。像UML一样，Barker ER符号甚至没有包含性或约束的符号，因此无法绘制此图，也无法绘制实践中发生的许多其他此类情况。

在Barker符号中，一个角色最多只能出现在一个排他弧中。ORM没有此限制。例如，在[图 8.14](#Ch008_309-346_B9780443237904000177.xhtml#f0075)(a)中，没有学生既是ethnic又是aboriginal，也没有学生既是aboriginal又是migrant（这些规则来自澳大利亚的一个学生记录系统）。即使Barker符号支持一元，这种情况也无法用排他弧处理。像UML一样，Barker ER不提供角色序列上排除约束的图形符号。例如，它无法捕获[图 8.14](#Ch008_309-346_B9780443237904000177.xhtml#f0075)(b)中的ORM成对排除约束，该约束声明编写书籍的人不得评审同一本书。此类规则非常常见。此外，Barker符号完全无法表达任何ORM子集或等值约束，即使是在简单角色上。
