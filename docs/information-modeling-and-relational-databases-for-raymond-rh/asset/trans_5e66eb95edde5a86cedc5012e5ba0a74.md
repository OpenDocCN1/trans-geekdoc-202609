
在 [Fig. 10.26](#Ch010_401-479_B9780443237904000244.xhtml#f0135)(c) 的 Barker ER 解决方案中，添加了一个 `visit-id` 属性，“#” 将其标记为主标识符，并移除了关联线上的短划线。Barker ER 没有备用标识符的表示法，因此现在两个外部唯一性约束都丢失了。

第三种方法是*引入序数作为标识符的一部分*。在这里，该数字用于计算同一员工访问同一国家的次数。例如，您对荷兰的第一次访问与第二次访问仅通过在确定性描述中包含“第一”和“第二”来区分。该访问编号包含在 [Fig. 10.27](#Ch010_401-479_B9780443237904000244.xhtml#f0140) 的模型中。例如，员工 1002 对荷兰的第一次和第二次访问分别映射到元组（“1002”、“NL”、1）和（“1002”、“NL”、2）。

在 UML 中，第四种方法是在 [Fig. 10.24](#Ch010_401-479_B9780443237904000244.xhtml#f0125)(b) 的关联端标记 `{nonunique}`，这样关联的实例就是一组 (员工, 国家) 对。然后代理标识符提供访问标识符。虽然这是允许的，但这种方法是亚概念化的，因为访问标识符不再是人类交流的一部分。

虽然我们现在已经介绍了最常见的时序数据模型模式，但在实践中可能会出现其他复杂性，需要进一步分析。到目前为止，我们的约束都是*静态的*——它们适用于对业务领域建模的信息系统的每个状态，并且可以通过单独检查每个状态来验证（例如，每个人最多只在一个日期出生）。

*动态约束*至少引用两个状态，这些状态可能是连续的（例如，员工的职级不得降级）或相隔一段时间的（例如，发票应在开具后 30 天内支付）。

UML 通过图表（例如状态机和活动图，将在后续章节讨论）以及 OCL 中动态规则的文本表述来支持动态约束。除了 Barker ER 中的不可转移设置外，工业级 ER 不提供对动态约束的支持。ORM 允许将动态规则作为文本注释添加，并可为其提供形式语义。人们已经为 ER 和 ORM 提出了各种动态规则扩展，但到目前为止，这些尚未进入流行的建模工具。

我们现在简要勾勒一些向 ORM 添加动态规则支持的方法，首先关注功能事实类型实例的更新。[Fig. 10.28](#Ch010_401-479_B9780443237904000244.xhtml#f0145) 中的事实类型用于存储每位员工的*当前*薪水。

![Fig. 10.28 An ORM model with a functional fact type.](images/B9780443237904000244/f10-28-9780443237904.jpg)

[Fig. 10.28](#Ch010_401-479_B9780443237904000244.xhtml#B-f0145) 一个包含功能事实类型的 ORM 模型。

在任何给定时间，一名员工只有一份薪水，但随着时间的推移，一名员工可能有许多不同的薪水。假设业务希望强制执行这样一项政策：当更新员工薪水时，薪水绝不能减少。这种跨*连续状态*的动态约束也称为*转换约束*。

简单的转换约束可以使用具有预定义语义的保留字，通过*文本规则*正式声明。例如，分别使用“**old**”和“**new**”（或“**previous**”和“**next**”）来引用基本事务之前和之后的紧邻状态，我们可以通过以下任一方式定义一条防止薪水减少的规则。该约束的上下文是对象类型 Employee：

```
For each Employee,               Context Employeenew salary >= existing old salary.     new salary >= existing old salary.
```

刚才给出的示例涉及有序数量上的简单数值比较。当连续状态之间的关系更复杂时，通常可以使用*状态转换表*或*状态转换图*来指定。

[Fig. 10.29](#Ch010_401-479_B9780443237904000244.xhtml#f0150)(a) 显示了一个状态转换表，用于第 2 章前面考虑的婚姻状况示例。这里，“1”表示可能的转换，“0”表示不可能的转换。

![Fig. 10.29 Three state transition notations indicating possible transitions.](images/B9780443237904000244/f10-29-9780443237904.jpg)

[Fig. 10.29](#Ch010_401-479_B9780443237904000244.xhtml#B-f0150) 三种指示可能转换的状态转换表示法。

[Fig. 10.29](#Ch010_401-479_B9780443237904000244.xhtml#f0150)(b) 和 (c) 以状态转换图的形式列出了可能的婚姻状况变化。展示了两种常用表示法。在 [Fig. 10.29](#Ch010_401-479_B9780443237904000244.xhtml#f0150)(a) 中，每个状态显示为命名的水平条，允许的转换描绘为垂直箭头。在 [Fig. 10.29](#Ch010_401-479_B9780443237904000244.xhtml#f0150)(b) 中，每个状态显示为命名的圆角矩形。

鉴于 ORM 事实类型 Employee has MaritalStatus，转换约束也可以指定为动态规则的文本形式：

```
Context: Employeein case old maritalStatus =     ‘single’:   new maritalStatus = ‘married’
```

```
     ‘married’:  new maritalStatus in (‘widowed’, ‘divorced’)     ‘widowed’: new maritalStatus = ‘married’     ‘divorced’: new maritalStatus = ‘married’end cases
```

另一种可能的方法是允许使用具有预定义语义的*保留谓词*进行 ORM 扩展。例如，保留谓词“may change to”可应用于各种对象类型，以约束其从一个状态到下一个状态的变化。利用这一想法，[Fig. 10.30](#Ch010_401-479_B9780443237904000244.xhtml#f0155) 中的事实表可用于声明可能的婚姻状况转换。这实际上将元数据（在本例中为约束）降级为对象数据，从而简化了模式演化，因为转换规则的变更现在是数据变更而非模式变更。请注意，前面考虑的薪水规则无法用这种方式指定，因为其公式涉及运算符，而不仅仅是值。
