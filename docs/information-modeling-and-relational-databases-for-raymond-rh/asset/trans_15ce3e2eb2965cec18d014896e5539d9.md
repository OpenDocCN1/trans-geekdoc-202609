

## RIDL 和 LISA-D

```
FOR EACH o1, o2 IN Officer born-in Year < 1950 DO
    IF Rank OF o1 = Rank OF o2
        THEN LIST o1, o2
    END-IF
END-FOR
```

最初的 RIDL 软件将 RIDL 查询映射为内部语句，这些语句可直接在一些早期的 Control Data 计算机上执行。在后来的几年里，RIDL 的数据定义部分在 RIDL* 工具中以图形方式实现，但查询组件不受支持。

另一种 ORM 查询语言是信息结构和访问描述语言（LISA-D）。尽管它非常有表现力，但对最终用户来说在技术上具有挑战性，且目前缺乏工具支持（[ter Hofstede et al., 1996](#Ch018_935-1005_B9780443237904000104.xhtml#bb1245)）。

## OSM-QL

与 ORM 一样，面向对象系统建模（OSM）方法避免将属性作为基本构造。基于这种方法，开发了用于图形查询语言 OSM-QL 的学术原型（[Embley et al., 1996](#Ch018_935-1005_B9780443237904000104.xhtml#bb0380)）。对于任何给定的查询，用户选择概念模式的相关部分，并用限制条件注释生成的子模式图来构建查询。通过添加频率约束“0”来处理否定，并通过子类型联合运算符引入析取。通过单击相关的对象节点，然后单击标记为输出按钮来完成投影。

## ConQuer 和 ActiveQuery

另一种 ORM 查询语言是 **ConQuer**（名称源于“CONceptual QUERy”）。ConQuer 比 OSM-QL 更有表现力，且对新手用户更容易。其工具实现将概念查询转换为各种后端 DBMS 的 SQL 查询，并且不要求用户熟悉概念模式或 ORM 图符号。ConQuer 的第一个版本在 InfoAssistant 中发布（[Bloesch and Halpin, 1996](#Ch018_935-1005_B9780443237904000104.xhtml#bb0110)）。该版本的反馈导致对语言和用户界面进行了重新设计，以提高表现力和可用性，从而产生了一个名为 ActiveQuery 的工具（[Bloesch and Halpin, 1997](#Ch018_935-1005_B9780443237904000104.xhtml#bb0115)）。典型查询只需单击鼠标选择对象并添加条件即可构建。ActiveQuery 技术后来被微软收购。

对 ConQuer 技术的基本了解将有助于深入了解概念查询环境。ConQuer 语言及其工具支持的设计旨在实现表现力、清晰度、简洁性、语义稳定性和语义相关性。这些设计原则在 [Section 3.1](#Ch003_59-110_B9780443237904000037.xhtml#s0010) 中进行了解释。ConQuer 查询只能应用于 ORM 模式。使用软件工具，可以直接输入 ORM 模式，或者从现有的逻辑模式（例如关系或对象关系模式）反向工程生成。虽然反向工程是自动的，但人工的某些改进可以提高可读性（例如，为谓词生成的默认名称并不总是像人工提供的那样自然）。

尽管 ConQuer 查询基于 ORM，但用户不需要熟悉 ORM 或其符号。ConQuer 查询以文本（大纲）形式（基本上作为连接对象的谓词树）列出，底层约束被隐藏，因为它们不影响查询的含义。

使用 ActiveQuery，用户可以在不了解模式的情况下构建查询。打开模型时，会向用户显示一个对象选取列表。当将对象类型拖动到查询窗格时，另一个窗格会显示该对象在模型中扮演的角色。用户拖动感兴趣的任何关系。单击这些关系中的对象类型会显示其角色，用户可以拖动感兴趣的角色，依此类推。通过这种方式，用户可以快速声明穿越信息空间的查询路径，而无需任何底层数据结构的先验知识。用户也可以最初拖动多个对象类型。然后利用底层模型的结构自动推断出穿越信息空间的合理路径，这称为 **point-to-point query**。

要显示的项目用勾选标记“✓”指示。这些勾选标记可根据需要切换开/关。查询路径可以通过使用运算符和条件以各种方式进行限制。作为一个简单的例子，假设一家公司在世界各地的几个城市设有分支机构。现在，考虑查询：列出居住在 52 号分支机构所在城市的每位员工。这可以在 ConQuer 中这样列出：

该查询的隐式形式可以展开以显示引用方案（例如 `EmployeeNr`、`BranchNr`），并且可以在“52”前包含等号。因为任何 ConQuer 查询都对应于 ORM 模式中的合格路径，其中所有对象类型和谓词都定义良好，所以查询的含义基本上是透明的。ActiveQuery 还会生成查询的英文口语化表达，以防有任何疑问。这确保了 **语义清晰性**。

因为 ORM 对象类型是语义域，它们充当连接模式的语义“胶水”。这不仅促进了强类型，还促进了穿越信息空间的查询导航，使连接能够以最自然的方式可视化（回顾 [Section 4.6](#Ch004_111-158_B9780443237904000232.xhtml#s0055)）。查询 Q1 的底层 ORM 模式片段显示在 [Fig. 18.5](#Ch018_935-1005_B9780443237904000104.xhtml#f0030) 的阴影路径中，以及 City 的标识方案。

请注意 City 如何在此查询中用作连接对象类型。如果改用属性，查询构建会变得更加繁琐。如果允许复合属性，我们可能会使用 **List** `Employee.empNr` **where** `Employee.city = Branch.city` **and** `Branch.branchNr = 52`。如果不允许，我们可能不得不采用 **List** `Employee.empNr` **where** `Employee.cityName = Branch.cityName` **and** `Employee.stateCode = Branch.stateCode` **and** `Employee.country = Branch.country` **and** `Branch.branchNr = 52`。除了笨拙之外，这两种基于属性的方法都违反了 **语义相关性** 原则。因为 City 的标识方案与问题无关，所以不应强迫用户显式处理它。

即使我们有一个工具允许我们直接在 ER 或 OO 模型中构建查询，并且该工具显示当前对象类型的属性以便可能同化到查询中（类似于 ActiveQuery 显示高亮对象类型的角色），这也不会像 ORM 那样暴露直接连接。例如，检查 `Employee.city` 并不能告诉我们它与 `Branch.city` 存在某种连接。

在关系层面，我们有两个表：`Employee`（`empNr`、`countryCode`、`stateCode`、`cityName`……）和 `Branch`（`branchNr`、`countryCode`、`stateCode`、`cityName`……）。因为这些表中的城市属性之间没有外键引用来关联，自由文本查询工具依赖于连接连接被显式预先输入到字典中，这是一个有风险的假设。自动揭示所有连接可能性的唯一方法是将域本身作为连接性的基础，这是 ORM 的显著特征之一。
