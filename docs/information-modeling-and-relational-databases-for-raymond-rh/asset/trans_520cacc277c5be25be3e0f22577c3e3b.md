
虽然大多数员工都需要熟悉信息技术，但这些工作人员所需的信息管理任务在数量和复杂性方面存在巨大差异。最初，大多数技术性计算机工作由程序员和系统分析师等计算机专家执行。然而，用户友好型软件的出现以及功能强大、价格低廉的个人计算机的普及，导致了计算能力的重新分配。最终用户现在通常只需极少依赖专业计算机专家，即可执行许多信息管理任务（如电子表格处理）。

这一趋势是让更多用户“驾驭”自己的计算机系统，而不是依赖专家“司机”，但这并不消除对计算机专家的需求。仍然需要使用 C# 和 Java 等语言进行编程。然而，对建模复杂信息系统等高级技能的需求日益增加。

*信息系统工程*领域包含需求分析、数据库设计、用户界面设计和报表编写等子学科。所有这些子领域都涉及信息。数据库设计阶段选择捕获相关信息的底层结构，因此至关重要。

每个关系表都必须命名。此处我们将该表命名为 “Movie”。请在继续阅读前，看看能否发现该设计的问题。

该表包含*冗余*信息。例如，电影 5 标题为 *Crater*、发行于 2023 年、由 Kyle Patrick Alvarez 执导这些事实显示了三次（每位主演对应一次）。我们可能会尝试通过删除 movieTitle、releaseYr 和 director 列中的额外副本来修复此问题，但这会人为地使某些行变得特殊，并引入空值问题。

在本例中，我们选择 movieNr 作为在整个数据库中识别电影的主要方式。此处通过为 movieNr 列添加双下划线来表示，表明它是 Movie 表的*主键*。如果一个表只有一个候选键，单下划线即表示主键。

每部电影只有一个标题、发行年份和导演的约束，通过检查每个电影编号在 Movie 表中仅出现一次来强制执行。每部电影必须有标题、发行年份和导演的约束，通过检查所有电影都出现在 Movie 表中，以及从标题、发行年份和导演列中排除空值来强制执行。在模式中，这通过虚线箭头捕获（表示如果某电影列在 Starred 表中，则必须列在 Movie 表中），并通过不将任何列标记为可选来实现。在关系数据库术语中，该箭头描绘了一个*外键约束*，即 Starred 表中的 movieNr 列是引用 Movie 表主键的外键。Starred 表的主键是其列的组合，此处通过下划线表示。

这些概念和符号将在本书后面详细解释。即使有这个简单的例子，数据库设计也需要谨慎。对于复杂情况，设计问题要困难得多。本书其余部分主要致力于帮助您应对此类挑战。

数据库设计既是一门科学，也是一门艺术。在良好方法的支持下，这一设计过程是一项令人振奋且富有智力满足感的活动，从所生产的数据库应用程序的质量中可获得切实的收益。下一节将解释为何选择对象角色建模（ORM）作为我们的首选建模方法。后续章节提供历史背景并强调必要的沟通技巧。本章以总结和补充说明部分（包括进一步阅读的参考文献）结束。
