
# Column-Oriented Databases

Joins between tables in a column-oriented database are more complex than in the row-oriented case and are likely to have lower performance. An alternative strategy is to consider the usage patterns of the database and define a schema that "prejoins" the relevant tables. This obviously requires additional controls to ensure the integrity of the duplicate data that will inevitably result, but the new table can then be treated in the same way as any other table with respect to a columnar arrangement. The risk here is that this optimization will make the database perform very badly if the usage patterns do not turn out to be as expected.

A major advantage of column-oriented databases is their ability to deal with very large datasets. Their structure lends itself very well to partitioning. An obvious first step is to partition the database vertically so that different columns (or perhaps column families) can be mounted on different servers. There is no need for each of these to be of the same type. Columns that are accessed less frequently can be mounted on less-powerful servers.

Within each vertical partition, there are options for further partitioning in the horizontal direction. A column can be split into shards, which, again, can be mounted on separate servers. Some additional effort is required to direct queries to the relevant shard, but this provides the potential for a huge expansion of capacity.

An additional measure to increase performance is replication: copies of the same data can be stored on multiple servers that can be accessed independently. This requires some kind of automated load-balancing mechanism to share queries evenly among the servers. A concern in replication is maintaining consistency between different copies of (what should be) the same data. However, as already noted, column-oriented databases are most applicable in situations with rare updates but frequent queries. Because updates are scarce in such cases, the consistency problem may be easily manageable in the right type of application.

The following characteristics summarize the features that are likely to be important in an application requiring a column-oriented database:

*   Large amounts of data are involved, corresponding to millions of rows in more traditional row-oriented tables.
*   Efficient use of storage is relevant, for example, in dealing with large amounts of sparse or repetitive data.
*   Database operations are dominated by queries, with few (if any) changes to data once loaded.
*   Queries typically use aggregation functions such as `avg()`, `count()`, `min()`, `max()`, and `sum()`.
*   Each individual query involves only a small number of columns.

If we want to find a generic term to describe applications of column-oriented databases, the most appropriate is probably "analytic", often referred to by the acronym OLAP (online analytic processing). Column orientation is not appropriate for transactional systems, often referred to by the acronym OLTP (online transactional processing). Examples of typical applications include the following:

**Data warehouses and data marts**: These are commonly used to extract insights from existing data. The input is usually created (or updated) by extracting data from transactional systems and reorganizing it into a more appropriate format. Information is added not on a row-by-row basis, but by bulk loading, which can be quite efficient.

**Scientific research**: Scientific research applications can involve complex queries across large datasets, making column-oriented databases a natural fit. Researchers can use these databases to analyze data quickly and efficiently, allowing them to focus on their research rather than on managing data.

**Financial trading**: Financial trading applications often require real-time access to large volumes of data. Column-oriented databases are specifically designed to handle data of this type, allowing traders to access information quickly and accurately.

**Analysis of historical data**: Stored data can be modeled and analyzed using various statistical and logical methods and techniques to gain insights of various types, such as descriptive, exploratory, predictive, diagnostic, and prescriptive viewpoints.

## 17.4 Document Databases

In [Chapter 3](#Ch003_59-110_B9780443237904000037.xhtml), we discussed how reports and other documents can be analyzed and expressed in terms of elementary fact types. Modeling these fact types in ORM, along with the relevant constraints, leads to a model that can form the basis for a database schema. Document databases take a different approach by storing documents directly using their original structure, so, as the name suggests, a database of this type consists of collections of documents. Because no preanalysis of documents is necessary, it seems possible to add any kind of document to any collection without any kind of preparation. In principle, this promises a great deal of flexibility, but in practice, some degree of control is required to have any hope of making the database manageable over its lifetime.

Several document database systems are available, including the following:

*   **MongoDB** is one of the most popular document databases. It stores data in flexible, JSON-like documents and allows for dynamic schemas.
*   **Couchbase** is a distributed NoSQL database that offers high performance and scalability. It is commonly used for applications requiring real-time data updates, caching, and mobile synchronization.
*   **CouchDB** is an open-source document database focused on ease of replication and conflict resolution.
*   Document databases are available from cloud service providers such as **Amazon DocumentDB** and **Google Firestore**.
*   **MarkLogic** is a NoSQL database that supports flexible schema design and stores data in XML or JSON documents. It is commonly used for applications that require complex data modeling and querying.

The examples in this chapter are based on **MongoDB**, though other document database systems have broadly similar capabilities to the ones we will discuss.

Documents are typically expressed using the structural capabilities of **JSON**, previously described in [Chapter 16](#Ch016_831-873_B9780443237904000207.xhtml). Internally, the information storage may adopt **BSON**, a binary form of JSON that incorporates additional metadata to make data scans faster and can also reduce storage requirements, but we will ignore this detail.

A document database is formed from *collections*. Each collection contains *documents* of a similar kind: for example, Products, Orders, Customers, and so on. Each document can contain several *fields*, but the data in a field need not be single-valued as it would be in a normalized relational database—a field can contain a structure that, in turn, can contain other structures and so on.
