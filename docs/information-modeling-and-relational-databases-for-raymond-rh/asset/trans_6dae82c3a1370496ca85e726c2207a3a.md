
# 将流程与数据关联

我们已经了解了如何在概念层面（例如使用 ORM 模式）和逻辑层面（例如使用关系模式）指定数据模型。整体信息系统生命周期还包括其他任务，详见[第 2 章](#Ch002_27-57_B9780443237904000128.xhtml)。[第 15 章](#Ch015_773-830_B9780443237904000190.xhtml)讨论了如何使用 UML 和业务流程模型与符号（BPMN）来指定业务流程。本节简要概述其他设计任务，例如将流程与数据关联、组织大型模型以及指定用户界面。

假设我们需要为一家信用合作社运营的自动取款机（ATM）设计一个信息系统。作为需求分析阶段的一部分，我们确定该系统的四个主要功能是：允许客户进行存款、取款和转账（例如从储蓄账户转至支票账户），以及获取账户余额打印单。在 UML 中，这些功能中的每一个都可被视为一个用例，并包含在用例图中，以提供系统支持的流程概览。然后，我们可以使用 UML 的活动图集或 BPMN 的工作流图来充实这些功能。

假设当客户将信用卡插入 ATM 时，系统会检查该卡是否为其自有卡，如果是，则从卡中读取客户的标识符（客户编号）。同一个账户可供多个客户使用（例如夫妻共同的联名账户），而每个客户都有唯一的客户编号。这样，系统就能追踪究竟是哪位客户进行了任何特定交易。

假设在绘制 `ValidateClient`（验证客户）和 `GetBalance`（获取余额）流程图时，我们发现验证客户并打印所请求余额的组合流程涉及来自客户的两个输入数据流（`clientNr`、`accountType`）和一个输出数据流（`balance`）给客户。如果将信用合作社的账户数据库系统视为独立于 ATM 的另一个参与者，则可认为它响应从 ATM 发送的请求（例如 SQL 查询）来提供余额详情。

在如此高层级的视图中，很少或不提供关于数据存储结构的细节，也不提供关于流程如何找到相关数据的细节。由于这些细节尚未定义，流程图往往无法为数据视角建模提供充分的基础。尽管存在这种非正式性，它们在阐明论域（UoD）以及识别应包含在应用程序屏幕菜单中的功能方面仍很有用。确实，带有直观图标的普通漫画在需求分析的早期阶段，对于建模者与领域专家之间的沟通非常有用。

原则上，流程模型可以逐步细化为基本事务，从而暴露底层的事实类型。然而，对于数据密集型系统，这种方法实在太耗时，且往往不稳定，因为业务流程的变化速度通常远快于底层数据。为了加快数据建模进程，我们应该用数据用例为其播种，并应用诸如 ORM 概念模式设计程序（CSDP）之类的建模程序。如果已有示例，请使用它们。如果没有，请与领域专家坐下来生成它们。这些可以是表格、表单、图表或任何形式。到现在为止，你应该已具备口语化技能，能够妥善地对这些各种形式执行 CSDP 步骤 1，而且由于客户发现实例层面更易于处理，这是最稳妥的途径。此外，这样做你已经开始原型化客户想要的外部屏幕和报表。

流程模型应正式地连接到数据模型。最好在确定概念和逻辑数据模型之后进行此操作。虽然熟练的建模者可以将流程模型细化为数据模型，但这种方法容易出错。例如，假设我们跳过概念数据建模，转而将前面提到的用于验证客户和获取余额的流程模型细化为以下表方案和 SQL 过程。这里，“&1”和“&2”是输入参数或占位符。执行过程时，实际值会被输入到这些参数中。

```
D1: Account ( clientNr, accountType, balance )
P1: select balance from Account where clientNr = &1 and accountType = &2
```

你能发现这个设计潜在的问题吗？如果你为 D1 绘制一个概念模式，就最容易看出问题。这在[图 18.13](#Ch018_935-1005_B9780443237904000104.xhtml#f0070)中有描绘。每个账户有一个或多个用户，且恰好有一个账户类型（例如 L = 贷款，C = 支票账户，S1 = 主储蓄账户，S2 = 其他储蓄账户）。这没问题。问题在于 Account 的标识方案。虽然 `clientNr` 和 `accountType` 的组合确实能在该论域中标识一个账户，但不应将其用作优先参考，因为（`clientNr`、`accountType`）对与账户的关系不是 1:1 的。

![图 18.13 账户的优先参考方案不安全。](images/B9780443237904000104/f18-13-9780443237904.jpg)

[图 18.13](#Ch018_935-1005_B9780443237904000104.xhtml#B-f0070) 账户的优先参考方案不安全。

例如，假设你配偶的 `clientNr` 是 1001，你的是 1002，你们共享一个主储蓄账户（类型 = “S1”）。这个联名账户既可由（1001，“S1”）引用，也可由（1002，“S1”）引用。这不适合优先参考。例如，D1 使用的 `Account` 表将接受填充数据 {(1001, “S1”, 9000), (1002, “S1”, 0)}。但这意味着同一个账户有两个不同的余额，这说不通。显而易见的解决方案是引入另一个优先标识符（例如 `accountNr`），如[图 18.14](#Ch018_935-1005_B9780443237904000104.xhtml#f0075)所示。该图还包含新的关系模式（D1′）和计算余额的新过程（P1′）。

![图 18.14 账户的优先参考方案现在安全了。](images/B9780443237904000104/f18-14-9780443237904.jpg)

[图 18.14](#Ch018_935-1005_B9780443237904000104.xhtml#B-f0075) 账户的优先参考方案现在安全了。

这个例子经过了简化（例如练习 6.4 讨论了余额如何从账户交易中派生），但它确实说明了概念建模如何促进正确的数据设计，以及除非流程所操作的数据结构被准确定义，否则详细的流程规范用处不大。

在实践中，通过检查与该用例或会计系统相关用例（例如余额单）关联的其他数据示例，应该显而易见地发现应使用 `accountNr` 进行优先参考。正如[第 5.3 节](#Ch005_159-209_B9780443237904000098.xhtml#s0025)所讨论的，在特定上下文中的参考方案可能不适合全局应用。在与领域专家讨论数据用例时请记住这一点。

虽然严谨的流程模型最好建立在数据模型之上，但流程概览作为数据建模的前驱很有用，特别是当应用程序很大或仅被模糊理解时。首先弄清应用程序的功能通常很有帮助。

从总体目标出发，可以使用各种图系统地指定应用程序的主要功能和流程。这种分析有助于我们将论域划分为大小可控的连贯模块，并有助于在不存在信息示例时指定它们。此时，可对每个模块应用 CSDP 步骤 1。
