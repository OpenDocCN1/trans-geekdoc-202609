
# 关系模式

**关系模式**（relational schema，或关系数据库模式）是一组关系表定义、约束，或许还有推导规则。您可能希望回顾[第 1.3 节](#Ch001_1-25_B9780443237904000062.xhtml#s0020)和[第 2.3 节](#Ch002_27-57_B9780443237904000128.xhtml#s0020)，那里讨论了基本概念。单个关系表的结构称为**表模式**（table scheme）或关系变量。这基本上是一组命名的**属性**（列），它们的值取自数据**域**。每个表模式可以由一组未命名的数据**元组**（行）填充，但填充内容不是表模式本身的一部分。

## 表模式的表示法

存在许多用于表模式的**表示法**。`NORMA`工具使用垂直布局，其中列名垂直列出。为了节省空间并便于讨论填充内容，本书通常使用**水平布局**，即表名位于一个用逗号分隔的括号列名列表之前。如果需要，可以在列名后使用冒号分隔符显示域名。

例如，忽略约束，[图 11.1](#Ch011_481-537_B9780443237904000141.xhtml#f0010)(a) 中的 ORM 概念模式映射为表模式 `Employee( empNr: EmployeeNr, salary: Money, tax: Money )`。此处表名为“Employee”，属性 `empNr` 基于域 `EmployeeNr`，属性 `salary` 和 `tax` 均基于域 `Money`。

![图 11.1 将 ORM 模式映射为关系模式（省略约束）。](images/B9780443237904000141/f11-01-9780443237904.jpg)

[图 11.1](#Ch011_481-537_B9780443237904000141.xhtml#B-f0010) 将 ORM 模式映射为关系模式（省略约束）。

因为基于单位的参考模式 USD 基于单位维度 `Money`，所以 ORM 模式也可以像[图 11.1](#Ch011_481-537_B9780443237904000141.xhtml#f0010)(b) 那样显示。

我们采用的惯例是：表名和域名以大写字母开头，属性名以小写字母开头。这种大小写惯例类似于 UML，且相当流行。无论您选择哪种大小写惯例，坚持使用它都将有助于使您的模式更具可读性。

使用水平布局时，我们通常用斜体书写表名。我们也倾向于连接名称组件，后续组件首字母大写（例如 `empNr`），而不是使用下划线或空格等分隔符（例如 `emp_nr` 或“emp nr”）。正如下一章所讨论的，SQL 标准要求包含空格字符的名称必须用双引号括起来。

建模工具通常允许您控制此类名称的生成方式。例如，`NORMA`工具允许您声明“Employee”在列名中缩写为“Emp”但不在表名中缩写，并且它可以利用角色名来确定列名。您可以选择自己的风格并坚持使用。为了紧凑，列出表模式时通常省略域名，例如 `Employee( empNr, salary, tax )`。

理论上，关系模型支持语义域，这基本上对应于 ORM 概念对象类型。1992 年之前，SQL 标准要求每个属性必须直接定义在数值或字符串数据类型上。例如：

```
Person ( surname: varchar(20), city: varchar(20), height: smallint, weight: smallint )
```

这可能导致语义上的胡扯，例如比较人和城市，或比较身高和体重。SQL 标准现在允许属性定义在用户定义的语法域上，这些域指定底层数据类型，并可选择性地指定值列表和/或默认值。标准 SQL 中的底层数据类型支持字符串、数字、日期、时间和位串，但不支持 `Money`，后者是用数值数据类型定义的，例如 **`decimal`**(9,2)。SQL:1999 引入了用户定义类型，可用作语义域。然而，许多商业 SQL 仍不支持用户定义的域或类型，因此从这一点开始，我们通常会忽略域的细节。

## 关系模式中的约束表示法

现在让我们考虑关系模式中用于指定**约束**的主要表示法。后续章节将讨论如何将事实类型分组到表模式中，以及如何更详细地映射约束和规则。

使用水平布局时，关系列上的**唯一性约束**通过下划线表示。表的**超键**（superkey）是一个或多个列的集合，其条目必须唯一，从而提供了一种识别表中行的方法。**候选键**（candidate key）是**最小**超键。换句话说，如果从复合键中移除一个属性，剩余属性不再受唯一性约束约束。如果只有一个候选键，它自动成为**主键**（primary key）。例如，我们可以指示 `empNr` 是 `Employee` 表的主键，如下所示：

```
Employee ( empNr, salary, tax )
```

如果存在多个候选键，必须选择其中一个作为主键。其他的则称为“**备选键**”（alternate keys）或“**次要键**”（secondary keys）。

如果存在备选键，主键用双下划线标记。例如，假设我们还记录每个员工的姓名和部门，且员工姓名与部门的组合是唯一的。主键和次要键可以如下所示：

```
Employee ( empNr, empName, deptCode, salary, tax )
```

列出列的顺序在语义上无关紧要，因为每个列都有一个在其表中唯一的名称。如果复合键中的列未连续列出，则用虚线连接下划线，以表明应用的是单个复合唯一性约束，而不是多个简单约束。例如，前面的 `Employee` 表模式也可以如下显示：

不允许空值的列被称为**强制性**的（针对其表）。允许空值的列被称为*可选*的。对于水平布局，本书采用以下惯例：可选列用*方括号*括起；除非标记为可选，否则列在其表中是强制性的。这种做法与著名的巴科斯-诺尔范式（BNF）表示法一致。例如，因为纳税是可选的，前面的 ORM 模式映射为以下表模式，其中 `tax` 列为可选（允许空值）：

```
Employee ( empNr, salary, [tax] )
```

此映射在[图 11.2](#Ch011_481-537_B9780443237904000141.xhtml#f0015) 中通过示例填充进行了说明。概念填充包含三个基本事实：员工 101 的薪水为 80,000 美元（USD），员工 102 的薪水为 30,000 美元，员工 101 缴纳了 30,000 美元的税。员工 102 尚未记录纳税情况。

关系表的每一行表达一个或多个基本事实或存在性事实。因为这两种事实类型被分组到同一个表中，所以每一行表达一两个事实。

第一行记录了关于员工 101 的薪水和纳税事实。第二行记录了关于员工 102 的薪水事实。第二行还包含一个空值（此处显示为“？”），表示员工 102 缺少纳税事实。行的显示顺序在语义上无关紧要。
