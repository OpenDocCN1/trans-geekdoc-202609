

## 映射强制角色约束

[图 11.3](#Ch011_481-537_B9780443237904000141.xhtml#f0020)(a) 在 [图 11.1](#Ch011_481-537_B9780443237904000141.xhtml#f0010) 的基础上增加了两个事实类型。现在记录每位员工的性别以及员工驾驶的汽车。仅当对象类型 *O* 扮演的每个其他角色的总体必须是角色 *r* 总体的子集时，角色 *r* 对对象类型 *O* 才是强制的。因此，一个对象类型的每个可选角色都对该对象类型的每个强制角色有一个*隐含子集约束*。[图 11.3](#Ch011_481-537_B9780443237904000141.xhtml#f0020)(b) 显示了从 `Employee` 的每个可选角色到 `Employee` 的一个强制角色的隐含子集约束（绿色标注）。强制角色之间隐含相等约束，但与我们的讨论无关。

![图 11.3 子集约束由强制角色约束隐含。](images/B9780443237904000141/f11-03-9780443237904.jpg)

[图 11.3](#Ch011_481-537_B9780443237904000141.xhtml#B-f0020) 子集约束由强制角色约束隐含。

如果一个对象类型扮演的所有角色都映射到同一张表，其强制角色只需指定为强制列即可。然而，关系模型通常要求关于同一对象的不同事实存储在不同的表中。一般来说，*强制角色约束通过使其列在各自的表中成为强制列来捕获，并从包含该对象类型事实的其他表（如果有）运行子集约束*。

正如下一节所讨论的，*m:n* 性质的 `drives` 事实类型要求将其映射到不同于其他三个事实类型的关系表中。因此，`Employee` 的信息分散在 [图 11.3](#Ch011_481-537_B9780443237904000141.xhtml#f0020)(c) 所示的两个关系表中。在这里，强制角色约束仅被部分捕获——没有任何机制阻止我们在 `Drives` 表中输入 `Employee` 表中不存在的员工编号。

那么我们如何映射概念层面的强制角色约束呢？

`salary`、`gender` 和 `tax` 这三个 *n*:1 事实类型被归组到 `Employee` 表中。强制的 `salary` 和 `gender` 谓词映射为强制列，而 `tax` 角色上的子集约束通过使 `tax` 成为 `Employee` 表中唯一的可选列来捕获。`drives` 事实类型映射到一个单独的表。

为了捕获来自 `drives` 角色的子集约束，我们向关系模式添加一个从 `Drives` 表的 `empNr` 列到 `Employee` 表的 `empNr` 列的子集约束。在水平布局中，该子集约束描绘为虚线箭头，如 [图 11.3](#Ch011_481-537_B9780443237904000141.xhtml#f0020)(c) 所示。这确保了任何被列为驾驶汽车的员工也列在 `Employee` 表中，在那里 `gender` 和 `salary` 被强制记录。

在关系术语中，该子集约束是一个*参照完整性约束*，`Drives` 表的 `empNr` 属性是一个*外键*，它*引用* `Employee` 表的 `empNr` 属性。在标准关系模型中，外键只能引用主键，但 SQL 也允许外键以候选键为目标。

关系模型有两条基本完整性规则。*实体完整性规则*要求主键不包含空值（即主键中的每一列都是其表的强制列）。*参照完整性规则*基本上规定外键的每个非空值必须匹配某个主键的值。关系模型还允许用户定义约束和派生规则。

为了体会关系模式在实践中可能如何实现，让我们稍微扩展一下示例并将其映射到 SQL。[图 11.4](#Ch011_481-537_B9780443237904000141.xhtml#f0025) 增加了事实类型以记录每位员工的部门和姓名。它还增加了除内部唯一性约束和简单强制约束之外的三个约束。员工姓名在给定部门内是唯一的，可能的性别代码为 "M" 和 "F"，并且每位员工最多驾驶三辆车。

员工姓名和部门上的外部唯一性约束映射为跨越两个属性的复合唯一性约束。在水平布局中，如前所述，通过为相关列加下划线来表示。性别代码上的值约束和每位员工最多驾驶三辆车的频率约束通过使用类 ORM 符号标注表模式来在水平布局中指定，如 [图 11.5](#Ch011_481-537_B9780443237904000141.xhtml#f0030)(a) 所示。

![图 11.5 (a) 水平布局和 (b, c) 某些垂直布局的关系模式。](images/B9780443237904000141/f11-05-9780443237904.jpg)

[图 11.5](#Ch011_481-537_B9780443237904000141.xhtml#B-f0030) (a) 水平布局和 (b, c) 某些垂直布局的关系模式。

大多数 ORM 约束符号可用类似方式用于设计关系模式。有时我们会调整这些符号或引入新符号（稍后讨论）。虽然我们的半图形化符号紧凑且直观，但商业工具通常使用*垂直布局*以图解方式描绘关系模式，并辅以存储在属性表或代码中的文本规则。虽然垂直布局占用更多空间，但对于列数较多的表很方便。

[图 11.5](#Ch011_481-537_B9780443237904000141.xhtml#f0030)(b) 显示了 Visio 绘制相同示例的方式之一。这里，表名列在顶部区室，列名垂直列在下方。强制列以粗体显示，因此 `tax` 是唯一的可选列。主键列加下划线并标注 "PK"。

如果需要，主键也可以在单独的区室中显示。外键标注为 "FK*n*" (*n* > 0)，箭头描绘从外键到目标表的子集约束。非主键唯一性约束用 "U*n*" 表示。性别上的值约束和 `carRegNr` 上的频率约束未在图上显示，但可在关联代码中检查。

[图 11.5](#Ch011_481-537_B9780443237904000141.xhtml#f0030)(c) 显示了 Microsoft SQL Server 绘制相同示例的一种方式。这里，主键列用键符号标记，外键约束描绘为带有键符号（目标端）和 "∞"（无穷大，表示源端基数为 "多"）的关系线。列的强制或可选性质分别由 `Allow Nulls` 复选框的缺失或存在来指示。其他约束可在关联代码中检查。

没有统一采用的行业标准用于绘制关系模式图。使用特定的计算机辅助软件工程 (CASE) 工具或 DBMS 时，你需要熟悉其特定的关系符号。

相同的关系模式可按如下方式在 SQL 中指定。保留字以粗体显示，但这不是必需的。为节省书写，多个列基于的域首先声明（`EmpNr` 和 `Money`），且省略约束名称。自 1999 年以来，ISO SQL 标准允许声明类型代替域。

*   ```
    create domain EmpNr smallint;
    ```

*   ```
    create domain Money decimal(9,2);
    ```

*   ```
    create table Employee (
    ```

*   ```
        empNr                         EmpNr                    not null primary key,
    ```

*   ```
          empName                  varchar(30)                    not null,
    ```
