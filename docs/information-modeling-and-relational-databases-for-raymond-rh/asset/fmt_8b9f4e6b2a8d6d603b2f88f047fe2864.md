(3) 从 `R` 表中删除一行，其中 `R.a` 的值也是 `S.a` 中的值。

(4) 更新 `R` 表的一行，将同时也是 `S.a` 中值的 `R.a` 值进行替换。

我们不必将子集约束声明为 `S.a` **references** `R.a`，而是可以通过编写触发器代码来处理这四种情况，从而强制执行该约束。**触发器** 基本上是为单个表定义的一段过程化代码，每当该表发生指定类型的事件（插入、删除或更新）时，就会执行相应的动作。我们将在本章稍后更详细地介绍触发器。SQL:1999 包含了一种功能齐全的过程化触发器语言，其能力相当于典型的第三代编程语言。

虽然触发器对于强制执行规则（如约束或派生规则）非常有用，但如果系统支持该规则的声明式版本，通常首选声明式方法。首先，规则的声明式版本更容易理解，因此也更容易与领域专家进行验证。其次，声明式版本比过程式版本更简短、更易于编写。例如，声明 `S.a` **references** `R.a` 与相应触发器的代码相比微不足道。最后，系统通常能比过程式代码更好地优化声明式代码。话虽如此，仍有许多情况只能通过触发器或存储过程来实现系统执行某些动作。直到最近，参照动作还属于这一类。

**参照动作** 是针对参照完整性约束违规而采取的行动。在 SQL-89 中，如果尝试的更新（插入/删除/更新）违反了外键约束，该更新会被直接拒绝；换句话说，不采取任何行动。在 SQL-92 中，可以通过在 **references** 子句末尾声明适当的参照动作，用其他选项替换更新和删除操作的这种“无动作”默认值。SQL-92 还允许使用 **match** 子句，提供 **full** 或 **partial** 选项，以便更精细地控制空值匹配。SQL:1999 增加了 **simple** 选项，允许显式声明匹配的默认选项，但除此之外，对 **references** 子句使用相同的语法，其完整语法如下：

```
references table [ (col-list) ][ match { full | partial | simple } ][ delete-action [ update-action ] | update-action [ delete-action ] ]
```

其中 `delete-action` 的语法为：
`on delete` { `no action` | `cascade` | `set null` | `set default` }

`update-action` 的语法为：
`on update` { `no action` | `cascade` | `set null` | `set default` }

如果尝试通过插入、删除或更新操作更改数据库，且该操作会违反参照约束，默认的 **no action** 选项将拒绝该更改。其他三个参照动作选项接受该更改，但也会采取一些补偿措施以保持数据库一致性。**cascade** 选项将更改传播到所有引用的外键值；**set null** 将相关外键值设为 null；**set default** 将相关外键值设为列默认值。例如，考虑以下关系模式：

SQL-92 引入了 **match** 操作符作为布尔运算符，用于测试元组是否属于一个元组集合，即 `(*a*[1], …, *a*[n])` ∈ `{(*b*[1], …, *b*[n]), …}`？除布尔特性外，它是 **in** 操作符的推广，可用于以下形式的搜索条件：`(*a*[1], …, *a*[n])` **match** [`unique`] [`full` | `partial` | `simple`] `(*subquery*)`。**unique** 选项要求元组恰好匹配一行。默认情况下，或声明了 **simple** 时，如果所有值 `*a*[1]`..`*a*[n]` 都匹配或*部分*为 null，匹配操作返回 True；否则返回 False。如果指定了 **full**，当所有值 `*a*[1]`..`*a*[n]` 都匹配或*全部*为 null 时，匹配操作返回 True；否则返回 False。如果指定了 **partial**，当所有*非空*值都匹配时，匹配操作返回 True；否则返回 False。**match** 操作符也可用于 **references** 子句中，方式类似。虽然 SQL-89 的 **references** 子句语法被广泛支持，但大多数 SQL 方言对 SQL-92 或 SQL:1999 中进一步的参照语法支持较少。

## 修改表定义

创建并填充基表后，我们可能希望更改其定义。这在 SQL-89 中是不可能的，但 SQL-92 允许使用 **alter table** 语句更改表模式。SQL:1999 稍微扩展了此功能以适应列作用域。每项更改需要单独的语句。基本语法如下：

```
alter table tablename add [ column ] col-defn  | alter [ column ] colname set default-defn | drop default | drop [ column ] colname restrict | cascade | add table-constraint-defn  | drop constraint constraint-name restrict | cascade
```

如果指定了 **restrict** 且该列在约束或视图定义中被引用，则不允许删除该列。**cascade** 选项会导致其他定义也被删除。商业 SQL 通常不支持删除列或约束的 **restrict** 或 **cascade** 选项。

尽管标准禁止更改列的数据类型，但某些方言允许将列的数据类型更改为“更大的类型”，例如将 `roomNr` 列从 `char(2)` 改为 `char(4)`。许多供应商不支持某些 alter 操作，例如 **drop column**。为简化自动建表，某些供应商倾向于在 **alter table** 语句中添加大多数表约束。以下示例不言自明：

```
alter table Person add column email_address varchar(20)
alter table Person add foreign key starsign references starsignPeriod
```

SQL-92 允许使用 **drop table** 语句从数据库中删除表（包括其数据）。虽然 SQL-89 不允许这样做，但所有供应商都支持该功能。语法如下：

```
drop table tablename cascade | restrict
```

如果指定了 **restrict** 且该表在约束或视图定义中被引用，则不允许删除该表。**cascade** 选项会导致其他定义也被删除。大多数商业 SQL 此处不要求 cascade/restrict。
