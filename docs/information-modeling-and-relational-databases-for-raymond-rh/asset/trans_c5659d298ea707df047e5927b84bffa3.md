
# 10.4 集合类型

数据建模方法对*集合类型*的支持程度差异很大。虽然实现目标通常支持此类类型（例如，SQL:2003 支持数组、行类型和包），但高层数据建模方法通常不提供直接支持，或仅提供非常有限的直接支持。即使没有为事实集合提供直接支持，也可以用基本事实来建模相同的信息，因此集合类型支持的问题关乎便利性而非表达能力。以下集合类型是在概念建模中最常遇到的：

*   集合（无序，无重复）
*   包或多重集（无序，允许重复）
*   有序集合或唯一序列（有序，无重复）
*   序列（有序包）
*   数组（索引序列）
*   模式

工业 ER 不为这些集合提供直接支持。UML 允许将许多此类集合类型指定为带有构造型的类、多值属性或受约束的关联端。尽管大多数版本的 ORM（包括 ORM 2）都是“扁平的”，即它们不为集合提供直接支持，但 ORM 的谓词集合模型（PSM）变体将它们作为一等类型提供了深度支持（ter Hofstede 等人，1993 年）。

虽然在逻辑和物理数据结构中使用集合类型是合理的，但在概念分析中是否应完全使用集合类型，仍然是一个有争议的问题。为构建各种集合类型而添加构造器，需要额外的语言特性，不仅用于声明此类结构，还用于操作它们。有了集合选项，建模者在如何构思模型、更新或查询方面有了更多选择。

我们的经验表明，在开发概念模型时，应极其谨慎地使用集合类型（如果一定要用的话）。构造器的无序使用往往会导致不正确或不完整的解决方案，或忽略不使用集合的更简单的解决方案。请回顾我们在第 9.3 节中关于在概念模型中避免使用多值属性的早期建议。

以下观点被提出以支持在概念层面使用构造器：集合能产生更紧凑的模型；它们能更好地揭示概念模型与使用集合的物理模型之间的联系；并且它们允许直接对未命名结构建模。

## 角色扮演模式

此情况下的一个适当模式是从一个将所有角色析取的超类型开始，然后逐步子类型化为更小的析取，如图 10.34(c) 所示。我们称之为*递减析取模式*。根据业务领域，顶层超类型可能有一个简单的名称（例如，Person）。

一种使用我们称为*一次性角色扮演模式*的替代方法，是为角色的实际扮演创建子类型，如图 10.35 所示。在这里，子类型 `PersonAsChild`、`PersonAsTeenager` 和 `PersonAsAdult` 不是 `Person` 的子类型，而是对象化关联 `LifeRolePlaying` 的子类型，该关联的实例对应于一个人扮演这些角色之一。时间顺序可以通过多种方式添加，例如，通过添加动态约束来限制可能的角色转换，如图 10.35 所示。
