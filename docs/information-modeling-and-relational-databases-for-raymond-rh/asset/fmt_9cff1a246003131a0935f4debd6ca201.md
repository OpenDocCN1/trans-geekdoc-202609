
# XML and ORM Mapping Issues

## Hierarchy Representation in XML

The first issue is that XML obliges us to represent the data as a hierarchy, even if no natural hierarchy exists in the ORM model. This is a consequence of the nesting of elements within elements, which is intrinsic to XML. Consider the tiny ORM model shown in [Fig. 16.5](#Ch016_831-873_B9780443237904000207.xhtml#f0030).

![Fig. 16.5 Student-Course relationship.](images/B9780443237904000207/f16-05-9780443237904.jpg)

[Fig. 16.5](#Ch016_831-873_B9780443237904000207.xhtml#B-f0030) Student-Course relationship.

One option would be to nest Courses under Students.

```
<Model>
    <Student name="Alice" …>
        <Course id="CS101" …> …</Course>
        <Course id="CS104" …> …</Course>
    </Student>
    <Student name="Bob" …>
        <Course id="CS101" …> …</Course>
    </Student>
</Model>
```

But nesting of Students under Courses could be equally valid.

```
<Model>
    <Course id="CS101" …>
        <Student name="Alice" …> … </Student>
        <Student name="Bob" …>… </Student>
    </Course>
    <Course id="CS104" …>
        <Student name="Alice" …> … </Student>
    </Course>
</Model>
```

We could also consider something closer to a relational style, with a Student list, a Course list, and a list of linking Enrolment elements.

```
<Model>
    <Students>
        <Student name="Alice" …> … </Student>
        <Student name="Bob" …>… </Student>
    </Students>
    <Courses>
        <Course id="CS101" …> …</Course>
        <Course id="CS104" …> …</Course>
    </Courses>
    <Enrolments>
        <Enrolment student="Alice" course="CS101"> … </Enrolment>
        <Enrolment student="Alice" course="CS104"> … </Enrolment>
        <Enrolment student="Bob" course="CS101"> … </Enrolment>
    </Enrolments>
</Model>
```

Which of these would be preferable cannot be inferred from the ORM model because the choice depends on external factors such as the intended use of the data and patterns of access.

## Element Attributes vs. Element Content

A second issue is that XML provides two options for storing data: as the value of an element attribute or as the content of an element. The examples above show student name as an attribute, but the following would be an equally valid alternative:

```
<Student>
    <Name>Alice</Name>
    …
</Student>
```

There is no firm rule for deciding between these options, although various guidelines have been suggested, such as reserving attributes for metadata only. Attributes have some limitations that would make elements preferable in some cases, for instance, data that is multivalued or has some inner structure, but for straightforward scalar values either approach could be used.

Although we have been describing the situation with XML, similar issues arise with JSON, which also offers choices about how to represent the data. What all this means is that two different developers mapping the same ORM model may produce very different XML schemas (or JSON schemas).

## Systematic Procedure for XML Rendering

To produce an XML rendering of a relational structure, we can follow a systematic procedure that is straightforward to automate.

Each relational table will map to an element type in XML, which can have a plural tag name (e.g., `<Employees>`). Each of these major element types will be nested under a suitably named root node. These major elements will contain a list of subelements of the relevant type.

Rows in a table will map to subelements with a singular tag name (e.g., `<Employee>`), nested under their parent element (e.g., `<Employees>`). Relational columns map to attributes of their related subelements. A UUID attribute can be added to each subelement for easy identification and cross-referencing.

The result is an XML file similar to the "relational" style in the examples above. Even if this is not the preferred format, it may still be a good first step. Once we have an XML file, it can be transformed into alternative XML structures using appropriate code, perhaps using the XML Stylesheet Language for Transforms (XSLT).

If we need to produce an XML file directly from an ORM schema, we can adapt the approach above by adding some extra steps. First, we follow the Rmap procedure to identify the relational structure corresponding to the ORM schema. Next, we apply the procedure above to this relational structure to define the XML schema elements. Finally, we need to add any required constraints from the ORM schema to the XML schema. This last step is not necessary when producing a data transfer file from a database because we can assume that the appropriate constraints will already have been applied to the data.

Mapping to a JSON schema can follow a similar procedure. Tables become JSON objects, rows become lists of nested objects within the parent types, and column values appear as key-value pairs within the nested object.

## 16.6 Summary

XML is a member of a family of markup languages based on the Standard Generalized Markup Language (SGML). Other languages based on SGML include HTML, though this has now diverged somewhat from its original basis. XML was designed to be easy to parse, initially in the context of web applications, but it is now well established as a general-purpose tool for describing data structure independent of any specific data container. It has become a built-in feature of many applications, though its presence may not be immediately obvious. As examples, the current formats of Microsoft Office files (such as `*.docx`, `*.pptx`, and `*.xlsx`) are based on XML, and the NORMA tool used to create and manage object relational models uses XML in its `*.orm` file format.

A key feature of XML is its extensibility. Unlike HTML, it does not assume predefined tag names, so a schema can be designed to meet any required scenario. If warranted, the schema can be documented in machine-readable form so that an XML document can be validated against the schema definition to ensure that it is consistent. The original schema definition method, inherited from SGML, used DTDs, which are expressed in their own language. Modern usage has moved to the expression of the schema in XML itself, using XML Schema Definition (XSD) or the simpler alternative Relax NG.

The XML definition is controlled by the World Wide Web Consortium (W3C). Several other W3C standards exist within the XML family. In addition to XML Schema, we have already discussed XPath and XQuery in some depth. These allow XML data to be queried in a way that corresponds roughly to the way that the `select` statement is used in querying SQL tables. Other W3C standards include the following:

*   **XSLT** (Extensible Stylesheet Language Transformations) is an XML-based language used to convert an XML document into a different XML schema or into a completely different format such as PDF.
*   **XLink** (XML Linking Language) provides methods for creating internal and external links within XML documents and associating metadata with the links.
*   **XPointer** is based on XPath and supports addressing into the internal structures of XML documents. This can be used to create something equivalent to a foreign key in a relational database.
*   **XHTML** is a somewhat stricter version of HTML with a syntax conforming to XML.
*   **SVG** (Scalable Vector Graphics) is a language for describing two-dimensional vector graphics that allows smooth scaling to different display resolutions.

There are many other XML-based standards produced by W3C and other bodies, perhaps running into hundreds of examples, as well as an uncountable number of private applications. This makes XML probably the most well-established method of defining structured data outside of a database system.
