
# Changeability Restrictions and Derived Data

## Changeability Restrictions

Some traditional data modeling approaches also note some restrictions on changeability. The Barker ER notation includes a diamond to mark a relationship as nontransferable (once an instance of an entity type plays a role with an object, it cannot play this role with another object). Although changeability restrictions can be useful, in practice their application in database settings is limited.

One reason for this is that facts entered into a database might need to be changed. With snapshot data, this is the norm, but even with historical data changes can occur. The most common occurrence is to allow for corrections of mistakes, which might be because we were told the wrong information originally or because we carelessly made a misspelling or typo when entering the data.

In exceptional cases, we might require that mistakes of a certain kind be retained in the database (e.g., for auditing purposes) but be corrected by entering later facts to compensate for the error. This kind of approach makes sense for bank transactions (see [Fig. 9.50](#Ch009_347-399_B9780443237904000013.xhtml#f0255)). For example, if a deposit transaction for $100 was mistakenly entered as $1000, the record of this error is kept, but once the error is detected it can be compensated for by a bank withdrawal of $900. The balance is both derived and stored, and its `readOnly` status is typically implied by the `readOnly` settings on the base attributes, together with a derivation rule.

![Fig. 9.50 All attributes of Transaction are readOnly.](images/B9780443237904000013/f09-50-9780443237904.jpg)

[Fig. 9.50](#Ch009_347-399_B9780443237904000013.xhtml#B-f0255) All attributes of Transaction are readOnly.

Some authors allow changeability to be specified for a class, as an abbreviation for declaring this for all its attributes and opposite association ends ([Booch et al., 1999](#Ch009_347-399_B9780443237904000013.xhtml#bb0120), p. 184). For instance, all the `{readOnly}` constraints in [Fig. 9.50](#Ch009_347-399_B9780443237904000013.xhtml#f0255) might be replaced by a single `{readOnly}` constraint below the name “Transaction”. While this notation is neater, it would be rarely used. Even in this example, we would probably want to allow for the possibility of adding nonfrozen information later (e.g., a transaction might be audited by zero or more auditors).

Changeability settings are useful in the design of program code. Although changeability settings are not yet supported in ORM, which focuses on static constraints, they are being considered in extensions to support dynamic constraints (see next chapter). In the wider picture, being able to completely model security issues (e.g., who has the authority to change what) would provide extra value.

## Ordered Sets and Collection Types

UML allows `{ordered}` and `{unique}` properties to be specified for multivalued attributes and association ends. Because `{unique}` is true by default, the use of `{ordered}` indicates an ordered set (a sequence with no duplicates). For example, [Fig. 9.51](#Ch009_347-399_B9780443237904000013.xhtml#f0260)(a) shows one way of modeling authorship of papers in UML. Each paper has a list of authors, each of whom may appear at most once on the list.

![Fig. 9.51 An ordered set modeled in (a) UML and (b) ORM.](images/B9780443237904000013/f09-51-9780443237904.jpg)

[Fig. 9.51](#Ch009_347-399_B9780443237904000013.xhtml#B-f0260) An ordered set modeled in (a) UML and (b) ORM.

This may be modeled in flat ORM by using a `Position` object type to store the sequential position of authors on the list, as shown in [Fig. 9.51](#Ch009_347-399_B9780443237904000013.xhtml#f0260)(b). The uniqueness constraint on the first two roles declares that for each paper an author occupies at most one position; the constraint covering the first and third roles indicates that for any paper, each position is occupied by at most one author. The textual constraint notes that the list positions are numbered sequentially from 1.

Although this ternary representation may appear awkward, it is easy to populate and it facilitates any discussion involving position (e.g., who is the second author for paper 21?). From an implementation perspective, an ordered set structure could still be chosen.

An ordered set is an example of a collection type. As discussed in [Chapter 10](#Ch010_401-479_B9780443237904000244.xhtml), some versions of ORM allow collections to be specified as mapping annotations in a similar way to UML, and some ORM versions allow collections to be modeled directly as first-class objects.

## Association Redefinition

UML 2 introduced the notion of *association redefinition*. This concept applies to generalizations as well as associations. One main use of it is to specify stronger constraints on an association that specializes an association involving a supertype. For example, in [Fig. 9.52](#Ch009_347-399_B9780443237904000013.xhtml#f0265)(a) the `executiveCar` role redefines the `assignedCar` role, applying a stronger multiplicity constraint that applies only to executives. Effectively, the association Executive is assigned CompanyCar is treated as a specialization of the Employee is assigned CompanyCar association. The stronger multiplicity constraint may be expressed in ORM by a textual constraint as in [Fig. 9.52](#Ch009_347-399_B9780443237904000013.xhtml#f0265)(b), or by a subset constraint involving the subtyping link (see [Section 10.8](#Ch010_401-479_B9780443237904000244.xhtml#s0080)).

## Derived Data

Now let’s consider *derived data*. In UML, derived elements (e.g., attributes, associations, or association-roles) are indicated by prefixing their names with “/”. Optionally, a *derivation rule* may be specified as well. The derivation rule can be expressed as a constraint or note, connected to the derived element by a dashed line. This line is actually shorthand for a dependency arrow, optionally annotated with the stereotype name `«derive»`.

Because a constraint or note is involved, the arrow tip may be omitted (the constraint or note is assumed to be the source). For example, [Fig. 9.53](#Ch009_347-399_B9780443237904000013.xhtml#f0270)(a) includes `area` as a derived attribute. [Fig. 9.53](#Ch009_347-399_B9780443237904000013.xhtml#f0270)(b) shows the ORM schema.

![Fig. 9.53 Derivation of area in (a) UML and (b) ORM.](images/B9780443237904000013/f09-53-9780443237904.jpg)

[Fig. 9.53](#Ch009_347-399_B9780443237904000013.xhtml#B-f0270) Derivation of area in (a) UML and (b) ORM.

The UML dependency line may also be omitted entirely, with the constraint shown in braces next to the derived element (in this case, it is the modeling tool’s responsibility to maintain the graphical linkage implicitly). The example in [Fig. 9.54](#Ch009_347-399_B9780443237904000013.xhtml#f0275)(a) expresses unclehood as a derived association. For illustration purposes, rolenames are included for association ends. The corresponding ORM schema is shown in [Fig. 9.54](#Ch009_347-399_B9780443237904000013.xhtml#f0275)(b), with the derivation rule specified in relational style.

![Fig. 9.54 Derived uncle association in (a) UML and (b) ORM.](images/B9780443237904000013/f09-54-9780443237904.jpg)

[Fig. 9.54](#Ch009_347-399_B9780443237904000013.xhtml#B-f0275) Derived uncle association in (a) UML and (b) ORM.

Although precise role names are not always elegant, the use of role names in derivation rules involving a path projection can facilitate the concise expression of rules, as shown here in the UML model. By adding role names to the ORM schema, the derivation rule may be specified compactly in attribute style thus: `define uncle of Person as brother of parent of Person`. More complex derivation rules can be stated informally in English or formally in a language such as OCL.
