

## 反规范化与底层优化

如果规范化的双表设计性能不佳，我们可能会将设计反规范化为单表，即它们的自然连接，如[图 14.74](#Ch014_681-771_B9780443237904000189.xhtml#f0375)(b)所示。将[图 14.71](#Ch014_681-771_B9780443237904000189.xhtml#f0360)(a)的子集约束替换为等值约束后，分配事实可以通过在三元事实类型的前两个角色上投影来检索，但分配二元事实类型上的唯一性约束仍需处理。在反规范化的三元事实类型中，该约束无法作为唯一性约束来强制执行，因此需要一个单独的约束来强制执行函数依赖 `lecturer → course`。只要强制执行此额外约束（例如，作为 SQL 中的用户定义约束），单表设计就是安全的。如前所述，备选键约束是隐含的，因此省略了。

关系语言的进步使得指定非基于键的约束（如函数依赖）变得更加容易。然而，在选择最终的关系设计时，必须考虑强制执行此类约束的开销。一般来说，我们应该首先尝试完全规范化的设计，在相关的地方使用概念优化来改进它。如果性能仍然不可接受，受控反规范化是一种选择。

## 14.7 反规范化与底层优化

应用概念优化过程并遵循 Rmap 过程可确保一个无冗余的关系模式，其效率应当相当合理。要测试此逻辑模式的性能，应使用真实的数据量将其作为内部模式在目标 DBMS 上实现。在此阶段，通常应为所有主键和外键以及在聚焦查询中起重要作用的任何其他列创建 `indexes`（索引）。

对于大表，索引可以显著提高性能，因为它们通常可以部分或整体地加载到主存中，且其条目被排序进允许快速检索的结构中（例如，二叉树）。有时，索引可能会减慢更新速度，因为当相关更改发生在基表上时，索引必须更新；但即使有更新，索引也能加快许多种约束检查（例如，确保键的唯一性）。索引有多种类型（例如，聚簇、非聚簇），且索引方案在不同供应商之间往往有所不同。

为了加速或促进某些复杂查询，可以使用 `working tables`（工作表，预先声明或临时创建均可）（例如，用于保存中间结果，这些结果可能通过连接多个表获得，在基础值更新前可能被重用多次）。预先声明的工作表在会话开始时填充，用于保存该会话中可视为稳定的中间结果；这些临时表在会话结束时删除。临时创建的工作表类似，但在会话期间创建，并且一旦不再需要，可在会话结束前随时删除。

另一个流行的选项是使用 `materialized views`（物化视图）——这些视图根据其定义自动填充数据，并在其基表更新时根据需要自动更新。对物化视图的支持因 DBMS 而异；在 SQL Server 中，它们称为索引视图。

不同的 DBMS 提供其他调整内部模式的方法（例如，聚簇存储相关数据）。此外，由于没有查询优化器是完美的，实际查询本身的形式也会影响（有时严重影响）性能。对于某些较旧的优化器，仅更改连接条件中列出表的顺序就可能导致响应时间发生显著变化。在大多数情况下，你可以使用 DBMS 提供的性能调优辅助来比较执行计划并选择最佳方案。

如果数据已预先检查过完整性，考虑在执行批量更新时（例如，从操作数据库加载数据仓库）停用约束检查。你也可以将昂贵的约束检查推迟到执行批量更新之后。虽然大多数数据库应用程序可以完全使用 4GL 开发，但考虑用 3GL（例如 C#）编写某些模块，以加速关键方面或实现更好的控制（例如，在 3GL 中检查非循环约束通常比在 SQL 中使用递归并集更快）。

对于极少数特定应用，关系 DBMS 系统可能无法提供所需的性能，可能需要另一种类型的 DBMS（例如，对象数据库）。

由于实际应用通常要求用户通过外部接口（例如，屏幕表单）而不是直接在基表上执行数据更新，因此需要决定在表级进行多少约束检查，在表单级进行多少。对于客户端-服务器网络，我们需要决定在客户端完成多少工作，在服务器端完成多少。约束通常同时在用户界面和 DBMS 中实现。

在屏幕表单上实现约束可以尽早检测数据录入错误。在 DBMS 上实现约束可确保无论用户界面如何，都会对其进行检查。对于非集中式数据库系统，在决定如何复制数据以减少通信开销时需要极大的谨慎。对这些问题的适当讨论超出了本书的范围。
