
假设我们记录汽车所选的颜色。添加事实类型 `Car is of Color`，该情况可由 [图 10.70](#Ch010_401-479_B9780443237904000244.xhtml#f0355) 所示的 ORM 模式建模。此处，颜色选择集通过常规规范化方式处理，采用多对多关联。子集约束确保汽车的颜色是其车型可用颜色之一。

![图 10.70 非规范化表部分的一阶解决方案。](images/B9780443237904000244/f10-70-9780443237904.jpg)

在需要记录许多属性信息且属性并非全部预先已知的情况下，可通过引入 `Attribute` 作为一阶类型，以及记录其名称和值的事实类型来建模。通过这种将元数据降级为地面数据的方式，我们保持在一阶层面。

支持使用高阶类型的最后一个理由是：允许在同一模型中表达那些似乎跨越层级/元层级（或忽略层级区分）的业务规则（例如，财务部门负责定义 `AccountType` 的可能取值）。

如果我们确实想直接形式化此类情况，则显然需要高阶类型。然而，作为一种务实的替代方案，通常可以通过一阶方式处理此类规则：要么将元层面分离到一个单独的一阶模型中（原元类型现为地面类型），要么将元数据降级为地面数据，要么直接忽略跨层级身份。

作为一个简单示例，我们可能在元模式的核心包中内置诸如 `FactRole is played by ObjectType`、`BusinessRule has IllocutionaryForce` 等元事实类型；而在元模式的管理包中，包含处理安全和授权等方面的元事实类型（例如 `UserGroup has AccessRight to FactType`）。在元模型中填充后者元事实类型，随后可能允许我们添加期望类型的规则，而无需跨越元层级。

例如，考虑 [图 10.71](#Ch010_401-479_B9780443237904000244.xhtml#f0360)(a) 所示的简单业务模型。此处有两个基本事实类型（F2 和 F4）和三个存在性事实类型（F1、F3 和 F5），均以带括号的引用模式简写形式描绘。在这种情况下，`AccountType` 的当前值存储在参考表中，而非严格声明在值类型约束中。

![图 10.71 业务模型 (a) 和相关元模型片段 (b)。](images/B9780443237904000244/f10-71-9780443237904.jpg)

[图 10.71](#Ch010_401-479_B9780443237904000244.xhtml#B-f0360) 业务模型 (a) 和相关元模型片段 (b)。

采用这种方法，`AccountType` 的单列事实表可像模型中的任何其他事实表一样处理，包括确定谁对哪个事实类型拥有何种访问权限的方式。处理安全性的简化元片段如 [图 10.71](#Ch010_401-479_B9780443237904000244.xhtml#f0360)(b) 所示。[图 10.71](#Ch010_401-479_B9780443237904000244.xhtml#f0360)(b) 中的元模型位于 [图 10.71](#Ch010_401-479_B9780443237904000244.xhtml#f0360)(a) 业务模型之上。这些模型均可单独形式化，使用一阶逻辑或前文讨论的用于分类的高阶逻辑扩展。

此图景缺失的是：将业务模型中提到的市场部门，与元模型中作为用户组出现的市场部门识别为同一实体。似乎没有令人信服的业务理由要求正式支持这种身份认同，因为企业在没有这种支持的情况下也运行良好（例如在 SQL 系统中，应用表和元表通常分别访问）。

## 10.8 涉及子类型的进一步约束

在 [图 10.72](#Ch010_401-479_B9780443237904000244.xhtml#f0365)(a) 中，异或约束连接子类型箭头的上部。在 ORM 中，从子类型指向超类型的箭头显示一种类型层面的关系，该关系蕴含链接子类型和超类型实例的实例层面身份关系。例如，[图 10.72](#Ch010_401-479_B9780443237904000244.xhtml#f0365)(a) 中的异或约束被理解为适用于 [图 10.72](#Ch010_401-479_B9780443237904000244.xhtml#f0365)(b) 中虚线所示的实例层面链接事实类型的*超类型角色*。

![图 10.72 子类型链接角色上的约束。](images/B9780443237904000244/f10-72-9780443237904.jpg)

[图 10.72](#Ch010_401-479_B9780443237904000244.xhtml#B-f0365) 子类型链接角色上的约束。

在本例中，子类型从其超类型继承首选引用方案，因此这些身份（“=”或“is”）关系构成子类型实例引用方案的一部分，例如，`is` 那个名为“Tom Smith”的 `AdultPerson` 的 `Man`。

使用公司车的角色对员工是可选的，但对高管是强制的。[图 10.72](#Ch010_401-479_B9780443237904000244.xhtml#f0365)(c) 以文本约束形式显示这种*受限强制角色约束*。[图 10.72](#Ch010_401-479_B9780443237904000244.xhtml#f0365)(c) 重现了前文 [第 9.7 节](#Ch009_347-399_B9780443237904000013.xhtml#s0040) 中讨论的一个示例。

2013 年，ORM 和 NORMA 扩展为允许其他种类的约束应用于超类型链接角色。除其他外，这允许以图形方式表达受限强制角色约束，如 [图 10.72](#Ch010_401-479_B9780443237904000244.xhtml#f0365)(d) 所示的子集约束，其解释如 [图 10.72](#Ch010_401-479_B9780443237904000244.xhtml#f0365)(e) 所示。NORMA 自动将此子集约束口语化如下：

*   ```
    If some Employee is some Executive
    ```

*     **then that** Employee uses **some** CompanyCar.
