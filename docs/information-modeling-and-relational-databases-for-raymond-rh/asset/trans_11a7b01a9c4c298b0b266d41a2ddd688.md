
*   ```
    or not exists Seating1.endtTime)
    ```

*   **那么没有** `Table` 被 `Seating[1]` **和** `Seating[2]` 使用。

有关以建议的 ORM 动态规则语言表示的状态转换动态规则的更复杂示例的详细讨论，以及基于日志语义的形式化，请参见 [Balsters and Halpin (2016)](#Ch010_401-479_B9780443237904000244.xhtml#bb0045)。

*受保护转换图* 允许将表示为公式的守卫条件应用于转换。在实践中，许多不同的图表和形式化方法被用来指定各种类型的动态约束。这些包括状态图、活动图、状态网、着色 Petri 网、基于过程代数的任务结构，以及 *事件-条件-动作* (*ECA*) 声明。ECA 语言允许形式为 **如果** *事件* **则在** *条件* **则** *动作1* \[**否则** *动作2*\] 的语句。这为 *控制违反约束时所采取的动作* 提供了一个通用框架。更新是事件的一个例子，约束违反是条件的一个例子。

转换约束的一个极端版本是使事实 *不可变* (不可更改)。换句话说，一旦录入了基本事实，就无法将其删除。这种约束最好结合子类型的动态方面来考虑，我们稍后将讨论。

如前所述，某些动态规则引用的状态是由指定周期分隔的，而不是连续的。在实践中，许多此类规则本质上是 *道义* 的。例如，考虑这样一条规则：发票 *应当* 在开具后 30 天内付清。假设相关事实类型已在模式中声明，该规则可正式表示如下。

*   ```
    这是强制性的
    ```

*   ```
    每个在某 Date1 开具的 Invoice
    ```

*   ```
                        在某 Date2 付清
    ```

*   ```
    其中 Date2 <= Date1 + 30 天。
    ```

作为本节关于建模中时间问题的最后一部分，我们现在转向 *子类型的动态方面*。这假设你熟悉 [第 6.5 节](#Ch006_211-271_B9780443237904000025.xhtml#s0040) 和 [第 6.6 节](#Ch006_211-271_B9780443237904000025.xhtml#s0050) 中讨论的 ORM 和 UML 中子类型的静态方面。

本体工程社区的一些提议采用了类型元属性，以确保从本体论角度来看子类型方案是构造良好的。例如，[Guarino and Welty (2002)](#Ch010_401-479_B9780443237904000244.xhtml#bb0505) 认为本体中的每个属性都应标记为刚性、非刚性或反刚性。

*刚性* 属性 (例如，是一个人) 必然适用于其所有实例，贯穿其整个存在周期。*非刚性* 属性 (例如，是硬的) 必然适用于其部分而非全部实例。*反刚性* 属性 (例如，是一个病人) 偶然地适用于其所有实例。随后可应用元约束 (例如，反刚性属性不能包含刚性属性) 来对子类型施加限制 (例如，`Patient` 不能是 `Person` 的超类型)。

[Guizzardi et al. (2004)](#Ch010_401-479_B9780443237904000244.xhtml#bb0515) 提出了一个 UML 配置文件，将类刻板为种类、亚种、阶段、角色、范畴、角色混入和混入，并配合一组元约束，以帮助确保 UML 类模型在本体论上构造良好。[Guizzardi (2005)](#Ch010_401-479_B9780443237904000244.xhtml#bb0510) 在其关于概念信息模型本体论基础的博士论文中使用了这一建模配置文件。

虽然上述研究提供了有价值的贡献，但我们对其在工业信息系统建模中的应用持保留意见。我们与工业数据建模师的合作经验表明，七类方案对他们中的大多数人来说似乎过于繁重。

我们目前正在为 ORM 2 考虑的一个更简单的替代方案是 *将每个子类型分类为刚性子类型或角色子类型*。当且仅当该类型的每个实例在其整个生命周期内 (在所建模的业务领域中) 必须属于该类型时，*类型才是刚性* 的。示例包括 `Person`、`Animal` 和 `Book`。

相反，*角色类型* 的实例在其生命周期内 (在业务领域中) 不必始终是该类型的实例。这里，我们宽泛地使用“角色”，以包括对象扮演的角色 (例如 `Manager`、`Student`、`Patient` —— 假设这些在业务领域中是可变的) 以及对象的阶段或状态 (例如 `Child`、`Adult`、`FaultyProduct` —— 假设可变性)。

虽然这种刚性/角色分类方案适用于任何类型，但我们通常只要求对子类型做出这种区分 (以控制子类型迁移并减轻建模师的分类负担)。作为一个示例，[图 10.32](#Ch010_401-479_B9780443237904000244.xhtml#f0165) 描绘了 ORM 和 UML 中作为刚性子类型的 `Dog` 和 `Cat`。

![图 10.32 (a) ORM 和 (b) UML 中描绘的刚性子类型。](images/B9780443237904000244/f10-32-9780443237904.jpg)

[图 10.32](#Ch010_401-479_B9780443237904000244.xhtml#B-f0165) (a) ORM 和 (b) UML 中描绘的刚性子类型。

为 ORM 建议的刚性表示法是子类型名称的方括号标注 (真理模态为紫色；道义模态为带 ^("o") 的蓝色，例如，从男性变为女性可能是可能的但被禁止的)。

NORMA 工具尚不支持此表示法来对子类型进行分类，但可在子类型的“备注”属性中非正式地记录。对于 UML，我们选择了刚性刻板印象。刚性是一种 *动态约束* 而非静态约束，因为它限制状态变更 (例如，狗不能变成猫)。

在前文中，子类型是断言的。如果我们添加事实类型 `Animal is of AnimalKind`，我们可以用它来派生 `Dog` 和 `Cat` 子类型。如果事实类型 `Animal is of AnimalKind` 被设为 *不可更改* (动物不能改变其种类)，则派生子类型的刚性现在变得可推导。ORM 尚不支持事实类型的可更改性状态。UML 识别四种可更改性设置：无限制、只读、仅添加和仅删除。如果我们从 `Animal.kind` 属性派生 `Dog` 和 `Cat` 作为 `Animal` 的子类，并将该属性声明为只读，则子类的刚性便被暗示了。

为避免显式声明角色子类型，ORM 子类型默认可假定为角色子类型。与刚性子类型不同，*角色子类型之间的迁移通常被允许*。作为一个简单示例，一个人在其一生的不同时间可能扮演儿童、青少年和成人的角色 (参见 [图 10.33](#Ch010_401-479_B9780443237904000244.xhtml#f0170))。

![图 10.33 允许角色子类型之间的迁移。](images/B9780443237904000244/f10-33-9780443237904.jpg)

[图 10.33](#Ch010_401-479_B9780443237904000244.xhtml#B-f0170) 允许角色子类型之间的迁移。
