
即使像这样简单的示例也能得出一些总体结论。首先，信息可能以许多不同的方式演变，这些差异对业务可能非常重要；在刚才的示例中，不同的选项导致了不同的成本和不同的处理时间。其次，信息*结构*与信息*用法*之间的关系是一对多：单一的信息结构有可能以多种方式被使用，但特定的活动序列将始终与一种特定的信息结构相关联。第三，我们不能仅通过考虑信息结构（如[图 15.1](#Ch015_773-830_B9780443237904000190.xhtml#f0010)所示）来定义业务活动（如[图 15.2](#Ch015_773-830_B9780443237904000190.xhtml#f0015)所示）。虽然信息结构模型是必要的，但它并不能提供足够的信息来完全指定一个信息系统，因为我们还需要知道信息将如何被使用。

这种关注点分离被证明是信息建模的一个有用方面。企业经常根据感知到的机会或威胁来审查和修订其活动。在“结构”视图和“行为”视图之间保持一定程度的正交性，可以最小化变更的连锁反应。例如，企业可以在“最低成本”和“最短时间”策略之间切换，而不一定需要对信息模型进行任何更改。

虽然仅凭信息结构不能完全指定活动序列，但它可能会对信息创建的顺序施加一些约束。如果我们以关系模式的形式查看信息结构，这一点很容易看出来。[图 15.3](#Ch015_773-830_B9780443237904000190.xhtml#f0020) 显示了一个示例。

对于该模式，除非我们之前已记录了涉及的 Employee（员工）和 Item（物品），否则无法录入关于 Fitting（装配/试装）的信息。同样，除非 Item 已被记录，否则无法录入 Test（测试）。这些约束可以从表之间的外键引用中识别出来。然而，对于 tester（测试员）信息存在一个较弱的排序约束：该列是可选的，因此我们可以创建一条 Test 记录，将 tester 的值留为 null。被引用的 Employee 仅需在我们添加 tester 信息时存在，这可能是在创建 Test 记录之后的一段时间。相应的约束也适用于信息的删除。例如，当我们仍有与该 Employee 相关的 Fitting 记录时，我们大概不想删除该 Employee。对于 tester 列，外键引用可能会被指定为 `on delete set null`，这将允许我们删除 Test 中仍被引用的 Employee 行，并将对 Employee 表的任何现有 tester 引用设置为 null。

尽管这类约束不能完全决定我们创建、更新或删除信息的序列，但无论我们采用何种建模方法来定义信息行为，都必须遵守这些约束。本章主要关注两种常用于建模行为（有时称为*动态*）方面的方法：过程建模和状态建模。

## 15.2 过程与工作流

对于企业而言，管理其业务过程一直很重要。无论剧烈还是微妙的过程变更，都是保持业务高效和具有竞争力的常用机制（[Hammer and Champy, 1993](#Ch015_773-830_B9780443237904000190.xhtml#bb0800)）。任何中大型企业都可能拥有一套全面的过程，定义了其打算如何开展活动。旨在达到 ISO 9000 系列等标准质量认证的公司需要这种定义。除其他要求外，这些质量标准要求组织定义其过程并保留其执行的充分记录。

拥有一套已定义的业务过程并不一定意味着对自动化的任何承诺。直到 20 世纪下半叶，由于可用技术的限制，过程自动化的机会有限，手工过程很常见。如今，拥有某种自动化支持更为普遍。我们可以大致区分几个自动化级别，如[表 15.1](#Ch015_773-830_B9780443237904000190.xhtml#t0010)所示。

组织可能在不同级别拥有不同的过程，但总体趋势是过程向第 3 级迁移。在第 3 级的极端端，我们拥有所有活动均实现自动化的过程，这种状况得益于支持面向服务架构的技术日益普及。

我们还可以根据涉及活动的结构和可重复性对过程进行分类。一些过程是临时的*：* 涉及的活动未预先定义，因此显然它们的顺序也无法预先定义。临时过程通常受一组规则约束，这些规则定义了允许何种活动、如何启动或结束活动等，以取代预定义的结构。

目前对过程建模的大多数关注都集中在活动的更结构化安排上，有时称为*有框架*过程。*单独*有框架的过程定义明确，但过程定义仅执行几次，甚至可能只执行一次。一个例子是项目计划，它通常定义了一组详细的活动及其顺序，但不太可能在不修改的情况下在任何其他项目中重用。*松散*有框架的过程，有时也称为“行政过程”，具有定义的活动和协调规则，但在一定限度内拥有改变活动及其顺序的灵活性。*紧密*有框架的过程，有时也称为“生产过程”，具有高度可预测的活动和稳定的协调规则，并始终如一地遵循这些规则。

松散有框架和紧密有框架过程的一个重要特征是它们通常是可重复的。这使得投资其自动化成为一个有吸引力的主张，因为开发成本可以通过更好地控制过程执行所带来的潜在节省来证明其合理性。在本章的其余部分，我们将假设我们处理的是此类过程。

过程建模中常见的一个术语是*工作流*。工作流最初的重点是将业务活动机械化，这些活动在历史上涉及在收件箱和发件箱之间传递纸质文档。因此，工作流及其在工作流系统中的体现，非常强调执行。最近，人们意识到工作流是一组更大关注点的一部分，涉及业务信息的系统化处理。在许多语境中，工作流一词可以与业务过程建模互换使用，但工作流通常意味着一种稍低层级的视角，主要处理操作和技术问题。
