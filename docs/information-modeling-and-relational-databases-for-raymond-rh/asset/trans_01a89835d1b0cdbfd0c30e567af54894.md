
在这里，相同的表名“Human”同时出现在内层和外层查询的 **from** 子句中。因此，为了区分内层表中的 gender 列与外层表中的 gender 列，为外层表引入了别名 `X`。这使我们能够将关联条件指定为“gender = `X`.gender”，而不是“gender = gender”（后者当然永远为真）。这里，`X` 被称为 *相关变量*。你可以把 `X` 看作是 Human 表的一个额外副本。

或者，你可以把它看作是一个元组变量，其取值范围是 Human 表的各行，如 [图 12.60](#Ch012_539-646_B9780443237904000268_2.xhtml#f0305) 所示。尽管 SQL 查询采用面向集合的语法，但其处理过程是一次一行地进行的。在这里，`X` 依次被赋予 Human 表的每一行，经历六种状态（在本例中），在每种状态下它持有一行数据。对于这些状态中的每一个，都会对内层查询进行求值，计算当前赋予 `X` 的性别对应的平均身高。如果你熟悉编程语言，这应该会让你联想到嵌套的 **for** 循环。

![图 12.60 在外层查询中，X 依次被赋予六行中的一行。](images/B9780443237904000268/f12-60-9780443237904.jpg)

[图 12.60](#Ch012_539-646_B9780443237904000268_2.xhtml#B-f0305) 在外层查询中，X 依次被赋予六行中的一行。

让我们演练一下查询的执行过程。在外层，我们从第一行开始，因此 `X` 被赋予元组（“Ann”，“F”，160）。因此，在外层，gender = “F” 且 height = 160。换句话说，`X`.gender = “F” 且 `X`.height = 160。在子查询中，关联条件“gender = `X`.gender”现在变为“gender = ‘F’”。因此，子查询返回女性的平均身高，对于给定数据该值为 165。

外层查询中的条件现在变为“160 > 165”，结果为假。因为第一行不满足条件，所以被过滤掉了，Ann 被排除在结果之外。

在外层，我们接着处理第二行，因此 `X` 被赋予元组（“Bill”，“M”，180）。因此，`X`.gender = “M” 且 height = 180。在子查询中，条件“gender = `X`.gender”变为“gender = ‘M’”。因此，子查询返回男性的平均身高，即 175。外层查询中的条件现在变为“180 > 175”，结果为真。因此，Bill 的 firstname 和 height（“Bill”，180）被包含在结果中。

同样地，我们在外层依次处理第 3、4、5、6 行，每次都重新计算子查询。Carol 被选中（170 > 165 为真），但其他行被拒绝（因为条件 175 > 175、165 > 165 和 170 > 175 均为假）。因此，最终结果仅列出 Bill 和 Carol 的 firstname 和 height，正如之前在 [图 12.59](#Ch012_539-646_B9780443237904000268_2.xhtml#f0300) 中所示。

考虑查询：谁的薪水至少达到其上司薪水的 80%？让我们先尝试使用示例数据回答这个问题：员工 1 被排除，因为他/她没有上司。员工 2 获得其上司薪水的 900/1000 即 90%，员工 3 获得其上司薪水的 70%，员工 4 获得其上司薪水的 780/900 即 86.67%。因此，结果应列出员工 2 和 4。

如何用 SQL 构制定义该查询以适用于任意数据集？你可能想在继续阅读前自己尝试一下。

问题中包含代词“his/her”是一个线索，表明该查询可以用相关子查询来构建，稍后将详述。`E` 用于表示外层的员工。虽然不是必需的，但使用了第二个别名 `B` 以帮助表明内层员工是上司。

```
select empNr
```

```
from Employee as E
```

```
where pay >=
```

```
            (select 0.8 * pay
```

```
             from  Employee as B
```

```
             where B.empNr = E.bossNr)
```

作为替代方案，你可以使用自连接来构建该查询，如下所示：

```
select E.empNr
```

```
from Employee as E join Employee as B
```

```
on E.bossNr = B.empNr
```

```
and E.pay >= 0.8 * B.pay
```

正如这个例子所示，计算相关子查询基本上等同于计算连接，因此在构建相关子查询时需要格外小心，以避免不可接受的性能。

现在，让我们考虑 *存在量词子查询*。在谓词逻辑中，命题“存在一只青蛙”可以表述为“∃*x Fx*”。这里，“∃”是存在量词，意为“至少存在一个”，“*x*”是代表某个对象的个体变量，“*F* …”是谓词“…是一只青蛙”的缩写。

SQL 中的存在量词子查询有些类似。它出现在以下形式的 *存在量词条件* 中：

```
exists ( subquery )
```

这里，使用 **exists** 代替“∃”作为存在量词，而子查询实际上是一个元组变量，其取值范围是子查询返回的行。**exists** 量词可以被视为一个布尔函数，*如果子查询返回一行则返回 True，否则返回 False。*

**exists** 量词前面可以加上逻辑 **not** 运算符。可能的情况如下所示。“一行”意味着“至少一行”。因为系统总是知道是否返回了行，所以适用简单的二值逻辑——存在量词条件的求值结果为 True 或 False，永远不会是 Unknown。

```
exists ( subquery )                    →     True      - - 返回了一行（由子查询返回）
```

```
                                                                                  →     False     - - 未返回行
```

```
not exists ( subquery )          →     True       - - 未返回行
```

```
                                                                                  →     False     - - 返回了一行
```

存在量词子查询可用于 **where** 子句的搜索条件中，从而形成以下形式的整体查询：

```
select …
```

```
from  …
```

```
where [ not ] exists
```

```
            ( select * …)
```

因为子查询结果中仅关心行的存在与否，所以在存在量词子查询的 **select** 列表中通常直接使用“*”代替列列表。

在 SQL-92 之前，存在量词子查询是唯一可以返回多列的子查询，因为在 SQL-89 中，成员资格子查询和比较子查询都必须返回单列。某些 SQL 方言至今仍保留这一限制。
