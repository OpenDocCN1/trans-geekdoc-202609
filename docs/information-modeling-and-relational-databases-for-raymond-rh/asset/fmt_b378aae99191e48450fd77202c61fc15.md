
# Another function, `xmltable`

Another function, `xmltable`, provides a useful way to integrate XQuery results back into SQL. Normally, an XQuery expression would return a sequence, but by using `xmltable`, we can execute an XQuery expression and return values as a table instead. The returned table can contain columns of any SQL data type, including XML, although values inserted into `xml` columns in `xmltable` must be well-formed with a single root node. The basic syntax is:

```
xmltable ( [ xmlnamespaces ( namespace-declaration-item [,…] ), ] row-pattern [ passing [ { by ref | by value } ] XMLquery-argument [,…] ]columns { { colname for ordinality | colname datatype [ by ref | by value ] path column-pattern} [,…] } )
```

The row-pattern defines an expression that produces a sequence of elements. Each element in this sequence will become a row in the resulting table. The `columns` clause lists the column definitions and the path expression used to find the column value within each element of the row-pattern. The `for ordinality` option creates a column with an automatic ordinal reference to the row, so the first row is 1, the second row 2, and so on. An example is shown here. This assumes that we have an `xml` value called `movieXML`, the contents of which are similar to the examples we used when discussing XQuery. If this `xmltable` function call is contained in a `select` statement, the value being passed could be selected from a suitable xml column in a table.

```
xmltable (‘//movies'passing movieXMLcolumns “Seqno” for ordinality, “MovieNr” int path ‘@movieNr', “Movie Name” varchar (50) path ‘title', “Release Year” char(4) path ‘released' “Director” varchar(50) path ‘director' )
```

The resulting table would have the following form, and could be aliased and so on, in the same way as a table produced by other means.

In this case, values in the automatically generated SeqNo column and the retrieved MovieNr column are coincidentally the same. Had the XML data been in a different order, the SeqNo column would remain unchanged, but the MovieNr column (and the other retrieved columns) would reflect the XML element ordering.

## 16.3 JSON

JSON stands for JavaScript Object Notation, which describes its origin and function very clearly. Like XML, JSON is a text-based format that makes it very easy to interchange data between different systems. Each system can store the data in its own internal form for efficient processing, but these internal representations do not need to be the same. JSON was first defined by Douglas Crockford in the early 2000s as a format for data interchange, but it subsequently became widely adopted as a convenient way of expressing data structure and is supported in most programming languages. An early “informational” standard ([Crockford, 2006](#Ch016_831-873_B9780443237904000207.xhtml#bb0260)) was followed by the first international standard (ECMA-404) in 2013.

The syntax of JSON is very simple and is a slightly modified version of JavaScript syntax. There are two main structural elements.

1.  Sets of key-value pairs. A colon character separates the key and the value, as in:

    ```
     “givenName” : “Alan”, “familyName” : “Turing”
    ```

    The key is enclosed in double quotes. Successive items are separated by a comma character and the set is enclosed in braces. The order of items in the set is not significant. Such sets are termed “objects” from their JavaScript origins.

2.  Arrays containing an ordered collection of values. Values are separated by comma characters. An array is enclosed in square brackets.

Whitespace characters (space, tab, newline, …) outside quoted values are ignored. Values can be a string, a number, a Boolean, the special value null, or either of the structured types (objects and arrays). The broad guidelines are that arrays are used for collections of similar items and objects are used for collections of properties for an individual item.

The JSON syntax is slightly different to JavaScript, which does not require quoted keys and allows other possible values, such as functions, but the general style is similar. This makes JSON processing in JavaScript very straightforward, and the language has built-in functions for handling JSON text. `JSON.parse()` converts a text representation into a JavaScript object structure and `JSON.stringify()` converts a JavaScript object structure into text. Similar functionality is provided in other object-oriented languages. One noticeable absence from JSON is any capability for expressing comments. This was a deliberate choice made by its designers but has been a source of frustration for many users.

This straightforward processing is a distinct advantage over XML, which requires a more complex parser to process text into an internal representation and provides only indirect access to data values.

The nesting of entities (e.g., objects containing objects) produces a hierarchical structure in much the same way as XML, but JSON also provides arrays, which have no direct equivalent in XML. Like XML, a JSON file can be opened and edited with nothing more than a simple text editor. Human readability can be helped by sensible use of whitespace characters, but dedicated editors, sensitive to JSON structure, are also available. JSON files are generally more compact than the equivalent XML representation of the same data.

Another difference between XML and JSON is the approach to data typing. XML, like SQL, has an extensive range of data types that can be specified in a schema. JavaScript is a dynamically typed language, and this is carried over into JSON, which has only three scalar data types: string, number, and Boolean (plus null, which, like SQL, indicates the absence of a value). Numbers can be integer or floating point, and Booleans have the value true or false.
