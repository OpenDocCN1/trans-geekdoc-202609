

# 优化过程的最后步骤（3、4、5）

我们现在考虑优化过程中的最后步骤（3、4、5）。与之前的步骤不同，这些步骤不会减少表的数量。*步骤 3* 如 [图 14.48](#Ch014_681-771_B9780443237904000189.xhtml#f0245) 所示。其目的是减少自连接，称为*表宽指南*（TWG），因为它指示何时更宽的表（更多列）可能更可取。

![Fig. 14.48 Optimization step 3: the table width guideline.](images/B9780443237904000189/f14-48-9780443237904.jpg)

[图 14.48](#Ch014_681-771_B9780443237904000189.xhtml#B-f0245) 优化步骤 3：表宽指南。

前面已经讨论了图中所示的模式等价性。如果对象类型 *A* 扮演功能角色，转换为二元事实类型本应已在步骤 2.1 的最后阶段发生。即使 *A* 没有功能角色，如果专门化为二元事实类型能避免聚焦查询中的自连接，这种专门化仍然可能是值得的。

作为步骤 3 的一个示例，假设我们想查看 2021–2023 三年间各学位的全日制大学学费变化情况。让我们用三元事实类型 `Degree in Year had FulltimeFee` 来建模，其前两个角色跨越唯一性约束，第一个角色上有频率约束 3，`Year` 的角色上有值约束 `{2021…2023}`，如 [图 14.49](#Ch014_681-771_B9780443237904000189.xhtml#f0250) 所示。假设我们将其映射到关系模式 `FulltimeFee(degree, feeYear, Fee)`，并在关系层面强制执行频率约束和值约束。

![Fig. 14.49 This query requires a self-join because it compares different rows.](images/B9780443237904000189/f14-49-9780443237904.jpg)

[图 14.49](#Ch014_681-771_B9780443237904000189.xhtml#B-f0250) 此查询需要自连接，因为它比较不同的行。

[图 14.49](#Ch014_681-771_B9780443237904000189.xhtml#f0250) 展示了该表的一个样本数据片段。设一个聚焦查询为：BS 全日制学费在三年间增加了多少？请通过检查表格自行回答该查询。

在得出答案（$500）的过程中，你比较了同一表中两行不同的值。要在关系数据库中执行此查询，需要将表与自身连接（自连接）。[图 14.49](#Ch014_681-771_B9780443237904000189.xhtml#f0250) 中包含了该查询的一个 SQL 版本。

通过首先应用 TWG 转换模式，可以避免此类连接。应用 PSG1 的一个变体，其中值约束应用于*角色*而非对象类型，该三元事实类型专门化为三个概念二元事实类型：`Degree had 2021- FulltimeFee`；`Degree had 2022- FulltimeFee`；`Degree had 2023- FulltimeFee`。

在这里，`Degree` 的角色是功能性的，并由等值约束链接。如果在全局模式中，学费信息对 `Degree` 是强制的，这些角色就是强制的（这意味着等值约束）。如果 `Degree` 没有其他功能角色，这三个概念二元事实类型映射到单个表：`FulltimeFee(degree, fee2021, fee2002, fee2023)`。

如果 `Degree` 有其他功能角色，优化本应在步骤 2.1 执行，额外的功能事实类型映射到同一个表。

[图 14.50](#Ch014_681-771_B9780443237904000189.xhtml#f0255) 展示了概念模式，并说明了更宽的表如何使查询只需比较同一行上的值即可执行，这比之前的查询简单得多。

![Fig. 14.50 The transformed schema leads to a more efficient query.](images/B9780443237904000189/f14-50-9780443237904.jpg)

[图 14.50](#Ch014_681-771_B9780443237904000189.xhtml#B-f0255) 转换后的模式带来更高效的查询。

这个例子很简单明了，但现实并不总是如此简单。如果学费年份范围很大，转换产生的额外列数可能太高。例如，假设我们必须记录 1984…2023 期间的学费。专门化三元事实类型将生成 50 个二元事实类型，并导致一个包含 51 列的关系表：`FulltimeFee(degree, fee1984, …, fee2023)`。

如此大量的二元事实类型会使概念模式杂乱（尽管灵活的 CASE 工具可以设置为显示三元事实类型，并将优化隐藏在映射中）。非常宽的关系表也难以查看（大量水平滚动）和打印。出于这些原因，一旦值约束的*基数*超过一个合理的数字（例如 5），可能首选三元事实类型。

值约束的*稳定性*也很重要。在许多情况下，此类约束是已知稳定的（例如性别代码的 `{"m", "f"}`）。然而，有时值约束会随时间变化。例如，假设学费要记录从 2001 年到当前年份的所有年份，或者仅记录最近三年。二元方法要求每年更改事实类型和关系列。在这种情况下，可能首选三元方法，因为不需要结构更改（年份更改仅针对数据行，而非表结构本身）。

优化步骤 3 的措辞反映了查询效率与表显示及模式演化易用性之间的权衡。虽然可以将默认选择内置到自动优化器中，但建议与人类建模者交互，以确保最佳权衡。

优化过程的最后步骤（4 和 5）处理互斥角色（见 [图 14.51](#Ch014_681-771_B9780443237904000189.xhtml#f0260)）。

![Fig. 14.51 Optimization steps 4 and 5: further aspects of exclusive roles.](images/B9780443237904000189/f14-51-9780443237904.jpg)

[图 14.51](#Ch014_681-771_B9780443237904000189.xhtml#B-f0260) 优化步骤 4 和 5：互斥角色的进一步方面。

*步骤 4* 很简单。附加到同一对象类型的不同一元事实类型映射到同一表的不同列。如果这些一元事实类型互斥，我们可以用一个映射到单列的功能二元事实类型来替换它们。此外，将排斥约束转换为唯一性约束，使其能通过表的主键约束简单地强制执行。回顾 [图 14.7](#Ch014_681-771_B9780443237904000189.xhtml#f0040)，其中三个互斥一元事实类型（`Employee is a manager`；`Employee is a clerk`；`Employee is a secretary`）被功能二元事实类型 `Employee has Rank {'M', 'C', 'S'}` 替换。

*步骤 5* 帮助我们决定在应用定理 PSG2 时何时倾向于谓词泛化。这连同其他优化由我们的下一个例子说明。考虑 [图 14.52](#Ch014_681-771_B9780443237904000189.xhtml#f0265) 所示的概念模式。

![Fig. 14.52 This unoptimized conceptual schema maps to seven tables.](images/B9780443237904000189/f14-52-9780443237904.jpg)

[图 14.52](#Ch014_681-771_B9780443237904000189.xhtml#B-f0265) 此未优化的概念模式映射到七个表。

[图 14.52](#Ch014_681-771_B9780443237904000189.xhtml#f0265) 中的谓词间唯一性约束断言一支队伍每种性别只能有一名队员。此概念模式映射到七个表。作为练习，你可能想自行验证这一点，然后在继续阅读前优化该概念模式。

重叠算法（步骤 1.3）应用于 [图 14.52](#Ch014_681-771_B9780443237904000189.xhtml#f0265) 底部的三元事实类型，生成 [图 14.53](#Ch014_681-771_B9780443237904000189.xhtml#f0270) 中所示的中间嵌套子模式。随后通过步骤 5 将其转换为优化概念模式（[图 14.54](#Ch014_681-771_B9780443237904000189.xhtml#f0275)）中包含的嵌套模式。这种对嵌套的修改不会改变表或列的数量，但确实简化了必须强制执行的约束模式。
