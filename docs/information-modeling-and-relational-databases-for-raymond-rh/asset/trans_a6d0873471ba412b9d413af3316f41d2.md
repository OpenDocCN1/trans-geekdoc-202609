
# 评估信息模型中使用高阶类型的可行性

本节评估在信息模型中使用高阶类型的可行性。我们首先回顾逻辑学中的一些基本概念。

**一阶逻辑**仅对个体进行量化，不对谓词进行量化。例如，约束“**每个** Person 至多出生于 **一个** Date”可形式化为一阶类型逻辑如下：

```
∀x:Person ∃^(0..1)y:Date x was born on y
```

此处，类型 `Person` 和 `Date` 作为一元谓词出现，“∀”是全称量词（“**对于每个**”），而“∃^(0..1)”是“**至多存在一个**”量词。量化针对个别人和个别日期。一阶谓词只能由个体实例化。

**二阶逻辑**允许对一阶谓词（以及个体）进行量化。例如，规则“每个非对称谓词也是非自反的”可形式化为二阶逻辑如下：

```
∀R:Predicate (Asymmetric R → Irreflexive R)
```

三阶逻辑允许对二阶谓词进行量化，以此类推。所有阶数高于一阶的逻辑称为**高阶逻辑**。因为类型可由一元谓词形式化，如果类型 `A` 的实例本身就是一个类型，则 `A` 是**高阶类型**。

**分类类型**是用于将另一个类型分类为子类型的对象类型。例如，`Gender` 可用于事实类型 `Person is of Gender` 中，将 `Person` 分类为 `MalePerson` 和 `FemalePerson`。

ORM、ER 和关系模型的大多数形式化都基于一阶逻辑。相比之下，UML 引入了幂类型的概念，其实例本身可能是类型，因此需要高阶语义。

在信息建模中使用高阶类型似乎有三个主要论据：

1.  允许将某些分类类型（如 `AccountType`、`CarModel`）的实例视为类型本身（如 UML 幂类型）。
2.  直接形式化灵活数据结构的语义，其中属性条目本身可能表示集合或一般概念（如非第一范式中的对象关系表）。
3.  允许在同一模型中指定似乎跨越层级/元层级（或忽略层级区分）的业务规则（如：只有财务部门可指定 `AccountType` 的允许实例）。

由于转向高阶逻辑可能会给形式化和实施建模方法的任务增加相当大的复杂性，因此值得研究是否可以在保持一阶框架的同时实现相同的实际建模目标。我们认为可以。

首先让我们解决这个问题：分类类型的实例可以是类型本身吗？例如，在 [图 10.61](#Ch010_401-479_B9780443237904000244.xhtml#f0310) 所示的银行模式中，`AccountType` 的储蓄账户实例是否与子类型 `SavingsAccount` 相同？为便于讨论，名为“CheckingAccount”和“SavingsAccount”的两个 `AccountType` 实例在此分别描绘为白点和阴影点，且子类型已着色。

![图 10.61 AccountType 的实例是否与 Account 的子类型相同？](images/B9780443237904000244/f10-61-9780443237904.jpg)

[图 10.61](#Ch010_401-479_B9780443237904000244.xhtml#B-f0310) AccountType 的实例是否与 Account 的子类型相同？

在实践中，我们通常会移除或扩展 `AccountType` 上的值约束，以允许其他类型的账户（如 `LoanAccount`）。无论如何，我们都需要解决这个根本问题，用 ORM 术语表述为：*阴影点所表示的 `AccountType` 实例是否与子类型 `SavingsAccount` 相同？* 如果回答是，则我们在同一模型中出现了实例即类型的情况，使 `AccountType` 成为二阶类型。

在 UML 模式中，枚举类型的使用要求回答“否”，因为 UML 将枚举类型视为其实例为字面量的数据类型。然而，正如稍后讨论的，UML 允许我们使用 `AccountType` 的幂类型来重塑该情形，这要求回答“是”。

要使阴影点所表示的 `AccountType` 实例与子类型 `SavingsAccount` 相同，事实类型 `Account is of AccountType` 的语义至少应满足以下必要条件：
1.  “is of”谓词**意味着**“是……的成员”或“是……的实例”，即 ∈（集合成员资格）。
2.  **只有** `Account` 实例可以是 `AccountType` 实例的实例。

这些条件（组合起来我们称之为**同质集合成员资格**）源于**同一者的不可辨别性**（如果 `a = b`，则 `a` 和 `b` 具有相同的属性）。子类型 `SavingsAccount` 精确包含业务领域中所有可能的储蓄账户——没有其他事物可以是它的实例。如果阴影点所表示的 `AccountType` 实例**实际上是**子类型 `SavingsAccount`，那么只有账户才能与其建立实例关系。

如果我们允许类型 = 实例的解释，则必须使用高阶逻辑进行形式化，并应将同质集合成员资格的语义应用于此类分类关系。如果我们拒绝类型 = 实例的解释，则可以坚持使用一阶逻辑（至少用于形式化此类分类关系），并可选择将此类分类关系区分为特殊关系，为其提供相关的形式语义。

为标记这种区别，可为此类分类关联采用特殊的图形或文本修饰。例如，在 ORM 中，可在用于此目的的任何谓词的前向读法后附加冒号“:”（基于冒号有时但不总是用于引入类型的常见用法）。将此建议应用于 [图 10.61](#Ch010_401-479_B9780443237904000244.xhtml#f0310)(a) 中的模型会将“is of”替换为“is of:”。

为提供一种最小化的通用方法来处理此类分类关系，无论我们是否采用类型 = 实例的观点，都可使用冒号标记来区分任何此类关系，并赋予其**非对称**、**非传递**和**局部同质**关系的语义。形式为 `A R: B` 的事实类型是**局部同质**的，当且仅当 `B` 用作 `A` 的分类方案，但不用于任何其他类型（因此没有其他类型与 `B` 建立冒号关系）。对于 [图 10.61](#Ch010_401-479_B9780443237904000244.xhtml#f0310) 中的示例，这意味着只有 `Account` 实例可以是 `AccountType` 实例的实例。除非这样做会使读法别扭，否则为所有此类分类谓词使用相同的谓词读法（如“is of:”，甚至仅用“:”）很方便。读法的选择取决于语言。

非对称性和非传递性似乎是与此处相关的集合成员资格运算符（∈）的唯一属性。如果我们始终对分类关系使用相同的读法（如“is of:”），可将其视为全局应用的预定义谓词常量（该谓词的所有出现具有相同语义）。如果我们仅为这种同质情况保留冒号，则不得在分类方案（如 `Gender`）可应用于多个类型（如 `Person`、`Dog`）的情况下使用它。
