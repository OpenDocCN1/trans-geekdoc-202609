
Although the falling cost of hardware has made minimizing storage space less important, it can still become significant with very large volumes of data. Some NoSQL approaches provide ways of compressing data and storing sparse data in an efficient way, both to reduce storage space and to increase performance. However, this must be set against the increased storage required for the duplicate data that inevitably arises without normalization.

Dealing with large databases also raises issues of performance. This is always a concern with any kind of database, but an approach that might give an acceptable performance with a small database may be totally unacceptable in a larger system. The need to scale out in a distributed system also provides opportunities for improving performance. For example, the load on a server can be reduced by directing a proportion of the queries to other servers that hold copies of the same data.

In relational systems, it’s quite common to denormalize the database to increase performance for specific types of queries, principally by avoiding the penalty of joins between tables. In most NoSQL systems, this is a standard feature, although it would be misleading to call the structure “denormalized” because it may never have been normalized in the first place.

Of course, knowledge of anticipated traffic is essential to maximizing performance, especially the relative frequency of reading from the database versus writing to the database. NoSQL systems are typically aimed at scenarios with a large proportion of reads but few writes. Database records may be entered with some form of bulk loading of relatively static data. This also eases the problems of consistency: if there are no writes there is no way for the database to become inconsistent!

Another efficiency bonus claimed for NoSQL databases is the simplification (and reduced cost) of system management. This can be due to built-in automation of various administrative tasks that traditionally required special expertise and complex manual procedures. Examples include automated sharding, data distribution and replication, easier deployment, and easier system configuration.

Agile development methodologies have gained popularity in all areas of system development. They promise rapid delivery of an initial working system, the ability to respond promptly to changes as they occur during development, and risk reduction through the early identification of problems.

Some NoSQL products define a database schema as a burdensome overhead and promote the lack of a schema as a major agility benefit. The usual example quoted is the ad hoc addition of new data elements to an existing database. However, this is not as distinctive as it may seem. It’s also straightforward to extend a relational database using commands such as:

*   `create table MyNewTable …`
*   
```
alter table MyOldTable add myNewColumn …
```

The situation is more difficult when we consider deleting or modifying an existing structure. The impact of this depends on whether the database is intended to support a single application (such as a mobile phone app) or multiple applications (sometimes called an integration database).

The latter case is more typical of business systems. The two styles are illustrated in [Fig. 17.5](#Ch017_875-933_B9780443237904000050.xhtml#f0030).

In an application database, the developer of the application and the developer of the database are typically the same person. This makes it easy for changes in the application to be reflected in corresponding changes to the database structure and vice versa. However, things may not be so simple for an integration database because database changes to suit one application may require changes to other applications. Without some kind of schema, it becomes very difficult to manage database integrity. The lack of any authoritative reference to the data structure can also make general application development unnecessarily difficult and error prone.

NoSQL databases often store data in a form that directly matches its external usage, for example using the structure of a business document. This is typically encoded in the same way as the interchange formats described in [Chapter 16](#Ch016_831-873_B9780443237904000207.xhtml), with `JSON` being a common choice. Interfacing between object-oriented application code and a relational database is usually accomplished through some kind of object-relational mapping layer, and it’s possible to eliminate this so-called “impedance mismatch” in some NoSQL systems.

The definition of a relational table requires that a specific data type is allocated to each column. NoSQL databases are often considered in situations involving unstructured or ad hoc data or where data has high variability, and so dynamic typing may be preferable.

### Potential Drawbacks of NoSQL Databases

NoSQL databases have gained popularity due to their flexibility and scalability for certain use cases. However, they also have some drawbacks that need to be considered. Here are some common drawbacks associated with NoSQL databases:

*   **Lack of a standardized query language**: Unlike relational databases that use `SQL` as a standardized query language, each NoSQL database has its own unique query language or application programming interface (`API`). This can make it difficult to switch between different NoSQL databases or integrate them with existing systems. The lack of standardization leads to smaller user communities compared to `SQL` databases, which may make it more challenging to find support and resources.

*   **Data duplication and denormalization**: NoSQL databases typically denormalize data to improve performance and enable horizontal scalability. This means that data may be duplicated across multiple records or collections, leading to increased storage requirements. More importantly, maintaining data consistency across denormalized structures can involve extra complexity.

*   **Lack of data integrity constraints**: Unlike relational databases, which enforce data integrity through constraints such as primary keys, foreign keys, and unique indexes, NoSQL databases often lack built-in mechanisms for ensuring data consistency and enforcing relationships among data entities. This makes developers responsible for handling data integrity at the application level.

*   **Lack of mature tooling and ecosystem**: Although NoSQL databases have been around for some time, they generally have a less-mature tooling and ecosystem compared to relational databases. This can result in smaller community support, limited development frameworks, and fewer third-party integrations.

*   **Learning curve and developer expertise**: Working with NoSQL databases may require developers to learn new concepts, query languages, and data modeling techniques. This can increase the learning curve and the need for specialized expertise, especially when migrating from a relational database environment.

*   **Limited transactional consistency guarantees**: Some NoSQL databases sacrifice strong consistency guarantees in favor of high availability and partition tolerance, following the `CAP` theorem. This means that in certain failure scenarios, trade-offs are made that can lead to eventual consistency or data staleness. There is also an increased risk of inconsistent data due to the eventual consistency model used by some NoSQL databases.
