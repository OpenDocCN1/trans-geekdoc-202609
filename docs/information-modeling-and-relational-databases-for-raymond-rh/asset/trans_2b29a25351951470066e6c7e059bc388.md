
除非被另一个初始化过程（例如构造函数）覆盖，否则声明的初始值会在创建该类的对象时被赋值。这类似于数据库中*默认值*的概念，即在插入元组时，如果用户未提供值，则属性可能会被赋予预先声明的默认值。然而，UML 仅在其他语境中使用“默认值”一词（例如模板和操作参数），且一些作者声称默认值不是 UML 模型的一部分（[Rumbaugh et al., 1999](#Ch009_347-399_B9780443237904000013.xhtml#bb1125)，第 249 页）。

SQL 标准将**null**视为默认值的一种特殊实例，UML 支持这一点，因为规范指出“0..1 的多重性提供了 null 值的可能性：值的缺失”。因此，UML 中的可选属性可用于建模一种特性，当映射到关系数据库时，它将表现为一个默认值为 null 的列。推测，对于任意 *n* > 1，多重性 `[0..*]` 或 `[0..*n*]` 也允许多值属性为 null，尽管也可以使用空集合代替。

目前，ORM 没有对初始/默认值的显式支持。一个可能的扩展可以允许为 ORM 角色指定默认值。在元层面，我们添加事实类型 `Role has default-Value`。在外部层面，该事实类型的实例可以在谓词属性表上指定，或在图表上输入（例如，通过将注解 `d: value` 附加到角色上，并最好允许切换此显示的开/关）。例如，[图 9.48](#Ch009_347-399_B9780443237904000013.xhtml#f0245)(b) 中 `NrColors` 扮演的角色被分配了默认值 1。当映射到 SQL 时，这应在 `ClipArt.nrColors` 的列定义中添加声明“default 1”。

为了支持 UML 允许的复合初始值，可以为由复合标识的对象类型（共引用或嵌套）扮演的 ORM 角色指定复合默认值。当共引用涉及由相同或兼容对象类型扮演的至少两个角色时，需要一个顺序来消除复合值含义的歧义。例如，在[图 9.48](#Ch009_347-399_B9780443237904000013.xhtml#f0245)(b) 中，`Resolution` 扮演的角色被分配了默认复合值 `(640, 480)`。为确保 640 应用于水平像素计数，480 应用于垂直像素计数（而不是反过来），此顺序需要应用于外部唯一性约束的定义角色。ORM 工具通常根据输入此约束时选择角色的顺序来确定此顺序。

如果一个对象类型扮演的所有或大多数角色具有相同的默认值，则允许为对象类型本身指定默认值可能很有用。这可以通过在 ORM 中添加元事实类型 `ObjectType has default-Value` 并提供一些表示法来实例化它来实现（例如，通过对象类型属性表中的条目，或通过用 `d: value` 注解对象类型形状）。这对应于 SQL 标准中 `create-domain` 语句允许的默认子句。请注意，对象类型默认值总是可以用基于角色的默认值来表示，但反之则不然（因为默认值可能随角色而异）。

默认值的规范并不涵盖关于一般默认信息可能出现的所有情况。[Halpin and Vermeir (1997)](#Ch009_347-399_B9780443237904000013.xhtml#bb0770) 中讨论了一个为 ORM 提供更多默认信息支持的提议，但这超出了 UML 或 SQL 中内置的默认支持范围。默认信息可以通过使用谓词来非正式地建模，以向人类传达这一意图。例如，我们可以使用 1:n 事实类型 `Medium is default preference for SoftProduct` 来指定软产品（如音乐、视频、软件）交付的默认媒介（如“CD”、“DVD”）偏好。

在默认值与实际值重叠的情况下，我们可能还希望将相关事实类型的实例分类为实际或默认（例如 `Shipment used Medium`）。对于唯一性约束跨越 *n* **−** 1 个角色的典型情况，这可以通过包含指示默认状态的事实类型来实现（例如 `Shipment was based on Choice {actual, default}`），从而在数据库中产生额外的列来记录状态。虽然这种方法是通用的，但它要求建模者和用户承担全部责任来区分实际值和默认值。

在 UML 中，除了二元关联的角色（端点）外，还可以对属性的*可变性*施加限制。不清楚可变性是否可以应用于 *n*-元关联的端点。UML 2 识别以下四种可变性值，在给定时间只能应用其中一种：

*   `unrestricted`
*   `readOnly`
*   `addOnly`
*   `removeOnly`

默认可变性是“unrestricted”（允许任何更改）。值“unrestricted”以前称为“changeable”，而“changeable”以前称为“none”。其他设置可以在大括号中显式声明。对于属性，大括号放在属性声明的末尾。对于关联，大括号放在关联的另一端，远离约束所应用的对象实例。

回想一下，在 UML 中，“链接”是关联的实例。术语“`readOnly`”（以前称为“frozen”）意味着一旦插入了属性值或链接，就不能更新或删除它，也不能向该属性/关联添加额外的值/链接（针对受约束的对象实例）。

术语“`addOnly`”意味着虽然原始值/链接不能被删除或更新，但可以向该属性/关联添加其他值/链接（针对受约束的对象实例）。显然，只有当属性/关联角色的最大多重性超过其最小多重性时，`addOnly` 才有意义。术语“`removeOnly`”意味着对现有属性值或链接允许的唯一更改是删除它。

作为一个简单但不切实际的示例，请参见[图 9.49](#Ch009_347-399_B9780443237904000013.xhtml#f0250)。此处 `Employee` 的员工编号、出生日期和出生国均为 `readOnly`，因此它们不能从原始值更改。例如，如果我们给员工分配员工编号 007，并输入其出生日期为 02/15/1946、出生国为“Australia”，那么我们永远无法对此进行任何更改或添加。

对于每个员工，语言集合和访问过的国家集合均为 `addOnly`。假设对于员工 007，我们最初将其语言设为 {Latin, Japanese}，访问过的国家设为 {Japan}。只要数据库中引用了员工 007，这些事实就不能被删除。但是，我们可以对此进行添加（例如，稍后我们可能添加员工 007 会说 German 且访问过 India 的事实）。

默认情况下，其他属性是可变的。例如，员工 007 可能合法地将其姓名从“Terry Hagar”改为“Hari Seldon”，并将想访问的国家从 {Ireland, USA} 改为 {Greece, Ireland}。
