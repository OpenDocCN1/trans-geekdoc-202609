
# 查询语言与概念查询方法

## 关系与面向对象查询语言

对于关系型数据库，SQL 和 示例查询 更具表达力。然而，复杂查询甚至用自然语言很容易表达的查询（例如：谁不会说超过一种语言？）对于非技术用户来说，用这些语言表达起来可能很困难。此外，即使查询的含义未变，如果概念模式或内部模式的相关部分发生变化，SQL 或 QBE 查询通常也需要修改。最后，关系查询优化器忽略了许多源于约束知识的语义优化机会。

面向对象和对象关系 DBMS 的查询语言也面临类似问题。它们额外的结构（例如：集合、数组、包和列表）往往导致用户编写和系统优化的复杂性都更高。例如，对象查询语言 (OQL) 通过各种导航函数以及组合和扁平化结构的函数扩展了 SQL，从而迫使用户直接处理信息在内部的存储方式 ([Cattell and Barry, 2000](#Ch018_935-1005_B9780443237904000104.xhtml#bb0175))。在物理层面，编程语言可用于直接访问内部结构（例如：使用指针和记录），但这种非常低层次的查询编写方法完全不适合最终用户。

## 自然语言查询工具

一些商业工具允许用户直接用英语输入查询，然后将其翻译成 SQL 或 MDX 等数据库查询语言。此类早期工具常受困于歧义性和表达能力问题，以及生成的 SQL 代码的正确性问题。我们所考察的大多数自然语言输入工具都要求你花费大量精力建立字典，以将概念术语关联到底层数据库结构，而且它们大多在处理自然语言输入方面做得不完美。考虑到自然语言固有的歧义性和复杂性，这并不令人惊讶。

### English Query 方法

解决歧义问题的一种方法是采用 `English Query`，它多年前曾包含在 Microsoft SQL Server 中，但现已不再提供。当你用英语输入一个问题时，它会被重述以指示所采用的理解。有时会给出不止一种重述，你可以选择能传达你预期含义的那一个。

当然，能被理解的问题类型是有限的，而且你需要花时间建立语义模型与数据库结构之间的连接。例如，如果你想要在除外键引用主键以外的表之间建立连接，你需要预先显式添加此连接。此外，生成的 SQL 可能不如你自己编写的那样高效。

然而，一旦完成所有这些工作，你就可以让非技术最终用户用通俗易懂的英语查询数据库。虽然常见的、可预测的查询最好通过预写过程提供，但 `English Query` 对于特设查询特别有用。例如，参考上一节中的数据集市模式，并假设已进行充分设置，问题“哪个区域拥有最多的商店？”可能会生成以下 SQL 代码：

```
select top 1 with ties dbo.Store.region as “Region”, count(*) as “count”
from   dbo.Store
where dbo.Store.region is not null
group by dbo.Store.region
order by 2 desc
```

除了返回拥有最多商店的区域外，该查询还返回这些区域中的商店数量，这可能不是我们想要的。此外，`where` 子句和 `order by` 子句都是冗余的。但对于无法编写 SQL 查询的非技术用户来说，这些都是小问题。对于 OLAP 应用，`English Query` 也被用于生成 MDX 查询。例如，参考上一节讨论的 SalesCube，问题“列出单位销量最多的三个商品”可能会导致重述“显示总单位销量最高的三个商品”以及以下 MDX 查询：

```
select { Measures.[UnitsSold] } on columns,topcount([Item].[ItemCode].members, 3, Measures.[UnitsSold] ) on rowsfrom [SalesCube]
```

正如这些示例所示，自然语言的自由输入极大地拓展了数据库的受众范围，使任何会写字的人都能使用数据库。随着语言识别技术的成熟，它也将使任何会说话的人都能使用数据库。然而，在该技术变得完全可靠之前，我们还有很长的路要走。

## 概念查询语言

已经提出了几种 `conceptual query languages`，允许用户直接在概念模式上编写查询。这些语言提案大多是学术研究项目，充其量只有原型工具支持，且通常基于 ER 模式（例如：ERQL、Super、Hybris）或演绎模型（例如：CBQL）。这些对于初学者来说通常具有挑战性，而且它们对属性的使用使查询面临不稳定性，因为随着应用模型的演进，属性可能会演变为实体或关系。

## 基于概念模式的查询

通过采用一种不同的方法：`conceptual-schema-based queries`，可以一举消除歧义和繁琐的字典准备问题。在这里，用户通过选择现有概念模式中的路径来发出查询，而不是使用自由文本输入，因此不会产生歧义。正如稍后讨论的，如果使用 ORM 概念模式，则无需预先声明任何连接路径，因为 ORM 对象类型是所有连接所基于的语义域。由于 ORM 在其基本概念模型中不包含属性，它还避免了基于属性的查询的不稳定性问题，后者在属性演变为关系时需要重新编写（见后文示例）。此外，ORM 的唯一数据结构是关系类型，提供了一个简单的、基于句子的框架。基于这些原因，我们认为 ORM 概念查询技术是现有所有方法中潜力最大的。

## 参考与构想语言 (RIDL)

第一个重要的基于 ORM 的查询语言是参考与构想语言 (RIDL)，一种兼具声明式和过程式特点的混合语言 ([Meersman, 1982](#Ch018_935-1005_B9780443237904000104.xhtml#bb0965); [Meersman et al., 1984](#Ch018_935-1005_B9780443237904000104.xhtml#bb0975))。RIDL 是一种文本语言，用于定义、填充和查询 NIAM 模型，NIAM 是面向事实建模的早期版本。它是在布鲁塞尔大学的 Control Data 研究实验室开发的，是有史以来第一个真正被实现的概念查询语言。让我们看一些 RIDL 示例。考虑一个包含以下事实类型的军事概念模式：军官 拥有 军衔；军官 出生于 年份。在 RIDL 中，这些事实类型通常会被声明为 Officer having Rank；Officer born-in Year。要查找 1950 年前出生的中士，可以使用以下 RIDL 查询：

```
LIST Officer (having Rank ‘sergeant’ AND born-in Year < 1950)
```
