
# “OODBMS宣言”中的特性列表 ([Atkinson et al., 1990](#Ch017_875-933_B9780443237904000050.xhtml#bb0020))

![t17-03-9780443237904](images/B9780443237904000050/t17-03-9780443237904.jpg)

**复杂对象** 由更简单的对象通过构造器构建而成。该宣言提议这些构造器至少应包括集合、列表和元组，并且应是正交的（即可以按任意顺序递归应用）。例如，一个对象可能是元组的集合的集合的列表。在关系模型中构造器不是正交的（仅允许原子值的元组集合），嵌套关系模型中也不是（例如，顶层构造必须是集合）。复杂对象的概念被认为很重要，因为它允许我们以直接、自然的方式对复杂结构进行建模。

**对象标识** 的基本思想是对象应由系统生成的对象标识符（OID）来标识，而不是由其属性的值来标识。这与关系模型形成鲜明对比，在关系模型中，例如元组由其主键的值来标识。

除其他作用外，OID 还有助于跟踪那些基于外部值的标识可能随时间变化的对象。这可能因简单的重命名而发生。例如，电视频道 0 变为频道 10，或女性婚后改姓。更极端的情况是，引用方案本身可能发生变化（例如，由学号标识的学生变为由工号标识的员工）。

面向对象意义上的对象标识符一定程度上克服了这个问题，因为它们是刚性标识符（即始终指代同一对象）。它们由系统生成、不可重用、不可变，且通常是隐藏的。在 ODB 系统中，它们可能被实现为代理（逻辑标识符或自增计数器，通过索引映射到物理地址）、类型化代理（这使得类型间的迁移变得困难）或结构化地址。

**封装** 涉及将对象的操作和数据捆绑在一起，正常情况下通过其操作接口访问对象，实现细节被隐藏。例如，雇佣、解雇和晋升员工被视为 `Employee` 上的操作，并与其封装在一起。操作的实现通常称为“方法”。

封装包含这样的思想：正如在概念模式中一样，对象应按**类型**或**类**进行分类。此外，应提供某种形式的**继承**机制（例如，使子类型可继承其超类型的数据和操作）。子类型可能拥有与其超类型函数同名的特化版本函数。在这种情况下，当在子类型上调用该操作时，特化版本通常会**覆盖**更通用的版本。

例如，彩色等边三角形的显示过程可能不同于多边形的通用显示过程。存在各种覆盖选项。

**计算完备性** 要求数据操作语言能表达任何可计算函数（如有必要，可通过调用编程语言）。**可扩展性** 要求用户可定义自己的类型，且系统应像支持内置类型一样支持它们。

## “第三代DBMS宣言”

部分作为对 OODB 宣言的回应，一群学术界和工业界的研究人员提出了另一种“第三代 DBMS 宣言”([Stonebraker et al., 1990](#Ch017_875-933_B9780443237904000050.xhtml#bb1205))。在此方案中，他们将层次和网络系统称为第一代，关系系统称为第二代。按此划分，第三代 DBMS 被视为下一代。

该宣言规定了下一代 DBMS 应遵循的三条基本原则和 13 条详细提案（见[表 17.4](#Ch017_875-933_B9780443237904000050.xhtml#t0025)）。该提案本质上主张用面向对象特性扩展现有关系系统，并有效地为当今的对象-关系数据库系统奠定了基础，我们稍后将讨论。

[表 17.4](#Ch017_875-933_B9780443237904000050.xhtml#B-t0025)

[Stonebraker et al. (1990)](#Ch017_875-933_B9780443237904000050.xhtml#bb1205) 提出的下一代 DBMS 特性。

![t17-04-9780443237904](images/B9780443237904000050/t17-04-9780443237904.jpg)

尽管支持若干面向对象特性，但该小组反对以否定关系方法关键进步的方式实现它们。例如，关系系统中的所有事实都存储在表中。相反，在层次、网络和对象数据库系统中，某些事实可能被指定为结构之间的链接，访问数据时需要指定导航路径。

因此，OO 查询通常需要指定访问路径。尽管路径表达式通常比关系查询更紧凑，但它们对现有导航链接的依赖可能使高效执行临时查询变得困难。

## 示例：大学记录 ORM 模式

以[图 17.16](#Ch017_875-933_B9780443237904000050.xhtml#f0085) 中图式化的 UoD 为例。学生要么持有学位，要么正在攻读学位（或两者兼有）。排他约束禁止学生重新注册其已持有的学位。学科仅针对在读学生记录，如子集约束所示。因为这不是等值约束，学生可在选择学科前注册学位。

![Fig. 17.16 An ORM schema about university records.](images/B9780443237904000050/f17-16-9780443237904.jpg)

[图 17.16](#Ch017_875-933_B9780443237904000050.xhtml#B-f0085) 关于大学记录的 ORM 模式。

该模式的这一方面也可通过引入子类型 `CurrentStudent` 来建模，将可选的 `takes` 角色附加到该子类型，定义为：**每个** `CurrentStudent` **是** 某个 **正在攻读****某个** `Degree` 的 `Student`。

每个学科由其学科代码标识，但也有唯一的标题。对于某些学科，可能有讲座计划可用。这列出了各讲座讨论的主题。例如，`CS114` 的第 10 讲可能讨论关系投影、关系选择和自然连接。带脚注的文本约束限定（并隐含）了外部唯一性约束，要求讲座在每个学科内从 1 开始编号。

[图 17.16](#Ch017_875-933_B9780443237904000050.xhtml#f0085) 的概念模式（减去某些约束）大致可用对象定义语言（ODL）语法在 ODB 模式中指定，如 [Cattell and Barry (2000)](#Ch017_875-933_B9780443237904000050.xhtml#bb0175) 所规定。

```
class Student {
    attribute unsigned long studentNr;
    attribute string studentName;
    attribute set<string> degreesHeld;
    attribute string currentDegree;
};
class CurrentStudent extends Student {
    relationship set<Subject> takes inverse Subject::is_taken_by;
};
class Subject {
    attribute string subjectCode;
    attribute string title;
    attribute unsigned short credit;
    relationship set<CurrentStudent> is_taken_by inverse CurrentStudent::takes;
    relationship list<Lecture> has inverse Lecture::is_for;
};
```

```
class Lecture {
    attribute unsigned short lectureNr;
    relationship Subject is_for inverse Subject::has;
    attribute set<string> topics;
};
```

虽然可读，但此 OO 模式不完整，还需为概念模式中的额外约束编写额外代码。我们可以在 UML 类图上显示此模式，将额外约束放在注释中（例如，异或、配对排除和子集约束）。一般来说，OO 模式最好作为 ORM 模式的抽象来开发。
