

# 时间数据与数据集市设计

为了便于历史趋势分析，应在所需粒度（例如每日、每周或每月）包含适当的时间数据。例如，假设一个操作数据源存储以下事实类型：`Employee manages Store`（员工管理门店）。随着时间的推移，一家门店可能会有不同的经理。为了保留这些变更的历史记录，当门店管理事实被加载到数据仓库时，可将加载日期插入键中，以填充历史事实类型 `Employee on Date managed Store`（员工于某日期管理门店）。时间建模的基本方面已在[第 10.3 节](#Ch010_401-479_B9780443237904000244.xhtml#s0030)中讨论。

为了提高查询性能，数据集市（通常也包括数据仓库）往往包含派生数据和反规范化结构。作为派生数据的一个简单示例，假设操作源存储事实类型 `Customer was born on Date`（客户出生于某日期）。对于人口统计分析，我们可能关心产品偏好如何受客户年龄影响。在这种情况下，在数据集市中存储客户的年龄，甚至仅存储年龄段，而非其出生日期，可能更为合适，可使用如 `Customer on Date belonged to AgeGroup`（客户于某日期属于某年龄段）这样的事实类型。快照日期会在事实类型增量更新时插入。

## 销售数据集市示例

一个结合了派生和反规范化的更典型示例是用于分析销售趋势的数据集市。此类集市的 ORM 概念模型（简化版）如[图 18.2](#Ch018_935-1005_B9780443237904000104.xhtml#f0015)所示。在该论域（UoD）中，公司通过位于同一国家（如美国）各城市的众多门店进行销售。城市通过其名称和州的组合来标识（例如，俄勒冈州的波特兰不同于缅因州的波特兰）。

![Fig. 18.2 A conceptual schema for the Sales data mart (derivation rules omitted).](images/B9780443237904000104/f18-02-9780443237904.jpg)

[图 18.2](#Ch018_935-1005_B9780443237904000104.xhtml#B-f0015) 销售数据集市的概念模式（省略派生规则）。

州被划分为区域（例如，俄勒冈州和华盛顿州属于西北区域）。销售商品拥有唯一代码和标题，并属于某个类别（如开发工具）。发票行项通过其在给定发票上的行号来标识，并记录商品的销售情况以及该商品的数量和单价。每个发票行项的行总额通过数量乘以单价得出，并予以存储。

为了支持随时间的销售分析，每个日期的月份编号、季度编号和年份被派生并存储。虽然此处使用的是自然年，但我们也可以改用会计年度，或两者兼用。在[图 18.2](#Ch018_935-1005_B9780443237904000104.xhtml#f0015)中，被派生并存储的事实类型标记为“**”，但为简化起见，省略了派生规则。

使用默认的 `Rmap` 算法，该概念模式映射为以下六个表模式：

* `LineItem`(invoiceNr, lineNr, itemCode, quantity, unitPrice, lineTotal)
* `Invoice`(invoiceNr, saleDate, storeNr)
* `Item`(itemCode, itemTitle, category)
* `Store`(storeNr, stateCode, cityName)
* `StateLocation`(stateCode, region)
* `TimeDimension`(saleDate, saleYear, QuarterNr, MonthNr)

然而，为提高查询性能，决定将关系模式反规范化为四个表模式，如[图 18.3](#Ch018_935-1005_B9780443237904000104.xhtml#f0020)所示。

![Fig. 18.3 A denormalized, relational star schema for the model in Fig. 18.2.](images/B9780443237904000104/f18-03-9780443237904.jpg)

[图 18.3](#Ch018_935-1005_B9780443237904000104.xhtml#B-f0020) 基于[图 18.2](#Ch018_935-1005_B9780443237904000104.xhtml#f0015)模型的反规范化关系星型模式。

`Item` 和 `TimeDimension` 表是规范化的，但 `Sale` 和 `Store` 表不是。`Sale` 表被反规范化至 1NF，因为 `saleDate` 和 `storeNr` 函数依赖于 `invoiceNr`，而后者只是主键的一部分。`Store` 表被反规范化至 2NF，因为 `region` 函数依赖于非键属性 `stateCode`。

以这种方式进行反规范化的决定通过标注概念模式来指示，如[图 18.2](#Ch018_935-1005_B9780443237904000104.xhtml#f0015)所示。此处，*键对象类型*被*着色阴影*。当且仅当一个对象类型的首选标识方案被用作某表的主键时，它才是键对象类型。从图形上看，每个键对象类型形成一棵树的根，其中每个节点是一个对象类型，每条边是一个函数（n:1 或 1:1）谓词。

例如，从 `Store` 对象类型出发，我们沿函数链向下追踪至叶对象类型 `CityName` 和 `Region`，沿途收集所有事实类型，根据 `Store` 的标识符将它们归入单个表中。

如果函数链遇到键对象类型（或叶节点、或非函数谓词），则停止。例如，从 `LineItem` 开始，我们收集其所有函数事实类型以及 `Invoice` 的函数事实类型，但无法越过 `Date`、`Store` 或 `Item`，因为它们是键对象类型。这形成了[图 18.3](#Ch018_935-1005_B9780443237904000104.xhtml#f0020)中的 `Sale` 表。

反规范化的 `Sale` 和 `Store` 表包含嵌入的函数依赖（例如 `stateCode` → `region`），但无需强制执行这些依赖，因为它们已在数据集市所源自的操作表中得到强制执行。由于操作表用于基础更新，而非数据集市，因此以这种方式反规范化数据集市是可以接受的。减少表的数量消除了许多连接操作的需要，从而加快了查询速度。

## 星型模式与术语

[图 18.3](#Ch018_935-1005_B9780443237904000104.xhtml#f0020)中的模式由一个中心表（`Sale`）通过外键连接链接到外围表（`Item`、`Store` 和 `TimeDimension`）组成。这被称为*星型模式*，因为中心表可被视为星型模式的中心，其外围表成为“星星的尖角”。在数据仓库术语中，*中心表*称为*事实表*，外围表称为*维度表*。由于所有表都包含事实，“事实表”一词在此处颇不恰当。此外，ORM 使用“事实表”指代原子事实表。为避免混淆，我们在该语境下将使用更具描述性的“中心表”，而非更通用的“事实表”。

某些方法要求中心表的主键包含其所有维度表的键。这将要求[图 18.3](#Ch018_935-1005_B9780443237904000104.xhtml#f0020)中 `Sale` 表的 (`invoiceNr`, `lineNr`) 键扩展为超键 (`invoiceNr`, `lineNr`, `itemCode`, `saleDate`, `storeNr`)。从纯逻辑角度来看，这是不必要的，因为可以在非键属性上进行连接。

如果某些维度表本身被用作其他星型的中心表，则整体模式称为“雪花模式”。一组共享维度表的星型模式有时称为“星系”。

## OLAP 与数据挖掘

数据仓库和数据集市用于*联机分析处理 (OLAP)* 和*数据挖掘*。OLAP 一术语由 E.F. Codd 引入，用于描述针对决策支持的、对维度化和聚合数据的交互式分析（[Codd et al., 1993](#Ch018_935-1005_B9780443237904000104.xhtml#bb0240)）。数据挖掘涉及对数据的深度分析，通常使用复杂的统计技术和复杂的算法来检测模式。如今，许多 OLAP 和数据挖掘工具正在使用中。每个主题本身都值得专著一本书。本节剩余部分简要概述 OLAP。
