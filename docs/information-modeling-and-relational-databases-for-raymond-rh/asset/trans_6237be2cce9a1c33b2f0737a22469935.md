

现在请看 [图 11.10](#Ch011_481-537_B9780443237904000141.xhtml#f0055) 中的 ORM 模式。请注意*等值约束*，它显示为两个表的 `empNr` 字段之间一条带箭头的虚线。之所以需要它，是因为 `Academic` 扮演的两个角色都是强制的，且每个角色都映射到不同的表。等值约束等同于方向相反的两个子集约束。这导致了一个*引用循环*，因为每个表都引用了另一个表。

![图 11.10 等值约束导致引用循环。](images/B9780443237904000141/f11-10-9780443237904.jpg)

[图 11.10](#Ch011_481-537_B9780443237904000141.xhtml#B-f0055) 等值约束导致引用循环。

从 `Qualification.empNr` 到 `Academic.empNr` 的子集约束是一个简单的外键约束，因为它引用了主键。但从 `Academic.empNr` 到 `Qualification.empNr` 的子集约束不是外键约束，因为它的目标只是主键的一部分。

后一个子集约束可以通过多种方式强制实施（例如，通过断言、触发器或存储过程）。引用循环通常源于没有简单唯一性约束的强制角色。因为引用循环的实施需要特殊处理，所以如果可能的话，应避免这种概念约束模式。然而在我们的例子中，每位教职员工至少拥有一个学位这一业务规则似乎是合理的，因此这种情况下我们保留原样。

在离开这个例子之前，关于命名还值得再提几点。表名“Qualification”是传达“教职员工由其学位决定资格”这一概念的众多可能选择之一。另外两个选择是使用关联名（“Holds”）或连接对象类型名（“AcademicDegree”）。部门列命名为“deptCode”，是因为我们预期其他部门事实（此处未显示）将记录在部门表中，并且我们想避免用“department”同时命名一列和一个表。同样，学位列命名为“degreeCode”而不是“degree”，是因为我们可能想记录关于学位的其他事实（例如它们的标题）。一般来说，如果某列底层的对象类型也将作为另一个表主键的底层对象类型，建议在列名中包含引用方案。

现在请看 [图 11.11](#Ch011_481-537_B9780443237904000141.xhtml#f0060)。这里，每匹马都记录了其性别和体重。每场比赛最多有一个获胜者（我们不允许平局）。规则 1 没有复合键可用。性别和体重事实类型具有连接到 `Horse` 的函数角色。根据规则 2，这两个关联必须分组到同一个表中，该表以 `Horse` 的标识符为键。类似地，时间和获胜事实类型是 `race` 的函数，并被分组到 `Race` 表中。我们选择列名“raceTime”而不是“time”，主要是因为“time”是 SQL 的保留字。最好避免将保留字用作名称，因为它们需要双引号。我们稍后将提供 SQL 保留字在线列表的链接。使用列名“winner”而不是“horseName”是为了更好地传达语义。

### 映射 1:1 关联

现在让我们考虑一些涉及*1:1 事实类型*的例子。在 [图 11.12](#Ch011_481-537_B9780443237904000141.xhtml#f0065) 的概念模式中，`Bankcard` 和 `Client` 共享一个 1:1 关联。如果我们确定 `Bankcard` 不会扮演其他函数角色，通常最好将 1:1 事实类型与其他函数事实类型分组到同一个表中，如图所示。

![图 11.12 如果 Bankcard 不扮演其他函数角色时的映射选择。](images/B9780443237904000141/f11-12-9780443237904.jpg)

[图 11.12](#Ch011_481-537_B9780443237904000141.xhtml#B-f0065) 如果 Bankcard 不扮演其他函数角色时的映射选择。

`bankcard` 列是可选的，但此处空值的劣势通常被将所有数据放在一个表中的优势所抵消。`bankcard` 的下划线表示其非空值的唯一性约束。因为它可能包含多个空值，所以 `bankcard` 列不能用于标识行，因此不能作为主键。由于有两个唯一性约束，我们对 `clientNr` 使用双下划线以将其突出显示为主键。

然而，如果 `Bankcard` 确实扮演其他函数角色，则银行卡所有权关联应分组到 `Bankcard` 表中，如 [图 11.13](#Ch011_481-537_B9780443237904000141.xhtml#f0070) 所示。请注意，`Bankcard` 扮演的 `owned` 角色现在是显式强制的；在前一个例子中，它只是隐式强制的（因为它是 `Bankcard` 扮演的唯一角色）。请注意，*该 1:1 关联的只有一个角色是强制的*。在这样的非对称情况下，通常最好*在强制角色一侧分组*，如图所示。

![图 11.13 如果 Bankcard 扮演另一个函数角色时的映射选择。](images/B9780443237904000141/f11-13-9780443237904.jpg)

[图 11.13](#Ch011_481-537_B9780443237904000141.xhtml#B-f0070) 如果 Bankcard 扮演另一个函数角色时的映射选择。

为了进一步说明这一想法，请看 [图 11.14](#Ch011_481-537_B9780443237904000141.xhtml#f0075) 中的概念模式。每位员工主要由其员工编号标识，但也拥有唯一的姓名（这不寻常，但有些部门通过细化原本重复的姓名来这样工作）。每个部门有一位主管，且主管只领导一个部门。因为并非所有员工都是部门主管，所以领导角色是可选的。

![图 11.14 heads 事实类型在强制角色一侧分组。](images/B9780443237904000141/f11-14-9780443237904.jpg)

[图 11.14](#Ch011_481-537_B9780443237904000141.xhtml#B-f0075) heads 事实类型在强制角色一侧分组。

因此，`Employee` 和 `Department` 之间的 1:1 关联对于 `Employee` 是可选的，但对于 `Department` 是强制的。因为通常最好在强制角色一侧分组，所以这里意味着将 `headEmployeeNr` 列包含在 `Department` 表中，如图所示。

`NORMA` 工具允许您通过简单地编辑其名称属性来编辑关系模式中生成的列名。例如，我们可以分别将“employeeNr”、“employeeName”和“departmentCode”缩短为“empNr”、“empName”和“deptCode”。

假设我们在可选一侧分组 1:1 关联，即向 `Employee` 表添加 `deptHeaded` 列。这将导致以下关系模式：

![](images/B9780443237904000141/u11-01-9780443237904.jpg)

这种替代方案有两个缺点。首先，可选的 `deptHeaded` 列允许空值（不像强制的 `headEmpNr` 列）。在其他条件相同的情况下，如果可能应避免空值。除了消耗存储空间外，它们通常也让人难以处理。第二个缺点是我们现在在表之间有了一个等值约束，而不仅仅是一个子集约束。

原则上，我们可以将涉及 1:1 关联的两个对象类型的所有函数谓词分组到一个表中。以我们的例子为例，这给出了方案 `EmployeeDept`(`empNr`, `empName`, `salary`, [`deptHeaded`, `deptBudget`])。这里，将最后两列放在同一个方括号内声明了其中一个为空当且仅当另一个也为空。

然而，除了需要两个可选列和一个要求它们同时为空的特殊约束外，这种分组是不自然的。例如，主键暗示整个表处理的是员工而不是他们的部门。出于这些原因，通常应避免这种单表方法。
