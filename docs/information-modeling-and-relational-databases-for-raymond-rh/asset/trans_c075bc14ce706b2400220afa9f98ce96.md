
# 演绎数据库系统

请注意，OO 类对应于从概念模式抽象出的主要对象类型。因此，它们为构建应用程序的屏幕表单提供了有用的基础。封装涉及添加通用操作以及特定类型的操作（例如，可能会向 `Student` 添加 graduate 操作）。

ODB 方法的一个问题是它将太多层级混合在一起——OO 模式包含概念、逻辑和物理元素。它还涉及关联的冗余规范。例如，考虑事实类型 `Student takes Subject`。在 OO 模式中，这被指定了两次：一次在 `CurrentStudent` 上，另一次在 `Subject` 上。

在指定 OO 模式时，使用了逆向引用来声明 `CurrentStudent` 与 `Subject` 之间以及 `Subject` 与 `Lecture` 之间的双向对象链接。这使得可以使用路径表达式指定任一方向的查询。如果链接变为单向，这种通用性就会丧失。请注意，在关系模型中不存在此类导航问题，尽管当然许多查询将需要连接。虽然连接可能会降低速度，但对其使用没有限制，因为它们不需要预先建立链接。相比之下，ODB 方法通过“硬连线”查询中使用的链接来获得效率。这使得难以优化临时查询。

依赖模式本身中预先声明的访问路径来实现效率的问题，在模式演变时会加剧。届时我们可能不得不重置导航路径以针对新情况进行优化，而不能像当前的关系系统那样，仅依赖系统优化器来完成这项工作。

这并不是说 ODB 是个坏主意，或者复杂对象不应在实现层面建模为复杂对象。许多复杂结构用关系术语建模很别扭。然而，我们应该能够以一种清晰的方式指定此类结构，而不必求助于低级机制。

与 ODB 不同，关系数据库基于单一数据模型，该模型正式基于谓词逻辑。此外，关系 DBMS 现在占据主导地位，并且许多正在被扩展以解决前面提到的几个缺陷。这种扩展的关系数据库系统通常称为*对象-关系数据库*（ORDB）系统。这些本质上是通过添加对许多 OO 特性的支持来扩展的关系 DBMS，例如额外的数据类型（空间、图像、视频、文本……）、构造器（数组、集合……）和继承。一些主要的商业系统通过允许插入模块来支持扩展数据类型。此类模块可能由供应商或第三方开发。这些模块被称为“关系扩展器”、“数据刀片”或“数据盒”。

SQL 标准已大幅逐步扩展，以包含若干面向对象特性（例如，用户定义类型和函数、封装、对 oid 的支持、子类型、触发动作和计算完备性）以及演绎特性（例如，递归并）。

鉴于关系 DBMS 庞大的安装基础、这些产品的持续扩展、将应用程序移植到新数据模型的成本，以及 SQL 标准的广泛采用，下一代 DBMS 很可能会从当前的关系产品中演变而来。正如印度教吸收了威胁其存在的其他宗教的特性一样，关系模型很可能会吸收面向对象信仰的有趣特性，而不会被其取代。

SQL 基础 DBMS 中发生的所有变革是否真正可取，这是有争议的。虽然扩展数据类型（空间、视频等）的使用显然是一个进步，但在许多情况下，构造器（数组、多重集等）的使用是值得商榷的，因为它们可能使为临时查询和更新设计高效数据库变得更难，并使编写优秀优化器的任务复杂化。

关于许多 OO 特性如何被移植到关系模型上的详细评论，请参见 [Date (2000)](#Ch017_875-933_B9780443237904000050.xhtml#bb0300) 和 [Date and Darwen (1998)](#Ch017_875-933_B9780443237904000050.xhtml#bb0310)。无论如何，关系和对象-关系系统目前在商业上占据主导地位，而其他竞争者如对象数据库系统正努力争取任何有意义的市场份额。

SQL 包括数组、行类型和多重集。一个挑战是对这些集合建模并提供映射算法以高效实现它们。各种构造器（例如用于集合、包、序列和模式）已被添加到某些版本的 ORM 和 ER 中。此外，ORM 和 UML 都允许将某些类型的集合表示为概念模式上的映射注解。虽然在概念模型中使用集合类型有利于映射到等效的实现结构，但直接在概念层面建模复杂对象通常要困难得多，并且通过口头化和填充实例来验证它们极其别扭。复杂对象也倾向于被过度使用，而更简单的解决方案被忽视。关于集合类型的进一步讨论，请参见 [第 10 章](#Ch010_401-479_B9780443237904000244.xhtml)。

如今，许多应用程序使用第三代语言（3GL），如 `C#` 或 `Java` 来指定用于瞬态内存存储的对象模型，并使用 SQL 来指定用于持久存储的关系或对象-关系数据库。由于数据必须在对象模型和关系模型之间移动，因此在*对象-关系映射*上花费了大量精力。使用诸如 `NORMA` 之类的工具从 ORM 模型生成对象模型和关系模型，简化了创建对象-关系映射过程的任务。

## 演绎数据库系统

*逻辑编程语言*（如 `Prolog`）是基于一阶谓词逻辑的声明性语言。事实和推导规则（包括递归规则）可以简洁地声明，并具有内置的回溯支持。

`Datalog` 结合了关系数据库系统的特性和逻辑编程语言的一个安全子集。与 `Prolog` 不同，`Datalog` 中的查询保证在有限时间内执行完毕。`Datalog` 已被用于自然语言处理，并作为演绎数据库系统的查询语言。

*演绎数据库*为以声明方式管理复杂数据提供了优雅而强大的方法，特别是对于通过递归推导出的信息。这赋予了它们强大的规则强制机制，具有内置的回溯和对递归规则的优秀支持。例如，`isanAncestorOf` 关系可以从基本的 `parent` 关系和以下两条霍恩子句规则中推导出来：

*    `X isanAncestorOf Y :- X isaParentOf Y.`（基础子句）
*    `X isanAncestorOf Y :- X isaParentOf Z, Z isanAncestorOf Y.`（递归子句）。

此处，规则头部和主体之间的“:-”表示“**如果**”，规则主体中的逗号“,”表示“**且**”。规则头部中的个别变量假定为全称量化，而在主体中引入的变量假定为存在量化，因此这些规则等价于谓词逻辑中的以下公式：

*    `∀x,y ( x isanAncestorOf y  if  x isaParentOf y )`
*    `∀x,y [ x isanAncestorOf y  if  ∃z(x isaParentOf z and z isanAncestor of y) ]`

相比之下，`SQL-92` 完全无法表达递归查询。`SQL:1999` 引入了递归并运算符，但其语法更复杂，且其执行不享有内置的回溯功能。
