
# 抽象机制

*抽象机制* 允许从直接考量中移除不需要的细节。这对于大型模型（例如墙面大小的模式图）非常重要。因为 ORM 图往往比相应的 ER 或 UML 图更详细、更大，所以经常使用抽象机制。例如，全局模式可以根据跨度或视角模块化为各种作用域（例如，数据模型的单页或活动模型的单页）。逐步求精可用于将高层视图分解为更详细的视图。虽然这不是一个语言问题，但工具可以提供额外支持，如分层和对象缩放（见后文）。此类机制可用于隐藏细节，仅显示与用户当前需求相关的模型部分。通过细微的变化，这些技术可应用于 ORM、ER 和 UML。ORM 还包含一个属性抽象过程，用于生成 ER 和 UML 图作为视图。

# 形式化基础

需要形式化基础来确保无歧义性和可执行性（例如，自动化模型的存储、验证、转换和仿真），并允许对模型间的等价性和蕴含关系进行形式化证明。尽管 ORM 更丰富的图形化约束表示法提供了更完整的模式转换图解处理，但文本约束语言的使用可以部分抵消这一优势。对于其数据建模构造，ORM、ER 和 UML 都可以获得充分的形式化基础。

# 语言设计权衡

语言设计通常涉及在相互竞争的标准之间进行多项 *权衡*。一个众所周知的权衡是 *表达能力* 与 *可处理性* 之间的权衡：语言的表达能力越强，要使其高效可执行就越困难 ([Levesque, 1984](#Ch003_59-110_B9780443237904000037.xhtml#bb0930))。另一个权衡是 *简洁性* 与 *便利性* 之间的权衡。虽然 *其他条件相同* 时，概念越少越好（参见奥卡姆剃刀原则），但将自己限制在最少可能的概念数量有时可能过于不便。例如，可以使用仅由 0 和 1 组成的字符串，用纯二进制编写计算机程序，但用 `C#` 等高级语言编写程序要容易得多。作为一个逻辑示例，使用“非”、“与”、“或”和“如果-那么”等多个运算符更方便，尽管我们只用一个（例如“与非”）就足够了。有关此示例的进一步讨论，请参阅本章注释。

# 属性概念作为基本构造

与简洁性-便利性权衡相关的一个基本问题是：是否将属性概念作为基本建模构造。我们已经倾向于否定这个问题的答案。ORM 使用关系而非属性，以便于捕获、验证和演进概念模式，同时仍允许自动推导出紧凑的属性视图，用于汇总或实现目的。传统 ER 支持单值属性，而 UML 支持单值和多值属性。我们稍后将论证，多值属性通常不适合概念建模，尽管它们对于逻辑和物理建模可能很有用。

## 3.2 概念模式设计过程

在开发信息系统时，我们首先指定需求并产出满足这些需求的设计。我们建议首先使用 ORM 在概念层面开发此设计。这意味着用 ORM 概念模式正式描述论域（UoD）的结构。如果理解了 ORM 上下文，我们通常会将“ORM 概念模式”简称为“概念模式”。

用于设计足够小、可作为单一单元管理的概念模式的过程称为 **概念模式设计过程** (CSDP)。大型业务领域首先被划分为子领域（可能重叠）。这些子领域通常会按优先级排序，以确定先开发哪些，并使用 CSDP 为每个子领域设计一个概念 *子模式*。

在建模师团队中，会就术语达成共识，以便对相同概念使用相同的名称。稍后，将子模式 *集成* 或合并为一个覆盖整个 UoD 的全局概念模式。这种集成通常是迭代执行的。

这种自顶向下的设计方法可总结如下：

*   将论域划分为可管理的子领域。
*   对每个子领域应用 CSDP。
*   将子模式集成为全局概念模式。

对于每个大小可控的业务领域或子领域，概念模式设计分 **七个步骤** 执行，如下所示。通常，在与领域专家讨论每个模型组件时，会对该组件执行所有七个步骤，而不是先对所有组件应用步骤 1，然后步骤 2，以此类推。

1.  将熟悉的例子转换为基本事实。
2.  绘制事实类型，并应用实例检查。
3.  检查要合并的实体类型，并记录任何算术推导。
4.  添加唯一性约束，并检查事实类型的元数。
5.  添加强制角色约束，并检查逻辑推导。
6.  添加值约束、集合比较约束和子类型约束。
7.  添加其他约束并执行最终检查。

**事实** (或 *事实实例*) 是业务领域用户视为真实的命题。该命题在 UoD 中实际上是否为真，与信息系统无关。这里的“视为真实”具有认识论承诺的含义，即业务用户准备像相信该断言为真那样行事。

**事实类型** 是给定种类的所有可能事实实例的集合（例如 `Person smokes`，或 `Person was born in Country`）。CSDP 过程始于对信息系统将要输出或输入的信息示例进行分析。基本上，前三个步骤关注于识别事实类型。

在后续步骤中，我们为事实类型添加约束。在整个过程中，会执行检查以发现推导事实，并确保没有错误。本章其余部分详细讨论前三个步骤。

对于大型业务领域，初步分割和最终集成增加了两个额外阶段，总共九个步骤。虽然最好按所示步骤顺序学习 CSDP，但在实践中，我们可能会以不同方式应用这些步骤。例如，我们可能在录入事实类型后立即添加约束，而不是等到所有事实类型都录入后再添加约束。

在商业世界中，许多现有应用程序是使用较低层级方法实现的，导致数据库设计可能不一致、不完整、低效或难以维护。此类系统通常文档匮乏。这些问题可以通过使用概念建模技术对现有应用程序进行 **重构** 来克服。例如，现有数据库表的样本实例可用作 CSDP 的输入。

即使没有样本实例，也可以通过利用约束和数据类型信息并对名称用法做出假设，将现有数据库模式 *逆向工程* 为一个尝试性的概念模式。
