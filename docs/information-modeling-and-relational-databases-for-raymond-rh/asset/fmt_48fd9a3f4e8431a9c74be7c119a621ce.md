
规范化有两种技术：`synthesis`（综合）和 `decomposition`（分解，有时称为“分析”）。每种技术仅在关系层面上操作，并从完整的关系属性集以及这些属性上的依赖集（如函数依赖 `FDs`）开始。回顾一下，如果 `X` 和 `Y` 是简单或复合属性（一列或多列表头的集合），我们说 `X` 函数决定 `Y`（写作 `X → Y`），当且仅当对于 `X` 的每个值，`Y` 至多有一个值。

在任何现实的业务领域中，如果我们仅仅通过写下属性列表和依赖列表来开始，很容易得到一个不正确的模型，因为概念建模的优势和保障被移除了（例如，通过口语化和填充进行验证）。此外，规范化中考虑的依赖集通常非常有限，因此许多 UoD 约束被简单地忽略了。

综合和分解两种技术的输出都是一组表模式，每个模式都保证处于特定的“范式”中。我们稍后将更仔细地研究范式。综合算法基本上通过为原始依赖找到一个最小、简化、环状覆盖，将属性分组到表中。冗余 `FDs`（例如传递 `FDs`）被移除，冗余源属性（`→` 左侧的属性）被移除，具有相同源属性的 `FDs` 被放置在同一个表中。就其指定的依赖类和属性而言，综合算法保证一种设计，其表的数量最少，且每个表都处于基本键范式（EKNF，稍后定义该概念）。

例如，给定 `FDs {empNr → gender, empNr → birthdate, empNr → job, job → salary, empNr → salary}`，综合生成两个表：`R1(empNr, gender, birthdate, job)`；`R2(job, salary)`。虽然这个例子很简单，但对于更复杂的情况，执行综合算法非常繁琐，最好交给计算机。显而易见，CSDP 中的派生事实类型检查，以及 Rmap 中的基本事实类型分组，与综合方法有着密切的对应关系。

尽管综合在学术界经常被教授，但从业者很少使用它，部分原因是其高度技术性，但主要是因为它在实践中几乎无用。综合的主要问题是它假设其输入为一组正确的全局属性和依赖。然而在实践中，这样的输入很少见，而且确定这样的输入往往比通过其他方式确定正确设计更难。基于这些原因，我们从这一点开始基本上忽略综合技术。

规范化（无论是综合还是分解）的另一个问题是它无法改变属性集。因此，除了忽略涉及其他类型约束的转换外，规范化还错失了通过允许转换改变属性而可能产生的语义优化机会。

例如，`FD` 集 `{department → budget, (department, gender) → nrStaff}` 综合为两个表模式：`R1(department, budget)` 和 `R2(department, gender, nrStaff)`。但规范化无法将该 `FD` 集转换为 `{department → budget, department → nrMaleStaff, department → nrFemaleStaff}`，后者将导致单表设计 `R(department, budget, nrMaleStaff, nrFemaleStaff)`。将此与刚才讨论的 ORM 模式优化方法进行比较。

这些考虑表明，单独使用规范化作为设计方法是不充分的。尽管如此，将规范化作为对我们概念建模的一种检查，有时可能是有帮助的。从积极方面来看，通过将范围限制在一小类但重要的约束上，并忽略语义转换，规范化理论家建立了一些有趣的结果。

与综合不同，规范化的分解方法是迭代的，它逐步将设计不良的表分割成更小的表，直到最终它们没有某些更新异常，并且它不保证表数量的最小性。然而，分解方法更为人所知，一些建模者发现其原理对于纠正不良的关系设计很有用。本节其余部分重点关注分解方法，并与 ORM 进行一些比较。为了帮助可能跳着读这一节的读者，简要回顾一下前面处理的一些基本概念。

从正确的 ORM 概念模式 `Rmapping` 得到的关系模式已经完全规范化。然而，假设在概念化或映射中出现了某些错误，或者关系模式是在没有使用概念模式的情况下直接设计的。现在某些表设计可能是不安全的，因为某些概念约束未被强制执行。如果在通过插入、删除或修改行来更新表时违反了概念约束，则称该表设计包含`update anomaly`（更新异常）。

概念引用类型上的约束是人类的责任。只有人才能确保首选引用模式确实提供了从现实世界实体集到数据值集合（或数据元组集合）的正确 1:1 映射。当实体类型仅扮演一个事实角色，该角色不是函数的，且该实体类型的实例更改其首选标识符时，需要特别小心。

例如，假设 `City` 仅出现在 `m:n` 事实类型 `RussianTour(.Nr) visits City (.Name)` 中。在 1990 年代初，当时称为“Leningrad”的城市恢复了其原名“St. Petersburg”。作为练习，讨论如果仅重命名部分“Leningrad”实例会出现什么问题。

假设首选引用模式已被强制执行，信息系统本身通常应强制执行所有事实类型约束。因此，所有概念事实类型上的约束（以及它们之间的约束）都应在关系模式中捕获。规范化过程确保了大多数此类约束被捕获。特别是，它旨在消除任何冗余（基本事实的重复）的可能性。如果一个事实在数据库中被复制，当该事实改变时，就必须更新它的每一个实例；否则，数据库将变得不一致。

从一个可能糟糕的表设计开始，规范化过程应用规则将其连续细化为更高的“范式”，直到完全规范化。让我们将注意力局限于那些专注于通过将表分割成更小的表来消除表问题的范式。有许多这样的范式。按可接受性递增的顺序，主要有：第一范式 (`1NF`)、第二范式 (`2NF`)、第三范式 (`3NF`)、基本键范式 (`EKNF`)、Boyce/Codd 范式 (`BCNF`)、第四范式 (`4NF`)、第五范式 (`5NF`)、域键范式 (`DKNF`)。我们将依次讨论这些范式。

不在第一范式中的表被称为“非规范化”或处于`Non-First Normal Form`（`NFNF` = `NF²`）。处于较高范式的表也处于其较低的范式中（例如，`3NF` 表也处于 `2NF` 和 `1NF`）。因此，表可以按如 [Fig. 14.56](#Ch014_681-771_B9780443237904000189.xhtml#f0285) 所示进行分类。表的`highest normal form`（`hNF`，最高范式）是其最深的规范化级别。
