
ORM 包含用于动态生成 ER 和 UML 图作为属性视图的算法。这些算法根据对象类型当前的角色和约束为其分配不同的重要性级别，将次要事实类型重新显示为主要对象类型的属性。建模和维护是迭代过程。随着我们发现更多的全局模型，以及被建模的领域本身发生变化，某个特性的重要性可能会随时间改变。

为了促进语义稳定性，ORM 在其基础模型中不对相对重要性做出承诺，而是通过视图动态支持这一点。基本事实是信息的基本单位，统一表示为关系，它们如何分组到结构中并非概念问题。您可以使用 ORM 进行分析，如果想使用 UML 类图，可以从 ORM 模型派生它们。

在 UML 中建模“员工可能从事多项运动”的一种方式如[图 9.7](#Ch009_347-399_B9780443237904000013.xhtml#f0040)(a)所示。此处，关于谁从事什么运动的信息被建模为*多值属性*“sports”。该属性上的“\[0..\*]”多重性约束指示每个员工可录入多少项运动。“0”表示某些员工可能没有录入运动。UML 对此情况使用*空值*，就像关系模型一样。空值的存在使用户面临实现问题而非概念问题，并增加了查询语义的复杂性。“\[0..\*]”中的“\*”表示单个员工的运动数量*没有上限*。换句话说，员工可能从事多项运动，我们不关心具体有多少。如果“\*”使用时未指定下限，这被视为“0..\*”的缩写。

一个等价的 ORM 模式如[图 9.7](#Ch009_347-399_B9780443237904000013.xhtml#f0040)(b)所示。使用了一个可选的多对多事实类型，而不是多值 sports 属性。正如下一节所述，这种方法也可在 UML 中使用* m:n *关联。

为了讨论*类实例种群*，UML 使用*对象图*。这些本质上是类图，其中每个对象显示为类的一个单独实例，并为其属性提供数据值。作为一个简单示例，[图 9.8](#Ch009_347-399_B9780443237904000013.xhtml#f0045)(a) 包含对象图，以建模三个员工实例及其属性值。[图 9.8](#Ch009_347-399_B9780443237904000013.xhtml#f0045)(b) 中的 ORM 模型使用事实表列出事实实例，显示相同的样本种群。

![Fig. 9.8 Populated models in (a) UML and (b) ORM.](images/B9780443237904000013/f09-08-9780443237904.jpg)

[图 9.8](#Ch009_347-399_B9780443237904000013.xhtml#B-f0045) (a) UML 和 (b) ORM 中的已填充模型。

对于这种简单情况，对象图很有用。然而，如果我们希望为更复杂的情况显示多个实例，它们会迅速变得难以驾驭。相比之下，事实表可轻松扩展以处理大型复杂情况。

ORM 约束可通过样本种群轻松阐明。例如，在[图 9.8](#Ch009_347-399_B9780443237904000013.xhtml#f0045)(b)中，Plays 事实表中缺少员工 101 表明从事运动是可选的，唯一性约束标记出哪个列或列组合的值最多只能出现在一行上。在 EmployeeName 事实表中，第一列的值是唯一的，但第二列包含重复项。在 Plays 表中，每列都包含重复项，因为只有整行是唯一的。此类种群对于与主题专家一起检查约束很有用。ORM 的这种通过示例验证的特性适用于其所有约束，而不仅仅是强制角色和唯一性，因为其所有约束都是基于角色或基于类型的，且每个角色对应一个事实表列。

作为多值属性的最后一个示例，假设我们希望记录国家旗帜的昵称和颜色。我们约定最多为任何给定旗帜记录两个昵称，且昵称仅适用于一面旗帜。例如，“Old Glory” 和 “The Star-Spangled Banner” 可能用作美国国旗的昵称。旗帜至少有一种颜色。

[图 9.9](#Ch009_347-399_B9780443237904000013.xhtml#f0050)(a) 显示了在 UML 中建模此问题的一种方式。“\[0..2\]”表示每面旗帜最多有两个（从零到两个）昵称。“\[1..\*]”声明旗帜有一种或多种颜色。需要额外的约束来确保每个昵称最多指代一面旗帜。简单的属性唯一性约束（例如 {U1}）是不够的，因为 nicknames 属性是集合值的。不仅每个旗帜的 nicknames 集合必须唯一，而且每个集合中的每个元素也必须唯一（后一条件蕴含前一条件）。这种更复杂的约束在附带的注释中非正式地指定。

![Fig. 9.9 A flag model in (a) UML and (b) ORM.](images/B9780443237904000013/f09-09-9780443237904.jpg)

[图 9.9](#Ch009_347-399_B9780443237904000013.xhtml#B-f0050) (a) UML 和 (b) ORM 中的旗帜模型。

此处属性域被隐藏。Nickname 元素通常具有数据类型域（例如 String）。如果我们不存储关于国家或颜色的其他信息，可能会为 country 和 color 也选择 String 作为域（尽管这是亚概念的，因为真实的国家和颜色不是字符串）。然而，因为我们以后可能想添加关于这些的信息，最好使用类作为它们的域（例如 Country 和 Color）。如果这样做，我们需要定义这些类。

[图 9.9](#Ch009_347-399_B9780443237904000013.xhtml#f0050)(b) 显示了在 ORM 中建模此问题的一种方式。为了口语化，我们通过国家来标识每面旗帜。因为 country 是实体类型，所以显式显示了引用方案（引用模式仅在引用类型为值类型时才可缩写引用方案）。“≤2”频率约束表示每面旗帜最多有两个昵称，NickName 角色上的唯一性约束表示每个昵称最多指代一面旗帜。

UML 给我们选择将特性建模为属性或关联。对于概念分析和查询，显式关联通常比属性（尤其是多值属性）具有更多优势。这种选择有助于我们口语化、可视化和填充关联，并使用标准符号表达涉及“属性所扮演角色”的各种约束，而不必求助于非标准扩展。这不仅适用于简单的唯一性约束，也适用于包含属性域所扮演角色（在对应于属性的隐式关联中）的一个或多个角色上的其他类型约束（频率、子集、排除等）。

例如，如果关联“Flag is of Country”在 UML 中显式描绘，则可以通过在此关联的左侧角色上添加“0..1”的多重性约束来捕获“每个国家最多有一面旗帜”这一约束。虽然 country 和 color 自然被构想为类，但 nickname 通常会被解释为数据类型（例如 String 的子类型）。虽然 UML 中的关联可以包含数据类型（不仅仅是类），但这有点别扭；因此在 UML 中，nicknames 最好仍作为多值属性保留。
