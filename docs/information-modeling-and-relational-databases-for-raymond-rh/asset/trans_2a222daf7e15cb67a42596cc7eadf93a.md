
# UML 排除约束

UML 没有用于属性之间、或属性与关联角色之间排除关系的图形符号。此类情况下的排除约束通常可用文本约束来表示。例如，在[图 9.34](#Ch009_347-399_B9780443237904000013.xhtml#f0175)(a) 中，每位员工要么是终身制，要么是合同制（直至某日期）这一排除约束，可用所示的文本约束来捕获。

![图 9.34 (a) UML 和 (b) ORM 中建模的排除约束。](images/B9780443237904000013/f09-34-9780443237904.jpg)

[图 9.34](#Ch009_347-399_B9780443237904000013.xhtml#B-f0175) (a) UML 和 (b) ORM 中建模的排除约束。

此处，约束是用 OCL 指定的。表达式 `->isEmpty()` 和 `->notEmpty()` 分别等同于 SQL 中的 `is null` 和 `is not null`。[图 9.34](#Ch009_347-399_B9780443237904000013.xhtml#f0175)(b) 在 ORM 中以图形方式描绘了该排除约束。在 UML 中还有其他建模此情况的方法（例如使用子类型），这些方法提供了更多以图形方式捕获约束的机会。

## 9.6 子类型化

UML 和 ORM 均支持使用“is-a”（是一种）语义的*子类型化*，即子类型的每个实例同时也是其超类型（父类型）的实例。例如，声明 Woman（女性）是 Person（人）的子类型，意味着每个女性都是人，因此 Woman 继承 Person 的所有属性。给定两个对象类型 *A* 和 *B*，如果在每个数据库状态下，*A* 的实例总体都包含在 *B* 的实例总体中，则 *A* 是 *B* 的*子类型*。对于数据建模，感兴趣的只有*真*子类型。我们称 *A* 是 *B* 的真子类型，当且仅当 *A* 是 *B* 的子类型，且存在一种可能的状态，使得 *B* 的实例总体包含不在 *A* 中的实例。从现在起，我们将用“子类型”作为“真子类型”的简写。

在 UML 和 ORM 中，*特化*是引入子类型的过程，*泛化*是引入超类型的逆过程。UML 和 ORM 都允许单一*继承*以及多重继承（即一个子类型有多个直接超类型）。例如，AsianWoman（亚洲女性）可以同时是 AsianPerson（亚洲人）和 Woman 的子类型。在 UML 中，“子类”和“超类”分别是“子类型”和“超类型”的同义词，泛化也可应用于类以外的事物（如接口、用例参与者和包）。本节重点关注对象类型（类）之间的子类型化。

在 ORM 中，子类型继承其超类型的所有角色。在 UML 中，子类继承其超类型的所有属性、关联和操作/方法。操作实现一项服务，具有签名（名称和形式参数）和可见性，但可以用不同方式实现。方法是操作的一种实现，包含签名和主体，主体详述执行该操作的可执行算法。在继承图中，同一操作可能有多个方法（*多态*），作用域规则决定给定类使用哪个方法。如果子类拥有与其某个超类型的方法具有相同签名的方法，则该子类将改用这个方法（*覆盖*）。例如，如果 Rectangle（矩形）和 Triangle（三角形）是 Shape（形状）的子类，这三个类可能都有不同的 display 方法。本节专注于数据建模，涵盖静态属性（属性和关联）的继承，但忽略操作或方法的继承。

子类型在数据建模中用于断言类型约束、鼓励模型组件复用以及展示分类方案（分类学）。在此语境下，类型约束确保子类型特有的角色仅由相关子类型扮演。

因为子类型继承其超类型的属性，所以引入子类型时只需声明其特有的角色。除了减少代码重复，更通用的超类型也更有可能在其他应用中得到复用。在编码层面，操作/方法的继承增强了通过属性和关联角色继承获得的复用。用子类型展示分类学用处有限，因为分类学通常用谓词捕获更高效。例如，事实类型“Person is of Gender {male, female}”（人的性别为{男，女}）隐式地为 MalePerson（男性）和 FemalePerson（女性）子类型提供了分类学。

UML 和 ORM 均使用*有向无环图*显示子类型化。有向图是带有向连接的节点图，“无环”意味着没有环路（这是真子类型化的结果）。[图 9.35](#Ch009_347-399_B9780443237904000013.xhtml#f0180) 展示了 UML 和 ORM 中的子类型模式。从一个节点指向另一个节点的箭头表示前者是后者的子类型。UML 使用细箭杆和空心箭头，而 ORM 使用实心箭杆和箭头。UML 还允许单独的箭杆汇合成一根，由一个箭头代表所有（例如，*E* 和 *F* 都是 *C* 的子类型）。因为子类型关系具有传递性，所以省略间接连接（例如，因为 *E* 是 *C* 的子类型，而 *C* 是 *A* 的子类型，所以 *E* 也是 *A* 的子类型，无需显示这一隐含连接）。

![图 9.35 (a) UML 和 (b) ORM 中用有向无环图显示的子类型化。](images/B9780443237904000013/f09-35-9780443237904.jpg)

[图 9.35](#Ch009_347-399_B9780443237904000013.xhtml#B-f0180) (a) UML 和 (b) ORM 中用有向无环图显示的子类型化。

UML 包含四个预定义约束，用于指示子类型是否互斥或穷尽。如果子类型连线使用单独的箭头，则约束放在连接子类型链接的虚线旁的大括号中，如[图 9.35](#Ch009_347-399_B9780443237904000013.xhtml#f0180)(a)（顶部）所示。我们假设此线可包含折角（如 disjoint 约束所示），以便指定此类情况。如果子类型连线共享箭头，则约束放在共享箭头附近，如[图 9.35](#Ch009_347-399_B9780443237904000013.xhtml#f0180)(a)（底部）所示。{overlapping}（重叠）和 {disjoint}（不相交）选项分别表示子类型重叠或互斥。最初 {complete}（完整）仅意味着显示了所有子类型，但现在意味着穷尽（即超类型等于其子类型的并集）。{incomplete}（不完整）选项意味着超类型不止是其子类型的并集。UML 2.5 将默认值从 {disjoint, incomplete} 改为 {overlapping, incomplete}。用户可添加其他关键字。

默认情况下，ORM 子类型可以重叠，且子类型不必共同穷尽其超类型。ORM 允许使用图形约束指示子类型互斥（带圆圈的“X”连接到相关子类型链接）、共同穷尽（带圆圈的点）或两者兼具（带圆圈的叉号点），如[图 9.35](#Ch009_347-399_B9780443237904000013.xhtml#f0180)(b)所示。ORM 的方法是：排除约束和总体性约束作用于实例总体，而非类型。重叠“约束”并不意味着实例总体必须重叠，只是意味着它们可以重叠。从 ORM 角度看，这根本不算约束，因此无需描绘。在 ORM 中，子类型排除约束和总体性约束通常由其他约束结合形式化的子类型定义所隐含。
