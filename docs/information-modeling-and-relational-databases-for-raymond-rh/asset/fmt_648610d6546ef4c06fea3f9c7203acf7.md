
## Process-Information Bridge (PIB)

An alternative approach is to introduce an intermediate stage between the BPMN model and the ORM model, forming a **Process-Information Bridge (PIB)**. The Data Store reference can then be to a PIB element containing the relevant ORM linkage. One data item can be used in multiple activities in a process, so this also provides a location to resolve the one-to-many relationship. [Fig. 15.37](#Ch015_773-830_B9780443237904000190.xhtml#f0190) shows the relevant diagram notation.

[Fig. 15.37](#Ch015_773-830_B9780443237904000190.xhtml#B-f0190) Activity linked to PIBRef.

Next, we can turn to the ORM end of the relationship. In ORM (as opposed to an Entity-Attribute model), the attributes (properties) of the entity are unbundled and can be addressed in terms of separate fact types. "Entities" are formed from collections of fact types in a mapping process that produces a new model of a type defined by the mapping (for example, a relational model).

Although the unbundling of entities in ORM potentially offers a finer-grained definition of a relationship between activity and information, it is not necessarily convenient for cross-referencing of the kind we are considering. An activity is likely to require all information about an entity to be treated together rather than as isolated facts. For example, an agent updating stored data about personnel would probably expect to see all relevant information about a particular employee to be displayed at the same time. Instead of referring to individual fact types, it would be much simpler if the fact types were arranged in convenient bundles related to major entity types.

A straightforward way of achieving this is to group fact types into `relations`, in the sense originally expressed by Codd. Facilities already exist in ORM to produce normalized relations from an ORM model with the `Rmap` procedure. In a conceptual model, there is no prior commitment to a relational database solution, but this does not matter because normalized relations can be realized in other types of data structures such as `XML` and `JSON`; see [Chapter 16](#Ch016_831-873_B9780443237904000207.xhtml) for more details.

A convenient data reference to a group of fact types in an information model can therefore be made by simply using the (unique) name of the relation. Accessing a particular data item during the execution of a process would require the relation name plus a key value that is unique within the relation. The same activity may access different instances of the relation in different instances (executions) of the process. However, only the relation's name is necessary to define the linkage between a process model and an information model.

This approach would create a set of hierarchical links between the process model and the information model, as outlined in [Fig. 15.38](#Ch015_773-830_B9780443237904000190.xhtml#f0195).

### PIBRef Components

Each PIBRef will contain the following:

*   **CRUD Access Indicator**: An indicator showing the type of CRUD access intended in this case. The usual access will be either Read-only, where the activity is not expected to change the data, or Full, where the activity can view the data and possibly also change it. These can be indicated by a single letter (`R` or `F`, where `F` is a shorthand for CRUD). In the unlikely event of more specificity being necessary, then the individual letters of CRUD can be used.
*   **ORM Element Identification**: The identification of the ORM elements involved in this case, using relation names. More than one relation could be used in the same PIBRef. For example, an activity might involve reading from one relation and updating another.

Each set of PIBRef access/relation values is likely to appear in one PIBRef only—the same PIBRef can be reused in the process model so there would be no need to repeat it. However, if duplication is accidentally introduced, it would not be harmful, merely slightly wasteful. The general scheme is summarized in [Fig. 15.39](#Ch015_773-830_B9780443237904000190.xhtml#f0200).

### Example: Complaints Process

To illustrate some of these points, we can look at an example process model. [Fig. 15.40](#Ch015_773-830_B9780443237904000190.xhtml#f0205) illustrates a simple complaints process using BPMN. After recording the complaint, the client is contacted to acknowledge receipt and the relevant department is contacted to assess the complaint. After assessment, the client is either compensated in some way or a standard letter is sent to explain the resolution. Details of the case are filed in case of any future query, and the process terminates.

![Fig. 15.40 A simple complaints process.](images/B9780443237904000190/f15-40-9780443237904.jpg)

[Fig. 15.40](#Ch015_773-830_B9780443237904000190.xhtml#B-f0205) A simple complaints process.

To provide a concrete example of the relationship between process and information, we'll look at the `SendStandardLetter` activity; a corresponding picture could be drawn for any of the other activities. We will assume that appropriate resources and manual services are available to the activity, such as printing, envelope stuffing, and franking, and focus on the information usage. [Fig. 15.41](#Ch015_773-830_B9780443237904000190.xhtml#f0210) shows a fragment of an information model, including the types of facts that might be relevant to the `SendStandardLetter` activity.

![Fig. 15.41 An ORM model fragment relating to the SendStandardLetter information.](images/B9780443237904000190/f15-41-9780443237904.jpg)

[Fig. 15.41](#Ch015_773-830_B9780443237904000190.xhtml#B-f0210) An ORM model fragment relating to the SendStandardLetter information.

We are assuming here that the letter consists mainly of "boilerplate" text with the client information, the case reference, and dates inserted at the appropriate points. To identify the relevant facts, the activity requires two primary objects to be identified: a `Case` and a `LetterType`. From the `Case`, we can uniquely identify the `Client` and hence the Client's Title, Name, and Address. From the `LetterType`, we can identify the appropriate text to form the body of the letter. The current date is assumed to be available from the activity's environment. This information is sufficient for the activity to create and send the standard letter.

[Fig. 15.42](#Ch015_773-830_B9780443237904000190.xhtml#f0215) shows a relational view of the information. This can be used as the basis for defining the necessary bridge between process and information.

![Fig. 15.42 A relational view of the SendStandardLetter information.](images/B9780443237904000190/f15-42-9780443237904.jpg)

[Fig. 15.42](#Ch015_773-830_B9780443237904000190.xhtml#B-f0215) A relational view of the SendStandardLetter information.

From the process perspective, the necessary link is provided by the `SendLetter` Data Store reference in the process model of [Fig. 15.40](#Ch015_773-830_B9780443237904000190.xhtml#f0205). The `SendStandardLetter` activity requires Read access (`R`) to the `LetterType`, `Client`, and `Case` relations but full access (`F`) to the `ClientWasSentLetterTypeOnDate` relation. The associated PIB can be defined in a suitable editing tool, as illustrated in [Fig. 15.43](#Ch015_773-830_B9780443237904000190.xhtml#f0220). This shows the four relations, with the last relation being expanded to show its attributes. This specific tool also allows the use of alternative names in the process context.
