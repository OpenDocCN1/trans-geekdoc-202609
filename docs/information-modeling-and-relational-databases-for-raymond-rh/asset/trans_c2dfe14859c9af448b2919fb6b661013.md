引用循环有时不可避免，但实现起来很麻烦。在这种情况下，循环是由于配对子集约束与 is-chaired-by 上的强制角色约束相结合而产生的。鉴于配对子集约束，如果 Committee 是独立的或扮演另一个强制的、函数式的角色，该循环也将适用。关系映射在[第 11 章](#Ch011_481-537_B9780443237904000141.xhtml)中有详细介绍。

因为 UML 不允许一元关系，所以 ORM 一元之间的子集约束需要通过文本方式捕获，使用注释来指定布尔属性之间的等效约束。例如，[图 9.25](#Ch009_347-399_B9780443237904000013.xhtml#f0130)(b)中的 ORM 子集约束，其语义为**每个**吸烟的 Patient 都是易患癌的，可以通过[图 9.25](#Ch009_347-399_B9780443237904000013.xhtml#f0130)(a)中的注释在 UML 中以文本方式捕获。

此外，UML 不支持针对仅为关系一部分的参数的子集约束，例如[图 9.27](#Ch009_347-399_B9780443237904000013.xhtml#f0140)(b)中的子集约束：学生只有在注册了该课程的情况下，才能通过该课程的测试。[图 9.27](#Ch009_347-399_B9780443237904000013.xhtml#f0140)(a)通过将三元转换为具有与 TestNr 二元关联的二元关联类来在 UML 中建模此约束。尽管在这种情况下关联类为复合子集约束提供了良好的处理方式，但有时这种嵌套转换会导致对世界的非常不自然的看法。理想情况下，建模者应该能够自然地看待世界，而将任何降低概念模式清晰度的优化转换在幕后执行。

一个明显的问题是主键关联上的“1”应该是“0..1”（并非所有列都属于主键），如[图 9.29](#Ch009_347-399_B9780443237904000013.xhtml#f0150)(a)所示。如果我们允许表没有列（例如，以适应表正在建设中的情况），那么 define 关联上的“*”没问题；否则它应该是“1..*”。假设表和列由 oid 或人工标识符标识，子集约束讲得通，但该模型可以说是次优的，因为主键关联和子集约束可以用 Column 上的布尔属性 `isaPKfield` 来替代。

从 ORM 的角度来看，启发式方法引导我们最初使用自然引用方案来建模该情况，如[图 9.29](#Ch009_347-399_B9780443237904000013.xhtml#f0150)(b)所示。这里，ColumnName 表示列在表中的局部名称。我们通过假设表可以仅由其名称标识来简化现实。外部唯一性约束为 Column 提示了两种自然引用方案：名称加表，或位置加表。我们选择了前者作为首选，但也可以引入人工标识符。一元谓词指示某列是否为主键列或主键的一部分。如果需要，我们可以从路径“Column is in Table **and** Column is a primary key column”推导出关联“Column is a primary key field of Table”（UML 模型中的子集约束由此隐含）。

这个例子有趣的是建模方法的差异。大多数 UML 建模者似乎假设在初始建模中将使用 oid 作为标识符，而 ORM 建模者喜欢从一开始就暴露自然引用方案，并据此填充他们的事实类型。这些不同的方法通常会导致不同的解决方案。

最重要的是首先提出一个对领域专家来说自然且易懂的解决方案，因为这是模型验证最关键的阶段。一旦确定了正确的模型，就可以使用优化指南来增强它。
