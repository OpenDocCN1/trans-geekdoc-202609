
根据性别，我们可以将 `Person` 分类为子类型 `MalePerson` 和 `FemalePerson`。我们在[图 6.30](#Ch006_211-271_B9780443237904000025.xhtml#f0155)中将男性放在左侧，女性放在右侧，这样你就可以直观地看到通过垂直划分 `Person` 类型来创建这些子类型。我们也可以根据出生国将人员分类为子类型。在[图 6.30](#Ch006_211-271_B9780443237904000025.xhtml#f0155)中，这通过将 `Person` 水平划分为 `Australian`、`Italian`、`Mexican` 等来表示。对于所示的人口，有三个澳大利亚人、两个意大利人和三个墨西哥人，其他国籍位于下方的各个层中（此处简标为“等”）。为简化起见，忽略归化问题，因此此处“Australian”用于“澳大利亚出生者”之意，以此类推。

在建模中使用子类型的主要原因是*声明类型约束*（在本例中，是*声明一个或多个特定角色仅由给定子类型扮演*）。例如，医疗数据库可能会记录患者是否受过割礼，但这仅针对男性患者记录。

子类型化的第二个原因是*鼓励模型组件的复用*。例如，如果我们已经拥有一个描述对象类型 `Employee` 的详尽子模式，并想讨论经理，我们可以将 `Manager` 声明为 `Employee` 的子类型，并仅添加特定于经理的额外细节。

如果 `Employee` 在参考模型中定义，它可以被导入到许多不同的模型中，并根据每种情况适当地进行特化。如果为对象类型定义了行为，这也可以连同数据方面一起复用。在编程应用中，这可以显著减少代码重复。

子类型化的第三个原因是揭示 UoD 中使用的*分类法*或分类方案。然而，在 ORM 中，我们通常避免仅为暴露分类方案而引入子类型。为什么？首先，分类法通常可以用更经济的方式建模。例如，要表明有两种性别，我们只需在 `Gender` (`.code`) 上添加一个值约束，如 `{"M", "F"}`。除非我们在应用领域中有一些特定角色需要它们扮演，否则无需引入 `Male` 和 `Female` 子类型。

其次，如果我们纯粹为分类法使用子类型，子类型的数量会迅速失控。例如，假设我们希望根据出生国对人员进行分类。我们只需要事实类型：`Person was born in Country`。如果我们改为引入 `Person` 的子类型，每个国家一个，这将导致模式中出现近 200 个子类型！

这太疯狂了。如果这些子类型中的某一个扮演特定角色，那么我们应该引入它；但如果不扮演，我们就没有必要引入。例如，假设我们想记录 `Australians` 是否希望他们的国家成为共和国，但对其他国籍没有特定内容要记录。在这种情况下，`Australian` 是我们应该引入的唯一子类型。

本章前面使用欧拉图来描绘一个集合作为另一个集合的子集。在设计概念模式时，我们经常需要引入子类型，并明确说明什么是什么的子类型。对于简单情况，例如[图 6.31](#Ch006_211-271_B9780443237904000025.xhtml#f0160)(a)中 *B* 和 *C* 是 *A* 的子类型，可以使用欧拉图。

![图 6.31 欧拉图适用于简单的子类型化 (a)，但不适用于复杂情况 (b)。](images/B9780443237904000025/f06-31-9780443237904.jpg)

[图 6.31](#Ch006_211-271_B9780443237904000025.xhtml#B-f0160) 欧拉图适用于简单的子类型化 (a)，但不适用于复杂情况 (b)。

将其解释为假设的欧拉图，问题是 *A* 是否包含不在 *B* 或 *C* 中的元素。如果 *A* 确实有更多元素，可以通过在 *B* 和 *C* 外部区域添加星号来表示。正如[第 8.2 节](#Ch008_309-346_B9780443237904000177.xhtml#s0015)所讨论的，ER 的 Barker 表示法为此目的使用一种称为“Other”的特殊类型。

欧拉图的优点是通过将一个集合或类型在空间上放置在另一个内部，直观地显示包含关系。这对简单情况效果很好。然而在实践中，一个对象类型可能有许多子类型，它们可能重叠，且一个子类型可能有许多超类型。

例如，[图 6.31](#Ch006_211-271_B9780443237904000025.xhtml#f0160)(b) 中的子类型模式描绘了以下信息：*B*、*C* 和 *D* 是 *A* 的子类型，而 *E* 是 *C* 和 *D* 共同的子类型。此外，*B* 与 *C* *重叠*（即它们可能有共同实例），*C* 与 *D* *重叠*，但 *B* 和 *D* 是*互斥的*（不能有共同实例）。例如，*A* = `Person`；*B* = `Asian`；*C* = `Consultant`；*D* = `American`；*E* = `TexanConsultant`。

对于这种情况，欧拉图变得无望地复杂。此外，个别子类型可能有许多特定细节需要记录，如果子类型节点挤在其超类型节点内部，根本没有空间附加这些细节。

基于这些原因，非平凡的子类型化不采用欧拉图。我们需要一种简单的表示法，无论情况多大或多复杂，都能用来显示子类型关系和子类型角色。这通过将子类型显示在其超类型*外部*，并通过*箭头*描绘子类型-超类型连接来实现。

基本思想如[图 6.32](#Ch006_211-271_B9780443237904000025.xhtml#f0165)所示。这里，*A* 和 *B* 是对象类型。假设 *A* = `Employee` 而 *B* = `Manager`。实体类型 `Employee` 是可能记录事实的所有员工的集合。子类型 `Manager` 是可能记录事实的所有经理的集合。在任何给定的数据库状态下，`pop(Employee)` 和 `pop(Manager)` 分别是数据库中实际引用的员工集合和经理集合。

![图 6.32 B 是 A 的真子类型。](images/B9780443237904000025/f06-32-9780443237904.jpg)

[图 6.32](#Ch006_211-271_B9780443237904000025.xhtml#B-f0165) *B* 是 *A* 的真子类型。

一般来说，当且仅当 `pop(B)` 始终是 `pop(A)` 的子集，且 *A* ≠ *B* 时，*B* 是 *A* 的**真子类型**。在这种情况下，*A* 是 *B* 的*真超类型*。如果 *A* = *B*，我们不指定任何子类型连接。基于此理解，我们在谈论子类型和超类型时通常省略“真”。

形容词“真”适用于类型关系，但不一定适用于*人口*关系。可能存在一种数据库状态，其中 `pop(A)` = `pop(B)`。例如，如果尚未录入关于 *A* 的事实，则 `pop(A)` 和 `pop(B)` 都等于 {}；以我们的例子为例，我们可能选择先录入关于经理的信息，再录入其他员工。

这种表示法不如欧拉图直观，因为子类型显示在其超类型“外部”，尽管子类型内的每个对象实例也必须包含在超类型内。此外，除非我们添加某种方式来捕获，否则关于子类型重叠的信息就会丢失。

这是用箭头而非空间包含来描绘子类型连接的后果。然而，这种劣势远远被以下优势抵消：能够方便地表示任意复杂度的子类型模式，同时仍在每个节点周围留出足够空间以附加细节。
