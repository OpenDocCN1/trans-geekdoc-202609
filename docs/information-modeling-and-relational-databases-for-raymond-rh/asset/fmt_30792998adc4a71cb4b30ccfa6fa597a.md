## 16.1 External Data Structures

Previous chapters have made the implicit assumption that data will be stored in a database system of some kind, such as a relational database. In this chapter, we consider how data can be represented in a way that's independent of a particular type of data store. This may be necessary when we need to transfer data between different systems. If the transfer takes place between two systems of the same kind, we can make use of any functionality built into the system. As examples, we can use a server-to-server replication mechanism, or restore a backup made on one server onto a different server. But these approaches will not usually work between two unlike systems, even if they are of the same general kind. For instance, a backup copy made on SQL Server cannot be restored on an Oracle system. We also need to be aware of possible interchange between different kinds of systems, such as a database management system and a spreadsheet.

A widely used and long-established approach is to use comma-separated values, typically referred to as a "CSV file". This is a simple file format used to store tabular data in a plain text format. In a CSV file, each line of text represents a record, with the fields in each record being separated by commas. This structure is roughly equivalent to the values in a single table in a relational database. Tab-separated values are a close cousin; as the name suggests, the separator between fields here is a tab character instead of a comma. If the data itself contains delimiter characters (comma, tab, newline), additional measures such as quoting or escaping are needed.

The main advantage of a CSV file is its simplicity. The file can be opened and edited with any text editor, and the structure is easy to understand, just rows and columns (though the columns may not be obvious because of different field lengths in different rows). CSV files are widely supported by a variety of applications, including spreadsheets, programming languages, and databases. They are quite compact because they consist mainly of data with only a minimal set of delimiter characters. Because they contain no information about how the data might be stored, they are a popular choice for straightforward data transfer between different kinds of systems. Text files of this kind can also be used as simple databases when partnered with an appropriate query facility, such as the venerable `AWK` language found in the UNIX environment.

However, this same lack of structure limits the expressiveness of the format. There's no built-in way to include metadata about the data or the file itself. There's no way of defining data types. Most important of all, there's no way of expressing even moderately complex structures or relationships.

The need to address these issues has promoted interest in more sophisticated representations. Two major alternatives have emerged: the eXtensible Markup Language (XML) and JavaScript Object Notation (JSON). Both are in widespread use, especially for the transfer of structured data between systems, though they can both be used as information stores in their own right. They share some common features.

1.  **They are text-based.** Like CSV files, XML and JSON files can be opened and edited with a simple text editor. However, the complexity of the structure can make this a daunting task. It's very easy to make editing errors that render the structure invalid, and it's difficult to visualize the structure unless it is laid out appropriately. For this reason, it's common to use special editors that are sensitive to the conventions of the notation. The result, though, is still just text, which can be stored and retrieved using standard facilities.

2.  **They are hierarchical.** Elements can contain other elements (recursively), which results in the data being contained in a tree-like structure. This is the case even when the original data is not a natural hierarchy. An inevitable consequence is the possibility of data duplication, which will need to be managed, either in a data store or in applications that use the data.

3.  **They use a "bracketed" notation.** Data elements are contained within a matching pair of opening and closing delimiters such as `< x >`, `( x )`, `[ x ]`, or `{ x }`. Nested elements must be wholly contained, so `< x < y >>` may be valid, but `<x < > y >` is definitely not.

4.  **They are nondeterminative**, in the sense that the same data structure could be represented in different, but equally valid, ways. For example, in XML a data item could appear as the value of an attribute or the content of an element. The choice between these can be guided by some high-level nonspecific policies or by the intended use of the data, but this is not enforced by any language constraints or tools. This is different from the application of normalization rules in a relational scenario.

Although both XML and JSON are text-based, in structured query language (SQL) terms, they can also be considered as complex data types alongside `BLOB`, `DATETIME`, etc., and both have been adopted as such within the SQL standard. XML was added as a data type in SQL:2003. JSON was introduced through text operations in SQL:2016, and as a data type in SQL:2023. Using a built-in data type instead of text has some advantages. Validation is simpler, some operations are more efficient, and the overhead of conversion can be avoided when the input or output is required to be in XML or JSON form. In this chapter, we will focus mainly on how XML and JSON can be used for the representation of structured data.

## 16.2 XML

XML is a key member of a family of standards produced by the World Wide Web Consortium (W3C). Version 1.0 first appeared in 1998, with Version 1.1 following in 2004. Several subsequent revisions have corrected errata and provided clarifications. The growth of WWW systems using HTML (itself introduced in 1993) exposed the need for a language that provided a stronger way of representing structured data to support seamless data exchange, transformation, and interoperability across different systems and platforms, and also to allow for extensions to customize the language for specific applications.

There are several other standards relating to XML. In addition to XML itself (and its relationship to SQL), we will limit our main discussion in this chapter to the following:

**XPath**. This is an expression language that provides a means of hierarchic addressing of the nodes in an XML tree. As well as modeling the tree structure of XML, the data model also includes atomic values, function items, and sequences.

**XQuery**. This is a query language designed to be broadly applicable across many types of XML data sources, including structured and semistructured documents, relational databases, and object repositories. XQuery uses the structure of XML intelligently to express queries across all these kinds of data, whether physically stored in XML or viewed as XML via middleware.

These both depend in turn on the *XQuery and XPath Data Model*. This defines the information contained in the input to a query processor and all permissible values of expressions in the XQuery and XPath languages. Both languages have been extended to provide support for JSON as well as XML.
