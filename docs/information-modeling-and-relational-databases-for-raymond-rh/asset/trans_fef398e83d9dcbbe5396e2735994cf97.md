def inCourseHasNrEnrollments(s, c, n): n = count[(e): isanEnrollmentByStudent(s, e) and isanEnrollmentInCourse(e, c)]
ic (s, c, n) requires inCourseHasNrEnrollments(s, c, n) implies n <= 2

示例 (d) 中的*外部频率约束*确保对于每个国家，其政府成员中同时担任共治者的政治家最多有两位。此约束可使用 count 函数制定，也可简单地这样表述：

```
ic (p1, p2, p3, c) requires (isaCoregent(p1) and servesOnGovtOf(p1, c) and isaCoregent(p2) and servesOnGovtOf(p2, c) and isaCoregent(p3) and servesOnGovtOf(p3, c)) implies p1 = p2 or p1 = p3 or p2 = p3
```

*环约束* 在 Rel 中很容易指定。人认识他们自己的*自反*环约束可表达为：`ic(p) requires Person(p) implies knows(p, p)`。没有人是其自己的父母这一*非自反*环约束可表达为：`ic (p) requires not isaParentOf(p, p)`。兄弟姐妹关系的*对称*约束可这样指定：`ic (p1, p2) requires isaSiblingOf(p1, p2) implies isaSiblingOf(p2, p1)`。没有人是其自己父母这一*非对称*环约束可这样表达：`ic (p1, p2) requires isaParentOf(p1, p2) implies not isaParentOf(p2, p1)`。

`isOlderThan` 关系的*传递*性质可按如下方式制定：`ic (p1, p2, p3) requires (isOlderThan(p1, p2) and isOlderThan(p2, p3)) implies isOlderThan(p1, p3)`。直接优先关系的*非传递*约束可按如下方式制定：`ic (e1, e2, e3) requires (directlyPrecedes(e1, e2) and directlyPrecedes(e2, e3)) implies not directlyPrecedes(e1, e3)`。

祖先关系可按如下方式定义：`def isanAncestorOf(p1, p2): isaParentOf(p1, p2) or isaParentOf(p1, p3) and isanAncestorOf(p3, p2)`。祖先关系的*无环约束*可这样指定：`ic (p) requires not isanAncestorOf(p, p)`。

### 其他数据库种类

有时会调用专用数据库种类来处理特定类型的应用。*空间数据库* 需要对空间数据进行高效管理，例如地图（道路、土地等）、二维设计（电路、城镇规划等）和三维设计（医疗手术可视化、分子结构、飞行路径等）。它们为空间数据类型（点、线、多边形等）、空间操作符（重叠、包含、相交等）和空间索引（R 树、四叉树等）提供内置支持。这允许高效地构建和处理空间查询，例如：拟建购物中心 5 公里范围内有多少房屋？哪些航班飞越大洛杉矶地区？哪些图表与图表 37 相似？

以前，空间数据使用专用系统，而字母数字数据使用关系 DBMS。当前的趋势是在一个系统中同时管理标准数据和空间数据。地理信息系统 (GIS) 的典型应用可能按如下方式进行：输入交通事故的标准数据；显示道路地图以突出事故地点；然后用于确定需要采取额外预防措施的区域（例如雷达测速陷阱）。

历史上，GIS 厂商采用了三种主要方法：混合式（空间文件存储中的地理关系对象被赋予可在关系表中引用的标识符）；集成式（空间和非空间数据存储在关系表中）；面向对象（所有数据存储在 ODB 中）。最近，许多空间数据库应用以及其他使用非标准数据的应用已使用对象关系技术实现。

虽然时间只有一个维度，不像空间有三个维度，但*时间信息*的高效管理并非易事。如果需要维护关于对象的历史记录而非快照记录，时间将在建模中占据重要地位。

正如[第 10 章](#Ch010_401-479_B9780443237904000244.xhtml)所讨论的，建模时间可采用多种方法。在某些情况下，我们只需在概念模式中包含 Time 和 Period 等对象类型，并像映射其他对象类型一样映射它们。可能需要区分事务时间（系统记录事实的时间）和有效时间（事实在被建模的 UoD 中为真的时间）。通常，我们需要利用时间关系（如前、后）和时间操作（例如计算两个时间点之间的间隔）。

SQL 标准目前仅包含对时间数据的基本支持，有时普通关系数据库无法高效实现时间方面的功能。对于此类应用，有时会使用称为“时间数据库系统”的专用 DBMS；这些系统为自动时间戳和各种时间操作符提供内置支持。

大多数时间数据库的工作侧重于随时间维护应用对象的相关历史，前提是概念模式本身是固定的。上升一层，如果我们允许概念模式本身随时间变化，问题会变得更复杂。这是模式演化问题的一个方面。

再上升一层，我们可能允许概念元模式本身随时间变化（例如，我们可能在后期决定允许在概念模式语言中使用复杂对象类型的构造器）。此类高阶演化的管理已在不断演化的信息系统研究中得到解决。这一主题为[第 18 章](#Ch018_935-1005_B9780443237904000104.xhtml)中关于元建模的讨论提供了一个动机。

本章前面讨论了集中式和分布式数据库。*联邦数据库* 提供了另一个维度。它们处理在几个不同的数据库系统之间（可能是异构的，例如有的关系型、有的列式、有的键值型等）需要共享数据的情况。在此框架中，每个单独的系统保持其局部自主性，并按需与其他系统通信。由于异构性问题要求在不同数据模型之间进行转换，联邦系统的控制是非同小可的。

云计算的出现加速了对联邦数据库的兴趣。大多数组织发现管理一组异构数据库可能是一场噩梦，但通过将功能外包给云服务提供商，这可以大大缓解。通常提供三级服务：

*基础设施即服务* 提供基于专用或虚拟硬件的基本处理、存储和网络功能。这本质上是在云服务中复制了一个内部数据中心。用户仍负责标准管理功能。
