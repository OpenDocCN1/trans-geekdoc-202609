

# UML 验证的局限性与 ORM 的优势

由于 UML 中的语言化表达支持不足，让我们尝试使用样本总体进行验证。这里也没什么好运气。首先，基于属性的表示法对于多重实例化几乎毫无用处，并且它们将空值引入基础总体，连同空值所有令人困惑的特性一并引入。

UML 支持对象图以便讨论类的单个实例，但这对多重实例化无济于事。例如，活动代码与名称之间关联的 1:1 特性在 [图 1.3](#Ch001_1-25_B9780443237904000062.xhtml#f0020) 的 ORM 事实表中一目了然，但通过扫描多个活动对象则较难看清。

原则上，我们可以引入事实表来在 UML 中实例化二元关联，但这对非二元关联行不通。为什么？在 UML 中，除非关联是二元的，否则无法为其指定阅读方向。因此，关联角色与事实列之间不存在像 ORM 中那样显而易见的联系。

我们所能做的最好办法是为每个角色命名，然后将角色名用作事实表的表头。然而，由于关联角色的非线性布局，事实列与类图的视觉联系将很薄弱，而且关联的元数越高，情况越糟。

## UML 在应用设计方面的优势

就其优势而言，UML 在捕获应用设计的其他方面（如操作、活动、组件封装和部署）的能力上远比 ORM 或 ER 丰富。UML 包含状态机图和活动图等图表，用于捕获业务流程。任何完整的业务领域规范都需要涉及这些动态方面。如果应用程序将用面向对象代码实现，UML 能够更精确地描述要指定的编程代码结构（例如，属性可见性和关联可导航性）。

## 概念数据建模中 ORM 的优势

然而，如果我们将注意力限制在概念数据建模上，ORM 表示法在表达数据业务约束的能力上远比 ER 或 UML 丰富，且更加正交，受变更影响也小得多。作为一个简单的例子，请考虑 [表 1.4](#Ch001_1-25_B9780443237904000062.xhtml#t0025) 的输出报告（评论员和电影 3 为虚构）。您可能想在继续阅读前尝试自行建模该报告。

假设人员仅由姓名标识，Movie 和 Person 类可按如图所示显示。此处使用角色名“director”和“reviewer”来区分 Person 扮演的两个角色。同样，也提供了角色名以区分 Movie 扮演的角色。在本例中，所有四个角色名均为必需。如有需要，也可使用关联名。

与陈氏原始 ER 表示法不同，UML 二元关联通常用不带菱形的线来描绘。虽然这很方便，但 UML 对较长关联使用菱形的做法有些不一致，且避免一元关系是不自然的。原则上，UML 确实允许将菱形作为二元关联的替代表示法，但在实践中很少见。

相比之下，ORM 将关系描绘为一个或多个角色的序列，其中每个角色与一个事实表列相关联，这提供了一种统一、通用的表示法，便于通过语言化表达和样本总体进行验证。

多重性约束表明每部电影恰好有一位导演但可以有多位评论员，且一个人可以导演或评论多部电影。但仍缺少一条业务规则。您能发现它吗？

[图 1.6](#Ch001_1-25_B9780443237904000062.xhtml#f0035) 使用 ORM 对同一领域建模。此处“has”前的“◀”反转了正常的从左向右阅读方向。UML 模型中缺失的规则由“directed”和“reviewed”关联所组成的角色对之间的圆圈“X”约束以图形方式捕获。这称为 `exclusion constraint`（排除约束）。directed 和 reviewed 事实类型填充了违反该排除约束的样本数据——即该约束的一个 `counterexample`（反例）。

![Fig. 1.6 ORM model for Table 1.4, with counterexample for the exclusion constraint.](images/B9780443237904000062/f01-06-9780443237904.jpg)

[图 1.6](#Ch001_1-25_B9780443237904000062.xhtml#B-f0035) [表 1.4](#Ch001_1-25_B9780443237904000062.xhtml#t0025) 的 ORM 模型，包含排除约束的反例。

该排除约束语言化表达为：**No** Person directed **and** reviewed **the same** Movie（没有人既导演又评论了**同一部**电影），或者反过来读：**No** Movie was directed by **and** was reviewed by **the same** Person（没有电影既被**同一个人**导演又被其评论）。要与领域专家验证此规则，您应语言化表达该规则并提供一个反例。例如，在您的模型中，电影 1 由 Ann Green 导演且也由 Ann Green 评论，这是可能的吗？[图 1.6](#Ch001_1-25_B9780443237904000062.xhtml#f0035) 包含此反例。如果排除约束确实适用，那么这两个事实中至少有一个必定是错的。

有些领域专家乐于使用图表工作，有些则不然。有些擅长理解自然语言中的规则，有些则不然。但**所有**领域专家都擅长使用具体示例工作。虽然领域专家不必查看图表，但能够直接在图表上实例化任何角色，使您能清晰地思考规则。

UML 没有通用排除约束的图形表示法，但允许您在附加到相关模型元素的注释中记录约束。如果一个概念已经是您建模语言的一部分，则更容易想到它。

由于排除约束表示法并非 UML 语言的内置部分，在开发模型时很容易遗漏该约束。ER 也是如此。相比之下，ORM 建模过程会提示您考虑此类约束，并允许您正式地可视化和捕获规则。ORM 工具随后可将约束自动映射为可执行代码，以确保规则在实现中得到强制执行。

## ORM 图中的语义域与角色名

ORM 图总是将 `semantic domains`（语义域）显示为对象类型。[图 1.7](#Ch001_1-25_B9780443237904000062.xhtml#f0040)(a) 中的 ORM 图包含 birthdate 和 deathdate 的 `role names`（角色名），显示在相关角色旁边的方括号中。这些角色显然是兼容的，因为它们都由对象类型 Date 扮演。在 ORM 中，角色名可像属性名一样用于自动生成的属性视图，以及用属性风格指定的规则中（例如 `deathdate > birthdate`）。
