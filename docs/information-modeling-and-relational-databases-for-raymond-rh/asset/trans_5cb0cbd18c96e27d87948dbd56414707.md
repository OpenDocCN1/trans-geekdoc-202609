
例如，[图 11.17](#Ch011_481-537_B9780443237904000141.xhtml#f0090) 和 [图 11.18](#Ch011_481-537_B9780443237904000141.xhtml#f0095) 的概念模式最初都映射到 `Employee(e, g)`，其含义是员工 `e` 属于性别 `g`。在这两种情况下，`g` 随后都被 "genderCode" 替换。对于 [图 11.17](#Ch011_481-537_B9780443237904000141.xhtml#f0090)，`e` 被 empNr 替换；但对于 [图 11.18](#Ch011_481-537_B9780443237904000141.xhtml#f0095)，`e` 被解包为 (familyName, initials)，因为标识方案是复合的。由于唯一性约束跨越 `e`，因此它也必须跨越替换它的属性组合。

现在考虑 [图 11.19](#Ch011_481-537_B9780443237904000141.xhtml#f0100) 的概念模式。这里的结构差异在于事实类型具有复合唯一性约束。我们最初可能认为它映射到表 `Drives(e, c)`，其中 `e` 和 `c` 分别是员工和汽车角色的代理标识符。用真实标识符替换代理标识符后，得到表模式 `Drives(familyName, initials, carRegNr)`。因为 `e` 只是较长键的一部分，所以替换它的员工复合标识符也是如此。

### 映射对象化关联

现在让我们讨论一些涉及 `objectification`（也称为 `nesting`）的情况。在 [图 11.22](#Ch011_481-537_B9780443237904000141.xhtml#f0115) 中，关联 Employee worked on Project 被对象化为 Work。这个对象化类型扮演一个强制角色和一个可选角色，两者都是函数的。与其他对象类型一样，我们*最初将对象化关联视为“黑盒”，在脑海中擦除其标识方案*。

![图 11.22 具有函数角色的活动对象化关联。](images/B9780443237904000141/f11-22-9780443237904.jpg)

[图 11.22](#Ch011_481-537_B9780443237904000141.xhtml#B-f0115) 具有函数角色的活动对象化关联。

从这个角度来看，概念模式似乎只有两个事实类型，两者都有连接到对象类型 Work 的函数角色。*事实类型现在按常规方式分组*。因此，这两个事实类型被分组到同一个表中。将嵌套对象类型 Work 可视化为黑盒 "▪"，得到表 `Work(▪, startdate, [enddate])`。最后，我们将 ▪ *解包为其组成属性*（empNr 和 projectName），得到 `Work(empNr, projectName, startdate, [enddate])`。

[图 11.22](#Ch011_481-537_B9780443237904000141.xhtml#f0115) 中的值约束表述为：**对于每个** Work，**现存的** enddate >= startdate。值约束被违反当且仅当其求值为 false（就像 SQL 检查子句一样）。此处关系模式上的脚注注释对应 SQL 检查子句 `check (enddate >= startdate)`。

现在考虑 [图 11.23](#Ch011_481-537_B9780443237904000141.xhtml#f0120) 的 ORM 模式。在这里，员工可能在其实际开始日期已知之前就被分配到项目。因此，对象化的 Assignment 关联的一些实例可能被记录下来，但在（某些数据库状态下）不扮演任何连接的角色。在本例中，因为即使连接角色的析取也是可选的，所以嵌套对象类型是*独立的*——这由 "Assignment !" 中的感叹号标记。与此形成对比的是前一个例子（[图 11.22](#Ch011_481-537_B9780443237904000141.xhtml#f0115)），其中嵌套对象类型 Work 是活动的，且关系模式中的 startdate 列不是可选的。

![图 11.23 映射具有函数角色的独立对象化关联。](images/B9780443237904000141/f11-23-9780443237904.jpg)

[图 11.23](#Ch011_481-537_B9780443237904000141.xhtml#B-f0120) 映射具有函数角色的独立对象化关联。

无论嵌套与否，独立对象类型在映射时都需要特殊处理，如下所示。

*   • 将每个独立对象类型及其扮演函数角色的事实类型（如果有）映射到一个单独的表，以该对象类型的标识符作为主键，所有其他属性为可选。从每个映射自独立对象类型非函数角色（如果有）的列序列，向该主键添加一个子集约束。

如果我们只想记录某员工被分配到特定项目这一事实，我们只需输入 empNr 和 projectName 的值。关于项目工作的开始和结束日期的细节，可以在已知时稍后添加。因为开始日期和结束日期都是可选的，值约束现在表述为：**对于每个** Assignment，**现存的** enddate >= **现存的** startdate。

[图 11.24](#Ch011_481-537_B9780443237904000141.xhtml#f0125) 展示了建模此 UoD 的另一种方式。独立对象类型没有连接的函数角色，并单独映射到一个表。`m:n` 事实类型映射到另一个表。一个子集约束捕获其可选性。如果我们尝试将所有内容映射到一个表，这将违反实体完整性（为什么？）。
