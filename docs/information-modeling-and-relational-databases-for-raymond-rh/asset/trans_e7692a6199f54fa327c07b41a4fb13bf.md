
![图 8.14 Barker 专有弧未处理的一些 ORM 排除约束。](images/B9780443237904000177/f08-14-9780443237904.jpg)

[图 8.14](#Ch008_309-346_B9780443237904000177.xhtml#B-f0075) Barker 专有弧未处理的一些 ORM 排除约束。

Barker ER 表示法允许指定简单的*频率约束*。对于任意正整数 *n*，形式为 = *n*、<*n*、≤*n*、>*n*、≥*n* 的约束可写在单个角色旁，以指示可与扮演另一角色的实例相关联的实例数量。例如，[图 8.15](#Ch008_309-346_B9780443237904000177.xhtml#f0080) 中的频率约束“≤2”表明每个人最多是两个父母的孩子。在 Barker 表示法中，此约束放在父角色上，使得从另一角色开始读取该约束作为一个句子变得容易。

![图 8.15 (a) Barker 表示法和 (b) ORM 中的简单频率约束。](images/B9780443237904000177/f08-15-9780443237904.jpg)

[图 8.15](#Ch008_309-346_B9780443237904000177.xhtml#B-f0080) (a) Barker 表示法和 (b) ORM 中的简单频率约束。

在 ORM 中，约束放在子角色上，使得容易看到该约束对总体的影响（每个人在子角色总体中最多出现两次）。与 Barker 表示法不同，ORM 允许频率约束包含范围（例如 `2..5`）并应用于角色序列。

在 Barker 表示法中，*子类型划分* 使用欧拉图的一种变体来描述。实际上，只能显示分区（互斥且穷尽）。例如，[图 8.16](#Ch008_309-346_B9780443237904000177.xhtml#f0085)(a) 表明每个患者是男性患者或女性患者，但不能两者兼是。正如[第 6.5 节](#Ch006_211-271_B9780443237904000025.xhtml#s0030)所讨论的，ORM 使用有向无环图（DAG）显示子类型划分，并可使用异或约束符号来显示分区约束（通常由子类型定义和其他约束隐含）。

![图 8.16 (a) Barker ER 和 (b) ORM 中的子类型分区。](images/B9780443237904000177/f08-16-9780443237904.jpg)

[图 8.16](#Ch008_309-346_B9780443237904000177.xhtml#B-f0085) (a) Barker ER 和 (b) ORM 中的子类型分区。

欧拉图适用于简单情况，因为它们直观地显示了超类型内部的子类型。然而，与 DAG 不同，它们无法处理复杂情况（例如许多重叠的子类型），并且使得向子类型附加细节变得不方便。出于后一个原因，使用 Barker 表示法时有时会从子类型中省略属性。欧拉图的另一个问题是在单个图上显示多分区（例如，尝试将 Patient 不仅划分为 MalePatient 和 FemalePatient，还划分为 InPatient 和 OutPatient）。

在 Barker 表示法中，如果原始子类型列表不穷尽，则会添加一个“Other”子类型使其穷尽，即使它不扮演特定角色。例如，在[图 8.17](#Ch008_309-346_B9780443237904000177.xhtml#f0090) 中，车辆是汽车或卡车或可能是其他东西，而汽车是轿车或旅行车或可能是其他东西。在 ORM 中，除非 OtherCar 或 OtherVehicle 扮演特定角色，否则无需为它们引入子类型。

![图 8.17 (a) Barker ER 和 (b) ORM 中的非穷尽、互斥子类型。](images/B9780443237904000177/f08-17-9780443237904.jpg)

[图 8.17](#Ch008_309-346_B9780443237904000177.xhtml#B-f0090) (a) Barker ER 和 (b) ORM 中的非穷尽、互斥子类型。

Barker 表示法用于子类型划分的一个主要问题是它不描述重叠子类型（例如 Employee 的子类型 Manager 和 FemaleEmployee）或多重继承（例如 FemaleManager 作为 FemaleEmployee 和 Manager 的子类型）。虽然可以通过一些低级技巧在单继承系统（例如 `Java`）中实现多重继承，但出于概念建模目的，多重继承应直接建模。作为关于子类型划分的最后一个比较点，Barker ER 缺乏 ORM 正式子类型定义和上下文相关标识方案的能力。

除了静态约束外，Barker ER 还包含一个动态的“可变性约束”，用于标记“*不可转移关系*”。该约束声明：一旦某实体类型的实例与一个对象扮演了某角色，它就永远不能再与另一个对象扮演该角色。这通过受约束角色上的空心菱形来指示。例如，[图 8.18](#Ch008_309-346_B9780443237904000177.xhtml#f0095)(a) 声明一个人的出生国是不可转移的。

![图 8.18 Barker 中声明了不可转移性，但 ORM 中没有。](images/B9780443237904000177/f08-18-9780443237904.jpg)

[图 8.18](#Ch008_309-346_B9780443237904000177.xhtml#B-f0095) Barker 中声明了不可转移性，但 ORM 中没有。

正如[图 8.18](#Ch008_309-346_B9780443237904000177.xhtml#f0095)(b) 所示，ORM 目前不支持此约束。为这种及其他动态约束在 ORM 中增加正式支持是一个活跃的研究领域。在实践中，不可转移约束的规范需要确保实现的模型仍然允许授权用户进行错误更正。例如，如果某澳大利亚人的出生国被误录为奥地利，应该能够将其更正为澳大利亚。我们在下一章检查 UML 中的可变性属性时将进一步讨论此问题。

好了，这相当全面地涵盖了用于 ER 的 Barker 表示法。正如我们所见，它在表达简单的强制性、唯一性、排除和频率约束；简单的子类型划分；以及不可转移关系方面做得很好。然而，如果特性被建模为属性而不是关系，则几乎无法为其指定这些约束。

与 ORM 不同，Barker 表示法不支持一元、*n* 元或对象化关联（嵌套）。此外，它缺乏对大多数高级 ORM 约束的支持（例如子集、多角色排除、环约束和连接约束）。它不包含用于在概念层面指定查询、其他约束和派生规则的正式文本语言。尽管如此，它优于许多其他 ER 表示法，且仍被广泛使用。如果您需要用 Barker ER 表示法指定模型，我们建议您先在 ORM 中建模，将其映射到 Barker 表示法，并记下无法用图形方式表达的任何规则。

我们现在不给您布置关于 Barker 表示法的练习，而是等到本章结束，届时我们将介绍正在使用的主要 ER 表示法以及一些从 ORM 映射到 ER 的技术。那时您可以决定想练习哪种表示法。

## 8.3 信息工程表示法

IE 方法始于 Clive Finkelstein 在澳大利亚的工作和 CACI 在英国的工作，后来由 James Martin 进行了改编。存在不同版本的 IE，没有单一标准。以某种形式，IE 受许多数据建模工具支持，是数据库设计最流行的表示法之一。

在 IE 方法中，*实体类型* 显示为命名矩形，如[图 8.19](#Ch008_309-346_B9780443237904000177.xhtml#f0100)(a) 所示。*属性* 通常显示在实体类型名称下方的分区中，如[图 8.19](#Ch008_309-346_B9780443237904000177.xhtml#f0100)(b) 所示，但有时也单独显示（例如气泡图）。某些版本支持属性上的基本约束，如 Ma/Op/Unique。
