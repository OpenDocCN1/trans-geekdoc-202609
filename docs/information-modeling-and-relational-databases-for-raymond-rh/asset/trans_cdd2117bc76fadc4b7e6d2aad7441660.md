

# ORM 处理推导规则方法的一个优势

ORM 处理推导规则方法的一个优势在于其更加稳定，因为它不受模式变更的影响，例如属性后来被重构为关联。

## 9.8 从 ORM 到 UML 的映射

在 **步骤 2** 中，我们决定将哪些对象类型建模为类，以及将哪些 *n*:1 和 1:1 ORM 关联重构为属性。通常，扮演函数性事实角色的实体类型成为类。从实体类型 *A* 到值类型 B，或到一个你永远不想记录其细节的实体类型 *B* 的函数性二元关联（*n*:1 和 1:1），通常映射为 *A* 的一个属性。如果你已经指定了角色名，这些通常可以用作属性名，对象类型名则成为属性的域名。

[图 9.56](#Ch009_347-399_B9780443237904000013.xhtml#f0285) 中的映射演示了这些步骤 2 的考量因素中的几个，以及步骤 6（将 ORM 约束映射为 UML 图形约束、文本约束或注释）。`{U1}` 唯一性标注不是标准 UML。性别代码上的值约束通过枚举类型来捕获。

![Fig. 9.56 Step 2: Map selected n:1 and 1:1 associations to attributes.](images/B9780443237904000013/f09-56-9780443237904.jpg)

[图 9.56](#Ch009_347-399_B9780443237904000013.xhtml#B-f0285) 步骤 2：将选定的 *n*:1 和 1:1 关联映射为属性。

在极少数情况下，独立的值类型扮演显式强制角色，或在 1:*n* 事实类型中扮演函数性事实角色，则映射为类。[图 9.57](#Ch009_347-399_B9780443237904000013.xhtml#f0290)(a) 中的示例处理了我们存储头衔-性别限制的情况（例如，头衔“Mr”仅限男性）。

![Fig. 9.57 Step 2: Rare cases of value types mapping to classes.](images/B9780443237904000013/f09-57-9780443237904.jpg)

[图 9.57](#Ch009_347-399_B9780443237904000013.xhtml#B-f0290) 步骤 2：值类型映射为类的罕见情况。

[图 9.57](#Ch009_347-399_B9780443237904000013.xhtml#f0290)(b) 中的示例使用多值属性来存储适用于某头衔的所有性别（例如，头衔“Dr.”适用于男性和女性两种性别）。Title 类提供了从头衔到适用性别的快速访问，但从性别到头衔的访问较慢。如前所述，多值属性应谨慎使用。

在 **步骤 3** 中，我们将一元角色映射为布尔属性或子类。[图 9.58](#Ch009_347-399_B9780443237904000013.xhtml#f0295) 中的示例假设一元角色采用通常的 *CWA* 解释，因此任何未被显式断言为吸烟者的人都被理解为不吸烟者。采用 *开放世界方法* (*OWA*) 时，未能断言某人吸烟意味着该人是否吸烟是未知的。

![Fig. 9.58 Step 3: Map unaries to Boolean attributes or subclasses (CWA approach).](images/B9780443237904000013/f09-58-9780443237904.jpg)

[图 9.58](#Ch009_347-399_B9780443237904000013.xhtml#B-f0295) 步骤 3：将一元角色映射为布尔属性或子类（CWA 方法）。

如果我们需要显式记录某雇员是吸烟者还是不吸烟者，而对于某些雇员这可能是未知的，则修改 UML 类图，使 smokes 属性的多重度为 `[0..1]`，并将 `{complete}` 约束改为 `{incomplete}`。

在 ORM 中建模这种情况的一种方法是用二元事实类型 Employee has SmokerStatus 替换一元角色，其中第一个角色具有唯一性约束但无强制角色约束，将 SmokerStatus 值类型的数据类型设置为布尔型。在 NORMA 中，编辑值类型的属性表，将 Logical 设为 True 或 False。

在 **步骤 4** 中，剩余的事实类型映射为关联。任何 *m:n* 关联通常应保持原样。在 [图 9.59](#Ch009_347-399_B9780443237904000013.xhtml#f0300) 的示例中，保留 *n*:1 事实类型作为关联，因为它关联两个在映射中成为类的实体类型。即使 *m:n* 关联不适用，我们通常也会保留 Country 作为类，因为现在或将来，我们很可能会记录其详细信息（例如国家名称）。

![Fig. 9.59 Step 4: Map remaining fact types to associations.](images/B9780443237904000013/f09-59-9780443237904.jpg)

[图 9.59](#Ch009_347-399_B9780443237904000013.xhtml#B-f0300) 步骤 4：将剩余事实类型映射为关联。

如果 *m:n* 关联涉及值类型（例如 Employee has PhoneNr），请检查是否可以将 *m:n* 关联转换为多个 *n*:1 关联（例如 Employee has PhoneNr1; Employee has PhoneNr2 等）。此类概念模式转换在 [第 14 章](#Ch014_681-771_B9780443237904000189.xhtml) 中有深入讨论。如果 *n*-元事实类型中的每个对象类型都应映射为类（例如，它扮演其他函数性角色），则将 *n*-元事实类型映射为 *n*-元关联。[图 9.60](#Ch009_347-399_B9780443237904000013.xhtml#f0305) 提供了一个示例。

![Fig. 9.60 Step 4: Map some n-ary fact types to n-ary associations.](images/B9780443237904000013/f09-60-9780443237904.jpg)

[图 9.60](#Ch009_347-399_B9780443237904000013.xhtml#B-f0305) 步骤 4：将某些 *n*-元事实类型映射为 *n*-元关联。

如果三元事实类型中的某个对象类型不应映射为类（通常是 *m:n:1* 唯一性模式且该对象类型在唯一性约束之外），则将关联的其余部分对象化为关联类，并将其角色映射为属性。[图 9.61](#Ch009_347-399_B9780443237904000013.xhtml#f0310)(b) 显示了一个示例。一种不太理想的替代方案是使用同名类代替关联类，如 [图 9.61](#Ch009_347-399_B9780443237904000013.xhtml#f0310)(c) 所示。

![Fig. 9.61 Step 4: Map an n-ary fact type to association classes or coreferenced classes.](images/B9780443237904000013/f09-61-9780443237904.jpg)

[图 9.61](#Ch009_347-399_B9780443237904000013.xhtml#B-f0310) 步骤 4：将 *n*-元事实类型映射为关联类或同名类。

对象化关联映射为关联类，如前所示的 [图 9.18](#Ch009_347-399_B9780443237904000013.xhtml#f0095)。某些同名情况可映射为限定关联，但映射为由文本复合唯一性约束补充的单独属性或关联，提供了更通用的解决方案。

在 **步骤 5** 中，ORM 中最简单的约束通常以显而易见的方式映射为多重度约束，如前所示。更复杂的 ORM 约束在 UML 中没有图形对应项，因此你需要以文本形式单独记录这些约束。[表 9.4](#Ch009_347-399_B9780443237904000013.xhtml#t0025) 总结了主要对应关系。连接约束将在下一章讨论。
