

# 可变性限制与派生数据

## 可变性限制

一些传统的数据建模方法也提到了一些可变性限制。Barker ER 表示法包含一个菱形，用于将关系标记为不可转移的（一旦实体类型的一个实例与一个对象扮演了某个角色，它就不能与另一个对象扮演该角色）。虽然可变性限制可能很有用，但在实践中，它们在数据库环境中的应用是有限的。

其中一个原因是，输入数据库的事实可能需要更改。对于快照数据，这是常态，但即使对于历史数据，也可能发生更改。最常见的情况是允许纠正错误，这可能是因为我们最初被告知了错误的信息，或者因为我们在录入数据时粗心大意导致了拼写错误或笔误。

在特殊情况下，我们可能要求将某种错误保留在数据库中（例如，出于审计目的），但通过录入后续事实来纠正该错误。这种方法对于银行交易很有意义（参见[图 9.50](#Ch009_347-399_B9780443237904000013.xhtml#f0255)）。例如，如果一笔 100 美元的存款交易被错误地录入为 1000 美元，该错误记录会被保留，但一旦发现错误，就可以通过一笔 900 美元的银行取款来补偿。余额既是派生的又是存储的，其 `readOnly` 状态通常由基本属性上的 `readOnly` 设置连同派生规则共同暗示。

![Fig. 9.50 Transaction 的所有属性均为 readOnly。](images/B9780443237904000013/f09-50-9780443237904.jpg)

[图 9.50](#Ch009_347-399_B9780443237904000013.xhtml#B-f0255) Transaction 的所有属性均为 readOnly。

一些作者允许为类指定可变性，作为为其所有属性和相反关联端声明此项的缩写（[Booch et al., 1999](#Ch009_347-399_B9780443237904000013.xhtml#bb0120)，第 184 页）。例如，[图 9.50](#Ch009_347-399_B9780443237904000013.xhtml#f0255) 中所有的 `{readOnly}` 约束可能被替换为“Transaction”名称下方的单个 `{readOnly}` 约束。虽然这种表示法更整洁，但很少使用。即使在这个例子中，我们可能仍希望允许稍后添加非冻结信息的可能性（例如，一笔交易可能由零个或多个审计员审计）。

可变性设置在程序代码设计中很有用。虽然可变性设置在 ORM 中尚不受支持，因为 ORM 侧重于静态约束，但它们正在被考虑纳入扩展以支持动态约束（见下一章）。从更广泛的角度来看，能够完整建模安全问题（例如，谁有权更改什么）将提供额外价值。

## 有序集合与集合类型

UML 允许为多值属性和关联端指定 `{ordered}` 和 `{unique}` 属性。因为 `{unique}` 默认为 true，所以使用 `{ordered}` 表示有序集合（一个无重复项的序列）。例如，[图 9.51](#Ch009_347-399_B9780443237904000013.xhtml#f0260)(a) 展示了在 UML 中建模论文作者身份的一种方式。每篇论文都有一个作者列表，每位作者在该列表中最多只能出现一次。

![Fig. 9.51 (a) UML 和 (b) ORM 中建模的有序集合。](images/B9780443237904000013/f09-51-9780443237904.jpg)

[图 9.51](#Ch009_347-399_B9780443237904000013.xhtml#B-f0260) (a) UML 和 (b) ORM 中建模的有序集合。

这可以通过使用 `Position` 对象类型来存储作者在列表中的顺序位置，在平面 ORM 中建模，如[图 9.51](#Ch009_347-399_B9780443237904000013.xhtml#f0260)(b) 所示。前两个角色上的唯一性约束声明了对于每篇论文，一位作者最多占据一个位置；覆盖第一和第三个角色的约束表明对于任何论文，每个位置最多由一位作者占据。文本约束指出列表位置从 1 开始按顺序编号。

虽然这种三元表示法看起来可能笨拙，但它易于填充，并且便于任何涉及位置的讨论（例如，论文 21 的第二作者是谁？）。从实现角度来看，仍可选择有序集合结构。

有序集合是集合类型的一个例子。正如[第 10 章](#Ch010_401-479_B9780443237904000244.xhtml)所述，某些版本的 ORM 允许以类似 UML 的方式将集合指定为映射注解，某些 ORM 版本允许将集合直接建模为一等对象。

## 关联重定义

UML 2 引入了*关联重定义*的概念。此概念适用于泛化以及关联。其主要用途之一是指定对涉及超类型的关联进行特化的关联的更强约束。例如，在[图 9.52](#Ch009_347-399_B9780443237904000013.xhtml#f0265)(a) 中，`executiveCar` 角色重定义了 `assignedCar` 角色，应用了仅适用于高管的更强的多重性约束。实际上，关联“高管被分配公司汽车”被视为“员工被分配公司汽车”关联的一个特化。更强的多重性约束可以通过文本约束在 ORM 中表示，如[图 9.52](#Ch009_347-399_B9780443237904000013.xhtml#f0265)(b) 所示，或通过涉及子类型链接的子集约束表示（见[第 10.8 节](#Ch010_401-479_B9780443237904000244.xhtml#s0080)）。

![Fig. 9.52 (a) UML 和 (b) ORM 中的关联重定义。](images/B9780443237904000013/f09-52-9780443237904.jpg)

## 派生数据

现在让我们考虑*派生数据*。在 UML 中，派生元素（例如属性、关联或关联角色）通过在其名称前加前缀“/”来指示。也可以选择性地指定*派生规则*。派生规则可以表示为约束或注释，通过虚线连接到派生元素。这条线实际上是依赖箭头的简写，可选择性地用构造型名称 `«derive»` 标注。

因为涉及约束或注释，所以箭头尖可以省略（假定约束或注释为源）。例如，[图 9.53](#Ch009_347-399_B9780443237904000013.xhtml#f0270)(a) 包含 `area` 作为派生属性。[图 9.53](#Ch009_347-399_B9780443237904000013.xhtml#f0270)(b) 显示了 ORM 模式。

![Fig. 9.53 (a) UML 和 (b) ORM 中 area 的派生。](images/B9780443237904000013/f09-53-9780443237904.jpg)

[图 9.53](#Ch009_347-399_B9780443237904000013.xhtml#B-f0270) (a) UML 和 (b) ORM 中 area 的派生。

UML 依赖线也可以完全省略，约束显示在派生元素旁边的大括号中（在这种情况下，由建模工具负责隐式维护图形链接）。[图 9.54](#Ch009_347-399_B9780443237904000013.xhtml#f0275)(a) 中的示例将舅舅关系表示为派生关联。为了演示目的，关联端包含了角色名。相应的 ORM 模式显示在[图 9.54](#Ch009_347-399_B9780443237904000013.xhtml#f0275)(b) 中，派生规则以关系风格指定。

![Fig. 9.54 (a) UML 和 (b) ORM 中的派生舅舅关联。](images/B9780443237904000013/f09-54-9780443237904.jpg)

[图 9.54](#Ch009_347-399_B9780443237904000013.xhtml#B-f0275) (a) UML 和 (b) ORM 中的派生舅舅关联。

虽然精确的角色名并不总是优雅的，但在涉及路径投影的派生规则中使用角色名可以促进规则的简洁表达，如这里的 UML 模型所示。通过向 ORM 模式添加角色名，派生规则可以用属性风格简洁地指定为：`define uncle of Person as brother of parent of Person`。更复杂的派生规则可以用英语非正式地陈述，或用 OCL 等语言正式地陈述。
