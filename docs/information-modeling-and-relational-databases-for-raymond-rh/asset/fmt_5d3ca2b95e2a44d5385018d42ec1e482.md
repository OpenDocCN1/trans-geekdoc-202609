
## 角色基数约束

*角色基数约束*限制每个数据库状态下角色填充集的基数。[图 7.22](#Ch007_273-308_B978044323790400013X.xhtml#f0115)(c) 中的角色基数约束“# ≤ 1”意味着最多只有一名员工扮演董事角色。请注意，ORM 基数约束与实体-关系建模（ER）中所谓的“基数”约束不同，后者对应频率约束和/或强制角色约束。

基数约束很少包含在图表中，因为它们*通常由现有的值约束或频率约束隐含*。例如，`Gender(.Code)` 上的 `{"M", "F"}` 值约束隐含了 `Gender` 上的“# ≤ 2”。如果最多只有一个参议院，那么[图 7.23](#Ch007_273-308_B978044323790400013X.xhtml#f0120)(b) 中 `Senate` 角色上 ≤100 的频率约束隐含了 `Senator` 上的 # ≤100 基数约束。但请注意，`Senate` 上的 # ≤1 基数约束仍然是必需的。

![图 7.23 由值约束或频率约束隐含的对象基数约束。](images/B978044323790400013X/f07-23-9780443237904.jpg)

[图 7.23](#Ch007_273-308_B978044323790400013X.xhtml#B-f0120) 由值约束或频率约束隐含的对象基数约束。

在实践中，通常允许多个参议院更有用，在这种情况下，我们使用频率约束将每个参议院的规模限制在最多 100 名成员，即使 `Senate` 上的基数约束不再适用（参见[图 7.23](#Ch007_273-308_B978044323790400013X.xhtml#f0120)(c)）。

*析取基数约束*将基数限制为符合用大括号“{}”括起来、条目间用逗号分隔的集合中列出的多个简单基数约束中的至少一个。例如，`#{0,12}` 意味着基数必须是 0 或 12，而 `#{≤2, 4, 6, 8..10}` 表示基数必须是 0、1、2、4、6、8、9 或 10。

## 值比较约束

*值比较约束*使用六个比较运算符之一（`<`、`≤`、`>`、`≥`、`=`、`≠`）将一个值与另一个值进行比较。该约束由一个带圆圈的运算符表示，通过一条虚线箭头从左操作数角色连接到右操作数角色。圆圈上添加两个点以表示被比较的两个实例（提醒我们这是实例间的比较，而非集合间的比较）。

`=` 和 `≠` 值比较约束通常最好用环约束替代（例如，`Country borders Country` 上的 `≠` 值比较约束可替代为非自反环约束）。

[图 7.24](#Ch007_273-308_B978044323790400013X.xhtml#f0125) 中的值比较约束可口头表述为：**对于每个** `Employee`，`birthdate < hiredate`；**对于每个** `Project`，**现有的** `enddate ≥ startdate`。对于可选属性（如 `enddate`），“**现有的**”将比较限制在属性实例存在的情况下。因此，“**现有的** `enddate ≥ startdate`”是“**如果** `enddate` **存在则** `enddate ≥ startdate`”的简写。因此，如果一个项目没有结束日期，该约束仍然得到满足（它映射到 SQL 检查子句 `check (enddate >= startdate)`，仅当其评估为 false 时才被违反）。

![图 7.24 值比较约束示例。](images/B978044323790400013X/f07-24-9780443237904.jpg)

[图 7.24](#Ch007_273-308_B978044323790400013X.xhtml#B-f0125) 值比较约束示例。

值比较约束有点像环约束，因为被约束的角色是兼容的（例如，[图 7.24](#Ch007_273-308_B978044323790400013X.xhtml#f0125)(a) 中比较的 `birthdate` 和 `hiredate` 属于同一员工）。与非自反环约束一样，值比较约束通常执行成本较低，因为它们通常比较表中同一行的值，而不是比较值的集合。

## 文本规则

你现在已经了解了几乎所有的 ORM 图形符号。一些更高级的约束和规则将在[第 10 章](#Ch010_401-479_B9780443237904000244.xhtml)中讨论。为更多约束添加图形符号会使图形语言难以学习并导致图表杂乱。概念模式图提供了一个面向人类的、无歧义的、但通常不完整的 UoD 结构规范。

无法使用预定义图形符号表达的规则可指定为*文本规则*，最好使用高级形式语言。在 ORM 2 中，显示这些文本规则的首选方式是通过*脚注*，脚注编号标记图表上涉及的模型元素。文本规则（约束、推导规则和子类型定义）本身可显示在文本框中，作为脚注或出现在图表的其他位置，理想情况下可切换其显示开关。

[图 7.25](#Ch007_273-308_B978044323790400013X.xhtml#f0130)(a) 展示了显示三条文本规则的一种方式。规则 1 声明员工的受雇日期晚于出生日期。这与[图 7.24](#Ch007_273-308_B978044323790400013X.xhtml#f0125)(a) 中的值比较约束相同，但在[图 7.25](#Ch007_273-308_B978044323790400013X.xhtml#f0130)(a) 中该约束以文本形式表达。脚注编号 1 附加在 `Employee` 类型名称后。`birth` 和 `hire` 谓词之间也存在成对排斥约束，但因现已隐含而省略。

![图 7.25 文本规则示例。](images/B978044323790400013X/f07-25-9780443237904.jpg)

[图 7.25](#Ch007_273-308_B978044323790400013X.xhtml#B-f0130) 文本规则示例。

规则 2 规定非高管最多使用一辆公司车。这是一个*受限唯一性约束*，因为它加强了 `Employee uses CompanyCar` 上的唯一性约束，但将其限制为 `Employee` 的一个子类型。

规则 3 规定每位高管必须拥有公司车的使用权。这是一个*受限强制角色约束*，因为它使 `Employee` 的一个可选角色对 `Employee` 的一个子类型变为强制的。

[图 7.25](#Ch007_273-308_B978044323790400013X.xhtml#f0130)(b) 展示了建模受限强制角色约束的另一种方式：显式定义 `Executive` 作为 `Employee` 的子类型，并从子类型链接（`Executive **is an** Employee`）到 `Employee uses CompanyCar` 中的 `Employee` 角色添加子集约束，以声明每位高管必须扮演使用公司车的角色。

## 综合示例：计算机网络
