## 7.3 Ring Constraints

When two roles in a predicate are played by the same object type, the path from the object type through the role pair and back to the object type forms a “ring”. If the roles are played by subtypes with a common supertype, the path from and back to the supertype also forms a ring. The role pair typically forms a binary predicate that is then called a *ring predicate*, but may be part of a longer predicate (see the shaded role pairs in [Fig. 7.7](#Ch007_273-308_B978044323790400013X.xhtml#f0040)) or may even come from different predicates in a join path (join constraints are discussed in [Chapter 10](#Ch010_401-479_B9780443237904000244.xhtml)). A *ring constraint* may apply only to a pair of roles like this.

[Fig. 7.7](#Ch007_273-308_B978044323790400013X.xhtml#B-f0040) Ring constraints may apply to the shaded role pairs.

In [Fig. 7.8](#Ch007_273-308_B978044323790400013X.xhtml#f0045), the predicate *R* might be obtained from a longer predicate by projecting on roles *r*[1] and *r*[2], and *A* might be a supertype of the object types playing *r*[1] and *r*[2]. For each state of the database, pop(*r*[1],*r*[2]) is a set of ordered pairs, and hence a relation, of type *R*. Derived as well as asserted relations are allowed.

Consider the model in [Fig. 7.9](#Ch007_273-308_B978044323790400013X.xhtml#f0050)(a). For simplicity, assume people in this UoD are identified by their first name. Here, each person likes himself/herself. Suppose that in our UoD, this is true for all possible populations—each person who plays the role of liking or of being liked must like himself/herself. In this case, the Likes predicate is said to be *locally reflexive* (or reflexive over its populations). If we delete just the third row from [Fig. 7.9](#Ch007_273-308_B978044323790400013X.xhtml#f0050)(a), then Bill doesn’t like himself, and the relation is not reflexive. The infix notation “*xRy*” (read “*x R*s *y*”) means *x* bears the relationship *R* to *y*. Using *R* in the general sense discussed above, and using “→” for “*implies*” and ∀ for the *universal quantifier* (read as “for each”), we define:

![Fig. 7.9 (a) A locally reflexive constraint, and (b) a purely reflexive constraint.](images/B978044323790400013X/f07-09-9780443237904.jpg)

[Fig. 7.9](#Ch007_273-308_B978044323790400013X.xhtml#B-f0050) (a) A locally reflexive constraint, and (b) a purely reflexive constraint.

```
R is locally reflexive iff ∀ x,y (xRy → xRx)
R is purely reflexive iff ∀ x,y (xRy → x = y)
```

If we picture an object as a black dot and Likes as an arrow, we can picture this reflexion as a relationship line starting and ending at the same object, as shown at the left of [Fig. 7.9](#Ch007_273-308_B978044323790400013X.xhtml#f0050)(a). A *locally reflexive constraint* is displayed using a simplified version of this icon (arrow-tip removed), attached to the role pair. A *purely reflective constraint* adds a vertical stroke inside the circle, as in [Fig. 7.9](#Ch007_273-308_B978044323790400013X.xhtml#f0050)(b).

Many important relations are reflexive (e.g., =, ≤, is parallel to, implies). A relation that is reflexive over all things in the UoD is said to be *globally reflexive* (or *totally reflexive*), that is, for all *x*, *xRx*. Of the four examples cited, only “=” is globally reflexive. For example, “implies” is defined for propositions but not for people. When we say “reflexive”, we usually mean locally reflexive. In practice, purely reflexive constraints are rare, and globally reflexive constraints are so rare that object-role modeling (ORM) does not support them.

Now, consider a UoD where anybody who likes a person is also liked by that person. One satisfying population comprises the three facts: Ann likes Bill; Bill likes Bill; Bill likes Ann (see [Fig. 7.10](#Ch007_273-308_B978044323790400013X.xhtml#f0055)(a)). Here, given any persons *x* and *y*, not necessarily distinct, if *x* likes *y* then *y* likes *x*. If this is always the case, Likes is *symmetric*. The dot-arrow diagram in [Fig. 7.10](#Ch007_273-308_B978044323790400013X.xhtml#f0055)(a) conveys the idea that if the relationship holds in one direction, it also holds in the other direction. A *symmetric constraint* is displayed using a simplified version of this icon (arrow-tips removed), attached to the role pair, as shown. We define this notion for any predicate or relation *R* as follows:

![Fig. 7.10 Symmetric ring constraints.](images/B978044323790400013X/f07-10-9780443237904.jpg)

[Fig. 7.10](#Ch007_273-308_B978044323790400013X.xhtml#B-f0055) Symmetric ring constraints.

```
R is symmetric iff   ∀ x,y (xRy → yRx)
```

Now consider a UoD where, if one person likes a second, and the second person likes a third, then the first person must like the third. In this case, we say that likes is *transitive*. The definition includes the case where the persons are the same. The populated schema in [Fig. 7.11](#Ch007_273-308_B978044323790400013X.xhtml#f0060)(a) illustrates this property.

![Fig. 7.11 Transitive ring constraints.](images/B978044323790400013X/f07-11-9780443237904.jpg)

[Fig. 7.11](#Ch007_273-308_B978044323790400013X.xhtml#B-f0060) Transitive ring constraints.

The dot-arrow diagram in [Fig. 7.11](#Ch007_273-308_B978044323790400013X.xhtml#f0060)(a) indicates that if a chain of relationships exists, the relationship also applies from the first to the last member of the chain. A *transitive constraint* is displayed using a simplified version of this icon (arrow-tip removed), attached to the role pair. In general, transitivity may be defined as follows. Here, we use “&” for “and” and give “&” precedence over “→” (so that the & operation is evaluated first). Note that *x*, *y*, and *z* need not be distinct.

```
R is transitive iff ∀ x,y,z [(xRy & yRz) → xRz]
```

We leave it as an exercise to prove that a relation that is both symmetric and transitive must also be reflexive over its population. A relation that is reflexive, symmetric, and transitive is called an “RST relation” or “equivalence relation”. The classic example of this is the identity relation “=”. The inequality relation “≠” is symmetric only, while the less than relation “<” is transitive only.

Relational properties such as reflexivity, symmetry, and transitivity might be thought of as constraints because they limit the allowable relations. However, such properties are *positive* and are used more often to *derive* additional facts than constrain existing facts.

We now consider *negative* relational properties such as irreflexivity and asymmetry. Given the existence of some facts, such negative properties imply the nonexistence of certain other facts. Such properties are best handled as simple constraints. An example will help clarify things. Look at the populated parenthood fact type in [Fig. 7.12](#Ch007_273-308_B978044323790400013X.xhtml#f0065) and see if you can spot anything wrong.

![Fig. 7.12 What is wrong here?](images/B978044323790400013X/f07-12-9780443237904.jpg)

[Fig. 7.12](#Ch007_273-308_B978044323790400013X.xhtml#B-f0065) What is wrong here?

The population shown is consistent with the constraints specified. Parenthood is many:many, and each person has at most two parents. But as you no doubt noticed, some of the facts in the table are inconsistent with the real-world concept of parenthood. We need to add more constraints so that the information system is able to reject such erroneous populations.
