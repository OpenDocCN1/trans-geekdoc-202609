
# One advantage of ORM’s approach to derivation rules

One advantage of ORM’s approach to derivation rules is that it is more stable because it is not impacted by schema changes such as attributes being later remodeled as associations.

## 9.8 Mapping from ORM to UML

The *UML map procedure* in [Table 9.3](#Ch009_347-399_B9780443237904000013.xhtml#t0020) provides basic guidelines for mapping ORM schemas to UML class diagrams. Selected entity types and value types map to object classes and data types, including attribute domains when associations are replaced by attributes. We now illustrate this procedure.

![Fig. 9.55 Step 1: Replace any set of exclusive binaries by a binary fact type.](images/B9780443237904000013/f09-55-9780443237904.jpg)

[Fig. 9.55](#Ch009_347-399_B9780443237904000013.xhtml#B-f0280) Step 1: Replace any set of exclusive binaries by a binary fact type.

In **step 2**, we decide which object types to model as classes and which *n*:1 and 1:1 ORM associations to remodel as attributes. Typically, entity types that play functional fact roles become classes. Functional binary (*n*:1 and 1:1) associations from an entity type *A* to a value type B, or to an entity type *B* about which you never want to record details, usually map to an attribute of *A*. If you have specified role names, these can usually be used as attribute names, with the object type name becoming the attribute’s domain name.

The mapping in [Fig. 9.56](#Ch009_347-399_B9780443237904000013.xhtml#f0285) illustrates several of these step 2 considerations as well as step 6 (map ORM constraints to UML graphic constraints, textual constraints, or notes). The `{U1}` annotation for uniqueness is not standard UML. The value constraint on gender codes is captured using an enumeration type.

![Fig. 9.56 Step 2: Map selected n:1 and 1:1 associations to attributes.](images/B9780443237904000013/f09-56-9780443237904.jpg)

[Fig. 9.56](#Ch009_347-399_B9780443237904000013.xhtml#B-f0285) Step 2: Map selected *n*:1 and 1:1 associations to attributes.

In rare cases, value types that are independent play an explicit mandatory role, or play a functional fact role in a 1:*n* fact type map to classes. The example in [Fig. 9.57](#Ch009_347-399_B9780443237904000013.xhtml#f0290)(a) deals with cases where we store title–gender restrictions (e.g., the title “Mr” is restricted to the male gender).

![Fig. 9.57 Step 2: Rare cases of value types mapping to classes.](images/B9780443237904000013/f09-57-9780443237904.jpg)

[Fig. 9.57](#Ch009_347-399_B9780443237904000013.xhtml#B-f0290) Step 2: Rare cases of value types mapping to classes.

The example in [Fig. 9.57](#Ch009_347-399_B9780443237904000013.xhtml#f0290)(b) uses a multivalued attribute to store all the genders applicable to a title (e.g., the title “Dr.” applies to both male and female genders). The Title class gives fast access from title to applicable gender, but slow access from gender to title. As discussed earlier, multivalued attributes should be used sparingly.

In **step 3**, we map unaries to Boolean attributes or to subclasses. The example in [Fig. 9.58](#Ch009_347-399_B9780443237904000013.xhtml#f0295) assumes the usual *CWA* interpretation for the unary, so anyone not explicitly asserted to smoke is understood to be a nonsmoker. With an *open world approach* (*OWA*), failure to assert that a given person smokes means it is unknown whether that person smokes.

![Fig. 9.58 Step 3: Map unaries to Boolean attributes or subclasses (CWA approach).](images/B9780443237904000013/f09-58-9780443237904.jpg)

[Fig. 9.58](#Ch009_347-399_B9780443237904000013.xhtml#B-f0295) Step 3: Map unaries to Boolean attributes or subclasses (CWA approach).

If we need to explicitly record that an employee is a smoker or is a nonsmoker, and this might be unknown for some employees, the UML class diagrams are modified so that the smokes attribute has a multiplicity of `[0..1]` and the `{complete}` constraint is changed to `{incomplete}`.

One way to model this situation in ORM is to replace the unary with the binary fact type Employee has SmokerStatus, where the first role has a uniqueness constraint but no mandatory role constraint, setting the data type of the SmokerStatus value type to Boolean. To do this in NORMA, edit the Properties sheet for the value type to Logical: True or False.

In **step 4**, the remaining fact types are mapped to associations. Any *m:n* associations should normally remain that way. In the example in [Fig. 9.59](#Ch009_347-399_B9780443237904000013.xhtml#f0300), the *n*:1 fact type is retained as an association because it relates two entity types that become classes in the mapping. Even if the *m:n* association did not apply, we would normally retain Country as a class because now or later, we are likely to record details for it (e.g., country name).

![Fig. 9.59 Step 4: Map remaining fact types to associations.](images/B9780443237904000013/f09-59-9780443237904.jpg)

[Fig. 9.59](#Ch009_347-399_B9780443237904000013.xhtml#B-f0300) Step 4: Map remaining fact types to associations.

If an *m:n* association involves a value type (e.g., Employee has PhoneNr), see if it is possible to transform the *m:n* association into multiple *n*:1 associations (e.g., Employee has PhoneNr1; Employee has PhoneNr2, etc.). Conceptual schema transformations like this are discussed in depth in [Chapter 14](#Ch014_681-771_B9780443237904000189.xhtml). If each object type in an *n*-ary fact type should map to a class (e.g., it plays other functional roles), then map the *n*-ary fact type to an *n*-ary association. [Fig. 9.60](#Ch009_347-399_B9780443237904000013.xhtml#f0305) provides an example.

![Fig. 9.60 Step 4: Map some n-ary fact types to n-ary associations.](images/B9780443237904000013/f09-60-9780443237904.jpg)

[Fig. 9.60](#Ch009_347-399_B9780443237904000013.xhtml#B-f0305) Step 4: Map some *n*-ary fact types to *n*-ary associations.

If an object type in a ternary fact type should not map to a class (typically an *m:n:1* uniqueness pattern with it outside the uniqueness constraint), then objectify the rest of the association as an association class, and map its role as an attribute. [Fig. 9.61](#Ch009_347-399_B9780443237904000013.xhtml#f0310)(b) shows an example. A less preferable alternative is to use a coreferenced class instead of an association class, as in [Fig. 9.61](#Ch009_347-399_B9780443237904000013.xhtml#f0310)(c).

![Fig. 9.61 Step 4: Map an n-ary fact type to association classes or coreferenced classes.](images/B9780443237904000013/f09-61-9780443237904.jpg)

[Fig. 9.61](#Ch009_347-399_B9780443237904000013.xhtml#B-f0310) Step 4: Map an *n*-ary fact type to association classes or coreferenced classes.

Objectified associations map to association classes, as shown earlier in [Fig. 9.18](#Ch009_347-399_B9780443237904000013.xhtml#f0095). Some cases of coreference could be mapped into qualified associations, but mapping to separate attributes or associations supplemented by a textual composite uniqueness constraint offers a more general solution.

In **step 5**, the simplest constraints in ORM usually map in an obvious way to multiplicity constraints, as illustrated earlier. The more complex ORM constraints have no graphic counterpart in UML, so you need to record these separately in textual form.
