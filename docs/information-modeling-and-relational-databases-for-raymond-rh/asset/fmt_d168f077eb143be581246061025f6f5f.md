## Step 2: Map selected n:1 and 1:1 associations to attributes

In step 2, we decide which object types to model as entity types and which *n*:1 and 1:1 ORM associations to remodel as attributes. Typically, entity types that play functional fact roles are retained as entity types. In rare cases, value types that are independent or play explicit mandatory, functional fact roles map to entity types. Functional binary (*n*:1 and 1:1) associations from an entity type *A* to a value type B, or to an entity type *B* about which you never want to record details, usually map to an attribute of *A*. If you have specified role names, these can usually be used as attribute names, with the object type name becoming the attribute's domain name.

The mapping in [Fig. 8.46](#Ch008_309-346_B9780443237904000177.xhtml#f0235) illustrates several of these step 2 considerations as well as step 5 (map ORM constraints to ER graphic constraints, textual constraints, or notes).

## Step 4: Map remaining fact types to associations

In step 4, the remaining fact types are mapped to associations. Any *m:n* associations should remain that way, unless the target notation doesn't support them (e.g., IDEF1X). In that case, you can replace the association by an intersection entity type as discussed earlier.

In [Fig. 8.48](#Ch008_309-346_B9780443237904000177.xhtml#f0245), the *n*:1 fact type is retained as an association because it relates two entity types that will remain as such in the mapping. Even if the *m:n* association did not apply, we would normally retain Country as an entity type because now or later we are likely to record details for it (e.g., country name).

![Fig. 8.48 Step 4: Map remaining fact types to associations.](images/B9780443237904000177/f08-48-9780443237904.jpg)

[Fig. 8.48](#Ch008_309-346_B9780443237904000177.xhtml#B-f0245) Step 4: Map remaining fact types to associations.

If an *m:n* association involves a value type, and the ER dialect does not support multivalued attributes, map the value type to an entity type. [Fig. 8.49](#Ch008_309-346_B9780443237904000177.xhtml#f0250) provides an example. Otherwise, where possible, transform the *m:n* association into multiple *n*:1 associations (e.g., Employee has PhoneNr1; Employee has PhoneNr2, etc.). Conceptual schema transformations like this are discussed in depth in [Chapter 14](#Ch014_681-771_B9780443237904000189.xhtml).

## Step 6: Map subtyping

In step 6, subtypes are mapped to subtypes, adding relevant constraints if needed. Subtype definitions are handled with discriminators and/or textual constraints. If needed, introduce an "Other" subtype to complete a partition. If needed, use multiple diagrams (e.g., when multiple categorization schemes apply to the same supertype). [Fig. 8.50](#Ch008_309-346_B9780443237904000177.xhtml#f0255) shows a simple example. The braced value constraint and footnoted constraints are not part of the Barker ER notation.

## Step 7: Map derivation rules

In step 7, we map derived and semiderived fact types. Industrial ER typically has no graphical support for derivation, so the derivation rules are captured as textual notes. [Fig. 8.51](#Ch008_309-346_B9780443237904000177.xhtml#f0260) provides a simple example. With these few hints, and the examples discussed, you should have enough background to do the mapping manually. The mapping procedure is fairly boring and is best automated with a CASE tool.
