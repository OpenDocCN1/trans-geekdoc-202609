| What Can Go Wrong? | Threat Type | Mitigation |
|---|---|---|
| 10 Alteration of application code | Data validation/parameter validation | 1 Data type, format, length and range checks are enforced.<br>2 All data sent from the client are validated.<br>3 No security decision is based upon parameters (e.g., URL parameters) that can be manipulated.<br>4 Input filtering via whitelist validation is used.<br>5 Output encoding is used. |
| 11 Ability to disrupt the application | Error handling and exception management | 1 All exceptions are handled in a structured manner.<br>2 Privileges are restored to the appropriate level in case of errors and exceptions.<br>3 Error messages are scrubbed to ensure that no sensitive information is revealed to the attacker. |
| 12 Leakage of sensitive information | User and session management | 1 No sensitive information is stored in clear text in the cookie.<br>2 The content of the authentication cookies is encrypted.<br>3 Cookies are configured to expire.<br>4 Sessions are resistant to replay attacks.<br>5 Secure communication channels are used to protect authentication cookies.<br>6 The user is forced to re-authenticate when performing critical functions.<br>7 Sessions expire at logout. |
| 13 Malicious activity goes unnoticed | Auditing and logging | 1 Sensitive information (e.g., passwords, PII) is not logged.<br>2 Access controls (e.g., ACLs) are enforced on log files to prevent unauthorized access.<br>3 Integrity controls (e.g., signatures) are enforced on log files to provide non-repudiation.<br>4 Log files provide an audit trail for sensitive operations and logging of key events.<br>5 Auditing and logging are enabled across tiers on multiple servers. |
