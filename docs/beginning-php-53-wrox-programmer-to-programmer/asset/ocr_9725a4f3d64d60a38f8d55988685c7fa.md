# The Binary Attribute and Collations

All character data types have a collation that is used to determine how characters in the field are compared. By default, a character field's collation is case insensitive. This means that when you sort the column alphabetically (which you learn to shortly), “a” comes before “b” and “B”. It also means that queries for the text “banana” will match the field values “banana” and “Banana”.

However, by adding the BINARY attribute after the data type definition, you switch to a binary collation, which is case sensitive; when sorting, “a” comes before “b”, but “B” comes before “a” (generally speaking, uppercase comes before lowercase letters in a character set). This means that matches are case sensitive too; “banana” will only match “banana”, not “Banana”.

In this case, you create the username field of members with the BINARY attribute, making it case sensitive:

```
username VARCHAR(30) BINARY NOT NULL UNIQUE,
```

This ensures there is no ambiguity about the case of the letters in each user’s username; for example, “john” is a different username than “John”. This is important because many people choose usernames where the case of the username’s characters is significant to them. If they created their account with a username of “john”, and later found out they could also log using “John”, they might wonder if they were working with one account or two!
