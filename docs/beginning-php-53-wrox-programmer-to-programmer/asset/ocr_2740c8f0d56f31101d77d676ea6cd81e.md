To control the warp drive, the script creates a ChiefEngineer class. This class contains a single method, doWarp(), which accepts a factor. It creates a new WarpDrive object and attempts to set the correct speed.

In this situation, the ChiefEngineer is a bit of a "yes man". He takes his orders — the required warp factor — and passes it to a new WarpDrive object via its setWarpFactor() method. He does not do any checking of the requested speed, nor does he attempt to catch any exceptions that might be thrown by the WarpDrive object

```
class ChiefEngineer {
    public function doWarp($factor) {
        $wd = new WarpDrive;
        $wd->setWarpFactor($factor);
    }
```

The final class created is Captain. This class contains a single method, newWarpOrder(), which accepts a factor. The method then creates a new ChiefEngineer object and passes the orders to the object via its doWarp() method.

Unlike the ChiefEngineer class, the Captain's newWarpOrder() method checks for problems with the warp order with a try ... catch block. Because exceptions bubble up through the calling chain, any exceptions raised by a WarpDrive object will be caught here.
