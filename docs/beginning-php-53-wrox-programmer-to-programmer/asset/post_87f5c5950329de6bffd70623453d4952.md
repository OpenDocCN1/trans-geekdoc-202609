# Destroying a Session

As mentioned earlier, by default PHP sessions are automatically deleted when users quit their browser, because the PHPSESSID cookie's expires field is set to zero. However, sometimes you might want to destroy a session manually. For example, if a shopper has checked out and placed an order over your online store, you might have wiped shopping cart by destroying that session.

To destroy a session, you can simply call the built-in session_destroy() function:

```
session_destroy();
```

Note, however this merely erases the session data from the disk. The data is still in the $_SESSION array until the current execution of the script ends. To make sure that all session data has been erased, you should also initialize the $_SESSION array:

```php
$_SESSION = array();
session_destroy();
```

Even however, a trace of the session remains in the form of the PHPSESSID cookie in the user's browser. When the next visitor visits your site, PHP will pick up the PHPSESSID cookie and re-create the session (though the session won't contain any data when it's re-created). To make sure you have wiped the session from the server and the browser, you should also destroy the session code:

```php
if ( isset($_COOKIE[session_name()]) ) {
    setcookie(session_name(), "*", time()-3600, "*/");
}
```

This snippet makes use of another PHP function, session_name(). This function simply returns the name of the session (PHPSESSID by default).

PHP actually lets you work with more than one session in the same script by using session_name() to create different named sessions. This topic is outside the scope of this look, but you can find out more in the "Session Handling" of the PHP manual at http://www.php.net/session.

As you know, PHP session IDs are saved in cookies. However, if a user has disabled cookies in their browser? One obvious approach is to add some text to your page asking the user (nicely) to turn on cookies. Another alternative is to pass the session ID inside links between the pages of your site.

PHP helps automate this process with the built-in SID constant. If the browser supports cookies, this constant is empty; however, if the session cookie contains a string from the browser, SID contains a string to the following:

```
PHPSESSID=b8306b025a762a50f0428fc0efd20a11
```

This means that you can use the links in your pages to include the session ID, if available:

```php
<?php session_start() ?>
<a href="myscript.php?<?php echo SID;?>">Home page</a>
```

If the session ID was successfully stored in a cookie, the code will output the following:

```php
<a href="myscript.php?<?php echo SID;?>">Home page</a>
```

However, if PHP cannot create the session cookie, the code will output something along the lines of:

```php
<a href="myscript.php?PHPSESSID=5bf28913309ba166b3a3ea8b67ff1c7*">Home page</a>
```

When the user clicks the link to view myscript.php, the PHPSESSID query string value is automatically picked up by the PHP engine and the session data is made available to the script.

> Note that you have to call session_start() before trying to access the SID.

Convenient though this feature is, passing session IDs in URLs is best avoided if possible. It's easy for a visitor to enable a link — including her session ID — to a friend, thereby inadvertently giving the friend access to her session! You can mitigate against this somewhat with short session cookie lifetimes (the next section), but generally is best to use only cookies if possible.

You can also retrieve the current session ID by calling the session_id() function. This allows you, among other things, to embed the session ID in a hidden field in a form, so that the session can be propagated across form submissions.

As well as altering session behavior, you can write your own custom code to store the session data on the server. For example, instead of letting PHP store the data in temporary files, you might prefer to store it in a database.
