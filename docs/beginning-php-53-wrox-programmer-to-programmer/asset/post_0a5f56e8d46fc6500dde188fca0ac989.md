```php
function validateField($fieldName, $missingFields) {
    if (in_array($fieldName, $missingFields) ) {
        return ' class="error";
    }
}

function setValue($fieldName) {
    if (isset($_POST[$fieldName])) {
        return htmlspecialchars($_POST[$fieldName]);
    }
}

function setChecked($fieldName, $fieldValue) {
    if (isset($_POST[$fieldName]) && $_POST[$fieldName] == $fieldValue ) {
        return ' checked="checked";
    }
}

function setSelected($fieldName, $fieldValue) {
    if (isset($_POST[$fieldName]) && $_POST[$fieldName] == $fieldValue ) {
        return ' selected="selected";
    }
}
```

### How It Works
Functionally, this application is pretty much the same as registration.php from Chapter 9. The main difference is that the presentation code has been separated from the application code and stored in separate template files in the templates folder.

Take a look at the registration.php script. Unlike the Chapter 9 script, the displayForm() and displayThanks() functions no longer contain embedded HTML. Instead, use require() to include the relevant page templates from the templates folder:

```php
function displayForm($missingFields) {
  $results = array (
    "pageTitle" => "Membership Form",
    "scriptUrl" => "registration.php",
    "missingFields" => $missingFields,
    "firstNameAttr" => validateField('firstName', $missingFields),
    "firstNameValue" => setValue('firstName'),
    "lastNameAttr" => validateField('lastName', $missingFields),
    "lastNameValue" => setValue('lastName'),
    "gender" => validateField('gender', $missingFields),
    "genderChecked" => setChecked('gender', "M"),
    "genderFChecked" => setChecked('gender', "F"),
    "favoriteWidgetOptions" => array (
      "superWidget" => setSelected('favoriteWidget', 'superWidget'),
      "megaWidget" => setSelected('favoriteWidget', 'megaWidget'),
      "wonderWidget" => setSelected('favoriteWidget', 'wonderWidget')
    ),
    "newsletterChecked" => setChecked('newsletter', 'yes'),
    "commentsValue" => setValue('comments')
  );

require("templates/registration_form.php");
```

```php
function displayThanks() {
  $results = array (
    "pageTitle" => "Thank You"
  );

require("templates/thanks.php");
```

Each function creates a $results array containing information to display on the page. The page template then uses this array to display between the application and presentation code. For example, registration_form.php uses the firstNameAttr element to insert any attributes (such as 'class="error"') into the firstName label's tag, and the firstNameValue element to display any properly typed value in the firstName field:

```html
<label for="firstName"><?php echo $results["firstNameAttr"] ?? ""?></label>
First name *
<input type="text" name="firstName" id="firstName" value="<?php echo $results["firstNameValue"] ?? "" />
```

The form helper functions in registration.php, as such validateField() and setValue(), have been rewritten to return their output values, rather than displaying them using echo. This is so that the values can be seen by the $results array to the template pages.

The end result of these changes is that nearly all presentation markup has been removed from registration.php, which the template pages contain very little PHP — in fact there is just one choice of decision-making code (if the block not from registration_form.php), a few calls to require() to include the page header and footer files, and a series of echo statements to display the results. Generally you should try to limit your templates 'PHP' code to echo/print statements, and avoid complex logic if the code is directly related to displaying results. Anything more complex belongs in the application code.

This example could be improved further. For instance, ideally registration.php would not contain the form helper functions validateField(), setValue(), setChecked(), and setSelected(), because these are specific to the output medium (HTML). A better approach would be to separate the presentation code from the application logic, so that the application logic has no knowledge of the output medium (whether it's HTML, XML, plain text, PDF, and so on).

A good example of such technique is the Model-View-Controller design pattern. This is out of the scope of this book, but you can find an overview at http://en.wikipedia.org/wiki/Model-view-controller. A great book on design patterns is Patterns of Enterprise Application Architecture by Martin Fowler (Addison-Wesley).
