
## 10.16 DATA INTEGRITY

Data is the 'blood' of any computing system including IoT systems. And if a network of 'things' involves many sensors, there may be a lot of data.

The ability to trust data involves many factors: (1) accuracy, (2) fidelity, (3) availability, (4) confidence that the data cannot be corrupted or tampered with, etc. Whether any of these is more important than the others depends on the system's requirements; however, with respect to a network of 'things', the timeliness with which the data is transferred is of particular importance. Stale, latent, and tardy data is a trust concern, and while it is not a direct problem with the "goodness" of the data itself, it is a performance concern for the mechanisms within the network of 'things' that transfer. In short, late, and tardy data in certain situations will be no worse than data at all.

Cloud computing epitizes the importance of trusting data. Where resides is important. Where is the cloud? And can the data be leaked from location? A tendency to "your data" on "your machine". But in some cases, the data is not just "yours". Least data can originate from anywhere and from vendors at the time of their choosing and with the integrity of their choosing. Competitors can lease the same data (Miller, Voas & Lapante, 2010; NIST, 2016).

The production, communication, transformation, and output of large amounts in networks of 'things' create various concerns related to trust. A few of these include:

- Missing or Incomplete Data: How does one identify and address missing or incomplete data? Here, missing or incomplete data could originate from a variety of cases, but in IoT, probably refers to sensor data that is not released or transferred to databases of information that are inaccessible (e.g., clouds). Each network of 'things' will need some level of resilience to be built-in to allow a potentially crippled network of 'things' to still perform even when data is missing or incomplete.
- Data Quality: How does one address data quality? To begin, a definition is needed for what data quality means for a particular system. Is it fidelity of the information, accuracy of the information, etc.? Each network of 'things' will need some description for what an acceptable level of data quality.
- Faulty Interfaces and Communication Protocols: How does one identify and address faulty interfaces and communication protocols? Here, data is the 'blood' of a network of 'things', the interfaces and communication protocols are the veins and arteries of that system. Defective mechanisms that perform transfer within a system if 'things' are equally as damaging to the overall trust in the data as is poor quality, missing data, and incomplete data. Each network of 'things' will need some level of resilience to be built in to ensure that the data moves from point A to point B in a timely manner. This solution might include fault-tolerance techniques such as redundancy of the interfaces and the protocols.

- 4. Data Tampering: How does one address data tampering or even know it occurred? Rarely can tamperproof exist if someone has malicious intent and the appropriate resources to fulfill that intent. Each network of 'things' will need some type of reliance for tampering, such as a back-up collection of the original data and in a different geographic location.

This requires that the specifications of a network of 'things' have some risk assessment that assigns weights to the value of data if it were compromised. Each network of 'things' will need a data security and privacy plan.
- 6. Data Leakage: Data can leak, and if so, would you know that it had it? Assume worst-case scenario where all networks of 'things' leak not directly impact the data, it may well impact the business model of the organization that relies on the system of 'things'. If this is problematic, an analysis of where leakage could originate be performed; however, this is technically difficult and costly.

## 10.18 SPEED AND PERFORMANCE

The speed at which computations and data generation can occur in a network of 'things' is increasing. Increased computational speed inhibits a system's ability to log and audit transactions as the rate of data generation exceeds the speed of storage. This, in turn, makes real-time analysis and recovery from faults and failures more difficult as data is lost and computational deadlines harder to meet. Consequently, there are fewer ways to “put on the brakes”, undo incorrect computations, fix internal and external data anomalies. Furthermore, computing to a wrong outcome offers little trust.

A related problem is of measuring the speed of any network of 'things'. Speed-oriented metrics are needed for optimization, comparison between networks of 'things', and identification of slowdowns that could be due to anomalies – all of which affect trust.

But there are no simple speed metrics for IoT systems and no dashboards, rules for interoperability and composability, rules of trust, and established approaches to testing (Voas, Kuhn & Lapantie, 2018a).

Possible metrics to measure speed in an IoT system include:

- 1. Time to decision once all requisite data is presented; this is an end-to-end measure.
- 2. Throughput speed of the outlying network,
- 3. Weighted average of a cluster of sensors’s “time to release data”,
- 4. Some linear combination of the above or other application domain specific metrics.
