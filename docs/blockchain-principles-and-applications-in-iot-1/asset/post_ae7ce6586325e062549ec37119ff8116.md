P35 introduces CapChain built for the Monero blockchain making of Monero's Ring Confidential Transactions to preserve privacy. The method makes use of the token approach to allow users to not just grant access rights but also delegate rights to other users. The implementation models Cap-BAC by treating access rights as capabilities on the blockchain that can be transferred to users just like cryptocurrency. To preserve identities, instead of using public addresses, transactions on the blockchain use a hash chain as these permissions are delegated from user to user. The use of sub-addresses allow for easy revocation of all rights from a user with other users that have derived their rights from this user. The implementation does suffer from drawbacks.

The limitation of this approach is that it doesn't provide the ability to revoke access as easily as revocation requires a transaction on the chain. As the access policies are stored in the form of contracts on the blockchain blockchain, these are publicly visible which can form a threat [52].

The authors of [64] continue their work on FairAccess using the second generation of blockchain to implement the architecture. This new generation of blockchain, called the account model, allows fine-grained access control through the use of advertised scripting for smart contracts [56].

To tackle the issue of distance between IoT devices and the cloud storage which has an increase in latency, authors of [48] used a blockchain layer to provide an access control and data management framework over time-series IoT data stored at the edge of the network using a locality-aware decentralized storage system. Even cloud nodes can be used as storage nodes for this purpose. To secure the storage on devices, the IoT data streams are chained, compressed, and encrypted at the application layer. Transactions are made on the blockchain to facilitate sharing of data with a service.

They include the dataset and the public key of the service. Access requests are checked on the blockchain for a corresponding transaction by the owner and only then the key is shared with the requester. This method suffers from the drawback of slow transaction speeds.

IoT devices constantly change managers or may be under the control of more than one manager at a time. However, manager devices are also lower power devices that cannot easily execute the access control. Handling hard coding of managing access control, security, scalability, transparency, and currency will not be easy to execute on these devices. [57,58] by Oscar Novo proposes an architecture using a single smart contract on the blockchain is used to define all access controls. The IoT devices are however not included as part of the blockchain. A new entity defined as the management hub translates information between the blockchain and the devices. Managers are however considered lightweight nodes in the blockchain that are responsible for managing the access control of the IoT devices under them by accessing the smart contract. A single contract automatically handles the issues of managing multiple devices and currency.

However, this architecture does not support the ability to audit the access control permissions. To obtain access, the management hub simply query the access control policy in the blockchain and translate the request back to the devices. Transactions aren't supported as in current blockchain implementations; it takes a couple of seconds to minutes for the operation. Additionally, modification of access control policy requires a transaction against the smart contract which might take some significant amount of time to reflect in the blockchain. This inherent limitation of the blockchain also poses as a threat to the strength of the access control model.

# Access Control and Data Security

Another model proposed in [59] involves the usage of multiple blockchain structures for the following purposes:

- Storage of public credentials and relationships between entities (Relationships)
- Contextual data obtained from sensors (Contextual)
- History of permissions and denies for auditing (Accountability)
- Access control policies defined by the owners (Rules)

The novelty introduced in this paper involves defining relationships between devices or any other entities. Attributes and characteristics could be assigned to a pair of devices and could be used in the access control policy. The paper also suggests storing information judged to be important in limited power devices, such as only rules associated with the device. Another option would be find another device with sufficient power and define a relationship in the blockchain.

To overcome the limitations of processing in the IoT devices, [60-62] opts for a blockchain-based architecture where the blockchain is stored on the IoT gateway nodes rather than the IoT devices. By including the blockchain on the gateway nodes, the problem of heterogeneity of the devices is also taken care of.
[60] defines a model using multiple smart contracts:

- Access control contracts which contain the policy for subject-resource pair
- Judge contract to facilitate dynamic access validation by checking misbehaviour reports and assigning penalties if required
- Register contract that is used to define the two types of contracts

Here, IoT gateways act as agents for their local IoT devices and enforce the access control models for them. The paper introduces the ability to perform dynamic validation that can protect from attacks such as denial of service which can arise from requests to access an unauthorized resource. However one limitation that the paper doesn't solve is that the interactions between the gateway and the IoT devices are assumed to secure. IoT devices can be accessed with a single gateway or sometimes be dynamic and link to any gateway; thus, a mechanism has to be developed to secure these interactions. Additionally, gateways are assumed to be trusted devices managing access control for their local IoT devices.

[63] describes yet another model using blockchain and smart contracts for enforcing access control. However, the policies in this model are stored on the owner's local database while a URL is provided on the blockchain to access this. Any user requesting the resource must load this policy and to a defined smart contract along with his public key for authorization. An advantage of this system is that it is easy for a user to update the policy easily as it is available with them. The model also enables dynamic policy creation whose addresses are stored on a private blockchain and are specific only to users. However, the access policies defined on public are visible to all which is one limitation of this model.

[47]58 uses the blockchain to store only capability tokens in the form of delegation. The proposed method is developed to grant or deny access. Mechanism in the distributed manner. User identification and authentication are performed on the cloud. Service providers upon receiving service requests check the blockchain for these delegations. However, the problem with this method of revocation is that rights cannot be revoked immediately but require the transaction to be completed on the blockchain.

# 14.7 Future Directions for Research

Based on the study of the works on blockchain-based access control systems, we have attempted to provide an insight into what must be the grounds of future work. This domain is fairly new and we hope that these insights form a foundation for future work to be structured around.

- **Auditing:** Blockchain technology has made popular due to the collection of immutable records. Hence, auditing is a facility that is by default a feature of the blockchain. However, some implementations still do not provide this feature. Auditing of access control helps in understanding and improving the security system in place. Hence, an immutable ledger like blockchain must be deployed for its use in auditing.
- **Blockchain as an Overlay:** Storage in blockchain is not as easy as the size of data stored in blockchains must be kept in control. However, size of data needs to be monitored grows in size daily. Off-chain storage methods are better opted for compared to on-chain storage methods. Using the blockchain as an overlay over the existing storage method is the approach to go for in the future.
- **Transaction Speed:** A number of transaction based approaches imitating the CapBAC model have been described, especially in the domains of IoT and cloud. However, these suffer from the slower transaction speed in current generation transaction speeds, these models can lay the foundation of better consensus models and faster access control systems. However, currently transaction speeds may still be made better with the use of permissioned blockchain or fewer consensus nodes.
- **Easy setup and Interoperability:** Any system proposed to be integrated with existing systems in little or no setup costs. Additionally, these systems have to be designed that they can operate on any existing system. This requirement is necessary for consumers to be comfortable with the usage of a newer security system while the existing one is still performing as needs. This concern also requires attention in the field of IoT containing high amounts of heterogeneity.
