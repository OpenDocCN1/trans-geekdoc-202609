# 9.3.1.4 Committing Peer

The committing peer commits the block received from the order into its ledger after validating the transactions in the block. Once the comm validates all transactions in the received block, it is added to the committing peer's ledger and the world state is also updated with the Write Set received in the transactions. The committing peer can also be an endorser i.e it can have smart contracts as well.

# 9.3.1.5 Ordering Peer

The main function of the ordering peer is to receive the endorsed transactions and to order them into a block. These ordered blocks are delivered to the committing peers by the ordering peer. The main function of the ordering service is to provide a totally ordered set of transactions to the nodes. The ordering service itself is decentralized and may consist of many nodes. These nodes do not have smart contracts and ledgers.

# 9.3.2 Chaincodes

Chaincodes are basically smart contracts in a hyperledger. They execute when certain conditions are written in them. The chaincodes are written in various languages like Go, node.js, or Java. The chaincodes are deployed on the endorsing peers and once deployed they can be invoked using the transactions only and using the transactions ledger state is updated.

# 9.3.3 Transaction Flow

Consensus is achieved using the following transaction flow: Endorse transaction then order transaction then validate. The client application is going to submit this transaction to a few peer nodes and these peers are going to execute this transaction and get the output and add their signature to the output. After that, these signed outputs will be sent back to the client application. The client application receiving these endorsements will check if all the outputs are the same and will confirm that this is a valid transaction. This is the endorsement step, then it is submitted for ordering. Once the transaction is found to be valid after the ordering service will ensure that the transactions are totally ordered across all nodes. After, there is a validation step that ensures that two transactions that are trying to modify the same state should not be executed simultaneously. The transaction that will be executed out of these will depend on the ordering service.
