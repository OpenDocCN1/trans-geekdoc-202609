## Algorithm Complexity

DOI: 10.1201/9781032687759-13

## Abstract

An understanding of an algorithm's complexity is an important planning consideration, especially before processing huge data sets, as the run-time required to test algorithms may be costly. Before code is compiled and run, algorithmic efficiency can be estimated by relatively simple means.

Algorithm complexity analysis is rooted in the counting of operations and concerns how well an algorithm scales with data. It is distinct from algorithm performance, which in addition to the complexity of the algorithm, depends on the unique aspects of a computer, such as its CPU, memory, disk read/write speed, bus bandwidth, and the latency of data distribution over networks.

In addition to ignoring the parameters unique to specific computing environments, complexity analysis ignores the effects of constants that are hard-coded in algorithms, focusing instead on how well an algorithm generally processes a series of input data. The limits of such performance is a matter of *asymptotic analysis*.

## 13.1 ALGORITHM ANALYSIS

Different algorithms that solve the same problem may have much different complexities, and they may incur significantly different processing times for intensive tasks. The difference may be most noticeable when processing large data sets.

For example, consider the following algorithms that compute an average for a list called *nums*. For each algorithm, we consider time complexity in *t* units of time along with an input size of *n* and a translation to Big-O notation, which will be explained in more detail shortly.

```forth
( Some utility functions and variables.)
{ 1 3 5 7 9 } nums LIST
nums ' LEN n !
0 m !
{ m @ i+ m ! } m+ WORD
```

```forth
( 5 operations. Big-O is O(1))
{ 1 3 5 7 9 + + + + 5 / } avg1 WORD
```

```forth
( 2 x n + 1 operations. Big-O is O(n))
{ + GSC 1 > sum ? } sum WORD
{ nums sum n @ / } avgn WORD
```

```forth
( 5 x n + 2 operations. Big-O is O(n))
{ T > R > ++ GRC 0 > sum2 ? } sum2 WORD
{ nums DS2RS nums DS2TS sum2 n @ 2 * / } avg5n WORD
```

```forth
( 3 x n x n + 2 operations. Big-O is O(n^2))
{ n @ SQUARE / } div WORD
{ nums { + } n @ LREPEAT } repeatadd WORD
{ repeatadd m+ m @ n @ < avgnn div ?? } avgnn WORD
```

The first algorithm, avg1, has a single statement of six operations, a problem size that is independent of input size. This is a constant time complexity, which in Big-O notation is O(1).

The algorithm avgn, has 2n + 1 operations: n recursive function calls, each with one addition and one comparison operation, and then finally a single division operation. The expression 2n + 1 can be given as (2n)t units of time complexity, which translates into a Big-O of O(n).

The algorithm avg5n, has 5n + 2 operations: n recursive function calls, each with five operations, and finally a single multiplication operation and a single division operation. This may be expressed as (5n)t units of time complexity or a big-O of O(n).

The algorithm *avgnn*, has 3 × n × n + 2 operations, making its expected performance the worst overall. It expands its input by an order of magnitude for redundant operations. This algorithm requires (n²)t units of time complexity and has a big-O of O(n²).

## 13.2 BIG-O NOTATION

The *O* in Big-O notation stands for *order of magnitude*. For expediency, we describe *time-complexity* in terms of Big-O, a mathematical shorthand that accounts for an algorithm's magnitude of expansion as its input increases.

There are external factors besides the algorithm itself that affect its computational speed. We ignore those in algorithm analysis, as we are concerned with a common criteria for objectively comparing algorithms (the algorithms themselves).

Non-algorithm factors affecting algorithmic performance include:

- Memory size and memory access speed.
- CPU clock rate and CPU cache behavior.
- Other programs competing for CPU time and memory.
- Code length, sometimes inversely proportional to computational efficiency.
- Distribution of the algorithm on multi-CPU systems.
- Compiler/interpreter garbage collection, interim compilations, thread scheduling, etc.
- Compiler versus operating-system optimizations.

The data scientist usually has little immediate control over non-algorithm factors such as hardware. Therefore, it is often more expedient to craft a better algorithm in consideration of a minimal problem size than to swap out hardware.

The problem size is the total number of operations performed by an algorithm.

*problem size = number of statements × number of elements*

To make an objective comparison of algorithms, we ignore all the above performance factors, except the problem size. This is because the hardware and operating systems vary from machine to machine.

As mentioned earlier, a (2n)t algorithm, with t units of time and an input size of n, is considered to have a Big-O of O(n). As n increases, 2n increases by the same magnitude, with the problem size of both $n$ and $2n$ exhibiting a linear or tandem relationship. However, the time complexity of a $(n \times n)t$ operation is expressed as $O(n^2)$, reflecting a 2nd degree order of magnitude in the growth of the problem size as $n$ increases.

We are interested in the general number of operations that an algorithm requires as its input data increases. For that purpose, we determine a growth rate function $g(n)$ representing the growth of the algorithm's _problem size_ (operation count \(\times\) input size $n$). Such a function should approximate the growth of an algorithm's time requirement as the input size, $n$, increases.

Suppose $f$ is a function representing the time complexity of an algorithm. While a formal definition of Big-O is provided in the next section, the steps for establishing an algorithm's Big-O boil down to isolating the main growth term if $f$. This can be done by discarding:

- Terms that diminish toward 0 as n increases.
- Constants.
- All terms besides the leading term in a polynomial function.

After making those simplifications, the main growth term will remain, reflecting an algorithm's general tendency as a problem size expands.
