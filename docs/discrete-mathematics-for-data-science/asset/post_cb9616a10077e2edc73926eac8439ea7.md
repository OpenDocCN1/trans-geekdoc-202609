
i/2, i/4, i/8, i/16, ... until i/2<sup>n</sup> or i <= 1

That is: O(log<sub>2</sub> n) or O(log n).

O(n log n): Log linear. An algorithm with O(n log n) performs better than O(n<sup>2</sup>) and worse than O(n). A notable example of this type of algorithm is a sorting routine called the merge sort, which we won't go into here.

O(n): Linear or first degree polynomial. All n elements of a data structure must be potentially traversed to arrive at a solution. On average, one-half of the elements must be traversed.

The following example of a linear case uses a C like pseudo code, with a counter variable i incrementing as i = i + 1, from 0 to n, and an “operation” being repeated n times.

```
for (i = 0; i < n; i = i + 1) operation
```

The equivalent epop code:

```
operation n LREPEAT
```

O(c^n): Exponential, where c is a constant. This type of algorithm includes c branches or recursive calls in each cycle.

O(n^2): Quadratic. This is slow relative to O(n) algorithms, as there are generally n x n operations. That is, for each of n elements, apply an operation to n elements. This is characteristic of operations inside of nested loops.

For example:

```
for (i = 0; i < n; i++)
for (j = 0; j < n; j++)
operation
```

The inner most operation here is executed n^2 times, n times in the outer loop and n times in the inner loop. Therefore, this quadratic case has O(n^2) efficiency.

The equivalent epop code:

```
{ { operation } n LREPEAT } n LREPEAT
```

The following variation of the quadratic case puts the upper bound of the inner loop as the counter of the outer loop.

```
for (i = 0; i < n; i++)
for (j = 0; j < i; j++) operation
```

There are n(n - 1)/2 or (n^2 - n)/2 operations, with an upper bound of n^2 for efficiency of O(n^2). Note that O(n^2) is a quadratic or second degree polynomial.

O(n^3): Cubic or third degree polynomial. Consider the loop nesting of an O(n^2) algorithm with poor performance compounded by an extra nested loop. Accordingly, the performance is much worse.

O(n!): Factorial. Consider applying an operation to all possible permutations of n elements. Examples of this include _brute-force_ searches of all possible permutations. Such algorithms are extremely slow.

In summary, in evaluating the efficiency of an algorithm, we are interested in the worst case scenario, the upper bound of the problem size that may be met by the algorithm.

For algorithms whose problem size is represented by a polynomial function, the upper bound can be identified by observing the greatest exponent on the variable. For example, in the quadratic expression _n_<sup>2</sup> + 4_n_ + 2, 2 is the greatest exponent. Such _O_(_n_<sup>2</sup>) quadratic efficiency is shown in the following example code.

```
for (i = 0; i < n; i++)
for (j = 0; j < n; j++)
operation ... _n_<sup>2</sup> operations

for (i = 0; i < n; i++) {
operation
operation
operation
operation
} ... 4_n_ operations

operation ... 1 operation
operation ... 1 operation
```

The above code amounts to _n_<sup>2</sup> + 4_n_ + 2 operations, or _O_(_n_<sup>2</sup>) in terms of Big-O efficiency.

## 13.3 TIMING COMPUTATION

To corroborate algorithm complexity analysis, software profiling and timing analysis may also be performed.

Formally, algorithm complexity analysis is limited to abstract functions that we can control and, hence, analysis may ignore code that is responsible for significantly complex underlying computations.

Algorithm performance is relative to the problem at hand. If real-time processing for game graphics is of interest, latency in microseconds or milliseconds may be a concern. If processing terabytes of data for statistical analysis is the objective, then processing run-times of minutes and much longer may be acceptable.

To corroborate function efficiency, we can record the run-time of different versions of the same function. Example *epop* code in Appendix C.13 does just that. The benchtest program there shows a recursive Fibonacci sequence algorithm that is generally 20 nanoseconds slower than an iterative version.

## Abstract

Data organization entails ways in which collections organize their elements. Collections are generally categorized as connected, unconnected, or branched.

As an analogy, consider the stars in the night sky, a myriad twinkling points of light. With a quick glance it may seem that these are random entities without any connections. But, with careful observation certain patterns can be seen. These patterns are defined as stellar constellations with names such as the Big Dipper and Orion's Belt. These galactic structures are actually abstract constructs that were defined into existence by ancient astronomers.

Similarly, data structures exist as the organization of individual data objects that are ascribed based on their topological relationships and groupings.

## 14.1 DATA ORGANIZATION

This section provides a brief overview of the data structures in this book, each of which are given in-depth coverage in the following three chapters.

An unconnected collection implies that elements are free of order such that elements appear to be placed at random. These collection types are sets and bags. A bag collection has the least restrictions of all the collection definitions, as it may contain duplicates and is not ordered.

A connected collection implies that each element has a predecessor and a successor, with the exception of the first and last elements. Connection is synonymous with linking, as in linked-lists. The linear variety of such collection types includes lists, stacks, and queues.

Of the connected types, some are branched, which means that an element may have multiple predecessors and successors, depending on a predefined topology. These collection types include graphs and trees.

## 14.2 ORDERING

Connected collections have an order. In turn, order indicates that the elements of a collection are connected.

While the sequence of the order may be assigned by an index, lexical or numeric ordering is not necessary. Where a particular ordering of a sequence is necessary, the use of pre-sorted collections may be used. These include sorted lists, priority queues, and search trees.
