
However, if the solution is known, should the probabilistic state be 1? “Is a problem solvable merely because we have the solution?” This poses the infamous and seemingly paradoxical question of computability:

## $P = NP?$

It is sometimes practical to seek a probabilistic solution using a less complex model, incrementally reducing the number of variables (data dimensions), sample rates, and records, or by settling for less prediction accuracy. The implementation of relaxed models as such translate into shorter processing time.

Problems can be shown to be NP-complete (solvable) using *transitive polynomial time reduction*, breaking problems down into smaller solvable sub-problems. Given problem $A$ consisting of $a_1$, ..., $a_n$ sub problems, $A = P$ if for all $a$, including the worst case $a$. Thus, the solution entails a transitive relation between sub problem $a_1$ and sub problem $a_n$.

A metaphor for transitive polynomial time reduction is “the weakest link in the chain,” referring to the idea that the efficacy of a solution depends on its weakest component, which in this case would be the worst performing sub algorithm of a solution.

## Selected problem classifications:

One application of data resampling to probabilistic state machines is the well known method of analysis in finance and economics called Markov Chains.

- Decision: A problem with a yes or no answer.
- P: Solved in Polynomial time, such as for algorithmic complexity analysis.
- NP: Solved in Non-deterministic Polynomial time.
- NP-Complete: The set of all sub-problems in NP which reduce ultimately to NP.
- NP-Hard: Both a problem and its sub-problems are NP-complete.
- Undecidable: Not always solvable (The model may suffer from too many variables).

A related topic is abductive inference, which seeks the plausibility or likelihood of a conclusion from a non-deterministic or exploratory system. Abductive inference is a subtopic of Exploratory Data Analysis, a more advanced topic of data science.

## 9.2 PROGRAMMING LANGUAGE ELEMENTS

A metalanguage is a language that is used to define other languages. Metalanguages are commonly used in the lexing stage of compilation. Lexing is the breaking of input into separate words called tokens. A lexer may be referred to as a metaprogram.

Formalities aside, the programming language that we wish to compose may be referred to as a *guest, target, or object language*. The language used to generate (compile) a guest language may be referred to as the host or meta language. The symbols of the host may be referred to as *terminals* or *primitives*. The symbols of the guest language may be referred to as *non-terminals* or *abstractions*.

Incidentally, by composing a function of functions we effectively get what is referred to as a *higher order function*. In other words, an abstract word or function is a *higher order word*. Conversely, a primitive word or function may be called *lower order word*.

5These concepts are covered in more depth in the *Functions & Abstractions* chapter.

A metalanguage and a *host language* may be one and the same. That is, if host language A is used to compile *guest* language B, then A may be referred to as a metalanguage. For example, the Python programming language is written in the C programming language. Python is the guest language and C is the host language.

Metalanguages employ grammars that are either *context-sensitive* (*context-aware*) or *context-free* (CFGs). A *grammar* is a rule for a language's word and symbol sequences, such as starting at the left and processing toward the right. The lexing stage of a compiler that is oriented only to generating tokens is context free. Later compiler stages that entail parsing certain token sequences are, thus, context sensitive. A parser enforces token sequences in accordance with the grammar of a given programming language. Without imposing an expected order, context free grammars would otherwise be ambiguous.

The output of the parser will be a series of primitive (terminal) words. These terminal words may be indexed to correspond to a parse tree, also called a concrete parse tree. If the parse tree maps abstract words to primitive words, then this parse tree may also be called an abstract syntax tree. What follows in Figure 9.1 is an illustration of a simple parse tree for an abstract function i+, which adds 1 to an operand i. The illustration shows the hierarchical relationship between i+ and its primitive dependencies.

The manner in which non-terminals are decomposed into terminals requires a repeated inspection of nested non-terminals. A popular algorithm for such a task is called *recursive descent parsing*. The traversal of a recursive descent algorithm corresponds with a parse tree.

Lexical analysis entails breaking input into units of usable data and rejecting unusable input. The outputs of the lexing stage are referred to as tokens. Depending on a language's keywords, tokens that match keywords will be treated differently than unrecognized tokens. For example, during program execution tokens that are recognized may be directed to a program stack, whereas unrecognized tokens may be treated as literal data, or arguments, and directed to a data stack.

The symbols of the metalanguage are referred to as *terminals*. These may include characters, keywords, operators, etc. The words of the guest language are called *non-terminals* and are abstractions of terminal symbols. Terminals are considered atomic, as they are not reducible to other instructions. As such, terminals may be referred to as *atoms*, in accordance with concepts discussed in the *Atoms & Abstractions* chapter.

For a message to have meaning, as between a sender and a receiver, or between a coder and a machine, there must be shared rules of grammar.

Symbolically, a rule for a context-free grammar might be:

```
X → x
```

where *X* is a non-terminal symbol and *x* is a terminal symbol. This means that when *X* is encountered it gets replaced with *x*, regardless of the context surrounding *X*.

A rule for a context-sensitive grammar might be:

```
XY → xY
```

In this case, X is replaced by x if and only if X is followed by Y.

However, context-free expressions allow for ambiguity. For example, while the following expressions, denoted E, are acceptable as context-free tokens, they require a contextual interpretation of certain *production rules* for a working program, such as recognizing the tokens +, −, × and *number* as terminals.

```
E → E + E
E → E − E
E → E × E
E → number
```

Depending on the complexity of the terms and the rules of abstraction, a practical programming language will normally be context-sensitive, with only the lexing stage being context-free.

As already mentioned, grammars define operation sequences that are acceptable to a language. Consider the following postfix series:

1 2+

The + symbol is an alias for the addition operation, likely defined as ADD in the host language. Further, the word ADD may itself be an alias for a binary opcode (operational code), such as 1001000100, as it is for a version of the ARM CPU's Assembly language. ADD is much easier to remember than 1001000100, hence ADD is referred to as a mnemonic.

Mathematics is often done using binary operators (not to be confused with binary numbers), meaning that they take two arguments. Thus, a program's compiler will have grammars that enforce binary operations for a certain set of mathematical symbols. The enforcement of syntax rules must be a context-aware process (i.e., not context-free).

When ADD is executed, the program will look for two numeric values to add together. In general, the whereabouts of the operands will be in memory, to be transferred into registers in the CPU in order to invoke addition upon them. The result may be kept in a CPU register for further operations, or it may be transferred to memory. At a higher level of abstraction, such storage may be within abstract data structures such as stacks, arrays, or linked-lists, depending on the architecture of the language.

Given that the composition of the addition function reduces, ultimately, to ADD, then ADD is considered a terminal symbol. Conversely, we may have an abstract function for addition that is not terminal. Consider the following function called addone.

```
{ 1 + } addone WORD
```

The word addone is an abstract non-terminal word, as it consists of at least one other word.
