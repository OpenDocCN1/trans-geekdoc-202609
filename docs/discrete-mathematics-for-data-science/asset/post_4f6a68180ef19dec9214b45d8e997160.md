Free variables are defined outside of a function's scope, the boundaries of a function's definition. Conversely, bound variables are those which exist inside of a function's scope. Pure lambda expressions have no free variables.

In the application (y λx.x), y is a free variable and x is a bound variable. In the function: λx.(s x), s is also a free variable and x is a bound variable.

A function application may be comprised of sequences of function abstractions, much like a chain of commands. Thus, we can express an application by combining two function abstractions like this:

```
(λx.x λy.y)
```

This application has the first function abstraction as the function and the latter one as the parameter. This is similar to a nesting, or composition, of functions such as f(g(x)), where the result of the latter becomes the parameter of the first.

An expression must reduce, or simplify, to a single value or function expression. Accordingly, the sub expressions must be reduced first, as these become parameters for the outer function. Otherwise we end up with a so-called *stuck expression*, an expression that is not a value and cannot be reduced. Think of it as an abstract function that has no concrete implementation.

Consider the identity function λx.x, which simply returns the argument specified. In the form of an application, such as (λx.x λx.x), the argument expression λx.x is applied to the function expression λx.x. When the application is evaluated, the bound variable x for the function expression λx.x is replaced by the latter argument expression λx.x in the body expression x giving λx.x.

A variation on the identity function is as follows, where the function λx.x both sets and gets the variable x.

```
{ x ! x @ } λx.x WORD
{ λx.x λx.x } (λx.x_ λx.x) WORD
```

The following application of the above function takes 5 as an argument and yields 5 as a result:

```
5 (λx.x_ λx.x) ( → 5)
```

A function with *self-application* contains an application. For example, the body of the function λs.(s s) contains the function application (s s), consisting of the function expression s and the argument s. A self-application function may also be part of an application, such as (λx.x λs.(s s)). In this application, the function expression is λx.x and the argument expression is λs.(s s). To evaluate this application the bound variable in the function expression body x is replaced by the argument expression giving λs.(s s).

## 12.3 APPLICABLE ORDER

In *normal order*, left-to-right, the value of a parameter is not evaluated until it is passed. The problem with this is that a concrete parameter may not exist until a function on the right is first evaluated. So, sometimes we need to first evaluate the right side. The term for this is *applicative order*.

Applicative order applies a normal order to the inner-most expression as it is needed. This is a strategy of *lazy evaluation* in which function execution is done only when needed and not earlier (aka, *call-by-need*).

With lazy evaluation there is no ongoing interim computation or need to *memoize* (cache) intermittent (iterative) results. As typical of recursive functions, laziness allows the operations of a recursive expression to accumulate as a series in memory, before being processed. While desirable for the benefits of immutable variables that are limited to a one-time assignment, this comes at a cost of higher memory usage.

As you may recall, a strategy of evaluation that executes all the functions of an expression without delay is referred to as eager evaluation. Problems arise with the eager evaluation of abstract functions when function components have, themselves, not yet been completely evaluated. It should be stated that the actual evaluation sequence in practice depends on the programming language being used.

Consider the update of a value in this list x.

```
{ 5 } x LIST
{ x ’ S2LIST } updatex WORD
{ x i+ updatex } increment1 WORD
{ x, i+ updatex } increment2 WORD ( make list x lazy)
increment1 ( x → 6)
increment1 ( x → 6)
increment2 ( x → 7)
increment2 ( x → 8)
```

The first increment function does not enforce laziness as it merely uses the value of the list x in the definition of increment1. As a result, each time the increment function is invoked, the original list values are used. Conversely, the second increment function enforces laziness by instead storing the name of the list, x, in the definition of increment2. This allows increment2 to update the original list values each time increment2 is invoked. This matter of names versus values relates to concepts in computer science known as call-by-value and call-by-name.

## 12.4 REDUCTION & CONVERSION

To deal with problems of naming conflicts and sequence precedence, we can use techniques of name conversion and expression reduction, called alpha α conversion and beta β reduction, respectively.

When a lambda expression cannot be further reduced, as it is completely evaluated, it is said to be in normal form. When a lambda expression in which the outermost application (the head) cannot be reduced, it is said to be in head normal form.

Alpha α conversion is the renaming of a bound variable to prevent name clashes. This conversion is normally done before beta reduction.

For alpha conversion, consider the general function:

```
λ < name1 > . < body >
λx. E
```

The name x and all free occurrences of x in the expression E may be replaced by a new name, provided the new name is not the name of a free variable in λx.E.

Given λx.E, suppose that we want to replace all occurrences of x with y. Such substitution is denoted [x/y].

This can be stated as λx.E → λy.E[x/y].

Following alpha conversion, beta β reduction evaluates the respective parameters within a named function, replacing these sub-expressions with the resultant values.

Beta reduction of an application has the form (λx.E x) and is done by replacing all free occurrences of name x in body E with the argument x. For example, in the following application the function F replaces all occurrences of x in E.

```
(λx.E F) → E[x/F]
```

Similarly, the variable x would be replaced by the argument 5 as follows:

```
(λx.fx) 5 → f(5)
```

In lambda calculus, a function cannot take more than one argument. Therefore, to use multiple variables, a process called currying must be used to convert the function that takes multiple arguments into series of single argument functions.6

Consider a multiple argument operation such as the addition of many numbers. For lambda calculus, the arguments are curried, one at a time, before the addition function is evaluated. In epop, the operations might be likened to the following mutually recursive functions:

```
{ + GSC 10 < curry ? } add WORD
{ GSC 1 > add ? } curry WORD
```

That is, instead of applying the function f to arguments x and y at the same time, which would be written as:

```
( x y f )
