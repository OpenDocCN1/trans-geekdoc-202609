

# 适应底层提供的各种帧大小

为了创建一个所有上层协议都可以在其上运行的单一协议，`IP` 必须“适配”多种不同物理层协议的帧类型。

一系列草案描述了如何在特定物理层之上运行 `IP`，包括 `MPEG-2` 网络、^([8](#ch05.xhtml#ch05fn-8)) `Asynchronous Transfer Mode`、^([9](#ch05.xhtml#ch05fn-9)) 光网络、^([10](#ch05.xhtml#ch05fn-10)) `Point-to-Point Protocol (PPP)`、^([11](#ch05.xhtml#ch05fn-11)) 电视中的 `Vertical Blanking Interval (VBI)`、^([12](#ch05.xhtml#ch05fn-12)) `Fiber Distributed Data Interface (FDDI)`、^([13](#ch05.xhtml#ch05fn-13)) 鸟类信使、^([14](#ch05.xhtml#ch05fn-14)) 以及许多其他物理层协议（请参阅下文“进一步阅读”部分）。这些草案主要说明了如何在底层物理层的帧（或数据包）中承载 `IP` 数据报（或数据包），以及如何使层间发现，例如 `Address Resolution Protocol (ARP)` 在每种媒体类型上工作（请参阅 [Chapter 6](#ch06.xhtml#ch06)，“[Interlayer Discovery](#ch06.xhtml#ch06)，”了解更多信息）。

`IP` 还必须指定如何在不同物理链路上可用的各种 `MTUs` 上承载大块数据。虽然原始 `Ethernet` 规范选择了 1,500 字节的 `MTU` 来在较大数据包大小和最大信道利用率之间取得平衡，但许多其他物理层是设计为具有更大的 `MTUs`。此外，应用程序往往不会以整齐的 `MTU` 大小块发送信息。`IP` 通过提供分片来解决这两个问题；[Figure 5-3](#ch05.xhtml#ch05fig03) 进行了说明。

![Image](`graphics/05fig03.jpg`)

**Figure 5-3** *Fragmentation in IPv6*

如果应用程序（或更高层协议）传递 2,000 字节的数据供 `IP` 传输，则 `IP` 实现将

- 确定数据必须通过的路径上的 `MTU`；这通常是读取系统软件设置的配置或默认值的问题
- 根据 `MTU` 减去头部的预计大小，包括隧道头部等——必须与数据一起传输的元数据，将信息分解为多个片段
- 发送第一个分片，其中带有 `IPv6` 可选头部（这意味着对于不是较大数据块的分片的数据包，无需包含分片头部）
- 将 more fragments 头部中的 `offset` 设置为原始数据块中此数据包表示的第一个字节除以 8；在 [Figure 5-3](#ch05.xhtml#ch05fig03) 中的示例中，第一个数据包的偏移量为 0，而第二个数据包的偏移量为 150（1200/8）。
- 如果这是数据块的最后一个分片，则将 more fragments 位设置为 0，如果后面还有更多分片，则设置为 1。

`IPv6` 可以通过分片携带的总数据块大小受 *offset* 字段大小的限制，该字段长 13 位。因此，`IPv6` 最多可以携带 2^(14) 字节的数据作为一系列分片，或约 65,536 字节加上一个 `MTU` 大小的分片的数据块。任何更大的数据都需要在传递给 `IPv6` 进行传输之前以某种方式由更高层协议分解。

最后，`IP` 必须提供一种在网络中使用多种物理层类型时承载数据包的方法。这是通过在网络中可能互连多种媒体类型的每个跳上重写下层头部来解决的。以这种方式重写下层头部的设备最初被称为网关，但现在通常称为路由器，因为它们根据 `IP` 头部中包含的信息路由流量。分组交换在 [Chapter 7](#ch07.xhtml#ch07)，“[Packet Switching](#ch07.xhtml#ch07)” 中进行了更详细的考虑。

`IPv6` 承载数据的方式还有一些其他有趣的方面；[Figure 5-4](#ch05.xhtml#ch05fig04) 说明了一个可供参考的 `IPv6` 头部。

![Image](`graphics/05fig04.jpg`)

**Figure 5-4** *The IPv6 Header Format*

在 [Figure 5-4](#ch05.xhtml#ch05fig04) 中：

- **`version`** 设置为 6，表示 `IPv6`。
- **`traffic class`** 分为两个字段，6 位用于承载服务类型（或服务类别），2 位用于承载拥塞通知。`Quality of Service (QoS)` 在 [Chapter 8](#ch08.xhtml#ch08)，“[Quality of Service](#ch08.xhtml#ch08)” 中进行了更详细的考虑。
- **`flow label`** 设计为提示，用于告诉转发设备如何在等价成本多路径（`ECMP`）路径集中沿同一路径保持单个流中的数据包。
- **`payload length`** 指示数据包中承载的数据量，以字节为单位。
- **`next header`** 提供有关数据包中包含的任何额外头部的信息。`IPv6` 头部可以包含超出基本头部所包含的信息；这些可选头部将在后面的部分中更详细地讨论。
- **`hop limit`** 是此数据包在被丢弃之前可以被网络设备“处理”的次数。任何重写下层头部的路由器（或其他设备）都应在转发过程中将此数字递减一；当跳数限制达到 0 或 1 时，应丢弃数据包。

**Note**

跳数用于防止数据包在网络中无限循环。每次网络设备转发数据包时，跳数都会递减一。如果跳数达到 0，则数据包将被丢弃。如果数据包在网络内循环，跳数（也称为生存时间，或 `TTL`）最终将被减少到 0，数据包将被丢弃。

`IPv6` 头部是可变（类型长度值 [`TLV`]) 和定长信息的混合。基本头部由定长字段组成，但 *next header* 字段为可选（或扩展）头部留下了可能性，其中一些头部被格式化为 `TLVs`。这允许构建定制硬件（例如，专用集成电路 [`ASIC`]）来基于定长字段快速交换数据包，同时仍有可能携带可能仅在软件中处理的变长数据。

## Multiplexing

`IPv6` 以两种不同的方式实现多路复用：

- 通过提供一个用于标识主机和网络（或更广泛地说，可达目的地）的庞大地址空间
- 通过提供一个空间供上层协议放置协议号，从而允许多个协议在 `IPv6` 之上运行

### IPv6 Addressing

`IPv6` 地址为 128 位，这意味着可以有高达 2^(128) 个地址——一个庞大的数字，足以可能为地球上的每一粒尘埃编号。`IPv6` 地址通常写成一系列十六进制数字，而不是写成一系列 128 个 0 和 1，如 [Figure 5-5](#ch05.xhtml#ch05fig05) 所示。

![Image](`graphics/05fig05.jpg`)

**Figure 5-5** *IPv6 Address*

`IPv6` 地址格式中关于零的两个要点值得注意：

- 每个部分（以冒号分隔）中的前导零被省略。
- 地址中一个长串零可以用双冒号替换一次（不能两次）。

**Note**

当网络中的每个地址都以相同的数字集开头时，*有时* 仅包含变化的部分以缩短地址。例如，在具有 2001:db8:3e8:100::1 和 2001:db8:3e8:101::2 的网络中，这两个地址可能被称为 100::1 和 101::2，而不是重复整个地址。你需要从上下文中填补地址的其余部分，例如网络图，或对地址的某些早期提及等。

为什么需要这么多地址？因为在任何寻址方案中，许多地址从未被使用。
