

通过最少的链路（因此也是最少的网络设备）转发流量会消耗最少的资源，但冷土豆路由和热土豆路由都会选择较长的路径以满足策略约束。这用资源的高效使用换取了协议或服务的有效运行，以增加收入。路由系统也可能适用其他策略，例如选择带宽最高的路径，或选择将流量引导至地理出口点最接近用户的路径。无论策略如何，它通常都代表了一种优化与另一种优化之间的权衡，并且需要某种额外的状态来实现。

### 资源分段

很多时候网络在逻辑上被划分以控制对特定资源的访问。文中将使用[Figure 17-2](#ch17.xhtml#ch17fig02)所示的网络来说明。

![Image](graphics/17fig02.jpg)

**Figure 17-2** *Overlays as a Form of Segmentation*

[Figure 17-2](#ch17.xhtml#ch17fig02)显示了三个不同的网络：

• Network A 显示基础（路由）拓扑。
• Network B 显示必须相互连接的一组设备和链路。
• Network C 显示必须相互连接的另一组设备和链路。

在[Figure 17-2](#ch17.xhtml#ch17fig02)中，主机 B 只能连接到服务器 L，而主机 A 只能连接到 H。当然，可以通过在 G 和 K 上配置简单的包过滤器来提供这种分段，但进一步的要求可能排除了使用简单包过滤器。例如：

• A 和 H 之间通过的流量可能需要使用路径 `[C,E,F,K,G]`；这将流量工程要求与服务访问要求混合在一起。
• 服务器 H 和 L 可能甚至不能*看到*来自另一拓扑的路由和其他信息。如果这两个服务器参与路由控制平面，这可能非常困难，例如如果它们托管许多虚拟机（`VMs`），每个虚拟机都需要将其自己的 IP 地址通告到控制平面。

当达到这种要求级别时，一个常见的解决方案是创建覆盖网络，通常使用隧道来承担将网络分离为多个虚拟拓扑的重任。在[Figure 17-2](#ch17.xhtml#ch17fig02)中，这些要求通过覆盖网络得到满足。在网络 B 中，隧道将从面向主机 B 的 D 的入站接口开始构建（隧道入口）。该隧道将跨越 G 和 K，最终在 K 连接到 L 的接口上终止（隧道出口）。为了将流量从 B 引导到 L，必须有一些路由控制平面将流量拉入隧道入口，以便将其通过隧道路由到 L。在网络 C 中，隧道将从面向 A 的 C 的入站接口开始构建。隧道跨越 C、E、F、K 和 G，并在 G 面向 H 的出站接口处终止。同样，必须有一些控制平面将数据拉过该隧道，以便从 A 发起的流量在 C 处被拉入隧道，并在 G 处作为“原始 IP 包”（不带隧道头）呈现，以便 G 可以将包交换到 H。

引导流量通过这两个隧道的路由信息实际上可能在单独的控制平面中承载。在这种情况下，下层控制平面将提供对隧道端点的可达性，而覆盖控制平面将引导流量通过隧道。这种控制平面的分离使得不同的拓扑、下层和覆盖层完全分离；可达性和拓扑信息不会在这两个控制平面之间共享。

通过网络引导的流量也是如此；两个流通过隧道化被分离。不仅流量通过隧道化被分离，而且流的路径也在网络中被工程化。隧道化，以及覆盖的更完整概念，在满足许多不同的策略要求方面很有用；这就是为什么覆盖在网络工程中被广泛使用。

### 为应用优化的流固定

大象流和老鼠流是工程师经常遇到的两类流。大象流通常是大型、持久的数据流。例如，任何占用单个链路可用带宽超过约 20% 且持续超过两三分钟的流都可能被归类为大象流。另一方面，老鼠流的带宽要低得多，例如任何链路可用带宽的 1% 以下，并且往往持续时间很短。大多数流量都可以分为大象流和老鼠流。*应该如何处理大象流和老鼠流？*

一种解决方案是交错每个流的包，这允许每个流公平地访问可用带宽。虽然服务质量（`QoS`）是一种解决方案，但另一种解决方案是将特定流量流固定到特定路径，或路径固定。[Figure 17-3](#ch17.xhtml#ch17fig03)用于进一步解释。

![Image](graphics/17fig03.jpg)

**Figure 17-3** *Pinning an Elephant Flow in a Network*

在[Figure 17-3](#ch17.xhtml#ch17fig03)中，A 开始了一个将持续数小时的流，消耗链路可用带宽的 20%（假设所有链路带宽相同，为 100Mbps），并终止于 H。几乎同一时刻，B 发送一系列终止于 H 的短期小流。鉴于 C 和 G 之间只会选择一条最佳路径，两个流都将沿同一路径，例如沿路径 `[C,E,G]`。以这种方式混合两个流可能会导致两者在性能方面都受损。为了理解问题，最好考虑将包序列化到线路上的速率：

• **64-byte packet onto a 100Mbps link:** .05ms
• **1,500-byte packet onto a 100Mbps link:** .12ms
• **9,000-byte packet onto a 100Mbps link:** .72ms

假设整个网络能够支持 9,000 字节的包大小（最大传输单元，或 `MTU` 端到端为 9,000 字节），并且大象流实际上正在发送 9,000 字节的包。对于老鼠流，假设包大小为 64 字节包（至少在一个方向）。如果单个老鼠流包被困在单个大象流包后面，老鼠流包将被保持 .72ms 才能序列化到物理接口上。如果两个流的包始终交替出现，可能会出现一些显著的性能下降，但两个应用程序可能仍然足够好地工作。

但如果两个流之间的交错不是最优的会怎样？例如，如果存在类似于[Figure 17-4](#ch17.xhtml#ch17fig04)所示的包序列的情况？

![Image](graphics/17fig04.jpg)

**Figure 17-4** *A Problematic Mixture of Packets from Elephant and Mouse Flows*

老鼠流包之间最短和最长间隔的差异为 .05ms 和 .288ms。大象流包之间最短和最长间隔的差异为 .05ms 和 .15ms。这些变化似乎很小，但即使是最小的变化也会在端到端显示为抖动。这种抖动，特别是在更大规模上，对流量控制和错误校正是有问题的。在这种情况下，即使大象流远远大于老鼠流，两者仍然受到负面影响。这种相同类型的问题在数据中心结构中也很常见。[Figure 17-5](#ch17.xhtml#ch17fig05)说明了这一点。
