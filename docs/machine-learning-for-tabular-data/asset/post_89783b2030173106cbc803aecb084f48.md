Different stopping points may be found for each model trained on the entire folds in a cross-validation process with early stopping. When training on the entire dataset, you can still rely on using early stopping based on a validation sample. Hence, you just need to set a high number of iterations and see when the training stops. Otherwise, you can use a fixed number of iterations based on the stopping iterations observed in cross-validation. In this case, you can calculate the average or median of all stopping points in cross-validation to determine the number of boosting trees to use. However, there's no fixed rule, and you may choose to use the second maximum value for an aggressive stopping policy or the second minimum value for a conservative one.

Additionally, consider increasing the number of boosting trees since training is done on more data during cross-validation. As a general guideline, increase the number of boosting trees by a percentage equivalent to dividing one by the number of folds used in cross-validation. However, since no one-fits-all solution exists, experimentation may be necessary to find the best approach for your problem.

As an example, we run the previous code again, this time setting a higher number of estimators to use and parameters, validation_fraction and n_iter_no_change, that activate the early stopping. The parameter validation_fraction defines the fraction of the training data to be used for validation, and it is effective only when n_iter_no_change is set to an integer indicating how many iterations should pass without improvements testing the model on the validation set before stopping the process.

## 5.4 Using XGBoost

XGBoost gained traction after being successful in a Kaggle competition, the Higgs Boson Machine Learning Challenge (https://www.kaggle.com/c/higgs-boson), which was proposed in the composition for a fast and accurate solution in comparison to Scikit-learn's gradient boosting. XGBoost has been adopted successfully in many other data science competitions, proving its effectiveness as a good place to introduce innovations. At the time of writing, the XGBoost package has been updated and reached the milestone of version 0.3, which is the version we have used. Initially conceived as a research project by Tianqi Chen, later further developed with Carlos Guestrin, XGBoost is a gradient boosting framework available as open-source software. It is noticeable that unlike other initiatives, such as LightGBM, and Decision Forests (see https://github.com/dmlc/xgboost), XGBoost remained completely independent by the Machine Learning Community. Over time, the framework has undergone significant enhancements and now provides advantages for distributed processing and parallelism, which allows it to operate on large-scale datasets. XGBoost has also gained wide adoption and is currently available in several programming languages, including C++, Python, and R. Moreover you will immediately notice key characteristics of the framework including:

- The ability to handle various input types
- Support for customized evaluation functions
- Automatic handling of missing values
- Easy support for GPU
- Accommodation of monotonicity and feature constraints
- Optimization of multiple cores
- Networked parallel training, which allows for distributed computing across a cluster
- Utilization of all available CPU when tree construction
- Out-of-core computing when working with large datasets

However, what sets the "extreme" XGBoost algorithm apart is its innovative details for optimization, including a variant of gradient descent known as Newton Descent, as well as its unique approach to feature splitting and sparse data handling. The following section briefly summarizes these techniques that power XGBoost's performance.

## 5.4.1 XGBoost's key parameters

Let's review the specific options we decided on in our previous example shown in listing5.12, with the n_estimators parameter, which specifies the number of decision trees involved in building the ensemble and is part of the gradient descent process we discussed previously in this chapter.

The n_estimators parameter in XGBoost determines the number of decision trees to produce the output. In standard tabular data, the usual values for this parameter range from 10 to 10000. Increasing this value can improve performance by involving more weak learners, it can also slow the training time. It's worth noting that there is an ideal number of trees that maximizes performance on prediction with unseen data, and finding this sweet spot depends on other XGBoost parameters, such as the learning rate. To achieve a high-performing XGBoost model, it's important to choose the appropriate number of trees based on the problem at hand while setting the other parameters correctly.

Whereas Scikit-learn is limited to just decision trees, XGBoost proposes more choices using its booster parameter:

- gtree—Decision trees, as you would expect in gradient boosting
- gblinear—Linear regression models
