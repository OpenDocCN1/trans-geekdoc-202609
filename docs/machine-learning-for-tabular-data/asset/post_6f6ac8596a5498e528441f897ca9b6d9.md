Although target encoding is a convenient procedure because doing so may quickly transform any categorical into a numeric feature, you have to pay attention to keeping all important information from your data. Target encoding renders modeling of any interaction between features impossible. Let's, for instance, that you are working on an advertising response dataset with click formats. Using both features, having transformed two high cardinality categoricals with potentially thousands and thousands of values, you may easily create any tree of classical model. However, after encoding, your model, whether linear or tree-based, won't be able to grasp any possible interaction between the encoded features. In this case, the solution is to create a new feature beforehand, combining the two high cardinality categorical features and then encode their combination.

Hence, for other tools, we should consider the pros and cons of this advanced encoding technology. In our experience, depending on the situation, before resorting to target encoding, there are few options for classic machine learning algorithms and gradient boosting for dealing with high cardinality categorical features:

- Just dropping categorical features
- Using a OneHotEncoder
- Using an OrdinalEncoder and treating categories as ordered equidistant quantities
- Using an OrdinalEncoder and relying on the native category support of boosting histogram-based algorithms
- Using target encoding as a last resort

Dropping features is only sometimes considered. However, we already mentioned in chapter 2 how you can evaluate how nominal feature can contribute to predicting a target utilizing Cramer's V measure of association.

When confronted with a high cardinality categorical feature, opting for one-hot encoding is almost necessary for linear models. When dealing with other models, such as decision trees and their ensembles, there might be a more suitable approach. This is because one-hot encoding creates an additional feature for each value of the categorical feature. This leads to an increased number of split points that the tree-based model must consider during fitting. Consequently, using one-hot encoding requires more depth in a decision tree to achieve an equivalent split than could be achieved with a single split point using a different way of handling the categorical feature.

For an ordinal encoder, the categories are encoded as 0, 1, 2, and so on, treating them as continuous features. While this approach can be misleading for linear models, it works effectively for decision trees. Decision trees can accurately split the data based on ordinal encoding, separating the categories according to their relationship with the target variable. While with XGBoost, which treats all features as numerical, continuous features.

If we decide to use the support for categorical features, this option is available in LightGBM and the version of XGBoost provided by the H2O.ai library (https://mng.bz/6ce75). Native categorical support allows these models to handle categorical features more effectively, without converting them into numerical values. In that case, since native handling requires sorting categories, we expect the algorithm to be slightly slower when using native handling of categorical features as ordinal numbers. In the native category support, the sorting of the categories of a feature is based on the associated target variance for each category. Once the sort having passed, the feature can be used as a continuous numerical attribute.

## 6.1.4 Transforming numerical data

Decision trees can automatically handle nonlinearities and interactions in data. This is because they can split a variable at any point into two parts and then further split it repeatedly. This property is particularly handy for handling subtle and deep interactions in the data, with a caveat, decision trees are quite rough approximators. Under the aspect of precisely modeling complex relationships in data, neural networks with enough examples are better approximators.

Figure 6.1 shows how a bagged ensemble of decision trees can approximate a nonlinear function. The result is an approximation constructed by a set of if-else decision rules that recursively divide the space. However, noise in the data can result in inaccuracies in certain parts of the space. In contrast, a neural network with the same number of nodes as the trees used in the bagged decision trees can provide a smoother and more accurate curve estimation.

**Figure 6.1** Comparison of predictions between a neural network and a bagged decision ensemble for a random dataset with a noisy sine function

Since GBDT is also based on decision trees, it may similarly split in shaping non own functions using binary splits. Consequently, when using GBDT, and you know specific nonlinearities or interactions, it benefits you to explicitly define them by using transformations toward linear forms, binning or discretization, and precomputed interactions of features. For nonlinearities, transformations help the number of splits. Before applying transformations, you need to understand your data. Linearities and nonlinearities, even if there is no relationship with the target, can be easily spotted after fitting your training data by a partial dependence plot (PDP). This model-agnostic chart explains how features and targets are related through the model you have trained.

PDPs display how the target output changes based on specific input features ignoring the effects of other features. In other words, it shows the average expected prediction if we set a value on all the data points of the input feature we are examining. Assumption underlying the analysis is the input we represent by a PDP is independent of other features. Under such conditions, the PDP represents how the input directly affects the target. However, this assumption is violated in practice, meaning that the input feature we are examining is usually completely independent of the other features.
