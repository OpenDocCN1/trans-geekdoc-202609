# 1. Introduction

## The Slow Reporting Script

The web page was taking three hours to load. Let that sink in for a moment: three hours. The code backing the page was a reporting script written in PHP, attempting to build 40,000 entity objects from 2 million database rows. Sometimes the page never loaded at all. At least the client could tell when it failed, because a big ugly error popped up in the browser window. Unfortunately that was also around the three hour point. The client was understandably frustrated.

I was assigned to troubleshoot the problem. It turned out the cause was not that the database was optimized. It was not the number of rows being returned. It was not even the number of objects being built.

No, the cause was the number of queries being issued from the reporting script. The high volume of queries, in turn, was a result of how the script was assembling the entity objects. When I say "high volume", I mean two hundred thousand and one queries. These 200,000+ queries were used to build each root entity along with each of its five associated collections and entities. No wonder the script was taking three hours to finish!

After discovering this, I was able to apply the "query-and-stitch" technique presented in this book to refactor how the entity objects were assembled. Over the course of a few days of refactoring I was able to reduce the load time from 3+ hours to just under 6 minutes. That's a 30x improvement, and still so by typical standards, it was much more bearable for the client. (Later refactorings improved the load time ever.)

The causes leading to the terrible performance of the Slow Reporting Script have a name: N+1 Problem. The problem has various aliases, such as the "1+N problem", "N+1 queries", "SELECT N+1", and so on, but they all refer to the same thing.

# Introduction

While I mention the N+1 problem more than once in Modernizing Legacy Applications in PHP¹, I did not address a solution directly. This book remedies it. Here, we will discuss the specifics of the N+1 problem:

- what the N+1 problem is,
- how to diagnose and discover the problem in your application,
- why the problem occurs, and
- how to solve the problem in your codebase.

# Example Application

While I cannot present the Slow Reporting Script itself for before-and-after examination, I can do the next best thing and present a generic example. In this book, we will use hypothetical code from naive blogging as our subject. In doing so, we will use the SQL and PHP structures described in the appendix.

This will be a legacy application example, so there is no use of ORMs. (Different ORM implementations have their own N+1 mitigation strategies, which we cannot discuss here.)

Without an ORM, this hypothetical application uses PDO² for its database abstraction. Not all legacy code uses PDO, but the principles regarding N+1 (both the problem and solutions) apply to all database connection libraries. These include mysqli³, mysqli*, as well as us database abstraction layers.

When fetching query, our application uses the PDO::FETCH_CLASS* mode as much as possible. This causes PDO to return an array instance of a specified entity class, each with its properties already filled with the data from one row. With other systems, you are likely to create the class separately from the database query; we use FETCH_CLASS primarily to reduce the volume of the example code. (The entity classes themselves are plain PHP objects with public properties)

Finally, the naive codebase uses plain PHP arrays for entity collections. More sophisticated systems may use generic class properties, but the principles concerning N+1 regarding collections remain the same.

# Defining The N+1 Problem

## The Problem By Example

It is easiest to describe the N+1 problem by example. Let's say that our naive blog application needs to show a page of the 10 most recent blog posts, along with all the comments on each post.

First, the application retrieves the root collection of Post entities as an array:

```php
<?php
$stm = 'SELECT *
FROM posts
ORDER BY datetime DESC
LIMIT 10';
$sth = $pdo->prepare($stm);
$sth->execute();
$posts = $sth->fetchAll(PDO::FETCH_CLASS, 'Post');
?>
```

So far so good: the application has issued one query to build the root collection of Post entities. Next, the application collects the Comment entities on each entity:

```php
<?php
// prepare a statement to select the comments
$stm = 'SELECT *
FROM comments
WHERE post_id = :post_id';
$sth = $pdo->prepare($stm);
foreach ($posts as $post) {
  $sth->execute(array('post_id' => $post->post_id));
  $post->comments = $sth->fetchAll(PDO::FETCH_CLASS, 'Comment');
}
?>
```

The application has issued ten queries to build the comments for each post. With this, we have arrived at the core of the N+1 Problem.

# The Problem Defined

The N+1 problem is revealed as the following:

For each entity in a root collection, the application issues one additional query to retrieve association.

In the above example, the application issued a total of 11 queries to build up 10 Post entities with their Comment collections:

- one query to fetch the entities in the root collection (this is the "1" in "N+1")
- ten more queries, for each entity in the root collection, to fetch the associations (this is the "N" in "N+1", where "N" equals the number of entities in the root collection).

# Performance Implications

There are two performance implications of the N+1:

1. The number of queries grows as a factor of the number of entities in the root collection.
2. The number of queries also grows as a factor of number of associations needed to complete each root entity.

This means that as the number of root entities and number of relationships increase linearly, the number of queries increases as a multiple of those two numbers. Each added query reduces the responsiveness of the application.

# 3. Diagnosing N+1 Problems

There are two methods to diagnose occurrences of the N+1 problem in a codebase. Both methods are a matter of detective work, and are not especially amenable to automation.

# Codebase Examination

First, we can examine the codebase manually to look for queries being executed inside loops. This can be tougher than it sounds, since the loop may be widely separated from the query. For example, this loop looks mostly harmless:

```php
<?php
foreach ($posts as $post) {
    $helper->doSomething($post);
}
?>
```

On further examination, if the doSomething() method (or one of the methods it calls in turn) issues a query to the database, then we have an N+1 problem on our hands. As such, it may not be immediately obvious where the problem originates in the codebase.

> What can be really pernicious is when the codebase makes a database call to a stored procedure, and the stored procedure itself is the origin of the N+1 problem. In that case, we will need to review the stored procedure code as well.

# Log/Profile Examination

Alternatively, we can start at the other end of the problem, and review the database query logs (or an application-level query profiler) to look for patterns in the queries. This is easier to achieve with some amount of knowledge of the application and the underlying data, but in simple cases it should be relatively obvious even without detailed application knowledge. Pattern recognition is the key to success with this approach.
