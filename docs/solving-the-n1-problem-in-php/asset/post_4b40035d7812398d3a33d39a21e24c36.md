
# The Process

The general process for resolving N+1 problems is as follows:

- 1. Diagnose the existence of an N+1 problem and discover its location in the codebase.
- 2. Determine the nature of the N+1 code:
    - If root collection and the associations are all built together, we should be able to refactor the code in place.
    - On the other hand, if the root collection is built in one location, and the associations are built elsewhere, we must either modify the code in different locations, or collect it into a single location.
- 3. Once the N+1 problem is resolved, test or spot-check the application to make sure it still works.
- 4. Commit the changes, push them to the central repository, and notify QA.
- 5. Diagnose the existence of any remaining N+1 problems, and start the process over again.

Since we have already gone over the diagnosis and discovery techniques for N+1 problems, we can proceed to determining the nature of the discovered N+1 code.

# N+1 In A Single Location

This is the easiest variation of N+1 to resolve. In this case, the root collection of entities and all the associations are built in a single function, method, or class. It will look something like our earlier posts-and-comments examples, and we can apply the single-query solution and/or the query-and-stitch directly on the code as it is.

# N+1 Across Separated Locations

This is a more difficult variation of N+1, one that can be prevalent in modernized codebases. Here, the root collection of entities is built in one location in the codebase, but the associations are built in a separate location.

For example, if our business-logic builds a collection of Post entities ...

# Embed Query-And-Stitch Logic Inline

Because the "1" and the "N" are in separate locations, we cannot apply the single-query solution, even in cases where the association is a single entity. We will need to embed query-and-stitch logic inline in the separate locations.

First, we change the code that builds the root collection so that it keys the collection on the Post identity values. (This should look familiar; it is taken from the chapter on query-and-stitch.)

/path/to/posts_controller.php

```php
<?php
$stm = 'SELECT * FROM posts ORDER BY datetime DESC LIMIT 10';
$stm = $pdo->prepare($stm);
$stm->execute();
$post_entities = $stm->fetchAll(PDO::FETCH_CLASS, 'Post');

$posts = array();
foreach ($post_entities as $post) {
    $post_id = $post->post_id;
    $posts[$post_id] = $post;
}
?>
```

Then, in the separate location where the associations are built, we apply the query-and-stitch approach inline. (This too should look familiar.)

/path/to/templates/show_posts.php

```php
<?php
$quoted_post_ids = [];
foreach (array_keys($posts) as $post_id) {
    $quoted_post_ids[] = $pdo->quote($post_id);
}
$quoted_post_ids = implode(',', $quoted_post_ids);

// fetch all the comments for all the posts and stitch into posts
$stm = "SELECT * FROM comments WHERE post_id IN ($quoted_post_ids)";
$stm = $pdo->prepare($stm)->execute();
$comment_entities = $stm->fetchAll(PDO::FETCH_CLASS, 'Comment');
foreach ($comment_entities as $comment) {
    $post_id = $comment->post_id;
    $comment_id = $comment->comment_id;
    $posts[$post_id]->comments[$comment_id] = $comment;
}

// refactored presentation logic
foreach ($posts as $post) {
    // display the post, and then ...
    foreach ($post->comments as $comment) {
        // display each comment
    }
}
?>
```

# Unify Query-And-Stitch Logic

The inline approach is fine for legacy codebases, but it is messy. If we have a more modern codebase with well-separated layers, we would do better to extract the separated association-building logic to an appropriate layer. This is by far the preferred approach.

For example, let's say we have a PostsMapper and a CommentsMapper:

Mapper classes

```php
<?php
class PostsMapper
{
    protected $pdo;

    public function fetchRecentPosts()
    {
        $stm = 'SELECT * FROM posts ORDER BY datetime DESC LIMIT 10';
        $sth = $this->pdo->prepare($stm);
        $sth->execute();
        $posts = $sth->fetchAll(PDO::FETCH_CLASS, 'Post');
        return $posts;
    }
}

class CommentsMapper
{
    protected $pdo;

    public function fetchCommentsForPost($post_id)
    {
        $stm = 'SELECT * FROM comments WHERE post_id = :post_id';
        $sth = $this->pdo->prepare($stm);
        $sth->execute(array('post_id' => $post_id));
        $comments = $sth->fetchAll(PDO::FETCH_CLASS, 'Comment');
        return $comments;
    }
}
?>
```

# Refactoring The Codebase To Remove N+1 Problems

Our N+1 presentation logic might look like this:

/path/to/templates/show_posts.php

```php
foreach ($posts as $post) {
    // display the post, and then ...
    foreach ($post->comments as $comment) {
        // display each comment
    }
}
```

One way of using query-and-stitch would be to place it in CommentsMapper.

CommentsMapper.php

```php
<?php
class CommentsMapper {
    public function fetchIntoPosts($posts) {
        $quoted_post_ids = [];
        foreach (array_keys($posts) as $post_id) {
            $quoted_post_ids[] = $pdo->quote($post_id);
        }
        $quoted_post_ids = implode(',', $quoted_post_ids);

        // fetch all the comments for all the posts
        $stmt = "SELECT * FROM comments WHERE post_id IN ($quoted_post_ids)";
        $stmt = $pdo->prepare($stmt)->execute();
        $comment_entities = $stm->fetchAll(PDO::FETCH_CLASS, 'Comment');

        // stitch into the posts
        foreach ($comment_entities as $comment) {
            $post_id = $comment->post_id;
            $comment_id = $comment->comment_id;
            $posts[$post_id]->comments[$comment_id] = $comment;
        }
    }
}
?>
```

(There is no need to return $posts since $posts was passed by reference.)

The presentation logic can then become something like this:

/path/to/templates/show_posts.php

```php
<?php
$comments_mapper->fetchIntoPosts($posts);
foreach ($posts as $post) {
    // display the post
    foreach ($post->comments as $comment) {
        // display each comment
    }
}
?>
```

With this, we have removed the N+1 problem. However, we still have layer-separation issues. As a further refactoring, we would probably want to unify the query-and-stitch logic in the domain layer and build the collection of Post entities in a better-separated way.

# Test, Commit, Push, Notify QA

After making our changes, we need to make sure the application still works. We do this by running our pre-existing unit or characterization tests. If we do not have tests in place, we must browse to or otherwise invoke the changed code.

If these tests fail, we rejoice! We have discovered that the refactoring has errors. We now have a chance to fix them before we deploy to production.

If the tests pass, we likewise rejoice. We can now commit all of our new work and push it to the central repository. Then we can notify the QA team that our better-performing code is ready for them to review.

# Do ... While

Once we have solved that occurrence of one N+1 problem, we can start over again and look for remaining ones, and apply the process again.
