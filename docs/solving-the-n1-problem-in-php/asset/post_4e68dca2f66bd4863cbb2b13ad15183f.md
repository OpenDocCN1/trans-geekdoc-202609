
## Handling “To-Many” Relationships

Unfortunately, the single-query solution is almost entirely unsuitable for most "one-to-many" and "many-to-many" situations. Let’s take a look at our post-and-comments example to see why. We will start by retrieving all the Post entities (not just 10) and all their comments:

```php
<?php
$stmt = 'SELECT
    posts.post_id AS post__post_id,
    posts.author_id AS post__author_id,
    posts.datetime AS post__datetime,
    posts.title AS post__title,
    posts.body AS post__body,
    comments.id AS comment__comment_id,
    comments.name AS comment__name,
    comments.email AS comment__email,
    comments.website AS comment__website,
    comments.body AS comment__body
FROM posts
LEFT JOIN comments ON comments.post_id = posts.post_id';
$stmt = $pdo->prepare($stmt);
$stmt->execute();
$rows = $stmt->fetchAll(PDO::FETCH_ASSOC);
?>
```

Some things to note about this code:

- 1. With “to-one”, we no longer use SELECT *; deconstruction of similar column names is still needed.
- 2. We add a LEFT JOIN clause for the “to-many” relationship, in this case joining the comments table. (We use a LEFT JOIN in case there are no comments on a post).
- 3. Again with “to-one”, we use the PDO::FETCH_ASSOC mode instead of PDO::FETCH_CLASS, and we will have to create the object instances ourselves.

The result set is going to be rather large and will contain a lot of repetition. If there are 50 Post entities in the system, there are 5 Comment entities associated with each Post, that means there will be 250 rows in the result set. It will look something like this:

## Single-Query Fails With “To-Many” Relationships

At the first single-query solution may seem like a solution for N+1 problems as applied to “to-many” relationships, but there are some major drawbacks.

First, there is no reasonable way to add a LIMIT clause that works the way we need it to. This is because the LIMIT applies to the number of rows returned, and not to the number of entities represented. The difference is subtle but important.

If we were to add LIMIT 10 to the above query, we would in fact get back 10 rows. But those rows would not necessarily represent 10 Post entities (at least, unless there was only one Comment per Post). Even variations on sub-selects for the FROM and JOIN clauses, with LIMIT clauses in the sub-selects, do not work the way we would like in “to-many” relationships.

It turns out the only way to enforce a LIMIT involving a “to-many” relationship in the single-query solution is to count the entities in the PHP looping code. It is left to say that this is a sub-optimal approach.

Second, if there are two or more “to-many” relationships, it becomes much more difficult to construct the query and then pick apart the result set to create the entities. The repetition becomes exponentially more troublesome, we need to track the existence of each related entities. In addition, the size of the result set becomes a problem, whether in terms of columns (because each row has every column for every entity) or in terms of rows (because each row repeats every data element for every entity, multiplied by the number of relationships).

Overall, then, the single-query solution may be fine for “to-one” relationships, but is almost entirely unsuitable for any number of “to-many” relationships.

## 6. Solving N+1 With Query-And-Stitch

There is an alternative to the single-query solution that is easy to implement and more scalable across any number of associations. This alternative is called "query-and-stitch."

The query-and-stitch approach is as follows:

- 1. Issue one query for the root collection of entities.
- 2. Issue one additional query per association to get all of the associated entities for all of the root entities.
- 3. Stitch the associated entities into the root entities using a PHP loop.

## Tradeoffs In Query-And-Stitch

The key here is that we issue one additional query per relationship, not one per root entity. The increase in the number of queries is thus linear, not exponential.

For example, if there are 10 entities in the root collection and 2 associations:

- Under N+1 we would issue 21 queries (1 for the root collection, and 10 for each association).
- With the single-query solution, we might be able to retrieve the data in one query, but the costs of working with the result set are too high.
- Using query-and-stitch, we issue a total of 3 queries (1 for the root collection, and 1 for each association). Adding a third association would result in 4 queries.

The query-and-stitch approach represents an effective tradeoff between N+1 and the single-query solution, both for "to-one" and "to-many" relationships.

## Handling “One-To-Many” Relationships

The following is a rewritten version of our earlier posts-comments example using the query-and-stitch technique. The query to fetch the master set of Post entities is identical, but note that we follow it by creating a root collection keyed on the post_id (i.e., instead of sequential keys).

```php
<?php
// fetch the sequentially-indexed entities
$stmt = 'SELECT
FROM posts
ORDER BY datetime DESC
LIMIT 10';
$stmt = $pdo->prepare($stmt);
$stmt->execute();
$post_entities = $stmt->fetchAll(PDO::FETCH_CLASS, 'Post');

// reindex the entities on their primary key values
$posts = array();
foreach ($post_entities as $post) {
    $post_id = $post->post_id;
    $posts[$post_id] = $post;
}
?>
```

Now that we have our collection of Post entities keyed on their identity values, we fetch all the Comment entities for the entire $posts collection in a single query.
