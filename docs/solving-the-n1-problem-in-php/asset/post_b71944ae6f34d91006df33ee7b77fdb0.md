## Easier Query Examination

If we have a non-trivial number of root entities, more than 100 or so, reviewing the query logs or profiles will be a heavy undertaking. If at all possible, try to reduce the data set to something more manageable, so that the logs are relatively short. At the very least, reducing the data set will decrease the amount of time it takes to generate the logs in the first place.

In the case of the Slow Reporting Script, it would have taken three hours to run the script and get a log, and the log itself would have been hundreds of thousands of lines. That would have for a very slow “change-and-retest” iteration cycle. Realizing this, I reduced the data set from 2 million rows to just 2 thousand; as a result, the script had to build only 40 root entities instead of 40,000. This had the benefit reducing the time for the script to run and to generate the query log, as well as reducing the number of lines in the log. That meant looking through only 201 relevant log lines, instead of 200,001.

## 4. Why Does The N+1 Problem Occur?

Why is it that the N+1 problem appears at all? After fixing the problem in several codebases, and talking with some of the original developers on those codebases, I have concluded that the problem stems from a CRUD-dy developer mindset.

## CRUD Is The Problem

We all know the CRUD acronym: Create, Read, Update, Delete. The key here is that CRUD applies primarily to single entity, retrieve a single entity, edit and delete a single entity.

This one-at-a-time approach is useful for the vast majority of database interactions. It leads to using such patterns as RowDataGateway and ActiveRecord?. In these, the concentration is on how to build a single entity, usually with its associations.

The single-entity concentration is the source of the N+1 problem. With that mindset, developers approach building a collection of multiple entities as a variation on building entities. The developer just loops over the single-entity creation process once for each entity in the collection. Collections of entities are essentially an afterthought. Because they are not a primary focus, the developer naturally gravitates towards queries-inside-loops, the hallmark of the N+1 problem.

## B Is The Answer

The key to solving the N+1 problem, then, begins with a change in developer mindset. Instead of thinking in terms of CRUD, we should think in terms of BREAD: Browse, Read, Edit, Add, and Delete.

Although the "R-E-A-D" parts map directly to "C-R-U-D", notice that the very first letter represents a collection of entities.

## Why Does The N+1 Problem Occur?

By thinking first about collections of entities, instead of only individual entities, a developer begins to consider different approaches. Patterns such as TableGateway³, Table⁴, and even DataMapper⁵ deal with collections as a first-class part. After treating entity collections as a first-class concern, it becomes relatively easy to build a single entity, one that contains only a single entity.

If we can efficiently build a collection of entities, then building a single entity is also efficient. The reverse is simply not true, as we have seen by example.

## 5. Solving N+1 With A Single Query

One approach to solving the N+1 problem is to retrieve all the data for the root entities, and all data for all the associations, all in one query:

- Issue a query that joins all necessary tables in a single result set.
- Convert each result row to entity objects in a PHP loop.

This approach is intuitively appealing, because it results in only a single query no matter the number of root entities or associations. While it works reasonably well for "to-one" relationships, it is generally unsuitable for "to-many" relationships. Even so, it warrants discussion, if only for completeness' sake.

 Handling “Many-To-One” Relationships

Let's say our blogging application needs to present a list of the 10 most-recent blog posts and their authors. In an N+1 situation, the relevant code might look like the following.

# The Original N+1 Code

```
<?php
// get the most recent posts
$stmt = 'SELECT *
FROM posts
ORDER BY datetime DESC
LIMIT 10';
$stmt = $pdo->prepare($stmt);
$stmt->execute();
$posts = $stmt->fetchAll(PDO::FETCH_CLASS, 'Post');

// get the author for each post
$stmt = 'SELECT *
FROM authors
WHERE author_id = :author_id'
$stmt = $pdo->prepare($stmt);
foreach ($posts as $post) {
    $stmt->execute(array('author_id' => $post->author_id));
    $post->author = $stmt->fetchObject('Author');
}
?>
```
