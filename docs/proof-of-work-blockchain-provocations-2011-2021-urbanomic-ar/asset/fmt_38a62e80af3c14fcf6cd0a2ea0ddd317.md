## Visualisations (26/04/2014)

A Bitcoin address is an identifier of 27–34 alphanumeric characters. It is a 160-bit hash of a public key.

A transaction hash is 32 bytes (256 bits).

This can provide:

| Data Type | Address (bits) | Transaction (bits) |
| :--- | :---: | :---: |
| 4-bit values | 40 | 64 |
| 8-bit values | 20 | 32 |
| 15-bit values | 10.6 | 17.07 |
| 16-bit values | 10 | 16 |

There are no 3-value divisors that go precisely into either number of bits.

Single values can be used as depths for height or bump maps, or as indexes into palettes.

Pairs can be used as `a`, `b` in Lab colour space, as 2D coordinates on a plane or surface which can then be incrementally raised (by an amount equal to the index of the pair), or as {unfinished in original—2021}.

Visualise addresses (identity/portrait), transactions (event/still life), block hashes (landscape).

Animate successive blocks, or successive transactions or account addresses in a chain of transactions.

Graph into planetary systems, constellations.

## Coloured Coins (27/04/2014)

e.g. coins representing gold bars. The issuer gives you a transaction hash, called the genesis transaction, and tells you to enter this into a coloured coin client. They then tell you that every 0.0004 BTC from the genesis BTC means you have 4 gold bars.

Coloured coins vs. Mastercoin vs. OpenTransactions. The latter two have problems.

Coloured coins are a category of smart property. A finite but divisible or multiple resource.

Art editions or units?

Shares.

In a transaction, if input is colour coded, then output is colour coded.

To issue a new colour, release the coins of that colour by creating a ‘genesis transaction’.

Non-reissuable colours—the inputs are irrelevant. The issuer has no power once the transaction is issued, so all that matters is the transaction(’s outputs…).

## DAO Art Fund (27/04/2014)

A funds-redistributing DAO that votes on and pays for artworks.

Individuals or orgs join up, add funds, and get to vote on their allocation.

Let artists submit URLs and addresses to each round of allocations.

Let members vote to add/remove members.

Only allow people to vote if they add funds in a round? OR/ Have funding and voting members/groups, who may or may not overlap.

Run like Rhizome’s art prize, or find a better model.

Have Furtherfield involved as a voting party. Do it under their banner or find a new brand to use?

Vote validity & tiebreaker rules.

Definitely allow outside sponsorship/funding OR/ require that it be channelled through members?

Tie votes to amount of funds, or have a one-member-one-vote system? Which incentivises better? Which is better governance?

Spawn contracts to vote on works.

# Hot Cold

## 2014 Ethereum DApp

![](image/hot_cold.png)

One of the example contracts from [‘Artworld Ethereum’](#6-Artworld-ethereum.xhtml) was a Conceptual Art homage called `hot_cold.se`. Here’s an updated version:

```
init:
 contract.storage[1000] = "hot"
 contract.storage[1001] = "cold"
code:
 // Swap
 temp = contract.storage[1000]
 contract.storage[1000] = contract.storage[1001]
 contract.storage[1001] = temp
```

When it receives a message, it swaps the strings ‘hot’ and ‘cold’ in its memory.
