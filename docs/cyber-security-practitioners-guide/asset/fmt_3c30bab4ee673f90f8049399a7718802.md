
# 10.4.5.*Summary*

Data Modelling and Access Control lists are modelled above using a combination of class diagrams, use cases and flowcharts. The data modelling is abstract and the Blockchain application developed above does not enforce referential integrity, nor does it explicitly allow composite keys — not without some complications. This places some restrictions on the implementation of the blockchain. It is also why class diagrams are better abstraction tools than ERDs, which are typically used to model many of the databases that blockchain aims to be integrated with or even to replace. If an implementation is of a simple register of a manager assigning staff to an FRT, then there are some simple rules that are taken for granted in databases but that need consideration in blockchain. The manager would have privileges to add and remove members of the FRT. Submission of evidence can only be done by these members of the FRT since no one else has authorisation. There would have to be a check of whether the staff member existed and then it would have to be possible to add them to the group via a simple update. Only existing group members can be removed from the group. All these rules sound obvious and simplistic but need consideration and coding. As a result, there is a danger of data duplication, something that databases strive to prevent. Such duplication not only results in an increase in the amount of effort required but also in inconsistencies in data if not approached properly.

The design of the operational logic for the transactions is modelled using flowcharts. Having a clear breakdown is not only important for designers and programmers, but also important for training purposes and ensuring that users follow the correct procedures for updating the blockchain. The procedures followed by programmers are the same as the procedures followed by users. This provides some consistency and gives the additional benefit of allowing users to concentrate on the investigation instead of having to bear a cognitive burden when completing the form.

# 10.5.Results

The implementation of BoC was completed using Hyperledger Composer-Playground and Hyperledger Fabric. The programming language for data modelling was completed in CTO, the access control was completed in Access Control Language and the operational logic was completed in Node.js. The operating system was Ubuntu 16.04 LTS (64-bit).

Two mock investigations were carried out. These were small digital investigations in which between 2 and 10 artefacts were seized. The two mock incident scenes were conducted using BoC and the output is extracted from the blockchain and in JSON format. From the results below the implementation of BoC was a success; however, problems were encountered. The first problem was using class diagrams to model the investigations, as typically the encapsulation of both data and methods is not possible with blockchain. The data, stored in registries, is on the blockchain, but methods such as transactions are not. This is why no data or methods are displayed in the class diagram in [Fig. 10.3](#chapter10.xhtml#fig10.3). However, other alternatives are also restrictive, e.g., ERDs are more restrictive with relationships. Class diagrams also allow the modelling to be more abstract from the physical representation.

A further problem that arose during the implementation was that a polymorphic method was required to capture the participant type at runtime. This would be required to access the correct and associated registries at runtime. In the design there is a separate registry for each specific role. This was necessary to implement restrictions on access, e.g., members of the legal profession can access the blockchain to inspect all transactions for the case, but are not allowed to exchange artefacts. Polymorphism is not possible, so an enumerator type was passed as a parameter in transaction-related methods in order to provide an indication of the registries required for inspection. This was considered a better solution than returning all the registries, which was the alternative but which had the issue of being inefficient.

As aforementioned, at least four transactions are required to make BoC possible. These are: the creation of a new Investigation; the addition of a new Member to the FRT; the seizure of an artefact; and the exchange of an artefact. These are discussed in the subsections below.
