
The data was reassembled, and a sequence number was added at the beginning of each data set. To reduce the length of the data processed, a unique User ID field was also added. This associated the Media Access Control (MAC) address of the Bluetooth proximity ID pass with a simple, much smaller numerical value. An entry and exit flag was then included as this would indicate if the Bluetooth ID pass entered or exited a zone.

To identify the time spent in each zone, two data sets were required for the calculation, one made up of instances when the Bluetooth ID badge entered a zone (or beacon) and one made up of instances when it left a zone. By default, each beacon sends a signal when the Bluetooth ID badge enters a zone and a second signal when it leaves a zone. To connect these two data sets together an Enter ID flag was inserted. As the Bluetooth ID badge enters a zone, a null value is added to the data set, but when the badge leaves the zone, the Enter ID flag is set to the sequence number associated with entering that zone. [Table 4.5](#chapter4.xhtml#tab4.5) depicts how the two fields and data sets are connected, thus identifying the time spent within each zone.

By calculating the difference between the entry and exit time stamp fields (connected by the entry/exit flag and the enter ID field), the time spent in each location was calculated and displayed within the Timing field.

Using [Fig. 4.9](#chapter4.xhtml#fig4.9) as an example, the individual entered the zone and generated the REC ID ‘1’ at 13:46:20 (time stamp), the entry/exit flag was set to ‘1’ (denoting an entry) and the enter ID field was set to null (no connection with another data set). When the individual left the zone, a second data set was created, sequence no ‘2’ (within the rec ID field) at 13:46:25.

### 4.6.2.**Threat detection application**

To build a threat detection system that could identify anomalies from movement data retrieved via the RTLS system, a threat detection application was created, named Shadow Guard.

Shadow Guard was written as a progressive web based application using Hypertext Mark-up Language (HTML), Cascading Style Sheets (CSS) and PHP: Hypertext Pre-processor (PHP). A MySQL database was embedded within the threat detection server to store and process the data.

[Figure 4.10](#chapter4.xhtml#fig4.10) depicts how movement data is detected and passed from the ID badge to the beacon (using Bluetooth) and then into the RTLS server through an Ethernet connection.

Once the data was written into the Zonith proprietary database, a trigger was created (within RTLS) that copies data from the RTLS database into the Shadow Guard server where the data is reconstructed and stored in the new format.

### 4.6.3.*Baseline behaviour*

Once the data collection method was constructed and the data sorted into a readable format within the Shadow Cloud application a series of baselines was constructed to determine the normal working patterns of Dakota’s contractors.

Extensive testing was undertaken by the researcher, who was assisted by Dakota’s facilities staff. Each security pass was checked to ensure each of the beacons was able to detect the badges and the zoning was correct with minimal bleedover.

Referencing the job roles outlined in [Table 4.5](#chapter4.xhtml#tab4.5), Dakota’s security personnel staff were engaged and each of the Bluetooth access cards was activated and handed to each of the contractors working within the office area of Dakota’s head office in London.

To ensure sufficent data was collected to provide an effective baseline, an initial two-month collection period was implemented. Whilst data from all contract staff was collected, the initial baseline analysis was concentrated on the 9 cleaning contractors employed by Dakota.

Data was collected from November 2017 until January 2018; this included the Christmas holiday period. ### 4.6.4.*Analysing data*

Once sufficient data was collected the analysis process could take place. The data was separated into individual floors. To detect abnormal behaviour patterns it was evident that there could be multiple determining factors that indicate potential malicious intentions. To understand and analyse the risk factor, the data was separated into different sections.

### 4.6.5.*Entry points*

As each floor had its own unique characteristics, including specific hotzones, critical areas and entry/exit points. It was considered important to analyse each floor’s entry point as this could indicate an anomaly.

As an example Dakota’s 3^(rd) floor has four separate entry points, these are as follows:

•Elevator A

•Elevator B

•Stairwell A

•Stairwell B (fire escape)

As the three elevators that service each of the floors are communal, there was a risk of unauthorised access to Dakota’s private floorspace. To reduce this risk Dakota installed two glass doors on either side of the exit/entry path from the elevators.

[Figure 4.11](#chapter4.xhtml#fig4.11) depicts Dakota’s 3^(rd) floor layout, incorporating two security doors. Note that each access point requires RFID access control to enter and triggers separate beacons (zones) at each entry point.

Two stairwells also service the 3^(rd) floor and are located at separate areas of the open plan office. These extry/exit points also require access control and trigger separate Bluetooth beacons.
