
Rule 1 is initially provided for privacy, and all submitters can only view themselves on the system. This puts a restriction on the access of the current user. The dynamic situation means that the receiver inherits new privileges upon becoming the new custodian of the object, e.g. the receiver can now exchange that artefact with someone else. Unlike relational databases, blockchain does not enforce referential integrity, therefore it is possible to exchange an artefact with a receiver that does not exist. To prevent this the transactional code will check two things: i) if the current participant is the custodian of the artefact that is to be exchanged; and, ii) if the receiver exists in the participant registry. The second of the two checks will always fail, since rule 1 in the list above only allows the current participant to read themselves, and therefore when access to the participant registry is requested, only the current user is included in it. Therefore, even if the receiver exists, rule 1 prevents them from being identified and the exchange will be denied (under these rules the exchange does allow the submitter to exchange the artefact with themselves).

Deconfliction of access control rules often needs to occur to allow some transactions to be completed correctly. There is a compromise, which is unusual for security and which could potentially create vulnerability. When a user accesses the system, it would be unusual to allow read privileges to other users.

Modelling access control is problematic due to the dynamic process, however, all possibilities still have to be considered when designing a blockchain application. Here we have opted for flowcharts and demonstrate access control by providing a single role example.

Flowcharts are often overlooked as simplistic, but many are used in proposing standard operating procedures (SOP), e.g., Mitchell *et al*. (2018), and these can provide a sequence of instructions that are followed. Of course, there are many criticisms of such a simplistic method; however, here the aim is to provide a sequence of events for each transaction identified in the system. Normally, this would be identified in UML by sequence diagrams; however, this would be misleading and incorrect since the methods and data are not encapsulated in a class. In the physical implementation they are separated.

### 10.4.4.*Operational Logic*

[Figure 10.2](#chapter10.xhtml#fig10.2) identified four transactions, which are discussed in more detail below.

**Adding a New Investigation:** Only managers can add a new investigation.^([1](#chapter10.xhtml#fn_1)) Managers cannot add a new investigation on behalf of others. Therefore, the current participant has to be a manager and can only add themselves as manager to the new investigation. Finally, the Investigation ID provided has to be unique and only then can the blockchain be updated. This procedure is illustrated in a flowchart in [Fig. 10.4](#chapter10.xhtml#fig10.4) (left) which shows a single update to the blockchain before the entire procedure terminates. Strictly, the access control list is less dynamic and more role-based for this procedure.

![image](images/fig10.4.jpg)

**Fig. 10.4.**Flowcharts for Adding a New Investigation (left) and Adding a Member of Staff to the FRT (right).

During the procedure for adding an investigation ID, the ID is checked to see if it already exists in the system. This test of the integrity of the data is unusual since in most data modelling techniques it is accepted that such items would be validated by the system, e.g., referential integrity provided by RDBMS. Hyperledger does this, however, it is worthwhile to remember that the data on the blockchain is just that, and the processes, functions and methods controlling that data are driven by the business logic provided by the designer and stored elsewhere. So, the final test in the flowchart in [Fig. 10.4](#chapter10.xhtml#fig10.4) accesses all the investigations from the asset registries and searches to see if the ID provided is unique. For the implementation in Hyperledger, this is included in the system since each investigation asset is unambiguously and uniquely identified, and therefore duplicate investigations are prevented. However, it is included here to emphasise the point of the separation of data and methods and is not akin to the object-oriented or relational database methods the designers may be used to.

**Adding a Member of Staff to the FRT:** Again, only managers of the Investigation can add members of staff to the FRT. Here the access control is a little more dynamic, and the update can only be executed by the manager of the investigation to which staff are going to be added. This prevents managers from updating the FRT via proxy and links authority to responsibility. Remember, once updated on the blockchain, this information is immutable and therefore it is important to get this accurate. The procedure is for the manager to log in and add members of staff by providing the investigation ID and staff ID. Firstly, a check to see if the manager is the manager of the investigation ID is completed. Secondly, a check to see if the member of staff selected exists and is qualified is carried out. If the first and second checks are compliant, then the blockchain is updated. Finally, the second stage can be repeated many times to add further staff. The updates are not completed in batch mode; each individual added to the FRT is updated as an individual on the blockchain. The blockchain is updated at the first opportunity possible and not left to batch mode, i.e., information is not stored for a given length of time before all the updates are made at once. This procedure is illustrated in the flowchart in [Fig. 10.4](#chapter10.xhtml#fig10.4), which shows possible multiple updates to the blockchain before the procedure ends. Access here is dynamic and dependent on user type and membership.

As in the subsection on ‘Adding a New Investigation’, there is a check to see if the current user is the manager. The ID of the user is checked against the IDs on an access control list. Those classified as managers in the list are given update, read and write privileges with regard to the Investigation asset on the blockchain. There is no referential integrity and this needs encoding, so a further check is carried out to see if the ID of the person provided exists in the appropriate registry. An update to the Investigation asset and the blockchain is completed. This can then be repeated for further FRT members. Each blockchain has a unique transaction code. The ID of the manager submitting a timestamp and the unique transaction code are used to identify the transaction during later audits.
