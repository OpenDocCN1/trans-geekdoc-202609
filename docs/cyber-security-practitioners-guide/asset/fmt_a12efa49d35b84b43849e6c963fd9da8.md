### 4.5.3.*Classification*

The primary purpose of this research paper is to construct a security model that incorporates an algorithm that will detect a potential threat through an anomaly detection process. An important aspect of the detection process is the classification of an anomaly once the anomaly is detected.

The research has classified the anomalies into the following groups, classes or sets.

### 4.5.4.**Point-based anomalies**

Based on data collected over a period of time, an individual whose movement patterns are considered anomalous in relation to the baseline data would represent an anomaly. Chandola *et al.* (2009) describe anomaly detection as the problem of finding patterns in data that do not conform to expected behaviour. They define the term anomaly as identifiable patterns in data that do not conform to a well-defined notion of normal within a twodimensional dataset.

This can be visualised in [Fig. 4.7](#chapter4.xhtml#fig4.7) which depicts a typical pointbased anomaly approach.

N1 and N2 represent the baseline data areas that have been identified as normal behaviour. T1, T2, T3 and T4 are classed as anomalies (potential threats) as they fall outside of the boundaries of the baseline areas denoted by N1 and N2.

![image](images/fig4.7.jpg)

**Fig. 4.7.**`Point-based anomaly approach` (source: `Chandola et al.` (2009)).

A simple example of a point-based anomaly could be a bank account, where N1 and N2 represent normal spending patterns. T1, T2, T3 and T4 represent abnormally high spending patterns, or spending outside of normal geographical locations.

Whilst this could be considered a simple example, it does demonstrate how pattern analysis can be used to detect spurious patterns and how it has real-life applications. The detection of anomalies in credit card transaction data could indicate credit card or identity theft (`Aleskerov et al., 1997`). The anomalous patterns within an MRI image may indicate the presence of malignant tumours (`Spence et al., 2001`).

### 4.5.5.*Contextual-based anomalies*

Contextual or conditional (Song *et al.*, 2007) data is anomalous but only in a specific context. In other ways the data may conform to normal behaviour. The contextual attribute of the data will determine if it represents abnormal or normal behaviour.

Contextual anomalies are defined through two attributes:

•`Contextual`Determines the context or location of that instance. As an example, in geospatial data, latitude and longitude could be used as contextual attributes.

•`Behavioural`The behavioural attributes of a data set could be defined as the non-contextual characteristics of each specific instance. As an example, in a spatial data set representing global average temperatures, the temperature of a city would be considered behavioural.

[Figure 4.8](#chapter4.xhtml#fig4.8) depicts a graph demonstrating contextual abnormality within a temperature time period.

The temperature (data) is the same in T1 and T2; the context of that data within the different time periods has an impact when determining if the data is abnormal for the season. T1 is normal but T2 can be seen as an anomaly for the time of year.

### 4.5.6.**Collective anomalies**

If a collection of related data instances is anomalous with respect to the entire data set, it is termed a collective anomaly. The individual data instances in a collective anomaly may not be anomalies by themselves, but their occurrence together as a collection is anomalous (`Chandola et al., 2009`). This does not imply that individual data sets are anomalies, but that their occurrence collectively with other data sets can be classified as an anomaly.

As an example, during August 2017, Dakota’s access control logs displayed an unusual increase in staff located on the 3^(rd) floor visiting other floors, and in particular the floor directly below. The data was analysed and the entry point used by the vast majority of staff was to the right of the elevator. Under closer inspection the log data also appeared to only affect male members of staff.

The issue was quickly identified. The male toilets on the 3^(rd) floor were unavailable for 24 hours so staff had to use the facilities on other floors. The toilet was also located to the right of the elevator, so staff used this access point.

A single observation (member of staff) visiting another floor is not unusual, but a collective data set (multiple staff) could be considered anomalous and can be classed as a collective anomaly.

### 4.6.Threat Model and Algorithm

The primary objective of this research paper is to reduce the risk posed by an insider through the development of a robust threat detection model which incorporates an effective and tested algorithm.

Dakota’s recently implemented proximity monitoring solution provides a constant stream of human movement data that is interpreted and processed within a dedicated security server.

Whilst Dakota security personnel are able to selectively monitor movement of the Bluetooth security badges, Dakota senior management believe it is not cost-effective to deploy a team of dedicated security staff to permanently monitor the movement of 50 separate individual contractors. It is also believed impractical for security personnel to understand the regular movement patterns of contract staff, their working practises and the specific zones in which they operate.

Leveraging data obtained from the Bluetooth proximity monitoring solution, a purpose-built application has been constructed to process the data using an algorithm that determines the threat posture of each individual contractor.

### 4.6.1.*Extracting the data*

The proximity solution is provided by Zonith, a Danish-based security solution provider who specialises in security, alarm handling and notification solutions (`Zonith, 2018`). Zonith’s proximity solution is based around generic hardware components that are not vendor-specific.

The Zonith solution comprises adapted Bluetooth Beacons, Bluetooth enabled devices (including Bluetooth security badges) and the Zonith application. The Zonith application is known as the Real Time Location Solution (RTLS), and incorporates customised schematics of the client office space. Dakota have preloaded a plan for each of the floors it occupies within its London headquarters.

RTLS is hosted on a single dedicated security server, running Windows 2016. The front-end application is delivered through an Internet browser environment using an Apache Tomcat server. The data is stored on a dedicated proprietary database, which is located on the same server (`Project, 2018`).

![image](images/fig4.9.jpg)

**Fig. 4.9.**`Zonith RTLS`.

Data is fed from the Bluetooth-enabled ID badge to the beacon. This is then sent to the RTLS server and stored onto the embedded database. [Figure 4.9](#chapter4.xhtml#fig4.9) outlines this process.

After analysis of the data provided by the RTLS system, it was discovered that in its native format the data was not sufficient to construct time analysis. Additionally, the native data set did not provide the sequence number that would be required for time calculation or movement profiling.

Sufficient data from all the job roles was therefore required to provide a baseline for the algorithm. To achieve this an extraction of two months’ historic data was analysed to determine recognised movement patterns and anomalies within the data set.
