## 12.2 BACKGROUND OF IIoT

This section mainly focuses on the framework and architecture, and communication protocol and enabling technologies of IIoT.

### 12.2.1 FRAMEWORK AND ARCHITECTURE OF IIoT

Campobello et al. [11] suggested Wireless EVolution for Automation (WEVA) as an IIoT solution. It is based on communication protocols and open source software. Its architecture consists of applications, services, sensors, actuator boards, protocols, access gateway and motes, and operating system. Easy wireless sensor network (WSN) is used by WEVA like a tool for graphical management. Author suggested IPv6 for flexibility in IIoT. However, incorporating network technologies to achieve a high-performance IIoT is not an easy job. A solution is however proposed by many researchers; they address an issue of high performance and ignore WSN integration which in industrial application plays an important role.

Lee et al. [12] suggested an IIoT suite to attain reindustrialization, conveying various challenges of instance object locations in all the manufacturing processes and their identification in real time, and to establish a system of network that allows communication of the object with the other objects in real time and network. The cloud platform and smart hub are the main components of IIoT. Smart hub acts as an entrance of IoT devices, and also at different locations it manages IoT devices. Smart hub focuses on accomplishing three tasks. First, it helps to facilitate data processing, data exchange, and communication in IoT devices. Second, when scaling a system with latest devices of IoT, it provides appropriate solutions. Third, a channel with secure connection is provided in-between the cloud platform and IoT devices by performing formatting, filtering, data collection, and aggregation. The IoT cloud platform behaves as the brain of the IIoT suite. It is also accountable for performing load balancing, identity and access management, controlling IoT devices, device configuration, monitoring, and routing algorithms.

Khan et al. [13] suggested architecture based on IoT for monitoring and controlling the gas and oil industry operations. This architecture consists of three modules that include control center, gateway, and smart object. All the modules execute a unique functionality which comprises three layers that include a network layer, sensing layer, and application layer. These smart objects have different types of sensors for the detection of various events like fire and leaks. Sensed data from smart objects are then sent to the control system which comprises databases for management applications, storage of data, data analysis, interfaces of smart object, and tools of data visualization.

The configuration, exchange among the heterogeneous IIoT devices, and deployment are some major issues. To handle such issues, Tao et al. [14] suggested a hub based IIoT known as IIHUB. It includes three modules. The first module is known as customized access module (CA-Module), accountable for the connection of the heterogeneous devices known as physical manufacturing resources (PMRs) by a group of some of the communication protocols. Access Hub (A-Hub) is the second module and acts as a link between the smart terminals, CA-Module, and factory worker via Wi-Fi and some constrained application protocol. Smart terminals or local pool service (LPS) is the third and one of the main modules. LPS performs various tasks and is accountable for smart decision-making, data collection, storing, and processing. On the basis of the data that are produced by PMRs, LPS carries out real-time data processing and estimates the consumption of total energy, predicted maintenance of PMRs, and expected production rate.

### 12.2.2 IIoT COMMUNICATION PROTOCOLS

In this section, we originate a taxonomy presenting the different communication protocols in IIoT. This section also introduces all the communication protocols and their vulnerabilities.

#### 12.2.2.1 Modbus

It is one of the most frequently used protocols in SCADA systems. In this protocol, the communication is established on master–slave configuration and is serial. Master is the device that is seeking the information, while slave is the one that is providing the information. Data can also be written by the master on the memory register of slave. In standard Modbus network, a master can have 247 slaves, each of them having a unique identification code. Slave device has four tables to store data: two for the numerical analog data and two for storing digital data. Modbus traffic is conveyed in unencrypted text; therefore, it lacks confidentiality. Any private or public key management is not provided by it, thus no authentication is present. Also, the lack of sufficient security mechanism makes it easier for the attacker to manage the probity of the data.

#### 12.2.2.2 BACnet

It was initially designed for control systems and building automation. This standard is a part of ASHRAE Standing Standard Project Committee 135. Like most of the industrial communication protocols, it was not built with a security perspective. This standard delivers many communication options, for example, master–slave, token-passing, Ethernet, and point-to-point. This protocol does not have authentication policy and also lacks proper mechanisms for confidentiality of data, which makes reconnaissance attack feasible. Some cryptography mechanisms like advanced encryption standard and data encryption standard are included in the new versions in BACnet standard. In general, encryption adds large overheads and communication delays in the system; therefore, they are almost never used in industrial systems. The scan cycle times of human machine interface (HMI) and programmable logic controller (PLC) are normally in the order of milliseconds, and since decryption and encryption of data take longer time, it is not feasible yet. Also denial of service (DoS) attacks could be used to halt the service and also target system availability.

#### 12.2.2.3 DNP3

It is a further standard protocol that is applied in systems of SCADA. It does not provide any sufficient security mechanism; therefore, most of the devices of DNP3 lack encryption, authentication, and access control. There are four OSI (open systems interconnections) layers in DNP3: physical layer, application layer, data link layer, and network layer. Communication occurs in master–slave configuration with multiple masters and multiple slaves; it can also occur in a point-to-point mode. The message authentication is not established in this protocol, and thus it puts the integrity of data at risk. Spoofing and eavesdropping are easy since there is no encryption in data.
