# Service Meshes

Service meshes shift the needs of reliability, observability, routing, and error handling away from each process to separate out-of-process infrastructure. This new infrastructure is portable and independent of any specific programming languages and frameworks selected by each process, making it portable. Service meshes have grown in popularity due to the introduction of microservices may be used for any architecture or combination of architectural styles.

Service meshes replace the direct communication of processes with a series of proxies that direct the communication and error handling on behalf of the process. A proxy is deployed alongside running process to eliminate any central point of failure. Deployment is to a single virtual machine (VM) or alongside each container as a sidecar. A centralized management control plane is used to configure the proxies, communicate outages, and oversee the network health. The controller, however, does not involve itself with network data communications.

Service meshes may be seen as a competitor to API gateways and APIMs. However, while service meshes manage on OSI layer 4 (TCP/IP) and OSI layer 7 (HTTP), they are often paired with an API gateway or APIM. This offers the best of worlds by providing resilient network communications using a service mesh, with API product and lifecycle management offered by APIM or API gateway.

Service meshes introduce additional network hops and may have a negative impact on network performance. However, the capabilities offered by a service mesh offset the negative impact and may produce a net gain when factoring in the many separate network management elements that have to be coordinated when a service mesh is not present.

Finally, be in mind that smaller organizations may not see the need for the added complexity of a service mesh. However, larger organizations managing many developer teams producing a multitude of services across one or more cloud environments may benefit from the use of a service mesh.
