While GraphQL is popular with frontend developers, it has also gained significant traction across enterprises as a means to stitch REST APIs together into a single query-based API. It is also useful for producing query-reporting APIs alongside REST-based APIs, offering a best-of-breed approach to API platforms.

Many of the challenges around GraphQL are centered on its choice to tunnel through a single endpoint rather than take advantage of the full capabilities of HTTP. This prevents use of HTTP content negotiation for the support of multiple media types beyond JSON. It also prevents the use of concurrency controls and optimistic locking offered by HTTP conditional headers. Similar challenges were experienced with SOAP-based services, which was designed to work across multiple protocols including HTTP, SMTP, and JMS-based message brokers.

Enforcing authorization is also a challenge because traditional API gateways that enforce access control by URL are limited to the single GraphQL operation. However, some API gateways are extending their capabilities to include authorization enforcement around GraphQL queries and mutations. Likewise, rate limiting, often associated with a combination of path and HTTP method, must be rethought to accommodate this new interaction style.
