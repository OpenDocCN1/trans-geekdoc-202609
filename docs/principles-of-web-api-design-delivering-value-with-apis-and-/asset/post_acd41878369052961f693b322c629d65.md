# Customizing the Process

Remember that EventStorming is a tool that offers discovery-based learning in a collaborative environment. Customizing the process helps organizations gain the most from sessions. The following additions or modifications have been explored beyond the original process suggested by Brandolini.

- **The three-lane approach:** Rather than a single sheet of paper covering the wall, using narrow paper allows for creating three separate lanes in parallel. All initial events are attached to the top line during business event identification. When ordering them into a narrative, the events are moved to the middle lane. The top line is then used to expand the available space when expanding the canvas with new sticky notes beyond the initial business events. The bottom line is used as a "parking lot" for events considered out of scope or identified as duplicate. This approach was built out of necessity, as the only available paper rolls from an organization’s supply closet were only 12 inches (30 cm) high.

- **45-degree sticky notes:** When a note is clear, needs to be rewritten into past tense, or is revisited for another reason, anyone is empowered to tilt a sticky note at a 45-degree angle. This flags the note for follow-up before proceeding to the next step of the process.

- **Multipart EventStorming sessions:** With the introduction of remote sessions, fatigue often sets in more quickly than with high-energy in-person sessions. In this case, consider breaking an EventStorming session into multiple parts that take more than two hours before a one-hour break. If necessary, a session may be spread across two days as long as all attendees will be available to participate both days.

- **Shared facilitation:** The facilitator is encouraged to ask different people to lead the narration/storytelling effort. Shared facilitation encourages ownership of the session, keeps team members engaged and away from email, and helps cross-train others in the EventStorming process. The facilitator demonstrates, facilitates for a time, then asks for a volunteer or selects someone to facilitate a portion of the process. This continues until everyone has had a chance to facilitate some portion of the session. During the activity, the original facilitator remains available and coaches everyone as needed.

# Avoiding API Boundary Antipatterns

It is important to clarify the intent and scope of an API. Identifying the scope and responsibility of an API also helps guide the design of this mental model, contributing to a more positive developer experience. Without a clear set of responsibilities, APIs will suffer from common antipatterns.

# The Mega All-in-One Antipattern

Even the most experienced API designers are faced with challenges when a single API tries to do everything. Creating a large API product makes it difficult for developers to find what they need. The lack of scope and responsibility of the API makes the developer confused and unable to use it effectively.

# The Overloaded API Antipattern

In larger organizations, a single team may become responsible for most of the API through this incorrect assumption that a single API is the best way to organize support across the book catalog, inventory, shopping, and fulfillment processes. The velocity of delivery is greatly reduced as the remainder of the organization waits for the single team to add the operations needed to support new functionality.

# The Fragmentation Antipattern

What starts as a well-intentioned goal eventually leads to many small APIs that are scattered all over the codebase.

# AVOIDING API BOUNDARY ANTIPTERNS

In the bookstore example, *books* could imply one of several contexts:

- Books that are entries in the catalog
- Books available as part of the warehouse inventory
- Books added to a shopping cart
- Books that are part of a placed order
- Books that have been shipped as part of an order

Creating a single API is likely not the best route to clarity or sanity. API changes would become constant as new contexts around the term *books* are introduced. The result would be operations that mix and match the term in different ways until the API becomes a confusing mess.

Instead, to clarify single-word terms such as *book* with more context. For example, a Books Catalog API helps to limit the scope of API operations to those involved in catalog management. Within this clearly defined scope are additional responsibilities, including managing public descriptions, associated metadata to each book, book covers, sample chapters, and more. Only those interested in catalog management need to work with this API.

# The Helper API Antipattern

Nearly every development team has built a helper library. This library is a mixture of utilities that are scattered all over the codebase. The namespace used to store the helpers (e.g., `com.mycompany.util`) is referenced over all the codebase.

Some APIs suffer the same challenges as the sad, overused helper API. These APIs that have a mixture of uses but aren't cohesive as a unit. Developers integrating with the API struggle to understand when and where to apply each one.
