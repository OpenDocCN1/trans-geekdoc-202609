the specific properties that changed when an update occurred to help consumers
determine the event is of interest.

# Event-Carried State Transfer Events

Event-carried state transfer events contain all available information at the time of the
event. This avoids the need to contact an API for the complete resource representation,
though additional APIs may be used to augment the data required by the subscriber
to perform any processing.

There are a few reasons why event-carried state transfer may be preferred over
inthin events:

+   - Subscribers watch a snapshot of the resource associated with the event rather
than the few details and associated multimedia links offered by thin events.
- Data state changes using messaging streaming to support replaying message
history, requiring a complete point-in-time snapshot of a resource.
- Messaging via async API is used for interservice communication, requiring
t publication of a full resource representation to avoid increased API traffic
and tighter coupling between services.

It is common for this style of message design to mimic API representation
structures whenever possible. Deviation is common when the event must offer the
old and values of any modified properties on an update event.

Finally, use nested rather flat structures to group related properties for
medium-to-large payloads. This helps drive evolability, as property names are
scoped to the parent property, avoiding property name collisions or long property
names to clarify relationships. The following is a demonstration of a flat structure to
event-carried state transfer message styles.

```
{
"eventType": "customerAddress.updated",
"eventId": "123e4567",
"updatedAt": "2020-01-14T03:56:45Z",
"customerId": "330001003",
"previousBillingAddressLine1": "...",
"previousBillingAddressLine2": "...",
"previousBillingAddressCity": "...",
"previousBillingAddressState": "...",
```
