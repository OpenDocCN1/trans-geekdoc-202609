As shown in Figure 10.8, the pattern shows an example of a file upload or a Pub/Sub message triggering an Eventarc trigger. Based on the event, a cloud function will be triggered that will start the Cloud DLP scan.

+   * Provide necessary permissions to the service account: Cloud DLP creates service agent accounts by default, which will have the necessary permissions to run Cloud DLP scan jobs. Alternatively, if you are scanning a restricted table or file, the relevant IAM roles must be added to the Cloud DLP service account. If you are using a Cloud Function or Cloud Run instance to trigger Cloud DLP jobs, those service accounts must have the `dlp.jobTriggers` permission to successfully start the Cloud DLP scan job.
* Publish Cloud DLP tags to Data Catalog: Once the classification is complete, the results are sent to Data Catalog so that the tables are tagged, only the right people get access to the data, and any sensitive data is protected. Cloud DLP allows native integration with the Data Catalog, so once we scan the BigQuery tables, it can send the tagging results to Data Catalog in the form of tag templates. The findings will be included in the summary form for the table in Data Catalog.
* Restrict access prior to running Cloud DLP scans: Access to any BigQuery tables must be restricted until the Cloud DLP profiling is complete. To achieve this goal, the Cloud DLP profiler must be enabled, and only after it passes the policy checks should the data assets be moved to a state where quarantine can be added to policy tags for all new tables so that users won't have access. Once Cloud DLP identifies sensitive data, a policy tag can be created in the form of a hierarchy of high, medium, and low to further restrict access depending on the content Cloud DLP identifies.
