Figure 8.20 – Cloud Armor deployment models

We will use 8.20 to look at the deployment models:

- Cloud Armor supports the protection of Cloud Content Delivery Network (CDN) origin servers by enforcing Cloud Armor security policies on dynamic requests as well as cache misses missed by the CDN origin server. Most applications are often complex, serving both cacheable static content and dynamic requests from the same services. Cloud Armor is a security service that can protect websites and applications from malicious attacks. It is able to inspect and filter requests that are sent to the origin servers of CDN. This helps to prevent so-called cache-buster attacks, which are attempts to bypass the cache and force the origin servers to send updated content. Additionally, Cloud Armor can help protect dynamic portions of websites and applications from the 10 most common security vulnerabilities as defined by OWASP.

- There is often a need to enforce a consistent set of security controls to applications no matter where they are deployed, whether they are migrating to Google Cloud or running in a hybrid configuration. With internet Network Endpoint Groups (NEGs), you can leverage all of Google’s edge infrastructure, including global load balancers, Cloud CDN, and Cloud Armor, to protect your website or applications no matter where they are hosted. Cloud Armor can help protect your applications, from DDoS attacks or other common web attacks, without you having to deploy your applications on Google Cloud.

Note
NEGs do not fall within the scope of the exam. You can refer to the Further reading section to read more about NEGs and how to configure them.

- With GKE Ingress support for Cloud Armor, you can protect your containerized workloads by placing them behind Google's global load balancers and configuring Cloud Armor security policies for Layer 7 filtering and WAF use cases.

## Security policies

In Cloud Armor, you can build security policies that help you defend applications operating behind a load balancer against DDoS and other web-based attacks, regardless of whether the apps are deployed on Google Cloud or in a hybrid or multi-cloud architecture. It is possible to stop traffic before it reaches your load-balanced backend services and buckets using security policies filter Layer 3 and Layer 7 requests for common exploits. An IP address, an IP range, a region code, and request headers are only a few examples of the conditions used to filter traffic by security policies.

## Google Cloud Armor 215

Use Cloud Armor custom rules to define expressions in the match condition of one or more. When Cloud Armor receives a request, it analyzes it against the following. Depending on whether the rules are met, inbound traffic is either denied or allowed. There are some instances of Cloud Armor expressions written in Common Expression Language (CEL):

- To define expressions in a rule, use the gcloud --expression flag or the Google Cloud console.

- In the following example, requests from 2001:db8::32 in the AU region match the following expression:

```
origin.region_code == "AU" && inRange(origin.ip, 2001:db8::32);
```

- The following example matches requests from 192.0.2.0/24 and with a user agent that contains the string WordPress:

```
inRange(origin.ip, '192.0.2.0/24') && has(request, headers['user-agent']) && request.headers['user-agent'] contains('WordPress')
```

## WAF rules

In this section, we look at the different types of rules you can create. There are some WAF rules that can be pre-configured, but you have the option of creating custom rules to meet your requirements. Let's look at the options available.

You can create IP-address-based rules both at the edge and for your backend services. These rules are the IP address allowlist- and denylist-based rules. Both ipv4 and ipv6 are supported. HTTP 403 (Unauthorized), 404 (Access Denied), and 502 (Bad Gateway) responses are all possible outcomes of denies. An HTTP 429 is an error code that is returned when an application has exceeded a number of requests. This is usually caused by an action rule that limits the number of requests that can be made in a given period of time.

There are pre-configured rules based on the OWASP ModSecurity rule set version 3.0. These rules can provide you with protection from the following types of attacks:

- SQL injection

- Cross-site scripting (XSS) attacks

- Local file inclusion (LFI) attacks
- Remote file inclusion (RFI) attacks
- Remote code execution (RCE)
