## Best practices and design considerations

In this section, we will look at some VPC best practices and design considerations that you need to factor in when designing and building your secure network on Google Cloud. From an exam perspective, it is important to understand these as you will find questions about best practices.

## VPC best practices

For VPC, some of the best practices include the following:

- Prevent overlapping IPs and control subnet creation by creating VPC networks using custom subnet creation.
- Reduce management and topology complexity by making use of Shared VPC where possible.
- Group similar applications into fewer, more manageable, and larger subnets.

## Virtual Private Cloud

- Apply organization policies to do the following:
  - Skip the creation of default networks for new projects.
  - Restrict shared VPC projects and subnets.
  - Restrict VPC peering usage.
- Ensure the design scales to your needs by considering the limitations of each network component.

## Key decisions

Some of the key decisions you need to make include in the following:

- How will your Google Cloud resources communicate with each other? Will it involve VPC design or Shared VPC?
  - How will resources be segmented into networks and subnets? Will there be micro-segmentation?
  - How will name resolution be solved among cloud resources and between the cloud and connected environments? Will Cloud DNS and DNSSEC be factored into your public zones?
  - What strategies will be used to connect Google Cloud with corporate networks? Will you use hybrid connectivity options?
  - How will your resources communicate with the internet? Will you use external load balancing Global or regional?

It is important not just to understand best practices but also to consider answering the preceding questions around design considerations, which will help you define requirements and build a resilient and secure network on Google Cloud and across your hybrid network.

## Private Google Access

Private Google Access addresses the challenge where you want virtual machines (VMs)/Google Compute Engine (GCE) instances that do not have external IP addresses but addresses to access Google APIs. Instances without public IP addresses cannot access Google Cloud's public API endpoints – but the Private Access service enables that capability. Let's look at some use cases on why Private Google Access is required.

## Advanced Network Security

VMs often have to communicate with managed services, for example Cloud Storage, BigQuery, and GCE. An external IP address is not assigned to the VM to access Google APIs. When connecting via Virtual Private Network (VPN) or Cloud Interconnect, Private Access allows access to Google endpoints without requiring an external IP.

## Figure 8.1 – Private Access

Private Google Access is enabled on a subnet-by-subnet basis. Let’s consider an example where you have two subnets (subnet-a and subnet-b) inside a VPC with four VMs. Subnet-a has Private Access enabled and subnet-b does not. VM1 and VM2 are in subnet-a and VM3 and VM4 are in subnet-b. Based on these settings:

- VM1 can access Google APIs as it is part of subnet-a with Private Access.
- VM3 has a private address but is inside subnet-b, which does not have Private Access; therefore, it cannot access Google APIs.
- VM2 and VM4 both have external IP addresses and therefore are able to access Google APIs regardless of whether they are in a subnet with enabled.
