
## Import a key (BYOK)

- In addition to these options, make sure you follow these guidelines as well:

- Verify that your key's algorithm and length are supported by Google Cloud KMS. Allowable algorithms for a key depend on whether the key is used for symmetric encryption, asymmetric encryption, or asymmetric signing, and whether it is stored in software or an HSM. You will specify the key's algorithm as part of the import request.

- Separately, you must also verify how the key is encoded, and adjust if necessary.

Now let us start with the instructions on importing keys to Google Cloud. For simplicity, we will use gcloud.

## Step 1: Creating a blank key

- 1. Create a project in the Google Cloud console, and enable Cloud KMS.

- 2. If you do not have a key to import but want to test importing keys, you can create a symmetric key on the local system, using the following command:

```bash
openssl rand 32 > ${HOME}/test.bin
```

> Note
> Use this key for testing only. A key created this way might not be appropriate for production use.

- 3. Create a new key in a region of your choice.

- 4. Create a new key of type imported key by using the following parameters:

I. Name: ext-key-3
II. Protection Level: Software
III. Purpose: Symmetric encrypt/decrypt
IV. Rotation Period: Manual

- 5. An empty key created with no version; you will be redirected to create a key version.

- 6. Use the following gcloud command to create the key version. We will be creating a symmetric key:

```bash
gcloud kms keys create-key-4 --location us-central \
--keyring external-central-key-ring --purpose encryption \
--skip-initial-version-creation
```

- 7. Create a new import job.

- 8. Download the wrapping key.

This key will not be available for yet since it is an empty shell to hold the key material that you will import in the following steps. Now, you have two options:

- Upload your pre-wrapped encryption key.

- Use the gcloud command to provide your key to the job, which will automatically wrap it. You will use different flags to make the import request, depending on whether you want the gcloud command-line-tool to wrap your key automatically or if you have wrapped your key manually. We will use the gcloud option as it is simple to understand.

## Step 2: Importing the key using an import job

- 1. Set export CLOUDSDK_PYTHON_SITEPACKAGES=1, otherwise, you will see the following error:

Cannot load the Pyca cryptography library. Either the library is not installed, or site packages are not enabled for the Google Cloud SDK. Please consult https://cloud.google.com/kms/docs/crypto for further instructions.

- 2. Make sure the preceding environment variable is set by your command:

```bash
echo $CLOUDSDK_PYTHON_SITEPACKAGES
```

- 3. Execute the command to upload your key to Cloud KMS:

```bash
user@cloudshell:~ $ gcloud kms keys versions import --import-job ext-key-import-job --location us-central --keyring external-central-key-name --ext-key-4 --algorithm google-symmetric-encryption --target-file ${HOME}/test.bin --public-key-file /home/user/ext-key-import-job pub --verbosity info
```

Now you will see output about what is shown:

```
INFO: Display format: "default"
algorithm: GOOGLE_SYMMETRIC_ENCRYPTION
createTime: "2020-04-08T22:25:46.597631370Z"
importJob: projects/PROJECT_ID/locations/us-central/keyRings/central-key-name/importJobs/ext-key-import-job
name: projects/PROJECT_ID/locations/us-central/keyRings/external-central-key-name/cryptoKeys/ext-key-1/
protectionLevel: SOFTWARE
state: PENDING_IMPORT
```

- 4. Wait until the key version in the ENABLED state, then set it to primary using the following gcloud command:

```bash
gcloud kms keys set-primary-version ext-key-1 --version=1 \
  --keyring=external-central-key-name --location=us-central1
```

Cloud KMS will only use the primary version of the key. Now that you have set it, let us move on using it.

## Step 3: Verifying key encryption and decryption

- 1. Create a secrets.txt file with some plain text in it. Encrypt it using gcloud:

```bash
gcloud kms encrypt --ciphertext-file=secrets.txt.enc \
  --plaintext-file=secrets.txt --key=ext-key-4 --keyring=external-central-key-name --location=us-central1
```

- 2. Now use the following command to decrypt it using the same key:

```bash
gcloud kms decrypt --ciphertext-file=secrets.txt \
  --plaintext-file=secrets.txt.dec --key=ext-key-1 \
  --keyring=external-central-key-name --location=us-central1
```

Verify that you have decrypted is the same as the plain text. This tutorial demonstrated that you can bring your own key material for it encryption and decryption.

Now that we understand several types of keys you can use in Cloud KMS, let us understand the lifecycle of keys.

## Key lifecycle management

While operating your workloads, you need to manage the lifecycle of your keys. US National Information Standards Institute (NIST) special publication (SP) 800-57, Part 1 describes a key management lifecycle that is divided into four phases: pre-operational, operational, post-operational, and destroyed.

The following section provides a mapping of the NIST lifecycle functions from the publication to Google Cloud KMS lifecycle functions.

- 1. The Pre-operational lifecycle phase is mapped to the following:

- I. NIST 8.1.4 Keying-Material Installation Function: The equivalent Cloud KMS operation is Key import.

- II. NIST 8.1.5 Key Establishment Function: The equivalent Cloud KMS operation is Key creation (symmetric, asymmetric).

- 2. The Operational lifecycle phase is mapped to the following:

- I. NIST section 8.2.1 Normal Operational Storage Function: The equivalent Cloud KMS operation is Key creation in SOFTWARE, HSM, or EXTERNAL protection levels (symmetric, asymmetric).

- II. NIST section 8.2.3 Key Change Function: The equivalent Cloud KMS operation is Key rotation.

- 3. The Post-operational lifecycle phase is mapped to the following:

- I. NIST section 8.3.4 Key Destruction Function: The equivalent Cloud KMS operation is Key destruction (and recovery).

In addition, Cloud KMS offers the capability to disable the key. You can re-enable the key if you discover it needs to. To grant broad administrative access without the ability to encrypt or decrypt, grant the Cloud KMS Admin (roles/cloudkms.admin) role instead. 

Recall that there are two fundamental principles IAM enforces:

- Principle of separation of duties
- Principle of least privilege

We have looked at various roles and permissions for Cloud KMS; let us now look at some best practices on how to manage:

- For a small organization, each project team can manage its own Cloud KMS and the security team.
- For a large or complex organization, you might decide on an approach such as the following:

## Cloud HSM

- Grant members of your security team the Cloud KMS Admin (roles/cloudkms.admin) across all projects. If different team handle various aspects of a key, you can grant them a more granular role, such as the Cloud KMS Importer role (roles/cloudkms.importer).

- Grant the Cloud KMS Encrypter/Decrypter role (roles/cloudkms.cryptKeyEncrypterDecpter) to users or service accounts that can read or write encrypted data.

- Grant the Cloud KMS Public Viewer role (roles/cloudkms.publicKeyViewer) to users or service accounts that need to view the public portion of a key used for asymmetric encryption.

- For projects using the VPC Service Controls perimeter, we recommend that you have a separate Cloud KMS project for the perimeter.

Cloud HSM is a cloud-hosted HSM service that allows you to host encryption keys and perform cryptographic operations in a cluster of FIPS 140-2 Level 3 certified HSMs. The Cloud HSM cluster is managed by Google for you; you do not get access to the physical device. You do not need to patch or scale it for multi-regional applications. Cloud HSM uses Cloud KMS as its frontend to interact with the Cloud HSM backend. This abstracts the communication with Cloud HSM, so you do not need to use Cloud HSM-specific code.
