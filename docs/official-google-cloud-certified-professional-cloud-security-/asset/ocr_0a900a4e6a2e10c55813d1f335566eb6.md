# Cloud Data Loss Prevention

Using hybrid jobs, Cloud DLP can inspect data sent to it from any of these sources. Example scenarios include the following:

+   - Inspect stored data in Amazon Relational Database Service (RDS), MySQL running inside a virtual machine, or an on-premises database
- Inspect and tokenize data as you migrate from on-premises to the cloud, or between production, development, and analytics
- Inspect and de-identify transactions from a web or mobile application before storing the data at rest

The basic workflow for hybrid jobs and triggers is as follows:

+   - You write a script or create a workflow that sends data to Cloud DLP for inspection along with some metadata.
- You configure and create a hybrid job resource or trigger and enable it to activate when it receives data.
- Your script or workflow runs on the client side and sends data to Cloud DLP. The data includes an activation message and the job's identifier, which triggers the inspection.
- Cloud DLP inspects the data according to the criteria you set in the hybrid job or trigger.
- Cloud DLP saves the results of the scan to the hybrid job resource, along with the metadata that you provide. You can examine the results using the Cloud DLP UI in the Console.
- Optionally, Cloud DLP can run post-scan actions, such as saving inspection results to a BigQuery table or notifying you by email or Pub/Sub.

A hybrid job enables you to create, activate, and stop jobs so that you can trigger actions whenever you need them. By ensuring that your script or code sends data that includes the hybrid job's identifier, you don't need to update your script or code whenever a new job is started.

# DLP infoTypes

Information types, also known as infoTypes, are sensitive data kinds that Cloud DLP is preconfigured to scan and identify—for instance, US Security numbers, credit card numbers, phone numbers, zip codes, and names. Built-in and custom InfoTypes are supported by Cloud DLP.
