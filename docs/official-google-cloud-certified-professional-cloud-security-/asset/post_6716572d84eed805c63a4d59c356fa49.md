
## Load balancers

Let us start by looking at the different types of load balancers:

- **Global HTTP(S) load balancer:** This load balancer handles both HTTP and HTTPS traffic is a proxy-based Layer 7 function that caters to your services and is configured behind a single external IP address. It can service traffic to different types of Google Cloud services as backends, such as Google Compute Engine, Google GKE, and Cloud Storage. You can use an external HTTP(S) load balancer to distribute and manage traffic for your hybrid workloads in an on-premises environment as well. This load balancer is implemented on Google Front End (GFE) and is global when using Premium Tier but can be configured to regional using Standard Tier.

- **Regional TCP/UDP load balancer:** This is also referred to as a regional network load balancer and is configured as a pass-through. It balances the traffic for VMs in the same region. This is offered as a managed service and can cater to any client on the internet, using Google Compute Engine (NAT). With an external IP address and clients using Cloud Network Address Translation, this load balancer is not a proxy, and it distributes traffic to the backend VMs at the packet's source and destination IP address and protocol. The traffic is terminated directly to the client and not through the load balancer.

- **SSL proxy load balancer (global):** This is a reverse proxy load balancer that distributes SSL traffic to the nearest backend VMs. The SSL proxy load balancer terminating the TLS requests and forwards the traffic to the backend VM as TLS or TCP. With the HTTP(S) load balancer, based on the network tier, you can configure the SSL proxy load balancer by using Premium Tier or configure it to be regional if using Standard Tier. Both IPv4 and IPv6 are supported, and the traffic is intelligently routed to the backends based on capacity. Self-managed and Google-managed certificates are supported. You can also control the SSL features on the load balancer by configuring SSL policies.

- **TCP proxy load balancer (global):** This is a reverse proxy load balancer, and it distributes the traffic to the VMs as globally inside the Google Cloud VPC network. It uses a single external IP address for all users globally. All TCP traffic coming from the external is terminated at the load balancer and can be routed to the VMs as TCP or SSL. With this load balancer, you can have global load balancing if using Premium Tier or regional load balancer if using Standard Tier.

- **Internal TCP/UDP load balancer:** This load balancer distributes traffic to your internal VMs within the region in a VPC. A typical use case is using internal load balancers in a three-tier web architecture, where they can be deployed with an external load balancer. In this architecture, you will have an external HTTP(S) load balancer in front of your web servers and then have internal load balancers behind the web servers to cater and scale traffic to your VMs, which are private and only accessible within the VPC.

- **Internal HTTP(S) load balancer:** An internal HTTP(S) load balancer is a regional proxy-based Layer 7 load balancer. Using this load balancer, you can distribute traffic to backend services such as Compute Engine and GKE. The internal load balancer is built on Envoy.

Now we will look at some important distinctions, such as external versus internal and when to use what load balancer. Google Cloud balancers are of two types: external or internal. You will use an external load balancer if you have traffic coming from the internet to access services in your Google Cloud VPC. An internal load balancer, on the other hand, is only used when you need to load balance traffic to VMs that are private and only accessible within the VPC.

Another aspect to understand is when to use global versus regional balancers. A global load balancer will manage and distribute traffic coming from the internet to backends distributed across multiple regions. Users only interact with one same unicast IP address, and a global load balancer can distribute traffic to the closest backend location. Premium Tier is a requirement for global load balancer. Regional balancers, however, are used when you have a requirement to keep your traffic limited to backends in a particular region. For this type of load balancer, you can use Standard Tier.

## Hybrid connectivity options

Throughout this chapter, we have made references to hybrid connectivity. The term hybrid connectivity means that you can join your Google Cloud network to on-premises network and a third-party cloud provider using multiple connectivity options. We will look at two options: Cloud VPN (IPSec) and Cloud Interconnect.

Before we look at the different connectivity options, it is important to understand what Cloud Router is, as it is a key component when creating a Google Cloud-based VPC. Cloud Router is a managed service and a regional resource. It is responsible for exchanging routes between your VPC and your on-premises network via BGP. Dynamic routing options include both regional and global. With regional routing, Cloud Router shares routes only in the region where Cloud Router is provisioned. With global routing, it shares routes for all subnets in the VPC network.

## Virtual Private Cloud

Let us now look at the connectivity options that are available for building hybrid connections with Google Cloud:

- **Cloud VPN (IPSec-based):** Creating a Cloud VPN instance, which is an IPSec-based VPN over the internet, is the fastest and easiest way to connect your cloud environment with other clouds or with your on-premises network. You can leverage your existing internet connection. This option supports a bandwidth of 1.5-3 Gbps per tunnel, depending on peer location or within Google Cloud (Direct peer), with multi-tunnel support for higher bandwidth. A VPN device at the on-premises data center is required to support IPSEC/IKE/Multi-tunnel protocols.

- **Cloud Interconnect:** Using dedicated Cloud Interconnect, you can connect your on-premises network with dedicated private links that do not traverse the public internet. The traffic takes fewer hops and a high level of reliability and security. Your network internal (RFC 1918) IP addresses are directly accessible from your on-premises network. There is no requirement for establishing a VPN or NAT. It supports high bandwidth from 8x10 Gbps, or 2x100 Gbps, depending on the need. You can further reduce your egress costs as traffic remains internal. It works with Private Google Access to allow Google API access through internal links. Although the traffic is unencrypted, you can use a self-managed IPS VPN if that's a requirement. Cloud VPN over Cloud Interconnect is not supported. You can create VLAN attachments and associate them with Cloud Router. You can also attach to multiple VPCs, Cloud Router is used to dynamically exchange routes.
