So far, we have looked at IAM; now we will shift gears and look at access control for Cloud Storage. Cloud Storage is one of the original Google Cloud products and has evolved to have some fine-grained access policies (ACLs), so we will also look at those.

# Cloud Storage ACLs

Cloud Storage provides separate access control in IAM. There are two ways, in fact: a more uniform way of doing access via IAM and a legacy way of doing access via fine-grained ACLs. Object ACLs do not appear in the hierarchy of IAM policies, so please be aware of how your Cloud Storage buckets are controlled. When evaluating how to access one of your objects, make sure you check the ACLs for the object, in addition to checking your project- and bucket-level IAM policies. This could get convoluted, so the recommendation is to use uniform access control using IAM in most cases.

# Access Control Lists (ACLs)

You can use an ACL to determine who has access to your buckets and objects, as well as what level of access they have. ACLs are applied to specific buckets and objects in Cloud Storage. There are one or more entries in each ACL. An entry allows a certain user (or group) to carry out specific tasks. Each entry is made up of two bits of:

+   - A *permission*, defines what actions can be performed (for example, read or write)
- A *scope* (sometimes referred to as a grantee), defines who can perform the specified actions (for example, a specific user or group of users)

Consider the following scenario: you have a bucket from which you want anonymous users to be able to access objects, but you also want your collaborator to be able to add and delete objects from the bucket. Your ACL would be made up of two entries in this case:

+   - In one entry, you would give `READER` permission to a scope of `allUsers`
- In the other entry, you would give `WRITER` permission to the scope of your `collaborator` (there are several ways to specify this person, such as by their email)
