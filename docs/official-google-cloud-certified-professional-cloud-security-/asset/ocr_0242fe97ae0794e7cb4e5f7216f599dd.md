# Best practices for WSS

You should use WSS with caution because it populates fields, buttons, clicks links, and performs other actions. This is especially true if you are scanning production resources. WSS may trigger features that alter the condition of your data or system, resulting in unfavorable outcomes. Here are some best practices:

+   * Use a test environment for scanning: Create a separate App Engine and load your application and there to create a test environment. When you upload your application using the Google Cloud CLI, you can provide the target project as a command-line argument.
* Create a test account: Create a user account with no access to sensitive data or potentially dangerous operations that you do wish to activate. When users log in for the first time, many applications need to go through a unique process, such as accepting terms and creating a profile. A test account for an initial user may have different results than an established user account due to the different workflow. After the first-time flow is complete, scan using an account that is in the typical user state.
* Deactivate UI elements: Apply the no-click CSS class to individual user interface elements that you do not wish to activate. Regardless of whether they are inline JavaScript, attached using addEventListener, or attached by specifying the appropriate event handler property, event handlers attached to this element are not enabled during crawling and testing.
* Use backup data: Before scanning, consider making a backup of your data.
* Exclude URLs: You can exclude patterns from being crawled or tested. See the following link for further details on the syntax: https://packt.link/nldrwr
* Scope of the scan: Before you, check your app for any features that could affect data, users, or systems in ways that go beyond the scope of your scan.
