## Cloud DNS

In this section, we will look at Cloud DNS and how to configure it with some basics. For the exam, you only need basic knowledge of the Cloud DNS topics. We will look at an overview of Cloud DNS and some key components that you need to understand.

Cloud DNS is a highly scalable managed service offered by Google Cloud. You can create both public and private zones using Cloud DNS. Cloud DNS uses an internal metadata server as the DNS resolver for both internal and external resolutions, well as resolving hostnames on the public internet. Every VM instance has a metadata server for querying instance information – for example, name, ID, startup/shutdown scripts, custom metadata, service account, and so – and the DNS resolver is set on VMs as default DHCP (Dynamic Host Configuration Protocol). Overriding leases is possible by customizing the DHCP configuration; however, it is not a common pattern.

Cloud DNS also supports split-horizon, where VMs can be resolved within a private zone or public zone, depending on where the query comes from. For hybrid connectivity, you can use DNS forwarding zones, where you can forward requests to an on-premises resolver.

You can also create DNS peering, allowing you to query zones in different VPC networks. Peering is one-way and no connectivity is required. It supports two levels of depth, meaning that transitive DNS peering across two DNS peers is supported. This is required in a hub-and-spoke model to allow spokes to query their private zones without creating a full-mesh topology.

With Cloud DNS, you can also create a managed reverse zone to prevent non-RFC 1918 address resolutions from being set to the internet. Domain Name System Security Extensions (DNSSEC) is also supported, and we will cover DNSSEC in the next section. You can create resolver policies to configure access to private and restricted Google APIs from within a VPC-SC perimeter. We will cover VPC-SC in Chapter 10, Cloud Data Loss Prevention.

The internal DNS is where the records are automatically created for the VM's primary IP, such as instance.us-west1b.c.projectx.internal. These are used for resolution within the same VPC and project.

In Figure 7.25, you first assign a name to your private zone in the Zone field. Then, specify DNS name, which is the domain name, and then set the DNSSEC option to On. Once completed, click the CREATE button.

In the most basic form, DNSSEC works by including a digital signature in responses to DNS queries. So, for every DNS zone, public and private keys are created. Cloud DNS serves the public key (DNSKEY), resource record signatures (RRSIG), and non-existence (NSEC) records to authenticate your zone. These are automatically managed by Cloud DNS when you have enabled DNSSEC.

An important thing to note is that for DNSSEC to work, your registrar and registry should support DNSSEC for top-level domain. This means that for DNSSEC to be effective, the company that is responsible for registering the domain name (registrar) and the company that is responsible for maintaining the database of domain names and their associated IP addresses (registry) must support DNSSEC.

If you are unable to add Delegation Sign (DS) record through your registrar to enable DNSSEC, enabling on Cloud DNS will have no effect. Another thing to be aware of is that DNSSEC is not encrypted; keys are used to authenticate the resolver, not to encrypt client-server queries and resolutions.

If you are migrating from your DNSSEC-signed zone to Cloud DNS, you can use the Transfer state when enabling DNSSEC for your public zone. The Transfer state copies relevant keys, such as the key signing key (KSK) and zone signing key (ZSK), from your old zone to Cloud DNS. You should keep the state as Transfer until all DNS changes have propagated to the authoritative DNS server and then change the state to On.
