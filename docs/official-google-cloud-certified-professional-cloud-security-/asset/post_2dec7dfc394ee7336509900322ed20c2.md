# Understanding IAM policy inheritance works

We will cover IAM depth in Chapter 6, Google Cloud Identity and Access Management. In this section, we will understand how IAM policy inheritance works in organizations. Cloud IAM allows you to configure fine-grained access to your resources. It lets you configure who (users) have access (permissions) to what (resources) by means of an IAM policy.

The following figure depicts how IAM policy inheritance works, which is top-down, meaning you can configure IAM policy at the organization level, folder level, project level, and even at the resource level. If you recall from previous sections, we looked at how an organization hierarchy is created.

![](img/f681dfc12450e3a4c257352b70dbca71_0)

The effective policy for a resource is the union of the policy set at that resource and the policy inherited from its parent. Essentially, this means that resources inherit the policy from the project, and the project inherits the policy from folders and the organization. From the preceding figure, if you give Alice the role of Project Editor at folder level, Alice will have access as Project Editor for all the projects under that folder. If you assign Bob the role of Instance Admin at the resource level for a given project, Bob will only have access as Instance Admin for that particular project.

# Applying constraints using the Organization Policy

The Organization Policy Service provides you with a centralized and programmatic method to apply constraints across your organization and the respective cloud resources. We often dictate requirements that need to be applied organization-wide; these constraints are non-negotiable and every resource in your cloud environment has to adhere. This is where Organization Policy Service comes in, giving you the ability to centrally apply these policies to avoid or mitigate misconfigurations downstream in your projects and cloud resources. This helps you create guardrails that you can define, based on regulatory requirements or internal compliance. The development teams who are now consuming Google Cloud services do not have to worry about applying these policies and duplicating the effort. This further reduces the number of errors that may happen as you are now centrally in control of applying organization-wide constraints.

It is important to know the difference between IAM and Organization Policy Service constraints. While IAM focuses on who can execute an authorized action on a particular resource, policy constraints focus on the what, making what enforced on the resources dictating how they can be configured. An example would be giving access to a user called Bob to perform administrative functions on Compute Engine using an IAM policy, but by defining a constraint of not allowing external IP addresses to be assigned to the compute, you can restrict Bob from configuring an external IP address for any instance under the organization.

# Organization policy constraints

Constraints, simply put, are restrictions that can be applied to a resource. You have the ability to apply these constraints at different node levels, such as organization-wide or at the folder or project level. Google Cloud defines these constraints as a guardrail that defines what cannot be for a particular resource.

Every constraint is defined by a set of attributes and include a unique name such as `constraints/compute.disableSerialAccess`, a human-friendly name with a description of what the constraint is, followed by the default behavior of the constraint.

# Policy inheritance

Organization policy inheritance works by applying the policy at the node level (organization/folder/project), where the policy will be inherited. You can also create custom policies at child nodes, and these can either merge or overwrite the inherited policy.

Let's further understand the inheritance rules to better understand how policies are evaluated:

- The first rule applies when no policy is defined. A resource doesn't inherit or have a policy anywhere in the hierarchy, then the constraint's default behavior is enforced.
- The second rule states that if a resource has a policy set, it will override any policy set for that node. However, there is an exception to this rule. If the policy has the inheritParent attribute set to true, the resource node will inherit the policy from the parent node. In this case, the node-level policy will be merged with the inherited policy, and the two will be reconciled and evaluated.
- The third rule is if a resource has inheritParent = false set, the resource will not inherit the policy from the parent node. If a policy is configured at the resource level, it will take effect; if no policy is configured, then the default behavior of the policy will be enforced as defined in the first rule.
- The fourth rule is about managing conflicting policies. Let's consider an example where you have a policy constraint defined at the folder that allows project/123, and you have another policy constraint at the project level under the folder that denies the value project/123. In such circumstances, a parent policy allows an action and the project level denies the same action. DENY will always take precedence. This is how policies are merged. It is also highly recommended as a best practice to not create policy conflicts where one policy contradicts another.

An important note on exceptions that applies to policy merges: for all organization policies that are derived from Boolean constraints, do not merge. For example, say you have defined a policy constraint at the folder level and set enforcement to true. Another policy constraint for the project under the folder is set to false. In this case, the most specific policy action, false, will take effect.
