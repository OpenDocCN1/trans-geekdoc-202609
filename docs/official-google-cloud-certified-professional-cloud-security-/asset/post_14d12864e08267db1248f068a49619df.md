## Overview of Cloud DLP

Cloud DLP offers some key features for Google's:

- BigQuery-based data warehouses can be profiled to detect sensitive data, allowing for automated data discovery. You can scan the entire Google Cloud organization or choose folders or projects with the profiler's flexibility.
- Over 150 built-in information detectors are available in Cloud DLP. Because DLP is API-based, it can be used to swiftly scan, discover, and classify data from anywhere.
- Support for Cloud Storage, Datastore, and BigQuery is built in: Cloud DLP comes with built-in support for these storage options.
- You can calculate the level of risk to your privacy: quasi-identifiers are data elements or combinations of data that can be linked to a single individual or a small group of people. Cloud DLP gives you the option to examine statistical features such as k-anonymity and l-diversity, allowing you to assess the risk of data re-identification.
- DLP classification results can be delivered to BigQuery for more thorough analysis or exported to your analytical instrument of choice. BigQuery and Data Studio can be used to create bespoke reports.
- Cloud DLP secures your data by storing it in memory. The data in the backend is not persistent. In addition, the data is subject to various independent third-party audits to ensure data confidentiality, privacy, and safety.
- Cloud DLP may be swiftly deployed using reusable templates, with periodic scans monitoring the data and Pub/Sub notifications for integration into serverless architectures.
- To suit your company's needs, you can add your own custom info types, alter detection levels, and establish detection rules.

Now that you understand Cloud DLP's capabilities at a high level, let us understand the DLP architecture.

## DLP architecture options

Cloud DLP primarily is seen in three architecture patterns: the content/streaming and storage methods and a hybrid architecture that combines these two patterns.

## Content methods

In this architecture, the data is streamed to the Cloud DLP APIs for inspection/classification or de-identification/transformation. A synchronous API response is received from Cloud DLP. In this case, the client application is expected to process the response. This architecture is typically seen in data pipelines or call center applications where real-time response is needed.

![](img/f681dfc12450e3a4c257352b70dbceca_285_0.png)

Figure 10.1 – Content method architecture

As shown in Figure 10.1, using content inspection, you stream small payloads of data to Cloud DLP along with instructions about what to inspect for. Cloud DLP inspects the data for sensitive content and personally identifiable information (PII) and returns the results of its scan back to you.

## Storage methods

In this architecture option, a job is set up by a trigger to scan for sensitive data. The results of the scans are published so that action can be taken based on the results. The results can be pushed to Security Operations Center (SOC) tools such as Security Command Center so security responders can take action or an automated response detection can be built using Cloud Functions or a more sophisticated product such as SOA.

![](img/f681dfc12450e3a4c257352b70dbceca_286_0.png)

Figure 10.2 – Storage method architecture

As shown in Figure 10.2, in this architecture option, you tell Cloud DLP what to inspect and then Cloud DLP runs a job that scans the repository. After the scan is complete, Cloud DLP saves a summary of the results of the scan back to the job. You can additionally specify that the results are sent to another Google Cloud project for analysis, as a separate BigQuery table or Security Command Center.

The type of scan typically involves those Google Cloud projects where you do not expect to have sensitive data. For projects that are meant to have sensitive data such as cardholder data or PII, you should also invest in data exfiltration controls such as VPC Service Controls for DLP.

## Hybrid methods

Hybrid jobs and triggers enable you to broaden the scope of protection that Cloud DLP provides beyond simple content inspection requests and Google Cloud Storage (GCS) repository scanning.

Hybrid environments are common in enterprises. Many organizations store and process data using the following:

## Cloud Data Loss Prevention

Using hybrid jobs, Cloud DLP can inspect data sent to it from any source. Example scenarios include:

- Inspect stored data in Amazon Relational Database Service (RDS), MySQL running inside virtual machine, or on-premises database
- Inspect and tokenize data as you migrate from on-premises to the cloud, or between production, development, and analytics
- Inspect and de-identify transactions from web or mobile application before storing rest

- You write a script or create a workflow that sends data to Cloud DLP for inspection along with some metadata.
- You configure and create a hybrid job resource or trigger and enable it to activate when it receives data.
- Your script or workflow runs on the client side and sends data to Cloud DLP. The data includes an activation message and the job's identifier, which triggers the inspection.
- Cloud DLP inspects the data according to the criteria you set in the hybrid job or trigger.
- Cloud DLP saves the results of the scan to the hybrid job resource, along with the metadata that you provide. You can examine the results using the Cloud DLP UI in the Console.
- Optionally, Cloud DLP can run post-scan actions, such as saving inspection results to a BigQuery table or notifying you by email or Pub/Sub.

A hybrid job enables you to create, activate, and stop jobs so that you can trigger actions whenever you need them. By ensuring that your script or code sends data that includes the hybrid job's identifier, you don't need to update your script or code whenever a new job is started.
