
On a K8s workload, you would usually follow the following steps for your application (running on a pod) to communicate with Google Cloud services, for example, Cloud Storage:

1. Define a volume with the secret.
2. Mount the volume inside the container.
3. Point $GOOGLE_APPLICATION_CREDENTIALS at the key file.
4. The workload can now authenticate to Google Cloud APIs as that service account.

This is too much time to set up and harden. A better option is to use Workload Identity. With Workload Identity, you can do the following:

1. Enable Workload Identity for GKE cluster.
2. Run a workload using a dedicated KSA.
3. Grant KSA access to desired Google Cloud resources using IAM roles.
4. The workload can now access Google Cloud Storage APIs by presenting (short-lived, auto-rotated) KSA tokens.

You can see Workload Identity removes a lot of steps and makes GKE workloads more secure than using service account keys.

## Center for Internet Security (CIS) best practices

Here are some security best practices to harden your GKE cluster security. These are presented in the Google Cloud documentation as well as CIS GKE benchmarks, make sure to understand them:

- Upgrade your GKE infrastructure in a timely fashion
- Restrict network access to the control plane and nodes
- Consider managing Kubernetes RBAC users with Google Groups for RBAC
- Enable Shielded GKE nodes
- Choose a hardened node image with the containerd runtime
- Enable Workload Identity
- Harden workload isolation with GKE Sandbox
- Enable security bulletin notifications
- Use least-privilege Google service accounts
- Restrict access to cluster API discovery

## Container security best practices

Here are some security best practices: 

- Use namespaces and RBAC to restrict access to cluster resources
- Restrict traffic among pods with a network policy
- Consider encrypting Kubernetes secrets using keys managed in Cloud KMS
- Use admission controllers to enforce policies
- Restrict the ability of workloads to self-modify
- Audit your cluster configurations for deviations from your defined settings
- Ensure legacy Compute Engine instance metadata APIs are disabled and also ensure the GKE metadata server is enabled
- Ensure Basic authentication using static passwords is disabled
- Ensure authentication with Client Certificates is disabled
- Leave Logging enabled
- Leave the Kubernetes web UI (dashboard) disabled
- Disable Attribute-Based Access Control (ABAC), and instead use RBAC in GKE
- Do not disable the DenyServiceExternalIP admission controller

Now let us see some best practices for containers in general.

Here are a few general best practices when using containers for your application development process. We will look at these in three parts: the build phase, the distribution/deployment phase, and the production/run phase. These go hand in hand with your CI/CD security:

### Security in the container build phase: This is where the container starts:

- Source image control: In this phase, you write the code to create a container. Follow these best practices for this phase:
    i. Avoid retrieving/using source images with unknown/untrusted publishers.
    ii. If a third-party image is used, it is strongly recommended to identify and document detailed information, such as the version/build of code included and information about the creator of the image.
    iii. Never include code from unverified/untrusted sources in an image.
    iv. Use digital signature/checksum verification services on images whenever possible.
    v. Prior to completing image creation, all dependencies and libraries in source images should contain the latest security updates.
    vi. Less is more—include only core, necessary software/code in a base image. This alleviates future work and maintenance load from a security perspective.
    vii. Never include code from unverified/untrusted sources in an image.

- Security/vulnerability scanning: In this phase, you have the container image ready. Follow these best practices for scanning containers:
    i. It is recommended to perform security and vulnerability scanning on images regularly. Most security scanning services can be integrated with the container environment and batched to automatically perform security scanning.
    ii. It is recommended to leverage security scanning tools. Clair is an open source security scanner developed by CoreOS and is widely used for container scanning. There are other commercial scanners available on the market as well.
    iii. Use both static scanning (for example, package integrity verification) and dynamic scanning (for example, binary-level code analysis).

### Security in the distribution phase: In this phase, your container is ready.

- Container registry:
    i. Use vulnerability scanning to scan images in the registry for vulnerabilities.
    ii. Ensure that the registry is private and access is restricted.
    iii. Use content trust features to ensure that the images you are deploying are the same as the images you built.
- Version control:
    i. Use image tagging to manage different versions of your images.
    ii. Avoid using generic tags like "latest" in production to ensure consistency.

### Security in the run phase: Now the container is running.

- Authentication:
    i. Use RBAC to control access to cluster resources.
    ii. Use service accounts with least privilege to authenticate your pods.
    iii. Use short-lived tokens instead of long-lived keys.
- Attack surface reduction:
    i. Minimize the attack surface by removing unnecessary packages and services.
    ii. Use network policies to limit the communication between pods.
    iii. Monitor and audit logs for suspicious activity and potential threats.
- Patch management:
    i. Regularly update your container images with the latest patches.
    ii. Use automated tools to identify and patch vulnerable dependencies.
    iii. Prioritize patching of critical and high vulnerabilities.

## Container Security

- **Secret management**: Secret management is one of the largest attack planes. Follow these best practices to minimize the risk:
    i. Secrets, or sensitive data, should not be stored within an image. They should be stored outside the image and called dynamically at runtime.
    ii. Major orchestration platforms, such as Kubernetes and Docker Swarm, provide native secret management features. Configure the settings properly so that the sensitive data is handled securely when it is stored in a container and when it is transmitted between services.
    iii. If the organization has an existing secret management system, it should be integrated with the container environment by providing secrets from the non-container environment, through a secure channel.
