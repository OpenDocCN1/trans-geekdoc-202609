# Google Cloud Identity and Access Management

The version field is set to 3 in this example because of a condition expression in the policy. The policy's role binding lists only until July 1, 2022, and only for the Google groups prod-dev@acme.com prod-example@acme-project-id.iam.serviceaccount.com.

Let us see an example now that shows a policy with conditional and unconditional role bindings.

In this example an IAM policy contains both conditional and unconditional role bindings for the same role:

```
{"bindings": [
  {
    "members": [
      "serviceAccount:prod@acme-project-id.iam.serviceaccount.com"
    ],
    "role": "roles/appendine.deployer"
  },
  {
    "members": [
      "group:prod@acme.com",
      "serviceAccount:prod@acme-project-id.iam.serviceaccount.com"
    ],
    "role": "roles/appendine.deployer",
    "condition": {
      "title": "Expires_July_1_2024",
      "description": "Expires on July 1, 2024",
      "expression": "request.time < timestamp('2024-07-01T00:00:00.000Z')"
    }
  ],
  "etag": "BwUjMhCsZyP =",
  "version": 3
}prod@acme-project-id.iam.serviceaccount.com
```

The serviceAccount:prod@acme-project-id.iam.serviceaccount.com is included in two role bindings for the same role in this case. No conditions are attached to the first binding. Until July 1, 2024, the second role binding grants the role.

In Google Cloud IAM, conditional role bindings take precedence over role bindings without conditions. When a conditional role binding is specified for a principal, it overrides any non-conditional role bindings for that principal. This means that the conditions defined in the role binding will determine whether the principal is granted the specified role. If the conditions are not met, non-conditional role bindings will not be considered for that principal.
