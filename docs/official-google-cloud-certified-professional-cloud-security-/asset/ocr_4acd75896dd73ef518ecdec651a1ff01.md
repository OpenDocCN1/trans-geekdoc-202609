# Data security

Google ensures that data in motion and data at rest are secured. We've already covered how Google enforces TLS for all data in motion and encryption by default for data at rest. In addition to the default encryption of data at rest, as a Google Cloud user, you also get the option to select a different options for how you can encrypt data. Recall the previous section on data privacy and Google's commitment to establishing itself as a trusted cloud provider; as a Google Cloud customer have full control and ownership over your data you may choose to use the default encryption or use Cloud Key Management Service. Alternatively, you can use Cloud Key Management Service and import your own key material, or you can go the Bring Your Own Key (BYOK) route or multi-tenant Cloud HSM, which provides FIPS 140-2 Level 3 protection for your keys. If you are in a highly regulated environment and need to retain full control of the keys and the infrastructure, you have the option to use a Google-partner-external HSM that is integrated with an external key management service and is accessed via Google's Cloud Key Management Service.

The challenge with data security is that data has to remain secure throughout its lifecycle. When the data is created, shared, stored, analyzed, archived, or deleted, it has to be secured. This brings us to how Google manages the data deletion side of things. A key concern for customers is when you stop using a service that you've stored sensitive data, when you delete the data how can you be sure that the data will be wiped from physical media as well? Let's take a quick look at the controls and compliance side of data deletion. When you want to delete data on Google Cloud, it's not immediately deleted but is marked as deletion, so, if you accidentally deleted your data, you have the option to recover it. After the data is scheduled for deletion, it is deleted in accordance with service-specific policies.

Google details the entire handling and data governance as part of their called Trusting your Data with Google Cloud Platform; a link to this resource can be found in the Further section of this chapter. We will be covering the data management side of things in more detail in the next chapter on trust and compliance on Google Cloud.

# Services and identity

For human-to-system interaction or for calls between systems (such as inter-service access), Google provides cryptographic authentication and authorization at the application layer before any access is granted. Although there are network-perimeter-based controls and network segmentation and firewall rules, Google does not rely solely on that and zero-trust principles. Each service that's running also has an associated service account, including the cryptographic credentials that are used for authenticating and authorizing when a remote call is initiated to access other services. Besides, there is a number of techniques used, such as isolating and sandboxing in order to protect services that might be running on the same machine. Some of the techniques used are language- and kernel-based sandboxing, hardware virtualization, and Linux user separation.
