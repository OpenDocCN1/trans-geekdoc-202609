
# 11 Secret Manager

In this chapter, we will look at Google Cloud Secret Manager. A secret is any piece of data that needs to be protected, such as passwords, encryption keys, API keys, certificate private keys, and other sensitive information. Secrets can be stored in a secure and encrypted format using Google Cloud Secret Manager. Secrets that run on the cloud platform often need to be able to securely store secrets and rotate them as needed. The secrets should also provide redundancy in the event that a region goes down. Traditionally, secrets were stored in configuration files embedded within the application using some form of encryption or in clear text.

Secret Manager is a native offering on Google Cloud to store application secrets such as database passwords or API keys. It provides a single place to store application secrets and be able to manage access and audit who did what.

In this chapter, we will cover the following topics:

- Overview of Secret Manager
- Managing secrets and versions
- Accessing a secret
- Secret rotation policy
- CMEKs for Secret Manager
- Best practices for secret management

## Overview of Secret Manager

Secret Manager allows you to store and access secrets as binary blobs. It uses IAM permissions to grant access to the secrets and be able to manage them. Secret Manager is used for applications running on Google Cloud to store information such as database passwords, API keys, or certificates.

## 302 Secret Manager

> Note
> Cryptographic keys should not be stored in Secret Manager. Cloud KMS is a better service since it allows you to encrypt the key material.

Before we start Secret Manager, let us go over some core concepts. This will help you understand how Secret Manager works so you can make the right decision for your workloads.

## Secret Manager concepts

Let us look at some key definitions related to Secret Manager as defined in the Google Cloud documentation:

- **Secret**: A secret is an object at the project level that stores a collection of metadata and secret versions. The metadata includes replication locations, labels, and permissions.
- **Version**: A secret version stores the actual confidential information, such as API keys, passwords, and certificates. You cannot modify a secret once you create, but you can delete it and create a new version.
- **Rotation**: Secret Manager supports rotational schedules for secrets. This, however, doesn't create a new secret version automatically but merely sends a message to a Pub/Sub topic configured for that secret based on rotational frequency and time.
- **Replication policy**: Secrets have global names and metadata. The replication policy can only determine where the payload is stored. Upon the creation of each secret, it will have its own replication policy. You cannot modify the location in replication policy.
- **Resource consistency**: Adding a secret version and immediately accessing it is an example of a consistent operation in Secret Manager. Consistent operations usually synchronize in minutes but may take a few hours. You should take consistency into consideration when designing your applications.

## Managing secrets and versions

Now look at some basic operations you can perform in Secret Manager. These operations can either be performed using gcloud, the console, or APIs. We used the console to keep it simple.

### Creating a secret

Follow these steps to create a secret using the Cloud console:

1. Go to Security | Secret Manager.
2. Click on Create secret.

img/f681dfc2450e3a4c257352b70dbceca_227.png

By default, Google automatically manages where this secret is stored. If you need to manually manage this, you can customize the locations by checking the box below. Secrets are globally accessible regardless of how they are replicated and stored. The replication policy cannot be changed after a secret is created.

- Manually manage locations for this secret

### Encryption

This secret is encrypted with a Google-managed key by default. If you need to manage your encryption, you can use a customer-managed key instead.

- Use a customer-managed key (CMEK)

Figure 11.1 – Creating a new secret

As shown in Figure 11.1, a secret value can be copied directly into the console or provided via a file. Typically, binary secrets are provided via a file.

3. Choose rotation period (Set rotation period). Note that this will only set notification but not rotate the secret automatically.

### Rotation

Setting a rotation period will send notifications to Pub/Sub topics. Secret Manager will not rotate the secret value.

### Notifications

Select Pub/Sub topic(s) that will receive notifications whenever the secret or one of its versions is changed. These events can be user-initiated or scheduled events.

### Expiration

By default, the secret never expires. To set an expiration date for this secret, select expiration date. If you choose an expiration date, the secret will be deleted and unavailable after that time.

- Set expiration date

### Labels

Use labels to organize and categorize your secrets.

Figure 11.2 – Creating a new secret—rotation period

As shown in Figure 11.2, there are additional properties you can set on a secret. I recommend that you do not set expiration since this can cause unintended behavior. You can set labels to organize secrets.

Alternatively, you can use the gcloud command to create a secret:

```bash
gcloud secrets versions add secret-id --data-file="/path/to/secret.txt"
```
