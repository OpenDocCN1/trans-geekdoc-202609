
Note: If you're training your own embeddings, you would define your vocabulary differently. You'd most likely start by counting the uses of each token in your training data, and then choosing some of most commonly used terms. Those terms define the vocabulary for which you'd train embeddings.

Once you've settled on the vocabulary you'll support — let's assume it's a set of tokens stored in in_vocab — you need to go through all your training, validation test data and replace any OOV tokens with the appropriate <UNK> token(s). This is different from how you removed OOV from your datasets when you work with characters.

At this point your embeddings are likely in a dictionary keyed off of tokens, and it may contain more embeddings than you actually plan to use in your vocabulary. You'll need to put the embeddings for these individual vocabulary words into a single NumPy array to use with your network, like this:

```python
# 1
num_enc_embeddings = in_vocab_size + 1
# 2
pretrained_embeddings = np.zeros(
    (num_enc, embedding_dim), dtype=np.float32)
# 3
for i, t in enumerate(in_vocab):
    pretrained_embeddings[i+1] = es_token_vectors[t]
```

Here's how you'd grab the embeddings for your words in your vocabulary:

- 1. Your encoder will need to embed each token in your vocabulary, plus an additional embedding to act as a padding token during training.
- 2. Create a NumPy array of all zeros, shaped to hold the correct number of embeddings embedding_dim. You can find pre-trained embeddings in various dimensions, especially for English, but it seems 300 is the most common. Embeddings of that size for a reasonably-sized vocabulary may give you models that are too big for mobile devices, so you may need to train your own if you cannot find smaller embeddings for the language you need.
- 3. Notice how each embedding is stored with the index i+1. This leaves zero unassigned, which is the value reserved by Keras's Embedding layer for the padding token. You'll read about the Embedding layer next.

Next, you'd replace the Masking layers you were using in your earlier seq2seq models with Embedding layers. These can perform the same masking, but additionally they map scalar integers into higher dimensional vector coordinates. Here's how you would define your encoder's layer:

```python
# 1
enc_embeddings = Embedding(
    num_embeddings, embedding_dim,
    weights=[pretrained_embeddings], trainable=False,
    mask_zero="encoder_embeddings")
# 2
enc_embeddings_in = enc_embeddings(encoder_in)
```

- 1. When creating an Embedding layer, you specify the number of possible input tokens — defined as num_enc_embeddings — the number of dimensions to map those values into, defined as embedding_dim. When using pre-trained embeddings, you provide them using the weights parameter and set trainable=False so the model does not modify their values during training.
- 2. When you pass your Input layer into the Embedding layer, just like what you did before with the Masking layers. The Embedding layer will still perform masking because you created it with mask_zero=True. That tells it to treat the input value zero as a padding token, which is why you had to add one to the size of the vocabulary count you declared num_enc_embeddings.

You could declare the decoder's Embedding layer the same way, using pre-trained embeddings for your target language. Keras can also learn its own embedding values during training. To do that in your decoder, for example, you declare your Embedding layer like this:

```python
num_dec_embeddings = out_vocab_size + 1
dec_embeddings = Embedding(
    num_dec_embeddings, embedding_dim,
    mask_zero=True, name="decoder_embeddings")
```

The difference is that you don't supply an argument for the weights parameter, and you rely on the default value of True for the trainable parameter. Embedding layer will initialize its embeddings to random values and modifying them during training, unless it modifies the weights of other layers in the network.

> Note: Another option for your Embedding layers is to start with pre-trained embeddings being set trainable=True. Or train for a while with it set to False before training for additional epochs if it set to True. In either case, the idea is to take advantage of the information the embeddings contain fine-tuning them to be more appropriate for your model's specific task.

The Embedding layers reserve zero for the padding token, so you'll need to avoid that ID for real tokens. One option is to shift all token IDs by one when making y conversion maps, like this:

```python
in_token2int = {:token : i + 1
              for i, token in enumerate(in_vocab)}
out_token2int = {:token : i + 1
              for i, token in enumerate(out_vocab)}
```

You'd need to make minor differences in make_batch_storage and encode_batch to, because the input sequences are no longer one-hot encoded. For example, you would set tokens like this:

```python
enc_seqs[i, time_step] = in_token2int[token]
```

Instead of:

```python
enc_seqs[i, time_step, in_token2int[token]] = 1
```

You still one-hot encode the target sequence, since the decoder outputs a probability distribution over the vocabulary. However, make sure the decoder's output layer has the correct size.

You can use num_dec_embeddings, but that includes an extra padding token that your model should never output. Or can use out_vocab_size, but then you'll need to subtract 1 from its training output targets so it doesn't try one-hot encoding values larger than its max.

# Using word embeddings in iOS

When it comes to using your trained model in an app, it's similar to what you did in the SMDB project. However, there are a few important caveats:

- You'll have to include mappings for your tokens, just like you did with the character-based models. However, these will be quite a bit larger than the larger vocabulary and that the tokens aren't single characters. You'll also need to know the indices of any special tokens, like <START>, <STOP> and <UNK>.

![](img/5720be5c3cca252e12448e68d25607b5_550_0.png)

- Pre-trained word embeddings are often produced for lower-case tokens. That means you'll need to convert your input sequences to lower case prior to translating, then figure out what to capitalize in the output.
- As mentioned earlier, tokenize input text the same way you did during. You didn't have to worry about that when working with characters.
- Be sure to replace OOV tokens with the proper <UNK> token(s). You just dropped OOV tokens when working with characters, but you'll lose too much information if you do that.
- After running your model — maybe with a nice search — you'll be left with a list of tokens that might look like this: ['i', 'do', 'n't', '<UNK>', 'or', 'bugs', '.']. You'll need to perform post-processing to properly capitalize words, insert spaces appropriately and connect contractions. You'll also need a plan for dealing with <UNK> tokens. One option is to align the sentence in some way and carry over words that seem to match. For example, if there is an <UNK> token in each of the input and output, just copy the original unknown input token into the output. Translating between some language pairs requires a reordering of terms, and sometimes the numbers of missing terms won't match. Even when things seem to line up, that won't always produce a good result. To conclude this introduction using word tokens, keep these tips in mind:

- Pre-trained embeddings learn the biases of the data they are trained on. For example, embeddings trained on internet data usually place the word "apple" closer to their companies, like Microsoft, than to fruit, like bananas.
- Each embedding represents the average of all uses for that word. That means words used in multiple ways have diluted embeddings that don't always represent any of uses. There have been attempts to deal with this issue using context-sensitive embeddings. These are more complex but may be worth looking into some
- Try running a spell checker on your sequences prior to looking for OOV tokens. That should help reduce the number of tokens you can't find in your vocabulary.
