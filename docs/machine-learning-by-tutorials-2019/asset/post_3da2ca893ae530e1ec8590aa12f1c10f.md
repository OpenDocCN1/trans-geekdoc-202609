Both of these sessions contain data that will only confuse your model, reducing its performance, so it's best to remove them from your dataset before continuing. To do so, run the following code, replacing the index values with ones that work for your dataset:

```
# 1
bad_session_1 = test_sf[21350] ["sessionId"]
bad_session_2 = test_sf[22250] ["sessionId"]
# 2
test_sf = test_sf.filter_by(
[bad_session_1, bad_session_2],
column_name="sessionId", exclude=True)
```

Here's what that does:

- Grabs the session ID from a row in the middle of each bad data. Each session contains data for only one activity, so once you know the session ID for one, you know it all the rows you want to delete.
- Calls SFrame's filter_by method to return a new SFrame that excludes any rows where the session column contains the value of either of the bad sessions.

Plotting the test set's drive_it data again shows the suspect sessions are now gone. The plot isn't included here to save space, but the Data_Exploration_Complete.ipynb notebook includes this plot if you'd like to compare it to your results.

# Optional: Removing non-activity data

What about motions that have nothing to do with gestures? You know, all sensor readings that arrive between the gestures? Take a look at that data by plotting the rest_it activity. Here's how you do so for the test set:

![](img/5720be5c3cca252e12448e68d25607b5_395_0.png)

# utils.plot_gesture_activity(test_sf, activity="rest_it")

This plots all samples in the test set labeled rest_it, which means data is not a gesture. Here are the results:

![](img/5720be5c3cca252e12448e68d25607b5_396_0.png)

Unlike the gestures you plotted earlier, the resting data shows no clear pattern. That makes sense — users can do whatever they want between gestures, so there are basically an infinite number of sequences that could appear with this label. Depending on how similar the resting and activity data are, a model might have trouble to classify both. In those cases, it often helps to increase the size of your dataset. However, in many cases — such as this one — the model will learn to recognize both resting and activity. This is probably because the sequences related to the other gestures are so distinct. It is likely to classify the other gestures well, and then learn that anything is resting. It will get some wrong — users sometimes performs gestures while recording data, essentially adding mislabeled data to your dataset — but the juxtaposition of the messy data and the patterned gestures should make the model even more confident about its predictions.

For this app, you're encouraged to try making another model that excludes the resting data to see which the results might vary depending on exactly what you prefer. If you ever want to remove that data, you can do so with the following code:

```
train_sf = train_sf.filter_by(
['rest_it'], 'activity', exclude=True)
test_sf = test_sf.filter_by(
['rest_it'], 'activity', exclude=True)
valid_sf = valid_sf.filter_by(
['rest_it'], 'activity', exclude=True)
```

Much like how you removed the bad sessions, this would create SFrames that not contain any samples whose activity value rest_it.

# Balancing your classes

After you are satisfied you cleaned your data, there's one final thing you should check: How many examples of each class you have? Run the following code to count the examples in each dataset:

```
utils.count_activities(train_sf)
utils.count_activities(valid_sf)
utils.count_activities(test_sf)
```

Here you call count_activities, another helper function defined in activity_detector.py. It displays a table showing how many sessions are for activity, both per user and total. The following shows counts for the datasets we provided:

Here we see that each dataset contains three gestures, and no gesture is represented more than one other within a specific dataset. Within a dataset are represented equally as well. For example, the training set's two users supplied 50% of the training data. Things are looking great! You won't always find perfectly balanced datasets, but you want them to be as well balanced as possible. If any gesture or user is overrepresented in the training set, your model may become biased towards that outcome. Unbalanced validation or test sets can be a problem, too, because they'll skew your evaluation results, making it more difficult to judge your model.

> Note: The rest_it activity takes up half of each dataset — you might want to remove some of those samples to bring it in with the other gutters, but it wasn't a problem when training the model included with the book.

It's not a lot of data, but it's as the author's family was willing to put up with collecting. Still, it's a reasonable balance, with about 80% of your data for training, and around 10% for validation and testing.
