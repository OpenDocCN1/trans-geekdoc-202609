> Note: There's another option you aren't using here, but you may want to consider for your projects. Perform data collection at a high rate, and then downsample to train multiple models and find the lowest rate that works. For example, collect data at 80Hz and then train multiple models — 80Hz using all the data, 40Hz using every fourth sample, etc. This lets you collect once and then have different options for how to use it, which is better than having to collect multiple times with update rates. Once you find the lowest rate that still works, use that in your production app.

In this app, you'll store all the sensor data in memory and write it out to disk at the end of the recording session. Add the following array with the other properties under the comment that reads // MARK: Core Motion properties in ViewController

```swift
var activityData:[String] = []
```

You'll create a single string containing all the data you want to record for a sample, and append it to activityData. The entire recording session will live inside this array as one long sequence, and GestureDataRecorder calls saveActivityData at the end of session to save all strings to file. However, you will need to add the following line to actually save the array. Put it inside saveActivityData in ViewController, inside the do block that currently contains a print statement:

```swift
try self.activityData.appendLinesToURL(fileURL: dataURL)
```

This writes all strings in the array out to the appropriate file using a helper function from inside StringArrayExtensions.swift. This function creates the file if it doesn't already exist, or appends to the file otherwise.

One important aspect of GestureDataRecorder is that it keeps recording sessions very short. As such, there's no fear of running out of memory while storing data in activityData. That also means it's not a big deal if something goes wrong while recording — it's never much more than a minute's worth. Shorter sessions are easier on your test subjects — it's probably a bit much to ask someone to shake their phone for an hour straight, doing lots of tiny sessions isn't so bad.

However, when working with longer activities, where data collection takes several minutes or more, you don't want to risk having to throw away too much data. In that case, you should write your data out periodically rather than at the end of the session. You should also consider making your app more robust, by saving data when the app gets interrupted from things like phone calls, for example.

You've enabled motion updates just yet, but eventually the app will receive them in the form of CMDeviceMotion objects. Add the following method to them:

```swift
func processMotionData(_ motionData: CMDeviceMotion) {
  // ...
  let activity = isRecording ? currActivity : .none
  // 2
  let sample = """
  \(sessionID!)-\(unActionsRecorded),
  \(activity.attitude.rawValue()),
  \(motionData.attitude.roll),
  \(motionData.attitude.pitch),
  \(motionData.attitude.yaw),
  \(motionData.rotationRate.x),
  \(motionData.rotationRate.y),
  \(motionData.rotationRate.z),
  \(motionData.gravity.x),
  \(motionData.gravity.y),
  \(motionData.gravity.z),
  \(motionData.userAcceleration.x),
  \(motionData.userAcceleration.y),
  \(motionData.userAcceleration.z)
  """
  // 3
  activityData.append(sample)
}
```

This method creates samples for your dataset from CMDeviceMotion objects. Here's how it works:

- You label each sample with the activity it represents. This line checks to see if there is an activity being recorded or if this data is arriving in-between activities. In the latter case, you label it as ActivityType.none. The current activity is set from within the starter code after the app announces the activity to the user.
- 2. Here you create one big string representing a single data sample. It includes a session ID, the current activity and the sensor readings extracted from motionData, all separated by commas.
- 3. This line appends the string to activityData. The entire array gets saved to disk later, when the recording session ends.

Along with the session ID and the activity type, you're saving 12 different values at each moment in time. These were chosen because they seem like they could be relevant to the task at hand. However, you might not use all of them when you train your model.

But it's a good idea to record as much data as you can, because it gives you more options later you can always remove data that you need, but there's no way to go back to these moments.
