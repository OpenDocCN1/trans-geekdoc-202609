> Note: Training is suddenly lot slower now because this time Keras needs to train all the layers, not just the Dense layer. On the author's iMac, the estimated time for a single epoch from six to 20 minutes. On the Linux machine with the GPU, the time went from 10 seconds per epoch to 50 seconds — not nearly as bad. It also possible that you will get an out-of-memory error at this point. There are more parameters to update and so the GPU needs more RAM. If that happens, make the batch size smaller and run the cells that create the generators.

After 10 epochs, the validation loss and accuracy no longer appear to improve. When that happens, it is useful to reduce the learning rate. Here, you make it three times smaller:

```
K.set_value(top_model.optimizer.lr, K.get_value(top_model.optimizer.lr) / 3)
```

Now, train again for five or so epochs. For the author, the validation accuracy immediately shot up from 0.79 to 0.81, even though it stopped improving earlier.

When the learning rate is too large, the optimizer may not be able to hone in on a good solution. This is why you start with a large-ish learning rate, to get quickly in the neighborhood of a good solution, and then make the learning rate smaller over time, in order to get close to this solution as you can.

You can repeat this process of lowering the learning rate and training for a few epochs several times out until the loss and accuracy are no longer noticeably improving.

> Tip: Keras also has a LearningRateScheduler callback that can automatically reduce the learning rate, which is especially useful for training sessions with hundreds of epochs that you don't want to babysit. The ReduceLROnPlateau callback will automatically lower the learning rate when the validation accuracy or loss has stopped improving. Very handy!
