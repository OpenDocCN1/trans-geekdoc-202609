Along with the session ID and the activity type, you're saving 12 different values at each moment in time. These were chosen because they seem like they could be relevant to the task at hand. However, you might not use all of them when you train your model.

But it's a good idea to record as much data as you can, because it gives you more options later you can always remove data that you need, but there's no way to go back to these moments and record additional data — adding features require a new data collection effort.

Notice the session IDs created by combining sessionId, which is aစီး created when recording starts, and the number of which the user is currently doing. That means each time user runs the app, they'll choose between creating one, two or three sessions, even though to the user it will seem just one session.

Why is that important? You'll be using Core it currently requires a few things when training. (Comments from its developers on GitHub seem to indicate they would like to make it more flexible in the future). First, it doesn't like super short sessions. Without going into detail here, you'll want your sessions to be as long as 20 predictions worth of data. So if you plan predicting once per second, for example, sessions should be at least 20 seconds long. It doesn't need to be exact, but sessions much shorter than that may not work well.

Secondly, Turi Comes to prefer a lot of sessions. So instead of fewer, longer sessions, this app opts for creating more, shorter ones. Note however that sessions do not need to contain just a single activity. In fact, the sessions for this app will contain activities — the gesture itself, as well as a period of none data recorded before the gesture. In your apps you can record any number of activities within a single session, but labeling this like was an way to get more sessions with fewer actual user recordings.
