```python
verbose=1,
save_best_only=True),
]
my_callbacks = create_callbacks()
```

By the way, if you wanted to save the current state of the model by hand, you can also write model.save('convnet.h5')`. Remember that Create ML and Turi trained their models using a two-step process:

- 1. First, extract the features from all the training images. This can take a while.
- 2. But once they have those feature vectors, training the logistic regression is fast.

By doing the feature extraction once, Turi and ML could save a lot of time in the training stage. It is also possible to do this with Keras, see the SqueezeNet notebook for details. But because you're doing a lot of data augmentation, it's not really worth the trouble.

# Chapter 8: Advanced Convolutional Neural Networks

Having feature extraction as a separate step only makes sense if you plan to reuse the same images in every epoch. But with random data augmentation — where images are rotated, flipped and distorted in many ways — no two images are the same. And all the feature vectors will be different for every epoch.

That's why this MobileNet-based model is trained end-to-end and not in two separate stages. In every epoch, Keras needs to compute all the feature vectors again because all the training images are now slightly different from last time. It's a bit slower, but that's a small price to pay for having a much larger training set with very little effort.

# Fine-tuning the feature extractor

At this point, it's a good idea to start fine-tuning the feature extractor. So far, you've been using the pre-trained MobileNet as the feature extractor. This was trained on the ImageNet dataset, which contains a large variety of photos from 1,000 different kinds of objects.

The pretrained MobileNet knows a lot about photos in general, including photos of food items. This is why you've trained a classifier on top of MobileNet's layers so that it can translate this general knowledge about photos to your 20 categories of snacks.

The pretrained feature extractor contains a lot of irrelevant knowledge, too, about animals, vehicles and all kinds of things that are not snacks. We don't need this knowledge for our task of classifying snacks.

With fine-tuning, you can adjust the knowledge inside the feature extractor to make it more relevant to your own data. Now the feature extractor itself understands more about this specific task.

To fine-tune the MobileNet layers, first set them to trainable and then compile the model again:

```python
for layer in base_model.layers:
    layer.trainable = True

top_model.compile(loss="categorical_crossentropy",
                   optimizer=optimizers.Adam(lr=1e-4),
                   metrics=["accuracy"])
```

It's important to use a lower learning rate, lr=1e-4. That's why you don't want to completely throw away the MobileNet layers you have already learned — only you tweak these values a little.

It's better to set the learning rate too low than too high at this point, or you might end destroying useful knowledge. The author found 1e-4 by experimenting a bit.

Run top_model.summary() and you will see there are now 3 million parameters instead of 20,500. There are still non-trainable parameters; these are used by BatchNorm layers to keep track of internal state.

Simply run the cell with top_model.fit_generator() to start fine-tuning. The loss may bounce around a bit because suddenly the optimizer has a lot more work to do.

Again, you should see the training and validation accuracy start to improve quite quickly. If not, lower the learning rate.

> Note: Training is suddenly lot slower now because this Keras needs to train all the layers, not just the Dense layer. On the author's iMac, the estimated time for a single epoch went to 20 minutes. On the Linux machine with the GPU, the time went from 10 seconds per epoch to 50 seconds — not nearly as bad. It also possible that you will get an out-of-memory error at this point. There are more parameters to update and so the GPU needs more RAM. If that happens, make the batch size smaller and run the cells that create the generators.

After 10 epochs, the validation loss and accuracy no longer appear to improve. When that happens, it is useful to reduce the learning rate. Here, you make it three times smaller:

```python
K.set_value(top_model.optimizer.lr, K.get_value(top_model.optimizer.lr) / 3)
```

Now, train again for five or so epochs. For the author, the validation accuracy immediately shot up from 0.79 to 0.81, even though it stopped improving earlier.

When the learning rate is too large, the optimizer may not be able to hone in on a good solution. This is why you start with a large-ish learning rate, to get quickly in the neighborhood of a good solution, and then make the learning rate smaller over time, in order to get close to this solution as you can.

You can repeat this process of lowering the learning rate and training for a few epochs several times until the loss and accuracy are no longer noticeably improving.

> Tip: Keras also has a LearningRateScheduler callback that can automatically reduce the learning rate, which is especially useful for training sessions with hundreds of epochs that you don't want to babysit. The ReduceLROnPlateau callback will automatically lower the learning rate when the validation accuracy or loss has stopped improving. Very handy!
