```go
pb "github.com/juanmanuel-tirado/savetheworldwithgo/13_grpc/streaming/example_03/chat"
"google.golang.org/grpc"
"io"
"net"
"time"

type ChatServer struct {
	pb.UnimplementedChatServices
}

func (c *ChatServer) SendTxt(stream pb.ChatService_SendTxtServer) error {
	var total int64 = 0
	go func() {
		for {
			timer := time.NewTicker(time.Second*2)
			select {
			case <-timer.C:
				stream.Send(&pb.StatsResponse{TotalChar: total})
			}
		}
	}()
	for {
		next, err := stream.Recv()
		if err == io.EOF {
			fmt.Println("Client closed")
			return nil
		}
		if err != nil {
			return nil
		}
		fmt.Println("-", next.Txt)
		total = total + int64(len(next.Txt))
	}
	return nil
}

func main() {
	lis, err := net.Listen("tcp", "localhost:50051")
	if err != nil {
		panic(err)
	}
	s := grpc.NewServer()
	pb.RegisterChatServices(s, &ChatServer{})
	if err := s.Serve(lis); err != nil {
		panic(err)
	}
}
```

## 15.6 TRANSCODING

gRPC works on top of the HTTP/2 transfer protocol offering full-duplex communication, high performance, among other features. Unfortunately, HTTP/2 is not available in every scenario and sometimes can become a drawback. Many servers are behind load balancers and/or proxies that do not support HTTP/2. In other scenarios, remote clients cannot work with gRPC due to other limitations simply because they cannot easily adopt this technology.

Transcoding permits gRPC to emulate REST APIs (HTTP + JSON). This can be done using annotations in the .proto file. Using the grpc-gateway, the protoc program can generate reverse proxies transcoding HTTP requests to the corresponding gRPC handler. Figure 15.5 shows a schema of HTTP transcoding to gRPC where a HTTP client sends a GET request to a remote server. This request travels through the Internet and may traverse different load balancers or service providers. Finally, the request reaches the target HTTP server. The incoming request is transformed into a gRPC compatible request and sent to the corresponding gRPC server.

![](img/c7dcb4df7215ed1d3fb76d25373be6c7_214_0.png)

Figure 15.5: Summary of elements in a gRPC deployment.

This transformation is obtained adding the google.api.http notations to the .proto file. Observe in the figure that the output from proto includes two files like in a regular gRPC scenario, user_grpc.pb.go has been replaced by user.pb.gw.go. This file contains the definition of the necessary transcoding operations. Using transcoding is a powerful option to enable accessing remote methods to a vast number clients with minimal coding.

### 15.6.1 Generation of stubs and gRPC-gateway

Transcoding is defined in the .proto file using annotations. Example 15.14, defines a user service that creates and generates. There are two important elements we have added here. First, we have imported the annotations.proto file that defines the google.api.http option.

Example 15.14: gRPC services definition with transcoding notations.

```proto
syntax = "proto3";
package user;

option go_package="github.com/juanuel-tirado/savetheorldwithgo/13_grpc/transcoding/example_01/user";
import "google/api/annotations.proto";

message User {
  string user_id = 1;
  string email = 2;
}
```

```go
message UserRequest {
  string user_id = 1;
}

service UserService {
  rpc Get(UserRequest) returns (User) {
    option(google.api.http) = {
      get: "/v1/user/{user_id}"
    }
  }
  rpc Create (User) returns (User) {
    option(google.api.http) = {
      post: "/v1/user"
    }
  }
}
```

For every RPC method we want to expose through HTTP we must define the path and the required HTTP method. The method Get will be served at /v1/user/{user_id}, where `user_id` corresponds to the field with the same name from the corresponding input message. In this case, this will fill the unique field from the UserRequest message to be sent into the body of the HTTP request. By setting body="*", we indicate that a User message will be filled with all the available data from the body. If required, single fields can be specified, for example, body="email" will only expect the body to contain the email field.

> Remember that the URL of a remote procedure should not be changed unilaterally once this function is consumed by others. There are some good practices to be followed indicating the API version in the URL. In other cases, you can define additional bindings for the same procedure.

```go
Get (UserRequest) returns (User) {
  option(google.api.http) = {
    get: "/v1/user/{user_id}"
    additional_bindings {
      get: "/v2/user/{user_id}"
    }
  }
}
```

Before running protoc, we must install the grpc-gateway plugin.

```bash
go install \
github.com/grpc-ecosystem/grpc-gateway/v2/protoc-gen-grpc-gateway \
github.com/grpc-ecosystem/grpc-gateway/v2/protoc-gen-openapi2 \
google.golang.org/protobuf/cmd/protoc-gen-go \
google.golang.org/grpc/cmd/protoc-gen-go-grpc
```

Now protoc should be able to use the additional plugins by running:

```bash
protoc -I . \
-I $GOPATH/src/github.com/grpc-ecosystem/grpc-gateway/third_party/googleapis \
--go_out=-plugins=grpc-go-opt=paths=source_relative:$GOPATH/src *.proto \
--grpc-gateway_out=.
```

This execution puts you in the same folder as the .proto file. Some arguments may vary depending on your environment.

### 15.6.2 Create an HTTP server

To demonstrate how transcoding works, we are going to implement the remote methods we defined in the previous .proto file and serve using gRPC as we have already explained, then we show how this can be done using an HTTP server. For clarity, we split the code into two parts. In Example 15.15 the code contains the logic of the remote procedures defined in our .proto file. This code is similar to the examples we have already explained. The only method you may find is Serve, which simply encapsulates the gRPC server starting logic.

Example 15.15: gRPC gateway using HTTP (part I).

```go
package main

import (
	"context"
	"fmt"
	"github.com/grpc-ecosystem/grpc-gateway/v2/runtime"
	"github.com/juanmanuel-tirado/savetheworldwithgo/13_grpc/transcoding/example_01/user"
	"google.golang.org/grpc"
	"net"
	"net/http"
)

type UserServer struct {
	user.UnimplementedUserServiceServer
	httpaddr string
	grpcaddr string
}

func (u *UserServer) Get(ctx context.Context, req *user.UserRequest) (*user.User, error) {
	fmt.Printf("Server received: %s\n", req.String())
	return &user.User{ID: "John", Email: "john@gmail.com"}, nil
}

func (u *UserServer) Create(ctx context.Context, req *user.User) (*user.User, error) {
	fmt.Printf("Server received: %s\n", req.String())
	return &user.User{ID: req.UserID, Email: req.Email}, nil
}

func (u *UserServer) ServeGrpc() {
	lis, err := net.Listen("tcp", u.grpcAddr)
	if err != nil {
		panic(err)
	}
	s := grpc.NewServer()
	user.RegisterUserServiceServer(s, u)
	fmt.Println("Server listening GRPC!")

	if err := s.Serve(lis); err != nil {
		panic(err)
	}
}
```

```go
func (u *UserServer) ServeHttp() {
	mux := runtime.NewServeMux()
	opts := []grpc.DialOption{grpc.WithInsecure()}
	endpoint := u.grpcAddr

	err := user.RegisterUserServiceHandlerFromEndPoint(context.Background(), mux, endpoint, opts)
	if err != nil {
		panic(err)
	}

	httpServer := &http.Server{
		Addr: u.httpAddr,
		Handler: mux,
	}

	fmt.Println("Server listing HTTP:")
	if err := httpServer.ListenAndServeServe(); err != nil {
		panic(err)
	}
}

func main() {
	us := NewServer(httpAddr=":8080", grpcAddr:":50051")
	go us.ServeGrpc()
	us.ServeHttp()
}
```
