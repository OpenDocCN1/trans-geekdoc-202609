laptops set<frozen<laptop>>;

Using the set collection guarantees that the same laptop cannot appear twice in the same user and querying the laptops of every user would be straight forward. However, the same laptop can appear in different users. To guarantee that there is only one user per laptop we can maintain the laptop table with the `user_id`.

# Example 19.7: Guarantee that every laptop has a unique user.

```
CREATE TABLE laptops (
 sn int PRIMARY KEY,
 model text,
 memory int,
 user_id int);
```

Note that the primary key is used to partition the table across the nodes. If we query all the laptops of this user query could be extended across cluster nodes to return a few records. However, this would be a good solution to find the user who owns a laptop.

# Many-to-many

Now let's assume that laptops can be shared by many users and we have two potential queries: getting the laptops of a user and getting the users of a laptop. We create two tables to facilitate both.

# Example 19.8: Users and laptops in a many to many relationship.

```
CREATE TABLE user_laptops (
 user_id int,
 sn int,
 PRIMARY KEY (user_id, sn));
 CREATE TABLE laptops_user (
 sn int,
 user_id int,
 PRIMARY KEY (sn, user_id));
```

Using a compound primary key (`user_id, sn`) partitions a table by the `user_id` and then inside the partition, the rows are ordered by the laptop serial number `sn`. Querying the laptops of a user with SELECT * from user_laptops where user_id=?` is intended to be particularly efficient by hitting a single partition.
