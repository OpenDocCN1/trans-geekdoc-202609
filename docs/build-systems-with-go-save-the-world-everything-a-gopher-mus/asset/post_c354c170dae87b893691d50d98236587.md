## 6.6.5 Parent contexts

When creating a new context this can use the empty context.Background() or it can use another existing context. This can be used to stack restrictions and generate more complex contexts. Example 6.19 combines a timeout context with a context with values. While the value selects what action to be performed, the timeout sets the time to wait until completion. Check that for the "slow" action the message is not printed because it takes longer than the timeout limit.

# Example 6.19: Context withValue.

```go
package main

import (
	"context"
	"fmt"
	"time"
)

func calc(ctx context.Context) {
	switch ctx.Value("action") {
	case "quick":
			fmt.Println("quick answer")
	case "slow":
			time.Sleep(time.Millisecond * 500)
			fmt.Println("slow answer")
	case <-ctx.Done():
			fmt.Println("Done!!!")

			panic("unknown action")
```

## 6.7 ONCE

In certain scenarios, it only makes sense to execute certain operations once. If several goroutines can execute these operations, the sync.Once type ensures that they are run once. Its method Do receives a function by an argument that is executed a single time. This type is very useful to use with initialization functions.

Example 6.20 starts five goroutines to initialize a value. However, the initialization time for each is random. Using Once we can register the first goroutine to be started. When the Do method is invoked, other goroutines simply continue the program flow.

# Example 6.20: Single actionable variable using Once.

```go
package main

import (
	"math/rand"
	"sync"
	"time"
)

var first int

func setter(i int, ch chan bool, once *sync.Once) {
	t := rand.Uint32() % 300
	time.Sleep(time.Duration(t)*time.Millisecond)
	once.Do(func() {
		first = 1
	})
	ch <- true
	fmt.Println(i, "Done")
}

func main() {
	rand.Seed(time.Now().UnixNano())

	ch := make(chan bool)
	for i := 0; i < 10; i++ {
		go setter(i, ch, &once)
	}

	for i := 0; i < 10; i++ {
		<-ch
	}
	fmt.Println("The first was", first)
}
```

## 6.8 MUTEXES

Race conditions occur when a variable is accessed by two or several goroutines concurrently. To ensure the correctness of the program, we can set mutual exclusion areas that force goroutines to wait until no goroutine is operating in that area. The type Mutex and its methods Lock() and Unlock() restrict the access to regions. When a goroutine attempts to operate in a region it must acquire the mutex by invoking the Lock method. After the operations in the mutual exclusion finish, the unlock method returns control and other goroutines enter.

Example 6.21 shows a common scenario with three goroutines accessing a common variable. Observe that the two writers modify x with different frequencies. To make a safe mutual exclusion area defined around x, the output shows how when the reader prints the x value, it sometimes corresponds to the modifications done by the first or second goroutine.

# Example 6.21: Mutex.

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

func writer(x *int, factor int, m *sync.Mutex) {
	i := 1
	for {
		time.Sleep(time.Millisecond * 300)
		m.Lock()
		*x = *x + factor
		m.Unlock()
		i++
	}
}

func reader(x *int, m *sync.Mutex) {
	for {
		time.Sleep(time.Millisecond * 500)
		m.Lock()
		fmt.Println(*x)
		m.Unlock()
	}
}

func main() {
	x := 0
	m := sync.Mutex{}
	go writer(&x, 2, &m)
	go reader(&x, &m)
}
```

![](img/c7dcb4df7215ed1d3fb76d25373be6c7_89_0.png)

The Lock method blocks the thread execution. This means that the longer the exclusion area, the longer the wait. The size of the mutual exclusion area must be small enough to permit the execution.

## 6.9 ATOMIC

The package sync/atomic defines a set of functions for atomic operations. Atomic use low-level primitives out mutexes when used correctly. However, as stated in the Go reference, these functions must be used with care and only for low-level applications. For other applications, the sync package offers better tools (WaitGroup, etc.).

Atomic offers functions for specific native types. See Table 6.1 for a description of the available functions for type int32.

| Function | Description |
|---|---|
| AddInt32(addr *int32, delta int32) (new int32) | Add a delta value |
| CompareAndSwapInt32(addr *int32, old, new int32) (swapped bool) | If value at *addr is equal to old, return true |
| LoadInt32(addr *int32) (val int32) | Safe load |
| StoreInt32(addr *int32, val int32) | Safe store |
| SwapInt32(addr *int32, new int32) (old int32) | Swap value at *addr |

**Table 6.1:** Atomic operations available for the int32 type.

With atomic is similar to work with mutexes, we ensure safe reading and writing operations for shared variables. Example 6.22 shows how two goroutines concurrently modify the shared variable and how this is accessed. Notice how AddInt32 ensures safe concurrency without the need for a mutual exclusion area. On the other side, to ensure a safe read we use atomic.LoadInt32.

**Example 6.22:** Atomic access to variable.

```go
package main
import (
	"fmt"
	"sync/atomic"
	"time"
)

func incrementer(counter *int32) {
	for {
		atomic.AddInt32(counter, 2)
		time.Sleep(time.Millisecond * 500)
	}
}

func decrementar(counter *int32) {
	for {
		atomic.AddInt32(counter, -1)
		time.Sleep(time.Millisecond * 250)
	}
}

func main() {
	var counter int32 = 0

	go incrementer(&counter)
	go decrementar(&counter)

	for i := 0; i < 5; i++ {
		time.Sleep(time.Millisecond * 500)
		fmt.Println(atomic.LoadInt32(&counter))
	}
	fmt.Println(atomic.LoadInt32(&counter))
}
```

Atomic operations are designed only for the native types shown in Table 6.1. Fortunately, Go offers the type Value that can load and store any type by using the empty interface. Example 6.23 shows a case with a shared variable of type struct. The Value type comes with the Load() and Store() functions that perform to safely read and write our struct. In this example, updater sets values to the shared variable and one observer checks its content. By invoking monitor.load, the observer loads the latest stored version of the struct. To ensure concurrent writing, a mutual exclusion region must be defined. Observe this that the fields of the Monitor type are not modified and this may lead to concurrency problems if no mutex is used.

**Example 6.23:** Atomic access to value type.

```go
    "sync/atomic"
```
