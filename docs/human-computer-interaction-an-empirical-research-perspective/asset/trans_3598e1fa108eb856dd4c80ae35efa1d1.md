### 3.5.2 反馈与模式错误

让用户清晰知晓当前模式是用户界面设计中一项由来已久的原则。关键在于反馈。Shneiderman 和 Plaisant 建议要“提供信息丰富的反馈” [\[450, p. 74\]](#Chp003_93-160_B9780443140969000099.xhtml#br2250)。Norman 主张要“让事物可见” [\[376, pp. 17-25\]](#Chp003_93-160_B9780443140969000099.xhtml#br1880)。显然，如果用户不知道系统处于什么模式或状态，就会出现问题。

一个经典例子是 `unix` 操作系统中的 `vi` 编辑器。它有两种模式：命令模式和插入模式。`vi` 启动时处于命令模式。这本身就很有意思。如果用户启动 `vi` 后立即输入“hello”，后果自负！输入的字母会被解释为命令。用户必须输入的第一个键是“i”以进入插入模式。按下 `Esc` 键可切回命令模式。参见 [图 3.46](#Chp003_93-160_B9780443140969000099.xhtml#f0235)a。值得注意的是，没有任何反馈指示当前模式，也没有反馈指示模式间的转换。因此，`vi` 编辑器容易发生模式错误，这一现象在 HCI 文献中有详细记录（例如 [\[41\]](#Chp003_93-160_B9780443140969000099.xhtml#br0205)、[\[276\]](#Chp003_93-160_B9780443140969000099.xhtml#br1380)、[\[375\]](#Chp003_93-160_B9780443140969000099.xhtml#br1875)、[\[403\]](#Chp003_93-160_B9780443140969000099.xhtml#br2015)、[\[439\]](#Chp003_93-160_B9780443140969000099.xhtml#br2195)）。

![Figure 3.46 Changing modes and mode visibility. (a) vi editor. (b) Microsoft Word. See text for discussion.](images/B9780443140969000099/gr046.jpg)

图 3.46 模式切换与模式可见性。(a) vi 编辑器。(b) Microsoft Word。详见正文讨论。

`vi` 文本编辑器是一款传统应用，象征着 GUI 之前基于文本的顺序编程和命令行交互时代。大多数 `vi` 用户都是计算机专家——专家级用户。基于 GUI 的系统需要更高的易用性标准，因为它们面向广大用户群体，其中许多人并非计算机专业人士。这一点在第一章 [1](#Chp001_1-29_B9780443140969000075.xhtml) 中已有论述。然而，问题依然存在。Microsoft Word 中的插入模式与改写模式便是一个类似 `vi` 的例子。参见 [图 3.46](#Chp003_93-160_B9780443140969000099.xhtml#f0235)b。Word 的默认模式是插入模式。在插入模式下，输入的文本会出现在现有文本中。在改写模式下，输入的文本会覆盖现有文本。这里存在两个问题：模式切换和模式可见性。模式切换使用 `Insert` 键。这看似简单，但快速浏览键盘布局图就会发现 `Insert` 键的位置差异很大。^([^(65)](#fn65))

因此，`Insert` 键导致模式切换成为一个潜在问题。模式可见性也是一个问题。虽然有反馈（参见 [图 3.46](#Chp003_93-160_B9780443140969000099.xhtml#f0235)b），但它位于屏幕底部状态栏中。它过于隐蔽，以至于许多用户不太可能注意到。此外，意外进入改写模式的用户，可能无法将他们正在经历的问题与“overtype（改写）”这一术语建立语言关联。这是*评估鸿沟*的一个例子——即系统提供的内容与用户的意图和预期之间的脱节 [\[376, p. 51\]](#Chp003_93-160_B9780443140969000099.xhtml#br1880)。^([^(66)](#fn66))

从实证研究的角度来看，值得思考改进涉及模式的交互的方法。反馈是关键问题。音频反馈能否提高用户对模式转换的感知？更大的视觉指示是否有帮助？如果有，权衡是什么？如果进入模式时屏幕中央出现一个大的视觉指示，随后收缩为屏幕底部一个小的持久模式显示，能否提高模式感知？另请参阅本章末尾的学生练习 [3-7](#Chp003_93-160_B9780443140969000099.xhtml#o0040)。

### 3.5.3 图形与 3D

模式在图形和 3D 交互中很常见。请看 [图 3.47](#Chp003_93-160_B9780443140969000099.xhtml#f0240) 中的控制-显示操作。在 (a) 中，手+鼠标的运动结合了左右和前后移动。显示器上被操作的物体也以类似方式移动。当然，手鼠运动发生在桌面上，即 `x`-`z` 平面，而物体运动发生在显示器上，即 `x`-`y` 平面（使用 [图 3.25](#Chp003_93-160_B9780443140969000099.xhtml#f0130) 中的标注）。尽管存在空间不一致性，但用户已习惯这种（习得的）关系。在 [图 3.47](#Chp003_93-160_B9780443140969000099.xhtml#f0240)b 中，手鼠动作包含扫动或旋转运动。这里还存在一个额外的缺陷。请注意，三角形在 (a) 和 (b) 中的最终位置相同。然而手鼠的运动却不同。让我们更详细地分析这一点。

![Figure 3.47 Two-dimensional movement with the hand+mouse. (a) x and y displacement only. (b) z-axis rotation of the hand+mouse is not sensed, so the object on the display undergoes x and y displacement only.](images/B9780443140969000099/gr047.jpg)

图 3.47 手+鼠标的二维运动。(a) 仅 `x` 和 `y` 位移。(b) 手+鼠标的 `z` 轴旋转未被检测到，因此显示器上的物体仅经历 `x` 和 `y` 位移。

如果用户希望三角形随手部移动而移动，则交互就会中断。这源于二维指点设备（如鼠标）的能力与二维平面特性之间的鸿沟。典型的修复方法是*旋转模式*。在典型图形应用中旋转三角形需几个步骤：(1) 选择三角形，(2) 选择应用程序的旋转工具，(3) 获取三角形的控制柄，(4) 拖动控制柄。这在 [图 3.48](#Chp003_93-160_B9780443140969000099.xhtml#f0245) 中展示。部分 (a) 显示了 Microsoft PowerPoint 的旋转工具，下方附有使用说明。部分 (b) 显示了正在被旋转的三角形。鼠标的左右 `x` 轴运动或前后 `z` 轴运动（按住按钮拖动）用于旋转三角形。这里明显存在脱节。我们虽然能应付，但交互笨拙且困难。首先，处于旋转模式时无法平移三角形。这种控制-显示关系绝谈不上自然。

![Figure 3.48 Rotate mode. (a) Microsoft PowerPoint's rotate tool is selected, with instructions below on using it. (b) The selected triangle enters rotate mode. The x and y displacement of the mouse with the button down (dragging) is used to rotate the triangle. (c) Newer version of PowerPoint. Rotate handle appears when triangle is selected.](images/B9780443140969000099/gr048.jpg)

图 3.48 旋转模式。(a) 选中了 Microsoft PowerPoint 的旋转工具，下方附有使用说明。(b) 选中的三角形进入旋转模式。按住鼠标按钮拖动时的 `x` 和 `y` 位移用于旋转三角形。(c) 较新版本的 PowerPoint。选中三角形时会出现旋转控制柄。

在较新版本的 PowerPoint 中，选中对象时会出现旋转控制柄。参见 [图 3.48](#Chp003_93-160_B9780443140969000099.xhtml#f0245)c。这消除了对旋转模式的需求。然而，控制-显示关系依然相同——旋转用一种映射，平移用另一种映射。
