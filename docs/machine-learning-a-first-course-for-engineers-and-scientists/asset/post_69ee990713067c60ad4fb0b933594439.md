
## User aspects of model learning

Hopefully, the model will perform well the naive baselines stated above. In addition, it is also good to define an achievable performance which is on par with the maximum performance we can expect from the model. For a regression problem this performance is limited by the irreducible error presented in Chapter 4 and for classification problems the analogue is the so-called Bayes error rate. In practice, we may not have access to these theoretical bounds but there are a few strategies to estimate them. For supervised problems that are easily solved by human annotations, the human-level performance can serve as the achievable performance. Consider for example an accuracy of 99%, which serves as a reference point for what we can expect to achieve from our model. The achievable performance can also be based on what other state-of-the-art models on the same or similar problem achieve. Comparing the achievable performance gives us a reference point to assess the quality of the model. Also, if the model is close to the achievable performance we might not be able to improve our future results.

## 11.2 Improving a machine learning model

As already mentioned, solving a machine learning problem is an iterative procedure where we train, evaluate and suggest actions for improvement, by changing some hyperparameters or tuning another models. How do we start this iterative procedure?

### Try simple things

A good strategy is to try things first. This could example be to start with basic methods like k-NN or linear/logistic regression. Also, do not add extras-on like regularization for the first model—this will come at a later stage when the basic model is up and running. A simple thing can also be to start with an existing solution to the same or similar problem you trust. For example, when building an image classifier it can be simpler with using a pretrained neural network and fine-tune one later, also mean using only a subset of the available data for the first model, and retrain the model on all if it looks promising. Also, avoiding doing more pre-processing than necessary for the first step does not involve writing code for learning your first model, but also for evaluating it on your validation data using clear number evaluation metrics.

Trying simple things first allows us to explore the iterative procedure of finding a good model. This is important, since it might reveal important aspects of the problem formulation that we need to re-think before it makes sense to proceed with more complicated models. Also, if we start with a low-complexity model it reduces the risk of ending up with a too complicated model, when a simpler model would be just as good (or even better).

### Debugging your model

Before proceeding we make sure that the code we have doing what we are expecting it to do. The first objective is to make sure that the code runs without any errors or warnings. If it does not, use a debugging tool to spot the error. The tricky books are those where the code is syntactically correct and runs without warnings, but is still not what we expect it to do. The procedure how depends on the model you have picked, but there are a few general tips:

- **Compare with baseline.** Compare model performance on validation data with the baselines we have stated (see Section 11.1). If we do not manage these baselines or are even worse than then, the code for learning and evaluating the model might not work as expected.
- **Overfit a small subset.** Try to overfit the model on a very small subset (e.g., as small as two data points) of the training data and make sure that we achieve the best possible performance evaluated on training data subset. If it is a parametric model, also the lowest possible training cost.

When we have verified to the best of our ability that the code is bug-free and we are ready to proceed. There are many actions that could be taken to improve the model, for example changing the type of model, increasing/decreasing model complexity, changing input variables, collecting more data, start correcting mislabeled data (if there are any). What should we do next? Two possible strategies for guiding us to meaningful actions to improve the system are by training error and generalization gap, or by applying error analysis.

## Training error vs generalization gap

With the notation from Chapter 4, the error $E_{train}$ is the performance of the model on training data and the validation error $E_{holdout}$ is the performance on hold-out validation. In the validation step, we are interested in the model complexity and that $E_{holdout}$ is minimized. We can validate the validation error as a sum of the training error and the generalization gap

`$E_{hold-out} = E_{train} + (E_{hold-out} - E_{train}) \approx$ generalization gap`

In words, the generalization gap is approximated by the difference between the validation error $E_{hold-out}$ and the training error $E_{train}^{1}$.

We can easily compute the training error $E_{train}$ and the generalization gap $E_{holdout} - E_{train}$, we just have to evaluate the error on the training data and validation data respectively. By computing these, we can get good guidance for what changes we make for the next iteration.

As discussed in Chapter 4, if the error is small and the generalization gap is big ($E_{train}$ small, $E_{holdout}$ big), we typically overfitted the model. The opposite situation, big error and small generalization gap (both $E_{train}$ and $E_{holdout}$ big), indicates underfitting.

- Use a less flexible model. If we have a very flexible model we might start overfitting to training data, that is, $E_{train}$ is much smaller than $E_{holdout}$. If we use a less flexible model, we also reduce this gap.
- Use more regularization. Using more regularization will reduce the flexibility of the model, and hence reduce the generalization gap. Read more about regularization in Section 5.3.
- Early stopping. For models that are trained iteratively we can stop the training before reaching the minimum. One good practice is to monitor $E_{holdout}$ during training and if it starts increasing, see Example 5.7.
- Bagging, or use ensemble members if we are using it. Bagging is a method for reducing the variance of the model, which also means that we reduce the generalization gap, see in Section 7.1.
- Collect more training data. If we collect more training data, the model is less prone to overfit that extended training dataset and is forced to focus on aspects that generalizes to the validation data.

If we want to reduce the training error (4.11), by approximating $E_{train} \approx E_{train}$ and $E_{new} \approx E_{holdout}$. If we use k-fold validation instead of a hold-out validation data, we use $E_{fold} \approx E_{holdout}$, when computing the generalization gap.

## Learning curves

Of the different methods used to reduce the generalization gap, collecting more training data is the simplest and most reliable strategy. In contrast to the other techniques, collecting and labeling data is far more costly than consuming. Before collecting more data, we would like to tell how much improvement we can expect. Learning curves can give us such indication.
In a learning curve we train models and evaluate $E_{train}$ and $E_{holdout}$ using different sizes of the training data. For example, we can train different models with $10\%$, $20\%$, $30\%$, $\dots$ of the available training data and plot $E_{train}$ and $E_{holdout}$ with the amount of training data. By extrapolating these plots, we can get an indication of the improvement on the generalization gap we can get by collecting more data.
