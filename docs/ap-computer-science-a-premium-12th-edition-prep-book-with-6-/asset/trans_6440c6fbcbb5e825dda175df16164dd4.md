

## 答案解析

[1](#51_Chapter43.xhtml#fn6-1). **(E)** 程序员绝不应单方面决定程序规格说明。存疑时，应与编写规格说明的人核对。

[2](#51_Chapter43.xhtml#fn6-2). **(D)** 在 I 和 II 中，被操作的对象是一个三位数。然而对于 III，对象是一个六字符字符串，这暗示了一个不同于 `ThreeDigitNumber` 的类。

[3](#51_Chapter43.xhtml#fn6-3). **(E)** 自顶向下编程包含列出主对象的方法，然后使用逐步求精将每个方法分解为子任务列表。排除选项 A、C 和 D：自顶向下编程指的是设计和规划阶段，不涉及任何实际代码编写。选项 B 更接近要点，但“自顶向下”意味着操作列表，而非描述方法的文章。

[4](#51_Chapter43.xhtml#fn6-4). **(E)** 选择算法时，这三个考量因素均有效。如果你的代码将成为由多位程序员创建的大型项目的一部分，因素 III 尤为重要。然而，即使你是某软件的唯一编写者，也要意识到你的代码将来可能需要由他人修改。

[5](#51_Chapter43.xhtml#fn6-5). **(B)** 导致过度数据移动的过程是低效的。将元素插入其正确（已排序）的位置涉及移动元素以腾出空位。在最坏情况下，新元素必须插入第一个位置，这涉及将每个元素都向上移动一个位置。类似地，删除元素涉及将元素向下移动一个位置以填补“空隙”。在最坏情况下（删除第一个元素），数组中的所有元素都需要移动。对列表中最小的五个元素求和意味着对前五个元素求和。这不需要测试元素，也不涉及过度数据移动，因此是高效的。在已排序列表中查找最大值非常快——只需选取列表适当一端的元素即可。

[6](#51_Chapter43.xhtml#fn6-6). **(C)** “健壮性”意味着能够处理用户输入的所有数据，并即使对于极端数据值也能给出正确答案。一个不健壮的程序完全可能在另一台计算机上无需修改即可运行，而一个健壮的程序在另一台计算机上运行前可能需要修改。

[7](#51_Chapter43.xhtml#fn6-7). **(C)** 排除选项 D，因为 0 是无效重量，且从方法描述可推断无效数据已被筛除。排除选项 E，因为它测试了 10–25 范围内的两个值（这并非错误，但选项 C 更好）。排除选项 A，因为它仅测试端点值。排除选项 B，因为它*不*测试任何端点值。

[8](#51_Chapter43.xhtml#fn6-8). **(A)** 该语句在语法上是正确的，但按原样编写将无法求出这些整数的平均值。因此该 bug 属于意图错误或逻辑错误。要按预期执行，该语句需要加上括号：

```
double average = (n1 + n2 + n3 + n4) / (double) 4;
```

[9](#51_Chapter43.xhtml#fn6-9). **(D)** 发生的错误是由尝试除以零（`ArithmeticException`）引起的运行时错误。不要被选项 C 迷惑。仅从输入文件读取表达式 `8/0` 不会导致错误。注意如果操作数类型为 `double`，正确答案将是 E。在这种情况下，除以零不会导致异常；它会给出 `Infinity` 作为答案。只有检查输出时才会清楚地发现出了问题。

[10](#51_Chapter43.xhtml#fn6-10). **(D)** 游戏 I 和 II 非常适合使用整数值来描述下一步移动。对于猜数字游戏，`getMove()` 将返回下一次猜测；对于筹码游戏，`getMove()` 将返回玩家回合移除的筹码数量。游戏 III 井字棋要求玩家的下一步移动是 3×3 网格上的一个位置：简单的整数值不适合作为 `getMove` 方法的返回类型。

[11](#51_Chapter43.xhtml#fn6-11). **(A)** 前置条件不关心方法的动作、局部变量、算法或后置条件。它也不初始化参数。它仅断言方法执行直接之前必须为真的条件。

[12](#51_Chapter43.xhtml#fn6-12). **(A)** 最佳情况导致最少的计算机操作，最坏情况导致最多的操作。在给定算法中，初始测试 `if (a1 > a2)` 和对 `max` 的赋值无论哪个值最大都会发生。第二个测试 `if (max < a3)` 也将始终发生。最终语句 `max = a3` 仅在最大值位于 `a3` 时发生；因此这代表最坏情况。所以最佳情况必须是在 `a1` 或 `a2` 中包含最大值。

[13](#51_Chapter43.xhtml#fn6-13). **(D)** 前置条件是关于循环执行前变量的断言。变量 `N`、`k` 和 `sum` 均已初始化为选项 D 所示的值。选项 C 错误，因为 `k` 可能等于 `N`。选项 A 错误，因为 `k` 可能小于 `N`。选项 E 错误，因为 `mean` 直到循环退出后才被定义。选项 B 错误，因为它省略了关于 `N` 和 `k` 的断言。

[14](#51_Chapter43.xhtml#fn6-14). **(C)** 排除选项 A 和 B，因为 `i` 在 `for` 循环中被初始化为 `3`。选项 D 和 E 错误，因为第一次循环时 `i` 等于 `3`。

[15](#51_Chapter43.xhtml#fn6-15). **(D)** 量 `a` 被加到 `total` 中 `b` 次，这意味着执行结束时 `total = a*b`。

[16](#51_Chapter43.xhtml#fn6-16). **(D)** 让 `Item` 负责其名称、单价、数量和总价是合理的。让它负责*其他* `Item` 是*不*合理的。然而，既然 `ItemList` 将包含所有购买 `Item` 的信息，让它同时计算总 `amountDue`（应付金额）是合理的。让 `Invoice`（发票）负责显示购买物品的信息以及提供最终总计 `amountDue` 同样合理。

[17](#51_Chapter43.xhtml#fn6-17). **(C)** *is-a*（是一个）关系定义继承，而 *has-a*（有一个）关系定义关联。这两种关系是互斥的。例如，研究生 *is-a* 学生。说学生 *has-a* 研究生是讲不通的！

[18](#51_Chapter43.xhtml#fn6-18). **(B)** 尽管让 `Tire` 对象继承 `Circle` 方法很方便，但 `Tire` 和 `Circle` 之间的继承关系是不正确的：说 `Tire` *is-a* `Circle` 是错误的。`Tire` 是汽车零件，而 `Circle` 是几何形状。注意 `Tire` 和 `Circle` 之间存在*关联*关系：`Tire` *has-a* `Circle` 作为其边界。

[19](#51_Chapter43.xhtml#fn6-19). **(E)** 独立类与其他类没有关系，因此可以更容易地编写代码和测试。

[20](#51_Chapter43.xhtml#fn6-20). **(C)** 在这种语境下使用时，“program”（程序）一词永远不会被包含在内。“integer”（整数）一词描述坐标 *x* 和 *y* 的类型，在规格说明中无进一步用途。虽然“direction”（方向）、“boundary”（边界）和“simulation”（模拟）等词稍后可能会从候选类中移除，但在你斟酌设计时保留它们作为候选并非不合理。
