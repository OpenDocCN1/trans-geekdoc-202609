## 5.4.2 Architectural Overview

5.3 shows the architecture of the designed system consisting mainly of five AWS EC2 instances which are responsible for handling the function of IoT server, Suricata IDS, ELK stack SIEM, trained ML models (RF and XGBoost) and the attacking machine. All instances had to be interconnected for a seamless interaction between them, which would enable real-time threat detection. Executing on solution also enabled the system to be completely isolated and controlled for the experimental purpose. The IoT server hosts the virtual IoT devices on Node-RED and communicating with MQTT broker as the primary target for the DDoS attack, as it represents to be an integral part of any IoT setup. The attacking machine was used to simulate the DDoS attack via a docker container which would generate the SYN and UDP flood attack using the ping3 command. Traffic mirroring was done on AWS by setting up mirror session between the IoT server and IDS. This approach ensured complete monitoring of the resource. The Suricata IDS was then responsible for analysing this captured traffic and generating detailed logs for all the network activity. These logs were then passed to the SIEM server with the help of filebeat (a lightweight shipper), where the logs were indexed and presented in real-time dashboards. The ML models were deployed and run on an EC2 instance which would link them to the SIEM for instance detection. This connection helped in SIEM sending the logs to the instance where the models could classify the DDoS and benign and predict the attacks. Within Elasticsearch, two distinct indexes are maintained: one for rule-based detections generated by Suricata and another for logs that are analysed by ML models. These indexes help in splitting the results from both sources, ensuring a comprehensive analysis. Lastly, Kibana is used as the visualization layer to provide more engaging dashboards for the outcome of rule-based and ML-based detections. The central component for generating system alerts, the dashboards grant administrators visibility into system activity and expose possible attacks, their trends, and categorisation, which is useful for managing network activity.

- Suricata (IDS): This IDS being an open-source and highly customizable system emerges to have prominence to perform a real-time network traffic analysis. It generates detailed logs of the captured network activity which is primary need of the research. It also supports emerging threat rule sets real-detection of not only DDoS and attack patterns but also hundreds of other attacks. Snort IDS) [17] (Waleed, Jamali and Masood, 2022).
- ML models (RF and XGBoost): Both being ensemble learning models have improved classification rate and can reduce overfitting notably. While RF is a robust ML model usually used to handle large datasets, XGBoost provides optimum performance over unbalanced datasets, making both an ideal selection for adaptive detection in real-time environment considering their speed and effectiveness.
- Node-RED: Being user-friendly with flow-based interface, Node-RED was chosen to simulate the IoT devices because it aids in quick prototyping and visualizing the IoT data flows. It gives a simple platform to create the functions of real devices such as temperature sensors, motion detectors and humidity monitors and also save them to the MQTT broker.

Unlike HTTP-based communication, MQTT offers a better messaging with a lower overhead that makes it suitable for IoT cases where devices are.

## 5.4.4 Design Considerations and Constraints

The balance between realism, scalability and adaptability was the core while designing the entire system. Scalability was highly prioritised as the system had to deal with large volume of traffic which would be generated during the simulated attack; this traffic was to be processed for giving the results in real time. Thus, the use of AWS EC2 instances became crucial as it provided the flexibility to deploy components with different computational needs, as lightweight instances for attacking server and other machines and high-performance and high storage instances for IDS and SIEM. This setup was entirely in an AWS environment, ensuring that simulated attacks are not creating any issues for the external system. Docker container was deployed on the attacking machine to set apart the traffic sources of two distinguished attacks. This enabled control over traffic generation without any issues, as cross-contamination of logs. The next big thing to be constituted realism as the entire setup had to be replicated as a real-world attack scenario. The usage of MQTT broker resembles an actual communication happening between the IoT devices with its central hub. Also, the system encompasses the rules set from emerging threat point on Suricata, the detection capabilities of the system in terminating the DDoS attacks were enhanced and well equipped with industry standards.

While all this to be done, several challenges arose during the implementation, which were to be addressed and overcome for making a resilient system. Initially, AWS lambda and AWS Sagemaker were implemented for the deployment of ML models. But due to configuration and connectivity issues and also because of problems raised by IAM constraints, this approach was not feasible and thus was replaced by the adoption of EC2 instances wherein these models are deployed.
