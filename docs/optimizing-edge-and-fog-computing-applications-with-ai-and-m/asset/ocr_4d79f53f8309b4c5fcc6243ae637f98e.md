Elasticsearch and Kibana configuration: Elasticsearch is deployed as a single-node cluster. It is configured to listen on all the network interfaces (0.0.0.0) on port 9200 so that connections between the localhost can be accepted. This was mainly essential for ensuring a seamless connection with other SIEM components, like Logstash and Kibana. The xpack.security module was added to support the authentication and secure access through API keys. On the other hand, Kibana has also been configured to bind all the network interfaces as server.host is set to 0.0.0.0 on port 5601. For accessibility from any system, with the network and interaction with Elasticsearch. Although Elasticsearch and Kibana are configured to an initial localhost for development usage, these parameters were changed to fix the distributed cluster structure. Elasticsearch accesses its own credentials which are set in its conf file (kibana_system user and passwords). Along the default elastic rules, a total of 686 are updated in the Kibana along with the custom rules. For rule detecting DDoS in Kibana, which uses suricata-logs-* and fields such as: type, alert.signature and hostname. The DDoS detections are generated on SYN flood signatures tagged as Attempted Denial of Service attack patterns. A specific connector was put in place for the integration of this rule which made sure the alerts are stored in a particular index.

ML integration-: Here two .pkl files for the selected ensemble learning models which are pre-processed as per the instructions in Section 5.4 are hosted in a h3micro server. These models are deployed to analyse the logs in real time from suricata-logs-* located at Elasticsearch. A connection to Elasticsearch is established here using the Representational State Transfer (REST) Application Programming Interface (API), using the SIEM server IP is 35.172.58.170. It has also been using the authentication credentials for a secure data connection. As the system is designed to work continuously with real-time data, the @timestamp field is used to fetch only the logs that are new or updated since the last batch processed. This dynamic strategy helped the models to deal with fresh data every day. The next step is the preprocessing pipeline which is applied to extract the relevant features from the fetched logs to match the feature requirements of the model for effective classification. Logs with missing values are filtered out during this stage to ensure that the model works on complete data.
