*   线性计数在主内存中使用一个大小为 `m` 的哈希表以及一个哈希函数。哈希表的每个条目都初始化为 0。对于每个传入的项目，应用哈希函数，并将哈希表中对应的索引设置为 1。

*   接下来，记录空白条目（即 0）的数量。我们将这个数字称为 `x`。然后通过取 `x` 和 `m` 的分数来分析空位的比例（`V[n]`）。最终估计的基数是通过将值代入以下方程计算得出的：

    $$\\begin{array}{l} {\\,\\hat{n} \\approx - m\\, ln\\, V\\_{N}} \\\\ \\end{array}$$  

    (11.1)

    其中，`n` 是计算出的估计基数。

线性计数算法的时间复杂度为 `O(n)`，其中 `n` 是集合 `S` 中元素的总数。线性计数算法结果的准确性取决于负载因子。在这里，负载因子定义为唯一元素与哈希表大小的比例。负载因子值越高，结果的准确性越低；负载因子值越低，结果的准确性越高。因此，如果哈希表大小相对于元素总数非常小，可能会导致高碰撞风险。否则，如果哈希表大小足够大，碰撞风险会降低，但它会占用更多空间。作者得出结论，对于大于 1 的负载因子，线性计数会产生 1% 的错误。对于给定的包含 `N` 个唯一元素的多重集，估计基数 `n̂` 的预期相对误差由公式 11.3 给出。变量 `t` 表示负载因子（$\frac{N}{m}$）。相对误差表示，平均而言，估计基数 `n̂` 有多少百分比被错误计算，并由以下公式给出。

$$\\begin{array}{l} \\frac{(e^{t} - t - 1)}{2N} \\\\ \\end{array}$$  

(11.2)

哈希表大小也受标准误差的影响。标准误差被描述为 $\frac{\hat{(}n)}{N}$ 的标准偏差，并通过以下方程计算。

$$\\begin{array}{l} {\\sqrt{m}\\frac{{(e^{t} - t - 1)}^{1/2}}{N}} \\\\ \\end{array}$$  

(11.3)

尽管为了使用此方法，必须事先知道唯一项目的数量，以便分配适当大小的哈希表。显然，线性计数方法比传统方法更快，但它无法产生准确的结果。因此，这种数据结构的用例是针对不需要 100% 准确性的应用。尽管如此，`[[38](#bib.xhtml#ch00-bib-38)]`中的作者建议不要对基数大于 2000 万的数据库关系使用线性计数算法，因为表大小极大。该方法能以更少的存储需求提供更准确的结果。作为更好的解决方案，LogLog 和 HyperLogLog 算法也可用。

让我们通过一个示例来理解线性计数。假设 `m` = 16，且哈希函数基于模哈希，即 `h(k)` = (`k` + 2)*`m`**o**d*16，其中 `k` 是要插入的键。设集合 `S` 包含总共 10 个元素，即 `S` = 4, 34, 6, 4, 14, 36, 6, 7, 0, 7。值得注意的是，该集合的基数为 7。将这些元素传递给哈希函数并将相应的位设置为 1。传递这些元素后哈希表的结果状态表示为 `h(4)` = 6, `h(34)` = 0, `h(6)` = 8, `h(4)` = 6, `h(14)` = 0, `h(36)` = 2, `h(6)` = 8, `h(7)` = 9, `h(0)` = 2`a**n**d**h(7)` = 9。在这种情况下，`x` 的值为 11，负载因子为 $\\frac{7}{16}$，因此（`V[n]`）的值为 $\\frac{11}{16}$，等于 0.6875。要获得最终估计基数，将（`V[n]`）的值代入公式 11.1，结果为 `n̂` ≈  − 16 \* `l**n`(0.6875)，求解后得到 5.99 ≈ 6。由于碰撞，估计计数为 6，而实际基数为 7。整个示例在 `[Fig. 11.1](#14chap_11.xhtml#fig11_1)` 中表示。

## [11.3 LogLog](#contents.xhtml#rsec11_3)

线性计数仍然消耗 O(n) 空间，即线性空间消耗。在此背景下，`[[74](#bib.xhtml#ch00-bib-74)]`中引入了 LogLog，它为大型数据集的基数估计提供了解决方案。该算法使用的内存量级为 `l**o**g`[2](`l**o**g`[2](`N`))，其中 `N` 是唯一项目数量的上限。为了计算 2^(32)（40 亿）个不同的项目，该算法只需要 `l**o**g`[2](`l**o**g`[2](2^(32))) = 5 位的空间。为了理解 LogLog 的概念，举个类比：假设两个朋友 Tom 和 Jerry 参加了一个会议，他们在那里决定打赌谁与最多陌生人互动。于是，他们开始记录自己互动的人数。然而，这样计数可能是一项繁琐的任务。因此，在下一次会议中，他们不再只是计数，而是开始在纸上写下名字。这样更容易计算唯一的人数，而不是被总对话次数搞混。然而，随身携带笔和纸并不容易。于是，Tom 提出了一个替代方案，而不是记下人的名字，他们决定询问对方联系号码的最后 6 位数字，最后 6 位数字中前导零序列最长的人将被宣布为获胜者。例如，某人的联系号码是 988866336，那么这里的最长序列是 0，因为没有前导零；如果联系号码是 00639，那么最长序列变为 2。显然，如果 Tom 或 Jerry 只与少数人互动，获得最长前导零序列的概率要么是 0，要么是 1。随着他们互动的人数增加，获得前导零序列的机会会增加到 3 或 4。要获得最长零序列为 6 的值，他们中的任何一人都必须与数千人互动，才能找到某人其联系号码的最后 6 位数字为 00000。

同样的概念应用于 LogLog 算法。在这里，通过对每个元素进行哈希处理，然后记录每个元素的最长零序列，来计算大型集合中的唯一元素。LogLog 使用一个包含 `m` 个条目或桶的哈希表，以及一个单一的哈希函数。值得注意的是，随着 `m` 值的增加，平均错误率会降低。由于哈希函数的输出长度固定，元素插入的时间复杂度为 O(1)。使用 LogLog 估计基数的逐步说明描述如下：

*   对于每个传入的项目，计算每个项目的固定长度哈希值。
