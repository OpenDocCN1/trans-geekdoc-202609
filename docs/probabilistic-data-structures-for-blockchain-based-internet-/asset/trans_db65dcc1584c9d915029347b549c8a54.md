

值得注意的是，网络使用量的增加影响了网络中的获取延迟。在此背景下，分布式代理服务器通过维护彼此代理服务器信息的网页缓存内存来改善延迟，从而允许从客户端附近的邻居缓存中访问所需页面，而不是从原始网页源访问。网页缓存共享可以从 `BF` 中获益良多，因为总消息交换量与代理服务器总数成平方关系。网页缓存的优势在于降低因互联网请求增加而导致的不必要带宽消耗。在此过程中，每个代理服务器都配备了其他代理服务器缓存文档的紧凑且汇总的信息。Web 代理服务器定期构建当前缓存条目的 `BF` 并将其广播到网络中。对于缓存未命中，代理服务器会探测 `BF` 以查找其他代理服务器中的缓存命中。然后将查询发送到结果为正的代理服务器。假阳性概率通过减少带宽消耗得到补偿，因为 `BF` 阻止了完整的 URL 缓存摘要列表的传输。分布式 Web 缓存的概念在 [图 10.7](#13chap_10.xhtml#fig10_7) 中表示。

在此，在计数 `BF` 中，而不是使用单个位来表示过滤器中的每个条目，而是使用固定大小的计数器值来跟踪哈希到该位置的元素计数。为了避免计数器溢出，毒药近似建议大多数应用程序每个计数器使用 4 位。计数 `BF` 不仅仅用于检查元素的存在，而是用于检查元素出现 `θ` 次或更多次的情况，其中 `θ` 表示计数阈值。例如，如果 `θ`=2 对于一击即绝的情况，它意味着特定事件的一击或两击。与标准 `BF` 类似，计数 `BF` 也会产生假阳性。但是，与标准 `BF` 不同，如果尝试从过滤器中删除从未插入的元素，计数 `BF` 可能会导致假阴性。参数 `m`、`n`、`k` 的定义与标准 `BF` 相同。但是，计数 `BF` 会导致空间浪费，如在 \[[51](#bib.xhtml#ch00-bib-51)\] 中报告。

最初，此过滤器中的所有位均为零。计数 `BF` 支持的操作描述如下：

*   插入：要插入元素，将其传递给 `k` 个哈希函数，并将与这些哈希函数对应的 `k` 个计数器各加一。为了解释这一概念，请考虑具有 3 个哈希函数的 `BF`，即 `h[1]`、`h[2]`、`h[3]`，其中 `h[1]` = `x mod 10`，`h[2]` = `(2x + 3) mod 10`，`h3` = `(2 * x) mod 10`，且 `x` 表示要插入的数字。元素 9、15、8 的插入在 [图 10.8](#13chap_10.xhtml#fig10_8) 中表示。每个元素对应的哈希索引为：

    `h[1](9)` = 9, `h[2](9)` = 1, `h[3](9)` = 8

    `h[1](15)` = 5, `h[2](15)` = 3, `h[3](15)` = 0

    `h[1](8)` = 8, `h[2](8)` = 9, `h[3](9)` = 6

然而，计数溢出是计数 `BF` 的一个缺点。如果计数器值达到 `2^(w) − 1`（其中 `w` 表示计数器的宽度），则在此点之后无法再增加。计数 `BF` 还支持与标准 `BF` 所述相同的应用。不同之处在于，可以将计数 `BF` 用于替代 `BF`，以允许从 Web 缓存中删除最近最少使用的 Web 信息。计数 `BF` 的一个有价值的应用是通过在短时间内对给定网页的访问设置近似计数来检测 DDoS 攻击。

#### [10.2.3.2 Compressed BF](#contents.xhtml#rsec10_2_3_2)

引入压缩 `BF` \[[146](#bib.xhtml#ch00-bib-146)\] 的意图是使 `BF` 能够作为消息在不同网络节点之间传递。压缩是减少传输大小的有效技术，压缩 `BF` 可以提高网络性能。然而，作者推荐使用算术编码来实现快速压缩过程。显然，开发者关注的是优化高流量网络中的传输大小。除了减少要广播的位数外，假阳性率和查找成本也会降低。不幸的是，压缩和解压缩会增加处理成本。在此，哈希函数不是针对 `m` 和 `n` 进行优化，而是针对传输大小（不一定是 `m`，而是压缩数组）。但是，压缩后的目标是尽量降低假阳性概率。

在标准 `BF` 中，开发者的主要关注点是通过操纵 `k` 来最小化假阳性概率，前提是 `m` 和 `n` 为固定值。当每个位置被设置为 0 或 1 的概率为 `1/2` 时，标准 `BF` 针对 `k_opt = ln(2) m/n = 0.7 m/n` 进行了优化。虽然，在压缩 `BF` 中，`k` 的选择使得每个数组条目为 1 的概率为 `1/3`。因此，由此产生的不平衡过滤器将包含 `1/3` 的 1 和 `2/3` 的 0，从而易于压缩。此特性被用于压缩 `m` 位数组并抑制其传输大小。为了实现这一点，对于大型过滤器大小，采用了减少的哈希函数数量，以便在网络中传输的位数比标准 `BF` 少，且具有低假阳性率。具体来说，在传输相同位数的情况下，压缩 `BF` 比标准 `BF` 实现更低的假阳性率。值得注意的是，假阳性率降低到 `0.5^((z/n))`，其中 `z` 是压缩后的数组大小。作者得出结论，随着过滤器大小的增加，可以尽量减少哈希函数的使用。[表 10.2](#13chap_10.xhtml#tab10_2) 显示了每个元素使用 8 位进行传输时的结果，即 `z/n = 8`。与标准 `BF` 类似，使用完全随机哈希函数，且无法删除元素。此外，`w` 的大值可能导致由于未使用的零的数量而造成空间浪费。因此，确定 `w` 的正确值是一个复杂的权衡，取决于应用程序类型和数据分布。此外，`BF` 的其他变体，如计数 `BF`，也可以从这种压缩中受益。在接收节点，`BF` 被解压缩。显然，此过滤器在端点仍然需要较大的内存空间。具体来说，压缩 `BF` 用于分布式节点之间的 P2P 共享。然而，计算能力和内存资源有限的轻量级节点可能无法处理此复杂算法。
