## 3.2. Finality

It is an affirmation that all the committed blocks in the blockchain will not be revoked again if wrong data is input in the blockchain. As the transaction once added to the blockchain could not be altered. Finality falls back to Nakamoto Consensus. When the race ends and the longest chain proof of work overtakes the attacker chain eventually (no matter how long), it is finalized in the purest sense. The 51% attack is discussed by Satoshi in his first white paper, which elaborates that blockchain characteristics can be overtaken by attaining 51% of the computation power. To ensure the proper functioning of blockchain, finality becomes vital. There are three types of finality in the blockchain:

*   **Probabilistic Finality**
*   **Absolute Finality**
*   **Economic Finality**

In probabilistic finality, chained-based protocols are used. Bitcoin’s Nakamoto consensus is an example of probabilistic finality, where it is recommended to wait for at least 6 blocks to confirm a transaction. This ensures the less likelihood of revert of transaction. In the case of absolute finality, a transaction is confirmed by PBFT-based protocols, viz. Tendermint. A list of validators approves the transaction. Economic finality applies monetarily cost for a block to be reverted. This type of finality is opted by Casper FFG.

According to Eric Brewer’s CAP theorem, in case of partition, a distributed system can preserve either consistency or availability. Consistency ensures the correct state of the system which can be attained through probabilistic finality, and availability is favoured by absolute finality.

## 3.3. Scalability

Scalability is one of the main rooted issues related to blockchain. Researchers are trying to solve the scalability issue from its initial stage. Scalability defines the number of transactions per second. The very first application of blockchain is Bitcoin that offers a maximum of 6-7 transactions per second (tps), and the 2nd application is Ethereum that offers 20 tps, which is very low as compared to other applications' transactions. For example, Visa handles 1667 tps, PayPal processes 170 tps, etc. (Conti, Kumar, Lal, & Ruj, 2018).

Scalability depends on many factors such as block size, network latency, consensus algorithm, complex calculations, etc. With the advancement of these factors, we have to compromise with security and tend more towards centralisation. ### 3.3.1 Block Size

Nakamoto suggested 1 MB block size for Bitcoin. These blocks contain numerous transactions. Generally, a block contains approximately 1500-3500 transactions, given the 1 MB limit. It varies with the size of transaction details. Miners take 10 minutes to generate a new block (Conti et al., 2018). Let's consider some cases with block size to increase the scalability.

The first one is to increase block size up to a tolerable limit that will acquire more transactions. In this case, all nodes need to perform all the required calculations. Due to the increase in size, it will be harder for the node to process all transactions. To verify the transactions, miners need more advanced resources, and it will filter out the less equipped miners and empower the more equipped miners. Thus, it will lead to more centralisation. Also, it results in threats to security like the 51% attack.

The second case is to increase the block size up to infinity. This case is the worst situation. For miners, it will be very difficult to process the transactions, and resources can’t be enough for it. The final case is to increase block size narrowly. It will amass a bit more transactions but it is not an optimal and feasible solution.

Another case is that we have several blockchains and run different applications on different blockchains, i.e., no need to run all computation on a single blockchain; rather, distribute it. This approach distributes the load of a single blockchain into many of them. So, it increases the performance but will bargain with Security. This approach will distribute the hash power across different blockchains, and to avoid a 51% attack, we need a large chain that should have all hashing power with it. So, scattering the hash may lead to security issues.

### 3.3.2 Median Confirmation Time: Another Reason for Scalability

This is one more reason that delays the transaction and generating the block. Median Confirmation Time is the duration of time that the user must wait as the transaction is accepted into a mined block. It happens due to the lower transaction fee. The higher the transaction fee, the more chance to be accepted for mining. Currently (on 19-05-2020), 71,141,960 bytes is the aggregate size of transactions that are waiting to be confirmed, and this is known as Mempool size.

To solve the scalability issue, many approaches have been done and some new techniques and methods are introduced. Sharding and Lightning Network are the methods that tried to solve the scalability issue. Now, we will have a look over them.

### 3.3.3 Sharding

Sharding is a database concept to make it more efficient. In blockchain, Sharding splits the overhead of computation among multiple groups of shards/nodes. These shards keep a part of the blockchain and not the complete blockchain information. These shards work in parallel to increase efficiency, allowing the network to enhance scalability. Sharding-based projects are Ethereum, Zilliqa, and Cardano to get scalability solutions. However, Sharding is still an unproven technology in terms of blockchain (Moubarak, Filiol, & Chamoun, 2018).

### 3.3.4 Lightning Network

This technique is also called an off-chain approach. In this network, there is no need to keep each record on the blockchain; rather, it adds another layer on top of the blockchain and creates a payment channel between any two parties on that extra layer.

These two parties need to create a multi-signature wallet and they can access it with their private keys. At least one of them must deposit some amount of cryptocurrency into that wallet. After every payment, the amount will be deducted from the wallet if both do signing with their private keys. They can do any number of transactions on this channel. They can use this channel as long as they need. Anyone of them can close the channel. After closing, the latest balance sheet of the wallet that was signed by both parties will be broadcast to the network. Miners will check the balance sheet and if found everything right, will release the funds to the respective parties. This will be considered as a single transaction on the blockchain. So in this way, the Lightning Network can reduce the load on the blockchain (Poon, Dryja, 2016).
