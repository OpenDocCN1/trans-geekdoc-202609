From the previous researches, we can see that it is necessary to use sufficient blocks to generate an unbiased randomness. But in Plume, we do not need an unbiased randomness, we just need a randomness that has sufficient entropy so that adversaries cannot manipulate the randomness to let the proportion of the adversaries in committee above threshold. We get our randomness from a confirmed slow block by computing the hash of the block, i.e., $r_i = H(B_i^s)$. And we switch to the next slow block to generate the next confirmed randomness an certain interval that is $E$ slots, where $E$ is a systemic parameter. More precisely, we get our first randomness $r_0$ from the genesis block $B_0^s$ of a confirmed slow blockchain, after $E$ slots where $E$ is larger than the interval of generating a slow block, we get the second randomness $r_1$ from the block $B_1^s$, and so on.

Every party in the network can become a committee in $slot_j$ by computing $(y, \pi) = \text{VRF}_{s,k}(slot_j || r_i)$, as long as his public key is registered in block $B_j^s$ or the blocks before it, where VRF(Verifiable

Random Functions)[11] is firstly proposed by Miceli in 1986. If $y < D$ where $D$ is the difficulty, the party can generate a fast block in $slot_j$, and how to generate it will be described in section 4.4.

# **4.3 Receiving fast blocks and ordering them**

For a party that is always online, he will receive the fast blocks generated by others, and he needs to order them according to the *slot* recorded in the block. Once he receives a fast block $B_F$, the first thing he needs to do is to check the validity of the block according to definition 3.2. If the fast block is valid, he will decide which set the fast block belongs to. Because of network delay, there is the possibility that a party receives a fast block before receiving its ancestors. It is necessary to check if the ancestors have been received.
