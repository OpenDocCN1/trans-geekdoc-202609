Before ordering the fast blocks in DAG G, the party needs to select some fast blocks from candidateSet and pendingSet into confirmedSet. If a fast block in candidateSet or pendingSet whose child nodes in a period are enough, it can be selected into confirmedSet. In $\Delta$ slots after it was generated, it might not have spread all over the network, because of the maximum network delay $\Delta$ slots. Thus, we just consider the child nodes generated more than $\Delta$ slots later than the fast block. Formally, for a fast block $B_f$ in candidateSet or pendingSet, if the number of Density[$B_f$, Slot[$B_f$] + $\Delta$, Slot[$B_f$] + $\Delta$ + $T$] is larger than the threshold $T$ the party would add $B_f$ into confirmedSet. Then the party needs to give every fast block in confirmedSet a unique sequence number according to the slot value included in the fast block. The larger slot value a fast block has, the larger sequence number it will get. There is the possibility that more than one fast blocks have the same slot value, we order them by comparing their hash values. The details is shown in Algorithm 2.

## 4.4 Generating fast blocks and organizing them into DAG structure

A party who gets the qualification by computing ($y, \pi$) can pack his local transactions and generate a fast block in a slot $t$. Besides calculating merkle_root and signing the fast block, the most important thing is how to reference previous fast blocks. Before describing the reference rule, we need to define some notation.

**leaf node**. In a party's view, if a node is valid and has not been referenced by any other nodes, we call it leaf node. The three black shaded nodes in Fig. 2 are leaf node. And because of network delay and the behaviors of malicious adversaries, the sets of leaf nodes for different party may vary different. Therefore, there is not a unique set of leaf nodes on the whole, the concept is relative to a party. In order to guarantee that a fast block can be referenced directly or indirectly by all the fast blocks later, we require a new fast block $B^{new}_f$ to reference all the qualified leaf nodes in candidateSet.

**qualified leaf nodes**. Leaf nodes in candidateSet can be divided into two categories showed in the two red boxes (labeled in “1”, “2” respectively) in Fig. 2. We denote the slot in which the new fast block $B_{f}^{new}$ is generated as $t$, and we can see that the difference value between the generating times of the fast blocks labeled in "1" and $t$ is less than 2Δ slots. We regard the fast blocks labeled in "1" as qualified leaf nodes and require $B_{f}^{new}$ to reference them, but the fast block labeled in "2" was generated more than 2Δ slots ago, so $B_{f}^{new}$ cannot reference it. The details is shown in Algorithm 3.

**Algorithm 3** Generate a Fast blocks

**Require:** $DAG \mathbb{G}$, candidateSet, current slot $t$, $(y, \pi)$, randomness $r$, tlist $L_{tx}$ and sign key $sk$.

**Ensure:** $B_{f}^{new}$.
1: Calculate merkle_root based on the tlist;
2: Set reference_number = 0 and reference_hash = {};
3: **for** each leaf node $B_{j}^{leef-j}$ in candidateSet **do**
4: 	**if** $t - Slot[B_{j}^{leef-j}] \le 2\Delta$ **then**
5: 		reference_hash=reference_hash+{hash($B_{j}^{leef-j}$)};
6: 		reference_number=reference_number+1;
7: 	**end if**
8: **end for**
9: Calculate signature $\sigma$ on $(y, \pi)||r||t||merkle_root||reference_number||reference_hash||L_{tx}$ by $sk$;
10: $B_{f}^{new} = (y, \pi)||r||t||merkle_root||reference_number||reference_hash||L_{tx}||\sigma$;
11: Output $B_{f}^{new}$.

## 4.5 Storing the current state of DAG in slow blocks for quick start of a new party

If a new party wants to join the network, he needs to download the whole DAG he missed. But adversaries can send him an incorrect DAG that the new party but cannot judge it. So we require the miners of slow chain to store the current state of DAG in their slow blocks. The new party can check the correction of a received DAG according to the states recorded in slow chain. For a new party, he cannot decide which fast block can belong to pendingSet during the downloading of DAG that generated before his joining, because he missed these fast blocks. For the DAG that he has missed, he needs to verify the validity of every fast blocks, and adds valid fast blocks whose child blocks are enough to confirmedSet, then add their valid child fast blocks who need more time to confirm to candidateSet. It is possible that adversaries give the new party a DAG part that was hidden before. If the part meets our requirement, we regard it valid, otherwise, we need the new party to discard it. For the fast blocks that generated after his joining, we can decide whether these fast blocks belong to pendingSet or candidateSet by Algorithm 1. When he can generate a new fast block, he generates it through Algorithm 3 too. It is obviously that the new party can order DAG as the same as the online parties, so we just describe the process of downloading and dealing with the fast blocks that generated before his joining in Algorithm 4.

**Algorithm 4** Download the missed fast blocks

**Require:** states recorded in slow chain.

**Ensure:** DAG $\mathbb{G}$, candidateSet and confirmedSet.
1: Download a DAG $\mathbb{G}$ and check it by the states recorded in slow chain;
2: Set candidateSet={} and confirmedSet={};
3: Set the largest slot in $\mathbb{G}$ as $t_L$;
4: **for** each valid $B_{f}^{'}$ in $\mathbb{G}$ **do** // $\mathbb{G}$ may be updated.
5: 	**if** $T-Slot[B_{f}^{'}] < T+\Delta$ **then**
6: 		candidateSet=candidateSet+$\{B_{f}^{'}\}$;
7: 	**else**
8: 		**if** $Density[B_{f}^{'} , Slot[B_{f}^{'}] + \Delta , Slot[B_{f}^{'}] + \Delta + T] \ge Th$ **then**
9: 			confirmedSet=confirmedSet+$\{B_{f}^{'}\}$;
10: 		**else**
11: 			Discard $Density[B_{f}^{'} , Slot[B_{f}^{'}] + \Delta , Slot[B_{f}^{'}] + \Delta + T]$ and $B_{f}^{'}$;
12: 			Update $\mathbb{G}$;
13: 		**end if**
14: 	**end if**
15: **end for**

## 5.1 Setting the threshold

In this section, we will analyze how to set the threshold Th which is based on to decide whether a fast block can be selected into confirmedSet. We need to ensure that if malicious players withhold a part of DAG all the time, they can only exceed the threshold with a small probability. Meanwhile, we also need to guarantee that the number of nodes in the DAG graph generated only by honest players over the same period cannot reach the threshold with a small probability. For an always online party, he can recognize the DAG part that had been withhold all the time, but for a new party, it is possible to accept a hiding part. Thus, the threshold Th is the key to prevent a new party from being cheated. If a new party sees two or more parts, we needs to recognize all the leaf nodes of the parts in which the number of nodes reaches the threshold, and reject the parts that do not conform to requirements as described in Algorithm 4.
