### 5.2 Security under unbiased randomness

In this section, we will prove that Plume can meet the security definitions in section 3 while the randomness used to select committee is unbiased. Then, in the next section, we will explain that the biased randomness generated from slow blockchain cannot affect the overall security.

**CLAIM 5.1.** *Plume meets the 5 security definitions, that are unique sequence number, stable finality state, sequence growth, sequence quality and sequence common prefix, when the randomness used to select committee is unbiased.*

**PROOF.** We will prove Plume meets the 5 security definitions respectively.

*Unique sequence number.* In Plume, the sequence number of a fast block is set based on the slot in which the fast block was generated. And we require that there is a fast block can be generated in a slot averagely, but it is possible that there are more than one fast blocks are generated in a slot. We deal with this situation by comparing their hash values where we use the collision-resistant hash algorithm. It is obvious that if an adversary can break the unique sequence number property, he can break the collision-resistance of the hash algorithm.

**Figure 3**: when \( \alpha = 0.9 \), \( T = 5, 10, 15 \), the probability density maps of \( \mathcal{X} \) and \( \mathcal{Y} \)

*Stable finality state.* If an adversary wants to make the sequence number of a fast block \( B_f \) in Seq[\( \mathfrak{S} \)\] changed, he must generate a fast block \( B_f' \) with enough child blocks and less slot than \( B_f \)'s so that \( B_f' \) satisfies the criteria for being added to confirmedSet. Once \( B_f' \) is in an honest party's confirmedSet, it will be added into Seq[\( \mathfrak{S} \)\] and given a sequence number. Because of Slot[\( B_f' \)] < Slot[\( B_f \)], there must be Index[\( B_f' \)] < Index[\( B_f \)] which means the sequence number of \( B_f \) is changed. But fortunately, as long as \( T \) is large enough, the success probability of the adversary is negligible which is shown in Table 2. To be specific, when \( T = 100 \) slots and \( \alpha = 0.9 \), the success probability only is \( 5.44851 \cdot 10^{-11} \).

Fig. 4 shows the variation trend of adversaries' success probability where \( T \) is from 10 to 100 at intervals of 10. We can see that as time goes on, the probability of malicious adversaries alone exceeding the threshold gets smaller and smaller. When \( \alpha = 0.9 \) the success probability is too small to be presented in the top figure in Fig. 4, so we present it in the bottom figure alone. And we present the specific data in Table. 2.

*Sequence growth.* Algorithm 3 can guarantee that a fast block can be referenced directly or indirectly by all the fast blocks later, and the probability that a DAG part generated only by honest players in $T$ slots cannot reach the threshold $\mathsf{Th}$ is negligible, so a fast block $B_f$ generated by an honest player must be able to be added into $\mathsf{Seq}[\mathbb{G}]$ after $\Delta + T$ slots. Thus, $\mathsf{Seq}[\mathbb{G}]$ keeps growing.

*Sequence quality.* The fast blocks in $\mathsf{Seq}[\mathbb{G}]$ are generated by committee that are selected randomly. When the randomness is unbiased and the ratio of honest players is $\alpha$, it is obvious that for large enough $T$ consecutive fast blocks of $\mathsf{Seq}[\mathbb{G}]$, the number of honest fast blocks is $\alpha \cdot T$ averagely.

*Sequence common prefix.* In Plume, a fast block that is received by an honest party, then the honest party would send the fast block to all other honest parties. Thus, except for the most recent fast blocks, the union set of pendingSet and candidateSet in every honest party's view is the same, and then the confirmedSet selected from the union set of pendingSet and candidateSet is the same.

Therefore, for any honest player $P_1$ with local $\mathbf{S}_1 = \mathsf{Seq}[\mathbb{G}_1]$ at slot $s_1$ and $P_2$ with local $\mathbf{S}_2 = \mathsf{Seq}[\mathbb{G}_2]$ at slot $s_2$, where $s_1 < s_2$, it holds that $\mathbf{S}_1^{[k]} \preceq \mathbf{S}_2$. \quad $\Box$

### 5.3 Security under biased randomness

In this section, we will prove that although our randomness is biased, it will not break the security of Plume. When the randomness is unbiased, the success probability of an adversary is shown in Table 2, but in Plume, an adversary can select a randomness that is better for him, so firstly, we analyze the success probability of adversary who can bias the randomness.

In Plume, we regard the hash value of a slow block that has been confirmed as the randomness. Malicious adversaries can select an optimal slow block to broadcast. The optimal slow block is that the randomness generated from it can make the number of elected malicious adversary is maximal. So we can compute the expectation of the maximal number of elected malicious adversary when they can select a randomness from $k$ randomneses. It means that adversaries can generate $k$ slow blocks at the same time, and we define the event as $A_k$. It is easy to get the happening probability of $A_k$ is $\gamma^k$ where $\gamma$ is the proportion of malicious adversaries' computing power.

We denoted the number of adversaries elected in $k$ times as $Y_1$, $Y_2, \cdots, Y_k$ respectively. And we denoted the variable $\mathbf{Z} = \textbf{Max}\{Y_1$, $Y_2, \cdots, Y_k\}$. We also consider $T$ slots, so $Y_1$, $Y_2, \cdots, Y_k$ all obey the normal distribution $N(\alpha T, (1-\alpha)T)$ (s.t., $\mu = (1-\alpha)\cdot T$, $\sigma = \sqrt{(1-\alpha)\cdot T}$). And we set $Y_i = \mu + \sigma \cdot Y_i'$, where $Y_i'$ obeys standard normal distribution. Then we can get $\mathbf{Z} = \textbf{Max}\{Y_1, Y_2, \cdots, Y_k\} = \mu + \sigma \cdot \textbf{Max}\{Y_1', Y_2', \cdots, Y_k'\}$. For the sake of explanation, we denoted $\textbf{Max}\{Y_1', Y_2', \cdots, Y_k'\}$ as $Z'$. And we can get the expectation of $Z'$ by the equation (1), where $\Phi(y)$ is the distribution function of standard normal distribution, and get the expectation of $\mathbf{Z}$ by the equation (2).

$$\mathbb{E}[Z'] = \int_{-\infty}^{\infty} y \cdot \frac{d(\Phi(y)^k)}{dy} dy \tag{1}$$
$$\mathbb{E}[\mathbf{Z}] = \mu + \sigma \cdot \mathbb{E}[Z'] = (1-\alpha) \cdot T + \sqrt{(1-\alpha) \cdot T} \cdot \mathbb{E}[Z']. \tag{2}$$

We can see the growing trend of $\mathbb{E}[Z']$ as $k$ increases from 1 to 10 from Fig. 5. so the larger $k$ is, the higher the probability that adversaries can success will be. Next, we just consider the situation when $k = 10$, $\mathbb{E}[Z'] = 1.53873$. We set $T$ changes from 10 to 100 at an interval of 10, to compare the success probability under biased randomness with that in Table. 3 shows that when $\alpha = 0.9$ and $\alpha = 0.8$, the expectation of the maximal number of elected adversaries is smaller than our threshold all the time. It is to say that even though adversaries can prepare 10 slow blocks to select a randomness, they cannot double spend a confirmed transaction. Moreover, the probability of getting 10 slow blocks at the same time is only $\gamma^{10}$, where $\gamma < 0.5$. Table. 4 shows that when $\alpha = 0.7$ and $T = 10, 20$, the expectation of the maximal number of elected adversaries exceeds our threshold, but when $T \ge 30$, adversaries cannot success. So when $\alpha = 0.7$, we need to set $T \ge 30$ to prevent adversaries from breaking the security.

From the above, we can see that adversaries can increase the success probability by selecting randomness, but the success probability is negligible even if they have 10 chances to pick a preferable randomness.
