# 2  RELATED WORK

Thunderella [14] is proposed by Pass and Eilam in 2018 to speed up the confirmation of public chain. It needs a trusted accelerator to collect transactions and output them in order, then comminute votes for these sequential transactions and pack them to generate a consistent log. [14] can only guarantee the fast confirmation in the optimistic case, but fall back to the traditional blockchain in the worst-case, and it depends on a designated entity called accelerator. In relation to Thunderella, Plume proves a stable and fast confirmation without losing the decentralization.

In the past few years, several DAG-based consensus protocols have been proposed. SPECTRE[16], specifies a non-transitive partial orders for all pairs of blocks in the DAG, while Plume provides a global consistent unique number for all the blocks which is critical to support applications like smart contract. And as a PoW consensus protocol, ConfLux [9] uses PoW protocol to generate blocks which wastes a great of electricity. Because of the usage of GHOST[17] to decides which branch as the valid one when encountering forks, ConfLux also suffers a balance attack. Balance attack [10] means that adversary which hold less than 50% computing power can make some blocks never be confirmed by spotrupting the weaker one between two parts from the fork point. While in Plume, generation of fast block of DAG is according to the randomness provided by the underground single chain, which is economic. And the order protocol given by Plume resists the balance attack.

# 3  DEFINITIONS AND MODEL

In Plume, we have two kinds of blocks, one is the slow blocks in traditional single-chain blockchain, and the other is the fast blocks that can be used to construct DAG structure. Next, we will give formal descriptions of the two blocks. In subsequent contents, we call the traditional single-chain blockchain as slow chain, and the DAG-structure blockchain as fast chain.

# 3.1  Notations and security definitions of slow blockchain

Slow blockchain notations. We use slowChain to denote a slow chain. The notation slowChain$^{(\ell}$ denotes the entire slowChain except the trailing $\ell$ blocks; slowChain$[ \ell : t ]$ denotes the entire slowChain upto the block at time $t$; and slowChain$[\ell : c_2]$ denotes all blocks at length between $\ell_1$ and $\ell_2$. And we use the notation slowChain$_i^t$ to denote player $i$'s slowChain in round $t$. And symbol $\le$ denotes the prefix relationship.

Security definitions. A slow chain protocol should satisfy chain growth, chain quality, and common prefix [13,15]. Intuitively, chain growth requires that honest nodes' blocks[5] grow steadily, neither too fast nor too slow, which is the reason why we call the traditional single-chain blockchain slow chain, and honest parties have chains of roughly the same length. Chain quality requires that in any honest node's chain, any sufficiently long window of consecutive blocks contains a certain fraction of blocks that are mined by honest nodes. Common prefix requests that all honest nodes' chains agree with each other except for the trailing few blocks. We will formally define these security properties below.

# 3.2  Execution Model

Semi-synchronous Communication Setting. We divide time into non-overlapping segments called slots. Messages sent from one honest node would be received by all the other honest nodes within $\Delta$ slots. And when a new node joins in this network, he can receive all the messages he missed. We defined that a epoch, in which a slow traditional block is generated on average, is composed of $R$ slots. At the beginning of each epoch, Plume selects a committee to generate DAG structure, and as the epoch changes, the committee would change.

Ability of Adversary. Adversaries in our analysis cannot prevent the transmission of messages, but they can delay the transmission of a message to an honest party by up to $\Delta$ slots and reorder the messages sent to others. Adversaries can also transmit their own messages to a part of honest parties, but after a period all the honest parties can receive these messages. Meanwhile, adversaries can corrupt honest nodes immediately at any time. Also adversaries can constantly adjust the strategy of mining fast or slow blocks and broadcasting them.

# 3.3  Notations and security definitions of fast blockchain

DEFINITION 3.1. DAG structure

A DAG of fast blocks is denoted $\mathcal{G} = (V,E)$, where $V$ represents fast blocks and $E$ represents the hash references to previous fast blocks. If a $B_F$ is in our DAG, we denote it as $B_F \in \mathcal{G}$. We define Child[$B_F^i$] as the subset of fast blocks from which $B_F$ is reachable, and Ancestor[$B_F$] as the subset of blocks reachable from $B_F$. Parents[$B_F$]$] represents the blocks that are referenced by $B_F$ directly. Slot[$B_F$] means the slot in which $B_F$ was generated. Density[$B_F$, $s_1, s_2$] represents the number of Child[$B_F$] between slot $s_1$ and $s_2$. And Index[$B_F$] is the sequence number of $B_F$ after ordering. It is worth mentioning that Index[$B_F$] # Slot[$B_F^i$], but for Slot[$B_F^{i_1}$] < Slot[$B_F^{i_2}$], there must be Index[$B_F^{i_1}$] < Index[$B_F^{i_2}$], and for each fast block $B_F$, its sequence number [Index[$B_F$]] is unique.
