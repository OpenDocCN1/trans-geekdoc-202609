
```
[[f[α]]]_G^u = { f : λ(u, f[a]) if (u, f[a]) ∈ dom(λ), f : null else. }
```

```
[[f[α]{φ}]]_G^u = { f : {[[φ]]_G^{v1} ... [[φ]]_G^{vk}} if type_S(f) ∈ L_T and {v1 ... vk} = {vi | (u, f[a], vi) ∈ E}, f : {[[φ]]_G^{v}} if type_S(f) ∉ L_T and (u, f[a], v) ∈ E, f : null if type_S(f) ∉ L_T and there is no v ∈ N s.t. (u, f[a], v) ∈ E. (1)
```

```
[[on t{φ}]]_G^u = { [[φ]]_G^u if t ∈ O_T and τ(u) = t, ε else (ε denotes the empty word). }
```

```
[[φ1 ... φk]]_G^u = [[φ1]]_G^u ... [[φk]]_G^u.
```

在本文中，我们假设 A ⊂ F。更具体地说，我们将字段 f ∈ F 的参数集合限制为其类型的标量字段集合，即 args_S(f) ⊆ {f' | f' ∈ fields_S(type_S(f)), type_S(f') ∈ Scalars}。因此，叶子字段不分配任何参数，且表达式 f[α] 和 ℓ : f[α] 可分别写成 f 和 ℓ : f，分别 [22]。在 [22] 中，集合 F 和 A 被假设为不相交；然而，我们的假设符合 GraphQL 规范，并且不影响所提供的语义。

### 2.2. 最坏情况最优多路连接算法

最坏情况最优多路算法 [26] 近期受到了大量关注（例如 [3,27,28,29]），并在评估图模式查询 [27,29,30] 中展现出高性能。此类算法满足 AGM 界 [31]，其运行时间与输入查询结果的最坏情况大小相匹配 [23,27]。成对连接算法每次对两个连接操作数执行连接操作。相反，最坏情况最优多路算法（例如 Leapfrog Triejoin [32]）是递归的，并按变量逐个评估输入查询。这种评估方法不存储任何中间结果，并允许解映射直接写入结果。

## 3. 在 RDF 图上评估 GraphQL 查询

在本节中，我们介绍为 RDF 图上 GraphQL 查询的原生执行而开发的多路左连接算法。受 [3,27] 中提出的基本图模式查询评估最新结果的启发，所提出的左连接算法借鉴了最坏情况最优多路连接算法，并按变量逐个评估查询。然而，与连接操作不同，左连接操作的重新排序是不允许的。因此，我们必须注意查询变量的评估顺序。此外，左连接操作可能会产生部分解（即在 GraphQL 上下文中包含空值的解）。为了在查询评估期间尊重操作的顺序并确保部分解不会被丢弃，我们额外引入了操作数依赖图。在介绍操作数依赖图和所提出的多路左连接算法之前，我们首先定义 GraphQL 查询的操作数生成过程。

### 3.1. GraphQL 查询操作数

在 SPARQL 的情况下，语言中有多个特性会生成查询操作数，其中最常见的是三元组模式。在 GraphQL 的情况下，需要为查询的每个字段、参数和内联片段生成一个操作数。在这里，为简单起见，我们使用类似于 SPARQL 三元组模式的记法，并介绍如何生成 GraphQL 查询的操作数。请注意，我们实际上并没有将 GraphQL 查询翻译为 SPARQL 查询。潜在的实现可以自由使用任何可用手段（例如索引）来生成这些操作数。为了生成 GraphQL 查询操作数，我们还必须将提供的 GraphQL 模式的类型和字段映射到 RDF 项。我们的实现使用 GraphQL 指令 [25, 第 3.13 节] 计算此映射。在下文中，为简洁起见，我们省略了此映射。

在 GraphQL 查询中，我们区分三种类型的字段：i) 根字段，ii) 内部字段，以及 iii) 叶子字段。查询的根字段是遍历的起点。其对应的操作数应仅包含底层 RDF 图中属于其类型的实例的实体。模式 (?var, rdf:type, type_S(f)) 用于提取这些实例，其中 ?var 是一个将被赋予提取实例的变量。内部字段和叶子字段表示图中源顶点与目标顶点之间的边，其操作数使用形式为 (?var1, f, ?var2) 的模式创建。最终，?var1 将被赋予边的源顶点，而 ?var2 将被赋予目标顶点。对于内部字段和叶子字段，我们还需要考虑目标顶点的类型。更具体地说，在 RDF 中，属性的对象类型可能各不相同，而在 GraphQL 中，字段的目标顶点具有特定类型。为了限制目标顶点的类型，使用上述根字段的模式生成一个额外的操作数。在实践中，如果模式允许（例如通过指令），可以省略此额外操作数。给定表达式 f[α]{φ}，参数-值对 a = (f', v) ∈ α 的操作数由 (?var, f', v) 创建。最后，内联片段 t{φ} 的操作数，其子表达式 φ 仅在父字段是类型 t 的实例时执行，由 (?var, rdf:type, t) 创建。别名字段 ℓ : f[α]{φ} 和 ℓ : f[α] 的操作数分别使用 f[α]{φ} 和 f[α] 的模式生成。

如果两个查询操作数共享一个变量，则它们参与 (左) 连接操作。为了为操作数分配变量，我们利用了 GraphQL 的层次结构。更具体地说，一个字段的目标顶点与其嵌套字段的源顶点共享同一个变量。内联片段的操作数也分配给其父字段的目标顶点的变量。对于参数，其操作数分配给已分配给其字段操作数的变量。示例 3.1 展示了 GraphQL 查询的操作数生成过程。

**示例 3.1** 考虑示例 2.2 中的查询。φ₁ 的操作数由以下模式生成：1) ⟨?x, rdf:type, Person⟩，2) ⟨?x, lname, "Doe"⟩，3) ⟨?x, fname, ?y⟩，以及 4) ⟨?x, email, ?z⟩。请注意，根字段及其参数的操作数共享同一个变量。因此，表示姓氏不是 "Doe" 的人的顶点将被丢弃。内部字段通过变量 ?x 与根字段关联。还请注意，内部字段的目标顶点被分配了不同的变量。φ₁ 和 φ₂ 的操作数以类似方式创建，其对应模式为：1) ⟨?x, rdf:type, Company⟩，2) ⟨?x, name, ?y⟩，3) ⟨?x, employees, ?z⟩，4) ⟨?z, rdf:type, Person⟩，5) ⟨?z, lname, ?w⟩，以及 6) ⟨?z, id, ?v⟩。内部字段 name 和 employees 通过变量 ?x 与根字段 companies 关联，而叶子字段 id 和 lname 的操作数则通过 ?z 与其父字段操作数 employees 关联。最后，请注意为字段 employees 生成的额外操作数。其目标是丢弃不是 Person 类型的顶点。我们假设标量类型不需要类型过滤，为简洁起见。

### 3.2. 操作数依赖图

操作数依赖图借鉴了模式树 [33]，并捕获查询操作数之间的依赖关系。如果在查询评估期间某个操作数未能成功解析，则其依赖的操作数不应被评估。例如，给定 GraphQL 查询 f [α]{φ}，如果 f [α] 的操作数未产生任何结果，则不应考虑 φ 的操作数。然而，如果 φ 的操作数未产生任何结果，则 f [α] 生成的结果不应被丢弃。操作数依赖图正式定义如下。

**定义 3.1（操作数依赖图）** _设 O 为查询操作数的列表，Σ 为字母表。此外，设 Iₙ = {i ∈ ℕ | 1 ≤ i ≤ n}。操作数依赖图是一个有向顶点-边标记图 G = (V, E)，其中 V = I_{|O|} 且 E ⊆ V × Σ × V。操作数 v ∈ V 依赖于操作数 u ∈ V，当且仅当 ∃e ∈ E 使得 e = (u, σ, v) 且 σ ∈ Σ。_

根据定义 3.1，操作数依赖图的顶点对应于其各自查询的操作数。出现在查询操作数中的变量被分配来自 Σ 的唯一标签，并用于标记依赖图的顶点和边。依赖图的顶点被分配其各自操作数变量的标签。只有当两个操作数共享一个变量时，它们才通过边连接。边的标签由其关联顶点共享的标签决定。

为了构建操作数依赖图，我们利用了 GraphQL 查询的层次结构。给定表达式 f [α]{φ}（ℓ : f [α]{φ}），f [α] 的操作数在依赖图中构成一个强连通分量，因为它们彼此依赖。这意味着，只要 f [α] 生成多个操作数，f [α] 的任意顶点 v 都可以从 f [α] 的任意其他顶点 u 到达，其中 v ≠ u。由于 φ 的操作数依赖于 f [α] 的操作数，因此 f [α] 的顶点无法从 φ 的顶点到达。对于 on t{φ} 表达式，φ 的操作数依赖于 t 的操作数。这意味着 t 的顶点与 φ 的顶点通过边连接，其源为对应于 t 的顶点。对于 φ₁…φₖ 表达式，任意 φᵢ 与 φⱼ（其中 1 ≤ i, j ≤ k 且 i ≠ j）的顶点之间没有边，因为 φᵢ 的评估不影响 φⱼ 的评估（定义 2.4）。相互依赖的操作数参与连接操作，而单向边表示左连接操作。最后，在下面介绍的多路左连接算法中，我们使用了连接操作数依赖图的强连通分量的有向无环图的根节点。在此，我们将该节点称为依赖图的独立强连通分量。
