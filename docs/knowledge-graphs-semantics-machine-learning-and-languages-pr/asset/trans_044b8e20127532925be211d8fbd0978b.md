

```
Algorithm 1 Multi-way Left-join Algorithm

1: **function** MWLJ(Q)                                      ▷ Q: Input GraphQL query
2:     O ← generate the operands of Q
3:     G ← create the operand dependency graph of Q using O
4:     X ← initialize solution mapping with domain equal to the set of labels appearing in G
5:     MWLJ_REC(G, X)
6: **function** MWLJ_REC(G, X)                                ▷ G: operand dependency graph, X: solution mapping
7:     **if** G is disconnected **then**                     ▷ Evaluation of φ₁ ... φₖ expressions
8:         **for all** connected components Gᵢ of G **do**    ▷ Each Gᵢ corresponds to a φᵢ, 1 ≤ i ≤ k
9:             MWLJ_REC(Gᵢ, X)
10:    **else if** G is not strongly connected **then**        ▷ Left-join operation
11:        U ← the set of labels appearing in the independent strong component of G
12:        x ← select a label from U
13:        **for all** values χ of x **do**
14:            resolve x in all operands using χ                 ▷ Carries out join and left joins simultaneously
15:            G′ ← prune vertices of empty operands and their transitively dependent vertices from G
16:            **if** G′ is empty **then**
17:                **continue**                                 ▷ All operands are pruned (unsuccessful join); continue with the next χ
18:            update the value of x in X with χ                 ▷ Join operations were successful
19:            remove x from G′; remove vertices without any labels from G′
20:            MWLJ_REC(G′, X)
21:    **else**                                                  ▷ G is strongly connected (no left-join operations)
22:        MWJ(G, X)                                             ▷ Carry out multi-way join (no more left joins after this point)
```

从U中选择标签x后，算法遍历x的所有可能值，并对x执行所有连接和左连接操作（第14行）。算法通过移除任何未成功解析的操作数及其传递依赖操作数（可通过遍历依赖图找到）来继续（第15行）。如果得到的图G′最终为空，则连接操作未成功，算法继续处理x的下一个值（第16–17行）。如果G′不为空，则用x的当前值更新解决方案映射X，该值连同任何已完全解析的操作数一起从G′中移除，然后算法进入下一个递归步骤（第18–20行）。如果提供的图G是强连通的，则算法进入多路连接算法，因为不再有需要执行的左连接操作。一旦剩余连接操作由多路连接算法执行完毕，活动解决方案映射X最终将被投影。

### 示例3.3

考虑示例2.2中的查询φ₁。

```
<p1> rdf:type <Person>; <lname> "Doe"; <fname> "Jon"; <email> "e1".
<p2> rdf:type <Person>; <lname> "Doe"; <fname> "Jan".
```

所提出的算法将产生三个解决方案：{x:p1, y:"Jon"}、{x:p1, z:"e1"}和{x:p2, y:"Jan"}。该算法首先选择与变量x对应的标签，该标签被赋值为图中人物的标识符。对于x的值p1，算法生成两个解决方案。第一个提供p1的名字（fname），赋给y；第二个提供其电子邮件，赋给z。对于值p2，由于示例图中p2没有电子邮件，算法仅生成一个解决方案。注意，在选择x并将其从操作数依赖图中移除后，所得依赖图是断开的。未出现在解决方案映射中的变量在该特定映射中是不绑定的。

关于GraphQL查询的枚举，在[22]中，作者研究了非冗余且处于基础类型正规形式的GraphQL查询的枚举问题。回顾一下，此类查询可以在与其响应大小成线性关系的时间内计算（第2.1节）。我们算法生成的每个解决方案映射对应所提供查询的响应的唯一路径。由于我们的左连接算法完全计算一个解决方案映射，因此一旦计算出某个特定解决方案映射，我们就能直接构造与之对应的路径。此外，由于我们算法的递归性质，GraphQL响应中特定节点的子树的解决方案映射共享公共值（示例3.3）。因此，我们能够避免多次访问响应的节点。

## 3.4. 实现

我们已在基于张量的三元组存储Tentris [3]中实现了所提出的算法。Tentris在基本图模式的评估中实现了最先进的性能，这些基本图模式通过一种最坏情况下最优的多路连接算法 [3,34] 进行评估。我们的实现，即TentrisGQL，使用Tentris的多路连接算法（算法1，第22行）和张量切片操作来生成GraphQL查询的操作数。

为了弥合GraphQL模式与RDF图之间的差距，我们遵循Neo4j的示例⁴并在实现中定义了几个指令。根据GraphQL规范，“指令可用于描述类型、字段、片段和操作的附加信息” [25, 第3.13节]。我们在第3.1节中提到，GraphQL类型和字段需要映射到RDF项。为此，我们在实现中定义了指令@uri。例如，类型定义 type Person @uri(value: "http://www.exmpl.org/Person") 将类型Person映射到RDF项http://www.exmpl.org/Person。由于RDF图中并非总是存在属性的逆，我们还定义了字段指令@inverse，它表示应使用字段属性的逆方向。最后，我们引入了字段指令@filter，它表示应使用该字段的类型来过滤特定字段的结果。此指令应用于映射到其范围包含多个RDF类的属性的字段（第3.1节）。

### 4.3. 基准配置与执行

我们的GraphQL服务在两个不同的基准配置上进行了评估。第一个配置的目的是评估我们服务在每个查询模板上的性能。对于每个模板，我们创建了一个压力测试，包含每个模板十个查询实例（110个查询）。我们还为每个非参数化查询创建了一个压力测试（共112个查询）。压力测试连续执行5次，并且彼此独立，从而确保查询实例被执行相同的次数。在第二个配置中，我们测量了系统在多个客户端查询时的性能。该配置由一个压力测试组成，其中包含来自每个模板的一个查询实例和两个非参数化查询（即13个查询）。在第二个配置的执行期间，始终有多个客户端发出查询是很重要的。因此，我们将客户端配置为并发发出查询一小时[3,36]。在两种配置中，每个压力测试的执行之前都有一个预热运行，其中相应压力测试的查询被执行一次。这使Neo4j能够将其数据结构加载并缓存到主内存中。
