
## 3. 算法改进与查询数据集

基于第2节的见解，本节旨在回答研究问题RQ1至RQ3。由于RQ4与评估相关，其讨论将在第5节进行。

### 3.1. 实体间的精确语义距离

如第2节所述，[2]将两个实体之间的语义距离估计为实体标签向量表示之间的余弦距离。然而，仅凭实体标签的歧义性就会损害向量表示的准确性，进而影响由此得到的语义距离。例如，Wikidata中有许多实体共享标签“Paris”，其中部分实体来自完全不同的类别：实体Q90指法国巴黎市，而实体Q167646指特洛伊国王普里阿摩斯的神话之子¹³。在路径查找过程中，必须准确锁定当前检查的实体，否则，当具有所谓低语义距离的实体被优先选择时，可能会得到概念漂移的路径。因此，RQ1询问如何更准确地估计实体之间的语义距离。

我们提出以下两项修改来缓解该问题。第一项修改是：除了实体标签之外，还将实体描述（Wikidata中大多数实体均可获得的另一资源）输入词嵌入模型。为此，只需将实体标签和实体描述拼接起来。其思想是，描述提供的额外信息能够使向量表示更准确地捕获实体含义。其次，将fastText替换为SBERT结合all-mpnet-base-v2，以高效计算新输入类型（即由实体标签和描述组成的字符串）的高质量向量表示。另外需要注意的是，Wikidata中的数据是经过整理的，因此不太可能出现拼写错误，也就不需要fastText对拼写错误的鲁棒性。

### 3.2. 用于Wikidata路径查找的双实体查询数据集

尽管[2]中讨论的十二个双实体查询足以展示该算法的潜力，但其数量少且为手工精心挑选，既无法进行适当的评估，也无法进行超参数优化。因此，RQ2提出了这样的问题：什么是适合在Wikidata中进行路径查找的双实体查询数据集？考虑到将该算法应用于网页搜索引擎知识面板生成的长期目标，这样的查询数据集必须是真实的，即查询必须来源于真实用户向网络搜索引擎提交的查询。然而，目前尚无这样的查询数据集（或基准）被提出。

在信息检索研究中，TREC[21]数据集尤其流行，已被用于评估各种信息检索系统。这些数据集旨在让研究人员通过一组通用的测试集来评估其信息检索系统的性能。多年来，TREC生成了许多不同的数据集，涵盖多个领域和文本类型。乍一看，TREC 2009、2010和2011的实体赛道（Entity Track）¹⁴中的数据集似乎有助于推导用于Wikidata路径查找的双实体查询数据集，因为它们包含用于评估面向实体搜索系统的实体集合。然而，从这些数据集推导双实体查询数据集需要将集合中的各个实体进行人为的两两组合，这显然违背了真实性的要求。此外，TREC数据集仅提供ClueWeb09¹⁵ IRI作为实体的标识符，而这些IRI必须先与Wikidata实体进行代价高昂的链接。

因此，我们采用了另一种方法。TREC 2007的Million Query Track¹⁶数据集包含10,000个面向网络搜索引擎的真实文本查询。以此作为起点，对TREC数据集中的每个查询应用以下流程，以推导用于Wikidata路径查找的双实体查询数据集：

1. 使用最先进的Wikidata实体链接器GENRE¹⁷ [22]在查询中查找Wikidata实体。如果识别出两个或更多实体，则进入下一步；否则丢弃该查询。

2. 由于GENRE仅提供实体标签，而不提供必要的实体ID，因此使用SPARQL查询Wikidata以获取实体ID。为尽量减少错误匹配¹⁸，仅保留标签完全匹配的实体。如果识别出两个或更多实体，则进入下一步；否则丢弃该查询。

3. 最后，组成 $\frac{n(n-1)}{2}$ 个实体对，其中 $n$ 是识别并成功匹配的实体数量。每个实体对的两个ID代表一个双实体查询，并最终存储。

例如，考虑TREC数据集中编号为4480的查询 *children books on the effect of music on plants*。在第一步中，GENRE识别出该查询中的三个实体，即标签为 *book*、*music* 和 *plant* 的实体。第二步中查询Wikidata将实体识别为Q571、Q638和Q756，这些是合理的匹配¹⁹。在最后一步中，组成 $\frac{3(3-1)}{2}=3$ 个双实体查询，即 ⟨Q571, Q638⟩、⟨Q571, Q756⟩ 和 ⟨Q638, Q756⟩。请注意，这些查询正确反映了原TREC查询中实体出现的顺序。总共有1,196个双实体查询通过此流程获得²⁰。

### 3.3. 超参数 α、β 和 γ 的优化

双实体查询数据集不仅能够对路径查找算法进行适当评估，还能对其超参数进行优化。基于第2节中解释的原因，利用Simple优化器为路径查找算法寻找优化的超参数配置，这代表了RQ3的答案。为此，优化器需要一个目标函数，该函数接受超参数配置并返回某个目标值来评估该配置的性能。根据用例不同，优化器的任务是通过测试不同配置来最小化或最大化目标值。

在网页搜索引擎的背景下，目标是在Wikidata中快速找到实体之间的路径，即访问少量实体即可快速显示结果。因此，选择访问的实体数量作为要最小化的目标值。为了满足网页搜索引擎的低延迟要求，实体限制设置为100。此外，路径查找算法必须能够可靠地找到未见过的双实体查询的路径，因为用户可能输入任意查询。为了评估这种能力，优化仅使用20%（即239个）双实体查询，其余80%（即957个）查询作为第5节评估的测试集。由于TREC 2007 Million Query Track数据集中的查询是任意排序的，因此选取前239个双实体查询用于优化。
