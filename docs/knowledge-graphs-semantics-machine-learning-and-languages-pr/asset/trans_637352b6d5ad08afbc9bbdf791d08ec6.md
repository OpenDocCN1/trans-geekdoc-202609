

## 算法2 用于优化超参数 α、β、γ 的算法

要求：包含 239 个双实体查询的样本列表、路径查找过程 FIND PATH、Simple 优化器的 minimize 函数

```
procedure TESTCONF(α, β, γ)
  score ← 0 // lower is better
  entityLimit ← 100
  for ⟨e, e′⟩ ∈ samples do
    path, numberOfVisitedEntities ← FIND PATH(e, e′, α, β, γ, entityLimit)
    if path == ⊥ then
      score ← score + numberOfVisitedEntities × 2
    else
      score ← score + numberOfVisitedEntities
    end if
  end for
  objectiveValue ← score / |samples|
  return objectiveValue
end procedure
```

```
procedure PERFORMOPTIMIZATION
  interval ← [0.0;1.0]
  iterations ← 150
  minValue, α, β, γ ← minimize(TESTCONF, interval, iterations)
  return minValue, α, β, γ
end procedure
```

在关于贝叶斯优化的文献中，关于迭代次数的建议会根据超参数数量和所采用的采集函数等因素而有所不同（参见[23]）。[20] 报告称，Simple 在约 25 次迭代时即可逼近具有两个超参数的目标函数的全局最优值。因此，针对我们包含三个超参数的问题，采用了充足的 150 次迭代。由于超参数 α、β、γ 表示代价函数各组成部分的权重，因此指定它们每个都可以在区间 [0.0;1.0] 内取值即可。基于这些设置，算法2展示了用于优化超参数 α、β、γ 的 PERFORMOPTIMIZATION 过程。为此，该过程调用 Simple 优化器的 minimize 函数来最小化 TESTCONF 过程返回的 objectiveValue。因此，TESTCONF 代表目标函数，它接受一个候选超参数配置，并返回使用该配置时，对样本中所有查询进行路径查找期间访问实体的平均数量，作为 objectiveValue。如果在达到实体限制之前未找到路径，则访问实体数量将加倍，作为对该特定查询的惩罚。

图2 显示了优化过程中每次迭代产生的 objectiveValue 以及 minValue，即迄今为止最小的 objectiveValue。如图所示，在第 17 次迭代时就已经找到了一个较好的 minValue，并且直到第 150 次迭代都没有观察到重大改进。因此，预计超过 150 次迭代后不会再有显著改进。最低的 minValue（即 59.347）是在第 101 次迭代时使用以下超参数配置得到的：

## 4. 实现：BiPaSS

另一个需要解决的点是实现的本身，尽管它与研究问题的回答没有直接关系。最初，实现路径查找算法的原型是用 Python²² 编写的。对于本文，我们进行了完整的重新实现⁷。为便于日后引用，我们称该实现为双向路径查找系统（Bidirectional Pathfinding System，BiPaSS）。新的实现使用 Rust²³ 作为路径查找算法本身，并利用了最先进的数据结构，包括基于斐波那契堆的优先队列。如图3所示，该实现包含四个组件。第一个是 *Query Factory*，它实现了第3节中从 TREC 数据集导出双实体查询数据集的过程。由此产生的双实体查询被提供给 *Pathfinder* 组件，该组件包含路径查找算法以及用于运行超参数优化和基准测试的代码。为了使用 SBERT 和 all-mpnet-base-v2 计算语义距离，它通过 HTTP 与 *Wembed API* 组件交互。为了从 Wikidata 检索实体数据，它与 *Wikidata API* 组件交互，该组件是向 Wikidata Query Service 发出 SPARQL 查询的包装器，同样通过 HTTP 进行。因此，*Pathfinder*、*Wikidata API* 和 *Wembed API* 构成了路径查找系统。为了便于使用和复现，所有组件都已 Docker 化²⁴。此外，相当多的 HTTP 交互都被缓存，这使得尽管 Wikidata Query Service 的查询限制（这是路径查找耗时的主要原因）较为严格，仍能快速复现结果。

平均而言。第二组，即仅语义和贪婪配置，产生的平均路径长度约为前者的两倍。请注意，前一组使用的 β 值大于 0，而后一组使用的 β 值恰好为 0。这表明 β 在控制路径长度方面起着关键作用。

总而言之，对 RQ4 的回答如下：无信息配置的覆盖率低于考虑语义距离的配置，从而支持了将语义距离作为搜索启发式一部分的效用。鉴于网络搜索引擎的背景，优化配置是最佳选择，因为它以较低的平均访问实体数量和适中的平均路径长度达到了测试集的最高覆盖率。其高覆盖率也支持了[2]中的假设，即限制算法仅考虑出边是没有问题的。乍一看，仅语义配置似乎也很有竞争力。然而，该配置所找到的路径的平均长度较高，这使人们对其对用户的实用性产生了怀疑。

为了研究实体关系的有用性，未来需要实施一项具有代表性的用户研究。该研究的目的是加深对实体关系在网络搜索引擎上下文中意义的理解，并评估代价函数和超参数配置在多大程度上符合用户对实体关系意义的感知。尽管如此，为了大致了解不同配置所找到的路径，表4给出了一些示例。总的来说，这些示例与定量结果一致。一个有趣的观察是，查询A的仅语义路径表现出概念漂移，尽管所使用的配置完全依赖于语义距离。此外，在给定实体限制的情况下，均衡和无信息配置无法找到查询B的路径。优化配置产生的路径长度适中，且保持了查询的语义焦点。

## 6. 结论

以研究[2]中未解决的问题为目标，本文的主要贡献包括：改进了路径查找算法代价函数中所利用的语义距离、引入了用于 Wikidata 路径查找的双实体查询数据集、优化了算法的三个超参数，以及针对所述超参数配置在所述数据集上对算法进行了评估。所提供的重新实现补齐了完整图景。

除了上述未来工作的方向外，一个重要的点是将路径查找算法集成到端到端应用中，用户可以输入双实体查询，随后触发路径查找器，从而生成解释查询实体之间关系的知识面板并最终显示出来。在这方面，需要研究哪种呈现方式能带来最佳用户体验。例如，可以基于找到的路径，使用自然语言生成技术来生成描述该关系的实际文本。同时，基于图形的可视化也是可以想象的。

除了采用[2]中引入的代价函数外，还可以研究也考虑谓词含义的替代代价函数。直觉上，表达分类学关系的谓词对于非专业用户而言可能比更专门化的谓词更容易理解。

最后，[2]中提出的一个观点也应在此重复，即如何处理提及两个以上实体的多实体查询。虽然显而易见的选项是简单地在所有实体对之间执行路径查找并拼接生成的路径，但例如，也可以设想一种尝试识别一个能够以最小全局概念漂移连接查询实体的实体的方法。
