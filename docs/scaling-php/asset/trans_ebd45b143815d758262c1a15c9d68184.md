## 案例研究：水平扩展用户上传

类似于Cookie处理，当你扩展应用服务器时，另一个常见问题是处理用户上传。关于用户上传，我有以下要求：

##### 1\. 上传文件需要立即可用

在大多数情况下，用户期望他们的上传文件立即可用。显示损坏的图片或不可用的文件通常是不可接受的（视频除外，因为涉及处理时间）。如果我们在系统中移动上传文件，它必须对用户完全透明且无缝。

##### 2\. 上传文件需在后台推送到长期存储

在应用服务器上存储上传数据超过几分钟是危险且不负责任的。我们设计应用服务器以水平扩展，以**在不丢失数据的情况下失败**，因此在应用服务器上进行长期存储违背了这些原则。硬盘会损坏，在应用服务器上配置RAID-10也不具成本效益。

有很多*轻松*的长期存储解决方案，可以根据你的具体需求选择。我们将宠物字节的数据存储在[Amazon S3](http://aws.amazon.com/s3/)，但其他选项包括[Rackspace Cloud Files](http://www.rackspace.com/cloud/public/files/)和[Edgecast Storage](http://www.edgecast.com/services/storage/)。

如果你的数据量到使IaaS解决方案过于昂贵（或者你不想或不能使用IaaS），还有“自己动手”的解决方案，如[MogileFS](https://github.com/mogilefs)和[GridFS](http://www.mongodb.org/display/DOCS/GridFS)值得探索。

记住，扩展的一个主要原则是** decouple your systems!**（解耦你的系统！）——应用服务器应负责运行你的应用，而不是存储数据。

**P.S. 千万不要把上传的文件存储在数据库中。** 使用正确的工具做正确的事。

##### 3\. 不存在单点故障或中心化（孩子们，说不！NFS！）

上传系统中不应该存在单点故障。故障会发生，需要优雅处理。上传应立即处理，而不是由集中化系统处理。我像躲避鼠疫一样避免NFS，因为它通常非常慢，并且创建一个灾难性的单点故障——当它不可用时，我们将失去处理**所有**上传的能力。如果上传是你业务的核心，你就知道这有多大的问题。Facebook有一篇（虽然略显过时）[文章](https://www.facebook.com/note.php?note_id=76191543919)介绍了他们如何从NFS迁移到他们自研的Haystack系统。这篇文章值得阅读，如果只是为了获得灵感。

#### 直接将文件上传到S3（或任何长期存储）是错误的做法

很多人通过在Web请求的上下文中直接将用户文件上传到Amazon S3来处理文件上传，也就是说，他们在文件最初上传的同一请求中将文件上传到长期存储。伪码如下：

```
1 <?php
2 if ($_FILES['upload']) {
3   upload_to_amazon_s3($_FILE['upload']);
4 }
```

虽然这种方式简单且适用于较小的服务，但有两个主要问题。

1. 如果Amazon S3宕机或运行缓慢，且没有重试机制，我们将丢失用户的上传文件。

2. 这显著增加了HTTP请求的时间，占用一个PHP-FPM进程更长时间。少一个PHP-FPM进程意味着应用服务器处理的并发连接减少，用户需要等待的时间不仅包括从他们的电脑上传到你的服务器，还包括从你的服务器上传到Amazon S3（尽管可以通过`fastcgi_finish_request()`或使用专用PHP-FPM池来缓解这个问题）。

#### 正确处理用户上传的方法
