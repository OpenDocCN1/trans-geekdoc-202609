One could argue that the SSI solution is slightly superior in that the AES secret is generated and held by the data provider, whereas in the OP solution, there is a reliance on a third party. In addition, in the SSI solution, the data provider only ever stores fully homomorphically encrypted data, providing another layer of protection from an untrusted decentralized storage provider.

Regarding limiting unauthorized secondary use of data, i.e., preventing the double-spending problem, both solutions remain quite limited in the defense they provide. Each can provide for a time-limited access token that provisions access to the data for a specified period. In the case of the SSI solution, the data manager manages FHE data in the cloud and is responsible for issuing a storage credential with the access token for the data. Only after verifying the license credential, which the consumer purchases through the distributor app, does the individual provide with the token used to access the data and the AES keys used to decrypt the data to gain access to the FHE data. The design also considers the fact that the data manager is likely to need providing computing environment for their restrict use; thus, the infringed mentioned should be above of an access token for the computing environment will provide access to a virtual environment which contains a computing resource (e.g., Amazon EC2) and the storage. However, at the present time, the solution does not provide this capability and the data is transferred into the custody of the consumer for processing. Nevertheless, it is emphasized that, in the SSI solution, the data are never decrypted into clear text; they remain fully homomorphically encrypted thus limiting the possibility of unauthorized secondary usage; however, this approach limits the type of computations that might be performed over the data.

In the case of the OP solution, the Brizo (Provider) provides access to the data by means of a service URL. Consumers request direct or compute access to the data using the service URL. The Brizo (Provider) receives the request and provides access to data, identified by the data's unique DID. In a compute-to-data scenario, the consumer's algorithm is given access to the provider's data store to run computations over unencrypted data, in contrast to the SSI solution that consumers access only to that data that remains fully homomorphically encrypted.

Unauthorized secondary use of data could be achieved in either solution through techniques such as data mining to statistically revealing identities, this also needs to be prevented to protect against a data double spend. Even if a single pseudonym identity is used many times, it may be possible to determine who the data provider is, and from there to discover transaction value information and patterns of transactions that enlace multiple data shares.

In the OP ecosystem, the data token is independent of identity and does not rely on the identity credentials, unless metadata embedded in the token reveals personally identifiable information. This is a path to finding out the owner of data unless a possibility, however, and OP therefore provides for encryption of certain types of metadata for compliance with privacy laws.
