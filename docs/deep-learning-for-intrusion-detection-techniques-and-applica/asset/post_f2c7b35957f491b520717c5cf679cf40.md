These systems depend on established repositories of attack information to classify incoming traffic as either normal or a recognized type of attack. Operating on pattern-matching techniques, they identify known attacks by comparing intrusion signatures with those stored in the database. When a match occurs, indicating a previously identified intrusion signature, an alarm signal is triggered. Examples of signatures include an attack attempt using the username "root," which poses a threat to network security, an email with the subject line "Free Programs" commonly associated with prevalent malware, or a system log indicating the disabling of host control in the operating system. The fundamental idea is to build a database of intrusion signatures and use it to assess ongoing actions by comparing them with existing signatures. If a match is found, an alert is generated. For instance, a regulation in the format of "if antecedent, then consequent" could result in labeling a scenario as an attack if the source IP address matches the destination IP address. Signature-based intrusion detection systems (SIDSS) are utilized in widely used tools like Snort and NetSTAT.

Traditional methods of detecting potential attacks in SIDSS typically involve examining network packets and comparing them to a database of predefined signatures. In cases where an attacker substitutes a malicious file named "prog.exe" with a different name, such as "prog2.exe," a signature searching for "prog.exe" would not detect the attack. However, these techniques have limitations in detecting attacks that occur across multiple packets. With the increasing sophistication of modern malware, IDSs may need to retrieve the previous packet contents to extract signature information. Various approaches, such as creating signatures as state machines, using formal language string patterns, or semantic conditions, have been employed to create signatures for SIDS. These systems are effective at detecting known attacks and boast high accuracy rates with minimal false positives. However, they are computationally intensive and require a significant amount of time to maintain. Unfortunately, the number of attack variants and zero-day attacks is increasing rapidly, making it challenging to keep these systems up-to-date. These systems require continuous updating of the attack repository for new attacks and are not suitable for detecting zero-day attacks. To address this issue, an anomaly-based intrusion detection system (AIDS) can be utilized, functioning by establishing a profile of what is considered acceptable behavior rather than focusing on detecting anomalies.

## Anomaly-Based Method

AIDS surpasses the limitations of SIDS and is recognized as a behavior-based system with robust capabilities for detecting unknown, zero-day attacks. In this system, traffic patterns are analyzed, allowing for the identification of normal traffic patterns, while malicious traffic is blocked. However, the diverse nature of malicious traffic patterns often results in high numbers of false positives generated by these systems.

The detection of an intrusion as an anomaly hinges on a significant deviation between observed behavior and the established model. These methods operate on the premise that malicious activity differs from normal user activity, categorizing any unusual actions deviating from regular behavior as intrusions. Constructing such a system requires special care.

An anomaly-based detection system relies on rules that define the expected behavior of applications, users, hosts, or network connections. These rules are established by analyzing the attributes of regular activities within a defined timeframe. For instance, a rule related to network activity might specify the average occurrence of web activity during standard business hours. The IDS creates alerts by comparing current activity attributes with established rules based on statistical techniques.

Behavioral attributes, such as unsuccessful login attempts, the number of emails sent by a user, and the volume of packets transferred within a specific period, serve as the basis for formulating rules. Anomaly-based detection methods excel in detecting new types of attacks that were previously unknown. For instance, when a system is infected with a new and unknown malware variant exhibiting behaviors deviating from established system profiles, the anomaly-based detection system can identify and detect such anomalies.

Rules in anomaly-based systems can be categorized as static or dynamic. A static rule list remains unchanged unless a new rule is added, while a dynamic list is updated in real-time as new events occur. The advantage of dynamic lists is their constant relevance, but they may be targeted by attackers attempting to manipulate them.

Despite the advantages of AIDSS, challenges exist. Accidental integration of malicious activities into the rules is a common problem, as is the difficulty of establishing accurate rules in certain situations. AIDSS often produce a high number of false positives, especially in diverse or constantly changing environments. Additionally, determining the cause of an alert and validating whether it is a false positive can be complex due to the sheer number and intricacy of events involved.

The creation of AIDS involves two steps: the training stage and the testing step. In the training stage, a normal behavior model is created using the regular traffic profile, while the testing step employs a fresh dataset to evaluate the system’s ability to identify novel intrusions and generalize its detection capability. AIDS can be classified based on the training method employed, such as machine learning-based, statistical-based, or knowledge-based techniques.

A key advantage of AIDS is its capacity to detect zero-day attacks without relying on a signature database. Instead, the system triggers an alert when it observes behavior different from the usual activity. AIDS has several benefits, including the ability to detect malicious activities within an organization and the challenge it poses for cybercriminals to avoid detection due to personalized profiles designed to make normal user behavior difficult to identify without triggering an alarm.

## Stateful Protocol Analysis

Stateful protocol analysis stands apart from anomaly-based detection in that it does not depend on host-based or network-specific profiles; instead, it relies on standardized profiles that describe the correct or incorrect usage of protocols. This method involves comparing predefined profiles of typical protocol activities, widely accepted as normal for each protocol state, with observed events to identify any deviations. Stateful protocol analysis specifically refers to the IDS’s capacity to comprehend and monitor the current state of application, transport, and network protocols, as indicated by the term “stateful.”

For example, during the initiation of an FTP session, it begins as unauthenticated, allowing users who haven’t been verified to perform only a limited set of actions. After authentication, users are permitted to execute authorized commands. Any attempt to execute commands without proper authentication is considered suspicious, while performing them in an authenticated state is deemed normal behavior. In stateful protocol analysis, the process involves verifying specific conditions for individual commands, such as checking the maximum and minimum lengths for each command. For instance, if a standard command requires a password argument with a maximum length of 10 characters, any argument exceeding 20 characters is viewed as suspicious.
