
一旦系统投入运行，为确保在面对不断变化的运行、数据处理、存储和环境需求时继续正常运作，必须开展多种维护任务。确保您已在岗的熟练支持团队至关重要，以便处理任何常规或突发的维护工作。同时，任何代码变更都应通过第1章“通过原则和政策的安全治理”所述的正式变更管理流程进行，这是必须的。

## 生命周期模型

从更成熟的工程学科（如土木工程、机械工程和电气工程）的从业者中，经常听到的主要抱怨是软件工程根本不是工程学科。事实上，他们认为，它不过是一系列混乱的过程，偶尔能凑出可行的解决方案。事实上，当今开发环境中的所谓“软件工程”很多只是靠“胶带和铁丝”拼凑的快速搭建代码。

然而，随着行业成熟，正式的生命周期管理流程的采用已被主流软件工程所接受。毕竟，将一门古老的学科（如土木工程）的流程与仅几十年历史的行业进行比较是不公平的。20 世纪 70 年代和 80 年代，像温斯顿·罗伊斯（Winston Royce）和巴里·布埃姆（Barry Boehm）这样的先驱提出了多种软件开发生命周期（SDLC）模型，以指导实践向正式流程的演进。1991 年，软件工程研究所（Software Engineering Institute）推出了能力成熟度模型（Capability Maturity Model），描述了组织在将工程原则融入软件开发流程时所经历的过程。下面的章节将回顾这些研究的成果。建立管理模型应能提升最终产品的质量。但如果 SDLC 方法不足，项目可能无法满足业务和用户需求。因此，有必要验证 SDLC 模型是否已正确实施且适合所在环境。此外，实施 SDLC 的最初步骤之一应包括管理层的批准。

### 水fall 模型

水fall 模型最初由温斯顿·罗伊斯于 1970 年开发，旨在将系统开发生命周期视为一系列迭代活动。如 [Figure 20.2](#c20.xhtml#figure20-2) 所示，传统的水fall 模型包含七个开发阶段。每当一个阶段完成，项目便进入下一阶段。正如倒退箭头所示，现代水fall 模型允许开发在后续阶段发现缺陷后返回前一阶段进行修正。这被称为水fall 模型的*反馈循环特征*。

![FIGURE 20.2 The waterfall lifecycle model ](images/c20f002.jpg)

[**FIGURE 20.2**](#c20.xhtml#figureanchor20-2) The waterfall lifecycle model 

水fall 模型是最早尝试在考虑必须返回前序阶段以修正系统故障的前提下，对软件开发过程进行全面建模的尝试之一。但其主要批评之一是，它仅允许开发人员向后退回一个阶段，未为在开发周期后期发现错误提供机制。

### 螺旋模型

1988 年，TRW 的巴里·布埃姆（Barry Boehm）提出了一种替代生命周期模型，允许对水fall 样式过程进行多次迭代。[Figure 20.3](#c20.xhtml#figure20-3) 展示了该模型。由于螺旋模型包含了另一个模型（水fall 模型）的多次迭代，它被称为*元模型*，即“模型的模型”。

![FIGURE 20.3 The spiral lifecycle mode ](images/c20f003.jpg)

[**FIGURE 20.3**](#c20.xhtml#figureanchor20-3) The spiral lifecycle mode 

请注意，螺旋的每一次“环”都会产生一个新的系统原型（在 [Figure 20.3](#c20.xhtml#figure20-3) 中用 P1、P2、P3 表示）。理论上，系统开发人员会对每个原型应用完整的水fall 流程，从而逐步构建出满足所有功能需求、经过充分验证的成熟系统。螺旋模型解决了水fall 模型的主要批评——它让开发人员能够回到规划阶段，以适应技术需求和客户要求的变化。

### 敏捷软件开发

近年来，敏捷软件开发模式在软件工程界日益流行。自 90 年代中期起，开发人员愈发接受摒弃过去僵硬模式、强调客户需求并快速迭代交付满足该需求的新功能的开发方法。

1990 年代末，17 位敏捷开发实践者聚集并撰写了《敏捷软件开发宣言》（*Manifesto for Agile Software Development*）([http://agilemanifesto.org](http://agilemanifesto.org))，阐述了敏捷方法的核心哲学：

> 我们通过实践开发软件并帮助他人实践，不断发现更好的开发方式。通过这份工作，我们珍视：

> **个人和互动** 重于流程和工具

> **可工作的软件** 重于完整的文档

> **客户合作** 重于合同谈判

> **响应变化** 重于遵循计划

> 也就是说，虽然右侧项目有价值，但我们更看重左侧项目。

《敏捷软件开发宣言》还定义了 12 条支撑该哲学的原则，可在此查阅：[http://agilemanifesto.org/principles.html](http://agilemanifesto.org/principles.html)。

以下是《敏捷软件开发宣言》所列的 12 条原则：

* 最高优先级是通过早期且持续的有价值软件交付来满足客户需求。

* 欢迎即使在开发后期也改变的需求。敏捷流程利用变化为客户提供竞争优势。

* 以数周到数月的频繁交付可工作软件，倾向于较短的时间跨度。

* 业务人员与开发人员必须在整个项目期间每日协作。

* 围绕有动力的个人构建项目，为他们提供所需环境和支持，并信任他们完成工作。
