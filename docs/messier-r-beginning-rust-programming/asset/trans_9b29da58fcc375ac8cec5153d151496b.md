
Windows 将日志分为 Windows 日志和应用程序日志。这不是以前的情况，但在较新版本的 Windows 中已如此。历史上的 Windows 日志包括 `Application`、`Security`、`System` 和 `Setup`。如果仔细查看 [Figure 13.1](#c13.xhtml#c13-fig-0001)，还会看到一个 `Forwarded Events` 日志。在 Windows 日志之上，还有应用程序日志和服务日志。这里是供应商特定日志的所在地。每个通过 Windows 事件日志子系统生成自己的日志的供应商，都会使用 Windows 编程接口（API）来创建日志条目，一旦注册了日志，就会在这里出现一条记录。

每条日志记录都包含与 syslog 相同类型的信息，包括消息和严重程度——但在 Windows 中，信息更丰富。这包括来源，即生成消息的服务或进程。[Figure 13.2](#c13.xhtml#c13-fig-0002) 展示了一条日志消息的展开视图，该消息来自所有日志消息的列表。你会看到日志的名称，这将是前文提到的日志之一。你还会看到进程运行的用户名称。与 syslog 类似，也可以获取其他系统的消息，因此生成日志的计算机名称可用。

![FIGURE 13.2: Windows Event Log entry](images/c13f002.png)

[**FIGURE 13.2**](#c13.xhtml#R_c13-fig-0002): Windows Event Log entry

每条记录中还可以看到事件 ID。这是一个唯一标识特定事件的数字，而不是事件实例。例如，如果服务正在重启，每次重启时，事件 ID 都相同。这很便利。与 syslog 相比，使用文本搜索工具（如 grep）查找日志文件中的所有条目并不完美，因为如果事件 ID 本身是数字，它可能出现在日志的其他位置。而在 Windows 中，我们拥有按列排列的表格视图，每一列对应一类信息，包括事件 ID；因此，如果想查找特定事件 ID 的所有实例，只需点击列标题排序即可，如 [Figure 13.3](#c13.xhtml#c13-fig-0003) 所示。这保留了所有原有信息，只是以更便捷的方式重新排序日志条目。

要在 Windows 上生成事件日志消息，需要 `Pywin32` 包。可以通过 `pip` 工具安装。该包提供所有必要的导入，用于写入日志条目以及获取条目所需的信息。首先，我们获取当前进程的句柄。这很重要，因为我们需要进程所有者的用户名来在日志消息中使用。获取进程句柄后，我们可以获取进程的令牌，从而提取安全标识符（SID）。这需要三步：获取当前进程句柄、获取进程令牌、从令牌中获取安全标识符——最终得到当前用户的安全标识符。

在处理 Windows 事件日志时，需要注册一个事件源。常见的做法是将事件源存储在 Windows 注册表中。本脚本仅在运行期间注册源。另一种方式是使用 `AddSourcetoRegistry()` 函数，它不仅注册源，还将其存储在注册表中以供将来使用。请记住，Windows 事件条目中的源是产生事件的应用程序或服务。

如前所述，创建事件日志条目需要大量信息。首先，我们需要一个变量来存储应用程序的名称。同时还需要一个唯一标识错误类型的事件 ID，该 ID 应唯一标识错误条件，无论出现多少次该错误，都使用相同的 ID。它是一个数值。在编写应用程序时，也应明确定义要生成的错误及其所属类别。我们用变量 `event_category` 设置事件所属的类别，该类别和标识符均为应用程序开发者控制的数值。

最后，我们添加描述以及一些数据。数据不是必须的，但可以加入以示示例。当所有变量都已填充包含要写入日志的信息后，我们调用 `win32evtlogutil.ReportEvent()`。Python 支持使用命名参数而非按位置指定的参数。调用函数后，就会生成如 [Figure 13.4](#c13.xhtml#c13-fig-0004) 所示的事件日志条目。

Rust 也有一个 crate 允许向 Windows 事件日志写入条目。`winlog` crate 提供注册事件源以及向事件日志写入条目的功能。文档说明，它使用宏根据调用的宏确定日志级别。要编写使用 `winlog` 的程序，需要在 `Cargo.toml` 中添加它，就像添加其他 crate 一样。
