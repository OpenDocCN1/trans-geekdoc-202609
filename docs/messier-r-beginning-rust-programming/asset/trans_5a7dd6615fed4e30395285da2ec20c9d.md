
这给我们提供了三个主要层级来构建我们的应用模型，如果算上浏览器则有四个。概念上，你可以这样思考（如果你愿意为事物赋予通用的标签）：

*   **Presentation layer**：这是用户界面，在我们的情况中就是用户的浏览器。

*   **Application layer**：这是服务层，在我们的示例中就是Web服务器。

*   **Business logic layer**：这是应用功能所在的层，被称为业务逻辑层，因为它是应用规则被应用和实现的地方（让应用“运作”的所有事情）。

*   **Data access layer**：这是数据持久化和检索的地方。

这种概念化不同层的方式的问题在于，对于我来说，应用层显得有些混乱。它听起来像是应用程序所在的位置，但实际上应用逻辑是在业务逻辑层。也许更容易理解的方式是以下三个层级。再次强调，这是概念性的，我们将把几个物理/实际层合并为我们的层级：

*   **Presentation layer**：这是负责向用户展示所有内容的层，包括从用户那里接收任何输入。对于我们来说，这包括用户的浏览器以及Web服务器，或者至少是Web服务器的组件，因为Web服务器负责提供在用户浏览器中显示的信息。

*   **Application layer**：这是所有业务逻辑发生的地方，即所有程序化元素的所在。应用层可能负责格式化数据，以便能够正确返回给Presentation layer进行显示。

*   **Data tier**：这里再次发生持久化。这通常是数据库服务器，尽管实现持久化的方法有很多种。

你可以轻易地看到这在Web服务器中如何应用，即使它们只是应用程序而不是不同的服务器。将这种方式应用于原生应用程序设计可能就不那么直观了。一种思考方式是始终让一个元素/模块/函数处理I/O。你不应该让应用中的所有函数（无论它们在哪里）直接与用户通信。确保所有的I/O都在一个地方发生。这使得你可以在不修改应用中每个函数的情况下，对用户界面做其他事情。

数据持久化也一样。每个函数都不应该直接与数据库服务器通信。处理这些事情的最佳方式是通过接口实现。如果你思考一下，我们已经花费了大量时间讨论如何实现这一点。Rust中的struct提供了创建接口的能力。你可以构建一个struct，其中包含对输出句柄的引用，无论是用于控制台界面的stdin/stdout，还是文件句柄。在该struct上，你创建可以通用使用的trait。无论底层I/O句柄或接口是什么，作为程序员你调用的部分始终是相同的。

### Microservices

多年前，这个想法出现为所谓的服务导向架构（SOA）。SOA是一种将面向对象设计所能实现的所有模块化可能性“爆炸”出的方式。也许想象一下《钢铁侠2》中的场景，他把新元素的3D分子取出来并放大，以便你能看到它由所有原子粒子组成。这里本质上是同样的事情。以前，即使在面向对象设计中，你也有这些小元素被紧密打包在一起形成一个整体——分子或原子。如果你把它“吹爆”，然后以质子、电子和中子的层面来思考呢？

这正是微服务设计的核心思想。以前，你可能有一个类（在面向对象术语中），它提供了一个功能，你可以将其视为一个服务；现在，你可以把它视为一个服务。这个服务将被其他服务消费。每个微服务都有自己独立的接口供其他服务通信，并且也有本质上是合同：我，声明我的名字，庄严宣誓作为服务，我会向任何询问者提供以下内容。然后每个服务都会填写他们将向外部提供的内容空白。这在服务的接口中被编码——即服务被调用的方式。

[Figure 8.2](#c08.xhtml#c08-fig-0002) 展示了一个使用微服务架构设计的应用示例。使用微服务设计的一个常见原因是如果你在使用移动应用。一些应用逻辑包含在移动应用中，但它可能会调用云端的Web基版应用后端来完成大量工作。移动设备上的应用程序知道如何在云环境中通过API网关进行通信。你可以在[Figure 8.2](#c08.xhtml#c08-fig-0002)中看到，浏览器或移动应用都可能使用云端的API。图中可以看到一些微服务，它们是API的端点。

![FIGURE 8.2: Microservices design](images/c08f002.png)

[**FIGURE 8.2**](#c08.xhtml#R_c08-fig-0002): Microservices design

应用只知道如何调用云端应用中的端点，类似于远程过程调用。所有关键代码都在那里，由开发团队或提供整体应用的公司控制。这使得更新变得容易。无需等待终端用户在他们的端更新应用程序。端点上运行的代码大多微不足道。所有更新都可以在代码准备好部署后立即在云端实例上进行部署。

这并不意味着你必须开发移动或Web应用才能使用微服务模型。只要你能以任何方式进行进程间通信，你就可以在原生应用（如我们正在开发的那些）中实现微服务。你只需要能够让一个组件与另一个组件通信，而有许多方法可以实现这一点。

### Model-View-Controller

一个流行的应用程序设计模式是Model-View-Controller（MVC）。事实上，这与我们之前讨论的其他应用设计策略是不冲突的。使用MVC，你就有非常明确的指示，消息在应用的三个主要元素之间流动——模型、视图和控制器。[Figure 8.3](#c08.xhtml#c08-fig-0003) 展示了如何思考MVC应用及其不同组件。左侧是模型，它包含数据和其表示，以及用于操作和访问数据的代码。视图包含与用户界面交互的代码。在两者之间，你有控制器。它处理所有必要的业务逻辑，使模型与视图以有意义的方式连接。
