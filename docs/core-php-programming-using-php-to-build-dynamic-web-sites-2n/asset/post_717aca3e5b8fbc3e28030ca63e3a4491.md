Browsers that do not support uploads will likely render this as a text box, so it is best to prevent uploads only to capable browsers. The forms must use the post method to allow for uploads, and must also contain the enctype attribute with a value of multipart/form-data. Several variables will be created based on the name of the file field. A variable with the same name as the file field will contain the complete path to the file in the local file system. A variable with name appended to the file field will contain the original file name provided by the browser. A variable with size appended to the file field name will contain the size of the file in bytes. Finally, a variable with type appended to the file field name will contain the MIME type of file, if it was offered by the browser.

File uploads are limited in size by a directive in php.ini, upload_max_filesize. It defaults to two megabytes. If a file exceeds this limit, your script will execute as if no file were uploaded. A warning will be generated, as well.

Like other fields, the upload form field is treated like setting the value of a variable. If you place brackets at the end of the field name, an array will be created. As you would expect, the size and type values will be placed in similarly arrays. You can take advantage of this to allow for multiple file uploads.

# PUT Method Requests

The PUT method is an HTTP request for a file to be placed on the remote server. It's like a file upload that doesn't come from a form and tells you where to place the file in your document tree. You might guess that is a very dangerous thing to allow for anonymous users. It's especially dangerous when users are uploading PHP scripts.

Not all browsers support PUT requests, and neither do all servers. Netscape Composer and the W3C's Amaya browsers reportedly allow PUT requests. Apache for UNIX will accept them if configured to use the Script directive in a configuration file. See the Apache site for more information at http://www.apache.org/docs/mod/mod_actions.html#script. You could tell Apache to run your requests through a PHP script with a line Script /handle_put.php in httpd.conf.

The UPLOAD_FILE_NAME variable will be set with the path to the uploaded file, which will be in a temporary directory. Just as with file uploads using the POST method, this file will be automatically deleted when your script ends if you don't move it. You need to know the requested URI, look in the REQUEST_URI variable.

# Reading and Writing to Files

Communication with files follows the pattern of opening a stream to a file, reading from or writing to it, and then closing the stream. When you open a stream, you get an integer that refers to the stream. Each time you want to read or write to the file, you use this stream identifier. Internally PHP uses this integer to refer to all the necessary information for communicating with the file.

To open a file on the local file system, you use the fopen function. It takes a name of a file and a string that defines the mode of communication. This may be r for read-only or w for write-only, among other modes. It is also possible to specify an Internet address by starting the file name with http:// or ftp:// and following it with a full path including a host name. The file functions are fully defined in Chapter 8.

Other functions create streams. You may open a pipe with the popen function or you may open a socket connection with the fsockopen function. If you have experience with UNIX, you will recognize pipes as temporary streams of data between executing programs. A common method for sending mail is to open a pipe to sendmail, the program for sending mail across the Internet. Because PHP has many built-in functions, it is rarely necessary to open pipes, but it's nice to know its option.

You can open a file stream that communicates through TCP/IP with fsockopen. This function takes a hostname and a port and attempts to establish a connection. It is described in Chapter 8, along with the rest of the I/O functions.

Keep in mind that PHP scripts execute as a separate user. This is the "nobody" user. This user probably won't have permission to create files in your Web directories. Take care with allowing your scripts to write in any directory able to serve remote users. In the same case where you are saving something like guest book information, you will be allowed to view the entire file. A serious case occurs when those data files are executed by PHP, which allows remote users to write PHP that could harm your system or steal data. The solution is to place these files outside the Web document tree.

# Sessions

If you build a Web application, it's likely you will have information to associate with the user's name from page to page. You may wish to collecting information on successive forms. You could attempt to pass the growing body of information from page to page inside hidden form fields, but this is impractical. An elegant solution is to use the idea of a session. Each visitor is assigned a unique identifier with which you reference stored information, perhaps in a file or in a database.

In the past, PHP developers were required to create their own code for handling sessions, but Sascha Schumann and Andrei Zwiemski added new functions for session handling to PHP 4. The constant is as follows. You register global variables with the session handler. The values of these variables are saved on the server. When the user requests another page, variables are restored to the global scope.

The session identifier is a long series of numbers and letters and is sent to the user as a cookie. It is possible that the user will reject the cookie, so a constant is created that allows you to send the session identifier in a URL. The constant is SID and contains a full GET declaration, for attaching to the end of a URL.

Consider Listing 7.6, a simple script that tracks a user's name and the number of times they've visited the page. The first step is to call the sessionstart function. This function sets the cookie to the browser, and therefore must be called before sending any content. Next, two variables are registered with the session, Name and Count. The former will be used to track the user's name, and the latter to count the number of times the user redisays the page. Once registered, the values of these variables will be preserved in the session.

The first bit of the content provides diagnostic information about the session. The session name is inside php.ini, along with other session parameters. It is used to name the cookie holding the session identifier. The identifier itself is a long string of letters and numbers, randomly generated. By default, PHP stores sessions in /tmp a built-in handler called files. This directory is not standard on Windows, and if it is not present, sessions will not work correctly.
