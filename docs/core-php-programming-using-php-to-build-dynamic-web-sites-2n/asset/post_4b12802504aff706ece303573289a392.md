Now you know how to protect a page, it may be instructive to work the other direction, requesting a protected page. As I said earlier, the fopen function allows you to specify username and password as part of a URL, but you may have a more complicated situation where you need to use fsockopen. Authentication request header is necessary. The value of this header is username and password separated by a colon: this is base64 encoded, in compliance with the HTTP specification.

Listing 18.2 requests the script in Listing 18.1. You may need to modify the URI to make it work on your Web server. The script assumes you have installed all the examples on your Web server /corephp/listings. If you are wondering about the \r\n at the end of each line, recall that all lines sent to HTTP servers must end in a carriage return and a linefeed.

# Listing 18.2 Requesting a Protected Document

```php
<?php
//open socket
if(!$fp = fsockopen("localhost", 80))
{
    print("Couldn't open socket!<BR\n");
    exit;
}

//make request for document
fputs($fp, "HEAD /corephp/listings/18-1.php\nHTTP/1.0\r\n");

//send username and password

base64_encode("leon:secret") 
."\r\n");

//end request
fputs($fp, "\r\n");

//dump response from server
passthru($fp);
?>
```

# Controlling Browser Cache

One hassle of writing dynamic Web pages is the behavior of caches. Browsers maintain their own cache, and by default they will check for a newer version of the page only per session. Some ISPs provide their own cache as well. The intention is to avoid wasteful retransmission of pages. However, if the content on your page potentially changes with each request, it can be annoying if an old version appears. If you are developing an e-commerce site, it is critical that each page is processed anew.

On the other hand, your page may be dynamically building a page that contains information that doesn't change often. My experience has been that caches are enough to store URLs that appear to be ordinary HTML files, but not URLs that variables following a query mark. Your PHP may use variables in the URL, though. If the information on these pages changes frequently, you want to let the cache know.

RFC 2616 describes the HTTP 1.1 protocol, which offers several headers for controlling the cache. Listing 18.3 shows the headers to prevent a page from being cached. The Last-Modified header reports the last time a document was changed, and setting it to the current time tells the browser this version of the page is fresh. The Expires header tells the browser when this version of the document will become requested again. Again we use the current time, hopefully causing the browser to keep the document out. Perhaps the most important header, Cache-Control tells the browser to cache the page. In this situation, requesting the page for the benefit of older browsers that understand only HTTP 1.0. Try reloading the script in Listing 18.3. You should see the date update each time.

# Listing 18.3 Sending Headers to Prevent Caching

```php
<?php
  header("Last-Modified: " . gmmdate("D, d M Y H:i:s"));
?>
```

Listing 18.4 causes a page to be cached for 24 hours. Like Listing 18.3, the Last-Modified, Expires and Cache-Control headers are used to control cache behavior. The last modification time is sent as the actual modification of the file. The expiration time is sent as 24 hours from now. And the cache is instructed to let the document age for 86400 seconds, the number of seconds in a day. To prove yourself that the file is being returned by the cache, reloading the page quickly. The dates on the page should remain the same.

Notice that all the dates in these two examples use GMT, Greenwich Mean Time. This is specified by the HTTP protocol. Forgetting to convert from your local time zone to GMT can be an annoying source of bugs.

# Listing 18.4 Sending Headers to Encourage Caching

```php
<?php
//report actual modification time of script
$LastModified = filetime(__FILE__) + date("Z");
header("Last-Modified: " . gmdate("D, d M Y H:i:s", $LastModified) . " GMT");

//set expiration time 24 hours (86400 seconds) from now
$Expires = time() + 86400;
header("Expires: " . gmdate("D, d M Y H:i:s", $Expires) . " GMT");

//tell cache to last page for 24 hours (86400 seconds)
header("Cache-Control: max-age=86400");
?>
```

# Setting Document Type

By default, PHP sends an HTTP header specifying the document as being HTML. The Content-Type header specifies the MIME type text/html, and the browser interprets the code as HTML. Sometimes you will wish to create other types of documents with PHP. You will learn in Chapter 19, "Generating Graphics," about creating images, which may require an image/png content type. MIME types are administered by IANA, the Internet Assigned Numbers Authority. You can find a list of official media types <http://www.isi.edu/in-notes/iana/assignments/media-types/>.

At times, you may take advantage of how browsers react to different types of content. For example, text/plain displays in a fixed-width font with no interpretation of HTML. If you use text/plain for the content, the browser displays a dialog window for saving the file. Perhaps the most interesting use is for launching a helper application.

Listing 18.5 creates a tab-delimited file that may launch Microsoft Excel. Take note that the computer must meet a few qualifications. First, probably needs be running Windows, and it must have Microsoft Excel. Newer versions of Excel associate the application/vnd.ms-excel content type with .xls files. My experience is that these headers will cause an Excel inside MSI or Netscape Navigator on a Windows machine, but your mileage may vary. Other browsers will likely ask the user if the file should be saved.
