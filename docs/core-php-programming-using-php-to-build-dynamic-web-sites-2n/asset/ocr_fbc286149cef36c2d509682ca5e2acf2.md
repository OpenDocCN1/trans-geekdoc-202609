The mail function assembles the parts that make up a MIME message. These parts are sent in the fourth argument of the mail function, which is generally used for headers. In the case of a MIME message, this is used for both headers and attachments. After sending the customary From headers, a MIME-Version header is sent. Unless only one attachment, a boundary string must be created. This is used to divide attachments from one another. Another way is to avoid using a boundary value that might appear in the image, so we use the uniqid function.

Each attachment is surrounded by the boundaries with two dashes. The attachment is prepared by the makeAttachment function. Each attachment requires Content-Type and Content-Transfer-Encoding headers. The type of content depends on the attachment. If an image file is being sent, it might be the image/jpg. These are the same codes discussed above with the HTTP protocol. For the sake of simplicity, this function always encodes attachments using base64, which can turn binary files into 7-bit ASCII. This prevents them from being corrupted as they travel through the network. As you might imagine, text files do not require encoding, and complete implementations encode attachments based on content type.

It may be instructive to see the assembled message in full. Try sending a message. On a UNIX operating system, you should be able to peek at the file inside /var/spool/mail before reading it, or perhaps inside ~/Mail/received afterward.
