In this final chapter, I will touch upon some issues of efficiency and debugging, which are more art than science. Efficiency should not be your first concern when writing code. You must first write code that works, and hopefully your second concern is keeping the code maintainable. As I write this, the Zend optimizer has become available. Your optimizer can reduce memory use and execution time for you behind the scenes, but it can't address all issues of efficiency.

You will pick up some tactical design issues as you gain more experience in programming. These begin to get as idioms—repeated structures applied to similar problems. Individuals and organizations tend to develop their own idioms, and you will notice them in code found in magazine articles and code repositories. Once you accept an idiom as your own, you can consider it a solved problem. This consistency saves time when writing code and when reading it later.

In projects, a tiny minority of code is responsible for most of the execution time. Consequently, it pays to measure first and optimize the slowest section. If performance increases to acceptable levels, stop optimizing.

When a bug appears in your script, the time you spent writing meaningful comments and indenting will pay off. Sometimes reading over troublesome code will reveal its flaws. Most of the time you will print incremental values of variables to understand the problem.

Among the many books on the subject, I can recommend two. The first is Writing Solid Code by Steve Maguire is oriented towards writing applications in C, but many of the concepts to writing PHP scripts. The other is Practice of Programming by Brian Kernighan and Rob Pike; Chapter 7 will be of particular interest.
