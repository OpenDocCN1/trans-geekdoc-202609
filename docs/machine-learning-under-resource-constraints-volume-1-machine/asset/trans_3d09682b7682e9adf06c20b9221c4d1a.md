

## 6.4.3 针对同构架构的调度策略

图 6.21 使用时间函数 `rosenbrock(·)` [\[385\]](#backmatter-001.xhtml#b_9783110785944-010_ref_385)，展示了在 4 个核心上不同目标函数的执行时间随精度水平的变化。对于中等精度水平，执行时间较低，且对 RAMBO（蓝色显示）有利。

与传统的同步 MBO 方法 `ei.bel` 和 `qLCB` 相比，`rambo`、`asyn.eei` 和 `asyn.ei.bel` 在 16 个 CPU 核心上能在更短的时间内达到给定的精度水平。对于代理模型难以建模的高度多模态目标函数（`ackley(·)`、`rastrigin(·)`），这一点尤为明显，如[图 6.22](#9783110785937_066530.xhtml#b_9783110785944-006_fig_022)所示。

[表 6.7](#9783110785937_066530.xhtml#b_9783110785944-006_tab_007) 显示，在 16 个 CPU 上，开销较小的 `asyn.ei.bel` 方法表现优于计算量大的 `asyn.eei`。在 4 个 CPU 上，对于最高精度水平 0.01，同步 `qLCB` 方法比异步方法更快。这一结果受 `qLCB` 在光滑表面函数上的良好表现影响，如[图 6.21](#9783110785937_066530.xhtml#b_9783110785944-006_fig_021)中 `bohachevsky(·)` 基准测试的 5 维和 10 维版本所示。在比较基准测试 2 维版本与 10 维版本的方法性能时，[图 6.22](#9783110785937_066530.xhtml#b_9783110785944-006_fig_022) 显示，与低维问题相比，`rambo` 方法在高维问题上优于所有其他方法。

[图 6.23](#9783110785937_066530.xhtml#b_9783110785944-006_fig_023) 以基准测试的 5*d* 版本为例，可视化了所有 MBO 方法在 16 个 CPU 核心上的并行配置评估（作业）映射。每个灰色方框代表相应 CPU 上作业的执行时间。间隙代表 CPU 空闲时间。对于同步执行的 MBO 方法 `rambo`、`qLCB` 和 `ei.bel`，垂直线代表一个 MBO 迭代的结束。红色方框表示 CPU 正在进行点提议计算。

由于同步变体 `qLCB` 和 `ei.bel` 会将运行时差异巨大的作业排在一起，从而导致长时间的空闲，因此对运行时各异的作业进行资源估计的必要性显而易见。`rambo` 中的调度能够减少这种空闲时间。这种高效资源利用的效果随 CPU 数量的增加而增强。`rambo` 达到了与异步方法近乎相同的有效资源利用率，同时最快达到精度水平。蒙特卡洛方法 `asyn.eei` 产生了高计算开销（红色方框所示），这降低了有效评估次数。此处，新点提议的开销有时需要与作业评估相同的时间。空闲发生的原因是 EEI 的计算被鼓励等待正在进行的 EEI 计算以纳入其提议。这种开销也随评估点数的增加而增加。相比之下，`asyn.ei.bel` 的开销相对较低，因此基本没有空闲时间。这似乎是 `asyn.ei.bel` 在 16 个 CPU 核心上的优势，平均而言，它在所有精度水平上的表现优于计算量大的 `asyn.eei`，尤其是在高维问题上。

**观察** `rambo` 优于传统的同步 MBO。`rambo` 中调度获得的资源利用率带来了更快、更好的结果，特别是在问题维度（可配置参数）和可用 CPU 核心数量增加时。平均而言，`rambo` 收敛到最优解的速度比所有考虑的异步方法都快。这表明 RAMBO 方法获得的资源利用率改进了 MBO，尤其是在可用 CPU 核心数量增加时。即使难以预先确定运行时间估计的质量，对于机器学习方法的超参数优化等实际应用，也可以假设运行时间是可预测的。结果还表明，在某些设置中，填充准则的选择决定了并行化策略以获得更好的性能。

### 6.4.4 针对异构架构的调度策略

正如[第 6.4.3 节](#9783110785937_066530.xhtml#b_9783110785944-006_s_004_s_003)所述，MBO 的资源感知调度使用两个输入：估计的资源利用率和提议候选的优先级。虽然候选的优先级按上述方式计算，但异构系统需要增强资源利用率的估计。

**异构系统的资源估计** 之前用于估计候选执行时间的回归模型基于克里金法；现在改用随机森林。随机森林更适合异构系统，因为由于表示处理器类型的额外分类变量，作业执行时间构建了一个不连续模型。回归模型现在需要为提议的作业集 `J = {1, ..., q}` 中的每个候选作业，以及每个可用的 CPU 核心 `K = {1, ..., m}` 估计运行时间 `t̑[j]`。这是必需的，因为作业的执行依赖于处理器。如果底层异构架构已知，每个作业的运行时间估计数量可以减少到不同处理器类型的数量。因此，基于所有先前评估作业的运行时间来构建黑盒函数的运行时间模型，在每次 MBO 迭代中，为每个可用处理器类型 `k ∈ K` 预测作业 `j ∈ J` 的运行时间，因此表示为 `t̑[kj]`。
