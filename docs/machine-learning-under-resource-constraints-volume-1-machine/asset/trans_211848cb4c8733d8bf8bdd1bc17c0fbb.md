
我们执行并分析了来自 TPC-H 基准测试的查询，以展示放宽星型模式基准测试的特定假设（例如使用一个中心化表）时的效果。我们根据 Boncz 等人 [\[61\]](#backmatter-001.xhtml#b_9783110785944-010_ref_061) 的工作选择了一组查询子集，以捕捉 TPC-H 基准测试的挑战性方面：Q1、Q4、Q13 和 Q21 包含繁重的聚合操作；Q9 和 Q18 包含繁重的连接操作；Q4、Q19 和 Q21 包含并行性瓶颈。我们修改了 4 个查询，因为 `HorseQC` 目前不支持所有操作，例如 like 表达式。实验结果如 [图 8.22](#9783110785937_085767.xhtml#b_9783110785944-008_fig_022) 所示。对于 Q1，`HorseQC`：多遍 没有结果，因为该策略耗尽了 GPU 显存。算子逐个执行 显示的结果是针对 DBMS 支持的所有 TPC-H 查询。

**观察结果** PCIe 和内存受限的基线比 SSB 基准测试显示出更大的变化。这主要是由连接结构引起的，例如，Q13 连接三个小表，而 Q17、Q18 和 Q21 连接最大 `lineitem` 表的多个实例。

内核执行时间显示，`HorseQC` 相比算子逐个执行 最高可提升 8.6 倍。对于 Q1、Q4 和 Q9，存在算子逐个执行 的内核执行时间短于编译策略的情况。进一步调查显示，在这些情况下，算子逐个执行 将某些算子移至 CPU 执行，这意味着测量仅涵盖了有限数量的操作。

对比查询编译器的各个变体，我们观察到 `HorseQC`：全流水线 始终优于 `HorseQC`：多遍，最高提升 5.4 倍。`HorseQC`：全流水线 在 11 个查询中的 8 个查询上实现了低于 PCIe 传输时间的执行时间。对于 Q1、Q13 和 Q18，PCIe 带宽无法完全饱和。这是因为这些查询包含未过滤列的分组聚合（参见实验 2）。`HorseQC`：全流水线 的执行时间在最好情况下仅为 PCIe 传输时间的 5.6%，在最坏情况下为 268.1%。

#### 8.2.10.8 实验 5：可扩展性

由于宿主 DBMS CoGaDB 深度集成的存储层实现，我们无法构建一个完全可扩展的 `HorseQC` 版本。因此，我们进行了一项单独的实验，将 Resolution 微执行模型与批处理宏执行模型相结合，用于 SSB 查询 3.1 的星型连接。解耦该实验使我们能够应用 Yuan 等人 [\[728\]](#backmatter-001.xhtml#b_9783110785944-010_ref_728) 的协处理器数据管理规则，并测量更大数据集的端到端性能。

星型连接以总体 3.4% 的选择率重组三个维度表和一个事实表。我们在 GPU 全局内存中为维度表构建哈希表。事实表驻留在页锁定主机内存中，每列被划分为 0.5 MB、2 MB 或 8 MB 的块。这些块通过 PCIe 异步传输到一个内部内核中，该内核通过探测每个维度哈希表来计算星型连接。

[图 8.23](#9783110785937_085767.xhtml#b_9783110785944-008_fig_023) 显示了执行实验时每种块大小的端到端执行时间。我们观察到执行时间随着规模因子的增加而线性增长，并且大于 2 MB 的块大小可以饱和 PCIe 带宽。在所检查的规模因子下，计算不会成为瓶颈。当块大小为 4 MB 且规模因子为 300 时，GPU 全局内存中中间数据的大小仅为 473 MB。因此，我们预期该方法能以线性性能扩展到更大的数据库。

**观察结果** 对于支持的查询，`HorseQC` 比 CoGaDB 快达 5.8 倍。虽然 CoGaDB 使用 GPU 全局内存作为频繁使用列的缓存，但 `HorseQC` 不在查询间缓存数据。这表明 `HorseQC` 利用内存和互连的效率更高。对于 Q6 没有性能提升，因为查询执行受限于 PCIe 带宽。

`HorseQC` 的执行时间比 MonetDB 低达 26.9 倍。尽管数据通过 PCIe 瓶颈移动，但 GPU 全局内存的额外带宽资源提供了加速。对于 Q19，MonetDB 的执行时间低于 `HorseQC`。这表明对于低复杂度的查询，直接处理数据比通过 PCIe 移动数据更有效。

### 8.2.11 讨论

在之前的实验中，我们评估了面向协处理器的查询编译新方法。在所有实验中，我们都展示了查询编译相对于算子逐个执行 处理的改进。算子逐个执行 由于大量的物化数据和重复操作，内存效率低。因此，该方法无法高效利用协处理器周围的内存系统。

虽然朴素编译技术提高了内存效率，但归约和前缀和将算子流水线拆分为多个遍数。这样，该方法继承了算子逐个执行 的缺点。这表现为内核执行时间经常超过 PCIe 传输时间。

我们演示了一种查询编译技术，将流水线的算子合并为一个复合内核。结合高效的归约技术，复合内核相较于其他处理方法实现了显著优势。随着即将到来的 OpenCAPI 和 NVLink 互连技术，这些对 GPU 本地处理的改进对于利用新硬件的增加带宽至关重要。在评估设置中，所有 SSB 查询都能饱和 PCIe 带宽。对于 TPC-H 基准测试，该方法优于算子逐个执行 和朴素编译，但在 11 个查询中仅有 8 个查询饱和了 PCIe。我们得出结论，复合内核特别适合星型连接查询。

### 8.2.12 总结

在本节中，我们展示了有助于在 GPU 风格协处理器上平衡数据移动成本和计算吞吐量的查询处理技术。我们测量了不同可扩展处理方法中的数据传输量，以评估带宽瓶颈。虽然朴素的可扩展执行技术受限于 PCIe 带宽，但批处理受限于 GPU 本地吞吐量。为了解决瓶颈，我们提出了受益于片上流水线的微执行模型。朴素查询编译技术允许简单的代码生成，但继承了算子逐个执行 的内存密集型特性。我们引入了将多个流水线阶段合并为一个高效内核的复合内核。
