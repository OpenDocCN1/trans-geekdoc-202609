

# 2.1.2.1 现有框架分析

设计了大量方法和工具，用于从操作系统中提取数据，而无需重复的手动插桩和重新编译。例如，LTTng [[172]](#backmatter-001.xhtml#b_9783110785944-010_ref_172) 和 ftrace 支持对性能关键型插桩进行静态激活和停用。然而，这些框架在所获取的数据方面缺乏灵活性。例如，函数追踪器 `ftrace` 仅涵盖函数调用、相应的函数参数以及上下文信息（如进程标识符）。

通用插桩框架（如 `kprobes` [[400]](#backmatter-001.xhtml#b_9783110785944-010_ref_400)）允许按需追踪 Linux 内核中几乎任何指令，但使用繁琐且潜在危险，因为它们允许任意修改数据结构。与 `kprobes` 不同，`ExtOS` [[42]](#backmatter-001.xhtml#b_9783110785944-010_ref_042) 和 `AnyCall` [[248]](#backmatter-001.xhtml#b_9783110785944-010_ref_248) 专注于在操作系统内核中安全执行用户级代码，从而促进了 `近数据处理` [[41]](#backmatter-001.xhtml#b_9783110785944-010_ref_041)。然而，这两种方法都使用命令式编写的代码。

理想情况下，OSDAF 应提供高层视图和语言来定义插桩、数据收集以及可能的现场处理。为简化起见，我们将所有这些定义统称为“查询”，即使它们是以命令式编写的。通用 OSDAF 必须在无需重新编译的情况下提供对操作系统（OS）潜在任何部分的访问，且运行时应仅施加最小开销。现有 OSDAF 中常见的以下概念和处理步骤：

*   **事件** 是主要信息来源。起点通常是低层事件，即操作系统控制流中的点。可以追踪函数调用，某些框架也允许追踪单条指令。高层事件抽象自低层控制流事件。例如，它们可能指示网络数据包的接收或系统服务的调用。事件可以具有关联的上下文数据。对于函数边界，这些是调用参数和相应函数的返回值。相应地，高层事件提供更高层的上下文数据，例如网络数据包的目标地址，这可能无法直接作为函数参数获得。可用于数据采集任务的事件的提供是框架的一部分，或属于其可扩展库。某些框架还允许基于其他高层事件添加新的高层事件。

*   **操作系统状态** 是操作系统状态的任意部分。低层状态直接引用变量和数据结构的内容，而高层状态提供某种解释，例如，直接访问发出操作系统调用的进程名称。可用于数据采集任务的状态的提供类似于事件的提供。

*   **流** 由从事件及其关联上下文数据生成的数据流组成。例如，追踪所有关于 I/O 系统的系统调用可能已足以完成某些任务。对于其他任务，需要进一步处理或与状态结合，例如在追踪系统调用时提供调用进程的名称。

在下面列出的前三个事件驱动的 OSDAF 中，查询通常由一组探针组成。探针处理从事件（或探针点）生成数据。它由一个声明式的事件规范（指定要探测的事件）和一个生成数据的探针体组成。

**SystemTap** `SystemTap` [[196]](#backmatter-001.xhtml#b_9783110785944-010_ref_196) 探针体是一段命令式编写的代码，用于处理事件数据、将其与操作系统状态结合，并通过 `printf` 语句生成输出。它用一种类 C 语言编写，并编译为带有额外安全检查的实际 C 代码，该代码使用 `kprobes` [[400]](#backmatter-001.xhtml#b_9783110785944-010_ref_400) 来插桩内核代码。除了探针，`SystemTap` 还允许用户定义函数和全局状态。它也可以包含普通但不安全的 C 代码。可追踪事件和可访问状态的集合是可扩展的。其中大部分是库（tapsets）的一部分，该库使用与脚本相同的语言编写。

**DTrace** `DTrace` [[119]](#backmatter-001.xhtml#b_9783110785944-010_ref_119) 查询用类 C 且受限（控制流图中无循环）的 D 语言编写。D 程序仅由一组探针组成，这些探针被编译为字节码以在虚拟机中执行。可通过内置变量访问内核状态。事件和状态的提供由提供者负责，这将数据提供的细节与查询解耦。虽然 D 是一种命令式语言，但关联数组和聚合函数允许半声明式的单行查询。

**Fay** 也存在允许完全声明式指定数据检索的框架。声明式规范允许转换和优化查询以提高性能。`Fay` [[202]](#backmatter-001.xhtml#b_9783110785944-010_ref_202) 为 Windows 机器集群提供追踪功能。`热补丁` 机制作为探针的挂钩，探针负责数据收集。`Fay` 既可以通过 Windows `PowerShell` 编写脚本，也可以通过声明式接口编写 SQL 查询（针对可能的追踪点），这些查询随后被转换为一组探针并分布式处理到多个主机上。查询被表述为在已有探针输出上的关系运算。`Fay` 不允许将基于事件的数据与上下文信息作为语言机制进行结合。相反，探针独自负责在插桩代码中收集所有相关状态信息，并将其作为事件上下文数据提供。

**PiCO QL** `PiCO QL` [[233]](#backmatter-001.xhtml#b_9783110785944-010_ref_233) 完全不处理事件。相反，它提供了一个关系接口来访问内核数据结构，可通过 SQL 查询进行检查。尽管这种接口有广泛的应用范围，但基于事件（如传入网络数据包）的查询无法通过这种方式回答。因此，及时的数据采集需要高频轮询。其作者称其为一种互补方法，用于补充那些不允许基于模型的声明式访问内部数据结构的现有基于事件的系统。

# 2.1.2.2 对比

`DTrace` 提供提供者，它们隐式地扩展可用数据模型，且不绑定任何特定的低层数据提供方式。`SystemTap` 也是可扩展的，因为它基于现有的高层抽象提供高层状态和事件。相比之下，`Fay` 提供事件流上的声明式查询，可自动优化。`PiCO QL` 具有互补性，因为它以关系数据模型表示状态，可通过 SQL 查询。

我们的目标是将事件流和状态集成到一个通用模型中，并提供语言机制，支持具有 `PiCO QL` 和 `Fay` 结合的表达能力、以及 `DTrace` 和 `SystemTap` 的可扩展性的查询，且不损失性能。这将在一个框架中提供所有模型的优势。
