## 28.3.2 Towards the MCTS

In this section, we implement the MCTS algorithm. We will follow the steps outlined in the previous section and utilise the notion of bucket. We add more content into the dictionary when needed. The concept of the game as a sequence of moves or control for variable end is preserved.

Let us start by defining the empty tree, which we want to build during the MCTS iterations. The game tree is a table with three variables:

- index - variable indexing the iterations,
- gameTree - the list of nodes, which have been recorded for a given playout,
- isWinner - the status of the game at the end of the playout.

Let us further stress that gameTree is a list of nodes which are appended to the state of the board at the game starts. All the options have been played out, the last item of the list corresponds to the Expansion. Such a node is newly explored. The information stored in the gameTree is used during every iteration of the MCTS algorithm when the Selection step takes place.

The empty game tree is thus defined as:
treeCTS::[] index=`j$`;gameTree: `$()`;isWinner:`j$`);

Further, we define the dictionary with all the variables needed to run MCTS. The dictionary will be propagated through the MCTS algorithm and updated accordingly.

bucket:(`moveStateisWinner`numberOfRuns`treeMCTS`c)!($);0;j;treeMCTS;sqrt(2);

where the dictionary describes a game in the beginning when no stone has been placed and there is no information to proceed (no simulations). The meaning of the variables is follows:

- moveState - starting position of the game, it can be empty,
- isWinner - control variable to run MCTS,
- numberOfRuns - max number of trees to run by the algorithm,
- treeMCTS - game tree built so far,
- c - parameter of the UCT formula, to be chosen $\sqrt{2}$.

The key component of the MCTS algorithm is the formula for the Upper Confidence Bound, or UCT, defined in (28.0). We implement it as a function with three input. Let us implement a function which forms the MCTS algorithm. The function itself places a stone on the board, i.e. appends the move to the sequence of moves. The move is chosen according to the current state of the algorithm evolution, i.e. it can be the Expansion move by the UCT formula if there exists a populated game tree for all relevant nodes, or the Expansion step if a new node is explored, or even the Simulation step, when nodes are added randomly. The Backpropagation step is executed separately outside of this function. Function oneMCTSTRun takes as input the dictionary with variables introduced previously, expanded for local variables:

- indexInTree — this variable defines what part of the game is stored in the persisting MCTS tree
- treeDepthCounter — counter of local iterations, to keep track when going the existing game tree.
- isWinner — local meaning of isWinner controls the iteration of the MCTS algorithm, i.e., performing four steps.

The table treeCTS with the game tree built so far is in a format which needs some manipulation in order to go through the game tree during the Selection and Expansion steps. For purpose, we define a local subset of the table, called relevantTrees, which contains entries from bucket[`treeMCTS` relevant for a given iteration of the M algorithm. The relevantTrees table is used to extract allExpandedMoves, a subset of moves which have been explored in the previous playouts.

This is used in the body of the function, where the evaluation can take place based on the validity of the following condition: (available Moves~allExpandedMoves). If the condition is true, then all possible moves have been already tried. If we have a game tree already explored every node of the tree spanning from the given node and can then use the UCT function to select which child node to follow. On the other hand, if the condition is not satisfied, there exists at least one child node which has not been explored by the existing game tree. In such a case, the node is chosen randomly out of all the set of nodes which has not explored yet.
