## 7.2.7 aj

aj or “as-of” join, is the first of the three functions which provide as-of joining functionality in db+/q. These functions allow us to align time series tables with different time samplings. The as-of accepts two tables and a list of column names. For every row of the first table, it returns the values of the second table at “as-of” i.e. the index “as-of” the value of the time series column. We will illustrate the concept of aj in this example:

```
at1: [[ ]] t: 0 5; a: 10 20 30; b: 1000 2000 3000);
at2: [[ ]] t:(1+til 10); b:100*(1+til 10); c:10000*(1+til 10));
```

where we have created two tables: at1 is the one that drives the times at which we want to know the last valid observations, can be found in the other table at2. The notion of last valid is derived from the variable t – we have started with one variable in the initial case. The as-of-join is then performed as:

```
aj[ `t; at1; at2]
```

giving the output:

| t a b c |
|---|---|---|---|
| 0 10 1000 | |
| 5 20 500 50000 |
| 7 30 7000 | |

The first row of at1 has t=0, for which there is no “last valid” value in the other table at2. The output is a table, which has the same number of rows as the table at1 . contains all the columns of table at1 as well as the columns from the other table at2. This simple example illustrates the difference in join behaviour what we saw till. Second, column b is present in both tables, taking different values in each of them. First, column a is present in table at1 only and thus as such, it is present in the output. The output contains only the corresponding column in the output, where t values are mixed from both tables. If there is no last valid value from the look-up table, as is the case for the first observation, the value from at1 is used, otherwise, the last value from at2 is used. The column c is taken from the table at2 which, where the row is missing as there is no value prior to t=0 and there is no default value of at1.

The ordering of rows in table at1 does not matter. Let us change the order of table at1, perform the as-of join and compare it with the original join, having the outputs (and outputs only) sorted by the t:

```
aj[ `t; at1; at2` ] ~ t xasc[ `t; at1[1 2 0]; at2]
```

What is required in sorting is that the second table is sorted by the last column specified in the first argument (`t` in our example). The reason for this is to the lookup algorithm used in an aj being binary search. Also, note that the common columns in both tables are of the same type.

Let us further that more than one column may be provided for the last-valid code. The order of the columns specified matters: all columns specified prior to the last column are used for the exact join. The last column is used as an approximate lookup using binary search, which allows us to align two differently sampled time series.

The additional columns may correspond to the symbol named, traded venue or any further characteristics. The aj operation thus allows us to provide as-of join functionality for all the different symbols in the table. Let us create two additional model with all exact matches column sum

```
at3: ([[:] t: 0 5 7 1 2 6; sym:(3=a),(3=b); a: 10 20 30 40 50 60)
at4: ([[:] t:razen enlist(1+til 10); sym:(10*=a),(10*=b); b:(100*(i+til 10)),10000*(i+til 10)))
```

where the column a plays role of the time index and the column takes a role of the symbol for an exact match. The as-of join with both the time index and the symbol is written as:

```
aj[`t; at3; at4]
```

| t a b c |
|---|---|---|---|
| 0 10 1000 | |
| 5 20 500 50000 |
| 7 30 7000 | |

which, for every time index and symbol, i.e. every row from at3, finds corresponding last value in at4. Keep in mind that the ordering should be such that the left-most specified column should be the observations into categories while the right-most column is the actual time index, the case which is present in most of the high-frequency analysis. Thus the case aj[`t;at3; at4] is preferred to aj[`t;sym; at4`]. To illustrate the usage of binary search - and the retrieval of the last valid record - delete the exact matches of the column from at4:

```
at4: delete from at4 where t in at3`t;at4
```

| t a b |
|---|---|---|
| 3 a 100 |
| 4 a 400 |
| 8 a 800 |
| 9 a 900 |
| 10 a 1000 |
| 3 b 30000 |
| 4 b 40000 |
| 8 b 50000 |
| 9 b 60000 |
| 10 b 100000 |

Further, to enhance the speed of retrieve over the large tables, it is recommended that for in-memory lookup table the symbol is grouped, i.e. and within sym, the time index should be sorted. On the other hand, for on-disk tables, the symbol should be partitioned and the time index should be sorted within sym. Virtual partitions should be avoided. This is a modified version of aj, which replaces the time column from the table on the right. If we change the tables at3 and at4 such that the time indices in both of them do not overlap:

```
at5: update from at3;
at6: update from at4;
```

and aj returns the time index taken from at5:

```
aj[`sym; at5; at6]
```

| t a b c |
|---|---|---|---|
| 0 10 1000 | |
| 5 20 500 50000 | |
| 7 30 7000 | |

whereas, aj gives the actual times from the look-up table:

```
aj[`sym; at5; at6]
```

| t a b c |
|---|---|---|---|
| 0 10 1000 | |
| 5 20 500 50000 | |
| 7 30 7000 | |
| 10 40 500 500000 |

The exception is the first row, which corresponds to the case where no “last valid” observation was found and thus the time from at5 was used.

## 7.2.8.1 The Valid Join

Empirical analysis requires time to time using the concept of the “next valid” value. This may arise, for example, when we analyse the outcome of an action or exploring the predictive features of the model at hand. In such a case, we may need to find the next valid quote as given time series. Fortunately, it is easy to derive such functionality from the functions we know.

Let us consider two sets of data, each containing information about trades indicator of buy or sell as the timestamp when the trade took place – for one asset traded at distinct venues. Such an example corresponds to the stock traded at different exchanges, contract for differences (CDF) or currency pair traded at different communication networks (ECNs). When proposing hypothesis we want to (dis)prove causality between trades among the data sets, namely that the buy/sell trade in one set is Granger-causing the buy/sell trade in the other set.

We create two sample data sets such that there is no underlying law between the two sets and any causality found would be a random coincidence. The first data set contains 100 observations while the second one contains 1000 data points

dataSet2: ([ time: asc "t$-10000"j$23:59:59.999; trade2:10000(-1 i));
