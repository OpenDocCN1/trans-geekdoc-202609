The output clearly shows that the mean of the approximate TWAP is around zero. The same is for the original values val as well. The standard deviation is, on the other hand, smaller for the approximate TWAP, being approximately half the value of the original time series. Thus, the TWAP seems out the randomness in val.

The provided algorithm looks to be working well, and thus we should answer the question why we call this algorithm the "approximate" TWAP. The reason lies in the fact that over which we average the averages is always longer or equal to the specified value winFor. This comes from the verb w, which takes all the values in the window AND the last value before the beginning of the window. The weighted average takes the unequal length of the time window into consideration, and weights sum up to one.

The TWAP thus starts before the beginning of the window. Let us sum up timeVal for each row to see how the window is:

The column timeLength, which summarizes the length of each window, starts exceeding the period of 00:10:00 once we have enough observations in the window starting at i. The inequality of the window is pronounced for sparse data, where the window is comparable or smaller to the frequency of the data. For high-frequency data, where updates are at millisecond frequency, and the window is on the time scale of seconds, the approximate TWAP works well. If the window gets shorter, to tens of milliseconds, the approximate TWAP does not work well. Thus, we present the algorithm for the exact TWAP.

We calculate the TWAP using the following algorithm:

+   * Aggregate the table data using the window join wj where:
  - Variable time: Apply :: identity verb for each aggregated window.
  - Variable val: Apply :: identity verb while removing the last element of the list.
