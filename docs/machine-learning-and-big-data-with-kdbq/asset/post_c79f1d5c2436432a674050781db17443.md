When the functional query is called from within a function, it perceives `tab` as a global variable. In such a case, we have to refer to the local variable within the function, and thus we pass the name by value. We can illustrate it as follows: Let us call the functional select from a dummy function, where we first pass the table by reference and then by value. Before we call the functional select, though, we define the local table with the same name as a global variable, tab.

The call when the table is passed by reference returns the globally defined table:

```
tab: ([][] aa:til 5);
?:[`tab`();0b;)
()
```

| 4 | 5 | 1 |
| 5 | 4 | 1 |
| 6 | 3 | 1 |
| 7 | 2 | 1 |

| 9 | 0 | 1 |

On the other hand, when we pass the argument by value, we refer to the locally defined table:

```
tab: ([][] d:til 5);

()
```

| 0 |
| 1 |

We can confirm the difference by using the standard select:

```
tab: ([][] d:til 5);
:select from tab
()

Let us illustrate several examples of how the functional select can be used as this is a powerful concept. If we want to turn the qSQL select query into its functional counterpart, we recommend to proceed as follows:

- Decompose the original query into the atomic parts. We can do that by building the query step by step.
- Apply parse function on the atomised elements. The parse tree of the simplified queries shows how the components of the full query are converted.
- There is no need to parse every function into the pure functional form. We can keep functions like xbar in its form instead of turning it into the k version. This makes the query more gotten and understandable.
- Since column names are parsed by reference as symbols, we need to be able make a distinction between referring to a column name or a symbol constant: we do this by using enlist on the symbol constants, as we will see in the example below.

The following examples functional queries. All the queries return 1b. We encourage readers to run them on their own and see what the output is.

```
?[tab;);();()] ~ select from tab
```

```
?[tab;((<;b;8);(>;a;b));0b)] ~ select from tab where a>b
```

```
?[tab;((<;b;8);(+;a;c));(>;a;b));0b)] ~ select from tab where a>b, b8
```

```
?[tab;((within;b(1;6));(>;a;b));0b)] ~ select from tab where a>b, b
within (1;6)
```

```
?[tab;);();(enlist a!)!(enlist a)] ~ select a from tab
```

```
?[tab;);b;(enlist newA)!(enlist a)] ~ select newA:a from tab
```

```
?[tab;);0b;(enlist "newA")!(enlist a)] ~ select newA:a from tab
```

# 10.2.2 Functional Exec

A similar function to qSQL select is the exec function. select will always return a table, but exec will return a dictionary, or vector, if only column is selected. The functional counterpart is the same as select:

```
table;where;columns
```

where the four arguments are slightly different:

- table is referencing the table from which we want to select data. The table is passed by reference or value.
- where contains the filter criteria on which choose from the tree. Its form is a list of criteria in parse tree. The columns are passed by reference.
- group dictionary of column names upon which the table is grouped. The keys are the new column names while values are formed of the old names. The names are passed by reference.
- columns dictionary of columns to be updated. The keys define the new names, e.g. a:, while values correspond to the right-hand side of the statements of assign operator, eg.:b+1.

The input parameters to illustrate how the functional select. Let us provide a number of examples to illustrate how the functional update works:

```
tab(););0;() ~ update from tab
```

This actually gives error on both sides of ~ as this is not a valid update. Further queries are:

```
tab(););0;(enlist `a`)!{enlist `a`)] ~ update a from tab // update column a with itself
```

```
tab(););0;(enlist `newA`)] ~ update newA:a from tab
```

```
tab(););0;(`newb`)!(``a`)] ~ update newA:a, b from tab
```

```
tab(););0;(enlist `newA`){enlist (+;ab)] ~ update newA:a+b from tab
```

```
tab(););0;(enlist `a`){enlist (sum;`a`)] ~ update sum a from tab
```

# 10.2.3 Functional Update

Another important qSQL functionality is the update function. The functional-part is given as:

```
tab;where;group;columns
```

the four arguments are:

- table is referring to the table from which we want to make an update. The table is passed by reference or value.
- where contains the filter criteria on which to choose from the tree. Its form is a list of criteria in parse tree. The columns are passed by reference.
- group dictionary of the column names upon which the table is grouped. The keys are the new column names while values are formed of the old names. The names are passed by reference.
- columns dictionary of columns to be updated. The keys define the new names, e.g. a:, while values correspond to the right-hand side of the statements of assign operator, eg.:b+1.

The input parameters to illustrate how the functional select. Let us provide a number of examples to illustrate how the functional update works:

```
tab(););0;() ~ update tab
```

This actually gives error on both sides of ~ as this is not a valid update. Further queries are:

```
tab(););0;(enlist `a`)!{enlist `a`)] ~ update a from tab // update column a with itself

# 10.2.4 Functional Delete

The functional version of delete is:

```
table;where;ob;columns
```

where the four arguments are slightly different now:

- table is referencing the table from which we want to select. The table is passed by value.
- where contains the filter criteria on which choose from the tree. Its form is a list of criteria in parse tree. The table columns are passed by reference.
- group is false ob.
- columns list of columns has to be chosen.

The function symbol ! is same as in functional update. In order to achieve the delete functionality, either where or columns to be empty. Let us illustrate the functionality ahead:

```
tab;enlist(;`a;4);ob;symbol($) ~ delete from tab where a>4
```

```
tab();ob;`a-c ~ delete a,c from tab
```
