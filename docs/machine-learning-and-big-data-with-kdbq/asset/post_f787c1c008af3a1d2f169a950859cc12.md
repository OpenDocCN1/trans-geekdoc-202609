
and exploration – the second term. The value of C is a meta-parameter in the algorithm; a popular choice is $\sqrt{2}$.

The child node with the highest $UCT_j$ is chosen in the selection step. If more than one node reaches the highest number, the node is chosen randomly with equal probability. The decision based on the formula in fact reflects the minimax algorithm. The value of $w_i$, at a given point is recorded from the perspective of the player making a move. Thus, the formula makes the optimal decision for every player and thus player 1 optimizes her decision given player 2 is the same.

At the end of the selection step, the simulated game is a node with at least one child node which has not been explored.

## 28.2.2 Expansion Step

The process of expansion is to extend the existing tree and include new nodes. The iteration process reaches at the end of the selection step node which has at least one child which has not been selected before. Such a child does not have an assigned pair $(w_i, n_i)$. The iteration progresses from the node to:

- Among the child nodes which have not been visited, randomly choose one and extend the selection tree.

The new node is chosen uniformly as there is no preference among the unvisited nodes or we assume a uniform prior. The new node is included in the selection tree. Using programming, the decision tree $(w_i, n_i)$ is initialised with 0. This node will get assigned in last its values $(w_i, n_i)$.

The mechanism of the step is such that it explores new options and extends the knowledge structure – the mechanism aims to expand every node fully. Namely, at a given node, there cannot be unvisited nodes here. If a specific node is promising – it is repeatedly chosen by the selection step – all the options from the node are to be explored.

The full expansion of every node can have a disadvantage. In particular, if there is a large branching ratio, the tree will aim to grow too slowly. The selection tree row will be explored by moves which are deeply inferior and such a tree can be costly to grow. This is apparent for a game of go, for instance, where some moves wasting of computational time. The reasonable component would be here of “value” function which use heuristic rules and rule out some moves. Such approach is in AlphaGo implementation of the MCTS using deep neural networks. We omit this at this stage and follow the expansion step outlined.

We can expand by more than one node and provide faster building up of the game tree. Even though this is possible, we have to keep in mind that our objective is to fill the full/deep selection tree. The aim is to build a knowledge about the nearest neighbourhood of the game node we want to move from. The process of building would also carry a considerable storage cost; let recall the dimensionality of the game tree for go. It is feasible to stay at expansion by one node only.

Once the new node is added to the tree and the pair $(w_i, n_i)$ is initialised, the game is played.

## 28.2.3 Simulation Step

The purpose of the simulation step is to finish the game from the newly expanded node. The game is simulated randomly:

- Players are taking turns. In every turn, among all possible moves, one of the players is chosen randomly with equal probability.

The simulation is played until the game ends. Let us assume game is a zero-sum game, and one unit is awarded at the end:

```
$Y_1 + Y_2 = 1,$$
```

where $Y_i$ is the award assigned to player $i$. In where with the binary entry, the number can be 0 or 1. When there is a draw as an option at the end of the game, the value of 0.5 can be assigned to both players.

The critical feature of the simulation step is that the simulation itself is not stored. Once the simulation from the newly created node is finished, only $Y_i$ are remembered. This prevents the exhaustion of memory. We need to keep in memory the index of the player who makes a move and the state of the game, i.e. the arrangement of the board. As a result, the simulation step is memory efficient, and the simulation can be easily outsourced to external resources without the need to transfer an additional amount of data. A possible option at this step is to simulate independent games in parallel and then average $Y_i$ across simulations.

Once the simulation is finished, the output of the simulated game is obtained, the iteration proceeds with the back propagation step.

## 28.2.4 Back Propagation Step

In the final step, every node of the decision tree is updated by the information obtained from the simulated playout. In particular, every node of the decision tree has been chosen during the particular game is updated as follows:

```
$n_i \leftarrow n_i + 1,$
```

and $w_i$ is updated based on which player was making the move:

```
$w_i \leftarrow w_i + Y_j,$
```

where $j$ corresponds to the index of the player who made a move. In particular, every odd-numbered level of the tree corresponds to $j=1$, and every even-numbered level of the tree corresponds to $j=2$, respectively.

This step concludes one iteration of the MCTS.

## 28.2.5 Finishing the Algorithm

The MCTS algorithm is composed of many iterations. Player 1 chooses such an action which corresponds to the node with highest $w_i/n_i$, where $i$ corresponds to the index of nodes in the first level, i.e child nodes of the root node. The decision rule at the end considers the best node as the one chosen. The exploratory part is not employed when making a move; the move is pure exploitation.

The number of iterations is chosen based on available resources. The MCTS algorithm can be interrupted anytime, and the algorithm can have dynamically set the number of iterations. For instance, the game can contain a cap on the amount of time to decide the move. In such a case, the MCTS algorithm will try to run as many iterations as possible. Since simulated games can take a variable amount of time, such numerical policy can be allocated resources efficiently as opposed to the fixed number of it iterations. Similar policies can be adapted for variable numerical resources (CPUs or memory).

## 28.2.6 Remarks and Extensions

Let us make a couple of remarks about how to extend the MCTS presented above. First, for some games value of every move/stone can be the number of the stones already placed. In such a setup, we can control the number of simulations tremendously. G and Silver (2007) proposed an extension to the algorithm called Rapid Action Value Estimation, or RAVE. This assumes that the value of a stone is independent of the state of the game. Then, when we are supposed to update $(w_i, n_i)$ for nodes contributing to the game, we update moves across the entire game. if player 1 places a stone at, say, a center and the game where it resulted in a win, we identify all possible games in the game tree where player 1 places a move and update the pair $(w_i, n_i)$ in all of them. However, it is more convenient to updating in the way as we have introduced above and preferably adjust the formula for UCT as we will see.

This extension boosts the statistics gathered by the MCTS. The disadvantage of this approach is a strong assumption being made on the game. For the game of go, this assumption is highly unfeasible, given the game to be driven by various patterns. Further, players are introduced to the game through recognizing patterns of varying complexity. The same holds for the game of chess. Since the usage of the MCTS goes well beyond the world of games, this is a possible extension. In order to mimic the absolute of the key assumption, the formula for UCT in the Selection step can be amended to provide some flexibility:

```
$UCT_i = (1 - \beta) \frac{w_i}{n_i} + \beta \frac{w'_i}{n'_i} + C \cdot \sqrt{\frac{\log s_{parent}}{s_i}},\quad (28.20)$
```

where $w_i$ and $n_i$ are defined and populated as the original MCTS algorithm deduced above, $w'_i$ and $n'_i$ are the total numbers of wins and the total number of games containing this given move, i.e.

```
$w'_i = \sum_{nodes} w_i \quad (28.21)$
```

```
$n'_i = \sum_{nodes} n_i, \quad (28.22)$
```

with sum running over trees of which which are the same.
