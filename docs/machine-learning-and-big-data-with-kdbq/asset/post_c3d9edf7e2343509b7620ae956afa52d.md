## 11.3 CONSECUTIVE RUNS OF

Assume we have a time series – typically a series of observed metrics such as a price – we want to calculate the time series points which obey a given rule for a number of consecutive occurrences in a row.

For example, in the following list of randomly generated prices:

```
prices: 10?5;
```

```
4 1 4 4 4 0 2 0 4
```

We want to know if the time series is outside 50 percent of its five-point moving standard deviation, for two ticks in a row.

We first calculate the indices which are outside half of the standard deviation:

```
indices: { not x within (a-d;(a:5 mdev x)+d:.5*mdev x) } prices;
```

```
0011010011
```

How would we calculate the sequential occurrence of this rule? In other words, how do we find the indices where this rule holds for N times in a row?

The solution to this appears to require some recursion and thus brings adverts into our mind. We recall a very useful optimisation of scan which we saw in Chapter 3 when presenting the exponential moving average, which was the fact that

```
{x y'z}
```

is an optimised shortcut to

```
{{z+y+x}\[x;y;z]}
```

We can therefore implement a trivial case of this on the indices vector itself, where x is our starting point (0 runs), y is the output of the last (recursive) call and z is the (recursive) element of the indices vector, indices[i]:

```
.quant.stats.runs: @ x\"f";
```

which gives the desired count of "truths" (1's) for the time series:

```
.quant.stats.runs indices
```

0 0 1 2 0 1 0 1 2

It is now simple to find the locations where that rules hold:

```
where 2=.quant.stats.runs indices
```

## 11.4 REAL-TIME SIGNALS AND ALERTS

In the previous section, we saw how one would perform standard tasks such as moving calculations and scanning for consecutive runs of a given rule. This is useful for analysis of data and to initially conclude which type of functions – signals – we are interested in analysing and calibrating their parameters. Once have done that, we would like to explore sign creation in a real-time fashion, as well as a simulated scenario where we stream the data – just like it would be streamed in real-life – then we run the calculations as the events happens. This enables us to create a time signal based on the result of our calculation. As mentioned, this could be either triggered in real-time, or for backtesting purposes, in a simulated run where our software is just like it would be in a real-time scenario.

To perform such window calculations in real-time and create an actionable outcome – a signal or alert – we need a way to efficiently run such rules on the incoming updates, as soon as they arrive.

One way to perform this is to have an in-memory cache which effectively is a table upon which incoming updates are joined and trigger our favourite computation in one go.

A way to store the in-memory cache is by having the time series of trade prices, their times and volumes, stored in a nested structure, keyed by sym.

Using standard trd trade data, and pretending that this is now the result of today's past updates, stored in cache, we can represent our cache as:

// run a 3-tick vwap using each record

Notice the use of the global assignment inside our function, since we want to update the global tables. Beside, we want to clean up cache to not contain updates which are not needed for our computation. This is important since cache can rapidly grow in size and cause memory usage throughout the day.

This can be achieved by updating the trades tables to only keeping the last N ticks for each of the nested caches:

```
.quant0.upd.trades:{new
// the incoming data sent by the upstreamhandler or
// tickerplant, in table format
// aggregate the new data by time,volume and price
// then insert each list to each column for each key (record) of the
global cache
trades:: select time,volume,price by sym from new;
// run a 3-tick moving vwap
ret: select sym, (-3*volume) wavg(-3-price) from trades;
trades:: update -3*time,-3*volume,-3*price from trades;
};
```

The advantage of storing incoming data in a single nested cache is that we can run a series of rules, looking at a variable window of data. Our cache can retain the history of observations only up to the maximum window required by our rules.

## 12.1 HISTOGRAM

A histogram is a representation of the data distribution, a visualisation tool for the data points in our sample. Theoretically, it represents an estimate of the probability function for a continuous variable. It is, in fact, an empirical function. In this chapter, we treat histograms as a visual tool which allows us to see and investigate the structure of our data.

A histogram can have two inputs, and the bins (or buckets); it returns the number of data points per bin. The bins represent a scheme which will split the interval of the data into a list of non-overlapping intervals. Although the bins are not necessarily equal, in this section we will only consider equidistant intervals.

It is convenient to normalise the histogram so it can represent a probability function, where every plot captures relative frequency. In such a case, the histogram is a kernel density estimator. Using some form of polynomials or splines, the kernel can be further enhanced to obtain smoothed histograms. In our example, we will use qPad, with the option "Bars", to obtain a visual representation of the histograms.
