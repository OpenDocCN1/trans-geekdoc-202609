#  5.1 INTRODUCTION TO MAKING IT WORK: ERRORS

One of the common reasons heard around against using the q language is the limited ability to debug the code, especially when compared to conventional programming languages and their IDEs. Ask any q developer about his or opinion of q and this argument will be surely mentioned among the three arguments: when one gets beyond a “no”. Indeed, the debugging tools are in the case of q relatively limited. However, q and java are fundamentally different languages. q has a much more interactive programming environment, so a lot of the development is a mixture of running snippets of code dynamically on some sample (test or real) data and then building out from that. In other words, to go through the code step by step and monitor what the code is doing is innate to the language itself. What we focus on is two main points: first is avoiding syntax errors when initially writing our code in our IDE, and secondly, interpreting the generally obscure and short q errors and how we can make these more verbose while our code increases complexity.
