```
We will now show a second – and more efficient – way to achieve the same result. Recall that aj will return the values of the lookup table as-of of the first table, i.e. the 'last valid' observation. In order to get the 'next valid' observation, we can shift the lookup values of the second table in order to receive the next value when we perform the aj. This can be written as:

```
dataCombined: aj[`time; dataSet1; update next2 from dataSet2`]
```

And the result is the same (and faster) in the previous method. By finishing our hypothesis about dataSet1 Granger-causing trades dataSet2, we can test the simplified Granger causality by running the correlation between trade1 and trade2 as variables are properly linked, i.e. entry trade2 is the successor of entry1 within the same row. Besides, the Granger causality is based on a linear regression model and in the case of two variables, the problem is equivalent to finding a significant correlation coefficient.

We implement the Granger causality test for trades by first calculating the correlation coefficient between the two columns trade1 and trade2:

```
correlation: exec trade1 trade2 from dataSetCombined
```

and, second, assessing the statistical significance of the estimated coefficient. In other words, we want to determine whether the estimated number is statistically significant from zero or not. This can be done by calculating the t-statistic of:

> $t = \rho \sqrt{\frac{N-2}{1-\rho^2}}$

where $N$ is number of observations and $\rho$ is the estimated correlation coefficient. The t-statistic reads:

```
.quantQ.join.tStats[rho;N]
// rho -- correlation
// N -- size of sample
rho*sqrt[(N-2)/(1-rho^2)];
```

and applied on our data:

```
.quantQ.join.tStats[correlation; dataSetCombined]
```

The corresponding p-value allows us to conclude that the correlation coefficient is statistically significant from zero and there is Granger causality link between trades – see Chapter 14 for how this corresponds to the data generating process where both sets were independent.

# 7.2 asof

The asof verb has similar functionality to aj but also supports the “asof” mode. The right-hand side argument is a dictionary or table where the key or column plays a role of reference time for which we want to find last valid observation if the dictionary/table has more than one key/column the last one is considered to be time while the remaining ones play the role of grouping column demonstrated in the aj verb. select sym, b from aj[`select t from at5;at6]`
```

at6 asof select t from at5 where a=60

select b from aj[`sym`;t;at5;at6]`

```
# 2.1.10 wj

wj is the last of the three "as-of" functions provided in q and stands for a "window" join. The window join aggregates data from the lookup table over a window applying a specified function and joins the result with another table. The window join is defined as a function of four arguments. The first argument specifies windows over which the aggregation takes place. The second argument is the list with names of the columns which are used for joining just like in: group(column) followed by a sorted field, which is typically a time column. The third argument is a table that provides our data to join on. The last argument is a list of the lookup table to perform the aggregation on, followed by pairs of aggregator functions and the corresponding column to aggregate on.

An example illustrates the case explained in the previous paragraph. We use the generated datasets dataset1 and dataset2 and aim to aggregate data from trade2 over a window around the times in trade1.

```
dataset1([{time: "t-$100?"$23:59:59.999; trade1:100(-1 1)})
dataset2([{time: "t-$100?"$23:59:59.999; trade2:10000(-1 1)}])
```

For every realised trade in dataset1, we aim to aggregate data from the table dataset2 over a window starting 1 minute before the trade and ending at the time of the trade. Thus, we have to create a series of time windows, one pair per row in dataset1:

```
