
## Splayed and Partitioned Tables

We can use the following command to save this table as a binary file.

```
`:tradesfile set trades
```

The resulting file will have 965 bytes on Windows and will reside in the current directory, which you can check with \cd; by default this will be the directory containing the q exe executable. To save it in a different directory, i.e. what we have specified as datadir, we can use something like this:

```
(`$":,datadir,/tradesfile") set trades
```

The brackets are needed, as

```
`$":,datadir,/tradesfile" set trades
```

is interpreted by q, from right to left, as

```
`$":,datadir,/tradesfile" set trades
```

which is not what we want. In the case of success the return is the file path as a symbol:

```
:C:/data/tradesfile
```

We can then load the table from a file either using get, in which case we can specify the new table name (by assigning to a variable with name the result of get):

```
trades1 : get "$:\,datadir,/tradesfile"
```

or load, in which case the loaded table will be assigned to a new variable, the variable's name matching the name of the file, in this particular case, tradesfile:

```
load "$:\,datadir,/tradesfile"
```

Finally, we note that in the examples above, a file descriptor – an indicator to a file or output resource – is denoted by a symbol whose first character is the colon .. Another way to construct the file descriptor if we are already dealing with a symbol path, using the hsym function:

```
path:`datadir
path
/path/to/file
hsym path
:/path/to/file
```

## DATA OPERATIONS

### 6.3 SPLAYED TABLES

Instead of saving the table as a single binary file, we could save splayed, i.e. so that each column is saved in a separate binary file. This is particularly useful for medium-sized tables (up to 100 million rows). Queries often refer to a small subset of such table's columns. Storing the columns in separate files allows kdb+ to save time by loading only them. To achieve this, we would normally call set with a directory path, rather than a file as its argument. However, the following will fail to play the table since it contains unenumerated columns of type symbol:

```
hsm[`$datadir//tradesdir` set trades
```

We can remove those columns and save the table in one

```
hsm[`$datadir//tradesdir` set mktflag
```

Notice the trailing / in the directory path. As a result of this, the tradesdir will be created under datadir. It will contain files with names .d, code, comments, date, time, and volume. We couldn't save the original trades table because we show how to enumerate them. Before proceeding, delete the directory with all its contents in case you create that following the steps above, so we start with a clean slate. To enumerate the symbol columns in trades, we use .Q:

```
tradesdir: hsm `$datadir//tradesdir/;
tradesenum: .Q[tradesdir; trades];
```

This will create the directory tradesdir with a single binary file in it, named sym. That file enumerates the values found in the columns of type symbol, named `code`, `price`, and `time`. Once this is, we run

```
tradesdir set tradesenum
```

The directory now contains the files with .d, code, date, mktflag, price, sym, volume. Notice that this time, with the symbol columns enumerated, we were able to save the columns of type successfully. Note that, unlike the command,

```
tradesdir set trades
```

will fail with 'type', as before. ¹The same error would be thrown if the table were keyed. We would need to remove the key with () before saving the table.

Let us take a look at the individual files in the directory tradesdir. The files date, price, and volume contain the serialisations of the columns with the corresponding names. Notice that you can serialise the columns individually. The command will create a file myfile whose contents are identical to tradesdir/price. Recall that trades[`price`] is a list of type float:

| |
| :--- |
| 38.3 1239.7 1240.5 38.04 18.85 124.2 1240 18.53 40.61 18.44 40.78 |
| 41.43 18.35 19.05 1257.9 1258.7 |

When we run

```
hsm[`$datadir,/mycols` ] set col tradesdir[ `$datadir,/mycols` ] set col trades
```

we obtain a file, mycols, whose contents match those of tradesdir/.d. This is the serialisation of the column names (as symbols) in the table. Here, when we run

```
hsm[`$datadir,/mycode` ] set trades[`code`]
```

we obtain the myfile whose contents differ from those of tradesdir/code. This is because all the symbols in the enumerated table are stored in tradesdir/sym, whereas tradesdir/code contains indices of the symbols within tradesdir/sym. We will reproduce tradesdir/code by running

```
hsm[`$datadir,/mycode` ] set tradesenum[`code`
```

This underlines the difference between trades and tradesenum: .Q returns a copy of the columns that have been enumerated and those that haven't as follows:

```
type trades[`code`]
type tradesenum[`code`]
```

although the results of meta trades and meta tradesenum look identical.

Similarly to tradesdir/code, the file tradesdir/mktflag contains serialised enumerated strings containing indices of the actual strings within tradesdir/sym. Each distinct text string, corresponding to each distinct symbol value, is stored in tradesdir/sym. Using the terminology from Java, symbols are interned. The column comments, whose type is string (rather than symbol), was analysed by two files: tradesdir/comments and tradesdir/comments\. The latter, comments\ contains the actual text found in the strings. The serialisations of the enumerated symbol columns, where distinct values are stored only once, comments\ contains them. If you open this file in a binary viewer, you will see that "NEXYM/CME Group trade", for example, occurs multiple times.
