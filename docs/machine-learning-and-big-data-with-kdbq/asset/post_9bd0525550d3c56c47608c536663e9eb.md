# 5.3 DEBUGGING-SERVER-SIDE

It is not always possible to debug directly on the console. When using an IDE to connect to a remote server, or our local process connects to a q process, we may need to deal with our function while executing server-side.

One way to facilitate investigation here is following the guidelines we gave earlier in this chapter around safety checks using statements and detailed logging. Another tool we have is the ability to trap execution and return the details when these fail. We define a utility function which uses the .trap internal function which traps execution and returns the error and the full stack trace.

```
.q.debug.trap: {[func;args]
.Q.trap{[value enlist[x,y];func];args;(x.Q.s y)]};
```

To illustrate the concept, assume a remote server is listening to port 5000, and we do not have access to its console or logs (e.g. it could be administered by another user or running on a remote host)

We open a connection handle h to this server and run our function with its arguments passed in as a list:

```
h:hopen=:localhost:5000
h (wrongFunction;1;2)
```

```
'type
[0] h (wrongFunction;1;2)
```

The server returns the 'type as expected. However, we are unsure where this occurred, and we wish to get more debug information. Stepping through the code or using the meta utility is not going to help us since the function was run on a different process and we do not have access to the scope like previously.

¹Execution of function and its arguments as a list of (func;arg1;arg2;...) is a generic way of evaluating code in q, as we will see in Chapter 10. In this example, the execution of the function happens remotely by sending the prepended line with the connection handle h.

q)result: h (.q.debug.trap;wrongFunction;1 2)

We conclude that there are sufficient debugging options for us to pinpoint where an error occurs in q. Moreover, in a modular design with small functions, finding the incorrect statement should be straightforward. # 6.1 INTRODUCTION

Neither the kdb+ instance, nor the q code, live in isolation. In a kdb+tick setup, the data may be captured straight into a kdb+ instance. In other cases, we may obtain the data as flat files from an external source and choose to use q to process it. It is clear why we make this choice: the database is an excellent environment for dealing with large volumes of data, more often than not, high-frequency data and q is a powerful tool for analysing this type of data.

q's efficiency extends to dealing with files: while we could use, for example, Python or R, to preprocess the data to a kdb+ instance, we will have to take a performance hit compared to kdb+ native methods for reading files. It is true that Python and R offer richer toolkits for dealing with system objects. However, there are situations when we may still choose an external tool to process the data. We may choose to use Python's regular expressions and library. Alternatively, we may need to unzip or decompress the files before reading them from kdb+. Luckily we can do this without leaving kdb+, q offers us toolkits for calling shell commands and external programs. In this chapter we discuss kdb+ concepts of splayed and partitioned tables and also show how to load and save data using q. Both types of data, especially partitioned tables, are useful for representing large sets. Data occurs in applications referred to as big data.
