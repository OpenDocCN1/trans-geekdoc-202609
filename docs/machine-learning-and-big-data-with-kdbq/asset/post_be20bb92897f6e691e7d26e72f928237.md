The price process is driven by a variation without the need for iteration. The parameters are such that log-prices are expressed as a percentage. We multiply the equation by a factor of 0.1, which ensures that price changes are normalised to one. As we have pointed out in the beginning, the jumps in the price process are scaled to the prevailing value of volatility calculated as the previous value. This value is not available on the first tick, and thus we have to replace the first entry which is done using the zero-fill function. Since the volatility $\sigma$ corresponds to a value normalised to trading day, we have to provide an extra scaling factor of $1/\sqrt{\Delta}$. Beside, jumps are always positive. This means that the price process is always increasing and the price is increasing. If we normalise the price to start at 1, we recover the price path as:

```q
// price path 1
tableSim: update price1: exp logP1 from tableSim;
// price path 2
tableSim: update price2: exp logP2 from tableSim;
// price path 3
tableSim: update price3: exp logP3 from tableSim;
```

We may also change the magnitude of jumps to make them more dominant. We encourage readers to explore the price evolution by varying the different parameters.

## 19.1 Non-Numeric Features and Normalisation

Let us discuss two technical tricks which are useful to cover before we dive into the machine learning methods themselves: dealing with non-numeric features and the normalisation of features. For both, we provide q functions.

### 19.1.1 Non-Numeric Features

When working with large and rich data sets, we often encounter features which do not have a numerical representation. In the context of finance, such a feature can be the venue where a financial transaction took place: some assets are traded at the same time on several exchanges—due to regulatory or exchange/venue related rules or constraints—may lead to a different price discovery process. Other examples are the day of the week, which itself is a non-numeric characteristic, or the output of a questionnaire submitted by analysts. Machine learning methods have to deal with such features, and we thus briefly outline how to incorporate non-numeric features into the learning algorithms.

In general, we may encounter two types of non-numeric variables: ordinal variables and categorical variables. The former stands for variables which are ordered and thus a quantitative measure of the difference between values can be assigned. Such an example is investment grade, which tends to have an alphabetical representation—e.g AAA+, AAA, AA, .... The difference between two assets of grade AAA+ and AAA is smaller than the difference between two assets of grade AAA+ and AA.

The latter, on the other hand, do not have such property and we cannot establish any intuitive difference between different values. The days of the week under this category, as we may easily say that market activity on Monday is different to Wednesday's, but we cannot say that market activity on Tuesday just lies between them.

### 19.1.1.1 Ordinal Features

A common approach to turn the ordinal variables into numerical ones is to use integer representation for them, i.e., to provide a map between features and integers. As an example of such procedure, let us assume grade, which captures the quality of an asset. The variable takes values from set A,...,E, where the best quality is represented by A and the worst by E. Let us generate a random list of 15 features:

| feature |
| :--- |
| C'A'B'C'B'A'B'C'D'E'E'C' |

We used some symbols for convenience, as the values may be repetitive. A step further would be to restrict ourselves to the enum type and we encourage the reader to extend the example with such a type. In order to turn the feature into an integer list, we need a dictionary which maps the values onto integers. In our case, we may achieve this programmatically as we know that alphabetical ordering is the right one:

```q
.quantQ.preml.alpha2Int:[list]
// list -- the input list of all non-numeric features, underlying list
// is alphabetically ordered ordinal variable
listIndep: asc distinct list;
// dictionary mapping the underlying list on the integers
:listIndep!til count listIndep}
```

This gives:

```q
(`s*='A'B'C'D'E'!0j, 1j, 2j, 3j, 4j)
```

where the dictionary also contains the sorting attribute as a side effect of calling the function on the unique types from A to E.

We can map the underlying arrays by

```q
.quantQ.preml.alpha2Int[feature] feature
```
