

# Security Center 架构

当你使用 Security Center Monitor Azure 中的资源——无论是本地还是托管在其他云提供商（如 Amazon AWS）时——其架构与图 2-1 。

![](img/4b11e95292819ab1a383a41ef73aedb4_42_0.png)

图 2-1 Security Center 代理与 Security Center 服务之间的连接

Security Center 使用 Microsoft 监控代理（Monitoring Agent），这与 Operations Management Suite 和 Log Analytics 服务使用的代理相同。在 Windows 系统中，Security Center 会安装 Microsoft 监控代理（HealthService.exe）。在 Linux 系统中，Security Center 会创建 `omsagent` 守护进程，该进程在特定账户下运行。该账户在安装代理时会自动创建。

在 Linux 系统中，Security Center 利用审计框架（audit framework）从 Linux 机器收集审计记录。审计框架由两个主要部分组成：第一部分是一组用户空间工具，它们提供了大量操作，允许管理员更好地调整规则、分析审计日志或在配置错误时进行故障排除。第二部分是一个内核级子系统，负责监控系统调用、通过 netlink socket 对其进行过滤，并将匹配消息写入缓冲区。审计记录被收集并聚合为事件，并使用最新版本的 Linux 版 Microsoft 监控代理进行增强。审计事件的一个集存储在你的工作区中并由 Security Center 管理。当检测到威胁时，Security Center 会触发警报。从 2019 年 6 月开始，Linux 代理不再需要在机器上运行守护进程（尽管它仍使用审计框架）。如果目标机器已经运行了审计守护进程，代理将尊重这一点，并与审计守护进程交互以收集数据。

## 了解 Azure Security Center

在 Windows 系统中，Microsoft 监控代理会在 Windows 事件跟踪 (ETW) 跟踪程序中扫描各种安全相关的配置和事件。此外，该代理还会收集以下内容：

- 操作系统日志（例如 Windows 事件）
- 操作系统类型和版本
- 运行中的进程
- 计算机名称
- IP 地址
- 登录用户（用户名）
- 租户 ID
- Windows 错误报告 (WER) 创建的用户模式转储储

> 注意：在本章的稍后部分，你将学习如何更改 Windows 系统数据收集的粒度级别。

这些信息会被发送到你的工作区，工作区是用于存储你数据的 Azure 资源。工作区提供了数据存储的地理位置、计费的粒度和数据隔离，并能帮助你更好地划分配置范围。

如果你正在使用 Azure Monitor，可能已经有了一个 Log Analytics 工作区。Security Center 可以使用该工作区来存储来自代理的数据。如果你没有使用 Log Analytics 工作区，当你开始使用 Security Center 时会自动创建一个新工作区。Security Center 创建的工作区基于 VM 的位置，如下：

- 对于位于美国、巴西和加拿大的 VM，工作区位于美国。
- 对于位于欧洲和英国的 VM，工作区位于欧洲。
- 对于位于亚太地区、日本和印度 VM，工作区位于亚太。
- 对于位于澳大利亚的 VM，工作区位于澳大利亚。

如果你是一家全球公司的一部分，并且由于数据主权或合性原因需要在特定区域存储数据，你可以考虑创建多个工作区。另一种可能需要多个工作区的场景是你想要隔离不同的用户。例如，你可能希望每个客户、部门或业务组只能看到自己的数据，而看不到其他组的数据。

> 提示：你需要使用 Log Analytics 创建多个工作区。如果你需要执行此操作，请阅读此文章：https://aka.ms/ascworkspaces。

图 2-2 显示了 Security Center 架构以及这些组件如何组合并通信。在例例中，非 Azure 机器和 Azure VM 将代理收集的数据发送到工作区。Security Center 使用这些数据进行高级威胁检测分析，并生成符合预防模块的建议，或发布属于检测模块的警报。Security Center 采用了高级安全分析方法——这种方法比传统的基于签名的方法强大得多。

一旦数据进入工作区，Security Center 将使用机器学习技术评估跨云织架构的所有相关事件。通过这种方法，Security Center 可以检测到手动方法无法识别的威胁。Security Center 使用以下类型的分析：

- **集成威胁情报**：这利用了微软针对已知恶意攻击者的全球威胁情报。（你将在第 9 章“与其他 Microsoft 解决方案的集成”中学习更多相关内容。）
- **行为分析**：这会寻找已知的模式和恶意行为，例如以可疑方式执行的进程、隐藏的恶意软件、利用尝试或恶意 PowerShell 脚本的执行。
- **异常检测**：这使用统计分析来构建历史基准，并根据偏离基准的情况触发警报。例如，一个 VM 通常每天接收 5 次远程桌面连接，但突然收到了 100 次连接尝试。这种偏差将触发警报。

> 提示：要了解更多关于 Security Center 检测能力和其他相关场景，请访问 https://aka.ms/ascdetections。

# Security Center 仪表板

访问 Security Center 仪表板，请登录 Azure Portal (https://portal.azure.com) 并点击左侧窗格中的 **Security Center**。首次打开 Security Center 仪表板时发生的情况取决于你拥有的资源。出于本例的目的，仪表板已完全填充资源、建议和警报，如图 2-4 所示。

![](img/4b11e95292819ab1a383a41ef73aedb4_45_0.png)

**图 2-4** Security Center 仪表板

如图 2-4 所示，Security Center 概述仪表板三个三个区域：策略与合规（Policy & Compliance）、资源安全与卫生（Resource Security & Hygiene）以及威胁防护（Threat Protection）。此处显示的数据来自你自己的工作区。

在左侧导航窗中，你有以下区域：

- **常规 (General)**：在此区域，你将找到可以在日常活动使用的选项；这里还有接入非 Azure 机器以及搜索警报或事件的选项。
- **策略与合规 (Policy & Compliance)**：此处的选项用于管理安全策略、显示安全评分并可视化合规性报告。
- **资源安全卫生 (Resource Security Hygiene)**：此处显示的选项用于增强你的安全态。在这里，你能够查看资源的安全评估、连接安全解决方案并监控身份访问活动。
- **高级云防护 (Advanced Cloud Defense)**：此处的选项用于进一步保护你的 VM、白名单应用程序并跟踪 VM 的更改。
- **威胁防护 (Threat Protection)**：此区域的选项用于事件响应以及对与环境相关的安全问题进行进一步调查。
- **自动化与编排 (Automation & Orchestration)**：在这里，你将利用 Azure Logic Apps 创建针对安全警报运行的工作流。

在本书中，将涵盖所有这些选项。现在，你只需浏览这些选项以熟悉界面。

# 规划采用

尽管 Security Center 是一项云服务——这意味着你并不真的需要在本地部署任何服务器——但在采用方面仍有一些你应该考虑的方面。关键领域之一是确定谁有权访问 Security Center。根据你组织的规模和结构，多个个人和团队可能使用 Security Center 执行不同的安全任务。

# 角色与权限

Security Center 使用基于 Azure 的角色的访问控制 (RBAC)。默认情况下，Security Center 有两个角色：安全读取者（Security Reader）和安全管理员（Security Admin）。安全读取者角色应分配给所有需要仪表板权限的用户。例如，安全读取者角色应分配给需要监控和响应安全警报的安全运营人员。需要注意的是，该角色的分配是在 Azure 级别进行的，位于 Security Center 监控的资源组下，并使用**访问控制 (IAM)**，如图 2-5 所示。（IAM 代表身份和访问管理。）
