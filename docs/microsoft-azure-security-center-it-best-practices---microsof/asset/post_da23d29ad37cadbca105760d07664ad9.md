
# Appendix A

## Managing Security Center at scale

BY TIANDER TURPLIN, SENIOR PROGRAM MANAGER, CxE SECURITY

In this fast-evolving world where threats are equally fast evolving, any security solution must be able to support a Continuous Integration/Continuous Deployment (CI/CD) pipeline with a management-at-scale vision. Microsoft Azure has three important cornerstones to support this: Azure Resource Manager (ARM) templates, Azure Policy, and Azure management groups. This appendix covers the main considerations regarding managing Security Center in scale.

## The importance of management at scale

Limiteless cloud speed and scale allows you to create as many subscriptions in Azure as you like. However, this introduces manageability and compliance challenges. How can you enforce and achieve compliance across your tenants—and potentially, across hundreds of subscriptions—in an efficient and automated way? Key concepts to achieve that are management groups, ARM Templates, and Azure Policy.

## The three templates

With ARM templates, you declare your deployment in the form of a JSON file, which contains the objects you want. It contains the type of resources, names, and properties. The JSON file can be checked into a source control solution, supports versioning, and enables you to deploy Azure “infrastructure as code.” The two deployment types, incremental and complete, enable you to only deploy what is declared in the template (complete) or to add/update additional resources (incremental). The complete deployment deletes all the resources that are not specified in the template. Therefore, incremental is the default deployment type. An ARM template is idempotent, meaning that either a resource will be created if it does not exist, or an existing resource will be updated. Idempotency allows you to repeatedly deploy the same template without breaking something. Upon deployment of an ARM template, the JSON file is consumed by the Azure Resource Manager API that has a contract with its Resource Providers. A Resource Provider (RP) is a trusted HTTPS RESTful API endpoint that can provision, delete, and manage services on a user's behalf. Azure Policy provides you with governance controls for your Azure environment. It can stop (deny) from creating non-compliant resources, and it can audit compliance (audit and auditIfNotExists). It can even remediate (deployIfNotExists) non-compliant resources, either upon creation or for existing resources. The Azure Policy definition example shown in Figure A-2 stops the creation of websites in Azure that are not HTTPS enabled.

```json
{
  "mode": "All",
  "policyRule": {
    "if": {
      "allOf": [
        {
          "field": "type",
          "equals": "Microsoft.Web/sites"
        },
        {
          "not": {
            "field": "Microsoft.Web/sites/httpsOnly",
            "equals": "true"
          }
        }
      ]
    },
    "then": {
      "effect": "deny",
      "details": {
        "type": "Microsoft.Web/sites",
        "existenceCondition": {
          "field": "Microsoft.Web/sites/httpsOnly",
          "equals": "true"
        }
      }
    }
  },
  "parameters": {}
}
```

When a collection of Azure Policy definitions is grouped, it is called an initiative. Both a definition and an initiative can be assigned to a scope, such as a Subscription or a management group, and it then becomes an Azure Policy assignment.

Azure management groups are the third cornerstone for supporting management at scale, and they provide a level of scope above subscriptions. ## Security Center and Azure Policy, better together

When a new Azure subscription is created and the subscription is registered with the Microsoft Security Resource Provider (RP), the default behavior is that a Security Center policy initiative is provisioned and assigned at the subscription level. The exception is that if the subscription resides in a Management Group that already has the Security Center initiative assigned, the Security Center initiative will not be assigned to any of the subscriptions within that management group. This approach has a couple of advantages:

- You define the governance conditions in a single place, either at the Root Management Group or at the lower management groups.
- You can assign deny policies at a high-level that cannot be overridden at a lower level.
- There is a clear view of your compliance state across your management groups and subscriptions.

## Scoping your deployment of ARM templates and Azure Policy

Every ARM template deployment and Azure Policy assignment is targeted at a scope, such as management groups, subscriptions, or resource groups. Because Security Center is a subscription-level resource, ARM templates and Azure Policy deployments and assignments must be targeted at the subscription level. ## Best practices for managing Security Center at scale

Research and define compliance conditions that apply to your organization, group them in Azure initiative, Inheritance ensures that these apply to lower management groups and subscriptions. Also, you should follow the general best practices:

- Tailor the Security Center initiative to your needs.
- Create custom Policy definitions according to your needs.
- Target exceptions at lower management groups, such as dev and test environments.
- Deploy and maintain Azure Policies and initiatives using Infrastructure as Code (IaC).
- Don't be tempted to “manually” configure ASC. Instead, you should leverage Azure Policy and ARM Templates where possible.
- Ask yourself if you can provision a new tenant or subscription with automation.
- First, test with auditIfNotExists Azure Policies using deny policies.
