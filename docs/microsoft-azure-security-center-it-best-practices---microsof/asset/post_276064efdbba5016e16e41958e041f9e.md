
# Security Center architecture

When you use Security Center to monitor resources in Azure—either on-premises or hosted by other cloud providers (such as Amazon AWS)—the architecture looks similar to Figure 2-1.

![](img/4b11e95292819ab1a383a41ef73aedb4_42_0.png)

Figure 2-1 Connectivity between Security Center agents and the Security Center service

Security Center uses the Microsoft Monitoring Agent, which is the same agent used by Operations Management Suite and the Log Analytics service. In Windows systems, Security Center installs the Microsoft Monitoring Agent (HealthService.exe). In Linux systems, Security Center creates the omsagent daemon, which runs under the account. This account is automatically created during agent installation.

In Linux systems, Security Center collects audit records from Linux machines by leveraging the audit framework. The audit framework consists of two major components, the first is a set of user-space utilities offering a wide collection of operations allowing administrators to better adjust rules, analyze audit logs, or troubleshoot if things are misconfigured. The second is a kernel-level subsystem that is responsible for monitoring system calls, filtering them by netlink socket, and writing match messages to a buffer. Audit records are collected, aggregated into events, and enriched with the latest version of the Microsoft Monitoring Agent for Linux. A subset of the audit events are stored in your workspace and managed by Security Center. When threats are detected, Security Center triggers an alert. Starting in June 2019, the Linux Agent no longer requires the audit daemon (although it still uses the audit framework) to be running on the machine. If the target machine already has the audit daemon running, the agent will respect that, and it will interact with the audit daemon to collect the data.

## Understanding Azure Security Center

In Windows systems, Microsoft Monitoring Agent scans for various security-related configurations and events in Event Tracing for Windows (ETW) traces. In addition, this agent collects the following:

- Operating system logs, such as Windows events
- Operating system type and version
- Running processes
- Computer name
- IP addresses
- Logged-in user (username)
- Tenant ID
- User-mode crash dump created by Windows Error Reporting (WER)

> NOTE Later in this chapter, you will learn how to change the level of granularity of the data collection for Windows systems.

This information is sent to your workspace, which is an Azure resource used as a container to store your data. A workspace provides a geographic location for data storage, granularity for billing, and data isolation, and it helps you to better scope the configuration.

If you are using Azure Monitor, chances you already have a Log Analytics workspace. This workspace can be used by Security Center to store data coming from the agent. If you are not using a Log Analytics workspace, a new workspace will be automatically created when you start using Security Center. The location of the workspace created by Security Center is based on the location of the VM, as follows:

- For VMs in the United States, Brazil, and Canada, the workspace location is the United States.
- For VMs in Europe and the United Kingdom, the workspace location is Europe.
- For VMs in the Asia-Pacific region, Japan, and India, the workspace location is Asia Pacific.
- For VMs in Australia, the workspace location is Australia.

If you are part of a global company and you need to store data in specific regions for data sovereignty or compliance reasons, you might consider creating multiple workspaces. Another scenario that might call for multiple workspaces is if you want to isolate various users. For example, you might want each customer, department, or business group to see its data but not data from the other groups.

> TIP You need to use Log Analytics to create multiple workspaces. If you need to perform this operation, read this article: https://aka.ms/ascworkspaces.

Once the data is in the workspace, Security Center uses machine-learning technologies to evaluate all relevant events across the cloud fabric. By this approach, Security Center can detect threats that would be impossible to identify using manual approaches. Security Center uses the following type of analytics:

- **Integrated threat intelligence:** This leverages global threat intelligence from Microsoft for known bad actors. (You will learn more about this in Chapter 9, "Integration with other Microsoft Solutions."
- **Behavioral analytics:** this looks for known patterns and malicious behaviors, such as a process executed in a suspicious manner, hidden malware, an exploitation attempt, or the execution of a malicious PowerShell script.
- **Anomaly detection:** this uses statistical profiling to build a historical baseline and triggers an alert based on deviations from this baseline. An example of this would be a VM that normally receives remote desktop connections five times a day but suddenly receives 100 connection attempts. This deviation would trigger an alert.

> TIP To read more about Security Center detection capabilities and other relevant scenarios, see https://aka.ms/ascdetections.

# Security Center dashboard

To access the Security Center dashboard, sign in to Azure Portal (https://portal.azure.com) and click **Security Center** in the left pane. What happens the first time you open the Security Center dashboard may vary based on the resources you have. For the purposes of this example, the dashboard is fully populated with resources, recommendations, and alerts, as shown in Figure 2-4.

![](img/4b11e95292819ab1a383a41ef73aedb4_45_0.png)

**FIGURE 2-4** Security Center dashboard

As you can see in Figure 2-4, the Security Center Overview dashboard has three major areas: Policy & Compliance, Resource Security & Hygiene, and Threat Protection. The data shown here is pulled from your own workspace.

In the left navigation pane, you have the following areas:

- **General**: In this area, you will find options that can be used in your daily activities; also, the options for onboarding non-Azure machines and searching for alerts or events are available here.
- **Policy & Compliance**: The options available here are used to manage your security policy, show your secure score, and visualize regulatory compliance reports.
- **Resource Security Hygiene**: The options shown here will be used to enhance your security posture. Here, you will be able to view the security assessment of your resources, connect with security solutions, and monitor your identity access activities.
- **Advanced Cloud Defense**: The options available here are to further protect your VMs, whitelist your applications, and track changes to your VMs.
- **Threat Protection**: The options available in this area will be used for incident response and further investigation on security issues that are relevant to your environment.
- **Automation & Orchestration**: Here, you will be able to leverage Azure Logic Apps to create workflows that you run against Security Alerts.

Throughout this book, all of these options will be covered. For now, you should just browse each of these options to familiarize yourself with the interface.

# Planning adoption

Although Security Center is a cloud service—which means you don't really need to deploy any server on-premises—there are still some aspects around the adoption that you should take in consideration. One of the critical areas is to determine who should have access to Security Center. Depending on the size and structure of your organization, multiple individuals and teams may use Security Center to perform different security-related tasks.

# Roles and permissions

Security Center uses Role-Based Access Control (RBAC) based in Azure. By default, there are two roles in Security Center: Security Reader and Security Admin. The Security Reader role should be assigned to all users who need read access to the dashboard. For example, the security Reader role should be assigned to security operations personnel who need to monitor and respond to security alerts. It is important to mention that the assignment of this role is done at the Azure level, under the resource group Security Center is monitoring and using the **Access Control (IAM)** as shown in Figure 2-5. (IAM stands for Identity and Access Management.)
