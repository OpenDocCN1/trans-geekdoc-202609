

危险的明显迹象是，在旧系统被新系统取代的过程中，项目问题丛生，并且很明显新系统无法达到预期。伦敦外交部（FCO）在1990年的经历提供了可能发生情况的一个例子。FCO 曾委托开发一套新的会计系统，在长达2年的转换项目中，该项目从一次危机挣扎到另一场危机。最终，FCO 被迫采用新系统，尽管它远未达到可接受的标准，因为旧系统崩溃且无法修复。

FCO 按照所有正确的原则规划了新系统的实施。投入使用前，使用虚拟会计信息对新系统进行测试。还将有一段并行运行期，在此期间旧系统仍作为备份，以防新系统失败。然而，新系统的问题如此可怕，以至于在允许的并行运行期间，员工试图通过将分录转入特殊的“转储账户”来弥补软件中已知的错误。转储账户的内容从未得到妥善梳理。最初尝试将新系统中的数字与旧系统得出的数字进行核对时，发现差异约为 4600 万英镑（UK Accounts [1991](#reference.xhtml#ref_r226)）。没有理由认为这笔钱已经消失，后来通过粗略的账目平衡最终得以实现。然而，在几个月的时间里，FCO 依赖的会计系统缺乏任何内部控制，完全无法审计。

项目混乱当然也可能源于从一开始就竭力排斥审计人员的关注。1993年，加州机动车管理局最终被迫取消一项升级其驾驶执照数据库的项目。在投入约 5000 万美元于该项目期间，采用了各种手段来掩盖项目的资金方式，并且不断提供关于正在进行工作的过于乐观的报告。Collins（[1997](#reference.xhtml#ref_r55): 228）指出：“如果有定期的独立核实或审计，欺骗测试行为本会被发现，因为审计人员应向首席执行官或其等同职位报告，而不是向计算机部门报告。”该案例很好地说明了需要由内部审计职能指导*所有*审计，并与组织负责人保持直接沟通渠道的必要性。

必须对项目的技术可行性“吹哨”的前景，使计算机审计员处于无疑感到非常不舒服的位置。这是对她忠诚度是否在于应用开发团队，还是整个组织的终极考验。然而，如果审计员不愿意采取此类行动，那么一开始设立审计角色就毫无意义。

在大多数项目最终取得某种成功的情况下，计算机审计员的目标将是：

* *验证设计中规定的预防性控制和反馈控制是否运行并有效*。这可能意味着在强调将软件更具生产力的功能“推向市场”时，坚持要求优先考虑这些控制。控制很容易被视为可选项或额外负担，如果时间资源紧张，可以留到以后再做。控制的测试也可能遭到抵制，因为其中一些控制（尤其是访问控制）只有在软件的所有要素整合在一起，接近发布就绪时才能完全测试。
* *确保所需的并发控制已到位*。并发控制使计算机审计员能够在软件日常使用中检查其中的流程。它们将在[第 12.3 节](#ch12.xhtml#ch12_sa3)中进一步讨论。
* *确保控制得到充分记录*。控制的目的、它们在软件中的构建位置以及预期使用方式不应存在任何神秘之处，所有这些都应在文档中进行说明。
* *检查是否已为变更管理做出安排*。不可避免地，软件投入生产后会进行修改和升级。其中一些变更将涉及安全问题。变更管理系统应确保在考虑此类变更时，计算机审计员会收到通知。

## 11.5 问题

1. 计算机审计员是否应积极参与软件开发项目？探讨计算机审计员参与系统开发生命周期不同阶段的利弊。
2. 描述计算机审计员在评估和实施控制时可能面临的一些困难：
    1. 在为专业市场服务的软件包中，以及
    2. 在由工资部门的行政助理编写的 JAVA 程序中。
3. 你负责一个内部审计部门，正在尝试任命一名计算机审计角色。你可能对以下每种可能性会预见到什么缺点？
    1. 一家营销安全软件的公司提出让你免费使用一名“审计顾问”一个月。
    2. 任命一名来自 IT 服务部的系统程序员，他自 30 年前安装第一台大型机以来一直从事这份工作。
    3. 任命一名 25 岁的自称“专业资格”的计算机审计员。他在一家使用与你公司完全不同的计算机系统的公司担任计算机审计员已有 3 年经验。
4. 你是一名初级经理，刚刚获得使用雇主开发的全新人力资源应用的权限。当你登录新系统时，你惊讶地发现你可以浏览最高级经理以及公司其他各部门员工的个人档案。可能出现这种疏漏的原因是什么？在哪些情况下你会认为计算机审计员负有过错？

## 12.1 引言

1973 年，美国 Equity Funding Corporation 发生了一起大规模欺诈案被曝光。该公司严重依赖计算机的使用，计算机被用来大规模虚构保险客户。某一阶段，甚至编写了一个程序来创建数千条不存在的保险单记录，总价值达 4.3 亿美元。公司许多员工积极参与了欺诈。该案例生动地说明了计算机在完全缺乏有效内部控制的情况下，能够迅速生成大量看似真实的数据的强大能力。
