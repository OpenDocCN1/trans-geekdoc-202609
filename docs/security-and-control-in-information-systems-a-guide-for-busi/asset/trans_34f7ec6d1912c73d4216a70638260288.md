## 9.4.2 磁盘：镜像和影子

个人电脑通常依赖于单个容量为数 GB 的磁盘驱动器。较大的系统使用多个驱动器，并非全部相同；例如，正在归档的数据可能会写入较慢且更便宜的设备，例如 WORM（“一次写入，多次读取”光驱）。

只有对经常需要的数据才可能考虑对组件故障的保护。有三种不同的方法可以实现这一点，如 [Figure 9.3](#ch9.xhtml#fig9_3) 所示。这显示了一个相当简化的图示，其中处理器可以将数据存储在三个磁盘中的任何一个上。有两个文件 A 和 B，每个文件都假设，为了简单起见，只包含两条记录。

![Figure 9.3 ](images/fig9_3_B.jpg)

[Figure 9.3 ](#ch9.xhtml#R_fig9_3)

复制文件 A 的最简单方法是将它完整写入同一单元（图示顶部的单元 1）中的 *both* 磁盘。或者，可以将副本发送到完全不同的磁盘单元（单元 2），它可能位于完全不同的位置。第一个选项更容易、更便宜地实现，但第二个选项中使用单独的单元使该安排更具弹性。创建副本，尤其是在远程站点保存副本，被称为 *mirroring* 或 *shadowing*。

第三种可能性使用文件 B 显示。同样，该文件只有两条记录，但这次记录被拆分到两个驱动器上。这被称为 *striping* 数据。将条带化应用于仅两条记录意义不大，但它是 RAID 存储系统的基本特征，其中 RAID 代表 Redundant Array of Independent (or Inexpensive) Disks。RAID 系统包含大量磁盘驱动器，数据被条带化到所有驱动器中（不一定是单个记录，而是 RAID 单元控制系统选择的任何方式）。RAID 供应商已经设计出管理数据的高级方法，以帮助确保即使单个驱动器发生故障也能访问。

RAID 不仅因其弹性而变得流行，而且因为它可以为写入和检索记录提供极好的响应时间。供应商开发了各种各样的系统，其中许多系统结合了 *both* 条带化和影子复制的优点（Brackenridge [1993](#reference.xhtml#ref_r40)）。因此，可以获得两全其美的效果——性能和弹性，尽管通常价格较高。用户应记住，在严重灾难发生时，单个磁盘的内容在很大程度上毫无意义，并且数据只能在专有 RAID 软件的帮助下以及它维护的表的情况下重新拼凑。

## 9.5 创建和实施灾难恢复计划

Schweitzer（[1996](#reference.xhtml#ref_r206)：112）引用了一位信息系统经理的说法，他在一次现场检查中被要求提供灾难恢复计划的副本。他回应说：“我们没有应急计划 *because we have never had a disaster*。”这或许概括了许多管理者的私下看法。为什么要费心和花钱制定 DRP？过去从未需要过它，而且将来永远不需要的可能性很大。

有一小部分，并且在减少的组织不需要 DRP；这种稀有品种的成员很少使用信息系统，并且工作在长期的销售和生产周期中。所有组织都应至少审查是否需要 DRP。一旦计划的理由成立，高级管理层必须通过提供开发计划所需的工作资源，并批准对计划所涵盖服务的定义作为组织生存的绝对必需品，采取初步步骤。

如果部分或全部 IT 系统外包，恢复程序必须由外包协议涵盖。即便如此，从灾难中恢复的实际过程将需要 *both* 方的合作，并且 DRP 应该说明哪些责任属于组织，哪些属于外包商。

DRP 需要包含 [Figure 9.4](#ch9.xhtml#fig9_4) 中显示的六个关键要素。前两个条目被下划线标出，因为它们指的是资产，一旦丢失，可能无法替代。清单上的其他一切都可以从其他地方购买、乞求或借用。组织会发现自己无法在公开市场上购买（事实上也不愿购买）的是上个月的销售明细，以及员工的经验和专业知识。

![Figure 9.4 ](images/fig9_4_B.jpg)

[Figure 9.4 ](#ch9.xhtml#R_fig9_4)

DRP 是行动计划，因此应集中于实际问题，例如人们如何联系、他们应该做什么、他们将在哪里找到东西。在紧急情况的高峰期，员工不会对阅读政策的细微差别感兴趣。结构应以向新车或计算机所有者发布的指南的最佳示例为模型，提供所有必要的参考资料并有良好的索引，并以简单的方式解释应遵循的程序。

计划的副本应分发给所有可能在实施中发挥重要作用的人。应鼓励员工将副本带回家，以便即使办公室无法进入也能获得。这意味着维护一份流通清单和对任何更新的系统分发；否则，人们会试图实施计划的不同版本，从而导致混乱。

一些措施需要在持续的基础上实施。例如，必须定期进行备份，并且需要测试备用设施。

让我们依次考虑计划的每个要素。

1. *People*。有充分的理由坚持制定计划的人 *not* 是在计划实施时负责的人。首先，计划的作者应假设有必要详细说明员工的所有角色和职责，包括将负责恢复操作的人的职责。这确保了计划中没有任何内容依赖于仅作者知道的信息，从而避免了可能在关键时刻出现的问题，如果作者离开公司或休假。第二，很可能如果灾难威胁到企业的整个未来，首席执行官希望直接控制。

同样，计划中定义的程序不应假设指定个人可用。实际上，他们可能无法联系，或可能因灾难的影响而受伤甚至死亡。这并不意味着计划中应避免使用姓名——事实上，姓名和家庭电话号码将是其中的重要部分；但是，在可能的情况下，应确定替补和副手。

2. *Data and software*。应假设灾难会摧毁组织场所内保存的所有数据和软件副本。这引发了关于备份副本应保存在何处以及如何保持最新等众多问题。
