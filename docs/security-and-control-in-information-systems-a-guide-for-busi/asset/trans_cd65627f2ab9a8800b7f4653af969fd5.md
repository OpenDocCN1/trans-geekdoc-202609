
在另一极端，则是“自己动手”的编程工具，可用于在 PC 上创建简单的应用程序，例如 Visual Basic 和 Java。文字处理软件和电子表格等软件包中也内置了许多“定制”选项。这种大杂烩式的活动有时被归类为*最终用户*计算。对于因中央编程服务延误而感到沮丧、并希望组建一些简单的定制功能的部门来说，这种选择可能极具诱惑力。如果在敏感领域采用最终用户方法，风险会特别高，例如为个人信息数据库添加前端设施，或建立公众可访问的网站。除非采取措施控制局面，否则企业将完全暴露在对热心业余爱好者编写的程序的依赖风险中。计算机审计师控制这些开发的能力将微乎其微，因为在大多数情况下，她将对这些开发一无所知，处于一种幸福的无知状态。

在两个极端之间还有许多其他选择，其中大多数引发的控制问题同样棘手。软件包可能包含一些标准模块，以及一些可“裁剪”以满足客户需求的模块。现有软件的增补或扩展可能委托给外部编程承包商（他们可能在完全不同的地点远程办公，甚至可能在另一个大陆），或委托给实习学生。互联网站点和杂志赠送的 CD-ROM 上也流通着无数代码片段，声称能提供有用的业务功能。过去可以通过中央编程部门自然强制执行的许多严谨性几乎已荡然无存。计算机审计师现在必须制定策略，确保所有信息系统开发——即使那些乍看之下后果微不足道的开发——都纳入其管辖范围。

计算机审计师可能面临的其他问题包括以下几点：

1. *需求蔓延*。当委托软件开发的人开始改变主意，对软件功能提出新要求时，就会发生这种情况。这是内部软件开发中的常见问题，但在这种情况下，后果虽昂贵，却可通过修订软件规格说明来解决。试图修改现成软件包的成本可能更高，而且会破坏最初用于证明采购软件包合理性的大多数优势。一个例子是命运多舛的 TAURUS 项目，该项目始于 1988 年，旨在实现伦敦证券交易所的计算机化。项目团队决定以 Vista Corporation 的一个软件包为基础，但随后意识到需要进行大量更改，以使其适应英国而非美国的交易惯例。Drummond（[1996](#reference.xhtml#ref_r70): 102）对此描述道：

> 修改工作成了一个问题。Vista Corporation 不是一家软件公司，而是一家拥有一款成品软件的企业。他们习惯只做微小修改，根本无力承担证券交易所现在要求的大规模重写工作。

从完整性和安全性的角度来看，对软件包的修改导致了一个无解的局面。如果供应商在一个小众市场运营，不太可能拥有进行重大更改的资源（如 Vista 的情况）。如果产品服务于一个大得多的市场（例如小企业会计或 EDI 消息传递），其售价将因规模经济而大幅降低，且错误和故障本应已被早期用户暴露出来。即使供应商愿意提供修改，现在的收费标准也将是通常与定制系统相关的较高费率，且极有可能引入新的错误。

2. *认证标志与标准*。供应商可能会引用各种标准，以证明其产品的质量或安全性。一个例子是与数据安全相关的 ISO 7498 系列标准。（其中一些标准的详情见[第 14 章](#ch14.xhtml)）。在依赖这些标准之前，应铭记两点考量。首先，某些标准可能并不特别相关。例如，根据“橙皮书”（见[第 14.3 节](#ch14.xhtml#ch14_sa3)）的规定，许多类型的安全特性可按从 A1（优秀）到 C2（最低）的等级评级。然而，这些评级主要与集中式系统中的保密性保护相关。例如，它们无法保证系统能抵御病毒攻击、检查消息是否被篡改，或执行商业环境中可能需要的其他功能。其次，评级只能反映产品的*潜在*能力。如果安全特性未能以称职的方式实际实施，产品拥有的任何质量评级将迅速变得无关紧要。

3. *安全管理功能*。安装后，安全管理员将需要不时更新用户授权，计算机审计师将希望查阅审计踪迹信息。如果与系统的交互笨拙，或文档晦涩难懂，这些功能的使用将受到阻碍。这也可能表明整体设计存在弱点。对于软件包，至少应能在实际运行的系统上看到相关功能的演示，并询问其他用户站点是否遇到过问题。对于最终用户计算，作者不太可能在编程工作中充分考虑安全或审计影响，其工作甚至可能破坏原有的控制措施。

4. *与现有软件的集成*。这将关乎安装软件的人员，但也对内部控制有影响。软件包将有自己的约定，涉及最大允许密码长度、非活动用户超时、增量备份等特性。最终用户程序可能没有此类约定，或依赖标准产品的约定。如果用户习惯了高度集成，例如系统提供单点登录或统一的备份方法，这将是一个特别的问题。

### 11.4 系统测试与实施审计

有大量记录在案的 IT 项目彻底“脱轨”的案例，且关于导致此类项目失控因素的文献也日益增多（Beynon-Davies [1995](#reference.xhtml#ref_r30)，Drummond [1996](#reference.xhtml#ref_r70)，Keil [1995](#reference.xhtml#ref_r139)，Margetts 和 Willcocks [1993](#reference.xhtml#ref_r159)）。如果项目严重偏离轨道以至于被取消（这种情况有时会发生），后果可能严重影响组织的财务状况及其高级管理层的信誉。然而，如果旧系统在灾难期间持续运行，则不一定会有任何安全风险暴露。
