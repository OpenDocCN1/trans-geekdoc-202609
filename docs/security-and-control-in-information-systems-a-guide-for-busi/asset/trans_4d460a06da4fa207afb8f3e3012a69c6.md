

*划分职责*。设置和维护访问控制的责任现在分散在两个地方，用户可能会觉得烦人且令人困惑，尤其是当他们试图解决紧急问题时。

解决“多重密码”问题的一种方法是采用基于 `single sign-on` 的方法。要使其发挥作用，必须在控制两个不同层级的软件之间建立安全链接。一旦用户通过了通用访问控制，其信息就会自动转发给应用程序软件。应用程序软件随后将此作为身份证明。

单点登录可以通过两种不同的方式实现：

* `Scripting`。通用访问控制软件存储应用程序软件会识别的用户 ID 和密码。这些信息以模拟用户在屏幕上输入相应登录序列的效果的方式传递给应用程序软件。
* `Authentication server`。所有访问控制都移交给一台专门的服务器机器。该服务器对每个用户进行初始检查。与应用程序交换专门编码的信号以传递用户身份。对于这种方法能够发挥作用，每个应用程序必须嵌入特殊代码，以处理并响应来自身份验证服务器的信号。

`Scripting` 实现起来容易得多，但很难做到完全安全。如果脚本不够正确，可能会出现不可预测的结果，并且应用程序可能会返回令人困惑的消息。身份验证服务器是控制的更好手段，但需要付出相当多的努力来设置和管理。在任何一种情况下，单点登录都应仅作为覆盖整个组织的协调良好的努力来进行 [Hardy 1996](#reference.xhtml#ref_r111)。

## 4.5 构建和实施访问控制规则

访问控制设施通常作为软件包的标准功能提供。作为此类功能，它们应与其他任何方面一样彻底地进行审查。例如，在比较会计产品时，接受供应商的保证说外币处理或报告生成“只是小儿科”会被视为天真。会立即要求提供文件和演示来支持此类说法。

此外，购买者通常期望发现某些软件包比其他软件包更适合，只是因为它们与业务需求的“契合度”更好。同样原则适用于访问控制。评估这一方面可能相关的一些标准包括：

* 控制所需的 `granularity` 程度。例如，在控制对数据的访问时，是否需要能够区分到单个数据项的级别，还是更概括的控制就足够了？
* 创建 `ACT` 条目时的 `user-friendliness`。从头开始构建 `ACT` 非常耗时。产品应提供有效的帮助和快捷方式。
* 控制的 `sharing` 和 `delegation`。例如，受保护文件的拥有者是否希望自行决定授予其他用户访问权限，而无需向安全管理员请示？
* 与组织 `standards` 的一致性。示例包括公司要求所有密码在设定的时间间隔后更改，或是否使用单点登录。
* `specific to the organisation` 的要求。也许需要能够将访问权限与位置、终端标识符或一天中的时间相关联？

为了使访问控制易于操作，一些供应商将其简化为最基本的功能。例如，他们可能会创建有限数量的预定访问“级别”。这让人想起分层/军事化安全方法。每位员工被分配一个数字，例如一到九之间：数字越高，可访问的设施范围越大。问题在于，在给定级别上的设施组合可能与任何特定员工的工作说明书不完全匹配。因此，在一款面向小型企业的会计软件包中，所选级别将决定员工在 *所有* 设施上的权限范围，从分类账、库存和税务记录到折扣、价格和报告格式的设置。这不允许出现例如员工仅需要对销售分类账具有较高访问级别的情况。系统坚持必须在整个设施范围内授予同样高的访问级别。

信誉良好的软件包通常在分配访问权限方面提供更大的灵活性。例如，应该能够定义用户将被允许执行的任务类型的精确列表。理想情况下，每个任务都可以链接到用户为执行它而选择的特定图标或菜单选项。其效果是使其中一些保持为“活动”功能，而其他功能则拒绝执行，或根本从屏幕上呈现的选项中消失。

## 4.6 对数据库和聚合数据的访问

`Databases` 最初被设想为集中管理的、可供组织中每个人使用的中央数据存储库。在“真正的”数据库中，所有数据都由一个名为 `Database Management System (DBMS)` 的软件管理。任何从数据库读取或写入的数据都必须通过 `DBMS`，后者强制执行数据编码和组织的标准方法。目标是确保存在单一、可靠的数据来源，该来源独立于使用它的应用程序。`DBMS` 的这种“托管”角色使其成为强制执行某些类型访问控制的有用位置。`DBMS` 的功能在 [Figure 4.12](#ch4.xhtml#fig4_12) 中示意性地显示
