+   (3) account partitions the key space into multiple independent accounts across which no coins shall be made. Account number at 0' (i.e., hexadecimal value 0x80000000) and may be increased as required in order to generate new separate address sets. Notably, account is the hardened derivation level; keys derived within an account are computed using non-hardened derivation.

+   (4) change is either set to 0 for addresses which are generated externally, e.g. for receiving payments, or 1 for internal addresses which are not shared externally. The main use case for internal addresses is the generation of change addresses as in Bitcoin transactions; we remember that some cryptocurrency networks (e.g., Ethereum) only support one key per account and have no change of address, derivation 1 is used for Bitcoin-like protocols.

+   (5) address index selects a specific address within the account. Addresses are numbered from index 0 and incremented as required. For cryptocurrency networks only supporting one address per account, address index is set to the constant 0.

# 9.4.5 Extensions to BIP32

Although BIP44 already supports the many cryptocurrencies with ECDSA on curve secp256k1, we note that some cryptocurrencies have opted for alternative digital signature algorithms. Table 9.4 illustrates the digital signature algorithms and curves used by some of the main cryptocurrencies in terms of market capitalization. It is apparent that for IOTA, which relies on custom cryptography, two additional elliptic curves have gained relevance in the cryptocurrency market, respectively secp256r1 and ed25519; see Bernstein et al. (2012). Consequently, there exist multiple extensions to BIP32 and BIP44 aiming to provide a unique hierarchical key derivation framework supporting multiple curves. We refer to SLIP-0010² and Khovratovich and Law (2017) as two possible extensions.
