
With these requirements and restrictions defined, the security consultant recommends that the user management repository role be limited to only those system privileges required to manage users. Grantees of this role should not have the ability to assign roles to user accounts. Allowing them to assign roles would grant the ability to both manipulate a user and assign privileges to the user. This level of access gives the grantee the ability to impersonate a user account, allowing it to perform fraudulent or malicious actions within the system. To achieve the listed requirements, the user management repository role only requires the `USER ADMIN` system privilege.

In addition to only granting the `USER ADMIN` system privilege, the following conditions must also exist for the user accounts within this repository role:

*   The user account must not have the `ROLE ADMIN` system privilege, which grants the ability to create standard roles and to grant them to other users.

*   The user account must not have `EXECUTE` access to the `_SYS_REPO.GRANT_ACTIVATED_ROLE` stored procedure or other stored procedures in the `_SYS_REPO` schema that are used to manage security. Granting such access to these procedures will allow repository roles to be granted or other privileges to be assigned.

*   The user account must not have been granted any other privileges using the `WITH ADMIN OPTION` or `WITH GRANT OPTION`. This rule prevents the user from granting any individual privileges to other user accounts directly. Note that a user will be able to grant others access to its own schema in SAP HANA 1.0. Starting with SAP HANA 2.0, users can be restricted from their own user schema and subsequently prevented from granting privileges to their own schema.

*   The grantee must be granted the `sap.hana.ide.roles::SecurityAdmin` role to use web-based GUIs for managing users.

*   To prevent access to the auditing mechanism, the `AUDIT ADMIN` and `AUDIT OPERATOR` system privileges must not be granted to the user.

When implemented according to these requirements, the grantee will not be able to elevate his own privileges or the privileges of another user account. In addition, because the grantee doesn’t have access to manipulate the auditing mechanisms, he won’t be able to cover his tracks. All actions he performs on a user account should be captured by the auditing mechanism. Now, let’s look at how the role management role should be structured and why.

## 7.4.2 Role Management Role

The second repository role recommended by the security consultant grants the necessary privileges to provision roles and grant roles to users. Grantees of this role will be responsible for the following tasks:

*   Creating repository-based roles and assigning all privileges

*   Creating standard roles when necessary

*   Mapping LDAP groups to roles

*   Managing structured privileges other than analytic privileges

*   Creating analytic privileges and assigning restrictions

*   Granting roles to and revoking roles from users

Grantees assigned this role shouldn’t be able to create or manipulate user accounts. This rule prevents these grantees from impersonating a user account, subsequently allowing them to perform fraudulent or malicious actions within the system while concealing their identity.

To ensure that best practices are followed and that the separation of duties is implemented properly, the following list contains tasks that the grantees should not be able to perform:

*   Creating user accounts or changing user account passwords

*   Granting individual privileges to users

*   Managing system auditing

To achieve the listed requirements, the role management repository role requires the following system privileges: `ROLE ADMIN`, `LDAP ADMIN`, and `STRUCTUREDPRIVILEGE ADMIN`. In addition to granting these system privileges, the following conditions must also exist for the user accounts within this repository role:

*   The grantee must have package privileges for the package hierarchy node used to store the repository roles and analytic privileges. Grantees must be able to create, edit, and activate repository-based roles within this package.

*   The grantee must have the `REPO.READ` package privilege on package nodes they intend to grant to repository roles using a GUI. This privilege is only required to view them in the graphical list.

*   The grantee must have the `REPO.READ` package privilege on packages containing information views that will be configured within analytic privileges.

*   The grantee and `_SYS_REPO` must have `SELECT` access to any tables containing data-level security information, for example, tables that map user accounts to data attributes. These tables are used to define dynamic analytic privileges.

*   The grantee must have `EXECUTE` privileges for stored procedures in the `_SYS_REPO` schema the names of which begin with `GRANT_` and `REVOKE_`.

*   The grantee must have `EXECUTE` privileges for the `SYS.REPOSITORY_REST` stored procedure. This privilege is required to work in the SAP HANA package hierarchy or repository in which repository roles are created.

*   If standard roles are used in the security model, the grantee must have been granted the grantable privileges using the `WITH ADMIN OPTION` or `WITH GRANT OPTION`. This privilege isn’t necessary if repository roles are used. With repository roles, the system account `_SYS_REPO` must be granted the grantable privileges using the `WITH ADMIN OPTION` or `WITH GRANT OPTION`.

*   The grantee must be granted the `sap.hana.ide.roles::EditorDeveloper` and `sap.hana.ide.roles::SecurityAdmin` roles to use web-based GUIs when creating repository roles or managing roles.

*   To prevent access to the auditing mechanism, the `AUDIT ADMIN` and `AUDIT OPERATOR` system privileges must not be granted to the user.

When implemented according to these requirements, the grantee won’t be able to use another user account to perform fraudulent or malicious actions in the SAP HANA system. In addition, because the grantee doesn’t have access to manipulate the auditing mechanisms, he can’t cover his tracks. All actions he performs using his assigned account should be captured by the auditing mechanism.

## 7.4.3 Data and Communication Encryption Role

The third repository role recommended by the security consultant grants the necessary privileges to administer communication protocol, log volume, and data volume encryption. Grantees of this role will be responsible for the following tasks:

*   Changing the root key

*   Enabling persistent data volume encryption

*   Enabling transaction log volume encryption

*   Managing credentials used by remote sources

*   Managing keystores and certificate files on the SAP HANA operating system

*   Administering SSL certificates used for authentication and secure communications

Given that a high degree of operating system and administrative level access is required by this role, system administrators will need to be assigned this role, and individuals on the security team won’t perform the listed actions. A separation of duties in this case has more to do with the amount of access required to manage end-to-end encryption. For example, a user administering a role doesn’t require operating system-level access or SAP HANA INI file access to perform her functions. Therefore, she shouldn’t automatically obtain administrative functionality just because she’s a member of the security team.
