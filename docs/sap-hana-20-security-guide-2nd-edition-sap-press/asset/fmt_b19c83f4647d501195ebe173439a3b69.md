
The SAP HANA software appliance layer, which includes the SAP HANA in-memory database layer, also includes the SAP HANA extended application services, classic model (SAP HANA XS) engine (XS engine) to enable SAP HANA’s use as a development platform. Some features are embedded, such as the Predictive Analytics Library (PAL), the Business Function Library (BFL), planning engines, rules engines, and geospatial engines. SAP HANA supports the real-time replication of data using replication agents and data integration using SAP HANA smart data integration. SAP HANA also offers a more robust and sophisticated SAP HANA extended application services, advanced model (SAP HANA XSA) application server, which supports more complex coding languages and application process isolation. In total, these layers build upon each other to form the SAP HANA appliance. Because SAP HANA is a robust data and application platform, securing this data and application appliance can be a challenging endeavor.

## Hardware Layers and Features

Understanding SAP HANA’s hardware components is also fundamentally important for understanding what SAP HANA is and how it is secured. With SAP HANA, data is stored in dynamic random-access memory (DRAM), in Intel Optane DC persistent memory, and within the central processing unit (CPU) cache. As a result, SAP HANA software can deliver exceptional performance because data is stored close to the CPU. Traditional databases store and access data on disk drives that are architecturally further away from the CPU and, for a variety of technical reasons, slower in accessing data.

Each server is also configured with multiple CPU sockets, each with multiple CPU cores. Multiple CPU sockets and cores allow the software to process multiple requests concurrently. For example, when data is stored in a column store, the software can reduce the processing of each column of data into one or more parallel requests. Because multiple CPU cores are available, each request can be processed by one or more CPU cores in parallel. The net result is more data is processed at the same time for an individual query.

Because DRAM is volatile or erased when the server loses power, the data stored in DRAM must be backed up to nonvolatile storage layers both automatically and periodically. The SAP HANA appliance manages these periodic snapshots of memory to disk and persistent memory automatically. The SAP HANA in-memory database stores data in two primary persistent locations: First, a mirror image of the in-memory data is routinely synchronized and stored in the `/hana/data` file path. For systems with persistent memory, non-delta data storage can also be placed in a persistent memory pool and in the `/hana/data` path simultaneously. Second, all transactions are recorded within the redo logs. SAP HANA is compliant with the principles of atomicity, consistency, isolation, and durability (ACID). ACID compliance guarantees that each database transaction is reliable, even if the server loses power. SAP HANA’s redo logs facilitate ACID compliance, and redo logs are stored in the default `/hana/log` path. Security administrators must understand this process because these locations must also be encrypted.

The amount of RAM supported on a single SAP HANA appliance is finite, and organizations often need to store more data in-memory than is supported on a single host. To overcome this limitation, SAP HANA can be scaled out to run on multiple servers that act as a single instance, acting as a single appliance when scaled over multiple nodes while also serving as a single point of access for users. When distributed on multiple nodes, the core software engines are active on each node and are used to manage the distributed data in memory.

In a multinode or scale-out SAP HANA appliance, all nodes share a single logical persistent storage layer. As a result, the in-memory data of each node is written to the same shared persistent storage layer during regular in-memory data snapshots and backups. [Figure 2](#00_002.html#f0.2) shows the SAP HANA appliance running as a single instance distributed over multiple nodes.

Each SAP HANA node communicates over dedicated redundant network links. From a security standpoint, the communications between each SAP node must be secured. In addition, the data stored in the persistent layers might also need to be encrypted. Fortunately, because the SAP HANA scale-out cluster acts as a single instance, users, roles, and privileges are centrally managed for all server nodes.

### SAP HANA Hardware Selection

A variety of server hardware vendors provide certified, prebuilt systems for running SAP HANA. Each hardware vendor must undergo strenuous certification processes to ensure that its hardware platform meets or exceeds the standards set by SAP. A certified SAP HANA 2.0 appliance should only be run on the following CPU modes:

*   Haswell v3 Intel E7-8880 v3, E7-8890 v3, or E7-8880L v3

*   Broadwell v4 Intel E7-8880 v4, E7-8890 v4, or E7-8894 v4

*   Skylake SP Intel Xeon Platinum 8176, 8176M, 8180, or 8180M

*   Cascade Lake SP Intel Xeon Platinum 8276 or 8280

For a complete listing of certified servers by vendor, refer to the SAP Certified Appliance Hardware for SAP HANA Directory, available at [http://s-prs.co/v498226](http://s-prs.co/v498226).

In addition to using certified, prebuilt SAP HANA systems, you can design your own certified systems using the Tailored Datacenter Integration (TDI) program. This program allows you to use your own internal network infrastructure and storage infrastructure to build a fully supported SAP HANA system. However, you can only use servers or compute nodes listed in the SAP Certified Appliance Hardware for SAP HANA directory. For more information, refer to [http://www.saphana.com/docs/DOC-4380](http://www.saphana.com/docs/DOC-4380).

## SAP HANA Architecture

At a high level, [Figure 3](#00_002.html#f0.3) shows the basic service architecture of SAP HANA, including the standard connectivity or communications protocols. The SAP HANA system is comprised of several core services, such as the name server, the preprocessor server, the compile server, the script server, the index server, the XS engine, and the XSA engine. Each service provides one or more of the many features available within the SAP HANA platform. Interservice communications are secured automatically within SAP HANA. The index server is predominantly responsible for the core security model elements, such as users, roles, and privilege verification. The index server is also responsible for the core RDBMS catalog objects and their security. Both the XS engine and the XSA engine also have security that extends through to the index server.
