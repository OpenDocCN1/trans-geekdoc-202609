## Using .hdbgrants to Provide Access between HDI Containers

Establishing access between two containers can be accomplished by developers without little intervention by the security team. This process assumes that developers have access to the spaces or organizations where the HDI containers are stored. While convenient, this arrangement also violates most segregation of duties standards. Despite this lack of control, organizations often find creating multiple containers and then granting access between the containers necessary. To help you understand this process, let’s establish the names of two containers within an example SAP Web IDE for SAP HANA workspace. The name of the first HDI container will be `MyProj`, an example we’ve already used many times throughout this chapter. The name of the second example HDI container will be `EXAMPLE`. We’ll refer to `MyProj` as the primary HDI container and `EXAMPLE` as the target HDI container.

To begin the setup process, you’ll need to create two HDI container roles in the primary container `MyProj`. These roles should be set up exclusively to manage the universal connection between containers. The following list includes runtime names of the two roles that will be created in the `MyProj` project:

*   `MYPROJ_EXT_HDI_APP_ACCESS`
*   `MYPROJ_EXT_HDI_OO_ACCESS#`

In addition to the two roles, you’ll also need to create an `.hdbroleconfig` file that will map these two roles to a schema alias or schema reference. This step is required because you’ll grant external schema access to the target HDI container. Effectively, you’ll use the `MyProj` schema as a proxy to the external schema in the `.hdbroleconfig` file.

Within the project, you’ve created the folder structure `db • src • roles` and will be placing the role scripts in that folder. The design-time name of the first role will be `MYPROJ_EXT_HDI_APP_ACCESS.hdbrole`. Its runtime name will be `MyProj.db.roles::MYPROJ_EXT_HDI_APP_ACCESS`, and the role will be configured with JSON syntax shown in [Listing 18.10](#18_004.html#l18.10).

```
{ 
  "role":{ 
    "name":"MyProj.db.roles::MYPROJ_EXT_HDI_APP_ACCESS", 
      "object_privileges":[ 
      { 
       "name":"MyProj.db::CUSTOMERS", 
       "type":"TABLE", 
       "privileges":[ "SELECT" ]
      } ,
      { 
       "name":"MyProj.db::CS_CUSTOMERS", 
       "type":"TABLE", 
       "privileges":[ "SELECT" ]
      }
    ],
      "schema_privileges":[  
{  
    "reference":"REF_SYSTEM",
    "privileges":[ "SELECT" ]
},
{  
    "privileges":[ "SELECT" ]
}
  ],
 "schema_analytic_privileges":[
   {
     "privileges": ["MyProj.db.aps::AP_CUSTOMER"]
    }
          ]
    }
   }
```

### Listing 18.10 The MYPROJ_EXT_HDI_APP_ACCESS.hdbrole Script

The script shown in [Listing 18.10](#18_004.html#l18.10) will grant the following:

*   `SELECT` to the HDI table `"MyProj.db::CUSTOMERS"`
*   `SELECT` to the HDI synonym `"MyProj.db::CS_CUSTOMERS"` which actually points to the `SYSTEM.CUSTOMER` table.
*   `SELECT` to the schema reference `REF_SYSTEM` which actually points to the `SYSTEM` schema.
*   `SELECT` to the HDI container schema `MYPRJ_HDI_DB_1`
*   The HDI container analytic privilege `MyProj.db.aps::AP_CUSTOMER`

Note that, in the script found shown in [Listing 18.10](#18_004.html#l18.10), anything granted in the `"schema_privileges"` value array that does not include a `"reference"` value is assumed to be a grant on the HDI container schema `MYPRJ_HDI_DB_1`.
