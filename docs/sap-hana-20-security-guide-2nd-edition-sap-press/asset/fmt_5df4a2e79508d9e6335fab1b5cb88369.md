## 5.6 Summary

The process of creating and managing roles can be accomplished using SQL statements, the SAP HANA cockpit, or the SAP HANA Web-Based Development Workbench security manager hosted in the XS engine. You can also use all three interfaces to grant and revoke both privileges and roles with some limitations with the SAP HANA cockpit and repository-based roles. In the next chapter, we’ll will explore repository-based roles, which are an alternative to standard roles and which in most cases provide advantages over standard roles.

# 6 Repository Roles

In this chapter, we’ll provide a complete overview of repository roles, including the processes used to create, maintain, and grant privileges to repository roles.

Roles are objects that aid in the creation of a security model. The bulk of the security model development process involves defining roles, assigning privileges to roles, and assigning roles to user accounts. However, SAP HANA offers a unique type of role called a repository role, which we’ll explore throughout this chapter. We’ll start by defining repository roles and discussing their importance, then we’ll review the options for creating and managing repository roles. As with standard roles, we’ll also review the process for granting and revoking privileges and roles to repository roles. Because of the importance of repository roles, we’ll outline a basic example of the structure of a repository role. Finally, we’ll demonstrate the process for creating a basic security model with repository roles.

## 6.1 What Are Repository Roles?

In [Chapter 5](#05_001.html#h5), we discussed standard roles and the process used to create them. If you have experience creating roles in other relational database management systems (RDBMSs), creating standard SAP HANA roles will seem quite similar. During the process, you’ll issue statements to generate a runtime version of the role, meaning that the object only exists in an active state within the RDBMS. Once the standard role is created, that role is instantly available for use.

Once a role is created, you’ll issue a series of `GRANT` statements to assign privileges to the role. To remove privileges from the role, you’ll issue `REVOKE` statements. As each individual command is issued, the runtime version of the role is immediately updated. With this process, you won’t be able to easily roll back changes or promote changes seamlessly to upstream SAP HANA environments. For example, if you make a change in a development environment, you’ll need to make the same change in a test environment and possibly a production environment by issuing the same commands. This process historically has been cumbersome to manage, a problem that often required third-party software to remedy. Without software to help, the SQL scripts issued to create, alter, grant, or revoke roles would all need to be manually retained and executed sequentially in each upstream environment.

Repository-based roles can overcome many of the limitations attributed to standard database roles. Repository roles are defined and saved in the SAP HANA development repository or package hierarchy. These roles can be defined using an SAP HANA-specific script language or using the SAP HANA Web-Based Development Workbench editor. In either case, you can save a design-time version of the role within a development artifact, meaning that the role and its granted privileges can exist as a separate object, independent of the runtime version. Once the design-time version of the role is activated, a matching runtime version is created in the SAP HANA RDBMS. This feature of SAP HANA allows you to implement change management, rollback, and transportation of roles between environments.

In addition to these benefits, repository roles also help simplify the management of your SAP HANA security model. To illustrate these benefits, let’s first discuss the importance of the `_SYS_REPO` system account. We’ll then discuss how repository roles can help you avoid issues related to the grantor of privileges and roles. Finally, we’ll outline the overall benefits of using repository roles.

### 6.1.1 User Account `_SYS_REPO` and Repository Roles

As mentioned earlier, when you use the SAP HANA development repository to define repository-based objects and roles, the runtime versions of these objects will be owned or granted by the `_SYS_REPO` system account. You must understand the importance of this ownership arrangement, which has a profound impact on how you establish security models in SAP HANA.

Recall that catalog objects created using the SQL `CREATE` statement will be owned by the user issuing the statement. The owner therefore must grant privileges to other users or roles if those users/roles require access to the owner’s catalog objects. The owner must also grant privileges to security administrators if these administrators are expected to facilitate access to the owner’s objects. This step is required because of the how standard catalog security in RDBMSs operates in a multiple user account environment. By design, no single user is automatically granted privileges to objects owned by other users without some form of action by the owner or security administrator.

Although this methodology enhances security, a nearly unmanageable security model may result in practice. Object owners must work closely with security administrators and follow strict procedures to maintain a security model. Security administrators must rely on each other to revoke any roles they granted because only the grantor can revoke a granted role. This requirement, among other requirements, makes the security management of standard catalog roles and objects quite difficult without an external software system delegating, managing, controlling, and tracking the process.
