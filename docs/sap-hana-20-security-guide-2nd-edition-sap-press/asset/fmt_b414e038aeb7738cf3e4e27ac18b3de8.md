## 15.4 Querying Audit Data

You can query three main system views that are related to audit data and the auditing configuration within SAP HANA. These views are useful for a variety of purposes. The three views are `AUDIT_ACTIONS`, `AUDIT_LOG`, and `AUDIT_POLICIES` and are all located in the `SYS` schema.

###### Note

For more information on each of these views, refer to the SAP HANA SQL and System View Reference Guide, available at [http://s-prs.co/v498219](http://s-prs.co/v498219).

* `AUDIT_ACTIONS`

    The audit actions view provides access to a listing of all possible auditable actions within the SAP HANA system. This view provides a listing of audit actions and flags to indicate actions that require a user or catalog object reference. This view is useful when you need to see a listing of supported audit actions. To query the view, issue the following SQL statement:

    ```
    SELECT * FROM SYS.AUDIT_ACTIONS;
    ```

* `AUDIT_LOG`

    The audit log view provides access to all recorded actions based on enabled audit policies. When an audit policy is enabled, events are written to the hidden system table `_SYS_AUDIT.CS_AUDIT_LOG_`. The audit log view references this system table. Administrators can create a variety of audit-related queries referencing this system view, and the view contains several columns. To query the view, issue the following SQL statement:

    ```
    SELECT * FROM SYS.AUDIT_LOG;
    ```

* `AUDIT_POLICIES`

    The audit policies view provides a complete listing of all audit policies defined within the system. This view can be queried to determine the quantity and scope of audit policies defined within the SAP HANA system. Note that a single policy might have multiple records within the view; each record represents a unique configuration option. For example, if you reference multiple users in the policy, a record for each user will be represented in this view. To query the view, issue the following SQL statement:

    ```
    SELECT * FROM SYS.AUDIT_POLICIES;
    ```

The views listed in this section are useful when your organization needs to examine the data that is collected from auditing and the configuration of the auditing mechanism itself. ## 15.5 Case Study: Defining Audit Policies

E-Corporation recently enabled auditing within the SAP HANA landscape. Its internal audit group determined that capturing audit events for the purposes of regulatory compliance and best practices was necessary. E-Corporation contacted its SAP HANA security consultant and requested help reviewing and implementing proposed audit policies. Thus, E-Corporation listed its requirements followed by its consultant’s recommendations, which we’ll review in the following sections. The consultant will use SQL statements to define the exact policy recommended.

E-Corporation requires that the audit policy be configured to facilitate proactive event monitoring, audit reporting, authentication actions, unauthorized access, system change, security management, and super user events. Let’s look at each requirement in detail.

### 15.5.1 Proactive Event Monitoring

#### Requirements

E-Corporation requires that the SAP HANA audit system support external tools that can proactively mine the system’s audit logs. These tools will require Open Database Connectivity (ODBC) and Java Database Connectivity (JDBC) access to the audit log tables.

#### Solution

Audit policies should be configured to support events that can be proactively monitored. These events include, but are not limited to, failed logon events, unauthorized actions, excessive query access to the system, and other activities. In addition, events will need to be recorded to the internal SAP HANA database table to allow these events to be available via JDBC or ODBC connections and via SQL queries. Most monitoring tools support this type of access.

### 15.5.2 Audit Reporting

#### Requirements

E-Corporation requires that all audit log data be accessible using the ODBC and JDBC protocols.

#### Solution

Audit events must be recorded to the internal SAP HANA database table, which will allow these events to be available via JDBC or ODBC connections and via SQL queries. Most reporting tools support this type of access.

### 15.5.3 Authentication Auditing

#### Requirements

E-Corporation requires that all connection and disconnection attempts are recorded within the audit logs. However, E-Corporation doesn’t want to record authentication attempts made by internal system accounts.

#### Solution

The security consultant recommends that an audit policy be created to record these activities to table `AUDIT_LOG` within SAP HANA. An audit policy titled `USER CONNECT AND DISCONNECT` will be created to monitor all SUCCESSFUL connections and subsequent disconnection actions performed by standard users. Unsuccessful attempts won’t be recorded in this policy because they’ll be captured in a subsequent audit policy. The policy won’t record events for system-generated accounts.

The policy will be defined using the SQL code shown in [Listing 15.5](#15_005.html#l15.5).

```
CREATE AUDIT POLICY "USER CONNECT AND DISCONNECT" 
AUDITING SUCCESSFUL CONNECT, DISCONNECT SESSION 
EXCEPT FOR 
     _SYS_AFL,
     _SYS_DI,
     _SYS_DI_BI_CATALOG,
     _SYS_DI_CATALOG,
     _SYS_DI_CDS_CATALOG,
     _SYS_DI_SEARCH_CATALOG,
     _SYS_DI_SU,
     _SYS_DI_TO,
     _SYS_EPM,
     _SYS_ES,
     _SYS_REPO,
     _SYS_SQL_ANALYZER,
     _SYS_STATISTICS,
     _SYS_TASK,
     _SYS_WORKLOAD_REPLAY,
     _SYS_XB,
     SYS_XS_SBSS 
LEVEL INFO;
```

**Listing 15.5** SQL Code to Create Policy Named `USER CONNECT AND DISCONNECT`

To activate the policy, the following SQL statement must be executed:

```
ALTER AUDIT POLICY "USER CONNECT AND DISCONNECT" ENABLE;
```
