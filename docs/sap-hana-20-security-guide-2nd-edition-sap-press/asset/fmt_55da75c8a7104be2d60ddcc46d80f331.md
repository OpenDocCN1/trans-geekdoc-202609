
# SAP Logon Tickets

SAP logon tickets act as digital credentials for authenticating an SAP system user with supported external systems. In the case of SAP HANA, logon tickets can provide SSO from SAP applications to XS engine web-based applications. For example, a user could log on to a web-based application hosted on an SAP NetWeaver Application Server (SAP NetWeaver AS). Within that application is a proxy link to an XS engine-based web application. The SAP NetWeaver-based application is configured to generate a logon ticket and store this ticket in the user’s browser as a temporary session HTTP cookie. The XS engine application is configured to support logon tickets. When the proxy link is clicked, the SAP HANA system finds the cookie in the browser and uses it to authenticate with the XS engine application.

Before the SAP HANA system will trust the logon ticket, external SAP application server certificates must be imported into the SAP HANA trust store. Once this trust is established, each SAP HANA user must be configured to support this authentication mechanism. The assumption is that the user ID found in the cookie will match the ID of a user configured in the SAP HANA system. Unlike Kerberos and SAML, no options are available for explicitly defining the external identities of users with logon ticket authentication enabled.

## Additional Configuration Information

For additional configuration details, refer to the “Configure SSO with SAP Logon Tickets for SAP HANA XS Applications” section in the SAP HANA Administration Guide, available at [http://s-prs.co/v498213](http://s-prs.co/v498213).

The SAP HANA Security Guide also provides a few additional details about the configuration process. Look for the “Single Sign-On Using SAP Logon and Assertion Tickets” section: [http://s-prs.co/v498214](http://s-prs.co/v498214).

Each SAP HANA user account must be configured to support logon tickets. You can enable support for a user within the user management options in the SAP HANA cockpit or with SQL commands.

To enable logon tickets for a user in the SAP HANA cockpit, open the user management window. In the user management window, select the SAP Logon Ticket checkbox located just below the Kerberos configuration area, as shown in [Figure 12.11](#12_003.html#f12.11).

[![Enable Logon Ticket in the SAP HANA Cockpit](bilderklein/klein12_011.png)](img-f12.11.html)

**Figure 12.11** Enable Logon Ticket in the SAP HANA Cockpit

To perform the same operation using SQL, execute the following command in the SQL console, replacing the `<USER_NAME>` variable with an SAP HANA user:

```
ALTER USER <USER_NAME> ENABLE SAP LOGON TICKET;
```

# 12.3.5 SAP Assertion Tickets

SAP assertion tickets work like logon tickets, with a few exceptions. The main difference is that assertion tickets are transmitted in an HTTP header from one application server to the next. In the case of SAP HANA, SAP credentials are obtained from the HTTP header, not from a session cookie. These tickets are configured to work with only one specific target system and have a fixed lifetime of 2 minutes. Once used, an assertion ticket is deleted. Most experts would argue that assertion tickets are somewhat more secure than logon tickets because of these factors. Outside of these differences, the assertion ticket process is like the logon ticket process.

An SAP HANA user account must be configured to support assertion tickets. You can enable support for a user with the user management options in the SAP HANA cockpit or with SQL commands.

To enable assertion tickets for a user in the SAP HANA cockpit, open the user management window. In the user management window, select the SAP Assertion Ticket checkbox, as shown in [Figure 12.12](#12_003.html#f12.12).

[![Enable Assertion Ticket in the SAP HANA Cockpit](bilderklein/klein12_012.png)](img-f12.12.html)

**Figure 12.12** Enable Assertion Ticket in the SAP HANA Cockpit

To perform the same operation using SQL, execute the following command in the SQL console, replacing the `<USER_NAME>` variable with an SAP HANA user:

```
ALTER USER <USER_NAME> ENABLE SAP ASSERTION TICKET;
```

# 12.3.6 JWT Identity Providers

JSON Web Token (JWT), sometimes pronounced “jot,” is an open standard (RFC 7519) that outlines a means for communicating security information between two parties using JavaScript Object Notation (JSON) objects. SAP HANA uses this standard for the purpose of third-party SSO and authentication for the SAP HANA smart data access feature between two SAP HANA systems. Much like SAML, you must import a shared certificate within a PSE configured for the purpose JWT authentication.

When configuring the SAP HANA smart data access source, the SAP HANA system is registered as a JWT provider in the SAP HANA cockpit or via SQL commands. For the JWT provider, you’ll use the JWT claims setting to configure how the user will be identified. In most cases, you’ll use the ’user’ value in the JSON file that is transmitted. Certificates are shared between the two SAP HANA databases to protect and trust the exchange of credentials.

# 12.4 Case Study: Adding SAML Identity User Accounts

When originally implementing SAP HANA, E-Corporation created several hundred user accounts before deciding to implement SAML authentication. Now, the company needs a script that will update existing user accounts and add the appropriate SAML identities. In [Chapter 4](#04_001.html#h4), we discussed how E-Corporation imported user data from a file and used stored procedures to provision users. That procedure could create new users and add their SAML identities, but it couldn’t perform the same action on existing user accounts. To remedy this situation, E-Corporation has decided to create a new stored procedure that will add SAML identities to existing accounts. The procedure will only add SAML identities for users that are listed in the `Security.Tables::adusers` table that don’t already have SAML identities.

The company has the following additional requirements for the stored procedure and the process needed to update user accounts programmatically:

* User accounts will only be updated with a SAML identity if they have a record in table `Security.Tables::adusers`. This table is populated with user attributes obtained from an external system.
* The user account’s internal basic authentication password won’t be changed; users can continue to use internal basic authentication and SAML authentication for SSO.
* The user account’s internal basis authentication password lifetime will comply with the configured password policy at E-Corporation.

To create the repository-based stored procedure in SAP HANA Web-Based Development Workbench editor, right-click the `Security.Provisioning` package and choose New • HDB Procedure.

The New Stored Procedure window will appear. In the File Name\* field, enter “ADD\_SAML\_TO\_EXISTING\_USERS,” using uppercase letters. In the schema field, enter or choose `Security_tables`. Click Create to save the file and open the `ADD_SAML_TO_EXISTING_USERS.hdbtable` configuration file for editing. A blank template will appear and can be used as a guide when defining the procedure.

To define the `ADD_SAML_TO_EXISTING_USERS` repository-based stored procedure in SQL, use the syntax shown in [Listing 12.4](#12_004.html#l12.4). Activate the design-time script by pressing (Ctrl)+(S).
