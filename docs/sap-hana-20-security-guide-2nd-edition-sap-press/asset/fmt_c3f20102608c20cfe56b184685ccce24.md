
Most of the chapters in this book have spent a great deal of time discussing authorization, a process in which the SAP HANA system determines if a user is allowed to perform specific actions within the platform. To define allowable actions in SAP HANA, you’ll effectively grant privileges to a user to define the individual actions a user account is authorized to perform. However, for the authorization mechanism to work properly, the SAP HANA system must first properly identify each user. The process of identifying a user is called authentication. SAP HANA supports several different types of authentication mechanisms, including both internal basic authentication, Lightweight Directory Access Protocol (LDAP) authentication, and external authentication systems supporting single sign-on (SSO).

SAP HANA’s internal basic authentication systems work through password authentication, meaning that SAP HANA will challenge users to supply both their user name and password—or, user credentials—as a form of identification. Like most authentication systems, SAP HANA assumes that the account owner is the only individual with knowledge of these credentials and therefore can prove his identity. Once an account is verified through password authentication, SAP HANA will conduct authorization checks based on the user’s granted privileges or roles.

Starting with SAP HANA 2.0 SPS 03, SAP HANA also supports LDAP authentication. With LDAP authentication, SAP HANA will delegate the process of validating credentials to an external system. Most organizations support one or more LDAP-based directory and authentication system. The most common being Microsoft’s Active Directory.

SAP HANA can also leverage many external authentication systems to support SSO, which allows a user’s credentials to be challenged once by a master system and then passed to subsequent systems without the need to supply the credentials again. In the case of SAP HANA, you can configure the system to support the following external provider options: Kerberos, Security Assertion Markup Language (SAML), JSON Web Tokens (JWT), SAP logon tickets, SAP assertion tickets, and X.509 client certificates. By default, all user accounts support SAP HANA’s internal basic authentication mechanism. LDAP authentication is also supported, but SAP HANA will not allow an account to support both LDAP authentication and internal basic authentication at the same time. However, both internal and LDAP users can be configured to support one or more additional external authentication providers for the purposes of SSO.

When configuring a user account for external authentication, you must first activate the external provider and then specify mapping data. SAP HANA uses this mapping data to validate an SAP HANA user account’s external identity. Thus, a dedicated SAP HANA user account is required for every internal or external user of the system. For example, you can’t use SAML SSO authentication between SAP HANA and another system unless a user account exists in SAP HANA, with its SAML identity enabled and configured. Therefore, every authenticating user must be a provisioned user for all authentication scenarios.

To better understand the authentication providers supported by SAP HANA, this chapter will walk you through the internal basic authentication system and its configurable settings in detail. We’ll also discuss LDAP authentication and its setup. Finally, we’ll discuss the various external providers supported for SSO to the SAP HANA system.

## 12.1 SAP HANA Internal Authentication Mechanism

SAP HANA provides an internal basic authentication mechanism, in the form of an internal user account and password system. The internal password authentication mechanism must be secured in two ways: First, you’ll need to identify the methods you’ll use to transmit these passwords to the SAP HANA system and implement encryption to prevent others from intercepting these passwords. Second, you’ll need to establish policies related to a user’s password. The password should be sufficiently complex and changed periodically. Let’s look at how to use both encryption and password policies to protect the internal SAP HANA authentication mechanism.

### 12.1.1 Protecting SAP HANA Passwords with Encryption

When a client application communicates with SAP HANA and when password authentication is used to authenticate the user, you’ll often need to use encryption to prevent unauthorized individuals from intercepting the password. By default, many client applications don’t use encryption when communicating with SAP HANA. However, SAP HANA supports communication encryption with the Open Database Connectivity (ODBC), Java Database Connectivity (JDBC), and Hypertext Transfer Protocol (HTTP) protocols.

You can use ODBC, JDBC, HTTP, or HTTPS client connection protocols depending on your mode of connection. Tools like SAP HANA Studio will use JDBC to communicate user-provided authentication credentials to the SAP HANA system. Business intelligence tools often use ODBC and JDBC as well. Users accessing applications in the SAP HANA extended application services, classic mode (SAP HANA XS) engine (XS engine) will likely use HTTP or HTTPS to communicate authentication credentials to the SAP HANA system.

JDBC and ODBC client credentials can be transmitted in an encrypted format to help protect them from unauthorized access. Applications hosted in the XS engine can be accessed using the HTTPS protocol. The HTTP protocol isn’t encrypted; using HTTPS will provide the necessary encryption. In general, HTTP access shouldn’t be used for SSO or form-based authentication because HTTP isn’t secure. Form-based authentication, in which users enter their user name and password in a form, is used by web-based applications to collect credentials for authentication. Most XS engine applications support form-based authentication by default. Many external authentication systems also rely on the HTTP protocol when communicating SSO credentials. In all cases, SAP HANA should be configured to use HTTP with SSL or HTTPS for encrypted communications over the HTTP protocol. We’ll discuss how encryption is enabled and managed in [Chapter 13](#13_001.html#h13); for now, note that you need encryption in addition to strong password policies to properly protect SAP HANA’s internal authentication mechanism.

### 12.1.2 Configuring the Internal Authentication Password Policy

Password policy security settings within SAP HANA can be configured using a few different methods: First, you can issue `ALTER SYSTEM ALTER CONFIGURATION` SQL commands to update security settings stored in the SAP HANA INI configuration files. Second, you can use the SAP HANA cockpit’s database administration Manage System Configuration options to directly update the individual INI settings. Third, the SAP HANA cockpit also provides a graphical user interface (GUI) for authentication with password policy that provides easy access to security settings within SAP HANA. Fourth, you can use the SAP HANA cockpit’s manage user groups GUI to establish a unique policy for each custom user group. Finally, the SAP HANA Web-Based Development Workbench security manager provides an interface where you can manage legacy settings.
