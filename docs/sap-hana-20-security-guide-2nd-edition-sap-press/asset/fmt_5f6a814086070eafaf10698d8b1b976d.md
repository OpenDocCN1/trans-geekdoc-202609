
#### Remote Sources

Remote sources are a unique type of catalog object. They’re virtual tables that reference RDBMS tables through SAP HANA smart data access, a mechanism built into SAP HANA that supports data federation from a third-party or remote RDBMS. Using SAP HANA smart data access, you can treat a remote table as though it were a local table within the SAP HANA database catalog. When this table is queried within SAP HANA, the system will fetch the requested data from the remote table in real time. Because of its unique nature, special privileges are available within SAP HANA to accommodate interactions with remote sources and virtual tables. [Table 8.5](#08_001.html#t8.5) lists the available privileges by name and describes their behavior related to remote sources.

| Grantable Privileges for Remote Sources || Description of SQL Action |

| --- | --- |

| `CREATE VIRTUAL TABLE` || This privilege grants the ability to create a virtual table within an authorized schema. The user must also have the `CREATE ANY` privilege or own the schema in which the virtual table is placed. |

| --- | --- |

| `DROP` || This privilege grants the ability to delete or drop a virtual table from the system. |

| `CREATE VIRTUAL FUNCTION` || This privilege grants the ability to create a function. |

| `CREATE VIRTUAL PROCEDURE` || This privilege grants the ability to create a virtual procedure. |

| `PROCESS REMOTE SUBSCRIPTION EXCEPTION` || This privilege allows processing exceptions for a remote subscription. |

| `CREATE REMOTE SUBSCRIPTION` || This privilege allows for the creation of subscriptions for capturing changed data from a virtual source. |

| `ALTER` || This privilege allows for the modification of an existing remote source configuration. |

### 8.1.2    Security Considerations for Catalog Objects

Let’s take a moment to discuss a few critical security considerations when dealing with catalog objects. We discussed some of these items in [Chapter 2](#02_001.html#h2), but we feel that reiterating them in this chapter is important. When designing a security model, you’ll need to consider the Grantable to Others authorization, object ownership, schema-level privileges, object-level privileges, authorizations for catalog views, authorizations for stored procedures, authorizations for functions, and repository objects.

#### Grantable to Others Authorization

In addition to the SQL privileges outlined in the tables in [Section 8.1](#08_001.html#h8.1), you also must consider the authorizations required to grant privileges to other users. In most cases, a security administrator will need both a SQL privilege and the Grantable to Others authorization for that privilege to establish a security model. SAP HANA won’t allow just any user account to grant other users access to an object. If the user is the owner of the objects, he can grant rights to other users.

However, most security administrators aren’t the owners of all objects; each object has only one owner, and often, you’ll need multiple security administrators. Therefore, security administrators require both SQL access to an object and the ability to grant those same privileges to other users.

When you establish privileges for a user and a role using the SAP HANA cockpit, notice that to the right of each privilege are Yes and No indicators in a column labeled Grantable to Others. When the Yes option is selected, the grantee can grant the same privilege to a different grantee.

#### Object Ownership

Recall that the individual that creates an object is the owner of that object. She inherently has full control of the privileges for that catalog object. Depending on the setup of your security model, each time an object is created, you’ll probably need to grant privileges to other users and roles for that object. However, authorizing privileges at the schema level might simplify this requirement, which we’ll discuss in the next subsection.

Object ownership is also important in relation to the user account that creates the object. If a user account is used to create a catalog object, that user account should never be deleted because deleting the account also deletes any catalog objects and granted privileges established by that user account. Thus, special technical accounts are often created for users that create catalog objects and manage security. Hopefully, an established policy ensures that technical user accounts are never deleted. As we’ll discuss shortly, alternatively, you can create most objects as repository objects. These objects are owned by the `_SYS_REPO` system account and won’t be deleted when a developer’s account is deleted.

#### Authorizations at the Schema Level

When securing catalog objects, you can establish authorizations either at the schema level or, in some cases, for each individual object. Simply establishing the privileges at the schema level is much easier; when privileges are established at the individual object level, the security model must be adjusted each time a new object is created. The owner of the object or a security administrator will then need to update existing roles to accommodate each new object. These tasks can become tedious and are often overlooked if objects are created frequently. To simplify the security model, privileges can be established at the schema level. In this way, all objects with a schema automatically inherit the privileges assigned to the schema.

#### Authorizations at the Catalog Object Level

Although establishing privileges at the schema level is easier, this approach can be less secure. If you determine that using schema-level privileges is acceptable, be aware that all current and future objects in that schema will be accessible for the assigned users or roles. No mechanisms exist for denying privileges in SAP HANA. Therefore, if your security requirements call for two catalog tables in the same schema, each with different privileges assigned to different roles, you’ll have to establish privileges at the individual table level and forgo the use of schema-level privileges. While this approach is more tedious, it provides more granular control of the privileges for objects within the same schema.

#### Considerations for Catalog Views

As discussed in [Chapter 2](#02_001.html#h2), catalog views reference other catalog views or tables within their definitions. When a user queries a catalog view, he only needs the SELECT privilege on that catalog view. The system doesn’t validate the privileges against objects referenced within the view.
