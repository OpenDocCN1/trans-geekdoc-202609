
The SAP HANA Web-Based Development Workbench security manager, hosted within the XS engine, provides an interface that you can use to create users, create roles, or manage security for standard roles. This interface provides a web-based alternative to SAP HANA Studio and also serves as an alternative to issues `GRANT` and `REVOKE` statement with SQL.

You can access the SAP HANA Web-Based Development Workbench via a supported Internet browser. The following URLs can be customized to match the details of your environment:

*   `http://sap-hana.myhost.com:8000/sap/hana/ide/security`

*   `http://<sap_hana_host>:80<instance_number>/sap/hana/ide/security`

In the last example, replace `<sap_hana_host>` with the host name of the SAP HANA system in your environment and `<instance_number>` with the two-digit instance number corresponding to your SAP HANA system.

For secure access, the following examples should help you construct the correct URL:

*   `https://<sap_hana_host>:43<instance_number>/sap/hana/ide/security`

*   `https://sap-hana.myhost.com:4300/sap/hana/ide/security`

Once you have access to the SAP HANA Web-Based Development Workbench security manager, expand the Security node on the right. Expand Roles to reveal a list of standard roles defined in the system. Double-click a role to open the management interface for the given role. With the selected role management window open, you can begin granting and revoking privileges.

###### Note

To perform the same action for an individual user account, expand the Users node and double-click the desired user account.

Recall that we recommend you use repository-based roles to support an SAP HANA security model. However, in this section, we’ll simply highlight the basic workflow if you choose to manage security with standard roles or directly on individual user accounts.

With the GUI management interface open for a given grantee, you can add an application privilege as follows. Click the Application Privileges tab. Click the plus sign (`+`) button to add and search for the desired analytic privilege. The Find Application Privileges window appears allowing you to search for a specific application privilege. Select the desired application privileges and click OK to add them to the list.

To save your changes, press (`Ctrl`)+(`S`) or click the disk icon at the top left to save and activate the privilege. To revoke an application privilege, select it in the list and click the red X. Once again, save the changes to make them active within the database system.

If any activation issues arise, warning messages will appear in the status pane at the bottom of the user management window. The status pane has a dark background color. Error messages will appear in red text. Errors are only generated when you attempt activation or save changes.

### 11.3.4 Granting Application Privileges within Repository Roles

As mentioned earlier, basing a security model on repository-based roles is best. Because of their benefits, we’ll review the process of granting application privileges within repository-based roles. To assign application privileges to a repository-based role, you can either modify or develop repository roles within design-time scripts, or you can use the SAP HANA Web-Based Development Workbench editor to create and modify repository-based roles.

#### SQL Syntax in Design-Time Scripts

In [Chapter 6](#06_001.html#h6), we introduced you to repository roles and outlined the workflows required to create and manage repository roles. In this section, we’ll again review the syntax necessary to assign application privileges to design-time repository-based role scripts. If you require more information about this process, refer to [Chapter 6](#06_001.html#h6).

When defining application privileges within repository-based role scripts, you must start each line with `application privilege`. Following this term, include a colon, then include the name of the application privilege. The application privilege name must include the package hierarchy name, two colons, and the name of the application privilege. For case-sensitivity purposes, the name must be enclosed in double quotes. At the end of the statement, include a semicolon to finish the line.

The following example shows a single line used to grant application privileges within a repository-based role:

```
application privilege: "sap.hana.security.base::DataService";
```

#### Granting and Revoking with the SAP HANA Web-Based Development Workbench

The SAP HANA Web-Based Development Workbench editor, hosted within the XS engine, provides an interface that you can use to build and test development artifacts. From a security perspective, you can use this interface to create and manage repository-based roles. This interface offers all the advantages of repository-based roles without the need to define the repository roles using scripts and the SAP HANA domain-specific language. However, you can use this same interface to either edit the role via a GUI or open the role file in the text editor.

You can access the SAP HANA Web-Based Development Workbench via a supported Internet browser. The following URLs can be customized to match the details of your environment:

*   `http://sap-hana.myhost.com:8000/sap/hana/ide/editor`

*   `http://<sap_hana_host>:80<instance_number>/sap/hana/ide/editor`

In the last example, replace `<sap_hana_host>` with the host name of the SAP HANA system in your environment and `<instance_number>` with the two-digit instance number corresponding to your SAP HANA system.

For secure access, the following examples should help you construct the correct URL:

*   `https://<sap_hana_host>:43<instance_number>/sap/hana/ide/editor`

*   `https://sap-hana.myhost.com:4300/sap/hana/ide/editor`

To use the editor, the user account first will need to be granted one of the roles listed in [Table 11.1](#11_003.html#t11.1). Users only need one of the two roles to access the SAP HANA Web-Based Development Workbench editor.

###### Additional Privileges Needed to Use the Editor

Note that the roles listed in [Table 11.1](#11_003.html#t11.1) simply allow the granted user access to the interface. Users will also need access to the package in which the repository roles are stored. To grant repository roles to other users and roles, users will need EXECUTE access to the system stored procedure named "`_SYS_REPO`"."`GRANT_ACTIVATED_ROLE`". To revoke repository roles, they’ll need EXECUTE access to the "`_SYS_REPO`"."`REVOKE_ACTIVATED_ROLE`" stored procedure.

As mentioned earlier, repository roles must be stored in a package that only security administrators can access. You would typically create a top-level package named Security to host such objects.
