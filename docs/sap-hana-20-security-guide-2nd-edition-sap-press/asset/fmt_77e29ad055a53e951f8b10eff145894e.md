
When using the CSV file option, you should also specify a secure path where the CSV file will be stored. To specify the path, update the path setting (`default_audit_trail_path`) in the `global.ini` file. For example, you can execute the following SQL code to specify that the audit log CSV file use the path `/usr/sap/HDB/HDB00/auditlog`:

```
ALTER SYSTEM ALTER CONFIGURATION ('global.ini', 'SYSTEM') 
   SET ('auditing configuration', 'default_audit_trail_path') = 
'/usr/sap/HDB/HDB00/auditlog' WITH RECONFIGURE ;
```

You can also use SQL to define custom audit log targets based on levels. You can choose from among alert, emergency, and critical audit levels. Three specific `global.ini` file settings are used for the auditing configuration: `emergency_audit_trail_type`, `critical_audit_trail_type`, and `alert_audit_trail_type`. For example, execute the three SQL statements shown in [Listing 15.1](#15_002.html#l15.1) to specify custom audit targets for the alert, emergency, and critical audit levels.

```
ALTER SYSTEM ALTER CONFIGURATION ('global.ini', 'SYSTEM') 
   SET ('auditing configuration', 'emergency_audit_trail_type') = 'CSTABLE, SYSLOGPROTOCOL, CSVTEXTFILE' WITH RECONFIGURE ; 

ALTER SYSTEM ALTER CONFIGURATION ('global.ini', 'SYSTEM') 
   SET ('auditing configuration', 'critical_audit_trail_type') = 
'CSTABLE, SYSLOGPROTOCOL' WITH RECONFIGURE ;

ALTER SYSTEM ALTER CONFIGURATION ('global.ini', 'SYSTEM') 
   SET ('auditing configuration', 'alert_audit_trail_type') = 
'CSTABLE, SYSLOGPROTOCOL' WITH RECONFIGURE ;
```

Simply enabling auditing isn’t sufficient. You must also define audit policies to track specific events within the SAP HANA system. In the next section, we’ll discuss how audit policies are configured.

## 15.3 Creating Audit Policies

As mentioned earlier, auditing is disabled by default within the SAP HANA system. In addition, no custom audit policies are included out of the box. Audit policies can be defined to track specific events based on specific conditions. Audit policies are defined by an audit administrator based on your organization’s requirements. In an ideal situation, your organization would record every event within its SAP HANA system. However, recording all events to an in-memory database is costly, both financially and architecturally. Therefore, you must configure specific audit policies to record only events that are critical to the security and stability of the system.

Even after auditing is enabled globally, most events won’t be recorded until specific audit policies are defined, although SAP HANA does have several mandatory audit policies that cover events specific to the audit mechanism itself. For example, if you disable auditing, change auditing settings, or truncate the audit logs, these events will be recorded in the default target location even if no policies are defined. A user must have the `AUDIT ADMIN` system privilege to define audit policies.

Most actions within the SAP HANA system can be audited. Audit policies are comprised of a combination of specific actions, an action status, and a user performing the action. The action status is based on one of three status options: successful, unsuccessful, or all.

Some actions can only be activated if they reference one or more user accounts. In addition, policies can also be enacted for all users except specified users. If an action doesn’t require a referenced user, the assumption is that the action applies to all users within the system. Furthermore, some actions also require a referenced catalog object. For example, you must reference a user and a catalog object when defining audit policies with data manipulation actions.

Before we review the makeup of an audit policy and the various tools used to define them, let’s look at the 16 different categories of actions that can be audited. In the following section, we’ve outlined these categories and provided a few examples of the specific actions they encompass.

### 15.3.1 Components of the Audit Policy

An audit policy is comprised of an audit action, audit action statuses, audit levels, target object(s), target user(s), and a trail target. In the following sections, we’ll look closer at each of these items.

#### Actions Available for Auditing

Twenty different categories of actions can be monitored within SAP HANA. Most of the actions within these categories directly correspond to the SQL statements executed to perform actions related to the category. Within each category, you’ll find a variety of actions that can be configured and selected. Most audit policies can only be defined using actions from the same action category. In addition, some actions within each category can range from broad to specific. To better understand the types of actions that can be audited, let’s review the twenty categories:

1. All actions  

   The all actions category includes a single audit action by the same name. This action must be mapped to specific users or excluded from specific users. When enabled, all actions within the system will be audited based on the configured audit action status and selected user. In general, you don’t want to enable this rule for many users because this rule can negatively influence the performance of the system. You should limit this category to events that don’t occur often. For example, this category can be used as a universal policy to capture all unsuccessful events for all users except the system accounts. In this case, the system will record any action by a user when he isn’t authorized to perform the action. A policy referencing all actions must be mapped to specific users or must be mapped to a list of excluded users. This category can’t be universally applied to all users in the system.

2. Application auditing  

   The application auditing category can be selected for auditing events and actions taking place in SAP HANA XSA applications. Application deployed in the SAP HANA XSA can be configured to record events to the SAP HANA XSA audit log service. This service records events in the SAP HANA database audit system.

3. Authentication provider management  

   The authentication provider category can be selected when you want to audit events and actions related to Security Assertion Markup Language (SAML), Lightweight Directory Access Protocol (LDAP), or JSON Web Token (JWT) authentication providers. Any changes to these providers can be recorded as well as when these providers are created.

4. Audit configuration  

   The audit configuration category can be selected when you want to specifically record when an audit policy is disabled or enabled within a tenant database by a user with sufficient access.

5. Backup deletion  

   The backup deletion category includes only the `BACKUP CATALOG DELETE` action. This action is useful for monitoring users that delete backup catalog entries and files. Policies with this action do not have to be assigned to specific users.

6. Certificate and PSE store  

   The certificate and personal security environment (PSE) store category includes all `ALTER`, `CREATE`, and `DROP` SQL actions related to the management of the PSE or certificates within the SAP HANA system. Policies with this action do not have to be assigned to specific users.

7. Client-side encryption  

   The client-side encryption category records events when client-side encryption is created, altered, or dropped for a given table column. Client-side encryption is a feature where data within a column can be encrypted and subsequently only decrypted when a client has the proper key pair to view it.
