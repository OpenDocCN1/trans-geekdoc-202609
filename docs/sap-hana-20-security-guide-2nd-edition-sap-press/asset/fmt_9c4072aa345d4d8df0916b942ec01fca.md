
Starting with the system administrators, the consultant recommends that their `ROOT`-level package privileges be limited to `REPO.READ`, `REPO`, `REPO_MAINTAIN_NATIVE_PACKAGES`, and `REPO_MAINTAIN_IMPORTED_PACKAGES`, which will allow them to add package nodes at any level without automatically being granted privileges to activate or modify existing development artifacts within existing packages. The Grantable to Others or `WITH GRANT` option must not be assigned to the system administrators role type, to prevent them from assigning their package privileges to other users or standard roles. System administrators can be granted full access to the `E-corp.Admins` package because it contains their development-related artifacts. This package should be the only area in which system administrators can activate or modify content.

Unless justified, developer’s role should not receive `REPO.READ` privileges on the top-level `E-corp` package node. Developers should only be granted privileges on the nodes containing their development artifacts. For example, for the `E-corp.sales` package node, they might have full access to create SAP HANA information views. Developers don’t require `REPO.READ` on parent or grandparent nodes to work within their designated packages. Recall that package privileges are evaluated from the bottom up; therefore, you won’t need to grant `REPO.READ` access for each parent or grandparent level of the package hierarchy. Developers will be able to navigate the package hierarchy because of this bottom-up evaluation.

The managers role should be granted full access to the top-level package security. This top-level package is where role managers will create development artifacts used for the security model.

Overall, the recommended changes will create a more secure environment. Moving the security package to the top level will reduce the likelihood of both accidental and deliberate privilege elevation within the environment. Adding a few additional subpackages within the Security node helps better organize security-related development artifacts. By preventing system administrators from having full access at the `ROOT` node, E-Corporation can better ensure that only role managers are able to manage repository roles within the environment.

## 9.5 Summary

Securing the package hierarchy plays an important role in any security model. Package privileges are divided into two broad categories: privileges for native content and privileges for imported content. When repository-based roles are used within the model, you must ensure that only role managers can modify repository roles. In addition, you must establish the appropriate security to support development activities within the environment. Inheritance can be both beneficial and risky when leveraged to implement package privileges.

# 10 Analytic Privileges

In this chapter, we’ll explore analytic privileges and describe how you can use these privileges to secure access to SAP HANA information views and data.

Analytic privileges grant or restrict access to data hosted within the SAP HANA system. These privileges provide two levels of access. First, they provide read-only access to information views. Assuming that the information view requires an analytics privilege check, to query an information view, you must have an associated analytic privilege; in other words, users can’t query an information view unless they’re granted an analytic privilege referencing that information view or an analytic privilege that applies to all information views. Second, analytic privileges can be configured to restrict the data that an information view returns when queried. At a high level, this data restriction is achieved by filtering the attribute data during query execution. When using analytic privileges to filter data, each user accessing an information view will require his own unique user account, which becomes the basis for filtering the data.

In this chapter, we’ll provide an overview of analytic privileges and discuss the differences between static and dynamic analytic privileges. We’ll also discuss how classic XML-based analytic privileges are being replaced with the new SQL-based analytic privileges, and we’ll explain how to manage and create static and dynamic privileges. Finally, we’ll review the process used to troubleshoot a grantee’s effective analytic privileges and discuss the processes available to grant analytic privileges.

However, before we can begin discussing analytic privileges, first you’ll need understand a few basics about SAP HANA information views, which we’ll discuss next.

## 10.1 What Are SAP HANA Information Views?

Information view is a generic term describing any of the components used to create metadata-rich, multidimensional models within the SAP HANA system. In addition to SAP HANA’s ability to store data in columnar tables, you can also create information views to consolidate the complex relationships between tables and data elements. Information views are typically used to produce analytical models that aggregate quantifiable data elements by various attributes. For example, an information view for Controlling and Profitability Analysis (CO-PA) in SAP ERP can be created to generate analytics for gross margin by time, material, customer, market, and region, attributes that become the basis for restricting the data using analytic privileges.

Three main types of information views exist in SAP HANA: attribute views, analytic views, and calculation views. In this section, we’ll briefly discuss these three view types and how they relate to analytic privileges.

### 10.1.1 Attribute Views

Attribute views are models created to produce views of master data. For example, a customer attribute view would generate columns such as customer ID, customer name, customer address line 1, customer region, customer sales region, and many more customer-related attributes. Attribute views are objects that help associated attributes with measures within analytic views. These reusable objects can be associated with multiple analytic views. On their own, attribute views don’t create a complete multidimensional model. They simply model the master data that will be used within a multidimensional model. Each column within an attribute view is a candidate for filtering through an analytic privilege. For example, you can limit the customers returned in a query based on the sales region attribute column.

Starting with SAP HANA 1.0 SPS 07, SAP replaced attribute views with a new type of calculation view: dimensional calculation views. Dimensional calculation views are defined when you initially create the calculation view within the various graphical user interfaces (GUIs). When creating the view, you’ll notice the Dimension option when defining the view’s Data Category. Dimensional calculation views support more advanced transformations like the use of ranking and unions, which is appealing from a modeling standpoint. These views also allow SAP to maintain a single user interface for all calculation view types. Another main difference with a dimensional calculation view is that their final transformation node is always a projection node, meaning the view will produce a flat dataset without aggregating the results.

###### Differences between SAP HANA 1.0 and SAP HANA 2.0

With SAP HANA 1.0 through SAP HANA 2.0 SPS 04, attribute views can only be created using SAP HANA Studio and cannot be created using the SAP HANA Web-Based Development Workbench editor. In addition, as SAP has transitioned SAP HANA extended application services, classic model (SAP HANA XS) to SAP HANA extended application services, advanced model (SAP HANA XSA), SAP Web IDE for SAP HANA can be used for creating SAP HANA dimensional calculation views.
