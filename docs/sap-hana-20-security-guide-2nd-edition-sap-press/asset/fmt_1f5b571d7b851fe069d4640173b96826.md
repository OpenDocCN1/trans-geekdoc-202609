
Based on testing and research, the `_SYS_BI_CP_ALL` analytic privilege doesn’t override SQL-based analytic privileges. When using SQL-based analytic privileges, all users require at least one custom analytic privilege referencing each information view they want to query. To grant full access to an information view, simply reference the information view without any defined restrictions. This approach will grant such grantees full data access to the referenced information view, even if other SQL-based analytic privileges are granted to the same user. Now, let’s look at the processes for creating analytic privileges.

## 10.4 Managing Static Analytic Privileges

You can create two types of static analytic privileges: XML-based or SQL-based. Both options are nearly identical, with a few exceptions. SAP has not officially deprecated the classic XML-based option as of SAP HANA 2.0 SPS 04, but the documentation indicates that SAP will deprecate this option in the future. Some user interfaces (UIs) also refer to XML-based analytic privileges as the classic option. Therefore, we recommend that all new developments be based on SQL analytic privilege workflows. In this section, we’ll provide instructions for creating both types.

### 10.4.1 Creating Static XML-Based Analytic Privileges

Analytic privileges are development artifacts and, as such, are created and stored in the SAP HANA repository. Typically, they’re stored in a package with limited access. For example, the same package structure that stores repository roles would be an ideal location. This package structure should already be set up so that only role administrators have the proper package privileges. Developers must have the appropriate package privileges to create and activate these development artifacts.

To create an analytic privilege, open the SAP HANA Web-Based Development Workbench editor. Within the content repository, locate a package in a secure location. Right-click the package and choose New • Analytic Privilege…. A popup window will appear labeled New Analytic Privilege, as shown in [Figure 10.4](#10_004.html#f10.4).

In this window, specify the technical name of the analytic privilege in the `Name*` field. The name can only contain the characters Aa–Zz and the underscore (`_`) special character. In the `Label` field, enter a description for the analytic privilege. In the `Type` dropdown list, choose the appropriate option based on the referenced information views. For example, select the Classical analytic privilege option for referenced information views configured to use classical XML-based analytic privileges. Click `Create` to continue.

**Figure 10.4** New XML-Based Analytic Privilege Window

The classic XML-based or classic analytic privilege management window is organized into four main sections, as shown in [Figure 10.5](#10_004.html#f10.5).

[![XML-Based Analytic Privilege Management Window](bilderklein/klein10_005.png)](img-f10.5.html)

**Figure 10.5** XML-Based Analytic Privilege Management Window

The `General` section (top left) provides the option of updating the `Label` field. Just below this field is a second option, the `Apply to all information models` checkbox. When the `Apply to all information models` checkbox is selected, all XML-based information views will be subject to the analytic privilege restrictions. For example, if 12 information views have been activated in the system and each information view has an attribute column with a technical name of `CUSTOMER_REGION`, the restrictions defined within this analytic privilege will apply even if they aren’t explicitly referenced within the analytic privilege.

The `Secured Models` section (bottom left) provides the option to add or remove referenced information models. If the `Apply to all information models` option isn’t selected, information views will be within the scope of the analytics privileges access and applied restrictions. Remove an information view by selecting it in the list and then clicking the `Remove` button.

In the `Privilege Validity` section (top right), you can define a validity period for the restrictions. To define a validity period, click the `Add…` button, then choose an `Operator` to define the date range. Maintain the `From` and `To` date fields to define the date based on the chosen operator. When validity is defined, the analytic privileges will only be applied within the date range specified. If no validity is defined, the privilege will be valid all the time. To remove the validity, select it in the list and click the `Remove` button.

In the `Associated Attribute Restrictions` section (bottom right of [Figure 10.5](#10_004.html#f10.5)), you can select the attribute columns that will be subject to the filter restrictions. Click the `Add…` button to select an attribute column from an information view referenced in the `Secured Models` section. If the attribute column is derived from a dimensional calculation view or attribute view, the checkbox in the column labeled `Shared` will be selected. To remove the attribute column, select it in the list and click the `Remove` button.

Once you’ve added a column, click the `+ Restrictions` button within the restriction type column. You can use this interface to define the filter conditions or restrictions for each column specified in the `Associated Attribute Restrictions` section. When you click the `+ Restrictions` button, a row will be inserted below the column. You can add multiple rows to define multiple restrictions for a given column. In each case, the restriction conditions will be listed in a row below the attribute column. To define the filter condition, for static analytic privileges, choose the `Fixed value` option. Select an `Operator` in the column to its right from the dropdown list to define part of the filter condition. For example, choose `Equal` if the filter condition requires that the attribute column value equal the static value specified in the `Value` field. Alternatively, choose `GreaterEqual` if the value must be greater than or equal to the static value specified. The `Value` column contains the static value used in the filter condition. You can click the icon in the corner of this field to see a list of possible values in the attribute column.

Filter conditions in the static XML-based analytic privileges support the use of the `Between`, `ContainsPattern`, `Equal`, `GreaterEqual`, `GreaterThan`, `Is Not Null`, `IsNull`, `LessEqual`, and `LessThan` operators. If multiple restrictions are applied to the same attribute column, all filter conditions will be executed as true or executed using an `AND` condition. [Figure 10.6](#10_004.html#f10.6) shows static restrictions configured for the example attribute `TYPE`. The filter conditions of `EQUEL CHAR30` are applied in the example.

[![Example Restrictions Applied in an Analytic Privilege](bilderklein/klein10_006.png)](img-f10.6.html)

**Figure 10.6** Example Restrictions Applied in an Analytic Privilege

Note that the `Count` column and the `Associated Attribute Restrictions` section shown in [Figure 10.6](#10_004.html#f10.6) indicate that one restriction has been applied to the attribute column. Expect the count to increase each time you add an additional restriction for a given attribute column.

When you’ve finished defining the analytic privilege, click the save icon (floppy disk) in the top left to save and activate the analytic privilege. Clicking the save icon will both save the analytic privilege within the repository and deploy it to the system for use within a role.

Once the analytic privileges are activated, their restrictions won’t apply until the analytic privileges are granted to existing roles or users. If no competing analytic privileges are also applied to the grantee, queries to the referenced information views will be limited based on the defined filter conditions or restrictions.
