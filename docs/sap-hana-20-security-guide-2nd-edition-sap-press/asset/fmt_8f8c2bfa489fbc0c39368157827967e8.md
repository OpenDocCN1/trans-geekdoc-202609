
Select the checkbox beside each privilege to assign the selected privilege to the selected package. Repeat the process for all packages. To remove the privilege, simply deselect the checkbox beside the privilege you want to remove.

To remove an assigned package and all its privileges, select an object from the list on the left, then click the large minus sign (–) above the list to remove the package. Items in the list must be deleted one at a time.

Once you’ve configured the desired list of packages and established their privileges, click the Save All button at the top left, which looks like three stacked floppy disks.

If any issues arise when saving and activating the repository role, messages will appear in red text within the console window just below the opened Repository Roles tab. The console window has a dark background and is located at the bottom of the open tab. Affirmative messages will appear in white text, and error messages will appear in red text.

To close the Repository Roles tab, click the small X to the right of the tab.

## 9.4 Case Study: Preventing Content Developers from Elevating Their Privileges

E-Corporation has several developers using the SAP HANA system to create information views and custom applications within the SAP HANA XS engine. The company also relies heavily on the use of repository-based roles to support its security model. Because developers and security administrators both require access to the same repository, E-Corporation management is concerned that developers might have access to the repository roles. If developers were to gain access, they could edit the repository roles and grant their assigned roles additional privileges. In the following sections, we’ll look at E-Corporation’s current security model before discussing some changes the company can make to improve it.

### 9.4.1 Assessing the Current Configuration

E-Corporation requests that the company’s security consultant review the security model and repository structure to make sure the company has properly secured access to its repository-based roles. To properly assess the current design, the security consultant creates a diagram to outline the current package hierarchy, as shown in [Figure 9.8](#09_004.html#f9.8).

[![Current E-Corporation Package Hierarchy](bilderklein/klein09_008.png)](img-f9.8.html)

### 9.4.2 Recommendations

The consultant recommends changes to both the package hierarchy and the package privileges that are assigned the role types at E-Corporation. The predominant recommendation is that only security managers should have access to elevate the privileges assigned within repository roles. System administrators should not have access to create or edit existing repository roles because of the need for the separation of duties at E-Corporation. To achieve this separation, changes related to the package hierarchy and the package privileges assigned to roles are needed.

#### Changes to the Package Hierarchy

E-Corporation’s current package hierarchy places repository roles in the `E-corp.Admins.Security` package. This design allows repository roles to reside in a dedicated package but complicates the design of the security model. Recall that you can’t explicitly deny privileges in SAP HANA, and packages inherit the privileges assigned to parent and grandparent nodes. If a role is assigned privileges at a parent or grandparent node, child nodes will inherit those privileges. You have no option to break this inheritance or to explicitly deny a privilege on a child node. The current design grants full access to the system administrators, even though they were not explicitly granted full access on the `E-corp.Admins.Security` node. This problem is due to the inheritance of privileges assigned at the `ROOT` and `E-corp.Admins` nodes. The design also grants `REPO.READ` access to all developers. Although read access for developers is not a significant concern, it does highlight the importance of calculating the risk of accidental privilege inheritance within the package hierarchy. For example, the security team might accidently grant the `REPO.EDIT_NATIVE_OBJECTS` developer role to the `E-corp` package node, which would grant developers edit access to the repository roles via inheritance.

The security consultant recommends a simple change to the hierarchy. Given the significance of inheritance and the likelihood of accidental privilege elevation through inheritance, he recommends that the Security package node move to the top level of the hierarchy. In this way, only `ROOT`-level package privileges will present a challenge to the security model design. Furthermore, the security consultant recommends that the `Security.Roles`, `Security.UserProvisioning`, and `Security.Schemas` packages be created to better organize and potentially restrict security-related development artifacts.
