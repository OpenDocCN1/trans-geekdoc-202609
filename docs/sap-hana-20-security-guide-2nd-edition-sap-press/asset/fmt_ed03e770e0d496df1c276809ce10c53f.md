
Regardless of how your organization decides to configure encryption-related administration access, limiting access to these activities is still important. If communication encryption is disabled, man-in-the-middle attacks may intercept data and credentials. If data volume or log volume encryption is disabled, unauthorized individuals with physical access to SAP HANA persistent storage devices might be able to access confidential or proprietary data. This vulnerability is especially important to consider when the SAP HANA system is hosted outside the physical security of your organization’s internal data center or network.

With that in mind, let’s look at the system privileges required to manage data and communication encryption. To manage all aspects of encryption, the `CERTIFICATE ADMIN`, `ENCRYPTION ROOT KEY ADMIN`, `SSL ADMIN`, `TRUST ADMIN`, `INIFILE ADMIN`, `CREDENTIAL ADMIN`, and `CATALOG READ` system privileges will be required. In addition, an operating system user account will be required if certificates are stored on the file system of the operating system.

### 7.4.4 System Auditing Role

The final repository role recommended by the security consultant grants the necessary privileges to manage auditing within the SAP HANA system. This critically important role should be limited to individuals that have no other security or system administration-related privileges within the system. Grantees of this role will be responsible for the following tasks:

*   Enabling or disabling auditing

*   Creating audit policies to track actions within the SAP HANA system

*   Clearing the audit database table, logs, or files

The `AUDIT ADMIN` and `AUDIT OPERATOR` system privileges must be granted to roles that will facilitate these requirements. The ability to maintain a separation of duties with this role is critical. Grantees of this role must not be able to cover their tracks within the system, which means they can’t simultaneously administer users, roles, and auditing. Granting a single user all these abilities would allow that user to commit fraud or perform malicious actions without accountability.

## 7.5 Summary

System privileges govern access to a variety of actions within an SAP HANA system. These actions can be categorized into development, security, administration, system monitoring, and performance testing areas. System privileges can be granted to users, roles, and repository roles, but using repository roles is best because the `_SYS_REPO` account has the necessary privileges by default to grant system privileges to other users.

# 8 Object Privileges

In this chapter, we’ll explore the different privileges that you can grant to catalog objects and walk you through the process of granting privileges.

Object privileges play an important role in the development of any SAP HANA security model and define the types of SQL script actions a user can perform on a catalog object. SAP HANA hosts multiple types of catalog objects. In [Chapter 3](#03_001.html#h3), we discussed the various types of catalog objects that you can create in SAP HANA and how the way you create catalog objects affects your security model.

As a reminder, catalog objects consist of various relational database management system (RDBMS) artifacts, such as schemas, tables, views, stored procedures, triggers, sequences, and a few other items. Items such as tables both store and define the structure of the data. Other items, such as views, express query logic.

Schemas are crucially important in the world of catalog objects. All catalog objects are assigned to a single schema. You could say that the schema is the parent object to all other catalog objects. SAP HANA allows security administrators the option of granting privileges on a schema, in which case all objects within the schema inherit the privileges assigned to the schema. Alternatively, security administrators can assign privileges to individual objects, in which case the security administrator will need to update the security model to grant the appropriate privileges to the catalog object each time a new object is created within a schema.

In this chapter, we’ll look at object privileges and demonstrate how you can grant object privileges to users or roles using SQL statements, using the SAP HANA cockpit, or within repository-based roles.

## 8.1 What Are Object Privileges?

When you grant privileges to a catalog object, you’re essentially specifying the types of actions that you can execute against the catalog object using SQL. Some of those actions correlate directly with the syntax you’ll use in a SQL statement. For example, you can query a table using the following SQL statement:

```
SELECT TOP 100 "FirstName" FROM "EDW"."DimCustomer" WHERE "Status" = 'Active'
```

Notice that this SQL statement starts with SELECT. To properly execute this SQL statement, a user or its associated role must be granted the `SELECT` privilege for the catalog table `DimCustomer`. You could also grant `SELECT` to the enterprise data warehouse (`EDW`) schema, allowing the user or associated role to query any table in that schema.

In the following sections, we’ll explore catalog object privileges related to schemas, tables, views, stored procedures, functions, remote sources, and sequences.

### 8.1.1 Catalog Object Privileges

Before we explore the process of granting privileges to catalog objects, let’s look at the different privileges that you can grant to each of the major types of catalog objects, starting with catalog schemas.

#### Granting All Privileges

SAP HANA 2.0 supports a special `GRANT` statement as a shortcut for granting all Data Definition Language (`DDL`) and Data Manipulation Language (`DML`) privileges currently granted to the grantor, for a given object, to a grantee. This `GRANT` statement is only applicable for schemas, tables, and view catalog objects. Based on testing, for schemas, this `GRANT` statement only seems to work if the grantor is also the owner of the schema. However, this special statement does work for tables and views even if the grantor is not also the owner. If the grantor has the ability to grant to others, he can use this special shortcut, which does partially grant privileges. If the grantor only has one privilege that is grantable to others, only that one privilege is applied to the target grantee.

The following example SQL statements can be used by a grantor to grant all currently granted privileges to another grantee:

```
GRANT ALL PRIVILEGES ON SCHEMA <SCHEMA_NAME> TO <GRANTEE_NAME>;
GRANT ALL PRIVILEGES ON <SCHEMA_NAME>.<TABLE_NAME> TO <GRANTEE_NAME> WITH GRANT OPTION;
```
