
# SAP HANA 密码策略与服务账户配置

Six key password policy items need to be addressed with any SAP HANA system: password lifetime, complexity, number of reused passwords, lockout policy, initial password policy, and password disabled option.

## Password Lifetime

Passwords should be configured so that they expire after a specified number of days; in SAP HANA, the default is 182 days. Depending on the required password complexity and length, this number might need to be lowered. For example, many organizations require passwords to expire every 90 days because they require only 8 characters and require only limited complexity. Consult with your organization’s security team for a policy appropriate for your situation.

In addition to the maximum password lifetime, a minimum password lifetime should be implemented to prevent users from making frequent, consecutive password changes. For example, a user might try to change his password several times to circumvent the password reuse policy. The default value of one day will generally discourage users from circumventing the reuse policy, but the value should be increased if users frequently abuse the policy.

## Password Complexity

Passwords should require a minimum number of character types to decrease the likelihood that both software programs and other users might guess them. By default, passwords require an uppercase letter, a lowercase letter, and a number in SAP HANA. The default minimum length is 8 characters. Organizations can increase the complexity requirement for passwords by requiring a special character in addition to the other character types. Complexity can also be increased by increasing the minimum number of required characters and preventing the use of common dictionary words in passwords.

## Number of Reused Passwords

When changing passwords, based on the maximum lifetime, organizations should prevent users from reusing passwords for a time. The default value for SAP HANA is the five previous passwords. Multiply 5 times 182 days, and you’ll see that passwords can’t be reused for about 2.5 years by default in SAP HANA. This calculation assumes that users don’t change their passwords before the expiration date.

Your organization should review this setting and increase this number as needed based on the configured minimum and maximum password lifetime. For example, many organizations increase this value to 12 previous passwords to reduce the likelihood that a password is compromised.

## Lockout Policy

When a password is entered incorrectly a specified number of times, the account should be locked out or restricted from use until the owner and administrator can review the cause. SAP HANA defaults to a value of six invalid passwords before an account is locked out. In addition, SAP HANA defaults to 1,440 minutes or one day until the system automatically removes the lockout.

Your organization should review these default settings and implement a policy based on its security team’s requirements. For example, many organizations will increase the number of failed attempts from 6 to 10 but also force an account to remain locked out indefinitely. When locked out indefinitely, only an administrator can remove the account lockout condition, which forces the user and administrator to communicate about the cause of the lockout, thus helping identify instances in which someone else might be trying to guess the account password.

## Initial Password

When an administrator creates an account for a user, she establishes an initial password. SAP HANA defaults to forcing a user to change this initial password the first time they log on. An administrator should never know a user’s password in the long term. Therefore, users must change this password as soon as possible. SAP HANA also disables an account if this initial password isn’t changed within 7 days of its creation.

These settings are crucial, and the default values within SAP HANA are typically acceptable. However, your organization should consult its security policy team about its own required settings. For example, some organizations might increase the initial password lifetime if new users typically don’t access the system within the first 30 days of the account creation. However, when increasing this policy setting, security administrators should choose an initial password that is unique for each user, which will reduce the likelihood of a new user account being compromised.

## Disable Password Authentication

Organizations that use third-party authentication and single sign-on (SSO) with SAP HANA accounts don’t necessarily need password authentication enabled for a given user. The following SQL code will disable password authentication for a given user:

```
ALTER USER <USER_NAME> DISABLE PASSWORD;
```

Users configured with a Security Assertion Markup Language (SAML) or Kerberos identity can still authenticate using a third-party authentication mechanism without the need to authenticate with SAP HANA via a password managed by SAP HANA. This methodology eliminates the need to manage passwords for a user.

## 17.1.2 Service Accounts

Service accounts or technical user accounts will probably need to be created within your SAP HANA system. These accounts are used by software applications to authenticate with the SAP HANA system. For example, a service account is set up to allow SAP NetWeaver to manage the SAP HANA relational database management system (RDBMS). Also, the password lifetime limit for such accounts is often disabled, which ensures that the password doesn’t expire and thus stop the external application from functioning. In fact, the SAP HANA Security Checklist tool, found in the SAP HANA cockpit, will specifically warn you if a service account has a nonexpiring password. While this warning is warranted, you simply can’t just remove the setting without putting your production systems at risk when the password expires. To that end, when establishing service accounts, we recommend the following guidelines:

*   Generate a 64-character or longer password using a secure random password generator. This approach helps prevent the password from being compromised by software applications designed to decrypt a password store or brute force a password.

*   Limit the overall privileges assigned to service accounts. Only grant what’s necessary for the account to service the application’s use within SAP HANA.

*   Plan to generate a new password every year—and remember that applications using the service account must also support changes to the password. Changing this password is important because this password can easily be compromised due to human error. For example, media containing the password might be unencrypted and easy to compromise.

*   Use a secure password manager application to store the password. These applications typically have their own internal security mechanisms and auditing capabilities to help organizations manage service account passwords that are accessible by multiple users. For example, the password can be checked out for testing. When checked out, SAP HANA security administrators can correlate the use of the account with SAP HANA audit logs.

*   SAP HANA audit policies should be created to monitor service account activity, especially for critical actions. Not all actions need to be monitored, but we highly recommend that important actions be audited.

*   An acceptable use policy for service accounts should be drafted. These policies should limit how these accounts are used within your organization and should establish guidelines for password policies, limitations for use, and limitations of individuals with access to the accounts’ passwords.
