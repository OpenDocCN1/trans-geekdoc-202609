
# HDI Container Roles

Effectively, you’ll use HDI container roles as the basis for granting database users access to runtime objects within an HDI container’s schema. Once an HDI container role is created, you can then use a special SQL console, found in the SAP HANA database explorer, to execute special stored procedures that can grant HDI container roles to users. Within this section, we’ll provide an overview of HDI container roles, describe the steps for granting HDI container roles using the SAP HANA database explorer, and finally describe the steps required to authorize a standard database user EXECUTE access to the store procedures in the HDI container’s `#DI` schema.

## Defining HDI Container Roles

HDI container roles are like legacy the SAP HANA XS repository roles we discussed in [Chapter 6](#06_001.html#h6); however HDI container roles can only provide security access to objects within the container by default. For the HDI role to reference external catalog objects, the `#OO` user must have the same access to the external catalog object including the `WITH GRANT OPTION`. In most cases, HDI container roles are created by developers within their project. As such, HDI container roles are not a feasible alternative to the SAP HANA XS repository-based roles that you could use to manage an entire database system’s security model. This limitation is the case for two major reasons:

*   First, no design-time security exists to prevent developers from manipulating HDI container roles when they have access to the design-time content and the ability to deploy it to container at runtime. Without this protection, developers could elevate their access to HDI content, external objects, and data within the SAP HANA database, thus bypassing standard security-based segregations. In this case, we’re specifically referring to tables, analytic privileges, and calculation views typically used in an SAP HANA-based business intelligence solution.

*   Second, the HDI container database `#OO` user, by default, has no access to objects outside of the container. This user would need access similar to what the `_SYS_REPO` user had if you were to create system-wide HDI container roles to manage the entire database’s security model. This approach would in turn give anyone with the corresponding HDI container design-time access the ability escalate their own privileges if even a single HDI container role was granted to the developer’s user account. In addition, granting HDI container roles to standard SAP HANA users is difficult, as is setting up cross-HDI container access exclusively for a security team. A complex SQL statement is required to grant HDI container roles, and complex scripts are required to grant cross-container access. This model would not be compliant with the segregation of duties and would not be secure, nor would this solution be scalable as a system-wide security model.

This process would also not be a one-time activity since, as each additional HDI container is created, access to runtime objects within that container would need to be granted to the legacy containers containing HDI roles used to govern the SAP HANA security model. The tedious nature of this arrangement also makes this solution unscalable.

Hopefully, SAP HANA will one day devise a solution where a system-managed HDI container is deployed within every SAP HANA database. A container that would have access to all new HDI containers and any classic runtime database objects in a way that is both secure from a design-time perspective and scalable from a management perspective. In the SAP HANA XS model, the `_SYS_REPO` service account was deployed with a high level of database access and had access to grant access to all design-time objects it owned. You could also easily grant `_SYS_REPO` access to runtime objects that were not created at design time. Furthermore, this grant activity only needs to be executed one time for each newly created runtime schema.

With that said, in this section, we’ll explain the makeup of HDI container roles and show you how they can be granted to users. An understanding of this process is necessary even if not recommended for supporting a system-wide security model. Some organizations have already began developing content within SAP HANA XSA, where establishing security for HDI containers is important.

HDI container roles are design-time scripts, using a JavaScript Object Notation (JSON)-compliant syntax, that when built or activated, create runtime roles in the SAP HANA database. The privileges specified within the script must be possessed by the HDI `#OO` user, and the privileges must include the `WITH GRANT OPTION`. For catalog objects created in the HDI container, the `#OO` user will be the owner and therefore will have the necessary privileges.

For objects outside the container, `#OO` users will need to be granted permission, will need references to external schemas, and will need synonyms to reference external catalog objects. The synonym is required so that the `.hdbrole` can find the external object in the database. Based on testing, the `.hdbrole` only looks for catalog objects in the HDI container schema. Synonyms allow you to alias external objects in a way that the `.hdbrole` builder can find them. You can easily define a `.hdbsynonym` file to create the needed synonyms, and SAP Web IDE for SAP HANA has a GUI to help you create synonyms.

For external schemas, you’ll also need a schema reference, which can be configured in a `.hdbconfig` file. No GUI exists for this file, and we’ll share the JSON syntax for this file in [Listing 18.5](#18_004.html#l18.5). Let’s start by looking at the syntax for the `.hdbrole` file. [Listing 18.2](#18_004.html#l18.2) shows a basic `.hdbrole` file with no privileges being granted.

```
{ 
  "role":{ 
                "name":"MyProj.db.roles::EMPTYROLE" 
          }
 }
```

**Listing 18.2** A Basic `.hdbrole` File with No Privileges Being Granted

The format starts with opening and closing curly brackets, as in `{<some text>}`. At the next value level, you’ll define a JSON value titled “role”: `{ <some text> }`. Within that value pair level, you’ll define the “name”:`"<namespace + role name>"`,`{<privilege text>}` value. The namespace follows the project’s folder structure. For example, if you create this role in the `MyProj` project and store the role in the folder path `MyProj • db • src • roles`, the namespace would be `MyProj.db.roles::` followed by the name of the role.

The remaining structure varies based on the privilege type. To further describe the syntax, let’s specify some requirements and then provide an example `.hdbrole` script. For example, let’s say you need to create a role granting `SELECT` access on the HDI table `MyProj.db::CUSTOMERS`, the external table in the `SYSTEM` schema `CUSTOMERS`, the entire `SYSTEM` schema, and the `MYPROJ_HDI_DB_1` schema. You would define the role using the code shown in [Listing 18.3](#18_004.html#l18.3).

```
{ 
  "role":{ 
    "name":"MyProj.db.roles::TABLE_READ_ONLY_ACCESS", 
      "object_privileges":[ 
      { 
       "name":"MyProj.db::CUSTOMERS", 
       "type":"TABLE", 
       "privileges":[ "SELECT" ]
      } ,
      { 
       "name":"MyProj.db::CS_CUSTOMERS", 
       "type":"TABLE", 
       "privileges":[ "SELECT" ]
      }
    ],
      
      "schema_privileges":[  
{  
    "reference":"REF_SYSTEM",
    "privileges":[ "SELECT" ]
},
{  
    "privileges":[ "SELECT" ]
}
  ]
    }
   }
```

**Listing 18.3** Example `.hdbrole`

In addition to the `.hdbrole` file, you’ll also need to define `.hdbsynonym` and `.hdbroleconfig` files for the externally referenced catalog table objects and schemas. [Listing 18.4](#18_004.html#l18.4) shows the syntax of the required `SYSTEM.hdbsynonym` file. This file is required because “`MyProj.db::CS_CUSTOMERS`” is actually a synonym pointing to the `SYSTEM.CUSTOMERS` table.

```
{
  "MyProj.db::CS_CUSTOMERS": {
    "target": {
      "object": "CUSTOMERS",
      "schema": "SYSTEM"
    }
  }
}
```
