
However, you can also grant object privileges to individual catalog objects within a schema. In this case, we’re granting catalog object privileges to each individual object. Security administrators might use this approach if they want to limit access to individual tables and views within a schema. Some administrators will find granting privileges to each individual catalog object to be an unscalable and tedious task. Fortunately, you also have the option of simply providing access to all objects in a schema.

Object ownership is also an important concept related to object privileges. When a user creates a catalog object, he is the owner of that object. As the owner, he has full access to the object. He is also the only user that can grant rights for that catalog object to other users in the system. Note that the SYSTEM database user account cannot grant rights to other users because it doesn’t own the object. The SYSTEM account will have no privileges on the object until the object’s owner specifically grants the necessary privileges to the SYSTEM account. The owner must also allow the SYSTEM account to grant those rights to other users via the `WITH GRANT OPTION` or `Grantable to Others` option before the SYSTEM account can grant those catalog object rights to other users.

Understanding object ownership as it relates to the deletion of user accounts is important. When a user account is deleted, all catalog objects that the user owns are also deleted. If the user owns a schema, all objects in that schema are deleted. The same rule is true of any object privileges that the user has granted to other users. In [Chapter 6](#06_001.html#h6), we’ll focus on strategies to help you prevent the cascading deletion of objects and granted privileges, but in this chapter, we’re focused on a basic understanding of the concepts of object privileges, object ownership, and user deletion.

To help further your understanding of object privileges and how users are given access to catalog objects, note the following considerations:

*   When you create a user, the system generates a schema matching the user name. The user is the only owner of this user schema.

*   When a user creates a schema using the `CREATE SCHEMA` SQL command, that user is the owner of that schema.

*   If a user is granted privileges to a schema, all objects in that schema inherit the same privileges, including the `WITH GRANT OPTION` or `Grantable to Others` privileges.

Object privileges play an important role in the overall SAP HANA security model. They govern access to catalog objects and the types of actions users can perform on those objects using SQL commands. In the next section, we’ll look at how you can govern access to the data stored or presented through catalog objects using analytic privileges.

### 2.1.3 Analytic Privileges

Analytic privileges govern access to data made available through SAP HANA’s information views and, in some cases, catalog or database views. Information views are development and runtime objects that convert data into multidimensional models and enrich the view with metadata elements. These metadata elements include attributes, measures, hierarchies, key columns, label columns, and counters.

The three specific types of information views are as follows:

*   Dimensional calculation views are a type of information view for logically organizing and managing reusable master data. These views reference catalog tables and define the join relationships between those tables to produce a logical master data view. Dimensional calculation views replace attribute views, as of SAP HANA 1.0 SPS 11. However, from the perspective of analytic privileges, dimensional calculation views are secured exactly the same way as attribute views.

*   Star join calculation views are a type of information view for defining star schema multidimensional models. In such models, star join calculation views join to transaction base catalog tables to produce logical data cubes that contain attribute data columns and measures. Star join calculation views have replaced analytics views, as of SAP HANA 1.0 SPS 11. However, from the perspective of analytic privileges, star join calculation views are secured exactly the same way as analytics views.

*   Calculation views are the final type of information view. These views are a diverse type of information view that can express both star schema multidimensional models and complex analysis queries. They can be designed using catalog tables or other information views. This type of calculation view exists in all versions of SAP HANA.

Database views are catalog objects that produce a dataset when queried. However, catalog views are essentially predefined queries stored as catalog objects. Catalog views are programmed using SQL statements and can express datasets based on filtering data, joining catalog tables, and joining existing catalog views. They provide basic metadata such as column names and column descriptions but don’t offer rich metadata elements such as attributes, measures, hierarchies, or column labels.

Two types of analytic privileges exist: XML-based and SQL-based. XML-based analytic privileges are the legacy type. You’ll use this kind of analytic privilege to manage access to information views and provide both simple and dynamic filtering capabilities. SQL-based analytic privileges offer you the ability to govern access to both information views and catalog database views. They also offer the ability to implement more complex filter logic using subquery statements. The ability to use subquery statements overcomes some of the limitations associated with the filter logic available within XML-based analytic privileges.

XML-based analytic privileges provide a twofold level of access. First, these privileges grant read access to the information views associated with the analytic privilege. In most security models, every information view will be associated with at least one analytic privilege. The analytic privilege is assigned to a user, subsequently granting the user read access to the data expressed through the information view. Second, data restrictions can be applied within analytic privilege to statically or dynamically filter the data based on specified filter criteria. People in the world of business intelligence call this row-level security. Rows of data are strategically filtered to restrict user access to data. For example, if an administrator needs to restrict data so that regional managers can only see records associated with their regions, he would use analytic privileges to do so.

In contrast, SQL-based analytic privileges grant twofold access to both information views and catalog views. First, they govern read access to both types of views. SQL-based analytic privileges are unique in this regard because they offer the ability to govern both information views and catalog views. Second, they offer the ability to define both simple and complex data restrictions using subquery filter logic. Note that information views are automatically registered for authorization checks when they’re activated. However, catalog views must be explicitly registered for an authorization check before their SQL-based analytic privileges are honored.

At this point, you should now have a basic understanding of how analytic privileges can be used to govern access to both information views and catalog views. In [Chapter 10](#10_001.html#h10), we’ll explore the process of creating both XML-based and SQL-based analytic privileges in detail.
