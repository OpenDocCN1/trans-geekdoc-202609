### SAP HANA Database Explorer in SAP Web IDE for SAP HANA

SAP Web IDE for SAP HANA also provides the SAP HANA database explorer where you can connect to an SAP HANA database or HDI container schema to look for and work with catalog objects at runtime. From SAP Web IDE for SAP HANA homepage, locate the file menu bar and select Tools • Database Explorer to access the SAP HANA database explorer.

Within this interface, you can add connections by clicking the large plus sign (`+`) in the pane just below the file menu bar. ## HDI Containers and Security

With the SAP HANA XSA framework, SAP HANA development occurs within a service layer called the SAP HANA Deployment Infrastructure (`HDI`). Like the SAP HANA XS or `_SYS_REPO` model, HDI containers have a design-time concept and a runtime concept, but as you’ll see, HDI has several differences. When creating an HDI container, SAP HANA will separate out a design-time container and a runtime container. The design-time container will host metadata and code representing database artifacts and applications. The design-time container is not part of the runtime SAP HANA database but is always attached to its corresponding runtime container. The runtime container represents deployed objects that have been activated in the SAP HANA database within a specified SAP HANA XSA space. A runtime container is part of the SAP HANA database, and when built, several corresponding database objects will be created.

From a security perspective, each HDI container is isolated from other containers and even from other SAP HANA database catalog objects out of the box. In general, a container only has access to runtime objects within that same container. HDI container-based roles, like repository roles in SAP HANA XS, can be created within the container and granted to developers and users. At design time, no known security exists: Design-time workspace security is decoupled from the SAP HANA database. A developer has access to all development artifacts within the design-time container assuming the code was shared with them from outside of SAP HANA. If they import that same content into their SAP Web IDE for SAP HANA workspace and have been granted access to the corresponding SAP HANA XSA managed organization or space, they can potentially modify security at runtime.

This arrangement alone poses the most pressing security concern when using HDI containers to manage HDI-based repository roles. In theory, a developer could escalate their own privileges or the privileges of other users by modifying the makeup of an HDI container-based role. In addition, a developer could modify analytic privileges that govern access to data. In our opinion, a developer should not have the ability to elevate their own privileges inside or outside a container. With the SAP HANA XS repository, you could use package organization and package privileges to prevent developers from elevating their own privileges at design time. With the SAP HANA XSA development environment, you would have to set up and manage a complex landscape of independent HDI containers to decouple security objects from development objects. This decoupling is complex because HDI containers are not aware of each other, nor do they have access to each other’s content without a significant amount of repetitive administration.

To this end, we recommend that administrators continue to manage their SAP HANA security model using the SAP HANA XS repository-based roles and continue developing SAP HANA calculation views, database objects, and other items in SAP HANA XS until SAP addresses these security concerns. This recommendation is limited to the use of SAP HANA as a business intelligence solution or where the security of data is crucial. If you’re simply managing applications like OData services or GUIs, the current security capabilities of SAP HANA XSA are probably sufficient.
