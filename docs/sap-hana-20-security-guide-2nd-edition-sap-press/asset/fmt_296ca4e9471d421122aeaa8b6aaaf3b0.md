
# Analytic Views

Analytic views are models that connect one or more attribute views to quantifiable transactions. Within analytic views, you can define measure objects to aggregate values within specific tables. The combination of attribute views and analytic views create a complete multidimensional model. These views can answer analytic questions, such as the following: What are my sales by region? Which are my top 10 customers by gross margin? What quantity did we sell in January of 2016? What is the current balance of the expense account?

Starting with SAP HANA 1.0 SPS 07, SAP replaced analytics views with a new type of calculation view: star join calculation views. Star join calculation views are calculation views with unique settings and a specific composition. When creating the view, you’ll notice the option Cube under the Data Category dropdown list and the additional With Star Join setting checkbox. If these options are selected properly, you’ll find a unique star join transformation node within the definition of the calculation view.

Star join calculation views support more advanced transformations like the use of ranking, measures from multiple tables, and unions before the star join node, which is appealing from a modeling standpoint. These views also allowed SAP to maintain a single user interface for all calculation view types. Another main difference with a star join calculation view is that their final transformation node is always a star join node followed by an aggregation node. Another unique aspect of the star join is that it is designed to join dimensional calculi on views only. In this way, a star join calculation view is almost identical to the legacy analytics view.

Nonaggregate columns within analytic views or star join calculation views can be filtered using analytic privileges. With both analytic views and star join calculation views, the attribute views or dimensional calculation views within each play a role in the analytic privilege evaluation. In general terms, a user must have access directly to the analytic view or star join views as well as their constituent attribute views or dimensional calculation views.

## Differences between SAP HANA 1.0 and SAP HANA 2.0

With SAP HANA 1.0 through SAP HANA 2.0 SPS 04, analytic views can only be created using SAP HANA Studio and cannot be created using the SAP HANA Web-Based Development Workbench editor. In addition, as SAP has transitioned the SAP HANA XS to the SAP HANA XSA platform, SAP Web IDE for SAP HANA can be used for creating SAP HANA star join calculation views.

# 10.1.3 Calculation Views

Historically, standard calculation views were the third type of information view available within SAP HANA. You could use these views to perform complex calculations, scripted calculations, and complex denormalizations of data. Given the advent of dimensional calculation views and star join calculation views, determining exactly when to use a standard calculation view can be confusing. However, without going into too much detail, the use of standard calculation views has not evolved recently.

Standard calculation views are defined with the Data Category option Cube only. The With Star Join option should not be configured in this case. In many cases, you’ll use these views to merge multiple star join calculation views or to create user-specific query type models to accommodate user demand and requirements. However, from the perspective of analytic privileges, they can also be secured like all other types of information views. Attribute columns within the final semantic node of the view can be leveraged with static or dynamic filter conditions to secure access to the data.

# 10.2 What Are Analytic Privileges?

Analytic privileges govern access to data made available through SAP HANA’s information views. Two types of analytic privileges exist: classic XML-based and SQL-based. XML-based analytic privileges are a legacy type of analytic privilege. These privileges manage access to information views and provide both simple and dynamic filtering capabilities. SQL-based analytic privileges offer the ability to govern access to both information views and catalog database views. These privileges also offer the ability to implement more complex filter logic using subquery statements, which overcomes some of the limitations associated with the filter logic available with XML-based analytic privileges.

## 10.2.1 XML-Based Analytic Privileges

Like all analytic privileges, XML-based analytic privileges provide a twofold level of access. First, XML-based analytic privileges grant read access to the information views associated with the analytic privilege. Within the SAP HANA, we refer to them as secured models. In most security models, every information view will be associated with at least one analytic privilege, which will then be assigned to a role. When an analytic privilege is assigned to a role, grantees of that role will have read access to the information views.

Second, data restrictions can be applied within analytic privileges to statically or dynamically filter the data based on specified filter criteria. In the world of business intelligence, we call this row-level security. Rows of data are strategically filtered to restrict a user’s access to specific rows of data. For example, if the security administrator needs to restrict data so that regional managers can only see records associated with their region, he’d use analytic privileges to do so.

XML-based analytic privileges provide two different types of restriction to filter data. You can define static analytic privileges using static filter conditions or dynamic analytic privileges that will dynamically look up filter conditions on a user-by-user basis. Let’s look at these options in more detail.

### Static Analytic Privileges

The methodology behind static analytic privileges dictates that an analytic privilege object be created for each unique filter scenario. For example, if your organization wanted to filter its information views for 10 different regions, you would need to define 10 different analytic privilege objects within the repository. You would probably define 10 different roles for each analytic privilege and assign user accounts one or more corresponding roles for matching filter conditions. [Figure 10.1](#10_002.html#f10.1) shows how the mapping between static analytic privileges and roles/users typically would be set up.

**Figure 10.1** Static Analytic Privileges Mapped to Roles and Users

Let’s assume that each analytic privilege filters the sales region attribute column within each assigned information view. For example, the attribute column `SALES_REGION = 'NORTH'` would be applied to the analytic privilege `AP_STATIC_REGION_NORTH`, and the `SALES_REGION = 'SOUTH EAST'` condition would be applied to the analytic privilege `AP_STATIC_REGION_SOUTH_EAST`. As shown in [Figure 10.1](#10_002.html#f10.1), each filter condition would require an analytic privilege, and each analytic privilege would require a role. Each user can be granted one or more roles.

Each analytic privilege can be assigned one or more filter conditions or restrictions. When multiple conditions are configured within the same analytic privilege, they’re executed using an AND condition, which means that all filter conditions or restrictions must be true. For example, if you configured an analytic privilege with the conditions `SALES_REGION = 'NORTH' AND SELLING_PLANT = 'Chicago North'`, only data records that fulfill both conditions would be returned when queried.
