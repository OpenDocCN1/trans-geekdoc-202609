
The SAP HANA Web-Based Development Workbench editor, hosted within the XS engine, provides an interface that you can use to build and test development artifacts. From a security perspective, you can use this interface to create and manage repository-based roles. This interface offers all the advantages of repository-based roles without the need to define repository roles using scripts and SAP HANA domain-specific language. However, you can use this interface to edit the role via a GUI or open the role file in the text editor.

You can access the SAP HANA Web-Based Development Workbench editor via a supported Internet browser. The following URLs can be customized to match the details of your environment:

*   `http://sap-hana.myhost.com:8000/sap/hana/ide/editor`
*   `http://<sap_hana_host>:80<instance_number>/sap/hana/ide/editor`

Replace `<sap_hana_host>` with the host name of the SAP HANA system in your environment. Replace `<instance_number>` with the two-digit instance corresponding to your SAP HANA system.

For secure access, the following examples should help you construct the correct URL:

*   `https://<sap_hana_host>:43<instance_number>/sap/hana/ide/editor`
*   `https://sap-hana.myhost.com:4300/sap/hana/ide/editor`

To use the SAP HANA Web-Based Development Workbench and define a repository role, the user account first will need to be granted one of the roles listed in [Table 7.1](#07_003.html#t7.1). Users only need one of the two roles to use the SAP HANA Web-Based Development Workbench.

## 7.4 Case Study: Security Administrator System Privileges

E-Corporation has contacted its lead SAP HANA security consultant and has requested help defining a series of repository roles to be used by its security team to manage security within the SAP HANA environment. Based on previous experience, the consultant recommends defining four repository roles for the security team to allow for the separation of duties within the system. This separation helps reduce both fraud and negligence within the security model. The consultant suggests that the four roles be created based on the following groups:

*   Admins responsible for managing users
*   Admins responsible for creating roles
*   Admins that manage communication and data encryption
*   Admins that manage system auditing

To help E-Corporation better understand the consultant’s reasoning, he provided a justification for each activity and why they needed to be separated from each other. In addition, he also listed the capabilities and system privileges that were required for each broad activity. In this case study, we’ll examine the consultant’s suggestions and his justifications for each.

### 7.4.1 User Management Role

The first repository role recommended by the security consultant grants the necessary privileges to provision and administer user accounts. Grantees of this role will be responsible for the following tasks:

*   Provisioning user accounts
*   Resetting user account passwords
*   Assigning Security Assertion Markup Language (SAML) and Kerberos identities

To ensure that best practices are followed and that the separation of duties is implemented properly, grantees with this role should not be able to perform the following tasks:

*   Creating or updating existing roles
*   Granting standard roles to users
*   Granting repository roles to users
*   Granting individual privileges to users
*   Managing system auditing
