
Note that the package name and object name are separated by two colons. You can also specify multiple repository objects within a comma-separated list. After the name of the repository object, you’ll need to include another colon. After the final colon, include a comma-separated list of object privileges. At the end of the list, include a semicolon to finish the line. [Listing 6.5](#06_003.html#l6.5) shows two lines of code referencing design-time object privileges within a repository role script.

```
sql object Security.Tables::adusers: SELECT, ALTER, DROP;

sql object 
 e-corp.tables::STG_CUSTOMERS, e-corp.tables::STG_PRODUCTS,
 e-corp.tables::STG_EMPLOYEE: 
SELECT, ALTER, DROP, DELETE;
```

### 6.3.4 Structured Privileges

As of SAP HANA 2.0 SPS 04, structured privileges can only be defined as standard catalog objects. No documented repository artifacts can produce a structured privilege other than an analytic privilege. As you’ll recall, an analytic privilege is a type of structured privilege that regulates access to SAP HANA information views. In generic terms, structured privileges extend beyond information views and can also provide restrictions to standard catalog views. Therefore, we only need to discuss the syntax required to include catalog-structured privileges within a repository role.

When defining runtime structured privileges within repository-based role scripts, you must start each line with `catalog analytic privilege`. Following this term, include a colon and the structured privilege name, wrapped in double quotes for avoiding potential case-sensitivity issues. Include a semicolon to finish the line, such as in the following:

```
catalog analytic privilege : "MyStructuredPriv";
```

Note that a catalog-structured privilege will be owned by the account that created it. Repository roles are activated when the system account `_SYS_REPO` is the grantor of privileges. Therefore, the owner of the structured privilege will need to grant `_SYS_REPO` the structured privilege and include `WITH GRANT OPTION`. The following example SQL statement grants the structured privilege `"MyStructuredPriv"` to the `_SYS_REPO` user and includes the `WITH GRANT OPTION`:

```
GRANT STRUCTURED PRIVILEGE "MyStructuredPriv" TO "_SYS_REPO" WITH GRANT 
OPTION;
```

This statement must be executed by the user that owns the structured privilege or by a user that was previously granted full access to the structured privilege.

### 6.3.5 Remote Source Privileges

In SAP HANA 2.0 SPS 04, remote source catalog object privileges can’t be specified within SAP HANA repository roles. We couldn’t find any documentation from SAP that provides an example, nor were we able to configure such privileges using the SAP HANA Web-Based Development Workbench editor. To all appearances, remote source privileges aren’t supported.

If you’re using SAP HANA smart data access or SAP HANA smart data integration and you need to develop a security model that includes remote source privileges, we have the following recommendations:

*   You can configure repository role privileges for individual remote source virtual tables that are published in a schema. This arrangement helps limit access to the individual remote source tables without the need for a workaround.

*   Create one or more standard roles using a technical user account and assign the remote source privileges. Grant the roles and privileges to the `_SYS_REPO` system account and include the `WITH GRANT OPTION` or `WITH ADMIN OPTION`.

*   Extend the standard catalog roles within a standard repository role.

*   Preserve all SQL statements in a repository text object, which is the only way to store SQL code in the repository. You’ll likely need to use this SQL code in upstream SAP HANA environments governed by proper lifecycle management. Remember that these repository roles won’t activate until the catalog roles have been created.

### 6.3.6 Analytic Privileges

When defining analytic privileges within repository-based role scripts, you must start each line with `analytic privilege`. Following this term, include a colon. After the colon, include the fully qualified name of the analytic privilege file. The file name must include the package hierarchy name, analytic privilege name, and `.analytic privilege` extension. The package hierarchy name and analytic privilege name will be separated by a single colon. At the end of the statement, include a semicolon to finish the line. Because all analytic privileges are owned by `_SYS_REPO`, you won’t need to grant `_SYS_REPO` privileges to these analytic privilege objects, as shown in the following example:

```
analytic privilege: <package.name> : <analytic privilege name>   
<.analyticprivilege> ;
```

The following example grants the `ap_sales_reporting_region` analytic privilege, stored in the `e-corp.sales.security` package. Remember that repository package and object names are case-sensitive:

```
analytic privilege:     
  e-corp.security:ap_sales_reporting_region.analyticprivilege;
```

In a final example, you’ll grant the `_SYS_BI_CP_ALL` system analytic privilege. This special catalog analytic privilege, when granted, gives full access to all information views defined within the repository:

```
catalog analytic privilege : "_SYS_BI_CP_ALL";
```

### 6.3.7 Application Privileges

When defining application privileges within repository-based role scripts, you must start each line with `application privilege`. Following this term, include a colon. After the colon, include the name of the application privilege. The application privilege name must include the package hierarchy name, two colons, and the name of the application privilege. For case-sensitivity purposes, the name must be wrapped in double quotes. At the end of the statement, include a semicolon to finish the line.

The following example is a single line used to grant application privileges within a repository-based role:

```
application privilege: "sap.hana.security.base::DataService";
```

### 6.3.8 Package Privileges

When defining package privileges within repository-based roles scripts, you must start each line with `package`. Following this term, include the name of the package hierarchy node. After the package name, include a single colon, then a comma-separated list of package privileges. At the end of the statement, include a semicolon to finish the line.

The following example is a single line used to grant package privileges within a repository-based role:

```
Package e-corp.sales: REPO.READ, REPO.ACTIVATE_NATIVE_OBJECTS, REPO.MAINTAIN_NATIVE_PACKAGES, REPO.EDIT_IMPORTED_OBJECTS;
```

To grant root package privileges, use the system package value of `.REPO_PACKAGE_ROOT` to represent privileges that will be applied to all packages. The following example shows the syntax needed to grant root package privileges:

```
package .REPO_PACKAGE_ROOT: REPO.READ;
```

## 6.4 Managing Repository Roles with the SAP HANA Web-Based Development Workbench

The SAP HANA Web-Based Development Workbench editor, hosted within the SAP HANA XS engine, provides an interface that you can use to manage and create repository roles.
