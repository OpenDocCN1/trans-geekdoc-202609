## 14.4 Additional Options in SAP HANA Application Lifecycle Management

In addition to the management of delivery units and the transportation of delivery units between systems, SAP HANA application lifecycle management offers a few other features that might benefit the lifecycle management of security-related artifacts. SAP HANA application lifecycle management provides the ability to use a change recording mechanism and also supports the Change and Transport System (CTS). Let’s take a closer look at each of these options.

### 14.4.1 Change Recording

Change recording is an option you can enable in the SAP HANA repository. When enabled, the initial activation of a development artifact will need to be assigned to a change list or change ID until the change list is released. The purpose of the change list is to track changes within a development artifact. Recall that artifacts are assigned to a package and that packages are assigned to a delivery unit. When change recording is enabled, delivery unit changes aren’t available for transport until they’re confirmed and released within the change management interface of SAP HANA application lifecycle management. Thus, you can’t transport a change until its individual revision is confirmed and the change list is released using the change management area of SAP HANA application lifecycle management.

When change recording is enabled, your organization will have a middle layer within the transport process. This middle layer requires that all changes be approved before they’re transported or even exported to a delivery unit file. Without change tracking, a delivery unit would be composed of the most recent changes each time the transport process executes or each time a delivery unit file exports from SAP HANA Studio. All objects within the delivery unit and package would need to be transported even if they weren’t ready. Change tracking allows the transport manager to reassign changes to different change lists. For example, let’s assume that a delivery unit contains five development artifacts. One of the five artifacts must be promoted to QA as soon as possible. However, the remaining four artifacts haven’t been validated. The transport manager can reassign the one artifact needed in QA to a new change list and then approve and release the change list for transport, thus allowing the transport manager to transport individual development artifacts within a package and delivery unit if needed.

### 14.4.2 Using the Change and Transport System

The Change and Transport System (CTS) is a utility that organizations often use to manage the lifecycle of a traditional SAP NetWeaver Application Server (SAP NetWeaver AS). CTS facilitates the promotion of development projects in the ABAP Workbench. Although independent applications, SAP HANA application lifecycle management offers integration with the CTS. When this integration is enabled, your organization can use the tools and processes available from the CTS to manage the promotion of native SAP HANA development artifacts between SAP HANA instances.

## 14.5 Summary

Managing the full lifecycle of a security model is vital for eliminating potential security vulnerabilities from your landscape. For an SAP HANA security model, the lifecycle management process involves the use of software tools, adherence to policies, and adherence to procedures. You’ll use tools such as SAP HANA application lifecycle management to ensure consistency within the model between environments. You’ll develop policies and procedures to properly test and audit your security design.

# 15 Auditing

Implementing a security model is just the beginning. You’ll also need to set up rules to record and track select changes made within the SAP HANA system. In this chapter, we’ll discuss SAP HANA’s internal auditing mechanism for recording and tracking changes by user name, client address, and other attributes.

Auditing allows organizations to configure rules that record important activities conducted within the SAP HANA system. For example, administrators can record any SQL statement issued containing the ALTER ROLE or GRANT ROLE syntax. These details are recorded to a log that can be reviewed as needed. In this chapter, we’ll discuss why you need auditing within SAP HANA. We’ll also discuss the steps required to enable auditing and define policies to record critical activities. Finally, we’ll walk you through a case study in which you’ll create auditing rules to track important changes within the SAP HANA landscape.

## 15.1 Why Do You Need Auditing?

From a technical standpoint, auditing on its own doesn’t protect the SAP HANA system from unauthorized access. However, auditing can, in many instances, determine the source of unauthorized access. In addition, auditing can serve as a deterrent to users who may want to fraudulently change the data or maliciously harm the system’s integrity. You need to implement auditing with SAP HANA for many reasons, such as the following:

*   Provide accountability

    When auditing is enabled, your organization will have accountability for the configuration, security, and object changes made within the SAP HANA system. This information can be used for a variety of purposes. Most importantly, auditing can provide your organization with insight into the events that lead to changes within the SAP HANA system. Organizations often must grant administrators significant access to the SAP HANA system. When auditing is enabled and set up properly, users understand that their actions are being recorded, making them accountable for any changes they implement.

*   Regulatory compliance

    Many organizations are subject to several regulatory compliance measures. These measures often require that systems like SAP HANA not only remain secure but also have specific auditing measures in place. Audit logs and audit rules are principal requirements for most regulations. Auditing doesn’t prevent a security breach, but it can help authorities identify the source of the breach.

*   Discourage incongruous actions

    When enabled, auditing discourages others from performing unauthorized or malicious actions within the system. The auditing mechanism records actions by user name and records information about the computer used to make the change, such as IP address, host name, and operating system user name. This information can help identify the true source of actions executed within the SAP HANA system.

*   Monitor suspicious activity

    When auditing is enabled, your organization could set up monitors that probe the audit log data for suspicious activities. For example, monitors can be developed to search for multiple sequential failed logon events. Multiple consecutive failed logons from a single source could indicate that someone is attempting to gain unauthorized access to the SAP HANA system. Monitoring the logs might be an organization’s only mechanism to stop a breach before sensitive data is stolen or the system is compromised.
