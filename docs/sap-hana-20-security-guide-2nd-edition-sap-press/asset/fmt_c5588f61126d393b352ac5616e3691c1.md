
In this chapter, we’ll introduce you to SAP HANA privileges and define several related key terms. Privileges are a major component of SAP HANA security because they control what operations a user can conduct.

Users can interact with SAP HANA in a variety of different ways. In the past, users would use `SAP HANA Studio` to develop content and administer the system. With `SAP HANA 2.0`, you’ll probably use the `SAP HANA Web-Based Development Workbench` editor and `SAP Web IDE for SAP HANA` to develop content. You’ll also use the `SAP HANA cockpit` to administer the system. Other users might interact with business intelligence tools and query the data hosted in `SAP HANA`. In other cases, `SAP NetWeaver` uses the `SAP HANA` database to help operate applications like `SAP Business Warehouse (SAP BW)` and `SAP S/4HANA`. In all cases, database user accounts are required to interact with `SAP HANA`. These user accounts are often assigned to individual people. However, you can also set up dedicated service accounts to allow an application to delegate access for multiple users to the `SAP HANA` system. To govern these interactions, user accounts must be assigned a variety of privileges.

When a user account interacts with `SAP HANA`, that user can only perform operations and actions that have been granted via privileges. Granting privileges is the process whereby a grantor assigns privileges to another user account. For a grantor to grant an individual privilege, the grantor must be granted that privilege and must also have been assigned the `WITH GRANT OPTION` or `Grantable to Others` option, an additional right that allows the grantor the ability to grant the same privilege to another user. If you’re using `SQL` to grant privileges, you’ll use the `WITH GRANT OPTION` syntax. If you’re using the graphical user interface (`GUI`) in the `SAP HANA cockpit`, you’ll see a slider button labeled `Grantable to Others`.

When you first set up an `SAP HANA` system, the first user account available will be the `SYSTEM` account. The user name of that account is just `SYSTEM`. By default, the `SYSTEM` account can create users and grant privileges to other user accounts for all the default system objects, privileges, and roles.

The first time you interact with `SAP HANA`, you’ll most likely log on using the `SYSTEM` user account. If you’re following best practices, you’ll then create new user accounts, set up a new security model, and assign that security model to new dedicated user accounts. Most organizations will then disable access to the `SYSTEM` account so that they can properly audit activities by individual users.

By definition, the various operations and actions you perform in `SAP HANA` are organized into objects called privileges. Throughout this chapter, we’ll introduce you to the five major categories of privileges available in `SAP HANA`, and we’ll also describe how privileges are properly granted to roles and users and how the system validates a user’s access. In subsequent chapters, we’ll take a much deeper dive into individual privileges and outline what each privilege authorizes; however, the goal of this chapter is to provide an overview of privileges.

## 2.1 Privileges within SAP HANA

The five major categories of privileges available in `SAP HANA` are system, object, analytic, package, and application. Each category contains individual privileges that can be granted to either users or roles. In the following sections, we’ll look at each category in turn.

### 2.1.1 System Privileges

System privileges are designed to govern various system activities that a user can perform. They are predominantly used to govern administrative actives within the `SAP HANA` database. However, some system privileges specifically govern developer activities related to the `SAP HANA` development repository and development content.

To help you better understand what system privileges govern, let’s review a few examples. Administrative system privileges include activities such as the ability to create schemas. Although each user account is assigned a dedicated schema, users cannot create additional schemas without first being granted the appropriate rights. Unless a user is granted the `CREATE SCHEMA` system privilege, that user won’t be able to execute `SQL` commands that create additional schemas. Other administrative system privileges govern a user’s ability to import and export catalog objects using the `SAP HANA database explorer` found in the `SAP HANA cockpit`. Unless users are granted the `IMPORT` or `EXPORT` privilege, they can’t perform these actions.

As you’ll discover in subsequent chapters, numerous system privileges can be granted. We’ll go through all the different privileges in detail starting with [Chapter 7](#07_001.html#h7). Now, in the next section, we’ll look at object privileges and how they govern access to catalog objects.

### 2.1.2 Object Privileges

Object privileges govern a user’s ability to both access and manipulate database or catalog objects. Database objects are also called catalog objects; some `SAP HANA` interfaces will use these terms interchangeably. In early versions of `SAP HANA`, these privileges were called `SQL` privileges. The name was appropriate because you used `SQL` statements to access and change catalog objects. Object privileges control the types of `SQL` statements that can be executed against a catalog object. A few examples of the types of `SQL` statements that object privileges govern include the following:

*   `SELECT "column" FROM "schema"."table"`
*   `EXECUTE "schema"."stored_procedure"()`
*   `DROP "schema"."table"`
*   `ALTER "schema"."table"`

When you grant object privileges, you’re specifying the types of `SQL` statement commands that can be executed against a catalog object. As in the preceding examples, you can specify whether a user can execute `SQL` statements containing syntax like `SELECT`, `EXECUTE`, `DELETE`, or `ALTER`. In [Chapter 8](#08_001.html#h8), we’ll go into more detail about the different types of `SQL` statements that object privileges govern.

In more recent versions of `SAP HANA`, object privileges can also be granted to development objects. Therefore, referring to them by the more generic term “object privileges” is more appropriate.

###### Managing Object Privileges Using GUIs

Technically, you could say that object privileges govern the types of `SQL` statements executed against catalog objects, but administrators aren’t always aware that they’re issuing `SQL` commands when interacting with a `GUI` to manage security. For example, when adding object privileges to a user via the user administration `GUI` in the `SAP HANA cockpit`, you aren’t entering `SQL` statements directly. Instead, the `SAP HANA cockpit` converts the graphical workflow of the administrator into the appropriate `SQL` statements and issues those statements to the system in the background.

Catalog objects include items such as tables, views, stored procedures, schemas, sequences, and triggers. To properly understand object privileges, you can separate them into two broad categories: First, we have schema object privileges. Schemas are catalog objects that logically contain other catalog objects. You can think of schemas as parent objects to other catalog objects. You can grant object privileges to the entire schema or to individual database catalog objects within a schema. When you grant object privileges to the schema, you’re also granting those same rights to all objects within that schema. Thus, you could say that child objects inherit the rights granted to the parent schema.
