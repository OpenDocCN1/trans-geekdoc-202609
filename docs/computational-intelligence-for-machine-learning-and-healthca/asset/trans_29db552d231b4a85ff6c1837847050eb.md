

基于 NDP 的已实现系统通常会被扩展，使其更可能与少数特定的系统或应用兼容并执行更优。关注方向主要集中于数据中心架构的领域特定应用，因为受限于功耗。系统通过适用于各自软件应用和硬件的特定模拟器进行评估。系统设计在 [Awan et al., (2017](#bodymatter-008.xhtml#b_9783110648195-008_ref_001))、([Hong et al., (2016](#bodymatter-008.xhtml#b_9783110648195-008_ref_004))、[Vermij et al., (2017](#bodymatter-008.xhtml#b_9783110648195-008_ref_011))、[Kampars et al., (2017](#bodymatter-008.xhtml#b_9783110648195-008_ref_016))、[Lee et al., (2015](#bodymatter-008.xhtml#b_9783110648195-008_ref_018))、Gao et al., (2016)、[Gao et al., (2015](#bodymatter-008.xhtml#b_9783110648195-008_ref_025))、[Das et al., (2018](#bodymatter-008.xhtml#b_9783110648195-008_ref_027))、[Lee et al., (2017](#bodymatter-008.xhtml#b_9783110648195-008_ref_040)) 和 [Lee et al., (2018](#bodymatter-008.xhtml#b_9783110648195-008_ref_041)) 中给出了基于内存处理的系统。上述架构采用了诸如混合内存立方体 (HMC)、DRAM 等元件。系统架构在 [Awan et al., (2017](#bodymatter-008.xhtml#b_9783110648195-008_ref_001))、[Acharya et al., (1998](#bodymatter-008.xhtml#b_9783110648195-008_ref_002))、[Gu et al., (2016](#bodymatter-008.xhtml#b_9783110648195-008_ref_003))、[Riedel et al., (2001](#bodymatter-008.xhtml#b_9783110648195-008_ref_012))、[Sun et al., (2018](#bodymatter-008.xhtml#b_9783110648195-008_ref_014))、[Choe et al., (2017](#bodymatter-008.xhtml#b_9783110648195-008_ref_015))、[Lee et al., (2017](#bodymatter-008.xhtml#b_9783110648195-008_ref_037))、[Kaplan et al., (2016](#bodymatter-008.xhtml#b_9783110648195-008_ref_032))、[Kang et al., (2013](#bodymatter-008.xhtml#b_9783110648195-008_ref_042)) 和 Ruan et al., (2019) 中得到启发或提出，给出了源自存储内处理的系统设计。从所有这些系统中，若干架构使用了 HDD，少量 SDD 被使用，另外 FPGA 被用于若干系统的开发。新系统可以采用具有 RAID 能力的崭新 NVMe SSD（[Gu et al., 2016](#bodymatter-008.xhtml#b_9783110648195-008_ref_003)）。上述现有框架所描绘的软件栈包含用于 NDP 架构硬件创建的软件应用、用于评估各自框架执行的模拟器，以及用于可编程硬件的程序 (EH)。

现有方案中的一些问题或挑战如下：

* 现有系统未考虑地理分散地点的多个存储单元，因而没有负载均衡机制。
* 现有框架仅针对特定类型的 ML 应用或算法进行调优。
* 在存储内处理场景下，在数据、硬件框架、处理器上下文切换和 OS 等多个阶段需要额外的安全保障。
* 需具备可扩展的系统，以实现在硬件和软件方面对应用可扩展性的支持。

## 8.5 建议的实现范式

CI 预计可通过从当代应用约束中导出 NDP 来发现解决方案集合。本节针对第 8.4.2 节中指定的问题提供预期解决方案的展望。

### 8.5.1 预计的工作 ML 范式

下面解释的框架包含两个主要组件，即软件栈和硬件栈。两个栈框架在此阐述。

#### 8.5.1.1 硬件组件

[Figure 8.3](#bodymatter-008.xhtml#b_9783110648195-008_fig_003) 阐述了建议架构的硬件组件，其中包含处理/主机单元 (CPU)、内存和存储节点/设备，因为系统源自存储内处理的概念。

![Figure 8.3: Proposed system block diagram (components of hardware).](graphic/converted/b_9783110648195-008_fig_003.png)

Figure 8.3: Proposed system block diagram (components of hardware).

计算机 (PC) 的 CPU 可被用作处理/主机单元，以实现主机内处理的目的。内存已默认与主机系统 CPU 耦合。需要规划和实现的关键组件是存储节点。存储驱动包含两个主要部分，即控制器单元和存储内计算。在此，SSD 可用作系统中的存储单元；控制器单元由 SSD 的固件组成；存储内计算部分包括用于运行在 SSD 上安装所需数据过滤程序的编译器。需要在存储设备上加载内核以将编译器安装到 SSD 上。这可通过使用 docker 和容器的模型来实现，该模型将有助于在磁盘固件之上添加一个软件层。

#### 8.5.1.2 软件栈

从广义上讲，计划系统的软件栈包含若干为不同功能设计的程序单元，描述如下：

* Compiler: 为了编译两侧，编程元素编译器必须为系统的所有子部分实现，即主机处理系统和驱动单元或存储单元。
* Simulator: 模拟器可大幅减少执行时间，如从数小时减少到数分钟。模拟器可在系统级开发，并可用于模拟实现。
* Program unit for host side: 软件栈的这一部分将包括用于激活存储驱动编程的编程，用于在多个存储节点之间平衡负载。
* Program unit for drive side: 该组件包含应用于存储单元或节点中累积数据的计算。可能存在适用于存储的安全技术。
* Drivers for Linux kernel: 系统驱动可能像典型存储设备一样被访问，因为它可在 Linux OS 内被视为块设备。另一个驱动管理虚拟文件功能。
