![](OEBPS/images/box.jpg) `Authorized`: 两个阶段，管理权限以访问系统或系统的一部分，以及基于系统的该权限的实现

IT 部门执行 `provisioning` 过程，即在适当的身份验证和授权后激活访问。有足够的工具使访问控制过程能够设计为工作流程，消除了对纸质文档和正式签名的需求。用户将能够在线提交请求，管理层也可以在线审查和授权请求。最后，授权的请求可以转移到系统管理组进行 `provisioning`。访问控制的完整过程包括对识别、身份验证、授权和 `provisioning` 过程的强制性 `assessment`，包括记录所有初始访问请求和 `provisioning` 响应，记录访问活动（成功且适当的尝试，更重要的是，不成功且不适当的尝试），以及对整个过程的定期 `audits`。

与任何与 IT 相关的主题一样，缩写词和“流行语”层出不穷。许多组织都瞄准了 `single sign-on` 的概念，承诺为用户和 IT 系统管理员简化跨组织系统的访问过程。这意味着单个 ID 和密码（以及其他限定条件）可用于访问任何或所有组织系统和服务。它还可以减轻访问控制过程的行政负担。但是，如果用户未能断开会话，可能会导致滥用，从而允许其他个人进行开放访问。一些 IT 和 IS 专业人员更喜欢 `simplified sign-on` 的概念，它为所有系统使用单个 ID 和密码组合，但对每个系统使用单独的身份验证步骤。单一或简化的登录机制可以是组织身份管理方案的一个组成部分，其中对大量用户群进行集中控制至关重要。同样，人为活动是任何身份验证方案中最普遍的故障点。

另一种可用于将大型系统中不同组件的访问隔离开来的访问机制是基于角色的访问控制。该过程由 Dr. Ravi Sandhu ([http://profsandhu.com/](http://profsandhu.com/))、他的学生和同事开发，近年来已得到完善并更广泛地使用（参见 [Figure 16.3](#9781466508507_epub_c16_r1.htm#fig_16.3））。它现在作为 ANSI 标准（美国信息技术国家标准，2004 年）存在。

**From the ANSI INCITS Standard**

Core RBAC 模型元素集和关系在 [Figure 16.3](#9781466508507_epub_c16_r1.htm#fig_16.3) 中定义。Core RBAC 包括五个基本数据元素集，称为 `users` (USERS)、`roles` (ROLES)、`objects` (OBS)、`operations` (OPS) 和 `permissions` (PRMS)。RBAC 模型整体从根本上定义为单个用户被分配到角色，权限被分配到角色。因此，角色是命名单个用户和权限之间多对多关系的一种手段。此外，Core RBAC 模型包括一组 `sessions` (SESSIONS)，其中每个会话是用户与分配给该用户的已激活角色子集之间的映射。

RBAC 的核心是角色关系的概念，围绕该概念，角色是一种用于制定策略的语义构造。\[[Figure 16.3](#9781466508507_epub_c16_r1.htm#fig_16.3)\] 说明了 `user assignment` (`UA`) 和 `permission assignment` (`PA`) 关系。箭头表示多对多关系（例如，一个用户可以被分配到一个或多个角色，一个角色可以被分配到一个或多个用户）。这种安排为将权限分配给角色和将用户分配给角色提供了极大的灵活性和粒度。如果没有这些便利，由于对可以与用户和资源关联的访问类型的控制有限，用户可能被授予超过所需资源访问权限的危险性会增加。例如，用户可能需要列出目录和修改现有文件，而无需创建新文件，或者他们可能需要将记录追加到文件而不修改现有记录。控制对资源访问的灵活性的任何增加也加强了最小特权原则的应用。

该模型（[Figure 16.3](#9781466508507_epub_c16_r1.htm#fig_16.3））本身相当简单，但在大型组织和复杂系统中实现可能很困难，例如，单个实现机制可能无法适应所有 COTS 系统。结构化信息标准促进组织 (OASIS) \[32\] 已开发了一种使用名为 XACML \[33\] 的 XML 适配的实现机制，专门用于访问控制系统。RBAC 对用户访问和授权提供了更严格的控制，并减少了网络漫游的机会，这种情况经常发生在医院和其他医疗中心等组织中，其中个人信息是信息资源的主要组成部分。对核心模型的改进包括使用控制（限制数据的收集和使用方式）和时间约束（防止在特定每日时间段内或超过特定日历时间范围内访问）。

越来越多的系统正在开发具有基于 Web 或 Web 门户界面的系统，既面向系统的内部用户，也面向外部用户。这增加了数据泄露的另一个关注领域，因为设计不良的 Web 界面可能会引入大量漏洞，尤其是当天真的开发人员使用生成现成界面的快速开发工具时。IS 必须坚持适当的 Web 界面安全实践，以关闭通过多个潜在漏洞（URL 字段、数据输入和数据库查询的输入字段）传递 SQL 命令的机会。必须对 Web 设计进行适当审查，以持续关注 Web 漏洞 \[34\]。
