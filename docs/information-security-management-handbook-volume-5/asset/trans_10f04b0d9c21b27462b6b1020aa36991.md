

在大多数环境中，实施白名单时，文化必须随用户行为而改变。如前所述，用户不应被允许以管理员权限操作，也不应被允许作为正常操作的一部分更改白名单策略。对于大多数用户，不应授予更改白名单策略的能力；对于那些例外用户，其正常登录不应允许更改这些策略。这实际上是另一种确保最终用户无法自行安装或更新应用程序的方式，并代表了大多数环境中工作方式的转变。这种影响将以意想不到的方式显现，最好的做法是提供一种手段，以快速且轻松地响应用户关于新应用程序或更新应用程序的请求。这种需求最意想不到的形式可能是需要安装或更新小程序或其他基于 Web 的控件；例如，大多数在线协作工具都依赖于此类组件，最终用户往往会在最不合适的时刻发现自己无法安装它们。快速介入、临时安装小程序/ActiveX/插件、确定策略更改，然后将该策略推送到所有终端，通常是解决此问题的最佳方式，但不同的白名单解决方案将提供不同的选项来处理此类短周期请求。另一方面，所有软件安装都需要经过审查流程（无论多短）这一事实，有助于保持对桌面配置的控制，并防止不仅引入恶意软件，还防止引入不适合工作场所或盗版软件。

# 何时不采用白名单

有几种类型的用户和用户环境不适合采用白名单方法。家庭用户不适合使用白名单；事实上，当今市场上没有面向消费者的白名单产品。确定起始策略并维护它（包括补丁管理以及对策略更改进行适当审查）这两项挑战，超出了几乎所有家庭用户的能力范围。此外，使用双重登录（一个用于日常使用，另一个用于更改白名单策略）的原则不仅不太可能被典型用户遵循，而且也不符合面向家庭的 Windows 版本的运行方式。除此之外，还存在排查错误策略设置影响的挑战，以及正确管理白名单系统所需的对应用程序工作原理的基本熟悉程度。相比之下，从普通用户的角度来看，常规防病毒产品只需安装后无需管理即可。（直到发布有缺陷的签名为止。）

其他不适合使用白名单的环境是正在进行开发工作的环境。每个新构建的可执行文件都会有不同的签名，因此开发人员将无法进行大部分（或任何）测试，除非他们不断以受信任用户身份运行（这违背了白名单的整个意义），或者不断将新可执行文件添加到现有的允许应用程序策略中。理论上可以配置白名单，使其将编译器识别为受信任代理，但这有时说起来容易做起来难。

# 评估白名单产品

在撰写本文时，白名单产品领域已相当成熟，尽管从年份来看相对年轻。一家主要出版物最近对基于文件的白名单产品进行了比较，给每个评审产品都打了高分，虽然有一款产品脱颖而出，但没有一款被认为是劣质产品。（就大部分而言，基于调用的白名单似乎已被边缘化，仅用于需要极端安全性和保障的情况，原因如前文所述。）值得注意的是，随着 Windows 7 的推出，Windows 原生具有一种白名单功能：`AppLocker`。

在选择（甚至评估）任何技术解决方案之前，识别需求至关重要。这一点无论如何强调都不为过，尤其在涉及白名单时。除非明确需要或期望哪些功能、特性和特征（以及两者之间的区别），否则就无法正确满足这些需求或期望。这一点在白名单领域尤其正确，因为初始规划和准备比大多数其他技术更为重要。话虽如此，在评估白名单产品以满足这些需求时，可以比较许多组件/属性。

可评估的白名单功能的第一个方面是可管理性。终端代理有能力完全使系统或应用程序失效；如果没有适当管理整个白名单解决方案的手段，就有可能在整个环境中造成混乱。此外，随着策略的演变，应该有一种方法来跟踪更改或将其拆分为组件。一个示例是特定策略禁止执行某些应用程序（如 iTunes，或公司可接受使用政策禁止的其他应用程序），但该策略可以独立于管理每个终端的单独策略。其他需要考虑的重要事项包括报告功能以及获取终端代理整体状态的可靠可见性的能力。在非常大的环境中，将信息（如受控终端列表）组织成可管理的组至关重要。想象一下，在排查问题时，需要在成千上万或数万个系统的列表中查找特定系统，那会是什么样子。在确定管理功能的需求时，考虑需要或希望收集哪些信息，以及哪些形式的控制应集中化。

部署是另一个因素。最佳解决方案将能够从管理控制台远程部署到终端。问题则变成如何确定哪些代理未能正确部署（由于所有白名单解决方案都会挂钩内核，已感染终端的内核挂钩恶意软件可能是此原因），并解决该问题。自动发现（无论是通过网络发现还是从 Active Directory 提取信息）非常有帮助；确保有一种方法可以识别不应安装白名单代理的系统，如果有理由相信此类系统会存在。否则，使简单快速部署成为可能的同一功能，也会在不打算接受白名单控制的机器（例如开发系统）被过度热心或粗心的管理员强制实施时造成问题。这可以通过将此类系统放入管理系统中的特定组织单元，或通过应用不强制执行白名单控制的策略来实现。
