

拥有一种用于表达系统配置问题的标准语言，在该领域能带来诸多好处。首先，单一的配置规范只需编写一次。此时，它可以被任何配置管理产品所使用。其次，组织可以更轻松地开发和维护自己的配置标准，因为这只需要学习一种语言，而无需学习特定于某个产品的语言。最后，如上述某些情况所示，将语言与产品分离，可以为产品供应商提供更广泛的内容库，并使他们能够更专注于功能和特性。

# 相关 OVAL 功能

*Authoring Tool*—组织可以利用 Authoring Tool 来协助开发配置检查内容。最终用户可以利用 Authoring Tool 来协助开发他们自己的检查。

*Definition Repository*—当创建最佳实践配置，或建立配置策略时，验证给定系统是否按此配置的检查逻辑可以表示为一组 OVAL 定义，并发布在 Definition Repositories 中。供应商随后可以利用来自多个组织的这些 Definition Repositories，作为其产品的输入。IT 人员可以利用并定制最佳实践配置检查内容，以满足其自身组织的需求。[^(\*)](#9781466508507_epub_c06_r1.htm#ch6-ftn34)

来自多个工具的库存和配置信息可以通过标准 SCAP 枚举和检查清单，以及新兴的标准化报告功能轻松关联。关联的结果可以在单个组织内或整个企业范围内聚合，以提供关于存在哪些网络；哪些设备、电路和人员驻留在网络上；以及这些资产如何配置的统一、可共享和可用的决策信息。SCM 计划将扩展当前的 SCAP 规范，超越收集 DoD 资产的安全态势，进而识别和实施推荐的对策。IAVMs、CTOs 和其他策略变更将变为由配置评估工具使用的机器可读文件，用于自动识别受影响的资产，并由修复工具使用，用于自动实施所需的修复操作。SCM 将可在企业中部署，并在多层基础设施环境中运行。如图 1 所示，国家级安全配置策略及相关系统安全检查清单（例如体现在管理和预算办公室联邦桌面核心配置中的那些）将作为 DoD 系统的基础，但将在每个层级根据需要进行定制，以满足特定的组织和操作要求。SCAP 检查清单记录在标准 XML 中，因此检查可以轻松添加、删除或修改。组织将使用经过 SCAP 验证的工具定期使用检查清单，以确认系统按预期得到保护。NIST 维护和分发高级安全控件的映射，这使工具能够自动生成合规性证据。合规性证据和库存配置评估结果将通过 DoD 基础设施上报，提供对 DoD 系统安全态势越来越广泛的视图。”[^(\*)](#9781466508507_epub_c06_r1.htm#ch6-ftn35)

她在这里用“关联”一词触及了一个关键点，虽然我相信她最初指的是 SCAP 套件之间的交互，但也很清楚她“理解”在社区和组织高层就标准和实践的对齐（在可能的情况下）进行积极协作的重要性。她提到的涉及负载平衡的松耦合、紧集成网络，说明了需要完成的工作，这清楚地说明了这一点。她特别指出：

“SCM 计划将扩展当前的 SCAP 规范，超越收集 DoD 资产的安全态势，进而识别和实施推荐的对策。”[^†](#9781466508507_epub_c06_r1.htm#ch6-ftn36)

考虑到要使之成为现实所涉及的大量人员，这是一个相当有力的声明。同时，这正是我们需要达到的地方。当你将这些概念、MITRE 网站上的 SCM 用例，以及我们对 IF-MAP 和涉及它的用例的了解提升到下一个层次时，你会得到一个类似于 Steve Hanna 与一家对这类标准交互的成功至关重要的政府组织成员之间对话延续的东西。他们写道：

“目前，我认为它们可以被视为互补的。存在一些重叠，尤其是关于 CPE 和 OVAL，但重叠只是部分的。我可以想到几个 PA-TNC 和 SCAP 可以一起使用的用例；有时在不同层级，有时在同一层级协同工作。我只列举两个这样的案例：

1. 分离层：态势验证器可以使用 OVAL 和 XCCDF 来评估和/或向企业级安全管理框架报告态势。与设备的通信将是纯 TNC。目前该场景的唯一障碍可能是缺乏允许编写定义并从 TNC 态势传递特征的 OVAL 模式。

2. 交错层：能够通过 PA-TNC 报告 OVAL 测试结果将很有用。我认为可以将客户端对 OVAL 测试的合规性状态视为该客户端的一个属性。我不太清楚 PA-TNC 将如何传达这一点，但这当然看起来是可能的。”（Steve Hanna，个人通信，2010 年 5 月/6 月；匿名政府雇员，个人通信，2010 年 5 月/6 月。）
