

# 清楚建立信息所有权

清楚建立各部门拥有和使用的信息是另一项重要交付成果，应在非结构化数据访问的开发中使用。这可以作为文档保留系列的附录添加，并应列出每个部门的三类内容类别。更具体地说，这三类应包括该特定部门拥有的内容类别（a）、所有部门拥有的内容类别（b）以及该特定部门使用的内容类别（c）。拥有某内容类别的部门也应是负责根据文档保留系列保留或销毁该内容类别内文档的部门。可通过考虑“文档落入谁手中”（S. Murchison，个人通信，2009 年 1 月）来区分由某部门拥有和使用的内容类别。例如，假设人力资源部门创建了一个显示特定项目预估成本的商业案例。一旦商业案例获批，也许公司的标准做法是采购部门保留最终签署的副本用于预算目的。在这种情况下，商业案例“落入了采购部门手中”。在这种情况下，采购部门是商业案例内容类别的所有者，而人力资源部门只是使用该类别。还有其他文档似乎落入每个部门手中，并被视为由所有部门拥有。由所有部门拥有的文档可能包括政策、表格以及其他非特定部门类型。组织内信息技术（IT）部门的内容类别分组示例可能类似于[图 15.1](#9781466508507_epub_c15_r1.htm#fig_15.1)中列出的内容。

# 敏感性处理级别和程序

最后，为了制定全面的非结构化数据访问策略，应作为数据治理计划的一部分建立清晰的敏感性处理级别和程序。这些是用于定义文档敏感性以及此类文档应如何作为数据分类模型的一部分进行处理的分类级别（Whitman & Mattord, 2008, 270）。清晰的敏感性处理级别对于指导员工在组织内可接受地使用机密信息，以及帮助正确使用非结构化数据访问结构是必要的。一个简单的数据分类模型示例可能包括“公共”、“仅限官方使用”、“敏感”和“机密”等级别。在这种模型中，“公共”文档的规范是任何可向公众发布的文档，例如新闻稿。“仅限官方使用”可能表示不特别敏感但应保留在组织内的文档，例如内部通信。“敏感”文档可能表示被认为包含重要信息的文档，如果泄露给公众，可能会使公司尴尬或损害市场份额。最后，“机密”信息可能表示极度机密的信息，可能会严重损害公司的利益（Whitman & Mattord, 2008, p. 271）。

# 确定访问要求

一旦数据治理计划已启动，并且制定非结构化数据访问策略所需的所有交付成果均已完成，策略开发的第二步即可开始。第二步是确定必须考虑的所有访问情况。由于每种信息的访问要求最好由处理该信息的人员理解，因此此步骤应由各部门单独完成。作为数据治理计划一部分建立的部门代表应负责协调其部门的此步骤。此外，虽然每个部门将单独完成此步骤，但所有部门应使用相同的方法来完成任务，以确保整个企业的一致性。

在协作型商业文化中，确定信息的访问要求可能很困难。信息需要在许多部门之间共享，但也需要得到适当的保护。与其从 DAC、MAC、RBAC 或 ABAC 等已知的访问结构方法入手，我建议检查信息以了解每种文档实际上需要哪种安全性。可以通过提出以下问题来确定所有访问要求：谁需要访问哪些信息？需要访问多长时间？矩阵可能有助于确定所有可能的访问情况。我建议用于确定谁需要访问哪些数据的矩阵示例是一种同时检查组织内垂直和水平访问平面的矩阵。在这种类型的矩阵中，组织的管理层级可以垂直列出，而部门分组可以水平列出，如[图 15.2](#9781466508507_epub_c15_r1.htm#fig_15.2)所示。在本文中，此矩阵将被称为访问要求矩阵。

# 访问要求矩阵应用

使用访问要求矩阵，可以根据内容类别所需的访问级别对其进行映射，类似于基于属性的访问控制（ABAC）方法，其中访问由属性决定。当然，矩阵中列出的垂直和水平访问级别将因公司的组织结构而异。为了限制复杂性，应为每个部门使用单独的访问要求矩阵。为了演示这一概念，我将使用之前举例说明的 IT 部门。请记住，示例 IT 部门拥有的内容类别包括系统开发文档和系统维护文档。假设这两种内容类别在 IT 部门的所有部分和所有个人之间共享。此外，假设部门内部及上级的所有级别都可以访问这些类别。假设除了在部门内共享的系统开发和系统维护文档外，还存在必须由其他部门员工访问的系统维护文档。例如，用于维护财务应用程序的文档可能需要由组织财务部门的员工访问。为了满足这两项访问要求，系统开发和系统维护文档可以按[图 15.3](#9781466508507_epub_c15_r1.htm#fig_15.3)所示放置在矩阵中。[图 15.3](#9781466508507_epub_c15_r1.htm#fig_15.3)中的灰色箭头已添加，以演示根据矩阵中的位置，哪些垂直和水平级别应有权访问这些内容类别。
