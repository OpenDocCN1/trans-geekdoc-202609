

当站在商户位置时，持卡人在销售点（`POS`）输入其个人识别号码（`PIN`），该号码会立即被加密。借记卡授权请求消息包含加密的 `PIN`，发卡行将使用它来帮助验证持卡人。用于在 `POS` 终端内加密 `PIN` 的 PIN 加密密钥通过 `KSI` 进行标识。当收单行从商户处接收到授权请求时，PIN 加密密钥由 `KSI` 唯一标识。收单行将来自 `POS` 终端密钥的加密 `PIN` 转换为具有不同 `KSI` 的另一个 PIN 加密密钥，以便授权请求可以转发到中介金融网络。该网络还将加密的 `PIN` 从与收单行共享的密钥转换为与发卡行共享的密钥，该密钥具有另一个 `KSI`。当发卡行通过金融网络从收单行处接收到授权请求时，PIN 加密密钥再次由 `KSI` 唯一标识。

`KSI` 不仅标识授权请求中使用的 PIN 加密密钥，还指示密钥的相关属性。这些属性包括加密算法、密钥长度和密钥所有者。此外，由于 `KSI` 存在于每个请求消息中，当 PIN 加密密钥更改时，接收方可以确定该特定消息是使用之前的密钥还是当前密钥。通过这种方式，PIN 加密密钥可以保持同步，甚至可以快速更改而不会中断授权流量。

# 隐式加密密钥

`EncryptedData` 类型传输加密数据但不提供任何密钥管理。其内容加密密钥被假定为先前建立，并且进一步假定密钥永远不会更改。与 `NamedKeyEncryptedData` 类型不同，`EncryptedData` 类型不提供任何机制来保持加密密钥同步。由于密钥分发与实际密钥使用解耦，更改密钥的唯一实际方法是关闭应用程序，建立新密钥，然后重新启动应用程序。有些系统确实以这种方式执行密钥更改。

# 证书管理

公钥证书通过数字签名封装信息，将非对称公钥与订户的身份以及颁发的证书颁发机构（`CA`）绑定。订户的内容签名可以通过订户证书中的公钥进行验证。`CA` 的证书签名可以通过 `CA` 的公钥进行验证。通常使用 `CA` 层次结构，即签署并颁发订户证书的 `CA` 在另一个由上级 `CA` 签署的证书中拥有自己的公钥。[图 23.10](#9781466508507_epub_c23_r1.htm#fig_23.10) 描绘了一个示例。

![](OEBPS/images/fig_23.10.jpg)

![](OEBPS/images/line-2.jpg)

**图 23.10 公钥基础设施。**

订户证书包含订户的公钥，该公钥由下级 `CA` 签署。下级 `CA` 签名使用下级 `CA` 的公钥进行验证。下级证书包含下级 `CA` 的公钥，该公钥由根 `CA` 签署。根 `CA` 签名使用根 `CA` 的公钥进行验证。根 `CA` 证书包含根 `CA` 的公钥，该公钥由其自身签署并由其自身验证。因此，根 `CA` 证书是所有其他证书和公钥的信任锚。每个实体维护自己的私钥。

证书包含有效期，即“不早于”日期和“不迟于”日期。证书在“不早于”日期之后才有效，并在“不迟于”日期之后失效。非对称密钥（如任何加密密钥一样）有其有用的生命周期，不应在其生命周期结束后使用。但是，有时证书需要在其“不迟于”日期之前被吊销，因此 `CA` 通常会发布 `CRL`。因此，信赖方不仅需要验证证书的数字签名和有效期，还需要检查当前的 `CRL` 以确保证书仍然有效。并非每个 `CA` 都提供 `CRL`，这被视为“负面”文件。有些 `CA` 使用在线证书状态协议（`OCSP`）技术提供证书状态，该技术提供由该特定 `CA` 颁发的证书的当前状态。

# CMS 配置文件

`CMS` 提供多种不同的数据保护方法，包括数据机密性、数据完整性和数据身份验证，更不用说“分离”数据选项了。因此，`CMS` 不能“原样”使用，而必须开发一个配置文件来阐明 `CMS` 对象的使用方式。配置文件定义了 `CMS` 内容类型的封装顺序，以及发起方（或签名方）生成对象和接收方验证对象的规则。当对象在消息协议中使用时，通常配置文件还会提供用例、操作规则和异常处理。还有针对其他 `CMS` 对象的高级 `CMS` 用法，这些对象未在 `CMS` 中定义，但其内容类型可以被采用或调整。
