

为了向 IPv4 网络发送 IPv6 传输，或者反之，有三种方法可以实现该过程：双栈过渡机制（DSTM）、隧道和转换。冒着“抢走缓解部分风头”的风险，在 DSTM 中，“双栈”是过渡到 IPv6 的首选方法（GAO, 2005）。安全问题是，由于两个 IP 栈同时运行，组织更容易受到漏洞的影响。因此，第二个问题是，运行双栈时有多少可用路由器资源？具体来说，必须维护两个 IP 路由表和路由。

目前有几种可用的隧道方法。

1. `Automatic tunneling`：一个 IPv4 地址映射到一个 IPv6 地址（Beijnum, 2006）。

2. `6over4`：RFC 2529“在没有显式隧道的情况下通过 IPv4 域传输 IPv6”，它使用端口 41（Shelton, 2006）。

3. `Intra-Site Automatic Tunneling Addressing Protocol (ISATAP)`：使用非广播多点接入（NBMA），是一种自动将站点上的 IPv6 主机与 IPv4 网络互连的机制（Beijnum, 2006）。

4. `6to4`：一种自动将 IPv6 站点与 IPv4 网络互连的过程（类似于 ISATAP，但允许站点之间的隧道）（Beijnum, 2006）。

5. `Teredo`：一种 Microsoft 实现，它使用 UDP（即端口 3544）（Microsoft, 2007）。

自动隧道的问题是，它接受来自全球 IPv6 网络的任何人发送的数据包。大多数“主机”计算机位于边界网络防御（即，入侵检测系统（IDS）、防火墙、代理等）之后，而自动隧道只是允许一个直接通往主机计算机的“后门”通道。Chapple (2005, para. 7) 就隧道问题写道：

然而，迁移中固有的最大风险之一是使用隧道协议来支持向 IPv6 的过渡。这些协议允许将 IPv6 流量封装在 IPv4 数据流中，以便通过不合规的设备进行路由。因此，您网络上的用户可能在您准备好在生产环境中正式支持 IPv6 之前，就开始使用这些隧道协议运行 IPv6。

关于隧道问题的另一点说明：Cisco 开发了一种名为通用路由封装（GRE）的隧道协议（Beijnum, 2006）。该协议允许通过 IP 隧道传输除 IPv6 以外的协议（Beijnum, 2006）。

Teredo 特别令人担忧，因为它允许向主机计算机发送 UDP 数据包，并基本上将其变成 IPv6 世界中的路由器；换句话说：“芝麻开门”（Microsoft, 2007）。还应该提到，在安装了 IPv6 的 Windows XP 下，“如果可用公共 IPv4 地址，系统会自动设置 6to4 伪接口”（Beijnum, 2006, 36）。

转换技术“引入了与第三方的自动隧道以及额外的 DoS 向量”（Convery & Miller, 2004, 20）。Beijnum (2006) 指出，IPv4 和 IPv6 之间的转换是三种过渡技术中最具争议的一种，并带来了与 NAT 相同的问题，而 IPv6 本应消除 NAT。

# 路由/协议问题

IPv6 对路由器和主机都带来了一些安全挑战。IPv6 已消除 IPv4 的地址解析协议（ARP），改用 ICMPv6 的邻居发现（ND）功能执行类似的过程（Convery & Miller, 2004）。当系统或主机想要在同一子网上发送消息时，它需要“链路地址”（即 IPv4 的 MAC，但有了新名称）（Beijnum, 2006）。ND 允许主机发现其他“链路地址”，但在“源”处。IPv6 还引入了“无状态自动配置”，因此必须允许一些 ICMPv6 流量通过，以便获得一些合理的功能（Convery & Miller, 2004）。“这种去中心化的\[无状态自动配置\]方法从系统管理角度来看可能更容易，但对于负责跟踪网络资源使用（和滥用！）的人来说，它带来了挑战”（Chapple, 2005, para 8）。无状态自动配置消息可以被“伪造”，这是一种 DoS 形式（Convery & Miller, 2004）。最后，另一个需要注意的功能是，“IPv6 主机默认执行无状态地址自动配置，并根据相邻路由器发送的路由器通告消息中的以下字段执行有状态地址自动配置”（Microsoft 2008, 78）。

Beijnum (2006) 指出，RFC 2461 制定了一种方法来规避远程黑客发送的 ICMPv6 消息。该过程涉及在单个子网上使用 ND 和其他 ICMPv6 消息，将源主机的跳数限制设置为 255（Beijnum, 2006）。远程用户不可能向目标发送跳数为 255 的 ICMPv6 消息，因为路由器在路由过程中会减少该数字（Beijnum, 2006）。问题是，其他 IPv6 协议，如 RIPng、OSPFv3 和 DHCPv6，没有实施 RFC 2461 程序。

鉴于前面讨论过的“链路本地地址”带来的担忧，有可能在管理员不知情的情况下，让系统加入本地子网。ND 还有其他关键服务会带来安全问题（例如，前缀发现，主机可以了解本地子网上哪些 IPv6 前缀处于活动状态，或者使用“重定向”将主机指向不同的路由器，因为通往目标提供了更好的路径）（Microsoft, 2008）。此外，随着扩展头的引入，没有标准，IPv6 防火墙无法处理各种扩展头。配置为过滤 IPv6 的防火墙和路由器将面临两难境地：要么“允许数据包”，要么丢弃它，因为它是未知实体（Beijnum, 2006）。

# 侦察

Warfield (2003) 和 Convery and Miller (2004) 指出，由于 IPv6 相当大的地址空间和相关的子网大小（即，默认 2^(64)），几乎不可能扫描 IP 范围。但是，基于特定供应商的 EUI-64 值（即，想想 MAC 值）扫描 /64 子网，缩小了范围，只需通过 DSL 调制解调器连接花费几个小时即可完成大幅缩小的扫描（Beijnum, 2006）。

# 培训不足

Warfield (2003) 写道，网络管理员经常忽视 IPv6，在运行 IPv4 网络时不认识它的存在，并且缺乏管理 IPv6 所需的技能、培训和专业知识。安全最好通过分层过程来实施。“不要把所有鸡蛋放在一个篮子里”的比喻对网络安全专业人员具有重要的意义和理解。当然，没有经过培训的人员来识别 IPv6 带来的风险或能力是一种风险，因为正是这些人，组织通常依赖他们（即，网络管理员和 IA 工具）来支持组织的网络及其 IT 目标。

# 病毒/蠕虫等

IPv4 中存在的大多数病毒，那些不扫描漏洞的病毒，在 IPv6 中也存在相同的问题和困难。这是因为 IPv4 的上层（即，OSI 模型）安全问题在 IPv6 中几乎是相同的。一个细微的区别是，针对易受攻击系统的扫描技术更有可能减缓病毒传播（即，由于 IPv6 的大地址空间）（Beijnum, 2006）。此外，困扰 IPv4 的应用程序漏洞在 IPv6 中也是相同的。最后，支持负责运行 IPv6 的系统管理员所需的现有 IDS（即，与 IPv4 相同的功能）、防火墙和其他 IA 工具仍然稀缺，这在管理 IPv6 网络时带来了各种问题。
