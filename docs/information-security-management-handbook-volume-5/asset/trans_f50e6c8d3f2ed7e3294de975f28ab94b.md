

CMS 将数据对象定义为“内容类型”，在大多数情况下，所有 CMS 标准都相似，但并非所有内容类型在不同标准中都受支持，且内容类型在 CMS 20 年的历史中不断演变。本章后半部分为每个标准提供了 CMS 变更历史。本章主体部分概述了不同的内容类型。由于对象标识符（`OID`）是 CMS 的基本要素，下一节将概述 `OID`。

# 对象标识符

`OID` 是由一个或多个数字组成的序列，其中每个位置和值都提供关于相应对象的信息。`OID` 有多种表示形式，例如以下示例都表示同一个对象标识符：

a. `iso(1), member-iso(2), us(840), rsa-data-security(113549) pkcs(1), pkcs7(7)`

b. `1.2.840.113549.1.7`

c. `{1 2 840 113549 1 7}`

第一种表示形式（a）既包含每个值的定义，也包含括号中的实际值，而第二种（b）和第三种（c）表示形式仅提供位置值。表示形式（a）是技术规范中使用的更正式语法。表示形式（b）是一种简写格式，使用句点（“.”）作为每个值之间的分隔符。表示形式（c）更像是一种集合论记法格式，使用花括号并在每个值之间加空格。其他表示形式可能使用方括号或圆括号，并使用斜杠等其他分隔符。几乎任何格式都是可接受的，只要每个位置值清晰划分且可读即可。`OID` 通常会被赋予名称，例如：

d. `id-pkcs-7 OBJECT IDENTIFIER ::= {iso(1), member-iso(2), us(840), rsa-data-security(113549) pkcs(1), pkcs7(7)}`

任何 `OID` 的第一个位置定义了对象标识符注册所在的标准组织。仅有三个已分配值：“0”是国际电信联盟（ITU）标准化部门，原名 CCITT；“1”是 ISO 国际标准化组织；“2”是联合 ISO 和 ITU。每个后续位置的含义基于前一个位置。

上面提供的 `OID` 示例（`1.2.840.113549.1.7`）由六个值组成，起始于 ISO（`1`）弧。第二个位置有多个已分配值：“0”指代标准；“1”指代注册机构；“2”指代 ISO 成员（例如，美国）；“3”指代非 ISO 成员组织（例如，国防部）。其他次级位置值只能由 ISO 分配。

对于相同的 `OID` 示例，第三个位置的值为“840”，用于标识美国，因此只有美国可以在该弧（`1.2.840`）下分配进一步的位置。第四个位置的值为“113549”，用于标识 RSA Data Security 作为一家美国公司。在此弧（`1.2.840.113549`）下，只有该公司可以分配进一步的位置。RSA Data Security 在弧（`1.2.840.113549.1`）下开发了一系列 PKCS，并将 `OID`“7”分配给了 PKCS #7 `CMS Standard`。一旦弧被命名和定义，就可以使用先前的定义来定义其他 `OID`，例如：

a. `id-signedData OBJECT IDENTIFIER ::= {id-pkcs-7 signedData(2)}` 或（`1.2.840.113549.1.7.2`）

由于每个位置可以有无限个值，且位置数量同样无限，`OID` 结构既可扩展又可扩张，使得每个 `OID` 都是唯一的，任何 `OID` 都不需要重复使用，世界也永远不会耗尽 `OID`。

# 内容类型

CMS 提供六种常见内容类型：一种（`data`）是不带任何加密保护的基本构建块；另一种（`digested data`）提供数据完整性；两种（`signed data` 和 `authenticated data`）提供数据完整性和真实性；两种（`encrypted data` 和 `enveloped data`）提供数据机密性。任何内容类型都可以封装在任何其他内容类型中。这通常被描述为构建洋葱，每一层都完全包裹在另一层之中，这样可以一层层剥开洋葱，直到最终内容类型揭示数据。

[表 23.1](#9781466508507_epub_c23_r1.htm#table_23.1) 列出了六种常见类型和两种附加类型。PKCS #7 还定义了一种组合类型（`signed` 和 `enveloped data`），但未包含在 IETF 或 X9 标准中，因为 CMS 的封装特性允许此类型递归定义。X9.73 和 X9.96 提供了一种附加类型（名为 `encrypted data`），以反映金融服务行业中使用的密钥管理方法。新类型的加入是为了避免与现有 CMS 类型（`encrypted data`）产生歧义。

# 数据类型

内容类型“`data`”如 [图 23.2](#9781466508507_epub_c23_r1.htm#fig_23.2) 所示，是一个复杂组件，由两个名为 `contentType` 和 `content` 的简单组件组成。组件 `contentType` 是一个 `OID`，组件 `content` 是一个包含任何二进制数据的八位组字符串。[图 23.2](#9781466508507_epub_c23_r1.htm#fig_23.2) 显示了复杂组件 `ContentInfo` 对象，描绘为一个扁平的三维（`3D`）立方体，二维（`2D`）方框代表两个简单组件。当 `content` 为“`data`”时，`contentType` 包含适当的 `OID`，提供明确的标签，指示数据未受保护。相反，当 `content` 是加密类型（如 `EncryptedData`）时，`contentType` 包含不同且唯一的 `OID`，表示数据使用隐式加密密钥进行加密。
