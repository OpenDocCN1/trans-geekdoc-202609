

# vSwitch 安全配置建议

## NCN03

**确保“MAC 地址更改”策略设置为拒绝**

通过将 MAC 地址更改策略设置为拒绝，除了初始 MAC 地址分配的值之外，无法更改有效的 MAC 地址。这可以降低攻击者使用 VM 操作系统在向接收网络发送帧时冒充授权网络适配器 MAC 地址的风险。

## NCN04

**确保“伪造传输”策略设置为拒绝**

伪造传输默认设置为允许——这允许 MAC 地址冒充，恶意人员可以使用允许访问接收网络的 MAC 地址来发起攻击。应将伪造传输设置为拒绝，以减轻此问题的风险。

## NCN05

**确保“混杂模式”策略设置为拒绝**

在 vSwitch 上启用时，混杂模式允许连接到 vSwitch 的任何机器查看连接到 vSwitch 的所有其他 VM 关联的所有网络流量。混杂模式默认设置为拒绝，这是建议的设置。为 vSwitch 启用混杂模式的更安全方法是保留默认拒绝设置，并为仅需要以混杂模式监控的 VM 配置端口组，并将端口组设置为混杂模式，这允许端口组设置覆盖 vSwitch 设置，但仅适用于特定端口组内的 VM。

## NCN06

**确保端口组未配置为原生 VLAN 的值**

ESX 不支持原生 VLAN 的概念。当仅连接到 VMware 设备时这不是问题，但当连接到确实支持原生 VLAN 的设备时，可能会产生兼容性问题。

## NCN07

**确保端口组未配置为 VLAN 4095，除非用于虚拟宾客标记**

VLAN 标记 4095 保留用于激活虚拟宾客标记，其中 vSwitch 将所有帧传递给宾客 VM 而不修改 VLAN 标记。简单来说，仅在宾客预期处理 VLAN 的所有标记操作时才使用它。

## NCN10

**确保端口组配置有清晰的网络标签**

随着网络增长和变得更加复杂，使用与端口组用途不相关的通用标签会使故障排除变得困难。选择与端口组用途相关的有意义的端口组名称，是在网络实施早期应采用的良好做法。

## NCN11

**确保所有 vSwitch 配置有清晰的网络标签**

随着网络增长和变得更加复杂，使用与 vSwitch 用途不相关的通用标签会使故障排除变得困难。选择与 vSwitch 用途相关的有意义的 vSwitch 名称，是在网络实施早期应采用的良好做法。

## NCN12

**完整记录 vSwitch 上使用的所有 VLAN**

在记录任何网络组件之前，无法验证其安全性/配置。完整的 vSwitch 配置详细信息应包含在变更控制和配置文档中。

## NCN13

**确保只有授权管理员才能访问虚拟网络组件**

通过利用 vSphere 中可用的细粒度基于角色的控制，对网络组件实施最小权限原则和职责分离规则。

## NPN01

**确保物理交换机端口配置为禁用生成树协议**

VMware 中的虚拟交换机不支持生成树协议，因此在物理网络交换机端口上不禁用生成树协议可能会导致潜在的连接性和性能问题。

## NPN02

**确保外部物理交换机与 VST 模式下虚拟交换机之间的干线链路配置为非协商选项**

当连接到 VLAN 干线中虚拟交换机的物理交换机端口启用了协商选项时，vSwitch 会产生不必要的网络流量，因为 vSwitch 不支持动态干线协议。应选择非协商选项以减少网络上的不必要流量。

## NPN03

**确保 VLAN 干线链路仅连接到充当干线链路的物理交换机端口**

在带有 vSwitch 的 VLAN 中配置不当的物理交换机可能会导致帧丢失并可能导致流量误向。

## VSH01

**维护 vCenter 支持的操作系统、数据库和硬件**

加固底层操作系统以减轻漏洞风险。作者建议遵循 NIST 的安全技术实施指南 (STIGS)。[http://iase.disa.mil/stigs/index.html](http://iase.disa.mil/stigs/index.html)。

## VSH02

**保持 vCenter Server 系统正确打补丁**

绝大多数漏洞都有供应商补丁可用于完全减轻相关风险。在当前环境中不实施补丁管理计划，最好也只是不负责任。

## VSH03

**在 vCenter Server 主机上提供 Windows 系统保护**

在当前环境中，实施防病毒和反恶意软件解决方案仍可能使您不必要地暴露。作者建议用当前一代的白名单/应用程序控制技术来补充这些解决方案。简单来说，在虚拟领域中，您明确知道服务器上应该运行什么，因此只允许该软件（经验证后）执行是有道理的。

## VSH04

**避免用户登录到 vCenter Server 系统**

通过仅允许有明确需求使用 vCenter 服务器设施的用户登录到服务器，来实施最小权限原则和职责分离。请记住，vCenter 在您的虚拟领域中实际上是“王国的钥匙”。

## VSH05

**使用服务帐户而不是内置 Windows 帐户安装 vCenter Server**

Windows 中的内置管理帐户仅仅拥有比运行 vCenter 服务器所需的更多权限。

## VSH06

**限制 vSphere 管理员权限的使用**

通过仅将管理权限授予真正需要它来完成工作的用户，来实施最小权限原则和职责分离。

## VSC01

**不要使用默认自签名证书**

只需将自签名证书替换为来自商业证书颁发机构 (CA) 或组织 CA 的证书，就可以减轻大部分中间人攻击的风险。这是风险缓解中的易举之事，应作为任何虚拟领域部署的先决条件。
