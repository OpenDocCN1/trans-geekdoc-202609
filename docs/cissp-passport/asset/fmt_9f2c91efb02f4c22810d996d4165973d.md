## Define and apply secure coding guidelines and standards

In this last objective of Domain 8, we’re going to complete our discussion of software security by covering secure coding standards and guidelines, common software vulnerabilities, and software-defined security.

### Secure Coding Guidelines and Standards

Writing code that is free of common security flaws is the key to developing secure software. Using even the most secure development environment makes no difference if the final software product is riddled with flaws and vulnerabilities. In the following section, we will discuss common security vulnerabilities that often make it into source code if secure programming practices are not followed. Next, we’ll focus on the necessity of application programming interface (`API`) security. We’ll then take a look at secure coding practices and why they are important. Finally, we’ll briefly discuss the next logical extension of software-defined networking, which is software-defined security.

#### Security Weaknesses and Vulnerabilities at the Source-Code Level

Despite the best development efforts, even those that include a secure separate environment, code repository, and strong management practices, application source code will always have vulnerabilities. Sometimes these flaws are quite serious, and other times they are minor and only affect functionality. But even minor vulnerabilities can be chained together to lead to a greater weakness. There are several common vulnerabilities that you can easily address in source code, but other vulnerabilities may require you to dig very hard to find them.

The best way to find vulnerabilities, of course, is through testing. We discussed both static application security testing (`SAST`) and dynamic application security testing (`DAST`) in Objective 8.2. Both types of tests look for common vulnerabilities that you can identify and remedy. Most of the vulnerabilities you will encounter are related to faulty input, resource misuse (`e.g., memory, CPU, and storage space`), vulnerable functions inherent to the programming language itself, and faulty security mechanisms (`e.g., legacy or vulnerable authentication and encryption modules`). Recall from Objective 8.3 that common vulnerabilities are listed in sources such as the OWASP Top Ten and the CWE Top 25 Most Dangerous Software Weaknesses. #### Security of Application Programming Interfaces

An application programming interface (`API`) is a stand-alone piece of code, usually a module, that allows separate applications (and operating systems) to connect to each other and exchange data. The applications may have different data formats, security mechanisms (`authentication` and `encryption`, for instance), and methods of exchanging data. An `API` serves to bridge those gaps and allow seamless integration between the applications at their various levels, up to and including user interfaces. APIs can be constructed to be reusable, based on the different applications they connect to, and are often found in an organization’s code libraries, enabling developers who are building a new application to incorporate an existing API to connect the new application to legacy applications, for example.

APIs have security issues that must be addressed as well. In addition to the normal common software vulnerabilities mentioned earlier, APIs must be programmed to accept a variety of inputs and translate them to data that is secure, formatted correctly, and useful to the other application. Parameter validation is important here; the API must determine if the data or commands it is receiving from the other application or OS are correct.

#### Secure Coding Practices

There are many processes involved with secure coding. First, having a secure coding methodology that is standardized throughout the organization and required to be followed by programmers is a first step of the process. A second step is intense code review, often from peers, but also from formal review and test processes. Although secure development was traditionally not included in most software development life cycle models, it has been increasingly integrated from the beginning of those life cycles, as early as the requirements stage using modern development methodologies, such as `DevSecOps`, for instance.

Some of the more common secure software coding methodologies include the secure practices promulgated by OWASP, an independent professional organization that recommends software security methods (and publishes the previously introduced OWASP Top Ten). OWASP recommends establishing the following foundation for secure software development:

• Defined roles and responsibilities for security and development personnel  
• Adequate security training for developers  
• Implementation of a secure development life cycle model  
• Adoption of secure coding methodologies  

In addition to these overarching recommendations, OWASP also has published a Secure Coding Practices Checklist, which focuses on the following areas (adapted from *OWASP Secure Coding Practices Quick Reference Guide*, [`https://owasp.org/www-pdf-archive/OWASP_SCP_Quick_Reference_Guide_v2.pdf`](https://owasp.org/www-pdf-archive/OWASP_SCP_Quick_Reference_Guide_v2.pdf)):

• Input validation  
• Output encoding  
• Authentication and password management  
• Session management  
• Access control  
• Cryptographic practices  
• Error handling and logging  
• Data protection  
• Communication security  
• System configuration  
• Database security  
• File management  
• Memory management  

OWASP also includes in the checklist general coding practices, including some of the ones we’ve already discussed, such as the need for secure code review and testing, separate development environments, use of proven code modules and libraries, and so on.

A variety of other secure coding practices are available to the public, some developed and promulgated by independent professional organizations like OWASP, others by software or OS vendors, and still others by the U.S. government and industry standards bodies.
