
RAD evolved into a serious development methodology because other, more structured methodologies, such as `Waterfall`, `Incremental`, and `Spiral`, were too slow to keep up with the rapidly changing environment of customers. Often, by the time the software was finally developed to meet the original requirements, those requirements had changed or become obsolete due to the operating environment, technology, market, and so on. The RAD theory is that a 60 percent solution right now is better than a 100 percent solution in three years, with the understanding that over the course of iterative development, the solution would approach the final needs of the customers faster.

## Agile

Agile is more of an approach to software development than a single methodology; in fact, many methodologies follow the Agile approach. As its name indicates, Agile promotes agility in software development that is not restricted by the overuse of structured processes that can get in the way of actual development. At the same time, Agile methodologies typically provide more structure than prototyping and RAD methodologies, but the structure is geared to assist in understanding the customer’s requirements versus achieving software perfection over a longer period of time. A strength of the Agile approach is that it draws from all other methodologies and uses the best techniques in each. Agile can be incremental and iterative, but also flexible enough to adapt to the needs of each application. Agile methodologies focus on delivering small increments of functional code that are based on business need, versus delivering one large, monolithic application that may take years to perfect.

A key characteristic of Agile methodologies is a `user story`. This essentially is a use case from the user’s point of view, which states exactly what a user wants to do (function), why the user wants to do it (result), and how (performance). This user story is effective in telling the developer exactly what the end customer wants to see in the software functionality. This approach may be more effective than formal requirements development because it allows the user to express what they want in their own words.

Key Agile methodologies include

• `Scrum` This allows for development points to be reset as product features need to be added, changed, or removed; it uses a two-week development interval called a `sprint`, after which new features or changes are delivered.

• `Extreme Programing (XP)` This approach is similar to Scrum, except without the sprints and with more code review using an approach called `pair programming`, where programmers work in pairs and are constantly inputting and checking each other’s work. XP also is unique in that developers write test cases before the code is even written, so the code is constantly improved until it actually succeeds at passing the test case.

• `Kanban` Kanban was originally a production scheduling system developed by Toyota, but eventually software developers adapted it. It uses visual tracking of tasks so all team members understand what the priorities are and what they should be working on at that particular time.

## DevOps and DevSecOps

In traditional development environments, software developers and operations personnel were two separate groups, with little productive interaction between them. This often resulted in software that did not meet its customers’ requirements, was faulty, or became subject to rework. Over time, a new paradigm of combining these two functional entities during software development emerged, known as `DevOps`. Now integrated development teams consist of developers and operations personnel. These two broad areas include programmers, software engineers, IT personnel, and quality control team members. The benefit of this new paradigm is that developers and operators can work together to produce code that better meets more realistic customer requirements and can be adapted as needed when those requirements change.

Although `DevOps` is an advancement in integrating direct functional areas for producing better-performing code, it leaves out the security piece of the equation. Code still tends to be developed in a security vacuum, such that security considerations are not included in the development process. Although `DevOps` makes code better from a functionality perspective, it leaves it very vulnerable to increasingly sophisticated software attacks. A newer paradigm, known as `DevSecOps`, integrates security personnel into the `DevOps` team, allowing security consideration to be included in the development process, in the application code itself from the beginning of development, rather than attempting to add it on to a complete piece of software after the fact.

**NOTE** `DevOps` and `DevSecOps` really aren’t development methodologies per se, they are simply a method of combining personnel from different functional areas to contribute to the development process. Both can use a variety of development methodologies within the team.

## Maturity Models

A maturity model is not a software development methodology. It is a formalized model for determining how well organized, defined, and managed an organization’s development effort is. Maturity models provide a measurement or view of an organization’s software development capabilities, classifying them as loose and ad hoc on one end of the spectrum, or highly organized, defined, and precise on the opposite end. Most organizations fall somewhere in between these two extremes. The purpose of a maturity model is to give an organization a method and framework to help improve its software engineering and development capabilities. Although there are many different maturity models that span different functional areas, including security, software development, engineering, and so on, we will discuss in the following sections two key maturity models that you will need to know for the CISSP exam.

## Capability Maturity Model

A `Capability Maturity Model` (`CMM`) provides a method to evaluate an organization’s software development program along a defined spectrum of increasing effectiveness and identify areas for improvement. The maturity of an organization’s software development effort can be gauged by inspecting the quality of its management, software development personnel, training, development methodology, and, in the end, the quality of its software.

`Capability Maturity Model Integration` (`CMMI`), originally developed by Carnegie Mellon University, and now managed by ISACA, is a popular maturity model that provides measurements of the software development program in an organization. It also provides guidance on the different phases of a software development life cycle and identifies best practices organizations should be using in their software development efforts. `CMMI` consists of six maturity levels:

**0.** `Incomplete` This level is considered ad hoc with no known formal processes.

**1.** `Initial` At the `initial` level, the development effort is unpredictable and reactive to circumstances; the development effort is often over budget and behind schedule.

**2.** `Managed` At the `managed` maturity level, there are the beginnings of a management infrastructure in place to control the software development effort at the project level, using basic planning techniques and metrics.

**3.** `Defined` At the `defined` level, there are formal organization standards in place that provide structure for the software development effort.

**4.** `Quantitatively Managed` At the `quantitatively managed` level, the organization has formal processes to not only manage the software development effort, but to extrapolate and analyze data to gain efficiencies and a roadmap for more effective management.
