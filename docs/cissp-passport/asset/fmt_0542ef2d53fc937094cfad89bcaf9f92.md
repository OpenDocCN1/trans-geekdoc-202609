
A tool set used by a development team may not be standardized between organizations, or even within the same organization. Every programmer has their favorite tool set, but an effort must be made to standardize these tool sets within the organization so that standardized development methodologies and predictable results are possible. A developer’s tool set can come in many forms: customized scripts, homegrown applications, databases, spreadsheets, custom libraries, and many other nonstandard tools implemented to make a developer’s job easier. Standardizing a developer’s tool set can be difficult, but if management listens to the developers and adopts the best-of-breed tools that developers really need to do their jobs, along with incorporating a standardized integrated development environment (discussed next), it is possible. Note that these tool sets, in addition to being used for general software programming and development tasks, also typically include security functions, such as encryption and authentication mechanisms.

## Integrated Development Environment

An integrated development environment (IDE) is a suite of tools designed for code development and leveraged through a single graphical user interface. In the early days of software development, code was written strictly as sequential lines of text. Today’s IDEs allow object-oriented programming (OOP) using a visual graphical interface. IDEs support much more than simply writing lines of code by enabling developers to frequently check code for errors, execute it in a controlled environment, and test it using various built-in or customizable test cases. IDEs can be used for a variety of languages, provided the IDE supports them. Sophisticated IDEs can also be used to control access to code repositories, implement version control, and log and audit changes to code. IDEs can also include security functions and controls that can be easily implemented in the software they are used to develop.

## Runtime

`Runtime` is a name given to an environment in which code written for any platform can be executed. A runtime environment acts as a sort of miniature operating system or virtual machine container where the application, often called `portable` or `mobile code`, can run as it is natively written. You’ll most often see runtime environments used with mobile code written for web-based applications, such as Java, for example. The runtime environment serves as a layer between the code and the operating system that the code can communicate with, and in turn, translates the code’s request for resources and the responses returned from the host. Because it serves as a layer between the operating system and the code that runs within it, a runtime environment can protect both the running code from non-secure conditions in its environment, and vice versa.

## Continuous Integration and Continuous Delivery

The manner in which code is released into the production environment has become extremely critical, especially as development methodologies have changed and code is delivered to the customer more efficiently. You should understand two key delivery concepts for the CISSP exam, continuous integration and continuous delivery (CI/CD).

`Continuous integration` means that as soon as the code is developed, tested, and approved, it is integrated into the test (or pre-staged) environment. This is very much an automated process; code is developed and merged into the code repository, where a series of automated tests take place. If the tests yield good results, the automated process delivers the code into the repository and a new software version is produced. Errors are identified quickly and can be corrected much more efficiently.

`Continuous delivery` allows for a constant, incremental rebuild of software versions that can be released at any time. Again, this is far more of an automated process than traditional delivery methods, so code can be released into production almost in real time, provided it meets all the testing and acceptance requirements.

Because both of these processes rely heavily on automation, it’s important that code repositories and the automation pieces are kept secure. A popular CI/CD platform known as `Codecov` was compromised in 2021, allowing malicious actors to potentially infiltrate the code bases of any product or organization that used the platform.

## Security Orchestration, Automation, and Response

Security orchestration, automation, and response (SOAR) is a new way of managing the wide assortment of security tools, such as suites, scripts, and executables, that organizations use to manage security processes within the organization. Typically implemented as an integrated platform, SOAR attempts to bring all of the various tools under one umbrella to make them easier to manage and integrate. SOAR supports common data formats so that security information can be easily exchanged between tools; in some cases APIs are available or developed to connect one application to another.

Enabling an organization to execute the functionality of each disparate tool and receive the results through a single user interface saves time and creates efficiencies in security management. SOAR can accelerate security responses by automating standard remediations, allowing analysts to focus on higher-priority events that require human analysis. Many security information and event management (SIEM) suites can also function as SOAR platforms, although additional add-on modules may be required, or the organization may custom-build interfaces between some of its homegrown tools and the SOAR platform.

## Software Configuration Management

As its name indicates, software configuration management (SCM) is a management process. It is the process used to ensure that software is built and configured to an exacting set of standards, that it is documented, and that its versions are strictly controlled. Much of this is done through automated processes, although manual tasks and human management must be present to ensure that these automated processes work to maintain a controlled code base. Configuration management and change control were discussed in detail in Objective 7.9 and briefly in Objective 8.1, and the principles discussed in those objectives also apply to software configuration management.

Documentation and version control are likely the two most important aspects of software configuration management. Software must be documented in several respects. The code itself must be commented and thoroughly documented so that programmers who review it in the future will understand how and why the code was designed. Higher-level manuals detailing how to operate an application must also be written; sometimes security mechanisms must be documented for users or technicians.

`Version control` means that strict adherence to change and configuration control processes must be followed. Any change to the official code base must be documented and version numbers must be incremented, whether they are major or minor version numbers. The code base versions that are put into production must be separated from the code versions that are in development and test repositories. `Code synchronization`, which ensures that all working versions are synchronized with the latest approved changes, can be an issue if developers are allowed to randomly work on code without going through a formal code checkout process.
