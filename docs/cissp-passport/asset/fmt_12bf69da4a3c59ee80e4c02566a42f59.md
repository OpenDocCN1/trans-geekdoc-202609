
A code repository can be both a physical and logical secure storage area for code management. Code repositories function as a code library, where the various versions of software are stored and managed. Access control is critical for code repositories; developers should have access to development code only, while IT personnel and others responsible for actually implementing code into production environments should only have access to production code. Since versioning is a critical function of software configuration management, the ability to audit and identify changes to code must be part of any code repository system. Code in various stages, such as development, test, and production, should be “checked out” by an individual so that auditing can be implemented; changes can be locked or allowed, but attempts should be logged and audited.

## Application Security Testing

As part of the majority of SDLC models, application security testing takes place after development but before software is implemented and goes into operation and maintenance. There are several different types of testing that can take place, in addition to several testing methods. The typical types of application security testing that you will see during the SDLC include the following:

• **Unit** Tests individual pieces of code for performance and functionality.

• **Interface** Tests the interface between the code and other components of the application, as well as hardware.

• **Integration** Tests that the integration of the software application code with other system components does not reduce functionality or security in those components; this is closely related to interoperability testing as well.

• **Use case** Puts code through the paces for the various use cases that have been developed from user requirements, which ensures that the code performs its intended functionality under predefined conditions.

• **Security** Assesses the security of the software before implementation; includes vulnerability testing, penetration testing, and misuse case testing (also discussed in Objective 6.2).

Application code is tested for a variety of potential issues. These include ordinary programming flaws, known programming language vulnerabilities (such as certain unsecure functions in C++), and, of course, security issues. The following list recaps the security aspects of code testing mentioned in Objective 6.2:

• Input validation

• Secure data storage

• Encryption and authentication mechanisms

• Secure transmission

• Reliance on unsecured or unknown resources, such as library files

• Interaction with system resources, such as memory and CPU

• Bounds checking

• Error conditions resulting in a nonsecure application or system state

The CISSP exam requires you to know not only the types of application security tests and the issues tested for, but also a few of the key test methods that are used. These include both static and dynamic application security testing, as well as others, discussed next.

### Static Application Security Testing

Static application security testing (SAST) involves testing application code without actually executing it. SAST requires access to the actual source code rather than the compiled executable. SAST can be performed in several ways, including through manual or automated means. With manual SAST, the code is reviewed line-by-line by another programmer; this is a basic code review technique. Automated testing uses software suites that are specifically designed to rapidly go line-by-line through the application code to look for syntax errors, known flaws, faulty logic or sequencing, improper variable use, and many other common issues. Some of the more sophisticated software suites can look for issues such as lack of input validation, faulty function calls, and so on. Additionally, customized tests can be added to the software suites based on the needs of the organization.

### Dynamic Application Security Testing

Dynamic application security testing (DAST) is performed while the application is in production mode. Once static testing takes place, the application is tested while actually executing. Since DAST is run during code execution, it does not require access to the source code. Specific software suites used for DAST can identify a variety of issues, including hardware resource overuse, lack of interoperability with other applications or operating systems, and so on. The test suite can also create artificial error conditions to see how the software code reacts.

### Forms of Application Security Testing

Whether using SAST or DAST, application security testing has a specific goal, like unit testing or interface testing. Application security testing can take several forms, including:

• Vulnerability testing, during which known vulnerabilities in software code are discovered.

• Penetration testing, which attempts to “hack” the code using a variety of manual and automated methods, in an effort to circumvent security mechanisms. Ideally, the results of vulnerability and penetration testing are used to improve security mechanisms in the software code after the test.

• Misuse cases testing, which attempts to determine all the different ways software can be abused or misused. Misuse case testing is not always limited to security functions; it can also be used to check if users are using the software incorrectly for the functions it was intended. However, misuse often results in a security problem, such as an error (also called an exception) that may allow access to administrative privileges or the underlying operating system or hardware.

• Fuzzing is a form of misuse case testing that can be employed during security tests using both automated and manual means. Fuzzing takes nonstandard input and feeds it into the application while it is running to see how the application reacts. It essentially tests input validation, as well as variable usage and memory management.
