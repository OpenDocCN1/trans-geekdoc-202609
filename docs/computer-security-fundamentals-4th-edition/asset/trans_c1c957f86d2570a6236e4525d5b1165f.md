
-   [所有关系型数据库都使用 SQL，其中包括 `SELECT`、`UPDATE`、`DELETE`、`INSERT` 和 `WHERE` 等命令。至少基本查询非常容易理解和解释。  
    大多数基本的 SQL 注入操作方式如下：许多网站或应用程序有一个页面，用户在该页面输入用户名和密码。该用户名和密码需要与数据库中的某些记录进行比对，以判断其有效性。无论数据库类型如何（Oracle、SQL Server、MySQL），所有数据库都使用 SQL。SQL 的外观和功能在很大程度上类似于英语。例如，要检查用户名和密码，你可能需要查询数据库，看看 `users` 表中是否存在匹配用户名和密码的记录。如果存在这种记录，则表示匹配。用于查询的 SQL 语句可能如下所示：  

    [Click here to view code image](Images/ch06_images.xhtml#p163pro01)  

    ```  
    `SELECT * FROM tblUsers WHERE USERNAME = 'jdoe' AND PASSWORD = 'letmein'`  
    ```  

    该查询的问题在于，虽然它是合法的 SQL，但硬编码了用户名和密码。对于真实网站，你需要将用户在用户名输入框和密码输入框中输入的内容取代硬编码值进行检查。这可以在任何编程或脚本语言中轻松实现，具体方式如下：  

    [Click here to view code image](Images/ch06_images.xhtml#p164pro01)  

    ```  
    `SELECT * FROM tblUsers WHERE USERNAME = '" + txtUsername.Text + ' AND PASSWORD = '" +  
    txtPassword.Text +"'`  
    ```  

    如果你输入用户名 `'jdoe'`、密码 `'letmein'`，则会生成以下 SQL 命令：  

    [Click here to view code image](Images/ch06_images.xhtml#p164pro02)  

    ```  
    SELECT * FROM tblUsers WHERE USERNAME = 'jdoe' AND PASSWORD = 'letmein'  
    ```  

    如果 `tblUsers` 中存在用户名为 `jdoe`、密码为 `letmein` 的记录，则该用户将被登录；否则会出现错误。  

    SQL 注入通过在用户名和密码输入框中插入始终为真（true）的 SQL 语句来实现。例如，假设你在用户名和密码框中输入 `'OR X=X'`，这将导致程序生成如下查询：  

    [Click here to view code image](Images/ch06_images.xhtml#p164pro03)  

    ```  
    SELECT * FROM tblUsers WHERE USERNAME = ''OR X=X' AND PASSWORD = ''OR X=X'  
    ```  

    注意，你在 `'OR X=X'` 之前加上了单引号（`'`），这会关闭代码中已有的开启的引号。如果你看到 `''`，这本质上是空或空值，意味着如果用户名为空或 `X=X`，或者密码为空或 `X=X`，则数据库会登录你。如果你稍作思考，会发现 `X` 始终等于 `X`，因此这始终为真。  

    `'OR X=X'` 本身没有特殊意义，它只是一个始终为真（true）的语句。攻击者还会尝试类似的语句，例如：  

    ```  
    ' or 'a' ='a  
    ' or '1' ='1  
    ' or (1=1)  
    ```  

    本例展示了最基础的 SQL 注入方式，但也是最常见的。攻击者可以根据其对 SQL 的了解和目标数据库系统的限制，进行更高级的注入操作。  

    防御此类攻击的方法是对用户输入进行过滤。这一过程通常称为 *input validation*，它可以阻止攻击者输入 SQL 命令而非用户名和密码。遗憾的是，许多网站未对用户输入进行过滤，仍然容易受到 SQL 注入攻击。  

    请回顾前文提到的 SQL 注入时，我们简要说明过滤输入可以防止此类攻击。例如，创建网站的程序员应先检查是否包含常见的 SQL 注入符号，如单引号（`'`）、百分号（`%`）、等号（`=`）或井号（`&`），若检测到这些符号则停止处理并记录错误。这将阻止许多 SQL 注入攻击。虽然存在绕过这些安全措施的方法，但实施这些措施仍能阻止大量 SQL 注入攻击。  

-   [跨站脚本（Cross-Site Scripting）  
    通过 *跨站脚本*，攻击者在其他用户查看的网页中注入客户端脚本。关键在于攻击者将脚本注入用户与网站交互的区域。当用户访问该部分页面时，攻击者的脚本会被执行，而不是预期的网站功能。例如，假设一个购物网站允许用户对产品进行评论。与手动输入评论不同，攻击者可能输入 JavaScript 代码，将用户重定向到钓鱼网站。当另一位用户查看该“评论”时，脚本会执行并跳转到新站点。同样，这类攻击可以通过简单过滤用户输入来防止。截至本文撰写时，所有主要在线购物平台（如 Amazon.com）均对输入进行过滤，不受此类攻击影响。然而，许多小型网站仍易受跨站脚本攻击。  

-   [跨站请求伪造（Cross-Site Request Forgery）  
    *跨站请求伪造* 可以被视为跨站脚本的另一面。跨站脚本针对用户，基于用户对网站的信任；而跨站请求伪造则针对网站，基于网站对用户的信任。受信任的用户（已认证登录）会被骗发送请求给网站。  

-   [目录遍历（Directory Traversal）  
    *目录遍历* 允许攻击者访问受限目录，包括包含应用程序源代码、配置文件以及关键系统文件的目录，并执行位于 Web 服务器根目录之外的命令。  

    攻击者可操控包含 “点点斜杠（../）” 及其变体的文件引用变量，例如：  

    [http://www.example.com/process.aspx=../../../../some](http://www.example.com/process.aspx=../../../../some) dir/some file  
    [http://www.example.com/../../../../some](http://www.example.com/../../../../some) dir/some file  

-   [Cookie 中毒（Cookie Poisoning）  
    许多 Web 应用使用 Cookie 保存信息（如用户 ID、时间戳等）在客户端机器上。例如，用户登录时，登录脚本会验证用户名和密码，并设置包含其数字标识的 Cookie。当用户稍后查看偏好设置时，另一个脚本（如 preferences.asp）会读取 Cookie 并显示对应用户的信息记录。由于 Cookie 并非总是加密，它们可以被修改；这种修改类型的攻击称为 *cookie poisoning*。事实上，JavaScript 可以修改、写入或读取 Cookie，因此该攻击可以与跨站脚本结合使用。  

-   [URL 劫持（URL Hijacking）  
    *URL 劫持*，也称为 *typosquatting*，涉及一个非常接近真实 URL 的假 URL。例如，我的网站是 [www.Chuckeasttom.com](http://www.Chuckeasttom.com)。有人可能创建 [www.Chuckeastom.com](http://www.Chuckeastom.com)，仅在最后名字中少一个 *t*。  

-   [无线攻击  
    常见的无线攻击包括 *evil twin attack*（恶意双子攻击）。在该攻击中，恶意方设置一个与合法访问点（AP）具有相同 SSID 的 rogue WAP，并利用其发起拒绝服务攻击，使合法 AP 无法响应用户请求，从而将用户重定向至恶意双子。
