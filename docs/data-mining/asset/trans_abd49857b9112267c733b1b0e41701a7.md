
一个例子有助于解释候选项集是如何生成的。假设有 5 个三项集——`(A B C)`、`(A B D)`、`(A C D)`、`(A C E)` 和 `(B C D)`——其中 A 是一个特征，例如 `outlook` = `sunny`。前两个的并集 `(A B C D)` 是一个候选四项集，因为其另外两个三项子集 `(A C D)` 和 `(B C D)` 的覆盖度大于最小覆盖度。如果三项集按字典顺序排序，如本列表所示，则我们只需考虑前两个成员相同的配对。例如，我们不考虑 `(A C D)` 和 `(B C D)`，因为 `(A B C D)` 也可以由 `(A B C)` 和 `(A B D)` 生成，并且如果这两个不是具有最小覆盖度的三项集，则 `(A B C D)` 不能成为候选四项集。这剩下配对 `(A B C)` 和 `(A B D)`，我们已经解释过，以及 `(A C D)` 和 `(A C E)`。这个第二对导致集合 `(A C D E)`，其三项子集并非全部具有最小覆盖度，因此被丢弃。哈希表有助于此检查；我们只需依次从集合中移除每个项目并检查剩余的三项集是否确实存在于哈希表中。因此在此示例中只有一个候选四项集 `(A B C D)`。它是否实际具有最小覆盖度只能通过检查数据集中的实例来确定。

该过程的第二阶段取每个项集并从中生成规则，检查它们是否具有指定的最小准确度。如果只寻求右手边只有一个测试的规则，那么只需依次将每个条件作为规则的后件考虑，从项集中删除它，并将整个项集的覆盖度除以由此产生的子集——从哈希表中获得——的覆盖度，以得出相应规则的准确度。鉴于我们也对后件中包含多个测试的关联规则感兴趣，看起来我们必须评估将项集的每个 `subset` 放在右手边的效果，将集合的其余部分作为前件。

这种暴力方法除非项集很小，否则计算量会过大，因为可能的子集数量随项集大小呈指数增长。然而，有更好的方法。我们在描述关联规则时在 [第 3.4 节](#Ch003_67-89_B9780443158889000042.xhtml#s0025) 中观察到，如果双后件规则

```
If windy = false and play = no
```
then `outlook` = `sunny` and `humidity` = `high`

在给定的最小覆盖度和准确度下成立，则由同一项集形成的两个单后件规则也必须成立：

```
If humidity = high and windy = false and play = no
```
then `outlook` = `sunny`

```
If outlook = sunny and windy = false and play = no
```
then `humidity` = `high`

反之，如果这两个单后件规则之一不成立，就没有考虑双后件规则的意义。这提供了一种从单后件规则构建候选双后件规则、从双后件规则构建候选三后件规则，依此类推的方法。当然，每个候选规则都必须对照哈希表进行检查，以查看它是否确实具有超过指定的最小准确度。但这通常涉及检查的规则远少于暴力方法。有趣的是，这种从实际 `n`-后件规则构建候选 (`n` + 1<mml:math><mml:mi>n</mml:mi><mml:mo>+</mml:mo><mml:mn>1</mml:mn></mml:math>![Equation](images/F000054si59.png))-后件规则的方式，实际上与前面描述的从实际 `n`-项集构建候选 (`n` + 1<mml:math><mml:mi>n</mml:mi><mml:mo>+</mml:mo><mml:mn>1</mml:mn></mml:math>![Equation](images/F000054si60.png))-项集的方式相同。

要为特定数据集找到所有规则，第二部分所示的过程将应用于使用第一部分算法找到的所有项集。请注意，第二部分中的代码需要访问第一部分建立的哈希表，其中包含已找到的所有足够频繁的项集及其覆盖度。以这种方式，[图 4.9B](#Ch004_91-164_B9780443158889000054_a.xhtml#f0050) 中的算法完全不需要重新访问原始数据；准确度可以根据这些表中的信息进行估计。

关联规则通常是为非常大的数据集寻求的，高效的算法备受重视。我们描述的方法对每种不同的项集大小进行一次数据集遍历。有时数据集太大无法读入主内存，必须保存在磁盘上；然后通过一次检查两个连续大小的项集来减少遍历次数可能是值得的。例如，一旦生成了包含两项的集合，就可以在遍历实例集以计算集合中实际项目数量之前，从它们生成所有三项集合。会考虑比必要更多的三项集，但整个数据集的遍历次数会减少。

实际上，生成关联规则所需的计算量在很大程度上取决于指定的最小覆盖度。准确度的影响较小，因为它不影响必须对数据集进行的遍历次数。在许多情况下，我们希望在预先指定的最小准确度水平下获得一定数量的规则——比如 50 条——具有尽可能大的覆盖度。一种方法是首先将覆盖度指定为相当高，然后逐步降低它，对每个覆盖度值重新执行整个规则查找算法并重复，直到生成所需数量的规则。

我们在整本书中使用的表格输入格式，特别是基于它的标准属性-关系文件格式 (`ARFF`) 格式，对于许多关联规则问题来说非常低效。关联规则通常用于属性为二元——存在或不存在——的情况，并且与给定实例相关的大多数属性值都不存在。这是 [第 2.4 节](#Ch002_43-66_B9780443158889000030.xhtml#s0035) 中描述的稀疏数据表示的适用情况；查找关联规则的相同算法适用。
