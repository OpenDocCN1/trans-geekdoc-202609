
[表 2.4](#Ch002_43-66_B9780443158889000030.xhtml#t0025) 的结构可用于描述两个人之间的任何关系——祖父母关系、隔了两代的二代表亲等等。涉及更多人的关系则需要更大的表。最大人数事先未指定的关系会带来更严重的问题。如果我们想学习 *核家庭*（父母及其子女）的概念，涉及的人数取决于最大核家庭的大小，虽然我们可以猜测一个合理的最大值（10？20？），但实际数字只能通过扫描树本身才能找到。尽管如此，给定一组有限的关系，我们原则上可以形成一个新的“超关系”，其中包含针对 *每一个* 人的组合的一行，这足以表达人与人之间无论涉及多少人的任何关系。然而，其计算和存储成本将是难以承受的。

反规范化带来的另一个问题是，它会在数据中产生完全虚假的表面规律，而这些规律实际上只是原始数据库结构的反映。例如，想象一个超市数据库，其中有一个关系记录顾客及其购买的产品，一个关系记录产品及其供应商，还有一个关系记录供应商及其地址。对其进行反规范化会产生一个平面文件，其中每个实例都包含顾客、产品、供应商和供应商地址。寻求数据库中结构的数据挖掘工具可能会得出顾客购买啤酒也会购买薯片这一事实，从超市经理的角度来看，这一发现可能很重要。然而，它也可能得出供应商地址可以从供应商中完全预测这一事实——这一“发现”根本不会让超市经理印象深刻。这一事实在平面文件中伪装成重要发现，但在原始数据库结构中已明确存在。

许多抽象的计算问题涉及非有限的关系，尽管很明显任何实际的输入示例集合必须是有限的。诸如 *祖先关系* 之类的概念涉及树中任意长的路径，虽然人类及其族谱可能是有限的（尽管庞大无比），但许多人工问题生成的数据确实是无限的。虽然这听起来可能晦涩难懂，但在列表处理和逻辑编程等领域，这种情况是常态，并且在机器学习的一个子学科 *归纳逻辑编程* 中得到解决。计算机科学家通常使用递归来处理可能示例数量无限的情况。例如，

```
If person1 is a parent of person2
```

```
then person1 is an ancestor of person2
```

```
If person1 is a parent of person2
```

```
and person2 is an ancestor of person3
```

```
then person1 is an ancestor of person3
```

是一个简单的递归定义 *祖先*，无论两个人关系多么遥远都适用。归纳逻辑编程技术可以从有限的实例集合（如 [表 2.5](#Ch002_43-66_B9780443158889000030.xhtml#t0030) 中的实例）学习此类递归规则。

### 其他示例类型

正如我们所见，一般关系带来了实质性的挑战，本书将不再进一步讨论它们。诸如图和树之类的结构化示例可以被视为关系的特殊情况，通常通过基于其结构提取局部或全局特征并将其表示为属性的方式映射为独立实例。同样，项目序列可以通过用一组固定的属性表示它们或其单个项目来处理。幸运的是，大多数实际的数据挖掘问题可以相当有效地表示为一组实例，每个实例都是要学习的概念的一个示例。

在某些情况下，单个实例并不是概念的示例，每个单独的示例包含一组由相同属性描述的实例。这种“多实例”设置涵盖了一些重要的现实世界应用。其中一个涉及活性药物分子的特征推断，其中 *活性* 对应于药物分子与靶分子上的“结合位点”结合的程度。问题在于药物分子可以通过旋转其键来假设替代形状。如果其中一种形状实际结合到该位点并产生预期效果，则将其归类为阳性——但不知道是哪种形状。另一方面，如果没有任何形状成功结合，则药物分子为阴性。在这种情况下，多实例是一组形状，整个集合被分类为阳性或阴性。

多实例问题在数据库关系连接时也经常自然出现，例如当二级关系的若干行与目标关系中的同一行相关联时。例如，我们可能希望根据存储在二级表中的用户会话描述将计算机用户分类为专家或新手。目标关系仅具有分类和用户 ID。连接两个表会创建一个平面文件。然而，属于单个用户的行并不是独立的。分类是按用户进行的，因此与同一用户关联的会话实例集合应被视为学习的一个示例。

多实例学习的目標仍然是產生概念描述，但现在任务更困難，因為學習算法必須應對每個訓練示例的不完整信息。與將每個示例視為單個明確的屬性向量不同，學習算法將每個示例視為一組屬性向量。如果它知道集合中哪個成員負責示例的分類，那就容易了——但這並不知道。
