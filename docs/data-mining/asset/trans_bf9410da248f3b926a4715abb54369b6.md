
机器学习系统可以利用关于属性的各种其他信息。例如，量纲考虑可用于将搜索限制为量纲正确的表达式或比较。循环排序可能会影响所考虑的测试类型。例如，在时间上下文中，对 `day` 属性的测试可能涉及下一天、前一天、下周的同一天等。部分排序，即泛化或特化关系，在实际情况下经常出现。这类信息通常被称为 `metadata`，即关于数据的数据。然而，用于数据挖掘的实际方案很少能够考虑元数据，尽管这些能力在未来很可能迅速发展。

## 2.4 准备输入

为数据挖掘调查准备输入通常消耗了整个数据挖掘过程中投入的大部分精力。虽然本书并不是真正关于数据准备的问题，但我们希望让你感受到所涉及的问题，以便你能体会其复杂性。接下来，我们将介绍一种特定的输入文件格式，即属性-关系文件格式 (ARFF)，该格式在 Weka 系统中使用，该系统在 [附录 B](#AppendixB_637-654_B9780443158889000224.xhtml#AppendixB_637-654_B9780443158889000224) 中描述。然后我们考虑将数据集转换为此类格式时出现的问题，因为有一些简单的实用要点需要注意。苦涩的经验表明，真实数据质量往往令人失望地低下，而仔细检查——这一过程被称为 `data cleaning`——会带来多倍的回报。

### 收集数据

开始处理数据挖掘问题时，首先需要将所有数据汇集到一组实例中。我们在描述家谱示例时解释了反规范化关系数据的必要性。虽然它说明了基本问题，但这个自成体系且相当人为的示例并不能真正传达实际操作中该过程会是什么样的感觉。在实际的业务应用中，需要从不同部门汇集数据。例如，在市场研究中，需要来自销售部门、客户账单部门和客户服务部门的数据。

整合来自不同来源的数据通常会带来许多挑战——不是原则上的深层问题，而是实践中的棘手现实。不同部门会使用不同的记录方式、不同的约定、不同的时间段、不同的数据聚合程度、不同的主键，并且会有不同类型的错误。数据必须被汇集、整合和清理。公司范围内的数据库集成思想被称为 `data warehousing`。数据仓库为企业或组织数据提供单一一致的访问点，超越部门划分。它们是旧数据以可用于指导业务决策的方式发布的地方。向数据仓库发展的趋势是对这样一个事实的认可：组织在部门层面用于支持日常运营的碎片化信息，当汇集在一起时可以具有巨大的战略价值。显然，数据仓库的存在是数据挖掘非常有用的先决条件，如果没有它，就必须执行数据仓库涉及的许多步骤来为挖掘准备数据。

即使是数据仓库也可能不包含所有必要的数据，你可能需要超出组织范围引入与手头问题相关的数据。例如，在 [第1章](#Ch001_3-42_B9780443158889000029.xhtml#Ch001_3-42_B9780443158889000029) 中的负荷预测示例中必须获取天气数据，“它到底是关于什么的？”，而人口统计数据对于营销和销售应用是必需的。有时被称为 `overlay data`，这类数据通常不是由组织收集的，但显然与数据挖掘问题相关。它也必须清理并与已收集的其他数据集成。

汇集数据时另一个实际问题是适当的聚合程度。当奶农决定卖掉哪些奶牛时，牛奶生产记录——自动挤奶机每天记录两次——必须进行聚合。同样，当电信公司研究客户行为时，原始电话呼叫数据用处不大；数据必须聚合到客户层面。但你想要按月还是按季度使用，以及追溯多少个月或季度？选择正确的聚合类型和级别通常对成功至关重要。

由于涉及如此多不同的问题，你不能指望第一次就做对。这就是为什么数据汇集、集成、清理、聚合和一般准备工作需要花费这么长时间。

### ARFF 格式

我们现在来看一种表示数据集的标准方式，称为 `ARFF file`。我们描述的是常规版本，但还有一个名为 `XRFF` 的版本，正如名称所示，它以 XML 标记语言给出 ARFF 头部和实例信息。

[图 2.2](#Ch002_43-66_B9780443158889000030.xhtml#f0015) 显示了 [表 1.3](#Ch001_3-42_B9780443158889000029.xhtml#t0020) 中的天气数据的 ARFF 文件，即带有一些数值特征的版本。以 % 符号开头的行是注释。在文件开头的注释之后是关系的名称 (`weather`) 和一个定义属性的块 (`outlook`, `temperature`, `humidity`, `windy`, `play?`)。标称属性后面跟着它们可以取的值的集合，用花括号括起来。值可以包含空格；如果是这样，它们必须放在引号内。数值后面跟着关键字 `numeric`。

![图 2.2 天气数据的 ARFF 文件.](images/F000030f02-02-9780443158889.jpg)

[图 2.2](#Ch002_43-66_B9780443158889000030.xhtml#Bf0015) 天气数据的 ARFF 文件。

虽然天气问题的目标是从其他属性的值预测类别值 `play?`，但在数据文件中类别属性没有任何区别。ARFF 格式仅提供一个数据集；它不指定哪个属性是应该被预测的。这意味着同一个文件可用于研究每个属性能被其他属性预测得多好，或用于寻找关联规则，或用于聚类。

在属性定义之后是一行 `@data`，它标志着数据集中实例的开始。实例每行写一个，按顺序给出每个属性的值，以逗号分隔。如果某个值缺失，则用单个问号表示（该数据集中没有缺失值）。ARFF 文件中的属性规范允许检查数据集以确保其包含所有属性的合法值，而读取 ARFF 文件的程序会自动执行此检查。

除了天气数据所示例的标称和数值属性外，ARFF 格式还有三种其他属性类型：字符串属性、日期属性和关系值属性。字符串属性的值为文本。假设你有一个字符串属性想命名为 `description`。在定义属性的块中，它是这样指定的：

```
@attribute description string
```

然后，在实例数据中，用引号包含任意字符字符串（要在字符串中包含引号，请使用标准约定，即在每个引号前加反斜杠 “\\”）。字符串在内部存储在字符串表中，并由其在该表中的地址表示。因此，包含相同字符的两个字符串将具有相同的值。
