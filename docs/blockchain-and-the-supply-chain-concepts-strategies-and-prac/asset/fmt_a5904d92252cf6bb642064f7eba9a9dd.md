
### Enterprise Ethereum

The Enterprise Ethereum Alliance is an industry organization formed to promote the use of Ethereum for business applications. It has created a specification for a permissioned version of Ethereum where nodes can be deployed by businesses, in such a way that only permissioned or allowed organizations can deploy nodes. Two different implementations of Enterprise Ethereum are `Quorum` (Consensys, 2022) and `Hyperledger Besu` (Hyperledger Besu, 2022). Both are permissioned and allow for private transactions by use of public-key encryption. Both support multiple proof of authority-based consensus mechanisms: `IBFT`, `Clique` (supported by both Besu and Quorum), `QBFT` (supported by Besu) and `Raft` (supported by Quorum). Besu also supports proof of work. Quorum is a fork of the Ethereum `Geth` implementation, while Besu is a Java-based Ethereum implementation. Both support the `EVM` and hence the `Solidity` programming language.

### Tendermint

Tendermint Core is software that can be used to implement a permissioned blockchain (Tendermint, 2022). At its heart is the Tendermint consensus protocol (Buchman, 2016). At each round, a node proposes the next block, in round-robin fashion. There is a multi-stage voting process to validate and commit each block. The protocol can support the Byzantine (arbitrary) failure of up to one third of the nodes in the network. The Tendermint implementation is quite fast, capable of processing thousands of transactions per second with a fast block confirmation time in the order of one second. It is also relatively lightweight, capable of running on relatively resource-constrained nodes.

For its version of smart contract programming, Tendermint provides an application interface called the Application BlockChain Interface (`ABCI`). The `ABCI` allows a bring-your-own-language model in that transactions can be processed in any language such as `Python`, `Go` or `Java`. The Hyperledger Burrow project has combined Tendermint consensus with an `EVM` to allow solidity-based smart contracts (Hyperledger Burrow, 2022).

We mention in passing that the Tendermint software can also be used in permissionless protocols, and is the basis for the Cosmos protocol mentioned in the previous chapter.

### TradeLens: permissioned blockchain for supply chain

TradeLens is one concrete implementation of a supply chain platform built using permissioned blockchain technology (TradeLens, 2022). TradeLens is a supply chain platform developed jointly by IBM and GTD Solution Inc. TradeLens uses the IBM blockchain platform, which in turn is based on the open-source Hyperledger Fabric blockchain platform.

The goal of TradeLens is to allow for sharing of all relevant data between participants in the shipping supply chain in a private and secure manner. As goods are shipped from some source to a destination, participants involved in the transport and logistics provide a variety of data to the TradeLens platform such as logistics milestones, movement information and trade documents. Examples of documents shared on the platform include certificates of origin, import declarations, packing lists, invoices, waybills and bills of lading.

The TradeLens ecosystem includes the following stakeholders, who may need to send transactions, have access to data on chain or be involved in processing the data on chain:

*   shippers and cargo owners;
*   third-party logistics providers;
*   train, drayage and barge operators;
*   government agencies including customs;
*   port and terminal operators;
*   ocean carriers;
*   financial services and insurance providers.

TradeLens allows all (and only) relevant parties to access specific types of information related to a shipment, with access enabled to different organizations based on their role and the data type using a permission matrix which works as follows. Participant roles for a given data type are designated by one of the following codes: `M` (mandatory), `C` (conditional), `O` (optional), `R` (read-only) or blank. Participants whose roles are labeled with `M`, `C` or `O` are allowed read and write access; participants with `R` only have read access and a blank indicates no access to the corresponding data type. Some of the roles are implicitly and automatically assigned to certain participants (eg customs authorities may be automatically given read access to relevant documents pertaining to consignments passing through their jurisdiction), while others can be assigned by authorized parties.

Multiple persistence layers are used including document storage, object storage, relational databases and the blockchain, depending on the type of information and how it needs to be accessed. The storage of hashes of all key documents on the blockchain ensures the integrity of those documents (they cannot be tampered with once committed to the chain). As a permissioned blockchain platform, all members of the network are known to each other based on their cryptographic identities.

For consistency, TradeLens uses a standard data model (TradeLens DSS, 2022) that is aligned with the Supply Chain Reference Data Model from UN/CEFACT (Clark *et al*, 2002), with three main objects: shipments, consignments and transport equipment. The platform provides `APIs` to allow easy integration with third-party off-chain software.

## When to use blockchain

As we have discussed in this chapter, there are now a number of alternative blockchain platforms that can be used for Enterprise applications. It is worth considering the conditions under which blockchains are the right solution in a business context, or whether a more traditional (eg centralized server-based approach) would suffice to offer all the required guarantees, possibly at a better performance and cost. This is a question that has been considered by many researchers and practitioners (Wüst *et al*, 2018; Pederson *et al*, 2019).

Generally, there is some consensus that the following conditions must hold for blockchain to be relevant:

*   There must be multiple parties involved, with conflicting interests or trust issues, that also do not trust a single third party.
*   These parties must have some need to share some data, potentially privately with subsets of other parties.
*   There is some need for the shared data to be logged in an immutable manner.
*   The volume and velocity of data to be logged is within the storage and throughput capabilities of blockchain technology.

Since blockchain systems are still relatively slow compared to traditional databases, even if a blockchain is used, there is often some need to carefully consider what should be logged in the immutable ledger and what can be stored or replicated using more traditional approaches. For example, if some very large file is being shared among participants, it may suffice to log only the hash of that file on the blockchain and share the file itself using a more conventional server-based or peer-to-peer approach. This way, any tampering of the file can be readily detected (since the hash on chain would no longer match the file).

It is challenging to coordinate and establish a permissioned blockchain platform that spans many different entities and organizations. The initial success of TradeLens suggests that it is possible to do so in industries where there is a clear benefit to many or all participants to switch from their current processes to a unified blockchain-based platform.
