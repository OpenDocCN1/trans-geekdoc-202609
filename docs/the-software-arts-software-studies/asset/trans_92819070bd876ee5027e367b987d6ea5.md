
# 超越算法

正如第 2 章所讨论的，图灵证明了他的自动机器——现在称为图灵机——与阿隆佐·邱奇的 λ 演算之间的等价性。邱奇的学生斯蒂芬·科尔·克莱尼创造了“邱奇-图灵论题”这一短语来指代这种等价性。同样在第 2 章中，我们探讨了邱奇-图灵论题是如何被普及并扩展为一种奇想：即图灵 1936 年的论文表明，任何类型的机器——无论它们是否已被渲染为图灵机或 λ 演算——都可以由图灵机模拟。但图灵和邱奇都没有证明*所有*机器都能用他们的形式化体系来表示。他们形式化体系所能表达的，是任何符合算法定义的过程。尽管如此，这种对邱奇-图灵论题的夸张普及却一次又一次地被重复——甚至至今仍在重复。

计算机科学家爱德华·李撰写了一篇技术精确且通俗易懂的文章，反驳了这种对邱奇-图灵论题的普及。李写道：“图灵和邱奇只考虑了处理数字数据的机器，以及通过逐步过程进行算法计算的机器。我们经常制造既不满足这两个属性的机器，比如我的洗碗机。”^([17](#chapter_8.xhtml#chapter8-17)) 这段引文出自李的讨论开头。在后续内容中，他带领我们浏览了计算机科学的一些技术文献，这些文献反驳了通用图灵机（UTM）不仅仅是一台可编程图灵机的观点。想象一下，如果 UTM 真的是通用的：我们就能在智能手机上下载一个 App 来洗碗、当作自行车骑行，或者修剪草坪！

但自动驾驶汽车呢？机器人呢？难道不能设计一个洗碗的机器人吗？大概可以。但关键在于，虽然这样的机器人可能包含许多可建模为函数的算法，但整个系统的设计——这种机器人软件系统中所有相互作用的部分——无法被建模为一个数学函数。

## 算法之外

### 超越算法：案例 1，米尔纳的并发系统演算

要理解数学函数与大多数软件之间的鸿沟，我们可以阅读罗宾·米尔纳的著作，他扩展了 λ 演算以试图弥合这一鸿沟。在他的图灵奖演讲“交互的要素”中^([18](#chapter_8.xhtml#chapter8-18))，米尔纳解释了为什么需要扩展 λ 演算：“对于规模小得多的顺序计算世界，一个通用的语义框架建立在数学函数这一核心概念之上，并用函数演算正式表达——阿隆佐·邱奇的 `λ-calculus` 就是著名的原型。函数是我们讨论顺序编程语义时呼吸的空气中的必需成分，可以说。但对于并发编程和一般交互系统，我们却没有任何可比拟的东西。”^([19](#chapter_8.xhtml#chapter8-19)) 米尔纳将他对 λ 演算的扩展称为并发系统演算（CCS）。

米尔纳继续进行比较：“在 `λ-calculus` 中，所有计算归结为一件事，称为*归约*——即将参数传递给函数的行为；我们可以称之为 `λ-calculus` 的*行为原子*。同样地，*交互*——进程间单个数据的传递——是 CCS 中的行为原子。”^([20](#chapter_8.xhtml#chapter8-20))

机器人包含多个并发进程，任何包含软件并与世界交互的系统也是如此——即使是键盘这样简单的接口，也能在我们打字时异步捕获按键。`λ-calculus`（因此也包括算法和图灵的自动机器）不足以对这种并发系统建模，因为它们根据定义排除了任何形式的交互。

图灵机是具有输入和输出的自动机器，但不会停下来与用户、一个“外部操作员”交互。`λ-calculus` 的函数通过替换变量和归约函数体来工作，不会停下来交互。这些形式化体系被设想为瞬间完成工作。例如，将 `y` 的值代入变量 `x` 被认为是“原子性的”，因为在符号中并未涉及中途打断替换的情况：`(λx.x)y = [y/x]x`，但如果在替换过程中，某些东西改变了 `y` 的值，会怎样呢？

米尔纳用三个简单的程序说明了这种可能性，每个程序包含一两条赋值语句。回顾第 2 章，类 ALGOL 语言中的赋值语句可以这样写：`y := 1`，意思是赋值语句执行后，变量 `y` 包含值 1。以下是米尔纳的三个示例程序：

```
P1: y := 1; y := y + 1;
P2: y := 2;
P3: y := 3.
```

如果在没有任何干扰的情况下运行，P1 和 P2 都将变量 `y` 赋值为 2。在 P1 中，需要两条赋值语句来完成：首先 `y` 得到值 1，然后得到值 1 + 1 即 2。因此，在函数符号中，P1 和 P2 是等价的，因为它们都将变量 `y` 赋值为 2。

然而，如果我们将 P1 或 P2 与 P3 并发运行，P1 和 P2 将不再等价。假设赋值语句执行所需时间大致相同；即将值移动到变量指定的内存位置。然后并发运行时，P2 和 P3 将导致 `y` 的值为 2 或 3（取决于哪条赋值语句最后完成）。相比之下，当 P1 和 P3 并发执行时，`y` 将是 2、3 或 4——同样取决于哪条赋值语句最后完成。

让我们用符号 `Q | R` 表示程序 Q 和 R 并发执行——即并行——并用一个集合来表示执行的可能结果，其中元素是变量 `y` 可能的值：`P1 = {2}`，`P2 = {2}`，`P1 | P3 = {2, 3}`，以及 `P2 | P3 = {2, 3, 4}`。

米尔纳这个小例子的要点在于：尽管 `P1 = P2`，但当它们与 P3 并发运行时，二者是不同的。具体来说，如果我们用集合来表示“函数”的值域，当它们与第三个“函数”组合时，P1 和 P2 就不再相同了。

米尔纳的这个小例子给将软件建模为图灵机、算法或 `λ-calculus` 函数的任何尝试都带来了一个大问题，因为数学函数的组合不应该改变被组合函数的定义。然而，用 `|` 算子组合函数，与用加、减、乘、除组合函数截然不同。想象一下，如果 `1 + 1` 等于 2、3 或 4，取决于其他算术运算是否正在进行以及何时进行，算术会变成什么样！

为什么这对数学家来说是个大问题？简短的回答就是：计算机程序不是数学函数，或者至少不*只是*数学函数。详细的回答是：在实际连接其他系统并供人使用的系统中，时序和交互至关重要，而图灵正如前所述，从一开始就通过将其形式化体系限制为类似于数学函数的自动机器（随后被称为算法），排除了交互。
