
### Security

A stored procedure can help prevent SQL injection attacks when parameters are used and the stored procedure is prepared (meaning it is precompiled before its first use). The benefit is that because the stored procedure is precompiled, if the hacker tries to inject an SQL command into the parameter, they will receive an error because the stored procedure has already been compiled so that code inserted as a parameter is not accepted.

#### Code Signing

Developers can digitally sign their code so that companies know where the code came from. This way, they can trust that the code will do no harm to the system. Code signing also adds integrity to the code because a hash of the code is generated, meaning the code is run through an algorithm and an answer is generated. The answer is stored with the code. This gives you a way to verify that the code has not been altered when you check the code against the hash (answer) later on.

In order to digitally sign code, such as a DLL or EXE file, or even a script, such as a PowerShell script, you need a code-signing certificate. This certificate is an electronic file that contains keys used to digitally sign other files. You will learn more about certificates and public key infrastructure (PKI) in [Chapters 12](#ch12.xhtml#ch12) and [13](#ch13.xhtml#ch13).

#### Encryption

Encrypting sensitive data is an important consideration when developing applications. There are a few areas where you should look at encryption when developing an application. The first is communication protocols. If your application is communicating with other systems on the network or Internet, should you be encrypting the communication? If you are transmitting sensitive data, then the answer is yes. Another area to consider encryption is with the storage of data. If you are storing sensitive information to a file, then that file should be encrypted, or the data in the file should be encrypted. If you are storing sensitive data in a database, be sure to encrypt the information as it is stored in the database.

#### Other Techniques

There are a number of other common secure coding practices you should follow when developing applications. If you are not a programmer but rather an information security officer within your organization, you also need to be aware of these coding techniques and ensure that your in-house applications are being built using these techniques. When developing applications or assessing the security of the applications, be sure to check for secure coding techniques in the following areas:

- **Normalization** When developing the database for the application, you break the data into multiple tables to reduce redundancy in the data. For example, there is a customer table in the database that stores customer information such as CustomerID, Lastname, and Firstname. Each time the customer makes a purchase, you only record the CustomerID in the purchase table and not the customer name information.

- **Obfuscation/camouflage** Obfuscation and camouflage are common security principles that add to security by making a feature or component obscure or unclear. The idea here is that if the product or feature is hard to understand or find, then it will be harder to exploit.

- **Code reuse/dead code** Code reuse is a common programming practice that can add to the security of the application. You would create a set of functions that follow secure coding principles and then call those functions from any of your applications that need the functionality. The purpose is that you know you are calling already tested and tried code, versus re-creating new code that could have vulnerabilities. You should also evaluate your code and look for dead code, which is code in a function that executes and returns a result, but the result is never used in the application anywhere. Dead code should be removed because the code could be vulnerable to an exploit if left unmaintained and then forgotten over time. For example, you may have an API that has a function that is no longer used. The function should be removed from the API to prevent future exploits against the function.

- **Server-side vs. client-side execution and validation** From a secure application design point of view, it is more secure to have server-side code execute than client-side code. Client-side code can be changed at the client and really should not be relied upon. For example, you should always implement validation code on the server side, but whenever possible it does not hurt to implement validation code on both the client side and the server side.

- **Memory management** It is critical that developers learn to properly manage memory. This involves freeing memory from objects that are no longer in use by properly destroying those objects. If a developer fails to clean up memory, this could cause memory leaks in the application.

- **Use of third-party libraries and SDKs** Limit the use of third-party DLLs in your application and software development kits (SDKs). You do not know how secure the code is in those components because you did not write it.

- **Data exposure** Be sure to limit the amount of data that is exposed from your application. One of the techniques to do this is known as *encapsulation.* You can create public methods that interact with the data without making the data directly available.

#### Open Web Application Security Project

As a security professional, if you are responsible for testing software for secure coding practices, you should definitely check out the Open Web Application Security Project (OWASP). This project is supported by an online community and has many articles, tools, and documents published that are focused on educating people on common vulnerabilities in web applications and common security techniques that should be used to protect web applications.

You can check out OWASP at [www.owasp.org](http://www.owasp.org). One of the most common documents to come out of OWASP is “OWASP Top 10,” which details the top 10 vulnerabilities found in web applications. Check out “OWASP Top 10” at [https://owasp.org/www-project-top-ten/](https://owasp.org/www-project-top-ten/). With each of the top 10 vulnerabilities, you can choose a link to read more about the vulnerability, including prevention techniques. I highly recommend reviewing this information.

#### Software Diversity

You will encounter various types of software environments. For example, you will come across *compiled code*, which is when a developer develops an application that is then compiled into a binary file (an executable file that is unreadable).

This is different from programs created in a script environment. A script is not compiled, so it can be easily opened in an editor, modified, saved, and then run again. The script is parsed and run by a scripting engine that has been installed on the system.

*Software diversity* is the use of different compilers to create different compiled versions of binary code. This also includes randomization of binaries, where you could have runtime randomization applied to the binary files to make the code more difficult to exploit.

#### Automation/Scripting

A big part of security today is to automate as much as possible so that you do not have to perform repetitive tasks over and over again. Automation is the concept of creating scripts to perform the tasks for us. The benefit of automation is that once the scripts are created and tested, you can be sure that the process is performed in a consistent manner each time you run the script.
