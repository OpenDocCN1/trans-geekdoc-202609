# 336 Part IV: Not So Simple Applications

The status table is a lookup table, containing the possible states of a problem; notably “open,” “closed,” “in processing,” etc. The sources table is another lookup table that records where the problem was originally recorded. If a user enters a complaint over the Web, the sources table will record that; complaints received by the staff might originate from a phone call, e-mail, or flaming arrow.

The entries_type table notes whether a specific item in the history table should be public or private. If it is private it will not be available on the Web page when the user comes to view the problem and an e-mail will not be sent to the user when there is an update. The “public” updates will be viewable and the user will receive e-mail notification.

There is something bit strange in this schema; namely, the calls table. The purpose of the calls table is to store the most recent entry for each call that has an owner. If you look at you might wonder why this is necessary. After all, there are relationships between staff, problems, and history. Therefore, there should be a way to join these three tables to get the information you are after. Normally you would use sub-selects for something like this.

```
select problem.*, history.*, staff.*
from problem, history, staff
where problem.owner = '$PHP_AUTH_USER'
and history.dt_in (
select max(n.entry_dt) from history)
```

If we are using MySQL version 3.23, we would make use of temporary tables.

```
create temporary table calls
select max(entry_dt) from history
```

Then you could join the problem and history table onto this temporary table. However, since it's not available in version 3.23, which we used when creating these applications, we had to use a make temporary table. Each time it is accessed, the calls table will be emptied and repopulated with information we need to complete the joins. See the staff.php page for the schema and the create statements in SQL we used.
