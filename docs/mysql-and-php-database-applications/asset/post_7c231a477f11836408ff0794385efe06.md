## Why Use a Relational Database?

If you're still here and ready to read with rapt attention about database theory and the wonders of normalization, you probably don't know much about the history of the relational database. You may not even care. For that reason, IBM in brief. Dr. E. F. Codd was a research scientist at IBM in the 1960s. A mathematician by training, he was unhappy with the available models of data storage. He found that all the available methods were prone to error and redundancy. He worked on these problems and, in 1970, published a paper titled “A Relational Model of Data for Large Shared Databanks,” in all honesty, nothing has been the same.

A programmer named Larry Ellison read the paper and worked on software that could put Dr. Codd's theories into practice. If you've been a resident of this planet over the past 20 years, you may know that Ellison's product and company took the name Oracle and that he is now one of the richest men in the world. His earliest product was designed for huge mainframes. Responding to market demands over the years, Oracle, and many other companies that have sprung up since, have designed systems with a variety of features geared toward a variety of operating systems.

# Part I: Working with MySQL

Now, relational databases are so common that you can get one that runs on a Palm Pilot.

To understand how Dr. Codd's theories have revolutionized the data storage world, it's best to have an idea as to what the troubles are with other means of data storage. Take the example of a simple address book—nothing too complex, just some that stores names, addresses, phone numbers, e-mails, and the like. There's no persistent, running program that we can put this information into, the file system of whatever is running the natural choice for storage.

For a simple address book, a delimited file can be created to store the information. If the first row serves as a header and commas are used as the delimiter, it might look like this:

```
Name, Addr2, City, State, Zip, Phone, E-mail
Jay Greenspan, 411 Some St, Apt 2, San Francisco, CA, 94107, 4155551212, jgreen_1@yahoo.com
Bud Badger, 411 Some St, Apt 6, San Francisco, CA, 94109, 4155552222, bbulger@yahoo.com
John Doe, 441 Madison Ave,, New York, NY, 11234, 2125566666, nnody@hotmail.com
```

This isn't much to look at, but it is at least machine-readable. Unless you use it, you can write a script that opens this file and parses the information. You will probably want it in some sort of two-dimensional or associative array that you will have some flexibility in addressing each portion or line of the file. Any time you look at it, there's going to be a fair amount of criteria, if you want it to be sortable and queryable by a variety of criteria, you're going to have to write scripts that, for instance, sort the list alphabetically by name or find all people within a certain area code. What a pain.

You might face another problem if your data needs to be used across a network by a variety of people. Presumably more than one person is going to need to write information to this file. What happens if two people try to make changes at once? ... To prevent this, the programmer needs to specify file locking if the file is in use. While this might, it's kind of a pain in the neck for the person who gets locked out. Obviously, the larger the system gets the more unmanageable this becomes.

What you need is something robust than the file system—a program or daemon that stays in memory seems a good choice. Further, you'll need a data storage system that reduces the amount of parsing and scripting that the programmer needs to be concerned with. No need for anything arcane here. A plain, simple table like Table 1-1 would be fine.

Now this is pretty convenient. It's easy to look at, and if there is a running program that accesses this table, it should be pretty quick. What might this program do? First, it should address one row at a time without affecting the others. That way, if two or more people want to insert information into this table, they won't be tripping over each other. It would be even better if the program provided a simple and elegant way to extract information from a table such as this. There should be a quick way of finding all the people from California that doesn't involve parsing and sorting the file. Furthermore, this wondrous program should be able to accept statements that describe what you want in a language very similar to English. That way you can just say: "Give me all rows where the State column equals 'CA.'"

Yes, this would be great, but it isn't enough. There are still major problems that will need to be dealt with. These problems, which I'll discuss in the following pages, are the ones that made Codd his famous paper, and that made Ellison a billionaire.

## Data Anomalies

Dr. Codd's goal was to have a model of information that was dependable. All of the data-storage methods available to him had inherent problems. He referred to these as anomalies. There are three types of anomalies: Update, Delete, and Insert.

## Update anomaly

Now that we assume a table structure can quickly and easily handle multiple requests, we need to see what happens when the information gets complex. Adding some information to the previous table introduces some serious problems

Table 1-2 is meant to store information for an entire office, not just a single person. Since this company deals with large companies, there will be times more than one contact will be at a single office location. In Table 1-2, there are two contacts at 43rd St. At first may appear to be OK: we can get all the information available relatively easily. The problem comes when the BigCo decides to up and move to another address. In that case, we'd have to update the address for BigCo in two different rows.

Another concern is the potential for error. It's very possible that one of these rows would be altered one row at a time, while the other remains the same. Or, if changes are keyed in one row at a time, it's likely that somebody would introduce a typo. Then you're left wondering if the correct address is 1121 or 1211.
