Now the pertinent information to BigCo Co. is in its own table, named Companies. If you look at the next table (Table 1-4), named Contacts, you'll see that we have inserted another column, called company_id. This column references the company_id column of the Companies table. In Brad's row, we see that the company_id (the second column) equals 1. We can then go to the Companies table, look at the information and see all the relevant address information. What's happened here is we've created a relationship between these two tables—the name database.

We still have all the information we had in the previous setup, we just mentioned it. In this setup we can change the address for both Jay and Brad by altering only a row. That's the kind of convenience we're after.

Perhaps this leaves you wondering how we get information un-segmented. Relational databases give us the ability to merge or join tables. Consider the following statement, which is intended to give us all the available information for Brad: give me all columns from the contacts table where contact_id is equal to 1, and you're at it to throw all the columns from the Companies table where the company_id field equals the value shown in Brad's company column. In other words, in this statement, you are asking to join these two tables where the company_id fields are the same. The result of this request, or query, would look something like Table 1-5.

In the course of a few pages, you've learned how to solve a data-integrity problem by segmenting information and creating additional tables. But I have yet to give this problem name. When I learned the vocabulary associated with relational databases from a thick and expensive book, this sort of problem was called an update anomaly. There may or not be people using this term in the real world; if there are, I haven't met them. However, this term is pretty apt. In the table presented earlier in this section, if we were to update one row in the table, other rows containing the same information would not be affected.

## Delete anomaly

Now take a look at Table 1-6, focusing on row 3. Consider what happens if Mr. Doe is deleted from the database. This might seem like a simple change but suppose someone database wants a list of all the companies contacted over the previous year. In the current setup, we remove row 3 we take out not only information about John Doe, we remove information about the company as well. This problem is called a deletion anomaly.

If the information is moved to its own table, as we saw in the previous section, this won't be a problem. We can remove Mr. Doe and then decide independently if we want to remove the company he's associated with.

## Normalization

Now that we've shown you some of the problems you might encounter, you need to learn the ways to find and eliminate these anomalies. This process is known as normalization. Understanding normalization is vital to working with relational databases. But, anyone who has database experience, normalization is not the be-all and end of data design. Experience and instinct also play a part in creating a good database. In the examples presented later in this book, the data will be normalized, for the most part—but there will also be occasions when an unnormalized structure is preferable.

One quick caveat. The normalization process consists of several "normal forms." In this chapter, we will cover 1st, 2nd, and 3rd forms. In addition to these, there are also called Boyce-Codd normal form, 4th normal form, 5th normal form, and Domain-key normal form. In the real world, there are many forms. Getting data into 1st form is fairly easy. Data needs to the following criteria:

- Each column must be atomic. That means there will be only one value per cell.
- Each table must have a unique name.
- No two rows can be identical.
- No repeating groups are allowed.

## Part I: Working with MySQL

As we've already seen, row 1 and row 2 contain identical information. This is a repeating group. Only when we remove these columns and place them in their own table will this data be first normal form. The separation of tables that we did in 1-3 and 1-4 will move this data into normal form.

Before we move on to 2nd and 3rd normal form, you're going to need a couple of quick definitions. The primary key is a column or set of columns by which each can be uniquely identified. In the tables presented far, I have included a column with sequential values, and as rows are added to these tables the database engine will automatically insert an integer greater than the maximum value for the column. Every database in the world has some method of defining a column like this. In MySQL it's called auto_increment. Depending on your data, there are all kinds of values that will work for a primary key. Social security numbers work, do e-mail addresses and URLs. The data needs to be unique. In some cases, two or more columns may your primary key. For instance, continuing with our address book, if contact information needs to be stored for a company with many locations, it will probably be best to store the know and mailing address information in a table that has the company_id and company city as its primary key.

Next, we need to define the word dependency, which means pretty what you think it means. A dependent column is one that is obviously tied to the primary key. It can't exist in the table if the key is removed.
