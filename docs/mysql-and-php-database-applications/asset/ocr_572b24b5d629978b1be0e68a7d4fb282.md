# Blasted Anomalies

Dr. Codd's goal was to have a model of information that was dependable. All of the data-storage methods available to him had inherent problems. He referred to these as anomalies. There are three types of anomalies: Update, Delete, and Insert.

# Update anomaly

Now that we assume that a table structure can quickly and easily handle multiple requests, we need to see what happens when the information gets more complex. Adding some information to the previous table introduces some serious problems (Table 1-2)

Table 1-2 is meant to store information for an entire office, not just a single person. Since this company deals with large companies, there will be times more than one contact will be at a single office location. In Table 1-2, there are two contacts at 1121 43rd St. At this first may appear to be OK: we can get all the information available relatively easily. The problem comes when the BigCo decides to up and move to another address. In that case, we'd have to update the address for BigCo in two different rows. This might not sound like such an task, but consider if this table has 3,000 rows instead of 3—or 300,000 for that matter. Someone, or some program, has to make sure the data is changed in every appropriate place.

Another concern is the potential for error. It's very possible that one of these rows would be altered one row at a time, while the other remains the same. Or, if changes are keyed in one row at a time, it's likely that somebody would introduce a typo. Then you're left wondering if the correct address is 1121 or 1211.
