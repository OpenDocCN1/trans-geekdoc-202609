> There isn't a development tool on the planet that doesn't have its quirks. Every language and every database presents its own challenges. The more of these you are aware of before writing your application, the better off you will be.

The missing thing from MySQL that would have been nice to use is a more restrictive grant (please see Appendix D). As it stands, MySQL can grant authorities on several levels: for an entire instance, for a specific database, for tables within a database, or columns within a table. While this may sound quite extensive, it is not as complete as it could.

Consider this problem: in MySQL, using table- column grants, how you prevent a user who has only editor privileges, updating stories that are already live? The best way to go around it is to have very specific privileges in the stories table. If the stage_id for Live is 4, you'd want a grant to join have access to any of the rows in the stories table, except where stage_id = 4. Other databases allow this, but MySQL does not.

The best you could do with MySQL is provide backup to the content_users, content_stages, and user_stage_map tables. This backup plan will only work within the PHP scripts that access the database. If you grant permission, they will be able to log into the database via avenues over the Web. And, as we have mentioned, the rights you grant may not be as restrictive as you like. Grant rights at your discretion.

Here's how the secondary security works within the PHP scripts. When the administrator creates a stage, row is added to the content_stages table. In addition, a create query makes a table with a single column to store the stage_ids. For the proofreading stage, there is a table called proofreading_stories.

If you are logged into the application as a user listed in the content_admin table, you will have the rights to create this stage. The stage will first be added to the content_stages table. When you create the stage, you will indicate which of the users should have the authority to use this stage.
