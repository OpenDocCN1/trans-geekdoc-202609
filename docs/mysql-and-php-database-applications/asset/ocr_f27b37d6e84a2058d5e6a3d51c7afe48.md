# Chapter 11: Content Management System

# What do you need to prevent?

The major issue in application is ensuring that users do only what they are permitted to do, and absolutely no more. To do this, the application makes use of MySQL administrative privileges.

In all of the previous applications, there was a simple header file that called a function to log into the database. Each file ended up using the same dbconnect() call with the same username and password. That won't work because different users need different levels of access.

More, in this application some users are going to need the ability to access others. Workers will come and go and their responsibilities will change. Since we don't want everybody who needs to log into the database with the same rights, this application will need the facility to have different people log in different names and passwords.

Privileges in MySQL are granted and revoked by the aptly named grant state. It's fairly plain and is described in Appendix D. Before you move forward with this application, it might be worth taking a quick look at that appendix.

It's worth mentioning here in this application you will run into some of the weirder aspects of MySQL. If some of the design of this application seems a little strange, that's because it is. But proverbial bridge will be crossed in due time.

# Designing the Database

The schema represented in Figure 11-8 shows how this application divides its data. Keep in mind as you look at this that in database-development land there is usually more than one decent way to go about things. You might find a different way to arrange this type of data that works equally well. In fact, you may prefer another way. That's fine with the writers of this book. We encourage independent thought and creativity, as long as it does not result in immoral or ungodly behavior. Normalize your data as you see fit, but in the process please not violate any natural laws.

Start by looking at the story_author_map table. Notice how it is on the many end of one-to-many relationships with tables: the story table and the author table. This is a classic many-to-many relationship. The reason for this is as follows: It is possible that a single story will have more than one author, and it's more likely an author will contribute to more than one story. The forms as set up in the application do not at this point have a facility for adding multiple authors, but that's not enough to change if you wish. It's best to start with this flexibility, even if you don't need it right away.
