## What do you need to prevent?

There are essentially two things you need to be careful about here. The first is making sure you can track your users from page to page. The second is keeping credit-card numbers and other personal information away from prying eyes.

A couple of things here are worth noting. First notice the order is really the center of the works. Every table, in one way or another, is related to the order. The order table stores a user_id, address_id, and all the needed payment information. Notice that the order table has a one-to-many relationship with the items table. That's because each order can have many items, which makes sense.

![](img/245156cc770929860a3ede93c01f9981_394_0.png)

Think about whether or not you want to store credit-card numbers in your database. We have included a column for the credit card number, but that doesn't mean you should use it. First consider if your box is secure enough. If you're not sure of the answer, the answer is no. If you are using a shared server, maybe a secure server offered by your ISP, you should consider it unsafe for storing card numbers. Other people will have access to that box and they will be able to see what you've written to the database. Keep in mind there is no requirement that you store the credit-card numbers anywhere. You can simply validate the number and drop it from memory. If it is never written to a disk, it will be very hard to steal.

Notice that user and address information is separated. This is so you can enable a single user (who will identify him—or herself by an e-mail address) to supply two addresses—may work and home.
The shipping table will store options for moving your goods. It might have options for UPS, USPS, and Fed Ex, if you choose. I'll talk a little more about these options in the "Code Overview".
The status table will enable you to know if the order is backordered, shipped, cancelled, and the cc_types table store credit cards that you're willing to accept.

CREATE TABLE orders (
