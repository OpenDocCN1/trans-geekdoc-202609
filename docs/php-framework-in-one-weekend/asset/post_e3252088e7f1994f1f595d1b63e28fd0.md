## Chapter 10

### Reuse

At the moment our framework is not very useful because it’s tied very closely to the example app we’ve been building. The point of building a framework is to have a collection of reusable code. We should be able to include this in a project when we want to do something similar, to save us having to do all the ground work again. In order to be able to do that we need to make our code as reusable as possible.

Up until now, we have put all our PHP code into the src folder. We also have PHP code, managed by Composer, in the vendor folder. Eventually, we could make our framework a separate project and include it via Composer, but for now we will store it in a separate folder in our project. This will allow us to identify and separate out the reusable bits of our framework.

Create a folder called lib/weekend and move all the code that is currently in the src folder into this new location. If you try to access the application now you will get an error, like: “Uncaught Error: Class Weekend\App not found”. We need to tell Composer that we’ve move the code for the namespace Weekend and update its autoloader. Edit the autoload section of composer.json as per listing 10.1. Notice how we also add our src folder to the autoloader config so it can find our site’s code. In this example, I’m not using a namespace for my site-specific code.

```
19 "autoload":{
20 "psr-4":{
21 "Weekend\\": "lib/weekend",
22 "": "src/"
23 }
24 }
```

Use Composer’s update or dump-autoload commands to recreate the autoloader. You should now find that the site is working again (assuming you still have PHP’s built-in webserver running).

We can now put our site-specific code into the src folder. First, move both of the controllers back into src as they are specific to this site. This creates a new error, as the dependency injection container can no longer find them. To get around this we add a services.yml file to the src folder for site-specific configuration. Refer to 10.2 to see how we update the constructor in App so that it can find our extra configuration. Listing 10.3 shows the new file with the additional configuration.

Notice that we are loading the services.yml file that is local to the App into the dependency injection container first. This allows us to specify the dependencies that are core to our framework. We then load a second services.yml Configuration from the src folder. This allows our app to supply additional configuration, such as site-specific controllers, to the dependency injection container. This is a useful mechanism as it will also allow us to override framework configuration on a site-by-site basis.

The second load() call in the App constructor (line 19, listing 10.2) looks like it has potential to cause us bugs in the future. You might want to consider alternative ways to provide the location of this extra configuration so that it’s not hard-coded in the framework. For example, you might want to provide a root directory option that can be set when instantiating the App.

The previous router in the run() method of App had the routes hard coded in it. This won't work because the framework no longer knows about what routes are available. To make the router more general we allow the user to configure their own routes. A simple example is provided in listing 10.2 which uses an addRoute() method to build an array of available routes in the App. This is used by the router in run(), lines 33-38, listing 10.2.

We also have to make a small change to the get() callback on the BasicPageController. To allow for the generalised router code, all route callbacks on controllers take the same parameters.
