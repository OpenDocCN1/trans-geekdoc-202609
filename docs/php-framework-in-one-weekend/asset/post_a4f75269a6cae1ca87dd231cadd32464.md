
## HTTP Requests

PHP makes the data from the incoming request available as global variables. They look like this:

```php
$name = $_GET['name'];
```

We don’t want to work with these global variables directly. And, now we have a library of code to make working with HTTP messages easier, we don’t have to. The HTTP Foundation component can create a request object for you from the data provided by PHP in the global variables.

When we used the Composer require command to download the package it added it to the autoloader so that the classes are automatically available to us. The code for them will be automatically included when we first use the class in our code. We can create an object to represent the request like this:

```php
$request = \Symfony\Component\HttpFoundation\Request::createFromGlobals();
```

When we are including code from multiple packages we need to ensure that the names of things defined by the packages don’t clash. PHP provides a feature called namespaces that protects against naming collisions. You can see in the previous example that the Request object provided by the HttpFoundation component has the _fully qualified_ name:

```php
\Symfony\Component\HttpFoundation\Request
```

Because we don’t have anything called Request in this file there will not be a clash of names. We can therefore tidy up our code by _importing_ the name to our local scope with PHP’s use keyword. You can see this demonstrated in listing 3.2 (lines 2 and 5).

Now we have an object we can use to get information from the request:

```php
$name = $request->get('name');
```

You will notice that I have also added a print_r statement to our example page (line 16, listing 3.2) so you can see the structure of the $request object. Listing 3.2 shows our new public/index.php file.

```php
1 <?php
2 use Symfony\Component\HttpFoundation\Request;
3 require __DIR__.'../vendor/autoload.php';
4
5 $request = Request::createFromGlobals();
6 $name = $request->get('name');
7 ?>
8 <!DOCTYPE html>
9 <html lang="en">
10 <head>
11 <meta charset="UTF-8">
12 <title>Document</title>
13 </head>
14 <body>
15 <h1>Hello <?php print $name; ?>!</h1>
16 <pre><?php print_r($request); ?></pre>
17 </body>
18 </html>
```

### Listing 3.2: public/index.php

Start PHP’s built-in web server (if it’s not already still running from before) and load up the page in your browser to check it works.

```bash
$ php -S localhost:4000 -t public/
```

Be sure to provide a value for the $name parameter in the URL, like this:

```
http://localhost:4000/?name=World
```

NB: Directly printing out user input is never a good idea. It is the easiest way to introduce security issues into your code. In this example we have taken the $name variable directly from user input and then printed it out. In reality you would filter this value to remove any dangerous characters to prevent against cross-site scripting (XSS). We’re not doing this here because we’re going to use a templating system that takes care of this for us. You can confirm that this is insecure by loading the following URL:

```
http://localhost:4000/?name=Danger<script>alert('hi!')</script>
```

You will see a JavaScript alert. The code in the GET parameter is embedded directly in the page. You don’t have to be a security expert to realise that allowing users to inject JavaScript code into the page is a bad idea.

## Chapter 4
### Templating

At the moment we’ve got all of our code in one source file (index.php). In our PHP web framework we want to separate our logic from the display. This will be more scalable and easier to maintain as our project gets bigger. It also means that designers can work on the templates separately without having to know any PHP code. We can also benefit from security features such as automatic escaping (filtering of dangerous content).

There are many template engines available as PHP packages^1. You (or your web designers) might have a favourite. You might want to use a specific template because it’s supported by other tools in your workflow. Mustache[13] is popular because it has implementations in almost every language, but some find it’s logic-less templates limiting. We will be using Twig[29] because it’s “flexible, fast, and secure.”

Let’s install Twig using Composer:

```bash
$ composer require twig/twig
```

The require section of your composer.json configuration file should now look like listing 4.1.

```json
9 "require": {
10 "symfony/http-foundation": "^3.0",
11 "twig/twig": "^1.24"
12 }
```

### Listing 4.1: composer.json

Create a template folder inside your project and create a new file called templates/index.html as per listing 4.2.

^1 You can use the Packagist website to search for PHP packages. Here is a search for “template” sorted by number of downloads[15].

```html
1 <!doctype html>
2 <html lang="en">
3 <head>
4 <meta charset="UTF-8">
5 <title>Document</title>
6 </head>
7 <body>
8 <h1>Hello {{ name }}!</h1>
9 </body>
10 </html>
```

### Listing 4.2: templates/index.html

The Twig website has a full reference for the template syntax[28]. Notice how it uses {{ and }} to delimit expressions. The content outside the delimiters is output as HTML. The expressions inside the delimiters are evaluated and their output inserted into the HTML. In this example the simple expression {{ name }} evaluates to the value of the provided name variable. You will see below how to pass in all the variables a template expects.

Now let's get the rest of the system converted over to use templates. This means changing public/index.php so that it no longer has HTML markup hard-coded inside it. For now, we will replace this with the code to load and execute Twig.

Twig is a very flexible system made up of various components. To get started you just need a *Template Loader* so that Twig knows how to load template files, and a *Twig Environment* where all template processing happens.

Listing 4.3 shows the new public/index.php file, with the template loader created in line 9 and the Twig environment loaded in line 10.

```php
1 <?php
2 use Symfony\Component\HttpFoundation\Request;
3 require __DIR__.'.././vendor/autoload.php';
4
5 $request = Request::createFromGlobals();
6
7 $name = $request->get('name');
8
9 $loader = new Twig_Loader_Filesystem(__DIR__.'.././templates');
10 $twig = new Twig_Environment($loader);
11
12 echo $twig->render('index.html',['name' => $name]);
```

### Listing 4.3: public/index.php

The HTML markup has been removed, and is now generated when we call the render() method on the $twig object on line 12. The call to $twig->render() takes two arguments. The first is the template name, and the second is the array of *template variables* to pass to the template. In our template file (templates/index.html) we had one expression {{ name }} that referenced one variable called name. In the call to render we pass the $name variable we retrieved from the request object.

Run the PHP built-in web server again, if not still running from before. If you load the following URL you should see “Hello World!”.
http://localhost:4000/?name=World

Notice that if you go directly to http://localhost:4000 without providing the name parameter you just see “Hello !” The basic test script we created in chapter 2 (listing 2.1) will fail. Let’s fix this by providing a default value for name.

Listing 4.4 shows the use of Twig’s default() filter. The pipe symbol (|) is used to *pipe* the output of the *name* variable into the *default* filter. Twig has many filters available[12]. This one simply provides a default value, if the input is empty.

```html
1 <!doctype html>
2 <html lang="en">
3 <head>
4 <meta charset="UTF-8">
5 <title>Document</title>
6 </head>
7 <body>
8 <h1>Hello {{ name | default('World') }}</h1>
9 </body>
10 </html>
```

### Listing 4.4: templates/index.html

NB: As an aside, you might like to test how this fixes the security issues discussed at the end of the last chapter. You could try accessing the same insecure URL, except this time notice how you see Hello Danger<script>alert(...)</script>! in the output. Twig is automatically filtering the variable on output. The HTML tags are escaped so they display on the page, rather than being interpreted as valid script tags.
