
## App Class

Now we are ready to start adding other routes to our application. Let’s tidy things up a bit first by creating a separate App class for our code. We will then move the code out of our index.php so we can be a bit more organised.

We need our own namespace so when we define our App class we don’t have to worry about clashing with other things called App in the future. We also use this namespace to configure Composer with the location for our source code. Let’s use Weekend as our namespace.

Create a src folder in the root of our project. This will be where our source code goes. From now on we will only use the public folder for publicly accessible resources, separate from our source code. The public folder will contain our static assets like images, CSS, and JavaScript. We will also need to keep the public/index.php file as this is where all web requests get routed to. We will change the public/index.php file so it just loads and runs our App.

We create the source file for our application in src/App.php. We follow the PSR-4 specification[19] for naming our files and classes. We tell Composer where our source files are and then it will add them to its autoloader. This means we don’t need to include all our source files as they will be loaded automatically when needed.

Listing 6.2 shows the code for the new App class that we put in src/App.php, using the code from our previous index.php file. Listing 6.3 shows the new index.php file that loads and runs our App.

### Listing 6.2: src/App.php

```php
<?php
namespace Weekend;

use League\Flysystem\Adapter\Local;
use League\Flysystem\Filesystem;
use Symfony\Component\HttpFoundation\Request;
use Symfony\Component\HttpFoundation\Response;
use Twig_Environment;
use Twig_Loader_Filesystem;

class App
{
    public function run(Request $request)
    {
        $adapter = new Local(__DIR__ . '/../data');
        $filesystem = new Filesystem($adapter);
        $variables = json_decode($filesystem->read('menu.json'), true);
        $loader = new Twig_Loader_Filesystem(__DIR__ . '/../templates');
        $twig = new Twig_Environment($loader);
        $content = $twig->render('index.html', $variables['index']);
        return Response::create($content);
    }
}
```

### Listing 6.3: public/index.php

```php
<?php
use Symfony\Component\HttpFoundation\Request;

require __DIR__ . '/../vendor/autoload.php';
$request = Request::createFromGlobals();

$app = new \Weekend\App();
$response = $app->run($request);
$response->send();
```

If you try and run this now you will get an error. The message will appear in your browser or your PHP error logs, depending on how you've got things configured. It will say Class Weekend\App not found. This is because we have not yet included our class in the autoloading system. To do this we need to add it to the composer.json configuration. Create a psr-4 entry under autoload and map the Weekend namespace to our src/folder. Composer is particular about the formatting here. The file must be valid JSON. Take care to not add a superfluous comma, or miss the double backslash at the end of the namespace. Listing 6.4 shows the updated composer.json file.

### Listing 6.4: composer.json

```json
{
    "name": "darrenmothersel/php-framework",
    "authors": [
        {
            "name": "Darren",
            "email": "darren@darrenmothersele.com"
        }
    ],
    "require": {
        "symfony/http-foundation": "^3.0",
        "twig/twig": "^1.24",
        "league/flysystem": "^1.0"
    },
    "autoload": {
        "psr-4": {
            "Weekend\\": "src/"
        }
    }
}
```

Now use the dump-autoload Composer command to re-generate the autoloader:

```bash
$ composer dump-autoload
```

You only need to run this command if you manually edit the autoloader settings in the composer.json file. The autoloader is re-generated automatically when you use Composer to update or require new packages.

## Routing

Now we are ready to implement a basic router. In the previous step we moved all the functionality into a run() method on our App class. The run() method takes a Request object as input, and returns a Response object. This is the foundation for all web apps, and all web frameworks have this basic functionality.

The limitation of our simple app (in its current state) is that the functionality is hard coded into the run() method. We will need a way to route calls to different functionality depending on the request.

First let's try a simple router that uses the information in the request and the configuration in the data/menu.json file we created earlier. We get the requested path from the request using the getPathInfo() method:

```php
$path = $request->getPathInfo();
```

Now we can alter the $content of the response by inspecting the $path variable. For example, by using a switch statement like this:

```php
$content = "";
switch ($path) {
case '/':
case '/index':
    $content = $twig->render('index.html', $variables['index']);
    break;
case '/about':
    $content = $twig->render('index.html', $variables['about']);
    break;
}
```

This switch statement defines two different routes and the corresponding code for each. We will come back to this, but you may already see ways to improve this. In our run() method we then just need to wrap the $content in a Response and return it. We also do an error check and return a 404 when the path was not matched:

```php
if (empty($content)) {
    return Response::create("Not found", 404);
}
return Response::create($content);
```

You can confirm this works by trying each one of these URLs:

- http://localhost:4000/
- http://localhost:4000/index
- http://localhost:4000/about

Also, try loading a URL that does not have a route defined and check that you get a 404 error:

```
http://localhost:4000/contact
```

## Chapter 7

### Controllers

We’ve come a long way since our first “Hello World!” example where we did everything in a single PHP script. We now have some structure in place, but everything is still in the single run() method of our App class.

In a web framework you will often find that separate objects are responsible for different types of request. The front controller dispatches the request to the appropriate controller to generate the response. The two routes we have defined so far could both be handled by the same controller. If you look at the basic router we created, the code that generates the content is almost the same. Let’s create a BasicPageController class that encapsulates this functionality.

Following the naming rules for autoloading from PSR-4, we create a folder for our controllers called src/Controller. Our Weekend namespace maps to the src folder, so the namespace for our controllers will be Weekend\Controller. If we ever need to refer to our new controller class in full it will be called Weekend\Controller\BasicPageController. Listing 7.1 shows the code of our new BasicPageController class.

### Listing 7.1: src/Controller/BasicPageController.php

```php
<?php
namespace Weekend\Controller;

use League\Flysystem\Adapter\Local;
use League\Flysystem\Filesystem;
use Symfony\Component\HttpFoundation\Response;
use Twig_Environment;
use Twig_Loader_Filesystem;

class BasicPageController
{
    protected $filesystem;
    protected $menu;
    protected $twig;

    public function __construct()
    {
        $adapter = new Local(__DIR__ . '/../../data');
        $this->filesystem = new Filesystem($adapter);
        $this->menu = json_decode($this->filesystem->read('menu.json'), true);
        $loader = new Twig_Loader_Filesystem(__DIR__ . '/../../templates');
        $this->twig = new Twig_Environment($loader);
    }

    public function get($path)
    {
        $page = ($path == '/') ? 'index' : substr($path, 1);
        if (isset($this->menu[$page])) {
            $content = $this->twig->render('index.html', $this->menu[$page]);
            return new Response($content);
        }
        return Response::create("not found", 404);
    }
}
```

The constructor (lines 16-25) now deals with creating the filesystem and the Twig environments. We also load the content of menu.json into a $menu variable so that it can be used later in our _controller callback_. The get() method (lines 27-36) is our callback to which the router will _dispatch_ requests defined for this controller. The code which dealt with handling the response, that was previously hard-coded into the router has been moved from App’s run() method to this controller’s get() method.

Line 29 in the get() callback checks for a default path, and drops the leading / from paths. The value of $page is used to fetch the appropriate section of the $this->menu array that was created in the constructor by reading from menu.json file.

The router in our App class is now much simpler. We route all three of the defined paths to the same controller. Listing 7.2 shows the new routing code in our run() method.

### Listing 7.2: src/App.php

```php
public function run(Request $request)
{
    $path = $request->getPathInfo();
    switch ($path)
    {
    case '/':
    case '/index':
    case '/about':
        $controller = new BasicPageController();
        return $controller->get($path);
    }
    return Response::create("Not found", 404);
}
```
