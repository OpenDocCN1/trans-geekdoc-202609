
## DI Container

We’ve seen how using dependency injection simplified our controller classes. In general, dependency injection makes code easier to maintain, easier to reuse, and more testable. But, it made the code that called our controllers do more work as the calling code had to create and pass in the dependencies before it could use the controllers. We also instantiated the $filesystem dependency even though it wasn’t used on every request. We can fix both of these issues by using a dependency injection container.

Let’s get a bit abstract for a second, so we can see in more detail how dependency injection works. We have a class A that needs a B, but we don’t want to hard code the creation of B inside A. So we pass B into A’s constructor.

Instead of this (pseudocode):

```
class A
{
public function doSomething() { $b = new B();
return $b->run($this->data);
}
}
$a = new A();
$a->doSomething();
```

We use dependency injection, and do this:

```
class A {
protected $b;
public function __construct(B $b) {
$this->b = $b;
}
public function doSomething() {
return $this->b->run($this->data);
}
}
$b = new B();
$a = new A($b);
$a->doSomething();
```

But what if b also has dependencies? And those dependencies have dependencies? The process of creating an object could get very complex. You end up with:

```
$d = new D();
$c = new C();
$b = new B($c, $d);
$a = new A($b);
$a->doSomething();
```

When all you really wanted to do was:

```
$a = new A();
$a->doSomething();
```

The solution provided by most PHP web frameworks is some mechanism for managing dependencies and dependency injection. Essentially, this is just a recommended way of creating objects and configuring the dependencies they require. This is usually called a container. Our pseudocode example using a container might look something like this:

```
$container->get('A')->doSomething();
```

There are many options available for PHP, including:

- Symfony provides a DI component[26] that allows you to configure dependencies using XML, JSON or PHP.
- Pimple[24] is a good stand-alone option that is used by the Silex micro-framework.
- Container[11] is a solution offered by the same team of developers that created the filesystem abstraction we are using.
- Auryn[1] provides auto-wiring of dependencies.

### Note
It is important to note that the DI container should only be used to create the objects needed to run your app. You should never pass a DI container into a class as a dependency. This actually happens quite a lot, and is considered an *anti-pattern* (i.e. opposite to best practise). What you've done in this case is convert your DI container into a *service locator* which does the opposite of what dependency injection should do. It hides dependencies deep inside your classes, when you're really trying to expose and provide all dependencies at the top level.

## Using a DI Container

We will configure a dependency injection container to create objects and their dependencies when we request them. Doing this means that our objects will only get instantiated when they are needed, and make the calling code easier to write as we will be able to just create objects, without worrying about instantiating dependencies first.

We will use the Symfony Dependency Injection container and a YAML configuration file. Use the Composer require command to install these PHP packages as dependencies:

```
$ composer require symfony/dependency-injection
$ composer require symfony/config
$ composer require symfony/yaml
```

We can now remove the _global services_ we created in App and replace them with the Container:

```
protected $container;
public function __construct() {
$this->container = new ContainerBuilder();
$loader = new YamlFileLoader($this->container, new FileLocator(__DIR__));
$loader->load('services.yml');
}
```

This code uses a YamlFileLoader to load up a configuration file where our _service_ definitions are stored. Listing 8.2 shows the services.yml config file for our example. The format of this file is defined by the Symfony DI container. It allows you to specify a parameters section, and a list of services. The services are the objects that the container knows how to build. The configuration for each one specifies which class is used, and what arguments are needed for its constructor. These can reference other services (dependencies) or configuration from the parameters section.

```
parameters:
  template_dir: '../templates'

  data_dir: '../data'

services:
  loader:
    class: Twig_Loader_Filesystem
    arguments: ["%template_dir%"]
  twig:
    class: Twig_Environment
    arguments: ["@loader"]
  adapter:
    class: League\Flysystem\Adapter\Local
    arguments: ["%data_dir%"]
  filesystem:
    class: League\Flysystem\Filesystem
    arguments: ["@adapter"]
```

**Listing 8.2:** src/services.yml

We get objects out of the container when we need them. Only the dependencies that actually get used will be instantiated, and the container will wire together all the dependencies for us. We just request the item we want, like this:

```
$fs = $this->container->get('filesystem');
```

So, as an example, our /contact route becomes this:

```
case '/contact':
$twig = $this->container->get('twig');
$controller = new ContactController($twig);
if ($method == 'POST') {
return $controller->post($request);
}
return $controller->get();
```

As you can see, in this example, we get() the dependency from the container, and pass it to the controller as before. We should probably add this dependency to our configuration as well. Let's add the controllers to our services.yml file then use the container to create them.

The configuration for our ContactController is quite simple, as it just has a dependency on Twig. We add this to the services: section of our services.yml file:

```
contact_controller:
  class: Weekend\Controller\ContactController
  arguments: ['@twig']
```

We can now get the controller directly from the DI container. It will automatically create the Twig dependency that is required when creating the contact controller. The **BasicPageController is a bit more complicated because we are doing some processing** of the menu config before we pass it to the constructor. To help with this we will create a service class that will load and manage our configuration. Create a src/Service folder and use listing 8.3 as a guide for creating the ConfigService class.

```
<?php
namespace Weekend\Service;

use League\Flysystem\FilesystemInterface;

class ConfigService
{
  protected $config;
  public function __construct(FilesystemInterface $fs)
  {
    $this->config = json_decode($fs->read('menu.json'), true);
  }

  public function getConfig()
  {
    return $this->config;
  }
}
```

**Listing 8.3:** src/Service/ConfigService.php

Aside In the ConfigService class constructor I have actually defined the parameter type as FilesystemInterface. An interface is a bit like a contract. It doesn't specify any details about the implementation, it only states what functionality exists. It’s a specification. Classes can declare that they implement the interface specification, meaning that they provide an implementation for all the functionality described by the interface specification. This allows us to easily swap in other implementations later. We only use functionality defined in the interface, so we can be sure that any other implementation provided will work.

We can now add this ConfigService to our services.yml file:

```
config_service:
  class: Weekend\Service\ConfigService
  arguments: ['@filesystem']
```

And also add the BasicPageController which depends on Twig and this new config service:

```
basic_page_controller:
  class: Weekend\Controller\BasicPageController
  arguments: ['@twig', '@config_service']
```

Update the constructor in BasicPageController to take the ConfigService as a dependency, rather than the raw menu data that was being passed before:

```
public function __construct(Twig_Environment $twig, ConfigService $config) {
$this->twig = $twig;
$this->config = $config;
}
```

Update the get() callback in the controller so that it fetches the $menuConfiguration from the ConfigService:

```
public function get($path) {
$Page = ($path == '/') ? 'index' : substr($path, 1);
$menu = $this->config->getConfig();
if (isset($menu[$Page])) {
$content = $this->twig->render('index.html', $menu[$page]);
return new Response($content);
}
return Response::create("not found", 404);

```

And then finally, tidy up the router so that it now fetches the controllers from the container:

```
switch ($path) {
case '/':
case '/index':
case '/about':
$controller = $this->container->get('basic_page_controller');
return $controller->get($path);
case '/contact':
$controller = $this->container->get('contact_controller');
if ($method == 'POST') {
return $controller->post($request);
}
return $controller->get();
}
```

Maybe you can start to think about ways to improve this. The run() method now doesn't have to deal with instantiating dependencies and controllers. In run() we are just dealing with routing requests to the correct controller callback. How would you extract the route configuration from the router logic? This is something we’ll come back to, but for now consider the following example. Can you see how to improve it?

```
public function run(Request $request) {
$path = $request->getPathInfo();
$method = strtolower($request->getMethod());
$routes = [
'/' => 'basic_page_controller',
'/index' => 'basic_page_controller',
'/about' => 'basic_page_controller',
'/contact' => 'contact_controller',
];
if (isset($routes[$path])) {
$controller = $this->container->get($routes[$path]);
if (is_callable([$controller, $method])) {
return call_user_func_array([$controller, $method], [$request]);
}
}
}
```
