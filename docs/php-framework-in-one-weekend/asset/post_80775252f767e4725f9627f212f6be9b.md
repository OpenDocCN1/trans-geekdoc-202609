
## Chapter 1: Managing Complexity

A lot of what we do this weekend will seem like overkill. This is because the examples are simple in order to demonstrate the concepts in use on more complex systems. As projects get bigger, and complexity increases, you need ways to manage complexity. In web development, we tackle complexity by layering.

When you write code you write instruction statements. These statements are grouped into functions (or methods) which are grouped into classes, which are combined into systems. Once this all gets so big you can’t fit it in your head, you can’t reason about it. We need to keep the design of the system as simple as possible.

In order to simplify design, we split things into separate chunks. These chunks have many names, such as modules, packages, components, and libraries. The aim is to make them as self-contained as possible. When a component’s dependencies are minimised we say it is loosely coupled (as opposed to tightly coupled). We group all the related components (i.e. those that share dependencies) so that we can think about them independently from the rest of the system. It often looks like we’ve split the design of the system into layers. We call this process layering.

In modern PHP we talk about packages a lot. These are separate blocks of reusable code with minimal dependencies and a clean, well-defined API. When we create our own apps we prefer to reuse functionality provided by packages, rather than create our own. Packages vary in size from a few functions, through to entire sub-systems.

A framework is a collection of components that work well together. Traditionally the components in a framework will have been designed and bundled together to fulfil a specific type of problem. Increasingly, thanks to the wide open-source ecosystem of PHP packages, we’re able to pull together components from different sources and have them work together easily.

The packages that our project depends on are defined in a configuration file called composer.json which exists in the root folder of our codebase.

Use the Composer init command to create a composer.json file interactively. You will be prompted for some details about your project and asked if you want to define dependencies interactively. Respond with no to skip adding dependencies (require) and dev dependencies (require-dev) for now.

```
$ mkdir php-framework
$ cd php-framework
$ composer init
```

You should now have a project folder called php-framework with a bare Composer config file (composer.json) that looks a bit like this:

```
1 {
2 "name": "darrenmothersole/php-framework",
3 "authors": [
4 {
5 "name": "Darren",
6 "email": "darren@darrenmothersel.com"
7 }
8 ],
9 "require": {}
10 }
```

Listing 1.1: composer.json

The require section is where we will list all the packages that our project depends on and what versions we require. Composer will download them all into a vendor folder, and create an autoloader to make them available in our PHP code.

### Autoloading

PHP doesn’t need to load up all your app and dependencies on every request. Each request will use only a small fraction of the code. In modern PHP we split our code into multiple files, usually one class per file, and then only include the files we need to deal with the current task in hand. To make this process easier for the developer PHP has an autoloading mechanism. It means you don’t have to specify which files to include for each request. PHP will use the autoloader to work out which files to include when they are needed. Composer creates an autoloader for us based on the configuration in our composer.json file.

Use the composer install command to download dependencies and create the autoloader.

```
$ composer install
```

We have not specified any required packages yet, so nothing is downloaded to our project. Composer just creates the autoloader in the vendor/composer folder. We load this in our app by including the vendor/autoload.php file.

### Hello World

Now let's get a simple page up and running. In modern PHP we keep our source code separate from our web accessible resources. Create a public folder into which we will put all publicly accessible files. In this folder create an index.php file as per listing 1.2.

```
1 <?php
2 require __DIR__.'../vendor/autoload.php';
3 $name = "World";
4 ?>
5 <!DOCTYPE html>
6 <html lang="en">
7 <head>
8 <meta charset="UTF-8">
9 <title>Document</title>
10 </head>
11 <body>
12 <h1>Hello <?php print $name; ?>!</h1>
13 </body>
14 </html>
```

Listing 1.2: public/index.php

Then use PHP's built in web server to view the content:

$ php -S localhost:4000 -t public/

Now if you go to http://localhost:4000/ in a browser you should see “Hello World!”.

### Testing

Testing is an important concept in modern PHP development, and it would not do it justice to try and cover it in this weekend. For our purposes we will define a simple test script, but on real projects you will more likely use a testing framework like PHPUnit[17].

At the moment, all our application does is print out “Hello World!”. If we were to write a test for this we would request the page, then check that it contains the text “Hello World!”. Create a file called test.php as per listing 2.1.

```
1 <?php
2 ob_start();
3 include 'public/index.php';
4 $output = ob_get_clean();
5 echo strpos($output, "Hello World!"), PHP_EOL;
```

Listing 2.1: test.php

This simple test starts an output buffer, includes the index.php file, then grabs the content of the buffer into a string variable $output. The final line of the script tests that the string “Hello World!” occurs in the output.

You can now run this test from the command line using PHP:

```
$ php test.php
109
```

You should see a number (like 109) printed out. This is the position of the “Hello World!” string within the output. If you see a blank line then the test failed to find the required “Hello World!” string in the output.

You can probably imagine how testing in this way will get complicated and time consuming as your project gets bigger. At some point you will want to use a testing framework.

We will also strive to make our code easy to test by separating out functionality into components so they can be tested independently.

In the example above we are testing more than just the correct output of our $name variable. We are also testing any other functionality in the index.php file. This will become more clear as the project gets bigger. Ideally we want a way to test every bit of functionality independently. For example, if the output in our very basic app was generated by a callback function, we could test this single function independently:

```
1 <?php
2 require 'vendor/autoload.php';
3 $controller = new HelloController();
4 $output = $controller->run("World");
5 if ($output == "Hello World!") echo "Test Passed!";
```

Listing 2.2: test.php

This is just pseudo code. It doesn’t need to make sense right now, just notice how we are only testing the run() method of the controller. And, we are only testing under specific circumstances (i.e. when it’s input is equal to “World”). Compare this to the previous example in listing 2.1 and see how the test is now more targeted. When a test is targeting one specific unit of code we call it a unit test. Hence the name of PHP’s most popular testing framework PHPUnit.

## Chapter 3: HTTP

Our web framework is going to deal with HTTP messages. We will receive a HTTP request, and return a HTTP response.

We need to parse and extract information from the HTTP request. What resource is being requested? What action is to be taken? What content types does the client accept? Our application may be accepting input from the user, in which case we'll need to look in the HTTP request for form field inputs, url parameters, and uploaded files.

We also need to construct a valid HTTP response so the client can understand what we are sending back to them in reply to their request. This includes the content, and information about the format and how it is encoded.

Rather than studying the specifications of HTTP messages and URIs we can use a PHP package that hides all the details and provides a more developer-friendly way of receiving and creating HTTP messages. The PHP FIG (Framework Interoperability Group) has defined a standard set of HTTP message interfaces[20] which frameworks and PHP packages can adopt to improve interoperability. You can search Packagist[14] for popular PHP packages related to HTTP. We will use the most popular HTTP message abstraction, the Symfony HttpFoundation component[27]. It is the same component used in many popular PHP systems like Drupal and Laravel.

Let's go back to our composer.json and add the HTTP Foundation component to our requirements, so Composer can install it in our project. You can edit the composer.json file manually, or use the Composer require command:

```
$ composer require symfony/http-foundation
```

This will download the most recent stable version. At the time of writing this is v3.0.6. You will notice that it also downloads the mbstring polyfill package because it is a required dependency of the HTTP Foundation component. The require section of your composer.json configuration file now looks something like listing 3.1.

```
9 "require": {
10 "symfony/http-foundation": "^3.0"
11 }
```
