
## Use Atomic Column Values

Using atomic column values means that for each attribute in each row, you store only one thing. For example, you need to know what books make up each order. You could do this in several ways.

One solution would be to add a Column to the Orders table listing all the books that have been ordered, as shown in Figure 8.5.

# ORDERS

| OrderID | CustomerID | Amount | Date | Books Ordered |
|---|---|---|---|---|
| 1 | 3 | 27.50 | 02-Apr-2007 | 0-672-31697-8 |
| 2 | 1 | 12.99 | 15-Apr-2007 | 0-672-31745-1, 0-672-31509-2 |
| 3 | 2 | 74.00 | 19-Apr-2007 | 0-672-31697-8 |
| 4 | 3 | 6.99 | 01-May-2007 | 0-672-31697-8, 0-672-31509-2 |

Figure 8.5 With this design, the Books Ordered attribute in each row has multiple values

This solution isn't a good idea for few reasons. What you're really doing is nesting a table inside one column–table that relates to orders. When you set up your columns this way, it becomes more difficult to answer questions as "How many copies of Java 2 for Professional Developers have been ordered?" Instead, it has to parse each attribute value to see whether it contains a match anywhere inside it.

Because you're creating a table-inside-a-table, you should really just create that new table. This new table, called Order_Items, is shown in Figure 8.6.

# ORDER_ITEMS

| OrderID | ISBN | Quantity |
|---|---|---|
| 1 | 0-672-31697-8 | 1 |
| 2 | 0-672-31745-1 | 2 |
| 2 | 0-672-31509-2 | 1 |
| 3 | 0-672-31697-8 | 1 |
| 4 | 0-672-31745-1 | 1 |
| 4 | 0-672-31509-2 | 2 |
| 4 | 0-672-31697-8 | 1 |

Figure 8.6 This design makes it easier to search for particular books that have been ordered

## Designing Your Web Database

This table provides a link between the Orders and Books tables. This type of table is common when a many-to-many relationship exists between two objects; in this case, one order might consist of many books, and each book can be ordered by many people.

When you have a problem to solve that needs non-atomic column values, you should consider using a database that is designed for that type of data, instead of a relational database. These databases are non-relational, and often referred to as NoSQL databases or datastores. (NoSQL datastores are not covered in this book.)

## Choose Sensible Keys

Make sure the keys you choose are unique. In this case, we created a special key for customers (CustomerID) and for orders (OrderID) because these real-world objects might not naturally have an identifier that can be guaranteed to be unique. You don't need to create a unique identifier for books; this has already been done, in the form of an ISBN. For Order_Items you can add an extra key if you want, but the combination of the two attributes OrderID and ISBN is unique as long as one copy of the same book in an order is treated as one. For this reason, the table Order_Items has a Quantity column.

## Think About What You Want to Ask the Database

Continuing from the previous section, think about what questions you want the database to answer. (For example, what are Book-O-Rama's best-selling books?) Make sure that the database contains all the data you require and that the appropriate links exist between tables to answer the questions you have.

## Avoid Designs with Many Empty Attributes

If you wanted to add book reviews to the database, you could do so in at least two ways. These two approaches are shown in 8.7.

# BOOKS

| ISBN | Author | Title | Price | Review |
|---|---|---|---|---|
| 0-672-31697 | Michael Morgan | Java 2 for Professional Developers | 34.99 | |
| 0-672-31745-1 | Thomas Dunn | Installing GNU/Linux | 24.99 | |
| 0-672-31509-2 | Pruitt et | Teach Yourself GIMP in 24 Hours | 24.99 | |

# BOOKS_REVIEWS

| ISBN | Review |
|---|---|

Figure 8.7 To add reviews, you can either add a Review column to the Books table or add a table specifically for reviews

The first way means adding a Review column to the Books table. This way, there is a field for the Review to be added for each book. If many books are in the database, and the reviewer doesn't plan to review all, many rows won't have a value in this attribute. This is called having a null value.

Having many values in your database is a bad idea. It wastes space and causes problems when working out totals and other functions on numerical columns. When a user sees a value in a table, he doesn't know whether it is because the attribute is irrelevant, whether the database contains a mistake, or whether the data just hasn't been entered. In this case, you can use the second design proposed in Figure 8.7. Here, only books with a review are listed in the Book_Reviews table, with all their reviews.

Note that this design is based on the idea of having a single in-house reviewer; that is, a one-to-one relationship exists between Books and Reviews. If you want to include many reviews of the same book, this would be a one-to-many relationship, and you would need to go with the second design option. Also, with one review per book, you could use the ISBN as the primary key in the Book_Reviews table. If you have multiple reviews per book, you should introduce a unique identifier for each.

## Summary of Table Types

- Simple tables that describe a real-world object.
- Linking tables that describe a one-to-many relationship.
- Linking tables that describe a many-to-many relationship.
- Tables that describe a one-to-one relationship.
