
## Chapter 15 Building a Secure Web Application

```html
<script><p align="center">The user gets us "15000&euro;".</p><br />
<br />
<script type="text/javascript"> // malicious JavaScript code goes here.<br />
</script>
```

And it would look like this in the browser:

```html
<p align="center">The user gets us "15000".</p>

<script type="text/javascript">
// malicious JavaScript code goes here.
</script><p align="center">The user gets us "15000".</p>

<script type="text/javascript">
// malicious JavaScript code goes here.
</script>
```

Note that the `htmlentities()` function replaces the symbol for the Euro currency symbol (€) with an entity (`&euro;`), whereas the `htmlspecialchars()` leaves it alone.

For situations where we would like to permit users to enter some HTML, such as a message board where people might like to use characters to control font, color, and style (or italicized), we will have to pick out our way through the strings to find those and strip them out.

## Code Organization

A good guideline is that any file not intended to be directly accessible to the user from the Internet. For example, the document root for our message board website is `/home/http/messageboard/www`, you should place include files in a location such as `/home/http/messageboard/lib`. Then, if you want to include these files, you can write:

```php
require_once('.lib/user_object.php');
```

There are a couple of reasons to do this.

First, consider what happens when a malicious user makes a request for a file that is not a .php or .html file. Many web servers will default to dumping the contents of that file to the output stream if properly configured. If you use some `library_inc` in the public document tree, and the user were to request it, the user might see a full dump of your code in the web browser. This may let the user see server paths and potentially find exploits that you have missed.

To fix this, we should be sure the web server is configured to only allow the request of .php and .html files and that requests for other types of files (such as *.inc, *.mo, *.txt and so on) should return an error from the server.

Second, even if your files all end in .php, some designed-to-be-included files may have unintended consequences if loaded out of context. Consider a library of administrative code. You may check for authorization in the usual context, but if a file is loaded alone, the authorization may be subverted.

Similarly, other files, such as password files, text files, configuration files, or special directories must be kept out of the public document tree. Even if you have your web server configured properly, may have missed something, or if, in the future, your web application is moved to a new server that is not properly configured, you may be exposed to exploitation.

If you have `allow_url_fopen` in your `php.ini`—and it is enabled by default—you could theoretically include or require files from remote servers. This is a possible point of security failure in your application, and you should avoid execution of files from separate machines, especially which you have full control. You should likewise use user input when choosing files to include or require, as bad input could also cause problems.

## What Goes In Your Code

Many of the code snippets you looked at for accessing databases have been included in the code database name, username, and password in text, as follows:

```php
$conn = new mysqli("localhost", "bob", "secret", "somedb");
```

Although this is convenient, it is slightly insecure in that if crackers were to get their hands on this file, they would have immediate access to our database with the full permissions that the user has.

Better would be to put username and password in a file that is not in the document tree of the web application, and include it in your script, as follows:

```php
<?php
// this is dbconnect.php
$db_server = 'localhost';
$db_user_name = 'bob';
$db_password = 'secret';
$db_name = 'somedb';
?>
```

The above file could be called as:

```php
<?php
include('../code/dbconnect.php');

$conn = @new mysqli($db_server, $db_user_name, $db_password,
      $db_name);

// etc
?>
```

You should think about doing the same thing for other similarly sensitive data for which you might want an additional layer of protection.
