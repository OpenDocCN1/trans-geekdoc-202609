The Grantor column in the tables_priv and procs_priv tables stores the name of the user who granted this privilege to them. The Timestamp column in each of these tables stores the date and time the privilege was granted. In proxies_priv table, these columns are currently unused.

# Access Control: How MySQL Uses the Grant Tables

MySQL uses the grant tables to determine what a user is allowed to do in a two-stage process:

+   1. Connection verification. Here, MySQL checks whether you are allowed to connect at all, based on information from the user table, as shown. This authentication is based on username, hostname, and password. If a username is blank, it matches all users. Hostnames can be specified with a wildcard character (%). This character can be used as the entire field (that is, % matches all) or as part of a hostname (for example, %.example.com matches all hosts ending in example.com). If the password is blank, no password is required. Your system is more secure if you have blank users, wildcards in hosts, and users without passwords. If the hostname is blank, it is effectively a wildcard, with lower precedence than a wildcard.
2. Request verification. Each time you make a request, after you have established a connection, MySQL checks whether you have the appropriate level of privileges to perform that request. The system begins by checking your global privileges (in the user table) and, if they are not sufficient, it checks the db table. If you still don't have sufficient privileges, MySQL checks the tables_priv table, and if this is not enough, finally it checks the columns_priv table. If the operation uses stored routines, MySQL checks the procs_priv table instead of the tables_priv and columns_priv table. If you are trying to proxy another user, or grant proxy privileges to a user, MySQL checks the proxies_priv table.
