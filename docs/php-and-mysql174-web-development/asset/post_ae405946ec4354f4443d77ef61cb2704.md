# Error Reporting Levels

PHP allows you to set how fussy it is with errors. You can modify what types of events generate messages. By default, PHP reports all other than notices.
The error reporting level is assigned using a set of predefined constants, shown in Table 26.1.

Table 26.1 Error Reporting Constants

| Value | Name | Meaning |
| --- | --- | --- |
| 1 | E_ERROR | Report fatal errors at runtime |
| 2 | E_WARNING | Report nonfatal errors at runtime |
| 4 | E_PARSE | Report parse errors |
| 8 | E_NOTICE | Report notices, notifications that something you have done might be an error |
| 16 | E_CORE_ERROR | Report failures in the startup of the PHP engine |
| 32 | E_CORE_WARNING | Report nonfatal failures during the startup of the PHP engine |
| 64 | E_COMPILE_ERROR | Report errors in compilation |

| Value | Name | Meaning |
| --- | --- | --- |
| 128 | E_COMPILE_WARNING | Report nonfatal errors in compilation |
| 256 | E_USER_ERROR | Report user-triggered errors |
| 512 | E_USER_WARNING | Report user-triggered warnings |
| 1024 | E_USER_NOTICE | Report user-triggered notices |
| 2048 | E_STRICT | Report uses deprecated and unrecommended behavior; not included in E_ALL but very useful for code refactoring. Suggests changes for interoperability. |
| 4096 | E_RECOVERABLE_ERROR | Report catchable fatal errors. |
| 8192 | E_DEPRECATED | Report warnings about code that will not work in future PHP releases. |
| 16384 | E_USER_DEPRECATED | Report warnings generated by the PHP function trigger_error(). |
| 32767 | E_ALL | Report all errors and except except reported in E_Strict |

Each constant represents a type of error that can be reported or ignored. If, for instance you set the error level as E_ERROR, only fatal errors will be reported. These constants can be combined using bitwise arithmetic, to produce different error levels.

The default error level—report all errors except notices—is specified as follows:

```
E_ALL & -E_NOTICE
```

This expression consists of two the predefined constants combined using bitwise arithmetic operators. The operands are the bitwise AND and the tilde (-) is the bitwise NOT operator. This expression can be read as E_ALL AND NOT_NOTICE.

E_ERROR is itself a combination of all the other error types except E_STRICT. It could be replaced by the other levels combined using the bitwise OR (|):

```
E_ERROR | E_WARNING | E_PARSE | E_NOTICE | E_CORE_ERROR | E_CORE_WARNING |
E_COMPILE_ERROR | E_COMPILE_WARNING | E_USER_ERROR | E_USER_NOTICE
```

Similarly, the default error reporting level could be specified by all levels except E_NOTICE combined with OR:

```
E_ERROR | E_WARNING | E_PARSE | E_CORE_ERROR | E_CORE_WARNING | E_COMPILE_ERROR |
E_COMPILE_WARNING | E_USER_ERROR | E_USER_WARNING | E_USER_NOTICE
```

# Altering the Error Reporting Settings

You can set the error reporting settings globally, in your php.ini file or on per-script basis.

To alter the error reporting for all scripts, you can modify these lines in the default php.ini file:

```
error_reporting = E_ALL & ~E_NOTICE & ~E_STRICT & ~E_DEPRECATED
display_errors = On
display_startup_errors = Off
log_errors = Off
log_errors_max_len = 1024
ignore_repeated_errors = Off
ignore_repeated_source = Off
report_memleaks = Off
track_errors = On
html_errors =
error_log = =
```

The default global settings are to

- Report errors except notices, strict compatibility, and deprecated notices.
- Not display errors during startup sequence.
- Not log error messages to disk, if you do the maximum length would be 1024 bytes.
- Report memory leaks.
- Not track errors, storing the error in the variable $php_errormsgs.
- Output error messages as HTML to standard output.
- Send all errors to stderr.

The most likely change you will make is to turn the error reporting up to E_ALL | E_STRICT. This change results in many notices being reported, for incidents that might indicate an error, or might just result from the programmer taking advantage of PHP's weakly typed nature and the fact that it automatically initializes variables to .

While debugging, you might find it useful to set the error_reporting level higher. If you are providing useful error messages of your own, the production code could be more professional looking you turn display_errors off and log_errors on, leaving the error_reporting level high. You can refer to detailed errors in the logs if problems are reported.

Turning track_errors on might help you to deal with errors in your code, rather than letting PHP provide its default functionality. Although PHP provides useful error messages, default behavior looks ugly when things go wrong.

By default, at a fatal error occurs, PHP outputs

```
<br>
<b>Error Type</b>: error message in <b>path/file.php</b><br>
on line <b>lineNumber</b><br>
```

and stops executing the script. For nonfatal errors, the same text is output, but execution continues.

This HTML output makes the error stand out but looks poor. The style of the error message is unlikely to fit the rest of the site's. It might also result in some users seeing no output at all if the page's content is displayed within a table and their browser is fussy about HTML. HTML opens does not close table elements, such as

```
<table>
<tr><td>
<br>
<b>Error Type:</b> error message in <b>path/file.php</b>
on line <b>lineNumber:</b><br></td
```

You do not have PHP's default error handling behavior or even the same settings for all files. To change the error reporting level for the current script, you can call the function error_reporting().

Passing an error reporting constant, or a combination of them, sets the level in the same way that the similar directive in php.ini does. The function returns the previous error reporting level. A common way to use the function is like this:

```
// turn off error reporting
$old_level = error_reporting(0);
```

```
// here, put code that will generate warnings
```

```
// turn error reporting back on
error_reporting($old_level);
```

Turning off error reporting permanently is a bad idea because it makes finding coding errors and fixing them more difficult.

# Triggering Your Errors

The function trigger_error() can be used to trigger your own errors. Errors created this way are handled the same way as regular functions.

The function requires an error message and optionally an error type. The error type must be one of E_ERROR, E_WARNING, or E_NOTICE. If you do not specify a type, the default is E_NOTICE.

You use trigger_error() as follows:

```
trigger_error('This computer will self destruct in 15 seconds', E_WARNING);
```

# Logging Errors Gracefully

If you come from a C++ or Java background, you are probably comfortable using exceptions. Exceptions allow functions to signal that an error has occurred and leave dealing with the error to an exception handler. Exceptions are an excellent way to handle errors in large projects. They are adequately covered in Chapter 7, "Error and Exception Handling," so they will not be revisitedYou have already seen how you can trigger your own errors. You can also provide your own error handlers to catch errors.

The function set_error_handler() lets you provide a function to be called when user-level errors, warnings and notices occur. You can call set_error_handler() with the name of the function you want to use as your handler.

Your error handler takes two parameters: an error type and an error message. Based on these two variables, function can decide how to handle the error. The error type must be one of the defined-error constants. The error message is a descriptive string.

A call to set_error_handler() looks like this:

```
set_error_handler('my_error_handler');
```

Having told PHP to use a function called my_error_handler(), you must provide a function with that name. This function must have the following prototype:

```
my_error_handler(int error_type, string error_msg,
      [string errfile, int errline, array errcontext]])
```

What it actually does, however, is up to you.

The parameters passed to your handler function are

- The error type
- The error message
- The file error occurred in
- The line error occurred on
- The symbol table—that is, a set of all the variables and their values at the time the error occurred

Logical actions might include

- Displaying the error message provided
- Logging the information in a log file
- Emailing the error to an address
- Terminating the script with a call to exit
