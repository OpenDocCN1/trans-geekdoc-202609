# Filtering Even Basic Values

HTML elements have no types associated with them and most simply pass strings (which in, turn, represent such as dates, times, or numbers) to the server. Even if you have a numeric field, you cannot assume or trust that it was entered correctly. In environments where particularly powerful client-side code try to make sure that the value entered is of a particular type, there is no guarantee that the values will not be sent to the server directly, as we saw in the previous section.

An easy way to make sure that a value is of the expected type is to cast or convert it to that type and then use that value, as follows:

```php
$number_of_nights = (int)$_POST['num_nights'];
if ($number_of_nights == 0) {
    echo "ERROR: Invalid number of nights for the room!";
}
```

If we have the user input a date in some localized format, such as mm/dd/yy for users in the United States, we can then write some code to make it a real using the PHP function checkdate(). This function takes a month, day, and year value (two-digit years), and indicates whether they combined, form a valid date:

```php
$mmddyy = explode('/', $_POST['departure_date']);
if (count($mmddyy) != 3) {
    echo "ERROR: Invalid Date specified!";
    exit;
}

// handle years like 02 or 95
if ((int)$mmddyy[2] < 100) {
    if ((int)$mmddyy[2] = (int)$mmddyy[2] + 1900);
} else if ((int)$mmddyy[2] >= 0) {
    $mmddyy[2] = (int)$mmddyy[2] + 2000;

// else it's < 0 and checkdate will catch it
```


By taking the time to filter and validate the input, not only can we help ourselves out for natural error-checking that we should be doing in the first place (such as verifying a departure date for a plane ticket is a valid date), but we can also improve the security of our system.

# Making Strings Safe for SQL

One other where we need to process our strings to make them safe is to prevent SQL injection attacks, which were mentioned when first looking at MySQL in PHP. In these attacks, the malicious user tries to take advantage of poorly protected code and user permissions to execute SQL code that we do not necessarily want to. If we are not careful, a username of

```
kitty_cat; DELETE FROM users;
```

You can use two primary methods to prevent this sort of breach:

- Use parameterized queries wherever possible. These queries separate SQL from data. The case where this won't help you is column and table names, as these cannot be passed via parameterized query. However, because you have a priori knowledge of your schema, you can whitelist appropriate values.

- Make sure that all inputs conform to what you expect it to be. If our usernames are supposed to be up to 50 characters and include only letters and numbers, we can be sure that " DELETE FROM users" at the end of it is probably something we would not want to permit. Writing the PHP code to make sure inputs conform to the possible values before we send it to the database server means we can print out a much more meaningful error than the database would give us (if we checking such things), and reduce our risks.

The mysqli extension has the added security advantage of allowing only a single query to execute with the mysql_query or mysqli::query methods. To execute multiple queries, you have to use the mysqli_multi_query or mysqli::multi_query methods, which help us prevent the execution of potentially harmful statements or queries.

# Escaping Output

Of equal importance to filtering our input is what we'll call escaping our output. After we have user values in our system, it is critical to be sure that these cannot do any damage or cause any unintended consequences. We do this by using a key of functions to ensure that values cannot be mistaken by the client browser for anything other than display text.

Many web applications take the user input specified and display it on a page. Pages where users can comment on a published article or message boards are examples of where this might occur. In these situations, we need to be careful that they do not inject malicious HTML into the text.

One of the easiest to do this is to use the htmlspecialchars() function or the htmlentities() function. These functions take certain characters that they see in the input string and convert them to HTML entities. In short, an HTML entity is a special character sequence, begun with the ampersand (&), used to indicate some special character that cannot be easily represented in HTML. After the ampersand comes the entity name and a terminating semicolon (;). Alternatively, an entity can be an ASCII character specified by # and a decimal number, such as &amp; for the forward slash (/).

For example, because all markup elements in HTML are demarcated by < and > characters, the browser will attempt to delineate markup elements. To get around this, we use the entities &lt; and &gt;. Similarly, if we want to include the ampersand character in our HTML, we use double quotes represented by &#39; and &quot;. Entities are converted into output by the HTML client (web browser) and are thus not considered part of the markup.

The difference between the htmlspecialchars() function and the htmlentities() function is as follows: The former defaults to only replacing <, and >, with optional switches for single and double quotes. The latter replaces anything that can be represented by a named entity with that named entity. Examples of such entities are the copyright symbol ©, represented by &copy;,, the Euro currency symbol €, represented by &euro;. It will not convert characters to numeric entities, however.

Both functions take their second parameter as a value that specifies how to handle quotes and invalid code sequences, and both functions also take as an optional third parameter the character set in which the input string is encoded (which is vital for us, because we want this function to be safe on our UTF-8 strings). The five most common values for the second parameter are the following:

- ENT_COMPAT (the default value)—Double quotes are converted to &quot; but single quotes are left untouched.
- ENT_QUOTES—Both single and double quotes are converted, to &#39; and &quot;
- ENT_NOQUOT—Neither single nor double quotes are converted by this function.
- ENT_SUBSTITUTE—Invalid code sequences are replaced with a Unicode Replacement character instead of returning an empty string.
- ENT_DISALLOWED—Invalid code sequences are replaced with a Unicode character leaving them as is.

Consider the following snippets:

```php
$input_str = "<p align=\"center\">The user gave us \"15000?\".</p>\n<script type=\"text/javascript\">
// malicious JavaScript code goes here.
</script>";
```

If we run the following PHP script using the n2br function to ensure that it is formatted nicely in the browser,

```php
<?php

$str = htmlspecialchars($input_str, ENT_NOQUOTES, "UTF-8");
echo n2br($str);

$str = htmlentities($input_str, ENT_QUOTES, "UTF-8");
echo n2br($str);

?>
```
