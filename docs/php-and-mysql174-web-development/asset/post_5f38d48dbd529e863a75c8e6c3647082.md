# Storing Passwords

There are many places to store usernames and passwords inside the script. Inside the script, modifying the data is difficult. It is possible, but a bad idea, to write a script to modify itself. Doing so would mean a script on your server that is executed on your server that can be written or modified by others. Storing the data in another file on the server lets you more easily write a program to add and remove users and alter passwords.

Inside a script or other data file, you are limited to the number of users you can have without seriously affecting the speed of the script. If you are considering storing and searching through a large number of items in a file, you should use a database instead, as previously discussed. As a rule of thumb, if you want to store and search through a list of more than a handful of items, they should be in a database rather than a flat file.

Using a database to store usernames and passwords would not make the script much complex but would allow you to authenticate many different users quickly. It would also allow you to easily write a script to add new users, delete users, and allow users to change their passwords. When storing passwords in a database, however, be sure not to store plain text passwords. Instead, it is common to hash passwords using the built-in PHP md5() function, for example, and comparing the hashed value of the user’s form input to the hashed value stored in the database table. Using this approach, you can still authenticate a user who is attempting to gain access to your protected resource, but you are not storing any actual passwords.

# Securing Passwords

Regardless of whether you store your data in a database or a file, storing the passwords as plain text is an unnecessary risk. A one-way hashing algorithm can provide better security with very little extra effort.

In older versions of PHP, it was typical to explicitly use the one-way hash functions. The oldest and least secure is the Unix Crypt algorithm, provided by the function crypt(). Then there's the Message Digest 5 (MD5) algorithm, implemented in the function md5(). More recently people have Secure Hashing Algorithm functions such as sha1() and sha256(), among others.

The problem with specifying a hash function is that time passes, hashing algorithms become insecure. How does this happen? Security researchers find a way to break the hash. This becomes easier as computing powers increase,

As PHP 5.5, and still present in PHP 7, a function called password_hash() applies a string one-way hashing function to it. A prototype for this is

```
string password_hash ( string $password , array $options )
```

Because the reason is so simple, this enables you to change the hashing algorithm by changing configuration instead of code, and by changing it in a single place.

One other thing you might notice here is that there is a constant called PASSWORD_DEFAULT, which you can pass as the name of the hashing algorithm. PHP will update the value of this over versions to keep it at a secure level. The default algorithm is CRYPT_BLOWFISH, which you can also specify by passing PASSWORD_BCRYPT as the $algo parameter.

With PASSWORD_BCRYPT, it will also generate a salt for you. A salt, in this context, is a randomly generated piece of data added to the password before hashing. It makes more difficult to guess a password.

Given the $password and the PASSWORD_BCRYPT function, this will return a 60-character hash. Strings returned by password_hash() contain all the information necessary to reproduce the hash. This includes the algorithm used and the salt.

This salt cannot be decrypted and turned back into the original string by its creator, so it might not seem very useful at first glance. The property that makes such hashing functions useful is that the output is deterministic. Given the same string, it will return the same result every time it run.

Rather than having PHP code

```php
if (($username == 'username') &&
    ($password == 'password')) {
    // OK passwords match
}
```

you can have code

```php
if (password_verify($password, $hash)) {
    // OK passwords match
}
```

You do not need to know what the password looked like before you used the hashing function on it. You need to know only if the hash of the password typed is the same as the hash of the password that has been set previously.

# Implementing Access Control

As mentioned, hard-coding acceptable usernames and passwords into a script is a bad idea. You should use a separate file or a database to store them.

Keep in mind that the hash functions generally return data of a fixed size. In the case of PASSWORD_BCRYPT, it is 60 characters when represented as a string. Future algorithms may generate longer hashes, so you should make sure your database column has space for future expansion—255 characters is a reasonable length for now.

# Protecting Multiple Pages

Making a script like one in the previous section more than one page is a little harder. Because HTTP is stateless, there is no automatic link or association between subsequent requests from the same person. This makes it harder to have data, as authentication information that you have entered, carried from page to page.

The easiest way to protect multiple pages is to use the access control mechanisms provided by your web server. We look at these mechanisms shortly.

To create this yourself, you could include parts of the script shown in Listing 16.1 in every page you want to protect. Using auto_prepend_file and auto_append_file, you can automatically prepend and append the code to every file in particular directories. The use of these directives was discussed in Chapter 5, "Reusing Code and Writing Functions."

If you use this approach, what happens when your visitors to multiple pages within your site? Requiring them to re-enter their names and passwords for every page they want to visit would not be acceptable.

You could add the details entered into every hyperlink on the page. Because they may have spaces or other characters that are not allowed in URLs, you could use the function urlencode() to encode these characters.

This approach has a few problems, because the data would be included in pages sent to the users and the URLs they visit, the protected pages they visit will be visible to anybody who uses the same computer and steps back through cached pages or looks at the browser's history list. Because you are sending the password back and forth with every page requested or delivered, this sensitive information is transmitted more often than necessary.

There are two good ways to tackle these problems: HTTP basic authentication and sessions. Basic authentication overcomes the caching problem, but the browser still sends the password to the server with every request. Session control overcomes both of these problems. We look at HTTP basic authentication now and examine session control in Chapter 22, "Using Session Control in PHP," and in more detail in Chapter 27, "Building User Authentication and Personalization.".
