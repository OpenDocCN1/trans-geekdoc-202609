The first way means adding a Review column to the Books table. This way, there is a field for the Review to be added for each book. If many books are in the database, and the reviewer doesn't plan to review all, many rows won't have a value in this attribute. This is called having a null value.

Having many values in your database is a bad idea. It wastes space and causes problems when working out totals and other functions on numerical columns. When a user sees a value in a table, he doesn't know whether it is because the attribute is irrelevant, whether the database contains a mistake, or whether the data just hasn't been entered. In this case, you can use the second design proposed in Figure 8.7. Here, only books with a review are listed in the Book_Reviews table, with all their reviews.

Note that this design is based on the idea of having a single in-house reviewer; that is, a one-to-one relationship exists between Books and Reviews. If you want to include many reviews of the same book, this would be a one-to-many relationship, and you would need to go with the second design option. Also, with one review per book, you could use the ISBN as the primary key in the Book_Reviews table. If you have multiple reviews per book, you should introduce a unique identifier for each.

# Summary of Table Types

+   - Simple tables that describe a real-world object. They might also contain keys to other objects which they have a one-to-one or one-to-many relationship. For example, one customer might have many orders, but an order is placed by a single customer. Thus, you put a reference to the customer in the order.

+   - Linking tables that describe a many-to-many relationship between two real objects as the relationship between Orders and Books. These tables are often associated with some kind of real-world transaction.
