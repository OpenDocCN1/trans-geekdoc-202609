# Optimizing Your Database

In addition to the previous query optimization tips, you can do a few things to generally increase the performance of your MySQL database.

## Design Optimization

Basically want everything in your database to be as small as possible. You can achieve this in result, with a decent design that minimizes redundancy. You can also achieve it by using the smallest data type for columns. You should also minimize NULLs wherever possible and make your primary key as short as possible.

Avoid variable length columns at all possible with MyISAM (such as VARCHAR, TEXT, and BLOB). If your tables have fixed-length fields, they will be faster to use but might take up a little more space.

## Permissions

In addition to the suggestions mentioned in the previous section on EXPLAIN, you can improve the speed of queries by simplifying your permissions. Earlier, we discussed the way that queries are checked with the permission system before being executed. The simpler this process is, the faster your query will run.

## Table Optimization

If a table has been in use for a period of time, data can become fragmented as updates and deletions are processed. This fragmentation increases the time taken to find things in this table. You can fix this problem by using the statement

```sql
OPTIMIZE TABLE tableName;
```

## Using Indexes

You should use indexes where required to speed up your queries. Keep them simple and don't create indexes that are not being used by your queries. You can check which indexes are used by running EXPLAIN, as shown previously. You should also minimize the length of primary keys.

## Using Default Values

Wherever possible, you should use default values for columns and insert data only if it differs from the default. This way, you reduce the time taken to execute the INSERT statement.

## Other Tips

You can make many other tweaks to improve performance in particular situations and address particular needs. The MySQL website offers a good set of additional tips. You can find it at http://www.mysql.com.

# Backing Up Your MySQL Database

In MySQL, there are several ways to do a backup.

The first way is to lock the tables you copy the physical files, using a LOCK TABLES command with the following syntax:

```sql
LOCK TABLES table lock_type [, table lock_type ... ]
```

Each table should be the name of a table, and the lock type should be READ or WRITE. For a backup, you only need a read lock. You need to execute a FLUSH TABLES; command to make sure any changes to your indexes have been written to disk before performing a backup.

Users and scripts can run read-only queries while you make your backup. If you have a reasonable volume of queries that alter the database, as customer orders, this solution is not practical.

The second, and superior, method is using the mysqldump command. Usage is from the operating system command line, and is typically something as

```bash
> mysqldump --all-databases > all.sql
```

# Implementing Replication

This command dumps a set of all the SQL required to reconstruct the database to the file called all.sql.

If using InnoDB (the default engine), you can make an online backup, and even better keep track of where you were up to in the binary log. What this means is if you are restoring your database from that backup, you will be able to restore the backup and replay changes since the backup was made. You can do this with the following options:

```bash
> mysqldump --all-databases --single-transaction --flush-logs --master-data=2 --all_databases.sql
```

The --single-transaction option does the backup while the database is still running (by acquiring a read lock). The --flush-logs and --master-data options flush the logs and then note the point in the log where the backup was made.

A third method is using the mysqlhotcopy script. You can invoke it with

```bash
> mysqlhotcopy database /path/for/backup
```

A final method of backup, which also has other advantages, is to maintain one or more replicated copies of the database. Replication is discussed later in this chapter.

# Restoring Your MySQL Database

If you need to restore your MySQL database, there are, again, a couple of approaches.

If you used the first method, you need a couple of steps. First, you need to create the database. Second, you need to restore the data from the snapshot:

```bash
> mysql -u root -p datename < all.sql
```

If you used the second method, you need to restore the snapshot and then reapply the changes from the binary log:

```bash
> mysql -u root -p --execute-log
```

If you used the third method, you need to use the mysqlhotcopy tool.

# Implementing Replication

Replication is a technology that allows you to have multiple servers hosting the same data. This can improve system reliability. The usual way of using this setup is to write queries to the master and read queries to the slaves. This is called read-write splitting and can be implemented using a tool or in your application logic.

More complex architectures are possible, as having multiple masters, but we will only consider the master-slave example.

You need to realize that slave data is generally not up to date as the master. The difference between the master and slaves is sometimes referred to as slave lag.

To begin up a master and slave architecture, you need to make sure binary logging is enabled on the master. Enabling binary logging is discussed in Appendix A, “Installing Apache, PHP, and MySQL."

You need to edit your my.ini or my.cnf files on both the master and slave servers. You need the following settings:

```ini
[mysqld]
log-bin
server-id=1
```

The first setting turns on binary logging (so you should already have this one; if not, add it now). The second setting gives your master a unique ID. Each of the slaves also needs an ID, so you need to add a similar line to the my.ini/cnff files on each of the slaves. Make sure the numbers are unique! For example, your first slave could have server-id=2; the next server-id=3; and so on.

## Setting Up the Master

On the master, you need to create a user for slaves to connect. There is a special privilege for levels called REPLICATION SLAVE. Depending on how you plan to do the initial data transfer, you may need to grant some privileges.

In most cases, you will use a database snapshot to transfer the data, and in this case, only the special replication privilege is needed. If you decide to use the LOAD DATA FROM MASTER command (you learn about it in the next section), this user will also need the RELOAD, SUPER, and SELECT privileges, but only for initial setup. As per the principle of least privilege, in Chapter 9, you should revoke these privileges after the system is up and running.

Create a user on the master. You can call it anything you like and give it any password you choose. In our example, we call this user rep_slave:

```sql
GRANT REPLICATION SLAVE
ON *.*
```
