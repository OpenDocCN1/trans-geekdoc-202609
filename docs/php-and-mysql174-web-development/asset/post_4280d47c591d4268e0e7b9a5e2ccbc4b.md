Variable names should describe the data they contain. If you are storing somebody's surname, call it $surname. In general, strike a balance between length and readability. storing the name in $n makes it easy to type, but the code is difficult to understand. storing the name in $surname_of_the_current_user is more informative, but it's a lot to type (and therefore easier to make a typing error) and doesn't really add much.

You need to make a decision on capitalization. Variable names are sensitive in PHP, as we've mentioned previously. You need to decide whether your variable names will be lowercase, uppercase, or a mix—example, capitalizing the first letters of words. We tend to use lowercase letters and separate with underscores (sometimes called snake case) because this scheme is the easiest to remember for us. Some organizations will settle on a standard of lowerCamelCase or UpperCamelCase for mysqli variables; at the end of the day it doesn't matter what you use, as long as it is standardized within your codebase. You might also want to set a maximum length of two to three words in a variable name.

Distinguishing between variables and constants is also a good idea. A common scheme is to use all lowercase for variables (for example, $result) and all uppercase for constants (for example, PI).

One bad practice programmers use is to have two variables with the same name but different capitalization they can, as $name and $Name. We hope it is obvious why this practice is a terrible idea.

It is also best to avoid capitalization schemes as $WaReZ because no one will be able to remember how it works.

Function names have many of the same considerations as variables, with a couple of extras. Function names should generally be well oriented. Built-in PHP functions such as like() or mysqli_connect(), which describe what they are going to do or with what parameters they are passed. This naming scheme greatly enhances code readability. Note that these two functions have a different naming scheme for dealing with multivunction names. PHP's functions are inconsistent in this regard, as a result of being written by a large group of people, but mostly many PHP functions have been adopted unchanged from different languages and APIs.

Unlike variables, function names are not case sensitive in PHP. You should probably stick to a proper format when creating your own functions, just to avoid confusion within the code (or your organization).

Additionally, you might want to consider using the module-naming scheme in many PHP modules—that is, prefixing the name of functions with the module name. For example, the improved MySQL functions begin with mysqli_ and all the IMAP functions begin with imap_. If, you have a shopping cart module in your code, you could prefix the function in that module with cart_.

Note, however, that when PHP provides both a procedural and an object-oriented interface, the function names are different. Usually, the procedural ones use snake case (my_function()) and the object-oriented ones use lowerCamelCase(myFunction()).

## Commenting Your Code

All programs should be commented to a sensible level. You might ask what level of commenting is sensible. Generally, you should consider adding a comment to each of the following items:

- Files, where complete scripts or include files—Each file should have a comment stating what this is, what it's for, who wrote it, and when it was updated.
- Functions—Function comments should specify what the function does, what input expects, and what it returns.
- Classes—Comments should describe the purpose of the class. Class methods should have the same types and levels of comments as any other functions.
- Chunks of code within a script or function—We often find it useful to write a script beginning with a set of pseudocode-style comments and then filling the code for each section. An initial script might resemble this:

```php
<?php
// validate input data
// send to database
// report results
?>
```

This commenting scheme is quite handy after you've filled in all the sections with function calls or whatever you need, your code is already commented to a certain extent.

- Complex code or hacks—When performing some task takes you all day, or you have to do it in a weird way, write a comment explaining why you used that approach. This way, when you look at the code, you won't be scratching your head and thinking, "What on earth was that supposed to do?"

In general another general guideline to follow: Comment as you go. You might think you will come back and comment your code when you are finished with a project, but you can guarantee that this will not happen, unless you have far less publishing timetables and more self-discipline than (most developers) do.

## Breaking Up Code

Monolithic code is awful. Some people create one huge script that does everything, but it's generally a good idea to break up code into chunks. It is far better to split related items into functions.

Reasons for breaking up code include:

- It makes your code easier to read and understand
- It makes your code reusable
- It facilitates teamwork
- It minimizes redundancy

At the start of any project, you need to spend some time thinking about how you are going to break up. This process requires drawing lines between functionality and classes.

## Documenting and Sharing In-House Functions

As you develop libraries, you need to make them available to other programmers on your team. Very often, we have seen every programmer on a team write his or her set of database, data, or debugging functions. This scheme is a time was. You should make functions and classes available to others via shared libraries or code repositories.

Remember that even if code is stored in an area or directory commonly available to your team members, they won't know it's there unless you tell them. Develop a system for documenting in-house function libraries and make it available to programmers on your team.
