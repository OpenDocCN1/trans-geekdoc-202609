# Getting More Information About Databases

The type column explains how the table is being used in joins in the query. The set of values this column can have is shown in Table 12.9. These values are listed in order from fastest to slowest in terms of query execution. The table gives you an idea of how many rows need to be read to execute a query.

# Table 12.9 Possible Join Types As Shown in Output from EXPLAIN

| Type | Description |
| --- | --- |
| const or system | The table is read from only once. This happens when the table has exactly one row. The type system is used when it is a system table, and the type const otherwise. |
| eq_ref | For every set of rows from the other tables in the join, you read one row from this table. This type is used when the join uses all parts of the index on the table, and the index is UNIQUE or is the primary key. |
| fulltext | A join has been performed using a fulltext index. |
| ref | For every set of rows from the other tables in the join, you read a set of table rows that match. This type is used when the join cannot choose a single row based on the join condition—that is, when only part of the key is used in the join, or if it is not UNIQUE or a primary key. |
| ref_or_null | This is like ref query, but MySQL also looks for rows that are NULL. (This type is mostly used in subqueries.) |
| index_merge | A specific optimization, the Index Merge, has been used. |
| unique_subquery | This join is used to replace ref for some IN subqueries where one row is returned. |
| index_subquery | This join is similar to unique_subquery but is used for indexed nonempty subqueries. |
| range | For every set of rows from the other tables in the join, you read a set of table rows that fall into a particular range. |
| index | The entire index is scanned. |
| ALL | Every row in the table is scanned. |

In the previous example, you can see that one of the tables is joined using eq_ref (Books), one joined using ref (Order_Items), one joined using index (Orders), and one (Customers) is joined using ALL—that is, by looking every single row in the table.

The rows count back up: its (roughly) the number of rows of each table that has to be scanned. You can multiply these numbers to get the total number of rows examined when a query is performed. You multiply these numbers because a join is like a product of rows in different tables. Check out Chapter 10, "Working with Your MySQL Database," for details. Remember that this is the number of rows examined, not the number of rows returned, and that it is an estimate; MySQL can't know the exact number without the query.
