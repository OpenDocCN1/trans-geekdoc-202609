# Understanding the Privilege System in Detail

Most rows in this table correspond to a set of privileges for a User coming from a Host and logging in with the password. These are the *scope* fields for this table because they describe the scope of the *privilege* fields. The privilege fields end with _priv.

The privileges listed in this table (and the others to follow) correspond to the privileges granted using GRANT in Chapter 9. For example, Select_priv corresponds to the privilege to run a SELECT command.

If a user has a particular privilege, the value in that column will be Y. Conversely, if a user has not granted that privilege, the value will be N.

All the privileges listed in the user table are global; that is, apply to all databases in the system (including the mysql database). Administrators will therefore have all Y in there, but the majority of users should have all N. Normal users should have rights to appropriate databases, not all tables.

The other two sets of fields in this table are the security fields and the resource control fields.

The security fields are ssl_type, ssl_cipher, x5_issuer, x5_subject, plugin, authentication_string, and password_expired. The plugin field is NULL by default but may be set to contain an authentication plugin that will be used to authenticate a particular user account. The authentication_string may be used by plugins. The ssl_type and ssl_cipher are used if you have enabled SSL connections.

# Access Control: How MySQL Uses the Grant Tables

MySQL uses the grant tables to determine what a user is allowed to do in a two-stage process:

1. Connection verification. Here, MySQL checks whether you are allowed to connect at all, based on information from the user table, as shown. This authentication is based on username, hostname, and password. If a username is blank, it matches all users. Hostnames can be specified with a wildcard character (%). This character can be used as the entire field (that is, % matches all) or as part of a hostname (for example, %.example.com matches all hosts ending in example.com). If the password is blank, no password is required. Your system is more secure if you have blank users, wildcards in hosts, and users without passwords. If the hostname is blank, it is effectively a wildcard, with lower precedence than a wildcard.

2. Request verification. Each time you make a request, after you have established a connection, MySQL checks whether you have the appropriate level of privileges to perform that request. The system begins by checking your global privileges (in the user table) and, if they are not sufficient, it checks the db table. If you still don't have sufficient privileges, MySQL checks the tables_priv table, and if this is not enough, finally it checks the columns_priv table. If the operation uses stored routines, MySQL checks the procs_priv table instead of the tables_priv and columns_priv table. If you are trying to proxy another user, or grant proxy privileges to a user, MySQL checks the proxies_priv table.

# Updating Privileges: When Do Changes Take Effect?

The MySQL server automatically reads the grant tables when it is started and when you issue GRANT and REVOKE statements. However, now that you know where and how those privileges are stored, you can alter them manually. When you update them manually, the MySQL server will not notice that they have changed.

You need to point out to server that a change has occurred, and you can do this in three ways. You can type

```
mysql> flush privileges;
```

at the MySQL prompt, (You need to be logged in as an administrator to use this command.) This is the most common way of updating the privileges.

Alternatively, you can run either

- > mysqladmin flush-privileges

or

- > mysqladmin reload

from your operating system.

Finally, the MySQL server will reload the grant tables when it is restarted. Next time a user connects; database privileges will be checked when the use statement is issued; and table- and column-level privileges will be checked on a user's next request.

# Making Your MySQL Database Secure

Security is important, especially when you begin connecting your MySQL database to your website. The following sections explain a basic set of precautions you ought to protect your database.

# MySQL from the Operating System's Point of View

Running the MySQL server (mysqld) as root is a bad idea if you are running a Unix-like operating system. Doing this gives a MySQL user with a full set of privileges the right to read and write anywhere in the operating system. This is an important point, easily overlooked, which was famously used to hack Apache's website. (Fortunately, the crackers were "white hats" [good guys], and their only action was to tighten up security.)

Setting up a MySQL user specifically for the purpose of running mysql is a good idea. In addition, you can then make the directories (where the physical data is stored) accessible only by the MySQL user. In many installations, the server is set up to run as user mysql, in the mysql group.
