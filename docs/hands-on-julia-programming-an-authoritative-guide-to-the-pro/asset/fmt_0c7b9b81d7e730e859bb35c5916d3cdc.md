
`fib(n) = n < 3 ? 1 : fib(n-1) + fib(n-2)`

Here are some test outcomes from running the code in the REPL.

```
julia> fib(3)
2
julia> fib(10)
55
julia> fib(-1)
1
julia> fib(0)
1
```

The recursive function terminates as there is a termination condition for all values of `n < 3`. The fundamental question remains if the Fibonacci sequence is valid for negative values of `n`. Having a small pure function and verifying it in the REPL makes it easier to ensure a properly running code is verified and introduced into the actual code. Running parts of code in the IDE is another way to achieve the same result.

While the preceding ones are some of the easier ways to test and use small chunks of code, they are unlike the line debugging used with tools like `gdb` for native binaries. Julia has a fully functional debugger for the command line[21](#iftzdvy1.html#n4upl4fndlp).

## Line Debugging

Line debugging is best carried out with the IDEs as it is easier to set break points using the pointers; add watches on variables and see those values change as you step-in, step-out, or step-over of the code blocks or functions. You can run the code until a particular condition is met or a break point is hit. While line debugging is the most sought-after technique for most programmers, it may not be the most efficient option for an interpreted language like Julia.

*   Initializing the debugger environment can be very slow.
*   Debugging may require a higher amount of memory.
*   Stepping over the code and verifying watch variables can be a slow process in itself.
*   Line debugging is the last option when one does not have enough understanding of the code or does not have any easier means to eliminate code that is already functioning properly.
*   Line debugging can be very effective when the erroneous code can be localized to a very small part and specifically validated:

## Revise.jl and Runtime Limitations

However adept a programmer is, she would like to try the idea in her mind, quickly experience the outcome, fix the changes, and move on with the next chunk of code. Julia's runtime is pre-loaded. As you load more data structures or modules and packages to the system, the older symbols and code blocks get loaded to the runtime. It may not be possible to modify the symbols already defined without affecting the overall working of the runtime elsewhere. For example, changing a function definition in the REPL is straightforward. But, adding or removing an attribute of a `struct` data type is not permitted. When a package is modified, it is not loaded on the subsequent usage of the command using `<<module>>`. To overcome these limitations, `Revise.jl`[22](#iftzdvy1.html#n4upl4fndlq) package may be used. This package can be autoloaded and can update symbols as part of code-run-fix cycles of development. We suggest the readers review the package documentation for a detailed understanding.
