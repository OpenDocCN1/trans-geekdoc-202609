# Modules, packages, and projects

You will be seeing the usage of terms module, package, and project in several of the discussions. While these are related, there are certain specific characteristics each of the terms have.

## Modules

We have already seen modules in . They represent a namespace in Julia. Modules can be:

*   Defined anywhere in the code. They need not have to be specified at the beginning of the file.
*   The filename does not have to match a module name.
*   One module can be defined inside another. Creating a hierarchical structure.

In the example we discussed in , we have seen all the above characteristics and also realized the need to export a symbol from a module to be used inside another module. However, there are ways to access symbols using the keyword `using`.

## Projects

Any code in Julia can make up a project. There is no specific definition of a project. They are mere collections of Julia or non-Julia files. However, no source code works in isolation; they depend on other well-known libraries for major parts of their functionalities. Those dependencies are captured as part of two metadata files: `Project.toml` and `Manifest.toml`. This set up is called an `environment`. The environment ensures the project is executed with a consistent set of dependent libraries. The constituents of these files we shall look into in some details later.

## Libraries

We discussed about the standard library in . However, if you look into Julia as a language there is no specific definition of a library. Any code or binary written in any language that you can integrate with Julia can be considered as a library. Libraries can be Julia packages, native C/C++ shared objects, Java `*.jar` files, or Python packages, etc. Each type of library shall require a different form of integration. For example, standard library is a Julia library that ships with the Julia installation. However, it is not always true for all Julia libraries. `FileIO` ships as an external Julia package that one needs to add to her project if she needs to utilize some of its functionalities.

## Packages

Packages provide a formal structure to a Julia project or library. Here are some characteristics of a package:

*   **Git Repositories**: The Julia packages can be Git repositories. Their deployment mechanism is based on Git library integration with Julia. Hence, once created, the packages can be pushed to GitHub by default.[2](#g395jpsk.html#n4upl4fndou) Packages can be deployed in local directories as well.
*   **Folder Structure**: The packages are organized in a well-defined folder structure:
    ![](n4upl4fndrp.jpeg)
    **Figure 13.1:** Folder structure of package PDFIO
    While the `src` and `test` folders are seen in almost all packages, the folders like `deps`, `docs` and `data`, and so on may be missing in some packages. Similarly, packages that are not public may not have a `LICENCE.md` file.
*   **Environment**: Packages have their inherent environment metadata files `Project.toml` and `Manifest.toml`. This ensures when they are deployed, they have a consistent library dependency maintained.
*   **Module**: Packages are wrapped inside the highest level module. That is the name of the package and it is defined in a file named `<ModuleName>.jl` inside the `src` folder. However, you can have sub-modules defined inside the highest level module as well.

# N-Queens example with UI

Remember the example of the N-queens problem[3](#g395jpsk.html#n4upl4fndov) we discussed in ? Suppose we will like to place queens on a board and show the visual result. How will we go about it?

1.  **UI Rendering API**: Browsers being the easiest to render we will go to JuliaHub[4](#g395jpsk.html#n4upl4fndow) and search for a few available options. All these are fairly good package options like: `Electron`, `Blink`, etc. We will suggest `WebIO` as that is an aggregator that can render on all the frontends of Blink, Jupyter, a custom window from a Julia REPL or Atom IDE.[5](#g395jpsk.html#n4upl4fndox)
2.  **Adding the package**: Now that you decided to use the WebIO, you can add it to the project by using the command `add WebIO`.
3.  **Add the relevant frontend**: If you decide to use Jupyter to render the UI, make sure you add the `IJulia` package. If you want to use the Electron-based Blink as a frontend, you will need to add Blink to your project:
    ![](n4upl4fndrq.jpeg)
    **Figure 13.2:** Sample rendering using WebIO and Blink

The starter code is given in the folder `Chapter-13/NQueens`. Two options are provided one with Jupyter notebook and the other with REPL. You can launch the application in REPL using the commands as follows:

```
julia> cd("Chapter-13/NQueens")
julia> ]
(@v1.6) pkg> activate .
(@v1.5) pkg> instantiate
Activating environment at `Chapter-13\NQueens\Project.toml`
julia> include("NQueens.jl")
```

For Jupyter notebooks, start `IJulia` and open the Jupyter notebook `Chapter-13/NQueens/NQueens.ipynb`. Run the notebook to view the rendering on the notebook.

If you open the `Project.toml` file, you will see the following:

```
[deps]
Blink = "ad839575-38b3-5650-b840-f874b8c74a25"
IJulia = "7073ff75-c697-5162-941a-fcdaad2a7d2a"
WebIO = "0f1e0344-ec1d-5b48-a673-e5cf874b6c29"
```

These are all the packages your application depends on. However, internally these packages also depend on other packages. If you open the `Manifest.toml`, you will be able to see all those packages with versions on which the project effectively depends on. Normally, the `Project.toml` is provided to set up the environment. When instantiate command is invoked, it analyzes the `Project.toml` and computes all the dependencies and creates a `Manifest.toml` if that does not exist. Subsequently, it installs all the needed packages if they are not available. Thus, ensuring the environment is set up to launch the application.
