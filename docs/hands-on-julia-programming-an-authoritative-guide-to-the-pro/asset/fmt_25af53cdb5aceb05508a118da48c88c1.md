# Continuous Integration with GitHub Actions

There are many continuous integration platforms available in the market. GitHub Actions are one of the most popular frameworks used in the GitHub environments. We shall use GitHub Actions to automate the execution of test, coverage, and documentation creation tasks for the Julia projects.

1.  GitHub Actions reside in a folder called `.github/workflows` as yaml files. We shall create a file called `ci.yml` and study various aspects of the integration framework.
2.  **Event**: The first part of the yaml file is an event when the action has to be triggered.

    ```yaml
    name: CI
    on:
      push:
        branches: [master]
        tags: ["*"]
    ```

3.  **Jobs**: Next we specify the jobs that are to be run as part of the action trigger. The ids of the jobs can be any name like `myjob`. We use `test` and `doc` to use two categories of jobs we want to perform.
4.  **Test Jobs**: The test jobs essentially do a lot more than just running the unit tests. They help set up the environment, checkout the code, run the relevant unit tests and submit the coverage results to `codecov.io` for visualization.
5.  **Setting up the operating environment**:

    ```yaml
    jobs:
      test:
        name: Julia ${{matrix.version}} - ${{matrix.os}} - ${{matrix.arch}} - ${{github.event_name}}
        runs-on: ${{matrix.os}}
        strategy:
          fail-fast: false
          matrix:
            version:
              - '1.0'
              - '1' # automatically expands to the latest stable 1.x release of Julia
              - nightly
            os:
              - ubuntu-latest
            arch:
              - x64
            include:
              # test macOS and Windows with latest Julia only
              - os: macOS-latest
                arch: x64
                version: 1
              - os: windows-latest
                arch: x64
                version: 1
    ```

    You have the option of specifying the OS versions, Julia versions and you can also specify granular combinations of the Julia version with a specific OS. It may be ideal to pick up a sample `ci.yml` and modify it as appropriate than writing from scratch.

6.  **Steps**: The steps to be executed for a test job are given as follows:

    ```yaml
    steps:
      - uses: actions/checkout@v2
      - uses: julia-actions/setup-julia@v1
        with:
          version: ${{matrix.version}}
          arch: ${{matrix.arch}}
      - uses: actions/cache@v1
        env:
          cache-name: cache-artifacts
        with:
          path: ~/.julia/artifacts
          key: ${{runner.os}}-test-${{env.cache-name}}-${{hashFiles('**/Project.toml')}}
          restore-keys: |
            ${{runner.os}}-test-${{env.cache-name}}-
            ${{runner.os}}-test-
            ${{runner.os}}-
      - uses: julia-actions/julia-buildpkg@v1
      - uses: julia-actions/julia-runtest@v1
      - uses: julia-actions/julia-processcoverage@v1
      - uses: codecov/codecov-action@v1
        with:
          file: lcov.info
    ```

    The steps need not be defined in the steps section. Rather they are picked up from a few predefined scripts developed in the projects GitHub Actions and Julia Actions. This makes the steps declarative.

7.  **Documentation Job**: Invokes the `makedocs` and creates the documentation as part of the doc build process which we have seen earlier.

# Build Steps and Binary Dependencies

When a package is deployed, an optional pre-deployment build step is run to download data files external to the package, executing the build process or placing the built binaries in the right location, and so on. Some of the build steps can be fairly complex; we shall look at a few of the build steps carried out in the package PDFIO as an example.

*   `PDFIO` depends on binary libraries `zlib` and `libcrypto` from the OpenSSL library.
*   The libraries may be available in the operating system. The names of the libraries can vary based on the OS or distro. Julia provides `library_dependency` tools to resolve such issues.
*   The action taken can vary based on the OS.
    *   **Windows**: Prebuilt binaries are downloaded from a specific URL.
    *   **Non-Windows**: The libraries are built from the sources and deployed at specific locations so that only PDFIO can utilize them.

The process can be quite complex, yet highly flexible in addressing all possible build and deployment needs.

However, if you look closely at the line 3 of the `build.jl` of `PDFIO`, for Julia 1.3 or higher the build step is completely ignored. This is possible as the Julia community now provides pre-built binaries for many well-known binary libraries and wraps them with a package name like: `<libraryname>_jll`.

`PDFIO` depends on:

*   OpenSSL_jll
*   Zlib_jll

These packages are built using a build template generation tool called *BinaryBuilder*. If you require pre-built binaries you can be refer to the *JuliaBinaryWrappers* organization and look for the repository you are interested in or submit an issue in project `JuliaPackaging/Yggdrasil`. You can also build binary using `BinaryBuilder` templates and contribute to the project.

# Calling C and Fortran Code

Using a native binary library in Julia requires compatible `Application Binary Interfaces` (`ABI`) across the Julia and the native library. The commonest binaries have C compatible interfaces that are to be accessed from Julia. Such functions can be called using a keyword `ccall()`.

```julia
_zlibVersion() = ccall((:zlibVersion, libz), Ptr{Cstring}, ())
```

The library `libz` has a method symbol of `zlibVersion` that has no input parameters but returns a pointer to a `Cstring`. `Cstring` is a representation of a C style string which is a byte array.

Alternatively, a function in C can invoke a Julia function as a callback using a macro `@cfunction`. Interested readers are suggested to review the manual on Calling C and Fortran Code. The calling convention requires the type mappings be set up properly to be able to use objects allocated in Julia in C or vice versa.

`CXX.jl` can be used to integrate C++ code with Julia. Similarly, `PyCall.jl` provides integration of Python libraries with Julia. `JavaCall.jl` provides ways to invoke Java code from Julia.

# Package Environments: Project.toml and Manifest.toml

A project environment is controlled by the files `Project.toml` and `Manifest.toml`. The `Project.toml` has the package name, UUID, version, and direct dependencies. Each dependency may further depend on other packages. The dependent packages may have dependency on specific version of a package.

![](n4upl4fndrz.jpeg)

**Figure 13.8:** Package A depends on v1 of B. A depends on F which needs version 3 of B. Hence, v3 of B will be the eventual package that A will use

In the example above, packages are assumed to have perfect forward compatibility. Hence, any higher version of the package can provide all the functionalities of a lower version of the package. It may not be the case always. Sometimes, packages specify a range of versions of a package they are dependent on. In such cases, the most useful or compatible version of the package is to be decided. The `Project.toml` of `A.jl` will have dependency listing for `B.jl`, `C.jl`, and `F.jl`. However, the `Manifest.toml` will be computed after the resolution of specific versions and will have information on `B.jl v3`, `C.jl v1`, `D.jl v1`, `E.jl v1`, `F.jl v2`. Whenever you need to reproduce an environment, sharing `Project.toml` and `Manifest.toml` can help. However, in most source-controlled (Git) packages only `Project.toml` is checked-in as `Manifest.toml` is kept flexible to be updated based on the additional packages in the environment. While we realized that the packages have version information, we have so far not discussed how a package manager is aware of the location of the package. Such information is kept at a central registry.

# Julia Package Registry

Packages are core units of delivering functionalities. Once you develop such a package it is natural to advertise it to the external world to be able to access it and use it. The best way to communicate information about your package is to make it available to everyone to use and deliver over a delivery ecosystem. GitHub is a very useful mechanism to achieve the same. Good quality documentation serves as a minimal advertising media. The second part is to make it available through the package registry of Julia. Julia package ecosystem has over 4000 packages. Such packages are mostly Git packages hosted in public Git repositories like GitHub or GitLab. The registered packages are analyzed and made search friendly and documentation is published over JuliaHub for easier access and cloud deployment. Every Julia installation has a local registry that syncs up with the Julia global registry on a periodic basis or on demand when a package update is requested:

![](n4upl4fndr0.jpeg)

**Figure 13.9:** Julia registry in action. The local registry has information about the packages not registered with the global registry. However, it is synced for all the registered packages

Let us assume in the example above, we are developing `A.jl` package in a local system. Hence, information regarding `A.jl` is currently available only in the local registry. It depends on package `F.jl` which is GitHub but not registered with the Julia registry. This is possible when you add a package with the GitHub URL and not the registered package name.

```julia
(dir) pkg> add https://github.com/user_name/F.jl
```

However, information regarding B, C, D, and E packages are all available in the global cloud registry. The registry has the following information about a package:

1.  Version of the Package
2.  Location of the Package: This can be a Git address with version tags or file system path
3.  Dependency of the package on other packages: The information you normally find in a `Project.toml` file.

Location and dependency are stored per version of the package. For example, if you want to modify `C.jl` while using it in `A.jl`, you will need to make a development copy of the same. This is done using develop or `dev` command.

```julia
(A) pkg> dev C
```

The GitHub repository of `C.jl` will be cloned locally into the `$JULIA_DEPOT_PATH/dev`. The package manager interacts with the local registry, updates it with the contents of the cloud registry as and when such information needs updating. It also ensures packages are consistent with the environmental requirements of a project. The `Manifest.toml` is also generated by the package manager after the dependencies are resolved for a project:

![](n4upl4fndr1.jpeg)

**Figure 13.10:** Julia depot folder structure

`JULIA_DEPOT_PATH` is a useful directory where all the packages and information related to them reside. They also have precompiled copies of packages and built binaries. It is by default configured as `$USER_HOME/.julia` folder. It must be noted that irrespective of number of project environments, only one depot exists in a Julia installation. The relevant versions of the packages are downloaded as needed by various environments and shared across them. Julia depot or any other files or package related datastructures should not be manipulated directly. Julia provides extensive command line interfaces and APIs to help with such needs.

# Package Manager REPL Mode

One can switch to pkg mode of the REPL using the character `]`. Once in pkg mode, you can use `add` to add packages to a project, `rm` to remove packages from projects. `update` command updates the registry and downloads the latest registry from the global server. Like packages, the registry is also a Git repository in Julia. Just like methods and types, help can be requested for a package command by pre-pending a question mark (`?`). `?add` will print the command line help on the REPL.

# Programmatic Package Management with Pkg.jl

Although, REPL commands are very helpful for interactive sessions, they may not be entirely helpful in case of scripts or including them in Julia programs. `Pkg` module becomes handy in such cases. The methods like `add()`, `rm()`, etc. provide similar functionalities as command line. Like arguments to the command line, parameters can be provided to the function calls.

Package management in Julia is quite elaborate. However, we have just touched the surface with an overview. The users should get used to packages and learn complex operations as they work with Julia. As many things with Julia package management are implemented using Git, a good knowledge of Git can be very helpful as well.

### Exposing Julia Functions as REST APIs

Julia is a preferred environment for server-based computations. It will be ideal if Julia methods can be exposed as REST endpoints that can be accessed from a browser or a normal HTTP client. We will pick up the N-queens problem from Chapter 13 and try to deploy the computational elements as a server while we render the client locally as would be a typical deployment. `JuliaWebAPI` provides the perfect interface to expose APIs as a web interface.

```julia
webqueens(N) = queens(parse(Int, N))

process(
    JuliaWebAPI.create_responder([
        (webqueens, true)
    ], "tcp://127.0.0.1:9999", true, ""), async=true
)

const apiclnt = APIInvoker("tcp://127.0.0.1:9999")
run_http(apiclnt, 8888)
```

This is only the relevant piece of code for you to expose the `queens(N)` function. Let us look into it in detail:

*   The server application listens to HTTP requests on the port 8888.
*   When it receives a valid REST request, it invokes with the `APIInvoker` with JMQ transport and JSON format.
*   The `APIResponder` running on port 9999 responds after launching the relevant function and converting the return values to a JSON format.

### Deploying with Kuber.jl

Now that the images are registered in the AKS registry, we shall use the `Kuber` package and deploy the services, as follows:

1.  Start a context that connects with AKS using the proxy:
    ```julia
    using Kuber
    ctx = Kuber.KuberContext()
    ```
2.  A pod that is served by one or more containers is taken from the kubqueens image, as follows:
    ```julia
    kubqueens_pod = kuber_obj(ctx, """
    {
    "kind": "Pod",
    "metadata":{
    "name": "kubqueens-pod",
    "namespace": "default",
    "labels": {
    "name": "kubqueens-pod"
    }
    },
    "spec": {
    "containers": [{
    "name": "kubqueens",
    "image": "hojpreg.azurecr.io/kubqueens",
    "ports": [{"containerPort": 8888}]
    }]
    }
    }""")
    ```
3.  Create a load balancer service such that the containers can be exposed with a public URL.
    ```julia
    kubqueens_service = kuber_obj(ctx, """
    {
    "kind": "Service",
    "metadata": {
    "name": "kubqueens-service",
    "namespace": "default",
    "labels": {"name": "kubqueens-service"}
    },
    "spec": {
    "type": "LoadBalancer",
    "ports": [{"port": 8888}],
    "selector": {"name": "kubqueens-pod"}
    }
    }""")
    ```
4.  Both the objects must be attached to the context to make deploy them to the AKS cluster, as follows:
    ```julia
    put!(ctx, kubqueens_pod);
    put!(ctx, kubqueens_service);
    ```
5.  Now wait for the load balancer to come up:
    ```julia
    while true
        println("waiting for loadbalancer to be configured…")
        status = get(ctx, :Service, "kubqueens-service").status
        if nothing !== status.loadBalancer.ingress &&
            !isempty(status.loadBalancer.ingress)
            println(status.loadBalancer.ingress[1])
            break
        end
        sleep(5)
    end
    ```
6.  We can access the AKS deployed service by accessing the REST end point with the public IP address, as follows:
    ```bash
    C:\>curl http://<public_IP>:8888/webqueens/8
    {"data":[4,2,7,3,6,8,5,1],"code":0}
    ```
    You can also use the client code mentioned earlier to connect to the AKS and render the UI. The complete Kubernetes orchestrator code can be seen in `Chapter-14/kubernetes/kubserver.jl`. The services can be removed easily by calling the `delete!` Method, as follows:
    ```julia
    delete!(ctx, kubqueens_service)
    delete!(ctx, kubqueens_pod)
    ```

## Public Cloud Providers: AWS, Azure, and GCP

Amazon Web Services, Microsoft Azure, and Google Cloud Platforms are almost the default public cloud infrastructures available today. Julia packages can connect to all of these platforms and provide service management APIs. In most cases, they are generated using the web services architectures of these platforms, and thus can be extended to adopt to the newer APIs as they are developed.

### AWS.jl

While we can orchestrate workloads using the Kubernetes, native platforms provide granular controls and the ability to use across a larger stack of services. They are not confined to container-based workloads only. Julia provides an extensive coverage of managing AWS-based services using the package `AWS`. AWS is by far the most comprehensive integration among all the public cloud infrastructures for Julia. A large part of this is due to the automated code generation using a *GitHub* action, which is executed every day at 6:00am UTC. It queries the *GitHub* repository `aws-sdk-js` repository for the REST-based APIs. This action generates the wrapper functions for AWS services in Julia. The documentation is also pulled from the AWS documentation and presented as Juliadocs. This ensures the sources can accommodate all the changes to the AWS APIs and documentations. The APIs are generally designed as two categories:

*   Lower-level APIs
*   High-level APIs

Lower-level APIs query the AWS as URLs and commands like GET or POST. High-level APIs are function calls. Whenever Julia functions are generated for AWS functions, camel case names of functions are modified to lower case, and words are separated by an underscore (`_`). For example, the `S3` function call `ListObjectsV2` shall become `list_objects_v2`.

### Azure.jl

Just like AWS, the `Azure` package provides connectivity to Azure cloud infrastructure from a Julia client. The client has a very similar architecture as AWS. It uses Swagger Java Library to generate the Julia signatures for the REST APIs exposed by the Azure framework. Unlike AWS, Julia signatures for Azure APIs are generated intermittently and are not part of an automated GitHub Action. We suggest the reader to explore the APIs and use them for their Azure management needs.

### GoogleCloud.jl

`GoogleCloud` provides connectivity to the `Google Clouds Platform` (`GCP`). It wraps the Google JSON APIs and provides a lightweight framework to invoke the GCP APIs. Just like AWS and Azure, this provides connectivity to the GCP using the web services connectivity frameworks.

## FileIO: A Unified File Interface

Julia has conceptually preferred a driver-like architecture in addressing a class of problems. In Chapter 13, we saw the `WebIO` framework where HTML5 could be rendered on various frontends utilizing a common set of functional APIs. `FileIO` is inherently a similar API framework. It helps load contents of a complete file or save it out using the framework methods `load` and `save`. Based on the underlying file type the relevant reader and writer shall be invoked and the file shall be loaded into the memory. The framework currently supports many file types. A few being: PBM, PGM, PPM, NRRD, AVI, JPG, PDF, TIFF, or a large number of image, sound, and video formats. The following code shall display an image on a Jupyter notebook:

```julia
using FileIO
using ImageShow

tiff = joinpath(pathof(FileIO), "..", "..", "test", "files", "magic2.tiff")
image = load(tiff)
```

You did not need any complex understanding of the `ImageMagick` library. Since, `.tiff` file is registered in the `FileIO` registry as a supported file type and is to be handled by the `ImageMagick` library, a simple `load` method could invoke the necessary module and function and deliver the needed image. Similarly, a call to `save` method with a filename can convert the file to a `.jpg` file.

```julia
save("magic2.jpg", image)
```
