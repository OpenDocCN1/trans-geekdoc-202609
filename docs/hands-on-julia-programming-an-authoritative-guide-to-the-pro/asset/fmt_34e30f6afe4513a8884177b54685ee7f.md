
```julia
function mycumsum(n)
    if n <= 0
        return 0
    else
        return n + mycumsum(n-1)
    end
end
```

While this code is fairly simple, after every function call the computation from the previous call has to be aggregated and added to the current function stack variable. Thus, at every function call, the stack frame has to be constructed before a new function is called. Why?

![](n4upl4fndqo.jpeg)

**Figure 4.3:** In a function call, stack frame has to be created and all internal temporary variables are stored on the stack. `%0` has to be retained during stack unwinding to compute the return value. Each row is a stack frame before the call is made to the recursive function.

Let us rewrite this function in the following manner with an accumulator (`acc`) in the function argument.

```julia
julia> function mycumsum(n, acc=0)
           if n <= 0
               return acc
           else
               return mycumsum(n-1, n+acc)
           end
       end
mycumsum (generic function with 2 methods)

julia> mycumsum(4)
10

julia> mycumsum(10)
55
```

There is no further computation after the recursive function call. The aggregation is to be carried out through the accumulator. There is no need to construct a stack frame on every function call.

![](n4upl4fndqp.jpeg)

**Figure 4.4:** When each recursive function is called a new frame is created. The computations are carried out in the forward direction. There is no need for an unwinding of the stack for result aggregation as the last function call has the computed result. Unwinding is only needed to pass the return value and reclaiming of the resources.

Hence, the function call can be replaced with a jump instruction. Some functional programming languages like *Lisp* or *Lua* identify such conditions programmatically and eliminate the stack frame creation. This process is called **Tail Call Optimization** (`TCO`). In functional programming, recursion is given higher importance over iterative programming. Stack frame creation consumes memory. Hence, deep recursive function calls can lead to stack overflow. Unlike Lisp, Julia does not have native support for TCO[^3].

![](n4upl4fndqq.jpeg)

**Figure 4.5:** A TCO optimizing compiler would have converted to an iterative code.

Although Julia is a functional programming language, it also has complete iterative programming support. Some programmers have used Julia macros and generative programming to emulate TCO-like behavior.

## Multiple Dispatch

In object-oriented programming, polymorphism is used to describe the change of behavior of a method based on the objects that it is acting upon. Simply put, the `area` method called on a `rectangle` object will be a different computation from the `area` method called on a `triangle` object. We saw functions behave differently based on the number of arguments in earlier examples. In this section, we shall see functions can behave differently based on the types of arguments. In Julia, when functions of the same name have different behaviors depending on the type and count of the arguments, they are called **methods**.

## Example: Area Calculation

The following example shows two `area` functions: one for `Triangle` and the other for the `Rectangle` type. Since both the shapes are subtypes of a parent abstract type `Shape`, we shall modify the default `show` method so that the relevant `area` function is called from the `show` method. `Base.show` is the default method that is called to display an object on the REPL.

```julia
abstract type Shape end

struct Rectangle <: Shape
    w::Float32
    h::Float32
end

struct Triangle <: Shape
    a::Float32
    b::Float32
    c::Float32
end

area(r::Rectangle) = r.w * r.h

function area(t::Triangle)
    a, b, c = t.a, t.b, t.c
    s = (a + b + c) / 2
    return sqrt(s * (s-a) * (s-b) * (s-c))
end

julia> r, t = Rectangle(3, 4), Triangle(3, 4, 5)
(Rectangle(3.0f0, 4.0f0), Triangle(3.0f0, 4.0f0, 5.0f0))

julia> area(r)
12.0f0

julia> area(t)
6.0f0

julia> Base.show(io::IO, s::Shape) =
           print(io, "Shape Type:", typeof(s), " Area:", area(s))

julia> r
Shape Type:Rectangle Area:12.0

julia> t
Shape Type:Triangle Area:6.0
```

[^4]: Reference link placeholder.

In a typical object-oriented language, a method is associated with an object. Based on the object type a specific function is called. This kind of method dispatch is called a **single dispatch interface**. However, languages that support multiple dispatch interfaces do not associate a function to a specific type. Depending on the runtime type of the object they resolve to the relevant method interface and invoke the most relevant method. `area` method is not a method for the `Rectangle` type or the `Triangle` type. Rather based on the object type they are to be looked up from a multiple dispatch lookup. This architecture is also seen with languages like *Lisp*.

## Constructors

Objects can have inherent constraints. When created they must be enforced so that invalid objects are not created. Constructors ascertain such behaviors. In the `Rectangle` or `Triangle` types, one can create invalid objects by providing negative values for the sides.

```julia
struct RectangleA
    w::Float32
    h::Float32
    function RectangleA(w::Real, h::Real)
        (w > 0 && h > 0) ||
            error("invalid rectangle with non-positive h or w")
        return new(w, h)
    end
end
```

The creation of the object now invokes the constructor.

```julia
julia> a = RectangleA(1.0, -4.0)
ERROR: invalid rectangle with non-positive h or w
Stacktrace:
…

julia> a = RectangleA(1//5, 4//5)
Rectangle(0.2f0, 0.8f0)

julia> a = RectangleA(1, 4)
Rectangle(1.0f0, 4.0f0)

julia> a = RectangleA(1.0, 4.0)
Rectangle(1.0f0, 4.0f0)

julia> a = RectangleA(1.0, 4)
Rectangle(1.0f0, 4.0f0)
```

The constructors can take any `Real` number as a parameter and they ensure no non-positive value is permitted as part of the arguments. Suppose we were to create two additional constructors to construct squares.
