## 优化的第一原则

*优化的第一原则是不要*[^1]。这一建议由 Unix 操作系统大师 *Kernighan* 和 *Pike* 在其开创性著作 *The Practice of Programming* 中提出。二十多年来，这点并未有太大变化。一个正确运行的程序远胜过一个运行错误的快速程序。然而，为了确保程序表现出接近可接受的性能，采取了许多变通方法。不存在绝对的性能，也不存在针对所有条件都优化的代码。按今天的标准高性能的代码，其计算能力在未来可能远不如一个相对简单的应用程序。Voyager（旅行者号）是离开太阳系的首个人造物体，其计算能力远不如现代手机[^2]。人们并不必真正手动优化每一行代码。在大多数情况下，许多最优代码生成器和编译器编译出的代码远优于手动优化的代码。像 Julia 这样的现代语言利用 LLVM 来处理跨平台最优代码生成，并在编译或代码生成期间解决许多已知的优化问题。有人可能会问，既然硬件便宜且易于获取，为什么还要费心去优化代码？答案在于：无论硬件变得多么便宜，你都需要从中榨取那额外的一丁点性能。

## 空闲循环处理与响应性

在单线程的单处理器上运行多个应用程序并非真正的同时多任务处理。操作系统根据计划抢占任务，让处理器一次执行一个任务。用户会感觉所有任务都在同时运行，而实际上它们只是在很短的时间间隔内执行，然后切换到下一个任务。在基于**图形用户界面 (GUI)** 的应用程序中，用户界面对用户输入的响应性被赋予了高于将其他后台任务执行完成的重要性。在单处理器系统上运行长时间计算密集型任务的多任务应用程序中，惯常的做法是间歇性地处理 UI 事件以保持 UI 响应。这在 Windows 系统中称为**空闲循环处理**[^3]。这里最优响应时间优先于原始执行速度。因此，代码的纯执行速度可能并非所有代码优化项目的目标。
