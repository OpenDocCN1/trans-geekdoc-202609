# Profiling

In the examples we analyzed so far, we knew a specific function has a performance bottleneck that we would like to get over. In many large applications, such knowledge is unlikely. For example, a particular word processor is slow to open a file and render the contents on the screen. There could be many factors. The file reading may be slow, some particular feature in the document is computationally complex, or file size is too big and reading all the data and caching data in the memory can be a bottleneck. Profiling helps you identify such scenarios. At certain fixed intervals (say every milli-seconds), statistical profilers would look at the code execution stack and record the state of the stack like the line number and function where the execution was during the query. Once the run is complete, they would correlate all such data and report the number of times a particular function was encountered along with the back trace of all the functions called to reach such function.

Julia has an in-built statistical profiler. `Profiler` is in the module called `Profile`. We shall use this tool to profile a function `profile_test`[10](#9ztdqvro.html#n4upl4fndio).

```julia
using Profile

function profile_test(n)
    for i = 1:n
        A = randn(100,100,20)
        m = maximum(A)
        Am = mapslices(sum, A; dims=2)
        B = A[:,:,5]
        Bsort = mapslices(sort, B; dims=1)
        b = rand(100)
        C = B.*b
    end
end
```

```julia
julia> profile_test(1)
```

The code is run once so that it is compiled and the time taken for such activities is not captured as part of the profiler sampling. Now we run the function over 100 iterations and profile the run.

```julia
julia> @profile profile_test(100)
```

# Performance Design Patterns

In [previous section], we looked at design patterns related to functional programming. In this section, we will review a few patterns that help improve the performance of the code.

## Memoization

When a pure function is called several times, it shall produce the same output. Rather than computing the result again and again, if we can cache the value, it will reduce the computation overheads. This process is called `memoization`. One of the most common examples discussed in the context of memoization is the Fibonacci series[11](#9ztdqvro.html#n4upl4fndip). A Fibonacci series is best described recursively with the following code:

```julia
fib(n) = n < 3 ? 1 : fib(n-1) + fib(n-2)
```

The function is called recursively twice for every invocation. If we record the number of invocations by modifying the function a bit, you can see the number of function calls growing exponentially.

```julia
function fib(n)
    if n < 3
        return (result=1, calls=1)
    else
        r1, c1 = fib(n-2)
        r2, c2 = fib(n-1)
        return (result=r1+r2, calls=1+c1+c2)
    end
end
```

```julia

           r, c = fib(i)
           println("n:", i, "\tresult: ", r, "\tcalls: ", c)
       end

n:4 result: 3 calls: 5
n:5 result: 5 calls: 9
n:6 result: 8 calls: 15
```

```julia
julia> @btime fib(20)
```

The function is quite expensive still, considering there are only addition operations involved. `fib(6) = fib(5) + fib(4)`. We have already seen `fib(4)` in the computation of `fib(5)`. If we cache `f(4)` as soon as we compute it, we need not have to compute again while computing `f(5)` and `f(6)`. We can reuse the value from the previous computation. We employ the same concept in the following code:

```julia
const mem = Dict()

function fib(n)
    haskey(mem, n) && return mem[n]
    println("Calling fib: ", n)
    res = n < 3 ? 1 : fib(n-1) + fib(n-2)
    mem[n] = res
    return res
end
```

```julia
julia> fib(5)
Calling fib: 5
Calling fib: 4
```
