## Background

*The first principle of optimization is don’t*[^1]. The recommendation was given by *Kernighan* and *Pike*, the masters of Unix operating system, in their seminal book *The Practice of Programming*. Nothing much has changed over two decades. A correctly working program is far superior to an incorrect fast program. However, many workarounds are taken in ensuring a program behaves close to the performance that is acceptable. There is nothing like absolute performance or code optimized for all conditions. The code that is high performing in today’s standards may be much less in computational capability than a relatively simpler application in the future. Voyager, the first manmade object to leave the solar system, had much lesser computing power than a modern-day cell phone[^2]. One does not have to really optimize every bit of code manually. The code compiled by many of the optimal code generators and compilers are far superior to manually optimized code in most cases. Modern languages like Julia utilize `LLVM` to handle the cross-platform optimal code generation and address many of the well-known optimization issues during compilation or code generation. One may ask if the hardware is cheap and easily accessible, why do we need to bother about optimized code? The answer lies in however cheaper hardware may get you will need to squeeze that extra bit from it.

Running several applications over a single processor on a single thread is not true simultaneous multitasking. The operating system preempts the tasks based on a schedule, letting the processor execute one task at a time. The user gets a feeling that all the tasks are running simultaneously, while they are only executed for small intervals and switched over to the next. In **Graphical User Interfaces (GUI)**-based applications, the responsiveness of the user interface to user inputs is given higher importance over the execution of other background tasks to completion. With multitasked applications running long computationally intensive tasks on single-processor systems, the usual practice is to process UI events intermittently to keep the UI responsive. This is known as **idle loop processing**[^3] in the Windows systems. Here the optimal response time is given priority over raw execution speed. Hence, sheer execution speed of the code may not be the objective of all code optimization projects.

When processors did not have trigonometric functions as part of the instruction sets, computations of trigonometric functions would be time consuming as they were to be computed by software emulations. The performance-sensitive applications like game programs would simulate the behavior with the following mathematical equations.

![Trigonometric approximation](n4upl4fndqh.jpeg)

They would essentially keep lookup values for `sinθ` and `cosθ` at 15- or 30-degree intervals and compute intermediate values using the incremental equations given previously. Tables generated at 15-degree intervals using the preceding equations are still within significant range of accuracy.

```julia
julia> n = 6;
δ = pi/180*(90/n);
sinδ, cosδ = δ, (1 - δ*δ/2);

m = Matrix{Float64}(undef, (n+1, 2));
m[1, 1], m[1, 2] = 0.0, 1.0;

for i = 1:n
    m[i+1, 1] = m[i, 1]*cosδ + m[i, 2]*sinδ
    m[i+1, 2] = m[i, 2]*cosδ - m[i, 1]*sinδ
end

julia> m
7×2 Array{Float64,2}:
 0.0        1.0
 0.261799   0.965731
 0.505655   0.864097
 0.714547   0.702104
 0.87387    0.490976

julia> m1 = [[sin(i*δ) for i=0:n] [cos(i*δ) for i=0:n]]
7×2 Array{Float64,2}:
 0.0        1.0
 0.258819   0.965926
 0.5        0.866025
 0.707107   0.707107
 0.866025   0.5

julia> using Statistics
julia> mean(m1-m), std(m1-m)
(0.0009570353971457324, 0.00784842483267987)
```

Such a crude estimation can produce reasonably accurate computation while keeping the computation fast enough. With modern CPUs with in-built trigonometric functions as instructions, these tradeoffs may not be needed. However, performance versus accuracy tradeoff is common in an optimization which this serves to illustrate. And, they are mostly domain specific.

## Cloud Computing and Resource Management

Cloud computing resources can be added to a project or problem at demand. However, the cost of resources is adding significant cost to the projects. Adding more hardware or processing power can solve significantly bigger problems. They are adding to the overall cost as well. For example, smartphones today are able to handle on device speech recognition and many computationally complex tasks involving deep learning and neural computing. This was not possible with advanced desktops a decade back. The hardware of smartphones today is more advanced than the decade-old desktops. So, adding more resources to solve complex problems is never a solution. Optimal utilization of resources to reduce cost overruns is a necessity. Hence, performance management will always be a need for every software system.
