
If this is not the case, the resultant doubly-encrypted ciphertext block should be much harder to break using an exhaustive search. Instead of $2^n$ attempts [where $n$ is the bit length of the key], it would require $2^{2n}$ attempts. If the algorithm is a 64-bit algorithm, the doubly-encrypted ciphertext would require $2^{128}$ attempts to find the key.

This turns out to be true for a known-plaintext attack. Merkle and Hellman [1075] could break this double-encryption scheme in $2^{n+1}$ encryptions, not in $2^n$ encryptions. This was showed for DES, the result can be generated by encrypting from one end, decrypting from the other, and matching the results in memory.

In this attack, the cryptanalyst knows $P_1, P_2$, and $C_2$, such that

```
$C_1 = E_{K_1}[P_1]$
$C_2 = E_{K_2}[C_1]$
```

For each possible $K$, he computes $E_K[P_1]$ and stores the result in memory. After collecting them, he computes $D_K[C_1]$ for each $K$ and looks for the same result in memory. If he finds it, it is possible that the current key is $K_2$ and the key in memory is $K_1$. He then encrypts $P_2$ with $K_1$ and $K_2$; if $C_2$ he can be sure [with a probability of success of 1 in $2^{m-n}$, where $m$ is the block size] that he has both $K_1$ and $K_2$, he keeps looking. The maximum number of encryption attempts he will probably have is $2^n$, or $2^n$. If the probability of error is too large, he can use a three ciphertext block to get a probability of success of 1 in $2^{m-n}$. There are still other optimizations [912].

This attack requires a lot of $2^n$ blocks. For a 64-bit algorithm, this translates to $2^{64}$-64-bit blocks, or $10^{19}$ bytes. This is still considerably more storage than one could comprehend, but it's enough to convince the paranoid of cryptographers that double encryption is not anything.

For a 128-bit key, the amount of memory required is an enormous $10^{39}$ bytes. If we assume that a way exists to store a bit of information on a single atom of aluminum, the memory device required to launch this attack would be a cube of solid aluminum over a side. And then you put it! The meet-in-the-middle attack seems feasible for this size.

Another double-encryption mode, called Davies-Price, is a variant of CBC [435].

```
$C_1 = E_{K_1}[P_1 \oplus E_{K_2}[C-1]]$
$P_1 = D_{K_1}[C_1 \oplus E_{K_2}[C-1]]$
```

They claim "no virtual virtue of this mode," but it seems to be vulnerable to the same meet-in-the-middle attack as other double-encryption modes.

## 15.2 Triple Encryption

### Triple Encryption with Two Keys

A better idea, proposed by Tschman in [1551], operates on a block three times with two keys: with the first key, with the second key, and finally with the first key again. He suggested that the sender encrypts with the first key, decrypts with the second key, and finally encrypts with the first key. The receiver decrypts with the first key, then decrypts with the second key, and finally decrypts with the first key.

```
$C = E_{K_1}(D_{K_2}(E_{K_3}(|P|)))$
$P = D_{K_1}(E_{K_2}(D_{K_3}(C)))$
```

This is sometimes called **encrypt-decrypt-encrypt** (EDE) mode [55]. If the algorithm has an n-bit key, then this scheme is a 2n-1 key. The curious encrypt-decrypt pattern was designed by IBM to preserve compatibility with conventional implementations of the algorithm: Setting the two keys to each other is identical to encrypting with one key. There is no security inherent in the encrypt-decrypt pattern, but this mode has been adopted to improve the DES algorithm in the X.17 and ISO 8732 standards [55, 761].

Triple encryption with two keys is not susceptible to the meet-in-the-middle attack described earlier. But Merkle and Hellman developed another time-memory trade-off that could break this technique in $2^{n-1}$ steps using $2^n$ blocks of memory [1075].

For each possible $K_2$, decrypt $C_2$ and store in memory. Then, decrypt $C_2$ with possible $K_1$ to get $P$. Triple-encrypt $P$ to get $C$, and then decrypt $C$ with $K_1$. If that decryption of $C_2$ with $K_3$ (stored in memory), the $K_1, K_2$ pair is a possible candidate. Check if it is right. If it is, not keep looking.

This is a chosen-plaintext attack, requiring an enormous amount of chosen-plaintext to mount. It requires $2^n$ time and $2^n$ chosen plaintexts. It is not very practical, but it is a weakness. Paul Oorschot and Michael Wiener converted this to a known-plaintext attack. This example assumes EDE mode:

(1) Guess the first intermediate value, $a$.
(2) Tabulate, for each possible $K_1$, the second intermediate value, $b$, when first intermediate value is $a$, using plaintext:
(3) Look up in table, for each possible $K_2$, elements with matching intermediate value, $b$: $b = E_{K_3}(a)$
(4) The probability of success is $p/m$, where $p$ is the number of known plaintexts and $m$ is the block size. If there is no match, then another $a$ and start again.

The attack requires $2^n/p$ time and $p$ memory. For DES, this is $2^{64}/p$. For $p$ greater than $2^{64}$, this attack is faster than exhaustive search.

### Triple Encryption with Three Keys

If you are going to use triple encryption, I recommend three different keys. The key is longer, but storage is usually not a problem. Bits are cheap.

```
$C = E_{k1}(D_{k2}(E_{k3}(P)))$
$P = D_{k1}(E_{k2}(D_{k3}(C)))$
```

The best memory-time attack takes $2^n$ steps and requires $2^n$ blocks of memory; it is a meet-in-the-middle attack [1075]. Triple encryption, with three independent keys, is as secure as one might expect double encryption to be.

### Triple Encryption with Minimum Key (TEMK)

There is a secure way of using triple encryption with two keys that prevents the previous attack called Triple Encryption with Minimum Key (TEMK) [858]. The trick is to derive three keys from two $X_1$ and $X_2$:

```
$K_1 = E_{x1}(D_{x2}(E_{x1}(T1)))$
$K_2 = E_{x1}(D_{x2}(E_{x1}(T2)))$
$K_3 = E_{x1}(D_{x2}(E_{x1}(T3)))$
```

$T_1, T_2$, and $T_3$ are constants, which do not have to be secret. This is a special construction that guarantees for any particular pair of keys, the best attack is a known-plaintext attack.

## Triple-Encryption Modes

It's not enough to justify triple encryption; there are several ways to do it. The decision of which to use affects both security and efficiency. Here are two possible triple-encryption modes:

**Inner-CBC:** Encrypt the file in CBC mode three different times (see Figure 15.1a). This requires three IVs.

```
$C_1 = E_{k1}(S_0 \oplus P)$
$S_1 = D_{k2}(T_1 \oplus S_0)$
$P_1 = T_1 \oplus D_{k1}(T_1)$
$T_2 = S_1 \oplus E_{k2}(S_1)$
$S_2 = C_1 \oplus D_{k1}(C_2)$
```

**Outer-CBC:** Triple-encrypt the file in CBC mode (see Figure 15.1b). This requires one IV.

```
$C_1 = E_{k3}(D_{k2}(E_{k1}(P \oplus C_0)))$
$P_1 = C_1 \oplus D_{k3}(E_{k2}(D_{k1}(C_1)))$
```

Both require more resources than single encryption: hardware or more time. However, given three encryption chips, the throughput of inner-CBC is no slower than single encryption. Since the three CBC encryptions are independent, three chips can be kept busy all the time, each feeding back into itself.

On the other hand, outer-CBC feedback is outside the three encryptions. This means that with three chips, the throughput is only one-third of single encryption.

$C_i = E_{K_3}(D_{K_2}(E_{K_1}(P \oplus C_{i-3})))$

In this case $C_0, C_1$, and $C_2$ are IVs. This doesn't help software implementations any, unless you have a parallel machine.

Unfortunately, the simpler mode is less secure. Biham analyzed various modes with respect to chosen-ciphertext differential cryptanalysis and found that inner-CBC is only slightly more secure than single encryption against a differential attack. If you think of triple encryption as a single larger algorithm, then inner feedbacks allow the introduction of external and known information into the inner workings of the algorithm; this facilitates cryptanalysis. The differential attacks require enormous amounts of chosen ciphertext to mount and are not very practical, but the results should be enough to give the most paranoid pause. Another analysis against meet-in-the-middle and brute-force attacks concludes that they are all secure [806].
