# 8.4 VERIFYING KEYS

When Bob receives a key, how does he know it from Alice and not from some-pretending to be Alice? If Alice gives it to him when they are face-to-face, it's easy. If Alice sends her key via a trusted courier, Bob has to trust the courier. If the key is encrypted with a key-encryption, then Bob has to trust that only Alice has that key. If Alice uses a digital signature protocol to sign the key, Bob has to trust the public-key database when he verifies it. (He also has to trust Alice has kept her key secret.) If a Key Distribution Center [KDC] signs Alice's public key, Bob has to trust that the KDC's public key has not been tampered with.

In the end, one who controls the entire network around Bob can make him whatever he likes. Mallory could send an encrypted and signed message porting to from Alice. When Bob tried to access the public-key database to verify Alice's signature. Mallory could substitute his own public key. Mallory could invent his own false key and exchange the real KDC's public key for his own creation. Bob wouldn't be the winner.

Some people have used this argument to claim that public-key cryptography is useless. The only way for Alice and Bob to ensure that their keys have not been tampered with is to meet face-to-face, public-key cryptography doesn't enhance security at all.

This is naive. It is theoretically true, but reality is far more complicated. Public-key cryptography, with digital signatures and trusted KDCs, makes it much more difficult to substitute one for another. Bob can never be absolutely certain that Mallory is controlling his entire reality, but Bob could be confident that doing so requires more resources than real-world Mallorys have access to.

Bob could verify Alice's key over the phone, where he can hear her voice. Voice recognition is a really good authentication scheme. If it's a public key, he can safely verify it in. If it's a secret key, he can use a one-way hash function to verify the key. Both PGP (see Section 24.12) and AT&T TSD (see Section 24.18) use this kind of key verification.

Sometimes it may not be important to verify exactly which public key belongs to. It may be necessary to verify that it belongs to the same person to whom it belonged last year. If someone sends a signed withdrawal message to a bank, the bank does not have to be concerned with who withdraws the money, only it is the same person who deposited the money in the first place.

# Error Detection during Key Transmission

Sometimes keys get garbled in transmission. Since a garbled key can mean megabytes of decryptable ciphertext, this is a problem. All keys must be transmitted with some kind of error detection and correction bits. This errors in transmission can be easily detected and, if required, the key can be.

One of the widely used methods is to encrypt a constant value with the key, and to send the first 2 to 4 bytes of ciphertext along with the key. At the receiving end, do the same thing. If the encrypted constant matches, then the key has been transmitted without error. The chance of an undetected error ranges from $2^{-26}$ to one in $2^{35}$.
