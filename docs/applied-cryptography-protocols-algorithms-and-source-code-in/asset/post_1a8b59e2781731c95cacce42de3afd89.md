The algorithm operates on plaintext and ciphertext in 32-byte blocks. The key can be any length, although certain key lengths are more efficient for certain one-way hash functions. For the one-way hash functions MD4 and MD5, 96-byte keys work best.

To encrypt, first split the plaintext into two 48-byte halves: $P_l$ and $P_r$. Then, split the key into two 48-byte halves: $K_l$ and $K_r$.

```
$P = P_l, P_r\nK = K_l, K_r$
```

Append $K_t$ to $P_l$ and hash it with a one-way hash function, XOR the result of the hash with $P_r$ to produce $C_r$, the right half of the ciphertext. Then, append $K_l$ to $C_r$, and hash it with the one-way hash function. XOR the result with $P_l$ to produce $C_l$. Finally, append $C_l$ to $C_r$ to produce the ciphertext.

```
$C_l = P_l \oplus H(P_r, K_l)\n$C_r = P_r \oplus H(C_l, K_r)\nC = C_l, C_r$
```

To decrypt, reverse the process. Append $K_l$ to $C_r$, and XOR with $C_l$ to produce $P_r$. Append $K_r$ to $P_r$, and hash and XOR with $C_l$ to produce $P_l$.

```
$P_r = C_r \oplus H(C_l, K_r)\n$P_l = C_l \oplus H(P_r, K_l)\nP = P_l, P_r$
```

The overall structure of Karn is same as many of the other block algorithms discussed in this section. It has only two rows, because the complexity of the algorithm is embedded in the one-way hash function. And since the key is used only as the input to the hash function, it cannot be recovered using a chosen-plaintext attack—assuming, of course, the one-way hash function is secure.

# Luby-Rackoff

Michael Luby and Charles Rackoff showed that Karn is not secure [992]. Consider two single-block messages: $AB$ and $AC$. If a cryptanalyst knows both the plaintext of the first message and the ciphertext of the second, he can easily compute the entire second message. This known-plaintext attack is useful only in certain circumstances, but it is a major security problem.

A three-round encryption algorithm avoids this [992,1643,1644]. It uses three different hash functions: $H_1, H_2$, and $H_3$. Further work shows that $H_1$ can equal $H_3$, or $H_2$ can equal $H_3$, but not both. Also, $H_1, H_2$, and $H_3$ cannot be based on iterating the same basic function [1643]. Anyway, assuming that $H[k,x]$ behaves like a pseudo-random function, here is a three-round version:

- (1) Divide the key into two halves: $K_l$ and $K_r$.
- (2) Divide the plaintext into two halves: $L_0$ and $R_0$.

# Message Digest Cipher (MDC)

MDC, invented by Peter Gutmann [676], is a means of turning one-way hash functions into a block cipher in CFB mode. The ciphers run almost as fast as the hash function and is at least as secure as the hash function. The rest of this section assumes you are familiar with Chapter 18.

Hash functions as MD5 and SHA use a 512-bit text block to transform an input value [128 bits with MD5, and 160 bits with SHA] into an output value of equal size. This transformation is not reversible, but it is perfect for CFB mode: the same operation is used for both encryption and decryption.

Let's look at MDC with SHA. MDC has a 160-bit block size and a 512-bit key. The hash function run "sideways" with the old hash state as the input plaintext block [160 bits] and the 512-bit hash input as a key [Figure 14.5]. Normally, when using the hash to simply hash input, the 512-bit input is varied as each new 512-bit input is hashed. This becomes an unique key.

MDC can be used with any one-way hash function: MD4, MD5, Snefru, and others. It is unpainted. Anyone can use it at any time, in any way, royalty-free[676].

However, I don't trust this construction. It is possible to attack the hash function in a way that hash functions are not designed to withstand. It is not important for hash functions to be able to resist a chosen-plaintext attack, where a cryptanalyst chooses several over 160-bit values, has them "encrypted" by the same 512-bit "Key," and uses these to learn some information about the 512-bit key used. Since the designers didn't have to worry about this, it seems like a bad idea to count on your cipher being able to resist this attack.

# Combining Block Ciphers

There are many ways to combine block algorithms to get new algorithms. The impetus behind these schemes is to try to increase security without going through the trouble of designing a new algorithm. DES is a secure algorithm, it has been cryptanalyzed for good years and the most practical way to break it is still brute force. However, the key is too short. Wouldn't it be to use DES as a building block for another algorithm with a longer key? We'd have the best of both worlds: the assurance of two decades of cryptanalysis plus a long key.

**Multiple encryption** is one combination technique: using an algorithm to encrypt the plaintext multiple times with multiple keys. Cascading is like multiple encryption, but it uses different algorithms. There are other techniques.

Encrypting a plaintext twice with the same key, whether the same algorithm or a different one, is not smart. For the same algorithm, it does not affect the complexity of a brute-force search. (Remember, you assume the algorithm including the number of encryptions used.) For different algorithms, it may or may not.
