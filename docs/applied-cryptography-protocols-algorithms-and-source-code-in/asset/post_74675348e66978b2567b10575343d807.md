The key certification provisions of PEM make this unlikely if everyone follows proper procedures, but people have been known to be sloppy. A more insidious attack would be for Mallory to modify the PEM implementation running on your system. This modified implementation could surreptiously send all of your mail, encrypted with his public key. If the modified implementation works well, you will never know what is happening. There's no way to prevent this kind of attack. You could use a one-way function and fingerprint the PEM code. Then, each time you do, you could check the fingerprint for modification. But Mallory could modify that at the same time as well. If Mallory can get access to your machine, he can subvert the security of PEM. The moral is that you can never trust a piece of software if you cannot trust the hardware it is running on. For most people, this kind of paranoia is unwarranted. For some, it is very real.

### RIP

PEM implements the PEM protocols. Although technically not public domain, the program is publicly available and can be used royalty-free for personal, noncommercial applications. A license for its use is included with the documentation. The code cannot be exported. For example, U.S. government laws do not apply outside the United States, and some people have ignored the export rules. PEM code available on bulletin boards worldwide. Something/SIG, which only digital signatures, is exportable. At this writing, PEM is not a complete implementation of the protocols; it does not implement certificates for authenticating keys. Before writing PEM, Riordan wrote a similar program called RP. This was intended as a public-domain electronic-mail encryption program. To avoid issues, Riordan used Rabin's algorithm (see Section 19.5). Public Key Partners claimed that their patents were broad enough to cover all of public-key cryptography and threatened to use it; Riordan stopped distributing the program. PEM is not really used anymore. It is not compatible with PEM. Since PEM was used with the full blessing of Public Key Partners, there is no reason to use instead.

## 24.11 MESSAGE SECURITY PROTOCOL (MSP)

The Message Security Protocol (MSP) is the military equivalent of PEM. It was developed by the NSA in the late 1980s by the Secure Data Network System (SDNS) program. It is an X-400-compatible application-level protocol for securing electronic mail. MSP will be used for signing and encrypting messages in the Department of Defense's planned Defense Message System (DMS) network.

The Preliminary Message Security Protocol (PMSP), to be used for "unclassified but sensitive" messages, is a version of MSP adapted for use with both X.400 and TCP/IP. This protocol is also Mosaic. Like PEM, MSP and PMSP software are flexible and designed to accommodate a variety of algorithms for security functions including signing, hashing, and encryption. PSMP will work with the Capstone chip (see Section 24.17).

## 24.12 PRETTY GOOD PRIVACY (PGP)

Pretty Good Privacy (PGP) is a freeway electronic-mail security program, originally designed by Phil Zimmermann [1652]. It uses IDEA for data encryption, RSA (with keys up to 2047 bits) for key management and digital signatures, and MD5 as a one-way hash function.

PGP's random public keys use a probabilistic primality test, and get their initial seeds from measuring the user's keyboard latency while typing. PGP generates random IDEA keys using the method delineated in ANSI X9.17, Appendix C [see Section 8.1 [55]]. PGP uses the symmetric algorithm instead of DES. PGP encrypts the user's private key using a hashed passphrase instead of a password.

PGP-encrypted messages have layered security. The only thing a cryptanalyst can learn about an encrypted message is, assuming the recipient knows the recipient's key ID, only after the recipient decrypts the message does he learn who signed the message, if it is signed. Contrast this approach with PEM, which leaves a bit of information about the sender, recipient, and message in the unencrypted header.

### 24.12 Pretty Good Privacy (PGP)

The most interesting aspect of PGP is its distributed approach to key management (sec Section 8.12). There are no key certification authorities, PGP instead supports a "web of trust." Every user generates and distributes his public key. Users sign each other's public keys, creating an interconnected community of PGP users.

For example, Alice signs Bob's public key, Bob signs Charlie's, and Charlie signs Alice's. If Alice trusts Bob, and Bob trusts Charlie, then Alice can trust Charlie's key even if she has never met him. This allows a way to establish trust without a central authority.
