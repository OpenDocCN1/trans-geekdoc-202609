## Authentication Protocol

- [1] Peggy picks a random number, $r$, less than $q$, and computes $x = a^r \pmod p$. This is the preprocessing stage and can be done long before Victor is present.
- [2] Peggy sends $x$ to Victor.
- [3] Victor sends a random number, $e$, between 0 and $2^t - 1$. [I'll discuss $t$ in a moment.]
- [4] Peggy computes $y = (r + se) \pmod q$ and sends $y$ to Victor.
- [5] Victor verifies that $x = a^v \pmod p$.

The security is based on the parameter $t$. The difficulty of breaking the algorithm is about $2^t$. Schnorr recommended $p$ to be about 512 bits, $q$ be about 140 bits, and $t$ be 72.

## Digital Signature Protocol

Schnorr can also be used as a digital signature protocol on a message, $M$. The public-key/private-key pair is the same, but we're now adding a one-way hash function, $H[M]$.

- [1] Alice picks a random number, $r$, less than $q$, and computes $x = a^r \pmod p$. This computation is the preprocessing stage.
- [2] Alice concatenates $M$ and $x$, and hashes the result:

```
$e = H[M,x]$
```
- [3] Alice computes $x' = a^{v'} \pmod p$. The signature is $e$ and $y$; she sends $y$ to Bob.
- [4] Bob computes $x' = y^v \pmod p$. He then confirms that the concatenation of $M$ and $x'$ hashes to $e$.

```
$e = H[M,x']$
```

If it does, he accepts the signature as valid.

In his paper, Schnorr cites these novel features of his algorithm:

Most of the computation for signature generation can be completed in a preprocessing stage, independent of the message being signed. Hence, it can be done during idle time and not affect the signature speed. An attack against this preprocessing stage is discussed in [475], but I don't think it's practical.

For the same level of security, the length of signatures is less for Schnorr for RSA. For example, a 140-bit $q$, signatures are only 212-bits long, less half the length of RSA signatures. Schnorr's signatures are also much shorter than ElGamal.

Of course, practical considerations may make even fewer bits suitable for a given scheme: For example, an identification scheme where the cheater must perform an on-line attack in only a few seconds, versus a signature scheme where the cheater can calculate for years off-line to come up with a forgery.

A modification of this algorithm, by Ernie Brickell and Kevin McCurley, enhances its security [265].

## 21.4 CONVERTING IDENTIFICATION SCHEMES TO SIGNATURE SCHEMES

There is a standard method of converting an identification scheme into a signature scheme: Replace Victor with a one-way hash function. The message is not hashed before it is signed; instead the hashing is incorporated into the signing algorithm. In principle, this can be done with any identification scheme.

### 22.1 DIFFIE-HELLMAN

Diffie-Hellman was the first public-key algorithm ever invented, back way in 1976 [496]. It gets its security from the difficulty of calculating discrete logarithms in a finite field, as compared with the ease of calculating exponentiation in the same field. Diffie-Hellman can be used for key distribution—Alice and Bob can use this alg to generate a secret key—but it cannot be used to encrypt and decrypt messages.

The math is simple. Alice and Bob agree on a large prime, $n$ and $g$, such that $g$ is primitive mod $n$. These two integers do not have to be secret; Alice and Bob can agree over some insecure channel. They can even be common among a group of users. It doesn't matter.

Then, the protocol goes as follows:

- (1) Alice chooses a random integer $x$ and sends Bob $X = g^x \bmod n$
- (2) Bob chooses a random integer $y$ and sends Alice $Y = g^y \bmod n$
- (3) Alice computes $k = Y^x \bmod n$
- (4) Bob computes $k' = X^y \bmod n$

Both $k$ and $k'$ are equal to $g^{xy} \pmod n$. No one listening on the channel can compute that value. The choice of $n$ can have a substantial impact on the security of this system. The choice of $g$ should also be large: you can choose any $g$ that is primitive; actually, g does not have to be primitive.

## Diffie-Hellman with Three or More Parties

The Diffie-Hellman key-exchange protocol can easily be extended to work with more people. In this example, Alice, Bob, and Carol together generate:

- (1) Alice chooses a random integer $x$ and sends Bob $X = g^x \bmod n$
- (2) Bob chooses a random integer $y$ and sends Carol $Y = g^y \bmod n$
- (3) Carol chooses a random integer $z$ and sends Alice $Z = g^z \bmod n$
- (4) Alice sends Bob $X' = Z^x \bmod n$
- (5) Bob sends Carol $Y' = X^y \bmod n$
- (6) Carol sends Alice $Z' = Y^z \bmod n$
- (7) Alice computes $k = Y^z \bmod n$
- (8) Bob computes $k = Z^y \bmod n$
- (9) Carol computes $k = X^z \bmod n$

The secret key, $k$, is equal to $g^{xyz} \pmod n$.

## Hughes

This variant of Diffie-Hellman allows Alice to generate a key and send it to Bob [745].

- (1) Alice chooses a random integer $x$ and generates $k = g^x \bmod n$
- (2) Bob chooses a random integer $y$ and sends Alice $Y = g^y \bmod n$
- (3) Alice sends Bob $X = Y^x \bmod n$
- (4) Bob computes $z = y^{-1} \bmod n$ and $k' = X^y \bmod n$

If everything goes correctly, $k = k'$. The advantage of this protocol over Diffie-Hellman is that $k$ can be computed before any interaction, and Alice can encrypt a message using $k$ prior to contacting Bob.

## Key Exchange Without Exchanging Keys

If you have a community of users, each could publish a public key, $X = g^y \bmod n$, in a common database. If Alice wants to communicate with Bob, she just has to retrieve Bob's public key and generate their shared secret key. She could encrypt a message with that key and send it to Bob. Bob would retrieve Alice's public key to generate the shared secret key.

Each pair of users would have a unique secret key, and no prior communication between users is required. The public keys to be certified to prevent spoofing attacks and should be changed regularly, but otherwise this is a pretty clever idea.
