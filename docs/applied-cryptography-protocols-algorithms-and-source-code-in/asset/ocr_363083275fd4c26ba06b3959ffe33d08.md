# 182 CHAPTER 8 Key Management

The problem with this key management system is that Bob has to trust his security officer not to misuse everyone's keys. Even more significantly, the employees have to trust the security officer not to misuse their keys. A better solution is to use a secret-sharing protocol [see Section 3.7].

When Alice generates a key, she divides up that key into some number of pieces. She sends each piece—encrypted, of course—to a different company officer. None of those alone is the key, but someone can gather all the pieces and reconstruct the key. Now Alice is protected against any malicious person, and Bob is protected against losing all of Alice's data after her run-in with the truck. Or, she could store the different pieces, with each of the officer's different public keys, on her hard disk. That way, no one gets involved with key management until it becomes necessary.

Another backup scheme [188] uses smart cards (see Section 24.13) for the temporary storage of keys. Alice can put the key to secure her hard drive onto the smart card and give it to Bob while she is away. Bob can use the card to get into Alice's drive, because the key inside Bob cannot learn. And the drive is bilaterally audible: Bob can verify that the key will open Alice's drive, and Alice returns it if Bob has used the key and how many times.

A such scheme makes no sense for data transmission. On a secure telephone, the key should exist for the length of the call and no longer. For data storage, as is described, escrow key can be a good idea. I lost about one key every five years, and memory is better than that. If 200 million people were using cryptography, that rate would equal 40 million keys per year. I keep copies of my house keys with a neighbor be lose mine. If keys were like cryptographic keys, and I lost them, I could never get inside and recover my possessions, ever again. Just as I keep off-site backups of my data, it makes sense to keep backups of my data-encryption keys.

# 8.9 COMPROMISED KEYS

All of the protocols, techniques, and algorithms in this book are secure only if the key (the private key in a public-key system) remains secret. If Alice's key is lost, stolen in the newspaper, or otherwise compromised, then all her security is gone.

If the compromised key was for a symmetric cryptosystem, Alice has to change her key and the actual damage was minimal. If it was a private key, she has big problems, her public key is on servers all over the network. And Eve gets access to Alice's private key, she can impersonate her on the network: reading mail, signing correspondence, entering into contracts, and so forth. Eve can effectively, become Alice.

It is vital that news of a private key's compromise propagate quickly throughout the network. Any databases of public keys must immediately be notified that a particular key has been compromised, lest unsuspecting person encrypt a message in that compromised key.
