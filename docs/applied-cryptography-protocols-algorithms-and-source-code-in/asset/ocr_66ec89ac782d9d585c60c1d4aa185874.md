# Security Kerberos

Steve Bellovin and Michael Merritt discussed potential security vulnerabilities of Kerberos [108]. Although this paper was written about the Version 4 protocols, many of their comments also apply to Version 5.

It may be possible to cache and replay old authenticators. Although timestamps are stored to prevent this, replays can be done during the lifetime of the ticket. Servers are supposed to store all valid tickets to prevent replay, but this is not always possible. And lifetimes can be long, eight hours is typical.

Authenticators rely on the fact that all the clocks in the network are more or less synchronized. If a fault can be fueled by the correct time, then an old authenticator can be replayed without any problem. Most network protocols are insecure, so this can be a serious problem.

Kerberos is also vulnerable to password-guessing attacks. An intruder can collect tickets and try to decrypt them. Remember that the average user doesn't always choose good passwords. If Mallory collects enough tickets, she has chances of recovering a password as good.

The most serious attack involves malicious software. The Kerberos protocols rely on the fact that the Kerberos software is trustworthy. There is nothing to stop Mallory from surreptitiously replacing all client Kerberos software with a version that, in addition to completing the Kerberos protocols, records passwords. This is a problem with any cryptographic software package on an insecure computer, but the widespread use of Kerberos in these environments makes it a particularly tempting.

Enhancements to Kerberos are in the works, including an implementation of public-key cryptography and a smart-card interface for key management.
