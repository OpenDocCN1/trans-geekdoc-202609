
## 3.1 Key Exchange

Key and Message Transmission
Alice and Bob need not complete the key-exchange protocol before exchanging messages. In this protocol, Alice sends Bob the message, $M$, without any previous key exchange protocol:

- (1) Alice generates a random session key, $K$, and encrypts $M$ using $K$. $E_K[M]$
- (2) Alice gets Bob's public key from the database.
- (3) Alice encrypts $K$ with Bob's public key. $E_B[K]$
- (4) Alice sends both the encrypted message and encrypted session key to Bob. $E_B[M], E_B[K]$

For security against man-in-the-middle attacks, Alice can sign the transmission.
- (5) Bob decrypts Alice's session key, $K$, using his private key.
- (6) Bob decrypts Alice's message using the session key.

This hybrid system is how public-key cryptography is most often used in a communications system. It can be combined with digital signatures, timestamps, and any other security protocols.

## Key and Message Broadcast

There is no reason Alice can't send the encrypted message to several people. In this example, Alice will send the encrypted message to Bob, Carol, and Dave:

- (1) Alice generates a random session key, $K$, and encrypts $M$ using $K$. $E_K[M]$
- (2) Alice gets Bob's, Carol's, and Dave's public keys from the database.
- (3) Alice encrypts $K$ with Bob's public key, Alice encrypts $K$ with Carol's public key, and then encrypts $K$ with Dave's public key. $E_B[K], E_C[K], E_D[K]$
- (4) Alice broadcasts the encrypted message and all the encrypted keys to anybody who can receive it. $E_B[K], E_C[K], E_D[K]$
- (5) Only Bob, Carol, and Dave can decrypt the key, $K$, each using his or her private key.
- (6) Only Bob, Carol, and Dave can decrypt Alice's message using $K$.

This protocol can be implemented on a store-and-forward network. A central server can forward Alice's message to Bob, Carol, and Dave along with their particular encrypted key. The server doesn't have to be secure or trusted, since it will not be able to decrypt any of the messages.

## 3.2 AUTHENTICATION

When Alice logs into a host computer (or an automatic teller, or a telephone banking system, or any other type of terminal), how does the host know who she is? How does the host know she knows is not Eve trying to falsify Alice's identity? Traditionally, passwords solve this problem. Alice enters her password, and the host confirms that it is correct. Both Alice and the host know this secret of knowledge and the host requests from Alice every time she tries to log in.

## Authentication Using One-Way Functions

What Roger and Mike Guy realized that the host does not need to know the passwords; the host just has to differentiate valid passwords from invalid passwords. This is easy with one-way functions [1599,526,1274,1121]. Instead of storing, the host stores one-way functions of the passwords.

- (1) Alice sends the host her password.
- (2) The host performs a one-way function on the password.
- (3) The host compares the result of the one-way function to the value it previously stored.

Since the host no longer stores a tale of everybody's valid password, the threat of some breaking into the host and stealing the password list is mitigated. The list of passwords operated by the one-way function is useless, the one-way function cannot recover the passwords.

## Dictionary Attacks and Salt

A file of passwords encrypted with a one-way function is still vulnerable. In spare time, Mallory collects a list of 1,000,000 common passwords. He hashes all 1,000,000 of them with the one-way function and stores the results. If each password is 8 bytes, the resulting file will be no more than 8 megabytes, it will fit on a few floppy disks. Mallory stores an encrypted password file. He compares that file with his file of encrypted passwords and sees what matches.

This is a dictionary attack, and it's surprisingly successful [Section 8.1]. Salt is a way to make it more difficult. Salt is a random string that is concatenated before being operated by the one-way function. Then, both the salt value and the result of the one-way function are stored in a database of the host. If the number of possible salt values is large enough, this practically eliminates a dictionary attack against commonly used passwords because Mallory has to generate the hash for each possible salt value. This is a simple attempt at an initialization vector (see Section 9.3).

## 3.2 Authentication

The point here is to make sure that Mallory has to do a trial encryption of each password in his dictionary every time he tries to break another person's password, rather than just doing one massive precomputation for all possible passwords.

A lot of salt is needed. Most UNIX systems use only 12 bits of salt. Even with, Daniel Klein developed a password-guessing program that often cracks 40 percent of the passwords on a given host system within a week [847,848] [sec Section 8.1]. David Feldmeier and Philip Karn compiled a list of about 732,000 common passwords concatenated with each of 4096 possible salt values. They estimate that 40 percent of passwords on any given host can be broken with this salt [51].

Salt isn't magic; increasing the number of salt bits won't solve everything. Salt protects against general dictionary attacks on a password file, not against a concerted attack on a single password. It protects people who have the same password on multiple machines, but doesn't make poorly chosen passwords any better.

## SKEY

SKEY is an authentication program that relies on a one-way function for its security.

To set up the system, Alice enters a number, R. The computer computes $f(R), f(f(R)), f(f(f(R))), and so on, around a hundred times. Call these numbers $x_1, x_2, ..., x_{10}$. The computer prints out this list of numbers, and Alice puts it in her pocket for safekeeping. The computer also stores $x_{10}$ in the clear, in a login database next to Alice's name.

The first time Alice wants to log in, she types her name and $x_{10}$. The computer calculates $f(x_{10})$ and compares it with $x_{10}$; if they match, Alice is authenticated. Then, the computer replaces $x_{10}$ with $x_1$ in the database. Alice keeps $x_{10}$ off her list.

Every time Alice logs in, she enters the last unused number for her host: $x$. The computer computes $f(x)$ and compares it with $x_{i+1}$ stored in the database. Eve cannot get any useful information because each number is used only once, and the function is one-way. Similarly, the database is not useful to an attacker. Of course, when Alice runs out of numbers on her list, she has to reinitialize the system.

## Authentication Using Public-Key Cryptography

Even with salt, the first protocol has security problems. When Alice sends her password, anyone who has access to the data path can read it. She might be accessing her host through a convoluted transmission path that passes through four industrial competitors, three countries, and two thinking universes. Eve can be any one of those points, listening to Alice's sequence. If Eve has access to the processor memory of the host, she can see the password before she hashes it.

Public-key cryptography solves this problem. The host keeps a file of every user's public key, all users keep their own private keys. Here is a naive attempt at a protocol. When logging in, the protocol proceeds as follows:

## Basic Protocols

- (1) The host sends Alice a random string.
- (2) Alice encrypts the string with her private key and sends it back to the host, along with her name.
- (3) The host looks up Alice's public key in its database and decrypts the message using that key.
- (4) If the decrypted string matches what the host sent in the first place, the host allows Alice access.

No one else can access Alice's private key, so no one can impersonate Alice. More importantly, Alice never sends her private key over the transmission line to the host. This requires an intelligent terminal Alice trusts; neither the host nor the communications needs to be secure.
