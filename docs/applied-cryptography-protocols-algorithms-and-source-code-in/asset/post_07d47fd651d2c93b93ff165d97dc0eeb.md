## Pseudo-Random-Sequence Generators

Primitive polynomials are fastest in software, unless two bits of the shift register have to be XORed to generate each new bit. Actually, all the feedback polynomials listed in Table 16.2 are sparse, meaning that they only have a few coefficients. Sparseness is a source of weakness, sometimes break the algorithm. It is better to use dense polynomials, those with a lot of coefficients, for cryptographic applications. If you use dense polynomials, and especially if you make them part of the key, you can have shorter LFSRs.

Generating dense polynomials modulo 2 is not easy. In general, to generate primitive polynomials of degree $k$ you need to know the factorization of $2^k-1$. Three good references for finding primitive polynomials are [652,1285,1287].

LFSRs are decent pseudo-random-sequence generators all by themselves, but they have some annoying nonrandom properties. Sequential bits are linear, which make them useless for encryption. For an LFSR of length $n$, the internal state is the next $n$ output bits of the generator. If the feedback scheme is unknown, it can be determined from only $2n$ output bits of the generator, by using the highly efficient Berlekamp-Massey algorithm [1082,1083]; See Section 16.3.

Also, large random numbers generated from sequences of this sequence are highly correlated, and for certain types of applications, not very random at all. Even so, LFSRs are often used as building blocks in encryption algorithms.

## LFSRs in Software

LFSRs are slow in software, but they are faster in assembly language than C. One solution is to run 16 LFSRs (or 32, depending on your computer's word size) in parallel. This scheme uses an array of words that is the length of LFSR, with each bit position in the words representing a different LFSR. Assuming all the feedback polynomials are the same, this can run quite quickly. In general, the best way to update shift registers is to multiply the current state by suitable binary matrices. Instead of using the bits in the tap sequence to generate the new leftmost bit, each bit in the tap sequence is XORed with the output of the generator and replaced; then the output of the generator becomes the new leftmost bit (see Figure 16.5). This is sometimes called Galois configuration.

In C, this looks like:

```c
#define mask 0x8000057
static unsigned long ShiftRegister=1;
void seed_LFSR(unsigned long seed){
    if (seed == 0)
        seed = 1;
    ShiftRegister = seed;
}
```

In general, if you are using hardware that is good at shifts, use Fibonacci configuration; if you can exploit parallelism, use Galois configuration.

## DESIGN AND ANALYSIS OF STREAM CIPHERS

Most practical stream-cipher designs center around LFSRs. In the early days of electronics, they were easy to build. A shift register is nothing more than an array of bit memories and the feedback sequence is just a series of XOR gates. Even in VLSI circuitry, an LFSR-based stream cipher can give you a lot of security with only a few gates. The problem with LFSRs is that they are very inefficient in software. Any stream cipher outputs a bit at a time; you have to iterate the algorithm 64 times to encrypt what a single DES can encrypt.

This branch of cryptography is fast-paced and very charged. Most designs are secret; a majority of encryption systems used today are based on LFSRs. In fact, most CPUs (X-MP, Y-MP) have a curious instruction generally known as "population count." It counts the bits in a register and can be used both to efficiently calculate the Hamming distance between two binary words and to implement a vectorized version of LFSR. I've heard that the canonical instruction, demanded by almost all computer contracts, is [9901, 1272]. Sometimes it's amazing to see the simple ones proposed again. On the other hand, an astonishing large number of seemingly complex shift-register-based generators have been cracked. And certainly military cryptanalysis institutions such as the NSA have cracked a lot more.

## Linear Complexity

Analyzing stream ciphers is often easier than analyzing block ciphers. For example, one important metric to analyze LFSR-based generators is **linear complexity**, or linear span. This is defined as the length, *n*, of the shortest LFSR that can mimic the generator output. Any sequence generated by a finite state machine over a field has a linear complexity [1006]. Linear complexity is important because a simple algorithm, the *Berlekamp-Massey algorithm*, can generate this LFSR after examining $2n$ bits of the keystream [1005]. Once you've generated this LFSR, you've broken the stream cipher.

This idea has extensions from fields to rings [1298], and when the output sequence is viewed as numbers over fields of odd characteristic [842]. A further enhancement is the notion of a **linear complexity profile**, which measures the linear complexity of the sequence as it gets longer and longer [1357,116,441,582]. Another algorithm for computing linear complexity is useful only in specialized circumstances [597,595,596,1333]. A generalization of linear complexity is in [776]. There is also the notion of sphere complexity [502] and 2-adic complexity [844].

In any case, a high linear complexity does not necessarily indicate a secure generator, but a low linear complexity indicates an insecure one [1357,1249].

## Correlation Immunity

Cryptographers try to get a high complexity by combining the output of several output sequences in some nonlinear manner. The danger is there that one or more of the internal output sequences—just outputs of individual LFSRs—can be correlated with the combined keystream and attacked using linear algebra. Thomas Siegenthaler shows that **correlation immunity** or a divide-and-conquer attack can be precisely defined, and that there is a trade-off between correlation immunity and linear complexity [1450].

The basic idea behind a correlation attack is to identify some correlation between the output of the generator and the output of one of its pieces. Then, by observing the output sequence, you can obtain information about that internal output. Using that information and other correlations, collect information about the other inputs until the entire generator is broken.

Correlation attacks and variations such as fast correlation attacks—offer a tradeoff between computational complexity and effectiveness—have been fully applied to a number of LFSR-based keystream generators [1451,278,1452,572, 1636,1051,1090,350,633,1054,1089,995]. Some interesting new ideas among these lines are in [46,1641].
