Some communications applications, such as telephone encryptors, can use session keys. A session key is a key that is used for one communications session—a single telephone conversation—and discarded. There is no reason to store the key after it has been used. And if you use some key-exchange protocol to transfer the key from one consonant to the other, the key doesn't have to be stored before it is used. This makes far less likely that the key might be compromised.

# Controlling Key Usage

In applications it may be desirable to control how a session key is used. Some users may need session keys only for encryption or for decryption. Session keys might only be authorized for use on a certain machine or at a certain time. One scheme to handle these sorts of restrictions attaches a Control Vector (CV) to the key; the control vector specifies the uses and restrictions for that key [see Section 24.1] [[1025,1026]]. This CV is hashed and XORed with a master key; the result is used as an encrypted key with the CV. To recover the session key, hash the CV and XOR it with the master key, and use the result to decrypt the encrypted session.
The advantages of this scheme are that the CV can be of arbitrary length and it is always stored in the clear with the encrypted key. This scheme assumes quite a bit tamperproof hardware and the inability of users to get at the keys directly. This system is discussed further in Sections 24.1 and 24.8.

# 8.6 UPDATING KEYS

Imagine an encrypted data link where you want to change keys daily. Sometimes it's a pain to distribute a new key every day. An easier solution is to generate a new key from the old key, which is sometimes called key updating.

All it takes is one-way function. If Alice and Bob share the same key and both operate on it the same one-way function, they will get the result. Then they can take the bits they need from the results to create the new key.

Key updating works, but remember that the key is only as secure as the old key. If Eve managed to get her hands on the old key, she can perform the key updating function herself. However, if Eve doesn' have the old key and is trying a ciphertext-only attack on the encrypted traffic, this is a good way for Alice and Bob to protect themselves.

# 8.7 STORING KEYS

The least complex key storage problem is that of a single user, Alice, encrypting files for later. Since she is the only person involved, she is the only person responsible for the key. Some systems use the easy approach: The key is stored in Alice's brain and never on system. Alice is responsible for remembering the key and entering it every time she needs a file encrypted or decrypted.
