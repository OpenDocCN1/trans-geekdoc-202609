## How Kerberos Works

This section discusses Kerberos Version 5. I will outline the differences between Version 4 and Version 5 further on. The Kerberos protocol is straightforward [see Figure 24.1]. A client requests a ticket for a Ticket-Granting Service [TGS] from Kerberos. This ticket is sent to the client, encrypted in the client's secret key. To use a particular server, the client requests a ticket for that server from the TGS. Assuming everything is in order, the TGS sends the ticket back to the client. The client then presents this ticket to the server along with an authenticator. Again, if nothing is wrong with the client's credentials, the server lets the client have access to the service.

## Credentials

Kerberos uses two types of credentials: tickets and authenticators. (The rest of this section uses the notation used in Kerberos documents—see Table 24.1.) A ticket is used to pass securely to the server the identity of the client for whom the ticket was issued. It also contains information that the server can use to ensure that the client using the ticket is the same client to whom the ticket was issued. An authenticator is an additional credential, presented with the ticket.

A Kerberos ticket takes this form:

```
$T_{c,s} = [c, a, v_{c}, k_{cs}]$
```

A ticket is good for a single server and a single client. It contains the client's name and network address, the server's name, a timestamp, and a session key. This information is encrypted with the server's secret key. Once the client gets this ticket, she can use multiple times to the server—until the ticket expires. The client cannot decrypt the ticket (she does not know the server's secret key), but can present it to the server in its encrypted form. No one listening on the network can read or modify the ticket as it passes through the network.

A Kerberos authenticator takes this form:

```
$A_{c,s} = [c, t, k_{cs}]_{k_{cs}}$
```

The client generates it every time she wishes to use a service on the server. The authenticator contains the client's name, a timestamp, and an additional session key, all encrypted with the session key shared between the client and the server. Unlike a ticket, it can only be used once. However, since the client can generate authenticators as needed (it knows the secret key), this is not a problem.

The authenticator serves two purposes: it contains some plaintext encrypted in the session key. This proves that it also knows the key. Just as important, the sealed packet includes the timestamp. An eavesdropper who records both the ticket and the authenticator cannot replay them two days later.

## Kerberos Version 5 Messages

Kerberos Version 5 has five messages (see Figure 24.1):

- 1. Client to Kerberos: $c, t_{gs}$
- 2. Kerberos to client: $[K_{c,gs}]_{K_{c}}, [T_{c,gs}]_{T_{gs}}|_{K_{gs}}$
- 3. Client to TGS: $[A_{c,gs}]_{K_{c}}, t_{gs}, [T_{c,gs}]_{T_{gs}}|_{K_{gs}}$
- 4. TGS to client: $[K_{c,s}]_{K_{c}}, T_{gs}, [T_{c,s}]_{K_{s}}$
- 5. Client to server: $[A_{c,s}]_{K_{c}}, [T_{c,s}]_{K_{s}}$

These will now be discussed in detail.

## 24.5 Kerberos

### Getting an Initial Ticket

The client has one piece of information that proves her identity: her password. Obviously we don't want her to send this password over the network. The Kerberos protocol minimizes the chance that this password will be compromised, while at the same time not allowing a user to properly authenticate unless she knows the password.

The client sends a message containing her name and the name of the TGS authentication server. [There can be many TGS servers.] In reality, the user probably just enters her name into the system and the login program sends the request.

The Kerberos authentication server looks up the client in its database. If the client is in the database, Kerberos generates a session key to be used between her and the TGS. This is called a Ticket Granting Ticket (TGT). Kerberos encrypts this session key with the client's secret key. It creates a TGT for the client to authenticate herself to the TGS and encrypts in the TGS's secret key. The authentication server sends both of these encrypted messages back to the client.

The client now decrypts the first message and retrieves the session key. The secret key is one-way hash of her password, as a legitimate user will have trouble doing it. If the user were an imposter, he would not know the password.

### Getting Server Tickets

When the client needs a ticket, she sends a request to the TGS. The TGS, upon receiving the request, decrypts the TGT with its secret key. It then creates a new session key for the client and the server, encrypted with the session key. Both of these messages are sent back to the client. The client decrypts the message and extracts the session key. The client presents the ticket to the server. The server decrypts the ticket and the authenticator, as discussed previously, and also checks the client's address and the timestamp with the current time. If everything matches, the server allows the client to proceed.

Checking timestamps assumes that all machines have synchronized clocks, at least within several minutes.

### Example Implementations

The TGS responds to a valid request by returning a valid ticket for the client. The TGS should also keep track of all authenticators, because past requests can have timestamps that are still valid. If another request with the same ticket and timestamp is received, it treats it as an attempt to replay.

### Requesting a Service

Now the client is ready to authenticate herself to the server. She creates a message very similar to the one sent to the TGS. The request consists of the ticket received from Kerberos (already encrypted with the server's secret key) and the encrypted authenticator.

For applications that require mutual authentication, the server sends the client back a message consisting of the timestamp, encrypted with the session key. This proves that the server knew its secret key and could decrypt the ticket and therefore the authenticator.
