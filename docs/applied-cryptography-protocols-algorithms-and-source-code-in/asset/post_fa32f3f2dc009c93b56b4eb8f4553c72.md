An example of this system is IPS [881]. Users can either enter the 64-bit key or enter the key as a longer string. The system then generates a 64-bit key from the character string using a key-crunching technique.

Another solution is to store the key in a magnetic stripe card, plastic card with an embedded ROM chip (called a ROM key), or smart card [556,557,455]. A user could then enter his key by inserting the physical token into his encryption box or attached to his computer terminal. While the user can use the key, he does not know it and cannot compromise it. He can use it only in the way and for the purposes indicated by the control vector.

A ROM key is a very clever idea. People understand physical keys, what they signify and how to protect them. Putting a cryptographic key in the same physical format makes storing and protecting that key more intuitive.

This technique is made by splitting the key into two halves, one half in the terminal and the other half in the ROM key. The U.S. government's STU-III secure telephone works this. Losing the ROM key does not compromise the cryptographic key—change that and everything is back to normal. The same is true with the loss of the terminal. This way, compromising the ROM key or the system does not compromise the cryptographic key—an adversary has both parts.

Hard-remember keys can be stored in encrypted form, for example, an RSA key could be encrypted with a DES key and stored on disk. To recover the RSA key, the user has to type in the DES key to a decryption.

If the keys are generated deterministically [with a cryptographically secure pseudorandom generator], it might be easier to regenerate the keys from an easy-to-remember password every time they are required.

Ideally, a key should never appear unencrypted outside the encryption device. This isn't always possible, but it is a worthy goal.

## 8.8 BACKUP KEYS

Alice is the chief financial officer at Sec., Ltd.—We don't tell you motto.” Like any good corporate officer, she follows the company's security guidelines and encrypts all her data. Unfortunately, she ignores the company's street-crossing guidelines and gets hit by a truck. What does the company's president, Bob, do?

Unless Alice left a copy of the key, she's in deep trouble. The whole point of encryption is to make files irrecoverable without the key. Unless Alice was a moron and used lousy encryption software, her files are gone forever.

Bob can avoid this is sometimes called key escrow [see Section 4.1]: He requires all employees to write their keys on paper and give the company's security officer, who will lock them in a safe somewhere [or encrypt them all with a master key]. Now, when Alice is bowled over the Interstate, Bob can ask his security officer for her key. Bob should make sure to have the combination to the safe somewhere; otherwise, if the security officer is run over by another truck, Bob will be out of luck again.

## CHAPTER 8 Key Management

The problem with this key management system is that Bob has has to trust his security officer not to misuse everyone's keys. Even more significantly, the employees have to trust the security officer not to misuse their keys. A better solution is to use a secret-sharing protocol [see Section 3.7].

When Alice generates a key, she divides up that key into some number of pieces. She sends each piece—encrypted, of course—to a different company officer. None of those alone is the key, but someone can gather all the pieces and reconstruct the key. Now Alice is protected against any malicious person, and Bob is protected against losing all of Alice's data after her run-in with the truck. Or, she could store the different pieces, with each of the officer's different public keys, on her hard disk. That way, no one gets involved with key management until it becomes necessary.

Another backup scheme [188] uses smart cards (see Section 24.13) for the temporary storage of keys. Alice can put the key to secure her hard drive onto the smart card and give it to Bob while she is away. Bob can use the card to get into Alice's drive, because the key inside Bob cannot learn. And the drive is bilaterally audible: Bob can verify that the key will open Alice's drive, and Alice returns it if Bob has used the key and how many times.

## 8.9 COMPROMSED KEYS

The longer a key is used, the greater the chance it will be compromised. If you use the key for a year, there's a far greater chance of compromise than if you use it for a day.

The longer a key is, the greater the loss if the key is compromised. If a key is used only to encrypt a single document on a file server, then the loss of the key means only the compromise of that document. If the same key is used to encrypt all the budgetary information on the file server, then its loss is most devastating.

The longer a key is used, the greater the temptation for some to spend the effort to break it—even if that is a brute attack. Breaking a key shared between two military units for a day would enable someone to read and fabricate messages between those units for that day. Breaking a key shared by an entire military command structure for a year would enable that same person to read and fabricate messages throughout the world for a year.

## 8.10 Lifetime of KEYS

No encryption key should be used for an indefinite period. It should expire automatically-like passwords and licenses. There are several reasons for this:

- The longer a key is, the greater the chance that it will be compromised. People write keys down, people lose them. Accidents happen. If you use the key for a year, there's a far greater chance of compromise than if you use it for a day.
- The longer a key is, the greater the loss if the key is compromised. If a key is used only to encrypt a single document on a file server, then the loss of the key means only the compromise of that document. If the same key is used to encrypt all the budgetary information on the file server, then its loss is most devastating.
- The longer a key is used, the greater the temptation for some to spend the effort to break it—even if that is a brute attack. Breaking a key shared between two military units for a day would enable someone to read and fabricate messages between those units for that day. Breaking a key shared by an entire military command structure for a year would enable that same person to read and fabricate messages throughout the world for a year.

If Alice doesn't know exactly when her key was compromised, things are difficult. Alice might want to back out of a contract because she signed it. If the system allows this, then anyone can back out of a contract claiming his key was compromised before it was signed. It has to be a matter for an adjudicator to decide.

This is a serious problem and brings to light the dangers of tying all her identity to a single key. It would be better for Alice to have different keys for different applications—as she has physical keys in her pocket for different locks. Other solutions to this problem involve biometrics, limits on what can be done with a key, time delays, and counters.

These procedures and tips are hardly optimal, but are the best we can do. The moral of the story is to protect keys, and protect private keys above all.
