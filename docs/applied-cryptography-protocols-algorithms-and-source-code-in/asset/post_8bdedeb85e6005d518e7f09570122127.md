
## 7.3 Comparing SYMMETRIC AND PUBLIC-KEY LENGTH

A system is going to be attacked at its weakest point. If you are designing a system that uses both symmetric and public-key cryptography, the lengths for each type of cryptography should be chosen so that it is equally difficult to attack the system via each mechanism. It makes no sense to use a symmetric algorithm with a 128-bit key together with a public-key algorithm with a 386-bit key, just as it makes no sense to use a symmetric algorithm with a 56-bit key together with a public-key algorithm with a 1024-bit key.

Table 7.9 lists public-key modulus whose factoring difficulty roughly the equality of a brute-force attack for popular symmetric key lengths. This table shows that if you are concerned enough about security to choose a symmetric algorithm with a 112-bit key, you should choose a modulus for your public-key algorithm of about 1792 bits. In general, though, you should choose a public-key length that is more secure than your symmetric-key length. Public keys generally stay around, and are used to protect more information.

## 7.4 BIRTHDAY ATTACKS AGAINST ONE-WAY HASH FUNCTIONS

### Table 7.9
Symmetric and Public-key Key Lengths with Brute-Force Attacks
| Symmetric Key Length | Public-key Key Length |
| :--- | :--- |
| 56 bits | 384 bits |
| 64 bits | 512 bits |
| 80 bits | 768 bits |
| 112 bits | 1792 bits |
| 128 bits | 2304 bits |

There are two brute-force attacks against a one-way hash function. The first is the most obvious: Given the hash of message, H(M), an adversary would like to create another document, M', such that H(M) = H(M').

The second attack is more subtle: An adversary would like to find two random messages, $M$, and $M'$, such that $H(M)=H(M')$. This is called a *collision*, and it is a far easier attack than the first one.

The birthday paradox is a standard statistics problem. How many people must be in a room for the chance to be greater than even one of them shares their birthday? The answer is 253. How many people must be there for the chance to be greater than at least two of them share the same birthday? The answer is surprisingly low: 23. With 23 people in the room, there are still 253 different *pairs* of people in the room.

Finding with a specific birthday is analogous to the first attack, finding two people with the same random birthday is analogous to the second attack. The second is commonly known as a **birthday attack**.

Assume that one one-way hash function is secure and the best way to attack it is by brute force. It produces an $m$-bit output. Finding a message that hashes to a given value would require hashing $2^m$ random messages. Finding two messages that hash to the same value would only require $2^{m/2}$ random messages. A machine that has a million messages per second would take 600,000 years to find a second message that matched a 64-bit hash. The same machine could find a pair of messages matched to the same value in an hour.

This means if you are worried about a birthday attack, you should choose a hash-value twice as long as you otherwise might think you. For example, if you want to drop the odds of someone breaking your system to less than 1 in $2^{80}$, use a 160-bit one-way hash function.

## 7.5 How LONG SHOULD A KEY BE?

There's no single answer to this question; it depends on the situation. To determine how much security you need, you must ask yourself some questions. How much is your data worth? How long does it need to be secure? What are your adversaries' resources?

A list might be worth $1000. Financial data for an acrimonious divorce might be worth $10,000. Advertising and marketing data for a large corporation might be $1 million. Master keys for a digital system might be worth billions. In the world of commodities trading, secrets only need to be kept for minutes. In the newspaper, today's secrets are tomorrow's headlines. Product development information might need to remain secret for a year or two. U.S. Census data are required to remain secret for 100 years.

You can even specify security requirements in these terms. For example: The key length must be such that there is a probability less than 1 in $2^{80}$ that an attacker with $100 million could break the system within one year, even using technology advances at 30 percent per annum over the period.

Future computing is hard to estimate, but here is a reasonable rule of thumb: The efficiency of computing equipment doubles every eighteen months and increases by a factor of 10 every five years. So, in 50 years the fastest computers will be 10 billion faster than today! Remember, too, that these numbers only relate to general-purpose computers; who knows what kind of cryptystem-breaking equipment will be developed in the next 50 years?

Assuming that a cryptographic algorithm will be used in 30 years, you can get some idea how secure it is. An algorithm designed today will probably not get used until 2000, will still be used in 2025 to encrypt messages that must remain secret until 2075.

## 7.6 CAVEAT EMPOR

This entire chapter is a whole lot of nonsense. The very notion of predicting computing power 10 years in the future, let alone 50 years is absolutely ridiculous. These calculations are meant to be a guide, nothing more. If the past is any guide, the future will be vastly different from anything we can predict.

Be conservative. If your keys are longer than you imagine necessary, then fewer technological surprises can harm you.
