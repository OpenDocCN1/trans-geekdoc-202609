There's no reason Alice to use the same public-key/private-key pair for encrypting and signing. She can have two keys: one for encryption and the other for signatures. Separation has its advantages: she can surrender her encryption key to the police without compromising her signature, one key can be escrowed [see Section 4.13] without affecting the other, and the keys can have different sizes and expire at different times.

Of course, timestamps should be used with this protocol to prevent reuse of messages. Timestamps can also protect against other pitfalls, such as the one described.

# Resending the Message as a Receipt

Consider an implementation of this protocol, with the additional feature of confirmation messages. Whenever Bob receives a message, he returns it as a confirmation of receipt.

+   Alice sends a message with her private key, encrypts it with Bob's public key, and sends it to Bob.
$E_B(S_A(M))$

+   Bob decrypts the message with his private key and verifies the signature with Alice's public key, verifying that Alice signed the message and recovering the message.
$V_A(D_B(E_A(M))) = M$

+   Bob sends a message with his private key, encrypts it with Alice's public key, and sends it back to Alice.
$E_A(S_B(M))$

+   Alice decrypts the message with her private key and verifies the signature with Bob's public key. If the resultant message is the same she sent to Bob, she knows that Bob received it accurately.
