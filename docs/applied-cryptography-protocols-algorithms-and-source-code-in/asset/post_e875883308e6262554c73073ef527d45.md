## Cryptanalysis of IDEA

IDEA's key is 128 bits—over twice as DES. Assuming a brute-force attack is the most efficient, it would require $2^{128}$ [$10^{38}$] encryptions to recover the key. Design a chip that can test a billion keys per second and throw a billion at the problem, and it will still take $10^{13}$ years—longer than the age of the universe. An array of $10^{24}$ chips could find the key in a day, but there aren't enough silicon atoms in the universe to build such a machine. Now we're getting somewhere—although I'd kept my eye on the dark matter debate.

Perhaps brute force isn't the best way to attack IDEA. The algorithm is still too new for any differential cryptanalytic results. The designers have done their best to make the algorithm immune to differential cryptanalysis; they defined the concept of a Markov cipher and showed that resistance to differential cryptanalysis can be modeled and quantified [931,925]. Figure 13.10 shows the original IDEA algorithm to be strengthened against differential cryptanalysis. It's amazing how a few changes can make such a difference. In [925] Jahan argued (he gave, but no proof) that IDEA is immune to differential cryptanalytic attack only after 4 or 8 rounds. According to Biham, the key-cryptanalytic attack works against IDEA, either could [160].

Meier examined the three algebraic operations of IDEA, and pointed out that while they are incompatible, there are instances where they could be simplified in such a way as to facilitate cryptanalysis some of the time [1050]. His attack is more efficient than brute-force—for 2-round IDEA ($2^{24}$ operations), but less effective for 3-round IDEA or higher. IDEA, with 8 rounds, is safe.

Jean Daemen discovered a class of weak keys for IDEA [406,409]. These are not weak keys in the sense of the DES weak keys; that is, the encryption function is self-inverse. They are weak in the sense that if they use them, an attacker can easily identify them in a cipher-plaintext attack. A weak key is [in hex]

```
0000,0x0000,0x000000x,xxxx,0000
```

The number at positions of "x" can be any number. If this is used, the bitwise XOR of certain plaintext pairs guarantees the bitwise XOR of the resultant ciphertext pairs.

In any case, the chance of accidentally generating one of these weak keys is small: in $2^{68}$. There is no danger you choose keys at random. And it is easy to modify IDEA so that it doesn't have any weak keys: XOR every subkey the value 0xdae [409].

I know of no other cryptanalytic results against IDEA, although many people have tried.

## IDEA Modes of Operation and Variants

IDEA can work within any block cipher mode discussed in Chapter 9. Any double-IDEA implementation would be susceptible to the same meet-in-the-middle attack on DES (Section 15.1). However, because IDEA's key length is more than double DES, the attack is impractical. It would require a storage space of $64 \cdot 2^{128}$ bits, or $10^{39}$ bytes. Maybe there is enough matter in the universe to create a memory device that large, I doubt it.

If you're worried about parallel universes, using a triple-IDEA implementation (Section 15.2):

```
$C = E_{k3}[D_{k2}[E_{k1}[P]]]$
```

It is immune to the meet-in-the-middle attack.

There's no reason why you can't implement IDEA with independent subkeys, especially if you have key-management tools to handle the longer key. IDEA needs a total of 52 16-bit keys, for a total key length of 832 bits. This variant is definitely more secure, but no one knows how much.

## MMB

A naïve variation might double the block size. The algorithm would work just well with 32-bit sub-blocks instead of 16-bit-blocks, and a 256-bit key. Encryption would be quicker and security would increase $2^3$ times. Would it? The theory behind the algorithm hinges on the fact that $2^{16} + 1$ is prime; Perhaps the algorithm could be modified to work, but it would have very different properties. Lai says it would be difficult to make it work significantly secure than DES, it's always easy to substitute one for the other in existing applications. If your database templates accept a 64-bit key, generate a 128-bit key by concatenating the 64-bit key with itself. Remember that IDEA is weakened considerably by this modification. If you are more concerned with speed than security, you might consider a variant of IDEA with fewer rounds. Currently the best attack against IDEA is faster than brute force for 5 rounds or less [1050]; 4 round IDEA would be twice as fast, and far as secure. 

## Caveats

IDEA is a relatively new algorithm, and many questions remain. Is IDEA a group? (Lai thinks not [926].) Are there still undiscovered ways of breaking this cipher? IDEA has a theoretical basis, but time has fallen to new forms of cryptanalysis. Several academic and military groups have cryptanalized IDEA. None of them have gone public about successes they might have had.

## MMB

A complaint against IDEA, that it uses a 64-bit encryption block, was addressed by Joao in an algorithm called MMB (Modular Multiplication-based cipher); MMB is based on the same theory as IDEA: mixing operations of different algebraic groups. MMB is an iterative algorithm that mainly consists of linear steps (XOR and key operations) and parallel applications of four nonlinear substitutions. These substitutions are determined by multiplication modulo $2^{32}$ – constant factors. The result is an algorithm that has both a 128-bit key and 128-bit block size. MMB operates on 32-bit sub-blocks of text $[X_0, X_1, X_2, X_3]$ and 32-bit sub-blocks of key $[K_0, K_1, K_2, K_3]$. This makes the algorithm well suited for implementation on modern, 32-bit processors. A nonlinear function, $f$, is applied six times alternating XORing. Here it is [all index operations are mod 4]:

x_i = x_i \oplus k_i$, for $i = 0$ to $3$
$f(x_0,x_1,x_2,x_3)$

$x_i = x_i \oplus k_{i+1}$, for $i = 0$ to $3$
$f(x_0,x_1,x_2,x_3)$

$x_i = x_i \oplus k_{i+2}$, for $i = 0$ to $3$
$f(x_0,x_1,x_2,x_3)$

$x_i = x_i \oplus k_i$, for $i = 0$ to $3$
$f(x_0,x_1,x_2,x_3)$

$x_i = x_i \oplus k_{i+1}$, for $i = 0$ to $3$
$f(x_0,x_1,x_2,x_3)$

$x_i = x_i \oplus k_{i+2}$, for $i = 0$ to $3$
$f(x_0,x_1,x_2,x_3)$

The function $f$ has three steps:

- (1) $x_i = x_i \cdot x_i$, for $i = 0$ to $3$ (If the multiplication is all 1s, the output is also all 1s).
- (2) If the least significant bit of $x_0$ is 1, then $x_0 = x_0 \oplus C$. If the least significant byte of $x_3$ is 0, then $x_3 = x_3 \oplus C$.
- (3) $x_i = x_{i-1} \oplus x_i \oplus x_{i+1}$, for $i = 0$ to $3$

All index operations are 4. The multiplication operation in step [1] is $2^{32}-1$. For purposes of the algorithm, if the second operand is $2^{32}-1$, then the result is $2^{32}-1$. The various constants are:

$C = 2aaaaaa$
$c_0 = 025fcdb$
$c_1 = 2 \cdot c_0$
$c_2 = 2^3 \cdot c_0$
$c_3 = 2^7 \cdot c_0$

Decryption is the reverse process. Steps [2] and [3] are their own inverse. Step [1] uses $c^{-1}$ instead of $c_0$. The value of $c_0^{-1}$ is 0odad4694.

## Security of MMB

The design of MMB ensures that each round has considerable diffusion independent of the key. In IDEA, the amount of diffusion is to some extent dependent on the particular subkeys. MMB was also designed not to have weak keys as IDEA.
