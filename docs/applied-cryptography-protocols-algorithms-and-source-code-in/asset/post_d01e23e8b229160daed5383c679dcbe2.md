## Using Random Noise

The best way to collect a large number of random bits is to tap the natural randomness of the world. This method requires specialized hardware, but you can try with computers.

Find an event that happens randomly: atmospheric noise peaking at a certain threshold, a toddler falling while learning to walk, or some such. Measure the time interval between one event and the next. Record it. Measure the time interval between the second event and the third. Record it as well. If the first time interval is greater than the second, output 1 as the bit. If the second time is greater, output 0 as the event. Do it for the next event.

Throw a dart at the New York Stock Exchange closing prices in your local newspaper. Compare the price of the stock with the closing price of the stock directly above it. If the one you hit is higher, output 0; if it is less, output 1.

Hold a Geiger counter up to your computer, count emissions over a fixed time, and keep the least significant. Or measure the time between successive ticks (since the radioactive source is decaying, the average time between successive ticks is continuously increasing. You want to choose a source with a half life long enough to make negligible—like platinum. Or if you're worried about health, apply appropriate statistical corrections.)

One of them are placed in proximity, and the random bit is a function of the difference in change between the two events. ## CHAPTER 17 Other Stream Ciphers

There is also a random-number generator that uses the computer's disk drive [49]. It measures the time required to read a disk block and uses the variation in that time as a random source. It filters the data to remove structure that comes from quantization, then applies a Fourier transform to vectors of numbers. This removes bias and correlation. Finally, it uses the spectral angles for frequencies in [0, pi], normalized to the unit interval, as the random bits. A large part of the variation in disk rotation speed is caused by turbulence, so there is randomness in the system. There are caveats, if you keep too many bits of the output, you are using the fast transform as a random-number generator and risk predictability. And it's best to read the same disk block over and over, so that your filtering doesn't have to remove structure that comes from the disk-scheduler. An implementation of this system was able to collect about 100 bits per minute [49].

## Using the Computer's Clock

If you want a single random bit (or even a few), take the least significant bit from any clock register. This might not be terribly random in a UNIX system because of potential synchronizations, but it works on some personal computers.

Beware of getting too many bits this way. Executing the same subroutine times in succession could easily skew bits generated in this manner. For example, if each generation subroutine takes an even number of clock ticks to execute, you will get an endless stream of the same bit out of the generator. If each subroutine takes an odd number of clock ticks to execute, you will get an endless stream of alternating bits out of generator. Even if the reason isn't this obvious, the result bit will be far from random.

One random-number generator works this way [918]:

> Our random-number generator ... works by setting an alarm and then incrementing a counter register in the CPU until an interrupt occurs. The contents of the register are then XORed with the contents of an output buffer (truncating the register to 8 bits). After each byte of the output buffer is filled, the buffer is further processed by a right, circular shift of each character by 2 bits. This has the effect of moving the most active (and random) bits into the most significant positions. The entire process is repeated 3 times. Each character of the buffer has been touched by the two random bits of the counter register after interrupts. It is 4n interrupts have occurred where n is the number of desired random bits.

This method is very sensitive to the randomness of system interrupts and the granularity of the clock. The output looked pretty good when tested on real UNIX machines.

## Measuring Keyboard Latency

People's typing patterns are both random and nonfiction. They are random enough that they can be used as a means of identification, but they are random enough that they can be used to generate random bits. Measure the time between successive keystrokes, then take the least significant bits of these measurements. These bits are going to be pretty random. This technique may not work on a UNIX terminal, since the keystrokes pass through filters and other mechanisms before they get to your program, but it will work on most personal computers.

Ideally, you only want to collect one random bit per keystroke. Collecting more may skew the results, depending on how good a type is sitting on the keyboard. This technique is limited, though. While it's easy to have someone type 100 words or when it is time to generate a key, it isn't reasonable to ask the typer to type a 100,000-word essay to generate a keystream for a one-time pad.

## Biases and Correlations

A major problem with all these systems is that there could be nonrandomness in the generated sequence. The underlying physical processes might be between the digital part of the computer and the physical process. These instruments could easily introduce problems.

To eliminate bias, or skew, is to XOR several bits together. If a random bit is biased toward 0 by a factor e, then the probability of 0 can be written as:

```
P(0) = .5 + e
```

XORing two bits together yields:

```
P(0) = |.5 + e|^2 + |.5 - e|^2 = .5 + 2e^2
```

By the same calculation, XORing 4 bits together yields:

```
P(0) = .5 + 8e^4
```

XORing m bits will exponentially converge to an equal probability of 0 and 1. If you know the maximum bias you are willing to accept for your application, you can calculate how many bits you need to XOR in pairs to get random bits below that bias.

An even better method is to look at the bits in pairs. If the 2 bits are different, take the first as the output of the generator and the second at the next pair. This eliminates bias completely. Other techniques for reducing bias using transition mappings, compression, and fast Fourier transforms [51].

The potential problem with both methods is if there is a correlation between adjacent bits, these methods will increase the bias. One way to correct this is to use multiple random sources. Take four different random sources and XOR them together, or take two random sources, and look at them bits in pairs.

For example, take a radioactive source and record an event every time the noise exceeds a certain level. atmospheric noise. Get a random bit from each and XOR them to produce the random bit.
