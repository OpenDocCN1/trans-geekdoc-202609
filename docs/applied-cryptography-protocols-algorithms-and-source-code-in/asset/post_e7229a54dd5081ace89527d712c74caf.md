
## 3.3 Authentication and Key Exchange

### Denning-Sacco

This protocol also uses public-key cryptography [461]. Trent keeps a database of everyone's public keys.

- (1) Alice sends a message to Trent with her identity and Bob's identity:
$A, B$
- (2) Trent sends Alice Bob's public key, $K_B$, signed with Trent's private key, $T$. Trent also sends Alice her public key, $K_A$, signed with his private key.
$S_T(B,K_B),S_T(A,K_A)$
- (3) Alice sends Bob a random session key and a timestamp, signed in her private key and encrypted in Bob's public key, along with signed public keys:
$E_B(S_A(K,T_A)),S_A(B,K_B),S_A(A,K_A)$
- (4) Bob decrypts Alice's message with his private key and verifies Alice's signature with her public key. He checks to make sure that the timestamp is still valid.

At this point both Alice and Bob have $K$, and can communicate securely. This looks good, but it isn't. After completing the protocol with Alice, Bob can then masquerade as Alice [5]. Watch:

- (1) Bob sends name and Carol's name to Trent
$B, C$
- (2) Trent sends both Bob and Carol's signed keys.
$S_T(B,K_B),S_T(C,K_C)$
- (3) Bob sends Carol the session key and timestamp he received from Alice, encrypted with Carol's public key, along with Alice's certificate and Carol's certificate.
$E_C(S_A(K,T_A)),S_A(A,K_A),S_A(C,K_C)$
- (4) Carol decrypts Alice's message with her private key and verifies Alice's signature with her public key. She checks to make sure that the timestamp is still valid.

Carol now knows she is talking to Alice; Bob has successfully fooled her. In fact, Bob can fool everyone on the network until the timestamp expires. This is easy to fix. Add the names inside the encrypted message in step [3]:

$E_B(S_A(A,B,K_A)),S_A(A,K_A),S_A(B,K_B)$

Now Bob can't replay the old message to Carol, because it is meant for communication between Alice and Bob.

### Woo-Lam

This protocol also uses public-key cryptography [1610,1611]:

- (1) Alice sends a message to Trent with her identity and Bob's identity:
$A,B$
- (2) Trent sends Bob's public key, $K_B$, signed with Trent's private key, $T$.
$S_T(K_B)$
- (3) Alice verifies Trent's signature. Then she sends Bob her name and a random number, encrypted with Bob's public key.
$E_{K_B}(A,R_A)$
- (4) Bob sends Trent Alice's name, and Alice's random number encrypted with Trent's public key, $K_T$.
$A,B,E_{K_T}(A,R_A)$
- (5) Trent sends Bob's public key, $K_A$, signed with Trent's private key. He also sends Alice's random number, a random session, Alice's name, and Bob's name, all signed with Trent's private key and encrypted with Bob's public key.
$S_T(K_A),E_{K_B}S_T(R_A,K,B)$
- (6) Bob verifies Trent's signatures. Then he sends Trent's message from step (5) and a new random number—all encrypted in Alice's public key.
$E_{K_A}(S_T(R_A,K,B),R_B)$
- (7) Alice verifies Trent's signature and her random number. Then she sends Bob the second random number, encrypted in the session key.
$E_{K_B}(R_B)$
- (8) Bob decrypts his random number and verifies that it is unchanged.

### Other Protocols

There are many protocols in the literature. The X509 protocols are discussed in Section 24.9, KryptoKnight is discussed in Section 24.6, and Encrypted Key Exchange is discussed in Section 22.5.

Another new public-key protocol is Kuperee [694]. And work is being done on protocols that use beacons, a trusted node on a network that continuously broadcasts authenticated nonces [783].

### Lessons Learned

There are some important lessons in the previous protocols, both which have been broken and those which have not:

- Many protocols failed because the designers tried to be too clever. They optimized their protocols by leaving out pieces: names, random numbers, and so on. The remedy is to make everything perfect [43,44].
- Trying to optimize is an absolute pit and pays whole lot on the assumptions you make. For example: if you have authenticated time, you can do a whole lot of things you can't do if you don't.

## 3.4 Formal Analysis

- The protocol of choice depends on the underlying communications architecture. Do you want to minimize the size of messages or the number of messages? Can all parties talk with each other or can only a few of them?

It's questions like that led to the development of formal methods for analyzing protocols.

### 3.4 FORMAL ANALYSIS OF AUTHENTICATION AND KEY-CHANGE PROTOCOLS

The problem of establishing secure session keys between pairs of computers (and people) on a network is so fundamental that it has led to a great deal of research. Some of the research focused on the development of protocols like the ones discussed in Sections 3.1, 3.2, and 3.3. This, in turn, has led to a greater and more interesting problem: the formal analysis of authentication and key-exchange protocols. People have found flaws in securing protocols years after they were proposed, and researchers wanted tools that could provide a protocol's security from the start. Although much of this work can apply to general cryptographic protocols, the emphasis in research is almost exclusively on authentication and key exchange. There are four basic approaches to the analysis of cryptographic protocols [1045]:

- 1. Model and verify the protocol using specification languages and verification tools not specifically designed for the analysis of cryptographic protocols.
- 2. Develop expert systems that a protocol designer can use to develop and investigate different scenarios.
- 3. Model the requirements of a protocol using logic for the analysis of knowledge and belief.
- 4. Develop a formal method based on the algebraic term-rewriting properties of cryptographic systems.

A discussion on these four approaches and the research surrounding them is well beyond the scope of this book. See [104,1355] for a good introduction to the topic, I am only going to touch on the major contributions to the field.

The first approach treats a cryptographic protocol as any other computer program and attempts to prove correctness. Some researchers represent a protocol as a finite-machine [1449,1565], and others use extensions of first-order predicate calculus [822], and still use specification languages to analyze protocols [1566]. However, proving correctness is not the same as proving security and this approach fails to detect many flawed protocols. Thus, most of the work in this area has been redirected as this approach gained popularity.

The second approach uses expert systems to determine if a protocol can reach an undesirable state (the leaking of a key, for example). While this approach identifies flaws, it never guarantees security nor provides techniques for developing attacks. It is good at determining whether a protocol contains a given flaw, but is unlikely to discover unknown flaws. Examples of this approach can be found in [987,1521]; [1092] discusses a rule-based system developed by the U.S. military, called the Interrogator.

The third approach is by far the most popular, was pioneered by Michael Burrows, Martin Abadi, and Roger Needham. They developed a formal logic model for the analysis of knowledge and belief, called BAN logic [283,284]. BAN logic is the most widely used for analyzing authentication protocols. It assumes that authentication is a function of integrity and freshness, and uses logical rules to trace back through the protocol. Although many variants and extensions have been proposed, protocol designers still refer back to the original work.

BAN logic doesn't provide a proof of security; it can only reason about authentication. Its simple, straightforward logic is easy to apply and still useful for detecting flaws. Some of the statements in BAN logic include:

> Alice X. (Alice acts as X is true).
> Alice sees. (Someone sent a message containing X to Alice, who can read and repeat X--possibly after decrypting it).
> Alice said X. (At time, Alice sent a message that includes the statement X. It is not known how long the message was sent or even that it was during the current run of the protocol. It is known Alice believed X when she said it.)
> X is fresh. (X has not sent in a message at any time before the current run of the protocol.)

And so, BAN logic also provides rules for reasoning about belief in a protocol. These rules can be applied to the logical statements about the protocol to prove things or answer questions about the protocol. One example is the message-meaning rule:

If Alice believes that Alice and Bob share a secret key, K, and Alice sees X, encrypted under K, and Alice did not encrypt X under K, THEN Alice believes that Bob once said X.

Another is the nonce-verification rule:

If Alice believes that X could have been sent recently and Bob once said X, THEN Alice believes Bob believes X.

There are four steps in BAN analysis:

- (1) Convert the protocol into idealized form, using the statements previously described.
- (2) Add all assumptions about the initial state of the protocol.
