This is the easiest mode to work with. If you don't have to encrypt a file linearly, you can encrypt the blocks in the middle first, the blocks at the end, and finally the blocks in the beginning. This is important for files that are accessed randomly, like a database. If a database is encrypted with ECB mode, then any record can be deleted, edited, or decrypted independently of any other record—assuming that a record consists of a discrete number of encryption blocks. And processing is parallizable; if you multiple encryption or decrypt blocks without regard for each other.

The problem with ECB mode is if a cryptanalyst has the plaintext and ciphertext for several messages, he can start to compile a code book without knowing the key. In real-world situations, fragments of messages tend to repeat. Different messages may have sequences in common. Computer-generated messages, like electronic mail, have regular structures. Messages may be highly redundant or have long strings of zeros or spaces.

If a cryptanalyst learns that the plaintext block "5e8bc5" encrypts the ciphertext block "7ea59d4", he can immediately decrypt ciphertext whenever it appears in another message. If the encrypted messages have a lot of redundancies, and these tend to up in the same places in different messages, a cryptanalyst can get a lot of information. Statistical attacks on the underlying plaintext, irrespective of the strength of the block cipher.

This vulnerability is greatest at the beginning and end of messages, where predefined headers and footers contain information about the sender, date, and so on. This problem is called stereotyped beginnings and stereotyped endings.

On the other side, there is no security in encrypting multiple messages with the same key. In fact, each block can be looked at as a separate message encrypted with the same key.
