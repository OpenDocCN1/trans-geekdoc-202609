# 8.5 Using Keys

# Key-error Detection during Decryption

Sometimes the receiver wants to check if a particular key has is the correct symmetric decryption key. If the plaintext message is something like ASCII, he can try to decrypt and read the message. If the plaintext is random, there are other tricks.

The naive approach is to use a verification block: a known header to the plain-text message before encryption. At the receiving end, Bob decrypts the header and verifies it is correct. This works, and it gives Eve a known plaintext to crystallize the system. It also makes against against short ciphers like DES and all exportable ciphers. Precalculate the checksum once for each key, then use that checksum to determine the key in any message you intercept after that. This is a feature of any checksum that doesn't include random or at least data in each checksum. It's very similar in concept to using salt when generating keys from passrases.

Here's a better way to do this [821]:

+   1. Generate an IV [ not one used for the message).
2. Use that IV to generate a large block of bits: say, 512.
3. Hash the result.
4. Use the same fixed bits of the hash, say 32, for the checksum.

This gives Eve some information, but very little. If she tries to use the low 32 bits of the final hash value to mount a brute-force attack, she has to do multiple encryptions plus a per candidate key, brute-force of the key itself would be quicker. She also gets no known-plaintext values to try out, and even if she manages to choose our value for us, never gets a chosen-plaintext out of us, since it goes through the hash function before she sees it.

# 8.5 USING KEYS

Software encryption is scary. Gone are the days of simple microcomputers under the control of single programs. Now there's Macintosh System 7, Windows NT, and UNIX. You can't tell when the operating system will suspend the encryption application in progress, write everything to disk, and take some of pressing task. When the operating system finally gets back to encrypting whatever is encrypted, everything will look just fine. No one will realize that the operating system wrote the encryption application to disk, and that it wrote the key with it. The key will sit on the disk, unencrypted, until the computer writes or it could be months. It could be never; the key could still be sitting when an adversary goes over the hard with a fine-tooth comb. In a preemptive, multitasking environment, you can set your encryption to a high priority so it will not be interrupted. This would mitigate the risk. Even so, the whole thing is dice at best.
