
## 8.3 Transferring Keys

Another solution to the distribution problem splits the key into several different parts (see Section 3.6) and sends each of these parts over a different channel. One part could be sent over the telephone, by mail, or by overnight delivery service, by carrier pigeon, and so on [see Figure 8.2]. Section 3.6 discusses schemes for splitting a key into several parts. Alice could even use a secret sharing scheme (see Section 3.7), allowing Bob to reconstruct the key if some of the parts are lost in transmission.

Alice sends Bob the key-encryption key, either by a face-to-face meeting or the splitting technique just discussed. Once Alice and Bob have the key-encryption key, Alice can send Bob daily keys over the same communications channel. Alice encrypts each day with the key-encryption key. Since the amount of traffic being encrypted with the key-encryption key is low, it does not have to be changed as often. However, compromise of the key-encryption key could compromise every message encrypted with every key that was encrypted with the key-encryption key; it must be stored securely.

## Key Distribution in Large Networks

Key-encryption keys are shared by pairs of users who work in small networks, but can quickly become cumbersome if the networks become large. Since every pair of users must exchange keys, the total number of exchanges required in an $n$-person network is $n(n-1)/2$.

In a six-person network, 15 exchanges are required. In a 1000-person network, nearly 500,000 exchanges are required. In these cases, creating a central key server (or servers) makes the operation more efficient.

Alternatively, any of the symmetric-cryptography or public-key-cryptography protocols in Section 3.1 provides for secure key distribution.

## 8.4 VERIFYING KEYS

When Bob receives a key, how does he know it is from Alice and not from someone pretending to be Alice? If Alice gives it to him when they are face-to-face, it's easy. If Alice sends her key via a trusted courier, Bob has to trust the courier. If the key is encrypted with a key-encryption key, then Bob has to trust that only Alice has that key. If Alice uses a digital signature protocol to sign the key, Bob has to trust the public-key database when he verifies it. (He also has to trust Alice has kept her key secret.) If a Key Distribution Center [KDC] signs Alice's public key, Bob has to trust that the KDC's public key has not been tampered with.

In the end, one who controls the entire network around Bob can make him whatever he likes. Mallory could send an encrypted and signed message pretending to be from Alice. When Bob tries to access the public-key database to verify Alice's signature, Mallory could substitute his own public key. Mallory could invent his own false key and exchange the real KDC's public key for his own creation. Bob wouldnt not be the winner.

Some people have used this argument to claim that public-key cryptography is useless. The only way for Alice and Bob to ensure that their keys have not been tampered with is to meet face-to-face; public-key cryptography doesn't enhance security at all.

This is naive. It is theoretically true, but reality is far more complicated. Public-key cryptography, with digital signatures and trusted KDCs, makes it much more difficult to substitute one for another. Bob can never be absolutely certain that Mallory is controlling his entire reality, but Bob could be confident that doing so requires more resources than real-world Mallorys have access to.

Bob could verify Alice's key over the phone, where he can hear her voice. Voice recognition is a really good authentication scheme. If it's a public key, he can safely verify it. If it's a secret key, he can use a one-way hash function to verify the key. Both PGP (see Section 24.12) and AT&T TSD (see Section 24.18) use this kind of key verification.

Sometimes it may not be important to verify exactly which public key belongs to whom. It may be necessary to verify that it belongs to the same person to whom it belonged last year. If someone sends a signed withdrawal message to a bank, the bank does not have to be concerned with who withdraws the money, only it is the same person who deposited the money in the first place.

## Error Detection during Key Transmission

Sometimes keys get garbled in transmission. Since a garbled key can mean megabytes of decryptable ciphertext, this is a problem. All keys must be transmitted with some kind of error detection and correction bits. These errors in transmission can be easily detected and, if required, the key can be corrected.

One of the widely used methods is to encrypt a constant value with the key, and to send the first 2 to 4 bytes of ciphertext along with the key. At the receiving end, do the same thing. If the encrypted constant matches, then the key has been transmitted without error. The chance of an undetected error ranges from $2^{-26}$ to one in $2^{35}$.

## 8.6 Updating Keys

Imagine an encrypted data link where you want to change keys daily. Sometimes it's a pain to distribute a new key every day. An easier solution is to generate a new key from the old key, which is sometimes called key updating.

All it takes is one-way function. If Alice and Bob share the same key and both operate on it the same one-way function, they will get the result. Then they can take the bits they need from the results to create the new key.

Key updating works, but remember that the key is only as secure as the old key. If Eve managed to get her hands on the old key, she can perform the key updating function herself. However, if Eve doesn' have the old key and is trying a ciphertext-only attack on the encrypted traffic, this is a good way for Alice and Bob to protect themselves.

## 8.4 VERIFYING KEYS

When Bob receives a key, how does he know it is from Alice and not from someone pretending to be Alice? If Alice gives it to him when they are face-to-face, it's easy. If Alice sends her key via a trusted courier, Bob has to trust the courier. If the key is encrypted with a key-encryption key, then Bob has to trust that only Alice has that key. If Alice uses a digital signature protocol to sign the key, Bob has to trust the public-key database when he verifies it. (He also has to trust Alice has kept her key secret.) If a Key Distribution Center [KDC] signs Alice's public key, Bob has to trust that the KDC's public key has not been tampered with.

In the end, one who controls the entire network around Bob can make him whatever he likes. Mallory could send an encrypted and signed message pretending to be from Alice. When Bob tries to access the public-key database to verify Alice's signature, Mallory could substitute his own public key. Mallory could invent his own false key and exchange the real KDC's public key for his own creation. Bob wouldnt not be the winner.

Some people have used this argument to claim that public-key cryptography is useless. The only way for Alice and Bob to ensure that their keys have not been tampered with is to meet face-to-face; public-key cryptography doesn't enhance security at all.

This is naive. It is theoretically true, but reality is far more complicated. Public-key cryptography, with digital signatures and trusted KDCs, makes it much more difficult to substitute one for another. Bob can never be absolutely certain that Mallory is controlling his entire reality, but Bob could be confident that doing so requires more resources than real-world Mallorys have access to.

Bob could verify Alice's key over the phone, where he can hear her voice. Voice recognition is a really good authentication scheme. If it's a public key, he can safely verify it. If it's a secret key, he can use a one-way hash function to verify the key. Both PGP (see Section 24.12) and AT&T TSD (see Section 24.18) use this kind of key verification.

Sometimes it may not be important to verify exactly which public key belongs to whom. It may be necessary to verify that it belongs to the same person to whom it belonged last year. If someone sends a signed withdrawal message to a bank, the bank does not have to be concerned with who withdraws the money, only it is the same person who deposited the money in the first place.

One of the widely used methods is to encrypt a constant value with the key, and to send the first 2 to 4 bytes of ciphertext along with the key. At the receiving end, do the same thing. If the encrypted constant matches, then the key has been transmitted without error. The chance of an undetected error ranges from $2^{-26}$ to one in $2^{35}$.

## 8.6 Updating Keys

Imagine an encrypted data link where you want to change keys daily. Sometimes it's a pain to distribute a new key every day. An easier solution is to generate a new key from the old key, which is sometimes called key updating.

All it takes is one-way function. If Alice and Bob share the same key and both operate on it the same one-way function, they will get the result. Then they can take the bits they need from the results to create the new key.

Key updating works, but remember that the key is only as secure as the old key. If Eve managed to get her hands on the old key, she can perform the key updating function herself. However, if Eve doesn' have the old key and is trying a ciphertext-only attack on the encrypted traffic, this is a good way for Alice and Bob to protect themselves.

## 8.3 Transferring Keys

Another solution to the distribution problem splits the key into several different parts (see Section 3.6) and sends each of these parts over a different channel. One part could be sent over the telephone, by mail, or by overnight delivery service, by carrier pigeon, and so on [see Figure 8.2]. Since an adversary could collect all of the parts and still have no idea what the key is, this method will work in all but extreme cases. Section 3.6 discusses schemes for splitting a key into several parts. Alice could even use a secret sharing scheme (see Section 3.7), allowing Bob to reconstruct the key if some of the parts are lost in transmission.

Alice sends Bob the key-encryption key, either by a face-to-face meeting or the splitting technique just discussed. Once Alice and Bob have the key-encryption key, Alice can send Bob daily keys over the same communications channel. Alice encrypts each day with the key-encryption key. Since the amount of traffic being encrypted with the key-encryption key is low, it does not have to be changed as often. However, compromise of the key-encryption key could compromise every message encrypted with every key that was encrypted with the key-encryption key; it must be stored securely.

## Key Distribution in Large Networks

Key-encryption keys are shared by pairs of users who work in small networks, but can quickly become cumbersome if the networks become large. Since every pair of users must exchange keys, the total number of exchanges required in an $n$-person network is $n(n-1)/2$.

In a six-person network, 15 exchanges are required. In a 1000-person network, nearly 500,000 exchanges are required. In these cases, creating a central key server (or servers) makes the operation more efficient.

Alternatively, any of the symmetric-cryptography or public-key-cryptography protocols in Section 3.1 provides for secure key distribution.

## 8.4 VERIFYING KEYS

When Bob receives a key, how does he know it is from Alice and not from someone pretending to be Alice? If Alice gives it to him when they are face-to-face, it's easy. If Alice sends her key via a trusted courier, Bob has to trust the courier. If the key is encrypted with a key-encryption key, then Bob has to trust that only Alice has that key. If Alice uses a digital signature protocol to sign the key, Bob has to trust the public-key database when he verifies it. (He also has to trust Alice has kept her key secret.) If a Key Distribution Center [KDC] signs Alice's public key, Bob has to trust that the KDC's public key has not been tampered with.

In the end, one who controls the entire network around Bob can make him whatever he likes. Mallory could send an encrypted and signed message pretending to be from Alice. When Bob tries to access the public-key database to verify Alice's signature, Mallory could substitute his own public key. Mallory could invent his own false key and exchange the real KDC's public key for his own creation. Bob wouldn' not be the winner.

Some people have used this argument to claim that public-key cryptography is useless. The only way for Alice and Bob to ensure that their keys have not been tampered with is to meet face-to-face; public-key cryptography doesn't enhance security at all.

This is naive. It is theoretically true, but reality is far more complicated. Public-key cryptography, with digital signatures and trusted KDCs, makes it much more difficult to substitute one for another. Bob can never be absolutely certain that Mallory is controlling his entire reality, but Bob could be confident that doing so requires more resources than real-world Mallorys have access to.

Bob could verify Alice's key over the phone, where he can hear her voice. Voice recognition is a really good authentication scheme. If it's a public key, he can safely verify it. If it's a secret key, he can use a one-way hash function to verify the key. Both PGP (see Section 24.12) and AT&T TSD (see Section 24.18) use this kind of key verification.

Sometimes it may not be important to verify exactly which public key belongs to whom. It may be necessary to verify that it belongs to the same person to whom it belonged last year. If someone sends a signed withdrawal message to a bank, the bank does not have to be concerned with who withdraws the money, only it is the same person who deposited the money in the first place.

## Error Detection during Key Transmission

Sometimes keys get garbled in transmission. Since a garbled key can mean megabytes of decryptable ciphertext, this is a problem. All keys must be transmitted with some kind of error detection and correction bits. These errors in transmission can be easily detected and, if required, the key can be corrected.

One of the widely used methods is to encrypt a constant value with the key, and to send the first 2 to 4 bytes of ciphertext along with the key. At the receiving end, do the same thing. If the encrypted constant matches, then the key has been transmitted without error. The chance of an undetected error ranges from $2^{-26}$ to one in $2^{35}$.
