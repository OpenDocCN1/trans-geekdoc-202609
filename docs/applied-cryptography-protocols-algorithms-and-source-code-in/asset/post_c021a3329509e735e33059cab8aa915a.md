## Foiling the Resend Attack

The attack just described works because the encryption operation is the same as the signature-verification operation and the decryption operation is the same as the signature operation. A secure protocol would use a slightly different operation for encryption and digital signatures. Using different keys for each operation solves the problem, as using different algorithms for each operation; as timestamps, which make the incoming message and the outgoing message different; as digital signatures are secure with one-way hash functions (Section 2.6).

In general, the following protocol is secure as the public-key algorithm used:

- (1) Alice signs a message.
- (2) Alice encrypts the message and signature with Bob's public key (using a different encryption algorithm than for the signature) and sends it to Bob.
- (3) Bob decrypts the message with his private key.
- (4) Bob verifies Alice's signature.

## Attacks against Public-Key Cryptography

In these public-key cryptography protocols, I glossed over how Alice gets Bob's public key. Section 3.1 discusses this in detail, but it is worth mentioning here.

The easiest way to get someone's public key is from a secure database where where that database be public, so that anyone can get Alice's public key. The database also has to be protected from any access except Trent; otherwise Mallory could substitute any public key for Bob's. After he did, Bob couldn't read messages addressed to him, but Mallory could.

Even if the public keys are stored in a secure database, Mallory could still substitute one for another during transmission. To prevent this, Trent can sign each public key with his own private key. Trent, used in this manner, is known as a Key Certification Authority or Key Distribution Center (KDC). In practical implementations, the KDC signs a compound message consisting of the user's name, public key, and any other important information about the user. This signed compound message is stored in the KDC's database. When Alice gets Bob's key, she verifies the KDC's signature to assure herself of the key's validity.

In the final analysis, this is not impossible for Mallory, Alice still has the KDC's public key stored somewhere. ## 2.8 RANDOM AND PSEUDO-RANDOM-SEQUENCE GENERATION

Why bother with random-number generation in a book on cryptography? There's already a random-number generator built into most compiler, a mere function call. Why not use that? Unfortunately, those random-number generators are almost definitely not secure for cryptography, and probably not even random. Most of them are embarrassingly bad.

Random-number generators are not random because need few random numbers that hardly notice. However, cryptography is extremely sensitive to the properties of random-number generators. Use a poor random-number generator and you start getting weird correlations and string results [1231,1238]. If you are depending on your random-number generator for sequence, weird correlations and strange results are the last things you want.

The problem is that a random-number generator doesn't produce a random sequence. It probably doesn't produce anything that looks remotely like a random sequence. Of course is impossible to produce truly random on a computer. Donald Knight quotes von Neumann as: "Anyone who considers arithmetic methods of producing random digits is, of course, in a state of sin" [863]. Computers are deterministic: State goes in one, completely dictable operations occur inside, and different stuff comes out the end part. The same stuff in two separate occasions and the same stuff comes out both times. The same stuff into two identical computers, and the same stuff comes out of them. A computer can only be in a finite number of states (a large finite number, but a finite number nonetheless), and the stuff that will always be a deterministic function of the state that went in and the computer's current state. It means that any random-number generator on a computer (at least, in a finite-state machine) is, by definition, periodic. And if it is periodic, by definition, dictable. And if dictable, it can't be random. A true random-number generator requires some random input, a computer can't provide that.

## Cryptographically Secure Pseudo-Random Sequences

Cryptographic applications demand much more of a pseudo-random-sequence generator than most other applications. Cryptographic randomness doesn't mean just statistical randomness, although that is part of it. For a sequence to be cryptographically secure pseudo-random, it must also have this property:

- 2. It is unpredictable. It must be computationally infeasible to predict the next random bit will be, given complete knowledge of the algorithm or hardware generating the sequence and all of the previous bits in the stream.

Cryptographically secure pseudo-random sequences should not be compressible... unless you know the key. The key is the seed used to set the initial state of the generator.

Like any cryptographic algorithm, cryptographically secure pseudo-random sequence generators are subject to attack. Just as it is possible to break an encryption, it is possible to break a cryptographically secure pseudo-random sequence generator. Making generators resistant to attack is what cryptography is all about.
