## 17.1 RC4

RC4 is a variable-key-size cipher developed in 1987 by Ron Rivest for RSA Data Security, Inc. For seven years it was proprietary, and details of the algorithm were only available after signing a nondisclosure agreement.

In September, 1994 someone posted source code to the CypherP mailing list—anonymously. It quickly spread to the Usenet newsgroup sci.crypt, and via the Internet to find sites around legal copies of RC4 confirmed compatibility. RSA Data Security, Inc. tried to put the genie back into the bottle, claiming that it was still a trade secret even though it was public, it was too late. It has since been discussed and dissected on Usenet, distributed at conferences, and taught in cryptography courses.

RC4 is simple to describe. The algorithm works in OFB: The keystream is independent of plaintext. It has a $8 \times 8$ box: $S_0, S_1, \dots, S_{255}$. The entries are a permutation of the numbers 0 through 255, and the permutation is a function of the variable-length key $K$. It has two counters, $i$ and $j$, initialized to zero. To generate a random byte, by doing the:

```
$i = (i + 1) \bmod 256$
$j = (j + S_i) \bmod 256$
swap $S_i$ and $S_j$
$t = (S_i + S_j) \bmod 256$
$K = S_t$
```

The byte $K$ is XORed with the plaintext to produce ciphertext or decrypted plaintext. Encryption is fast—about 10 times faster than DES. Initializing the S-box is easy. First it linearly: $S_0 = 0, S_1 = 1, \dots, S_{255} = 255$. Then fill another 256-byte array with the key, repeating the key as necessary to fill the entire array: $K_0, K_1, \dots, K_{255}$. Set the index $j$ to zero. Then:

for i = 0 to 255:
$j = [j + S_i + K_j] \bmod 256$
swap $S_i$ and $S_j$

And that RSA DSI claims that the algorithm is immune to differential and linear cryptanalysis, doesn't seem to have any small cycles, and is highly non-linear. (There are no more public results. RC4 can be in about $2^{1700} [256! \times 256^2]$ possible states: an enormous number.) The S-box slowly evolves with $i$: ensures that every element changes and ensures the elements change randomly. The algorithm is simple enough that most programmers can quickly code it from memory.

It should be possible to generalize this to larger S-boxes and word sizes. The previous version is 8-bit RC4. There's no reason why you can't define 16-bit RC4 with a $16 \times 16$ S-box (10KB of memory) and a 16-bit word. You'd have to iterate the initial setup a lot times—65536—but the resulting algorithm should be faster.

RC4 has special export status if its key length is 40 bits or under (see Section 3.8). This special status has nothing to do with the secrecy of the algorithm, although RSA Data Security, Inc. has fought for years that it does. The name is trademarked, so anyone who writes his own code can call it. Various internal details by RSA Data Security, Inc. have not been made public [337].

So, what's the deal with RC4? It is no longer a secret, so presumably anyone can use it. However, RSA Data Security, Inc. will almost certainly sue anyone uses RC4 in a commercial product. They won't win, but they will certainly make it cheaper than to license. RC4 is in dozens of cryptography products, including Lotus Notes, Apple Computer's OS, and Oracle SQL. It is part of Cellular specification [71].

## 17.2 SEAL

SEAL is a software-efficient stream cipher designed at IBM by Phil Rogaway and Don Coppersmith [4]. To run it well needs 32-bit registers and a cache of a few kilobytes. Using a relatively slow operation, SEAL preprocesses every key into a set of tables. These tables are used to speed up encryption and decryption.

### Pseudo-random Function Family

One feature of SEAL is that it isn't really a stream cipher: it is a pseudo-random function family. Given a 128-bit key $k$, and 32-bit $n$, SEAL stretches $n$ into an $L$-bit string can take any value less than 64. SEAL ensures the property that if $k$ is selected at random, $k[n]$ should be computationally indistinguishable from a random $L$-bit function of $n$.

The practical effect of SEAL being a pseudo-random function is that it is useful in applications where traditional stream ciphers are not. With most stream ciphers you generate a sequence of bits in one direction: knowing the key and position $i$, the only way to determine the $i$th bit is to generate all the bits until the $n$th one. A pseudo-random function is different: you get easy access at any desired position in the hard drive. This is very useful. Imagine you need to encrypt and decrypt a 512-byte vector. With a pseudo-random function like SEAL, you can encrypt the contents of $n$ XORing it with $k[n]$. It is as though the entire disk is XORed with a long pseudo-random string, where any piece of that long string can be computed without any.

A pseudo-random function also simplifies the synchronization problem encountered with stream ciphers. Suppose you encrypted messages over a channel that drops messages. With a pseudo-random function family, you can encrypt the $k$th message you transmit, $x_m$ as together with the XOR of $x_k$ and $k[n]$. The receiver doesn't need to store any state to recover $x_m$, nor does he need to worry about messages affecting the decryption process.

### Description of SEAL

The inner loop of SEAL is shown by Figure 17.1. Three key-derived tables, called R, S, and T drive the algorithm. The preprocessing steps map the key $k$ to these tables using a procedure based on SHA (Section 18.7). The 2KB table T is a $9 \times 32$ S-box.

SEAL uses four 32-bit registers, A, B, C and D, whose initial values are determined by $n$ and the key-derived tables R and T. These registers modified over several iterations, each one involving 8 rounds. In each round 9 bits of a first register (either A, B, C or D) are indexed into table T. The value retrieved from T is added to or XORed with the second register: another one of A, B, C or D. The first register is then circularly shifted by nine positions. In some rounds the second register is further modified by adding or XORing it with the [now shifted] first register. After 8 rounds, A, B, C and D are added to the keystream, each masked firstly by XORing it with a certain word from S. The iteration is completed by adding A and C conditional values depend on $n, n_j, n_b, n_{aj}$ exactly which one depends on the parity of the iteration number.

The important ideas in this design seem to:

1. Use a large, secret, key-derived S and T tables.
2. Alternate arithmetic operations which don't commute (addition and XOR).
3. Use an internal state maintained by the cipher which is not directly manifest in the data stream [the $n$ values which modify A and C at the end of each iteration].
4. Vary the round function according to the round number, and vary the iteration function according to the iteration number.

SEAL requires about five elementary operations to encrypt each byte of text. It runs at 58 megabits per second on a 50 megahertz 486 machine. This is probably the fastest software algorithm in the book. On the other hand, SEAL must preprocess its key into internal tables. These tables total roughly 3 kilobytes in size, and their calculation takes about 200 SHA computations. Thus, SEAL is not appropriate to use where you don't have the time to perform the key setup or you don't have the memory to store the tables.

## Security of SEAL

SEAL is a new algorithm and has yet to be subjected to any published cryptanalysis. This suggests caution. However, SEAL seems to be well thought through. Its peculiarities, in the end, make a good deal of sense. And Don Coppersmith is generally regarded as the world's cleverest cryptanalyst.
