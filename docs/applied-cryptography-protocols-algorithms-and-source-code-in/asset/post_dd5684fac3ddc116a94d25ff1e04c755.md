## Basic Protocols

Others try to show that BAN logic can deduce characteristics about protocols that are obviously false [111]—[285, 1509] for a rebuttal—and that BAN logic only deals with trust and not security [1509]. More debate is in [1488, 706, 1002].

Despite these criticisms, BAN logic has been a success. It has flaws in several protocols, including Neham-Schroeder and an early draft of CCIT X.500 protocol [303]. It has uncovered redundancies in many protocols, including Yamaha, Neham-Schroeder, and Kerberos. Many published papers use BAN logic to make claims about their protocol's security [40, 1162, 73].

Other systems have been published, some designed as extensions to BAN logic [645, 586, 1556, 828] and others use BAN to correct perceived weaknesses [1488, 1002]. The most successful of these is GNY [645]; although it has some shortcomings [40]. Probabilistic beliefs are added to BAN logic, with mixed success, coming [292, 474]. Other formal logics are added [156, 798, 288], [1514] attempts to combine the features of several logics. [124, 1511] present logics where beliefs can change over time.

The fourth approach to the analysis of cryptographic protocols models the protocol as an algebraic system, expresses the state of the participants' knowledge about the protocol, and analyzes the attainability of certain states. This approach has not received much attention as formal logic, but it is changing. It was first used by Michael Merritt [1076], who showed that an algebraic model can be used to analyze cryptographic protocols. Other approaches are in [473, 1508, 1531, 1532, 1510, 162].

The Navy Research Laboratory (NRL) Protocol Analyzer is probably the most successful application of these techniques [1512, 823, 1046, 1513]; it has been used to discover both new and known facts in a variety of protocols [1044, 1045, 1047]. The Protocol Analyzer defines the following:

- Accept (Bob, Alice, N). Bob accepts the message from Alice during Bob's local N.
- Learn (Eve, M). Eve learns M.
- Send (Alice, Bob, Q). Alice sends M to Bob in response to Q.
- Request (Bob, Alice, N). Bob sends Q to Alice during Bob's local N.

From these actions, requirements can be specified. For example:

- If Bob accepted message M from Alice at some point in the past, Eve did not learn M.
- If Bob accepted message M from Alice in Bob's local N, Alice sent M to Bob as a response to a query in Bob's local N.

Using the NRL Protocol Analyzer, a protocol must be specified with the previous constructs. Then, there are four phases of analysis: defining transition rules for honest participants, describing dishonest participants, describing building blocks of the protocol, and describing reduction rules. Point of all this is to show that a given protocol meets its requirements. While the work in formal methods involves applying methods to existing protocols, there is some push towards using formal methods to design the protocols in the first place. The Protocol Analyzer also opts to design [1512, 222, 222]. The application of formal methods to cryptographic protocols is still a fairly new idea and it's hard to figure out it is headed. At this point, the weakest links seem to the formal process.

Public-key cryptography uses two keys. A message encrypted with one key can be decrypted with the other. Usually one key is private and the other is public. However, let's assume that Alice has one key and Bob has the other. Now Alice can encrypt a message so only Bob can decrypt it, and Bob can encrypt a message so only Alice can read. This concept was generalized by Boyd [217]. Imagine a variant of public-key cryptography with three keys: $K_A, K_B$, and $K_C$, distributed as shown in Table 3.2.

### TABLE 3.2 Three-Key Distribution

| | Key |
| :--- | :--- |
| Alice | $K_A$ |
| Bob | $K_B$ |
| Carol | $K_C$ |
| Dave | $K_A$ and $K_B$ |
| Ellen | $K_B$ and $K_C$ |
| Frank | $K_C$ and $K_A$ |

Similarly, Ellen can encrypt a message so Dave can read it. Dave can encrypt a message with $K_A$ so that Ellen can read it, with $K_C$ so that Frank can read it, or with both $K_A$ and $K_B$ so that Carol can read it. The possible combinations are summarized in Table 3.3, there are no others. This can be extended to $n$ keys. If a subset of keys is used to encrypt the message, then the other keys are required to decrypt the message.

## 3.6 SECRET SPLITTING

Imagine you've invented a new, extra gooey, extra sauce, cream filling or a burger sauce that is even more tasteless than your competitors'. This is important, you have to keep secret. You could tell only your employees the exact mixture of ingredients, but what if one of them defects to the competition? There goes the secret, and before every grease palace on the block will be making burgers with sauce as tasteless as yours.

This calls for secret splitting. There are ways to take a message and divide it up into pieces [551]. Each piece by itself means nothing, but put them together and the message appears. If the message is the recipe and each employee has a piece, then only they can make the sauce. If one employee resigns with his piece, it is useless by itself.

The simplest sharing scheme splits a message between two people. Here's a protocol in which Trent can split a message between Alice and Bob:

- (1) Trent generates a random-bit string, R, the same length as the message.
- (2) Trent XORs M with R to generate S: M @ R = S
- (3) Trent gives R to Alice and S to Bob.

To reconstruct the message, Alice and Bob have only one step to do:

- (4) Alice and Bob XOR their pieces to reconstruct the message: R @ S = M

This technique, if done properly, is absolutely secure. Each piece, by itself, is absolutely worthless. Essentially, Trent is encrypting the message with a one-time pad and giving the ciphertext to one person and the pad to the other person.

## Broadcasting a Message

Imagine that you have 100 operatives out in the field. You can be able to send messages to subsets of them, but you can either encrypt the message separately for each person or give out keys for every possible combination of people. The first option requires a lot of messages; the second requires a lot of keys. Multiple-key cryptography is much easier. We'll use Alice, Bob, and Carol. You give Alice $K_A$ and $K_B$, Bob $K_A$ and $K_C$, and Carol $K_B$ and $K_C$. Now you can talk to any subset of them. If you want to send a message so only Alice can read it, encrypt it with $K_C$. When Alice receives the message, she decrypts with $K_A$ and $K_B$. If you want to send a message so only Bob can read it, encrypt it with $K_A$ and $K_C$ so that Alice and Bob can both read it, encrypt it with $K_A$ and $K_C$ and so on.

This might not be exciting, but with 100 operatives it is efficient. Individual messages share a shared key with each operative (100 keys total) and each message. Keys for every possible subset means $2^{100}-2$ different keys [messages to all operatives and no operatives excluded]. This scheme needs only one encrypted message and 100 different keys. The drawback of this scheme is that whichever subset of operatives can read the message, each would have to try every combination of keys looking for the correct one. Even just the names of the intended recipients may be significant. At least for the straightforward implementation of this, everyone gets a really large amount of key data.

There are other techniques for message broadcasting, some of which avoid the previous problem. These are discussed in Section 2.7.
