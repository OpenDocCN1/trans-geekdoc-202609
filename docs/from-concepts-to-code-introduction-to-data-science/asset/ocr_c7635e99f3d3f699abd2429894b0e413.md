Given this new structure, there is no duplication of user status. This reduces the chance of data inconsistency. In fact, the first table can be broken down into smaller tables. We won't do this here, but the important point is that each concept should be stored in a separate table. The user's status is a concept, and this data should be stored in one table. Another concept is device, and the unique devices should be stored in another table. In this way, the structure is cleaner and less prone to error.

There is complexity that is required when breaking data into one table per concept, when the required data is spread across multiple tables, the tables need to be joined. If the required data is in three tables A, B, and C, then we need a join between A and B, and a second join between B and C. This is fundamental to relational databases – it is what makes them “relational.” When joins cannot be done, or aren't needed, then a relational database is not the right tool for the job.
