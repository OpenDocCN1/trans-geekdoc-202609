

Pod 资源是 Kubernetes 中最小的可部署单元。Pod 是一组共享卷、环境和上下文的容器的集合。我们可能不需要单独部署 Pod；Pod 通常是正在运行的工作负载的一部分。然而，大多数调查都将围绕 Pod 进行，包括描述它、获取其日志或获取关于 Pod 的基本数据。

![](OEBPS/images/Figure-8.5.jpg)

**图 8.5：** 使用宽输出模式获取 pods

描述 Pod：

```
kubectl describe pods/nginx-deployment8-6dcf8bbd4c-459fx
```

描述 Pod 是一个典型命令；它提供了关于 Pod 和 Pod 最近事件的许多详细信息。我们也可以对任何其他资源使用 `describe` 命令，格式如下：

```
kubectl describe <resource-kind>/<resource-name>
```

查看日志：

```
kubectl logs pods/frontend2
```

与 `describe` 命令类似，我们可以对每种资源使用 `logs` 命令，但它的价值较低。

# 工作负载管理

工作负载是在 Kubernetes 上运行的应用程序。工作负载是微服务架构中的一项服务。正如我们已经看到的，部署和管理服务（工作负载）具有挑战性、复杂，且需要大量工作。Kubernetes 通过工作负载资源提供了部署和管理服务的解决方案。在这里，我们将介绍并解释内置的工作负载资源。

# Deployment（部署）

Deployment 是 Kubernetes 中最常见的工作负载。Deployment 用于管理无状态服务。由 Deployment 管理的 Pod 是易失的。当一个 Pod 被终止（无论是由于故障还是发布导致），Deployment 资源会创建另一个具有不同名称的新 Pod。Deployment 使用一种称为 `ReplicaSet` 的资源来管理 Pod。每次我们发布新版本（仅应用新的 YAML），就会创建一个新的 `ReplicaSet` 并替换旧的 `ReplicaSet` 和旧的 Pod。

```
apiVersion: apps/v1
kind: Deployment
metadata:
  name: random-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: random-app
  template:
    metadata:
      labels:
        app: random-app
    spec:
      containers:
        - name: random-container
          image: nginx:latest
          ports:
            - containerPort: 80
```

前面的 YAML 是 Kubernetes 中最小化 Deployment YAML 的示例。

# DaemonSet

DaemonSet 是一种适合在节点上运行 Pod 的工作负载。DaemonSet 的目标是提供与本地节点相关的功能。例如，具有单个副本的 DaemonSet 会在集群中的每个节点上调度一个 Pod。用例可以是存储守护进程、网络相关守护进程、日志聚合器、遥测守护进程等。

# StatefulSet

StatefulSet 是为需要持久状态或唯一标识的 Pod 设计的工作负载资源。与 Pod 可互换且短暂的 Deployment 资源不同，StatefulSet 确保 Pod 在终止后以相同的名称和状态被重新创建。StatefulSet 提供一致的卷，Pod 可以使用称为 `PV`（PersistentVolume，持久卷）和 `PVC`（PersistentVolumeClaim，持久卷声明）的其他资源挂载该卷。StatefulSet 的用例可以是数据库服务、消息系统等。

# Job

Job 资源允许我们定义一个可以运行直到完成的任务。就这么简单。Job 资源可用于数据处理等场景。

# CronJob

它是一种运行 Job 资源的方式，但用 cron 调度器将其包装起来。CronJob 资源的用例可以是维护任务、计划备份、批处理等。

```
apiVersion: batch/v1beta1
kind: CronJob
metadata:
  name: random-cronjob
spec:
  schedule: "*/5 * * * *" # Runs every 5 minutes
  jobTemplate:
    spec:
      template:
        metadata:
          labels:
            app: random-cronjob
        spec:
          containers:
            - name: random-container
              image: busybox
              command: ["echo", "Hello from the cronjob!"]
          restartPolicy: OnFailure
```

在前面的 YAML 示例中，我们可以看到 CronJob YAML；请注意，在 CronJob YAML 内部，我们定义了一个 Job YAML 并用调度器将其包装。

# 重要资源

以下资源在使用 Kubernetes 时很常见；作为开发人员，我们可能会遇到它们。

# ConfigMap

ConfigMap 是一种以键值对形式存储非机密数据的资源。Pod 可以通过环境变量、参数或卷来使用 ConfigMap 数据。ConfigMap 帮助我们实现微服务的要素之一：外部配置。可以存储在 ConfigMap 中的数据包括应用属性、连接字符串、环境数据、端点等。

```
apiVersion: v1
kind: ConfigMap
metadata:
  name: random-configmap
data:
  app_name: my-app
  database_url: "mongodb://localhost:27017"
```

前面的 YAML 示例描述了 ConfigMap。

# Secret

Secret 资源就像 ConfigMap 资源一样，但存储的是敏感数据而非非敏感数据。可以存储在 Secret 中的数据包括密码、API 密钥、证书等。

# HPA

HPA 代表 Horizontal Pod Autoscaling（水平 Pod 自动伸缩），是一种用于自动缩放工作负载资源（并非适用于所有工作负载）的资源。水平自动伸缩意味着通过增加或减少副本（Pod）的数量来进行缩放。缩放基于指标（CPU 或内存）及其期望值。在 HPA 配置中，有最小和最大 Pod 数量限制。我们经常将 HPA 用于动态规模且负载偶尔不同的服务。

# Ingress

> “Ingress 将来自集群外部的 HTTP 和 HTTPS 路由暴露给集群内部的服务。流量路由由 Ingress 资源上定义的规则控制。”

在该引语中，术语“`services`”特指名为“`service`”的 Kubernetes 资源。该资源负责 Kubernetes 环境内的网络，不应与服务的广泛概念混淆，特别是在微服务的语境下。

![](OEBPS/images/Figure-8.6.jpg)

**图 8.6：** Kubernetes 中的 Ingress 资源

这是本章提到的最复杂的资源。作为开发人员，我们可能只会在想要添加新路由或更改路由时遇到 Ingress。最后，请注意 Ingress 资源解决了 API 网关（微服务架构中的核心要素）的一些重要关注点，例如负载均衡、安全性和高层路由。

# 就绪和存活探针

在 Kubernetes 中，当所有容器都在运行时，Pod 会接收流量。此外，当 Kubernetes 检测到 Pod 崩溃（由于退出代码或其他故障）时，它会重启该 Pod。这些检测（无论是 Pod 准备好接收流量还是需要重启）都由 Kubernetes 自动解决。然而，在某些场景下，我们作为开发人员希望为 Kubernetes 提供额外信息以执行这些检测。例如，我们可以决定 Pod 在建立与数据库的连接之前无法接收流量。另一个例子是，如果我们发现 Pod 缓存无效，则希望重启该 Pod。执行这种手动检测的方法就是就绪和存活探针。

*   **就绪探针**：指示容器是否准备好接收流量和请求。
*   **存活探针**：指示容器是否正常运行。如果不是，则需要被杀掉并重启。

```
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web-app
  template:
    metadata:
      labels:
        app: web-app
    spec:
      containers:
        - name: web-app-container
          image: nginx:latest
          ports:
            - containerPort: 80
          readinessProbe:
            httpGet:
              path: /healthz
              port: 80
            initialDelaySeconds: 5
            periodSeconds: 10
          livenessProbe:
```
