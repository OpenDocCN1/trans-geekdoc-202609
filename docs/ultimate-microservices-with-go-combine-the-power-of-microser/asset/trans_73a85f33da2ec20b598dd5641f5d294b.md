
让我们强调这样一个事实：Goroutine 泄漏表现为内存泄漏。后台运行的 goroutine 持有变量，导致这些变量无法从内存中释放。检测 goroutine 泄漏主要有两种方法：

*   **性能分析**：我们将在 *[第 10 章，生产环境的下一步](#c10.xhtml)* 中更详细地讨论性能分析。通常，在进行性能分析和代码分析时，我们可以使用 Go 的 `pprof` 或 `gops` 来检查是否有未终止的 goroutine。

*   **测试**：最好但也最费力的方法是编写能够揭示 goroutine 泄漏的单元测试。我们的目标是覆盖所有可能发生 goroutine 泄漏的场景。测试本质上会在测试结束时检查后台是否仍有 goroutine 在运行。Go 允许我们使用 `runtime.NumGoroutine()` 查看后台运行了多少个 goroutine。我们也可以使用外部包，如 `uber-go/goleak`。

# Fan In Fan Out 模式

Fan In Fan Out 是一种流行的模式，它帮助我们将多个来源转换为单个流（fan-in），或将来自单个来源的输入流式传输到多个管道中（fan-out）。在 Go 中，如果我们需要多个函数从同一个通道读取数据直到该通道关闭 —— 即 fan-out。一个函数可以从多个输入（来源）读取数据，直到所有输入通道都关闭 —— 即 fan-in。

# Fan Out

当我们想要将工作分配给一组工作协程，以通过并行利用 CPU 和 I/O 等资源来进行优化时，应使用 fan-out 模式。

```
func generator(numbers []int) <-chan int {
    out := make(chan int)
    go func() {
        for _, num := range numbers {
            out <- num
        }
        close(out)
    }()
    return out
}

func businessLogic(num int) int {
    return num * 2
}

func main() {
    data := []int{1, 2, 3, 4, 5, 6}
    var wg sync.WaitGroup
    ch1 := generator(data[0:3])
    ch2 := generator(data[3:])
    wg.Add(2)
    go func() {
        for num := range ch1 {
            println(businessLogic(num))
        }
        wg.Done()
    }()
    go func() {
        for num := range ch2 {
            println(businessLogic(num))
        }
        wg.Done()
    }()
    wg.Wait()
}
```

在前面的示例中，我们有一个 `data` 变量（来源），但我们想要并行化该数据的处理过程。我们决定将工作分配给两个工作协程。我们做的第一件事是将数据分成两份。然后，我们调用了 `generator` 函数。`generator` 函数的目的是接收输入，将所有输入发送到一个名为 `out` 的通道中，然后返回该通道。在两次调用 `generator` 函数后，我们使用了 `WaitGroup` 来等待所有工作协程完成工作。最后，我们启动了两个 goroutine（工作协程）。每个工作协程执行一些业务逻辑，然后结束。

# Fan In

我们应该使用 fan-in 模式将多个输入（来源）处理汇总到单个函数中。我们将通过将多个通道合并为一个来实现这一点。将多个通道合并为单个通道的过程称为多路复用。只有当所有输入通道都关闭时，单个输出通道才会关闭。我们将通过一个名为 `merge` 的函数来研究多路复用过程。

```
func merge(sourcesCh …<-chan int) <-chan int {
    var wg sync.WaitGroup
    wg.Add(len(sourcesCh))
    out := make(chan int)
    outputFunc := func(sourceCh <-chan int) {
        for num := range sourceCh {
            out <- num
        }
        wg.Done()
    }
    for _, sourceCh := range sourcesCh {
        go outputFunc(sourceCh)
    }
    go func() {
        wg.Wait()
        close(out)
    }()
    return out
}

func generator(numbers []int) <-chan int {
    out := make(chan int)
    go func() {
        for _, num := range numbers {
            out <- num
        }
        close(out)
    }()
    return out
}

func main() {
    data := []int{1, 2, 3, 4, 5, 6}
    ch1 := generator(data[0:3])
    ch2 := generator(data[3:])
    ch := merge(ch1, ch2)
    for num := range ch {
        println(num)
    }
}
```

`generator` 函数与我们在 fan-out 模式示例中看到的相同。我们首先在 `merge` 函数中声明单个输出通道 `out`。其次，我们创建一个 `WaitGroup` 来确定何时所有源通道都已关闭。在它们关闭后，我们将使用 `Wait()` 并关闭输出（`out`）通道。然后，我们创建了一个函数（`outputFunc`），它接收源通道并将该源通道的所有数据发送到输出通道（`out`）。最后，我们遍历所有源通道并启动 goroutine 执行 `outputFunc`。

现在我们在 `main` 函数中拥有了一个单一的通道，可以安全地迭代，直到 `merge` 函数关闭该通道。

# 微服务的核心要素

# 简介

在涵盖了与 Go 编程语言相关的所有基础知识后，我们将把它与微服务架构的核心要素相结合。你可能会问自己，什么是这些“**核心要素**”；微服务架构是一种**方法**，而非终点。因此，核心要素是技术行业的方法论、设计模式和技术。所有这些要素共同构成了一个完整的系统。没有一个配方能告诉我们如何构建出一个架构。存在许多约束、产品需求（可能会牵引出工程需求）和假设 —— 每个系统都有其独特的结构。然而，所有这些系统都有共同的要素。本章介绍这些要素，何时它们会变得有益，它们的优缺点，以及何时使用/避免它们。我们不会深入探讨每一个要素；相反，目标是提供一个框架，概述每个要素的边界。

我们不会涵盖微服务的所有现有要素。相反，我们将介绍主要的要素。以下是本章**不**涵盖的要素：

*   **Saga 模式**：允许我们通过将分布式事务分解为更小、隔离的步骤来管理微服务架构中的分布式事务，每个步骤都有其补偿事务来处理潜在故障。
*   **Aggregator 模式**：从多个服务中聚合数据，以简化其他希望拉取该数据的服务的数据获取。
*   **Decomposition 模式**：帮助我们将单体应用拆解为微服务。
