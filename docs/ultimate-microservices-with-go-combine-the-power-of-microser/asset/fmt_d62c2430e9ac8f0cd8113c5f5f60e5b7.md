
在开发者构建众多服务以组成更大的微服务架构的世界里，他们通常将这些服务打包为称为容器的可交付单元，这导致我们需要管理海量的容器。在支持每位开发者的需求和特定要求的同时，几乎不可能管理和运维如此数量的容器。幸运的是，Google 的一些人预见到了这个问题，并打造了一个单一项目来解决它。这个项目叫做 Kubernetes。

为什么我们要学习 Kubernetes？*“我只需要编写代码，让运维侧（通常是 DevOps）为我完成所有其他工作。”* 这个答案在完美的世界里是可以接受的，但现实并非如此。应用程序与其部署方式之间存在耦合。作为开发者，我们必须确保功能在生产环境中按预期运行。本地环境与生产环境之间存在巨大差异 —— 不同的参数、我们未曾考虑的边缘情况、扩展问题、安全顾虑等。为了缓解这些差异带来的问题，我们作为开发者需要了解 Kubernetes 的基础知识 —— 常见资源、发布流程、故障排查、核心最佳实践、监控等。在本章中，我们将探讨这些主题。

Kubernetes 与微服务架构有什么关系？

简单来说，Kubernetes 解决了微服务架构的许多问题和缺点。例如，在微服务架构中建议使用外部配置。Kubernetes 通过提供 `ConfigMap` 和 `Secret`（存储资源）将数据注入应用容器来解决这个问题。这就是两者结合强大的原因。

另一个例子是，可以使用 `Ingress`（Kubernetes 资源）高效地实现路由能力。

Kubernetes 是一个开源的容器编排系统。该系统由 Google 于 2014 年发明，现由 CNCF（云原生计算基金会）维护。Kubernetes 的简写是 `K8s`（因 K 和 S 之间有 8 个字母）。

# Kubernetes Adoption

如今，Kubernetes 被广泛使用，世界上大多数公司都在使用它。Kubernetes 社区庞大且逐年增长。全球有大量会议的主题仅围绕 Kubernetes。有大量与 Kubernetes 相关的开源项目和工具。

此外，一些公司拥有原生面向 Kubernetes 的产品。使用 Kubernetes 作为部署服务和工作负载的场所已成为行业标准。

![](OEBPS/images/Figure-8.2.jpg)

**Figure 8.2:** Kubernetes Adoption December 2022

Kubernetes 旨在管理容器化的工作负载和服务。此外，其目标是自动化复杂的部署流程。Kubernetes 负责部署过程的多个方面 —— 网络、配置、发布等，也负责管理 —— 存储、安全等。

Kubernetes 在其内部组合了多个工具和项目，并利用它们各自的能力。例如，Kubernetes 使用 Docker 作为容器运行时引擎，并没有自己的容器运行时引擎。Kubernetes 作为一个称为 **cluster** 的单一单元提供。我们可以通过定义期望的资源在该集群中创建资源。我们将使用 YAML 配置想要的期望资源。Kubernetes 将为我们完成所有其他工作，并努力达到我们定义的期望状态。在本章后续内容中，我们将详细阐述与软件工程师相关的不同 Kubernetes 资源。

# Kubernetes Essential Tools

让我们讨论一些 Kubernetes 的必要工具：

## Kind

`Kind` 代表 Kubernetes IN Docker，是一个在 Docker 容器中运行 Kubernetes 集群的工具。它简单直接，通常用于本地或测试环境，因为它轻量且易于使用。其他实现相同功能的工具有 `Minikube` 和 `K3s`。以下是如何使用 `kind` 启动集群：

```
kind create cluster --name example
```

## Kubectl

`Kubectl` 是 Kubernetes OSS 项目的一部分。它是一个 CLI，让我们能轻松与 Kubernetes API 交互。以下是一些 `kubectl` 的常用命令：

获取资源：

```
kubectl get pods
kubectl get nodes --output json
```

![](OEBPS/images/Figure-8.3.jpg)

**Figure 8.3:** kubectl get pods output sample response

第一个示例展示如何以默认命名空间获取集群中所有的 Pod。第二个示例以 JSON 输出格式获取集群中所有的 Node。

创建新资源：

```
kubectl create -f pod.yaml
```

修改/创建资源：

```
kubectl apply -f pod.yaml
```

删除名为 frontend 的 Pod：

```
kubectl delete pods/frontend
```

要查看 `kubectl` 所有的命令，可以运行：

```
kubectl help
kubectl help <command-name>
```

## Kubectx

`Kubectx` 是一个极简的 CLI 工具，帮助我们在集群间切换。当我们使用 `kubectl` 时，它会访问 `~/.kube` 目录中声明的集群 API。通过使用 `kubectx`，它只会将上下文切换到期望的集群。例如：

```
kubectx <cluster-name>
```

# Basic Resources

以下三个资源在 Kubernetes 中被广泛使用。了解它们是什么对于理解 Kubernetes 至关重要。我们将在本章中反复提及它们。

## Node

> “Node 是 Kubernetes 中的工作机器，可以是虚拟机也可以是物理机，取决于集群。每个 Node 由控制平面管理。一个 Node 可以运行多个 Pod，Kubernetes 控制平面会自动处理在集群中的 Node 间调度 Pod。”

这是 Kubernetes 官方文档的引用。这段引用很好地解释了什么是 Node。作为开发者，这已足够，我们不需要操作它们或处理 Node 问题。但请注意，有时我们的应用程序会因 Node 问题而出现故障。至少，我们需要理解问题与 Node 相关，并将其移交给运维人员处理。

## Namespace

Kubernetes 中的 Namespace 是资源间分离和隔离的机制。一些资源可以被命名空间化，一些则不能。每次我们使用 `kubectl get` 获取资源时，除非另行指定，否则它会带来 `default` 命名空间中的所有资源；通过添加 `-A`，我们可以获取所有命名空间中的所有资源。资源的名称和类型在命名空间内必须唯一。要查看哪些资源被命名空间化、哪些没有，可以运行：

```
kubectl api-resources
```

![](OEBPS/images/Figure-8.4.jpg)

**Figure 8.4:** kubectl api-resources output

请注意 “`NAMESPACED`” 列，它给出布尔答案，指示资源类型是否被命名空间化。
