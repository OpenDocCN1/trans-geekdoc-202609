
微服务因其固有设计而具有简单、自包含的特点。遵循适配器设计模式，我们应通过封装 HTTP 客户端来实现服务间通信的封装。关于该设计模式的参考资料请见“参考文献”部分。

在创建与其他服务通信的自定义客户端（封装后的客户端）时，我们应尽量将这些客户端创建为结构体（`struct`）。这些结构体必须实现一个接口。关于在微服务中使用客户端接口，有两种最佳实践：

*   每个服务客户端拥有自己的接口 —— 灵活性更高，但工作量更大。
*   所有服务共享一个通用接口 —— 灵活性较低，但工作量较少。

无论选择哪种方案，引入接口的原因都是为了具备模拟客户端响应的能力，正如前文（“模拟”）所述。我们希望在单个服务的测试范围内模拟客户端响应。

一种更强大的测试类型是服务间测试。虽然它功能更强，但也需要投入大量时间和精力。关于此类服务间测试存在无数理论。核心在于正确设置这些测试的 `Setup` 和 `Teardown`，同时确保测试的可复现性。通常，这类测试在敏捷性方面容易变得不稳定。我们应致力于使用本章介绍的 `Functional Options Pattern`。在最佳场景下，`Setup` 函数应表现为定义多个 `Options`（基本上即配置）。

Go 语言在构建微服务架构时提供了两个相关的高效工具：

*   性能基准测试
*   竞态检测器

# 性能基准测试

基准测试是测试 CLI 的内置选项。它有助于我们测试函数的性能。基准测试是一种强大的方法论，帮助我们实现良好的性能。构建微服务时它甚至更强大，因为我们可以在特定端点变慢时进行调查。让我们看看如何执行基准测试。

```
func Fib(n int) int {
    if n < 2 {
        return n
    }
    return Fib(n-1) + Fib(n-2)
}
```

我们想要查看该函数在大输入下的性能表现。我们需要创建一个以 `Benchmark` 为前缀、签名为 `(b *testing.B)` 的测试函数，测试代码如下：

```
func BenchmarkFib(b *testing.B) {
    for n := 0; n < b.N; n++ {
        Fib(20)
    }
}
```

运行基准测试需使用 Go CLI，命令如下：

`go test -bench=.`

还有多种运行基准测试的配置可供探索。

# 竞态检测器

Go CLI 内置选项可用于检测竞态条件。竞态条件是微服务系统中常见的情况。此外，由于 Go 的并发模型，竞态条件很容易发生。竞态检测器可针对可执行程序或测试运行。让我们看一个针对简单情况运行竞态检测器的示例：

```
func main() {
    i := 0
    go func() {
        i++
    }()
    fmt.Println(i)
}
```

在上述示例中，函数第二行启动了一个 goroutine。当我们打印 `i` 时，可能得到两种结果：`0` 或 `1`。原因是存在竞态条件。我们无法确定 goroutine 是否会在 `Println` 调用前执行完毕，因为它们是并行运行的。运行竞态检测器的命令为：

`go run -race race-detector.go`

我们将得到如下警告：

```
==================
WARNING: DATA RACE
Write at 0x00c00011a028 by goroutine 6:
main.main.func1()
  /Users/nirshtein/Documents/GitHub/Microservices-with-Go/chapter-5/race-detector/race-detector.go:8 +0x3c
Previous read at 0x00c00011a028 by main goroutine:
main.main()
  /Users/nirshtein/Documents/GitHub/Microservices-with-Go/chapter-5/race-detector/race-detector.go:10 +0xa8
Goroutine 6 (running) created at:
main.main()
  /Users/nirshtein/Documents/GitHub/Microservices-with-Go/chapter-5/race-detector/race-detector.go:7 +0x9c

```

该警告明确无误。建议探索 Go 中检测竞态条件的各种配置。后续章节将讨论解决这些竞态条件的技术。
