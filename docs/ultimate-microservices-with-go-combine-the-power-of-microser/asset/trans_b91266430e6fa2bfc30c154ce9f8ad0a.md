
例如，像 `DELETE + URI` 这样的 HTTP 方法用于特定资源（`DELETE` `https://domain:port/api/account/{accountId}`）表示客户端请求 API 删除一个具有 `accountId` Account ID 的账户。开发人员必须能够轻松理解 URI，而无需进一步的文档（至少在大多数情况下）。

*   **自描述消息：** 消息必须包含所需资源上所有的“指令”。服务器应仅从消息中获取所有必要信息，而无需进一步的询问或信息。

*   **超媒体作为应用状态引擎：** 超媒体指电影、图片、文件等所有形式的媒体。当客户端请求 RESTful API 服务器获取资源数据时，它期望获得该资源的数据。部分数据可以是超媒体，REST 旨在提供指向媒体数据的链接，而不是以某种形式直接提供数据本身。

# 无状态

每个从客户端到服务器的请求都是隔离的。服务器绝不能以任何方式依赖之前的请求，也不能依赖服务器的本地动态上下文。客户端请求必须包含执行请求所需的所有必要数据。

# 分层系统

每个从客户端到服务器的请求都会经过各层。客户端与业务逻辑之间从不存在直接连接。这些层可以是认证、缓存、负载均衡等。此约束鼓励我们在客户端和服务器之间创建分离的层，例如微服务架构中那样。客户端对其与服务器之间的不同层是不可知的。大多数层通常存在于 API 网关中——正如上一章所述。

# 可缓存

此约束强制服务器返回一个响应，其中包含指示数据是否来自缓存的数据。

# 按需代码

此约束不常见，也不是必需的。服务器可以通过下载小程序或脚本为客户端提供额外功能。例如，客户端想要将 JPEG 转换为 PDF，因此它向服务器请求一个执行此操作的脚本。客户端获取脚本并执行它。

# 设计 API

在着手编写服务之前，第一步是了解产品需求、工程约束以及可能影响决策的任何因素。定义它将是什么样子、必要的能力是什么、什么不是、以及如何实现它。决定可用资源及其对应的表现形式。

# 能力

RESTful API 的标准能力如下：

*   文档
*   认证和授权（可以在 API 网关层）
*   RBAC（可以在 API 网关层）
*   分页
*   限流
*   缓存
*   过滤
*   排序
*   监控和可观测性
*   功能开关
*   告警
*   错误处理
*   自动生成代码客户端

每个 API 可能不需要所有这些能力，也可能需要此处未提及的其他能力。在构建微服务架构时，每个 API 都希望实现这些能力的一部分或更多，且实现方式可能与其他 API 相同。如果我们为每个 API 重复实现相同的能力（即使我们为每个能力使用一个包），最终将得到大量略有差异的样板代码。

为了解决这个问题，我们需要创建共享基础设施。实现共享基础设施的一种方式是通过共享代码（使用单体仓库时）。在 Go 中，这些代码将位于名为 `pkg` 的目录中。另一种实现共享基础设施的方式是使用 SDK（使用多仓库时）；每个 API 将导入并使用此 SDK 以满足其自身需求。

# 文档：Swagger 和 OpenAPI

构建 API 最关键的部分是记录 API 规范。记录 API 规范的行业标准是使用 Swagger 和 OpenAPI。

OpenAPI 是一种用于标准化 API 文档的规范的官方名称。它具有独特的语法，可以用 JSON 或 YAML 编写。

Swagger 是一组帮助实现 OpenAPI 的工具。大多数 Swagger 工具可在开源项目中获取；付费是获取高级工具的一种选择。

*   **Swagger Editor**：允许我们在线编辑 Swagger YAML 并查看变更的工具。
*   **Swagger UI**：为 OpenAPI 规范生成 UI 的工具。
*   **Swagger Codegen**：通过 OpenAPI 规范，Swagger Codegen 可以用多种编程语言生成各种 API 客户端和服务端。
*   其他可以帮助满足各种需求的工具，此处不一一列举。
