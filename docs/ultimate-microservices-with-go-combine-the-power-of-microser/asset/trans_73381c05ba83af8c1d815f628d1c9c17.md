# 链路追踪

链路追踪比日志和指标更新的遥测手段。它能提供更全面的应用视图。链路追踪的目标是跟踪应用的流程，无论是数据传播还是请求流程，这对于微服务架构中的 RESTful API 服务尤为重要，因为其请求频率很高。链路追踪让我们能够看到从开始到结束的函数流向、哪个函数调用了哪个函数、每个函数的持续时间、它们之间传递的参数、每个步骤的元数据等。每个步骤位于一个称为“跨度”的追踪内。完整的追踪可以讲述一个用户的故事，以及他在途中发生了什么。

![](OEBPS/images/Figure-10.4.jpg)

**图 10.4：** 链路追踪示例

在上图中，我们可以看到一个追踪示例。该追踪旨在跟踪端点 `GET /api/v1/articles/:article_id`。在追踪中，我们可以看到三个跨度：`authenticate`、`get article:41348`、`SELECT FROM articles WHERE id`。对于每个跨度，我们可以看到持续时间、跨度的顺序以及图中未显示的其他数据。一种更高级的追踪能力是执行分布式追踪。这涉及执行广泛的追踪，而不是在单个应用程序内进行追踪，而是跨越许多服务的单次追踪。

# 生产环境故障排查

生产环境故障排查是一个系统性过程，包括采取即时行动修复问题以恢复系统健康状态、执行 RCA 以及解决根本原因以防止同类问题再次发生。让我们拆解这一故障排查过程。

![](OEBPS/images/Figure-10.5.jpg)

**图 10.5：** 故障排查组成部分

**RCA**，即**根因分析**，是识别 Bug 底层原因的过程。例如，某服务有一个指标用于跟踪其一个月的错误率，数值始终在 0.1% 到 0.2% 之间。紧随一个名为“更改 API 配置”的 PR（Pull Request）部署到生产环境后，错误率指标显著飙升至 50%。我们可以有把握地假设根因就是上述 PR。

执行 RCA 的方法多种多样——查看服务仪表盘、为服务设置告警（本章稍后将讨论）、排查有问题的日志、查看系统指标、Kubernetes 集群指标、Kubernetes 日志、在 Kubernetes 中描述服务的 Pod、CI/CD 变更、第三方服务停机、异常检测、性能分析（本章将进一步讨论）等。

**补救** 是指防止当前不良状态发生的过程。

在我们执行任何补救措施之前，系统无法正常工作，甚至完全瘫痪。这种情况称为 P0 级故障。补救过程可以通过多种方式执行：Kubernetes 回滚（详见*[第 8 章 微服务简介](#c08.xhtml)*）、撤销 PR、增加副本数、更新过期配置等。

有时，我们无需执行完整的 RCA 即可进行补救，补救可以是部分的。例如，如果我们确定了是某个糟糕的 PR 导致的，补救措施很可能是撤销它，尽管我们不知道 PR 中具体是什么内容导致了 Bug。

**解决** 是指防止不良状态再次发生的过程。通过理解问题的根本原因，我们可以采取预防措施。解决措施的示例包括：通过调试修复 Bug、调整 API/DB 配置、增加副本数量等。注意，补救措施有时与解决措施是相同的。

# 理论的力量

**没有可观测性就没有理论，反之亦然。**

我们已经讨论了可观测性，但让我们来谈谈理论，并解释上述陈述。理论是解释现有数据的观点：为什么图表呈现这种堆叠方式而不是其他方式？例如，我们可以看到内存使用量持续增长的图表，这可以用内存泄漏来解释。

为了说明**理论**与**可观测性**之间的关系，我们将引用参考文献 5 中的一个类比。

一位拥有丰富人体知识且时刻掌握最新医学资讯的医生，就是好医生吗？答案是否定的，除非该医生能够检查患者并获取其数据。如果没有对患者进行适当的检测，他就无法提供恰当的治疗，没有数据支撑的每一次治疗都只是猜测。

另一方面，你是一个对人体缺乏基本了解的普通人。但你拥有最先进的患者检测技术和所有患者数据。你是好医生吗？答案也是否定的，除非你具备关于人体的基本知识。

![](OEBPS/images/Figure-10.6.jpg)

**图 10.6：** 可观测性与理论

医生的类比映射到开发人员，理论映射到医生的知识，数据映射到数据。一方面如果没有基于软件知识和内部业务知识的丰富理论，另一方面没有数据，我们就无法获得可观测性。

每当我们开始排查故障或执行 RCA 时，都应心中预设一些关于根因的理论，并用数据去验证该理论；或者通过观察数据，形成另一个可供验证的理论。

# 性能分析

性能分析通过在运行时分析程序来测量执行时间、CPU 使用率、内存使用量、运行中的 Goroutine 等指标。性能分析使我们能够识别瓶颈、提升性能并优化代码效率。通常，使用 Grafana 或 DataDog 等第三方工具会生成火焰图。尽管还有其他查看性能分析数据的方式。

![](OEBPS/images/Figure-10.7.jpg)

**图 10.7：** CPU 时间性能分析火焰图

在上图中，我们可以看到 Google Cloud 中 Golang 应用 CPU 时间性能分析的示例。不过，我们也可以使用 Golang 团队发明的原生工具 `pprof`。让我们看看如何使用它：

```
package main

import (
	"net/http"
	_ "net/http/pprof"
	"sync"
	"time"
)

var leakSlice1 = []string{}
var leakSlice2 = []string{}
var leakSlice3 = []string{}

func main() {
	// start pprof server
	go func() {
		http.ListenAndServe(":6060", nil)
	}()
	wg := sync.WaitGroup{}
	wg.Add(1)
	go leak(&wg)
	wg.Wait()
}

func leak(wg *sync.WaitGroup) {
	defer wg.Done()
	for i := 0; i < 10_000_000; i++ {
		appendToLeakSlice1()
		if (i % 10_000) == 0 {
			time.Sleep(100 * time.Millisecond)
		}
	}
}

func appendToLeakSlice1() {
	leakSlice1 = append(leakSlice1, "a")
	appendToLeakSlice2()
}

func appendToLeakSlice2() {
	leakSlice2 = append(leakSlice2, "ab")
	appendToLeakSlice3()
}

func appendToLeakSlice3() {
	leakSlice3 = append(leakSlice3, "abc")
}
```

在上述示例中，启动性能分析所需的仅有：

*   通过声明 `_ "net/http/pprof"` 导入 `pprof` 包。
*   在某个端口启动一个 goroutine：

```
go func() {
	http.ListenAndServe(":6060", nil)
}()
```
