# 微服务简史

首先要说明的是，许多人声称他们有权发明微服务架构。根据维基百科，2004 年 Fred George 是第一个提到类似微服务概念的人。他研究的架构被称为“贝叶斯原则”。2005 年，Peter Rodgers 在 Web Services Edge 大会上引入了“微 Web 服务”这一术语。由于缺乏对微服务架构的明确定义，许多人都可以声称是他们发明了它。从那时起，许多人展示了看起来或感觉上像微服务的事物。重要的是不要将微服务与 SOA 混淆，我们稍后将详细说明它们之间的区别。从那时起，其流行度逐年上升，并在 2014 年至 2015 年间加速增长（图 1.1）。

# 单体架构、SOA 和无服务器架构

了解某些术语或技术的其他替代方案有助于清晰地理解它们。从软件行业早期开始使用了一段时间的常见架构风格包括单体架构、“面向服务架构”，即 SOA，以及一些我们在本书中不再详述的其他架构。

# 单体架构

源自古希腊语的“Mono”意为单独、单一。顾名思义，这种架构被构建为部署在单一平台上的单个代码块。通常，在单体架构中，有三个主要部分——存储（数据库）、包含客户端的 Web 应用，以及充当服务端的后端，后者包含所有业务逻辑、数据层和其他所有内容（图 1.2）。

![](OEBPS/images/Figure-1.2.jpg)

**图 1.2：** 简单的单体结构

`DAL` 是 Data Access Layer（数据访问层）的首字母缩写。该软件中间件负责为拥有数据库直接访问权的软件层提供支持，并提供重试、错误处理、缓存等工具。

从简单的图表中可以看出，这种架构非常直观。然而，所有组件都紧密相互依赖。

简而言之，单体架构的优缺点如下：

## 优点

*   开发简单，交付生产简单。
*   最少的跳转次数：无需在服务之间通信，通过降低延迟可以节省大量时间，从而带来更好的性能。
*   非常容易实施 `DRY` 原则（不要重复自己）——归功于单一代码库。

## 缺点

*   **面条代码**：随着代码库的扩展，代码更有可能变得笨重难管理。
*   **更难排查故障和调试**：在庞大的代码库中导航极具挑战性。甚至更难找到隐藏在某个函数中导致副作用的恶性 Bug。
*   **IDE**：集成开发环境（IDE）不堪重负。请注意，存在一种在单体仓库中编写微服务的方法，即所有服务使用单一仓库。
*   **容易积累遗留代码和技术**：我们害怕在大型代码库中更改核心功能、基础设施和技术。这些更改可能会显著影响应用程序，因为保留旧代码和旧技术很方便。

如今，微服务架构是市场上最流行的架构，人们倾向于摒弃单体架构，因为他们认为它已过时。然而，单体架构在各种用例中依然受益良多。

# SOA

`SOA` 代表面向服务架构。虽然与微服务相比，该名称可能容易产生误解，但它们确实有共同点。然而，它们之间存在许多差异。SOA 是一种架构风格，它将软件系统组织为一组松耦合且可复用的服务。在 SOA 架构中，有两个主要部分——提供者和消费者。提供者和消费者可以位于同一部署组件/应用程序/服务器上。这是 SOA 与微服务的重大区别。这种方法诞生于 90 年代初。那时，软件工程的运维部分更为复杂。我们有专门专注于基础设施、安全、数据库等的团队。

在分解层面上，我们可以将 SOA 架构置于单体架构和微服务架构之间。单体架构表现为单一单元，而微服务架构表现为细粒度的划分。

![](OEBPS/images/Figure-1.3.jpg)

**图 1.3：** 简单的 SOA 结构

简而言之，SOA 的优缺点如下：

## 优点

*   **可复用性**：可复用性是该方法的核心。它允许我们在服务/API 层面分离关注点，并复用基础设施，如硬件、网络、操作系统等。
*   **关注点分离**：其粒度不如微服务细。但它仍允许我们并行交付服务/API，而无需依赖其他团队。

## 缺点

*   **副作用**：共享组件中的问题可能影响其他组件。例如，如果消费者或提供者消耗过多资源、环境变量发生变化，或任何其他副作用，所有这些都很容易影响所有现有服务。
*   **性能开销**：SOA 中额外的抽象层和通信协议可能引入性能开销。跨不同组件和网络的服务调用可能导致延迟，潜在地影响响应时间和整体系统性能。网络问题的顾虑同样适用于数据库。
*   **复杂性**：实施 SOA 可能给我们的服务带来复杂性。

# 无服务器架构

在我们这里介绍的架构中，这种架构方法是最现代的。

云计算的诞生自然催生了无服务器架构。这种方法的核心是剥离基础设施顾虑，让我们专注于重要的事情——业务逻辑。顾名思义，这是“server”（服务器）+“less”（无）——意味着不存在服务器。当然，某处确实存在运行代码的基础设施和服务器。但我们不负责管理这台服务器。云厂商负责所有这些工作。此类技术的例子包括 GCP 的 Functions 服务或 AWS 的 Lambda。还有许多服务/产品旨在支持无服务器架构。

在探讨无服务器架构的优缺点之前，我们想讨论两个核心概念：FaaS 和 BaaS。

*   **FaaS**：代表函数即服务。我们编写函数/API 端点，其余工作交由云端完成。
*   **BaaS**：代表后端即服务。我们可以专注于开发和维护客户端，而无需关注存储、数据库管理、网络和其他基础设施方面。

![](OEBPS/images/Figure-1.4.jpg)

**图 1.4：** 简单的无服务器结构

从图中可以看出，作为开发者，我们只编写了绿色方块（函数），云厂商提供了所有黄色方块（第三方服务/数据库）。

## 优点

*   **高效的开发流程**：开发流程高效，初期开发迅速。基础设施顾虑不再是负担，因为无服务器架构无缝地管理了它们。
