# 服务间通信

正如我们在*[第 1 章，微服务简介](#c01.xhtml)*中所见，微服务架构由小型、独立且解耦的服务组成。每个服务旨在实现**单一**目的。然而，系统需要利用所有服务来达成更大的目标。为追求这些目标，服务需要一种通信手段，通过发送和接收来交换数据。这种通信形式因其复杂性而呈现多种面貌。

需要考虑的方面很多——消息类型、消息大小、响应方式、延迟、故障、文档、消息打包等。以下是在微服务架构中通信的主要形式：

*   API 调用
*   消息代理
*   gRPC

我们不会深入探讨这些形式，因为每一个都很庞大，需要透彻的理解。要正确、精确地使用它们，我们必须知道如何正确构建它们。我们还必须熟悉它们的优缺点，以便在选择时做出最佳决策。此外，还有其他几个因素、约束和假设增加了局势的复杂性。

# API 调用

API 代表应用程序编程接口。API 调用由发送调用的服务发起的请求和接收请求的服务返回的响应组成。每个请求包含参数，指明请求的是哪些数据。我们通过网络的第 7 层（应用层）发送 API 请求。

API 调用是微服务架构中服务间最常用的通信方式。多样的 API 风格（如 REST、SOAP 和 GraphQL）值得深入讨论。其中，REST 是采用最广泛的。因此，下一章（*[第 7 章，构建 RESTful API](#c07.xhtml)*）将探讨 RESTful API。

# 消息代理

我们在上一章提到了消息代理，并将其与发布/订阅设计模式进行了比较。对消息代理的一个贴切描述是：将其定义为一项服务与另一项服务之间消息的中介。服务不直接向另一服务发送请求，而是将消息发送给代理。消息主要包含数据、配置，有时还包含指令。消息代理是一个独立的服务，通常由许多服务组成，并作为一个独立的集群运行。代理的目标是接收消息，并通知其他服务有关此消息，或将其存储直到另一服务拉取它。消息代理还有许多额外功能，如重试、存储 DLQ（即死信队列）、监控、临时存储、加密、控制消息中介的速度等。

# gRPC

gRPC 是一个现代的、开源的 Google 远程过程调用（RPC）**框架**。gRPC 允许使用 Protocol Buffers 定义与语言无关的 API。Protocol Buffers（protobuf）是一种与语言无关的序列化格式，可高效地构建和序列化数据。我们可以使用 Protocol Buffers 在各种编程语言中快速创建客户端和服务端实现。gRPC 框架利用 HTTP/2 作为底层协议，支持双向流式传输和实时通信等多种能力。在幕后，它本质上只是一个 API 调用，但它利用了 HTTP/2 的能力，这使其非常强大。虽然简单的 API 很直观，但 gRPC 学习曲线平缓。此外，gRPC 框架并不支持所有编程语言。

# API 网关

在微服务架构中，服务间通信有多种方式。标准方式是通过简单的 API，正如我们所见。

API 网关是一项充当微服务架构入口（网关）的服务。API 网关接受来自所有客户端的请求，然后将客户端请求导向目标服务，并将响应返回给客户端。拥有单一的系统入口点，使我们能完全**控制**进出的内容。我们可以使用 API 网关实现几类功能：

*   **安全性**：每个服务可以使用身份验证、授权和加密功能。每个服务不必强制执行这些安全要求。相反，大多数事情可以在 API 网关中完成。有时，由于业务逻辑约束，无法执行任何操作。
*   **可观测性**：每个服务可以使用指标、日志和追踪等功能。我们可以从 API 网关开始追踪所有请求。
*   **路由**：限流、缓存、故障处理、负载均衡、滚动更新功能等。所有这些逻辑都可以在 API 网关内部实现。

![](OEBPS/images/Figure-6.3.jpg)

**图 6.3：** API 网关，客户端向服务发送请求

在上图中，我们可以看到不同的客户端向 API 网关发送请求。API 网关根据请求的路径和域名知道如何将每个请求导向目标服务。此示例演示了我们提到的 API 网关路由功能等。

构建架构时要记住的最重要一点是优先考虑**简洁性**。API 网关模式之所以有益且强大，是因为它帮助我们实现更简单的架构。它集中处理了许多关注点——安全性、可观测性、负载均衡、限流等。当问题发生时，我们会知道去哪里调查事故。

请注意，每个 API 网关各不相同。每个架构有不同的需求，导致不同的 API 网关方案。*[第 8 章，Kubernetes 简介](#c08.xhtml)*将讨论 Kubernetes 如何使用名为 ingress 的资源独立实现某些 API 网关模式功能。
