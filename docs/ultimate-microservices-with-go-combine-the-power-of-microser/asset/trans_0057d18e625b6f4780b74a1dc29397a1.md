

## 资源分配

在 Kubernetes 中指定 Pod 或工作负载内的 Pod 时，我们可以选择性地指定可以分配给容器的资源数量。标准且常见的分配资源是 CPU 和内存，但还有其他类型。我们可以为资源分配指定两个参数——`request`（请求）和 `limit`（限制）。

*   **Request（请求）**：定义资源 `requests` 时，调度器会据此决定将 Pod 放置在哪个节点上。`request` 代表资源使用预期。
*   **Limit（限制）**：定义资源 `limit` 时，`kubelet`（“节点代理”）会强制执行该 `limit`，不允许容器超过这些 `limits`。如果 CPU 达到 `limit`，容器会被限流；如果内存达到 `limit`，运行该容器的 Pod 会被终止并重启。

掌握我们分配的资源至关重要。如果没有适当的分配，Pod 就会为所欲为。例如，我们的应用程序可能存在内存泄漏并消耗大量内存，从而影响节点或整个集群上的其他 Pod。另一个反面例子是，过小的内存分配可能会限制应用程序无法正常运行。作为开发人员，我们有责任确定容器所需的资源数量。

下面是一个 Pod YAML 示例，它启动一个名为 `hello` 的容器，并设置了 CPU 和内存的 `requests` 和 `limits`：

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: example
spec:
  containers:
  - name: hello
    image: hello-world:latest
    resources:
      requests:
        memory: "128Mi"
        cpu: "250m"
      limits:
        memory: "256Mi"
        cpu: "1"
```

## Kubernetes 最佳实践

以下四项最佳实践与 Kubernetes 开发人员更为相关。还有其他几项最佳实践更多地与运维相关。推荐一本关于 Kubernetes 详细最佳实践的书籍——*Kubernetes Patterns*。参考资料中有它的链接。这些模式并非摘自该书。

### 保持良好的 YAML 卫生

YAML 在 Kubernetes 中就是一切。YAML 代表了 Kubernetes 中的期望状态。作为用户，我们定义它们，Kubernetes 会为我们完成所有其他工作。它致力于将当前状态转换为期望状态（YAML 文件）。基于这一理解，YAML 必须满足以下要求：

*   **整洁干净**：不包含任何我们不需要或不想要的配置。此外，我们需要避免在 YAML 文件中声明默认配置。
*   **标签和注解**：这两个术语是与 YAML 资源相关的元数据。注解用于存储任意元数据，标签用于在 Kubernetes 中识别资源。这是 Kubernetes 中一个广泛的话题，但我们在此不作讨论。我们需要在每个 YAML 文件中充分利用这两种元数据。
*   **针对工作负载**：指定**存活探针和就绪探针**，正如我们之前提到的。
*   **ConfigMap 和 Secret 必须妥善配置**：切勿重复声明现有 ConfigMap 或 Secret 中已声明的键值。

### 日志记录 —— 专门针对 Kubernetes

我们在 Kubernetes 中使用日志的方式与在其他系统中使用日志的方式略有不同。为避免错误，我们必须通过包含以下内容来正确标记和标记日志：

*   **正确的服务名称**：不是 Pod 名称！我们必须在日志中包含服务名称，以便能够将日志关联到同一服务。一个常见的错误是日志仅包含实例名称（在 Kubernetes 中即 Pod 名称），而不是服务名称。
*   **版本**：为了确定哪个版本在何时发生了什么变化，我们必须在每条日志上指定服务版本。这样做，我们就能看到并观察服务的生命周期。例如，错误日志仅从版本 1.3.2 开始出现，这意味着该版本引入了一个 Bug。
*   **集群环境信息**：任何可能影响应用程序行为的数据。有时，服务出现问题或错误并非其本身的过错。集群或节点可能对此问题负责。例如，记录节点名称可能非常有用。

### 环境管理

在任何系统中，我们都会出于不同原因拥有不同的环境。生产环境、预发布环境（有时称为预生产）、测试环境、本地环境等。在 Kubernetes 中分离环境主要有两种方法：

*   **每个环境使用不同的集群**：这种方法的主要优势是环境解耦，彼此之间没有依赖。其主要劣势是为每个环境搭建不同的集群需要付出更多努力，维护多个集群也需要付出更多努力。
*   **每个环境使用不同的命名空间**：这种方法的优劣势与前一种方法恰好相反。虽然环境之间存在依赖（例如，来自不同环境的 Pod 可能被分配到同一节点上），但搭建和维护所需的精力要少得多。

### 合理的监控

除了我们作为开发人员倾向于在服务上实施的常规监控外，还有一些监控专门针对运行在 Kubernetes 上的服务。以下是三个重要的监控指标：

*   **资源**：监控 CPU、内存和存储的使用情况。监控这些资源对于优化服务性能、识别瓶颈和确保高效的资源分配至关重要。
*   **容器状态**：监控容器是否宕机/运行中/报错/探针失败/重启次数等。这些指标对于确保服务的可靠性和健康状况至关重要。此外，它们有助于发现问题、便于故障排查，并有助于构建更稳定、更有弹性的服务。
*   **Kubernetes 事件**：Kubernetes 通过事件审计其采取的操作。Kubernetes 事件记录了集群的历史。通过监控 Kubernetes 事件，我们可以检测趋势、问题和异常，并通过查看事件获得许多洞见。

## 总结

在本章中，我们浏览了 Kubernetes 的基础知识，重点关注与开发人员相关的资源和操作，而非运维侧面。我们介绍了 Kubernetes 中的三个基本术语——Node（节点）、Pod 和 Namespace（命名空间）。这些术语为理解 Kubernetes 中的其他资源奠定了基础。我们了解了 Kubernetes 工作负载——Deployment（部署）、DaemonSet、StatefulSet（有状态集）、Job 和 CronJob。作为开发人员，我们必须为服务选择合适的工作负载资源。随后，我们介绍了使用 Kubernetes 时可能会遇到的常见资源——ConfigMap、Secret、HPA 和 Ingress。

接着，我们讨论了两个与开发人员息息相关的主要 Kubernetes 概念。第一个是就绪探针和存活探针，它们确保我们的服务已准备好工作（接受流量）并正常运行。第二个是资源分配——我们了解了使用工作负载时需要指定的内容（主要是 CPU 和内存的 requests 和 limits）。
