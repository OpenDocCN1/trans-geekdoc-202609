## 2.4.3 Smart contract programming

Most of the DL smart contract execution environments, including Ethereum, Hashgraph, and BTC, follow state machine replication on the order-execute principle. The consensus mechanism of these DLTs assures a clear order of the smart contract-invoking transactions before their execution. The ordered transactions are executed sequentially on all peers, reflecting the common change of the ledger/smart contract state. For this to happen, the execution of smart contracts (processing of all transactions address to a smart contract by the smart contract's code) needs to be deterministic.

The requirement for deterministic execution places a strong limitation on what a smart contract can do. For example, using date or time functions, generating random values, or retrieving data from off-chain resources (e.g., external API calls) prevents deterministic execution. It is, therefore, very common that these DLUs use special smart contract programming languages to enforce the determinism even at the level of programming language. Suppose the deterministic scripting language used by the VM is Turing-complete. In that case, this essentially means that the types of smart contracts that the developers can design are limited only by their programming skills and creativity.

However, not all DL smart contract execution environments follow the order-execute principle. Hyperledger applies a different transaction lifecycle and, therefore, different smart contract execution and validation principle. It is called execution-order-validate [33]. The name indicates that a smart contract call, invoked by a transaction to a smart contract, is first executed. The transactions to smart contracts can therefore be executed in any order, or in parallel. A transaction need not be executed by every node in the network. After a transaction is deed, endorsement policies define which nodes need to agree on the result of a transaction, and then it is added to the ledger. This is the phase where transaction ordering occurs. The transaction validation, which happens last, is separated from the execution. During validation, each node has an ordered list of already executed transactions and can check if any of them is invalid, for example to double-spending.

The execute-order-validate approach has several benefits: increased performance (only nodes need to agree on the result of a transaction), code privacy (only endorsement nodes need to see the code), and the possibility of using general-purpose languages.

### 2.4.3.2 Tools

At the beginning of the DApp era, only a basic set of tools was available. Most of the tools were manual, and there were no de editors with added highlighting or syntax checking for smart contracts. With the maturing of DApp environments, new tools and frameworks became more integrated. These tools support the development, validation, and deployment of smart contracts. For example, Remix is an online-based IDE for smart contracts. The MythX API has been integrated into development frameworks, including Hardhat, Truffle, and VS Studio.

Various levels of code testing are essential for efficient and secure smart contracts (see Section 2.4.4 for more details). Several projects aim to formal verification of smart contracts, and a comprehensive list is being maintained. Some of these tests operate at the source code level, whereas others operate at the compiled bytecode level. MythX is a cloud-based smart contract security service. It performs security analysis remotely, accepting jobs and returning results via an API. It covers byte-code safety, authorization controls, control flow, correct implementation of ERC standards, and varying coding best practices for Solidity. The analysis types include symbolic analysis, fuzzing (bytecode), Solidity code analysis, and static analysis. OYENTE is another tool to analyze Ethereum smart contracts code, based on symbolic execution. OYENTE takes two inputs, the Ethereum smart contract bytecode and Ethereum global state. It checks a contract against several software weaknesses.
