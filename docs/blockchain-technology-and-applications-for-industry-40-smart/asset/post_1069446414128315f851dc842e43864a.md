In this way, the consensus timestamps of events (and transactions contained) begin being determined after practically two rounds, that is, only a few seconds after the event's creation. Of course, the virtual voting process may encounter ties during election of the round $n+3$ (and even from higher rounds) which are engaged in resolving. This certainly prolongs the time of reaching consensus, that is, the consensus on time order of $n-1$ events, but even then the whole process is very fast.

After determining consensus timestamps of all events in a round, the consensus on their time order is automatically achieved, which was the aim of the whole procedure. The consensus timestamps of events are assigned to the transactions they contain, so the consensus timestamp of a transaction is fair, since it reflects the moment when the majority of nodes received that transaction and cannot be corrupted or significantly changed by a malicious node. Due to the gossiped protocol, the whole idea of splitting into rounds, elections of famous witnesses, etc., might seem complicated. But this is not an issue since the software that implements hashgraph on a node does not require any special hardware – it requires more than an average computer with a CPU for universal purposes. The amount of gossiped data between two nodes is minimal. As mentioned earlier, within a sync message, a node sends only the events without hashes of the events' parents (when sending message, a node can calculate those hashes). Besides, hashgraph's virtual voting algorithm does not require any additional bandwidth. As reference to noted, a fast home Internet connection (of each node) would be enough to support the same number of transactions per second as the network can handle worldwide. Another indicator of hashgraph's speed is the test results for the network of 32 computers (nodes) spread across eight regions around the globe. Namely, when the network runs at 50,000 transactions per second, the consensus on transactions is reached in 3 s. If the network is connected in a single region, the time needed for consensus is 0.75 s. Also, the same number of computers (spread in eight regions worldwide) can provide performances of fewer than 7 s to handle up to 200,000 transactions per second.

There are other advantages of the described concept of virtual voting. The most important one is the hashgraph's BFT property, achieved in the strict sense of the BFT definition (and mathematically proven), unlike blockchain or tangle technologies where BFT is accomplished only as a possibility. To be specific, the hashgraph's honest members will be able to keep running given application (e.g., cryptocurrency) correctly, even when the number of fraudulent members/nodes is very close to 1/3 of the whole population. The BFT property of a hashgraph is a direct consequence of the implemented rules (i.e., of the Byzantine protocols) within virtual voting. The strongly seeing and supermajorities of nodes and witnesses are required.

The second advantage is that all voting processes and getting consensus are stamped virtually and independently by each node. Every member/node does everything on its own, as if it were alone on a desert island and without the need for any communication with anyone (except the regular gossip). Besides reduced demand for Internet bandwidth, the benefit of this is an increased speed of realization and verification of transactions. To be specific, an alternative consensus algorithm that would obtain BFT property certainly should be running separate Byzantine protocols, including a large amount of communication between all members. Thus, if the aim is to determine the order of events in time, each separate communication between two nodes would contain either Yes/No questions (in both directions), where each question would have the form, "did X come before Y?". such an algorithm would be very slow due to the delays in communication between nodes over the Internet, and perhaps due to its complexity.

Instead of mentioned so far, by applying the virtual voting algorithm, the Byzantine agreement protocol is run only for witnesses, whereas famous witnesses are chosen as a result of a small number of witnesses, such as: "Is this witness famous?". In this way, the process of time ordering (through performing some sorting algorithm) is as obvious. Already explained, the time order of events is (automatically) determined as soon as their consensus timestamps are found, as the median values of the candidate timestampsed by the nodes that created the famous witnesses.
