
虽然能够审查或审计日志文件很重要，但这属于事后事项。因此，系统和网络管理员以及其他运营人员必须始终保持警惕，实时监控，但这在以下三个因素的影响下可能非常困难：(1) 长时间查看日志文件和监控仪表盘指标时，这项任务有时会感到极度无聊；(2) 入侵检测系统（IDS）有时甚至经常会发出误报，从而导致(3) 运营人员和管理员因频繁应对“杂音”——例如在出现大量误报后忽略警报——而养成不良的安全行为。

关于 IDS 监控的另一个问题在于被动攻击通常比主动攻击更容易实施且更难被发现。例如，在无线网络中，攻击者只需一根天线和接收器，或像 Pineapple® 与 HAK-5® 套件以及其他捕获和分解应用程序，即可读取所有报文并窃取信息。同样，在小型组织的有线网络中，攻击者可能只需入侵单个主机即可获取该网络接口上所有流量的数据，或访问其连接的域名服务器（DNS）或认证系统。

即使是主动攻击，如果它们足够隐蔽或复杂，尤其是利用暗网（Dark Web）或暗网（Darknet）中的多个隐藏代理，或者通过曲折的网络路径发起时，也可能难以被检测。数据包注入、重放攻击和冒充攻击可能只需要一台被入侵的主机，其攻击痕迹可能非常小，即“在地面雷达”范围内，难以被检测系统捕获。一次针对路由器或网关主机的冒充攻击可能成功将流量重定向至攻击者的机器，此时 IDS 将“脱离工作”。相反，较为明显的攻击如数据包删除、延迟、重新排序或修改，可能需要入侵网关主机，从而完全控制该链路的流量，进而使检测系统完全失效。虽然这些攻击会产生更大的痕迹，但其根源往往难以发现，甚至更难定位。到那时，损害已造成，只能处理其后果。

### 2.3.3 保持运营能力

我们所说的运营，是指确保企业或政府机构能够正常开展业务，但在技术管理中，这需要事先规划。在信息安全方面，当系统被开发或技术被实施时，安全特性必须作为关键成功因素（CSFs）在整体计划和预算中占据重要位置，与其他质量保障（QA）方面同等重要。技术管理者必须确保 DevSecOps 评审循环中包含剔除可能导致组织受损的漏洞和缺陷，并确保技术被正确使用、系统按预期实现。

无论是开发产品还是实施技术或服务，其生命周期都包括规划阶段，具体的规划方法因公司而异，甚至在遵循相同指南的公司之间也可能有所不同。无论如何，信息安全必须是组织内部制衡机制的一部分——尽管大多数人将其视为业务成本的超额部分，并希望予以削减。

此外，所实施的控制措施（如安全策略，无论是文档形式还是在防火墙等设备上实现）必须针对我们职责范围内最可能出现的问题进行妥善处理，否则我们可能被指责疏忽。因此，除了技术措施外，我们还实施安全策略，对网络、节点和系统的使用施加限制，作为防御措施。安全事件（ incident）是指任何破坏政策中定义的网络资产合法使用，或导致系统退化、无法按预期使用的行为。漏洞是网络或计算机系统的特性，能够导致政策或已建立的防御机制被故意或 unintentional（意外）规避。威胁是指可能对个人或组织造成损失或伤害的情形。最终，攻击是有意利用漏洞的尝试。自然灾害可构成对数据中心的威胁，因此组织通常会部署多个数据中心并引入冗余措施以缓解此类威胁。在充分认识到这些问题后，责任与问责随之而来。

作为我们责任框架的一部分，技术管理者和管理员必须保持警惕，监测来自诸如 Mitre 的 CVE、卡内基梅隆大学的 CERT® 与 SANS® 的通知，因为已知可被利用的漏洞更容易被黑客社区使用，因而对网络或系统的威胁高于那些尚未被识别的漏洞。此点当然忽视了所谓的零日攻击（zero‑day attacks），即安全社区或技术供应商尚未识别的全新攻击方式。

另一个核心概念是“威胁强度”。威胁强度或威胁级别的一个要素是成功攻击可能导致的实际损害。因此，审计、检测和恢复在运营安全中尤为重要。审计包括评估日志及相关情报。某些基于审计的技术能够在特定网络攻击中实现检测和恢复。恢复通常涉及使用备份或启动备用系统。而防攻击则往往需要构建强健、有弹性的基础设施，并对资产进行细致的控制与监控——在某些情况下，甚至监控员工在电脑上的活动。键盘记录器和屏幕截图等工具常用于高安全环境中实现此目的。

从安全运营的角度来看，需要注意的是，当采用旨在实现其他目标（如保密性或完整性）的安全措施时，所选机制不应使系统更易受到某些其他攻击（如分布式拒绝服务攻击 DDoS）的威胁。例如，计算密集型的加密操作用于验证连接，可能会增加工作负载，从而助长 DDoS 攻击，导致认证服务器被淹没。以 2014 年为例，七家美国和加拿大的大型银行遭受外国国家行为体发起的恶意数据包洪水，这些数据包设计用于迫使边缘路由器在丢包时过度 labor，导致 overheating 并 malfunction。银行随后进行了大规模清理，且需应对大量不满的客户。
