
因为政府和军事组织有大量可用的检查清单，而且许多检查清单本身也对企业有用，私人组织可能会在确定使用哪一项或哪几项时感到困难。需要注意的是，检查清单通常是针对特定标准的，这些标准是机构或企业必须满足的，以符合规定、政策、规则和法律的要求。换句话说，虽然有些检查清单是通用的，但有些是特定于某个领域的。确定哪些检查清单对组织本身有用可能是一项艰巨的任务。一旦选择或定义，基线就需要相应地进行管理——这正如所指出的，也可能很令人望而生畏。这对于私营技术供应商尤其如此。

为帮助，技术供应商基于安全的检查清单通常包含自动化工具，帮助公司以更安全的方式评估和配置资产，其中包括 Microsoft Baseline Security Analyzer 和 Microsoft Security Compliance Manager（用于 Microsoft 产品），以及 Bastille Linux（用于多种 Linux 变体）。Microsoft Baseline Security Analyzer（MBSA）设计用于帮助组织“根据 Microsoft 安全建议确定其安全状态，并提供具体的修复指导。”[⁹](#9781284211658_CH11_08.xhtml#c11-bib0009) MBSA 专注于中小型组织，类似于 NCP 所描述的独立环境。

Microsoft Security Compliance Manager 设计用于大型企业，允许组织将 Microsoft 安全建议纳入基线配置，然后以多种格式（包括 SCAP）导出，供用于保护组织中 Microsoft 架构的自动化工具使用。Bastille Linux 是一个硬化脚本，已随多种 Linux 发行版预装。脚本会向管理员提供一系列选择，据此构建策略并配置系统。脚本还提供了一个详细的交互式模式，用于教导用户关于安全及其选项。

### 11.4.8 Center for Internet Security Benchmarks

回顾，配置管理（CM）涉及诸多方面，包括系统性能，而性能的显著下降往往是安全攻击的指标。技术管理者和安全专业人员需要考虑系统性能基准作为安全问题，因为基线用于判断性能下降是由于工作负载还是异常（可能由系统故障或安全攻击引起）。因此，我们将性能基准视为基线配置的一部分。性能基准也可能是合同质量和性能承诺的一部分，即服务质量（QoS）指标或参数。

Center for Internet Security（CIS）是一家非营利组织，使命是“制定并推广基于共识的标准，以提升 Internet 连接系统的安全性和隐私性，并确保业务、政府和私人 Internet 功能及交易的完整性，这些是社会日益依赖的。”[^(10)](#9781284211658_CH11_08.xhtml#c11-bib0010) CIS 网站至少提供 52 份配置指南，涵盖各类 IT 资产、基准审计工具以及 21 项安全指标，用于评估安全流程的结果。这些基准通常包含符合 NPS 规范的独立或托管环境的安全配置文件。

对最近一份 Windows 基准的简要总结：“在完成资产的基线配置后，重要的是在与生产环境相当的环境中对其进行测试。测试将揭示在生产环境中可能导致重大功能问题的交互和配置设置。”[^(10)](#9781284211658_CH11_08.xhtml#c11-bib0010) 如前所述，最好在测试环境中发现问题，而不是在生产环境中，但大多数组织缺乏能够直接匹配生产环境负载和交互复杂性的测试环境，因此需要理解，无论如何，某些意外的交互仍可能发生。因此，对于任何对生产环境的变更，都应有一个明确的回滚程序，说明如何撤销所做的更改。

### 11.4.9 Maintaining the Secure State

随着技术环境的不断演进，不断发现并引入新的威胁和漏洞，任何资产的基线配置变更都是不可避免的。然而，明确且明确地管理这些变更的过程至关重要。大量工作表明，控制变更管理过程是对信息系统实现有效控制的关键，也是改进 IT 服务质量的第一步。如前所述，管理安全状态的基础是控制变更管理过程以及控制谁有权进行变更。NIST 建议实施变更管理的四个阶段：(1) 实施变更访问限制，(2) 实施配置变更控制流程，(3) 进行安全影响分析，和 (4) 记录并归档变更。[⁴](#9781284211658_CH11_08.xhtml#c11-bib0004) “实施变更访问限制”阶段将限制谁可以进行变更，并通过约束系统上允许的行为类型来开始执行变更管理流程。初始化变更访问限制的推荐流程包括三个步骤：

1. 确定需要对单个 IT 资产进行哪些类型的变更。

2. 确定谁将被授权进行这些变更。

3. 建立适当的控制措施，仅允许上述已识别并授权的个人进行变更。

实施变更管理的第二阶段是引入配置变更流程。虽然具体流程应在 SeCM 的组织规划阶段确定，但通常建议该过程经过接收、记录、测试、批准并实施，并在相应地更新基线配置的同时完成。NIST 推荐以下八个步骤：

1. 请求变更。此步骤发生在变更最初构思时。请求可能来自信息系统的最终用户、帮助台或管理层，也可能来源于供应商提供的补丁、应用程序更新等。

2. 记录变更请求。当变更正式进入配置变更控制流程时，必须记录。组织可使用纸质请求、电子邮件或自动化工具来跟踪变更请求、按工作流程路由，并允许电子确认/批准。

3. 判断变更是否需要配置控制。某些变更类型可能免于配置变更控制，如 SeCM 计划或程序中定义的豁免项。如果变更被豁免，请在变更请求上注明，并允许在无需进一步分析或批准的情况下直接执行；但系统文档仍需更新（如系统安全计划、基线配置、组件清单等）。

4. 分析变更对信息系统的安全影响。

5. 测试拟议的变更，评估其安全性和功能影响。变更的影响应提交给 CCB 进行审查。
