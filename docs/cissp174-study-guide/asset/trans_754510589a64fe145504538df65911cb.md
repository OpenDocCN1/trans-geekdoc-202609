

# 极限编程（XP）

极限编程（XP）是一种敏捷开发方法，采用成对的程序员基于详细规格说明进行工作。客户参与度极高。“极限编程在五个关键方面改进了软件项目：沟通、简洁、反馈、尊重和勇气。极限程序员与客户及同行程序员保持持续沟通。他们保持设计简洁清晰。从第一天起就通过测试软件来获取反馈。他们尽早将系统交付给客户，并实施建议的变更”[[13]](#Ch009_459-508_B9780443187346000088.xhtml#bb0070)。XP 核心实践包括：

*   **计划**：指定所需功能，称为用户故事。它们用于确定迭代（时间线）并驱动详细规格说明。
*   **结对编程**：程序员以团队形式工作。
*   **四十小时工作周**：预测的迭代应足够准确，以预测完成项目所需的工时。如果程序员必须加班，则说明迭代规划有缺陷。
*   **全程客户参与**：客户随时可用，并密切监控项目。
*   **详细测试程序**：称为单元测试[[13]](#Ch009_459-508_B9780443187346000088.xhtml#bb0070)。

> **注意**
>
> XP 开发模型不应与 Microsoft Windows XP 混淆：极限编程对首字母缩写词“XP”的使用早于微软。

## 螺旋模型

螺旋模型是一种旨在控制风险的软件开发模型。Barry W. Boehm 创建了该模型，并在其 1986 年的论文《软件开发与改进的螺旋模型》中进行了描述（参见 [http://portal.acm.org/citation.cfm?id=12948](http://portal.acm.org/citation.cfm?id=12948)）。Boehm 指出：“螺旋模型的主要显著特征是它创造了一种风险驱动的软件过程方法，而非主要的文档驱动或代码驱动过程。它融合了其他模型的许多优点，并解决了它们的许多困难”[[8]](#Ch009_459-508_B9780443187346000088.xhtml#bb0045)。

螺旋模型重复项目的步骤，从适度的目标开始，以不断扩大的螺旋向外扩展（称为轮次）。螺旋的每一轮构成一个项目，每一轮可以遵循传统的软件开发方法，如修改的瀑布模型。每一轮都会进行风险分析。项目或过程中的根本缺陷更有可能在早期阶段被发现，从而导致更简单的修复。这降低了项目的整体风险：大型风险应被识别并缓解。

Boehm 使用螺旋模型开发了 TRW 软件生产力系统（TRW-SPS），这是一个复杂的软件项目，产生了 1,300,000 条计算机指令。“第零轮”是一项可行性研究，一个旨在确定 TRW-SPS 项目是否对组织具有重大价值、从而值得承担风险的小型项目。可行性研究表明该项目值得进行（低风险），项目随之向外螺旋扩展。后续轮次的交付物包括：

1.  操作概念（COOP）
2.  软件需求
3.  软件产品设计
4.  详细设计[[8]](#Ch009_459-508_B9780443187346000088.xhtml#bb0045)

每一轮包含多个重复步骤，包括原型开发，最重要的是风险分析。Boehm 的螺旋模型如[图 9.5](#Ch009_459-508_B9780443187346000088.xhtml#f0030)所示。

螺旋以项目的成功实施告终。任何潜在的高风险，如对组织缺乏价值或实施失败，都在螺旋早期被识别并缓解，此时成本更低、更容易缓解。

## 快速应用开发（RAD）

**快速应用开发**（RAD）通过使用原型、“虚拟”GUI、后端数据库等快速开发软件。RAD 的目标是快速满足系统的业务需求；技术顾虑居于次要地位。客户深度参与整个过程。

根据医疗保险和医疗补助服务中心（参见 [http://www.cms.gov/Research-Statistics-Data-and-Systems/CMS-Information-Technology/XLC/Downloads/SelectingDevelopmentApproach.pdf](http://www.cms.gov/Research-Statistics-Data-and-Systems/CMS-Information-Technology/XLC/Downloads/SelectingDevelopmentApproach.pdf)），RAD“旨在快速生成高质量系统，主要通过迭代原型（在开发的任何阶段）、积极的用户参与和计算机辅助开发工具。这些工具可能包括图形用户界面（GUI）构建器、计算机辅助软件工程（CASE）工具、数据库管理系统（DBMS）、第四代编程语言、代码生成器和面向对象技术”[[14]](#Ch009_459-508_B9780443187346000088.xhtml#bb0075)。

## 原型法

原型法是一种迭代方法，将项目分解为较小的任务，创建系统设计特性的多个模型（原型）。这通过允许客户在最终产品完成前很久就看到逼真的结果来降低风险。与其他现代开发方法一样，客户参与度很高：客户检查原型以确保项目按计划进行并达到其目标。

“原型”一词可能有点误导：后期阶段的原型可能被用作实际的最终产品。原型可以被视为“工作模型”。原型法不是一个成熟的软件开发方法论：它被螺旋模型或 RAD 等其他迭代方法所使用。

## DevOps

传统软件开发是在开发人员、质量保证团队和生产团队之间严格分离职责的情况下进行的。开发人员拥有镜像生产模型的硬件和测试数据。他们将代码移交给质量保证团队，后者也拥有镜像生产模型的硬件以及测试数据。质量保证团队随后将测试过的代码移交给生产团队，后者拥有生产硬件和真实数据。

在旧的（不那么敏捷的）模型中：开发人员与生产环境没有直接接触，实际上通过职责分离被严格隔离在生产环境之外。

DevOps 是一种更敏捷的开发和支持模型，呼应了我们在本章前面了解到的敏捷编程方法，包括 Sashimi 和 Scrum。DevOps 是“运维和开发工程师共同参与整个服务生命周期的实践，从设计、开发过程到生产支持”[[15]](#Ch009_459-508_B9780443187346000088.xhtml#bb0080)。

## DevSecOps

DevSecOps 是一种将信息安全集成到开发过程中的敏捷方法。安全贯穿每一步。DevSecOps 宣言概述了目标：

*   **主动介入** 胜过 **总是说“不”**
*   **数据与安全科学** 胜过 **恐惧、不确定性和怀疑**
*   **开放贡献与协作** 胜过 **仅限安全需求**
*   **带有 API 的可用安全服务** 胜过 **强制安全控制与文书工作**
*   **业务驱动的安全评分** 胜过 **橡皮图章式安全**
