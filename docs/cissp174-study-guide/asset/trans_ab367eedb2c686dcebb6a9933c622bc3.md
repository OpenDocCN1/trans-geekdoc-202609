

# UDP

UDP 是用户数据报协议，是 TCP 更简单、更快的“表亲”。UDP 没有握手、会话或可靠性保证：因此它非正式地被称为“发送后祈祷”。与 TCP 默认 20 字节的头部相比，UDP 拥有更简单、更短的 8 字节头部（如 [图 5.9](#Ch005_225-293_B9780443187346000039.xhtml#f0050) 所示）。UDP 头部字段包括源 IP、目的 IP、数据包长度（头部和数据）以及一个简单的（且可选的）校验和。如果使用校验和，它将为 UDP 头部和数据提供有限的完整性保护。与 TCP 不同，数据通常会立即传输，在第一个 UDP 数据包中完成。UDP 工作在第 4 层。

[图 5.9](#Ch005_225-293_B9780443187346000039.xhtml#B-f0050) UDP 头部 [\[7\]](#Ch005_225-293_B9780443187346000039.xhtml#bb0040)。

UDP 通常用于“可容忍丢包”的应用程序（能够处理一定的数据包丢失），例如流式音频和视频。它也用于查询-响应应用程序，例如 DNS 查询。

## ICMP

ICMP 是互联网控制消息协议，一种辅助协议，用于辅助第 3 层（IP，参见注释）。ICMP 用于排查故障和报告错误状况：如果没有 ICMP 协助，IP 在面对路由环路、端口、主机或网络宕机等情况时将会失败。与 TCP 和 UDP 不同，ICMP 没有端口的概念，而是使用类型和代码。常用的 ICMP 类型包括回显请求和回显应答（用于 ping）以及传输过程中生存时间超时（用于 traceroute）。

> **注意**
>
> “哪个协议运行在哪一层”通常是激烈争论的主题。我们称之为“归桶游戏”。例如，ICMP 应该归入哪个桶：第 3 层还是第 4 层？ICMP 头部位于第 4 层，就像 TCP 和 UDP 一样，所以许多人会回答“第 4 层”。另一些人则认为 ICMP 是第 3 层协议，因为它协助 IP（一种第 3 层协议），且没有端口。
>
> 这表明归桶游戏是多么随意：抓包显示 ICMP 头部位于第 4 层，因此许多网络工程师倾向于回答“第 4 层”：永远不要与数据包争辩。许多路由协议也存在同样的争论：例如，BGP 用于第 3 层路由，但 BGP 本身由 TCP（和 IP）承载。本书将在正文和自测题中引用界限分明的归桶游戏协议/层，但避开模糊不清的例子（正如考试所应做的那样）。

### Ping

*Ping*（得名于用于“探测”潜艇的声纳）向节点发送 ICMP 回显请求并监听 ICMP 回显应答。Ping 的设计目的是确定节点是启动还是关闭。

在 ARPAnet 或早期互联网上，当防火墙不常见（或不存在）时，Ping 是节点状态的可靠指示器。如今，ICMP 回显应答是节点处于启动状态的一个相当可靠的指示器。攻击者利用 ICMP 绘制目标网络拓扑，因此许多站点会过滤诸如回显请求和回显应答之类的 ICMP 类型。

无应答的 ping（发出 ICMP 回显请求但未收到回显应答）并不意味着主机已关闭。节点可能已关闭，也可能节点已启动，但回显请求或回显应答可能在某处被过滤了。

### Traceroute

*traceroute* 命令利用 ICMP 时间超时消息来追踪网络路由。正如在讨论 IP 时所述，生存时间字段用于避免路由环路：每当数据包经过一个路由器，路由器就会递减 TTL 字段。如果 TTL 降为零，路由器将丢弃该数据包，并向原始发送者发送一个 ICMP 时间超时消息。

Traceroute 巧妙地利用了这一 TTL 特性。假设客户端距离服务器四跳：客户端的 traceroute 客户端发送一个 TTL 为 1 的数据包给服务器。路由器 A 将 TTL 递减为 0，丢弃数据包，并向客户端发送一个 ICMP 时间超时消息。路由器 A 由此被识别。

随后客户端发送一个 TTL 为 2 的数据包给服务器。路由器 A 将 TTL 递减为 1 并将数据包转发给路由器 B。路由器 B 将 TTL 递减为 0，丢弃数据包，并向客户端发送一个 ICMP 时间超时消息。路由器 B 由此被识别。此过程持续进行，直到到达服务器，如 [图 5.10](#Ch005_225-293_B9780443187346000039.xhtml#f0055) 所示，从而识别出路径上的所有路由器。

# 应用层 TCP/IP 协议与概念

TCP/IP 应用层存在大量协议，该层融合了 OSI 模型的会话层、表示层和应用层。

## Telnet

Telnet 提供网络上的终端仿真。“终端”意指基于文本的 VT100 风格终端访问。Telnet 服务器监听 TCP 端口 23。Telnet 曾是通过网络访问交互式命令 Shell 的标准方式，延续了 20 多年。

Telnet 的弱点在于它不提供机密性；Telnet 会话期间传输的所有数据均为明文，包括用于向系统认证的用户名和密码。能够嗅探网络流量的攻击者可通过这种方式窃取认证凭据。

Telnet 也只有有限的完整性：拥有网络写入权限的攻击者可以篡改数据，甚至劫持 Telnet 会话。安全 Shell（SSH）提供安全认证、机密性和完整性，是 Telnet 的推荐替代品。

## FTP

FTP 是文件传输协议，用于向服务器传输文件或从服务器下载文件。与 Telnet 一样，FTP 既无机密性也无完整性，不应用于通过不安全信道传输敏感数据。

> **注意**
>
> 当讨论 Telnet 和 FTP 等不安全协议时，“无机密性”这类陈述假设它们使用默认设置，且未进行额外加固或加密（例如通过 IPsec VPN 隧道使用它们）。您可以通过在加密 VPN 隧道上运行 Telnet 或 FTP，或用 SSH 替代它们等方式来缓解缺乏机密性的问题。此外，“无完整性”意味着应用层几乎没有或完全没有完整性保护：某些完整性可能由较低层（如传输层）提供。

FTP 使用两个端口：控制连接（发送命令的地方）是 TCP 端口 21；“主动 FTP”使用的数据连接（传输数据的地方）源自 TCP 端口 20。以下是两个套接字对（接下来的两个示例使用任意临时端口）：

*   客户端:1025 → 服务器:21（控制连接）
*   服务器:20 → 客户端:1026（数据连接）

请注意，数据连接源自服务器，方向与控制通道相反。这打破了经典的客户端-服务器数据流向。因此，许多防火墙会阻断主动 FTP 的数据连接，导致主动 FTP 失效。被动 FTP 通过保持所有通信均从客户端发向服务器来解决此问题：

*   客户端:1025 → 服务器:21（控制连接）
*   客户端:1026 → 服务器:1025（数据连接）

FTP 服务器告知客户端要连接的监听数据连接端口；客户端随后发起第二个连接。被动 FTP 更有可能顺利穿越防火墙，因为它符合经典的客户端-服务器流向。
