
# 安全架构与工程

安全架构与工程领域是考试将旧版 10 个领域的概念重新排序并合并为当前 8 个领域的一个典型例子。该领域包含了三个以前独立领域的大量内容：安全架构、密码学和物理安全。因此，该领域规模相当大，内容丰富。

正如[第 1 章](#Ch001_1-10_B9780443187346000040.xhtml)“简介”中所述，新的顺序并不总是符合逻辑流程，但这对考试成功并不重要。最终你将面对来自所有 8 个领域的问题，且问题不会明显引用其来源领域。

本领域从安全设计原则开始，包括威胁建模、纵深防御、零信任等。随后是安全架构概念，包括安全模型，以及硬件和软件中的安全系统组件。接下来是密码学，包括对称加密、非对称加密和哈希函数的核心概念。最后，我们将讨论物理安全，了解人员安全至上。

## 安全设计原则

我们将首先讨论安全设计原则，重点介绍保护系统的现代方法。旧式的“城堡围墙”设计（坏东西在外面，好东西在里面）已过时，且往往难以抵御现代对手。零信任是现代防御的关键组成部分，我们稍后将讨论。

### 威胁建模

威胁建模旨在正式描述系统可用的各种攻击向量，并有助于规划部署适当的缓解措施。OWASP 对威胁建模的描述如下：

> *威胁建模旨在识别、沟通和理解威胁及缓解措施，背景是在保护有价值资产的语境下。*
>
> *威胁模型是影响应用程序安全的所有信息的结构化表示。从本质上讲，它是通过安全视角审视应用程序及其环境的一种视图。*
>
> *威胁建模可应用于广泛的事物，包括软件、应用程序、系统、网络、分布式系统、物联网设备和业务流程。*
>
> *威胁模型通常包括：*
>
> *   *待建模主题的描述*
> *   *可在威胁形势变化时进行检查或质疑的假设*
> *   *系统面临的潜在威胁*
> *   *可针对每个威胁采取的缓解措施*
> *   *验证模型和威胁的方法，以及验证所采取行动成效的方法* [\[1\]](#Ch004_107-223_B9780443187346000076_2.xhtml#bb0010)。

### 最小权限与纵深防御

如前所述，最小权限意味着用户应仅被授予完成其工作所需的最低访问权限（授权），不能更多。知情需要比最小权限粒度更细：用户在访问特定信息前，必须有知晓该特定信息的必要性。纵深防御（也称为分层防御）应用多种保障措施（也称为控制：为降低风险而采取的措施）来保护资产。任何单一安全控制都可能失效；通过部署多重控制，可提高数据的机密性、完整性和可用性。

### 安全默认值

安全默认值（也称为默认安全）意味着操作系统和应用程序以安全状态部署。历史上，操作系统通常以（有时）高度不安全的状态部署，安装后需要进行加固。

例如：在 20 世纪 90 年代，Unix 和 Linux 系统通常默认启用十几个监听网络服务。由于这些系统*默认不安全*，系统管理员随后会通过禁用不必要的服务来加固系统。这引出一个问题：既然服务是不必要的，为什么默认启用它们？大多数 Linux 发行版现在采用安全默认值：Ubuntu Linux 22.04（桌面版）默认零监听网络服务。甚至 OpenSSH 守护进程默认也不安装（尽管在大多数服务器发行版上会自动安装）。

### 隐私设计

隐私设计与安全默认值类似，顾名思义，侧重于隐私。历史上，许多隐私控制（如手机上的控制）默认禁用，要求用户选择退出共享数据给广告商等做法。隐私设计要求此类控制默认启用，允许用户选择加入共享数据给广告商（如果他们愿意）。

德勤将隐私设计描述为“一个基于主动将隐私嵌入 IT 系统、网络基础设施和业务实践的设计与运营中的框架”[\[2\]](#Ch004_107-223_B9780443187346000076_2.xhtml#bb0015)，并阐述了隐私设计的七大基础原则：

1.  **主动而非被动——预防而非补救**
    *   在入侵性事件发生前预判、识别并预防；这意味着事前采取行动，而非事后。
2.  **以隐私作为默认设置**
    *   确保个人数据在所有 IT 系统或业务实践中自动受到保护，无需任何个人采取额外行动。
3.  **将隐私嵌入设计**
    *   隐私措施不应是附加组件，而应是系统的完全集成组件。
4.  **保持全功能（正和，而非零和）**
    *   隐私设计采用“双赢”方法实现所有合法的系统设计目标；即隐私和安全都很重要，无需做出不必要的权衡即可两者兼得。
5.  **确保端到端安全**
    *   数据生命周期安全意味着所有数据应按需安全保留，并在不再需要时销毁。
6.  **保持可见性和透明度——公开透明**
    *   向利益相关者保证业务实践和技术按目标运行，并接受独立验证。
7.  **尊重用户隐私——以用户为中心**
    *   保持以用户为中心；个人隐私利益必须由强有力的隐私默认值、适当的通知和用户友好的选项来支持 [\[2\]](#Ch004_107-223_B9780443187346000076_2.xhtml#bb0015)。

### 安全失效

顾名思义，安全失效意味着系统在发生故障时保持安全状态。设想一栋配有电子锁的建筑：发生停电时，门锁应在断电时保持锁定，还是解锁？安全失效要求它们保持锁定。

UNIX/Linux 系统使用 `fsck` 命令（文件系统检查）来修复受损磁盘。重启后，`fsck` 可检查受损磁盘扇区，并尝试自动修复。若修复失败，许多系统将在控制台终端打开一个 root（超级用户）会话（无需认证）。这是设计使然：若磁盘受损，认证可能变得不可能（因登录程序损坏、密码文件损坏等）。这是不安全失效的一个例子：安全失效将在所有情况下要求认证。

### 职责分离

正如我们将在[第 8 章](#Ch008_361-457_B9780443187346000064_1.xhtml)“领域 7：安全运营”中讨论的，职责分离要求多人共同完成关键或敏感交易。职责分离的目标是确保要想滥用对敏感数据或交易的访问权限，必须说服另一方共同行动。串通是指双方密谋破坏交易安全的行为。职责分离的经典动作电影案例涉及两把钥匙、一艘核潜艇和一名叛变舰长。
