

# 瀑布模型

`Waterfall Model`（瀑布模型）是一种线性的应用开发模型，使用严格的阶段；当一个阶段结束时，下一个阶段开始。瀑布模型早于软件设计，最早用于制造业。1969年，它首次被用于描述软件开发过程，当时大型软件项目已变得过于复杂，无法使用非正式方法进行设计。步骤按顺序发生，未修改的瀑布模型不允许开发人员返回之前的步骤。之所以称之为瀑布，是因为它模拟水流向下：无法回流向上。

Winston W. Royce博士在《大型软件系统开发管理》（"Managing the Development of Large Software Systems"）中首次结合软件开发描述了瀑布模型（参见 [http://leadinganswers.typepad.com/leading_answers/files/original_waterfall_paper_winston_royce.pdf](http://leadinganswers.typepad.com/leading_answers/files/original_waterfall_paper_winston_royce.pdf)）。Royce的未修改瀑布模型（无迭代，有时称为“阶段式”）如[图 9.2](#Ch009_459-508_B9780443187346000088.xhtml#f0015)所示，包含以下步骤：系统需求、软件需求、分析、程序设计、编码、测试和运维。

![图 9.2 未修改的瀑布开发模型 [7]。](images/B9780443187346000088/f09-02-9780443187346.jpg)

[图 9.2](#Ch009_459-508_B9780443187346000088.xhtml#B-f0015) 未修改的瀑布开发模型 [[7]](#Ch009_459-508_B9780443187346000088.xhtml#bb0040)。

Royce的论文未使用“瀑布”一词，但描述了该过程。未修改的瀑布模型不允许迭代：即返回之前的步骤。这给早期步骤带来了沉重的规划负担。此外，由于每个后续步骤要等到前一步骤结束才能开始，早期步骤的任何延迟都会级联传递到后续步骤。

具有讽刺意味的是，Royce的论文是在批评该模型。关于[图 9.2](#Ch009_459-508_B9780443187346000088.xhtml#f0015)所示模型，“上述实现充满风险，招致失败” [[7]](#Ch009_459-508_B9780443187346000088.xhtml#bb0040)。在现实世界中，需要迭代：通常不现实禁止返回之前的步骤。Royce提出了在测试阶段发现根本设计错误的问题：“测试阶段发生在开发周期末尾，这是首次将时序、存储、输入/输出传输等作为实际体验而非分析对象的事件。这些现象无法精确分析……然而，如果这些现象未能满足各种外部约束，则不可避免地需要进行大规模重新设计” [[7]](#Ch009_459-508_B9780443187346000088.xhtml#bb0040)。许多后续的软件设计模型被称为迭代模型：它们明确设计为允许迭代，即返回之前的步骤。

> **考试警告**
>
> Royce未修改瀑布模型的具体阶段名称不可考：请掌握整体流程。此外，Royce遗漏了一个关键的最终步骤：销毁。任何导致包含敏感生产数据的操作系统投入运行的开发过程，在该系统退役、数据归档、以及这些物理系统上剩余数据被安全销毁之前，都不算真正完成。

Royce描述了一个修改后的瀑布模型，允许返回前一阶段进行验证或确认，理想情况下仅限于相邻步骤。Barry Boehm的论文《软件开发与改进的螺旋模型》（"A Spiral Model of Software Development and Enhancement"，见下文“螺旋模型”部分）展示了一个基于Royce论文的修改后瀑布模型，如[图 9.3](#Ch009_459-508_B9780443187346000088.xhtml#f0020)所示。

![图 9.3 修改后的瀑布开发模型 [8]。](images/B9780443187346000088/f09-03-9780443187346.jpg)

[图 9.3](#Ch009_459-508_B9780443187346000088.xhtml#B-f0020) 修改后的瀑布开发模型 [[8]](#Ch009_459-508_B9780443187346000088.xhtml#bb0045)。

其他人提出了类似的修改或扩展瀑布模型。Sashimi模型（鱼片模型）基于（并作为对……的反应）瀑布模型。

> **注意**
>
> 未修改的瀑布模型不允许回退。修改后的瀑布模型至少允许回退一步。

## Sashimi模型（鱼片模型）

`Sashimi Model`（鱼片模型）具有高度重叠的步骤；可将其视为瀑布模型在现实世界中的继任者（有时称为Sashimi瀑布模型）。其名称源自日本美食“刺身”，其特点是鱼片层层重叠（这也是考试的一个提示）。该模型基于富士施乐使用的硬件设计模型：“商业学者和从业者在询问：‘日本制造商显著成功的关键因素是什么？’以及‘他们的竞争优势来源是什么？’Sashimi系统似乎给出了这些问题的答案。” [[9]](#Ch009_459-508_B9780443187346000088.xhtml#bb0050)

Peter DeGrace在其著作《棘手的问题，正义的解决方案：现代目录》（*Wicked Problems, Righteous Solutions: A Catalogue of Modern Software*）中结合软件开发描述了Sashimi。Sashimi的步骤与瀑布模型相似；区别在于显式的重叠，如[图 9.4](#Ch009_459-508_B9780443187346000088.xhtml#f0025)所示。

## 敏捷软件开发

`Agile Software Development`（敏捷软件开发）是作为对瀑布模型等僵化软件开发模型的反应而演变而来的。敏捷方法包括`Scrum`（Scrum）和`Extreme Programming`（极限编程，XP）。敏捷宣言（参见 [http://agilemanifesto.org/](http://agilemanifesto.org/)）指出：

> “我们通过实践并帮助他人实践，发掘出更好的软件开发方法。通过这项工作，我们开始重视：
>
> *   **个体和互动** 高于 流程和工具
> *   **可工作的软件** 高于 详尽的文档
> *   **客户协作** 高于 合同谈判
> *   **响应变化** 高于 遵循计划” [[11]](#Ch009_459-508_B9780443187346000088.xhtml#bb0060)

敏捷体现了许多现代开发概念，包括更大的灵活性、以较小里程碑实现快速周转、团队内部的强沟通以及更多的客户参与。

### Scrum

`Scrum`开发模型（以橄榄球运动中的“争球”命名）是一种敏捷模型，最早由Hirotaka Takeuchi和Ikujiro Nonaka在《新新产品开发游戏》（"The New New Product Development Game"）中结合产品开发进行描述；他们指出：“停止接力赛，改打橄榄球” [[12]](#Ch009_459-508_B9780443187346000088.xhtml#bb0065)。“接力赛”指瀑布模型，即团队在步骤完成后将工作移交给其他团队。他们建议：“相反，整体或‘橄榄球’式方法——团队作为一个整体尝试全程推进，来回传球——可能更好地满足当今的竞争要求” [[12]](#Ch009_459-508_B9780443187346000088.xhtml#bb0065)。

Peter DeGrace（因Sashimi而知名）结合软件开发描述了（并命名了）Scrum。Scrum包含小型开发团队，称为`Scrum Team`（Scrum团队）。`Scrum Master`（Scrum主管）是组织中的资深成员，像教练一样为团队提供支持。最后，`Product Owner`（产品负责人）是业务部门的代言人。
