

# 要有效管理安全事件，必须执行根因分析

根因分析旨在确定导致事件发生的潜在弱点或漏洞。如果没有成功的根因分析，受害组织恢复系统的方式可能仍包含导致事件的对手所利用的特定弱点。除了可能恢复带有可利用缺陷的系统外，另一种可能性是从已被攻陷的备份或快照重建系统。

## 运营预防和检测控制

许多预防和检测控制需要更高的运营支持，是日常运营安全的重点。例如：路由器和交换机往往具有相对较低的运营支出（OPEX）。其他控制，如 NIDS 和 NIPS、防病毒软件和应用程序白名单，具有相对较高的运营支出，是本领域的重点。

### 防火墙

防火墙过滤网络间的流量。TCP/IP 包过滤器和状态检测防火墙基于第 3 层和第 4 层（IP 地址和端口）做决策。代理防火墙也可以基于第 5-7 层做决策。防火墙是多宿主的：它们拥有连接到多个不同网络的多个 NIC。

#### 包过滤器

`packet filter` 是一种简单快速的防火墙。它没有“状态”概念：每个过滤决策必须基于单个数据包做出。无法参考过去的数据包来做出当前决策。

缺乏状态使得包过滤防火墙安全性较低，特别是对于无会话协议（如 UDP 和 ICMP）。为了通过防火墙允许 ping，必须独立允许 ICMP 回显请求和回显应答：防火墙无法将之前的请求与当前的应答匹配。通常允许所有回显应答，基于的假设是之前必定存在匹配的回显请求。

[图 8.5](#Ch008_361-457_B9780443187346000064_1.xhtml#f0030) 所示的包过滤防火墙允许出站 ICMP 回显请求和入站 ICMP 回显应答。计算机 1 可以 ping 通 `bank.example.com`。问题在于：位于 `evil.example.com` 的攻击者可以发送未经请求的回显应答，防火墙将予以允许。

![Fig. 8.5 Packet filter firewall design.](images/B9780443187346000064/f08-05-9780443187346.jpg)

[图 8.5](#Ch008_361-457_B9780443187346000064_1.xhtml#B-f0030) 包过滤防火墙设计。

基于 UDP 的协议存在类似问题。DNS 对小查询使用 UDP 端口 53，因此包过滤器通常允许所有 UDP DNS 应答，假设之前必定存在匹配的请求。

#### 状态检测防火墙

`Stateful firewalls` 拥有状态表，允许防火墙将当前数据包与之前的数据包进行比较。状态检测防火墙比包过滤器慢，但安全得多。

在 [图 8.6](#Ch008_361-457_B9780443187346000064_1.xhtml#f0035) 中，计算机 1 向 `bank.example.com` 发送 ICMP 回显请求。防火墙配置为允许 ping 互联网站点，因此状态检测防火墙允许该流量，并在其状态表中添加一条记录。

![Fig. 8.6 Stateful firewall design.](images/B9780443187346000064/f08-06-9780443187346.jpg)

[图 8.6](#Ch008_361-457_B9780443187346000064_1.xhtml#B-f0035) 状态检测防火墙设计。

随后在 [图 8.6](#Ch008_361-457_B9780443187346000064_1.xhtml#f0035) 中，从 `bank.example.com` 向计算机 1 接收到一个回显应答。防火墙检查是否允许该流量（允许），然后检查状态表中是否有反方向的匹配回显请求。防火墙找到匹配条目，将其从状态表中删除，并放行该流量。

接着 `evil.example.com` 发送一个未经请求的 ICMP 回显应答。[图 8.6](#Ch008_361-457_B9780443187346000064_1.xhtml#f0035) 所示的状态检测防火墙发现没有匹配的状态表条目，从而拒绝该流量。

#### 代理防火墙

`Proxies` 是预防性设备，可以被视为一种类型的防火墙，且历史上一直如此。代理作为中间服务器运行，内联部署在客户端和目标服务器之间。包过滤器和状态检测防火墙要么放行流量要么拒绝流量：它们只是路由途中的另一跳。TCP 三次握手发生在客户端和服务器之间，并由包过滤器或状态检测防火墙转发。

然而，代理实际上会**终止**连接，而不仅仅是在流量遍历设备时进行检查。[图 8.7](#Ch008_361-457_B9780443187346000064_1.xhtml#f0040) 展示了计算机 1 到 `bank.example.com` 的 TCP Web 流量通过状态检测防火墙和代理的区别。状态检测防火墙在计算机 1 和 `bank.example.com` 之间转发一个 TCP 三次握手。包过滤器也会执行相同操作。

![Fig. 8.7 Stateful inspection vs. proxy.](images/B9780443187346000064/f08-07-9780443187346.jpg)

[图 8.7](#Ch008_361-457_B9780443187346000064_1.xhtml#B-f0040) 状态检测 vs. 代理。

多年来存在各种类型的代理和代理防火墙。这些通常根据它们对网络流量可见性的深度进行分类。电路级代理（最常与 SOCKS 关联）工作在第 5 层（会话层），而应用级代理工作在第 7 层。

代理实际上终止来自计算机 1 的 TCP 连接，并发起与 `bank.example.com` 的 TCP 连接。在这种情况下，有两次握手：计算机 1 → 代理，以及代理 → `bank.example.com`。

像 NAT 一样，代理隐藏连接的来源。在 [图 8.7](#Ch008_361-457_B9780443187346000064_1.xhtml#f0040) 的下半部分，连接到 `bank.example.com` 的源 IP 地址属于防火墙，而非计算机 1。

#### 下一代防火墙 (NGFW)

NGFW（下一代防火墙）工作在第 7 层。与仅基于第 3 层和第 4 层做决策的包过滤器和状态检测防火墙不同，NGFW 除了第 3 层和第 4 层外，还可以基于应用层数据（如 HTTP 或 DNS 流量）做过滤决策。这一看似简单的区别提供了针对现代威胁极大改进的防护能力。凭借增强的可见性，NGFW 可以结合网络入侵检测系统（NIDS）采用的第 7 层过滤和检测方法，以及其预防性对应物网络入侵防御系统（NIPS），后者将在本章后面讨论。

许多 NGFW 提供动态确定所用第 7 层协议的能力，无论通信发生在哪个端口上。此能力可用于识别可能将一种第 7 层协议通过该协议不常用的 TCP 端口进行隧道传输的对手流量。设想对手在受感染的内部资产上实例化一个出站 SSH 隧道，通常使用 TCP 端口 22，但通过 TCP 端口 443 传输。缺乏第 7 层可见性的包过滤器和状态检测防火墙会假定目标 TCP 443 的流量是 HTTPS，因为它们缺乏判断其他情况的可见性。

NGFW 的功能已远远超出防火墙的传统范围，包含传统上在独立产品中才有的安全功能。潜在的扩展功能集，包括 Web 内容过滤、沙箱、反恶意软件、威胁情报和 HTTPS 解密等能力，可使组织潜在地降低在单独设备中维护这些功能的总体成本。
