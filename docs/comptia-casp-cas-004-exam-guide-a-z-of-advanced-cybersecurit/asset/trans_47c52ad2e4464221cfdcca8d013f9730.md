# 应用程序安全设计考量

基于 Web 的应用程序无处不在；这些应用程序旨在使用 Web 服务器作为平台，并与用户的浏览器进行响应和通信。由于它们被广泛使用，因此也被广泛攻击。**开放 Web 应用程序安全项目**（**OWASP**）维护着一份 Web 应用程序中发现的十大错误清单。挑战在于，编写使应用程序运行的代码的人，往往不以安全为主要目标。很多时候，存在将应用程序推向市场的匆忙心理。以下部分探讨安全设计、安全默认和安全部署的概念。

## 安全：设计时、默认时、部署时

应用程序应做到设计时安全、默认时安全和部署时安全，具体讨论如下：

- **安全设计**：这意味着应用程序在设计之初就考虑了安全性，而非事后补救。如果你将应用程序安全系统的细节告知某人，而该人仍无法攻破该安全性，则该应用程序才是真正安全的。应用程序不应依赖黑客缺乏知识这一事实。

- **安全默认**：这意味着在不更改任何默认设置的情况下，应用程序是安全的。例如，某些服务器产品具有特定的安全功能，但必须启用这些服务才能运行，以便该服务不对黑客可用。需要启用安全功能的产品不符合安全默认原则。

- **安全部署**：这意味着从安全角度考虑了引入应用程序的环境。例如，在一台服务器上禁用所有未使用的接口可能是明智的，而在另一台服务器上则可能并不关键。

# 应用程序安全问题

要了解如何保护应用程序，你需要了解面临的威胁。你需要了解许多具体的安全问题和攻击。以下部分调查其中的一些问题。

## 不安全的直接对象引用

应用程序在生成网页时，经常使用对象的实际名称或键。应用程序并不总是验证用户是否被授权访问目标对象。这导致了不安全的直接对象引用缺陷。此类攻击可能来自授权用户，即该用户有权使用该应用程序，但正在访问其不应有权访问的信息。为防止此问题，每个直接对象引用都应进行访问检查，如[图 11.1](#c11.xhtml#fig11_1)所示。（建议也针对这一特定问题进行应用程序代码审查。）

## XSS

**跨站脚本攻击**（**XSS**）发生在攻击者发现网站漏洞并将恶意代码注入 Web 应用程序时。许多网站允许甚至合并用户输入到网页中以定制页面。如果 Web 应用程序未正确验证此输入，可能发生两种情况之一——要么文本将在页面上渲染，要么当其他人访问该网页时脚本可能被执行。[图 11.2](#c11.xhtml#fig11_2) 显示了一个 XSS 攻击：

![](images/Image27036.jpg)

**图 11.2：** XSS 攻击

应对所有输入执行适当的验证以防止此类攻击。这涉及识别所有用户提供的输入并测试所有输出。

## 跨站请求伪造

**跨站请求伪造**（**CSRF**）是一种攻击，它导致最终用户在当前已通过身份验证的 Web 应用程序上执行非预期的操作。与 XSS 不同，CSRF 利用的是网站对浏览器的信任，而非相反。网站认为请求来自用户的浏览器且确实由用户发起。然而，该请求被植入了用户的浏览器中。通常通过用户访问一个已包含待注入代码的 URL 而植入，如[图 11.3](#c11.xhtml#fig11_3)所示：

![](images/Image27046.jpg)

**图 11.3：** CSRF

以下措施有助于防止 Web 应用程序中的 CSRF 漏洞：

- 使用 `URLEncode()` 和 `HTMLEncode()` 等技术，根据输入参数对所有输出进行特殊字符编码，以防止恶意脚本执行。
- 根据特殊字符（那些能使恶意脚本执行的字符）过滤输入参数。
- 根据输入参数对特殊字符过滤输出。

## 点击劫持

使用点击劫持攻击的黑客会在一个看起来合法的页面上制作一个透明的页面或框架，诱使用户点击某处。当用户点击时，实际上点击的是一个不同的 URL。在许多情况下，该网站或应用程序可能会诱使用户输入凭据，这些凭据稍后可能被攻击者利用，如[图 11.4](#c11.xhtml#fig11_4)所示。防止点击劫持的主要责任在于网站所有者。在设计网站应用程序时，使用 `X-FRAME-OPTIONS` 标头来控制网站在框架内的嵌入。此选项应设置为 `DENY`，这几乎能确保点击劫持攻击失败。此外，`X-FRAME` 的 `SAMEORIGIN` 选项可用于限制网站仅在同源网页中被框架化。[图 11.4](#c11.xhtml#fig11_4) 说明了点击劫持：
