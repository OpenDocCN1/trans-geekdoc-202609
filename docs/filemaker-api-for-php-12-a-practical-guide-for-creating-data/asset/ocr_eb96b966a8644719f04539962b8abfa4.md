# Security

Security is a major concern when you create and host your own web site. Especially if you use credit card numbers, social security numbers, HIPAA protected information, or allow the upload of files to your server. Not only do you have to protect your web pages and data, but you have to protect the web server and database server. Fortunately, the physical security of the hardware is easy. All you have to do is lock the hardware in the server room and limit access to authorized personnel. Make sure you install accounts and passwords for the servers for each administrator. Never give your server's Admin password to an internal developer. If someone calls the company you have to delete their account from the server and don't have to worry that your master Admin password has to be changed on all your systems.

# Connection String

As mentioned earlier in the book, every web page has to make a connection to the database by including dbclass.php This file contains the account name and password to connect to the database. You never want this information to fall into the hands of a hacker because it will give them access to your database. This file should not be stored in the root directory of your web site. Keeping it in the root directory runs the risk that someone might be able to download the file and open it. Technically the connection is all hidden within PHP code, which means the web server should never return it as text to a web browser. However for some reason Apache might expose sensitive information. Therefore you should place the connection string inside the outside the root directory. On Apache, you should place it in the C:\inetpub\php folder.

# FileMaker Accounts and Privileges

Your database should have one or more specific Privilege sets and accounts. One account should be for guests, access you may want through the Internet. This will be extremely limited. For example, you may not want Internet users to add or delete records from your database. They are view only users. Another account should be for business purpose internal users that gives them more access to add and delete records and upload files. In elastic, the PHP Privilege Set is only used for web access to access the database. These accounts should have the bare minimum access. When normally do I create the PHP privilege sets to start with absolutely no access to anything — "All no access" for Records, Layouts, Value Lists, Scripts, Others, and Extended Privileges (only access via PHP). Then I go through each item one by one and until only the items that are needed. That way any hacker is able to get the account name and password can only perform tasks that the PHP Privilege Set is designed to do.

# Sanitizing Incoming Data

If you allow users to add, update, or upload files to your database and web server you will need to sanitize or filter the data with PHP code. It is not to trust your internal users. The problem is that they may insert data entry errors, such as a bad date format that will cause the database to throw an error. Hackers on the internet how ever try to insert PHP code, SQL code, links to other web sites with HTML code, insert thousands of garbage records, etc that can damage your web server, database, and even havoc on your site. The worst case scenario comes from uploading viruses to your web site. Even trusted users can unknowingly upload infected files. It's best to limit what type of files are uploaded and scan them out of them folder.

# FileMaker Server Administrator Groups

FileMaker Server 12 has a feature that allows you to enable server access to "power users" so they can administer their own databases. This really offloads a lot of work from the administrator(s) to the group level. You can limit this group to their own specific folder of databases so they do not get on other systems on the server. The Privilege Sets can also limit the group to perform actions on the database, view statistics, and run schedules.
