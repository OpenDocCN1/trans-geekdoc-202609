## Performance Considerations

All system administrators need to know how to tweak the server operating system, the web and/or application server, the database, and their web pages to maximize the performance of their web site. FileMaker Server is adept at handling relatively large, complex web sites. It really doesn't do well when you have thousands of concurrent connections because it's not designed for load balancing outside of the server-side configurations. However, apparently FileMaker has modified their own for internal load balancing, but the database won't scale even to the most developed server. In the past FileMaker could be hosted with a RAC, but that went away with FileMaker Server 7. Now we're stuck with the supplied materials. As I mentioned previously, with today's hardware and the tremendous improvements that FileMaker has made to the product line, your biggest performance problem is going to come from your bandwidth connection to the Internet and the skill in which you program your web pages.

## Minimize the Number of Fields on PHP Layers

When you search the database it will return every single field on the specified layer. Therefore, if you don't display the fields on the web page you have wasted the performance of the database web to process useless information. If you make multiple lists for the same, it's best to use only what you need instead of overwhelming the database to reduce the total number of records in your database. This also lets you filter relevant fields, then display the result from a layout with fewer fields using theSearchResultMethod. We saw how that works in the Quick Find example. In many cases your PHP layout will be accessed by FileMaker Pro clients, so you don't need to do any fancy design work. A simple table will do the trick.

## Minimize the Number of Records (Related) Displayed on PHP

The same applies to portal records with related records as the the. If you don't need to display the records on the web page, the portal should not be on the layout. Related records compound the performance problems. You can have literally hundreds or thousands of records in a portal. When you return the parent record to the browser it's going to return thousands of related records at the same time - except that if you use the related records, you can limit the number of related records that are returned to the web page using the setRelatedFilters Method. In option, if you have more than a handful of related records in any web solution you need to address your design issues first or it'll will be a serious problem.

## Use the setRange Method to Limit the Number of Records Returned to the Browser

Just because you have a table 100,000 records does not mean that you should return 100,000 records to the server. The more records you return to the browser the slower the server and database will respond. It's also confusing to the user have to scroll through so many records. I recommend that you limit the number of records by using the setRange Method to specify the number of records to fetch from the database. This will enable the user to see the number of records from a pop menu choices with 10, 25, 50, and 100 records per page. You should program the number of records to return based on whatever your site uses.

## Limit the Number of FileMaker Pro Connections to Minimum Number of Users

Change the setting on FileMaker Server to max connected users. When I'm a client to query the server I always find that they set the limit to 1000 users "because they can". Because you can doesn't mean that it's the correct setting. FileMaker Server provides 2 threads for each user. If they aren't being the performance of the database is being wasted. How do you know what is right start? By setting the limit to the maximum number of FileMaker Pro licenses that you have. Check the server statistics after a few weeks to a month. Then you'll know the result. It would be good to know how many of our clients with 2500+ employees have more than 50 users on the server. If your FileMaker is only being used to host the database for your web site you are one of the lucky few with a big budget. In this case you probably only need to set the number of connections to the number of database developers, which is probably 1! However most must share their server with other business applications.

## Limit the Maximum Number of Files to the Exact Number of Databases on the Server

This issue is similar to the number of concurrent users to the database. Because you can just because FileMaker Server to host 125 files does not mean that it is the best setting. It simply wastes the performance of the server to have FileMaker main threads that are not being used. Since you don't need to restart FileMaker when you add a new database to the server you can just as easily changing the setting on the file. Realistically, what I do on my servers is to set the number of files to one or two more than the total of files on the server. That way I was scratching my head to figure out why the file didn't open after I uploaded it to the server.

## Disconnect Idle Users.

FileMaker Server is a client-server product. It means that there is a constant connection between the FileMaker Server and the FileMaker Pro clients. If the clients are idle for long periods of time it wastes the performance of the server. You should set the maximum idle time for FileMaker Pro clients to a setting such as one or two hours. I prefer this time range because it gives users enough time to go to a meeting or lunch break. Come back and resume the work. If they are longer than that they will be disconnected automatically. Otherwise your internal security issues will dictate if this needs to be more strict.

This setting has nothing to do with your web server. The web server is not a persistent connection. When a search query is sent by the web server to a database connection opened, the records are found by the database and returned to the web server, then the connection is closed. That's why FileMaker Server only allows 200 concurrent connections from the web server. The process is literally completed in milliseconds. Therefore, 200 concurrent connections can be thousands of concurrent users. If you have a lot of users they will wait in the queue until the server is ready to handle the request.

## Assign FileMaker Server as Much RAM as Possible

In most cases you will assign 64 GB of RAM to FileMaker Server which does not mean that this is the best idea. Again, just because you need enough RAM for the operating system and your web server to operate efficiently, you do have to determine the setting for how frequently you need to flush the cache. Most modern operating systems and processes can flush several gigabytes of RAM in 1 minute, which is the recommended setting. However, if you have a busy web server or a lot of users you can boost the performance of the server by increasing the time interval. The longer the interval, the more RAM you will use. By constantly changing and clearing the caches in RAM, the change will be. This is why you will want to set the flush lower. If the server crashes, rely on the backup schedules to recover from an older copy. You really don't need to assign more RAM to FileMaker Server than the total size of your databases. Anytime the operating system has to dig into Virtual RAM the performance will take a huge hit because Virtual RAM is actually taken from the hard drive, which is the slowest component.

You can turn off the logging for both the database and web server. The logs don't take up space. However, it's just one more for the server to do that may not provide you with the most useful information. You can keep them on for your testing server so you can troubleshoot the web server, database server, and web pages. When you first set up your production server you also keep them for a period of time until you determine that the server is stable. If you encounter any problems you can always turn them back.
