# Layouts

Using the FileMaker API for PHP requires that you have a layout with all the fields that you want to display on a web page. If you remove any fields from the layout web page will break. As with all web applications I don't recommend changing field names or layout names because the changes won't be automatically reflected in the web pages. The good news is that FileMaker Pro users probably won't be accessing your PHP layouts. Therefore, you won't have to create any exotic interfaces. A simple table or form view will probably be more adequate than enough. The php_demof12 file has four layouts. All layout names end with "php". This is for you to know that this is a special layout and no fields should be added or removed without understanding the impact on the web pages. Because it's a sample database, all the major fields for the php_demo table are displayed on the Demo layout. However, this is a sample file, so it's easier for you to use a simple setup layout than have to create each specific layout. There is also a specific layout for the related_data table, the import table, and a Quick Find layout that demonstrates a specific technique for dynamically searching a small set of fields from the Quick Find layout, displaying all the fields from the Demo php layout.

You must create a layout with the fields that you need to display on your web page.

# Portals

I've mentioned this several times, but it's worth mentioning again. The FileMaker API for PHP requires that you have any elements you want to display on the web page on the layout. This also applies to related records and portals. You need to include the portal on the layout with any fields that need to be displayed. Although it may seem awkward at first, you'll see in the lessons that the API makes quick work of displaying and working with related records.
