## Security

Security is a major concern when you create and host your own web site. Especially if you use credit card numbers, social security numbers, HIPAA information, or allow the upload of files to your server. Not only do you have to protect your web pages and data, but you have to protect the server and database. Fortunately, the physical security of the hardware is easy. All you have to do is lock the hardware in server room and limit access to authorized personnel. Make sure you install accounts and passwords for each administrator. If someone calls you have to delete their account from the server and change your master password on all systems.

## Connection String

As mentioned earlier in the book, every web page has to make a connection to the database by including class.php. This file contains the account name and password. You never want this information to fall into the hands of a hacker because it will give them access to your database. This file should not be stored in the root directory of web site. Keeping it in the root directory runs the risk that Apache might expose sensitive information. Therefore, you should place connection string outside the root directory.

## FileMaker Accounts and Privileges

Your database should have one or more specific Privilege sets and accounts. One account should be for guests who may access through the Internet. This will be extremely limited; for example, you may not want Internet users to add or delete records from your database—view only. Another account should be for internal users that gives them more access to add and delete records and upload files. In fact, the Privilege Set is only used for web access to the database. These accounts should have the bare minimum access. Normally I create privilege sets to start with absolutely no access to Records, Layouts, Value Lists, Scripts, Others, and Extended Privileges. Then I go through each item one one until only the items that are needed can perform tasks that the Privilege Set is designed to do.

## Sanitizing Incoming Data

If you allow users to add, update, or upload files to your database and web server you will need to sanitize the data with PHP code. It is not to trust your internal users. The problem is that they may insert data entry errors such as a bad date format that will cause the database to throw an error. Hackers on the internet however try to insert PHP code, SQL code, links to other sites with HTML code, insert thousands of garbage records, etc that can damage your web server, database, and even havoc on site. The worst case scenario comes from uploading viruses to your site. Even trusted users can unknowingly upload infected files. It's best to limit what type of files are uploaded and scan them out of folder.

## FileMaker Server Administrator Groups

FileMaker Server 12 has a feature that allows you to enable server access to "power users" so they can administer their own databases. This really offloads a lot of work from the administrator(s) to the group level. You can limit this group to their own specific folder of databases so they do not get on other systems on the server. The Privilege Sets can also limit the group to perform actions on the database, view statistics, and run schedules.

## Do Not Display Errors

Throughout the image we have reported errors back to the browser to give you a sense of how the code works to trap errors. In reality, when your code or database creates an error you may not want to report it back to the user if it's new. In many cases an error can provide the user with information about your server and the path to sensitive files. A smart hacker can take advantage of this information. Therefore, the best way to make sure that errors are not displayed to the user is to change the display_errors setting in your php.ini file to a value of 0. If you are using a hosted server where they have not configured this setting you can include the following code:

```
ini_set('display_errors', '0');
```

You can find more information about ini_set at http://php.net/manual/en/function.ini-set.php.

## Error Logs

When I write PHP code I'm constantly checking each section of code for errors by loading the web page in a browser. There's nothing worse than trying to write an entire page to find out there's a semicolon or misspelling in the code somewhere and I have to spend several hours to troubleshoot. Sometimes it's so bad that I actually re-write the entire page from scratch because it's simply faster than troubleshooting. It's also helpful to refer to the error logs Apache, IIS, the web publishing engine, or the web publishing core to find out what's going wrong. This is especially true if you are troubleshooting script from your PHP code.

Apache and IIS Server generate an access log and an error log. These text files record every request made to the web server by a. The access log contains information such as the URL, the date, the time, the IP address, the requested files, etc. These logs can be used to help measure the metrics of your site. The error logs record every problem the server has encountered. In a multiple machine deployment, the log files are on the same machine as the FileMaker Server component that generates the log. All log files are located in the Logs folder:
