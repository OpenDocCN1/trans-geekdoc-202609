Anyone who has a database knows about using an auto-generated serial number for the primary for every record. In fact, FileMaker has a built-in feature to create a developer-defined serial number. However, if you are using an ODBC driver you would certainly need to have a serial field. However, the FileMaker API for PHP knows absolutely nothing about your serial number field and won't help you. Try to force it will be very difficult. Instead, FileMaker has a unique RecordID created under the head. The RecordID is also a serial number. However, it cannot be modified or deleted. That's why the FileMaker API for PHP uses this RecordID - it is an absolutely guaranteed method to access the expected record.

So you might be thinking great, I can easily get the Serial from my tables and use the RecordID that's already there. There's a problem with that: I would highly suggest that you change your serial field to the auto-generated, calculated value of Get(RecordID). There are a couple of good reasons for this. In fact, the RecordID is essentially a hidden feature in the FileMaker Pro database. Therefore, if you want to work on it, you can't export it, and there is no specific script step that uses it. However, the API for PHP exposes it so you can use it and create related records based on the RecordID. Second, if you have combined FileMaker and PHP client interfaces you will need to link the primary key (RecordID) to the related record's foreign key. To make it very easy I highly recommend that you use the RecordID for the primary and foreign keys rather than an auto-generated serial number. The only time the RecordID becomes an issue is if you need to import records back into the database for a new record will be different from the imported record. This can severely impact displaying the correct related records.
