Anyone who has a database knows about using an auto-generated serial number for the primary for every record. In fact, FileMaker has a built-in feature to create a developer-defined serial number. However, if you are using an ODBC driver you would certainly need to have a serial field. However, the FileMaker API for PHP knows absolutely nothing about your serial number field and won't help you. Try to force it will be very difficult. Instead, FileMaker has a unique RecordID created under the head. The RecordID is also a serial number. However, it cannot be modified or deleted. That's why the FileMaker API for PHP uses this RecordID - it is an absolutely guaranteed method to access the expected record.

So you might be thinking great, I can easily get the Serial from my tables and use the RecordID that's already there. There's a problem with that: I would highly suggest that you change your serial field to the auto-generated, calculated value of Get(RecordID). There are a couple of good reasons for this. In fact, the RecordID is essentially a hidden feature in the FileMaker Pro database. Therefore, if you want to work on it, you can't export it, and there is no specific script step that uses it. However, the API for PHP exposes it so you can use it and create related records based on the RecordID. Second, if you have combined FileMaker and PHP client interfaces you will need to link the primary key (RecordID) to the related record's foreign key. To make it very easy I highly recommend that you use the RecordID for the primary and foreign keys rather than an auto-generated serial number. The only time the RecordID becomes an issue is if you need to import records back into the database for a new record will be different from the imported record. This can severely impact displaying the correct related records.

# Layouts, Not Table Access

For those of you who have experience with ASP or JSP you are well accustomed to using SQL to retrieve data from tables and joining tables. I hate to run on your parade, the FileMaker API for PHP does not give you that kind of access to the database. You have to create a specific layout for your web page that includes all the bells and whistles that you might need, such as value lists attached to the fields and portals. The real problem with this scenario is that a single layout may force you to expose extra fields and records, which will dramatically impact the performance of your web application. Therefore, the only way to improve performance is to create PHP workflow layouts that have only the fields and portals you need to display on your web pages. Of course, more layouts also mean more system management and more documentation. The good news is that FileMaker clients won't access your PHP layouts. Therefore, you probably don't need to create an extensive user interface. Just the fields and portals will give you the opportunity to do things such as put development and name the layout something specific as "Contact php" and to never ever delete the layout unless you want to break your PHP pages. I also suggest that you have all your PHP layouts organized into a single folder FileMaker Pro as an additional reminder to developers to be incredibly careful when making changes to any database content related to PHP.

Changes to your layouts, value lists, tables, and scripts will break your PHP pages. If you make changes to your database you will have to update your PHP web pages.

# Naming Conventions

Naming conventions for fields are not only important for FileMaker Pro, but also for PHP. Web pages tend to be a lot more fickle when it comes to special characters, whereas FileMaker lets you get away with them. Standard web conventions state that you should name fields using a-z, 0-9, underscore, and no special characters such as periods, spaces, or high ASCII characters such as "??. The field name should start with a letter rather than a number or underscore. For example, use "FirstName", not "First Name". Notice that I used an uppercase letter to start each word to make reading the field name easier.
