
![Figure 15.6 The ReLU activation function. For values equal or less than 0, the function is constant at 0, whereas for values greater than 0, the slope of the function is equal to 1.Return to text.⏎](images/fig15.6.jpg)

*Figure 15.6* The `ReLU` activation function. For values equal or less than 0, the function is constant at 0, whereas for values greater than 0, the slope of the function is equal to 1.[Return to text.⏎](#c15.xhtml#re_f15.6)

We can see that the `ReLU` “cuts out” values less than 0 but activates values greater than 0 in a steady “ramp” fashion. One benefit of the `ReLU` function is that the function and its derivatives are very easily implemented at a relatively low computational cost ([Lederer, 2021](#ref.xhtml#re_CIT000213)).

For all of its advantages, there is nonetheless a weakness with `ReLU`. The problem is if initialized weights are large and negative such may translate into many `ReLU` nodes being *inactive* during a big part of the training process, which can make it difficult or impossible for the algorithm to learn increasingly complex models. That is, there is no information going into the network for values less than 0 since they are set to equal 0 by default of the way the function defines negative values. This is known in the literature as the `dead ReLU` problem. It is a version of the *vanishing gradient problem* (Dubey et al., [2022](#ref.xhtml#re_CIT000092); [Lederer, 2021](#ref.xhtml#re_CIT000213)). Possible solutions to the problem include choosing a lower learning rate or replacing `ReLU` by `leakyReLU`, which we now discuss.545

### 15.5.3.2 LeakyReLU

The `leakyReLU` is given by (where weight `a` = 0.01 is featured)

$$L{Re}LU\\left( x \\right) = \\left\\{ \\begin{array}{l} {x,\\,\\,\\,\\,\\,\\,\\,\\,\\,\\,\\,\\,\\,\\,\\,\\,\\,\\, x \\geq 0} \\\\ {0.01\\left( x \\right),\\,\\,\\,\\,\\, x < 0} \\\\ \\end{array} \\right.$$  

(15.7)

A comparison of `ReLU` vs. `leakyReLU` appears in [Figure 15.7](#c15.xhtml#f15.7).

![Figure 15.7 ReLU (left) vs. leakyReLU (right). The leakyReLU slopes downward for values less than zero instead of remaining constant at zero as with the ReLU.Return to text.⏎](images/fig15.7.jpg)

*Figure 15.7* `ReLU` (left) vs. `leakyReLU` (right). The `leakyReLU` slopes downward for values less than zero instead of remaining constant at zero as with the `ReLU`.[Return to text.⏎](#c15.xhtml#re_f15.7)

We see that instead of the function being equal to 0 for all values less than 0, as was the case for `ReLU`, `leaky ReLU` will simply equal some very small negative number instead of the constant zero. This translates to a small negative slope for values less than 0. Consequently, the range of `leakyReLU` is (−∞,∞) instead of \[0,∞) as it is for `ReLU`. This allows for updates for values less than 0 and avoids the vanishing gradient problem ([Alpaydin, 2020](#ref.xhtml#re_CIT000009)). As Dubey et al. ([2022](#ref.xhtml#re_CIT000092)) note, a problem with `leakyReLU` is in determining the correct slope for negative inputs, as different slopes may be appropriate or most relevant for different types of problems. The `parametric ReLU` (`PReLU`) attempts to rectify this by considering negative inputs as a training parameter, however this can lead to overfitting. See Dubey et al. ([2022](#ref.xhtml#re_CIT000092)) for details.

Another activation function that attempts to improve on the `ReLU` is the `elu`, or *exponential linear unit*, which is a smooth function and thus has an advantage over `ReLU`:

$$elu\\left( x \\right) = \\left\\{ \\begin{array}{l} {x,\\,\\,\\,\\,\\,\\,\\,\\,\\,\\,\\,\\,\\,\\,\\,\\,\\,\\,\\,\\,\\, x \\geq 0} \\\\ {\\alpha\\left( e^{x} - 1 \\right),\\,\\,\\,\\,\\, x < 0} \\\\ \\end{array} \\right.$$  

(15.8)

In `elu`, `α` is a trainable hyperparameter in `α(e^(x)-1)`. While `elu` has shown positive results, its theoretical backing is lacking ([Basirat & Roth, 2019](#ref.xhtml#re_CIT000022)). A variant of `elu` is `selu`, where the “*s*” stands for “*scaled*” and constrains the slope larger than one for positive inputs (Dubey et al., [2022](#ref.xhtml#re_CIT000092); [Lederer, 2021](#ref.xhtml#re_CIT000213)).

## 15.5.4 Which Activation Function to Use?

As discussed at the outset of our review of activation functions, according to [Lederer (2021)](#ref.xhtml#re_CIT000213), `softsign` and `ReLU` (or `leakyReLU`) should be the preferred activation functions in practice. According to [Basirat](#ref.xhtml#re_CIT000022) and Roth (2019), most deep learning approaches use `ReLU` largely due to its simplicity and reliability. [Izenman (2008)](#ref.xhtml#re_CIT000167) notes that algorithms that feature the `tanh` function generally tend to converge more rapidly than those featuring the logistic, however the `tanh` itself has been found to be computationally inefficient (Dubey et al., [2022](#ref.xhtml#re_CIT000092)). As discussed, the `sigmoid` and the `tanh`, originally motivated by the biological neuronal firing of the brain in the early days of neural nets (Dubey et al., [2022](#ref.xhtml#re_CIT000092)), suffer from the *vanishing gradient problem* ([Basirat](#ref.xhtml#re_CIT000022) & Roth, 2019) due to the fact that they are squashing functions. Recall this is because the gradient becomes very close to 0, resulting in virtually no update in parameters during training. With `ReLU`, since the derivative of positive inputs is equal to one, the gradient cannot vanish.

There is an entire literature and specialization within machine learning and mathematics devoted to evaluating existing activation functions as well as proposing new ones. Recent work has also introduced the idea of *learning/adaptive activation functions*, which, as the name suggests, contain learnable parameters to exploit more of the data’s complexity. These include such activation functions as the `Adaptive Piecewise Linear` (`APL`), the `swish`, `e-swish` and more. Consult [Dubey et al. (2022)](#ref.xhtml#re_CIT000092) for a thorough and excellent review of the strengths and weaknesses of a variety of non-adaptive and adaptive activation functions and who also give a series of recommendations regarding which activation functions to use under a variety of conditions. While `ReLU` is commonly a default choice, these authors also recommend the `swish`, `mish,` and `PAU` (`Padé activation unit`) to be tried for most problems. Of course, there is absolutely nothing wrong with trying out a variety of activation functions for any given problem. There is no theoretical “type I error rate” on activation functions that would restrict the user from trying out a handful, so long as the resulting network is ideally subjected to cross-validation.
