如果交易成功构建、签名并提交，则我们会更新应用程序数据库，增加票务兑换金额，减少交换中的提供数量。我们还将包含交易 ID，并在 *[图 10.17](#c10.xhtml#fig10_17)* 第 481–482 行将确认标志设置为 `false`。在 3 个区块确认后，将会有一个 Blockfrost webhook 回调应用程序，将确认标志设置为 `true`。最后，第 493 行调用 `handleClose()` 用于强制刷新 `Swap View` 和 `Event View` 中的交换和事件。

# 智能合约

票务应用的链上代码涉及以下 Plutus 脚本：

*   信标铸造策略
*   票务铸造策略

# 信标铸造策略

信标链上代码通过 Redeemer 传递交易 ID 和索引，以创建唯一的代币名称，从而轻松定位所有交换。这与 *[第 7 章，铸造](#c07.xhtml)* 中看到的方法不同，那里我们将交易 ID 和索引用作合约参数。应用程序所有者的 PKH 是信标铸造策略中唯一的合约参数，如 *[图 10.18](#c10.xhtml#fig10_18)* 所示。

**图 10.18：** 信标 Redeemer[^(17)](#c10.xhtml#ftn17)

在 *[图 10.19](#c10.xhtml#fig10_19)* 中，第 22 行确定铸造内容的值，第 23 行确定脚本本身的铸造策略哈希值。第 28 行将 `TxId` 和 `TxIdx` 组合，然后使用 `blake2b` 哈希算法对其进行哈希。这遵循链下代码的做法，使铸造的代币名称与链上代码一致。我们还在第 36 行检查只铸造了 1 个代币，并且该铸造策略不铸造其他代币。

# 票务铸造策略

票务铸造策略包含 Mint、Convert 和 Burn Redeemer。Convert Redeemer 传递要转换的票数，并铸造一系列唯一的票务代币，如 *[图 10.21](#c10.xhtml#fig10_21)* 所示。应注意，传递任意长度的列表时需要仔细考虑。执行此脚本的预算成本将取决于 `userTicketTokenName` 数组中包含多少张票。在我们的案例中，这是必需的，因为我们显式铸造单个唯一的 NFT 代币。因此，我们需要知道每张票的名称，以便在铸造和验证器脚本中相应地铸造和验证它们。

![](images/Figure-10.21.jpg)

**图 10.21：** 票务铸造策略[^(19)](#c10.xhtml#ftn19)

在 *[图 10.22](#c10.xhtml#fig10_22)* 中，第 27 和 28 行使用 `TX_ID` 和 `TX_IDX` 合约参数创建 `TxOutputId`。这将用于确保每个事件的铸造策略都是唯一的。第 31 行的 `totalAssetVal` 函数是一个递归函数，将所有 NFT 代币和参考代币组合成一个 Value。

# 持有验证器

`Holding` 验证器脚本充当已铸造但尚未释放到交换中的票务代币的暂存区。它们只能由活动所有者的质押密钥花费，该密钥作为合约参数硬编码，如 *[图 10.25](#c10.xhtml#fig10_25)* 所示。持有验证器脚本的实现有些棘手，因为我们想确保在来回转移到交换时没有代币泄露。挑战在于，创建持有验证器时，交换地址未知。因此我们遇到了**循环引用**场景：持有脚本需要知道交换地址，交换地址需要知道持有地址，两者本应互为合约参数。

为了缓解此问题，我们利用信标代币铸造策略，它可以预先计算。如 *[图 10.18](#c10.xhtml#fig10_18)* 所示，`beaconMPH` 在第 16 行设置为合约参数。在 *[图 10.25](#c10.xhtml#fig10_25)* 中，我们在第 19 行引入了一个名为 `checkTokenOut` 的新辅助函数，如果一组输出中包含任何代币，它将返回 `true`，用于检查代币泄露。

![](images/Figure-10.25.jpg)

**图 10.25：** 持有验证器 checkTokensOut[^(23)](#c10.xhtml#ftn23)

如 *[图 10.26](#c10.xhtml#fig10_26)* 所示，`Transfer` Redeemer 用于将票务代币从持有脚本转移到交换。交易必须由活动所有者的质押密钥签名，且必须包含信标代币。回顾一下，每个交换都必须有信标代币，这将有助于确保这些票务代币只流向交换而非其他地方。只有发送到交换和可选的持有验证器脚本（用于找零）的输出才应包含代币。第 43–49 行强制执行此规则。
