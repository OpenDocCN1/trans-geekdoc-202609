
测试策略同时使用传统测试和基于属性的测试。[³](#c11.xhtml#ftn3) 传统测试涉及创建特定的测试用例，以确认智能合约正确地实现了需求。这可以包括正向和负向测试用例。基于属性的测试将尝试利用输入来攻击智能合约，并测试那些意料之外的条件。[⁴](#c11.xhtml#ftn4) 我们将使用与 `Vitest` 集成良好的 `fast-check`[⁵](#c11.xhtml#ftn5) TypeScript 库。一个考量因素是链下交易构建器框架会在 **UPLC** 求值前执行有效性检查。因此，一些失败的测试将是链下交易构建器的错误处理，而非智能合约本身。一个潜在的解决方案是拥有链下工具，在构建和提交交易时避免任何检查。进行此类更改超出了本书的范围，但未来可能会将其作为一项功能请求来启用此选项。使用 `Aiken` 时，你可以为传统测试和基于属性的测试修改脚本上下文。然而，这种方法的缺点是它不能很好地集成到 `Vitest` 等测试框架中，且设置耗时。

# Property-Based Testing

要执行基于属性的测试，我们通常需要使用链下代码构建交易，以直接将输入馈送到智能合约的 `redeemer`、`datum` 或合约参数中。如 *[Figure 11.9](#c11.xhtml#fig11_9)* 所示，`unlock` 测试用例涉及向链下 `unlock` 函数发送无效的 `redeemer` 消息。要使用 `fast-check` 库，我们必须在第 163 行调用 `fc.assert`，它将包装 `fc.asyncProperty`。在 `asyncProperty` 内部，`fast-check` 将生成伪随机字符串，我们可以将其作为消息传递给 `unlock` 函数。我们预期每次执行都会失败，因此当每次执行尝试都失败时，属性测试即通过。

![](images/Figure-11.9.jpg)

**Figure 11.9:** Unlock Property Test Case[^(10)](#c11.xhtml#ftn10)

`Helios` 和 `Aiken` 也都有原生的基于属性的测试框架。`Helios` 有一个名为 `FuzzyTest`[^(11)](#c11.xhtml#ftn11) 的辅助类，允许你创建随机数据，并将其馈送到你的 Plutus 脚本中。`Aiken` 对单元测试和基于属性的测试有极好的支持，包括覆盖率报告。以下是一个 `Aiken` 单元测试和模糊测试的示例：[^(12)](#c11.xhtml#ftn12)

```
use aiken/fuzz

fn answer_of_life(n: Int) -> Bool {
  n == 42
}

test question_of_life() {
  answer_of_life(42) == True
}

test prop_bool_distribution(predicate via fuzz.bool()) {
  fuzz.label(
    if predicate {
      @"True"
    } else {
      @"False"
    },
  )
  True
}
```

当运行 `aiken check` 命令时，将生成以下报告：

```
┍━ aiken_test ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
│ PASS [mem: 1802, cpu: 680589] question_of_life
│ PASS [after 100 tests] prop_bool_distribution
│ · with coverage
│ | False  53.0%
│ | True   47.0%
┕ with --seed=4272986809 → 2 tests | 2 passed | 0 failed
Summary 101 checks, 0 errors, 0 warnings
```

`Aiken` 属性测试允许你指定一个用于求值的谓词，该谓词包含在报告中。在该示例中，我们可以验证 `True` 和 `False` 值被生成且具有良好的分布。

# Secure Smart Contracts

智能合约开发最重要的方面是安全性。智能合约可能负责数百万美元的价值转移，或负责验证选举结果。因此，在设计和编写智能合约时，需要特别考虑以尽可能以最安全的方式进行。只有当你了解*不该做什么*以及*该做什么*的示例和最佳实践时，才能做到这一点。本节将回顾一些通过 Cardano 审计发现的常见陷阱。
