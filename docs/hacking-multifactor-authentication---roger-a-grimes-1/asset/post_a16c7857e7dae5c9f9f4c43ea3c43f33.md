
## Chapter 11 Fake Authentication Attacks

Not allowing regular users and programs to run with the highest privileges and permissions (known as root) by default, Linux had to have a stronger default user security profile than Microsoft Windows. The new default security posture broke a lot of programs, and Linux users had to be retrained in a new way of doing things, but for most it worked. Users complained early, but within a few weeks the complaints stopped and Linux people now know to use sudo when they needed to. After you've used Linux for a few months, you don't even think about it. It’s “muscle memory”—do it without thinking about it.

Because Windows didn’t have a similar sudo command, Windows users were far more likely to run in elevated contexts all the time. Until Vista, Microsoft could easily take a large part of the blame. They really didn't care about the issue or highlight it beyond a list of some general recommendations that no one followed. Microsoft made it easy to run as a non-administrator. In the waning days of Windows XP, some professional colleagues and I decided to follow Microsoft’s advice (and our own advice that had been given for years) and run as non-administrators as much as we could. Turned out it was very hard to do. Many applications broke or had critical errors, and we had to go out and back as administrators all the time to do very, frequently. Logging in and out, and saving all our applications, could take minutes each time. In most cases, our “tests” lasted only a few days to a weeks before we cried and just went back to being logged in as Administrator the time. Microsoft heard our collectives.

While moving from Windows XP to Vista, Microsoft agreed they needed something similar to sudo, more complex and confusing. Microsoft created a new default feature called User Account Control (UAC). By default, if a user logged in as Administrator (or a member of any elevated group or elevated privileges), UAC would automatically “de-elevate the logged-user’s permissions, and group memberships to that of a normal user. If the user or program needed to run with higher privileges, they would need to approve a logon prompt (by clicking OK or elevating logon credentials) to get to the higher level of access. Figure 11.2 gives an example of the UAC prompt screen.

Overall, even though it looks friendly and easy to use in the picture, I (and millions of others) were not quite fine. Behind the scenes, the way it worked was complex, complicated and clunky; It took me months to figure what it did and how it worked. I did a presentation during this time, and it took me over 100 slides to discuss, in detail, how it really worked. Most people didn't understand it much at all. But even with a thorough understanding most users and vendors hated it!

NOTE I had to understand UAC in detail I was writing a book on Windows Vista security (Windows Vista Security: Securing Vista Against Malicious Attacks, Wiley, 2007) and because I was going to teach Vista security to thousands of internal Microsoft employees and tens of thousands of interested customers.

But as much as UAC was hated, in a year or two it had the same desired effect as sudo did in the Linux world: most users and programs were no longer running as full administrators. Over time Microsoft tweaked UAC to be more user friendly and less bothersome (although the behind-the-scenes complexity stayed). Today even users barely notice UAC other than they have to click OK to install a program or enter their password to change a system setting. UAC (and sudo) are success stories if you ignore the early warts and frustrations of the first few years.

I related this long narrative for two reasons. First, sometimes usability issues cannot be avoided and the vendors just have to take a risk that users will understand the new, constant interruptions over the long term.

NOTE Keep in mind that far too many security vendors think this is always the case for everyone they do, and in reality, forced instances of major changes should be used rarely. As covered in Chapter 4, “Usability as Security,” users will more often work around security blockers, turn them off, or use something else when faced with too high of a security obstacle—even when it is in the user’s own best self-interest.

Second, and more important to this particular chapter, I wanted you to understand the background of how important UAC was to the success of Windows' enhanced security 2007. Many remember Vista with mixed emotions, but it contained a ton of upgraded security that improved the default security posture of OS and its customers as well as computer security in general. Many of the security improvements Microsoft added were the first time they had been added to a major, general-purpose OS, or the other operating systems following Microsoft lead. Even then, UAC suffered from security issues that Microsoft could not overcome or are still potential issues today. One of those was the threat from fake authentication.

When a user program requested elevation, Windows and UAC tried its best to prevent potentially malicious programs from getting around the UAC prompt. Microsoft didn’t want malicious programs to be able to click on or answer the UAC prompts, bypassing it, tricky users into accidentally clicking on the wrong things (known as clickjacking), or interacting at all with the end user during the UAC elevation prompting interaction. If malicious programs can interact with UAC or the user during a UAC elevation event, the chances that they could do anything are significantly higher. Every hacker wants to be able to interact with any security feature in a way that fools the UAC or bypasses the prompt. Every security-conscious developer needs to regulate what is known as focus of control so that only the legitimate programs are able to interact in authorized ways at the appropriate times.

UAC’s developers decided they needed a way to prevent any unauthorized program from interacting with anything else but the UAC prompt until an elevation event and prevent the user from accidentally interacting with anything else but the UAC prompt until the elevation event was finished. What UAC developers needed total isolation except for the one elevation decision for the program the user needed to master. UAC takes a snapshot of the user’s desktop and places it over the real desktop. Windows creates a single-color picture that becomes the temporary background, covering your real desktop during the elevation prompt action.

After that happens, the true UAC prompt could display over the fake desktop. Even if the user was accidentally tricked into clicking on anything besides the UAC prompt, nothing would happen. They would only be clicking on a picture and not the actual desktop behind the scenes. It was a pretty cool switch switch. Fewer than 0.001 percent of Windows users even saw this happening. If you know how UAC works in detail and what knowing and looking for it, you might see the millisec switch out. Most people just saw that the user’s desktop was darker (Microsoft dimmed the photo to remove any user focus on anything other than the foreground prompt). The only major side effect was that some early video drivers couldn’t handle the switch action and would not work with UAC. Those video drivers had to be updated to handle UAC or, until the driver was updated, the impacted users had to run commands to disable the protected UAC prompt.

It was a great example of a security solution from the minds of top computer security experts. What Microsoft didn’t share with people outside the company was that they could not solve the opposite problem: a malicious program faking the UAC experience. In fact, no one can easily solve it or other similar authentication problems like it. I have seen ways to solve it, but most are clunky and unkly to become pervasive. More on that later in this chapter.

Let me go into more detail about the authentication experience involving UAC so you'll better understand what I'm talking about. What Windows developers could easily stop malicious programs simulating the entire UAC experience when it did not happen. With the real UAC experience, the UAC prompt comes up when Windows requests it. But there is nothing to stop a malicious program that is actively faking the UAC experience when it isn't. All the malicious program has to take a desktop picture and offer a single-colored, dimmed background; make a fake UAC prompt appear; ask the user to click OK or type in their credentials; and have to see what the user did. The user can even be tricked into providing their credentials to the UAC prompt, which is made to appear as if it. The user will likely just think they've typed in the first time and then think the second time they typed in correctly. There is no way for Windows or U to accurately detect that a fake UAC experience occurred or to block it with a high level of accuracy. Even if Windows actively tried to look for and detect instances of fake UAC prompts, the fake UAC prompt could be changed so much that Windows detects it no matter how much it tries.

If the user types in their credentials, the malicious program can record the user's elevated credentials and then use them behind to do anything the user can. The hacker or malware program will "own" the system. They can install more malware, record the user's keystrokes with a keystroke logger, dump all the system credentials, manipulate data, and spread around the network. What the malware or attacker can do is limited only by their malware developer's or hacker's imagination and what is possible the software and hardware constraints.

The user can also be tricked into providing other confidential information or believing they had performed some necessary administrative action, such as fooling the user into thinking they had run (a) antivirus scan or install a new, (but really fake) Microsoft patch. A real UAC prompt will often show the legitimate vendor of the program if that program is signed by a trusted digital certificate. So, all the malicious program has to do the whole experience, including showing a fake trusted digital certificate that Windows appears to be saying is real and trusted. Fake authentication can be used to do many things, including:

- Steal credentials.
- Perform a man-the-middle attack, which is then used by the attacker to access the real site/service as the victim.
- Steal other confidential information.
- Take over the logon account.
- Make the victim think some legitimate action occurred that did not in actually.
