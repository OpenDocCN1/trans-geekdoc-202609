# Use Push Authentication

MFA solutions involving "push" authentication have become increasingly popular over the last few years. Push authentication is when an authentication service transmits, or "pushes," a message to a registered device or application involved in an action sequence, which the user acknowledges (or declines). A common scenario is a user logging into a website and then the authentication solution pushes a message to the user's MFA app. The user gets the authentication message, reviews, and approves. The approval process generates a response to the website, which automatically logs the user on. There are even popular push notification cloud services, like Google Cloud Messaging and Apple Push Notification service, that MFA providers use as part of solution to push their messages.

Because the server is pushing to the user via a registered, out-of-band app installed on the mobile device, it makes many forms of hacking harder to achieve. For example, if the user's session was compromised by a MitM attack, the eavesdropping would not capture any of the outof-band messages, as if the user used an in-band OTP code. In most instances, the pushing is done to the user's phone, to an authentication app directly tied to the login experience. Because of the inherent issues with SMS covered in this chapter, push authentication to a phone app or hardware is preferred over SMS.

There are even "pull" messages. Because push messages often rely on potentially unreliable and cellular phone service, the push notifications cannot guarantee delivery. MFA vendors, such as WatchGuard, use their client-side app to send "pull" messages to the server side. When you open the MFA phone app, the WatchGuard app will proactively check for waiting, outstanding push messages to make sure one wasn't lost or delayed (for example, as it was sent while you were on a long flight) and still waiting for a retry sometime.

Most messages are sent to an "app ID" that ties the push message to a particular user application. If the push message is sent using a general push service serving multiple sites and services, the push message should include all the necessary authentication "transaction" details so that the user can acknowledge the push is tied to the correct, desired authentication. Without the necessary details, an attacker could possibly create a login credential to a second website or service the user is also registered, but doesn't know they are logging in, and inadvertently be tricked into responding to an alternate push message tied to a second website or service they are unaware involved.
