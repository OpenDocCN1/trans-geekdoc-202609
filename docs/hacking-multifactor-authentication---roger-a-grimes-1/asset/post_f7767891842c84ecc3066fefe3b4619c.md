## Subject Hijack Domain Attack

Right now everything is as it should be. In our hacker fantasy scenario, we're going to assume the Super Admin user logs out and goes home and the Help Desk user hangs around to mischief.

Adam discovered this by accident while successfully trying to understand how Active Directory and smartcards interacted while we were both on-site at the same customer. I was installing a smartcard pilot project and I was part of a response team fighting foreign hacking adversaries that had successfully attacked this company several times over the years.

The "hack" is the Help Desk user changing the Super Admin's UPN to `helpdesk@victim.com` so when the Help Desk user logs in using their smartcard with a UPN of `helpdesk@victim.com`, AD maps the Admin's account to the Help Desk user's login. To do this, he must first rename Help Desk's UPN to almost anything (`frogtemp@victim.com` in this demo) because there are two UPNs with the same values (i.e., `helpdesk@victim.com`) at the same time in the same AD forest. So, by renaming the Help Desk UPN to something else, the Help Desk user can rename Super Admin's UPN to `helpdesk@victim.com`. This sequence of steps is illustrated in Figure 10.11.

After the UPN change, the Help Desk user must log out and wait for the account change to replicate across Active Directory so all account databases get the new change. This can take up to 10 minutes (or longer) in some environments, but often takes only 1–2 minutes. At the very least, the UPN must be replicated to the Active Directory domain controller before the Help Desk user is logging on. Then all Help Desk user logs into Windows and Active Directory using their smartcard and PIN (as shown in Figure 10.12). During the logon, anyone watching in real time would see the Help Desk username suddenly change to Super Admin before the logon goes away to reveal the successful logon.

The Help Desk user is Super Admin user. This occurred Active Directory had no way of knowing that the Super Admin user account should not have a UPN of `helpdesk@victim.com`. Active Directory gets told by Windows that a successful smart card logon has occurred and the UPN of `helpdesk@victim.com` is part of that transaction. AD looks it up and finds the user with the associated UPN, and then gives that user the access control token of the Super Admin user, including groups and privileges.

At this point, the Help Desk user can do anything the Super Admin can do. They can add their regular Help Desk account to privileged groups; verify, modify, and copy files they not normally have access to; and install eavesdropping trojans and other malware. They can modify operating systems and Active Directory itself.

And to make matters, Microsoft Windows and Active Directory will track all Windows Event Log events committed by the Help Desk user as if they were committed by Super Admin. After committing any unauthorized actions, the Help Desk user could swap the UPNs and log out. Unless UPN updates are logged and the importance of those particular actions were noticed, it would be difficult to see exactly what happened if he suspected it had.
