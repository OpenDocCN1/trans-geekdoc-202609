# 302 Hacking Multifactor Authentication

Why would Instagram, or any other vendor, allow hundreds of bad attempts before locking out an account? It may be because of their past experience or simply their personal belief about what the right settings are. For example, for decades Microsoft's default password lockout policy was that five guesses in 30 minutes caused a 30-minute lockout. After 30 minutes without any further password guessing, the counter would be restarted and bad attempts would be set to 0. The recommended defaults (which often varied with the default settings in their products) changed, starting with Windows Vista/2008, to many bad attempts before an account locked out. Today, Microsoft is not recommending a one-size-fits-all default policy for any organization (docs.microsoft.com/en-us/archive/blogs/securing/configuring-account-lockout). Why?

I can give you a couple of reasons. Microsoft felt that if an organization's policy was sufficiently strong—requiring at least eight characters and multiple character sets of complexity with a 90-day or shorter expiration period—then an attacker would be unlikely to successfully guess anyone's password before it expired. With a sufficiently strong password policy, it would take a hacker billions of guesses before they would succeed, and even with authentication, the password would be changed before the automated tool guessed anyway.

Account lockouts are used to stop guessing against passwords using online methods. Using online portals that allow the login name and password to be entered and the Enter key or OK clicked to send the login to the authentication system for verification. The rounding process of entering in a particular login name/password combination and waiting for the system to validate, either successfully or with a failure message, normally takes 2-3 seconds in most scenarios. So, automated (online) generators can guess at a single login combination only every 2-3 seconds per portal instance (usually). At 2 seconds per guess, at best would allow a guesser 3,888,000 attempts in a 90-day period with no account lockout or throttling enabled. That's a lot of guessing but far less than what it would take to randomly guess an eight-character, "complex" password (without any usable knowledge or birthday attack). If you hit passwords to get eight characters and not any bigger, you get 95% possible passwords. That's billions of billions, over six quadrillion possible passwords (i.e., 6,634,204,312,890,625). If all was allowed for 26 lowercase (2⁶), it would still be 808,287,056 possible different passwords. This is because of course the entropy issues discussed in Chapter 1 and premature birthday attack collisions. But since it to say, guessing at "complex" passwords at a time using online portal is nontrivial if the passwords are sufficiently "complex." So, the thinking is if you've got sufficiently complex passwords required by the password policy, you dont account enabled because a malicious password guesser or their tool will never be successful.

Second, Microsoft tech support had seen tens thousands of instances where legitimate scripts or tools caused big account lockout problems and operational issues because someone updated a user account password script or tool (as recommended by every password guesser and regulation) did not update it in the script or tool. So, the automated tool was trying to do legitimate, routine task and in the process unintentionally causing account lockout issues across the network.
