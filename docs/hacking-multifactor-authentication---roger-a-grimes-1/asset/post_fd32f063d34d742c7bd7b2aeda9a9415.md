
# Prevent OTP Replay

Some OTP solutions allow previously generated or used OTP codes to continue to be valid into the future. This is crazy! All OTP codes surpassed by newer OTP codes should no longer be valid. Some OTP solutions include timestamps that are recorded and stored with the OTP code when it is generated and used. This can help prevent easy replay. An OTP system should not allow multiple OTP codes to be generated, or remain valid at once. This prevents an attacker from obtaining older OTP codes and re-using them as easily.

> NOTE This recommendation causes an issue for MFA solutions with master codes, which are often generated in the same time and never expire, are given long expiration periods, or don expire until the user generates new ones or cancels the old ones.

# Make Your RNG NIST-Certified or Quantum

OTP security protection relies on the true randomness of the static value and the involved hash. Mess up that and the rest does not matter. Most traditional operating systems contain freely trusted random number generators (RNGs) and you can rely on them. Don’t “roll your own.” Today's best RNGs are known as pseudo-RNGs (PRNGs) and inspire a bit of confidence because we are acknowledging that they aren’t perfect. Funny, but by acknowledging that they aren’t perfect as they seem from themselves. I avoid RNGs that don’t understand that they aren’t perfect as they pretend. Quantum random number generators are truly and random. All other factors consider equal, I would trust any quantum random number generator (QRNG) over an RNG/PRNG.

NIST created a series of tests that any—quantum or otherwise—RNG vendor or customer can run to see how bad their RNG/PRNG is compared to a theoretically perfect number generator. NIST documented the tests and requirements in NIST Special Publication 800-22 (nvpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication-800-22la.pdf).

# Increase Security by Requiring Additional Entry Upon OTP Code

One thing RSA got right early on was requiring logins involving TOTP devices also use a static code that the user provided during the time of login. When the adding static code could be compromised as easily as a seed or typed value, it does make that sort of attack slightly harder to accomplish. Additionally, if the seed database gets compromised and the other static values are not located in the same place, the seed value alone will not give the hackers immediate access.

# Secure Seed Value Database

Seed value databases are the targets of hackers. All seed value databases should be particularly secured as the high-risk assets that they are. Wherever they are stored, they need to be protected by field-level encryption, data-leak protection, containerization, heightened security monitoring, and quick incident response methods. Ensure that any additional static secrets used in OTP code calculation are not stored in the same databases as the seed values.

# User Defenses

Let's look at some defenses users can take to protect themselves against OTP attacks above and beyond what developers can do.

# Don't Get Socially Engineered Out of Your OTP Code

The single best thing any OTP user can do is not allow them to get socially engineered out of their request OTP code. Users need to be aware of phishing scenarios, how to spot rogue URL links, and about rogue proxy servers. Many end users think that if they have an MFA solution don't have to be as worried if they had a simple logon name/password solution. A false sense of security can be as dangerous as a weak security solution.

# Delete Setup Codes

Delete and erase MFA setup codes. Don't simply delete and forget. Delete and empty the trash. Make sure there is no setup code can be recovered by another unauthorized person and used to create an additional identical OTP instance. Developers, of course, could make this non-worry by expiring setup codes after a reasonable period of time or by implementing DSKPP as desired.

# Tie to Single Device/Instance

Developers can create risk by tying one OTP instances to a single device so that only one person can use it at the same time. This would prevent an unauthorized user from compromising the original instance and generating a second, unauthorized instance that they then use to log on as legitimate.

# Physically Protect Your Device

Protect your OTP device (e.g., phone) from unauthorized access. If your device goes missing, report the issue to IT immediately. They should disable your ability to log on until they decommission the old device.

> NOTE Remember to securely protect any “backup” or “travel” master codes so that they cannot be discovered.
