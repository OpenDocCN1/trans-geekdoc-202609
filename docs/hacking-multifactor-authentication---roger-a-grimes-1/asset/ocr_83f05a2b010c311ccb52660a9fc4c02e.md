# Chapter 9 One-Time Password Attacks 223

# Use Reliable and Trusted OTP Algorithms

Unless you are or have access some of the world's best cryptography experts who the cryptography industry trusts, don't attempt to make your own OTP algorithms or cryptography. Today's tried-and-trusted algorithms and cryptography are more than sufficient for whatever you need.

If you are lucky and your OTP solution survives for a long time (say over half a decade... most do not last this), you will likely need to update the cryptography associated with your OTP solution. Assume whatever cryptography you use will eventually need to be updated or replaced and make your solution "crypto agile." This means that you and your customers can easily update the covid without major actions or issues. All cryptography weakens over time and eventually gets replaced. Survive long enough or it happen. Harden the algorithms and cryptography in a way that makes it difficult to replace or upgrade. At the same time setup ensure that unauthorized changes can be made to your solution.

# OTP Setup Must Expire

Any initial seed value/code used to set a unique OTP instance should expire within a reasonable period of time. You don't want an "old" code sitting around waiting for an unauthorized user to discover. This also applies to master, backup and travel codes. All codes which make a new instance or to bypass an MFA instance should expire in a reasonable period of time.

One related solution Dynamic Symmetric Key Provisioning Protocol (PSK). Officially registered in RFC 6063 (tools.ietf.org/html/rfc6063), DSPKP is a simple method sharing symmetric secrets between two authenticating parties—the client and server of an OTP solution, for example. DSPKP allows a shared secret, like a seed, to be generated between the parties. And—this is important—it could be used and over to establish new secret values they are needed. So if the original seed base value or any old values were compromised, the information learned could not be as easily to duplicate future OTP codes. An OTP token, for example, could generate a new shared secret every day or at any predefined time interval. Although DSPKP is new, I'm already thinking that any OTP solution using it has a lag up on the competition.

# OTP Result Must Expire

Any resulting OTP code should expire whether or not the code was created by an OTP. If OTP codes did not expire or took a long time to expire, then an unauthorized user might be able to use an "old" code for a future authentication. This is a big problem, particularly around HOTP solutions. There is a very popular HOTP vendor solution that never expires or used HOTP codes. Some knowledgeable people and competitors agree showing how 20 HOTP codes generated over a year still work just fine current logins. This is unacceptably dangerous.
