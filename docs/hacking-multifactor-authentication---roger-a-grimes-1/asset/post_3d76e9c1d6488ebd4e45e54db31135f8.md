You can see that the resulting outcomes are unique, long, random, and unpredictable. Using a good cryptographic hash, like SHA-256, with an additional random portion ensures that any hacker viewing one session ID won't be easily to guess another. The session ID should be time bound (i.e., expire after a specified time limit) to ensure that one session ID can't be reused for the same user in another session after the first ones. At the same time, as long as the service is storing the calculated values, it will be easy for it to track the user across multiple actions and transactions during the allowed session.

All the protections session ID are nullified if the session ID turns out to have an easy-predictable pattern. If someone can view or guess the identifying information, they can easily craft an identical access token. Access control tokens often look for predictable patterns in what is supposed to be random and unpredictable. Hackers will authenticate to a website many times with different identities and review the resulting access token information for predictable patterns. If they see a suspect pattern in the cookie's supposedly identifying information, they will begin to construct additional cookies, modifying them in their way, and connect to the website to see if it (a) accepts the cookie, and (b) authenticates as another valid user account. If the attacker has hacked there are many hacking tools (Firesheep, Burp Suite, Cookie Cadger, to name a few) that help with theft, re-creation, and hacking. It's a matter of generating as many legitimate subject IDs and cookies as possible. This part can be scripted. If the attacker figures out the pattern, then there is nothing to stop them from harvesting the whole database. Many of the data breaches you read about in the news are really hackers who figured out a session ID pattern and used it to dump an entire database.

# Token Theft

If the attacker has the appropriate access, it's probably just easy to steal a user's legitimate access token. Most access tokens contain correctly generated randomly session IDs, as shown in Table 6.1, and so trying to guess them or find a repeatable pattern is nontrivial (i.e., very hard to implement using known technologies and techniques in a reasonable amount of time). Access control theft can happen locally or over the network. If an attacker has complete control of a user's computer or device, usually this is enough to let access, view, steal, and/or manipulate and use the access control token.

Admin does not guarantee immediate access to an access token. Many operating systems provide special protections to access control tokens and the processes around them, and even the highest admin access won't let a user directly access the token. Most of the time, ultimately, if an attacker has unencumbered access to a device or network, with enough time and resources, access to the access token will be gained, one way or another.

Other times, especially if the token is stored on a cryptographically protected token device, it can be outside of exceptional attempts to access and duplicate the access token. Instead, it would be easier for attackers to manipulate or reuse the token when it is being used by the legitimate user. You'll learn more about this type of scenario in later chapters.

# Hacking Multifactor Authentication

Another method is to steal the access token during its use or transmission over a network. In most instances, the attacker must inject themselves in the communication between client and server, in what is known as a man-in-the-middle (MitM) attack. MitM attacker can eavesdrop and/or manipulate the access token. Network theft of access tokens has been done for decades and is among the most common ways to hack any authentication solution, including multifactor authentication.

Guessable IDs are a popular bug because programmers are rarely taught to avoid common session vulnerabilities in schools or using self-studying. The rare programming instruction covers development lifecycle topics. So, it is very common for new programmers, when designing a system involving authentication and access control tokens, to fail the process that generates session ID numbers. Unless they have been trained about the importance of making authentication and access control tokens random they usually dont realize how easy they are to predict.

Creating random, unique, and unpredictable session IDs becomes a part of the Web Application Security Project (OWASP) Top 10 list (https://owasp.org/images/7/72/OWASP_Top_10_2017_B2829.pdf). OWASP is a not-profit group dedicated to helping web programmers secure more. The OWASP Top 10 is considered one of the guides of its kind and has become a global de facto standard. OWASP explains poor session IDs and how to defend against them in its A2:2017 Broken Authentication. In particular, OWASP recommends to prevent insecure session IDs: "Use a server-side, built-in session manager that generates a new random session ID with high entropy after login. Session IDs should not be in the URL, be securely stored and invalidated after logout, and absolute timeouts."

That's the long of saying that you should make sure that your session IDs are unique and unpredictable. When hackers can guess or predict session IDs, the IDs can be exploited to further compromise the website or its users. The patterns are so easy to see that they just stick out like a thumb. This is usually the case when an attacker can see sequential patterns that increment a single number or letter at a time (as shown in Figure 6.2).
