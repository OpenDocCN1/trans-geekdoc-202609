
## Chapter 8 SMS Attacks

## Defenses to SMS-Based MFA

The best protection against SMS-based MFA attacks is to not use or rely on SMS-based MFA solutions. However, as I said earlier, SMS-based MFA attacks are the most popular type of MFA on the Internet. Often you cannot get access to a site or service that requires MFA without SMS-based MFA. Sometimes a vendor may have a phone app for their services, but they often resort to sending SMS codes because everyone has SMS active but not everyone has their app running. So good luck trying to avoid SMS-based MFA. Many times you have no choice. If you have to use SMS-based MFA, here are some developer and user defenses.

## Developer Defenses

First, let's look at some developer defenses.

### Security Awareness Training

Any SMS-based MFA vendor should share examples of the risks of using their solution, educating users about the types of rogue attacks that could be accomplished even when the users rely on their solution. Educate the users about common risks and scams.

### Way to Verify SMS Message Legitimacy

As long as SMS doesn't have an easy way to verify a vendor's message legitimacy, the vendor's solution should include a method that the user can verify that an SMS message claiming to be from the legitimate vendor really is from that vendor. It can be something as easy as creating a user portal where the user can verify the legitimacy of all SMS messages. The user should be able to easily pull up that portal and verify that it is on the real website for purpose.

### Expire SMS Codes in Ten Minutes or Less

All SMS codes should have a useful life of 10 minutes or less. You don't want to authenticate code sent via SMS to be used indefinitely. Having an expired code increases the risk of unauthorized viewing and reuse. Make sure all SMS secrets are only sent to registered phone numbers, and if the user generates the SMS recovery code, they should have to provide not at least a portion of the preregistered number that the SMS code is being sent to but also another piece of authentication information that the user should know.

### Tell Users to Put Your Contact Info in Their Contact List

Tell users to put the phone number or code related to your SMS-sending service in their phone so that when you send an SMS message it automatically comes up as a validated contact name. Educate users not to accept SMS messages from phone numbers outside of the communicated contact information.

### Prevent Suspicious SMS Messages from Being Sent

If the user can initiate SMS messages, look at the actions of the user and see whether or not they are suspicious. The request coming from the user's usual devices, locations, and other normal behavior characteristics. If not, require additional authentication before sending the user's requested SMS code.

### Use Push Authentication

MFA solutions involving "push" authentication have become increasingly popular over the last few years. Push authentication is when an authentication service transmits, or "pushes," a message to a registered device or application involved in an action sequence, which the user acknowledges (or declines). A common scenario is a user logging into a website and then the authentication solution pushes a message to the user's MFA app. The user gets the authentication message, reviews, and approves. The approval process generates a response to the website, which automatically logs the user on. There are even popular push notification cloud services, like Google Cloud Messaging and Apple Push Notification service, that MFA providers use as part of solution to push their messages.

Because the server is pushing to the user via a registered, out-of-band app installed on the mobile device, it makes many forms of hacking harder to achieve. For example, if the user's session was compromised by a MitM attack, the eavesdropping would not capture any of the out-of-band messages, as if the user used an in-band OTP code. In most instances, the pushing is done to the user's phone, to an authentication app directly tied to the login experience. Because of the inherent issues with SMS covered in this chapter, push authentication to a phone app or hardware is preferred over SMS.

There are even "pull" messages. Because push messages often rely on potentially unreliable and cellular phone service, the push notifications cannot guarantee delivery. MFA vendors, such as WatchGuard, use their client-side app to send "pull" messages to the server side. When you open the MFA phone app, the WatchGuard app will proactively check for waiting, outstanding push messages to make sure one wasn't lost or delayed (for example, as it was sent while you were on a long flight) and still waiting for a retry sometime.

Most messages are sent to an "app ID" that ties the push message to a particular user application. If the push message is sent using a general push service serving multiple sites and services, the push message should include all the necessary authentication "transaction" details so that the user can acknowledge the push is tied to the correct, desired authentication. Without the necessary details, an attacker could possibly create a login credential to a second website or service the user is also registered, but doesn't know they are logging in, and inadvertently be tricked into responding to an alternate push message tied to a second website or service they are unaware involved. The attacker could trick the user into logging into an incorrect site or use the push acknowledgement to log on the second site themselves using the victim's identity. Another potential security issue is that if the device or app being used to receive the push is compromised and/or in the hacker's possession, the push will be sent to the attacker, who can then acknowledge the push message. Phone apps should always require authentication, well, such as a PIN or biometrics, to prevent a phone from being used to further compromise the victim's online experiences. But in general, push messages are a good thing and usually employ MFA security.

## User Defenses

The number defense is to use any MFA solution other than that relies on SMS. Outside of that, if you must use and rely on SMS-based MFA, here are some other defenses you can implement.

### Security Awareness Training

The best piece of defense advice I can give you to let users know they can still be hacked though they are using an MFA solution. Make sure users are educated about the risks and specifically associated with SMS-based MFA. You want to cover SIM swap attacks, SMS impersonation, rogue SMS URL links that can lead to device takeovers. Educate users so that they understand they dont have all the protections they may have on a full-sized phone, such as the ability to hover a link. Make all SMS-based MFA users get this training at least once a month.

### Be Aware of Rogue Recovery Messages

Users should be aware of SMS recovery schemes and what they look like. Examples include unexpected SMS or voice calls warning of a possible compromise.

### Be Wary of SMS Recovery PINs

Users should be told that, if they are sent an SMS recovery PIN, it would be suspicious if they were instructed to type it back into another separate SMS message or to tell someone over a phone the PIN number.

### Try to Place a Lock on Your SIM Info

Some phone network providers allow high-risk users to place a "lock" or "block" on their SIM information. That is, if some callers requesting their SIM information be moved to another phone, that individual must know the additional piece of information to get the lock removed. Be aware that this could frustrate users if they cannot remember the information needed to remove the block.

### Protect Your Cell Phone Account Logon with MFA

This may sound like circular logic, but it can't hurt to protect your cell phone network user account with MFA if that is an available option. Yes, MFA can be hacked, but protecting logon accounts with MFA usually provides you with more security. So use it.
