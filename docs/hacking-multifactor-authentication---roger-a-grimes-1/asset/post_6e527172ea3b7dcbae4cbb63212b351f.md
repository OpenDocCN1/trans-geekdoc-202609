## Bypassing PayPal 2FA Using an API

Reported in 2014, this incident was a little aged but provides another example of how APIs can be used in bypassing MFA and of the slowness of some vendors to protect MFA security bugs. The bug was discovered by a single researcher and then reported to Duo Security (duo.com/blog/duo-security-researchers-uncover-bypass-of-paypal-s-two-factor-authentication), who got involved and thoroughly investigated.

PayPal has a RESTful API that uses OAuth and JSON. PayPal also allows MFA to be required to use their service, but at the time MFA did not work with PayPal’s mobile app. It was found that PayPal included in their OAuth message an indicator of whether the field was even named 2FA Enabled and possible values were True or False. Sniffing the connection between a participating client and PayPal’s service would have easily seen this.

> NOTE: Discovery of this bug would have been delayed a bit if PayPal had not labeled the field 2FA Enabled.

So, all any attacker knowing victim’s login name and password would be to craft or intercept the authentication message headed to PayPal and change the 2FA Enabled value from True to False, and PayPal would take the user’s login name and password as valid credentials if the victim required 2FA. For reasons not reported, PayPal did not report to Saltman over three weeks. In frustration, Saltman contacted Duo Security for their help, and got involved through the buggy program and assigned a case number. It still took PayPal another two weeks to request additional information about the vulnerability before they fixed it. ## Auth0 MFA Bypass

Auth0 (auth0.com) is a popular authentication vendor offering MFA solutions. Their API auth0.com/api/authentication uses OAuth, OpenID Connect, REST, JSON, and SAML. Auth0 MFA users use this API when they authenticate using an Auth0 MFA solution. The API uses a JSON web token standard (JWT), and tokens can assert claims (as 'I'm MFA and I'm using this for my digital signatures').

The issue is that the JWT standard allows a digital signature algorithm value (alg) of None.

It's also good in dependencies. The initial problem wasn't Auth0's. Auth0 responded to the initial report by looking for and reportedly treating any JWT message with an alg value of None. Problem solved, right?

No. In April 2020, another person discovered (insniac.com/blog/auth0-jwt-validation-bypass) that Auth0 treated an alg value of None correctly, but any other case-sensitive value (i.e., none, nOne, nONE) would be treated as a valid JWT value of None but not subject to the offset, offsetting mitigations. And it was not noticed and publicly reported for another five years. The second finder finally realized that he could enable and a completely different MFA solution with the user's name, password, and Auth0 ID. So, they could bypass the Auth0 MFA requirement and create another rogue MFA tied to Auth0's API that could be successfully used once Auth0 fixed the problem.

## Authy API Injection

Authy is a popular MFA vendor. In 2015, a security researcher found out Authy's MFA initial token response to a new (sakury.com/03/authy.html) allowed an attacker to supply a token. This was because the API did not validate the token properly. An attacker could inject their own token into the response and bypass the. The vulnerability was that the API didn't check if the token was signed by Authy. This allowed the attacker to bypass MFA without knowing the user's password. This is a serious security flaw, and it should be patched immediately. Authy has since fixed this issue, but it is still important to be aware of such vulnerabilities.

## Bypassing Duo with an API

Duo is another popular MFA vendor. In 2019, a vulnerability was found in Duo's API that allowed attackers to bypass MFA. The vulnerability was caused by the API failing to properly validate the MFA token provided by the client. An attacker could forge a token and gain access to the account without MFA. This is similar to the vulnerability found in Auth0 and Authy. Duo has since fixed the issue, but it serves as a reminder that no vendor is perfectly secure.

## The Risks of APIs

APIs are a powerful tool, but they can also be a security risk. If an API is not properly secured, it can be exploited to steal data. For example, if an API has weak authentication, an attacker could gain access to user accounts. If an API has no rate limiting, an attacker could perform a brute-force attack to guess passwords. It is important for developers to follow best practices when building APIs to protect against these risks.
