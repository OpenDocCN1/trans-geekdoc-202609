# Chapter 3 Types of Authentication 95

OAuth is an open standard authorization protocol or framework that describes how unrelated servers and services can safely allow authenticated access to their assets without sharing initial login credential. In official authentication parlance, this is known as secure, third-party, user agent delegated authorization.

Created and strongly supported from the start by Twitter, Google, Google, and other companies, OAuth was released as an open standard in 2010 as RFC 5849 (tools.iet.net/html/rfc5849) and became widely adopted. Over the next two years, it underwent substantial revision, and version 2.0 of OAuth was released in 2012 as RFC 5849 (tools.ietf.net/html/rfc5849). You can join Amazon, Facebook, Instagram, LinkedIn, Netflix, PayPal, and a list of other Who's-Who's (en.wikipedia.org/wiki/List_of_OAuth_providers) as adapters.

An early opponent of introduction() describes OAuth as similar to a car's valet key. Some luxury cars have special, limited keys, which can be used to allow a valet to drive and park a car that doesn't allow the holder full, unlimited access like a regular key. Instead, the car can be driven by a few miles, the key can't access the trunk or locked box, and may other limitations. OAuth essentially allows the user, via an authentication provider that they have previously successfully authenticated, to give another website or service a limited-access authorization token for additional resources.

Additionally, OAuth 2.0 is a framework, not a protocol (like version 1.0). It would be like the car manufacturers agreeing how valets would automatically request, receive, and use the keys and how those keys would generally look like, more than anything else. The valet keys could do compared to the full care about how it works. Just as in real life, valets and car owners don't need to care about how it works. They just want it to work seamlessly as possible. Here is how OAuth works behind the scenes, step-by-step. Let's assume a user has signed into one website or service using HTTP/S. The then initiates a feature or transaction that has access to another unrelated site or service. The following happens (greatly simplified):

+   1. The first website connects to the second site on behalf of the user, using OAuth, providing the user's verified identity.
2. The second site generates a one-time token and a one-time secret to the transaction and parties involved.
3. The first site gives this token and secret to the initiating's client software.
4. The client's software presents the request token and secret to their authorization provider (which or may not be the second site).
5. If not already authenticated to the authorization provider, the client may be authenticated. Once authenticated (or if already authenticated), the client is asked to approve the authorization transaction to the second website.
6. The user approves (or their software silently approves) a particular transaction type at the first website.
