
Sign In With Apple was a new SSO method announced (www.apple.com/newsroom/2019/06/apple-previews-ios-13) by Apple in June 2019. It uses OAuth and JWT to allow users who had previously authenticated to their Apple product using Touch ID or Face ID MFA to access participating sites without revealing their email address or to. In May 2020, a researcher found that any previously validated token could submit any other Apple account (bhavukjain.com/blog/2020/05/30/zeroday-sign-in-with-apple) and get an approved, valid JWT token, which would then allow the attacker to authenticate as the user on the website. The bug was so critical that Apple paid this researcher $100,000 (www.forbes.com/sites/daveywinder/2020/05/31/apple-pays-hacker-100000-for-sign-in-with-apple-security-shocker).

# Token TOTP BLOB Future Attack

This is an interesting type of API attack secured by Alexandre Cagnoni of WatchGuard (he's one of the tech editors for this book). Many companies store TOTP secrets as what is known as a BLOB, a binary object. When a user uses their TOTP token to log on, to say, a bank, this type of scenario is very common, the inputted TOTP code is compared to the stored TOTP secret (and other information) stored as a BLOB in the backend database. Attackers, using a well-known API and logon authentication, can reach the backend database and BLOB. These APIs are often known by the names of the vendors that created or popularized their use (e.g., OneSpan or Datablink).

The attacker must know how the API works and what the targeted TOTP BLOB database or access to it (an impossible hurdle to climb). Because the API is fairly well known within the banking industry, this part is not difficult to learn at all. Then, the attacker changes the time on their computer to a future time—say, tomorrow at 6:00 a.m.—and then uses the API and their computer against the BLOB. With a six-digit TOTP code, there are only one million possible combinations of numbers. Using the API on their computer, the attacker can automate the process and guess very fast. At some point they are going to get an OK response from the API and learn what TOTP code works at future time. The attacker can then use the TOTP code to implement a future fraudulent transaction. Alexander performed this sort of test attack in his downtime to prove it could work, and it did. Luckily, he nor I am aware of this type of attack being used successfully in a real-world attack. And it just goes to seem always come.

# Defenses Against API Abuses

Now we'll look at developer and user defenses against MFA API hacking.

# Developer Defenses Against API Abuses

First, let's explore some developer defenses to MFA API hacking.

# Chapter 19 API Abuses 421

# Educate Developers

Developers should be educated about the past history of MFA solution API abuses. The inexperienced developer likely doesn't understand how APIs can be abused. Share with them the potential threats and show them real-world examples, like those discussed in this chapter, so that they can see it isn't just a theoretical concern.

# Threat-Model APIs

Any developed APIs should be threat modeled for potential risks and attacks and the appropriate mitigations implemented. If you are not sure to start, use the examples listed earlier starting places.

# Limit API Attack Surface

Minimize source code and surface area to limit what angles an attacker can attempt to abuse. With APIs, less is better for security.

# Use Industry-Proven APIs, Standards, and Protocols

As stated earlier, the industry standards and protocols as OAuth, OpenID Connect, SAML, REST, SOAP, and JSON are industry-proven methods. Nothing they do is inherently weak. Some MFA vendors try to "roll their own" methods, and in doing so may inadvertently insert security weaknesses where security weaknesses didn't need to be. Don't fix what broke. Use standards. Just make sure you implement them in safe ways.

# Validate Authentication Workflow

Many API abuses were caused by authentication workflow issues, where if something later on was correctly done, the attack would not have happened. Order matters in authentication. For example, with the Auth0 example, the authentication system was treating the alg value as valid and relying on it, which then led them to rely on the "digital signature" in the API message. The message's header and digital signature have been checked before first, relying on the information in the header.

# Lock API Keys to Locations Instead of Email

Many API uses only work because the API or API key is allowed to be used from anywhere. Today, most APIs don't care a link about origin location or tie it to a provided email address. Preregistering users/devices would prevent hackers from using the API

# Use Client-Side Enforcements Cautiously

Any time a client provides critical information that can impact authentication, that information must be validated, if possible, before accepting. Any security decision that essentially asks a client "Are you secure?" is taking a risk that an attacker

An attacker needed to change only a single value in a single API message to bypass MFA. That’s not good.

# Default Fail Closed

Whenever there is a decision between “fail open” and “fail closed,” a security vendor should choose fail close. I know that’s easy for me to write without any developer or customer responsibilities, and in practice, you need to be responsive to customer needs. But defaults matters. You can offer the fail open—just dont it as a default, because nearly everyone takes the defaults. You’re a security specialist in the 21st century. Act like it.

# Obscure MFA-Related Values

Lastly, when vendors are passing values to and from their API, it can’t hurt to use obscure naming conventions and values to make it easy for people investigating your API and messages to see what values may or not be impacting authentication decisions. Yes, this is a “security by obscurity” recommendation, but security obscurity works. It’s low cost and easy to use. A hacker seeing a field name of Field32 will have a harder figuring out that Field32 equates to a particular authentication decision.

# User Defenses Against API Abuses

User defenses against API abuses are limited, but I thought of a few good ones.

# Education

Users need to be aware that APIs can be abused, and if their MFA solution has an open API, like if any dependency, represents a potential area for exploitation. If your MFA solution has an API, like the vendor if they have threat-mode the API and implemented mitigations for weaknesses. If the vendor has not performed a threat model over their API, suggest that they do or explore what that means for your organization’s risk profile.

# Implement Secure Configuration Options

Look out for insecure default installation configurations and choose “fail secure” options when faced with a “fail open” versus “fail closed” decision. Realize that not all vendors choose default secure choices. Vendors are under lots of pressure to avoid impacting user options, even when those options could invalidate the whole reason you are using the product. Respect vendors who have secure defaults even when sometimes causes operational disruption to an “as-designed” default configuration option. We need to reward vendors who default to more security and not less.
