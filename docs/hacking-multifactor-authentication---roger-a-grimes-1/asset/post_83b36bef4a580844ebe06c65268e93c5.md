The TOTP return will be the same code every time measured during the same 30-second Epoch cycle. ## Example OTP Attacks

Like everything in the world, OTP MFA solutions can be attacked and hacked. This section examines some methods and examples.

## Phishing OTP Codes

Without a doubt, one of the most common ways to hack OTP-based MFA solutions is for the hackers to phish and intercept the resulting codes, especially if all that is needed to log on is the account identifier and the OTP code. The OTP code is essentially just replacing a password as the secret needed to get in.

The most popular hacking method to get the OTP code is similar to what was shown in Chapter 6, "Access Control Tokens," with the Kevin Mitnick hacking LinkedIn Video. The attacker somehow convinces an OTP-based MFA user to use a rogue, lookalike website that is functioning as a man-in-the-middle proxy site between the victim and their intended destination. Everything the victim types is proxy to the ultimate server/service, and everything from the real server/service is proxied to the user. When the user is prompted to enter their OTP code, the hacker grabs it and uses it to log on the real server.

With HOTP tokens, a hacker could trick a user into inputting valid, sequential HOTP codes. Maybe they create a simulated logon page that asks the user to log on. The user types in their current HOTP code, and the fake website returns an error and asks the user to type in their next HOTP code, which the fake logon website then records. The first (and valid) code is now forwarded on to the real logon portal, and the user is moved to the real website. But the attacker has a second code that they can also use. In this type of attack, the hacker could induce the victim to type in a HOTP codes, storing up multiple valid future codes. Either way, by sending the first code to the real website and redirecting the user, the users their second (or subsequent) codes are the ones that worked (instead of the first). On the legitimate user goes to log on again, because their HOTP token is now unsynchronized with the logon portal, their future codes will not work, but the attacker's list of HOTP codes will.

## Poor OTP Creation

It goes without saying that OTP solutions use tried-and-true standards such as documented in IETF RFC 2104 (OTP) and/or RFC 6238 (TOTP) are often full of calculation vulnerabilities that do not make them nearly as difficult to figure out as the vendors thought. The risk goes significantly if the OTP vendors create their own cryptographic routines. Strong and secure cryptographic algorithms are hard to create, even for the most advanced and studied cryptographers with decades of experience. If your vendor starts talking about proprietary or secret ciphers algorithms, don't walk away from them. If I get a "new" cryptographic cipher claims from a vendor who can't tell me about their new super-duper proprietary encryption scheme that has solved all the problems of the previous ones. Never has this been true. If you get told distributed-split keys, quantum-distribution, or billion-bit keys, you can be assured that the person doesn't know what they are talking about and anything they create will be worthless to waste. Only rely on used-and-true routines trusted by everyone in the public domain.

On a related note, Google Authenticator has an 80-bit seed. An 80-bit key gives a lot of potential combinations of keys (i.e., ²⁸⁰ by the official RFCs on the matter, 4226 (tools.ietf.org/html/rfc4226) and 6238 (tools.ietf.org/html/rfc6238), recommend minimum OTP seed values of 128 bits, and 160 bits (but Google Authenticator uses). OTPs should use random seed values equal to or greater the key of the involved hash. When Google Authenticator was created, SHA-1 was the most common hash and SHA-1 has a 160-bit hash. Today, the most common hash is SHA-256, meaning it is SHA-2 with a 256-bit key. Any OTP solution should use a minimum of 256-bit seed values and 256-bit hash keys.

With that said, much of the digital security protection as part of the hash's longer length is diminished diminished by truncations of the message digest from a 20-byte array into a 32-bit integer, which has 9 numeric characters, which is eventually truncated to 6 to 8 characters. In the end, the answer can have a max of 64 bits of different information. The truncated, short OTP codes are probably far too hard to crack, especially when they are only for 30 seconds.

> Soon quantum computers, with Grover's algorithm, will lessen the protective capabilities of hashes and symmetric keys to half their stated size. So, the 80-bit seed value will essentially have the security of 40 bits, and that is considerably in the range of a realistic breach.
