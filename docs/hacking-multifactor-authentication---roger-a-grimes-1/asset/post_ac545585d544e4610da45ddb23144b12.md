I think it surprised everyone in the room, including me. I think I all thought that unpatched software, buffer overflow, or some more sophisticated type of attack was going to be involved. The real answer was simple: hard-coded password problems. So, the problem persisted in one of the largest and cheapest companies in the world just a few years ago, and it exists on a multitude of systems we use all over the world.

Many computers and devices come with built-in default credentials. There are dozens of sites around the Internet that list default passwords—such as datcovery.com/rd/default-passwords—that any hacker can look up and use when faced with a device logon.

Default passwords that are never changed are so popular that malware, like Mirai bot (en.wikipedia.org/wiki/Mirai_(malware)), tries default passwords to take over vulnerable devices. Mirai bot has taken tens, if not, millions of devices (like IP cameras and cable modem routers). Those devices are then organized into huge botnets (malware networks), which then attack other devices and networks.

Defenses include implementing custom passwords for each unique device. For example, many home cable modem come now with the unique password printed on a sticker stuck to the side of the modem or device, such as its MAC address. The best solutions use unique login credentials stored in “security enclaves” like TPM chips or facilities built into CPUs and other chips.

## Insecure Authentication

Good authentication is hard to do, and there are a lot of dependencies. It is easy—probably easier—for a developer to authenticate incorrectly than insecure to do it right and securely. There are many ways a developer can mess up authentication that entire books could be devoted to just simple types of mistakes. The Common Weakness Enumeration lists 18 ways a developer can incorrectly code authentication (cwe.mitre.org/data/definitions/1211.html), and most of them have several different sub-methods listed under them. It suffices to say, doing good authentication is difficult work. Defenses include everything I will list in the “Developer Defenses Against Vulnerability Attacks”, later in this chapter.

## Cleartext Storage or Transmission of Confidential Information

Another vulnerability is the insecure storage or transmission of confidential information, either data that is supposed to be protected or some type of authentication secret. Many times, an attacker has to do so as a properly protected secret is. For example, many encrypted USB storage devices stored the private encryption key that “locked” the devices in plaintext. All an attacker needed the right equipment and software to inspect the device at the “bit level.” There have been cases where private encryption keys generated on the fly were left in what was supposed to be temporary storage areas. Or data that was wanted and designed to be sent over HTTPS was sent using HTTP instead. Defenses against inadvertently revealing confidential information include a good understanding, enforced use, and review of cryptographic systems and processes.

## Vulnerability Outcomes

The exploitation of any vulnerability can result in a myriad of outcomes, most of them can be grouped into three major categories: security bypasses, information disclosure, and denial of service.

### Security Bypass

As the name implies, vulnerabilities often allow an attacker to bypass whatever security system has in place. This is the most common type of outcome when the attack is against an MFA solution. Security bypasses range from an attacker gaining regular privileges on a device they are not authorized to be all the way up to compromise whatever the attacker can doing the device and programming is capable of without further limitations.

Some bypass attacks are known as escalation of privilege (EoP) attacks, where the attacker is elevating their current status to one with more permissions and privileges. For example, many times a hacker’s initial exploit of a device results in the attacker only getting the security context of the logged-in user or program they are using. An EoP attack allows them to gain more privileged security contexts, which permits them to do more sensitive operations and potentially damaging actions.

### Information Disclosure

This is essentially a security bypass, but one where the security bypass only allows the attacker to see information they otherwise could not. In this case, the attacker is not “in control” of the system they have compromised. They are simply seeing their default level of access should not have allowed them to see. They cannot modify or delete the information—they can only read, download, and share it. Unfortunately, most security systems exist to protect information; it is the reason for the security in the first place. Like security bypasses, information disclosures range from low risk to high risk, from the ability to see just one bit of confidential information to being able to see all on the involved system.

### Denial of Service

Denial-of-service (DoS) events allow an attacker to prevent legitimate and authorized users and systems from using allowed systems and information in a timely manner. For example, an attacker may target a web server with tens of billions of useless network packets, overwhelming the capabilities of the server, which results in “404 errors” being displayed to users trying to access it. Other types of DoS attacks can result from a vulnerability that doesn’t allow security bypass or information disclosure. Instead, it corrupts the program to a point that it can no longer run.

## Examples of Vulnerability Attacks

When I first started in computer security three decades ago, I thought that in computer security you just magically know how to stop all potential security issues. I felt I did, at least in my area of expertise. But I soon found that most programmers, even programmers of security software, had very little, innate understanding of computer security issues, including how to avoid software vulnerabilities. This isn't surprising, yet few programming schools and universities devote much time to teaching programming. Currently, I know of two universities that offer a complete course in how to program securely. So, it should be no surprise that most of our programmers, even security programmers, aren't so strong in avoiding vulnerabilities in their code.

I remember being shocked when I worked for Foundstone when they were purchased by McAfee in 2004. One of the first tasks McAfee asked us to do was a vulnerability analysis of all their software. McAfee was one of the largest sellers of computer software in the world. We found hundreds of vulnerabilities, often in a single program. At the time, I couldn't believe how many errors we found. I worried the news would leak out. Over the years, I've learned that McAfee's buggy software is not an outlier. It's normal. The reality is unusual to find computer security without a lot of bugs. Still, to this day, most security programmers do not get training in how to avoid common vulnerabilities. This includes the programs of MFA solution software.

# Uber MFA Vulnerability

The popular ridesharing vendor, Uber, offered MFA since 2015. A white-hat hacker noted a two-factor bypass in 2018 and reported it to the trusted HackerOne (hackerone.com) bug bounty program. Uber responded by saying that his finding was not substantial and that at best all we needed was a documentation update. Frustrated, the hacker contacted the media and after being contacted by a popular tech site (ZDNet), Uber finally fixed the bug and paid the hacker for the report. For over two months after it was reported, Uber did not fix the bug. For more details, see www.zdnet.com/article/uber-security-flaw-two-factor-login-bypass.
