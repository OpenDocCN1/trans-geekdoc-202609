
# 396 Hacking Multifactor Authentication

## Education

All users should be educated about malicious namespace attacks, especially common DNS tricks, including DIN and Punycode mischievousness. Users need to understand how to determine between legitimate and malicious domains and be aware of how a namespace compromise can impact their MFA solution of choice. Admins should choose MFA solutions that take namespace attacks into account and mitigate them. Users should be aware of DNS-changing attacks and malware.

## Implement DNSSEC

DNS Security Extensions (DNSSEC) is a long-standing protocol that attempts to make DNS hijacking and other malicious purposes harder to pull off for attackers. When DNSSEC is enabled, the DNS servers include digital certificates that allow them to sign their files and answer the DNS clients. Clients, when enabled, can verify that the DNS answers they receive from the verified authority servers prevent all types of DNS attacks, but it does not prevent, and for alone it should be enabled. It can even prevent routing like BGP from working. For more information on DNSSEC, see en.wikipedia.org/wiki/Domain_Name_Security_Extensions.

Sadly, even ever after a decade of attempts to get the world to embrace DNSSEC, as Microsoft, did not fully support DNSSEC for many years after it came out, and when they did, it was difficult to configure and/or not conform to open standards. Today, most DNS vendors have made making DNSSEC easier than ever to be.

In order to get the full protection, all the DNS servers involved in answering a query need to be DNSSEC-enabled. The root servers were DNSSEC-enabled in 2010. Since then, the most popular and important DNS TLD servers (COM, EDU, ORG, MIL, and others) have been enabled for DNSSEC. The only thing left is for each participating subdomain DNS server to be DNSSEC. Unfortunately, is where strong compliance ends. As of 2020, 1 percent (0.8 percent or 1.7 million domains) of COM subordinates participate with DNSSEC. You can get up-to-date statistics here: scoreboard.verisign.com.

It cannot hurt to enable DNSSEC on the servers you control. You likely enjoy its benefit by telling all DNS clients to reject any answers from DNS servers that do not have DNSSEC enabled, that would mean DNS clients would probably be rejecting 99 percent of the DNS answers they get to their queries. But for the DNS domains that support DNSSEC, it means hackers will have a harder time with malicious DNS misdirection.

## Detect and Alert on Unauthorized DNS Changes

Users systems should detect and alert on unauthorized changes to DNS settings (the HOSTS file), however that no one can guarantee that they prevent 100 percent of malicious DNS attacks. But if a significant DNS change is made, the event always generates an alert that will be read and investigated if unauthorized, you can limit the damage. DNS clients always report changes to their local HOSTS files or changes to their relied-on DNS server addresses. Both types of changes are fairly rare in most environments. DNS domain owners should get alerts of DNS server address changes and DNS record ownership changes. If you can't prevent an attack from happening, quick warning is the next best defense.

This chapter covered DNS and other namespace hijacks like BGP and ASN.1 exploits. We discussed common DNS hacking methods and seven example real-world attacks. We concluded by describing developer and user defenses against namespace hijacks.
