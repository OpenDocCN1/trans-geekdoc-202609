
# Other Common API Standards and Components

This section covers other common API standards and technologies and terms you may come across when you are looking at MFA APIs.

## RESTful APIs

You may read about RESTful APIs. REST stands for representational state transfer web service standard. A RESTful API supports and uses the REST standard, rules, and syntax to allow interfacing with it. REST is language independent and uses very common HTTP commands and syntax to connect and communicate. If you are an HTTP programmer, you can use HTTP to connect to a RESTful API. own APIs are popular and well supported by all sorts of servers and client frameworks (such as Node.js and Apache CXF).

Here is an example POST message to pass login credentials to a server with an API:

```
POST /api/auth/login HTTP/1.1
HOST: example.org
Content-Type:text/xml
<Request>
  <login name="administrator" password="password">
  <site content="/"
  </credentials>
</Request>
```

REST is not a very complex standard, which is its strength and its weakness. Sophisticated interactions are more difficult to do without lots of additional programming outside the REST standard. Every REST request, unlike the HTTP it relies on, is stateless, meaning the state of a client to a particular server is not inherited between REST transactions. REST transactions use methods like cookies and GUID numbers to track clients and servers between separate transactions. You can learn more about RESTful APIs here: restfulapi.net.

## SOAP

REST's most direct (early) competitor is Simple Object Access Protocol (SOAP). SOAP is a messaging protocol and API that uses XML to communicate data between a client and server. SOAP was created by people at Microsoft in the late 1990s and never became a standard. For nearly a decade it was a popular messaging format and API to develop, especially for enterprise apps. Here is an example of a SOAP request:

```
POST /Transaction HTTP/1.1
Host: example.org
Content-Type: application/soap+xml;charset=utf-8
<xml version="1.0"?>
<Envelope xmlns="http://schemas.xmlsoap.org/soap/envelope/">
  <Header>
  <Action soap:mustUnderstand="1"
```

```
xmlns="http://example.org/transaction">
http://example.org/IService/Operation
</Action>
<soap:Header>
<soap:Body>
<GetCount xmlns="http://example.org/TransAPI">
  <Item>345699</Item>
</GetCount>
</soap:Body>
</Envelope>
```

One of SOAP's benefits was that it used XML. Once you got used to reading XML, you could fairly quickly understand what the SOAP request or reply was attempting to do. But all the required information and using XML also made the SOAP messages "bulky" compared to alternatives, especially as compared to REST requests and replies. Many programmers were distrustful of a standard made by and promoted by Microsoft, and Microsoft was late in submitting it as an open standard, allowing other competitors to overtake.

> NOTE Another standard you may come across as Common Object Request Broker Architecture CORBA; en.wikipedia.org/wiki/Common_Object_Request_Broker_Architecture. Years ago, it was gaining a lot of traction inside enterprises, but it's now taking a backseat to REST.

REST's simplicity gained overwhelming popularity as SOAP and other earlier API standards started to dwindle. Today, SOAP and CORBA are basically “legacy” corporate standards.

## SOA APIs and Web Services

Most of today's Internet-accessible APIs, including REST, are considered part of the service-oriented architecture (SOA) style of software design. In SOA, the client requests an action or service of a server using an API over a network using one or more network protocols. If this is done over the Wide Web of the Internet, using HTTP/HTTPS, the service accessed may be defined as a web service. Web service protocols, and there are many, often defined by WI- at the beginning of their name. Web services often offer and work with RESTful APIs.

## JSON

JavaScript Object Notation (JSON) is a common way of communicating between services. JSON is based on the JavaScript language which is programming language independent. Most JSON messages are human-readable. Here is a simple example of JSON data within a message:

```
{
  "LogonName": "Administrator",
  "password": "TheyWillNeverGuess",
  "PrimaryGroup": "Administrators",
```

```
"address": {
  "streetAddress": "33 N Garden Ave",
  "city": "Clearwater",
  "state": "FL",
  "postalCode": "33755-6610"
}
```

JSON was recently involved in a Twitter data leak situation because Twitter's improperly constructed JSON headers allowed browsers to keep and leak confidential information if an intruder could get into a victim's browser cache. See twitter.com/AlexMartin/status12754396648095744. This is as low as you can get. The bigger problem would be how an attacker get access to your browser's cache, but it goes to show that JSON is now yet another dependency component we have to worry about.

## Wireless Standards and APIs

Of course, most MFA solutions rely on multiple other standards, each often with their own API (if present), as Universal Serial Bus (USB), smartcard, and Bluetooth. As covered in previous chapters, each of these is a potential area of exploitation and attack.

In this section, I want to add two points. First, none of these standards and APIs are inherently weak. They are as insecure as designed and lead to more than average exploitation. The standards and protocols I discussed here are considered poorly designed or overly. They are just another component dependency that can be a potential exploitation vector in a particular implementation.

Second, I don't want to agree here to say: No, APIs and standards change all the time—I've seen not all of them, but most of them. No doubt, some of these latest, greatest, agreed-on standards will become tomorrow's legacy standards. It could benefit the world greatly if a few single authentication and authorization standards were allowed to be the "winners" and for a significant period of time. Application developers would need to worry about creating one way of sharing authentication data and improving automation. And maybe having varying and changing standards isn't always a bad thing.

Common, long-lasting standards also mean increasing chances for single point of failures. It also gives the malicious hackers to port common way of making bad things. You will see this in computer security as the weaknesses of a computer "monoculture." Monocultures allow malware many times at once. So, common standards and APIs are a dual-edged sword, giving us the ability to work and interface across platforms but at the same time open potential vulnerabilities that might be exploited more widely.

# 414 Hacking Multifactor Authentication

## Examples of API Abuse

APIs allow malicious hackers to do bad things destructively across a wider group of people. APIs have been used to rob hundreds of thousands of dollars in seconds and to compromise accounts of very popular websites and services. The two main motives for API abuse are:

- To speed automated compromise of a single victim
- To automate attack of multiple victims

Turns out APIs are used by malicious hackers for the same reasons as legitimate programs: speed and automation. In either case, APIs can be used to bypass MFA. This section looks at APIs being used to compromise MFA solutions.

## Compromised API Keys
