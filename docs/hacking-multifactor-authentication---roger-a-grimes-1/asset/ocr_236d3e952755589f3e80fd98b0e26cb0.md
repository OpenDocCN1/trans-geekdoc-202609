The Base64 conversion, you can see in Table 6.2, results in different characters, but it definitely has an easy-to-discover, repeatable pattern. Using Base64 obfuscation, you could replace that type of vulnerability to a lesser extent with weak cryptographic hash (MD-5, LM, SHA-1, etc.). Any modifier routine that includes a cryptographic weak algorithm is itself cryptographically weak, and potentially vulnerable. Web and MFA developers should use only industry-accepted safe and secure cryptography with safe key sizes when generating session IDs.

The SHA-256 hash is cryptographically strong (at this time), and you won't find an easy-to-see pattern just by examining the hashed output. But in either case, any you get pen tester to take known account numbers or login IDs and put them through some obfuscation and hashing routines to see what comes out what you would expect to see if the developer only used a conversion or hash routine to the session ID.

For protection, it is critical that session IDs include some kind of random value that isn't easily predictable and that component added is then hashed and manipulated to create the final outcome. Perhaps the final outcome can also be tied to a time stamp and maybe even a user's previously registered device. Developers can use any value that is not known and easily guessed by an attacker. But the hashed output should not just be representative of a plaintext, sequentially updated number. Hackers follow these sessions quite quickly.

It's important to note that insecure IDs don't make session hijacking easier on websites and services. Wherever a session ID is used, including in an MFA solution, they need to be securely generated. A weakly generated session ID can bring down an otherwise solid MFA solution.
