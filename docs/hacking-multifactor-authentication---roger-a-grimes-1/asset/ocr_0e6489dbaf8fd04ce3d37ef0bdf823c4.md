# 310 Hacking Multifactor Authentication

Buffer overflows are one of the most common types of exploitable vulnerabilities. The most dangerous ones are those that reside in “listening” services or daemons. Listening means they accept incoming connections (locally on the same computer or device or over the network from other computers and devices). A vulnerable vulnerable network service reachable over the network can be remotely abused.

The fastest malware program, the 2003 SQL Slammer worm (en.wikipedia.org/wiki/SQL_slammer/), buffer-overloaded nearly every unpatched Microsoft SQL instance reachable from the Internet or from an infected computer on the local network in just a few hours using a 376-character payload against UDP (User Datagram Protocol) port 143. It did not appear to do anything other, but it spread so fast and wide that it made the closest to shutting down the Internet than any other malware program in the era (so far). Because of SQL Slammer and other malicious worms using buffer overflows, most operating system and application vendors go to great lengths to harden their services and daemons against remote buffer overflows, although buffer overflows requiring the end user to be involved (by social engineering) are still popular.

These days, most of the time an end user must be tricked into clicking on a malicious link or running a trojan horse program in order for the buffer overflow to be executed. Either attacks against programs that can be buffer overflow are among the most vulnerable. They are many different types of buffer overflows (e.g., memory corruptions, underflows, stack-based, heap-based), but most can be prevented by the targeted program preventing invalid input when requesting information. On top of that, most modern-day operating systems and some hardware have several anti-buffer overflow mechanisms built into them by these default days.

# Cross-Site Scripting

Cross-site scripting (XSS) is when a hacker inadvertently tricks someone’s local program into running their malicious code or instructions instead of displaying it as data. Let me give you my personal example from the time I was an instructor and penetration tester for Foundation (now a division of McAfee: www.macafee.com/enterprise/en-us/services/foundstone-services.html). My team was testing a new cable device for one of the world’s largest cable providers. The device was fairly sophisticated and even included a fully functional feature that any of us would be glad to have on our home networks. The firewall did not log any attacks against the cable device but logged all the detailed and payload from any network packet it blocked. We realized, almost by accident, that any HTML coding or scripting displayed in the firewall log would be executed on whoever’s browser was looking at the firewall.
