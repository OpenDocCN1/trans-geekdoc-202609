**NOTE** Some MFA tests do not call the value that a TOTP solution uses a *counter*. The *counter* value is for non-TOTP solutions.

Like HMAC-based, TOTP solutions have gained a common standard ([wikipedia.org/wiki/Time-based_one_time_Password_algorithm]) defined in IEEE RFC 6238 ([tools.iet.org/html/rfc6238]). Considered a subclass of HMAC-TOTP, OTP solutions are trusted and secure when following the same rules (i.e., shared but secret static seed value, trusted hash involved, TOTP-based algorithm involved, etc.). The only added requirement for a TOTP is a trustworthy time source for all involved authenticators that can stay in sync (“synced”) with each other.

Any trusted time source can be used and the time to be "grabbed" using any language or device, but in general the time value tends to be the (YYYY-MM-DD) followed immediately by the time (HH:MM:SS); I have also seen the hundreds of seconds as well. The date and time is usually measured in Coordinated Universal Time (UTC), which is also known as Greenwich Mean Time (GMT) and Zulu Time. UTC is usually used because it does not have to be converted and time read is often converted into other numerical values as the number of seconds since January 1, 1980 or the number of 30-second periods since January 1, 1970 (known as Epoch or Unix time: en [wikipedia.org/wiki/Unix_time]). Most of today’s TOTP solutions use “epoch time” as the time value of OTP calculation.

Many times, the difference between an HOTP solution and a TOTP solution is that the TOTP solution uses the current timestamp as the counter and HOTP uses something else. Plus, when an HOTP gives a result, it remains valid until another HOTP counter action occurs. A TOTP is always updating based on all the time, and older TOTP values automatically invalidate more frequently based on time. The distinction is that an HOTP value may potentially valid much longer, and thus attacker much longer, than a TOTP, which is always moving on.

## TOTP Popular Examples

The two most popular TOTP-based MFA examples are RSA’s SecurID and Alphabet’s Google Authenticator. RSA offers hard token and software versions (also known as “soft tokens”), whereas Google offers software-only versions that run on phones and other computing devices.

## Hacking Multifactor Authentication

RSA SecurID I don't know if RSA SecurIDs (see an example in Figure 9.1) were the first hard token TOTP-based MFA, but they have been around for decades. For many of us long-term, experienced computer security users, a SecurID was the first-token MFA device we had ever seen, and of the time, the only TOTP device we had used. If it wasn't, it was one of the most popular. The little parallel bars on the left-hand side of the token device were countdown timer bars. By by one, they went away as the time for the current TOTP code expired. When they all went away, a new code with a full set of bars would be displayed and the timer and countdown bars would begin all over again.

Eventually this requirement was relaxed or made optional that RSA could provide a more seamless experience, as some of their competitors required both the static code and TOTP. RSA SecurID and other remain among the most popular solutions today, although there is a lot competition now.

Base32 is an encoding system, using all capitalized English letters (A–Z) and numeric digits 2–7. That’s 32 characters (26 letters plus 6 numbers). Each Base32 character can represent 5 bits of information, so an 80-bit seed value takes 16 characters to send. Typing in sixteen Base32 characters can be challenging, so administrators often choose to use QR codes instead. QR codes can hold thousands of characters so it has no problem representing the 80-bit seed needed for Google Authenticator as well as what site or service the code is tied to. The user takes the received QR code and holds it up to the Google Authenticator app installed on their phone or computing device, and the code then transfers to the Google Authenticator app for that particular instance. When Google first created Google Authenticator, it was an open source application and Google shared the algorithm used. Google turned Google Authenticator and its algorithm into a proprietary app, and the open source version (github.com/google/google-authenticator) became the FreeOTP project (en.wikipedia.org/wiki/FreeOTP), which is now used by Linux distros, as RedHat. The initial open source nature of Google Authenticator allowed anyone to see the original Google Authenticator algorithm. The Google Authenticator is posted on the Google Authenticator Wikipedia page (en.wikipedia.org/wiki/Google_Authenticator) and is implemented in an open source project called Pharo (smalltalk.com/#!-SvenvanCaenberghe/GoogleAuthenticator). Figure 9-4 shows the Wikipedia description/pseudo-code of Google Authenticator's TOTP generation.

```function GoogleAuthenticator(string secret) {
  message := floor(current time / 30)
  hash := HMAC-SHA1(secret, message)
  offset := last of hash
  truncatedHash := hash[offset:offset+4] // 4 bytes starting at the offset
  set first bit of truncatedHash to zero // remove the most significant bit
  code := truncatedHash % 100000
  pad code with 0 from the left until length of code is 6
  return code
}
```

Figure 9.4: Wikipedia description/pseudo-code of Google Authenticator

Pharo allows anyone to code a virtual instance of Google Authenticator. So far, it does not seem as if the underlying algorithm has changed since Pharo was created. Pharo's author created a document that steps through the Google Authenticator algorithm (medium.com/concerning-pharo/the-code-behind-google-authenticator-95c9cc06a572). It should not be surprising that the Google Authenticator algorithm, although fairly simple, goes through a lot of conversion steps, and so it appear complex to someone unaccustomed to programming, computer cryptography, and byte conversions.

Here's an example conversion routine based on the Google Authenticator algorithm according to Pharo's author:

- 1. The 32-character Base32 key (seed value) is used and converted to a byte array.
- 2. The current time is taken and converted to Unix/Zulu time, which is the number of 30-second time periods since January 1, 1970.
- 3. The secret value and time value are used in HMAC-1 hashing event, with the secret value as the secret key and time value as the message acted upon by the hashing algorithm and secret key.
- 4. This outputs the 160-bit results from the hash calculation (i.e., the hash).
- 5. The 160-bit SHA-1 result is converted to a 20-byte array.
- 6. The 20-byte array is converted into a 32-bit integer, which has 9 numeric characters.
