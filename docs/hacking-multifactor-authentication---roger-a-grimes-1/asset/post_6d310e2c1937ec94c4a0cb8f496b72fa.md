## DNS

We'll cover a few types of namespaces and attacks in this chapter, but certainly attacks against DNS are the most important and popular. DNS (along IP addresses) is the backbone of our Internet, and the majority of organizational networks use it to work.

DNS converts the "common names" you type in or click, such as www.google.com, to officially registered IP (version 4 or 6) host addresses (e.g., 104.117.113.180, 16A7:F1ED:10B2:51:8, etc.) by Internet routers before the senses to transmit intended communications. Each computer or device accessible directly from or to the Internet must have a unique (fully qualified) DNS name and associated (public) IP address.

> NOTE Directly contactable Internet devices must have "public" IP addresses, but one private, non-unique, addressable IP devices using a protocol known as Network Address Translation (NAT). But public IP addresses can be routed to and from directly on the Internet. There are millions of private IP addresses that anyone can use on their private networks as long as they don't try to connect them directly to the Internet.

## Chapter 18 DNS Hijacking

DNS was officially put to use on the Internet in 1983. Prior to DNS, each communicating computer or device that wanted to connect to another computer or device across the Internet (at the time called ARPANET) had to use the destination computer's IP address, even though most computers also had more typed-in English-language hostnames. The humans using and configuring these computers were not as good at remembering a bunch of long numbers (i.e., IP addresses) as were hostnames. Everyone agreed that using hostnames for connections would be easier; they just needed a method for converting hostnames to IP addresses.

Initially, computers' operating systems (and/or applications) were updated to include and use a file named hosts (or hosts, hosts.TXT, hosts.txt), which listed the names of the desired computers followed by their IP address. Users could then use a computer's hostname and the OS or application would look to the HOSTS file to convert the hostname to an IP address, which it then needed to connect to the destination computer(s).

> You can still find a HOSTS file on most computer systems. In a Microsoft Windows computer, the HOSTS file is located under \Windows\System32\drivers\etc.

This method still required a local or human process to update the HOST file on each participating computer with the necessary computer hostnames and IP addresses. Most of the time, because of previous queries, at least a few of these are already cached in memory.

DNS provides services to DNS clients. DNS clients point to DNS servers. For example, when someone on the Internet types www.knowbe4.com on their computer to look for the KnowBe4, Inc. website, their computer typically does a DNS query that looks like

- It checks to see if the IP address of www.knowbe4.com is already cached in memory from a previous query.
- If not, the application/OS checks the HOSTS file.
- If it is not located, the DNS sends out a single DNS query to its locally defined DNS server essentially asking, "What is the IP address for www.knowbe4.com?"
- The local DNS server returns the IP address if it is already cached in its local memory from a previous query, and if not, may or not check its own HOSTS file.
- The DNS service checks its own DNS database if it is authoritative for the domain (i.e., knowbe4.com) being requested.
- If the DNS answer is not in either location, or if DNS server does not respond, the server attempts to ask another DNS server to resolve the query or directly connect to the "root" DNS servers.

Most DNS servers are configured with a list of 13 root DNS servers (www.iana.org/root/servers/), which then point to the TLD DNS servers that are authoritative for the TLD domains. Most of the time, because of previous queries, at least a few of these are already cached in memory.

- The querying DNS server asks the TLD domain I am requesting? (COM in this example).
- The root DNS server returns one or more IP addresses of TLD DNS servers for the TLD.
- The querying DNS server directly connects to the TLD DNS server that is returned and asks the TLD DNS server, "Where is the authoritative DNS server for the subdomain I am requesting? (knowbe4.com) in our example.
- The TLD DNS server returns the answer.
