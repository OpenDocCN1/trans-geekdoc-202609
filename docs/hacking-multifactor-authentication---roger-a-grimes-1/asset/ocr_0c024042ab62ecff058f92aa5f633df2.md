# Chapter 10 Subject Hijack Attacks

Every MFA solution is tied to one or more subject identities. In AD, smartcards are tied to different user accounts using the user's Principal Name (UPN). The UPN value is defaulted to the user's logon name followed by an @ sign and the user's Active Directory domain name (e.g., roger@knowbe.ad), but can be many other custom values. A populate UPN format is the user's address (e.g., roger@knowbe4.com), which may or not be the same as the user's default UPN or Active Directory domain. A user can have only one UPN at a time, and it must be unique in the Active Directory forest. If an AD administrator fills out a user account field labeled Logon Name (see Figure 10.1). In the Figure 10.1 example, the user's logon name is Super Admin, the AD forest is victim.com, and so complete UPN is SuperAdminvictim.com (letter case does not matter).

When a user smartcard is created with Active Directory, the user's UPN is written as a value in a x.509 certificate called Principal Name under the Subject's Subject Alternative Name field (see Figure 10.2 for an example). A cert's Subject Alternative Name has a lot of values (e.g., LDAP, DNS, IP address, Common Name, NetBIOS). A UPN is just one type of value, but it must be present for the user's account. When a user logs in using a smartcard, Windows and Active Directory lines link the smartcard to the appropriate account using the UPN field.

When the user logs using a smartcard, they don't type in their username. Instead, they insert their smartcard into the computer's smart reader (or it is wirelessly read for contactless smartcards), and Windows (if smart enabled) receives the logon event and automatically takes the logon identity from the smartcard's UPN value. If a smartcard has multiple smartcard certificates, the user will be prompted to choose which smartcard certificate to log on with. The user's input PIN is passed to the smartcard and the evaluation of whether the correct PIN will be completely up to the smartcard and its own operations. Windows and Active Directory are not involved in the actual authentication event that determines success or failure other than passing the information to and from the smartcard. All of the actual authentication and processing is performed within the secure confines of the smartcard's integrated circuit.

After the user successfully authenticates, the user's public portion of the smartcard certificate is transferred to the user's local certificate store, and Active Directory looks up the UPN of the certificate to confirm that it exists in the AD forest. Once, the logon is mapped to the user's account which contains it, and the user is assigned a Windows/Active Directory access control token.
