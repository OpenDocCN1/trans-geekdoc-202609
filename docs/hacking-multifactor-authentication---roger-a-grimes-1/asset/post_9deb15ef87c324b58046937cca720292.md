# 1FA vs. 2FA vs. MFA

A single-factor authentication (1FA) requires only a single authentication proof for a subject to successfully authenticate. A two-factor authentication (2FA) requires two authentication proofs, and a multifactor authentication (MFA) requires two or more factors. All other things being equal, MFA is usually (but not always) better than single-factor authentication for better security, although a single MFA solution is rarely universally allowed across all subject scenarios, so 1FA or multiple MFA methods will usually be needed.

> NOTE MFA includes 2FA, and many people will say MFA when speaking only about 2FA, and vice versa (even though MFA isn't 2FA if it includes more than two factors).

For authentication factors to provide the best security protection in a multifactor process, there should be different types of factors. Using two or more of the same factor is still better than using a single factor when authentication but isn't perfect when using different types of factors. The thinking is, for example, that an attacker will have a harder time phishing a user may know (e.g., password, PIN) and a physical device the user uses to log on at the same time. So, all things considered equally, multiple factors of different types is preferred over multiple instances of the same type of factor.

You will sometimes hear about MFA solutions that have more than three factors (e.g., five-factor), but what these solutions are usually referring to is multiple instances of the same three traditional factors. In order for the factors to be most protective in an MFA solution, they should be different.

# One-Way vs. Mutual Authentication

Authentication is normally conducted between two or more parties, often referred (as covered in Chapter 1) to the server (the object/application/process being authenticated to) and client (the object authentication to the server), and can be one-way or two-way (also known as mutual authentication).

Many authenticating objects can act as both a server or a client depending on the reason for authenticating. This is to say, a physical server isn't always acting as a server and a client isn't always acting as a client. Additional servers may also be involved in the authentication process, and there may be multiple authentications occurring during a single authentication event. A good example of that is Kerberos, where the client must authenticate to the Kerberos server as well as the intended target server.

Most authentication is one-way, meaning the client authenticates to the server or the server to the client, but the opposite is not true, at least during the same authentication event. A common example of this is webs using HTTPS. When HTTPS is used, the web has an HTTPS/TLS digital certificate, which is linked to and asserts to the server's identity (usually by DNS address or hostname). When a client connects to the web server over HTTPS, the website sends its digital certificate to the client to prove its identity and to an encrypted channel to generate symmetric key material. The client receives the server's digital certificate and verifies its trustworthiness. If successful, the client will trust the website to be the website it says is (based on the subject's identity). In one-way authentication, the client does not prove its identity to the server, at least within the same authentication transaction.

With two-way, mutual authentication, both the client and server authenticate to each other as part of the same authentication process. If either side fails, the authentication fails regardless of the success. Kerberos is a good example of two-way authentication. Two-way authentication is more secure than one-way authentication, but one-way authentication is significantly more used (at least currently) because two-way authentication is more complex to set up and accomplish, and it's subject to increased failures. For reason, most authentication mechanisms use only one-way authentication or rely on two, one-way, authentications.

For example, a banking website may authenticate itself to the user using a TLS digital certificate and the user might authenticate themselves to the website using a logon name and password after establishing the TLS trust. These are two one-way authentication events, and they are not, all things considered equal, as secure as a simultaneous two-way authentication logon.
