NOTE Microsoft is desperately trying to eradicate users who use older legacy protocols which do not support MFA. Microsoft understands the weaknesses of using older legacy protocols, but when you have hundreds of customers, shifting off older, weaker protocols takes much longer than you would think.

It is very common for trusted services to access other services using programming interfaces (APIs). While doing services cannot easily (or at all) log on the other service using MFA. So, instead the services are not required to log on all, they are allowed to use hard-coded credentials, or they can use else to mitigate the risk. An attacker knowing that MFA is not required and knowing what mitigations may be used to log on or an otherwise MFA-required service. For example, in this blog article (www.agilepointinxblog.com/bypass-multi-factor-authentication-in-office-365), the researchers revealed that many 365 APIs are locked down using only IP addresses. The involved parties often lock down the APIs so that they can accept only logins from predefined, trusted IP addresses while every other connection from anywhere else will require MFA. An attacker learning this information could modify the IP address range to include an IP address they are originating or make sure they originate logins from the previously approved IP addresses. Other types of API attacks will be discussed in Chapter 19, “API Abuses”.

Fake authentication can be very difficult to detect and stop. It's even difficult to blame the MFA solution developers. The MFA developers might have done everything within their control to ensure that their MFA solution, when used correctly, prevents bypasses and hacks. But in fake authentication instances, the hackers are simply simulating the MFA solution experience or bypassing MFA being demanded. Using fake authentication, the hackers can trick the user into revealing confidential information or performing other actions that are contrary to the victim's own self-interest.
