This is not to say that this type of maliciousness cannot be noticed and stopped. The changing of the UPN usually creates an event in the Windows log file that shows the UPN is changed and what it changed to. Unless someone was looking for that and alerted on it, it would probably go unnoticed. And there are some log events, such as Event ID 4768, registered at the involved domain controllers which would include such smartcard's fingerprint, which would be reviewed as evidence to reveal that the Help Desk user's smartcard was somehow associated with the Super Admin account. But forensics investigators would have to be aware of and to validate this particular hack scenario. We would have to know that a particular certificate printed to the Help Desk user and not Super Admin. It would be something most people looked for unless they knew it was even a possibility and what to look for. Even then, it's such a rare case (i.e., it's never been done in the kind I of), that it's probably not going to be the first thing most incident responders check for. It's not going to be what most incident responders ever check, first or last. Beyond the people reading this chapter, perhaps a few dozen in the world would know about this link between smartcard and AD, and how it can be abused. Welcome to a very small group.

There are other related hacks. For anyone who is able to generate a trusted smartcard that anyone else can log as that user. In the first example, we modified the Super Admin's UPN to helpdesk@victim.com. But we could simply generate a brand-new smartcard that contains the UPN of superadmin@victim.com and be able to log as Super Admin. I've done this technique using a "foreign" CA (i.e., a CA belonging to another organization) that was simply installed as a CA in the victim organization. The foreign CA can generate smartcards with the victim's UPN. Again, the only evidence a forensic examiner might find is a certificate fingerprint in the logs that doesn't match the Super Admin's certificate thumbprint.

To be clear, this is not a real hack or bug. Microsoft is not going to fix this. This is an "as-designed" outcome in which the Active Directory-integrated smartcards work. Smartcards are tied to a user's UPN and the Help Desk user changed UPNs. So, in Active Directory's defense, it did map the "user account to the authenticated smartcard as was defined in Active Directory. Active Directory has no way of knowing which UPN is the correct UPN over.

The defense to the smartcard hijack attack is not able to make sure unauthorized UPNs and to prevent smartcard administrators from simply creating any smartcard with any UPN they like. More realistically, log UPN changes (there are legitimate reasons why they occur as due to changes from marriage and divorce) and make sure the change was authorized. And make sure you trust your admins. Administrators are very powerful accounts that can do a lot of malicious things, well beyond just hijack attacks. You need to make sure your admins are trustworthy as rule #1.
