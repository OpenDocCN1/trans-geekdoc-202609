Still, deciding on the "right" account lockout policy is not an exact science and is debated even within Microsoft, who thought about it more than most. For example, their Azure Directory default settings are 10 guesses in a row leads to a one-minute lockout (docs.microsoft.com/en-us/azure/directory/authentication/howto-password-smart-lockout). Each bad guess after 10 leads to a 1-minute or longer lockout for each additional bad attempt. Microsoft Active Directory Federated Services (ADFS) has different account policy recommendations depending on the feature being used and docs.microsoft.com/en-us/windows-server/identity/ad-fs/operations/configure-ad-fs-extranet-smart-lockout-protection and docs.microsoft.com/en-us/windows-server/identity/ad-fs/operations/configure-ad-fs-extranet-smart-lockout-protection). There are differences between on-premises Active Directory user accounts and those same entities in the Azure cloud. It just goes to show that any account lockout policy is not an exact science. There is no "right" policy.

With that said, I think having any account lockout policy with any reasonable setting is better than having no policy. That's because when you enable account lockout policy, when someone or something makes guesses too many times, systems will generate an account lockout security event, and that event can be sent to an alerting mechanism and can be investigated. It's another tool in a defense-in-depth strategy to help defeat malicious hackers and malware. Without account lockout, most enterprises would probably be unaware that a bunch of bad password attempts were happening (either unintentionally from misconfigured scripts and tools or from malicious hacking).

Perhaps they had a history and experience of many "bad" logs inadvertently caused by legitimate users, just below that they should need. Maybe they read one of my previous books where I was recommending the sets at above 100 bad attempts because of my belief that a strong password policy needs a strict account lockout policy. In any case, when you are using MFA it's because you've decided to use stronger security than what is normally provided with passwords. MFA solutions should use stricter account lockout policies by default, especially when the number of characters a malicious hacker may have to guess is only 4–6 digits long and contains only numbers. What number should it be, I'm not sure, but should be at a level that reasonably protects users and prevents hacking attacks from being successful. Without relevant, contradictory facts, allowing 250 bad attempts per IP address at the same login doesn't seem like a reasonable policy.

Many MFA solutions allow multiple code attempts at one time against the same MFA instance. I'm not sure why more than one within a reasonable time period (say 2 seconds) should ever be allowed. Anything faster than that is indicative of automated brute-forcing and should be prevented.

## Black Rogue IP Addresses

Multiple bad attempts from the same IP address force the IP address to be blacklisted that no further attempts are allowed for a long period of time (say months), or a manual process must be accomplished to get the IP address "unblacklisted" for future attempts. Security logs should log attempts and alert on obvious brute-forcing attempts.

> NOTE: When you're locking out future attempts from IP addresses, take care to confirm that the originating IP address is the true originating IP address. You don't want to block addresses that are just being forged in the IP packet header by attacker hoping the IP address forged fraudulently gets locked out, causing a DoS event to the legitimate owner. Typically, all that is needed to confirm the originating IP address is the "true" IP address is a completed TCP handshake. The connection-oriented, three-way TCP network handshake (i.e., ACK, SYN-ACK, ACK) is intended exactly for purpose. For course, an attacker could be temporarily controlling an otherwise innocent host or doing some sort of "reflection" attack, but make at least an attempt to verify the originating IP address is the originating IP address of an attack blocking.

## Increase Wait Time Between Each Allowed Guess

Each bad attempt should be penalized with longer and longer waiting periods before another attempt, successful or not, can be attempted. For example, 10 seconds should go before a second attempt can be made, 30 seconds and 60 seconds before a third attempt. Microsoft implemented this sort of rate-limiting control in Windows for regular logins with its latest versions, and it has been effective at slowing down automated guessing attacks. Trusted Platform Module (TPM) chips have the same mechanism enabled for entering the wrong TPM PIN to lock their secrets. I remember correctly, TPM version 1.2 had a setting wait between guesses and after two guesses locked out the user until some extraordinary reset event was accomplished. TPM version 2.0 chips implemented an increasing and random minimum time limit between incorrect guesses but don't lock out the chip permanently or require a hard reset no matter how many guesses.

## Increase the Number of Possible Answers

Increase the number of possible answers so that it is harder for a brute-force guesser to be successful. Requiring six-digit PINs (1,000,000 possible answers) is far better than four-digit PINs (10,000 possible answers). Having more possible answers just makes the brute-force guessers take longer. This is where non-OTP MFA solutions gain an advantage.

## Enforced Answer Complexity

If possible, require a larger number of possible characters allowed or required. With most PINs use only numbers 0–9, that is hard to do. But if a MFA solution allows letters and symbols to be used along with numbers, it's so better. If it requires them, so much the better. Allowing or requiring greater character complexity increases the number of possible answers and makes the brute-force attacker's job harder.

Offsetting this is the fact that users don't want to use an OTP solution that uses something besides numbers. There have been a handful of OTP solutions in the past that used character types than numbers, and all eventually failed in the marketplace. A better solution for any MFA vendor is to allow customers or admins to choose among required sets. Some admins and, desiring stronger security, require complexity. Others can disable complexity or leave it at the default or using numbers only. That way, you get the best of both worlds that satisfy the security-minded and less friction at the same time.

## Send Emails to Warn End Users

All MFA users should be warned if their devices or accounts were involved in multiple bad attempts. The user should be aware of the issue and can determine whether it came from something they did, a broken faulty, or a legitimate process, or was the result of some hacker attack. Either way, the user should be aware of the multiple bad attempts, along with the relevant details, so that they can make the appropriate response to the risk.

## User Defenses Against Brute-Force Attacks

Sadly, there isn't lot an end user can do to prevent brute-force attacks, especially when using OTP-based solutions. Most of the possible controls the only "control" a user has is when buying or renewing a particular solution. If you or someone else discovers a new brute-force attack against your MFA solution, you hope the vendor acts and closes the hole quickly.

## Education and Using Only Solutions That Fight Brute-Force Attacks

MFA solution buyers should be aware of brute-force attacks and ask the right questions investigating a new MFA solution. Don't always assume your or a solution you are looking for has defense against brute-force attacks. All the users of the previous examples thought, "Sure, account lockout is enabled"—and it wasn't. Ask your vendor. And if they don't have account lockout, insist that it be enabled at a reasonable value.
