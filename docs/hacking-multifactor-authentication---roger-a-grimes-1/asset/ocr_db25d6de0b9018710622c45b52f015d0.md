# Chapter 22 Designing a Secure Solution

Once the user confirms the green OK, they are shown a logon screen and asked to authenticate. The voter is asked to type in their voter ID and OTP code (plus the voter's four-digit static personal knowledge at the beginning). The entire authentication process and application is loaded and originates from the MFA solution's secure enclave, much like a smartcard. The session shown is a virtual session, protected by a hardware hypervisor to prevent tampering. All voter inputs are selected using touch-screen or mouse inputs. No keyboards are used to prevent easy keystroke logging. If higher security is desired, all inputs could be made by the MFA device by a button or voice interface, as is often used on portable media players and voice recorders. Either way, great care should be taken to make sure the selections are recorded onto the voter's ballot within the secure confines of the MFA-provided application and hypervisor. It should be nontrivial for the MFA-protected session.

The hardware hypervisor should protect the electronic ballot from nontrivial eavesdropping or tampering. There are occasionally ways to hardware-based hypervisors to do "host-to-client" or DoS attacks, but doing so is not easy. Most hypervisor vulnerabilities can be remedied with a firmware or software update.

The OS and application should have minimal lines of code and footprint down on possible attack vectors. All communications outside the secure enclave should be accomplished using a Transport Layer Security (TLS)-VPN to predefined IP addresses or domain names.
Perhaps if the device is started up and finds no active ballot to download, it tells the user and either it powers off after a few minutes or allows the user to perform a simulated ballot demo. Technical supports websites and phone numbers should be physically located on the MFA device and displayed whenever the device boots.

The OTP code can be event based and key each new election ballot package, or like a regular TOTP device, generate codes all the time. If it is event based (HOTP), the device should use the Initiative for Open Authentication (OATH) Challenge-Response Algorithm (tools.ietf.org/html/rfc6287) and incorporate critical parts of the ballot information and voter's response to that of the challenge-response.

By the entry of the OTP code (either HOTP or TOTP) by the user into the voting software or process must require the four-digit static code in addition to the OTP code. The OTP code display on the device should have a physical printed area or sticker reminding the voter of the need for both portions, as something similar to "Don't forget to enter in all codes using your 4-digit PIN plus the code here: XXX-XXXXXX or something like that. The screen can require the two needed codes separately as well

Any OTP code should use open standards and processes, such as discussed in Chapter 9, "One-Time Passwords." OTP codes should expire in a reasonable amount of time. OTP codes should use Dynamic Symmetric Key Provisioning Protocol (DSKP) to securely generate shared seed values on a regular basis.
