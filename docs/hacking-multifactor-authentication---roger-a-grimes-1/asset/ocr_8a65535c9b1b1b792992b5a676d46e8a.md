# SDL Design

All design starts with the Security Development Lifecycle (SDL). All programmers and designers must be trained in SDL ideas, processes, and tools before being allowed to be a contributing member of the project. All programming tools used should have secure default settings. High-risk security methods must be banned. Programmers should know the basic threat models currently under consideration and be asked if they know additional ones. They should be shown the components and the 10 general ways each of them can be hacked

All code should be checked for vulnerabilities before being allowed to be submitted as "checked-in" to the source code repository. Each programmer should review their own code for security bugs and submit it to other team members for review. Rewards could be offered for the code with the least number of lines of code and for the most number of bugs found by someone. Source code review should be done with automated tools by internal parties and by humans—as external reviewers and testers. It is important to conduct external reviews on at least a biannual basis. Source code should be released for public, and an official bug offering thousands of dollars in rewards should be established at one of the reputable bug bounty sites. Reported bugs should be investigated aggressively. Bug report ever, be treated with dignity and respect. Vendors should monitor bug payment payments and the dark web. When reasonable, any verified bugs should be purchased to prevent them from leaking outside the commercial bug sale service. Any known critical security bugs should be responsibly disclosed in a timely manner (no more than a few months) after patches (if reasonable and possible) are available.

The MFA solution should have automatic updating and should check automatically for updates time it is powered up and at least least daily. There should be no end-user involvement or approval needed. Only code digitally signed by an authorized agent should be allowed to update the MFA solution. All updates must update SDL processes. A failure to successfully update when vulnerability is involved should result in additional attempts to the device or a "hard" locking of the device to prevent it from being used with a known vulnerability. Applied updates should not be able to be reversed by emergency orders with an authorized digital signature, if at all.
