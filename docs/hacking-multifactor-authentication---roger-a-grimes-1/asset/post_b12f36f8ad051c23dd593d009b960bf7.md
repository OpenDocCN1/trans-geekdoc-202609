There are a myriad of ways to show dependent component attacks, but in this chapter I'm going to show a simulated subject identity hijacking involving Microsoft's Active Directory and smartcards. Before I show the hack demo, I need to quickly explain what Active Directory is and how it works with smartcards.

## Active Directory and Smartcards

Microsoft Active Directory (AD) is easily the most popular enterprise network directory and authentication service in the world. Based on open standards, Lightweight Directory Services and its Directory Access Protocol (LDAP) was introduced by Microsoft in 1999 along with Windows 2000. It is, at its most basic level, a database for serving and storing local objects, such as user accounts, files, printers, and their attributes (i.e., fields and data). It can also be used for authenticating users, groups, computers, and other participating subjects against protected objects (e.g., servers, folders, services). Today, AD is also supported in the Microsoft Azure cloud, although the cloud version is currently not as feature-rich as the "on-premises" version is. Microsoft likes to plan how their cloud makes an irresistible "must-buy" for enterprise users.

Active Directory supports smartcards and has since the beginning of AD, although newer versions of Microsoft Windows and AD support more functionality and flexibility than earlier versions. As previously covered in Chapter 3, "Type of Authentication," traditional smartcards are physical devices about the shape of a thick credit card, which contain a digital certificate with an Object Identifier (OID) field containing the following value: Smart Card Logon (1.3.6.1.4.1.311.20.2). Applications accepting smartcards for this particular OID value.

Some smartcard-enabled applications will accept non-smartcard OIDs, client (1.3.6.1.5.573.2), and server (1.3.6.1.5.573.1) authentication, as example alternatives. But officially, any smartcard-using application should explicitly look for and accept only the one, which is Smart Card Logon OID (1.3.6.1.4.1.311.20.2). The smartcard OID supposedly means the digital certificates that have been securely generated and the associated private keys have only been generated and stored on the smartcard's chip.

The smartcard usually contains both the public and private keys of each digital certificate. The smartcard's integrated circuit chip cryptographically protects the private key of stored certificates from ever being exposed by external programs or intruders. The private key is stored on the card and remains there, even when used. Most smartcards require a PIN to be entered as a second factor whether the digital certificates on the card are to be used. Smartcards are tamper-resistant and may be disabled if someone tries to hack them or physically access them (although Chapter 17, "Physical Attacks," will cover how to successfully attack them).

## Chapter 10 Subject Hijack Attacks

Every MFA solution is tied to one or more subject identities. In AD, smartcards are tied to different user accounts using the user's Principal Name (UPN). The UPN value is defaulted to the user's logon name followed by an @ sign and the user's Active Directory domain name (e.g., roger@knowbe.ad), but can be many other custom values. A popular UPN format is the user's address (e.g., roger@knowbe4.com), which may or not be the same as the user's default UPN or Active Directory domain. A user can have only one UPN at a time, and it must be unique in the Active Directory forest. If an AD administrator fills out a user account field labeled Logon Name (see Figure 10.1). In the Figure 10.1 example, the user's logon name is Super Admin, the AD forest is victim.com, and so the complete UPN is SuperAdmin@victim.com (letter case does not matter).
