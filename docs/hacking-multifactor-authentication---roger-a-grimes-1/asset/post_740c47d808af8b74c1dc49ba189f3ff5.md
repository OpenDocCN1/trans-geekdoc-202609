## Buffer Overflow

A buffer overflow happens when a program expecting a certain type or range of data as an input gets something else that overwrites the storage area set aside for the input. For example, the program may have a field asking a user for their first name. The programmer expected someone to type in Roger, Richard, or Ángela, or something like that. But instead, a hacker in a bunch of executable code, which overwrites not only the storage area aside for the first and other inputted data, but also the current executable code that is part of the programming. The data is essentially overwriting and rewriting the program's coding instructions (as conceptually diagrammed in Figure 15.2). If the overflow can be done “neatly” without causing the program to lock up or quit, there is a chance that the hacker's executable code will start being executed instead of the original program. The overflow usually results in the attacker's program running in the security context as the program that was overwhelmed.

## Hacking Multifactor Authentication

Buffer overflows are one of the most common types of exploitable vulnerabilities. The most dangerous ones are those that reside in “listening” services or daemons. Listening means they accept incoming connections (locally on the same computer or device or over the network from other computers and devices). A vulnerable network service reachable over the network can be remotely abused.

The fastest malware program, the 2003 SQL Slammer worm (en.wikipedia.org/wiki/SQL_slammer/), buffer-overloaded nearly every unpatched Microsoft SQL instance reachable from the Internet or from an infected computer on the local network in just a few hours using a 376-character payload against UDP (User Datagram Protocol) port 143. It did not appear to do anything other, but it spread so fast and wide that it made the closest to shutting down the Internet than any other malware program in the era (so far). Because of SQL Slammer and other malicious worms using buffer overflows, most operating system and application vendors go to great lengths to harden their services and daemons against remote buffer overflows, although buffer overflows requiring the end user to be involved (by social engineering) are still popular.

These days, most of the time an end user must be tricked into clicking on a malicious link or running a trojan horse program in order for the buffer overflow to be executed. Either attacks against programs that can be buffer overflow are among the most vulnerable. There are many different types of buffer overflows (e.g., memory corruptions, underflows, stack-based, heap-based), but most can be prevented by the targeted program preventing invalid input when requesting information. On top of that, most modern-day operating systems and some hardware have several anti-buffer overflow mechanisms built into them by these default days.

## Cross-Site Scripting

Cross-site scripting (XSS) is when a hacker inadvertently tricks someone’s local program into running their malicious code or instructions instead of displaying it as data. Let me give you my personal example from the time I was an instructor and penetration tester for Foundation (now a division of McAfee: www.macafee.com/enterprise/en-us/services/foundstone-services.html). My team was testing a new cable device for one of the world’s largest cable providers. The device was fairly sophisticated and even included a fully functional feature that any of us would be glad to have on our home networks. The firewall did not log any attacks against the cable device but logged all the detailed and payload from any network packet it blocked. We realized, almost by accident, that any HTML coding or scripting displayed in the firewall log would be executed on whoever’s browser was looking at the firewall. We sent a small “Hello World!” scripting test to the firewall on a blocked port, and so enough, when we looked at the firewall log using a browser, a “Hello World!” message popped up—confirmation of the cross-site scripting vulnerability.

Someone on the team—I forgot who, but it wasn’t me—created a malicious script and “attacked” the firewall. We then called the cable company’s technical support team and pretended to be regular cable customers who believed we were being attacked by hackers. We asked the technical support person to look at our firewall if we were indeed “attacked” to confirm our suspicions. They agreed to look at the firewall logs, and when they did, their Linux-based system sent us their passwd and shadow files (the password files on a Linux system). The stolen credentials worked across every computer in their corporation. So, from a single XSS vulnerability in a single product, we were able to take over the entire corporation. You can see why this is my favorite story.

Another common XSS example is an example of what is called a reflected XSS attack. An attacker sends you a link that looks like any link you would click on and use to visit a website. Unknown to the user, it has additional commands to the end of the link that executing extra, malicious content. For example, you link to connect to a website that looks familiar to you, but the link not only goes to that website, but also abuses a feature of that website allows users to be redirected somewhere else. Here’s an example: www.reddit.com/r/sysadmin/comments/d9dnf/heres_a_phishing_url_to_give_you_nightmares/. In this instance, any user connecting on have been redirected to a website of the attacker’s choosing (before the bug was corrected). An attacker would usually redirect the user to a look-alike website and then get them to download trojan Adobe software.

Defending against XSS attacks relies on any program that can accept and display scripting or coding to ensure that the scripting or coding is always displayed like regular data or writing and not executed. For example, web application developers need to write or use mechanisms to sanitize inputs by looking for and removing “escaping” characters that often get used to indicate to a browser that a script or piece of code is involved or being injected. In general, developers should always sanitize inputs to ensure clients only enter the specific type of data required for that particular input. Nowadays, programming tools use sorts of input sanitation controls built in, but they aren’t always enabled by default and it’s up to developers to take advantage of them.

## Directory Traversal Attacks

Directory traversal attacks are a vulnerability where an attacker tries to navigate to otherwise security-protected directories, files, and folders without supposedly being allowed to go to those locations or the parent folders. A good, super-simple, example is suppose that I can get to the folder C:\child when I’m not allowed to get to C:\ or C:\parent. Simply having and using the full pathname (i.e., C:\parent\child) allows me to bypass the parent directories I had less permissive access.

A real-life example of a common hacker directory traversal bypass test string is ../ or something like that. The forward slashes represent folder subdirectories and the dot-dot (...) represents a parent folder in many operating systems.
