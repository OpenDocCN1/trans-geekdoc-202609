## Use Industry-Accepted Cryptography and Key Sizes

If cryptography is involved, use industry-accepted cryptography and key sizes. Don't try to make your own. Many developers have taken a cryptography course or they think they can create a new cryptography solution that is uncrackable. Few of them can. Strong cryptography is much more difficult than it seems, and only a few people in the world at any time are good at it. Unfortunately, thousands of people think they can design a stronger cipher. Even the very best cryptographers get it wrong.

As an example, the National Institute of Standards and Technology (NIST) received 82 proposed quantum-resistant cryptography candidates during round 1 of its post-quantum cipher contest (csrc.nist.gov/SRC/media/Projects/Post-Quantum-Cryptography/documents/call-of-proposals-final-dec-2016.pdf). Most of these submissions were highly respected, experienced cryptographers, with PhDs in cryptography. Of those original 82 submissions, only 26 were selected to compete in the next round. Although there were other disqualifications and consolidations, most of the rejections were because of obvious cryptographic flaws that others easily discovered. Of the 26 remaining candidates, observers are still finding errors. Some promising candidates turned out to have huge cryptographic flaws that, had been prematurely implemented, would have caused security issues.

And this is the result from experienced cryptography professors and practitioners. Good cryptography takes many years and a lot of testing to prove. If cryptography is your day job, don't even think about trying to invent your own cryptography when many other great candidates already exist and are trusted as secure around the world. Don't try to prove how smart you are. Just use industry-accepted cryptography and key sizes.

For bonus points, code your application in such a way that the cryptography used is easily changed (crypto-agile) as new cryptography and schemes become available as recommended replacements. It makes it so that your customers can easily upgrade and replace them without having to do a complete installation or replacement. Don't hard-code the cryptography in a way that is not easily replaceable or upgradable.

> NOTE: Quantum computers are expected to break traditional forms of public key cryptography and weaken by half the symmetric ciphers, hashes, and random number generators. It is likely that, by 2022 or soon thereafter, we will be upgrading our asymmetric ciphers and digital signatures to newer, quantum-resistant cryptography. If you are a developer, help the world's move to quantum-resistant cryptography. For more information, consider reading my book on quantum cryptography (Wiley, 2019).

## Chapter 6 Access Control

## Developers Should Secure Coding Practices

You would be surprised by how security solutions contain bugs. All developers, especially MFA solution creators, should learn and aim to use security development lifecycle (SDL) techniques. SDL is a process that builds security from the very beginning of any project. Before the first line of code is written, all the people involved in the project are using threat modeling to evaluate all the ways the code can be attacked and striving to mitigate the most likely attacks. One of the earliest SDL proponents was Microsoft, and soon thereafter shared information about secure coding practices. If you are a developer and don't already master SDL, you can learn as much as you can by visiting Microsoft's website: www.microsoft.com/en-us/security/sdl also check out the OWASP Foundation: www.owasp.org.

## Use Secure Transmission

Any time the access token is transmitted, it should only be done over secure channels. Ideally, on the local OS or device, this means the access control token should be protected against eavesdropping. More importantly, at the very least, the network channel should be protected by industry-accepted cryptography and key sizes. Using HTTPS is fine as long as the network channel does not contain known vulnerabilities. The participating client and server should be authenticated.

## Include Timeout Protections

All access tokens should come with server-side expirations, after which the issued token should no longer be valid. Token validity ranges from minutes to days—the idea is to prevent theft and replay of token forever.

## Tie the Token to Specific Devices

The most effective defense against stolen token is to tie all access tokens to previously registered devices. That way, if an attacker steals it they cannot reuse it on a new device or location. At the very least, if an access token is used on a new device or location, the user should be prompted for additional authentication to ensure that the legitimate user is using the access control.

This is a good time to bring up the FIDO Alliance's (fidoalliance.org) method of tokens to sites. As explained here (fidoalliance.org/how-fido-works), the FIDO registration process starts with the user registration on the intended FIDO-enabled website. The site's registration page is tied to a FIDO API, which hooks to a FIDO server. The website queries the user's connected FIDO-compliant browser or application to see if the user has registered a FIDO authenticator with the site's authentication policies (e.g., requiring user verification in order to provide strong 2FA in a single step). If one is found, the website prompts the user to select the FIDO authenticator they want to use for this website instance. When the user selects the FIDO authenticator they want to use, the FIDO server sends a challenge (a large random number), and it sends it to the user's FIDO authenticator with its unique AppID/RP ID and other information. The FIDO authenticator prompts the user to provide a gesture to the authenticator (pushing a button, using a biometric attribute, etc.) and the authenticator creates a unique private/public key pair registered for the website or application by its DNS name. The public key is for the website's domain name or application, the user's account name, and FIDO authenticator binding.

> The private/public key is not a traditional x.509 digital certificate because a trusted third party (i.e., the CA) is not needed.

The public key is sent to the website with the FIDO authenticator's response to the challenge. If the challenge is successfully verified by the website, the user's FIDO authenticator instance is registered with the related public key. The private key and any other authentication information, as a biometric attribute, never leaves the FIDO authenticator. Each website has a unique key for each user account and FIDO authenticator. Each user and authenticator will use a different key with each website. The combination of the authenticator as a possession factor plus the biometric or a PIN leads to MFA in a single step.

When the user starts to log on a FIDO-enabled website they have previously registered with, the site will require and send a FIDO challenge to the user's FIDO-enabled browser or application, which passes it along to the FIDO authenticator. The user must provide a gesture to unlock the related private key, which signs the challenge and sends it back to the FIDO website. The website verifies the signed response using the FIDO authenticator's public key instance and, if verified, allows the user's login to proceed.

When the user connects to what they think is their intended website, the FIDO authenticator can only be involved if the DNS name of the site is the one that was previously registered with the FIDO authenticator. If the domain name is not previously registered—say, because the user is accidentally connecting to a malicious MitM proxy—the FIDO authenticator will read the proxy's domain name and ignore it because it was not previously registered.
