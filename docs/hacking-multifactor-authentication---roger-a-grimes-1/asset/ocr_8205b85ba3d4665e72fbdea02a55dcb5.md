# Chapter 15 Buggy Software 315

I think it surprised everyone in the room, including me. I think I all thought that unpatched software, buffer overflow, or some more sophisticated type of attack was going to be involved. The real answer was simple, hard-coded password problems. So, the problem persisted in one of the largest and cheapest companies in the world just a few years ago, and it exists on a multitude of systems we use all over the world.

Many computers and devices come with built-in default credentials. There are dozens of sites around the Internet that list default passwords—such as datcovery.com/rd/default-passwords—that any hacker can look up and use when faced with a device logon.

Default passwords that are never changed are so popular malware, like Mirai bot (en.wikipedia.org/wiki/Mirai_(malware)), tries default passwords to take over vulnerable devices. Mirai bot has taken tens, if not, millions of devices (like IP cameras and cable modem routers). Those devices are then organized into huge botnets (malware networks), which then attack other devices and networks.

Defenses include implementing custom passwords for each unique device. For example, many home cable modem come now with the unique password printed on a sticker stuck to the side of the modem or device, such as its MAC address. The best solutions use unique login credentials stored in “security enclaves” like TPM chips or facilities built into CPUs and other chips.

# Insecure Authentication

Good authentication is hard to do, and there are a lot of dependencies. It is easy—probably easier—for a developer to authenticate incorrectly and insecure to do it right and securely. There are many ways a developer can mess up authentication that entire books could be devoted to just simple types of mistakes. The Common Weakness Enumeration we lists 18 a developer can incorrectly code authentication (cwe.mitre.org/data/definitions/1211.html), and most of them have several different sub-methods listed under them. It suffices to say, doing good authentication is difficult work. Defenses include everything I will list in the “Developer Defenses Against Vulnerability Attacks”, later in this chapter.

# Cleartext Storage or Transmission of Confidential Information

Another vulnerability is the insecure storage or transmission of confidential information, either data that is supposed to be protected or some type of authentication secret. Many times, an attacker has to do so a properly protected secret is. For example, many encrypted USB storage devices stored the private encryption key that “locked” the devices in plaintext. All an attacker needed the right equipment and software to inspect the device at the “bit level.” There have been cases where private encryption keys generated on the fly were left in what was supposed to be temporary storage areas. Or data that was wanted and designed to be sent over HTTPS was sent using HTTP instead. Defenses against inadvertently revealing confidential information include a good understanding, enforced use, and review of cryptographic systems and processes.
