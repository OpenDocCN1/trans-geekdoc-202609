# Authentication and Operations

Because it is nearly impossible to display a full-sized election ballot nicely on a small-form device, our MFA solution requires that the MFA device be plugged into another computer that meets the communicated minimum requirements, whatever they may be. The voting ballot will be displayed on the voter's other device and screen, and the voter interacts with the additional device to recover their choices.

When the MFA device is plugged into a computer—say, by USB cable—the MFA device should power up and do its hardware and software self-checks. Then the user should execute the MFA device's main program (however that is, depending on the operating system). This will launch a secure, very limited operating system and application, which is completely stored, contained, and loaded from the MFA device.

The user sees a voting application initialization message appear on the computer screen. The voter waits while the MFA device uses their existing Internet connection from the host device or a valid, supplied phone connection to check on updates and download any allowed, waiting online voting ballots. If updates are available, the device applies the updates and reboots. Upon rebooting, it checks again for both additional updates and voter ballots.

Updates and ballot downloads are encrypted with an asymmetric key that is specific to the MFA device being used so that only a particular ballot package, tied to voter and device, is allowed to be decrypted and installed on any particular MFA device. No other device or voter ID can use that particular ballot package, and it can run to completion only once. Incomplete voting requires that the whole process begin again with no previous choices shown or recorded.

Once updating and ballot downloading are finished, the device should confirm that it is securely communicating with the legitimate, expected voting device. If it is, the device should perform a challenge-response push to the device. Only the legitimate device and voter can generate the agreed-on challenge-response sequence. Verified, the MFA device should display a big, green OK on the MFA device's OLED. The software should allow the user to confirm that the big, green OK appears on the MFA device. If nothing is wrong with communications, or it's possible that the user's authentication experience on the computer's screen is simulated by a fake website. The user should be educated not to proceed with typing in their credentials or participating in voting or updating until the big, green OK appears on the MFA device. This, along with the preregistration of the device, should prevent authentication attacks from being successful.

> NOTE Of course, never underestimate the ability of users to ignore all signs of compromise and training no matter how well you've attempted to do.

# Chapter 22 Designing a Secure Solution

Once the user confirms the green OK, they are shown a logon screen and asked to authenticate. The voter is asked to type in their voter ID and OTP code (plus the voter's four-digit static personal knowledge at the beginning). The entire authentication process and application is loaded and originates from the MFA solution's secure enclave, much like a smartcard. The session shown is a virtual session, protected by a hardware hypervisor to prevent tampering. All voter inputs are selected using touch-screen or mouse inputs. No keyboards are used to prevent easy keystroke logging. If higher security is desired, all inputs could be made by the MFA device by a button or voice interface, as is often used on portable media players and voice recorders. Either way, great care should be taken to make sure the selections are recorded onto the voter's ballot within the secure confines of the MFA-provided application and hypervisor. It should be nontrivial for the MFA-protected session.

The hardware hypervisor should protect the electronic ballot from nontrivial eavesdropping or tampering. There are occasionally ways for hardware-based hypervisors to do "host-to-client" or DoS attacks, but doing so is not easy. Most hypervisor vulnerabilities can be remedied with a firmware or software update.

The OS and application should have minimal lines of code and footprint down on possible attack vectors. All communications outside the secure enclave should be accomplished using a Transport Layer Security (TLS)-VPN to predefined IP addresses or domain names.

Perhaps if the device is started up and finds no active ballot to download, it tells the user and either it powers off after a few minutes or allows the user to perform a simulated ballot demo. Technical supports websites and phone numbers should be physically located on the MFA device and displayed whenever the device boots.

The OTP code can be event based and key each new election ballot package, or like a regular TOTP device, generate codes all the time. If it is event based (HOTP), the device should use the Initiative for Open Authentication (OATH) Challenge-Response Algorithm (tools.ietf.org/html/rfc6287) and incorporate critical parts of the ballot information and voter's response to that of the challenge-response.

By the entry of the OTP code (either HOTP or TOTP) by the user into the voting software or process must require the four-digit static code in addition to the OTP code. The OTP code display on the device should have a physical printed area or sticker reminding the voter of the need for both portions, as something similar to "Don't forget to enter in all codes using your 4-digit PIN plus the code here: XXX-XXXXXX or something like that. The screen can require the two needed codes separately as well.

Any OTP code should use open standards and processes, such as discussed in Chapter 9, "One-Time Passwords." OTP codes should expire in a reasonable amount of time. OTP codes should use Dynamic Symmetric Key Provisioning Protocol (DSKP) to securely generate shared seed values on a regular basis.

# Hacking Multifactor Authentication

The MFA device should, similar to what FIDO Alliance devices do, require you to register the main voting site/service to the device (and vice versa), and the main voting site should always check for origination identification when a ballot download is requested. Channel binding should be enabled by default. If voters are not detected as originating from the specific MFA unit, then an MitM attack should be assumed and the vote counted.

I love the Bloomberg-Unit and Datablink's example of how the application authenticate with the host device by using flashing lights and an MFA device sensor. However, this sort of authentication isn't needed because the application is originating from the device itself. It would be in, authenticating to itself. In the Bloomberg-Unit example, the application originates as already installed on the primary device being used or using a web service. The software is installed and executed prior to the MFA device being involved, and the software instance is being called from locations outside the MFA device's control. In our example, the code execution is under complete control of the MFA device and travels with the MFA device. But if additional option to MFA authentication is desired, I like the B-Unit's Datablink's idea of flashing lights to communicate with the MFA device and having the user input a code.

# Verifiable/Auditable Vote

After successfully authenticating, the current ballot is displayed on the screen and the voter reads it and makes their choices, with the ballot moving as directed by the voter. The voter can see every vote on the computer screen and at the same time on the MFA device's OLED. The full-sized computer screen, the entire ballot and text can be viewed. On the MFA device, only the question numbers and answers are shown. But a user could look at the computer where they are making their selections and compare to the answers and choices being reported by the MFA device.

When finished, the voter is asked if they would like to print a copy of their ballots Regardless of that, a custom link is sent to them via their registered email address (which is shown in partial format so they can verify it). They can click that link to see their choices immediately after the vote is finished. Alternatively, the voter can always go to the main voting website, authenticate using the MFA device, and see their past voting history. The voter should have the ability to report incorrect votes at any time.

A verifiable voting paper trail is needed for every electronic voting solution, or in-person. It is essential that the voter be able to compare what they voted for what is printed. Solutions not allowing real-time printing of selections cannot be trusted. Solutions that need the verification through untrusted channels, like the Internet or to the host device, cannot be completely trusted. That's why the verifiable voting option must also be displayed on the MFA device (i.e., transaction verification) so that the voter can verify it on the trustworthy device and location.
