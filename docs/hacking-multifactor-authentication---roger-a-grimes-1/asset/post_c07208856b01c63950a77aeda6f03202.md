If an attacker steals an OTP device, the legitimate owner will notice and report it, and it will be decommissioned. If it is re-created, the legitimate owner likely will not know, and it can be used by the attacker multiple times before the unauthorized access is detected.

Google Authenticator has this risk in spades. The 80-bit seed value communicated in the original setup (via text or QR code) is all that is needed to create one or more instances of the same Google Authenticator OTP code. Worse yet, it never expires! If anyone gets the setup information at any time before the Google Authenticator instance is decommissioned, they can create additional, potentially unintended instances of the same Google Authenticator.

There have been many instances where someone's "old" Google Authenticator initial setup or picture was later compromised by a hacker. ## Stolen Seed Database

The shared, secret, seed values can be compromised wherever they are stored. Seed values are typically stored on the participating OTP device/instance and authenticating database, wherever that database is stored. They are often stored at the OTP solution vendor and may be additionally stored on a database near the log server/service. These databases have been compromised in the past, although these compromises are not super common. But when they have happened they are often accomplished by advanced persistent threat (APT) adversaries of nation-states.

The most famous example was a compromise of several RSA customers in 2011 (www.wired.com/2011/06/rsa-replaces-securid-tokens/). An APT actor phished RSA employees with emails containing attachments (i.e., Microsoft Excel spreadsheets). Some of the RSA employees who fell for the phishing had long unpatched versions of Microsoft Office, and when they opened the malicious files included malware program that compromised their workstations and eventually much of RSA's network. With the unpatched software, the employees had to ignore or bypass multiple warnings from Microsoft Office products. During other things, it was rumored that several RSA customer databases, including Lockheed Martin's, containing their RSA SecID seeds and device guides were compromised.

Over the years I have heard stories from press and RSA employees as to whether the APT attackers truly obtained RSA SecID secret information and used it to compromise customer accounts. RSA denied that such events have never happened. This is made difficult to believe because of a few factors. One, RSA confirmed the breach and ultimately told customers to replace all customer's RSA SecID devices. This could have been out of an abundance of caution and to head off continuing negative goodwill headwinds. Second, at least two RSA customers said they were compromised directly because of the RSA compromise, including Lockheed Martin (www.theregister.co.uk/2011/05/27/lockheed_seurid_hack_flap/) and I-3 (www.wired.com/2011/05-1-3).

Lastly, I have re-created SecID myself. I'm not alone. Likely hundreds of interested computer people did. For over a decade a hacker called Cain & Abel proved it easy to make any RSA SecID if you knew the serial number and value. Cain & Abel contained dozens of features of hacking tools all wrapped up in one package. It excelled at sniffing passwords over the wire and doing man-in-the-middle attacks, ARP poisoning and password cracking. It also included a feature that would allow anyone to create virtual instances of RSA SecID tokens and even a way to import many SecID key files. But it hasn't been greatly much since the days of Microsoft Windows XP (2004) and is no longer hosted on creators' original website (oxid.it). If I'm not sure if you can use Cain & Abel today without some malicious modification to abuse people who use it. So, it's best to avoid it unless you can be assured you can get and use a clean version. I assume since the big hack RSA has updated the SecID token algorithm even if you had a clean copy of Cain & Abel would not work against today's SecID tokens. RSA is likely using updating hashing algorithms and more secure changes.

## Defenses to OTP Attacks

There are methods developers and users can take to decrease the risk of attacks-based MFA. The following sections explain some developer defenses against attacks.

## Use Reliable and Trusted Algorithms

Unless you are lucky and your OTP solution lasts long enough (say over half a decade), you will likely need to update the cryptography. Assume whatever cryptography you use will eventually need to be updated. This means that you and your customers can easily update without major issues. All cryptography weakens over time and eventually gets replaced. Harden the algorithms in a way that makes it difficult to replace. At the same time ensure that unauthorized changes can be made.

## OTP Setup Must Expire

Any initial seed value/code used to set a OTP instance should expire within a reasonable period of time. You don't want an "old" code sitting around waiting for an unauthorized user to discover. This also applies to master, backup and travel codes. All codes which make a new instance or bypass MFA should expire in a reasonable period of time.

One related solution Dynamic Symmetric Key Provisioning Protocol (PSK). Officially registered in RFC 6063 (tools.ietf.org/html/rfc6063), DSPKP is a simple method sharing symmetric secrets between two authenticating parties—the client and server of an OTP solution, for example. DSPKP allows a shared secret, like a seed, to be generated between the parties. And—this is important—it could be used over to establish new secret values they are needed. So if the original seed base value or any old values were compromised, the information learned could not be as easily duplicate future OTP codes. An OTP token, for example, could generate a new shared secret every day or at any predefined time interval.

## OTP Result Must Expire

Any resulting OTP code should expire whether or not the code was created by an OTP. If OTP codes did not expire or took a long time to expire, then an unauthorized user might be able to use an "old" code for a future authentication. This is a big problem, particularly around HOTP solutions. There is a very popular HOTP vendor solution that never expires or used HOTP codes. Some knowledgeable people and competitors agree showing how 20 HOTP codes generated over a year still work fine current logins. This is unacceptably dangerous.
