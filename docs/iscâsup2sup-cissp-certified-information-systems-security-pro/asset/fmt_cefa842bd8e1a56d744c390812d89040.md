
# Web 安全评估与 SQL 注入攻击

## Web 应用漏洞与 OWASP

在基于 Web 的系统中，存在各种各样的应用和系统漏洞及威胁，且范围在不断扩大。漏洞包括与可扩展标记语言（XML）和安全断言标记语言（SAML）相关的问题，以及由专注于开放社区的 Web 项目 **Open Web Application Security Project (OWASP)** 讨论的许多其他问题。

OWASP 是一个非营利性安全项目，专注于改进在线或基于 Web 的应用程序的安全性。OWASP 不仅仅是一个组织，它还是一个庞大的社区，大家共同努力，自由分享与更好的编码实践和更安全的部署架构相关的信息、方法论、工具和技术。有关 OWASP 的更多信息以及参与社区，请访问 [www.owasp.org](http://www.owasp.org)。

OWASP 组织维护了一份评估 Web 服务安全性的建议指南，地址为 [https://www.owasp.org/index.php/Web_Application_Security_Testing_Cheat_Sheet](https://www.owasp.org/index.php/Web_Application_Security_Testing_Cheat_Sheet)。OWASP 还维护了一份十大最关键 Web 应用攻击清单，地址为 [https://www.owasp.org/images/7/72/OWASP_Top_10-2017_%28en%29.pdf.pdf](https://www.owasp.org/images/7/72/OWASP_Top_10-2017_%28en%29.pdf.pdf)。这两份文档都是规划组织 Web 服务安全评估或渗透测试的合理切入点。

## 安全评估流程

任何安全评估都应从侦察或信息收集开始。此步骤旨在收集尽可能多的目标信息，供后续步骤使用。这通常包括查看每个托管的 Web 页面、发现正在使用的自动化技术、查找不应发布的信息，以及检查配置和安全泄露。

随后进行站点配置管理评估（如文件处理、使用的扩展、备份、在客户端代码中查找敏感数据），并评估站点的传输安全性（如检查安全套接字层（SSL）/传输层安全性（TLS）版本支持、评估密码套件、Cookie/会话 ID/令牌管理，以及对伪造请求的易感性）。

Web 安全评估的下一步是评估身份认证和会话管理。随后评估站点的加密技术以及用于数据验证和清理的方法。Web 安全评估还应涉及检查 DoS 防御、评估风险响应，并测试错误处理。

这只是 Web 安全评估概念的简要概述，因为 CISSP 考试不要求你成为专业的渗透测试人员，但你应该大致了解安全评估的概念。如果你对这个主题感兴趣，欢迎从 OWASP 指南中探索更多关于 Web 安全评估的细节。

> **注意**：你可能想了解的 OWASP 十大 Web 风险包括注入、XML 利用、跨站脚本（XSS）和 XSRF。

## 注入攻击

**注入攻击**是指允许攻击者向目标系统提交代码，以修改其操作和/或污染和破坏其数据集的任何利用行为。存在各种潜在的注入攻击。通常，注入攻击以其利用的后端系统类型或投递（注入）到目标上的有效载荷类型命名。示例包括结构化查询语言（SQL）注入、轻量级目录访问协议（LDAP）、XML 注入、命令注入、超文本标记语言（HTML）注入、代码注入和文件注入。本节将详细介绍其中几种。

## SQL 注入攻击

从组织的角度来看，**SQL 注入攻击**比 XSS 攻击（见下节）风险更大，因为 SQL 注入攻击的目标是组织资产，而 XSS 攻击的目标是网站的客户或访问者。SQL 注入攻击利用意外输入来更改或破坏 Web 应用程序。然而，SQL 注入攻击不是利用此输入试图欺骗用户，而是利用它来获得对底层数据库及相关资产的未授权访问。

### Web 应用演进背景

在 Web 早期，所有网页都是**静态**的，即不变的。网站管理员创建包含信息的网页并将其放置在 Web 服务器上，用户可使用其 Web 浏览器检索这些页面。Web 迅速超越了这一模式，因为用户希望能够根据个人需求访问定制信息。例如，银行网站的访问者不仅对包含银行位置、营业时间和服务信息的静态页面感兴趣，他们还想检索包含其个人账户信息的**动态**内容。显然，网站管理员不可能在 Web 服务器上为每个用户创建包含该用户个人账户信息的页面。在大型银行中，这将要求维护数百万个包含最新信息的页面。这就是动态 Web 应用程序发挥作用的地方。

Web 应用程序利用数据库在用户发出请求时按需创建内容。在银行示例中，用户登录 Web 应用程序，提供账号和密码。Web 应用程序随后从银行数据库检索当前账户信息，并利用它即时创建包含用户当前账户信息的网页。如果该用户一小时后返回，Web 服务器将重复该过程，从数据库获取更新的账户信息。

### 安全架构影响

作为安全专业人员，这对你意味着什么？Web 应用程序增加了传统安全模型的复杂性。Web 服务器作为公共可访问服务器，属于独立的网络区域，通常称为**非军事区（DMZ）**，与其他服务器分离。另一方面，数据库服务器不面向公众访问，因此属于内部网络，或至少是与 DMZ 隔离的安全子网。Web 应用程序需要访问数据库，因此防火墙管理员必须创建一条规则，允许从 Web 服务器访问数据库服务器。这条规则为互联网用户访问数据库服务器创建了一条潜在路径。

如果 Web 应用程序运行正常，它只允许对数据库进行授权请求。然而，如果 Web 应用程序存在缺陷，它可能会让个人通过 **SQL 注入攻击**以意想不到且未授权的方式篡改数据库。这些攻击允许恶意个人直接针对底层数据库执行 SQL 事务。SQL 注入攻击可能使攻击者绕过身份认证、从数据库表中泄露机密数据、更改现有数据、向数据库添加新记录、销毁整个表或数据库，甚至通过某些数据库功能（如命令 Shell 存储过程）获得类命令行访问权限。

## 防御 SQL 注入的两种技术

你可以使用两种技术来保护 Web 应用程序免受 SQL 注入攻击。

### 1. 执行输入验证

输入验证可让你限制用户在表单中提供的数据类型。存在许多输入注入或操纵攻击的变体，需要广谱防御方法，包括白名单和黑名单过滤器。应采用的主要输入清理形式包括限制输入长度、基于已知恶意内容模式进行过滤，以及转义**元字符**。

### 2. 限制账户权限

Web 服务器使用的数据库账户应拥有尽可能小的权限集。如果 Web 应用程序只需检索数据，则应仅具备该能力。
