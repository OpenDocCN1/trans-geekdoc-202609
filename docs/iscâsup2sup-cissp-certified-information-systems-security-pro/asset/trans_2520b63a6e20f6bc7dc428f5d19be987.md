
# 对于系统开发人员而言，安全策略最好以文档的形式呈现，该文档定义了一组规则、实践和程序，描述系统应如何管理、保护和分发敏感信息。防止信息从较高安全级别流向较低安全级别的安全策略称为多级安全策略。随着系统的开发，安全策略应在设计、构建、实施和测试时，关联所有适用的系统组件或要素，包括以下任何或所有内容：物理硬件组件、固件、软件，以及组织如何与系统交互和使用系统。总体要点是，安全需求必须贯穿项目的整个生命周期。如果仅在最后阶段才应用安全措施，通常会失败。

## 策略机制

与任何安全计划一样，策略机制也应到位。这些机制是基本计算机安全原则的延伸，但本节所述的应用专门针对计算机体系结构和设计领域。

### 最小权限原则

第 13 章“管理身份和认证”讨论了通用安全*最小权限原则*及其如何应用于计算系统的用户。该原则对于计算机和操作系统的设计也至关重要，特别是在应用于系统模式时。设计操作系统进程时，应始终确保它们在可能的情况下运行在用户模式下。在特权模式下执行的进程越多，恶意人员可利用以获取系统监管访问权限的潜在漏洞就越多。通常，最好使用 API 请求监管模式服务，或在用户模式应用程序需要时将控制权传递给受信任、受良好保护的监管模式进程，而不是将此类程序或进程整体提升到监管模式。

### 特权分离

*特权分离*原则建立在最小权限原则之上。它要求使用细粒度的访问权限；即针对每种类型的特权操作设置不同的权限。这使设计人员能够授予某些进程执行特定监管功能的权限，而无需授予它们对系统的无限制访问权限。它还允许对服务的单个请求或资源访问请求进行检查，根据提出请求的用户身份、用户所属的组或用户占据的安全角色，将其与访问控制进行核对，并予以批准或拒绝。

可将职责分离视为将最小权限原则应用于管理员。在大多数中大型组织中，有许多管理员，各自承担不同的分配任务。因此，通常很少或没有个别管理员完全需要访问整个环境或基础设施的权限。例如，用户管理员不需要重新配置网络路由、格式化存储设备或执行备份功能的特权。

职责分离也是一种工具，用于防止在分配访问特权和工作任务时产生利益冲突。例如，负责编写代码的人员不应被指派测试和实施该代码。同样，从事应付账款工作的人员也不应同时承担应收账款职责。通过正确实施职责分离，可以安全地管理许多此类工作或任务冲突。

### 问责制

*问责制*是任何安全设计中必不可少的组成部分。许多高安全系统包含物理设备（如纸笔访客日志和不可修改的审计跟踪），以强制执行个人对特权功能的问责。然而，总体而言，此类功能依赖于系统监控系统资源和配置数据上的活动与交互，并保护生成的日志免受未经授权的访问或篡改，从而提供准确可靠的活动和交互记录，记录每个用户（包括管理员或其他拥有高级特权的受信任人员）在该系统上的历史。除了需要可靠的审计和监控系统来支持问责制外，还必须具备弹性的授权系统和无懈可击的认证系统。

## 常见架构缺陷和安全问题

没有任何安全架构是完整且完全安全的。每个计算机系统都存在弱点和漏洞。安全模型和架构的目标是解决尽可能多的已知弱点。基于这一事实，必须采取纠正措施来解决安全问题。以下部分介绍了一些与安全架构漏洞相关的、影响计算机系统的更常见的安全问题。您应了解每个问题以及它们如何降低系统的整体安全性。某些问题和缺陷相互重叠，并被创造性地用于攻击系统。虽然以下讨论涵盖了最常见的缺陷，但列表并非详尽无遗。攻击者非常狡猾。

### 隐蔽信道

*隐蔽信道*是一种通过正常不用于通信的路径传递信息的方法。因为该路径正常不用于通信，所以可能不受系统正常安全控制的保护。使用隐蔽信道提供了一种未被检测到地违反、绕过或规避安全策略的手段。隐蔽信道是安全架构漏洞的重要示例之一。

正如您所想象的，隐蔽信道与*公开信道*相反。公开信道是一种已知的、预期的、授权的、设计的、受监控的和受控的通信方法。

隐蔽信道有两种基本类型：

**隐蔽定时信道** 隐蔽定时信道通过改变系统组件的性能或以可预测的方式修改资源的时序来传递信息。使用隐蔽定时信道通常是一种秘密传输数据的方法，且非常难以检测。

**隐蔽存储信道** 隐蔽存储信道通过将数据写入另一个进程可读取的公共存储区域来传递信息。在评估软件安全性时，应警惕任何向另一个进程可读取的内存区域写入数据的进程。

这两种类型的隐蔽信道都依赖通信技术，与其他未授权主体交换信息。因为隐蔽信道位于正常数据传输环境之外，所以检测它可能很困难。最好的防御是实施审计并分析日志文件，以查找任何隐蔽信道活动。

### 基于设计或编码缺陷和安全问题的攻击

某些攻击可能源于不良的设计技术、可疑的实施实践和程序，或不充分的测试。某些攻击可能源于故意的设计决策，即在开发过程中为绕过访问控制、登录或其他安全检查而内置在代码中的特殊入口点，在代码投入生产时未被移除。出于显而易见的原因，此类出口点恰当地称为后门，因为它们通过设计避开了安全措施（本章后面的“维护钩子和特权程序”中将介绍）。需要进行广泛的测试和代码审查，以发现此类隐蔽访问手段，这些手段在开发的最后阶段很容易移除，但在测试和维护阶段却极难检测。
