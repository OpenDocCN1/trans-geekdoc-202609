
# 输入验证

当用户与软件交互时，他们通常以输入的形式向应用程序提供信息。这可能包括键入稍后由程序使用的值。开发人员通常期望这些值落在特定参数范围内。例如，如果程序员要求用户输入月份，程序可能期望看到 1 到 12 之间的整数值。如果用户输入的值超出该范围，编写不当的程序在最好的情况下可能会崩溃，在最坏的情况下可能允许用户控制底层系统。

**输入验证**在允许进一步处理之前，验证用户提供的值是否与程序员的预期相符。例如，输入验证会检查月份值是否为 1 到 12 之间的整数。如果该值超出该范围，程序将不会尝试将该数字作为日期处理，并会告知用户输入要求。这种代码检查以确保数字落在可接受范围内的输入验证类型，称为**限制检查**。

输入验证还可能检查异常字符，例如文本字段中的引号，这可能表明正在发生攻击。在某些情况下，输入验证例程可以转换输入以移除有风险的字符序列，并用安全值替换它们。此过程称为**转义输入**。

输入验证应始终发生在事务的服务器端。发送到用户浏览器的任何代码都可能被用户操纵，因此很容易被绕过。

# 认证和会话管理

许多应用程序，特别是 Web 应用程序，要求用户在访问敏感信息或修改应用程序中的数据之前进行认证。开发人员面临的核心安全任务之一是确保这些用户经过适当认证、仅执行授权操作，并且其会话从开始到结束都被安全地跟踪。

应用程序所需的认证级别应直接与该应用程序的敏感度级别挂钩。例如，如果应用程序为用户提供对敏感信息的访问权限，或允许用户执行关键业务应用程序，则应要求使用强多因素认证。

在大多数情况下，开发人员应寻求将其应用程序与组织现有的认证系统集成。利用现有的、经过强化的认证系统通常比尝试为特定应用程序开发认证系统更安全。如果无法做到这一点，请考虑使用外部开发并经过验证的认证库。

同样，开发人员应使用成熟的方法进行会话管理。这包括确保用于 Web 会话管理的任何 Cookie 仅通过安全的加密通道传输，并且这些 Cookie 中使用的标识符应当又长又随机生成。会话令牌应在指定时间段后过期，并要求用户重新认证。

# 错误处理

开发人员喜欢详细的错误消息。这些错误中返回的深度信息对于调试代码至关重要，并使技术人员更容易诊断用户遇到的问题。

然而，这些错误消息也可能向攻击者暴露敏感的内部信息，包括数据库表的结构、内部服务器的地址，以及可能有助于攻击前侦察工作的其他数据。因此，开发人员应在任何公开可访问的服务器和应用程序上禁用详细错误消息（也称为**调试模式**）。

# 日志记录

虽然面向用户的详细错误消息可能构成安全威胁，但这些消息包含的信息非常有用，不仅对开发人员，对网络安全分析师也是如此。因此，应用程序应配置为将错误和其他安全事件的详细日志发送到集中式日志存储库。

开放 Web 应用程序安全项目 (OWASP) 安全编码指南建议记录以下事件：

- 输入验证失败
- 认证尝试，特别是失败
- 访问控制失败
- 篡改尝试
- 使用无效或过期的会话令牌
- 操作系统或应用程序引发的异常
- 使用管理权限
- 传输层安全性 (TLS) 失败
- 加密错误

这些信息可用于诊断安全问题和调查安全事件。

# 故障安全与故障开放

尽管程序员、产品设计师和项目经理尽了最大努力，开发的应用程序仍会以意想不到的方式被使用。其中一些情况会导致故障。由于故障不可预测，程序员应在代码中设计一种通用的响应和处理故障的机制。

在规划系统故障时，有两种基本选择：

- **故障安全故障状态**将系统置于高安全级别（甚至可能完全禁用系统），直到管理员能够诊断问题并将系统恢复正常运行。
- **故障开放状态**允许用户绕过失败的安全控制，倾向于宽容。

在绝大多数环境中，故障安全是适当的故障状态，因为它可以防止未经授权访问信息和资源。

软件应恢复到故障安全状态。这可能意味着仅关闭应用程序，也可能意味着停止整个主机系统的运行。Windows 操作系统 (OS) 中臭名昭著的蓝屏死机 (BSOD) 就是这种故障响应的一个例子，它指示发生了 STOP 错误。当 OS 尽力阻止但仍发生不良活动时，就会发生 STOP 错误。这可能包括应用程序获得对硬件的直接访问、尝试绕过安全访问检查，或一个进程干扰另一个进程的内存空间。一旦发生这些条件之一，环境就不再可信。因此，OS 不会继续支持不可靠且不安全的操作环境，而是发起 STOP 错误作为其故障安全响应。

一旦发生故障安全操作，程序员应考虑之后发生的活动。选项是保持故障安全状态或自动重启系统。前者需要管理员手动重启系统并监督该过程。此操作可通过使用启动密码来强制执行。后者无需人工干预即可使系统恢复到运行状态，但也有其自身的独特问题。例如，它必须限制系统重启进入非特权状态。换句话说，系统不应重启并执行自动登录；相反，它应提示用户输入授权访问凭据。

即使安全性在软件中经过适当设计和嵌入，为了支持更轻松的安装，该安全性通常会被禁用。因此，IT 管理员通常有责任开启并配置安全性，以满足其特定环境的需求。维护安全性通常是在用户友好性和功能性之间进行权衡，如[图 20.1](#c20.xhtml#figure20-1)所示。此外，随着安全性的增加或增强，成本、管理开销也会增加，而生产力/吞吐量会降低。
