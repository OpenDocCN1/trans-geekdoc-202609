
# 数据库事务与安全机制

## 事务处理的重要性

假设这两条语句不是作为事务的一部分执行，而是分别单独执行。如果数据库在第一个事务完成和第二个事务完成之间的时刻发生故障，`$250` 将会被添加到账户 `1001`，但账户 `2002` 没有相应的扣除。这 `$250` 将凭空出现！交换这两条语句的顺序也无济于事——如果被中断，这会导致 `$250` 凭空消失！这个简单的例子凸显了面向事务处理的重要性。

当事务成功完成时，称其已**提交**到数据库，且无法撤销。事务提交可以是显式的，使用 SQL 的 `COMMIT` 命令；也可以是隐式的，即成功到达事务末尾。如果必须中止事务，可以使用 `ROLLBACK` 命令显式回滚，或在发生硬件或软件故障时隐式回滚。事务回滚时，数据库会恢复到事务开始前的状态。

所有数据库事务都具有四个必需特征：原子性、一致性、隔离性和持久性。这些属性统称为 **ACID 模型**，是数据库管理系统开发中的关键概念。让我们简要了解一下每个要求：

### 原子性
数据库事务必须是原子的——即要么全做，要么全不做。如果事务的任何部分失败，整个事务必须回滚，就像从未发生过一样。

### 一致性
所有事务必须在一个与数据库所有规则一致的环境中开始操作（例如，所有记录都有唯一的主键）。事务完成时，数据库必须再次与规则保持一致，无论这些规则在事务处理过程中是否被违反。任何其他事务都不应能使用另一个事务执行过程中可能生成的不一致数据。

### 隔离性
隔离性原则要求事务彼此独立操作。如果数据库接收到两个修改相同数据的 SQL 事务，必须在允许另一个事务修改相同数据之前，完成其中一个事务的全部过程。这可以防止一个事务使用另一个事务作为中间步骤生成的无效数据。

### 持久性
数据库事务必须是持久的。即一旦提交到数据库，就必须被保留。数据库通过备份机制（如事务日志）来确保持久性。

在以下章节中，我们将讨论数据库开发人员和管理员关注的各种具体安全问题。

## 多级数据库安全

正如您在第 1 章所学，许多组织使用数据分类方案，根据分配给数据对象和个别用户的安全标签来实施访问控制限制。当组织的安全策略强制要求时，这一分类概念也必须扩展到组织的数据库中。

多级安全数据库包含不同分类级别的信息。它们必须验证分配给用户的标签，并根据用户请求，仅提供适当的信息。然而，在考虑数据库安全时，这一概念变得更加复杂。

当需要多级安全时，管理员和开发人员必须努力将具有不同安全要求的数据分开。混合不同分类级别和/或“需知”要求的数据被称为**数据库污染**，这是一个重大的安全挑战。通常，管理员会部署可信前端，为遗留或不安全的 DBMS 增加多级安全功能。

### 并发控制

**并发控制**（或编辑控制）是一种预防性安全机制，旨在确保数据库中存储的信息始终正确，或者至少保护其完整性和可用性。此功能可用于单级或多级数据库。

未能正确实现并发控制的数据库可能会遭受以下问题：

*   **丢失更新**：当两个不同的进程在不知晓对方活动的情况下对数据库进行更新时发生。例如，设想一个仓库的库存数据库，有不同的接收站。仓库目前可能有 `10` 本《CISSP 学习指南》库存。如果两个不同的接收站同时各收到一本《CISSP 学习指南》，它们都可能检查当前库存水平，发现是 `10`，将其加 `1`，并将表更新为 `11`，而实际值应为 `12`。

*   **脏读**：当一个进程读取未成功提交的事务的记录时发生。回到仓库示例，如果一个接收站开始向数据库写入新库存记录，但在更新中途崩溃，如果事务未完全回滚，可能会在数据库中留下部分不正确的信息。

并发控制使用“锁”功能允许一个用户进行更改，但拒绝其他用户同时访问视图或更改数据元素。然后，更改完成后，“解锁”功能恢复其他用户访问所需数据的能力。在某些情况下，管理员会将并发控制与审计机制结合使用，以跟踪文档和/或字段更改。当审查这些记录数据时，并发控制就变成了一种侦查型控制。

### 其他安全机制

使用 DBMS 时，管理员可以部署其他几种安全机制。这些功能相对容易实现，在行业中很常见。例如，与语义完整性相关的机制是 DBMS 的常见安全功能。语义完整性确保用户操作不违反任何结构规则。它还检查所有存储的数据类型是否在有效域范围内，确保只存在逻辑值，并确认系统符合所有唯一性约束。

管理员可以使用时间和日期戳来维护数据完整性和可用性。时间和日期戳常出现在分布式数据库系统中。当时间戳被放置在所有更改事务上，并且这些更改被分发或复制到其他数据库成员时，所有更改都会应用到所有成员，但会按正确的时间顺序实施。

DBMS 的另一个常见安全功能是数据库内的对象可以被细粒度控制；这也可以改进安全控制。**基于内容的访问控制** 是细粒度对象控制的一个例子。基于内容的访问控制基于被访问对象的内容或有效载荷。因为必须逐个对象做出决策，基于内容的控制会增加处理开销。另一种细粒度控制形式是**单元抑制**。单元抑制是隐藏单个数据库字段或单元，或对它们施加更多安全限制的概念。

**基于上下文的访问控制** 常与基于内容的访问控制一起讨论，因为术语相似。基于上下文的访问控制从大局出发做出访问控制决策。基于上下文的访问控制的关键因素是每个对象、数据包或字段如何与整体活动或通信相关联。任何单个元素单独看可能都无害，但在更大的上下文中，该元素可能被揭示为良性或恶性。
