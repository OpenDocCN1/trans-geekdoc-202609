
# 寻址与命名

寻址与命名是实现网络通信的重要组成部分。如果没有寻址方案，联网计算机将无法区分彼此，也无法指定通信的目标。同样，如果没有命名方案，人类将不得不依靠记忆和编号系统来标识计算机。记住 [Google.com](http://Google.com) 比记住 `64.233.187.99` 容易得多。因此，大多数命名方案的设立是为了人类使用，而非计算机使用。

掌握基于 TCP/IP 网络中寻址和编号的基本概念非常重要。需要了解三个不同的层次。此处按逆序呈现，因为第三层是最基础的：

*   **第三层，即底层，是 MAC 地址。** MAC 地址，或称硬件地址，是一个“永久”的物理地址。
*   **第二层，即中间层，是 IP 地址。** IP 地址是一个“临时”的逻辑地址，分配在 MAC 地址之上。
*   **顶层是域名。** 域名或计算机名是一个“临时”的、面向人类的约定，分配在 IP 地址之上。

这一命名与寻址系统赋予每个网络组件所需的信息，同时使其对这些信息的使用尽可能简单。人类获得便于记忆的域名，网络协议获得便于路由的 IP 地址，网络接口获得物理地址。然而，这三种方案必须关联在一起，以实现互操作性。因此，开发了 `域名系统 (DNS)` 和 `ARP` 系统，分别用于在域名与 IP 地址之间、IP 地址与 MAC 地址之间进行互换或解析。`DNS` 将便于人类记忆的域名解析为其对应的 IP 地址。然后，`ARP` 将 IP 地址解析为其对应的 MAC 地址。如果定义了 `PTR` 记录，也可以通过 `DNS` 反向查找将 IP 地址解析为域名（详见本章后面的“域名系统”）。

`DNS` 是公共网络和私有网络中使用的分层命名方案。`DNS` 将 IP 地址与便于人类记忆的 `完全合格域名 (FQDN)` 关联起来。一个 `FQDN` 由三个主要部分组成：

*   **顶级域 (TLD)**—[www.google.com](http://www.google.com) 中的 `com`
*   **注册域名**—[www.google.com](http://www.google.com) 中的 `google`
*   **子域或主机名**—[www.google.com](http://www.google.com) 中的 `www`

`TLD` 可以是任意数量的官方选项，包括最初七个 TLD 中的六个——`com`、`org`、`edu`、`mil`、`gov` 和 `net`——以及许多较新的选项，如 `info`、`museum`、`telephone`、`mobi`、`biz` 等。还有被称为**国家代码**的国家变体。（有关当前 TLD 和国家代码的详细信息，请参阅 [www.iana.org/domains/root/db/](http://www.iana.org/domains/root/db/)。）请注意，第七个原始 TLD 是 `int`（代表 international，国际），已被双字母国家代码取代。

注册域名必须在经批准的域名注册商处正式注册，例如 Network Solutions 或 1and1.com。

`FQDN` 最左侧的部分可以是单个主机名，如 `www`、`ftp` 等，也可以是多节的子域名标识，如 [server1.group3.bldg5.mycompany.com](http://server1.group3.bldg5.mycompany.com)。

`FQDN` 的总长度不能超过 253 个字符（包括点）。任何单个部分不能超过 63 个字符。`FQDN` 只能包含字母、数字和连字符。

每个注册域名都有一个指定的权威名称服务器。**主权威名称服务器**托管该域的原始区域文件。**辅助权威名称服务器**可用于托管区域文件的只读副本。**区域文件**是**资源记录**的集合，包含特定域的详细信息。有几十种可能的资源记录（详见 [http://en.wikipedia.org/wiki/List_of_DNS_record_types](http://en.wikipedia.org/wiki/List_of_DNS_record_types)）；最常见的记录列在[表 11.6](#c11.xhtml#table11-6)中。

| 记录 | 类型 | 说明 |
| :--- | :--- | :--- |
| `A` | 地址记录 | 将 `FQDN` 映射到 `IPv4` 地址 |
| `AAAA` | 地址记录 | 将 `FQDN` 映射到 `IPv6` 地址 |

| `SOA` | 起始授权记录 | 指定关于区域文件的权威信息，如主名称服务器、序列号、超时时间和刷新间隔 |

最初，`DNS` 由一个称为 **HOSTS 文件** 的静态本地文件处理。该文件仍然存在，但动态 `DNS` 查询系统已在很大程度上取代了它，尤其是在大型私有网络和互联网中。当客户端软件指向一个 `FQDN` 时，协议栈会发起一个 `DNS` 查询，以将该名称解析为可用于构建 IP 头部的 IP 地址。解析过程首先检查本地 `DNS` 缓存，以查看答案是否已知。`DNS` 缓存由本地 **HOSTS 文件** 的预加载内容以及当前启动会话期间执行的 `DNS` 查询（尚未超时的）组成。如果缓存中没有所需答案，则会向本地 IP 配置中指定的 `DNS` 服务器发送 `DNS` 查询。解析查询的过程既有趣又复杂，但其中大部分与 `(ISC)² CISSP` 考试无关。

`DNS` 在 `TCP` 和 `UDP` 端口 `53` 上运行。`TCP` 端口 `53` 用于区域传输。这些是 `DNS` 服务器之间的区域文件交换，用于特殊的手动查询，或当响应超过 512 字节时。`UDP` 端口 `53` 用于大多数典型的 `DNS` 查询。

**域名系统安全扩展 (DNSSEC)** 是对现有 `DNS` 基础设施的安全改进。`DNSSEC` 的主要功能是在 `DNS` 操作期间为设备之间提供可靠的身份验证。`DNSSEC` 已在 `DNS` 系统的很大一部分中实施。每个 `DNS` 服务器都会被颁发一个数字证书，随后用于执行相互证书认证。`DNSSEC` 的目标是防止一系列 `DNS` 滥用行为，即虚假数据被注入解析过程。一旦完全实施，`DNSSEC` 将显著减少针对服务器的 `DNS` 滥用行为。

## DNS 投毒

**DNS 投毒** 是伪造客户端用于访问目标系统的 `DNS` 信息的行为。它可以通过多种方式发生。每当客户端需要将 `DNS` 名称解析为 IP 地址时，可能会经历以下过程：

1.  检查本地缓存（其中包含 **HOSTS 文件** 的内容）。
2.  向已知的 `DNS` 服务器发送 `DNS` 查询。
3.  向任何可能的本地子网 `DNS` 服务器发送广播查询。（此步骤并未得到广泛支持。）

如果客户端无法从上述任何步骤获得 `DNS` 到 IP 的解析，则解析失败，通信无法发送。`DNS` 投毒可能发生在上述任何步骤中，但最简单的方法是破坏 **HOSTS 文件** 或 `DNS` 服务器查询。
