# Configuring PHPUnit XML Configuration File

To use the PHPUnit XML configuration file to define which tests to run, modify the PHPUnit configuration file in CodeIgniter directory to include the following listeners element:

```diff
a/CodeIgniter/application/tests/phpunit.xml
+++ b/CodeIgniter/application/tests/phpunit.xml
@@ -27,4 +27,8 @@

<log type="coverage-clover" target="Build/logs/clover.xml">
<log type="phpunit" target="build/logs/phpunit.xml" logIncompleteSkipped="false" />
<logging>
    <!-- This is required for VPU to work correctly -->
    <listeners>
        <listener class="PHPUnit_Util_Log_JSON"></listener>
    </listeners>
</logging>
</phpunit>
```

# Installing CodeIgniter via Composer

```
$ composer create-project kenjis/codeigniter-composer-installer CodeIgniter
```

The command listed above installs CodeIgniter 3.0 with a more secure directory structure.

- CodeIgniter/
  application/ ... Your application files.
  composer.json ... Composer's configuration file.
  composer.lock ... Composer's lock file, managed by Composer.
  public/
    index.php ... Front controller.
  vendor/ ... Composer's vendor directory, managed by Composer.
    autoload.php ... Composer's autoloader.
  codeigniter/
    framework/
      application/ ... You don't use this directory.
      system/ ... CodeIgniter system directory.
      user_guide/ ... CodeIgniter User Guide (HTML).

The composer.json file describes the dependencies of your project. Packages by Composer can be found in the vendor directory. They are installed, updated, or removed by the composer command, so you shouldn't edit any of the files in the vendor directory.

This chapter is intended to help you understand the generally-used jargon, as well as the specific meaning we intend when we use that.

# 3.1 Testing levels

# Unit Testing

Unit Testing refers to tests that verify the functionality of a specific section of code. In an object-oriented environment, this is usually at the class level. In other words, a unit is usually a class and a unit test would verify the functionality of the class as a whole.

However, when you have, for example, two tightly coupled classes, and your team may decide that they need to be tested as a single unit. In short, your team and your code decide what makes up a unit.

If you are not sure what constitutes a unit in your code base, a class is a good place to start. The smallest unit is a class, or a function if you have some code which PHP functions outside of classes. A method (a function defined within a class) is usually not considered a unit, so it can't be tested in isolation from the class which defines it.

> Testing Tip: Test Classes, Not Methods
Testing rather than individual methods is good practice, because we don't have to concern ourselves with the internal state of a class if it never changes the outcome of a method call. If you write a test to check the internal logic of a class, it may prevent you from refactoring the class.

# Integration Testing

Integration Testing refers to tests that verify the functionality of more than one unit. If all units pass, there might be bugs where two units interact with each other, so unit testing is not enough.

We can say that Functional Testing, Database Testing, and Browser Testing are types of Integration Testing.
