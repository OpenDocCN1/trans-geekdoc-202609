
# VPN 解决方案

VPN 解决方案采用对称加密来保护传输中的通信。这种保护可防止未经授权的窃听或中途篡改。

## 非对称加密

[非对称加密](#30_glossary.xhtml#gloss30)基于使用[密钥对](#30_glossary.xhtml#gloss270)或其他特殊数学机制的算法。使用密钥对的非对称加密通常称为[公钥加密](#30_glossary.xhtml#gloss378)。所有公钥加密都是非对称的，但某些非对称算法并非公钥算法。记住非对称加密所用密钥或非密钥类型的常用方法是记住“asymmetric”（非对称）的同义词：“different”（不同）。不同的密钥用于不同的目的，不同的密钥由通信会话的不同成员使用，某些系统则完全使用不同于密钥的东西。

### 技术提示

请记住，平均 2,048 位非对称密钥不仅仅是非常强的 256 位对称密钥长度的 8 倍；实际上，其密钥空间是 256 位密钥密钥空间的 2^1,792 倍（即 2.79 × 10^539 倍），这是一个天文数字。这种规模的数字非常难以管理，更不用说进行复杂的数学计算了。

与对称加密相比，非对称加密非常慢。这是由于这些算法所用数学的复杂性，以及非对称密钥的长度（当存在密钥时）。公钥加密使用的密钥长度为 1,024 到 8,192 位（有时更长）。

非对称加密还使用基于单向函数概念的数学。[单向函数](#30_glossary.xhtml#gloss324)是指在一个方向上相对容易执行，但不可能或几乎不可能逆向执行的数学运算。这种数学在 20 世纪 70 年代末被形式化为加密算法。不要因为它看起来很旧就低估这类函数的强度。

由于非对称加密具有极长的密钥和极其复杂的数学函数，因此与对称加密相比速度较慢。因此，非对称加密通常不适合用于加密存储或传输的大量数据；相反，这种加密最适合用于[身份验证](#30_glossary.xhtml#gloss232)和[密钥交换](#30_glossary.xhtml#gloss269)。

非对称加密提供的保护是真实性和不可抵赖性。[真实性](#30_glossary.xhtml#gloss38)是一个用于传达认证与访问控制相结合的术语。根据用法，特别是结合公钥加密，非对称解决方案可以证明消息来源的身份（认证）或控制消息的目标或接收者（访问控制）。此外，当正确使用时，非对称加密可提供发送者发送了消息的证明，并防止发送者可信地否认发送过该消息，这称为不可抵赖性。

公钥加密是非对称加密的一个子集，基于密钥对。通信或社区中的每个参与者都有一组离散的密钥对。密钥对集由一个[私钥](#30_glossary.xhtml#gloss365)和一个[公钥](#30_glossary.xhtml#gloss377)组成。私钥始终保持安全和私密。公钥则公开供公众访问和使用。密钥对作为相反数协同工作。其中一个密钥执行的加密或编码只能由该密钥对的相反密钥撤销。

非对称加密提供的一种机制是[数字信封](#30_glossary.xhtml#gloss134)。其工作原理如下（[**图 9-10**](#20_chapter09_07.xhtml#fig9-10)）：

![图 9-10 数字信封的非对称加密过程](Images/9781284183658_CH09_FIGF10.png)

**图 9-10** 数字信封的非对称加密过程。

1.  Bob 获取 Alice 的公钥。
2.  Bob 使用 Alice 的公钥对消息进行编码。
3.  Bob 将消息发送给 Alice。
4.  Alice 使用她的私钥对消息进行解码。

编码后的消息只有拥有相应私钥的 Alice 才能读取。数字信封确保消息仅可由预期接收者（即相应私钥的所有者）访问。数字信封机制在通信伙伴之间交换对称密钥。在此机制中，对话的一方执行密钥生成，然后安全地交换该密钥。这是 VPN 用于安全交换密钥的机制。

非对称加密提供的另一种机制是数字签名。[数字签名](#30_glossary.xhtml#gloss135)可证明发送者的身份。其工作原理如下（[**图 9-11**](#20_chapter09_07.xhtml#fig9-11)）：

![图 9-11 数字签名的非对称加密过程](Images/9781284183658_CH09_FIGF11.png)

**图 9-11** 数字签名的非对称加密过程。

1.  Alice 使用她的私钥对消息进行编码。
2.  Alice 将编码后的消息发送给 Bob。
3.  Bob 获取 Alice 的公钥。
4.  Bob 使用 Alice 的公钥解锁编码。

此过程向 Bob 证明消息来自 Alice。这就是真实性。数字签名并不阻止他人查看消息或确认消息来源。数字签名不是加密；它不提供机密性保护。VPN 使用数字签名，但这些通常采用将哈希作为过程一部分的版本（见下一个示例）。

通过添加哈希，数字签名机制得以改进。（哈希在下一节中有更详细的描述。）使用哈希的数字签名稍微复杂一些，采用以下程序（[**图 9-12**](#20_chapter09_07.xhtml#fig9-12)）：

![图 9-12 带哈希的数字签名非对称加密过程](Images/9781284183658_CH09_FIGF12.png)

**图 9-12** 带哈希的数字签名非对称加密过程。

1.  Alice 计算消息的哈希值。
2.  Alice 使用她的私钥对哈希值进行编码。此编码后的哈希即为数字签名。
3.  Alice 将编码后的哈希添加到消息中。
4.  Alice 传输消息。
5.  Bob 去除 Alice 的数字签名。
6.  Bob 对原始消息进行哈希运算以计算其哈希值。
7.  Bob 获取 Alice 的公钥。
8.  Bob 解码 Alice 的数字签名以显示 Alice 的原始哈希值。
9.  Bob 将 Alice 的原始哈希值与 Bob 计算的哈希值进行比较。

如果哈希值相同，Bob 将接受该消息为保持完整性。这也证明了消息来自 Alice（真实性）。此外，此过程确保 Alice 不能否认曾发送过该消息（不可抵赖性）。VPN 通常采用这种形式的数字签名来证明端点身份并确认传输的完整性。

一些非公钥加密的非对称加密算法或系统示例包括 Diffie-Hellmann、El Gamal 和椭圆曲线加密（ECC）。作为公钥加密的非对称加密算法或系统的最常见示例是 Rivest-Shamir-Adleman（RSA）。VPN 解决方案采用非对称加密来保护对称密钥交换（通过数字信封）、认证 VPN 链路端点或用户（通过数字签名），以及在结合哈希时验证传输消息的来源和完整性（同样是数字签名）。
