最好但也最费力的方法是编写能够揭示 goroutine 泄漏的单元测试。我们的目标是覆盖所有可能发生 goroutine 泄漏的场景。测试本质上会在测试结束时检查后台是否仍有 goroutine 在运行。Go 允许我们使用 `runtime.NumGoroutine()` 查看后台运行了多少个 goroutine。我们也可以使用外部包，如 `uber-go/goleak`。

## Fan In Fan Out 模式

Fan In Fan Out 是一种流行的模式，它帮助我们将多个来源转换为单个流（fan-in），或将来自单个来源的输入流式传输到多个管道中（fan-out）。在 Go 中，如果我们需要多个函数从同一个通道读取数据直到该通道关闭 —— 即 fan-out。一个函数可以从多个输入（来源）读取数据，直到所有输入通道都关闭 —— 即 fan-in。

### Fan Out

当我们想要将工作分配给一组工作协程，以通过并行利用 CPU 和 I/O 等资源来进行优化时，应使用 fan-out 模式。

```go
func generator(numbers []int) <-chan int {
    out := make(chan int)
    go func() {
        for _, num := range numbers {
            out <- num
        }
        close(out)
    }()
    return out
}

func businessLogic(num int) int {
    return num * 2
}

func main() {
    data := []int{1, 2, 3, 4, 5, 6}
    var wg sync.WaitGroup
    ch1 := generator(data[0:3])
    ch2 := generator(data[3:])
    wg.Add(2)
    go func() {
        for num := range ch1 {
            println(businessLogic(num))
        }
        wg.Done()
    }()
    go func() {
        for num := range ch2 {
            println(businessLogic(num))
        }
        wg.Done()
    }()
    wg.Wait()
}
```

在前面的示例中，我们有一个 `data` 变量（来源），但我们想要并行化该数据的处理过程。我们决定将工作分配给两个工作协程。我们做的第一件事是将数据分成两份。然后，我们调用了 `generator` 函数。`generator` 函数的目的是接收输入，将所有输入发送到一个名为 `out` 的通道中，然后返回该通道。在两次调用 `generator` 函数后，我们使用了 `WaitGroup` 来等待所有工作协程完成工作。最后，我们启动了两个 goroutine（工作协程）。每个工作协程执行一些业务逻辑，然后结束。

### Fan In

我们应该使用 fan-in 模式将多个输入（来源）处理汇总到单个函数中。我们将通过将多个通道合并为一个来实现这一点。将多个通道合并为单个通道的过程称为多路复用。只有当所有输入通道都关闭时，单个输出通道才会关闭。我们将通过一个名为 `merge` 的函数来研究多路复用过程。

```go
func merge(sourcesCh ...<-chan int) <-chan int {
    var wg sync.WaitGroup
    wg.Add(len(sourcesCh))
    out := make(chan int)
    outputFunc := func(sourceCh <-chan int) {
        for num := range sourceCh {
            out <- num
        }
        wg.Done()
    }
    for _, sourceCh := range sourcesCh {
        go outputFunc(sourceCh)
    }
    go func() {
        wg.Wait()
        close(out)
    }()
    return out
}

func generator(numbers []int) <-chan int {
    out := make(chan int)
    go func() {
        for _, num := range numbers {
            out <- num
        }
        close(out)
    }()
    return out
}

func main() {
    data := []int{1, 2, 3, 4, 5, 6}
    ch1 := generator(data[0:3])
    ch2 := generator(data[3:])
    ch := merge(ch1, ch2)
    for num := range ch {
        println(num)
    }
}
```

`generator` 函数与我们在 fan-out 模式示例中看到的相同。我们首先在 `merge` 函数中声明单个输出通道 `out`。其次，我们创建一个 `WaitGroup` 来确定何时所有源通道都已关闭。在它们关闭后，我们将使用 `Wait()` 并关闭输出（`out`）通道。然后，我们创建了一个函数（`outputFunc`），它接收源通道并将该源通道的所有数据发送到输出通道（`out`）。最后，我们遍历所有源通道并启动 goroutine 执行 `outputFunc`。

现在我们在 `main` 函数中拥有了一个单一的通道，可以安全地迭代，直到 `merge` 函数关闭该通道。

## 服务间通信

正如我们在*第 1 章，微服务简介*中所见，微服务架构由小型、独立且解耦的服务组成。每个服务旨在实现**单一**目的。然而，系统需要利用所有服务来达成更大的目标。为追求这些目标，服务需要一种通信手段，通过发送和接收来交换数据。这种通信形式因其复杂性而呈现多种面貌。

需要考虑的方面很多——消息类型、消息大小、响应方式、延迟、故障、文档、消息打包等。以下是在微服务架构中通信的主要形式：

*   API 调用
*   消息代理
*   gRPC

我们不会深入探讨这些形式，因为每一个都很庞大，需要透彻的理解。要正确、精确地使用它们，我们必须知道如何正确构建它们。我们还必须熟悉它们的优缺点，以便在选择时做出最佳决策。此外，还有其他几个因素、约束和假设增加了局势的复杂性。

### API 调用

API 代表应用程序编程接口。API 调用由发送调用的服务发起的请求和接收请求的服务返回的响应组成。每个请求包含参数，指明请求的是哪些数据。我们通过网络的第 7 层（应用层）发送 API 请求。

API 调用是微服务架构中服务间最常用的通信方式。多样的 API 风格（如 REST、SOAP 和 GraphQL）值得深入讨论。其中，REST 是采用最广泛的。因此，下一章（*第 7 章，构建 RESTful API*）将探讨 RESTful API。

### 消息代理

我们在上一章提到了消息代理，并将其与发布/订阅设计模式进行了比较。对消息代理的一个贴切描述是：将其定义为一项服务与另一项服务之间消息的中介。服务不直接向另一服务发送请求，而是将消息发送给代理。消息主要包含数据、配置，有时还包含指令。消息代理是一个独立的服务，通常由许多服务组成，并作为一个独立的集群运行。代理的目标是接收消息，并通知其他服务有关此消息，或将其存储直到另一服务拉取它。消息代理还有许多额外功能，如重试、存储 DLQ（即死信队列）、监控、临时存储、加密、控制消息中介的速度等。

### gRPC

gRPC 是一个现代的、开源的 Google 远程过程调用（RPC）**框架**。gRPC 允许使用 Protocol Buffers 定义与语言无关的 API。Protocol Buffers（protobuf）是一种与语言无关的序列化格式，可高效地构建和序列化数据。我们可以使用 Protocol Buffers 在各种编程语言中快速创建客户端和服务端实现。gRPC 框架利用 HTTP/2 作为底层协议，支持双向流式传输和实时通信等多种能力。在幕后，它本质上只是一个 API 调用，但它利用了 HTTP/2 的能力，这使其非常强大。虽然简单的 API 很直观，但 gRPC 学习曲线平缓。此外，gRPC 框架并不支持所有编程语言。

## API 网关

在微服务架构中，服务间通信有多种方式。标准方式是通过简单的 API，正如我们所见。

API 网关是一项充当微服务架构入口（网关）的服务。API 网关接受来自所有客户端的请求，然后将客户端请求导向目标服务，并将响应返回给客户端。拥有单一的系统入口点，使我们能完全**控制**进出的内容。我们可以使用 API 网关实现几类功能：

*   **安全性**：每个服务可以使用身份验证、授权和加密功能。每个服务不必强制执行这些安全要求。相反，大多数事情可以在 API 网关中完成。有时，由于业务逻辑约束，无法执行任何操作。
*   **可观测性**：每个服务可以使用指标、日志和追踪等功能。我们可以从 API 网关开始追踪所有请求。
*   **路由**：限流、缓存、故障处理、负载均衡、滚动更新功能等。所有这些逻辑都可以在 API 网关内部实现。

![图 6.3：API 网关，客户端向服务发送请求](img/Figure-6.3.jpg)

在上图中，我们可以看到不同的客户端向 API 网关发送请求。API 网关根据请求的路径和域名知道如何将每个请求导向目标服务。此示例演示了我们提到的 API 网关路由功能等。

构建架构时要记住的最重要一点是优先考虑**简洁性**。API 网关模式之所以有益且强大，是因为它帮助我们实现更简单的架构。它集中处理了许多关注点——安全性、可观测性、负载均衡、限流等。当问题发生时，我们会知道去哪里调查事故。

请注意，每个 API 网关各不相同。每个架构有不同的需求，导致不同的 API 网关方案。*第 8 章，Kubernetes 简介*将讨论 Kubernetes 如何使用名为 ingress 的资源独立实现某些 API 网关模式功能。

## 服务发现

### 微服务架构中的服务发现与负载均衡

在微服务架构中，正如我们所说，服务之间的通信方式是通过 API。每当一个服务需要发送 API 请求时，它必须确定目标服务的网络位置（IP 地址和端口）。由于系统需求（每台服务器能并发处理的请求数有限），每个服务可能有多个实例。每个服务实例都有不同的网络位置（IP 地址和端口）。在动态云环境中，由于更新、扩缩容、故障等原因，每个服务实例的网络位置是临时且频繁变化的。我们需要帮助来识别现有的服务实例及其对应的网络位置。

解决此问题的方案是**服务发现**。服务发现模式让服务知道被请求服务实例的网络位置。当请求服务得知服务网络位置后，即可开始与目标服务通信。实现服务发现主要有两种模式：

*   客户端发现
*   服务端发现

#### 客户端发现

客户端使用此模式确定被请求服务实例的网络位置。请求服务向一个已知的存储发送请求，该存储保存着每个服务的网络位置。所谓的 `service registry`（服务注册表）即拥有所有服务实例网络位置的存储。

![图 6.4：通过客户端发现进行服务发现](img/Figure-6.4.jpg)

`Requesting Service Instance`（请求服务实例）通过 HTTP 请求向服务注册表询问 `ServiceA` 实例的网络位置。服务注册表拥有 `ServiceA` 实例的网络位置。服务实例负责将其网络位置发送给服务注册表。`Requesting Service Instance` 获取网络位置后，即可请求其想要的每个 `ServiceA` 实例。在上图中，我们请求地址为 `1.2.3.4:5555` 的实例。

该模式的主要缺点是我们必须在客户端实现复杂的负载均衡和发现逻辑，这意味着必须为每种编程语言复制一套逻辑。

#### 服务端发现

服务端发现模式是两者中更流行的一种。在此模式中，所有“问题”都转移给负载均衡器，它充当“服务端”的角色。客户端向负载均衡器发送请求，负载均衡器的行为类似于客户端发现模式中的客户端。

![图 6.5：通过服务端发现进行服务发现](img/Figure-6.5.jpg)

所有关于负载均衡的功能都在 `Load Balancer`（负载均衡器）中，而非客户端。该模式将发现逻辑从 `Requesting Service Instance`（请求服务实例）分离到 `Load Balancer`（负载均衡器），这是该模式的主要优势。

`NGINX`、`AWS ALB` 和 `AWS ELB` 是常见的可充当服务端的负载均衡器。在*第 8 章 Kubernetes 简介*中，我们将讨论 Kubernetes，它使用服务端方法实现了服务发现模式。

#### 服务注册表
