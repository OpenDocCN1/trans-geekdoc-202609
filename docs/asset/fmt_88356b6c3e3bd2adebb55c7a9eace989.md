
存储过程是在数据库上创建的对象，它们封装了执行插入记录、删除记录和更新记录等操作所需的 SQL 代码。这些代码可以直接写在客户端应用程序（Web 应用、移动应用或桌面应用程序）中，但将数据库逻辑放在存储过程中有许多好处：

- **性能** 如果数据库代码在客户端应用程序中，当应用程序执行时，它必须将代码发送到服务器，服务器随后会解析代码、优化它、编译它并执行它。使用存储过程，解析、优化和编译仅在首次调用存储过程时完成。后续调用只需执行已缓存的、已编译的存储过程版本。

- **可维护性** 如果您将 SQL 代码放在存储过程中而不是每个软件应用程序中，您就有一个集中的位置来更新数据库逻辑。当逻辑需要更改时，您只需更改存储过程中的 SQL 代码，所有调用该存储过程的应用程序都将运行更新后的代码。

### 安全性

当使用参数且存储过程已准备就绪（意味着在首次使用前已预编译）时，存储过程有助于防止 SQL 注入攻击。其优势在于：因为存储过程已预编译，如果黑客试图将 SQL 命令注入参数，他们将收到错误，因为存储过程已经过编译，所以作为参数插入的代码不被接受。

#### 代码签名

开发人员可以对其代码进行数字签名，以便公司知晓代码的来源。这样，他们就可以信任该代码不会对系统造成危害。代码签名还为代码增加了完整性，因为会生成代码的哈希值，这意味着代码通过算法运行并生成一个结果。该结果与代码一起存储。稍后当你将代码与哈希值（结果）进行核对时，这提供了一种验证代码未被篡改的方法。

为了对代码（如 DLL 或 EXE 文件）甚至脚本（如 PowerShell 脚本）进行数字签名，你需要一个代码签名证书。该证书是一个电子文件，包含用于对其他文件进行数字签名的密钥。你将在 `第 12 章` 和 `第 13 章` 了解更多关于证书和公钥基础设施 (PKI) 的内容。

# 加密

在开发应用程序时，加密敏感数据是一个重要的考量因素。开发应用程序时，有几个方面需要考虑加密。第一是通信协议。如果你的应用程序正在与网络或互联网上的其他系统通信，是否应该加密通信？如果你正在传输敏感数据，答案是肯定的。另一个需要考虑加密的方面是数据存储。如果你将敏感信息存储到文件中，则该文件应被加密，或文件中的数据应被加密。如果你在数据库中存储敏感数据，请务必在数据存入数据库时对其进行加密。

#### 其他技术

开发应用程序时，还有许多其他常见的安全编码实践你应该遵循。如果你不是程序员，而是组织内的信息安全官员，你也需要了解这些编码技术，并确保内部应用程序是使用这些技术构建的。在开发应用程序或评估应用程序安全性时，请务必在以下领域检查安全编码技术：

- **规范化** 在为应用程序开发数据库时，你将数据拆分到多个表中以减少数据冗余。例如，数据库中有一个客户表，存储客户 ID、姓和名等客户信息。每当客户进行购买时，你只在购买表中记录客户 ID，而不记录客户姓名信息。

- **混淆/伪装** 混淆和伪装是常见的安全原则，通过使功能或组件变得晦涩或不清晰来增加安全性。这里的思路是，如果产品或功能难以理解或发现，那么它就更难被利用。

- **代码重用/死代码** 代码重用是一种常见的编程实践，可以增加应用程序的安全性。你可以创建一组遵循安全编码原则的函数，然后从任何需要该功能的应用程序中调用这些函数。其目的是让你知道你正在调用已经过测试和验证的代码，而不是重新创建可能存在漏洞的新代码。你还应该评估代码并查找死代码，即函数中执行并返回结果，但该结果在应用程序的任何地方都未被使用的代码。死代码应被移除，因为如果留着不管、久而久之被遗忘，该代码可能容易受到攻击。例如，你可能有一个包含不再使用的函数的 API。应从 API 中移除该函数，以防止未来针对该函数的攻击。

- **服务端与客户端执行和验证** 从安全应用程序设计的角度来看，让服务端代码执行比客户端代码更安全。客户端代码可以在客户端被更改，确实不应依赖它。例如，你应该始终在服务端实现验证代码，但只要可能，在客户端和服务端同时实现验证代码也无妨。

- **内存管理** 开发人员学会正确管理内存至关重要。这涉及通过正确销毁不再使用的对象来释放内存。如果开发人员未能清理内存，可能会导致应用程序出现内存泄漏。

- **使用第三方库和 SDK** 限制在应用程序和软件开发工具包 (SDK) 中使用第三方 DLL。你不知道这些组件中的代码有多安全，因为你没有编写它。

- **数据暴露** 请务必限制从应用程序暴露的数据量。实现这一点的技术之一称为*封装*。你可以创建与数据交互的公共方法，而不直接暴露数据。

#### 开放 Web 应用程序安全项目

作为一名安全专业人员，如果你负责测试软件的安全编码实践，你绝对应该了解开放 Web 应用程序安全项目 (OWASP)。该项目由一个在线社区支持，发布了许多专注于教育人们了解 Web 应用程序常见漏洞以及应用于保护 Web 应用程序的常见安全技术的文章、工具和文档。

你可以在 [www.owasp.org](http://www.owasp.org) 查看 OWASP。OWASP 产出的最常见文档之一是“OWASP Top 10”，详细列出了 Web 应用程序中发现的前 10 大漏洞。请在 [`owasp.org/www-project-top-ten/`](https://owasp.org/www-project-top-ten/) 查看“OWASP Top 10”。针对前 10 大漏洞中的每一个，你都可以选择链接阅读更多关于该漏洞的信息，包括预防技术。我强烈建议查看这些信息。

#### 软件多样性

你将遇到各种类型的软件环境。例如，你会遇到*编译代码*，即开发人员开发应用程序，然后将其编译成二进制文件（不可读的可执行文件）。

这不同于在脚本环境中创建的程序。脚本未经过编译，因此可以轻松在编辑器中打开、修改、保存，然后再次运行。脚本由已安装在系统上的脚本引擎解析并运行。

*软件多样性*是指使用不同的编译器创建不同的已编译二进制代码版本。这还包括二进制随机化，即你可以对二进制文件应用运行时随机化，使代码更难被利用。

### 自动化/脚本

当今安全工作的很大一部分是尽可能实现自动化，这样你就不必一遍又一遍地执行重复性任务。自动化是创建脚本来为我们执行任务的概念。自动化的好处是，一旦脚本创建并测试完成，你就可以确信每次运行脚本时，该过程都将以一致的方式执行。以下是使用自动化的常见领域（请注意，此列表中的*持续*一词是指可重复的、持续进行的过程）：

### 自动化处理流程

自动化的目标是将您必须定期执行的任务或处理流程自动化，从而降低执行这些任务时发生人为错误的几率。

### 持续交付

一个编程术语，指软件开发团队以短周期更新软件，以确保能够随时发布新版本。

### 持续验证

使用脚本在应用程序编译并最终部署之前执行代码检查，从而实现验证代码过程的自动化。

### 持续部署

将编译后的应用程序部署到生产系统中。

### 持续集成

一种流程，每当代码被签入系统时，就会触发持续验证；如果验证成功，则编译代码。一旦构建成功（应用程序编译完成），可能会触发通过持续部署将应用程序自动部署到生产环境中。

### 持续监控

系统或应用程序部署后，您可以使用脚本自动监控该系统或应用程序的健康状况。

### 弹性与可扩展性

如今我们常听到的术语，尤其是在云计算领域，就是 `elasticity` 和 `scalability`。将应用程序置于云端将为您带来弹性和可扩展性的优势。`Elasticity`（弹性）是指云环境可以根据工作负载动态调整分配给应用程序的资源。如果负载较重，云环境可以分配更多内存或处理能力，然后在不需要时降低这些资源。`Scalability`（可扩展性）是指云提供商可以随着需求在较长时期内增长，在后台手动提供更多服务器。

## 主机安全

有多种方法可以帮助保护主机系统免受在该系统上运行的恶意代码侵害。以下是针对 Security+ 考试需要了解的三项关键安全功能：

- **允许列表** 以前称为白名单。您可以创建一个允许在系统上运行的应用程序列表。任何其他应用程序都将被禁止运行。这有助于确保只有经过测试和批准的应用程序才能在公司系统上运行。

- **阻止列表/拒绝列表** 以前称为黑名单。您可以创建一个应用程序阻止列表（或拒绝列表）。除您放入阻止/拒绝列表的应用程序外，所有应用程序都将被允许在系统上运行。这是处理通过电子邮件发送给人们的恶意应用程序的绝佳方式，可确保您的用户不会运行它。

- **安全编码实践** 遵循我们之前讨论的安全编码实践至关重要，包括在将应用程序部署到生产环境之前对其进行测试。

### 应用安全

为帮助提高应用安全性，您可以遵循以下最佳实践：

- **输入验证** 如果软件程序员在处理发送给应用程序的输入之前对其进行验证，则可以防止许多针对应用程序的攻击。这是防止多种注入攻击和跨站脚本攻击的方法。

- **安全 Cookie** Cookie 用于存储用户访问网站时的偏好设置。Cookie 从客户端发送到 Web 服务器以读取信息，并根据用户偏好定制站点。使用安全 Cookie 会在 Cookie 上设置一个标志，使其仅在站点使用 HTTPS 时才发送到 Web 服务器。

- **超文本传输协议 (HTTP) 标头** HTTP 现在支持可提高 Web 应用程序安全性并防范点击劫持和跨站脚本攻击的标头值。例如，您可以使用 `Content-Security-Policy` 标头来控制脚本、样式和图片的允许来源。

- **代码签名** 代码签名是验证应用程序代码完整性的重要功能。出于安全原因，许多环境将仅执行由受信任来源使用代码签名证书进行数字签名的代码。

### 代码质量与测试

创建安全应用程序的关键在于确保实施适当的代码质量检查和测试。以下是应执行的不同代码质量检查和应用程序测试：

- **静态代码分析** 静态代码分析通常是执行的第一种代码测试类型，涉及在不运行代码的情况下审查代码以识别问题。代码可以人工审查，由团队通读，但也有称为静态代码分析器的工具可用于审查代码并查找潜在漏洞。

- **动态代码分析** 动态分析涉及通过执行代码来测试代码，并查看应用程序在系统上使用时的响应方式。动态分析的示例包括运行单元测试、集成测试、系统测试和验收测试。

- **压力测试** 压力测试是一种测试形式，它给应用程序施加大量负载，以确定如果大量用户同时使用该应用程序，它在生产环境中会如何响应。

- **沙箱** `Sandboxing`（沙箱技术）是指在隔离环境中运行已更改的代码（远离生产系统），以测试代码更改的影响。

- **模型验证** 模型是对即将开发的真实程序的模拟，但并非所有功能都编程在模型中。模型在应用程序开发的初始阶段创建，用于验证客户是否对应用程序的基本元素满意。应定期验证模型，以确保其仍满足客户需求。

#### 模糊测试

公司必须通过在应用程序的所有数据输入屏幕中故意输入无效信息，来测试他们创建的任何软件。向应用程序的输入字段输入无效或随机数据的软件测试术语称为 `fuzzing`（模糊测试）。
