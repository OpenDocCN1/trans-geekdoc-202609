## 10.1 连接约束

### 高级建模主题

本章探讨若干高级建模主题，并假设读者熟悉对象角色建模（`ORM`）、Barker 实体关系（`ER`）建模以及统一建模语言（`UML`）类图的基础知识。虽然主要关注点在于 `ORM`，但也会对其他方法给予一定关注。即使 `ER` 和 `UML` 无法为所讨论的特性提供内置支持，许多思想至少可作为扩展应用于这些方法中。

### 连接约束

本节考察*连接约束*，首先考虑单一连接路径上的连接约束，然后是涉及连接的集合比较约束。虽然这些约束的考量实际上属于*概念模式设计过程（CSDP）*步骤 7 的一部分，但由于其高级性质，我们将其详细讨论推迟至今。

概念连接的概念在第 4.4 节中引入，并在第 9.7 节中进一步阐述。通过跨两个或多个角色的*概念内连接*，同一对象扮演所有这些角色。在图 10.1(a)中，存在一条单一连接路径：Building contains Room **that** has RoomNr。从语言学角度来看，该路径表达式中的代词“**that**”声明了该连接，表明是同一个房间在扮演这两个连接角色（此处为讨论目的而着色）。

![图 10.1 (a) ORM、(b) Barker ER 和 (c) UML 中的简单概念连接。](img/f10-01-9780443237904.jpg)

图 10.1 (a) ORM、(b) Barker ER 和 (c) UML 中的简单概念连接。

外部唯一性约束声明了每个建筑、房间号组合最多适用于一个房间。这等价于在实例化该概念连接路径的（建筑、房间、房间号）元组集合上，施加一个针对建筑、房间号的内部唯一性约束。

图 10.1(b) 以 Barker ER 符号展示了相同的模式。外部唯一性约束通过结合 "`#`" 和 "`|`" 来捕获。图 10.1(c) 展示了 UML 版本，外部唯一性约束通过结合两个 `{id}` 标记来捕获。

在房间示例中，参与概念连接的两个角色对于连接对象类型（Room）均是强制的。这确保了概念连接为内连接。然而，如果参与概念连接的一个或多个角色是可选的，则使用外部唯一性约束需要特别小心。例如，考虑图 10.2 中所示的三个 ORM 模式。

![图 10.2 可选角色可能涉及内连接 (a) 或外连接 (b)、(c)。](img/f10-02-9780443237904.jpg)

图 10.2 可选角色可能涉及内连接 (a) 或外连接 (b)、(c)。

图 10.2(a) 中的 ORM 模式是 ORM 元模式的一个片段。`ORM` 要求每个谓词至少有一种读法，但角色是否被赋予名称则是可选的。在图中，`RoleName` 扮演的角色被命名为 "name"，但其他角色未命名。外部唯一性约束表明，角色名称在给定谓词内是唯一的。一个谓词可能有许多未命名的角色，但如果一个角色被命名，它就可以通过其名称与其谓词的组合来识别。

这种情况要求对外部唯一性约束底层连接路径采用*内连接解释*。让我们将关联 `Role is in Predicate` 的谓词标识为 `P1`，其左、右角色分别标识为 `r1` 和 `r2`。同样，将关联 `Role has RoleName` 的谓词标识为 `P2`，其左、右角色分别标识为 `r3` 和 `r4`。这两个事实类型的内连接产生一个复合三元事实类型，等价于以下关系表模式。

```
Role( roleId, predicateId, [roleName] )       r4     P2      name
```

此关系符号下划线标识唯一性约束；若存在多个，主键以双下划线标识。可选列用方括号标记。外部唯一性约束表现为复合内部唯一性约束。因为我们仅要求角色在被命名时才在谓词内拥有唯一名称，所以图 10.2(a) 中 `Role` 角色之间的概念连接是内连接，从而产生如图所示的单行填充。

使用 "`?`" 表示空值，外连接结果将包含四个元组：(`r1`, `P1`, `?`)、(`r2`, `P1`, `?`)、(`r3`, `P2`, `?`) 和 (`r4`, `P2`, `name`)。前两个元组将违反复合唯一性约束，因此不应在此示例中使用外连接语义。

图 10.2(b) 和 (c) 中的外部唯一性约束在唯一性横杠上标有一个*内部的 "o"*。这表明该外部唯一性约束具有*外连接语义*，并附带一个条件：*外连接产生的空值被视为实际值*。

因此，每门课程恰好可由以下模式之一引用：课程标题与其院系的组合（课程由某院系开设）；或仅其课程标题（课程不由任何院系开设，例如由客座讲师开设的课程）。

此类外部唯一性约束用两句话表达，一句针对内连接语义，另一句针对外连接的额外语义。图 10.2(b) 中的外部唯一性约束表达如下：

```
对于每个 CourseTitle 和 Department，至多有一个 Course 拥有该 CourseTitle 并由该 Department 开设。
对于每个 CourseTitle，至多有一个 Course 拥有该 CourseTitle 且不由任何 Department 开设。
```

考虑一个包含三门课程 `C1`、`C2` 和 `C3` 的示例填充，它们拥有相同的标题，一门由物理系开设，一门由数学系开设，一门不由任何院系开设。标题和院系事实类型的连接产生一个复合三元事实类型，等价于以下关系表模式。外部唯一性约束表现为跨越 courseTitle 和 departmentCode 的内部唯一性约束。

*   ```
    Course( courseCode, courseTitle, [departmentCode] )
    ```

*   ```
                              C1                            Mechanics            PY
    ```

*   ```
                              C2                            Mechanics            MA
    ```

*   ```
                              C3                            Mechanics            ?
    ```

*   ```
    C4 Mechanics            ?                        - - 违反约束
    ```

第四行（`C4`、`Mechanics`、`?`）被拒绝，因为在第 3 行存在的情况下，它违反了无院系课程必须拥有不同标题的约束。为确定约束满足情况，第 3 行和第 4 行上的空值被视为普通值，因此被等同对待。这实际上应用了*外连接语义*。

即使离散标识方案是识别课程的唯一手段，外连接语义也可能适用，如图 10.2(c) 所示。

仅当该实体类型在受约束关系中承载的共角色为强制时，具有内连接语义的外部约束才可用作实体类型的首选标识方案，如图 10.2(a) 所示。

在之前的示例中，外部唯一性约束底层的连接路径仅涉及一次连接。但在实践中，*连接路径*可能涉及多个内连接或外连接。图 10.3 总结了*连接路径歧义*问题。要找到外部唯一性约束底层的连接路径，我们需要找到一条连接角色 r2 和 r9 的路径，从 r2 向右移动，从 r9 向左移动。

![图 10.3 连接路径可能需要显式声明连接角色。](img/f10-03-9780443237904.jpg)

图 10.3 连接路径可能需要显式声明连接角色。

我们的选择已加阴影标出，但在 *B* 和 *C* 之间存在三条可能的路径。我们可以遍历顶部谓词，执行连接 `r2 = r3` 和 `r4 = r9`。我们可以遍历隐含在子类型连接下的中间谓词，执行连接 `r2 = r5` 和 `r6 = r9`，或者我们可以遍历底部谓词，执行连接 `r2 = r7` 和 `r8 = r9`。

ORM 不会以图形方式高亮显示相关连接（此处通过阴影演示）。一般来说，阴影标注是不够的，因为路径可能会多次遍历同一个谓词。一种通用的图形解决方案是对用于执行连接的角色进行编号，但这可能导致图表混乱。工具可以提示用户选择连接角色列表，然后在用户控制下切换连接的显示/隐藏。另一种替代方案是使用文本语言来制定具有多个候选连接路径的约束。NORMA 专业版提供了对连接路径的正式支持。

对于非 ORM 方法，需要基本的外部唯一性支持，然后连接路径可以像 ORM 一样以图形方式消除歧义，或者如果该方法包含足够强大的形式化查询语言，则以文本方式消除歧义。UML 可以使用对象约束语言（OCL）进行此类规范，尽管 OCL 表达式对非技术领域专家来说通常显得晦涩难懂。

正如外部唯一性约束一样，外部频率约束也有底层的连接路径。如果连接涉及可选角色，则假定为内连接。例如，图 10.4 中的外部频率约束仅适用于作为共同摄政王的政治家，因此其语言化表述为：**对于每个** Country，**至多有** 2 **个** Politician 实例，**使得该** Politician **是** 共同摄政王 **并且** 在 **该** Country 的政府中任职。

![图 10.4 涉及一元事实类型的外部频率约束。](img/f10-04-9780443237904.jpg)

图 10.4 涉及一元事实类型的外部频率约束。

回顾一下，ORM *集合比较约束*在兼容的角色序列之间应用子集、等值或排斥约束。有时这些角色序列中的一个或多个是从连接路径投影而来的。作为一个简单示例，图 10.5(a) 中的连接子集约束从组成“Advisor serves in Country”事实类型的角色对，运行到组成“Advisor speaks Language”和“Country uses Language”事实类型的第一角色的角色对。

![图 10.5 (a)、(c) ORM 和 (b)、(d) UML 中的连接子集约束。](img/f10-05-9780443237904.jpg)

图 10.5 (a)、(c) ORM 和 (b)、(d) UML 中的连接子集约束。

该约束意味着填充“serves-in”谓词的顾问-国家对集合，必须是通过在连接路径“Advisor speaks Language **that** is used by Country”上投影顾问和国家角色获得的顾问-国家对集合的子集。

图 10.5(a) 中的连接路径在 Language 上涉及一个概念性的内连接，将扮演其两个角色的实例等同起来。换句话说，如果一位顾问在某个国家任职，则该顾问必须会说该国家使用的至少一种语言。该约束可以在 ORM 中正式语言化为：**每个** 在 **某个** Country 任职的 Advisor **也** 会说 **某个** 被 **该** Country 使用的 Language。

像 ER 一样，UML 没有用于表达连接子集约束的图形符号，但确实允许将约束以文本形式表达在附加到相关模型元素（在本例中为三个关联）的注释中，如图 10.5(b) 所示。ER 也可以改编为允许此类注释用法。

图 10.5(c) 显示了本书前面讨论的另一个示例。该约束可以在 ORM 中这样语言化：**如果某个** Employee **拥有某个** 受限于 **某个** Gender 的 PersonTitle，**则该** Employee **属于** 该 Gender。示例种群说明了头衔-性别限制。

如果将 personTitle 建模为属性，则无法在 UML 中表达头衔-性别限制。但是，如果我们将 PersonTitle 建模为类并为该限制附加注释，则可以在 UML 中建模，如图 10.5(d) 所示。附加到 Employee 类的注释用 OCL 正式捕获了头衔-性别限制。

连接子集约束在实际应用中经常出现。关于涉及三元事实类型的更复杂的连接子集，请回顾图 9.42 中的会议室设施示例。

*连接等值约束*较少见。图 10.6 中的 ORM 模式包含角色三元组之间的等值约束，其中第一个三元组涉及对象化关联上的连接。此处显示角色编号是为了阐明约束参数（NORMA 工具仅在输入或选择约束时显示这些编号）。该约束捕获了这样一条规则：小费必须针对赚取小费的那些服务进行报告，且仅针对那些服务。

图 10.7 中的 ORM 模式包含两个角色对之间的*连接排斥约束*。每个角色对都从涉及 Person 上连接的路径投影而来。角色对编号为 1.1、1.2 和 2.1、2.2。由于 Institute 扮演的角色出现在两个角色对中，因此它被编号了两次。

针对集合比较约束中涉及的每个连接路径，都可以提出与外部唯一性和频率约束底层连接路径相同的考量。虽然我们已经建模了许多涉及连接集合比较约束的业务领域，但连接类型始终是内连接。外部环约束以及值比较约束也可能涉及连接。对于值比较约束，连接类型始终是内连接。

我们建议使用正式语言以文本方式指定涉及外连接的任何集合比较或环约束，而不是为罕见情况使图形符号复杂化。

连接约束的映射取决于映射目标，通常是数据库管理系统（`DBMS`）或第三代编程语言（`3GL`）。商业结构化查询语言（`SQL`）往往偏离标准 `SQL`，在将唯一性约束映射到可空列时需要特别小心（详见第 12 章和第 13 章中关于 `SQL` 的进一步细节）。例如，假设我们要在 `SQL Server` 中实现 `Role`（`roleId`、`predicateId`、`[roleName]`）最后两列上的复合唯一性约束。如果声明了唯一约束，`SQL Server` 只允许一个 `null` 值，但我们想允许多个 `null` 值。为了实现此复合唯一性约束的内连接语义，我们需要显式地编写代码。所涉及的逻辑可列出如下：

```
check( not exists
         (select predicateId, roleName from Role
          where roleName is not null
          group by predicateId, roleName
          having count(*) > 1) )
```

## 10.2 Deontic Rules（道义规则）

业务领域受各种*业务规则*约束，这些规则指定了所需或期望的事务状态或行为。这些规则可能具有不同的*模态*（例如，真实模态和道义模态）。*真实规则*施加*必然性*，业务无法违反，通常是因为某些物理或逻辑定律。例如，每个人最多只在一个日期出生；没有产品是其自身的部件。

到目前为止我们考虑的所有约束都是真实规则。将它们包含在信息系统中的目的，不是为了防止规则在业务领域中被违反（因为在那里它们无法被违反），而是为了确保信息模型准确反映业务领域。

真实规则只是防止代表不可能情况的数据被录入系统。例如，如果信息系统强制执行员工出生事实类型的唯一性约束，我们就无法为同一员工记录两个出生日期。

*道义规则*施加*义务*，即使不应该违反，但仍可能被违反。例如，在大多数文化中，每个人最多只能与一个人结婚是强制性的，且通常禁止任何人在任何办公室吸烟。

企业应清楚了解其所有规则，包括道义规则，无论它是否选择强制执行这些规则，或通过自动化系统监控其违规情况。鉴于这一需求，ORM 2 和对象管理组的业务词汇与规则语义（`SBVR`）规范（<https://www.omg.org/spec/SBVR>）都支持道义规则的表述（OMG, 2019）。虽然 ER 和 UML 目前将规范限制在真实模态的规则上，但原则上这些方法可以扩展以适应道义规则。
