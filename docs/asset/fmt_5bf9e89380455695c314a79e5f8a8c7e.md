
本章前面介绍了几种优化策略。总体而言，该过程包含两个主要阶段：

* 通过减少映射表的数量进行转换（步骤 1 和 2）
* 通过简化单个表进行转换（步骤 3-5）

由于慢查询往往涉及连接或子查询，一种默认策略是尝试减少涉及连接或子查询的聚焦查询数量。优化过程的步骤 1 和 2 通过转换以减少这些查询涉及的表数量，从而针对主要情况（涉及两个或更多表）实现此目标。由于需要检查表间约束的更新也往往代价高昂，此策略通常也能改善更新性能。

回想一下，谓词中的复合键涉及跨越两个或更多角色的 UC（唯一性约束）。由于映射算法将带有复合键的谓词映射到单独的表，因此一种基本策略是减少概念模式中（相关的）复合键事实类型的数量。有两种主要情况有可能实现这一点：可统一的兼容键，以及可被功能角色替换的非功能角色。让我们依次考虑这些情况。

### 步骤 1

**步骤 1** 旨在统一兼容的复合键（参见图 14.42）。作为准备，步骤 1.1 包含两个动作。作为其第二个动作的一个例子，考虑一个包含以下事实类型的模式：`Company in State has staff of Gender {'m', 'f'} in Quantity`（公司在州拥有性别为 {'m', 'f'} 的员工，数量为 Quantity）；`Company in State has Budget`（公司在州拥有预算）。基于 `Company–State`（公司-州）的兼容键是通过吸收 `Gender`（性别）将四元事实类型特化为两个三元事实类型而形成的：`Company in State has male staff in Quantity`（公司在州拥有男性员工，数量为 Quantity）；`Company in State has female staff in Quantity`（公司在州拥有女性员工，数量为 Quantity）。

![图 14.42 优化步骤 1：统一兼容的复合键。](img/f14-42-9780443237904.jpg)

图 14.42 优化步骤 1：统一兼容的复合键。

步骤 1.2 和 1.3 确保涉及 *n* 个兼容复合键的每个模式都被单个谓词取代（*n* ≥ 2）。前几节讨论了几个示例。原始模式映射到 *n* 个表，而嵌套版本仅映射到一个表。

如果嵌套导致概念模式清晰度下降，建模者可能倾向于不进行嵌套。理想情况下，建模者可以选择是否让嵌套作为 `Rmap` 的一个不可见预处理阶段自动执行。如果显得更自然，任何嵌套对象类型都可以重新转换为共指对象类型。

**步骤 2** 检查*同时具有功能角色和非功能角色的对象类型*，并通常尝试用可以与前者分组在同一表中的功能角色来替换后者（参见图 14.43）。

作为一个例子，考虑事实类型 `Official holds Position {'president', 'secretary', 'treasury'}`（官员担任职位 {'president', 'secretary', 'treasury'}）。我们可以将其转换为三个一元事实类型：`Official is president`（官员是主席）；`Official is secretary`（官员是秘书）；`Official is treasurer`（官员是财务）。假设每个职位最多由一位官员担任，我们还需要在每个一元事实类型上添加一个角色基数约束，声明 `# ≤ 1`。

作为练习，绘制模式并执行映射。步骤 2.2 完成了减少映射表数量的优化策略。

### 优化过程的最后步骤（3、4、5）

我们现在考虑优化过程中的最后步骤（3、4、5）。与之前的步骤不同，这些步骤不会减少表的数量。*步骤 3* 如图 14.48 所示。其目的是减少自连接，称为*表宽指南*（TWG），因为它指示何时更宽的表（更多列）可能更可取。

![Fig. 14.48 Optimization step 3: the table width guideline.](img/f14-48-9780443237904.jpg)

图 14.48 优化步骤 3：表宽指南。

前面已经讨论了图中所示的模式等价性。如果对象类型 *A* 扮演功能角色，转换为二元事实类型本应已在步骤 2.1 的最后阶段发生。即使 *A* 没有功能角色，如果专门化为二元事实类型能避免聚焦查询中的自连接，这种专门化仍然可能是值得的。

作为步骤 3 的一个示例，假设我们想查看 2021–2023 三年间各学位的全日制大学学费变化情况。让我们用三元事实类型 `Degree in Year had FulltimeFee` 来建模，其前两个角色跨越唯一性约束，第一个角色上有频率约束 3，`Year` 的角色上有值约束 `{2021…2023}`，如图 14.49 所示。假设我们将其映射到关系模式 `FulltimeFee(degree, feeYear, Fee)`，并在关系层面强制执行频率约束和值约束。

![Fig. 14.49 This query requires a self-join because it compares different rows.](img/f14-49-9780443237904.jpg)

图 14.49 此查询需要自连接，因为它比较不同的行。

图 14.49 展示了该表的一个样本数据片段。设一个聚焦查询为：BS 全日制学费在三年间增加了多少？请通过检查表格自行回答该查询。

在得出答案（$500）的过程中，你比较了同一表中两行不同的值。要在关系数据库中执行此查询，需要将表与自身连接（自连接）。图 14.49 中包含了该查询的一个 SQL 版本。

通过首先应用 TWG 转换模式，可以避免此类连接。应用 PSG1 的一个变体，其中值约束应用于*角色*而非对象类型，该三元事实类型专门化为三个概念二元事实类型：`Degree had 2021- FulltimeFee`；`Degree had 2022- FulltimeFee`；`Degree had 2023- FulltimeFee`。

在这里，`Degree` 的角色是功能性的，并由等值约束链接。如果在全局模式中，学费信息对 `Degree` 是强制的，这些角色就是强制的（这意味着等值约束）。如果 `Degree` 没有其他功能角色，这三个概念二元事实类型映射到单个表：`FulltimeFee(degree, fee2021, fee2002, fee2023)`。

如果 `Degree` 有其他功能角色，优化本应在步骤 2.1 执行，额外的功能事实类型映射到同一个表。

图 14.50 展示了概念模式，并说明了更宽的表如何使查询只需比较同一行上的值即可执行，这比之前的查询简单得多。

![Fig. 14.50 The transformed schema leads to a more efficient query.](img/f14-50-9780443237904.jpg)

图 14.50 转换后的模式带来更高效的查询。

这个例子很简单明了，但现实并不总是如此简单。如果学费年份范围很大，转换产生的额外列数可能太高。例如，假设我们必须记录 1984…2023 期间的学费。专门化三元事实类型将生成 50 个二元事实类型，并导致一个包含 51 列的关系表：`FulltimeFee(degree, fee1984, …, fee2023)`。

如此大量的二元事实类型会使概念模式杂乱（尽管灵活的 CASE 工具可以设置为显示三元事实类型，并将优化隐藏在映射中）。非常宽的关系表也难以查看（大量水平滚动）和打印。出于这些原因，一旦值约束的*基数*超过一个合理的数字（例如 5），可能首选三元事实类型。

值约束的*稳定性*也很重要。在许多情况下，此类约束是已知稳定的（例如性别代码的 `{"m", "f"}`）。然而，有时值约束会随时间变化。例如，假设学费要记录从 2001 年到当前年份的所有年份，或者仅记录最近三年。二元方法要求每年更改事实类型和关系列。在这种情况下，可能首选三元方法，因为不需要结构更改（年份更改仅针对数据行，而非表结构本身）。

优化步骤 3 的措辞反映了查询效率与表显示及模式演化易用性之间的权衡。虽然可以将默认选择内置到自动优化器中，但建议与人类建模者交互，以确保最佳权衡。

列集之间的排除用“⊗”表示。同一行上值之间较弱的排除约束用“≠”表示。将属性放在同一个方括号内意味着任何限定都适用于每一个属性，并且如果其中一个为空，则另一个也为空（此约束由其限定隐含地适用于颜色属性）。

此处讨论的模式优化过程不包括关于如何映射子类型和对称 1:1 事实类型的决策，因为这些不会改变概念模式本身。然而，正如第 11 章所讨论的，这些映射选择可能对所获得的关系模式的效率产生重大影响。

回顾一下，优化过程假设目标系统是关系 DBMS，至少意味着表列中的每个条目要么是原子值，要么是空值。如果允许多值字段（如 SQL:2003 及以后版本），则可使用其他设计来避免表连接，从而实现进一步的可能优化（参见 14.7 节）。
