
防御此类输入需要真正的深度防御。这从在进入网络之前过滤流量开始。一种方法是使用 Web 防火墙（WAF），这是防火墙设计的下一步。`WAF`分析网络流量并可以过滤掉诸如 XSS 和 CSRF。

另一种可帮助防御注入的项目是数据库活动监控（DAM）。`DAM`系统的出现是因为公司面临的威胁比过去多得多。对跟踪数据库内活动的需求也日益增加。如 HIPAA 和 PCI-DSS 等法律法规增加了这种需求。你可以认为`DAM`类似于安全信息和事件管理（SIEM），只是`SIEM`系统会从多个数据源关联并分析事件，而`DAM`专门关注访问和活动。

## 应用沙箱（Application Sandboxing）

**应用沙箱**是将文件写入沙箱或临时存储区域而不是其正常位置的过程。沙箱化被用于限制代码在用户计算机上执行恶意操作的能力。如果你在沙箱中运行应用程序，它将无法编辑注册表，无法对用户硬盘上的其他文件进行任何更改。

使用沙箱的一个应用领域是带有移动代码。移动代码是从远程系统下载并在计算机本地运行的软件。许多时候，用户可能甚至不知道代码正在执行。`Java`是移动代码，它在沙箱环境中运行以提供额外的安全性。数据可以作为客户端处理或服务器端处理进行处理。服务器端处理是代码在服务器上进行处理，而在客户端处理中，代码将在客户端运行。`PHP`是服务器端处理语言的示例，而`JavaScript`在客户端处理并可以由浏览器执行。

> 虚拟机可以作为沙箱的一种类型，用于执行可疑程序或潜在恶意软件。

# 标准库

# 安全编码标准

安全编码是指以高水平的安全和质量保证构建安全软件的实践。构建安全软件要求你执行以下操作：

- 理解导致安全漏洞的常见软件缺陷
- 遵循安全编码标准和实践
- 执行深度的代码审查

许多公司面临的问题是，程序员通常不是安全专业人员，并且受不同因素驱动。很多时候，他们急于开发代码并推向市场。此外，程序员通常最关心让应用程序运行。安全编码要求程序员考虑安全专业人员的考量，在遵守规定的编码标准的同时解决为软件指定的所有安全需求，并假设有人会尝试直接、间接或通过操纵软件来破坏程序的行为。一些最佳实践包括：

- 不要依赖任何非自生成的参数。
- 避免复杂代码，并尽可能保持代码简单且短小。
- 不要添加功能。程序员应该只实现软件规范中定义的函数。
- 最小化入口点，并尽可能减少出口点。
- 验证所有输入值。输入必须具有正确的长度、范围、格式和数据类型。

> 注意：输入值的示例包括金额、交易计数以及错误检测和纠正。测试用于验证这些值的正确性的控制措施是安全编码的重要部分。

- 应尽力减少相互依赖性，以便在不需要时禁用任何进程模块或组件。
- 模块的开发应具有高内聚、低耦合。

> 内聚性是指一个模块可以在接受其他模块少量输入的情况下执行单一任务。耦合是衡量模块之间互连程度的指标。

一旦编写了安全代码，就需要进行测试。测试分为以下几类：

- **单元测试**检查单个程序或模块
- **接口测试**检查硬件或软件，以评估数据如何从一个实体传递到另一个实体
- **系统测试**一系列可能包含恢复和安全测试的测试
- **最终验收测试**通常在实施阶段团队对所有内容满意后进行

# 应用程序漏洞

应用程序漏洞是计算机犯罪分子用于攻击应用程序的广泛攻击向量。攻击者有许多方法可以针对应用程序。无论采取何种路径，一旦成功，攻击者就可以对你的业务或组织造成伤害。造成的损害从轻微到导致公司破产不等。取决于应用程序的设计，应用程序漏洞可能很容易发现，也可能极其困难。由于需要考虑的因素很多，我们需要起点。因此，`OWASP`列出了 2013 年十大应用程序安全风险如下：

- 1 注入
- 2 身份验证和会话管理破解
- 3 XSS（跨站脚本）
- 4 不安全的直接对象请求
- 5 安全配置错误
- 6 敏感数据泄露
- 7 缺失功能级访问控制
- 8 CSRF（跨站请求伪造）
- 9 使用已知漏洞的组件
- 0 未验证的重定向和转发

# 权限提升

权限提升是指攻击者将其在系统的权限从低级用户提升到管理员或 root 的过程。当代码运行的权限高于执行用户的权限时，就会发生权限提升。权限提升技术包括：

- **垂直权限提升** 低权限用户或应用程序访问留给高权限用户或应用程序的功能或内容。
- **水平权限提升** 普通用户访问留给另一个普通用户的功能或内容。

和操作系统通过多种方式防止此类攻击。其中一种是构建保护环。保护环模型为操作系统提供了执行代码或限制其访问的不同级别。它比仅在用户模式和特权模式下运行系统具有更高的细粒度。越靠近模型的外部边界，权限越低；越靠近内部边界，权限越高。该模型的示例可以在[图 5.3]中看到。

## 敏感数据的存储不当

敏感数据的存储不当是一个大问题。敏感数据并不总是受到适当控制措施或加密解决方案的保护。在软件开发生命周期（SDLC）过程的需求阶段，必须定义敏感数据的安全控制措施。此时，必须提出以下问题：

- 数据是否需要加密？
- 是否正在存储诸如信用卡号、健康记录或其他敏感数据等个人信息？
- 是否使用了强加密标准？

如果你对这些问题中的任何一个问题的回答是“是”，则应该实施控制措施来保护数据。认证安全专业人员（CASP）不仅必须关注敏感数据的存储，还必须关注如何访问数据。其中一个问题是允许发生直接对象引用（Direct Object Reference）。当开发者允许以参数的形式直接访问文件、目录或 URL 等对象时，就会发生直接对象引用。例如，假设 URL 为`c=265`。如果攻击者可以操纵对象引用（在此例中为数字 265），在没有实施适当访问检查的情况下，他们可能会将其改为 275 并在未经授权的情况下访问其他账户。这种攻击曾在 2000 年发生在一个加拿大的网站上。你可以在 www.abc.net.au/7.30/stories/s146760.htm 了解更多信息。

CASP 还必须关注数据在生命周期结束时发生的情况。这就是数据遗留（Data Remence）成为大关注的问题。数据遗留是指留在存储介质上的任何残留数据。根据信息的敏感性，擦除驱动器可能足够，或者你可能需要监督介质的销毁。有提供安全硬件销毁的服务，它们在处理剩余碎片之前会进行粉碎。在使用云服务时，数据遗留也是一个主要问题。

![](img/7868547987f5920cfe632b85047c64af_321_0.png)

> 注意：根据 OWASP，该领域最常见的缺陷是对敏感数据不使用加密。

## Cookie 的存储与传输

Cookie 被用于维护会话状态。之所以需要 Cookie，是因为 HTTP 是无状态协议。它们的原始目的是存储所需的信息。假设 Mike 计划为出差在俄克拉荷马城市预订酒店。当 Mike 在酒店网站的各个页面之间移动时，Cookie 被用于维护在之前页面上做的选择。并不是所有网站在传输或存储敏感信息时都能妥善保护 Cookie。如果攻击者可以访问传输中或存储中的 Cookie，那么攻击者极有可能执行以下操作：

- 修改 Cookie 内容。
- 注入恶意内容。
- 重写会话数据。

你可能认为 Cookie 设计用于安全地存储敏感信息，但情况并非总是如此。配合“记住我”功能使用的 Cookie 可能会包含密码或用户名。这是一个例子：

```
Set-Cookie: UID=bWlrZTptaW1c3Bhc3N3b3JkDQoNCg; expires=Fri, 16-May-2011
```

## 弱加密并不比完全不加密好！

我花了一些时间审查了一个客户的路由器配置文件，注意到他们继续使用 Cisco 类型 7 密码。这是一种弱的身份验证形式，可以被轻易破解。根据 Cisco 的说法，类型 7 密码旨在仅提供基础水平的保护。

由于加密算法较弱，Cisco 的立场是客户应该将配置文件视为敏感信息。问题在于，攻击者可以通过多种不同手段获取这些配置文件，例如嗅探、窥视或访问简单文件传输协议（TFTP）服务器。获取了配置文件的的攻击者将看到如下的内容：

```
enable password 7 120G0C161D595C5472825213F3C2E1402
```

拥有编码后的密码后，攻击者可以使用任何工具来快速解码这些混淆的密码。可以解码这些密码的知名工具包括 Cain & Abel 和 Cisco 密码解码器。在 Web 上快速搜索就能得到几十条结果。（注：OCR 文本在此处突然结束或过渡到其他章节）。

浏览可能会引入安全漏洞。扩展程序的一些示例包括：

- TinyURL 生成器，用于创建短网址（URL）
- Print Pages to PDF，这是一个 PDF 打印机。
- Heartbleed Notifier，用于告知您网站是否容易受到 Heartbleed SSL 漏洞的影响。

# Ajax

Ajax 是一种用于开发 Web 程序的编程语言，它结合了 XHTML、CSS、基于标准的呈现方式以及 JavaScript。Ajax 允许网页上的内容在用户执行操作时立即更新。像其他编程语言一样，Ajax 可能会存在安全问题，主要是极易受到注入攻击。一种设计方法是使用 Ajax 开发应用程序，使其仅对按预期发送的请求做出响应。所有格式不正确的请求都应该被静地忽略，从而减少安全问题的可能性。

# JavaScript/Applets

JavaScript 是一种面向对象的脚本语言。JavaScript 是 ECMAScript 语言的实现，广泛应用于网页和应用程序中。它对于与网页文档对象模型（DOM）交互的函数非常有用。

Java applet 与 JavaScript 有某种关联。Java applet 是以字节码形式传递给用户的短代码段。这些少量的代码（通常只有一或两个字节）允许程序员传递特定的特定指令以便执行。它们的优势是速度快，而且 applet 可以在许多不同的平台上执行。当支持 Java 的浏览器遇到 applet 时，它会获取字节码并传递给浏览器，由浏览器执行代码。

从安全角度来看，JavaScript 是一个令人关注的问题，因为它可以在用户的浏览器中本地响应。尽管这也意味着 JavaScript 容易受到 XSS 和 CSRF 攻击。XSS 可能会是危险的。考虑一种情况：当受害者连接到银行网站时，攻击者可以发起 XSS 攻击。这可能允许攻击者以受害者的权限访问银行应用程序。结果可能是机密信息的泄露，或者在未经受害者授权的情况下转移大额资金。这会导致受害者的浏览器执行了用户无意执行的操作（例如在银行网站上转账）。

> 商业网站并非唯一容易受到 CSRF 攻击的网站。安全人员在某些 Linksys 家庭路由器中发现了类似的漏洞。[The Register](http://www.theregister.co.uk/2009/06/01/linksys_router_remote_takeover/)

> CASP 考试候选人应该注意，JavaScript 既容易受到 XSS 攻击，也容易受到 CSRF 攻击。

# HTML5

HTML5 是 HTML 编程语言的第五修订版本。HTML5 设计为向后兼容。它支持新功能、新输入类型以及表单验证。任何新事物的问题在于，攻击者会开始寻找可以被利用的漏洞。在 2012 年的黑帽大会上，人们发现了 HTML5 的问题；这些问题包括 CSRF、点击劫持、XSS 和攻击 DOM 变量。你可以在 [Security Week](https://www.securityweek.com/top-10-security-threats-html5-black-hat) 阅读更多信息。

# SOAP

简单对象访问协议（SOAP）旨在在计算机网络中交换基于 XML 的信息。SOAP 提供了一种基本的消息格式。消息是 SOAP 节点之间的单向消息。消息由三部分组成：封包、一组过程调用和响应。SOAP 的优势是它构建在开放技术之上，可以在各种平台上运行。然而，由于 SOAP 可以通过 HTML 传递消息，存在攻击者可能拦截这些消息并更改或偏移内容的可能性。

# 缓冲区溢出

溢溢发生在程序或应用程序尝试在变量中存储超过其能容纳的数据时。这可能导致内存损坏和安全漏洞。缓冲区是一个临时存储区域。当程序超过缓冲区容量时，它可能会覆盖相邻的内存。这允许攻击者更改程序的执行流。例如，在 C 语言中，你使用`malloc`函数分配内存，可能忘记调用`free`来释放内存。如果这个过程重复进行，可能会丢失大量内存。缓冲区溢出在没有内置内存管理的语言中很常见。一个很好的例子如图 5.4 所示。

### 图 5.4 缓冲区溢出

缓冲区溢出会导致各种安全漏洞。无论发生什么，溢出都允许攻击者运行其代码。试图发起缓冲区溢出的攻击者通常遵循以下步骤：

- 找到缓冲区的存在和位置。
- 向其写入超过其能处理的数据。
- 覆盖函数的返回地址。
- 将执行流更改为攻击者的代码。

# 内存泄漏
