## 监控

监控机器学习（ML）模型是机器学习流水线的最后一步，它在一定程度上可以实现自动化，也可以在一段时间后周期性地进行手动检查。由于流程的变化，几乎所有模型随着推移而衰减。在这些变化导致模型产生错误推理之前，更新模型变得至关重要。为了监控，我们可以按照特定的频率使用实际数据检查模型性能。例如，在训练一个二分类问题时，我们确定了一个模型并将其部署到环境中，其 `AUC` 为 `0.75`，`Accuracy` 为百分之九十。现在，一旦模型进入生产环境，根据新数据评分的频率，我们可以回溯一个或两个时间周期，检查模型在新数据集上的性能，并了解其是否在接受范围内。这在任何情况下都是不可能的，但对于每个迁移到生产环境的模型，都应该配备此类机制。

挑战在于，我们根据输出做出决策，而这些决策会对现实产生影响；例如，为了避免潜在的客户流失，我们向他们发送了一些优惠，这将使客户留下。模型本会预测这是一个流失案例，但由于所采取的行动，我们在现实中永远不会看到这种情况。对模型性能的任何监控也应考虑这些因素。

虽然前面的示例是监控模型的一种方法，但它本质上更具反应性，因此我们至少会比现实晚一个周期才发现任何性能衰减。另一种主动监控的方法是通过进入的新数据。可以将这些数据与训练模型时的数据进行比较，以查看它们是否来自相同的分布。有多种统计测试可以实现此目标，取决于我们处理的变量类型。如果变量是连续的，我们可以采用 `KS` 非参数检验；对于分类变量，我们可以采用 `Chi-Square`（独立性检验）；对于有序变量，可以使用 `Spearman rank correlation`。我们将在参考共享的代码中展示一个使用 `Evidently` 的示例。`Evidently` 生成的输出可以自动化到自定义的仪表板或 HTML 中，也可以直接分析 Jupyter notebook 报告。我们将在 `Git` 仓库中提供 Jupyter notebook 作为示例。

## 结论

在本章中，我们详细介绍了创建机器学习流水线以及将 MLOps 作为一种实践进行实施的步骤。在此过程中，我们分享了代码并利用开源工具来实现这些过程。需要注意的是，工具可能会随着时间的推移而变化和演变，但过程将保持不变。我们使用的大多数工具（如 `Feast` 或 `KServe`）仍处于测试阶段，或者几乎每月都会出一个新版本。未来可能会更好的开源工具，或者你可以根据需要获取工具的付费订阅；然而，MLOps 的过程将保持不变。如果带宽和资源允许，你可以根据需求开发定制的工具集。

广而言之，你想捕获所有能够复现并帮助你解释模型性能任何衰减或偏离的制品。你还希望尽快捕获这些性能衰减，以避免任何财务或业务价值的损失。这就是我们在书中想要涵盖的所有。作为数据科学家或机器学习从业人员，最重要的是你不需要了解所有的细节，但你应该理解何时向谁寻求帮助，以及为了实施 MLOps 实践需要完成什么。此外，只有当机器学习生命中的之前的步骤显示前景时，许多步骤才会执行。
