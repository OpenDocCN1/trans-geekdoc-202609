
队伍通过语义代码标识（例如，`MR-A`、`BS-B`、`WS-A` 分别表示男子橄榄球 A 队、男子足球 B 队和女子足球 A 队），但这些代码的含义并未在信息系统中显式存储。系统记录了每支队伍获得的总分。每支队伍初始分数为零，即使它尚无成员。

`Team` 上的强制角色点表示每支队伍都有总分（可能为 0）。`Member` 上的其他强制角色表示每位成员都记录了出生日期和入会日期。圆圈强制角色点连接到两个角色：这是一个 **包含性或** (**析取强制角色**) **约束**，表明这两个角色的析取对于 `Member` 是强制的。即每位成员 *要么* 指导 *要么* 效力 (*或两者兼任*)。

例如，Adams 仅是球员，Downes 仅是教练，Collins 既是球员又是教练。一支队伍的教练甚至可以为同一支队伍效力（尽管种群未说明这一点）。`Team` 的“is coached by”和“includes”角色上缺乏包含性或约束，表明在不知道其教练或任何球员的情况下也可以了解一支队伍。

如果图 5.10 包含 `Date` 在全局模式中扮演的所有角色，那么 `Date` 角色的析取也是强制的（每个日期都是出生日期或入会日期）。这可以通过将这些角色链接到包含性或点来显式显示；然而，该约束是隐含理解的，如果我们为 `Date` 添加另一种事实类型，显式约束将需要更改，因此最好保持图表原样。

这个 `Date` 示例说明了前面提到的单一强制角色规则的以下推广：*默认情况下，基元对象类型扮演的角色的析取是强制的*。如果对象类型是 *实体类型，其事实角色的析取默认也是强制的*（此默认值可通过声明对象类型为独立类型来覆盖；见下一章）。

除了突出显示需要强制执行析取强制角色的重要情况（例如教练-球员析取）并简化模式演进外，此规则还便于绘制模式。例如，`Date` 和 `MoneyAmount` 等对象类型通常有多个析取强制角色，显式显示此约束会很乱（如果对象类型出现在单独的模式页面上甚至不可能）。

为避免混淆，如果被约束的对象类型是子类型（见第 6 章），则应 *显式* 显示强制角色约束（简单或析取）。

对于隐含的（可能是析取的）强制角色约束，如果添加更多角色到对象类型时该约束仍适用（这些额外角色被排除在约束之外），则可以 *显式标记该约束*。对于 `Date` 等对象类型，这种情况几乎不会发生。

包含性或（析取强制角色）约束表示对象类型种群中的每个实例必须至少扮演受约束角色之一（也可能全部扮演）。

与顶层实体类型不同，值类型之间可能相互重叠。例如，此处 `Surname` 和 `CityName` 的取值集发生重叠，因为两者都包含字符串“Brisbane”。

假设表 5.3 中的数据和一种适当的查询语言，请考虑用户与 CIP 之间的以下对话。

|  |  |
| --- | --- |
| `User:` | `Which person lives in a city with the same name as his/her surname?` |
| `CIP:` | `Darwin.` |
| `User:` | `Which person is a city?` |
| `CIP:` | `None: Entity types Person and City are mutually exclusive.` |

比较 `Person` 和 `City` 的名称是有意义的，因为它们都是字符串。但比较人和城市则讲不通——它们是完全不同类型的实体。虽然 IQ、质量和长度的值类型都是数值型的，但质量和长度有不同的单位，而 IQ 是无量纲的（即没有单位）。概念上，两个数值引用的实体只有在具有相同单位（或都没有单位）时才能进行比较或相加。因此，以下查询讲不通：

```
List persons whose mass equals their IQ.
List persons whose height is more than twice their mass.
List height + mass for each person.
```

当然，数字本身总是可以比较的。此外，身高和胸围都基于相同的域和单位，所以它们是兼容的。因此，以下查询是可以接受的。

```
List persons whose mass number equals their IQ number.
List persons whose height number is more than twice their mass number.
List height + chest size for each person.
```

大多数当前的数据库系统很少或根本不支持实体与其值之间的区别。查询中指定的操作被解释为直接应用于值。例如，假设表 5.3 的数据作为表 `Athlete`（person, city, height, chest, mass, IQ）存储在关系数据库中，以下结构化查询语言（SQL）查询完全合法：

```
select person from Athlete
where person = city
and mass = iq and chest + mass > height
```

对于表 5.3 中的数据，该查询返回“Darwin”，尽管从字面上看该查询是胡扯。查询中评估的比较是在值之间进行的，而非实体之间。我们可以通过更好的列名选择来澄清这一点（例如，使用“Surname”和“Cityname”代替“Person”和“City”）。

值是具有预定义解释的常量，因此不需要显式引用方案。例如，“Brisbane”指代其本身（即字符串“Brisbane”），当不加引号书写时，数字“77”表示数字 77（假设采用阿拉伯十进制记数法）。有人可能会声称，不加引号书写的常量（如“Brisbane”）足以标识单个实体。然而，总是需要某些上下文（至少是隐式的）。即使在表 5.3 中，“Brisbane”也被用来同时指代一个人和一座城市。

在本书前面，我们看到实体是通过确定性描述来引用的（例如，“名为‘Brisbane’的那个 City”）。在引用类型的上下文中，如果一个值仅与该类型的一个实体相关联，则可以宽松地说该值是该实体的标识符。

如果确定性描述中仅使用一个值，则我们有一个简单的 1:1 引用方案。然而，有时可能需要两个或更多值。在这种情况下，我们有一个*复合引用方案*。作为一个例子，考虑表 5.4 中计算机文件是如何被识别的。在给定文件夹中，文件可以通过其本地文件名来识别，例如“flag.vsd”。但当涉及许多文件夹时，我们需要将文件夹名称与本地文件名结合起来，才能知道我们在谈论哪个文件。
