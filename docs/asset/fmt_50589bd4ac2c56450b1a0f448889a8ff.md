# 第3章 使用 Zachman 框架实现企业安全

本章是对企业架构的独立介绍，从“什么是架构？为什么我们需要它？”这一基础问题开始。接下来，本章介绍了 `Zachman Framework`（Zachman 框架），这是企业架构领域最著名的概念标准。本章以一个用于解决企业架构问题的模式目录作为结束。

### 什么是架构？为什么我们需要它？

几千年来，人类一直利用架构来创建和重复使用建筑。架构是建筑的核心描述。架构描述了建筑的结构以及建筑的所有系统。

当架构反映了优化且有效的设计时，你可以放心地对建筑进行更改。通过了解架构，你知道是否可以拆掉墙、钻孔或安装一扇新窗，而不会导致灾难性后果，例如屋顶塌陷、水管破裂或电线损坏。

如果你不知道架构，或者架构存在缺陷或无效，那么对建筑进行更改将非常困难。如果你通过试错来进行更改，可能会拆掉一面承重墙，导致建筑部分坍塌。

另一种替代方案是对建筑进行逆向工程并重建架构。但，逆向工程既耗时又昂贵。如果你的原始架构设计优化，并保持更新，以便在下次需要更改建筑时可用，情况会好得多。

系统架构也是如此。它代表了计算机系统的设计元素。就像墙支撑建筑的屋顶一样，这些元素也应该支持系统的安全需求。理想情况下，安全性应该从系统设计之初就被设计并构建到架构中。

### 企业是复杂且不断变化的

考虑位于华盛顿特区的美国国会山大厦。这是一个极其复杂的企业——美国联邦政府——的一座巨大立法建筑。考虑这栋建筑以及所有其他联邦建筑的复杂性。然后考虑内部的家具，它们是移动的；设备，如复印机和电话；最后是随着系统升级、迁移和更新而实时变化的计算机。

最后是人，他们拥有错综复杂且不断波动的组织结构、人际关系、角色、职责、知识、技能和能力。这些人不仅包括政治家、政府员工和承包商，还包括与联邦政府交互的外部人员和组织，包括超过 3 亿名公民。

联邦政府是一个在激进的立法截止日期和其他环境力量驱动下经历巨大变革的组织。因为政府需要变革，他们就需要企业架构。每个机构都有几十位架构师维护他们的企业架构，还有几十位架构师设计他们的解决方案架构（系统架构）。他们面临着艰巨的任务，但为了满足政府变革的需求，任务必须完成。

美国国会山是极其复杂的动态企业中的一个复杂建筑。为了以有意义的方式表示（或建模）这种复杂性，你需要一个企业架构框架来指导你的分析。`Zachman Framework` 是一种广泛使用的事实标准，用于分析和表示企业架构。

### 用于企业架构的 Zachman 框架

`Zachman Framework` 由 John A. Zachman 发明，是一种用于描述企业的事实工具。由于企业本质上是复杂的，你需要一个强大的框架来描述它们——一个能够分而治之复杂性的框架。

`Zachman Framework`（见图 3-1）将复杂性切分为行和列。列是你针对任何主题可以提出的六个基本问题。这些提问词包括：什么（What）？怎么做（How）？在哪里（Where）？谁（Who）？什么时候（When）？为什么（Why）？这些是记者在写报纸故事时提出的相同问题。当记者回答了这六个问题后，他们就可以声称拥有了一个完整的故事。

`Zachman Framework` 进一步将复杂性分为行。行代表角色的总体概述。每个复杂企业的层级都有：执行官、业务管理、架构师、技术人员和用户。这些角色可以提出相同的问题；因此每行六个单元格。

`Zachman Framework` 中的每个行列交叉点是要填充模型和规范的单元格，这些是对企业的表示。每个人都有自己的规范。填充后的行从行的视角表示了企业架构。

### 原始模型与复合模型

原始模型是仅包含单列实体的模型。第一行包含每列的原始列表。第二行具有从这些列表构建的层级（参见图 3-1）。

在我们的模型中保持列分离有许多优势。它使得框架在概念上很简单；基于 `Zachman Framework` 的模型也可以很简单；因为列是独立的，你可以并行填充它们。原始模型相对稳定且变化缓慢。

例如，考虑图 3-1 中第一列的信息模型；我们的模型可以包含数据实体列表（第一行）、数据层级（第二行）、概念模式（第三行）、逻辑模式（第四行）、物理模式（第五行）以及记录实例（第六行）。显然，第六行在实施过程中不断变化，但其他单元格将保持相对稳定。在大多数企业中，你多多久更改一次需要软件重构的物理模式呢？可能并不频繁。

复合模型结合了多个列的原始元素。一个示例是显示原始元素之间关系的矩阵，例如处理数据。通过该矩阵你可以回答：“哪些过程使用了哪些数据？”复合模型对于评估列之间的影响（例如哪些数据被哪些过程处理）以及描述实现是必要的。

### Zachman 框架如何帮助网络安全？

在 `NIST` 特别出版物（`SP`）大量的页数中，有一些实用的想法。`NIST SP 800-39` 建议建立组织范围风险管理活动。该活动负责企业的风险执行官（职能）。

#### 第 3 章 - 使用 Zachman 框架进行企业安全

风险执行官是企业投资决策的关键利益相关者，特别是信息技术（`IT`）投资。风险执行官不属于 `IT` 部门，而是从业务管理的角度提供风险视角（第 2 行）。`Zachman Framework` 使风险执行官能够在企业范围内具备可见性，以便在做出明智决策时管理企业的安全风险。

风险执行官确保从启动开始，每一项导致 `IT` 项目和 `IT` 系统的决策从第一天起就会考虑安全风险。安全需求（即控制措施）将会在前期阶段被纳入系统设计，就像所有其他需求一样。

实际上，系统将在具有可见安全需求的情况下进行开发。这与当今的常态业务相比发生了巨大的变化。实践中发生（至少在大多数组织中）的是，只有在安全认证测试人员到达时才会考虑安全（参考第 2 章中的“没有时间搞安全”反模式）。人们手忙脚乱地为开发者发放自己的账户以取代共享的管理员账户，并采取其他最后时刻临时措施来管理组织的安全态势。由于安全状况极其糟糕，认证测试人员往往被抽调帮助开发者重新设计他们的系统以确保安全。不幸的是，这种情况经常发生。

`Zachman Framework` 可以改变这一切。每个组织都应该有一个企业架构（`EA`），这是变革的蓝图。风险执行官利用 `EA` 来评估风险、制定安全需求，并对实施情况进行持续监控。

风险执行官采取的行动之一是在每个系统的架构中建立一个“审计员”用户角色。审计员是一个只读用户角色，监察长（或相当组织）的审计人员可以使用它来发现浪费、欺诈和滥用。在商业世界，这些审计人员正在通过信息和相关技术控制目标（`COBIT`）等框架实施《萨班斯-奥克斯利法案》。同样，安全审计师可以使用审计员角色来确保对系统的持续监控以及足够的机密性、完整性和可用性。

## 每个人都有自己的规范

`Zachman Framework` 是企业模型的“周期表”。它是一种科学抽象，可以帮助你管理现实世界。`Zachman Framework` 的真正价值在于意识到每个人都有自己的模型。如果模型没有满足你的需求，或者你不知道如何组织它们，你可以使用 `Zachman Framework` 对其进行重新组织。模型应该从你的视角回答所有重要问题。

## 第一部分 - 网络安全概念

你可以从任何视角使用 `Zachman Framework` 作为基准框架，对事物和概念进行盘点；对它们进行组织和定义；并将它们相互关联，以评估影响、寻找共同点并理解结构。

如果你没有更好的方法来描述和理解你的世界，`Zachman Framework` 是你记录它的一个富有成果的起点，无论你处于哪个层级，这都是架构。在理解了你的架构后，你就处于了可以改变它的可行位置。

想象你是一个政府 `IT` 安全专业人员，你有一个对你非常有效的框架。你可能有一份系统安全计划（`System Security Plan`）、行动与里程碑计划（`Plan of Actions and Milestones`）、认证测试报告（`Certification Test Report`）和认证信（`Accreditation Letter`）。这些是你需要从你的视角回答所有重要问题的项目。这意味着你拥有了一个记录的架构——一个变革的蓝图。

## 宝矿在第 2 行

`Zachman Framework` 的第 1 行包含了企业事物的详尽列表，这些事物本身没有用，但当它们被转换为第 2 行中的层级结构时，你就可以视觉化你的企业并导航到共性集群。你的企业管理的每种数据、企业中的每个角色以及每个系统。看到此类信息有助于业务管理（即第 2 行视角）为执行决策提供明智的建议。因为第 2 行模型帮助人们视觉化企业，你现在有了一个基于事实进行决策的新基础。你第一次看到了企业的游戏板，并可以根据新发现的知识做出敏捷决策。

## 第 3 行的框架

`Zachman Framework` 的第 3 行是架构师的视角，你必须问：“我们知道如何描述我们的企业及其系统吗？”如果你无法回答这个问题，你就可以继续通过 `Zachman Framework` 填充第 3 行的单元格。关联不同列的实体的矩阵就变成了你的视图对应关系。

然而，许多组织对第 3 行模型的选择有自己的主见。美国国防部选择国防部架构框架（`DoDAF`）。英国选择国防部架构框架（`MODAF`）。欧盟使用欧洲架构框架（`EAF`）。北约使用北约架构框架（`NAF`）。许多商业组织使用开放体系架构框架（`TOGAF`）或部门架构方法（`DADM`）。

## 架构问题解决模式

自发布二十年以来，人们一直在广泛应用 `Zachman Framework`。关键技术如下：

- **业务问题分析**：从领域专家（`SMEs`）那里收集知识。选择一列并检查每个文档。记录你发现的内容、定义它的企业文本以及所在的文档和页码。完成对所有疑问的文档挖掘将填充第 1 行。

## 企业工作坊

- **又名：** 大群体共识形成会议、评审会议
- **问题解决类型：** 信息共享、收敛性思维
- **流程角色：** 客户负责人（理想情况下）或引导者
- **内容角色：** 客户评审团队

- **时长范围：** 1.5 小时到 6.5 小时

客户评审团队是一个比客户负责人更大的群体，需要他们的共识才能继续实施问题的解决方案。此工作坊的目的是通过征求解决方案的意见来共享信息并建立共识。
