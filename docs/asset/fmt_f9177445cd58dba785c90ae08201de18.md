`Check` 的参数是一个 `Var` 集合，它累积表达式中找到的变量名集合。这些变量必须都存在于环境中，求值才能成功。从逻辑上讲，这个集合是调用 `Check` 的*结果*，但由于该方法是递归的，将一个作为参数传递的集合传入并由 `Check` 填充会更方便。客户端必须在初始调用时提供一个空集合。

在第 3.2 节中，我们绘制了一个在编译时固定的函数 `f(x,y)`。现在我们可以解析、检查并求值字符串中的表达式，因此可以构建一个 Web 应用程序，它在运行时从客户端接收一个表达式并绘制该函数的曲面。我们可以使用 `vars` 集合来检查该表达式是否仅为两个变量 `x` 和 `y` 的函数——实际上是三个，因为我们将把半径 `r` 作为一个便利变量提供。并且我们将使用 `Check` 方法在求值开始前拒绝格式错误的表达式，这样我们就不必在随后的 40,000 次函数求值（100×100 个单元格，每个单元格有四个角）中重复这些检查。

`parseAndCheck` 函数结合了这些解析和检查步骤：

点击此处查看代码图像

gopl.io/ch7/surface

```
import "gopl.io/ch7/eval"

func parseAndCheck(s string) (eval.Expr, error) {
    if s == "" {
        return nil, fmt.Errorf("empty expression")
    }
    expr, err := eval.Parse(s)
    if err != nil {
        return nil, err
    }
    vars := make(map[eval.Var]bool)
    if err := expr.Check(vars); err != nil {
        return nil, err
    }
    for v := range vars {
        if v != "x" && v != "y" && v != "r" {
            return nil, fmt.Errorf("undefined variable: %s", v)
        }
    }
    return expr, nil
}
```

要使其成为一个 Web 应用程序，我们只需要下面的 `plot` 函数，它具有熟悉的 `http.HandlerFunc` 签名：

## 7.10 类型断言

*类型断言* 是一种应用于接口值的操作。在语法上，它看起来像 `x.(T)`，其中 `x` 是一个接口类型的表达式，`T` 是一个类型，称为“断言”类型。类型断言检查其操作数的动态类型是否与断言类型匹配。

有两种可能性。首先，如果断言类型 `T` 是一个具体类型，则类型断言检查 `x` 的动态类型是否*等同于* `T`。如果此检查成功，类型断言的结果是 `x` 的动态值，其类型当然是 `T`。换句话说，对具体类型的类型断言从其操作数中提取具体值。如果检查失败，则该操作会引发 panic。例如：

点击此处查看代码图像

```
var w io.Writer
w = os.Stdout
f := w.(*os.File)      // success: f == os.Stdout
c := w.(*bytes.Buffer) // panic: interface holds *os.File, not *bytes.Buffer
```

其次，如果断言类型 `T` 是一个接口类型，则类型断言检查 `x` 的动态类型是否*满足* `T`。如果此检查成功，动态值不会被提取；结果仍然是一个具有相同类型和值组件的接口值，但结果具有接口类型 `T`。换句话说，对接口类型的类型断言改变了表达式的类型，使一组不同的（通常更大的）方法变得可访问，但它保留了接口值内部的动态类型和值组件。

在下面的第一个类型断言之后，`w` 和 `rw` 都持有 `os.Stdout`，因此它们都具有动态类型 `*os.File`，但 `w` 作为一个 `io.Writer` 仅暴露文件的 `Write` 方法，而 `rw` 也暴露其 `Read` 方法。

点击此处查看代码图像

```
var w io.Writer
w = os.Stdout
rw := w.(io.ReadWriter) // success: *os.File has both Read and Write

w = new(ByteCounter)
rw = w.(io.ReadWriter) // panic: *ByteCounter has no Read method
```

无论断言什么类型，如果操作数是一个 nil 接口值，类型断言就会失败。对限制性较弱的接口类型（方法较少的类型）进行类型断言很少见，因为它的行为就像赋值一样，除了在 nil 的情况下。

点击此处查看代码图像

```
w = rw             // io.ReadWriter is assignable to io.Writer
w = rw.(io.Writer) // fails only if rw == nil
```

我们通常不确定接口值的动态类型，并且我们想测试它是否为某个特定类型。如果类型断言出现在期望两个结果的赋值中，例如以下声明，则该操作在失败时不会 panic，而是返回一个额外的第二个结果，一个表示成功的布尔值：

点击此处查看代码图像

```
var w io.Writer = os.Stdout
f, ok := w.(*os.File)      // success:  ok, f == os.Stdout
b, ok := w.(*bytes.Buffer) // failure: !ok, b == nil
```

第二个结果通常赋值给一个名为 `ok` 的变量。如果操作失败，`ok` 为 false，第一个结果等于断言类型的零值，在本例中为 nil `*bytes.Buffer`。

`ok` 结果通常立即用于决定下一步做什么。`if` 语句的扩展形式使这非常紧凑：

```
if f, ok := w.(*os.File); ok {
    // ...use f...
}
```

当类型断言的操作数是一个变量时，你有时会看到重用原始名称来命名新的局部变量，从而遮蔽原来的变量，如下所示：

```
if w, ok := w.(*os.File); ok {
    // ...use w...
}
```

## 考虑 `os` 包中文件操作返回的错误集合

I/O 可能因各种原因失败，但通常必须区别处理三种失败：文件已存在（针对创建操作）、文件未找到（针对读取操作）和权限被拒绝。`os` 包提供了三个辅助函数，用于对给定 `error` 值指示的失败进行分类：

点击此处查看代码图片

```go
package os

func IsExist(err error) bool
func IsNotExist(err error) bool
func IsPermission(err error) bool
```

一个简单的实现可能会检查错误消息是否包含特定子串：

点击此处查看代码图片

```go
func IsNotExist(err error) bool {
    // NOTE: not robust!
    return strings.Contains(err.Error(), "file does not exist")
}
```

但由于处理 I/O 错误的逻辑可能因平台而异，这种方法不够健壮，同一种失败可能会用各种不同的错误消息报告。检查错误消息的子串在测试期间可能有用，以确保函数按预期方式失败，但不适用于生产代码。

一种更可靠的方法是使用专用类型表示结构化错误值。`os` 包定义了一个名为 `PathError` 的类型，用于描述涉及文件路径操作（如 `Open` 或 `Delete`）的失败，以及一个名为 `LinkError` 的变体，用于描述涉及两个文件路径的操作（如 `Symlink` 和 `Rename`）的失败。以下是 `os.PathError`：

点击此处查看代码图片

```go
package os

// PathError records an error and the operation and file path that caused it.
type PathError struct {
    Op   string
    Path string
    Err  error
}

func (e *PathError) Error() string {
    return e.Op + " " + e.Path + ": " + e.Err.Error()
}
```

大多数客户端不关心 `PathError`，而是通过调用其 `Error` 方法以统一方式处理所有错误。虽然 `PathError` 的 `Error` 方法通过简单拼接字段来形成消息，但 `PathError` 的结构保留了错误的底层组件。需要区分不同失败类型的客户端可以使用类型断言来检测错误的具体类型；具体类型提供的细节比简单字符串更多。

点击此处查看代码图片

```go
_, err := os.Open("/no/such/file")
fmt.Println(err) // "open /no/such/file: No such file or directory"
fmt.Printf("%#v\n", err)
// Output:
// &os.PathError{Op:"open", Path:"/no/such/file", Err:0x2}
```

这正是这三个辅助函数的工作原理。例如，下面展示的 `IsNotExist` 报告错误是否等于 `syscall.ENOENT`（参见 §7.8）或特定错误 `os.ErrNotExist`（参见 §5.4.2 中的 `io.EOF`），或者是一个其底层错误为上述两者之一的 `*PathError`。

点击此处查看代码图片

```go
import (
    "errors"
    "syscall"
)

var ErrNotExist = errors.New("file does not exist")

// IsNotExist returns a boolean indicating whether the error is known to
// report that a file or directory does not exist. It is satisfied by
// ErrNotExist as well as some syscall errors.
func IsNotExist(err error) bool {
    if pe, ok := err.(*PathError); ok {
        err = pe.Err
    }
    return err == syscall.ENOENT || err == ErrNotExist
}
```

实际效果如下：

点击此处查看代码图片

```go
_, err := os.Open("/no/such/file")
fmt.Println(os.IsNotExist(err)) // "true"
```

当然，如果错误消息被组合成更大的字符串（例如通过调用 `fmt.Errorf`），`PathError` 的结构就会丢失。错误判别通常必须在失败操作后立即进行，在错误传播给调用者之前。

## 7.12 使用接口类型断言查询行为

下面的逻辑类似于 `net/http` Web 服务器中负责写入 HTTP 头字段（如 `"Content-type: text/html"`）的部分。`io.Writer` `w` 代表 HTTP 响应；写入其中的字节最终会发送到某人的 Web 浏览器。

点击此处查看代码图片

```go
func writeHeader(w io.Writer, contentType string) error {
    if _, err := w.Write([]byte("Content-Type: ")); err != nil {
        return err
    }
    if _, err := w.Write([]byte(contentType)); err != nil {
        return err
    }
    // ...
}
```

因为 `Write` 方法需要字节切片，而我们想写入的是字符串，所以需要 `[]byte(...)` 转换。这种转换会分配内存并进行复制，但复制品几乎在转换后立即被丢弃。假设这是 Web 服务器的核心部分，且性能分析显示这种内存分配拖慢了速度。我们能否避免在此处分配内存？

`io.Writer` 接口仅告诉我们关于 `w` 所持有的具体类型的一个事实：可以向其写入字节。如果我们查看 `net/http` 包的内部实现，会发现 `w` 在此程序中持有的动态类型还有一个 `WriteString` 方法，允许高效地写入字符串，避免了分配临时副本的需要。（这看似是碰运气，但许多满足 `io.Writer` 的重要类型也有 `WriteString` 方法，包括 `*bytes.Buffer`、`*os.File` 和 `*bufio.Writer`。）

我们不能假设任意 `io.Writer` `w` 也有 `WriteString` 方法。但我们可以定义一个仅包含此方法的新接口，并使用类型断言来测试 `w` 的动态类型是否满足这个新接口。
