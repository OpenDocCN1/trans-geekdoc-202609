# 利用代码 – 创建你自己的程序

如果你在渗透测试期间有时间，你可能创建自己的利用程序。然而，这并不是一件简单的事情。创建自己的利用程序是一个高级课题，我们无法在书中进行有效的涵盖。我们将从高层面上讨论创建利用程序的方法，并提供几个示例以便我们理解这一概念。

**警告** 项目经理：在项目中创建利用代码的成本极高，特别是在项目周期和人力方面。虽然有一些自动化工具可以降低这种成本，但创建利用程序的时间仍然是密集的。

## 模糊测试 (Fuzzing)

模糊测试可以帮助识别应用程序中可能被利用的部分。简单来说，模糊测试是一个向应用程序传递随机数据并期望检测到异常的过程。当目标是接受用户输入的应用程序部分时，异常可能表明存在数据清洗不当，这可能导致缓冲区溢出。理解模糊测试概念的另一种方法是将其视为暴力破解。通常，我们将暴力破解与密码攻击联系起来，但我们可以对接受用户提供数据的应用程序的任何部分进行模糊测试。使用示例可能会更容易解释。例如在图 11.43 中，我们正在运行一个名为“Jbrofuzz”的程序，这是一种以发现 Web 服务器目录而闻名的模糊测试应用程序。在这种情况下，我们要求模糊测试器寻找 IP 地址为`192.168.1.107`的目标上的任何目录。在图 11.43 中，我们可以看到它正通过使用伪随机字符串作为目录名称来暴力破解检测目录。这个特定版本的`Jbrofuzz`拥有一个包含 58,658 个名称的列表，可以在模糊过程中将其作为目录名称。模糊测试可能需要相当长才能完成，因此最好在非工作时间进行自动化。

![B9781597494250000166/f11-43.jpg is missing](img/f11-43.jpg)

**图 11.43.** Java 模糊测试器扫描 80 端口

**警告** 工程师：在监控的网络上对远程系统进行模糊攻击可能会引起网络安全部门注意。如果你需要保持不被发现，模糊测试可能不是一项合适的渗透测试活动。每当我们发现应用程序中有插入用户提供数据的地方时，就可以使用模糊测试器——而是为了寻找目录。现在有很多不同的模糊测试器，它们的工作原理不同。我们在图 11.43 中使用的原理被称为“生成式 (Generation)”。基本上，模糊测试器被给定了一些关于寻找什么的信息，但它不会偏离给定的参数。在图 11.43 中，给定的信息是 58,658 个尝试作为目录的词。真正复杂的生成式模糊测试器还会使用预定义词的组合并修改这些目录词，以（希望）发现新目录。模糊测试的另一种类型是变异式模糊 (Mutation)，它获取数据（例如传输控制协议 [TCP] 数据包）并对其进行变异。这种技术对于发现通信协议或与应用程序通信中的缺陷有用。变异式模糊通常用于 Web 服务器应用程序的会话。从 OSSTMM 的角度来看，识别额外的目录可能会影响系统的隐私性和机密性。发现本应该受密码保护但由于配置错误导致保护措施失效的目录并不罕见。

检测漏洞的另一种方法是通过检查代码本身。在某些情况下，你的渗透测试工作将包括对应用程序代码的访问；优势在于你将确切知道应用程序在做什么。缺点是代码库的规模通常过大——在一个应用程序中遇到数千万行代码并不罕见。寻找缺陷的快速方法是使用专门为此类工作设计的应用程序；微软的`PREfast Analysis Tool`能够分析 C/C++ 代码的安全问题。还有其他工具，包括可以在 [www.fortify.com/security-resources/rats.jsp](http://www.fortify.com/security-resources/rats.jsp) 获取的`安全审计工具 (Rough Auditing Tool for Security (RATS))`，它也可以根据已知的漏洞列表对 C/C++ 程序进行扫描。然而，仅仅因为我们在应用程序中发现了漏洞，并不意味着它可以被用来创建利用程序。决定漏洞可利用性的因素在于程序是如何编译的。我们希望找到一种将我们自己的数据注入到漏洞中的方法，从而导致程序崩溃。仅仅通过查看代码这一点是非常困难的，因为正如前面提到的，编译器构建可执行文件可能会使得无论代码显示了什么，都不可能让应用程序崩溃。充其情况下，你只能找到可以开始攻击的区域。你在分析代码时最可能成功的地方是用户名、密码和域名（或 IP 地址）的添加。在某些情况下，程序员会走捷径，故意在代码中添加访问信息，以便应用程序可以在不需要用户的情况下与服务器通信。这在连接数据库的应用程序中经常发生，通常是为了日志记录。我们可能会跳过代码审查，仅使用流量嗅探器收集这些信息；然而，我们发现大多数情况下通信通道是加密的，这阻止了我们检测这些粗糙的编程技术。我们还应该寻找开发者安装的后门。这些后门是包含在代码中的快捷方式，以便开发者在编写代码时能够更容易访问应用程序。

# 应用程序逆向

对于那些对学习汇编感兴趣的人来说，应用程序逆向是非常兴奋的。对于我们其他人来说，对程序进行逆向工程似乎是一项巨大的任务。如果我们必须知道应用程序在做什么，而又无法访问代码，我们唯一的选择就是开始逆向工程。我们不会在这里解析汇编；有很多其他书籍对逆向工程的讨论比我这个短章节写的要得多。然而，理解人们编写的内容与计算机读取并执行的内容之间存在巨大差异是有帮助的。了解可能存在的攻击向量也是有帮助的，即使它超出了本书的预设范围。让我们来看一个大多数人都熟悉的非常简单的程序：
