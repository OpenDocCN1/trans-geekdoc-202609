
可以构建一个分布式系统，以克服当前语义 Web 框架的可扩展性和性能问题。数据库正在被分布式部署，以提供此类可扩展的解决方案。然而，迄今为止，还没有用于存储和管理`RDF`数据的分布式存储库。研究人员只是最近才开始探索必须解决的问题和技术解决方案，以构建这样一个分布式系统。一条有前景的研究路线涉及利用现成的分布式数据库系统或关系数据库。此类数据库系统可以使用关系模式来存储`RDF`数据。`SPARQL`查询可以通过首先将其转换为`SQL`来回答[CHEB2007, CHON2005, CYGA2005]。最优关系模式正在为此目的被探究[ABAD2007]。此类系统的主要缺点是它们针对关系数据进行了优化。它们可能无法针对`RDF`数据表现良好，特别是因为`RDF`数据是三元组集合[W3a]（一个有序的三元组，分别称为主语、谓语和宾语），这些三元组形成大型有向图。在`SPARQL`查询中，任意数量的三元组模式（TP）[W3e]可以在单个变量[W3d]上连接，这使得关系数据库查询计划变得复杂。由于这些系统针对关系数据模式和事务性数据库用法进行了优化，性能和可扩展性将仍然是一个具有挑战性的问题。

然而，另一种方法是从头构建一个用于`RDF`的分布式系统。在这里，将有机会设计和优化一个专门针对`RDF`数据的系统。在这种方法中，研究人员将是在重复造轮子。我们没有从空白开始，而是构建了一个利用云计算平台的通用分布式存储系统解决方案。然后，我们专门定制了系统和模式，以满足语义 Web 数据的需求。最后，我们使用这种存储设施构建了一个语义 Web 存储库。

## 基于 Hadoop 的 RDF 存储与查询处理

Hadoop [HADOa] 是一种分布式文件系统，文件可通过复制进行保存。它是构建存储系统的理想选择。Hadoop 具有高容错性和极高的可靠性。此外，它还包含 MapReduce [DEAN2004] 编程模型的实现，这是一种适合大规模数据并行处理的函数式编程模型。通过将数据划分为若干独立的数据块，MapReduce 进程针对这些数据块运行，从而简化了并行化。而且，MapReduce 编程模型有助于简化连接多个三元组模式的任务。

在本章中，我们将描述一种在 Hadoop 中存储 RDF 数据的模式，并详细介绍针对这些数据处理查询的解决方案。在预处理阶段，我们处理 RDF 数据并填充分布式文件系统中的文件。此过程包括对数据文件进行分区和组织，以及执行字典编码。随后，我们将详细介绍用于信息检索的查询引擎。我们将明确说明如何利用 MapReduce 编程来满足 SPARQL 查询。具体而言，我们必须确定将要执行哪些 Hadoop“作业”来解决查询。我们提出了一种贪心算法，该算法生成的查询计划所需的 Hadoop 作业数量最少。这是一种利用启发式方法的近似算法，但我们证明了最坏情况具有合理的上界。最后，我们利用两个标准基准数据集进行实验。我们展示了数据集从 0.1 亿到超过 66 亿三元组的实验结果。我们证明了我们的解决方案具有极佳的可扩展性。我们还证明了在超大数据集上使用标准基准查询时，我们的解决方案优于领先的最先进语义网存储库。

我们还为大数据设计并开发了两种访问控制模型。一种是基于令牌的机制，另一种基于 XACML。这两个系统均构建在我们的 SPARQL 查询优化器和用于语义网数据的 JENA 数据管理系统之上。我们的贡献如下所示，并以 图 15.2 进行说明。更多细节请参见 [HUSA2011a]。

1.  我们设计了一种存储方案，用于在 Hadoop 分布式文件系统 (HDFS) [HADOb] 中存储 RDF 数据。

2.  我们开发了一种算法，保证提供的查询计划成本由给定 SPARQL 查询中变量总数的对数上界约束。它利用汇总统计信息估算连接选择性以打破平局。

## 15.3 相关工作

MapReduce 虽是一种编程范式，但正被研究人员迅速采纳。这项技术在处理大量数据的社区中日益流行。它是解决研究人员在云计算中面临的性能问题最有前景的技术。在 [ABAD09a] 中，作者讨论了 MapReduce 如何满足构建理想云数据库管理系统 (Cloud DBMS) 的大部分需求。研究人员和企业正利用 MapReduce 技术进行网页索引、搜索和数据挖掘。在本节中，我们首先调查与 MapReduce 相关的研究。接下来，我们讨论与语义网相关的工作。

Google 将 MapReduce 用于网页索引、数据存储和社交网络 [CHAN2006]。Yahoo! 在其数据分析任务中大量使用 MapReduce [OLST2008]。IBM 已成功试验了利用 MapReduce 技术的纵向扩展-横向扩展搜索框架 [MORE07]。在 [SISM2010] 中，他们报告了如何集成 Hadoop 和 System R。Teradata 通过将 Hadoop 与并行数据库管理系统集成完成了类似工作 [XU2010]。

研究人员已利用 MapReduce 扩展分类器以挖掘 PB 级数据 [MORE2008]。他们研究了用于数据挖掘的数据分发和分区，并应用了三种数据挖掘算法来测试性能。数据挖掘算法正以不同形式被重写，以利用 MapReduce 技术。在 [CHU2006] 中，研究人员通过利用 MapReduce 编程范式重写知名机器学习算法，以发挥多核机器的优势。该技术成功应用的另一个领域是仿真 [MCNA2007]。在 [ABOU09] 中，研究人员报告了一个将 MapReduce 与现有关系数据库技术相结合的有趣想法。这些工作与我们的研究不同之处在于，我们将 MapReduce 用于语义网技术。我们的重点是开发一种可扩展的解决方案，用于存储 RDF 数据并通过 SPARQL 查询检索它们。

在语义网领域，利用 MapReduce 技术的工作并不多。我们发现了两个相关项目：BioMANTA [ITEE] 项目和可扩展、高性能、稳健和分布式 (SHARD) [CLOU]。BioMANTA 提出了对 RDF 分子 [DING2005] 的扩展，并实现了一个基于 MapReduce 的分子存储 [NEWM2008]。他们使用 MapReduce 来回答查询。他们最多查询了四百万三元组。我们的工作有以下不同之处：首先，我们查询了十亿级三元组。其次，我们设计了一种存储模式，专门针对提高 RDF 数据的查询执行性能。我们根据三元组的谓词和对象的类型，将 RDF 三元组存储在文件中。最后，我们还有一种算法，用于确定查询处理计划，其成本由给定 SPARQL 查询中变量总数的对数上界约束。通过使用该算法，我们可以确定作业的输入文件及其运行顺序。据我们所知，我们是首批提出一种在 HDFS 中使用平面文件存储 RDF 数据的存储模式，以及一种用于回答 SPARQL 查询的 MapReduce 作业确定算法的人。

SHARD 是一个使用 Hadoop Cloudera 发行版的 RDF 三元组存储。该项目展示了初步结果，证明了 Hadoop 提高 RDF 数据集可扩展性的能力。然而，SHARD 仅以三元组存储模式存储数据。它目前不进行查询规划或重排序，且其查询处理器不会最小化 Hadoop 作业的数量。针对语义网存储库的研究已相当深入，特别强调查询效率和可扩展性。事实上，此类存储库太多，无法逐一公平评估和讨论。因此，我们关注那些开源或可下载、且在语义网和数据库社区获得良好声誉的语义网存储库。

在 [ABAD2009b] 和 [ABAD2007] 中，研究人员报告了一种用于 RDF 数据存储和检索的垂直分区 DBMS。他们的解决方案是一种模式，为每个谓词使用一张两列的表。然后，他们的模式在列式关系数据库（如 CStore [STON2005] 或 MonetDB [BONC06]）之上实现。他们观察到，与传统的关系数据库模式相比，他们的方案提升了性能。我们在 MapReduce 框架内的基于谓词的分区中利用了这项技术。然而，在垂直分区研究中，仅使用了小型数据库（<1 亿）。有几篇论文 [SIDI2008, MCGL2009, WEIS2008] 表明，随着数据集规模的增加，垂直分区的性能会大幅下降。

Jena [CARR2004] 是一个用于 Jena 的语义 Web 框架。忠实于其框架设计，它允许集成多种持久化解决案。它还支持通过开发推理器进行推理。然而，Jena 仅限于三元组存储模式。换句话说，所有数据都存储在一张单一的三列表中。Jena 对大型数据集的查询性能非常差。此外，对数据集的任何更改都需要对推理三元组进行完全重新计算。

BigOWLIM [KIRY2005] 是目前可用的最快、最具可扩展性的语义 Web 框架之一。然而，它的可扩展性不如我们的框架，且需要非常高端且昂贵的机器。它需要昂贵的硬件（大量主内存）来加载大型数据集，且加载时间很长。正如我们的实验所示，当查询中没有绑定对象时，它的表现不佳。然而，我们的框架在这种情况下性能不受影响。

RDF-3X [NEUM2008] 被认为是现有最快的语义 Web 存储库。换句话说，它拥有最快的查询时间。RDF-3X 使用直方图、汇总统计和查询优化来实现高性能语义 Web 查询。因此，RDF-3X 通常能在带有绑定对象的查询和聚合查询上胜过任何其他解决方案。然而，RDF-3X 的性能对于非绑定查询会呈指数级下降，对于选择性因子低的甚至简单的连接查询也是如此。这对于推理查询变得越来越相关，因为推理查询通常需要带有非绑定对象的子查询的并集。我们的实验表明，RDF-3X 不仅在这类查询上较慢，而且经常中止且无法完成查询。例如，考虑一个简单的查询“选择所有学生”。在 LUBM 中，该查询要求我们选择所有研究生、选择所有本科生，并将结果合并。然而，该并集包含大量结果。虽然两个子查询都能轻松完成，但在拥有 33 亿三元组的 LUBM (30,000) 上，RDF-3X 的并集操作会中止。

RDF 知识库 (RDFKB) [MCGL2010] 是一种使用基于位向量的关系数据库模式构建的语义 Web 存储库。RDFKB 实现了比 RDF-3X 或垂直分区更好的查询性能。然而，RDFKB 旨在提供知识库功能，如推理正向链接、不确定性推理和本体对齐。RDFKB 将这些目标置于可扩展性之前。RDFKB 无法加载拥有 30 亿三元组的 LUBM (30,000)，因此在可扩展性方面无法与我们的解决方案竞争。

Hexastore [WEIS08] 和 BitMat [ATRE2008] 是针对 RDF 索引优化的主内存数据结构。这些解决方案在热运行中可能实现卓越的性能，但它们未针对从持久化存储进行的冷运行进行优化。此外，它们的可扩展性直接与可用的主内存 RAM 数量相关。这些产品不可用于测试和评估。

在我们之前的工作 [HUSA2009, HUSA2010] 中，我们提出了一种贪心算法和一种穷举搜索算法来生成查询处理计划。然而，穷举搜索算法开销大，而贪心算法无界限且其理论复杂度未定义。在本章中，我们提出了一种新的带有上界的贪心算法。此外，我们确实观察到旧贪心算法无法生成最优计划的场景。新算法能够在每种此类情况下获得最优计划。Join Executer 组件使用 MapReduce 框架运行作业。然后它将查询答案从 Hadoop 传回给用户。

### 15.4.1 数据生成与存储

在我们的实验中，我们使用 LUBM [GUO2005] 数据集。它是一个基准数据集，旨在使研究人员能够评估语义 Web 存储库的性能 [GUO2004]。LUBM 数据生成器以 RDF/XML 序列化格式生成数据。这种格式不适合我们的目的，因为我们将数据作为平面文件存储在 HDFS 中，因此即使检索单个三元组，也需要解析整个文件。因此，我们将数据转换为 N-triples 以存储数据，因为采用该格式，一个文件的一行就包含一个完整的 RDF 三元组（主语、谓语和宾语），这非常方便与 MapReduce 作业配合使用。为将数据转换为我们预期格式所需的处理步骤将在以下章节中描述。

### 15.4.2 文件组织

我们不将数据存储在单个文件中，因为在 Hadoop 和 MapReduce 框架中，文件是 MapReduce 作业的最小输入单位，且在没有缓存的情况下，文件总是从磁盘读取。如果我们将所有数据放在一个文件中，整个文件将作为输入用于每个查询的作业。相反，我们将数据分割成多个较小的文件。分割分两步进行，我们将在以下章节中讨论。

### 15.4.3 谓词分割

在第一步中，我们根据谓词对数据进行划分。这种划分能立即让我们缩减任何不包含变量谓词的 SPARQL 查询的搜索空间。对于此类查询，我们只需为每个谓词选取一个文件，并仅在这些文件上运行查询。为求简化，我们使用谓词命名文件，例如，所有包含谓词 `p1:pred` 的三元组都存入名为 `p1-pred` 的文件中。然而，如果三元组模式 [W3e] 中存在变量谓词，且我们无法确定对象的类型，则必须考虑所有文件。如果我们能确定对象的类型，则考虑所有包含该类型对象的文件。我们将在 第 15.5 节 中进一步讨论这一点。在真实的 RDF 数据集中，不同谓词的数量通常不大 [STOC2008]。不过，也存在拥有许多谓词的数据集。在这种情况下，我们的系统性能不会变化，因为我们只选择与 SPARQL 查询中指定的谓词相关的文件。

### 15.4.4 使用对象的显式类型信息进行分割

在下一步中，我们处理 `rdf_type` 文件中的显式类型信息。谓词 `rdf:type` 在 RDF 中用于表示某资源是某个类的实例。`rdf_type` 文件首先被分割成与 `rdf:type` 谓词拥有的不同对象数量相同数量的文件。例如，如果在本体中，类层次结构的叶子节点是 `c[1]`、`c[2]`、…、`c[n]`，那么我们将为这些叶子节点中的每一个创建文件，文件名将类似于 `type_c[1]`、`type_c[2]`、…、`type_c[n]`。请注意，对象值 `c[1]`、`c[2]`、…、`c[n]` 不再需要存储在文件内部，因为它们可以轻松地从文件名中获取。这进一步减少了存储数据所需的空间。我们为谓词 `rdf:type` 的每个不同对象值生成这样一个文件。

### 15.4.5 使用对象的隐式类型信息进行分割

我们根据对象的类型对剩余的谓词文件进行划分。并非所有对象都是 URI（统一资源标识符）；有些是字面值。字面值保留在以谓词命名的文件中；它们不需要进一步处理。URI 对象的类型信息未在这些文件中提及，但可以从 `type_*` 文件中检索。URI 对象会移入以“谓词 _ 类型”命名的相应文件中。例如，如果一个三元组具有谓词 `p`，且 URI 对象的类型为 `c[i]`，则主语和对象将在文件 `p_c[i]` 中以一行的形式出现。为了进行这种分割，我们需要将谓词文件与 `type_*` 文件进行连接，以检索类型信息。

我们的 MapReduce 框架（详见 第 15.5 节）包含三个子组件。它接收用户的 SPARQL 查询并将其传递给输入与计划生成器。该组件使用我们在 第 15.5 节 中描述的算法选择输入文件，决定需要多少个 MapReduce 作业，并将信息传递给连接执行器组件，后者使用 MapReduce 框架运行作业。随后，它将来自 Hadoop 的查询结果返回给用户。

### 15.4.6 访问控制模型

我们在 RDF 数据系统之上开发了一种基于令牌的访问控制机制以及一种基于 XACML 的访问控制模型。运行架构的右侧展示了 XACML 策略是如何实施的。也就是说，当数据从优化组件（左侧）到达时，根据 XACML 模型在数据上强制执行策略。具体流程为：请求被提交给 PEP（策略执行点）。PEP 执行一些检查，然后将其交给 PDP（策略决策点）进行决策。PDP 随后咨询 PAP（策略接入点）和 PIP（策略信息点），然后决定应如何强制执行策略。最后，PEP 强制执行该决策。值得注意的是，基于 XACML 的框架可以被任何访问控制模型替代，因此我们也实现了基于令牌的访问控制模型。这些安全模型将在 第 15.7 节 中讨论。

## 15.5 MapReduce 框架

### 15.5.1 概述

MapReduce 框架是我们云计算工作的核心。在本节中，我们将讨论如何在我们的 MapReduce 框架组件中回答 SPARQL 查询。

第 15.5.2 节 讨论了我们用于选择输入文件以回答查询的算法。第 15.5.3 节 描述了生成回答 SPARQL 查询计划所需的成本估算。它介绍了我们在后续讨论中使用的一些术语。我们还描述了我们应遵循的用于估算计划成本的理想模型，并介绍了我们在实践中使用的基于启发式的模型。第 15.5.4 节 展示了我们基于启发式的贪心算法，用于生成使用 第 15.5.3 节 中介绍的成本模型的查询计划。在某些生成计划的情况下，我们会面临平局情况。在 第 15.5.5 节 中，我们将讨论如何处理这些特殊情况。第 15.5.6 节 通过一个示例查询展示了我们如何在 Hadoop MapReduce 作业中实现连接。

### 15.5.2 输入文件选择

在确定作业之前，我们选择需要输入到作业中的文件。我们在此查询处理步骤中应用一些查询重写能力。我们获取用户提交的查询并遍历三元组模式。我们可能会遇到以下情况：
