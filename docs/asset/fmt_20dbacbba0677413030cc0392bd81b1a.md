## 第 1 章：微服务简介

### 简介

在本章中，我们将探索微服务的世界，这是一种彻底改变了现代软件构建与部署方式的革命性架构风格。微服务提供了一种粒度更细的软件开发方法，将应用程序拆解为更小、独立的服务，每个服务负责特定功能。这种模块化结构促进了敏捷性、可扩展性和弹性，使组织能够快速适应不断变化的市场需求和技术进步。

在本章及全书中，我们将概述本书两大核心主题——微服务架构与 Golang 编程语言——的趋势与耦合关系。我们将看到它们的强相关性、成因及方式。

本章将简要概述构建架构的当代方法——微服务架构。我们将把它与其他架构进行对比，并了解何时使用该架构有益，以及微服务在何种情况下会产生不利影响。

#### 结构

在本章中，我们将讨论以下主题：

*   微服务的优势

### 微服务简史

首先要说明的是，许多人声称他们有权发明微服务架构。根据维基百科，2004 年 Fred George 是第一个提到类似微服务概念的人。他研究的架构被称为“贝叶斯原则”。2005 年，Peter Rodgers 在 Web Services Edge 大会上引入了“微 Web 服务”这一术语。由于缺乏对微服务架构的明确定义，许多人都可以声称是他们发明了它。从那时起，许多人展示了看起来或感觉上像微服务的事物。重要的是不要将微服务与 SOA 混淆，我们稍后将详细说明它们之间的区别。从那时起，其流行度逐年上升，并在 2014 年至 2015 年间加速增长（图 1.1）。

### 单体架构、SOA 和无服务器架构

了解某些术语或技术的其他替代方案有助于清晰地理解它们。从软件行业早期开始使用了一段时间的常见架构风格包括单体架构、“面向服务架构”，即 SOA，以及一些我们在本书中不再详述的其他架构。

#### 单体架构

源自古希腊语的“Mono”意为单独、单一。顾名思义，这种架构被构建为部署在单一平台上的单个代码块。通常，在单体架构中，有三个主要部分——存储（数据库）、包含客户端的 Web 应用，以及充当服务端的后端，后者包含所有业务逻辑、数据层和其他所有内容（图 1.2）。

![](img/Figure-1.2.jpg)

**图 1.2：** 简单的单体结构

`DAL` 是 Data Access Layer（数据访问层）的首字母缩写。该软件中间件负责为拥有数据库直接访问权的软件层提供支持，并提供重试、错误处理、缓存等工具。

从简单的图表中可以看出，这种架构非常直观。然而，所有组件都紧密相互依赖。

简而言之，单体架构的优缺点如下：

#### 优点

*   开发简单，交付生产简单。
*   最少的跳转次数：无需在服务之间通信，通过降低延迟可以节省大量时间，从而带来更好的性能。
*   非常容易实施 `DRY` 原则（不要重复自己）——归功于单一代码库。

#### 缺点

*   **面条代码**：随着代码库的扩展，代码更有可能变得笨重难管理。
*   **更难排查故障和调试**：在庞大的代码库中导航极具挑战性。甚至更难找到隐藏在某个函数中导致副作用的恶性 Bug。
*   **IDE**：集成开发环境（IDE）不堪重负。请注意，存在一种在单体仓库中编写微服务的方法，即所有服务使用单一仓库。
*   **容易积累遗留代码和技术**：我们害怕在大型代码库中更改核心功能、基础设施和技术。这些更改可能会显著影响应用程序，因为保留旧代码和旧技术很方便。

如今，微服务架构是市场上最流行的架构，人们倾向于摒弃单体架构，因为他们认为它已过时。然而，单体架构在各种用例中依然受益良多。

#### SOA

`SOA` 代表面向服务架构。虽然与微服务相比，该名称可能容易产生误解，但它们确实有共同点。然而，它们之间存在许多差异。SOA 是一种架构风格，它将软件系统组织为一组松耦合且可复用的服务。在 SOA 架构中，有两个主要部分——提供者和消费者。提供者和消费者可以位于同一部署组件/应用程序/服务器上。这是 SOA 与微服务的重大区别。这种方法诞生于 90 年代初。那时，软件工程的运维部分更为复杂。我们有专门专注于基础设施、安全、数据库等的团队。

在分解层面上，我们可以将 SOA 架构置于单体架构和微服务架构之间。单体架构表现为单一单元，而微服务架构表现为细粒度的划分。

![](img/Figure-1.3.jpg)

**图 1.3：** 简单的 SOA 结构

简而言之，SOA 的优缺点如下：

#### 优点

*   **可复用性**：可复用性是该方法的核心。它允许我们在服务/API 层面分离关注点，并复用基础设施，如硬件、网络、操作系统等。
*   **关注点分离**：其粒度不如微服务细。但它仍允许我们并行交付服务/API，而无需依赖其他团队。

#### 缺点

*   **副作用**：共享组件中的问题可能影响其他组件。例如，如果消费者或提供者消耗过多资源、环境变量发生变化，或任何其他副作用，所有这些都很容易影响所有现有服务。
*   **性能开销**：SOA 中额外的抽象层和通信协议可能引入性能开销。跨不同组件和网络的服务调用可能导致延迟，潜在地影响响应时间和整体系统性能。网络问题的顾虑同样适用于数据库。
*   **复杂性**：实施 SOA 可能给我们的服务带来复杂性。

#### 无服务器架构

在我们这里介绍的架构中，这种架构方法是最现代的。

云计算的诞生自然催生了无服务器架构。这种方法的核心是剥离基础设施顾虑，让我们专注于重要的事情——业务逻辑。顾名思义，这是“server”（服务器）+“less”（无）——意味着不存在服务器。当然，某处确实存在运行代码的基础设施和服务器。但我们不负责管理这台服务器。云厂商负责所有这些工作。此类技术的例子包括 GCP 的 Functions 服务或 AWS 的 Lambda。还有许多服务/产品旨在支持无服务器架构。

在探讨无服务器架构的优缺点之前，我们想讨论两个核心概念：FaaS 和 BaaS。

*   **FaaS**：代表函数即服务。我们编写函数/API 端点，其余工作交由云端完成。
*   **BaaS**：代表后端即服务。我们可以专注于开发和维护客户端，而无需关注存储、数据库管理、网络和其他基础设施方面。

![](img/Figure-1.4.jpg)

**图 1.4：** 简单的无服务器结构

从图中可以看出，作为开发者，我们只编写了绿色方块（函数），云厂商提供了所有黄色方块（第三方服务/数据库）。

#### 优点

*   **高效的开发流程**：开发流程高效，初期开发迅速。基础设施顾虑不再是负担，因为无服务器架构无缝地管理了它们。
*   **易于扩展**：扩展过程非常简单——我们唯一需要担心的是函数使用的资源。

#### 缺点

*   **供应商锁定**：一旦我们使用特定供应商，所有配置和设置都将专门针对我们的服务。迁移到另一个供应商可能会非常痛苦。
*   **边缘场景**：有些场景下我们想做某事，但由于所用供应商服务的限制而无法实现。
*   **监控**：由于我们依赖供应商管理基础设施，因此也需要依赖其提供监控工具，或集成其他 SaaS/OSS 监控工具。

无服务器架构的成本颇具争议。在无服务器架构中，我们按使用量付费，通常针对 CPU 和内存。我们拥有精简的计费模型，且使用方法简单。不仅如此，显而易见，我们在 DevOps、运维和基础设施工程师方面节省了资金。然而，另一种观点认为自己做这些事能省钱，理由是我们没有灵活性来利用我们特定的架构和运维方式。

### 微服务的优势

下图大致描述了微服务的样貌，我们已经可以看到这种架构与其他架构的区别。

![](img/Figure-1.5.jpg)

**图 1.5：** 简单的微服务结构

#### 独立工作负载

根据设计，微服务架构将架构拆分为独立的服务/API/组件。这些服务作为独立的可部署单元单独交付和打包。自包含单元原则是 SOA 与微服务之间的重大区别之一。将许多工作负载分离减小了代码库的体量，从而形成更小的服务。

更小的服务意味着精简的二进制文件、快速的构建等。另一个显著效果是每个工作负载不影响其他工作负载。我们预先知道依赖关系，这使得将服务作为容器交付变得轻而易举。容器化是微服务的最佳实践。这两个概念都实现了同一个目标——关注点分离。

由于代码库按服务划分，因此没有共享代码（通常情况）。每个团队可以独立处理自己的代码，而不干扰其他团队。分离的代码库带来了极快的初始开发速度。另一个效果是每个团队可以测试自己的服务，而无需考虑其他团队的服务。

#### 易于扩展

首先谈谈垂直扩展。垂直扩展意味着增加更多资源（更大的机器）。然而，资源消耗与服务处理更多负载的能力之间并不总是存在直接相关性。当我们想要执行水平扩展时，微服务架构变得更有帮助。执行扩容非常顺畅，只需增加目标机器的复制机器/容器数量即可。

#### 即插即用

一个令人兴奋的视角是将微服务视为蜂窝结构。每只蜜蜂建造自己的细胞。用另一个服务替换一个服务也非常简单。当我们想要重塑架构、尝试新技术或在当前架构中执行某些测试时，用另一个服务替换一个服务的能力会变得很方便。此外，回滚/发布流程变得简单易行。

#### 容错性

故障是始终会发生的典型场景，我们应为此做好准备。我们不生活在代码完美、服务器拥有 100% 成功率的完美世界中。由于服务间的松耦合，微服务架构使这种准备变得更容易。每个服务都可以在不影响其他服务的情况下发生故障。还请注意，谈到故障时还有许多其他因素需要考虑（重试、优雅关闭等），我们稍后会讨论。但至少微服务为在不考虑其他服务的情况下妥善处理故障奠定了基础，使工作变得更轻松。

#### 提高敏捷性

简而言之，敏捷是指快速工作和灵活应变的能力。关于如何实现敏捷，有庞大的理论和技巧，我们将在本书后续章节中讨论。

每个服务拥有自己的代码库。一个团队可以负责一个或多个服务，而无需依赖其他团队，这对于使用敏捷方法至关重要。此外，当新成员加入团队时，入职变得轻而易举。他们不需要学习所有服务的代码，只需了解其团队负责的服务即可。

#### 运维开销

正如之前讨论的，微服务的主要优势在于每个工作负载/部署都是独立的，并与其他服务分开交付。我们看到了所有巨大的优势。但硬币有另一面。为了允许每个服务作为独立部署交付，我们需要从运维侧提供支持。

每个服务有许多事项需要考虑——服务配置、打包、独立测试、独立交付单元等。这些示例强调了与单体架构或 SOA 相比，使用微服务需要更多的运维工作。
