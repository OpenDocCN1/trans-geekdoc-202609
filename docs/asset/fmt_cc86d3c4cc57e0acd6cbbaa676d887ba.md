
这将创建一个标签（即节点类型）为 `Customer` 且具有给定属性的节点。可以通过在后续查询中使用 `customerId` 属性来标识单个节点。关键字 `create` 可替代 `merge` 使用，区别在于：如果匹配的节点已存在（本例中为具有相同 `customerId` 的 `Customer` 节点），`merge` 将不执行任何操作，而 `create` 将引入重复节点。可以添加约束以强制属性值的唯一性。添加该约束会自动在唯一属性上创建索引。

```
create constraint cust_id_uniq for (c:Customer) require c.customerID is unique
```

在关系型数据库中，相关表单元格中的 null 表示值的缺失。在图数据库中，null 的含义略有不同。属性不以 null 作为值；null 仅表示该属性不存在。这意味着对于节点和关系的属性而言，不存在与 null 是等价的。可以约束属性为非 null，在 `Neo4j` 中这等同于要求该属性必须存在。

```
create constraint cust_existence for (c:Customer) require c.customerID is not null
```

属性上的唯一性约束和存在性约束的组合，提供了大致相当于关系型数据库中主键的功能。

插入关系也使用相同的 `merge` 或 `create` 关键字。Cypher 表示法允许指定关系的方向，如下例所示：

```
merge (:Customer {customerID:"ABCDE"}) -[:PURCHASED]-> (:Order {orderID:12345})
```

这将创建指定的 `Customer` 和 `Order` 节点，以及它们之间一条指向的 `PURCHASED` 关系。在两个*现有*节点之间添加关系需要略微不同的策略。我们首先通过查询数据库找到相关节点，然后在创建关系时使用对这些节点的引用，如下例所示。

```
match ( c:Customer { customerID:"ABCDE" } ) match ( o:Order { orderID:12345 } ) merge ( c ) - [ :PURCHASED ] -> ( o )
```

对于大型数据集，可使用批量插入方法在单个事务中插入多个节点和关系。还提供了用于从外部来源（如 CSV 文件或其他数据库）批量导入数据的工具。

### 更新与删除

最常见的更新操作之一是修改节点和关系的属性。可以通过查询找到相关的节点或关系，并将更新应用于查询结果。与创建类似，可使用批量更新方法在单个事务中更新多个节点和/或关系。以下示例展示了在图数据库中进行简单 Cypher 更新数据的操作：

```
match ( c:Customer { companyName: "Tamale Spice" } ) set c.country = "Mexico"
```

此处，变量 `c` 绑定到特定的 `Customer`，然后将其 `country` 属性设置为指定值。如果属性值已存在，将被新值替换。如果属性不存在，将被创建。可以通过移除现有属性来彻底删除它。这相当于在关系型数据库中将相关表单元格设置为 null。

```
match ( c:Customer { companyName: "Tamale Spice" } ) remove c.country
```

可以使用适当的过滤条件删除完整的节点（或节点集）及其所有关联属性。

```
match ( c:Customer ) where c.country = "Mexico" delete c
```

这将删除位于 Mexico 的所有 `Customer` 的数据，当然：

```
match ( x ) delete x
```

可能会删除数据库中的所有节点，因此正确设置过滤条件非常重要。

```
select distinct customerName from Customers
```

## 将 ORM 映射到图数据库

### ORM 到图映射

第 11 章 讨论了 ORM 模型到关系结构的映射，并提出了一个系统化的过程（`Rmap`）来生成无冗余的关系设计。现在我们将考虑针对图数据库的等效方法的可能性。

图 17.11 显示了一个简单的 ORM 模型（约束省略，稍后讨论）和一个显示节点标签的可比较图模型。撇开图形符号的明显差异不谈，很明显这两个模型在结构上非常相似。

![图 17.11 简单 ORM 和图结构的比较。](img/f17-11-9780443237904.jpg)

**图 17.11 简单 ORM 和图结构的比较。**

在这个简单的层面上，似乎 ORM 模型可以直接作为图模式的定义。不幸的是，当我们深入细节时，事情变得更加复杂。第一个困难是图数据库只能表示二元关系。

其他元数的 ORM 事实类型必须映射到图模型中结构不同的东西。

一元事实类型可以以一种相当直接的方式映射到图属性（通常是节点属性）或二元关系。三元或更高元数的事实类型必须重新映射为二元关系，一个 ORM 事实类型可能涉及多个二元关系。这可能需要额外的约束来保留原始 ORM 模型的意图。

然而，这引出了下一个困难，即图数据库通常提供非常有限的约束选项。在 `Neo4j` 中，唯一的选项是唯一性和非空约束（尽管企业版中还提供了其他几种）。虽然可以通过仔细构建创建或更新语句来保留适当的结构来解决这些问题，但对于许多 ORM 约束，唯一现实的解决方案是在应用程序中实现约束，而不是在数据库中。

能力上的最后一个差异是子类型的概念。当然可以用图的形式表达子类型概念，例如：

```
(:Species) – [:IS_MEMBER_OF] -> (:Genus) – [:IS_MEMBER_OF] -> (:Family) ...
```

但这种关系在任何方面都没有与其他类型的关系区分开来。在决定是否可以将子类型合并到一个标签下，或者不同的节点标签是否更可取时，会出现关于吸收、分离和划分的类似考量。ORM 子类型关系中涉及的任何约束都面临与 n 元关系相同的问题，可能需要在相关的应用程序代码中强制执行。

尽管存在这些困难，ORM 模式和图模式之间的相似性依然很强，并且可以概述一个系统化的 ORM 到图映射过程，我们可以称之为 `Gmap`。这可以在类似 `Rmap` 过程的基础上运行，遵循一系列步骤将结果强制转换为适当的形式。

这最好通过一个具体的例子来说明。第 11 章 讨论了 `Rmap` 过程在几个模型中的应用，包括此处作为图 17.12 再现的电视频道模型。这可以为两种方法之间的有用比较提供基础。该模型展示了任何可能的 `Gmap` 过程必须适应的许多特征。

![图 17.12 电视频道的 ORM 模式（重复自图 11.30）。](img/f17-12-9780443237904.jpg)

**图 17.12 电视频道的 ORM 模式（重复自图 11.30）。**

任何一对一事实类型都可以通过合并两个对象类型来解决，使其中一个成为另一个的属性。哪个对象类型应被视为“父级”通常从模型中显而易见，但在某些情况下必须做出任意选择。在该模型中，我们可以将 `Frequency` 作为 `Channel` 的属性，将 `ProgramTitle` 作为 `Program` 的属性。这本质上与 `Rmap` 过程中的策略相同。

ORM 模型中的 `TimeSlot` 对象类型具有复合标识符：`Day` 和 `Hour`。复合标识符在图数据库中可能难以复制，因此可能需要引入代理标识符。在这种情况下，我们可以通过连接 `Day` 和 `Hour` 来形成 `timeSlotCode`，但这不是必须的，因为 `TimeSlot` 仅在特定 `Program` 的上下文中相关。

带有跨越唯一性约束的事实类型将在图模型中成为关系。对于三元或更高元数的约束，必须选择最佳标签作为关系的两端，因为关系在图模型中只能是二元的。其他角色将成为关系的属性。对于该模型中的四元事实类型，我们可以在 `Survey` 和 `Channel` 之间建立关系，将 `Category` 和 `Rating` 作为属性。

对象化事实类型也映射到关系，任何函数依赖的事实类型指示关系的属性。在本例中，这将适用于“Office”和“Department”。两个对象化事实类型之间的函数依赖引入了进一步的复杂性，稍后将讨论。

连接到同一对象类型的函数角色的事实类型可以分组到同一节点类型（标签）中，成为“父级”的属性。在该模型中，`MoneyAmount` 对象类型可以成为 `Channel` 节点的“worth”属性和 `Company` 节点的“assets”属性。

### 图数据库中的约束

我们还需要考虑 ORM 模型中指定的约束。这可能会有问题，因为图数据库中可用的约束选项非常有限。通过仔细构建修改结构的语句，存在一些变通的可能性，但这并不总是可行。

强制性约束可以在一定程度上通过要求（例如）标签的属性非空来强制执行，但如果在创建相关节点时不知道属性值，这可能会成为一种麻烦。

唯一性约束在 `Neo4j` 中可用，可在适当的地方使用。在上述模型中，`Company`、`Channel`、`Survey` 和 `Program` 的标识属性可以定义为唯一。这意味着，例如，将只有一个带有“Channel”标签且 `ChannelNumber` 属性等于“1”的节点。但是，对于 `Suburb`、`Department` 或 `TimeSlot`，不应这样做，因为这些标签可以拥有多个具有相同属性的节点，如图 17.14 所示。这些节点可以通过它们与其他节点的不同关系实例来相互区分。

`Channel` 角色和 `TimeSlot` 角色之间的外部唯一性约束更难处理。我们需要确保一个 `TimeSlot` 对于给定的 `Channel` 只能关联一个 `Program`，尽管同一个 `TimeSlot` 可以被其他频道用于它们自己的节目。`Neo4j` 中没有约束来表达这一点，但我们可以使用以下策略指定在特定 `Program` 和特定 `TimeSlot` 之间创建 `IS_SHOWN_IN` 关系：

1. 使用查询查找播放指定 `Program` 的 `Channel`。
2. 使用查询查找该 `Channel` 在指定 `TimeSlot` 播放的任何 `Program`。
3. 如果结果为空，则在 `Program` 和 `TimeSlot` 之间创建 `IS_SHOWN_IN` 关系。

ORM 拥有非常丰富的约束语言，尝试编写复杂的 `Cypher` 代码来捕捉 ORM 模型的完整意图可能并不值得。在这种情况下，最好将约束委托给应用程序代码，而不是试图在数据库中强制执行。

从这个例子可以清楚地看出，ORM 和图数据库之间有着密切的亲和力，这或许并不奇怪，因为 ORM 模型本身就是一个图。在更侧重于关系而非数据处理的应用中，图数据库为关系系统提供了一个有用的替代方案。它们与关系系统共享许多相同的可扩展性问题，但可以通过复制服务器来提供高可用性。

将 ORM 模型转换为图数据库可以通过一种系统的方式完成，这种方式能保留 ORM 模型的大部分意图，尽管在处理约束时可能需要一些创造性。对于特定的图数据库系统，自动化 `Gmap` 过程以生成模式设计是可行的，这可能包括一些代码（采用适当的语言）来处理约束等问题。

图数据库最重要的特性可能是它们能够沿着连接的数据网络追踪链接，这种网络可能延伸至长长的连接链。

许多常见问题可以用搜索数据空间来表达，并且有已知的高效算法来执行此操作。这些能力使得图数据库在以下应用领域成为热门选择：

* 对社交网络数据和其他人际关系进行建模和查询。
* 通过分析用户的偏好和活动，为系统用户创建推荐。
* 通过分析实体之间的连接，识别欺诈行为模式。
* 构建表示实体间语义关系的知识图谱。
* 在刑事调查中分析个人、组织和事件之间的连接。

## 17.6 其他非关系型数据库

概念模式可以映射到各种逻辑数据模型。第 11 章 中讨论的 `Rmap` 过程假设应用平台是一个集中式的关系型 DBMS。正如我们在本章前面所见，为映射到其他类型的 DBMS 指定其他过程是一项相当简单的任务。

尽管关系型 DBMS 长期以来一直主导着商业市场，但存在许多替代方案。这些包括基于层次或网状数据模型的旧系统，以及如前所述的较新替代方案。虽然纯关系型 DBMS 适合大多数业务应用，但它们可能不是某些专业应用的理想选择，例如计算机辅助软件工程 (CASE) 工具、计算机辅助设计工具（如 VLSI 设计、机械工程、建筑）、文档处理、空间数据库、专家系统、科学数据库（如基因工程）和通信管理。请注意，这些应用大多涉及复杂对象，并且可能最多只占数据库应用的 10%。

人们引用许多理由来表达对*纯*关系型 DBMS 在复杂应用中不满意。它们可能太慢——主要因为它们需要太多的表连接，所以在处理复杂对象时表现不佳。它们经常以不自然的方式对对象建模（例如，关于单个对象（如一个人）的信息可能分散在多个表中——对于复杂对象，情况会更糟）。它们依赖于基于值的标识符。它们不利于复用（例如，它们没有对子类型提供直接支持）。它们需要访问过程式语言来完成困难任务（例如，特殊规则和行为），这导致了与声明式、基于集合的关系查询语言的“阻抗失配”。它们可能不支持二进制大对象 (BLOB)，如图像（图标、照片、地图等）、音轨、视频等。

### 面向对象

*对象数据库* (ODB)，或*面向对象数据库* (OODB)，包含各种面向对象特性。历史上，ODB 研究借鉴了四个相关领域的发展：编程语言、语义数据模型、逻辑数据模型和人工智能。

在编程语言方面，人们看到了对用户可定义抽象数据类型和持久化数据的需求。面向对象编程范式始于 1962 年的 `Simula` 和 1972 年的 `Smalltalk`。如今，存在许多面向对象编程语言（如 `Eiffel`），许多传统编程语言也获得了面向对象扩展（如 `C++` 和 `C#`）。
