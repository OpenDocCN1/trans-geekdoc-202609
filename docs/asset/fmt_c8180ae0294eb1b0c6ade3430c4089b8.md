
输出将如下所示（数字的顺序可能会变化）：

```
Waiting…
2
0
1
3
4
Done
```

`WaitGroup` 类型作为一个计数器工作。在幕后，`WaitGroup` 类型持有一个 `int` 类型的计数器，初始值为 0。如果计数器值变为 0，则所有阻塞在 `Wait()` 上的 Goroutine 都会被释放。我们使用 `Add(delta int)` 函数来增加计数器的大小。要减少计数器的值，我们使用 `Done()` 函数——它从计数器中减去 1。这些是 `WaitGroup` 类型的所有方法——`Add`、`Done`、`Wait`。

请注意，`Add` 函数中的负值会导致 panic。此外，如果我们在函数之间传递 `WaitGroup` 实例，应该通过指针传递。

这种技术最大的缺点是没有常规的方式来处理错误。有一个单独的包叫 `errgroup`，它可以帮助我们实现这一点。

## 锁

为了在多个 Goroutine 之间访问相同的数据，我们需要在一个 Goroutine 访问数据时保护数据不被另一个 Goroutine 访问。这种情况可能导致数据错误，甚至更糟——致命错误。

```go
func main() {
	counter := 0
	wg := sync.WaitGroup{}
	wg.Add(10000)
	for i := 0; i < 10000; i++ {
		go func() {
			defer wg.Done()
			counter++
		}()
	}
	wg.Wait()
	fmt.Println("counter:", counter)
}
```

在前面的示例中，计数器的输出应该是 10,000。不幸的是，计数器的值远低于它。原因是多个 Goroutine 试图访问 `counter` 变量；一些失败是因为其他 Goroutine 锁定了计数器值并写入它。如果我们用 map 替换计数器并尝试写入同一个键，我们将得到一个更糟的场景——`fatal error: concurrent map writes`。为了避免这种情况，我们需要使用 `mutex`。`Mutex` 是 `sync` 包的一种类型，帮助我们加锁和解锁。

```go
func main() {
	counter := 0
	wg := sync.WaitGroup{}
	mu := sync.Mutex{}
	wg.Add(10000)
	for i := 0; i < 10000; i++ {
		go func() {
			defer wg.Done()
			mu.Lock()
			counter++
			mu.Unlock()
		}()
	}
	wg.Wait()
	fmt.Println("counter:", counter)
}
```

现在输出将是 - `counter: 10000`，符合预期。`mutex` 类型让我们能够加锁。对于任何其他想要 `Lock()` 互斥锁 (`mu`) 的 Goroutine，我们必须等待直到另一个 Goroutine `Unlock()` 互斥锁 (`mu`)。

## Go 语言中的单例模式 - `Once.Do`

总结单例的概念——它是确保特定类型仅创建单个实例的最知名设计模式之一。在许多其他编程语言中，存在各种模式来实现这一点，同时保持线程安全。在 Go 中，利用 `sync` 包中的 `Once` 类型，实现此模式非常容易。

```go
type cache struct{}

var cacheSingleton *cache
var once sync.Once

func main() {
	GetCache()
	GetCache()
	GetCache()
}

func GetCache() *cache {
	once.Do(func() {
		println("Creating singleton object")
		cacheSingleton = &cache{}
	})
	return cacheSingleton
}
```

该程序的输出是 - `Creating singleton object`。仅此而已（不是三次）。

`Do` 函数接收一个函数作为参数。`Do` 函数确保内部函数**恰好执行一次**，这正是我们在编写单例时想要实现的。`Do` 也是 `Once` 类型上唯一存在的函数。

## 发布/订阅

发布-订阅是最知名的模式之一。Pub/Sub 模式是一种消息传递模式，帮助我们在系统/服务/对象之间进行通信。它通过所谓的主题从发布者广播数据/消息。每个订阅者被分配到一个特定主题，并且每个订阅者都会接收到与其分配主题相关的所有消息。

![Figure 5.4: Publish-Subscribe pattern](img/Figure-5.4.jpg)

```go
type PubSub struct {
	subscribers map[string][]chan interface{}
}

func NewPubSub() *PubSub {
	return &PubSub{
		subscribers: make(map[string][]chan interface{}),
	}
}

func (ps *PubSub) Publish(topic string, item interface{}) {
	for _, ch := range ps.subscribers[topic] {
		ch <- item
	}
}

func (ps *PubSub) Subscribe(topic string) <-chan interface{} {
	ch := make(chan interface{})
	ps.subscribers[topic] = append(ps.subscribers[topic], ch)
	return ch
}

func main() {
	ps := NewPubSub()
	ch := ps.Subscribe("t1")
	go ps.Publish("t1", "hello")
	item := <-ch
	println(item.(string))
}
```

这是 Go 语言中发布-订阅模式的一个简单实现。请注意，这个示例并不完美——我们没有关闭通道，也没有正确处理并发。实现此模式时，建议使用现有的库。

## 微服务架构中的发布/订阅模式

发布/订阅是微服务架构中的一种模式。在构建微服务架构时，每个服务独立工作并相互解耦，这正是发布/订阅模式所要实现的目标。它允许在不更改发布者代码的情况下独立编写每个订阅者以获取其数据。订阅者只需将自己分配给一个现有的主题即可。微服务架构的诸多优势在此模式中得以体现。一个主要例子是使用发布/订阅时，服务的可扩展性变得无缝衔接。

更高级的发布/订阅用法允许更多功能，如计划进程、延迟、工作流等。以下是一些使用发布/订阅的实际案例：

*   事件数据广播
*   实时通知
*   分布式缓存
*   实时位置追踪

请注意，要在微服务架构中实现服务间的发布/订阅，我们需要使用第三方服务来管理主题、发布者和订阅者。常见的发布/订阅技术可在所有最大的云厂商服务或开源项目（如 `Redis`）中找到。

许多人倾向于将发布/订阅与消息代理混淆。让我们简要了解一下它们的区别。

| **PubSub** | **消息代理** |
| --- | --- |
| 类似广播 - 单条消息复制给多个订阅者 | 单播 - 单条消息发给单个消费者 |
| 发布者和订阅者 | 发布者和消费者 |
| 适合广播 | 适合任务委派 |
| 更容易丢失消息 | 更健壮，可靠性更好 |
| 无 FIFO 能力 | 具备 FIFO 能力 - 保持顺序 |

## 通道关闭原则

我们之前简要提到了通道关闭原则。然而，它非常重要，值得我们再次讨论。简单的原则是：如果是单个发送者，我们必须从发送者的 goroutine 关闭通道。我们不应该从接收者一侧关闭通道，也不应在有多个发送者时从发送者一侧关闭通道。

虽然原则如此，但也存在需要从多个发送者关闭通道的场景。在这种情况下，如果我们有多个发送者并需要关闭通道，必须执行优雅关闭。

```go
func main() {
    ch := make(chan int)
    wg := &sync.WaitGroup{}
    wg.Add(10)
    for i := 0; i < 10; i++ {
        go Sender(ch, wg, i)
    }
    go func() {
        wg.Wait()
        close(ch) // 优雅关闭
    }()
    // 接收者
    for i := range ch {
        println(i)
    }
}

func Sender(ch chan<- int, wg *sync.WaitGroup, i int) {
    defer wg.Done()
    ch <- i
}
```

在前面的示例中，我们可以观察到使用多个发送者 goroutine 实现优雅通道关闭的情况。

## 避免 Goroutine 泄漏

到目前为止，我们已经体验了 goroutine 所提供的所有优势。不幸的是，goroutine 也有缺点 —— goroutine 泄漏！

当发送者 goroutine 阻塞等待接收者到达通道，反之亦然时，就会发生 goroutine `泄漏`。同时，被阻塞的 goroutine 永远无法被解除阻塞。

```go
func leak(ch chan int) {
    data := <-ch
    fmt.Println(data)
}

func main() {
    ch := make(chan int)
    go leak(ch)
}
```

让我们看看前面的示例；为什么这是泄漏？这是因为我们没有接收者！`leak` 函数将永远卡住。

导致 goroutine 泄漏的两种常见情况：

*   被遗忘的发送者
*   被遗弃的接收者

### 被遗忘的发送者

这是一种发送者 goroutine 被“`遗忘`”并试图通过通道发送数据的场景。然而，另一侧没有接收者。

```go
func forgottenSender(ch chan int) {
    data := 3
    // 因为没有人接收数据，这里会阻塞
    ch <- data
}

func main() {
    ch := make(chan int)
    go forgottenSender(ch)
    println(runtime.NumGoroutine()) // 2 而不是 1
}
```

`forgottenSender` 函数将在一个 goroutine 中永远运行下去。在该示例中，我们必须使用带缓冲通道来避免 goroutine 泄漏，这样 `forgottenSender` 才能完成其工作。

```go
func forgottenSender(ch chan int) {
    data := 3
    // 因为没有人接收数据，这里会阻塞
    ch <- data
}

func main() {
    ch := make(chan int, 1) // 通过使用带缓冲通道避免 goroutine 泄漏
    go forgottenSender(ch)
}
```

Goroutine 泄漏并不总是显而易见的。我们可以看到许多错误处理导致无意 goroutine 泄漏的场景。

```go
func networkCall() int {
    return 1
}

func anotherAction() error {
    return errors.New("data is invalid! Returning")
}

func forgottenSender(ch chan int) {
    data := networkCall()
    ch <- data
}

func handler() error {
    ch := make(chan int)
    go forgottenSender(ch)
    err := anotherAction()
    if err != nil {
        return err
    }
    data := <-ch
    fmt.Println(data)
    return nil
}
```

如果我们去掉调用 `anotherAction` 函数的部分，一切都会正常。不幸的是，假设该代码块是必要的。我们遇到了 goroutine 泄漏，因为 `forgottenSender` 函数在后台持续运行，而 `handler` 函数返回了错误，且该函数已完成工作。要解决这种情况，我们必须在调用 `anotherAction` 函数之前在 goroutine 中运行接收者，或者使用带缓冲通道。

类似于错误处理用例，当我们对多个通道使用 select case 时，也可能发生这种情况。

```go
func networkCall() int {
    time.Sleep(3 * time.Second)
    return 1
}

func forgottenSender(ch chan int) {
    data := networkCall()
    ch <- data
}

func handler() error {
    ctx, cancel := context.WithTimeout(context.Background(), 10*time.Millisecond)
    defer cancel()
    ch := make(chan int)
    go forgottenSender(ch)
    for {
        select {
        case data := <-ch:
            fmt.Printf("received data! %d\n", data)
            return nil
        case <-ctx.Done():
            return errors.New("timeout! Process canceled. Returning")
        }
    }
}
```

我们面临同样的问题：`handler` 函数在网络调用完成前就结束了工作（10 毫秒的超时低于 3 秒）。`forgottenSender` 函数卡住了，另一侧没有接收者，从而导致 goroutine 泄漏。我们可以通过使用带缓冲通道来解决这个 goroutine 泄漏。

当我们使用带缓冲通道时，它会解除 goroutine 的阻塞，随后 GC 会注意到没有人在使用通道 `ch` 并将其从内存中清理。

### 被遗弃的接收者

这是一种发送者发送了数据，但发送者从未通知接收者停止接收数据的场景。

```go
func abandonedReceiver(ch chan string) {
    for data := range ch {
        println(data)
    }
    println("Worker is done")
}

func sender(ch chan string) {
    for _, data := range []string{"one", "two", "three"} {
        ch <- data
    }
}

func handler() {
    ch := make(chan string, 3)
    sender(ch)
    go abandonedReceiver(ch)
}

func main() {
    handler()
    time.Sleep(1 * time.Second)
    println(runtime.NumGoroutine()) // 2 而不是 1
}
```

正如我们所见，`abandonedReceiver` 函数将永远运行下去。当前程序的输出如下所示：

```
one
two
three
```

`"Worker is done"` 这一行永远不会被打印，因为 `abandonedReceiver` 在 range 循环上被阻塞 —— 这导致了 goroutine 泄漏。要解决它，我们需要在发送者完成工作后关闭通道，正如我们在关闭通道一节中所见。

```go
func sender(ch chan string) {
    for _, data := range []string{"one", "two", "three"} {
        ch <- data
    }
    close(ch) // 解决 goroutine 泄漏
}
```

### 检测 Goroutine 泄漏

让我们强调这样一个事实：Goroutine 泄漏表现为内存泄漏。后台运行的 goroutine 持有变量，导致这些变量无法从内存中释放。检测 goroutine 泄漏主要有两种方法：

*   **性能分析**：我们将在 *第 10 章，生产环境的下一步* 中更详细地讨论性能分析。通常，在进行性能分析和代码分析时，我们可以使用 Go 的 `pprof` 或 `gops` 来检查是否有未终止的 goroutine。
