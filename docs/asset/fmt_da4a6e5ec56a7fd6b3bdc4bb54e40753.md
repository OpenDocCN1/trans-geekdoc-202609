
在图 8.27 中，`empNr` 是 `Employee` 的主键。`bldgNr`、`roomNr` 对为 `Room` 提供了复合主键。社会安全号码属性（`ssn`）是 `Employee` 的备选键。在 `Employee` 中，`bldgNr`、`roomNr` 对是一个外键（引用 `Room` 的主键）。在 `Room` 中，`bldgNr` 是一个外键（引用此处未显示的 `Building` 实体类型的主键）。除 `fax` 和 `phoneNr` 标记为可选外，所有属性均为强制性。

![Fig. 8.27 Key (primary, alternate, and foreign) and optionality indicators.](img/f08-27-9780443237904.jpg)

Fig. 8.27 键（主键、备选键和外键）及可选性指示符。

在所有视图中，`relationships`（关系）仅为二元。在 ER 视图中，关系是概念关联，可能是“非特定的”（多对多）。在基于键和完全属性视图中，每个“关系”要么是“`connection`”（`外键对主键的引用`），要么是 `categorization`（`子类型链接`）。连接是子实体类型与父实体类型之间“`specific`”（特定的）（多对一）二元关联，其中每个子实体最多有一个父实体。

连接关系分为标识和非标识两种。原则上，`identifying relationship`（标识关系）是概念上用于子实体标识方案的关联。实际上，它仅仅是 `reference from a foreign key in the child’s primary key to the parent’s primary key`（子实体主键中的外键对父实体主键的引用）。

在 `nonidentifying`（非标识）关系中，子实体的 `nonkey`（非键）属性包含一个引用父实体主键的外键。

所有连接关系均表示为在子实体一端带有 `dot`“•”的命名线。`identifying`（标识）关系显示为命名的 `solid line`（实线），如 Fig. 8.28 所示。此处，`a` 和 `b` 为属性（可能是复合属性）。

![Fig. 8.28 An identifying connection “relationship.”](img/f08-28-9780443237904.jpg)

Fig. 8.28 一个标识连接“关系”。

对于标识连接，每个子实体与 `exactly one`（恰好一个）父实例关联。这是因为每个子实例在其主键中的外键都具有非空值，该值引用父实体。根据定义，子实体必须是标识符依赖的，如虚线矩形所示。除非父实体因其他关系而变为依赖，否则父实体是标识符独立的（如此处所示）。

IDEF1X 允许关系进行正向和逆向谓词读取。这些可以一起编写，如 Fig. 8.29(a) 所示，或写在关系线的不同侧，如稍后的 Fig. 8.30(a) 所示。

![Fig. 8.29 The IDEF1X schema (a) is equivalent to the ORM schema (b).](img/f08-29-9780443237904.jpg)

Fig. 8.29 IDEF1X 模式 (a) 等同于 ORM 模式 (b)。

![Fig. 8.30 Building’s primary key “migrates” to become a foreign key in Room.](img/f08-30-9780443237904.jpg)

Fig. 8.30 Building 的主键“迁移”成为 Room 中的外键。

`forward reading of a specific connection relationship is always toward the child`（特定连接关系的正向读取始终朝向子实体），因此 `toward the dot`“●”（朝向圆点）。必须提供此正向或“父实体视角”读取。如果提供了逆向或“子实体视角”读取，则朝向父实体（远离圆点）。如果两者都提供，则在正向读取后附加斜杠“/”。在 Fig. 8.29(a) 中，正向读取为 Building contains Room，逆向读取为 Room is in Building。子实体在左侧，因此正向读取为从右向左。对于非特定（`m:n`）关系，正向读取始终从左向右读取（如果关系线垂直，则从上向下）。回顾一下，`m:n` 关系仅存在于 ER 视图层级。

Fig. 8.29(b) 中等效的 ORM 图清楚地表明，关联 Room is in Building 是 Room 复合引用方案的一部分。在 IDEF1X 图中，该关联实际上是通过将 `bldgNr` 作为 Room 键的一部分来描绘的，而连接“关系”显示了外键引用。我们可以通过谈论父实体主键 `migrating`（迁移）到子实体（参见 Fig. 8.30），将 IDEF1X 讨论部分提升到概念层面。

虽然不是合法的 IDEF1X 图，但 Fig. 8.30(a) 有助于描绘 Room 部分由其房间号标识，部分由其与 Building 的关系标识。请将其与 Fig. 8.9 中的 Barker 表示法描绘进行比较。在此层级，关联 Room is in Building 是概念性的。

现在，想象 Building 的主键副本迁移以完成 Room 的主键，如 Fig. 8.30(b) 所示。此时，我们已降至逻辑层面。Room 和 Building 之间的概念关系现在由 Room 的 `bldgNr` 属性描绘。我们仍需指示该属性的任何值也必须作为 Building 的主键值出现，而这一外键引用正是连接线现在所代表的。我们移除了“关系”名称以强调这一点。现在你可以将连接线视为外键箭头。

对于标识关系，每个子实体（实例）与恰好一个父实体（实例）关联，如无装饰的实线所示。默认情况下，父实体与零个或多个子实体关联，如线端无装饰的圆点“•”所示。如果熟悉 UML，可将其视为等同于“`*`”。你可以通过用 `cardinality constraint`（基数约束）标记装饰圆点来覆盖此默认子实体基数。主要情况如 Fig. 8.31 所示，同时给出了其 ORM 对应图。此处，“P”表示正数（至少 1），“Z”表示零或 1（至多 1）。单个数字（如 3）表示恰好该数字。也可以表示范围。例如，“2–5”表示至少 2 且至多 5。

![Fig. 8.31 Main child cardinality cases for identifying relationships.](img/f08-31-9780443237904.jpg)

Fig. 8.31 标识关系的主要子实体基数情况。

要理解这些基数约束，可将其视为应用于键迁移到子实体之前存在的概念关系（外键引用上的基数约束毫无意义）。“Z”标记表示“至多 1”并不直观，在 IDEF1X[97] 中，此约束的替代表示法是使用空心圆点“◯”。

`nonidentifying relationship`（非标识关系）显示为命名的 `dashed line`（虚线）。除非因其他关系而变为依赖，否则子实体和父实体是独立的。如果虚线无装饰，则每个子实体（实例）与 `exactly one parent`（恰好一个父实体）（实例）关联，如 Fig. 8.32(a) 所示。如果在父实体端添加 `diamond`（菱形），则每个子实体与 `at most one parent`（至多一个父实体）关联，如 Fig. 8.32(b) 所示。同时也给出了相应的 ORM 图。

### 非标识关系

在非标识关系中，子实体的`nonkey`（非键）属性（即不在主键中的属性）包含一个引用父实体主键的外键。如果该外键是强制的（其每个组成部分均非空），则每个子实例恰好关联一个父实例。这被称为*强制*关系，但其真实含义是：在迁移之前产生该外键引用的概念关系中，子角色是强制的。

图 8.33(a) 更详细地描绘了这种情况。此处，`a` 和 `b` 为简单或复合属性。如果外键是可选的（其组成部分可能全为空），则每个子实例至多关联一个父实例。图 8.33(b) 描绘了这种情况。在 IDEF1X 中，这被称为*可选*关系。

![图 8.33 “强制”(a) 和 “可选”(b) 非标识 “关系”。](img/f08-33-9780443237904.jpg)

图 8.33 “强制”(a) 和 “可选”(b) 非标识 “关系”。

在强制和可选两种情况下，子实体外键的每个无空值组成部分的实例都必须作为父实体主键的一个实例出现。这是结构化查询语言（SQL）中外键约束的默认含义。当然，对于强制情况，不允许有空值组成部分。

图 8.34(a) 展示了一个强制非标识连接关系的示例。在此，每个雇员由雇员编号标识，必须有姓名，且必须为某个部门工作。每个部门由其代码标识，且必须有唯一名称。

![图 8.34 同一示例的 (a) IDEF1X、(b) IE、(c) 关系和 (d) ORM 表示。](img/f08-34-9780443237904.jpg)

图 8.34 同一示例的 (a) IDEF1X、(b) IE、(c) 关系和 (d) ORM 表示。

某雇员为某部门工作这一事实（概念关系）通过实例化 `Employee` 的 `empNr` 和 `deptCode` 属性来存储（例如 `empNr = 101`，`deptCode = "HR"`）。该连接“关系”仅是一个外键引用，指示雇员的每个部门代码必须是某个部门的部门代码。

同一示例在 图 8.34(b) 中以 IE 表示法展示，在 图 8.34(d) 中以 ORM 表示法展示。此处，关联“雇员为部门工作”被概念性地描绘，而非将 `deptCode` 作为 `Employee` 的属性包含在内。Barker 表示法也是这种情况。图 8.34(c) 以关系表示法描绘了该情况。在此，关于谁为哪个部门工作的事实存储在 `Employee` 表中，该表包含一个引用 `Department` 表的 `deptCode` 属性。将其与 图 8.34(a) 中的 IDEF1X 表示法比较，应能清楚地看出它们只是同一结构的两种符号变体。在基于键和全属性视图中，IDEF1X 表示法本质上是一种逻辑表示法，而非概念表示法。

在 ER 视图或“实体级图”中，所有实体类型均用实线矩形描绘，并允许非特定（`m:n`）关系。每条非特定关系线必须以一个点结束，该点可能带有基数标记。若无标记，则假定基数恰好为一。在转向基于键或全属性视图时，每个 `m:n relationship` 必须解析为一个带有两个 `n:1` 关系的“`intersection entity type`”（交集实体类型）。图 8.39 展示了 IDEF1X 和 ORM 中的示例。

![图 8.39 (a) 在 IDEF1X 中，`m:n` 关系必须解析为 `n:1` 关系。(b) 同一示例的 ORM 表示。](img/f08-39-9780443237904.jpg)

图 8.39 (a) 在 IDEF1X 中，`m:n` 关系必须解析为 `n:1` 关系。(b) 同一示例的 ORM 表示。

交集实体类型有时称为“`associative entity type`”（关联实体类型）。尽管概念上这对应于 ORM 中的共引用对象类型，但在 IDEF1X 中，标识属性必须被“迁移”以成为交集实体类型主键内的外键，因此交集实体类型必须是标识符依赖的，显示为虚线矩形。这种外键描绘有效地将表示层级降低到了关系层级。

尽管这种解析通常不自然，但它确实允许向曾经的关系添加属性。例如，我们可能希望为 `Play` 记录技能等级。在 ORM 和 UML 中，也可以通过简单地允许关系被对象化（作为对象化关联或关联类）来实现这一目标，但 IDEF1X 不允许这种概念替代方案。

如果 *m:n* 关系是环关联，则可以在迁移外键的名称前加上角色名以区分它们。例如，在 图 8.40(a) 中，角色名“subPartNr”和“superPartNr”被加在“partNr”前面，以消除 Containment 主键属性的歧义。

![图 8.40 角色名可用于 (a) IDEF1X 和 (b) ORM。](img/f08-40-9780443237904.jpg)

图 8.40 角色名可用于 (a) IDEF1X 和 (b) ORM。

虽然 IDEF1X 标准在角色名后使用点号，但某些 CASE 工具不支持这种点号表示法。不过，仅使用角色名（例如，用“subPartNr”代替“subPartNr.partNr”）即可轻松实现区分，无需点号。无论哪种情况，角色名都应显示为名词短语，即使不附加被引用主键的名称也能识别该属性。在 ORM 中，对这种情况建模更自然的方式是将包含关联对象化，如 图 8.40(b) 所示。

在 IDEF1X 中，实体类型可分类为一个或多个互斥的*类别*（子类型）簇。超类型称为*泛型*实体（类型）。每个子类型继承其超类型的主键，因此是标识符依赖的。子类型联系称为“*分类关系*”。

与 ORM 子类型相比，这种子类型版本受限得多。ORM 子类型允许“簇”内有重叠类型，以及上下文依赖引用。实际上，IDEF1X 的子类型方法将实体类型视为表，“分类关系”仅仅是外键引用。相比之下，ORM 子类型纯粹是概念性的，在实现时可选择不同的映射策略（参见 第 11 章）。

然而，IDEF1X 的子类型方法有两个方面表达的不仅仅是简单的外键引用。它们是完整性声明和判别器声明。子类型联系显示为一条线，在超类型端有一个带下划线的圆圈。*单下划线*表示该簇是*不完整*的（即，超类型不仅仅是其子类型的并集）。这意味着超类型的实例可能包含不属于其任何子类型的实例。

例如，在 图 8.41(a) 中，子类型 TallPerson 和 ShortPerson 互斥，但不详尽。一个人可能是中等身高，而不被归类为高或矮。与 IDEF1X 相反，ORM 常使用派生子类型，必须根据其超类型所扮演的角色来定义。图 8.41(b) 显示了在 ORM 中建模这种情况的一种方式。

![图 8.41 (a) IDEF1X 和 (b) ORM 中的不完整且互斥的子类型簇。](img/f08-41-9780443237904.jpg)

图 8.41 (a) IDEF1X 和 (b) ORM 中的不完整且互斥的子类型簇。

这里，一个人的身高用于确定他或她是否属于 TallPerson 或 ShortPerson。子类型定义和 Height 上缺乏值约束表明这些子类型是互斥但不详尽的。这也可以通过显式的隐含排除约束来描述。作为使用身高的替代方案，可以将可选且互斥的一元角色“是高个子”和“是矮个子”附加到 Person，并提供显而易见的定义。

在 IDEF1X 中，超类型端的*双下划线*表示该簇是*完整*的。这意味着超类型是其子类型的并集。由于 IDEF1X 簇的成员也是互斥的，这意味着我们有一个分区。例如，在 图 8.42(a) 中，Person 被分区为 MalePerson 和 FemalePerson。

![图 8.42 (a) IDEF1X 和 (b) ORM 中的完整、互斥子类型簇。](img/f08-42-9780443237904.jpg)

图 8.42 (a) IDEF1X 和 (b) ORM 中的完整、互斥子类型簇。

超类型的一个强制属性可用作*判别器*，并写在圆圈旁边以指示子类型划分的依据。例如，在 图 8.42(a) 中，`gender` 被用作判别器将 Person 分类为 MalePerson 和 FemalePerson。相应的 ORM 模式如 图 8.42(b) 所示。此处显式显示的分区约束由子类型定义和其他约束隐含。

好了，这基本涵盖了 IDEF1X 表示法。虽然它是一种广泛使用的标准，特别是在国防工业中，但我们发现它不如 Barker 或 IE 表示法适合概念建模。要在 IDEF1X 中捕获任何细节甚至基本约束，必须将模型解析为本质上是关系模型的东西。此外，IDEF1X 的概念集及其表示法不必要地复杂且难记。对于概念分析和验证，它还受制于基于属性方法的弱点。
