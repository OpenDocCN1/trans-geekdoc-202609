### 将流程与数据关联

我们已经了解了如何在概念层面（例如使用 ORM 模式）和逻辑层面（例如使用关系模式）指定数据模型。整体信息系统生命周期还包括其他任务，详见第 2 章。第 15 章讨论了如何使用 UML 和业务流程模型与符号（BPMN）来指定业务流程。本节简要概述其他设计任务，例如将流程与数据关联、组织大型模型以及指定用户界面。

假设我们需要为一家信用合作社运营的自动取款机（ATM）设计一个信息系统。作为需求分析阶段的一部分，我们确定该系统的四个主要功能是：允许客户进行存款、取款和转账（例如从储蓄账户转至支票账户），以及获取账户余额打印单。在 UML 中，这些功能中的每一个都可被视为一个用例，并包含在用例图中，以提供系统支持的流程概览。然后，我们可以使用 UML 的活动图集或 BPMN 的工作流图来充实这些功能。

假设当客户将信用卡插入 ATM 时，系统会检查该卡是否为其自有卡，如果是，则从卡中读取客户的标识符（客户编号）。同一个账户可供多个客户使用（例如夫妻共同的联名账户），而每个客户都有唯一的客户编号。这样，系统就能追踪究竟是哪位客户进行了任何特定交易。

假设在绘制 `ValidateClient`（验证客户）和 `GetBalance`（获取余额）流程图时，我们发现验证客户并打印所请求余额的组合流程涉及来自客户的两个输入数据流（`clientNr`、`accountType`）和一个输出数据流（`balance`）给客户。如果将信用合作社的账户数据库系统视为独立于 ATM 的另一个参与者，则可认为它响应从 ATM 发送的请求（例如 SQL 查询）来提供余额详情。

在如此高层级的视图中，很少或不提供关于数据存储结构的细节，也不提供关于流程如何找到相关数据的细节。由于这些细节尚未定义，流程图往往无法为数据视角建模提供充分的基础。尽管存在这种非正式性，它们在阐明论域（UoD）以及识别应包含在应用程序屏幕菜单中的功能方面仍很有用。确实，带有直观图标的普通漫画在需求分析的早期阶段，对于建模者与领域专家之间的沟通非常有用。

原则上，流程模型可以逐步细化为基本事务，从而暴露底层的事实类型。然而，对于数据密集型系统，这种方法实在太耗时，且往往不稳定，因为业务流程的变化速度通常远快于底层数据。为了加快数据建模进程，我们应该用数据用例为其播种，并应用诸如 ORM 概念模式设计程序（CSDP）之类的建模程序。如果已有示例，请使用它们。如果没有，请与领域专家坐下来生成它们。这些可以是表格、表单、图表或任何形式。到现在为止，你应该已具备口语化技能，能够妥善地对这些各种形式执行 CSDP 步骤 1，而且由于客户发现实例层面更易于处理，这是最稳妥的途径。此外，这样做你已经开始原型化客户想要的外部屏幕和报表。

流程模型应正式地连接到数据模型。最好在确定概念和逻辑数据模型之后进行此操作。虽然熟练的建模者可以将流程模型细化为数据模型，但这种方法容易出错。例如，假设我们跳过概念数据建模，转而将前面提到的用于验证客户和获取余额的流程模型细化为以下表方案和 SQL 过程。这里，“&1”和“&2”是输入参数或占位符。执行过程时，实际值会被输入到这些参数中。

```
D1: Account ( clientNr, accountType, balance )
P1: select balance from Account where clientNr = &1 and accountType = &2
```

你能发现这个设计潜在的问题吗？如果你为 D1 绘制一个概念模式，就最容易看出问题。这在图 18.13 中有描绘。每个账户有一个或多个用户，且恰好有一个账户类型（例如 L = 贷款，C = 支票账户，S1 = 主储蓄账户，S2 = 其他储蓄账户）。这没问题。问题在于 Account 的标识方案。虽然 `clientNr` 和 `accountType` 的组合确实能在该论域中标识一个账户，但不应将其用作优先参考，因为（`clientNr`、`accountType`）对与账户的关系不是 1:1 的。

![图 18.13 账户的优先参考方案不安全。](img/f18-13-9780443237904.jpg)

图 18.13 账户的优先参考方案不安全。

例如，假设你配偶的 `clientNr` 是 1001，你的是 1002，你们共享一个主储蓄账户（类型 = “S1”）。这个联名账户既可由（1001，“S1”）引用，也可由（1002，“S1”）引用。这不适合优先参考。例如，D1 使用的 `Account` 表将接受填充数据 {(1001, “S1”, 9000), (1002, “S1”, 0)}。但这意味着同一个账户有两个不同的余额，这说不通。显而易见的解决方案是引入另一个优先标识符（例如 `accountNr`），如图 18.14 所示。该图还包含新的关系模式（D1′）和计算余额的新过程（P1′）。

在实践中，通过检查与该用例或会计系统相关用例（例如余额单）关联的其他数据示例，应该显而易见地发现应使用 `accountNr` 进行优先参考。正如第 5.3 节所讨论的，在特定上下文中的参考方案可能不适合全局应用。在与领域专家讨论数据用例时请记住这一点。

虽然严谨的流程模型最好建立在数据模型之上，但流程概览作为数据建模的前驱很有用，特别是当应用程序很大或仅被模糊理解时。首先弄清应用程序的功能通常很有帮助。

从总体目标出发，可以使用各种图系统地指定应用程序的主要功能和流程。这种分析有助于我们将论域划分为大小可控的连贯模块，并有助于在不存在信息示例时指定它们。此时，可对每个模块应用 CSDP 步骤 1。

### 外部模式与用户界面

现在可以为各类用户开发外部模式。正是通过用户与外部接口的交互，需求分析阶段指定的原始功能最终得以执行。因此，以自然反映这些功能的方式设计外部接口非常重要。

从根本上说，用户与信息系统交互时发生的一切，无非是基本事实的添加、删除、检索或推导。原则上，我们可以用这两种更新和两种查询操作来规定进程视角。但这对人类来说粒度太细，无法高效处理。

我们需要一种将这些基本操作分组为更大单元的方法。将操作视为作用于重要`对象`（如患者和库存项）上，这通常很自然。从 ORM 模式抽象出的主要对象类型（见前一节）与这些对象类型紧密对应，因此为定义操作提供了良好的基础。UML 类图或 ER 图中更重要的类或实体类型为此提供了另一个很好的选择。

现在可以生成一组通用的外部更新操作，包含三种变体：添加对象、删除对象和修改对象。可以生成一些通用查询操作（例如，列出关于某对象的所有事实），但特定查询需要对相关事实类型（存储的或推导的）进行适当选择。

用户通过`外部接口`执行此类操作，通常是`屏幕`表单或菜单。对于每个屏幕，我们需要考虑 `content`（包含哪些事实类型和操作）、`format`（屏幕如何显示）和 `use`（用户如何调用操作）。如前所述，关于屏幕内容的默认决策可以基于主要对象类型上的操作。例如，如果 Patient（患者）是医院系统的主要对象类型，则需要一个针对它的屏幕，至少包含添加 Patient、修改 Patient、删除 Patient、显示 Patient 等操作。

与概念表和逻辑表不同，表单在内容上可能重叠。外部层级的这种冗余方便地允许用户在相关时执行操作，而无需切换屏幕。例如，考虑 *m:n* 事实类型 Doctor treated Patient（医生治疗患者）。在使用 Doctor 屏幕时，我们可能会查询该医生治疗了哪些患者。在使用 Patient 屏幕时，我们可能会查询哪些医生治疗了该患者。在概念模式和逻辑模式中，此类事实仅存储一次。只要外部屏幕已正确关联到底层数据结构，这种重叠就是安全的。关于使用 ORM 模式生成屏幕表单和事务的讨论，请参见 Campbell and Halpin (1993)。

#### 访问权限

尽管一个应用程序只有一个（全局）概念模式，但可能有多个外部模式。不同用户组可能具有不同的`授权`级别，可在`访问权限表`中指定。这可以在概念层面完成（例如，对于每个事实类型，哪些组拥有读、添加、删除权限），也可以在逻辑层面完成（例如，对于每个表或列，哪些组拥有读、插入、删除、更新权限）。

关于屏幕表单上选项的访问，通常最好仅向用户显示他们被授权选择的选项。像往常一样，屏幕选项的访问权限最好作为表中的数据进行软编码，而不是在过程中硬编码。这避免了在访问权限更改时重新编译表单，并简化了通用代码的重用。作为整体安全性的一部分，需要密码，并赋予用户更改其密码的权限。

#### 人机交互设计

除了访问权限，用户在`能力`级别上也可能存在差异。设计应用程序屏幕以优化各类用户执行任务的方式，是`人机交互（HCI）设计`的一个重要方面。

可使用多种类型的接口。例如，与用户的对话可以使用自然语言、简短问题、命令行、菜单、表单、表格、图表、图像或声音。输入设备包括键盘、鼠标、操纵杆、触控笔和麦克风。

### 用户界面设计原则

一般来说，用户界面应该`易于学习`且`易于使用`。为实现这一目标，界面应具备一致性、简洁性、结构化、高效性，并能适应用户。下面我们逐一探讨这些原则。

#### 一致性

界面的`一致性`意味着所有组件在显示格式和操作方面均采用相同的基本约定。这有助于正向迁移（学会使用一个屏幕有助于使用其他屏幕），并避免负向迁移。一致性可在不同层面实现，例如单个屏幕内部、应用程序内部、同一公司开发的不同应用程序之间，以及与外部标准的一致性。例如，如今许多 Windows 应用程序的开发均遵循微软的用户界面指南。

#### 简洁性

界面的`简洁性`意味着其使用直观，用户付出的精力最少。每个屏幕应提供适量的相关信息（例如，限制一次显示的菜单选项数量）。不要让屏幕显得杂乱。为允许从同一屏幕直接执行许多操作，应从永久屏幕显示中移除除主要选项外的所有选项，允许用户根据需要切换额外选项的显示。例如，使用下拉菜单、弹出窗口（如用于查找代码）和状态栏帮助（及弹出式详细帮助）。为便于在屏幕内部及屏幕之间导航，可考虑使用方向键进行移动，并允许窗口和菜单以层叠或平铺方式排列。

#### 高效性

界面的`高效性`意味着选项可被快速且直观地选择。`图形用户界面`（`GUI`）提供了更直观的操作方式，尤其是在涉及图形或复杂布局时；此时，“所见即所得”（WYSIWYG）至关重要。不过，基于按键的快捷方式（如热键）有时更快，应为经验丰富的用户提供。

菜单设计对高效性有重大影响。菜单形式多样（全屏、下拉、弹出、环形、按钮栏等）。它们提供了应用程序绝大多数（甚至全部）操作。同一菜单上的选项应在语义上相关。

菜单或屏幕之间的导航需要规划（状态图在此有帮助），特别是对于使用超链接从一处导航到另一处的基于 Web 的应用程序。图 18.18 展示了一些导航模式。超链接访问通常是循环的。

![图 18.18 菜单或屏幕之间导航的几种方式。](img/f18-18-9780443237904.jpg)

图 18.18 菜单或屏幕之间导航的几种方式。

此外，还应遵守以下原则：

- 按使用频率递减的顺序排列菜单选项。
- 变化颜色和字体，但切勿过度。
- 对于选项，使用直观的图标或简洁明了的文字描述，文字描述多为小写。
- 允许通过鼠标点击或热键选择选项，并支持撤销操作。

#### 适应性

按如下方式使界面`适应`用户：

- 仅显示与用户相关的内容。
- 为普通用户提供简单流程，为经验丰富的用户提供快捷方式。
- 允许用户根据自己的喜好配置环境。
- 提供分级的上下文敏感帮助：状态栏上的简短消息，弹出窗口中的详细帮助。
- 尽早捕获错误，并给出简短和详细的错误消息。
- 提供在线教程、用户手册、技术支持和培训课程。

如果你使用某些觉得特别直观的软件包，请仔细观察其界面设计，看看能否将其优点应用到你自己的设计中（前提是不侵犯版权！）。一旦开发出原型界面，让典型用户测试，并利用他们的反馈进行润色。

以上快速浏览了几个主题，每个主题本身都足以写成一本书。确实，有许多专著专门论述界面设计；针对建模过程存在许多改进方法，包括一些非常技术性的方法，试图将这些模型与数据模型正式集成。章节注释中引用了一些这方面的有趣工作。对于项目管理（如甘特图和 PERT 图）、测试、性能度量、文档和版本控制等相关任务，也有各种常用的方法和工具。

## 18.6 本体与语义网

从词源学上讲，“本体论”一词意味着对存在的研究。在哲学中，本体论是形而上学的一个分支，关注存在的基本性质，探讨诸如“非物质事物存在吗？”、“事物在变化时是否保持与自身同一？”等深刻问题。信息学界后来采用了“本体”这一术语，通常用其指代关于某个业务领域的概念模型，该模型通过遵循某组标准构造，促进该领域信息的共享。

随着互联网的兴起，数百万文档现可通过万维网轻松访问。2001 年，为简化不同 Web 文档中信息的共享或组合，互联网创始人蒂姆·伯纳斯-李爵士提出了`语义网`的新愿景，作为当前 Web 的延伸，“在其中信息被赋予明确定义的含义，从而更好地使计算机和人能够协同工作”(Berners-Lee 等, 2001)。主要思想是为文档添加全局标识符和结构（例如使用统一资源标识符和嵌入式标签），以一种自动化代理可访问的方式揭示待共享内容的底层语义。

1999 年，万维网联盟 (W3C) 发布了`资源描述框架` (RDF) 语言的第一个版本，作为构建在 XML 之上的标准，用于捕获 Web 资源的元数据（例如，谁编写了某个 Web 文档）。美国国防高级研究计划局 (DARPA) 通过标记标签为语言添加自动可访问含义的其他工作，产生了 DARPA 代理标记语言 (DAML)。怀着类似目标，欧盟 (EU) 的研究人员开发了本体推理层 (OIL)。2001 年，美国和欧盟的联合工作将 OIL 的许多概念合并到 DAML 中，形成了 DAML+OIL 语言，并于 2002 年底提交给 W3C。
