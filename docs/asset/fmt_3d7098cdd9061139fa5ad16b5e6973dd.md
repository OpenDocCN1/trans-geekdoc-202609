从代码审查的角度来看，我们对`printf`命令感兴趣，因为它没有检查输入的长度。如果使用`printf`命令来打印用户提供的数据，我们看到的将是一个可能的利用漏洞（缓冲区溢出）。从逆向工程的角度来看，我们可以识别出数据被推入内存（`$0x80484c4`）而没有经过任何缓冲区长度检查。不过，我们实际上需要某种方法来修改该缓冲区——目前程序没有包含用户输入。如果我们包含允许用户添加信息的方法，就可能进行缓冲区溢出攻击。外部资源可以帮助你更好地理解在渗透测试中使用逆向工程的力量。这是一个缓慢的过程——比代码审查还要慢。

## Web 黑客攻击

一种非常流行的攻击向量是针对 Web 网站的。在外部渗透测试中，通常可用的应用程序是 Web 服务器，因为防火墙被配置为限制任何通信。Web 攻击在成功时效率非常高；大量数据与购物相关。现在有很多工具可以协助 Web 黑客攻击；然而，我们将以相同的方式开始——手动操作。在本节中，我们讨论了两种最流行的攻击：SQL 注入和 XSS 攻击。我们还从高层次讨论了 Web 应用程序攻击，因为我们已经演示了一个 Web 应用程序（章节开头的 Webmin 漏洞）。为了演示这些利用程序，我们将使用较好的训练应用程序之一——`WebGoat`，它由开放 Web 安全项目（`OWASP`）支持。你可以在 [www.owasp.org](http://www.owasp.org) 找到关于`WebGoat`项目的信息。为了方便起见，DVD 中包含了`WebGoat` 5 版本。

## SQL 注入

根据 NIST 特别出版 800-95，SQL 注入是一种“用于操纵 Web 服务并向 RDBMS [关系型数据库管理系统] 发送 SQL 查询以更改、插入或删除数据库中的数据的方法”。换句话说，是时候学习构建数据库命令了。`WebGoat`提供了一些背景信息，但不足以真正理解和编写必要的语法。有很多书籍可以帮助填补你在 SQL 语法方面的任何知识空白，但接接的示例并不复杂，应该易于理解。如果使用后端数据库的应用程序对用户输入进行了适当过滤，SQL 注入将无法运行；然而，SQL 注入发生的频率比应该的要高。通过`WebGoat`，我们可以看到 SQL 注入是如何工作的——在图 11.44 中，我们可以看到尝试登录 Tom 的结果。不幸的是，登录失败了。看起来数据库中没有姓“Tom”的人。我们可以尝试使用一堆名称进行暴力破解，或者尝试让后端数据库把它知道的一切都给我们。

在本挑战中，提供给我们的提示之一（如图 11.44 所示）是数据库查询的工作原理：`SELECT * FROM user_data WHERE last_name =‘Tom’`。一旦我们学会了正确的数据库命令是什么样的，就会知道以下命令应该给我们所有内容：`SELECT * FROM user_data WHERE last_name = ‘Tom’ OR ‘1’ = ‘1’`。我们通过新命令告诉数据库的是：显示与用户`Tom`关联的`user_data`……或者因为`1 = 1`而给我们所有内容（数据库只有在查询语句为真值时才会返回信息。当我们只查找`Tom`且没有找到姓氏为`Tom`的用户时，它会返回假，意味着我们没有收到任何信息。`OR 1 = 1`语句强制数据库查询被解释为真，从而提示数据库向我们提供`user_data`中的所有内容）。利用这些知识，我们可以修改输入，使数据库接收到完整的字符串。在图 11.45 中，我们看到已成功将数据库命令注入应用程序中，并获取了数据库中所有用户的信用卡信息。

尽管 SQL 注入和 XSS 攻击可以获取数据，但与外界交互的应用程序也可能受到漏洞利用。本章开头提到的 Webmin 漏洞就是 Web 应用程序漏洞的完美示例。如果我们查看漏洞代码本身，会发现该技巧在于向 URL 中注入额外的字符——换句话说，就是缓冲区溢出……这是一个常见但危险的错误。在寻找 Web 应用程序的利用程序时，我们只需遵循本章开头提到的相同流程：

1. 识别运行在端口上的应用程序（Web 应用程序通常使用`80`或`443`端口，但不要局限于这些端口——高位端口上有许多管理类 Web 应用程序）。

2. 查找版本信息（如果可能的话）。

3. 在互联网上寻找漏洞。

4. 针对目标应用程序运行漏洞。同时，确保使用多个工具来识别应用程序。正如我们在第 10 章中所所示，横幅信息（banners）可能是错误的。

那么，Web 应用程序中具体存在哪些类型的漏洞呢？大部分我们已经涵盖过了，但根据 OWASP 标准，这些是前 10 大攻击向量：

*   跨站脚本（在 WebGoat 中演示）

*   注入缺陷（包括 SQL 注入）

*   恶意文件执行（通常涉及向服务器上传恶意且未经检查的程序；例如“PHP 远程文件包含”漏洞）

*   不安全的直接对象引用（与 Webmin 任意文件披露漏洞类似）

*   跨站请求伪造（一种针对受害者浏览器的攻击）

*   信息泄露和不当错误处理（类似于 Nessus 在扫描 pWnOS 服务器后识别的`/php` Web 目录）

*   破坏身份验证和会话管理（会话劫持，如 WebGoat 所示）

*   不安全的加密存储（这纯粹是应用程序设计不当，当程序员没有使用最佳形式的加密或错误地实现了加密时）

*   不安全的通信（包括在网络上以明文形式发送用户名和密码，网络分段上的监听者可以捕获数据）

*   未能限制 URL 访问（更多是编程不当，导致恶意用户可以绕过登录安全措施）

在进行渗透测试时，我们需要寻找所有这些漏洞。在检查了前 10 名列表后，大多数可以归类为配置错误或不当的编码实践。你会发现，大约 90% 的成功利用将源于配置错误——其余 10% 是由在`CORE IMPACT`等应用程序中发现的、或在 [www.milw0rm.org](http://www.milw0rm.org) 上提供的公开漏洞。还有一些自动化工具在分析和利用 Web 应用程序漏洞方面非常有效。`CORE IMPACT`已将 XSS 和 SQL 攻击加入了其 RPT 产品中。另一个强大的工具是惠尔惠开发公司提供的`HP WebInspect`。它也是一个商业产品，我也用过，发现它在分析 Web 应用程序非常有用。也有一些免费解决方案，包括`Nikto`和`Paros Proxy`。

# 项目管理

如前所述，我们仍然处于执行过程组——具体来说是在“指导和管理项目执行”过程中。前两个章中提供的关于执行过程以及指导和管理项目执行的信息仍然适用于渗透测试项目的这一阶段。

## 执行过程阶段

随着渗透测试“漏洞验证”阶段的启动，我们深度参与了执行过程阶段。根据发现，漏洞验证可能仍需要对分配的资源进行修改，包括人员和测试系统。资源压力最大的时刻是从目标中提取出新信息并揭示新漏洞时。为了减少这些发现对项目整体成功的影响，通信承担了更为关键的角色。

### 信息分发

通信计划是“信息分发”和“管理利益相关者”过程中最重要的输入。虽然信息分发对于渗透测试的所有阶段都至关重要，但在漏洞验证阶段更是如此。期间渗透测试团队面临着负面影响系统的最大风险；因此更新、验证和确认通信计划至关重要。信息分发关注几个不同方面，包括在正确的时间将正确的信息交给正确的人。对于渗透测试项目，通信计划受影响最大的需求包括利益相关者通信需求（下文讨论）、负责传递信息的、通信方式（电子邮件、电话等）以及升级流程。由于渗透测试的这一阶段可能涉及高成本和时间敏感的事件，请确保与紧急情况相关的通信项目包含反映渗透项目敏感性的通信计划。

# 漏洞验证

漏洞验证主要涉及识别目标系统、应用程序和网络设备中的配置错误。在所有已验证的漏洞中，只有约 10%是已发布漏洞利用的结果。由于工程师在渗透测试任务的“漏洞识别”阶段无法识别所有潜在漏洞，项目经理必须为渗透测试项目的这一阶段分配额外时间。如果能为未发现的漏洞提供一个大致的时间估算那就太好了，但影响所需长度的因素太多，在不预先知道这些因素的情况下，这是无法可能的。这些因素包括目标系统或网络的规模和复杂性、目标与外部系统之间的信任关系、渗透测试团队的技能水平及其与目标的相关性等。与渗透测试团队沟通是衡量该阶段应分配多少时间的最佳方式。范围蔓延（scope creep）问题之前提到过，但通常是从客户发起的范围变更角度来看。在漏洞验证阶段，扩大项目范围的压力来自于渗透测试团队内部。在充足的时间、精力和资源的情况下，渗透测试团队理论上可以破解任何系统。渗透测试项目经理将面临在项目此阶段将渗透测试团队限制在规定时间内的挑战，仅仅因为渗透测试团队往往接近实现额外的漏洞利用。项目经理会被那些对渗透测试最终报告产生积极影响的漏洞利用承诺所诱惑。是否为此阶段分配额外时间，应该与额外的攻破对目标系统和/或网络整体安全态势的实际影响进行仔细平衡。通常，额外的漏洞利用不会增强利益相关者对目标安全状况的理解。然而，在某些情况下，允许渗透测试团队获得额外时间可能是客户或高层的转折点。与渗透测试团队及利益相关者的有效沟通有助于确定采取最佳方案。

## 管理利益相关者

项目经理负责利益相关者管理。理解利益相关者的需求、目标和目的，并促进满足这些需求、目标和目的所需的沟通水平，是项目经理职责。当渗透测试团队开始对跨网络系统发起攻击时，利益相关者的沟通需求会剧增。对他们需求的响应时间应以分钟计，而不是小时或天。在系统崩溃的最坏情况下，工程师必须立即停止活动，并对他们在崩溃前做什么提供极其详尽的信息，甚至细到在什么时间按了哪些键。这就是为什么在渗透测试期间向工程师强调日志的必要性至关重要。问题日志在渗透测试的这一阶段非常有帮助。通过对所有问题进行注释并监控它们的解决情况，项目经理可以跟踪发生了哪些问题，以及为了修复问题做了哪些工作。未能解决问题可能会导致冲突和延迟。

## 总结

在本章中，我们跨越了审计工作与专业渗透测试人员预留工作之间的界限。通过利用我们的目标系统，我们能够验证审计项目只能预测的漏洞。大众有大量关于漏洞验证的书籍和在线教程供选择。然而，重要的是，在专业的渗透测试中，有许多外部因素影响着我们使用什么工具以及何时使用。项目范围可能会将你的攻击限制仅限于那些非破坏性的攻击。虽然这降低了系统崩溃的概率，但它并没有对目标安全态势提供全面的分析。此外，渗透测试项目始终存在时间限制，这迫使项目经理挑选哪些渗透测试任务可以尝试，以及持续多久——项目经理很少有奢侈让工程师完全放主性。由于这些限制，使用自动化工具和对范围变更进行严格控制是必不可少的。自动化工具的分析可能是错误的。工具可能会错误识别应用程序，导致遗漏利用机会。尽可能验证发现的结果。这并不意味着手动方法也是识别漏洞的最佳方法。模糊测试（Fuzzing）和暴力破解工具执行的操作在专业渗透测试中是人类无法完成的。总结一下：任何兴趣成为专业渗透测试人员或需要管理渗透测试项目的人，必须密切熟悉漏洞验证的所有方面。渗透测试人员不能仅仅依靠工具来识别和利用目标系统或网络上的所有漏洞。是的，工具可以加速进度，但工程师必须理解这些工具的优点和局限性。几，公司还满足于简单的 Nessus 扫描来建立安全态势基准。行业已经从那时走了很远，现在需要具备知识的工程师和项目经理深入研究其架构，因为公司知道这正是恶意用户正在做的。遗憾的是，执行专业渗透测试人员任务所需的知识仍在不断增长。对于刚进入该领域的人来说，有很多需要追赶的。这本书只是一个起点——只需确保在过程中完成所有的练习即可。对于那些已经在领域内工作了一段时间的人，你们会同意：学得越多，知道的越少，而且总有我们学得不够充分的东西。我们查看了数据库攻击、Web 攻击、应用程序攻击、编码实践、缓冲区溢出等。我们只触及了在所有可能情况下要求的表面。对于那些想要避免不断学习的人来说，渗透测试领域可能是一个糟糕的选择。对于那些想在渗透测试领域追求职业的人来说，他们发现这是一个令人兴奋且充满持续挑战的。

## 漏洞代码 – 寻找与运行

- 在使用任何漏洞之前，确保你查看并理解了其所有部分。

- 始终使用至少两个工具来验证任何发现。

- 自动化工具可以节省时间，但需要验证发现结果的准确性。

- 使用任务所需的工具——不要让资金成为问题。

- 由于系统崩溃的风险增加，一个强有通信计划至关重要。

- 范围蔓延（Scope creep）是项目此阶段的一个问题——如有必要，请确定未来项目中应调查的领域，然后继续进行。

**Q：** 寻找可用漏洞程序的好来源是什么？

**A：** 本章提到了 [www.milw0rm.org](http://www.milw0rm.org) 是许多漏洞程序的存储库，通常是一个极佳的起点。Metasploit 框架也包含许多漏洞程序。当这两个来源都没有你需要的内容时，开始在互联网上寻找。许多安全专家仅在他们的个人网站上发布漏洞程序。

**Q：** 我下载的漏洞程序不起作用——我该怎么办？

**A：** 通常情况下，漏洞程序是针对特定的操作系统和语言包编写的。不同的系统通常需要不同的漏洞利用方法。可能该漏洞程序是有效的，但需要重写以适应目标操作系统的版本。

**Q：** 在渗透测试的这一部分，防止范围蔓延的最佳方法是什么？

**A：** 要完全理解网络或系统中安全威胁的全貌几乎是不可能的，因此几乎总会有新东西需要追求。根据工程师的反馈，新发现的漏洞可能产生不足以继续追求的结果。然而，该漏洞仍应在最终报告中提及，并在未来的渗透测试中进行检查。项目开始时定义良好的范围将帮助项目经理了解何时越界了，并需要实施控制措施以防止项目无限扩张。

**Q：** 你建议使用哪些额外的学习工具来更好地学习 Web 黑客、逆向工程、模糊测试（fuzzing）等？

**A：** 有许多致力于这些主题的网站，可以对执行渗透测试所需的技术提供良好的理解。然而，这些主题属于高级内容，自学需要花费大量时间。对于专业的渗透测试人员，我强烈鼓励他们参加专业的培训课程并获取有关主题的最新书籍。合格的培训课程和行业认可的书籍是获取信息的更快方法，而在这一行业，时间就是金钱。
