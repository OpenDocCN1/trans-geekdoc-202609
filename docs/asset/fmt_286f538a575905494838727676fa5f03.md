
# 组织必须在有限的审计资源与持续产生的日志数据供应之间取得平衡

能够汇总甚至绘制该日志数据图表的软件工具是管理员极佳的生产力工具。

为了缓解监控和审计操作给网络安全团队带来的压力，许多`安全编排、自动化和响应 (SOAR)`工具已进入 IT/OT 安全市场。这些是使组织能够自动化和标准化其安全运营和事件响应活动的软件工具。

这些安全工具收集安全数据，以识别、分析和应对来自不同攻击向量的威胁和漏洞。它们被设计为与网络中的其他安全工具协同工作，以检索和分析网络生成的安全信息。信息安全团队将称为`剧本`的工作流指令集构建到 SOAR 中，以自动化其许多安全运营，从而减少重复性任务。

这类安全工具依赖人工智能和机器学习来自动化和微调组织的日常安全任务。可用的领先 SOAR 工具示例包括 `Splunk Phantom`、`IBM Resilient`、`DFLabs IncMan`、`Insightconnect`、`RespondX`、`Exabeam`、`ServiceNow` 和 `SIRP`。

# 事件日志记录

**事件日志记录**是指记录网络设备、服务器、客户端和智能网络连接设备的操作系统所执行的系统事件。操作系统日志通常记录各种不同类型的系统信息。其中相当一部分数据与管理和合规功能相关。

在讨论操作系统时，**审核**一词用于描述操作系统的一项安全功能，该功能支持将在计算机上执行的用户和操作系统活动记录在日志中（进行监控和跟踪）。然后可以使用这些信息来识别或分析潜在的不良活动，例如未经授权的入侵尝试。事件日志记录是在本地计算机层面设置的，而审核则是在服务器层面建立的。

在网络安全设备/系统识别出可疑活动后，通常会使用操作系统日志从特定设备获取更多信息。对于这些活动，需要考虑两种常见的操作系统审核记录类型：

*   **原生日志记录**—大多数现代多用户操作系统生成的事件记录。由于这些记录已由操作系统生成，因此始终可用，但它们可能不包含所需的事件，或不是易于使用的形式。
*   **检测专用审核记录**—为提供有关所需操作或事件的特定信息而生成的记录。这些操作或事件可以基于操作系统活动、应用程序事件或安全事件。

大多数操作系统可用的审核系统由两个主要组件组成：**审核策略**（或**审核规则**），它定义将要监控并添加到系统**安全日志**中的事件类型；以及**审核条目**（或**审核记录**），它们由发生受审核事件时添加到安全日志中的各个条目组成。系统管理员实施审核策略。

事件日志管理是监控 IT/OT 网络最重要的方面之一。在操作系统层面，`Windows 事件查看器`或 `Linux 安全审核框架`等简单实用程序为事件监控活动提供了第一道防线工具。

## Linux 审核

Linux 系统还具备安全审核功能，用于跟踪指定的安全事件。图 10.5 提供了 Linux 安全审核框架的通用表示。与其他审核系统一样，Linux 模块将计算机进程映射到用户 ID，以便管理员能够将攻击准确追溯到拥有该进程并在系统中执行潜在恶意活动的用户。

![FIGURE 10.5 Linux auditing system](img/c10f005.png)

**图 10.5** Linux 审核系统

系统的核心是**审核守护进程**，它与 Linux 内核的审核模块协同工作，记录相关事件并将其写入磁盘上的日志文件。审核规则在系统启动时执行的文件中进行配置。审核控制器实用程序使用这些规则中的参数来确定跟踪哪些系统事件以及如何将它们写入**审核事件日志文件**。

当应用程序遇到触发预配置审核事件的情况时，一条消息会呈现给内核的审核接口并传递给审核控制器。在审核控制器的指导下，审核守护进程将事件写入审核事件日志。

Linux 审核系统还包括一个报表生成工具，管理员可以使用它来生成自定义安全报表。它还可能包含一个搜索实用程序，以便快速/专门地检查特定事件的日志条目。

与 Windows 组策略配置一样，您必须考虑希望 Linux 审核系统在主机上执行的审核级别及其运营后果。

有一个非常优秀的审核工具可用于 Linux 和 MAC 系统，称为 `Lynis`。该工具可以从 GitHub 下载并安装在 Linux 平台上。安装并配置 Lynis 后，它可以扫描系统并提供报告、警告和缓解系统漏洞的建议。其他著名的审核工具包括 `Qualio`、`AuditBoard`、`Hyperproof`、`Onspring`、`Audit Prodigy`、`Audits Management Software`、`HighBond`、`Standard Fusion` 和 `Benchmark ESG`。

## 网络日志记录

来自网络设备（如托管交换机、路由器、防火墙和无线接入点）的日志，以及分布在整个网络中的 NSM 程序的日志，都可能包含与安全相关的信息。网络管理员主要将这些类型的日志用于管理和审核，而安全管理员则更关注来自不同来源的安全日志，以维护组织的网络安全目标。

# 安全日志记录

**安全日志**用于跟踪通过设备审核策略配置指定的安全相关活动或事件。虽然安全日志的配置主要是为了存储计算机安全信息，但还有许多其他日志（如操作系统日志和应用程序日志）通常也包含一些与安全相关的信息，以及各种其他事件文档。

审核条目保存在安全日志中，管理员可以查看。为了使审核成为有效的安全工具，应定期审查和归档安全日志。

组织通常运行多种基于主机和基于网络的软件工具来生成安全日志数据。最常见的软件类型包括但不限于以下各项（每个项目记录的内容不限于所述内容）：

*   **反恶意软件**—这些工具通常记录所有检测到的恶意软件遭遇实例。
*   **IDS/IPS 系统**—这些设备或工具通常记录网络中发生的异常或威胁活动。
*   **身份验证服务器**—这些设备记录身份验证尝试，并包含尝试的来源、日期/时间和用户名，以及成功或失败的指示。
*   **远程访问/VPN 软件**—这些工具通常记录成功和失败的登录尝试。
*   **Web 代理**—这些设备通常记录通过它们访问的所有 URL。
*   **漏洞扫描器**—这些工具通常记录安全项目，例如补丁安装和网络中不同主机的漏洞状态。这可能包括已知漏洞和缺失的软件更新数据。

这些是安全管理员通常最感兴趣的日志。在所有情况下，关于审核什么内容都有许多选项。例如，登录尝试的成功或失败可能为即将发生的攻击活动提供线索，并应提供导致修改组织密码策略或需要持续进行用户教育的信息。审核结果如果表明攻击者试图识别并使用密码、试图突破访问控制列表，或试图解密加密数据，都可能得出有人试图渗透网络的结论。

审核结果可能显示某用户账户在非正常时间被使用。此审核可能表明该用户的登录账户已被泄露。受限文件夹等对象可针对访问尝试和不当的用户访问权限进行审核。通常，单个打印机不进行审核，尽管它们可以在短时间内被审核。

审核用户**登录尝试**可能是识别用户密码是否已泄露的最重要方法之一。网络管理员应了解分配员工的正常工作时间表。如果员工仅在白天工作或正在按计划休假，则其账户不应在夜间或其不在时处于活动状态。

审核**用户权限**是识别本地主机是否感染了提升用户权限病毒的有用技术。**权限提升**是指用户登录服务器后，能够执行包含嵌入式代码的程序，从而获得管理权限的情况。

网络防火墙可配置为审核内部组织用户是否访问不当网站。这些防火墙也可配置为识别来自互联网的用户正在访问的文件、文件夹和服务。这些审核的结果放置在提供**审计跟踪**的审核日志中。未能遵守公司政策的用户可接受劝导，在某些情况下可被解雇。

## 日志记录注意事项

审核是一项重要的安全功能，必须经过周密规划。审核可计划用于扫描组织网络内部的不当活动（内部审核），或试图渗透网络的外部活动。然而，在配置审核系统之前，应深思熟虑以确定应审核哪些对象和事件以及何时审核。开启多个审核工具会给大多数网络带来负担，导致性能下降。

例如，记录网络中发生的所有对象和事件是不切实际的，特别是在 OT 网络中，因为这将严重影响其性能。这样做会导致网络陷入瘫痪或至少大幅减速。因此，审慎使用日志记录/审核工具一直是网络和设备级审核的标准方法。

当然，审核需要额外的资源，包括时间和人员，来审查审核数据。在考虑审核事件时，必须分配时间来评估审核报告、日志或警报通知。确保系统日志提供有效安全措施的唯一方法是要求网络管理员定期审查日志。创建过多的审核日志可能导致无法审查或识别可能与安全问题或违规相关的关键事件。因此，在决定需要审核什么以及谁应接收审核日志和警报时，必须非常慎重地进行选择。

与事件日志记录相关的另一个重要考虑因素是管理每个日志的大小、位置和覆盖策略。例如，Windows 操作系统默认配置为在日志达到一定大小时覆盖日志。

## SIEM 系统

许多**安全信息和事件管理 (SIEM)** 系统正在增加**人工智能 (AI)** 和**机器学习**功能，以近实时地跟踪人和机器的活动。这些功能包括**用户行为分析 (UBA)** 工具，可用于识别网络中用户和机器的行为模式。UBA 工具为网络的用户和设备构建活动配置文件。SIEM 利用这些配置文件将当前活动与人和机器的过往活动模式进行比较，并将其分类为正常或异常。

由于每个网络环境都不同，SIEM 系统需要初始配置和持续的“调优”。配置工作涉及为来自不同网络源的事件关联创建自定义规则，这些规则将触发警报。这些规则关注的活动包括：

*   用户身份验证尝试（由终端设备和服务器中的审核系统报告）
*   检测到的攻击（由入侵检测系统报告）
*   检测到的感染（由防病毒和反恶意软件包报告）

通常，这些规则依赖于为特定事件发生次数设定的阈值级别。例如，规则可配置为：如果网络中任何主机在一分钟内记录到三次登录失败尝试，则生成警报。

AI 组件用于调优 SIEM 的运行，并根据网络中各设备的持续活动构建正常用户和设备活动的配置文件。当 SIEM 首次安装时，网络管理员通常非常忙碌，需要响应系统报告的所有误报指标。然而，随着 AI 组件“学习”网络用户和设备的正常活动，运行变得更加自动化和流畅。

因为 UBA 工具学习什么被归类为正常活动，SIEM 成为检测内部威胁的非常好的工具，并且当涉及不满的管理员时，可能是检测此类威胁的最佳工具之一。

当跨 ICS/企业网络监控如此多的设备时，收集的数据量将远超管理员的管理能力，因此显然需要某种集中式日志管理系统。此功能通常由某种类型的 SIEM 系统来实现。可采用三种通用类型的 SIEM。

*   **安全信息事件管理 (SIEM)** 系统—此名称包括数据检查工具，它们收集其他网络设备生成的日志，并将其汇编在集中的网络位置。这些工具通常还提供解释和分析功能，以自动帮助管理员审核其网络。
*   **安全事件管理 (SEM)** 系统——此术语通常适用于提供实时事件分析和通知的 SIEM 工具。
*   **安全信息管理 (SIM)** 系统——此 SEIM 版本通常指为提供网络日志长期存储而创建的系统。

# 归档日志

在 OT 环境中，组织可能需要出于多种原因将其生产日志**归档**较长时间（例如数年或数十年）。例如，用于核反应堆或航空航天应用的组件制造过程控制记录，可能需要在该组件的整个生命周期内保持可用。例如，如果与生产相关的法律诉讼变得必要，可能需要提供用于生产该组件的工艺的审计结果。此类存储要求可能延伸至其他数据的存储，包括安全日志数据。

组织的审计策略应规定日志存储的要求和指南，以便管理员能够妥善管理日志存储，并确保日志按要求保留相应的时间段。例如，NERC CIP 发电和配电成员会定期接受审计，并必须提供证据证明其符合所有 CIP 类别。现有 NERC 指南中有 50 多项证据保留要求。NERC CIP 006-3 标准的一部分要求以访问控制日志的形式提供与物理访问控制相关的文档。除非 NERC 合规执法机构指示作为正在进行的调查的一部分保留更长时间，否则这些日志必须保留一个完整的日历年。

如果存储要求时间较长（不仅仅是几天或几周），则需要对日志进行归档。这可能要求管理员确定日志的文件格式在指定的时间段内是否仍可用。

例如，某些设备以专有格式生成安全日志，这些格式可能在数年内无法保持有效。在这种情况下，管理员可能决定以原始格式、标准格式或两种格式兼存的方式归档文件。

长期归档日志文件的另一个考量因素是选择使用的存储介质。虽然有多种不同的存储介质选项可用于归档日志数据，但必须考虑该介质（及其支持的硬件和软件）预计在要求的保留期内能保持可用多长时间。如果任何格式似乎面临变得不可用或无法访问的风险，管理员必须采取行动将日志传输到另一种介质类型。

与其他备份类型一样，管理员负责确保日志存储介质安全存储。这包括实施物理和逻辑访问控制策略及设备，以防止未经授权访问介质。这还涉及提供适当的环境控制，以确保介质不受损坏。这通常涉及在异地设施或云存储环境中存储日志归档介质的副本。

最后，管理员还负责确保在归档日志的要求数据保留期结束后，像其他数据备份一样对其进行妥善销毁。

# 事件管理

**事件管理** 是一种旨在事件发生后尽快将运营恢复到“正常”水平的流程，以最大限度地减少对组织生产和盈利能力的负面影响。在本章前面的部分中，您一直在处理“事件”的监控、记录和审计。然而，在网络安全环境中，事件在技术上并非您关注的对象。造成这种混淆的部分原因是术语问题。正如监控和审计经常互换使用一样，**事件** 和 **事故** 这两个术语也经常互换使用。

**事件** 通常被定义为“网络环境中的任何变更、错误或中断”。在其 SP 800-61r2 文档《计算机安全事故处理指南》中，NIST 组织将事件定义为“网络环境中任何可观察到的发生情况”。此定义涵盖了系统崩溃、磁盘错误和遗忘访问凭据等项目。这些是在正常操作过程中例行处理的事件。

另一方面，**事故** 由 NIST 定义为“违反（或迫在眉睫的违反威胁）安全策略、可接受使用策略或标准安全实践”。根据此定义，事故是需要安全人员进行管理的事件。

**NIST 800-61r2** 建议，为建立高效的事故响应能力，组织应采取以下行动：

1.  制定事故响应策略和计划。
2.  制定执行事故处理和报告的程序。
3.  制定关于事故方面与外部各方沟通的指南。
4.  选择响应团队结构和人员配置模型。
5.  在事故响应团队与其他内部（如法务部门）和外部（如执法机构）群体之间建立关系和沟通渠道。
6.  确定事故响应团队应提供的服务。
7.  配备并培训事故响应团队。

在分析安全日志时，管理员可能会发现需要某种响应来解决的事故。这包括在网络上发现恶意软件、发生 DoS/DDoS 攻击、软件、固件或硬件配置被未经授权更改的证据，以及个人或机构身份盗窃的报告。发生此类情况时，他们必须启动组织的网络安全计划，并开始执行其事故响应计划 (IRP)，如 第 8 章 “ICS 安全治理与风险管理”所述。

回顾一下，IRP 旨在识别潜在的紧急和灾难性活动，这些活动将触发启用 BCP 和 DRP 的需求。它旨在首先采取主动——通过监控活动发现潜在麻烦。然而，它也必须具备响应性，因为它旨在在组织的边缘防护和人员培训工作失败的情况下被激活。

该计划通常涉及信息安全、取证和网络安全职能，用于识别针对组织系统的攻击或漏洞利用的来源、载体和目标。该计划步骤的结果应为今后实施正确的行动方案指明路径。
