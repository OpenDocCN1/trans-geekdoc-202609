
*工程师*：ISSAF 版本 `0.2.1` 编写时，`Windows NT` 系统还是主导操作系统。情况已经发生了巨大变化，因此不要期望 ISSAF 中的示例适用于所有微软平台。

*经理*：在期望渗透测试团队正确识别漏洞之前，请确保他们已经接受了目标操作系统最新版本的培训。

操作系统的底层架构多年年来发生了巨大的变化，要求一个熟悉 `Windows NT` 的工程师能够攻击 `Server 2008` 系统是不合理的。我在各种网络设备中见过操作系统，其中许多在发现它们在运行时令我很惊讶。Web 服务器也包含在大量设备中，包括路由器、交换机、防火墙等。Web 服务器不再仅仅用于互联网——它们一直被用作管理的图形界面。

## 应用程序安全

应用程序与数据库之间的界限很难界定——许多应用程序访问数据库才能运行。ISSAF 对界限的划分也不佳，将许多攻击活动包含在应用程序安全中（例如为了“控制数据库”的结构查询语言攻击）。根据 ISSAF，属于应用程序安全的评估如下 (OISSG, 2006):

- Web 应用程序安全评估
- SQL 注入
- 源码审计
- 二进制审计

Web 应用安全是一个很大的话题；我们将讨论针对 Web 应用程序的特定技术。但我们将看到，我们攻击 Web 应用程序的方法与我们攻击所有应用程序的方法非常相似。通常，Web 应用程序的不同之处仅在于涉及到数据库。

## 数据库安全

ISSAF 为评估人员提供了四个不同的评估层，这些层可能涉及或不涉及 Web 和服务 (OISSG, 2006):

- 数据库远程枚举
- 数据库暴力破解
- 进程操控攻击
- 数据库端到端审计

## 社会工程学

ISAF 的社会工程学章节讨论了许多较旧且为人知的社会工程技术，这些技术用于从系统用户处获取信息。遗憾的是，这些旧技术仍然非常有效。然而，该章节中缺少了一些目前更流行的技术，包括网络钓鱼（及其所有子集）和跨站脚本攻击（XSS 攻击）。这正是将 ISSAF 作为渗透测试（PenTest）团队理解潜在威胁的起点的另一个原因，但而不应将其作为渗透测试项目的整个框架。

## 报告、清理和销毁产物 – 第三阶段

ISAF 的最后阶段涉及将必要的报告提交给相关的利益相关者，并确保渗透测试期间生成的任何数据的安全。ISAF 并没有详细说明如何执行此阶段的任务，但提供了一些概括性的描述。

### 报告

在专业的渗透测试中，可能会发生两种类型的报告——口头报告和书面报告。根据 ISSAF 的规定，口头报告适用于那些发现关键问题并需要几乎立即报告的情况。尽管 ISSAF 没有特别提到，但将任何口头交流的发现包含在最终报告中可能是明智的。这意味着，即使关键问题在最终报告发布给利益相关者之前已修复，也会形成一份正式记录。

**警告**：任何关于关键问题或具有敏感或法律性质发现的口头报告都需要仔细处理。如果违反了法律，可能需要通知当地或联邦探员，利益相关者可能需要被排除在任何形式的口头报告之外。在渗透测试之前，应该根据需要识别并联系法律和执法部门代表。在最终书面报告中，ISAF 要求包含以下内容（OISSG, 2006）：■ 管理层摘要 ■ 项目范围 ■ 使用的渗透测试工具 ■ 使用的利用程序 ■ 测试日期和时间 ■ 工具和利用程序的所有输出 ■ 已识别漏洞列表 ■ 减轻已识别漏洞的建议（按优先级组织）。这些要求应该出现在最终文档的正文中，而不是被归类到附件中。根据个人经验，这可能会产生一份难以阅读的冗长文档。我们将在本书的第 3 部分中讨论报告，以扩展这一主题。

### 清理和销毁产物

ISAF 没有在渗透测试的第三阶段详细讨论这一步骤。事实上，整个步骤仅限制在以下段落（OISSG, 2006）：在被测试系统上创建和/或存储的所有信息都应从这些系统中移除。如果由于某些原因无法从远程系统实现，则所有这些文件（及其位置）都应在技术报告中说明，以便客户技术人员在收到报告后能够删除这些文件。在 ISSAF 的未来版本中，可能会提供有关如何加密、清理和销毁渗透测试期间创建并在之后保留的数据的更多细节。在此，我们将在本书的第三部分讨论这些问题。

# 开源安全测试方法手册

OSSTMM 最初于 2000 年引入信息系统安全行业。当前版本为 3.0 版，由安全与开放方法学会 (ISECOM) 维护。该手册通过同行评审开发，并以开源许可发布，可以在 [www.isecom.org](http://www.isecom.org) 获取。虽然 OSSTMM 提供了一种执行渗透测试的方法，但它首要是一种审计方法，可以满足监管和行业要求。尽管 OSSTMM 提供执行渗透测试的方法，但在应用于企业资产时，它首先是一个审计方法。OSSTMM 的作者将其描述如下（Herzog, 2008）：该方法持续提供事实性的测试。作为一种方法，你无法从从中学习如何或为什么要进行测试；然而，你可以将其整合到你的需求中，使其与现有的法律和政策相符，以确保审计的详尽性。OSSTMM 的早期版本也可以在随附的光盘中找到。OSSTMM 2.2 版本与新版本有显著不同，它似乎从头开始重写，涵盖了网络之外的多个安全领域。

**注意**：OSSTMM 有多个版本的文档。虽然可以免费获取 OSSTMM，但访问最新版本需要加入 ISECOM 网站。

## 规则

为了满足某些项目需求，OSSTMM 强制某些活动的发生并生成各种文档。尽管 OSSTMM 在列举渗透测试项目的组成部分方面比 ISSAF 更详尽，但并没有为项目经理在分配渗透测试项目时提供相应的流程。OSSTMM 内部提供的信息包含了一些行业最佳实践，对于没有渗透测试社区经验的项目经理非常有益。以下是 OSSTMM 中“参与规则”的一段节录，列出了项目开始前所需的内容（Herzog, 2008）：■ 项目范围 ■ 保密与非披露保证 ■ 紧急联系信息 ■ 工作说明变更流程 ■ 测试计划 ■ 测试过程 ■ 报告。在某些渗透测试中，这些可能满足客户的需求。然而，项目经理还需要许多补充来改进渗透测试项目（或任何项目），包括采购、风险识别（项目内部而非目标系统）、定性和定量风险分析、获取资源、成本估算和控制。无论如何，OSSTMM 的规则章节确实包含价值信息，应该被阅读和遵循。

## 通道

OSSTMM 使用“通道”一词来分类组织内部不同的感兴趣的安全领域，包括物理安全、无线通信、电信和数据网络。这四个通道受审计和渗透测试的影响最大，并涉及 (ISC)² 识别的 10 个安全领域的大部分（参见第 3 章）。

### 人员安全

OSSTMM 这一部分的主要目的是确定组织内部安全培训的有效性。执行人员安全评估所需的技巧和工具包括对员工进行社会工程学。某些测试包括欺诈能力；对“心理虐待”的敏感性；窃听闭门会议、识别黑市活动以及发现获取企业员工隐私信息的程度；以及评估人员从企业员工处获取专有信息的能力。

### 物理安全

使用 OSSTMM 进行物理安全审计涉及尝试在没有适当授权的情况下访问设施。任何有意从事涉及物理安全审计职业的人员都需要意识到其中涉及的危险，OSSTMM 对这些危险列举（Herzog, 2008）：……由于传统屏障和武器导致的意外人伤害、与动物的互动、遭受有害细菌、病毒和真菌的影响、暴露于电磁和微波辐射（特别是可能永久损害听力或视力的辐射），以及任何形式的毒性或腐蚀性化学剂。物理安全审计侧重于评估设施内监控系统、安保人员及其部署、照明以及对安全事件的反应时间的有效性。

`Warning`：任何进行物理安全审计的人都需要准备好可能被执法部门发现并拘留。渗透测试人员在物理安全审计中的活动模仿了犯罪分活动，首要假设是你的活动是非授权的，且你对财产或他人安全构成了威胁。当面对携带实弹武器的人时，不要感到惊讶——这只是工作的一部分。

### 无线通信

OSSTMM 不将无线通信通道限制为网络接入点与计算系统之间的连接。电子安全、信号安全和发射安全是该通道内的主题。任何可以被中断或拦截的电子发射都属于该通道，包括无线射识别 (RFID)、视频监控器发射、医疗设备和网络无线接入点。

## 电信

电信通道内的攻击领域涉及任何模式的语音通信，包括 PBX 系统、语音信箱和 VoIP。这些许多通信模式现在由计算机运行，容易受到网络攻击。渗透测试可以识别可能的信息泄露，无论是通过网络数据包的误导，还是访问员工账户的弱保护机制。

## 数据网络

本书的主要目的是指导读者如何进行数据网络渗透测试。该通道专注于计算机和网络安全，涵盖了以下渗透测试程序（Herzog, 2008）：■ 网络侦查 ■ 枚举 ■ 识别 ■ 访问过程 ■ 服务识别 ■ 认证 ■ 欺骗 ■ 钓鱼 ■ 资源滥用。从第 9 章开始，我们将讨论所有这些程序，但将使用 ISSAF 的术语。

## 模块

与 PMBOK 中的过程概念类似，OSSTMM 拥有模块，这些是渗透测试中可重复的过程。这些模块被用于 OSSTMM 识别的所有通道中。每个模块的实施可能不同，取决于目标系统或网络；然而，下介绍的概念描述了每个模块的高级目标（Herzog, 2008）：

### 第一阶段：监管

- 态势审查：识别适用于目标的监管和立法政策。还会考虑行业惯例。
- 物流：由于任何活动都不会在真空中发生，网络延迟和服务器位置可能会改变结果；有必要识别项目中存在的任何物流限制。
- 主动检测验证：验证交互检测、响应和响应可预测性的实践和广度。

### 第二阶段：定义

- 可视性审计：一旦确定了项目范围，渗透测试人员需要确定项目范围内目标的“可视性”。
- 访问验证：识别目标内的访问点。
- 信任验证：系统通常与其他系统有信任关系以开展业务。该模块试图确定这些关系。
- 控制验证：该模块衡量系统内违反机密性、完整性、隐私和不可否认性的能力，以及采取了哪些控制措施来防止此类损失。

### 第三阶段：信息阶段

- 过程验证：评估人员检查了哪些过程来确保系统的安全态势维持在当前水平，以及这些过程的有效性。
- 配置验证：在人员安全通道中，该模块被称为`培训验证`，检查目标的默认操作。将默认操作与组织的业务需求进行比较。
- 属性效验：识别目标系统上的知识产权 (IP) 或应用程序，并验证该 IP 或应用程序的许可情况。
- 隔离审查：尝试识别系统上的个人信息，以及合法或未经授权的用户可以访问这些信息的程度。
- 暴露验证：识别互联网上关于目标系统的可用信息。
- 竞争情报侦察：识别可能通过竞争影响目标所有者的竞争对手信息。

### 第四阶段：交互控制测试阶段

- 隔离验证：验证系统隔离外部访问系统和内部系统数据的能力。
- 权限审计：检查在系统内提升权限的能力。
- 生存性验证：在人员安全通道中，该模块被称为`业务连续性`，用于确定系统对过度或不利情况的抵抗力。
- 告警和日志审查：在人员安全通道中，该模块被称为`结束调查`，涉及审查审计活动。OSSTMM 提供了具体的步骤以便实现模块的高级目标并消除任何歧。虽然不像 ISSAF 内部步骤那样具体，但 OSSTMM 模块提供了足够的粒度，让经验丰富的渗透测试专业人员在攻击时选择合适的工具。与 ISSAF 不同，OSSTMM 通过提供渗透测试中需要执行的通用概述，为渗透测试工程师提供了如何最好攻击目标的一些灵活性。对于那些刚刚开始渗透测试领域职业的人来说，没有关于使用什么工具或遵循什么流程的指导可能会令他们望而生畏。

## 总结

这里列出的任何方法论都不适用于渗透测试从构思到结束的所有方面。然而，所有方法论都包含某些组件，结合在一起可以为任何渗透测试项目提供有效的基础。困难之处在于识别应该使用哪些部分，哪些部分应该避免。

`PMBOK` 为任何渗透测试提供了一个非常有结构性的框架。如果负责渗透测试的工程师拥有多年经验且工作非常胜任，`PMBOK` 可能绰绰有。然而，如果工程师在知识上存在空白，引入 `OSSTMM` 或 `ISSAF` 可能更为合适。`PMBOK` 包含许多过程，但并非所有过程都需要在每次渗透测试中使用。这些过程甚至可能不需要正式记录。支持项目的文档详尽程度应仅根据需要而定。仅仅为了创建文档而创建文档，这会将重点错误地放在了执行项目的过程上，而不是它本该所在的地方：渗透测试的圆满完成。然而，`PMBOK` 内部的流程是为了提高项目的成功率，同时确保项目按时且在预算内完成。因为成本或不喜欢项目管理而规避项目管理流程可能会导致项目失败。

渗透测试专业领域还相当新，支持渗透测试的方法论更新。`OSSTMM` 和 `ISSAF` 尝试为该领域提供一些结构并强制执行最佳实践，但它们并没有像其他行业那样拥有数十年的经验支撑。随着时间的推移，这些方法论将会改进；但目前，从事 `PenTest` 项目的项目经理和工程师需要带着自己的经验工作，以填充 `OSSTMM`、`ISSAF` 和 `PMBOK` 中存在的任何空白。

## 项目管理知识体系 (Project Management of Knowledge)

- 项目周期由五个不同的组组成：启动过程、规划过程、执行过程、结束过程和监控控制过程。
- 启动过程组的目的是获得启动项目的批准。
- 规划过程组获取成功完成项目所需的信息，并将项目定义到更细的粒度上。
- 执行过程组积极涉及渗透测试工程师，通常表示为“计划-执行-检查-处理（Plan-Do-Check-Act）”循环中的“执行”。
- 结束过程组向客户交付文档，释放已采购的资源，并允许项目经理为随后的渗透测试识别改进之处。
- 只有监控控制过程组涵盖了从构思到结束的整个渗透测试。
- 并非所有过程都需要在所有渗透测试中使用。
- 文档的详细程度仅取决于需要——过多的文档会阻碍任何渗透测试的进展。

## 信息系统安全评估框架 (Information System Security Assessment Framework)

- 规划和处理阶段可能无法为成功的渗透测试提供足够的支持。根据需要纳入其他方法论的过程。
- 尽管 `ISSAF` 中存在示例，但渗透测试人员需要对提供的示例进行扩展。
- `ISSAF` 正迅速过时。

## 开源测试手册 (Open Source Testing Manual)

- 有四种不同的“通道”可以从渗透测试中受益：物理安全、无线、电信和数据网络。
- `PenTest` 中有四个阶段：监管、信息和交互式控制。
- **Q:** 在没有工具的情况下，为什么要讨论 `PMBOK`？
- **A:** 为了从构思到完成成功完成一个项目，必须进行某种形式的项目管理。
- **Q:** 在 `OSSTMM` 和 `ISSAF` 之间，哪种方法论最好？
- **A:** 取决于渗透测试人员的技能。
- **Q:** `OSSTMM` 似乎讨论渗透测试的层次太高。为什么没有著名的工具？
- **A:** 遗憾的是，每次渗透测试都是不同的，需要不同的方法。提供示例和命令会限制思维，并将工程师变成“脚本小子”（script kiddie）。

## 引言 (Introduction)
