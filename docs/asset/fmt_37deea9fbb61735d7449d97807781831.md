
例如，在我们的运行示例查询中，初始状态 `v[0] = {X, Y, Z, XY, XZ}`，目标状态 `v[goal] = ∅`，即不再有剩余的三元组模式。假设第一个作业执行 `join(X, XY, XZ)`。那么，生成的三元组模式（新状态）将为 `v[1] = {Y, Z, YZ}`，作业 1 将由边 `(v[0], v[1])` 表示。边 `(v[0], v[1])` 的权重即为 `job[1]` 的代价 `= cost(job[1])`，其中 cost 为给定的代价函数。图 15.4 展示了示例查询的部分图。

#### 15.5.4.3 搜索空间大小

给定图 `G = (V, E)`，Dijkstra 最短路径算法可在 `O(|V| log |V| + |E|)` 时间内找到从源点到所有其他节点的最短路径。然而，对于 Bestplan，可以证明在最坏情况下，`|V| ≥ 2^K`，其中 `K` 为给定查询中连接变量的总数。因此，图中的顶点数量呈指数级增长，导致这是一个指数级搜索问题。在 [HUSA11a] 中，我们已证明 Bestplan 问题的最坏情况复杂度在给定查询的连接变量数 `K` 上呈指数级。

#### 15.5.4.4 松弛 Bestplan 问题与近似解

在松弛 Bestplan 问题中，我们假设所有作业的代价均匀。尽管这种松弛并未减小搜索空间，但问题简化为寻找具有最少作业数量的作业计划。请注意，这是该模型实用版本所面临的问题。

**定义 15.12：松弛 Bestplan 问题**：松弛 Bestplan 问题旨在寻找具有最少作业数量的作业计划。

接下来，我们将证明：如果合理选择连接，且在一个作业中不留下任何符合条件的连接操作未执行，则可为任意给定查询所需的最大作业数设定一个上界。然而，生成所有可能的作业计划在计算上仍然昂贵。因此，我们采用了一种贪心算法（算法 15.1），它能求得松弛 Bestplan 问题的近似解，但保证能在上界内找到一个作业计划。

**定义 15.13：早期消除启发式**：早期消除启发式旨在每个作业中尽可能多地进行完全消除。

该启发式使得留给下一个作业进行连接的变量数量最少。为应用该启发式，我们必须首先在每个作业中选择 E-count 最小的变量。该启发式应用于算法 15.1 中。

##### 算法 15.1 说明

算法首先从查询 `Q` 中移除所有非连接变量。在我们的运行示例中，`Q = {X, Y, VZ, XY, XZ}`，移除非连接变量 `V` 后得到 `Q = {X, Y, Z, XY, XZ}`。在 while 循环中，从 `Job[1]` 开始生成作业计划。第 4 行，我们根据变量的 E-count 对其进行排序。排序后的变量为：`U = {Y, Z, X}`，因为 `Y` 和 `Z` 的 E-count = 1，而 `X` 的 E-count = 2。对于每个作业，要执行的连接操作列表存储在变量 `Job[J]` 中，其中 `J` 为当前作业的 ID。此外，临时变量 `tmp` 用于存储当前作业中将要执行的连接所产生的结果三元组（第 6 行）。在 for 循环中，检查每个变量以判断其是否可以被完全或部分消除（第 8 行）。若可以，则将连接结果存入临时变量（第 9 行），更新 `Q`（第 10 行），并将该连接加入当前作业（第 11 行）。在我们的运行示例中，这将导致以下操作：

for 循环第 1 次迭代：`u[1] = (Y)` 可被完全消除。此处，`TP(Q, Y)` 为包含

for 循环第 3 次迭代：`u[3] = (X)` 无法被完全或部分消除，因为没有其他 `TP` 剩余可与其连接。因此，当 for 循环结束时，我们得到 `job[1] = {join(Y, XY), join(Z, XZ)}`，且 `Q = {X, X, X}`。在 while 循环的第 2 次迭代中，我们将得到 `{job[2] = {X, X, X}}`。由于执行此连接后 `Q` 变为空，while 循环退出。最终，算法返回 `{job[1], job[2]}`。

在 [HUSA2011a] 中，我们已证明：对于包含 `K` 个连接变量和 `N` 个三元组模式的任意给定查询 `Q`，算法松弛 Bestplan (`Q`) 生成的作业计划最多包含 `J` 个作业，其中

```
J = { 0                    若 N = 0
    { 1                    若 N = 1 或 K = 1
    { min(ceil(1.71 log₂ N), K)  若 N, K > 1
```

### 15.5.5 利用摘要统计信息打破平局

### 15.5.6 MapReduce Join 执行

在本节中，我们将讨论如何利用 Hadoop 的 MapReduce 框架实现回答 SPARQL 查询所需的连接操作。`算法 15.1` 确定了回答一个查询所需的作业数量。它返回一个有序的作业集合。每个作业都有关联的输入信息。我们 MapReduce 框架的作业处理组件按有序集合中出现的顺序运行这些作业。一个作业的输出文件是下一个作业的输入文件。最后一个作业的输出文件包含查询的答案。

#### 列表 7：LUBM 查询 2

```
SELECT ?X, ?Y, ?Z WHERE {
?X rdf:type ub:GraduateStudent.
?Y rdf:type ub:University.
?Z rdf:type ub:Department.
?X ub:memberOf ?Z.
?Z ub:subOrganizationOf ?Y.
?X ub:undergraduateDegreeFrom ?Y }
```

`列表 7` 展示了 LUBM 查询 2，我们将用它来说明我们如何使用 map 和 reduce 方法进行连接。该查询有六个三元组模式，并在变量 `X`、`Y` 和 `Z` 上存在九个连接。

我们的输入选择算法选择文件 `type_GraduateStudent`、`type_University`、`type_Department`、所有具有前缀 `memberOf` 的文件、所有具有前缀 `subOrganizationOf` 的文件，以及所有具有前缀 `underGraduateDegreeFrom` 的文件，作为回答查询所需作业的输入。

查询计划包含两个作业。在作业 1 中，第 2、5、7 行的三元组模式在 `X` 上连接，第 3、6 行的三元组模式在 `Y` 上连接。在作业 2 中，第 4 行的三元组模式与前两个连接的输出在 `Z` 上连接，同时作业 1 的连接输出在 `Y` 上连接。

作业 1 的输入文件包括 `type_GraduateStudent`、`type_University`、所有具有前缀 `memberOf` 的文件、所有具有前缀 `subOrganizationOf` 的文件，以及所有具有前缀 `underGraduateDegreeFrom` 的文件。在 map 阶段，我们首先对输入值（实际上是输入文件的一行）进行分词。然后，我们检查输入文件名，如果输入来自 `type_GraduateStudent`，我们输出一个键值对，其键为带有前缀 `X#` 的主语 URI，值为标志字符串 `GS#`。该值作为标志，指示该键的类型为 GraduateStudent。主语 URI 是分词器返回的第一个标记。同样，对于来自文件 `type_University` 的输入，输出一个键值对，其键为带有前缀 `Y#` 的主语 URI，值为标志字符串 `U#`。如果输入来自任何具有前缀 `memberOf` 的文件，我们通过分词器从输入行中检索主语和宾语，并输出一个键值对，其键为带有前缀 `X#` 的主语 URI，值为带有前缀 `MO#` 的宾语值。对于来自具有前缀 `subOrganizationOf` 的文件的输入，我们输出键值对，将带有前缀 `Y#` 的宾语作为键，带有前缀 `SO#` 的主语作为值。对于来自具有前缀 `underGraduateDegreeFrom` 的文件的输入，我们输出键值对，将带有前缀 `X#` 的主语 URI 作为键，带有前缀 `UDF#` 的宾语值作为值。因此，我们根据连接的变量将主语或宾语作为 map 输出键。这就是为什么对于具有前缀 `subOrganizationOf` 的文件中的三元组，将宾语作为键的原因，因为连接变量 `Y` 在第 6 行的三元组模式中是宾语。对于所有其他输入，主语被作为键，因为连接变量 `X` 和 `Y` 在第 2、3、5 和 7 行的三元组模式中是主语。

在 reduce 阶段，Hadoop 将单个键的所有值分组，并为每个键提供该键和一个值集合的迭代器。通过查看前缀，我们可以立即判断它是 `X` 的值还是 `Y` 的值，这归功于我们使用的前缀。无论哪种情况，我们都使用相同的键输出一个键值对，并将所有值连接起来形成一个字符串值。因此，在此 reduce 阶段之后，`X` 上的连接已完成，`Y` 上的连接部分完成。

作业 2 的输入文件是 `type_Department` 文件和作业 1 的输出文件 `job1.out`。与作业 1 的 map 阶段类似，在作业 2 的 map 阶段，我们也对输入值（实际上是输入文件的一行）进行分词。然后，我们检查输入文件名，如果输入来自 `type_Department`，我们输出一个键值对，其键为带有前缀 `Z#` 的主语 URI，值为标志字符串 `D#`。如果输入来自 `job1.out`，我们查找带有前缀 `Z#` 的值。我们将该值作为输出键，并将其余值连接成一个字符串作为输出值。基本上，我们将 `Z#` 值作为键以便在 `Z` 上进行连接。

在 reduce 阶段，我们知道键是 `Z` 的值。值集合包含两类字符串。一类包含 `X` 值（即研究生的 URI）以及他们获得本科学位的 `Y` 值。`Z` 值（即键）可能是也可能不是 `Y` 值的 `subOrganizationOf`。另一类字符串仅包含 `Y` 值（即大学），`Z` 值是这些大学的子组织。我们遍历值集合，然后根据 `Y` 值连接这两类元组。从连接输出中，我们找到包含 `X`、`Y` 和 `Z` 值的结果元组。

#### 15.6.1.2 基准框架

#### 15.6.1.3 硬件

我们拥有一个 10 节点的 Hadoop 集群，用于我们的框架。每个节点的配置如下：奔腾 IV 2.80 GHz 处理器、4 GB 内存和 640 GB 磁盘空间。我们在一台配置强劲的单机上运行 Jena、RDF-3X 和 BigOWLIM 框架，该机器配备 2.80 GHz 四核处理器、8 GB 内存和 1 TB 磁盘空间。

### 15.6.2 评估

我们展示了我们的框架、`RDF-3X`、`Jena` 内存模型和 SDB 模型以及 `BigOWLIM` 之间的性能比较。更多细节请参见 `[HUSA2011a]`。我们使用了三个 LUBM 数据集：10,000、20,000 和 30,000，它们分别包含超过 11 亿、22 亿和 33 亿个三元组。`RDF-3X` 的初始加载时间分别为 655、1,756 和 3,353 分钟。这表明 `RDF-3X` 的加载时间呈指数级增长。LUBM (30,000) 的三元组数量是 LUBM (10,000) 的三倍，但其加载时间却是后者的五倍多。

出于评估目的，我们选择了 LUBM 查询 1、2、4、9、12 和 13 在本文中报告。这些查询提供了良好的组合，包含简单和复杂的结构、推理以及多种类型的连接。它们代表了基准测试中的其他查询，因此仅报告这些查询即涵盖了我们省略的查询中发现的所有变化类型，同时也节省了篇幅。

查询 1 是一个简单的选择性查询。对于此查询，`RDF-3X` 比 `HadoopRDF` 快得多。`RDF-3X` 利用了六个索引 `[NEUM2008]`，这六个索引实际上构成了数据集。这些索引为 `RDF-3X` 提供了一种非常快速的三元组查找方式，类似于哈希表。因此，高选择性查询可由 `RDF-3X` 高效回答。

查询 2 是一个具有复杂结构、低选择性且无绑定对象的查询。结果集相当大。对于此查询，`HadoopRDF` 在所有三种数据集规模下均优于 `RDF-3X`。当数据集规模达到 33 亿三元组时，`RDF-3X` 完全无法回答该查询。`RDF-3X` 返回内存段错误消息，且未产生任何查询结果。

查询 4 也是一个高选择性查询，即由于第二个三元组模式中有绑定对象，结果集较小，但需要推理来回答。第一个三元组模式使用了类 `Person`，它是许多类的超类。LUBM 数据集中没有类型为 `Person` 的资源，而是有许多其子类型的资源。`RDF-3X` 不支持推理，因此我们必须将查询转换为包含一些并集操作的等价查询。对于此查询，`RDF-3X` 优于 `HadoopRDF`。

查询 9 在结构上类似于查询 2，但需要大量推理。该查询的前三个三元组模式使用的类在数据集中未显式实例化。然而，数据集包含许多对应子类的实例。这也是我们评估的查询中需要最大数据集连接并返回最大结果集的查询。对于 11 亿三元组的数据集，`RDF-3X` 比 `HadoopRDF` 快；但对于另外两个数据集，它完全无法回答该查询。

查询 12 类似于查询 4，因为它既具有选择性，又在一个三元组模式中包含推理。对于此查询，`RDF-3X` 优于 `HadoopRDF`。

查询 13 只有两个三元组模式。两者都涉及推理。第二个三元组模式中有绑定主语。它返回第二大的结果集。对于所有数据集，`HadoopRDF` 在此查询上均优于 `RDF-3X`。`RDF-3X` 性能较慢，因为第一个三元组模式选择性极低，且需要通过反向链接进行低选择性连接以执行推理。

这些结果引出了一些简单的结论。`RDF-3X` 在高选择性和有绑定对象的查询上实现了最佳性能。然而，`HadoopRDF` 在无绑定对象、低选择性或大数据集连接的查询上优于 `RDF-3X`。`RDF-3X` 无法针对 33 亿三元组的数据集执行两个无绑定对象的查询（查询 2 和 9）。这表明 `HadoopRDF` 具有更好的可扩展性，并能比 `RDF-3X` 更高效地处理低选择性查询。

我们还将我们的实现与 `Jena` 内存模型、SDB 模型和 `BigOWLIM` 模型进行了比较。由于空间和时间限制，我们仅针对 LUBM 数据集的 LUBM 查询 2 和 9 执行了这些测试。我们选择这些查询是因为它们具有复杂结构并需要推理。值得注意的是，`BigOWLIM` 需要 7 GB 的 Java 堆空间才能成功加载十亿三元组数据集。我们仅针对最大的三个数据集运行了 `BigOWLIM`，因为我们关注其在大数据集上的性能。对于每个数据集，我们分别获得了 `Jena` 内存模型、`Jena` SDB 模型、我们的 `Hadoop` 实现和 `BigOWLIM` 的结果。有时查询无法完成或内存耗尽。在大多数情况下，我们的方法最快。

对于查询 2，`Jena` 内存模型和 `Jena` SDB 模型比我们的方法更快，分别在 3.9 秒和 0.4 秒内给出结果。然而，随着数据集规模增长，`Jena` 内存模型内存耗尽。对于大数据集，我们的实现比 `Jena` SDB 模型快得多。例如，对于 1.1 亿三元组，我们的方法耗时 143.5 秒，而 `Jena` SDB 模型约需 5,000 秒。我们发现 `Jena` SDB 模型无法完成查询 9 的回答。`Jena` 内存模型在小数据集上表现良好，但随着数据集规模增长变得比我们的实现慢，最终内存耗尽。

对于查询 2，在 1.1 亿和 5.5 亿数据集上，`BigOWLIM` 比我们的方法慢。对于 5.5 亿数据集，它耗时 22,693.4 秒，与其其他计时相比突然升高。对于十亿三元组数据集，`BigOWLIM` 更快。应注意到，我们的框架没有任何索引或三元组缓存，而 `BigOWLIM` 利用索引，并在启动时将其加载到主内存中。它也可能将三元组预取到主内存中。

对于查询 9，我们的实现在所有实验中均快于 `BigOWLIM`。

还应注意，我们的 `RDF-3X` 和 `HadoopRDF` 查询均使用冷运行进行测试。这意味着执行前清除了主内存和文件系统缓存。然而，对于 `BigOWLIM`，我们被迫执行热运行。这是因为将数据库加载到 `BigOWLIM` 需要大量时间。因此，在冷运行下我们将轻松胜过 `BigOWLIM`。所以，我们实际上是将 `BigOWLIM` 的热运行与 `HadoopRDF` 的冷运行进行对比。这给 `BigOWLIM` 带来了巨大优势，但在大数据集上，`HadoopRDF` 仍产生了好得多的结果。这表明 `HadoopRDF` 比 `BigOWLIM` 具有更好的可扩展性，并为大数据集提供更高效的查询。

我们执行的最后测试是深度可扩展性测试。为此，我们针对八种不同的数据集大小重复执行了相同的查询，最大规模达到 66 亿。
