
# 降低风险

**降低风险**，或 **风险缓解**，是实施防护措施和对策以消除漏洞或阻断威胁。选择最具成本效益或最有益的对策是风险管理的一部分，但不是风险评估的要素。事实上，对策选择是风险评估后或风险分析后的活动。风险缓解的另一种潜在变体是风险规避。通过消除风险原因来规避风险。一个简单的例子是从服务器中移除文件传输协议 (FTP) 以避免 FTP 攻击，一个更大的例子是搬到内陆位置以避免飓风风险。

## 风险转移

**分配风险** 或 **转移风险** 是将风险所代表的损失成本转嫁给另一个实体或组织。购买保险和外包是分配或转移风险的常见形式。

## 风险接受

**接受风险**、风险容忍度或风险接受，是成本/效益分析显示对策成本会超过因风险导致的可能损失成本后的结果。这也意味着管理层已同意在风险实现时承担后果和损失。在大多数情况下，接受风险需要一份清晰的书面声明，说明为何未实施防护措施、谁对该决策负责，以及风险实现时谁将对损失负责，通常以免责函的形式呈现。组织接受风险的决定基于其风险容忍度。这也称为风险容忍度或风险偏好，即组织吸收已实现风险相关损失的能力。

## 风险威慑

**风险威慑** 是实施威慑措施以阻止潜在的安全和策略违规者的过程。示例包括实施审计、安全摄像头、保安、指示标牌、警告横幅、运动探测器、强认证，以及让人知晓组织愿意与当局合作并起诉参与网络犯罪的人员。

## 风险规避

**风险规避** 是选择风险较低的替代方案或活动，而非默认、常见、权宜或廉价的选项。例如，选择飞往目的地而不是开车前往，就是一种风险规避。另一个例子是将企业选址在亚利桑那州而非佛罗里达州，以避免飓风。

## 风险拒绝

对风险的最后一种但不可接受的可能响应是 **拒绝风险** 或 **忽略风险**。否认风险存在并希望它永远不会实现，都不是对风险有效或审慎的应有注意义务响应。

一旦实施了对策，剩余的风险称为剩余风险。**剩余风险** 包含高层管理人员选择不实施防护措施的针对特定资产的威胁。换句话说，剩余风险是管理层选择接受而非缓解的风险。在大多数情况下，剩余风险的存在表明成本/效益分析显示可用的防护措施不是具有成本效益的威慑手段。

**总风险** 是组织在未实施任何防护措施时将面临的风险总量。总风险的公式如下：

```
威胁 * 漏洞 * 资产价值 = 总风险
```

(注意，此处的 `*` 并不意味着乘法，而是组合函数；这不是一个真正的数学公式。) 总风险与剩余风险之间的差额称为控制差距。控制差距是通过实施防护措施所降低的风险量。剩余风险的公式如下：

```
总风险 - 控制差距 = 剩余风险
```

与一般风险管理一样，处理风险不是一次性过程。相反，安全必须持续维护并不断重申。事实上，重复风险评估和分析过程是一种机制，用于随时间评估安全计划的完整性和有效性。此外，它有助于定位缺陷和发生变更的领域。由于安全会随时间变化，定期重新评估对于维持合理的安全至关重要。

## 对策选择与实施

在风险管理领域，选择对策或控制措施（`security control` 的简称）很大程度上依赖于成本/收益分析结果。但是，在评估安全控制的价值或相关性时，还应考虑其他几个因素：

*   对策的成本应低于资产的价值。
*   对策的成本应低于对策的收益。
*   应用对策的结果应使攻击者的攻击成本高于其从攻击中获得的收益。
*   对策应为真实且已识别的问题提供解决方案。（不要仅仅因为对策可用、有广告宣传或听起来很酷就安装它们。）
*   对策的收益不应依赖于其保密性。这意味着“通过隐晦实现安全”不是可行的对策，任何可行的对策都能经受住公开披露和审查。
*   对策的收益应可测试且可验证。
*   对策应在所有用户、系统、协议等方面提供一致且统一的保护。
*   对策应极少或没有依赖关系，以减少级联故障。
*   对策在初始部署和配置后应只需最少的人工干预。
*   对策应防篡改。
*   对策的覆盖/重置功能应仅对特权操作员可访问。
*   对策应提供故障安全和/或故障保密选项。

请记住，安全的设计应旨在支持和实现业务任务与功能。因此，需要在业务任务的背景下评估对策和防护措施。

安全控制、对策和防护措施可通过管理、逻辑/技术或物理方式实施。这三类安全机制应以纵深防御方式实施，以提供最大效益（参见图 2.6）。

### 技术控制

*技术或逻辑控制*涉及用于管理访问并为资源和系统提供保护的硬件或软件机制。顾名思义，它使用技术手段。逻辑或技术控制的示例包括身份验证方法（如用户名、密码、智能卡和生物识别）、加密、受限接口、访问控制列表、协议、防火墙、路由器、入侵检测系统（`IDS`）和剪裁级别。

### 管理控制

*管理控制*是由组织的安全策略及其他法规或要求定义的政策和程序。它们有时被称为管理控制。这些控制侧重于人员和业务实践。管理控制的示例包括政策、程序、招聘实践、背景调查、数据分类和标记、安全意识和培训工作、休假记录、报告和审查、工作监督、人员控制和测试。

### 物理控制

*物理控制*是你可以亲身接触的项目。它们包括部署的物理机制，用于防止、监控或检测与设施内系统或区域的直接接触。物理控制的示例包括警卫、围栏、运动探测器、上锁的门、密封的窗户、灯光、线缆保护、笔记本电脑锁、工牌、刷卡、护卫犬、摄像头、人员闸和警报器。

## 适用的控制类型

术语*安全控制*指的是一系列广泛的控制，它们执行诸如确保只有授权用户可以登录、防止未授权用户访问资源等任务。*控制*可缓解各种信息安全风险。

只要可能，你都希望预防任何类型的安全问题或事件。当然，这并不总是可能的，意外事件仍会发生。一旦发生，你希望尽快检测到这些事件。检测到事件后，你希望对其进行纠正。

在阅读控制描述时，请注意有些控制被列为多种访问控制类型的示例。例如，建筑物周围的围栏（或周界界定设备）可以是一种预防性控制（物理上阻止某人进入建筑物院落）和/或一种威慑性控制（劝阻某人尝试进入）。

### 威慑控制

*威慑控制*的部署是为了阻止违反安全策略的行为。威慑控制和预防控制相似，但威慑控制通常取决于个人决定不采取不当行动。相比之下，预防控制实际上会阻止该行动。示例包括政策、安全意识培训、锁、围栏、安全工牌、警卫、人员闸和安全摄像头。

### 预防控制

*预防控制*的部署是为了阻止或停止发生不需要的或未授权的活动。预防控制的示例包括围栏、锁、生物识别、人员闸、照明、报警系统、职责分离、轮岗、数据分类、渗透测试、访问控制方法、加密、审计、安全摄像头或闭路电视（`CCTV`）的存在、智能卡、回叫程序、安全策略、安全意识培训、防病毒软件、防火墙和入侵防御系统（`IPS`）。

### 检测控制

*检测控制*的部署是为了发现或检测不需要的或未授权的活动。检测控制在事后运行，只能在活动发生后发现它。检测控制的示例包括保安、运动探测器、安全摄像头或 `CCTV` 捕获事件的记录和审查、轮岗、强制休假、审计追踪、蜜罐或蜜网、入侵检测系统（`IDS`）、违规报告、用户监督和审查以及事件调查。

### 补偿控制

*补偿控制*的部署是为其他现有控制提供各种选项，以协助安全策略的执行和支持。它们可以是除另一控制外额外使用的控制，或代替另一控制使用的控制。例如，组织政策可能规定所有 `PII` 必须加密。审查发现一种预防控制正在加密数据库中的所有 `PII` 数据，但通过网络传输的 `PII` 却以明文形式发送。可以添加补偿控制来保护传输中的数据。

### 纠正控制

`corrective control`（纠正控制）会修改环境，以便在发生不需要或未授权的活动后将系统恢复正常。它试图纠正因安全事件而导致的任何问题。纠正控制可以很简单，例如终止恶意活动或重启系统。它们还包括能够移除或隔离病毒的防病毒解决方案、用于确保丢失数据可恢复的备份和恢复计划，以及能够修改环境以阻止正在进行的攻击的主动 IDS。该控制部署用于在违反安全策略后修复或恢复资源、功能和能力。

### 恢复

`Recovery controls`（恢复控制）是纠正控制的延伸，但具有更高级或更复杂的能力。恢复控制的示例包括备份和恢复、容错驱动器系统、系统镜像、服务器集群、防病毒软件，以及数据库或虚拟机影子复制。就业务连续性和灾难恢复而言，恢复控制可以包括热站点、温站点、冷站点、备用处理设施、服务局、互惠协议、云提供商、移动滚动运营中心和多站点解决方案。

### 指令控制

`directive control`（指令控制）部署用于指导、限制或控制主体的行为，以强制或鼓励其遵守安全策略。指令控制的示例包括安全策略要求或标准、张贴的通知、逃生路线出口标志、监控、监督和程序。

## 安全控制评估

`security control assessment (SCA)`（安全控制评估）是对安全基础设施的各个机制依据基线或可靠性预期进行的正式评估。SCA 可以作为完整安全评估（如渗透测试或漏洞评估）的补充，也可以独立执行。

SCA 的目标是确保安全机制的有效性，评估组织风险管理流程的质量和彻底性，并生成一份报告，说明已部署安全基础设施的相对优势和劣势。

通常，SCA 是联邦机构基于 NIST 特别出版物 800-53A《联邦信息系统安全控制评估指南》（[`csrc.nist.gov/publications/detail/sp/800-53a/rev-4/final`](https://csrc.nist.gov/publications/detail/sp/800-53a/rev-4/final)）实施的一个过程。然而，虽然它被定义为一个政府流程，但评估安全控制可靠性和有效性的概念应被每个致力于维持成功安全工作的组织所采用。

## 监控与度量

安全控制应提供可被监控和度量的效益。如果安全控制的效益无法量化、评估或比较，那么它实际上并不提供任何安全性。安全控制可能提供原生或内部监控，或者可能需要外部监控。在进行初始对策选择时，应将此纳入考量。

衡量对策的有效性并不总是一个绝对值。许多对策提供的是改进的程度，而不是阻止了多少次入侵或挫败了多少次攻击尝试等具体的硬性数字。通常，为了获得对策成功或失败的度量，有必要在安装防护措施前后对事件进行监控和记录。只有已知起点（即正常点或初始风险水平），效益才能被准确度量。成本/效益方程式的一部分要考虑对策的监控和度量。仅仅因为安全控制提供了某级别的安全性提升，并不一定意味着获得的效益具有成本效益。应确定显著的安全性改进，以明确证明部署新对策的费用是合理的。

## 资产估值与报告

风险分析中的一个重要步骤是评估组织资产的价值。如果资产没有价值，则无需为其提供保护。风险分析的主要目标是确保仅部署具有成本效益的防护措施。花费 100,000 美元保护仅值 1,000 美元的资产是毫无意义的。资产的价值直接影响并指导为保护它而部署的防护措施和安全级别。原则上，防护措施的年成本不应超过资产预期年损失成本。

评估资产成本时，有许多方面需要考虑。资产估值的目标是为资产分配一个特定的美元价值，该价值涵盖有形成本和无形成本。确定确切价值通常很难，甚至不可能，但尽管如此，必须建立一个具体的价值。（请注意，下一节关于定性与定量风险分析的讨论可能会阐明此问题。）不当地分配资产价值可能导致无法妥善保护资产，或实施财务上不可行的防护措施。以下列表包括一些影响资产估值的有形和无形因素：

- 采购成本
- 开发成本
- 行政或管理成本
- 维护或保养成本
- 资产获取成本
- 保护或维持资产的成本
- 对所有者和用户的价值
- 对竞争对手的价值
- 知识产权或权益价值
- 市场估值（可持续价格）
- 替换成本
- 生产力提升或降低
- 资产存在和丢失的运营成本
- 资产丢失的责任
- 实用性

为组织分配或确定资产价值可以满足多种需求。它是通过部署防护措施进行资产保护成本/效益分析的基础。它是选择或评估防护措施和对策的一种手段。它为保险目的提供价值，并确立组织的总体净值。它帮助高级管理层准确了解组织内部有哪些资产处于风险之中。了解资产价值还有助于防止尽职照管的疏忽，并鼓励遵守法律要求、行业法规和内部安全策略。

### 风险报告

`Risk reporting`（风险报告）是在风险分析结束时执行的一项关键任务。风险报告涉及制作风险报告并向相关利益方/相关方汇报该报告。对许多组织而言，风险报告只是内部关注的事项，而其他组织可能有法规强制要求向第三方或公众报告其风险发现。

风险报告应准确、及时、涵盖整个组织、清晰精确以支持决策，并定期更新。

## 持续改进

执行风险分析是为了向高层管理人员提供必要的细节，以决定哪些风险应缓解、哪些应转移、哪些应威慑、哪些应规避、哪些应接受。结果是资产预期损失成本与针对威胁和漏洞部署防护措施成本之间的成本/效益比较。风险分析识别风险、量化威胁影响，并协助安全预算编制。它有助于将安全策略的需求和目标与组织的业务目标和意图相结合。风险分析/风险评估是一个“时间点”指标。威胁和漏洞不断变化，风险评估需要定期重新进行，以支持持续改进。

安全性始终在变化。因此，任何已实施的安全解决方案都需要随着时间的推移进行更新和变更。如果所选对策未提供持续改进路径，则应将其替换为提供可扩展安全性改进的对策。

### 风险框架

`风险框架` 是关于如何评估、解决和监控风险的指南或配方。CISSP 考试引用的风险框架的主要示例是 NIST 在特别出版物 800-37 ([`nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-37r1.pdf`](http://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-37r1.pdf)) 中定义的框架。我们鼓励您完整阅读该出版物，但以下是与 CISSP 相关的几段摘录：

> 本出版物提供了将 `风险管理框架 (RMF)` 应用于联邦信息系统的指南。六步 RMF 包括安全分类、安全控制选择、安全控制实施、安全控制评估、信息系统授权和安全控制监控。RMF 通过实施稳健的持续监控流程，推广近实时风险管理和持续信息系统授权的概念，为高级领导提供必要信息，以便就支持其核心任务和业务职能的组织信息系统做出具有成本效益、基于风险的决策，并将信息安全集成到企业架构和系统开发生命周期 (SDLC) 中。在企业内应用 RMF 通过风险执行（职能）将信息系统层面的风险管理流程与组织层面的风险管理流程联系起来，并确立了在组织信息系统中部署并由这些系统继承（即通用控制）的安全控制的责任和问责制。RMF 具有以下特征：
>
> *   通过实施稳健的持续监控流程，推广近实时风险管理和持续信息系统授权的概念；
> *   鼓励使用自动化为高级领导提供必要信息，以便就支持其核心任务和业务职能的组织信息系统做出具有成本效益、基于风险的决策；
> *   将信息安全集成到企业架构和 SDLC 中；
> *   强调安全控制的选择、实施、评估和监控，以及信息系统的授权；
> *   通过风险执行（职能）将信息系统层面的风险管理流程与组织层面的风险管理流程联系起来；以及
> *   确立对部署在组织信息系统中并由这些系统继承（即通用控制）的安全控制的责任和问责制
>
> RMF 步骤包括 [(参见图 2.7)]：
>
> *   **分类** 信息系统以及由该系统处理、存储和传输的信息，依据为影响分析。
> *   **选择** 信息系统的一组初始基线安全控制，依据为安全分类；根据组织风险评估和本地条件，根据需要调整和补充安全控制基线。
> *   **实施** 安全控制，并描述控制如何在信息系统及其运行环境中采用。
> *   **评估** 安全控制，使用适当的评估程序确定控制实施的正确程度、是否按预期运行，以及是否产生了满足系统安全要求方面的预期结果。
> *   **授权** 信息系统运行，依据为对组织运营和资产、个人、其他组织以及国家因信息系统运行而产生的风险的判断，并决定该风险是可接受的。
> *   **监控** 信息系统中的安全控制，持续进行，包括评估控制有效性、记录系统或其运行环境的变更、对相关变更进行安全影响分析，并向指定的组织官员报告系统的安全状态。
>

### 建立并维护安全意识、教育和培训计划

安全解决方案的成功实施需要改变用户行为。这些变化主要包含为遵守安全策略强制规定的标准、指南和程序而对正常工作活动进行的调整。`行为矫正` 涉及用户一定程度的学习。为了开发和管理安全教育、培训和意识，必须明确确定所有相关的知识传递项目，并设计演示、接触、协同和实施计划。

安全培训的前提是 `意识`。建立意识的目标是将安全置于首要位置，使其成为用户公认的实体。意识在整个组织中建立了安全理解的通用基线或基础，重点关注所有员工必须理解和领会的与安全相关的关键或基本主题和问题。意识的建立不仅限于课堂类型的练习，还通过工作环境进行。可以使用许多工具来建立意识，例如海报、通告、时事通讯文章、屏幕保护程序、T 恤、管理层的动员讲话、公告、演示、鼠标垫、办公用品和备忘录，以及传统的讲师授课培训课程。

意识建立了安全理解的最低标准共同分母或基础。所有人员都应充分了解其安全责任和义务。他们应接受培训，知道该做什么和不该做什么。
