## 2. 一个目标机器（MAC 地址为 `12:34:56:AB:CD:EF`）连接到交换机端口。攻击者（MAC 地址为 `78:91:00:ED:BC:A1`）连接到同一台交换机的另一个端口，并运行了数据包捕获程序。网络没有开启端口镜像（span）或端口安全设置。有两条数据包从目标机器发出。消息 1 的目标 MAC 地址为 `E1:22:BA:87:AC:12`。消息 2 的目标 MAC 地址为 `FF:FF:FF:FF:FF:FF`。关于发送的消息，以下哪种说法是正确的？

- **A.** 攻击者将看到消息 1。

- **B.** 攻击者将看到消息 2。

- **C.** 攻击者将看到这两条消息。

- **D.** 攻击者哪条消息都看不见。

![Image](img/r.jpg) **B.** 这个题完全关于交换机的工作原理，并夹杂了一些 MAC 知识。记住，交换机的设计用于过滤单播消息，但会对多组播和广播消息进行泛洪（过滤只发送到一个端口，而泛洪会发送到所有端口）。帧中的广播 MAC 地址很容易识别——它们全都是 *F*，表示地址中的所有 48 位都处于开启状态。在这种情况下，消息 1 是一个单播地址并发送到了它的目的地，而消息 2 显然是一条广播消息，交换机会乐意地将其泛洪到所有端口，包括攻击者的端口。

该题的其他版本将集中在攻击者可以利用哪些手段来查看该数据包上。如果攻击者希望看到所有消息，可以使用 MAC 泛洪（MAC flood）将交换机变成集线器，从而有效地将所有数据包泛洪到所有端口。另一个选项是端口镜像（span，进入交换机配置并告诉它将所有指向特定端口的流量发送到该端口*以及*攻击者的端口）。最后，*端口窃取*（port stealing，来自 EC-Council 一个非常有趣的记忆术语）允许攻击者在 MAC 泛洪尝试期间利用竞态条件（交换机不断更新端口的 MAC 地址绑定），从而有效地窃取一个端口并嗅探所有指向目标机器的流量。

![Image](img/w.jpg) **A** 是错误的，因为单播目标 MAC 地址与攻击者的机器不匹配。当交换机读取帧并与内部地址列表（CAM 表）对比时，它会被过滤并发送到适当的权限端口。

![Image](img/w.jpg) **C** 是错误的，因为交换机不会将两条消息都泛洪到攻击者的端口——它只泛洪广播和多组播。

![Image](img/w.jpg) **D** 是错误的，因为广播地址肯定会被攻击者看到。

## 3. 你接入了目标组织的一个网络子网。你开始通过学习该子网上所有重要的 MAC 地址来发起攻击。一段时间后，你决定拦截两个主机之间的消息。你向 Host A 发送广播消息，显示你的 MAC 地址属于 Host B。这里实现的是什么操作？

- **A.** ARP 毒攻击，允许你在不中断它们通信过程的情况下，看到来自任一主机的所有消息

- **B.** ARP 毒攻击，允许你看到从 Host A 发到 Host B 的消息

- **C.** ARP 毒攻击，允许你看到从 Host B 发到 Host A 的消息

- **D.** ARP 毒攻击，允许你看到从 Host A 发往任何地址的消息

- **E.** ARP 毒攻击，允许你看到从 Host B 发往任何地址的消息

![Image](img/r.jpg) **B.** ARP 毒攻击是一种相对简单的方法，可以让自己处于“中间人”位置并监视流量（顺便说一下，小心使用 *man in the middle* 这个词，因为它通常指的是你并不中断流量的位置）。每当你的机器进行名称查找或 ARP（一种广播协议）接收到宣称 MAC 与 IP 匹配的未请求请求消息时，ARP 缓存就会更新。在这个例子中，你告诉 Host A 你拥有 Host B 的 MAC 地址。Host A 将更新其缓存，当操作系统正在构造消息时，它会乐意地将伪造的地址放在其中。只需记住，ARP 毒攻击通常带有很大的噪声，如果开启了端口安全，可能很容易被发现：取决于实现方式，当一个错误的 MAC 尝试使用端口或当看到多个声称不同 MAC 的广播包时，端口将锁定（在极客术语中为 *琥色*）。此外，注意尝试 ARP 毒攻击可能带来的拒绝攻击副作用——你可能甚至还没尝试就让目标崩溃了，更不用说 Host B 最终会发现它没有从 Host A 接收到任何东西。顺带一提，可以使用名为 `xARP` ([www.chrismc.de](https://www.chrismc.de)) 的工具检测 ARP 毒攻击。

![Image](img/w.jpg) **A** 错误原因有两个。首先，你不会收到发往世界任何地方的消息——你只会收到从 Host A 发到 Host B 的消息。其次，两个主机之间的通信流将受到影响。事实上，Host A 永远无法与 Host B 通信：ARP 毒攻击让所有消息都发给了你，这个黑客。

![Image](img/w.jpg) **C** 是错误的，因为交换机不会将两条消息都泛洪到攻击者的端口——它只泛洪广播和多组播。

![Image](img/w.jpg) **D** 是错误的，因为广播地址肯定会被接收者看到。

![Image](img/w.jpg) **E** 是错误的，因为你没有对 Host B 投毒。

## 4. 你的目标子网受防火墙 DMZ 保护。侦测显示防火墙允许从外部到内部的部分流量，但阻止了大部分。指向 DMZ 中 Web 服务器的 HTTP 流量是被允许的，以及标准的 DNS 查询。以下哪项可以提供规避防火墙的方法？

- **A.** ACK 扫描

- **B.** 防墙漫

- **C.** 误报泛洪

- **D.** TCP over DNS

![Image](img/r.jpg) **D.** 在提供的选项中，TCP over DNS 是唯一合理的。TCP over DNS 正如其名——通过使用 53 端口发送本应使用其他端口的 TCP 流量。由于防火墙通常允许 DNS 请求通过，因此将流量隐藏在 53 端口变得既方便又相对简单。整个过程确实需要特殊的 DNS 服务器和 DNS 客户端设置，但实现步骤并不是高科学。虽然 TCP over DNS *会*允许你规避防火墙并在内部发送流量，但它*不会*为你提供即时的机器访问或其他功能——它只是允许你在不被察觉的情况下通过防火墙发送流量。TCP over DNS 工具包括 `Iodine` ([`code.kryo.se/iodine/`](http://code.kryo.se/iodine/)), `DNS Tunnel` ([`dnstunnel.de`](http://dnstunnel.de)) 和 `Netcross` ([`sourceforge.net/projects/netcross`](https://sourceforge.net/projects/netcross))。

另一种常见的通过防火墙的方法是 HTTP 隧道。原理相同，只是在 HTTP 隧道中你滥用 80 端口而不是 53 端口。HTTP 隧道工具包括 `HTTPort` ([www.targeted.org](https://www.targeted.org))、`SuperNetwork Tunnel` ([networktunnel.net](https://networktunnel.net)) 和 `HTTP-Tunnel` (www.http-tunnel.com)。

![Image](img/w.jpg) **A** 是错误的，因为 ACK 扫描无法隐藏流量或规避防火墙。扫描本身会很大且嘈杂，且对防火墙产生任何影响。

![Image](img/w.jpg) **B** 是错误的，因为防火墙漫是一种发现哪些端口是开启的（即防火墙允许通过的端口）以及哪些是关闭的极佳技术。然而，它无法隐藏流量或规避任何怀疑。

![Image](img/w.jpg) **C** 是错误的，因为虽然误报洪水（false positive flooding）确实为 IDS 中的攻击者提供了良好的“掩护火力”，但它对防火墙没有任何实质影响——指向其他端口的流量将被拦截，因为这就是防火墙的功能。
