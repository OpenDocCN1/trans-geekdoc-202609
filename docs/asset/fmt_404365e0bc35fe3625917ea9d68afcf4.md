# 第 7 章：领域 6：安全评估与测试

## 摘要

领域 6 讨论安全评估与测试，它们是任何信息安全计划的关键组成部分。组织必须准确评估其实际安全状况，聚焦最关键的组件，并做出必要的变更以实现改进。本领域描述了评估与测试的两大主要组成部分：整体安全评估（包括漏洞扫描、渗透测试、安全评估和安全审计）以及通过静态和动态方法测试软件。静态测试被动地测试代码：代码不运行。这包括演练、语法检查和代码审查。动态方法包括模糊测试，这是一种黑盒测试，向软件程序提交随机的、格式错误的数据作为输入，以确定它们是否会崩溃。

## 关键词

违规攻击模拟；动态应用安全测试；模糊测试；关键绩效指标；关键风险指标；误用用例测试；渗透测试；静态应用安全测试；合成事务

## 本章考试目标

*   安全控制测试
*   收集安全流程数据

## 独有术语与定义

*   **违规攻击模拟**——旨在自动化渗透测试，且通常全天候（24/7/365）运行
*   **动态应用安全测试**——在执行代码时对其进行测试
*   **模糊测试**——一种黑盒测试，向软件程序提交随机的、格式错误的数据作为输入，以确定它们是否会崩溃
*   **关键绩效指标**——一种衡量可用性的方法
*   **关键风险指标**——一种衡量风险的方法
*   **误用用例测试**——对对手滥用应用程序的影响进行建模
*   **渗透测试**——经授权尝试闯入组织的物理或电子边界（有时两者兼有）
*   **静态应用安全测试**——被动测试代码：代码不运行
*   **合成事务**——也称为合成监控：涉及构建脚本或工具，模拟应用程序中通常执行的活动

## 简介

安全评估与测试是任何信息安全计划的关键组成部分。组织必须准确评估其实际安全状况，聚焦最关键的组件，并做出必要的变更以实现改进。

在本领域中，我们将讨论评估与测试的两大主要组成部分：安全控制测试（包括漏洞评估、渗透测试和安全审计）以及收集和分析安全流程数据（以确定安全控制的有效性）。

请注意，本领域与第 9 章，领域 8：软件开发安全存在重叠，特别是在应用程序测试方面。我们将在第 9 章中讨论道德披露和代码审查等概念。

## 安全控制测试

存在多种流程来评估安全控制的有效性。范围较窄的测试包括渗透测试、漏洞评估和安全审计。安全评估是一种范围更广的测试，可能将较窄的测试（如渗透测试）作为子部分包含在内。

### 内部、外部、员工和第三方测试

“内部”和“外部”这两个术语可能存在歧义。“外部”是指测试的发起位置（例如从互联网发起的渗透测试），还是指渗透测试人员的角色（第三方或员工）？NIST SP 800-115 给出了明确定义：

*   **内部安全测试**：从组织安全边界内部进行的安全测试
*   **外部安全测试**：从组织安全边界外部进行的安全测试 [[1]](#Ch007_337-359_B978044318734600009X.xhtml#bb0010)

这总共衍生出四种测试类型：内部/员工、外部/员工、内部/第三方和外部/第三方。

### 渗透测试

渗透测试人员是一名道德黑客，获得授权尝试闯入组织的物理或电子边界（有时两者兼有）。**渗透测试**（简称“渗透测试”）旨在确定不道德的黑客是否能做到同样的事情。这是一种范围较窄但通常很有用的测试，特别是当渗透测试人员成功时。

渗透测试可能包括以下测试：

*   网络（互联网）
*   网络（内部或 DMZ）
*   电话扫描
*   无线
*   物理（尝试进入设施或房间）

网络攻击可能利用客户端攻击、服务端攻击或 Web 应用程序攻击。有关这些攻击的更多信息，请参阅第 4 章，领域 3：安全架构与工程。**电话扫描**使用调制解调器拨打一系列电话号码，寻找应答调制解调器的载波音（渗透测试人员随后尝试访问应答系统）；该名称源自 1983 年的电影《战争游戏》。

**社会工程学**是一种无技术或低技术手段，利用人类心理绕过安全控制。社会工程学可结合多种攻击类型使用，特别是客户端攻击或物理测试。将社会工程学攻击与客户端攻击相结合的一个例子是：发送主题为“五级飓风即将袭击佛罗里达！”的恶意软件邮件。第 4 章，领域 3：安全架构与工程中描述了一种物理社会工程学攻击（用于尾随授权用户进入大楼）。

**零知识**测试（也称为黑盒测试）是“盲测”；渗透测试人员没有任何外部或受信信息，仅凭公开信息开始攻击。**全知识测试**（也称为**透明盒测试**）向渗透测试人员提供内部信息，包括网络图、策略和程序，有时还包括之前渗透测试人员的报告。**部分知识**测试介于零知识和全知识之间：渗透测试人员接收一些有限的受信信息。

一些客户倾向于零知识方法，认为这能更准确地模拟真实攻击者的过程。这可能是一个错误的前提：真实攻击者可能是内部人员，或拥有内部信息。

全知识测试可以高效得多，使渗透测试人员能更快地发现薄弱环节。大多数渗透测试的范围都包含对测试耗时的限制。有限的测试时间可能导致测试失败，而更多的时间可能带来成功。全知识测试也更安全：如果渗透测试人员在开始测试前拥有关于目标的详尽信息，系统崩溃的可能性就较小。

#### 渗透测试工具与方法论

渗透测试人员通常使用渗透测试工具，其中包括开源的 `Metasploit` ([`www.metasploit.com`](https://www.metasploit.com)) 和闭源的 `Cobalt Strike` ([`www.cobaltstrike.com/`](https://www.cobaltstrike.com/)) 以及 `Immunity Canvas` ([`www.immunitysec.com/`](https://www.immunitysec.com/))。渗透测试人员还使用自定义工具，以及发布在互联网上的恶意软件样本和代码。

渗透测试人员使用以下方法论：

*   规划
*   侦察
*   扫描（也称为枚举）
*   漏洞评估
*   利用
*   报告

不道德的黑客通常遵循类似的方法论（尽管他们可能进行较少的规划，且显然会省略报告环节）。他们还会掩盖踪迹（擦除日志和其他入侵迹象），并经常通过安装后门来破坏系统完整性（以维持访问权限）。渗透测试人员应始终保护数据和系统完整性。

> **Note**
>
> 渗透测试有时颇具争议。有人认为渗透测试实际上测试的是渗透测试人员的技能，而非组织的边界安全。如果渗透测试成功，对组织是有价值的。但如果渗透测试失败了怎么办？是因为不存在边界风险？还是因为渗透测试人员缺乏技能或时间来完成测试？抑或是因为渗透测试的范围过窄？

#### 确保机密性、数据完整性和系统完整性

渗透测试人员必须确保测试过程中访问的任何敏感数据的机密性。例如，如果渗透测试的目标是信用卡数据库，测试人员可能无合法权利查看或下载信用卡信息。测试人员通常会要求在系统中与信用卡数据相同区域、受相同权限保护的位置放置一个不包含受监管或敏感数据的虚拟文件（有时称为 Flag）。如果测试人员能读取和/或写入该文件，即证明他们本可以对信用卡数据做同样的操作。

渗透测试人员必须确保客户系统的系统完整性和数据完整性。任何主动攻击（向系统发送数据，而非被动的只读攻击）都可能造成损害：即使是经验丰富的渗透测试人员也不例外。所有相关方必须清楚理解这一风险：测试通常在变更维护窗口期间进行，就是出于这个原因。

在渗透测试开始前应讨论的一个潜在问题是，遇到先前或当前成功恶意攻击迹象的风险。渗透测试人员有时会发现他们不是第一个攻破系统的攻击者：别人抢先了一步。如果攻击者认为已被发现，往往会变得更加恶意，有时会破坏数据和系统完整性。此时系统完整性处于风险之中，渗透测试人员应终止测试，并立即上报该问题。

最后，最终的渗透测试报告应受到最高级别的保护：它包含攻击该组织的路线图。

### 入侵攻击模拟

许多组织每年进行一次第三方渗透测试，通常出于合规原因。这是一种有用但不频繁的测试。入侵攻击模拟旨在实现渗透测试的自动化，且通常全天候运行。其目标是测试组织的预防和检测能力。例如：自动化渗透测试是否成功（预防：系统是否被攻破）？检测：SOC 是否察觉？这是一种紫队演练形式，将红队演练（渗透测试）与蓝队演练（检测和防御入侵）相结合：

> 红队和蓝队演练长期以来一直是重要的安全工具，但它们有两个关键缺点：高度依赖人工且资源密集。这意味着大多数组织只能间歇性地运行这些测试。这意味着在测试间隔的几周或几个月内，漏洞可能在未被发现的情况下出现，而防御者对其安全环境的真实状态知之甚少……
>
> 通过结合红队和蓝队技术（称为“紫队演练”实践）并将其自动化，入侵攻击平台提供持续覆盖。这些模拟可全天候运行，确保组织对其防御就绪状态的真实情况保持更深度的可见性。这至关重要，因为攻击者只要有足够的时间就能攻破任何安全设置，这使得持续测试成为降低风险最有效的方式 [[2]](#Ch007_337-359_B978044318734600009X.xhtml#bb0015)。

### 漏洞评估

**漏洞评估**（也称为漏洞扫描）针对预定义漏洞列表（如系统配置错误、软件过时或缺乏补丁）扫描网络或系统。可使用 `Nessus`（<https://www.tenable.com/products/nessus-vulnerability-scanner>）或 `OpenVAS`（<https://www.openvas.org>）等漏洞测试工具来识别漏洞。

我们在第 2 章“领域 1：安全与风险管理”中了解到风险 = 威胁 × 漏洞。重要的是要记住，漏洞扫描器只展示了风险方程的一半：其输出必须与威胁相匹配，才能映射真实风险。这是需要识别的重要一半，但这些工具只完成了总工作的一部分。许多组织陷入只查看漏洞而不将其与威胁匹配的误区，因此无法理解或缓解真实的业务风险。

### 安全审计

**安全审计**是针对已发布标准的测试。例如，组织可能因 PCI-DSS（支付卡行业数据安全标准，详见第 3 章“领域 2：资产安全”）合规性而接受审计。PCI-DSS 包含许多必需控制，如防火墙、特定访问控制模型和无线加密。审计员随后验证站点或组织是否符合发布的标准。

### 安全评估

**安全评估**是评估访问控制有效性的整体方法。安全评估不局限于渗透测试或漏洞评估，而是具有更广泛的范围。

安全评估跨多个领域查看许多控制，可能包括以下内容：

*   Policies, procedures, and other administrative controls（策略、程序和其他管理控制）
*   Assessing the real world-effectiveness of administrative controls（评估管理控制的现实有效性）
*   Change management（变更管理）
*   Architectural review（架构审查）
*   Penetration tests（渗透测试）
*   Vulnerability assessments（漏洞评估）
*   Security audits（安全审计）

如上列表所示，安全评估可能包含其他不同的测试，如渗透测试。其目标是广泛覆盖许多其他特定测试，以确保考虑访问控制的所有方面。

### 日志审查

作为一种安全控制，日志在安全问题检测、事件响应决策支持及取证审查中发挥着至关重要的作用。从评估和测试的角度来看，目标是审查日志以确保它们能尽可能有效地支持信息安全。

审查 IT 系统中的安全审计日志是验证访问控制机制是否充分执行的最简单方法之一。审查审计日志主要是一种检测性控制。

根据 NIST Special Publication 800-92（<https://csrc.nist.gov/publications/detail/sp/800-92/final>），应收集以下日志类型：

*   **Network Security Software/Hardware（网络安全软件/硬件）：**
    *   Antivirus logs（防病毒日志）
    *   IDS/IPS logs（入侵检测/防御系统日志）
    *   Remote Access Software（远程访问软件，如 VPN 日志）
    *   Web proxy（Web 代理）
    *   Vulnerability management（漏洞管理）
    *   Authentication servers（认证服务器）
    *   Routers and firewalls（路由器和防火墙）
*   **Operating System（操作系统）：**
    *   System events（系统事件）
    *   Audit records（审计记录）
*   **Applications（应用程序）：**
    *   Client requests and server responses（客户端请求和服务端响应）
    *   Usage information（使用信息）
*   重大运营行动 [[3]](#Ch007_337-359_B978044318734600009X.xhtml#bb0020)

从主动审计日志管理和监控中获得的情报非常有益：数千个系统收集的防病毒日志可以非常准确地描绘恶意软件的当前状态。防病毒警报结合来自身份验证服务器的失败身份验证警报激增，或出站防火墙拒绝激增，可能表明密码猜测蠕虫正试图在网络上传播。

根据 Anton Chuvakin 的《日志分析的五个错误》（参见 [`www.computerworld.com/article/2567666/five-mistakes-of-log-analysis.xhtml`](https://www.computerworld.com/article/2567666/five-mistakes-of-log-analysis.xhtml)），审计记录管理通常面临五个不同的问题：

1.  日志未定期及时审查。
2.  审计日志和审计跟踪存储时间不够长。
3.  日志未标准化，也无法通过关联工具集查看——只能从被审计的系统查看。
4.  日志条目和警报未按优先级排序。
5.  审计记录仅针对“坏东西”进行审查 [[4]](#Ch007_337-359_B978044318734600009X.xhtml#bb0025)。

许多组织收集审计日志，然后犯下上述一种或多种错误。上一段提到的有用情报（通过防病毒警报结合身份验证失败或防火墙拒绝来识别蠕虫）只有避免这些错误才能实现。

### 集中式日志记录

应配置集中式日志存储。将日志存放在中央存储库中，可实现更具可扩展性的安全监控和入侵检测能力。如果端点的日志视图被损坏或被故意篡改，集中式日志存储库还可以帮助验证日志信息的完整性。在传输和存储日志数据时，应考虑确保日志信息的完整性。

> **注意**
>
> `Syslog` 是应用最广泛的日志记录子系统，默认通过 `UDP/514` 以明文形式向远程服务器传输日志数据。`UDP` 是一种不保证传输送达的传输协议，这对确保日志记录的连续性有影响。这意味着，即使端点没有任何机制得知传输失败，中央日志服务器也可能未接收到所有日志数据。`Syslog` 的明文特性意味着处于合适位置的攻击者可以在日志数据遍历网络时查看（潜在的敏感）日志数据。由于缺乏认证、缺乏加密，且使用 `UDP` 作为第 4 层传输协议，`Syslog` 消息也可能被伪造。

除了集中式日志外，最好至少在端点系统本身上保留一些有限的近期日志。除了集中式日志存储外，拥有本地日志在多方面都有帮助。如果日志记录的连续性中断，仍可能从端点恢复日志。如果攻击者故意破坏或编辑端点上的日志，对比差异可指导事件响应人员了解攻击者的活动。

### 日志保留
