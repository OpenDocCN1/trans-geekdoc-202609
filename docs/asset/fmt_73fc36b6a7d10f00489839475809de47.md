## 第 8 章：安全模型、设计与能力原则

**本章涵盖的 CISSP 考试主题包括：**

*   **领域 3：安全架构与工程**
    *   3.1 使用安全设计原则实施和管理工程流程
    *   3.2 理解安全模型的基本概念
    *   3.3 根据系统安全需求选择控制措施
    *   3.4 理解信息系统的安全能力

理解安全解决方案背后的理念有助于缩小寻找特定安全需求的最佳控制措施的范围。在本章中，我们将讨论安全模型，包括状态机模型、`Bell-LaPadula` 模型、`Biba` 模型、`Clark-Wilson` 模型、`Take-Grant` 模型以及 `Brewer` 和 `Nash` 模型。本章还描述了通用准则以及政府和企业用于从安全角度评估信息系统的其他方法，特别强调美国国防部和国际安全评估标准。最后，我们将讨论常见的设计缺陷和其他可能使信息系统易受攻击的问题。

### 使用安全设计原则实施和管理工程流程

安全性应在系统开发的每个阶段都予以考量。程序员应致力于将安全性构建到他们开发的每个应用程序中，为关键应用程序以及处理敏感信息的应用程序提供更高级别的安全性。从开发项目的早期阶段就考虑其安全影响至关重要，因为将安全性构建*进*系统比向现有系统*添加*安全性要容易得多。以下各节将讨论几项基本的安全设计原则，这些原则应在硬件或软件项目的工程流程早期实施和管理。

#### 对象和主体

在安全系统中控制对任何资源的访问涉及两个实体。*主体* 是发出请求以访问资源的用户或进程。访问可以指从资源读取或向资源写入。*对象* 是用户或进程想要访问的资源。请记住，主体和对象是指某个特定的访问请求，因此同一资源在不同的访问请求中既可以充当主体，也可以充当对象。

例如，进程 A 可能会向进程 B 请求数据。为了满足进程 A 的请求，进程 B 必须向进程 C 请求数据。在该示例中，进程 B 是第一个请求的对象，也是第二个请求的主体：

| 第一个请求 | | 进程 A (主体) | | 进程 B (对象) |
| --- | --- | --- | --- | --- |
| 第二个请求 | | 进程 B (主体) | | 进程 C (对象) |

这也是*传递信任*的一个示例。*传递信任* 是指如果 A 信任 B 且 B 信任 C，则 A 通过传递性继承了对 C 的信任——这就像在数学方程中一样：如果 a = b，且 b = c，则 a = c。在前面的示例中，当 A 向 B 请求数据，然后 B 向 C 请求数据时，A 接收到的数据实质上来自 C。传递信任是一个严重的安全问题，因为它可能导致绕过 A 和 C 之间的限制，特别是当 A 和 C 都支持与 B 交互时。一个例子是组织为提高员工工作效率而屏蔽对 Facebook 或 YouTube 的访问。因此，员工 (A) 无法访问特定互联网站点 (C)。然而，如果员工能够访问 Web 代理、虚拟专用网络 (VPN) 或匿名化服务，则这可以作为绕过本地网络限制的手段。换句话说，如果员工 (A) 正在访问 VPN 服务 (B)，而 VPN 服务 (B) 可以访问被屏蔽的互联网服务 (C)；那么 A 就能通过利用传递信任，经由 B 访问 C。

#### 闭源系统和开源系统

系统的设计和构建遵循两种不同的理念：*闭源系统* 旨在与有限范围的其他系统良好协作，这些系统通常均来自同一制造商。闭源系统的标准通常是专有的，且不公开披露。另一方面，*开源系统* 是使用商定的行业标准进行设计的。开源系统更容易与支持相同标准的不同制造商的系统集成。

闭源系统较难与异构系统集成，但可能更安全。闭源系统通常由不包含行业标准的专有硬件和软件组成。这种缺乏集成便利性的特性意味着，针对许多通用系统组件的攻击要么无效，要么必须经过定制才能成功。在许多情况下，攻击闭源系统比攻击开源系统更难。许多已知存在漏洞的软件和硬件组件可能不存在于闭源系统中。除了闭源系统缺乏已知易受攻击的组件外，通常还需要具备针对特定目标系统更深入的知识才能发动成功的攻击。

开源系统通常更容易与其他开源系统集成。例如，用一台 Microsoft Windows Server 机器、一台 Linux 机器和一台 Macintosh 机器创建局域网 (LAN) 非常容易。尽管这三台计算机使用不同的操作系统，且可能代表多达三种不同的硬件架构，但每台都支持行业标准，使得网络通信（或其他通信）变得容易。然而，这种便利性是有代价的。因为标准通信组件被纳入了这三个开源系统中的每一个，所以存在更多可预测的入口点和攻击方法。总体而言，它们的开放性使其更容易受到攻击，而其广泛的可用性使得攻击者能够找到（甚至练手）大量潜在目标。此外，开源系统比闭源系统更流行，吸引了更多关注。掌握了基本攻击技能的攻击者会在开源系统上发现比闭源系统更多的目标。这个更大的潜在目标“市场”通常意味着更重视以开源系统为攻击目标。不可否认，关于如何攻击开源系统的共享经验和知识库比闭源系统大得多。

#### 确保机密性、完整性和可用性的技术

为保证数据的机密性、完整性和可用性，必须确保所有有权访问数据的组件都是安全且行为良好的。软件设计师使用不同的技术来确保程序仅执行所需操作，不做多余操作。假设一个程序对另一个程序正在使用的内存区域进行写入和读取。第一个程序可能会破坏所有三大安全原则：机密性、完整性和可用性。如果受影响的程序正在处理敏感或机密数据，则无法再保证该数据的机密性。如果数据以不可预测的方式被覆盖或篡改（当多个读取者和写入者无意中访问同一共享数据时，这是常见问题），则无法保证完整性。而且，如果数据修改导致损坏或彻底丢失，则可能导致数据无法在未来使用。虽然以下各节讨论的概念都与软件程序相关，但它们也常用于安全领域的各个方面。例如，物理隔离可确保对硬件的所有物理访问均受到控制。

#### 隔离

软件设计师使用进程限制来限制程序的行为。简单来说，进程 `confinement` 允许进程仅对特定的内存位置和资源进行读写。这也被称为 `sandboxing`（沙箱隔离）。操作系统或其他安全组件会禁止非法的读/写请求。如果进程尝试发起超出其授权权限的操作，该操作将被拒绝。此外，还可能采取进一步的措施，例如记录违规尝试。必须符合更高安全等级的系统通常会记录所有违规行为，并以某种切实的方式做出响应。通常，违规进程会被终止。限制可以在操作系统本身中实现（例如通过进程隔离和内存保护），通过使用限制应用程序或服务来实现（例如 `www.sandboxie.com` 上的 Sandboxie），或者通过虚拟化或 Hypervisor 解决方案来实现（例如 VMware 或 Oracle 的 VirtualBox）。

#### 边界

在系统上运行的每个进程都会被分配一个授权级别。授权级别告诉操作系统该进程可以做什么。在简单的系统中，可能只有两个授权级别：用户和内核。授权级别告诉操作系统如何为进程设置边界。进程的 `bounds`（边界）由对其可访问的内存地址和资源设置的限制组成。边界规定了进程被限制或包含在其中的区域。在大多数系统中，这些边界为每个进程划分出逻辑内存区域供其使用。操作系统负责强制执行这些逻辑边界，并禁止访问其他进程。更安全的系统可能需要物理边界的进程。物理边界要求每个受限进程在物理上与其他受限进程分离的内存区域中运行，而不仅仅是在同一内存空间中逻辑上受限。物理边界内存成本可能非常高，但它也比逻辑边界更安全。

#### 隔离

当进程通过强制执行访问边界而被限制时，该进程将在隔离环境中运行。进程隔离确保任何行为仅影响与该隔离进程相关的内存和资源。`Isolation`（隔离）用于保护操作环境、操作系统（OS）内核以及其他独立应用程序。隔离是稳定操作系统的基本组成部分。无论出于善意还是恶意，隔离都能防止应用程序访问另一个应用程序的内存或资源。操作系统可能提供中介服务，例如剪切粘贴和资源共享（如键盘、网络接口和存储设备访问）。

这三个概念（限制、边界和隔离）使设计安全程序和操作系统变得更加困难，但它们也使实施更安全的系统成为可能。

#### 控制

为确保系统安全，你需要允许主体仅访问授权的客体。`control`（控制）使用访问规则来限制主体对客体的访问。访问规则规定了哪些客体对每个主体是有效的。此外，一个客体可能对一种访问类型有效，但对另一种访问类型无效。一种常见的控制是文件访问控制。可以通过将文件设置为大多数用户只读、仅对拥有修改权限的一小部分用户可读写，来保护文件免遭修改。

既有强制访问控制，也有自主访问控制，通常分别称为强制访问控制（MAC）和自主访问控制（DAC）（有关访问控制的深入讨论，请参见第 14 章“控制和监控访问”）。对于强制控制，会考虑主体和客体的静态属性来确定访问的允许性。每个主体拥有定义其访问资源的许可或权限的属性。每个客体拥有定义其分类的属性。不同类型的安全方法以不同方式对资源进行分类。例如，如果安全系统能找到一条规则，允许具有主体 A 许可的主体访问具有客体 B 分类的客体，则授予主体 A 访问客体 B 的权限。

自主控制与强制控制的不同之处在于，主体有一定能力定义要访问的客体。在限制范围内，自主访问控制允许主体根据需要定义要访问的客体列表。此访问控制列表充当主体可修改的动态访问规则集。施加在修改上的约束通常与主体的身份有关。基于身份，主体可能被允许添加或修改定义对客体访问的规则。

强制和自主访问控制都通过主体限制对客体的访问。控制的主要目标是通过禁止授权或未授权主体的未授权访问，来确保数据的机密性和完整性。

#### 信任与保证

适当的安全概念、控制和机制必须在设计和架构阶段之前及期间集成，以生成可靠的安全产品。安全问题不应作为事后补充添加；这会导致疏忽、成本增加和可靠性降低。一旦安全集成到设计中，就必须对其进行工程化、实施、测试、审计、评估、认证，最后授权。

`trusted system`（可信系统）是指所有保护机制协同工作，为多类用户处理敏感数据，同时保持稳定安全的计算环境的系统。`Assurance`（保证）简单定义为对安全需求满足程度的信心度。保证必须持续维护、更新和重新验证。如果可信系统经历已知变更，或已过相当长一段时间，均属实。无论哪种情况，都发生了某种层面的变更。变更往往是安全的对立面；它常会削弱安全。因此，每当发生变更时，都需要重新评估系统，以验证其先前提供的安全级别是否仍然完好。保证因系统而异，必须在单个系统上建立。然而，可以跨同类型的众多系统、支持相同服务的系统或部署在相同地理位置的系统，建立保证等级或级别。因此，信任可以通过实施特定安全功能构建到系统中，而保证则是在现实场景中对这些安全功能的可靠性和可用性的评估。

### 理解安全模型的基本概念

在信息安全领域，模型提供了一种将安全策略形式化的方法。此类模型可以是抽象的或直观的（有些是明确数学化的），但所有模型旨在提供一组显式规则，计算机可遵循这些规则来实现构成安全策略的基本安全概念、过程和程序。这些模型提供了一种途径，加深你对计算机操作系统应如何设计和开发以支持特定安全策略的理解。

`security model`（安全模型）为设计师提供了一种将抽象陈述映射为安全策略的方法，该策略规定了构建硬件和软件所需的算法和数据结构。因此，安全模型给软件设计师提供了一个衡量其设计和实现的标准。当然，该模型必须支持安全策略的每个部分。这样，开发人员可以确信其安全实现支持安全策略。

#### 安全模型概述

您将在以下章节中探索多种安全模型；所有这些模型都能阐明安全性是如何融入计算机体系结构和操作系统设计中的：

*   可信计算基
*   状态机模型
*   信息流模型
*   非干扰模型
*   Take-Grant 模型
*   访问控制矩阵
*   Bell-LaPadula 模型
*   Biba 模型
*   Clark-Wilson 模型
*   Brewer 和 Nash 模型（也称为中墙模型）
*   Goguen-Meseguer 模型
*   Sutherland 模型
*   Graham-Denning 模型

尽管不存在绝对安全的系统，但我们可以设计和构建合理安全的系统。事实上，如果一个安全系统符合一组特定的安全标准，就可以说它表现出一定级别的信任度。因此，信任可以构建到系统中，随后进行评估、认证和授权。但在讨论每个安全模型之前，我们必须建立一个大多数安全模型赖以构建的基础。这个基础就是可信计算基。

##### 可信计算基

美国国防部的一项旧标准，俗称橙皮书/可信计算机系统评价标准（`TCSEC`）（DoD 标准 5200.28，本章后面“彩虹系列”部分将详细介绍）将*可信计算基（`TCB`）*描述为硬件、软件和控制措施的组合，它们协同工作以形成一个可信基础，从而强制执行您的安全策略。`TCB` 是完整信息系统的一个子集。它应尽可能小，以便通过详细分析合理地确保系统满足设计规范和要求。`TCB` 是该系统中唯一可被信任以遵循并强制执行安全策略的部分。系统的每个组件不一定都要受信。但每当您从安全角度考虑系统时，评估都应包括定义该系统 `TCB` 的所有受信组件。

一般来说，系统中的 `TCB` 组件负责控制对系统的访问。`TCB` 必须提供方法来访问 `TCB` 内部和外部的资源。`TCB` 组件通常限制 `TCB` 外部组件的活动。`TCB` 组件有责任确保系统在所有情况下都能正常运行，并在任何情况下都遵守安全策略。
