
* **负载均衡** 技术将传入请求分发到分布式数据库的多个节点上，确保工作负载均匀分布。这有助于防止任何单个节点因请求过多而不堪重负，通过避免瓶颈和优化资源利用率来提高可用性。

* **故障检测与恢复** 机制对高可用性至关重要。节点可以定期检查其他节点的健康状况并检测故障。检测到故障后，系统可采取适当措施，如提升副本以替换故障节点或重新分发数据。自动故障检测和恢复可将停机时间降至最低，确保持续可用。

* **冗余与故障转移**：冗余涉及拥有多个可执行相同功能的节点或组件。发生故障时，故障转移机制可将请求重定向到健康节点或激活备用副本。冗余和故障转移策略通过最大限度地减少故障对系统运行的影响，提供容错能力并提高可用性。

通过组合这些技术，分布式数据库可以通过确保持续访问数据和不间断运行来实现高可用性，即使面临故障或网络中断。具体使用的方法取决于数据库系统的设计、需求和期望的可用性级别。

# NoSQL 的优势

在比较来自不同供应商的关系型数据库系统时，很明显它们有许多共同点。考虑到它们都基于同一个基本逻辑概念，这并不令人惊讶。但 NoSQL 数据库则不然。每个 NoSQL 数据库都是为填补特定利基市场而设计的，导致不同系统之间存在广泛的差异。正如我们稍后将看到的，这些数据库可以归类为大的家族，但它们都共享一组共同的存在动机。这些动机主要分为三类：应对大量数据、提升性能，以及实现更敏捷的数据库开发流程。

正如我们已经注意到的，数据库规模不断增大是一致的趋势。出于实际原因，这意味着实施“横向扩展”策略，在多台计算机上支持数据库，从而引发上述所有分布式系统问题。

对于关系型数据库而言，分发并非易事，许多 NoSQL 方法旨在提供利用相对廉价的商用硬件进行扩展的方式，通常通过以某种方式对数据库进行分区来实现。这也使得云计算架构非常适合大数据系统，所有云服务提供商都提供托管的 NoSQL 解决方案。

NoSQL 系统通常提供调整一致性与可用性之间权衡边界的选项，使系统在预期应用类型的条件下尽可能保持一致，同时也尽可能保持可用。特定的应用领域可能提供特殊功能，可在该特定上下文中被利用以提高一致性或可用性。

尽管硬件成本的下降使得最小化存储空间的重要性降低了，但在数据量非常大的情况下，存储空间仍可能成为重要因素。某些 NoSQL 方法提供了压缩数据和以高效方式存储稀疏数据的途径，既可减少存储空间，又可提高性能。然而，这必须权衡因缺乏规范化而不可避免产生的重复数据所需的额外存储空间。

处理大型数据库也引发了性能问题。这始终是任何类型数据库的关注点，但一种在小型数据库中可能提供可接受性能的方法，在大型系统中可能完全不可接受。在分布式系统中横向扩展的需求也为提高性能提供了机会。例如，通过将一定比例的查询导向持有相同数据副本的其他服务器，可以减轻某台服务器的负载。

在关系型系统中，为提高特定类型查询的性能而对数据库进行反规范化是相当常见的，主要是为了避免表间连接的性能损耗。在大多数 NoSQL 系统中，这是一项标准功能，尽管称其结构为“反规范化”具有误导性，因为它最初可能从未经过规范化。

当然，了解预期流量对于最大化性能至关重要，特别是读取数据库与写入数据库的相对频率。NoSQL 系统通常面向读取比例大但写入较少的场景。数据库记录可能通过某种形式的批量加载相对静态的数据来录入。这也缓解了一致性问题：如果没有写入，数据库就不可能变得不一致！

NoSQL 数据库声称的另一个效率优势是系统管理的简化（及成本降低）。这可能归因于各种管理任务的内置自动化，而这些任务传统上需要专门的专业知识和复杂的手动程序。示例包括自动分片、数据分发和复制、更简便的部署以及更简便的系统配置。

敏捷开发方法论在系统开发的各个领域都已流行开来。它们承诺快速交付初始可工作系统，能够在开发过程中及时响应变更，并通过尽早识别问题来降低风险。

一些 NoSQL 产品将数据库模式定义为繁重的开销，并将无模式宣传为主要的敏捷性优势。通常引用的例子是向现有数据库临时添加新数据元素。然而，这并不像看起来那样独特。使用以下命令扩展关系型数据库也很简单：

* `create table MyNewTable …`
* `alter table MyOldTable add myNewColumn …`

当我们考虑删除或修改现有结构时，情况会更加困难。其影响取决于数据库是旨在支持单个应用程序（如移动电话应用），还是多个应用程序（有时称为集成数据库）。

在应用数据库中，应用程序开发人员和数据库开发人员通常是同一个人。这使得应用程序的变更易于体现为数据库结构的相应变更，反之亦然。然而，对于集成数据库，情况可能没那么简单，因为为适应某个应用程序而进行的数据库变更可能要求对其他应用程序进行变更。如果没有某种模式，管理数据库完整性就会变得非常困难。缺乏对数据结构的权威参考也会使通用应用程序开发变得不必要地困难且容易出错。

NoSQL 数据库通常以直接匹配其外部用法的形式存储数据，例如使用业务文档的结构。这通常以第 16 章中描述的交换格式相同的方式编码，`JSON` 是常见的选择。面向对象的应用程序代码与关系型数据库之间的接口通常通过某种对象-关系映射层来实现，而在某些 NoSQL 系统中，可以消除这种所谓的“阻抗失配”。

关系表的定义要求为每一列分配特定的数据类型。NoSQL 数据库常用于涉及非结构化或临时数据，或数据变异性高的情况，因此动态类型可能更可取。

## NoSQL 数据库的潜在缺点

NoSQL 数据库因其在特定用例下的灵活性和可扩展性而广受欢迎。然而，它们也有一些需要考虑的缺点。以下是与 NoSQL 数据库相关的一些常见缺点：

* **缺乏标准化的查询语言**：与使用 `SQL` 作为标准化查询语言的关系型数据库不同，每个 NoSQL 数据库都有其自己独特的查询语言或应用程序编程接口（`API`）。这使得在不同 NoSQL 数据库之间切换或将其与现有系统集成变得困难。缺乏标准化导致用户社区比 `SQL` 数据库小，这可能使得寻找支持和资源更具挑战性。

* **数据重复与反规范化**：NoSQL 数据库通常对数据进行反规范化以提高性能并实现水平可扩展性。这意味着数据可能跨多个记录或集合重复，导致存储需求增加。更重要的是，跨反规范化结构维护数据一致性可能涉及额外的复杂性。

* **缺乏数据完整性约束**：与通过主键、外键和唯一索引等约束来强制数据完整性的关系型数据库不同，NoSQL 数据库通常缺乏确保数据一致性和强制数据实体间关系的内置机制。这使得开发人员负责在应用层面处理数据完整性。

* **工具和生态系统不够成熟**：尽管 NoSQL 数据库已存在一段时间，但与关系型数据库相比，它们通常拥有不那么成熟的工具和生态系统。这可能导致社区支持较小、开发框架有限以及第三方集成较少。

* **学习曲线与开发人员专业知识**：使用 NoSQL 数据库可能要求开发人员学习新概念、查询语言和数据建模技术。这会增加学习曲线和对专业技能的需求，尤其是在从关系型数据库环境迁移时。

* **有限的事务一致性保证**：一些 NoSQL 数据库遵循 `CAP` 定理，牺牲强一致性保证以换取高可用性和分区容错性。这意味着在某些故障场景下，所做的权衡可能导致最终一致性或数据陈旧。由于某些 NoSQL 数据库使用最终一致性模型，也存在数据不一致的更高风险。

# 17.2 键值存储

键值数据存储是一种 NoSQL 数据库，因其灵活性和可扩展性而日益流行。与传统的关系型数据库不同，键值存储不对大多数数据使用固定模式。相反，数据以键值对集合的形式存储，其中键用于唯一标识数据，值则是实际数据。这种类型的数据存储对于需要快速、高效的数据访问和检索的应用程序特别有用。

如今市场上有许多商业键值数据存储可供选择，此外还有一些虽然不以键值存储为卖点，但提供类似功能的产品。`Redis` 是一种内存数据结构存储，用于数据库缓存、消息代理和实时分析。它以速度快和用途广泛著称，常被用作分布式缓存。`RiakKV` 是一种高可用性分布式键值数据存储，设计为容错且可扩展。`Apache HBase` 是一种开源、分布式的键值存储，构建在 Hadoop 分布式文件系统 (`HDFS`) 之上。它专为大规模、随机读/写访问大数据而设计，并以 Google 的 BigTable 方法为蓝本。`Amazon DynamoDB` 是由 Amazon Web Services (`AWS`) 提供的全托管键值数据存储。它提供数据复制、静态加密和灵活的索引选项等功能。

键值存储的主要特性是其概念上的简单性。它们建立在众所周知的 `哈希` 技术之上，提供了一种访问数据值的一致方式，这些数据值不一定具有规则格式。值保存在一种专用结构中，用户可以暂时忽略其内部细节。值与唯一键关联，该键提供了一种在结构中定位值的方法。使用哈希函数，给定一个键，即可直接或间接（使用某种形式的指针）访问相关的值。

许多编程语言都支持此类结构。术语因语言而异，这些结构可能被称为哈希映射、哈希表、字典、关联数组等。术语的使用也不一致，因此精确的定义仅在特定语言的上下文中才相关。例如，`Python` 使用术语 `dictionary` 来指代包含键值对的结构。在较新版本的 `Python` 中，项按键值排序，但这在其他语言的等效结构中不一定成立。`JavaScript` 可以简单地使用 JSON 风格的 Object 实现相同目的。尽管语法不同，所有这些编程方法都支持大致相当范围的操作，例如：

* 插入项 (`key`, `value`)
* 更新值 (`key`, `new value`)
* 删除项 (`key`)
* 检索值 (`key`)
* 测试是否存在 (`key`)

大多数语言允许存储的值类型为该语言中可表达的任何内容，范围从简单类型（数字、字符串等）到具有自身内部结构的项，如对象、列表，甚至可能是进一步的字典。虽然这些结构可在程序内部使用，但无法直接从程序外部访问，如有需要必须以某种形式导出，例如 `JSON`。

程序内的数据显然会在程序终止时消失，因此键值存储在持久化存储中提供了等效功能。这也使得数据可从许多不同的程序访问（假设有合适的语言绑定）。

我们可以使用关系型数据库来近似一个键值数据库，只需定义一个类似于以下 SQL 片段的单表：

```
create table myKV (  theKey varchar(20) primary key,  theValue BLOB )
```

此处假设键是最多 20 个字符的字符串，但也可使用任何 SQL 数据类型。此处的值是 `BLOB` 数据类型，用于包含未经数据库解析的未分化二进制数据。在某些 SQL 方言中，`BLOB` 可替换为 `varbinary()` 等其他类型。

键值存储与关系型数据库的区别在于，它们仅专注于完整数据单元的高效存储和检索。数据存储可以忽略数据单元的内部结构，将其视为单个项目。这消除了对复杂查询的支持需求，因为仅需的基本操作是写入和读取单个数据单元。数据存储不再负责理解信息的内部值、数据类型和结构。该责任现下放给使用它的应用程序。对内部数据结构的任何更改、添加或删除值，对数据存储没有影响，尽管显然会影响任何相关应用程序。

除了使存储和检索更高效外，这种扁平结构还极大地简化了数据存储的设计和实现，因为其模式可以非常简单。但重要的是要记住，对详细模式的需求并未完全消失——它只是从数据存储转移到了应用程序。

虽然键值存储擅长快速检索数据单元，但某些存储也提供在单元内部操作数据值的特定方式，例如向字符串追加内容、向列表推入元素、获取有序集合中排名最高的成员。如果数据单元的内容以某种结构化形式（如 `JSON` 或 `XML`）编码，则可提供相应设施以适当方式查询内容。

键值存储非常适合分布式部署，其流行度的上升与云计算作为可行平台的出现同步，这恐怕并非巧合。通过跨许多服务器进行水平分区，每个服务器处理自己的键值子集，数据存储几乎可以无限扩展。通过复制，可在不同服务器上保存多个副本并通过适当的负载均衡机制访问，从而提高弹性和性能。

分布式并不适用于所有情况；一些键值存储设计为驻留内存，以提供最快的检索速度。固态硬盘比旧式硬盘快约 100 倍，但 `RAM` 还要快几个数量级。分布式对内存存储而言问题更大，但可以找到混合解决方案。例如，可使用内存存储在基于应用程序的键和基于服务器的键之间提供查找，后者可用于访问分布式键值存储。

在所有情况下，都需要对键的设计进行一些思考。显然，这需要提供唯一值，并且必须在数据存储的整个生命周期内保持一致生成。最好使键尽可能紧凑，同时要能完全识别相关的数据单元。在不影响效率的前提下，使键具备一定的可读性有助于故障排查。在分布式系统的情况下，键还必须指示要访问的分区。这可以通过使键更复杂来实现，这与通过文件路径在计算机上唯一标识文件的方式非常相似。键几乎肯定会被索引以实现快速检索。在某些情况下，如果值可以通过不同方式查找，提供辅助索引也可能很有用。

正如已经指出的，NoSQL 数据库之间存在巨大的多样性，这当然也适用于键值存储。各个系统都有其自身的特性，但大多数流行的键值存储具有一些共同特征。

* **简洁性**：键值存储通常提供简单的数据模型，数据以键值对的形式存储，使其易于理解和使用。它们不需要复杂的模式或复杂的表结构，可以轻松集成到现有应用程序中。

* **高性能**：键值存储专为高速数据访问和低延迟操作而设计。这部分归因于它们使用简单的数据结构并避免复杂的连接或索引。它们也倾向于最小化磁盘 I/O，使用内存缓存并优化数据结构和算法以实现快速的基于键的查找。

* **可扩展性**：键值存储通过跨多个节点分发数据，易于水平扩展。它们支持分片和分区技术来处理大型数据集，并能随着数据量随时间增加而优雅地增长。这使它们成为需要处理大量数据并要求高可用性的应用程序的良好选择。

* **复制和容错**：键值存储通常提供复制机制以确保高可用性和容错能力。它们跨多个节点或分区存储数据的冗余副本，并在节点发生故障时提供服务的自动再平衡。

* **灵活的数据模型**：大多数键值数据存储可以存储各种数据类型，包括结构化、半结构化和非结构化数据。这使它们适用于存储用户配置文件、传感器数据、会话数据以及需要多种类型和格式的物联网应用程序等场景。

显然，键值存储提供了一些可以在特定类型的应用程序中利用的优势，但我们必须将这些优势与可能使键值存储在其他情况下不太合适的特性进行权衡。

* **临时或复杂查询通常不受支持**：数据存储不支持临时或复杂查询，例如搜索具有特定特征的数据或跨不同键值对的数据连接。任何此类操作都必须在数据存储外部的应用程序代码中执行。

* **对作为键值对值存储的数据进行操作的机会有限**：数据检索通常旨在将值作为一个单元高效检索。这也可能使对数据中某个元素的修改效率降低，因为必须将整个值作为一个完整的数据块来处理。

* **缺乏标准**：与关系型数据库不同，键值存储的结构没有标准。由于每个产品都使用自己的专有函数和方法，因此很难将专业知识从一个键值产品转移到另一个。

* **ACID 支持有限**：键值存储通常无法提供通常与关系型系统相关的 ACID 属性支持。事务通常仅限于对单个数据单元的操作。

* **验证和约束范围有限**：在数据存储内验证数据或应用约束的范围有限。同样，此类操作必须由应用程序代码在数据存储前或作为一个单元检索后执行。

确定合适的键值存储，甚至决定键值存储是否合适，将很大程度上取决于每个具体案例的需求。键值存储非常适合需要从大量相似单元池中快速访问单个复杂数据单元的应用程序。一些典型用例包括：

### 缓存

频繁访问的数据可以存储在键值数据存储中以实现更快的检索。这有助于提高应用程序性能并降低延迟。例如，电子商务网站可能会使用键值数据存储来缓存热门产品的产品信息，以便网站能快速提供服务，而无需每次都查询传统数据库。

### 会话管理

在用户会话需要跨多个请求或跨多个服务器保持的应用程序中，键值数据存储非常有用。登录信息和购物车内容等值可以被保存，以便在需要时快速检索信息。

### 存储用户偏好

用户偏好可以存储为键值对，从而允许轻松检索和更新用户偏好。这在用户需要自定义其体验或用户偏好需要跨多个设备共享的应用程序中非常有用。

### 内容管理

数字内容现在很普遍。这包括文本、图像、视频、文档和其他多媒体资产。应用程序可能需要将各种媒体收集到一个集合中，作为一个单元存储和检索，这非常适合键值存储。

# 17.3 面向列的数据库

面向列的数据库与关系型数据库的主要区别在于数据的组织和存储方式，而不是数据的逻辑结构。关系型数据库将信息存储在表中，组织成行和列。表可以被视为关于特定实体类型的信息，每一行代表该类型的一个单独实体，列包含与该实体类型相关的值。行通常被称为记录，相关的列值被称为该记录的字段。主要关注点是管理记录，因此将这种类型的数据库描述为面向行的是合理的。

如果我们需要查询特定数据，数据库必须扫描表中的所有行以查找相关信息。索引虽有帮助，但对于拥有数百万条记录的大型数据库，这可能会很慢且效率低下。

相比之下，面向列的数据库将数据存储在列中，每一列代表表中的单个属性或字段。这意味着特定属性类型的值存储在一列中，无论它们属于哪条记录。

当数据库被查询特定数据时，数据库只需扫描相关列，而不是表中的每一行。这可以快得多且效率更高，特别是在处理大型数据集和聚合等操作时。

## 面向列的数据库系统

有几种面向列的数据库系统可用，包括以下几种：

* **Amazon Redshift** 与其他 AWS 产品有着极佳的集成。它提供动态扩展并自动化许多系统管理活动。
* 有几种开源系统可用。
* **PostgreSQL** 是一种著名的基于行的数据库，但它也有一个列存储选项，当你想要仅使用一个数据库同时进行列存储和行存储时，这非常有用。
* **MariaDB** 是另一种流行的开源数据库，支持行存储和列存储两种方式。
* **Apache Cassandra** 是一种面向列的数据库，旨在跨许多通用服务器处理大量数据。
