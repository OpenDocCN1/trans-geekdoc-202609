
除了与访问控制相关的策略外，组织的安全策略还包括后续章节中描述的具体策略。所有政策都应定期审查并根据需要进行更新。通常，政策的更新频率应低于实施这些程序的频率，因为高层次的目标不会像其实施的环境那样频繁变化。所有政策都应由组织的法律顾问审查，并概述一个描述组织将如何确保员工了解这些政策的计划。通过引用制定政策的权威（无论该政策是来自 CEO 还是部门级政策）也可以加强政策的效力，并引用适用于特定策略和环境的任何法律或法规。

## Mandatory Vacations

多年来，组织一直在为员工提供休假。然而，直到最近，很少有组织在员工不愿的情况下强制他们休息这段时间。某些员工被允许“使用或失去”他们的休假时间，如果他们没有用完所有时间，就会失去至少一部分。关于休假的益处可以有很多论点，但更重要的是，从安全的角度来看，从不休假的员工可能是潜在的活动指标。从不休假的员工可能参与了欺诈或挪用资金等活动，并可能担心如果他们去休假，组织就会发现他们的非法活动。因此，通过强制休假政策要求员工使用休假时间，可以作为一种安全保护机制。将强制休假作为检测欺诈的工具需要另一个人也对休假员工的职能进行培训。

## Job Rotation

另一种提供多重益处的政策是`job rotation`（轮岗）。轮岗可以为个人提供更好的视角，了解组织的各个部分如何增强（或阻碍）业务。由于人们在工作中通常将安全视为次要考虑的因素，让人员轮换到安全岗位可以使其对组织的安全问题产生更广泛的理解。另一个次要益处是，它还消除了对个人安全专业知识的依赖。如果所有安全任务都由一名员工负责，那么当该人员离开组织时，安全工作将受到影响。此外，如果只有一个人了解安全领域，而这个人又产生了不满情绪并决定伤害组织，那么从其攻击中恢复可能会非常困难。

### 职责分工

职责分工是许多组织采用的一项原则，以确保没有个人个人能够独立执行交易的能力。这意味着对任何一个个人的信任度降低了，而且任何个人对组织造成灾难性损害的能力也随之降低。例如，某个组织中，一个人有权订购设备，但另一个人负责付款。想要为了个人利益进行未经授权购买的个人，必须说服另一个人参与该交易。

将职责分工作为一种安全工具是一种良好的做法，但也有可能过头，将交易拆分为过多的碎片或要求过多的监督。这会导致效率低下，实际上可能更不安全，因为个人可能由于知道其他人也会审查这些交易，他们不会详尽地审查交易。这种诱惑是会促成某事的完成，并假设别人会检查它或者别人已经检查过了。

### 最小权限原则

另外两个常见的安全原则是`need to know`（知情需要）和`least privilege`（最小权限原则）。这里的指导因素是组织中的每个个人仅获得执行所分配工作任务所需的绝对最少的信息和权限。为了访问任何信息，个人必须具有正当的知情需求。此外，员工仅被授予执行工作所需的极少权限。

应该制定一项将这两个原则阐明为组织指导哲学的政策。政策还应该说明组织中谁可以授予信息访问权限或可能为员工分配权限。

### 风险计算

更复杂的模型允许基于统计和数学模型进行分析。常用方法是计算年化损失预期（ALE）。计算 ALE 为影响产生了货币价值。这种计算从计算单次损失预期（SLE）开始。

#### SLE

单次损失预期使用以下公式计算：

```
SLE = asset value × exposure factor
```

影响因子是资产损失规模的衡量。

例如，为了计算影响因子，假设该资产的价值。

#### ALE

年化损失预期产生了影响的货币价值。这种计算通常表示为：

```
ALE = SLE × ARO
```

#### ARO

年化发生率是预计一年内威胁发生的频率。

#### MTTR

平均修复时间是指系统故障后恢复系统所需的平均时间。

#### MTBF

平均故障间隔时间是衡量可靠性的常用指标，是系统故障之间的平均时间。

```
MTBF = MTTF + MTTR
```

#### MTTF

平均失效时间是 MTBF 的变体，用于系统被更换而非修复的情况。

### 定量与定性

业界公认的是，进行纯定量的风险管理是不可能的。通常，风险管理包含定性和定量两个元素，需要分析也需要判断。与定量评估相比，完成纯定性的风险管理是可能的。

### 漏洞 (Vulnerabilities)

漏洞是资产的特征，可以被威胁利用造成危害。例如，如果你没有安装补丁来修复网站上的跨站脚本（`XSS`）错误，那么你的系统就存在安全漏洞。并不是所有的错误或缺陷都是漏洞。要将一个错误或缺陷归类为漏洞，它必须是可利用的，这意味着攻击者能够利用该漏洞产生预期的结果。漏洞的发生需要三个要素：

* 系统必须存在缺陷。

* 缺陷必须能被攻击者访问。

* 攻击者必须具备利用该缺陷的能力。

漏洞存在于多个层次，由多种原因引起。从设计错误、编码错误到复杂系统中无意（且未经测试）的组合，漏洞有许多形式。漏洞可以存在于软件、硬件和程序中。无论是在底层系统、旨在保护系统的安全控制，还是在系统运行过程中采用的程序中，结果都是一样的：漏洞代表了一个可以被利用的弱点，增加了与系统相关的风险水平。

### 威胁向量 (Threat Vectors)

威胁是指任何可能对资产造成危害的状况或事件。例如，恶意的黑客可能会选择使用现成的黑客工具来入侵你的系统。威胁可以分类分组，“威胁向量”一词描述了这些组包含的元素。威胁向量是攻击者用于攻击目标时使用的路径或工具。安全专业人员需要理解的威胁向量范围广泛：

* `Web`（虚假网站、会话劫持、恶意软件、水坑洞攻击）

* 无不安全的无线热点

* 移动设备（`iOS`/`Android`）

* `USB`（可移动式）介质

* `E-mail`（链接、附件、恶意软件）

* `社会工程学`（欺骗、骗局、诈骗和欺诈）

此列表仅为威胁的示例。从防御的角度来看，重要的是不要固着于特定的威胁，而是要关注威胁向量。如果用户访问了带有恶意代码的网站，那么代码的性质虽然在技术角度上很重要，但并不是首要考虑的问题。首要问题是恶意网站，因为这就是威胁向量。

### 概率/威胁可能性 (Probability/Threat Likelihood)

事件的概率或可能性是衡量其预期发生频率的度量。从使用“频繁”、“偶尔”和“罕见”等术语的定性评估，到定量衡量的 `ARO`，其目的是允许根据事件发生的频率进行缩放。要准确地确定安全事件的特定概率是一项几乎不可能的任务。在使用概率和可能性时，重要的是它与确定相对风险之间的关系。正如保险公司无法预判你何时会发生事故一样，也没有能预测安全事件何时会发生。可以确定的是，在一段时间内（例如明年），将大量用户点击电子邮件中的恶意链接。不同类型攻击的威胁可能性会随着时间的推移而变化。几年前，网页破坏曾风靡；今天，鱼叉式网络钓鱼更加流行。

### 风险规避、转移、接受、缓解、威慑 (Risk Avoidance, Transference, Acceptance, Mitigation, Deterrence)

风险是绝对的——它们无法被移除或消除。可以采取行动来改变风险对系统造成的影响，但无论采取什么缓解风险的行动，风险本身并不会改变。高风险始终是高风险。然而，可以采取行动来减少该风险的影响。可以使用有限的策略来管理风险。风险可以被规避、转移、接受或缓解。规避风险可以通过多种方式实现。不部署增加风险的模块是规避风险的一种方式。这减少了环境风险。当发生超出接受风险范围的操作时，可以应用第二套规则。管理风险的另一种方法是转移。风险的常用方法是购买保险。保险允许风险转移给第三方，从而降低个人成本。

风险也可以通过应用减少影响的控制来缓解。此类控制可以提醒操作人员，从而通过干预降低暴露水平。这减少了与操作相关的风险。除了缓解风险或转移风险外，经理也可以接受风险，尽管存在风险的成本及其相关概率。例如，经理可能会选择允许程序员对生产系统进行“紧急”更改（这违反了职责分离原则），因为系统在特定段时间内不能宕机。经理接受程序员可能做出未经授权更改的风险大于该系统的高可用性需求。

理解风险无法被完全消除。实施控制后剩余的风险被称为`残留风险`。在这一步中，你进一步评估`残留风险`，以识别何时需要额外的控制来进一步降低风险。这让我们回到我们在章节引言中的陈述：风险管理过程是迭代的。

### 云计算 (The Cloud)

`云计算`是一个用于描述通过网络提供的计算服务的常用术语。这些计算服务是通过 IP 协议提供的计算、存储、应用程序和服务。云计算的一个特征是对终端用户透明的。这改进了这种服务提供形式的易用性。云计算为用户提供了许多好处：性能、扩展性、灵活性、安全性和可靠性的提高。这些改进是与云服务实施相关的特定属性的直接结果。云计算的承诺是提高效用性，并以`平台即服务`、`软件即服务`和`基础设施即服务`的概念进行营销。云风险风险的挑战在于预先确定谁承担什么种的安全责任——云提供商、服务提供商还是用户？

### 与云计算和虚拟化相关的风险

从风险的角度检查云端或虚拟计算环境等复杂系统时，始终需要观察几个基本考虑因素。首先，系统是处于云端还是虚拟化，这一事实并不会改变风险运作的方式。风险无处不在，将系统迁移到新环境也不会改变存在风险这一事实。其次，复杂性会增加风险暴露。云和/或虚拟化的引入简单地通过增加系统的复杂性来增加风险。

虚拟化和云环境都与特定的风险相关。在不属于数据所有者直接控制的环境中进行数据处理和计算，会同时增加复杂性和风险程度。随着对环境直接控制的丧失，机密性、完整性和可用性方面的潜在问题随之增加。虚拟化层和云层还提供了新的攻击途径。当数据由远程方处理（如云计算所示）时，安全是一项特别的挑战。具体的挑战在于如何允许使用数据。通过在数据离开企业之前妥善使用加密技术，仍然可以安全地进行外部存储。与机密性、完整性和可用相关的要求仍然是数据所有者的责任，必须采取措施来确保满足这些要求。另一层保护是通过与云服务供应商签署服务水平协议（`SLAs`），尽管这些协议通常在数据丢失时提供补救。

### 虚拟化

虚拟化是创建虚拟系统而非实际硬件和软件。硬件与软件的分离使得企业具有灵活性。在实际硬件之上，虚拟化层允许将完整的系统（包括计算机和网络设备）创建为虚拟机。这使得改进成为可能。尽管存在可能允许一个虚拟环境中的进程访问主机的漏洞，但这些漏洞非常罕见且极难利用。必须解决一种新形式的漏洞——复制整个系统的能力，因为这可能导致财产损失。虚拟化系统应该像非虚拟化系统一样进行更新/补丁。虚拟系统仍然需要安全服务，以防范恶意软件和普通系统面临的相同威胁。

### 恢复时间目标和恢复点目标

`恢复时间目标 (RTO)` 术语用于描述事故发生后恢复运营的目标时间。这是由业务根据企业定义的一段时间。较短的 `RTO` 会导致更高的成本，因为它需要更多的协调和资源。该术语通常用于业务连续性和灾难恢复操作。

`恢复点目标 (RPO)` 是一个与 `RTO` 完全不同的概念，它代表可接受损失的最大时间段。`RPO` 定义了防止发生不可接受的数据丢失水平所需的备份操作频率。建立 `RPO` 的简单示例是回答以下问题：你能承受丢失多少数据？可以容忍多大程度的重新？

`RTO` 和 `RPO` 似乎有关，但实际上衡量的是完全不同的东西。`RTO` 的目的是定义业务连续性的需求，而 `RPO` 处理的是备份频率。存在 `RTO` 为 1 天而 `RPO` 为 1 小时，或者 `RTO` 为 1 小时而 `RPO` 为 1 天的情况。决定因素是业务需求。

![image](img/examtip.jpg)

**考试贴士**：尽管恢复时间目标和恢复点目标看起来相同或相似，但它们非常不同。`RTO` 的目的是定义业务连续性的需求，而 `RPO` 处理的是备份频率。
