从 ORM 的角度来看，启发式方法引导我们最初使用自然引用方案来建模该情况，如图 9.29(b)所示。这里，ColumnName 表示列在表中的局部名称。我们通过假设表可以仅由其名称标识来简化现实。外部唯一性约束为 Column 提示了两种自然引用方案：名称加表，或位置加表。我们选择了前者作为首选，但也可以引入人工标识符。一元谓词指示某列是否为主键列或主键的一部分。如果需要，我们可以从路径“Column is in Table **and** Column is a primary key column”推导出关联“Column is a primary key field of Table”（UML 模型中的子集约束由此隐含）。

这个例子有趣的是建模方法的差异。大多数 UML 建模者似乎假设在初始建模中将使用 oid 作为标识符，而 ORM 建模者喜欢从一开始就暴露自然引用方案，并据此填充他们的事实类型。这些不同的方法通常会导致不同的解决方案。

最重要的是首先提出一个对领域专家来说自然且易懂的解决方案，因为这是模型验证最关键的阶段。一旦确定了正确的模型，就可以使用优化指南来增强它。

示例中还有一个特性值得一提。图 9.29(a) 中的 UML 解决方案使用注解 `{ordered, unique}` 来表明表由一个*有序集合*（即无重复项的序列）的列组成。UML 2 允许在有或无*有序属性*的情况下指定*唯一属性*。默认情况下，`ordered = false` 且 `unique = true`。因此，设置 `{ordered}` 或 `{ordered, unique}` 均可用于表示有序集合。无设置或单一设置 `{unique}` 均表示集合（默认值）。如果在此上下文中允许 `{nonunique}`（UML 规范对此不明确），则可以分别用设置 `{nonunique}` 或 `{ordered, nonunique}` 来指定包或序列。

在 ORM 社区中，关于在概念层面处理集合类型（如集合、有序集合、包、序列）的构造器的最佳方式，争论已持续多年。我们的观点是，此类构造器不应出现在基础概念模型中。因此，图 9.29(b) 中使用 `Position` 来传达列的顺序（顺序的唯一性由 `Column has Position` 上的唯一性约束传达）。保持事实类型的基本性具有诸多优势（如验证、约束表达、灵活性和简洁性），因此最好将构造器归入派生视图。我们将在第 10 章中更多地讨论集合类型。

在 ORM 中，两个兼容角色序列之间的*等值约束*是两个子集约束（双向各一个）的简写，显示为圆圈 `=`。此约束表明角色序列的实例集必须始终相等。如果一个对象类型扮演的两个角色都是强制的，则它们之间隐含了等值约束（因此不显示）。UML 没有等值约束的图形符号。对于整个关联，我们可以使用两个单独的子集约束，但这会非常混乱。一般来说，UML 中的等值约束可在注释中指定为文本约束。

作为一个简单示例，图 9.30(b) 中的等值约束表明，如果测量了患者的收缩压，则也会测量舒张压（反之亦然）。换句话说，要么两项测量都进行，要么都不进行。

## 9.6 子类型化

UML 和 ORM 均支持使用“is-a”（是一种）语义的*子类型化*，即子类型的每个实例同时也是其超类型（父类型）的实例。例如，声明 Woman（女性）是 Person（人）的子类型，意味着每个女性都是人，因此 Woman 继承 Person 的所有属性。给定两个对象类型 *A* 和 *B*，如果在每个数据库状态下，*A* 的实例总体都包含在 *B* 的实例总体中，则 *A* 是 *B* 的*子类型*。对于数据建模，感兴趣的只有*真*子类型。我们称 *A* 是 *B* 的真子类型，当且仅当 *A* 是 *B* 的子类型，且存在一种可能的状态，使得 *B* 的实例总体包含不在 *A* 中的实例。从现在起，我们将用“子类型”作为“真子类型”的简写。

在 UML 和 ORM 中，*特化*是引入子类型的过程，*泛化*是引入超类型的逆过程。UML 和 ORM 都允许单一*继承*以及多重继承（即一个子类型有多个直接超类型）。例如，AsianWoman（亚洲女性）可以同时是 AsianPerson（亚洲人）和 Woman 的子类型。在 UML 中，“子类”和“超类”分别是“子类型”和“超类型”的同义词，泛化也可应用于类以外的事物（如接口、用例参与者和包）。本节重点关注对象类型（类）之间的子类型化。

在 ORM 中，子类型继承其超类型的所有角色。在 UML 中，子类继承其超类型的所有属性、关联和操作/方法。操作实现一项服务，具有签名（名称和形式参数）和可见性，但可以用不同方式实现。方法是操作的一种实现，包含签名和主体，主体详述执行该操作的可执行算法。在继承图中，同一操作可能有多个方法（*多态*），作用域规则决定给定类使用哪个方法。如果子类拥有与其某个超类型的方法具有相同签名的方法，则该子类将改用这个方法（*覆盖*）。例如，如果 Rectangle（矩形）和 Triangle（三角形）是 Shape（形状）的子类，这三个类可能都有不同的 display 方法。本节专注于数据建模，涵盖静态属性（属性和关联）的继承，但忽略操作或方法的继承。

子类型在数据建模中用于断言类型约束、鼓励模型组件复用以及展示分类方案（分类学）。在此语境下，类型约束确保子类型特有的角色仅由相关子类型扮演。

因为子类型继承其超类型的属性，所以引入子类型时只需声明其特有的角色。除了减少代码重复，更通用的超类型也更有可能在其他应用中得到复用。在编码层面，操作/方法的继承增强了通过属性和关联角色继承获得的复用。用子类型展示分类学用处有限，因为分类学通常用谓词捕获更高效。例如，事实类型“Person is of Gender {male, female}”（人的性别为{男，女}）隐式地为 MalePerson（男性）和 FemalePerson（女性）子类型提供了分类学。
