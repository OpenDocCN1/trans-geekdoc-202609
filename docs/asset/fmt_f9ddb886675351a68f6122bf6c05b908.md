由于 RDF 数据将作为我们存储模式的一部分，存储在不同的 HDFS 文件夹下的单独文件中，我们需要为这些文件夹和文件采用特定的命名约定。

#### 16.2.4.4 命名约定

在我们的框架中，一个 Hadoop 存储可以由多个不同的 RDF 图组成。因此，将在 HDFS 中为每个此类 Hadoop 存储创建一个单独的文件夹。该文件夹的名称将对应于为给定存储选定的名称。此外，在我们的框架中，根据所选的存储布局，一个 RDF 图被划分为多个文件。因此，将在 HDFS 中为每个不同的 RDF 图创建一个单独的文件夹。默认 RDF 图的该文件夹名定义为 `default`，而对于命名 RDF 图，则使用该图的统一资源标识符 (URI) 作为文件夹名称。我们在框架中使用存储的抽象，原因是这将简化属于不同机构的数据的管理。我们框架支持的两种布局将在后面讨论。这些布局使用数量不等的 HDFS 文件来存储 RDF 数据。

#### 16.2.4.5 垂直分区布局

图 16.10 展示了垂直分区布局的存储模式。对于 RDF 图中包含的每个唯一谓词，该布局在底层 HDFS 中使用谓词名称作为文件名创建一个单独的文件。请注意，文件名中仅使用谓词 URI（统一资源标识符）的本地名称部分，且文件名与谓词 URI 之间存在单独的映射。给定谓词的文件为包含该谓词的每个三元组包含单独的一行。该行存储构成三元组的主语和宾语值。因为将谓词名称移至文件名完全消除了该谓词值的存储，所以这种模式将带来显著的存储空间节省。然而，相同的资源 URI 或字面值的多次出现将在所有文件中以及文件内部被多次存储。此外，SPARQL 查询可能需要查找多个文件，以确保向用户返回完整的结果，例如，查找属于特定主语或宾语的所有三元组的查询。

#### 16.2.4.6 混合布局

图 16.11 展示了混合布局的存储模式。该布局是垂直分区布局的扩展，因为除了为 RDF 图中的每个唯一谓词创建单独的文件外，它还创建了一个单独的三元组文件，包含采用 `SPO`（主语、谓语、宾语）格式的所有三元组。拥有此类文件的优势在于，它能直接提供属于特定主语或宾语的所有三元组。回想一下，在垂直分区布局中，此类搜索操作需要扫描多个文件。由于增加了三元组文件，该布局的存储空间效率不如垂直分区布局。然而，使用该布局可以更高效地执行查找属于特定主语或宾语的所有三元组的 `SPARQL` 查询。

#### 16.2.4.7 SPARQL 的分布式处理

`CAISS++` 中的查询处理包含多个步骤（图 16.12）。第一步是查询解析和转换，给定的 `SPARQL` 查询首先被解析以验证语法正确性，然后构建与输入查询对应的解析树。解析树随后被转换为 `SPARQL` 代数表达式。由于给定的 `SPARQL` 查询可以有多个等价的 `SPARQL` 代数表达式，我们用关于如何评估该表达式中每个操作的指令来标注每个此类表达式。此类带标注的 `SPARQL` 代数表达式对应于查询评估计划，作为优化器的输入。优化器选择一个使查询评估成本最小化的查询计划。为了优化查询，优化器必须知道每个操作的成本。为了计算每个操作的成本，优化器使用一个元存储，其中存储与 `RDF` 数据相关的统计信息。给定查询评估计划的成本也可以用 `MapReduce` 作业的数量或作为查询执行一部分将被访问的三元组数量来衡量。一旦选定查询计划，将使用该计划评估查询并输出查询结果。由于我们使用以云为中心的框架来存储 `RDF` 数据，评估引擎需要将 `SPARQL` 代数算子转换为底层存储布局（前文所述）上的等价 `MapReduce` 作业。因此，在 `CAISS++` 中，我们将为每个 `SPARQL` 代数算子实现一个 `MapReduce` 作业。此外，评估引擎使用分布式推理器来计算查询评估所需的推论。

#### 16.2.4.8 框架集成

我们概述的作为 `CAISS++` 一部分的组件需要集成以协同工作。此外，这一集成过程取决于用户对 `CAISS++` 提供的三种可能设计选择之一的选择，即集中式 `CAISS++`、分散式 `CAISS++` 或混合 `CAISS++`。迄今为止提出的 `CAISS++` 各个部分的集成需要考虑若干问题。首先，我们需要确保本体工程过程已成功捕获机构的需求，并且本体可以存储在 `Hadoop` 存储架构使用的存储模式中。其次，我们需要确保分布式 `SPARQL` 查询处理器能够高效地评估底层 `RDF` 存储上的查询（即用户生成的 `SPARQL` 查询以及评估策略的 `SPARQL` 查询）。最后，我们需要对 `CAISS++` 进行性能评估，以验证其是否满足各参与机构的性能要求，以及与 `CAISS` 相比是否带来显著的性能优势。

#### 16.2.4.9 策略规范与实施

`CAISS++` 的用户可以使用他们选择的语言（例如 `XACML`、`RDF` 和 `Rei`）来指定其信息共享策略。这些策略将使用现有的或定制的转换器转换为 `OWL` 的合适子语言。我们将扩展 `CAISS` 的策略引擎以处理用 `OWL` 指定的策略。除了 `RDF` 策略外，我们当前的策略引擎还可以处理用于实现基于角色的访问控制、推理控制和社会网络分析的 `OWL` 策略。

### 16.2.5 设计扩展

#### 16.2.5.1 形式化策略分析

我们的框架适用于各种关键任务、高保障的应用，这些应用跨越多个可能相互不信任的组织。为了在这类环境中提供最大程度的安全保障，建立关于系统正确性及其所执行策略的强有力形式化保证非常重要。为此，我们研究了为我们的系统构建重要系统属性和策略分析的形式化、机器可检查证明的基础设施。虽然对于许多大型软件系统，构建机器可检查证明可能非常困难且耗时，但我们选择 `SPARQL`、`RDF` 和 `OWL` 作为查询、本体和策略语言，为在逻辑编程环境中优雅地构建此类证明提供了独特的机会。我们将把策略、策略重写算法和安全属性编码为 `Prolog` 中基于规则的逻辑推导系统，并应用模型检查和定理证明系统（如 `ACL2`）生成机器可检查的证明，以证明系统遵守这些属性。我们打算在模型中考虑的属性包括可靠性、透明性、一致性和完整性。我们的形式化策略分析结果将驱动 `CAISS++` 的详细设计和实现。据我们所知，以往的研究中没有专注于针对 `SPARQL`、`RDF` 和 `OWL` 的此类形式化策略分析。我们关于带内联参考监视器的形式化策略分析的广泛研究在相关工作中讨论。

通过将高级安全策略规范和系统模型降低到其二进制级实现的指称语义和操作语义层面，我们过去的工作为各种复杂软件系统开发了形式化的、机器可认证的安全实施机制，包括用 [.NET](http://in.NET) 实现的系统 \[HAML2006b\]、`ActionScript` \[SRID2010\]、`Java` \[JONE2010\] 和本地代码 \[HAML2010b\]。在二进制级工作提供了极高的形式化保证，因为它允许生成关键任务软件组件的工具链保持不可信；工具链生成的二进制代码可以直接被认证。该策略非常适合 `CAISS++`，因为诸如 `XACML` 和 `OWL` 等数据安全规范语言可以通过具有 `XML` 感知的系统应用程序编程接口（`API`）（如 `Java` 字节码）优雅地映射到字节码语言的二进制级。我们过去的工作应用了二进制插桩（例如内联参考监控）以及二进制类型检查 \[HAML2006b\]、模型检查 \[SRID2010\] 和自动定理证明（例如通过 `ACL2`）的组合，在上述领域实现了二进制软件的完全自动化机器认证。

#### 16.2.5.2 面向大数据应用的扩展

在第 17 章中，我们将讨论一个用于社交媒体数据的访问控制框架。我们可以将该工作与本章讨论的工作（即第 16 章）相结合，并基于大数据开发面向社交媒体的 AIS 方法。我们可以针对利用大数据管理和分析的社交媒体应用，改编本章讨论的几种设计变体。首先，网络成员可能希望共享数据。因此，他们可以实施信息共享策略，每个成员拥有自己的数据存储。在第二种设计中，成员可以使用共享空间或云来存储数据和策略，并安全地共享数据。

成员也可能属于多个社交网络。也就是说，一个人可能属于多个网络，也可能只属于一个网络。在这种情况下，成员可以与其网络中的成员共享更多数据，而与另一个网络的成员仅共享有限数据。此外，不同网络可能使用异构技术进行表示。因此，必须解决异构表示问题。也可以为多个网络开发逻辑表示，并建立到各个网络的映射。随着时间的推移，多个社交网络中的用户数量可能会快速增长，他们在网络中存储和共享的数据量可能巨大。因此，必须探索我们在第 5 章以及第 I 部分和第 II 部分其他章节中讨论的几种大数据技术，以用于多个社交网络之间的 AIS。

松耦合系统为我们的 `RDF` 策略引擎框架提供了易于配置和灵活的特性。通过采用包含机构对策略偏好或数据存储数据连接的 `RDF` 文档，每个组件都与其他组件抽象开来。此外，松耦合的 Web 前端促进了策略框架的更易维护和复用，因为适配器模式抽象了 Web 接口（及通信）到其他层的映射。抽象向机构隐藏了策略引擎管理器和数据管理器的实际实现及复杂性。因此，这允许机构使用任何表示语言（如 `XML`、`RDF` 或 `Rei` [KAGA2002]）指定其策略；适配器隐藏了从高层策略规范到策略实现的转换。

我们的系统架构由三层组成。前端是用户界面；中间层包含我们的策略引擎逻辑；后端是我们的数据存储。接下来我们将讨论这些模块。应注意，在本实现中，我们的重点在于共享数据的溯源。该实现受本章前面讨论的原型以及第 17 章中讨论的基于溯源的推理控制器的驱动。
