
# Kubernetes 核心概念与最佳实践

## 基础命令

应用 Pod 配置：

```
kubectl apply -f pod.yaml
```

删除名为 `frontend` 的 Pod：

```
kubectl delete pods/frontend
```

查看 `kubectl` 所有命令：

```
kubectl help
kubectl help <command-name>
```

## Kubectx

`Kubectx` 是一个极简的 CLI 工具，帮助我们在集群间切换。当我们使用 `kubectl` 时，它会访问 `~/.kube` 目录中声明的集群 API。通过使用 `kubectx`，它只会将上下文切换到期望的集群。例如：

```
kubectx <cluster-name>
```

## 基础资源

以下三个资源在 Kubernetes 中被广泛使用。了解它们是什么对于理解 Kubernetes 至关重要。我们将在本章中反复提及它们。

### Node

> “Node 是 Kubernetes 中的工作机器，可以是虚拟机也可以是物理机，取决于集群。每个 Node 由控制平面管理。一个 Node 可以运行多个 Pod，Kubernetes 控制平面会自动处理在集群中的 Node 间调度 Pod。”

这是 Kubernetes 官方文档的引用。这段引用很好地解释了什么是 Node。作为开发者，这已足够，我们不需要操作它们或处理 Node 问题。但请注意，有时我们的应用程序会因 Node 问题而出现故障。至少，我们需要理解问题与 Node 相关，并将其移交给运维人员处理。

### Namespace

Kubernetes 中的 Namespace 是资源间分离和隔离的机制。一些资源可以被命名空间化，一些则不能。每次我们使用 `kubectl get` 获取资源时，除非另行指定，否则它会带来 `default` 命名空间中的所有资源；通过添加 `-A`，我们可以获取所有命名空间中的所有资源。资源的名称和类型在命名空间内必须唯一。要查看哪些资源被命名空间化、哪些没有，可以运行：

```
kubectl api-resources
```

![](img/Figure-8.4.jpg)

**Figure 8.4:** `kubectl api-resources` 输出

请注意 "`NAMESPACED`" 列，它给出布尔答案，指示资源类型是否被命名空间化。

### Pod

Pod 资源是 Kubernetes 中最小的可部署单元。Pod 是一组共享卷、环境和上下文的容器的集合。我们可能不需要单独部署 Pod；Pod 通常是正在运行的工作负载的一部分。然而，大多数调查都将围绕 Pod 进行，包括描述它、获取其日志或获取关于 Pod 的基本数据。

![](img/Figure-8.5.jpg)

**图 8.5：** 使用宽输出模式获取 pods

描述 Pod：

```
kubectl describe pods/nginx-deployment8-6dcf8bbd4c-459fx
```

描述 Pod 是一个典型命令；它提供了关于 Pod 和 Pod 最近事件的许多详细信息。我们也可以对任何其他资源使用 `describe` 命令，格式如下：

```
kubectl describe <resource-kind>/<resource-name>
```

查看日志：

```
kubectl logs pods/frontend2
```

与 `describe` 命令类似，我们可以对每种资源使用 `logs` 命令，但它的价值较低。

## 工作负载管理

工作负载是在 Kubernetes 上运行的应用程序。工作负载是微服务架构中的一项服务。正如我们已经看到的，部署和管理服务（工作负载）具有挑战性、复杂，且需要大量工作。Kubernetes 通过工作负载资源提供了部署和管理服务的解决方案。在这里，我们将介绍并解释内置的工作负载资源。

### Deployment（部署）

Deployment 是 Kubernetes 中最常见的工作负载。Deployment 用于管理无状态服务。由 Deployment 管理的 Pod 是易失的。当一个 Pod 被终止（无论是由于故障还是发布导致），Deployment 资源会创建另一个具有不同名称的新 Pod。Deployment 使用一种称为 `ReplicaSet` 的资源来管理 Pod。每次我们发布新版本（仅应用新的 YAML），就会创建一个新的 `ReplicaSet` 并替换旧的 `ReplicaSet` 和旧的 Pod。

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: random-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: random-app
  template:
    metadata:
      labels:
        app: random-app
    spec:
      containers:
        - name: random-container
          image: nginx:latest
          ports:
            - containerPort: 80
```

前面的 YAML 是 Kubernetes 中最小化 Deployment YAML 的示例。

### DaemonSet

DaemonSet 是一种适合在节点上运行 Pod 的工作负载。DaemonSet 的目标是提供与本地节点相关的功能。例如，具有单个副本的 DaemonSet 会在集群中的每个节点上调度一个 Pod。用例可以是存储守护进程、网络相关守护进程、日志聚合器、遥测守护进程等。

### StatefulSet

StatefulSet 是为需要持久状态或唯一标识的 Pod 设计的工作负载资源。与 Pod 可互换且短暂的 Deployment 资源不同，StatefulSet 确保 Pod 在终止后以相同的名称和状态被重新创建。StatefulSet 提供一致的卷，Pod 可以使用称为 `PV`（PersistentVolume，持久卷）和 `PVC`（PersistentVolumeClaim，持久卷声明）的其他资源挂载该卷。StatefulSet 的用例可以是数据库服务、消息系统等。

### Job

Job 资源允许我们定义一个可以运行直到完成的任务。就这么简单。Job 资源可用于数据处理等场景。

### CronJob

它是一种运行 Job 资源的方式，但用 cron 调度器将其包装起来。CronJob 资源的用例可以是维护任务、计划备份、批处理等。

```yaml
apiVersion: batch/v1beta1
kind: CronJob
metadata:
  name: random-cronjob
spec:
  schedule: "*/5 * * * *" # Runs every 5 minutes
  jobTemplate:
    spec:
      template:
        metadata:
          labels:
            app: random-cronjob
        spec:
          containers:
            - name: random-container
              image: busybox
              command: ["echo", "Hello from the cronjob!"]
          restartPolicy: OnFailure
```

在前面的 YAML 示例中，我们可以看到 CronJob YAML；请注意，在 CronJob YAML 内部，我们定义了一个 Job YAML 并用调度器将其包装。

## 重要资源

以下资源在使用 Kubernetes 时很常见；作为开发人员，我们可能会遇到它们。

### ConfigMap

ConfigMap 是一种以键值对形式存储非机密数据的资源。Pod 可以通过环境变量、参数或卷来使用 ConfigMap 数据。ConfigMap 帮助我们实现微服务的要素之一：外部配置。可以存储在 ConfigMap 中的数据包括应用属性、连接字符串、环境数据、端点等。

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: random-configmap
data:
  app_name: my-app
  database_url: "mongodb://localhost:27017"
```

前面的 YAML 示例描述了 ConfigMap。

### Secret

Secret 资源就像 ConfigMap 资源一样，但存储的是敏感数据而非非敏感数据。可以存储在 Secret 中的数据包括密码、API 密钥、证书等。

### HPA

HPA 代表 Horizontal Pod Autoscaling（水平 Pod 自动伸缩），是一种用于自动缩放工作负载资源（并非适用于所有工作负载）的资源。水平自动伸缩意味着通过增加或减少副本（Pod）的数量来进行缩放。缩放基于指标（CPU 或内存）及其期望值。在 HPA 配置中，有最小和最大 Pod 数量限制。我们经常将 HPA 用于动态规模且负载偶尔不同的服务。

### Ingress

> “Ingress 将来自集群外部的 HTTP 和 HTTPS 路由暴露给集群内部的服务。流量路由由 Ingress 资源上定义的规则控制。”

在该引语中，术语“`services`”特指名为“`service`”的 Kubernetes 资源。该资源负责 Kubernetes 环境内的网络，不应与服务的广泛概念混淆，特别是在微服务的语境下。

![](img/Figure-8.6.jpg)

**图 8.6：** Kubernetes 中的 Ingress 资源

这是本章提到的最复杂的资源。作为开发人员，我们可能只会在想要添加新路由或更改路由时遇到 Ingress。最后，请注意 Ingress 资源解决了 API 网关（微服务架构中的核心要素）的一些重要关注点，例如负载均衡、安全性和高层路由。

## 就绪和存活探针

在 Kubernetes 中，当所有容器都在运行时，Pod 会接收流量。此外，当 Kubernetes 检测到 Pod 崩溃（由于退出代码或其他故障）时，它会重启该 Pod。这些检测（无论是 Pod 准备好接收流量还是需要重启）都由 Kubernetes 自动解决。然而，在某些场景下，我们作为开发人员希望为 Kubernetes 提供额外信息以执行这些检测。例如，我们可以决定 Pod 在建立与数据库的连接之前无法接收流量。另一个例子是，如果我们发现 Pod 缓存无效，则希望重启该 Pod。执行这种手动检测的方法就是就绪和存活探针。

*   **就绪探针**：指示容器是否准备好接收流量和请求。
*   **存活探针**：指示容器是否正常运行。如果不是，则需要被杀掉并重启。

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web-app
  template:
    metadata:
      labels:
        app: web-app
    spec:
      containers:
        - name: web-app-container
          image: nginx:latest
          ports:
            - containerPort: 80
          readinessProbe:
            httpGet:
              path: /healthz
              port: 80
            initialDelaySeconds: 5
            periodSeconds: 10
          livenessProbe:
```

## 资源分配

在 Kubernetes 中指定 Pod 或工作负载内的 Pod 时，我们可以选择性地指定可以分配给容器的资源数量。标准且常见的分配资源是 CPU 和内存，但还有其他类型。我们可以为资源分配指定两个参数——`request`（请求）和 `limit`（限制）。

*   **Request（请求）**：定义资源 `requests` 时，调度器会据此决定将 Pod 放置在哪个节点上。`request` 代表资源使用预期。
*   **Limit（限制）**：定义资源 `limit` 时，`kubelet`（“节点代理”）会强制执行该 `limit`，不允许容器超过这些 `limits`。如果 CPU 达到 `limit`，容器会被限流；如果内存达到 `limit`，运行该容器的 Pod 会被终止并重启。

掌握我们分配的资源至关重要。如果没有适当的分配，Pod 就会为所欲为。例如，我们的应用程序可能存在内存泄漏并消耗大量内存，从而影响节点或整个集群上的其他 Pod。另一个反面例子是，过小的内存分配可能会限制应用程序无法正常运行。作为开发人员，我们有责任确定容器所需的资源数量。

下面是一个 Pod YAML 示例，它启动一个名为 `hello` 的容器，并设置了 CPU 和内存的 `requests` 和 `limits`：

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: example
spec:
  containers:
  - name: hello
    image: hello-world:latest
    resources:
      requests:
        memory: "128Mi"
        cpu: "250m"
      limits:
        memory: "256Mi"
        cpu: "1"
```

## Kubernetes 最佳实践

以下四项最佳实践与 Kubernetes 开发人员更为相关。还有其他几项最佳实践更多地与运维相关。推荐一本关于 Kubernetes 详细最佳实践的书籍——*Kubernetes Patterns*。参考资料中有它的链接。这些模式并非摘自该书。

### 保持良好的 YAML 卫生

YAML 在 Kubernetes 中就是一切。YAML 代表了 Kubernetes 中的期望状态。作为用户，我们定义它们，Kubernetes 会为我们完成所有其他工作。它致力于将当前状态转换为期望状态（YAML 文件）。基于这一理解，YAML 必须满足以下要求：

*   **整洁干净**：不包含任何我们不需要或不想要的配置。此外，我们需要避免在 YAML 文件中声明默认配置。
*   **标签和注解**：这两个术语是与 YAML 资源相关的元数据。注解用于存储任意元数据，标签用于在 Kubernetes 中识别资源。这是 Kubernetes 中一个广泛的话题，但我们在此不作讨论。我们需要在每个 YAML 文件中充分利用这两种元数据。
*   **针对工作负载**：指定**存活探针和就绪探针**，正如我们之前提到的。
*   **ConfigMap 和 Secret 必须妥善配置**：切勿重复声明现有 ConfigMap 或 Secret 中已声明的键值。

### 日志记录 —— 专门针对 Kubernetes

我们在 Kubernetes 中使用日志的方式与在其他系统中使用日志的方式略有不同。为避免错误，我们必须通过包含以下内容来正确标记和标记日志：

*   **正确的服务名称**：不是 Pod 名称！我们必须在日志中包含服务名称，以便能够将日志关联到同一服务。一个常见的错误是日志仅包含实例名称（在 Kubernetes 中即 Pod 名称），而不是服务名称。
*   **版本**：为了确定哪个版本在何时发生了什么变化，我们必须在每条日志上指定服务版本。这样做，我们就能看到并观察服务的生命周期。例如，错误日志仅从版本 1.3.2 开始出现，这意味着该版本引入了一个 Bug。
*   **集群环境信息**：任何可能影响应用程序行为的数据。有时，服务出现问题或错误并非其本身的过错。集群或节点可能对此问题负责。例如，记录节点名称可能非常有用。

### 环境管理

在任何系统中，我们都会出于不同原因拥有不同的环境。生产环境、预发布环境（有时称为预生产）、测试环境、本地环境等。在 Kubernetes 中分离环境主要有两种方法：

*   **每个环境使用不同的集群**：这种方法的主要优势是环境解耦，彼此之间没有依赖。其主要劣势是为每个环境搭建不同的集群需要付出更多努力，维护多个集群也需要付出更多努力。
*   **每个环境使用不同的命名空间**：这种方法的优劣势与前一种方法恰好相反。虽然环境之间存在依赖（例如，来自不同环境的 Pod 可能被分配到同一节点上），但搭建和维护所需的精力要少得多。

### 合理的监控

除了我们作为开发人员倾向于在服务上实施的常规监控外，还有一些监控专门针对运行在 Kubernetes 上的服务。以下是三个重要的监控指标：

*   **资源**：监控 CPU、内存和存储的使用情况。监控这些资源对于优化服务性能、识别瓶颈和确保高效的资源分配至关重要。
*   **容器状态**：监控容器是否宕机/运行中/报错/探针失败/重启次数等。这些指标对于确保服务的可靠性和健康状况至关重要。此外，它们有助于发现问题、便于故障排查，并有助于构建更稳定、更有弹性的服务。
*   **Kubernetes 事件**：Kubernetes 通过事件审计其采取的操作。Kubernetes 事件记录了集群的历史。通过监控 Kubernetes 事件，我们可以检测趋势、问题和异常，并通过查看事件获得许多洞见。
