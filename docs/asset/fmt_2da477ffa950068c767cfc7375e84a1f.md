
通过将每个角色描绘为与表列关联的框，ORM 使 UCs 能以一种自然的方式呈现，从而使约束对总体的影响一目了然。实体关系（ER）建模和 UML 使用多种“基数约束”或“多重性约束”表示法来描绘关联上的内部 UCs，稍后将讨论。ER 和 UML 仅为属性上的 UCs 提供部分图形支持。ER 和 UML 均未为外部 UCs 提供任何实质性支持。

ORM 极少使用函数依赖的概念，但该概念是许多其他方法的核心。关于 ER 方法和函数依赖理论的清晰阐述，请参阅 Elmasri and Navathe (1994)。

尽管通常只有在谓词具有跨越 UC 时才明智地对其进行对象化，但在极少数情况下，移除此限制可能有用，详见第 10 章。

## 5.1 CSDP 第 5 步简介

到目前为止，我们已学会如何从熟悉的信息示例出发，得到一个概念模式图，其中基本事实类型清晰列出，并标记了每个事实类型相关的唯一性约束。我们还学会了如何对模式质量执行一些检查。在实践中，还需考虑其他类型的约束和检查。

仅次于唯一性约束重要的是 **强制角色约束**。这些约束指明对象类型的总体*必须*扮演哪些角色，哪些角色是可选的。一旦指定了强制角色约束，就会进行检查，看某些事实类型是否可从其他事实类型*逻辑推导*得出。这构成了设计程序的下一步。

接下来两节涵盖此步骤。本节讨论我们处理强制角色及后续约束时使用的一些基本概念。理解强制角色后，我们将深入探讨引用模式，特别是复合引用——这将在本章后面进行。

回顾一下，*类型*可等同于其所有可能实例的集合。这对对象类型和关系类型均适用。对于给定模式，类型是固定不变的。对于数据库的*给定状态*和给定类型 `T`，我们定义 `pop(T)`，即 `T` 的 **总体**，为 *该状态下 T 的所有实例的集合*。

我们用 `{ }` 表示 *空集*（没有成员的集合）。当数据库为空时，其每个类型的总体 = `{ }`。随着数据库更新，总体可能改变。例如，假设图 5.1 中的三元事实类型存储各国在下届奥运会中获得奖牌的信息。为便于引用，对事实类型和角色进行了编号。

![图 5.1 奥运会结果的事实类型。](img/f05-01-9780443237904.jpg)

图 5.1 奥运会结果的事实类型。

最初 `F1` 的事实表为空，因为尚不知晓任何比赛结果，所以 `pop(F1)` = `{ }`。现在假设每场比赛后更新数据库，首场比赛中美国获得金牌和铜牌，日本获得银牌。事实表的新状态如图 5.2 所示，用“G”、“S”、“B”分别代表金、银、铜牌。该事实类型的总体现包含三个事实，每录入新结果总体就会进一步增长。

![图 5.2 填入首场比赛结果后的事实类型。](img/f05-02-9780443237904.jpg)

图 5.2 填入首场比赛结果后的事实类型。

我们还定义 *角色的总体*。事实类型的每个角色关联其事实表中的一列。列中录入的值引用扮演该角色的对象类型的实例。给定任意角色 `r` 和数据库的任意状态：

*   `pop(r)` = 角色 `r` 的总体
    = `r` 列中引用的对象集合

通常引用的对象是实体而非值。例如在图 5.2 中，`pop(r1)` = {代码为“US”的国家，代码为“JP”的国家}。角色 `r` 的 *取值*，记作 `val(r)`，为其列中录入的值的集合。例如在图 5.2 中，`val(r1)` = {"US", "JP"}。

当没有混淆的可能时，对象项在列出种群时可以缩写为常量。基于此理解，在图 5.2 中，`pop(r1) = {US, JP}`，`pop(r2) = {G, S, B}`，`pop(r3) = {1}`。角色种群用于确定*对象类型种群*。以我们当前的示例为例，如果数据库中引用的每个国家都必须扮演 `r1`，那么在第一个事件后，`pop(Country)` 从 `{ }` 变为 `{US, JP}`，而 `pop(CountryCode)` 从 `{ }` 变为 `{"US", "JP"}`。假设论域仅关于奥运会，实体类型 `Country` 是可能参加奥运会的所有国家的集合。

谓词出现在基本事实类型或引用类型（又称存在事实类型）中。引用类型通常缩写为带括号的引用模式。引用类型中的角色称为*引用角色*。基本事实类型中的角色称为“*事实角色*”。在一个完成的概念模式中，每个实体类型至少扮演一个引用角色，并且除非它被声明为独立（参见第 6.3 节），否则至少扮演一个事实角色。通常，*实体类型的种群等于其角色种群的并集*。除非实体类型是独立的，否则其种群是其事实角色种群的并集。

例如，图 5.3 中的已填充模式显示了截至 2020 年测量的某些国家的面积（以平方公里为单位）和二氧化碳排放量（占全球排放量的百分比）。`Country` 实体*类型*可能包含许多国家（例如从阿富汗到津巴布韦），但此数据库状态仅列出了四个国家。数据库中 `Country` 种群的每个实例都扮演角色 `r1`、`r2` 或两者兼有。因此，`Country` 当前的*种群*是 `r1` 列或 `r2` 列中引用的所有实例的集合。

![图 5.3 pop(Country) = pop(r1) ∪ pop(r2)。](img/f05-03-9780443237904.jpg)

图 5.3 `pop(Country) = pop(r1) ∪ pop(r2)`。

我们可以将其列出如下：

| `pop(Country)` | = `pop(r1) ∪ pop(r2)` |
| --- | --- |
| | = `{AU, FR, US} ∪ {AU, CN, US}` |
| | `= {AU, CN, FR, US}` |

这里，“∪”是集合并集的运算符。两个集合的并集是两个集合中所有元素的集合。例如，`{1,2} ∪ {2, 3, 4} = {1, 2, 3, 4}`。在上述情况下，澳大利亚和美国同时出现在两个角色种群中，而中国和法国仅出现在一个中。

我们必须记录每个患者的姓名，但记录电话号码是可选的。图 5.4 显示了此情况的初步概念模型。概念事实是基本的，因此它们不能包含空值。表 5.1 中的空值通过在事实类型 `Patient has PhoneNr` 中省略患者 002 的事实来处理。

在设计过程的第 5 步中，每个角色被分类为强制或可选。**当且仅当对于数据库的所有状态，该角色必须由其对象类型种群的每个成员扮演时，该角色才是强制的**；否则，该角色是**可选的**。强制角色也称为*全角色*，因为它由其对象类型的全体种群扮演。

图 5.4 中的四个角色哪些是强制的，哪些是可选的？如果该图包含论域的所有事实类型，且其样本种群具有显著性，我们可以轻松确定哪些角色是强制的。

然而在实践中，我们大多使用子模式而非完整的或全局模式；且样本种群很少具有显著性。在这种情况下，我们应咨询领域专家，以确定相关信息是否必须为对象类型的所有实例记录（例如，我们是否必须记录每个患者的姓名？）。

考虑 `Patient` 扮演的两个事实角色。对于所示的数据库状态，这些角色的种群分别为 `{001,003}` 和 `{001,002,003}`。如果这些是 `Patient` 唯一的事实角色，则 `pop(Patient) = {001, 002, 003}`。拥有姓名的角色由所有记录在案的患者扮演，而拥有电话号码的角色仅由部分患者扮演。假设种群在这一方面具有显著性，则姓名角色是强制的，电话号码角色是可选的。

为了明确指示角色是强制的，我们在连接角色与其对象类型的线上添加一个**强制角色点**。该点可放置在角色线的任一端。在图 5.5(a) 中，该点放置在对象类型一端。这强化了约束的*全局*性质，因为它适用于对象类型的种群。如果我们向强制 `Patient` 角色的种群添加一个患者实例，则必须也将该实例包含在为 `Patient` 声明的每个其他强制角色的种群中。

![图 5.5 强制角色约束显示为角色线任一端的点。](img/f05-05-9780443237904.jpg)

图 5.5 强制角色约束显示为角色线任一端的点。

从这个意义上说，强制角色约束的影响可能超出其谓词。相反，唯一性约束在本质上是*局部*的，仅约束其角色的种群，不影响其他谓词。

在图 5.5(b) 中，强制点放置在角色一端。当对象类型的角色线非常靠近以至于在对象类型一端添加点会导致不清晰哪个角色是预期时，这种方式最好。当对象类型在同一模式页面上显示大量角色时，可能会出现这种情况。

在图 5.5 中，顶部谓词的第一个角色是强制且唯一的。强制角色约束可以口语化为“**每个** Patient **至少有一个** PatientName”，或“**每个** Patient **有一些** PatientName”。唯一性约束口语化为“**每个** Patient **至多有一个** PatientName”。组合起来，这些约束口语化为“**每个** Patient **恰好有一个** PatientName”（即每个记录在案的患者有且仅有一个记录在案的姓名）。通常，*至少一个 + 至多一个 = 恰好一个*。

在模式中，*如果同一对象类型扮演两个或多个事实角色，则这些角色单独来看是可选的，除非标记为强制*。例如，在图 5.5 中，`Patient has PhoneNr` 的第一个角色是可选的。因此，我们可以向数据库种群添加患者，而无需为该患者添加电话号码。

那么 `PatientName` 和 `PhoneNr` 所扮演的角色又如何呢？如果这些是这些对象类型在全局模式中扮演的唯一角色，那么这些角色就是强制性的。除非声明为独立（参见第 6.3 节），否则每个基本对象必须扮演某个角色，每个基本实体必须扮演某个事实角色。因此，*默认情况下，如果一个基本对象类型只扮演一个角色，或者一个基本实体类型只扮演一个事实角色*（在全局模式中），*该角色就是强制性的*。在这种情况下，隐含的强制性角色点通常会被省略。在图 5.5 中，如果 `PatientName` 和 `PhoneNr` 没有扮演其他角色，则根据隐含规则它们的角色是强制性的。在这种情况下，虽然不推荐，但这些隐含约束可以显式标记，如图 5.6 最右侧的模式所示。

![图 5.6 显式指定的隐含强制性约束（不推荐）。](img/f05-06-9780443237904.jpg)

图 5.6 显式指定的隐含强制性约束（不推荐）。

显式描绘隐含的强制性角色约束有几个缺点。首先，它使模式演进变得复杂。例如，假设明天我们决定添加事实类型 `Patient had previous—PatientName`（患者曾用名——患者姓名）；`Patient has secondary—PhoneNr`（患者有备用——电话号码）。采用隐式方法，这只是对当前模式的简单添加。但采用显式方法，我们需要删除以前隐含的强制性角色约束，并用较弱的约束来替换它们（例如，每个 `PatientName` 至少是某个 `Patient` 的现用名或曾用名；每个 `PhoneNr` 至少被某个 `Patient` 用作主号码或备用号码——这种包含性或约束稍后将讨论）。

标记隐含强制性约束的另一个问题是，这会削弱重要的强制性角色约束的突出程度（即我们需要强制执行的约束，例如，我们必须为每位患者记录姓名）。隐含强制性约束会自动强制执行，因此它们没有实现影响。

如果我们要求对简单的强制性约束采用显式方法，那么对析取强制性（包含性或）约束也应采用同样的做法。但如果析取中涉及的角色出现在不同的模式页面上，则没有方便的方法在它们之间标记该约束。

显式方法的另一个问题是它使定理规范变得复杂。稍后我们将讨论一些模式等价定理。在这种情况下，隐式方法允许我们独立于全局模式中扮演的其他角色来讨论模式片段，但显式方法会禁止这样做，从而导致额外的复杂性。

基于这些原因，除非我们有特殊理由引起人类对隐含约束的注意，否则应避免显式规范。正如下一章所讨论的，隐含强制性角色规则不适用于子类型：如果它们只扮演一个事实角色，除非标记为强制性，否则该角色是可选的。

强制性角色的总体等于其所附对象类型的总体。图 5.7 描绘了对象类型 *A* 和附加角色 *r* 的一般情况。角色 *r* 可以出现在任何元数谓词的任何位置，*A* 可以参与其他谓词。强制性角色约束是在总体上而非类型上强制执行的。如果存储的唯一事实是患者 001 名为 "Adams C"，即使 `Patient` 类型的更多实例尚未添加到总体中，`Patient` 扮演的姓名角色仍然是强制性的。

![图 5.7 角色 r 是强制性的。](img/f05-07-9780443237904.jpg)

图 5.7 角色 *r* 是强制性的。

UoD（通常是现实世界的一部分）与记录世界或 UoD 的形式模型并不相同。与其他约束一样，强制性角色约束是关于我们模型的断言，并不一定适用于被建模的世界。以我们当前的例子为例，患者是否有电话是可选的。这仅意味着我们不需要为每位患者记录电话号码。也许这是因为在现实世界中并非每位患者都有电话，又或许是有电话的患者不愿提供他们的电话号码。

图 5.8(a) 的现实世界模式涉及学术职位的申请人。按本性，每个人恰好有一个性别。作为一项业务决策，要求每位申请人都有学位。申请人可能有传真号，也可能没有。图 5.8(b) 显示了实际使用的模型。在这里，申请人可以选择是否记录其性别，但必须提供其学位的详细信息。对于该模型，做出了一项业务决策（也许是为了避免性别偏见），移除了一个在现实世界中适用的强制性约束。这种放宽某些现实世界强制性约束的相当普遍的做法，应始终是一个有意识的决定。

![图 5.8 有意决定使申请人的性别记录变为可选。](img/f05-08-9780443237904.jpg)

图 5.8 有意决定使申请人的性别记录变为可选。

*不要* 将强制性角色约束理解为“如果一个对象在现实生活中扮演该角色，则我们必须记录它”。信息系统只能使用我们提供给它的世界模型来工作——它无法强制执行模型中未表达的现实世界约束。

以下检查程序有助于确保我们的强制性角色约束是正确的。对于每个强制性角色，它在现实世界中是强制性的吗？如果不是，将其设为可选。对于每个可选角色，它在现实世界中是可选的吗？如果不是，将其设为可选的理由是什么？当我们讨论子类型时，将进一步细化这一点。

在图 5.8(b)中，强制性约束位于一个*非函数角色* 上（即未被简单唯一性约束覆盖的角色）。在这种情况下这是可以接受的，因为我们不想雇佣任何没有学位的学者，并且我们对他们的所有学位都感兴趣。

然而，总体而言，*你应该警惕向非函数角色添加强制性约束*。只有当你确定需要该约束时才这样做。此类情况可能导致实现中的复杂性（例如，引用循环），如果可能最好避免。当然，如果你的应用程序确实需要此类约束，那么无论其实现影响如何，你都应该声明它。

新手建模者往往在强制性角色约束上过于重手，如果某角色在现实世界中是强制性的，就总是将其设为强制性。然而在实践中，通常最好在模型中将其中一些角色设为可选，以允许因某些原因无法获取所有信息的情况。作为一个通用的建议，*当且仅当你需要时，才将角色设为强制性*。

当一个对象类型扮演多个角色时，在更新数据库以考虑强制性角色时需要特别小心。假设我们想将表 5.1 中的一些事实添加到一个由图 5.5 的概念模式约束的数据库中（回顾一下，记录患者姓名是强制性的，但记录电话号码是可选的）。
