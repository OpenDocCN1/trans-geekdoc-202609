
正式 IT 结构之外的对象所有权通常不那么明显。公司文档可以为设施、业务任务、流程、资产等定义所有者。然而，此类文档并不总能在现实世界中“强制执行”这种所有权。文件对象的所有权由操作系统和文件系统强制执行，而物理对象、无形资产或组织概念（如研究部门或开发项目）的所有权仅在纸面上定义，更容易被破坏。必须实施额外的安全治理，以在物理世界中提供所有权的强制执行。

### 组织角色与职责

#### 安全角色与框架

##### 安全角色

`security role`（安全角色）是指个人在组织内部安全实施和管理的整体方案中所扮演的角色。安全角色不一定在职位描述中规定，因为它们并不总是截然不同或静态的。熟悉安全角色将有助于在组织内建立通信和支持结构。该结构将实现安全策略的部署和执行。以下六个角色按其在安全环境中出现的逻辑顺序呈现：

###### 高级管理者

组织所有者（`senior manager`，高级管理者）角色分配给对组织维护的安全负最终责任、且最应关注其资产保护的人员。高级管理者必须对所有策略问题签署批准。事实上，所有活动必须经高级管理者批准并签署后方可执行。如果高级管理者不授权和支持，就不存在有效的安全策略。高级管理者对安全策略的背书表明组织接受所实施安全的所有权。高级管理者是对安全解决方案的整体成败负责的人员，并负责在为组织建立安全时履行应有的注意义务和尽职调查。

尽管高级管理者对安全负最终责任，但他们很少亲自实施安全解决方案。在大多数情况下，该责任委派给组织内的安全专业人员。

###### 安全专业人员

`security professional`（安全专业人员）、`information security (InfoSec) officer`（信息安全官）或 `computer incident response team (CIRT)`（计算机事件响应小组）角色分配给受过培训且经验丰富的网络、系统和安全工程师，他们负责遵循高级管理层授权的指令。安全专业人员对安全负有职能责任，包括编写安全策略并实施它。安全专业人员的角色可被标记为 IS/IT 职能角色。安全专业人员角色通常由一个团队担任，负责根据批准的安全策略设计和实施安全解决方案。安全专业人员不是决策者；他们是执行者。所有决策必须留给高级管理者。

###### 数据所有者

`data owner`（数据所有者）角色分配给负责对信息进行分类，以便在安全解决方案中进行放置和保护的人员。数据所有者通常是高层管理人员，对数据保护负最终责任。然而，数据所有者通常将实际数据管理任务的责任委派给数据管理员。

###### 数据管理员

`data custodian`（数据管理员）角色分配给负责实施安全策略和高级管理层规定的保护措施的用户。数据管理员执行所有必要的活动，以充分保护数据的 CIA 三要素（机密性、完整性和可用性），并履行上级管理层委派的要求和职责。这些活动可以包括执行和测试备份、验证数据完整性、部署安全解决方案以及根据分类管理数据存储。

###### 用户

`user`（用户，`end user` 最终用户或 `operator` 操作员）角色分配给任何有权访问受保护系统的人员。用户的访问权限与其工作任务相关联，并受到限制，使其仅拥有执行其职位所需任务所必需的访问权限（最小权限原则）。用户负责理解并维护组织的安全策略，方法是遵循规定的操作程序并在定义的安全参数内操作。

###### 审计员

`auditor`（审计员）负责审查和验证安全策略是否正确实施，以及衍生的安全解决方案是否充分。审计员角色可分配给安全专业人员或受过培训的用户。审计员生成合规性和有效性报告，由高级管理者审查。通过这些报告发现的问题将转化为由高级管理者分配给安全专业人员或数据管理员的新指令。然而，审计员被列为最后一个角色，因为审计员需要一个活动源头（即在环境中工作的用户或操作员）来进行审计或监控。

所有这些角色在安全环境中都发挥着重要作用。它们对于识别责任和义务，以及识别分层管理和委派方案非常有用。

#### 安全控制框架

为组织制定安全立场通常不仅仅是写下几个崇高的理想。在大多数情况下，制定可靠的安全策略需要大量的规划。许多《呆伯特》漫画的粉丝可能认识“开会计划开会，为未来的开会做准备”这一看似荒诞的概念。但事实证明，安全规划必须从“计划规划”开始，然后转入标准和合规规划，最后进入实际的计划开发和设计。跳过这些“计划规划”中的任何步骤，都可能在组织的安全解决方案启动之前就使其偏离轨道。

最重要的安全规划步骤之一是考虑组织期望的安全解决方案的整体 `security control framework`（安全控制框架）或结构。关于安全概念基础设施，您可以从多个选项中进行选择；然而，更广泛使用的安全控制框架之一是 **Control Objectives for Information and Related Technology (COBIT，信息及相关技术控制目标)**。COBIT 是由 **Information Systems Audit and Control Association (ISACA，信息系统审计与控制协会)** 制定的一套记录在案的 IT 安全最佳实践。它规定了安全控制的目标和要求，并鼓励将 IT 安全理想映射到业务目标。COBIT 5 基于企业 IT 治理和管理的五大核心原则：

*   **原则 1**：满足利益相关者需求
*   **原则 2**：覆盖企业端到端
*   **原则 3**：应用单一集成框架
*   **原则 4**：实现整体方法
*   **原则 5**：将治理与管理分离

COBIT 不仅用于规划组织的 IT 安全，还作为审计员的指南。COBIT 是一个广泛认可和受尊重的安全控制框架。

幸运的是，考试中仅适度引用 COBIT，因此无需了解更多细节。但是，如果您对这一概念感兴趣，请访问 ISACA 网站（[www.isaca.org](http://www.isaca.org)），或者如果您想要一个总体概览，请阅读维基百科上的 COBIT 条目。

还有许多其他 IT 安全标准和指南。其中一些包括：

*   **开源安全测试方法手册 (OSSTMM)**（[www.isecom.org/research/](http://www.isecom.org/research/)）：一份经过同行评审的指南，用于安全基础设施的测试和分析
*   **ISO/IEC 27002**（取代了 ISO 17799）（[www.iso.org/standard/54533.html](https://www.iso.org/standard/54533.html)）：一项国际标准，可作为实施组织安全和相关管理实践的基础
*   **信息技术基础设施库 (ITIL)**（[www.itlibrary.org](http://www.itlibrary.org)）：最初由英国政府制定，ITIL 是一套核心 IT 安全和运营流程的推荐最佳实践，常被用作定制 IT 安全解决方案的起点

#### 应有的注意义务与尽职调查

### 为什么计划安全如此重要？

其中一个原因是对 `due care`（应有注意）和 `due diligence`（应有勤勉）的要求。`Due care` 是指运用合理的注意来保护组织的利益。`Due diligence` 是指执行维持应有注意工作的活动。例如，应有注意是开发一个包含安全策略、标准、基线、指南和程序的正式安全架构。应有勤勉是将这一安全架构持续应用到组织的 IT 基础设施上。运营安全是组织内所有责任方对应有注意和应有勤勉的持续维护。

在当今的商业环境中，审慎是强制性的。展示应有注意和应有勤勉是发生损失时证明无过失的唯一途径。高级管理层必须展示应有注意和应有勤勉，以在损失发生时降低其责任和法律义务。

### 制定、记录并实施安全策略、标准、程序和指南

对于大多数组织而言，维护安全是持续业务的重要组成部分。如果其安全受到严重威胁，许多组织将面临倒闭。为了降低安全故障的可能性，实施安全的过程已通过文档的层级化组织而某种程度上正式化。每一层级侧重于特定类型或类别的信息和问题。制定并实施文档化的安全策略、标准、程序和指南，可构建可靠坚实的安全基础设施。这种正式化极大地减少了为 IT 基础设施设计和实施安全解决方案时的混乱与复杂性。

#### 安全策略

正式化的顶层称为安全策略。`security policy`（安全策略）是一份定义组织所需安全范围的文档，论述需要保护的资产，以及安全解决方案为提供必要保护应达到的程度。安全策略是组织安全需求的概览或概括。它定义了主要安全目标，并概述了组织的安全框架。它还确定了数据处理的主要功能领域，并阐明和定义了所有相关术语。它应明确界定安全为何重要以及哪些资产有价值。它是实施安全的战略计划。它应广泛概述为保护组织关键利益而应采用的安全目标和实践。该文档论述了安全对日常业务运营各方面的重要性，以及高级管理层对安全实施的支持的重要性。安全策略用于分配职责、定义角色、指定审计要求、概述执行流程、表明合规要求，并定义可接受的风险级别。该文档常作为高级管理层已履行应有注意义务、保护自身免受入侵、攻击和灾害的证据。安全策略是强制性的。

许多组织采用多种类型的安全策略来定义或概述其整体安全战略。`organizational security policy`（组织安全策略）关注与组织各方面相关的问题。`issue-specific security policy`（特定议题安全策略）关注某个特定的网络服务、部门、职能或其他有别于整个组织的方面。`system-specific security policy`（特定系统安全策略）关注单个系统或系统类型，规定批准的硬件和软件，概述系统加固方法，甚至强制要求防火墙或其他特定安全控制。

除了这些聚焦类型的安全策略外，还有三大总体类别的安全策略：监管类、建议类和信息类。`regulatory policy`（监管策略）在行业或法律标准适用于您的组织时是必需的。该策略论述必须遵守的法规，并概述用于实现合规的程序。`advisory policy`（建议策略）论述可接受的行为和活动，并定义违规后果。它解释了高级管理层对组织内安全与合规的期望。大多数策略属于建议类。`informative policy`（信息策略）旨在提供关于特定主题的信息或知识，例如公司目标、使命宣言，或组织如何与合作伙伴和客户互动。信息策略提供与整体策略特定要素相关的支持、研究或背景信息。

从安全策略中衍生出许多其他文档或子要素，这些是完整安全解决方案所必需的。策略是宽泛的概览，而标准、基线、指南和程序则包含关于实际安全解决方案更具体、更详细的信息。标准是安全策略的下一层级。

#### 安全标准、基线和指南

一旦确定了主要安全策略，其余安全文档即可在策略指导下编写。`Standards`（标准）定义了硬件、软件、技术和安全控制统一使用的强制性要求。它们提供了一种行动方针，使技术和程序在整个组织中统一实施。标准是战术文档，定义了为实现安全策略所定目标和总体方向而采取的步骤或方法。

下一层级是基线。`baseline`（基线）定义了组织内每个系统必须达到的最低安全级别。所有不符合基线的系统应停止投入生产，直到其达到基线要求。基线建立了一个通用的基础安全状态，所有额外的、更严格的安全措施均可在此基础上构建。基线通常针对特定系统，且常参考行业或政府标准，如可信计算机系统评价标准（TCSEC）、信息技术安全评估标准（ITSEC）或美国国家标准与技术研究院（NIST）标准。

指南是正式化安全策略结构的下一个要素。`guideline`（指南）提供关于如何实施标准和基线的建议，并作为安全专业人员和用户的操作指南。指南具有灵活性，可针对每个独特的系统或条件进行定制，并可用于创建新程序。它们陈述应部署哪些安全机制，而非规定特定产品或控制及详细配置设置。它们概述方法论，包含建议行动，且非强制性。

#### 安全程序

程序是正式化安全策略结构的最后要素。`procedure`（程序）或 `standard operating procedure (SOP)`（标准操作程序）是一份详细的分步操作指南文档，描述实施特定安全机制、控制或解决方案所需的确切行动。程序可以论述整个系统部署操作，也可以聚焦于单个产品或方面，例如部署防火墙或更新病毒定义。在大多数情况下，程序针对特定系统和软件。随着系统软硬件的演进，程序必须更新。程序的目的是确保业务流程的完整性。如果所有工作都遵循详细程序执行，则所有活动应符合策略、标准和指南。程序有助于确保所有系统安全的标准化。

很多时候，策略、标准、基线、指南和程序仅仅是在顾问或审计师的敦促下作为事后诸葛亮般的产物被制定出来的。如果这些文档不被使用和更新，安全环境的管理将无法将它们作为指南。如果没有这些文档提供的规划、设计、结构和监督，任何环境都无法保持安全，也无法体现应有的尽职调查。

将所有这些要素的各个方面整合到单个文档中也是常见的做法。这应该避免。这些结构中的每一个都必须作为一个独立的实体存在，因为每一个都执行不同的专门功能。在正式安全策略文档结构的顶层，文档较少，因为它们包含对概览和目标的宏观概括讨论。在正式结构的较低层（即指南和程序）有更多的文档，因为它们包含针对有限数量的系统、网络、部门和领域的具体细节。

将这些文档作为独立实体保存可带来多项优势：

*   并非所有用户都需要知道所有安全分级层面的安全标准、基线、指南和程序。
*   当变更发生时，仅更新和重新分发受影响的材料，比更新整体庞大的策略并将其在整个组织中重新分发要容易得多。

编写安全策略的全部内容及所有支持文档可能是一项艰巨的任务。许多组织光是定义其安全的基础参数就已捉襟见肘，更别提详述其日常活动的每一个方面。然而，理论上，详细且完整的安全策略能以指导性、高效且具体的方式支持现实世界的安全。一旦安全策略文档合理完善，它就可用于指导决策、培训新用户、响应问题，并预测未来扩展的趋势。安全策略不应是事后诸葛亮，而应是建立组织的关键部分。

关于构成完整安全策略的文档，还有几个额外的视角需要理解。图 1.6 展示了这些组件的依赖关系：策略、标准、指南和程序。安全策略定义了有组织的安全文档的整体结构。然后，标准基于这些策略，同时也由法规和合同强制要求。由此衍生出指南。最后，程序基于其他三个组件。倒金字塔用于表示这些文档各自的体量或规模。在一个完整的安全策略中，程序的数量通常远多于任何其他要素。相比之下，指南比程序少，标准比指南更少，而全局性或组织级的安全策略通常最少。

#### 理解并应用威胁建模概念和方法论

威胁建模是识别、分类和分析潜在威胁的安全过程。`威胁建模` 可在设计和开发阶段作为主动措施执行，也可在产品部署后作为被动措施执行。无论哪种情况，该过程都会识别潜在危害、发生概率、关注优先级，以及消除或降低威胁的手段。本节将介绍各种威胁建模概念示例以及几种威胁建模方法论。

威胁建模不应是一次性事件。相反，组织通常在系统设计过程早期就开始威胁建模，并贯穿其整个生命周期。例如，微软使用 `安全开发生命周期 (SDL)` 流程，在产品开发的每个阶段考虑并实施安全。这支持“设计安全、默认安全、部署和通信安全”（也称为 `SD3+C`）的座右铭。该流程有两个目标：

*   减少与安全相关的设计和编码缺陷数量
*   降低任何剩余缺陷的严重程度

换句话说，它试图减少漏洞，并降低任何残留漏洞的影响。总体结果是风险降低。

`主动方法` 威胁建模发生在系统开发的早期阶段，具体是在初始设计和规格建立期间。这种类型的威胁建模也称为防御性方法。该方法基于预测威胁并在编码和构建过程中设计特定防御，而不是依赖部署后的更新和补丁。在大多数情况下，集成的安全解决方案比事后强行塞入的解决方案更具成本效益且更成功。不幸的是，并非所有威胁都能在设计阶段预测到，因此仍需要被动方法威胁建模来解决不可预见的问题。

`被动方法` 威胁建模发生在产品创建并部署之后。这种部署可能是在测试或实验室环境中，也可能面向大众市场。这种类型的威胁建模也称为对抗性方法。这种威胁建模技术是道德黑客、渗透测试、源代码审查和模糊测试的核心概念。虽然这些过程在发现需要解决的缺陷和威胁方面通常很有用，但它们不幸的是会导致额外的编码工作来添加新的对策。回归设计阶段从长远来看可能会产生更好的产品，但从头开始的成本极高，且会导致产品发布显著延迟。因此，捷径是在部署后制作更新或补丁添加到产品中。这导致安全改进效果较差（相对于主动威胁建模），代价是潜在的功能性和用户友好度降低。

##### 识别威胁

威胁的可能性几乎是无限的，因此使用结构化方法准确识别相关威胁非常重要。例如，一些组织使用以下三种方法中的一种或多种：

**聚焦资产** 此方法利用资产估值结果，尝试识别针对有价值资产的威胁。例如，可评估特定资产以确定其是否易受攻击。如果资产托管数据，可评估访问控制以识别可绕过身份验证或授权机制的威胁。

**聚焦攻击者** 某些组织能够识别潜在攻击者，并根据攻击者的目标识别其代表的威胁。例如，政府通常能够识别潜在攻击者并认识到攻击者想要实现的目标。然后，他们可以利用这些知识来识别和保护其相关资产。这种方法的一个挑战是，可能会出现以前不被视为威胁的新攻击者。

**聚焦软件** 如果组织开发软件，它可以考虑针对软件的潜在威胁。虽然多年前组织不常开发自己的软件，但如今这很常见。具体来说，大多数组织都有网络业务，许多组织创建自己的网页。花哨的网页能带来更多流量，但也需要更复杂的编程，并带来额外的威胁。

### 威胁建模

如果威胁被识别为攻击者（而非自然威胁），威胁建模会尝试识别攻击者可能试图完成的目标。某些攻击者可能想要使系统瘫痪，而其他攻击者可能想要窃取数据。一旦识别出此类威胁，就会根据其目标或动机对其进行分类。此外，将威胁与漏洞配对以识别可利用漏洞并对组织构成重大风险的威胁也是一种常见做法。威胁建模的最终目标是针对组织的宝贵资产对潜在威胁进行优先级排序。
