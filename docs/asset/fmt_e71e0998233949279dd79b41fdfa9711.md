    ```

例程是显式`调用`的代码主体，这与本质上由事件驱动的触发器形成对比。UDF 返回标量或表结果。创建函数的基本语法是：

```
create function functionname ( [ parameter-list ] ) returns { data-type | table col-name data-type [,…] } function-body
```

存储过程能够执行比函数更广泛的活动，例如更新表，是封装 SQL 代码的标准方式。存储过程常用于将数据库与可能造成损害的用户操作“隔离”开。创建存储过程的基本语法是：

```
create procedure procedurename ( [ { in | out | inout } parmname parmtype [,…] ] ) procedure-body
```

数据库模式可能包含其他类型的对象。`序列`提供标识符的自动唯一生成。`索引`可用于提高查询性能。`游标`可用于提供逐行处理。

实际的数据库系统包含处理并发的措施，通常基于资源的选择性锁定以避免事务间的干扰。可以在语句级或连接级指定更多隔离与更多吞吐量之间的首选平衡点。

数据库安全围绕两个主要概念。用户根据指定的凭据进行身份验证以确认其身份。权限——执行特定类型操作的权利——可以授予或保留给特定个人或组。

元数据——关于数据库系统本身的信息——存储在各种表中供系统内部使用。这些信息也可以被查询，尽管标准做法是不鼓励直接访问这些表，而是使用系统视图。

## 14.1 模式等价性与优化

前几章讨论了如何用概念模式对应用程序结构建模，然后将其映射为用于关系数据库系统实现的逻辑模式。虽然大部分设计和映射可以自动化，但人类必须执行概念模式设计过程（CSDP）步骤 1，因为用语言表达关于现实世界的相关事实涉及人类理解。考虑到建模论述域（UoD）这一初始步骤的非正式性质，人们往往会想出不同的方式来描述同一现实，这并不令人惊讶。

因此，同一业务领域可以用多个概念模式建模。此外，同一概念模式可以通过不同方式映射到逻辑模式，要么选择不同类型的逻辑模型（例如面向对象关系型），要么覆盖默认映射选择（例如选择单独的子类型表或反规范化）。最后，同一逻辑模式可以通过多种方式在物理模式中实现（例如不同的索引选择）。

### 模式转换与优化

为了帮助您从如此多样的不同设计中进行选择，本章探讨了模式转换以提供备选方案的各种方法，随后给出了优化选择的指导原则。在此过程中，我们将介绍一些关于模式转换和规范化的理论，以确保对底层概念有正确的理解。我们将从概念层面入手，然后深入到逻辑层和物理层。示例将说明这些思想如何也可用于重构那些被证明不令人满意的现有应用程序。

#### 模式转换与优化简介

本节其余部分通过一个示例，为模式转换和优化提供一个简单的介绍。前几章介绍了一些建模选择。例如，我们可以用扁平形式或嵌套形式来建模一个三元事实类型。基本上，如果且仅当一个概念模式中能建模的任何 UoD 状态或转换也能在另一个中建模时，这两个概念模式才是`等价`的。

#### 模式转换的应用

对模式转换的了解有助于我们看到可能的不同设计选择。此外，如果两个独立开发的模式需要完全或部分集成，我们通常需要解决每个模式对共同 UoD 特征建模方式的差异。为此，我们需要知道一种表示是否可以转换为另一种，以及如果可以，如何转换。

概念模式转换的另一个用途是将原始概念模式重塑为直接映射到更高效实现的模式。此过程称为`概念模式优化`。例如，图 14.1(a) 中的概念模式映射到单个表。采用封闭世界解释，我们可以使用 图 14.3(a) 所示的表模式。为便于讨论，包含了样本数据的数据量。然而，由于沉溺事实类型是 *m:n* 的，图 14.1(b) 中的模式映射到两个表，如 图 14.3(b) 所示。同样，也包含了样本数据量。

对于许多应用程序，单表解决方案更高效。它使我们能够列出关于患者的所有信息，而无需表连接。它还避免了强制执行子集约束所需的任何表间访问（例如，添加恶习事实或删除患者时）。因此，在将 图 14.1(b) 的模式传递给正常的 Rmap 过程之前，可以通过将其转换为 图 14.1(a) 的模式来进行优化。

然而，如果我们想要记录的恶习集合经常发生变化，两表方案可能更可取，因为它无需更改模式本身即可适应此类变化。关于执行此类优化的指南将在本章后面给出。如果优化后的概念模式仍无法提供高效的映射，则可能需要进行一些反规范化，如第 14.7 节所述。

在重构工程中，优化是应用于现有数据库的。因此，在模式本身转换之后，我们还有将存储在原始数据库中的信息迁移到新模式中的`数据迁移`这一额外任务。如果没有自动化工具的协助，这项任务可能既漫长又繁琐。

下面是将图 14.3(b) 中填充的两表模型转换为图 14.3(a) 中单表模型的一种基本方法，假设使用的是结构化查询语言 (SQL) 数据库。首先，使用以下语句向 `Patient` 表添加一个可选的 `isSmoker` 列：

```
alter table Patient add column isSmoker char check (isSmoker in ('Y','N'))
```

此时，`isSmoker` 列填充的是空值。检查约束未被违反，因为其计算结果为 unknown（未知）（而不是 false）。现在，添加适当的“Y”或“N”值以指示谁吸烟：

```
update Patient set isSmoker = case when patientNr in (select patientNr from Indulges where vice = 'S') then 'Y' else 'N' end
```

现在，使 `isSmoker` 列成为强制性的：

```
alter table Patient add constraint isSmokerNonNull check (isSmoker is not null)
```

同样，向 `Patient` 表添加 `isDrinker` 列，更新其填充数据，最后删除 `Indulges` 表。在实践中，迁移数据的最高效方式可能取决于所使用的数据库管理系统 (DBMS)。与刚才讨论的简单示例相反，更典型的做法是保持原始数据库不变，创建一个新模式，将数据迁移到新模式，然后删除原始数据库（参见第 14.9 节）。

这完成了我们对模式等价和优化基本概念的高层介绍。以下章节将进一步展开这些概念，同时也简要阐述规范化理论。

## 14.2 谓词特化与泛化

上一节指出了相同的 UoD 结构如何能用不同的等价模式来描述，并讨论了将一种模式重塑为另一种模式的转换。本节讨论一类称为`谓词特化`的模式转换，以及其逆操作`谓词泛化`。

如果两个或多个谓词可被视为一个更泛化谓词的特殊情况，则我们可以用该更泛化的谓词来替换它们，只要原来的区别能以某种方式保留下来即可。例如，如果我们将图 14.1(a) 的模式转换为图 14.1(b) 的模式，我们就将吸烟和饮酒`泛化`为沉溺于恶习，其中恶习有两种特定情况。如果我们按相反方向转换，则将沉溺于恶习`特化`为两个谓词，每个情况对应一个。

谓词特化和泛化与对象类型特化和泛化是相似的概念，不同之处在于很少在谓词之间指定任何子类型联系（为此谓词必须被对象化）。

如果`值约束`或`频率约束`表明某谓词具有有限数量的情况，则该谓词可以被特化。带有值约束的示例更常见，因此我们首先考察这些示例。吸烟者-饮酒者示例提供了一个说明，其中 `Vice` 具有值约束 {“S”, “D”}。作为另一个示例，回顾图 14.4(a) 中复现的奥林匹克运动会模式。

![Fig. 14.4 The ternary is specialized into three binaries by absorbing MedalKind.](img/f14-04-9780443237904.jpg)

图 14.4 通过吸收 `MedalKind`，三元谓词被特化为三个二元谓词。

奖牌恰好有三种，因此如图 14.4(b) 所示，三元谓词可被特化为三个二元谓词，每种奖牌一种。您可以将从模式 (a) 到模式 (b) 的转换可视化为将对象类型 `MedalKind` `吸收` 进三元谓词，以将其划分（或特化）为三个二元谓词。因此，这种转换也称为`对象类型吸收`。

从 (b) 到 (a) 的逆向转换通过提取对象类型 `MedalKind` 将三个二元谓词泛化为三元谓词——这可称为`对象类型提取`。在恶习示例中，一个二元谓词被特化为一元谓词。在运动会示例中，一个三元谓词被特化为二元谓词。一般来说，当一个 *n* 值对象类型被吸收进一个谓词时，产生的 *n* 个特化谓词每个都比原谓词少一个角色（因为对象类型已被吸收）。

虽然等价关系是以图表形式列出以辅助理解，但存在将图表形式映射为谓词逻辑的形式化映射，实际的等价证明是在其中进行的（Halpin, 1989b）。从这个意义上说，这些结果可称为定理。这一通用结果列于图 14.5。

![Fig. 14.5 PSG1: R may be specialized into S1 … Sn by absorbing B.](img/f14-05-9780443237904.jpg)

图 14.5 PSG1：通过吸收 *B*，*R* 可被特化为 *S*[1] … *S*[*n*]。

图 14.5 中的模式等价称为`谓词特化/泛化定理 1` (PSG1)。谓词 *R* 和 *S* 分别具有 *m* + 1 个角色和 *m* 个角色，其中 *m* ≥ 1。对象类型 *A*[1] … *A*[*m*] 和 *B* 不一定是不同的。*B* 的值类型具有 *n* 个值 *b*[1], …, *b*[*n*]。如果 *m* = 1，则是在二元谓词与 *n* 个一元谓词之间转换；如果 *m* = 2，则是在三元谓词与 *n* 个二元谓词之间转换；以此类推。从左向右转换通过吸收对象类型 *B* 将谓词 *R* 特化为 *n* 个谓词 *S*[1] … *S*[*n*]。从右向左的逆向转换通过提取 *B* 将较短的谓词泛化为较长的谓词。作为练习，绘制 *m* = 1、2 和 3 时的图表。

无论添加什么额外约束，定理 PSG1 都成立。但是，`添加到其中一个模式的任何约束都必须转换为另一个模式上等价的额外约束`。例如，图 14.4(a) 中的唯一性约束转换为图 14.4(b) 中的三个较短的唯一性约束。这是 PSG1 的以下推论的一个实例（使用“UC”代表“唯一性约束”，并将“spans”读作“精确跨越”）。

*   如果 *R* 中的一个 UC 跨越了 *B* 的角色与其他角色的组合，则 *S*[1] … *S*[*n*] 中这些其他角色的特化上跨越一个 UC；反之亦然。

### Figure 14.6 illustrates the most common case
