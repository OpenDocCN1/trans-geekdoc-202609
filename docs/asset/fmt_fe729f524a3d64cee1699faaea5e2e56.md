风险登记表可以包含潜在风险，而不仅仅是实际风险；项目经理和渗透测试工程师可以通过头脑风暴创建一个潜在风险和解决方案的登记表。以这种方式构建风险登记表的优势在于，一旦风险发生，团队已经想出了解决方案。

# 知识数据库

知识数据库用于保留渗透测试团队执行的所有项目的历史数据以及最终结果。该数据库应包含常见问题（如缩写词、协议和最佳实践）、已知问题（漏洞数据、易受攻击系统）以及解决方案（利用脚本、配置错误发现）。

## 创建知识数据库

知识数据库主要是为了渗透测试工程师的利益，它将以自由流注释的形式存在，类似于表 18.3 中所示的内容。数据应存储在数据库中并具有可搜索性，以便工程师能够快速找到与查询相关的所有引用。然而，我们需要对输入的数据保持谨慎——在向数据库添加任何内容之前需要考虑机密性。我们将在本章后的“发现结果的脱敏”部分对此进行更详细的介绍。

**表 18.3.** 知识数据库条目

| 知识类型 | 数据 |
| --- | --- |
| 漏洞利用 | 要利用 Webmin 任意文件任意漏洞：1. 从 [`milw0rm.org/exploits/2017`](http://milw0rm.org/exploits/2017) 下载 Perl 脚本 2. 将文件保存为 `webmin_exploit.pl` 3. 使用以下命令更改 `webmin_exploit.pl` 文件的权限：`chmod +x webmin.pl` 4. 使用以下命令启动 webmin 利用：`webmin_exploit.pl <url> <port> <filename> <target>` |

知识库可以包含任何对未来渗透测试项目可能有益的数据。然而，随着时间的推移，数据库可能会变得很大。只要输入知识数据库的数据能提供某些收益，这并不一定是坏事。为了防止工程师向数据库中输入无意义的数据，对所有提交进行同行评审有助于识别哪些内容属于数据库，哪些内容应该被丢弃。

# 要求知识数据库条目

许多维护知识数据库的组织要求工程师为每个项目生成条目。要求员工输入数据有一些缺点——无价值的条目。为了达到配额，工程师可能会输入实际上并不属于这里的有效数据。我见过的最糟糕例子是一个关于“如何开启我的电脑”的条目。了解这些信息固然好，但真的属于数据库吗？！

## 发现结果的脱敏

添加到知识库中的信息不应包含敏感信息，包括互联网协议（IP）地址。随着时间的推移，知识库可能会被公司内部其他部门或组织使用；通过在输入数据库之前对数据进行脱敏可以避免隐私问题。

**警告** 即使没有打算让风险清单离开渗透测试团队，也始终存在未经授权访问的风险。风险清单中真的没有包含敏感数据，特别是如果目标是在未来的任务中保持灵活性——在与不同客户的项目中，了解旧的 IP 地址和用户名可能是毫无用处。对于知识数据库条目的匿名化也有一些支持论点。由于条目在输入数据库之前经过了同行评审，它们已经通过了准确性审查。然而，某些工程师可能可能会于向注册表中添加信息，担心对其添加内容的同行评审或未来的编辑会被批评。允许匿名输入数据的想法是这将为数据库添加更多更有价值的信息。在实践中，输入信息的工程师匿名化产生的问题多于其收益。在小型项目中，每个人都知道任务是如何分配给工程师的，因此尽管匿名，每个人也都能识别出是谁写了哪些条目。另一个问题是，如果以后其他工程师有疑问，没有办法找到输入数据的工程师进行跟进。有一种观点认为，当工程师知道他们的条目会被其他人看到时，他们可能会投入更多精力准备数据。对知识数据库中的客户信息进行脱敏是开发知识数据库的重要步骤，但对员工数据的脱敏并没有那么有益。

## 项目管理知识数据库

工程师并不是唯一能从知识库中受益的人。尽管风险清单是改进整个项目的关键工具，但*项目管理知识数据库*可以帮助提高项目经理的技能和响应时间，特别是渗透测试团队使用不同的项目经理时。项目管理知识库可能包含以下内容：

- 公司内部的联系人
- 客户组织的联系人
- 资源供应商
- 领域专家列表
- 过去的团队成员列表
- 合同
- 工作说明（SOW）
- 项目模板

上述列表主要由联系信息组成。虽然相同的信息可以保存在通讯录中，但项目管理数据库的意义在于它可以扩展到整个公司乃至海外，并且对所有项目经理都有益。能够快速识别出曾与公司合作但可能不熟悉渗透测试项目的供应商，仍然会为渗透团队带来利益。

# 行后回顾

在第 15 章中，我们讨论了同行评审如何提高最终报告的清晰度和准确性。在本章中，我们将讨论类似的评审——项目评估和团队评估。与第 15 章中的同行评审不同，行后回顾可以作为小组活动或个人活动进行。在所有团队成员参加的会议上进行项目和团队评估的优点是促进知识共享和头脑风暴。然而，参与者可能在对项目和同事进行评价时有所顾虑。要求团队成员匿名提供评估可以增加获得项目执行人员诚实意见的机会。

## 项目评估

项目评估应识别渗透测试项目中良好或需要改进的部分。项目评估的主要目标是为项目经理提供有关渗透测试项目流程的反馈，以及哪些项目阶段需要改进。项目经理感兴趣的话题包括：

- 调度问题（时间太短、时间太长等）
- 资源可用性
- 风险管理
- 项目范围问题（范围太宽、太窄等）
- 沟通问题

评估中提供的信息应该证实或挑战项目经理对项目流程的评估观点，并对如何在未来项目中改进项目管理流程提出想法。

## 团队评估

进行团队评估是一项敏感的任务——团队成员通常不喜欢互相进行批评，即使这些批评是具有建设性的。项目经理在向团队展示评估结果时必须非常小心，特别是评估问卷的措辞；评估的整体基调必须是积极的，并传达出评估问卷背后的目的是改进项目团队，而不是为了找错。问卷应包含对每位渗透测试（PenTest）团队成员（包括其自身）以下几个方面的提问：

- 技术优势
- 技术劣势
- 在项目每个组件中的投入精力
- 团队培训想法
- 时间管理技能
- 阻碍有效团队的的
- 对团队生产力的总体评价

**警告** 如果团队评估的危害大于益处，请毫不犹豫地放弃该评估流程。团队评估的结果并不是为了在团队内部传的；相反，项目经理应该利用结果来制定改进未来项目的计划。问卷将对团队成员之间的群体动态提供一些见解，并提供可用于分配未来任务的额外质量指标。培训需求可以得到完善，项目风险也可以被识别。

## 培训建议

通过识别未来项目所需的技能组合并获取渗透测试工程师的反馈，项目经理可以列出一份团队知识差距清单。一旦确定了知识短板，项目经理就可以找到合适的培训计划，在下一个项目开始之前将团队提升到必要的技能水平。如果项目经理成功提升了团队技能，新知识可能有助于获得更多项目。客户经理和营销团队需要了解任何新的技能组合，以便发现额外的业务机会。

# 狡猾的工程师

我曾被一个项目中的工程师欺骗过，他们在行动后回顾（AAR）之前合谋，这样他们就会要求相同类型的培训。行动后回顾本应该是匿名的，但团队成员通力合作，对需要什么培训达成了统一的口号。虽然培训请求与未来的项目有些契合，但工程师选择这项特定培训的原因是因为地点和时间——春假期间，在佛罗里达州的奥兰多。他们的想法是想让公司支付他们带孩子去迪士尼乐园的费用的一部分。我想他们当时玩得很开心。如果项目经理过去安排过培训，可以对培训课程进行指标化评估，这些指标应该表明培训公司的课程是否有益。如果之前的培训没有让团队的渗透测试技能得到满意的提高，可以考虑其他资源。选择培训不应仅仅基于精美的传单、口口碑或“酷”因素；项目经理应该根据未来项目的需求定义团队内部的缺陷，并找到一种符合公司业务目标的培训课程。

**提示** 信息安全会议是提高渗透测试团队技能的绝佳方式。许多会议会增加每年演讲的视频，让团队能够从过去的会议中学习。当地活动也可能提供培训机会。请参阅第 3 章

## 总结

使用风险管理登记对于专业的渗透测试项目经理来说非常有益，无论团队规模或项目频率如何。其中某些信息可以用于不同类型的项目，而不仅仅是渗透测试。然而，有些问题是渗透测试特有的——网络中断对建筑现场的影响可能小于对渗透测试的影响。项目经理需要根据情况调整团队的应对措施。知识数据库将帮助工程师比翻旧报告或努力记忆更容易访问历史数据。尽管数据库条目是自由流格式，但通过将条目纳入数据库，可以快速查询相关信息。对进入数据库的所有内容进行审查是一个好主意，可以排除无用信息。行动后回顾可以为项目经理提供额外的指标，用于改进渗透测试团队成员的优缺点和项目流程。确保回顾的整体基调是积极的。利用行动后回顾获得的知识为未来项目制定计划并安排适当的培训。

### 行动后回顾

# 团队评估指南

- 要求团队成员匿名提供评估，可以增加从参与项目的人那里获得诚实意见的几率。
- 项目评估应识别出渗透测试项目中运行良好或需要改进的方面。
- 团队评估的整体基调必须是积极的，并传达出评估问卷背后的目的是改进项目团队——而不是找错。

**问：** 风险管理注册表条目应该多久重新评估一次？

**答：** 每当风险变为现实时，项目团队都应该评估事件的结果并相应修改注册表条目。除非有迫切需求，否则在风险发生之前不应重新评估条目。

**问：** 作为处理风险的决策者，我可以选择执行风险注册表中列出的清单之外的其他操作吗？

**答：** 风险注册表是一份指南，旨在提供在冷静时期开发的选项。由于无法预测未来事件涉及的所有变量，因此可以做出与风险注册表中列目相反的决策。然而，在现实案例中，当经理偏离风险注册表的选项时，经理往往会被要求解释为什么没有遵循建议。

**问：** 知识数据库与互联网上漏洞数据库中的信息有何区别？

**答：** 知识数据库中与漏洞相关的条目可能与漏洞数据库中发布的常见漏洞披露（`CVE`）信息非常相似。在这种情况下，区别在于知识数据库条目只有在公司或客户网络内发现漏洞时才会创建。此外，知识库中提供的信息将针对实际漏洞进行定制，而不是通用信息。

**问：** 团队成员提交的行动后回顾要求了不合理的培训数额。当他们因为预算限制或与未来项目不匹配而没有获得培训时，团队成员将大部分延迟归咎于缺乏适当的培训。这可以避免吗？

**答：** 培训资金总是需求巨大而供不应求。如果有一些培训资金，缓解某些投诉的最佳方法是允许工程师在可用培训资金的范围内优先考虑自己的培训。如果资金非常紧张，以至于每年只能一两个人参加，那么就将优先排序定为一个小组项目，让工程师们作为一个团队来选择谁去参加哪些课程——当然，任何参加课程的人都应该回来向团队其他成员教授他们学到的知识。互联网上还有许多免费培训。可以通过这些免费资源来补充培训。
