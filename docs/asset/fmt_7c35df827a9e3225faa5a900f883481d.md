
欧拉图适用于简单情况，因为它们直观地显示了超类型内部的子类型。然而，与 DAG 不同，它们无法处理复杂情况（例如许多重叠的子类型），并且使得向子类型附加细节变得不方便。出于后一个原因，使用 Barker 表示法时有时会从子类型中省略属性。欧拉图的另一个问题是在单个图上显示多分区（例如，尝试将 Patient 不仅划分为 MalePatient 和 FemalePatient，还划分为 InPatient 和 OutPatient）。

在 Barker 表示法中，如果原始子类型列表不穷尽，则会添加一个“Other”子类型使其穷尽，即使它不扮演特定角色。例如，在图 8.17 中，车辆是汽车或卡车或可能是其他东西，而汽车是轿车或旅行车或可能是其他东西。在 ORM 中，除非 OtherCar 或 OtherVehicle 扮演特定角色，否则无需为它们引入子类型。

![图 8.17 (a) Barker ER 和 (b) ORM 中的非穷尽、互斥子类型。](img/f08-17-9780443237904.jpg)

图 8.17 (a) Barker ER 和 (b) ORM 中的非穷尽、互斥子类型。

Barker 表示法用于子类型划分的一个主要问题是它不描述重叠子类型（例如 Employee 的子类型 Manager 和 FemaleEmployee）或多重继承（例如 FemaleManager 作为 FemaleEmployee 和 Manager 的子类型）。虽然可以通过一些低级技巧在单继承系统（例如 `Java`）中实现多重继承，但出于概念建模目的，多重继承应直接建模。作为关于子类型划分的最后一个比较点，Barker ER 缺乏 ORM 正式子类型定义和上下文相关标识方案的能力。

除了静态约束外，Barker ER 还包含一个动态的“可变性约束”，用于标记“*不可转移关系*”。该约束声明：一旦某实体类型的实例与一个对象扮演了某角色，它就永远不能再与另一个对象扮演该角色。这通过受约束角色上的空心菱形来指示。例如，图 8.18(a) 声明一个人的出生国是不可转移的。

![图 8.18 Barker 中声明了不可转移性，但 ORM 中没有。](img/f08-18-9780443237904.jpg)

图 8.18 Barker 中声明了不可转移性，但 ORM 中没有。

正如图 8.18(b) 所示，ORM 目前不支持此约束。为这种及其他动态约束在 ORM 中增加正式支持是一个活跃的研究领域。在实践中，不可转移约束的规范需要确保实现的模型仍然允许授权用户进行错误更正。例如，如果某澳大利亚人的出生国被误录为奥地利，应该能够将其更正为澳大利亚。我们在下一章检查 UML 中的可变性属性时将进一步讨论此问题。

好了，这相当全面地涵盖了用于 ER 的 Barker 表示法。正如我们所见，它在表达简单的强制性、唯一性、排除和频率约束；简单的子类型划分；以及不可转移关系方面做得很好。然而，如果特性被建模为属性而不是关系，则几乎无法为其指定这些约束。

与 ORM 不同，Barker 表示法不支持一元、*n* 元或对象化关联（嵌套）。此外，它缺乏对大多数高级 ORM 约束的支持（例如子集、多角色排除、环约束和连接约束）。它不包含用于在概念层面指定查询、其他约束和派生规则的正式文本语言。尽管如此，它优于许多其他 ER 表示法，且仍被广泛使用。如果您需要用 Barker ER 表示法指定模型，我们建议您先在 ORM 中建模，将其映射到 Barker 表示法，并记下无法用图形方式表达的任何规则。

我们现在不给您布置关于 Barker 表示法的练习，而是等到本章结束，届时我们将介绍正在使用的主要 ER 表示法以及一些从 ORM 映射到 ER 的技术。那时您可以决定想练习哪种表示法。

### 关系

关系通常仅限于二元关联，显示为连接实体类型的命名线。关系名称从左向右、从上向下阅读。与 Barker 表示法一样，半线或线端对应 ORM 中的角色。

可选性和基数设置通过标注线端来指示。要指示角色是`可选`的，在线的另一端放置一个圆圈“◯”，表示最小参与频率为 0。要指示角色是`强制`的，在线的另一端放置一个竖线“|”，表示最小参与频率为 1。在尝试了不同的“*多*”基数表示法后，Finkelstein 采用了 Gordon Everest 博士建议的直观鸭掌符号（crow’s foot）。

结合最小频率 0 或 1，竖线“|”常用于指示最大频率为 1。在这种安排下，组合“◯|”表示“*至多一个*”，组合“||”表示“*恰好一个*”。本节采用此约定。然而，存在不同的 IE 约定。例如，一些约定假设如果未使用鸭掌符号，则最大基数为 1，因此仅使用单个“|”表示“恰好一个”。Clive Finkelstein 使用组合“◯|”表示“可选但将变为强制”，这实际上是动态而非静态约束；这可以与鸭掌符号结合使用。一些约定允许鸭掌符号意味着最小（因此也是最大）频率为多。使用某个版本的 IE 时，请检查这些约定中的哪一个适用。

图 8.20 展示了一个简单的 IE 图及其等价的 ORM 图。使用 IE 时，当你从左向右阅读一个关联时，你要口头表达右侧端点的约束符号。在此，每位员工恰好占用一个（至少 1 个且至多 1 个）房间。IE 并不总是支持逆向谓词，但你可以自行提供它们以获得反方向的口语化表达，例如，“每个房间由零名或多名员工占用”。与 Barker 表示法一样，引入实体类型名称的复数形式来处理多的情况。

![图 8.20 IE 图 (a) 等价于 ORM 图 (b)。](img/f08-20-9780443237904.jpg)

## 8.4 IDEF1X

### IDEF 建模语言

20 世纪 70 年代，美国空军启动了一个集成计算机辅助制造（ICAM）项目。这标志着 `IDEF 建模语言` 家族的诞生。首字母缩写词 "IDEF" 最初代表 "ICAM DEFinition"（ICAM 定义），但现在代表 "Integration DEFinition"（集成定义），反映了其可用于在不同建模语言之间交换信息。ICAM 项目并未规定一种通用的建模语言，而是为不同任务定义了以下语言：

*   `IDEF0` 活动建模
*   `IDEF1` 概念数据建模
*   `IDEF2` 仿真建模

后来，又增加了其他语言，包括：

*   `IDEF1X` 逻辑数据建模
*   `IDEF3` 过程建模
*   `IDEF4` 面向对象软件设计
*   `IDEF5` 企业本体的知识工程
*   `IDEF1X[97]` 具有面向对象扩展的逻辑数据建模

名称 "`IDEF1X`" 代表 "IDEF1 eXtended"（IDEF1 扩展）。尽管基于概念 `IDEF1` 语言，`IDEF1X` 进行了更改以专注于逻辑数据建模。尽管有人对此表示遗憾，但 `IDEF1X` 的引入实际上宣告了 `IDEF1` 的终结。随着时间的推移，`IDEF3` 在很大程度上吸收了 `IDEF2` 和 `IDEF5`。如今，`IDEF1X` 是最流行的 `IDEF` 语言，受到许多 CASE 工具的支持，并广泛应用于美国政府部门，特别是国防领域。其他 `IDEF` 语言也在使用，尽管程度较低。

### IDEF1X 概述

`IDEF1X` 是一种混合语言，结合了一些概念概念（如实体、关系）与关系数据库构造（如外键）。它于 1993 年被美国国家标准与技术研究院（NIST，1993）接受为标准。一个名为 `IDEF1X[97]` 的后继版本（也称为 `IDEF[object]`）于 1998 年经 IEEE 批准，并于 2012 年进一步完善，成为目前仍在使用的版本（[`www.iso.org/standard/60614.html`](https://www.iso.org/standard/60614.html)）。该版本为 `IDEF1X` 增加了面向对象特性，以便于在面向对象数据库和编程语言中实现，同时保持与用于关系数据库实现的 `IDEF1X` 的兼容性。这种向后兼容性使 `IDEF1X[97]` 在美国政府部门的采用方面比 UML 具有一项优势。

然而，`IDEF1X[97]` 的面向对象扩展不如 UML 中的全面。虽然 UML 尚未广泛用于数据库设计，但它迄今为止是设计面向对象代码最广泛使用的语言，并受到许多 CASE 工具的支持。在撰写本文时，只有少数 CASE 工具支持 `IDEF1X[97]`。相比之下，`IDEF1X` 语言的原始（1993）版本继续被广泛用于数据库设计，并受到许多建模工具的支持。基于这些原因，本节其余部分我们将关注原始 `IDEF1X`。

### 建模构造

为了对事实建模，`IDEF1X` 使用了 ER 的三个主要构造：实体、属性和关系。遗憾的是，`IDEF1X` 标准使用术语 "entity"（实体）来表示 "entity type"（实体类型），而非 "entity instance"（实体实例）。更遗憾的是，一些从业者采用了这种误用。因此，你可能不得不比你想要的更频繁地使用 "instance"（实例）一词，仅仅是为了确保不被误解。每个实体类型具有一个或多个基于域的属性。域是一组具有相同数据类型的命名数据值集合。关系仅限于实体类型之间的二元关联。

`ER 视图` 可在分析早期使用，但与真正的 ER 相比表达能力非常弱。未为实体类型指定标识方案，且无需声明属性。如果指定了属性，则不为它们声明约束（如强制性）。

`IDEF1X` 中的 ER 视图基本上是 ER 模型的一个不完整草图。原则上，它可以细化为真正的 ER 模型。遗憾的是，`IDEF1X` 并未在概念层面进行细化，而是降至逻辑层面以添加额外细节。任何 ER 视图都必须解析为基于键的视图，并最终解析为完全属性视图以完成模型。基于键的视图和完全属性视图在许多方面类似于关系模型。一些支持 `IDEF1X` 的 CASE 工具不支持其 ER 视图，因此我们从这一点起忽略 ER 视图。

*在基于键和完全属性视图中，IDEF1X 实体类型基本上是关系表，而 "关系" 是外键到主键的引用*。回想一下，外键是一组一个或多个属性，其值（可能是复合的）必须作为某个主键的值出现。源或引用实体（类型）称为 `child`（子实体），目标或被引用实体（类型）称为 `parent`（父实体）。关系可以像概念关联或子类型链接一样被赋予正向和反向读法。然而，它们最终代表子集约束。实际事实全部存储在属性中，就像在关系模型中一样。

#### 实体类型

实体类型分为标识符独立和标识符依赖两类。当且仅当实体类型的标识符不依赖于其他实体类型时，它才是 `identifier independent`（标识符独立）的。换句话说，其标识方案不包含与另一个实体类型的概念关系。就键而言，这意味着 *当且仅当实体类型的主键没有任何组件是（完整的）外键时，该实体类型才是标识符独立的*；不过，其主键可能包含仅是外键一部分的属性。否则，该实体类型就是 `identifier dependent`（标识符依赖）的。术语 "identifier independent" 和 "identifier dependent" 常简称为 "independent"（独立）和 "dependent"（依赖）。这种 "independent" 的概念与 ORM 中独立对象类型的概念无关。

在 `IDEF1X` 中，独立实体（类型）描绘为硬矩形（直角），其名称写在上方，如 图 8.26(a) 所示。依赖实体类型描绘为软矩形（圆角），如 图 8.26(b) 所示。

#### 属性

实体类型的 `Attributes`（属性）列在其矩形内部。`Primary key`（主键）属性出现在顶部区间。这些提供实体类型的主要标识方案。`Alternate keys`（备选键）通过附加 "(AK*n*)" 来标记，其中 *n* > 0。这些提供备选标识方案。如果备选键是复合的，则其每个组件具有相同的 *n* 值。不同的备选键必须具有不同的 *n* 值。`Foreign keys`（外键）通过附加 "(FK)" 来指示。属性 `默认为强制性`。要显示属性为 `可选`，则附加 "(O)"。所有属性均为单值。
