
## 图 10.61 AccountType 的实例是否与 Account 的子类型相同？

在实践中，我们通常会移除或扩展 `AccountType` 上的值约束，以允许其他类型的账户（如 `LoanAccount`）。无论如何，我们都需要解决这个根本问题，用 ORM 术语表述为：*阴影点所表示的 `AccountType` 实例是否与子类型 `SavingsAccount` 相同？* 如果回答是，则我们在同一模型中出现了实例即类型的情况，使 `AccountType` 成为二阶类型。

在 UML 模式中，枚举类型的使用要求回答“否”，因为 UML 将枚举类型视为其实例为字面量的数据类型。然而，正如稍后讨论的，UML 允许我们使用 `AccountType` 的幂类型来重塑该情形，这要求回答“是”。

要使阴影点所表示的 `AccountType` 实例与子类型 `SavingsAccount` 相同，事实类型 `Account is of AccountType` 的语义至少应满足以下必要条件：

1.  “is of”谓词**意味着**“是……的成员”或“是……的实例”，即 ∈（集合成员资格）。
2.  **只有** `Account` 实例可以是 `AccountType` 实例的实例。

这些条件（组合起来我们称之为**同质集合成员资格**）源于**同一者的不可辨别性**（如果 `a = b`，则 `a` 和 `b` 具有相同的属性）。子类型 `SavingsAccount` 精确包含业务领域中所有可能的储蓄账户——没有其他事物可以是它的实例。如果阴影点所表示的 `AccountType` 实例**实际上是**子类型 `SavingsAccount`，那么只有账户才能与其建立实例关系。

如果我们允许类型 = 实例的解释，则必须使用高阶逻辑进行形式化，并应将同质集合成员资格的语义应用于此类分类关系。如果我们拒绝类型 = 实例的解释，则可以坚持使用一阶逻辑（至少用于形式化此类分类关系），并可选择将此类分类关系区分为特殊关系，为其提供相关的形式语义。

为标记这种区别，可为此类分类关联采用特殊的图形或文本修饰。例如，在 ORM 中，可在用于此目的的任何谓词的前向读法后附加冒号“:”（基于冒号有时但不总是用于引入类型的常见用法）。将此建议应用于 图 10.61(a) 中的模型会将“is of”替换为“is of:”。

为提供一种最小化的通用方法来处理此类分类关系，无论我们是否采用类型 = 实例的观点，都可使用冒号标记来区分任何此类关系，并赋予其**非对称**、**非传递**和**局部同质**关系的语义。形式为 `A R: B` 的事实类型是**局部同质**的，当且仅当 `B` 用作 `A` 的分类方案，但不用于任何其他类型（因此没有其他类型与 `B` 建立冒号关系）。对于 图 10.61 中的示例，这意味着只有 `Account` 实例可以是 `AccountType` 实例的实例。除非这样做会使读法别扭，否则为所有此类分类谓词使用相同的谓词读法（如“is of:”，甚至仅用“:”）很方便。读法的选择取决于语言。

非对称性和非传递性似乎是与此处相关的集合成员资格运算符（∈）的唯一属性。如果我们始终对分类关系使用相同的读法（如“is of:”），可将其视为全局应用的预定义谓词常量（该谓词的所有出现具有相同语义）。如果我们仅为这种同质情况保留冒号，则不得在分类方案（如 `Gender`）可应用于多个类型（如 `Person`、`Dog`）的情况下使用它。

请注意，类型所扮演的*任何*角色都可用作对其进行分类的基础。因此，将此类 is-of 关联标记为分类关系的主要原因，是为了强制执行此类关系的形式化属性。我们现在可以形式化此类分类关系。图 10.62(a) 描述了一般情况，假设始终使用相同的谓词读法 "is of:"（如果并非如此，则不失一般性，首先将每个读法替换为 "is of:"）。我们使用 "~" 表示否定（"并非……"），"&" 表示合取（"且"），"→" 表示实质蕴涵（"蕴含"）。与局部同质性不同，非对称性和非传递性属性可以独立于对象类型进行声明。

![图 10.62 分类关系 "is of:"。](img/f10-62-9780443237904.jpg)

图 10.62 分类关系 "is of:"。

对于*一阶逻辑解释*，所有类型均为一阶，因此其实例为个体，而非类型。我们使用小写字母（可能带下标）来遍历个体。对于*高阶逻辑解释*，我们使用大写字母（斜体）表示任意阶的类型变量。任何类型的阶（1, 2, 3, …）均为隐含的，因为它可以通过检查完整模式来推导。如果需要显式显示类型的阶，可使用前上标（例如，²B 表示 B 为二阶类型）。

后上标通常用于表示元数，后下标常用于区分同类型的变量。忽略跨越元层级的情况，将类型的阶指定为 1，加上以该类型为终点的、包含零个或多个分类关系的连续链中的关系数量。

使用 ∃¹ 表示"存在唯一"量词，我们现在可以形式化 图 10.62(b) 中分类关系的约束，该约束具有强制性和唯一性约束。一阶形式化将 `AccountType` 视为个体类型。

| *一阶形式化* |
| --- |
| ∀*xy* \[*x* is of: *y* → ~ (*y* is of: *x*)\] | \-- 非对称性 |
| ∀*xyz* \[*x* is of: *y* & *y* is of: *z* → ~ (*x* is of: *z*)\] | \-- 非传递性 |
| ∀*xy* \[AccountType *y* & *x* is of: y → Account *x*\] | \-- 局部同质性 |
| ∀*x* \[Account *x* → ∃¹*y* (AccountType *y* & *x* is of: *y*)\] | \-- 强制性和唯一性 |

高阶形式化将 `AccountType` 视为一阶类型的类型，因此它用 "`Y`" 和 "`Z`" 替换上述表述中的 "`y`" 和 "`z`"。或者，高阶形式化可将形式为 `α is of: β` 的任何表达式（其中 `β` 为类型变量）替换为 `βα`，因为它认为在这种情况下 `α is of: β` 蕴含 `α` 实例化了 `β` 谓词。

区分此类分类关系的一个动机，是为了便于转换到或来自包含所谓*幂类型* 的 UML 模型，UML 专门引入幂类型来建模此类分类方案。在 UML 1.4 中，幂类型使用 «powertype» 标注声明为刻板印象类，但该符号在 UML 2 中已废弃。在 UML 2 中，判断一个类是否为幂类型的唯一方法，是查看它是否在泛化约束中被引用。

图 10.63 显示了一个常用于说明幂类型必要性的示例的简化版本，采用 UML 2 符号。这种对树的分类方式在植物学上是错误的，但这与该问题无关。假设树可以简单地分类为橡树、榆树和柳树等物种。此处，`TreeSpecies` 是一个类，类似于 图 10.61 中的对象类型 `AccountType`。

如果 "powertype" 这个名称源自幂集的概念（集合 *A* 的幂集是 *A* 的所有子集的集合），那么该术语具有误导性，因为 `TreeSpecies` 幂类型排除了树的幂集中的许多实例（例如空集、所有树的集合以及许多其他树的集合）。因此，术语"*高阶类型*"比"幂类型"更为恰当。

无论如何，该图并未显式包含成员关联，如 `Tree is a member of TreeSpecies`（类似于 `Account is of AccountType`）。我们可以在此将此关联视为隐式的，但在实践中，通常需要该关联的显式版本，因为我们通常想知道任何给定树的物种，而有数百个树种时，为所有物种引入子类型在图表上过于繁琐。

在 UML 2 中，冒号 ":" 前置幂类型名称（例如 ": TreeSpecies"），以标注属于基于将超类型与幂类型相关联的关联所提供的分类方案的、所有可能泛化关系集合（称为 *GeneralizationSet*）中所显示的子类型-超类型连接集合。

如果子类型使用不同的箭头连接到超类型，则幂类型标注放置在穿过相关子类型连接的虚线旁边（参见 图 10.63(a)）。

如果使用公共箭头，则标注放置在该箭头旁边（参见 图 10.63(b)）。

如果一个类的名称用于泛化集约束，我们就可以知道它是一个幂类型。我们不能假设从一个类到幂类型的任何二元关联都具有这种性质。例如，除了 `Tree is a member of TreeSpecies`，我们可能还有 `Person named TreeSpecies` 等事实类型。

虽然角色名称 "account classifier" *非正式地* 暗示了这些额外的语义，但这没有任何形式效力（UML 规范中的其他示例使用不同的角色名称，如 "vehicle category" 等）。因此，*我们需要区分分类关联本身*，例如，通过在关系读法（如 "is of:"）和/或相关关联角色名称后附加冒号。

即使泛化关系用相关幂类型名称标注，也并不总是能正式保证所需的语义。例如，假设我们将员工分类为兼职或全职，并记录其首选雇佣状态（兼职或全职）（如果有）。图 10.65 中的 UML 模型在 `Employee` 和 `EmployeeType` 之间有两个关联，但没有正式的方法知道哪个关联被用作子类型成员资格的基础。

为了解决这个问题，我们可以要求在注解中包含角色名称，或者采用 ORM 提供正式子类型定义的做法。类型 `Employee`、`ParttimeEmployee` 和 `FulltimeEmployee` 是时间指示性的，因为它们的含义部分取决于其术语被表述/记录的时间。

UML 允许泛化注解包含泛化集的名称（当涉及幂类型时，推测是作为幂类型名称的前缀，但 UML 规范并未阐明这种可能性）。然而，此类名称被视为非正式注释。没有正式要求将这些名称关联回超类型的属性（属性或远端角色），就像那些使用判别器来指示子类型依据的数据库建模技术所做的那样。

如果我们要在模型中允许高阶类型，什么样的高阶逻辑是合适的？目前的 ORM 形式化仅使用一阶逻辑、基本算术和包推导。一旦我们采用高阶逻辑，就需要允许任意阶（而不仅仅是二阶），因为原则上，人们总可能引入新类型来对现有类型进行分类，无论这些类型是否为一阶。如果我们采用高阶逻辑的标准语义，其中量词可以遍历任何可想象的谓词，我们将失去一阶逻辑的一些有用性质（例如完备性和紧致性）。

此外，需要小心避免一些著名的悖论。`Russell’s paradox`（罗素悖论）考虑的是所有不包含自身的集合的集合：这个集合是否包含自身？如果是，则不是；如果不是，则是，从而导致矛盾。

`Grelling’s paradox`（格雷林悖论）处理自谓或自指性质（适用于自身的性质）。例如，我们可能会争辩说，非人的性质本身是非人的（因此是自谓性质），而人的性质本身不是人（因此是非自谓性质）。如果谓词可以实例化自身，那么用 `N` 和 `H` 分别表示非人和人的性质，我们可能将其形式化为 `NN` 和 `~HH`。但那么非自谓性质本身如何？它是自谓的还是非自谓的？如果它是，那么它不是；如果它不是，那么它是。无论哪种方式，我们都会得到矛盾。

为了避免此类悖论，伯特兰·罗素发展了一种类型论，其中类型按层级排序，只有当第二个类型位于层级的下一层时，说一个类型是另一个类型的实例才有意义。同样，高阶谓词仅适用于较低阶的谓词或对象。特别是，没有谓词可以适用于同阶的任何谓词。因此，没有谓词可以适用于自身。本质上，通过禁止谓词适用于自身，采用类型只能拥有较低层级实例的层级体系，从而避免了悖论。

虽然这似乎是采用高阶逻辑的合理方法，但其他一些版本的高阶逻辑并不采用这种方法。例如，知识交换格式（`KIF`）和 ISO Common Logic 标准都允许谓词实例化自身，因此允许诸如 `(R R)` 之类的表达式。

为了使高阶逻辑的实现更易处理，似乎最好采用非标准语义（类似于 Henkin 语义），以限制我们可以量化的谓词/函数范围，从而保留一阶逻辑的有用性质（如完备性）。在标准语义下，一元一阶谓词可以遍历个体域（对象：词汇或非词汇）的幂集。

对于我们希望断言实例为类型的分类类型（例如 `AccountType`），似乎我们超越一阶逻辑所需的唯一扩展，是允许对已声明分类类型的实例对象类型进行量化（无论这些实例是否已显式声明为子类型）。

作为一个单独的决定，如果我们希望允许在同一模型中跨越元层级（见后文），我们应该允许对模式中显式声明的任何阶的对象类型（原始或派生）进行量化。如果我们允许这一点，似乎没有令人信服的理由允许对多元谓词进行量化，因此这种放宽可被视为 Henkin 语义的一个受限情况。

我们现在概述一种保持一阶的分类方法。考虑 图 10.66 中的 ORM 模式，这是一个经典案例，高阶逻辑支持者会要求 `CarModel` 是一个二阶类型，其实例是 `Car` 的子类型（例如丰田卡罗拉 2022、道奇大黄蜂 2023、雪佛兰科尔维特 2025）。

![图 10.66 子类型（或任何类型）的总体通常随时间变化。](img/f10-66-9780443237904.jpg)

图 10.66 子类型（或任何类型）的总体通常随时间变化。

当我们想到 `Person` 和 `Car`（具体概念）的实例时，我们想到的是实际的人或车。当我们想到 `CarModel`（抽象概念）的实例时，我们通常想到的是一种本质上是汽车设计的抽象——一种可能由示意图表示的汽车*结构或规格*。

对于任何给定的业务域，我们将*类型*定义为*一组可能的实例，对于业务域的任何给定状态，该类型恰好有一个子集是该类型在该状态下的总体*。

在任何给定时间，类型的*总体*是该类型在该时间存在于业务域中的实例集合。需要时间维度来区分那些具有相同*随时间变化的外延*但在*某一时刻的外延*可能不同的类型（例如 `HumanPerson` 和 `HumanBaby`）。

根据外延性原则，集合由其外延定义。因此，除非我们诉诸非良基集合论，否则必须将集合视为固定的——它们不会随时间改变。对于任何给定的业务域，类型（例如 `Person` 或 `Country`）的当前总体可能随时间变化，但类型本身不会。

鉴于上述类型定义，不将汽车模型的实例视为该模式下可能汽车的集合（子类型）似乎是合理的。每个 `CarModel` 实例都与这种子类型（隐式或显式）存在 1:1 对应关系，但它不等同于子类型。我们认为这种区别总是可以做出的。如果是这样，我们可以将此类“分类类型”的实例视为非类型的普通个体，因此一阶逻辑就足够了。

假设我们如 图 10.66 所示显式引入一个名为 `DodgeHornet2023` 的汽车子类型。子类型定义提供了子类型与汽车模型实例之间的正式联系。使用 ORM 的标准参考模式语义，定义中的表达式 `CarModel ‘DodgeHornet2023’` 简写为 `CarModel **that** has CarModelName ‘DodgeHornet2023’`。

假设我们在生产任何该型号汽车之前，将存在性事实**存在一个** `CarModel` **具有** `CarModelName` ‘DodgeHornet2023’ 添加到信息库中。此时，汽车子类型 `DodgeHornet2023` 的总体是空集。假设稍后生产了 1000 辆该型号汽车。在那个较晚的时间，汽车子类型 `DodgeHornet2023` 的总体包含 1000 辆汽车。

在任何时候，子类型 `DodgeHornet2023` 都包含那 1000 辆车，以及该型号将来生产的所有其他车辆。因此，将 `CarModel` 的实例（被视为汽车实例所遵循的基本汽车结构或设计）视为与一组（可能的）汽车处于 1:1 对应关系，这完全没问题。

因此，将“分类类型”（如 `CarModel` 或 `AccountType`）的实例视为一个个体（例如结构模式），并认为它在本体论上不同于类型（即可能实例的集合），这是合理的。因此，对于这种情况，坚持使用一阶逻辑似乎已足够。

尽管“AccountType”中的“Type”一词可能暗示其实例本身就是类型，但这更多源于对该类型的一个不幸命名选择，而非任何根本直觉。

避免为分类使用高阶类型的第二种方法是*避免使用无信息量的分类方案*。“AccountType”一词没有信息量，因为它未提供对账户进行分类的任何依据。原则上，任何对象类型（如 `Account`）都可以通过许多不同方式进行分类，从而导致不同类型的银行账户。例如，我们可以定义 `AccountKind {Local, National, International}`、`AccountCategory {Taxable, Nontaxable}` 等。这些都是分类方案，我们可能希望在同一模型中使用它们，而“AccountType”和“AccountKind”这类名称完全无法告知我们，某个分类方案用于将账户归入账户类别的标准是什么。

有人可能会辩称，施加在分类方案上的值约束提供了这一标准，但这要求建模者根据他/她对这些值名称含义的非正式理解来推导标准，而这种理解无法被自动化系统正式获取。更重要的是，我们可能希望在不承诺一组固定实例的情况下引入分类方案。
