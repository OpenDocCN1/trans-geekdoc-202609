## 数字取证中的人为因素

数字取证中的人为因素也可能很重要；对涉案人员的访谈可以提供重要线索。这意味着在某些情况下，你不能仅仅是一名技术取证专家——相反，你必须利用你对技术和人类行为的双重知识来完成你的取证工作。

### 法律保全与电子取证

在许多情况下，当诉讼正在进行或预期将会发生时，取证工作便随之开始。法律顾问可以发送**法律保全通知**或诉讼保全通知，这是一份通知，告知组织必须保留在正常运营过程中可能会被销毁或修改的数据和记录。各类备份、纸质文档和电子文件都必须得到保存。

法律保全通知通常是电子取证或**电子发现**流程的首要环节之一。发现程序允许法律案件的各方从对方及其他涉案方获取证据，而电子发现就是电子化的发现程序。除了法律案件，发现程序也常用于公共记录、《信息自由法》请求和调查。使用框架来审视电子发现会有所帮助，**电子发现参考模型 (EDRM)** 就是一个有用的模型。EDRM 模型通过九个阶段来描述发现程序：

1. **信息治理**：事前进行，以评估存在哪些数据，并允许对需要提供的数据进行范围界定和控制。
2. **识别**：识别电子存储信息，以便了解拥有什么数据以及数据存储在何处。
3. **保全**：保全信息，确保其不被更改或销毁。
4. **收集**：收集信息，以便将其作为收集过程的一部分进行处理和管理。
5. **处理**：处理数据以移除不需要或无关的信息，并通过格式化或整理使其做好审查和分析的准备。
6. **审查**：审查数据以确保其仅包含应有的内容，且不包含不应共享的信息。
7. **分析**：分析信息以识别关键要素，如主题、术语、个人或组织。
8. **生成**：生成数据，向第三方或法律程序相关方提供信息。
9. **呈现**：呈现数据，既用于法庭作证，也用于与专家或相关方进行进一步分析。

这一过程中最重要且同时最具挑战性的要求之一，可能是电子信息的保全，特别是当法律保全或发现程序涵盖的数据频繁被组织内的用户使用或修改时。电子发现和法律保全支持工具可以提供帮助，它们具备为处于诉讼保全状态的用户或群组捕获数据的能力。这些工具通常带有桌面、移动设备和服务器代理，可收集数据、跟踪变更，并在整个法律保全时间范围内记录数据的适当处理情况。在频繁处于法律保全状态的组织中，CEO、总裁等常成为诉讼目标的高管，长期处于近乎持续的法律保全和发现状态并不罕见。

云运营使电子发现变得更加复杂。云供应商提供服务，但不会允许你在其云服务中植入侵入式的法律保全和发现代理。这意味着在采用云服务时，你必须解决如何应对这些服务的法律保全问题。像 **Google Vault** 这样的工具同时提供电子邮件归档和发现支持，帮助组织满足其发现要求。

### 实施数字取证

取证数据是使用取证工具获取的，如磁盘和内存成像工具、镜像分析和时间线工具、可显示磁盘上数据内容和结构详细信息的低级编辑器，以及其他专用工具。Security+ 考试重点关注获取的关键方面，包括易失性顺序，以及如何以及为何从常见位置和设备获取数据的详细信息。

#### 获取取证数据

当取证从业者计划获取数据时，他们要审查的第一件事之一是**易失性顺序**。易失性顺序记录了因系统操作或正常进程而最可能丢失的数据。图 15.1 展示了一个典型的易失性顺序图表。请注意，CPU 寄存器和缓存状态等频繁变化的信息排在首位，因此易失性最高；随后是路由信息、进程和内核统计信息。随着列表往下，每个项目迅速消失的可能性逐渐降低，备份数据最不可能发生变化。遵循易失性顺序进行获取——除非有令人信服且紧迫的理由偏离该列表——将使取证分析师最大程度地完整捕获数据。重要的是要记住，当系统关机或重启时，哪些项目会消失。一般来说，在该列表中，临时文件和交换空间位于第 4 位会发生这种情况。能否恢复完整的临时文件和交换空间中的数据，取决于系统是如何关闭的，以及之后是否成功重启。

![图 15.1 易失性顺序](img/c15f001.png)

**图 15.1** 易失性顺序

Security+ 考试要求你熟悉针对以下取证目标获取信息的基本概念：

* **CPU 缓存和寄存器**极少作为常规取证工作的一部分被直接捕获。尽管可以使用专用硬件或软件捕获其中一些信息，但大多数调查不需要这种级别的细节。随着处理过程的进行，CPU 缓存和寄存器在不断变化，因此具有极高的易失性。
* **临时性数据**，如进程表、内核统计信息、系统的 `ARP 缓存` 等，可以通过内存和磁盘获取相结合的方式捕获，但必须记住，捕获只能反映获取那一刻的时间点状态。如果事件发生在过去，这些数据可能无法反映事件发生时系统的状态。
* **随机存取存储器 (RAM)** 的内容对调查和事件响应都非常有帮助。内存中可能包含加密密钥、来自应用程序的临时性数据，以及可能未写入磁盘但对调查有用的信息。
* **交换空间和页面文件** 信息是用于补充物理内存的磁盘空间。与从 RAM 捕获信息非常相似，捕获交换空间和页面文件可以深入了解运行中的进程。由于系统会主动使用它，特别是在内存较小的机器上，它的变化速度也比磁盘上的许多文件要快。
* **磁盘上的文件和数据** 变化较慢，但却是许多调查的主要焦点。重要的是要捕获整个磁盘，而不仅仅是复制文件，以便查看仍驻留在磁盘上的已删除文件和其他残留痕迹。
* **操作系统** 本身可能包含有用信息。**Windows 注册表** 是分析的常见目标，因为 Windows 中的许多活动都会修改或更新注册表。
* **设备**，如智能手机或平板电脑，也可能包含作为取证目标的数据。
* **固件** 是较少成为取证目标的工件，但如果固件作为事件的一部分被修改，或者固件可能包含取证相关数据，则知道如何从设备复制固件可能是必要的。固件通常可通过硬件接口（如串行电缆或直接 USB 连接）或通过内存取证技术访问。

虚拟机快照是取证从业人员必须处理的日益常见的工件。

网络流量和日志可以提供关于发送或接收了什么、何时发送或接收、通过什么端口和协议以及其他有用细节的详细信息或线索。

设备、打印输出、介质以及与调查相关的其他物品等工件都可以提供额外的有用取证数据。

无论获得或处理哪种类型的取证数据，如果取证案件可能导致法律诉讼，保持*证据保管链*文档非常重要。事实上，一些组织无论案件如何都应用这些规则，以确保在必要时案件能得到支持。证据保管链表单是简单的签署和文档记录表单，如图 15.2 所示。每次访问、传输或以其他方式处理驱动器、设备或工件时，都会按照表单所示进行记录。

![图 15.2 证据保管链表单示例](img/c15f002.png)

**图 15.2 证据保管链表单示例**

法庭案件中的证据通常具有法律可采性，前提是它被用来证明案件事实且不违反法律。要确定证据是否可采，会应用诸如证据的相关性和可靠性、证据是否合法获取、证据是否真实等标准。证据必须是可获得的最佳证据，且流程和程序应经得起法庭质疑。

除了这些要求外，数字取证的*可采性*还要求数据完整且未被篡改，并能证明在取证过程之前和期间一直保持未被篡改。取证分析师必须能够证明他们具备适当的技能、使用了适当的工具和技术，并以一种可靠且可通过可审计线索进行测试的方式记录了他们的行动。因此，如有必要，第三方必须能够重复他们的工作和发现。

##### 云取证

尽管现场取证构成了传统取证工作的大部分，但向云服务的广泛迁移给取证分析师带来了新的挑战。除了需要支持取证发现需求的工具和能力外，组织越来越多地确保他们已与云提供商合作。除了组织必须考虑的关于从云提供商保留和生成数据能力的高层关注点外，Security+ 考试专门包含三个概念：

* **审计权条款**，它是云服务与组织之间合同的一部分。审计权条款提供直接审计云提供商的能力，或同意使用第三方审计机构的协议。许多云提供商使用标准合同，可能不同意为小型组织提供审计权条款。在这种情况下，他们可能会提供定期更新的第三方审计声明的访问权限，这可能符合您组织的需求。如果您有特定的审计要求，应尽可能在合同中解决它们，并决定如果无法进行审计，审计能力是否是贵组织决定采用云提供商服务的决定性因素。
* **法规**和**管辖权**顾虑也是采用云服务的重要因素。法规要求可能因云服务提供商的运营地和总部所在地而异。涵盖您的数据、服务或基础设施的法律可能不是您所在地区、区域或国家的法律。此外，管辖权顾虑可能超出涵盖整个组织的法律范围。云提供商通常在世界各地设有站点，数据复制和其他服务要素意味着您的数据或服务可能存储或使用在同样广泛的位置。当地司法管辖区可能声称有权通过搜查令或其他法律手段访问该数据。对此有重大顾虑的组织通常通过合同条款、提供商提供的仅在特定区域或国家托管数据或系统的服务选择，以及技术控制（如自行处理加密密钥以确保知晓数据是否被访问）来解决此问题。
* **数据泄露通知法律**，与其他法规要素一样，因国家而异，在美国各州之间也明显不同。合同通常涵盖通知客户前可经过的最长时间，确保您拥有满足需求的适当泄露通知条款可能很重要。一些供应商延迟数天、数周甚至数月通知，可能导致不知情的客户面临重大问题。

这些考虑因素意味着从云提供商获取取证数据的可能性不大。虽然您可能能够从日志或您在基础设施即服务提供商环境中维护的系统和基础设施中恢复取证数据，但服务本身的取证数据很少移交给客户。因此，使用云服务的组织必须制定计划来处理潜在事件和调查，而不依赖直接取证技术。

##### 采集工具

获取驱动器或设备的取证副本需要一种能在比特级创建设备完整副本的工具。Security+ 考试涉及多种可获取磁盘映像的工具，包括 `dd`、`FTK Imager` 和 `WinHex`。

在 Linux 中，`dd` 是一个命令行实用程序，允许您为取证或其他目的创建映像。`dd` 命令行接受输入，如输入位置（`if`）、输出位置（`of`）以及描述您想要执行操作的标志，例如尽管出错仍创建完整副本。

要将挂载为 `/dev/sda` 的驱动器复制到名为 `example.img` 的文件，可以执行如下命令：

```
dd if=/dev/sda of=example.img conv=noerror,sync
```

其他设置通常有助于获得更好的性能，例如设置适合驱动器的块大小。如果您想将 `dd` 用于取证目的，值得投入额外时间学习如何使用针对您用于取证工作站的设备和接口的块大小设置来调整其性能。

`FTK Imager` 是一款用于创建取证映像的免费工具。它支持原始（`dd`）格式，以及 `SMART`（ASR Data 的 SMART 取证工具格式）、`E01`（EnCase）和 `AFF`（高级取证格式）等取证工具常用的格式。了解您需要为分析工具生成什么格式，以及是否可能需要多种格式的副本，在设计取证流程时非常重要。

`FTK Imager` 支持物理驱动器、逻辑驱动器、映像文件、文件夹以及多 CD/DVD 卷。在大多数情况下，取证采集可能来自物理或逻辑驱动器。图 15.3 显示了使用 `FTK Imager` 从物理驱动器完成映像创建的过程。注意匹配且经过验证的 MD5 和 SHA1 哈希值，以及确认没有坏块（这将表明潜在的数据丢失或驱动器问题）。

##### 获取网络取证数据

并非所有取证数据都能在磁盘或系统上找到。网络取证的作用日益重要，无论是针对传统的有线和无线网络、蜂窝网络还是其他网络。由于网络流量是短暂的，为取证调查捕获流量通常需要直接努力提前捕获和记录数据。如果网络流量没有被主动记录，防火墙日志、`IDS` 和 `IPS` 日志、邮件服务器日志、认证日志以及其他次要来源等取证工件可能会提供关于设备何时在网络上、发送了什么流量以及将流量发送到何处的信息。

当取证检查员确实处理网络流量信息时，他们经常会使用像 `Wireshark` 这样的数据包分析器来查看捕获的网络流量。对数据包、流量流和元数据的深入分析可以提供关于网络行为和内容的详细信息。

用于网络安全设备的相同网络抽头、SPAN 端口和端口镜像也可用于网络取证，允许将网络流量的副本发送到收集服务器。虽然这很有用，但也可能导致海量数据。捕获所有或选定的网络流量是大多数组织为特定目的而保留的过程，而非常规做法。相反，大多数组织最终依赖日志、元数据、流量流信息和其他常见收集的网络信息来支持取证活动。

##### 从其他来源获取取证信息

除了您迄今为止了解的取证获取类型外，还有两种特定类型的获取越来越常见。从虚拟机获取需要额外的规划。与服务器、台式机或笔记本电脑不同，虚拟机通常运行在共享环境中，移除该系统会导致多个其他服务和服务中断。同时，为整个底层虚拟化主机创建镜像将包含比正在进行的取证调查所需或适当的更多的数据和系统。幸运的是，虚拟机快照将提供取证分析师所需的信息，并且可以被捕获，然后使用可用工具导入到取证工具中。

**容器** 的使用显著增长，并为取证检查员带来了新的挑战。由于容器被设计为短暂的，且其资源通常是共享的，因此它们产生的取证工件比虚拟机或物理机少。事实上，虽然容器可以被暂停，但捕获它们并将其恢复到取证合规的状态可能具有挑战性。容器取证需要额外的规划，取证和事件响应工具正变得可用以支持这些需求。

##### 验证取证数据完整性

一旦您获取了取证数据，就需要在开始取证分析之前确保您拥有一个完整、准确的副本。同时，记录数据的**来源**，并确保数据和过程不可抵赖（**不可抵赖性**），也很重要。

验证取证副本与原始副本匹配的最常用方法是创建副本的**哈希值**和原始驱动器的哈希值，然后进行比较。如果哈希值匹配，则取证副本与原始副本完全相同。虽然 `MD5` 和 `SHA1` 在攻击者可能介入的场景中已基本淘汰，但它们对于快速哈希取证镜像仍然有用。提供两个驱动器的 `MD5` 或 `SHA1` 哈希值，以及所用过程和程序的文档，是建立副本来源的常见部分。哈希值和其他相关信息将作为案件的保管链和取证文档的一部分进行存储。

手动创建镜像文件或驱动器的哈希值只需将哈希工具指向它即可。以下是在 Linux 系统上挂载为 `/dev/sdb` 的驱动器和当前目录下的镜像文件的哈希示例。为输出选择的文件名是 `drive1.hash`，但可以是您选择的任何文件名。

```
md5sum /dev/sdb > drive1.hash
```

或

```
md5sum image_file.img > drive1.hash
```

驱动器或镜像的哈希值也可以用作**校验和**，以确保其未被更改。只需重新哈希驱动器或镜像并比较生成的值，如果发生更改，哈希值将会不同，从而告知您是否发生了更改。
