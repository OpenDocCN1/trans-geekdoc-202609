
一个简单的例子可能是，在网络中发现了多个低风险漏洞。尽管漏洞扫描器可能会将这些情况中的每一个归类为“低风险”，但如果没有网络其他区域安全态势的背景，就无法真正理解这些低风险漏洞可能产生的累积效应。事实证明，累积效应可能超过其简单叠加效应的总和。管理员和普通用户的弱密码都是问题，但管理员账户被攻破的潜在影响对组织来说可能大得多。没有任何单一工具能够自动提供这种深度的洞察，因此，了解工具的局限性与了解它们的能力同样重要。

## 执行扫描

现代扫描器无法发现它们未感知或不理解的弱点。虽然它们只能识别自己已知的弱点，但最流行的漏洞扫描器已经积累了巨大的漏洞库。我们将讨论市场上的三种流行的漏洞扫描器：Tenable Network Security 的`Nessus`、Greenbone Network 的`OpenVAS`以及`Nikto Web Scanner`。这些工具可以从外部人员的视角也可以从合法用户的视角扫描你的网络。在后一种情况下，扫描器将执行所谓的*认证扫描*（authenticated scan）。进行认证扫描有两种主要方法。第一种是在端点上安装本地代理，以与漏洞扫描服务器同步，并在扫描过程中对端点进行分析。第二种方法是直接向扫描器提供管理员凭据，扫描器将在过程中根据需要调用这些凭据。在评估期间同时使用认证和未认证扫描是良好的做法，因为使用其中一种方法可能会发现另一种方法无法发现的漏洞。

### Nessus

`Nessus`是一种流行且强大的扫描器，它于 20 世纪 90 年代后期作为一种开源免费工具诞生，此后成为进行漏洞扫描的首选。凭借超过 80,000 个插件，`Nessus`允许用户根据自定义策略在多个网络上调度并执行扫描。你可能记得在我们讨论端口扫描工具时提到过`Nessus`包含基本的端口扫描功能。然而，它的真正威力在于其用于漏洞识别、误配置检测、默认密码使用和合规性判定的众多功能。标准安装包含`Nessus`服务器，它将协调漏洞扫描、生成报告并促进漏洞管理功能。它可以位于与`Nessus`Web 客户端相同的同一台机器上，也可以位于网络其他地方。客户端设计为从 Web 界面运行，允许管理员使用任何支持 HTML5 的浏览器来操作扫描设置。[图 6-1] 显示了在网络中几个目标上使用的`Nessus`架构。位于`Nessus`服务器上的是在对目标进行评估时所使用的各种插件。通过注册机制，Tenable 经常更新这些插件和服务器软件，通常是每天一次。

### 生成报告

报告生成是事件响应过程的重要部分，对于漏洞管理尤为关键。所有漏洞扫描器都执行某种形式的报告，但并非所有的都带有自定义选项。Nessus 以常见格式提供报告，如 PDF、HTML 和 CSV。此外，还可以使用 Nessus 自己的格式。

作为管理员，考虑你的工具能够生成哪些报告以及你可能如何自动化报告过程是非常。将相关信息及时传递给正确的人是成功利用漏洞扫描的关键。

#### 自动化与手动分配

创建报告模板允许你根据漏洞扫描结果快速准备自定义报告，然后将其转发给必要的联系人。例如，你可以让所有 Web 服务器漏洞自动收集并发送给 Web 服务器管理员。同样，你可以将数据存储违规情况发送给溢出团队以便采取行动。除非只有一个管理员，否则自动化报告交付过程可能有意义，以减轻主管理员管理每个报告的负担。服务管理员可以通过获取与其角色最相关的报告来提高效率。

当扫描器发现漏洞时，它会提供尽可能的信息。图 6-11 显示了 OpenVAS 对发现的漏洞提供的详细界面。此界面显示了漏洞的摘要、关注资源的位置、漏洞的影响、发现方式以及任何解决方案或变通方法。

![Images](img/00049.jpeg)

**图 6-11** OpenVAS 漏洞详情截图

网络漏洞的修复应在发现后尽快进行，但不能由于草率行事而导致情况恶化。有效的修复需要对漏洞进行持续检查，并结合深思熟虑的处理来解决问题，以保持组织资源的机密性和可用性。验证修复的最简单机制是比较连续的漏洞扫描结果，以确定漏洞已通过软件补丁或升级得到解决。许多供应商提供了管理整个补丁过程的解决方案，这种独立的实践方法被称为“补丁管理”。如果需要使用补偿控制，您可以通过在报告中添加备注来向漏洞管理系统提供反馈，或者可以忽略告警。这有助于在您无法应用更新的情况下，记录您为解决问题所采取的行动。

### 优先级排序

系统管理员很容易被海量的扫描结果搞得不可应交。这时，对漏洞及相关的修复步骤进行优先级排序就会有所帮助。理想情况下，关于如何确定响应优先级的讨论应既包括技术人员的能力，也包括组织的整体业务目标。将关键利益相关者纳入讨论（或者至少让他们了解你们的方法论），将确保确保未来的策略变更能够获得支持。

### 关键性

对于如何响应扫描结果的决策是由经济因素驱动的；我们用于修复问题的时间、资金或人员都是有限的，因此在做出响应时必须审慎。为了帮助这一点，`Nessus`和`OpenVAS`在结果结果页面上都提供了发现漏洞严重程度的快速视觉参考，如图 6-12 所示。对结果进行颜色标记并允许排序将有助于决策者快速关注最关键的问题，并最大限度地利用有限的资源。

### 实施难度

由于实施解决方案的困难，您在修复过程中可能会遇到挑战。由于技术原因或成本导致实施严重延迟的情况下，您仍应通过某些补偿控制来实现安全需求的目标。让非技术团队成员加入将有助于在实施主要解决方案的过程中，采纳所开发的任何替代方案。

### 通信/变更控制

你可以看到，在获得漏洞扫描结果后，管理所采取的行动投入了巨大的精力。虽然从表面上看实施每项建议似乎是个好主意，但我们无法一次性完成。如果没有系统的方法来管理所有必要的安全变更，我们就有可能让自己陷入比开始时更糟的境地。建立正式通信和变更管理程序的目的是确保第一次就做出正确的变更，保持服务可用，并在整个变更过程中高效地使用资源。

### 变更顾问委员会

许多组织使用变更顾问委员会（`CAB`）来批准公司政策的主要变更，并协助变更管理对变更进行监控和评估。`CAB`的成员通常包括可能受拟议变更产生不利影响的实体。这些包括客户、经理、技术人员和公司领导层。在召开会议时，委员会成员确保所有拟议的变更都能解决问题，并且从业务和技术角度来看都是合理的。

### 沙箱/测试

2016 年 9 月，维护广泛使用的 SSL 和 TLS 协议开源实现的`OpenSSL 项目`在其定期更新中，发布了一个被他们认为是常规的安全补丁。其中包含的公告表明，在某些情况下，该不安全代码会导致拒绝服务，且其严重性评级为“低”。然而，发现该补丁了另一个另一个严重的漏洞，允许攻击者执行任意代码。现在想象一下，在没有对部分设备或在沙箱进行测试的情况下，直接在大型网络中部署第一个补丁。这不仅会极大地增加你组织的攻击面，还会导致停机，因为你必须多次修补。这说明了在部署到整个企业之前，在安全环境中测试补丁的重要性。

### 修复障碍

即使是经过利益相关者支持的可靠修复计划，有时也会面临障碍。许多挑战源于对 IT 系统有严重依赖的流程，或未能充分应对变化的技术格局的过时策略在本节中，我们将涵盖修复的一些常见障碍以及我们可能如何避免它们。

### 谅解备录

谅解备录（`MOU`）概述了所有相关方的职责和预期。与渗透测试一样，漏洞扫描应该有明确定义的范围，以及正式的介入规则（`ROE`），这些规则首先规定了在评估期间以及发现漏洞时可以做什么。例如，在业务用量高峰期间对生产系统进行扫描是不合适的。还可能出现一种情况，如果没有正式的`MOU`，将留下太多的模糊性。不难想象，在你的网络上发现漏洞可能会对你未控制的相邻网络产生影响。此外，相邻网络的配置错误可能会直接影响你组织的服务。无论何种情况，涵盖此类条件的`MOU`都将以让所有参与者满意的方式继续进行。

### 服务水平协议

许多 IT 服务提供商根据与其服务接收方之间现有的服务水平协议（`SLA`）来提供服务。`SLA`是一种合同，可以存在公司内部（例如业务部门与 IT 员工之间），也可以存在组织与外部供应商之间。`SLA`的存在是为了概述服务提供商的角色和责任，包括他们可以执行的服务限制。除非修复明确包含在`SLA`中，否则不能强制他们执行这些步骤。

#### 组织治理

组织用于指导和控制运营的流程和规则体系被称为`企业治理`（corporate governance）。企业治理旨在公司利益相关者的优先考虑事项之间达成合理的平衡。在某些情况下，治理可能会中断补救措施的应用，因为这些行动可能会对其他业务领域产生负面影响。这凸显了与公司领导层沟通你的行动的重要性，以便他们可以将补救措施的影响与其他问题一并考虑，从而做出决策。良好的沟通有利于为了公司的最大利益做出及时决策。

## 业务流程中断

应用补丁或采取其他补救措施何时都不合适。高效的业务和工业流程，如准时制生产（just-in-time manufacturing），允许企业缩短流程时间并提高整体效率。这些系统的基础是生产 IT 系统，这些系统本身已经针对业务进行了优化。然而，一个主要的缺点是，某些系统由于其优化状态，可能更容易受到干扰。这种对整体流程的不可预测性或不稳定性的恐惧，通常足以让公司领导层推迟对生产系统的重大更改，或者完全避免更改。

## 功能退化

虽然网络管理中没有等同于“希波拉底誓言”的规定，但我们必须始终尝试对生产系统“不伤害”。有时，建议的治疗方案（例如由于关键漏洞而对关键系统进行隔离）可能被领导层认为是不可接受的。你和你的领导层愿意承担多少风险是你们组织的决定，但你应该尽可能获得有关漏洞状态的最准确信息。如果你发现某个重要的补救措施在测试环境中破坏了关键应用程序，那么替代方案并不是避免打补丁。相反，你必须设计其他缓解控制来解决漏洞，直到开发出合适的补丁为止。

## 持续扫描与持续监控

如果可行，你应该安排每天进行自动漏洞扫描。根据你运营的网络类型和安全策略，你可能会选择更频繁地执行操作，并始终使用最新版本的扫描工具。你应该特别关注关键漏洞，并目标是在 48 小时内修复它们。考虑到维护软件、库和报告对管理员来说可能是枯燥的，一些公司开始提供基于 Web 的扫描解决方案。例如，`Qualys`和`Tenable`都提供了云端 Web 应用程序扫描器，可以从任何云服务提供商运行。这些公司承诺在各种规模的网络中提高可扩展性和扫描速度，并根据订阅层级提供多项相关服务。
