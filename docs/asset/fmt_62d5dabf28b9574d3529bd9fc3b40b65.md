
映射过程步骤 0 的最终细化（步骤 0.7）处理了对象化谓词未被唯一性约束跨越的情况。某些 ORM 版本禁止这种情况，因为它违反了元素性。正如第 10.5 节所讨论的，我们也倾向于避免此类情况。

然而，如果允许这种情况，则在执行过程的分组部分之前需要一些预处理。

在嵌套 1:1 的情况下，应在分组时决定偏向其中一个角色。例如，假设图 11.49 中的模式用于模拟一夫一妻制社会中的当前婚姻。该模式违反了元素性。它可以分裂为两个事实类型：一个关于婚姻，一个关于婚姻年份。如果 `Person` 不扮演其他函数角色，我们可能将其映射到图 11.49 中所示的任一表方案。对于这种 1:1 情况，必须做出选择（例如，通过选择其中一个唯一性约束作为主键）。

![图 11.49 对象化 1:1 关联的两种可能映射。](img/f11-49-9780443237904.jpg)

图 11.49 对象化 1:1 关联的两种可能映射。

如果对象化谓词中的只有一个角色是函数性的，它会自动被选为主键。例如，在一夫多妻制社会中，一个男人最多只能娶一个女人，但反之不然，`husband` 列将被选为主键（而 `wife` 将不再是键）。

尽管有步骤 0.7 的规定，没有跨越唯一性约束的对象化关联通常应通过无嵌套的重建模来避免。回顾图 10.52，它展示了针对讨论中的婚姻案例的两种无嵌套重建模方法。图 10.54 和 10.55 说明了如何在不使用对象化的情况下重建模其他一些案例。

一旦在关系映射中确定了列和约束，您可能希望考虑更改表内的*列顺序*。虽然关系模型将列顺序视为无关紧要，但在实践中，列顺序会影响可读性和性能。CASE 工具会为您选择一种排序，但您可以覆盖它。

通常，最好将主键列放在前面，并将组合标识的对象类型的组成部分或具有强语义亲和力的列分组在一起。在这种情况下，通常首选自顶向下的顺序（例如 `buildingNr`、`roomNr` 而不是 `roomNr`、`buildingNr`）。对于此类组合情况，将取值较少的属性放在前面在某些情况下有助于加快连接速度。类似的观点也适用于组合索引。如果将可选列放在最后，某些系统的性能也会更好。

## 11.5 小结

### 概念模式与关系映射

概念模式通常通过将其映射到逻辑模式（例如关系模式）、对其进行细化，然后生成内部和外部模式（包括访问权限）来实现。随后可对数据库和模式执行更新和查询。

*关系（数据库）模式*是一组表定义（存储的基本表或派生视图）、约束和派生规则。*表模式*是一组命名的*属性*（列），其取值来自*域*。每个列，或由最小唯一性约束跨越的列集，都是一个*候选键*。键以下划线标识。每个表行由其*主键*标识（若存在其他键则双下划线）。*实体完整性*规则要求主键不能有空值。可选列允许空值，并用方括号括起。例如：`Employee( empNr, empName, address, gender, [phone] )`。

强制角色映射到非可选列，且子集约束从包含该对象类型事实的任何其他表运行而来。*参照完整性约束*是从外键到某个主键的子集约束。表之间的子集约束显示为虚线箭头。也使用其他约束符号。

关系映射过程（`Rmap`）使用两个基本思想将每个事实类型分组到单个表中：具有复合唯一性约束的每个事实类型（例如 *m:n* 关联或三元关联）映射到单独的表；附加到同一对象类型上的功能角色的事实类型分组到同一个表中，以该对象类型的标识符为键。

*基本 Rmap 过程*可总结如下。将子类型吸收到其顶层超类型中。在脑海中擦除所有显式首选标识方案，将复合标识的对象类型视为“黑盒”。将每个具有复合 UC 的事实类型映射到单独的表。将附加到同一对象类型上的功能事实角色的事实类型分组到同一个表中，以该对象类型的标识符为键。将 1:1 情况映射到单个表，通常倾向于减少空值。将每个没有功能事实角色的独立对象类型映射到单独的表。将每个“黑盒列”解包为其组成属性。映射所有其他约束和派生规则。功能角色上的子类型约束映射到限定可选列，而非功能角色上的子类型约束映射到限定子集约束。

如果某对象类型的总体实例包含在一个表中，这称为该对象类型的*总表*。更多详情请参见*总表过程*。

*Rmap 步骤 0 过程*中的高级映射方面可总结如下。转换相反的一元事实类型，然后根据其开放/封闭世界语义映射一元事实类型。在脑海中擦除所有引用（首选标识）谓词。将复合标识的对象类型视为“黑盒”。指示任何吸收覆盖（例如分离或分区）以用于子类型。识别任何必须存储的派生事实类型。指示对称 1:1 情况的映射选择。考虑通过使用人工标识符或连接标识符或强制默认值来替换任何析取引用方案。在需要时，指示任何没有跨越唯一性约束的对象化关联的映射选择。

### 章节注释

许多数据库教科书讨论了将 ER 模式映射到关系模式（例如，Batini 等人, 1992）以及将 UML 类图映射到关系模式（例如，Blaha 和 Premerlani, 1998）。扩展旧 ONF 算法以开发 Rmap 原始版本的映射扩展是由 Peter Ritson 和 Terry Halpin 共同开发的。本章讨论的 Rmap 版本包含若干修订，以适应 ORM 2 中的新特性，例如对象化的进一步选项以及开放/封闭世界语义。

## 12.1 SQL：关系代数

前几章讨论了如何设计概念模式并将其映射到关系模式。本章讨论如何在关系数据库管理系统（`DBMS`）中实现关系模式，然后用数据填充其表。为了从生成的数据库中检索信息，我们需要发出查询。在实践中，最流行的查询语言是 `SQL`（通俗但不准确地称为“结构化查询语言”）和 `QBE`（示例查询）。这两种语言至少部分基于一种称为*关系代数*的形式化查询语言，本节将讨论该语言。首先学习这种代数可以阐明基本查询操作，而不会被商业查询语言的特定语法所干扰。

掌握了关系代数后，我们可以定义“关系数据库系统”一词的真正含义。随后几节将深入介绍 SQL，从基础开始，逐步深入到中级和高级概念。虽然我们的重点是 SQL 标准，但也会包含一些关于 SQL 商业方言的额外细节。我们从关系代数开始。

在数据的关系模型中，所有事实都存储在*表*（或*关系*）中。通过应用关系代数运算，可以从现有表形成新表。这些运算产生的表可通过关系赋值进行命名和存储。Codd 定义的原始关系代数包含八个*关系运算符*：四个基于传统集合运算（*并*、*交*、*差*和*笛卡尔积*），四个特殊运算（*选择*、*投影*、*连接*和*除*）。关系代数现在包含一个*重命名*运算符，用于为查询结果的表模式定义别名。这九个关系运算符中的每一个都是作用于表的成表运算符。例如，两个表的并集本身就是一个表。

### 关系代数

关系代数包含六个*比较运算符*（`=`、`<>`、`<`、`>`、`<=`、`>=`）。这些是作用于项的命题形成运算符。例如，`x <> 0` 断言 `x` 不等于零。它还包含三个*逻辑运算符*（`and`、`or`、`not`）。这些是作用于命题的命题形成运算符（例如，`x > 0 and x < 8`）。因为该代数不包含算术运算符（例如 `+`）或函数（例如 `count`），所以它的表达能力不如 SQL。这里忽略了将这些及其他运算符纳入代数的建议扩展。

存在许多不同的符号表示法来表达关系代数。我们的表示法与一种常见的学术表示法的比较将在后面给出。为简化讨论，我们将经常使用非正式术语代替严格的关系术语（例如，用“表”和“行”代替“关系”和“元组”）。

#### 并、交与差

当且仅当两个表具有相同数量的列，且它们对应的列基于同一个域（列名可以不同）时，这两个表是*并兼容*的。将表视为行的集合，传统的集合运算——并、交和差——可以在并兼容的表之间定义。

请考虑 图 12.1 中的概念模式。为简单起见，假设在这个小的论域（UoD）中，人员由其名字标识。我们记录人们吃的食物以及他们喜欢的食物的事实。关系模式包含所示的两个表。这些表的数据集合可以适当地重叠，甚至可以是不相交的。因此，关系模式中没有表间约束——这种情况相当罕见。

表 `A` 和 `B` 的**交**是 `A` 和 `B` 共有的行的集合。我们将其写为 `A ∩ B` 或 `A intersect B`。例如，要列出人们既吃又喜欢的食物的事实，我们可以将其指定为两个基本表的交，即 `Eats ∩ Likes`（参见 图 12.3）。

我们定义表之间的**差**运算如下。`A − B` 是属于 `A` 但不属于 `B` 的行的集合。我们也可以将其写为 `A minus B` 或 `A except B`。例如，表达式 `Eats − Likes` 返回关于吃自己不喜欢的食物的人的详细信息（参见 图 12.4(a)）。

正如在普通集合论中一样，并运算是可交换的（即操作数的顺序无关紧要）。因此，给定任意表 `A` 和 `B`，`A ∪ B = B ∪ A` 为真。同样，交运算也是可交换的，即 `A ∩ B = B ∩ A`。然而，差运算不可交换，因此 `A − B` 可能不等于 `B − A`。例如，`Likes − Eats` 返回关于喜欢某种食物但不吃它的人的事实（参见 图 12.4(b)）。将其与前一个结果进行比较。

#### 笛卡尔积（无限制连接）

在数学中，集合 `A` 和 `B` 的**笛卡尔积**定义为所有有序对 `(x, y)` 的集合，使得 `x` 属于 `A` 且 `y` 属于 `B`。例如，如果 `A = {1,2}` 且 `B = {3, 4, 5}`，则 `A` 和 `B` 的笛卡尔积为 `{(1,3), (1, 4), (1, 5), (2,3), (2, 4), (2, 5)}`。我们将此积写为 `A ⨉ B`（读作 `A cross B`）。此定义也适用于表，尽管行的有序对 `(x, y)` 被视为积表的单行，并继承相应的列名。

因此，如果 `A` 和 `B` 是表，`A ⨉ B` 是通过将 *A 的每一行与 B 的每一行配对* 形成的。这里的“配对”意味着“前置到”。表达式 `A ⨉ B` 也可以写为 `A times B`。笛卡尔积也称为“交叉连接”或“无限制连接”。

因为 `A ⨉ B` 将 `A` 的每一行与 `B` 的所有行配对，如果 `A` 有 `n` 行而 `B` 有 `m` 行，则表 `A ⨉ B` 有 `n × m` 行。因此，*A ⨉ B 中的行数是 A 和 B 行数的乘积*。因为配对的行被连接成单行，*A ⨉ B 中的列数是 A 和 B 列数的总和*。

让我们看一个简单的例子。在 图 12.5 中，`A` 是一个 `3 × 2` 表（即 3 行 × 2 列），`B` 是一个 `2 × 1` 表。因此，`A ⨉ B` 有六行（`3 × 2`），三列（`2 + 1`）。包含列名 `a1, a2, b1` 的表头行不计入此计算。在该示例中，行之间用虚线分隔以提高可读性。请注意，对于任意表 `A` 和 `B`，笛卡尔积 `A ⨉ B` 都存在；`A` 和 `B` 无需并兼容。

![图 12.5 A × B 将 A 的每一行与 B 的每一行配对。](img/f12-05-9780443237904.jpg)

图 12.5 `A × B` 将 `A` 的每一行与 `B` 的每一行配对。

如果我们将笛卡尔积定义为视为有序值序列的元组，则 `⨉` 运算符不可交换（即 `A ⨉ B` 不一定等于 `B ⨉ A`）。这是数学中的常规处理方式。然而，在关系数据库中，每一列都有唯一的名称，因此元组可以被视为（无序的）属性-值对集合（行中的每个值都与其列名关联）。从这个意义上说，列被称为“按名称排序”。在这种元组视图下，`⨉` 运算符是可交换的。

为了阐明这一点，请计算示例中 *B* ⨉ *A*（参见图 12.5）。尽管生成的表按 *b1, a1, a2* 的顺序显示列，且值也按此顺序排列，但信息与 *A* ⨉ *B* 相同，因为每个值都可以链接到其列名。例如，*B* × *A* 的第一行可表示为 {(b1, 7), (a1, 1), (a2, 2)}，这等同于 {(a1, 1), (a2, 2), (b1, 7)}，即表示 *A* ⨉ *B* 的第一行。一旦列被唯一命名，其物理顺序就没有语义意义。

与标准集合论一样，并、交和笛卡尔积运算具有*结合性*。例如，*A* ∪ (*B* ∪ *C*) = (*A* ∪ *B*) ∪ *C*。因为不会产生歧义，在这种情况下可以省略括号。例如，表达式“*A* ∪ *B* ∪ *C*”是允许的。在目前考虑的四种表运算中，差运算是唯一不具有结合性的；即 *A* − (*B* − *C*) 可能不等于 (*A* − *B*) − *C*。作为练习，请使用文氏图验证这些断言。
