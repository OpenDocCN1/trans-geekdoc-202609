
* `GPU` 在某些地区不可用。

* 每个 `DeployedModel` 资源或 `BatchPredictionJob` 只能使用一种类型的 `GPU`，并且根据您使用的机器类型，可添加的 `GPU` 数量存在限制。

以上考量因素针对的是云端预测。在许多用例中，训练好的模型需要部署在边缘设备上。让我们在下文探讨这些用例。

### Edge TPU

物联网（`IoT`）的重要组成部分是边缘设备。这些设备收集实时数据、做出决策、采取行动，并与其他设备或云端通信。由于此类设备带宽有限，有时可能完全离线运行，因此在设备本身上运行推理（称为*边缘推理*）的需求日益增长。

`Google` 设计的 `Edge TPU` 协处理器可加速这些边缘设备上的 `ML` 推理。单个 `Edge TPU` 仅消耗 2 瓦功率，即可执行每秒 4 万亿次运算（4 `TOPS`）。

`Edge TPU` 为您的原型和生产设备提供多种外形规格，包括单板计算机、系统级模块、 `Edge TPU` 本身及所有可用产品。这些产品以 `Coral.ai` 品牌销售。

### 部署到 Android 或 iOS 设备

`ML Kit`（`https://developers.google.com/ml-kit`）将 `Google` 的机器学习专业知识以功能强大且易于使用的软件包形式带给移动开发者。您可以利用针对设备端运行进行优化的解决方案，使您的 `iOS` 和 `Android` 应用更具吸引力、个性化和实用性。

您可以在 `Google Cloud` 上训练 `ML` 模型，使用 `AutoML` 或自定义模型，并将模型部署到您的 `Android` 或 `iOS` 应用中。预测在设备端进行，以实现低响应时间、节省带宽，并支持离线模式下的预测。

### 总结

在本章中，您了解了 `Google Cloud` 上可用的不同预训练模型。您还了解了 `AutoML` 模型及其在不同场景下的适用性。在本章的主要部分，您了解了可用于训练模型的不同硬件选项，以及训练工作负载和预测工作负载的区别。`Google Cloud` 以 `GPU` 和 `TPU` 的形式为您提供了各种硬件加速器。最后，超越云端，您了解了部署到边缘设备的理念。

### 设计可靠、可扩展且高可用的 ML 解决方案

要设计高度可靠、可扩展且可用的 ML 解决方案，你需要考虑如何自动化和编排 AI/ML 流水线的各个步骤。

你的 ML 流水线包含以下步骤：

1. 数据收集

2. 数据转换

3. 模型训练

4. 模型调优

5. 模型部署

6. 模型监控

此外，这是一个迭代过程，因为你可能需要根据评估指标（准确率、置信度得分等）重新训练模型。

你需要一个可扩展的存储解决方案来管理和存储数据——例如 `Google Cloud Storage`。然后你需要一个可扩展的基础设施来运行转换作业，例如在 `Google Cloud Dataflow` 上运行 `PySpark` 转换作业。数据转换完成后，你需要可扩展的算力来训练模型。要创建无法在笔记本电脑中容纳的大型模型，你需要分布式训练。

对于自定义模型训练（`TensorFlow`、`Scikit`、`PyTorch` 或其他框架），你可以使用 `Vertex AI Training`，因为你无需担心为训练启动基础设施，也无需管理该基础设施以在训练结束时停止。如果你不使用 `TensorFlow`、`Scikit` 或 `PyTorch` 进行自定义训练，你也可以选择使用 `Vertex AI AutoML` 和 `Vertex AI APIs`。训练结束后，你可能想通过运行 100 个此类训练作业（这些作业包含来自搜索空间的各种超参数组合）来调整模型的各种超参数。这就是你可以使用 `Vertex AI Hyperparameter Tuning` 以可扩展的方式自动运行多个训练作业的地方。你还希望以托管、可扩展且可靠的方式跟踪这些变量和多次训练结果。这就是 `Vertex AI Experiments` 可以帮助跟踪训练运行的参数和结果的地方。既然你能跟踪实验，这将有助于更快地选择模型。

最后，一旦你选出了准确率最高的最佳训练作业，你就必须考虑在生产环境中部署此模型。你还需要担心生产模型的扩缩容；`Vertex AI Prediction` 可以帮助你以全托管方式在生产环境中扩缩容预测端点。

模型部署到生产环境后，你需要考虑监控托管模型以检查是否存在任何模型漂移。这就是 `Vertex AI Model Monitoring` 可以提供帮助的地方。你还需要考虑如何复现从数据收集到模型部署的完整流水线，因为 ML 是一个迭代过程。`Vertex AI Pipelines` 可以在此提供帮助。
