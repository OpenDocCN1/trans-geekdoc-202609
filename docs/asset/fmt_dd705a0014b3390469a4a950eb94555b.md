
该 bug 存在于 Visual Studio 2015 中包含的 GitHub 扩展中，标记为私有的代码被标记为公开。该代码包含一个私有的亚马逊访问密钥：“令我沮丧的是，我发现该仓库被创建为公共仓库。不仅我的源代码泄露了，包含在配置文件中的 Alexa 网络信息服务的亚马逊访问密钥也暴露在外” [[22]](#Ch009_459-508_B9780443187346000088.xhtml#bb0115)。

机器人很快蜂拥而至：“一旦暴露在外，就为时已晚。机器人扫描 GitHub 仓库，它们只需 2 或 3 分钟就能捕捉到此类信息。” 犯罪分子随后利用 Carlo 的账户生成了许多亚马逊云实例，并用它们挖掘加密货币比特币。

Carlo 总结了关键问题：

“为何我的数据会如此迅速地被泄露？

*   比特币矿工持续扫描 GitHub 源代码以寻找亚马逊访问密钥。
*   他们随后利用这些密钥生成大量（亚马逊云）EC2 实例来挖掘比特币。
*   他们大赚特赚，而被利用者却背负巨额账单。

可以采取哪些措施来预防和缓解此类情况？

*   在实际使用新版本控制 GUI 之前务必先进行测试。可能存在会暴露你数据的 bug。
*   加密配置文件中的敏感信息。
*   将访问密钥移至单独的配置文件，并将其从 Git 部署中排除。
*   亚马逊可默认实施每日最大预算限制。
*   理想情况下，亚马逊不应允许无限额支出” [[22]](#Ch009_459-508_B9780443187346000088.xhtml#bb0115)。

## 应用程序编程接口 (API) 安全性

应用程序编程接口 (API) 允许应用程序与另一个应用程序、操作系统、数据库、网络等进行通信。例如，Google Maps API 允许应用程序集成第三方内容，例如叠加在 Google 地图上的餐厅信息。

### API 利用的真实案例

API 利用的真实案例包括 Facebook API 遭到黑客攻击，安全研究员 Reza Moaiandin 利用该漏洞收集了数千个 Facebook 个人资料：

> “发现该漏洞的软件工程师 Reza Moaiandin 利用了一个鲜为人知的隐私设置，该设置允许任何人通过在社交网络中输入电话号码来查找 Facebook 用户。
>
> 默认情况下，这个‘谁可以找到我？’的设置被设为‘所有人/公开’——意味着任何人都可以通过手机号码找到其他用户。即使该用户选择不在其公开个人资料中显示手机号码，这仍然是默认设置。
>
> Moaiandin 使用一个简单的算法，每秒生成数万个手机号码，然后将这些号码发送给 Facebook 的应用程序编程接口（API），这是一个允许开发者构建与社交网络关联的应用程序的工具。几分钟内，Facebook 就向他返回了大量用户的个人资料。
>
> Moaiandin 接收到的所有信息都是公开可用的，但能够大规模地将个人资料与手机号码关联起来，使得该系统面临被滥用的风险” [[23]](#Ch009_459-508_B9780443187346000088.xhtml#bb0120)。

## 软件变更与配置管理

软件变更与配置管理为软件在开发、维护和最终退役过程中管理变更提供了一个框架。一些组织将其视为一门学科；考试将配置管理和变更管理视为独立的（但相关的）学科。

就软件开发安全领域而言，配置管理跟踪特定软件的变更。例如：跟踪对 `Content Management System (CMS)`（内容管理系统）的变更，包括软件内的特定设置。变更管理范围更广，跟踪整个软件开发项目的变更。在这两种情况下，配置管理和变更管理旨在确保变更有序进行，不损害（并理想地改善）信息安全。我们在第 8 章，领域 7：安全运营中讨论了变更管理。

NIST 特别出版物 800-128：面向信息系统的安全聚焦配置管理指南（可在 `https://csrc.nist.gov/publications/detail/sp/800-128/final` 获取）描述了以下配置管理术语：

> “配置管理计划（CM 计划）是对管理产品和系统配置时适用的角色、职责、政策和程序的全面描述。CM 计划的基本组成部分包括：
>
> *   配置控制委员会（CCB）——建立并授权一组合格人员负责在产品和系统的开发和运行生命周期中控制和批准变更的过程；也可称为变更控制委员会；
> *   配置项标识——选择和命名需要纳入配置管理的配置项的方法；
> *   配置变更控制——管理配置项基线配置更新的过程；以及
> *   配置监控——评估或测试对既定基线配置的合规程度以及报告纳入配置管理的项目配置状态的机制” [[25]](#Ch009_459-508_B9780443187346000088.xhtml#bb0130)。

## 数据库

*数据库*是相关数据的结构化集合。数据库允许查询（搜索）、插入（更新）、删除和许多其他功能。数据库由*数据库管理系统*（DBMS）管理，它控制对数据库的所有访问并强制执行数据库安全。数据库由*数据库管理员*（DBA）管理。数据库可以使用数据库*查询语言*进行搜索，例如*结构化查询语言*（SQL）。典型的数据库安全问题包括存储数据的机密性和完整性。当复制的数据库被更新时，完整性是首要关注点。

其他数据库机密性问题包括*推理*和*聚合*攻击，详见第 4 章，领域 3：安全架构与工程。聚合是一种数学攻击，攻击者聚合较低密级的细节以确定较高密级的信息。推理是一种类似的攻击，但攻击者必须逻辑推导缺失的细节：与聚合不同，推理需要解开一个谜题。

### 数据库类型

正式的数据库类型包括*关系型*（二维）、*层次型*和*面向对象型*。最简单的数据库形式是*平面文件*：一个包含多行数据的文本文件，每行采用标准格式。主机文件（在 UNIX 系统上位于 `/etc/hosts`，在许多版本的 Microsoft Windows 上位于 `c:\windows\system32\drivers\etc\hosts`）是平面文件的一个例子：每个条目（行）至少包含一个 IP 地址和一个主机名。

#### 关系型数据库

最常见的现代数据库是*关系型数据库*，它包含相关（因此称为“关系型”）数据的二维*表*。表也称为关系。表有行和列：行是数据库记录，称为*元组*；列称为*属性*。数据库中单个单元格（行和列的交叉点）称为值。关系型数据库要求表中每个元组都有一个称为*主键*的唯一值。表 9.1 显示了一个关系型数据库员工表，按主键（SSN，即社会安全号码）排序。

**表 9.1 关系型数据库员工表。**

| SSN | 姓名 | 职称 |
| --- | --- | --- |
| 133-73-1337 | J.F. Sebastian | 设计师 |
| 343-53-4334 | Eldon Tyrell | 博士 |
| 425-22-8422 | Gaff | 侦探 |
| 737-54-2268 | Rick Deckard | 侦探 |
| 990-69-4771 | Hannibal Chew | 工程师 |

表 9.1 的属性包括 SSN、姓名和职称。元组包括每一行：133-73-1337、343-53-4334 等。“Gaff”是一个值（单元格）的例子。*候选键*是表中具有唯一值的任何属性（列）：表 9.1 中的候选键包括 SSN 和姓名；选择 SSN 作为主键是因为它真正唯一（两名员工可能同名，但不会有相同的 SSN）。主键可以在关系型数据库中连接两个表。

##### 外键

*外键*是相关数据库表中的一个键，它与父数据库表中的主键匹配。请注意，外键是本地表的主键：当引用父表时，它被称为外键。表 9.2 是人力资源数据库表，列出了员工的休假时间（天）和病假时间（天）；它有一个 SSN 外键。人力资源数据库表可以通过将人力资源表的外键连接到员工表的主键，与父（员工）数据库表连接。

**表 9.2 人力资源数据库表。**

| SSN | 休假时间 | 病假时间 |
| --- | --- | --- |
| 133-73-1337 | 15 天 | 20 天 |
| 343-53-4334 | 60 天 | 90 天 |
| 425-22-8422 | 10 天 | 15 天 |
| 737-54-2268 | 3 天 | 1 天 |
| 990-69-4771 | 15 天 | 5 天 |

#### 引用完整性、语义完整性和实体完整性

数据库必须确保表中数据的完整性：这称为数据完整性，将在下文的“数据库完整性”一节中讨论。除了数据本身的正确性之外，还有三个具体的完整性问题必须解决：引用完整性、语义完整性和实体完整性。这些与 DBMS（数据库管理系统）的逻辑操作紧密相关。

*引用完整性* 是指辅助表中的每个外键都与父表中的一个主键匹配：如果不满足此条件，则引用完整性已被破坏。*语义完整性* 是指每个属性（列）的值与属性数据类型一致。*实体完整性* 是指每个元组都有一个非空的唯一主键。前面看到的 HR 数据库表（见表 9.2）具有引用完整性、语义完整性和实体完整性。另一方面，表 9.3 存在多个问题：一个元组违反了引用完整性，一个元组违反了语义完整性，最后两个元组违反了实体完整性。

**表 9.3 缺乏完整性的数据库表。**

| SSN | 休假时间 | 病假时间 |
| --- | --- | --- |
| 467-51-9732 | 7 天 | 14 天 |
| 737-54-2268 | 3 天 | Nexus 6 |
| 133-73-1337 | 16 天 | 22 天 |
| 133-73-1337 | 15 天 | 20 天 |

带有外键 `467-51-9732` 的元组在员工数据库表中没有匹配的条目。这破坏了引用完整性：无法将此条目链接到姓名或职位。单元格“Nexus 6”违反了语义完整性：病假时间属性要求天数值，而“Nexus 6”不是有效的病假天数。最后，最后两个元组具有相同的主键（对此表为主键；对父员工表为外键）；这破坏了实体完整性。

#### 数据库规范化

数据库*规范化*旨在使数据库表中的数据在逻辑上简洁、有序且一致。规范化可移除冗余数据，并提高数据库的完整性和可用性。规范化有三条规则，称为范式（更多信息请见 [`www.informit.com/articles/article.aspx?p=30646`](http://www.informit.com/articles/article.aspx?p=30646)）：

*   **第一范式 (1NF)：** 将数据划分到多个表中。
*   **第二范式 (2NF)：** 将部分依赖于主键的数据移至另一个表中。HR 数据库（表 9.2）即为 2NF 的示例。
*   **第三范式 (3NF)：** 移除不依赖于主键的数据 [[26]](#Ch009_459-508_B9780443187346000088.xhtml#bb0135)。

#### 数据库视图

数据库表可被查询；查询的结果称为*数据库视图*。视图可用于提供*受限用户界面*：例如，非管理层员工只能通过数据库视图查看其个人记录。表 9.4 显示了通过字符串“Detective”查询员工表“Title”属性所得的数据库视图。虽然 HR 部门员工可能有权查看整个员工表，但此视图可授权给侦探队长，例如。

**表 9.4 员工表数据库视图“Detective”。**

| SSN | Name | Title |
| --- | --- | --- |
| 425-22-8422 | Gaff | Detective |
| 737-54-2268 | Rick Deckard | Detective |

#### 数据字典

*数据字典*包含数据库表的描述。这称为*元数据*：关于数据的数据。数据字典包含数据库视图信息、授权数据库管理员的信息、包括姓名和权限在内的用户账户、审计信息等。数据字典的关键组成部分是*数据库模式*：它描述数据库表的属性和值。表 9.5 显示了一个非常简单的数据字典，描述了本章前面见到的两个表：employees 和 HR。

**表 9.5 简单的数据库模式。**

| Table | Attribute | Type | Format |
| --- | --- | --- | --- |
| Employee | SSN | Digits | `###-##-####` |
| Employee | Name | String | `<30 characters>` |
| Employee | Title | String | `<30 characters>` |
| HR | SSN | Digits | `###-##-####` |
| HR | Sick Time | Digits | `### days` |
| HR | Vacation Time | Digits | `### days` |

#### 数据库查询语言

数据库查询语言允许创建数据库表、对这些表进行读/写访问以及许多其他功能。数据库查询语言至少有两个命令子集：*数据定义语言* (DDL) 和*数据操纵语言* (DML)。DDL 用于创建、修改和删除表。DML 用于查询和更新存储在表中的数据。

最流行的关系型数据库查询语言是 SQL（结构化查询语言），由 IBM 于 1974 年创建。存在多种类型的 SQL，包括 MySQL、PostgreSQL、PL/SQL（过程语言/SQL，Oracle 使用）、T-SQL 和 ANSI SQL（Microsoft SQL 使用）等。

常用 SQL 命令包括：

*   **CREATE：** 创建表
*   **SELECT：** 选择记录
*   **DELETE：** 删除记录（或整个表）
*   **INSERT：** 插入记录
*   **UPDATE：** 更改记录

表是通过 `CREATE` 命令创建的，该命令使用数据定义语言来描述正在创建的表的格式。数据操纵语言命令的一个示例是 `SELECT`，用于从表中搜索和选择数据。以下 `SELECT` 命令可用于创建表 9.4 中所示的数据库视图：

```
SELECT * FROM Employees WHERE Title = "Detective"
```

这意味着：显示 Title 为“Detective”的任何（“*”）记录。

#### 层次数据库

层次数据库形成一棵树：全局域名服务 (DNS) 服务器构成一棵全局树。根名称服务器位于树基部的“根区”；单个 DNS 条目构成叶子节点。`www.syngress.com` 指向 `syngress.com` DNS 数据库，它是顶级域 (TLD) dot com (.com) 的一部分，而后者又是全局 DNS（根区）的一部分。从根节点出发，你可以沿另一分支向下，到达顶级域 dot gov (.gov)，再到 `nist.gov`（美国国家标准与技术研究院）域，最后到 `www.nist.gov`。

层次数据库的一种特殊形式是*网络模型*（指人员网络，而非数据网络）：这允许层次数据库的分支拥有两个父节点（两条回溯到根节点的连接）。设想一个组织的组织架构图存储在一个形成树状的数据库中，CEO 位于层次结构的根部。在该公司中，物理安保人员同时向设施部门（针对设施问题）和 IT 部门（针对数据中心物理安保）汇报。网络模型允许物理安保人员在层次数据库中拥有“两个上级”：通过 IT 经理和设施经理汇报。

#### 面向对象数据库

数据库传统上仅包含（被动）数据，而面向对象数据库则在面向对象框架中将数据与函数（代码）结合在一起。面向对象编程（OOP）用于操作由对象数据库管理系统（ODBMS）管理的对象（及其数据）。

#### 数据库完整性

除了前面讨论的关系数据库完整性问题（语义完整性、参照完整性和实体完整性）外，数据库还必须确保数据完整性：即数据库表中条目的完整性。这将完整性视为一个更普遍的问题：减轻数据的未授权修改。数据库内数据完整性面临的主要挑战是对数据的并发修改尝试。数据库服务器通常运行多个线程（轻量级进程），每个线程都能修改数据。如果两个线程尝试修改同一条记录会发生什么？

DBMS 可能会尝试*提交*更新：使挂起的更改永久生效。如果提交不成功，DBMS 可以*回滚*（也称为中止）并从*保存点*（数据库表的干净快照）恢复。

*数据库日志*是所有数据库事务的日志。如果数据库损坏，可以将数据库还原为备份副本，然后从日志中“重放”后续事务，恢复数据库完整性。

#### 数据库复制与影子

数据库可以是高可用（HA）的，通过包含表的多个副本的多个服务器进行复制。完整性是复制数据库的主要关注点：如果一条记录在一个表中被更新，它必须同时在所有表中更新。此外，如果两个进程尝试在两个不同的服务器上同时更新同一个元组会发生什么？它们不能都成功；这将违反元组的完整性。

*数据库复制*镜像一个活动数据库，允许客户端同时对多个复制数据库进行读写。复制数据库带来了额外的完整性挑战。可以使用两阶段（或多阶段）提交来保证完整性：在提交前，DBMS 请求投票。如果每台服务器上的 DBMS 都同意提交，则更改永久生效。如果有任何 DBMS 不同意，投票失败，更改不被提交（不永久生效）。

*影子数据库*类似于复制数据库，但有一个关键区别：影子数据库镜像主数据库的所有更改，但客户端不访问影子数据库。与复制数据库不同，影子数据库是单向的（数据从主库流向影子库）：它作为主数据库的实时数据备份。

#### 数据仓库与数据挖掘

顾名思义，*数据仓库*是大量数据的集合。现代数据仓库可能存储数 TB（1000 GB）甚至数 PB（1000 TB）的数据。这需要大规模可扩展的存储解决方案。存储必须是高性能的，并允许对数据进行分析和搜索。
