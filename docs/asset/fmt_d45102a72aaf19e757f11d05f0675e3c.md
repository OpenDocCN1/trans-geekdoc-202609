
我们的主要重点是对呈现为 RDF 图的社交媒体数据进行分类和保护。然而，我们推理控制器的初始实现是针对溯源数据的，溯源数据存在于包括社交媒体数据在内的众多领域中。我们的推理控制器可针对社交媒体数据进行调整，因为我们的社交网络表示为 RDF 图。语义 Web 通过使用形式语义扩展了 RDF 图模型，使其具备推理能力。正是这种推理服务被我们用来支持推理控制器的推理策略。此外，我们还展示了如何执行新的查询修改技术，以在溯源图上强制执行安全策略，这可以扩展到 `第 19 章` 和 `第 20 章` 中讨论的社交媒体图。

语义推理器使我们能够从一组公理中推断逻辑后果。它提供了一组更丰富的机制，使我们能够从使用 OWL 词汇编码的溯源图中得出推论。我们可以通过本体语言指定推理规则。推理器通常使用一阶谓词逻辑进行推理。推理通过前向链接和后向链接进行。（图 18.4）。

### 18.5.1 示例

#### 推理规则

*推理规则*可用于从前提推导出结论以构建论证。重要的是要指出，如果一组规则是完备的，则可用于推导任何有效的结论。如果一组规则不会推导出无效的结论，则该规则集是可靠的。某些规则可能是冗余的，因此一个可靠且完备的规则集在得出结论时不必包含每一条规则。如前所述，当结论不是用户被授权查看的内容时，我们就存在安全泄露和推理问题。

规则可以在前向链接或后向链接中调用：

*   **前向链接模式**：我们得到一组陈述，并使用规则推导出新的陈述。原则上，反复应用前向链接将找到可以从知识库中的某个初始事实集通过推理规则推导出的所有事实。

**示例 18.4：**

考虑以下两条规则：

1. `(med:HeartSurgery opm:wasControlledBy ?X) → (X rdf:type med:Surgeon)`

2. `(med:Results_n_1 opm:Used med:Doc_n_6) ^ (med:Results_n_1 opm:wasControlledBy ?X) → (X rdf:type med:Surgeon)`

如果我们的知识库包含以下三元组：

```
<med:HeartSurgery_n_1> <opm:Used> <med:Doc_n_5>
<med:Doc_n_6> <opm:WasGeneratedBy> <med:HeartSurgery_n_1>
<med:Doc_n_6> <opm:wasDerivedFrom> <med:Doc_n_5>
<med:Results_n_1> <opm:Used> <med:Doc_n_6>
<med:Results_n_1> <opm:WasControlledBy> <med:Surgeon_n_1>
<med:HeartSurgery_n_1> <opm:WasControlledBy> <med:Surgeon_n_1>
```

我们可以通过使用上述知识库中的最后一个三元组得出 `?X` 是一名外科医生的结论。三元组 `(med:Surgeon_n_1 rdf:type med:Surgeon)` 随后将被添加到知识库中。请注意，执行规则 2 也会将此三元组添加到知识库中。

在**后向链接**中，我们得到某个表达式，并确定必须满足的所有前件，以使给定的后件表达式为真。

**示例 18.5：**

考虑以下规则：

1. `(med:HeartSurgery opm:wasControlledBy ?X) → (X rdf:type med:Surgeon)`

2. `(med:Results_n_1 opm:Used med:Doc_n_6) ∧ (med:Results_n_1 opm:wasControlledBy ?X) → (X rdf:type med:Surgeon)`

如果我们想满足规则 1，推理器会得出结论 `med:HeartSurgery opm:wasControlledBy ?X`。给定陈述：

```
<med:HeartSurgery_n_1> <opm:WasControlledBy> <med:Surgeon_n_1>
```

该推导将导致推理器产生 `med:Surgeon_n_1` 作为问题 `(X rdf:type med:Surgeon)` 的答案。

### 18.5.2 推理问题的方法

可以采用不同的方法来构建推理控制器。例如，我们可以使用最先进的机器学习技术来构建一个学习器，该学习器能自动学习识别复杂模式，并基于某些显式数据做出智能决策。我们还可以构建一个推理控制器，它使用配备推理器的语义 Web 技术，对知识库中的数据执行推理。在本节中，我们将阐述基于语义 Web 技术使用的推理控制器的一些方法。

**聚合问题**是推理问题的一个特例——数据元素的集合是机密的，但单个元素是非密的。

`A ⊔ B ⊔ C ⊑ Secret`

我们可以通过检查溯源 KB 或发布 KB 中是否存在任何敏感概念来强制执行此规则。

`A ⊓ B ⊓ C ⊑ Secret`

`≥ 10 R.(A ⊓ B ⊓ C)`

如果我们知道至少有十个人拥有某个属性，则对 KB 进行分类。

**关联问题**：属性 A 和 B 组合在一起是机密的，但单独来看它们是非密的。

**示例 18.3：** `A and B and C → Secret`。

*我们可以将其编码为一条 SWRL 规则，然后检查溯源 KB 或发布 KB 中是否有任何机密内容*。

```
(med:Doc_n_6 opm:wasDerivedFrom med:Doc_n_5)
  ∧ (med:Doc_n_6 opm:WasGeneratedBy med:HeartSurgery_n_1)
  ∧ (med:HeartSurgery_n_1 opm:WasControlledBy med:Surgeon_n_1)
  →
  (med:HeartSurgery_n_1 med:Classification Secret)
```

如果我们认为手术操作是敏感的，可以将其分类为机密。类似地，由该操作生成的患者记录的结果版本也应被视为机密。

```
(med:Doc_n_6 opm:wasDerivedFrom med:Doc_n_5)
  ∧ (med:Doc_n_6 opm:WasGeneratedBy med:HeartSurgery_n_1)
  ∧ (med:HeartSurgery_n_1 opm:WasControlledBy med:Surgeon_n_1)
  →
  (med:Doc_n_6 med:Classification Secret)
```

**示例 18.4：** *同时属于这三个类的事物是私有的*：

`A ⊓ B ⊓ C ⊑ Secret`

**示例 18.5：** *如果在所有三个类中最多只有一个个体，则对 KB 进行分类*：

`≤ 1 R.(A ⊓ B ⊓ C)`

#### 18.5.2.1 域限制

我们可以对属性的限定值施加范围限制作为机密。例如，值为 9 位数字的属性是敏感的。请注意，SSN（社会安全号）包含 9 位数字，因此如果发布了包含 9 位数字的内容，则需要对 KB 进行分类。类似地，我们可以指定 16 位数字的内容为信用卡号。

#### 18.5.2.2 统计推理

在统计推理中，我们得到汇总数据；目的是了解关于总体的宏观属性。

**示例 18.6：** *如果在患者就诊期间值班的心脏外科医生最多只有一位，且我们向用户揭示以下三元组*：

```
<med:HeartSurgery_n_1> <opm:WasControlledBy> <_:b>
```

那么，用户可以得出结论：值班外科医生对该患者实施了手术操作。

##### 18.5.2.2.1 机器学习技术

在 [[CHAN1998]](#ch18.xhtml#ref18_6) 中，作者使用基于决策树的节约型降级框架来处理推理问题。假设是当 Low 出于性能和功能等目的需要信息时，High 必须决定是否将（即降级）信息提供给 Low。换句话说，当 High 希望将一组数据降级给 Low 时，由于推理通道的存在，可能有必要对该数据集进行裁剪。基本上，决策树用于从 High 提供给 Low 的降级数据中形成规则。请记住，我们可以利用个体的非敏感属性，通过在类似个体（出现在先前发布的数据中）上训练的规则，来推导（即预测）敏感属性。在节约型降级中，为未发送给 Low 的潜在降级信息分配一个成本度量。其思路是确定因（High）不降级该数据而导致的功能损失（对 Low）是否值得额外的保密性。决策树有助于分析想要降级的数据中的潜在推理通道。作者为这种节约型降级分配惩罚函数，以最小化未降级的信息量，并将惩罚成本与获得的额外保密性进行比较。

我们的推理引擎涵盖的其他方法包括以下内容。

*   **数据库设计阶段处理推理**：这种方法被认为相对静态。它主要取决于模式设计和完整性约束。也有人指出，针对每个用户的查询不断更改数据库模式并不方便。

*   **处理查询处理过程中的推理**：大部分研究主要集中在查询修改上，主要是因为查询是动态的。

### 18.5.3 来源中的推理

用户可以通过对来源图执行频繁查询并从返回的结果中推断出敏感信息。我们特别关注从前提形成的任何结论，其中该结论的形成未经任何控制或处理前提或前提衍生信息的个人或组织的明示或事先批准。此外，我们的目标是研究发生在来源数据中的推理问题。我们需要自动化软件工具来发现和评估来源存储中的有趣模式和语义关联。记录细粒度来源所产生的信息量是安全分析师一项重要但耗时的工作。我们可以使用语义网语言记录来源，以便智能代理和推理器能够在不损害底层来源语义的情况下自动执行推理。

#### 18.5.3.1 来源中的隐式信息

来源文档包含数据项及其关系，这些关系被构建为有向图。该图中路径上的一个中间节点可能包含敏感信息，例如提交情报报告的代理人的身份，因此我们也需要用于查询和推理的高效工具。此外，我们需要支持大规模来源图，并具备查询该图的能力，以便构建过滤用户查询的用户视图。

安全策略（即安全约束）用于确定谁可以访问文档以及在什么条件下授予访问权限。在情报工作中，可能有必要保护方法和来源；因此，访问控制策略可能将报告来源的访问权限限制在姐妹机构内。然而，这些策略仅限于创建视图，并未考虑来源中的隐式信息，我们需要开发能随来源数据扩展的策略。我们需要为来源构建大型数据存储。来源可以用任何知识表示语言记录，例如 RDF、RDFS 和 OWL。使用这些语言允许我们稍后对来源图执行推理。因此，我们可以确定来源图上的隐式信息。

#### 18.5.4.4 用例：谁说的？

该场景基于为政府机构进行的财务架构设计。这是一个涉及信息、服务和流程的大型架构。大多数利益相关者是非技术人员，许多是会计师。与任何此类架构一样，它基于一系列连续的输入和与利益相关者的会议——并非同时进行。虽然该架构不是使用语义网工具完成的（而是 UML），但无论使用何种形式化方法，都会出现相同的情况。在项目接近尾声时，一位利益相关者正在审查订单的信息模型。这不是该利益相关者第一次看到模型的这部分，但他们有一段时间没审查了。该利益相关者指着处理订单的模型部分上的一个属性问道：“这是从哪来的？谁让你把它放进去的？” 这当然是个合理的问题，但如果不翻阅大量手工笔记，我们无法回答。模型中没有任何内容说明该属性来自哪里、何时添加或基于什么权限。此外，该利益相关者指出，他们以为在模型中的某些内容已被移除，并想知道去哪了。同样，工具也无法提供帮助。**结论**：必须追踪每个断言在模型中的来源（包括录入数据的人和告诉他们放置数据的人）、情境（如会议）和时间。这应成为核心知识管理基础设施的一部分，并直接关系到知识库随时间演变的可信度。

#### 18.5.4.5 用例：作弊的独裁者

某些情报活动似乎会查看感兴趣人物的大学成绩单等信息，并以此推断其能力和品格。据传（这可能只是个传闻）“萨达姆·侯赛因”几十年前曾在澳大利亚的一所大学就读。该校的成绩单被获取并纳入其个人档案。该档案影响了重要的政治和军事活动。显而易见，为了宣传目的，这些成绩单已被篡改。分析人员想知道人工和自动化手段分别做出了哪些推断，推断出了什么信息，以及这些如何改变萨达姆的档案和潜在行动。无法追踪这条信息路径，导致许多观点存疑。这当然只是信息可能被故意伪造或掩盖、且由此得出的结论至关重要的世界中的一个小例子。信息的来源及其下游影响至关重要，特别是在重新评估来源和信息质量时。*结论*：推断的轨迹可能跨越数十年，且该轨迹可能具有关键的战略价值。此外，推断是人工和自动化活动的结合，会影响下游结论。

### 18.5.5 处理规则

推理规则可以用多种格式编码和处理。这些格式包括使用 `SPARQL` 查询编码规则、使用描述逻辑编码规则，最后是将表达力最强的规则编码为 `SWRL` 规则。这些方法各有差异。具体选择取决于知识库的大小、规则的表达能力和可判定性。查询处理引擎不处理推理规则，但功能依然强大。例如，我们可以在溯源的 `RDF` 图编码中查询蕴含关系。这些查询也可用于发现溯源图中的路径（即使用正则表达式路径查询）。这些查询的结果可以组合起来，为复杂的推理问题提供答案。此外，在可扩展性是一个因素的情况下，最佳选择是查询信息片段，并在较小的知识库中组合相关部分。另一方面，在某些情况下，可能无法枚举回答特定推理问题的所有可能查询。因此，我们可能需要配备足够表达能力的自动推理器来为我们进行推理。这些推理器还可能产生仅靠查询引擎无法发现的新演绎。然而，这种能力是有代价的：可判定性。

规则通常比无规则情况下的逻辑更复杂。例如，在 `RDF` 查询引擎中，只需要图蕴含的简单原则。`RuleML` 是一项重要工作，旨在定义万维网可用的规则。推理网是一个新近的实现，它定义了一个在语义网上处理不同推理引擎的系统 [MCGU2003]。

## 18.6 实现细节

### 18.6.1 架构
