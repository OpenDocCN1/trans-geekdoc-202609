**Listing 4-9: Decoding bytes from a reader into a Binary or String type (`types.go`)**

The `decode` function 1 accepts an `io.Reader` and returns a `Payload` interface and an `error` interface. If `decode` cannot decode the bytes read from the `reader` into a `Binary` or `String` type, it will return an error along with a nil `Payload`.

You must first read a byte from the `reader` 2 to determine the type and create a `payload` variable 3 to hold the decoded type. If the type you read from the `reader` is an expected type constant 4, you assign the corresponding type to the `payload` variable.

You now have enough information to finish decoding the binary data from the `reader` into the `payload` variable by using its `ReadFrom` method. But you have a problem here. You cannot simply pass the `reader` to the `ReadFrom` method. You’ve already read a byte from it corresponding to the type, yet the `ReadFrom` method expects the first byte it reads to be the type as well. Thankfully, the `io` package has a helpful function you can use: `io.MultiReader`. We cover `io.MultiReader` in more detail later in this chapter, but here you use it to concatenate the byte you’ve already read with the `reader` 5. From the `ReadFrom` method’s perspective, it will read the bytes in the sequence it expects.

Although the use of `io.MultiReader` shows you how to inject bytes back into a `reader`, it isn’t optimal in this use case. The proper fix is to remove each type’s need to read the first byte in its `ReadFrom` method. Then, the `ReadFrom` method would read only the 4-byte size and the payload, eliminating the need to inject the type byte back into the `reader` before passing it on to `ReadFrom`. As an exercise, I recommend you refactor the code to eliminate the need for `io.MultiReader`.

## Handling Errors While Reading and Writing Data

Unlike writing to file objects, writing to network connections can be unreliable, especially if your network connection is spotty. Files don’t often return errors while you’re writing to them, but the receiver on the other end of a network connection may abruptly disconnect before you write your entire payload.

Not all errors returned when reading from or writing to a network connection are permanent. The connection can recover from some errors. For example, writing data to a network connection where adverse network conditions delay the receiver’s ACK packets, and where your connection times out while waiting to receive them, can result in a temporary error. This can occur if someone temporarily unplugs a network cable between you and the receiver. In that case, the network connection is still active, and you can either attempt to recover from the error or gracefully terminate your end of the connection.

To write to the connection, you pass a byte slice 3 to the connection’s `Write` method 2 as you would to any other `io.Writer`. This returns the number of bytes written and an `error` interface. If the `net.Error`’s `Temporary` method returns true, the code makes another write attempt by iterating around the `for` loop. If the error is permanent, the code returns the error 6. A successful write breaks out of the loop.

## Creating Robust Network Applications by Using the io Package

In addition to interfaces common in Go code, such as `io.Reader` and `io.Writer`, the `io` package provides several useful functions and utilities that make the creation of robust network applications easy. In this section, you’ll learn how to use the `io.Copy`, `io.MultiWriter`, and `io.TeeReader` functions to proxy data between connections, log network traffic, and ping hosts when firewalls attempt to keep you from doing so.

### Proxying Data Between Connections

One of the most useful functions from the `io` package, the `io.Copy` function reads data from an `io.Reader` and writes it to an `io.Writer`. This is useful for creating a *proxy*, which, in this context, is an intermediary that transfers data between two nodes. Since `net.Conn` includes both `io.Reader` and `io.Writer` interfaces, and `io.Copy` writes whatever it reads from an `io.Reader` to an `io.Writer`, you can easily create a proxy between network connections, such as the one you define in the `proxyConn` function in Listing 4-14. This function copies any data sent from the source node to the destination node, and vice versa.

```
package main

import (
    "io"
    "net"
)

func proxyConn(source, destination string) error {
    connSource, err := 1net.Dial("tcp", source)
    if err != nil {
        return err
    }
    defer connSource.Close()

    connDestination, err := 2net.Dial("tcp", destination)
    if err != nil {
        return err
    }
    defer connDestination.Close()

    // connDestination replies to connSource
    3 go func() { _, _ = io.Copy(connSource, connDestination) }()

    // connSource messages to connDestination
    4 _, err = io.Copy(connDestination, connSource)
    return err
}
```

**Listing 4-14: Proxying data between two network connections (`proxy_conn.go`)**

The `io.Copy` function does all the heavy input/output (I/O) lifting for you. It takes an `io.Writer` as its first argument and an `io.Reader` as its second argument. It then writes, to the writer, everything it reads from the reader until the reader returns an `io.EOF`, or, alternately, either the reader or writer returns an error. The `io.Copy` function returns an error only if a non-`io.EOF` error occurred during the copy, because `io.EOF` means it has read all the data from the reader.

You start by creating a connection to the source node 1 and a connection to the destination node 2. Next, you run `io.Copy` in a goroutine, reading from `connDestination` and writing to `connSource` 3 to handle any replies. You don’t need to worry about leaking this goroutine, since `io.Copy` will return when either connection is closed. Then, you make another call to `io.Copy`, reading from `connSource` and writing to `connDestination` 4. Once this call returns and the function returns, each connection’s `Close` method runs, which causes `io.Copy` to return, terminating its goroutine 3. As a result, the data is proxied between network connections as if they had a direct connection to one another.

**NOTE**

Since Go version 1.11, if you use `io.Copy` or `io.CopyN` when the source and destination are both `*net.TCPConn` objects, the data never enters the user space on Linux, thereby causing the data transfer to occur more efficiently. Think of it as the Linux kernel reading from one socket and writing to the other without the data needing to interact directly with your Go code. `io.CopyN` functions like `io.Copy` except it copies up to n bytes. We’ll use `io.CopyN` in the next chapter.

Whereas Listing 4-14’s `proxyConn` function established network connections and proxied traffic between them, Listing 4-15’s `proxy` function proxies data between an `io.Reader` and an `io.Writer`, making it applicable to more than just network connections and much easier to test.

### Pinging Hosts in ICMP-Filtered Environments

In the "Internet Control Message Protocol" (ICMP) section (page 31)[¹], you learned that ICMP is a protocol that provides feedback about local network conditions. Its most common use is to determine whether a host is online by sending a ping request and receiving a pong reply from the host. Most operating systems come with a `ping` command that sends an ICMP echo request to a destination IP address and, once the host returns an ICMP echo reply, `ping` prints the time between sending the ping and receiving the pong.

Unfortunately, many internet hosts filter or block ICMP echo replies. If the host filters pong, `ping` will incorrectly report that the remote system is unavailable. A viable alternative is to establish a TCP connection. If you know the host is listening for inbound TCP connections on a specific port, you can use this to determine whether the host is available, since a TCP connection can only be established if the host is up and completes the three-way handshake.

Listing 4-21 demonstrates a small application that reports the time it takes to establish a TCP connection to a particular host and port.

```
package main

import (
    "flag"
    "fmt"
    "net"
    "os"
    "time"
)

var (
    count    = flag.Int("c", 3, "number of pings: <= 0 means forever")
    interval = flag.Duration("i", time.Second, "interval between pings")
    timeout  = flag.Duration("W", 5*time.Second, "time to wait for a reply")
)

func init() {
    flag.Usage = func() {
        fmt.Printf("Usage: %s [options] host:port\nOptions:\n", os.Args[0])
        flag.PrintDefaults()
    }
}

func main() {
    flag.Parse()

    if flag.NArg() != 1 {
        fmt.Print("host:port is required\n\n")
        flag.Usage()
        os.Exit(1)
    }

    target := flag.Arg(0)
    fmt.Println("PING", target)

    if *count <= 0 {
        fmt.Println("CTRL+C to stop.")
    }

    msg := 0
    for (*count <= 0) || (msg < *count) {
        msg++
        fmt.Print(msg, " ")

        start := time.Now()

        c, err := net.DialTimeout("tcp", target, *timeout)
        dur := time.Since(start)

        if err != nil {
            fmt.Printf("fail in %s: %v\n", dur, err)
            if nErr, ok := err.(net.Error); !ok || !nErr.Temporary() {
                os.Exit(1)
            }
        } else {
            _ = c.Close()
            fmt.Println(dur)
        }

        time.Sleep(*interval)
    }
}
```

## Handling Pending Data on Close

As mentioned earlier in this chapter, deadlines provide better cross-platform support, penetrate firewalls better, and ensure your application actively manages network connections.

By default, if you have written data to a `net.Conn` but the data hasn’t been sent or acknowledged by the receiver, and you close the network connection, the operating system completes the data transfer in the background. If you don’t want this behavior, the `net.TCPConn` object’s `SetLinger` method allows you to adjust it:

```
err := tcpConn.SetLinger(-1) // any value less than 0 uses default behavior
```

With linger disabled, when you close the connection, the last segment of data may be sent to the server along with the FIN. Since calling `conn.Close` doesn’t block, you can’t know whether the server has received the data you just sent before the FIN. Data may remain in the server’s receive buffer, and if the server crashes, unacknowledged data and the FIN are lost. It may seem tempting to keep linger to give the server enough time to acknowledge the data.

But if the server crashes (as in the example), using linger won’t help either. Additionally, some developers consider using linger in this situation a code smell. Your application should ensure that, when worried about unacknowledged data, it confirms the server has received all data before tearing down the connection.

If you want to immediately discard all unsent data when closing a network connection and ignore acknowledgment of sent data, set the connection’s linger to 0:

```
err := tcpConn.SetLinger(0) // immediately discard unsent data on close
```

Setting linger to 0 causes a RST packet to be sent when you call the connection’s `Close` method, abruptly interrupting the connection and bypassing the normal teardown process.

If you want to find a middle ground where the OS supports it, pass a positive integer n to `SetLinger`. The OS will attempt to transmit all pending data within n seconds, then discard any unsent or unacknowledged data:

```
err := tcpConn.SetLinger(10) // discard unsent data after 10 seconds
```

If you decide to modify the linger value of a connection, read how the OS handles linger on network connections. When in doubt, use the default.

## Resolving Common Go TCP Network Problems

Go doesn’t hold your hand when using TCP network connections. Therefore, bugs can appear in your code that cause network errors. This section covers two common TCP network problems: zero window errors and sockets stuck in the `CLOSE_WAIT` state.

### Zero Window Errors

We discussed TCP’s sliding window in the "Receive Buffers and Window Sizes" section (page 48), and how the window size tells the sender how much more data the receiver can accept until the next acknowledgment.

The common pattern for reading network data is: read some data from the connection, process it, read more data, continue processing, and so on. But if you don’t read data fast enough, eventually the sender’s receive buffer fills up, leading to a **zero window** condition. At this point, the receiver can’t accept more data until the application reads from the buffer. This often happens when processing data read from the network blocks, preventing the code from reading the socket again (as in Listing 4-26).

```
buf := make([]byte, 1024)

for {
    n, err := conn.Read(buf)
    if err != nil {
        return err
    }
    handle(buf[:n]) // BLOCKS!
}
```

**Listing 4-26: Processing received data blocks the loop**

Reading from the network releases receive buffer space. If you block for too long while processing data, the receive buffer can fill up. ### Sockets Stuck in CLOSE_WAIT

# Unreliable UDP Communication

Although most network applications leverage TCP’s reliability and flow control, the User Datagram Protocol (UDP) remains an important part of the TCP/IP stack. UDP is a minimal protocol, and some applications don’t need the session setup and overhead that TCP provides. These applications, such as domain name resolution services, choose UDP over other protocols.

This chapter first compares UDP with TCP, highlighting scenarios where UDP might be more suitable than TCP. Then you’ll learn how to send and receive UDP packets in Go. Finally, you’ll explore why limiting the size of UDP packets sent on a network is important and how to determine the optimal packet size.

## Using UDP: Simple and Unreliable

UDP is unreliable because it lacks many of TCP’s reliability mechanisms. It only provides a socket address (IP address and port). In fact, the protocol is so concise that RFC 768 describes the complete protocol in about three pages. Unlike TCP, UDP doesn’t provide session support and doesn’t confirm whether the destination is reachable; it only attempts to deliver packets on a best-effort basis. Receivers don’t automatically acknowledge UDP packets, so UDP has no built-in delivery confirmation mechanism. UDP doesn’t manage congestion, control data flow, or retransmit packets. Finally, UDP doesn’t guarantee that packets are received in the order they were sent. UDP acts only as a channel between applications and the IP layer. This simplicity makes UDP faster and more attractive for some applications.

UDP has several advantages over TCP. TCP can transmit data only after establishing a session with each group node, while UDP can send a single packet to a group of nodes without copying the packet, known as `multicasting`. UDP can also broadcast packets to all members of a subnet because it doesn’t need to establish a session with each node.

UDP is ideal when lost packets aren’t fatal to overall communication, because the newest received packet can replace an earlier lost one. Weather data is a classic example. If you’re receiving weather data over your phone to track a tornado, you don’t care about the loss of data from two minutes ago, as long as you have the current tornado location.

If your application doesn’t need all the features TCP provides, consider UDP. For most network applications, TCP remains the right choice. But if UDP’s speed and simplicity better suit your use case, and the reliability trade-off isn’t a concern, UDP is a viable option.

The UDP packet structure consists of an 8-byte header plus a payload. The header contains a 2-byte source port, a 2-byte destination port, a 2-byte packet length (in bytes), and a 2-byte checksum. The minimum packet length is 8 bytes to accommodate the header and an empty payload. Figure 5-1 shows the UDP packet organization.

## Sending and Receiving UDP Data

When sending and receiving data, UDP is more "brutal" than TCP. For example, suppose your neighbor bakes a pie and wants to give it to you. Communicating over TCP is like the neighbor calling out from her window (her socket address) to your open window (your socket address), you hear the greeting and reply (TCP handshake), the neighbor then delivers the pie. You accept the pie and acknowledge receipt (data transfer), then both sides exchange goodbyes and leave (connection termination). In contrast, communicating over UDP is like the neighbor suddenly throwing the pie at your window (whether or not it’s open), without waiting to confirm you received it.

The `net.Conn` interface, introduced in the section "Using the net.Conn Interface" on page 74, is used for client-server communication over stream-oriented connections (like TCP). But this interface isn’t suitable for UDP connections, because UDP isn’t a stream-oriented protocol; it doesn’t maintain sessions and doesn’t perform a handshake like TCP. UDP has no concept of acknowledgments, retransmissions, or flow control.

Instead, UDP relies primarily on the `net.PacketConn` interface for packet-oriented communication. We’ll discuss using `net.Conn` with UDP later in this chapter, but for most UDP applications, `net.PacketConn` is more appropriate.

UDP is a minimal, datagram-based protocol that prioritizes speed over reliability by giving up many of TCP’s flow control and reliability features.

UDP is ideal when speed and simplicity are key and data loss is acceptable, such as for real-time video streaming.

Because UDP isn’t session-oriented, there is no "UDP listener" concept. Instead of using `net.ListenPacket` to create a network connection, which returns a `net.PacketConn` interface. Your code can read any incoming message or datagram from the `net.PacketConn` interface, because each `net.PacketConn` listens for incoming messages.

When using UDP, fragmentation is a serious consideration. Avoid UDP packet fragmentation as much as possible to help ensure delivery. The `ping` command can help you determine the appropriate maximum transmission unit (MTU) between your machine and the target network. Since the ICMP packet header used by `ping` is the same size as the UDP header, you can easily determine the payload size threshold before fragmentation occurs. In addition to managing fragmentation by appropriately sizing the payload, your code must also manage acknowledgments and retransmissions to ensure reliability.

# Ensuring UDP Reliability

Chapter 5 introduced basic network applications using UDP and showed the flexibility of Go’s `net` package and interfaces for writing portable code. This chapter continues from the previous chapter by introducing one way to ensure reliability over UDP communication.

## Reliable File Transfer with TFTP

As discussed in the previous chapter, UDP is inherently unreliable. This means that making a UDP connection reliable is the responsibility of your application. In the previous chapter, we discussed UDP and its best-usage scenarios, which require only a subset of TCP’s features. Therefore, it’s reasonable to study a typical application-layer protocol.

*Trivial File Transfer Protocol (TFTP)* is an example that ensures reliable data transfer over UDP. It allows two nodes to transfer files by implementing a subset of TCP’s reliability features. A TFTP server implements ordered packet delivery, acknowledgments, and retransmission. To keep this example focused on core points, your server only allows clients to download binary data. It doesn’t support uploads, ASCII transfers, or features added to TFTP beyond RFC 1350. Your server simply serves the same file under the client-requested filename to simplify processing.

Remember that TFTP is not suitable for secure file transfer. While it provides reliability for UDP connections, it doesn’t support encryption or authentication. If your application needs to communicate over UDP, you might want to use WireGuard (*https://github.com/WireGuard/wireguard-go/*), an application that allows secure communication over UDP.

The following sections implement a read-only TFTP server, teaching you the basics of adding reliability over UDP. "Read-only" means your server only allows clients to download files, not upload. ### Read Requests

When a client wants to download a file, the server receives a *read request* packet. The server must then respond with either a data packet or an error packet, both of which signal that the server has received the read request. If the client doesn’t receive a data or error packet, it may resend the read request until the server responds or the client gives up.

|---------|------------|---------|------------|---------|

The read request packet contains a 2-byte operation code, filename, a null byte, mode, and a trailing null byte. The operation code is the integer that uniquely identifies each operation type. The mode indicates how the server should send the file: `netascii` or `octet`. If a client requests a file in *netascii* mode, the client must convert the file to a format conforming to its own newline conventions. For simplicity, we only accept *octet* mode, which instructs the server to send the file in binary format (i.e., as-is).

### Data Packets

Clients receive *data packets* in response to their read requests, provided the server was able to retrieve the requested file. The server sends the file in a series of data packets, each of which has an assigned block number, starting at 1 and incrementing with every subsequent data packet. The block number allows the client to properly order the received data and account for duplicates.

All data packets have a payload of 512 bytes except for the last packet. The client continues to read data packets until it receives a data packet whose payload is less than 512 bytes, indicating the end of the transmission. At any point, the client can return an error packet instead of an acknowledgment, and the server can return an error packet instead of a data packet. An error packet immediately terminates the transfer.

Figure 6-2 shows the format of a data packet.

| 2 bytes | 2 bytes | *n* bytes |
|---------|---------|-----------|
| OpCode | Block # | Payload |

*Figure 6-2: Data packet structure*

Like the read request packet, the data packet’s first 2 bytes contain its operation code. The next 2 bytes represent the block number. The remaining bytes, up to 512, are the payload.

The server requires an acknowledgment from the client after each data packet. If the server doesn’t receive a timely acknowledgment or an error from the client, the server will retry the transmission until it receives a reply or exhausts its number of retries. The `Data` struct 1 keeps track of the current block number and the data source. In this case, your payload is an `io.Reader` instead of a byte slice, because an `io.Reader` allows greater flexibility about where you retrieve the payload. You may have noticed the potential for integer overflow of the 16-bit unsigned block number. If you send a payload larger than about 33.5 MB (65,535 × 512 bytes), the block number wraps around to 0. Your server will happily continue sending packets, but the client may not gracefully handle the overflow. You should mitigate the risk of overflow by limiting the maximum file size your TFTP server supports, by recognizing that overflow may occur and deciding whether it’s acceptable for the client, or by using a different protocol.

The handler (Listing 6-10) accepts a client read request and replies with the server’s payload. This handler is a method on the `Server` type 1 that takes a client address and a read request. Since you need to access the `Server` fields, it’s defined as a method. You then establish a connection with the client using `net.Dial` 2. The UDP connection object created by `net.Dial` only reads packets from the client, saving you from checking the sender’s address on every `Read` call. You prepare a `Data` object 3 using the server’s payload, then enter a `for` loop to send each packet 4. This loop continues as long as the packet size equals 516 bytes.

After marshaling the `Data` object into a byte slice, you enter the `for` loop 5 used to resend the packet when one of the following conditions occurs: either you exhaust the retry count or the packet is delivered successfully. Writing the packet to the network connection 6 updates the `n` loop variable, indicating the number of bytes sent. If that value is 516 bytes, control returns to the `NEXTPACKET` label and iteration continues. If the value is less than 516 bytes, the loop exits.

Before determining whether the transfer is complete, you must verify that the client has successfully received the last packet. You read bytes from the client and attempt to unmarshal them into either an `Ack` object or an `Err` object. If unmarshaling into `Err` succeeds, you know the client returned an error and should return early. Early return means the transfer terminated before sending the entire payload. For our purposes, this isn’t recoverable; the client needs to request the file again to start another transfer.

If unmarshaling into `Ack` succeeds, you check the object’s `Block` value to see if it matches the current packet’s block number 7. If it matches, you loop back to the outer `for` loop 4 and send the next packet. If it doesn’t match, you loop back to the inner `for` loop 5 and resend the current packet.
