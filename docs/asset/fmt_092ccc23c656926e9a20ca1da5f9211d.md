## 10.6 开放/封闭世界语义

在对业务领域建模时，可以就模型中所捕获知识的完整性采取不同立场。*封闭世界假设* (CWA) 假定所有相关事实均已知（即出现在模型中，无论是作为断言事实还是派生事实），且所有相关业务规则均已知。这是数据库的常用假设，并蕴含*失败即为假*（无法找到或证明某命题即意味着它为假）。

例如，考虑图 10.57(a) 中填充的 ORM 模型。共有四名学生（1001–1004），但只有两名（1001 和 1003）被建模为聪明。使用 CWA，我们可以推断学生 1002 和 1004 不聪明。同样，我们可以推断学生 1003 和 1004 不刻苦。利用断言事实和所示派生规则，我们推断三名学生（1001、1002 和 1003）预计会通过。如果没有针对事实类型 `Student is expected to pass` 的其他派生规则，则 **if** 运算符在 CWA 下被解释为 **iff**。因此，学生 1004 预计不会通过。

```
Fig. 10.57 The closed world assumption requires all facts to be modeled.
```

图 10.57 封闭世界假设要求对所有事实建模。

在封闭世界语义下，映射到关系数据库时，断言的正面事实和隐含的负面事实应分组到图 10.57(b) 所示的 Student 表中，对 `isIntelligent` 和 `worksHard` 使用强制性布尔属性。

关于通过预期的派生事实可映射到图 10.57(c) 所示 `Student_View` 表中的附加 `isExpectedToPass` 列。除了创建此视图外，还可将这些派生事实的计算列添加到基础 Student 表中。NORMA 工具目前将一元事实映射为可选的布尔列（而非强制性布尔值），因此这些列允许空值。

本书使用的关系模式符号为主键名称加下划线，可选列名称用方括号括起。因此，NORMA 将图 10.57(a) 的 ORM 模式映射为以下关系模式：`Student`( studentNr, `[isIntelligent]`, `[worksHard]` )。

计划扩展 NORMA 工具，增加对一元事实的开放/封闭世界语义的控制，并增加对否定一元事实的支持。在此期间，若要使用 NORMA 映射到强制性布尔值，可用一个针对具有布尔数据类型的值类型的强制性 `n`:1 事实类型来替换一元事实。例如，用强制性 `n`:1 事实类型 `Student has IsIntelligentStatus` 替换 `Student is intelligent` 事实类型，其中 `IsIntelligentStatus` 具有布尔数据类型。

重塑模型以实现一元事实 CWA 语义的第二种方法是，用一个针对具有恰好两个命名值的实体类型或值类型的强制性 `n`:1 事实类型来替换一元事实，例如 `Student has IntelligenceStatus(.Name)` {‘Intelligent’, ‘Unintelligent’}。

建模一元事实类型 CWA 语义的第三种方法是添加一个具有否定含义的*相反一元*（即其实例等同于原始一元实例的否定），例如，针对一元事实类型“Student is intelligent”添加“Student is unintelligent”。这两个一元之间适用一个异或约束。

NORMA 工具计划添加一种表示法，用于声明一元之间的否定含义关联。在这种情况下，异或约束是隐含的，且模式映射到带有单个布尔列的关系表；否则，此方法映射到带有两列的关系表。

作为另一个例子，图 10.58(a) 展示了一个闭世界一元事实类型“Country is monolingual”（恰好有一种官方语言）及其示例数据。加拿大 (CA) 和塞浦路斯 (CY) 未被记录为单语国家，因此 CWA 方法意味着它们不是单语国家。图 10.58(b) 用一个强制的 *n*:1 事实类型替换了该一元。

图 10.58 一些 CWA 建模选项。

图 10.58(c) 添加了一元事实类型“Country is multilingual”，其含义是单语一元的*相反*。如果我们添加一种正式声明一元含义相反的方式（不同提案正在讨论中），异或约束的排斥方面将被隐含，且两个事实类型均映射到单个布尔列。否则，此方法映射到带有两列的关系表。

*开放世界假设* (OWA) 允许某些相关事实可能是未知的（作为断言或可推导的事实）。图 10.59 在 OWA 语义下重新建模了我们的学生示例。

在图 10.59(a) 中，一元谓词的角色框采用虚线，暗示开放性，因此具有 OWA 语义。撰写本文时，NORMA 尚不支持 ORM 的这种 OWA 表示法。

OWA 意味着*经典否定*（找不到或无法证明一个命题或其否定，意味着其真值为*未知*）。例如，正如图 10.59(b) 基础 Student 表所示，未记录学生 1002 和 1004 聪明这一事实，仅意味着我们不知道他们是否聪明。此处记录条目“unknown”以指示此情况。在大多数数据库中，此条目将显示为 null。请自行核对其他“unknown”条目是否源于 OWA 解释。

图 10.59(b) 和 (c) 所示的关系模式表明，开放世界一元映射到一个可选布尔值，其真值被限制为 True。

在 NORMA 中获得此关系模式结果的一种方法是，用一个以具有布尔数据类型且限制为 True 的值类型为目标的可选 *n*:1 事实类型，替换每个一元。例如，用事实类型“Student has IsIntelligentStatus {true}”替换“Student is intelligent”，其中 IsIntelligentStatus 的角色命名为“isIntelligent”。

为一元建模 OWA 语义的另一种方法是，添加一个具有否定含义的一元，并在其角色与原始一元角色之间添加一个排斥约束。例如，添加“Student isUnintelligent”，并在其角色与“Student isIntelligent”事实类型的角色之间添加排斥约束。然而，若无法正式声明一个一元是另一个的否定，此方法将映射到带有两列的关系表，而非单列。

作为 CWA 和 OWA 之间的折中立场，*半闭世界假设* (SWA) 允许某些相关事实作为可推导事实可能是未知的，但作为断言事实则不能。这意味着*半正否定*（给定任何断言事实类型，在其中找不到事实实例意味着该实例为假；而无法证明某个可推导事实类型实例或其否定，意味着其真值为未知）。此方法仅当事实类型为断言或完全可推导（而非半可推导）时可用。

*带否定的开放世界* (OWN) 假设允许某些相关事实未知（作为断言或可推导事实），但也允许断言否定。与 OWA 一样，OWN 方法也导致经典否定，这是经典逻辑中的常用方法。尽管在数据库中断言负面事实很少见，但在逻辑系统中却很常见。OWN 方法只是 OWA 的一个特例。

在 ORM 中支持 OWN 语义的一种方法是，允许一元填充正例和负例，否定实例以波浪号“~”为前缀，该符号常用于逻辑中表示“**非**”（**并非如此**）运算符，如图 10.60(a) 所示。

![Fig. 10.60 Some OWN modeling options.](img/f10-60-9780443237904.jpg)

图 10.60 一些 OWN 建模选项。

支持*开放一元的否定实例*的另一种方法是，添加一个含义相反的单独一元事实类型（其实例等同于原始一元的否定实例）。相反的含义隐含了这两个一元之间的排斥约束。例如，要记录学生 1002 不聪明，将该学生纳入事实类型“Student isUnintelligent”的实例群，并在其角色与“Student isIntelligent”事实类型的角色之间设置排斥约束。

第三种选项是用第三种建模方式替换该一元。假设我们知道澳大利亚 (AU) 和美国 (US) 是单语国家，加拿大是多语国家，但不知道塞浦路斯的语言状态。这对应于 OWN 方法，如图 10.60(a) 直接建模所示。图 10.60 的其余部分展示了在 ORM 和 UML 中建模此情况的替代方法。

## 10.7 高阶类型

### 评估信息模型中使用高阶类型的可行性

本节评估在信息模型中使用高阶类型的可行性。我们首先回顾逻辑学中的一些基本概念。

**一阶逻辑**仅对个体进行量化，不对谓词进行量化。例如，约束“**每个** Person 至多出生于 **一个** Date”可形式化为一阶类型逻辑如下：

```
∀x:Person ∃^(0..1)y:Date x was born on y
```

此处，类型 `Person` 和 `Date` 作为一元谓词出现，“∀”是全称量词（“**对于每个**”），而“∃^(0..1)”是“**至多存在一个**”量词。量化针对个别人和个别日期。一阶谓词只能由个体实例化。

**二阶逻辑**允许对一阶谓词（以及个体）进行量化。例如，规则“每个非对称谓词也是非自反的”可形式化为二阶逻辑如下：

```
∀R:Predicate (Asymmetric R → Irreflexive R)
```

三阶逻辑允许对二阶谓词进行量化，以此类推。所有阶数高于一阶的逻辑称为**高阶逻辑**。因为类型可由一元谓词形式化，如果类型 `A` 的实例本身就是一个类型，则 `A` 是**高阶类型**。

**分类类型**是用于将另一个类型分类为子类型的对象类型。例如，`Gender` 可用于事实类型 `Person is of Gender` 中，将 `Person` 分类为 `MalePerson` 和 `FemalePerson`。

ORM、ER 和关系模型的大多数形式化都基于一阶逻辑。相比之下，UML 引入了幂类型的概念，其实例本身可能是类型，因此需要高阶语义。

在信息建模中使用高阶类型似乎有三个主要论据：

1.  允许将某些分类类型（如 `AccountType`、`CarModel`）的实例视为类型本身（如 UML 幂类型）。

2.  直接形式化灵活数据结构的语义，其中属性条目本身可能表示集合或一般概念（如非第一范式中的对象关系表）。

3.  允许在同一模型中指定似乎跨越层级/元层级（或忽略层级区分）的业务规则（如：只有财务部门可指定 `AccountType` 的允许实例）。

由于转向高阶逻辑可能会给形式化和实施建模方法的任务增加相当大的复杂性，因此值得研究是否可以在保持一阶框架的同时实现相同的实际建模目标。我们认为可以。

首先让我们解决这个问题：分类类型的实例可以是类型本身吗？例如，在 图 10.61 所示的银行模式中，`AccountType` 的储蓄账户实例是否与子类型 `SavingsAccount` 相同？为便于讨论，名为“CheckingAccount”和“SavingsAccount”的两个 `AccountType` 实例在此分别描绘为白点和阴影点，且子类型已着色。

![图 10.61 AccountType 的实例是否与 Account 的子类型相同？](img/f10-61-9780443237904.jpg)
