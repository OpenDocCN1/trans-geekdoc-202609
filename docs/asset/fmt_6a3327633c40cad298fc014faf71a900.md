## 16.4 其他标记语言

顾名思义，标记语言（如 `XML`）通过向原始信息添加某种额外标记来指示其功能或用途。历史上，标记的主要应用领域是出版业，用于（至今仍用于）指示对作者文本应用的处理方式，以将其转换为适合印刷的排版布局。在数据库语境中，我们可以将标记视为元数据。

一种与 `JSON` 理念相近的语言是 `YAML`。这最初代表 "Yet Another Markup Language"（另一种标记语言），但随后出现了对该名称的其他解释。`YAML` 是 `JSON` 的超集，具有一些额外功能，并且有可用的工具在 `YAML` 和 `JSON` 之间相互转换。`YAML` 的主要动机是提供比 `JSON` 更具 "人类可读性" 的格式，特别是避免大量使用括号（圆括号、方括号或花括号）。可以通过缩进项目来表示嵌套，类似于使用空格的 `Python` 语言。这减少了常见键盘错误的可能性。

`YAML` 的一些简要特性包括以下内容：

* 通过将子节点缩进到其父节点下方来嵌套项目。
* 键值对由冒号分隔，但不需要引号。
* 列表中的新项目由连字符指示。
* 标量值（包括字符串、数字和布尔值）可以自由使用。
* 字符串不需要引号，但如果需要可以使用（例如，如果需要将数字视为字符串处理）。
* 可以用井号字符表示注释（转换为 `JSON` 时注释会被剥离）。
* 提供了额外命令来控制输出中文本的布局（例如，抑制换行）。

以下显示了我们电影数据示例的简略版本，以 `YAML` 表示。

```yaml
--- # This is a YAML document
movies:
  - movieNr: 1
    title: Cosmology
    released: '2006'
    director: Lee Lafferty
  - movieNr: 2
    title: Kung Fu Hustle
    released: '2004'
    director: Stephen Chow
    stars:
      - name: Stephen Chow
        gender: M
  - movieNr: 5
    title: The Da Vinci Code
    released: '2006'
    director: Ron Howard
    stars:
      - name: Tom Hanks
        gender: M
      - name: Ian McKellen
        gender: M
      - name: Audrey Tautou
        gender: F
...
```

`YAML` 是在需要显式表示数据结构的相对较短文档中的热门选择。两个例子是包含应用程序数据的配置文件和结构化消息的交换。它不广泛用于大型数据集合。其易用性部分归因于对数据值背后意图的自动化决策，这可能导致意外后果。例如，某些解析器可能将未加引号的值 `No` 解释为布尔值 `false`，这可能并非原始意图。

最熟悉的标记语言可能是 `HTML`，用于定义网页结构。与 `XML` 不同，`HTML` 中的标签是预定义的，并在 `HTML` 标准中定义了特定含义。在 Web 使用的早期，`HTML` 也曾被用作识别数据结构某些方面的一种相当薄弱的方法，但这显然是令人不满意的。与 `XML` 一样，`HTML` 对作者来说可能显得笨拙和别扭，因此开发出了几种替代方案。一些例子包括以下内容。

* 可爱地命名为 `Markdown` 的轻量级语言，用于向文本文档添加格式指示符。标记文档可用于各种应用程序以生成发布格式（如 `PDF`）并转换为其他格式（如完整的静态网站）。然而，它在表达数据结构方面的能力显然有限。
* `AsciiDoc` 是基于 `XML` 的 `DocBook` 格式的纯文本等价物，用于结构化文档。文档可以简单地使用文本编辑器创建，然后渲染为所需的最终格式，如 `PDF`、`HTML` 等。
* `MediaWiki` 是另一种为易用性而设计的轻量级语言。顾名思义，它是为创建 Wiki 页面而开发的，也是 `Wikipedia` 的基础。与这类其他语言一样，其文档可以重新处理为许多其他格式，包括 `HTML`。

这些语言的主要目的是定义文档结构，而非数据结构。尽管存在一定程度的重叠，但既然有更好的替代方案可用，就没有迫切需要使用这些语言进行数据描述。因此，我们将不在本章中进一步探讨它们。

## 16.5 XML、JSON 和 ORM

一个值得考虑的问题是，对象角色建模（`ORM`）是否可用于设计 `XML` 模式或 `JSON` 模式，就像它可用于设计关系模式一样。答案当然是 "Yes"（可以），但有一些在关系情况中不相关的额外考量因素。

如前所述，`ORM` 模型可以用 `XML` 表示，这确实是 `NORMA` 工具使用的默认文件格式。大致结构可概述如下：

```xml
<ORMModel>
  <Objects>
    <Object id="123" ...> </ObjectType>
    <Object id="456" ...> </ObjectType>
    ...
  </Objects>
  <Facts>
    <Fact id="321" ...>
      <FactRole id="789" ...> </FactRole>
      <FactRole id="987" ...> </FactRole>
    </Fact>
    ...
  </Facts>
  <Constraints> ... </Constraints>
  ...
  <ORMDiagram> ... </ORMDiagram>
</ORMModel>
```

每个项目都有一个唯一标识符（`UUID`），这些标识符用于关联项目。例如，扮演事实角色的对象可以通过其 `UUID` 从角色实体引用。

虽然此结构捕获了所有 `ORM` 模型细节，但它并未为数据模型提供良好的模板。部分内容（如图表信息）与定义数据结构无关，且 `*.orm` 文件中的项目（如对象类型和事实类型）的表示方式旨在促进建模操作，而非数据传输。相反，需要的是从 `ORM` 模型到 `XML` 模式的映射，以适应相关数据。

从 `ORM` 模型映射到关系模式在第 11 章中讨论过。在 `Rmap` 过程中只有少数可能的选项，例如如何处理子类型。该过程在很大程度上是自动的，两个不同的开发人员映射相同的 `ORM` 模型通常会产生相同的关系模式。然而，对于 `XML` 情况则不同。

### XML 和 ORM 映射问题

#### XML 中的层次表示

第一个问题是 XML 强制我们将数据表示为层次结构，即使在 ORM 模型中不存在自然层次。这是元素嵌套在元素内部这一 XML 固有特性的结果。请看图 16.5 中所示的微小 ORM 模型。

![图 16.5 学生-课程关系。](img/f16-05-9780443237904.jpg)

图 16.5 学生-课程关系。

一种选择是将课程嵌套在学生之下。

```xml
<Model>
    <Student name="Alice" …>
        <Course id="CS101" …> …</Course>
        <Course id="CS104" …> …</Course>
    </Student>
    <Student name="Bob" …>
        <Course id="CS101" …> …</Course>
    </Student>
</Model>
```

但将学生嵌套在课程之下同样有效。

```xml
<Model>
    <Course id="CS101" …>
        <Student name="Alice" …> … </Student>
        <Student name="Bob" …>… </Student>
    </Course>
    <Course id="CS104" …>
        <Student name="Alice" …> … </Student>
    </Course>
</Model>
```

我们也可以考虑一种更接近关系风格的方式，包含一个学生列表、一个课程列表和一个链接注册元素的列表。

```xml
<Model>
    <Students>
        <Student name="Alice" …> … </Student>
        <Student name="Bob" …>… </Student>
    </Students>
    <Courses>
        <Course id="CS101" …> …</Course>
        <Course id="CS104" …> …</Course>
    </Courses>
    <Enrolments>
        <Enrolment student="Alice" course="CS101"> … </Enrolment>
        <Enrolment student="Alice" course="CS104"> … </Enrolment>
        <Enrolment student="Bob" course="CS101"> … </Enrolment>
    </Enrolments>
</Model>
```

无法从 ORM 模型推断出上述哪种方式更优，因为选择取决于外部因素，例如数据的预期用途和访问模式。

#### 元素属性与元素内容

第二个问题是 XML 提供了两种存储数据的选项：作为元素属性的值，或作为元素的内容。上述示例将学生姓名显示为属性，但以下方式也是同样有效的替代方案：

```xml
<Student>
    <Name>Alice</Name>
    …
</Student>
```

对于在这两个选项之间如何决定，没有硬性规定，尽管已提出过各种指导原则，例如仅将属性保留给元数据。属性有一些局限性，在某些情况下会使元素成为更优选择，例如多值数据或具有内部结构的数据，但对于简单的标量值，任一方法均可使用。

尽管我们一直在描述 XML 的情况，但 JSON 也会出现类似问题，它同样提供了如何表示数据的选择。所有这意味着：两个不同的开发人员映射同一个 ORM 模型，可能会产生截然不同的 XML 模式（或 JSON 模式）。

#### XML 渲染的系统化过程

为了生成关系结构的 XML 渲染，我们可以遵循一个易于自动化的系统化过程。

每个关系表将映射为 XML 中的一个元素类型，该类型可以拥有复数标签名（例如 `<Employees>`）。这些主要元素类型将嵌套在一个合适命名的根节点下。这些主要元素将包含相关类型的子元素列表。

表中的行将映射为具有单数标签名的子元素（例如 `<Employee>`），嵌套在其父元素下（例如 `<Employees>`）。关系列映射为其相关子元素的属性。可以为每个子元素添加一个 `UUID` 属性，以便于识别和交叉引用。

结果是一个类似于上述示例中“关系”风格的 XML 文件。即使这不是首选格式，它仍可能是一个良好的第一步。一旦我们有了 XML 文件，就可以使用适当的代码将其转换为替代的 XML 结构，或许可以使用用于转换的 XML 样式表语言（`XSLT`）。

如果我们需要直接从 ORM 模式生成 XML 文件，可以通过增加一些额外步骤来调整上述方法。首先，我们遵循 `Rmap` 过程以识别与 ORM 模式对应的关系结构。接下来，我们将上述过程应用于该关系结构以定义 XML 模式元素。最后，我们需要将 ORM 模式中所需的任何约束添加到 XML 模式中。当从数据库生成数据传输文件时，不需要这一最后步骤，因为我们可以假设适当的约束已经应用于数据。

映射到 JSON 模式可以遵循类似的过程。表变为 JSON 对象，行变为父类型中嵌套对象的列表，列值作为键值对出现在嵌套对象中。

## 16.6 总结

XML 是基于标准通用标记语言（SGML）的一系列标记语言家族中的一员。基于 SGML 的其他语言包括 HTML，尽管它现在已在一定程度上偏离了其原始基础。XML 设计初衷是易于解析，最初是在 Web 应用程序的背景下，但现在它已作为一种描述数据结构的通用工具而确立地位，独立于任何特定的数据容器。它已成为许多应用程序的内置功能，尽管其存在可能并不显而易见。例如，Microsoft Office 文件的当前格式（如 `*.docx`、`*.pptx` 和 `*.xlsx`）基于 XML，用于创建和管理对象关系模型的 `NORMA` 工具在其 `*.orm` 文件格式中使用 XML。

XML 的一个关键特性是其可扩展性。与 HTML 不同，它不预设预定义的标签名，因此可以设计模式以满足任何所需场景。如果有必要，模式可以用机器可读的形式记录，以便 XML 文档可以针对模式定义进行验证，确保其一致性。从 SGML 继承的原始模式定义方法使用 DTD，它们用自己的语言表达。现代用法已转向使用 XML 本身来表达模式，采用 XML Schema Definition（`XSD`）或更简单的替代方案 Relax NG。

XML 定义由万维网联盟（W3C）控制。XML 家族中存在其他几个 W3C 标准。除了 XML Schema，我们已经深入讨论了 `XPath` 和 `XQuery`。这些允许以大致对应于在 SQL 表中使用 `select` 语句进行查询的方式来查询 XML 数据。其他 W3C 标准包括以下内容：

* **XSLT**（可扩展样式表语言转换）是一种基于 XML 的语言，用于将 XML 文档转换为不同的 XML 模式或完全不同的格式（如 PDF）。
* **XLink**（XML 链接语言）提供在 XML 文档内创建内部和外部链接并将元数据与链接关联的方法。
* **XPointer** 基于 `XPath`，支持寻址 XML 文档的内部结构。这可用于创建类似于关系数据库中外键的东西。
* **XHTML** 是一种语法符合 XML 的更严格版本的 HTML。
* **SVG**（可缩放矢量图形）是一种描述二维矢量图形的语言，允许平滑缩放至不同的显示分辨率。

由 W3C 和其他机构制定的许多其他基于 XML 的标准，可能多达数百个，以及不可计数的私有应用。这使得 XML 成为在数据库系统之外定义结构化数据的最成熟方法。

XML 是一种文本格式，虽然它可以使用文本处理操作进行操作，但使用对所表达的数据结构敏感的处理操作会更有效。数据库系统最初开始将 XML 作为一种文本格式使用，但对其价值的认可促使它被纳入 SQL 标准作为一种原生数据类型。大多数数据库供商都增加了功能来存储 XML 数据、操作 XML 数据，并在 XML 和关系表结构之间进行双向转换，有时包括官方 SQL 标准中不包含的专有扩展。

JSON 是一种比 XML 稍年轻的语言。它最初是作为 Web 服务器和浏览器之间一种相对轻量级的通信语言而开发的，使用标准浏览器功能而不是辅助插件。这使得 JavaScript 成为定义标记语言的显而易见的起点，因此 JavaScript 对象成为了该表示法的基础。

JSON 流行的一个主要因素是与 XML 相比，它的简单性和易于处理。它是一种更紧凑的格式，减少了数据传输所需的带宽；考虑到其创建的初衷，这是一个重要因素。它通常也更适合 Web 相关技术，例如在应用程序开发中。相对而言，它的表达能力不如 XML。它不支持命名空间，并且不适用于精确定义数据类型很重要的应用。然而，它被采用为文档数据库的主要构建原则，并作为原生数据类型纳入 SQL，这表明它足够健壮，能够满足广泛现实场景的需求。

XML 和 JSON 在可预见的未来将继续共存，因为两者并非彼此的直接替代品。人们很容易将 XML 刻板地描述为数据存储之外的重量级数据结构化解决方案，将 JSON 描述为轻量级解决方案，但这模糊了两者各自的一些重要特性。当然，存在一个很大的中间地带，两者都可以有效地使用，它们之间的任何选择都将基于数据结构化能力以外的因素做出。
