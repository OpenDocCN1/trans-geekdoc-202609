
很难知道你上传到目标系统的文件是否会触发主机入侵检测系统（HIDS）的报警。除非你对被攻的系统拥有不受限制的访问权限（这在开始是不常的），否则你可能只能碰运气上传文件，并希望不要发生任何事。为了消除这种“赌运气”，你可以采取步骤修改你的工具，使其完全避免被检测。互联网上有许多教程讨论了如何修改二进制文件，使其与杀毒软件或入侵检测系统（IDS）的特征码不匹配。可能与本章最相关的标题为“夺回 Netcat（Taking Back Netcat）”，可以在网上找到：[`packetstormsecurity.org/papers/virus/Taking\_Back\_Netcat.pdf`](http://packetstormsecurity.org/papers/virus/Taking_Back_Netcat.pdf)。现在我们已经离开了明文的`netcat`反向隧道并改用加密的`SSH`隧道，我们可以更激进地向 Hackerdemia 服务器传输漏洞代码，而无必担心被入侵检测/防御系统检测到。这将增加我们在被攻系统上维持访问权限的时间，因为我们现在通过使用加密通信通道来避免网络检测。

# 其他加密和隧道方法

`SSH`并不是通信隧道加密的唯一方法。还存在一些使用不同加密类型的隧道应用程序。以下是使用各种加密和隧道方法的工具列表，它们可以替代本章中演示的方法。

## Cryptcat

与`netcat`类似，`cryptcat`可用于建立系统之间的通信通道，包括 Linux、Microsoft Windows 和多个伯克利标准发行版（BSD）。其区别在于`cryptcat`可以使用`twofish`加密算法加密通道，这是一种对称密钥块加密算法。要使用加密，两个系统必须拥有相同的密钥，这在设置`cryptcat`时需要额外的工作。

- 首页：[`cryptcat.sourceforge.net`](http://cryptcat.sourceforge.net)

## Matahari

`matahari`是一个用 Python 编写的反向超文本传输协议（HTTP）shell，它可以尝试以不同的间隔通过端口 80 连接到你的攻击系统；最快每 10 秒一次，最慢每 60 秒一次。`Matahari`使用`ARC4`加密算法加密系统之间的数据。`ARC4`现在是一个过时的加密方法，但在渗透测试环境中仍然有用。

- 首页：[`matahari.sourceforge.net`](http://matahari.sourceforge.net)

## Proxytunnel

这是一个同样通过 HTTP(S) 代理传输数据的有用工具。如果公司网络禁止除 HTTP(S) 连接外的所有出站通信，`Proxytunnel`可以创建一个通到我们攻击系统的`OpenSSH`隧道，为我们提供访问受害者服务器的 shell 权限。

- 首页：[`proxytunnel.sourceforge.net`](http://proxytunnel.sourceforge.net)

## Socat

与`netcat`类似，`socat`在服务器之间创建通信通道。与`netcat`不同，`socat`可以使用`OpenSSL`加密流量，允许额外的连接选项，例如使用`HTTPS`或`SSH`直接连接到端口。`Socat`通过允许用户派生进程、生成日志文件、打开和关闭文件、定义 IP 协议（`IPv4`或`IPv6`）以及管道数据增加了额外的灵活性。

- 首页：[`www.dest-unreach.org/socat/`](http://www.dest-unreach.org/socat/)

## Stunnel

该应用程序是一个 SSL 封装器——这意味着它可以用于加密仅发送明文数据的应用程序流量，而无需重新配置应用程序本身。明文数据的示例包括由邮局协议（POP）2、`POP3`、互联网邮件访问协议（IMAP）、简单邮件传输协议（SMTP）以及`HTTP`应用程序生成的任何内容。一旦配置`stunnel`加密数据通道，通过该端口的任何内容都将使用`SSL`加密。发送接收系统都需要`stunnel`，以便流量在传递给相应的应用程序之前还原为明文。

- 首页：[`stunnel.mirt.net/`](http://stunnel.mirt.net/)

这些隧道具有非常特定的应用，例如通过 HTTP(S) 代理建立隧道，而另一些则是`netcat`的加密版本。使用哪种应用程序取决于包含目标系统的网络架构和个人偏好。在使用任何加密方法之前，额外的考虑因素是被加密数据的敏感性以及攻击系统相对于受害者的位置。如果我们正在攻击一个系统并下载客户数据以证明破解是可能的，我们应该使用高级加密工具。所有提到的工具在在使用之前都需要额外的配置；如果通过通道发送的数据不敏感，或者我们在闭环网络中进行测试，那么设置加密隧道花费的时间可能更好地花在其他任务上。

# 总结

在渗透测试中使用后门至关重要，这样我们就能对受害者系统保持持续访问。我们最初对系统的破解可能会由于系统补丁或网络更改被阻止，导致我们在任何需要访问系统时无法利用它。通过安装使用反向 shell 的后门，我们可以规避阻止入站流量的防火墙，同时仍在目标网络内部继续渗透活动。开源工具`netcat`是一个可以在两个系统之间创建通信通道的有效应用程序。通过简单的脚本编写，`netcat`可以创建一个反向 shell，按我们选择的任何时间间隔连接回我们的攻击系统。使用`netcat`的缺点是我们的攻击服务器与受害者之间的所有通信都是明文发送的，这可能会被入侵防御系统识别并终止。为了避免检测，我们必须使用另一种通信模式——加密隧道。渗透测试人员有许多应用程序可用，可以在攻击系统和受害者服务器之间进行加密通信。通过理解网络，可以选择正确的工具来避免被可能监控基础设施中异常流量的网络安全工程师检测。

# 解决方案快速通道

## Shell 和反向 Shell

- 后门可以绕过所有防御，让渗透测试人员对被攻系统拥有不受限制的访问权限。
- 在内存中安装 shell 的缺点是如果系统重启，代理将丢失。
- 后门将继承启动`netcat`进程者的相同权限。
- 通过`netcat`通信连接发送的所有内容都是明文进行的——`netcat`不加密通信流。

## 加密隧道

- `SSH`隧道允许将恶意软件和额外的漏洞放置到受害者系统中，而不被网络检测系统发现，因为攻击系统和受害者之间的所有流量都是加密的。
- 根据攻击系统对目标服务器的可访问性，`SSH`隧道可以配置为直接 shell 或反向 shell。

用于跨代理和协议进行数据隧道的额外工具可能在所有操作系统上并不可用。即使底层通信协议不支持加密，也可以创建一个安全的隧道，从而隐藏原本可能被检测到的渗透测试活动。

**Q**：如果我没有服务器的权限，我该如何创建反向 shell？**A**：要向系统中创建后门，必须先利用目标系统。某些漏洞载荷（payloads）包含反向 shell，这使得本章的大部分内容变得意义；但是，在获得系统访问权限之前，创建后门只能等待。

**Q**：我该如何创建一个运行在内存中的后门，例如`CORE IMPACT`那样？**A**：问得好——我希望我也知道。虽然拥有内存中的后门会有帮助，但在专业的渗透测试中，让应用程序来处理后门通常比自己设置一个更明智。安装后门所需的时间通常花在其他活动上会更好。这是一个优先级问题——在大多数情况下，我直接让`CORE IMPACT`来处理一切。

**Q**：好吧，这没什么帮助——我真的需要一个运行在内存中的后门。**A**：你应该查看一下根内核程序（rootkits）。有些运行在内存中并提供远程连接。

**Q**：我应该对未加密的隧道有多担心？**A**：除了避免检测之外，加密隧道还能保护客户端的数据。在专业的渗透测试中使用加密数据是明智的选择。

# 第 14 章：隐藏踪迹

## 引言

Ночь все покрыват。 – 俄语谚语：*“黑夜掩盖一切。”* (Mertvago, 1995) 要完全成功利用一个系统，我们需要保持隐藏并避免检测。在游戏的这个阶段，我们已经成功避免了防火墙和入侵检测系统等网络防御设备的检测。我们的下一个挑战是在被利用的系统中避免检测。与网络防御相比，系统管理员使用类似的技术来识别恶意活动。系统管理员可以检查日志文件，安装监控恶意软件的应用程序，并设置查找未授权数据流的监控。管理员还可以查看系统上的进程，看是否有不适当的程序在运行（例如后门或暴力破解应用程序），并加固系统，以防止并警报核心系统文件内的任何更改。即使在成功利用目标系统后，渗透测试人员面临的挑战仍然有很多。在专业的渗透测试中，“隐藏踪迹”是一个不经常执行的步骤，但我们仍然会详细讨论，以便我们了解存在哪些障碍，这些障碍可能会阻止我们完全理解目标的安全态。

## 操纵日志数据

系统管理员监控恶意活动时使用的主要方法是检查日志文件。我们需要关注的日志文件有两种通用类型——系统生成的和应用程序生成的。我们正在做什么将决定我们需要关注哪种日志文件。在我们开始操纵日志文件之前，让我们讨论一下我们的最终目标——隐性。在操纵日志数据时我们有两种选择。我们可以删除整个日志，也可以修改日志文件的内容。如果我们删除日志，就能确保我们所有的活动都是不可追溯的。一旦日志文件从系统中删除，管理员在尝试重现他们在系统上的攻击时将面临极其困难。如果我们需要隐藏关于我们身份或来源的任何痕迹，这就是有利的。删除日志数据也有缺点——检测。当日志文件被删除时（尤其是系统日志文件），系统管理员很可能会注意到该事件。日志文件存在多个原因——检测恶意活动只是其中之一。管理员使用日志文件确定系统的状态和健康，如果服务器出现异常，会立即参考日志文件。如果日志文件突然消失或大小异常，系统管理员通常会怀疑恶意用户。我们操纵日志数据的第二个选择是更改日志中的数据。如果我们试图提升服务器的权限，一旦成功，我们可以移除日志中与我们的攻击相关的任何数据，这样当系统管理员检查日志文件时就不会发现我们的活动。更改日志文件也有缺点——我们可能没有获取全部，或者删除得太多导致日志中的空隙变得明显。

**警告** 系统管理员另一种防止恶意用户篡改日志文件的防御方法是远程日志服务器。如果系统管理员配置系统将所有日志传输到专门用于保留日志数据的远程服务器，除了关闭传输进程或攻击远程日志服务器外，我们做不了。如果我们切断日志传输，就有在日志服务器上触发报警的风险，这意味着我们被抓了……假设真的有人在看日志（不太可能）。
