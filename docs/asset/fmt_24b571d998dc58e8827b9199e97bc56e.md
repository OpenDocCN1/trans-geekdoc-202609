## 边界网络识别

在大型组织中，渗透测试期间，你经常会作为目标范围的一部分遇到非军事化区（DMZ）。从简单的定义来说，DMZ 通常是直接连接到互联网的网络，并在互联网和公司网络之间提供缓冲区。其核心思想是你需要弄清楚是否可以渗透 DMZ 的防御并突破到公司网络。渗透测试人员面临的问题在于识别你的目标网络从哪里开始，以及连接目标到互联网的基础设施在哪里结束。尽管这听起来很有道理，但实施起来要困难得多。你必须小心选择的目标系统，以免攻击了不属于你客户的系统。通常认为客户会为你提供他们控制的所有系统的 IP 地址，但出现疏漏并不罕见，例如系统被添加到网络中但没有更新记录。如果你发现了这些“被忽视”的系统，那么在打补丁方面它们也可能被忽视了，这可能会让你的网络利用工作变得容易得多。在图 9.25 中，我们看到了对目标系统——[Insecure.org](http://Insecure.org) 的`traceroute`结果。注意，有几个不同的域名我们需要进一步调查：`us.Above.net`和[sv.Svcolo.com](http://sv.Svcolo.com)。图 9.26 和 9.27 显示了`Above.net`和`Svcolo.com`的`whois`信息。我们就能发现这些系统并不属于[Insecure.org](http://Insecure.org)。如果我们进一步调查这些域名，会发现`Above.net`提供连接，而`Svcolo.com`提供服务。

如果我们仅仅对 IP 范围进行`ping`扫描，我们将会漏掉网络中的至少一个目标。这说明了使用多种工具进行扫描和攻击的必要性。如果你只使用你最喜欢的工具，你无法系统可能会如何反应。为了遵循我自己的建议，我也使用了`netdiscover`工具来寻找网络上的设备，如图 9.32 所示。

在项目的这一阶段，你应该已经分配至少一两个团队成员到项目中，他们能够成功执行信息收集阶段。他们的产出将对这一过程产生严重影响，因为团队成员需要根据目标网络的架构具备相应的技能。这可能基于目标系统使用的操作系统或网络中使用的通信协议。无论如何，他们的发现将要求构成最终团队的工程师具备专门技能，在完成此步骤并彻底识别目标系统之前，团队不应最终确定。

在规划阶段开发的的人员管理计划无疑会指导`Acquire Project Team`任务。然而，在此步中还应该发生额外的谈判和收购，以最好地确保项目的成功；如果需要使用虚拟团队，也可以对其进行管理。无论如何，利用信息收集阶段来帮助定义项目团队的最终的人员配置是重要的，而不仅仅仅仅为了满足某些任意的人头数而预先分配成员。如果你无法控制分配给团队的人员（我必须承认，这可能是常态），那么培训员工就成为项目团队开发任务的重要组成部分。自然，如果团队中有人精通目标网络架构涉及的任何技术将是最好的，但如果无法实现，则应该分配时间和资源进行培训。未能提供适当培训可能导致的缺陷是：目标系统或网络中的漏洞被忽视且未被记录。

## 请求卖家响应

如果你经历过那种罕见的时刻，即客户提供的文档与目标网络或系统完全匹配，那么我羡慕你。通常情况下，你认为要进行渗透测试的对象与你在该阶段结束时发现的内容之间存在差异，这要求你返回项目投标和建议书进行修改（或者在最坏的情况下，完全放弃该项目）。如果你有人负责招标过程（在此语境下称为卖家），那么这会让事情变得简单，因为作为项目经理，这部分工作从你手中抽离了出去。然而，通常的情况是项目经理被迫直接参与这一过程，因为他们本应该是对继续该项目所涉及的成本有更好理解的人。这不应是这样，但这就是现实。

无论如何，渗透测试此阶段的发现与项目状态（是按原计划进行、修改、放弃还是重新调整优先级）之间应该存在相关性。如果该项目完全局限在组织内部，成本仍然是一个因素，信息收集阶段将帮助定义这些成本。如果成本预算受到限制，此阶段最可能只会影响项目的优先顺序排序。

## 监控和控制过程

如前所述，监控和控制过程是一个持续的过程，涵盖项目的所有其他阶段。在信息收集阶段，相关性最大的项目管理过程是`Scope Verification`、`Scope Control`、`Schedule Control`和`Cost Control`。这并不意味着其他过程（如`Manage Project Team`、`Manage Stakeholders`、`Performance Reporting`等是不重要的——只是这四个过程在渗透测试的这一阶段影响最大，也是我们在本章中将讨论的内容。

### 范围验证

在渗透测试信息收集阶段结束时，项目经理应该能够对项目的未来表现`request changes`并`recommend corrective actions`。根据此阶段的发现，对项目范围的变更请求可能是相当重大的，特别是当目标系统或网络比客户最初呈现的要复杂或多样得多时。根据 PMBOK，`Scope Verification`的唯一推荐工具是`Inspection`。这可能涉及评审和审计，这些方法往往是最有效的。范围验证中评审的关键在于包含领域专家。

### 范围控制

在此阶段，范围蔓延是一个真实的威胁，可能会对项目的整体成功产生负面影响。在信息收集阶段结束时，会有额外的区域可以纳入渗透测试项目中。使用`Integrated Change Control`过程进行适当的变更管理可能是控制此类项目范围蔓延的最佳方式。范围变更是否必要或合适显然涉及相关利益相关者的大量投入，但如果是在`Integrated Change Control`过程的背景下进行的，成本可以得到更好的控制，对范围的任何影响也可以更有效地进行沟通。

### 进度控制

希望在信息收集阶段结束时，你不需要对项目进度表进行任何更改。人员配置肯定会有一些调整，但只有当预期内容与目标网络中实际存在的内容存在显著差异，且范围经过了修改以反映这些差异时，项目时间线本身才会发生变化。如果进度缺乏活性，可以实施几种可选方案：更改人员配置、修改范围或压缩`WBS`。遗憾的是，当时间线无法修改时，受影响的通常是`WBS`。这在渗透测试中通常是最糟糕的选项，因为`WBS`的收缩通常意味着增加额外任务并夺取其他任务的时间来补偿。最终结果是所有任务的执行效率都低于最佳水平。正如本书前面提到的，识别漏洞和创建破坏系统的利用程序通常非常耗费时间，因为大多数攻利用手段并不总是随手可得。作为处理渗透测试项目的项目经理，在修改`WBS`之前，修改范围或人员配置通常对项目的成功更有利。

### 成本控制
