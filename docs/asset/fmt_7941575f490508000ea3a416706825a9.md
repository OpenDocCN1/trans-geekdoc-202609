# 11. 测试

EDSAC（第一台存储程序计算机）的开发者 Maurice Wilkes，于 1949 年在爬实验室楼梯时有了一个惊人的感悟。他在《计算机先驱回忆录》中回忆道：“我充分意识到，我余生的大部分时间将花在寻找自己程序中的错误上。”自那以后，每一位存储程序计算机的程序员都能对 Wilkes 产生共鸣，尽管或许会对他对软件构建困难的天真感到一丝愉快的惊讶。

当然，如今的程序比 Wilkes 时代的要大得多、复杂得多，人们投入了大量精力研究使这种复杂性可控的技术。有两种技术因其有效性而脱颖而出。第一种是在部署前对程序进行例行同行评审。第二种是本章的主题：测试。

测试，在此我们隐含指*自动化*测试，是编写小程序检查被测代码（即*生产*代码）对于特定输入是否表现出预期行为的实践。这些输入通常是经过精心挑选以测试特定功能，或是随机生成以确保广泛覆盖。

软件测试领域极其庞大。测试任务占据了所有程序员的一部分时间，以及部分程序员的全部时间。关于测试的文献包括数千本印刷书籍和数百万字的博客文章。在每一种主流编程语言中，都有数十个用于构建测试的软件包，其中一些包含大量理论，而且该领域似乎吸引了不少拥有邪教般追随者的“先知”。这几乎足以让程序员相信，要编写有效的测试，他们必须掌握一套全新的技能。

相比之下，Go 的测试方法显得相当“低技术含量”。它依赖一个命令 `go test`，以及一套 `go test` 可运行的测试函数编写约定。这种相对轻量级的机制对纯测试很有效，并能自然扩展到基准测试和用于文档的系统化示例。

实际上，编写测试代码与编写原始程序本身差别不大。我们编写关注任务某一部分的短函数。我们必须小心边界条件，思考数据结构，并推断合适的输入应产生什么计算结果。但这与编写普通 Go 代码的过程相同；它不需要新的符号、约定和工具。

## 11.1 `go test` 工具

`go test` 子命令是针对按照特定约定组织的 Go 包的测试驱动程序。在包目录中，文件名以 `_test.go` 结尾的文件通常不是由 `go build` 构建的包的一部分，但由 `go test` 构建时是其中的一部分。

在 `*_test.go` 文件中，有三种函数受到特殊对待：测试、基准测试和示例。*测试函数*是以 `Test` 开头的函数，用于验证某些程序逻辑的正确行为；`go test` 调用测试函数并报告结果，即 `PASS` 或 `FAIL`。*基准测试函数*以 `Benchmark` 开头，用于衡量某项操作的性能；`go test` 报告该操作的平均执行时间。*示例函数*以 `Example` 开头，提供机器可验证的文档。我们将在 11.2 节 详细介绍测试，在 11.4 节 介绍基准测试，在 11.6 节 介绍示例。

`go test` 工具扫描 `*_test.go` 文件查找这些特殊函数，生成一个调用它们的临时 `main` 包，构建并运行它，报告结果，然后清理现场。

## 11.2 `Test` 函数

每个测试文件必须导入 `testing` 包。测试函数具有以下签名：

```
func TestName(t *testing.T) {
    // ...
}
```

测试函数名必须以 `Test` 开头；可选的后缀 `Name` 必须以大写字母开头：

```
func TestSin(t *testing.T) { /* ... */ }
func TestCos(t *testing.T) { /* ... */ }
func TestLog(t *testing.T) { /* ... */ }
```

参数 `t` 提供了报告测试失败和记录额外信息的方法。让我们定义一个示例包 `gopl.io/ch11/word1`，其中包含单个函数 `IsPalindrome`，用于判断字符串正读反读是否相同。（如果字符串是回文，此实现会测试每个字节两次；稍后我们会回到这个问题。）

`gopl.io/ch11/word1`

```
// Package word provides utilities for word games.
package word

// IsPalindrome reports whether s reads the same forward and backward.
// (Our first attempt.)
func IsPalindrome(s string) bool {
    for i := range s {
        if s[i] != s[len(s)-1-i] {
            return false
        }
    }
    return true
}
```

在同一目录下，文件 `word_test.go` 包含两个名为 `TestPalindrome` 和 `TestNonPalindrome` 的测试函数。每个函数检查 `IsPalindrome` 对单个输入是否给出正确答案，并使用 `t.Error` 报告失败：

```
package word

import "testing"

func TestPalindrome(t *testing.T) {
    if !IsPalindrome("detartrated") {
        t.Error(`IsPalindrome("detartrated") = false`)
    }
    if !IsPalindrome("kayak") {
        t.Error(`IsPalindrome("kayak") = false`)
    }
}

func TestNonPalindrome(t *testing.T) {
    if IsPalindrome("palindrome") {
        t.Error(`IsPalindrome("palindrome") = true`)
    }
}
```

不带包参数的 `go test`（或 `go build`）命令作用于当前目录下的包。我们可以使用以下命令构建并运行测试。

```
$ cd $GOPATH/src/gopl.io/ch11/word1
$ go test
ok   gopl.io/ch11/word1  0.008s
```

我们很满意，于是发布了程序，但发布会的客人刚走，Bug 报告就开始陆续到来。一位名叫 Noelle Eve Elleon 的法国用户抱怨 `IsPalindrome` 无法识别“été”。另一位来自中美洲的用户失望地发现它拒绝了“A man, a plan, a canal: Panama”。这些具体且微小的 Bug 报告自然适合转化为新的测试用例。

```
func TestFrenchPalindrome(t *testing.T) {
    if !IsPalindrome("été") {
        t.Error(`IsPalindrome("été") = false`)
    }
}

func TestCanalPalindrome(t *testing.T) {
    input := "A man, a plan, a canal: Panama"
    if !IsPalindrome(input) {
        t.Errorf(`IsPalindrome(%q) = false`, input)
    }
}
```

为了避免编写两次冗长的 `input` 字符串，我们使用了 `Errorf`，它提供类似 `Printf` 的格式化功能。

添加这两个新测试后，`go test` 命令失败并给出了信息丰富的错误消息。

```
$ go test
--- FAIL: TestFrenchPalindrome (0.00s)
    word_test.go:28: IsPalindrome("été") = false
--- FAIL: TestCanalPalindrome (0.00s)
    word_test.go:35: IsPalindrome("A man, a plan, a canal: Panama") = false
FAIL
FAIL    gopl.io/ch11/word1  0.014s
```

先编写测试并观察其触发与用户 Bug 报告中描述的相同失败，这是一种良好的实践。只有那样，我们才能确信我们想出的任何修复都解决了正确的问题。

作为额外收获，运行 `go test` 通常比手动执行 Bug 报告中描述的步骤更快，使我们能够更快地迭代。如果测试套件包含许多慢速测试，我们通过有选择地运行测试可能会取得更快的进展。

`-v` 标志会打印包中每个测试的名称和执行时间：

```
$ go test -v
=== RUN TestPalindrome
--- PASS: TestPalindrome (0.00s)
=== RUN TestNonPalindrome
--- PASS: TestNonPalindrome (0.00s)
=== RUN TestFrenchPalindrome
--- FAIL: TestFrenchPalindrome (0.00s)
    word_test.go:28: IsPalindrome("été") = false
=== RUN TestCanalPalindrome
--- FAIL: TestCanalPalindrome (0.00s)
    word_test.go:35: IsPalindrome("A man, a plan, a canal: Panama") = false
FAIL
exit status 1
FAIL    gopl.io/ch11/word1  0.017s
```

而 `-run` 标志的参数是一个正则表达式，它使 `go test` 仅运行函数名匹配该模式的测试：

```
$ go test -v -run="French|Canal"
=== RUN TestFrenchPalindrome
--- FAIL: TestFrenchPalindrome (0.00s)
    word_test.go:28: IsPalindrome("été") = false
=== RUN TestCanalPalindrome
--- FAIL: TestCanalPalindrome (0.00s)
    word_test.go:35: IsPalindrome("A man, a plan, a canal: Panama") = false
FAIL
exit status 1
FAIL    gopl.io/ch11/word1  0.014s
```

当然，一旦我们让选定的测试通过，在提交更改前，我们应该不带标志调用 `go test` 最后一次运行整个测试套件。

现在我们的任务是修复 Bug。快速调查揭示了第一个 Bug 的原因：`IsPalindrome` 使用的是字节序列，而非符文序列，因此像 `"été"` 中的 é 这样的非 ASCII 字符会使其困惑。第二个 Bug 则源于未忽略空格、标点和字母大小写。

吸取教训后，我们更仔细地重写了该函数：

`gopl.io/ch11/word2`

```
// Package word provides utilities for word games.
package word

import "unicode"

// IsPalindrome reports whether s reads the same forward and backward.
// Letter case is ignored, as are non-letters.
func IsPalindrome(s string) bool {
    var letters []rune
    for _, r := range s {
        if unicode.IsLetter(r) {
            letters = append(letters, unicode.ToLower(r))
        }
    }
    for i := range letters {
        if letters[i] != letters[len(letters)-1-i] {
            return false
        }
    }
    return true
}
```

我们还编写了一组更全面的测试用例，将所有之前的用例和许多新用例合并到一个表中。

```
func TestIsPalindrome(t *testing.T) {
    var tests = []struct {
        input string
        want  bool
    }{
        {"", true},
        {"a", true},
        {"aa", true},
        {"ab", false},
        {"kayak", true},
        {"detartrated", true},
        {"A man, a plan, a canal: Panama", true},
        {"Evil I did dwell; lewd did I live.", true},
        {"Able was I ere I saw Elba", true},
        {"été", true},
        {"Et se resservir, ivresse reste.", true},
        {"palindrome", false}, // 非回文
        {"desserts", false},   // 半回文
    }
    for _, test := range tests {
        if got := IsPalindrome(test.input); got != test.want {
            t.Errorf("IsPalindrome(%q) = %v", test.input, got)
        }
    }
}
```
