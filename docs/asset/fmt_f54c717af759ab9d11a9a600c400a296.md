
# 统一建模语言 (UML) 的迅速崛起

统一建模语言 (UML) 的迅速崛起伴随着这样的声称：UML 本身就是对任何软件应用进行建模的充分方法。一些 UML 支持者甚至大胆声称“建模战争已经结束——UML 获胜了”。这一说法遭到包括 Dave Hay 在内的多位经验丰富的数据建模师的强烈反对，他认为“根本不存在‘面向对象分析’这回事”(Hay, 1999a)，只有面向对象设计，并且“UML ……不适合与业务人员合作分析业务需求”(Hay, 1999b)。

迄今为止，UML 在工业界主要用于设计面向对象的程序代码。虽然它可用于设计数据库，但 UML 迄今为止在取代实体-联系 (ER) 建模等其他方法用于此目的方面鲜有建树。考虑到 UML 的面向对象焦点以及关系数据库管理系统 (DBMS) 的主导地位，这或许并不令人惊讶。尽管如此，UML 是一门非常重要的语言，未来很可能在数据库设计中流行起来。

UML 基于 Booch 对象建模技术 (OMT) 和面向对象软件工程 (OOSE) 方法的结合，由在对象管理组 (OMG) 内工作的公司和个人联盟进一步开发。它包含许多其他技术的改编（例如 Harel 状态图）。

UML 1.1 版于 1997 年被 OMG 采纳为面向对象分析和设计语言，后来被国际标准化组织 (ISO) 接受为标准。一个主要修订版 (2.0) 于 2005 年被 ISO 采纳，包含基础设施和超结构规范，以及对象约束语言 (OCL) 和图表交换的相关规范。2017 年，UML 2 更新至 2.5.1 版^(¹⁰)。

正如稍后讨论的那样，UML 元模型和符号存在不一致之处，有些未解决的问题具有根本性。尽管存在这些问题，UML 是工业界面向对象软件设计中最接近事实标准的语言，因此值得研究。

UML 符号实际上是一组语言，而非单一语言。它包含大量符号，可用于构建各种图表，从不同视角对应用程序建模。UML 1.5 中的九种主要图表类型包括：用例（用例图）；静态结构（类图、对象图）；行为（状态图、活动图）；交互（顺序图、协作图）；以及实现（构件图、部署图）。UML 2 将这些扩展为 13 种图表类型，如表 9.1 所示。

其中一些图表（例如协作图）仅用于设计面向对象程序代码。一些（例如活动图和用例图）可用于需求分析，而一些（例如类图）在概念分析中用途有限，最适合用于逻辑设计。

UML 规范为这些图类型提供了语法和语义，但尚未提供开发 UML 模型的过程，只是建议模型开发应以用例为驱动、迭代进行且以架构为中心。各家公司都在推广其自己的 UML 建模过程。

尽管所有 UML 图类型都值得研究，但本书主要关注数据库的信息建模。本章讨论 UML 中的数据建模，因此仅考虑静态结构（类和对象）图。类图用于数据模式。对象图提供了有限的手段来讨论数据实例。其他一些 UML 图类型将在第 15 章中讨论。

与 ER 一样，UML 也使用属性。正如前几章所讨论的，属性非常适合逻辑模型，但在进行概念分析时，最好将其建模为关系，因为这有助于验证并最小化变更的影响。基于这些原因，我们认为开发 UML 数据模型的最佳方式是先进行对象角色建模（ORM），然后将其映射到 UML。因为将使用 ORM 来阐明 UML 中的数据建模概念，为了充分获得这种阐明的益处，你应该熟悉前几章涵盖的 ORM 概念。

没有任何语言是完美的，ORM 也不例外。总体而言，UML 为数据和过程建模提供了一套有用的符号，而 ORM 目前仅专注于数据建模。

## 9.2 面向对象

UML 促进了面向对象（OO）代码设计，因为它涵盖了数据和行为建模，并允许你深入到与 OO 代码相关的物理设计细节。图 9.2 中的类图对一个类进行建模，其实例是屏幕对话框。

![图 9.2 UML 类示例。](img/f09-02-9780443237904.jpg)

图 9.2 UML 类示例。

图 9.2 中的类形状有三个区间。名称区间包含类名以及一个标记了类作者的标签值。属性区间列出了每个属性的可见性、名称和类型。可见性设置 `+`、`-`、`#` 和 `~` 分别表示属性是公共、私有、受保护还是包级的。这些可见性设置是软件层面的问题，而非概念层面的问题。`size` 属性被初始化为给定的面积值。操作区间指定了封装在类实例中的操作。在本例中，这些操作可通过方法实现，以在特定位置显示对话框并隐藏对话框。

图 9.3 展示了另一个类图，描绘了 `Employee` 和 `Car` 类以及对应 ORM 事实类型 `Employee drives Car`（员工驾驶汽车）的一个关联。关联由类之间的一条线表示。关联左端的角色名 `driver` 阐明了预期语义（也可提供关联读法）。关联右端的空心箭头是一个可导航性设置，指示需要从员工实例快速访问其汽车实例。这可以通过在员工对象（软件对象）中包含指向汽车对象的指针来实现，这些汽车对象建模了他们驾驶的汽车。可导航性设置是与性能相关的实现问题，而非关于业务领域的概念问题。

![图 9.3 可导航性设置要求从 Employee 到 Car 的快速访问。](img/f09-03-9780443237904.jpg)

图 9.3 可导航性设置要求从 Employee 到 Car 的快速访问。

通过省略属性可见性和关联可导航性等实现细节，类图可用于概念分析。以这种方式使用时，类图在一定程度上类似于 ER 模型。但由于 OO 视角的存在，两者有显著差异。如果你看看图 9.2 和 9.3 中的类，你会发现缺少了什么？

你猜对了！没有为类提供标识方案。在面向对象编程中，对象可以通过其内存地址或内部对象标识符（oid）来识别，因此 UML 不要求基于值的标识方案供人类在交流对象时使用。然而，对于概念分析，必须提供面向人类的引用方案（例如，对话框编号、员工编号、汽车注册号）。

为了部分解决此问题，UML 2.5 现在允许你通过在属性名称后附加 `{id}`，将一个属性（例如属性或关联端）标记为其所在类的 `identifier`（标识符）或标识符的一部分。然而，UML 没有标准符号来声明单值属性为备用标识符，甚至没有标准符号来声明其为唯一。

本书使用 `{U*n*}` 表示唯一性（*n* > 0），其中 *n* 用于消除同一唯一性约束可能适用于属性组合的情况的歧义。例如在图 9.4 中，员工编号和汽车注册号属性分别被标记为员工和汽车的主标识符。这意味着它们是强制且唯一的。此外，员工姓名和出生日期的组合也被声明为唯一。我们还去掉了导航箭头，因为它与业务语义无关。

![图 9.4 添加标识符和唯一性的符号。](img/f09-04-9780443237904.jpg)

图 9.4 添加标识符和唯一性的符号。

每个类*必须*拥有基于值的标识方案这一要求，将 ORM 和 ER 与 UML 区分开来。ORM 将对象分为实体（非词法对象）和值（词法对象），并要求每个实体都必须通过人类用于交流的引用方案来识别。ORM 使用 `object`、`entity` 和 `value` 分别表示 `object instance`（对象实例）、`entity instance`（实体实例）和 `value instance`（值实例），并加上 `type` 后缀表示相关的所有可能实例的集合。实体可以通过不同方式引用，且通常会随时间改变状态。略过一些微妙之处，值是常量（例如字符串），它们表示自身，因此不需要引用方案。

图 9.5(a) 在 ORM 中显式描绘了一个简单的引用方案。如果一个实体类型有多个候选引用方案，可以将其中一个声明为首选。实体类型的首选引用方案将其每个实例映射到一个唯一的标识值（或值的组合）。在图 9.5(a) 中，引用类型在引用表中显示了一个样本实例（每个角色一列）。此处，图标用于表示现实世界的员工实体。

![图 9.5 ORM 中的一个简单引用方案，（a）显式显示和（b）隐式显示。](img/f09-05-9780443237904.jpg)

图 9.5 ORM 中的一个简单引用方案，（a）显式显示和（b）隐式显示。

简单引用方案可通过将引用模式置于括号中来缩写，如图 9.5(b)所示，且对象类型的引用表包含值但无图标。引用可口语化为存在句，例如“存在一个员工，其员工编号为 101”。实体实例在其他地方通过确定性描述引用，例如“员工编号为 101 的那个员工”。

在关系数据库中，我们可能使用首选引用方案提供基于值的标识，或改用系统生成的行 ID。在面向对象实现中，我们可能使用 OID（隐藏的、系统生成的对象标识符）。此类选择可稍后作为注解添加到模型中。然而，为分析和验证目的，我们需要确保人类有办法在正常交流中识别对象。由人类（而非系统）负责强制执行首选引用类型上的约束。假设人类确实强制执行引用类型约束，则系统可用于强制执行基本事实类型约束。

UML 将实例分类为对象和数据值。UML *对象*基本对应 ORM 实体，但假定由 OID 标识。尽管 UML 不要求实体具有基于值的引用方案，但我们应在任何 UML 类中包含基于值的引用，以捕获所有概念语义。UML *数据值*基本对应 ORM 值：它们是常量（如字符串或数字），因此无需 OID 即可确立其标识。UML 中的实体类型称为 *类*，值类型基本为 *数据类型*。注意，“对象”指“对象实例”，而非“对象类型”。UML 中的关系实例称为 *链接*，关系类型称为 *关联*。

## 9.3 属性

与其他 ER 表示法一样，UML 允许将关系建模为属性。例如，在图 9.6(a)中，`Employee` 类有八个属性。对应的 ORM 图如图 9.6(b)所示。

![图 9.6 UML 属性 (a) 描绘为 ORM 关系类型 (b)。](img/f09-06-9780443237904.jpg)

图 9.6 UML 属性 (a) 描绘为 ORM 关系类型 (b)。

在 UML 中，*属性默认是强制且单值的*。因此员工编号、姓名、职称、性别和吸烟状态属性均为强制。在 ORM 模型中，一元谓词“吸烟”是可选的（并非每个人都必须吸烟）。UML 不支持一元关系，因此将其建模为取值为 True 或 False 的布尔属性“isSmoker”。在 UML 中，任何属性的域（即类型）可选择在其后显示（前面加冒号）。本例中仅为 `isSmoker` 属性显示了域。默认情况下，ORM 工具通常对一元谓词采用封闭世界假设（CWA），这与 `isSmoker` 属性为强制一致。

ORM 模型还表明 `Gender` 和 `Country` 由代码标识。我们可在 UML 图中追加域名以传达部分细节，例如可在“birthcountry”后追加“Countrycode”。

在 ORM 模型中，是否记录 `birthcountry`、社会安全号或护照号是 *可选* 的。这在 UML 中通过在属性名后追加 `[0..1]` 来体现（每位员工有 0 或 1 个出生国，0 或 1 个社会安全号）。这是 *属性多重性约束* 的一个示例。主要多重性情况见表 9.2。若未显式声明多重性，则假定为 1（恰好一个）。如有需要，可通过追加 `[1..1]` 或 `[1]` 显式指示默认多重性。

在 ORM 模型中，右侧角色上的唯一性约束（包括前面显式显示的 `EmployeeNr` 引用方案）表明每个员工编号、社会安全号和护照号最多指向一名员工。UML 没有此类 “*属性唯一性约束*” 的标准表示法，因此我们使用了 `{U*n*}` 表示法。UML 2 增加了在多重性声明中指定 `{unique}` 或 `{nonunique}` 的选项，但这仅用于声明多值属性或多值关联角色的集合实例是否可包含重复项，因此不能用于指定单值属性的实例或此类属性的组合在类中是唯一的。

UML 没有包含或约束的图形表示法，因此 ORM 约束“每位员工有社会安全号或护照号”需在附加的 *注释* 中用文本表达，如图 9.6(a)所示。此类 *文本约束* 可非正式表达，或用工具可解释的某种形式语言表达。后一种情况下，约束置于 *大括号* 中。

本例中，我们选择用 SQL 语法编码包含或约束。尽管 UML 提供了 OCL 为此目的服务，但不强制使用，允许用户自选语言（甚至编程代码）。这当然削弱了模型的可移植性。此外，与 ORM 口语化相比，此类约束的可读性通常较差。

ORM 事实类型“员工出生于国家”在图 9.6(a)的 UML 类图中建模为 `birthcountry` 属性。若后来决定记录国家人口，则需引入 `Country` 类，并为阐明 `birthcountry` 与 `Country` 的联系，可能会将 `birthcountry` 属性重构为 `Employee` 与 `Country` 之间的关联。这会对模型造成重大变更。此外，任何引用 `birthcountry` 属性的基于对象的查询或代码也需重构。ORM 通过始终使用关系而非属性，避免了此类语义不稳定性。

引入 `Country` 类的另一原因是存储国家列表，而不要求所有国家都参与某个事实。在 ORM 中，只需声明 `Country` 类型为独立即可。对象类型 `Country` 可由包含相关国家代码的引用表填充（例如“AU”代表澳大利亚）。

支持属性的典型论点如下：“优秀的 UML 建模者一开始就会将 country 声明为类，预见到以后可能需要记录关于它的信息，或维护参考列表”。此论点有缺陷。一般而言，你无法确定以后可能想记录何种信息，也无法确定某模型特性会变得多重要。

即使在职称和性别情况下，完整模型也应包含关系类型以指示哪些职称限于哪个性别（如“Mrs”、“Miss”、“Ms”、“Lady”仅适用于女性）。在 ORM 中，此类约束可图形化为连接子集约束，或用正式 ORM 语言以文本形式表达为约束（例如 `If Person[1] has a Title that is restricted to Gender[1] then Person[1] is of Gender[1]`）。相反，属性用法妨碍了相关限制关联的表达（尝试在 UML 中表达并填充此规则）。

ORM 包含用于动态生成 ER 和 UML 图作为属性视图的算法。这些算法根据对象类型当前的角色和约束为其分配不同的重要性级别，将次要事实类型重新显示为主要对象类型的属性。建模和维护是迭代过程。随着我们发现更多的全局模型，以及被建模的领域本身发生变化，某个特性的重要性可能会随时间改变。

为了促进语义稳定性，ORM 在其基础模型中不对相对重要性做出承诺，而是通过视图动态支持这一点。基本事实是信息的基本单位，统一表示为关系，它们如何分组到结构中并非概念问题。您可以使用 ORM 进行分析，如果想使用 UML 类图，可以从 ORM 模型派生它们。

在 UML 中建模“员工可能从事多项运动”的一种方式如图 9.7(a)所示。此处，关于谁从事什么运动的信息被建模为*多值属性*“sports”。该属性上的“\[0..\*]”多重性约束指示每个员工可录入多少项运动。“0”表示某些员工可能没有录入运动。UML 对此情况使用*空值*，就像关系模型一样。空值的存在使用户面临实现问题而非概念问题，并增加了查询语义的复杂性。“\[0..\*]”中的“\*”表示单个员工的运动数量*没有上限*。换句话说，员工可能从事多项运动，我们不关心具体有多少。如果“\*”使用时未指定下限，这被视为“0..\*”的缩写。

对于这种简单情况，对象图很有用。然而，如果我们希望为更复杂的情况显示多个实例，它们会迅速变得难以驾驭。相比之下，事实表可轻松扩展以处理大型复杂情况。

ORM 约束可通过样本种群轻松阐明。例如，在图 9.8(b)中，Plays 事实表中缺少员工 101 表明从事运动是可选的，唯一性约束标记出哪个列或列组合的值最多只能出现在一行上。在 EmployeeName 事实表中，第一列的值是唯一的，但第二列包含重复项。在 Plays 表中，每列都包含重复项，因为只有整行是唯一的。此类种群对于与主题专家一起检查约束很有用。ORM 的这种通过示例验证的特性适用于其所有约束，而不仅仅是强制角色和唯一性，因为其所有约束都是基于角色或基于类型的，且每个角色对应一个事实表列。

作为多值属性的最后一个示例，假设我们希望记录国家旗帜的昵称和颜色。我们约定最多为任何给定旗帜记录两个昵称，且昵称仅适用于一面旗帜。例如，“Old Glory” 和 “The Star-Spangled Banner” 可能用作美国国旗的昵称。旗帜至少有一种颜色。

图 9.9(a) 显示了在 UML 中建模此问题的一种方式。“\[0..2\]”表示每面旗帜最多有两个（从零到两个）昵称。“\[1..\*]”声明旗帜有一种或多种颜色。需要额外的约束来确保每个昵称最多指代一面旗帜。简单的属性唯一性约束（例如 {U1}）是不够的，因为 nicknames 属性是集合值的。不仅每个旗帜的 nicknames 集合必须唯一，而且每个集合中的每个元素也必须唯一（后一条件蕴含前一条件）。这种更复杂的约束在附带的注释中非正式地指定。
