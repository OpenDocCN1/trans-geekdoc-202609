
## CA 签发证书流程

*   CA 进行检查以确保 Alice 就是她声称的人；
*   CA 然后使用 CA 的私钥签署并生成证书。

### 证书的四个主要组成部分

1.  足够的信息来可靠地识别 Alice，通过提供她的全名和其他个人细节；
2.  Alice 公钥的副本；
3.  一个到期日期，超过该日期证书将不再有效；
4.  使用 CA 私钥创建的数字签名。

实际上，CA 可能选择通过对 (1) 至 (3) 的内容进行哈希，然后对哈希进行签名来签署证书。这与签署整个证书一样安全，并且具有将证书中所有重要信息保留为明文的优点。CA 也可能承诺为 Alice 生成她的密钥对，但理想情况下 Alice 应该独立完成，以确保只有她自己拥有私钥副本。

Alice 现在可以将已签名的证书副本传递给任何需要它的人。例如，Bob 在获得 CA 广泛宣传的公钥后，使用它来检查 Alice 证书副本上的签名。一旦他知道 Alice 的密钥获得了 CA 的“认可印章”，Bob 就可以更有信心地使用它来与 Alice 建立通信。

## 优秀 CA 应提供的持续服务

一个好的认证机构做的不仅仅是签署证书。事实上，如果这就是 CA 所提供的一切，其价值有限。它还应提供一系列持续服务，包括：

*   **证书吊销**。有时可能需要取消证书。例如，这可能是因为证书是为某人与其雇佣相关的而签发的，并且个人细节中包含对工作状态的引用。证书不能像实体卡或令牌一样在员工离职时“上交”。相反，CA 必须维护一份所有已取消证书的清单，并使其可供任何希望检查的人使用。理想情况下，这应是一个在线设施，也许可通过互联网访问。
*   **Legal liability**。证书旨在传达一种保证，即密钥与其使用者之间存在关联，并且是真实的。因此，CA 应对其所签署的信息的准确性承担一定责任。但这绝非总是如此。一些“CA”宣传的证书在申请人的背景上完全不做任何核查。来自此类来源的证书完全一文不值（有点像伪造大学学位的证书，可以通过邮件花 5 美元订购）。即使那些*确实*进行合理核查的 CA，通常也会通过法律免责声明来保护自己，这些免责声明可以严格限制其责任。
*   **Security within the CA**。CA 的私钥必须始终完全安全。任何获得该密钥的人都可以伪造新证书，并破坏所有现有证书的可信度。

这一系列要求，其中 CA 签名过程只是其中一部分，定义了应包含在适当的 `Public Key Infrastructure` 中的内容。PKI 涵盖了为可靠地分配和分发公钥所需的所有服务和设施。良好的 PKI 将提供管理良好且用户方便的设施，并且能够满足任何特殊需求（例如，为个人发放的密钥和为整个部门或组织发放的“企业”密钥提供混合支持（Dam and Lin 1996））。更复杂的 PKI 利用智能卡和其他附加技术来帮助密钥分发和管理。

### 三种主要密钥分发方法摘要 (Table 7.1)

| Method | Characteristics | Suitable for |
| :--- | :--- | :--- |
| Key Distribution Centre | Centralised; sets up symmetric key for each session | Large bounded group |
| Web of trust | Dispersed and informal; distribution of public (asymmetric) keys | Small ad hoc group |
| Public Key Infrastructure | Dispersed and formal; distribution of public (asymmetric) keys | Large unbounded group |

针对这些方法设计了许多变体。其中一些（如 `Kerberos` 身份验证系统）扩展了 KDC 的功能，通过生成“票据”来定义网络机器上要为每个用户开放的设施（Kaufman *et al* 1995）。应注意的是，无论多么复杂，*所有*此类身份验证系统最终都 crucially 依赖于设置时对用户身份进行的核查质量。

## 7.4 密钥存储、托管与恢复

经常使用密码学的企业应考虑出现问题时的情况。常见的一个例子是文本已成功加密，无论是由企业本身还是其交易伙伴加密，但用于解密的密钥却丢失或损坏。

如果企业已向所有客户发送了其公钥，而此时才发现丢失了至关重要的私钥，这就尤其尴尬。它现在将无法读取传入消息，也无法对消息进行数字签名。如果对称密钥在企业内部被广泛使用，特别是如果它已被用于加密已归档的数据，则对称密钥的丢失也会产生类似的毁灭性影响。

所有这些情况都需要某种获取“备用”密钥的程序。企业无法设法“重新创建”其密钥——如果可以的话，这将使任何潜在攻击者的工作变得太容易。有两种基本方法，可以与人们为备用前门或汽车钥匙所做的安排进行比较。最简单的解决方案是复制密钥并交给他人妥善保管。或者，最初提供密钥的公司可能能够在适当的安全措施下重新创建它（例如，丢失密钥的所有者可能需要提供与密钥关联的唯一参考号）。

任何密钥的重复副本最好保存在远离原件的地方。如果副本保存在同一系统中，就有危险会遭受与原始密钥相同的命运（例如，被病毒攻击清除）。将其放在不同的系统上，或放在锁在保险箱中的软盘上，也会让可能对它感兴趣的任何黑客的生活变得特别困难。按照惯例，企业自行安排的任何此类安排都被称为 `key recovery`。

外部机构可能被委托持有密钥的副本。如果密钥所有者要求这样做，这只不过是“外包”密钥恢复。然而，有时存在强制性因素。当有法律义务向外部机构——通常是负责监管或执法工作的机构——提供密钥副本时，这就被称为 `key escrow`。“Escrow”一词借自法律，简单地意味着独立第三方保管资产。

### 为什么当局对密钥托管感兴趣？

在世界各地，随着越来越多的商业活动以电子方式进行，政府越来越担心其监控通信的能力。迄今为止，官方窃听几乎没有遇到 `technical` 问题。在法治健全的国家，通常会有立法限制允许进行此类拦截的情况。然而，现代密码学发展的一个后果是，这种情况被颠倒了过来。随着越来越多的流量被加密，即使法律允许，政府在读取这些流量时也面临巨大的技术问题。因此，他们一直在寻找使自己能够获取所需任何密码密钥的方法。他们提出的理由通常集中在追踪涉嫌与毒品贩运或洗钱有关的资金转移，以及调查逃税和欺诈的需要。一些不太友好的批评者则认为，政府可能还发展出了对其他国家企业的商业间谍活动的兴趣（Anon 1999a）。

### 密钥托管的历史争议

这一领域的首次重大辩论始于 1994 年，当时美国政府引入了“托管加密标准”。该标准将体现在“Clipper 芯片”中。这些大批量生产的逻辑芯片将被纳入所有加密产品中，并将为其所有者提供高度安全的加密 *但* 带有所谓的执法访问字段。LEAF 不会直接透露加密密钥，但官员可以通过将 LEAF 与其他政府持有信息结合来计算出密钥。因此，LEAF 就像汽车钥匙上的参考号一样发挥作用（Dam and Lin 1996）。企业和公民自由主义者一致对该提案提出强烈反对，最终该提案被撤回（Diffie and Landau 1998）。Clipper 方法无论如何都会存在一些实际限制，因为该芯片主要设计用于在较低通信层执行加密的设备，而这并不总是使用它的最有效位置（参见 section 6.5）。

1997 年，英国政府的一份咨询文件提出了对托管（escrow）的一种新方法（DTI 1997）。在英国的方案中，密钥必须在收到“已验证的授权请求”后一小时内在线交出。该方案与美国的方案一样，因既压制又不可行而遭到广泛谴责。

政府还试图通过对销售和分销进行限制，防止加密软件落入“错误的人手中”。在美国，加密产品被定义为“军火”，并像坦克和导弹一样受到出口管制。由此引发了与计算机行业的激烈争论，因为供应商认为这些法规阻碍了他们向跨国公司和其他希望在全球建立安全通信的实体销售可信赖的产品。一些妥协已达成，但这些妥协主要集中在对较弱加密产品的豁免上（可以认为政府能够解密这些产品）。在其他地方，许多国家也纷纷效仿，对密码学的转让和使用施加限制（参见 第 14.1 节）。

## 7.5 公司间交易：EFT、EDI 和电子邮件

如果一家企业对其内部网络拥有完全控制权，它就可以完全按照自己的意愿使用密码学和其他安全措施。如果它希望与其它组织安全地交换信息，则并非如此。在这种情况下，它很可能会发现自己的选择受到了其他方的偏好或能力的限制。例如，他们可能无法处理某些加密方法，或希望遵守由外部提供商（如 VAN）设定的标准。

通常，企业对企业链接可分为三类：

### 1. 电子资金转账 (EFT)

EFT 消息只需包含与金额、账号等相关的少量基本细节。消息的接收方通常是银行（或者有人会认为，EFT 消息参与了授权 ATM 发放现金）。EFT 消息的构造相当简单，但必须高度重视确保其在传输过程中不会被篡改并且得到完全认证。

“电汇”式的资金转账可追溯到 1871 年，当时美国的 Western Union 公司推出了这项服务。安全性依赖于公司内部使用的授权码系统。电汇的潜在弱点在 1978 年的 Security Pacific Bank 诈骗案中被极其明显地暴露出来，当时一名在银行工作的承包商多次观察到员工使用资金转账程序，并记住了授权码。他利用这些知识向纽约的一个账户转账超过 1000 万美元（Cornwall 1989）。

今天的系统要复杂得多，并且由计算机驱动。SWIFT 组织提供了一项国际服务，用于银行之间发送金融指令，总部位于比利时的 La Hulpe。（它通常以缩写形式为人所知，但最初首字母缩写代表 Society for Worldwide Interbank Financial Telecommunication，世界银行间金融电信协会。）SWIFT 的成员由全球约 6,500 家精选金融机构组成。对网络的访问受到严格控制，成员必须使用基于 SWIFT 严格制定的标准的加密。

对于日常商业支付，多数国家都有服务可用于涉及相对小额的资金转账。这些通常是“批量”支付，例如在每周或每月末将组织所有员工的工资转入其银行账户。在英国，超过四分之三的劳动力现在以这种方式领取工资。使用此类服务的用户必须注册，并将被要求使用识别码和密码。然而，由于涉及的企业数量众多，管理加密的开销过大，因此加密被排除在外。

### 2. 电子数据交换 (EDI)

EDI 为企业对企业消息提供了一套标准格式。例如，销售发票和预订确认等项目的內容和布局都有格式规范。（类似的格式也用于资金转账，因此 EFT 可被视为 EDI 的一个专门子集。）

EDI 起源于 1980 年代的多个不同商业领域，最初每个行业都开发了自己的“方言”——用于汽车制造、航运、建筑、旅游等。欧洲和美国也曾一段时间存在不同的标准。所有这些标准最终都汇聚成了 UN/EDIFACT 规范（行政、商业和运输电子数据交换），该规范现已在全球使用。

EDI 提供的一项效率是，其消息现在被许多商业计算机软件所识别。这意味着，例如，订单的详细信息可以直接传递到订单录入系统，或发货通知可以直接记录到仓库数据库。这种人类干预的缺失无疑加快了业务流程并降低了成本，但也去除了有时至关重要的人能够注意到消息中存在不合理或可疑要素的机会。

### 3. 电子邮件

邮件消息完全自由格式。它们可用于传递业务信息和指令，但这些信息必须由人工阅读者（或也许是“智能”计算机程序）来解释。互联网上最常用的电子邮件格式是 SMTP（简单邮件传输协议）。基本的 SMTP 格式比 EFT/EDI 更简单、更通用，并假定其承载的消息仅为文本。然而，SMTP “扩展”此后已被发明，以使其能够承载其他类型的数据（见下文）。

原则上，电子邮件可用于发送从公司的秘密生产计划到最琐碎的小事的任何内容。除非企业愿意常规加密其电子邮件，否则唯一可行的政策是发布禁令，禁止使用电子邮件传输任何敏感信息。在此背景下，应记住不同类型的消息通常是“链式”连接的，例如 图 7.3 所示的案例。在此示例中，一名在家工作的经理向办公室的一名职员发送电子邮件，其指令导致向银行发送了一条 EDI 消息。银行随后根据 *其* 指令作出回应，向供应商进行 EFT 付款。

企业可能会发现，安全策略也因使用互联网交换 EDI 消息的做法日益普及而变得复杂。对于希望以低成本进入数据网络的小型和中型企业而言，这是一种越来越有吸引力的选择（Tucker 1997）。为了确保 EDI 消息在保持其特殊布局的同时送达，它会被“包裹”在电子邮件消息中，使用 SMTP 的特殊 MIME 扩展（其中 MIME 代表多用途互联网邮件扩展）。这使企业能够获得 EDI 的好处（例如，避免将详细信息重新输入其会计系统），同时也能利用互联网的廉价性和连通性。

## 7.6 与公众交易：电子商务

EDI 现在已证明对许多企业不可或缺，并已成为商业环境中被接受的一部分。大多数 EDI 交易都是在彼此知根知底的成熟组织之间进行的。除了能够通过公共注册和目录识别彼此外，各方通常会在安排开始时签署某种正式协议，以确定在 EDI 交易出现问题时各自的责任和义务。

另一方面，互联网商业发展的浪潮则集中在直接向消费者销售。在这种情况下，销售交易可能是双方之间第一次（也可能是唯一一次）接触。供应商希望从互联网获得两大关键优势。首先，它是一种廉价的销售媒介，全天候运行，可覆盖全球客户。其次，客户能够迅速做出并确认购买决定。因此，供应商对那些似乎威胁到这两大优势的安全措施持谨慎态度。例如，如果需要额外步骤来核实客户的资质，或付款方式过于繁琐，在线购物的吸引力就会开始消失。

事实上，若干因素需要有利地结合，互联网销售才具有商业可行性，而且在世界不同地区情况各异。例如，在拉丁美洲，消费者对在线支付系统特别不信任。这源于服务水平不佳的经历，以及企业对咨询和投诉普遍缺乏响应。信用卡服务也备受诟病，因为它们传统上不愿在出现问题时给予客户任何赔偿，例如信用卡被欺诈性使用或货物未送达。除了要与这种不利的舆论环境作斗争外，有意涉足网络交易的企业还必须克服一些技术障碍，因为电信服务昂贵且并不总是可靠，而且互联网服务提供商往往收取高额费用（Davis 1999）。与此同时，在东南亚的部分地区，虽然已在电信基础设施上投入了大量资金，但互联网服务提供的发展却未必跟上步伐。因此，在印度，一些公司宁愿在美国设立网站，也不愿在本国设立（Chowdhary 1997）。

就控制和安全而言，互联网上出现的新型面向消费者的服务带来了三个特别的挑战：

*   **建立买方和卖方的资质**。信任问题是*双向*的。客户一旦停止浏览在线目录并下订单，供应商就必须信任客户提出的付款方式。与此同时，客户必须相信供应商有意愿和能力交付所订购的商品。双方几乎没有什么可依据的，除了通过互联网传递的信息。
*   **在速度与安全之间取得平衡**。通过互联网交易的巨大吸引力在于其即时性和响应性。为了实现这一点，安全程序必须在“实时”进行，交易仍在进行中。任何引入额外检查的尝试，例如补充电话或传真消息，都会破坏这种即时性，并随之带走互联网的大部分吸引力。事实上，甚至一些号称“即时”的交易安全方法也被供应商抵制，认为它们太慢（见下文对 SET 的讨论）。
*   **小额交易**。从理论上讲，互联网应该是小额购买的理想媒介，特别是“数字”商品，如简短报告的文本或一段录制音乐。然而，传统的电子支付系统（如借记卡和信用卡）并不适合处理所涉及的小额资金。因此，人们正在寻找使电子支付变得容易的方法，适用于那种在传统购物之旅中会用零钱支付的小额金额。

### 主要安全协议与产品

第一个旨在解决上述至少部分问题的产品之一是 *Secure Socket Layer*（SSL）协议，它作为 Netscape 网络浏览器的功能引入。SSL 通过作为流行互联网浏览器的一部分免费提供，很快确立了事实上的标准地位。自推出以来，它已得到进一步发展，版本 3 不仅提供消息加密，还能使用非对称加密密钥对发送方和接收方的身份进行认证。

随后微软推出了其 *Secure Channel Services* 产品，声称支持多种安全协议，包括 SSL。与此同时，*Secure Electronic Transaction*（SET）协议也在推出，得到了包括 IBM、VISA 和 Mastercard 在内的主要商业公司联盟的支持。所有这些产品都在应用层附近工作，如 Figure 7.4 所示。

所有这些产品都提供类似的设施。它们中任何一个最终成为主导标准在多大程度上，将在很大程度上取决于商业和政治因素，以及它们的技术优点。SET 是这些产品中最专业的，因为它专为在线信用卡交易而设计。乍一看，这似乎让它在主导电子商务的竞争中抢占先机。然而，并非每个人都热衷于看到信用卡成为互联网上占主导地位的支付方式。一些商业利益更希望使用替代方法，或许更独立于现有的银行系统。此外，SET 还必须与为其设计的商户和发卡机构的抵制作斗争。SET 的第一个障碍是，必须说服所有客户在其个人电脑上安装软件，为他们创建“电子钱包”。每个客户随后使用该软件生成一对非对称密钥，公钥由认证机构（通常是发行信用卡的银行）担保。这确保了客户的正确认证，但也增加了营销和启动成本。金融服务业内部也出现了不安，因为单个 SET 交易虽然安全，但处理时间可能过长，令人无法接受（Lambeth 1999）。
