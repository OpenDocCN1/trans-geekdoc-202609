
# 配置控制过程

配置控制过程确保根据变更控制和配置管理策略对软件版本进行更改。更新只能根据这些策略从授权分发渠道进行。

## 配置状态记账

使用正式化的程序来跟踪发生的所有授权变更。

## 配置审计

应定期进行配置审计，以确保实际生产环境与会计记录一致，且未发生未经授权的配置变更。

变更管理和配置管理技术共同构成了软件工程师武器库的重要组成部分，并保护组织免受开发相关的安全问题影响。

## DevOps 方法

最近，许多技术专业人员认识到软件开发、质量保证和技术运维这三大主要 IT 职能之间存在脱节。这些职能通常由截然不同类型的人员组成，且位于独立的组织孤岛中，彼此经常发生冲突。这种冲突导致代码创建、测试和部署到生产系统的过程出现漫长延迟。当问题出现时，团队往往不是协作解决问题，而是将问题“扔过墙头”甩给对方，导致官僚主义的来回推诿。

DevOps 方法旨在通过将这三大职能融合在一个统一的运营模型中来解决这些问题。*DevOps* 一词是 Development（开发）和 Operations（运维）的组合，象征着这些职能必须融合协作以满足业务需求。图 20.6 中的模型展示了软件开发、质量保证和 IT 运维的重叠性质。

DevOps 模型与敏捷开发方法紧密契合，旨在大幅缩短开发、测试和部署软件变更所需的时间。虽然传统方法通常导致主要软件部署非常不频繁（可能一年一次），但使用 DevOps 模型的组织通常每天部署代码数次。有些组织甚至以持续部署为目标，代码每天可能推出数十次甚至数百次。

## 应用程序编程接口

虽然早期的 Web 应用程序通常是独立系统，处理用户请求并提供输出，但现代 Web 应用程序要复杂得多。它们通常包含多个不同 Web 服务之间的交互。例如，零售网站可能会使用外部信用卡处理服务，允许用户在社交媒体上分享购买记录，与物流提供商网站集成，并在其他网站上提供推荐计划。

为了使这些跨站点功能正常工作，网站之间必须相互交互。许多组织为此提供*应用程序编程接口 (API)*。API 允许应用程序开发人员绕过传统网页，通过函数调用直接与底层服务交互。例如，社交媒体 API 可能包含以下一些 API 函数调用：

*   `Post status`（发布状态）
*   `Follow user`（关注用户）
*   `Unfollow user`（取消关注用户）
*   `Like/Favorite a post`（点赞/收藏帖子）

提供和使用 API 为服务提供商创造了巨大的机遇，但也带来了一些安全风险。开发人员在创建和使用 API 时必须意识到这些挑战并加以解决。

首先，开发人员必须考虑身份验证要求。某些 API（如允许查询天气预报或产品库存的 API）可能面向公众开放，使用时不需要任何身份验证。其他 API（如允许修改信息、下单或访问敏感信息的 API）可能仅限特定用户使用，并依赖安全的身份验证。API 开发人员必须知道何时需要身份验证，并确保验证每次 API 调用的凭据和授权。这种身份验证通常通过向授权 API 用户提供复杂的 API 密钥来实现，该密钥随每次 API 调用传递。后端系统在处理请求前验证此 API 密钥，确保发起请求的系统已获授权进行特定的 API 调用。

API 还必须像任何 Web 应用程序一样经过彻底的安全缺陷测试。您将在下一节了解更多相关内容。

## 软件测试

作为开发过程的一部分，您的组织应在内部分发软件（或将其发布到市场）之前对其进行彻底测试。解决测试问题的最佳时机是在模块设计阶段。换句话说，您用于测试产品的机制和用于探索产品的数据集，应与产品本身并行设计。您的编程团队应开发特殊的测试数据套件，以最大程度地覆盖软件的所有路径，并预先知道正确的输出结果。

您应执行的测试之一是*合理性检查*。合理性检查确保软件返回的值符合指定标准，且在合理范围内。例如，一个计算人类最佳体重的程序如果返回 612 磅的值，肯定无法通过合理性检查！

此外，在进行软件测试时，您应检查产品如何处理正常有效的输入数据、错误的数据类型、超范围值以及其他边界和/或条件。实际工作负载提供了最佳的压力测试。但是，您不应使用实时或实际现场数据进行测试，尤其是在早期开发阶段，因为缺陷或错误可能导致测试数据的完整性或机密性遭到破坏。

测试软件时，您应适用与组织其他方面相同的职责分离规则。换句话说，您应将软件测试分配给开发代码的程序员以外的人员，以避免利益冲突，并确保成品更安全、功能更完善。当第三方测试您的软件时，您更有可能获得客观、无偏见的审查。第三方测试允许进行更广泛、更彻底的测试，并防止程序员的偏见和倾向影响测试结果。

您可以使用三种软件测试方法：

### 白盒测试

白盒测试检查程序的内部逻辑结构，逐行分析代码，以发现潜在错误。

### 黑盒测试

黑盒测试从用户角度检查程序，通过提供各种输入场景并检查输出来进行。黑盒测试人员无法访问内部代码。交付前进行的最终验收测试是黑盒测试的常见示例。

### 灰盒测试

灰盒测试结合了上述两种方法，常用于软件验证。在此方法中，测试人员从用户角度检查软件，分析输入和输出。他们也可以访问源代码，并利用它来帮助设计测试。然而，他们在测试过程中并不分析程序的内部运作。

除了评估软件质量外，程序员和安全专业人员还应仔细评估其软件的安全性，以确保满足组织的安全要求。对于面向公众的 Web 应用程序，这一点尤为关键。有两类测试专门用于评估应用程序安全性：

### 静态测试

静态测试通过分析源代码或编译后的应用程序，在不运行软件的情况下评估其安全性。静态分析通常涉及使用自动化工具，旨在检测常见的软件缺陷，例如缓冲区溢出。（有关缓冲区溢出的更多信息，请参阅第 21 章“恶意代码与应用攻击”。）在成熟的开发环境中，应用程序开发人员可使用静态分析工具，并在设计/构建/测试过程中全程使用它们。

### 动态测试

动态测试在运行时环境中评估软件的安全性，对于部署他人编写的应用程序的组织来说，这往往是唯一的选择。在这些情况下，测试人员通常无法访问底层源代码。动态软件测试的一个常见示例是使用 Web 应用程序扫描工具，以检测 Web 应用程序中是否存在跨站脚本、结构化查询语言 (SQL) 注入或其他缺陷。在生产环境上进行的动态测试应始终经过仔细协调，以避免无意中导致服务中断。

正确的软件测试实施是项目开发过程中的关键要素。商业软件和内部软件中常见的许多错误和疏漏都可以被消除。将测试计划和结果作为系统永久文档的一部分予以保存。

## 代码仓库

软件开发是一项协作工作，大型软件项目需要开发人员团队，他们可能同时在代码的不同部分工作。更复杂的是，这些开发人员可能分布在世界各地。

*代码仓库* 提供了支持这些协作的几项重要功能。主要而言，它们充当开发人员存放源代码的中心存储点。此外，`GitHub`、`Bitbucket` 和 `SourceForge` 等代码仓库还提供版本控制、缺陷跟踪、Web 托管、发布管理和通信功能，以支持软件开发。

代码仓库是促进软件开发的协作神器，但它们本身也存在安全风险。首先，开发人员必须适当控制对其仓库的访问。某些仓库（如支持开源软件开发的仓库）可能允许公共访问。而其他仓库（如托管包含商业机密信息代码的仓库）可能受到更多限制，仅限授权开发人员访问。仓库所有者必须仔细设计访问控制，仅允许适当的用户拥有读和/或写访问权限。

## 服务级别协议

使用服务级别协议 (SLA) 是一种日益流行的方式，旨在确保向内部和/或外部客户提供服务的组织维持服务提供商和供应商双方商定的适当服务水平。为任何数据电路、应用程序、信息处理系统、数据库或对组织持续生存能力至关重要的其他关键组件制定 SLA 是明智之举。SLA 中通常涉及以下问题：

*   系统正常运行时间（占总运行时间的百分比）
*   最大连续停机时间（以秒/分钟等为单位）
*   峰值负载
*   平均负载
*   诊断责任
*   故障切换时间（如果已部署冗余）

服务级别协议通常还包含财务和其他合同补救措施，如果未能维持协议，这些措施将生效。例如，如果关键电路中断超过 15 分钟，服务提供商可能同意免除该电路一周的所有费用。

## 软件采购

企业使用的大多数软件并非内部开发，而是从供应商处购买。其中一些软件是购买后在组织管理的服务器上运行，无论是本地部署还是在基础设施即服务 (IaaS) 环境中。其他软件则是通过互联网经由 Web 浏览器购买并交付，采用软件即服务 (SaaS) 的方式。大多数组织根据业务需求和软件可用性，结合使用这些方法。

例如，组织可能通过两种方式处理电子邮件服务。他们可能购买物理或虚拟服务器，然后在其上安装电子邮件软件，如 `Microsoft Exchange`。在这种情况下，组织从微软购买 Exchange 许可证，然后安装、配置和管理电子邮件环境。

作为替代方案，组织可能选择将电子邮件完全外包给 `Google`、`Microsoft` 或其他供应商。用户随后通过其 Web 浏览器或其他工具访问电子邮件，直接与供应商管理的电子邮件服务器交互。在这种情况下，组织仅负责创建账户和管理某些应用级设置。

无论哪种情况，安全都是重中之重。当组织自行购买和配置软件时，安全专业人员必须了解该软件的正确配置以满足安全目标。他们还必须时刻关注安全公告和补丁，以修复新发现的漏洞。未能履行这些义务可能导致环境不安全。

在 SaaS 环境中，大部分安全责任在于供应商，但组织的安全人员并未完全免责。虽然他们可能不负责那么多配置工作，但现在他们承担了监控供应商安全的责任。这可能包括审计、评估、漏洞扫描和其他措施，旨在验证供应商是否保持适当的控制。根据法规的性质和与服务提供商达成的协议，组织可能还保留全部或部分法律合规义务的责任。

## 建立数据库与数据仓库

几乎每个现代组织都维护着某种包含对运营至关重要的信息的数据库——无论是客户联系信息、订单跟踪数据、人力资源和福利信息，还是敏感商业机密。这些数据库中很可能包含用户保密的个人信息，例如信用卡使用活动、出行习惯、杂货店购买记录和电话记录。由于对数据库系统的依赖日益增加，信息安全专业人员必须确保存在足够的安全控制，以防止未经授权的访问、篡改或数据破坏。

在以下章节中，我们将讨论数据库管理系统 (DBMS) 架构，包括各种 DBMS 类型及其特性。然后我们将讨论数据库安全注意事项，包括多实例化、开放数据库互连 (ODBC)、聚合、推理和数据挖掘。

### 数据库管理系统架构

尽管目前有多种数据库管理系统 (DBMS) 架构可用，但绝大多数现代系统都实施了一种称为关系数据库管理系统 (RDBMS) 的技术。因此，以下章节主要关注关系数据库。不过，首先我们将讨论另外两种重要的 DBMS 架构：层次型和分布式。

#### 层次型和分布式数据库

层次型数据模型将以逻辑树结构相关联的记录和字段组合在一起。这导致了一种一对多的数据模型，其中每个节点可能有零个、一个或多个子节点，但只有一个父节点。层次型数据模型的示例见 图 20.7。

![图 20.7 层次型数据模型](img/c20f007.jpg)

**图 20.7** 层次型数据模型

图 20.7 中的层次模型是一个公司组织架构图。请注意，一对多的数据模型在此例中成立。每位员工仅有一位经理（即一对多中的“一”），但每位经理可能有一名或多名（即一对多中的“多”）员工。层次数据模型的其他示例包括 NCAA 疯狂三月锦标赛系统，以及互联网上用于域名系统 (DNS) 记录的层次化分发。层次数据库以这种层次化方式存储数据，适用于符合该模型的专业应用。例如，生物学家可能会使用层次数据库，根据该领域使用的界/门/纲/目/科/属/种层次模型来存储标本数据。

分布式数据模型将数据存储在多个数据库中，但这些数据库在逻辑上是相连的。用户将数据库视为一个单一实体，尽管它由通过网络互联的众多部分组成。每个字段可以有多个子项，也可以有多个父项。因此，分布式数据库的数据映射关系是多对多。

#### 关系数据库

关系数据库由由行和列组成的扁平二维表构成。事实上，每个表看起来类似于电子表格文件。行和列的结构提供了一对一的数据映射关系。关系数据库的主要构建模块是表（也称为*关系*）。每个表包含一组相关记录。例如，销售数据库可能包含以下表：

*   **客户表**，包含组织所有客户的联系信息
*   **销售代表表**，包含组织销售团队的身份信息
*   **订单表**，包含每位客户下达的订单记录

每个表包含若干属性，或称为*字段*。每个属性对应表中的一列。例如，**客户表**可能包含公司名称、地址、城市、州、邮政编码和电话号码等列。每位客户都有自己的记录，或称为*元组*，由表中的一行表示。关系中的行数称为*基数*，列数称为*度*。属性的*域*是该属性可取的允许值集合。图 20.8 展示了一个来自关系数据库的**客户表示例**。

![图 20.8 来自关系数据库的客户表 ](img/c20f008.jpg)

**图 20.8** 来自关系数据库的客户表

在此例中，该表的基数为 3（对应表中的三行），度为 8（对应八列）。在正常业务过程中，表的基数发生变化是常见的，例如当销售代表添加新客户时。表的度通常不会频繁变化，且通常需要数据库管理员介入。

表之间的关系被定义用于识别相关记录。在此例中，**客户表**和**销售代表表**之间存在关系，因为每位客户被分配一位销售代表，而每位销售代表被分配给一位或多位客户。该关系体现在图 20.8 所示的**客户表**中的**销售代表**字段/列中。该列中的值引用了**销售代表表**（未显示）中包含的**销售代表 ID** 字段。此外，**客户表**和**订单表**之间也可能存在关系，因为每个订单必须与一位客户关联，而每位客户与一个或多个产品订单关联。**订单表**（未显示）可能包含一个**客户**字段，其中包含图 20.8 中所示的**客户 ID** 值之一。

记录通过各种键来识别。简单来说，*键*是表字段的一个子集，用于唯一标识记录。它们也用于在需要交叉引用信息时连接表。你应该熟悉三种类型的键：

**候选键** *候选键*是可用于唯一标识表中任意记录的属性子集。同一表中的任意两条记录，其组成候选键的所有属性值绝不会完全相同。每个表可能有一个或多个候选键，这些候选键从列标题中选出。

**主键** *主键*是从表的候选键集合中选出，用于唯一标识表中记录的键。每个表仅有一个主键，由数据库设计者从候选键集合中选定。RDBMS 通过禁止插入具有相同主键的多条记录来强制主键的唯一性。在图 20.8 所示的**客户表**中，**客户 ID** 很可能是主键。

**外键** *外键*用于强制执行两个表之间的关系，也称为*参照完整性*。参照完整性确保如果一个表包含外键，它对应于关系中另一个表中仍然存在的主键。它确保没有记录/元组/行包含对不存在的记录/元组/行的主键的引用。在前面描述的示例中，图 20.8 中所示的**销售代表**字段是引用**销售代表表**主键的外键。

所有关系数据库都使用标准语言结构化查询语言 (SQL)，为用户提供一致的接口，用于数据的存储、检索和修改，以及对 DBMS 的管理控制。每个 DBMS 供应商实现的 SQL 版本略有不同（如 Microsoft 的 Transact-SQL 和 Oracle 的 PL/SQL），但都支持一组核心功能。SQL 的主要安全特性是其授权的粒度。这意味着 SQL 允许你在非常精细的层面上设置权限。你可以按表、行、列，甚至在某些情况下限制到单个单元格来限制用户访问。

SQL 为管理员、开发人员和最终用户提供了与数据库交互所需的完整功能。事实上，当今流行的图形化数据库界面仅仅是在标准 SQL 接口外包装了一些额外的花哨功能来连接 DBMS。SQL 本身分为两个不同的组件：数据定义语言 (DDL)，允许创建和修改数据库的结构（称为*模式*）；以及数据操作语言 (DML)，允许用户与该模式中包含的数据进行交互。

#### 数据库事务

关系数据库支持显式和隐式使用事务以确保数据完整性。每个事务是一组离散的 SQL 指令，将作为一个整体要么成功要么失败。事务的某一部分成功而另一部分失败是不可能的。考虑银行两个账户之间转账的例子。你可能会使用以下 SQL 代码，先给账户 1001 增加 250 美元，然后从账户 2002 扣除 250 美元：

```
BEGIN TRANSACTION
UPDATE accounts
SET balance = balance + 250
WHERE account_number = 1001;

UPDATE accounts
SET balance = balance – 250
WHERE account_number = 2002

END TRANSACTION
```

## 数据库事务与安全机制

### 事务处理的重要性

当事务成功完成时，称其已**提交**到数据库，且无法撤销。事务提交可以是显式的，使用 SQL 的 `COMMIT` 命令；也可以是隐式的，即成功到达事务末尾。如果必须中止事务，可以使用 `ROLLBACK` 命令显式回滚，或在发生硬件或软件故障时隐式回滚。事务回滚时，数据库会恢复到事务开始前的状态。

所有数据库事务都具有四个必需特征：原子性、一致性、隔离性和持久性。这些属性统称为 **ACID 模型**，是数据库管理系统开发中的关键概念。让我们简要了解一下每个要求：

#### 原子性

数据库事务必须是原子的——即要么全做，要么全不做。如果事务的任何部分失败，整个事务必须回滚，就像从未发生过一样。

#### 一致性

所有事务必须在一个与数据库所有规则一致的环境中开始操作（例如，所有记录都有唯一的主键）。事务完成时，数据库必须再次与规则保持一致，无论这些规则在事务处理过程中是否被违反。任何其他事务都不应能使用另一个事务执行过程中可能生成的不一致数据。

#### 隔离性

隔离性原则要求事务彼此独立操作。如果数据库接收到两个修改相同数据的 SQL 事务，必须在允许另一个事务修改相同数据之前，完成其中一个事务的全部过程。这可以防止一个事务使用另一个事务作为中间步骤生成的无效数据。
