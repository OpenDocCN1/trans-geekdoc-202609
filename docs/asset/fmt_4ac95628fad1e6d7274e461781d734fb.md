
如果一种语言是研究的对象，则称之为 `object language`（对象语言）。用于研究它的语言则称为 `metalanguage`（元语言）。例如，你可能用英语作为元语言来研究作为对象语言的日语。对象语言可以是它自己的元语言，例如，英语可以用来学习英语。任何概念模式都可以表示为一组句子，因此本身可以被视为一个数据库。

这使我们能够构建一个 `metaschema`（元模式）来谈论概念模式。这种元概念模式规定了任何概念模式必须遵守的设计规则（例如，每个角色恰好由一个对象类型扮演）。计算机辅助软件工程（CASE）工具被用来协助设计此类元模式的概念模式，以确保建模人员输入的模式是 well formed（格式良好）或“语法正确”的。

关于语法，让我们约定接受“schemas”和“schemata”作为“schema”的复数形式。虽然“data”是“datum”的复数，但我们将采用通用做法，允许“data”既作单数也作复数使用。本书的第一个练习如下所示。练习答案包含在在线补充材料中。

## 2.2 概念层

在概念层，人与信息系统之间的所有通信由 CIP 处理。这种通信可分为三个主要阶段：

1. 建模人员将 UoD 的概念模式输入系统。当且仅当该模式与元概念模式一致时，CIP 才接受它。

2. 用户通过添加或删除特定事实来更新数据库。当且仅当该更新与概念模式一致时，CIP 才接受它。

3. 用户向系统查询关于 UoD 的信息，并由 CIP 回答。只要 CIP 存储了相关信息或能推导出该信息，它就可以提供关于概念模式或数据库的信息。

在这些阶段中，CIP 分别扮演 `design filter`（设计过滤器）、`data filter`（数据过滤器）和 `information supplier`（信息提供者）的角色。为处理更新和查询请求，CIP 访问概念模式，后者包含如图 2.4 所示的三个主要部分。

![图 2.4 概念模式的三个主要部分。](img/f02-04-9780443237904.jpg)

图 2.4 概念模式的三个主要部分。

`fact`（事实或事实实例）是业务视为真实的命题。`fact types`（事实类型）部分列出了可在数据库中表示的事实种类。事实类型指明了 UoD 中允许哪些类型的 `object`（对象）（例如 Employee 员工、Country 国家），这些对象如何在数据库中通过值被 `referenced`（引用/标识）（例如 SSN、CountryCode），以及它们的 `relationships`（关系）（例如 was born in 出生于、lives in 居住于）。

`constraints`（约束）部分列出了对事实类型实例集的约束或限制。`Static constraints`（静态约束）适用于数据库的每一个状态。例如，假设数据库存储关于国家及其人口的信息。虽然一个国家的人口可能随时间变化，但在任何给定时间，每个国家最多只有一个值被记录为其当前人口。`Dynamic constraints`（动态约束）决定了数据库状态之间允许的转换。例如，一个人的年龄状态可能从儿童变为成年人，但不能反向变化。

约束也称为 `validation rules`（验证规则）或 `integrity rules`（完整性规则）。当数据库与所建模的 UoD 一致时，称该数据库具有完整性。虽然大多数数据库约束可以在概念模式图上用图形表示，但某些约束可能需要用其他方式表示（例如使用概念句子、公式、表格、图表或程序代码）。

`derivation rules`（推导规则）部分包含从其他事实推导出新事实的规则。非 `derived fact`（推导事实）的事实称为 `asserted fact`（断言事实，也称为原始事实或基本事实）。推导规则可能涉及 `mathematical calculation`（数学计算）或 `logical inference`（逻辑推理）。例如，平均分可以通过将各个分数相加再除以其数量来推导。为各种数据类型定义了许多运算符和函数。这使得无需记录每个推导即可进行多种可能的查询。典型的数学工具包括算术运算符，如 `+`、`−`、`*`（乘）、`/`（除）；集合运算符如 `∪`（并集）；以及用于计数、求和和计算平均值、最大值和最小值的函数。

除了这种通用的推导工具外，已知需要的特定 `derived fact types`（推导事实类型）可通过推导规则在模式中定义。数学计算得出的事实类型和几乎所有通过逻辑推理得出的事实类型都属于这一类。通过逻辑推理推导的事实类型通常涉及使用逻辑运算符（如 `and` 或 `if`）的规则。

虽然可推导的事实可以存储在数据库中，但通常最好避免这样做。除了节省存储空间外，从存储数据中省略推导事实的做法通常使处理更新变得容易得多。例如，假设我们想定期获取班级中学生的个人年龄（以年为单位），有时还需要获取班级的平均年龄。如果我们在数据库中存储了平均年龄，每当有学生加入或离开班级，以及班级中任何人的年龄增长时，都必须安排重新计算该平均年龄。

作为改进，我们可以存储学生人数及其各自的年龄，仅在请求时计算平均年龄。但这仍然很笨拙。你能想出更好的设计吗？

正如你可能意识到的，无需在类中存储学生人数，因为这可以通过计数函数得出。这避免了每当有人加入或离开班级时都要更新班级规模。此外，甚至无需存储学生的个别年龄。计算机系统拥有内置时钟，可访问当前日期。如果我们存储学生的出生日期，则可通过适当的日期减法算法，在请求时由系统推导出任何学生的年龄。这样，我们就不必担心随着学生长大一岁而更新他们的年龄。

有时，所需的不是当前年龄，而是某一特定日期的年龄（例如入学日期、未来体育比赛的年龄分组）。在这些需要为每个人提供单一、稳定年龄的情况下，存储年龄可能是合适的。

在考虑使用逻辑推理的推导示例之前，请注意*命题*与*句子*的区别。命题由陈述句断言，且永远是真或假（不能两者皆是）。同一命题可由不同句子断言，例如“巴黎是法国的首都”和“法国的首都是巴黎”。

虽然人类能以非常复杂的方式处理深层含义，但计算机完全是字面理解的：它们处理的是句子而非其含义。如果我们希望计算机建立对我们显而易见的联系，必须为其显式提供建立此类联系所需的背景知识或规则。

假设关于兄弟关系和父母关系的事实存储在数据库中。为简化起见，假设我们要讨论的对象仅为以名字标识的人。我们可以按如下方式陈述事实：

*   Alan 是 Betty 的兄弟。
*   Charles 是 Betty 的兄弟。
*   Betty 是 Fred 的父母。

你可以看到这些事实，并轻易推断出 Alan 和 Charles 都是 Fred 的叔叔。在此过程中，你使用了对“叔叔”一词的理解。如果我们希望计算机系统能做出类似推断，需要为其提供一条表达这种理解的规则。例如：

```
给定任意 X, Y，若存在某个 Z 使得 X 是 Z 的兄弟且 Z 是 Y 的父母，则 X 是 Y 的叔叔。
```

这可简写为：

```
X 是 Y 的叔叔，若 X 是 Z 的兄弟且 Z 是 Y 的父母。
```

此规则是*霍恩子句*的一个例子。子句左侧“**if**”的头部可从右侧所述条件推导得出。霍恩子句用于 Prolog 和 Datalog 等语言，使许多推导规则能简洁地陈述。在对象角色建模（ORM）中，此类规则使用更易读的语法指定，例如：

*   ```
    对于每个 Person1 和 Person2，
    ```

*   ```
              若 Person1 是某个 Person3 的兄弟
    ```

*                                                                   **who** 是 Person[2] 的父母，则 Person1 是 Person2 的叔叔。

*引用方案*部分声明了感兴趣的*对象*种类及其引用方式。对象要么是实体，要么是值。*实体*是通过以某种方式将*值*（如名字）与之关联来引用的真实或抽象事物。此处有三种*实体类型*：Person、Country 和 Year。在该 UoD 中，人由名字标识（实际中很少见！）。国家由代码标识（如“CU”代表古巴）。年份由 CE（公元）值标识（如第二次世界大战于 1945 CE 结束）。年份是时间段，因此是实体而非值。

*事实类型*部分声明了感兴趣的事实种类。这指明了对象类型如何参与关系。在本书中，英文对象类型名首字母大写，角色名以小写字母开头。由于数据库列具有“birthyear”等属性名，你可能认为将“Person was born in Year”改写为“Person has Birthyear”更好。

然而，假设我们添加事实类型“Person has Deathyear”。Birthyear 与 Deathyear 之间的形式联系现在被隐藏了。将新事实类型表达为“Person died in Year”揭示了与“Person was born in Year”的语义联系，并使出生年份与死亡年份的比较变得有意义（底层域为 Year）。

属性名常用于 ER、UML 和关系模式中表达事实，但这可能不自然（比较“Person has deathyear”与“Person died in Year”），且除非添加“Year”等域名，否则是不完整的。

*约束*部分声明了事实类型上的约束。此处的示例均为*静态*约束（即每个约束对数据库的每个状态均为真）。模式语言中的保留字以**粗体**显示。约束 C1 意味着数据库中引用的每个人，我们知道他们至少居住在一个国家。C2 表示没人能同时居住在多个国家。C3 表示没人出生于多个年份；注意我们可能不知道他们的出生年份。约束 C4 表示没人是自己的兄弟，C5 表示没人是自己的父母（兄弟关系和父母关系是非自反的）。

*推导规则*部分声明了叔叔关系的逻辑规则和计算任意人子女数量的函数。叔叔规则使用事实类型读法，以关系风格指定。nrChildren 规则使用角色名，以属性风格指定。

在概念层面上，数据库中的每个事实都是简单或*基本事实*。基本上，这意味着如果不丢失信息，就无法将其拆分为两个或更多更简单的事实。我们可以向数据库中*添加*或插入一个事实，也可以从中*删除*一个事实。但是，我们不能只修改或更改事实的一部分。这里的“事实”是指“事实*实例*”，而不是“事实类型”。

添加或删除单个事实的操作称为*基本更新*或*简单事务*。在我们的示例概念查询语言中，添加和删除请求以`**add**:`和`**del**:`开头，查询以`**list**`开头或以`?`结尾。CIP 要么接受更新，要么拒绝更新并指明违规情况。CIP 回答合法查询并拒绝非法查询。

为了解释数据库事务的基本概念，我们现在讨论一些 CIP 交互的示例。如果这看起来很繁琐，请记住我们讨论的是概念层面，而不是用户实际与系统交互的外部层面。在外部层面，用户通常在表单或表格的屏幕版本中输入、删除或更改值。然而，从概念上讲，我们可以认为这种操作在被传递给 CIP 之前，被转换为对基本事实的适当删除和添加操作。假设我们现在开始填充我们的概念数据库，如下所示：

```
User:                                                                                                                                      CIP: add: Person ‘Terry’ lives in Country ‘US’.          Accepted
```

因为 CIP 识别出该句子的类型，且发现没有违反约束，所以将其添加到数据库并回复“Accepted”。如果更新与概念模式不一致，CIP 会拒绝它，通过口头化被违反的约束来指明拒绝原因。你现在应该能够理解以下对话。为了节省空间，我们只列出被违反约束的编号，而不是其口头化描述。

```
add: Person ‘Norma’ was born in Year 1950.       Rejected. C1 violated.
add: Person ‘Norma’ lives in Country ‘US’.         Accepted.
add: Person ‘Norma’ was born in Year 1950.       Accepted.
add: Person ‘Terry’ is a brother of Person ‘Paul’.    Rejected. C1 violated.
add: Person ‘Paul’ lives in Country ‘AU’.          Accepted.
add: Person ‘Terry’ is a brother of Person ‘Paul’.    Accepted.
add: Person ‘Paul’ is a brother of Person ‘Paul’.     Rejected. C4 violated.
add: Person ‘Terry’ plays Sport ‘Judo’.           Rejected. Unknown fact type
```

现在假设 Norma 从美国搬到了澳大利亚。我们该如何记录这一变更？以下是两种错误的尝试：

```
add: Person ‘Norma’ lives in Country ‘AU’.         Rejected. C2 violated.
del: Person ‘Norma’ lives in Country ‘US’.         Rejected. C1 violated.
```

*   ```
    begin
    ```

*   ```
    del:  Person ‘Norma’ lives in Country ‘US’.
