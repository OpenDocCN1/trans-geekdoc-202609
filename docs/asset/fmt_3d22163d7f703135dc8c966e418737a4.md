
# 可观测性与生产环境故障排查

可观测性让我们理解系统行为**为何**以及**如何**呈现当前状态，这与监控不同，监控通过分析让我们了解**发生了什么**。

我们将利用可观测性的力量来解决实际和潜在的问题。没有可观测性，我们就无法维护系统，也无法进行故障排查，后者将在本章后面讨论。

区分监控和可观测性的一个好比喻是将我们的系统视为一名患者。监控就像查看患者的生命体征（心跳、血压、体温、伤情等）。而在另一端，要治愈患者，我们需要查看其历史病历，并调查关于他为何生病的具体理论。

## 监控系统构建

部署微服务架构时，我们必须创建一个监控系统。在使用 `Kubernetes` 时创建监控系统包含三个部分：

*   **集中式监控系统：** 一个从各种来源聚合数据的统一平台，提供查看和分析工具。我们可以使用开源工具如 `Prometheus` 和 `Grafana`，或 SaaS 工具如 `DataDog` 和 `NewRelic`。
*   **代理：** 它们将所有遥测数据上报给集中式监控系统，通常是作为 `DaemonSet` 运行在每个节点上。
*   **SDK：** 对于我们使用的每种语言，我们必须实现支持通过函数、中间件等上报遥测数据的逻辑。

## 遥测数据类型

### 日志

日志是软件应用程序或系统生成的事件、操作或消息的记录，用于故障排查、监控和分析。日志可用于提供信息和报告警告或错误。通过日志，我们可以了解**发生了什么以及何时发生**，就像在代码中留下面包屑。日志应采用人类可读的 JSON 格式编写，而不仅仅是纯文本，尽管纯文本也是一种选项。日志由元数据（日期、服务等）、日志级别和日志内容本身组成。通常，日志元数据是手动注入日志或在使用 SDK 过程中注入的。以下是常见的日志级别：

*   **Info（信息）：** 有用的信息；通常我们不太关心它们。它通常是默认日志级别。
*   **Debug（调试）：** 此日志旨在记录用于调试目的的详细信息。它将来会被删除。
*   **Warning（警告）：** 系统中任何可能导致错误的情况。可以是延迟、高延迟等。这类日志从不需要立即补救。
*   **Error（错误）：** 此日志指示发生了严重问题，通常需要用户干预。它通常需要立即关注。
*   **Fatal（致命）：** 导致服务宕机或重启的错误。这是一种极端情况，将需要即时响应。

以下是一些日志示例：

*   `[INFO] User was logged into the system. { "name": "John", "company": "Nick"}`
*   `[DEBUG] Query was executed. { "query": "SELECT * FROM accounts", "execution_time": "15s"}`
*   `[WARNING] Event took a lot of time to proceed. { "event_id": "12345", "time": "30s"}`
*   `[ERROR] Unable to connect to the external API. Retrying in 2 seconds.`
*   `[FATAL] Server got panic. Shutting down the application`

Golang 的核心包之一是 `log`，它包含日志功能。一个具有更高级选项的替代包是 `github.com/sirupsen/logrus`。

### 指标

指标是表示为数据点的定量测量。指标可以包含标签。标签代表指标上的元数据；示例包括账户名、用户名、环境、应用版本等。我们可以基于一段时间内的指标数据点，在任何监控系统中构建不同布局形式的图表。我们也可以使用指标标签和定义的指标聚合时间持续时间来创建分区图表。

指标类型多种多样。这里我们将提及三种主要类型。

*   **Counter（计数器）：** 这是一种累积指标，代表一个可以增加或重置为零的值。计数器指标的示例可以是失败请求数、总请求数、使用系统的用户数量等。

![图 10.2：“作业执行总数”的计数器指标示例](img/Figure-10.2.jpg)

*   **Gauge（仪表盘）：** 一种单一数值指标，表示可增可减的任意值。仪表盘指标的示例包括温度、CPU 使用率、内存使用率和活跃用户数。
*   **Histogram（直方图）：** 一种对观测值进行采样并统计落入各存储桶中观测次数的指标。例如，直方图可用于测量延迟、请求大小、任务持续时间等。

![图 10.3：人群身高（厘米）的直方图指标示例](img/Figure-10.3.jpg)

### 链路追踪

链路追踪比日志和指标更新的遥测手段。它能提供更全面的应用视图。链路追踪的目标是跟踪应用的流程，无论是数据传播还是请求流程，这对于微服务架构中的 RESTful API 服务尤为重要，因为其请求频率很高。链路追踪让我们能够看到从开始到结束的函数流向、哪个函数调用了哪个函数、每个函数的持续时间、它们之间传递的参数、每个步骤的元数据等。每个步骤位于一个称为“跨度”的追踪内。完整的追踪可以讲述一个用户的故事，以及他在途中发生了什么。

![图 10.4：链路追踪示例](img/Figure-10.4.jpg)

在上图中，我们可以看到一个追踪示例。该追踪旨在跟踪端点 `GET /api/v1/articles/:article_id`。在追踪中，我们可以看到三个跨度：`authenticate`、`get article:41348`、`SELECT FROM articles WHERE id`。对于每个跨度，我们可以看到持续时间、跨度的顺序以及图中未显示的其他数据。一种更高级的追踪能力是执行分布式追踪。这涉及执行广泛的追踪，而不是在单个应用程序内进行追踪，而是跨越许多服务的单次追踪。

## 生产环境故障排查

生产环境故障排查是一个系统性过程，包括采取即时行动修复问题以恢复系统健康状态、执行 RCA 以及解决根本原因以防止同类问题再次发生。让我们拆解这一故障排查过程。

![图 10.5：故障排查组成部分](img/Figure-10.5.jpg)

**RCA**，即**根因分析**，是识别 Bug 底层原因的过程。例如，某服务有一个指标用于跟踪其一个月的错误率，数值始终在 0.1% 到 0.2% 之间。紧随一个名为“更改 API 配置”的 PR（Pull Request）部署到生产环境后，错误率指标显著飙升至 50%。我们可以有把握地假设根因就是上述 PR。

执行 RCA 的方法多种多样——查看服务仪表盘、为服务设置告警（本章稍后将讨论）、排查有问题的日志、查看系统指标、Kubernetes 集群指标、Kubernetes 日志、在 Kubernetes 中描述服务的 Pod、CI/CD 变更、第三方服务停机、异常检测、性能分析（本章将进一步讨论）等。

**补救** 是指防止当前不良状态发生的过程。

在我们执行任何补救措施之前，系统无法正常工作，甚至完全瘫痪。这种情况称为 P0 级故障。补救过程可以通过多种方式执行：Kubernetes 回滚（详见*第 8 章 微服务简介*）、撤销 PR、增加副本数、更新过期配置等。

有时，我们无需执行完整的 RCA 即可进行补救，补救可以是部分的。例如，如果我们确定了是某个糟糕的 PR 导致的，补救措施很可能是撤销它，尽管我们不知道 PR 中具体是什么内容导致了 Bug。

**解决** 是指防止不良状态再次发生的过程。通过理解问题的根本原因，我们可以采取预防措施。解决措施的示例包括：通过调试修复 Bug、调整 API/DB 配置、增加副本数量等。注意，补救措施有时与解决措施是相同的。

## 理论的力量

**没有可观测性就没有理论，反之亦然。**

我们已经讨论了可观测性，但让我们来谈谈理论，并解释上述陈述。理论是解释现有数据的观点：为什么图表呈现这种堆叠方式而不是其他方式？例如，我们可以看到内存使用量持续增长的图表，这可以用内存泄漏来解释。

为了说明**理论**与**可观测性**之间的关系，我们将引用参考文献 5 中的一个类比。

一位拥有丰富人体知识且时刻掌握最新医学资讯的医生，就是好医生吗？答案是否定的，除非该医生能够检查患者并获取其数据。如果没有对患者进行适当的检测，他就无法提供恰当的治疗，没有数据支撑的每一次治疗都只是猜测。

另一方面，你是一个对人体缺乏基本了解的普通人。但你拥有最先进的患者检测技术和所有患者数据。你是好医生吗？答案也是否定的，除非你具备关于人体的基本知识。

![图 10.6：可观测性与理论](img/Figure-10.6.jpg)

医生的类比映射到开发人员，理论映射到医生的知识，数据映射到数据。一方面如果没有基于软件知识和内部业务知识的丰富理论，另一方面没有数据，我们就无法获得可观测性。

每当我们开始排查故障或执行 RCA 时，都应心中预设一些关于根因的理论，并用数据去验证该理论；或者通过观察数据，形成另一个可供验证的理论。

## 性能分析

性能分析通过在运行时分析程序来测量执行时间、CPU 使用率、内存使用量、运行中的 Goroutine 等指标。性能分析使我们能够识别瓶颈、提升性能并优化代码效率。通常，使用 Grafana 或 DataDog 等第三方工具会生成火焰图。尽管还有其他查看性能分析数据的方式。

![图 10.7：CPU 时间性能分析火焰图](img/Figure-10.7.jpg)

在上图中，我们可以看到 Google Cloud 中 Golang 应用 CPU 时间性能分析的示例。不过，我们也可以使用 Golang 团队发明的原生工具 `pprof`。让我们看看如何使用它：

```go
package main

import (
	"net/http"
	_ "net/http/pprof"
	"sync"
	"time"
)

var leakSlice1 = []string{}
var leakSlice2 = []string{}
var leakSlice3 = []string{}

func main() {
	// start pprof server
	go func() {
		http.ListenAndServe(":6060", nil)
	}()
	wg := sync.WaitGroup{}
	wg.Add(1)
	go leak(&wg)
	wg.Wait()
}

func leak(wg *sync.WaitGroup) {
	defer wg.Done()
	for i := 0; i < 10_000_000; i++ {
		appendToLeakSlice1()
		if (i % 10_000) == 0 {
			time.Sleep(100 * time.Millisecond)
		}
	}
}

func appendToLeakSlice1() {
	leakSlice1 = append(leakSlice1, "a")
	appendToLeakSlice2()
}

func appendToLeakSlice2() {
	leakSlice2 = append(leakSlice2, "ab")
	appendToLeakSlice3()
}

func appendToLeakSlice3() {
	leakSlice3 = append(leakSlice3, "abc")
}
```

在上述示例中，启动性能分析所需的仅有：

*   通过声明 `_ "net/http/pprof"` 导入 `pprof` 包。
*   在某个端口启动一个 goroutine：

```go
go func() {
	http.ListenAndServe(":6060", nil)
}()
```

此后的代码用于演示程序的内存使用情况。要查看内存使用情况，我们可以使用 Golang CLI：

`go tool pprof -web http://localhost:6060/debug/pprof/heap`

`-web` 标志会在一个友好的 UI 中打开内存分析数据。我们不需要使用它。

![图 10.8：pprof 堆内存使用情况](img/Figure-10.8.jpg)

几秒钟后，内存堆的呈现方式发生了变化。

![图 10.9：pprof 堆内存使用情况 2](img/Figure-10.9.jpg)

让我们不要关注前两个图表中的具体数据。引入它们的目的是为了展示 Golang 中 `pprof` 包的强大功能以及我们如何使用它。除了查看运行时函数间的内存分布，我们还可以查看 CPU 和 goroutine 执行等指标。要进一步了解这些选项，请参阅 `https://pkg.go.dev/net/http/pprof`。一旦理解了某一指标（如本节展示的 `heap` 指标）的用法，使用 `pprof` 就非常简单直接。

## PGO

**P**rofile-**G**uided **O**ptimization（基于配置文件引导的优化）是一种编译器优化方法，它利用分析得到的信息来进行优化。编译器将使用这些分析数据（`pprof` 输出）生成高性能的二进制代码。PGO 从 Golang 1.21 版本开始可用。每当构建 Golang 代码时，它都会寻找包含分析信息的 `default.pgo` 文件。另一种方式是指定特定的分析文件 `go build -pgo=/tmp/foo.pprof`。我们不会深入探讨使用 PGO 的过程；我们的目标是了解这种方法的存在。

## 性能问题

在进入下一节之前，让我们看看一些可以通过分析来解决的常见性能问题：

*   **CPU 节流**：CPU 使用率达到极限的场景。这是一个标准的 Kubernetes 场景，一旦达到 Pod 的 CPU 限制。一旦发生这种情况，将对应用程序的性能和稳定性产生负面影响。请注意，Kubernetes 不会重启容器。

![图 10.10：Kubernetes 中 Pod 的 CPU 节流](img/Figure-10.10.jpg)

*   **内存泄漏**：应用程序持续消耗内存而不释放的场景。在 Kubernetes 中，如果内存超过限制阈值，Pod 将会被重启。

![图 10.11：内存泄漏类型](img/Figure-10.11.jpg)

左侧的两个图表展示了可能发生内存泄漏的场景——如果应用程序消耗内存且从不释放或稳定下来（左上），不要被右下角的图表搞混。在那个图表中，应用程序消耗必要的内存然后趋于稳定。关于内存泄漏还有很多可讨论的内容；不过，本书不再深入讨论。

*   **Goroutine 泄漏：** 我们已经在 *第 5 章，释放 Go 的并发威力* 中讨论过这个主题。`pprof` 包还允许我们跟踪 Golang 中 goroutine 的数量和分布。

## 告警

我们将服务部署到生产环境，并监控服务的性能和行为；我们还构建了一个整洁的仪表盘，让我们能够观测所有 API 及其通信情况。一切都很棒。遗憾的是，我们并不总是在电脑旁，有时会处于 AFK（Away From Keyboard，离开键盘）状态。然而，系统是一个始终在运行的“生命体”；当我们不在身边时，必须照顾好它。为了符合我们期望的性能，我们必须设置告警，以便在需要时通知我们。

告警是由自动化监控系统生成的信号，通过确定阈值来为关键问题提供信息。这些信息对于维护系统的健康和性能至关重要。

流行的告警系统有 PagerDuty 和 Atlassian Opsgenie。这些系统具有高级升级功能，如通过 Slack、电子邮件、短信甚至电话发送消息。我们可以通过指定 OnCall（值班）排班表来配置在特定时刻将告警发送给谁。

## 性能指标

以下是 RESTful API 的推荐性能指标。我们应该监控这些指标，并在超过某个阈值时触发告警：

*   **请求成功率**：未出现错误的请求占所有请求的百分比。例如，1000 个请求中有 2 个失败——成功率为 99.8%。在每个小数点都代表大量用户的系统中，通常用“9 的个数”来衡量性能。例如，99.9992% 的成功率就是“五个 9”。每个请求被归类为一个布尔参数，以判断请求是成功还是失败，而不考虑延迟。通常，只有 5XX 错误被归类为失败。该指标表明有多少用户在使用您的应用程序时经历了糟糕的体验。
*   **P95 延迟**：P95 代表第 95 百分位数。该指标表明 95% 的请求持续时间低于该指标值。例如，如果 P95 是 0.5 秒，则 95% 的请求延迟低于 0.5 秒。
*   **P99 延迟**：这与前一个指标相同，但针对第 99 百分位数。这两个指标都有助于确保绝大多数用户在使用 API 或应用程序时获得良好的体验。我们不想测量平均值，因为平均值会掩盖无法反映真实用户体验的异常。请注意，在测量这些指标时，我们只考虑成功的请求。

## 结论

本最后一章探讨了在生产环境中维护服务的关键方面。我们强调，生产环境中的稳定服务需要持续的关注和维护才能保持弹性。

我们深入探讨了通过遥测数据（如日志、指标和追踪）实现可观测性的重要性。这种可观测性使我们能够监控系统、检测异常并有效排查问题。我们还讨论了处理生产故障排查的各种策略，包括理论的力量、性能分析，以及使用基于配置文件引导的优化（PGO）来提升性能。

此外，我们介绍了告警系统的重要性，以便在我们不主动监控服务时通知我们关键问题。最后，我们列出了一些 RESTful API 的推荐性能指标，以确保良好的用户体验。
