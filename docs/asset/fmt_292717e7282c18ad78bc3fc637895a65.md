
* 资源可以是集合或单例。例如：
    * `GET /api/accounts`：集合资源
    * `GET /api/accounts/{id}`：单例资源；当我们想要检索单例资源时，将使用**复数**形式的 `accounts`。
* 集合/单例资源可以包含子集合，例如：
    * `GET /api/accounts/{id}/users` - users 是子集合资源。
* **使用名词，而非动词**：URI 旨在将资源描述为实体（名词）而非动作（动词）。此外，不要在 URI 中包含操作名称。
    * `GET /api/deleteAccounts/{id}` - 不好
    * `DELETE /api/accounts/{id}` - 好
* **字符约定**：
    * 使用 `-` 提高 URI 可读性：
      `GET /api/user-management`
    * 不要使用尾部斜杠：
      `GET /api/account/` - 不好
      `GET /api/account` - 好
    * 始终使用正斜杠 `/` 而非反斜杠 `\`
    * 避免使用文件扩展名：
      `GET /api/accounts/billing.json` - 不好
      `GET /api/accounts/billing` - 好

在少数场景中，端点会变得高度复杂，我们需要尽可能简化它。如果变得过于复杂，我们应该考虑将其拆分为两个或多个端点。

## 版本控制与弃用

API 是一种承诺，文档是对用户的承诺。开发人员希望因产品/工程需求引入新功能或进行破坏性更改。API 版本控制有助于实现这一目标。版本控制允许开发人员在不破坏现有客户端的情况下，在一个承诺与另一个承诺（承诺=版本）之间建立清晰的分离。

### 版本控制策略

让我们看看 API 版本控制的主流策略。

* **URI 版本控制：** API 版本包含在每个端点中。
  `GET /api/v1/accounts`
  `GET /api/v2/accounts`
  这种方法很流行且非常容易实现。然而，REST 方法希望 URI 中仅包含资源详细信息，而不包含版本。
* **查询参数版本控制：** 与 URI 版本控制类似，版本在 URI 中，但不是作为路径参数；而是作为查询参数包含在内。
  `GET /api/account?version=1`
  `GET /api/account?version=2`
  这与前一种策略相同，但不那么出名，且不要求客户端更改 URL，只需更改参数。
* **Header 版本控制：** 它包含一个指示 API 版本的 Header。
  `GET /api/accounts Headers: { "X-API-version": "1" }`
  `GET /api/accounts Headers: { "X-API-version": "2" }`
  这种方法最符合 REST 方法。然而，版本可能对用户隐藏。

### 版本控制最佳实践

让我们探讨一些最佳实践：

* **采用三部分版本控制：** 版本控制模式的最佳实践如下：`major.minor.patch`。例如，1.3.2 - 主版本号为 1，次版本号为 3，补丁版本号为 2：
    * Major：用于引入破坏性或大规模 API 更改。
    * Minor：每当引入仍向后兼容的新功能和特性时。
    * Patch：用于错误修复。
* **向后兼容性：** 始终致力于支持旧功能和特性，而不是破坏它们。我们利用向后兼容性来减少对最终客户端的影响。
* **沟通变更：** 每当发布新版本时，反映并详细说明变更内容并将其有效地传达给客户至关重要。

### 弃用

当必须弃用旧 API 版本时，我们将优雅地进行。宽限期必须非常长，并且我们必须频繁地向客户报告变更。我们必须给用户足够的时间迁移到新版本。文档也应反映弃用情况，并将端点标记为已弃用。

## 常见陷阱

以下是 REST 中的一些常见陷阱：

* **过度使用 POST HTTP 方法：** 开发人员倾向于坚持使用 POST 操作，即使这不是正确的选择。我们必须利用所有其他 HTTP 方法：`DELETE`、`PATCH`、`PUT`、`GET` 等。
* **不遵守前述约定：** “资源”一词可能会让 REST 新手感到困惑，导致糟糕的资源命名。
* **缺乏版本控制：** 我们必须按照上一节所述保持 API 版本控制和弃用策略。
* **选择不当的 HTTP 状态码：** 开发人员总是使用 200、400 和 500 状态码，而不是使用适当的 HTTP 状态码。
* **Swagger 文档混乱且包含错误信息。**
* **过度复杂化：** 开发人员最大的陷阱是使 API 变得繁琐和困惑。保持简单并不容易，但我们必须这样做。

## Kubernetes 简介

### 简介

在谈论 Kubernetes 之前，有一项需要首先解释的基础技术，即 Docker。Docker 是一个使用操作系统级虚拟化来运行称为容器的打包软件的平台。这些容器封装了应用程序及其依赖项，确保跨各种环境的一致性。作为开发人员，我们必须熟悉容器化的基本术语 —— 镜像、容器等。并学习 Dockerfile 的基本语法：[`docs.docker.com/engine/reference/builder/`](https://docs.docker.com/engine/reference/builder/)。如果您不熟悉虚拟化和容器化，建议详细阅读相关内容。

在开发者构建众多服务以组成更大的微服务架构的世界里，他们通常将这些服务打包为称为容器的可交付单元，这导致我们需要管理海量的容器。在支持每位开发者的需求和特定要求的同时，几乎不可能管理和运维如此数量的容器。幸运的是，Google 的一些人预见到了这个问题，并打造了一个单一项目来解决它。这个项目叫做 Kubernetes。

为什么我们要学习 Kubernetes？*“我只需要编写代码，让运维侧（通常是 DevOps）为我完成所有其他工作。”* 这个答案在完美的世界里是可以接受的，但现实并非如此。应用程序与其部署方式之间存在耦合。作为开发者，我们必须确保功能在生产环境中按预期运行。本地环境与生产环境之间存在巨大差异 —— 不同的参数、我们未曾考虑的边缘情况、扩展问题、安全顾虑等。为了缓解这些差异带来的问题，我们作为开发者需要了解 Kubernetes 的基础知识 —— 常见资源、发布流程、故障排查、核心最佳实践、监控等。在本章中，我们将探讨这些主题。

Kubernetes 与微服务架构有什么关系？

简单来说，Kubernetes 解决了微服务架构的许多问题和缺点。例如，在微服务架构中建议使用外部配置。Kubernetes 通过提供 `ConfigMap` 和 `Secret`（存储资源）将数据注入应用容器来解决这个问题。这就是两者结合强大的原因。

另一个例子是，可以使用 `Ingress`（Kubernetes 资源）高效地实现路由能力。

Kubernetes 是一个开源的容器编排系统。该系统由 Google 于 2014 年发明，现由 CNCF（云原生计算基金会）维护。Kubernetes 的简写是 `K8s`（因 K 和 S 之间有 8 个字母）。

## Kubernetes Adoption

如今，Kubernetes 被广泛使用，世界上大多数公司都在使用它。Kubernetes 社区庞大且逐年增长。全球有大量会议的主题仅围绕 Kubernetes。有大量与 Kubernetes 相关的开源项目和工具。

此外，一些公司拥有原生面向 Kubernetes 的产品。使用 Kubernetes 作为部署服务和工作负载的场所已成为行业标准。

Kubernetes 旨在管理容器化的工作负载和服务。此外，其目标是自动化复杂的部署流程。Kubernetes 负责部署过程的多个方面 —— 网络、配置、发布等，也负责管理 —— 存储、安全等。

Kubernetes 在其内部组合了多个工具和项目，并利用它们各自的能力。例如，Kubernetes 使用 Docker 作为容器运行时引擎，并没有自己的容器运行时引擎。Kubernetes 作为一个称为 **cluster** 的单一单元提供。我们可以通过定义期望的资源在该集群中创建资源。我们将使用 YAML 配置想要的期望资源。Kubernetes 将为我们完成所有其他工作，并努力达到我们定义的期望状态。在本章后续内容中，我们将详细阐述与软件工程师相关的不同 Kubernetes 资源。
