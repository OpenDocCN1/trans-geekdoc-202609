在这个简单的层面上，我们无法看到持久存储中数据布局的具体细节。这很大程度上取决于所考虑的具体数据库。即便如此，显而易见的是，在一种情况下，检索会找到实体的共置信息，而在另一种情况下，检索会找到属性的共置信息。另一种说法可能是：面向行的检索获取实体的属性值，但面向列的检索获取属性的实体值。

考虑一个从这些信息中查找平均体重的查询。关系型情况将要求检索每一行以及行内的体重列值，然后再计算平均值。在面向列的情况下，我们只需检索图 17.8 所示表格中的体重行，即可获得计算所需的所有值。因为从持久存储中检索数据是操作中最耗时的部分，这表明面向列的方法在某些类型的查询上具有更好的性能潜力。性能可能是这种数据库类型最大的单一驱动因素，尤其是当数据库变得更大时。在面向列的数据库中，不断增加的数据量导致行变得更大（更宽），而不是行数变多，因此这些有时被称为“宽表”。

重要的是要记住，面向列数据库的显著特征是信息在物理上的存储方式。从概念角度来看，我们仍然可以用传统方式思考数据库，但我们会发现某些类型的操作比标准规范化关系数据库更高效，而另一些则效率较低。在某些情况下，面向列的数据库可以使用标准 `SQL` 进行查询，这使得 “NoSQL” 标签显得有点毫无意义。

面向列的优势仅在查询操作作用于一列或少量几列时才有效。涉及多列的查询从单列的信息局部性中获得的收益较小。如果多个列经常一起使用，可以通过将列分组为 `列族` 来增加另一层组织。例如，与个人客户详细信息相关的列（如姓名、地址、出生日期等）可以分组为一个 “Personal” 列族。这可用于确保相关列在数据库中共置。

面向列为高效存储信息提供了额外的机会。来自一个面向行的列（在面向列的数据库中可视化为一行）的所有数据类型相同，这为对值应用各种类型的压缩打开了可能性。一个明显的例子是当列包含许多重复条目时，例如 URL 或产品名称。在某些情况下，可能可以将一列压缩得足以放入内存以供直接访问，从而显著提高响应时间。压缩很有用，因为面向列的数据库通常用于超大数据集。也不需要为 `NULL` 预留空间。面向行数据库中的空单元格在其面向列的等效物中根本不需要存在。

面向列的模式设计不仅需要考虑要存储的信息，还需要考虑数据库将如何使用以及未来可能如何演变。向数据库添加新列非常容易——只需将其追加到现有列之后，而不会影响任何现有查询。其他类型的模式更改可能更成问题。查询模式的变化也会降低数据库的有效性，如果其设计已针对不再适用的预期场景进行了优化。在面向列的情况下，设计有效的索引方案也更加困难。

面向列的数据库非常倾向于提高读操作（`SQL` 中的 `select`）的效率。诸如 `insert`（新实体）、`update`（现有实体的属性）和 `delete`（现有实体）等操作通常较慢，因为信息在物理存储中的分布方式。此外，读操作仅针对某些类型的查询得到改进。考虑以下两个 `SQL` 查询：

```
select avg(weight) from Person
select * from Person
```

在面向列的数据库中，第一个查询会更快，但第二个查询会比面向行的等效查询慢（显然，这些差异仅在大数据集中才有意义）。通常，面向行的操作或涉及多列的操作在面向列的数据库中会更慢，这使得它们不适合事务型应用程序。

### 面向列的数据库

在面向列的数据库中，表之间的连接比面向行的情况更复杂，且性能可能较低。另一种策略是考虑数据库的使用模式，并定义一个“预连接”相关表的模式。这显然需要额外的控制来确保不可避免产生的重复数据的完整性，但随后该新表在列式排列方面可像其他任何表一样处理。此处的风险在于，如果使用模式并未如预期那样出现，这种优化会导致数据库性能变得非常差。

面向列的数据库的一大优势是其处理超大数据集的能力。其结构非常适合分区。一个显而易见的第一步是垂直分区数据库，以便将不同的列（或列族）挂载到不同的服务器上。这些服务器无需类型相同。访问频率较低的列可以挂载到性能较弱的服务器上。

在每个垂直分区内，还有水平方向进一步分区的选项。一列可以拆分为分片，同样可以挂载到独立的服务器上。将查询导向相关分片需要一些额外的工作，但这提供了巨大的扩容潜力。

提高性能的另一措施是复制：相同数据的副本可存储在多个可独立访问的服务器上。这需要某种自动负载均衡机制，以将查询均匀地分发到各服务器。复制中的一个顾虑是维护不同副本（本应）相同数据之间的一致性。然而，正如已指出的，面向列的数据库最适用于更新罕见但查询频繁的场景。因为在此类情况下更新稀少，所以在合适的应用类型中，一致性问题可能易于管理。

以下特征总结了面向列的数据库应用中可能重要的特性：

* 涉及大量数据，对应传统面向行表中的数百万行。
* 高效利用存储空间很重要，例如在处理大量稀疏或重复数据时。
* 数据库操作以查询为主，数据加载后极少（甚至没有）变更。
* 查询通常使用聚合函数，如 `avg()`、`count()`、`min()`、`max()` 和 `sum()`。
* 每个单独查询仅涉及少量列。

如果我们想找一个通用术语来描述面向列数据库的应用，最合适的可能是“分析型”，常被称为 OLAP（联机分析处理）。列式存储不适合事务型系统，常被称为 OLTP（联机事务处理）。典型应用示例包括：

**数据仓库和数据集市**：这些常用于从现有数据中提取洞察。输入通常通过从事务系统抽取数据并重组为更合适的格式来创建（或更新）。信息不是逐行添加，而是通过批量加载，这可以非常高效。

**科学研究**：科学研究应用可能涉及跨大数据集的复杂查询，使面向列的数据库成为天然选择。研究人员可利用这些数据库快速高效地分析数据，从而专注于研究而非数据管理。

**金融交易**：金融交易应用通常需要实时访问大量数据。面向列的数据库专为处理此类数据而设计，使交易员能快速准确地获取信息。

**历史数据分析**：存储的数据可使用各种统计和逻辑方法及技术进行建模和分析，以获得各类洞察，如描述性、探索性、预测性、诊断性和处方性视角。

## 17.4 文档数据库

在第 3 章中，我们讨论了如何分析报表和其他文档，并用基本事实类型来表达。在 ORM 中对这些事实类型及相关约束建模，可得到一个模型，该模型可作为数据库模式的基础。文档数据库采取不同方法，直接使用文档的原始结构存储文档，因此，顾名思义，此类数据库由文档集合组成。由于无需预先分析文档，似乎可将任何类型的文档添加到任何集合中，无需任何准备。原则上，这承诺了极大的灵活性，但在实践中，需要一定程度的控制，才能指望在数据库的整个生命周期内使其可管理。

有多种文档数据库系统可用，包括：

* **MongoDB** 是最流行的文档数据库之一。它以灵活的、类 JSON 的文档存储数据，并允许动态模式。
* **Couchbase** 是一个分布式 NoSQL 数据库，提供高性能和可扩展性。它常用于需要实时数据更新、缓存和移动同步的应用。
* **CouchDB** 是一个专注于易于复制和冲突解决的开源文档数据库。
* 云服务提供商提供文档数据库，如 **Amazon DocumentDB** 和 **Google Firestore**。
* **MarkLogic** 是一个支持灵活模式设计的 NoSQL 数据库，以 XML 或 JSON 文档存储数据。它常用于需要复杂数据建模和查询的应用。

本章示例基于 **MongoDB**，尽管其他文档数据库系统具有大体相似的能力，我们将讨论这些能力。

文档通常使用 `JSON` 的结构能力来表达，JSON 在第 16 章中已有描述。内部存储可能采用 `BSON`，一种包含额外元数据的 JSON 二进制形式，可加快数据扫描并减少存储需求，但我们将忽略此细节。

文档数据库由*集合*组成。每个集合包含同类*文档*：例如 Products（产品）、Orders（订单）、Customers（客户）等。每个文档可包含多个*字段*，但字段中的数据不必像规范化关系数据库那样是单值的——字段可包含一个结构，该结构又可包含其他结构，以此类推。这些概念与其关系对应物之间有粗略的对应关系，如表 17.1 所示。

### 六点注意事项

1. **`_id` 字段**已自动生成，用于为每个文档提供唯一标识符。为简化起见，我们将在后续示例中忽略此功能。

2. **字段名一致性**：不同文档中相同字段的名称无需保持一致。第一个文档中的 `activeDate` 字段和第二个文档中的 `startDate` 可能指代相同的业务概念，但它们的字段名称不同。

3. **数据类型一致性**：相同字段在不同文档中的数据类型无需相同。`customerId` 字段在第一个文档中是字母数字型，但在第二个文档中是数字型。

4. **字段值类型**：字段可以是多值的，也可以包含其他文档，如两个文档中的 `staffAllocation` 所示。

5. **内部结构灵活性**：集合中每个文档的内部结构无需相同。`staffAllocation` 字段在第一个文档中是一个列表，但在第二个文档中是一个对象（JSON 意义上），包含多个列表。

6. **字段存在性**：同一集合中的不同文档无需包含相同的字段。`contractType` 字段出现在第二个文档中，但在第一个文档中不存在。

这种灵活性有时被宣称为文档数据库相对于关系型数据库的巨大优势。在关系型数据库中，表中的每一行（相当于集合中的每个文档）都具有固定的结构，且每一列（相当于文档中的每个字段）都有定义好的数据类型。虽然这种灵活性使得添加文档变得容易，无需担心任何模式约束，但它使得对这种不受控数据库的其他操作几乎成为一项无法管理的任务。即使是检索特定字段值这样简单的操作，也可能需要检查集合以确定该字段名称的所有变体，从而编写足够健壮的查询。在上面的示例中，列出所有合同开始日期需要同时查询 `startDate` 和 `activeDate`（以及可能使用的任何其他名称变体）。

可以向集合添加**验证器**，以将其包含的文档约束为可接受的结构。这可以包括对必填字段、数据类型、值范围等的检查。实际上，验证器可以为单个关系表提供类似模式的功能。

文档的写入操作是**原子**的，因为文档要么完整写入，要么完全不写入。涉及多个文档的写入可以是**事务性**的，但这需要一些额外的工作。必须为每次更新创建一个会话，然后将会话组合在一起，以便所有更新要么一起完成，要么完全不完成。无论集合是物理存储在同一服务器上还是分布在多个服务器上，情况都是如此。此类操作对性能有很大影响，一般建议尽可能调整模式以避免这种情况。例如，与其对集合 A 和集合 B 进行事务性更新，不如定义一个新的 AB 集合，以便通过单次写入操作处理更新。

### 关联数据

插入、检索和管理单个文档相对简单，但在任何现实的数据库中，几乎肯定需要将不同的文档关联起来。这可以被视为关系数据库中外键引用的等价物。在文档数据库中，有两种方法可以实现这一点。为了提供示例，假设我们有（高度简化的）与大学课程中学生及其成绩相关的文档。

#### 嵌入

将课程和学生与客户关联的第一种方法是**嵌入**。通常，如果 `Document1` 需要关联到 `Document2`，可以通过将一个文档嵌套在另一个文档中来实现。在本例中，我们假设 `Course` 文档包含 `Student` 详细信息。

```
{  
  "Courses": [    
    {
      "_id": "DB102",    
      "courseName": "Databases",    
      "creditValue": 15,    
      "Students": [        
        {"studentId": "12345", "name": "Abby Akbar", "grade": 3.4},        
        {"studentId": "67890", "name": "Bill Briggs", "grade": 3.2}        
      ]    
    },    
    {
      "_id": "SW101",    
      "courseName": "Python",    
      "creditValue": 10,    
      "Students": [        
        {"studentId": "12345", "name": "Abby Akbar", "grade": 3.8}        
      ]     
    }  
  ] 
}
```

使用标准 JSON 结构，也可以将 `Courses` 列表嵌入到 `Student` 文档中。哪种方式更可取取决于数据的预期用法。在本例中，虽然我们有两种不同类型的信息（Courses 和 Students），但最终只得到一个文档集合：要么是 Courses（如上），要么是 Students，具体取决于我们决定如何嵌入文档。

很明显，以这种方式嵌入数据会导致冗余，这对应于关系数据库中的**反规范化**。考虑到硬件成本的下降，额外的存储空间需求可能是可以接受的。更严重的是保持一致性的问题。在上面的示例中，如果我们发现 Abby Akhbar 的名字可能拼写错误，我们必须找到所有可能包含她名字的 Course 文档以进行必要的更改。如果不严格执行此操作，结果将是一个不可靠且难以管理的数据存储。如果相反，我们将 Courses 嵌入到 Students 中，更新 Course 详细信息将需要访问所有 Student 文档。

#### 引用

**嵌入**的替代方法是**引用**。这一概念与关系数据库中使用外键引用的方式非常接近。使用与上面相同的示例，我们可以将 Course 文档和 Student 文档放入不同的集合中，如下例所示。

```
{
  "Courses": [
    {
      "_id": "DB102",
      "courseName": "Databases",
      "creditValue": 15
    },
    {
      "_id": "SW101",
      "courseName": "Python",
      "creditValue": 10
    }
  ]
}
```

```
{
  "Students": [
    {
      "_id": "12345",
      "name": "Abby Akbar",
      "courses": [
        {"courseId": "DB102", "grade": 3.4},
        {"courseId": "SW101", "grade": 3.8}
      ]
    },
    {
      "_id": "67890",
      "name": "Bill Briggs",
      "courses": [
        {"courseId": "DB102", "grade": 3.2}
      ]
    }
  ]
}
```
