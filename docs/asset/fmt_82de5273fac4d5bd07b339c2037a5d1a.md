
# ARP 缓存投毒

**ARP 缓存投毒** 是由攻击者响应 ARP 广播查询并发回伪造回复而导致的。如果客户端在收到有效回复之前先收到了虚假回复，则该虚假回复将被用于填充 ARP 缓存，而有效回复会被丢弃（视为超出开放查询范围）。**ARP 缓存** 的动态内容（无论是被投毒的还是合法的）将保留在缓存中，直到发生超时（通常在 10 分钟以内）。ARP 用于将 Internet 协议（`IP`）地址解析为适当的 MAC 地址，以便为数据传输构建以太网帧头。一旦 IP 到 MAC 的映射从缓存中失效，当客户端重新执行 ARP 广播查询时，攻击者便获得了另一次投毒 ARP 缓存的机会。

ARP 缓存投毒的第二种形式是创建静态 ARP 条目。这通过 `ARP` 命令完成，且必须在本地执行。但通过在客户端上执行脚本（通过木马、缓冲区溢出或社会工程学攻击），这很容易实现。静态 ARP 条目是永久的，甚至跨系统重启依然有效。一旦发生 ARP 投毒（无论是针对永久条目还是动态条目），客户端发送的流量将被发送到非预期的系统。这是由于将错误的或不同的硬件地址（即 MAC 地址）与某个 IP 地址关联所致。ARP 缓存投毒或简称 ARP 投毒是建立中间人攻击的一种手段。

## DNS 缓存投毒

实施中间人攻击的另一种流行手段是 **DNS 缓存投毒**。与 ARP 缓存类似，一旦客户端收到来自 DNS 的响应，该响应将被缓存以供将来使用。如果能向 **DNS 缓存** 注入虚假信息，则误导通信就变得轻而易举。实施 DNS 缓存投毒的方法有很多，包括 `HOSTS` 文件投毒、授权 DNS 服务器攻击、缓存 DNS 服务器攻击、DNS 查找地址篡改和 DNS 查询欺骗。

### HOSTS 文件投毒

**HOSTS 文件** 是支持传输控制协议/Internet 协议（`TCP/IP`）的系统上发现的静态文件，包含域名及其关联 IP 地址的硬编码引用。HOSTS 文件用于当今基于动态查询的 DNS 系统之前，但它作为一种后备措施或强制解析的手段而保留。管理员或黑客可以向 HOSTS 文件添加内容，在 **FQDN（完全合格域名）** 与自选 IP 地址之间建立映射关系。如果攻击者能在 HOSTS 文件中植入虚假信息，则系统启动时 HOSTS 文件的内容将被读入内存并生效。与最终会超时并从缓存过期的动态查询不同，来自 HOSTS 文件的条目是永久的。

### 授权 DNS 服务器攻击

授权 DNS 服务器攻击旨在篡改 FQDN 在其原始宿主系统（即主要授权 DNS 服务器）上的主记录。**主要授权 DNS 服务器** 托管区域文件或域数据库。如果该原始数据集被篡改，这些变更最终将传播至整个 Internet。然而，针对授权 DNS 服务器的攻击通常会被迅速发现，因此很少导致大规模利用。因此，大多数攻击者将目标集中在缓存 DNS 服务器上。

### 缓存 DNS 服务器攻击

**缓存 DNS 服务器** 是指部署用于缓存来自其他 DNS 服务器的 DNS 信息的任何 DNS 系统。大多数公司和 ISP 为其用户提供缓存 DNS 服务器。托管在缓存 DNS 服务器上的内容不受全球安全社区监控，仅由本地运营商监管。因此，针对缓存 DNS 服务器的攻击可能在相当长的一段时间内不被察觉。有关缓存 DNS 服务器攻击如何发生的详细信息，请参阅“Kaminsky DNS 漏洞图解指南”：[`unixwiz.net/techtips/iguide-kaminsky-dns-vuln.html`](http://unixwiz.net/techtips/iguide-kaminsky-dns-vuln.html)。尽管这两种攻击都针对 DNS 服务器，但它们最终影响的是客户端。一旦客户端执行动态 DNS 解析，从授权 DNS 服务器或缓存 DNS 服务器接收到的信息将临时存储在客户端的本地 DNS 缓存中。如果该信息是虚假的，则客户端的 DNS 缓存就被投毒了。

### DNS 查找地址篡改

第四种 DNS 投毒示例侧重于向客户端发送一个备用 IP 地址，使其作为客户端用于解析查询的 DNS 服务器。DNS 服务器地址通常通过动态主机配置协议（`DHCP`）分发给客户端，但也可以静态分配。即使所有其他 IP 配置元素均由 DHCP 分配，本地修改也可以轻松地静态指定 DNS 服务器地址。篡改客户端 DNS 服务器查找地址的攻击可通过脚本（类似于前面提到的 ARP 攻击）或通过攻破 DHCP 来实施。一旦客户端使用了错误的 DNS 服务器，它们将把查询发送给黑客控制的 DNS 服务器，后者将响应投毒的结果。

### DNS 查询欺骗

第五种 DNS 投毒示例是 DNS 查询欺骗。当黑客能够窃听客户端向 DNS 服务器发出的查询时，就会发生这种攻击。攻击者随后发回包含虚假信息的回复。如果客户端接受该虚假回复，就会将该信息放入其本地 DNS 缓存中。当真正的回复到达时，由于原始查询已被应答，它将被丢弃。无论采用这五种 DNS 攻击中的哪一种，虚假条目都将存在于客户端的本地 DNS 缓存中。因此，所有 IP 通信都将被发送到错误的端点。这使得黑客可以通过操作该虚假端点并将流量转发至正确目的地来建立中间人攻击。

## Internet 文件缓存投毒

关于本地缓存的第三个关注领域是临时 Internet 文件或 Internet 文件缓存。这是从 Internet 站点下载的文件的临时存储，由客户端的工具程序保留以供当前和将来可能的使用。该缓存主要包含网站内容，但其他 Internet 服务也可以使用文件缓存。多种攻击手段（如拆分响应攻击）可导致客户端下载并缓存非请求网页预期元素的内容。移动代码脚本攻击也可用于在缓存中植入虚假内容。一旦缓存中的文件被投毒，即使合法的 Web 文档调用缓存项，恶意项目也会被激活。

## 缓解与防御

缓解或解决这些攻击并不总是简单或直接的。没有简单的补丁或更新能防止这些攻击针对客户端发起。这是因为这些攻击利用了内置于各种协议、服务和应用程序中的正常且正确的机制。因此，防御不仅仅是修补缺陷的补丁，而更多的是一种检测和预防的工作。总体而言，作为起点，请保持操作系统和应用程序通过其各自供应商的补丁保持最新。接下来，部署基于主机的 IDS（`host-IDS`）和基于网络的 IDS（`network-IDS`）工具，以监控此类滥用行为。定期审查 DNS 和 DHCP 系统的日志，以及本地客户端系统日志，并可能包括防火墙、交换机和路由器日志，以查找指示异常或可疑事件的条目。

# 组织应使用拆分 DNS 系统

组织应使用 `split-DNS` 系统（也称为拆分视界 DNS、拆分视图 DNS 和拆分大脑 DNS）。`split-DNS` 是部署一台供公众使用的 DNS 服务器和一台供内部使用的独立 DNS 服务器。公共 DNS 服务器上区域文件中的所有数据均可通过查询或探测被公众访问。然而，内部 DNS 仅供内部使用。只有内部系统被授予访问权限以与内部 DNS 服务器交互。通过阻止传输控制协议 (TCP) 和用户数据报协议 (UDP) 的入站端口 53，禁止外部人员访问内部 DNS 服务器。`TCP 53` 用于区域传输（包括大多数 DNS 服务器到 DNS 服务器的通信），而 `UDP 53` 用于查询（即任何非 DNS 系统向 DNS 服务器发送查询）。内部系统可配置为仅与内部 DNS 服务器交互，也可允许其向外部 DNS 服务器发送查询（这需要防火墙为状态检测防火墙，并配置为允许响应从经批准的出站查询返回到内部系统）。

## 基于服务器的系统

一个重要的基于服务器的关注领域（可能也包括客户端）是 `data flow control`（数据流控制）问题。数据流是指数据在进程之间、设备之间、跨网络或跨通信通道的移动。数据流的管理不仅确保了高效传输，延迟或延迟最小化，还确保了使用哈希的可靠吞吐量和使用加密的机密性保护。数据流控制还确保接收系统不会因流量过载而不堪重负，特别是不会达到丢弃连接或遭受恶意甚至自我造成的拒绝服务的地步。当发生数据溢出时，数据可能会丢失或损坏，或触发重传需求。这些结果是不可取的，因此通常会实施数据流控制以防止这些问题发生。数据流控制可由网络设备（包括路由器和交换机）以及网络应用程序和服务提供。

负载均衡器用于将网络流量负载分散或分布到多个网络链路或网络设备上。负载均衡器可能能够提供对数据流更多的控制。负载均衡的目的是获得更优化的基础设施利用率，最小化响应时间，最大化吞吐量，减少过载，并消除瓶颈。虽然负载均衡可用于各种情况，但常见的实现是将负载分散到服务器场或集群的多个成员上。负载均衡器可能会使用多种技术来执行负载分发，包括随机选择、轮询、负载/利用率监控和优先级偏好。

拒绝服务攻击可能会严重损害数据流控制。监控 DoS 攻击并实施缓解措施非常重要。请参阅第 12 章和第 17 章，了解这些攻击和潜在防御的讨论。

## 数据库系统安全

`Database security`（数据库安全）是任何将大量数据集作为核心资产的组织的重要组成部分。如果没有数据库安全工作，业务任务可能会中断，机密信息可能会泄露。对于 CISSP 考试，重要的是你要了解与数据库安全相关的几个主题。这些包括聚合、推理、数据挖掘、数据仓库和数据分析。

### 聚合

SQL 提供了许多函数，可将来自一个或多个表的记录组合起来，生成潜在有用的信息。此过程称为 `aggregation`（聚合）。聚合并非没有安全漏洞。聚合攻击用于收集大量低级安全项目或低价值项目，并将它们组合起来，创建出具有更高安全级别或价值的东西。

尽管这些函数极其有用，但它们也对数据库中信息的安全构成风险。例如，假设一名低级军事记录职员负责在人员和装备从一个基地调往另一个基地时更新记录。作为其职责的一部分，该职员可能被授予查询和更新人员表所需的数据库权限。

军方可能不认为单个调动请求（即琼斯中士从 X 基地调往 Y 基地）属于机密信息。记录职员有权访问该信息，因为他需要它来处理琼斯中士的调动。然而，借助聚合函数的访问权限，记录职员可能能够统计全球每个军事基地分配的部队数量。这些兵力水平通常是严格保密的军事机密，但这名低级别的记录职员可以通过跨大量非机密记录使用聚合函数来推断出它们。

因此，数据库安全管理员严格控制对聚合函数的访问，并充分评估其可能向未经授权的个人泄露的潜在信息，这一点尤为重要。

### 推理

推理攻击带来的数据库安全问题与数据聚合的威胁类似。`Inference`（推理）攻击涉及将多条非敏感信息组合起来，以获取本应被归类为更高级别的信息。然而，推理利用的是人类思维的演绎能力，而非现代数据库平台的原始数学能力。

推理攻击的一个常见例子是大型企业的会计职员，他们被允许检索公司用于高层报告的工资总额，但不被允许访问个别员工的工资。会计职员经常需要准备过去生效日期的报告，因此被允许访问过去一年内任何一天的工资总额。例如，假设该职员还必须知道各员工的雇佣和解雇日期，并有权访问此信息。这为推理攻击打开了方便之门。如果某员工是某特定日期唯一被雇佣的人，会计职员现在可以检索该日期和前一天的工资总额，从而推断出该特定员工的工资——这是用户无权直接访问的敏感信息。

与聚合一样，防御推理攻击的最佳方法是持续监控授予个别用户的权限。此外，可使用有意模糊数据来防止推断敏感信息。例如，如果会计职员只能检索四舍五入到最近一百万的工资信息，他们可能无法获得关于个别员工的任何有用信息。最后，您可以使用数据库分区（本章前面已讨论）来帮助挫败这些攻击。

### 数据挖掘和数据仓库

许多组织使用称为 `data warehouses`（数据仓库）的大型数据库，从各种数据库存储大量信息，以供专门的分析技术使用。这些数据仓库通常包含详细的历史信息，由于存储限制或数据安全顾虑，这些信息通常不存储在生产数据库中。

`data dictionary`（数据字典）通常用于存储关于数据的关键信息，包括用法、类型、来源、关系和格式。数据库管理系统 (DBMS) 软件读取数据字典，以确定试图访问数据的用户的访问权限。

# 数据挖掘与分析

**数据挖掘**技术允许分析师梳理数据仓库并寻找潜在的相关信息。例如，分析师可能会发现灯泡的需求总是在冬季月份增加，然后在规划定价和促销策略时利用这一信息。数据挖掘技术会产生数据模型，可用于预测未来活动。

数据挖掘活动会产生**元数据**。**元数据**是关于数据的数据或关于数据的信息。元数据不仅仅是数据挖掘操作的结果；其他功能或服务也可以产生元数据。可以将数据挖掘操作产生的元数据视为数据的浓缩。它也可以是超集、子集或较大数据集的表示。元数据可以是数据集中重要的、显著的、相关的、异常的或离群的元素。

元数据的一个常见安全示例是安全事件报告。事件报告是通过使用安全审计数据挖掘工具，从审计日志数据仓库中提取的元数据。在大多数情况下，元数据比仓库中的大量数据具有更高的价值或敏感性（由于披露原因）。因此，元数据存储在一个称为**数据集市**的更安全的容器中。

数据仓库和数据挖掘对安全专业人员至关重要，主要有两个原因。首先，如前所述，数据仓库包含大量潜在敏感信息，容易受到聚合和推理攻击，安全从业者必须确保已采取适当的访问控制和其他安全措施来保护这些数据。其次，当数据挖掘用于为基于统计异常的入侵检测系统开发基线时，它实际上可以作为一种安全工具。数据挖掘用于在大量安全相关数据中“搜寻”异常事件，这些事件可能表明正在进行的攻击、失陷或违规。

## 数据分析

**数据分析**是检查原始数据的科学，其重点是从海量信息集中提取有用信息。数据分析的结果可能侧重于重要的离群值或偏离正常或标准项目的异常值、所有数据项的摘要，或对有趣信息的某种聚焦提取和组织。随着越来越多的组织从其客户和产品中收集惊人的数据量，数据分析正成为一个不断发展的领域。待处理的海量信息催生了一整类新的数据库结构和分析工具。它甚至获得了“大数据”的绰号。

**大数据**指的是数据集合变得如此之大，以至于传统的分析或处理手段变得无效、低效且不足。大数据涉及许多棘手的挑战，包括收集、存储、分析、挖掘、传输、分发和结果展示。如此大量的数据有可能揭示更平凡的数据集无法解决的细微差别和特性。从大数据中学习的潜力巨大，但处理大数据的负担同样巨大。随着数据量的增加，数据分析的复杂性也随之增加。大数据分析需要在大规模并行或分布式处理系统上运行高性能分析。就安全而言，组织正致力于收集越来越详细和详尽的事件数据和访问数据。收集这些数据的目的是评估合规性、提高效率、提高生产力和检测违规行为。

## 大规模并行数据系统

**并行数据系统**或**并行计算**是一种设计用于同时执行大量计算的计算系统。但并行数据系统通常远不止基本的多处理能力。它们通常包含将大任务分解为较小元素，然后将每个子元素分发到不同的处理子系统进行并行计算的概念。这种实现基于这样一种思想：如果将某些问题分解为可以并发处理的较小任务，就能高效地解决。并行数据处理可以通过使用不同的 CPU 或多核 CPU、使用虚拟系统，或这些方式的任意组合来实现。大规模并行数据系统还必须关注性能、功耗和可靠性/稳定性问题。

在多处理或并行处理领域，存在几个分支。第一个分支是**非对称多处理 (AMP)** 和**对称多处理 (SMP)** 之间的区别。在 AMP 中，处理器通常相互独立运行。通常每个处理器都有自己的操作系统和/或任务指令集。在 AMP 下，处理器可被配置为仅执行特定代码或操作特定任务（或特定代码或任务仅允许在特定处理器上运行；在某些情况下这可能称为**亲和性**）。在 SMP 中，处理器共享一个通用的操作系统和内存。处理器集合也共同协作处理单个任务、代码或项目。AMP 的一种变体是**海量并行处理 (MPP)**，即将多个 SMP 系统链接在一起，以便跨多个链接系统中的多个进程处理单个主要任务。传统上 MPP 涉及多个机箱，但现代 MPP 通常实现在同一芯片上。

大规模并行数据系统领域仍在不断发展。很可能还有许多管理问题有待发现，而已知问题的解决方案仍在探索中。大规模并行数据管理很可能是管理大数据的关键工具，并通常涉及云计算、网格计算或对等计算解决方案。这三个概念将在以下章节中介绍。

## 分布式系统与端点安全

随着计算从**主机/终端模型**（用户可物理分布，但所有功能、活动、数据和资源驻留在单个集中式系统上）演变为**客户端-服务器模型**（用户操作独立、功能齐全的台式计算机，但也访问网络服务器上的服务和资源），安全控制和概念也必须随之演变以适应变化。这意味着客户端具备计算和存储能力，通常多台服务器也是如此。客户端-服务器模型网络的概念也称为分布式系统或分布式架构。因此，安全必须无处不在，而不仅仅针对单个集中式主机。从安全角度来看，这意味着由于处理和存储分布在多个客户端和服务器上，所有这些计算机都必须得到适当的保护和安全防护。这也意味着客户端和服务器之间的网络链路（在某些情况下，这些链路可能并非纯粹是本地的）也必须得到保护和安全防护。在评估安全架构时，务必包含对分布式架构相关需求和风险的评估。

# 分布式架构的安全性

分布式架构容易遭受单体主机/终端系统中无法想象的漏洞攻击。桌面系统可能包含敏感信息，这些信息面临泄露风险，因此必须得到保护。个人用户可能缺乏通用的安全知识或意识，因此底层架构必须弥补这些不足。台式机、工作站和笔记本电脑可能成为分布式环境中其他关键信息系统的访问入口，因为用户需要访问网络服务器和服务来完成工作。通过允许用户机器访问网络及其分布式资源，组织也必须认识到，如果这些用户机器被滥用或攻破，它们可能成为威胁。必须对这类软件和系统漏洞及威胁进行妥善评估和处理。

通信设备也可能为分布式环境提供不必要的入口点。例如，连接在同时接入组织网络的台式机上的调制解调器，会使该网络容易遭受拨号攻击。客户端系统上的无线适配器也存在被用来创建开放网络的风险。同样，从互联网下载数据的用户会增加其自身及其他系统感染恶意代码、特洛伊木马等的风险。台式机、笔记本电脑、平板电脑、手机和工作站——及其关联的磁盘或其他存储设备——可能无法防范物理入侵或盗窃。最后，当数据仅驻留在客户端机器上时，可能无法通过适当的备份来保护（通常服务器会定期备份，但客户端计算机往往不会）。

上述分布式架构中潜在漏洞的罗列表明，此类环境需要大量防护措施来实施适当的安全性，并确保消除、缓解或补救这些漏洞。客户端必须遵守对其内容和用户活动施加防护的策略。这些措施包括：

*   必须对电子邮件进行筛选，使其无法成为恶意软件感染的载体；电子邮件还应遵守管控适当使用和限制潜在责任的策略。
*   必须制定下载/上传策略，对进出数据进行筛选并拦截可疑材料。
