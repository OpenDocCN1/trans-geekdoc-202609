## 12.8 显示类型的方法

我们反射的最后一个示例使用 `reflect.Type` 来打印任意值的类型并枚举其方法：

点击此处查看代码图像

gopl.io/ch12/methods

```go
func Print(x interface{}) {
    v := reflect.ValueOf(x)
    t := v.Type()
    fmt.Printf("type %s\n", t)
    for i := 0; i < v.NumMethod(); i++ {
        methType := v.Method(i).Type()
        fmt.Printf("func (%s) %s%s\n", t, t.Method(i).Name,
            strings.TrimPrefix(methType.String(), "func"))
    }
}
```

`reflect.Type` 和 `reflect.Value` 都有一个名为 `Method` 的方法。每次 `t.Method(i)` 调用返回一个 `reflect.Method` 实例，这是一个结构体类型，描述单个方法的名称和类型。每次 `v.Method(i)` 调用返回一个 `reflect.Value`，代表一个方法值（§6.4），即绑定到其接收者的方法。使用 `reflect.Value.Call` 方法（此处因篇幅限制不作展示），可以像调用这种 `Func` 类型的 `Value` 一样进行调用，但本程序只需要它的 `Type`。

## 12.9 一句忠告

反射 API 的内容远不止我们有空间展示的这些，但前面的示例已经让你了解可能实现的功能。反射是一个强大且富有表现力的工具，但应谨慎使用，主要有三个原因。

第一个原因是基于反射的代码比较脆弱。对于每一个会导致编译器报告类型错误的失误，都有相应的反射误用方式，但编译器会在构建时报告错误，而反射错误则在执行期间作为 panic 报告，可能是在程序编写很久之后，甚至是在程序开始运行很久之后。

如果 `readList` 函数（§12.6）例如在填充 `int` 类型变量时需要从输入读取字符串，对 `reflect.Value.SetString` 的调用将会 panic。大多数使用反射的程序都有类似的隐患，需要相当细致的注意力来跟踪每个 `reflect.Value` 的类型、可寻址性和可设置性。

避免这种脆弱性的最佳方法是确保反射的使用完全封装在你的包内，并且如果可能，在包的 API 中避免使用 `reflect.Value` 而改用具体类型，以将输入限制为合法值。如果做不到这一点，请在每次有风险的操作前执行额外的动态检查。以标准库为例，当 `fmt.Printf` 将动词应用于不合适的操作数时，它不会神秘地 panic，而是打印一条信息丰富的错误消息。程序仍然有 bug，但更容易诊断。

点击此处查看代码图像

```go
fmt.Printf("%d %s\n", "hello", 42) // "%!d(string=hello) %!s(int=42)"
```

反射还降低了自动重构和分析工具的安全性和准确性，因为它们无法确定或依赖类型信息。

避免反射的第二个原因是，既然类型作为一种文档形式，而反射操作无法接受静态类型检查，大量使用反射的代码通常难以理解。始终要仔细记录接受 `interface{}` 或 `reflect.Value` 的函数所期望的类型和其他不变量。

第三个原因是，基于反射的函数可能比针对特定类型专门化的代码慢一到两个数量级。在典型程序中，大多数函数与整体性能无关，因此如果反射能让程序更清晰，使用它是可以的。测试特别适合使用反射，因为大多数测试使用小数据集。但对于关键路径上的函数，最好避免使用反射。

# 13. 底层编程

Go 的设计保证了许多安全属性，限制了 Go 程序“出错”的方式。编译期间，类型检查会检测出大多数将操作应用于不适合其类型的值的尝试，例如，用一个字符串减去另一个字符串。严格的类型转换规则防止了直接访问字符串、映射、切片和通道等内置类型的内部结构。

对于无法静态检测的错误，例如越界数组访问或空指针解引用，动态检查确保每当发生禁止操作时，程序都会立即终止并显示信息丰富的错误。自动内存管理（垃圾回收）消除了“释放后使用” bug 以及大多数内存泄漏。

许多实现细节对 Go 程序是不可见的。无法发现聚合类型（如结构体）的内存布局、函数的机器码，或当前 goroutine 运行所在的操作系统线程的标识。实际上，Go 调度器会自由地将 goroutine 从一个线程移动到另一个线程。指针标识一个变量而不透露变量的数字地址。地址可能会随着垃圾回收器移动变量而改变；指针会被透明地更新。

这些特性共同使 Go 程序（尤其是失败的程序）比 C 语言程序（典型的底层语言）更具可预测性，也更少神秘感。通过隐藏底层细节，它们还使 Go 程序具有高度可移植性，因为语言语义在很大程度上独立于任何特定的编译器、操作系统或 CPU 架构。（并非完全独立：某些细节会泄露出来，例如处理器的字长、某些表达式的求值顺序，以及编译器施加的实现限制集合。）

有时，我们可能会选择放弃其中一些有益的保证，以实现尽可能高的性能、与其他语言编写的库互操作，或实现无法用纯 Go 表达的函数。

在本章中，我们将了解 `unsafe` 包如何让我们跳出常规规则，以及如何使用 `cgo` 工具为 C 库和操作系统调用创建 Go 绑定。

本章描述的方法不应轻率使用。如果不仔细注意细节，它们可能会导致 C 程序员深恶痛绝的那种不可预测、难以捉摸、非局部的故障。使用 `unsafe` 还会使 Go 关于与未来版本兼容性的保证失效，因为无论有意还是无意，很容易依赖未指定的实现细节，而这些细节可能会意外变更。

`unsafe` 包颇具魔力。虽然它看起来像一个常规包并以常规方式导入，但实际上它是由编译器实现的。它提供了许多内置语言特性的访问权限，这些特性通常不可用，因为它们暴露了 Go 内存布局的细节。将这些特性作为一个单独的包呈现，使得需要它们的罕见场合更加显眼。此外，出于安全原因，某些环境可能会限制 `unsafe` 包的使用。

`unsafe` 包广泛用于与操作系统交互的底层包（如 `runtime`、`os`、`syscall` 和 `net`）中，但普通程序几乎从不需要它。

## 13.1 `unsafe.Sizeof`、`Alignof` 和 `Offsetof`

`unsafe.Sizeof` 函数报告其操作数表示的大小（以字节为单位），操作数可以是任意类型的表达式；该表达式不会被求值。对 `Sizeof` 的调用是一个类型为 `uintptr` 的常量表达式，因此结果可用作数组类型的维度，或用于计算其他常量。

点击此处查看代码图像

```go
import "unsafe"

fmt.Println(unsafe.Sizeof(float64(0))) // "8"
```

`Sizeof` 仅报告每个数据结构固定部分的大小，例如字符串的指针和长度，但不包括字符串内容等间接部分。下表显示了所有非聚合 Go 类型的典型大小，尽管确切大小可能因工具链而异。为了可移植性，我们以字（word）为单位给出了引用类型（或包含引用的类型）的大小，其中在 32 位平台上一个字为 4 字节，在 64 位平台上为 8 字节。

| 类型 | 大小 |
| --- | --- |
| `bool` | 1 字节 |
| `intN`、`uintN`、`floatN`、`complexN` | `N` / 8 字节（例如，`float64` 为 8 字节） |
| `int`、`uint`、`uintptr` | 1 字 |
| `*T` | 1 字 |
| `string` | 2 字（数据、长度） |
| `[]T` | 3 字（数据、长度、容量） |
| `map` | 1 字 |
| `func` | 1 字 |
| `chan` | 1 字 |
| `interface` | 2 字（类型、值） |

当值正确*对齐*时，计算机从内存加载和存储值的效率最高。例如，两字节类型（如 `int16`）的值的地址应为偶数，四字节值（如 `rune`）的地址应为 4 的倍数，八字节值（如 `float64`、`uint64` 或 64 位指针）的地址应为 8 的倍数。更高倍数的对齐要求很少见，即使对于 `complex128` 等较大的数据类型也是如此。

因此，聚合类型（结构体或数组）的值的大小至少是其字段或元素大小之和，但由于存在“空洞”，可能会更大。空洞是编译器添加的未使用空间，以确保后续字段或元素相对于结构体或数组的起始位置正确对齐。

语言规范并不保证字段声明的顺序就是它们在内存中布局的顺序，因此理论上编译器可以自由地重新排列它们，尽管在我们撰写本书时，还没有编译器这样做。如果结构体字段的类型大小不同，按能使它们尽可能紧凑排列的顺序声明字段可能会更节省空间。下面三个结构体拥有相同的字段，但第一个比另外两个最多需要 50% 更多的内存：

```go
// 64-bit    32-bit
struct{ bool; float64; int16 }   // 3 字长   4 字长
struct{ float64; int16; bool }   // 2 字长   3 字长
struct{ bool; int16; float64 }   // 2 字长   3 字长
```

对齐算法的细节超出了本书的范围，而且当然也不值得为每个结构体都担心这个问题，但高效的打包可能会让频繁分配的数据结构更加紧凑，从而运行得更快。

`unsafe.Alignof` 函数返回其参数类型所需的对齐倍数。与 `Sizeof` 一样，它可以应用于任意类型的表达式，并返回一个常量。通常，布尔和数值类型按其自身大小对齐（最多 8 字节），而所有其他类型按字长对齐。

`unsafe.Offsetof` 函数的操作数必须是一个字段选择器 `x.f`，它计算字段 `f` 相对于其所属结构体 `x` 起始地址的偏移量，包括可能存在的空洞。

图 13.1 展示了一个结构体变量 `x` 及其在典型 32 位和 64 位 Go 实现中的内存布局。灰色区域代表空洞。

```go

    a bool
    b int16
    c []int
}
```

## 13.2 `unsafe.Pointer`

大多数指针类型写作 `*T`，意为“指向类型为 `T` 的变量的指针”。`unsafe.Pointer` 类型是一种特殊的指针，它可以存放任意变量的地址。当然，我们不能通过 `*p` 对 `unsafe.Pointer` 进行间接引用，因为我们不知道该表达式应该具有什么类型。与普通指针一样，`unsafe.Pointer` 也是可比较的，并且可以与 `nil` 比较，`nil` 是该类型的零值。

普通的 `*T` 指针可以转换为 `unsafe.Pointer`，而 `unsafe.Pointer` 可以转换回普通指针，不一定是相同类型 `*T`。例如，通过将 `*float64` 指针转换为 `*uint64`，我们可以检查浮点变量的位模式：

```go
package math

func Float64bits(f float64) uint64 { return *(*uint64)(unsafe.Pointer(&f)) }

fmt.Printf("%#016x\n", Float64bits(1.0)) // "0x3ff0000000000000"
```

通过生成的指针，我们也可以更新位模式。这对浮点变量是无害的，因为任何位模式都是合法的，但通常情况下，`unsafe.Pointer` 转换让我们能向内存写入任意值，从而破坏类型系统。

`unsafe.Pointer` 也可以转换为 `uintptr`，后者存放指针的数值，让我们能对地址进行算术运算。（回顾第 3 章，`uintptr` 是一个足以表示地址的无符号整数。）这种转换也可以反向应用，但同样，从 `uintptr` 转换为 `unsafe.Pointer` 可能会破坏类型系统，因为并非所有数字都是有效地址。

许多 `unsafe.Pointer` 值因此充当了将普通指针转换为原始数字地址并再转换回来的中介。下面的示例获取变量 `x` 的地址，加上其 `b` 字段的偏移量，将结果地址转换为 `*int16`，并通过该指针更新 `x.b`：

gopl.io/ch13/unsafeptr

```go
var x struct {
    a bool
    b int16
    c []int
}

// 等价于 pb := &x.b
pb := (*int16)(unsafe.Pointer(
    uintptr(unsafe.Pointer(&x)) + unsafe.Offsetof(x.b)))
*pb = 42
fmt.Println(x.b) // "42"
```

尽管语法繁琐——既然这些特性应少用，这或许并非坏事——但不要试图引入 `uintptr` 类型的临时变量来拆分语句。这段代码是 **不正确** 的：

```go
// 注意：微妙地不正确！
tmp := uintptr(unsafe.Pointer(&x)) + unsafe.Offsetof(x.b)
pb := (*int16)(unsafe.Pointer(tmp))
*pb = 42
```

原因非常微妙。某些垃圾收集器会在内存中移动变量以减少碎片或记账开销。这类收集器称为 *移动式 GC*。当变量被移动时，所有持有旧位置地址的指针都必须更新为指向新位置。从垃圾收集器的角度来看，`unsafe.Pointer` 是一个指针，因此其值必须随变量移动而改变，但 `uintptr` 只是一个数字，所以其值不应改变。上述不正确的代码在非指针变量 `tmp` 中 **向垃圾收集器隐藏了一个指针**。等到第二条语句执行时，变量 `x` 可能已经移动，`tmp` 中的数字将不再是 `&x.b` 的地址。第三条语句会用值 42 破坏任意内存位置。

对此主题存在无数病态变体。执行完这条语句后：

```go
pT := uintptr(unsafe.Pointer(new(T))) // 注意：错误！
```
