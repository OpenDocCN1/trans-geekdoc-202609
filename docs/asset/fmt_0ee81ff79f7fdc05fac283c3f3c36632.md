
要获取离线特征，我们需要实体数据框（entity data frame），它是一个 Pandas DataFrame 类型对象，在我们的案例中实体是`CustomerID`，并包含用于时间点连接（point-in-time join）的时间戳。一旦创建了实体数据框，我们就可以将其和特征列表作为`FeatureStore`对象方法`get_historical_features`的参数，获取该客户的所有相关特征。要获取在线特征，你可以使用同一对象的`get_online_features`方法，或者在需要时按照前面的流程创建一个。

我们到此结束对 Feast 的介绍。尽管特征存储会有一些延迟，并且可能不适用于组织中的每一个 ML 用例，但拥有一个特征存储并尽可能利用它以避免重复工作仍然是一个好主意。特征存储还使得数据漂移（data drift）和概念漂移的监控更容易。在下一章节中，我们将整合所有内容，查看如何部署模型并积极监控它们。

## 注意事项

- Feast 是一个特征存储，用于在一个地方集中管理实体的特征以供以后使用。它不是一个 ETL 工具。
- 如果你使用云服务，Feast 会为你创建基础设施部分。
- Feast 支持`Bigquery`、`Redshift`和`Files`作为数据源。在未来的发布中可能会有新的添加。
- 来自 Feast 的历史特征用于训练模型。要对新数据进行评分，特征将从在线特征存储中提取。

# 第 9 章：构建 ML 流水线

在之前的章节中，我们涵盖了 ML 生命周期中从 EDA（探索性数据分析）到模型训练和评估的所有各个方面。下一步是部署最终确的模型以对新数据进行评分并进行监控。我们还需要将 ML 流水线从训练到部署实现业务化，以便任何新的或更新的 ML 模型都可以在无停机的情况下部署。我们还应该有一个需要时回滚到旧模型的选项，我们将在章中讨论这一点。

在企业级，多个 ML 模型部署在生产环境中，并根据模型输出做出业务决策。为了确保模型提供正确的输出，需要定期跟踪 ML 模型的性能。模型性能可能会因为数据漂移或概念漂移而下降，在这两种情况下，我们都必须训练新模型并部署其进行消费。新模型的移动应该平滑进行，对下游流程的更改最小。为了实现这一点，我们需要一个像软件工程那样的持续集成和部署（CI/CD）机制。

我们将在本章详细讨论所有内容。

## 目标

学习本章后，你将能够理解 MLOps 的必要性，并围绕它为 ML 流水线设计必要的流程。你还将根据需要利用书中讨论的工具以发挥其最大潜力。在必须选择不同技术栈场景下，你将能够评估新工具以设计顺畅的 MLOps 流程。我们还将涵盖在适用情况下监控 ML 模型的频率的几个关键要点。

## 概述

ML 流水线的设计应能支持所有的 MLOps 步骤。我们将根据需要配置 Git、存储以及云相关的设置，并为生产级系统提供这些设置的关键要点。设置 ML 流水线可能需要多个团队共同工作，如 DevOps、安全、IT，当然还有数据科学。根据手头的用例，流水线的流程可能会有所不同；但我们将涉及如何根据特定需求调整流水线。我们将通过一个 ML 流水线的示例，使用我们创建 Feast 特征存储时使用的相同数据。`KServe`将用于部署训练好的模型，部署脚本将用于保存模型相关的元数据。我们还将学习如何利用已部署模型的保存元数据来持续跟踪数据漂移、概念漂移和模型性能。我们将使用开源监控工具`Evidently`来检查数据漂移和概念漂移。

我们将讨论 GitOps 和一些关于安全的最佳实践，但不会深入细节。本章使用的代码在参考部分提供。我们首先从更新 Polyaxon 配置开始，以便将元数据存储在云端。

## Polyaxon 配置更新

我们在第 5 章“训练和测试 ML 模型 – 第一部分”中配置了 Polyaxon，然而，训练模型会产生大量的元数据，我们希望将其存储更久。为了这样做，我们需要使用不依赖于`Pods`（运行在`K8s`上的容器）寿命存储。在我们的案例中，我们将配置 Google Cloud Storage。如果你使用云镜像注册表以及 GitHub 或 GitLab，你还可以进行其他配置。每个配置的细节可以在其他工具中找到。任何想要集成的额外工具可以在该 URL 上找到。在我们的示例中，我们不需要这样做，因为我们将使用公共 GitHub 仓库和 docker 镜像。

我们将配置`GCS`来存储模型元数据，细节可以在参考部分共享的 GitHub 仓库中的`config.yml`中找到。你需要更改存储桶（bucket）和密钥（secret）细节，并提供不同的名称。更新 Polyaxon 配置有两种方法：第一种是在安装时作为参数传递配置文件，另一种方法是直接使用以下命令升级 Polyaxon：

```
polyaxon admin upgrade -f config.yml
```

这将根据你的配置条目升级 Polyaxon 安装。下一步是训练模型，我们将在下一节中介绍。

## 部署

一旦我们根据定义的 KPI 和利益相关者的批准确定了模型，下一个任务就是部署模型。我们将利用 KServe 进行部署，它将安装在不同的 K8s 命名空间下。使用不同命名空间的想法更好，因为它将模型训练与模型提供隔离开。KServe 除了模型提供之外提供了许多额外服务，如自动伸缩、金丝雀发布（canarying）、可解释性等。由于这些优势，它是提供最终确定模型的理想工具。

我们在这里不会讨论 KServe 的安装；但是，“参考”部分提供的 Git 仓库将包含我们所使用的 KServe 安装的详情。我们还将分享一个比我们正在使用的更详细的安装链接。在 KServe 安装后，部署脚本将执行以下任务：

1. 将运行的元数据（如训练数据、模型二进制文件和任何其他产物）复制到生产文件夹。
2. 更新部署 yml 文件中的模型路径。
3. 执行 K8s 命令进行部署。
