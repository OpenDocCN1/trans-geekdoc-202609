## 11.4 `Benchmark` 函数

基准测试是指在固定工作负载下度量程序性能的实践。在 Go 中，基准测试函数看起来像测试函数，但带有 `Benchmark` 前缀和一个 `*testing.B` 参数，该参数提供了与 `*testing.T` 大部分相同的方法，外加一些与性能度量相关的额外方法。它还暴露了一个整数字段 `N`，指定执行被测操作的次数。

下面是一个 `IsPalindrome` 的基准测试，它在循环中调用该函数 `N` 次。

点击此处查看代码图像

```
import "testing"

func BenchmarkIsPalindrome(b *testing.B) {

    for i := 0; i < b.N; i++ {

        IsPalindrome("A man, a plan, a canal: Panama")

    }

}
```

我们使用下面的命令运行它。与测试不同，默认情况下不运行任何基准测试。`-bench` 标志的参数选择要运行的基准测试。它是一个匹配 `Benchmark` 函数名称的正则表达式，其默认值不匹配任何函数。模式“`.`”会使其匹配 `word` 包中的所有基准测试，但由于只有一个，`-bench=IsPalindrome` 也是等效的。

点击此处查看代码图像

```
$ cd $GOPATH/src/gopl.io/ch11/word2

$ go test -bench=.

PASS

BenchmarkIsPalindrome-8 1000000              1035 ns/op

ok      gopl.io/ch11/word2      2.179s
```

基准测试名称的数字后缀，此处为 `8`，表示 `GOMAXPROCS` 的值，这对于并发基准测试非常重要。

报告告诉我们，每次调用 `IsPalindrome` 约耗时 1.035 微秒，这是在 1,000,000 次运行后取平均值得出的。由于基准测试运行器最初不知道操作需要多长时间，它会先使用较小的 `N` 值进行一些初步测量，然后外推到一个足够大的值，以便进行稳定的计时测量。

之所以由基准测试函数实现循环，而不是由测试驱动程序中的调用代码实现，是为了让基准测试函数有机会在循环外执行任何必要的一次性设置代码，而不将这部分时间计入每次迭代的测量时间中。如果这些设置代码仍然干扰结果，`testing.B` 参数提供了停止、恢复和重置计时器的方法，但这些方法很少需要用到。

既然我们有了基准测试和测试，就很容易尝试各种想法来让程序运行得更快。也许最明显的优化是让 `IsPalindrome` 的第二个循环在中点停止检查，以避免每次比较都做两遍：

单击此处查看代码图像

```
n := len(letters)/2

for i := 0; i < n; i++ {

    if letters[i] != letters[len(letters)-1-i] {

        return false

    }

}

return true
```

但正如通常情况那样，显而易见的优化并不总能产生预期的收益。在一次实验中，这仅带来了 4% 的微弱改进。

单击此处查看代码图像

```
$ go test -bench=.

PASS

BenchmarkIsPalindrome-8 1000000               992 ns/op

ok      gopl.io/ch11/word2      2.093s
```

另一个想法是为 `letters` 预分配一个足够大的数组，而不是通过连续调用 `append` 来扩展它。像这样将 `letters` 声明为适当大小的数组：

单击此处查看代码图像

```
letters := make([]rune, 0, len(s))

for _, r := range s {

    if unicode.IsLetter(r) {

        letters = append(letters, unicode.ToLower(r))

    }

}
```

可带来近 35% 的性能提升，且基准测试运行器现在报告的是 2,000,000 次迭代的平均值。

单击此处查看代码图像

```
$ go test -bench=.

PASS

BenchmarkIsPalindrome-8 2000000               697 ns/op

ok      gopl.io/ch11/word2      1.468s
```

正如这个例子所示，最快的程序往往是内存分配最少的那个。`-benchmem` 命令行标志会在报告中包含内存分配统计信息。这里我们对比优化前的分配次数：

单击此处查看代码图像

```
$ go test -bench=. -benchmem

PASS

BenchmarkIsPalindrome    1000000  1026 ns/op   304 B/op  4 allocs/op
```

以及优化后的：

单击此处查看代码图像

```
$ go test -bench=. -benchmem

PASS

BenchmarkIsPalindrome    2000000    807 ns/op  128 B/op  1 allocs/op
```

在单次 `make` 调用中合并分配消除了 75% 的分配次数，并将分配的内存量减半。

此类基准测试告诉我们给定操作所需的绝对时间，但在许多场景中，有趣的性能问题在于两种不同操作的*相对*耗时。例如，如果一个函数处理 1,000 个元素需要 1ms，那么处理 10,000 个或一百万个需要多久？此类比较揭示了函数运行时间的渐近增长。另一个例子：I/O 缓冲区的最佳大小是多少？针对一系列大小进行的应用程序吞吐量基准测试可以帮助我们选择能提供满意性能的最小缓冲区。第三个例子：哪种算法最适合完成特定任务？在相同输入数据上评估两种不同算法的基准测试通常能显示出每种算法在重要或典型工作负载上的优势和劣势。

对比基准测试就是普通代码。它们通常采用单个参数化函数的形式，从多个具有不同值的 `Benchmark` 函数中调用，如下所示：

单击此处查看代码图像

```
func benchmark(b *testing.B, size int) { /* ... */ }

func Benchmark10(b *testing.B)   { benchmark(b, 10) }

func Benchmark100(b *testing.B)  { benchmark(b, 100) }

func Benchmark1000(b *testing.B) { benchmark(b, 1000) }
```

参数 `size` 指定输入大小，它在不同基准测试间变化，但在每个基准测试内部是常量。要抵制使用参数 `b.N` 作为输入大小的诱惑。除非你将其理解为固定大小输入的迭代计数，否则你的基准测试结果将毫无意义。

对比基准测试揭示的模式在程序设计阶段特别有用，但程序投入工作后我们并不会丢弃这些基准测试。随着程序的演进、输入的增长，或部署在具有不同特性的新操作系统或处理器上，我们可以重用这些基准测试来重新审视设计决策。

**练习 11.6：** 编写基准测试来比较 第 2.6.2 节 中的 `PopCount` 实现与你对 练习 2.4 和 练习 2.5 的解答。基于查表的方法在何时达到收支平衡？

## 11.5 剖析

基准测试适用于测量特定操作的性能，但当我们试图让一个慢程序变快时，往往不知道从何入手。每个程序员都知道 Donald Knuth 关于过早优化的格言，它出现在 1974 年的《带有 go to 语句的结构化编程》一文中。尽管这常被误解为性能不重要，但在其原始语境中，我们可以辨别出不同的含义：

> 毫无疑问，对效率的追求会导致滥用。程序员在思考或担心其程序中非关键部分的速度上浪费了大量时间，考虑到调试和维护，这些优化尝试实际上有强烈的负面影响。我们*应该*在大约 97% 的时间里忘记微小的效率：过早优化是万恶之源。然而我们不应放弃那关键 3% 的机会。优秀的程序员不会被这种推理哄骗得自满，他会明智地仔细审视关键代码；但*仅在*该代码被识别出来*之后*。对程序的哪些部分真正关键做出先验判断往往是错误的，因为使用过测量工具的程序员的普遍经验表明，他们的直觉猜测往往会失败。

当我们希望仔细审视程序速度时，识别关键代码的最佳技术是*剖析*。剖析是一种基于执行期间对若干配置文件*事件*进行采样，然后在后处理步骤中从中推断的性能测量自动化方法；生成的统计摘要称为*剖析配置文件*。

## Go 性能分析与示例函数

## 性能分析概述

Go 支持多种性能分析，每种关注性能的不同方面，但它们都涉及记录一系列感兴趣的事件序列，每个事件都附带一个堆栈跟踪——即事件发生时刻活跃的函数调用栈。`go test` 工具内置了对多种性能分析的支持。

### CPU 性能分析

*CPU 性能分析* 标识出执行最耗费 CPU 时间的函数。每个 CPU 上当前正在运行的线程会被操作系统每隔几毫秒周期性地中断，每次中断在恢复正常执行前记录一个性能分析事件。

### 堆性能分析

*堆性能分析* 标识出负责分配最多内存的语句。性能分析库对内部内存分配例程的调用进行采样，因此平均每分配 512KB 内存就会记录一个性能分析事件。

### 阻塞性能分析

*阻塞性能分析* 标识出导致 goroutine 阻塞时间最长的操作，例如系统调用、通道发送和接收、以及获取锁。每当 goroutine 被这些操作之一阻塞时，性能分析库就会记录一个事件。

为测试代码收集性能分析数据只需启用以下标志之一即可。但请注意，同时使用多个标志时要小心：收集一种性能分析的机制可能会扭曲其他性能分析的结果。

```
$ go test -cpuprofile=cpu.out

$ go test -blockprofile=block.out

$ go test -memprofile=mem.out
```

为非测试程序添加性能分析支持也很简单，尽管具体做法在短命命令行工具和长期运行的服务器应用之间有所不同。性能分析在长期运行的应用中特别有用，因此 Go 运行时的性能分析功能可以通过 `runtime` API 在程序员控制下启用。

## 使用 `pprof` 分析性能数据

收集到性能分析数据后，我们需要使用 `pprof` 工具进行分析。它是 Go 发行版的标准组成部分，但因为它不是日常工具，所以通过 `go tool pprof` 间接访问。它有数十种功能和选项，但基本用法只需要两个参数：生成性能分析数据的可执行文件和性能分析日志。

为了使性能分析高效并节省空间，日志中不包含函数名；相反，函数通过其地址来标识。这意味着 `pprof` 需要可执行文件才能解读日志。虽然 `go test` 通常在测试完成后丢弃测试可执行文件，但启用性能分析时，它会将可执行文件保存为 `foo.test`，其中 `foo` 是被测试包的名称。

以下命令展示了如何收集并显示简单的 CPU 性能分析。我们选择了 `net/http` 包中的一个基准测试。通常最好对特定的、具有代表性的基准测试进行性能分析。对测试用例进行基准测试几乎从不具备代表性，这就是为什么我们使用过滤器 `-run=NONE` 来禁用它们。

```
$ go test -run=NONE -bench=ClientServerParallelTLS64 \
    -cpuprofile=cpu.log net/http

PASS
```

`-text` 标志指定输出格式，本例中为文本表格，每行一个函数，按“最热”函数——即消耗 CPU 周期最多的函数——排在最前面。`-nodecount=10` 标志将结果限制为 10 行。对于明显的性能问题，这种文本格式可能足以定位原因。
