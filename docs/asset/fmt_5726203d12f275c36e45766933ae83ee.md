
# 对象基数约束

**对象基数约束**限制每个数据库状态下对象类型实例集的基数（成员数量）。图 7.22(a) 中的基数约束“#=12”意味着始终恰好有 12 名陪审团成员。这种相等设置很少见，因为大多数数据库从空状态开始，这会违反该约束。

![图 7.22 对象基数约束 (a 和 b) 和角色基数约束 (c)。](img/f07-22-9780443237904.jpg)

图 7.22 对象基数约束 (a 和 b) 和角色基数约束 (c)。

在图 7.22(b)中，“# ≤100”意味着每个数据库状态下至多有 100 名参议员。对象基数约束适用于类型的实例集，而不是类型本身。在很长一段时间内，曾担任过这些职位的陪审团成员或参议员总数可能要高得多。

## 角色基数约束

*角色基数约束*限制每个数据库状态下角色填充集的基数。图 7.22(c) 中的角色基数约束“# ≤ 1”意味着最多只有一名员工扮演董事角色。请注意，ORM 基数约束与实体-关系建模（ER）中所谓的“基数”约束不同，后者对应频率约束和/或强制角色约束。

基数约束很少包含在图表中，因为它们*通常由现有的值约束或频率约束隐含*。例如，`Gender(.Code)` 上的 `{"M", "F"}` 值约束隐含了 `Gender` 上的“# ≤ 2”。如果最多只有一个参议院，那么图 7.23(b) 中 `Senate` 角色上 ≤100 的频率约束隐含了 `Senator` 上的 # ≤100 基数约束。但请注意，`Senate` 上的 # ≤1 基数约束仍然是必需的。

![图 7.23 由值约束或频率约束隐含的对象基数约束。](img/f07-23-9780443237904.jpg)

图 7.23 由值约束或频率约束隐含的对象基数约束。

在实践中，通常允许多个参议院更有用，在这种情况下，我们使用频率约束将每个参议院的规模限制在最多 100 名成员，即使 `Senate` 上的基数约束不再适用（参见图 7.23(c)）。

*析取基数约束*将基数限制为符合用大括号“{}”括起来、条目间用逗号分隔的集合中列出的多个简单基数约束中的至少一个。例如，`#{0,12}` 意味着基数必须是 0 或 12，而 `#{≤2, 4, 6, 8..10}` 表示基数必须是 0、1、2、4、6、8、9 或 10。

## 值比较约束

*值比较约束*使用六个比较运算符之一（`<`、`≤`、`>`、`≥`、`=`、`≠`）将一个值与另一个值进行比较。该约束由一个带圆圈的运算符表示，通过一条虚线箭头从左操作数角色连接到右操作数角色。圆圈上添加两个点以表示被比较的两个实例（提醒我们这是实例间的比较，而非集合间的比较）。

`=` 和 `≠` 值比较约束通常最好用环约束替代（例如，`Country borders Country` 上的 `≠` 值比较约束可替代为非自反环约束）。

图 7.24 中的值比较约束可口头表述为：**对于每个** `Employee`，`birthdate < hiredate`；**对于每个** `Project`，**现有的** `enddate ≥ startdate`。对于可选属性（如 `enddate`），“**现有的**”将比较限制在属性实例存在的情况下。因此，“**现有的** `enddate ≥ startdate`”是“**如果** `enddate` **存在则** `enddate ≥ startdate`”的简写。因此，如果一个项目没有结束日期，该约束仍然得到满足（它映射到 SQL 检查子句 `check (enddate >= startdate)`，仅当其评估为 false 时才被违反）。

![图 7.24 值比较约束示例。](img/f07-24-9780443237904.jpg)

图 7.24 值比较约束示例。

值比较约束有点像环约束，因为被约束的角色是兼容的（例如，图 7.24(a) 中比较的 `birthdate` 和 `hiredate` 属于同一员工）。与非自反环约束一样，值比较约束通常执行成本较低，因为它们通常比较表中同一行的值，而不是比较值的集合。

## 文本规则

你现在已经了解了几乎所有的 ORM 图形符号。一些更高级的约束和规则将在第 10 章中讨论。为更多约束添加图形符号会使图形语言难以学习并导致图表杂乱。概念模式图提供了一个面向人类的、无歧义的、但通常不完整的 UoD 结构规范。

无法使用预定义图形符号表达的规则可指定为*文本规则*，最好使用高级形式语言。在 ORM 2 中，显示这些文本规则的首选方式是通过*脚注*，脚注编号标记图表上涉及的模型元素。文本规则（约束、推导规则和子类型定义）本身可显示在文本框中，作为脚注或出现在图表的其他位置，理想情况下可切换其显示开关。

图 7.25(a) 展示了显示三条文本规则的一种方式。规则 1 声明员工的受雇日期晚于出生日期。这与图 7.24(a) 中的值比较约束相同，但在图 7.25(a) 中该约束以文本形式表达。脚注编号 1 附加在 `Employee` 类型名称后。`birth` 和 `hire` 谓词之间也存在成对排斥约束，但因现已隐含而省略。

![图 7.25 文本规则示例。](img/f07-25-9780443237904.jpg)

图 7.25 文本规则示例。

规则 2 规定非高管最多使用一辆公司车。这是一个*受限唯一性约束*，因为它加强了 `Employee uses CompanyCar` 上的唯一性约束，但将其限制为 `Employee` 的一个子类型。

规则 3 规定每位高管必须拥有公司车的使用权。这是一个*受限强制角色约束*，因为它使 `Employee` 的一个可选角色对 `Employee` 的一个子类型变为强制的。

图 7.25(b) 展示了建模受限强制角色约束的另一种方式：显式定义 `Executive` 作为 `Employee` 的子类型，并从子类型链接（`Executive **is an** Employee`）到 `Employee uses CompanyCar` 中的 `Employee` 角色添加子集约束，以声明每位高管必须扮演使用公司车的角色。

## 综合示例：计算机网络

本节最后通过一个涉及文本约束和其他有趣问题的示例进行总结。假设我们的信息系统要维护计算机网络的详细信息。在总线网络中，一个或多个计算机工作站（WS）沿总线或传输线连接到一端的文件服务器（FS）。图 7.26 提供了这样一个网络的拓扑图（即显示哪些计算机相互连接，但不显示它们的距离或方向模式）。

![图 7.26 网络 1 的拓扑结构。](img/f07-26-9780443237904.jpg)

图 7.26 网络 1 的拓扑结构。

为简单起见，假设计算机用单个字母标识。记录每个节点的主存储器和文件服务器的硬盘容量。我们的任务是设计一个模式来记录内存和连接详情，以及其他总线网络的类似详情，以便用户能从该模型中提取与从实际网络图中提取的信息一样多。请在继续阅读前自行尝试。存在许多不同的正确解决方案。

将图表用基本事实来描述，会产生若干事实类型，例如：`Node belongs to Network`（节点属于网络）；`Node is of NodeKind {'FS', 'WS'}`（节点属于节点类型 {'FS', 'WS'}）；`Node has main memory of Capacity`（节点拥有主存容量）；`FileServer has disk of Capacity`（文件服务器拥有磁盘容量）。参考模式显而易见。对于子类型定义，我们可以使用：**Each** `FileServer` **is a** `Node` **that** is of `NodeKind` ‘FS’。现在到了困难的部分。我们如何描述节点是如何链接在一起的？

根据我们对基本谓词的选择，有多种方案。如果最初难以用基本句子表达信息，我们可以先记下脑海中浮现的任何内容样本。例如：

1.  Node “A” is directly connected to Node “F”。
2.  Node “F” is directly connected to Node “A”。
3.  Node “A” is indirectly connected to Node “E”。
4.  Node “A” is an end node。
5.  There is at most one link between each pair of nodes。
6.  No link connects a node to itself。
7.  Each node is directly connected to at most two nodes。

让我们退一步审视这个问题。关于拓扑结构，有两个基本方面需要捕捉。首先，给定网络中的所有节点都位于同一条 *continuous line*（连续线）上（这与星型网络、环型网络和复杂的环路结构等其他形状形成对比）。其次，节点在这条线上 *positioned in some order*（按某种顺序定位）。

如果我们将结构的线性视为一种约束，如何表达节点的顺序？鉴于节点位于一条线上，且文件服务器位于这条线的一端，让我们首先通过说“线从文件服务器开始”来确立这条线的 *direction*（方向）。这避免了与无向、对称谓词（例如 is directly connected to）相关的潜在冗余问题。

排序可以用相对排序或绝对排序来指定。采用第一种方法，我们使用 *directed linkage*（有向链接）谓词（例如 is just before）。采用第二种方法，我们为每个节点分配一个绝对位置（例如，从文件服务器端开始编号为 0、1、2、3、4）。

第一种方法导致了 Fig. 7.27(a) 中所示的环事实类型。这使用来自样本网络的数据进行填充。适用于多网络的扩展版本如 Fig. 7.27(b) 所示。这假设 `NodeId` 是全局标识符。显式显示了 inclusive-or 约束，因为 `Node` 在完整模式中扮演其他角色。邀请您添加相关的环约束以及其他事实类型。如果只考虑完整网络，现在可以推导出节点的类型（例如，当且仅当一个节点之前没有节点时，它才是文件服务器）。

![Fig. 7.27 A fact type for directed links in (a) one network and (b) many networks.](img/f07-27-9780443237904.jpg)

Fig. 7.27 A fact type for directed links in (a) one network and (b) many networks.

通过仅存储直接、有向链接的链接信息，我们减少了数据库的规模，同时避免了对称性和传递性问题。如果需要，可以通过使用递归规则来推导关于间接链接的信息，例如：

```
For each Node1 and Node2,
Node1 is before Node2 iff
Node1 is just before Node2
or
Node1 is just before some Node3 that is before Node2.
```

存在其他约束。例如，每个网络恰好有一个文件服务器。如果我们使用事实类型 `Node is in Network`，这可以用文本指定。如果我们改用单独的事实类型：`Node is the file server for Network`；`Node is a workstation for Network`，则可以用图形方式指定。

然而，无论我们如何选择事实类型，某些约束都必须用文本指定。例如，直接链接的节点属于同一个网络。如果每个网络都是连续的（无间隙），对此的约束也需要用文本声明。邀请您正式表达这些约束（及任何其他约束）。

作为练习，尝试使用节点位置编号来建模链接信息，并注意对约束和推导规则的影响。请注意，这种绝对位置方法使得在网络中添加或删除节点变得更加麻烦，因为需要对位置信息进行全局更改。

例如，如果我们添加一个节点，比如 D，在 F 和 E 之间，那么不仅 D 会被分配位置 2，而且节点 E、C 和 B 都需要将其位置编号加 1。使用我们之前的方法，只需要局部更改即可。交换节点用两种方法都很简单。作为练习，列出一些示例更新的复合事务。

# 7.5 Final Checks

概念模式设计程序通过各种检查促进错误的早期发现，包括通过示例与用户沟通。还可以执行四项最终检查，以帮助发现可能漏网的错误。这些检查旨在确保内部一致性、外部一致性、无冗余性和完整性。我们现在依次考虑这些检查。

## 概念模式的一致性与冗余检查

### 内部一致性

如果且仅当用作谓词或约束参数的每个角色序列都可以在某个状态下被填充，则概念模式在**内部是一致的**。本主题在前一章中已有讨论，当时称为“**填充一致性**”或“**强可满足性**”。基本上，这意味着当系统被填充时，指定的约束不会相互矛盾。例如，图 7.28 中的模式有三个错误。你能发现它们吗？

![图 7.28 该模式在三个方面上存在填充不一致。](img/f07-28-9780443237904.jpg)

图 7.28 该模式在三个方面上存在填充不一致。

首先，谓词 `R` 上的频率约束 `2` 与唯一性约束冲突；此外，如果频率约束跨越整个谓词，则任何大于 `1` 的频率都应被拒绝。其次，`A` 上的强制角色意味着这些角色之间存在等值约束，因此如果 `A` 被填充，排斥约束就无法被满足（回顾定理 NXS）。

最后，`S` 的第一个角色上的频率约束 `3` 一旦 `A` 被填充就无法被满足。如果它被满足，则 `C` 将包含至少三个实例（因为 `S` 的每一行都是唯一的），但这是不可能的，因为 `C` 是 `B` 的真子类型，因此最大基数为 `2`（值约束显示 `B` 只有三个可能的值）。通过练习，通常很容易发现矛盾的约束模式。计算机辅助软件工程（CASE）工具可以在此提供帮助。例如，`NORMA` 工具可以防止大多数不一致性甚至被录入。

### 外部一致性

如果概念模式与用于开发该模式的原始示例和需求一致，则该模式在**外部是一致的**。如果之前未执行此操作，我们用一些样本数据填充模式，并查看是否有约束被该填充违反。如果有，则在这一方面约束**过强**，因为它们拒绝了合法的示例。我们应修改模式，通常通过移除或放宽某些约束，直到允许该填充。
