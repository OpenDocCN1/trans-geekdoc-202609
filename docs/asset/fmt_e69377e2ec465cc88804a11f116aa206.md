
在这里，这两个集合分别包含一个 `Course` 文档列表和一个 `Student` 文档列表。学生和课程之间的关系通过 `Student` 文档中对 `Course` 文档标识符的引用来记录。这避免了前一个示例中的数据冗余，但引入了其他问题。例如，如果我们想获取某学生获得的学分总值，我们必须读取额外的 `Course` 文档以获取必要信息。这大致相当于关系型系统中的连接操作。

`Courses` 和 `Students` 之间的关系是多对多的（因此在上面的示例中，一个 `Student` 文档需要包含对多个 `Course` 文档的引用）。我们可以通过创建一种新的 `Course-Student` 文档来解决这个问题，这相当于关系型系统中的链接表。然而，这可能会被视为一种不自然的人为构造而被拒绝。如果考虑现实世界中基于纸质的对应物，`Course` 文档和 `Student` 文档很可能存在，但 `Course-Student` 文档则不太可能存在。

在设计文档数据库时，嵌入与引用的选择取决于在多个相互竞争的因素之间找到恰当的平衡。

首先，我们需要识别重要的文档类型。如果我们是从零开始，可以开发一个对象-角色模型（ORM）来理清与我们关注点相关的信息结构。由此，我们可以使用关系映射（如第 11 章所述）推导出一组候选文档类型，这些类型可以用适当的 JSON 格式表示。或者，我们可能希望基于预先存在的文档进行设计，如果它们采用其他形式（CSV、XML 等），则将其重新指定为 JSON 格式。

下一组决策高度依赖于文档的预期用法。广义上讲，我们希望文档的大小恰好满足需求，但不应过大。这可能表明应拆分某些候选文档以提高性能（数据库可能会对单个文档施加大小限制，但通常该限制足够大，不必担心）。在考虑文档间的关系时，我们需要了解数据上常见的创建、读取、更新、删除（CRUD）操作的相对频率。读取操作占主导地位的情况很常见，但并非总是如此。

如果我们考虑两种以某种方式相关的文档类型 A 和 B，以下是一些可能相关的场景。

*   如果 A 和 B 经常一起被查询，请考虑将 A 嵌入 B，或将 B 嵌入 A（以性能最优者为准）。
*   长列表效率低下，因此如果将 B 嵌入 A 会导致 B 的长列表，请考虑改用引用。
*   如果 B 很少被单独查询，请考虑将 B 嵌入 A。
*   如果 B 嵌入在 A 中，但 B 与许多其他文档类型相关联，请考虑改用引用。
*   如果 B 嵌入在 A 中，且 B 的更新频率远高于 A，请考虑改用引用。

### 分区

文档数据库中的分区通常指水平分区。通过拆分文档类型以创建两个新的文档类型，每个类型包含原始文档字段的不同子集，可以实现类似垂直分区的效果，但这属于原始数据库设计的内在部分。水平分区可以基于文档的任何部分，但选择取决于数据库的预期用法。每个分区或“分片”可以容纳一个集合中文档的子集，并且在物理上与其他分片截然不同。一个关键决策是选择用作分发依据的字段或字段组合。与其他方面一样，这将取决于数据库的预期使用模式。例如，如果查询经常聚焦于某一特定年份内的数据，则为每一年分配一个单独的分片，并使用相关的日期字段作为分发依据可能是合适的。

集合中的每个文档根据相关字段被分配一个 `shard key` 值。`shard key` 的选择应能将数据均匀地分布在各分片上，以防止热点并确保性能均衡。数据库中的每个分片都维护元数据，将 `shard key` 值的范围映射到特定的分片。执行操作时，数据库客户端会在发送给集群的查询或命令中包含 `shard key` 值。这由专用路由器处理，路由器检查 `shard key`，确定哪些分片需要参与执行该操作，然后制定在相关分片上执行查询的计划。

假设查询涉及多个分片，路由器会根据分片负责的 `shard key` 范围，将查询的各部分发送到相应的分片。每个分片在本地执行其部分查询，并将包含该特定分片特定的整体结果子集的部分结果返回给路由器。一旦路由器收到来自所有分片的结果，它会将它们合并以形成完整的结果集。这可能涉及排序、合并以及应用任何额外的查询操作（例如过滤）以匹配原始查询条件。最后，路由器将合并后的结果集发送回客户端应用程序，提供统一的查询结果视图，就好像它是在单个非分片数据库上执行的一样。

分布式结果的收集和合并显然会带来性能损耗，因此 `shard key` 的选择需要慎重考虑。理想情况下，分区设计应使大多数查询能够路由到集群中的单个分片。

## 索引

与关系型数据库一样，文档数据库可以通过创建允许高效数据检索的数据结构来使用索引以提高查询性能。与模式设计的其他方面一样，拥有清晰的索引策略很重要。虽然索引可以提高查询性能，但也会影响写入性能并增加存储需求。

应检查使用数据库的应用程序的查询类型及其相对频率。根据操作的数量和类型，可以确定合适的索引类型。有几种类型可用，包括：

*   单字段索引：最基本的索引类型，查询基于单个字段。
*   复合索引：在多个字段上创建，将它们组合成单个索引。
*   多键索引：单独为数组的元素建立索引。

还有其他类型的索引用于更专业的应用，如文本、地理空间和哈希索引。

索引是通过指定要索引的集合和字段以及可能需要的任何其他选项（例如在后台创建索引以最大程度减少干扰）的操作来创建的。例如，我们可以在 `Courses` 集合的 `courseName` 字段上创建一个单字段索引，如下所示：

```
db.Courses.createIndex( { courseName: 1 } )
```

这里，数字 `1` 表示索引应按升序排列；降序将由 `−1` 参数表示。

在文档数据库中，小心处理更新和删除也很重要。与关系型数据库不同，文档数据库不强制执行引用完整性或级联删除。由开发人员负责确保正确执行更新和删除，而不留下孤立数据或破坏关系。

### 文档数据库中的引用完整性

引用完整性是一个通常与关系型数据库相关联的概念，其中表之间的关系通过外键来维护和强制执行。在遵循 NoSQL 数据模型的文档数据库中，引用完整性并不以相同的方式原生提供。然而，可以采用类似引用完整性的模式和机制来确保数据一致性以及文档之间的关系。如前所述，嵌入和引用可以提供一定程度的完整性。其他措施可以包括：

*   **事务**，允许对不同文档执行多个操作，以原子方式确保受影响文档间的数据一致性。虽然事务不强制执行引用完整性，但它们有助于维护相关文档间的数据一致性。
*   **触发器和钩子**，允许在特定数据库操作（如插入、更新或删除）之前或之后运行自定义逻辑。这些可用于实现自定义引用完整性检查，并确保在数据修改操作期间相关文档保持一致。
*   **应用程序代码**，位于数据库外部，可以通过额外功能进行增强，以确保数据修改在持久化到数据库之前符合期望的关系和完整性约束。

### 数据库查询

由于其 NoSQL 的地位，文档数据库不包含来自 SQL 的熟悉的 `select` 语句。然而，它们确实在自己的查询语言中提供了等效的功能。我们将以 MongoDB 为例（[`www.mongodb.com`](https://www.mongodb.com)）及其 MQL 查询语言。该语言通过允许选择、投影、过滤、排序和聚合等操作的函数提供类似的功能。在这里，我们将看几个简单的示例，以了解可用功能的范围。

选择通过 `find()` 函数处理，该函数包含以 JSON 对象表示的查询条件。例如，我们在 Courses 集合中查找相关文档，如下所示：

```
db.Courses.find( { creditValue: { $gt: 12 } } )
```

在该示例中，`$gt` 是一个查询操作符，用于指定“大于”，因此该函数将返回学分值大于 12 的 Courses。其他常见的查询操作符包括 `$eq`、`$ne`、`$gt`、`$lt`、`$in`、`$exists` 等。

投影允许使用投影在查询结果中包含或排除字段。使用一个参数来指定要包含 (1) 或排除 (0) 的字段。

```
db.Courses.find( { }, { courseName: 1,  _id: 0 } )
```

在该示例中，将返回课程名称，但会隐藏关联的 `_id` 字段。

查询结果可以基于一个或多个字段进行排序。`sort()` 方法指定要排序的字段和排序顺序，升序 (1) 或降序 (−1)。

```
db.Courses.find( ).sort( { creditValue: -1, courseName: 1 } )
```

聚合提供了执行数据转换和计算的能力。聚合函数可以简单应用，如下所示。

```
db.Courses.aggregate( [ $avg { "$creditValue" } ] )
```

这提供了所有 Courses 的平均 creditValue。然而，聚合函数比这强大得多，因为它可以包含一个“管道”，即一个操作列表，排列方式使得一个操作的输出成为下一个操作的输入。这允许结合分组、求和、排序、平均等的复杂操作。典型的序列可能是：

```
$project → $match → $group → $sort
```

嵌套在 `aggregate()` 函数内。

总的来说，我们可以看到可用的功能与关系型系统提供的功能相似，尽管实现方式不同。文档模型的优势包括数据表示的灵活性和分区的可能性。与此相对的，必须考虑维护复制数据一致性的需求以及涉及多个文档的事务的复杂性等问题。

文档数据库是存储可视化为共享共同主题或目的的值组的数据的显而易见的选择。当数据库用于存储传统业务文档（如报表、申请表、规格说明书等）的电子等价物时，情况确实如此。文档数据库流行的其他应用领域包括：

*   **内容管理系统 (CMS)**，用于存储和管理各种类型的材料，如文章、图片、视频以及用于支持网站和其他应用程序的元数据。
*   **目录管理**，也包括目录或列表，如商业目录、房地产列表和在线市场，这些可以受益于在单个数据库中存储多样化数据结构的能力。
*   **存储用户配置文件和偏好**，以在社交网络、在线论坛和流媒体平台等应用程序中实现个性化体验。
*   **管理医疗信息**，如患者记录、病史、检测结果和治疗计划，这些构成了明确定界的信息单元。
*   **电子商务平台**，用于管理产品目录、用户配置文件、客户评价和订单历史，同时提供灵活性以适应不断变化的产品属性和关系。

## 17.5 图数据库

图数据库使用属性图模型来表示和存储数据。基本图结构由节点和关系（边）组成。每个节点代表一个实体、对象或数据点，每个关系代表两个节点之间的连接或关联。

节点是属性图的基本单位。每个节点可以有一个或多个属性，用于存储与该节点关联的数据属性或特征。例如，在社交网络图中，一个节点可以代表一个人，节点属性可以包括与该人相关的属性。

关系定义节点之间的连接或关联。它们代表实体之间的链接或交互。关系也可以拥有提供关于连接的额外信息的属性。例如，在社交网络图中，关系可能代表人与人之间的“友谊”连接，关系属性可以包括友谊建立的日期。

属性是与节点和关系都关联的键值对。它们存储与相应节点或关系相关的特定属性或数据值。例如，代表一个人的节点可能具有“姓名”、“年龄”和“电子邮件”等属性。

与关系型数据库相比，图数据库提供了几个优势，特别是在处理高度连接和复杂的数据结构时。在关系型数据库中，可以想象通过遵循中间表之间的关系来连接一对表。然而，如果这两个表相距甚远（即存在许多中间表），则查询变得复杂，且多次连接的成本可能很高。在图中遍历关系是一个直接操作，这使得查询高度连接的数据非常快。随着图规模的增长，图数据库保持一致的性能，使其成为关系不断扩展的应用程序的可扩展解决方案。

### 图数据库概述

图数据库通常具有灵活的模式，允许节点和关系拥有不同的属性，而无需严格的约束。这种适应性在数据模型随时间演变的场景中非常有益，因为可以在不更改整个模式的情况下进行修改，而在关系型数据库中这可能非常繁琐。数据点之间的关系被直接存储，当关系是应用程序的主要关注点时，这使得数据模型更加直观且易于处理。它们还能以高效的方式表示层次数据结构（这在某些领域很常见）。

图数据库的模式灵活性使其非常适合数据模型易变、关系动态，且应用程序要求数据表示具有适应性和敏捷性的场景。然而，更灵活的模式意味着数据库中的约束更少，因此结构和约束可能需要通过应用程序逻辑来定义，而不是通过数据库本身强制执行的集中式模式定义。

#### 数据库产品

在数据库产品方面，`Neo4j` 通常被认为是市场领导者，部分归功于其早期采用和强大的生态系统。`Amazon Neptune` 因其与其他 AWS 服务的集成也占有显著地位。其他图数据库如 `ArangoDB`、`JanusGraph` 和 `Stardog` 拥有各自的细分市场和用户群，并且有些能够与文档数据库和列式数据库等其他类型的 NoSQL 系统集成。

为了提供图数据库功能的具体示例，我们将使用 `Neo4j`（[www.neo4j.com](http://www.neo4j.com)）。其底层图处理引擎针对高效遍历和导航图进行了优化，使图遍历和模式匹配操作快速且可扩展。它使用一种名为 `Cypher` 的语言来编写图查询并执行常规的 CRUD 操作。企业版为商业运营提供了高级功能，但我们将重点关注社区版提供的功能。

与其他类型的 NoSQL 数据库不同，图数据库不适合水平分区。整个数据库驻留在单台服务器上，因此随着数据库的增长，服务器必须垂直扩展。通过提供服务器集群，可以将不同的读操作定向到集群中的不同服务器以分担负载，从而提高性能，但更新是通过主节点进行的，主节点随后将更改复制到集群中的其他服务器。在服务器内部，`Neo4j` 支持 ACID 事务以确保数据完整性和一致性。

#### 关系型与图数据库的对比

虽然关系型和图数据库在高层上有一些相似之处，但在细节层面差异巨大。在关系型数据库中，最基本的元素是表，而在图数据库中，则是节点。然而，这些对应于不同种类的概念。关系表关联特定*类型*的对象，但图节点关联类型的*实例*。节点类型的概念在图数据库中当然存在；在 `Neo4j` 中，它被称为“标签”。

所有具有相同标签的节点可以假定具有相似的属性。如果属性值未知（或不相关），关系型数据库将在表的相应单元格中存储 `NULL`。在图数据库的等效实现中，该属性将直接不存在（即不存储 `NULL`）。

当我们考虑对象之间的关系时，存在类似的二分法。在关系型数据库中，这通过外键引用在表级别定义，可能通过“连接”或“链接”表来处理多对多关系。这在*类型*层面固化了关系。在图数据库中，关系是在*实例*层面的节点之间定义的，这不依赖于*类型*的多重性，因此实例之间的关系就是简单的关系。

这在考虑数据库可容纳的关系类型时有重要含义。在关系型数据库中，所有实例（表中的行）必须遵守相同的关系结构，但在图数据库中，具有相同标签的不同节点可能具有不同的关系。将其与关系型系统对比，这就像表中的每一行都可以拥有自己独特的外键引用，且与表中的其他行不同。图方法为表达复杂关系提供了极大的灵活性，但使后续探索这些关系所需的文档工作变得复杂。

另一个区别是数据类型的处理方法。SQL 定义了一系列数据类型，表列中的所有值都被约束为一种特定类型，如 `int`、`char`、`float` 等（如果值缺失，可能为 null）。在 `Neo4j` 社区版中，节点和关系的属性没有预先约束为特定的数据类型。值有类型（字符串、整数等），但属性没有，因此例如一个属性可能先持有整数值，后来被更新为字符串值。

### 图数据库查询

图数据库中的数据查询涉及通过指定匹配所需数据的节点和关系模式，从图中检索信息。图数据库通常拥有针对图遍历和模式匹配优化的专用查询语言，`Neo4j` 提供了一种名为 `Cypher` 的语言。

图数据库中的查询通常涉及匹配特定的节点和关系模式。`Cypher` 可用于指定模式、基于属性过滤节点，以及根据特定标准包含或排除关系。数据可以使用 `match` 关键字检索，这大致相当于 SQL 中的 `select`。以下查询返回特定 `Customer` 节点的所有属性。

```
match ( c:Customer {customerID:"ABCDE"} ) return c
```

索引可用于根据指定属性加快节点和关系的查找速度，尽管这通常会减慢更新操作。

`Cypher` 查询可以包含基于节点和关系属性的条件。这允许以类似 SQL 的方式根据与节点和关系关联的属性值过滤数据，例如使用 `where` 子句。结果也可以以类似 SQL 的方式组织，例如使用 `order by` 子句。聚合函数可用于汇总跨节点和关系的数据，同样类似于 SQL，使用 `count()`、`sum()` 和 `avg()` 等函数。

图数据库的一个特定优势是图遍历的便捷性，这涉及通过关系从一个节点导航到另一个节点，以查找匹配特定标准或模式的数据。节点之间的路径可以指定为固定长度或带有指定限制的可变长度。提供了一个函数库来实现许多图算法，如广度优先搜索、深度优先搜索、最短路径、PageRank 等。这类查询在关系型数据库中很难实现。

在数据录入关系型数据库之前，必须先用表填充数据库，而这些表又是根据某个模式创建的。图数据库不需要这种准备，因为可以根据需要直接添加节点和边。从某种意义上说，我们可以说图数据库的模式是从对其执行的创建、更新和删除操作中涌现出来的。

这不应走得太远。完全临时性的方法可能导致数据库无法给出可靠结果，且无法维护。模式的一个重要优势在于，它为特定应用领域定义了一套词汇表，使所有参与者能够以一致的方式进行沟通。例如，图数据库中可能包含以下事实：

```
Holmes – WATCHED -> Watson Holmes – OBSERVED -> Watson Holmes – NOTICED -> Watson Holmes – RECOGNIZED -> Watson
```

其中每一条都可能是某事件的合理记录。像这样列在一起时，问题显而易见，但在实践中，各个条目可能由不同人员在不同时间录入，他们可能并不知晓已录入的其他数据。我们能否查询数据库以确认 Holmes SAW（看见）了 Watson？根据这些数据，不能！

#### 填充图数据库

在 SQL 中，对象通过 `insert` 语句创建，该语句将相关值添加到表中。关系的创建方式相同，即将目标键插入源表，因此不需要单独的 insert 操作。在图数据库中，节点和关系是分离的项，因此是分别创建的。

以下示例展示了节点创建的通用风格：

```
merge ( :Customer { customerId: "ABCDE" } )
```
