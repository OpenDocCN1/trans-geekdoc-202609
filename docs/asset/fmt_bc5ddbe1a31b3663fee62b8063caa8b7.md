
在讨论客户端和服务端方法时，我们已经提到了服务注册表组件。服务注册表是一个包含所有服务实例网络位置的数据库。它暴露服务实例注册/注销其网络位置的能力，并将网络位置注册的工作委托给服务实例。

此外，服务注册表要求它们发送心跳以确定实例是否仍然存活并能接受流量。正如我们所见，Kubernetes 中没有显式的服务注册表；相反，Kubernetes 利用现有的存储 `etcd`。Kubernetes 拥有将实例网络位置注册到 `etcd` 的内部逻辑。`etcd` 除用于此目的外，还被 Kubernetes 用于许多其他用途。总体而言，`etcd` 是一个高可用、分布式、一致的键值存储。

## 负载均衡器

负载均衡器是任何软件架构中的关键组件。一方面，我们有各种希望从我们的系统请求服务的客户端。另一方面，我们动态变化的环境构成了我们的服务。由于版本更新、故障、负载等多种原因，我们的环境可能高度动态。在这两者之间矗立着负载均衡器，它像交通警察一样路由流量。

负载均衡器负责在现有服务器之间有效地调度和分发网络流量。它应该知道当前哪些服务可用，哪些不可用。了解服务的可用性可以将新请求导向正常服务，并将现有请求从故障服务重定向到运行正常的服务。它确保了所有服务的可用性和可靠性。

如前所述，服务发现服务器可以充当负载均衡器，API 网关可以作为服务发现。因此，API 网关可以是一个负载均衡器。谈到负载均衡器，主要意图是将请求分发给可用服务的能力。请求分发可能非常复杂，我们稍后将给出不同用例和算法的示例。

负载均衡器有多种类型。本书此部分主要描述 L7 负载均衡器。划分负载均衡器不同组别的一种流行方式是按 L4 和 L7 分类。L4 负载均衡器工作在传输层，关注 IP 地址和端口等网络层，而 L7 负载均衡器专注于应用层。如今，无需自行编写负载均衡器。存在各种负载均衡器，如 `NGINX`、`HAProxy`、`AWS ELB` 和 `AWS ALB`。

这个广阔的主题足以填满整本书。重要的是要强调负载均衡器是**必要**的，幸运的是，通常易于操作。除非我们想编写负载均衡器或为现有项目做贡献，否则我们应专注于了解如何部署、排查故障和使用它。用法和配置因负载均衡器而异，通常可以找到在线指南引导我们完成部署。

接下来要理解的是负载均衡器所遵循的算法。我们可以根据特定需求配置负载均衡器。每种负载均衡器技术都有多种算法。最终，选择合适的负载均衡器算法对于满足系统需求至关重要。以下是一些广泛使用的负载均衡算法：

*   **轮询：** 请求在循环中依次分发，一个接一个。轮询是最常见且最简单的算法。
*   **最少连接：** 连接数最少的服务器获得下一个请求。
*   **最短时间：** 一个计算连接数和响应时间组合的公式；响应更快且连接数较少的服务器获得下一个请求。
*   **哈希：** 用于分发请求的键定义。键定义可以是 URL 路径、编码类型、端口、IP 地址等。
*   **两次随机选择：** 使用算法（最少连接、最短时间或其他）选择两台服务器，然后随机选择其中一台。

每种算法都有利弊。选择负载均衡器算法时，我们应调研并寻找最适合我们系统的算法。其他配置也能造福我们的系统。

## 每服务一个数据库

每个服务一个数据库是微服务架构中的典型模式。每个拥有多个服务的系统都可能需要一个持久化数据存储系统。建立稳健的数据分离对于促进微服务架构中服务间的松耦合至关重要。请记住，不同的服务有不同的数据存储需求。关系型数据库将是一个很好的选择；有时，NoSQL 和其他类型则是最佳选择。但这不是这里的重点。

数据分离可以发生在数据库内部——即所谓的共享数据库模式。然而，在本模式中，我们将讨论每个服务一个数据库。让我们在微服务架构中演示共享数据库（例如关系型数据库）与每个服务一个数据库之间的区别。

![](img/Figure-6.6.jpg)

**图 6.6：** 关系型数据库中的共享数据库 vs. 每个服务一个数据库

各个服务间的共享数据库可以通过单个数据库和表，或每个服务一个模式来实现。开发人员常倾向于执行 SQL 连接或直接读取另一个服务的数据。为了避免这种诱惑，我们可以使用每个服务一个数据库模式。按服务分离数据库为我们提供了最高级别的分离，这体现在几个优势中：

*   服务是松耦合的——正如我们所期望的！
*   每个服务可以使用不同的数据库。正如我们提到的，每个数据库有不同的需求。
*   扩展限制——许多数据库在速度和规模方面存在限制。当我们按服务分离数据库时，复制和扩展会更容易。我们可以独立管理每个数据库，不受其他服务施加的约束。

然而，按服务分离数据库也有几个缺点：

*   创建和管理更多数据库时，复杂度显著增加。
*   服务间的聚合和连接变得更加复杂和困难。SQL 连接发生在不同数据库之间。因此，我们需要外部服务或工具来促进这一点。
*   跨服务实现事务变得棘手且复杂。分布式事务具有挑战性；然而，前面提到的 Saga 模式可能有助于我们解决它。

将每个服务一个数据库的模式想象为服务之间的另一道屏障。许多公司通常在开始时使用共享数据库，因为它简单快捷。过了一段时间，他们意识到必须按服务分离数据库。尽管如此，经过很长时间后分离数据库的时间成本，与一开始就按服务分离数据库的场景相比，是非常高的。

## 面向前端的后端

BFF，即面向前端的后端，是一种帮助我们改善客户端与后端系统通信的模式。在构建系统时，我们通常有不同类型的客户端：使用 HTML/JS 的基于 Web 的应用程序、像 React 这样的 Web 框架、用于 iOS 或 Android 的移动客户端、桌面应用程序、直接的 API 请求或第三方应用程序。每个客户端都需要来自不同后端服务的、结构不同的数据。

我们的问题是，所有这些客户端如何与所有后端服务器通信，而不会过度增加复杂性并使其变得笨重。解决方案是使用本章前面讨论的 API 网关模式，但为每个客户端单独使用。

![](img/Figure-6.7.jpg)

**图 6.7：** 通过 API 网关实现面向前端的后端

该模式的主要缺点与我们描述的 API 网关的缺点相同：需要维护另一个服务，另一个活动部件，这增加了复杂性。此外，增加另一个服务意味着另一次网络跳转，会导致更慢的延迟。

另一方面，使用面向前端的后端具有与 API 网关相同的优势。当为每个客户端创建最优 API 时，面向前端的后端模式非常有益。每个客户端的优化可能因客户端而异；例如，基于 Web 的应用程序可能比移动应用程序需要更多的数据。

## 外部配置

在微服务架构中开发服务时，我们编写的代码会被部署到多个环境中，而非单一环境。每个环境彼此隔离。常见的环境类型包括生产、预发布（有时称为预生产）、QA 和开发。每个服务在每个环境中都需要不同的配置。例如，每个环境都有独立的数据库，连接第三方服务的配置各不相同，凭证也不同，还有许多其他差异。我们不想创建每个服务的副本；作为开发人员，我们讨厌重复（DRY）。问题在于如何在不创建代码重复的情况下将所有这些服务部署到不同的环境中。

解决方案就是这种模式——使配置对服务外部化。服务启动时，通常会通过环境变量从外部服务/源拉取配置。配置注入也可以通过环境变量以外的其他方式执行。必须谨慎小心。环境配置之间的混淆可能会非常痛苦，比如将开发和生产环境的数据库配置弄反了。

在 *第 8 章，Kubernetes 简介* 中，我们将看到 Kubernetes 如何通过环境变量无缝地帮助注入配置。一个广泛使用的工具 Helm，是 Kubernetes 之上的力量倍增器，并提供模板引擎，实现更无缝的配置。

## 服务网格

描述服务网格的最佳方式是将其作为一个专用的基础设施层，用于处理微服务之间的通信。它通常在网络层提供工具，如本章所述的元素——负载均衡器、服务发现、安全性和监控（日志、指标等）。理解这项技术的存在及其能给我们带来很大帮助至关重要。使用服务网格的主要缺点是它可能难以配置。当我们达到框架不存在的某些能力时，我们通常没有灵活性来满足我们的需求。

提供服务网格的三种流行市场技术是 Istio（用于 Kubernetes）、Linkerd 和 Consul。建议详细阅读相关内容；本节只是一个总结。

## 事件驱动架构

事件驱动架构是一个庞大的话题。我们将讨论在微服务架构中实施事件驱动架构的交集。事件驱动架构是一个迷人的话题，遗憾的是，我们无法在本书中妥善讨论它。相反，针对这一主题，强烈推荐的书籍是“*Designing Event-Driven Systems*”。

在深入探讨微服务与事件驱动的接口之前，让我们先了解事件驱动架构的基础知识。

### 事件与消息

**消息** 是具体的，我们从特定服务发送消息给另一个服务。发送方和接收方双方都知晓模式。发送方请求数据，并且知道如何根据约定的模式从接收方请求。另一方面，接收方期望根据约定的模式收到请求，并按承诺响应数据。模式对于发送方和接收方是唯一的，且位置是预先确定的。

**事件** 则更为通用。事件将包含数据，而非请求或指令。事件没有特定的目的地。它被发射并广播给那些将监听并消费该事件的对象。事件还包含一个 ID 以保证唯一性。事件是不可变的，不能被更改。

### 事件驱动架构

事件驱动架构基于我们在前几章学到的发布/订阅模式。正如发布/订阅模式中所讨论的，我们需要三个组件来实现事件驱动架构：发布者、事件代理和消费者。以下是事件驱动架构的常见用例：

*   **跟踪另一个系统的事件**：如果我们想创建一个通过事件跟踪另一个系统的系统，我们很可能被迫构建事件驱动架构。
*   **审计**。
*   **大数据处理**：CRUD 操作可能会产生许多冲突；转向事件驱动架构可以减少这种摩擦。
*   **后端处理**：由于业务逻辑的要求。

#### 优点

*   **解耦服务**：与微服务类似，事件驱动架构能更进一步地帮助我们减少服务间的摩擦，使其变为松耦合。
*   **可扩展性**：基于相同的原因，发布/订阅模式帮助我们进行扩展。我们可以分别控制生产者和消费者，分别对它们进行扩展、处理故障、部署新版本等。

#### 缺点

*   **数据一致性**：将发布者和订阅者隔离开的缺点是，订阅者在处理事件时可能会遇到延迟，主要是在处理大量消息时。维护一致性和处理事件变得具有挑战性，特别是当事件涉及与其他事件相关的逻辑或与第三方服务的交互时。
*   **重复事件**：事件驱动架构基于断点工作。如果发生严重故障，我们总是可以从之前的检查点“重新驱动”事件。问题在于在故障发生前我们可能已经处理了一些事件，因此我们必须再次处理相同的事件。
*   **复杂性**：正如本书多次提到的——当我们添加更多组件和服务时，我们的系统将变得更加复杂。

## 事件溯源

事件溯源是一种有助于利用事件优势和特性的模式。由于事件的威力，我们不必暴露 `update` 和 `delete` 操作。相反，所有事件将始终被保存，并在服务请求时进行聚合。这基本上就是事件溯源模式的作用。通常，使用 API 的服务希望对数据执行 CRUD（创建、读取、更新、删除）操作。相反，数据看起来将像是事件聚合成的状态。无论是否使用事件溯源，最终结果应该是相同的。

![](img/Figure-6.8.jpg)

**图 6.8：** 事件溯源与 CRUD 操作对比。

事件溯源“减少”了 CRUD 操作的数量。它“禁用”了更新和删除操作，“启用”了仅创建操作，并为读取操作创建了一个替代方案。该模式有两个优势，包括：

*   **不可变性**：所有内容均被保留和更新。原始数据被保存，我们无需猜测原始数据是什么。我们无需付出巨大努力即可获得强大的可见性，准确了解发生了什么。
*   **可重放性**：Bug 和问题终将发生。在其他场景中，我们对此无能为力。但现在，我们拥有从 Bug 引入时刻起流式传输事件所需的所有数据（事件）。

该模式的显著缺点是我们现在需要存储更多的数据！处理大量数据会暴露许多隐藏问题。例如，我们将不得不管理数据保留、索引和完整性；这只是冰山一角。只有当我们知道在某个时刻不再需要那些事件时，才能实现数据保留。

相反，查询时间可能会延长，因为我们需要在每次请求中执行聚合，但为此我们有 CQRS。

## CQRS

CQRS 代表命令查询职责分离，是一种帮助我们在独立进程中执行更新和读取的模式。CQRS 基于事件溯源模式。CQRS 模式旨在在写入和读取处理程序之间创建分离。正如我们提到的，用户最终希望检索数据，但数据是作为一组事件保存的。我们不在每次读取请求时计算聚合，而是每次处理事件（创建）时，触发带有某些逻辑的所有事件的聚合。最后，它将聚合作为状态保存到视图中。处理程序将暴露一个 API 从视图中读取数据。

![](img/Figure-6.9.jpg)

**图 6.9：** CQRS 标准用法

上图显示了三种事件类型 - `EventA`、`EventB` 和 `EventC`。所有这些事件类型都将事件流式传输到处理程序中（它们之间有一个我们未绘制的发布/订阅机制）。然后，处理程序将所有事件写入 `Tables`。每次写入都会触发一个逻辑，计算状态并将该状态写入 `View`。当图中的用户（`Reader`）希望读取数据时，它请求 `View`（绿色箭头）而不是 `Tables`（红色箭头）。

CQRS 的巨大优势显而易见——它提供了快速读取！尽管有巨大优势，CQRS 也有两个缺点：

*   我们需要将所有事件归约为一个状态，这有时涉及大量数据，因此执行时间可能很长。
*   写入后读取不能立即可用。

## 结论

在本章中，我们简要介绍了微服务架构的核心要素。虽然我们没有深入探讨每个要素和模式，但我们对微服务架构的重要要素有了清晰、明确的理解。通常，我们不会在每个微服务架构中使用本章描述的所有要素。然而，本章描述的大多数模式都以各种方式实现在大多数微服务架构中。此外，请记住我们是开发人员，运维人员（通常是 DevOps）可能会构建所有这些要素。他们将建立所有必要的基础设施，将我们的应用程序和服务部署到生产环境。作为开发人员，我们必须了解整个系统运维的工作原理。这些知识将帮助我们理解我们的单个服务与其他服务及整个系统之间的边界。

我们描述的所有要素都不包含我们业务的业务逻辑。业务逻辑会影响本章讨论的要素的决策和设计。我们没有深入探讨编写单个服务的实践，即业务逻辑。这是我们在下一章需要做的事情。我们将深入探讨在微服务架构中使用 Go 编写特定服务的最佳实践和技术。

# 构建 RESTful API

## 简介

REST 代表表述性状态转移，是一种架构风格。REST 定义了一组 API 应满足的约束，以符合 REST 风格的要求。RESTful 是形容词，指遵循 REST 约束的 API。在本章的第一节中，我们将详细阐述这些约束。

在本章中，我们将深入探讨 REST 的约束，并通过一个 Go 语言服务进行演示。在上一章中，我们讨论了微服务架构中服务间的通信方式。通信的普遍模式是通过 API 调用，而 REST 是 API 最广泛采用的架构风格。因此，我们的主要关注点将放在 REST 架构模式上。微服务架构天然贯穿了整个系统的 REST 约束，反之亦然。微服务与 REST 之间存在强关联。更广泛地说，微服务 <> Go <> REST <> Kubernetes 之间存在更强大的关联。

![](img/Figure-7.1.jpg)

**图 7.1：** Google Trends 中的“REST”搜索词

正如我们从 Google Trends 所见，REST 方法多年来变得非常流行。随着这种流行度，出现了许多 RESTful API，其中一些因其值得称道的 REST 实现而变得非常流行。在初学 REST 或刚编写新的 RESTful API 时，参考知名 API 既愉快又有启发。这里列举两个例子：

*   Stripe API
*   Twilio API

有三个主题我们不会在本章涉及，将在后续章节中涵盖，它们与 REST 相关：

*   故障设计
*   监控
*   安全 - 认证、授权
