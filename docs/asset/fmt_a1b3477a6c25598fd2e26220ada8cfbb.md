
我们已经演示了将 C 库链接到 Go 程序中。反之，也可以将 Go 程序编译为静态归档文件以便链接到 C 程序，或编译为共享库以便被 C 程序动态加载。我们这里只是浅显地介绍了`cgo`，关于内存管理、指针、回调、信号处理、字符串、`errno`、终结器，以及 goroutine 与操作系统线程之间的关系，还有很多内容要讲，其中许多都非常微妙。特别是正确地在 Go 和 C 之间传递指针的规则很复杂，原因类似于我们在第 13.2 节中讨论的，且尚未有权威规范。更多阅读请从`https://golang.org/cmd/cgo`开始。

**练习 13.3：** 使用`sync.Mutex`使`bzip2.writer`能够安全地被多个 goroutine 并发使用。

## 13.5 再一次警示

我们在上一章末尾曾警告过反射接口的缺点。本章所述的`unsafe`包，该警告适用得更为强烈。

高级语言不仅将程序和程序员与各个计算机指令集的晦涩细节隔离开来，还使其免受内存中变量位置、数据类型大小、结构体布局细节以及其他大量实现细节等无关因素的依赖。正是由于这层隔离，才能编写出安全、健壮且无需修改即可在任何操作系统上运行的程序。

`unsafe`包让程序员穿透这层隔离，以使用某些关键但原本无法访问的特性，或者可能为了获得更高的性能。代价通常是牺牲可移植性和安全性，因此使用`unsafe`需自担风险。我们关于如何以及何时使用`unsafe`的建议，与我们在第 11.5 节中引用的 Knuth 关于过早优化的评论不谋而合。大多数程序员永远不需要使用`unsafe`。尽管如此，偶尔会出现某些关键代码最适合用`unsafe`编写的情况。如果仔细研究和测量表明`unsafe`确实是最佳方法，请将其限制在尽可能小的区域内，使程序的大部分对其使用毫不知情。

暂时将最后两章放在脑后。编写一些实质性的 Go 程序。避免使用`reflect`和`unsafe`；只有在不得已时才回头阅读这些章节。

同时，祝你 Go 编程愉快。我们希望你像我们一样享受编写 Go 的乐趣。
