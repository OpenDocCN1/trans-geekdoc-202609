
# 国际标准化组织 (ISO) 开放分布式处理参考模型 (RM-ODP)

国际标准化组织 (ISO) 开放分布式处理参考模型 (RM-ODP) 包含五个视角：企业、信息、计算、工程和技术。RM-ODP 由 14 个标准组成，涵盖软件工程和企业架构，用于设计异构、可互操作的 IT 系统。关于 ISO 标准，请见 [`committee.iso.org/sites/jtc1sc7/home/projects/flagship-standards/isoiec-10746.html`](http://committee.iso.org/sites/jtc1sc7/home/projects/flagship-standards/isoiec-10746.html)。

## FRISCO

IFIP 工作组开发的信息系统概念框架 (FRISCO) 提供了信息系统工作中使用的概念分类法（Falkenberg et al., 1998）。尽管未被广泛采用，但 FRISCO 报告为信息系统开发提供了一些有用的见解。

## 2.5 总结

针对给定应用的信息系统可以从至少四个层级来看待：概念、逻辑、物理和外部。在每个层级，形式模型或知识库包含一个模式，它描述 UoD 的结构或设计，以及一个填充了事实实例的数据库。每个模式决定其数据库允许的状态和转换。

* **概念模式** 使用简单、面向人类的概念来做到这一点。
* **逻辑模式** 将信息分组为通用逻辑架构支持的结构（例如关系）。
* **物理模式** 指定用于实现应用程序的特定 DBMS 或平台的物理存储和访问结构（例如索引）。
* 对于相同的全局概念模式，可以根据要访问什么信息以及如何显示信息，为不同的用户群构建不同的 **外部模式**。

概念模式包含三个主要部分：`事实类型`、`约束` 和 `推导规则`。断言或基本事实是原始的（即它们不是从其他事实推导出来的）。推导事实是通过将推导规则应用于其他事实来计算或推断得出的。在声明事实类型时，我们指明 `对象类型`、这些对象类型如何被 `引用` 以及它们扮演什么 `角色`。关系中的每个角色仅由一个对象类型扮演。

最简单的对象类型是 `value`（例如字符串）。`Entities`（实体）是通过与其他对象（通常是值）的关系来识别的真实或抽象对象。例如，一个国家可以通过其名称来识别。

`Static constraints`（静态约束）决定了事实类型的允许实例集。`Dynamic constraints`（动态约束）限制了这些实例集之间的转换。例如，每个城市最多只能是一个国家的首都，且成年人不能变成儿童。

概念数据库中的每个事实通常是 `elementary`（基本）的。事实的添加或删除是一种简单更新。在 `compound transaction`（复合事务）中，可能包含多个简单更新；在这种情况下，约束仅适用于完整更新序列的净效果，而不适用于每个单独的更新。概念数据库或概念模式上的更新和查询由 CIP 处理。

每个 DBMS 都符合一种 `logical`（逻辑）数据模型（例如网状、层次或关系模型）。如果选择关系 DBMS 进行实现，概念模式将映射到 `relational schema`（关系模式）或关系数据库模式。在这里，所有存储的事实都被放置在命名的 `tables`（表）中，具有命名的列和未命名的行。关系表的每一行通常对应一个或多个基本事实。每个单元格（行列位置）最多包含一个值。在一个表内，不允许有重复的行。

关系表的实例集可以通过插入、删除或修改行来更改。大多数概念约束和派生规则可以在关系 DBMS 语言中表示，或通过与另一种语言的接口来表示。

`information systems life cycle`（信息系统生命周期）通常涉及以下阶段：可行性研究；需求分析；数据和过程的概念设计；逻辑设计；基本物理设计；基本外部设计；原型开发；生产版本实现；测试和验证；软件、文档和培训的发布；以及维护。来自后期阶段的反馈可能表明需要重做早期阶段。

仔细关注早期阶段可以减少总体工作量，重用以前在类似应用中使用的设计策略也是如此。对于大型项目，通常建议采用迭代开发方法，即在转移到另一个组件之前，将生命周期应用于一个组件。

存在多种信息系统架构框架。Zachman 框架由五行组成，从不同视角（范围、企业模型、系统模型、技术模型和细节）审视系统，以及六列，具有不同的关注点（数据、功能、网络、人员、时间和动机）。扩展的四模式框架使用相同的六列，但有六行，分别对应概念、外部、逻辑持久、逻辑瞬态、物理持久和物理瞬态视角。其他著名的系统架构包括 TOGAF、MDA 和 RM-ODP。

### 章节注释

关于信息系统的概念、内部和外部模式的经典论述见于 van Griethuysen (1982)。一些参与该 ISO 标准工作的人员也参与了 FRISCO 报告（Falkenberg et al., 1998）。与许多其他作者（例如 Elmasri and Navathe, 1994）一样，我们认为数据的关系模型是一种 `logical`（逻辑）模型，而不是概念模型，主要是因为它离自然语言太远。从这个角度来看，关系模式代表了内部模式的逻辑部分（省略了特定于所选 DBMS 的细节，以及索引等存储和访问细节）。Codd (1990, pp. 33–34) 提出了三级架构的另一种解释，其中关系数据库的基本关系提供概念模式，而视图提供外部模式。

需求分析的标准参考是 ANSI/IEEE 标准 830-1984。关于信息系统工作不同方法的比较综述见于 Olle et al. (1991)。Mylopoulos (1998) 提供了关于信息系统建模关键问题的信息丰富的概述。Pohl (1994) 详细阐述了需求工程的规范、表示和协议维度。Bubenko (2007) 提供了关于信息系统建模的历史视角。

各种业务领域的数据模型模式可在多本书籍中找到，包括 Hay (1996，2006) 和 Silverston (2001a，b)。这些示例模型通常用本书后面介绍的 ER 符号之一表示。

Zachman (1987) 介绍了他的架构框架（参见 [`en.wikipedia.org/wiki/Zachman_Framework`](https://en.wikipedia.org/wiki/Zachman_Framework)）。Hay (2003) 对 Zachman 框架进行了广泛讨论，并主张应重命名某些行描述符。

TOGAF 的详细信息可在 [www.opengroup.org/togaf/](http://www.opengroup.org/togaf/) 和 [`en.wikipedia.org/wiki/TOGAF`](http://en.wikipedia.org/wiki/TOGAF) 在线获取。关于 OMG 的 MDA 方法的资源，请参见 [`www.omg.org/mda/`](http://www.omg.org/mda/)。关于 ISO RM-ODP 标准，请参见 [`committee.iso.org/sites/jtc1sc7/home/projects/flagship-standards/isoiec-10746.html`](http://committee.iso.org/sites/jtc1sc7/home/projects/flagship-standards/isoiec-10746.html)。关于 RM-ODP 的更多详细信息，请参见 [`en.wikipedia.org/wiki/RM-ODP`](https://en.wikipedia.org/wiki/RM-ODP) 和 [`rm-odp-new.lcc.uma.es/`](https://rm-odp-new.lcc.uma.es/)。

## 3.1 概念建模语言标准

在讨论对象角色建模（ORM）的概念模式设计过程（CSDP）之前，让我们回顾一下支撑 ORM 语言的设计原则。其中一些观点之前已提及，但我们在此将讨论进行了概括，以便您可以应用这些原则来评估一般的建模语言。在阅读本书的过程中，请思考这些原则是如何在所讨论的各种语言中得以实现的。

建模方法（或建模过程）包含一种语言和一个描述如何使用该语言构建模型的过程。一种语言具有相关的语法（标记）、语义（含义）和语用学（用法）。书面语言可以是图形化的（图表）和/或文本化的。“抽象语法”和“具体语法”这两个术语有时分别用于区分底层概念（例如，对象类型）及其表示形式（例如，命名的圆角矩形）。

概念建模在高层级上描绘业务领域，使用业务用户熟悉的术语和概念，忽略逻辑和物理层面的方面（例如，用于实现的底层数据库或编程结构）以及外部层面的方面（例如，用于数据录入的屏幕表单）。源自不同来源的以下标准（van Griethuysen, 1982；ter Hofstede, 1993；Bloesch and Halpin, 1996）为评估概念建模语言提供了依据。

* 表达能力
* 清晰度
* 简洁性和正交性
* 语义稳定性
* 语义相关性
* 验证机制
* 抽象机制
* 形式化基础

一种语言的 **表达能力** 衡量的是它能用来表达什么。语言能表达的内容越多，其表达能力就越强。理想情况下，概念语言应能完整建模概念层面上与业务领域相关的所有细节。这被称为 **100%原则**（van Griethuysen, 1982）。ORM 是一种在概念层面对信息系统进行建模和查询，以及在概念层面与其他层面之间进行映射的方法。尽管 ORM 的过程建模扩展正在研究中，但 ORM 的主要焦点是信息建模（通俗称为数据建模），因为数据视角更稳定，并为操作的定义提供了形式化基础。总体而言，统一建模语言（UML）的范围比 ORM 更广，因为 UML 用例图、行为图和实现图对静态结构之外的方面进行建模。然而，对于概念数据建模，ORM 的图表符号比 UML 类图或实体关系（ER）图具有强得多的表达能力。

一种语言的 **清晰度** 衡量的是它有多容易理解和使用。首先，语言应当是无歧义的。语言的表达能力越强，越难保持清晰度。理想情况下，该语言中图表或文本表达式的含义应直观明显。这一理想很少能完全实现。一个更现实的目标是语言的概念和符号应易于学习和记忆。为达到这一目标，语言应表现出 **简洁性** 和 **正交性**。通过避免使用属性，ORM 基于角色的符号得以简化，但通过填充事实实例却易于理解。正交性允许在任何其含义或值可被使用的地方使用表达式。ORM 的构造从一开始就被设计为正交的。例如，ORM 约束可以在任何有意义的情况下被使用和组合。正如我们稍后将看到的，UML 等语言并不具备这一特性。

**语义稳定性** 衡量的是用该语言表达的模型或查询在面对业务领域变化时，保持其原始意图的程度。为了应对业务变化，我们需要对模型或查询做的修改越多，其稳定性就越低。ORM 中的模型和查询比 ER 或 UML 具有更高的语义稳定性，因为它们不受导致属性被重新建模为关系或反之亦然的变化的影响。

**语义相关性** 要求仅建模概念上相关的细节。任何与含义无关的方面（例如，实现选择、机器效率）都应避免。这被称为 **概念化原则**（van Griethuysen, 1982）。ORM 模型和查询纯粹是概念性的。相反，UML 类模型包含实现方面（例如，属性可见性和关联可导航性）。

**验证机制** 是领域专家检查模型是否与业务领域匹配的方式。例如，静态特征可通过口语化和实例化来检查，动态特征可通过模拟来检查。与 ER 和 UML 不同，ORM 模型总是易于口语化和填充实例。

### 抽象机制

**抽象机制** 允许从直接考量中移除不需要的细节。这对于大型模型（例如墙面大小的模式图）非常重要。因为 ORM 图往往比相应的 ER 或 UML 图更详细、更大，所以经常使用抽象机制。例如，全局模式可以根据跨度或视角模块化为各种作用域（例如，数据模型的单页或活动模型的单页）。逐步求精可用于将高层视图分解为更详细的视图。虽然这不是一个语言问题，但工具可以提供额外支持，如分层和对象缩放（见后文）。此类机制可用于隐藏细节，仅显示与用户当前需求相关的模型部分。通过细微的变化，这些技术可应用于 ORM、ER 和 UML。ORM 还包含一个属性抽象过程，用于生成 ER 和 UML 图作为视图。

### 形式化基础

需要 **形式化基础** 来确保无歧义性和可执行性（例如，自动化模型的存储、验证、转换和仿真），并允许对模型间的等价性和蕴含关系进行形式化证明。尽管 ORM 更丰富的图形化约束表示法提供了更完整的模式转换图解处理，但文本约束语言的使用可以部分抵消这一优势。对于其数据建模构造，ORM、ER 和 UML 都可以获得充分的形式化基础。

### 语言设计权衡

语言设计通常涉及在相互竞争的标准之间进行多项 **权衡**。一个众所周知的权衡是 **表达能力** 与 **可处理性** 之间的权衡：语言的表达能力越强，要使其高效可执行就越困难 (Levesque, 1984)。另一个权衡是 **简洁性** 与 **便利性** 之间的权衡。虽然 **其他条件相同** 时，概念越少越好（参见奥卡姆剃刀原则），但将自己限制在最少可能的概念数量有时可能过于不便。例如，可以使用仅由 0 和 1 组成的字符串，用纯二进制编写计算机程序，但用 `C#` 等高级语言编写程序要容易得多。作为一个逻辑示例，使用“非”、“与”、“或”和“如果-那么”等多个运算符更方便，尽管我们只用一个（例如“与非”）就足够了。有关此示例的进一步讨论，请参阅本章注释。

### 属性概念作为基本构造

与简洁性-便利性权衡相关的一个基本问题是：是否将属性概念作为基本建模构造。我们已经倾向于否定这个问题的答案。ORM 使用关系而非属性，以便于捕获、验证和演进概念模式，同时仍允许自动推导出紧凑的属性视图，用于汇总或实现目的。传统 ER 支持单值属性，而 UML 支持单值和多值属性。我们稍后将论证，多值属性通常不适合概念建模，尽管它们对于逻辑和物理建模可能很有用。

## 3.2 概念模式设计过程
