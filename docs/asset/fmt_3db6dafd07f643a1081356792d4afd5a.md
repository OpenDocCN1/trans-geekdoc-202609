## 13.4 SQL：触发器

*触发器*提供了另一种更改表内容的方式。尽管直到 SQL:1999 才被纳入标准，但商业方言已使用触发器多年。除了强制实施约束外，触发器还可用于执行其他操作，包括计算派生列、在其他表中维护审计或汇总数据，以及启动发送电子邮件等外部操作。

触发器指定一组 SQL 语句，当给定事件在表上发生时（或者在稍后讨论的某些情况下，在视图上发生时），这些语句将自动执行。导致触发器执行的事件可以是尝试*插入*新行、*删除*现有行或*更新*表中的现有行。触发器动作可以指定在相关操作（插入、更新或删除）发生之前*立即*或之后*立即*执行。

可以在一个表上定义多个触发器。所有**前置**触发器将在对表执行任何操作（包括约束检查）之前执行。这提供了一个机会来检查即将发生的操作，并在必要时对其进行修改。所有**后置**触发器将在执行完约束检查且操作已发生之后，但在任何更改被提交之前执行。这提供了一个机会来检查已发生的更改，并在需要时回滚相关事务。如果存在多个**前置**触发器，不同厂商可能提供指定触发器顺序的功能，**后置**触发器同理。

在触发器主体内，可以引用一个或两个*转换表*的内容。这些表包含受触发器事件影响的行。转换表的列与触发器所基于的表的列定义相匹配。对于删除触发器，有一个包含被删除行的*旧*转换表。对于插入触发器，有一个包含被插入行的*新*转换表。更新触发器同时拥有一个包含更新前行数据的*旧*转换表和一个包含更新后行数据的*新*转换表。在更新情况下，*旧*转换表中的每一行都将在*新*转换表中有一个对应的行。转换表仅在触发器持续期间存在，无法从触发器外部访问。

触发器动作可以指定在*行级*或*语句级*发生。在前一种情况下，动作针对转换表的每一行发生一次。在后一种情况下，动作仅在触发器事件发生时发生一次。根据触发器是在行级还是语句级定义，触发器代码可以访问*转换变量*，这些变量要么是来自旧/新转换表的单个行，要么是完整的转换表。

在 SQL:1999 中，创建和删除触发器的语句具有以下语法：

```
create trigger triggername
    { before | after }
    { insert | delete | update [ of col-list ] }
    on tablename
    [ referencing
        { old | new } [row] [ as ] correlation-name |
        { old | new } table [ as ] table-alias
        [, …] ]
    [ for each { row | statement } ]
    [ when ( condition ) ]
triggered-SQL-statement

drop trigger triggername
```

尽管大多数 SQL 方言支持触发器，但它们不一定符合上述创建触发器的标准语法。例如，SQL Server 目前不支持**前置**触发器。

除了**前置**和**后置**触发器外，SQL:2003 还引入了第三种触发器：**替代**触发器。顾名思义，触发器动作是*替代*触发事件执行的。**替代**触发器的一个重要应用是拦截修改视图的尝试，并将其替换为对该视图所基于的表进行的适当修改集。

作为示例，我们可以回到前面定义的 *FemaleCompScientist* 视图。

```
create view FemaleCompScientist ( empNr, name, rank ) as
select empNr, empName, grade
from Academic
where dept = ‘CS’ and gender = ‘F’
```

回想一下，基表 `Academic` 有列（`empNr`、`empName`、`dept`、`[ gender ]`、`grade`）。尝试向视图插入新行，例如

```
insert into FemaleCompScientist
values ( 105, ‘Bird, L’, ‘Lec’ )
```

将会失败，因为我们没有 `dept` 和 `gender` 列的值；空值条目将违反视图定义。然而，我们可以使用**替代**触发器来拦截尝试的插入，转而在基表中进行正确的插入，如下所示：

```
create trigger AddFCS
instead of insert on FemaleCompScientist
referencing new row as Inserted
for each row
insert into Academic ( empNr, empName, grade, dept, gender )
select empNr, empName, rank, 'CS', 'F'
from Inserted
```

我们从*新转换变量*中的 `empNr`、`empName` 和 `rank` 列获取 `empNr`、`empName` 和 `grade` 的适当值。根据视图定义，我们已经知道 `dept` 和 `gender` 的值必须分别为“CS”和“F”。这使我们能够正确地将新行插入 `Academic` 基表。随后对视图的 **select** 命令将显示插入似乎已成功，新行现已出现在视图中。

## 13.5 SQL：例程

SQL 标准使用通用术语*例程*来描述可以从其他代码调用的代码主体——这涵盖了函数、过程和用户定义数据类型的方法。

### 用户定义函数 (UDF)

### 函数与存储过程

#### 函数

我们首先来看函数，简单来说，函数是返回结果的代码体。SQL 标准定义了大量内置函数，用于计算对数、生成随机数、将字符串转换为全大写或全小写等。这些函数可在 SQL 代码中任何适当的地方使用。能够定义新函数来封装可能被重复使用的代码片段也非常方便。在 SQL 中，函数可以返回给定数据类型的标量（单个）值。SQL:2003 标准扩展了这一概念，使其包含返回表的函数。

创建函数的基本 SQL:2003 语法如下。

```
create function functionname ( [ parameter-list ] )
returns { data-type | table col-name data-type [,...] }
function-body
```

`parameter-list`（参数列表）是一个（可能为空的）以逗号分隔的参数名、参数类型对列表。返回值的数据类型可以是任何合法的 SQL 类型。函数体可以由任何有效的 SQL 语句组合而成，但必须包含一个 `return` 子句，用于返回 `returns` 子句中指定类型的参数。可以使用 `drop function function-name` 删除 UDF（用户定义函数）。

商业 DBMS 可能会施加其他限制。例如，在 SQL Server 中，UDF 不能使用那些如果使用相同参数重复调用函数会产生不同结果的 SQL 语句。此类语句的示例包括获取当前时间和生成随机数。SQL Server 还禁止 UDF 中的副作用，因此，例如，函数不能用于更新基表。

以下示例展示了一个用于 SQL Server 的标量 UDF，它接受一个货币金额（定义为十进制值）和一个货币符号作为参数，并返回一个由货币符号与金额的字符串版本连接而成的字符串。SQL Server 使用 `+` 进行字符串连接，这与标准的 `||` 不同。

```
create function moneyString ( @amount decimal( 9, 2 ), @symbol char ( 1 ) )
returns varchar ( 11 )
return @symbol + cast ( @amount as varchar(10) )
```

一旦定义，函数通常可以在任何可以使用返回类型值的地方使用。因此，以刚才的示例为例，我们可以在任何 `varchar(11)` 值合法的地方使用对 `moneyString()` 的调用。

#### 存储过程

存储过程，通常被称为 "sprocs"，是从其他代码中显式调用的代码体。在本节中，我们假设过程体是用 SQL 编写的，但过程操作也可以用其他语言（如 "C"）编写，然后从 SQL 中调用。存储过程可以（且经常）产生副作用，例如在执行期间更新表。将代码封装在存储过程中有几个潜在的好处。

##### 模块化

存储过程中的代码可在其他代码中轻松重用。一个维护良好的存储过程库在开发新应用程序时可以成为宝贵的资源。模块化也有助于确保一致性。例如，业务规则可以在存储过程中实现一次，然后根据需要调用，而不必在不同地方以略微不同的方式多次实现同一规则。同样的道理也适用于可维护性。如果需要更改，只需在一处应用即可。只要保持原有的接口不变，调用该存储过程的其他程序就无需知道所做的任何更改。

##### 安全性

存储过程的用户只能获得该过程提供的功能。以这种方式限制访问可大大降低对数据库造成损害的可能性，无论是故意还是意外。授予存储过程用户的权限可以不同于访问任何底层表的权限，因此任何操作只能在过程的上下文中进行。例如，对 "Orders" 表的所有修改都可以通过一个存储过程进行，该过程对可以进行的更改施加业务规则和其他约束，而不是给予用户对基表的直接访问权限。

##### 性能

存储过程通常会被编译、优化并缓存，以便在需要时随时可用。细节因实现而异，通常会提供基本语法的扩展来解决诸如使用环境改变时需要重新编译和优化等问题。存储过程还可以减少网络流量：应用程序不必构建查询并将生成的 SQL 通过网络传递，只需将参数传递给存储过程即可。

创建和删除存储过程的基本语法如下。

```
create procedure procedurename
    ( [ { in | out | inout } parmname parmtype [,...] ] )
procedure-body
drop procedure procedurename
```

存储过程接受零个或多个参数。每个参数可以指定为 `in`（向过程提供外部值）、`out`（过程使其结果可在外部访问）或 `inout`（输入参数可被过程修改以供外部访问）。像往常一样，商业系统可能与标准语法有所不同。例如，在 SQL Server 中，除非存储过程的参数被显式标记为 `out`，否则均视为 `in` 参数，并且没有 `inout` 选项。

过程体由任何合法的 SQL 语句组合构成。存储过程可以调用其他过程，过程也可以递归调用自身。实现可能会对允许的嵌套层数施加限制，例如，SQL Server 允许嵌套深度高达 32 层。存储过程也可以从触发器内部调用，这既提供了自动调用的优势（当相关触发器事件发生时），又提供了存储过程的模块化优势。例如，我们可能希望在几种不同的情况下应用相同的约束，这可以通过让几个不同的触发器调用同一个存储过程来实现。

存储过程中需要注意的一条 SQL 语句是 `return` 语句。一旦遇到 `return`，存储过程会立即退出，因此 `return` 通常与测试条件的一个分支相关联，逻辑类似于 "如果 x 成立则返回，否则……"。虽然实现不一定强制要求，但推荐的做法是使用与 `return` 语句关联的值来指示状态。通常，返回代码零表示 "一切正常"，非零值用于指示遇到的特定错误条件。存储过程执行的任何计算结果应通过 `out` 参数返回，而不是使用 `return` 值。

## 13.6 更多数据库对象

### 序列

在 SQL 中，序列是一种自动生成一系列值的数据库对象；请注意，这与 XQuery 中“sequence”（序列）一词的用法含义完全不同，稍后我们将看到。序列对象最早于 SQL:2003 中引入，当需要生成唯一键值时非常有用。在数据库内部生成唯一值，而不是在外部应用程序中生成，可以减少在性能和并发等领域出现问题的可能性。某些 SQL 实现可能会预先计算序列中的下一个值并将其缓存，以便立即使用。

在某些方面，序列类似于表中的标识列。然而，与标识列不同，序列不绑定到某个特定表，并且序列值在数据库范围内唯一，而非仅在表范围内唯一。可以使用以下语法创建序列。
