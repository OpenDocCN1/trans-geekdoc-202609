
例如，当许多较旧版本的 Windows 2000 的用户启动 IIS Web 服务器时，操作系统也会在默认安装下自动启动 Gopher 服务。从未听说过 Gopher？加入俱乐部吧。Gopher 是一种服务，在世界范围的网络浪潮来临之前，它在信息检索方面显示出巨大的前景。今天，没有人使用它。然而，当攻击者发现鲜为人知的 Gopher 程序存在问题时，他们使几乎所有 IIS 实现在公司安装补丁之前立即容易受到攻击。

## 应用程序最小化的安全基线

再次强调，安全基线应指导我们。安装程序必须知道为给定应用程序安装哪些可选辅助程序，以及哪些是自动安装的，安装后应将其删除。

## 创建安全配置

基线将一般描述如何创建安全配置。最重要的是，应用程序绝不应缺少密码或使用众所周知的默认密码。

## 安装应用程序补丁和更新

最重要的是，安装程序应确保安装所有应用程序补丁。如前所述，这通常涉及跟踪来自许多不同应用程序供应商的漏洞和修复报告。

此外，公司应安装软件的最新版本，必要时更新软件。应用程序的新版本一旦度过最初的“磨合期”，通常比旧版本安全得多。

## 最小化应用程序的权限

如前所述，如果攻击者可以接管应用程序，他们就可以使用程序的权限执行命令。一些程序必须以`root`权限运行。然而，许多程序可以用较低级别的权限运行，并且应使用它们完成工作所需的最低权限运行。

## 添加应用程序级身份验证、授权和审计

阻止攻击者的一种方法是忽略未经过适当身份验证的任何人的输入。因此，要破坏系统，攻击者必须同时拥有利用漏洞和对系统的经过身份验证的访问权限。

操作系统账户密码系统提供了一定的保护，但许多应用程序也提供自己的身份验证。与对计算机的广泛访问相比，应用程序身份验证可以专门针对应用程序程序的需求，例如，只接受访问控制列表上的人员，并给予不同人员与应用程序相关的权限。

应用程序程序可以要求自己的密码——具有强复杂性的密码。或者应用程序程序可能需要智能卡或其他形式的强身份验证，例如公钥身份验证。双因素身份验证甚至更好。

尽管添加应用程序级身份验证很困难，有时甚至不可能，但公司应尽可能做到。对于高度敏感的应用程序，例如人力资源数据库和客户信息数据库，这一点尤其重要。

## 实施加密系统

在第 3 章中，我们看到了 SSL/TLS 和 IPsec 等加密系统提供的强大保护。加密系统保护应始终在用户和应用程序之间使用。

## 保护自定义应用程序

商业现成软件很可能经过精心编写，包括检查安全漏洞。然而，专门为公司自身使用和客户使用而构建的自定义应用程序很少如此精心构建。问题在于普通程序员可能没有接受过良好的安全编码培训，也没有接受过给定编程语言所需良好安全实践的培训。

## 永不信任用户输入

对于所有应用程序，一个基本规则是“永不信任用户输入”。如果用户预计输入文本，请检查输入确实是文本，并确保它不过长，不包含不适当的 URL，不包含脚本，不包含结构化查询语言（SQL）语句或 SQL 语句的一部分，等等。本章后面我们将研究攻击者如何利用不当输入造成损害或入侵计算机。

### 跨站脚本（XSS）攻击

网站编程的另一个危险是意外允许**跨站脚本（XSS）**，即一个用户的输入可能出现在另一个用户的页面上。任何回显用户输入的网页都存在这种危险。例如，如果你输入用户名，下一个网页包含“你好，用户名”，就存在回显。

考虑以下示例。攻击者向目标受害者发送一封电子邮件。邮件中包含一个指向会进行回显的合法网站的链接。该链接很长，超出了 URL 窗口。在用户因超出 URL 窗口而看不到的部分，URL 中有一个脚本。当用户点击 URL 时，包含脚本的 `GET` 请求会发送到合法网站。合法网站会回显合法信息以及脚本。脚本将在用户不干预的情况下执行。如果目标受害者的浏览器存在该脚本旨在利用的漏洞，目标受害者就会成为实际受害者。

### SQL注入攻击

在互联网早期，大多数网站由相互链接的静态 HTML 页面组成。随着时间的推移，页面变得动态化，并与服务器上的后端数据库相连。Web 服务器可以使用户访问受密码保护的数据，并提供定制的网页。与静态页面相比，这是一个巨大的改进。然而，这也使服务器和数据库容易受到新型攻击。

SQL 注入是一种攻击方式，涉及向 Web 应用程序发送修改过的 SQL 语句，该应用程序随后会修改数据库。攻击者可以通过其 Web 浏览器发送意外输入，从而能够读取、写入甚至删除整个数据库。SQL 注入甚至可用于在服务器上执行命令。SQL 注入是许多新闻中常见的高调攻击所采用的一种常见攻击方法。

结构化查询语言 要理解 SQL 注入的工作原理，首先需要大致了解什么是 SQL 以及它如何与数据库交互。结构化查询语言（SQL）是用于访问、查询和管理数据库的计算机语言。SQL 语句使用子句（如`SELECT`、`UPDATE`、`WHERE`）来指定访问哪些数据以及如何操作这些数据。

SQL 查询是最常见的 SQL 语句之一。它使用`SELECT`子句。例如，假设你想买一辆新车。你想要一辆特定价格范围内的红色汽车。你可能在心里想：“从这个停车场中选择所有颜色为红色的汽车，并按价格排序。”这听起来可能有点别扭，但 SQL 查询的所有元素都已具备。下面是以 SQL 语句形式编写时的样子。

```sql
SELECT * FROM Cars WHERE
color='red' ORDER BY price;
```

在这种情况下，SQL 查询从包含汽车信息的数据库中检索信息。该表名为`Cars`，列名为`color`，它返回了所有红色汽车的信息，并根据`price`列的值对结果进行了排序。

> ***警告***：SQL 注入可能造成巨大的破坏和伤害。在其他系统上进行此类操作是违法的，你将受到起诉。未经许可，不要在任何系统上使用 SQL 注入。此处仅供信息参考。

## 传递SQL语句

通常，不允许用户通过网页提交他们自己的 SQL 语句。这对用户来说太难了。这也会让他们对数据库拥有过多的控制权。用户通常从下拉列表、组合框或复选框等控件中选择值。他们也可以输入用户名或密码等值。这些值随后被发送到 Web 服务器和 Web 应用程序（中间件），最终传递给数据库。

中间件服务器负责接受用户传递的值并格式化 SQL 语句。然而，通过 SQL 注入，可以发送格式错误的输入，从而改变 Web 应用程序创建的语句。如图 8-8 所示，修改后的 SQL 语句随后被发送到数据库。随后结果直接发送回用户。

在下面的示例中，你将看到登录屏幕中的值（用户名和密码）如何被输入并正确传递给 Web 应用程序。然后你将看到一个如何恶意使用 SQL 注入的示例。SQL 语句通常写在一行上。为了使语句更易于阅读，子句被放在了单独的行上。

## 正常SQL语句

登录屏幕要求用户输入用户名和密码。这些值随后被传递给 Web 应用程序，并与数据库中的值进行核对。下面的 SQL 语句显示了这些参数如何被传递给数据库，以实现图 8-9 中所示的合法登录。

### 图 8-8 简化的SQL注入路径

![](img/073342643701cc54eb7875c41ab92ef2_404_0.png)

```sql
SELECT * FROM Users WHERE
    username='boyle02' AND
    password='12345678';
```

用户名（boyle02）和密码（12345678）都是**字符串**，可以包含字母、数字和字符。它们都用单引号括起来，SQL 语句以分号结尾。

### 格式错误的SQL语句

在下面的 SQL 语句中，密码（12345678）被替换为文本（`whatever' or 1=1--`），如图 8-10 所示。这将改变 SQL 查询的解释方式。请注意，“whatever”后面的额外单引号将密码括起来。由于实际密码（12345678）不是“whatever”，登录本应失败。然而，额外的参数将确保登录成功。

注入的 SQL 语句的其余部分会正常处理。逻辑运算符“`or`”用于创建两部分的`WHERE`子句。该子句的第一部分将为`WHERE`子句返回一个假值。该子句的第二部分`1=1`将始终返回真值。这保证了登录将会成功。

```sql
SELECT * FROM Users WHERE
    username='boyle02' AND
    password='whatever' or 1=1--';
```

## 使用SQL注入的攻击方法

SQL 注入可以通过几种不同方式使用。**带内** SQL 注入直接从数据库提取数据并将其显示在 Web 浏览器中。**带外** SQL 注入使用格式错误的语句通过不同的应用程序（如电子邮件）提取数据。**推断式** SQL 注入不一定从数据库提取数据。而是通过响应格式错误的 SQL 语句来收集有关数据库的信息。

**基于错误的推断**根据查询后收到的错误消息对底层数据库进行假设。数据库会根据 SQL 语句的解释方式报告不同的错误。有时基于错误的推断不可能实现，因为应用程序开发人员要么阻止返回详细的错误消息，要么返回一个通用的错误页面。在这种情况下，必须使用盲 SQL 注入。

**盲 SQL 注入**使用一系列 SQL 语句，根据真/假问题或定时响应产生不同的响应。例如，一位精明的开发人员可能要求对多个不同的错误发送一条通用的错误消息。这将使基于错误的推断变得困难。

利用盲 SQL 注入，攻击者可以创建一个 SQL 语句，如果*成功*执行，将需要更长的时间来处理（即重复执行一百万次琐碎的任务）。失败的 SQL 语句几乎会立即返回错误页面。成功的 SQL 语句会在延迟（例如 10 秒）后返回错误页面。

## 防止SQL注入

应用程序开发人员可以通过使用带绑定参数的参数化查询和净化输入来最大程度地降低 SQL 注入攻击的威胁。使用绑定参数对查询进行*参数化*，将输入仅视为数据，而不是 SQL 语句的一部分。从用户接收的输入与 SQL 语句分离，且不被解析。

*净化*用户输入涉及删除所有可能用于 SQL 注入的字符。这可能存在问题，因为这些字符经常被用作输入。例如，许多外国姓名使用撇号和连字符（如 O’Connor、D’Angelo、Van’Campen、Al-Kurd 等）。应用程序可能还需要使用“&”或“$”等字符才能正常工作。

此外，限制运行 Web 应用程序所需的权限并使用*存储过程*有助于阻止 SQL 注入攻击。

## AJAX 操纵

Ajax，即异步 JavaScript XML 的缩写，使用多种技术创建动态客户端应用程序。使用 Ajax 有优势，因为它允许本地网页在每次更改时无需与服务器交互即可动态更改。然而，Ajax 的动态特性使其容易受到恶意代码注入、XML 被篡改、客户端验证被操纵等攻击。

当局担心黑客可能利用这些缺陷故意导致飞机坠毁。2015 年几乎发生了这种情况，当时 One World Labs 的安全研究员 Chris Roberts 在飞行中黑入了一架商业客机。^4 Roberts 发出了指令导致飞机爬升并侧飞。在 FBI 的讯问中，Roberts 表示他曾 15 到 20 次黑入飞机。

### 最大银行卡盗窃案

2018 年，俄罗斯黑客 Vladimir Drinkman 和 Dmitry Smilianets 因组织窃取超过 1.6 亿张银行卡被判入狱。^5 这两人是更大黑客组织的一员，该组织专门从事 SQL 注入攻击以窃取信息。该组织针对的是 7-Eleven、NASDAQ、Wet Seal、Heartland 和 JetBlue 等知名公司。联邦调查人员无法估计该黑客组织造成的损失，但他们估计仅 *三* 名受害者的损失就超过 3 亿美元。

Drinkman 和 Smilianets 被荷兰当局逮捕并引渡到美国。Drinkman 被判 12 年监禁，Smilianets 被判 4 年半监禁。剩余的三名同谋——Alexandr Kalinin、Roman Kotov 和 Mikhail Rytikov——仍在被当局通缉。

### 漏洞赏金

2018 年，研究员 Artem Moskowsky 在 Steam 的开发者门户中发现了一个缺陷，允许他下载游戏许可证并玩盗版游戏。更具体地说，Moskowsky 发现如果他在 API 请求中注入随机字符字符串，他就可以获取任何游戏的大量软件许可证密钥。^6 在一次实例中，他从一次修改后的请求中获得了 36,000 个密钥。每个密钥价值约 10 美元。Moskowsky 报告了该漏洞，并从 Valve 获得了 20,000 美元的漏洞赏金。支付漏洞赏金比应对价值数千万美元的知识产权损失要便宜得多也容易得多。黑客喜欢漏洞赏金，因为他们能得到报酬且不必违法。公司也喜欢它们，因为它们可以相当廉价地解决安全问题。
