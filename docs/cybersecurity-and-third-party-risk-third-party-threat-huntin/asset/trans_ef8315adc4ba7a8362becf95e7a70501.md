
# 云安全合规模式

## FedRAMP 标准和中等风险基线
联邦风险和授权管理计划（`FedRAMP`）为云安全提供了一个标准。其设计目的是通过提供标准化的安全和风险评估方法，促进在美国政府范围内采用安全的云服务。该计划有三个支柱。联邦机构是这些服务的请求方，`FedRAMP` 拥有获授权向政府机构提供云服务的 `CSPs`，第三方评估组织则执行初始和定期评估，以确保其符合 `FedRAMP` 要求。在 `FedRAMP` 网站内有一个基于高、中、低风险的安全控制基线。

KC Enterprises 确定，如果供应商能够满足 `FedRAMP` 中等风险要求，那么这就是其业务所需的风险降低水平。中等类别涵盖了前面讨论的许多云控制措施，并以可轻松与供应商和内部利益相关者共享的电子表格形式提供。理想情况下供应商应获得 `FedRAMP` 认证，但供应商也可以将其用作模式，然后提供实施的物理验证（在 `Intake` 和 `Ongoing` 评估监控期间）。

## 用于医疗数据的 HITRUST CSF
虽然 KC Enterprises 没有直接提供医疗服务的业务，但其多个生产工厂和两个大型办公室设有护士办公室。这些办公室提供多项服务，并通过第三方签约。此外，其他供应商可以访问员工的医疗记录。为了为这些情况提供模式，KC 选择了发布了通用安全框架（`CSF`）的健康信息信托（`HITRUST`）联盟。该组织提供了一个可认证的框架，以确保医疗保健提供者和组织能够证明其安全性和合规性。`HITRUST-CSF` 包含 19 个领域，范围从终端保护到移动设备安全。所支持的三个 `CSPs` 都提供 `HITRUST-CSF` 部署，并为网络第三方风险尽职调查提供了一致的方法。

## 云安全联盟 CCM 和 STAR
KC Enterprises 所在的云安全联盟（`CSA`）发布了云控制矩阵（`CCM`）。该 `CCM` 为供应商提供了一个理想的模式或指南。`CCM` 是将云安全控制映射到标准、最佳实践和法规的框架。这种映射对于结构和明确要求驱动因素非常理想。`CSA` 还提供了一个名为 CSA 安全信任与保证风险（`STAR`）的验证计划。`STAR` 使 `CSPs` 能够向其客户验证其云安全产品是安全的。它还允许云客户——在本例中是向 KC 提供云解决方案的供应商——获得认证，证明其遵循了这些指导。虽然优先选择由认可的 `STAR` 评估机构认证的 `STAR` 认证供应商，但 `STAR CCM` 提供了第三方将其用作模式所需的指导。

## CSP 原生安全基线
最后，所有主要 `CSPs` 都为其所有客户提供安全基线。在 `Azure` 上，基线涵盖从 `API Management Security Baseline` 到 `VPN Gateway Security Baseline` 等各个方面。`AWS` 也有类似的指南，`Google Cloud` 亦然。重点集中在涵盖 KC 决定支持的 `CSPs` 的三个选项上。事实上，这种关注是形成“模式”或标准决策的一部分：供应商希望与该公司开展业务，这涉及将敏感数据移至云端，而仅支持三大厂商作为选项。然而，该公司不遗余力地提供满足标准和执行尽职调查的方法。

## 模式方法的优势
这种借鉴自安全架构领域的模式方法，在成为供应商的几乎每个流程步骤中都提供了诸多优势。在 `Intake` 期间，模式以及仅支持三个常见的 `CSPs`（`AWS`、`Azure` 和 `Google`）使得能够更快、更透明地评估风险。`Ongoing` 尽职调查受益，因为您可以提出一套标准问题并获得预期答案，从而避免分析更大范围的潜在替代方案。现场流程使评估人员能够通过供应商从 `CSP` 获取 `Cloud Security Report` 来请求有关其模式的数据，从而获得大部分数据。同样，持续监控团队能够向供应商请求 `CSR`，以确认 IP 范围以及与他们正在追踪的任何警报相关的潜在风险。

供应商和内部客户/利益相关者受益，因为使用模式使网络安全尽职调查流程更高效。请求需要敏感数据的新服务的内部利益相关者拥有明确的选项，且要求更透明。当供应商进行 `RFP` 或 `Intake Risk Questionnaire`（`IRQ`）时，他们能够筛选出仅使用其中一个已批准的 `CSPs`。完成该流程并开始 `Intake` 后，网络安全尽职调查团队可以为供应商提供几种符合 KC 供应商云安全标准的选项，通过所选模式实现供应商与客户网络安全团队之间的更快沟通。

第三方在需要后续尽职调查工作时也获得了益处。在 `Ongoing` 评估期间，如果供应商坚持使用该模式，那么每年在安全供应商门户上重新验证的活动就是一个已知且简单的流程。益处包括提高透明度、加快尽职调查流程完成速度以及可重复扩展的解决方案，但团队仍然担心高风险供应商及其云部署带来的风险水平，该工作并未完全涵盖。在这种更高安全风险水平下，需要对云安全控制进行更实时、物理的验证。

## 用于实时监控的 CSP API
顶级 `CSPs` 通过 `API` 提供以编程方式近实时监控客户实例健康状况的方法。最初，这些工具旨在允许直接客户（而非为另一客户提供服务）将其内部监控软件连接到 `CSP` 中的数据。供应商可以利用这些 `APIs` 为客户提供对所使用特定实例健康状况的相同视图。

### Amazon Web Services
`Amazon` 的 `API Gateway` 使开发人员能够在 `AWS` 上创建和部署表示性状态转移（或 `REST`，说起来和输入都更容易）以及 `WebSocket` `APIs`。从这些 `APIs` 中，开发人员可以创建多个自动监控警报，这些警报可以自动采取行动或需要人工干预。鉴于客户 KC Enterprises 并非 `AWS` 的直接客户，除非另有约定并在必要时进行合同变更，否则警报将需要人工干预。

`Amazon CloudWatch Alarms`、`Logs` 和 `Events` 均可通过此 `API` 访问。这些可以监控实例上的几乎所有内容，因此需要缩小范围至最关键的安全控制。`MFA` 用于根访问是首要警报，以及任何加密状态更改警报。其目的不是以执行网络运营威胁狩猎的级别监控日志，而是让少数关键项目通知 KC 网络团队需要进行调查。

### Microsoft Azure
Microsoft `Azure Defender`（本书撰写期间该名称已更改，随着供应商随时间更改产品名称而发生）允许持续导出数据。`Azure` 允许从 `Security Center` 直接导出，使用 `REST API` 或使用 `Azure Policy`。最后一种 `Azure Policy` 旨在导出大量日志数据，并不适合大多数使用场景。`Azure` 的自动导出允许选择将发送警报的数据类型；再次强调，这些用例的范围是关键安全控制警报：特权账户的 `MFA`、加密状态更改以及任何数据库的漏洞评估。
