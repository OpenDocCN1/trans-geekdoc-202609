
Automated software tools can fulfill much of this activity and automagically store that information (e.g., code, version, location, etc.) so it is searchable and can create alerts. Some of the more sophisticated applications will even alert when there is a new vulnerability about the code it knows is in your application(s). This can be done manually, with a spreadsheet and updates done by developers as they code. Obviously, this method has its shortcomings and challenges, but if a firm can't afford the automated software packages, it is a perfectly acceptable solution.

The goal is to track and identify open source code in an application. In a large application, this can mean you have a lot of OSS to track. Using an automated software package enables the due diligence effort as a vendor to be much simpler. Confirm it is being used per process by requesting to see evidence that OSS has been flagged as having a vulnerability, then assigned an owner, and being updated or patched to close the risk. Physical validation on the manual process is as challenging as the manual process itself. You should view the log or tracking artifact that the development team is using for your application, then pick a sample or two (or more, depending on risk) from the tracking log to see how the vendor locates the code.

If any gaps are observed, this exercise with a manual OSS‐tracking method should involve some discussions with the vendor. If the application is a higher risk to your company (e.g., it's systemically critical or it traverses business operations that move funds) and the revenue they receive from it is sufficient, it is reasonable that the lack of automated OSS tools is declared a security gap. Check out the example of Heartbleed in the following section. The damage that was done stemmed largely from the Herculean effort to find and fix the vulnerable OpenSSL code.

## 软件成分分析

软件成分分析（SCA）是测试开源软件的另一种方法。当您使用这些工具进行自己的测试时，它将通过识别已知存在漏洞的开源软件来识别部分开源软件。这种测试可以与供应商使用 OSS 进行的尽职调查相结合，特别是对于高风险供应商，更好地了解他们在此领域遵守最佳实践的情况。

### 内部观察：Heartbleed

2014 年 4 月，Heartbleed 漏洞突然袭击了互联网。Heartbleed 是 CVE-2014-0160 的名称，该漏洞是 OpenSSL 中的一个利用，允许攻击者查看加密密钥、登录凭据和其他私人数据。OpenSSL 是 Apache 和 Nginx Web 服务器上最广泛使用的安全（据称）传输协议之一。

据估计，在宣布时，Alexa Top 100 万个启用 HTTPS 的网站中有多达 55% 容易受到该漏洞的影响。此软件安全缺陷影响了比特币客户端和交易所、Android 设备、电子邮件服务器、像 Cisco 和 Barracuda 这样的大牌厂商的防火墙以及数百万个网站。这个漏洞是如何被发现的？由 Google 和 Codenomicon 的安全工程师通过扫描和测试 OpenSSL 发现的。

测试显示 Heartbleed 漏洞能够窃取加密密钥、用户名、密码、即时消息、文档以及任何通过本应加密的媒介传输的数据。最糟糕的是，这个被利用的漏洞不会留下任何数据泄露的痕迹。将永远无法通过取证手段确定数据是否、何时以及去了哪里。有一些未具名的政府消息来源称，NSA 在漏洞出现附近的时间就知道了该漏洞，但将其保密以便利用，然而 NSA 已公开否认这一说法。

有几起 Heartbleed 利用的实例被报道。[Mumsent.com](http://mumsent.com)，一个英国育儿网站，其用户账户被劫持，其首席执行官被冒名顶替。加拿大税务局披露了 900 名公民的社保号码被盗。加拿大皇家骑警指控一名加拿大公民，该公民是一名计算机科学学生，犯有此罪。当时美国第二大营利性医院连锁机构 Community Health Systems 于 2014 年 8 月披露，Heartbleed 漏洞被攻击者用于窃取加密密钥。该医疗提供者未及时更新补丁，导致其 450 万患者和员工的个人健康信息（PHI）记录暴露。

该漏洞由 Google 安全团队于 2014 年 4 月 1 日发现。（是的，讽刺的是，在许多国家这被称为愚人节。）易受攻击的 OpenSSL 版本于 2012 年 3 月中旬随版本 1.0.1 发布。在接下来的两年中，任何后续版本都包含该漏洞。回顾起来，Apache Web 服务器（互联网上最广泛使用的服务器之一）在两年内使用 OpenSSL 且未进行任何测试似乎令人惊讶。

发布时以及客户方面的这种缺乏测试的后果导致了全球范围内的巨大努力。Cisco 在其产品中大量依赖此代码，不得不投入大量资源来查找和更新它，然后发布补丁。事实上，Cisco 决定自行制作一个 OpenSSL 版本，以确保其不会因安全补丁而过时。其他受影响系统的列表将占据本书的篇幅。Oracle、Juniper、HP、VMWare、Android、AirPort、Western Digital、Red Hat 以及许多其他知名公司和产品只是受影响的少数几个。

## 移动软件

移动软件被定义为在 *低计算设备* 上运行的任何应用程序，这是指平板电脑或智能手机等设备。高计算设备是指计算机。两者之间的计算能力差异正在缩小，但仍然存在。虽然新型平板电脑和智能手机具有强大的计算能力，但它们的使用和管理方式与典型的企业发放设备（如笔记本电脑或台式机）不同。如果使用第三方移动应用程序，请确保数据存储和备份得到适当保护（即加密）。

有一些移动应用程序中的关键易受攻击区域需要了解，以便理解测试及其验证目的。首先是移动设备上的数据问题。对敏感数据的保护，无论是凭据还是个人身份信息，往往没有得到很好的实施。如果软件使用操作系统的 API 通过与其它应用程序的不安全通信泄露数据，则数据泄露是一个问题。许多用户没有设置手机在进行一定次数的未授权解锁尝试后将其擦除，使其成为信息的宝库。此外，手机制造商的 Android 版本数量使得加密和安全通信的处理方式非常分散。较旧的 Android 版本安全性较低，但许多开发人员希望确保广泛采用，因此这带来了独特的风险。坚固的加密算法、密钥存储以及确保应用程序使用操作系统中的最新安全功能是关键控制措施。此外，如果开发中使用或允许较早版本的传输层安全协议（TLS，用于加密流量），例如，安全通信的方法就是一个薄弱环节。

移动设备上的身份验证方法通常安全性较低。它们具有长期会话令牌以使用户更方便。此外，登录的身份验证门槛可能非常低。四位数字 PIN 码无法阻止决心坚定的黑客入侵丢失或被盗的手机。黑客将登录设备上的移动应用程序，这使黑客能够以如此低的设备进入门槛访问后端敏感数据。这是移动开发中经常被忽视的已知利用区域。
