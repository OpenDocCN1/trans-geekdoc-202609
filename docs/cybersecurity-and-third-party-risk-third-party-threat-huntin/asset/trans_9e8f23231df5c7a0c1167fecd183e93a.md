
Juniper 从未解释过为何在其加密算法中使用 Dual_EC，尽管对其安全弱点已有警告。Juniper 坚持认为 Dual_EC 的任何弱点都可由名为 ANSI X9.31 的第二个随机数生成器所抵消。他们的断言是这将 *抵消* 第一款产品中的任何安全漏洞。不幸的是，这被证明是错误的，而他们是否以及如何测试该断言从未得到解答。一旦 Dual_EC 的漏洞被利用，第二个产品就无关紧要了——何时添加哪个产品的时间点进一步引发了怀疑。Dual_EC 是在 ANSI X9.31 已成为 Juniper 产品中的成熟产品之后才添加的。问题仍然存在：为何要在产品中添加已知存在漏洞的代码？

其他研究表明，Juniper 修改了 Dual_EC 实现的设置，进一步降低了本已存在缺陷的产品的安全性。后门被揭露一个月后，Juniper 发布了一个补丁，该补丁仅专注于消除放置在其中的用于利用 Dual_EC 后门的未经授权代码。然而，它并未发布移除该有缺陷算法本身或允许攻击者绕过第二个随机数生成器、仅从 Dual_EC 获取数据的漏洞的代码，直到次年为止。

这个问题并未对 Juniper 而消失。2020 年 6 月，三名美国参议员和 13 名众议院议员致信 Juniper，要求其披露其内部调查发现了什么，因为存在“秘密政府后门”的指控。这是故意放置还是极端巧合尚未得到证实，但对于在此期间使用 Juniper Networks 的任何公司而言，这对其网络设备的安全感产生了非常令人不安的影响。

## 本地部署软件

*本地部署软件*（也称为本地软件）是任何在您网络内部运行的代码或应用程序。如前所述，在任何中大型企业中，此类软件的候选者可能多达数千个。组织应测试哪些软件取决于规模、市场、行业以及数十个其他因素。在制造业中，它可能是运行工厂的软件；在金融业中，是转移资金的应用程序；在软件行业中，他们可以选择处理其代码的任何东西。一旦确定了这些标准，就有方法可以自行测试此第三方软件的风险和漏洞。

首先，您应检查软件所需的服务账户或特权访问。最小权限原则同样适用于应用程序，即应用程序仅拥有运行所需的最少权限。没有服务应需要完全的管理员或 root 权限。如果应用程序执行其功能需要对数据库的读写访问，但不删除任何数据，则应仅具有读写访问权限。此外，还应检查供应商愿意分享的任何高层设计，以便检查信息流是否存在任何薄弱环节。

应用程序安全测试（AST）工具有很多，可以提供有关供应商软件中漏洞和弱点的有价值信息。有多种 AST 工具，每种工具都有各自的最佳发现隐藏缺陷的方法。对于无法访问源代码的软件（例如第三方软件）的测试，动态应用程序安全测试（DAST）最有效，但使用软件组成分析（SCA）工具将提供有关应用程序中发现的其他第三方和开源代码的线索。通常，SCA 工具会与 DAST 工具一起运行，但如果两者预算不足，SCA 可能被视为更有帮助，因为它提供了已被广泛知晓的漏洞列表。

在 DAST 中，工具将软件视为黑盒（内部情况一无所知）。这些测试工具检测会导致软件在运行状态下变得脆弱的条件。DAST 在操作系统级别运行，并发现软件在各种功能（例如身份验证、脚本、API 调用、对 CPU 和内存的请求等）上的行为问题。这些工具在寻找响应中的缺陷时，会在软件中使用无效和意外的值。

SCA 检查所有组件和系统库以查找其来源。这些工具擅长查找常见组件的已知漏洞，尤其是在开源软件中，但它们不会发现供应商制作的客户代码中的漏洞。然而，SCA 工具无法发现此自定义代码并不削弱该工具的实用性。如果 SCA 工具与 DAST 工具一起运行，它应能为您提供第三方软件安全漏洞的非常完整的图景。

一旦由您的团队完成测试，就必须与供应商讨论结果和下一步措施。首先关注任何高风险或严重风险，通过提供使用工具收集的数据给供应商。他们可能知道也可能不知道某个问题，需要一些讨论才能达成结论。（这可能需要不止一次的电子邮件请求。）如果供应商对反馈持开放态度，请询问他们是否已有类似发现以及其补丁计划是什么。如果他们坚持认为这是误报（即这不是真正的问题，而是测试中的错误），一个选择是要求其开发团队对相关代码进行走查。与这些供应商保持积极的关系将证明是有益的，并允许对这一可能敏感的主题保持透明。

测试本地部署软件并非没有挑战，但对于高风险应用程序和代码而言，其回报可能非常值得付出努力。有大量例子表明，未经测试的第三方软件导致了泄露（或在 Juniper 的情况下是疑似泄露，因为从未有人展示过因后门导致的信息泄露）。现场测试应基于风险，并针对对运营和安全构成风险的供应商软件。

## 云软件

云软件通常作为软件即服务（SaaS）提供，由于部署速度快且需要最少的内部支持，往往是首选解决方案。SaaS 客户往往不知道的是，如果操作得当，他们能够使用静态和动态分析自行进行测试。这需要与使用本地部署软件和与供应商合作不同的方法。如果使用云软件是贵公司的要求，最好将此需求纳入任何主服务协议（MSA）或工作说明书中网络安全部分的条款和条件。

测试云软件的第一步是与供应商合作设置测试或沙箱区域（不含生产数据）。沙箱类似于测试区域，可进行测试和快速重新配置。请确保使用匿名化数据，这些数据无法逆向工程为个人身份信息（PII）。供应商应能够提供沙箱，并在需要时与测试合作。他们甚至可以提供一套用于测试的干净数据。云软件的测试必须与第三方合作进行，但供应商应已建立部署到云中的流程。

云应用程序静态分析的三个关注领域是：应用程序编程接口（APIs）、签名和字符串。API 的使用极其普遍，对于实现与其他软件的互操作性和通信非常重要。对 API 运行静态分析可执行输入验证。检查以验证 API 是否拒绝 null 或不可接受数据的输入值，以及确保 API 的输出为预期值。
