
REST API 方法是首选方法，因为它是两个团队——供应商和客户之间的通用语言。Azure 中的安全警报和建议存储在日志中的 `SecurityAlert` 和 `SecurityRecommendations` 表中。此外，如果团队想要对 KC Azure 基线进行比较，以查看生产日志中实际存在的内容，还提供了一个 `SecurityBaseline` 表。

这种能够查看设置是否被更改甚至采取行动的能力，使供应商的云安全达到了 KC Enterprises 最终希望看到的、任何使用 CSP 的供应商的状态。实现 100‐percent 的采用并非目标，而是一种愿景。KC 的决定由风险团队做出，首先关注关键供应商，以寻找愿意合作的合作伙伴。第三方必须有参与的激励，而团队知道这会被许多供应商视为有点令人担忧。

最初向首个供应商提出的方案是，如果他们参与，则对云安全控制的尽职调查工作将减少。这需要进行一些高层讨论，以具体确定尽职调查将减少多少，同时也为供应商提供更多关于将触发警报的安全事件的清晰度。在 KC Enterprises，团队在与每个供应商单独合作，找到最有效的激励措施后，成功让几乎所有关键供应商加入该计划。

所有 CSP API，如同任何 API 一样，可以指向内部的任何数据源，团队将其用于报告和预测建模。API 轮询的每个安全控制都反馈到数据库和商业智能报告中，以提供统一的审查。该数据也被纳入团队的任何紧急呼叫系统：由于这些是关键供应商，任何受监控的安全控制（MFA and Encryption）都严重到足以需要立即采取行动。

## 内部观察：Capital One 泄露事件

2019 年 7 月 29 日，一名前亚马逊云员工因涉嫌从 AWS 客户 Capital One（又称 CapOne）窃取超过 100 million applications for credit 而被逮捕。CapOne had swung hard to the cloud in recent years，transferring much of its technology workload to AWS。泄露事件是通过 CapOne 在 AWS 上托管时使用的配置错误的 Web Application Firewall（WAF）完成的。该 WAF 设计用于在 Apache Web Server 上运行，以抵御已知类别的漏洞。

被利用的漏洞类别称为 Server Side Request Forgery（SSRF），即系统被诱骗运行本不应能够运行的命令和服务。SSRF 攻击难以检测，且检测规则并非 WAF 默认配置的一部分。这不是一种常见的攻击，因为要做到这一点需要对 AWS 和技术栈有相当多的内部知识。

AWS 对泄露原因持不同看法，将大部分责任归咎于 CapOne 对 WAF 的错误配置。这可以追溯到 Shared Responsibility 模型，以及 CapOne 对安全的责任范围以及有多少责任落在 AWS 上。公众将其称为 CapOne 泄露事件，但对企业社区网络安全和云团队而言，它指出了 Shared Responsibility 模型中的一些缺陷。AWS 提供了一些额外的安全功能，本可以降低风险，但如果他们在防止 rogue employee 方面做得更好，事件可能就不太可能发生。通过定期或自动审查云配置作为确保持续云治理流程的一部分，也可能避免这种情况。

## 结论

虽然云尽职调查是整体网络安全流程的一部分，但由于 Shared Responsibility 模型相关的风险，建立更广泛、更深入的云安全计划是必要的。借鉴网络安全领域的另一学科，Security Architecture，使用模式可以为进入或使用云的供应商提供可重复且清晰的指导。此外，执行此任务有多种方式：Cloud security reports、frameworks、certifications、baselines 和 benchmarks 都是在内部和外部提供云安全控制要求指导的机会。

CSA's CCM 是评估供应商云安全控制的优秀工具，并且映射到大多数框架。它提供多种语言版本，并针对监管映射进行了本地化。

## 网络安全与法律保护

网络安全第三方风险并不局限于尽职调查工作和安全评估。作为一家公司降低网络安全风险的关键组成部分之一，是使用解决该风险的合同语言。这并不是说网络安全专业人员还需要成为其所在公司的律师；相反，网络安全团队必须向法务团队明确说明在合同签署和执行之前供应商需要满足哪些安全控制。网络安全始于为第三方定义安全标准——即网络安全语言适用的标准。然后，通过定义网络安全在法律条款和条件中适用的标准来进一步细化这些定义；必须明确定义流程如何完成，以及当存在对组织构成风险的任何项目时进行 Risk Acceptance（RA）的流程定义。

### 法律条款与保护

从 Security Standard 或 Policy 开始，网络安全团队明确规定供应商必须满足的内容。虽然围绕此的行动已在前几章中介绍过，本章讨论的是涵盖 access management、encryption、vulnerability management、patching cadence、right to perform audits/assessments、privacy、data center security 等领域的法律条款和保护措施。随着标准的制定，它们会与合同中应包含的 terms and conditions（T&Cs）相链接，前提是存在要求它们的标准。

这些标准与网络安全要求供应商进行尽职调查的触发条件相同：供应商拥有敏感数据或与贵公司网络的连接。标准可以基于风险，意味着控制的数量和授予 RAs 的能力取决于供应商带来的风险。例如，如果供应商被视为低风险，贵公司可以采用“thin” T&Cs 的方法，仅关注关键控制，如 encryption、right to audit、access management 和 breach notifications。高风险供应商则需要提供完整的安全控制 T&Cs 文件，且几乎没有或没有 Risk Acceptance 的途径。
