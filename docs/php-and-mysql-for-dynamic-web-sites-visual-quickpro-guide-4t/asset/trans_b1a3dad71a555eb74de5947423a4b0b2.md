

此语法已在前文解释过。查询已定义，使用占位符代表稍后将赋值的值。然后 `mysqli_prepare()` 函数将其发送给 MySQL，并将结果赋值给 `$stmt`。

该查询本身首次用于 [第 6 章](#ch06.html#ch06)。它填充 `messages` 表中的六个字段。`date_entered` 列的值将是 `NOW()` 函数的结果，而非绑定值。

**4.** 绑定相应的变量并创建要插入的值列表：

```
mysqli_stmt_bind_param($stmt, 'iiiss', $forum_id, $parent_id, $user_id, $subject, $body);

$forum_id = (int)$_POST['forum_id'];

$parent_id = (int)$_POST['parent_id'];

$user_id = 3;

$subject = strip_tags($_POST['subject']);

$body = strip_tags($_POST['body']);
```

第一行表明预处理语句中将使用三个整数和两个字符串。这些值将在后续的变量中找到。

对于这些变量，subject 和 body 的值直接来自表单 ![Image](graphics/circle-b.jpg)，并通过 `strip_tags()` 处理以移除任何潜在的危险代码。论坛 ID 和父 ID（指示该消息是否为对现有消息的回复）也来自表单。它们将被转型为整数（为增加安全性，转型后应确认它们为正数，或可使用 Filter 扩展）。

**5.** 执行查询：

```
mysqli_stmt_execute($stmt);
```

最后，执行预处理语句。

**6.** 输出执行结果并结束循环：

```
if (mysqli_stmt_affected_rows($stmt) == 1) {

  echo '<p>您的消息已发布。</p>';

} else {

  echo '<p style="font-weight: bold; color: #C00">您的消息无法发布。</p>';

  echo '<p>' . mysqli_stmt_error($stmt) . '</p>';

}
```

可使用 `mysqli_stmt_affected_rows()` 函数确认记录是否成功插入，其工作原理正如您所料（返回受影响的行数）。若成功，则打印一条简单消息 ![Image](graphics/circle-c.jpg)。若发生问题，`mysqli_stmt_error()` 函数将返回具体的 MySQL 错误消息。这仅用于您的调试目的，不应用于正式站点。话虽如此，PHP 的错误消息往往比 `mysqli_stmt_error()` 返回的更有用 ![Image](graphics/circle-d.jpg)。

**7.** 关闭语句和数据库连接：

```

```

第一个函数关闭预处理语句，释放资源。此时，`$stmt` 不再有值。第二个函数关闭数据库连接。

**更多安全建议**

本章介绍了许多提升 Web 安全性的具体技术。以下是其他几条建议：

*   尽最大努力限制向用户请求的信息以及网站存储的信息。网站以任何方式处理的信息越少，意味着需要担心被窃取的数据就越少。
*   将学习、遵循并遵守安全建议作为您的职责。不要仅依赖某一章、某本书或某位作者的建议。
*   不要保留用户提供的上传文件名。您将在 [第 19 章](#ch19.html#ch19) “[示例—电子商务](#ch19.html#ch19)” 中看到一种替代方案。
*   注意数据库引用的使用方式。例如，如果一个人的用户 ID 是其在数据库中的主键并存储在 Cookie 中（如 [第 12 章](#ch12.html#ch12) 所示），恶意用户只需修改该 Cookie 值即可访问另一个用户的账户。
*   不要显示详细的错误消息（这一点在 [第 8 章](#ch08.html#ch08) “[错误处理与调试](#ch08.html#ch08)” 中已重复强调）。
*   使用加密技术（[第 7 章](#ch07.html#ch07) “[高级 SQL 与 MySQL](#ch07.html#ch07)” 中讨论了针对数据库的加密，我的著作 *PHP 5 Advanced: Visual QuickPro Guide* (Peachpit Press, 2007) 中讨论了针对服务器的加密）。
*   不要存储信用卡号、社会安全号、银行信息等。唯一的例外是您有足够雄厚的资金支付最好的安全防护，并承担当这些数据从您的网站被窃取时（这不可避免会发生）引发的诉讼费用。
*   在适当的时候使用 SSL。安全连接是服务器能为用户提供的最佳保护之一。
*   可靠且一致地保护每一个需要保护的页面和目录。永远不要假设人们仅仅因为没有链接就找不到敏感区域。如果应限制对某页面或目录的访问，请务必确保其受到限制。

我最后的建议是认识到您自身的局限性。作为程序员，您处理脚本时往往考虑它*应该*如何被使用。这与它*实际*将如何被使用（无论是意外还是故意）是不同的。尝试破坏您的网站看看会发生什么。做坏事，做错事。也让其他人尝试破坏它（通常很容易找到这样的志愿者）。编码时，如果您假设没人会正确使用某个页面，它将比假设大家总会正确使用要安全得多。
