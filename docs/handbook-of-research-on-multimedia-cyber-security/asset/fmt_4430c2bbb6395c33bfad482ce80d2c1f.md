
# 容器编排框架

我们考虑一个部署在虚拟化公有云环境中的容器编排框架，由组织或平台即服务提供商部署。因此，该框架可以访问无限数量的虚拟机，这些虚拟机可按需供应和取消供应。在本工作的初始阶段，我们假设虚拟机是同构的，即具有相同的价格和特征，并按计费周期收费。虚拟机的特征由其内存和 CPU 容量定义。

本工作中考虑的工作负载特征源自 Google、Alibaba 和 Fuji 等组织大规模集群的使用模型。为了高效利用资源，这些组织倾向于在共享集群上运行不同类型的容器化应用程序，而不是运行同构容器的独立集群。我们考虑的工作负载由两种持续到达的容器化任务类型组成。第一类任务是长期运行的服务，需要高可用性且必须处理延迟敏感型请求。示例包括面向用户的 Web 应用程序或 Web 服务。第二类任务是批处理作业。这些作业生命周期有限，且更能容忍性能波动。示例包括科学计算、数据分析和 MapReduce 作业。

我们假设所有任务都定义了它们所需的 CPU 和内存数量（即资源请求）。这样，任务将仅部署在至少拥有其所需资源量的节点上。此外，长期运行的服务可由用户定义为可移动的。可移动任务是指那些为了重新调度和自动扩缩容，可以容忍被关闭并在不同节点上重新启动的任务。这可能包括无状态 Web 应用程序或复制的 Web 服务。

从高层视角来看，本工作解决的问题分为三个阶段：

*   **调度**：将传入的任务放置在至少拥有该任务请求的 CPU 和内存资源量的集群资源上。
*   **重新调度**：如果存在无法调度的传入任务（即没有节点有所需的可用资源量），则重新调度器将尝试重新排列可移动的运行中任务，以便为无法调度的任务腾出空间。
*   **自动扩缩容**：此问题分为两个子问题：i) 扩容和 ii) 缩容。一方面，如果尝试重新调度后仍有无法调度的任务，自动扩缩容器应考虑扩容（供应新的虚拟机）以增加集群容量。如果存在未使用的虚拟机或集群资源利用效率低下，自动扩缩容器应考虑关闭未使用的虚拟机或合并任务，以提高集群利用率并取消供应不必要的虚拟机。

本工作的总体目标是强调并说明容器编排需要整体资源管理方法的必要性；即一种同时考虑调度、重新调度和自动扩缩容的方法。所提出的框架集成了这三个过程，并允许不同的策略无缝插入。

## Kubernetes

Kubernetes 是一个旨在管理集群上容器化工作负载的框架。Kubernetes 中的基本构建块是 `pod`。一个 `pod` 封装一个或多个紧密耦合的容器，这些容器被放置在同一位置并共享同一组资源。`pod` 还封装存储资源、一个网络 IP 以及一组选项，这些选项控制 `pod` 的容器应如何运行。一个 `pod` 旨在运行应用程序的单个实例；通过这种方式，可以使用多个 `pod` 来水平扩展应用程序。创建 `pod` 时可以指定容器所需的 CPU、内存和临时存储量。然后调度程序可以使用此信息来决定 `pod` 的放置。这些计算资源既可以指定为请求量，也可以指定为容器允许消耗的量的限制。

默认的 Kubernetes 调度程序确保放置在节点上的所有 `pod` 的计算资源请求总量不超过节点的容量。即使实际资源消耗非常低，也是如此。这样做的原因是为了保护应用程序，防止当资源使用稍后增加时（例如在每日高峰期间）节点上出现资源短缺。如果容器超过其内存限制，它可能会被终止，并可能稍后重新启动。如果它超过其内存请求，当节点内存耗尽时它可能会被终止。关于 CPU 使用，容器可能被允许在一段时间内超过其限制，但不会因此被终止。另一方面，超过存储限制的容器和 `pod` 将被驱逐。

其他资源（称为 `Extended Resources`）可以被指定以宣告新的节点级资源，其资源核算由调度程序管理，以确保不会同时向 `pod` 分配超过可用数量的资源。

从技术角度来看，Kubernetes 允许使用各种类型的容器运行时，`Docker` 和 `rkt` 由平台原生支持。最近，框架的容器运行时接口 (`CRI`) API 的发布使 Kubernetes 能够支持其他容器技术，如 `containerd` 和 `frakti`（一种基于虚拟机监控程序的容器运行时）。此外，`CRI-O`（`CRI` API 的一种实现）目前使 Kubernetes 能够支持任何符合 `OCI` (Open Container Initiative) 标准的容器运行时，如 `runc`。此外，`etcd`（一个开源、高可用、分布式的键值存储）支持 Kubernetes 管理集群节点和作业。具体而言，`etcd` 用于存储集群的所有数据，并充当框架所有组件的单一事实来源。

总体而言，Kubernetes 是一个高度成熟的系统；它源自 Google 十年来在 `Borg` 和 `Omega` 上的经验，并且是拥有广泛社区驱动支持和开发基础的领先容器化集群管理系统。它为用户提供了广泛的选项来管理其 `pod` 及其调度方式，甚至允许可插拔的自定义调度程序轻松集成到系统中。总之，尽管 Kubernetes 的性能和可扩展性可能仍未达到 `Borg` 等行业系统的水平，但截至 1.10 版本，Kubernetes 能够支持多达 5000 个节点的集群，这适合许多现代组织的需求。

### Algorithm 1

```
while the scheduler exit condition is not satisfied
    get all pending tasks
    for each pending task t
        schedule t
        if t cannot be placed
            reschedule
            if rescheduling failed
                scale out
        scale in
```
