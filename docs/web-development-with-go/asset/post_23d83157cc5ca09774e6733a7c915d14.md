When we call the Delete method we need to make sure any IDs provided are greater than 0. If we accidentally pass in an ID with the value 0, it willll result in the entire database being deleted which likely isn't what we want.

## 12.5. WRITING VALIDATORS AND NORMALIZERS 383

We will go ahead and jump right into the code, then explain what is happening after seeing the code.

```go
func (uv *userValidator) idGreaterThan(n uint) userValFn {
	return userValFn(func (u *User) error {
		if u.ID <= n {
			return ErrInvalidID
		}
		return nil
	})
}
```

In the code above we first start off by defining a function that accepts an unsigned integer (uint), and then returns a userValFn. Notice that this function doesn't look like our other validation functions, but instead is used to create one.

That means that inside of our code we need to return a function that matches the userValFn definition; that is, it must accept a pointer to a user and return an error.

One way to create a function like this would be to do it dynamically and assign it to a variable, just like you would with any other data. That is, we could create a user validation function like this:

```go
fn := func(user *User) error {
	// do stuff
	return nil
}
```

The fn variable would then store a function that we could call much like we would any other function.

```go
var user User
err := fn(&user)
```

In our idGreaterThan function we are doing roughly the same thing, but rather than storing the function in a variable we precede it with the return keyword, signifying that we simply want to return that data.

We also wrap our function with userValFn(...) to imply that we want to convert this function into the userValFn type. This is similar to converting a string into a byte slice, which you have probably seen before.

```go
str := "Michael Scott"
b := []byte(str)
```

But this brings up the bigger question of, “Why did we just go through all that effort? What was the point?"

By doing all of this we have the ability to create a function that only accepts a user and returns an error, but inside of that we are able to access the unsigned integer, n, that we provided to our idGreaterThan function. That means we can dynamically create a validation function that verifies IDs are greater than any value, not just 0.

For example if we wanted to create a validation that says IDs must be greater than 10, could we do so with the following code.

```go
valFn := uv.idGreaterThan(10)
var User
// This runs just like all our other validation functions,
// but it gets the minimum ID value dynamically
err := valFn(user)
```

While it is unlikely that we will want to validate specific IDs like this in our code, this validation is meant to provide an example for when you do run into cases that require more dynamic validations.

### 12.6.1 Converting emails to lowercase and trimming whitespace
