We could do this inside of our Update method, but that would bring us right back to where we started. Adding new normalization and validation code wouldn't be as easy as we want it to be.

Rather than changing the Update method, we are going to instead update the bcrypt method to only run if the password is set. Checking this is easy to do - we simply need to see if the user’s password is equal to the empty string. If it is, then the password wasn’t updated. Otherwise it was and we can hashl it.

```
func (uv *UserValidator) bcryptPassword(user *User) error {
tif user.Password == "" {
	// DO NOT need to run this if the password
	// hasn't been changed.
	return nil
}
	// The rest remains the same
}
```

Now at this point you might be wondering, “Won’t this cause us issues in the Create method?” It a valid question, but later we will see when we need to ensure things like a password set on methods like Create, it is often easier to do this in a separate validation rather than trying to jam too many validations into a single function. By splitting these up, we make each of our individual validations much easier to reuse across our application.

With the changes we just made we have laid the groundwork for quickly and easily writing validators and normalizers for our users model. No extra frameworks or third party libraries were needed at all. Instead, we were able to just define our own types and write a few utility functions to simplify the process.
