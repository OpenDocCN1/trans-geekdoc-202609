
As a general rule, yes, panicking is indeed bad. Typically you should try to handle any errors that you can, or defer them to the caller of your function so that you can handle them.

If we were following that advice now, we would update our NewView function to return two values - a pointer to a View, and an error. So why aren't we?

In this specific situation I know that we are only using the NewView function when we start up our application. That is, when our program first running it will create all of the views it needs, and then it will never call NewView again. It will instead continue to use views that were already created.

If we were to change, we would want to update our code, but since we know that our code is working this way I find it acceptable to panic when an error is encountered encountered even if we returned the error to our main function, it would need to panic immediately after receiving the error anyway because we can't start our web application without our views being initialized correctly. We wouldn't have a way to render any HTML pages.

Once we have our layoutFiles function written we can start using inside of our NewView function. Navigate to that function definition. We are going to update the first few lines where we append our layoutFiles to the files slice. Instead of passing individual files to append, we are going to pass in all of the files returned by the layoutFiles function call. The code is shown in Listing 6.29.

## 6.5.3 Simplifying view rendering

If you open up main.go and look at the home and contact functions you will see that we are calling ExecuteTemplate in both of our handler functions.

We discussed earlier how views should contain all of the logic for rendering data, but here it looks like our handler functions are taking care of this logic instead of offloading it to the view.

To fix that we are going to add a method to the View type that is responsible for rendering the view. Then moving forward we can simply call this method in our handlers without worrying about any rendering logic in our handlers. Open up view.go again and we will get started.

```bash
$ atom views/view.go
```

Add the code in Listing 6.30 to your file. This will add a Render method to the View type, which is why the (v *View) part comes before the function name.

I typically place methods like below the type declaration in my source files, but you are welcome to do whatever you see fit.

Listing 6.30: Adding the Render method.
```go
func (v *View) Render(w http.ResponseWriter, data interface{}) error {
  return v.Template.ExecuteTemplate(w, v.Layout, data)
}
```

If you don't have any auto-imports enabled, you will also need to add an import to the net/http package to your source.

Now we are ready to go back to main.go and use our new rendering method. We are going to be updating both the home and contact functions, and the resulting code is shown in Listing 6.31. I have added a helper function - must - that will simplify our error handling a bit.

### Listing 6.31: Using the Render method.

```go
func home(w http.ResponseWriter, r *http.Request) {
  w.Header().Set("Content-Type", "text/html")
  must(home.Render(w, nil))
}

  w.Header().Set("Content-Type", "text/html")
  must(contact.Render(w, nil))
}

// A helper function that panics on any error
func must(err error) {
  if err != nil {
    panic(err)
  }
}
```
