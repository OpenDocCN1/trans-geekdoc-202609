
## 11.6 Analysis Modeling

A system’s analysis model is a specialized diagram of the system. It connects two documents, the description of the system and the design model. After the system’s data, actions, and features have been described in Analysis Modeling, they may be converted into the system’s architecture, components, and interfaces in Design Modeling.

### 11.6.1 Behavioral Modeling

A system’s behavior may be influenced by a number of different elements, all of which can be better understood with the use of a Behavioral Model. Figure 11.3 presents a use case diagram that represents the interactions between users and the system with its key functionalities.

- **Use Case Diagram:** A use case is a set of steps in which the user interacts with a system and in which other parties may be involved.

- **Sequence Diagram:** Sequence diagrams are interaction diagrams that display the interdependencies and dependencies between processes, as well as the sequence in which they occur. Message Sequence Charts make up this structure. A sequence diagram is a graphical representation of the temporal progression of an event or series of events involving a set of objects. We can see the classes and objects that will be used, as well as the messages that will be sent back and forth between them as the scenario unfolds. In the Logical View of the system being developed, sequence diagrams are often linked to implementations of use cases. Sometimes referred to as “event diagrams” or “event scenarios,” sequence diagrams have several names. Different processes or objects that exist concurrently are represented by parallel vertical lines (lifelines) in a sequence diagram, and the messages sent between them are represented by horizontal arrows in the correct order. ## 11.7 Software Testing

Testing is a crucial process that involves examining and evaluating the performance and functionality of a product or system. It is applied in various fields, including human knowledge and skills, as computer hardware and software development. In software development, testing is a critical step used to determine whether a project meets its objectives. Software testing can be conducted at any stage of the development process depending on the testing methods employed. The primary goal of software testing is to validate and verify that the software program or application conforms to the required standards and specifications. As a result, software testing is essential for ensuring that the final product is both trustworthy and suitable for its intended purpose.

### 11.7.1 Types of Testing

The quality of software programs may be tested in a number of ways, including white box testing, black box testing, and gray box testing. These testing methods involve different levels of access to the underlying code and architecture of the software being tested. The following is an explanation of each testing method along with some examples:

- White box testing: In software testing, “white box” refers to the practice of disassembling a program to see how it is put together from the inside. In this method, the tester has access to the underlying code and architecture of the software allowing them to identify any potential vulnerabilities.

- Black box testing: Black box testing is a testing method that focuses on the external behavior of a software application. In this method, the tester does not have access to the underlying code and architecture of the software, but rather tests the software from the perspective of the user or a customer.

- Gray box testing: The term “gray box testing” refers to an approach to testing that mixes white box and black box techniques. With this approach, the tester is only given partial visibility into the software’s source code and architecture, but is, nevertheless, able to get an understanding of its operation. Examples of gray box testing include API testing and database testing.

### 11.7.2 Test Cases

Specifications and requirements, or what the app should be capable of, serve as the foundation around which test cases are constructed. Typically, descriptions of the program found elsewhere, such as specifications, requirements, and design parameters, serve as the basis for creating test cases. The majority of the tests conducted are functional in nature; however, sometimes, non-functional tests are used.
