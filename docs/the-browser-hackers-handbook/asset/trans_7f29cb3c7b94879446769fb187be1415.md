
-   [浏览器沙箱化策略](https://example.org)将每个网站开启独立进程，使恶意网站难以进一步影响其他已打开的网站，或对操作系统本身造成影响。这种沙箱化同样适用于插件和扩展，例如独立处理 PDF 渲染。

沙箱规避漏洞通常属于编译代码类型，试图完全劫持正在运行进程的功能。此时沙箱的有效性会被检验：它能否阻止劫持的执行路径获得完整的进程权限？

### IFrame 沙箱化

IFrames 可用作包含来自跨域资源的潜在不受信任内容的机制，在某些情况下也可包含同源的不受信任内容。例如，网站中常用的 Facebook 社交媒体小部件就是一种流行的包含方式。12 IFrame 变为敌对的可能性并非新鲜概念，浏览器厂商长期以来已提供多种方式来减轻恶意 IFrame 的附带损害。

HTML5 规范提出了 IFrame 沙箱化的提案，现代浏览器已接受该提案。这为开发者提供了采用最小权限的方法。沙箱化的 IFrames 是通过添加 HTML5 属性来对内联框架施加额外限制的方法。

这些限制包括禁止使用表单、停止脚本执行、不允许顶级导航，并将其限制在指定的来源。这些限制从每个父框架继承，确保任何嵌套的 IFrames 在创建时自动继承相应的限制。

### 防钓鱼与防恶意软件

在线伪造实体（包括电子邮件）以窃取个人信息（如凭证）的行为传统上称为钓鱼。许多组织提供已知钓鱼网站的目录服务，现代浏览器可利用这些信息。

浏览器会将每个访问的站点与已知恶意站点列表进行比对。如果检测到请求的站点实际上是钓鱼站点，浏览器会采取行动。相关内容详见第 2 章。

同样，Web 服务器可能在未经所有者同意的情况下被感染，或专门用于托管可能通过利用已知漏洞来 compromise 浏览器的内容。这些站点也可能诱导用户手动下载并执行软件，从而绕过浏览器的防护并直接启动。

各类组织维护活跃的恶意代码托管站点黑名单，并可直接将其链接至浏览器以提供实时防护。13

### 混合内容

存在混合内容漏洞的网站使用 HTTPS 方案，但请求内容时使用 HTTP。即页面的所有组成部分均未通过 HTTPS 传输。

未通过 HTTPS 传输的数据面临被篡改的风险，可能抵消部分加密带来的优势。例如，若脚本经由未加密通道传输，攻击者可在数据流中注入指令， compromise 浏览器与 Web 应用之间的交互。

# 核心安全问题

浏览器安全控制功能不断扩展的演进凸显了更大且更根本的图景。传统网络安全依赖于部署和维护外围或边界防御措施，如防火墙。随着时间的推移，这些设备已被证明能够阻止除必需流量之外的所有流量，包括流入和流出组织的流量。

尽管网络日益紧密，企业仍需访问其信息，而 Web 技术的使用（几乎所有通过 TCP 端口 80 或 443 传输的流量）正以加速速度增长。事实上，防火墙在成功遏制流量洪水后，往往只剩下一道光亮的 HTTP 流量。例如，SSL VPN 技术的普及已超过传统的 IPSEC VPN。

可以认为，所有防火墙都仅仅将网络流量减少到两个端口：80 和 443。这将极度依赖 Web 浏览器的安全模型。

以下子节探讨围绕浏览器安全的整体图景，以及相互矛盾的力量如何创造复杂的攻击与防御游戏。我们聚焦于为何在一般情况下，Web 流量的“激光束”未能孤立网络边界，反而形成攻击可能性的棱镜。

## 攻击面

攻击面的含义可能不新鲜。攻击面是浏览器中可能受到不受信任来源影响的区域。即使在最小的情况下，即整个渲染引擎，问题的范围便已显而易见。Web 浏览器拥有庞大且不断增长的攻击面。存在大量 API 以及多种数据存储和读取的抽象层。

相反，网络整体的攻击面如今已能得到有效控制。访问点和允许的流量流是明确了解的，变更控制流程可应对变化。例如，可通过 well-known 方法轻松验证并限制防火墙上不同端口的访问。

浏览器厂商很少从软件中移除功能。更常见的是，厂商在不断添加最新的“铃声和灯光”。与大多数产品一样，很少出现因削减功能而获得明显回报的情况，同时保持向后兼容性。随着功能集的扩展，潜在的攻击面也随之增大。

现代浏览器会自动并在后台静默更新，有时在使用者不知情的情况下改变攻击面。在某些情况下这可能是好事。但对于成熟且有能力的安全团队而言，这可能带来更多挑战而非优势。

然而，对于普通 Web 浏览器，很少能在组织的安全团队中找到具有 substantial 经验来防御其的成员。尽管这是最受信任的单一软件之一，它仍可能成为 Internet 上最大的攻击面。

### 变化速率

浏览器安全团队的工作时间表往往与组织不匹配。组织往往无法自行实施想要的浏览器修复，以增强安全态势。

与安全社区偏好的相比，浏览器安全相关的错误通常由开发者给予较低优先级。例如，2013 年 1 月的 Firefox 18.0 版本发布时，Mozilla 宣称其一项修复是混合内容漏洞防止功能，即在 origin 方案为 HTTPS 时阻止加载 HTTP 内容。你可能会惊讶地发现，该错误最初在 2000 年 12 月就被报告。15 这可能是一个极端的例子，但它确实展示了可能出现的滞后。

用户对 Web 浏览器安全更新缺乏控制的情况并不与其他软件不同。而且，组织不太可能在等待关键修复期间停止使用所有浏览器。如果这一假设成立，那么大多数组织将在公开漏洞发布与厂商发布修复之间的时间窗口内面临浏览器攻击的威胁。

### 静默更新

静默的后台更新虽可能为攻击提供途径，但也为用户带来实质价值。为确保更新能迅速应用，一些开发者实现了自己的静默机制。
