
-   浏览器市场份额的格局在浏览器多彩的历史中始终没有保持稳定。有赢家和败者，有小众和主流浏览器，声誉起伏不定。Netscape 是浏览器之争的早期牺牲品，但它的没落催生了 Mozilla Organization，最终导致了 Firefox 的出现。那位老牌子、Internet Explorer 曾在浏览器市场占据主导地位，并击败了后来的 Netscape，如今正稳步被开源浏览器抢占份额，近年来也面临来自 Google Chrome 和 Apple Safari 等商业产品的竞争。然而，得益于其持续的开发以及财务巨头 Microsoft 的坚实支撑，它仍在持续生存和演进。可以说，这场战争的故事远未结束。

-   战场已变，浏览器也进化以应对新的地形。这场军备竞赛的重要成果是浏览器厂商认识到安全对用户至关重要，并持续努力使浏览器被利用变得更加困难。这促成了多项防御技术的进步。

-   下面的章节将介绍当今防御性强大的浏览器软件中一些主要的浏览器安全特性。

### HTTP Headers

-   浏览器安全演进的很大一部分发生在 HTTP 头部。由于整个请求或响应范围内的指令都放置在 HTTP 头部，它们为服务器提供了自然的机制，让浏览器在响应中加入额外的安全控制。

### Content Security Policy

-   XSS 在第 2 章中讨论过，这里简要提及以便将 Content Security Policy (CSP) 置于语境中。CSP 设计用于通过区分指令和内容来缓解 XSS 漏洞。

-   CSP HTTP 头部 `Content-Security-Policy` 或 `X-Content-Security-Policy` 由服务器发送，用于规定脚本可以加载的位置，并限制这些脚本的行为，例如是否允许使用 `eval()` JavaScript 函数。

### Secure Cookie Flag

-   传统上，Cookie 会在 HTTP 和 HTTPS 两种协议下都发送，不区分来源。这会影响通过浏览器建立的会话安全。安全通过 HTTPS 与服务器协商的会话令牌可能会通过普通的 HTTP 请求被攻击者窃取。

-   Secure Cookie 标志的作用是让浏览器永不通过不安全的通道发送 Cookie。这样，敏感的会话令牌在传输时始终被加密屏障包围。

### HttpOnly Cookie Flag

-   HttpOnly 标志是可应用于 Cookie 的另一选项，所有现代浏览器都会遵守该指令。HttpOnly 标志指示浏览器禁止任何脚本访问 Cookie 内容。这能有效防止因 XSS（第 2 章讨论）导致的 JavaScript 窃取 Cookie。

### X-Content-Type-Options

-   浏览器会使用多种内容嗅探方法猜测服务器返回内容的类型，然后根据该类型执行相应的操作。`nosniff` 指令的作用是禁用这种嗅探功能，强制浏览器严格按照响应头中的 `Content-Type` 来渲染内容。

-   例如，如果服务器在脚本标签的响应中加入 `nosniff` 指令，浏览器将忽略该响应，除非 MIME 类型匹配 `application/javascript`（以及少数其他类型）。像维基百科（允许上传文件）这样的站点，这尤为重要。

-   当缺少该指令时，恶意构造的文件上传后如果被下载，浏览器可能会错误解析 MIME 类型，例如将 JPEG 误判为脚本。这在浏览器安全控制方面存在明显风险：攻击者可能通过公共 Web 应用获得浏览器控制权。一种方式是上传看似安全的文件类型，随后在更危险、更易被利用的上下文中被解释。

### Strict-Transport-Security

-   该 HTTP 头部指示浏览器所有对网站的通信必须通过合法的 HTTPS 隧道进行。用户将无法接受 HTTPS 错误并继续使用不安全的连接；浏览器会在不允许继续浏览的情况下提示错误。

### X-Frame-Options

-   `X-Frame-Options` HTTP 头部用于防止页面在浏览器中的嵌入（iframe）。当浏览器检测到该头部时，应确保该页面不会被显示在 iframe 中。

-   该头部最初是为了防止 UI 重绑定攻击（包括 Clickjacking）。Clickjacking  attack 通过在前景窗口中将受害者页面以 100% 透明度嵌入，用户以为自己在操作透明的背景（攻击者）页面，实际上却点击了不可见的前景（受害者）页面。

-   `X-Frame-Options` 可以阻止一部分 UI 重绑定攻击的成功执行。这些攻击在第四章中有深入阐述。

## Reflected XSS Filtering

-   这是浏览器的安全特性，旨在检测、清理并阻止 Reflected XSS（第 2 章）。浏览器会被动发现成功的 Reflected XSS 利用，然后尝试对响应中传递的脚本进行清理，在大多数情况下阻止其执行。

## Sandboxing

-   Sandboxing 是一项针对真实问题的现实解决方案。其基本假设是浏览器会被入侵并受到攻击者控制——这话太真实了！开发者必然会编写有漏洞的代码。

-   许多人认为漏洞代码必然会在软件产品的某处出现。事实上，即便是安全界的批评者也难免存在漏洞。Sandbox 是应对这一普遍问题的一个良好尝试。

-   开发者是否遵循“写出易受漏洞影响代码”这一前提（即写出有漏洞的代码）取决于诸多复杂因素，如缺乏睡眠或咖啡因质量。Sandbox 仅是一种缓解措施，它试图在浏览器被入侵的高概率区域建立保护屏障。它让安全团队能够将精力集中在更小的攻击面上，从而在资源投入上实现良好的风险回报平衡。

-   Sandboxing 并非新鲜概念；它在计算的其他领域也有变体。例如，Sun 在 Trusted Solaris 中使用了隔离（compartmentalization），FreeBSD 使用 Jails。这些技术根据进程权限限制资源访问。

### Browser Sandboxing

-   Sandbox 可以在多个层级应用。例如，可以在内核层面将不同用户隔离，或在硬件层面实现内核与用户空间的特权分离。

-   浏览器沙箱是用户空间程序能达到的最高级沙箱，它是操作系统给予浏览器的特权与浏览器内部子进程特权之间的屏障。

-   要完全 compromising 浏览器，至少需要两步：第一步是找到浏览器功能中的漏洞；第二步是突破沙箱（即 sandbox bypass）。
