Inheriting vast wealth is not always good.

I've removed most of the methods that were previously defined just so that we can focus on the relevant parts. Our User model here isn't extending anything at present. Instead, it's consuming UserDataTransport instance that it has access to the different pieces of data that concerns itself with. The rub: what if that UserDataTransport class was how we extended the base model class provided by the framework?

```
class UserDataTransport extends FrameworkXYZ_Base_Model
{
  ..
}
```

It may not be an ideal solution because we are still having to accomod the reuse-by-extension idea that the framework imposes upon us, but by turning our derived so called model class into this notional UserDataTransport class, what we've actually achieved is a very nice layer of separation between our models and the framework's arguably kludged model proposal. In this turn allows us to maintain the purity of our models and keep them focussed on their primary purpose.

# Summary

Whilst this chapter on Inheritance isn't quite as wordy as the Abstraction chapter that precedes it, I hope that I've managed to convey the key concepts in a way that is, at the very least, comprehensible. If you accept that abstraction we are developers able to extend the range of data types that is natively available in our language of choice, hopefully you will also be to accept that the child classes that we derive from those abstract parents must remain compatible with the specification of the data type that the abstract parent provides.

Perhaps an easier way of thinking in these terms is to consider how other objects, the so-called client code, within our application needs to interact with particular variable instances of these new data types. If a renderer is expecting a string, or array, or a particular class of object as the return value from a method call, then it really shouldn't matter which particular class instance the renderer is dealing with.
