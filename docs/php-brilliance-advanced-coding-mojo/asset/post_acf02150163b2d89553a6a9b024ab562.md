
The only places where things of this sort should be happening inside factories, abstract or otherwise, and where the object returned conforms to a clear and well understood interface. If it happens out in the wilds, the code that forms the application's normal process flow, then you're, well, bugged to put it bluntly. The game over has knelt, it's time to start prompting the rewrite.

Instead of trying to wiggle out of it, let's say we're not going to do it. The concepts of loose coupling and dependency injection will be discussed at length later in this book. So too will the idea of developing an allergy to using the new keyword. For now though, I'd just like you to take it as read that instantiating validator instances inside our User class is a strictly-no scenario. I say take it as read, if this is already a second or more reading of this book, you'll already know why this should be so.

So how do we get the validator into the User class then? One answer, certainly, to pass it in the constructor as well. Our next refactor does exactly this.

```php
public function __construct(
    array $userData,
    UserDataValidator $udv
) {
    if (!$this->isValid($userData)) {
        throw new Exception(
            $udv->getErrorMessage(),
            $udv->getErrorCode()
        );
    }
    $this->userData = $userData;
}
```

Look at what we've done there! The suggestion here is that all of the validation logic for the $UserData array is tucked away nicely in the UserValidator object. As long as we can have faith in this validator and its operation, we initialise our User object with validated data in a very succinct fashion. Furthermore, any future changes to the structure of the $UserData (Y'know, the biz team wants 'favourite colour' recording. Next week, it'll be 'Shoe size') will result in zero changes to our User class as it stands, which can only be a good thing, right?

Still, we can take this one step further. We can combine the $UserData array and the UserValidator into a single object. Let's call it a UserDataTransport object and the code up the changes like:

```php
class User
{
  /**
   * @var UserDataTransport
   */
  private $userData;

  public function __construct(UserDataTransport $udt)
  {
    $this->userData = $udt;
  }
}
```

Finally, we've arrived at a very short and sweet User class which correctly holds its validated user attributes in a private property but in such a way as not clutter up the User class itself with validation routines that we might very well need elsewhere too. From the perspective of our User class, it's now initialised correctly with valid data since we are also trusting the $udt instance to have done its correctly prior to being passed in.

Some of you might be thinking at this point that all we've achieved here is to move the methods that should be in the User class into something else, and then proceeded to put a rather useless shell, called User, on top of that. If this was the end of our journey then it would be quite right.

It isn't the end of the journey though. Whilst we are indeed approaching the final straight, we have gotten to the point where we should take a pause, make a nice cup of tea and cogitate a bit.

# Encapsulating our ideas.

If you look at what we've done here, you can think of $udt instance as a seed, a kernel, a unit that simply represents the data that we want to persist to whatever storage systems we need to implement in our application. This is a very interesting point that we've arrived at. Our persistable data is now **encapsulated** in a discrete unit that is separate from and consumed by our model class.

This is a key design goal that we want to achieve when building out a large scale application. We want our model classes to concentrate on behaving like the model classes that they are supposed to be. Taking the approach of injecting something like a data transport object into a model class allows us to divorce the model layer from the implementation details of how we handle data persistence.

If you're remotely familiar with one or more of the PHP application frameworks that are out there, you will probably be aware of the many and varied approaches that they take to implementing persistence when it comes to the model layer. In some cases you are expected to implement application models by extending a framework provided base model. In others, you are expected to mingle the design of your model classes in order to expose the properties that they manage to decorators and adapters. In either case, you're required to adapt your model design to their persistence mechanism and in doing so, you're expected to eschew at least one sound design principle or another. To my mind, this not only sucks but it also blows.

By injecting the requisite kernel of data into your model classes, you free yourself from such principle-busting constraints. Your models can properly encapsulate the business logic that they were intended to and the vagaries of storage solutions are immediately and correctly relegated out of the model layer and into a persistence layer where they truly belong.

```php
class User {
    /**
     * @var UserDataTransport
     */
    private $userData;

    public function __construct(UserDataTransport $udt) {
        $this->userData = $udt;
    }

    private function getDataTransport() {
        return $this->userData;
    }

    public function getUsername() {
        return $this->userData->getUsername();
    }

    public function getEmail() {
        return $this->userData->getEmail();
    }

    public function setEmail($email) {
        try {
            $this->userData->setEmail($email);
            return $this;
        } catch (DataTransportException $e) {
            $msg = $e->getMessage();
            $code = $e->getCode();
            throw new ModelException($msg, $code);
        }
    }
}
```

There are a few things to note here. Firstly, since we don't currently have a use case for getting the data back out, I've set the access modifier of the getDataTransport() method private to serve the getters that form our public interface. Additionally, I've only one setter method here, being the one for the email property. Unless your application supports a user being able to change their username, the chances are good that a setter for the username property would be superfluous.

Even so, with the email setter I'm still not providing any validation within the setter itself. There is a very strong case for this. If we are confident enough that the data transport object provides everything needed to ensure that the data is valid and correct, confident enough to allow it to represent our entity's data at the point of instantiation, we should also have enough confidence in its integrity to delegate the validation responsibility to it when setting individual properties.

Ok, put the champagne on ice. We are almost there! Our User class is filling nicely now with the provision of the three public methods that represent the object's interface. We could certainly go on add further getters and setters as our application requires but I shall leave that for you to experiment rather than taking any further space here. To do so would only serve to labour the point.

Up until this point, I've largely concentrated on the objects that know things. This is primarily because it's such a critical area of concern. I've been keen to stress that we shouldn't allow our knowers to get bogged down with large quantities of bloated methods, the reasons for which, I hope, abundantly clear. This does lead us to building some rather anaemia data classes though. Nevertheless (rather than anaemic) data classes are exactly what we need if we are to weather the storms that change requests bring.
