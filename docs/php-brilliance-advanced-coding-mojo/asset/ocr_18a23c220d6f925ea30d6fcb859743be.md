# Object Oriented Thinking

What happens when Joe starts reading about object oriented development? He's introduced to a Car class that not only has properties for things like the wheels and the engine, but also methods (functions!) for the car needs to do things like move(), turn() and stop().

Joe thinks it'd be a great idea to wrap his carefully crafted library of functions in class statements. This is now the point where Joe could take one of two paths. Does he instantiate a Database object in order to use those transplanted library methods? Or he add the static keyword to the function declarations that he can call the class methods statically?

Well, instantiating the object doesn't really look to be terribly useful. Let's go with the static.

Now Joe's coding regularly features things like this:

```
<?php
include("Config.php");
include("Database.php");
$conn = Database::connect($dbname, $dbuser, $dbpass);
```

Youch.

Eventually our developer will make the transition from wrapping his function libraries in class statements to identifying the nouns in his system and building objects around those. This is very much in line with the tutorials that he has followed. What we see from Joe is the predominant but natural outcome of those tutorials and their habit of finishing a topic early.

Joe's classes become enormous. The classes at the centre of the application, whether this is a User class or a Product class, are truly huge, spanning thousands of lines of code and with methods so long the start and end of them cannot be viewed onscreen at the same time. Scroll, scroll, scroll.

What's going on here?
