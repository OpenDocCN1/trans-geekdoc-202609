No great shakes here - a class that defines an object that in turn appears to hold onto report data. Evidently this object has been emitted from a request passed into the model layer and again again, we seem to have a conditional structure that determines the format that the report data will be retrieved in.

It doesn't matter whether the conditional structure is a stack of if/else clauses as we saw in the State Pattern earlier, or a switch statement as we have here. If we find ourselves selecting blocks of code to run on the basis of a conditional statement, we are almost certainly going to benefit from abstracting these code blocks out into separate objects representing injectable behaviours.

Nevertheless, our example here illustrates how the report data may be returned either as a (poorly constructed) CSV string or as the raw data array. Despite the fact that the business team have been haranging us for html tables, PDFs and JSON strings for the API.

Are we going to add three more cases to the switch statement? No, of course we are not.

Nor are we going to create a family of ReportData classes linked by an abstract parent class for precisely the reasons that we saw with the Order example in the previous section. If this object represents report data it's reasonable to assume that there was at least cost in generating the result. Therefore, there are likely significant savings to be made from caching this data, even for a short time.

Why?

The business team are asking that the data be available as HTML tables and as PDF/CSV. No matter strangely their brains seem to operate sometimes, we can at least presume that their desires include displaying that data in the browser and also providing links to downloadable files.

These output format requirements are perfect candidates for being represented as injectable behaviours, with each desired output format being represented by a single, properly encapsulated algorithm for transforming the report data appropriately.
