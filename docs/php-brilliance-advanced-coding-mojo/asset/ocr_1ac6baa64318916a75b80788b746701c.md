Talking points.

```
class Application
{
  ... // All of the codes
}
```

```
$app = new Application();
$app->run();
```

One file. One class. All nicely encapsulated, without any traces of abstraction, inheritance and polymorphism to get in the way. Am I actually advocating this approach? I would hope that by now, you know that I'm not.

That doesn't stop it being a conceivable possibility though. In theory, there isn't any reason why a single Application instance couldn't handle each request and emit the correct response and frankly, the job perfectly well.

Did I say there isn't any reason? What I meant to say there isn't any reason except one. You see, we're returning to the knotty little problem inherent in all application development – the human factor. At the time of writing, we aren't currently employing artificial intelligence to build web applications for us on any sort of significant scale. Notice that I'm hedging this art. I suspect there's at least one project out we are attempting to do (Skynet, anyone?).

This in brings us to the question of why we write the code that we do? Why do we even trouble ourselves with class design? Why should we consider the knowers and the doers? Why we bother adhering to some standard that we use to write only one class per file? Is it to make the PHP interpreter's life easier – feeding smaller, more digestible chunks of code?

Naturally no, the answer is that it is not. We write our code with one audience in mind. Humans. The one person reads our code most often is us. If we're working in a commercial environment, our colleagues are likely to want to be able to read our code as well. If we're building open source software then the potential audience can run hundreds of thousands, if not millions of PHP developers.
