# How do I work out who gets what?

Whenever you import a trait into a consuming class it's usually by the trait represents a certain chunk of functionality that's required by two or more unrelated classes. As we've already seen, traits provide us with a convenient approach to creating reusable code without resorting to inheritance. This part we already understand.

Where things start to get a bit slippery when we realise that within a trait will only be successfully imported into a consuming class when that consuming class hasn't already declared its method with the same name. Or to put it another way, only those methods that aren't already in a consuming class will get imported from a trait.

This is why I was a cagey earlier with our example of a LoggingTrait that included a definition for a constructor. The trait's version of the constructor would only ever be imported into classes that don't already declare their.

How slippery is that? It's perfectly apparent that the result of the trait's code relies on that logger property but going down the route of specifying a constructor that requires a logger instance isn't appropriate, if only because from the trait's own perspective, it has no idea of its methods will end up being successfully imported and which ones will fail.

It should certainly start to become apparent now why I was suggesting the application of snake-proof claws at the beginning of this chapter. Traits are bitey critters, that's for sure.

Clearly then, now we have a need to start considering precedence. How we determine which methods would be successfully imported, and which methods wouldn't.

Well, to begin with I've already covered the circumstance whereby a class that already defines a particular method won't be able to import an identically named method from a trait. My first order of precedence lies with the consuming class, which is exactly as it should be. This does pose something of a problem for as the trait itself is concerned given that the trait has no guarantee that all of its code will be imported wholesale. However, the consuming class's ability to retain full control over its own interface is paramount.
