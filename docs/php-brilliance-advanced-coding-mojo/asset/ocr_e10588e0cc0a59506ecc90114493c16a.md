Any changes to the method signature in the overriding method must remain compatible with the method signature as declared in the parent class. Any changes to the value that is returned from the overriding method in the child class must remain compatible with the type of return value declared in the parent class. And finally, if the overriding method in the child class can throw exceptions (or indeed, trigger an exception to be thrown) then these exceptions must be of the same type or derived from the exceptions that can be thrown by the same method in the parent. As long as we follow these three rules we're keeping any future bugs and headaches down to a minimum. One telltale sign to look out for, one that quietly inform us that we're failing to keep these rules, is if you find yourself needing to implement special logic in the client code to accomod the quirks of one or more child classes from a particular inheritance hierarchy. That is to say, if you find yourself writing conditional statements to determine whether you're dealing with a RegularBullet or an ExplosiveRound then you can be sure that your child classes aren't conforming to the data type definition that the parent class provides.
