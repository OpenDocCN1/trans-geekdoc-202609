One file. One class. All nicely encapsulated, without any traces of abstraction, inheritance and polymorphism to get in the way. Am I actually advocating this approach? I would hope that by now, you know that I'm not.

That doesn't stop it being a conceivable possibility though. In theory, there isn't any reason why a single Application instance couldn't handle each request and emit the correct response and frankly, the job perfectly well.

Did I say there isn't any reason? What I meant to say is there isn't any reason except one. You see, we're returning to the knotty little problem inherent in all application development – the human factor. At the time of writing, we aren't currently employing artificial intelligence to build web applications for us on any sort of significant scale. Notice that I'm hedging this art. I suspect there's at least one project out there we are attempting to do (Skynet, anyone?).

This brings us to the question of why we write the code that we do? Why do we even trouble ourselves with class design? Why should we consider the knowers and the doers? Why we bother adhering to some standard that we use to write only one class per file? Is it to make the PHP interpreter's life easier – feeding smaller, more digestible chunks of code?

Naturally no, the answer is that it is not. We write our code with one audience in mind. Humans. The one person reads our code most often is us. If we're working in a commercial environment, our colleagues are likely to want to be able to read our code as well. If we're building open source software then the potential audience can run hundreds of thousands, if not millions of PHP developers.

We write code so that humans, not computers, can read and understand it. Obviously, we still have to follow the syntax rules and lexicon of the language itself but since our PHP brethren are also trained in this art to greater and lesser degrees,

it comes down to how we set the code out, how we structure it, how we tie it all together, the thing that is how we make it comprehensible to PHP developers like ourselves and the others around us.

Which brings us back to our monolithic “entire app in a single class” concept. I know for certain that I would have no chance of fathoming out an entire application in a single class, assuming the extent of the code ran to hundreds of methods and tens of thousands of lines of code. Even if we were able to get it into our preferred editor of code without crashing the blessed thing, comprehension of the application’s inner workings would be fragmentary at best.

So we need to break it down into more manageable chunks, to get into a more workable format that recognises the foibles of the people that will work on it. For an excellent starting point, remembering to separate our *knowers* from our *doers* will help us achieve this.

Do you remember that I mentioned of some developers felt inclined to treat a particular class like a solo? If some method can be seen as vaguely user-related, in it goes. This is the start of the troublesome trail that ultimately ends up with the “app in a class” effect. It starts with the notion that we need to isolate the nouns in our design but at the other end of the spectrum, it results in a recognisable anti-pattern known as the “God Object”.

## God objects

The God Object occurs precisely at the point when an object can be deemed to know too much or do too much.

That's quite a sweeping statement with virtually no qualification, so let’s go ahead and try to qualify it. The term “God Object” was coined to represent the manner in which an object appears to become “all knowing”, that is to say that its influence is felt in many parts of the codebase at large, either referring to large parts of the codebase external to itself or more commonly, through large parts of the codebase having to look to the *God Object* itself for, processing or both. From personal preference, I like to attach the idea that a *God Object* is not just “all knowing”, but also “omnipresent”.

How is this a bad thing?

## Talking points.

In the first case, when one object can cause things to happen in remote parts of the application, that is to say, at a distance, then we are certainly setting ourselves up for a hard time tracking down bugs, quite simply because there appears to be a clear separation between the symptoms of the bug and the cause of the problem itself (when we find it).

Consider this:

```php
$user->getBalanceManager()
  ->getBalance()
  ->getNewTransaction()
  ->setTitle('Foo')
  ->setValue('10')
  ->save();
```

As ugly as that is, the code that invoking this particular chain is separated by at least two degrees from the act of saving a new transaction on the user's account. Even though we have yet to look at the various principles and paradigms that guide us to achieving brilliance, you probably already know of least three violations taking place in there.

Regardless of what these might be at this stage, we can see quite clearly that the invoker, with a blatant disregard for encapsulation, simply knows far too much about the inner workings of creating a transaction. We can conclude, quite logically, that this is also a very fragile approach to coding. Even if it works today, with so many links in the chain and therefore many points where failure can occur, it wouldn’t take much for the chain to collapse tomorrow.

Wouldn't it be better expressed as:

```php
$result = $user->getBalanceManager()->addTransaction(
array(
  'title' => 'Foo',
  'value' => 10
)
);
```

As far as this particular piece of code is concerned, it's reasonable to expect that BalanceManager at least provides the relevant method for adding a transaction. What goes on under the hood and the finer details of how this is achieved isn’t important to your invoker. Or at least, it shouldn't be.

Knowing too much is a bad thing. Unless you're taking part in a game show or a pub quiz, that is.

The flip side of the “God Object” coin shows its face when an object finds itself getting involved in many processes. This comes as a direct result of the “silo” mentality, where vaguely related methods get lumped into the one class. In the process of registering a user? The User class has just the methods for that. Need to send a user email? Look again, the User class has just the ticket. Where I find all of the blog posts that a user has made? Yep, you guessed it. The User class has it all and much besides.

On the face of it, it becomes quite easy to justify all those different methods in there. They are all directly related to the user. An email, though, is a discrete entity in its own right. So too is a blog post. By means let the blog post carry a reference to its author through an $authorId property that we can acquire the appropriate User instance when the need arises for sure, there's no justification for getting a user object involved in every blog post related operation.
