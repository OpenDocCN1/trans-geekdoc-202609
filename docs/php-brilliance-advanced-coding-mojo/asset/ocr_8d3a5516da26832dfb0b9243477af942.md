The problem we're then faced with is how do we get an instance of a PhoneNumberValidator into the User object in the first place, now that we're no longer using those handy validators as constructor params?

One thing that we do not is this:

```
private function isValid(array $userData)
{
    $pnValidator = new PhoneNumberValidator($userData['mobileNumber']);
}
```

That single line of code above leads to something known as tight coupling; something that we want to avoid. What we're saying here is, with this line in place, the class now depends on the PhoneNumberValidator class. This validator class is, in all likelihood, located in a separate file. (If it's not, you've definitely got other problems!) This one line ties the two classes together in a way that the User class can't exist in an application without the validator. Of course, you could argue that if we have a User class that needs access to a validated phone number, then both classes are likely to exist within the same application anyway.

The situation that we've created is actually a bit worse than that though. In the User class, we've not only declared a hard dependency on the PhoneNumber-Validator class. We have also coded in that the validator is instantiated by passing one of the $userData array values to the validator's constructor.

This is one of the most common pitfalls that both junior and mid-level developers will succumb to. If the signature of constructor method ever changes, then we have at least one location where our application is broken. Not only that it's broken in that sweet old classic way that leads to the expression “Well, I fixed this bug here, but now that it's broken over there."

“Aha!” I hear you exclamation, “But in such a situation, where one is modifying the constructor of a particular class, I would naturally grep the codebase and fix every location in the code base where objects of that class are instantiated.”
