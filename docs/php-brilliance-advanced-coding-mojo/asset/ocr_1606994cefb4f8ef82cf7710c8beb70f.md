# An abstract class is also an interface

You knew this already, of course. Especially if you were paying attention to the chapter on *abstraction*. You weren't you? What we have here is an opportunity to reinforce that idea because we've just gone through the thinking of an interface as declared in code as being a *guarantee*.

Think back for a moment to the chapter on *abstraction*. Here we spent a fair amount of time exploring the idea that an abstract class is a means of defining a new data type. We were in recognition of the fact that the native data types PHP gives us aren't quite good enough for our purposes. Yes, we could call our user data in an associative array that doesn't adequately represent our notion of a user actually is. It doesn't bear the attributes and characteristics of a piece of data of type *User* quite quite simply because it bears the attributes and characteristics of a piece of data of type *Array*.

And that's the key point here too.

Now we've spent all this time writing up *interfaces* to represent a guaranteed form of behaviour, we should be able to take the same concept of a guarantee and apply it to the various *interfaces* provided by abstract classes.

The key distinction here thought is that an abstract class can and provide the actual implementation logic. The provided guarantee can be extended to include the logical implementation of the declared methods. Let's take a look at how an earlier example might be adapted to suit our needs here:

```
abstract class AbstractRenderer
{
    private $data;

    public function setData(array $data = [])
    {
        $this->data = $data;
    }

    abstract public function getTransformed();
}
```
