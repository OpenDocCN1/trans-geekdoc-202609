Ok, I accept that it's a rather spurious example but it does serve our purposes here; the only reason that our controller accepts the $db object in the first place is to pass it to a factory method on a model class.

This is The Courier anti-pattern in action. An object receives a dependency that it doesn't actually use. Instead, it receives a dependency to pass it on to another object, method or function.

Why is this such a problem?

It's one of those problems where, whilst it works just today it will almost certainly be broken tomorrow. It's simply plain bad design.

Let's concentrate on the broken scenario though. Whilst we appear to be following first fix that was presented in the previous chapter, that of implementing a factory method on the target itself, that very factory method itself declares a dependency in its method signature.

This in turn means that any code that invokes the factory method must supply that dependency.

But if our requirements change? What if we come to our senses and decide to migrate from factory methods to fully blown factory objects or, better yet, a dependency injection container?

In each case, a change to the way that we create Profile instances would entail a code change inside our ViewController class. No matter how good the global search and replace function in your IDE or editor of choice, you would be faced with the need to make changes, potentially far-reaching changes, in parts of the code base that needn't be touched in the first place.

This is precisely one of those situations where "I fixed this bit here, but now that there is broken" becomes an oft-heard phrase.

Yet ever one unwelcome intrusion upon our most valuable commodity, high quality pub time, is entirely unnecessary.

The way to fix this is to stop asking questions of the code itself. In a way, this is rubber

duck debugging¹⁵ but with experience, the rubber duck becomes entirely optional.

What are we really asking the controller to do?
