Inheriting vast wealth is not always good.

Some, and I stress the word some of these third party sources encourage the idea that the way to consume the functionality that they offer is to create classes that extend the classes that are included within the package. This hacks back to the core principle that a child class derived from a parent will inherit all of the public and protected methods of the parent and in making use of this principle, the third vendor is promoting the idea of code reuse through inheritance.

A particularly common example of this is the framework that advises you to create your specific model classes by extending their base model class, primarily because their base model class already preloads with what is effectively a library of convenience methods. If you've been following along with me thus far, you will already know that this isn't the best way to achieve code reuse. It is theoretically possible to create, by mind at least, a very thin argument for suggesting that the base model class defines the data type, that the underlying methods are an expression of that data type but once we've gotten past examining the Single Responsibility Principle, you'll see that such an argument is exceedingly difficult to maintain.

How might we deal with this situation?

First off the back, we don't necessarily have to take the vendor's advice at face value. As programmers we are awesome finders of solutions. At this point, we can summon the sage advice of Larry Wall's suggestion that “there's more than one way to do it”. To help illustrate where I'm going with this, let me bring back a piece of code that we've already seen.

```
class User
{
    /**
     * @var UserDataTransport
     */
    private $userData;

    public function __construct(UserDataTransport $udt)
    {
        $this->userData = $udt;
    }
}
```
