
“Computer science, the yo-yo problem is an anti-pattern that occurs when a programmer has to read and understand a program whose inheritance graph is so long and complicated that the programmer has to keep flipping between many different class definitions in order to follow the control flow of the program.” - Wikipedia.com

Why then do we do it? Why is the problem so prevalent that it gets its own name and a wikipedia page? The unrestrained ability to provide for three or more levels of inheritance is, to my mind, born out of the misguided notion that abstraction and inheritance promote code reuse and helps the developer to avoid duplication. I’m sorry that I reminded you about this idea but I still say vehemently that it doesn't.

Code reuse is good though. We know this. Avoiding duplication of code is also good. We know this too. Adherents to the “Don’t Repeat Yourself” (DRY) principle are keen to keep and spread this knowledge around, and wisely so. Don't get me wrong by thinking that I'm turning my nose up at code reuse because I'm not. If I were to express inheritance abuse as a singular concept, it would go like this.

Inheritance abuse occurs as a result of the unrestrained extension of one class by another for no reason than that the extending class would have access to and therefore be able to utilise the logic, routines and/or properties of the class being extended.

As you might deduce, I’m referring again to the matter of convenience, but this time, rather than describing the process of writing a convenience method deliberately in a parent class that the child may have easy access to, I’m specifically referring to the practice of having one class extend another *purely* because the intended class contains “useful stuff”. When this happens, the developer is clearly disregarding any notion of families, hierarchies or data types. When this happens, it happens because the developer wants to “import” some of the functionality of parental target into the child class that they are creating. This is another of those terribly and easily recognisable code smells.

One thing that I’m particularly keen to encourage is for developers to avoid falling into the Inheritance Abuse trap. Keep your hierarchies as flat as possibly can be. Just two levels is the ideal to strive for: a data type definition provided by an abstract parent and the concrete data type specialisations provided for by the children. Not all application requirements are the same of course, but should you need to go beyond these levels, please be sure to have a really good, really strong reason for doing so. And in the course of doing so, be certain to remember that every level you add to an inheritance hierarchy will also add a proportional amount of fragility to your application, largely because “to err is human”.

## Borrowing third party code by extension

Which brings us nicely to our next consideration. Sometimes we are forced into the Inheritance Abuse trap, pitched headfirst down the rabbit hole of hierarchies, tumbled into terrains unseen with our hands tied behind our backs. Before I get too melodramatic, the situation that I’m referring to is the one where we have unplanned hierarchies thrust upon. Unplanned in the sense that the authors of the original code are not directly connected to the project that we are working on.

I’m talking about the use of third party libraries, components and frameworks. The concept is to be lauded of course. One of the most fantastic aspects of the open source software movement is simply because awesome code can be created and curated by large numbers of clever people, and code reviewed, audited and sanity checked by very many people. This in turn leads to some robust packages of reusable code to cater for almost every conceivable use case. Remember, reusable code is good. If nothing else, it saves us reinventing the wheel over and over again.

Situations arise where we are all encouraged to adopt Inheritance Abuse as the right to do things. Whether it’s company policy or merely the CTO’s personal preference, we might find others tied to a particular library or framework. In a commercial setting, it’s often not possible to take the time to play and explore with the various offerings that are out there. The business needs, needs to get the product out there, to shorten the development time, to assemble a team of developers who are familiar with the application’s ecosystem. If the boss tells us we’re building with Symfony, reaching the point of shipping code comes sooner because there are lot more people out there already familiar with the Symfony way of doing things. Conversely, the company that insists on its own homemade framework also needs to allow new hires a certain amount of non-productive time in order to become familiar with the code environment that they’re intended to work in.

Some, and I stress the word some of these third party sources encourage the idea that the way to consume the functionality that they offer is to create classes that extend the classes that are included within the package. This hacks back to the core principle that a child class derived from a parent will inherit all of the public and protected methods of the parent and in making use of this principle, the third vendor is promoting the idea of code reuse through inheritance.

A particularly common example of this is the framework that advises you to create your specific model classes by extending their base model class, primarily because their base model class already preloads with what is effectively a library of convenience methods. If you've been following along with me thus far, you will already know that this isn't the best way to achieve code reuse. It is theoretically possible to create, by mind at least, a very thin argument for suggesting that the base model class defines the data type, that the underlying methods are an expression of that data type but once we've gotten past examining the Single Responsibility Principle, you'll see that such an argument is exceedingly difficult to maintain.

How might we deal with this situation?

First off the back, we don't necessarily have to take the vendor's advice at face value. As programmers we are awesome finders of solutions. At this point, we can summon the sage advice of Larry Wall's suggestion that “there's more than one way to do it”. To help illustrate where I'm going with this, let me bring back a piece of code that we've already seen.

```php
class User
{
    /**
     * @var UserDataTransport
     */
    private $userData;

    public function __construct(UserDataTransport $udt)
    {
        $this->userData = $udt;
    }
}
```

I've removed most of the methods that were previously defined just so that we can focus on the relevant parts. Our User model here isn't extending anything at present. Instead, it's consuming UserDataTransport instance that it has access to the different pieces of data that concerns itself with. The rub: what if that UserDataTransport class was how we extended the base model class provided by the framework?

```php
class UserDataTransport extends FrameworkXYZ_Base_Model
{
  ..
}
```

It may not be an ideal solution because we are still having to accomod the reuse-by-extension idea that the framework imposes upon us, but by turning our derived so called model class into this notional UserDataTransport class, what we've actually achieved is a very nice layer of separation between our models and the framework.

# Summary

Whilst this chapter on Inheritance isn't quite as wordy as the Abstraction chapter that precedes it, I hope that I've managed to convey the key concepts in a way that is, at the least, comprehensible. If you accept that abstraction we are developers able to extend the range of data types that is natively available in our language of choice, hopefully you will also be to accept that the child classes that we derive from those abstract parents must remain compatible with the specification of the data type that the abstract parent provides.
