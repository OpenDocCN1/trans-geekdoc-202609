```
class FixedMortgage extends MortgagePlan
{
    public function getPaymentPlan()
    {
        // Logic to calculate a mortgage repayment plan
        // based on a fixed interest rate
        ...
        return $mortgagePlan;
    }
}
```

```
class CappedMortgage extends MortgagePlan
{
    public function getPaymentPlan()
    {
        // Logic to calculate a mortgage repayment plan
        // based on variable interest rates but subject
        // to a nominal cap to prevent repayments exceeding
        // a certain value
        ...
        return $mortgagePlan;
    }
}
```

And here I've provided the usual suspects in terms of specialised child classes. In the first instance, we have a FixedMortgage stabilisation, which is capable of calculating the mortgage repayments that would fall when a fixed rate mortgage has been taken out by a customer. The second instance features the necessary logic in order to calculate a variable rate mortgage that nevertheless is subject to capping to prevent the repayments exceeding a certain level.

I would fairly feel confident that each and every one of my readers has encountered this kind of code: child classes that implement specialised logic based on a set of circumstances the stabilisation is intended to represent. This is standard practice but it doesn't actually have to be this.

If we were to apply delegate polymorphism to the scheme above, we could actually do away with the abstraction and inheritance process entirely. Even though this is clearly another simplistic example and real life projects are rarely this easy, it does rather make for a good illustration of the point.
