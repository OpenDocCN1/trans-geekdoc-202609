# Talking Points 299

Adopting a regimen of effective unit testing, building up an effective set of test suites with a high degree of code coverage will save you and your team countless hours of future bug fixing.

This is a very good thing. In order to build up those test suites though, you have to create code that is testable in the first place. Just to be clear, let's bring that OrderModel class back into view.

```
class OrderModel
{
    private $db;
    public function __construct()
    {
        $this->db = Database::getInstance();
    }
}
```

As stands, this poor model class is impossible to unit test. Why? Firstly, we have a hard coded dependency on the Database class, right there in the code, making virtually impossible to test this class without having the Database class also present, due to the call on the Database class static getInstance().

> I say virtually impossible because there's a clever piece of kit called Patchwork which allows you to rewrite class definitions on the fly, and includes statically defined class methods too. You should consider as an escape plan for testing legacy code though, rather than a get-out clause for writing untestable code now and in the future!

https://github.com/antecedent/patchwork
