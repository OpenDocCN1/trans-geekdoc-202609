Expressing good traits.

any consuming class must also provide a concrete implementation of that abstract method. Returning to our LoggingTrait example, we might end up with something looking like this.

```
trait LoggingTrait
{
    private $logger;

    public function log($msg, $level)
    {
        $filename = $this->getLogFileName();
        $this->logger->setFileName($filename)
        ->log($msg, $level);
    }

    abstract public function getLogFileName();
}
```

With this, we've specified that any class needing to consume the Logging-Trait must also provide a getLogFileName() method because the code in the trait now depends on it. This is our first type of leaky abstraction and admittedly, it's not a bad leak. Our trait is expressing an external dependency which must be provided for the trait class to work properly. Since the demand is an explicit one, we can accommodate it by modifying the Loggable interface accordingly and all should be well. Any class that wishes to consume the trait should also implement the interface provided for the trait.

However, we've gotten ourselves into a bit of a tangle. We should be clear on the idea that an interface is the public expression of a guarantee for the specific benefit of any client code encountering. Should getLogFileName() be part of the consumer's public guarantee? In this specific instance, probably not. For your own applications, it should be on a case-by-case basis backed by the knowledge of what your consuming classes need to provide. In the above example, we could fix this by making the getLogFileName() private and subsequently omitting it from the interface.

Our next example of leakiness is one that cannot guard against through an interface though. It happens when the code in a trait refers to a property that is supposed to be present in the consuming class.
