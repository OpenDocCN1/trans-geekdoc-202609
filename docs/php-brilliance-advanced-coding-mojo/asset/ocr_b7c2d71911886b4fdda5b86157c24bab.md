To provide a case in point, there's a toJson method in there; a clear cut convenience method if was ever one. Why would a model object need to provide a data formatting method when the responsibility clearly lies with a formatter instead? The answer appears to be a convenience when rendering model data in response to an API call or an AJAX request. But if a model object truly required a toJson method to complete its definition as a data type, why isn't there also a toXML method. Or a toYami method as well?

Now don't get wrong. I don't want you to start that I'm "hating" on Laravel in particular, do not I want to alienate fans of the product. The majority of frameworks out take a very similar approach and it should be borne in mind that these very same frameworks provide a huge range of benefits in terms of the problems they've already solved. Routing? Check. Caching? Check. A consistent approach to templating? Also check. The advantages of not reinventing the wheel are well documented.

This is to say nothing of the fact that the framework code is out there in the public domain, readily scrutinised by anyone wishing to do so. In turn, this leads to the faster identification of bugs and the faster fixing of those bugs. On its own, this is one distinct benefit of community curated code.

However, a developer who wants to exhibit Brilliance isn't one that loses control of their interfaces. Isn't one that accidentally overrides a method in the base class simply because the base class is too large to memorise. It's important to remember that our client code is going to rely on those very same interfaces to guarantee a certain mode of operation.

To bring ourselves back to the point, if our model classes are already extending a framework's base model we can no longer make the decision as to whether we should provide an abstract class or not. The interface, cluttered as it might already be, is already surrendered control.

Does this really have to be the case?
