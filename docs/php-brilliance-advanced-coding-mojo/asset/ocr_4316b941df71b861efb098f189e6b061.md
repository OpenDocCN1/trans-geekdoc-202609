# Instantiaphobia

A static method that is fully self-contained is one thing. A static method that calls other static methods located elsewhere is another thing. A chain of static methods that includes a call to another, entirely separate system such as a database or a hosted API is the worst poetry of all.

Such an approach will sneaky introduce a factor of brittleness into your application development. What do brittle things have in common? A tendency to break.

Now it's not just the application itself that can break, although that is likely to happen with a lot of hard coded dependencies lying around. No, the development process itself can also be broken and that's something we want to avoid.

Consider this; if a test suite inadvertently relies on the presence of the database in order to run, and that test suite takes seventeen minutes and thirty-four seconds to complete, how many times a day do you think test suite is going to be run? Before each commit? Or just the once and just as the developer is about to head out for lunch?

So we need to fix this, and fix it right now.

But how?

Easily, is the fortunate answer. Instead of having those hard coded dependencies reaching out to other parts of the code base, we can inject them into the factory that needs them.

What this actually means is that we will need to turn our factories into objects themselves. Like this:

```
class UserFactory {
    private $db;
    private $roleFactory;
    private $accountFactory;

    public function __construct(
        Database $db,
        UserRoleFactory $roleFactory,
        UserAccountFactory $accountFactory
    ) {

        $this->db = $db;
}
```
