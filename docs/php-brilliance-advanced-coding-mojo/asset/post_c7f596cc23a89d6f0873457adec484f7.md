What if, instead of using that Animal class as the root of the inheritance hierarchy that we think we need, instead of using that Animal class as a repository of the methods we think are a common requirement of the rest of the hierarchy, we were to treat that Animal class as the immutable definition of a new data type?

If our application needs an Animal data type, we've now got it, explicitly set out in perfectly readable code. If, the well behaved programmers that we are, were to properly document the code through the liberal use of docblocks, we could conceivably arrive at something that be considered an extension of the PHP manual itself, at least from the perspective of this application. The rest of our team could then refer to this code and its documentation and not just learn, but also understand all of the attributes (properties) and characteristics (methods) that go in describing the behaviour of the Animal data type.

I made mention of word immutable in the previous paragraph, but since we are creating these new data types in PHP code the term immutable is conceptual at best. We haven't even gotten to the topics of inheritance and polymorphism yet but even so, I know you guys are good. You guys know beans. When it comes to creating child classes from this abstract parent, you know that a developer can alter the behaviour that a child instance exhibit just by overriding one or more of the parent methods. Would this be a good thing? The answer must surely be no. Especially if we are indeed committing to the notion that the abstract parent defines the type.

Let's consider a very silly example to help illustrate the point. In another of those infinite parallel universes, the creators of PHP decided that it would be a good idea to allow developers to create their own custom versions of the array construct. Wise as they are, they figured that we should be able to set the first index value as a config setting in php.ini, thereby allowing the application builders themselves to pick the number that array indexing starts with.

As a result, in one application, the first element of a numerically indexed array can be referenced using the number 7, leading to code that looks something like this:

In another application, the Chief Architect has opted for a starting index of ‘42’ since it goes so well with their “I heart Douglas Adams” T-shirt.

This is it: if the attributes and characteristics of our most basic data types differ from one place to the next, how can we possibly and reasonably be expected to build robust, secure and reliable applications? The question is rhetorical of course, since we wouldn’t be able to. We might be tempted to migrate to an alternative language, one that doesn’t insidiously encourage such extensive maintenance nightmares

Consequently, why can’t we apply the same sort of rigour to the custom data types that we create in our code through the use of the class keyword? I say we can. I say we should. Indeed, I say we must.

For the safety and security of our application’s data, it is imperative that our data types, including our objects, behave consistently and in accordance with the specifications that are laid down. That means both for the types that are natively built into the language laid down, and so for the types that we add to the language whenever we declare an abstract base class. Just as arrays behave consistently from one php file to the next, so should the instances of the Animal type behave consistently from one to the next.

PHP does help us in some way to achieve this. Whenever you use the abstract keyword for a class and optionally for method(s) within that class, PHP will place some restrictions on how that abstract class may be used. I’ll cover those briefly, just to make sure that you know what I’m talking about.

The first of these restrictions is obviously that you may not instantiate objects directly from that class but must use a child class. This is spot on and in laying down this restriction, I think it helps promote the idea that we’re laying down the blueprint for a new data type.

The second restriction is that, for any of the methods in the abstract class that are also abstract, the developer is forced to implement them in any child classes that he or she creates. This concept alone helps to bolster the idea that the abstract is imposing rules on its usage.

Furthermore, the implemented method must have a level of visibility that is either the same or less restricted than stated in the abstract method. For example, if the abstract method is declared as being protected, then the implemented method in the child class must be declared as either protected (the same), or public (less restricted). However, the implemented method in the child class may not be declared private as it is more restricted than that of the abstract method.

Additionally, the signature of the implemented method must also match the signature of the abstract method in the parent. This means both should have the same name and type of input parameters. I would say here, because it is actually possible to define a longer list of input parameters in the implemented method but I'm only highlighting this in order to be factually correct. To my mind, able to have a longer list of input parameters in such an implemented method breaks the concept of an *immutable* data type in such a subtle way.

When it's laid out like this, it should be possible to divine the sense of it. Yet at times, I've been given the impression that somewhere along the line, we, as the collective PHP developer community, have allowed the very idea of abstraction to become clouded.
