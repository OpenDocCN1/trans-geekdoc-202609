This is as it should be – remember that we're keen to keep our methods right up to the point where we have to open them up to collaborators.

Additionally, I've only one setter method here, being the one for the email property. Unless your application supports a user being able to change their username, the chances are good that providing a setter for the username property would be superfluous to requirements.

Even so, with the email setter I'm still not providing any validation within the setter itself. There is a very strong case for this. If we are confident enough that the data transport object itself provides everything needed to ensure that the data is valid and correct, confident enough to allow it to represent our entity's data at the point of instantiation, we should also have enough confidence in its integrity to delegate the validation responsibility to it when setting individual properties.

For this setter method though, I implemented some raw exception handling. This is simply to illustrate the fact that we recognise the data transport instance could balk at the value that we are passing to its setEmail() method and subsequently emit an exception. Additionally, since we are crossing application layer boundaries, we are recognising the need to recast the exception to a new type. There'll be more on exception handling later on in the book.

Ok, put the champagne on ice. We are almost there! Our User class is filling nicely now with the provision of the three public methods that represent the object's interface. We could certainly go on add any further getters and setters as our application requires but I shall leave that for you to experiment rather than taking any further space here. To do so would only serve to labour the point.

Up until this point, I've largely concentrated on the objects that know things. This is primarily because it's such a critical area of concern. I've been keen to stress that we shouldn't allow our knowers to get bogged down with large quantities of bloated methods, the reasons for which, I hope, abundantly clear. This does lead us to building some rather anaemia data classes though. Nevertheless (rather than anaemic) data classes are exactly what we need if we are to weather the storms that change requests bring.
