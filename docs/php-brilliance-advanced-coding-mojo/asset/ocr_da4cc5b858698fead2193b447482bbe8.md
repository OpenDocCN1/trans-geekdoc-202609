In taking that shortcut, you're effectively declaring that this one method will suffice for all possible current and future for setting data within this object. That's when a change request will pop up that doesn't quite fit the bill and you find yourself saying “Heck, I'll just pop a little if() statement in the foreseeable future to handle this case…”

Those two magic methods are here to stay though, at least for the foreseeable future. I'd advise you to treat them with extreme caution, almost as if they were a pair of snakes. Those at arm's length. By the neck. Whilst wearing some very sturdy snakeproof gloves. In other words, I'd settle for it a rule of thumb that this pair of magic methods only ever used in very clearly sets of circumstances that are appropriate to the application in question. And by circumstances, I don't mean it's just quicker to do it this way.

If you recall, we'd gotten ourselves to the stage where the username, email and balance properties of our User class were declared private and that these values were passed via the constructor. As far as the rest of our application code is concerned, those properties don't even exist. They're hidden. Invisible. But what good is that? And how on earth do we use those properties in our application. There are clearly situations that are going to arise where we need to display the username - perhaps on a dashboard or profile page. We can also be certain that we'll want to send the user an email every now and then, otherwise why even collect that detail in the first place. If these properties aren't accessible, are not even visible, to the code outside of the User class, how do we get hold of their values? What if we need to update the $balance property following a user's transaction?
