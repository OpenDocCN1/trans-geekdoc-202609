I've excluded the namespace declarations here just to preserve clarity, but as you be able to see, our panic is over. The class that's consuming the Logging-Trait now also guarantees that it has Loggable functionality by implementing the corresponding interface.

This then should be our golden rule: For every trait we create, we should also provide a corresponding interface definition that covers the methods defined within that trait. Any object that subsequently consumes a trait should also implement the corresponding interface to maintain the integrity of its guarantees.

# Damn those leaky traits

Since we can't actually specify an interface directly on a trait, we've seen how we need to provide an independent but very specific interface declaration for that trait. I've posited that as a golden rule for the explicit reason that failing to do so is to open door to some rather buggy scenarios down the line. Nevertheless, it's possible for a trait to have a direct influence on the structure of any class that consumes it. This is what I mean by a “leaky” trait.

When a trait is introspective and concerns itself solely on its own contents, then we can consider it safe to use. Its boundaries are well defined. This entire mode of operation is encapsulated within the scope of its own curly braces. When this is so, we have ourselves a non-leaky trait.

However, since a trait is naturally composed of plain old PHP, a less informed developer can start popping holes in our previous watertight hull, causing the trait's concerns to dribble all over the place.
