
With Scalar type hinting it's different. Since PHP is historically a weakly typed language, it's always supported the idea that the underlying type of a particular variable can be changed to suit the circumstances described in code. Like this:

```
$myVar = "42"; // $myVar defined as a string
var_dump($myVar * 2);

// $myVar type internally changed to integer to perform multiplication
// Output: int(84)
```

As a result of this, it looks like PHP will continue to support the internal casting of a variable's type from one to another. When we look again at the add() method, what will actually happen is that PHP will attempt to cast the first parameter to a float if it isn't already one. Likewise, the second parameter will be cast to an integer, again if it isn't already an integer.

Where these casts are possible, it does least mean that the logic inside the method will get the data types that are being type hinted. On the other hand though, allows for a very subtle problem of data corruption, which we should be particularly interested in avoiding.

```
$calc = new Calculator();
var_dump($calc->addThe(3.5, "2.75"));

// Output: float(5.5)
```

Quite reasonably, we would have expected the result to be 6.25. That's not what we've gotten back though, we've been given the answer of 5.5.

It would appear that our calculator class is broken. The reason why comes from the fact that our second parameter, "2.75", was silently cast to an integer on the way in. As a result, our method's internal logic was dealing with an integer value of 2, rather than the intended value of 2.75.

If the type cast is possible, PHP won't complain. Even if converting floats and float-like strings into integers results in data corruption occurring from our perspective as the developers and bug-fixers of the code.

# PHP7 336

This represents a significant challenge. If we type hint for a parameter that supports the ArrayAccess interface, PHP will complain when we fail to give it one. If we type hint for a scalar value, PHP7 will only complain if it can't perform the type cast internally.

Given that we're perfectly capable of explicitly casting from one scalar to another if we truly needed to, i.e. $int = (int) "31.25"; I think it's preferable to have PHP complain when we have a method expecting one type but getting a different type passed in.

Can this be achieved? The answer is yes, but the solution is rather a clunky one in my opinion.

We can tell PHP7 to turn on strict checking by adding a statement to the top of every file that needs it. The format of that statement is this.

```php
<?php
declare(strict_types=1);
```

It should be noted at this stage that declare() statement must be the first directive in each file that requires strict type checking. When declaration is in place at the top of the file, then our scalar type hinting will work as we expect it to. That to say, PHP will raise an error if we tried to pass a float as a parameter that was hinted as an integer. Equally, we'll also get an error when we try to pass a numeric string when the hint requires a float or an integer.

> Just to confuse matters, when strict checking is turned on, you can still present an integer to a method expecting a float. This is a "feature" since integers can be readily cast to floats without any loss or corruption. Integer 42 simply becomes float 42.0.

This is what is needed. Rather than type casting happening silently in the background, if we we have a string and it needs to be either of the numeric types, we will be required to explicitly perform the cast in our code instead. This significantly improves the visibility of any errors that we make when performing the type casts manually and as such, will give us an easier time of it identifying and fixing the bugs as a result.

# PHP7

One thing more must be noted; the declaration only applies to the code that appears in the same file, or to code that is consumed via a trait. Any code that is pulled in the require or include directives won't be covered by the strict types declaration unless those files also have the same declaration at the top too.

I mentioned traits up above and I think these little beasties are worthy of further consideration. You might be tempted to think that adding the declaration at the top of a trait's file should be sufficient to turn on strict type checking for the contents of that trait.

What do I mean by this?

```php
<?php
declare(strict_types=1);

trait AddingTrait {
    public function add(float $a, int $b) {
        return $a+$b;
    }
}
```

Despite having told you that the declaration needs to be at the very top for any code that requires strict type checking to be turned on, it doesn't work for traits. Whether this is intentional or it has been overlooked, it's certainly something to be wary of. We might be tempted to think that the following code would now work.

```php
<?php
class Calculator {
    use AddingTrait;
}
```

Unfortunately, that's not the case. In short, a trait cannot turn on strict checking for its own methods. Instead, the onus is on the class that consumes the trait. With our example, this means that the file containing the Calculator class is the one that must make the strict types declaration. Whether the trait does it or not is irrelevant.

```php
<?php
declare(strict_types=1);

class Calculator {
    use AddingTrait;
}
```

So, in order to use strict type checking, you must add the declare(strict_types=1); statement to the top of the file where the class is defined.

# Return Hinting

One thing more must be noted; the declaration only applies to the code that appears in the same file, or to code that is consumed via a trait. Any code that is pulled in the require or include directives won't be covered by the strict types declaration unless those files also have the same declaration at the top too.

Return type hinting is exactly what you might imagine it to be: the ability to declare the data type returned from a method. You might assume that I'm about to go on about interfaces, contracts and guarantees, but actually I'm not going to do that. We'll get there shortly, but first of all, let's take look at the implementation.

```php
<?php
declare(strict_types=1);

class Calculator {
    public function addThe(float $sa, float $b): float {
        return $sa+$b;
    }
}
```

Hopefully, you'll recognise this class from the previous section. If you don't, where is your brain at? We were only just discussing this bit a few pages ago. I suppose you could be forgiven if you happen to be reading this in a coffee shop crewed by remarkably attractive baristas.

Alright, focus. Here we are again with a very simple object that allows us to add two numbers together. As you can see, we're declaring for the float parameters types of both $sa and $b. In addition, we're now declaring for the float type by appending to the method signature a colon followed by the type.

As a result, the public interface of objects of this type has now become much more expressive. Not only can we see what types of parameters the addThe method requires, but also we can be confident that the method invocation will give us back a float value. A string, not an array, but a float.

This is a great boon for us. Since we should be striving for code that is bug-free as it can be, this gives us the ability to express in code a fully documented interface finally. The whole gamut of input parameter types are now catered for with the addition of scalar type hinting, complemented by the ability to hint the whole gamut of data types that a method will return.

When our colleagues and co-developers read the code we've written, the ability to readily discern the type of thing that will come back from a particular method invocation has enormous value.
