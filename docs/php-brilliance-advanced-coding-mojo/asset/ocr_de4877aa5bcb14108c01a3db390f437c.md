The flip side of the “God Object” coin shows its face when an object finds itself getting involved in many processes. This comes as a direct result of the “silo” mentality, where vaguely related methods get lumped into the one class. In the process of registering a user? The User class has just the methods for that. Need to send a user email? Look again, the User class has just the ticket. Where I find all of the blog posts that a user has made? Yep, you guessed it. The User class has it all and much besides.

On the face of it, it becomes quite easy to justify all those different methods in there. They are all directly related to the user after. An email, though, is a discrete entity in its own right. So too is a blog post. By means let the blog post carry a reference to its author through an $authorId property that we can acquire the appropriate User instance when the need arises for sure, there's no justification for getting a user object involved in every blog post related operation.

God objects reveal themselves as violations of sound programming principles. We've already touched on encapsulation, an object that's reaching beyond its boundaries of concern is clearly violating that one. Later on in the book, we will also be looking at the Law of Demeter and the Single Responsibility Principle as other, closely related techniques for identifying the offenders within our midst.

The good news is that the the God Object lends itself very well to refactored, another that we'll get to explore.
