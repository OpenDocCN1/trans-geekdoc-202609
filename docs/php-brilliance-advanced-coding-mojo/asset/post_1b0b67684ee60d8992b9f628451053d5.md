And in the spirit of the aforementioned cliche, let's take a small diversion. I've seen developers time and time implement the magic `__get()` and `__set()` methods in order to manipulate the values of properties in objects. Some PHP frameworks even support the very same approach, which to my mind is a crime most heinous. Not because the very popularity of such frameworks means a lot of PHP developers are being exposed to this approach and many of those may even come to think that it's the right way to code Hey, these guys are doing it.

Let's look at that code so we can better see what's going on.

```php
// error handling and validation omitted for readability
class User
{
    private $data = array();

    public function __set($key, $value)
    {
        $this->data[$key] = $value;
    }

    public function __get($key)
    {
        return $this->data[$key];
    }
}
```

The developer's guilt is assuated. He's holding the object's attributes in a private $data array, which is of course the right thing to do, yes? Let me ask you something: Why is this any different to using public properties? The answer of course is that it is not. Sure, we can start adding logic to the `__get()` and `__set()` methods to tighten things up though we'd certainly be fooling ourselves if we thought were actually improving our code by doing this. This should become more apparent as we get further along the PHP Brilliance trail.

To be fair, there's no harm in using the magic `__get()` method like this purely from the perspective of its own operation as long as the method itself implement some kind of error handling for non-existent keys in the data array.

On its own, the `__get()` method does nothing but yield values. However, its presence unavoidably lowers the resulting quality of our software, if only by making the merest suggestion that it also be permissible to implement the corresponding `__set()`. The very first moment you introduce `__set()` into your application's codebase is the very first moment that you open a huge can of worms and you had better prepared to cook 'em and eat 'em and swallow 'em down as it will not be very long that the bugs come marching after should you happen to leave any dangling.

When you use the `__set()` method to modify an object's property values, you're effectively wasting your time by coding the thing up. Just set the properties to public and be with it!

Of course, I'm not actually advocating that particular course of action. Quite often you'll see the `__set()` method fleshed out with code and logic of varying complexities. This might seem like a wise and clever thing to do but let's face it, every time a change request comes in calls for this logic to be modified, the opportunity to introduce bugs into the application comes right along with it.

Personally, I'd like to strike `__set()` from the language itself as I don't believe any good can come of its most common usage. When you have at your fingertips the power to control the setting of each element of data by creating your own specific and dedicated method for the purpose, the use of the `__set()` method is naught but a shortcut. In taking that shortcut, you're effectively declaring that this one method will suffice for all possible current and future for setting data within this object. That's when a change request will pop up that doesn't quite fit the bill and you find yourself saying “Heck, I'll just pop a little if() statement in the foreseeable future to handle this case…”

Those two magic methods are here to stay though, at least for the foreseeable future. I'd advise you to treat them with extreme caution, almost as if they were a pair of snakes. Those at arm's length. By the neck. Whilst wearing some very sturdy snakeproof gloves. In other words, I'd settle for it a rule of thumb that this pair of magic methods only ever used in very clearly sets of circumstances that are appropriate to the application in question. And by circumstances, I don't mean it's just quicker to do it this way.

If you recall, we'd gotten ourselves to the stage where the username, email and balance properties our User class were declared private and that these values were passed via the constructor. As far as the rest of our application is concerned, those properties don't even exist. They're hidden. But what good is that? And how on earth do we use those properties. There are clearly situations that are going to arise where we need to display the username - perhaps on a dashboard or profile page. We can also be certain that we'll want to send the user an email every now then, otherwise why even collect that detail in the first place. If these properties aren't accessible, are not even visible, to the code outside the User class, how do we get hold of their values? What if we need to update the $balance following a user's transaction?

Let's look again the class that we've defined.

```php
class User
{
    private $username;

    private $email;
    private $balance;

    public function __construct($username, $email, $balance)
    {
        $this->username = $username;
        $this->email = $email;
        $this->balance = $balance;
    }
}
```

We've used a technique called constructor injection here in order to get the properties into the object when it's first instantiated. As a rule of thumb, you use constructor injection only for those properties that the new instance will need to function as a finished object. If we're saying that our new User instance won't work properly without the $username and $email properties, then those are the things we need to make sure are included in the constructor.

If however, we are able to say that the $balance property is a thing that we may or not need then we'd take it out. What goes in the constructor should only be the essentials for the object's operation in every case. Of all the others, such as the $balance property here, might be served served being lazily loaded on demand. We'll get to that. Going forward, we'll drop the optional property and just stick with the $username and $email.
