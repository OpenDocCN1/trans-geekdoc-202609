
More pub time through interfaces.

A particular method is included in an object, client code is only interested in the methods that it can actually invoke. It has no business knowing about the object’s internals. Again, an interface is a public declaration made for the benefit of the implementing object’s collaborators.

There are a couple of pretty important things to remember here though. Important as in “When is your spouse’s birthday” important.

The first is that an interface never declares the actual implementation logic that goes into a method. The guarantee being offered extends to declaring the method names that are provided, and the list of expected parameters for each of those methods. There, of course, no guarantee that the named methods will behave as the method name might suggest. That particular responsibility is down to you and/or the members of your team.

As such, the method names declared in an interface are always written down as a single line of code terminated with a semi-colon, like this:

```php
public function methodName($arg1, $arg2);
```

That right there is called the method signature, which in turn comprises precisely of the method name itself and a declaration of any parameters that the method requires. Whenever the opportunity arises the developer exhibiting PHP Brilliance will stick the appropriate type hints in there too, leading to a method specification that looks more like this one.

```php
public function setAdapter(AdapterInterface $adapter);
```

The second important thing to note is that, whilst we are waiting for PHP7 to go mainstream, our interfaces cannot declare the data type of any values that might be returned from invoking the declared methods. What means in reality is that even if an interface guarantees that the getEmail() will be present, the guarantee doesn’t extend as far as ensuring the implemented method will give you back an email address, or that the return value even be a string. PHP7 gives that ability in some degree but in the meantime, responsibility is also squarely on the shoulders of you and your team.

# An abstract class is also an interface

You knew this already, of course. Especially if you were paying attention to the chapter on *abstraction*. You weren't you? What we have here is an opportunity to reinforce that idea because we've just gone through the thinking of an interface as declared in code as being a *guarantee*.

Think back for a moment to the chapter on *abstraction*. Here we spent a fair amount of time exploring the idea that an abstract class is a means of defining a new data type. We were in recognition of the fact that the native data types PHP gives us aren't quite good enough for our purposes. Yes, we could call our user data in an associative array that doesn't adequately represent our notion of what a user actually is. It doesn't bear the attributes and characteristics of a piece of data of type *User* quite quite simply because it bears the attributes and characteristics of a piece of data of type *Array*.

And that's the key point here too.

Now we've spent all this time writing up *interfaces* to represent a guaranteed form of behaviour, we should be able to take the same concept of a guarantee and apply it to the various *interfaces* provided by abstract classes.

The key distinction here though is that an abstract class can also provide the actual implementation logic. The provided guarantee can be extended to include the logical implementation of the declared methods. Let's take a look at how an earlier example might be adapted to suit our needs here:

```php
abstract class AbstractRenderer
{
    private $data;

    public function setData(array $data = [])
    {
        $this->data = $data;
    }

    abstract public function getTransformed();
}
```

Here we have declared a new data type called *AbstractRenderer*, which provides an *interface* to the rest of our application. This *interface* states that whenever client code sees an object with the data type AbstractRenderer, it can be assured that there will be two methods available. The first one is the full logical implementation of a setter for the $data property. The second one, getTransformed() will be a special provided by any child classes derived from this data type blueprint. We know this because the getTransformed() method is declared as abstract.

Let's look at a complete implementation.

```php
class CsvRenderer extends AbstractRenderer
{
    public function getTransformed()
    {
        // logic to turn $data into a CSV string.
    }
}
```

When we spark up an instance of the CsvRenderer, we can see quite clearly (largely because it's a skinny piece of code) that the interface declared by the abstract parent is fully honoured in the derived child. Our guarantee is in place. We rock solid.

The abstract parent has all important attributes and characteristics laid out for us. Just as we can write code that knows how to deal with integers and arrays, we can also write code that knows how to deal with AbstractRenderers.

Unfortunately, now comes the point where some less capable developers start to fall over. Let's modify our abstract class to help illustrate the upcoming points.

```php
abstract class AbstractRenderer
{
    private $data;

    public function setData(array $data = [])
    {
        $this->data = $data;
    }

    public function getTransformed()
    {
        return print_r($this->data, true);
    }
}
```

A subtle difference has been introduced, and it's one that isn't as uncommon as we might hope. Instead of declaring the getTransformed() method as being abstract and therefore requiring a specific implementation in the derived children, what we've done here is an actual logical implementation of the method itself.

The usual justification for this approach is that we want to provide some default behaviour for child classes. But this can lead to problems if a child class is supposed to provide its own implementation but forgets to, thus using the default instead. This is why the abstract keyword is so important; it forces the child class to provide its own implementation, or the code won't run.

In our case, we've just changed the interface by explicitly stating that the getTransformed() method returns a string. This is a guarantee that the client code can rely on, regardless of which child class is providing the implementation.

```php
return print_r($this->data, true);
```

This may not be such a concern just so long as you remember that the abstract parent is now providing an extended guarantee that includes return types as well. That guarantee is there to inform client code how this data type behaves. As such, it's our responsibility to ensure that guarantee is honoured in every class that we derive from the parent.

Fortunately, the changes in PHP7 go some (but not all) of the way to mitigating this particular set of circumstances. I've included details of how this is achieved in the appendices you should wish to seek ahead and take a look.

# The curious case of the variable constants

This idea has always "prickled" me somehow, even though it's evidently a very useful feature. As a sticker as I am, the notion of a constant that can have variable values just makes me, I don't know, itchy somehow. At least I get to breathe a little earlier when I remember that a class constant can ever hold a scalar value.

```php
class AbstractDataTable {
    const TABLE_NAME=null;
}
```

```php
class UsersTable extends AbstractDataTable {
    const TABLE_NAME="users";
}
```

```php
class OrdersTable extends AbstractDataTable {
    const TABLE_NAME="orders";
}
```
