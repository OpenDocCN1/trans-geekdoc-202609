## Countermeasures against Timejacking

To validate new blocks to the Blockchain, network time is used. A Timejacking attack occurs when an attacker writes incorrect timestamps, modifies the time clock of the node, and fools it into accepting a block from another Blockchain instead of one from its own. This is a fictitious attack. Boverman [5] provides the following solutions as

- Instead of using network time for timestamps, the node's system time is used.
- 70 to 140 minutes is the maximum initial attack timeframe.
- 70 to 140 minutes is the maximum initial attack timeframe. This time is cut in half, to 30 to 60 minutes, bringing the network node time down to around 30 minutes. This strategy will not be able to entirely eliminate attacks, but it will help to reduce them.

Time-jacking attacks are rare, so no new strategies to combat them have been devised. As it is always related to double-spending, the majority of double-spending security measures also hold products for time-jacking attacks.

## Countermeasures against Routing Attacks

There are numerous strategies for defending against routing attacks [6]. Multi-homed bitcoin is recommended since it makes it more difficult to conduct attacks when there are more connections. Attackers must either know both IP addresses or abort all cryptographic communication, which is easily discovered, in order to interrupt links between nodes. In the second approach, during the attack, the round-trip time (RTT) to hijacked destinations increases. A node could notice abrupt changes in the RTT towards its peers. As a protective strategy, the node will make random connections as a result of the outlier identification. Using another approach, UDP packets between nodes can also be updated regularly to identify if traffic has been withdrawn in part and in case it is connected to the network.

## Countermeasures against Eclipse Attacks

The following are countermeasures against eclipse attacks offered by Heilman et al. [9] to increase the difficulty of successfully launching eclipse attack.

### Random Node Selection

By constructing a peer-to-peer network, a blockchain architect can dramatically limit the probability of a node connecting to a malicious node, even if it had recently joined as if each node is connected to a random range of IP addresses synchronizes with the network rather than sticking to set of repeatable, exploitable nodes.

### Deterministic Node Selection

When a node connects to the network, this strategy involves placing specific IP addresses into their respective fixed slots. If the network's connections are fixed, an adversary will have a harder time managing hostile nodes around the network and converging around a target. An eclipse attack attempt will not be successful if addresses under the attacker's control are inserted repeatedly. Similarly, a blockchain might include node identities to reconnect with genuine nodes with a greater level of trust in its network connection requirement. The blockchain network will be safer and less vulnerable to outside interference if node connections are made using identifying information rather than contextual data such as timestamps and availability; they deviate from authorised network activity. However, the network may suffer scalability if connections may only be made to specified nodes that other peers have authorised.

### Increased Node Connections

A network can raise the possibility by increasing the required number of node-to-node connections; a node can connect to a genuine user. However, bandwidth restrictions limit how many node connections a network can add without sacrificing speed, making this strategy ineffective as a self-contained solution against eclipse attacks.
