# Countermeasures against Eclipse Attacks

The following are countermeasures against eclipse attacks offered by Heilman et al. [9] to increase the difficulty of successfully launching eclipse attack.

# Random Node Selection:

By constructing a peer-to-peer network, a blockchain architect can dramatically limit the probability of a node connecting to a malicious node, even if it had recently joined as if each node is connected to a random range of IP addresses synchronizes with the network rather than sticking to set of repeatable, exploitable nodes.

# Deterministic Node Selection:

When a node connects to the network, this strategy involves placing specific IP addresses into their respective fixed slots. If the network's connections are fixed, an adversary will have a harder time managing hostile nodes around the network and converging around a target. An eclipse attack attempt will not be successful if addresses under the attacker's control are inserted repeatedly. Similarly, a blockchain might include node identities to reconnect with genuine nodes with a greater level of trust in its network connection requirement. The blockchain network will be safer and less vulnerable to outside interference if node connections are made using identifying information rather than contextual data such as timestamps and availability; they deviate from authorised network activity. However, the network may suffer scalability if connections may only be made to specified nodes that other peers have authorised.

# Increased Node Connections:

A network can raise the possibility by increasing the required number of node-t--node connections; a node can connect to a genuine user. However, bandwidth restrictions limit how many node connections a network can add without sacrificing speed, making this strategy ineffective as a self-contained solution against eclipse attacks.
