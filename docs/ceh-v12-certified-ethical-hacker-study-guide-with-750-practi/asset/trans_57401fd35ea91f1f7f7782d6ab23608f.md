
一旦你了解了端点，就可以开始对其进行测试。在 Burp Suite 中这是一项轻松的任务。你选择要使用的请求，即在客户端‑服务器通信流中找到一个针对你想要测试的端点的请求。你可以将该请求发送到 Burp Suite 的 Intruder 部分。这将帮助你识别想要变更的参数，以便看看是否可以破坏应用程序。这可能包括修改数据、获取未经授权的访问或导致应用程序出现故障。[Figure 15.14](#c15.xhtml#c15-fig-0014) 显示了一个已发送到 Burp Suite Intruder 的请求。Burp Suite 自动识别出它认为可以修改的参数。例如，以下内容被 Burp Suite 识别为一个参数：

```
<operationID>§esxui-b6df§</operationID>
```

[**FIGURE 15.14**](#c15.xhtml#R_c15-fig-0014) Burp Suite Intruder

位于两条 § 字符之间的数据是 Burp Suite 认为可以调整的内容。使用 Intruder 功能，Burp Suite 会对选定的参数取不同值，对一组输入进行重复请求。你可以使用 Burp Suite 创建不同类型的数据操作。[Figure 15.15](#c15.xhtml#c15-fig-0015) 展示了 Burp Suite 允许的不同负载类型。也许最简单的是 Simple List，它允许你使用包含数值列表的文件。这可能需要你了解参数，以判断提供给应用程序的合适值是什么。如果你不清楚哪种数据会有用，可以使用 Brute Forcer 选项。该选项允许你指定字符集来生成值。你告诉 Burp Suite 最小负载大小和最大负载大小，它会尝试所有可能的值。请记住，请求数量会呈指数增长。使用小写字母和数字，四字符的负载，Burp Suite 指示潜在负载数量超过 160 万。更长的负载或更多字符会显著增加请求数量。

[**FIGURE 15.15**](#c15.xhtml#R_c15-fig-0015) Payload options

然而，你可能会遇到的问题是能够识别端点。这是一个问题。在应用程序内部没有标准方式来识别所有可能的端点。例如，在我们正在使用的 VMware Web 界面中，似乎所有请求都通过单一端点进行。这并不常见。应用程序可能有数十个端点，具体取决于应用的复杂程度。测试端点时，你可以使用以下几种方法。首先，如果你在进行白盒测试，可以从执行测试的公司处获取所有端点的列表。如果你在进行黑盒测试，可以进行端点暴力枚举（forced browsing）。这涉及向 Web 服务器发送使用端点名称的请求。如果服务器返回未找到错误（通常是 400 系列），你就知道没有找到端点。其他响应可能需要解析。200 响应意味着你找到了服务器认识的名称，除非服务器被配置为返回 200 响应但显示错误页面。这不常见，因为这违背协议，但确实会发生。

进行强制浏览的方法有多种。你可以编写自己的工具，使用脚本语言，例如准备好一组词列表时。在 Python 等语言中发送 web 请求并跟踪响应非常容易。词列表可在全网找到，包括 API 端点名称列表 `https://github.com/chrislockard/api_wordlist`。这个词列表也可以用于诸如 Burp Suite 之类的工具。你可以再次使用 Intruder 功能，选择要变更的请求的最后部分。此外，你还可以使用 Zed Attack Proxy (ZAP)。它内置了强制浏览功能。你可以在 ZAP 中选择一个站点，右键以打开上下文菜单，然后选择 Attack；从那里你可以对站点或目录进行强制浏览。你可以在[Figure 15.16](#c15.xhtml#c15-fig-0016) 中看到上下文菜单和弹出菜单。

![FIGURE 15.16 Force browse in ZAP](images/c15f016.png)

一旦你识别出可用的端点（即使强制浏览也未必能够发现全部端点），你可以回到以往的方式对其进行测试。毕竟，我们仍然是在测试一个运行在应用服务器上的 Web 应用程序。测试不同的 RESTful 应用程序可能存在细微差别。例如，你可能需要更改 User-Agent 字符串来测试某些应用。如果预期请求来自移动应用，使用传统的 IE、Chrome 或 Firefox User-Agent 可能不奏效。应用可能会检查正确的 User-Agent，以确保请求来自正确的位置。

### 常见云端威胁

在实践中，使用云提供商并不一定会改变攻击者可用或会使用的途径。攻击者仍然可以使用钓鱼攻击获取凭据，进而访问云端环境。无论你的资源位于何处，你都需要采取必要的阻断和应对措施来保护它们。这可能需要了解云环境的不同特性来执行正确的操作，但所有基本防护仍然必须到位。以下是如果你的资源在云提供商处时可能需要应对的一些常见威胁。

#### 访问管理

即使在云端环境中，你也会有用户。通常，你需要处理与本地网络和系统相同的身份和访问管理问题。云环境的规则与你自己的网络和系统相同。所有访问都应被审查并批准，确保每个用户仅拥有完成其工作所需的最小访问权限。这意味着应使用基于角色的访问控制（RBAC）而非为每个用户单独管理权限。每个用户都应拥有强密码，且不在其他地方使用。此外，无论身处何地，都应启用多因素认证（MFA）。

对一些人来说，挑战在于不知道在不同云环境中如何定位身份和访问管理功能。这与直接在 Windows 服务器上加载 Active Directory 管理应用并不相同，除非你使用联合身份解决方案将云提供商与本地 Active Directory 实例关联。这样，你就可以在本地网络和云提供商网络中使用相同的用户，凭据会在本地 Active Directory 实例上进行验证，尽管请求是针对云提供商的。
