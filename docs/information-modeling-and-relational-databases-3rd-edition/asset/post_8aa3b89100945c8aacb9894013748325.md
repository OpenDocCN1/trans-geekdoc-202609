
required element (or elements) within the JSON text using *accessors*: square brackets (`[]`) for elements in an array and a period or “dot” (`.`) for members of an object. The ECMAScript Language Specification for JSONPath also allows bracket notation for object members, but this is not supported in SQL/JSON. An asterisk (`*`) is used as a wildcard character to indicate all elements in an array or all members of an object. To illustrate these concepts, assume we have the JSON text of Listing 16.3 stored in a movie column of a table called videos.

This text contains a single object called movies. The value of this object is a list of six elements. Each element of the list is an object with members such as “title”, “director”, and so on. We can use the following query to get a list of all movie names.

```sql
select json_query(movie, '$.movies[*].title') from videos
```

To build the path from the root, we first add the movies member (the only member at this level). Next, we add a wildcard specification for all elements of the movies array. Finally, we add the title member from each of the array elements. All path expressions work in this way, though they can be much more complex.

JSON path expressions can be used in two modes: *lax* and *strict*. Lax mode is the default, and it provides automatic handling of some structural problems. If an object accessor in a path expression finds an array instead of an object, the array is converted to a sequence and the object accessor is then applied to each element of the sequence. If an array accessor finds a value that is not an array, the value is converted to a single-element array. If an error cannot be handled by these mechanisms, an empty SQL/JSON sequence is returned.

In strict mode, a structural error is reported without any attempt at correction. This is useful for identifying why a path expression is returning unexpected results.

The purpose of json_query is to return an extract from the JSON text. This will be a structural item (an array or an object) containing other items. To return a scalar value, **json_value** is used. This has a similar syntax to json_query, but the path must identify a single item. Consider the following two queries:

```sql
select json_query(movie, '$.movies[*].movieNr') from videos
select json_value(movie, '$.movies[*].movieNr') from videos
```

The first will return a list of movie numbers, but the second will return null because the result is not a scalar value. It’s possible to cast a scalar returned by json_value into an appropriate SQL data type. For example:

```sql
select json_value(movie, '$.movies[0].movieNr returning decimal(5,2)') from videos
```

returns a scalar value (because this query specifies only the first array item) with a cast to the designated SQL type. If no cast is specified, the type of the return value is a system default (typically varchar).

If a null is returned, we might want to know the reason. There are three possibilities: the null may have been retrieved from the JSON text being queried, the specified value does not exist, or some error has occurred. The default for all these cases is to return null, but we can distinguish between them with optional clauses to deal with the “on empty” and “on error” cases. For example, the following query will return the text “Not found” because we have specified an array index that does not exist in the data. Such optional clauses are not supported in all systems.

```sql
select json_value(movie, '$.movies[8].movieNr' default 'Not found' on empty) from videos
```

We can use json_exists to check whether a specific item is present or not. In this case, the return value is 1 if the item exists and 0 if it does not. For example:

```sql
select json_exists(movie, '$.movies[*].director') from videos
```

will return 1 indicating that at least one occurrence of the specified item has been found, but:

```sql
select json_exists(movie, '$.movies[*].producer') from videos
```

returns 0 because our movie objects do not contain a producer member.

One useful application of json_exists is in the creation of check constraints to ensure that JSON data contains some mandatory elements. Further predicates can be used to check whether an item is (or is not) a JSON value, array, object, or scalar, but we won't go into the details of these here.

Although json_query can return results from JSON documents, the results remain in a JSON format. To be consistent with other operations, we may prefer results in the form of a standard SQL table. This is the functionality provided by json_table, which extracts data from a JSON document and returns it as a relational table. Here's a simple example, based on our usual movie data.

```sql
select jt.Title, jt.Director from videos as v,
json_table (v.movies, '$.movies[*]' columns(
Title varchar(20) path '$.title',
Director varchar(20) path '$.director'
)) as jt
```

The select statement identifies columns from the aliased JSON table (“jt”) created by the json_table function. The first argument to the function specifies the JSON source, in this case the movies column of the videos table. The second argument defines the starting point in the JSON text, in this case the movies array. The column list defines the column name, the SQL data type, and the path in the current context (in this case, the starting point defined previously). The result is a straightforward SQL table.

| Title | Director |
|---|---|
| Cosmology | Lee Lafferty |
| Kung Fu Hustle | Stephen Chow |
| The Secret Garden | Alan Grint |
| The Secret Garden | Agnieszka Holland |
| The Da Vinci Code | Ron Howard |
| Cast Away | Robert Zemeckis |

It's possible to include data from different levels of the JSON text by using “nested” columns. In our data, the names of any stars of a movie are at a level below the title of the movie. The following example shows how these levels can be combined.

```sql
select jt.* from videos as v,
json_table (v.movies, '$.movies[*]' columns(
Title varchar(20) path '$.title',
Released int path '$.released',
nested path '$[*]'
columns (
Starring varchar(20) path '$.name')
)) as jt
order by Released
```

Again, this produces a standard SQL result table.

Tables produced in this way can participate in all the usual table operations such as join operations with other (non-JSON) tables in the database. A possible use of `json_table` is to create views that allow the JSON origins of the data to be hidden from SQL developers.

There is one more SQL/JSON retrieval function, and that is `json_serialize`. This takes a JSON value as input and returns JSON text in one of the SQL character data types (typically `varchar`). This is useful if the “raw” JSON value is in a binary form, which is not intended for human readability. Some implementations may also include a “pretty” option to produce nicely formatted text.

The operations we have considered so far assume that we have some JSON value stored in the database and want to extract some or all of it, in various ways. SQL/JSON also defines construction functions that build SQL/JSON items from non-SQL/JSON values.

The most obvious of these is `json_parse`, which takes a text input and converts it to a JSON sequence. This is essentially the reverse operation to `json_serialize`. If the input text is not well-formed JSON, an error will be returned. The `json_scalar` function is simple: it creates a JSON value from a non-JSON value. For example, an SQL value of data type `int` would be converted to a JSON number.
