
Under closed world semantics, when mapped to a relational database the asserted positive facts and the implied negative facts should be grouped into the Student table shown in Fig. 10.57(b), using mandatory Boolean attributes for isIntelligent and worksHard.

The derived facts about pass expectations can be mapped to an additional isExpectedToPass column in the Student_View table shown in Fig. 10.57(c). Instead of creating this view, a computed column for these derived facts could be added to the base Student table. Instead of mapping unaries to mandatory Booleans, the NORMA tool currently maps them to Boolean columns that are optional, so null values are allowed there.

The relational schema notation used in this book underlines the primary key name(s) and adds square brackets around the names of optional columns. Hence, NORMA maps the ORM schema in Fig. 10.57(a) to the following relational schema: Student( studentNr, [isIntelligent], [worksHard] ).

There are plans to extend the NORMA tool with control over closed and open world semantics for unaries, and to add support for negated unaries. In the meantime, to use NORMA to map to a mandatory Boolean, replace the unary by a mandatory n:1 fact type that targets a value type with a Boolean data type. For example, replace the Student is intelligent fact type with the mandatory n:1 fact type Student has IsIntelligentStatus where IsIntelligentStatus has a Boolean data type.

A second way to remodel CWA semantics for unaries is to replace the unary with a mandatory n:1 fact type that targets an entity type or value type with exactly two named values, for example, Student has IntelligenceStatus(Name) {'Intelligent', 'Unintelligent'}.

A third way to model CWA semantics for unaries is to add an opposite unary with the negated meaning (i.e., its instances are equivalent to negated instances of the original unary), for example, for the unary fact type Student is intelligent add Student is unintelligent. An exclusive-or constraint applies between the two unaries.

There are plans for the NORMA tool to add a notation to declare the negated meaning between the unaries. In that case, the exclusive-or constraint is implied and the schema maps to a relational table with a single Boolean column; otherwise, this approach maps to a relational table with two columns.

As another example, Fig. 10.58(a) shows a closed world unary fact type Country is monolingual (has exactly one official language) together with sample data. Canada (CA) and Cyprus (CY) are not recorded as being monolingual, so the CWA approach implies that they are not monolingual. Fig. 10.58(b) replaces the unary by a mandatory n:1 fact type.

Fig. 10.58(c) adds the unary fact type Country is multilingual whose meaning is the opposite of the monolingual unary. If we add a way to formally declare that the unaries are opposite in meaning (different proposals are under discussion), the exclusion aspect of the exclusive-or constraint is implied, and both fact types map to a single Boolean column. Otherwise, this approach maps to a relational table with two columns.

The open world assumption (OWA) allows that some relevant facts may be unknown (as asserted or derivable facts). Fig. 10.59 remodels our student example under OWA semantics.

In Fig. 10.59(a), the role boxes for the unary predicates have dashed lines suggesting openness and hence OWA semantics. At the time of writing, this OWA notation for ORM is not supported by NORMA.

The OWA implies classical negation (failure to find or prove a proposition or its negation implies that its truth value is unknown). For example, as indicated in the base Student table in Fig. 10.59(b), the failure to record the facts that students 1002 and 1004 are intelligent simply means that we do not know whether they are intelligent. Here we record the entry “unknown” to indicate this. In most databases, this entry would appear as a null. Check for yourself that the other “unknown” entries follow from the OWA interpretation.

The relational schemas shown in Fig. 10.59(b) and (c) indicate that an open world unary is mapped to an optional Boolean whose truth value is restricted to True. For example, replace Student is intelligent by the fact type Student has IsIntelligentStatus {true} where the role of IsIntelligentStatus is named “isIntelligent”.

Another way to model OWA semantics for unaries is to add a unary with the negated meaning as well as with an exclusion constraint between its role and the role of the original unary. For example, add Student isUnIntelligent fact type with an exclusion-constraint between its role and the role of the Student isIntelligent fact type. However, without a way to formally declare that one unary is the negation of the other, this way maps to a relational table with two columns rather than one column.

As a halfway position between CWA and OWA, the semiclosed world assumption (SWA) allows that some relevant facts may be unknown as derived facts, but not as asserted facts. This implies semipositive negation (given any asserted fact type, failure to find a fact instance in it implies that instance is false; and failure to prove an instance of a derived fact type or its negation implies that its truth value is unknown). This approach can be used only when the fact types are asserted or fully derived (not semiderived).

The open world with negation (OWN) assumption allows some relevant facts to be unknown (as asserted or derived facts), but also allows negations to be asserted. Like OWA, the OWN approach also leads to classical negation, which is the usual approach in classical logic. Although it is rare to assert negative facts in databases, it is common in logic systems. The OWN approach is just a special case of OWA.

One way to support OWN semantics in ORM is to allow unaries to be populated with both positive and negative instances, with negated instances prepended by a tilde “~”, often used in logic for the “not” (it is not the case that) operator, as shown in Fig. 10.60(a).

Another way to support negated instances of an open unary is to add a separate unary fact type with the opposite meaning (its instances are equivalent to negated instances of the original unary). The opposite meaning implies an exclusion constraint between the two unaries. For example, to record that student 1002 is not intelligent, include that student in the population of the fact type Student isUnintelligent where there is an exclusion constraint between its role and the role of the Student isIntelligent fact type.

A third option is to replace the unary with a third way to model. Suppose that we know that Australia (AU) and the United States (US) are monolingual and that Canada is multilingual, but don’t know the language status of Cyprus.
