
More interesting are the functions to construct JSON structural elements, objects and arrays. The constructors can be nested, so we can build JSON values of arbitrary complexity. These functions are summarized in Table 16.8.

Table 16.8 SQL/JSON structural construction functions.

| Operator | Functionality |
| :--- | :--- |
| json_object() | Creates an SQL/JSON object from a given list of name-value pairs |
| json_array() | Creates an SQL/JSON array from a given list of values |
| json_objectagg() | Creates an SQL/JSON object from a given collection of rows |
| json_arrayagg() | Creates an SQL/JSON array from a given collection of rows |

Creating objects is straightforward. The following query defines an object structure with members for employee number and office, which is then applied to each row of the Agent table.

```
select json_object('empNr' value nr, 'office' value office) from Agent
```

Result:

```
{"empNr": 101, "office": "Boston"}
{"empNr": 232, "office": "Portland"}
{"empNr": 397, "office": "Durham"}
{"empNr": 468, "office": null}
```

Some implementations of json_object replace the value keyword with a comma. An ugly feature of the result is the null in the last object. A more natural JSON representation would omit this member entirely. SQL/JSON defines an optional absent on null clause to effect this, but it's not supported in all implementations. We may be able to find a workaround by providing something more meaningful based on domain knowledge. For instance, if we know that the reason for Dave Dunk having no office recorded is that he is mobile, so his office varies, we can replace the null.

```
select json_object('empNr', nr,
'office', case when office is not null then office else 'varies' end)
from Agent
```

Result:

```
{"empNr": 101, "office": "Boston"}
{"empNr": 232, "office": "Portland"}
{"empNr": 397, "office": "Durham"}
{"empNr": 468, "office": "varies"}
```

It's obvious how this query could be extended to include separate members for givenName and familyName, but an alternative would be to create a name member containing objects for each of the name components. This can be done by nesting additional json_object constructors within the name member.

Phone information is a little more complex because the member is not single-valued. We'll assume that a list of numbers is required, each represented by an object. This can be produced by nesting object constructors inside an array constructor in the following way.

```
select json_array( json_object('type' value 'home', 'number' value homePhone),
json_object('type' value 'work', 'number' value workPhone) )
from Agent
```

Result:

```
[{"type": "home", "number": "222-9876"}, {"type": "work", "number": "222-1234"}]
[{"type": "home", "number": null}, {"type": "work", "number": "555-6789"}]
[{"type": "home", "number": "777-6789"}, {"type": "work", "number": "777-4321"}]
[{"type": "home", "number": null}, {"type": "work", "number": null}]
```

To integrate this information, we can introduce a phones member into our earlier object, with the array construct above nested inside it. We have the same issue as before with nulls. If the absent on empty clause is not available, we could create a more complex SQL query to remove the null members from the JSON result, but for our current purposes, we'll just accept the nulls.

The functions not covered so far are the object aggregate and array aggregate constructors. We can illustrate these with the Project table. The json_objectagg function requires a key-value pair, as in the following example:

```
select empNr, json_objectagg(projName, rate)
from Project group by empNr
```

Result:

```
101 {"Grebe": 2, "Mallard": 1}
232 {"Grebe": 3, "Plover": 1, "Bittern": 2}
```

Here, the resulting object for each group has a member for each item in the group. This differs from json_object, which would give a separate object for each item.

Creating an aggregating array works similarly but requires only the identification of the value to be listed. This gives an array with an element for each item in the group.

```
select empNr, json_arrayagg(projName)
from Project group by empNr
```

Result:

```
101 ["Mallard", "Grebe"]
232 ["Grebe", "Plover", "Bittern"]
```

To meet our aim of a comprehensive Agent object, the json_arrayagg constructor looks the most appropriate. This can be integrated into the larger query by nesting it within a projects member of the main object structure.

To create the required final JSON structure, the rows containing the above elements can be aggregated together to form a list of agents within an enveloping object, as shown in the following query.

```
select json_object ('Agents', json_arrayagg(
    json_object(
    'empNr' value nr,
    'name', json_object('given' value givenName, 'family' value familyName),
    'phone', json_array(
    json_object('work' value workPhone),
    json_object('home' value homePhone))),
    'office', case when office is not null then office else 'varies' end,
    'projects', (select json_arrayagg(projName)
    from Project p where p.empNr = a.nr group by p.empNr))))
from Agent a
```

## 16.4 Other Markup Languages

As the name suggests, markup languages, like XML, work by adding additional markings of some kind to the original information to indicate its function or purpose. Historically, the leading application for markup was in the publishing industry, where it was (and still is) used to show the treatment to be applied to the author's text to turn it into a properly formatted layout for printing. In a database context, we might consider markup as metadata.

A language close in spirit to JSON is YAML. This originally stood for “Yet Another Markup Language”, but other interpretations of the name have emerged subsequently. YAML is a superset of JSON with some additional features, and utilities are available to convert back and forth between YAML and JSON. The main motivation for YAML was to provide a more “human-readable” format than JSON, especially avoiding extensive use of brackets (rounded, square, or curly). Nesting can be indicated by indenting items in a similar way to the Python language using spaces. This reduces the possibility of common keyboard errors.

Some brief features of YAML include the following:

- Items are nested by indenting child nodes below their parent.
- Key-value pairs are separated by a colon, but quotes are not required.
- New items in a list are indicated by a hyphen.
- Scalar values including strings, numbers, and Booleans can be used freely.
- Quotes are not needed for strings but can be used if needed (for example, if a number is required to be treated as a string).
- Comments can be indicated by a hash character (comments are stripped out when converted to JSON).
- Additional commands are provided to control the layout of text in output (e.g., suppressing newlines).
