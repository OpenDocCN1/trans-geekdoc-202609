As already noted, there is a great deal of diversity among NoSQL databases, and this certainly applies to key-value stores. Individual systems have their own individual features, but there are some common characteristics associated with most popular key-value stores.

- Simplicity: Key-value stores typically offer a simple data model where data is stored as key-value pairs, making them easy to understand and use. They do not require a complex schema or complex table structures and can be easily integrated into existing applications.

- High performance: Key-value stores are designed for high-speed data access and low-latency operations. This is partly because they use simple data structures and avoid complex joins or indexing. They also tend to minimize disk I/O, using in-memory caching and optimizing data structures and algorithms for fast key-based lookups.

- Scalability: Key-value stores are easy to scale horizontally by distributing data across multiple nodes. They support sharding and partitioning techniques to handle large datasets and can grow gracefully as data volumes increase over time. This makes them a good choice for applications that need to handle a large volume of data and require high availability.

- Replication and fault tolerance: Key-value stores often provide replication mechanisms to ensure high availability and fault tolerance. They store redundant copies of data across multiple nodes or partitions and can provide automatic rebalancing of services in case of node failures.

- Flexible data models: Most key-value data stores can store a wide range of data types, including structured, semistructured, and unstructured data. This makes them useful for applications such as storing user profiles, sensor data, session data, and IoT applications that require a variety of types and formats.

Clearly, key-value stores offer some advantages that can be exploited in certain types of applications, but we must set these off against features that may make a key-value store less suitable in other circumstances.

- Ad hoc or complex queries are often not supported in the data store, such as searching for data with a specific feature or connections between data across different key-value pairs. Any such operations must be carried out in application code external to the data store.

- There are limited opportunities for operating on the data stored as the value of a key-value pair. Data retrieval is typically aimed at the efficient retrieval of the value as a unit. This also potentially makes modifications to some element within the data less efficient because the whole value must be handled as a complete data chunk.

- Unlike relational databases, there is no standard for the structure of key-value stores. There is little opportunity for the transfer of expertise from one key-value product to another because each uses its own proprietary functions and methodologies.

- Key-value stores are generally not well equipped to provide the kind of support for the ACID properties that are usually associated with relational systems. Transactions are generally limited to operations on a single data unit.

- There is limited scope for the validation of data or the application of constraints within the data store. Again, such operations must be carried out by the application code before the data is stored or after it is retrieved as a unit.

Identifying the right key-value store, or even deciding if a key-value store is appropriate, will depend heavily on the requirements of each individual case. Key-value stores are very well suited to applications that require rapid access to an individual unit of complex data from a very large pool of similar units. Some typical use cases include the following:

- *Caching.* Data that is frequently accessed can be stored in a key-value data store for faster retrieval. This can help to improve application performance and reduce latency. For example, an e-commerce website may use a key-value data store to cache the product information for popular products so that the website can be served quickly without querying the traditional database every time.

- *Session management.* A key-value data store can be useful in applications where a user's session needs to be maintained across multiple requests or across multiple servers. Values such as log-in information and shopping cart contents can be held for quick retrieval of the information when needed.

- *Storing user preferences.* User preferences can be stored as key-value pairs, allowing for easy retrieval and updating of user preferences. This can be useful in applications where users need to be able to customize their experience or where user preferences need to be shared across multiple devices.

- *Content management.* Digital content is now commonplace. This includes text, images, videos, documents, and other multimedia assets. An application may need to collect diverse kinds of media into a collection that can be stored and retrieved as a single unit, which is ideally suited to a key-value store.

## 17.3 Column-Oriented Databases

The main difference between column-oriented databases and relational databases is how data is organized and stored rather than the logical structure of the data. A relational database stores information in tables, organized into rows and columns. A table can be thought of as information about a particular type of entity, with each row representing an individual entity of that type and the columns containing values that are relevant to that entity type. A row is often described as a record, and the related column values as fields of that record. The main focus is on managing records, so it is legitimate to describe this type of database as row-oriented.

If we need to query for specific data, the database must scan through all the rows in the table to find the relevant information. This can be aided by indexes but for large databases with millions of records, it can be slow and inefficient.

In contrast, column-oriented databases store data in columns, with each column representing a single attribute or field in a table. This means that the values for a particular attribute type are stored together in one column, regardless of which records they belong to.

When the database is queried for specific data, the database only needs to scan the relevant columns, rather than every row in the table. This can be much faster and more efficient, especially when dealing with large datasets and operations such as aggregation.

Several column-oriented database systems are available, including the following: Amazon Redshift has excellent integration with other AWS products. It provides dynamic scaling and automates many system management activities. Several open-source systems are available. PostgreSQL is a well-known row-based database, but it also has a column store option that is useful when you want to use only one database for both column and row store. MariaDB is another popular open-source database that supports both row and column storage. Apache Cassandra is a column-oriented database designed to handle large amounts of data across many commodity servers.
