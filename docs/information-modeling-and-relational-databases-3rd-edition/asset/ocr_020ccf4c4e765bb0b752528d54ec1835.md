# # Linking Data

Inserting, retrieving, and managing individual documents is relatively straightforward, but in any realistic database, there will almost certainly be a need to link different documents together. This can be seen as the equivalent of foreign key references in a relational database. There are two ways of achieving this in a document database. To provide some examples, assume that we have (highly simplified) documents relating to students and their grades in university courses.

The first approach to linking courses and students with customers is embedding. In general, if Document1 needs to be linked to Document2, this can be achieved by nesting one document within the other. In this example, we’ll assume that the Course document contains the Student details.

```
{
 "Courses": [
 {"_id": "DB102",
 "courseName": "Databases",
 "creditValue": 15,
 "Students": [
 {"studentId": "12345", "name": "Abby Akbar", "grade": 3.4},
 {"studentId": "67890", "name": "Bill Briggs", "grade": 3.2}
 ],
 },
 {"_id": "SW101",
 "courseName": "Python",
 "creditValue": 10,
 "Students": [
 {"studentId": "12345", "name": "Abby Akbar", "grade": 3.8}
 ]
 }
 ]
}
```

It would also be possible to embed a list of Courses into a Student document, using the standard JSON structuring. Which of these would be preferable depends on the anticipated usage of the data. In this case, although we have two different kinds of information (Courses and Students), we end up with only one document collection: either Courses (as above) or Students, depending on how we decided to embed the documents.

It’s clear that embedding the data in this way will result in redundancy, corresponding to denormalization in a relational database. Given the falling cost of hardware, the need for additional storage space might be acceptable. More serious is the problem of maintaining consistency.
