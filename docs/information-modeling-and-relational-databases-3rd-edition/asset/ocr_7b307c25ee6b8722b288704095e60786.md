We also need to consider the constraints specified in the ORM model. This is potentially problematic because of the very limited constraint options available in the graph database equivalent. Some workaround possibilities exist through careful framing of statements that modify the structure, but this may not always be possible.

Mandatory constraints can be enforced to some extent by requiring that, for example, a property of a label is not null, but this can be a nuisance if the property value is not known when the relevant node is created.

Uniqueness constraints are available in Neo4j and can be used where appropriate. In the model above, the identifying properties for Company, Channel, Survey, and Program can be defined as unique. This means that, for example, there will only be one node with the label "Channel" and a ChannelNumber property equal to "1". However, this should not be done in the case of Suburb, Department, or TimeSlot because these labels can have multiple nodes with the same property, as can be seen in Fig. 17.14. These nodes can be distinguished from each other by having different instances of their relations with other nodes.

The external uniqueness constraint between the Channel role and the TimeSlot role is more difficult. We need to ensure that a TimeSlot can only relate to one Program for a given Channel, although the same TimeSlot can be used by other channels for their own programs. There is no constraint in Neo4j to express this, but we could specify the creation of the IS_SHOWN_IN relation between a specific Program and a specific TimeSlot using the following strategy:

+   1. Use a query to find the Channel that shows the specified Program.
+   2. Use a query to find any Program shown by that Channel in the specified TimeSlot.
+   3. If the result is a null, create the IS_SHOWN_IN relation between Program and TimeSlot.

ORM has a very rich constraint language, and it may not be worthwhile to try to write complex Cipher code to capture the full intent of the ORM model. In such cases, it may be better to delegate the constraint to the application code instead of trying to enforce it in the database.

It's clear from this example that there is a close affinity between ORM and graph databases, which is perhaps not surprising because an ORM model is itself a graph. Graph databases offer a useful alternative to relational systems in applications that are focused more on relationships than data processing. They share many of the same issues on scalability as relational systems, but can provide high availability by replicating servers.

Translating an ORM model into a graph database can be done in a systematic way that preserves most of the intent of the ORM model, though some creativity may be required in dealing with constraints. For a specific graph database system, it would be feasible to automate a Gmap procedure to generate a schema design, possibly including some code (in the appropriate language) to deal with issues such as constraints.

Probably the most important feature of graph databases is their ability to follow links through a connected network of data, perhaps extending over long chains of connections.
