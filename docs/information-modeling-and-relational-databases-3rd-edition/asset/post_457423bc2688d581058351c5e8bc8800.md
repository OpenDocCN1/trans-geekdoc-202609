
Although time has only one dimension, unlike space’s three dimensions, the efficient management of *temporal information* is no easy task. If historical rather than snapshot records need to be maintained about objects, time will feature largely in the modeling.

As discussed in *Chapter 10*, a variety of approaches may be adopted for modeling time. In some cases, we simply include object types such as Time and Period on the conceptual schema and map these like other object types. Distinctions may be needed between transaction activity time (when the system records a fact) and valid time (when the fact is true in the UoD being modeled). Often, we need to make use of temporal relations (such as before and after) and temporal operations (e.g., to compute an interval between two time points).

The SQL standard currently includes only basic support for temporal data, and sometimes an ordinary relational database does not allow temporal aspects to be implemented efficiently. For such applications, special DBMSs known as “temporal database systems” are sometimes used; these provide in-built support for automatic time stamping and the various temporal operators.

Most work on temporal databases focuses on maintaining relevant histories of application objects through time, with the assumption that the conceptual schema itself is fixed. Moving up one level, the problem becomes more complicated if we allow the conceptual schema itself to change with time. This is one aspect of the schema evolution problem.

Moving up another level, we might allow the conceptual metaschema itself to change with time (e.g., we might decide at a later stage to allow constructors for complex object types in our conceptual schema language). The management of such higher-order evolution has been addressed in research on evolving information systems. This topic provides one motivation for the discussion on metamodeling in *Chapter 18*.

Centralized and distributed databases were discussed earlier in this chapter. A further dimension is offered by *federated databases*. These deal with situations where there is a need for data sharing between several different database systems, possibly heterogeneous (e.g., some relational, some column-oriented, some key-value, and so on). In this framework, each individual system maintains its local autonomy and communicates with other systems on an as-needs basis. As the heterogeneity problem requires translation between different data models, the control of federated systems is nontrivial.

Interest in federated databases has been accelerated by the advent of cloud computing. Most organizations find that management of a collection of heterogeneous databases can be a headache, but this can be greatly eased by outsourcing functionality to a cloud service provider. Three levels of service are typically offered:

- *Infrastructure as a Service (IaaS)* provides basic processing, storage, and networking functionality, based on dedicated or virtual hardware. This essentially replicates an in-house data center but within the cloud service. Users remain responsible for standard management functions.

- *Platform as a Service (PaaS)* transfers responsibility for managing infrastructure resources to the cloud service provider. Users are freed from concerns such as operating system updates, hardware maintenance, and so on. Additional capacity can be obtained easily and incrementally from the service provider, allowing the user to focus on installing and maintaining applications.

- *Software as a Service (SaaS)* includes all the previous features but also takes on responsibility for the software applications, including licensing, software updates, and so on. In this situation, the cloud service provider controls the application and users simply pay for access.

A cloud-based approach opens several other important possibilities. One is the idea of a serverless database. A database can be defined in the usual way, but the server hardware is absorbed into the broad cloud capability. This provides all the functionality of the traditional installation of a database installed on a server, plus some additional advantages. These include greater resilience, automatic scaling to meet demand, simpler resource management, and pay-as-you-go pricing.

Organizations commonly store large amounts of data in a data warehouse to make it available for further processing. In a cloud context, this idea can be extended into the concept of a data lake. The name is inspired by the analogy of a lake full of unprocessed water that can be drawn on and treated in various ways to make it suitable for consumption. A data lake is a repository for large amounts of data stored in its original “raw” form. This differs from a data warehouse in having no schema, as any necessary schema can be created on demand based on the requirement to be satisfied. Software tools can be used to develop the necessary functionality, such as creating a new SQL database from CSV files and spreadsheets in the data lake.

Various file formats have been created to cater for specific conditions and more will undoubtedly be defined in the future. Avro is an example of a row-oriented format that is useful for compressed data. Each record in the file contains binary data plus a JSON header that defines how the binary data can be parsed to extract individual fields. Parquet is an example of a column-oriented format that is useful for large datasets with nested values. Values from the same column are stored together and organized into row groups for efficient processing. Again, the file includes metadata to allow data to be located efficiently.

Creating a database in a cloud environment can be made easy through low-code development. Instead of writing code (perhaps in SQL) to define the structure, the creator can simply select from a range of options. The detailed operations to build the necessary structure can be automated and hidden from the user. Useful fields such as the user that created a record, the date it was last modified, and so on, can be automatically added to tables. An example of this approach is the Microsoft Dataverse, which is a cloud-based data platform. This allows users to create data-related applications without the need for technical knowledge using Microsoft’s Power Platform tools.

As discussed in Chapter 16, XML and JSON are notations that support a systematic approach to describing structured data, and either could potentially provide the foundation for a database system. As we have already seen, JSON provides the basis of the document database approach. Some examples of XML databases have been developed, but these have not been widely adopted. The general usage of XML is in the form of individual XML documents, particularly for the exchange of structured data between disparate systems. XML is now encompassed as a data type within SQL, and processing of XML data can be handled within a relational framework, reducing the appeal of a separate database for XML alone.

Although both XML and JSON are textual notations, the text is not well suited to human visualization of information in a business domain. In both cases, schemas are best developed by first modeling in a high-level language such as ORM and then mapping the model to the required lower-level notation. For a discussion of mapping ORM to XML schema, see Bird et al. (2000).

## Artificial Intelligence

Since the phrase was first coined in the 1950s, artificial intelligence (AI) has been promoted as a breakthrough that could revolutionize technology. Early approaches to AI were dominated by the idea that knowledge could be expressed in terms of logical expressions that used data values through a systematic procedure. Although some successes were reported, crafting such systems proved to be difficult, and the resulting systems were generally not sufficiently robust to deal with real-world data.

In the 1990s, attention started to turn to “connectionist” approaches. Instead of a human-centric analysis of data to identify logical relationships, systems were trained on data from the application domain. This developed an internal model of patterns in the training data that could then be deployed against new data. One feature of this approach is that it may not be easy to explain how a system has arrived at a particular result. But this is no different to the way that humans operate. For example, most native speakers of a language produce results that can be judged as grammatically correct, even though the person may not be able to explain the grammatical “rules” that are being followed.

A major leap forward was created when these ideas were applied to very large data-sets. This provided a solution to the robustness problem: how to deal with a wide range of situations. Instead of painstakingly trying to analyze each situation that can arise, a very large dataset can contain examples of all situations that can arise. Sophisticated learning algorithms can be applied to the data to build a capability sometimes referred to as “general AI”. The large amount of computing required is supported by very large databases (including the kinds discussed earlier in this chapter) and special-purpose processors to carry out the many repetitive operations in an efficient way.

Although general AI holds tremendous promise, it has not yet become a regular feature of database creation and management. All the major vendors are investing heavily in its application, in addition to many start-up companies with a focus on specific features. Here, we’ll limit ourselves to describing some of the areas where AI has obvious relevance, and in some cases is already being applied.
