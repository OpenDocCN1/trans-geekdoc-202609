
If the property does not exist, it will be created. An existing property can be deleted completely by removing it. This is equivalent to setting the relevant table cell to null in a relational database.

```
match ( c:Customer { companyName: "Tamale Spice" } )
remove c.country
```

A complete node (or set of nodes) can be deleted along with all associated properties using appropriate filter conditions.

```
match ( c:Customer )
where c.country = "Mexico"
delete c
```

This will have the effect of deleting all data for Customers located in Mexico, and of course:

```
match ( x ) delete x
```

could delete all nodes in the database, so it's important to get the filtering conditions correct.

## Comparison With Relational Databases

Table 17.2 lists some comparisons between the two database types (taking Neo4j as representative of graph databases).

### Table 17.2 Comparison of relational and graph databases.

| Relational database | Graph database |
|---|---|
| Tables | Labels |
| Rows | Nodes |
| Columns | Node or Relation properties |
| Primary keys | Uniqueness constraint on node properties |
| Foreign keys | Relations |
| "Join" or "Link" tables | Relations: columns become properties of the relation |
| Static data typing | Dynamic data typing |

To illustrate the differences in structure between the two approaches, we can look at a typical customer-order-product scenario. This is similar to the well-known “Northwind” example database, but only a few properties are shown here to make the model more compact.

Fig. 17.9 shows a fragment of the table structure. The OrderDetails join table is used to resolve the many-to-many relationship that exists between Orders and Products.

| Customers | | Orders | | OrderDetails | | Products |
|---|---|---|---|---|---|---|---|
| PK | customerId | PK | orderId | PK1 | orderId | PK | productId |
| | customerName | | customerId | PK2 | productId | | productName |
| | region | | orderDate | | quantity | | unitPrice |
| | ... | | ... | | ... | | ... |

FIG. 17.9 Customer-order-product relational structure.

The graph database equivalent of this structure that contains the same information is shown in Fig. 17.10. The properties associated with each element are shown for clarity. Note that there is no need for an OrderDetails node type between Orders and Products. In the graph model, each Order-Product combination is a separate relation, and the associated quantity value is simply a property of that relation.

![](img/1344db3eba3d550e6edb009556fcd95c_934_0.png)

FIG. 17.10 Customer-order-product graph structure.

Assume that we need to know the names of all customers who have ordered the product “Tofu”. In the relational case, we can express this in SQL using the following query:

```
select distinct customerName from Customers
join Orders on Customers.customerId = Orders.customerId
join OrderDetails on Orders.orderId = OrderDetails.orderId
join Products on OrderDetails.productId = Products.productId
where Products.productName = "Tofu"
```

Here, the distinct keyword is used to avoid duplicates if the same customer has ordered the product more than once. The equivalent query in Neo4j can be expressed in the Cypher language as follows:

```
match ( c:Customer ) - [ :PURCHASED ] -> ( :Order ) - [ :ORDERS ] -> ( p:Product )
where p.productName = "Tofu"
return distinct c.companyName
```

In the Cypher query, the variables c and p are bound to nodes with labels Customers and Products, respectively. No bindings are required for Orders nodes or the two relationships.

## Mapping ORM to a Graph Database

Chapter 11 discussed the mapping of an ORM model to a relational structure and presented a systematic procedure (Rmap) to produce a redundancy-free relational design. We'll now consider the possibility of an equivalent approach for a graph database.

Fig. 17.11 shows a simple ORM model (constraints omitted, as discussed later) and a comparable graph model showing node labels. Leaving aside the obvious differences in graphical notation, it's clear that the two models are very similar in structure.

At this simple level, it appears that an ORM model could potentially be taken as a direct definition of a graph schema. Unfortunately, things become more complicated when we get into the detail. The first difficulty is that graph databases can only represent binary relationships.

![](img/1344db3eba3d550e6edb009556fcd95c_935_0.png)

FIG. 17.11 Comparison of simple ORM and graph structures.

An ORM fact type of any other arity must be mapped to something structurally different in a graph model.

A unary fact type can be mapped to a graph property (normally a node property) or a binary relationship in a fairly straightforward way. Ternary or higher fact types must be remapped to binary relationships, perhaps involving multiple binary relationships for one ORM fact type. This may require additional constraints to preserve the intent of the original ORM model.

However, this raises the next difficulty, which is that graph databases generally provide very limited constraint options. In Neo4j, the only options are uniqueness and nonnull constraints (although a few more are available in the Enterprise Edition). It may be possible to work around these by taking care in the framing of create or update statements to preserve an appropriate structure, but for many ORM constraints, the only realistic solution is to implement the constraints in the application, not in the database.

A final difference in capability is the notion of subtypes. It is certainly possible to express subtyping notions in graph form, for example:

```
( :Species ) – [ :IS_MEMBER_OF ] -> ( :Genus ) – [ :IS_MEMBER_OF ] -> ( :Family ) ...
```

but the relationship is not distinguished in any way from other types of relationships. Similar considerations about absorption, separation, and partitioning arise when deciding if subtypes can be combined under one label or if different node labels are preferable. Any constraints involved in an ORM subtype relationship face the same issues as n-ary relationships and may need to be enforced in the related application code.

Despite these difficulties, the similarities between an ORM schema and a graph schema remain strong, and it’s possible to outline a systematic procedure for ORM-to-graph mapping, which we could call Gmap. This could run on similar lines to the Rmap procedure, following a series of steps to coerce the result into the appropriate form.

This is best illustrated with a concrete example. Chapter 11 discussed the application of the Rmap procedure to several models, including the TV channel model reproduced here as Fig. 17.12. This can provide the basis for a useful comparison between the two approaches. This model shows a number of features that must be accommodated in any possible Gmap procedure.

Any one-to-one fact type can be resolved by combining the two object types so that one becomes a property of the other. Which object type should be considered the “parent” is usually obvious from the model, but in some cases an arbitrary choice must be made. In this model, we can make Frequency a property of Channel and ProgramTitle a property of Program. This is essentially the same strategy as in the Rmap procedure.

![](img/1344db3eba3d550e6edb009556fcd95c_936_0.png)

FIG. 17.12. An ORM schema for TV channels (repeated from Fig. 11.30).

The TimeSlot object type in the ORM model has a composite identifier: Day and Hour. Composite identifiers may be difficult to replicate in a graph database, so it might be necessary to introduce a surrogate identifier. In this case, we could form a timeSlotCode by concatenating Day and Hour, but it’s not necessary because the TimeSlot is only relevant in the context of a particular Program.

Fact types with spanning uniqueness constraints will become relations in the graph model. For ternary or higher constraints, a choice must be made as to the best labels to use as the two ends of the relation because relations can only be binary in the graph model. The other roles will become properties of the relation. For the quaternary fact type in this model, we can set a relationship between Survey and Channel, with Category and Rating as properties.

Objectified fact types also map to relations, with any functionally dependent fact types indicating properties of the relation. This will apply to “Office” and “Department” in this case. A functional dependency between two objectified fact types introduces a further complication, to be discussed shortly.

Fact types with functional roles attached to the same object type can be grouped into the same node type (label), becoming properties of the “parent”. In this model, the Money-Amount object type can become a “worth” property of a Channel node and an “assets” property of a Company node.

The result so far is summarized in Fig. 17.13. In this figure, tentative node labels are shown in bold, and properties of nodes and relations are shown in italics to make the distinctions clearer.

![](img/1344db3eba3d550e6edb009556fcd95c_937_0.png)

FIG. 17.13 Initial modification of the TV channel model.

We can immediately see a problem. A relation must be between two nodes and cannot be between a relation and a node. We can resolve the problem by moving the DepartmentKind relationship to Suburb. Recall that a graph schema is never created explicitly, as it is simply a high-level summary of labels for nodes and their relationships created in the database.
