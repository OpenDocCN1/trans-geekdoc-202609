Six points to be noted for this example may be summarized as follows:

+   1. The _id field has been automatically generated to provide a unique identifier for each document. For simplicity, we'll ignore this feature in subsequent examples.
+   2. The names of the same fields in different documents need not be consistent. The activeDate field in the first document and the startDate in the second document may refer to the same business concept, but they do not have the same field name.
+   3. The data types for the same field need not be the same in different documents. The customerId field is alphanumeric in the first document, but numeric in the second document.
+   4. Fields can be multivalued and can also contain other documents, as with staffAllocation in the two documents.
+   5. The internal structure of each document in a collection need not be the same. The staffAllocation field is a list in the first document, but an object (in the JSON sense) that contains multiple lists in the second document.
+   6. Different documents in the same collection need not contain the same fields. The contractType field appears in the second document but is absent in the first document.

This kind of flexibility is sometimes claimed as a great advantage of document databases over the relational alternative, where each row in a table (equivalent to each document in a collection) has a fixed structure with defined data types for each column (equivalent to each field in a document). While this flexibility makes it easy to add documents without worrying about any kind of schema, it makes other operations on such an uncontrolled database an almost impossible task to manage. Even something as simple as retrieving the value of a particular field could require an examination of the collection to determine all variants of the field name to write a sufficiently robust query. In the example above, listing all the dates when contracts began would need to query for both startDate and activeDate (and any other name variants that might have been used).

It is possible to add a validator to a collection to constrain the documents it contains to an acceptable structure. This can include checks for mandatory fields, data types, value ranges, and so on. In effect, a validator can provide something like a schema for an individual relational table.

Write operations for a document are atomic, as the document is either written in full or not at all. Writes involving multiple documents can be transactional, but this involves some additional effort. A session must be created for each update, and then the sessions must be combined so that all the updates are completed together or not at all. This is the same whether the collections are physically stored together on the same server or distributed over multiple servers. Such operations have a big impact on performance, and the general recommendation is to adjust the schema to avoid this situation if possible. For example, instead of a transactional update to collection A and to collection B, it may be possible to define a new AB collection so that the update can be handled by a single write operation.
