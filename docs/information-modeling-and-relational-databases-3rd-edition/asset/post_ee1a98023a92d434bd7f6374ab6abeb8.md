
## 15.9 Process Models, Databases, and ORM

We are not limited to operating only at this level because, as we have seen, we can compose collections of low-level elements into higher-level elements until we reach a more convenient level of expression. However, this still leaves the realization underconstrained, as there could be many ways of linking data to process for the same conceptual design. The choices between the alternatives are somewhat orthogonal to the conceptual elements. For example, are we building a self-contained or distributed system operating over a network? How many users do we intend to support? Are we concerned about issues such as availability and scalability? The additional information required is what might be termed the *technical architecture* of the system, which is more concerned with the engineering aspects. In principle, given a definition of the technical architecture of a system, we should be able to generate the necessary system elements required from a business model. We have already seen how this could work in examples such as Executable UML. In the future, we can expect similar ideas to be widely adopted as a natural out-growth of conceptual modeling.

BPMN provides a standard notation and semantics for process descriptions. It has support for defining the execution of business processes but can be used to define processes at a purely conceptual (implementation-independent) level. Equivalently, ORM supports information modeling at a conceptual level, so we have the capability of defining both business information and business activities in a consistent way. But although both BPMN and ORM produce valid business models, neither approach makes any reference to the other in their basic forms. In this section, we will see how these two viewpoints can be reconciled.

The BPMN standard provides two elements relating to data along with the ability to associate them with activities, summarized in Fig. 15.36.

| Data Object | Represents temporary data that exists in a process instance while it is running. When the process instance terminates, the data object disappears. |
| --- | --- |
| Data Store | Represents an item of information that is stored persistently outside the process. When the process instance terminates the information remains. Note that the reference is to an item of information in some data store, not an entire data store or any specific data store. |

Because an ORM model generally specifies information that is intended to be stored (not temporary variables that are used then discarded), the BPMN Data Object is not relevant to a BPMN-ORM linkage. This leaves the Data Store reference as the only way of representing persistent information in a BPMN model.

A BPMN Data Store reference is linked to an Activity (usually a Task) by a Data Association. In BPMN, associations are generally used to link artifacts to process elements and are shown with a single dotted line (dashed lines have a different meaning). Associations can have an arrowhead showing the directionality of the association, but the semantics of this for a Data Store are a little ambiguous in the BPMN specification. Access to a database is usually a request-response cycle, so it's uncertain what an arrowhead would be indicating. The sensible option is therefore to use an association with no arrowhead.

The only textual notation provided for the Data Store reference is its name, which can be shown inside the icon or near it. A name alone is obviously not sufficient to define an adequate ORM linkage. A possible BPMN-compliant supplement would be the use of a Text Annotation linked to the Data Store, which could be used to add arbitrary text to a BPMN diagram. Text Annotations have no significant limitations or format requirements, and so a convention could be established for describing the linkages between Activities and Data Stores in a way that precisely locates the relevant areas of an associated ORM model. However, this would add considerable clutter to the BPMN diagram.

This exhausts the graphical options in BPMN, but a Data Association also has attributes that are not displayed on BPMN diagrams. One of these is "assignment", which identifies one or more data elements involved in the transfer from source to target. Potentially, this provides a point at which references to an ORM model could be stored, but these would only be visible in the BPMN tool being used to manage the process model and not to anyone viewing the graphical representation of the process from a business perspective. Such attributes are intended to facilitate process automation and have little relevance to modeling at a conceptual level.

An alternative approach is to introduce an intermediate stage between the BPMN model and the ORM model, forming a Process-Information Bridge (PIB). The Data Store reference can then be to a PIB element containing the relevant ORM linkage. One data item can be used in multiple activities in a process, so this also provides a location to resolve the one-to-many relationship. Fig. 15.37 shows the relevant diagram notation.

Next, we can turn to the ORM end of the relationship. In ORM (as opposed to an Entity-Attribute model), the attributes (properties) of the entity are unbundled and can be addressed in terms of separate fact types. "Entities" are formed from collections of fact types in a mapping process that produces a new model of a type defined by the mapping (for example, a relational model).

Although the unbundling of entities in ORM potentially offers a finer-grained definition of a relationship between activity and information, it is not necessarily convenient for cross-referencing of the kind we are considering. An activity is likely to require all information about an entity to be treated together rather than as isolated facts. For example, an agent updating stored data about personnel would probably expect to see all relevant information about a particular employee to be displayed at the same time. Instead of referring to individual fact types, it would be much simpler if the fact types were arranged in convenient bundles related to major entity types.

A straightforward way of achieving this is to group fact types into relations, in the sense originally expressed by Codd. Facilities already exist in ORM to produce normalized relations from an ORM model with the Rmap procedure. In a conceptual model, there is no prior commitment to a relational database solution, but this does not matter because normalized relations can be realized in other types of data structures such as XML and JSON; see Chapter 16 for more details.

A convenient data reference to a group of fact types in an information model can therefore be made by simply using the (unique) name of the relation. Accessing a particular data item during the execution of a process would require the relation name plus a key value that is unique within the relation. The same activity may access different instances of the relation in different instances (executions) of the process. However, only the relation's name is necessary to define the linkage between a process model and an information model.

Each PIBRef will contain the following:

- An indicator showing the type of CRUD access intended in this case. The usual access will be either Read-only, where the activity is not expected to change the data, or Full, where the activity can view the data and possibly also change it. These can be indicated by a single letter (R or F, where F is a shorthand for CRUD). In the unlikely event of more specificity being necessary, then the individual letters of CRUD can be used.

- The identification of the ORM elements involved in this case, using relation names. More than one relation could be used in the same PIBRef. For example, an activity might involve reading from one relation and updating another.
