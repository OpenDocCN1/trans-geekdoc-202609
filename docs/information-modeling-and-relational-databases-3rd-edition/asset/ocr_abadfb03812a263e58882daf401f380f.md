**Schema design.** Produce an initial schema design from a natural language description of a given domain. In the relational case, strict normalization could be enforced.

**Query design.** For a given database type and schema, write a query in the appropriate technical language to return results that have been expressed in natural language.

**Application design.** Produce a design based on a given database schema for an application described in natural language. This could include both desktop and mobile variants.

**Database Management.** Automation of routine operations that are normally carried out by a database administrator (DBA). These can include tasks such as index creation and updating, query tuning for evolving usage, performance assessment and optimization, and more.

**Data cleansing.** Historical data is often plagued with problems related to the original data capture that can obstruct subsequent analysis. Training on typical problems can be used to avoid or repair these issues.

**Code creation.** Technical code (in some given language) can be created from a description of the intent in nontechnical language. This is already operational as a “copilot” functionality in some development environments.

**Schema migration.** As the usage of a database evolves, it may become apparent that the schema originally envisioned is no longer appropriate. Migration to an alternative schema is a complex process that can be aided by automation.

**Advanced analytics.** The business-relevant information in the data can be processed to uncover patterns and trends that are not obvious through traditional queries.

The kinds of AI applications mentioned above often rely on a response to a prompt defining the necessary focus for the AI. Creating the appropriate prompt is at present a skill, but a skill that itself will surely become amenable to AI in time. The one area that cannot be determined by AI is what is, or is not, relevant to the user (often referred to as the UoD in an ORM context), and the user’s view of how the objects in the UoD are related. In some sense, the UoD could be seen as the ultimate prompt that cannot be reduced to anything else and cannot be defined without user knowledge. Clearly, an AI agent must understand the UoD to be effective, but how can that information be supplied? An obvious solution is provided by an ORM schema. It is certainly possible to describe a UoD through an informal discourse, but such descriptions are plagued by well-known ambiguities. Creating an ORM schema can sometimes be a painful process for a business (internal politics, unclear direction, etc.), but the eventual prize is an unambiguous description of the business intent. Once this is adopted by the business, it can be used as the basis for many facets of subsequent AI processing.
