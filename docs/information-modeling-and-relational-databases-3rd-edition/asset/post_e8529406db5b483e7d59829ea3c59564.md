
There is an equivalent dichotomy when we consider the relationships between objects. In the relational database case, this is defined at the table level with foreign key references, perhaps to “join” or “link” tables for many-to-many relationships. This cements the relationship at the type level. In a graph database, relationships are defined between nodes at the instance level, which does not depend on the multiplicity of types, so relationships between instances are simply relationships.

This has implications when we consider the kinds of relationships that can be accommodated in a database. In the relational case, all instances (rows in a table) must comply with the same relationship structure, but in the graph case, different nodes with the same label could have different relationships. Comparing this back to a relational system, it’s as though each row in a table could have its own individual foreign key references that differ from other rows in the table. The graph approach provides great flexibility to express complex relationships, but complicates the documentation needed to allow subsequent explorations of those relationships.

Another difference is the approach to data typing. SQL defines a range of data types, and all values in a table column are constrained to be of one specific type such as int, char, float, and so on (or perhaps null if a value is absent). In the community edition of Neo4j, the properties of nodes and relations are not preconstrained to a particular data type. Values have a type (string, integer, and so on) but properties do not, so, for example, a property may hold an integer value that later gets updated to a string value.

## Graph Database Queries

Data querying in a graph database involves retrieving information from the graph by specifying patterns of nodes and relationships that match the desired data. Graph databases typically have their own query languages optimized for graph traversal and pattern matching, and Neo4j provides a language called Cypher.

Queries in a graph database often involve matching specific patterns of nodes and relationships. Cypher can be used to specify patterns, filter nodes based on properties, and include or exclude relationships based on certain criteria. Data can be retrieved using the match keyword, which is roughly the equivalent of select in SQL. The following query returns all the properties for a particular Customer node.

```
match ( c:Customer {customerID:"ABCDE"} ) return c
```

Indexing can be used to allow faster lookup of nodes and relationships based on specified properties, although this has the usual effect of slowing updates.

Cypher queries can include conditions based on node and relationship properties. This allows data to be filtered based on the values of attributes associated with nodes and relationships in a similar way to SQL, for example, by using a where clause. Results can also be organized in a similar way to SQL, for example, by using an order by clause. Aggregation functions are available to summarize data across nodes and relationships, again in a similar way to SQL using functions such as count( ), sum( ) and avg( ).

A particular strength of graph databases is the ease of graph traversal, which involves navigating from one node to another through relationships to find data that matches certain criteria or patterns. Paths between nodes can be specified as a fixed length or a variable length with specified limits. A library of functions is provided to implement many graph algorithms, such as breadth-first and depth-first search, shortest path, page rank, and others. Queries of this kind are much harder to implement in a relational database.

Before data can be entered into a relational database, it must first be populated with tables, which, in turn, will have been created in accordance with some schema. A graph database does not require this kind of preparation, as nodes and edges can simply be added as needed. In a sense, we could say that the schema of a graph database emerges from the create, update, and delete operations carried out on it.

This should not be taken too far. A completely ad hoc approach can lead to a database that does not give reliable results and is impossible to maintain. One of the important benefits of a schema is that it defines a vocabulary for a given application area so that all participants can communicate in a consistent way. For example, we could have the following facts in a graph database:

- Holmes – WATCHED -> Watson
- Holmes – OBSERVED -> Watson
- Holmes – NOTICED -> Watson
- Holmes – RECOGNIZED -> Watson

Each of these could be a plausible record of some event. Listed together in this way, the problem is obvious, but in practice, the individual entries could be made by different people at different times who may not be aware of other data that has been entered. Can we query the database to confirm that Holmes SAW Watson? Not according to this data!

## Populating a Graph Database

In SQL, objects are created by an insert statement that adds the relevant values to a table. Relationships are created in the same way by inserting the destination key in the source table, so no separate insert is required. In a graph database, nodes and relations are separate items and so are created separately.

The following example shows the general style of node creation:

```
merge ( :Customer { customerId: "ABCDE" } )
```

This creates a node with a label (i.e., node type) of Customer with a given property. The individual node can be identified by using the customerId property in any subsequent queries. The keyword create can be used in place of merge, the difference being that if a matching node already exists (in this case, a Customer node with the same customerId), merge will do nothing but create will introduce a duplicate node. A constraint can be added to enforce uniqueness of a property value. Adding the constraint automatically creates an index on the unique property.

```cypher
create constraint cust_id_uniq for (c:Customer)
require c.customerID is unique
```

In a relational database, the absence of a value is indicated by a null in the relevant table cell. In a graph database, null has a slightly different interpretation. Properties do not have null as a value; null just indicates that the property doesn’t exist. This means that nonexistence and null are equivalent for properties of nodes and relationships. A property can be constrained to be not null, which in Neo4j is equivalent to saying that it must exist.

```cypher
create constraint cust_existence for (c:Customer)
require c.customerID is not null
```

The combination of uniqueness and existence constraints on a property provides something roughly equivalent to a primary key in a relational database.

The same merge or create keywords are used to insert relations. The Cypher notation allows the direction of the relation to be specified, as in the following example:

```cypher
merge (:Customer {customerID:"ABCDE"}) -[:PURCHASED]-> (:Order {orderID:12345})
```

This will create the specified Customer and Order nodes together with a directed PURCHASED relationship between them. Adding a relationship between two existing nodes requires a slightly different strategy. We first find the relevant nodes by querying the database, and then use references to those nodes in creating the relationship, as in the following example.

```cypher
match ( c:Customer { customerID:"ABCDE" } )
match ( o:Order { orderID:12345 } )
merge ( c ) - [ :PURCHASED ] -> ( o )
```

For large datasets, batch insertion methods can be used to insert multiple nodes and relationships in a single transaction. Utilities are also provided for the bulk import of data from external sources, such as CSV files or other databases.

## Updating and Deleting

One of the most common update operations is modifying the properties of nodes and relationships. The relevant nodes or relationships can be found through a query, and the update applied to the results of the query. As with creation, batch update methods can be used to update multiple nodes and/or relationships in a single transaction. The following example shows a simple Cypher update data in a graph database:

```cypher
match ( c:Customer { companyName: "Tamale Spice" } )
set c.country = "Mexico"
```

Here, the variable c is bound to a specific Customer, and its country property is then set to the specified value. If the property value already exists, it will be replaced by the new value.
