As for external uniqueness, external frequency constraints have an underlying join path. If the joins involve optional roles, inner joins are assumed. For example, the external frequency constraint in Fig. 10.4 applies only to politicians who are coregents, so verbalizes as **For each Country, there are at most 2 instances of Politician such that that Politician is a coregent and serves on the government of that Country.**

Recall that ORM *set-comparison constraints* apply a subset, equality, or exclusion constraint between compatible role sequences. Sometimes one or more of these role sequences are projected from a join path. As a simple example, the join subset constraint in Fig. 10.5(a) runs from the role pair comprising the Advisor serves in Country fact type to the role pair comprising the first roles of the Advisor speaks Language and Country uses Language fact types.

The constraint means that the set of advisor–country pairs populating the serves-in predicate must be a subset of the set of advisor–country pairs obtained by projecting on the advisor and country roles of the join path Advisor speaks Language **that** is used by Country.

The join path in Fig. 10.5(a) involves a conceptual inner join on Language, equating instances playing its two roles. In other words, if an advisor serves in a country, then that advisor must speak at least one language used by that country. This constraint may be verbalized formally in ORM as **Each Advisor who serves in some Country also speaks some Language that is used by that Country.**

Like ER, UML has no graphic notation for expressing a join subset constraint, but does allow the constraint to be expressed textually in a note attached to the relevant model elements (in this case, the three associations), as shown in Fig. 10.5(b). ER could also be adapted to allow such usage of notes.

Fig. 10.5(c) shows another example discussed earlier in the book. The constraint may be verbalized in ORM thus: **If some Employee has some PersonTitle that is restricted to some Gender then that Employee is of that Gender**. A sample population illustrates the title-gender restriction.

The title-gender restriction can't be expressed in UML if we model personTitle as an attribute. However, it can be modeled in UML if we model PersonTitle as a class and attach a note for the restriction, as shown in Fig. 10.5(d). The note attached to the Employee class captures the title-gender restriction formally in OCL.
