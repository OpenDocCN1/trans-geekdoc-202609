
Selection is handled through a find() function, which contains the query criteria expressed as a JSON object. For example, we find relevant documents in a Courses collection as follows:

```
db.Courses.find( { creditValue: { $gt: 12 } } )
```

In this example, $gt is a query operator used to specify “greater than”, so the function would return Courses with a credit value greater than 12. Other common query operators include $eq, $ne, $gt, $lt, $in, $exists, etc.

Projection allows fields to be included or excluded in the query results using projection. A parameter is used to specify the fields to be included (1) or excluded (0).

```
db.Courses.find( {}, { courseName: 1, _id: 0 } )
```

In this example, the names of courses would be returned, but the associated _id field would be suppressed.

Query results can be sorted based on one or more fields. The sort() method specifies the fields to sort and the sort order, either ascending (1) or descending (-1).

```
db.Courses.find( ).sort( { creditValue: -1, courseName: 1 } )
```

Aggregation provides the ability to perform data transformations and calculations. The aggregation function can be applied in a simple way, as in the following.

```
db.Courses.aggregate( [ $avg { "$creditValue" } ] )
```

This provides the average creditValue for all Courses. However, the aggregate function is much more powerful than this because it can contain a “pipeline”, a list of operations arranged so that the output of one operation becomes the input to the next operation. This allows complex operations combining grouping, summing, sorting, averaging, and so on. A typical sequence might be:

```
$project -> $match -> $group -> $sort
```

nested within the aggregate() function.

In general, we can see that the functionality available is similar to that provided by relational systems, though realized differently. The attractions of the document model include flexibility in the representation of data and the possibilities for partitioning. Against this must be set issues such as the need to maintain the consistency of replicated data and the complexity of transactions involving multiple documents.

Document databases are an obvious choice where the data to be stored can be visualized in terms of groups of values that share a common theme or purpose. This is certainly the case where the database is being used to store the electronic equivalent of traditional business documents such as statements, application forms, specifications, and so on.

Other application areas where document databases are popular include:
- Content management systems (CMS), used to store and manage various types of material such as articles, images, videos, and metadata used in support of websites and other applications.
- Management of catalogs, also directories or listings such as business directories, real estate listings, and online marketplaces, which can benefit from the ability to store diverse data structures within a single database.
- Storing user profiles and preferences to enable personalized experiences in applications such as social networks, online forums, and streaming platforms.
- Managing healthcare information such as patient records, medical histories, test results, and treatment plans that form well-bounded units of information.
- E-commerce platforms, used to manage product catalogs, user profiles, customer reviews, and order histories while providing flexibility to accommodate changing product attributes and relationships.

## 17.5 Graph Databases

Graph databases use a property graph model to represent and store data. The basic graph structure consists of nodes and relationships (edges). Each node represents an entity, object, or data point, and each relationship represents a connection or association between two nodes.

Nodes are the fundamental units of a property graph. Each node can have one or more properties that store data attributes or characteristics associated with the node. For example, in a social network graph, a node could represent a person, and node properties could include attributes related to that person.

Relationships define the connections or associations between nodes. They represent the links or interactions between entities. Relationships can also have properties that provide additional information about the connection. For instance, in a social network graph, relationships might represent “friendship” connections between people, and relationship properties could include the date the friendship was established.

Properties are key-value pairs associated with both nodes and relationships. They store specific attributes or data values related to the corresponding node or relationship. For example, a node representing a person might have properties such as “name”, “age”, and “email”.

Graph databases offer several advantages over relational databases, especially when dealing with highly connected and complex data structures. In a relational database, it’s possible to imagine a connection between a pair of tables by following the relationships between intermediate tables. However, if the two tables are widely separated (i.e., there are many intermediate tables), then the query becomes complex, and the cost of the multiple joins can be significant. Traversing relationships in a graph is a direct operation, which makes querying for highly connected data very fast. As the size of the graph grows, graph databases maintain consistent performance, making them scalable solutions for applications with expanding relationships.

Graph databases typically have a flexible schema, allowing nodes and relationships to have different properties without strict constraints. This adaptability can be beneficial in scenarios where the data model evolves over time, as changes can be made without altering the entire schema, which can be cumbersome in a relational database. Relationships between data points are stored directly, making the data model more intuitive and easier to work with when the relationships are the primary focus of the application. They also represent hierarchical data structures (which are common in some domains) in an efficient way.

The schema flexibility in graph databases makes them well suited for scenarios where data models are subject to change, relationships are dynamic, and applications require adaptability and agility in data representation. However, a more flexible schema implies fewer constraints in the database, and so structure and constraints may need to be defined through the application logic, rather than through a centralized schema definition enforced by the database itself.

In terms of database products, Neo4j is often considered the market leader, partly due to its early adoption and strong ecosystem. Amazon Neptune also has a notable presence due to its integration with other AWS services. Other graph databases such as ArangoDB, JanusGraph, and Stardog have their own niches and user bases, and some are able to integrate with other types of NoSQL systems such as document and column-oriented databases.

To provide some concrete examples of graph database features, we'll use Neo4j (www.neo4j.com). Its underlying graph processing engine is optimized for traversing and navigating graphs efficiently, making graph traversals and pattern-matching operations fast and scalable. It uses a language called Cypher to write graph queries and to carry out the usual CRUD types of operation. An Enterprise Edition provides advanced facilities for commercial operation, but we will focus on the facilities provided by the Community Edition.

Unlike other types of NoSQL databases, graph databases do not lend themselves to horizontal partitioning. The entire database resides on a single server, so as the database grows the server must be scaled vertically. Performance can be improved by providing a server cluster so that different read operations can be directed to different servers in the cluster to share the load, but updates are made through a master that then replicates changes to other servers in the cluster. Within a server, Neo4j supports ACID transactions to ensure data integrity and consistency.

Although there are some high-level similarities between relational and graph databases, the differences are considerable at the detail level. In the relational case, the most fundamental element is a table, whereas in the graph case, it is a node. However, these correspond to different kinds of concepts. A relational table relates to a particular type of object, but a graph node relates to an instance of a type. The notion of a node type certainly exists in graph databases; in Neo4j, it is referred to as a “label”.

All nodes with the same label can be assumed to have similar properties. If a property value is unknown (or not relevant), a relational database will hold a NULL in the corresponding cell of the table. In the graph database equivalent, the property will simply not exist (i.e., NULLs are not stored).
