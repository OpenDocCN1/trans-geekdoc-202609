A particular strength of graph databases is the ease of graph traversal, which involves navigating from one node to another through relationships to find data that matches certain criteria or patterns. Paths between nodes can be specified as a fixed length or a variable length with specified limits. A library of functions is provided to implement many graph algorithms, such as breadth-first and depth-first search, shortest path, page rank, and others. Queries of this kind are much harder to implement in a relational database.

Before data can be entered into a relational database, it must first be populated with tables, which, in turn, will have been created in accordance with some schema. A graph database does not require this kind of preparation, as nodes and edges can simply be added as needed. In a sense, we could say that the schema of a graph database emerges from the create, update, and delete operations carried out on it.

This should not be taken too far. A completely ad hoc approach can lead to a database that does not give reliable results and is impossible to maintain. One of the important benefits of a schema is that it defines a vocabulary for a given application area so that all participants can communicate in a consistent way. For example, we could have the following facts in a graph database:

+   Holmes – WATCHED -> Watson
+   Holmes – OBSERVED -> Watson
+   Holmes – NOTICED -> Watson
+   Holmes – RECOGNIZED -> Watson

Each of these could be a plausible record of some event. Listed together in this way, the problem is obvious, but in practice, the individual entries could be made by different people at different times who may not be aware of other data that has been entered. Can we query the database to confirm that Holmes SAW Watson? Not according to this data!

# Populating a Graph Database

In SQL, objects are created by an insert statement that adds the relevant values to a table. Relationships are created in the same way by inserting the destination key in the source table, so no separate insert is required. In a graph database, nodes and relations are separate items and so are created separately.

The following example shows the general style of node creation:

```
merge ( :Customer { customerId: "ABCDE" } )
```

This creates a node with a label (i.e., node type) of Customer with a given property. The individual node can be identified by using the customerId property in any subsequent queries. The keyword create can be used in place of merge, the difference being that if a matching node already exists (in this case, a Customer node with the same customerId), merge will do nothing but create will introduce a duplicate node. A constraint can be added to enforce uniqueness of a property value. Adding the constraint automatically creates an index on the unique property.
