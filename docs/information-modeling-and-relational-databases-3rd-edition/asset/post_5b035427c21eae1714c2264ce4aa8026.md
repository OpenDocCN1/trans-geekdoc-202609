## 17.4 Document Databases

In Chapter 3, we discussed how reports and other documents can be analyzed and expressed in terms of elementary fact types. Modeling these fact types in ORM, along with the relevant constraints, leads to a model that can form the basis for a database schema. Document databases take a different approach by storing documents directly using their original structure, so, as the name suggests, a database of this type consists of collections of documents. Because no preanalysis of documents is necessary, it seems possible to add any kind of document to any collection without any kind of preparation. In principle, this promises a great deal of flexibility, but in practice, some degree of control is required to have any hope of making the database manageable over its lifetime.

Several document database systems are available, including the following: MongoDB is one of the most popular document databases. It stores data in flexible, JSON-like documents and allows for dynamic schemas. Couchbase is a distributed NoSQL database that offers high performance and scalability. It’s commonly used for applications requiring real-time data updates, caching, and mobile synchronization.

CouchDB is an open-source document database focused on ease of replication and conflict resolution. Document databases are available from cloud service providers such as Amazon DocumentDB and Google Firestore. Finally, MarkLogic is a NoSQL database that supports flexible schema design and stores data in XML or JSON documents. It’s commonly used for applications that require complex data modeling and querying. The examples in this chapter are based on MongoDB, though other document database systems have broadly similar capabilities to the ones we will discuss.

Documents are typically expressed using the structural capabilities of JSON, previously described in Chapter 16. Internally, the information storage may adopt BSON, a binary form of JSON that incorporates additional metadata to make data scans faster and can also reduce storage requirements, but we will ignore this detail.

A document database is formed from collections. Each collection contains documents of a similar kind: for example, Products, Orders, Customers, and so on. Each document can contain several fields, but the data in a field need not be single-valued as it would be in a normalized relational database—a field can contain a structure that, in turn, can contain other structures and so on. There is a rough correspondence between these concepts and their relational equivalents, as shown in Table 17.1.

Table 17.1 Comparison of RelationalDB and Document DB concepts.

| Relational DB | Document DB |
|---|---|
| Table | Collection |
| Row | Document |
| Column | Field |

To illustrate some features of this type of structure, the following example shows two documents from a hypothetical Contracts collection:

```
Contracts: [
  {
    _id: ObjectId("6481d941f682789c3b8d71ef"),
    contractRef: 9876,
    activeDate: "Jan 1 2024",
    customerId: "DE876",
    staffAllocation: [ { person: "Alice123", hours: 15 },{ person: "Bob456", hours: 35 } ]
  },
  {
    _id: ObjectId("64820117f682789c3b8d71f0"),
    contractRef: 8765,
    startDate: "Jan 12 2024",
    customerId: 2024002,
    staffAllocation: {
      marketing: [ { person: "Carol999", hours: 5 } ],
      operations: [ { person: "Bob456", hours: 5 }, { person: "Dave666", hours: 30 } ]
    },
    contractType: "FP"
  }
]
```

Six points to be noted for this example may be summarized as follows:

- 1. The _id field has been automatically generated to provide a unique identifier for each document. For simplicity, we'll ignore this feature in subsequent examples.
- 2. The names of the same fields in different documents need not be consistent. The activeDate field in the first document and the startDate in the second document may refer to the same business concept, but they do not have the same field name.
- 3. The data types for the same field need not be the same in different documents. The customerId field is alphanumeric in the first document, but numeric in the second document.
- 4. Fields can be multivalued and can also contain other documents, as with staffAllocation in the two documents.
- 5. The internal structure of each document in a collection need not be the same. The staffAllocation field is a list in the first document, but an object (in the JSON sense) that contains multiple lists in the second document.
- 6. Different documents in the same collection need not contain the same fields. The contractType field appears in the second document but is absent in the first document.

This kind of flexibility is sometimes claimed as a great advantage of document databases over the relational alternative, where each row in a table (equivalent to each document in a collection) has a fixed structure with defined data types for each column (equivalent to each field in a document). While this flexibility makes it easy to add documents without worrying about any kind of schema, it makes other operations on such an uncontrolled database an almost impossible task to manage. Even something as simple as retrieving the value of a particular field could require an examination of the collection to determine all variants of the field name to write a sufficiently robust query. In the example above, listing all the dates when contracts began would need to query for both startDate and activeDate (and any other name variants that might have been used).

It is possible to add a validator to a collection to constrain the documents it contains to an acceptable structure. This can include checks for mandatory fields, data types, value ranges, and so on. In effect, a validator can provide something like a schema for an individual relational table.

Write operations for a document are atomic, as the document is either written in full or not at all. Writes involving multiple documents can be transactional, but this involves some additional effort. A session must be created for each update, and then the sessions must be combined so that all the updates are completed together or not at all. This is the same whether the collections are physically stored together on the same server or distributed over multiple servers. Such operations have a big impact on performance, and the general recommendation is to adjust the schema to avoid this situation if possible. For example, instead of a transactional update to collection A and to collection B, it may be possible to define a new AB collection so that the update can be handled by a single write operation.

### Linking Data

Inserting, retrieving, and managing individual documents is relatively straightforward, but in any realistic database, there will almost certainly be a need to link different documents together. This can be seen as the equivalent of foreign key references in a relational database. There are two ways of achieving this in a document database. To provide some examples, assume that we have (highly simplified) documents relating to students and their grades in university courses.

The first approach to linking courses and students with customers is embedding. In general, if Document1 needs to be linked to Document2, this can be achieved by nesting one document within the other. In this example, we’ll assume that the Course document contains the Student details.

```
{
 "Courses": [
 {"_id": "DB102",
 "courseName": "Databases",
 "creditValue": 15,
 "Students": [
 {"studentId": "12345", "name": "Abby Akbar", "grade": 3.4},
 {"studentId": "67890", "name": "Bill Briggs", "grade": 3.2}
 ],
 },
 {"_id": "SW101",
 "courseName": "Python",
 "creditValue": 10,
 "Students": [
 {"studentId": "12345", "name": "Abby Akbar", "grade": 3.8}
 ]
 }
 ]
}
```

It would also be possible to embed a list of Courses into a Student document, using the standard JSON structuring. Which of these would be preferable depends on the anticipated usage of the data. In this case, although we have two different kinds of information (Courses and Students), we end up with only one document collection: either Courses (as above) or Students, depending on how we decided to embed the documents.

It’s clear that embedding the data in this way will result in redundancy, corresponding to denormalization in a relational database. Given the falling cost of hardware, the need for additional storage space might be acceptable. More serious is the problem of maintaining consistency.
