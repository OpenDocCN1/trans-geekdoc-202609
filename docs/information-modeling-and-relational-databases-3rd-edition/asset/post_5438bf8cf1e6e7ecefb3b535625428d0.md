
Using “∃” (read “there exists some”) for the existential quantifier, we recursively define the path predicate P (read “has a path to”) to give the transitive closure of R and then use it to define the relation R as acyclic:

```
∀x,y (xPy iff [xRy or ∃z (xRz & zPy)])
R is acyclic iff ∀x ~xPx
```

Fig. 7.20(a) shows an intuitive icon for acyclicity, with the bar indicating that no cycles back are allowed. A simplified version of this icon (without arrow tips) is used for the _acyclic constraint_ symbol, as shown in Fig. 7.20(b). ORM 1 uses the alternative acyclic constraint symbol Oac.

Cycles may contain one or more links. Asymmetry is just the special case of acyclicity with two links in the cycle. Because _acyclic implies asymmetric_, if a role pair is declared acyclic, then don’t declare it asymmetric.

In Fig. 7.20(c), the population of the parenthood relation is both acyclic and intransitive. The two ring constraints are combined into a single icon, as shown. A homogeneous binary relation can be displayed as a graph, using named nodes for the objects and arrows for the relationship instances, as in Fig. 7.20(d). This makes it visually obvious whether a given population forms an acyclic relation.

Recall that the graph of a subtype family is directed and acyclic. Because of their recursive nature, acyclic constraints may be expensive or even impossible to enforce in some database systems. In SQL, they can be implemented using the recursive union operator, and they are easily enforceable in logic programming languages. In other systems, recursive constraint checks might be left to data entry operators to do manually.

A ring predicate R is _strongly intransitive_ if and only if ∀x,y,z[(xRy & yPz) → ~xPz], where the path predicate P (read “has a path to”) is recursively defined to give the transitive closure of R. For example, ignoring incest and reincarnation, the relation Person is an ancestor of Person is strongly intransitive. The strong intransitivity constraint is depicted with an extra dot to the intransitivity icon (see Fig. 7.21).

Of all the ring constraints, irreflexivity is the least expensive to enforce. With expensive constraints such as acyclicity, _incremental checking_ (for violations of the current update request, assuming the previous population is consistent with the constraint) is typically much cheaper than full checking.

The set of acyclic relations forms a proper subset of the set of *asymmetric relations*, so acyclic relations must be asymmetric. An intransitive relation must be irreflexive, and an asymmetric relation is irreflexive and antisymmetric.

The symmetry constraint may be combined with intransitive or irreflexive constraints. Other properties of ring relations may apply (e.g., connectivity) but are not discussed here. ## 7.4 Other Constraints and Rules

Having covered most of the main graphical constraints in ORM, we now consider three more graphical constraints: object cardinality, role cardinality, and value-comparison constraints. We then discuss basic textual constraints and derivation rules. More advanced graphical and textual rules are discussed in Chapter 10.

The hash symbol “#” denotes cardinality. Simple cardinality constraints are displayed by prepending “#” to the cardinality restriction, thus “#≤n” (at most n), “#=n” (exactly n), “#≥n” (at least n), “#n..m” (at least n and at most m).

An object cardinality constraint restricts the cardinality (number of members) of the population of an object type for each database state. The cardinality constraint “#=12” in Fig. 7.22(a) means there are always exactly 12 jury members. Equality settings like this are rare, as most databases start with the empty state, which would violate the constraint.

In Fig. 7.22(b), the “# ≤100” means there are at most 100 senators in each database state. Object cardinality constraints apply to the populations of the types rather than the types themselves. Over a long period, the total number of jury members or senators who ever filled these positions could be much higher.

A role cardinality constraint restricts the cardinality of the population of a role for each database state. The role cardinality constraint “# ≤ 1” in Fig. 7.22(c) means there is always at most one employee playing the director role. Note that ORM cardinality constraints are not the same as so-called “cardinality” constraints in entity-relationship modeling (ER), which instead correspond to frequency and/or mandatory role constraints.

Cardinality constraints are rarely included on diagrams because they are often implied by existing value constraints or frequency constraints. For example, an {‘M’, ‘F’} value constraint on Gender(.Code) implies “# ≤ 2” on Gender. If there is at most one senate, then a frequency constraint of ≤100 on Senate’s role in Fig. 7.23(b) implies the # ≤100 cardinality constraint on Senator. Note, however, that the cardinality constraint # ≤1 on Senate is still required.
