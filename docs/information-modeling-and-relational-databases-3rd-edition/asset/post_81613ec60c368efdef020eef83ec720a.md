
The XML definition is controlled by the World Wide Web Consortium (W3C). Several other W3C standards exist within the XML family. In addition to XML Schema, we have already discussed XPath and XQuery in some depth. These allow XML data to be queried in a way that corresponds roughly to the way that the **select** statement is used in querying SQL tables. Other W3C standards include the following:

XSLT (Extensible Stylesheet Language Transformations) is an XML-based language used to convert an XML document into a different XML schema or into a completely different format such as PDF.

XLink (XML Linking Language) provides methods for creating internal and external links within XML documents and associating metadata with the links.

XPointer is based on XPath and supports addressing into the internal structures of XML documents. This can be used to create something equivalent to a foreign key in a relational database.

XHTML is a somewhat stricter version of HTML with a syntax conforming to XML.

SVG (Scalable Vector Graphics) is a language for describing two-dimensional vector graphics that allows smooth scaling to different display resolutions.

There are many other XML-based standards produced by W3C and other bodies, perhaps running into hundreds of examples, as well as an uncountable number of private applications. This makes XML probably the most well-established method of defining structured data outside of a database system.

XML is a text format, and although it can be manipulated using text processing operations, it is more effective to use processing operations that are sensitive to the data structure being expressed. Database systems first started using XML as a text format, but recognition of its value led to its incorporation as a native data type in the SQL standard. Most database vendors have added features to store XML data, operate on XML data, and convert backward and forward between XML and relational table structures, sometimes including proprietary extensions that are not part of the official SQL standard.

JSON is a slightly younger language than XML. It was originally developed as a relatively lightweight communication language between web servers and browsers, using standard browser facilities instead of auxiliary plug-ins. This made JavaScript an obvious starting point for the definition of a markup language, and so JavaScript objects became the basis for the notation.

A major factor in the popularity of JSON is its simplicity and ease of processing compared to XML. It is a more compact format that reduces the bandwidth required for the transmission of data; this is an important factor given the reasons for its creation. It is also a better fit with web-related technology in general, relevant, for example, in application development. Against that, it is somewhat less expressive than XML. It has no support for namespaces, and it is unsuitable in applications where precise definition of data types is important. However, its adoption as the primary structuring principle in document databases and its incorporation into SQL as a native data type show that it is sufficiently robust to meet the demands of a wide range of real-world scenarios.

XML and JSON will continue to coexist for the foreseeable future because one is not a direct replacement for the other. It's tempting to caricature XML as heavyweight and JSON as lightweight solutions to data structuring outside of a data store, but this blurs some of the important features of each. It's certainly true that there is a large middle ground where either could be employed effectively, and any choice between them would be made on factors other than their data structuring capabilities.

The SQL standard has been adopted by the International Standards Organization (ISO) as ISO/IEC 9075. Copies can be ordered from ISO or via national standards organizations such as ANSI. Because of its size (several thousand pages in total), the standard is split into several parts. Part 2 (Foundations) and Part 14 (SQL/XML) are the most relevant to this chapter.

The relevant XML standards are being progressed through the W3C. Full details, including the current versions of the standards themselves, can be found at www.w3c.org. The standards documents are not particularly easy to read, but a large amount of more readable tutorial information is available. XQuery especially is still relatively unfamiliar to many database practitioners, but it seems likely to become progressively more important in utilizing heterogeneous data. Useful introductions can be found in Walmsley (2015) and Melton and Buxton (2006).

JSON arrived as a data format later than XML, but it is now established as an essential component in data management. A short introduction to JSON can be found in Basset (2015). Because of its origins in JavaScript, its standardization falls under ECMA, the same body responsible for the specification of the JavaScript language (now sometimes referred to as ECMAScript). A comprehensive description of JavaScript is given in Flanagan (2020). Copies of standards and further details can be found at www.ecma-international.org. JavaScript and JSON are covered in standards ECMA-262 and ECMA-404, respectively. The latter has also been adopted as an ISO standard (ISO/IEC 21778). JSON Schema is still a work in progress, but the latest status can be found at www.json-schema.org. For further details on JSONPath, see Gössner and Bormann (2021).

XML and JSON functionality is now included in major relational databases but because of variations between different implementations, the vendor's documentation is often the most useful resource. Most commercial systems provide online help that can be searched in various ways.

### 17.1 The Growth of the NoSQL Movement

Following the publication of E.F. Codd’s ground-breaking relational paper in 1970 (Codd, 1970), it was not until the 1980s that commercial relational database systems became widely available. Since that time, they have become the dominant data storage model. Other data resources are used at smaller scales, such as spreadsheets, text files, and so on, but for large-scale data, relational systems have reigned supreme.

The NoSQL movement started to emerge in the 2010s in response to perceived shortcomings in the relational approach (Leavitt, 2010). It’s worth noting straight away that “NoSQL” is not a particularly good choice of name. The crucial point is not really an issue with the structured query language (SQL). In fact, some NoSQL vendors try very hard to provide languages that are as similar as possible to SQL. Instead, NoSQL approaches rely on data models that are nonrelational to provide their distinctive features. There are some suggestions that “NoSQL” should be interpreted as “Not Only SQL”, but this would include every kind of database, rendering it completely meaningless.

The driving forces behind the movement did not result from a failure of the relational model as such but from new challenges and opportunities exposed by the general evolution of technology. The following trends are especially relevant:

- The cost of data storage has fallen dramatically. In the 1980s, there was a preoccupation with minimizing storage requirements because of the expense of the hardware involved. Today, consumers are commonly offered services that include gigabytes of free data storage space, which would have been unthinkable in earlier times. The decreasing incentives to minimize storage have contributed to the continual increase in database sizes.
- There is now a much greater understanding of the value of data. Even something as simple as a validated relationship between a person and their email address has a cash value. This has motivated organizations to collect as much data as possible, even if there appears to be no immediate use for the information.
- Relational databases evolved at a time when “client-server” was the dominant information system architecture. This naturally led to databases that served a limited internal pool of interests. Most organizations now recognize the advantages of being able to transfer data between disparate systems, both internally within the organization and externally with customers, suppliers, partners, and so on. This has been facilitated by interchange formats such as eXtensible Markup Language (XML) and JavaScript Object Notation (JSON), as discussed in Chapter 16.
- Since its public appearance in 1990, the Internet has grown by several orders of magnitude. Fast and reliable network connections are now widespread, and connectivity is taken for granted in most of the world. Many websites (and the databases that support them) have millions of users rather than the hundreds that would be considered a large user population in the 1980s.
- The day-to-day operations of most organizations are now reliant on some kind of information technology (IT) platform that facilitates data exchange within and without the organization. Growth in general data usage has been explosive. To a large extent, this has been fueled by today’s extensive use of smartphones. In other words, most people carry a computer and communication device with them all the time and do not need to be tethered to a static business system. For example, the publication of street maps has virtually collapsed because most people will now get the relevant map (accessing a remote database) via their phone.

As these trends have evolved, they have exposed database systems to new challenges and opportunities. Rising to these has raised questions about the best way to organize data resources, perhaps by deviating from the relational model that has been the standard for so long.

Before diving into more detail about NoSQL, it will be useful to review some selected database characteristics to provide a context for discussion to follow. For this chapter, we’ll assume that some important factors that might be relevant to choosing a database solution are equally balanced among all candidates. These include features such as security, ease of installation, documentation, vendor reputation, support, and so on. Our focus here will be on aspects that are important in discussing the distinction between relational and nonrelational databases.
