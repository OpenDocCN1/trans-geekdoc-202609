
If more than two predicates are mutually exclusive, it's more efficient to simply list them after the DisjointProperties header, for example,

```
ObjectProperty: gotFirstPlaceIn
ObjectProperty: gotSecondPlaceIn
ObjectProperty: gotThirdPlaceIn
DisjointProperties: gotFirstPlaceIn, gotSecondPlaceIn, gotThirdPlaceIn
```

If two predicates must always have the same instance populations, they are said to be (materially) equivalent. This is the same as declaring a subPropertyOf relationship in both directions. In Manchester syntax, equivalence between predicates is declared by listing the predicates after the EquivalentProperties header.

For example, an ORM pair-equality constraint to ensure that people drive a car if and only if they own the car (this constraint actually applies in some taxi companies) may be specified thus: EquivalentProperties: owns, drives.

Another use of equivalent properties is to support synonyms for predicate readings in the same document (or different documents), for example, EquivalentProperties: worksFor, isEmployedBy. A third use of equivalent properties is to specify derivation rules for derived predicates.

## Functional, Inverse, Mandatory, and Key Relationships

By default, all OWL predicates are optional and many-to-many (m:n). Although the predefined predicates for equating and distinguishing individuals have unrestricted domains and ranges, user-defined predicates typically have at least one domain and at least one range explicitly declared. This is always the case for relationships declared in information modeling approaches such as ORM, ER, and UML.

Fig. 18.24(a) depicts two ORM fact types. The fact type Politician was born in Country is a many-to-one (n:1) association (each politician was born in at most one country, and many politicians may be born in the same country). Both roles are optional as our knowledge might be incomplete. The fact type Politician heads/is headed by Country is 1:1 (each politician heads at most one country, and each country is headed by at most one politician).

Fig. 18.24(b) depicts the ORM schema in OWL using Manchester syntax. OWL confusingly uses the term “property” to mean predicate. Hence, an n:1 predicate is called a functional property. A functional predicate is declared as an object property, and then its functional nature is declared by including Functional as one of its characteristics. Knowledge of functional properties enables OWL tools to make useful inferences. For example, given:

```
Individual: Terry
Facts: wasBornIn TheLuckyCountry, wasBornIn Australia
```

we may deduce:

TheLuckyCountry SameAs Australia.

ORM treats an elementary fact type as a set of one or more typed predicates. In Fig. 18.24(a), the head of government fact type has a forward predicate reading “heads” as well as an inverse predicate reading “is headed by” directed from Country to Politician (a slash “/” separates forward and inverse readings).

![](img/1344db3eba3d550e6edb009556fcd95c_1001_0.png)

```
ObjectProperty: wasBornIn
Domain: Politician
Range: Country
Characteristics: Functional
ObjectProperty: heads
Domain: Politician
Range: Country
Characteristics: Functional, InverseFunctional
InverseOf: isHeadedBy
```

OWL allows you to declare one predicate to be the inverse of another using the owl:inverseOf predicate. In Manchester syntax, you prepend “InverseOf:” to the inverse predicate, for example, ObjectProperty: isaChildOf InverseOf: isaParentOf.

Functional and inverse functional declarations apply globally to the predicate in all contexts. OWL cardinality constraints, however, apply only locally to the domain classes being introduced in a local context. This local nature of cardinality restrictions differs markedly from the usual approach in information modeling.

*OWL does not allow an inverse to be declared for a data property, partly because it never allows a literal to be the subject of a predicate. This is unfortunate because we may wish to talk about literals.*

Consider the data property Person misspelt Word. OWL does not allow us to declare its inverse Word wasMisspeltBy Person. Moreover, OWL does not let us assert the fact type Word is a synonym for Word. To work around such problems in OWL, you have to cheat, for example by treating Word as an entity type rather than as a value type (literal type).

Consider the fact types Person is in Country and City is in Country. In information modeling approaches such as ORM, ER, and UML, the two is in predicates would be treated as different predicates/relationships/associations. However, in OWL we may treat these instead as different occurrences of the same predicate, simply by assigning them the same IRI.

*OWL does not allow a data property to be declared inverse functional. In practice, many data properties are either 1:1 or 1:n, thus requiring a uniqueness constraint on the role played by the literal. Although we can’t declare uniqueness constraints on roles played by literals as inverse functional characteristics, we can specify such constraints in OWL 2 using HasKey declarations.*

In Fig. 18.24(a), politicians are identified by their name and countries by their country codes. The ORM diagram depicts this compactly using parenthesized reference modes, but internally these are expanded to the injective (mandatory, 1:1) reference relationships Politician has PoliticianName and Country has CountryCode.

Unfortunately, the HasKey feature only partly addresses the need to specify identification schemes (simple or compound) for entity types because HasKey captures only the inverse functional nature of the data property.

The name choice “HasKey” for this feature is somewhat misleading, as it is weaker than the notion of “key” in relational databases. To fully capture the identification scheme, we need to explicitly declare the data property to be both functional and mandatory.

In Manchester syntax, the mandatory role constraint that each Politician has a name is expressed by using the SubClassOf property to declare that Politician is a subclass of those things that play the subject role in the hasPoliticianName predicate with a minCardinality of 1 (or more), as follows:

```
Class: Politician
SubClassOf: hasPoliticianName min 1.
```

A maxCardinality of 1 may be declared in a similar way using max 1, which is another way to declare that the predicate is functional. If minCardinality = maxCardinality, you can set both at once using exactCardinality. For example, the 1:1 reference scheme for Politician may be declared in OWL 2 as follows:

```
Class: Politician
SubClassOf: hasPoliticianName exactly 1.
HasKey: hasPoliticianName
DataProperty: hasPoliticianName
Domain: Politician
Range: PoliticianName
```

Now, consider the ORM schema in Fig. 18.26(a). In the fact type Employee drives Car, the drives predicate is optional and m:n. The two textual constraints in FORML add a restricted mandatory role constraint (see constraint footnote 1) and a restricted uniqueness constraint (see constraint footnote 2). Here, the drives predicate is functional only with respect to NonExecutive, not Employee. We should not declare drives as a FunctionalProperty because that would then apply to all employees (and any other subjects of the drives predicate in an OWL version of the model). These restricted constraints may be declared in OWL using qualified cardinality restrictions, as shown in Fig. 18.26(a) using Manchester syntax.

In practice, it is very rare to encounter explicit declarations for minCardinality = 0 and minQualifiedCardinality = 0 because these apply by default, so they may be ignored.
