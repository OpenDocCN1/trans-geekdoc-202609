In this case, serializing the data into physical storage might look something like the following:

```
1, Alice, 2, Bob, 3, Clare, 4, Dave, 5, Edna, 1, glutenfree, 4, vegan, 1, 68, 2, 92, 4, 66, 5, 78
```

At this simple level, we can’t see the specific detail of the data layout in persistent storage. This depends very much on the specific database being considered. Even so, it’s obvious that in one case, a retrieval will find colocated information for an entity and the other will find colocated information for an attribute. Another way of saying this might be that row-oriented retrieval gets values for the attributes of an entity, but column-oriented retrieval gets values for the entities of an attribute.

Consider a query to find the average person’s weight from this information. The relational case would require the retrieval of each row and the weight column value within the row before calculating the average value. In the column-oriented case, we simply need to retrieve the weight row in the table shown in Fig. 17.8 to get all the necessary values for the calculation. Because data retrieval from persistent storage is the most time-consuming part of the operation, this shows that the column-oriented approach has the potential for much better performance on certain types of queries. Performance is probably the greatest single motivator for this type of database, especially as the database becomes larger. In a column-oriented database, increasing amounts of data result in rows becoming bigger, not a bigger number of rows, so these are sometimes referred to as “wide tables”.

It’s important to remember that the distinctive feature of a column-oriented database is the way that the information is stored physically. From a conceptual viewpoint, we could still think of the database in the traditional manner, but we would find some types of operation more efficient and others less efficient than in a standard normalized relational database. In some cases, column-oriented databases can be queried using standard SQL, making the “NoSQL” label a little bit pointless.

The advantages of column orientation are only valid if queries operate on one column or a small number of columns. Queries involving several columns get less benefit from the localization of information from a single column. If multiple columns are frequently used together, it’s possible to add another level of organization by grouping columns into column families. For example, columns related to individual customer details (such as name, address, date of birth, etc.) could be grouped into a “Personal” column family. This can be used to ensure that the relevant columns are colocated in the database.

Column orientation provides additional opportunities for efficient storage of information. All the data from one row-oriented column (visualized as a row in a column-oriented database) is of the same type, opening possibilities for applying various types of compression to the values. An obvious instance of this is when the column contains many duplicate entries such as URLs or product names. In some cases, it may be possible to compress a column sufficiently to fit in memory for direct access, dramatically improving response time. Compression is useful because column-oriented databases are often used with very large datasets. There is also no need to allow for NULLs. An empty cell in a row-oriented database simply does not need to exist in its column-oriented equivalent.

The design of a column-oriented schema needs to consider not only the information to be stored but also how the database will be used and how it might evolve in the future. Adding a new column to the database is very easy—it can just be appended to the existing columns without impacting any existing queries. Other types of schema changes may be more problematic. Changes to query patterns can also reduce the effectiveness of the database if its design has been optimized for an anticipated scenario that no longer applies. It is also more difficult to design effective indexing schemes in the column-oriented case.

Column-oriented databases are very much skewed toward improving the efficiency of read operations (select in SQL). Operations such as insert (a new entity), update (an attribute of an existing entity), and delete (an existing entity) are generally slower because of the way the information is spread in physical storage. Also, read operations are improved only for certain types of queries. Consider the following two SQL queries:

```
**select avg(weight) from Person**
**select * from Person**
```

In a column-oriented database, the first of these will be faster but the second will be slower than the row-oriented equivalent (obviously, the differences will only be meaningful in large datasets). Generally, row-oriented operations or those involving many columns will be slower in a column-oriented database, making them unattractive for transactional applications.

Joins between tables in a column-oriented database are more complex than in the row-oriented case and are likely to have a lower performance. An alternative strategy is to consider the usage patterns of the database and define a schema that “prejoins” the relevant tables. This obviously requires additional controls to ensure the integrity of the duplicate data that will inevitably result, but the new table can then be treated in the same way as any other table with respect to a columnar arrangement. The risk here is that this optimization will make the database perform very badly if the usage patterns do not turn out to be as expected.

A major advantage of column-oriented databases is their ability to deal with very large datasets. Their structure lends itself very well to partitioning. An obvious first step is to partition the database vertically so that different columns (or perhaps column families) can be mounted on different servers. There is no need for each of these to be of the same type. Columns that are accessed less frequently can be mounted on less-powerful servers.

Within each vertical partition, there are options for further partitioning in the horizontal direction. A column can be split into shards, which, again, can be mounted on separate servers. Some additional effort is required to direct queries to the relevant shard, but this provides the potential for a huge expansion of capacity.

An additional measure to increase performance is replication: copies of the same data can be stored on multiple servers that can be accessed independently. This requires some kind of automated load-balancing mechanism to share queries evenly among the servers. A concern in replication is maintaining consistency between different copies of (what should be) the same data. However, as already noted, column-oriented databases are most applicable in situations with rare updates but frequent queries. Because updates are scarce in such cases, the consistency problem may be easily manageable in the right type of application.

The following characteristics summarize the features that are likely to be important in an application requiring a column-oriented database:

- Large amounts of data are involved, corresponding to millions of rows in more traditional row-oriented tables.
- Efficient use of storage is relevant, for example, in dealing with large amounts of sparse or repetitive data.
- Database operations are dominated by queries, with few (if any) changes to data once loaded.
- Queries typically use aggregation functions such as avg(), count(), min(), max(), and sum().
- Each individual query involves only a small number of columns.
