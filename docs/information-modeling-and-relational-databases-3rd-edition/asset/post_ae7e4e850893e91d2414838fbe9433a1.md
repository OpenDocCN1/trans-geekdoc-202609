
Individual: Romulus Facts: isaSiblingOf Remus

we may infer

Individual: Remus Facts: isaSiblingOf Romulus.

In ORM, constraining a predicate to be symmetric means that the asserted fact population must be symmetric. For example, if we assert that Romulus is a sibling of Remus, then we must also assert that Remus is a sibling of Romulus (both facts are stored). In OWL, however, you can assert just one of these facts and have the other fact inferred. To do that in ORM, you would provide a derivation rule for inferring the converse rather than constraining the fact type to be symmetric.

For example, in ORM you could declare the fact type Person is a sibling of Person to be semiderived, meaning that some of its instances may be asserted and some may be derived, and use the following rule to derive the converse facts: Person1 is a sibling of Person2 if Person2 is a sibling of Person1. In this case, you would constrain the siblinghood fact type to be irreflexive, but not symmetric.

A ring predicate R is asymmetric if and only if, for each individual x and y (not necessarily distinct), if xRy then it is not the case that yRx. In other words, if the relationship applies, then its converse cannot apply. For example, the parenthood relation is asymmetric because if one person is a parent of another, then the second person cannot be a parent of the first.

OWL object property expressions are declared asymmetric by characterizing them as asymmetric. To do this in Manchester syntax, we declare “Asymmetric” as a characteristic. For example, isaParentOf predicate may be declared to be asymmetric in OWL, as shown below.

```
Class: Person
ObjectProperty: isaParentOf
Domain: Person
Range: Person
Characteristics: Asymmetric
```

Note that if a predicate is asymmetric, it is automatically irreflexive as well (consider the definition of asymmetry for the case where x = y). Although asymmetry implies irreflexivity, the converse does not apply. For example, isaSiblingOf is irreflexive but not asymmetric.

If the above asymmetric constraint has been declared and we assert that Ann is a parent of Bill, then any attempt to add the fact that Bill is a parent of Ann would render the OWL ontology inconsistent.

A ring predicate R is transitive if and only if, for each individual x, y, and z (not necessarily distinct), if xRy and yRz then it is also the case that xRz. For example, the ancestor-hood relation is transitive because if one person is an ancestor of another, and the second person is an ancestor of a third person, then the first person is an ancestor of the third person.

Ignoring reincarnation, the ancestorhood predicate is actually acyclic (an object can never cycle back to itself by applying one or more ancestorhood facts). Unlike ORM, OWL does not support acyclicity constraints. However, OWL does allow object property expressions to be declared transitive by characterizing them as transitive. To do this in Manchester syntax, we declare “Transitive” as a characteristic. For example, isanAncestorOf predicate may be declared to be transitive, as shown below. For completeness, the asymmetric nature of the predicate is also declared.

```
Class: Person
ObjectProperty: isanAncestorOf
Domain: Person
Range: Person
Characteristics: Transitive, Asymmetric
```

In OWL, declaring the ancestorhood predicate to be transitive does not require that all its instances must be asserted. For example, if you declare the predicate to be transitive, and assert that Ann is an ancestor of Bill and that Bill is an ancestor of Chris, then the OWL engine can infer that Ann is an ancestor of Chris.

## Enumerated Types in OWL 2

Recall that OWL allows you to define a new class or datatype by specifying its intension (i.e., meaning) in terms of operations on classes or datatypes that are already declared. A type definition that specifies the necessary and sufficient conditions for an item to be a member of the type is said to be an intensional definition of the type. For example, intensional definitions for StudentEmployee and PassGradeNr may be declared in Manchester syntax as shown below, assuming that the types referenced (Student, Employee, GradeNr, FailGradeNr) have been previously declared.

```
Class: StudentEmployee
EquivalentTo: Student and Employee
Datatype: PassGradeNr
EquivalentTo: GradeNr and not FailGradeNr
```

The set of all possible instances of a type is said to be the extension of the type. If a class or data range is composed of a known, finite set of items, it may be defined by enumerating (i.e., listing) those items. For example, while EvenDigit could be defined intensionally as {x | x is a digit that is divisible by 2}, it could also be defined extensionally as a member of {0, 2, 4, 6, 8}. A type that is defined by enumerating its extension is said to be an enumerated type, and its definition is said to be an extensional definition. In Manchester syntax, the usual set notation is used to specify the extension, using braces as set delimiters and commas as element separators, such as.

```
Class: Weekday EquivalentTo: { Monday, Tuesday, Wednesday, Thursday, Friday }
Datatype: EvenDigit EquivalentTo: { 0, 2, 4, 6, 8 }
```

## "Value" Restrictions on Predicates

OWL uses the term “value” loosely to mean either an individual entity or a literal. Given this understanding, a named class or (unnamed) class expression may be defined as the subject of a predicate whose range is restricted to include one of the following three options: (1) some specific value; (2) some value from a specified class or data range; (3) only values from a specified class or data range. We consider these cases in turn.

In Manchester syntax, the set of all elements that relates via a binary relation R to the value v is expressed simply as “R value v”. As an example of option (1), if we treat Gender as an enumerated class of two individuals (male and female), the following OWL code defines MalePerson as the class of people who have male gender.

```
ObjectProperty: hasGender
Domain: Person
Range: Gender
Class: Gender
EquivalentTo: { male, female }
Class: MalePerson
EquivalentTo: Person and hasGender value male
```

In Manchester syntax, the set of all elements that relates via R to some value in a specified subrange D is expressed simply as “R some D”. As an example of option (2), the following OWL code defines CarDriver as the class of people who drive a car.

```
ObjectProperty: drives
Domain: Person
Range: Vehicle
Class: Car
SubclassOf: Vehicle
Class: Driver
EquivalentTo: Person and drives some Car
```

In Manchester syntax, the set of all elements that relate via R to some value in a specified subrange D only (if at all) is expressed simply as “R only D”. As an example of option (3), given the previous declarations for the drives predicate and Car subclass, the following OWL code defines CarOnlyDriver as the class of people who drive only vehicles that are cars. This subtype includes those people who drive no vehicles at all.

```
Class: CarOnlyDriver EquivalentTo: Person and drives only Car
```

## Property Chains in OWL 2

OWL 2 allows you to derive a new object property fact by composing two or more object property facts together in a chain, where the entity in the object position of one fact (other than the last fact) is also the subject of the following fact. In relational database work, this corresponds to performing an equijoin between two elementary relations and then projecting on the first and last attribute in the chain. In OWL, the equijoin operation is known as a *composition* operation, and an expression that composes two or more predicates is called a *property chain*.

To illustrate this notion, consider a business domain in which each person is born in at most one city (e.g., some people might instead be born in a village), and each city is located in exactly one country. One way of specifying this schema in OWL using Manchester syntax is as follows:

```
ObjectProperty: wasBornInCity
Domain: Person
Range: City
Characteristics: Functional
ObjectProperty: isLocatedInCountry
Domain: City
Range: Country
Class: Person SubClassOf: wasBornInCity max 1
Class: City SubClassOf: isLocatedInCountry exactly 1
```

Now, suppose we are also interested in knowing which countries people are born in. In ORM, we could add the semiderived fact type Person was born in Country, allowing some instances to be asserted and others derived using the derivation rule Person was born in Country if Person was born in some City that is located in that Country.

In OWL 2, we can specify the derivation rule by declaring the wasBornInCountry predicate to be a subproperty of the predicate formed by projecting on the start and end of the property chain that composes the wasBornInCity and isLocatedInCountry predicates. In Manchester syntax, the property chain is specified using the symbol “o” as the *composition operator* placed between adjacent predicates in the chain, and listed after the header “SubPropertyChain:”. Our current example may be specified in Manchester syntax by adding the following OWL code:

```
ObjectProperty: wasBornInCountry
Domain: Person
Range: Country
SubPropertyChain: wasBornInCity o isLocatedInCountry
```

The subproperty declaration is just a simple implication that applies to any satisfying models. OWL is not concerned with choices about how to actually implement implications. A property chain may compose multiple occurrences of the same predicate. For example, grandparenthood facts may be derived by composing two parenthood facts, as shown.

```
ObjectProperty: isaGrandparentOf
SubPropertyChain: isaParentOf o isaParentOf
```
