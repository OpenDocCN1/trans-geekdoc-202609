Relationships between data points are stored directly, making the data model more intuitive and easier to work with when the relationships are the primary focus of the application. They also represent hierarchical data structures (which are common in some domains) in an efficient way.

The schema flexibility in graph databases makes them well suited for scenarios where data models are subject to change, relationships are dynamic, and applications require adaptability and agility in data representation. However, a more flexible schema implies fewer constraints in the database, and so structure and constraints may need to be defined through the application logic, rather than through a centralized schema definition enforced by the database itself.

In terms of database products, Neo4j is often considered the market leader, partly due to its early adoption and strong ecosystem. Amazon Neptune also has a notable presence due to its integration with other AWS services. Other graph databases such as ArangoDB, JanusGraph, and Stardog have their own niches and user bases, and some are able to integrate with other types of NoSQL systems such as document and column-oriented databases.

To provide some concrete examples of graph database features, we'll use Neo4j (www.neo4j.com). Its underlying graph processing engine is optimized for traversing and navigating graphs efficiently, making graph traversals and pattern-matching operations fast and scalable. It uses a language called Cypher to write graph queries and to carry out the usual CRUD types of operation. An Enterprise Edition provides advanced facilities for commercial operation, but we will focus on the facilities provided by the Community Edition.

Unlike other types of NoSQL databases, graph databases do not lend themselves to horizontal partitioning. The entire database resides on a single server, so as the database grows the server must be scaled vertically. Performance can be improved by providing a server cluster so that different read operations can be directed to different servers in the cluster to share the load, but updates are made through a master that then replicates changes to other servers in the cluster. Within a server, Neo4j supports ACID transactions to ensure data integrity and consistency.

Although there are some high-level similarities between relational and graph databases, the differences are considerable at the detail level. In the relational case, the most fundamental element is a table, whereas in the graph case, it is a node. However, these correspond to different kinds of concepts. A relational table relates to a particular type of object, but a graph node relates to an instance of a type. The notion of a node type certainly exists in graph databases; in Neo4j, it is referred to as a “label”.

All nodes with the same label can be assumed to have similar properties. If a property value is unknown (or not relevant), a relational database will hold a NULL in the corresponding cell of the table. In the graph database equivalent, the property will simply not exist (i.e., NULLs are not stored).
