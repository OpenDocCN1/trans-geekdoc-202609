
Like any binary fact type, link fact types may be given predicate readings in both directions and role names. For discussion purposes, the example in Fig. 10.48 includes inverse predicate readings, role names, and a sample population. Note that the role names (acquirer, target) on the acquisition fact type provide role names for the Company roles in the link fact types.

ORM schemas may be navigated in relational style (using predicate names), attribute style (using role names), or a mixture of both. To navigate from Company to Acquisition, it matters which link fact type we use. For example, from the company Visio we may navigate via the left link to its acquisition of InfoModelers or via the right link to its acquisition by Microsoft.

![](img/1344db3eba3d550e6edb009556fcd95c_472_0.png)

Navigating via the left link, the schema path may be verbalized as “Company that is acquirer in Acquisition”. Navigating via the right link we have “Company that was acquired in Acquisition”. To navigate from Acquisition to company, it also matters which link we use. Navigating via the links, the schema paths may be verbalized in relational style as Acquisition that is by Company (navigation via left link); Acquisition that is of Company (navigation via right link).

Role paths may also be specified in attribute style, using role names for “attributes”. For example, to navigate from Company to Acquisition, we have the following two different options: Company.acquisitionBySelf (navigation via left link); Company.acquisitionOfSelf (navigation via right link). To navigate from Acquisition to Company, we have the following two different options: Acquisition.acquirer (navigation via left link); Acquisition.target (navigation via right link).

Although such expressions could be used to specify projections, here we use them simply to indicate a path obtained by jumping from an object type to one of its far roles. If the dot notation is replaced by the “of-notation”, then the component order is reversed (e.g., instead of Company.acquisitionBySelf we have acquisitionBySelf of Company).

In addition to purely relational and purely attribute styles, role paths may be specified using a mix of both styles (e.g., Company.acquisitionBySelf that occurred on Date). From an ORM perspective, it is all relational underneath.

UML provides no direct support for unary relationships, instead requiring their remodeling in terms of attributes or subclasses. ORM allows unary relationships to be objectified. Consider the unary fact: The President named “Abraham Lincoln” died. We may objectify this death using the normalization “that death” and declare the following additional fact: That death occurred in the Country with country code “US”. This natural way of communicating may be supported in a similar way to objectification of nonunary facts. An ORM model for this situation is shown in Fig. 10.49(a). Sample populations are included for the object types and fact types. Here, the unary fact type President died is objectified by the object type Death. This unary objectification is internalized using the expanded schema shown in Fig. 10.49(b).

![](img/1344db3eba3d550e6edb009556fcd95c_473_0.png)

Here, Death is a normal entity type with a simple reference scheme provided by its injective relationship to President (e.g., Abraham Lincoln’s death may be referenced by the definite description “The Death that is of the President who has the PresidentName ‘Abraham Lincoln’”). Hence, the result of objectifying a relationship type may be viewed as an entity type that has a reference scheme whose reference projection bears an equality constraint to the fact type being objectified.

This interpretation does not assume that the Death is of President relationship provides the only or even preferred way of referring to deaths (e.g., we may introduce a death number to reference deaths, without impacting this analysis).

The objectification of unaries as a case of situational normalization was introduced in ORM 2 (objectification of unaries was not supported at all in ORM 1). The fact-oriented version known as fully communication oriented information modeling (FCO-IM) introduced objectification of unaries to provide an alternative way to support existential facts and to treat all base objects as lexical in nature. With this approach, an entity (nonlexical object) is an objectification of a role played by a value (lexical object). In Fig. 10.50, for example, the entity type Country is derived by objectifying the unary fact type CountryCode refers to a country.

![](img/1344db3eba3d550e6edb009556fcd95c_474_0.png)

FIG. 10.50 In FCO-IM, nonlexical types objectify roles of lexical object types.

While the FCO-IM approach to objectified unaries encourages the use of natural reference schemes in modeling, and has tool support, we personally find it unintuitive and awkward in dealing with multiple inheritance, context-dependent reference schemes as well as changes to reference schemes. Nevertheless, some modelers favor this approach, so perhaps this is a subjective issue.

ORM 1 allowed objectification of 1:1 fact types as well as binary and longer fact types with a spanning uniqueness constraint. ORM 2 and UML also allow objectification of an n:1 (or 1:n) binary association, and a ternary or longer association whose longest uniqueness constraint spans exactly n-1 roles.

We exclude from consideration any n-ary association with a uniqueness constraint spanning fewer than n-1 roles because such an association is compound rather than elementary.

While NORMA allows objectification of fact types without a spanning UC, we feel this practice should be deprecated, as it can lead to confusion when populating fact types or declaring independence, and is typically better modeled in another way (Halpin, 2020).

We now recommend that *objectification of a fact type be restricted to fact types that are unary or have a spanning uniqueness constraint*.

The second edition of this book argued for objectification of a fact type with multiple uniqueness constraints to avoid forcing one to choose one of the UCs as the preferred way to identify the objectification. The simplest case is *objectification of a 1:1 fact type*, for example, the current marriage example shown in Fig. 10.51(a). Fig. 10.51(b) shows the UML version.

However, the 1:1 nature of the association means that an instance of CurrentMarriage may be identified by just the husband or just the wife, rather than the combination of husband and wife. Moreover, when mapping to SQL, each relational table must have a primary key, so one of the UCs in the binary fact type needs to be chosen as preferred for this purpose.

Entering the schema in Fig. 10.51(a) into NORMA generates two errors. NORMA automatically creates two *implicit 1:1 fact types* linking CurrentMarriage with Person using the fact type reading “Person involves / is involved in CurrentMarriage”, thus violating the rule that fact type reading must be unique within a given model.

The only way to fix this error is to drag the implicit fact types from the Model Browser onto the drawing window, and then edit the readings in the Fact Editor or Reading Editor. Fig. 10.51(c) does this as well as adding reference modes for Person and Date and the exclusion constraint that no person can be husband and wife.

The second error is that none of the UCs in the 1:1 fact types is marked as preferred, so CurrentMarriage has no preferred reference scheme. To fix this, we select one of the UCs in the Person is husband of /is wife of Person fact type and toggle its isPreferredIdentifier property from False to True.

The selected UC and the corresponding UC on an implicit fact type are then redisplayed with a double uniqueness bar. Choosing the left UC of the marriage fact type for this results in Fig. 10.51(c), which shows a screen shot from the NORMA tool.

Formally, there is an equality constraint between the pair of husband and wife roles of Person and the pair of roles in the marriage fact type in Fig. 10.51(c). However, instead of displaying this equality constraint, purely for performance reasons the NORMA tool internally treats the implicit roles of Person as “mirror roles” or role proxies whose population always matches the population of the roles they mirror (in this case, the roles in the marriage fact type).

![](img/1344db3eba3d550e6edb009556fcd95c_475_0.png)

FIG. 10.51 Objectifying a 1:1 association might be confusing.

Although CurrentMarriage is now primarily identified by the husband, NORMA requires the husband, wife combination to identify it when populating the fact type CurrentMarriage occurred on Date, as shown at the bottom of Fig. 10.51(c). This might be confusing, as the fact entry is not atomic and is inconsistent with the way the sample population editor works with normal fact types.

In this example, it is possible to record a current marriage without knowing the date of the marriage. This might confuse users who, by ignoring the implicit link fact types as in Fig. 10.51(a), think that CurrentMarriage is an independent object type because instances of it can exist without playing in the marriage date fact type. However, no objectification of a fact type with multiple UCs can be independent because in the link fact types, it plays a mandatory role in addition to the role in its preferred reference scheme.
