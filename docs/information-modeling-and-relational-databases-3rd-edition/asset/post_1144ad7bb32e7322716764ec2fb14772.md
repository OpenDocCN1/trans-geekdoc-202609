YAML is a popular choice for relatively short documents where data structure needs to be explicitly represented. Two examples are configuration files containing application data and the interchange of structured messages. It is not widely used for large data collections. Its ease of use is partly due to automated decisions about the intention behind a data value, which can lead to unexpected consequences. For example, some parsers may interpret the unquoted value **No** as the Boolean value *false*, which may not have been the original intention.

The most familiar markup language is probably *HTML*, used to define the structure of web pages. Unlike XML, the tags in HTML are predefined and have specific meanings defined in the HTML standard. In the early days of web usage, HTML was also used as a rather weak method of identifying some aspects of data structure, but this was clearly unsatisfactory. Like XML, HTML can seem clumsy and awkward for authors, and several alternatives have been developed. Some examples include the following.

- The cutely named *Markdown* is a lightweight language that is used to add formatting indicators to textual documents. The marked document can be used in various applications to generate publishing formats such as PDF and convert to other formats such as a complete static website. However, it is obviously limited in its capability to express data structures.

- *AsciiDoc* is a plain text equivalent to the XML-based DocBook format used for structured documents. Documents can be created simply using a text editor and then rendered to a desired final format, such as PDF, HTML, and many others.

- *MediaWiki* is another lightweight language designed for ease of use. As the name suggests, it was developed for the creation of Wiki pages and is the basis for Wikipedia. As with other languages of this type, its documents can be re-processed into many other formats, including HTML.

The main purpose of most of these languages is to define the structure of documents, not the structure of data. Although there is a certain amount of overlap, there is no pressing need to use these languages for data description when better alternatives are available. We will therefore not explore them any further in this chapter.

### 16.5 XML, JSON, and ORM

A question worth considering is whether object-role modeling (ORM) can be used to design an XML schema or a JSON schema, in much the same way that it can be used to design a relational schema. The answer is certainly “Yes”, but there are some additional considerations that are not relevant in the relational case.

As already mentioned, an ORM model can be represented in XML, and this indeed is the default file format used by the NORMA tool. The general structure can be outlined as follows:

```
<ORMModel>
  <Objects>
    <Object id = 123 ...> </ObjectType>
    <Object id = 456 ...> </ObjectType>
      ...
  </Objects>
  <Facts>
    <Fact id = 321 ...>
      <FactRole id = 789 ...> </FactRole>
      <FactRole id = 987 ...> </FactRole>
    </Fact>
      ...
  </Facts>
  <Constraints> ... </Constraints>
    ...
  <ORMDiagram> ... </ORMDiagram>
</ORMModel>
```

Each item has a unique identifier (UUID), and these are used to relate items together. For example, the object playing a fact role can be referenced from the role entity using its UUID.

Although this structure captures all the ORM model details, it does not provide a good template for a data model. Some of the content, such as the diagram information, has no relevance in defining a data structure, and items in the *.orm file such as object types and fact types are represented in ways that are intended to facilitate modeling operations, not data transfer. Instead, what is required is a mapping from the ORM model to an XML schema that accommodates the relevant data.

Mapping from an ORM model to a relational schema was discussed in Chapter 11. There are only a few possible options in the Rmap procedure, such as how to treat subtypes. The procedure is largely automatic, and two different developers mapping the same ORM model will generally produce the same relational schema. However, the situation is different for XML.

The first issue is that XML obliges us to represent the data as a hierarchy, even if no natural hierarchy exists in the ORM model. This is a consequence of the nesting of elements within elements, which is intrinsic to XML. Consider the tiny ORM model shown in Fig. 16.5.

One option would be to nest Courses under Students.

```
<Model>
  <Student name = "Alice" ...>
    <Course id = "CS101" .... ...</Course>
    <Course id = "CS104" .... ...</Course>
  </Student>
  <Student name = "Bob" ...>
    <Course id = "CS101" .... ...</Course>
  </Student>
</Model>
```

But nesting of Students under Courses could be equally valid.

```
<Model>
  <Course id = "CS101" ...>
    <Student name = "Alice" .... ...</Student>
    <Student name = "Bob" >.... </Student>
  </Course>
  <Course id = "CS104" ...>
    <Student name = "Alice" .... ...</Student>
  </Course>
</Model>
```

We could also consider something closer to a relational style, with a Student list, a Course list, and a list of linking Enrolment elements.

```
<Model>
<Students>
<Student name = "Alice" ...> ... </Student>
<Student name = "Bob" ...> ... </Student>
</Students>
<Courses>
<Course id = "CS101" ...> ... </Course>
<Course id = "CS104" ...> ... </Course>
</Courses>
<Enrolments>
<Enrolment student = "Alice" course = "CS101"> ... </Enrolment>
<Enrolment student = "Alice" course = "CS104"> ... </Enrolment>
<Enrolment student = "Bob" course = "CS101"> ... </Enrolment>
</Enrolments>
</Model>
```

Which of these would be preferable cannot be inferred from the ORM model because the choice depends on external factors such as the intended use of the data and patterns of access.

A second issue is that XML provides two options for storing data: as the value of an element attribute or as the content of an element. The examples above show student name as an attribute, but the following would be an equally valid alternative:

```
<Student>
<Name>Alice</Name>
...
</Student>
```

There is no firm rule for deciding between these options, although various guidelines have been suggested, such as reserving attributes for metadata only. Attributes have some limitations that would make elements preferable in some cases, for instance, data that is multivalued or has some inner structure, but for straightforward scalar values either approach could be used.

Although we have been describing the situation with XML, similar issues arise with JSON, which also offers choices about how to represent the data. What all this means is that two different developers mapping the same ORM model may produce very different XML schemas (or JSON schemas).

To produce an XML rendering of a relational structure, we can follow a systematic procedure that is straightforward to automate.

Each relational table will map to an element type in XML, which can have a plural tag name (e.g., <Employees>). Each of these major element types will be nested under a suitably named root node. These major elements will contain a list of subelements of the relevant type. Rows in a table will map to subelements with a singular tag name (e.g., <Employee>). nested under their parent element (e.g., <Employees>). Relational columns map to attributes of their related subelements. A UUID attribute can be added to each subelement for easy identification and cross-referencing.

The result is an XML file similar to the “relational” style in the examples above. Even if this is not the preferred format, it may still be a good first step. Once we have an XML file, it can be transformed into alternative XML structures using appropriate code, perhaps using the XML Stylesheet Language for Transforms (XSLT).

If we need to produce an XML file directly from an ORM schema, we can adapt the approach above by adding some extra steps. First, we follow the Rmap procedure to identify the relational structure corresponding to the ORM schema. Next, we apply the procedure above to this relational structure to define the XML schema elements. Finally, we need to add any required constraints from the ORM schema to the XML schema. This last step is not necessary when producing a data transfer file from a database because we can assume that the appropriate constraints will already have been applied to the data.

Mapping to a JSON schema can follow a similar procedure. Tables become JSON objects, rows become lists of nested objects within the parent types, and column values appear as key-value pairs within the nested object.

### 16.6 Summary

XML is a member of a family of markup languages based on the Standard Generalized Markup Language (SGML). Other languages based on SGML include HTML, though this has now diverged somewhat from its original basis. XML was designed to be easy to parse, initially in the context of web applications, but it is now well established as a general-purpose tool for describing data structure independent of any specific data container. It has become a built-in feature of many applications, though its presence may not be immediately obvious. As examples, the current formats of Microsoft Office files (such as *.docx, *.pptx, and *.xlsx) are based on XML, and the NORMA tool used to create and manage object relational models uses XML in its *.orm file format.

A key feature of XML is its extensibility. Unlike HTML, it does not assume predefined tag names, so a schema can be designed to meet any required scenario. If warranted, the schema can be documented in machine-readable form so that an XML document can be validated against the schema definition to ensure that it is consistent. The original schema definition method, inherited from SGML, used DTDs, which are expressed in their own language. Modern usage has moved to the expression of the schema in XML itself, using XML Schema Definition (XSD) or the simpler alternative Relax NG.
