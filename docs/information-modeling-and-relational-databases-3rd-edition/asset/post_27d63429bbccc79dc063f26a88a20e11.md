One feature deserves special attention. A relational schema captures the intrinsic structure of the information but has nothing to say about how the information will be (or can be) used. The neutral standpoint guides attention to what the information is, rather than what it does. Depending on the point of view, this can be seen as either a strength or a weakness.

If we assume that the schema has been properly normalized, then we can be sure that unnecessary duplication has been avoided, as each piece of information occurs only once. This provides the maximum flexibility when we consider how the information might be used because it is not optimized in a direction that favors any specific type of usage. We might subsequently choose to depart from a pure normalized model to optimize performance in a certain direction. Sadly though, optimizing one factor in a given situation normally deoptimizes other factors, so having a neutral position is a useful starting point.

The most common reason for denormalizing a relational schema is to improve performance in a specified usage scenario. Values from different relations can be combined to give any desired result, but this involves join operations that are relatively expensive in computational terms. The joins can be avoided by combining the relations involved, in effect prejoining them rather than waiting for a query. However, although this reduces the cost of queries, it makes updates more expensive because of the need to manage duplicate information that the denormalization has introduced.

Determining the best policy requires knowledge of the anticipated data traffic. To take some examples, an online catalogue might have infrequent updates but large numbers of queries, whereas a logging application might have many updates but only rare queries. Concerns about performance figure largely in NoSQL databases, as we will see later.

Many NoSQL platforms announce the lack of a schema as a major benefit. Defining a database schema of any kind may indeed involve a considerable amount of work, such as identifying the data to be accommodated, understanding its relevance to the business, arbitrating between competing demands, and so on. The websites of NoSQL vendors often include examples that show how easy it can be to create arbitrary data structures without in a reasonable time frame, regardless of whether a node in the system has failed or is experiencing issues.
