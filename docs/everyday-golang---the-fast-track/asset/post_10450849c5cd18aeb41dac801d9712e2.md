## Serverless use-cases

With the word Serverless, I find that potential users either “get it” or completely miss the point. And I’m not sure which camp you are in as you read this section of the book.

I’ve quite often heard the words “we’re not ready for serverless yet” or “I have no use-case” from developers who write HTTP microservices on a daily-basis, or who build integrations between platforms for their customers.

The thing that can be tricky to explain is that functions are microservices, only more specialised.

Functions tend to be:

- Smaller than a microservice
- More focused on a single use-case or responsibility
- Scaled & monitored automatically
- Built with a template, without dealing with HTTP servers

But they cover the same use-cases as microservices. They can read from and write to databases. They can serve webpages to customers, and have custom domains. They can be used to run batch jobs and to process data. There's not much that a function cannot do.

When we say functions, we're really saying: “It’s a microservice that has some additional management” and by being able to manage all your services in one way, it reduces the repetition, so that you can ship code faster.

So if you write, maintain or monitor back-end services for a living, then you could probably make use of functions in your day-job.

## Introduction to OpenFaaS

My earliest memory of Go was when I was learning and writing about Docker in 2015. The concept of reproducible builds fixed a major pain point at the company I was working at, but the technology was a world apart from what was being used at the time, so I embarked on a journey to relate it to others. In 2016 Docker released their “Swarm” product that allowed multiple computers running containers to work together as part of a distributed system. It must have been around that time that I heard of the term FaaS and Serverless, and I had no idea what the difference was between the two.

It was only when I started trying to use AWS Lambda for writing, debugging and shipping Alexa skills that I realised what containers could do for functions.

At the time, there was no way to run Go code inside AWS Lambda and the common trick was to add a binary to the Node.js runtime and have it get executed for every request. Then there was the pipeline. Working at an enterprise company, I couldn’t understand why it was so hard to link source control to AWS Lambda and have it deploy changes directly. Instead ZIP files and binaries compiled on your local machine were the way to go.

That’s when I started OpenFaaS, then called “faas” in late 2016 and the first version was demoed on the main stage at Dockercon in May the following year. One of the demos involved responding to Star events on the alexellis/faas GitHub repository. For each star, a virtual polaroid was generated and then uploaded to an S3 bucket and presented on the big screen.

Back then, if you asked 10 people what Serverless meant, they would probably give a different answer depending on where they worked, how much work they had done with functions and what time they started their journey. I started in 2016 and at the time, Serverless was largely synonymous with Functions as a Service (FaaS). Various working groups have tried to define the term, or to create a specification, but these efforts have resulted in weak standards and a lot of confusion. I was part of the CNCF’s Serverless Working Group that wrote the CNCF Whitepaper.

When I talk to users of OpenFaaS, they tend to care less about granular billing and whether server management is required, and more on having a cloud-agnostic runtime for code and events.

## The value vs cloud functions

So what’s the value of OpenFaaS vs. cloud functions?

- Avoid getting locked-in with a specific cloud provider. This means if you have a product, you can run it on a public cloud for customers, but also run it on their own private cloud on-premises.
- Set your own limits. Rather than being told the maximum amount of RAM allowable for a function, or the maximum size, number of concurrent requests, or timeout value, you can set this yourself. What would you do, if you hit a limit and it affected an important customer?
- White-label the solution. Some companies take OpenFaaS and integrate it into their platform as a kind of “black box” to run functions. It gives their platform the ability to run code for users and to extend their platform. Examples from the ADOPTERS file include Waylay (a low-code platform) and LivePerson (a customer-focused chat platform).
- Extend and adapt. If you need to integrate with a certain message queue or database, you can write some code and make it happen. If you need to customise the way a function is created or runs, then you can fork the code and update it to do what you need.

## Pros and Cons

At the same time, we should talk about disadvantages of OpenFaaS vs cloud functions.

Each cloud vendor such as Azure, Google Cloud et al tend to make their cloud functions platform very tightly integrated with their managed services. If you need a very tight integration between managed AWS services, then AWS Lambda may be a better fit for your needs.

OpenFaaS is relatively easy to run, and since we created faasd, no longer requires you to know Kubernetes to deploy a few functions. However, if you’re not already using Kubernetes, then it may be simpler (in some circumstances) to use cloud functions.

If you’re setting up a function for a client, which you don’t want to be responsible for, then you may find the support that comes with managed cloud functions reassuring. That said, if you are a consultant, you could operate one OpenFaaS cluster for all your clients.

Some end-user companies that use Kubernetes on AWS have told us that they would rather have one way to deploy and manage all of their code, which meant using OpenFaaS instead of the managed Lambda platform. Ultimately, you need to evaluate your needs and decide whether you want the flexibility and autonomy where you support and run your functions, or a managed platform where the cloud provider takes on some of that role.

## Where can you run OpenFaaS functions?

Any OpenFaaS function that you build will be packaged in a container image. You can then deploy that to at least three different platforms, and potentially more, if they support HTTP microservices.

- OpenFaaS - wherever you hear the word “OpenFaaS”, it's probably going to mean OpenFaaS running on Kubernetes. You can get managed Kubernetes from a cloud provider, which means the control-plane is hands-off. Then you'll just manage the nodes, but these can also be auto-scaled. Spot instances can drastically reduce the costs of cloud hosts.
- faasd - faasd is the same OpenFaaS as used on Kubernetes, but specialised for low overheads and resource requirements. It runs on a single host.
- Google Cloud Run - most functions that you build for OpenFaaS can run on Google's Cloud Run. You'll be billed according to your use, and you won't have to manage anything, other than the images themselves. This is not the full OpenFaaS experience, but could be useful for some users.

You'll need to have OpenFaaS set up before starting any of the examples in this section of the book.

Install Docker and the faas-cli on any computer where you want to build functions.

## The Go template for OpenFaaS

OpenFaaS has three Go templates that you can use to build functions:

- go - a legacy template that uses a cgi/bin approach
- golang-http - a Go template that gives you a user-friendly HTTP request/response struct to work with
- golang-middleware - my favourite template, that gives you a middleware from Go's standard library to work with
