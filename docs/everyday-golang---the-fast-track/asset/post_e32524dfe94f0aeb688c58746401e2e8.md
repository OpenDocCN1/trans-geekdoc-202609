
OpenFaaS templates are stored in various git repositories. The pull command fetches all the templates in a specific repository to your template folder.

```bash
faas-cli template pull \
    https://github.com/openfaas/golang-http-template
```

The template store has a list of official and community templates and can be used instead of typing a full URL:

```bash
faas-cli template store pull golang-http
```

Examine the results:


The golang-http template provides a request and response style, and is most similar to the approach managed cloud functions take.

See the contents of `template/golang-http/function/handler.go`:

```go
package function

import (
    "fmt"
    "net/http"

    handler "github.com/openfaas/templates-sdk/go-http"
)

// Handle a function invocation
func Handle(req handler.Request) (handler.Response, error) {
    var err error

    message := fmt.Sprintf("Body: %s", string(req.Body))

    return handler.Response{
        Body:       []byte(message),
        StatusCode: http.StatusOK,
    }, err
}
```

- The HTTP body is available in the `req.Body` variable.
- The HTTP headers are available in `req.Headers`.
- The HTTP querystring, path and method are also available in `req.QueryString`, `req.Path` and `req.Method`.

The golang-middleware template offers a standard HTTP request handler instead:

Contents of `template/golang-middleware/function/handler.go`:

```go
package function

import (
    "fmt"
    "io"
    "net/http"
)

func Handle(w http.ResponseWriter, r *http.Request) {
    var input []byte

    if r.Body != nil {
        defer r.Body.Close()

        body, _ := io.ReadAll(r.Body)

        input = body
    }

    w.WriteHeader(http.StatusOK)
    w.Write([]byte(fmt.Sprintf("Body: %s", string(input))))
}
```

Both OpenFaaS and Cloud Run require a container, so a Dockerfile is usually necessary. By using a template, the Dockerfile gets abstracted away along with all the common boilerplate code like how to set up a HTTP server and start listening on a TCP port. Those things still happen, but are hidden away from your workflow and don’t need to be duplicated in every function.

## Your first function

Let’s create a function that computes a bcrypt hash of whatever input you send to it. Bcrypt is often used to hash passwords for storage in databases.

See also: https://pkg.go.dev/golang.org/x/crypto/bcrypt

Decide where you want to upload your container images for your functions, and set the below environment variable:

```
export OPENFAAS_PREFIX="ghcr.io/alexellis"
export OPENFAAS_PREFIX="docker.io/alexellis2"
export OPENFAAS_PREFIX="private.gcr.io/my-company"
```

The Docker Hub and GitHub Container Registry provide a good starting point. You can also use your own private registries, if you configure OpenFaaS for this.

Make sure that you’ve logged into Docker:

```
docker login
```

Now set up your environment variable if you didn’t already do that in the previous step.

```
export OPENFAAS_PREFIX="docker.io/alexellis2"
```

Create a folder for the function:

```
export GH_USERNAME="alexellis"
mkdir -p $GOPATH/src/github.com/$GH_USERNAME/bcrypt-fn/
cd $GOPATH/src/github.com/$GH_USERNAME/bcrypt-fn/
```

Now scaffold a new function using the golang-middleware template:

```
faas-cli template store pull golang-middleware

faas-cli new --lang golang-middleware \
  bcrypt-fn
```

Check out the contents of the generated bcrypt-fn.yml file:

```
version: 1.0
provider:
  name: openfaas
  gateway: http://127.0.0.1:8080
functions:
  bcrypt-fn:
    lang: golang-middleware
    handler: ./bcrypt-fn
    image: docker.io/alexellis2/bcrypt-fn:latest
```

You can change the latest tag to a specific version such as 0.1.0 and then increment this before each build of your function.

Update the bcrypt-fn/handler.go file so that it computes a bcrypt hash of whatever input you send it:

```
package function

import (
  "fmt"
  "io"
  "net/http"

  "golang.org/x/crypto/bcrypt"
)

func Handle(w http.ResponseWriter, r *http.Request) {
  var input []byte

  if r.Body != nil {
    defer r.Body.Close()
    body, _ := io.ReadAll(r.Body)
    input = body
  }

  res, err := bcrypt.GenerateFromPassword(input, bcrypt.DefaultCost)
  if err != nil {
    http.Error(w, fmt.Sprintf("Error: %s", err), http.StatusInternalServerError)
    return
  }

  w.WriteHeader(http.StatusOK)
  w.Write(res)
}
```

Run these steps to set up the imported module:

```
cd bcrypt-fn
go mod init
go mod tidy
```

Then `cd ..` back to the top level of your project, where the `bcrypt-fn.yml` file is.

You must always run `go mod` commands alongside your `handler.go` file, and not at the level of the YAML file.

## Building your function

The workflow for building and deploying a function is as follows:

- `faas-cli build` creates a container image in your local Docker library
- `faas-cli push` pushes the image to your remote container registry
- `faas-cli deploy` deploys the function to your OpenFaaS Gateway using a REST API call

The above three commands can be run via the `faas-cli up` command.

All of these commands can be run in CI/CD pipelines.

Set up your OpenFaaS Gateway URL as an environment variable and run `faas-cli up` to try out the function.

```sh
export OPENFAAS_URL=http://127.0.0.1:8080

export DOCKER_BUILDKIT=1

faas-cli build --build-arg GO111MODULE=on -f bcrypt-fn.yml
```

The `export DOCKER_BUILDKIT=1` step will instruct Docker to use buildkit instead of its legacy approach for building functions. Buildkit can work out much faster because it can cache the layers in a more intelligent way and also run multiple steps in parallel. Ultimately, this means your builds will be quicker.

What will happen next is that the Dockerfile for the function will be executed. This is hidden away from you in the template at: `template/golang-middleware/Dockerfile`. You can read through it now, if you like.

In a separate window, invoke the container:

```sh
curl --data-binary "functions" \
  http://127.0.0.1:8080/function/bcrypt-fn

$2a$10$ziCqH4XsqdfO5SQ4QqCenuF9qi1hhW50N7f4914fqZjacU5PzJsqq
```

Each time you run the function, you’ll get the same result. You’ll also notice that the duration is relatively slow because the algorithm is designed to be CPU-intensive.

Time the invocation with:

```sh
time curl --data-binary "functions" \
  http://127.0.0.1:8080/function/bcrypt-fn

```

You can also check the HTTP header for the `X-Duration-Seconds:` header, which is the time taken for the function to run, rather than the round-trip between curl and the container.

```sh
curl -i --data-binary "functions" \
  http://127.0.0.1:8080/function/bcrypt-fn

Content-Length: 60
Content-Type: text/plain; charset=utf-8
```

Enter the directory, run go build and then invoke the handler:

```
faas-cli build --shrinkwrap -f bcrypt-fn.yml
cd ./build/bcrypt-fn

# Remove the function's go.mod
rm ./build/bcrypt-fn/go.mod

# Create one at the top-level
go mod init
go mod tidy

go build

./handler
```

Note that the handler won't print any output, but you can invoke it on port 8082:

```
curl http://localhost:8082

$2a$10$iho.B7JZNX8DDp610./eheEUxBuCOTEWGS47aIhuXchRSV0oYfYnW
```

This is an advanced technique, but can be used for testing out the function locally when something is going wrong and you need to make many edits in a short period of time.

## Split code into multiple files

Most of the time, your handler.go file will be relatively short, but if you want to break it out into multiple files for readability.

Consider that handler.go evolved to return a JSON struct containing the hash and the computation cost instead of the hash directly.

```
package function

import (
    "encoding/json"
    "fmt"
    "io"
    "net/http"

    "golang.org/x/crypto/bcrypt"
)

type HashResponse struct {
    Hash string
    Cost int
}

func Handle(w http.ResponseWriter, r *http.Request) {
    var input []byte

    if r.Body != nil {
        defer r.Body.Close()
        body, _ := io.ReadAll(r.Body)
        input = body
    }
}
```
