
其次，消息摘要可用于实现数字签名算法。本章后面的“数字签名”部分将介绍这一概念。

加密哈希函数有五个基本要求：

* 它们接受任意长度的输入。
* 无论输入长度如何，它们都产生固定长度的输出。
* 哈希值相对容易计算。
* 哈希函数是单向的（意味着在提供了输出的情况下，极难确定输入）。
* 哈希函数是 `collision` 免疫的（意味着极难找到产生相同哈希值的两条消息）。

### SHA

安全哈希算法（`SHA`）及其后继者 `SHA-1`、`SHA-2` 和 `SHA-3`，是由美国国家标准与技术研究院（`NIST`）推广的政府标准哈希函数，并在一份官方政府出版物——安全哈希标准（`SHS`）中规定，该标准也称为联邦信息处理标准（`FIPS`）180。

`SHA-1` 接受几乎任意长度的输入（实际上，该算法的上限约为 2,097,152 TB），并生成 160 位的消息摘要。`SHA-1` 算法以 512 位分块处理消息。因此，如果消息长度不是 512 的倍数，`SHA` 算法会用额外数据填充消息，直到长度达到下一个 512 的倍数。

密码分析攻击表明 `SHA-1` 算法存在弱点。这促使了 `SHA-2` 的诞生，后者有四个变体：

* `SHA-256` 使用 512 位分块大小生成 256 位消息摘要。
* `SHA-224` 使用 `SHA-256` 哈希的截断版本，利用 512 位分块大小生成 224 位消息摘要。
* `SHA-512` 使用 1,024 位分块大小生成 512 位消息摘要。
* `SHA-384` 使用 `SHA-512` 哈希的截断版本，利用 1,024 位分块大小生成 384 位摘要。

密码学界普遍认为 `SHA-2` 算法是安全的，但它们理论上存在与 `SHA-1` 算法相同的弱点。2015 年，联邦政府宣布发布 `Keccak` 算法作为 `SHA-3` 标准。`SHA-3` 套件的开发旨在作为 `SHA-2` 哈希函数的直接替代品，使用更安全的算法提供相同的变体和哈希长度。

### MD5

1991 年，Ron Rivest 发布了其消息摘要算法的下一个版本，称为 `MD5`。它同样以 512 位分块处理消息，但使用四轮不同的计算来生成与早期 `MD2` 和 `MD4` 算法长度相同的摘要（128 位）。

`MD5` 实现了显著降低消息摘要生成速度的安全特性。不幸的是，最近的密码分析攻击表明 `MD5` 协议易受碰撞攻击，这使其无法用于确保消息完整性。

## 数字签名

一旦选择了一个密码学上可靠的哈希算法，就可以用它来实现 `digital signature` 系统。数字签名基础设施有两个不同的目标：

* 经数字签名的消息向接收者保证该消息确实来自声称的发送者。它们强制执行不可否认性（即防止发送者事后声称消息是伪造的）。
* 经数字签名的消息向接收者保证该消息在发送者和接收者之间传输时未被篡改。这既防止恶意篡改（第三方改变消息含义），也防止无意篡改（因通信过程中的故障，如电气干扰）。

数字签名算法依赖于本章已介绍的两个主要概念的结合——公钥密码学和哈希函数。

如果 Alice 想要对发送给 Bob 的消息进行数字签名，她会执行以下操作：

1. Alice 使用密码学上可靠的哈希算法（如 `SHA3-512`）生成原始明文消息的消息摘要。
2. Alice 然后仅使用她的私钥加密消息摘要。这个加密后的消息摘要就是数字签名。
3. Alice 将签名后的消息摘要附加到明文消息后。
4. Alice 将附加后的消息发送给 Bob。

当 Bob 接收到数字签名消息时，他会反向执行该过程，步骤如下：

1. Bob 使用 Alice 的公钥解密数字签名。
2. Bob 使用相同的哈希函数为从 Alice 接收到的完整明文消息创建一个消息摘要。
3. Bob 然后将从 Alice 接收到的解密消息摘要与他自己计算的消息摘要进行比较。如果两个摘要匹配，他可以确信收到的消息是由 Alice 发送的。如果不匹配，则消息不是由 Alice 发送的，或者消息在传输过程中被修改过。

请注意，数字签名过程本身不提供任何隐私保护。它仅确保满足完整性、认证和不可否认性这些加密目标。然而，如果 Alice 想要确保发给 Bob 的消息的隐私，她可以在消息创建过程中增加一个步骤。在将签名后的消息摘要附加到明文消息后，Alice 可以用 Bob 的公钥加密整条消息。当 Bob 收到消息时，他会先用自己的私钥解密，然后再遵循上述步骤。

### HMAC

哈希消息认证码（`HMAC`）算法实现了部分数字签名——它保证消息在传输过程中的完整性，但不提供不可否认性。

`HMAC` 可以通过使用共享密钥与任何标准消息摘要生成算法（如 `SHA-3`）结合。因此，只有知道密钥的通信双方才能生成或验证数字签名。如果接收者解密了消息摘要，但无法将其与从明文消息生成的消息摘要成功比较，则意味着消息在传输过程中被篡改。

因为 `HMAC` 依赖于共享密钥，所以它不提供任何不可否认性功能（如前所述）。然而，它的运行效率比下一节描述的数字签名标准更高，可能适用于对称密钥密码学适用的场景。简而言之，它代表了未加密使用消息摘要算法与基于公钥密码学的计算成本高昂的数字签名算法之间的一个折中点。

### 数字签名标准

美国国家标准与技术研究院在联邦信息处理标准（`FIPS`）186-4 中规定了联邦政府可用的数字签名算法，该标准也称为数字签名标准（`DSS`）。该文件规定，所有联邦批准的数字签名算法必须使用 `SHA-3` 哈希函数。

`DSS` 还规定了可用于支持数字签名基础设施的加密算法。目前有三种批准的标准加密算法：

* `FIPS 186-4` 中规定的数字签名算法（`DSA`）
* `ANSI X9.31` 中规定的 Rivest、Shamir、Adleman（`RSA`）算法
* `ANSI X9.62` 中规定的椭圆曲线 DSA（`ECDSA`）

## 公钥基础设施

公钥加密的主要优势在于其促进相互未知各方之间通信的能力。这得益于 `public key infrastructure (PKI)` 信任关系层级。这些信任关系允许将非对称密码学与对称密码学相结合，并辅以哈希和数字证书，从而实现混合密码学。
