
## 攻击向量

*   实施社会工程学攻击，诱使用户直接或通过虚假认证机制泄露密码
*   窃听未加密的网络流量
*   从先前被攻陷的站点获取密码转储，并假设大量用户在其他站点复用了该站点的密码

除了这些方法，攻击者还可能实施凭证暴力破解攻击，即从目标系统获取一组弱哈希密码，然后进行穷举搜索以破解这些密码并获取系统访问权限。

在某些情况下，应用开发人员、供应商和系统管理员会让攻击者轻易得逞。系统通常带有默认管理员账户，且可能保持未修改状态。例如，[图 6.11](#c06.xhtml#c06-fig-0011) 展示了 Zyxel 路由器手册的一部分，其中包含默认用户名和密码以及修改密码的说明。

![FIGURE 6.11 Zyxel router default password ¶ Source: www.zyxel.com/support/Zyxel-password-changing-procedure-20161213-v2.pdf](images/c06f011.png)

[**图 6.11**](#c06.xhtml#R_c06-fig-0011) Zyxel 路由器默认密码 ¶ 来源：`www.zyxel.com/support/Zyxel-password-changing-procedure-20161213-v2.pdf`

渗透测试人员可能假设管理员未修改默认密码，并尝试在应用程序和设备上使用各种默认密码以尝试获取访问权限。一些常见的用户名/密码组合测试如下：

*   `administrator/password`
*   `admin/password`
*   `admin/admin`

许多网站维护着各类应用程序和设备使用的默认密码详细目录。这些网站是渗透测试人员寻求访问网络设备的绝佳切入点。

## 会话攻击

凭证窃取攻击允许黑客或渗透测试人员使用被盗账户直接向服务进行身份验证。*会话劫持* 攻击采取不同方法，通过窃取现有的已认证会话来实现。这些攻击不要求攻击者访问认证机制；相反，它们接管与网站已建立的认证会话。

大多数需要身份验证的网站使用用户浏览器中管理的 *Cookie*，并作为网站提供的 *HTTP 头* 信息的一部分进行传输。在这种方法中（如 [图 6.12](#c06.xhtml#c06-fig-0012) 所示），用户访问网站的登录表单并使用其凭证进行身份验证。如果用户通过身份验证过程，网站会向用户的浏览器提供一个 Cookie，该 Cookie 可用于验证未来的请求。一旦用户在浏览器中存储了有效的 Cookie，浏览器就会将该 Cookie 随发往该网站的所有未来请求一起传输。网站检查 Cookie，确定用户已通过身份验证，无需重新输入密码或完成其他身份验证任务。

![FIGURE 6.12 Session authentication with cookies](images/c06f012.png)

[**图 6.12**](#c06.xhtml#R_c06-fig-0012) 使用 Cookie 进行会话认证

Cookie 只是用户浏览器中维护的一个存储对象，它保存稍后可由创建它们的网站访问的变量。你可以将 Cookie 视为网站在用户浏览器中维护的一个小型信息数据库。Cookie 包含一个认证字符串，将 Cookie 与特定的用户会话关联。[图 6.13](#c06.xhtml#c06-fig-0013) 展示了 `CNN.com` 网站使用的一个 Cookie 示例，在 Chrome 浏览器中查看。如果你检查自己浏览器的 Cookie 缓存内容，可能会发现数百或数千个由你访问过的网站维护的 Cookie。有些 Cookie 可能已有数年历史。

![FIGURE 6.13 Session cookie from CNN.com](images/c06f013.png)

[**图 6.13**](#c06.xhtml#R_c06-fig-0013) 来自 `CNN.com` 的会话 Cookie

### Cookie 窃取与篡改

正如你所读到的，Cookie 作为绕过网站认证机制的关键。打个比方，想象一下参加一个行业会议。当你到达注册台时，可能会被要求提供带照片的身份证件并支付注册费。在这种情况下，你经历了一个认证过程。注册后，工作人员会给你一个挂在脖子上的胸牌，供你在展会剩余时间佩戴。从那时起，任何安保人员只需瞥一眼你的胸牌，就知道你已经过认证并获得了进入展会的权限。如果有人偷走了你的胸牌，他们现在就拥有了你享有的同等展会访问权限。

Cookie 的工作原理相同。它们只是胸牌的数字化版本。如果攻击者能够窃取某人的 Cookie，他们随后就可以向颁发该 Cookie 的网站冒充该用户。攻击者可能通过以下几种方式获取 Cookie：

*   窃听未加密的网络连接，并在 Cookie 在用户和网站之间传输时窃取副本。
*   在用户的浏览器上安装恶意软件，检索 Cookie 并将其传回攻击者。
*   实施 *中间人攻击*，攻击者欺骗用户认为攻击者实际上是目标网站，并呈现一个虚假的认证表单。随后，他们可能代表用户向网站进行身份验证并获取 Cookie。

一旦攻击者拥有了 Cookie，他们可能会执行 Cookie 篡改以更改发回网站的详细信息，或者直接将 Cookie 作为获取网站访问权限所需的“胸牌”。这被称为 *会话重放* 攻击，如 [图 6.14](#c06.xhtml#c06-fig-0014) 所示。

![FIGURE 6.14 Session replay](images/c06f014.png)

[**图 6.14**](#c06.xhtml#R_c06-fig-0014) 会话重放

Web 开发人员可以通过使用 `SECURE` 属性标记 Cookie 来防止 Cookie 窃取。*安全 Cookie* 永远不会通过未加密的 HTTP 连接传输。服务器和 Web 浏览器都理解它们必须仅通过加密通道发送，以防范会话重放攻击。

NTLM *传递哈希攻击* 是另一种重放攻击形式，它针对操作系统而非 Web 应用程序。攻击者首先访问 Windows 系统，然后从该系统收集存储的 NTLM 密码哈希。随后，他们可以尝试使用这些哈希来获取该系统或同一 Active Directory 域中其他系统的用户或管理员访问权限。

### 未验证的重定向

不安全的 URL 重定向是攻击者可能利用的另一种漏洞，旨在窃取用户会话。某些 Web 应用程序允许浏览器将目标 URL 传递给应用程序，并在交易完成时将用户重定向到该 URL。例如，订单页面可能使用如下结构的 URL：

```
https://www.mycompany.com/ordering.php?redirect=http%3a//www.mycompany.com/thankyou.htm
```

Web 应用程序随后会在交易结束时将用户发送到感谢页面。这种方法对 Web 开发人员很方便，因为它允许管理员在不更改应用程序代码的情况下修改目标页面。然而，如果应用程序允许重定向到任意 URL，就会产生 *未验证的重定向* 情况，攻击者可利用它将用户重定向到恶意站点。例如，攻击者可能在留言板上发布指向上述页面的链接，但将 URL 修改为：

```
https://www.mycompany.com/ordering.php?redirect=http%3a//www.evilhacker.com/passwordstealer.htm
```
