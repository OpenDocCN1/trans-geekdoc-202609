
# AWS 网络与安全考题解析

## 116. D
当你需要保护或限制特定实例的进出流量时，`Security Group`（安全组）是最佳选择。安全组与特定实例关联，因此可以有效地限制部分实例的流量，同时允许使用不同安全组的其他实例保持可访问。

## 117. A, C
这需要仔细阅读。首先，在一个子网中混合使用私有和公共实例并非最佳实践——尽管这不是一条铁律。因此，C 选项（将私有数据库实例移至不同的子网）至少值得考虑。D 选项在此情况下无帮助。如果你有两个子网（一个私有，一个公共），则 A 选项是个好主意：`NACL`（网络 ACL）可以保护一个子网并保持另一个子网公开。最后，B 选项因单词 *single*（单个）而 **无效**。你不能拥有一个单一的安全组既允许流量到达一个实例又不允许到达另一个实例。这使得 A 和 C 成为最佳组合解决方案。

## 118. C
安全组默认拒绝所有流量，除非显式允许。这意味着它充当**白名单**：只有特定规则允许入站流量，所有其他流量均被拒绝。

## 119. C, D
安全组在**实例级别**操作，而 `NACL` 在**子网级别**操作。

## 120. A
安全组执行**有状态过滤**，这意味着被允许进入的流量会自动被允许流出，无需显式的出站规则。

## 121. D
`Network ACLs`（网络 ACL）是**无状态**的。入站流量不会自动被允许流出；必须存在显式规则，流量才能从子网内部流回子网外部。

## 122. D
`VPC Peering`（VPC 对等连接）允许一个 VPC 与任何其他 VPC 连接：同一区域、不同区域，甚至完全不同的账户。

## 123. B, D
VPC 对等连接允许 VPC 与任何其他 VPC 连接，因此不涉及 VPC 的选项是不正确的：B 和 D。

## 124. B, D
只要源 VPC 上有网关（互联网网关或虚拟私有网关）并通过该网关进行路由，VPC 中的实例就可以与其他实例通信。因此本题需选择 B 和 D。不存在“跨 VPC 通信”选项，且安全组实际上无法解决此场景。

## 125. A, D
这稍有难度，但归根结底是可访问性：目标实例如何被访问？在可用答案中，公有 IP 会使目标可用，`VPN` 连接也是如此。

## 126. D
VPC 是 AWS 网络的基础，在所有 AWS 区域均可用。

## 127. D
一个 VPC 自动跨越其所在区域内的所有可用区。

## 128. B
启动实例时，必须指定可用区。这可以简单到接受 AWS 默认值，但选择权在你。

## 129. B
`EBS` 卷可以加密，但必须在启动时完成（B 选项）。

## 130. D
`VPC Endpoint`（VPC 终端节点）是到 AWS 服务的连接，明确**不**使用互联网网关、`VPN` 连接或 `NAT` 设备。

## 131. B
VPC 终端节点是虚拟设备，而非物理设备。

## 132. C
VPC 终端节点用于连接 AWS 服务，明确**不**需要互联网网关（C 选项）。

## 133. C
默认情况下，`IAM` 用户没有使用终端节点的权限。你可能需要创建一个 `IAM Role`（IAM 角色）。使用 VPC 终端节点**不**需要 `NAT` 设备（A 或 B）或安全组（D）。

## 134. B
如果没有堡垒主机或其他连接，以及从公共互联网到可访问主机再到私有实例的路由，私有子网是不可访问的。

## 135. B
堡垒主机应位于公共子网，以便通过公共互联网访问。随后它们可将流量路由至私有子网。

## 136. C
堡垒主机有时也称为**跳板服务器**，因为它们允许连接“跳转”到堡垒主机，再进入私有子网。

## 137. D
堡垒主机旨在提供对私有子网中私有实例的访问；换句话说，即通过其他方式无法从公共互联网访问的实例。

## 138. D
堡垒主机可公开访问且能访问你的私有主机。因此，它们必须是你网络中**最安全**的主机。为其所在子网使用网络 ACL，为实例使用安全组，并通过操作系统加固减少实例内部的访问权限。

## 139. B
Shell 访问仅需 `SSH`，因此应仅允许该协议。堡垒主机始终**仅允许绝对必要的内容**。

## 140. D
互联网网关**水平扩展**，而非垂直扩展。它们也是冗余且自动高可用的。

## 141. C
互联网网关连接到 VPC 并服务于多个子网（如有需要）。

## 142. B
路由 `0.0.0.0/0` 捕获所有目标为公共互联网的 IPv4 流量。`::/0` 用于 IPv6，`0.0.0.0/24` 将流量限制在特定 CIDR 块内，D 选项是内部 IP 地址。

## 143. C
路由 `::/0` 捕获所有目标为公共互联网的 IPv6 流量。`0.0.0.0/0` 用于 IPv4，`0.0.0.0/24` 将流量限制在特定 CIDR 块内，D 选项是内部 IP 地址。

## 144. D
实例必须拥有从自身（带公有 IP 地址）出发的 IPv6 通信，通过具有 IPv6 地址的子网，在具有 IPv6 地址的 VPC 中，才能通过 IPv6 到达互联网。`Virtual Private Gateway`（虚拟私有网关）与这些无关。

## 145. A, B
为使实例能从公共互联网访问并被访问，实例必须关联公有 IP 地址或弹性 IP 地址。`IAM Role` 不提供公共访问，`NACL` 连接到子网而非实例。

## 146. A, C
公共子网的定义是附加了互联网网关的子网。默认 VPC 自动附加了互联网网关。

## 147. B
`ALB` 代表 `Application Load Balancer`（应用负载均衡器）。

## 148. B
应用负载均衡器在**应用层**运行，即 OSI 模型的第 7 层。`ELB`（经典负载均衡器）在传输层（第 4 层）和第 7 层运行，网络负载均衡器也在第 4 层运行。

## 149. A
应用负载均衡器在**应用层**运行，即 OSI 模型的第 7 层。`ELB`（经典负载均衡器）在传输层（第 4 层）和第 7 层运行，网络负载均衡器也在第 4 层运行。

## 150. C
应用负载均衡器在**应用层**运行，即 OSI 模型的第 7 层。`ELB`（经典负载均衡器）在传输层（第 4 层）和第 7 层运行，网络负载均衡器也在第 4 层运行。

## 151. D
网络负载均衡器和经典负载均衡器均在传输层运行。经典负载均衡器也在第 7 层（应用层）运行。应用负载均衡器在应用层运行，即 OSI 模型的第 7 层。

## 152. D
经典负载均衡器和应用负载均衡器均在应用层运行。经典负载均衡器也在第 4 层（传输层）运行。网络负载均衡器在传输层运行，即 OSI 模型的第 4 层。

## 153. C
默认情况下，默认 VPC 中的子网是公共的。默认 VPC 附加了互联网网关，因此默认子网因此而成为公共子网。

## 154. A
默认情况下，自定义 VPC 中的子网是私有的。除默认 VPC 外，自定义 VPC 默认未附加互联网网关，创建的子网也没有公共访问权限。

## 155. C
启动到非默认子网的实例拥有私有 IPv4 地址，但没有公有 IPv4 地址，因此 C 正确。所有实例都会创建或关联安全组，且实例默认始终可以与同一子网中的其他实例通信。

## 156. C, D
启动到非默认子网的实例拥有私有 IPv4 地址，但没有公有 IPv4 地址，因此如 C 所示需要弹性 IP 地址（公有 IP 地址也可行）。还需要为实例配置互联网网关（D）。
