
# AWS 认证考试题解析

## 32. 弹性 IP 地址默认限额
**A.** AWS 账户默认允许每个区域拥有五个弹性 IP 地址。与大多数 AWS 默认限制一样，可以通过联系 AWS 并提供合理的理由来提高该限额。

## 33. 实例可挂载的 EBS 卷数量
**C.** 官方规定，实例最多可有 28 个挂载点。其中一个被网络接口占用，剩下 27 个可用于 EBS 卷。但更好的记忆方法是：实例可以挂载一个根卷和多个额外卷（超过两个）；这排除了选项 A 和 B。此外，实例不能有无限数量的挂载点。因此正确答案是 C。

## 34. EBS 卷的挂载限制
**A.** 注意措辞，不要误读为“一个 EC2 实例可以挂载多少个 EBS 卷”（这是完全不同的问题）。**单个 EBS 卷同一时间只能挂载到一个实例上。**

## 35. 应用负载均衡器支持的协议
**B, C.** 这应该是个简单的答案：应用负载均衡器以及经典负载均衡器仅支持 HTTP 和 HTTPS。

## 36. RDS 数据库备份方式
**A, C.** 目前 RDS 仅提供两种备份 RDS 数据库的方法：自动备份和自动快照。S3 生命周期管理策略不适用于 RDS 数据库，且 Data Pipeline 在此上下文中不相关。

## 37. 缓存数据的快照一致性
**B.** 写入和读取缓存的数据是临时的，如果实例频繁读写该数据，确保快照不丢失缓存数据的唯一方法是**完全停止实例运行**，然后再创建快照（选项 B）。选项 A 和 C 虽然会创建快照，但很可能会丢失缓存数据。选项 D 无法从实例分离根卷（题目未明确缓存数据写入的是 EBS、EFS 还是其他存储机制），因此不是安全的选择。

## 38. 减少数据库延迟的方案
**B, C.**
- 选项 A 无效，因为 Multi-AZ 是灾难恢复方案；正常操作下只有主数据库实例能响应流量（除非同时配置了只读副本）。
- 选项 B 有效；缓存用户数据可减少往返数据库的次数，从而降低用户延迟。
- 选项 C 也合理，因为增加可供读取的数据库实例应能降低对单个 RDS 实例的网络延迟。
- 选项 D 无帮助，因为问题出在检索凭证上，而非 Web 层本身。

## 39. 照片存储的成本优化选择
**C.** 标准 S3（A）虽非坏选择，但成本最高；它和 S3-IA（B）因可用性和弹性更高，均比 S3 One Zone-IA 昂贵。关键在于照片丢失不造成问题，因此 **S3 One Zone-IA 是更优选项**。AWS 不再推荐使用 S3 RRS。

## 40. 大数据传输解决方案
**C.** 这应是自动反应：涉及大数据传输时（尤其是在 AWS 考试中！），答案应为 **Snowball**。这类题目高频出现，应轻松拿下。

## 41. S3 分段上传
**A, D.** 唯一棘手的选项是 B。虽然**分段上传**绝对能改善大文件（如大于 10 GB）的上传体验，但它**不是必须的**；因此 B 不是最佳选项。选项 A 和 D 仅在启用分段上传时才可能实现。选项 C 错误，因为安全性与分段上传无关。

## 42. 置放群组的核心关注点
**C.** 置放群组主要关注网络吞吐量，并降低单一可用区内 EC2 实例间的延迟。AWS 确实支持通过分散置放群组跨越多个 AZ，但除非明确提到“分散”，否则应假设题目指的是“普通”（或“集群”）置放群组。

## 43. 集群置放群组特性
**A, B.** 集群置放群组（默认类型）必须由位于**单一可用区**内的实例组成（A）。这会带来网络活动吞吐量的增加（B），但不影响写入 S3 时的实际磁盘性能（C）。实例也可以是不同类型，因此 D 也是错误的。

## 44. 分散置放群组特性
**B, C.** 分散置放群组可跨越可用区，并支持每区最多七个实例（C）。与集群群组一样，这会带来网络活动吞吐量的增加（B）。必须为分散置放群组指定不同的底层硬件，因此 D 是错误的。

## 45. S3 存储类别的持久性
**D.** 这是一个反直觉的问题。**所有 S3 存储类别具有相同的持久性**。即使是 S3 One Zone-IA，在其所驻留的单个可用区内也拥有 11 个 9 的持久性。

## 46. S3 存储类别的可用性
**A.** 可用性从 S3 的 99.99% 起步，降至 S3-IA 的 99.9%、S3 One Zone-IA 的 99.5%，最后到 Glacier 的 N/A。

## 47. 生命周期转换支持的存储类别
**D.** 如果回忆起生命周期转换涉及在这些存储类别间移动，这题很简单。**因此，所有这些类别都支持这些转换。**

## 48. S3 数据存储的区域性
**A, C.** 所有 S3 和 S3-IA 数据均存储在单一区域内，且位于该区域内至少三个可用区中。**不存在用于 S3 存储的“全局”区域。**

## 49. 适合 OLAP 的数据库服务
**C.** **Redshift** 是此列表中唯一适合联机分析处理（OLAP）的数据库或服务。DynamoDB 是对象数据库（NoSQL），Aurora 和 Oracle 均为关系型数据库，更适合事务处理。

## 50. RDS 预置 IOPS 卷存储上限
**B.** RDS 支持的所有主流数据库——MariaDB、SQL Server、MySQL、Oracle 和 PostgreSQL——均允许预置 IOPS 卷拥有高达 **16 TB** 的存储空间。

## 51. 预置 IOPS EBS 卷类型
**A.** **预置 IOPS EBS 卷**是一种固态硬盘（SSD），提供最高性能的卷。

## 52. 冷 HDD EBS 卷特性
**B.** **冷 HDD** 是最便宜的 EBS 选项，故 B 正确。它不是固态（A），不适合数据仓储（C），也不可用作启动卷。

## 53. 可用作启动卷的 EBS 类型
**A, D.** 最容易的记忆方式是：**HDD 类型不可用作启动卷**。SSD 类型（A、D）可以，故为正确答案。

## 54. 通用型 SSD (gp2/gp3) 适用场景
**B, D.** **通用型 SSD** 是价格较低的 SSD（相比预置 IOPS），故 B 为有效答案。它还提供低延迟性能且可启动。选项 A 更适合预置 IOPS，选项 C 更适合吞吐量优化 HDD。

## 55. 磁性卷适用场景
**A, B.** 磁性卷较老旧，一般不常用。它们适合**省钱**（A）或存放**不常访问的数据**（B）。

## 56. 预置 IOPS 卷适用场景
**B, C.** 预置 IOPS 卷不便宜（A），但非常适合关键数据库工作负载和吞吐量需求（B 和 C）。

## 57. SSD 卷适用场景
**A, C.** **SSD 卷**最适合**事务性工作负载**（A），即包含大量小 I/O 尺寸读/写操作的场景。

## 58. HDD 卷适用场景
**B, D.** **HDD 支持的卷**最适合**流式工作负载**，即需要最大化吞吐量而非 IOPS 的场景。

## 59. Oracle 数据库存储推荐
**C.** 虽然通用型 SSD 可能足以支撑处理量不大的 Oracle 安装，但最佳选项是 **C，预置 IOPS SSD**。预置 IOPS 能很好地处理事务处理，并能应对 Oracle 安装所需的大量读写操作。

## 60. 低成本、低访问频率数据的存储选择
**A.** 此用例要求访问量最小，成本也最低。若数据不常访问且成本是主要驱动因素，**磁性驱动器**可能是个好选择。虽然吞吐量优化 HDD 仍比 SSD 便宜，但磁性存储是最便宜的选项，且对无高性能需求的数据集工作良好。

## 61. 可用作 EC2 启动卷的 EBS 类型
**A, C.** 可从**任何 SSD 类型**以及**磁性类型**启动 EC2 实例。HDD 选项不可用作启动卷。

## 62. 不可用作启动卷的 EBS 类型
**B, C.** **HDD EBS 卷类型不可用作启动卷**，故 B 和 C 为正确答案。

## 63. 不存在的负载均衡器类型
**C.** 不存在所谓的“加权负载均衡器”。其他选项均为实际存在的类型。

## 64. 负载均衡器缩写辨析
**A, C.** **ELB** 指弹性负载均衡，通常指经典负载均衡器。**ALB** 指应用负载均衡器。因此 A 和 C 有效；MLB 和 VLB 不是负载均衡器的缩写或简称。
