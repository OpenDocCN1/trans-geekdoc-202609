

## AWS Route 53 路由策略与 IAM 核心概念

### Route 53 路由策略

**138. B, C**  
Route 53 提供多种路由策略：简单、故障转移、地理位置、地理近邻、基于延迟、多值回答和加权。

**139. C**  
简单路由适合将所有流量发送到单个资源。

**140. B**  
故障转移路由用于将流量发送到单个资源，但如果该资源不健康，则故障转移到备用资源。

**141. C**  
地理位置路由使用用户 DNS 查询的位置来确定使用哪条路由。

**142. B**  
基于延迟的路由使用区域的延迟来确定路由应将用户导向何处。

**143. C**  
多值回答路由可将请求导向多个资源，并对这些资源执行健康检查。

**144. D**  
加权路由使用预定义的权重来确定流量如何跨多个资源路由。

**145. A**  
当只有一个资源需要接收流量时，简单路由是最佳选择。

**146. A, C**  
此处有效的两个选项是地理位置和地理近邻路由，两者在将用户路由到资源前都会考虑用户的位置。地理路由不是 Route 53 的有效路由策略。

**147. D**  
权重只是整数，可以求和以确定总权重，以及定向流量的每个资源的分数权重。

**148. C**  
在加权路由策略中，权重为 0 会将资源移出服务。

**149. A**  
在加权路由策略中，数值权重相加，每个资源的权重除以所有权重之和。本例中总权重为 400，因此 A 占 25%（100/400），B 占 25%（100/400），C 占 50%（200/400）。

**150. A, C**  
简单路由策略允许主资源和备用资源均为单个或多个资源，因此 A 和 C 正确。加权策略遵守健康检查（故 B 错误），且 D 不准确，因为权重数值不影响健康检查。

### EC2 实例类型与架构优化

**151. A, B**  
问题在于欧盟用户的地理近邻性和数据库负载（CPU 利用率高）。因此必须解决这些问题。`ElastiCache` (A) 应减少 `RDS` 实例的负载，`CloudFront` (B) 以一种能更快服务欧盟用户的方式缓存响应。

**152. B, D**  
这是一道记忆题。有效的实例类型以 T、M、C、R、X、Z、D、H、I、F、G 和 P 开头。E 和 Q 不是有效的实例类型前缀。

### IAM (Identity and Access Management) 基础

**153. B**  
IAM 为 AWS 资源提供权限，也为 AWS 平台用户提供访问权限。

**154. A, C**  
IAM 控制资源间交互的权限以及用户对 AWS 控制台的访问。它不提供认证接口或单点登录。

**155. B**  
IAM 代表 Identity and Access Management（身份与访问管理）。

**156. A, C**  
IAM 仅适用于用户、角色和组的权限，不影响账单、成本或特定应用功能的可访问性。

**157. B, C**  
IAM 处理用户访问 AWS 的权限 (A) 和 `EC2` 到 `S3` 的访问 (D)，因此这些陈述为真，故不选。它不处理托管应用程序权限 (B) 或与 `SNS` 相关，使 B 和 C 为正确答案。

**158. B**  
IAM 不是用于处理 `S3` 存储桶 MFA Delete 设置的托管服务。

**159. B**  
在 AWS 中共享单个账户时，通常存在安全风险。

**160. C**  
唯一的要求是创建一个不同于根用户登录链接的登录链接。为根用户或所有账户开启 MFA 不是必须的，虽然此时创建 IAM 组很常见，但并非访问的必要条件。

### IAM 实体与组织

**161. A, B**  
用户、组、角色、权限等构造属于 IAM。组织和组织单位属于 `AWS Organizations`，这是不同的工具。

**162. A, D**  
用户、组、角色、权限等构造属于 IAM。

**163. A, C**  
此处需创建一个允许 `EC2` 实例与另一个 AWS 服务（本例中为 `S3`）通信的角色。默认角色可能涵盖此用例，但若有特殊需求，也可编写自定义策略。

**164. A, D**  
可通过 IAM 提供控制台访问和编程访问。编程访问包含 API 和 CLI 访问。

### IAM 策略

**165. A, C**  
IAM 中有四种策略类型：基于身份、基于资源、组织 SCP 和访问控制列表 (ACL)。

**166. B**  
IAM 策略以 JSON 编写。

**167. A, C**  
基于身份的策略可附加到用户、组和角色；基于资源的策略可附加到 AWS 服务和组件。

**168. B**  
MFA 代表多因素认证，可由 IAM 在用户账户上启用。

**169. A, C**  
IAM 主要通过整合和集中管理权限来助力扩展性，既适用于 AWS 用户 (A)，也适用于实例到服务 (C)。

**170. C, D**  
IAM 提供权限、组、用户和角色；`AWS Organizations` 提供逻辑分组和账户管理。两者均跨所有 AWS 资源运作。

### IAM 角色与权限边界

**171. C**  
高级用户访问是预定义策略，允许访问除 IAM 内用户/组管理外的所有 AWS 服务。

**172. D**  
根用户可执行与 IAM 相关的所有操作。

**173. A**  
高级用户可使用托管服务，但无法创建（或管理）IAM 用户。

**174. B**  
虽听起来奇怪，AWS 强烈建议删除根用户访问密钥，并为日常使用创建 IAM 用户。

**175. A, C**  
起点考量：根账户通常用于账户级操作，如关闭账户 (A)。也用于高度特权访问；本例中即创建 `CloudFront` 密钥对，这提供应用的签名访问，属高度受信操作。IAM 允许分发用户和策略管理 (B 和 D)。

**176. A, B**  
影响其他账户通常需要根账户级访问。本例中即 D，以及用户权限恢复 (C)。A 和 B 非根用户也可用。

**177. D**  
无法移除 AWS 账户根用户的访问权限。

**178. C**  
这是道“送分题”但偶尔会考。AWS 坚定认为根账户访问应高度受限，但也不应限于单一用户。C 选项，由极少数工程师（最好持有 AWS 认证）组成的小组，是将根账户访问降至最低的最佳方法。

**179. D**  
AWS 定义并维护多种用户 IAM 策略，包括 Administrator、Billing 和 Power User。

**180. A, C**  
始终需为新用户提供非根登录 URL，故 A 必选。其余选项涉及权限，在可选项中（B 并非实际选项），Developer Power User 策略比 View-Only User 策略更合适。

**181. D**  
除非经理既高度技术化又从事实际开发，否则 D 最佳：提供 AWS 只读访问，不增加经理不需要的特权。

**182. D**  
Data Scientist 策略专为此设计：运行用于数据分析和商业智能的查询。

**183. A**  
这是系统管理员角色。Power User 虽授予相同服务的权限，但可能过于宽松。此类题关键是找到允许指定操作且不超出必要范围的角色。
