
## 15. C
这里的关键在于成本是驱动因素，且图像处理代码快速且廉价。这实际上意味着如果处理后的图像丢失，可以重新处理而不影响总体系统成本。因此，可以选择一种 S3 存储类，即使处理后的图像可能丢失，只要能降低总体成本即可。这使得 **S3 One Zone-IA** 成为可能，它是除 Glacier 之外最便宜的 S3 存储类，而 Glacier 的加载时间比可接受的时间长得多。S3 One Zone-IA 可能会丢失处理后的图像，但由于它们可以轻松重新创建，这并不构成阻碍。

## 16. C
**EFS**（Elastic File System，弹性文件系统）实际上是云中的 NAS，可提供同时被多个 EC2 实例访问的存储。

## 17. C, D
非默认 VPC 没有附加互联网网关，托管任何公有子网都需要一个，因此 C 是必需的。然后，附加了互联网网关后，子网中的实例将需要一条通过此网关的路由来处理互联网流量（D）。

## 18. A, B
AWS 定义了多个自定义请求头，它们都以 `x-amz` 开头，而不是 `x-aws`。这有助于排除错误答案；在本例中，这意味着 A 有效而 C 无效。然后，你只需记住其他请求头；`Content-Length`（C）有效，而 `Content-Size`（D）无效。

## 19. A, C
AWS 有四个支持级别：Basic、Developer、Business 和 Enterprise。Professional 和 Corporate 都不是有效的支持级别。

## 20. B, D
**RDS** 支持多种数据库选项：MariaDB、Aurora、PostgreSQL、MySQL、Oracle 和 SQL Server。**DynamoDB** 不是关系型数据库，**DB2** 不受支持。

## 21. B
**Scaling in**（缩容）是 Auto Scaling 组移除实例的过程。你可以把缩容想象为“向组边界*内部*移动”，扩容想象为“向组边界*外部*移动”。在可用选项中，只有 B——5 个实例——代表实例数量的减少。

## 22. B, D
**CloudFormation** 模板可以用 JSON 和 YAML 编写。

## 23. C
只有**地理位置路由**能确保用户位置是主要因素。虽然基于延迟的路由似乎等同于基于位置的路由，但网络流量可能导致附近区域的延迟更低，例如澳大利亚的用户可能被路由到美国区域。因此，只有地理位置路由能确保主要用户群按地理距离使用最近的区域。

## 24. C
**CNAME** 记录允许将流量定向到 DNS 名称，在本例中该 DNS 名称即为 **ELB**。ELB 不提供 IP 地址，因此 A 记录不适用。MX 记录用于邮件，AAAA 记录用于 IPv6 地址。

## 25. A, C
关键在于你不是在创建新用户（因此 B 不正确）；相反，你需要使用现有的 Active Directory 设置。这需要一个**身份提供商**（A）。然后，你可以颁发**临时令牌**（C）让用户开始使用，他们可以从那里更新凭证。

## 26. D
这是一个答案相对简单但干扰项很多的问题。当你有特定的周期性流量高峰时，**计划扩展**是一个简单的解决方案（D）。所有其他选项都复杂得多，甚至可能完全不起作用。

## 27. D
**DynamoDB** 是 AWS 托管服务的典型例子。它管理自己的资源，不向用户提供这些资源的控制权（答案 D）。在主动扩展方面，DynamoDB 和 AWS 将处理扩容。此外，DynamoDB 已经在无需用户干预的情况下使用 SSD 和多实例。

## 28. B
**CloudWatch** 的默认设置指定以 5 分钟间隔收集指标。

## 29. B, C
问题在于 CPU，你可以基本理解为“同时要求数据库做的事情太多了”。减少任何数据库 CPU 负载的最简单方法是减少请求和读取，**ElastiCache** 实例和**只读副本**都能做到这一点：减轻主数据库实例的负载。

## 30. A
**Simple Workflow Service (SWF)** 非常适合需要根据应用程序内的步骤执行的任务。此外，SWF 内置了应用程序挂钩，无需自定义基础设施代码即可自动获得。

## 31. B
标准配置下的 **SQS** 队列是 FIFO 的，但不保证顺序。如果必须保留顺序，应将队列设置为 **FIFO**（先进先出）队列（B）。使用 **LIFO** 队列（D）会反转顺序，不满足题目要求。

## 32. C
**Route 53** 有多种有效的路由策略：简单、故障转移、地理位置、地理近邻、基于延迟、多值回答和加权。在提供的答案中，只有 load-balancing（负载均衡）无效。

## 33. D
这里唯一可能有用的答案是 B 和 D：你需要更多处理能力来处理请求，并需要在高峰时段处理无响应的实例。竞价型实例市场对此无济于事，预热负载均衡器在流量突发产生巨大峰值时仍无法处理。在 B 和 D 中，只有 D 解决了无响应问题。通过让请求进入队列，用户完全不会体验到无响应的应用程序；**SQS** 队列将按需扩展，然后实例可以在队列中请求可用时处理它们。

## 34. A, B
适合竞价型实例市场的进程必须能在任何时间运行（B），因为竞价型实例市场不可预测地提供实例；进程必须能够停止、启动并继续工作（A），因为竞价型实例随时可能停止。

## 35. D
所有 S3 存储类都提供 11 个 9 的持久性（99.999999999%）。

## 36. A, C
**EBS** 使用块级存储，而 **S3** 使用对象存储（A）。此外，默认情况下，当附加的实例停止时，**EBS** 卷会被删除。虽然这可以更改，但这确实导致 EBS 卷默认是临时的，而 S3 默认不会消失。

## 37. B
关键在于管理成本的要求。选项 C 不具成本效益，因为它需要昂贵的 Oracle 许可证。选项 D 需要更大的实例，也会产生新成本。选项 A 可能有效，但运行自定义数据库安装可能比 RDS 成本更高，且会产生显著的管理开销。只有选项 B 提供了“原地”成本选项。在同等比较中，Aurora 通常优于 MySQL，尽管从 MySQL 迁移到 Aurora 会有一些开销。

## 38. C, D
**ELB**（弹性负载均衡器）和 **DynamoDB** 都提供容错能力，ELB 提供负载均衡。此外，这两项服务都在无需用户干预的情况下自动实现冗余。**Lightsail** 和 **AWS Organizations** 是用于 AWS 部署和管理的服务，而非提供冗余和高可用性。

## 39. A, D
**EC2** 实例不是自动冗余的；作为架构师，你需要额外工作以确保跨 AZ 的应用程序冗余。虽然 **RDS** 作为一项服务具有容错能力，但它不是自动高可用的。例如，Multi-AZ 设置可以解决这一需求。相反，**S3**（B）和 **SQS**（C）都能跨可用区自动实现高可用。

## 40. D
AWS 不允许在未提前通知的情况下运行漏洞扫描。有一些使用 AWS 批准工具的预批准扫描，但通常情况下，你需要在运行漏洞扫描前联系 AWS 账户经理或支持团队。
