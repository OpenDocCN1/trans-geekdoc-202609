
# AWS 认证考试题目解析

## 负载均衡器

### 65. C
ALB 在第 7 层（单个请求/应用层）运行。网络负载均衡器在第 4 层（连接/传输层）运行。没有负载均衡器在第 1 层运行，且 TCP/OSI 栈中不存在第 8 层。

### 66. B
ALB 在第 7 层（单个请求/应用层）运行。网络负载均衡器在第 4 层（连接/传输层）运行。没有负载均衡器在第 1 层运行，且 TCP/OSI 栈中不存在第 8 层。

### 67. B, C
经典负载均衡器在 TCP 栈的连接层（第 4 层）和请求层（第 7 层）均可运行。ALB 在第 7 层（单个请求层）运行。网络负载均衡器在第 4 层（连接/传输层）运行。

### 68. D
借助 ALB 的新特性，所有这些用例均受支持。重要的是要认识到 ALB 可跨容器进行负载均衡，这使得 B 正确，并指向 D：以上皆是。

### 69. B
这是一个困难的问题，处于架构师考试可能询问的边缘。然而，可以使用负载均衡器在 VPC 内部运行。它可以被指向内部，而非面向互联网，并将流量分发到 VPC 的私有 IP。

### 70. B
ALB 在路由和负载分发方面提供最大的灵活性。

### 71. C
网络负载均衡器可处理题目中提到的极高请求负载，并能在静态 IP 地址实例间路由。

### 72. B
ALB 提供 SSL 终止，并通过与 SSL 进程的紧密集成，使 SSL 卸载过程变得非常简单。虽然 ELB 也能处理 SSL 终止，但它不提供 ALB 所具备的管理功能。

### 73. D
ALB 和 ELB 均提供 SSL 终止。虽然考虑到 SSL 证书管理（因其 ACM 集成）时 ALB 是更好的选择，但若仅考虑 SSL 终止，ELB 和 ALB 均正确。

## Route 53

### 74. D
Route 53 默认支持最多 50 个域名，但可通过申请提高此限制。

### 75. D
Route 53 支持提到的所有记录类型，包括别名记录。

### 76. A
Route 53 支持区域顶点（裸域）记录。

## ElastiCache

### 77. A, B
ElastiCache 提供两种引擎：`memcached` 和 `redis`。C 和 D 根本不是真实存在的事物！

### 78. D
通过 AWS 使用 ElastiCache 时，其会处理所有这些任务及更多：硬件预置、软件补丁、设置、配置、监控、故障恢复和备份。

### 79. B, D
这是另一个怪异答案集的示例，有时会出现在 AWS 考试中。在这种情况下，所有答案均有效，这意味着需选择两个：B 和 D（D 引用了其余两个 A 和 C）！

### 80. A, C
ElastiCache 是内存数据存储（A），可跨实例分片（C）。它本身不是数据分发机制，因此 B 不正确。它也完全不是监控解决方案（D）。

## CloudFront

### 81. D
CloudFront 允许通过 `CloudFormation`、`AWS CLI`、`AWS 控制台`、`AWS APIs` 以及 AWS 提供的各种 `SDKs` 进行交互。

### 82. A, C
CloudFront 可作为多种 AWS 服务的前端：`AWS Shield`、`S3`、`ELBs`（包括 `ALBs`）和 `EC2` 实例。

### 83. B, C
CloudFront 可作为多种 AWS 服务的前端：`AWS Shield`、`S3`、`ELBs`（包括 `ALBs`）和 `EC2` 实例。

### 84. A, B
CloudFront 可作为多种 AWS 服务的前端：`AWS Shield`、`S3`、`ELBs`（包括 `ALBs`）和 `EC2` 实例。它最近还支持 `Lambda@Edge` 作为源站。

### 85. A, C
这有点难度，因为 CloudFront 通常与性能（A）相关联，而非其他。然而，CloudFront 还与许多托管 AWS 服务深度集成，如 `S3`、`EC2`、`ELBs` 甚至 `Route 53`。

### 86. B, D
CloudFront 自动提供 `AWS Shield`（标准版）以防护 DDoS，还可与 `AWS WAF` 和 `AWS Shield Advanced` 集成。这些结合可保护边缘内容。HTTPS 非强制（故 A 不正确），且 CloudFront 不涉及 `KMS`（C）。

### 87. B, D
边缘节点数量多于区域和可用区数量。

### 88. A, C
CloudFront 易于设置，让你无需合同即可创建全球内容分发网络（A）。它也是低延迟分发内容的机制（C）。创建网站和 B、D 中提到的实际文件存储并非 CloudFront 功能，而是 LightSail（例如）和 `S3` 的功能。

### 89. A, B
CloudFront 可从 `S3` 提供静态内容，也可提供由 `EC2` 实例生成的动态内容。

### 90. B
创建 CloudFront 分发时，你需为静态和动态内容注册一个域名。客户端应使用该域名。

### 91. A, C
CloudFront 始终处理接收到的请求。它要么返回缓存的请求内容（A），要么通过向源站服务器请求来获取内容（C）。它不会重定向客户端（D），也不会直接透传请求（B）。

### 92. C, D
A 和 B 均正确。C 不正确，因为路由会发生在离客户端最近的边缘节点，而非源站服务器。D 错误；`RDS` 不是 CloudFront 的有效源站服务器。

### 93. D
从任何区域向 CloudFront 边缘节点移动数据不收取费用。

### 94. A, B
`S3` 存储文件，CloudFront 存储文件副本，故 A 正确。两者均按需加密文件（B）。只有 CloudFront 缓存文件（C），只有 CloudFront 能保证低延迟分发（D）。

### 95. B, D
CloudFront 可存储并提供静态内容（HTML 和 CSS，选项 D）和动态内容（PHP，选项 B）。SQL 查询无法直接返回，实际的 `Lambda` 函数也不行。你可以作为前端提供 `Lambda@Edge` 函数的结果，但不能是函数本身。

### 96. A, B
CloudFront 支持多种源站服务器，包括非 AWS 源站服务器（A）。无论区域，它也支持 `EC2`（B）。它不支持 `RDS` 或 `SNS`。

### 97. A
边缘节点是分发 CloudFront 内容的数据中心。边缘节点分布在全球各地。

### 98. B
分发是包含你的源站服务器及这些服务器内容如何通过 CloudFront 分发的设置。它不特指某一时间点的缓存内容。

### 99. D
边缘节点默认每 24 小时检查一次更新内容，但此值可更改。

### 100. A
边缘节点可设为 0 秒过期周期，实际上意味着不进行缓存。

### 101. B, C
最明显的罪魁祸首是极低的过期周期（B）。确保时间不接近 0。除此之外，特别是结合极低的过期周期时，你的计算资源或存储资源可能被请求淹没。考虑使用额外的源站服务器。

### 102. A
将过期周期设为 0 会使所有内容过期（A）。这实际上会降低响应时间，与 DDoS 攻击无关。虽然技术上它会始终返回最新内容（D），但这不是采取此步骤的好理由；若周期保持该值，将违背 CloudFront 的初衷。

### 103. B, C
首先，无论在 `AWS 控制台`（A）还是 `AWS CLI`（D）中，均无机制直接与 CloudFront 分发或边缘节点上的文件交互。其次，正确方案是移除文件，然后等待过期周期触发重载——可通过将该时间设为 0 来强制执行。

### 104. C
你需先从 CloudFront 的源站服务器移除文件，再做其他操作，因为文件是从源站复制的。若文件存在，最终会出现在边缘节点。随后，文件移除后，可将过期周期设为 0，缓存将更新——导致文件被移除。
