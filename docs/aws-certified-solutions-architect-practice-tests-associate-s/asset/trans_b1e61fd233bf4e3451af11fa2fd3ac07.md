

## 207. B, D
RDS 提供 SQL 交互以及通过 RDS Web API 的访问。RDS 实例**不**允许通过 SSH 或 RDP 访问。

## 208. C
RDS 允许的备份保留期最长可达 35 天。

## 209. A
你无法使用 RDS，因为题目明确指出你是在 EC2 上安装 Oracle，而不是使用托管服务。在这种情况下，你需要最快的可用磁盘空间，即 `EBS`（Elastic Block Storage，弹性块存储）。

## 210. B, D
每当提到 OLTP，只需寻找 RDS 支持的数据库选项；如果不行，则寻找关系型数据库。在本题中，符合这些标准的答案是 `MariaDB` 和 `Aurora`。

## 211. A, C
每当提到 OLTP，只需寻找 RDS 支持的数据库选项；如果不行，则寻找关系型数据库。在本题中，符合这些标准的答案是 `PostgreSQL` 和 `SQL Server`。由于题目询问哪些**不**是合适的选项，正确的选择是 `Kinesis` (A) 和 `Redshift` (C)。

## 212. A, C
`Multi-AZ` 部署通过备用数据库提供灾难恢复选项。这也隐式地提供了数据冗余。

## 213. B, D
读取副本设置旨在通过提供额外的数据库来读取，从而减轻单个数据库实例的负载。这也具有通过跨多个实例分散流量来降低网络延迟的“副作用”。

## 214. A, C
读取副本设置旨在通过提供额外的数据库来读取，从而减轻单个数据库实例的负载。应用程序可以从副本读取 (A)，但不能写入 (B)。只有主实例——通过 RDS 和 AWS——可以将更改“写入”副本 (C)。

## 215. C
`Multi-AZ` 设置通过备用实例提供灾难恢复 (A 和 B)，并且所有 RDS 数据库都支持 `Multi-AZ` (D)。这只剩下 C，它**不**提供（也是正确答案）。因为只有主实例可访问，其性能并不比标准 RDS 设置更高。

## 216. B
`Multi-AZ` 设置使用同步复制 (B) 将数据备份到备用实例，用于灾难恢复目的。

## 217. D
读取副本使用异步复制 (D)，在可能的情况下将数据推送到读取副本，以提高读取性能。

## 218. A
读取副本旨在通过为应用程序添加额外的实例以增加读取次数，从而为应用程序提供可扩展性。

## 219. C
`Multi-AZ` 设置关乎灾难恢复，因此关乎持久性。它们提供自动备份（所以不是 A），升级发生在主数据库上然后复制（所以不是 B），并且有一个主实例和通常一个备用实例（所以不是 D）。这只剩下 C：持久性。

## 220. B
AWS 为单个数据库实例最多提供五个读取副本，可通过 AWS 控制台进行配置。

## 221. A, B
`DynamoDB` 是 NoSQL 数据库，而读取副本需要 RDS（所以 A 正确，因为它不支持读取副本）。`Redshift` 不是数据库，而是数据仓库工具，所以也应选择。`MySQL` 和 `MariaDB` 均通过 RDS 支持读取副本。

## 222. A, C
`DynamoDB` 是 NoSQL 数据库，确实提供“一键式”扩展 (A)。你可以随时扩展数据库大小，**无需**更改实例大小（这与 RDS 实例不同）。这使得 C 为真。

## 223. B, C
`DynamoDB` 比 RDS 更容易扩展，因为它不需要读取副本或实例大小更改来扩展，使得 A 为假。`DynamoDB` 确实使用 SSD 驱动器，所以 B 为真。根据 AWS 文档，它还分布在三个地理位置不同的数据中心，所以 D 正确。

## 224. A
`DynamoDB` 默认使用最终一致性读取，这意味着读取可能不会立即反映非常近期的写入结果。其余选项不是实际的一致性模型。

## 225. A, D
`DynamoDB` 默认使用最终一致性读取，这意味着读取可能不会立即反映非常近期的写入结果。它还提供强一致性读取模型，始终反映最近的写入操作。

## 226. A, D
当最近写入的数据无法返回时，强一致性读取模型会出现延迟。由于强一致性读取模型保证返回最新数据，在该数据可用之前，无法发送响应。选项 A 和 D 描述的就是这种情况。选项 B 涉及复制，这与此上下文无关，C 涉及之前的读取而非写入。

## 227. D
`VPC` 对支持的子网类型和数量限制较少。它们当然可以支持单个和多个私有及公有子网并存。

## 228. A, D
默认 `VPC` 中的所有实例在启动时默认都会获得公有和私有 IP 地址。

## 229. C, D
此处所有选项均有效。`EC2` 实例可以拥有公有和私有地址、弹性地址，以及 IPv4 和 IPv6 地址。

## 230. B, C
不存在 `VPC` 与自身对等连接的概念，且 `VPC` 只能与其他 `VPC` 对等连接，不能与子网对等连接。这使得 A 和 D 不正确。`VPC` **可以**与同一账户或不同账户中的其他 `VPC` 对等连接 (B 和 C)。

## 231. A
`/16` 提供 65,536 个 IP 地址。在 CIDR 表示法中，数字越小，IP 地址池越大。

## 232. A
`SWF` 代表 Simple Workflow，`Amazon SWF` 是 Amazon Simple Workflow Service。

## 233. D
只要交互可以通过 HTTP 请求和响应进行管理，`SWF` 对工作流的语言没有限制。

## 234. B
`SWF` 提供 API，但它既不是 AWS 特定的 API，也不是特定语言的。相反，`SWF` 支持标准的 HTTP 请求和响应。

## 235. D
`SWF` 代表 Simple Workflow，是一项 AWS 托管服务。这应该是一个线索，表明关键因素是工作流管理。任务通过 `SWF` 在应用程序组件间进行处理和协调。

## 236. C
`SWF` 通常被认为是异步服务，但也支持在需要时进行同步任务处理。

## 237. B
`SES` 是 Simple Email Service，用于 AWS 应用程序和服务的发送和接收电子邮件。

## 238. D
`SQS` 是 Simple Queue Service。这应该是一个提示，但题目中的**消息传递**才是关键词。`SQS` 确实提供排队功能，但本质上是一个基于队列的消息传递系统。

## 239. C, D
`SNS` 是 Simple Notification Service，`SQS` 是 Simple Queue Service。两者不可互换 (A 错误)。`SNS` 推送通知，而 `SQS` 允许拉取其消息（所以 B 错误，但 D 正确）。最后，`SNS` 处理通知，`SQS` 处理消息 (C 正确)。

## 240. B, D
工作节点 (D) 可以轮询 `SQS` 获取新消息 (B)，并在消息可用时拉取这些消息。任务与 `SWF` 相关，而通知与 `SNS` 相关。

## 241. B, C
`SNS` 是基于推送的服务 (C)，将通知 (B) 推送给订阅了相应主题的任何内容。

## 242. A, B
`SWF` 与任务相关，并因保证所有任务仅交付一次而与 `SQS` 等服务不同。

## 243. A, B
`SNS` 提供可订阅的主题；然后与该主题相关的通知会被推送给所有主题订阅者。

## 244. A
`SWF` 任务被分配一次且仅一次。

## 245. B
这有点晦涩，但即使不确定，也应该能推理出来。主题只是一个名称或“类别”，订阅者可以附加到其上以接收通知。因此，链表和命名消息讲不通（它们在 AWS 文档中也基本从未见过）。`IAM` 角色是 AWS 构造，但角色与权限相关。这只剩下 B，`Amazon Resource Name`，这是正确的。
