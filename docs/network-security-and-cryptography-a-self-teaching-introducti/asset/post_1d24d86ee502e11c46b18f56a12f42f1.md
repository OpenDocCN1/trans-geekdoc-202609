
- 1. Undefined Trust (the field is initialized to this value)
- 2. Unknown User
- 3. Usually not trusted to sign keys
- 4. Usually trusted to sign keys
- 5. Always trusted to sign keys
- 6. Ultimate Trust

Whenever a public key certificate is inserted into the public key ring of some user, trust values are assigned to the fields as follows:

i. Assigning value to Owner trust: PGP looks into the private key ring of user. If the Public Key indicated in Public Key Certificate also appears in Private Key Ring of user “A,” then it indicates that “A” itself is the owner of subject Key Certificate. Then, the “Complete Trust” value is assigned to the “Owner Trust Field” of subject Key Certificate. Otherwise, PGP will inquire “A” (the owner of subject Key) about the extent of trust “A” has in “B” for signing of other keys, and “A” will indicate one of the following trust values that is assigned to the Owner Trust Field:
- 1. Unknown user
- 2. Usually not trusted to sign keys
- 3. Usually trusted to sign keys
- 4. Always trusted to sign keys

ii. Assigning values to “Signature Trust”: When a public key certificate is inserted on public key ring, it will have some signatures by other users. More signatures may be obtained subsequently. If a Signature has Public Key Certificate, then the value of “Owner Trust Field” from signer’s public key is copied into Signature Trust Field; otherwise, a value of “Unknown User” is assigned to Signature Trust Field.

iii. Determining the value of Key Legitimacy Field: The value of Key Legitimacy Field is determined from signature trust fields in the certificate. If any of Signature Trust values has the value "Ultimate Trust,” then it is taken as weight "one" and the Key Legitimacy Field is set to the value "Complete Trust"; otherwise, it is computed as a weighted sum of the associated Signature Trust values. The weights assigned as follows:
- 1. Unknown user 0
- 2. Usually not trusted to sign keys 0
- 3. Usually trusted to sign keys 1/Y
- 4. Always trusted to sign keys 1/X

Here, if i/X > 1/Y, depending upon the weighted sum, the Key Legitimacy Field is assigned one of the following values:
- Key ownership not trusted (when weighted sum is low)
- Key ownership marginally trusted (when weighted sum is high but < 1)
- Complete trust in key ownership (when weighted sum = 1)

Thus, when the value of the weighted sum reaches one, the binding between the public key and its owner is considered to be complete and trustworthy.

## 11.5 S/MIME (SECURE MULTipurPOSE INTERNET MAIL EXTENSION)

S/MIME is an extension of the RFC822 framework that addresses some of the limitations and problem areas of SMTP (Simple Mail Protocol).

### 11.5.1 S/MIME Functionality

The following are the S/MIME functionalities:

1. Enveloped Data: it caters for symmetric encryption of message contents using a session key. The session key encrypted using the recipient's public key is appended to the encrypted contents of the message. The overall package is called Enveloped Data. The steps required to prepare Enveloped Data are:
a. Generate pseudorandom session key for the chosen symmetric encryption algorithm (3DES or RC2/40).
b. For each recipient, encrypt the session key with the recipient's Public Key using the chosen public encryption algorithm.
c. For each recipient, prepare a Recipient-Info block that contains:

Recipient-Info block:
| Identifier of Recipient's Public Key Certificate |
| Identifier of the Algorithm used to encrypt the session key |
| Encrypted Session Key |

d. Encrypt the message contents with the session key, using the chosen symmetric encryption algorithm.
e. The Recipient-Info block, followed by the encrypted message contents, constitute the Enveloped Data as follows:

Enveloped Data:
| Recipient-Info block (1) |
| Recipient-Info block (2) |
| - |
| Recipient info block (n) |
| Encrypted Message Contents |

![](img/d3b56042c756fbcc011ff06f1b9f53f0_456_0.png)

f. The Enveloped-Data block is encoded using base64 (B64) encoding.

2. Signed-Data: The Signed-Data block caters for multiple signatures. A Digital Signature is formed by taking a message digest of the message contents using the chosen message digest algorithm and then signing the digest with the signer's private key using the chosen signature algorithm. The message contents plus signature are then encoded using base64 transformation. A Signed-Data message can only be accessed by a recipient with S/MIME capability. The steps required to prepare a Signed-Data are:
a. Select a message digest algorithm (SHA or MD5) and compute a message digest of the message contents.
b. Encrypt the message digest with the signer's private key, using the chosen signing algorithm.
c. Prepare a Signer-Info block that contains:

Signer-Info block:
| Signer's Public Key Certificate |
| Identifier of the Algorithm used to generate the Message Digest |
| Identifier of the Algorithm used to encrypt the Message Digest |
| Encrypted Message Digest |

d. Prepare the Signed-Data that consists of:

Signed-Data:
| Message Algorithm Identifier |
| Message Contents |
| SignerInfo |

e. The Signed-Data is encoded using base64 transformation and then sent to the intended recipients. To recover the signed message the recipient will reverse the base64 transformation, use the signer’s public key to decrypt the message digest (m1), and compute the message digest (m2). If m1 = m2 then the signature is verified.

3. Clear Signed Data: It is similar to Signed Data that the message contents can be viewed by a recipient not having S/MIME capability. But such recipients will not be able to verify the digital signature.

4. Signed and Enveloped Data: This functionality combines the basic primitives of Encrypted Data and Signed Data to achieve the following:
- a. The Encrypted Data may be Signed, or
- b. The Signed Data or Clear Signed Data may be encrypted.

Table 11.1 shows the Cryptographic Algorithms supported by S/MIME

TABLE 11.1 Cryptographic Algorithms Supported by S/MIME

| Function | Mandatory Support | Referred Support |
|---|---|---|
| Message Digest Generation | SHA-1 | MD-5 |
| Message Digest encryption to form a Digital Signature | DSS/DSA | RSA with key-size 512–1024 bits |
| Session Key encryption using recipient's Public Key | Diffie-Hellman Key Exchange Algorithm | RSA with key-size 512–1024 bits |
| Encrypt message contents with one-time session | 3DES | RC2/40 |
