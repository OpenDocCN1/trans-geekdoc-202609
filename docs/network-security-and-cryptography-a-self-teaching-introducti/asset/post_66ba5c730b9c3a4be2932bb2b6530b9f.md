Message (5): Request Service: This message is sent by C to application Server V for obtaining the required service.

$C\rightarrow V: Ticket_c || Authenticator_v$
$Authenticator_{c^2} = E_{Kr,c}[ID_c || AD_v || TS_s]$

The Authenticator$_{c^2}$ is encrypted using $K_{r,c}$ that is shared between C and V. This will assure V that the message has been obtained from C only: V compares values of ID and AD specified in the [message]. If both match, it authenticates the user to V. Now, V sends a message to $C$ echoing back ($TS_s+1$) where $TS_s$ is time-received from C in message 5. This is for mutual authentication of C and V.

Message (6): Application Server to Client: This message is sent by the Application Server to C in response to the request for service.

$V\rightarrow C: E_{Kr,c}[TS_s+1]$

# 9.5.1 Inter-Kerberos Authentication

Different organizations have their Kerberos Realms catering to their registered clients and servers.

But Clients in one realm may like to access servers in other realms. Also, servers in a realm may be willing to provide service to clients in other realms the clients are authenticated by their own parent Kerberos. If a user logs on at Client Workstation at $C$ in Realm “A” intends to access a Remote Server $V$ in Realm “B”, the user request is processed as follows:

- 1. The client requests a Ticket to access the local TGS. The request comprises the ID of the user logged on the Client Workstation $C$, $ID_{tgs}$, and Time Stamp $TS_{tgs}$.

- 2. The local AS issues Ticket $_{tgs}$, and a session key $K_{c,tgs}$ for communication between C and the local TGS. The Ticket $_{tgs}$ is encrypted using secret key $K_{as,tgs}$ that is shared between the AS and the local TGS. So, Ticket can be opened only by the local TGS. The session key $K_{c,tgs}$ is to be used for communication between C and the local TGS.

- 3. Now, the client workstation sends a request to the local TGS for issue of a Ticket for accessing Remote TGS in Realm “B”. The request comprises $ID_{tgrem}$ Ticket $_{tgs}$ and Authenticator $_{c^1}$.

- 4. The local TGS issues Ticket and session key $K_{cgs}$. The ticket is encrypted using secret key $K_{tgs}$ that the local TGS shares with the remote TGS so that the remote TGS can open the ticket. The session key $K_{cgs}$ is used for communication between C and the remote TGS, that is, TGS_{rem}$.

# 9.5.2 Kerberos Version 5 Authentication Sequence

Message 1 Authentication Service Request (KRB_REQ) from Client to Authentication Server (AS)
$C\rightarrow AS: Options || ID_e || Realm_e || ID_{tgs} || Times || Nounce_e$

Where
- Options: Client specified options for Ticket Granting Ticket (TGT) requested from AS
- FORWARDABLE: The Ticket to be forwardable
- PROXYABLE: The ticket to be proxyable, etc.

The Authentication Server's response will be reflected in Flag.
- ID_e: User ID on the Client.
- Realm_e: Realm of the Client.
- ID_{tgs}: TGS identification.
- TIMES: includes validation period (From ... To).
- Nounce_e: A random integer value to prevent replay attacks

Message 2 Authentication Service Reply (KRB_AS_REP) from AS to C, for obtaining Ticket Granting Ticket (TGT) and a Session Key $K_{c,tgs}$ for communication between C and TGS.
$AS\rightarrow C: Realm || ID_e || Ticket_{tgs} || E_{k_{c,tgs}} || Times || Nounce_e || Realm_{tgs} Ticket_{tgs} || E_{k_{c,tgs}} [Flags || Realm_e || AD_e || Times]$

The Flag contains the options available for use of Ticket_{tgs}, like Forwardable, Proxyable, and so on. Times will indicate the validity period, and this can be postdated in the Flag.

Message 3 Ticket Granting Service Request (KRB_TGS_REQ) from C to TGS, for obtaining Service Ticket and a Session Key $K_{c,s}$ for communication between C and Application Server V.
$C\rightarrow TGS: Options || ID_e || Times || Nounce_e || Ticket_{tgs} || Authenticator_{Authenticator_{c^1}$

Message 4 Ticket Granting Service Reply (KRB_TGS_REP) from TGS to C, for conveying of Service Ticket, and a Session Key $K_{c,t}$ for communication between C and V.
$TGS\rightarrow C: Realm_e || ID_e || Ticket_e || E_{K_{c,s}}[K_{c,t} || Times || Nounce_s || Realm_s || ID_s] Ticket_e || E_{K_c}[Flags_e || Realm_e || AD_e || Times]$

The Flag will contain the options available for the use of Ticket$_e$, for forwardable, Proxyable, and so on. Times will indicate the validity period. Its start-time can be postdated, and this fact can be indicated in the Flag.

Message 5 Service Request (KRB_AP_REQ) from C to Application Server for obtaining service.
$C\rightarrow V: Options || Ticket_e || Authenticator_{c,s}$
$Authenticator_{c,s} = E_{K_{c,s}}[ID_c || Realm_s || Sub-Key || Seq#s]$

Message 6 Service Reply (KRB_AP_REP) from Application Server to C, for mutual authentication.
$V\rightarrow C: E_{K_{c,s}}[TS_s || Seq#s]$

# 9.5.3 Differences between Kerberos V4 and Kerberos V5

Kerberos V4 has the following environmental and technical limitations, which have been successfully overcome in Kerberos V5:

- 1. **Encryption Algorithm**: Kerberos V4 permits use of only DES for encryption. But, Kerberos V5 permits use of other encryption algorithms also; a tag attached to the ciphertext indicates the ID of the algorithm used.

- 2. **Communication Protocol**: Kerberos V4 uses only IP addressing for communication; but Kerberos V5 permits use of other network addressing protocols also; a tag indicates the ID of the network addressing used.

- 3. **Protocol for Message Byte Ordering**: Kerberos V4 uses a little-endian or big-endian format, which is tagged to the message; but in Kerberos V5, the structures are defined using Abstract Syntax Notation (ASN.1) and Basic Encoding Rules (BER), which provide unambiguous byte ordering.
