
# 安全原则与策略形式化

另一个涉及代码透明度需求的安全原则是**开放设计**（open design）原则。互联网工程任务组（IETF）的工作就是一个典型示例。作为如今无处不在的开源社区的先驱，IETF 自 1969 年以来一直管理着一个开放且协作的软件工程流程。其使命是产出相关、高质量的技术工程文档，以影响人们设计、使用和管理互联网的方式，从而让互联网运行得更好（IETF，[n.d.](#c04.xhtml#c4-bib-0005））。其志愿者成员（大多数由雇主付薪，以帮助影响标准）共同努力，就应实施哪些功能达成粗略共识。他们还协作编写和测试概念验证代码，随后通常会共享这些代码。指定代码特性和功能的标准，通过一种称为“请求评论”（request for comments）的流程公开分发。如果他们将协议保密，那么只有少数人会审查这些协议，在协议发布前有人发现漏洞的概率就会非常高。其态度是：如果你无法向朋友解释安全机制是如何工作的，那么唯一会弄明白的人，就是那些试图寻找你漏洞的人。在网络安全领域，对此的格言是：“当你把朋友挡在门外时，进入的将是你的敌人。”

正如我们从**预防、检测、响应**（prevent, detect, respond）三位一体中所知，如果无法预防，就应尽可能做到检测。当系统的机密性、完整性或可用性受到破坏时，无论是出于恶意还是意外，首要问题是：该事件是由授权用户造成的，还是授权用户了解未授权用户如何绕过控制从而做到的。这些问题的答案通常存在于系统活动日志中。系统算法中每一个导致访问宝贵资源的机制或活动，都应记录其激活情况以及任何访问控制检查或引用监视器操作的结果。例如，当请求某个资源时，其引用监视器会记录所有输入、查询其规则列表、检查并记录结果，然后记录它发回给请求者的响应。这样一来，如果资产确实被破坏，就有地方可以查看发生了什么以及何时发生。如果这种日志活动在系统部署时未创建，那么在发生网络安全事件时，当 SecOps 去查找时，通常将没有日志数据可用。

此外，仅开启标准日志是不够的。还必须有足够的信息，以便与其他系统产生的数据在端到端威胁向量中进行关联。在许多情况下，威胁行为者会先通过远程访问系统接入网络，然后穿过内部网络网关，接着登录到服务器或工作站，再使用数据库登录提取数据。这些设备的每个引用监视器都应收集源连接可用的所有数据。例如，用户在这些设备上建立的每个连接，都可以收集源 IP 地址和目标 IP 地址。还可以查询带有源 IP 地址的设备的身份验证日志，以识别在该先前登录时拥有该 IP 地址的用户名。法医调查人员会尝试这种查询，以收集他们需要的数据，找出是谁在何时做了什么。这些技术不仅用于事后法医分析，还用于在寻找绕过行为时进行实时检测。IP 地址踪迹可以被引用监视器规则用于拒绝访问那些用户名与同一网络连接上的先前身份验证所用用户名不匹配的请求。如果踪迹中至少有一个身份验证使用了授权的多因素身份验证，则应有首次登录、第二因素身份验证和内部资源授权的记录。只有在满足这些条件后，系统才应认为用户已获授权并允许处理事务。如果你有一条端到端事务的记录，但缺少中间步骤（即第二因素身份验证）的记录，那么你就知道有人能够将消息一直发送到第三层深度，绕过了所需的身份验证序列。鉴于日志中存在这种损坏的消息序列，很明显你的网络存在安全问题，并且即使尚未宣布安全事件，也有可能识别出问题。

这一概念被另一个安全原则所概括，即**全面问责**（comprehensive accountability）。这是一项要求，即保留所有重大系统活动的完整审计日志，并以防篡改的方式存储，以供未来调查和入侵检测算法的自动化分析之用。具有这些功能的安全数据库的名称是安全信息和事件管理（SIEM）。SecOps 通常会配置所有设备，自动将管理员执行的每个命令和所有应用程序安全日志复制到 SIEM 中，以便在需要进行法医调查以确定网络安全事件根本原因时安全保存。管理和业务功能及数据访问会被监控、审计，并在适当时自动分析，以识别并向 SecOps 发出系统资源可能被滥用的警报。

综合使用，安全原则在建立政策以将风险偏好维持在可接受水平时，是非常实用的词汇表。[表 4.1](#c04.xhtml#c4-tbl-0001) 提供了迄今介绍的安全原则以及政策通常基于的其他安全原则的摘要。

## 4.2.2 形式化

政策是基于安全原则的高层管理指令，与风险偏好相关联。它们通常在不参考任何实现的情况下制定，但至少应指明企业中谁主要负责确保遵守指令。因此，文档可能在组织层面围绕角色和职责进行正式组织。

政策的最关键功能是保持企业网络安全计划与其支持的业务流程之间的战略一致性。也就是说，随着威胁环境和业务环境的演变，政策必须保持其相关性。因此，运行网络安全计划的人与总体运营企业的人之间必须保持畅通的沟通渠道。这不仅是为了拥有适当的政策，也是为了确保受政策指令影响职能的人能够获得授权，以遵守这些指令执行其职责。

[表 4.1](#c04.xhtml#R_c4-tbl-0001) 安全原则

| 安全原则 |

| --- |

| `Complete Mediation` || 所有访问请求都由引用监视器拦截，以验证身份验证和授权。 |

| --- | --- |

| `Comprehensive Accountability` || 所有 `administrative` 和 `business functional` 和 `data` 访问都受到监控、审计，并在适当时自动分析，以识别并警报系统资源可能被滥用的情况。 |

| `Defense in Depth` || 所有对资源的访问都需要通过多个单独配置的控制层进行授权。 |

| `Economy of Mechanism` || 保持设计尽可能简单和小巧。 |

| `Fail Safe` || 除非明确授权，否则拒绝访问。 |

| `Least Common Mechanism` || 当多个用户共享同一系统机制时，尽量减少分配给每个用户的资源。 |
