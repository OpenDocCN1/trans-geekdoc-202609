

网络安全从业者常常忽略这一区别，直接将风险指标聚焦于发现和修复使系统易受攻击的安全属性，例如 CVE。这种关注点导致的指标看起来如 [图 7.21](#c07.xhtml#c7-fig-0021) 所示。2000 年代初期，“坏度计”（badness‐ometer）一词被引入用来描述此类安全指标（McGraw [2006](#c07.xhtml#c7-bib-0006)）。坏度计只能显示安全性差，而不能显示安全性优秀，因为它只衡量是否存在漏洞。它可以提供一个名义上的“坏”标签，但不能确定服务器绝对不存在漏洞，因为扫描器可能无法测试所有漏洞，也无法测试零日漏洞。因此，该指标不能正确地用于授予“好”的标签。[图 7.21](#c07.xhtml#c7-fig-0021) 底部的图表是一个失败的验证指标，因为它将漏洞（坏事）的数量与漏洞被识别后的时间度量相结合，并结合管理层设定的漏洞应尽快修复的时间阈值。按月间隔采取的三项措施加起来形成一个指标，显示什么是“坏”的——安全性能目标未实现。在目标与指标的语境下，它表明系统构建不正确。也有坏度计作为目标指标的示例，例如每年因网络攻击造成的货币损失（假设你的目标是没有任何损失）。除了漏洞扫描指标外，这些还包括但不限于软件源代码扫描指标、红队演习读取、渗透测试结果和审计结果。通常，坏度计措施由于不断变化的威胁和漏洞格局而无法满足一致性和可重复性的标准。因此，它们不应作为 KRIs 的唯一来源。

在从风险偏好到程序的整个控制集中，以及在每个控制密度层中，都有可衡量的网络安全属性。无论是否有企业标准，都存在技术配置；如果没有，则有行业衡量标准（例如，CIS）。只要有程序，而程序通常是普遍存在的，就会有被遵循的监控措施。只要有反映企业使命的风险偏好，就有方法来确定它是否得到维持。

以这种透明方式查看的控制，使目标受众更容易把握控制文档链中每个环节的要点，而对于新加入组织的人来说，整套控制文档可能既令人生畏又令人困惑。从整体上看待控制，能够激发测量的替代方案，并可能伴随指标，这些指标不仅能证明控制是否按设计运行，还能证明它们是否在实现政策或战略层面指定的控制目标方面有效。这一点很重要，因为除非程序与其支持的业务流程和政策之间存在直接链接，否则遵循程序的人可能不清楚控制的目标。

也许建立业务风险偏好与网络安全控制之间联系最简单的领域，是内部使用软件的 Web 应用程序开发。安全软件开发流程通常包括开发、质量保证测试和生产支持之间的代码交接（OWASP [2020](#c07.xhtml#c7-bib-0008)）。每个组织都会有少数安全程序，旨在确保应用程序在进入开发之前符合企业安全架构设计标准。在开发阶段，可能要求进行自动化静态和动态代码分析，以确保没有程序员和管理员（admins）最常见的那些会使系统易受黑客攻击的错误证据。这些分析应能揭示后门，例如硬编码密码或权限，或整个未经身份验证的 Web 可访问数据库连接。在质量保证阶段，这些测试将重复进行，并辅以应用程序用户角色和数据权限测试。质量保证程序可能包括独立的渗透测试和操作系统安全配置健康检查。在生产阶段，所有这些测试都将重复进行，应用程序还可能接受独立审计。每个阶段的控制测试结果将被跟踪，如果在开发阶段看似通过的测试，但在质量保证和/或生产阶段发现控制不足，这将显而易见。这些测试在生产阶段失败的程度是一个关键控制指标，因为这些指标可能提供业务流程软件中控制验证和确认失败的证据。

这个关键控制指标在 [图 7.22](#c07.xhtml#c7-fig-0022) 中得到说明。它根据组织特定的选定标准比较了三个应用程序。请注意，所有应用程序都已记录为通过了所有开发测试。如果不是这种情况，该应用程序就无法进入质量保证阶段。然而，有一个应用程序在质量保证阶段失败，因此生产测试记录为 0%，这并非因为它们失败了，而是因为它们尚未发生，因为通过质量保证是部署到生产环境的先决条件。此外，QA 阶段也没有渗透测试分数，通常是因为渗透测试通常是外包费用，因此会推迟到其他测试成功后再进行。取决于组织文化，将这些测试变成一种 DevOps 竞赛可能会有所帮助。这使得如此严格的测试活动感觉不再像是一项苦差事，而更像是一种挑战。

在任何网络安全计划中，安全事件响应都是一个热门话题。利益相关者理解，快速有效地消除安全事件是网络安全计划的主要业务目标。然而，他们并不总是意识到，消除是包含以下步骤的程序中的中间步骤：草稿 → 分析 → 缓解 → 遏制 → 消除 → 恢复 → 。在这个领域，GQM 练习中利益相关者的典型问题是：“消除一次网络安全攻击需要多长时间？”但当 SecOps 团队试图回答这个问题时，他们最终会遇到一些先决问题，例如：

*   自动在安全事件管理系统中创建安全事件的安全工具占比是多少？

*   手动起草安全事件响应工单需要多长时间？

*   分析安全事件需要多长时间？

*   遏制一次网络安全攻击需要多长时间？

这些问题通过响应时间（TTR）指标来回答。如果这些问题以前在阶段级别的细节上从未被问及，那么可能就没有可衡量的安全事件属性来回答它们。安全事件响应记录可能没有字段来记录间歇步骤的时间戳，有些事件几乎立即关闭，因此在所有响应记录中添加间歇步骤也没有意义。实际网络攻击的数据收集仪表将超过每个安全事件收集的数据量。在已知发生攻击之前，安全事件响应记录中可能不会明显看出这一点。
