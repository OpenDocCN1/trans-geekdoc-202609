

也就是说，在事件数据记录中，可能需要花费一些时间来确定的另一项内容是事件 `root cause`。在操作风险分析中，“root cause”是一个术语。它指的是一种情况，即与特定风险事件相比，如果 root cause 未发生，该事件也不会发生。`root` cause 与 `proximate` cause 之间存在差异。在法律环境中，proximate cause 的定义是与犯罪非常接近、无疑导致了犯罪的事件。在 [图 3.27](#c03.xhtml#c3-fig-0027) 描绘的场景中，钓鱼链接可能被认定为 proximate cause，因为事件发生在威胁行为者发送电子邮件时。然而，在操作风险中，也会考虑受害者的情况。例如，如果凶手在黑暗的小巷里刺伤受害者，那么刺伤行为就是受害者受伤的 proximate cause，即与事件最近的原因。但是，如果本应阻止受害者进入黑暗小巷，那么缺乏预防方法也可能被视为受伤的原因。也就是说，如果企业有办法阻止受害者进入那个小巷，那么该控制弱点也可能被视为一个原因。这个例子说明了 proximate cause 和 root cause 之间的区别。Root cause 是指没有该情况事件就不会发生，并且如果消除了该情况，将大大降低事件再次发生的概率，甚至完全防止事件发生。在这个例子中，无法防止刺伤行为，因为那是威胁行为者执行的活动。但是，理论上可以防止自己的员工独自待在黑暗的小巷里。这就是为什么在犯罪猖獗的国家出差的高管通常会获得企业实体保护服务的原因。虽然这听起来像是在指责受害者，但实际上更接近一种减少事件有害后果风险的实用方法。在操作风险中，关注点是事件的启发性特征，即网络防御者从对手与目标之间的交互中吸取的教训。如果可以完成将风险降低到可接受水平的事情，那么对 root cause 已被识别的信心就会增加，消除该 root cause 情况可能会防止事件再次发生。因此，为了识别 root cause，网络安全威胁分析师将仔细记录威胁向量中行为者为实现目标所需采取的步骤，这些更 proximate 的原因将回溯到 root。

成功进行情景分析的关键是一个结构化流程，用于将威胁向量组件映射到用于开发损失估算的数据。当数据或计算过程受到影响时，必须有一个衡量单位来提供该影响的可行估算。示例包括但不限于数据记录数量、丢失的 CPU 周期以及调查所花费的时间。情景总损失估算将取决于基于这些单位的计算。除非清楚该数据包含什么内容以及为什么它应该是计算情景影响的一个因素，否则无法累加负面影响。此外，威胁向量活动与这些衡量单位之间的联系应使用基于事实的证据和支持情景输出的清晰推理进行充分记录。这些单位应使得可以用定量术语记录情景导致的情况，包括但不限于调查威胁行为者活动所花费的时间、预期的数据外泄、恶意软件或勒索软件对数据完整性和/或系统可用性的损害、数据恢复或修复、生产力损失、业务损失、已发生的责任、保险罚款、监管违规以及技术控制恢复（Rohmeyer 和 Bayuk [2019](#c03.xhtml#c3-bib-0012)，第 62–71 页）。

为了充分计算损失，有时可能需要引入外部取证团队或类似顾问，对外包调查的预计成本发表意见。许多公司没有内部取证专家，因为安全事件不常发生，但可能有外部取证团队待命。情景分析是演练他们响应速度以及他们如何帮助遏制事件的机会。

为了确保涵盖所有潜在损失来源，管理良好的情景分析包括由受审查业务流程外的人员进行的 `challenge` 环节。通常，这一角色将由内部审计或独立风险管理部门担任。“挑战者”是必要的，以确保没有人故意忽略网络攻击范围内的关键功能。此外，管理良好的情景分析流程会随着环境的变化而改变和演变，以确保威胁情报是最新的，并且专家的选择不是因为他们在上一次情景分析中表现好，而是因为他们确实是当前受审查情景的专家。

虽然情景分析可能预期会以数据和单位的形式生成损失描述，但练习结束时不太可能获得实际损失数字。一旦所有损失数据汇总完毕，通常会聘请财务分析师来检索所识别单位的实际成本，并计算出最终报告中出现的损失估算值。

在情景研讨会期间，按时间轴分析活动是有帮助的。通常会使用共享工作区来实现此目的。它通常从报告日期开始，但可以向任何一方延长，以显示事件中发生的活动之间的间隔。对于任何给定的网络安全攻击，至少有三个重要的时间戳，可能还有其他：威胁行为者开始攻击的时间戳、报告攻击的时间戳，以及企业完全恢复的时间戳。攻击开始日期与恢复日期相隔越久，该事件造成的潜在损害影响就越长。如果识别时间、响应时间和恢复时间等间隔以天而非小时或分钟来衡量，那本身就是改进威胁情报和响应的建议理由。
