
# Data Poisoning
A method of corrupting the training data to manipulate the behavior of the model. We looked at how poisoned data can embed logic errors or latent vulnerabilities that only surface under certain conditions. It's a foundational concept in adversarial machine learning because it affects systems before they're even deployed.

# Prompt Injection
A technique that exploits the way generative or agentic models interpret user input as commands. The chapter showed how attackers can override system instructions using carefully crafted prompts. It matters because it blurs the line between user input and system behavior, making traditional input validation ineffective.

# Security Debt
This is the accumulation of unresolved security risks caused by prioritizing speed, performance, or deployment over secure design. We discussed how this debt builds silently across the AI development lifecycle. It's a crucial concept because it highlights that AI systems become more vulnerable the longer security is deferred.

# Model Extraction
A type of attack where adversaries reverse-engineer a deployed model by probing its outputs. In the chapter, it was tied to inference APIs that leak too much signal. This is important because it allows attackers to steal intellectual property and plan further attacks offline.

# Observability
This refers to how well a system's internal behavior can be monitored or understood in real time. We noted that many AI systems lack sufficient observability, making it difficult to detect anomalies or attacks. Without it, defenders are flying blind.

# Inference-Time Attack
An attack that targets the model during its operational phase, rather than during training. The chapter covered these as active, real-time threats that exploit the model's learned behavior. They're especially relevant because they don't require access to the training process—just access to the interface.

# Fine-Tuning
A process of adapting a pretrained model to new data or tasks. We explored how malicious behaviors can be inherited or introduced during this step. This is key because organizations often reuse models without realizing what's baked in.

# Opaque Architecture
A model design that's difficult to interpret or debug, often due to its size or complexity. The chapter emphasized how opacity limits the ability to audit models for security flaws. It raises the risk that dangerous behavior will go undetected.

# Logic Bomb
A malicious behavior hidden inside a model, triggered only under specific conditions. We discussed how these can be embedded during training and activated at inference. They're significant because they bypass normal validation and only reveal themselves when it's too late.

# Telemetry Spoofing
A method attackers use to manipulate or suppress monitoring signals. The chapter linked this to post-deployment phases where observability is critical. If logs or alerts are compromised, defenders lose the ability to detect and respond to intrusions.

# Model Lineage
This tracks the history and transformation of a model over time. We emphasized that without a clear lineage, it's hard to trace when or how a model became vulnerable. It's essential for accountability and root cause analysis in security incidents.

# Tool Use Exploitation
This describes the misuse of agentic models that have access to tools like code execution or web browsing. The chapter explored how prompt injection can hijack these tools. Understanding this helps defenders build stronger permission boundaries and containment strategies.

## Adversary Spotlight
An adversary reading this chapter would immediately recognize the opportunity that complexity creates. Rather than trying to break encryption or bypass firewalls, they would focus on places where assumptions were made—about clean data, trusted models, or harmless inputs. The training pipeline becomes an irresistible target because poisoned data or misaligned fine-tuning can embed undetectable weaknesses that persist for the model's lifetime. These types of compromises are elegant in their subtlety and devastating in their consequences.

They would also see the benefit of attacking inference systems in real time. If they can find a deployed endpoint—whether it's a chatbot, a classifier, or a vision system—they can test it interactively to discover adversarial triggers or ways to extract the model. Public APIs become reconnaissance tools for deeper attacks. The lack of observability and proper access control only makes this easier.

For generative models and agentic systems, prompt injection offers an almost comically simple vector. If the system doesn't properly separate instructions from data, an attacker can smuggle in commands disguised as input. And if that model can use tools—like calculators, browsers, or code runners—then prompt injection becomes code execution with very little effort. That's a goldmine for attackers.

What stands out most is that many of these attack paths are non-invasive and scalable. No need for rootkits or buffer overflows—just a little creativity and access to the right interface. The real advantage for the adversary is that defenders often don't see these paths as part of the attack surface until it's too late.

## Common Misunderstandings
- AI models are not inherently more secure just because they're complex. In fact, complexity often hides vulnerabilities.
- Only technical inputs can be dangerous. Natural language, images, or even formatting can trigger failures in modern models.
- Security issues don't always come from “outside” the system. Many are introduced internally during development and go unnoticed.
- Reusing pretrained models isn't always safe. Vulnerabilities and malicious logic can carry over during fine-tuning.
- Logging performance isn't the same as logging security-relevant events. Without telemetry on inputs and anomalies, attacks can go undetected.
- Just testing for accuracy doesn't mean the model is secure. Security evaluation requires separate, specialized testing for edge cases and adversarial behavior.

## Defense Framing
Defending AI systems starts with seeing them not as static programs but as evolving entities with deeply layered architecture. Unlike traditional software, where the code is known and controlled, AI models are shaped by data, training procedures, and hidden internal representations. This means defenders must adopt a systems-thinking approach—asking not just “what does the model do,” but “how was it built, where can it be steered, and what assumptions are hidden underneath.” Security in this space requires thinking one layer deeper.

The mindset shift involves treating each part of the AI pipeline—data sourcing, model configuration, fine-tuning, and deployment—as a potential attack surface. Rather than just focusing on endpoints or access controls, defenders should be reviewing data provenance, monitoring training behavior, and running red team simulations before models are exposed. Defensive practice moves upstream in the AI lifecycle, long before a system is exposed to end users.

Security professionals must also learn to work in partnership with data scientists, not just audit them after deployment. This means advocating for explainability, logging, and robust evaluation as core development practices, not afterthoughts. Building cross-disciplinary muscle is essential because many vulnerabilities originate in the places where no one thought to look—like annotation pipelines, model updates, or overly permissive agent tools.
