Done control returns to goroutine #2's for loop and the next job is sent from goroutine #1 and received by goroutine #2, and so on, until all the jobs are done.

```
for i := 0; i < len(jobList); i++ {
<-done // Blocks waiting for a receive
}
```

This snippet begins execution immediately after the two additional goroutines have been created and begun executing. and its purpose is to ensure that the main goroutine does not terminate until all jobs are done.

The for loop iterates as many times as there are jobs, but at each iteration, a receive is done on the done channel (with the result thrown) to ensure that each iteration is synchronized with the completion of a job. If there is nothing to receive (i.e., because a job is done but hasn't finished), the receive will block. Once all the jobs are finished the number of sends to receives from the done channel will equal the number of iterations and the for loop will finally complete. At this point the main goroutine can finish, terminating the program, and we can be sure that all processing has been completed.

Two rules of thumb should normally be applied to channels. First, we need only close a channel if we are checking that it is closed later on (e.g., using a for loop, a select, or a checked receive using the < operator). Second, a channel should be closed by the sending goroutine, not by a receiving goroutine. It is perfectly sensible not to close channels that are never checked for closed—channels are very lightweight, so they don't tie up resources in the way they say, an open file.

In this example, the jobs channel is iterated over a for range loop, so we close it—and inside the sending goroutine—in accordance with our rules of thumb. On the other hand, we did not to close the done channel, since no statement depends on it being closed later.

The handleCommandHandler() function (not shown) uses the standard library’s flag package to process command-line arguments. The pipeline works from the innermost function call (source(files)) to the outermost (sink()). Here is the pipeline laid out in an easy-to-understand way.

```
channel1 := source(files)
channel2 := filterSuffixes(suffixes, channel1)
channel3 := filterSize(minSize, maxSize, channel2)
sink(channel3)
```

The source() takes a slice of filenames and returns a channel of type chan string that is assigned to the channel1 variable. The source() function sends e filename in turn to the channel. The two filter functions take each filter criteria and a chan string, and return their own chan string. In this example, the first filter’s returned channel is assigned to channel2 and the second to channel3. The filters iterate over the items in the channel they receive and send each item that matches their criteria to the channel they have returned. The sink() function takes a channel and iterates over its items, printing each one.

func source(files []string) <-chan string {

    for _, filename := range files {

```

This function creates a channel for passing filenames. It uses a buffered channel since in tests it this improved throughput. (As is often the case we have traded memory for speed.)

Once the output channel has been created we create a goroutine which iterates over the files and sends each one to the channel. When all the files have been sent we close the channel. As usual, the go statement returns immediately, so there may be a long gap in time between sending the first item and sending the last item and closing the channel. The send to the channel does not block (at least, not for the first 1000 files—or however many files are if fewer than a 1000)—but block if there are more to send, at least until one or more are received from the channel.

As noted earlier, by default channels are bidirectional, but we can constrain a channel to unidirectional. Recall from the section that the chan<- Type is a send-only channel and the type<- Type is a receive-only channel. At the end of the function the bidirectional out is returned as a unidirectional receive-only so that can be received from it. We could, of course, have returned it as a bidirectional channel, but this way we have expressed our intentions.

After executing the go statement to start the anonymous function processing in its own goroutine, the function immediately returns the channel that the goroutine's function sends filenames to. So, the source() function has been called, there are two goroutines executing—the main goroutine and the additional one created in the function.

```
func filterSuffixes(suffixes []string, in <-chan string) <-chan string {
	out := make(chan string, cap(in))
	go func() {
	for filename := range in {
		if len(suffixes) == 0 {
			out <- filename

		}

		if ext == suffix {

The in channel parameter can be a receive-only channel or a bidirectional channel, but in either case, within the filterSuffixes() function the type declaration ensures that it may only be received from. (And as we know from the source() function's return value, in channel is, in fact, a receive-only channel.) Corresponding, we have returned the receive-only channel, just as we did for the source() function. In both cases, we could leave out the <-s and the function would work just the same. However, by including directions we have precisely expressed the semantics we want the function to have—and ensured that the policer enforces them.

The filterSuffixes() function begins by creating an output channel with a buffer size that is the same as the incoming channel, so as to maximize throughput. The function creates a goroutine to do its processing. The goroutine in the channel is iterated over (i.e., each filename is received in turn). If no suffixes have been specified then any suffix is acceptable in case each filename is simply sent to the output channel. If there are acceptable suffixes and the filename's lowercase suffix matches any of, it is sent to the output channel; otherwise it is discarded. (The filepath.Ext() function returns a filename's extension—that is, its suffix—including the leading-period; or an empty string for names that have no extension.)

Just like the source() function, once all the processing is finished the output channel is closed—although it may take some time to reach this point. And after the goroutine has created the output channel is returned so that the next function in the pipeline can receive filenames from.

At this point three goroutines are running; the main goroutine, the source() function's goroutine, and this function's goroutine. And after the call to filterSize() there will be a fourth goroutine, with all of them working concurrently.
