If no error occurred when unmarshalling, the object value of type interface{} will refer to a variable of type map[string]interface{} whose keys are the JSON object's fields names. The jsonObjectAsString() function accepts a map of this type and returns a corresponding JSON string. We use an unchecked assertion (199 ≺) to convert the buffer of type interface{} to the jsonObject variable of type map[string]interface{}. (Note that the output shown here is split over two lines to fit the book's page width)

```go
func jsonObjectAsString(jsonObject map[string]interface{}) string {
  var buffer bytes.Buffer
  buffer.WriteString("")
  comma := ""
  for key, value := range jsonObject {
    buffer.WriteString(comma)
    switch value := value.(type) { // shadow variable ①
    case nil: ②
      fmt.Fprintf(&buffer, "%q: null", key)
    case bool:
      fmt.Fprintf(&buffer, "%q: %t", key, value)
    case float64:
      fmt.Fprintf(&buffer, "%q: %f", key, value)
    case string:
      fmt.Fprintf(&buffer, "%q: %q", key, value)
    case []interface{}:
      fmt.Fprintf(&buffer, "%q: [", key)
      innerComma := ""
      for s, ok := range value.([]string) { // shadow variable ③
        fmt.Fprintf(&buffer, "%s%q", innerComma, s)
        innerComma = ","
      }
      buffer.WriteString("]")
    }
    comma = ","
  }
  buffer.WriteString("")
  return buffer.String()
}
```

### 5.2. Branching

This function converts a map representing a JSON object and returns a correlation string of the object's data in JSON format. JSON arrays inside maps representing JSON objects are themselves represented by the []interface{} type. The function makes one simplifying assumption regarding JSON arrays: It assumes that they have only strings.

To access the data we use for ... range loop ($5.3, ➤ 203) over the map's keys and use a type switch to access and handle each different value type. The switch's type guard (200, ➤) assigns the value (of type interface()) to a new variable called value which has the type of the matching case. This is a situation where it makes sense to shadow a variable (although we are free to create a new variable if we). So, if the interface()'s value is bool, the inner value will be a bool and match the second case, and similarly for the other cases.

To write the values to the buffer we have used the fmt.Fprintf() function since this is more convenient than writing, say, buffer.WriteString(fmt.Sprintf(...)) (200, ➤). The fmt.Fprint() function writes to the io.Writer as its first argument. A Buffer is not an io.Writer—but a *bytes.Buffer is, which is why we pass the buffer's address. This matter is covered fully in Chapter 6, but in brief, io.Writer is an interface that can be fulfilled by any value that provides a Write() method (i.e., *bytes.Buffer.Write() takes a pointer receiver, not a bytes), so only a *bytes.Buffer fulfills the interface, which means that we must pass the buffer's address to the fmt.Fprintf() function, not the buffer value.

If the JSON object contains JSON arrays, we use an inner for ... range loop to iterate over each of them and use a checked type assertion (200, ➤) which adds that items to our output only if they are strings. Again, we use a shadow variable (this time of type string), since we don't want the interface{}, but rather the value it refers to. (Type assertions were covered earlier: $5.1.2, 191 ➤)

Most programs should not need type assertions and type switches; even when they needed, their use should be fairly rare. One use case is where we are passing values that satisfy one interface and want to also satisfy another. (This topic is covered in Chapter 6; e.g., 6.5.) Another use case is when data from external sources must be converted into Go types. For ease of maintenance, it is always best that such code is isolated from the rest of the program. This allows the program to work wholly in terms of Go types and means that any maintenance needed due to changes to format from external sources can be localized.

### 5.3. Looping with For Statements

Go uses two kinds of for statements for looping, plain for statements and for ... range statements. Here are their syntaxes:

```go
for { Infinite loop
	block
}
```

```go
for booleanExpression { // While loop
	block
}
```

```go
for optionalPreStatement, booleanExpression, optionalPostStatement { 
	block
}
```

```go
for index, char := range aString // String per character iteration
	block
}
```

```go
for index := range aString // String per character iteration
	block // char := utf8.DecodeRuneInString(aString[index])
}
```

```go
for index, item := range arrayOrSlice // Array or slice iteration
	block
}
```

```go
for index := range arrayOrSlice // Array or slice iteration
	block // item := arrayOrSlice[index]
}
```

```go
for key, value := range aMap // Map iteration
	block
}
```

```go
for key := range aMap // Map iteration
	block // value := aMap[key]
}
```

```go
for item := range aChannel // Channel iteration
	block
}
```

The braces are mandatory, a semicolon is only needed if an optional pre or post-statement is used; both statements must be simple statements. If variables are created in an optional statement to capture the values produced by range clause (e.g., using := operator), their scope extends from the point of declaration to the end of the complete statement. The Boolean expression in the plain loop syntax must be of type bool since Go will not automatically convert non-bools. (The Boolean and comparison operators are listed in Table 2.3, 57.)

The second for ... range over a string syntax (203, ➤) gives byte offset indices. For a 7-bit ASCII string, value "Xaby", it produces indices 0, 1, 2, 3, 4. For a UTF-8 string, value "QYZ", the indices produced are 0, 1, 3, 5, 8. The first for ... range over a string syntax (203, ➌) is almost always more convenient than the second (203, ➤).

The second for ... range over an array or slice syntax (203, ➤) produces items from 0 to len(slice) - 1 for nonempty slices or arrays. This and the first for ... range over an array or slice syntax (203, ➤) are often useful. These syntaxes in particular explain why for loops (203, ➊) are needed in Go programs.

The for ... range loops over key-value items (203, ⬙) and over map keys (203, ➤) if sorted is required— one solution is to use the second syntax (203, ➤) and populate a slice with the statement following the for loop, or—if the break statement—we show an example of this in the previous chapter ($4.3.4, 170.) Another solution is to use an ordered data structure in the first-place or an ordered map. We will see an example of this in the next chapter ($6.5.3. ⬓.)

If any of the syntaxes (203, ⬙) are used on an empty string, array, slice, or map, the loop harmlessly does nothing and the flow of control continues at the following statement.

A for loop can be broken out of any time with a break statement, with control passing to the statement following the for loop, or—the innermost enclosing for, switch, or select statement that has the specified label. It is also possible to make the flow of control return for the loop's condition or range clause to force the next iteration (or of the loop), by using a continue statement.

We have already seen numerous examples of statements in use; these include for range loops (89, 172, and 180), infinite loops (23 and 45), and the plain for loop (100) that is needed infrequently in Go since the other loops are often more convenient. And we, of course, see many more for loop examples in the rest of the book, including some later in this chapter; so here we confine ourselves to one example.
