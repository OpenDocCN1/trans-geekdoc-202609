
## 9.1. Custom Packages

aGOPath/src/stacker/stacker.go

Here, aGOPath is the GOPATH directory (if there is one), or one of the colon-(semicolon on Windows) separated paths in the GOPATH environment variable.

If we are in the stacker directory and execute the command `go build`, we will get an executable called stacker (stacker.exe on Windows). However, if we want the executable to be in a GOPATH bin directory, or if we want other programs to be able to use the stacker/stack package, we must use `go install`.

When `go install` the stacker program it creates two directories (if they don't exist): aGOPath/bin contains the stacker executable, and aGOPath/pkg/linux_amd64, which contains the static package's binary library file. (Naturally, the operating system/architecture directory will match those of the machine being used, e.g., windows_36 for 32-bit Windows).

The stacker package is imported by the stacker program with the statement `import "stacker/"`, that is giving its (Unix-style) path, excluding the aGOPath/src part. In fact, any program or package in the GOPATH can use exactly this import since Go does not distinguish application-specific and shared packages.

The ordered map from Chapter 6 (§6.5.3, 302 ➤ in file omap.go) is in package omap. To avoid conflicts, we have created a directory for packages we want to share our GOPATH directory (or one of our GOPATH directories), and give it what should be a unique name (in this case a domain name). Here is the directory structure:

aGOPath/src/qrac.eu/omap/omap.go

Any of our programs (so long as they are in a GOPATH) can access the ordered map by using `import "qrac.eu/omap"`. If we had shared packages we would put them under aGOPath/src/qrac.eu, alongside the omap package.

When `go install` the omap package it creates the aGOPath/pkg/linux_amd64/qrac.eu directory (if it doesn't exist) containing the omap package's binary library file, with the operating system/architecture subdirectory depending on the machine.

If we want to create packages inside our packages, we can do so without formality. We create a package directory, say, aGOPath/src/my_package. And then we create one subdirectory underneath that, for example, aGOPath/src/my_package/pkg1 and aGOPath/src/my_package/pkg2, along with their corresponding files aGOPath/src/my_package/pkg1/pkg1.go and aGOPath/src/my_package/pkg2/pkg2.go. Then, to import, say pkg2, we would write `import "my_package/pkg2"`. The Go source archive package is an example of this approach. It is also possible to have code in the package itself (in this example, by creating the file `aGOPath/src/my_package/my_package.go`). See the source code’s image package for an example of this.

Go packages are imported from under GOROOT (specifically, $GOROOT/pkg/${GOOS}_${GOARCH}, e.g., /opt/go/pkg/linux_amd64), and from under the directories of the GOPATH environment. This means that name conflicts are possible. The easiest way to avoid name conflicts is to ensure that GOPATH paths have a unique directory, such as a domain name as we used for the omap package.

The go program works seamlessly with packages from the standard library and from GOPATH paths, as well as understanding the platform-specific source files discussed in the following subsection.

### 9.1.1. Platform-Specific Code

In situations we need to have code that differs between platforms. For example, on Unix-like systems the shell does wildcard expansion (expanded globbing), by * on the command line might be received by the program as, say, "README.txt", "INSTALL.txt" in the `os.Args[1:]` slice. But on Windows the program would just get *. We can get the program to do such globbing using `filepath.Glob()`, of course, we only do this on Windows.

One solution is to decide whether to use `filepath.Glob()` at runtime by using the test `if runtime.GOOS == "windows" { }`, and this is what most of the book’s examples (e.g., cgrep1/cgrep.go). Another solution is to use platform-specific code into its .go file or files. For example, the cgrep3 program consists of three files, cgrep.go, util_linux.go, and util_windows.go. Inside util_linux.go there is a single function defined.

```go
func commandLineFiles(files []string)string { return files }
```

Clearly, this function doesn't do any globbing since there is no need on Linux. The util_windows.go file defines a different function that has the same name.

```go
func commandLineFiles(files []string)string {
  args := make([]string, 0, len(files))
  for _, name := range files {
    if matches, err := filepath.Glob(name); err != nil {
      args = append(args, name) // Invalid pattern
    } else if matches != nil { // At least one match
      args = append(args, matches...)
    }
  }
  return args
}
```

### 9.1.2. Documenting Packages

What constitutes good documentation is a contentious matter, so in this-subsection we will concern ourselves purely with the mechanics of documenting Go packages.

By default exported types, constants, and variables are shown by godoc, so all of these should be documented. Documentation is written directly in source code.

```go
// Package omap implements // Keys and values may be of any type, but all keys must be comparable
// using the less function that is passed to the omap.New()
// function, or the less function provided by the omap.New*
// construction functions.
package omap
```
