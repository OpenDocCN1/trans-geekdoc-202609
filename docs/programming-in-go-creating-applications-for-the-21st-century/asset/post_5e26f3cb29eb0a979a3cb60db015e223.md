
# Chapter 8. File Handling

This chapter's first section shows how to read and write files using standard and custom format files. The second section covers Go's support for handling archive files and compression.

## 8.1. Custom Data Files

It is quite common for programs to maintain internal data structures and to provide import/export functionality to support data interchange, and also to facilitate the processing of their data by external tools. Since our concern here is with file handling, we will focus purely on how to write and read data to and from standard and custom formats from into a program's internal data structures.

For this section we use the same data for all the examples so that we can get a direct comparison between the various file formats. All the code is taken from the invoicedata program (in the invoicedata directory in the invoicedata.gob.go, inv.go, jsn.go, txt.go and xml.go). The program takes two filenames as command-line arguments, one to read and one to write (which must be different). The program reads the data from the first file (in whatever format its suffix indicates) and writes the same data to the second file (again, using whatever format its suffix indicates).

The files created by invoicedata work cross-platform, that is, a file created on say, Windows, is readable on Mac OS X and Linux, and vice versa, no matter which format it is. Gzip-compressed files (e.g., invoices.gz) can be read and written seamlessly; compression is covered in the second section (§8.2 -> 397).

The data consists of []Invoice, that is, a slice of pointers to Invoice values. Each invoice is held in an Invoice value, and each invoice holds zero or more items in its Items field of type []Item (slice of pointers to Item).

```go
type Invoice struct {
    Id int
    CustomerID int
    Raised time.Time
    Due time.Time
    Paid bool
    Note string
    Items []*Item
}

type Item struct {
    Id string
    Price float64
    Quantity int
    Note string
}
```

These structures are used to hold the data. Table 8.1 shows some informal comparisons of how long it takes to read and write the 50 000 random invoices, and the size of the file occupied by those invoices in each format. The timings are in seconds rounded up to the nearest tenth of a second—they should be taken as unitless unless they will undoubtedly vary on different hardware loads.

The size column shows the sizes in kibytes—these should be very consistent across machines. For this data set, the compressed sizes are surprisingly similar, even when the uncompressed sizes vary considerably. The lines of code exclude that that is common to all formats (e.g., for decompression and compressing the structs).

The timings and file sizes are what we reasonably expect—apart from the extremely fast reading and writing of the plain text format. This is thanks to the fmt package's excellent print and scan functions in conjunction with a custom text format that we designed to be easy to parse. For the JSON and XML formats, instead of using the default storage for time, Time values (ISO-8601 date/time string), we have simply stored the date part—which has slightly reduced the file size at the expense of some processing speed and some additional code. For example, the JSON code could run faster, and about the same number of lines as the Binary code, if we allowed it to handle time values.

For binary data, the Binary format is the most convenient to use—it is fast, extremely compact, requires very little code, and is relatively easy to adapt to data changes. However, if we use custom types that are not initially gob-encodable and have to make them satisfy the gob.Encoder and Decoder interfaces, this can considerably slow down writing and reading in gob format, and also bloat out the file size.

For human-readable data, XML is the probable format to use—particularly since it is so useful as a data exchange format. More lines are required to handle XML format than JSON format. This is because Go lacks an interface that is expected to be made good in a later Go 1.x release, and also because we have used parallel data types (XMLInvoice and XMLItem) to help map between the XML data and the invoice data (Invoice and Item). Applications that use XML as their external format would not need the parallel data types or the conversions that the invoicedata program needs, so are likely to be faster and require less code than the invoicedata examples.

In addition to reading and writing speed, file size, and lines of code, there is one other issue that we should consider: format robustness. For example, if we add one field to the Invoice struct and one item to the Item struct, we will need to change our file formats. How easy is it to adapt our code to write and read the new format—and also to continue reading the old format? Providing we take care of version our file formats changes are pretty straightforward to cater to (one of the chapter's exercises will demonstrate)—with the exception of JSON format for adapting the code to be read both the old and new formats is slightly tricky.

We have also created a couple of interfaces.

```go
const (
    fileType      = "INVOICES" // Used by text formats
    magicNumber   = 0x125      // Used by binary formats
    fileVersion   = 1          // Used by all formats
    dateFormat    = "2006-01-02" // This date must be used
)

type InvoicesMarshaler interface {
    MarshalInvoices(writer io.Writer, invoices []*Invoice) error
}

type InvoicesUnmarshaler interface {
    UnmarshalInvoices(reader io.Reader) ([]*Invoice, error)
}
```

The purpose of this is to make it easy to use a reader or writer in a generic way. For example, here is the function invoicedata program uses to read invoices from an open file.

* There is no universal repository of magic numbers, so we cannot be certain that any particular number has been used before.

```go
func readInvoices(reader io.Reader, suffix string) ([]*Invoice, error) {
	var unmarshaler InvoicesUnmarshaler
	switch suffix {
	case ".gob":
		unmarshaler = GobMarshaler{}
	case ".inv":
		unmarshaler = InvMarshaler{}
	case ".js", ".json":
		unmarshaler = JSONMarshaler{}
	case ".txt":
		unmarshaler = TxtMarshaler{}
	case ".xml":
		unmarshaler = XMLMarshaler{}
	}
	if unmarshaler != nil {
		return UnmarshalInvoices(reader)
	}
	return nil, fmt.Errorf("unrecognized input suffix: %s", suffix)
}
```

### 8.1.1. Handling JSON Files

According to www.json.org, JSON (JavaScript Object Notation) is a lightweight data interchange format that is easy for humans to read and write, and easy for machines to parse and generate. JSON is a plain text format using the UTF-8 encoding. JSON has become increasingly popular—particularly for transferring data over network connections—because it is more convenient to write, it is (usually) more compact, and requires much less power to parse than XML.

Here is the data for a single invoice in JSON format, but with most of the invoice's item's fields eclipsed.

```json
{
  "Id": 4461,
  "CustomerId": 917,
  "Raised": "2012-07-22"
}
```
