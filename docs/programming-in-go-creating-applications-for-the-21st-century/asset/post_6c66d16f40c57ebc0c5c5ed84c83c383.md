The aim of this chapter is to show how to do object-oriented programming in Go. Programmers coming from a procedural background (e.g., C) should find everything in this chapter builds nicely on what they already know and what the earlier chapters covered. But programmers coming from an inheritance-based object-oriented background (e.g., C++, Java, Python) will need to put aside many of the concepts and idioms they are used to—in particular, those relating to inheritance—since Go takes a radically different approach.

Go's standard library mostly provides functions, although where appropriate we created values of some custom types (e.g., regexp.Regexp and os.File) and called methods on them—so the basic use of types and calling them is already familiar. The chapter's very short first section introduces some key concepts in Go. The second section covers the creation of custom types with adding methods to custom types. The third section covers interfaces—these are fundamental to Go's approach to type-safe typing. The fourth section covers structs, introducing many new details that have not been seen earlier. The chapter's long final section presents three complete examples of custom types that draw most of the material covered in earlier sections: the first of these examples is a simple single-valued data type, the second is a small family of data types, and the third is a generic collection.

What makes Go orientation so different from, say, C++, Java, and (to a lesser extent) Python is that it does not support inheritance. When oriented programming first became popular, after a few decades of experience, it has turned out that this feature has significant drawbacks, especially when it comes to maintaining large systems. Instead of using both aggregation and inheritance like other object-oriented languages, Go supports aggregation (also composition) and embedding exclusively. To see the difference between aggregation and embedding, let's look at a tiny code snippet:

```go
type ColoredPoint struct {
  color Color // Anonymous field (embedding)
  x, y  int // Named fields (aggregation)
}
```

Here, color is the type from the image/color package and x and y are ints. In Go terminology, color.x and y are all fields in the ColoredPoint struct. The color field is anonymous (since it has no name) and is therefore an embedded field. The x and y fields are named fields. If we create a ColoredPoint value {}, the fields would be accessed as point.color, point.x, and point.y. Notice that when accessing a field of a type from another package we only use the last component of the name, that is, color and not color.Color (We will discuss these matters in more detail in 6.2.1, ► 261, 6.3, ► 265, 6.4, ► 275).

The terms “class”, “object”, and “instance” are so well established in inheritance-hierarchy-style object orientation, in Go we avoid them all together. Instead, we talk about “types” and “values”, which are values of custom types have methods. Without inheritance there are no virtual functions. Go's answer to this is to support type-safe duck typing. In Go, parameters can be specified as concrete types (e.g., int, string, *os.File, MyType), or as interfaces—that is, values that provide the methods that fulfill the interface. For a parameter specified as an interface we can pass any value—so long as it has the methods that the interface requires. For example, if we have a value that provides a method with the signature Write([]byte) (int, error) we can pass that as an io.Writer (i.e., as a value that satisfies the io.Writer interface) to any function that has an io.Writer parameter, no matter what the value's actual type is. This is incredibly flexible and powerful, especially when combined with Go's closure support for accessing the methods of embedded values.

One advantage of inheritance is that some methods need only be implemented once in a base class for all the subclasses to benefit. Go provides two solutions for this. One solution is to use embedding. If we embed a type, the method need created only once for the embedded type and is available to all types that include the embedded type. Another solution is to provide separate versions of the method for all the types we want to have—but to make these thin wrappers (typically one-liners) that simply pass on the work to a single function that all methods use.

One way of thinking about the Go approach is to consider that is-a relationships are defined by interfaces, purely in terms of method signatures. So, a value that satisfies the io.Reader interface (i.e., has a method with the Read([]byte) (int, error)) isn't a reader because of what it is (a file, a buffer, or custom type), but because of what it provides, in this case Read(). This is illustrated in Figure 6.1 (► 256).

Another aspect of Go object-oriented programming is that interfaces, values, and methods are kept separate. Interfaces are used to specify method signatures, structs are used to specify operations on custom types (which are often structs). There is no explicit connection between a custom type's methods and any particular interface—but if the type's methods fulfill one or more interfaces, values of the type can be wherever values of those interfaces are expected. Of course, every type fulfills the empty interface (interface{}), any value can be used where the empty interface is specified.
