# 5.5.1. Panic and Recover

Go provides an exception handling mechanism through the use of its built-in panic() and recover() functions. These functions could be used to provide a general-purpose exception handling mechanism, similar to those available in some other languages (e.g., C++, Java, and Python): But to do so is considered to poor Go style.

Go distinguishes between errors—that might go wrong and that a program should handle gracefully (e.g., a file that could not opened)—and exceptions—something that “cannot” happen (e.g., a precondition which should always be true that's actually false).

The idiomatic way to handle errors in Go is to return an error as the last (or only) return value from functions and methods to always check any returned errors. (The one case where it is common to ignore returned error values is printing to the console.)

For “cannot happen” situations we can call the built-in panic() function with any value like (e.g., a string that explains the invariant that has been broken). In other languages we might use an assertion for these situations, but in Go we call panic(). During early development and prior to any release the simplest and probably the best approach is to call panic() to terminate the program for problems to be impossible to ignore so that they get fixed. When we start deploying our application it is to avoid termination when problems occur at all possible, and this can be done while still leaving any recover() calls in our packages. During recovery we can catch and log any panic (so that they remain visible), and return non-nil errors to callers who can then restore the program to a sane state from which it can safely continue to run.

* In C++ destructors are used to clean up values. In Java and Python cleanup is problematic since they cannot guarantee when or if their finalizer()__del__() method will be called.
