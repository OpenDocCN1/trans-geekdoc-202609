# 7.1. Key Concepts

One way to serialize accesses to use mutexes. Another way is to apply a policy that a pointer or reference is only sent once, and once sent the sender never accesses it again. This leaves the receiver free to access the pointed-to or referred-value—and to send on the pointer or reference providing both sender and receiver the same policy. (We will see an example of using this policy-based approach;7.2.4.3 ►347.) A downside of policy-based approaches is that they require discipline. A third way to work safely with pointers or references is to provide them with exported methods that cannot change the pointedto or referred value and unexported methods that can perform changes. Such pointers or references could then be passed around and accessed concurrently through their exported methods, with only one goroutine to use their unexported methods (e.g., inside their own package; packages are covered in Chapter 9).

It is also possible to send interface values—that meet a particular interface—through channels. Values of read-only interfaces (unless the documentation says otherwise) can be used in any number of goroutines, but values of interfaces that include methods for changing a value's state must be treated in the same way as pointers, with channels to serialize.

For instance, if we create a new image using the image.NewRGBA() function we get an *image.RGBA. This type fulfils both the .Image interface (which has only methods, and is read-only) and the .draw.Image interface (which has all the image.Image methods plus a Set() method). So, it is safe to pass the *image.RGBA value to as many goroutines as we like—we pass it to functions that accept an image.Image. (Unfortunately, the safety could be defeated by the receiving method using a type assertion, as draw.Image interface has to policy that disallows such things.) And if we want to use the same *image.RGBA value in multiple goroutines that might change it, we should either send it as an *image.RGBA or draw, and in this case we ensure that all accesses to it are serialized.

One of the simplest ways to use concurrency is to use one goroutine to prepare jobs to do another, leaving the main goroutine and some channels to orchestrate everything. For example, here how we might create a “job” channel and a “done” channel in the main goroutine.

```
jobs := make(chan Job)
done := make(chan bool, len(joblist))
```

Here we created an unbuffered jobs channel to pass values of some custom job type. We have also created a done channel whose buffer size corresponds to the number of jobs to do based on the jobs available in variable jobList of type []whosewhose is shown).

With the channels and job list set up, we can begin.
