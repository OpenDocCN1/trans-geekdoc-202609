```
go func() {
  for _, job := range jobList {
    jobs <- job // Blocks waiting for a receive
  }
  close(jobs)
}()
```

This snippet creates the first additional goroutine. It iterates over the job slice and sends each job to the jobs channel. Because the channel is unbuffered the goroutine is immediately blocked and will remain blocked until another goroutine tries to receive from the jobs channel. Once all the jobs have been sent to the jobs channel the channel is closed so that receivers know when there are no more jobs to do.

The semantics of this snippet are not entirely obvious! The for loop runs to completion and closes the jobs channel—but this takes place concurrently with any other goroutines in the program. Furthermore, the go statement will return immediately, leaving the code to be executed in its own goroutine—and, of course, with no one to receive jobs at this time, the goroutine blocks. So, right after this go statement, the program has two goroutines, the main goroutine which continues to the next statement, the newly created goroutine is waiting for another goroutine to receive on the jobs channel. Hence, it will take some time before the loop completes and the channel is closed.

```
go func() {
  for job := range jobs // Blocks waiting for a send
    fmt.Println(job) // Do one job
  done <- true
}()
```

This snippet creates the second additional goroutine. This goroutine iterates over the jobs channel, and for each job it receives, it processes the job (here, just prints it), and sends true on the done channel for every job that completes. (We could just send false, since we only care how many sends are performed on the done channel, not any actual values).

Just like the first go statement, this statement returns immediately, and the statement blocks waiting for a send. So, at this point, three concurrent goroutines—the main goroutine and the two additional goroutines, as Figure 7.3 illustrates.
