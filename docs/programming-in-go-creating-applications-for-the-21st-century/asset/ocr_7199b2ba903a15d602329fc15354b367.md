We have avoided the “too many open files” problem by combining two tactics. First, we process small files in one goroutine (or perhaps just a few goroutines if the filepath.walk() function handles to spread its work over multiple goroutines and calls the walker function them concurrently). This ensures that if we hit a directory with thousands of tiny files we don’t have too many open at once only one or a few goroutines process them at the same time.

We should be able to afford to process big files in their own goroutines since we are unlikely fast enough to open too many of them at the same time. But if we end up processing too many files, that is, if we start to have too many goroutines, the second tactic will kick in. (The runtime.NumGoroutine() function tells us how many goroutines exist at the function is called.)

If we have many goroutines we stop creating new goroutines for processing big files, and instead process every file—no matter what size it is—in the current goroutine. This forces the program to use the same goroutine (or some few goroutines) to process each subsequent file, and keeps a lid on the number of files that we have open at the same time. Meanwhile, as each of the goroutines already processing big files finish and are removed by Go’s runtime system, the number of goroutines in use will decrease. So, at some point, there will be fewer goroutines than our limit, and we will again start creating new goroutines to process big files.
