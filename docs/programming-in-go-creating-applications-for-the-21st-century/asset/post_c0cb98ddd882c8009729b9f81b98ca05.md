If you get a “command not found” or “go” is not recognized...” error message then it means Go is not in the PATH. The easiest way to set this on Unix-like systems (Mac OS X) is to set the environment variables in .bashrc (or the equivalent file for other shells). the author’s .bashrc contains these lines:

```
export GOROOT=$HOME/opt/go
export PATH=$PATH:$GOROOT/bin
```

Naturally, you must adjust the values to match your own system. (And, of course, this is only necessary if the go version command fails.)

On Windows, one solution is to create a batch file that sets up the environment for Go, and to execute this time you start a console for Go programming. However, it is much more convenient to set the environment variables once and for all the Control Panel. Then click Start (the Windows logo), then Control Panel, then System and Security, then Advanced settings, and in the System Properties click the Environment Variables button, then New..., and add a variable with the name GOROOT and a suitable value, such as C:\Go. In the same day, edit the PATH environment variable by adding the text C:\Go\bin at the end—leading semicolon is vital! In both cases replace the C:\Go component with the actual path where Go is installed if it isn't C:\Go. (Again, this is only necessary if the go version command failed.)

From now on we will assume Go is installed and the Go binary directory containing all Go is in the PATH. (It may be necessary—once only—to open a new console window for the new settings to take effect.)

Two steps are required to build Go programs: compiling and linking.* Both of these steps are handled by the go tool which can not only build local programs and packages, but can also fetch, build, and install third-party programs and packages.

> * Since the book assumes the use of the gc compiler, readers using gccgo need to follow the compile and link process described in golang.org/doc/gccgo_install.html. Similarly, readers using other compilers will need to compile and link as per their compiler's instructions.

## Chapter 1. An Overview in Five Examples

For the go tool to be able to build local programs and packages, there are three requirements. First, the Go binary directory ($GOROT/bin or %GOROT%%\bin) must be in the path. Second, there must be a directory that has an src directory under which the source code for the local programs and packages resides. For example, the book's examples unpack to goeg/src/hello, goeg/src/bigdigits, and so on. Third, the directory above the src directory must be in the GOPATH environment variable. For example, to build the book's hello example using the go tool, we must do this:

```
$ export GOPATH=$HOME/goeg
$ cd $GOPATH/src/hello
$ go build
```

We do almost exactly the same on Windows:

```
C:\set GOPATH=C:\goeg
C:\>cd %GOPATH%\src\hello
C:\>goeg\src\hello-go build
```

In both cases we assume that the PATH includes $GOROT/bin or %GOROT%%\bin. Once the go tool has built the program we can run it. By default the executable is given the same name as the directory it is in (e.g., hello on Unix-like systems and hello.exe on Windows). Once built, we can run the program in the usual way.

```
$ ./hello
Hello World!
```

Or:

```
$ ./hello Go Programmers!
Hello Go Programmers!
```

On Windows it is very similar:

```
C:\goeg\src\hello-hello Windows Go Programmers!
Hello Go Programmers!
```

We have shown what must be typed in bold and the console's text in Roman. We have also assumed a $ prompt, but it doesn't matter what it is (e.g., C:\>).

Note that we do not need to compile—or even explicitly any other packages (even though we will see, hello.go uses three standard library packages). This is another reason why Go programs build so quickly.

If we have several Go programs, it would be convenient if all their executables could be in a single directory that we could add to our PATH. Fortunately, the go tool supports this as follows:

Again, we can do the same on Windows:

```
C:\set GOPATH=C:\goeg
C:\cd %GOPATH%\src\hello
C:\goeg\hello-go install
```

The go install command does the same as build but puts the executable in a standard location (%GOPATH%/bin or %GOPATH%%\bin). This means that by adding a single path (%GOPATH/bin or %GOPATH%%\bin) to our PATH, *all* the Go programs that we install will conveniently be in the PATH.

In addition to the book's examples, we are likely to want to develop our own Go programs and packages in our own directory. This can easily be modified by setting the GOPATH environment variable to two (or more) separated paths (semicolon-separated on Windows); for example.

## 1.3. Hello Who?

Now that we have seen how to build the hello program we will look at its source code. Don't worry about understanding the details—everything shown in this chapter (and much more!) is covered thoroughly. Here is the complete hello program (in file hello.go):

```
// hello.go
package main
import ( ①
    "fmt"
    "os"
    "strings"
)
func main() {
    who := "World!" ②
    if len(os.Args) > 1 { /* os.Args[0] is "hello" or "hello.exe" */ ⅓
        who = strings.Join(os.Args[1:], " ") ④
    fmt.Println("Hello", who) ⑤
}
```

Go uses C++ comments: // for single-line comments that finish at the end of the line and /* ... */ for comments that can span multiple lines. It is convenient in Go to mostly use single-line comments, with spanning comments often used for commenting chunks of code.

Every piece of Go code exists inside a package, and every Go program must have a main package with a main() function which serves as the program's entry point, that is, the function that is executed. In fact, Go packages may also have init() functions that are executed before main(), as we will see in. 

Go operates in terms of packages rather than files. This means we can split a package across as many files as we like, and from Go's point of view if they have the same package declaration, they are all part of the same package and no different than all their contents were in a single file.
