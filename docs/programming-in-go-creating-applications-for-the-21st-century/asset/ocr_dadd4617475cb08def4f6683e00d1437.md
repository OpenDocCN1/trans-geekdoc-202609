# 6.1. Key Concepts

What makes Go orientation so different from, say, C++, Java, and (to a lesser extent) Python, is that it does not support inheritance. When oriented programming first became popular touted as one of its biggest advantages. But now, after a few decades of experience, it has turned out that this feature has significant drawbacks, especially when it comes to maintaining large systems. Instead of using both aggregation and inheritance like other object-oriented languages, Go supports aggregation (also composition) and embedding exclusively. To see the difference between aggregation and embedding let's look at a tiny code snippet

```
type ColoredPoint struct {
  color.Color      // Anonymous field (embedding)
  x, y             int // Named fields (aggregation)
}
```

Here, color.Color is the type from the image/color package and x and y are ints. In Go terminology, color.Color,x, and y are all fields in the ColoredPoint struct. The color field is anonymous (since it has no variable name) and is therefore an embedded field. The x and y fields are named fields. If we create a ColoredPoint value (e.g., point ColoredPoint{}), the fields would be accessed as point.color, point.x, and point.y. Notice that when accessing a field of a type from another package we only use the last component of the name, that is, Color and not color.Color. (We will discuss these matters in more detail in $6.2.1.1, ► 261, $6.3, ► 265, $6.4, ► 275)
