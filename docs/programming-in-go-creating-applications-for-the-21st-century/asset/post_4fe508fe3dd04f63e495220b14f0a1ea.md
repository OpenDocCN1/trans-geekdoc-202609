### 6.4.1.3 Embedding Interfaces

In addition to aggregating and embedding concrete types in structs, it is also possible to aggregate and embed interfaces. (Naturally, the converse—aggregating and embedding a struct in an interface—isn't possible, because an interface is a wholly abstract type, so such aggregating or embedding would not make sense.) When a struct includes an aggregated (named) or embedded (anonymous) field of an interface type, it means that the struct can store in any value that satisfies the interface's specification.

We will round off our coverage of structs by looking at a simple example that shows how we might support "option" values that have short and long names (e.g., "-o" and "--outfile") a value of a particular type (int, float64, string), and some common methods. (This example is designed to be illustrative rather than elegant. For a fully option parser see the standard library's flag package, or one of the third-party option parsers for godashboard.appspot.project.)

```go
type Optioner interface {
  Name() string
  IsValid() bool
}

type OptionCommon struct {
  ShortName string "short option name"
  LongName string "long option name"
}
```

The Optioner interface specifies the generic methods that all our option types must provide. The OptionCommon struct has two fields that are common to every option. Go allows us to annotate struct fields with strings (called tags in Go terminology). These tags have no functional purpose, but comments—they are accessible using Go's reflection support (➤ 4,942). Some programmers use the tags to specify field validation—for example, with tags like "check:len(2,30)" for a string, or "check:range(0,500)" for a number, and with semantics the programmer creates.

```go
type InputOption struct {
  OptionCommon // Anonymous field (embedding)
  Value, Min, Max int // Named fields (aggregation)
}

func (option InputOption) Name() string {
  return name(option.ShortName, option.LongName)
}

func (option InputOption) IsValid() bool {
  return option.Min <= option.Value && option.Value <= option.Max
}

func name(shortName, longName string) string {
    if longName == "" {
        return shortName
    }
    return longName
}
```

This is the complete implementation of the custom IntOption type plus the supporting unexported name() function. Since the OptionCommon struct is embedded we can access its fields directly—as we do in the IntOption.Name() method. The IntOption satisfies the Optioner interface (it provides the Name() and Valid() methods with the correct signatures).

Although the processing done by the name() function is very simple we have chosen to use a separate function rather than implement it in the IntOption.Name() method. This makes the method very short and means we can reuse the functionality in other options. The GenericOption.Name() and StringOption.Name() methods' bodies are identical to the IntOption.Name() method's single statement body, with all three relying on the name() function to do the actual work. This is a common pattern in Go,

The StringOption's implementation is very similar to the IntOption we have not shown it. (The differences are that its Value field is of type string and its IsValid() method returns true if the Value is nonempty.) For the FloatOption we have used interface embedding, to show how it is done.

```go
type FloatOption struct {
```

This is the complete implementation of the FloatOption. The embedded Optioner field means that when we create FloatOption values we must assign to the embedded field any value that satisfies the Optioner interface.

This is the complete implementation of the GenericOption, a type that fulfills the Optioner interface.

The FloatOption type has an embedded field of type Optioner, so FloatOption values require a concrete type that fulfills the Optioner interface for this field. This need can be met by assigning a GenericOption value to a FloatOption's Optioner field.

### 6.5.1 Example: FuzzyBool—Single Valued Type

In this section we will see how to create a single-valued type and its supporting methods. This example is in fuzzy/fuzzybool.go and is based on a struct. The built-in bool type is two-valued (true and false), but in some areas, fuzzy Booleans are used. These values correspond to "true" and "false", and also to intermediates between them. In our implementation we use floating-point values, with 0.0 denoting false and 1.0 denoting true. In this system, 0.5 means 50% true (50% false), and 0.25 means 25% true (75% false), and so on. Here are some usage examples and the results they produce.

```go
func main() {
	a := fuzzy.New(0) // Safe to ignore error
	b := fuzzy.New(.25) // known valid values; check if using
	c := fuzzy.New(.75) // variables though.
	d := c.Copy()
	if err := d.Set(1); err != nil {
		fmt.Println(err)
	}
	process(a, b, c)
	s := []*FuzzyBool{a, b, c, d}
	fmt.Println(s)
}

func process(a, b, c, d *FuzzyBool) {
	fmt.Println("Not:", a.Not(), b.Not(), c.Not())
	fmt.Println("Not Not:", a.Not().Not(), b.Not().Not(), c.Not().Not(), d.Not().Not())
	fmt.Printf("And(.25):%v, .25.And(.75,1):%v, .75.And(1):%v\n", a.And(b), b.And(c), c.And(d))
	fmt.Printf("Or(.25):%v, .25.Or(.75):%v, .75.Or(1):%v\n", a.Or(b), b.Or(c), c.Or(d))
	fmt.Println("Bool: ", a.Bool())
	fmt.Println("Bool: < a, c = a, c: >", a.Less(c), a.Equal(c), c.Less(a))
	fmt.Println("Bool:", a.Bool(), b.Bool(), c.Bool(), d.Bool())
	fmt.Println("Float:", a.Float(), b.Float(), d.Float())
}
```
