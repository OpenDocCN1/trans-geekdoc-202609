```

```

This snippet begins execution immediately after the two additional goroutines have been created and begun executing. and its purpose is to ensure that the main goroutine does not terminate until all jobs are done.

The for loop iterates as many times as there are jobs, but at each iteration, a receive is done on the done channel (with the result thrown) to ensure that each iteration is synchronized with the completion of a job. If there is nothing to receive (i.e., because a job is done but hasn't finished), the receive will block. Once all the jobs are finished the number of sends to receives from the done channel will equal the number of iterations and the for loop will finally complete. At this point the main goroutine can finish, terminating the program, and we can be sure that all processing has been completed.

Two rules of thumb should normally be applied to channels. First, we need only close a channel if we are checking that it is closed later on (e.g., using a for loop, a select, or a checked receive using the < operator). Second, a channel should be closed by the sending goroutine, not by a receiving goroutine. It is perfectly sensible not to close channels that are never checked for closed—channels are very lightweight, so they don't tie up resources in the way they say, an open file.

In this example, the jobs channel is iterated over a for range loop, so we close it—and inside the sending goroutine—in accordance with our rules of thumb. On the other hand, we did not to close the done channel, since no statement depends on it being closed later.
