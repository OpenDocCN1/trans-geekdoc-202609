# Chapter 1. An Overview in Five Examples

Go supports both named and unnamed custom types. Unnamed types with the same structure can be used interchangeably; however, they cannot have methods. (We will discuss this more fully in $6.4 ► 275.) Any custom type can have methods and these methods together constitute the interface. Named custom types—even with the same structure—are not interchangeable. (Throughout the book reference to a “custom type” means a named custom type, unless stated otherwise.)

An interface is a type that can be formally defined by specifying a particular set of methods. Interfaces are abstract and cannot be instantiated. A concrete (i.e., noninterface) type that has the methods specified by an interface fulfills the interface, that is, values of a concrete type can be used as values of the interface's type as well as its own actual type. No formal connection is established between an interface and a concrete type that provides the methods specified by the interface. It is sufficient for a custom type to have the interface's methods for it to satisfy interface. And, of course, a type can satisfy more than one interface by providing all the methods for all we wants to satisfy.

The empty interface (i.e., the interface that has no methods) is specified as interface().* Since the empty interface makes no demands at all (because it doesn't require any methods), whether the value is of a built-in type or of a custom type. (Go's pointers and references are explained later; $4.1 ► 140.) Incidentally, in Go terminology we talk about types and values rather than classes or objects (since Go has no classes).

Function and method parameters can be of any built-in or custom type—or any interface type. In the latter case this means that a function can have a parameter that says, for example, “pass a value that can read data”, regardless of what that value's type actually is. (We will see this in practice shortly; $1.6 ► 29.)

Chapter 6 covers all of these matters in detail and presents many examples to ensure that the ideas are understood. For now, let's look at a very simple custom type—a stack—starting with how values are created and used, and looking at the implementation of the custom type itself.
