As is common when processing a text file in Go, if an error occurs when reading a line we handle it after reading the line. If the bufio.Reader.Bytes() encounters an error (including end of file), it returns any bytes prior to the error along with the error. Sometimes the very last line of a file does not end with a newline, so to make sure that we process the very last line. The disadvantage of handling the error afterward is that the regexp can match any string and we get a non-nil-to-io.EOF error if we get a spurious match. (This can be worked around, of course.)

The bufio.Reader.Bytes() method returns the bytes up to and including the specified byte (or up to the end of the file if the specified byte isn't present). We don't want the newline, so we remove it using the bytes.TrimRight() which removes from the right of the given line, the given character or characters. (This is just like the strings.TrimRight() function; 109 To make our program cross-platform we trim both newline and return characters.

Another small detail to note is that we handle the lines as slices and do the matching using the regexp.Regexp.Match() method rather than regexp.Regexp.Match(). So we only do the (very cheap) conversion from [byte] to string for matching lines. Also, we count line numbers from one rather than since that is conventional.

A particularly nice aspect of the cgrep programs' design is that their concurrency frameworks are both simple and separate from the actual processing (which is done by the Job.Do() method), the only connection between these two being the results channel. This separation of concerns is in concurrent Go programs and compares very favorably with the use of lower-level concurrency constructs (such as mutexes) where the locking and unlocking code is often needed throughout the program and can obscure and complicate the program's logic.
