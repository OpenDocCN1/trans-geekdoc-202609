```go
func processLines(results chan<- map[string]int, getRx *regexp.Regexp,
    lines <-chan string) {
    countPage := make(map[string]int)
    for line := range lines {
        if matches := getRx.FindStringSubmatch(line); matches != nil {
            countPage[matches[1]]++
        }
    }
    results <- countPage
}
```

This function is almost the same as the version shown before. The key differences are first that we have created a local map to hold page counts, and second that we return the local map to the results channel (rather than sending, a struct{} to a done channel, once the function has finished processing lines).

```go
func merge(results <-chan map[string]int, totalPage map[string]int) {
    for i := 0; i < workers; i++ {
        countPage := <-results
        for page, count := range countPage {
            totalPage[page] += count
        }
    }
}
```

This function is structurally the same as the waitUntil() function we saw earlier, only this time we make use of the received value, using it to update the overall totalPage map. Note that the maps received here are never accessed by their sending goroutines after they have been sent, so no locking is necessary.

### 7.2.5. Example: Find Duplicates

This chapter's final concurrency example is a program that attempts to find duplicate files using file sizes and SHA-1 values rather than filenames.

The program we will review is called findduplicates (in findduplicates/duplicates.go). The program uses the standard filepath.Walk() function to iterate over all the files and directories in a given path, including subdirectories, and subdirectories, and so on. The program uses a variable number of goroutines depending on the work it does. For each "big" file, each "small" file's SHA-1 is computed in the current goroutine. This means we don't know in how many goroutines any particular run of the program will use, although—and do—set an upper limit.

One way of handling a variable number of goroutines is to use a "done" channel just like in earlier examples, only this time keeping a running count of how many goroutines are created. An easier way is to use a sync.WaitGroup which achieves the same thing but passes on the counting to Go.

		fmt.Printf("usage: %s\n", filepath.Base(os.Args[0]))

	}
}

We need only the sync.Group.Add(1) method when we create a new goroutine, but when we do so we must be sure to call the corresponding sync.Group.Done() method once the goroutine has finished. We do this by taking advantage of Go’s closures (§5.6.3, 225 ◀). We for the processFile() function in a new goroutine we pass an anonymous function as the argument—when this anonymous function is called we call the sync.Group.Done() method. The processFile() function is expected to have a deferred call to Done() gets the goroutine finishes. If we call the processFile() method in the current goroutine, we pass nil instead of an anonymous function.

Why didn’t we simply process every file in a new goroutine? Go would have no problem with that since we can create hundreds or thousands of goroutines without hitting any problems. Unfortunately, most operating systems impose a limit as to how many files may be open at the same time. For Windows the default limit could be as small as 512 although this can be increased to 2048.
