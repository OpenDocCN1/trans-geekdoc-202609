The function begins by retrieving the names of the files to read and write an error value. If there was a problem parsing the command line we print the error (which contains the program's usage message), and terminate the program. Some of Go's print functions use reflection (introspection) to print a value using the value's Error method if it has one, or its String() method if it has one, or as best they can otherwise. If we provide our custom types of one of these methods, Go functions will automatically be able to print values of our custom types, as we will see in Chapter 6.

If err is nil, we have filename and filename strings (which may be empty), and we can continue. Files in Go are represented by pointers to values of os.File, and we create two variables initialized to the standard input and output streams (which are of type os.File). Since Go functions and methods can return multiple values it follows that Go supports multiple assignments as the ones we have used here (30 ➤ ●, ●).

Each filename is handled in essentially the same way. If the file has already been correctly set to os.stdin or os.stdout (both of which are of type *os.File, i.e., a pointer to os.File value representing the file); but if the filename is nonempty we create a new *os.File to read or write to the file as appropriate.

The os.Open() function takes a filename and returns an *os.File value that can be used for reading the file. Corresponding, the os.Create() function takes a filename and returns an os.File value that can be used for reading or writing creating the file if it doesn't exist and truncating it to zero if it exists. (Go also provides the os.OpenFile() function that can be used to exercise control over the mode and permissions used to open a file).

In fact, the os.Open(), os.Create(), and os.OpenFile() return two values: an *os.File and nil if the file was opened successfully, or nil and if an error occurred.

If err is nil we know that the file was successfully opened so we immediately execute a defer statement to close the file. Any function that is the subject of a defer statement—the parentheses after the functions' names (30 ➤ ●, ●)—but the calls actually occur when the function in which the defer statements are written returns. So the defer statement “captures” the function call and sets it aside for later. This means that the statement itself takes almost no time at all and control immediately passes to the following statement. Thus, the deferred os.File.Close() method actually called until the enclosing function—in this case, main() returns (whether normally or due to a panic, discussed in a moment), the file is open to be worked on and yet guaranteed to be closed when we are finished with it, if a panic occurs.

If we fail to open the file we call log.Fatal() with the error. As we noted in a previous section, this function logs the date, time, and err to os.Stderr—another log destination is specified, and calls os.Exit(1) to terminate the program. When os.Exit() is called (directly, or by log.Fatal()), the program is terminated immediately—and any deferred statements are lost. This is not a problem, though, since Go's runtime system will close any open files, the garbage collector will release the program's memory, and any other database or network that the application has been talking to will detect the application's demise and respond gracefully. The same just as the bigdigits example, we not use log.Fatal() in the first statement the err contains the usage message and we want to print this without the date and time the log.Fatal() function returns normally.

In Go a panic is a runtime error (rather like an exception in other languages). We can panic ourselves using the built-in panic() function and can stop a panic in its tracks using the recover() function ($5.5, 212). In theory, Go's panic/recover functionality can be used to provide a general-purpose exception handling mechanism—but doing so is considered to poor practice. The Go way to handle errors is for methods to return an error value as their sole or nil if no error occurred—and for callers to always check the error they receive. The purpose of panic/recover is to deal with genuinely erroneous (i.e., unexpected) problems and not with normal errors.

With both files successfully opened (the os.Stdin, os.Stdout, and os.Stderr are automatically opened by the Go runtime system), we can call the anonymous() function to do the processing, passing the files on which it works. If anonymous() returns nil the main() function terminates and any deferred statements—in one that closes the inputFile and outputFile if they are not os.Stdin and os.Stdout—executed. And if any err is not returned, the program is exited, and Go's runtime system closes any open files.
