
## 7.2. Examples

```go
defer file.Close()
reader := bufio.NewReader(file)
for {
    line, err := reader.ReadString('\n')
    if line != "" {
        lines <- line
    }
    if err != nil {
        if err != io.EOF {
            log.Println("failed to reading the file:", err)
        }
        break
    }
}
close(lines)
```

This function should be very familiar since it is so similar to ones we have seen before. The first key aspect is that each line is sent to the lines send-only channel—this will block if the channel's buffer becomes full, until another goroutine receives from it. Naturally, even if there is blocking, it affects this goroutine; all the others continue unaffected. The second key aspect is that all the lines have been sent we close the lines channel; this tells prospective receivers that there is no more data to receive. Keep in mind, though, that this goroutine executes concurrently with the program's goroutines—in particular, the line processing worker goroutines—so the close() statement is not reached until most of the work has been done.

```go
func processLines(done chan struct{}, pageMap safemap.SafeMap, lines <-chan string) {
    getRx := regexp.Compile(`GET [\t]+({^ \t\n[.]+\.html)`)
    incrementer := func(value interface{}, found interface{}) interface {
        if found {
            return value.(int) + 1
        }
    }
    for i := 0; i < workers; i++ {
        go func() {
            for line := range lines {
                if matches := getRx.FindStringSubmatch(line); matches != nil {
                    pageMap.Update(matches[1], incrementer)
                }
            }
        }()
    }
}
```

This function follows the Go parameter ordering convention of having destination channels first (in this case the done channel), followed by the source channels (in this case the lines channel).

The function creates the goroutines (in this example) that do the work. Each goroutine shares the same *regexp.Regexp* (since, unusually for pointed-to values, this is to be thread-safe), the same `increment()` function (since it has no side effects and doesn't access any shared data). They also share the same `pageMap` (of type SafeMap interface), even if the methods that modify a SafeMap are thread-safe.

The `regexp.FindSubstring()` returns nil if there is no match, or a `[string]` where the first item is the entire matching text and each subsequent item matches a parenthesized subexpression in the regular expression. In this case we have one subexpression, so we get a match at all, the `[string]` string will have exactly two items in it: the matching text and the text matched by the parenthesized subexpression, in this case the filename of an HTML page.

Each worker goroutine receives different lines that are read by the goroutine created in the `readLines()` function from the lines receive-only channel. If a line matches the regular expression that identifies GET on HTML files, the `safeMap.Update()` method is called with the page filename (matches[1]) and with the `increment()` function. The `increment()` function is executed inside the safe map's update returns an incremented value for existing pages and a value of 1 for pages that are new to the map. (Recall from the previous subsection that if the function passed to the safeMap.Update() method calls any other SafeMap method we will get a deadlock.) When there are no more pages to process, each worker goroutine sends an empty string to the done send-only channel to signal that it has finished its work.

```go
func waitUntil(done <-chan struct{}) {
    for i := 0; i < workers; i++ {
        <-done
    }
}
```

This function executes in the main goroutine and blocks waiting on the done receive-only channel. When every worker goroutine has sent an empty string to the done channel, the loop finishes. As usual, we don't bother to close the done channel since we never use it in a context where it is checked for being closed. By blocking, this function ensures that the processing gets done before the main goroutine terminates.

```go
func showResults(pageMap safemap.SafeMap) {
	pages := pageMap.Close()
	for page, count := range pages {
		fmt.Printf("%d %s\n", count, page)
	}
}
```

Once all the lines have been read and all the matches added to the safe map, this function begins by calling the `safemap.Close()` method which closes the safe map's channel, terminates the `safemap.run()` method executing in a goroutine, and returns the underlying `map[string]interface{}` to the caller. The returned map can no longer be accessed using the safe map's channel and can be safely used in a single goroutine (or multiple goroutines if we serialize accesses using a mutex). From this point, only the map in the main goroutine, so no serialization is necessary. We completely iterate over the map's key-value pairs and print them to the console.

Using a value type `SafeMap` interface provides thread safety and simple syntax—no need to concern ourselves with locks. One disadvantage of this approach is that the safe map's values are generic `interface{}` values rather than specific types, hence the need to use type assertion.

### 7.2.4.2. Synchronizing with Mutex-Protected Map

Whether we use a safe map or a plain map protected by a mutex, we might reasonably expect that by increasing the number of goroutines would increase the overall speed of the program. However, since accesses to the safe map or the plain map are serialized (behind the scenes in the case of the safe map), as we add goroutines, contention will increase.

### 7.2.4.3. Synchronizing by Merging Local Maps via Channels

As is often the case, we can trade some memory for increased speed. So, for example, we could let every worker goroutine have its own plain map. This would maximize throughput since there would be no contention at all during processing, but at the price of using extra memory (since most likely every map would have some even pages in common). At the end of course, we would have to merge these maps—and that could be a bottleneck since, while one map was being merged, others that were ready to merge would have to wait.

```go
type pageMap struct {
	count map[string]int
	mutex *sync.RWMutex
}
```
