
## 5.4. Communication Concurrency Statements

### 5.4.1. Select Statements

Go's select statement has the following syntax:

```go
select {
    case sendOrReceive1: block1
    case sendOrReceiveN: blockN
    default: blockD
}
```

In a select statement, Go evaluates each send or receive statement in order from first to last. If any of these can proceed (i.e., is not blocked), then of those that can proceed, an arbitrary choice is made as to which one to use. If none can proceed (i.e., they are all blocked), there are two scenarios. If a default case is present, the default is executed and execution resumes from the statement; but if there is no case the select will block until at least one communication can proceed. A consequence of the select statement's logic is as follows: A select with no default case is blocking and will only complete when one communication case (receive or send) has occurred. A select with a default case is nonblocking and executes immediately either because a communication occurred or if no communication is ready.

To get will review two examples. The first example is rather contrived but gives a good idea of how select works. The second example shows a more realistic approach.

```go
channels := make([]chan bool, 6)
for i := range channels {
    channels[i] = make(chan bool)
}
go func() {
    for {
        channels[rand.Intn(6)] <- true
    }
}()
```

In this snippet we have created single channels which can send and receive booleans. We have then created a goroutine that has an infinite loop in which one of the channels is chosen at random and sent a true value every iteration. The goroutine immediately blocks of course, since the channels are unbuffered and we have not tried to receive from any of them. Go's select statement has nothing to do with select() function used to monitor file descriptors—for that, use the syscall package.

```go
for i := 0; i < 6; i++ {
    var x int
    select {
    case <-channels[0]:
        x = 1
    case <-channels[1]:
        x = 2
    case <-channels[2]:
        x = 3
    case <-channels[3]:
        x = 4
    case <-channels[4]:
        x = 5
    }
    fmt.Printf("%d ", x)
}
fmt.Println()
```

In this snippet we use six channels to simulate rolls of a fair die (strictly speaking, the select statement waits for one of the channels to have something to send—the select blocks since we have not provided a default case—and as soon as one or more channels are ready one case is chosen randomly). Since the select is inside a plain for loop it is executed a fixed number of times. Now we will look at a more realistic example. Suppose that we want to perform the same computation on two data sets and the computation produces a sequence of results. Here is a skeleton of a function that performs such computation:

```go
func expensiveComputation(data any, answer chan int, done chan bool) {
    // setup ...
    finished := false
    for !finished {
        // computation ...
        answer <- result
    }
    done <- true
}
```

The function is given some data to work on and two channels. The answer channel is used to send each result to the monitoring code and the done channel is used to notify the monitoring code that the computation has finished.

```go
// setup ...

doneCount := 0

answerbeta := make(chan int)

    close(answer)
    close(answerbeta)
}()

	var result int
	select {
	case result = <-answer:
		which = "alpha"
	case result = <-answerbeta:
		which = "beta"
	case <-done:
		doneCount++
	}
	if result != 0 {
		fmt.Printf("%s-%d\n", which, result)
	}
}
fmt.Println()
```

This is the code that sets up the channels, starts the expensive computations, monitors progress, and cleans up the end—there isn't a lock in sight. We begin creating two channels to accept results, answer and answerbeta, and a channel to keep track of when the computations are finished. We create anonymous functions in which the channels are closed and can use defer statements so that they will be closed when they are no longer needed, that is, when the enclosing function returns. Next, we start off the expensive computations (in their own goroutines), giving each one its own unique data to work on, and for communications its own unique answer channel, and the done channel that is shared.

We could have given both computations the same answer channels, but if we did we would not know which one had given which result (which might not matter, of course). If we wanted to use the same channel and wanted to identify the origin of any particular result we could make a single answer channel that operated on a struct—for example:

```go
type answer struct {
    id int
    result int
}
```

With the expensive computations started in goroutines (but, since their channels are unbuffered), we are ready to receive their results. The for loop starts with fresh result values on every iteration, the blocking select statement executes an arbitrary case from those that are ready to proceed. If an answer is ready we set which to indicate its origin and print the origin and the result. If the done channel is closed when we reach the number of expensive computations doneCount—started we know they are all finished and the loop ends.

### 5.5. Defer, Panic, and Recover

The most common uses of defer are to ensure that successfully opened files are closed. The one case where it is common to ignore returned error values is printing to the console:

```go
var file *os.File
if file, err = os.Open(filename); err != nil {
  log.Println("failed to open: ", err)
  return
}
defer file.Close()
```

This is an extract from Chapter 7. It shows a typical pattern for opening a file and deferring the close if open succeeded. This pattern of creating a value and deferring some kind cleanup function is standard in Go. We can, of course, apply this pattern to our own types by providing them with a Close() or Cleanup() function, although this is rarely needed.

### 5.5.1. Panic and Recover

Go provides an exception handling mechanism through the use of its-in panic() and recover() functions. These functions could be used to provide a general-purpose exception handling mechanism, similar to those available in other languages (e.g., C++, Java, Python): But to do so is considered poor Go style.

Go distinguishes between errors—that might go wrong and that a program should handle gracefully (e.g., a file that could not open)—and exceptions—something that "cannot" happen (e.g., a precondition which should always be true). The idiomatic way to handle errors in Go is to return an error as the last (or only) return value from functions and methods to always check any returned errors. (The one case where it is common to ignore returned error values is printing to the console.)

For "cannot happen" situations we can call the built-in panic() function with any value like.g., a string that explains the invariant that has been broken. In other languages we might use an assertion for these situations, but in Go we call panic(). During early development and prior to any release the simplest and probably the best approach is to call panic() to terminate the program for problems to be impossible to ignore so that they get fixed. When we start deploying our application it is to avoid termination when problems occur at all possible, and this can be done while still leaving any recover() calls in our packages. During recovery we can catch and log any panic (so that they remain visible), and return non-nil errors to callers who can then restore the program to a sane state from which it can safely continue to run.
