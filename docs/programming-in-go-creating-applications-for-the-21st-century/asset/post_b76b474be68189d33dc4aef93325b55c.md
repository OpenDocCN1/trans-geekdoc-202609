We have avoided the “too many open files” problem by combining two tactics. First, we process small files in one goroutine (or perhaps just a few goroutines if the filepath.walk() function handles to spread its work over multiple goroutines and calls the walker function them concurrently). This ensures that if we hit a directory with thousands of tiny files we don’t have too many open at once; only one or a few goroutines process them at the same time.

We should be able to afford to process big files in their own goroutines since we are unlikely fast enough to open too many of them at the same time. But if we end up processing too many files, that is, if we start to have too many goroutines, the second tactic will kick in. (The runtime.NumGoroutine() function tells us how many goroutines exist when the function is called.)

If we have many goroutines we stop creating new goroutines for processing big files, and instead process every file—no matter what size it is—in the current goroutine. This forces the program to use the same goroutine (or some few goroutines) to process each subsequent file, and keeps a lid on the number of files that we have open at the same time. Meanwhile, as each of the goroutines already processing big files finish and are removed by Go’s runtime system, the number of goroutines in use will decrease. So, at some point, there will be fewer goroutines than our limit, and we will again start creating new goroutines to process big files.

```go
func processFile(filename string, info os.FileInfo, infoChan chan fileInfo, done func()) {
	if err != nil {
		defer done()
		return
	}
	file, err := os.Open(filename)
	if err != nil {
		log.Println("error:", err)
		return
	}
	defer file.Close()
	hash := sha1.New()
	size, err := io.Copy(hash, file)
	if err != nil {
		log.Println("error:", err)
		return
	}
	infoChan <- fileInfo(hash.Sum(nil), size, filename)
}
```

This function is called from the current goroutine or in a newly created goroutine to compute the file's SHA-1 and to send the file's details to the infoChan channel.

If the done variable is not nil, this function has been called in a goroutine, so we defer a call to the done() function (which simply calls a call to the sync.WaitGroup.Done() method). This is to ensure that for every sync.WaitGroup.Add(1), there is a corresponding sync.WaitGroup.Done() call, since this is essential to the correct operation of the sync.WaitGroup function(). If the variable is nil we ignore it.

Next, we open the file for reading, and defer closing it, in the usual way. The standard library's crypto/sha package provides the sha.New() function which returns a value that satisfies the hash.Interface. This interface provides a Sum() method that returns the hash value (i.e., the 20-byte SHA-1 hash in this case), and also fulfills the io.Writer interface. (We pass in nil to existing []byte to make the Sum() method give us a new []byte; alternatively, we could pass it an []byte to which it will append the hash sum.)

We could have read in the entire contents of the file and then called the sha.Write() method to write the file into the hash, but we have opted to take a much more efficient approach and used the io.Copy() function instead. This function takes a writer to write to (in this case the hash), and a reader to read from (here, the open file), and copies from the latter to the former. When the copy has finished, it returns nil or an error. Since the SHA-1 hash can work on chunks of data at a time, the maximum amount of memory used by the io.Copy() call will be the size of the buffer used by the SHA-1 plus some overhead. If we had read the entire file into memory first, we would have used the same amount of buffer and overhead—plus memory to store the whole file. So, for larger files, using io.Copy() achieves real savings. Once the computation is done we send a fileInfo to the infoChan channel with the SHA-1 value, the file's size (available from the os.FileInfo passed to the processFile() function), and the filename (including the full path).

```go
type pathsInfo struct {
	size  int64
	paths []string
}
```

This struct is used to store the details of each duplicate file, that is, its size, all the file paths and filenames. It is merged by the merge() and outputResults() functions.

```go
func mergeResults(infoChan <-chan fileInfo) map[string]*pathsInfo {
	pathData := make(map[string]*pathsInfo)
	format := fmt.Sprintf("%06X:%dX", shaSize*2) // "%06X:%40X"
	for info := range infoChan {
		key := fmt.Sprintf(format, info.size)
		value, found := pathData[key]
		if !found {
			value = &pathsInfo{size: info.size}
			pathData[key] = value
		}
		value.paths = append(value.paths, info.path)
	}
	return pathData
}
```

This function begins creating a map to store duplicate files. The keys are strings composed of the file's size, a colon, and the file's SHA-1, and the values are *pathsInfo. To produce the keys we have created a format string which has 16 zero-padded digits to represent the file's size and enough hexadecimal digits to represent the SHA-1. We use leading zeros for the file size part of the key so that we can sort the keys by size later. Since one byte is represented in hexadecimal with two digits, we must use twice as many characters as there are bytes for the SHA-1 in the format string. Although multiple goroutines send to infoChan, this function (in the main goroutine) is the only one that receives from the channel—or blocks. The loop ends when all the values have been received and infoChan is closed. For each fileInfo received, a map key is constructed. If the map doesn't have an item with the key, we create a suitable value with the file size, an empty slice of paths, and add it to the map under the new key. With the existing item in the map, append to the item's paths of the file in the infoInfo value. At the end, this will result in duplicate files having path slices with more than one path, and nonduplicates path slices with exactly one path. Once all the fileInfo values have been processed and the map populated, the function returns the map ready for further processing.

```go
func outputResults(pathData map[string]*pathsInfo) {
	keys := make([]string, 0, len(pathData))
	for key := range pathData {
		keys = append(keys, key)
	}
	sort.Strings(keys)
	for _, key := range keys {
		value := pathData[key]
		if len(value.paths) > 1 {
			fmt.Printf("%d duplicate files (%s):%s\n",
				len(value.paths), commas(value.size))
			sort.Strings(value.paths)
			for _, name := range value.paths {
				fmt.Printf("\t%s\n", name)
			}
		}
	}
}
```

the pathData map's keys are strings that begin with each file's size in 16 hexadecimal digits padded with leading zeros. (16 digits was chosen since this is large enough to represent an int64.) This means that retrieving and sorting the keys we can get the files in size order from smallest to biggest. So, the function begins by creating a slice to which each of the map's keys are appended, after which the keys are sorted. Then, the function iterates over the size-sorted slice of keys, retrieving the corresponding pathsInfo. For those that have more than one path the files' size is output followed by an indented list of the duplicate files in path-ordered, as shown below.
