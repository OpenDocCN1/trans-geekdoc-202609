At first it might appear that these other languages' string types are much more convenient than Go's individual characters in their strings can be directly indexed—something only possible in Go if the string exclusively 7-bit ASCII characters (since these are all represented by a single UTF-8 byte). In practical terms this is not a problem for programmers: first, direct indexing isn't used much in Go because Go supports character-by-character iteration over strings; second, because the standard library provides a comprehensive range of string searching and manipulation functions; and third, we can always convert a Go string into a slice of Unicode code points (of type `rune`) which can be indexed directly.

Go's use of UTF-8 for its string type has several advantages compared with, Java or Python, both of which also have Unicode strings. Java represents strings as sequences of code points, each occupying 16 bytes; Python 2.x to 3.2 use the same approach using 16 or 32 bits depending on how Python is built. For English Go uses 8 bits per character to at least twice that for Java and Python. Another advantage of UTF-8 is that it makes endianness doesn't matter, whereas for UTF-16 and UTF-32 it is essential to know the endianness (e.g., UTF-16 little-endian) to be able to decode the text correctly. In addition, UTF-8 is the de facto standard encoding for text files, while other languages decode and encode files to convert to their own internal Unicode representations. Go can read and write such files directly. Furthermore, some major libraries (such as GTK+) use UTF-8 natively, so Go can work with them without encoding or decoding.

In practice, Go strings are just as convenient and easy to use as other languages' string types—once we have learned the Go idioms for working with them.

## 3.1. Literals, Operators, and Escapes

String literals are created using double quotes (") and backticks (``). Double quotes are used to create interpreted string literals—such strings support the escape sequences listed in Table 3.1 ► but may not span multiple lines. Backticks are used to create raw string literals—these strings may span multiple lines; they do not support any escape sequences and may contain any character except for a backtick. Interpreted string literals are the most commonly used kind, but raw strings are useful for writing multiline messages, HTML, and regular expressions. Here are a few examples:

```
text1 = "what is that?", he said // Interpreted string literal
text2 = `what is that?`, he said // Raw string literal
radicals = "\u2221 \u00222" // radicals == "√√√"
```

The three variables created here are of type string, text1 and text2 contain exactly the same text. .go files use the UTF-8 encoding we can include Unicode characters in them without formality. However, we can still use Unicode escapes as we have done for the second and third symbols. We could not use an octal or hexadecimal escape in this particular case, since their code point range is limited to U+0000 to U+0FF, far too small for the √ symbol's U+221A code value.

If we want to create a long string literal without having an equal line length in code we can use the + concatenation operator. Furthermore, although Go's strings are immutable, they support the += append operator: This replaces the underlying string with concatenation the appended string, if the underlying string's capacity isn't large enough to accommodate the appended string. These operators are listed in Table 3.2 (► 85). Strings can be compared using the comparison operators (see Table 2.3, 57 ◄). Here is an example that uses some of these operators:

The first problem is that Unicode characters can be represented by two or more byte sequences. For example, the Å could be the Åström symbol or simply A with ring above—the two are visually indistinguishable. The Åström symbol's code point is U+012B, but an A with a ring above can be represented by U+0041 and U+030A. In UTF-8 bytes the Å (Å) is represented by the bytes [0xE2, 0x84, 0xAB], an Á by [0xC3, 0x85], and an A with combining character by [0x41, 0xCC, 0x81]. This first problem isn't necessarily significant as we imagine since all UTF-8 byte sequences (i.e., strings) in Go are produced using the same code point bytes mappings. This means, that an é character in a Go character or string literal will be represented by the same bytes. And, of course, if we are only concerned with ASCII characters (i.e., English), the problem doesn't occur at all. And even when we deal with non-ASCII characters that look the same, or when we are reading UTF-8 bytes from our program from a source that has used code point bytes mappings that are legal UTF-8 but differ from Go's. If this really does turn out to be a problem it is always possible to create a custom normalization function, for example, ensured that é was always represented by the bytes [0xC3, 0xA9] (i.e., an e and an ́ combining character). Normalizing Unicode characters is explained in the Unicode Normalization Forms document (unicode.org/reports/tr15). At the time of this writing, the Go standard library has an experimental normalization package (exp/norm).

Since this first problem can only arise with strings coming from external sources—and then only if they use different point bytes mappings than Go—it is probably best handled by isolating the code that accepts external strings. The isolating code could then normalize the strings it receives before providing them to the rest of the program.
