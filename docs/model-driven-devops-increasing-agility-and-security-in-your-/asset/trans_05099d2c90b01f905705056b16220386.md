

Jinja2 是一个模板语言，因此我们本质上为 OpenConfig 接口数据创建了一个 JSON 模板。它是一个简化的模板，仅处理基本属性和 IP 地址，但它展示了 Jinja2 处理一个模型中的传入数据并将其转换为另一个模型的能力。模板中大部分静态部分要么是默认值，要么是用于数据的标签。请记住，我们并不是像使用 Ansible 中的 `set_fact` 那样创建内存数据结构。因为这是一个文本模板，我们创建了一个包含数据的 JSON 数据结构的文本表示。我们仍然需要以编程方式将其提供给 playbook。为此，我们在 playbook 中创建一个任务，该任务获取通过 Jinja 模板提取的 NetBox 数据并将其分配给一个 fact。由于 Ansible 处理 playbook 的方式，此文本数据会被反序列化为数据结构，仿佛是手动输入的一样。此 playbook 在 [Listing 4-20](#ch04.xhtml#ch4list20) 中演示。

LISTING 4-20 Simple Playbook to Convert Text from Template into a Variable

[Click here to view code image](Images/ch04_images.xhtml#plist4-20)

```
- hosts: all
  gather_facts: no
  tasks:
    - set_fact:
        oc_interfaces: "{{ lookup('template', 'netbox-to-oc.j2') }}"
    - debug:
        var: oc_interfaces
```

此 playbook 将 NetBox 数据以 OpenConfig 系统模型的形式生成，如 [Listing 4-21](#ch04.xhtml#ch4list21) 中所示。

### Summary

本章演示了使用模型驱动原则构建 IaC 管道的基本构建块。具体来说，我们从两种事实来源（文本和数据库）中提取信息。文本事实来源以原生 OpenConfig 格式提供信息。由于数据库事实来源有其原生数据模型，我们使用 Jinja 将其转换为 OpenConfig。在这两种情况下，我们构建了一个 OpenConfig 服务（系统 + 接口），然后通过平台（例如 Cisco NSO）将其推送到设备，如 [Figure 4-8](#ch04.xhtml#ch4fig8) 所示。

本章中的示例表明，网络自动化更多是数据管理和移动的问题，而非纯粹的编码问题。基本上，我们将配置数据从其来源移动到网络中。数据模型可以表示网络中所有可能的配置。因此，所有配置更改都可以通过类似的流程来处理。不再需要为每种可能的更改类型（如 DNS、NTP、接口、BGP）编写单独的 playbook 或脚本，一套即可满足需求。此外，编码被简化，因为我们不需要知道如何或以什么顺序配置各种服务。平台或终端设备会为我们处理这些。虽然我们确实使用了平台（在我们的示例中是 Cisco NSO），但任何完全原生支持 OpenConfig 的设备都会以相同的方式工作。此外，有多种选项可以满足这一需求。最后，许多新的网络平台（例如 AWS、Azure、Meraki、Mist）都内置了执行相同功能的平台。

在下一章中，我们将在 IaC 基础之上构建，并通过利用 CI/CD 原则来正确测试和验证基础设施的更改，在将其应用于生产环境之前更进一步地迈向真正的基础设施 DevOps。

## Continuous Integration/Continuous Deployment

在前一章中，我们解释了基础设施即代码的概念，以及它如何让你将基础设施描述为一组有组织的数据和人类可读的文件，这些文件可以在源代码管理器中使用版本控制进行管理。有了 IaC，你现在拥有大规模自动化网络基础设施的工具；然而，IaC 也带来了新的风险。在传统的操作模型中，命令行界面输入错误通常只影响单个节点或网络中的少数几个节点，而使用 IaC 时的一个简单错误可能会对整个网络产生重大且广泛的影响。自动化和 IaC 的规模扩大可能会显著放大错误的影响范围。本章探讨了持续集成/持续部署的概念，以及它如何帮助降低在自动化网络基础设施时出错的风险。
