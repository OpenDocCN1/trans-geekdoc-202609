最后，我们希望专注于成果，并提供大量代码以在您的组织中实现该成果。我们专注于行业标准工具和方法。在可能的情况下，我们使用开源或免费工具。当我们不得不选择供应商解决方案时，我们会以一种使其成为特定实现选择的方式进行选择。也就是说，为各种组件使用不同的供应商实现不会显著改变我们所呈现的原则、框架甚至代码。

### 谁应该阅读本书？

本书面向信息技术领域内运行物理网络的基础设施团队，尽管这些原则适用于任何基础设施团队。我们深入探讨了模型驱动的 DevOps，并通过我们的开源配套代码仓库中的用例和具体示例对其进行定义。除了 IT 基础设施团队，本书也适用于希望在基础设施的所有阶段构建安全性的网络安全团队。最后，人为因素部分面向个人贡献者以及希望了解与通过团队实现高质量结果相关的现代最佳实践的业务和技术领导者。

### 本书如何组织

本书的章节遵循逻辑进展。首先，我们探讨*为什么*网络基础设施运营需要改变，然后探讨*什么*需要改变，最后向您展示*如何*改变它。您的旅程包括模型驱动 DevOps 的参考实现，它将指导您如何应用所学的技术和概念。在建立坚实的技术基础后，我们以讨论在进行如此重大的运营变更时需要考虑的重大人为因素来结束旅程。

在此过程中，您将遇到练习，这些练习将让您获得实践经验，更好地理解技术细节，并测试您的知识。这些练习基于参考实现，并在全书中标识。

为了提供一些背景并帮助说明书中许多概念，每一章都以一个涉及名为 Bob 的网络工程师的虚构故事开头。Bob 为 ACME Corp 工作。ACME Corp 是一家故意设计的通用公司，拥有典型的组织结构，包括 CIO、各种 IT 孤岛和顾问。最重要的是，它以非常依赖人力、亲力亲为的方式运行网络基础设施。在 CIO 的指示下，Bob 正在踏上 DevOps 之旅。正是通过他的挑战、惊人的失败和最终的成功，我们才看到了传统运营模式的问题，以及自动化，最终是 DevOps，如何实现真正的业务转型。

### 书籍结构

本书中的每一章都旨在基于前一章构建。基础设施 DevOps 是一段旅程，章节的排列旨在引导您完成这段旅程。以下是每一章的简要摘要及其如何融入旅程。

*   **[第 1 章](#ch01.xhtml#ch1)，“灯泡亮了”：** 在本章中，我们说明为什么网络基础设施的传统运营模式需要改变，简要介绍 DevOps 如何解决传统模式中的许多问题，并探讨 DevOps 为何未被广泛采用于本地 IT 基础设施的原因。

*   **[第 2 章](#ch02.xhtml#ch2)，“更好的方式”：** 在本章中，我们定义业务转型的目标，开始讨论模型驱动 DevOps 的高级框架，并介绍事实来源和数据模型等概念。

*   **[第 3 章](#ch03.xhtml#ch3)，“可消费的基础设施”：** 如果网络基础设施要成为业务转型的推动者，我们需要摆脱逐个设备的 CLI 管理模式。本章论证了 `API` 是新的 `CLI`，并探讨了我们可以利用和扩展 `API` 的方式。

*   **[第 4 章](#ch04.xhtml#ch4)，“基础设施即代码”：** 虽然 `API` 使您能够以编程方式处理网络基础设施，但您不必是程序员才能利用它们。本章探讨了您如何使用数据模型、事实来源、配置管理工具和模板工具等概念将网络基础设施称为“代码”。这些工具共同使基础设施即代码成为可能，并让您像在“云”中一样操作网络基础设施。

*   **[第 5 章](#ch05.xhtml#ch5)，“持续集成/持续部署”：** 基础设施即代码非常强大，但像许多强大的事物一样，如果滥用，会带来巨大的风险。在本章中，我们探讨了版本控制系统、数据验证工具、模拟平台和 CI/CD 的概念。这些工具共同使大规模安全地使用基础设施即代码以及自动化合规性和安全性成为可能。

*   **[第 6 章](#ch06.xhtml#ch6)，“实现”：** 关于 DevOps 的书籍通常关注*为什么*和*什么*，但它们常常省略*如何*。在本章中，我们将前几章涵盖的概念和技术汇集在一起，并将其应用于参考实现。参考实现作为 GitHub 上的仓库发布，以便您可以获得模型驱动 DevOps 的实践经验，并修改或扩展代码以满足您自己的需求。

*   **[第 7 章](#ch07.xhtml#ch7)，“人为因素”：** 本书大部分内容都集中在实现模型驱动 DevOps 的技术方面。然而，技术挑战只是旅程的一部分。涉及打破组织孤岛、文化变革和技能差距的人为因素的重要性无论如何强调都不为过。本章概述了为什么不仅关注技术能力是不够的，还要关注实施 DevOps 的人性方面。
