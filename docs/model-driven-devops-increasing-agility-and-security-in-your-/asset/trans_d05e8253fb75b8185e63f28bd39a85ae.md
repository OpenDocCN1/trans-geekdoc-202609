

文本事实来源，通常被归类为基础设施中的“代码”标签，是以某种文本形式指定的配置信息。在前面的示例中，我们创建了一个非常小的事实来源（仅限 DNS 服务器）。现在让我们来看一个使用 OpenConfig 的更完整的示例。由于 YAML 略具可读性，我们使用该格式，如 [清单 4-9](#ch04.xhtml#ch4list9) 所示。

### 清单 4-9 OpenConfig-System 数据

[点击此处查看代码图片](Images/ch04_images.xhtml#plist4-9)

```
openconfig-system:system:
  aaa:
    authentication:
      admin-user:
        config:
          admin-password: 'admin'
      config:
        authentication-method:
          - 'LOCAL'
    authorization:
      config:
        authorization-method:
          - 'LOCAL'
  clock:
    config:
      timezone-name: 'EDT -4 0'
  config:
    domain-name: 'domain.com'
    hostname: 'router1'
    login-banner: 'Go away!'
    motd-banner: 'Welcome!'
  dns:
    servers:
      server:
        - address: '1.1.1.1'
          config:
            address: '1.1.1.1'
        - address: '2.2.2.2'
          config:
            address: '2.2.2.2'
  ssh-server:
    config:
      enable: true
      protocol-version: 'V2'
```

此数据配置设备名称，以及管理员用户的密码，并启用 SSH。它使用 OpenConfig System YANG 模型，因此与厂商无关。此 YAML 可以放入 Ansible 库存文件中（例如，`oc-system.yaml`），并用于指定应推送到网络基础设施的系统配置。如果我们将此 YAML 放在组织级别（例如 `group_vars/all/oc-system.yaml`），所有设备都将继承它；但是，它包含需要特定于设备，并可能特定于区域或站点的信息。我们可以通过在工具中有选择地更改值，或者使用变量来替换适当的值来处理此场景。此外，我们可以利用 Ansible 对变量的惰性求值，在适当的级别插入正确的值。例如，我们可以将系统级配置块更改为 [清单 4-10](#ch04.xhtml#ch4list10) 中所示的内容。

### 清单 4-10 带有变量的 OC-System 片段

[点击此处查看代码图片](Images/ch04_images.xhtml#plist4-10)

```
config:
  domain-name: 'domain.com'
  hostname: '{{ inventory_hostname }}'
  login-banner: 'Banner'
motd-banner: 'MOTD'
```

此清单将 `hostname` 求值为 `'{{ inventory_hostname }}'`，从而生成一个具有特定设备主机名的负载。我们可以将此示例扩展到 DNS 服务，通过将 [清单 4-9](#ch04.xhtml#ch4list9) 中的 `dns` 块更改为使用 `DNS1` 和 `DNS2` 事实，如 [清单 4-11](#ch04.xhtml#ch4list11) 所示。

### 清单 4-11 在事实来源数据中使用变量

[点击此处查看代码图片](Images/ch04_images.xhtml#plist4-11)

```
dns:
  servers:
    server:
      - address: '{{ DNS1 }}'
        config:
          address: '{{ DNS1 }}'
      - address: '{{ DNS2 }}'
        config:
          address: '{{ DNS2 }}'
```

此方法生成一个单一的 OpenConfig 系统负载，该负载具有适当的区域级和站点级事实，如 [清单 4-12](#ch04.xhtml#ch4list12) 所示。

此简单的事实来源使用 YAML 渲染为文本，这使我们能够利用应用程序 DevOps 中使用的相同类型的基础设施 DevOps 工具。将事实来源呈现为 YAML 或 JSON 既灵活又可扩展，但有时您的事实来源需要包含数据库平台。

#### 数据库事实来源

数据库是组织数据的绝佳方式，许多组织已经将其事实来源的一部分存储在数据库中，例如配置管理数据库（CMDB）或 IT 服务管理（ITSM）平台。由于数据库通常不是可以签入并通过 SCM 跟踪的文本，因此其中包含的数据通常不被视为“代码”。对数据的更改跟踪以及回滚到早期版本的数据的能力需要由数据库处理。

我们介绍了两种从数据库中提取事实来源到 Ansible playbook 的方法：

*   作为动态库存脚本的一部分
*   临时调用以存储和检索特定信息

##### NetBox

为了演示这两种方法，我们使用一个常用的数据库支持的事实来源，名为 NetBox。根据其开发者的说法，NetBox 是一种“基础设施资源建模（IRM）应用程序”，旨在通过提供网络的 *期望* 状态来赋能网络自动化。NetBox 是开源的，可扩展，并拥有强大的 API。NetBox 提供了一组功能强大的 Ansible 模块和插件，利用此 API。

让我们来看看 NetBox 的 Ansible 动态库存插件。要使用该插件，我们需要通过环境变量向其提供 API 端点和令牌：

[点击此处查看代码图片](Images/ch04_images.xhtml#ppg60-1)

```
NETBOX_API=https://10.10.185.228
NETBOX_TOKEN=ad5fedecba150368c068fa3bbc90fe2d058fac2b
```

API 是 NetBox 设备的 IP 地址，令牌是通过 UI 生成的，方法是转到 **Profile > API Tokens > Add a Token**。我们创建一个具有所需访问权限的令牌，并将生成的令牌复制到 `NETBOX_TOKEN` 环境变量中。接下来，我们需要为插件创建配置文件，并将其放入库存目录中，如 [清单 4-13](#ch04.xhtml#ch4list13) 所示。

### 清单 4-13 NetBox Ansible 动态库存插件

[点击此处查看代码图片](Images/ch04_images.xhtml#plist4-13)

```
$ more org/netbox.yaml
plugin: netbox.netbox.nb_inventory
validate_certs: False
fetch_all: True
interfaces: True
group_names_raw: True

  - sites
```
