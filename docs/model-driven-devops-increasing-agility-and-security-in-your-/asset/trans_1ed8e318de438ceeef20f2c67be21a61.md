

# Chapter 3

## 平台 API：北向与南向

在 IT 基础架构领域，将平台 API 视为北向或南向通常很有用。典型的控制器平台会暴露一个“北向” API，旨在为其他应用程序提供功能。一个很好的示例是控制器本身的 UI。通常，控制器的 UI 会使用同一个北向 API 来检索数据并进行配置更改。当通过北向 API 收到请求，且控制器软件确定需要对一个或多个设备进行更改时，它会使用“南向” API 与各种设备进行通信。这些南向 API 特定于网络中设备所暴露的 API。不同设备供应商通常为其设备提供不同的 API。如 [图 3-3](#ch03.xhtml#ch3fig3) 所示，控制器平台可以将许多不同供应商或设备的 API 整合为单一、统一的北向 API。

### API 和功能标准化

平台可以发挥的一个重要作用是标准化一组异构设备之间的 API。从我们之前的示例来看，平台会在内部透明地执行任何数据转换，同时向用户呈现单一 API（参见 [图 3-4](#ch03.xhtml#ch3fig4)）。

![FIGURE 3-4 Platform API Normalization](Images/03fig04.jpg)

FIGURE 3-4 Platform API Normalization

这种标准化大大降低了网络自动化的复杂性，因为它允许自动化工具针对单一数据模型和单一 API 进行工作。如果没有这种规范化，工具就必须执行数据模型转换，然后为网络上可用的每种设备类型调用正确的 API。回想一下，当 ACME Corp 的 Bob 意识到网络上的每种设备都有不同的命令行，需要各自的自定义代码时，这似乎无法管理。具有将数据标准化为单一数据模型和单一 API 的平台解决了这个问题。

平台还通过标准化许多功能各异的异构设备的功能来提供帮助。例如，许多网络设备没有将配置更改回滚到先前状态的能力。如果向平台添加状态，则平台可以跟踪更改发生的过程，以便能够将设备的状态返回到更改发生前的配置。此外，在平台中存储状态允许比较设备的状态应该是什么，以防发生带外更改。如果设备与平台不同步，则可以采用或覆盖本地更改。

### 结构级服务

除了标准化之外，平台还可以为网络提供结构级服务。一种常见的结构级服务是以太网虚拟专用网络 (EVPN)。EVPN 用于在大型校园或站点之间通过第 3 层路由网络扩展以太网第 2 层服务。它被视为一种结构技术，因为它依赖于基于 BGP 的中央控制平面来分发 MAC 地址和其他信息，从而实现端节点之间的连接。如果没有控制平面，结构就无法正常工作，尽管各个设备可以自主运行。

平台可以提供网络的结构级视图以及运行该结构所需的服务（参见 [图 3-5](#ch03.xhtml#ch3fig5)）。这些功能大大简化了网络，并实现了没有此中央功能就不可能实现的服务。

### 可扩展性

平台还使网络自动化的规模更大。如果没有平台，用于自动化的控制节点需要直接与每个设备通信，而不是能够通过利用平台中的状态来优化通信（参见 [图 3-6](#ch03.xhtml#ch3fig6)）。例如，让我们看看 Ansible 等工具如何对设备进行更改。Ansible 的目标是将设备带到所需的最终状态。为此，它需要检查设备的当前状态，将该状态与所需的最终状态进行比较，然后将更改发送到设备。此操作使控制节点与最终设备之间的通信加倍。为了进一步复杂化问题，许多操作仅在配置的离散部分上工作，这意味着需要多次操作才能完成一次更改。

## Summary

本章介绍了成功基础架构自动化的两个主要因素：API 和平台。我们定义了可消费的基础架构，并展示了前一章讨论的 API 与数据模型如何使其成为可能。此外，我们说明了 API 如何实现确定性且高效的机器对机器交互，并且对于成功的自动化至关重要。平台使您能够更好地扩展通过 API 进行的操作，配置物理硬件，并使您能够在基础架构之上构建更复杂的自动化服务。我们还研究了云平台为何如此强大，以及如何将相同的平台概念应用于本地基础架构。在接下来的章节中，我们将介绍如何将基础架构表示为代码，然后如何将您迄今所学的一些高级概念组装成一个用于大规模基础架构自动化的框架。

## 基础架构即代码

在前一章中，您学习了如何通过 API 和平台使基础架构可消费，以减少自动化的复杂性。以可消费的基础架构为基础，本章介绍了基础架构即代码 (IaC) 的概念，并说明它在很大程度上可以被视为数据移动、转换和验证练习，而不是编程练习。本章和下一章中的许多代码片段有助于说明我们所呈现的概念。它们是更完整的参考实现的简化版本，该实现将在 [第 6 章](#ch06.xhtml#ch6) “实现”中介绍，也可通过 GitHub 获取。
