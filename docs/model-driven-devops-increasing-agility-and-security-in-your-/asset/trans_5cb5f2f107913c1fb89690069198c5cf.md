

# 数据模型编码格式

数据模型编码格式能够将数据存储在文本文件中，并通过 API 发送数据。存在此类格式很多，但我们将从 IaC 的运维和编程两个方面，介绍最常见的格式。为了便于比较，我们将用每种描述的格式对相同的数据进行编码表示。

## JSON

JavaScript 对象表示法（`JSON`）是一种源自 JavaScript 的开放标准文件格式，尽管已被多种语言广泛采用用于存储和传输数据。`JSON` 使用冒号分隔的键/值对以文本形式表示数据。`JSON` 值可以是标量、布尔值、列表和其他 `JSON` 对象。由于轻量且易于序列化，`JSON` 常用于 API。尽管仍然非常易于人类阅读，但有时可能会显得繁琐，因为它使用括号来划分列表和对象，使其结构更符合程序员的习惯，如 [清单 4-1](#ch04.xhtml#ch4list1) 所示。

### 清单 4-1 以 JSON 呈现的 OC-System 片段

[单击此处查看代码图片](Images/ch04_images.xhtml#plist4-1)

```
{
   "openconfig-system:system": {
      "config": {
         "domain-name": "domain.com",
         "hostname": "router1"
      }
   }
}
```

## YAML

YAML 是一种人类可读的语言，常用于配置文件以及 Ansible 等许多 IaC 工具。它是 `JSON` 的超集，可以用于表示所有相同的数据。尽管它具有简洁、紧凑的表示形式，但也可能难以创建和调试，因为它使用空格来表示特定值的层级关系。例如，如果没有遵循正确的间距，值可能会与数据结构的错误部分关联，或者整个数据结构可能因违反 YAML 结构而无法读取。大多数非程序员倾向于偏好 YAML，因为它更易于阅读，且更贴近配置而非编程，如 [清单 4-2](#ch04.xhtml#ch4list2) 所示。

### 清单 4-2 以 YAML 呈现的 OC-System 片段

[单击此处查看代码图片](Images/ch04_images.xhtml#plist4-2)

```
---
openconfig-system:system:
  config:
    domain-name: 'domain.com'
    hostname: 'router1'
```

## XML

可扩展标记语言（`XML`）定义了一套规则，用于以人类可读的格式对文档进行编码，尽管它比 YAML 稍显繁琐。不过，它是可序列化的，并且在各种应用中已使用数十年。它是一种语言，而不仅仅是一种数据格式，并支持查询。由于其结构严格，`XML` 手动构建往往更加复杂，如 [清单 4-3](#ch04.xhtml#ch4list3) 所示。尽管广泛部署，但在 IaC 工具中很少使用；不过，我们在此列表中包含它以便熟悉，因为在使用 NETCONF 时，它常用于对数据进行编码。

### 清单 4-3 以 XML 呈现的 OC-System 片段

[单击此处查看代码图片](Images/ch04_images.xhtml#plist4-3)

```
<?xml version="1.0" encoding="UTF-8" ?>
<openconfig-system:system>
  <config>
    <domain-name>domain.com</domain-name>
    <hostname>router1</hostname>
  </config>
</openconfig-system:system>
```

# 数据模型描述语言

为了拥有标准的数据模型，我们需要一种标准的方式来描述模型，使得一个人可以根据模型创建数据结构，而另一个人可以读取相同的数据结构并得到第一个人所期望的数据模型。我们在此介绍 YANG 和 JSON Schema。这两种描述语言都可以用于创建数据模型，并验证数据结构是否符合该模型。

## YANG

又一种下一代（`YANG`）是一种用于建模配置数据、状态数据、远程过程调用和通知的数据建模语言，适用于网络管理协议（RFC 7950）。当通过 NETCONF 和 RESTCONF 等网络管理协议发送时，它在 API 用户和设备之间提供了一个契约，即如果你以特定格式提供数据，该设备将配置设备的相应部分。该数据建模语言可用于对网络元素的配置数据和状态数据进行建模。由于它与协议无关，`YANG` 可以转换为网络配置协议支持的任何编码格式（例如 XML 或 JSON）。

[清单 4-4](#ch04.xhtml#ch4list4) 展示了 `YANG` 的示例。具体来说，它是一组配置信息，包括我们稍后将使用的 OpenConfig System 片段的 leaf hostname、domain-name、login-banner 和 motd-banner。

### 清单 4-4 YANG 模型

[单击此处查看代码图片](Images/ch04_images.xhtml#plist4-4)

```
grouping system-global-config {
  description "system-wide configuration parameters";
 
  leaf hostname {
    type oc-inet:domain-name;
    description
      "The hostname of the device -- should be a single domain
      label, without the domain.";
  }
 
  leaf domain-name {
    type oc-inet:domain-name;
    description
      "Specifies the domain name used to form fully qualified name
      for unqualified hostnames.";
  }
 
  leaf login-banner {
    type string;
    description
      "The console login message displayed before the login prompt,
      i.e., before a user logs into the system.";
  }
 
  leaf motd-banner {
    type string;
    description
      "The console message displayed after a user logs into the
      system.  They system may append additional standard
      information such as the current system date and time, uptime,
      last login timestamp, etc.";
  }
}
```

`YANG` 描述定义了结构（即 hostname 是 config 的成员）以及该成员可以保存的数据类型。

## JSON Schema

JSON Schema 与 YANG 类似，可用于定义数据的结构。顾名思义，JSON Schema 特定于 JSON，使用起来也稍微不那么繁琐。不过，由于 JSON 和 YAML 可以互换，我们也可以在 YAML 中定义架构，并使用它们来验证以 YAML 呈现的数据。我们将在 [第 6 章](#ch06.xhtml#ch6) 中更详细地介绍 JSON Schema，届时我们将使用它来验证真值数据源。

# 常见 IaC 工具

我们将 IaC 分为真值数据源和代码。我们所介绍的数据模型描述和编码格式主要适用于真值数据源数据。以下工具适用于“代码”。

## Ansible

Ansible 是开源软件，用于以过程化方式进行资源配置、配置管理和应用程序部署。它是一种 IaC 工具，包含其自身以 YAML 呈现的声明式语言，可以与 Git 等源代码管理系统配合使用。它本质上是 Python 上的一层，使非程序员能够更轻松地编排工作流。它通常使用 SSH 作为传输方式，用于自动化本地安装了 Python 的系统。然而，对于网络设备，设备上通常没有 Ansible 可用的 Python 解释器，因此它使用连接插件通过 CLI、NETCONF 和其他协议进行通信。此外，Ansible 具有一个 URI 模块，可用于通用 RESTful API。

尽管 Ansible 是 Python 上更易于使用的抽象层，但这种易用性也带来了局限性。一般来说，Ansible 最适合广泛使用，而不一定是深度使用。当 Ansible 语法被超出其设计范围来处理复杂操作时，可能会变得更加困难，这种特性可能会限制其有效性。通常，这种复杂性最好在插件或 Jinja 中处理。

## Jinja2

Jinja 是一种使用类 Python 语法的模板引擎。尽管主要用于创建 HTML 或 XML 等标记文档，但也可以用于创建通过 API 配置设备的负载。它处理循环的能力远优于 Ansible，因此更适合处理设备接口、路由和 ACL 等内容。
