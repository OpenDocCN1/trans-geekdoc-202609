
The sharpest contrast with the BPR security game is who decides the password inputs of honest `P[i]`’s. In the BMP model, the honest parties’ inputs are decided by a special entity called the *ring master*, but without loss of generality the ring master can follow the directions of the adversary ![image](images/a.jpg). Hence, somewhat counterintuitively, it is the adversary ![image](images/a.jpg) who decides all passwords. This is in a strong contrast to the BPR security game where `P[i]`’s passwords are chosen at random from some dictionary by the game challenger, not by the adversary. However, as we will see shortly, this seemingly counterintuitive choice not only makes sense, but it implies security for arbitrary password distributions, and helps overcome several other limitations of the BPR model (see [section 10.3.3](#c10.xhtml#sec10-3-3)). As in the BPR model, ![image](images/a.jpg) can reveal the session keys of any honest party, but since there are no longer any sessions which the adversary “tests”, without loss of generality ![image](images/a.jpg) can get the session keys output by of all `P[i]`’s.

### The ideal-world game

We reverse the presentation used in Boyko et al. (2000) by starting with the *implicitly authenticated* PAKE case, which serves as the base case of the BPR definition, and which subsequently became the standard notion of PAKE. We will explain an extension to *explicit authentication* (PAKE-EA) in [section 10.4.4](#c10.xhtml#sec10-4-4). The ideal-world game in the BMP model is an interaction between a simulator algorithm ![image](images/a.jpg)^∗ and the ideal functionality of a PAKE scheme, denoted ![image](images/f.jpg)`PAKE`, which proceeds as follows:

1.  When an honest party `P[i]` is invoked on some password `pw [P[i]]` by the ring master, ![image](images/f.jpg)`PAKE` sends (`NewSession`, `P`, `i`) to ![image](images/a.jpg)^∗ and creates an internal state for this session, marking it `fresh`. Therefore, the ideal-world adversary knows if some `P[i]` runs a protocol but it does not know their password inputs. The ring master starts `P[i]` on a signal from ![image](images/a.jpg)^∗, also setting `P[i]`’s `role` bit and its intended counterparty identifier `pid`.

2.  For any session `P[i]` adversary ![image](images/a.jpg)^∗ can send message (`TestPwd`, `P`, `i, pw*`^∗) to ![image](images/f.jpg)`PAKE`, which models an active attack in which a real-world adversary follows a PAKE scheme on password guess `pw*`^∗ when interacting with `P[i]`. If `pw*`^∗ = `pw[P[i]]`, then ![image](images/f.jpg)`PAKE` marks `P[i]`’s session as `compromised`, otherwise it marks it as `interrupted`. (These markings will determine how ![image](images/f.jpg)`PAKE` acts in response to `NewKey` queries; see below.) In addition, ![image](images/f.jpg)`PAKE` reveals this marking to ![image](images/a.jpg)^∗, which implies that a real-world PAKE protocol can reveal whether an active attack is successful. Crucially, ![image](images/a.jpg)^∗ can send *at most one* `TestPwd` query per each `P[i]` session, which enforces the requirement that an adversary can test at most one password guess on an attacked session. This query can be made on either a `fresh` session or on a `dangling` terminated session; see `NewKey` processing below. Indeed, the ability of ![image](images/a.jpg)^∗ to make *post-termination* password tests (which remains even for PAKE-EA, see [section 10.4.4](#c10.xhtml#sec10-4-4)) is a crucial difference between the simulation-based BMP model and the UC PAKE model of Canetti et al. (2005) (see [section 10.5](#c10.xhtml#sec10-5)).

3.  For any session `P[i]` adversary ![image](images/a.jpg)^∗ can send (`NewKey`, `P`, `i,` `P`′, `j, sk*`^∗) to ![image](images/f.jpg)`PAKE`, which models `P[i]` receiving the last protocol message (supposedly from ![image](images/ppj.jpg)) and terminating with some output. In response, ![image](images/f.jpg)`PAKE` terminates this session and decides on its output `sk[i]` as follows:

    a) If `P[i]` session is `compromised`, then set `sk[i]` ← `sk*`^∗.

    b) If `P[i]` and ![image](images/ppj.jpg) are both `fresh`, `pw [P[i]]` = `pw [![image](images/ppj.jpg)]`, `pid[P[i]]` = `P`′ and `pid[![image](images/ppj.jpg)]` = `P`, the `role` bits of ![image](images/ppj.jpg) and `P[i]` define them as the first and the last to complete, and ![image](images/ppj.jpg) outputted `sk[j]`, then `sk[i]` ← `sk[j]`.

    c) Else set `sk[i]` ←[$] {0, 1}^(*κ*), and if ![image](images/a.jpg)^∗ requests so, mark `P[i]` as `dangling`.

4.  ![image](images/a.jpg)^∗ can also ask for output `sk[i]` of any terminated session `P[i]` (hence without loss of generality one can assume that all `sk[i]` outputs are sent to ![image](images/a.jpg)^∗), and terminate any running session `P[i]` to output ⊥ (which models a denial-of-service attack on `P[i]` in the real world).

5.  The inputs `pw^i` and outputs `sk[i]` of each `P[i]` are recorded in the ideal-world interaction transcript `transcriptideal[![image](images/a.jpg)^∗, ![image](images/f.jpg)PAKE]`, and ![image](images/a.jpg)^∗ can also add any message to the transcript at any moment, emulating the messages which ![image](images/a.jpg) would receive and send in the real-world protocol.

### The BMP security definition

Given the above rules of the real-world and the ideal world games, the BMP notion of PAKE security is as follows:

**DEFINITION 10.3.** – *We call a PAKE scheme* Π *secure in the BMP model (Boyko et al. 2000) if for all efficient algorithms* ![image](images/a.jpg) *there exists an efficient algorithm* ![image](images/a.jpg)^∗ *such that*

![image](images/p228-1.jpg)

*that is, the real-world game transcript defined by* ![image](images/a.jpg) *and* Π *and the ideal-world game transcript defined by* ![image](images/a.jpg)^∗ *and* ![image](images/f.jpg)`PAKE`, *are computationally indistinguishable.*

Since the proof has to exhibit an algorithm ![image](images/a.jpg)^∗ that works for any ![image](images/a.jpg), a natural construction of ![image](images/a.jpg)^∗ uses ![image](images/a.jpg) as an *oracle*. Since ![image](images/a.jpg) expects to interact with real-world `P[i]`’s running protocol Π, ![image](images/a.jpg)^∗ needs to *simulate* these Π instances to ![image](images/a.jpg), that is, it needs to create messages which are indistinguishable from `P[i]`’s messages in protocol Π. The challenge of the security proof is that ![image](images/a.jpg)^∗ must do so given only the information supplied by ![image](images/f.jpg)`PAKE`, which, for example, does not contain `P[i]`’s inputs `pw`. However, if ![image](images/a.jpg)^∗ succeeds in such simulation, then ![image](images/a.jpg) must reply to these simulated messages as it would in the real-world game (except for negligible probability of distinguishing the simulated messages of ![image](images/a.jpg)^∗ from the real messages of `P[i]`’s), and the ideal-world transcript can be indistinguishable from the real-world transcript if ![image](images/a.jpg)^∗ places in `transcriptideal[![image](images/a.jpg)^∗, ![image](images/f.jpg)PAKE]` all the messages it sends to and receives from oracle ![image](images/a.jpg).
