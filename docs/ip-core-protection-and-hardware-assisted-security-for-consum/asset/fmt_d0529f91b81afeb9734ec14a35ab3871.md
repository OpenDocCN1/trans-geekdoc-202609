
# In the current IC supply chain model

In the current IC supply chain model, multiple parties are involved to handle the increasing design complexity and cost. To avoid establishing and maintaining charge of a foundry with advanced fabrication facility, fabless semiconductor companies export their designed ICs (such as DSP cores) to another company having fabrication facility. Additionally, sometimes system integrator while designing a SoC, imports DSP IP cores from 3PIP vendors to meet the time-to-market requirement ([Castillo *et al.*, 2007](#Chapter8.html#c08_bib4)). Thus, in this globalized business model for DSP cores, different countries and companies have different IP regulation policies and models. Therefore, in this scenario, chip designing process is susceptible to many serious IP security threats such as piracy, overbuilding, counterfeiting, RE, and insertion of hardware Trojan ([Sengupta and Kundu, 2017](#Chapter8.html#c08_bib29); [Sengupta *et al.*, 2018b](#Chapter8.html#c08_bib36); [Wong *et al.*, 2004](#Chapter8.html#c08_bib42); [Alkabani and Koushanfar, 2007](#Chapter8.html#c08_bib1)). This necessitates improvement in the chip-designing process to thwart these threats.

## IP piracy

IP piracy is a process of illegal usage or selling of IP cores. An untrusted foundry, present in the design flow of an IP core, can steal a design, clone it illegally, and then resell it to an other entity. Thus, it can bypass a substantial amount of research and development process, workforce, money, and time invested by an original IP designer. Moreover, he/she can claim the ownership of that IP core ([Koushanfar, 2012](#Chapter8.html#c08_bib16); [Roy and Sengupta, 2017](#Chapter8.html#c08_bib25); [Sengupta and Roy, 2017](#Chapter8.html#c08_bib30); [Sengupta *et al.*, 2018b](#Chapter8.html#c08_bib36)). Similarly, an untrusted foundry may insert malicious logic in the form of hardware Trojan into the design to introduce malfunctioning of DSP IP cores ([Sengupta *et al.*, 2017b](#Chapter8.html#c08_bib34)). Insertion of hardware Trojan can serve many benefits to the adversary based on its type. It can leak crucial information of a DSP IP core used in the defense system, damage the reputation of a well-established company, or degrade the performance of an IP core, etc. According to The Economic Impacts of Counterfeiting and Piracy (2017), the total fiscal revenue loss due to piracy and counterfeiting in 2013 for G20 nations was $96–130 billion which may rise to $199–270 billion in 2022. It is identified that 10% of the globally sold electronics products are counterfeited ([Guajardo *et al.*, 2008](#Chapter8.html#c08_bib12); [Lao and Parhi, 2015](#Chapter8.html#c08_bib17)).

## RE of a DSP/IP core

RE of a DSP/IP core is a process of gaining the complete understanding of its functionality, design, and structure ([Vijayakumar *et al.*, 2017](#Chapter8.html#c08_bib40); [Torrance and James, 2009](#Chapter8.html#c08_bib39); [Sengupta *et al.*, 2017a](#Chapter8.html#c08_bib33)). Therefore, people can use RE process for both honest and fraudulent intentions. People can also use RE as a tool for education, research and development, and analysis and evaluation purpose of an existing product. In many countries, RE with honest intentions is considered as a legal process until it violates any design copyrights and patents issues ([Biggerstaff, 1989](#Chapter8.html#c08_bib3)). However, RE can also be used for dishonest intentions such as overbuilding, piracy, or counterfeiting a DSP/IP core design or inserting a hardware Trojan, which may lead to huge profit for an adversary. Therefore, RE for dishonest intentions incubates or invites these aforementioned potential threats. One popular hardware hardening technique to counteract RE attack for DSP IP core is functional/logic obfuscation. Functional obfuscation (also known as logic encryption) inserts additional logic components known as key-components into the design to hide its functionality and implementation. These additional logic components accept key bits as input and produce the output based on these key values. Therefore, applying correct key combination will produce correct result while applying wrong keys will lead to exhibit an incorrect functionality of the design. Thus functional obfuscation thwarts RE process for fraudulent intentions.

# 8.2 Attack scenarios and threat model

This section discusses the possible attack scenarios and threat model of functional obfuscation.

## 8.2.1 Possible attack scenarios

To generate a locked netlist, key components or key-gates can be inserted anywhere in the circuit. However, incorrect placement of key components may invite several attacks. In this subsection, we discuss about the attacks related to placements of key components as well as other attacks.

1. Isolated key-gates-based key-sensitization attack: A key-gate in an locked netlist is considered as isolated if there is no path between that key-gate and any other key-gates ([Yasin *et al.*, 2016](#Chapter8.html#c08_bib44)). An attacker can easily sensitize the key value of an isolated key-gate. For example in [Figure 8.2(a)](#Chapter8.html#c08_fig2), there is no path between key-gates K1 and K2. Therefore, K1 and K2 are isolated key-gates. An attacker can sensitize the value of K1 as 0 to the output 1 (O1) by applying “100XXX” i/p pattern.

Figure 8.2 (a) Isolated key gates K1 and K2; (b) run of key gates K1 and K2; and (c) concurrently mutable key gates K1 and K2

2. Run of key-gates-based key-sensitization attack: A set of key-gates in an locked netlist is considered as run of key-gates if they are connected in a back-to-back fashion ([Yasin *et al.*, 2016](#Chapter8.html#c08_bib44)). Few run of key-gate structures are vulnerable for locked netlist as it reduces the effort of an attacker to identify the correct key by increasing the possible correct key combinations. The reason is that some run of key-gate structure may be replaceable with a single key-gate, thus, diminishing security strength. For example, in [Figure 8.2(b)](#Chapter8.html#c08_fig2), K1 and K2 are connected back to back, thus forming a run of key-gates. In this case both “01” and “10” are correct key values. Moreover, K1 and K2 can be replaced by a single key-gate (XOR) with “1” as the correct key value.

3. Mutable key-gates-based key-sensitization attack: If two or more key-gates converge but have no common path between them, sensitization may still occur ([Yasin *et al.*, 2016](#Chapter8.html#c08_bib44)). Therefore, if key-gates K1 and K2 converge to another gate so that a specific key-bit can be obtained by muting the other, then both key-gates are called concurrently mutable key-gates. In this type of scenario, an attacker can easily trace the key value of K1 by muting K2. For example, in [Figure 8.2(c)](#Chapter8.html#c08_fig2), K1 and K2 converge at the gate G. The value of K1 can be sensitized to O1 by muting the effect of K2. Applying *I*[6] = 0 in the input pattern will mute K2. Similarly, the value of K2 can be sensitized to O1 by muting the effect of K1. Applying *I*[1] = 1 in the input pattern will mute K1.

4. IP piracy and Trojan attack: If somehow the correct key combination of a locked netlist is identified by an attacker, he/she can easily discover the correct functionality of that netlist. This may enhance the possibility of IP piracy/counterfeit and Trojan insertion attacks. An attacker can either resell/redistribute the IP core illegally to make a profit or can insert a Trojan logic at safe places to introduce malfunctioning of an IP core.
