
# Consumer Electronics and IoT Security

Consumer electronics (CE), embracing high-end devices ranging from digital camera, multi-spectral camera, IP TV, smart tablets, night vision camera to smart meter, accompanied by data and communication know-how makes emerging smart cities and internet-of-things (IoT) a reality. In today’s world of CE and IoT, security, privacy, and protection of hardware and its information are increasingly becoming critically imperative. It is universally accepted that for IoT, security of underneath hardware is pivotal for its correct operation. The underlying hardware is affected by several threat factors. An adversary may generate secret exist that leaks crucial data such as encryption key employed in secure transmission line, the maker could meddle the design by implanting ‘hardware Trojans,’ or inserting artifacts with recognized dependable susceptibilities. Current generation designs and assimilates intellectual property (IP) blocks from manifold vendors, which are mass-produced and verified by diverse companies worldwide. Accordingly, numerous access points exist for any typical hardware and are prone to be attacked. For a trusted hardware design, defense of IP cores is of utmost importance and significance ([Sengupta and Kundu, 2017](#Chapter1.html#c01_bib26); [Sengupta *et al.*, 2018](#Chapter1.html#c01_bib27)).

A typical CE system ([Figure 1.1)](#Chapter1.html#c01_fig1) has digital signal processing (DSP), embedded processor, memory, system software, and application software. Significantly, various forms of attacks can occur to this CE system, i.e.: system security, information security, system privacy, information privacy, network security, firmware security, system trustworthiness, hardware IP rights, and information copyrights. The origins of all these attacks vary and are different, for example, they can be remote or local. They can be either attacked by software or hardware. They can attack either software or hardware components of the CE system. Thus, it is a quite challenging and difficult task for any system design engineer to ensure that the CE system that is being designed is completely full-proof. There is no single solution that can work for (1) overall system for all types of attacks and (2) for all types of hardware (e.g., digital, analog, and radio-frequency components). Thus, the protections from intellectual property rights (IPR) of both the hardware components and the information (including media) that a CE system processes needs different solutions. The chapter corresponding to this section will discuss the details of these attacks and explore the corresponding possible solutions for their mitigation. Moreover, many of these attacks and solutions will be discussed throughout the different chapters of this book. The hardware-assisted security is defined as the ‘security provided by hardware’ for: (1) information being processed, (2) hardware itself, and (3) overall system ([Sengupta *et al.*, 2018](#Chapter1.html#c01_bib27); [Mohanty 2018a](#Chapter1.html#c01_bib10), [2018b](#Chapter1.html#c01_bib14)). The hardware-assisted security solutions may be in different forms such as: (1) additional hardware components used for security, (2) hardware design modification performed, and (3) system design modifications performed ([Mohanty, 2018a](#Chapter1.html#c01_bib10), [2018b](#Chapter1.html#c01_bib14)). Overall, a system can be considered as trustworthy, if it incorporates security, privacy, and IP protection solutions during the design phase while obtaining the components from trusted vendors and trusted manufacturing units.

It is a well-known fact that the CE system is a heterogeneous combination of various types of hardware, software, and firmware and can be conceptualized as analog/mixed-signal system on a chip (AMS-SoC) ([Mohanty, 2015](#Chapter1.html#c01_bib13)). CEs or CE system are essentially AMS-SoCs, and it includes almost everything, e.g., smart watch, smart camera, smart phone, smart car, smart healthcare device, etc. (see [Figure 1.1)](#Chapter1.html#c01_fig1). In the hardware-digital-hardware, analog hardware, RF hardware, and mixed-signal hardware are needed for various signal processing and communications that happens in the CE system. Memory is needed for buffer processing and storage. The software are system software, application software, and middleware. The security vulnerability can arise from any of these components of a typical CE system ([Mohanty, 2018a](#Chapter1.html#c01_bib10), [2018b](#Chapter1.html#c01_bib14)). This section will present a brief overview, and detailed discussions are presented in the corresponding chapters. The following sections discuss about hardware design flow and more specifically at the architecture level.

## 1.2 Hardware-assisted security and IP core protection

Currently, design age of CE devices comprises complex data/control intensive hardware such as DSP cores in the form of IP cores which depend on the integrated circuit (IC) supply chains globally. To enhance the design efficiency and improve the design speed, the use of IP cores for DSP applications in CE devices, normally provided by a third-party vendor, has turned into a typical exercise in the CE industry. Nonetheless, surging threats to security is prevalent and rising piracy concerns make global supply chains vulnerable ([Sengupta, 2015](#Chapter1.html#c01_bib20), [2016](#Chapter1.html#c01_bib19)). [Figure 1.2](#Chapter1.html#c01_fig2) shows the hardware threats in a typical system-on-chip design cycle comprising third-party IP (3PIP) cores. The first location is during the process of importing 3PIP cores from outside vendors and second location is at the foundry where copying of design netlist is performed. Thus, security is mandatory in these two locations. Furthermore, [Figure 1.3](#Chapter1.html#c01_fig3) shows the various elements in a chip design cycle which are trustworthy and untrustworthy by nature. Other forms of hardware threats such as infringement of IP core ownership, IP core buyer ownership, etc., are also possible which will be discussed in the latter half of this chapter and other chapters.
