
# (1) Key-sensitization attack

In this attack, the attacker tries to determine/sensitize the correct key value by applying multiple input patterns. Key-sensitization attack will be easy for an attacker if key-gates are isolated, not pairwise secured, mutable, and connected in a back-to-back fashion. An attacker can apply a particular input pattern on the functional IC brought from the market and observe its corresponding, then apply the same input in the locked netlist with different key values to determine the correct one. Therefore, to prevent the key-sensitization attack placement of key-component is very important. Key-gates should be placed in a locked netlist in such a fashion that there is a dependency between key-gates. This ensures “prohibition of key isolation” and “multi pair-wise security” features (discussed in Section 8.2).

Multiple key-gates should not be connected in such a fashion that it can be replaceable using a single key-gate, which increases the number of valid keys in the key-space. This ensures “prohibition of run of key-gates.” Additionally, sensitization attack can also be performed if key-gates can be muted (discussed in Section 8.2.1). The ILBs are designed in such a way (with intertwining among gate structures for eight key inputs) that key-gates are multi pair-wise secure, no isolated key-gates are available in an ILB, no key-gates can be muted and enhances attack complexity to determine and replace run of key-gates using a single key. Thus, Sengupta *et al.*’s ([2018](#Chapter8.html#c08_bib35)) approach provides resilience against key-sensitization attacks.

# (2) IP piracy and Trojan attack

The ILB-based functional obfuscation methodology hinders an attacker’s effort (as key-gates structures are heavily intertwined among themselves for 8-bit key inputs) to detect the correct key through RE. Only a valid combination of key-value can actuate the locked netlist.

# (3) SAT attack

SAT solver is not scalable for multiplier circuit ([Subramanyan *et al.*, 2015](#Chapter8.html#c08_bib37); [Finke, 2015](#Chapter8.html#c08_bib11); [Chakraborty *et al.*, 2017](#Chapter8.html#c08_bib6)). Even for a small-size 3-bit multiplier, the equivalent CNF has 20 clauses ([Finke, 2015](#Chapter8.html#c08_bib11)). Generally, a DSP core comprises several large bit-size multipliers as an integral part. Therefore, DSP IP core designs are SAT-attack-resistant. However, authors in Sengupta *et al.* ([2018](#Chapter8.html#c08_bib35)) provide a proactive countermeasure (assuming efficient SAT attacks may be formulated for DSP cores in future), solution motivated from Yasin *et al.* ([2016](#Chapter8.html#c08_bib44)), where the subset of the key-bits are encrypted through a custom lightweight. *AES block (not public design)* with fixed secret key. Based on the encrypted key-bits, subset of ILBs are designed and inserted in the obfuscated netlist. This prevents an attacker from determining the correct key value if he/she does not have the key of AES block (shown in [Figure 8.7](#Chapter8.html#c08_fig7)). Sengupta *et al.* ([2018](#Chapter8.html#c08_bib35)) designed their own *custom lightweight AES architecture* comprising 429 logic elements. This AES block utilizes <1% of final design logic elements while implementation using Altera Quartus ([2018](#Chapter8.html#c08_bib23)) 13.0 version in [Cyclone II FPGA (2018)](#Chapter8.html#c08_bib7) after integration with the obfuscated netlist of the DSP core. Top-level design of custom AES block-integrated obfuscated 4-bit FIR and its corresponding gate structure implemented in Altera Quartus are shown in [Figures 8.8](#Chapter8.html#c08_fig8) and [8.9](#Chapter8.html#c08_fig9), respectively. A partially extracted portion of AES-integrated obfuscated netlist file is shown in [Figure 8.10](#Chapter8.html#c08_fig10), which demonstrates that individual logic components are indistinguishable. The simulation result of the FO FIR design is shown in [Figure 8.11](#Chapter8.html#c08_fig11). Some examples of lightweight AES architectures available in the literature are [Hamalainen *et al.* (2006)](#Chapter8.html#c08_bib13) and [Morioka and Satoh (2002](#Chapter8.html#c08_bib20)). Post-synthesis result for FIR DSP core after integrating custom AES block is shown in [Table 8.1](#Chapter8.html#c08_tbl1). It is computationally infeasible to determine the inputs of AES from its output when the key is unknown. To prevent SAT attack, following steps are performed:

* (i) Designer synthesizes an AES block with a fixed secret key.
* (ii) Subsets of keys of functional obfuscation are encrypted through the AES block.
* (iii) The outputs of the AES block (encrypted keys) are connected to few ILBs in the locked netlist depending on the number of keys are encrypted through AES.
* (iv) Based on the fixed secret key of the AES block and the input to AES, a designer can identify the output of AES and configures the ILBs accordingly by re-organizing the internal gate structure of ILB. (Note: The internal reorganization of the gate within ILB does not add any extra gate but only changes its configuration and connectivity.)
