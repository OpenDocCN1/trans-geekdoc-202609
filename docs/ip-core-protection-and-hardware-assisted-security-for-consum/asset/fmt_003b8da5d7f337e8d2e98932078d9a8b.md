
Another technique that targets protection of IP core(s) is hardware obfuscation. Obfuscation targets protection against IP piracy and Trojan insertion ([Yasin *et al.*, 2016](#Chapter6.html#c06_bib37)). It aims to obfuscate a design through either structural ([Sengupta *et al.*, 2017](#Chapter6.html#c06_bib34); [Li and Zhou, 2013](#Chapter6.html#c06_bib15)) or functional obfuscation ([Lao and Parhi, 2014](#Chapter6.html#c06_bib14)). The primary aim is to increase the efforts of an attacker to identify correct functionality of an IP ([Yasin *et al.*, 2016](#Chapter6.html#c06_bib37)), thus making it hard for an attacker to secretly insert Trojan that can go undetectable during testing phase of an IC design. Further, this also makes it difficult to resell or utilize an IP core because its correct functionality is unknown to an adversary. Obfuscation does not aim to provide protection against ownership conflict (since it does not insert a unique ID or signature). However, functional obfuscation can be used to protect against reverse engineering of an IP core. Functional obfuscation implements a locking technique that can be used to safeguard an IP core against reverse engineering of its netlist. However, an adversary can reverse engineer an IP core, identify the correct key through various attacks, and misuse the IP core.

Yet another technique named “IP metering” aims to provide protection against IP piracy and IP overbuilding. This methodology seeks to distinguish one IP from another made through same fabrication process ([Koushanfar and Qu, 2001](#Chapter6.html#c06_bib11)). Therefore, when the IP core passes through untrustworthy design phases ([Yasin *et al.*, 2016](#Chapter6.html#c06_bib37)) of a generic IC design flow, those which are pirated or not reported by the foundry (overbuild) can be detected. Since each IC contains a unique ID, they can detect piracy or overbuilding whenever required.

Another mechanism that primarily aims to provide protection against false claim of ownership is watermarking (Sengupta *et al.*, [2016](#Chapter6.html#c06_bib22), [2018](#Chapter6.html#c06_bib32); [Sengupta and Bhadauria, 2016](#Chapter6.html#c06_bib24)). Watermarking embeds a signature in an IP during design phases and detects it to resolve false claim of ownership (see Chapter 3). However, it is vulnerable to reverse engineering-based attacks such as signature tampering. Further, signature insertion may incur hardware overhead ([Sengupta *et al.*, 2018](#Chapter6.html#c06_bib32); [Sengupta and Roy, 2017](#Chapter6.html#c06_bib28)). To overcome some of the limitations of hardware watermarking, another alternative method suggested is computational forensics engineering-based IP core protection that can resolve ownership conflicts with 0% design overhead and no chances of signature tampering.

## 6.1.1 Overview of forensic engineering

FE has always been an impactful technique for resolving conflicts during criminal cases. Although it has been used intensively in fields such as image tampering and failure analysis, there has been little to no effort made in the literature to utilize such an impactful technique for intellectual property core protection. A good description of computational forensics can be found in Franke and Srihari ([2008](#Chapter6.html#c06_bib4)). A generic computational forensic engineering problem can be formulated as follows: given a solution S to a problem *P*, having a finite set of algorithms/tools A\_n (*n* = 1, …, *I*), applicable to problem P that can produce solution *S*, CFE targets automated identification with a very high degree of confidence that the algorithm/tool A\_i has been applied, to produce solution *S*. The approaches that utilize FE for IP protection are Kachave and Sengupta ([2016](#Chapter6.html#c06_bib9)), [Sengupta and Kachave (2018),](#Chapter6.html#c06_bib26) and Wong *et al.* ([2004](#Chapter6.html#c06_bib36)). However, method presented by Wong *et al.* ([2004](#Chapter6.html#c06_bib36)) requires multiple instances of an IP core (obtained through distinct implementation of an algorithm) for providing IP protection, which is not always feasible in real-world scenarios. Further, the technique (“feature-set”) presented in that approach is limited/only applicable to graph coloring and Boolean satisfiability. Additionally, the approach presented in Wong *et al.* ([2004](#Chapter6.html#c06_bib36)) is not applicable to DSP IP core.

A generic CFE approach comprises four steps, namely feature and statistical data collection, feature extraction, entity clustering, and validation (as shown in [Figure 6.2](#Chapter6.html#c06_fig2)). The purpose of these steps is explained as follows:

*   Feature and statistical data collection: In this step, the goal is to observe the solution(s) to problem *P* obtained by algorithm A\_*i* (*i* = 1, …, *n*) and deciding various features that could help in distinguishing one IP core solution from another. These unique features are typically processed through some statistical techniques. Therefore, this step is termed as feature and statistical data collection.

*   Feature extraction: Once the features are decided, one IP core solution from another solution can be distinguished, the next aim is to extract all these features from each IP core solution through some feature extraction rules.

*   Entity clustering: In this step, our aim is to divide “s” number of solutions into “k” number of clusters such that each cluster contains solutions that are closely matched. Through this step, the aim is to reduce complexity of problem. Thus, instead of considering “s” solutions separately, it is grouped based on the similarities, and then “k” groups are considered instead of “s” solutions. Further, a generic assumption is that solutions produced through different implementations of same algorithm A\_*i* will have closely matched features. Thus, a cluster should contain solutions generated from different implementations of same algorithm.

*   Validation: In this step, the features of IP core solution “S” obtained through algorithm A\_*i* is matched with the features of the IP core under test (see problem statement).
