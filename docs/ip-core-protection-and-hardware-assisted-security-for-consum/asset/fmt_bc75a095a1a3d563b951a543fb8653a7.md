*Chaining*: As explained in [Sengupta and Kachave (2018)](#Chapter6.html#c06_bib26) and Kachave and Sengupta ([2017](#Chapter6.html#c06_bib10)), the flow diagram of algorithm devised to detect the presence of chaining feature is shown in [Figure 6.8](#Chapter6.html#c06_fig8). The feature extraction algorithm accepts controller HDL of an IP core as input and produces output as whether chaining feature is detected or not. Detection of chaining is ascertained as follows: if during execution time of `i`th FU, multiple (“m”) instances of `j`th FU are executed then chaining feature is present in an IP core design. The algorithm is executed for `i` = 1–`n`, where “`n`” is the total number of FUs present in a particular IP core. The second “if” statement (in [Figure 6.8](#Chapter6.html#c06_fig8)) ensures that algorithm runs for all `j`th FU, other than the `i`th FU. Subsequently, the third “if” statement allows only those instances of `j`th FU to be compared with `i`th FU that started (represented as `CS[S](FU[i] ≤ CS[S](FU[j])`) and ended (represented as `CS[E](FU[i] ≥ CS[E](FU[j])`) between a single instance of `i`th FU, where `CS[S](FU[i])` and `CS[S](FU[j])` represent starting control step of `i`th and `j`th FU, respectively. Similarly, `CS[E](FU[i])` and `CS[E](FU[j])` symbolize ending control step of `i`th and `j`th FU, respectively. Finally, the last “if” statement checks whether during execution time (`CS[E](FU[i]) – CS[S](FU[i])`) of FU of `i`th type, multiple instances of FU of `j`th type are executed or not. Thus, if the last `if` condition is satisfied, then chaining feature is detected in a DSP IP core. [Figure 6.9](#Chapter6.html#c06_fig9) shows the partial HDL code of controller of an IP core. As shown in controller’s HDL, the multiplier FU is enabled in control step 1 represented by statement `MUL_En_1<= “1”`. Adder FU is enabled in the first CS and disabled in the second CS. Further, second instance of Adder FU is activated in third CS and deactivated in fourth CS. Last, multiplier FU execution continues until it is disabled in CS = 40. Thus, during execution of single multiplier FU, multiple instances of adder FU are executed. This indicates that chaining feature is present in this IP core design.

1. *Multicycling*: To detect multicycling feature in an IP core, the feature extraction rule reads the controller HDL code of the respective IP core. It checks to detect if the execution time of any FU consumes more than one CS. If the condition is true then it is inferred that multicycling feature is present in that IP core design. The condition to detect the presence of multicycling in the controller HDL code of an IP core is given as: `CS[E](FU[i]) > CS[S](FU[i])`, where `CS[S](FU[i])` and `CS[E](FU[i])` represent starting and ending control steps of `i`th FU, respectively.

3. *Design objective*: A generic HLS tool used to design an IP core typically has at least one design objective. The design objectives are typically optimization based on power-delay trade-off or area-delay tradeoff, etc. Based on the design objectives supported, one tool used for IP core creation can be distinguished from another. The feature extraction algorithm for extracting design objective feature takes user interface (graphical or nongraphical) of executable version of HLS tool as input. Subsequently, the extraction algorithm reads the interface and determines the design objectives available for selection in a tool’s user interface. Subsequently, the interface’s design objectives are matched and validated with the design objective details mentioned in the datasheet of the IP core under test.

4. *Reliability*: Reliability can take multiple forms such as reliability (detectability/security) against transient fault, reliability (detectability/security) against permanent faults ([Inoue *et al.*, 2011](#Chapter6.html#c06_bib7); [Nomura *et al.*, 2011](#Chapter6.html#c06_bib19)). A typical approach that aims to design a reliable system utilizes modular redundancy ([Inoue *et al.*, 2011](#Chapter6.html#c06_bib7); [Yu and McCluskey, 2001](#Chapter6.html#c06_bib38); [D’Angelo *et al.*, 1999](#Chapter6.html#c06_bib2)). Redundancy may be dual modular redundancy (DMR), triple modular redundancy, or multimodular redundancy. However, so far in the literature, such as Inoue *et al.* ([2011](#Chapter6.html#c06_bib7)), DSP IP core vendors have only implemented reliability against transient fault using DMR. Therefore, feature extraction rule is discussed only for this feature. The rule aims to detect the presence of DMR logic in DSP IP core design.

Reliability feature extraction process accepts datapath HDL of an IP core as input and aims to detect the presence of a DMR system. As shown in [Figure 6.12](#Chapter6.html#c06_fig12), in a typical DMR system, the outputs of each module of a DMR system are compared using a comparator component to determine whether the fault is detected or not. This comparator component accepts one input from output register of the first module (original) and another from the second module (duplicate). If a port mapping similar to following port map statement in HDL: `port map (output register signal 1, output register signal 2, comparator output signal)` is detected, the reliability feature is present in the respective IP core.
