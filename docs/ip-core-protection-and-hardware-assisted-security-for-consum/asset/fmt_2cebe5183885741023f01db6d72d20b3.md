
## Multi pair-wise security

All key-bits in a locked netlist are considered as multi pair-wise secure if an attacker cannot sensitize anyone of them to the output data bit without controlling or knowing the remaining all other key-bit values ([Yasin *et al.*, 2016](#Chapter8.html#c08_bib44)). In a locked netlist, key-bits are inaccessible to an attacker, therefore, he/she cannot feed input to it. Thus, in multi pair-wise secure key-bits, identifying one key value of a key-bit depends on the key value of all remaining key-bits, therefore an attacker cannot crack any key value of the locked design. Different sample ILB structures of Sengupta *et al.* ([2018](#Chapter8.html#c08_bib35)) are shown in [Figure 8.5](#Chapter8.html#c08_fig5). According to [Figure 8.5](#Chapter8.html#c08_fig5), all the ILBs have 8 key-bits and all are multi pair-wise secure. In other words, to sensitize any key-bit of an ILB to the output, an attacker has to know or control the correct value of other seven key-bits. Therefore, to identify the correct value of other seven key-bits, an attacker has to apply brute-force attack. For example, to sensitize key-bit `K1` of the ILB shown in [Figure 8.5(a)](#Chapter8.html#c08_fig5) to the output bit, an attacker has to control the other seven key-bits’ value, i.e., “0110000” which is challenging. Thus, multi pair-wise security feature enhances key-sensitization attack for the ILBs.

## Prohibiting key-gate isolation

To avoid key-sensitization attack, a locked netlist design should be prohibited from isolated key-gate. Different ILBs structures (shown in [Figure 8.5](#Chapter8.html#c08_fig5)) designed in Sengupta *et al.* ([2018](#Chapter8.html#c08_bib35)) consist of eight intertwined key-gates dependent on each other. This ensures no isolated key-gate is present in the ILBs. Thus, prohibiting isolated key-gate from the locked netlist enhances key-sensitization attack for the ILBs.

## Protection against run of key-gates

In Sengupta *et al.* ([2018](#Chapter8.html#c08_bib35)), the key-gates of ILBs are interlaced among each other, therefore, replacing all key-gates (eight input key-gates) with a single one is highly difficult.

## Nonmutable convergent key-gates

If two key-gates converge at some other gate in such a way that none of the key-bits can be muted, we can call these key-gates as nonmutable convergent key-gates ([Yasin *et al.*, 2016](#Chapter8.html#c08_bib44)). As in Sengupta *et al.* ([2018](#Chapter8.html#c08_bib35)), all the ILBs consist of eight nonmutable key-bits, therefore, to sensitize one key-bit to the output remaining seven key-bits need to be muted, which is a complicated process. Thus, nonmutable key-gate placement in the locked netlist enhances key-sensitization attack for the ILBs.

Post HLS, after obtaining gate-level datapath structures, ILBs are inserted in each output data bit of functional unit based on the “μ” value to generate a locked netlist. In this process, same ILB is inserted “μ” times into the design and then after “μ” repetition next ILB from `T[ILB]` is selected. For instance, a gate-level structure of FIR benchmark ([Mohanty, 2015](#Chapter8.html#c08_bib19)), designed using 1 adder and 1 multiplier, is functionally obfuscated through “μ” = 2. Insertion of ILBs in the design can be performed randomly also to lock the design, but according to Sengupta *et al.* ([2018](#Chapter8.html#c08_bib35)), this may incur huge power and cost overhead with compromised security. On the contrary, in this approach different “μ” values are explored through power-delay trade-off, thus optimizing the overheads. Additionally, no output data bit remains unobfuscated (unlocked) in this approach, thus ensuring strong security.

### 8.5.2 Security analysis

In the security analysis of the locked netlist, it is assumed that an attacker has access to following three things:

* (i) A FO netlist
* (ii) Activated functional circuit (brought from the market)
* (iii) Advance RE facility

In this scenario, through RE, an attacker can determine the total number of input key bits, he/she then searches in the key-space to identify the combination of key values. For instance, as shown in [Figure 8.6](#Chapter8.html#c08_fig6), an attacker can determine that the design contains 64 numbers of input key-bits. He/she can perform brute force attack to identify a correct combination of 64 key values, which require testing of total 2^(64) different combinations. During brute force attack, if we assume that 1 billion (10⁹) keys can be applied per second to the locked netlist, it will take approximately 585 years to identify the correct key value.
