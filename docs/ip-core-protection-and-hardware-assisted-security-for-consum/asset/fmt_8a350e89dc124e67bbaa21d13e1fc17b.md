
# A seven variables signature encoding scheme

A seven variables signature encoding scheme is devised in Sengupta *et al.* ([2018](#Chapter4.html#c04_bib22)) where each variable embeds decoded watermarking constraint in any of the three phases (scheduling, hardware allocation, and register allocation) of synthesis process. More specifically, each decoded signature digit inserts a watermarking constraint by modifying any of the aforementioned tables. An IP owner can select his desired signature using any random combination of these seven variables, i.e., ‘`α`’, ‘`β`’, ‘`γ`’, ‘`i`’, ‘`I`’, ‘`T`’ and ‘`!`’. The encoded rule of each variable is as follows:

*   ‘`γ`’ = Move/shift a non-critical path’s operation with the highest mobility into immediate next control step (`cs`).

*   ‘`α`’ = *In odd control steps only*: Even operation must be allocated to the hardware of vendor type 2 (`U2`) and odd operation must be allocated to the hardware of vendor type 1 (`U1`).

*   ‘`β`’ = *In even control steps only*: Even operation must be allocated to the hardware of vendor type 1 (`U1`) and odd operation must be allocated to the hardware of vendor type 2 (`U2`).

*   ‘`i`’ = Add an additional edge between (`prime`, `prime`) node pair of CIG.

*   ‘`I`’ = Add an additional edge between (`even`, `even`) node pair of CIG.

*   ‘`T`’ = Add an additional edge between (`odd`, `even`) node pair of CIG.

*   ‘`!`’ = Add an additional edge between (`0`, any integer) node pair of CIG.

In Sengupta *et al.* ([2018](#Chapter4.html#c04_bib22)), 3rd phase watermarking variables, i.e., ‘`i`’, ‘`I`’, ‘`T`’ and ‘`!`’ are independent of both 1st phase watermarking variable, i.e., ‘`γ`’ and 2nd phase watermarking variables, i.e., ‘`α`’ and ‘`β`’. Similarly, watermarking variable of 1st phase is independent of both watermarking variables of 2nd and 3rd phase. These advantages make the triple-phase watermarking approach exceptionally robust and tamper tolerant for an adversary. However, watermarking variable of 2nd phase is dependent on watermarking variables of 1st phase. Therefore, watermarking constraints of 2nd phase may be affected due to alteration of 1st phase watermark which is a limitation of this approach. Nevertheless, as mentioned earlier, it is tremendously tough for an adversary to detect in which step of synthesis, the 1st phase watermark is implanted, and how. Moreover, if 1st phase watermark is tampered somehow by an attacker, then still 3rd phase watermarking constraints (which is independent of 1st- and 2nd-phase watermark) are capable of resolving the ownership conflict and identifying the real IP core owner. Thus, triple-phase watermark provides a strong tamper tolerant watermarked IP core design.

## 4.3.3.2 Watermark embedding process

In the previous sub-section, we have discussed encoding rule of seven variables of the triple-phase watermark. In this sub-section, we will discuss about how to embed a triple-phase watermark in a non-watermarked IP design. The triple-phase watermark embedding process is divided into four parts, i.e., pre-processing steps, 1st phase watermark embedding steps, 2nd phase watermark embedding steps, and 3rd phase watermark embedding steps. Detailed steps of this watermarking process are as follows ([Sengupta *et al.*, 2018](#Chapter4.html#c04_bib22)):

### A. Pre-processing steps

1. Accept a non-watermarked DSP application as CDFG and schedule it based on user resource configuration.

2. Perform functional unit allocation and register allocation.

3. Construct the timing table for ‘non-critical operations (`μ`[`m`] > 0),’ ‘functional unit allocation’ table, and ‘register allocation’ table from the non-watermarked IP core design.

4. Sort the operations control stepwise based on their number in increasing order.

5. Accept an `n`-digit vendor’s signature as a combination of ‘`α`’, ‘`β`’, ‘`γ`’, ‘`i`’, ‘`I`’, ‘`T`’ and ‘`!`’ variables.

### B. 1st phase watermark embedding steps

1. For each occurrence of ‘`γ`’, shift an operation of the non-critical path into its very next control step while checking from control step 1 onward (without re-occurrence), if both of the following conditions satisfied:

    * (`i`) Respective operation does not have any child operation in very next control step.

    * (`ii`) Shifting does not violate the hardware resource constraints.

        (*Note: In case more than one operation is eligible to be shifted in the next control step, the operation with the highest mobility will be given the priority*).

2. Adjust the timing table of ‘non-critical operations (`μ`[`m`] > 0)’ after embedding all ‘`γ`’ variables.

### C. 2nd phase watermark embedding steps

1. Accept the 1st phase watermark embedded scheduled design as input to embed 2nd phase watermark.

2. For each occurrence of ‘`α`’ and/or ‘`β`’ variable in the vendor’s signature, re-allocation of functional unit needs to be performed according to the encoding rule of ‘`α`’ and ‘`β`’.

3. Modify the ‘functional unit allocation’ table after embedding all ‘`α`’ and ‘`β`’ variables.

### D. 3rd phase watermark embedding steps

1. Accept the dual phase (1st and 2nd phase) watermark embedded design as input to embed 3rd phase watermark.

2. Rest of the steps is similar to single-phase watermark embedding steps B.1–B.4 (refer Section 4.3.B).

## 4.3.3.3 Signature detection process

The signature detection process is a crucial and compulsory step to resolve ownership conflict. The inputs required to detect triple-phase watermark are: (a) decoded vendor signature, (b) application, and (c) watermarked IP core in the form of controller and datapath HDL. The triple-phase watermark can be achieved in three steps and each step verifies the presence of watermarking constraints of each phase. In the signature detection and verification process of phase 1 watermark, the control steps of modified operations are extracted from the decoded signature which is then compared with the controller HDL of the watermarked IP. To detect and verify the phase 2 watermark, the allocated hardware of the watermarked operations are extracted from the decoded signature which is then identified with the help of original application and its corresponding inputs. Then, the watermarked hardware information fetched from the decoded watermark is compared with the datapath HDL of the watermarked IP. Similarly, to detect and verify the phase 3 watermark, the shared inputs of each multiplexer should be fetched from the datapath HDL of the watermarked IP. It is then compared with the 3rd phase watermarking constraints extracted from the decoded signature. If all the constraints of decode signature are available in the watermarked IP core then the vendor who provided the decoded signature is awarded as the original owner of that IP core.
