
The destination then uses the public key and verifies if the code sent to it is authentic or is tampered with. The hash value must match with the hash generated by the embedded module. If they are not matching, then the software would have been tampered, and thus, cannot be used in the system. This method does not use any power intensive mechanisms to encrypt and decrypt the entire software which uses more power and performance from the embedded system. The initially generated hash of the software image is generated in a secure offline environment which can prove very limited chances of attacks from a remote location. Access to the original software is restricted before generating the hash. All systems can be provided with a public key which can be used to authenticate the software and RSA key. This also does not demand much processing power from the embedded system.

### 2.9 Blockchain technology

Transactions have been around for a very long time. Especially, financial transactions and banks have been around making it easier to transfer funds between accounts. With the advent of internet, online transactions have increased lately. Huge number of financial transactions is happening in the internet for online shopping, transfer funds between accounts and overseas. An intermediary or bank is given the responsibility of transferring the funds securely from the sender to the receiver. These are accurate, responsible, legitimate, and secure. But there are questions rising lately:

*   What happens when the trusted party goes rogue?
*   When an attacker steals all the data, and who is held responsible?
*   There is a delay between sender to intermediary and to the receiver.
*   Can the intermediary be trusted for authenticity?

As an answer to all these questions, the blockchain technology was introduced by Satoshi Nakamoto with Bitcoin ([Barber *et al.*, 2012](#Chapter2.html#c02_bib9); Bitcoin, 2008). It uses an open ledger or shared distributed ledger that contains the records of every transaction that occurred. There is no presence of intermediary in this scenario. This section discusses the Blockchain, its applications, and issues in implementations of blockchain.

#### 2.9.1 Blockchain – overview

Blockchain is the concept of shared ledger where all the participants or users will have a copy of the ledger which contains all the transactions that occurred till date. There is no trusted intermediary in this case which eliminates all the questions that raised. A public key infrastructure is implemented in the case of Bitcoin which is used for the authentication of the users and control the access. Every owner will sign and authenticate the transaction with his private key. A ‘block’ contains multiple transactions that happened along with its hash and is time stamped. For a transaction to be approved, majority of the users or nodes has to agree to the consensus. Miners are responsible to calculate the hash value of the block according to the consensus algorithm. The hash computed will be less than a threshold that was previously agreed to avoid any issues among the users. The value is set such that the miners will be able to calculate it in a less period of time, in this case, 10 min ([Li *et al.*, 2017](#Chapter2.html#c02_bib49)). There are various applications to the blockchain. Mainly, the security it offers makes it suitable to be implemented in different domains. #### 2.9.3 Blockchain as a security framework

The consensus is a distributed and decentralized network where the user is the only entity that can determine the future updates of the state can occur. In the blockchain, practical byzantine fault tolerance algorithm (PBFT) is responsible for establishing the consensus among different users or nodes. Each of the user will maintain a state which when receive a new message, is fed with the message data that is necessary for computing the value and reach a decision. Once a decision is reached, it is broadcasted to the network and when majority of the decisions match it leads to the next consensus.
