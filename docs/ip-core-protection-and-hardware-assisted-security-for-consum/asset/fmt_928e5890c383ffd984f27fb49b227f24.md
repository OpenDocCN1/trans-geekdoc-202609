
As discussed earlier, owing to several reasons, the HLS framework has become integral in efficient DSP IP core design processes. There are multiple successful academic and commercial HLS tools available for designing DSP IP cores. Generally, these HLS frameworks shave some pre-defined modules or blocks available in their library. These pre-defined modules or blocks are also known as micro IPs. While designing a complete DSP IP core, the DSP IP designer directly uses these micro IPs to increase reusability and reduce design effort. If HLS tool vendor imports these micro IPs from another vendor who is non-trustworthy, then in such a scenario, these IP cores could be vulnerable to hardware Trojan. Thus there is no guaranteeing that a 3PIP core in an HLS library will be 100% Trojan-free.

Let us assume there is a BCD adder IP available in the module library of an HLS framework as a black box. It contains three inputs and one output: (i) the enable signal (`En`) which switches on/off the execution of the adder, (ii) the first primary input `A` of bit width 4 (`A[3]A[2]A[1] A[0]`), (iii) the second primary input `B` of bit width 4 (`B[3]B[2]B[1] B[0]`), and (d) one output `O` of bit width 4 (`O[3]O[2]O[1] O[0]`). In a general scenario, during functional/simulation verification and test, the `En` signal is set (`En = 1`) to start the execution of the BCD adder IP. Once the verification process is completed, the `En` signal is reset (`En = 0`) to stop the execution of the BCD adder IP. Now, let us consider a BCD adder that is designed as shown in [Figure 3.10](#Chapter3.html#c03_fig10). In this case, the BCD adder IP would behave correctly during its verification process as the design verifier will set the `En` signal “ON” during functional simulation. He/she may falsely believe that the `En` signal truly starts and stops the execution of the IP. However, an adversary could design an IP in such a way that the Trojan will be triggered when the `En` signal is reset. Therefore, whenever the system designer/integrator resets the `En` signal, it may maliciously generate the wrong output thereby impacting the output of the DSP IP core design. Moreover, other than the aforementioned case, triggering of the Trojan can also be achieved through the finite state machine (`FSM`) counter, external antenna, and so on. Moreover, there is no golden IP (i.e., with a guarantee that it is100% Trojan-free) available in the open market; thus detecting this type of Trojan is difficult during lower abstraction level. There are several other reasons as well, which are discussed in the following.

## 3.3.2 Trojan detectability in a 3PIP module at RTL/lower levels

Detection of hardware Trojan logic which corrupts the functional output of a 3PIP module is difficult during RTL validation or lower design abstraction level verification/tests for the following reasons:

1. A Trojan logic-infected 3PIP produces functionally correct output in normal condition, that is, until the Trojan logic is triggered.

2. The Trojan logic is triggered under very rare and specific time/condition (discussed earlier), therefore identifying such a condition or event is difficult during functional verification ([Tehranipoor and Koushanfar, 2010](#Chapter3.html#c03_bib32)).

3. During functional verification, in most cases, only the functionality of the entire SoC is verified; each and every IP/module used (imported) in the system (after system integration) is not checked.

4. Normally, the Trojan logic is set in an IP in such a way that it remains dormant during functional verification and triggered when the complete SoC is deployed in a real-time situation.

5. As there is no trustworthy golden IP (i.e., guarantee of a 100% Trojan-free IP) model available, the evasion of detection of hardware Trojan in a 3PIP during HLS design for DSP core is possible.

6. Physical inspection and reverse engineering, a very costly and complex procedure, does not guarantee the detection of such Trojans.

7. The testing process to detect manufacturing faults (i.e., bridging faults, delay faults, stuck-at faults, etc.) also does not guarantee the detection of such Trojans.

8. Due to evolution in technology, the physical feature size of a 3PIP decreases. The analysis of parametric signals to detect such Trojans is not considered very effective ([Tehranipoor and Koushanfar, 2010](#Chapter3.html#c03_bib32)).

## 3.4 Selected Trojan security approaches

In this section, we discuss Trojan security approaches for DSP IP cores and few selected Trojan security approaches for other hardware types such as combinational/sequential circuits. We first view multiple Trojan detection approaches for DSP cores and next, we discuss selected Trojan detection approaches for combinational/sequential circuits.

### 3.4.1 Trojan security approaches for DSP cores

The Trojan detection approaches for DSP cores discussed in the following is based on the threat model where hardware the Trojan is capable of producing functional (computational) changes in the DSP core output. In other words, the Trojan payload considered for these approaches is one that causes functional (computational) changes in the DSP core output.

#### 3.4.1.1 Trojan security approach—Rajendran et al. ([2013)](#Chapter3.html#c03_bib17) and Liu et al. ([2014](#Chapter3.html#c03_bib12))

Rajendran et al. ([2013](#Chapter3.html#c03_bib17)) and Liu et al. ([2014](#Chapter3.html#c03_bib12)) have devised duplication-based concurrent error detection (`CED`) techniques to achieve a Trojan secured design through HLS. The hardware Trojan that is available in a 3PIP core and affects its output or denies service is handled in this approach. In the duplication-based `CED` technique, replication of the same design is performed and both the designs are fed with the same set of inputs. The incorrect/dissimilar outputs due to activation of Trojan logic can be identified by comparing their outputs. However, generally an untrusted third party vendor makes a single Trojan infected IP core design and then exports multiple copies of it to the system integrator/SoC designer. Therefore, normal replication of the design cannot detect the Trojan (as both the designs will produce the same malicious outputs). In Rajendran et al. ([2013](#Chapter3.html#c03_bib17)), the source of the 3PIP core is diversified in such a way so that the same operation of both the design uses 3PIP cores coming from different sources. This process not only detects the malicious output of a 3PIP core caused by a hardware Trojan but also can prevent the activation of the Trojan by preventing collusion. Two types of collusion are prevented in this approach, that is, parent-child collusion and parent-parent collusion. The binding rules to prevent collusion are as follows:

* A parent operation and its child operations in a design must be bound to the 3PIPs of different 3PIP vendors.

* At least one of the parent operations of a child operation in a design must be bound to a 3PIP from a different 3PIP vendor.

The generic overview of this approach is shown in [Figure 3.11](#Chapter3.html#c03_fig11). Although this approach is capable of achieving Trojan detection and collusion prevention, it may incur some design overheads as no low-cost design architecture is explored during the scheduling phase of HLS. Moreover, distinctness during 3PIP vendor allocation can be achieved in multiple ways which have a direct impact on the overall design cost. In this approach, no optimal vendor allocation is explored to minimize the overall design security cost. Further, this approach does not handle loop-based control data flow graph digital signal processing (`CDFG DSP`) applications.
