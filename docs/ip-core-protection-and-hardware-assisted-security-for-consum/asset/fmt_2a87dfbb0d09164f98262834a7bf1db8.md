
# One-way random functions (ORF) circuit based countermeasure against SAT based attack

One-way random functions (ORF) circuit based countermeasure against SAT based attack is shown in [Figure 8.3(b)](#Chapter8.html#c08_fig3) ([Yasin *et al.*, 2016](#Chapter8.html#c08_bib44)). In this approach, a public AES has been used as ORF to defend SAT attack instead of PUF because PUF has following drawbacks: (1) it cannot add a significant number of clauses as it has a small circuit; and (2) it is susceptible to modeling attacks ([Pappu *et al.*, 2002](#Chapter8.html#c08_bib22)). Removal attack on AES is handled by synthesizing the public AES along with the locked netlist, such that it changes the complete structure of the public AES. Therefore, it becomes difficult for an attacker to identify the AES block separately from the locked design.

Lee and Touba ([2015](#Chapter8.html#c08_bib18)) proposed key-components as a combination of XOR/XNOR gates and multiplexers to enhance the HD between incorrect and correct output. Baumgarten *et al.* ([2010](#Chapter8.html#c08_bib2)) used LUT as key-component to achieve the locked design. In this functional obfuscation approach, the complete design is subdivided into multiple fixed and reconfigurable parts, and then the LUTs are only used to implement reconfigurable parts. After fabrication, once the design is returned from the foundry, these key-controlled LUTs are changed to a different logic. Thus, misuse of a design by an untrusted foundry can be prevented.

Functional obfuscation is vulnerable to many attacks, such as key-component removal attack, key-sensitization attack ([Yasin *et al.*, 2016](#Chapter8.html#c08_bib44)), Boolean SAT attack and hill-climbing search-based attack ([Subramanyan *et al.*, 2015](#Chapter8.html#c08_bib37)), an approximate deobfuscation algorithm-based SAT attack ([Kaveh *et al.*, 2017](#Chapter8.html#c08_bib15)), etc. Moreover, inserting additional key-components into a design incur power and area overhead resulting in a higher design cost.

## 8.4 Design of functionally obfuscated DSP core

As mentioned earlier, Sengupta *et al.*’s approach ([2018](#Chapter8.html#c08_bib35)) is the only one which protects a DSP IP core completely through functional obfuscation. To achieve the FO design, this approach inserts different ILBs as key-component in the netlist design of a DSP core. Additionally, to explore optimal design architecture, PSO-driven DSE is integrated with the functional obfuscation approach. In this section, we discuss formulation and low-cost functional obfuscation approach for DSP core ([Sengupta *et al.*, 2018](#Chapter8.html#c08_bib35)).

### 8.4.1 Formulation

To generate a low-cost, low-power FO netlist for a DSP application (given in the form of a C-code or CDFG), which accepts module library and PSO control parameters as inputs.

### 8.4.2 Low-cost obfuscation method for DSP core

The design process of low-cost functional obfuscation for DSP core consists of two major phases, i.e., (1) designing functionally locked DSP core and (2) exploring low-cost design configuration through the PSO-DSE process. Both these phases perform iteratively until a globally optimal design configuration is explored. [Figure 8.4](#Chapter8.html#c08_fig4) shows the two major phases, their corresponding steps, and the primary inputs to perform low-cost functional obfuscation. As shown in [Figure 8.4](#Chapter8.html#c08_fig4), the primary inputs are a DSP application in the form of a C-code/CDFG, ILB design (based on each 8-bit key value), module library, and PSO control parameters (such as acceleration coefficient, inertia weight, swarm size, terminating criteria). In the process of PSO-DSE in HLS (detailed PSO-DSE framework is explained in Section 8.6), each iteration explores a design configuration and ILB structure, as a particle in the swarm. Based on this design configuration, a gate-level datapath structure (post-processing through standard HLS framework) of the input CDFG application is generated, which is then locked using ILB (where structures of some ILBs are decided on encrypted output from AES block and remaining without encryption. More details are provided in VC). This generates an FO design of the input DSP core. Then the total power and delay of the locked design are calculated to evaluate the design cost through a fitness function. Subsequently, particle positions are updated to explore a new fitter particle, and the complete process is repeated till the termination condition is met. Thus, the final particle position after meeting the terminating condition is used to generate a low-cost obfuscated design of a DSP core. Therefore, the final design architecture not only optimizes the total power, delay, and implementation cost but also minimizes the total gate count of the complete locked netlist, which includes total number of functional units, registers/latches, muxes/demuxes, and ILBs.

Lack of an optimization framework, for generating a locked netlist of DSP IP core, results in huge design overhead. This is because DSP cores are generally large in size and can be designed using multiple alternative hardware design solutions. Any random selection of design solution will lead to higher design overhead. In this approach ([Sengupta *et al.*, 2018](#Chapter8.html#c08_bib35)), particles are encoded with both hardware resource configuration and ILB block insertion procedure to obtain the optimal locked design. Thus, the optimal obfuscated design solution in terms of the number of gate count, power consumption, and execution delay of the locked netlist is achieved through a PSO-DSE process. In the next three subsections, we discuss the overviews of ILBs, its security features, and insertion technique, respectively.

1.  *Overview: IP core-locking blocks:* This subsection explains a brief overview of IP core-locking block. ILBs are key components inserted into a nonobfuscated design to generate a FO design. Each ILB consists of 8-bit key value inserted into each bit of output data. ILBs are designed using the different combination of AND, NAND, NOT, XOR, and XNOR gates. However, structures of ILB depend on the key values. Innumerable different structures of ILBs with the same area are possible. Each of these ILBs generates correct output if a correct key value is provided. In Sengupta *et al.* ([2018](#Chapter8.html#c08_bib35)), a subset of key-bits are fed as input to an AES block and based on the encrypted output the ILB structures are configured. However, rest of the key-bits are fed directly to the ILBs. This is because it can help prevent SAT attack for DSP core (which is not possible now but as a proactive countermeasure for future). The ILBs are designed using various combination of AND, NAND, NOT, XOR, and XNOR gates and with multiple features (explained in the next subsection) to handle different attacks.

2.  *Features: IP core-locking blocks:* This subsection discusses the major security features of ILB design. As mentioned earlier, the ILBs are inserted in each output data bit of the gate structure of DSP IP core to generate a locked netlist. These ILB structures are designed mainly to avoid key-sensitization and removal attacks. Key-sensitization attack is a process of identifying the key value by applying different input patterns and checking their corresponding outputs ([Yasin *et al.*, 2016](#Chapter8.html#c08_bib44)). Therefore, multiple features are considered while designing the ILBs to avoid any possible scenario of key-sensitization and removal attacks.
