
Therefore, the total area of ILB and design cost remain almost similar. For example, based on an encrypted output of key bits (first 8-bits, viz., 11001101) through AES block, a reconfigured ILB can be designed as shown in [Figure 8.12](#Chapter8.html#c08_fig12). As a custom AES block is designed in Sengupta *et al.* ([2018](#Chapter8.html#c08_bib35)), its structure is unknown to an outsider. Therefore, distinguishing and removing AES block from the post-synthesized functionally locked gate design is not feasible. However, it is important to note that more the number of key inputs of functional obfuscation fed into the AES block, more is the number of available exhaustive options for reconfigurable ILBs. For example, if the number of key inputs of functional obfuscation fed through AES block is 8 bit, then the exhaustive reconfigurations possible is 2⁸; while if it is 16 bits, the exhaustive reconfigurations possible is 2^(16) = 65,536 (which is large). Further, the attack time grows exponentially which enhances the difficulty for an attacker in determining the correct key value. However, instead of using custom lightweight AES block, alternative lightweight solutions such as anti-SAT block ([Xie and Srivastava, 2018](#Chapter8.html#c08_bib43)) may also be used to prevent SAT attack. However, as mentioned in Yasin *et al.* ([2017](#Chapter8.html#c08_bib45)), detection and removal of the anti-SAT block could be possible through “signal probability skew (SPS)” attack.

## (4) ILB and AES removal attack

The removal of ILBs and AES from the locked netlist is difficult because:

*   (i) The ILBs along with AES block inserted into the design for locking is resynthesized. This synthesis makes each component of the AES circuit along with the ILB-based locked netlist indistinguishable, which is not feasible to remove by an attacker. This is because of two reasons: (1) first, as mentioned earlier, the subset of ILB structures inserted in the netlist is reconfigured by the designer based on the AES-encrypted output corresponding to the secret key. Therefore, no fixed template of ILBs are available, the configuration of ILB depends on AES output which in turn depends on the secret key and input of the AES, resulting into several possible structures. Moreover, the number of possibilities also increase with the number of key-inputs fed to ILBs through AES. Therefore, knowing the structures of all the possible ILBs for an attacker is not practical in this scenario. (2) Second, since Sengupta *et al.* ([2018](#Chapter8.html#c08_bib35)) have designed their own custom lightweight AES architecture which is not publicly available, component of AES structure after post-synthesis become indistinguishable from the locked netlist of DSP core.

*   (ii) The sequencing of ILBs to generate a locked netlist of DSP core depends on the “μ” variable explored through PSO-DSE process. Therefore, identifying ILB configuration cannot be determined in advance.

## 8.6 Optimization engine for functional obfuscation of DSP cores

The ILB-based functional obfuscation approach for DSP cores ([Sengupta *et al.*, 2018](#Chapter8.html#c08_bib35)) uses the PSO-DSE framework to achieve low-cost obfuscated netlist for DSP IP cores. The PSO-DSE process used in this approach comprises three subprocesses, viz., encoding and initialization of particle, evaluating the fitness of a particle, and generating fitter particle position.
