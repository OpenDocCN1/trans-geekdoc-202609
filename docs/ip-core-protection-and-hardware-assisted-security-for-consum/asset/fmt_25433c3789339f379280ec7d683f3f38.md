##### 3.4.1.2 Trojan security approach—Sengupta et al. ([2017a](#Chapter3.html#c03_bib26))

Sengupta et al. ([2017a](#Chapter3.html#c03_bib26)) devised a hardware Trojan security aware approach that is capable of detecting the Trojan for DSP cores. It accepts a non-loop-based DSP application in the form of a data flow graph (DFG), user constraints, bacterial foraging optimization algorithm (BFOA) control parameters (such as step size, # of chemotactic steps, # of elimination-dispersal steps, # of replication steps, terminating criteria, and population size), and a module library. It then obtains a low-cost Trojan secured design based on the input DSP core (fed as DFG).

To obtain low-cost Trojan secured DSP IP core, a design solution consisting of hardware architecture configuration and vendor allocation mode is explored iteratively through BFOA. This approach explores an optimal vendor allocation procedure using variable `M[v]` in bacterial encoding. More explicitly, in this process, each bacterium is encoded with the number of resources of a particular resource type and the vendor allocation mode. The encoding of each bacterium can be represented as `B = (R[n], M[v])`, where `R[n]` indicates the hardware configuration and `M[v]` indicates the vendor allocation mode. Here, the vendor allocation mode includes two variances (`M[v] = 0` or `1`). Before discussing the vendor allocation process, let us assume the scheduled design includes DMR logic consisting of the original unit (indicated as `U^(OG)`) and the duplicate unit (indicated as `U^(DP)`).

The rules for vendor allocation mode at `M[v] = 0` are as follows:

*   In each control step for a particular unit (either `U^(OG)` or `U^(DP)`), alternate vendor allocation would be performed for similar types of operations. For example, if in control step 1, three addition operations (opn.1, opn.2 and opn.3) are available, then opn.1 and opn.3 would be allocated to hardware of same vendor and opn.2 would be allocated to hardware of another vendor.

*   In the other unit, orthogonal vendor allocation is performed to maintain distinctness. In others words, the same operation of both the units must be allocated to different vendors. For example, if in `U^(OG)`, opn.1 and opn.3 are allocated to hardware of vendor type 1 (V1) and opn.2 is allocated to hardware of vendor type 2 (V2), then in `U^(DP)`, opn.1 and opn.3 must be allocated to hardware of V2 and opn.2 must be allocated to hardware of V1.

The rules for vendor allocation mode at `M[v] = 1` are as follows:

*   All operations of a particular unit (either `U^(OG)` or `U^(DP)`) must be allocated to hardware of the same vendor. For example, all operations of `U^(OG)` must be allocated to hardware of V1.

*   Similar operation of both the units must be allocated to distinct vendors. For example, if all operations of `U^(OG)` are allocated to hardware of V1 then all operations of `U^(DP)` must be allocated to hardware of V2 and vice versa.

The generic overview of this approach is shown in [Figure 3.12](#Chapter3.html#c03_fig12). Although this approach is capable of handling hardware Trojan during HLS for non-loop based DSP applications, it does not provide any process to handle loop-based CDFG DSP cores.

##### 3.4.1.3 Trojan security approach—Sengupta et al. ([2017b](#Chapter3.html#c03_bib27))

Sengupta et al. ([2017b](#Chapter3.html#c03_bib27)) overcome the aforementioned shortcoming in their devised hardware Trojan security aware approach. This approach is capable of accepting single loop-based DSP applications in the form of a CDFG, user constraints, maximum loop iteration count (`I`), PSO control parameters (such as inertia weight, cognitive factor, and social factor), and module library. It finally produces a low-cost Trojan security aware DSP RTL design as output.

This approach obtains a low-cost design solution through a PSO-based DSE process within the user-specified design constraints (the details of the PSO-DSE approach is available in Section 3.6.3.1). The design solution in each iteration of the PSO-DSE contains not only hardware configuration and vendor allocation mode but also loop-unrolling factor, which is a crucial design parameter for loop-based CDFG. Moreover, in this approach, instead of searching among all the possible values of the unrolling factor, a list of selected unrolling factors is obtained through a pre-processing algorithm as shown in [Figure 3.13(a)](#Chapter3.html#c03_fig13a). The input to the pre-processing algorithm is the maximum loop iteration count and the output is the screened list of unrolling factors. The algorithm works as follows: the unrolling factors with the higher number of sequential execution and ones which increase code complexity without significantly improving the performance are not included in the screened list. This is because increase in sequential execution results in delay overhead, while increase in code complexity results in higher area/power. Further, large unrolling factors are not always monotonically increasing functions of performance. ##### 3.4.1.4 Trojan security approach—Sengupta et al. ([2017c](#Chapter3.html#c03_bib28))

Sengupta et al. ([2017c](#Chapter3.html#c03_bib28)) overcome the aforementioned shortcoming in their devised hardware Trojan security aware approach. This approach is capable of accepting nested-loop DSP applications in the form of a CDFG, user constraints, maximum loop iteration count for all nested loops (`I[1]`, `I[2]`, … `I[n]`), PSO control parameters (such as inertia weight, cognitive factor, and social factor), and module library, finally producing a low-cost Trojan secured DSP RTL design as output.
