

如前所述，由于多种原因，HLS 框架已成为高效 DSP IP 核心设计流程中不可或缺的一部分。目前有多种成功的学术和商业 HLS 工具可用于设计 DSP IP 核心。通常，这些 HLS 框架的库中包含一些预定义的模块或模块。这些预定义的模块或模块也被称为微 IP。在设计完整的 DSP IP 核心时，DSP IP 设计人员直接使用这些微 IP 以提高可重用性并减少设计工作量。如果 HLS 工具供应商从另一个不可信的供应商处导入这些微 IP，那么在这种情况下，这些 IP 核心可能容易受到硬件木马的攻击。因此，无法保证 HLS 库中的 3PIP 核心将 100% 不含木马。

让我们假设 HLS 框架的模块库中有一个 BCD 加法器 IP 作为黑盒可用。它包含三个输入和一个输出：(i) 使能信号 (`En`)，用于开启/关闭加法器的执行，(ii) 第一主输入 `A`，位宽为 4 (`A[3]A[2]A[1] A[0]`)，(iii) 第二主输入 `B`，位宽为 4 (`B[3]B[2]B[1] B[0]`)，以及 (d) 一个输出 `O`，位宽为 4 (`O[3]O[2]O[1] O[0]`)。在一般场景中，在功能/仿真验证和测试期间，`En` 信号被置位 (`En = 1`) 以启动 BCD 加法器 IP 的执行。一旦验证过程完成，`En` 信号被复位 (`En = 0`) 以停止 BCD 加法器 IP 的执行。现在，让我们考虑一个如 [图 3.10](#Chapter3.html#c03_fig10) 所示设计的 BCD 加法器。在这种情况下，BCD 加法器 IP 在其验证过程中将表现正确，因为设计验证人员将在功能仿真期间将 `En` 信号设置为“开启”。他/她可能会错误地认为 `En` 信号确实启动和停止 IP 的执行。然而，攻击者可以设计一个 IP，使得当 `En` 信号被复位时木马会被触发。因此，每当系统设计人员/集成人员复位 `En` 信号时，它可能会恶意生成错误的输出，从而影响 DSP IP 核心设计的输出。此外，除了上述情况外，木马的触发还可以通过有限状态机 (`FSM`) 计数器、外部天线等方式实现。此外，开放市场上没有黄金 IP（即保证 100% 不含木马的 IP）可用；因此，在较低抽象级别检测这种类型的木马是困难的。还有其他几个原因，将在以下部分讨论。

## 3.3.2 3PIP 模块在 RTL/较低级别中的木马可检测性

在 RTL 验证或较低设计抽象级别的验证/测试中，检测会破坏 3PIP 模块功能输出的硬件木马逻辑是困难的，原因如下：

1. 被木马逻辑感染的 3PIP 在正常条件下会产生功能正确的输出，即直到木马逻辑被触发。

2. 木马逻辑在非常罕见且特定的时间/条件下被触发（如前所述），因此在功能验证中识别此类条件或事件是困难的 ([Tehranipoor and Koushanfar, 2010](#Chapter3.html#c03_bib32))。

3. 在功能验证中，在大多数情况下，只验证整个 SoC 的功能；系统（系统集成后）中使用的（导入的）每个 IP/模块都不会被检查。

4. 通常，木马逻辑以一种方式设置在 IP 中，使其在功能验证期间保持休眠，并在完整的 SoC 部署到实时情况时被触发。

5. 由于没有可用的可信黄金 IP（即保证 100% 不含木马的 IP）模型，因此在 DSP 核心的 HLS 设计中，3PIP 中硬件木马的检测逃逸是可能的。

6. 物理检查和逆向工程是一项非常昂贵且复杂的程序，不能保证检测到此类木马。

7. 用于检测制造故障（即桥接故障、延迟故障、卡在故障等）的测试过程也不能保证检测到此类木马。

8. 由于技术的发展，3PIP 的物理特征尺寸减小。分析参数信号以检测此类木马不被认为非常有效 ([Tehranipoor and Koushanfar, 2010](#Chapter3.html#c03_bib32))。

## 3.4 选定的木马安全方法

在本节中，我们讨论 DSP IP 核心的木马安全方法以及其他硬件类型（如组合/时序电路）的几种选定的木马安全方法。我们首先查看 DSP 核心的多种木马检测方法，接下来，我们讨论组合/时序电路的选定木马检测方法。

### 3.4.1 DSP 核心的木马安全方法

以下讨论的 DSP 核心木马检测方法基于威胁模型，其中硬件木马能够在 DSP 核心输出中产生功能（计算）变化。换句话说，这些方法中考虑的木马有效载荷是导致 DSP 核心输出中功能（计算）变化的一种有效载荷。

#### 3.4.1.1 木马安全方法——Rajendran et al. ([2013)](#Chapter3.html#c03_bib17) 和 Liu et al. ([2014](#Chapter3.html#c03_bib12))

Rajendran et al. ([2013](#Chapter3.html#c03_bib17)) 和 Liu et al. ([2014](#Chapter3.html#c03_bib12)) 已制定基于复制的并发错误检测 (`CED`) 技术，以通过 HLS 实现木马安全设计。此方法处理 3PIP 核心中可用且影响其输出或拒绝服务的硬件木马。在基于复制的 `CED` 技术中，对相同的设计进行复制，并且两个设计都输入相同的一组输入。可以通过比较它们的输出来识别由于木马逻辑激活而导致的错误/不相似的输出。然而，通常不受信任的第三方供应商会制作一个被木马感染的 IP 核心设计，然后将其多个副本导出给系统集成人员/SoC 设计人员。因此，设计的正常复制无法检测木马（因为两个设计都会产生相同的恶意输出）。在 Rajendran et al. ([2013](#Chapter3.html#c03_bib17)) 中，3PIP 核心的来源以多样化的方式，使得两个设计的相同操作使用来自不同来源的 3PIP 核心。此过程不仅检测由硬件木马引起的 3PIP 核心的恶意输出，还可以通过防止串通来防止木马的激活。此方法防止了两种类型的串通，即父子串通和父父串通。防止串通的绑定规则如下：

* 设计中父操作及其子操作必须绑定到不同 3PIP 供应商的 3PIP。

* 设计中子操作的至少一个父操作必须绑定到来自不同 3PIP 供应商的 3PIP。

此方法的通用概述如 [图 3.11](#Chapter3.html#c03_fig11) 所示。尽管此方法能够实现木马检测和串通预防，但可能会产生一些设计开销，因为在 HLS 的调度阶段未探索低成本设计架构。此外，在 3PIP 供应商分配期间可以通过多种方式实现差异性，这对整体设计成本有直接影响。在此方法中，未探索最优供应商分配以最小化整体设计安全成本。此外，此方法不处理基于循环的控制数据流图数字信号处理 (`CDFG DSP`) 应用程序。
