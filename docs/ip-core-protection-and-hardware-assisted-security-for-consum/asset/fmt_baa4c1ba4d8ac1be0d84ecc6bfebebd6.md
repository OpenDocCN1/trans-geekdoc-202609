
Today’s CE devices, ranging from modern smart phone, smart TV, home appliance, set-top box, tablet, digicam to recent smart speaker, are designed using SoC platforms ([Thavalengal and Corcoran, 2016](#Chapter7.html#c07_bib40); [Mohanty, 2015](#Chapter7.html#c07_bib18); [Kim *et al.*, 2015](#Chapter7.html#c07_bib12)). These SoCs comprise various system modules such as memory (SRAM, Flash), A-to-D converter, custom processor, or co-processor, DSP kernels, A/V codecs, and wireless modems. Among these modules, DSP kernels in the form of IP cores are primarily responsible for data/power-intensive computation at high speed, minimal silicon area, and low power in an SoC ([Li *et al.*, 2015](#Chapter7.html#c07_bib16)). Thus, DSP IP cores are the heart of every SoC-based CE devices. For example, ConnX D2 DSP IP core used in telecom infrastructure of voice-over internet protocol (VoIP) and wireless mobile device ([ConnX, 2009](#Chapter7.html#c07_bib42)). In a cellular telephone system, it is used in speech encoding/decoding process. Low-end DSP IP cores are included in digital camera, portable phones, consumer audio, headsets, while mid-end DSP cores are included in cellular phone, fax/voice receiver. Finally, high-end DSP IP cores are included in various CE systems including wireless base station and cable modems. Further, reusability of DSP IP core maximizes design productivity to cope with the increasing design complexity in electronic systems ([Castillo *et al.*, 2007](#Chapter7.html#c07_bib6)), thus maintaining a balance in global supply chains for SoC-based CE devices (Sengupta and Sedaghat, [2011](#Chapter7.html#c07_bib33), [2013](#Chapter7.html#c07_bib34)).

These reusable DSP IP cores warrant a substantial investment in research, workforce, money, and time by an IP vendor/designer. Therefore, these mandate protection from emerging IP threats such as cloning and/or infringement, and RE ([Roy and Sengupta, 2017](#Chapter7.html#c07_bib24); [Sengupta and Bhadauria, 2016](#Chapter7.html#c07_bib28); [Wong *et al.*, 2004](#Chapter7.html#c07_bib47); [Koushanfar, 2012](#Chapter7.html#c07_bib13); [Alkabani and Koushanfar, 2007](#Chapter7.html#c07_bib1); [Sengupta and Kundu, 2017](#Chapter7.html#c07_bib29); [Sengupta *et al.*, 2018](#Chapter7.html#c07_bib35)). According to literature sources, the total fiscal revenue loss due to piracy and counterfeiting in 2013 for G20 nations was $96–130 billion which will increase to $199–270 billion in 2022. It is projected that 10% of the internationally sold electronics products are forged ([Guajardo *et al.*, 2008](#Chapter7.html#c07_bib11); [Lao and Parhi, 2015](#Chapter7.html#c07_bib14)). An attacker can “silently” reuse a DSP IP core without legal permission from the IP owner to save design time, cost, and effort ([Sengupta, 2016](#Chapter7.html#c07_bib26)). He/she can easily identify the functionality of a DSP IP core from its architecture through RE. RE of an IP core is a process of identifying its design, structure, and functionality ([Rajendran *et al.*, 2013](#Chapter7.html#c07_bib22)). Using RE, one can identify the device technology ([Intel Transistors, 2012](#Chapter7.html#c07_bib39)), extract the gate-level netlist ([Torrance and James, 2009](#Chapter7.html#c07_bib43)), and infer the IP functionality ([ExtremeTech, 2012](#Chapter7.html#c07_bib10)). Though according to the Semiconductor Chip Protection Act of 1984 (SCPA), RE is a legal process for teaching, analysis, and evaluation purpose; however, an attacker can use RE process for IP piracy/attacks which is illegal. An attacker can also insert malicious Trojan logic into an IP core, if he/she can identify the functionality of a DSP IP core through RE. Therefore, it is very crucial to design a DSP IP core in a way that it provides substantial resiliency against RE ([Yang *et al.*, 2013](#Chapter7.html#c07_bib48); [Parhi, 2012](#Chapter7.html#c07_bib20); [Lao and Parhi, 2015](#Chapter7.html#c07_bib14); [Walz and Schrder, 2016](#Chapter7.html#c07_bib45); [Sengupta, 2017](#Chapter7.html#c07_bib27)). A thematic attack scenario of protected DSP IP core for different CE devices is shown in [Figure 7.1](#Chapter7.html#c07_fig1) ([Mohanty, 2003](#Chapter7.html#c07_bib17); [Sengupta, 2016](#Chapter7.html#c07_bib26)). One way to achieve resilience against RE is to obscure the functionality of a DSP IP core by transforming its architecture. This transformation should change the standard structure of a DSP IP core into an unobvious architecture while preserving correct functionality. Therefore, the functionality will not be easily identifiable from its structure, thereby increasing the RE complexity for an adversary. This process is known as structural obfuscation. More broadly, obfuscation is a process of obscuring or disguising the actual functionality of the design (product) in order to protect its intellectual property content. Though hardware obfuscation is motivated from software obfuscation, the former is more complex than the latter, despite both of them fundamentally having the same objective. Software obfuscation aims to conceal the implementation code of an algorithm using techniques such as dead code elimination, code unrolling, while hardware obfuscation aims to obscure the circuit (hardware) functionality/structure. This process is classified, as it is achievable through several complex techniques, depending on which form (design abstraction layer. Refer [Figure 7.2](#Chapter7.html#c07_fig2)) the hardware circuit is described at, e.g., RTL codes, netlist, layout, fabricated chip. Sometimes, the software obfuscation methods after customization can be applied for hardware obfuscation. However, a completely exclusive method may be needed for hardware obfuscation depending on the hardware design abstraction level. In summary, a hardware obfuscator (process or algorithm) is responsible for transforming a design representation “D” into its obfuscated form “O(D)” that has the same functionality as “D,” yet is unintelligible to an adversary targeting to recover “D” from “O(D).” More details on the threat model of obfuscation are explained in the following sections of this chapter.

#### 7.1.1 Threat model

Hardware structural obfuscation transforms the original hardware design architecture of an IP core into a nonobvious structural architecture. Thus enhancing the RE complexity as it is more tough for an attacker to discover the actual functionality of an IP core from its transformed structure. Consequently, it provides defense against threats resulting due to `RE` such as `IP piracy`, `IP infringement (counterfeit)`, and `Trojan insertion`.
