
## Functionality changeable payload-based hardware Trojan

This type of Trojan affects the payload of a circuit by causing output malfunction. For example, as shown in [Figure 3.6](#Chapter3.html#c03_fig6), the BCD adder has two primary inputs, `A` and `B`, each of 4-bit size (`A[3]−A[0]` and `B[3]−B[0]`), one enable signal `En` of one bit and one primary output `O` of 4-bit size (`O[3]−O[0]`). The BCD adder will work correctly when the `En` signal is set to 1, but when the `En` signal is set to 0 to disable the component/module, the Trojan gets triggered and starts introducing malfunctioning. The system integrator would keep the component enabled (`En = 1`) during the testing phase, because he/she may assume that the `En` signal is for enabling and disabling the component ([Sengupta, 2017](#Chapter3.html#c03_bib21)); however, it is a covert triggering signal for the Trojan. Therefore, the rare condition test could evade and pass the functional simulation and test (explained later in greater detail).

## Performance degradable payload-based hardware Trojan

This type of Trojan affects the payload of a circuit by degrading its performance. In other words, this type of hardware Trojan may increase execution delay or power consumption of a circuit without altering the correctness of the output. Therefore, this type of Trojan may go unnoticed during the functional verification phase. For example, as shown in [Figure 3.7](#Chapter3.html#c03_fig7), for input values `A` = 1 and `B` = 0 or 1, the Trojan logic will not get triggered; therefore, there is no degradation of performance in terms of propagation delay of the 1-bit adder while calculating the sum (`S`). However, for input values `A` = 0 and `B` = 0 or 1, the Trojan logic gets triggered, therefore the propagation delay to calculate `S` will increase, thus degrading the performance of the circuit. However, in both the cases, the correct output will be generated, therefore, identification of this type of Trojan through functional/simulation verification could be evaded. This type of Trojan may result in an occasional timing violation of the circuit ([Sengupta, 2017](#Chapter3.html#c03_bib21)).

## Leaking confidential information and launching denial of service (DoS) payload-based hardware Trojan

This type of Trojan, which leaks confidential information, is designed in such a way, that it can bypass the encryption process applied on the confidential information. The Trojan could be a big threat for sensitive information. For example, as shown in [Figure 3.8](#Chapter3.html#c03_fig8), once the Trojan is triggered, the plaintext may skip the encryption process, thus disclosing confidential information ([Sinanoglu *et al.*, 2013](#Chapter3.html#c03_bib31)).

## 3.2.2 Benefit of Trojan security at higher abstraction level

As mentioned earlier, most of the CE devices integrate IP cores from the DSP and multimedia domain in their SoC design process, such as JPEG CODEC ([Sengupta *et al.*, 2018b](#Chapter3.html#c03_bib30)), FIR, IIR, FFT, DCT, and HWT ([Sengupta *et al.*, 2018a](#Chapter3.html#c03_bib29)). These IP cores contain complex algorithms that are very challenging and time-consuming to design if the design process starts from the register transfer level or lower abstraction layer. Additionally, multiple design architectures (hardware variances) are possible for implementing these IP cores. Selecting arbitrary hardware design architecture may result in large overheads in terms of design implementation cost (area, delay, power etc.). A high-level synthesis (HLS) process integrated with a DSE engine is capable of exploring and designing a low-cost (in terms of power, performance, energy, and area) hardware architecture for DSP/multimedia IP cores within an acceptable runtime. Thus for designing of hardware for complex algorithms, within design constraints, while concurrently satisfying time-to-market pressure, HLS is the key.

While designing a DSP IP core, multiple 3PIP cores are usually available in the module library of an HLS tool. As these IP cores are imported from 3PIP vendors, which are untrustworthy, there is high possibility of their containing hardware Trojan ([Rajendran *et al.*, 2013](#Chapter3.html#c03_bib17)). In a typical case, the vendor of the HLS tool imports IP cores/blocks available in its library from 3PIP vendors. Again, as mentioned earlier, these IP cores may also contain hardware Trojan. As designing a DSP IP core is vulnerable to such Trojan, handling hardware Trojan for DSP cores is necessary ([Rajendran *et al.*, 2013](#Chapter3.html#c03_bib17); Sengupta *et al.*, [2017b](#Chapter3.html#c03_bib27), [2017c](#Chapter3.html#c03_bib28)). In Section 3.4, we discuss different Trojan secured DSP IP core design processes that are available in the literature.

## 3.2.3 Threat model

There are different variations of hardware Trojan as discussed in Section 3.2.1. However, in the context of DSP, since hardware Trojan threats affecting the output functionality is a well-studied topic, in this chapter we lay emphasis only on those type of Trojans which change the computational (functional) output of an IP core circuit. As mentioned earlier, this type of Trojan can be available in the library of an HLS tool inside an IP block/module. Insertion of Trojan logic into the IP block/module is possible in two ways: (i) through an adversary within the HLS design house team; or (ii) when the design team of the HLS tool vendor imports the IP block/module from a 3PIP vendor. As this type of Trojan is triggered under very rare conditions, its detection is not always possible (i.e., the chances of evasion are high). The literature has studied the Trojan threat model on DSP cores that consider 3PIP vendors as untrustworthy. Thus the in-house design integrator team and foundry are considered trustworthy and the 3PIP vendor is considered an untrustworthy entity in the SoC design cycle.
