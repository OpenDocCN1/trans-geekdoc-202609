
The designing process of a DSP application in the form of an IP core is very complex. Therefore, the DSP IP core design flow is divided into multiple design abstraction levels such as system level, algorithmic level, register transfer level, logic level, and layout level (as shown in [Figure 7.2](#Chapter7.html#c07_fig2)). Every layer has its exclusive design automation or CAD method which enables the design of DSP IP cores with lesser design time. Architectural synthesis (also known as HLS) is one such automatic CAD process, which is responsible for generating equivalent register-transfer-level hardware description languages such as `VHDL`, `Verilog` of DSP applications. Examples of a few well-known commercial and academic HLS tools for DSP core/multimedia are shown in [Figure 7.3](#Chapter7.html#c07_fig3) ([Sengupta, 2016](#Chapter7.html#c07_bib26); [Mohanty, 2003](#Chapter7.html#c07_bib17)). As shown in [Figure 7.3](#Chapter7.html#c07_fig3), each HLS tool is represented as tool name, followed by the owner name (highlighted in bold) and the launching year of the tool. However, none of these tools incorporate security through obfuscation.

The resilience of a DSP IP core against RE can be provided in any abstraction level of the design flow. However, providing resilience against RE attack through structural obfuscation during architectural synthesis is beneficial as the structural change performed in higher design abstraction level obfuscates the datapath and control unit structures of the application. Thus, it also obfuscates the gate structure (netlist) of the application. Additionally, architectural synthesis for digital IPs is way matured to achieve hardware area minimization, power optimization, performance enhancement, and fault-tolerant IP design solution with lesser design complexity. Therefore, structural obfuscation during architectural synthesis is capable of generating a strongly obscured design which is functionally equivalent but appears remarkably different than the original structure. The only way to use this type of obfuscated design is as a “black-box” module ([Chakraborty and Bhunia, 2009](#Chapter7.html#c07_bib7)).

## 7.2 Obfuscation for IP core protection—a broad view

This section discusses the fundamentals of different obfuscation-based IP core protection mechanisms with emphasis on high-level transformation-based structural obfuscation mechanisms that are available in the literature.

Obfuscation-based IP protection can be achieved in three different ways: (1) by transforming the HDL code, known as “source code-based obfuscation,” (2) by using key-based logic locking, known as “logic obfuscation,” and (3) by hiding the functionalities of a design, known as “structural obfuscation.”

### 7.2.1 Code obfuscation techniques

To thwart an attacker from intercepting the HDL code, it either alters ([Brzozowski and Yarmolik, 2007](#Chapter7.html#c07_bib4)) the source code into a compound version or encrypts ([Barria *et al.*, 2016](#Chapter7.html#c07_bib2)) it. In Brzozowski and Yarmolik ([2007](#Chapter7.html#c07_bib4)), HDL code obfuscation is achieved using diverse alteration approaches which are challenging to reverse engineer. In Barria *et al.* ([2016](#Chapter7.html#c07_bib2)), the source code is encrypted using “Dead Code Addition” approach on a Crypter.

### 7.2.2 Logic obfuscation techniques

Logic obfuscation (also known as logic encryption) locks the implementation of a design by implanting supplementary components into it. These components are controlled by key gates. Applying incorrect key will produce functionally different output than the correct output of the design. Logic obfuscation is of two types: (1) sequential and (2) combinational ([Rajendran *et al.*, 2013](#Chapter7.html#c07_bib22)). In sequential logic obfuscation, the additional components could exist in a key-controlled obfuscation mode. For example, in Chakraborty and Bhunia ([2009](#Chapter7.html#c07_bib7)), dummy states are added with the original states of the FSM of a design to obfuscate it. These dummy states are controlled by an external key. Applying incorrect key leads to obfuscation mode or invalid state whereas applying correct key leads to normal mode. In Desai *et al.* ([2013](#Chapter7.html#c07_bib8)), the design is locked based on internally generated key sequence (known as Code-Word). This technique hides the design using this Code-Word in the transition function. On applying the incorrect key, the FSM will deviate from the correct transition path.

In combinational logic obfuscation, the additional components could be XOR/XNOR gates ([Roy *et al.*, 2008](#Chapter7.html#c07_bib25); [Rajendran *et al.*, 2012](#Chapter7.html#c07_bib21); [Rajendran *et al.*, 2015](#Chapter7.html#c07_bib23)), AND/OR gates ([Dupuis *et al.*, 2014](#Chapter7.html#c07_bib9)), Lookup Table (LUT) ([Baumgarten *et al.*, 2010](#Chapter7.html#c07_bib3)), muxes ([Wang *et al.*, 2016](#Chapter7.html#c07_bib46); [Zhang, 2016](#Chapter7.html#c07_bib49)), or combination of these elements ([Lee and Touba, 2015](#Chapter7.html#c07_bib15)). EPIC ([Roy *et al.*, 2008](#Chapter7.html#c07_bib25)) is one of the primary work where the framework of logic obfuscation is proposed. In this approach, XOR/XNOR gates are inserted as key-gates in the random location of the design. Random insertion of key-gates into a design does not always guarantee that wrong output is produced for all input patterns on application of incorrect key. Additionally, in this approach, the key can be sensitized by input pattern. Rajendran *et al.* ([2015](#Chapter7.html#c07_bib23)) inserted XOR/XNOR key-gates in the design in such a way that the Hamming distance (HD) between the incorrect output and correct output became maximum. In Lee and Touba ([2015](#Chapter7.html#c07_bib15)), XOR/XNOR key-gates are combined with mux key-gates to achieve a higher HD between correct and incorrect output. Key-controlled LUT-based logic obfuscation is proposed in Baumgarten *et al.* ([2010](#Chapter7.html#c07_bib3)). In this approach, the complete IP is divided into multiple fixed and configurable parts. The configurable part is then realized as a key-controlled LUT. As the logic type of the reconfigurable part can be changed after fabrication, an adversarial foundry cannot misuse the IP. Several attack strategies are available against these logic obfuscation techniques, such as key-sensitization ([Rajendran *et al.*, 2015](#Chapter7.html#c07_bib23)), Boolean satisfiability (SAT) and hill-climbing search-based attack ([Subramanyan *et al.*, 2015](#Chapter7.html#c07_bib38)). These logic obfuscation techniques have proven to be powerful for combinational/sequential circuits. However, in the context of DSP cores, these techniques incur more design overhead due to extra key-gates been implanted into the design, as well as lack of framework to select low-cost design architecture. Moreover, if the key is leaked somehow, the IP designer cannot prevent any attack until the IP is redesigned for a new key. More details on this technique are provided in Chapter 8.

### 7.2.3 Structural obfuscation techniques
