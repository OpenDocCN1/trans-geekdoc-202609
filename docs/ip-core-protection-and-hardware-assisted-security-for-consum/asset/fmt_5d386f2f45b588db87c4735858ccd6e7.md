
## 5. Loop support feature

The loop support feature aims to detect the type of application that can be fed as an input to an HLS tool used in the IP core design. In other words, this feature extracts whether input format of a tool can support loop-based application in the form of control data flow graph (CDFG) or non-loop-based application in the form of DFG ([Gupta, 2003](#Chapter6.html#c06_bib5); [Kurra and Panda, 2007](#Chapter6.html#c06_bib13); [Sengupta *et al.*, 2017](#Chapter6.html#c06_bib34)). The devised rule to identify loop support feature requires input application in C-code. This C-code is fed into executable version of HLS tool. If HLS tool runs correctly without any error and produce comprehensible RTL code, then it supports the respective input format.

Note: this case study only considers executable versions of HLS tools that do not require manual intervention.

## 6. Trojan security feature

In hardware domain, Trojan can be understood as a malicious modification of a hardware design that aims to achieve malicious intention of an attacker ([Rajendran *et al.*, 2013](#Chapter6.html#c06_bib21); [Bhunia *et al.*, 2013](#Chapter6.html#c06_bib1); [Zhang and Tehranipoor, 2011](#Chapter6.html#c06_bib40)). An attacker may intend to leak information, generate incorrect output, trigger denial of service attacks, etc. There can be several techniques to provide security against Trojan based on their intent. However, so far in the literature for DSP IP cores, protection against Trojan, which intends to harm correct functionality of an IP by generating incorrect output, has been considered. Thus, during the feature extraction rule, only this special Trojan for DSP cores is accounted for. Typically, Trojan security for DSP cores requires modules from at least two different IP vendors. Further, Trojan detection (security) is typically performed using modules from at least two distinct vendors and using them in DMR system as shown in [Figure 6.13](#Chapter6.html#c06_fig13). Therefore, the feature extraction algorithm accepts datapath HDL of an IP core as well as module library of HLS tool as inputs. The presence of DMR is detected (as discussed in reliability feature extraction process) by identifying the presence of a comparator component having port map similar to following port mapping statement: `port map (output register signal 1, output register signal 2, comparator output signal)`. Additionally, if the module library comprises design objectives (such as area, power, delay) corresponding to at least two different IP vendors, the presence of Trojan security feature is present in the IP core design.

Note: The main difference between reliability and Trojan security properties is that reliability does not require modules from two distinct IP vendors. On the other hand, Trojan security requires module from two distinct vendors.

### 6.3.2 IP core validation

Once all the features are extracted, the feature-set of each DSP IP core generated corresponding to competing vendors as well as IP whose ownership is to be determined (i.e., IP[ID]) are created. Subsequently, the feature-set of competing IP vendor is matched with the feature-set of IP[ID] as per (6.2). If match percent (*µ*) of 100% is obtained, then the ownership of IP[ID] is awarded to that particular IP vendor.

![image](OEBPS/images/c06_eqn62.gif)

In a typical scenario, the feature-set used in CFE approach ([Sengupta and Kachave, 2018](#Chapter6.html#c06_bib26); [Inoue *et al.*, 2011](#Chapter6.html#c06_bib7)) is enough for resolving the IP core ownership conflict. However, we would like to discuss various exceptional scenarios and procedure to follow to resolve the ownership conflict in those scenarios.

* I. **None of the competing IP vendors has a 100% match**: In such a scenario, the ownership of IP[ID] will not be awarded to any of the vendors competing for claiming the ownership of IP[ID].

* II. **More than one competing IP vendors have a 100% match**: In such a scenario (called “deadlock in IP resolution”), the feature-set should be expanded by identifying additional properties that may distinguish between two or more competing IP vendors. This is performed by further investigating each and every IP core to identify should there be additional properties that could be considered to break this deadlock. Based on this further investigation, new features are added in the feature set. In other words, the feature-set is expanded to incorporate these new features. Further, feature extraction rules need to be devised corresponding to these newly added features. Next, feature extraction is performed now for these newly features from the IP cores who are in deadlock. Subsequently, feature matching is performed with the updated feature-set. Finally, if there is no exceptional scenario, the ownership is awarded to the IP vendor whose feature-set matches 100% with that of IP[ID].

### 6.3.3 Important characteristics of customized CFE

* Customized CFE approach ([Sengupta and Kachave, 2018](#Chapter6.html#c06_bib26)) is applicable to a scenario where each competing IP vendor has a unique HLS tool for claiming ownership of IP[ID]. However, in scenarios when two or more IP vendors are claiming ownership based on same HLS tool obtained through third party, then the devised “feature-set” of customized CFE is not suffice for resolving ownership conflict.

* As already discussed in Section 6.2, customized CFE approach requires only executable version of HLS tool. Further, it does not require source code of these HLS tools. Thus, there is no concern for IP vendors about source code or breach of confidential information. Additionally, if some competing IP vendor refuses to provide executable version of HLS tool, the vendor is discarded from ownership-awarding process. This is because, typically, the rightful owner of an IP would not hesitate in providing executable version of his/her HLS tool, as ownership of the IP core is at stake.

* Customized CFE is applicable for IP vendors of DSP IP cores. However, IP vendors for FPGA would not fall within the scope of [Sengupta and Kachave (2018)](#Chapter6.html#c06_bib26).

## 6.4 Analysis on case studies
