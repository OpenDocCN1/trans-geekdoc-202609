
然而，位图索引的`size`（大小）带来了另一个重要问题，许多多维索引也面临这一问题。位图索引中的位图数量与被索引属性的不同值的数量成正比。为了处理高基数属性（最著名的是浮点数据），会使用量化策略来减少有效的不同值的数量，从而减少位图。此外，压缩是位图索引不可或缺的一部分。尽管使用了压缩，且它们的空间需求不会随着维度数量呈超线性增长，但它们通常仍消耗与被索引数据大致相同的空间 [[237](#9783110785951_034588.xhtml#b_9783110785968-011_ref_237)]。此外，在此语境下也称为`binning`（分箱）的量化，会引入误报候选项，通过膨胀索引访问的选择率来增加 I/O 访问次数。

### 6.4.1.3 高效数据库扫描

由于简单的列式扫描是评估高维数据查询最高效的方式之一，因此开发了许多技术来加速它。

一种直接的方法是并行化。大型集群中的机器可以独立筛选数据，这最终催生了诸如 `MapReduce` [[136](#9783110785951_034588.xhtml#b_9783110785968-011_ref_136)] 之类的框架，它们允许在由商用机器组成的大型集群上以直接且容错的方式实现扫描密集型工作负载。然而，在有限的项目预算下，仅通过扩展集群来提升性能的能力也是有限的。

当系统发出许多查询时，扫描工作通常可以在 `concurrent workloads`（并发工作负载）之间共享，从而更高效地利用存储有限的 I/O 带宽 [238, 397]。

其他方法试图减少查询的有效扫描量。实现这一点的一种方法是首先考虑关于硬件块（在磁盘上）的紧凑摘要统计信息。例如，在 `ADIOS` I/O 系统 [[252](#9783110785951_034588.xhtml#b_9783110785968-011_ref_252)] 中实现的 `BlockIndex` [[393](#9783110785951_034588.xhtml#b_9783110785968-011_ref_393)]，将每个块中值的范围作为元信息存储。将值范围与给定查询的谓词进行比较，允许在扫描期间跳过那些不可能包含符合条件元组的块。然而，只有当块中值的范围对数据存储顺序表现出统计依赖性时，该技术才能高效。尽管某些时空数据集的某些属性具备这一特性，但像 `LHCb` 这样的项目中来自独立事件的数据不太可能提供这种特性。

在顺序扫描期间减少考虑的数据量的另一种方法是扫描数据点的 `reduced representation`（简化表示）。`ColumnSketches` [[196](#9783110785951_034588.xhtml#b_9783110785968-011_ref_196)] 通过量化值来表示列的值，使得每个值所需的位数更少，但仍允许谓词求值。同样，这以膨胀选择率为代价，因为某些数据点可能被 `ColumnSketch` 误判为符合条件。然而，与普通的列式扫描相比，必须考虑的有效数据量可能会大幅减少。相同的技术以前也曾以 `VA-files` [[386](#9783110785951_034588.xhtml#b_9783110785968-011_ref_386)] 的形式用于最近邻查询。

### 6.4.2 DeLorean：面向高效数据访问的优化扫描

为了使上述数据库技术进步在物理学领域可用，我们在多特蒙德工业大学构建了 `DeLorean` 平台原型。`DeLorean` 假设存在一个大容量数据存储——例如 CERN `LHCb` 实验基于 `ROOT` 的存储——并将其与一个新颖的 `acceleration`（加速）引擎配对，该引擎基于关系数据库技术。

后者即 `DeLorean` 的“关系部分”，是通过从原始数据集中提取 `synopsis`（摘要/概要）或 `summary`（摘要）获得的。[图 6.4a](#9783110785951_014663.xhtml#b_9783110785968-006_fig_004) 说明了这一想法（其中我们将现有的 `ROOT` 存储称为“原始数据”）。摘要保存了我们稍后可以用来以非常审慎的方式访问“原始数据部分”的信息，即从潜在的海量数据集中仅挑选少数选定项目（参见 [图 6.4b](#9783110785951_014663.xhtml#b_9783110785968-006_fig_004)）。我们将在下文中详述可能的摘要实现。

**可行性与所需选择率** 为了使 `DeLorean` 架构可行，`synopsis` 的 `size`（大小）必须足够小，以免超出可用的存储预算。`DeLorean` 可以替代占用空间的剥离线，从存储空间角度来看，这通常使该概念具有可行性。

与在数据分析时访问原始数据存储所达到的 `selectivity`（选择率）相比，该方法要敏感得多。从数据存储中进行的每一次“拾取”都会产生相对较高的 `access latency`（访问延迟）。在实践中，这意味着只有当实际获取的存储事件 ≪ 1% 时，`DeLorean` 才比读取完整 (!) 数据集更廉价（参见 [图 6.4b](#9783110785951_014663.xhtml#b_9783110785968-006_fig_004)）。

**基于扫描的加速** 正如之前详述的，多维数据集倾向于基于扫描的处理。当数据集上的查询模式变化剧烈时（如 `LHCb` 的情况），这一点尤为正确。因此，`DeLorean` 的加速器主要基于扫描构建。

CERN 的软件框架严重依赖 `ROOT`，在我们当前的语境下，它为 `C++` 对象提供了一种持久化机制。也就是说，CERN 现有的存储层由序列化的 `C++` 对象组成。为了分析，这些对象被反序列化，然后移交给 `C++`/`Python` 代码进行处理。为了节省磁盘空间，`ROOT` 文件被积极压缩。

`ROOT` 的优势在于其与现有分析代码的无缝交互。随着时间的推移，一个主要用 `C++` 编写的庞大分析例程库已经演变而来。然而，要使该方法在超大规模下高效运行却颇具挑战。这主要有两个原因：

1.  `C++` 对象的（反）序列化导致磁盘和内存上出现相对复杂的数据结构。因此，该策略难以从现代硬件进步和深层内存层级中获益。相比之下，关系数据库引擎有意坚持非常严格且定义明确的数据模型——这是其卓越可扩展性的关键要素之一。
