

# IceCube 文件格式与数据组织

IceCube 合作组使用其自有的文件格式，该格式用于实验数据和模拟数据。这种标准化的文件格式是 **i3-file**，也用于并行文件处理。由于 IceCube 中的每次物理运行通常持续约八小时，因此会将该运行拆分为若干子运行，以加快整体处理速度。文件中的基本单元是 **帧**，每个帧恰好包含一个 IceCube 事件，对应约 10 ms 的 IceCube 数据。在 IceCube 中，事件由所谓的 **触发器** 形成，并以物理上有意义的方式组合来自 **数字光学模块（DOM）** 的信息（详见 [第 4.2.3 节](#9783110785951_010611.xhtml#b_9783110785968-004_s_002_s_003)）。文件中存在不同类型的帧，可分为两大类。

## 元数据帧

第一类是 **元数据**，通常每个文件仅需一次。

*   **I 帧**（也称为 **TrayInfo**）包含文件先前处理方式的信息。
*   **G 帧**（Geometry）包含基本探测器几何结构，特别是所有 DOM 的几何坐标。常规 IceCube 串的标称间距约为 125 m，但实际距离可能相差几米。填充阵列 **DeepCore** 具有密得多的串和 DOM 间距。精确了解 DOM 位置对于事件的准确重建至关重要。此处的 **重建** 是指一系列算法链。例如，要计算 **时间残差**，需要 DOM 位置作为输入（有关 IceCube 中事件属性重建的更多细节，请参见 [第 7.2 节](#9783110785951_015782.xhtml#b_9783110785968-007_s_002)）。引入 **G 帧** 是为了在实验建设期间更新几何结构，并允许细化位置信息。DOM 位置是相对于南极坐标网格（北向和东向坐标）测量的。在第一阶段，`x` 和 `y` 坐标由钻塔位置得出。`z` 坐标则通过在 DOM 部署期间利用压力传感器得出。部署后，利用 **闪光灯数据** 来校正几何结构的初始测量值。
*   **C 帧**（Calibration）包含光电倍增管的校准常数，后者是 DOM 的核心组件。
*   数据采集时的探测器状态保存在 **D 帧**（Detector）中，通常涵盖整个 8 小时运行。除其他信息外，该帧存储了数据采集期间哪些 DOM 和串处于激活状态。虽然 IceCube DOM 通常非常稳定，且大多数 DOM 故障发生在部署期间，但个别 DOM 或整串可能会暂时失效，导致其信息无法用于重建。

## 物理帧

单个事件的信息保存在 **P 帧** 和 **Q 帧** 中。

*   **Q 帧** 包含事件的记录波形。
*   **P 帧**（Physics）保存事件重建结果。可以对同一原始数据独立应用多种重建，从而产生多个 **P 帧**。在 **P 帧** 中，可以访问单个重建算法的中间结果。

## 数据级别

此外，IceCube 数据按 **级别** 进行层级组织。级别越高，数据越接近物理分析，且运行在其上的重建算法越多。

*   **Level 0**（常被称为 **触发级别**）旨在极快运行，旨在将任何类型的粒子相互作用与探测器中的噪声事件区分开来。这是通过应用专用触发算法实现的（详见 [第 4.2.3 节](#9783110785951_010611.xhtml#b_9783110785968-004_s_002_s_003)）。
*   **Level 1**（有时也称为 **滤波级别**）包含约 3 kHz 采集率的数据，主要由大气缪子主导。在此阶段，大气中微子（IceCube 探测到的第二丰富粒子类型）仅占约 10 到 20 mHz。通过使用选择不同能量和拓扑结构数据的专用滤波器，在此级别已可实现一定量的背景抑制。例如，**DeepCore 滤波器** 选择 100 GeV 以下、在探测器底部发生相互作用的事件。
*   **Level 2** 专用于全合作组范围的处理，此级别不丢弃任何事件。相反，应用重建算法，并针对每个滤波器处理事件。
*   **Level 3** 处理延续自 Level 2，变为特定工作组专用。Level 3 存在三条主要滤波链（**级联**、**缪子**、**低能量**），对通过一组滤波器子集的事件应用切选。此外，还应用新的重建算法，这些算法通常比 Level 1 应用的更复杂且消耗更多资源。在 Level 3（即 Level 2 重建的输出级别），数据率降至约 1 Hz。
*   **Level 4 及以上**：事件选择和处理变为分析专用，例如对数据进行滤波以获得中微子主导的样本。级别的编号以及清理过程的哪些阶段被归纳为一个级别，取决于分析者的个人偏好，本身不一定有深意。所应用的切选和使用的（机器学习）算法也是如此。然而，随着时间的推移，某些选择得以保留并确立下来，作为不同类型分析的输入。IceCube 的一个事件选择在第 8.3.1 节中介绍。

# 4.4 基于 GPU 的触发决策

*Holger Stevens*

**LHCb 实验** 目前正在进行升级。一项重大变革是采用纯软件触发。所有子探测器将以 40 MHz 的频率无触发读出，这将导致数据中心产生 40 Tbit/s 的输入数据率。该数据率将通过第一触发阶段的全 GPU 实现来降低。相应项目名为 **Allen**。LHCb 合作组将成为高能物理界首个拥有完整高吞吐量 GPU 触发器的实验。在触发的第一阶段，需要以最高速度解码来自子探测器的复杂原始数据，并为后续阶段做准备，在后续阶段中将推导粒子轨迹，这些轨迹是确定其产生顶点以及将粒子识别为缪子或强子的基础。由于多特蒙德参与了 **SciFi 径迹器** 的建设，初期重点放在了相应解码算法的开发上。

**Allen 项目** 是 LHCb 第一触发阶段（**HLT1**）的基于 GPU 的实现。触发器是 LHCb 整体数据获取系统的重要工具，如 [第 4.2.1 节](#9783110785951_010611.xhtml#b_9783110785968-004_s_002_s_001) 所述。触发器的总体必要性及第二阶段（**HLT2**）在 [第 4.1 节](#9783110785951_010611.xhtml#b_9783110785968-004_s_001) 和 [第 4.2.1 节](#9783110785951_010611.xhtml#b_9783110785968-004_s_002_s_001) 中已作介绍。为做出触发决策，将各子探测器的原始通道信息组合以构建轨迹和伪粒子。实验内的不同数据类型在 [第 4.3.1 节](#9783110785951_010611.xhtml#b_9783110785968-004_s_003_s_001) 中解释。本节首先介绍 Allen 的总体结构和任务并行化的不同方法。随后展示不同 GPU 在事件吞吐量方面的性能。
