
# 降低流失率的 AI/ML 解决方案

要有效降低流失率，我们必须首先了解导致流失的根本用户需求和痛点。流失并非随机发生，通常是由特定且可解决的问题驱动的。例如，如 [Figure 9-2](#c09.xhtml#c09-fig-0002) 所示，行业数据表明，订阅服务中超过一半的客户流失可归因于少数几个主要原因，例如入职引导无效、与客户建立的关系薄弱以及客户服务不佳。通过解决这些核心用户需求，我们可以制定更有效的留存策略。

## 2\. Define the AI/ML Application and Solution

在明确业务目标和用户需求后，下一步是概述具体的 AI 驱动解决方案。我们提议的应用是开发一个机器学习模型，在用户实际取消订阅之前预测哪些用户有高流失风险。

[Figure 9-3](#c09.xhtml#c09-fig-0003) 说明了这一概念。AI/ML 方法特别适合此场景，因为这是一个经典的预测问题（具体来说，是“流失”与“不流失”的分类任务）。我们可以利用丰富的历史用户数据，因为行为模式通常先于客户决定取消订阅。

## 3\. Identify Data Sources and Engineer Features: The Raw Materials

定义 AI 应用程序后，重点转移到其最关键的组成部分：数据。这一阶段是一个两部分的过程。首先，我们必须识别和收集所有潜在的“原材料”——可能包含预测信号的可用数据来源。然后，通过一种称为 *feature engineering* 的创造性分析过程，我们将这些原材料精炼成模型实际用于学习的高质量原料。

### Available Data

我们需要识别可能包含与流失相关信息的数据来源。这通常包括：

| CATEGORY | DATA POINTS |
| --- | --- |
| User Demographic | Age, location, subscription tier, profession, interests (if available) |
| User Activity | Course completion rates<br>Login frequency and recency<br>Time spent on the platform<br>Forum participation (posts, comments, replies)<br>Engagement with learning materials (downloads, views, quizzes taken)<br>Customer support interactions<br>Use of specific features |
| Subscription History | Start date, plan type, payment frequency, billing history, discounts used |
| Feedback Data | Survey responses, reviews, ratings |

### Feature Engineering

拥有这些原始数据只是第一步。然而，像原始“登录日期”这样的数据点并不总是以模型最有用的格式存在。下一个非常重要的步骤是 feature engineering，我们将原始数据转换为更有意义的信号，以提升模型性能。这就像厨师将基本食材变成美味酱汁一样。工程化特征的示例包括：

| FEATURE NAME | EXAMPLE VALUE | EXPLANATION |
| --- | --- | --- |
| Days Since Last Login | 15 | The user last accessed the platform fifteen days ago. |
| Average Courses Completed per Month | 1.5 | On average, the user completes 1.5 courses each month. |
| Number of Support Tickets in Last Thirty Days | 0 | The user has not opened any support tickets in the past month. |
| Forum Posts per Week | 0.2 | The user posts infrequently on the forum (e.g., about once every five weeks). |
| Subscription Length (in Months) | 24 | The user has been subscribed for two years (24 months). |
| Discount Usage Rate | 0.10 | The user has applied a discount code on 10% of their subscription payments. |
| Has User Given Feedback? (Boolean) | Yes | The user has submitted feedback through surveys or ratings. |

### The Product Manager's Role in This Stage

虽然数据识别和 feature engineering 具有高度技术性，但产品经理扮演着至关重要的协作角色：

*   **Provide domain expertise:** 你比任何人都更了解用户和产品。你的见解对于头脑风暴有意义的特征非常重要。例如，你可能会假设“完成入职引导清单的用户不太可能流失”——这一建议直接为模型带来了一个有价值的特征。
*   **Champion data quality and ethics:** 你负责确保所使用的数据是合乎伦理来源的，并考虑潜在的偏见。你将倡导高质量的数据，因为它是特征性能的基础。
*   **Help prioritize:** 鉴于可以工程化的特征数不胜数，你可以根据对用户行为的假设及其对模型潜在影响，帮助数据科学团队确定优先构建和测试哪些特征。

## 4\. Select the Metrics: Defining Success

在识别数据来源并工程化潜在特征后，下一步是定义如何衡量模型的成功。这需要将我们的业务目标（减少流失）转化为具体、可量化的模型性能指标。

### The Cost of Errors: Prioritizing What Matters

对于我们的流失预测模型，并非所有错误都同等重要。我们必须首先考虑 *false positive* 与 *false negative* 的相对成本。

*   A **false positive** would be incorrectly flagging a happy user as “high risk.” The cost is the resources spent on an unnecessary intervention (like sending them a discount they didn't need).
*   A **false negative** would be failing to identify a user who is actually about to churn. The cost is lost subscription revenue, which is significantly higher.

鉴于此，我们的主要目标是尽量减少 false negatives——我们想尽可能多地捕捉潜在的流失用户。这直接影响了我们对指标的选择。

这些指标（尤其是 Precision 和 Recall）之间的关系源自混淆矩阵的四个结果。[Figure 9-4](#c09.xhtml#c09-fig-0004) 提供了这些关键公式的视觉参考。

### Our Chosen Metrics

基于对错误成本的分析，我们将使用以下指标来评估模型：

*   **Primary Metric—Recall (Sensitivity):** 我们将优先考虑 Recall，以最大限度地提高模型正确识别的实际流失用户比例，从而尽量减少代价高昂的 false negatives。
*   **Secondary Metrics:**
    *   **Precision:** 虽然对于此问题来说不如 Recall 关键，但我们仍然需要相当精确，以避免在不必要的干预上浪费太多资源。
    *   **F1-Score:** F1-Score 将被监控，以通过计算 Precision 和 Recall 的调和平均数来提供性能的平衡度量，为我们提供一个跟踪模型整体健康状况的单一数字。
