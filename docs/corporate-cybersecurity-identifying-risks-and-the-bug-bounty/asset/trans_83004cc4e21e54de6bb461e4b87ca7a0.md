
*   软件工程师对修补漏洞的了解程度如何？毫不奇怪，漏洞将不得不由这些工程师来修复。如果他们不了解安全编码模型，就不可能提供足够的解决时间框架。

*   项目的统计数据是否已被分析？正如本书前面所述，从一开始就启动公开项目通常不是评估必要调整和建立一个像样项目的有效方式。虽然这并非不可能，但不推荐这样做。如果项目经理从私有项目开始，更容易熟悉工作流并确定 SLA 估算。安全从来不是短跑——而是马拉松。

虽然有多种方式来制定 SLA 协议，但以下是一些示例，可协助头脑风暴过程。

### 5.3.1 解决时间

关于漏洞赏金项目的解决时间存在误解。许多安全研究人员认为，错过解决时间代表着一个灾难性的项目，而纠正这些误解取决于项目经理。定义项目已知工程团队能对其负责的、关于漏洞解决的适当时间范围，是项目管理的重要组成部分。通过创建此类解决范围，项目经理在与研究人员保持透明方面拥有更大的灵活性。

作为补充说明，大多数漏洞赏金平台会自动填充平均解决时间、已解决的问题等。大多数研究人员可以从这些统计数据中推断出项目所付出的努力程度和责任感。然而，提供一个表格有助于研究人员将平均值与 SLA 进行比较，如果做得得当，它可以激发更多的项目参与度（见 [表 5.1](#c05.xhtml#c5-tbl-0001)）。

[**表 5.1**](#c05.xhtml#rc5-tbl-0001) 已识别漏洞的解决时间。

| **漏洞等级** | **解决时间** |
| --- | --- |
| 严重 | 2–7 天 |
| 高危 | 7–14 天 |
| 中危 | 14–30 天 |
| 低危 | 尽力而为 |
| 信息类 | 不适用 |

最好在企业能够妥善建立 SLA 且无需猜测时，直接在项目中定义 SLA。漏洞脱离团队视野的情况可能发生，错过 SLA 可能损害项目声誉，但这不应成为项目经理的阻碍因素。

### 5.3.2 分流时间

分流时间不同之处在于，如果项目决定采用托管服务模式，大多数漏洞赏金平台可以代表研究人员管理分流时间。尽管如此，如果建立了独立项目，或者企业必须建立自己的解决标准，[表 5.2](#c05.xhtml#c5-tbl-0002) 显示了可能的分流时间示例。除非漏洞赏金项目规模极大，否则分流通常不需要很宽的范围。验证漏洞通常不需要那么长时间。该过程中最困难的部分是解决，因为它需要多方协作。

[**表 5.2**](#c05.xhtml#rc5-tbl-0002) 已识别漏洞的分流时间。

| **漏洞等级** | **解决时间** |
| --- | --- |
| 严重 | 2 天 |
| 高危 | 5 天 |
| 中危 | 7 天 |
| 低危 | 14 天 |
| 信息类 | 不适用 |

所有这些流程的时间范围应根据项目需求进行调整。

# 6 项目配置

## 6.1 了解选项

配置项目的时刻终于到了。本章重点介绍所有可用的各种选项。实事求是地说，分步设置过程不太可能像描述所有可用选项的章节那样有用。为了最好地为企业环境配置项目，了解所有可用的各种技术将使漏洞赏金项目更加成功。许多设置项目的工程师会偏离触手可及的选项。具体来说，本章的目的不是专注于某一个众包平台，而是评估选项，以充分准备项目经理进行更成功的设置。尽管如此，Bugcrowd 和 HackerOne 之间的各种选项仍将呈现。

## 6.2 Bugcrowd

### 6.2.1 创建项目

当首次在 Bugcrowd 平台注册时，项目经理可以选择他们想要使用的项目或服务。在我们的示例中，我们将在漏洞披露和漏洞赏金项目之间进行选择。首先，项目经理将点击蓝色的“Start now”（立即开始）按钮，这会弹出给定的选项列表。

1.  点击“Start now”（[图 6.1](#c06.xhtml#c6-fig-0001)）

    [**图 6.1**](#c06.xhtml#rc6-fig-0001) Bugcrowd“Start now”按钮。

    ![Figure 6.2 Bugcrowd: selection “Bug Bounty Program”.](images/c06f002.png)

    [**图 6.2**](#c06.xhtml#rc6-fig-0002) Bugcrowd：选择“Bug Bounty Program”。

4.  当项目向导出现时，它将显示所有各个步骤。总共有 9 步。第 1 步侧重于命名项目。项目名称应该是项目经理将负责的公司的名称（[图 6.3](#c06.xhtml#c6-fig-0003)）。
