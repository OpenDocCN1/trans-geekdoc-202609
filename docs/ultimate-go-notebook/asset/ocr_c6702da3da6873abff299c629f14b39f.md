The question now becomes: Why can't methods implemented with pointer receivers be attached to values of type T? What is the integrity issue?

One reason is because I can't guarantee that every value of type T is addressable. If a value doesn't have an address, it can't be shared.

# Listing 4.31

```
type duration int

func (d *duration) notify() {
    fmt.Println("Sending Notification in", *d)
}

func main() {
    duration(42).notify()
}

Compiler Error:
cannot call pointer method on duration(42)
cannot take the address of duration(42)
```

In this example, the value of 42 is a constant of kind int. Even though the value is converted into a value of type duration, it's not stored inside a variable. This means the value is never on the stack or heap. There isn't an address. Constants only live at compile time.

The second reason is the bigger reason. The compiler is telling me that I am not allowed to use value semantics. In other words, I am forced to share the value with the interface since it's not safe to make a copy of a value that a pointer points to. If I chose to implement the method with pointer semantics, I am stating that a value of this type isn't safe to be copied.

# Listing 4.32

```
func main() {
    u := user("Bill", "bill@email.com")
    sendNotification(&u)
}
```

To fix the compiler message, I must use pointer semantics on the call to the polymorphic function and share u. The answer is not to change the method to use value semantics.

# 4.12 Slice of Interface

When I declare a slice of an interface type, I'm capable of grouping different concrete values together based on what they can do. This is why Go doesn't need the concept of sub-typing. It's not about a common DNA, it's about a common behavior.
