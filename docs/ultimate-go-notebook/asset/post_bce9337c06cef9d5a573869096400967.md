
# Chapter 2: Language Mechanics

In this chapter, I will learn about the basic language mechanics, idioms, and guidelines around types and memory management. I will learn the data semantics behind the built-in types.

## 2.1 Built-in Types

Types provide integrity and readability by asking 2 questions:

- What is the amount of memory to allocate? (e.g. 1, 2, 4, 8 bytes)
- What does memory represent? (e.g. int, uint, bool...)

Types can be specific to a precision as int32 or int64:

- uint8 represents an unsigned integer with 1 byte of allocation
- int32 represents a signed integer with 4 bytes of allocation

When I declare a type using a non-precision based type (unit, int) the size of the value is based on the architecture used to build the program:

- 32 bit arch: int represents a signed int at 4 bytes of memory allocation
- 64 bit arch: int represents a signed int at 8 bytes of memory allocation

## 2.2 Word Size

The word size represents the amount of memory allocation required to store integers and pointers for a given architecture. For example:

- 32 bit arch: word size is 4 bytes of memory allocation
- 64 bit arch: word size is 8 bytes of memory allocation

This is important because Go has internal data structures (maps, channels, slices, interfaces, and functions) that store integers and pointers. The size of these data structures will be based on the architecture used to build the program.

In Go, the amount of memory allocated for a value of type int, a pointer, or a value will always be the same on the same architecture.

## 2.3 Zero Value Concept

Every single value I construct in Go is initialized at least to its zero value state unless I specify the initialization value at construction. The zero value is the setting of bit in every byte to zero.

This is done for data integrity and it's not free. It takes time to push electrons through the machine to reset those bits, but I should always take integrity over performance.

# Listing 2.1

| Type | Zero Value |
|---|---|
| Boolean | false |
| Integer | 0 |
| Float | 0 |
| Complex | 0 |
| String | "" (empty) |
| Pointer | nil |

## 2.4 Declare and Initialize

The keyword var can be used to construct values to their zero value state for all types.

# Listing 2.2

```go
var a int
var b string
var c float64
var d bool

fmt.Printf("var int %t %+v\n\n", a, a)
fmt.Printf("var string %t %+v\n\n", b, b)
fmt.Printf("var float64 %t %+v\n\n", c, c)
fmt.Printf("var bool %t %+v\n\n", d, d)

Output:
var a int     int [0]
var b string string[]
var c float64 float64 [0]
var d bool    bool [false]
```

Strings use the UTF8 character set, but are really just a collection of bytes.

A string is a two-word internal data structure in:

- The first word represents a pointer to a backing array of bytes
- The second word represents the length or the number of bytes in the backing array
- If the string is set to its zero value state, the first word is nil and the second word is 0.

Using the short variable declaration operator, I can declare, construct, and initialize a value all at the same time.

```go
aa := 10          // int [10]
bb := "hello"     // string [hello]
cc := 3.14159     // float64 [3.14159]
dd := true         // bool [true]
```

```go
fmt.Printf("aa := %v %T %+v\n", aa, aa)
fmt.Printf("bb := %v %T %+v\n", bb, bb)
fmt.Printf("cc := %v %T %+v\n", cc, cc)
fmt.Printf("dd := %v %T %+v\n", dd, dd)
```

```go
Output:
aa := 10          int [10]
bb := "hello"     string [hello]
cc := 3.14159     float64 [3.14159]
dd := true         bool [true]
```

## 2.5 Conversion with Casting

Go does not have casting, but conversion. Instead of telling the compiler to map a set of bytes to a different representation, the bytes need to be copied to a new memory location for the new representation.

# Listing 2.4

```go
aaa := int32(10)
fmt.Printf("aaa := int32(10) %T %+v\n", aaa, aaa)
```

```go
Output:
aaa := int32(10) int32 [10]
```

Go does have a package in the standard library called unsafe if I need to perform an actual casting operation. I would really avoid that and be honest with myself why I am considering using it. Performing a conversion provides the highest level of integrity for these types of operations.

## 2.7 Padding and Alignment

How much memory is allocated for a value of type?

# Listing 2.9

```go
type example struct {
    flag    bool
    counter int16
    p       float32
}
```

A bool is 1 byte, int16 is 2 bytes, and float32 is 4 bytes. Add that all together I get 7 bytes. However, the actual answer is 8 bytes because there is a padding value sitting between the flag and counter fields for the reason of alignment.

# Figure 2.1

| Flag | Counter | Pi |
|---|---|---|
| 0 | 2 | 8 |

The idea of alignment is to allow the hardware to read memory more efficiently by placing memory on specific boundaries. The compiler takes care of the alignment boundary so I don't have to. Depending on the size of particular field and its placement in the struct, Go determines the padding.

# Listing 2.10

```go
type example2 struct {
    flag    bool
    counter int16
    flag2 bool
    p       float32
}
```

In this example, I’ve added a new field called flag2 between the counter and pi fields. This causes more padding inside the struct.

# Listing 2.11

```go
type example2 struct {
    flag bool      // 0x00010020 <- Starting Address
    byte          // 0x00010021 - 1 byte padding
    counter int16  // 0x00010022 - 2 byte alignment
    flag2 byte     // 0x00010024 - 1 byte alignment
    byte          // 0x00010025 - 1 byte padding
    byte          // 0x00010026 - 1 byte padding
    byte          // 0x00010027 - 1 byte padding
    pi float32    // 0x00010028 - 4 byte alignment
}
```

This is how alignment and padding play out a value of type example2 starts at address 0xc0010020. The flag field represents the starting address and is only 1 byte in size. Since the counter field requires 2 bytes of allocation, it must be placed in memory on a 2-byte alignment, meaning it needs to fall on an address that is a multiple of 2. This requires the counter field to start at address 0x0010022. This creates a 1-byte gap between the flag and counter fields.

# Figure 2.2

| Flag | | Counter | | Flag2 | | | | | 12 |
|---|---|---|---|---|---|---|---|---|---|
| 0 | 1 | | 4 | 5 | 6 | 7 | 8 | | 12 |

The flag2 field is a bool and can fall at the next address 0xc0010024. The final field is pi and requires 4 bytes of allocation as it needs to fall on a 4-byte alignment. The next address for a 4 byte value is at 0xc0010028. That means 3 padding bytes are needed to maintain a proper alignment. This results in a value of type example2 requiring 12 bytes of total memory allocation.

The largest field in a struct represents the alignment boundary for the entire struct. In this case, the largest field is 4 bytes so the starting address for this struct value must be a multiple of 4. I can see the address 0xc0010020 is a multiple of 4.

If I need to minimize the amount of padding bytes, I must lay out the fields from highest to lowest allocation. This will push any necessary padding bytes down to the bottom of the struct and reduce the total number of padding bytes necessary.

# Listing 2.12

```go
type example struct {
    pi float32    // 0x00010020 <- Starting Address
    counter int16  // 0x00010024 - 2 byte alignment
    flag bool      // 0x00010026 - 1 byte alignment
    flag2 bool     // 0x00010027 - 1 byte alignment
}
```

After the reordering of the fields, the struct value only requires 8 bytes of allocation.
