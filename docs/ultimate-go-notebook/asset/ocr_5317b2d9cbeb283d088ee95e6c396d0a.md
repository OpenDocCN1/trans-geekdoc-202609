If it's safe to be copied, start with value semantics. If it's not safe for copying or that's not even clear, start with pointer semantics.

After some time working with a new data type, the data semantic could become self-evident and refactoring the data semantic is what I want to do. Don’t become paralyzed if it’s not self-evident from the start.

# Listing 4.8

```
type Time struct {
  sec int64
  nsec int32
  loc *Location
}
```

Here is the Time struct from the package. If I was being asked to implement the API for this data structure, what should I choose, value or pointer semantics?

Sometimes I can ask these questions:

+   - Does a change in the data completely create a new data point?
- Is the data specific to a context, and are mutations isolated to that context?
- Should there only be one instance of this data?

If I’m looking at an existing code base and I want to know what data semantic was chosen, look for a factory function. The return type of a factory function should dictate the data semantics.

# Listing 4.9

```
func Now() Time {
  sec, nsec := unixToInternal(nsec)
  return Time{sec + nsec, Local}
}
```

This is the function for constructing Time values. Look at the return, it’s using value semantics. This tells me that I should be using value semantics for Time values which means every function gets its own copy of a Time value and fields in a struct should be declared as values of type Time.
