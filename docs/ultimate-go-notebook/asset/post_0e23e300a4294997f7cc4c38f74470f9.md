```go

```go

I can then assign the MoveLocker variable ml to the Mover variable m. This is possible because I'm not assigning the interface value ml but the concrete value stored inside of ml is a bike value. This assignment however is not valid.

# Listing 5.31

```

cannot use m (type Mover) as type MoveLocker in assignment:
Mover does not implement MoveLocker (missing Lock method)
```

I can't assign the Mover variable m back to the MoveLocker variable ml because the compiler can only guarantee the concrete value stored inside of m knows how to Move. It doesn't know at compile time if the concrete value also knows how to Lock and Unlock.

## 5.8 Type assertions

With all that said, there is a way at runtime to test if the assignment is legal and then make it happen. That is by using a type assertion.

# Listing 5.32

```go
b := m.(bike)
ml = b
```

A type assertion allows me at runtime to ask a question, is there a value of the given type stored inside the interface. I see that with the m.(bike) syntax. In this case, I am asking if there is a bike value stored inside of m at the moment the code is executed. If there is, the variable b is given a copy of the bike value stored. Then the copy can be copied inside of the ml interface variable.

If there isn't a bike value stored inside of the interface value, then the program panics. I wait if there absolutely should have been a bike value stored. What if there is a chance it isn't and that is valid? Then I need the second form of the type assertion.

# Listing 5.33

```go
b, ok := m.(bike)
```

In this form, if ok is true, there is a bike value stored inside of the interface. If ok is false, then there isn't and the program does not panic. The variable b however is still of type bike, but it is set to its zero value state.

```go
func main() {
	rand.Seed(time.Now().UnixNano())

	mvs := []fmt.Stringer{

Since it's possible it's not of type Cloud, the second form of the type assertion is critical here.

## 5.9 Interface Pollution

I spot interface pollution from a mile away. It mostly comes from the fact that people are designing software with interfaces instead of discovering them. I should design a concrete solution to the problem first. Then I can discover where the program needs to be polymorphic, if at all.

These things I've heard from other developers.

"I'm using interfaces because we have to use interfaces"

No. We don't have to use interfaces. We use interfaces when it's practical and reasonable to do so. There is a cost of using interfaces: a level of indirection and allocation when we store concrete values inside of them. Unless the cost of the allocation is worth what I'm gaining by decoupling, I shouldn't use interfaces.

"I need to be able to test my code so I need to use interfaces"

No. I must design my API for the first user, not my test. If the API is not testable, I should consider if it's usable. There are different layers of API's as well. The lower level unexported API's can and should focus on testability. The higher level exported API's need to focus on usability.

Functions that accept raw data in and return raw data out are most testable. Separate the data transformation from where the data comes from and where it is going. This is a refactoring exercise I need to perform during the engineering coding cycle.

Below is an example that creates interface pollution by improperly using an interface when one is not needed.

# Listing 5.35

```go
type Server interface {
    Start() error
    Stop() error
    Wait() error
}
```

The Server interface defines a contract for TCP servers. The problem here is I don't need a contract, I need an implementation. There will be only one implementation as well, especially since I am the one implementing it. I do not need someone else to implement this.

## 5.10 Interface Ownership

One thing that is different Go from other languages is the idea of ownership.

# Listing 5.36

```go
package pubsub

type PubSub struct {
    host string
}

func New(host string) *PubSub {
    return &PubSub{
        host: host,
    }
}

func (ps *PubSub) Publish(key string, v interface{}) error {
    // implementation
    return nil
}

func (ps *PubSub) Subscribe(key string) error {
    // implementation
    return nil
}
```

I've just implemented a new API that provides a concrete implementation. There are no interfaces being provided What if the application developer wanting to use this API needs to mock this implementation?

# Listing 5.37

```go
package main

type publisher interface {
    Publish(key string, v interface{}) error
    Subscribe(key string) error
}

type mock struct{}

func (m *mock) Publish(key string, v interface{}) error {
    // implementation
    return nil
}

func (m *mock) Subscribe(key string) error {
    // implementation
    return nil
}
```

The code in the main package is declaring an interface. This interface represents the API that the application is using from the pubsub package. The developer has implemented their own pubsub implementation for testing.

# Listing 5.38

```go
func main() {
    pubs := []publisher{
        pubsub.New("localhost"),
        &mock(),
    }
    for _, p := range pubs {
        p.Publish("key", "value")
        p.Subscribe("key")
    }
}
```
