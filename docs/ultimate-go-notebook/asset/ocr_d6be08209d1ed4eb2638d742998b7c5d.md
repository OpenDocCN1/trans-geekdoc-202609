If the parent Goroutine receives the timeout signal, it walks away. In this situation, it can't inform the child Goroutine that it won't be around to receive its signal. This is why it's important for the work channel to be a buffer of 1. The child Goroutine needs to be able to send its signal, whether or not the parent Goroutine is around to receive it. If a non-buffered channel is used, the child Goroutine will block forever and become a memory leak.

# 6.11.7 Fan Out/In Semaphore

The fan out/in semaphore pattern provides a mechanic to control the number of Goroutines executing out at any time while creating a unique Goroutine for each piece of work.

# Listing 6.41

```
func fanOutSem() {
	children := 2000
	ch := make(chan string,0)
	g := runtime.GOMAXPROCS(0)
	sem := make(chan bool, g)

for c := 0; c < g; c++ {
	go func(child int) {
		time := <-ch
		time = time.Duration(rand.Intn(2000)) * time.Millisecond
		time.Sleep(time)
		ch <- "data"
		fmt.Println("child : sent signal :", child)
		<-sem
	}
}

for children > 0 {
	d := <-ch
	children--
	fmt.Println("parent : recv'd signal :", d, child)
}

time.Sleep(time.Second)
fmt.Println("all Goroutines have finished their work ---")
}
```

At the start of the function, a channel with a buffer size of 2000 is set. This is the same thing we need in the original fan out/in pattern. One buffer for each child Goroutine that will be created. Like, the pooling pattern, the use of the GOMAXPROCS function is used to determine how many of the 2000 child Goroutines will be allowed to execute their work at any given time.

With g configured, a second buffered channel is constructed next with a buffer sized to the number of child Goroutines that can execute their work at the same time. This is the semaphore that will control the number of child Goroutines
