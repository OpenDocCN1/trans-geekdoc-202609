and attempt to execute all the Runnable Threads within that period of time. No problem: take the scheduling period and divide it by the number of Threads that need to execute.

As an example, if you define your scheduler period to 1000ms (1 second) and you have 10 Threads, then each thread gets 100ms. If you have 100 Threads, each Thread gets 10ms. However, what happens when you have 1000 Threads? Giving each Thread a slice of 1ms doesn't work because the percentage of time you're spending in context switches will be significantly related to the amount of time you're spending on application work.

What you need is to set a limit on how small a given time slice can be. In the last scenario, if the minimum time slice was 10ms and you have 1000 Threads, the scheduler period needs to increase to 10000ms (10 seconds). What if there were 10,000 Threads, now you are looking at a scheduler period of 100000ms (100 seconds). At 10,000 threads, with a minimal time slice of 10ms, it takes 100 seconds for all the Threads to run once in this simple example if Thread uses its full slice.

Be aware this is a very simple view of the world. There are more things that need to be considered and handled by the scheduler when making scheduling decisions discussed in this post.

https://blog.acolyer.org/2016/04/26/the-linux-scheduler-a-decade-of-wasted-cores/

You control the number of Threads you use in your application. When there are more Threads to consider, and I/O-Bound work happening, there is more chaos and nondeterministic behavior. Threads take longer to schedule and execute.

This is why the rule of the game is "Less is More". Less Threads in a Runnable state means less overhead and more time each Thread gets over time. More Threads in a Runnable state mean less time each Thread gets over time. More means less of your work is getting done over time as well.
