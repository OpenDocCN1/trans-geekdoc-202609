**图 8.2。** 一个空的带缓冲通道。

在带缓冲通道上的发送操作会在队列尾部插入一个元素，而接收操作则会从队列头部移除一个元素。如果通道已满，发送操作会阻塞其所在的 goroutine，直到另一个 goroutine 执行接收操作腾出空间。反之，如果通道为空，接收操作会阻塞，直到另一个 goroutine 发送一个值。

我们可以在此通道上发送多达三个值而不会导致 goroutine 阻塞：

```
ch <- "A"
ch <- "B"
ch <- "C"
```

此时，通道已满（图 8.3），第四条发送语句将会阻塞。

![一个满的带缓冲通道。](graphics/fullchannel.png)

**图 8.3。** 一个满的带缓冲通道。

如果我们接收一个值，

```
fmt.Println(<-ch) // "A"
```

通道既不满也不空（图 8.4），因此发送操作或接收操作都可以在不阻塞的情况下进行。通过这种方式，通道的缓冲解耦了发送和接收的 goroutine。

![一个部分填满的带缓冲通道。](graphics/nonemptychannel.png)

**图 8.4。** 一个部分填满的带缓冲通道。

在极少数程序需要知道通道缓冲容量的情况下，可以通过调用内置的 `cap` 函数获得：

```
fmt.Println(cap(ch)) // "3"
```

当应用于通道时，内置的 `len` 函数返回当前缓冲的元素数量。由于在并发程序中，该信息一旦获取很可能就已过时，因此其价值有限，但在故障诊断或性能优化时可能会有用。

```
fmt.Println(len(ch)) // "2"
```

再执行两次接收操作后，通道再次变空，第四次接收将会阻塞：

```
fmt.Println(<-ch) // "B"
fmt.Println(<-ch) // "C"
```

在本例中，发送和接收操作均由同一个 goroutine 执行，但在实际程序中，它们通常由不同的 goroutine 执行。新手有时会被带缓冲通道简洁优雅的语法所吸引，试图在单个 goroutine 内将其用作队列，但这是一个错误。通道与 goroutine 调度有着深层联系，如果没有另一个 goroutine 从通道接收，发送者——甚至整个程序——都面临永远阻塞的风险。如果你只需要一个简单的队列，请使用切片来实现。

下面的示例展示了带缓冲通道的一个应用。它向三个*镜像站点*发起并行请求，即功能等价但地理位置分布不同的服务器。它将响应发送到一个带缓冲通道，然后接收并仅返回第一个响应，也就是最快到达的那个。因此 `mirroredQuery()` 甚至在两个较慢的服务器响应之前就已返回结果。（顺便提一下，多个 goroutine 并发向同一通道发送值，如本例所示，或从同一通道接收值，都是很正常的情况。）

[点击此处查看代码图像](#ch08_images.html#id233pro01_r)

```
func mirroredQuery() string {
    responses := make(chan string, 3)
    go func() { responses <- request("asia.gopl.io") }()
    go func() { responses <- request("europe.gopl.io") }()
    go func() { responses <- request("americas.gopl.io") }()
    return <-responses // 返回最快的响应
}

func request(hostname string) (response string) { /* ... */ }
```

如果我们使用无缓冲通道，那两个较慢的 goroutine 会因试图在一个永远不会有 goroutine 接收的通道上发送响应而卡住。这种情况称为 *goroutine 泄漏*，属于 Bug。与垃圾变量不同，泄漏的 goroutine 不会被自动回收，因此确保 goroutine 在不再需要时自行终止非常重要。

在无缓冲和带缓冲通道之间进行选择，以及带缓冲通道容量的选择，都可能影响程序的正确性。无缓冲通道提供更强的同步保证，因为每个发送操作都与其对应的接收操作同步；而带缓冲通道则将这些操作解耦。此外，当我们知道将要发送到通道的值的数量上限时，创建一个该大小的带缓冲通道并在第一个值被接收前完成所有发送，这并不罕见。未能分配足够的缓冲容量会导致程序死锁。

通道缓冲也可能影响程序性能。想象蛋糕店里有三位厨师，分别负责烘焙、抹糖霜和装饰，每位厨师完成一个蛋糕后将其传递给流水线上的下一位。在空间狭小的厨房里，完成蛋糕的厨师必须等待下一位厨师准备好接收；这种会合类似于无缓冲通道上的通信。

如果每位厨师之间有一个蛋糕的放置空间，厨师可以将完成的蛋糕放在那里，然后立即开始制作下一个；这类似于容量为 1 的带缓冲通道。只要厨师们的平均工作速率大致相同，大多数交接都能快速进行，从而平滑各自速率的瞬时差异。厨师之间更大的空间——更大的缓冲——可以在不停滞流水线的情况下平滑更大的瞬时速率变化，例如某位厨师短暂休息后又赶工补进度的情况。

另一方面，如果流水线的前一阶段持续比后一阶段快，它们之间的缓冲区大部分时间将处于满载状态。反之，如果后一阶段更快，缓冲区通常将是空的。在这种情况下，缓冲区不提供任何益处。

流水线隐喻对于理解通道和 goroutine 很有帮助。例如，如果第二阶段更复杂，单个厨师可能无法跟上第一位厨师的供应速度，也无法满足第三位厨师的需求。为了解决这个问题，我们可以雇佣另一位厨师协助第二阶段，执行相同的任务但独立工作。这类似于创建另一个通过相同通道通信的 goroutine。

由于篇幅限制，此处不展示代码，但 `gopl.io/ch8/cake` 包模拟了这个蛋糕店，包含若干可调参数。其中包含了上述几种场景的基准测试（§11.4）。
