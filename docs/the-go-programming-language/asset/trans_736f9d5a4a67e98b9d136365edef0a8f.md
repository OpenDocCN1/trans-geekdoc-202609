
# 两种测试方法互补

黑盒测试通常更健壮，随着软件演进需要的更新较少。它们还有助于测试作者从包客户端的角度思考问题，并能揭示 API 设计中的缺陷。相比之下，白盒测试能为实现中较棘手的部分提供更详细的覆盖。

我们已经看过两种测试的示例。`TestIsPalindrome` 仅调用导出函数 `IsPalindrome()`，因此是黑盒测试。`TestEcho` 调用了未导出的 `echo()` 函数并更新了未导出的全局变量 `out`，因此是白盒测试。

## 开发 `TestEcho` 时的技巧

在开发 `TestEcho` 时，我们修改了 `echo()` 函数，使其在写入输出时使用包级变量 `out`，以便测试能用一个替代实现替换标准输出，该实现会记录数据供后续检查。使用相同技术，我们可以用易于测试的“伪”实现替换生产代码的其他部分。伪实现的优势在于：配置更简单、行为更可预测、更可靠、更易观察。它们还能避免不良副作用，如更新生产数据库或扣款信用卡。

## 配额检查逻辑示例

下面的代码展示了一个为用户提供网络存储的 Web 服务中的配额检查逻辑。当用户超过其配额的 90% 时，系统会发送警告邮件。

[点击此处查看代码图片](#ch11_images.html#id311pro01_r)

gopl.io/ch11/storage1

```
package storage

import (
    "fmt"
    "log"
    "net/smtp"
)

var usage = make(map[string]int64)

func bytesInUse(username string) int64 {
    return usage[username]
}

// Email sender configuration.
// NOTE: never put passwords in source code!
const sender = "notifications@example.com"
const password = "correcthorsebatterystaple"
const hostname = "smtp.example.com"

const template = `Warning: you are using %d bytes of storage,
%d%% of your quota.`

func CheckQuota(username string) {
    used := bytesInUse(username)
    const quota = 1000000000 // 1GB
    percent := 100 * used / quota
    if percent < 90 {
        return // OK
    }
    msg := fmt.Sprintf(template, used, percent)
    auth := smtp.PlainAuth("", sender, password, hostname)
    err := smtp.SendMail(hostname+":587", auth, sender,
        []string{username}, []byte(msg))
    if err != nil {
        log.Printf("smtp.SendMail(%s) failed: %s", username, err)
    }
}
```

我们想测试它，但不希望测试发送真实邮件。因此我们将邮件逻辑移入自己的函数，并将该函数存储在一个未导出的包级变量 `notifyUser` 中。

```
var notifyUser = func(username, msg string) {
    auth := smtp.PlainAuth("", sender, password, hostname)
    err := smtp.SendMail(hostname+":587", auth, sender,
        []string{username}, []byte(msg))
    if err != nil {
        log.Printf("smtp.SendEmail(%s) failed: %s", username, err)
    }
}

func CheckQuota(username string) {
    used := bytesInUse(username)
    const quota = 1000000000 // 1GB
    percent := 100 * used / quota
    if percent < 90 {
        return // OK
    }
    msg := fmt.Sprintf(template, used, percent)
    notifyUser(username, msg)
}
```

现在我们可以编写一个测试，用一个简单的伪通知机制替代发送真实邮件。这个机制会记录被通知的用户和消息内容。

[点击此处查看代码图片](#ch11_images.html#id312pro02_r)

```
package storage

import (
    "strings"
    "testing"
)

func TestCheckQuotaNotifiesUser(t *testing.T) {
    var notifiedUser, notifiedMsg string
    notifyUser = func(user, msg string) {
        notifiedUser, notifiedMsg = user, msg
    }

    const user = "joe@example.org"
    usage[user] = 980000000 // simulate a 980MB-used condition

    CheckQuota(user)
    if notifiedUser == "" && notifiedMsg == "" {
        t.Fatalf("notifyUser not called")
    }
    if notifiedUser != user {
        t.Errorf("wrong user (%s) notified, want %s",
            notifiedUser, user)
    }
    const wantSubstring = "98% of your quota"
    if !strings.Contains(notifiedMsg, wantSubstring) {
        t.Errorf("unexpected notification message <<%s>>, "+
            "want substring %q", notifiedMsg, wantSubstring)
    }
}
```

存在一个问题：测试函数返回后，`CheckQuota` 不再按预期工作，因为它仍在使用测试的 `notifyUser` 伪实现。（更新全局变量时总存在这种风险。）我们必须修改测试以恢复之前的值，使后续测试不受影响，且必须在所有执行路径上（包括测试失败和 panic）都执行恢复。这自然用到了 `defer`。

[点击此处查看代码图片](#ch11_images.html#id313pro01_r)

```
func TestCheckQuotaNotifiesUser(t *testing.T) {
    // Save and restore original notifyUser.
    saved := notifyUser
    defer func() { notifyUser = saved }()

    // Install the test's fake notifyUser.
    var notifiedUser, notifiedMsg string
    notifyUser = func(user, msg string) {
        notifiedUser, notifiedMsg = user, msg
    }
    // ...rest of test...
}
```

此模式可用于临时保存和恢复各种全局变量，包括命令行标志、调试选项和性能参数；安装和移除钩子，使生产代码在发生有趣事件时调用测试代码；以及诱导生产代码进入罕见但重要的状态，如超时、错误，甚至并发活动的特定交错时序。

仅因为 `go test` 通常不并发运行多个测试，以这种方式使用全局变量才是安全的。

# 11.2.4 外部测试包

考虑包 `net/url`（提供 URL 解析器）和 `net/http`（提供 Web 服务器和 HTTP 客户端库）。正如预期，高层包 `net/http` 依赖低层包 `net/url`。然而，`net/url` 中的一个测试是演示 URL 与 HTTP 客户端库交互的示例。换句话说，低层包的测试导入了高层包。

![A test of net/url depends on net/http.](graphics/testcycle.png)

**图 11.1.** `net/url` 的测试依赖 `net/http`。

如果在 `net/url` 包中声明此测试函数，将在包导入图中形成循环（如图 11.1 中的向上箭头所示），但正如第 10.1 节所述，Go 规范禁止导入循环。

我们通过在*外部测试包*中声明测试函数来解决此问题，即在 `net/url` 目录下的文件中，其包声明为 `package url_test`。额外的后缀 `_test` 向 `go test` 发出信号：它应构建一个仅包含这些文件的额外包并运行其测试。可以将此外部测试包视为导入路径为 `net/url_test` 的包，但它不能在此名称或任何其他名称下被导入。

因为外部测试位于单独的包中，它们可以导入也依赖被测包的辅助包；包内测试无法做到这一点。从设计层级来看，外部测试包在逻辑上高于它所依赖的两个包，如图 11.2 所示。

![External test packages break dependency cycles.](graphics/externaltest.png)

**图 11.2.** 外部测试包打破依赖循环。

通过避免导入循环，外部测试包允许测试（特别是*集成测试*，即测试多个组件的交互）自由导入其他包，就像应用程序一样。
