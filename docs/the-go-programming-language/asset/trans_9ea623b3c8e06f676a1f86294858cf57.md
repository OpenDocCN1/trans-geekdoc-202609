
`go get`创建的目录是远程仓库的真实客户端，而不仅仅是文件副本，因此你可以使用版本控制命令查看本地编辑的差异，或更新到不同的版本。例如，`golang.org/x/net`目录是一个Git客户端：

[单击此处查看代码图像](#ch10_images.html#id293pro01_r)

```
$ cd $GOPATH/src/golang.org/x/net
$ git remote -v
origin  https://go.googlesource.com/net (fetch)
origin  https://go.googlesource.com/net (push)
```

注意，包导入路径中的表观域名`golang.org`与实际Git服务器的域名`go.googlesource.com`不同。这是`go`工具的一项功能，它允许包在导入路径中使用自定义域名，同时由通用服务（如`googlesource.com`或`github.com`）托管。`https://golang.org/x/net/html`下的HTML页面包含如下所示的元数据，可将`go`工具重定向到实际托管网站的Git仓库：

[单击此处查看代码图像](#ch10_images.html#id293pro02_r)

```
$ go build gopl.io/ch1/fetch
$ ./fetch https://golang.org/x/net/html | grep go-import
<meta name="go-import"
      content="golang.org/x/net git https://go.googlesource.com/net">
```

如果指定`-u`标志，`go get`将确保其访问的所有包（包括依赖项）在构建和安装前都更新到最新版本。如果没有该标志，本地已存在的包将不会更新。

`go get -u`命令通常会获取每个包的最新版本，这在入门时很方便，但对于已部署的项目可能不合适，因为精确控制依赖项对于发布卫生至关重要。通常的解决方案是*vendor*代码，即制作所有必要依赖项的持久本地副本，并谨慎、刻意地更新此副本。在Go 1.5之前，这需要更改这些包的导入路径，因此我们的`golang.org/x/net/html`副本将变为`gopl.io/vendor/golang.org/x/net/html`。更新版本的`go`工具直接支持vendoring，尽管此处没有空间展示细节。请参阅`go help gopath`命令输出中的*Vendor Directories*。

**练习 10.3：** 使用`fetch http://gopl.io/ch1/helloworld?go-get=1`，找出哪个服务托管了本书的代码示例。（来自`go get`的HTTP请求包含`go-get`参数，以便服务器将其与普通浏览器请求区分开。）

### 10.7.3 构建包

`go build`命令编译每个参数包。如果包是库，则丢弃结果；这仅检查包是否没有编译错误。如果包名为`main`，`go build`将调用链接器在当前目录中创建可执行文件；可执行文件的名称取自包导入路径的最后一段。

由于每个目录包含一个包，每个可执行程序（或Unix术语中的*command*）都需要自己的目录。这些目录有时是名为`cmd`的目录的子目录，例如`golang.org/x/tools/cmd/godoc`命令，它通过Web界面提供Go包文档（[§10.7.4](#ebook_split_102.html#id-documentingpackages)）。

包可以通过其导入路径指定（如上所示），或通过相对目录名指定，后者必须以`.`或`..`段开头，即使通常不需要这样做。如果未提供参数，则假定为当前目录。因此，以下命令构建相同的包，尽管每个命令都在运行`go build`的目录中写入可执行文件：

[单击此处查看代码图像](#ch10_images.html#id294pro01_r)

```
$ cd $GOPATH/src/gopl.io/ch1/helloworld
$ go build
```

和：

[单击此处查看代码图像](#ch10_images.html#id294pro02_r)

```
$ cd anywhere
$ go build gopl.io/ch1/helloworld
```

和：

[单击此处查看代码图像](#ch10_images.html#id294pro03_r)

```
$ cd $GOPATH
$ go build ./src/gopl.io/ch1/helloworld
```

但不能：

[单击此处查看代码图像](#ch10_images.html#id294pro04_r)

```
$ cd $GOPATH
$ go build src/gopl.io/ch1/helloworld
Error: cannot find package "src/gopl.io/ch1/helloworld".
```

包也可以指定为文件名列表，尽管这通常仅用于小程序和一次性实验。如果包名为`main`，可执行文件名来自第一个`.go`文件的基本名称。

[单击此处查看代码图像](#ch10_images.html#id294pro05_r)

```
$ cat quoteargs.go
package main

import (
    "fmt"
    "os"
)

func main() {
    fmt.Printf("%q\n", os.Args[1:])
}
$ go build quoteargs.go
$ ./quoteargs one "two three" four\ five
["one" "two three" "four five"]
```

特别是对于这种一次性程序，我们希望在构建后立即运行可执行文件。`go run`命令将这两个步骤合二为一：

[单击此处查看代码图像](#ch10_images.html#id294pro06_r)

```
$ go run quoteargs.go one "two three" four\ five
["one" "two three" "four five"]
```

第一个不以`.go`结尾的参数被视为Go可执行文件参数列表的开始。

默认情况下，`go build`命令构建请求的包及其所有依赖项，然后丢弃除最终可执行文件（如果有）之外的所有编译代码。依赖分析和编译都非常快，但随着项目增长到数十个包和数十万行代码，重新编译依赖项的时间可能变得明显，甚至达数秒，即使那些依赖项根本没有改变。

`go install`命令与`go build`非常相似，不同之处在于它保存每个包和命令的编译代码，而不是丢弃它们。编译后的包保存在`$GOPATH/pkg`目录下，对应源码所在的`src`目录，命令可执行文件保存在`$GOPATH/bin`目录下。（许多用户将`$GOPATH/bin`加入可执行文件搜索路径。）此后，如果这些包和命令未更改，`go build`和`go install`将不再为它们运行编译器，从而使后续构建快得多。为方便起见，`go build -i`会安装构建目标的依赖包。

由于编译后的包因平台和架构而异，`go install`将它们保存在名称包含`GOOS`和`GOARCH`环境变量值的子目录下。例如，在Mac上，`golang.org/x/net/html`包被编译并安装在`$GOPATH/pkg/darwin_amd64`下的`golang.org/x/net/html.a`文件中。

*交叉编译*Go程序非常简单，即构建针对不同操作系统或CPU的可执行文件。只需在构建期间设置`GOOS`或`GOARCH`变量。`cross`程序打印其构建目标的操作系统和架构：

[单击此处查看代码图像](#ch10_images.html#id295pro01_r)

gopl.io/ch10/cross

```
func main() {
    fmt.Println(runtime.GOOS, runtime.GOARCH)
}
```

以下命令分别生成64位和32位可执行文件：

[单击此处查看代码图像](#ch10_images.html#id295pro02_r)

```
$ go build gopl.io/ch10/cross
$ ./cross
darwin amd64
$ GOARCH=386 go build gopl.io/ch10/cross
$ ./cross
darwin 386
```

某些包可能需要为特定平台或处理器编译不同版本的代码，以处理低级可移植性问题或提供重要例程的优化版本。如果文件名包含操作系统或处理器架构名称，如`net_linux.go`或`asm_amd64.s`，则`go`工具仅在为该目标构建时编译该文件。称为*build tags*的特殊注释提供了更细粒度的控制。例如，如果文件包含此注释：
