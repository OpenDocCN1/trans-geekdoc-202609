
`fmt.Errorf` 函数使用 `fmt.Sprintf` 格式化错误消息并返回一个新的 `error` 值。我们用它来构建描述性错误，方法是将额外的上下文信息逐层添加到原始错误消息的前面。当错误最终由程序的 `main` 函数处理时，它应提供一条从根本原因到整体失败的清晰因果链，这让人联想到 NASA 的事故调查报告：

[点击此处查看代码图片](#ch05_images.html#id129pro02_r)

```
genesis: crashed: no parachute: G-switch failed: bad relay orientation
```

因为错误消息经常被串联在一起，所以消息字符串不应大写，也应避免换行。生成的错误可能很长，但当被 `grep` 等工具发现时，它们将是自包含的。

设计错误消息时，要深思熟虑，使每一个错误都是对问题的有意义描述，包含充分且相关的细节；并要保持一致，使同一函数或同一包中一组函数返回的错误在形式上相似，并能以相同的方式处理。

例如，`os` 包保证文件操作（如 `os.Open` 或打开文件的 `Read`、`Write`、`Close` 方法）返回的每个错误，不仅描述故障的性质（权限被拒、无此目录等），还包含文件名，因此调用者无需在其构造的错误消息中包含此信息。

通常，调用 `f(x)` 负责报告尝试的操作 `f` 和参数值 `x`，以及它们与错误上下文的关系。调用者负责添加它拥有但调用 `f(x)` 所没有的进一步信息，例如上面对 `html.Parse` 的调用中的 URL。

让我们继续讨论处理错误的第二种策略。对于表示暂时性或不可预测问题的错误，重试失败的操作可能是合理的，尝试之间可能有延迟，并且可能对尝试次数或完全放弃前花费的时间设置限制。

[点击此处查看代码图片](#ch05_images.html#id130pro01_r)

gopl.io/ch5/wait

```
// WaitForServer 尝试联系 URL 的服务器。
// 它使用指数退避策略尝试一分钟。
// 如果所有尝试都失败，它报告一个错误。
func WaitForServer(url string) error {
    const timeout = 1 * time.Minute
    deadline := time.Now().Add(timeout)
    for tries := 0; time.Now().Before(deadline); tries++ {
        _, err := http.Head(url)
        if err == nil {
            return nil // success
        }
        log.Printf("server not responding (%s); retrying...", err)
        time.Sleep(time.Second << uint(tries)) // exponential back-off
    }
    return fmt.Errorf("server %s failed to respond after %s", url, timeout)
}
```

第三，如果无法继续执行，调用者可以打印错误并优雅地停止程序，但这种做法通常应保留给程序的 main 包。库函数通常应将错误传播给调用者，除非该错误标志着内部不一致——即一个 bug。

[点击此处查看代码图片](#ch05_images.html#id130pro02_r)

```

if err := WaitForServer(url); err != nil {
    fmt.Fprintf(os.Stderr, "Site is down: %v\n", err)
    os.Exit(1)
}
```

达到相同效果的更方便的方法是调用 `log.Fatalf`。与所有 `log` 函数一样，默认情况下它会在错误消息前加上时间和日期前缀。

[点击此处查看代码图片](#ch05_images.html#id130pro03_r)

if err := WaitForServer(url); err != nil {

```

第五，也是最后，在极少数情况下，我们可以安全地完全忽略错误：

[点击此处查看代码图片](#ch05_images.html#id131pro03_r)

    return fmt.Errorf("failed to create temp dir: %v", err)

```

对 `os.RemoveAll` 的调用可能会失败，但程序忽略它，因为操作系统会定期清理临时目录。在这种情况下，丢弃错误是有意为之，但如果我们忘记处理它，程序逻辑将是一样的。养成在每次函数调用后考虑错误的习惯，当你有意忽略一个错误时，请清楚地记录你的意图。

Go 语言的错误处理有一种特定的节奏。检查错误后，通常先处理失败再处理成功。如果失败导致函数返回，成功的逻辑不会缩进在 `else` 块中，而是在外层继续执行。函数倾向于表现出一种通用结构：一系列初始检查以排除错误，随后是函数的实质内容，缩进最小。

### 5.4.2 文件结束 (EOF)

通常，函数可能返回的各种错误对最终用户很有趣，但对中间的程序逻辑则不然。然而有时，程序必须根据发生的错误类型采取不同的行动。考虑从文件中读取 *n* 字节数据的尝试。如果 *n* 被选为文件的长度，任何错误都代表失败。另一方面，如果调用者反复尝试读取固定大小的块直到文件耗尽，调用者对文件结束条件的响应必须与对所有其他错误的响应不同。因此，`io` 包保证由文件结束条件引起的任何读取失败始终由一个独特的错误 `io.EOF` 报告，其定义如下：

[点击此处查看代码图片](#ch05_images.html#id132pro01_r)

```
package io

import "errors"

// EOF 是当没有更多输入可用时 Read 返回的错误。
var EOF = errors.New("EOF")
```

调用者可以使用简单的比较来检测此条件，如下面的循环所示，它从标准输入读取 Unicode 字符。（[第 4.3 节](#ebook_split_037.html#id-charcount) 中的 `charcount` 程序提供了一个更完整的示例。）

[点击此处查看代码图片](#ch05_images.html#id132pro02_r)

```
in := bufio.NewReader(os.Stdin)
for {
    r, _, err := in.ReadRune()
    if err == io.EOF {
        break // finished reading
    }
    if err != nil {
        return fmt.Errorf("read failed: %v", err)
    }
    // ...use r...
}
```
