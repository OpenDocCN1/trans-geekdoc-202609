
这种*互斥*模式非常有用，以至于 `sync` 包中的 `Mutex` 类型直接支持它。其 `Lock` 方法获取令牌（称为*锁*），而 `Unlock` 方法释放它：

[点击此处查看代码图片](#ch09_images.html#id263pro01_r)

`gopl.io/ch9/bank3`

```
import "sync"

var (
    mu      sync.Mutex // 保护 balance
    balance int
)

func Deposit(amount int) {
    mu.Lock()
    balance = balance + amount
    mu.Unlock()
}

func Balance() int {
    mu.Lock()
    b := balance
    mu.Unlock()
    return b
}
```

每当一个 goroutine 访问银行的变量（此处仅为 `balance`）时，它必须调用互斥锁的 `Lock` 方法来获取独占锁。如果另一个 goroutine 已经获取了该锁，此操作将阻塞，直到另一个 goroutine 调用 `Unlock` 并使锁再次可用。互斥锁*保护*共享变量。按照惯例，受互斥锁保护的变量会在互斥锁声明之后立即声明。如果你偏离了这一惯例，请务必在文档中说明。

`Lock` 和 `Unlock` 之间的代码区域，goroutine 可以在其中自由读取和修改共享变量，称为*临界区*。持有锁的 goroutine 对 `Unlock` 的调用*发生在*任何其他 goroutine 为自己获取该锁*之前*。至关重要的是，goroutine 在完成后必须释放锁，这适用于函数中的所有路径，包括错误处理路径。

上面的银行程序体现了一种常见的并发模式。一组导出函数封装了一个或多个变量，以便访问这些变量的唯一途径是通过这些函数（或方法，针对对象的变量）。每个函数在开头获取互斥锁，在结尾释放它，从而确保共享变量不会被并发访问。这种函数、互斥锁和变量的组合称为*监视器*。（“监视器”一词的这种较早用法启发了“监视器 goroutine”这一术语。两种用法共享确保变量被顺序访问的代理人含义。）

由于 `Deposit` 和 `Balance` 函数中的临界区非常短——只有一行，没有分支——在末尾调用 `Unlock` 很简单。在更复杂的临界区中，特别是那些必须通过提前返回来处理错误的情况，很难确认 `Lock` 和 `Unlock` 的调用在所有路径上都是严格配对的。Go 的 `defer` 语句解决了这个问题：通过推迟 `Unlock` 的调用，临界区隐式地延伸到当前函数的末尾，使我们无需记住在远离 `Lock` 调用的一个或多个位置插入 `Unlock` 调用。

```
func Balance() int {
    mu.Lock()
    defer mu.Unlock()
    return balance
}
```

在上面的示例中，`Unlock` 在 `return` 语句读取 `balance` 的值*之后*执行，因此 `Balance` 函数是并发安全的。作为额外收获，我们不再需要局部变量 `b`。

此外，即使临界区发生 panic，推迟的 `Unlock` 也会运行，这在使用 `recover`（[§5.10](#ebook_split_051.html#id-recover)）的程序中可能很重要。`defer` 的开销比显式调用 `Unlock` 略大，但不足以成为牺牲代码清晰度的理由。与并发程序一样，始终应倾向于清晰性，抵制过早优化。只要可能，就使用 `defer` 并让临界区延伸到函数末尾。

请看下面的 `Withdraw` 函数。成功时，它将余额减去指定金额并返回 `true`。但如果账户资金不足以完成交易，`Withdraw` 会恢复余额并返回 `false`。

[点击此处查看代码图片](#ch09_images.html#id264pro01_r)

```
// 注意：非原子操作！
func Withdraw(amount int) bool {
    Deposit(-amount)
    if Balance() < 0 {
        Deposit(amount)
        return false // 资金不足
    }
    return true
}
```

该函数最终会给出正确结果，但有一个恶劣的副作用。当尝试过度取款时，余额会瞬间跌破零。这可能导致并发的小额取款被错误地拒绝。所以如果 Bob 试图买一辆跑车，Alice 就无法支付她的早咖啡费。问题在于 `Withdraw` 不是*原子*的：它由三个独立的操作序列组成，每个操作都获取然后释放互斥锁，但没有任何东西锁定整个序列。

理想情况下，`Withdraw` 应该在整个操作周围获取一次互斥锁。然而，这种尝试行不通：

[点击此处查看代码图片](#ch09_images.html#id265pro01_r)

```
// 注意：错误！
func Withdraw(amount int) bool {
    mu.Lock()
    defer mu.Unlock()
    Deposit(-amount)
    if Balance() < 0 {
        Deposit(amount)
        return false // 资金不足
    }
    return true
}
```

`Deposit` 通过调用 `mu.Lock()` 试图第二次获取互斥锁，但由于互斥锁*不可重入*——无法锁定一个已经加锁的互斥锁——这会导致死锁，无法继续执行，`Withdraw` 将永远阻塞。

Go 的互斥锁不可重入是有充分理由的。互斥锁的目的是确保在程序执行的关键时刻，共享变量的某些不变量得以维护。其中一个不变量是“没有 goroutine 正在访问共享变量”，但互斥锁所保护的数据结构可能还有额外的特定不变量。当一个 goroutine 获取互斥锁时，它可以假设这些不变量成立。在持有锁期间，它可能会更新共享变量，导致不变量暂时被破坏。然而，在释放锁时，它必须保证秩序已恢复，不变量再次成立。虽然可重入互斥锁能确保没有其他 goroutine 访问共享变量，但它无法保护这些变量的额外不变量。

一种常见的解决方案是将像 `Deposit` 这样的函数分成两个：一个未导出的函数 `deposit`，假设锁已被持有并完成实际工作；一个导出函数 `Deposit`，在调用 `deposit` 前获取锁。然后我们可以用 `deposit` 来表达 `Withdraw`，如下所示：

[点击此处查看代码图片](#ch09_images.html#id265pro02_r)

```
func Withdraw(amount int) bool {
    mu.Lock()
    defer mu.Unlock()
    deposit(-amount)
    if balance < 0 {
        deposit(amount)
        return false // 资金不足
    }
    return true
}

func Deposit(amount int) {
    mu.Lock()
    defer mu.Unlock()
    deposit(amount)
}

func Balance() int {
    mu.Lock()
    defer mu.Unlock()
    return balance
}

// 此函数要求锁已被持有。
func deposit(amount int) { balance += amount }
```

当然，这里展示的 `deposit` 函数非常简单，以至于实际的 `Withdraw` 函数不会费心去调用它，但它仍然说明了这一原则。

封装（[§6.6](#ebook_split_058.html#id-encapsulation)）通过减少程序中意外的交互，帮助我们维护数据结构不变量。出于同样的原因，封装也有助于我们维护并发不变量。当你使用互斥锁时，请确保互斥锁本身及其保护的变量都未被导出，无论它们是包级变量还是结构体字段。
