
```
// +build linux darwin
```

在包声明（及其文档注释）之前，`go build` 将仅在为 Linux 或 Mac OS X 构建时编译它，而此注释表示永远不要编译该文件：

```
// +build ignore
```

有关更多详细信息，请参阅 `go/build` 包文档的 *Build Constraints* 部分：

```
$ go doc go/build
```

### 10.7.4 文档化包

Go 风格强烈鼓励对包 API 进行良好的文档记录。每个导出的包成员的声明以及包声明本身都应紧跟在一个解释其目的和用法的注释之前。

Go *文档注释* 始终是完整的句子，第一句通常是一个以声明名称开头的摘要。函数参数和其他标识符在提及时不加引号或标记。例如，这是 `fmt.Fprintf` 的文档注释：

[点击此处查看代码图像](#ch10_images.html#id296pro01_r)

```
// Fprintf formats according to a format specifier and writes to w.
// It returns the number of bytes written and any write error encountered.
func Fprintf(w io.Writer, format string, a ...interface{}) (int, error)
```

`Fprintf` 的格式化细节在与 `fmt` 包本身关联的文档注释中解释。紧接在 `package` 声明之前的注释被视为整个包的文档注释。必须只有一个，尽管它可以出现在任何文件中。较长的包注释可能需要单独的文件；`fmt` 的注释超过 300 行。此文件通常称为 `doc.go`。

良好的文档不必详尽，文档也不能替代简洁性。事实上，Go 的约定倾向于在文档中也保持简洁和简单，因为文档像代码一样也需要维护。许多声明可以用一个措辞得当的句子来解释，如果行为确实显而易见，则不需要注释。

全书中，在空间允许的情况下，我们在许多声明前加上了文档注释，但浏览标准库时你会找到更好的示例。两个工具可以帮助你做到这一点。

`go doc` 工具打印命令行指定实体的声明和文档注释，该实体可以是一个包：

[点击此处查看代码图像](#ch10_images.html#id296pro02_r)

```
$ go doc time
package time // import "time"

Package time provides functionality for measuring and displaying time.

const Nanosecond Duration = 1 ...
func After(d Duration) <-chan Time
func Sleep(d Duration)
func Since(t Time) Duration
func Now() Time
type Duration int64
type Time struct { ... }
...many more...
```

或一个包成员：

[点击此处查看代码图像](#ch10_images.html#id297pro01_r)

```
$ go doc time.Since
func Since(t Time) Duration

    Since returns the time elapsed since t.
    It is shorthand for time.Now().Sub(t).
```

或一个方法：

[点击此处查看代码图像](#ch10_images.html#id297pro02_r)

```
$ go doc time.Duration.Seconds
func (d Duration) Seconds() float64

    Seconds returns the duration as a floating-point number of seconds.
```

该工具不需要完整的导入路径或正确的标识符大小写。此命令从 `encoding/json` 包打印 `(*json.Decoder).Decode` 的文档：

[点击此处查看代码图像](#ch10_images.html#id297pro03_r)

```
$ go doc json.decode
func (dec *Decoder) Decode(v interface{}) error

    Decode reads the next JSON-encoded value from its input and stores
    it in the value pointed to by v.
```

第二个工具，令人困惑地命名为 `godoc`，提供交叉链接的 HTML 页面，提供与 `go doc` 相同的信息以及更多内容。`godoc` 服务器 `https://golang.org/pkg` 涵盖标准库。图 10.1 显示了 `time` 包的文档，在第 11.6 节中我们将看到 `godoc` 对示例程序的交互式显示。`godoc` 服务器 `https://godoc.org` 拥有数千个开源包的可搜索索引。

![The time package in godoc.](graphics/godoc-time.png)

**图 10.1.** `time` 包在 `godoc` 中的显示。

如果你想浏览自己的包，也可以在工作区运行一个 `godoc` 实例。在运行此命令时访问浏览器中的 `http://localhost:8000/pkg`：

```
$ godoc -http :8000
```

其 `-analysis=type` 和 `-analysis=pointer` 标志用高级静态分析的结果增强文档和源代码。

### 10.7.5 内部包

包是 Go 程序中封装的最重要机制。未导出的标识符仅在同一个包内可见，而导出的标识符对全世界可见。

不过，有时中间地带会很有帮助，一种定义标识符的方式，使其对一小组受信任的包可见，但不对所有人可见。例如，当我们将一个大包拆分为更易管理的部分时，我们可能不想向其他包公开这些部分之间的接口。或者我们可能想在项目的几个包之间共享工具函数，而不想更广泛地暴露它们。又或者我们只是想通过将一个新包“置于试用期”并限制其客户端集合，来在过早承诺其 API 之前对其进行试验。

为了满足这些需求，如果包的导入路径包含名为 `internal` 的路径段，`go build` 工具会对该包进行特殊处理。此类包称为 *内部包*。内部包只能由位于 `internal` 目录父级为根的树内的另一个包导入。例如，给定下面的包，`net/http/internal/chunked` 可以从 `net/http/httputil` 或 `net/http` 导入，但不能从 `net/url` 导入。然而，`net/url` 可以导入 `net/http/httputil`。

```
net/http
net/http/internal/chunked
net/http/httputil
net/url
```

### 10.7.6 查询包

`go list` 工具报告可用包的信息。在最简单的形式下，`go list` 测试包是否存在于工作区中，如果存在则打印其导入路径：

[点击此处查看代码图像](#ch10_images.html#id298pro01_r)

```
$ go list github.com/go-sql-driver/mysql
github.com/go-sql-driver/mysql
```

`go list` 的参数可能包含 “`...`” 通配符，它匹配包导入路径的任何子字符串。我们可以用它来枚举 Go 工作区内的所有包：

```
$ go list ...
archive/tar
archive/zip
bufio
bytes
cmd/addr2line
cmd/api
...many more...
```

或特定子树内的包：

```
$ go list gopl.io/ch3/...
gopl.io/ch3/basename1
gopl.io/ch3/basename2
gopl.io/ch3/comma
gopl.io/ch3/mandelbrot
gopl.io/ch3/netflag
gopl.io/ch3/printints
gopl.io/ch3/surface
```

或与特定主题相关的包：

```
$ go list ...xml...
encoding/xml
gopl.io/ch7/xmlselect
```
