
## Chapter 3: Mutation Testing

### What Is It?

Have you ever wondered if there was a way to test the tests you’ve been writing? That is essentially what mutation testing is.

My preferred tool for doing mutation testing in PHP is Infection[^1], and it defines mutation testing as:

> Mutation testing involves modifying a program in small ways. Each mutated version is called a Mutant. To assess the quality of a given test set, these mutants are executed against the input test set to see if the seeded faults can be detected. If mutated program produces failing tests, this is called a killed mutant. If tests are green with mutated code, then we have an escaped mutant.

In the case of Infection, it works together with PHPUnit to make informed random changes to the code, and then execute the test.

[^1]: [https://infection.github.io](https://infection.github.io)

### Why Should I Use It?

My approach to writing unit tests goes something like this:

- What is the scenario I am writing a test for?
- What are my dependencies?
- How do I create those dependencies?
- How do I give those dependencies to the code I am testing?
- What assertions do I need to make?
- Does any code need to change to make those assertions succeed?

If I come up with enough scenarios, I start to take it for granted that I have both sufficient test coverage and that the tests themselves are good.

Mutation testing sets about to challenge that second assumption. If it mutates your code by doing something like switching `if` (`$foo > $bar`) to `if` (`$foo < $bar`) and a test for that portion of code still passes, there is a problem with your test.

Yes, sometimes tests succeed by accident! If you are making heavy use of test doubles, you need a way to detect whether the code you are creating doubles for behaves the way the test expects. Otherwise, you end up with tests that pass but no longer reflect how the code actually works.

### How Do I Use It?

In our sample app, I wanted to create a test for some code which verifies that the ordering of teams in our standings works correctly. The test looks like this:

```php
public function it_sorts_standings_correctly(): void
{
    $unsortedStandings = unserialize(
        (string) file_get_contents(__DIR__ . '/../../Fixture/unSortedStandings.txt')
    );
    $expectedStandings = unserialize(
        (string) file_get_contents(__DIR__ . '/../../Fixture/sortedStandings.txt')
    );

    $results = $this->component->sort($unsortedStandings);

    self::assertSame($expectedStandings['AC1'], $results);
}
```

This seems like a straightforward test. Can mutation testing reveal that our expectations are wrong?

Before we can get to that point, there was some configuration work I had to do. First, I needed to create the configuration file for Infection itself. It's named `infection.json` and stored in the root directory for the project:

```json
{
    "source": {
```

Next, I made sure I had my PHPUnit configuration file set up the way I wanted it. It's named `phpunit.xml` and it goes in the root directory for the project as well:

```xml
<phpunit bootstrap="tests/bootstrap.php">
    <listeners>
        <listener class="\Cake\TestSuite\Fixture\FixtureInjector">
            <arguments>
                <object class="\Cake\TestSuite\Fixture\FixtureManager" />
            </arguments>
        </listener>
    </listeners>
    <testsuites>
        <testsuite name="unit">
            <directory>tests</directory>
        </testsuite>
    </testsuites>
</phpunit>
```

The framework I am using provided the `bootstrap.php` file for me. Check the documentation for your framework for more details, or if you are using a custom solution, you'll have to figure out what should belong in that file.

What information in that summary should we be worried about? Because we don’t have 100% code coverage for `StandingsComponent.php`, it’s hard to come up with a good answer. What answers the tool provides can lead us toward figuring out where to focus our attention.

### Mutation Score Indicator (MSI)

You want this value to be as high as possible. It represents the percentage of mutations that were caught by your tests. To understand what this means, the process is like this:

- change something in the code you are analyzing
- run the tests that “cover” that code
- if the tests still pass, you have a mutant that was not caught

13% is a very low number and represents that our existing tests did not find most of the mutations, meaning our tests happily passed despite changes that should’ve been found. Not great!

### Mutation Code Coverage

This value should be close to your existing code coverage. I have no idea what my current code coverage is, but seeing that it is 98% is very interesting. Given the spread between this value and the MSI, it means I need a lot more tests.

### Covered Code Mutation Score Indicator

This is the value to really look at – it shows what the MSI is for code that was actually covered by tests. Now, because I filtered things out and told Infection to only look at one file, this should map exactly to the MSI. Again, this number is really low.
