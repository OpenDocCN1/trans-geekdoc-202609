### When Should I Use Mutation Testing?

As I showed in the section above, the best time to use mutation testing is during development. It can be used as a tool to guide you towards creating better tests by examining any "escape mutants" to see if there is anything that can be done.

In my case, I had an invalid test to begin with. See, it even happens to to experienced developers! Taking a look at the mutants and applying the change myself sent me down the path towards fixing a broken test.

I would not run mutation testing as part of any continuous integration build system. The fact that it can return false positives means it could cause a failing build for no reason.

Much like static code analysis tools, it is an excellent tool for getting your testing to that "next level" status. Having tests is good; having effective tests is even better!

# Linting and Formatting Your Code

The first time I came across a programming language that came “out of the box” with a code formatter was when I first played around With Go[^1] more than a decade ago. I was equally shocked to see how the Go community embraced it so quickly. Given all the online arguments I had seen over the years about things like semicolon usage in JavaScript and where to put opening and closing braces in PHP, it felt like a small breath of fresh air to see it.

Over the years, I discovered code linters and formatters can do a lot more than tell you “that opening brace is in the wrong place.” They can enforce many practices that often come up in code reviews and can also be used in build systems to apply those changes for you. An OSS project I used to lead made heavy use of them in ways that would surprise you.

[^1]: https://golang.org

### What

Linters and formatters are usually CLI tools that can be run locally by developers. Many IDEs also have integrations for using them. Learn your IDE inside and out! It can help automate a lot of the repetitive work that makes up so much of coding.

These tools analyze your code, usually based on a customizable set of rules, and identify where these rules have not been followed. Formatters are often combined with a linter and use the same concept of configurable rules to identify and then modify the code.

The strength of them being run via a CLI is that they can also be used as part of any continuous integration or build service.

### Why

A concept I have tried to instill in other developers over the years is that we should ask the computer to do any repetitive tasks for us. That way (or so my theory goes), we can stop worrying about those tasks and use our mental energy to solve other problems.

The ability to enforce a coding standard or even the use of specific language constructs means you have code that is consistent across the entire application. That consistency, in turn, tends to speed up comprehension, debugging, and often allows you to introduce other tools that are expecting your code to look and behave in a specific way.

Given that some linters and formatters can insert copyright documentation blocks or even tell you that you are missing a unit test for that code (yes, that is something that can be done), why would you not want to have what is essentially an on-call coworker who can point out (and more importantly) fix problems that might not have surfaced until code review time?

### How

Much like my recommendations for testing frameworks, editors, static code analyzers, and operating systems—pick one that does the job you need it to and go from there. There is no perfect tool for this!

For my own projects, I advocate using Easy Coding Standard[^2] as it allows you to use definitions created by other tools. As I write this book, I am using version 9.3.12.

[^2]: https://github.com/symplify/easy-coding-standard

I have also used PHP_CodeSniffer[^3] and PHP CS Fixer[^4] and code linters and fixers in other languages; my preference was to use Black[^5] for the Python code I wrote at Mozilla. Again, it doesn't really matter what one you use.

How can we actually use this? I borrow a PHP CS Fixer ruleset from another project and get it to play nicely with ECS. There is some great documentation from the ECS project pointing to blog posts about how others converted rulesets.

For my first pass, I told it to:

- enforce short array syntax
- enforce PSR-12[^6]
- only apply it to my src and tests directories

Here is what the ecs.php configuration file looks like:

```php
<?php

declare(strict_types=1);

use PhpCsFixer\Fixer\ArrayNotation\ArraySyntaxFixer;
use Symfony\Component\DependencyInjection\Loader\Configurator\ContainerConfigurator;
use Simplify\EasyCodingStandard\ValueObject\Option;
use Simplify\EasyCodingStandard\ValueObject\Set\SetList;

return static function (ContainerConfigurator $containerConfigurator): void {
    $parameters = $containerConfigurator->parameters();
    $parameters->set(Option::PATHS, [
        __DIR__ . '/src',
        __DIR__ . '/tests',
    ]);

    $services = $containerConfigurator->services();
    $services->set(ArraySyntaxFixer::class)
        ->call('configure', [
            'syntax' => 'short',
        ]);
    $containerConfigurator->import(SetList::PSR_12);
};
```
