
## The Application

For various reasons, mostly related to the concept of “the prototype becomes production,” we have no test coverage. Typically, this would be a massive problem for any website people frequently use, but I am a “domain expert” for the problem we are solving. This allows me to make very lazy shortcuts and visually verify things work as expected.

Chances are, if you are joining a project and dealing with a long-lived legacy application it’s very likely you do not have the same level of knowledge of both the application’s code and the problem it’s solving. Because of my knowledge, I can skip a whole category of automated tests where the output of various pages is compared to a baseline. Manually reloading pages after making small changes is not a great practice. Still, at this point, it is highly unlikely that writing a series of automated tests will give us a sense of confidence about the deployments we need. No other developers are likely to join the “team” to work on it. I know enough to visually confirm if things are working as expected.

Still, no tests? Yes, to my great personal shame, it is a huge oversight that now needs to be corrected. Every year when we tweak things and ready the website to cover the upcoming season, a few things break. Because I understand how EVERYTHING is supposed to work, these are quick changes. It would be nice to get to the point where all the things that break happen before I push the changes into production.

So why am I bothering to add automated tests, given that some types of tests are likely not to help? That domain knowledge often leads me to forget to check that everything works instead of only visually checking the one thing I changed.

By adding tests that cover the things that have to work whenever updated code is deployed into production I am trying to change the cycle of:

- Make local changes
- Imperfectly test local changes
- Push changes to production
- Get email from people that “something is broken”

The price of failure here is pretty low–it’s a website supporting a hobby. Any urgency I feel is created by myself; chances are your own situation is much different. Bugs or unexpected behavior in your web applications can lead to losing money, losing jobs, or could even damage the business behind it.

I am a firm believer in getting a computer to do repeatable tasks for you. As humans, we make mistakes. We skip steps. We assume the state of things. Computers only follow the instructions we give them. Hopefully, those instructions match how we believe things should behave.

## 2. STATIC CODE ANALYSIS TOOLING

### What Is It?

I like to introduce programming ideas by sharing a definition from a reliable source. In this case, Wikipedia:

> Static program analysis is the analysis of computer software that is performed without actually executing programs, in contrast with dynamic analysis, which is analysis performed on programs while they are executing. In most cases the analysis is performed on some version of the source code, and in the other cases, some form of the object code.

The part of this that intrigued me when I first started looking into it was the “without actually executing programs” part. About a decade ago, I tried creating my own tool that would perform static analysis of PHP code to figure out dependencies and language constructs you needed to test. It quickly led me down a rabbit hole of figuring out how to parse PHP tokens and abstract syntax trees.

In the end, I figured out it was easier to write books and give talks about teaching people to do what my poorly-built tool was trying to do in an automated fashion.

In this book, I am using PHPStan⁸ but I have also used Psalm⁹ for the same purposes. Other options I am aware of are phan¹⁰ and exakat¹¹. However, PHPStan and Psalm are definitely the ones with the most “market share” in PHP.

As a quick summary and to focus the rest of this chapter: static code analysis provides a way of testing your code without having to run it. A static analysis tool can look at your PHP code and infer things about how it should work based on the types associated with your variables, functions, and classes. It can highlight whether you’re potentially passing a parameter with an ambiguous type, if you’re calling a function in an unexpected way, identify areas of code that will never be executed, and more. As PHP has matured and added features like type hints and strict mode, static analysis tools can give you a better understanding of application code and give more useful feedback.

⁸ https://phpstan.org  
⁹ https://psalm.dev  
¹⁰ https://github.com/phan/phan  
¹¹ https://exakat.io

### Why Should I Use It?

When I first started looking at and using these tools, I quickly realized that the high-level purpose was to accurately figure out the intent of the code I was writing.

When parameter typing and return value typing were added to the language, it helped me out in two ways. First, it eliminated a whole category of tests designed to answer questions like, “Did you get an array back?” Once you could say, at the language level, “this variable is supposed to be an integer,” then the PHP interpreter could do that test for me.

With the use of types, the static analysis tools could read in my code, parse it, and then start looking at code that is calling it. When I started using these tools, I began to appreciate that I had something looking at what I did and making suggestions:

“I know you are accepting an array as this parameter, but look at how in one place it is given an array of integers, while elsewhere it is an array of mixed values. Which one are you expecting?”

“I noticed that you are calling this method on this object you generated a few lines up. I can’t tell what type of object it is supposed to be due to some lazy loading behind the scenes. Can you add an annotation to help me figure it out?”
