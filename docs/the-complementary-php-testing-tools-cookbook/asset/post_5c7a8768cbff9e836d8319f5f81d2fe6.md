# When

In my experience, there are three places to use code linters and formatters:

## During Development

The most common practice if it is not mandatory for a particular project is to have the developers use the linting and formatting tools during their work and hopefully before committing and pushing their code for review or merging.

I have done this on projects where these tools were not mandatory.

## Before Version Control Usage

If you are using a version control system that has the concept of a “pre-commit hook” I highly recommend reading the documentation for your VCS on how to use them and set one up.

This way, if you have forgotten to run the linter it will be done before your VCS tooling pushes your code to the repository.

## During Builds or Continuous Integration

This is my preferred time to have linting tools run, with any problems being reported by the linter being considered a failed build. Again, this also relies on you having a build system or continuous integration system you can customize to run arbitrary commands from the command line.

If you are using something like GitHub Actions^[7]^ you can find examples of how to do it. In a later chapter of this book where I show some examples of using continuous integration systems, you can probably figure out where to add a linting step.

^[7]^ GitHub Actions: https://github.com/features/actions

# Chapter 5

## Continuous Integration

I am a big fan of getting computers to do repetitive actions for me. It frees up my attention to focus on solving other problems instead of remembering a series of steps where missing one can result in failure.

One of the issues most programming projects face is coming up with a way to integrate code changes with the least amount of friction. There is no way to do it without any kind of pain and effort either on the development side or the tool creation side.

As I write this in the spring of 2021, there are two dominant methods of integrating your code. The first I call “integrate into main with flags” and “integrate via pull-request.”

### Integrate Via Pull Request

With a large percentage of developers making use of GitHub (ironically a set of centralized web-based tools for a distributed version control system) most of the folks reading this are familiar with the use of the “pull request.”

For those not familiar, here’s a high-level explanation:

A developer creates a branch of the code under version control and does some work in that branch. Once they are ready to share, they use tooling to create a “pull request,” which is a notification that there are some changes to be reviewed. Generally speaking, you are comparing the developer’s work in their own branch with the main branch that gets deployed into a production environment.

People reviewing the pull request can see what the changes are and make comments about those changes. One of the downsides of the pull request method is that long-running work can easily get out of date if the codebase itself is changing rapidly. This, in turn, forces the developer to do a lot of work, constantly merging in other changes from other developers that have been applied to the main branch.

This method puts the pressure for smooth integrations onto the tooling by providing tools that reduce the friction involved in managing all these changes.

### Integrate Via Flags

As more people experience some of the pains and frustrations of a pull-request-centric integration plan, other programmers have been advocating not using separate branches for their work. Instead, they work in the main branch that is deployed and use “feature flags” or other techniques to make sure that the new code is only used under specific conditions.

Feature flags or other ways of configuring what code is available to users can be as complicated as an admin system where you define these values or as straight-forward as a conditional statement around a block of code.

The project I am using in this book does more of an “integrate with main” strategy, with a few flags to change what gets displayed. The other developer who helps out does pull requests for their work as they do not understand the codebase as well as I do.

This method puts the integration pressure on the developers to make sure the conditions under which this code should be executed are correct.

No matter what method you choose to use, the process for doing either method is well-established, and there are lots of resources available that can show how to do it.
