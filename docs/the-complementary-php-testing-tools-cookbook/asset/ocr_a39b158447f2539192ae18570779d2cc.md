# ## The Application

For a various reasons, mostly related to the concept of “the prototype becomes production,” we have no test coverage. Typically, this would be a massive problem for any website people frequently use, but I am a “domain expert” for the problem we are solving. This allows me to make very lazy shortcuts and visually verify things work as expected.

Chances are, if you are joining a project and dealing with a long-lived legacy application it’s very likely you do not have the same level of knowledge of both the application’s code and the problem it’s solving. Because of my knowledge, I can skip a whole category of automated tests where the output of various pages is compared to a baseline. Manually reloading pages after making small changes is not a great practice. Still, at this point, it is highly unlikely that writing a series of automated tests will give us a sense of confidence about the deployments we need. No other developers are likely to join the “team” to work on it. I know enough to visually confirm if things are working as expected.

Still, no tests? Yes, to my great personal shame, it is a huge oversight that now needs to be corrected. Every year when we tweak things and ready the website to cover the upcoming season, a few things break. Because I understand how EVERYTHING is supposed to work, these are quick changes. It would be nice to get to the point where all the things that break happen before I push the changes into production.

So why am I bothering to add automated tests, given that some types of tests are likely not to help? That domain knowledge often leads me to forget to check that everything works instead of only visually checking the one thing I changed.

By adding tests that cover the things that have to work whenever updated code is deployed into production I am trying to change the cycle of:

+   - make local changes
- imperfectly test local changes
- push changes to production
- get email from people that “something is broken”

The price of failure here is pretty low–it’s a website supporting a hobby. Any urgency I feel is created by myself; chances are your own situation is much different. Bugs or unexpected behavior in your web applications can lead to losing money, losing jobs, or could even damage the business behind it.

I am a firm believer in getting a computer to do repeatable tasks for you. As humans, we make mistakes. We skip steps. We assume the state of things. Computers only follow the instructions we give them. Hopefully, those instructions match how we believe things should behave.
