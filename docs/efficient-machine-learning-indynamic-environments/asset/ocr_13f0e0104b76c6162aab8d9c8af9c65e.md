# 1.2 Why Static Optimization Falls Short

A rich literature narrows the efficiency gap by *static* means. Broadly applicable methods such as model compression and distillation [21, 48, 50, 166], federated learning [66, 126], and efficient architecture design [52, 76, 87] complement rapid advances in hardware and software, including mixed-precision formats [67], tensor cores [205], and high-bandwidth interconnects [110]. These techniques yield large wins, but they share a common premise: the target deployment environment (dataset, resource budget, available hardware, query complexity) is fixed *a priori*. Once the model or approach is tuned, it is frozen and deployed unchanged. In practice, however, operating conditions and available resources in ML systems are rarely fixed:

+   • **Resource volatility.** On edge devices, battery level, thermal headroom, compute cycles, and wireless bandwidth can swing between successive inference calls. In the cloud, ephemeral GPU leases may be preempted with little warning, serverless functions incur cold-start delays, and backbone congestion leads to network delays and throttling. Any rigid deployment must therefore over-provision resources to accommodate these variances or risk timeouts.

+   • **Query heterogeneity.** Interactive services—web search, recommendation, dialogue—receive a highly skewed mix of easy and hard requests. A keyword query like “weather in Pittsburgh” is correctly answered by a tiny model, whereas an open-ended prompt—“What color is your raindrop?”—may need a much larger LLM with chain-of-thought reasoning. Using a single model for both wastes compute on the median case or sacrifices quality on the tail.
