
## 事件响应参数与SLA违规责任

此外，事件响应参数指示了一个此前未提及但能够被提及的额外属性：

事件响应与其他参数处于同一层级，因为事件和覆盖阈值是针对SLA中包含的其他参数描述的。例如，当90%的消费者在1个月内的可访问性低于99.99%时，即使弹性测试失败或发现特定严重程度的漏洞，也可能触发事件升级。

这可能是要求云供应商也对SLA违规负责的最有力案例之一，因为在这种情况下，问题不仅在于按用户基础量化多个运营参数的性能，还在于真正拥有一个衡量整个云流程如何为客户提供服务的国际指标。对安全SLA进行强大定制的需求的一个很好的例子是承担服务弹性和负载津贴的风险。此参数还可用于满足抵御DoS或DDoS攻击的需求。

另一方面，DoS/DDoS的财务影响（损失）因受害者的工商业务特性而异，变化极大。高度静态的程序（例如，运行一组无需求变化的低流量服务器）可能不需要纳入此要求，尽管仍可要求它以保证对DoS/DDoS攻击的弹性。

因此，ENISA手册的重要部分以及建议的参数在于：如果不讨论客户与供应商之间发现SLA违规的责任分担，且不给客户根据其特定风险概况定制SLA的机会，就不存在强有力的安全SLA。

## CUMULUS工作与漏洞风险分析

CUMULUS的工作非常详细且全面，必须被视为未来安全SLA规范的参考手册。无论如何，它无法摆脱安全风险分析的微妙之处。例如，它将漏洞数量作为一个需要考虑的重要参数，这在当前的SLA中未被提及，但通常由协会通过漏洞扫描、跟踪工具和渗透测试来评估。这是一个合理的观察，其普遍性超出了SLA的特定范围。

这表明评估漏洞带来的威胁不仅仅止步于技术评估，还意味着一个与漏洞属性、其对公司和运营的直接及间接影响以及建立优先级原则相关的评估阶段。

定义漏洞等级既是一项技术工作，也是一项管理工作，它总是意味着做出选择，除了极少数小场景外，这绝不可能只是“全部修复”。多年来这样做变得成本过高，充满负面影响，也是对稀缺资源的浪费。

漏洞必须被评级（即加权），必须根据风险接受标准进行危害分析，并必须为特定漏洞建立阈值。这是寻找可靠、稳健且合理的漏洞排序标准的必然逻辑。然而，这里应用于漏洞的危害评估微妙之处开始发挥作用：标准经常因过时而失效，其适用性必须受到挑战并持续研究，否则危害分析也会变得无效。这正是CVSS v2正在发生的情况：其作为评分系统的有效性受到严厉批评，对大多数人而言，它不再被视为管理漏洞威胁的实用替代方案（Allodi和Massacci 2014；Eiram和Martin n.d.；Freund和Jones 2014；Rothke 2015）。

## 云系统风险研究现状

本章探讨了云系统中的危险，这是一个自云系统早期以来就是许多研究、调查和民意测验主题的课题。然而，正如风险和数据安全（很大程度上与云系统中的风险重叠）一样，调查、分类法和通用语言距离成熟仍很遥远。相反，语言经常依赖于上下文或过于通用，我们仍在努力透明地识别哪些危险是云技术特有的，因此需要新的调查、策略和替代方案，哪些是云构建模块（如开放网络、远程访问、加密程序和互联网技术）的危险。

多租户和按需自适应资源供给是云系统的其他特性，因其特异性和对风险的影响而被研究最多。在计算风险管理时，除了参考全球组织的风险管理标准外，大量调查和研究的重点是管理解决方案的合同关系，它实现了风险从云客户向云供应商的转移。各方之间SLA的定义是规定安排条件的公认方式，但对于云技术，关于现有SLA存在持续的争论，这些SLA被认为主要不足，特别是在保护客户免受云风险方面。
