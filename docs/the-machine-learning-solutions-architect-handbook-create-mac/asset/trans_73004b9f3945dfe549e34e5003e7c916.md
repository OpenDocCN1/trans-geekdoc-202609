
在定义了业务目标和业务指标之后，你仍然需要确定是否可以使用机器学习（ML）解决方案来解决业务问题。虽然机器学习的应用范围广泛，但并不意味着它能解决所有的业务问题。

## 数据理解与数据准备

俗话说“数据是新新的石油”，这对于机器学习而言尤为如此。没有所需的数据，你就无法推进机器学习项目。机器学习生命周期中的下一个步骤就是数据获取、理解和准备。

根据业务问题和机器学习方法方法，你需要收集并理解可用数据，以确定你是否拥有正确的数据和规模来解决机器学习问题。例如，假设要解决的业务问题是信用卡欺诈检测。在这种情况下，你需要诸如历史信用卡交易数据、客户人口统计数据、账户数据、设备使用数据和网络访问数据等数据集。然后需要进行详细的数据分析，以确定数据集的特征和质量是否足以建模任务。你还需要决定是否进行数据标注，例如标记欺诈或非欺诈。在这一步，取决于数据质量，可能需要进行大量的数据清洗，以准备和清理数据，并为模型训练和评估生成数据集。

## 模型训练与评估

使用创建的训练集和验证集，数据科学家需要使用不同的机器学习算法和数据集特征运行多次实验，以进行特征选择和模型开发。这是一个高度迭代的过程，可能需要大量的数据处理和模型开发，以找到最佳模型性能的算法和数据集组合。除了模型性能之外，你可能还需要考虑数据偏偏差模型的可解释性，以满足监管要求。

在模型训练完成后、部署到生产环境之前，需要使用相关的技术指标（如留出数据集，也称为测试数据集）对模型质量进行验证，以衡量模型在未见数据上的表现。理解使用哪些指标进行模型验证非常重要，因为这取决于具体的机器学习问题和所使用的数据。例如，如果文档类型相对平衡，模型准确率将是文档分类案例的良好验证指标。对于欺诈检测用例，准确率将不是评估模型性能的良好指标——这是因为欺诈案件的数量很少，如果模型一直预测为非欺诈，模型的准确率可能很高。

## 模型部署

一旦模型充分训练并验证符合预期的性能指标，就可以将其部署到生产环境和业务工作流中。这里有两个主要的部署概念。第一个是部署模型本身，供客户端应用程序调用以生成预测。第二个概念是将此预测工作流集成到业务应用程序中。例如，部署信用卡欺诈模型时，可以将模型托管在 API 后面进行实时预测，或者作为一个可以动态加载的包来支持批量预测。此外，此预测工作流还需要集成到业务应用程序中用于欺诈检测，可能包括实时交易的欺诈检测、基于预测输出的决策自动化以及用于详细欺诈分析的欺诈检测分析。

## 模型监控

模型部署并不是机器学习生命周期的结束。与软件不同（软件的行为具有高度确定性的显式逻辑），机器学习模型在生产环境中的行为可能与其在模型训练和验证中的行为不同。这可能是由于生产数据特征的变化、数据分布或对请求数据的潜在操控造成的。因此，模型监控是检测模型漂移或数据漂移的重要后期步骤。

## 业务指标跟踪

应该对实际业务影响进行持续跟踪和衡量，通过比较模型部署前后的业务指标，或通过 A/B 测试（比较有无机器学习模型的工作流之间的业务指标），来确保模型带来了预期的业务收益。如果模型没有带来预期收益，应该重新评估以寻找改进机会。这可能意味着将业务问题重新构建为一个不同的机器学习问题。例如，如果流失预测没有提高客户满意度，那么请考虑提供个性化的产品/服务来解决该问题。

现在我们已经讨论了端到端机器学习生命周期涉及的内容，让我们来看看下一节中的机器学习挑战。

## 机器学习挑战

多年来，我使用机器学习解决方案处理过许多现实问题，并遇到了不同行业在采用机器学习过程中面临的各种挑战。

在开展机器学习项目时，我经常遇到这个问题：我们有大量数据——能帮我们找出使用机器学习可以生成哪些见解吗？这被称为业务用例。无法识别机器学习的业务用例对于许多公司来说是一个非常巨大的障碍。如果没有正确识别的业务问题及其价值主张，启动一个机器学习项目将具有挑战性。

当我与不同行业的公司交流时，我通常会问他们机器学习面临的首要挑战是什么。我收到的最频繁的回答总是关于数据的——即数据质量、数据清单、数据可访问性、数据治理和数据可用性。这个问题影响了数据匮乏和数据富足的公司，并且往往因数据孤岛、安全和行业法规而加剧。

数据科学和机器学习人才的短缺是我从许多公司听到的另一个挑战。公司在吸引和留住机器学习人才方面面临很大困难。

许多公司在采用机器学习时面临的另一个挑战是获得文化的认可。许多人将机器学习视为对其职业的威胁。对机器学习知识的缺乏让他们在使用这些新方法时感到不安。

解决方案架构的实践旨在解决机器学习中的某些挑战。接下来，让我们仔细查看解决方案架构及其在机器学习周期中的位置。

## 解决方案架构

当我最初作为解决方案架构师参与公司的机器学习项目时，重点是数据科学和建模。当时问题的规模和模型数量都很小。大多数问题可以使用简单的机器学习技术解决。数据集也很小。当时机器学习项目的范围限于少数数据科学家或团队。作为当时的架构师，我主要需要科学技能和通用云架构知识。

在过去的几年里，不同公司的机器学习项目变得复杂得多，开始涉及到更多职能和人员。我发现自己更多地与高管讨论机器学习战略和组织设计以实现广泛应用。我被要求使用各种技术为大型企业设计复杂的机器学习平台，以满足严格的安全和合规需求。近年来，关于机器学习工作流编排和运行的架构和流程讨论比任何时候都多。而且越来越多的公司寻求使用大数据训练机器学习模型。某些公司训练和部署的模型数量已达到数千个。安全敏感型客户也在寻求机器学习隐私、可解释性和数据模型偏差方面的指导。作为解决方案架构的从业者，我发现在该职能上表现所需的技能和知识发生了巨大变化。

那么，解决方案架构在这个复杂的业务、数据、科学和技术维恩图中处于什么位置？根据我在不同规模和行业公司的经验，我将解决方案架构视为一门连接机器学习项目各个部分的综合性学科。机器学习架构与不同的业务和技术合作伙伴交互，为业务问题提供机器学习解决方案，并设计运行这些解决方案的技术平台。
