## ML 与传统软件

在我开始从事 AI/ML 领域工作之前，我花费了多年时间为大型金融服务机构构建软件平台。我处理过的某些业务问题具有复杂的规则，例如，为投资银行交易识别用于可比性分析的公司，或者为来自不同数据提供者的所有不同公司标识符创建一个主数据库。我们必须在数据库存储存储过程和应用程序服务器后端中实现硬编码规则来解决这些问题。我们经常争论某些规则对于我们试图解决的业务问题是否合理。当我们更改这些规则时，必须重新实现这些规则，并确保这些更改不会破坏任何内容。为了测试新发布版本或更改，我们通常依赖人工专家在生产环境发布之前详尽地测试和验证之前实现的所有业务逻辑。这是一个非常耗时且容易出错的过程，并且每当引入新规则或需要更改现有规则时，都需要大量的工程工作、针对文档规范的测试以及用于部署的严谨变更管理。我们经常依赖用户来报告生产环境中的逻辑问题，当生产环境报告一个问题时，我们有时不得不打开源代码来排除故障或解释其运行逻辑。我经常问自己是否有更好的方法来这样做。

在我开始从事 AI/ML 领域工作后，我开始使用 ML 技术来解决许多类似的挑战。通过 ML，我不需要想出复杂的规则（这些规则通常需要深层的数据和领域知识来创建或维护用于决策的复杂规则）。相反，我专注于收集高质量数据，并使用 ML 算法直接从数据中学习规则和模式。这种新方法消除了创建新规则的许多具有挑战性的方面（例如，所需的深层领域知识，或避免人类偏见）以及维护现有性能指标的问题。在生产环境发布之前验证模型，我们可以检查准确率等模型性能指标。虽然仍然需要数据科学专家来根据业务问题的性质和数据集来解释模型指标，但不再需要对所有场景进行详尽的人工测试。当模型部署到生产环境时，我们会通过监控生产数据与我们模型训练数据之间的任何显著变化，来监控模型表现是否符合预期。我们会为生产数据收集新标签，并定期测试模型以确保其预测能力没有退化。为了解释模型为什么做出那样的决策，我们不需要打开源代码来重新检查硬编码逻辑。相反，我们依靠 ML 技术来解释输入特征的相对重要性，以理解哪些因素对 ML 模型的决策影响最大。

## ML 生命周期

我处理过的最早几个 ML 项目之一是针对某个大型体育联盟品牌的运动预测分析问题。我被给了一份预测分析结果列表供思考，看看这些问题是否有 ML 解决方案。我是运动的业余观众；我对要生成的分析一无所知，也不详细了解比赛规则。我被给了一些示例数据，但我不知道该如何处理它们。

我开始工作的第一件事是学习这项运动。我研究了比赛是如何进行的、不同的球员位置，以及如何确定和识别特定事件。在获取了相关的领域知识后，数据开始对我产生意义。然后，我与利益相关者讨论了不同分析结果的影响，并根据我们拥有的数据评估了建模的可行性。我们提出了几个对业务影响最大的顶级 ML 分析方向进行工作，并决定了它们将如何集成到现有的业务流程中，以及如何衡量它们的影响。

我开始详细地检查和探索数据，以了解可用信息以及缺失了什么。我根据正在考虑的几种 ML 算法处理并准备了数据集，并进行了不同的实验。我没有工具来跟踪实验。在经过几轮初始实验后，我觉得数据不足以训练高性能模型，我需要更多数据集。数据所有者能够提供我寻找的额外数据集，在进行了更多实验后，我建立了一个符合业务需求的模型。之后，困难的部分来了——在生产环境中部署和运行该模型，并将其集成到现有的业务流程中。我们经历了许多架构和工程讨论，最终为模型构建了部署方案。

从我的个人经验可以看出，将一个业务想法或预期结果从构思到生产有许多不同的步骤。现在，让我们正式地回顾一个典型的 ML 项目生命周期。一个正式的生命周期包括业务理解、数据获取和理解、数据准备、模型构建、模型评估和模型部署等步骤。由于生命周期中的很大一部分是对不同数据集、特征和算法的实验，因此可以在过程结束时创建一个工作模型。如数据的可用性和质量、特征工程技术（利用领域知识从原始数据中提取有用特征的过程）以及学习算法的能力等因素，可能防止成功的获得。

## 业务理解和 ML 问题定义

生命周期的第一步是业务理解步骤。在这一步，你需要对业务目标有明确的理解，并定义用于衡量 ML 项目成功的业务性能指标。以下是业务目标的一些示例：

- 运营流程的成本降低，例如文档处理。
- 业务或运营风险的缓解，例如欺诈和合规。
- 产品或服务收入的提高，例如更好的目标营销、决策的新洞察生成以及客户满意度的提高

用于衡量的具体业务指标示例可以是业务流程减少的小时、检测到的真阳性数量的增加、目标营销转化率的提高以及流失率降低的程度。这是一个非常重要的正确执行步骤，以确保 ML 项目有充分的理由，并且项目结果能够被成功衡量。
