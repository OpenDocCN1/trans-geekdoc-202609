This is the point at which we finally put our data model to use by extending the abstract Carte class with some sub carte objects. Remember that the abstract Carte class has a getAllCarteProducts method that generates CarteProduct objects and populates them with data stored in the carteProduct table within the database. Remember that the DinnerCarte class takes precedence over this method.

Because we used interfaces to enforce this business requirement, the LunchCarte and DinnerCarte in our application would use the same CarteProducts, as per our business design. Keep in mind that these interfaces are used to change the prices and serving sizes of the same carte Products on the lunch and dinner cartes.

As a result, the DinnerCarte class overrides the getAllCarteProducts() method of the abstract Carte class. If we hadn't designed our application in this manner, we would have added the getAllCarteProducts() method to the DBMapper class instead of the base Carte class. We did it this way to demonstrate how to use interfaces.

To begin, I'll just make instances of the DrinkCarte, AppetizerCarte, LunchCarte, and DinnerCarte classes in order to provide sub cartes for drinks, appetizers, lunch, and dinner. Each of these objects will use the getAllCarteProducts() method to retrieve relevant data associated with the class's const id. In order to implement the interfaces that the DinnerCarte class refers to, the $dinner_Carte object overrides the getAllCarteProducts() method. When evaluating the results, compare the prices and serving sizes of similar carte Products on the Lunch and Dinner Cartes.
