
请记住，你正在测试的机器可能根本没有“正确的”TPM芯片。许多设备仍在使用TPM 1.2芯片，这类芯片根本不兼容。此外，即使芯片标记为TPM 2.0，也不意味着它能执行证明部分，而这对于握手过程是必需的。我在几台配备TPM 2.0芯片的笔记本电脑上测试时，流程进行了95%才发现这些笔记本没有“正确类型”的TPM 2.0芯片，证明功能无法按预期工作，令人沮丧！如果你走到这一步仍无法工作，请尝试刷新升级TPM固件以支持证明功能。在这种情况下，请返回[图8.40](#c08.xhtml#figure8-40)所示的示例机器界面重新检查：是否有TPM 2.0？是否支持证明？是否使用的是物理机而非虚拟机？

### Autopilot混合Azure AD加入

还有一个最终的Autopilot场景我想与你一起设置。

对我来说，这凸显了Microsoft理解许多组织希望在云端做很多事情，同时（至少在一段时间内）保持一只脚在本地环境中。

在[第4章](#c04.xhtml)中，我们使用组策略引导已加入本地Active Directory的本地机器自动注册到MDM。

现在，在本节中，你将执行反向操作。

即，你将指示一台全新的机器（新开箱或已重置）通过Autopilot注册到MDM，然后神奇地加入你的本地Active Directory。

如何实现？当然需要一些“朋友”的帮助。

让我们从理解工作流程开始。请参考[图8.48](#c08.xhtml#figure8-48)随我讲解所有步骤。

1.  一台新机器送达用户手中。
2.  机器启动OOBE时，将联系Autopilot服务（你已经做了18次类似的事了）。
3.  配置文件类型是一种新的特殊Autopilot类型，称为“混合Azure AD加入”，我们将在本节中探讨。
4.  设备注册到MDM（本例中为Intune）。
5.  Intune通过一个新组件——脱机域加入连接器（`ODJ连接器`）联系你的本地AD，我们也将在本节中探讨。
6.  Intune下发一个称为脱机域加入Blob（`ODJ Blob`）的对象；这也是我们将要探讨的内容。
7.  计算机使用ODJ Blob完成加入。
8.  现在已加入域，可以获取组策略或其他本地/AD特定的内容。

#### 什么是ODJ Blob？

如果机器当前未连接到LAN，技术人员无法通过网络将其加入域，该如何加入机器？

事实是，你不能。但你可以做次优的事。

这个概念在本地AD领域已存在很久（自Windows 7以来），称为脱机域加入（`ODJ`）。

使用ODJ，你可以在Active Directory中为计算机创建预留。然后让计算机使用该预留。

很容易亲自尝试，以便在几分钟后我们加入Intune时理解自动发生的过程。在任意已加入AD的机器上，运行以下命令为名为`testjoin01`的“尚未加入域”的计算机预留空间：

```
djoin /provision /domain fabrikam.com /machine testjoin01 /savefile provision.txt
```

该输出文件`provision.txt`在技术上称为ODJ Blob，你可以用记事本查看。命令和文件如[图8.49](#c08.xhtml#figure8-49)所示。

![图8.49 创建和检查脱机域加入（ODJ）Blob](images/c08f049.jpg)

[**图8.49**](#c08.xhtml#figureanchor8-49) 创建和检查脱机域加入（ODJ）Blob

然后转到一台未加入域但与你的Active Directory在同一网络上的机器。当然，先将ODJ Blob文件复制过去。然后，使用提升的命令提示符，认领该预留。使用以下命令：

```
djoin /requestodj /loadfile provision.txt /windowspath c:\windows /localos
```

你可以在[图8.50](#c08.xhtml#figure8-50)中看到命令运行情况。

客户端重启后，当客户端首次能够联系本地Active Directory时，它们会同步，奇迹发生：机器现在真正加入了域。
