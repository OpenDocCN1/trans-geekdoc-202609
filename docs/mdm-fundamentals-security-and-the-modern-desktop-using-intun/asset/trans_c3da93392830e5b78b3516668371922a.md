

## 配置自定义 OMA-URI 策略

*   我们知道 PolicyCSP 的位置和策略名称：`InternetExplorer/DisableAdobeFlash`（见[图 3.18](#c03.xhtml#figure3-18)）。
*   我们知道在 MDM 中表达它的方式（通常情况）。
*   我们知道要在 User 端执行此操作。

将这些组合在一起，得到：

`./User/Vendor/MSFT/Policy/Config/InternetExplorer/DisableAdobeFlash`

且必须完全正确地大写，否则无法工作。请记下来，或在制作 MDM 配置文件和策略时备查。

这种特殊格式的行称为自定义 OMA-URI。请记住，OMA 是开放移动联盟，URI 统一资源标识符。它基本上是你想用 MDM 触达的地址或值。

使用 Intune，你将创建自定义配置文件类型，如[图 3.21](#c03.xhtml#figure3-21)所示。

![Figure 3.21 Create a Custom profile type for ADMX-backed policies with no GUI.](images/c03f021.jpg)

**[图 3.21](#c03.xhtml#figureanchor3-21)** 为无 GUI 的 ADMX 支持策略创建自定义配置文件类型。

你需要的最后两条信息埋藏在 MDM 文档中，我直接告诉你“数据类型”和“值”需要什么：

*   “数据类型”使用 `String`。
*   “值”使用 `<enabled/>`（无空格）。

你可以在[图 3.22](#c03.xhtml#figure3-22)中看到这些。

![Figure 3.22 Creating a custom OMA-URI setting](images/c03f022.jpg)

**[图 3.22](#c03.xhtml#figureanchor3-22)** 创建自定义 OMA-URI 设置

![image](images/warning.jpg) 我见过一些文档显示 `<enabled />`。即小于号、单词 `enabled`、一个空格、斜杠、大于号。当我使用该语法（添加空格）时，它无法工作，但某些 MDM 服务可能需要。

保存策略后，执行分配给所有用户（未显示）。

回到 Windows 10 机器，如果 IE 仍打开则关闭。然后再次与 MDM 同步，从 MDM 服务获取此设置。接着返回 Flash 播放器测试 URL，在广告弹出前，你应该看到[图 3.23](#c03.xhtml#figure3-23)所示内容，不再有弹跳的 Adobe Flash 动画。

![Figure 3.23 Flash should stop functioning in IE now.](images/c03f023.jpg)

**[图 3.23](#c03.xhtml#figureanchor3-23)** Flash 现在应在 IE 中停止运行。

这里发生了一个非常巧妙的底层过程。请记住，这不涉及组策略。你创建了一个自定义 OMA-URI 来分发 ADMX 支持的设置。既然是 ADMX 支持的设置，意味着它必须写入组策略风格的注册表项，对吧？没错。你可以在 `HKCU\Software\Policies\Microsoft\Internet Explorer` 中看到[图 3.24](#c03.xhtml#figure3-24)所示的结果示例。它将 `DisableFlashInIE` 设置为 `1`。

![Figure 3.24 No Group Policy involved, yet the Policies keys are manipulated.](images/c03f024.jpg)

**[图 3.24](#c03.xhtml#figureanchor3-24)** 未涉及组策略，但 Policies 键被操作了。

当你删除配置文件或终止策略设置时，设置会消失，就像组策略一样，恢复原始行为。

但同样，组策略引擎（也称为 GPsvc）完全不参与分发（或撤销分发）。

很巧妙。

话虽如此，并非每个 ADMX 支持的策略设置都是简单的启用/禁用值。有些 ADMX 项可能非常复杂，同样希望你不必深入 ADMX 内部，辨明其在组策略中的构建方式，并在 MDM 中“重建”它。MDM 服务应将你与这些细节隔离。

但如果你发现某 ADMX 支持的设置有无数基于文本的选项或其他可配置选项，你就得穿上更多装备，深入 ADMX 和 ADML 文件内部，弄清其行为，再将该策略制作成自定义 OMA-URI。

这里举一个复杂 ADMX 支持的例子太繁琐，会消耗太多篇幅，希望你永远不用这么做。

### 引入第三方 ADMX 文件

有时你可能需要分发微软“非内置”的策略。在组策略领域，这些通常以（旧）ADM 或较新的 ADMX 格式提供。

附带组策略 ADMX 文件的桌面应用程序不多。但有一些。这些是热门应用：

*   Office 2007 至今的 Office 版本
*   Acrobat Reader 和 Standard（说实话功能相当有限）
*   Google Chrome
*   Mozilla Firefox 正开始获得一些组策略支持。

还有一些其他的，但这些是你可能已在现有组策略中使用的重量级应用。你的 MDM 服务有方法引入第三方 ADMX 文件并将那些设置分发到 Windows 10 机器。

在组策略领域，引入 ADMX 文件的概念称为*使用* ADM 或 ADMX 文件。现在在 MDM 中，*只是为了与众不同*称为*引入*，对我来说听起来有点恶心。但这只是我个人感觉。

无论如何，记住之前的约定：微软维护的所有 ADMX 支持策略，嘛，都是来自微软的，正如我说的，（几乎）保证按预期工作。但对于第三方 ADMX 文件，微软态度较随意，不维护，因此不保证它们按预期工作。请记住，微软发布了我之前提到的管理模板技术预览版。截至目前，无法通过引入以点击方式添加 ADMX 模板。我衷心怀疑他们会添加此功能，似乎很容易实现。我无法展示分步操作，因为目前无内容可展示。但请留意这一可能性。

因此，目前步骤相当繁琐（又是）。

系好安全带，操作如下。

引入第三方 ADMX 分两步：

*   将第三方 ADMX 文件复制到自定义 OMA-URI
*   设置来自 ADMX 文件的值（与上一节所做几乎完全相同）

开始此示例，我将使用 Foxit Reader 的 ADMX，但同样，大多数第三方 ADMX 文件应适用。

你可能想知道为什么我不选 Adobe Acrobat Reader 或 Chrome 示例，我有充分理由：

*   **Google Chrome 及其 ADMX**：就要付印时，Chrome 获得了通过 MDM 遵循其 ADMX 的能力。官方分步说明见 `https://support.google.com/chrome/a/answer/9102677`。注意，并非每个 Chrome 设置在非域加入机器上实际生效。（PolicyPak 团队一成员花时间弄清哪些项目在非域加入机器上“完全正常”工作。若想查看，见：`https://kb.policypak.com/kb/article/284-which-items-in-chrome-will-and-will-not-work-when-nondomain-joined`。）
