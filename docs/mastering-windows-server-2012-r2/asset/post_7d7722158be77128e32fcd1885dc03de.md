# Domain Naming: A FSMO Example

To avoid the situation of duplicate names and to ensure the forest structure, Microsoft developed one DC to act as sort of central clearinghouse for domain creation, whenever you attempt to create a new domain or new name AD, DS stops and locates the DC in the first forest that is the “keeper of the names.” That DC is the domain-naming FSMO or domain-naming operations master. If AD on the new DC does not contact with the domain-naming FSMO, then it refuses to go further.

Remember, if you have a worldwide enterprise with dozens of domains, hundreds of offices all around the world, thousands of domain controllers, and hundreds of workstations, there is one and only one computer that serves as the domain-naming FSMO. If it were, in the Okinawa office and you in the New York office sitting at a server to create a new domain in the forest, then your computer would be unable to proceed until it contacted the Okinawa computer and got its OK on building the new domain.

# Why Administrators Must Know about FSMOs

In general, you need to know that the DCs act as FSMOs in your forest much all, and you need to do a little planning about which DCs will be FSMOs, and you need to know how to assign a particular FSMO role to a particular DC.

That reminds us, how to manage the FSMO roles by hand. The AD automatically picks a DC to act in each FSMO role—the first DC that you install—but it’s not right enough to manage those roles alone. For example, consider this scenario. Your company decides to plan with AD and sets up this first DC on a “junk” machine in a test-lab, the 1 GHz system with 1 GB of RAM. They see that AD works perfectly well, so they buying “big guns” to be the production DCs. They roll out these DCs, and things seem to work perfectly well.

They work until one Monday, comes to work, and AD apparently still thinks its weekend is not working. Administrators find that they can’t create new user accounts or joins a domain. Someone tries to install Exchange Server, but it complains about not having the authorization to change something the schema. The Cleveland office was supposed to create a new domain, but that’s refused, the remaining domain controllers complain that they can’t find the PDC, and account changes like password resets are clearly not getting to backup domain controllers.

What happened? Well, someone was playing in the lab that needed and an extra machine with which to do some experimentation. The 1 GHz system was just sitting there, still running Server 2003 and acting like an AD domain controller. But it wasn’t really relevant anymore, the weekend noodler reasoned, because the firm now has several dozen DCs running. So, the experimenter wiped the hard disk on the 1 GHz system and put Linux on.

# FSMOS AND GCS 1211

You see, by default, AD assigns the FSMO roles to the first DC that you install. In this story, 1 GHz system quickly served a very important role. But now it can't. And AD isn't smart enough to figure out that and nominate a new computer in that. You might say that our "sparkling" forest has lost its "fizz-moe." It's your job to transfer the FSMO roles to other DCs.

It's important to know where the FSMO roles live and operate in your environment. We have a few general recommendations on where certain roles should live in the domain and forest. Try not to spread roles across multiple domain controllers as much possible. For the most part, the primary domain controller of the forest root domain should be the PDC, Schema Master, Domain Naming Master and RID Master. Having them all centrally makes them easier to manage. Technically speaking, the Infrastructure Master role can operate on any domain controller in an environment where every domain controller is a GC server. If you are in a multicast environment where not all of your DCs are GC, you must place the Infrastructure Master role on a domain controller that does not have the global catalog. We will take a look at each role.

When the global catalog is needed in the login process. The global catalog has a little of everything. It has a subset of properties or attributes for every object in the forest. Remember, an object includes users, contacts, groups, computers, and other entities registered in Active Directory. Even if the global catalog isn't in the same domain as the user.

How many GCs are necessary? Typically it is dictated by how many sites you have. There are many uses for GCs: The most prominent is assisting in the login process. If all users assigned principal names (UPNs)@test.com within a multiple domain forest, domain controllers need to resolve which domain they actually belong. The global catalog provides this information. So, it would be nice if a global catalog was in a site where the users are logging onto the domain.

Since a global catalog has all of this information, Active Directory–applications like Exchange Server love global catalogs. Exchange Server uses the GC to find all recipients and distribution group members in the organization. It would be nice if the Exchange Server had a GC in the same site.

You'll have to weigh this against the potential replication traffic that the servers will receive from the other domains. Typically, the importance of global catalogs for login and Exchange Server significantly outweighs this consideration.
