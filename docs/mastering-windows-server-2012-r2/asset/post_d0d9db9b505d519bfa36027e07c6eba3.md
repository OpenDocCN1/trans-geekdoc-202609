## START OF AUTHORITY RECORDS

A Start of Authority (SOA) record is a single record within each zone. It has information about what DNS server controls this zone and parameters on how to resolve the records. It contains several values that should not be modified by editing the record. You should edit them on the Start of Authority (SOA) tab in the properties of the zone, as shown in Figure 6.23.

The following are the fields on the tab:

- **Serial Number** is the revision number of the zone file. This really counts with standard primary zones because the Active Directory replication has its own serial number, so to speak. Secondary zones compare their number with it to see whether their information is up to date. If it isn't, it's time for a zone transfer.
- **Primary Server** is this server in the zone which was initially up. You can switch a primary server to a secondary server and vice versa if you want to modify replication updates in your environment.
- **Responsible Person** This is supposed to be an email address of the person who administers the zone. Note that the @ is replaced by a dot (.). If you want to make someone really mad, you put their email address here!
- **Refresh Interval** is how long the secondary server can wait before attempting to check changes on the primary server. At this point of time, it compares the serial number of the SOA record with its own. By default it is 15 minutes. The value is in seconds within the actual record.
- **Retrial Interval** How long the secondary server wait before trying after a failed zone transfer? It is in seconds and defaults to 10 minutes.
- **Expires** How long can the secondary server continue to answer requests on after a zone transfer performed? The default is one day. This is also listed in seconds within the record, and the value is 86,400.
- **Minimum (Default) TTL** How long should these records be cached or, in other words, the Time's Time To Live (TTL) is an hour, or 3,600 seconds.

## NAME SERVER RECORDS

Name server (NS) records list the servers that can respond to queries for this zone. There will be at least one of these records in the zone. Like the SOA record, this is modified in the properties of the zone on the Name Servers tab, as shown earlier in Figure 6.5. The only value required in the NS record is the FQDN of the server. You will notice a notice at the bottom of the Name Servers tab stating that the IP address is retrieved value.

## Managing DNS Clients and Name Resolution

You can deduce that every computer is a DNS client. The DNS service is a vital component of the network even if Active Directory is not part of it. In addition, it is the only method for getting to your favorite Internet websites like: www.sysex.com.

On the Windows operating system, there are two areas concerning the DNS: resolving hostnames and registering hostnames and IP addresses through Dynamic DNS updates.

## HOSTNAME RESOLUTION

The Windows computer has two parts in the name-resolution process. This process is important that we'll call the "circle of life." One part, which is nearly dead, NetBIOS, and the other is DNS.(You could call it the hostname, but most admins call it DNS.) This circle consists of the steps a computer would take in resolving a given name, as illustrated in Figure 6.24.

The NetBIOS process involves the following steps:
1. Broadcast the name into the network and see whether someone answers.
2. Look the name up in WINS.
3. Look the name up in HOSTS file. This is another text file located in c:\windows\system32\drivers\etc. which lists NetBIOS names instead of hostnames.

The order of DNS steps is configurable, particularly through DHCP server. The broadcast step can be skipped, or WINS lookup can be skipped. The default on Windows Server 2012 R2 is to resolve through WINS first and then with HOSTS lookup always last.

The DNS process involves a shorter list:
1. Look the name up in HOSTS.
2. Look the name up in DNS.

The order of DNS steps is not configurable, but you can modify the behavior of DNS lookup. There are some good points about HOSTS file being first. If you are unable to access DNS server or you need redirect to another place, editing the HOSTS file works great. The name-resolution process cycles through both parts until it comes up with IP address. Either NetBIOS or DNS is basically application-dependent. Older Windows applications looked at name and considered it TCP/IP-based which affects how the name is resolved, is still part of Windows operating systems. Examples of this include the net view command and the ping command. The net view command is from ancient days of LAN Manager, which relied on NetBIOS. If you attempt to connect to a server using the command, you will see NetBIOS cache populated with the server name. This is displayed with nbtstat -c. The cache can be cleared.

## CONFIGURING CLIENTS

You can find the DNS and NetBIOS configurations in the IP properties of the network connection. Both are in the advanced settings. You can find the NetBIOS configurations on the WINS tab. Figure 6.25 details the WINS tab with the default configurations.

The settings enable LMHOSTS and default NetBIOS configurations to the DHCP server settings. First, by default the LMHOSTS file is empty. It would be good to disable this because malicious viruses have entered data into this file in the past.

Next, the NetBIOS settings default to what's on the DHCP server. The DHCP server scouts have an option NBT Node Type (046). This setting orders the first two steps in the NetBIOS process.
