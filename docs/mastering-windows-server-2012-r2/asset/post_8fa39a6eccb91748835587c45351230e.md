
In Windows Server 2012 R2, BranchCache improvements include automatic client computer database configuration and big performance and scalability increases. Clients can be configured through the use of a Group Policy object. If the GPO has not been configured for BranchCache, then BranchCache will check the cached server and use those settings by default.

One of the new advantages of BranchCache is the ability to reload specific content, like media and DVDs, on a cached server and then have content sent to the client cache.

Another nice advantage is the improvements that have been made to allow for better database performance. BranchCache has done this by using the Extensible Storage Engine (ESE). This is the same database technology used by Microsoft Exchange Server. It allows scaling of a single cached server to handle the increased demands of more people without having to increase hardware.

Hosted caches no longer need a server certificate issued by a certificate authority (CA). This will greatly reduce costs when deploying a public key with multiple CAs.

## SMB 3.0

Windows' file server bears the official name of SMB, which stands unfortunately for Server Message Block. (Blame IBM, not Microsoft, because an IBM guy first designed it) SMB has changed little over its roughly 25 years of life, with its biggest changes being of somewhat bigger block sizes so as to be able to make use of networks faster than 100 Mbps (appeared in 2000), the ability to handle multiple paths, and the addition of digital signatures to fool man-in-the-middle attacks (appeared in 2001).

Windows Server 2012 R2 sports a somewhat reworked version of SMB that handles slow networks better, handles encryption intelligently, cranks up throughput on file transfers, and supports PowerShell.

## Web Server IIS

Windows' file servers may not have changed much over the years, but that's not the case for Windows' web server. One key to hardening any server product is to keep the amount of code exposed to the Internet to a bare minimum; if a web server can support, for example, something called FastCGI but your website doesn't need FastCGI, why run FastCGI on an Internet-facing server and risk the possibility that someone discovers a way to use IIS's FastCGI to hack the server? Clearly so it'd be to strip your web server software of the things you're not going to need. (Security folks call this "minimizing the attack surface.") Sometimes we think they do too much (Halo).

The perfect web server would be composed of dozens of small modules, of which could be removed or added as needed to allow the web administrator to build a web server that did exactly what she needed to...but no more. That was the guiding light for Windows Server 2008's IIS 7.0, a complete overhaul of IIS including some of the latest technologies, using WinRM. (When you're doing administration of an IIS 7 box, you're using that protocol rather than RPC.)
