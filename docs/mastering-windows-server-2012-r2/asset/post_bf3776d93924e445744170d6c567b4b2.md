
# PREPARING TO PROMOTE THE MEMBER SERVER

Before you promote your Windows Server 2012 member server to a domain controller, make sure the domain has a forest functional level of at least Windows Server 2003. If you are going to promote a Windows Server 2012 into a forest with a forest functional level of 2000, you will get an error.

# PERFORM A SWING MIGRATION

A swing migration involves these basic steps:

- 1. Check your domain for errors.
- 2. Add the Active Directory role to the member server.
- 3. Run the Active Directory Domain Services Configuration Wizard with Schema Admin, Enterprise Admin, and Domain permissions.
- 4. Perform post-migration steps, such as placing FSMO, changing the IP address, and other changes.
- 5. Redeploy the source domain controller as necessary.

The ADSCW will automatically run adprep /forestprep and adprep /domainprep the schema-respective infrastructure master.

# PREP THE FOREST/SCHEMA AND DOMAIN

As with the in-place upgrade, the existing forest and target domain need to be prepped for Windows Server 2012's Active Directory changes. ForestPrep, DomainPrep, and GPPrep are required to run in the "Migrating with an In-Place Upgrade" procedures.
The other way of extending the domain is to start the Active Directory Domain Services Configuration Wizard right away. As we mentioned before, adprep.exe is integrated into the wizard, and it will take care of all the necessary steps. Whichever you choose, the rollback procedures at this point of the game are the same as for the in-place update. Restore the system state data on the schema master domain controller.

# BUILDING A WINDOW SERVER 2012 MEMBER SERVER

The target domain controller will start as a Windows Server 2012 member server in the original domain. In preparation, the Active Directory Domain Services and DNS role must be installed before running the Active Directory Domain Configuration Wizard.

# VERIFYING DNS

Since the new domain controller will support DNS, it should be added as a name server to the applicable forward and reverse zones. Once the member server is promoted as a domain controller, the DNS zones will be replicated.
To ensure proper name resolution of the domain controllers, the DNS resolution should be tested using Nslookup and Dcdi, which we covered earlier in this chapter.

# PREPARING THE SOURCE DOMAIN CONTROLLER

You need to decide what will be done with the source domain controller prior to performing the operation. If the server is to remain in the domain as a domain controller, little needs to be done. If it will be redeployed, you must consider how to replace the network's reliance on it.
The following data for the source server should be collected in order to apply similar settings to the target member server after the domain controller promotion:

- Server name.
- IP addresses (IPv4 and IPv6).
- Assigned Active Directory site.
- Assigned OU.
- Applied GPOs and RSOP output. You can type,
  `gresult /scope GPOResult.txt`
to push the results to a text file.
- Assigned FSMO roles. These will be transferred if the server will be decommissioned.
- Global catalog role.
- Additional services, as DHCP, file and printer sharing, and Internet Authentication Services for VPN connections.

Finally, perform system state backups for all domain controllers and file system backups for essential services to be migrated outside Active Directory Services.

# PROMOTING THE MEMBER SERVER

The Active Directory Domains Configuration Wizard does the meat of the work. You should select the option "Add a domain controller to an existing domain" for the deployment configuration. Also, you should enable the options for the DNS and Global Catalog roles as required.

After the wizard has finished, a restart is required and the DNS service should be configured on the target domain controller. Although the Active Directory integrated DNS zones have been replicated to the domain controller, the DNS service may not be showing.

- 1. On the source server, enumerate the DNS zones and application partitions:
  `dnscd /enumzones`
  `dnscd /enumdirectorypartitions`
- 2. On the target server, enumerate the DNS application partitions and zones using the previous command.
- 3. Compare the results between the two servers.

If they are not listed, you can use the dnscd /enlistdirectorypartitions command to force the new DNS server to start sharing the partitions. The zones should be listed since the domain controller is listed as a name server for the zones.

`dnscmd /EnlistDirectoryPartition <QDN of partition>`

- 4. As a last step, examine the DNS server settings and configure them to your company standard.

# POST-MIGRATION PROCEDURES

You should verify the domain services. You can perform tool-based tests with the Event Viewer, DCDiag, and NetDiag to see if there are initial problems. You should perform user acceptance tests well, such as attempting to log on and accessing network resources with the new domain controller as the available authentication service.
Given the plans for the migration process, you should perform the following:

- FSMO role transfers and GC assignment.
- IP address reassignment.
- Network name reassignment. The domain controller can be renamed using the System applet (sysdm.cpl) in Control Panel or the rename command.
- DNS, reassignment of the standard primary zones may be required.

> **GOOD TO KNOW...**
After adding a Windows Server 2012 domain controller to an existing domain, you should transfer the FSMO roles to the newest domain controller.

# REPURPOSING HARDWARE

The swing migration provides the opportunity to redeploy the source domain controller. The swing migration provides the opportunity to redeploy Windows Server 2012 on the original server. This procedure requires available machine capable of supporting Windows Server. Follow these steps:

- 1. Prep the forest/schema and domain.
- 2. Build a Windows Server 2012 member server on the spare machine.
- 3. Verify that DNS is supporting Active Directory.
- 4. Prep the source server.
- 5. Promote the member server.
- 6. Run DCPromo to uninstall Active Directory from the original controller.
- 7. Build a Windows Server 2012 member server on the original hardware.
- 8. Promote the member server to a domain controller.
- 9. Perform post-migration procedures including reviewing FSMO placement.
- 10. Once the domain and domain controller services are validated, the spare can be decommissioned by removing the Active Directory role or running the PowerShell Uninstall-ADDDomainController.

# SWING MIGRATION: PROS AND CONS

To summarize, these are the benefits of swing migrations:

- They are gradual in implementation. Once the first Windows Server 2012 domain controller is introduced, the rest of the domain controllers can be upgraded or replaced as necessary.
- Users keep their old SIDs and the domain keeps its old trust relationships, so any servers in other domains—resource domains containing perhaps file and print servers or email servers—will still recognize those users without trouble.
- Users keep their old passwords.
- The migration offers the opportunity to redeploy Windows Server 2012 on the original server.

There are few disadvantages of this method. These are the most common pain points:

- More preparation and planning are required to ensure a smooth delivery.
- Any leftover junk remains in your Active Directory database.

# Migrating with a Clean and Pristine

The third approach is characterized as clean and pristine (C&P). In this approach, you leave your existing domains alone and create a new, empty AD domain. You then use a migration tool to copy user and machine accounts from the old domain (or domains) to the new AD domain.
