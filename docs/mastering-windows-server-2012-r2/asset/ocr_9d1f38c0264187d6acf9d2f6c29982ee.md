If you look at this carefully, you can conclude some interesting things. First, Hyper-V allows a true node. Not only are the disks preserved, but the memory and the configuration are too. You can change memory and add disks and networks and still be able to revert the original situation. In a lab or test environment, there is no reason why you couldn't repeat this process. You can have a chain or multiple chains of checkpoints to a maximum of 50 (you really don't go that there). A limitation of this process is that it works with virtual disks. If your VMs pass-through disks in a lot of scenarios, you can't checkpoint.

Finally, although a checkpoint is quick and very tempting in a lot of scenarios, I highly recommend you use this feature with care and diligence and preferably in the confines of your lab or test environment. Using any VM in production with large checkpoints would notice a performance hit until the checkpoints were removed.

Taking a checkpoint can be done in various ways, similar to changing power states. To do it from the Hyper-V management console, right-click the VM and select Checkpoint from the context menu. Figure 27.40 illustrates the checkpoints of Hyper-V Manager. The base checkpoint is OS Initial and it has two subtrees called Join and Before Service Pack.

# CHECKPOINTS WITH POWERSHELL

If you need to script your checkpoints, then the new Checkpoint-VM cmdlet is where you start. Type the following to create a new checkpoint of a virtual machine with a custom name:
Checkpoint-VM -Name "WS2012R2-SRV" -SnapshotName "Before Service Pack Install"
