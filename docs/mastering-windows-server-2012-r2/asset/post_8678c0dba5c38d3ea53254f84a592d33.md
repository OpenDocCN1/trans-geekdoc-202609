
# WHY TCP: WHAT DOESN'T IP HAVE?

So, just what is wrong with IP that TCP needed inventing? IP doesn't have any concept of a connection—if we had to describe it as analogous to an existing system we were comfortable with, it would be the postal service. Every IP packet is like a postcard that goes through the system. Like the postal service, some IP packets get lost in transit and if you send two IP packets, one after the other; they may arrive in the opposite order. Unlike the postal service, some IP packets get delivered twice!

An IP packet, just like a postcard, cannot contain a simple message like “Please ignore the previous message” because it is impossible to be certain that the sender and recipient will agree on what the previous message was. With occasional packet duplication, a recipient could believe that they are to ignore the message told them to ignore the previous message—confusing!

So, for some kind of communications, these restrictions need to be overcome—and a system of communications needed to be developed to allow for something more akin to a telephone conversation, with a start, an ordered exchange of information, and an end. This is what TCP provides.

Strictly speaking, TCP adds to IP the following attributes:

- Handshaking: An exchange like “How do you?” “Fine, how are you?” “Oh, fine too,” in TCP is known as the three-way handshake and consists of short messages, known as SYN, SYN/ACK, and ACK. SYN is for “synchronize,” and ACK is for “acknowledgment.”
- Sequencing: A counter of bytes sent/received to ensure that no bytes are presented twice to the application and bytes received out of sequence be reordered. These sequences (on each side of the connection) are set by the initial SYN and acknowledged every ACK.
- Flow Control: A clever system called sliding windows keeps traffic flowing without having to wait and taking too much memory in the server or receiver.
- Error Induction: An application that closes unexpectedly (akin to a hang up on a phone conversation) can be signaled to its communicating partner with a reset (rst) packet.
- Ports: This is a little like having a switchboard that allows you to connect a company at one number and to any of thousands of extensions so that your conversation can be separated from other conversations with employees at that company.

# Sockets, Ports, and Winsock

Almost no one writes applications that talk directly in IP. Few still write applications that directly control TCP, particularly on Windows, because various security measures prevent any application other than the network stack from creating TCP packets.

Instead, applications communicate with the TCP layer by using something known as a socket. Sockets are not unique to Windows; they have been around since the earliest days of the Internet.

A socket, in Internet terms, consists of five things—a source address, a destination address, a source port, a destination port, and a protocol (in this case, the protocol is TCP). A pair of matching sockets (where the source address and port of one socket are the destination address and part of the other, and vice versa) constitute a TCP connection. A socket is unconnected if its destination port and address are zero, and it is unbound if its source port and address are zero. An unbound socket is also unconnected.

Although you know what an address is, we have not yet told what a port is. Quite simply, it's a number from 1 to 65,535, to make sure that sockets can be distinguished from one another. The ports below 1024 are considered reserved, in that they are assigned to a particular protocol. For instance, ports 21 and 20 are assigned to FTP.

The life cycle of a connection starts in one of states, depending on whether it is a server-side socket or a client-side socket. A server-side socket will start off in the LISTENING state, which requires a socket to be bound to a source address and port. The client-side socket, meanwhile, will start in the SYN-SENT state, when it starts its handshake with the server. This requires that the socket be bound and have a destination address and port. The server responds with its SYN-ACK, creating a new socket with the same source address and port as the listening socket, which it puts into the SYN-RECEIVED state. Ending the handshake, the client sends its ACK and puts its socket into the ESTABLISHED state. When the initial ACK is received, the server too puts its socket into the ESTABLISHED state.

You can use the netstat command to get an idea of what is connecting to your machine and what state it is in. Figure 20 shows the output from running the netstat command.

# ONE PORT MEANS TWO SOCKETS

It is not true that a connection to a listening socket creates a connection on a different port. It is an erroneous statement made by many who do not understand there are two ports in play—one at each side. An example is a connection to a web server—say a client at 192.168.1.2 wants to connect to the web server at 10.20.30.40, and this is the client's first connection since it started.

We'll use some shorthand to describe the sockets. Each socket will be described as [source address, source port, destination address, destination port]. The web server is LISTENING at port 80, meaning it has a socket bound to address 10.20.30.40, source port 80, TCP; destination address 0.0.0.0, destination port—[10.20.30.40, 80, TCP, 0.0.0, 0]. The client creates a socket [192.168.1.2, 1024, TCP, 10.20.30.40, 80]. How? Where does it come from? The first number is around 1024, so it's the first from the unreserved range, and it will be used as the source port for the first connection. The next connection will connect from port 8750. This is assigned randomly by applications and is rarely seen. Consider a security feature traffic is not easily identified.

The client sends a SYN to the server to initiate the handshake. When the listening socket receives the SYN, the TCP creates a copy of it with the destination address and port to match the connection request, so now it has two sockets: [10.20.30.40, 80, TCP, 0.0.0, 0] in the LISTENING state and [10.20.30.40, 80, TCP, 192.168.1.2, 1025] in the SYN-RECEIVED state after SYN-ACK. This socket is paired with the client socket of [192.168.1.2, 1025, TCP, 10.20.30.40, 80] to form the connection. When the client receives the SYN-ACK and sends its ACK, both sockets go to the ESTABLISHED state. A new socket, but by port, has been created at the server.

From now on, it is meaningless to call one socket the server and one the client; they are both on equal footing. Each can send and receive data at any time. Although protocols insist on strict command and response, TCP is an asynchronous protocol that allows any side to send data at any time.

To terminate the connection gracefully, one of the communication (we'll call the client) will send a FIN and set its socket into the FIN-WAIT-1 state that is waiting for an acknowledgment of FIN, as well as for the other (we'll call the closer) to close the socket with a FIN. The closer can keep on sending data but will not receive more data from the closer after the FIN that is received.

At some point, pretty quickly after receiving the FIN, the closer will send an ACK that acknowledges the FIN. This knows that it is not receiving anything more but that it's waiting for the application finish and close. When the closer receives this ACK, it will enter the FIN-WAIT-2 state.

The closer will eventually finish sending data and send a FIN to indicate that the application is finished. After sending the FIN, the closer enters the LAST-ACK state (it's waiting for an ACK—the last ACK—from the closer), and when the closer receives it, it will enter the TIME_WAIT state and send an ACK to the closer.
