
Remote Desktop Session Host The RD Session service enables the server to host Windows-based programs or a full Windows desktop. This is a required service for the role.

Remote Desktop Virtualization Host The RD Virtualization Host service is integrated with Hyper-V to allow users to connect to a virtual machine on a server hosting Hyper-V. It can be configured so that users will connect to their own virtual machine and allow users to run multiple operating systems simultaneously. This service requires the Hyper-V role and is needed if you are using the Hyper-V role.

Remote Desktop Licensing The RD Licensing service manages the Client Access Licenses (RDS CALs) that are needed to connect to an RD Session Host. It is possible to run Remote Desktop Services without licenses for a limited period of 120 days. This allows you to deploy, configure, and test the server.

Remote Desktop Connection Broker The RD Connection Broker is used for session load balancing and reconnection in an RD Session Host farm. It's also required to support RDS Remote Applications that allow users to launch applications on the RD Session Host via Internet Explorer.

If you are using multiple Session Hosts, the RD Connection Broker can redirect connections to the servers that are the least busy, which provides load balancing. Additionally, if a user is disconnected, the RD Connection Broker will ensure they are reconnected to the same server where their session is active.

Remote Desktop Gateway The RD Gateway service is used to allow users to connect to RD Session hosts and remote desktops over the Internet. This service requires additional roles including Web Server (IIS), Network Policy and Access Services, RPC over HTTP Proxy, and Remote Server Administration Tools.

We covered Remote Desktop Gateway in much greater depth in Chapter 17, including how to add the required services and enable it.

Remote Desktop Web Access The RD Web Access service allows users to access RemoteApp and Remote Desktop Connection through a web browser. If the clients are running Windows 7, they can access these through the Start menu on their system. This service requires additional roles including Web Server (IIS) and Remote Server Administration Tools. IIS is short for Microsoft's Internet Services.

## APPLICATION COMPATIBILITY

If you are using the RD Session Host to host applications for end users, you should first install RDS before installing the applications. Applications that are installed before adding the RD Session Host may not work correctly in a multiple-user environment.

Although some applications will work in multiuser mode even if they've already been installed, many will not. If you've already installed applications that you want to use with the RD Session Host server, you should consider uninstalling the applications before adding the Remote Desktop role.

## Easy Print

A new feature available since Windows Server 2008 is called Easy Print. Easy Print ensures that client printers are always installed in remote sessions without requiring printer drivers to be installed on the terminal server. There have no updates to Easy Print since Windows 2008 R2.

This might not seem like much, but in the past, you were required to install printer drivers on the terminal server for all the printers used by clients. If you have just 50 clients and were using 10 different print devices, you'd then need to install printer drivers for all 10 print devices on the server even if they were already installed on the client's systems.

Now you may be wondering what you need to support Easy Print. The answer is nothing. The support is there automatically as Remote Desktop Services is installed on Server 2008 and R2.

Clients need be running RDC 6.1 and the Microsoft .NET Framework 3.0 with SP1. RDC 6.1 is backward compatible with XP SP3 with a download, as mentioned earlier..NET Framework 3.0 with SP1 is available for download for XP clients from Microsoft's download site: http://www.microsoft.com/downloads. Search for "Microsoft .NET Framework 3.0 Service Pack 1."

## Single Sign-on

Single sign-on (SSO) is for the ability to provide their credentials once and use these credentials once and again. As long as these credentials have adequate permissions, users are not asked to provide them again. Without single sign-on, users can be queried several times to provide the same username and password.

You can implement single sign-on for users who access the RDS server using Windows XP SP3, Windows Vista, and Windows 7 clients or Windows Server 2008 or 2008 R2 servers. Two settings are required in the RDP TCP/IP Connection properties. You'll see graphics of these later, but here are the two settings:

- Ensure that the Security layer is set to Negotiate or SSL (TLS 1.0) on the General tab of RDP TCP/IP Connection.
- Ensure that "Always prompt for password" is not selected in the "Log on" settings of RDP TCP/IP Connection properties.

In Windows Server 2008, SSO was difficult to set up. In Windows Server 2012 (including R2), SSO has been simplified to work mostly out of the box. There is a small pitfall to this ease of enabling: the client must support RDP 8.0, the virtual desktop infrastructure must be Windows 8, and the servers must be 2012 and above. If you require a mixed environment, you must configure SSO the traditional way.

## Network Level Authentication

Network Level Authentication (NLA) can be used in Remote Desktop sessions to provide better security. When adding the Remote Services role, you need to specify whether NLA is required.

NLA ensures that the authentication is completed before a Remote Desktop connection is established. Without NLA, there is a small window of opportunity for a malicious user or malicious software to attack.

NLA is available by default in Windows Vista, Windows 7, and Windows 8. It relies on the Credential Support Provider (CredSSP).

Windows XP does not support NLA. However, if you upgrade to SP3 and enable CredSSP, you may need to modify the registry to use CredSSP. Check these two Knowledge bases for more information:

- KB 95108, "Description of the Credential Support Provider (CredSSP) in Windows XP Service 3": http://support.microsoft.com/kb/95108
- KB 95116, "Description of the Remote Desktop Connection 6.1 update for Terminal Services": http://support.microsoft.com/kb/95116

If your clients are Windows XP SP3, they cannot connect using NLA, and NLA should not be enabled.

## Licensing Mode

Youll be required to select the licensing mode when you configure Remote Desktop Services. The licensing mode specifies what type of Remote Services Access Licenses (RDS CALs) you use. You have three choices:

**Configure Later**: You'll have a period of 120 days to configure and select a licensing mode. It is common to choose this early in the deployment cycle and then configure the RDS CALs once you've worked out the kinks in your RD.

**Per Device**: A per-device CAL is issued to a client computer or device. If the licensing mode is set to Per Device and a licensing server has been configured, the licensing server will give the device a temporary license the first time the device connects. The second time the device connects, the licensing server will attempt to issue it a permanent license.

The licensing server will enforce per-device CALs. In other words, if a per-device CAL doesn't exist for the device and an RDS CAL isn't available to be issued, the connection will be blocked.

You should use per-device CALs if multiple users will use the same device to connect to an RD Session Host server.

**Per User**: A per-user CAL allows a user to connect to RD Session Host from any number of devices. Interestingly, the licensing server doesn't track the per-user CAL. This can make things both easier and more difficult. It is easier to manage on a day-to-day basis because the RD Session Host won't stop users from connecting. However, administrators have a responsibility to ensure that appropriate CALs have been purchased, which does take some extra administration.
