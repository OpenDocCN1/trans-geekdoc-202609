Adprep /domainprep (including /gpprep) requires membership in the following group:

- Domain Admins

- Enterprise Admins

You will need to run the command manually, as follows:

1. Open an elevated command prompt on the Windows Server 2008 R2 domain controller you wish to upgrade.
2. Run adprep at the command prompt. Type (substituting your DVD/CD drive letter for d: if necessary) d:\support\adprep adprep and press Enter.
3. To start the process of getting ready for the in-place upgrade, run adprep by typing adprep /forestprep and press Enter.

This will show all of the syntax options along with a small explanation.
You'll see something like this:

```
D:\support\adprep>adprep /forestprep
```

ADPREP WARNING:

Before running adprep, all Windows Active Directory Domain Controllers in the forest will be upgraded to Windows 2003 or later.

[User Action]
If all domain controllers in the forest run Windows Server 2003 or later and you want to upgrade the schema, confirm by typing 'C' then press ENTER to continue. Otherwise, type any other key and press ENTER to quit.

At this point, you might be tempted to skip reading the text and just hit Enter. This would abruptly end the command. Remember the text you have read.

4. Type c and press Enter to see adprep in action.

This will produce a blur of text and innumerable periods.

This continues when AD imports and installs a bunch of schema changes. Finally, it says the following:

Adprep successfully updated the forest-wide information.

A rollback after changing the schema requires getting ready the system state on the domain controller with the Schema Master role. The system state data will contain the latest backup of the Active Directory database. The schema master is the primary controller for schema replication, so restoring its Active Directory database will include the schema. This will be replicated to the other domain controllers.

If you have not run adprep for read-only domain controllers, now is a great opportunity to do so. I always recommend it to find possible RDC and to validate that it has been done previously.

7. Type adprep /rodprep.
To summarize, before you can upgrade a Windows Server 2008/2008 R2–based AD domain to a Windows Server 2012-based AD domain, you must do the following:

1. All domain controllers must be the 64-bit version of the system.

2. Upgrade the forest by running adprep /forestprep on the schema FSMO computer for your forest, even if machine is not in the domain that you are going to upgrade.

3. Upgrade the domain structure by running adprep /domainprep /gprep on the infrastructure FSMO for each domain that you are going to upgrade.
4. Optionally, run /rodprep to prepare for read-only domain controllers.

# Running Setup

Now you're ready to run Setup:

1. Insert the DVD (or ISO).
2. Double-click it in My Computer if it doesn't autostart.
3. Select the Setup option.

Setup will warn you about anything that will change in this upgrade. It will also check that your forest-prepped and domain-prepped properly. From there, Setup runs hands-off, and there's nothing to do until it's finished and you log onto onto your newly upgraded Windows Server 2012 DC for the first time. At this point, you're upgraded!

# IN-PLACE UPGRADES: PRO AND CONS

The following factors are favor of in-place upgrades:

- They don't typically require new machines.
- Your users keep their SIDs, and the domain keeps its old trust relationships, so any servers in other domains—resource domain contains includes file and printer email servers, for example—will recognize those users without trouble.
- The users keep their old passwords.
- It's a relatively simple, quick upgrade.
- If you're going from 2008-based ADs to 2012-based ADs, then the upgrade is basically trouble-free.
- In-place upgrades from Windows 2008 R2 are seamless and simple.

Some of the limitations are as follows:
- The upgrade path is somewhat limited. The Windows Server supported versions are 64-bit only. Many organizations deployed 32-bit domain controllers when Windows Server 2003 became available, so an in-place upgrade may not be.

# MIGRATING WITH A SWING MIGRATION

The swing migration is a method used to upgrade a domain by introducing new domain controllers running the newer operating system and decommissioning the old ones. This is particularly useful when an in-place upgrade is not feasible due to hardware constraints or specific requirements.

The swing migration involves these basic steps:

1. Prep the forest/schema to be compatible with Windows Server 2012.
2. Prep the domain for Windows Server 2012.
3. Prep the original domain controller for decommission or change.
4. Prep the new member server and add the Domain Controller role, followed by running DCPromo.
5. Perform post-migration procedures considering FSMO placement, IP address changes, or other changes.
6. Redeploy the source domain controller as necessary.

# PREPPING THE FOREST/SCHEMA AND DOMAIN

As with the in-place upgrade, the existing forest and target domain need to be prepared for Windows Server 2012. You must run ForestPrep, DomainPrep, and GPrep, but with Windows Server 2012 when you add the Active Directory Services it will run automatically, similarly to what we discussed in the “Migrating with an In-Place Upgrade” section.

Rollback points of all of the game are the same as for the in-place upgrade. You must restore the system state data on the schema domain controller.

# BUILDING A WINDOWS SERVER 2012 MEMBER SERVER

The new Domain Controller will start as a Windows Server 2012 member server in the original domain. In preparation, you will need to install the Active Directory Domain Services role and DNS role prior to running the Active Directory Roles process.

# VERIFYING DNS

Since the new domain controller will support DNS, you should add it as a name server to the applicable forward and reverse zones. Once the member server is promoted as a domain controller, the DNS zones will be replicated.

To ensure proper name resolution of the domain controllers, you should test DNS resolution. Perform checks of the service resource records using nslookup and nsdig that we covered earlier in this chapter, in 5, “IP Address Management (IPAM) and DHCP Fail-over.”
