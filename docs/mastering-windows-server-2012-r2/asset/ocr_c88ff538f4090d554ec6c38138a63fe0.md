# ONE PORT END MEANS TWO SOCKETS

It is not true that a connection to a listening socket creates a connection on a different port. It is an erroneous statement made by many who do not understand that there are two ports in play—one at each side. An example is a connection to a web server—say a client at 192.168.1.2 wants to connect to the web server at 10.20.30.40, and this is the client's first connection since it started.

We'll use some shorthand to describe the sockets. Each socket will be described as [source address, source port, destination address, destination port]. The web server is LISTENING at port 80, meaning it has a socket bound to address 10.20.30.40, source port 80, TCP; destination address 0.0.0.0, destination port—[10.20.30.40, 80, TCP, 0.0.0.0, 0]. The client creates a socket [192.168.1.2, 1024, TCP, 10.20.30.40, 80]. How? Where does it come from? The first number is around 1024, so it's the first from the unreserved range, and it will be used as the source port for the first connection. The next connection will connect from port 8750. This is assigned randomly by applications and is rarely seen. Consider a security feature traffic is not easily identified.

The client sends a SYN to the server to initiate the handshake. When the listening socket receives the SYN, the TCP creates a copy of it with the destination address and port to match the connection request, so now it has two sockets: [10.20.30.40, 80, TCP, 0.0.0.0, 0] in the LISTENING state and [10.20.30.40, 80, TCP, 192.168.1.2, 1025] in the SYN-RECEIVED state after SYN-ACK. This socket is paired with the client socket of [192.168.1.2, 1025, TCP, 10.20.30.40, 80] to form the connection. When the client receives the SYN-ACK and sends its ACK, both sockets go to the ESTABLISHED state. A new socket, but by port, has been created at the server.

From now on, it is meaningless to call one socket the server and one the client; they are both on equal footing. Each can send and receive data at any time. Although protocols insist on strict command and response, TCP is an asynchronous protocol that allows any side to send data at any time.

To terminate the connection gracefully, one of the communication (we'll call the client) will send a FIN and set its socket into the FIN-WAIT-1 state that it is waiting for an acknowledgment of FIN, as well as for the other (we'll call the closer) to close the socket with a FIN. The closer can keep on sending data but will not receive more data from the closer after the FIN that is received.

At some point, pretty quickly after receiving the FIN, the closer will send an ACK that acknowledges the FIN. This knows that it is not receiving anything more but that it's waiting for the application finish finish and close. When the closer receives this ACK, it will enter the FIN-WAIT-2 state.

The closer will eventually finish sending data and send a FIN to indicate that the application is finished. After sending the FIN, the closer enters the LAST-ACK state (it's waiting for an ACK—the last ACK—from the closer), and when the closer receives it, it will enter the TIME_WAIT state and send an ACK to the closer.
