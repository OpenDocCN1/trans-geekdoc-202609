In the Management OS, you installed the Hyper-V role, but clearly you needed to do something in the guest to supply the required software components. The Hyper-V software for VMs is commonly called the Integration Components and is also referred to in Microsoft documentation as Virtual Service Clients (VSCs). The VSC version of a virtual machine must match the Hyper-V server version of the host.

# ENLIGHTMENT COMES IN TWO FLAVORS

Enlightenment exists in two variants, a general flavor and a more specific one. Generally speaking, an operating system that works with the VMBus interface is considered an enlightened guest. Older systems, such as Windows XP and Windows 2003 that need the VSCs to be first installed, are considered non-enlightened guests. The specific variant applies to the kernel: if the natively knows about the hypervisor, the operating system is said to be an enlightened kernel. This would include any guest running Windows 2008 or higher for server Guest OSs and Vista SP1 and for client Guest OSs. The advantage of an enlightened kernel is that it can further optimize access to the VMBus. For instance, Windows 2012 can bypass some internal software layers for network and disk access when it realizes the data is intended for a virtual device.

Only guests running Windows 2008 and higher have a version of the VSCs built in, although that version will need to be upgraded to match the current Hyper-V version of your guest; running a Windows 2008 guest VM on a Windows Server 2012 R2 host would be an example of this. For other operating systems, you will need to install the VSCs explicitly. One of the ways to do this is to insert an ISO file with the VSCs into the VM. This ISO file comes bundled with Hyper-V.

The VSCs are actually a set of modules installed in %systemroot% in the virtual machine partition. There is one <version> folder for each update of VSCs. Taking a look at its functionality, you see that it splits into two parts. On one hand, there are drivers for storage, video, and network. Another driver directly integrates with the kernel to optimize its performance running as a VM. On the other hand, there is a multipurpose service (vmcsc.exe) executable that is started with four different arguments to provide the following functionality:

**Operating System Shutdown Service** On request of the parent partition, this service will shut down the VM in an orderly manner.

**Heartbeat Service** The parent needs a way to tell whether the guest is still alive. If the parent can no longer hear the heartbeats, it is safe to assume the guest has a severe problem.

**Time Synchronization Service** A child partition has no direct access to the hardware clock. This service offers an alternative. Don't use this in an Active Directory domain environment, because that has its own time-synchronization infrastructure.
