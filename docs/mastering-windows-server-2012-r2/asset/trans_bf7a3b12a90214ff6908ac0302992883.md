## 域控制器与 Hyper-V

虽然虚拟化已经席卷了服务器计算的大部分领域，但虚拟化域控制器（DC）始终带有一点危险。不过诚实地说，由于虚拟化的灵活性和成本节约，我们拥有理想化域控制器的诱惑实在太大了，在各种虚拟化程序程序平台上运行着大量的这样的控制器。在 Windows Server 2012 之前，如果你虚拟化了域控制器，就必须经过重重关卡并处理官僚程序，以确保活动目录（Active Directory）的完整性。

当你虚拟化域控制器时，由于 Kerberos 认证对可靠时间记录的依赖，在虚拟机内部维护准确的时间同步问题对于你整个活动目录的健康变得至关重要。

为了说明可能出现的问题，请考虑一个运行活动目录 域控制器的虚拟机真实案例。它运行在一个独立的 Hyper-V 主机上，该主机没有加入网络组件（例如位于中央的交换机）。交换机收到了新的固件更新，并不小心将时间后设了一年。在维护期间，主机获取了这一点，并将自己的时间也后设了一年。然后虚拟 DC 执行了同样的操作。从那时起，它停止了与伙伴节点的同步，因为 Kerberos 认证已失效，很快很快你的电话就会被打响不停，用户们都在抱怨登录问题。

虚拟域控制器内部时间同步不佳的另一个问题是，如果时间跳跃太远，内部活动目录对已删除对象的管理将变得非常糟糕。某些对象将被永久删除，而另一些则不会。结果是森林被严重损坏。如果你仔细考虑，这种问题层列不穷。

总结：在生产环境中，请确保真正拥有正确的时间同步配置，特别是对于虚拟机。

## 我应该禁用时间同步服务吗？

为了解决虚拟 DC 的时间同步问题，许多人通过 Hyper-V 控制台禁用虚拟机的时间同步部分（集成组件的一部分）来解决他们的问题。遗憾的是，事实并非如此，长远来看，这样做产生的问题比解决的还要。

最佳实践是永远不要禁用时间同步服务，只需通过外部源来调整其功能。Hyper-V 项目经理 Armstrong 的此博客解释了管理时间同步的最佳方法：http://blogs.msn.com/b/virtual_pc_guy/archive/2018/11/19/time-synchronization-in-hyper-v.aspx。

读完 Ben 的文章后，查看微软的这个链接，点击页面中间“配置 Windows 时间以使用外部源”部分下的“Microsoft Fit 按钮”来自动配置外部权威机构：http://microsoft.com/816042。

在处理虚拟 DC 时，时间同步并不是唯一需要注意的事项。在第 27 章“使用 Hyper-V 进行服务器虚拟化”中，我们讨论了在使用检查点时影响运行 Windows Server 2012 之前的版本活动目录的 DC 的 USN 回滚问题。如果你在运行于 Windows Server 2008 的 Hyper-V 故障转移集群上运行虚拟 DC，你可能遇到的另一个问题是，除非你以非常特定的方式部署它，否则你必须确保在集群重启后至少有一个 DC 在集群外部！这篇 KB 文章仅仅是虚拟 DC 的一些支持策略：http://microsoft.com/888794。

现在你可能会想，“如果虚拟化 DC 会引起这么多问题，何费劲呢？”坦率地说，Hyper-V 和 Windows Server 2012 的活动目录在解决这些问题上走了很远，你将在下一节学习。

## 正常工作的虚拟 DC

从 Windows 2012 开始，虚拟 DC 获得了一个名为 VM-Generation ID 的标识符。这个新标识符的目的是提供一个安全网，防止虚拟 DC 在使用检查点回滚时导致意外的序列号（USN）回滚情况，如此处：http://tinyurl.com/USNRollback。

当部署 Windows Server 2012 虚拟 DC 时，VM-Generation ID 被存储在活动目录数据库中新创建账户的 mDS-GenerationID 属性下（见图 28.1）。虚拟机内部 Windows 驱动程序确保 VM-Generation ID 始终被独立跟踪。
