让我们来看环形结构。环 -1 并不是虚拟机程序的强制性特性，但大多数现代虚拟机程序都使用了它。这个环是 Intel VT 和 AMD-V CPU 虚拟化的核心特性。它是一个相对新的层级，优先级比环 0 更高。它允许内核真正运行在环 0 上，而无需在不包含虚拟机程序的旧版混合模型中进行所需的调整。这使得架构更加整洁，代码中的 Bug 更少，且理想情况下性能更好。

图表说明所有虚拟机都是平等的，但其中一个优于其他所有：主机或管理操作系统（Management OS），它负责所有虚拟机的管理和高级仲裁。它是所有硬件资源的默认所有者，并控制子节点的启动和关闭。

Hyper-V 虚拟机程序是微内核（microkernel）。正如术语所示，它的编写尽可能精简高效。它不包含 GUI 代码，并具备足够的智能来完成主任务：管理内存和对硬件的访问。其他（非微软）虚拟机程序可能采取不同的方法。在单内核方法中，虚拟机程序包含驱动程序，并对虚拟机之间的通信承担更多责任。单内核虚拟机程序的一个优势是，由于与访问硬件的驱动程序集成更紧，它可以提供更高的最高性能收益。另一方面，如果该虚拟机程序没有针对你特定硬件的驱动程序，你就运气了。对于成熟产品，这不应该是一个真正的问题。在微内核虚拟机程序中，驱动程序实际上位于父分区（在 Hyper-V 的情况下，这是一个 Windows 2012 服务器）。父分区拥有驱动程序，因此如果你的硬件有适用于 Windows 2012 的驱动，它就能与 Hyper-V 工作。

# 管理操作系统分区

该分区包含两个部分。下块运行在环 0 或内核模式下。它包含四个块，其中三个是讨论中的新内容：VMBus、Windows 驱动程序和虚拟化服务提供程序（VSPs）。上块对应环 3 或用户模式。这里只有与 Hyper-V 相关的组件。管理操作系统分区必须运行可以运行 Hyper-V 的 Windows Server 版本（这意味着 Windows Server 2008 或更高版本）以支持虚拟机程序。根据你的需求，它可以是完整的 GUI 版本，也可以 Server Core 版本。

# 虚拟机程序的安装和引导过程

你可能奇怪这个“鸡生蛋蛋”的问题：虚拟机程序需要 Windows 2012 父分区来执行任何操作，而父分区需要虚拟机程序。当你启用 Hyper-V 时，虚拟机程序被安装在硬件上。当系统下次启动时，虚拟机程序首先加载，管理操作系统作为特殊分区加载。随后虚拟机程序控制硬件并启动管理操作系统以及任何其他客分区。虚拟机程序是微内核，因此它不包含任何驱动程序。相反，驱动程序在管理操作系统中。这就是为什么管理操作系统必须支持 Hyper-V 的 Windows Server 版本。虚拟机程序使用 VMBus 在管理操作系统和客分区之间进行通信。VMBus 是一种高速通信总线，允许分区之间进行快速数据传输。这就是客分区访问管理操作系统中硬件驱动程序的方式。表 27.3 显示了最重要的虚拟机程序文件概述。

## 表 27.3：相关的虚拟机程序文件

| 功能 | 文件路径 |
| :--- | :--- |
| 虚拟机程序引导 | %systemroot%\system32\hvboot.sys |

这些 VSP 模块与 VSC 配对。例如，VSC 的存储模块将与父分区中的存储模块进行通信。这就是虚拟化的工作方式。非微软开发者也可以设计并构建自己的模块，因为相关的 API 都是开放的。

在涵盖管理操作系统的内核部分后，现在我们将进入用户模式组件。虚拟机管理器（VMM）负责管理所有虚拟机分区。每当启动虚拟机分区时，VMM 都会启动一个新的虚拟机工作（VMW）进程。该进程本身不执行任何工作，除了监控、关闭等。

# 是什么进程在“运行”虚拟机？

与混合模型中的类似工作进程相反，VMW 进程并不真正“运行”虚拟机分区。它只是控制它。如果客体正在进行任何操作，你无法通过非感知设备的数据传输除外来释放 CPU。

事实上，所有虚拟机分区都可能占用高达 100% 的 CPU，而管理操作系统分区中不会直接显示任何内容。要发现客体在做什么，你需要直接使用标准的服务器管理工具、性能计数器，或访问管理操作系统分区中的 WMI 提供程序。

管理操作系统分区中的最后一个组件是 WMI 提供程序。多年前，微软决定 WMI 将成为管理和监控系统资源的首选方式，Hyper-V 也不例外。WMI 提供程序在 MSDN 上有广泛的文档，并提供以下功能：

* 鼠标和键盘的状态报告
* 访问虚拟机 BIOS
* 管理和读取网络、串口设备、存储、客分区等的配置
* 读取当前属性
* 管理电源状态

从这些功能set中可以看出，WMI 提供程序包含了管理 Hyper-V 环境所需的所有功能。事实上，大多数 Hyper-V 的管理系统预计将使用 WMI。遗憾的是，WMI 接口对于大多数日常管理活动来说直接使用又太复杂。只有具有丰富 WMI 编程经验的人才能有效地使用它，而且越来越多的功能被引入到 PowerShell 中以帮助管理和维护，这无疑是未来的方向。
