## Trusts

As discussed in the chapter, computers within a domain allow users domain controllers to access their resources. The computers trusted the domain controllers. For users outside the domain, an explicit trust was created between the domain controllers to authorize the users to access the computers' resources. This section will go into more detail on concepts behind these explicit trusts and how to administer them.

The trusts have characteristics that can be configured when they are created. They can have one direction or two. They can be transitive or nontransitive. Each of these characteristics is considered in the type of trust that it will be created.

You can create and administer the trust using the Active Domains and Trusts snap-in. In addition, the netdom utility can perform the same operations.

## Defining the Domain: "Trust"

So now if you have a server that can authenticate a user, a DC. But for whom will it do authenticating? Not just system. A PC (whether workstation or server) can only use a domain's DCs to authenticate if PC "joins" a domain to become a "member". Systems that are not members of any domain can authenticate using local accounts; systems that domain members can either authenticate a user with local accounts or with their domain's DCs. In the world of Microsoft networking, we say that systems in any domain trust only local accounts but systems in a domain trust their domain's DCs. Joining a domain creates a relationship between the PC and the DCs. Before a domain trusts a domain controller to provide login services, and a domain controller trusts a workstation to provide those login services, Microsoft requires the agreement of both domain-level admins.

When you join a machine to a domain, you are typically logged in using an account that the domain recognizes, but when you try to join the machine to a domain, you'll see that the domain comes back and says, "Now I need an administrative account that the domain recognizes." Just as a treaty between two countries requires signatures from both local and domain-level admins, but trusts can go further than that. As discussed earlier, trusts occur between domains in a forest. You can also create trust relationships between forest and other domains. Thus, if your PC is a member of Forest.com domain and if Forest.com domain trusts your domain, then your local DCs can authenticate not only user accounts in Forest.com but also user accounts in Forest.com.

## Trust Relationships in More Detail

If you want to connect a domain to another clean and pristine, if you want domains in one forest to trust domains in another due to a merger, or if you're just sharing data between domains, then you must create a trust relationship. When a domain trusts another domain, the first domain is saying it was only willing to accept authentication from its own DCs, but now it'll accept authentication from the second domain's DCs as well.

But how do you build these trusts? In the case of domain-to-domain trusts, you can use the GUI or a command-line tool named netdom.

## Trusts Have Direction

To understand trusts in depth, the first thing to grasp is that trusts have direction. Trusts can be built either way or two. The language to describe Windows Server seems to muddle the concepts. Refer to Figure 24.1 to get this concept down and use the terminology to get trust creation correct.

![img/trust_relationship_1262_0.png]

Any trust between two domains has a trusting domain and a trusted domain. The trusting domain is willing to accept login information and authentication from the trusted domain. For example, suppose you have two domains—a domain named Factory.com and another domain named Workers.com. Suppose that Factory.com is a domain that contains very few user accounts; instead, it contains machine accounts for several hundred servers. People with user accounts in Workers.com need to get access to data in Factory.com's servers.

Or, in other words, you nest the Factory.com domain to trust the Workers domain. "Resources" trust "accounts"

If you have never messed around trust relationships in the past, then read again so you're clear on it. The primary goal is to give Worker people access to Factory.com's data. Factory.com's service will of course not allow any users to get data unless they can authenticate those users. Factory.com cannot authenticate the users; only their home domain DCs can. Therefore, Factory.com must begin accepting authentication from Workers.com. That's the definition of "to trust" here: accept authentication from another domain's DCs. So, Worker folks get to use Factory.com's data because Workers.com is trusted, and Factory.com lets them believe it is trusting.

The automatically created trusts between domains within a forest are two-way in direction. Each domain trusts the other. Man created trusts may have no need to allow the trust in both directions, so the option to choose one-way trusts is still available.

## Some Trusts Are Transitive

One thing about a forest is that all of them trust each other because of transitive trusts—even if A does not trust B directly, it might be that A trusts D; D trusts C, and C trusts B.

We have illustrated the trust relationships with the trust potential earlier in the chapter "Kerberos and Trust". If the section had an equal geekky brother for yourself and he considers your sister a stub, the trust relationship between Mother and Mom works in the opposite direction. It would work if there was a forest of the neighborhood or a kind of more merry security devices to network through. As these trusts "flow through," there is a kind of "six degrees of Bacon" in that everyone trusts everyone.

This is the transitive nature of some trusts. The automatically built parent-child trusts and the forest-root-tree root trusts are transitive. Shortcut trusts and forest trusts are transitive, they are created manually. The transitive nature reduces the number of trusts needed to be created.

## Trusts Do Not Remove All Security

People sometimes fear trusts between two domains, thinking that if domain A and domain B trust one, then anyone with a user account in A can make mischief in B, and vice versa. That's not true at all. Establishing trusts between two domains just means that a system in domain A can recognize a user in B, and B in A. So this question: can a user in A do anything that he wants on system domain A? Of course not—group policies, user rights, and permissions control all of those.
