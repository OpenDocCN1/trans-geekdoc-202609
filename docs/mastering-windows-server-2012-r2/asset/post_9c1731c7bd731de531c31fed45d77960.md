# CONFIGURING THE FIREWALL

You have several firewall configurations to perform. The firewall needs to allow Remote protocols through it. This includes configuring the ports to allow communication that the Microsoft Management Console snap-ins requires. The following command enables ports associated with the Remote Administration group:

```
netsh advfirewall firewall set group="Remote Administration" new enable=yes
```

This group includes all MMC ports that can be accessed on the server. There are all the protocols so you can have fine-grained firewall policies to remotely manage MMC operations, such as Event Viewer, Disk Management, File and Print Services, and Task Scheduler.

Surprisingly, this group doesn't include Remote Desktop. It is part of its own group of the same name. It should be enabled with the following command, which, by the way, is the embedded field of netsh advfirewall firewall set rule. No real wizard is performed in generating this. (The new parameter indicates adding a new setting to the rule)

```
netsh advfirewall firewall set rule group="Remote Desktop" new enable=yes
```

If you want to administer the firewall from the MMC, you will need to also run the following command:

```
netsh advfirewall set currentprofile settings remotemanagement enable
```

Although the firewall should be enabled, there may be times, such as testing a new application, you may want to disable it. Here are the commands for turning it on and off:

```
netsh advfirewall set allprofiles state on
netsh advfirewall set allprofiles state off
```

You can also reset the firewall with this command should you make a configuration mistake:

```
netsh advfirewall reset
```

The last firewall command we will show is probably the most commonly used, to enable or disable a port. Here is an example of how to add and delete port 1433 for SQL Server:

```
netsh advfirewall add rule name="Open SQL Server Port 1433" dir=in action=allow protocol=TCP localport=1433
```

```
netsh advfirewall delete rule name="Open SQL Server Port 1433" protocol=tcp localport=1433
```

We also need to use the PowerShell cmdlet properties that you can use to configure the firewall. You can use this cmdlet to set rules, modify rules, and control behavior by changing the properties:

```
Set-NetFirewallProfile -Profile Domain,Public,Private -Enabled True
```

To remove a firewall rule just use this:

```
Remove-NetFirewallRule -Action Block
```

# Administering Server Remote Console

Before you get configuring the roles installed on the server, you need to be aware of the options for remote administration. We've touched on them briefly, and you will see them used in the configurations of the roles in the following sections.

Remote Desktop is a very reliable and secure method of administering remote standard installations, and it is available on Server Core as well. The Microsoft Management Console and its snap-ins are excellent for Server Core administration as long as the network supports it. A new option is Windows Remote Shell, which provides a command-line connection to the remote server.

# MANAGING SERVERS WITH REMOTE DESKTOP

Terminal Services (Administration mode) was released with Windows Server 2000. It was a welcome addition because it provided a virtual desktop environment of the computer you connected to. Windows Server 2003 improved it by making it a default installation. It is an essential method to perform remote work on servers. We have commonly installed and configured applications Windows servers located on the opposite side of the North American continent using this method. This is a reliable option for Server Core.

With Windows Server 2012 Server Core, you have to realize the desktop is still just the command prompt and few GUI tools. There are methods for publishing the command prompt of Server Core to your RemoteApp, but we don't recommend doing so. You will still need GUI tools as Task Manager, Notepad, and the Registry Editor, which are part of your Server Core essentials.

Remember, Remote Desktop and its firewall policy must be enabled to be available. We will tell this earlier in the "Initial Configurations for Server Core" section.

# MANAGING REMOTELY WITH MMC SNAP-INS

Administrators have found the Microsoft Management Console to be a versatile method of managing computers. Its strength lies in the use of the RPC protocol and integrated Windows authentication, making it quick and efficient in managing domain-based computers within a LAN.

You can run the authentication with alternate credentials. On the workstation, you can run the remote command to register these credentials:

```
cdkey /bfs1 /user:administrator /pass:P@ssw0
```

You could opt to leave the pass parameter empty to be prompted for password. After registering your credentials, you can connect to the server through the snap-ins.

In previous versions of Windows Server, you need to install the adminpak.msi package to have the snap-ins manage all the Windows services. In Windows Server 2012, the adminpak.msi package is replaced by the Remote Server Administration Tools. This features makes its installation easier and more fine-tuned. If you like, you can connect to another computer when you add a snap-in to a new MMC. Some snap-ins allow multiple servers to be added into one for consolidated administration. The following steps create MMC for managing the DHCP service on the Windows Server 2012 Server Core installation. Please note that these steps can be performed only after the DHCP service is started and authorized. This is discussed in the "Configuring the DHCP Service" section.

2. From the File drop-down menu, select Add/Remove Snap-in.
3. The Add/Remove Snap-in window is presented and lists the available snap-ins to add to this MMC instance.
4. Select the DHCP snap-in, and click Add. Then click OK.
5. In the MMC console, right-click the DHCP icon, and select Add Server.
6. In the Add Server window, the authorized DHCP servers are listed in the bottom area, as shown in Figure 3.11. Select the Server Core instance.
7. Click OK, and the selected DHCP server will be displayed and can be navigated through, as shown in Figure 3.12.
