
# RENAMING AND DELETING OBJECTS

As you can imagine, the decision to rename or delete something should be considered very carefully.
There's a very serious implication to this.

# RENAMING OBJECTS

Every object in Windows has a name. You use that name for logins, scripts, application configuration, and so on. For example, if you create a user Scorse, then Simona Corso will use that label to log in. Windows does not use that name to keep track of the object. That's because names change. Simona might get married and change her surname to Simona Red. That will require changing her username to SiRed. Windows needs to treat her as it always does. Windows won't want to find any resource on the network where Scorse used to change the reference to SiRed, as group memberships, file shares, mailbox associations, and so on.

# Understanding How a SID Comes into

We need something we can remember and type easily, so a friendly label is used. Windows has a special code for every object called a security identifier (SID). The SID is a globally unique identifier for every object in Active Directory. Every user object has a SID. Every computer object has a SID.

What happens when you rename a user or group, as a security principal? Sure enough, the name you know. In the case of Simona, she will remember. Windows tracks her user object only by the SID. Any resource permissions assigned to her user object or group memberships associated with her user object won't change. Her user object name has changed, but her SID has. Note that third-party applications use object names instead of SIDs will still require some administration to change the referenced object. But anything that integrates with Active Directory, such as SQL, SharePoint, or Exchange, will be OK.

# DELETING AN OBJECT

The other scenario you need to discuss is when you delete an object. If you assign permissions to SiRed, Windows maintains a list of permissions that are associated with her SID. The same happens if you assign permissions to a group of users. Windows will maintain the permissions associated with the SID of that object, not with its name.

# Restoring a Deleted Object

You have to be very careful about deleting a user or group object. If you accidentally delete them or you're told to restore them to their prior state, you cannot create a new object with an identical name. The SID is globally unique and is not tied to the name. A replacement SiRed object will have a different SID. The file share or mailbox that Simona used to have access to will recognize the new user object because it has a different SID than the old object. The only way to restore access to a deleted group or user object is to restore the deleted object from a backup.

There's few ways to do this, which Microsoft discusses at http://tinyurl.com/2wogo4. Microsoft added a new Active Directory Recycle Bin in Windows Server 2012, which will simplify the process of restoring recently deleted objects.

The point to remember is that the name of an object is not how Windows identifies the object. It uses a SID. You may re-create a copy of an object with the same name, but it will be a different object.

# A BEST PRACTICE

For this reason, we strongly recommend that you disable users when you are asked to remove a user by your manager or the human resources department. That turns the user off and blocks them from the network. Additionally we recommend creating a dedicated OU for accounts that have been disabled and that you move every account that you disable to this OU. Doing this gives you an immediate overview of all accounts that are not in use. There's always a chance that there has been a miscommunication or the person returns to work. Reabling their access is easy: enable their account. After an agreed cooling-off period of 30 or 60 days, you can go ahead and delete that object.

For your Active Directory domain, you can use this command to find inactive and disabled accounts:

```
dsquery user -inactive <number of weeks> -disabled
```

For example, this command will find users that are disabled and have been inactive for eight weeks:

```
dsquery user -inactive 8 -disabled
```

To delete a user or a number of users, you simply select them, right-click, and select Delete. Deleting a user isn't much of a challenge from the command prompt. You can run the following to delete a local user account:

```
net user <username> /delete
```

This command will delete the SRed local user account:

```
net user SRed /delete
```

You'll use the dsrm command and the user's DN to delete an Active Directory user account:

```
dsrm "CN=Steve Red,OU=Users,OU=BigFirm,DC=bigfirm,DC=com"
```

You will be prompted to confirm the deletion. That's necessarily a bad thing, but you won't want that to happen in a script. You can get a confirmation prompt by running this:

```
dsrm "CN=Steve Red,OU=Users,OU=BigFirm,DC=bigfirm,DC=com" -noprompt
```

# Managing Groups

Treating a collection of users as a single entity for one or more purposes saves a lot of administration tasks. For example, instead of performing 100 operations to assign permissions to each of the 10 users to 10 resources, you can assign the users to a group (1 operation) and assign the group permissions to the resources (11 operations). The math makes it clear why you should use groups. Instead of dealing with individuals, you deal with the collective or the group.

# MANAGING GROUPS

In fact, this practice is always you use groups for assigning permissions. Therefore, we need to know how to create, modify, and remove groups. You'll learn about creating, controlling, and deleting groups using Active Directory Users and Computers and the command prompt.
