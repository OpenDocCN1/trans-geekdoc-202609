Objects
In short, within Active Directory is an object. For example, joe is an object. If you change his first name, you will change a property of Joe that is saved in an account called First Name. Also, if you create a computer account, then the groups, organizational units, sites, IP subsets, and so on are objects with properties.

### Schema
The schema holds for the objects you create. You can imagine the schema as a bunch of templates that you will use if you create joe. Active Directory needs to know what the user will look like, for example which properties it has, with first name and last name. This is provided by the schema. If you plan to install other software like Lync or after Exchange, the schema will be extended. If you look at the user before and after a schema extension, you will see that there are more options (properties) available on the user object, such as SIP address, after the extension. SIP stands for Session Initiation Protocol, and a SIP address is used for video and voice calls over Internet Protocol (IP).

### Group Policy
As previously explained, group policies are needed to configure settings for users and computers. They are very handy because you can configure one or more settings in one group policy and apply these settings to one or more users or computers by linking the GPO to the respective OU.

As an example, let's say you want to enable the RDP connection on each server so you can connect using it. It would be a lot of work to set this every computer by hand. You can enable the remote desktop setting in the group policy and link it to the OU where your server resides, and all the computers within this OU will be enabled for remote desktop.

You can link GPOs to sites, domains, and OUs. When you promote your server to a domain controller, two policies are in place by default. Every domain has a Default Domain Policy and a Default Domain Controllers Policy.

### Organizational Units
Organizational units, as the name implies, are used to organize objects in Active Directory, many users and computer objects. An OU is just a kind of container that contains similar objects. There are two main reasons for organizing objects in Active Directory. The first reason is to link Group Policy objects (GPO) and the second is that you need an OU for delegation of control.

Let's create an organizational unit name US and put Joe into this OU. Now you want Joe to always receive its network drives mapped. Therefore you need to create a GPO and link this policy to the US OU. Now Joe will receive the settings from the GPO and all his network drives.

The icon for an OU looks like a folder from Windows Explorer, and because of a similar usage, administrators often get confused and use the OUs like Windows folders to group things together to find them more easily. This is not the main purpose of OUs. Sure, you can use them to group and organize objects to find the objects more easily in Active Directory, Active Directory administrator should be to use as many OU as necessary to apply delegation of control and to control the object in the OU through GPOs.

**Default Domain Policy**
The Default Domain Policy is created as soon as you create your first domain. This policy contains settings for users and computers that will apply to the entire domain. It is important to understand that this policy is essential for your environment and should not be deleted. You can modify this policy, but we don't recommend it. If you need to apply custom settings to domain, you should create a new policy on the domain level and store your custom settings in your newly created policy.

**Default Domain Controllers Policy**
The Default Domain Controllers Policy is also a very important policy that is linked to the Domain Controllers container in your Active Directory. The settings configured in the Default Domain Controllers Policy are specific configurations that apply only to the domain controllers. If you promote a member to a domain controller, this server is automatically placed into the Domain Controllers container. There are few cases where you need to touch this.

### Forest
Forest is a single instance of Active Directory. In a forest you can have one or multiple domains that share the same schema. If you set up a single domain controller, you are basically creating the smallest possible forest. It is also called single-domain forest. A forest is also referred as a security boundary in which users, computers, and objects are accessible.

### Global Catalog
A global catalog contains information about every object in a multidomain Active Directory forest. The global catalog is stored on domain controllers that have been enabled as global catalog servers, and its data is distributed through Active Directory replication. There is only one global catalog per forest but multiple copies of it. Applications like Exchange query the global catalog to get information about objects within the forest. A global catalog contains only partial information about objects within the domain. A global catalog provides other services as well, as providing references to other objects in different domains, resolving user principal names (UPN), and user group membership caching.

### Trust
Trust is a connection between domains to access their resources, such as servers or applications. For example, this could be used if some users need to access files or information in the opposite domain. If you install a domain and children domain, Active Directory automatically creates a transitive trust. You can access objects from the root domain in the children, and vice versa. If you need access to resources in another forest, you could create some form of trust to connect both forests.

If you have one or more domains within the same forest that have contiguous namespace/or share the same schema root name, you create a tree. A contiguous namespace is for example, the root is. A tree is a collection of domains that are built in hierarchy.

# Creating a Single-domain Forest
As you learned, a single-domain forest is the simplest topology you can build. The general recommendation is to create one domain if you have fewer users. Whenever possible, you should create a single forest it is easier to set up and manage. The advantages are:

- Manage users and permissions in a central place
- Centrally secure and manage GPOs
- Provide additional services

You might wonder if you would stick with one domain or why you might want to add more than one domain. Since Windows Server 2012 Active Directory did not change in terms of design as it was in Windows Server 2008 R2, the following rules are still valid. There are a few situations where you might consider more than one domain:

- You have slow WAN links and trouble performance. This is more important if you have high number of attribute or objects.
- You have a legacy domain and it needs to persist.
- Your domain is very dynamic and the objects change frequently. In this case replication traffic could be excessive at a threshold of 100,000 objects. To separate replication traffic in general, one option is to divide the domain.

It is important to understand that the reasons for creating multiple domains are not that one domain is reaching its technical limits; the problem lies in the replication, which could lead to several problems in your infrastructure. We previously discussed that a single domain is the smallest forest you can create. Just as you can install multiple domains in one forest, you can also create multiple forests. Here are some reasons for creating multiple forests:

- You need to separate administrative autonomy. Perhaps departments in your company do not trust each other. Or perhaps there are security reasons, completely isolating your HR department's IT infrastructure. Or perhaps there is no agreement on schema changes.
- You need to install Hyper-V clusters in a separate forest (fabric) and install all managing tools, as System Center products, in another forest.

# Benefits of a Single domain
The benefits of a single domain are obvious:

Cost If you build one domain, it is recommended that you install at least two domain controllers for redundancy. Of course, if you install additional domain controllers for new domains or forests, the costs for licenses, hardware, software, and managing and maintaining additional servers always increase. Although you can virtualize any domain controller, you still have costs for storage and managing these servers.

Management Every domain you add will have additional objects you need to control and take care of. In addition, there are many challenges in setting cross-domain or even cross-forest permissions using group nesting to share resources or keep all domains and forests up and running.
