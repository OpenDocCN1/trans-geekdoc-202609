
# Creating a Security Database

To see how this template will modify a system or to apply the template setting using the MMC snap-in, you must create a security database. To do this, you have to compile it from its simple ASCII to a binary format called a database. You do that from the other snap-in, Security Configuration and Analysis.

- 1. Right-click Security Configuration and Analysis and choose Open Database to open the Open Database dialog box

Within the Open Database dialog box, you want to create a new database, but there's no option for that; instead, just type the name of the new database.

- 2. Using this example

Typing in name of new database causes the snap-in to realize that you want to create a new database, so then it asks which template to build out of. (Yup, it's nonintuitive). By default, dialog box shows you the .inf extensions in the Windows\Security\Templates folder.

- 3. If you're following this example, click simple .inf.

Before you click enter, notice the Clear This Database Before Importing box.

- 4. Select that option.

Otherwise, when you're experimenting with a template, the snap-in makes your changes cumulative (which might well be your intention, but it's not usually ours) rather than wiping the slate state and starting from scratch.

- 5. Choose the template, and click Open.

Nothing obvious has happened, but the snap-in has now "compiled" (which is our word, not Microsoft's, but it seems a good shorthand for the process of converting your ASCII into a binary database) the template named simple.sdb in My Documents\Security\Database. In the details pane, you'll see the Configure and Analyze options.

- 6. Right-click Security Configuration and Analysis, and you'll see two options: Analyze Computer Now and Configure Computer Now.

Analyze doesn't change the computer. Instead, it shows you—the computer's state to the one you want to create with the template. It then saves a log file that explains—how your system varies from what the template installs. The log file is written to\Documents\Security\Logs.

- 7. To see how your computer measures up to the settings in the database, select Analyze Computer Now, and see what the current settings are compared to what you want them to be.

- 8. If you want to jump in headfirst and apply the settings, instead of choosing Analyze Computer Now, select Configure Computer Now to modify the system's settings to fall in line with the template.

That's all very nice, you may be thinking, but how do I apply it to dozens of computers? Do I have to visit each one? Well, if you want to use this tool! If you want to use other options, one would be to use a command-line tool. A command-program called sedit.exe will both convert templates into databases and apply databases. To read a template, apply, and then create a database in the process, use the following syntax:

```
/secedit /cfg templatefilename /db filename/overwrite /log filename
```

To apply an existing database without first reading the template, leave off the /cfg switch and argument. To apply the template to your workstations, you could use the sedit command in a login script (be sure to use full paths for the template, database, and log files) that will reapply it with every login. You could also use the Task Scheduler to run a batch file at specific intervals. Or you could enable the Telnet server on your Windows servers and apply the template whenever you like.

Automation and scripting are nice, but what if you want to take advantage of the "automatic" background refreshes through Group Policy, as well as the 16-hour forced security settings update? That's right, use Group Policy! You'll learn about this in the next section.

# Using Domain-based Group Policy to Apply Templates

sedit is nice, but it has to be invoked manually from a batch file, which means a lot of messy editing of login batch files or fiddling with the scheduled tasks on all your systems. If you use a login script, the security template gets applied at login time only. How do you enforce security settings more often? With a GPO.
Domain GPOs have a few benefits:

- It's easy to control whom they apply to, which is much easier than having to figure out which batch files go where.
- They reapply not only at login time but throughout the day—the workstations seek them every 60 to 120 minutes.
- Security settings are "reapplied" every 16 hours, just in case a security setting was modified by the user, an application, and so on.

# Import Security Templates

You already have your security template, simple.inf, which you created in the previous section. Now, you want to leverage the deployment of the security settings in the template by using a GPO.

The steps to import the template are very simple. Follow these steps to import the simple.inf template into a GPMC.

- 1. Launch the GPMC.
- 2. Go to an OU that contains the computers that you want to apply the security settings to.
For example, the simple.inf template could apply to all the desktops in your organization.

- 3. Right-click the OU, and select the “Create a GPO in this domain, and Link it here” menu option.

- 4. Type in a name for your new GPO; ours is named Desktop Enforcement Policy.

- 5. Right-click Desktop Enforcement Policy, and select the Edit menu option.

- 6. From within the GPME, drill down and select the Security Settings node, which is found under Computer Configuration\Policies.
- 7. Right-click the Security Settings node, and click Import.
- 8. Browse for the .inf template (you can have it on a network share or a USB drive), and select Open.
- 9. Verify that the settings were imported by going down the Restricted Groups node.
- 10. Click OK.

The result will be that you now have imported the security settings into the GPO, and—bam!—all settings apply to the Desktops.

# NEW TEMPLATES (ADMX/ADML)

The old-style templates were OK, but they had issues. In fact, ADM templates were plagued with size complexity, and language barriers. To solve all issues, Microsoft developed a new type of file that originated with Windows 2008. The new templates are XML and based in pairs. The new file extensions are ADMX and ADML.

When you open the PolicyDefinitions folder, you will see more than 100 ADMX files, all with English, which is named en-US. The en-US folder contains all the language-specific information for displaying the settings in the GPME.

The ADMX/ADML files have a few benefits:

- The files are not stored in the GPO.
- The files can be ported to nearly any language, as long as a new ADML file and folder structure is established.
- There is a central store option that allows for centralized administration.

Creating a central store for the storage of these files is as easy as making a copy of the folder! That’s right—all that needs to be done the domain controllers. In short, follow these steps to create the central store:

- 1. Open your Windows 8 or Server 2012 computer to view the C:\Windows\PolicyDefinitions folder.
- 2. Right-click the PolicyDefinitions folder, and select Copy.
- 3. Open the C:\Sysvol\sysvol\<domainname>\Policies folder on any of the domain controllers.
- 4. Right-click the Policy folder, and select Paste.

The result will be that you now have copied the ADMX/ADML folder structure and files on the domain controller, as seen in Figure 9.25. Since the folder exists in the domain controller, it will automatically be replicated to all the other domain controllers in the domain.

To verify that you are now consuming the ADMX files from the central store, just edit a GPO and view the text under Administrative Templates folder in the GPME.

If you have a custom ADMX/ADML file after creating the central store, you will need to copy the ADMX file to the PolicyDefinitions folder and the ADML file to the en-US folder. The new settings will show up in the GPME!
