# Enforcing Blocking Inheritance

Just security filtering is used to counter the blanket application of policy application, the Block Inheritance is a special setting on an AD node (domain or OU) to prevent higher-level GPOs from trickling down. When the Block Inheritance is set, the settings of higher policies will not be applied to lower containers at all. For example, if you create a GPO for a specific OU, say Brunswick, and set up all the necessary settings for the Brunswick OU, and then you want to prevent the Bigfin domain GPOs from affecting the Brunswick OU, enable the Block Inheritance setting on the Brunswick OU. The only GPOs applied will be those linked to the Brunswick OU.

There is also a counter to the Block inheritance configuration. When Force is turned on for a GPO, the Block Inheritance is neutralized for the enforced GPO. Also, the settings in subsequent GPOs are prevented from reversing the ones in the En-enforced GPO. For example, if domain admins have a set of highly settings turned on at the domain and rogue Brunswick admins set their own OU with ours policy settings and select the Block Inheritance, the Brunswick OU effectively manages the disputed settings, but only until the domain admin manages and sets the Force setting. The domain admin lives like OU people, who have the same restrictions as everyone else: Force beats Inheritance (just like force beats covers rows).

Like all secret weapons, the Force and Block Inheritance are best used sparingly. Otherwise, in a troubleshooting situation it becomes rather complex to determine what GPOs are applied. This could be detrimental to the mental health (and potentially the job security) of a network administrator.

Wew! Here's a summary of the factors that can decide which Group Policy object wins:

+   Examine policies in this order: local GPOs, then site GPOs, then domain GPOs, then OU GPOs, then child OU GPOs, and so.

+   Within any AD node—site, domain, or OU—examine the policies as they appear in the GUL, from the bottom up

+   If policy settings, pay attention to the last GPO that you have examined, unless you saw a policy that said Force. This means no matter what conflicting policy setting comes afterwards, you should ignore these because of the Force-enforced GPO.

+   Before you apply any GPO, check its ACL. If the target user or computer does not have the Read and Apply Group Policy permissions (usually through group membership), then the GPO doesn't apply.
