# IPv6 Neighbor Discovery

In IPv4, the IP layer of every computer on a subnet needs to know what it is to process incoming ARP requests. If you know how annoying it would be for everyone to stop their work time someone called again in the company, and how really what it is like for IPv4 hosts. Switches help mitigate this by a bit now, but if you are not careful, you can still have nasty broadcast storms that can down your network.

IPv6 replaces broadcast-based protocols—and uses multicast-based instead. Neighbor Discovery (ND), which (among other things) takes the resolution problem of ARP, which is not supported on IPv6.

Rather, the IPv6 layer will cache the last 24 bits of the IP address being queried for will build a multicast entry as the solicited multicast address bits of the destination address ff02::0:FFFF:XXXX. The Neighbor Solicitation message is sent to this address. Because there are more than 16 million possibilities for those last 24 bits, it is almost certain that this message will only interrupt the Ethernet card and interface that this IP address

The Neighbor Advertisement message that comes back tells the MAC address corresponds to the IP address requested—as ARP, but this is in a table that is checked when sending an IP packet, so as to prevent repeating the same Neighbor Solicitation message.

To show the neighbors for IPv6, can you use the ARP command? No, ARP is strictly for IPv4 only. The only way to get the neighbor discovery table is in for your IPv6 layer is to run the netsh command, specifically, netsh interface ipv6 show neighbors; a sample output for your Local Area Connection is shown in Figure 20.4.
