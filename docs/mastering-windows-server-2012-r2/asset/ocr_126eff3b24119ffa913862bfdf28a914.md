Kerberos works in this fashion across the domains' trust relations. A user account starts with its domain controller for a voucher (ticket). If the resource is in another domain, it has to travel across the trust relations to the resource domain. It needs to go up the parent-child trust, across and, needed, down the other tree's parent-child path. If the user is in Eacoast.Test.com, this means the user must contact the Eacoast.Test.com domain controller. If the resource is in Consolidated.com, the Eacoast.Test.com domain controller contacts one in Test.com. The Test.com domain controller needs to contact a domain controller in Consolidated.com. It takes time to get to the resource because that is the path the automatic trusts provide. Having taller trees means more traffic, more delay. If you find yourself within a large organization that houses many domains, instead of hopping from one domain to another, you could always create a shortcut trust, providing a direct link between two domains that are far away from each other within the domain hierarchy.

# You Must Build Trees and Forests Together

Multiple domains sound great, and of course have been a terrific improvement over the earlier Windows Server releases. But you cannot join domains in a tree. In nature, you can't transplant a forest next to another one. Nor can you join trees into a forest; transplanting trees is too tough. Just as the mighty oak comes from the acorn, the only way to build a forest is from scratch. You start with one domain. Then you can add a domain to an existing tree (a child domain) or add a tree to an existing forest (a root tree). Other domains will remain outside your forest.
