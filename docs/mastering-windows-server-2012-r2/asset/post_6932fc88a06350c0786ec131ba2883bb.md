# KEEPING YOUR INTEGRATION SERVICES UPDATED

It is recommended that you keep your Guest OS Integration Services up to date in the same way you keep your host OS updated with the latest patches and fixes from Microsoft. The Integration Services don't automatically update themselves with a newer version when you update the host, so you'll need to manually update them or automate the process using System Center 2012 - Orchestrator. To determine if your Integration Services need to be updated, you can check their version using this excellent script from Hyper-V MVP Didier Van Hoy: http://workinghardt.wordpress.com/2012/12/07/checking-host-integration-services-version-on-all-nodes-of-a-windows-server-2012-hyper-v-cluster-with-powershell/

A final word on the state of a VM: you can boot, shut down, hibernate, suspend, and reset a physical machine. A VM has an additional power state: to be in a saved state. This feature is very nice in a test environment. It is similar to a hibernate state initiated from the host. But it always works, no matter what OS is installed in the VM. The Save action can be found in the usual place in the Hyper-V management console or the VM virtual console, and when you click it, you'll see a state of Saving with a percentage counter showing its progress. Start the VM and the saved state will be reloaded to restore your exactly where you left off.

For some tests, it's useful to freeze the VM in place. This is different from a saved state because no data is saved to disk. A freeze (pause, as Hyper-V calls it) just stops the VM in its tracks, instantaneously. This is another feature that is hard to find on a physical machine. Figure 27:8 shows the power button on the Hyper-V console.

From left to right, you can do the following with these buttons:

- Send a Ctrl+Alt+Del sequence to the VM.

- Start the VM after a shutdown or saved state.

# Working with VLANs

Earlier we discussed virtual switches and Hyper-V networking. Now that you understand how to configure and install a new virtual machine, it is a good time to go into some detail about how you can connect your VMs to different network subnets. In the physical world, if you wanted to isolate different subsets for security or scalability reasons, you would most likely use virtual LAN (VLAN) technology. A VLAN is configured on the network device (usually a switch or router), and it delivers isolation of networks through ID tagging.

VLANS operate on the OSI network layer 2. The exact protocol definition is known as 802.1Q. Each packet belonging to a VLAN has an identifier. This is a number between 0 and 4095, with 4095 for other users. Let's assume a VLAN with an identifier of 100. A NIC with the VLAN ID will only update packets with the same ID and ignore all other IDs. The point of VLANs is that switches and routers enabled for 802.1Q can connect VLANs to different switch ports. In other words, where a normal IP switch is limited to a set of ports on a physical switch, a subnet in a VLAN can be present on any port—if configured, course.

With a Hyper-V virtual switch, you can leverage VLAN connectivity and ID tagging by assigning the IDs to virtual NICs. The physical NIC in the host needs to be connected to the VLAN trunk port on the physical switch (or whatever physical switch is created and assigned to the physical NIC). Once you've configured your networking in this way, all you have to do is follow these steps:

# Time Travel with Checkpoints

As you have seen, many features can be helpful. If you look at this carefully, you can conclude some interesting things. First, Hyper-V allows a true node. Not only are the disks preserved, but the memory and the configuration are too. You can change memory and add networks and still be able to revert the original situation.

A checkpoint is a point-in-time copy of the VM. It includes the state and configuration. In a lab or test environment, there is no reason why you couldn't repeat this process. You can have a chain or multiple chains of checkpoints to a maximum of 50 (you really don't go there). A limitation of this process is that it works with virtual disks. If your VMs pass-through disks in a lot of scenarios, you can't checkpoint.

Finally, although a checkpoint is quick and very tempting in a lot of scenarios, I highly recommend you use this feature with care and diligence and preferably in the confines of your lab or test environment. Using any VM in production with large checkpoints would notice a performance hit until the checkpoints were removed.

Taking a checkpoint can be done in various ways, similar to changing power states. To do it from the Hyper-V management console, right-click the VM and select Checkpoint from the context menu. If you need to script your checkpoints, then the new Checkpoint-VM cmdlet is where you start. Type the following to create a new checkpoint of a virtual machine with a custom name:
