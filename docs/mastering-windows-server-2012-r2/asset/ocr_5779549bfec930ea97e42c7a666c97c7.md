Additionally, a consider Redundant Array of Inexpensive Disks (RAID) solution to increase the performance and/fault tolerance of the drives. For a high-end RDS server, a RAID 1+0 solution provides both performance and redundancy. If you're deploying in a virtual-environment, consider the underlying storage tier as well. Use high-performance SSD when possible and Fixed VHDX for the operating system.

Network on a busy RDS server, consider NIC-teaming for high-speed network cards, which can assign multiple NICs to the same IP address and split the load of network traffic. An alternative is a multihomed server with one NIC dedicated to RDS session traffic. As far as network speed goes, sending application output and client-side input back and forth requires bandwidth, but client print jobs to mapped printers can take quite a bit of bandwidth. Mapped drives may also increase the load by making it possible to copy files and forth across the RDS connection.

# Performance Monitor

Performance Monitor can help you get an idea of how RDS sessions are stressing the server. Server load should closely scale with the number of people using the server; therefore, as you pick a representative group of about five people, you should be extrapolate to needs for larger groups. The key objects and counters for measuring general server stress can be found in a free tool called Performance Analysis of Logs (located at http://palex.com); these will help you your RDS servers. But a couple of Performance Monitors are worth examining to give you detailed information for your RDS server.

# Performance Monitor Objects Still Called Terminal Services

Although the name of Terminal Services has been changed to Remote Desktop Services since Windows Server 2008 R2, it is still called Terminal Services in Performance Monitor. It might look like a type, the two objects are called Terminal Services and Terminal Services Session.

The Terminal Services object has counters representing the number of active sessions (sessions where the user has connected to the RD Session server and successfully logged in), inactive sessions (where the user is still logged onto the RDS server but has stopped using the session), and the total combined.

Besides simply monitoring activity, you could use this to alert when the number of active sessions reaches a threshold. Say you wanted to know when the RDS server hosts more than 100 sessions. You could do this with a data collector.

In Performance Monitor, it is possible to set up a user-defined data collector set with an alert. This is by creating the user-defined data collector manually (not with a template), selecting Performance Counter Alert, and setting the threshold for the active sessions. You can then set a task for the alert to notify you with a basic script or log the event to a file.

Although you can get session-level information from the Remote Desktop Services Manager, a performance object called Terminal Services Session provides quite bit more data. Use the Remote Desktop Services Manager to find the session you want to monitor—sessions are identified in Performance Monitor by their session numbers, not user login name—and add counters to monitor that session.
