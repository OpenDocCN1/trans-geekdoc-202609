
# DE-MINISTRATION AND TROUBLESHOOTING WITH DNS TOOLS

Of course, nsLookup gives the IP addresses for the sites we need to hit. But—“Oh, "no”—the Microsoft websites don't just use the IP address in the URL. So, trying that around doesn't work either.

We found the solution using the Microsoft Windows Malicious Software Removal Tool (MSRT). It had to be downloaded on a separate computer, and then using Sneaker, we transferred the MSRT package to the infected computer. It identified and removed the viruses. These days, thankfully, the Conficker virus is restricted to other operating systems with out-of-date or missing antivirus and Windows Update definitions. It's a good example, though, of how name-resolution modifications can be used to create havoc and then tools, such as nsLookup, can be used to troubleshoot and identify its presence.

When an application cannot access a server, after checking TCP/IP connectivity, we start to poke around with the nsLookup command. Here are some things we look for:

- The DNS server responding? The command will tell you right if it can connect to the DNS server. If there is a delay or time-out, there's no need to continue. You have a connectivity issue.
- The default server is unknown? This indicates that the reverse lookup performed by nsLookup failed. When it is in this state, we find that the rest of nsLookup tests get squirrelly.
- Can you resolve a local FQDN? This bypasses a portion of the client's processing. The client will append primary DNS suffixes to search for hostnames.
- Can you resolve a hostname without the DNS suffix? This is what the client does so you can walk through it.
- Can you resolve external FQDNs? This will validate that the default DNS server can get out to the Internet.

nsLookup has two methods: single-query and interactive mode. The interactive mode is much more powerful, so we use it at the start. This mode offers the ability to perform queries on different types of resource records and allows you to switch server. The following are examples of queries we commonly perform (with remarks added for clarity):

```
C:\Users\Administrator.BF1>nslookup
Default Server: BF1.bigfirm.com
Address: 192.168.0.10
```

```
rem a host record query
> BF1.bigfirm.com
Server BF1.bigfirm.com
Address: 192.168.0.10

Name: BF1.bigfirm.com
Address: 192.168.0.10
```

```
rem a reverse "ptr" record query
> set q-ptr
> 192.168.0.10
Server: BF1.bigfirm.com
Address: 192.168.0.10

10.168.192.in-addr.arpa    name = BF1.bigfirm.com
```

```
rem a start of authority query
> set q-soa
> bigfirm.com
Server: BF1.bigfirm.com
Address: 192.168.0.10
```

```

```

# DCDAG

DcDiag was originally part of earlier versions of administrator support tools (which needed to be installed separately) from Windows Server but is now included by default as part of the Windows Server 2012 R2 installation. It's our first-choice tool to perform a quick health check on the DNS structure. Since it runs through score of domain controller diagnostics, it validates that DNS is working as needed. After running the standard battery of tests, you may see errors in attempting to connect to domain controllers. Then you could run additional DcDiag tests specifically for DNS. The following examples test whether a domain controller can perform DNS to register its SRV records:

```
dcdiag:/test:RegisterInDNS /DnsDomain:bigfirm.com /f:documents\dcdiagRegisterInDNS.txt
```

This produced the following test output:

Starting test: RegisterInDNS

DNS configuration is sufficient to allow this domain controller to dynamically register the domain controller Locator records in DNS.

The DNS configuration is sufficient to allow this computer to dynamically register the A record corresponding to its DNS name.

BF1 passed test RegisterInDNS

DcDiag performs a domain of domain controller-related tests, including DNS tests. We mentioned one, the RegisterInDNS test. These tests primarily focus on the integration between the DNS servers within an Active Directory environment. Tests can be performed on delegation, forwards, dynamic update, and external DNS name resolution.

The following is a portion of the help information for the DcDiag utility. It lists the tests available for DNS. We normally rely on Lookup to test external name resolution, so we never use the /DnsForwarders and /DnsResolveName tests but listed them here for transparency:

DNS
This test checks the health of DNS settings for the whole enterprise. Sub tests can run individually using the switches below. By default, all tests except external name resolution are run

- /DnsBasic (basic tests, can't be skipped)
- /DnsForwarders (forwards and root hints tests)
- /DnsDelegation (delegation tests)
- /DnsUpdate (dynamic update tests)
- /DnsRegistration (registration tests)
- /DnsResolveName (external name resolution tests)
- /DnsAll (all tests)
- /DnsInternet (internet tests)

# DIG

There's a DNS troubleshooting tool that's been used in the Unix for some time called the Domain Information Groper, or DIG for short. If you ask users of DIG for your opinion on how NSLookup stacks up as a DNS tool, don't be surprised if they start laughing before telling you it doesn't stack up!

The good news, is that you can download DIG for free (http://www.isc.org/software/bind) and install it into your Windows Server 2012 R2 environment to help troubleshoot your DNS skills: DIG can be run in query command-line format but also has a batch mode that supports the reading of lookup requests from a file

If you want to learn how to install DIG onto a Windows Server, have a look at the walk-through http://tinyurl.com/DIGInstall. You can also review an online usage guide for DIG for this link http://tinyurl.com/DIGusage.

# Helpful DNS Troubleshooting Links

The tools we have discussed up to now have all based on what's available out of the box with Windows Server 2012 R2. Those tools are where you should start your troubleshooting from the inside network. In this section, we want to share some DNS-related websites that you can use to assist with external DNS problems.

www.IntoDNS.com is a simple effective website to add to your DNS troubleshooting arsenal. When you reach the page, all you need to do is enter the DNS name of the domain that you want to get information on and then click the Report button. This will then return all of the available information for the A (parent), NS, SOA, MX, and WWW records for that domain. With this information, you can quickly identify whether any of those records have been configured incorrectly, or you can just use it as a cross-check for the information you have been given.
