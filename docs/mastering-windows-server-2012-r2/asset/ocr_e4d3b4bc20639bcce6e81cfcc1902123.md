When the virtual Windows Server 2012 DC is deployed, the VM-Generation ID gets stored as an attribute in the Active Directory database under the mDS-GenerationID attribute of the newly created computer account (shown in Figure 28.1). A Windows driver inside the VM ensures that the VM-Generation ID is independently tracked at all times.

When the virtual DC is rolled back to a previous point through one checkpoint, for example, the VM-Generation ID value of the checkpoint instance is cross-referenced with the current VM-Generation ID value stored in the Active Directory database. If the two values don't match, then another unique identifier known as the InvocationID resets, which prevents the VM from being reused, avoiding US rollback. This is definitely a welcome change from earlier versions of Active Directory and something that should serve as encouragement to safer virtualization of your DCs.

Another idea behind the VM-Generation ID design was to make it hypervisor vendor independent, meaning that its benefits are limited to virtual DCs running on Hyper-V. This feature works with virtual DCs running on a VMware host!

# CLUSTER BOOTSTRAPPING MEANS NO MORE PHYSICAL DCs

If you configure a Hyper-V failover cluster in the past with Windows Server 2008 R2, you're probably aware of the requirement to have a physical DC or at least a DC located on a stand-alone virtual host that wasn't part of the cluster. The reason for this requirement was that the failover cluster needed to be authenticate with a DC before it could boot up. If the DC that you had in your environment was a virtual machine on the cluster that was trying to boot, then you were caught between a rock and a hard place, so to speak.
