Let's take a look at the ring structure. Ring -1 is not a mandatory feature of a hypervisor, but most modern hypervisors use it. This ring is the main feature of the Intel VT and AMD-V CPU virtualization. It is a relatively new level of even higher priority than ring 0. It allows kernels to really run on ring 0 without the tweaking that is required in older hybrid models that don't include a hypervisor. This makes for a cleaner architecture, implementing fewer bugs in code and ideally better performance.

The diagram illustrates that all VMs are created equal but that one is more than the others: Host or Management OS that is responsible for the management and high-level arbitration of all VMs. It's the default owner of all hardware resources and controls the startup and shutdown of the children.

The Hyper-V hypervisor is microkernel. As the term suggests, it was written to be lean and mean as possible. It contains no GUI code and enough intelligence to do its main job: manage memory and access to the hardware. Other (non-Microsoft) hypervisors may take a different approach. In the monolithic approach, the hypervisor contains drivers, and takes more responsibility for inter-VM communication. One advantage of a monolithic hypervisor is that if it delivers a higher maximum performance bonus because of its tighter integration with drivers to access the hardware. On the other hand, if this hypervisor has no drivers for your specific hardware, you are out of luck. For mature products, this shouldn't be a real problem. In the microkernel hypervisor, the drivers actually reside in the parent partition, which in the case of Hyper-V is a Windows 2012 server. The parent partition has the drivers, so if your hardware has drivers for Windows 2012, it can work with Hyper-V.

Let's step away from the generalities and take a look at the specifics of Hyper-V in Windows Server 2012. Microsoft designed it with the following goals:

- The hypervisor should be lean and mean as possible.
- It should be manageable using open APIs.
- Reliability and performance should be maximized.
- It should be a built-feature of the Windows server.

The bottom of the diagram shows the by-now familiar layers of the hardware and the hypervisor. Kernel mode is where the kernel of the Management OS is running along with different virtual machine (Guest OS) partitions. Let's start with the Management OS partition.

# The Management OS Partition

This partition has two parts. The lower block runs in ring 0, or kernel mode. It contains four blocks, three of which are new in discussion: VMBus, the Windows drivers, and the virtualization service providers (VSPs). The upper block corresponds to ring 3, or user mode. Here are only the components that are relevant to Hyper-V. The Management OS partition must run at a version of Windows Server that can run Hyper-V (which means Windows Server 2008 or higher) in order to support the hypervisor. Depending on your needs, this can be a full GUI version or the Server Core edition.

# INSTALLATION AND BOOT PROCESS OF THE HYPERVISOR

You may wonder about this chicken-and-egg problem: the hypervisor needs the Windows 2012 parent to do anything, the parent needs the hypervisor. When you enable Hyper-V, the hypervisor is installed on the hardware. The next time the system boots, the hypervisor is loaded first, and the Management OS is loaded as a special partition. The hypervisor then controls the hardware and starts the Management OS and any other guest partitions. The hypervisor is a microkernel, so it doesn't contain any drivers. Instead, the drivers are in the Management OS. This is why the Management OS must be a version of Windows Server that supports Hyper-V. The hypervisor uses the VMBus to communicate between the Management OS and the guest partitions. VMBus is a high-speed communication bus that allows for fast data transfer between partitions. This is how the guest partitions access the hardware drivers in the Management OS. Table 27.3 shows an overview of the most important hypervisor files.

## Table 27.3: Relevant Hypervisor Files

| Function | PATH TO FILE |
| :--- | :--- |
| Hypervisor boot | %systemroot%\system32\hvboot.sys |
| Hypervisor (for AMD) | %systemroot%\system32\hvax64.exe |
| Hypervisor (for Intel) | %systemroot%\system32\hvix64.exe |
| Virtual Machine service | %systemroot%\system32\vmms.exe |
| VM worker process | %systemroot%\system32\vmwp.exe |

These VSP modules are paired with VSC. For example, the storage module of the VSC will communicate with the storage module in the parent partition. This is how the virtualization works. It is possible for non-Microsoft developers to design and build their own modules since the relevant APIs are all open.

With the kernel part of the Management OS covered, now we'll progress to the user mode components. The Virtual Machine (VMM) is responsible for managing all virtual partitions. Whenever a virtual partition is started, the VMM starts a new virtual machine worker (VMW) process. This process does not do any work, except for monitoring, shutting down, and so on.

# WHAT PROCESS “RUNS” THE VM?

Contary to similar worker processes in the hybrid model, the VMW process does not really "run" the virtual machine partition. It controls it. You can't free from the CPU using the VMW process if the guest is doing anything, except with the exception of data transfer by non-enlightened devices.

In fact, all virtual machine partitions may be running up to 100 percent CPU without anything showing up in the Management OS partition directly. To find out what the guest is doing, you will need to either connect to the guest directly using normal server management tools, Performance Counters, or accessing the WMI provider in the Management OS partition.

The final component in the Management OS partition is the WMI provider. Years ago Microsoft decided that WMI would be the preferred way to manage and monitor system resources, and Hyper-V is no exception. The WMI provider is widely documented on MSDN and provides the following functionality:

* Status reporting on mouse and keyboard
* Access to the VM BIOS
* Managing and reading the configuration of networking, serial devices, storage, guest partitions, and so on
* Reading current properties
* Managing power state

From this feature set you can see that the WMI provider has all the functionality required to manage the Hyper-V environment. In fact, most management systems for Hyper-V are expected to use WMI. Unfortunately, the WMI interface is a little too involved to use directly for most daily management activities. Only people with extensive WMI programming experience will be able to work productively with this, and more and more functionality has been introduced into PowerShell to help ease management and administration, this is surely the way forward.
