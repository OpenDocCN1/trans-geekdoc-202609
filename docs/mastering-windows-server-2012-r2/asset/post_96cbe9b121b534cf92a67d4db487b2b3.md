
## Experiencing the Flexible Desktop

The ideal scenario for a user's working environment is the desktop, the laptop computer, or even the Remote Desktop server is nothing more than an appliance.

Consider the help-desk engineer who gets a call from a user having problems with one of their custom applications. For some reason, it won't work. The legacy deployment of a desktop network would require the engineer to sit at that desktop until the problem is resolved. The user has all of their data on a "data partition." Their settings, including their mail archive, contacts, and web browsers, are all local on the PC. There is no alternative to fix that application installation, no matter how long it takes.

Although there have been many improvements to the hardware in our devices to make them more reliable and less likely to fail, it still happens when the users look to IT to recover their data that was wasted? Sure, Windows 8 and Windows 7 both have a backup tool, but do you really have the time or resources to manage backups for hundreds or thousands of devices and laptops? What would happen in these scenarios if the user's device was nothing more than an appliance? You could build the device using something like Windows Deployment Services, Microsoft Deployment Toolkit, or other paid-for-cloning solution like System Configuration Manager (SCCM/ConfigMgr 2012). That allows you to deploy an image of a configured operating system in minutes. Software deployment can be automated using solutions like Group Policy, ConfigMgr 2012, or using Microsoft's application virtualization solution, App-V. That connects the device to a previously known and managed standard in a few more minutes.

Patches are quickly deployed using Windows Software Update Services (WSUS) and ConfigMgr 2012. Group Policy manages the environment. Now the device is secured. This is all great because the device is back to a healthy state and the custom application is correct for the user. This entire process probably took no more than 30 minutes. That's probably much less than the help-desk engineer would have had to resolve the issue.

But what about the data the user had on the device? Either you've formatted the disk by rebuilding the device or their data was lost during the hardware failure. Don't worry; the data was on a server all along. If they had a laptop, you made it available locally using a synchronized cache. The user will still have access to all their data when they log into their newly built device.

Using the practices we'll cover in the users' data, you will show them how to follow:

- Provide backups
- Make data more available
- Allow the user to be mobile from one device to another or to a Remote server while maintaining access to data in a consistent manner
- Reduce time for troubleshooting
- Have users
- Create secure working environments where there is a shared computing
- Preconfigure the working environment to apply security policies or to even make the environment easier to use

### WHEN TO REBUILD THE DEVICE

Here is a simple rule of thumb when you deploy this approach. If a problem is unique to the device (that is, not a network or shared services issue) and it looks like it will take more than 30 minutes to resolve, you should rebuild the machine. It ends up being a time-saver for IT and the business. It also gives you a long-term stable solution. You may even find that educated users will be able to rebuild the device for themselves in this scenario if you allow them.

Of course, this assumes you have used the techniques that are contained in this chapter to keep users off the device and on the servers. You'll also need something like System Center Manager or similar to automatically deploy applications that are not contained within your standard images.

## Configuring Home Directories

A home directory is a shared folder or a folder within a network share that is dedicated to a user. Each user has their own home directory on a file server. The concept is that you want users to store data on servers so that it is easy to back up, audit, and archive. Some organizations use company policy and Group Policy to prevent users from using the drives on their devices that they are forced to use their home directories for their personal data. Organizations use home directories in two basic ways. The most common is that the directory's permissions are set up so the home directory is private; in other words, the user is the only person with access to the contents. Local administrators and local systems on the server will probably need access for administration, backup/recovery, and archive operations. An alternative you see in some deployments is that there is no privacy on the home directory. It's treated as the user's personal space for sharing data with others on the network.

This is where some people argue that storage is expensive. But when you use DFS namespaces, it is much more economical. You can use the namespace to ensure that data is being backed up and archived. This is a requirement for many organizations. You can use the namespace to ensure that data is available in an alternate location. You can quickly adjust the namespace without having to make many changes to the client devices.

### Setting Up the Lab

In this example, you'll be working with two servers. BF1 is a Windows Server 2012 domain controller for the BigFirm organization. BF2 is a Windows Server 2012 file server. The network will also have a desktop called Win8 that is running Windows 8. We strongly recommend that you do any work in a test lab and have everything documented approaching your production system.

In this chapter you're going to see how to use DFS namespaces whenever you're using file shares. There are two reasons why you should do this:

- You can abstract the physical location of the file shares: Users and applications map to a logical name rather than to a physical server. This means you can move the file shares from one server to another without having to change user configurations, login scripts, or application configurations. This is very convenient when a server becomes obsolete or during a server failure when you need to recover data to an alternate location. You can quickly adjust the namespace without having to make many changes that you would otherwise make elsewhere.
- You can take advantage of DFS Replication (DFS-R) while maintaining the same drive mappings in user configurations, login scripts, and application settings: This means you can replicate user data to another server. If a disaster destroys your production server or even the site, then the data is available in an alternate location using the same drive mappings. You can also introduce more creative backup strategies. For example, you can use Volume Shadow Copy Service (VSS) for short-term operational backups in the production site and use the DR site for long-term backups that might otherwise interfere with performance in the production site.

You should have already learned how to set up a namespace and how to configure DFS-R. You are going to be using a namespace called \bigfirm.com\BigFirmShares. You'll see later how you will add folders to this namespace that redirect to the shares that will contain the user's personal data.
