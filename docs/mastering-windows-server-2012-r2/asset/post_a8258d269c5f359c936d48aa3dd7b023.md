# Trust Involve Administrators from Both Sides

The decision to let domain A accept authentications from domain B (to use one-way trust example) isn't one that A can make unilaterally, and it's not one that B can force onto A. Creating a trust relationship is just like creating a treaty between countries; you need signatures from both sides to make it legal. We realize that in many cases one—probably you— be the domain administrator on both sides, but you will nevertheless have to establish credentials on both domains before you'll be able to create that.

# Four Kinds of Trusts

In a Windows Server 2012 R2 world, there are four kinds of trusts that can be created manually: external, shortcut, forest, and realm. These trusts were also available in Windows Server 2008. Only external and shortcut trusts were available on server editions prior to Windows Server 2003. You will probably work only with the external and, on occasions, forest trusts, but let's take a quick look at what they are:

**External** trusts are basically the kinds of trusts we've been mostly talking about when we talk domain-to-domain trusts. Since they come directly from the NT trust technology, if you want a domain in a forest to trust a domain outside the forest or, in Microsoft terms, an external domain, you must build an external trust. You'll use these for migration. For example, if you're migrating from a domain to a new Windows Server 2012 R2-based AD domain, then you must first create an external trust between the two domains so that you can copy the users and other things to the new domain.

**Shortcut** shortcut trusts, help-speed authentication in large forests. Remember the earlier discussion concerning the Kerberos and high-school dating? It would be nice to cut out the extra jumps between you and the cute date. The shortcut trust is like the date. For our example, EastTest.com can pass around Test.com and directly contact Consolidated.com with this. This isn't a really impressive example. A forest with several trees or great/great-great-child domains would actually benefit from this feature.

**Forest** trusts are the neat-to-2003 trust that lets you build one trust relationship between two forests. Once done, every domain in the first forest trusts every domain in the second forest.

**Realm** Realm trusts allow trust relationships with Unix systems that use Kerberos for authentication. (What we call domains, Unix Kerberos users call realms.)

We'll mostly use external trusts, but we'll show you how to build a forest trust.

# Understanding Transitive Forest Trusts

Since we can't graft forests together, we can't add a forest to another one. The best we can do is create a trust. The external trust is adequate for sharing resources across one domain. The forest trust is best for multiple domains. Forest trusts can only be utilized by domains running at least the 2003 forest functional level.

Like the automatic trust relationships, the forest trust provides a gateway for all domains in forest to trust the domains in other. Thus, Test.com buys Apex.com, both of which have an existing forest. Test.com wants its forest to work with Apex.com, so it creates a single forest-to-forest root trust, and trust is universal.

This is good news, but there are a few reasons why this may not be all that Test.com and Apex.com want. Here's:

- First, this is only if Test.com and Apex.com are upgraded to at least the Windows 2003 forest functional level. Ideally you would want to upgrade all of your domains and domain controllers to Windows Server 2012 R2 so that you get to use all of the great features provided by the most up-to-date technology.
- Second, two transitive forests do not exactly equal a single forest as far as AD-aware software is concerned. (Read: Exchange Server. Although it's not the only one, it is the most important one:) That's because there is not very important bit of "glue" binding forests together in addition to their transitive trusts: the global catalog.
- Third, and this is probably a smaller issue, forest-to-forest trusts are, believe it or not, transitive _across forests_. _forests_. By that we mean if forest 1 trusts forest 2, then as as you've seen, all of forest 1's domains all of forest 2's domains, and vice versa.

Exchange serves your enterprise as a big firm no how many domains it has because Exchange Server thinks "all domains sharing a global catalog equal one another." So, here's the problem: two separate transitive forests still have two separate global catalogs.

But now let's say you set up a transitive trust between forest 2 and forest 3. Now all of forest 2's domains trust all of forest 3's domains (and vice versa). But what about forest 1 and forest 3—what relationship do they have? Now, it turns out. Forest-to-forest trusts do not "flow through." You'd have to build a separate trust between forest 1 and forest 3 in order to have every forest around every other one.
