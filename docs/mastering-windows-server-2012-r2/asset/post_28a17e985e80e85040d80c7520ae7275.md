
Note that in addition to each client session, there's also a session for the server's use. All locally runs sessions and executables run within the context of this server session.

# RDP Protocol Versions

RDP has been around since NT 4.0 (the first version was RDP 4.0) and has a lot of upgrades. The current version available with Windows Server 2012 R2 is version 8.1.
Although there have been many incremental changes to the protocol, the core focus in Windows Server 2012 and R2 is on WAN optimization, providing easier administration over all components, reduced storage and network costs using online Data Deduplication (Dedup), and full support for storage spaces and tier storage. As you see, RDP has come a long way since NT 4.0.

# THE CLIENT

The client improvements are in line with what we have discussed for the Remote Desktop Protocol. You should make sure that the client supports the latest RDP version that the RDS server supports. Otherwise, you will not get all the nice features and benefits of the later protocols.

# Server and Client Requirements

The computing model for thin-client networking means that the horsepower is concentrated on the server end, not the client end. Because the server will be supporting dozens of people—hundreds—this is not the time to skip on power.

# Server Hardware

The notion of using a bigger server so that you can skimp on client-side hardware isn't new. That's all a file server is: a computer running a big, fast hard disk so that you don't have to buy big, fast disks for everyone in the office. RDS servers are designed on a similar principle—if most of the processing takes place in a single location, you can concentrate the hardware needed to support processing in a single location and worry less about power on the client end.

# USE A POWERFUL RDS SESSION SERVER

Since RDS Session Server will be serving applications or full desktops to clients, you need to purchase or build a powerful server. (Although good practice would be to have less-powerful hosts, so you can distribute the load).

Processing power and RAM are the most important resources. Depending on the types and number of sessions you're supporting, you may also want to consider boosting disk access and network bandwidth.

On the surface, calculating the needs seems straightforward. Just follow these steps:

- 1. Calculate the resources needed for the operating system.
- 2. Calculate the resources needed for a small number of sessions (such as 5).
- 3. Multiply the resources needed for your sessions based on the total number of sessions you support.

If you plan to support 100 sessions, for example, and you measured 5 sessions, you'd multiply by 20 to get to 100 sessions (20 × 5 = 100 sessions). So if you need 4 GB of RAM to support 5 Sessions you need 4 GB × 20 which will require you to have 80 GB of RAM to support 100 sessions. By the way, the multiplier 20 is obtained by dividing the total number of sessions you want (100 in this) by the sample number of sessions (5 in this case).

- 4. Add the total resources needed for the resources needed for the operating system.

Although this seems like simple math, it never seems to work out that way. Synergy is often hard to predict. (where the whole is greater than the sum of its parts) often results in something unexpected. Additionally, if the deployment is successful and users are happy with what they can do, they may end up using more than you anticipated.

You don't need to tell this to budget, but it's best to add a buffer for the unknowns and plan for expansion. Several vendors publish "reference architectures" for their hardware platforms that you can also use if you decide on the resources for the platform.

# Core HARDWARE RESOURCES

For the purposes of running an efficient RD Session Host server, the bare minimum required to run Server 2012 R2 won't cut it. There are no hard-and-fast specifications for RDS server, some general guidelines for their sizing following:

**Processor**: Faster is better than a fast processor one with enough cache so that it doesn't have to reach out to the (slow) memory for code and data. Faced with a choice between more cache and more processors, and these processors have multiple cores. Although RDS servers today have multiple processors, only multithreaded applications will actually use more than one processor at a time, if there are multiple processors, the threads needing execution can line up at.

**Memory**: servers tend to be memory bound, not processor bound. High-speed, error-correcting memory; plenty of it; and be prepared to add as much as you add more users or applications to the RDS server. Sometimes adding another box to reduce the load is better because there is so much memory you can add before it negatively impacts the system. The amount of memory depends on applications that people use, the number of sessions, and the demands of the files opened in those sessions—computer-aided design (CAD) programs will stress the system more than may, Notepad. Frankly, the 64-bit operating system goes well beyond the 4 GB limit. Start your calculations with at least 8 GB of RAM for the server, and starting based on the number of users and memory required by the applications they'll run on the server. Windows 2012 R2 will support up to 4 TB of RAM.

**Disk**: Consider using Serial Computer Interface (SCSI) disks on an RDS server if it is all possible. SCSI disk controller can multitask among all the devices in the SCSI chain. Most people believe SCSI performs much better than both Serial Advanced Attachment (SATA) and Enhanced Integrated Drive Electronics (EIDE) devices, although some are starting to find that high-end SATA solutions perform better than low-end SCSI solutions. Disk performance is an important capability in any server but especially in an RDS server.

Additionally, consider a Redundant Array of Inexpensive Disks (RAID) solution to increase the performance and fault tolerance of the drives. For a high-end RDS server, a RAID 1+0 solution provides both performance and redundancy. If you're deploying in a virtual-environment, consider the underlying storage tier as well. Use high-performance SSD when possible and Fixed VHDX for the operating system.

**Network**: on a busy RDS server, consider NIC-teaming for high-speed network cards, which can assign multiple NICs to the same IP address and split the load of network traffic. An alternative is a multihomed server with one NIC dedicated to RDS session traffic. As far as network speed goes, sending application output and client-side input back and forth requires bandwidth, but client print jobs to mapped printers can take quite a bit of bandwidth. Mapped drives may also increase the load by making it possible to copy files and forth across the RDS connection.

# Performance Monitor

Performance Monitor can help you get an idea of how RDS sessions are stressing the server. Server load should closely scale with the number of people using the server; therefore, as you pick a representative group of about five people, you should extrapolate needs for larger groups. The key objects and counters for measuring general server stress can be found in a free tool called Performance Analysis of Logs; these will help you RDS servers. But a couple of Performance Monitors are worth examining to give you detailed information.

# Performance Monitor Objects Still Called Terminal Services

Although the name of Terminal Services has been changed to Remote Desktop Services since Windows Server 2008 R2, it is still called Terminal Services in Performance Monitor. It might look like a type, the two objects are Terminal Services and Terminal Services Session.

The Terminal Services object has counters representing the number of active sessions (sessions where the user has connected to the RDS server and successfully logged in), inactive sessions (where the user is still logged onto the RDS server but has stopped using the session), and the total combined.

Besides simply monitoring activity, you could use this to alert when the number of active sessions reaches a threshold. Say you wanted to know when the RDS server hosts more than 100 sessions. You could do this with a data collector.

In Performance Monitor, it is possible to set up a user-defined data collector set with an alert. This is by creating the user-defined data collector manually (not with a template), selecting Performance Counter Alert, and setting the threshold for the active sessions. You can then set a task for the alert to notify you with a basic script or log the event to a file.

Although you can get session-level information from the Remote Desktop Services Manager, a performance object called Terminal Services Session provides quite bit more data. Use the Remote Desktop Services Manager to find the session you want to monitor—sessions are identified in Performance Monitor by their session numbers, not user login name—and add counters to monitor that session. Each session object has processor and memory counters.
