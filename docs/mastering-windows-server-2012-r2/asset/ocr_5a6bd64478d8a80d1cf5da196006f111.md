# Trust Involve Administrators from Both Sides

The decision to let domain A accept authentications from domain B (to use one-way trust example) isn't one that A can make unilaterally, and it's not one that B can force onto A. Creating a trust relationship is just like creating a treaty between countries; you need signatures from both sides to make it legal. We realize that in many cases one—probably you— be the domain administrator on both sides, but you will nevertheless have to establish credentials on both domains before you'll be able to create that.

# Four Kinds of Trusts

In a Windows Server 2012 R2 world, there are four kinds of trusts that can be created manually: external, shortcut, forest, and realm. These trusts were also available in Windows Server 2008. Only external and shortcut trusts were available on server editions prior to Windows Server 2003. You will probably work only with the external and, on occasions, forest trusts, but let's take a quick look at what they are:

**External** trusts are basically the kinds of trusts weve been mostly talking about when we talk domain-to-domain trusts. Since they come directly from the NT trust technology, if you want a domain in a forest to trust a domain outside the forest or, in Microsoft terms, an external domain, you must build an external trust. You'll use these for migration. For example, if you're migrating from a domain to a new Windows Server 2012 R2-based AD domain, then you must first create an external trust between the two domains so that you can copy the users and other things to the new domain.

**Shortcut** shortcut trusts, help-speed authentication in large forests. Remember the earlier discussion concerning the Kerberos and high-school dating? It would be nice to cut out the extra jumps between you and the cute date. The shortcut trust is like the date. For our example, EastTest.com can pass around Test.com and directly contact Consolidated.com with this. This isn't a really impressive example. A forest with several trees or great/great-great-child domains would actually benefit from this feature.

**Forest** trusts are the neat-to-2003 trust that lets you build one trust relationship between two forests. Once done, every domain in the first forest trusts every domain in the second forest.

**Realm** Realm trusts allow trust relationships with Unix systems that use Kerberos for authentication. (What we call domains, Unix Kerberos users call realms.)
