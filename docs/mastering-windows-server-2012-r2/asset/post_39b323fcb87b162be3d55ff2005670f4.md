
# VM Maintenance

Although virtualization brings a lot of new features and flexibility to the table, you still need to consider some of the more traditional maintenance tasks for the VMs such as backing them up, malware protection, and keeping them up to date with the latest patches. This section will discuss your options for these maintenance tasks.

# Backing Up and Restoring Virtual Machines

From a systems-management point of view, you should treat VMs as if they are physical machines, with some exceptions. When it comes to backup and restore, there are some special issues to consider. If you look at a Hyper-V host machine running a number of VMs, you may wonder whether you can back up all of that in one go. In the ideal world, you could do the following:

- Back up all VMs, and do so incrementally.
- Make all VMs aware of the backup so that they can do the right thing on restore. This is particularly important for Active Directory and Exchange Server.
- Restore VMs individually.

In principle you could do this way. The reality is different, however. We'll review briefly how a modern Windows Server backup works.

Since the days of Windows Server 2003, we have had the Volume Shadow Copy Service (VSS). This component does two things for the backup:

- **Freeze a Disk**: First, it can create a disk volume, take a snapshot, and unfreeze the disk (which again along the same lines as the host-level checkpoint that we take of a VM, which we discussed in Chapter 27). The snapshot stays on the volume. It works using a differing algorithm and takes little space.
- **Interact with Applications**: Second, VSS interacts with applications during the backup to allow them to clean up and prepare, as flush buffers, stabilize data structures, and so on. You can see how this benefits applications. VSS allows them to be backed up quickly and with data intact. Such applications would be Active Directory, SQL Server, Exchange Server, and, of course, Hyper-V.

So, to use VSS in a virtual environment, you need a VSS provider for Hyper-V and a component that integrates with that provider. How would the applications in the VM be aware a backup is in progress? In other words, it's a two-stage rocket: the VSS process in the host needs to trigger the VSS process in the VM during backup, using the Hyper-V VSS provider as the communication channel. In the VM itself, Integration Services takes care of the coordination. This is an important point to note: without Integration Services, you cannot have a real backup from the host. Yes, using .vhdx files that make up the VM, but the VM will not be aware of the backup. It would be nothing better than a live image backup with all its limitations and lack of application-aware functionality.

Let's recap. You have two options to back up operating systems and applications in a VM:

- Run a backup from the host, using a backup tool that is VSS aware such as Windows Server Backup or System Center 2012 Data Protection Manager. Integration Services in the VM is required.
- Treat the VM as a physical machine, and run backup software from inside the virtualized OS.

Both options have their merits:

- **Backing Up from the Host**: If you run a host-level backup of your VMs, then you are ensuring that you have a full and complete backup of the VM you should recover it—no more bare-metal recoveries and reinstatement of applications in the event of a server failure. This option also slots nicely into an off-disaster-recovery scenario where the entire VM is replicated offline. One downside of host-level backups, however, is that depending on the size of the VM, they can take longer to back up, even with an incremental plan. You also need to ensure that you have a large-capacity disk solution to use because tape-only backup is deemed legacy now and wouldn't be practical if you had a large number of VMs to back up in their entirety. Something else is the potential for a performance hit on the host as multiple VMs get backed up, but you can easily avoid this with proper planning and design.
- **Backing Up in the Virtualized OS**: This will fit right in your existing backup system, then it won't break, and you know how to do it. You would likely need to deploy a backup agent to each VM's guest operating system and back up the system state with files, folders, and applications. This way, the host is a black box that can be replaced at will, although you lose the host with all your VMs running on it and all you have are in-machine backups, you should be prepared to spend a long time recovering them all to another host. Something else to be aware of that a backup initiated from inside a VM generates a lot of disk I/O. If you have 10 VMs on one host doing all their backup at the same time, you will generate 10 times the load on the host. It gets pretty hard to keep up with!

If you want to have the full gamut of options available for Hyper-V backups, then we recommend System Center 2012 - Data Protection Manager (DPM), but if that's not an option, then mentioned earlier, the built-in tool for backing up Hyper-V is Windows Server Backup (WSB). Chapter 32, "Windows Server 2012 and Active Directory Backup and Maintenance," discusses this topic in greater detail, but for the purpose of getting an understanding of how to back up your VMs, we will take a quick walk-through here. First, you need to install WSB, and a nice and simple way to do this is to open up a PowerShell command with an administrative account and then type the following:

```
Install-WindowsFeature WindowsServer-Backup
```

After you have WSB installed, you can then carry on with backing up your VM:

- 1. From Server Manager > Local Server > Tools, click Windows Server Backup to open the MMC snap-in.
- 2. Right-click Local Backup in the left tree; then click Backup Schedule from the context menu to open the Backup Schedule Wizard.
- 3. Click Next in the Getting Started dialog box.
- 4. Select Custom for the backup type; then click Next.
- 5. Click the Add Items button to open the Select Items dialog box.
- 6. Expand Hyper-V and choose the VM that you wish to back up, as shown in Figure 28.15.

# Malware Protection and Patching

It goes a good idea. Having some type of malware protection on your servers is what you need continuous, or can you get away with daily or weekly scans? As long as you are in a position to counter threats, you are probably OK.

A possible complication with virtualization may have occurred to you. Not only do you have the host to consider, but I/O is a resource on a virtualization platform. If you have a host with 10 VMs, all of them performing continuous scanning, the I/O system of host gets 10 times more load than a single server would have. This practice is not a limiting factor. Modern antivirus software, certainly the server-class kind, knows how to be careful with I/O. For VMs, the advice is clear: install malware scanners in all of them. Treat each VM as a physical server, and ensure that you have implemented the documented exclusions for the workload.

But what about Hyper-V? If it has no services except, what is the need for malware scanning? Especially on Server Core, there is little for malware to attack. Although that’s true, that’s not the point. Any operating system connecting to a network is vulnerable to attacks. Each flaw in the TCP/IP stack could lead to a compromise of the system. If you want full protection, you need to scan the host as well. Consider that by far the most disk activity will be performed by the VMs, and you see that the performance impact of a malware scanner on the host will be low. Clearly, you will need to exclude the virtual disks and the Hyper-V processes from scanning. To be, exclude the default VM Configuration folder, the VHD folder, the Snapshot folder, VMMS.exe, and VMWP.exe. Without excluding these from an online access scanner, you might well find that some of the VMs don’t start or even disappear from Hyper-V Manager!
