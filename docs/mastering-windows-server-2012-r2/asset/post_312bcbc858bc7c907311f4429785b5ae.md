When the Active Directory Domain Services runs, a new domain controller is configured. Depending on the options selected within the wizard, a new domain may be created. In each case, the DNS service and settings are configured automatically. The following changes are made:

## CREATING APPLICATION PARTITIONS

Application partitions are divisions within the Active Directory database that are created for sharing DNS zones between different domains when a new domain or forest is created. The DNSZones.domain.name partition is created for domain controllers within a domain. The ForestZones.domain.name partition is created for sharing between domain controllers of an Active Directory forest.

If you look at Figure 6.9 earlier, you will notice the _msdcs.bigform.com subdomain is delegated just like Eastcoast. It is delegated to the same domain controller, in this case, DC1.Bigform.com. The _msdcs.bigform.com zone is created in the ForestDNSZone.Bigform.com partition allows this portion of the namespace to be replicated to all domain controllers in the forest.

When additional domain controllers are created, they are automatically enlisted in these application partitions.

## ADDING A FORWARDER

Within the DNS server's properties, a forwarder is added and can be viewed and configured from the Forwarders tab. This will typically be the IP address of the original DNS server that the server was using.

## MODIFYING IP PROPERTIES

The new domain controller created by the Active Directory Domain Services Wizard is also a new DNS server. The primary DNS server's address in the IP properties is configured to the loopback address, ::1 (for IPv6) and 127.0.0.1 (for IPv4).

## DELEGATING THE SUBDOMAIN

A child domain has a name that is a subdomain within an existing domain namespace. For example, East.Bigform.com is a subdomain within the Bigform.com namespace. When the Active Directory Domain Services Wizard does its thing, the new domain's namespace will be supported on the new domain controller as a delegated subdomain.

On the parent domain, a subdomain like East.Bigform.com is delegated to the new domain controller. The delegation will link the parent to the child domain for name resolution. This was illustrated earlier in Figure 6.9.

## ADDITIONAL RECOMMENDED CONFIGURATIONS

After a domain controller is created, we recommend that you make the following changes to the DNS settings:

- 1. In the network adapter TCP/IPv4 properties, change the primary DNS server to the IP address of the primary network connection. For example, if the primary IP address for your server is 192.168.0.1, then this is what you need to change your primary DNS server property to. 

When troubleshooting DNS with the nslookup utility, the loopback address (127.0.0.1) causes tests to be "unauthorized". Although this may be cosmetic, we have found results to be a little fickle using the loopback address, so it's best to stick with your primary IP address instead.

- 2. Create the reverse lookup zones in the ForestDNSZones.domain.name application partition.

The reverse lookup zone for subnets may be shared between domain controllers of different domains.

- 3. Create a stub zone for new domain trees on the root DNS server.

A domain tree has a different name than the root DNS server. Since the original DNS server entry is listed as a forwarder like the other domain controller promotions, the DNS server can communicate with the rest of the Active Directory DNS structure. However, there are no automatic configurations on the rest of the Active Directory DNS structure to resolve names in your new namespace. For example, we need to set up a conditional forwarder or a stub zone to point the DNS servers to the new domain controller for Apex.com. In Figure 6.19, you can see a stub zone to assist resolving Apex.com FDNs.

## Understanding SRV Records and Clients

Looking at a brand-spanning-new domain's DNS zone, you will notice that it has a lot of folders or subdomains. Drilling through these folders, you will find service location records by the bootload, as shown earlier in Figure 6.22. As we mentioned, Microsoft served SRV records and Dynamic DNS updates to make Active Directory work. This is the result of the two technologies working together.

The netlogon service needs to create the SRV records within the Active Directory DNS namespace. The sole reason is to ensure computers can find domain controllers in the domain.

Within the Windows operating system processes, the specific services are sought out with the use of the DNS. In Figure 6.22, you will notice a few different services:

- _gc, or global catalog: The LDAP service to look up data within the global catalog
- _kerberos: The authentication process
- _ldap: The LDAP service to look up data within the domain

Each of these services is performed by domain controllers within the domain or forest. In Figure 6.22, you will see DC01.Bigform. perform all of these roles and what TCP port it is listening on.

When a Windows SRV answer needs a specific domain controller service, such as LDAP, it will request an answer for _ldap.tcp.Bigfirm.com. It will then have it to get by an IP address and port.

If a computer needs a domain controller in its own site, it can look for it within the _sites.Bigfirm.com subdomain. This subdomain will list all the sites created within the Active Directory Services and consoles.

### GLOBAL QUERY LIST

There are few common records that can be registered in DNS by other services. Web Proxy Discovery Protocol (WPAD) is a common one. This helps browsers automatically download proxy configurations from a server. Since the record doesn't belong to a specific computer, any computer—including compromised hackers—could attempt to register the name. Another common host is Intra-site Tunneling Addressing Protocol (ISATAP). As you learned from Chapter 4, the purpose of ISATAP is to perform nothing for IPv4 on IPv6 networks.

The global query block lists the names blocked from DNS registration. Thus, a hacker computer's attempt to register names, such as WPAD or ISATAP, is rejected.

The following commands illustrate how you can administer this, such as WPAD or ISATAP. You can see this with Get-DNSServerGlobalQueryBlocklist. Notice that it is populated with wpad and isatap by default:

```
C:\Administrator.BF>Get-DNSServerGlobalQueryBlocklist
```
Enable: True
List: <wpad, isatap>

If you want to add a name to the list, such as www, you can use the Set-DNSServerGlobalQueryBlocklist option. By default, the feature is enabled. You can disable or reenable it using the -Enable option with a $True or $False Boolean value.
