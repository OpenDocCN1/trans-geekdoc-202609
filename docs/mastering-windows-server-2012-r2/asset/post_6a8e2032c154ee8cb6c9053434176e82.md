
The address 192.168.143.8 is equivalent to the netmask, 1100 0000 1010 1000 1000 1111 1111 0000, and when you line this underneath the netmask, you can see bits to ignore when calculating the network address and bits to count:

1111 1111 1111 0000 0000 0000 0000 0000: Netmask
1100 0000 1010 1000 1111 1111 0000 0000: Host address
1100 0000 0010 1000 0000 0000 0000 0000: Network address

In binary mathematics, this is equivalent to defining the mask as a number that's the same width as your address, with a 1 in every bit of the network portion, and a 0 in every bit of the host portion, and using AND operation with your network address. The binary compares bits in the two inputs at one time—where the two bits are set to 1, the result will have a 1; if or both are set to 0, the result will have a 0 bit. Check our binary math, and make sure that we got it right!

As you've guessed from this section's heading, there were organizations that had a class C and then they needed to use more than 254 addresses within their organization. They could have another class C, or if they could a class C was next door to their existing one, they could “supernet” to create a network of 2^9-addresses—510 in all. The savings in number of addresses were not the main point, however—the savings that were important in supernetting were in the sizes of the routing tables on the way to this network.

You will see these network masks in the output from route -a print which are a pain to calculate and understand how many bits each represents. The key is to remember that there are only nine values that can appear in any one of a netmask: 255, 254, 252, 248, 224, 192, 128—that's 8, 7, 6, 5, 4, 2, 1, and 0 bits. Add up the number of bits in each octet to come up with the total number of bits in a network mask to see how many bits of your host address are tied to the network.

Because a network might be submitted at different places, the netmask for an address depends on where you are in the network. 10.1.2.3, for instance, might be the third host in the network 10.1.2.0, or it might be the 661st host in the network 10.0.0.0–255.255.255.

Another case of subnetting and supernetting was the directed broadcast—even if the router allowed a directed broadcast to pass, how do you know how many bits to direct the broadcast? This was yet another nail in the coffin of the directed broadcast, which now only exists as an annoying reason not to use the all 1s in your network.

## SUBNETTING BY RFC OR REALITY

Many of you have encountered a recent subnet from RFC 1918 (http://tools.ietf.org/rfc/rfc918) values. Every time you connect to a wireless device in a local coffee shop, you get an address in the 10.0.0.0 class A range that is reserved for private networking. But this mask isn’t 255.0.0.0. It’s 255.255.255.0—allowing for only a maximum of 253 devices (the router takes one address!) using wireless inside the coffee shop. Whenever you may be, it’s a little optimistic to think that limit won’t be reached!

This 10.* range is also used frequently in home networks set up by broadband installers those who follow the instructions for the default configuration of several bands of routers. If you use 10.0.0.0-10.0.0.255 with a netmask of 255.255.255.0 in your home, technically you're in violation of RFC 950, which says that you shouldn't use a subset of 0s or 1s all. But don't worry; the Internet won't be knocking on your door.

If you're trying to take an exam based on this RFC and RFC 1122, you might want to trim off two subnets from your calculations—the all 0s subnet and the all 1 subnet.

## CLASSLESS INTER-DOMAIN ROUTING: THE INTERNET

LOSS ITS CLASS
As you can see from our assertion that the use of an all 1s or all 0s subnet address is no big deal, as from the widespread use of supersnetting (which has no subnet part or perhaps a-length part), it is clear that the Internet's scheme of segregating addresses by classes was becoming completely irrelevant.

Added to this was the sheer tedious of having to calculate the networks. Network masks were always a string of some number set to 1, followed by a number of bits set to 0, with the total number of bits being 32, which is the size of an IPv4 address. To save to write network addresses using "10.0.0.0-10.0.0.255" or "10.0.0.0 with netmask of 255.255.255.0", network administrators used a shorthand notation, writing a slash after the network number and then writing just the number of bits set to 1. So "10.0.0.0-10.0.0.255" would become "10.0.0.0/16." the default allocation of the 10.0.0.0 address as a class A with netmask of 255.255.0.0 would be noted by describing it as "10.0.0.0/8".

The Internet is ruled by RFCs, which we've already mentioned, and this shorthand notation was no exception. RFC 1198 defined the original solution as Classless Inter-Domain Routing (CIDR), and the name has held up. In fact the shortcut has been carried over into IPv6; you will see that IPv6 prefixes throughout are specified in exactly this manner.

Do you have enough information to read that router table in Figure 20.6? Let's look at the table again. Reading from top to bottom and ignoring the Metric and Idx fields, you have following routes:

| Prefix | Gateway/Interface | Comments |

As you can see, the table is displayed in order from least-specific route to most-specific route. You can think of the router inside this computer comparing the destination address of an IP packet: "Hmm, I have a packet for 192.168.0.2—where do I go? Well, 0.0.0.0/0 matches if I don't find anything else, entry will win. What about the next? They start with 127, and the prefix hasn't masked out. My destination doesn't start with 127, so that won't work. 192.168.0.0/24 matches, because my address is 192.168.0.2, and if I go past the first 24 bits (as the prefix says) I get 192.168.0.0, which is the same as the network address of the prefix for this entry. That's the match I will choose instead of less-specific match. No matches, so I am left with sending my packet through the Local Area Connection."

As long the routing table is complete and correct, the computer will always follow this procedure of checking the prefix against the destination address, masking the destination address with the number of bits in the prefix first, and always discarding a less-specific match when a more-specific match is found. The metric is used only as a tiebreaker in case two entries have the same prefixes—the one with the lowest metric is.

## COMPLETING THE TABLE
How do you correct an incomplete routing table? More to the point, how do you tell if a router table is incomplete? You've already seen that the router table is complete for every IPv6 packet. So, a correct and complete router table must be able to tell you the right place to send every packet.

It must have at least one default route, with a prefix of 0.0.0.0/0 (or :: for IPv6 routes), otherwise there will be packets that have no idea what to do. Don't forget that the routing table may have more than one default route; in that case, there are several routes volunteer for the task. Remember that the one with the lowest metric will win.

Other than that, it must know exactly how to route every destination address that does not go to the default route. In most home environments, this is not a problem. The default route is usually the one that connects to the DSL or cable router, and everything can be sent there.

In an enterprise environment, there are often several routes in your immediate subnet. Each leads to a different portion of your network. If you list the routers and the networks to each leads, you should have a list that matches all the entries in your routing table.

If you need to add a route to your routing table, that can be done very easily from the command line. There are two basic commands to use—the route add and our good friend netsh. Suppose you want to add a route to the prefix 192.168.0.0/16 with a metric of 100 that leads to the route 10.0.0.1. The command to do this could be any of the following:

```
route add 192.168.0.0/16 mask 255.255.0.0 10.0.0.1 metric 100
route add 192.168.0.0/16 10.0.0.1 metric 100
```

```
netsh interface ipv4 add route 192.168.0.0/16 "Local Area Connection" 10.0.0.1
```

The netsh command requires a little more typing than the route command, if you want to delete it:

```
netsh interface ipv4 add route 192.168.0.0/16 "Local" 10.0.0.1
```

Similarly, you can delete a route—though if it is one that is automatically added because of a router advertisement, it will come back as follows:

```
route del 192.168.0.0
netsh interface ipv4 delete route 129.0.0.0/8 "Local Area Connection"
```
