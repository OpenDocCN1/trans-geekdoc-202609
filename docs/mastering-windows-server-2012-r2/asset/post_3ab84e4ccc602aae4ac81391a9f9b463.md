
# IPv6 TUNNEL COMMANDS

In the absence of native IPv6 support from your ISP, you may be testing IPv6 Internet access through the use of an IPv6 tunneling service, such as that provided by Hurricane Electric. We do this, and set up our tunnel—IPv6 tunneling through IPv4—as follows:

```
netsh interface ipv6 add v4tunnel IPv6Tunnel myIPv4Address 72.52.104.74
netsh interface ipv6 add address IPv6Tunnel 2001:db8:1234:567:2
netsh interface ipv6 add route ::/ 2001:db8:1234:567:1 publish=yes
netsh interface ipv6 set interface IPv6Tunnel forwarding=enable
netsh interface ipv6 add route 2001:db8:fed:cba9::64 "Local Area Connection"
netsh interface ipv6 set interface "Local Area Connection" forwarding=enable
```

The first command creates the tunnel itself from this server to 72.52.104.74, and the server on which you run this command is now capable of communicating in IPv6 through this tunnel. The second command creates an address and assigns it to the tunnel, while the third command creates a route that forwards to the IPv6 tunnel if it has nowhere else more defined—/0 is the IPv6 placeholder for a default gateway in a routing.

The fourth command enables forwarding on the IPv6 tunnel so that any traffic coming through the tunnel for other machines on our network will be forwarded to them. The fifth command adds a route from this machine to other machines in our local network, and the sixth command enables forwarding and advertising traffic on the local network so that we are able to forward packets received on that network and the computers on that network know that we are willing to forward their traffic.

Another use for proxyport is "IPv6-enable" an application that is able to use IPv6 traffic only. Again, picking HTTP as the protocol, if you have an IPv4-only newsreader and an IPv6-only news server, you can connect the two with a proxyport command like this:

```
netsh interface proxyport add v4tov6 119 news6server.com 119
```

Then set your newsreader to localhost:119, and it will connect through the proxy to the IPv6 news server!

# Using the Application Itself

You can use many tools to debug the state of a network. Which you use, and when, will depend on the problem you are trying to fix. The first tool, as ever, should be the one you actually plan to use. Let's say you're trying to make an FTP connection—first, read the errors that the FTP client is giving you.

If the client says "Connection refused," then the client has received a TCP RST ostensibly from the IP address you tried to reach. This could be a sign of a firewall between you and the server, or the server application itself might not be running.

If the client says "Timed out," then the client has received nothing in response to multiple requests. This means either "stealth" firewall is in between the client and server or the server computer is unreachable right now, either because there is no network route to it or the computer is not currently running.

# AVOID STEALTH FIREWALLS

Although security proponents suggest using stealth firewalls, we do not. Stealth firewalls do respond to unexpected incoming requests, preferring to remain silent. The appropriate TCP expression for "go away and don't talk to me" is a TCP RST; silence traditionally means "try again in a little." Not only is RST going to restrict accidental connections from retrying, it will also prevent someone from using IP spoofing to pretend to be the server. If an IP spoofing session is under way, the generic server will receive a SYN, and the RST in response will cause the client to abort its connection. In the absence of an RST, the client will continue to the spoofed server, which is a security risk.

# Pinging a Remote Computer with ping

ping is the classic tool that many of us have used for decades. Its design has varied little, but the basic principle is to send a packet to a remote machine that the remote machine is supposed to reply and wait for the reply and indicate whether it is successful. Windows Server 2012 R2 still uses the "classic" method of sending an ICMP echo to the remote machine (with extra data) "abcdefghijklmnopqruvabcdefgh" and waiting for the ICMP echo to come back.

Thus, it is important to remember that pings only ICMP echo connectivity; it does not test the TCP connection to a server port. Only a TCP connection to the server port will do (which is we suggested earlier that your debugging tool is you), so, as you can demonstrate by first pinging and many firewalls block the ICMP echo server, so you can demonstrate connecting with a web browser to microsoft.com, a failed ping does not necessarily mean a failed result.

A successful ping indicates that some message is responding to your query. You can also use the output from the ping command to ensure that you are resolving the name to the IP address. The nsLookup tool allows you to query the name. ping has a following array of arguments. The most useful are:

- -t: This pings until stopped.
- -4: This forces the use of IPv4.
- -6: This forces the use of IPv6.

# Pinging a Remote Computer with traceroute

traceroute acts in a similar way to ping, in that it sends ICMP echo request and waits for ICMP reply. How it differs is that traceroute sets the TTL (hop count) on outgoing requests. Routers decrease the hop count as they pass through, and traceroute reports the address of the first router. Similarly, the second packets show where the second router is, and so. Some routers are not configured to respond with this information or replies will be seen as a "time-out". When you see several time-outs in a row, it usually indicates that the last router before the start of time-outs is unable to forward packets toward your destination.

As you can see from the ping output in Figure 20.24, the host for www.microsoft.com in this part of the world is lbl.ms.akdns.net. This may be different if you reproduce this test. We know already, from trying to ping this host, that it does not answer ICMP requests, and for reason, packets with hop counts of 14 or more are not replied to, either with echoes or errors.
