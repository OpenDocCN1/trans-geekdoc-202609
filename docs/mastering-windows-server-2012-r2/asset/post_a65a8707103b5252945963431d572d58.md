
# EXPLORING THE DISTRIBUTED FILE SYSTEM

DFS Replication is an efficient, multiple-master replication engine that can keep folders synchronized between servers across limited-bandwidth network connections. DFS Replication can occur across multiple sites and servers that live within the same forest. DFS Replication uses differential compression (RDC) to locate and replicate only the changed data blocks of a file. This works hand in hand with the new Data Deduplication features provided by Windows Server 2012 R2. Integrated with the new block-level storage technology, DFS Replication supports replicating folders and files that are hosted on volumes that have Dedupe enabled. Using Dedupe to reduce storage requirements on an NTFS file system has no effect on DFS Replication.

Before you use these features, you must first add these roles to your server. The DFS Namespaces and DFS Replication roles you will need to add the Roles and Features Wizard in Server Manager to add them, as seen in Figure 14.26.

There are a few additional requirements to take note of before running DFS. Your servers will need to be configured using the following steps before you can properly deploy DFS in your environment:

- All the servers you wish to be members of the replication group must have the DFS Replication installed.
- You must make sure your antivirus software is compatible with DFS Replication.
- All member servers must reside within the same forest. DFS Replication works great between domains, but it is not currently possible to replicate between forests.
- Verify that your AD schema is up to date with all relevant server element additions. Windows Server 2012 R2 comes already to date.
- Understand that DFS Replication does not support the FAT or NTFS File System (ReFS), nor does DFS support replicated data that is stored on cluster shared volumes. The data must be present on an NTFS file system to support replication between servers.

# CHAPTER 14 CREATING AND MANAGING SHARED FOLDERS

As an alternative to using the Roles and Features Wizard, you can always add the roles and features to your server by utilizing Windows PowerShell. Following are a few examples of using PowerShell to add these roles to a server and to create a DFS namespace:

- 1. Open Windows PowerShell from the taskbar, running the program as an administrator.

- 2. Run the following commands to install the DFS role on a server:

```
PS C:\> Import-Module ServerManager
PS C:\> Add-Windows Feature FS-DFS
PS C:\> Import-Module DFS
```

- 3. Run the following command to create a standalone-DFS namespace:

```
PS C:\> New-Dfsnroot -TargetPath \Test-DFS\Software" -Type Standalone -EnablesSiteHosting -Path \Test\Software"
```

- 4. To see all the DFS cmdlets available in Windows Server 2012 R2, run the following command:

```
PS C:\> Get-Command -Module DFS
```

# Understanding DFS Terminology

Before we go much further, you need to understand the terminology of DFS. Just like learning to understand Active Directory, a new set of concepts and terms comes into play.

You start with a root. This translates into the share that will be visible to the network. In the example, AP is the root. You can have many pages on the root of your site, and save with Server 2012 one can have more than one root just like Server 2008. A root is shared to the network and operates like any other share. You can have additional files and folders within the shared folder.

Under a root, you add DFS links. The link is another somewhere on the network that it is under the root. The link is part of our never-ending terminology. In this case, it is shifting to meaning of an Internet nomenclature. Picture the DFS root as a web page with nothing on the name of the page and a bunch of links to other pages. The links within the DFS hierarchy are hyperlinks on a web page that automatically directs you to a new location. As long as you get the page you are looking for. Once you find your home page (the DFS root), you will be directed by those hyperlinks (DFS links) to any other website you will save (your shares).

A target replica refer to either a root or a link. If you have two identical shares on the network, on separate servers, you can group them within the same link, as DFS targets. You can also replicate an entire root—you know, the table of contents—as a root replica member. Once the targets are configured for replication, the File Replication Service keeps the contents of roots in sync.

# Choosing Stand-Alone vs. Domain-Based DFS

Before begin making a DFS system, you need to decide which kind of DFS you want. This decision will be primarily based on whether you have an Active Directory. The big difference is going to be on the root of the DFS. In an Active Directory-based DFS or domain-based DFS, the root itself can have replicas. In other words, that single point of failure—the root—has spread out into the Active Directory. Using root replicas, if you have 27 places where every DFS information lives. Well, it's not all DFS information; it's enough information to point clients to all the DFS replicas. With, as long as the Active Directory is alive and available, the DFS is too. Also, when integrated into the Active Directory, the File Replication Service takes over the synchronization of the contents of replicated folders to ensure that all replicas contain the same information. It might be safe to say that if you have an Active-based domain, you should choose domain-based DFS.
But here's the really cool part of an Active-based DFS. If you host your DFS in the Active Directory of the test domain, do not only your users need to know which server a particular share is on, but also which server the DFS is running on. Instead of making a drive to \server\DFSName, your users could map a drive to \test.com\DFSName. Now, using the same logic you can use to find an available controller for Active Directory, the client can search for all of DFS. If one fails, the client just calls on.
A-based DFS automatically publishes its topology in Active Directory. What this means is the actual DFS hierarchy—the roots, links, and targets—is published into Active Directory so that all controllers will know where the DFS lives, what it looks like, and how to get to it. It doesn't every controller is a DFS replica server.
