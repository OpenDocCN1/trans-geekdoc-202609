# Introduction to Windows Azure Active Directory

We previously discussed Active Directory is on-premises. This means that Active Directory within your company is protected from the outside world. Let’s recall why you use Active Directory. You need this service to centrally store and manage all your users and computers to control the behavior of your Windows infrastructure.

A few years after Active Directory was developed, IT had a big problem. Without Active Directory, every application needed to store its access credentials in a store, such as in a database or on the server itself. Windows NT had a modest way of managing users and computers, but that solution was far from meeting the needs of an enterprise. One reason why Active Directory was developed to centrally manage the infrastructure. The same problem occurred in Windows Azure. Now the application landscape has fragmented with some of usernames and passwords that the application can authenticate and authorize the user to use this application in Azure. But now Windows Azure Active Directory comes into play. In this section we refer to your on-premises Active Directory as “Active Directory" and Azure-hosted Active Directory as “Windows Azure Active Directory” (WAAD, Windows Azure AD, or Azure Directory).

Windows Azure Directory is a service that provides identity and access-control capabilities for your cloud applications. Many online applications use Windows Azure AD. The most of these is Office 365; others use Dynamics CRM Online and Windows Directory.

WAAD is a mult-tenant service that can handle millions of companies, for more than 100 million users, and thousands of tenants on the same platform. It is optimized for availability and consistent performance for scalability. That means you can no longer need your on-premises Active Directory? Yes and no. Windows Azure AD can be used on its own, but the most common scenario is that in architecture, it can be considered as Active Directory in the cloud extended from your on-premises Active Directory (See Figure 7.69).

Providing this expansion from your on-premise Active Directory into the cloud allows you to manage your users and groups locally and replicate them to WAAD using DirSync, which we will discuss shortly. Because of mechanism, you will be able to create a single sign-on (SSO) experience for your cloud-hosted application. After that if you are using only DirSync you won't get an SSO experience. For SSO you also need to deploy Active Directory Federation Services (AD FS) in your on-premises Active Directory. For more details, see the section, “Active Directory Logon Favors.”

# How to Interact with Windows Azure Active Directory

If you're already familiar with Active Directory, you've probably used Lightweight Access Protocol (LDAP) to query the directory for objects. LDAP is an application protocol for accessing and maintaining directory information. However, you can't use LDAP for accessing WAAD because LDAP was not designed for a multitenancy scenario. One problem is that the protocol must be independent of multiple platforms across many different technologies. Because of this, Microsoft built a RESTful interface for accessing WAAD. Representational State Transfer (REST) is an architecture that uses HTTP to perform create, read, update, and delete (CRUD) actions using the GET, POST, PATCH, and DELETE methods. Microsoft refers to this RESTful interface as Windows Azure Active Directory Graph.

There are several advantages of using this kind of interface:

- Platform independent—Any device is capable of using HTTP and calling HTTP methods.
- Language independent—Any programming language can use REST architectures to talk to other programming languages; for example, C# can talk to Java.
- Standards based—Because it runs on HTTP and is based on the HTTP standard, Windows AD Graph can be used on any platform.
- Easily manageable—Firewalls can be easily configured to allow HTTP traffic.

# Synchronizing Windows Azure Active Directory

At this point, you have some idea of how WAAD is, where you can manage your WAAD users, and how you can interact with your Windows Azure Active Directory. The real benefit of WAAD starts when you integrate your WAAD with your on-premises Active Directory. Figure 7.69, shown previously, provides a high-level view of the integration concept.

The main goal is to have your on-premises directory as a source of authority and the Azure directory receive all users, groups, and contact objects. "Source of authority" means that you manage your on-premises directory, and all changes you make override the settings in Windows Azure AD. The mechanism that updates the Windows Azure AD is a tool called DirSync. This tool allows you to synchronize your objects to WAAD and keep it to date with your on-premises directory. Once DirSync is installed, it runs in the background synchronizing WAAD every few hours. The latest version of DirSync is also capable of synchronizing the users' passwords to the cloud. Not exactly the plain password, which would be a security issue, but rather the tool synchronizes hash values of the password hashes. Imagine what benefits brings to your company.

Your users can access the cloud applications using the same credentials they use for the corporate on-premises network.

# The DirSync Tool

DirSync is relatively easy to set up. It is a 64-bit tool that requires SQL Server 2008 R2 Express Edition or a full version of SQL Server. Once the tool is installed, it is basically "set and forget," meaning you will not need to touch the installation again.

It's important to understand that if you are going to enable directory synchronization, your on-premises Active Directory will be the authoritative data source. There is one exception: if you are going to deploy Exchange Server in a hybrid deployment, some attributes may be written to your Directory. Please check the Knowledge Base article at http://support.microsoft.com/kb/256198/en-us for the relevant attributes.

If you need more details on configuring directory synchronization, a good starting point for DirSync is TechNet; check http://technet.microsoft.com/en-us/library/hh96729.aspx.
