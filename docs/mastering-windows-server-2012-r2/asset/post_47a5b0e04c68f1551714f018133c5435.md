### Advanced Features In the Network Adapter
Features shown in Figure 27.35, you have the option to use a dynamic or static MAC address. Hyper-V manages its own pool of MAC addresses, unless you encounter a MAC conflict, you should probably leave this setting at Dynamic:

Then there's the "Enable MAC address spoofing." That sounds like a bad thing, doesn't it? It was the only behavior available when Hyper-V was first released. In one compromised VM could flood the switch or impersonate another VM. Hyper-V is far safer. The virtual switch learns which MAC address belongs to which VM and doesn't allow it to change its MAC address. Usually this isn't a problem, except for those situations where you really need multiple MAC addresses. Can't think of one? Consider network load balancing or failover clustering.

If you have problems in your production environment with administrators deploying unauthorized DHCP servers, then you don't need to tell them it can lead to an administrative nightmare of invalid IP addresses. The "DHCP guard" option comes in. If you enable it, your VM will stop answering DHCP clients through this specific network adapter.

"Router guard," and it will prevent your VMs from sending out rogue redirection to the network from this specific network adapter.

If you're running a Hyper-V failover cluster and enable the "Protected network" option, your VMs will move to another node if they detect a network disconnection, therefore ensuring network availability for your services.

The final advanced option here is "NIC teaming." Not to be confused with the NIC teaming of the host that we speak about in Chapter 4, "Enable this network adapter to be part of a team in guest operating system" does exactly what it says out! If you want to create a NIC team that stays up if one of the physical NIC stops working, then ensure that you have this option enabled.

Continuing the discussion of the left pane, we can go to the Management section. Normally you don't need to change any settings here, since the defaults are sensible. You can change the name of the VM here, configure the Integration Services components (discussed earlier in "Virtual Machine (Guest) Partitions"), specify the checkpoint file (discussed later when we discuss checkpoints) and smart paging file locations, and decide what should happen when the host starts up or shuts down.

We haven't finished discussing the actions in pane in Figure 27.29. With a VM selected, you have these additional options:

- Connect: Used to start the virtual console.
- Settings: Used to configure the VM, as discussed in previous sections.
- Start: Used to boot the VM. Depending on the state of the VM, you will have more options here, such as Shutdown.
- Checkpoint: Used to create a point-in-time image of the VM.
- Move: Used to move a virtual machine or its storage.
- Export: Used to save the entire VM, including configuration and virtual hardware.
- Rename: Used to give the VM another name.
- Delete: Used to remove the VM configuration but not its hard disks.
- Enable Replication: Used to replicate the VM to another Hyper-V host.

Another point to note is that the exact items in the Actions pane vary with the power state of the VM. The previous options assume that the VM is still running. When a VM is running, you have additional items to turn the VM off, reset, shut down, and so on.

With the VM configured, the hard part is done. The next step is to install the operating system in the VM. You are used to dealing with physical servers, but the details of installing in a VM here are a bit different.

To do that, open Hyper-V Manager, select the VM (WS2012R2-SRV in our example) you want to connect to, and Connect in the lower-right corner.
