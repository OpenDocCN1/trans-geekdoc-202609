
## CHAPTER 25 MIGRATING, MERGING, AND MODIFYING YOUR ACTIVE DIRECTORY

The network environment of many of the smaller companies seemed to be held together with duct tape and superlative. Unexplained system downtime in an aging environment, and performance slowed down after a few days of restarts.

Often they addressed issues in an aging and piecemeal environment; part-time administrators and IT professionals needed stop-gap measures, which became the long-term solutions. Similar solutions existed in Active Directory. The number of user accounts was triple the number of actual employees. The number of computer accounts surpassed the number of actual computers. The undocumented VPN solution relied on the original domain controller could not be reconfigured. Thus, an upgrade or swing migration would potentially compromise the remote users' tunnel into the network. They decided that a full domain migration was the best approach and could provide the centralized management and support infrastructure they needed.

## Re-ACLing the Server

One approach is the obvious (and somewhat laborious) way: just walk over all those servers and add Sarah's access to the permissions lists on those servers. This is called re-ACLing. The other name for a list of permissions on a network service is the access control list. It can be real pain, but some migration tools do the re-ACLing for you automatically.

Outside of this process offers effort, especially when you may have to do this 100+ for 100+ groups or users, the potential of error is high. The possibility of unintentionally renewing access for one group, adding access to the wrong group, or forgetting to add another required group will make this a fun-filled ordeal for everyone!

## Using SID Histories

You know that every user has an SID. Since NT 3, but since Windows Server 2000 native through Windows Server 2008 R2 domain functional levels, Active Directory leaves users with more than one SID. As migration tools create the user's old SIDs onto the new user account we get new SIDs as well, exploiting a feature called SID history. Then, when a user tries to access some resource that he had under his old SID, his workstation tries to log in to that resource using his new Active Directory.

With all domain locals, AD builds a token for the user that contains both his user SID and those of all global and universal groups to which he belongs. Here's the trick to SID histories, AD says, “Matthew is a member of group with this SID” and sends along his old SID from the old domain.

Even though it's a user's account, the AD domain controller processes the SID as if it were a global SID, and this is acceptable.

The resource, reviewing the token, then says, “Hmm...do I know any of these guys? Well, there is this user SID...nope, I don't know what Matthew guy...but wait, look, Matthew's a member of the ‘Resource’ group from the old domain’. I have an ACL for that group, so I let Matthew in. Thus, even though Matthew is logged in as a person from the new group with a new SID, he gets access to his old stuff.

This method is preferred over the re-ACLing method because the resources' permissions can remain unchanged. The key is ensuring that the SID is recorded during the migration and the trusts do not filter them when the user is “crossing the trust” to access the resource.

## UPGRADE AND MIGRATION STRATEGIES

### WHAT YOU NEED TO CREATE SID HISTORIES

You need a migration tool that knows how to create SID histories. Microsoft’s free Directory Migration Tool, which we’ll cover a bit later in this chapter, can do that. Other migration tools are available, but you have to pay for them. Quest Software, for example, offers a suite of industry-approved migration tools.

Migration tools create SID histories as they copy accounts from other domains to your 2012 functional-level domain. Before a migration tool can work, you must create a trust relationship between the old and new domains. But no matter which migration tool you have, your migration cannot create SID histories unless you have created that trust with netdom or with ADDT’s New Wizard. You can create SID histories only on domains with a functional level of Windows Server 2000 or better. So, if you're planning to use ADMT, make sure you have a trust relationship between the old and new domains. This is because at the time, ADMT v3.2 is not supported on Windows Server 2012.

### ACTIVE DIRECTORY (CLEAN AND PRISTINE)

Here are some advantages:

- Migration tools allow you to avoid manual errors.
- Migration tools help you manage the transition.
- Migration tools provide a way to de-duplicate accounts and groups.
- Migration tools allow you to maintain permissions across domains.

Here are some cons:

- The process can be complex and time-consuming.
- It requires specific domain functional levels.
- There is a risk of data loss if not handled correctly.
- Some tools require expensive third-party licenses.

### Using Microsoft's Free Migration Tool: ADMT

If you're thinking about a migration or domain consolidation, you might need a migration tool, and if you've priced migration tools, you might be reconsidering a domain migration. Since Microsoft offers a migration tool originally created for ADMT, it maintains the ease of use of the original and adds some new features.

### Version Incompatibility

At the time, ADMT 3.2 is not directly supported on Windows Server 2012. If you want to use ADMT, then you will need to configure a Windows Server 2008 R2 server that can act as the host. You will need to have a Windows Server 2008 R2 domain controller in your new Windows 2012 domain. This will allow you to process the ADMT and Password Encryption Service (PES) programs properly.

Once you have migrated and completed all tasks, moving the users and other components to be fully supported in your new Active Directory domain, you can use DPromo to remove the Windows Server 2008 R2 domain and move on.

If you have already placed your Windows Server 2012 Active Directory domain in a Windows Server 2012 domain functional level, you will need to utilize the following PowerShell commands to revert:

To set your functional level back to Windows Server 2008 R2, run:

```
Set-ADForestMode -identity oldfirm.com -forestmodeWindows2008 R2Forest
```

To set your domain level back to Windows Server 2008 R2, run:

```
Set-ADDomainMode -identity oldfirm.com -domainmodeWindows2008 R2Domain
```
