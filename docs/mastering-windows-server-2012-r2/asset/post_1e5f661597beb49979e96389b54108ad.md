
# C&P Is GRADUAL

In specific cases, you need the C&P approach. For one thing, if you need to restructure your forest. With an in-place in-place upgrade, you walk your domain through a one-way door. If you find that Server 2012-based ADs just aren't the thing for you, then too bad; you're stuck. But if you have a new domain and copy some subset of users over if they start using the new domain and find after a week or two that the AD is not the tool for you, then you can just tell the users to go back to their old domain accounts.

Although the swing migration is gradual, the process still leaves the junk that may have contributed to the performance issues and issues that ignited the migration in the first place. Over time, unknown administrators can configure Active Directory in some manner that conforms the wise champs who've read this book. These changes will be to work after the domain is migrated to a later version.

The C&P approach also provides an intermediate phase that is not available with the other two. During this phase, you have the opportunity to test the process, proving users will be able to access their resources and uncovering some common issues that may arise with later production runs of the domain. This migration reduces the headaches and heart attacks that could occur upon crossing the one-way door.

# INTRA-FOREST MIGRATIONS

Keep in mind that these same processes are applicable to intra-forest migrations too. "Intra-what" you might ask. This merely means within a forest. You learned in this book that the forest is a group of domains in relation to each other.

Users, computers, and groups may need to be transferred to another domain within the forest. You migrate these objects from one domain to another domain "in the forest" using these procedures. The primary difference is that objects, users and groups, must be moved rather than copied. The source user account is deleted after the target account is created. The ADMT is used to migrate the accounts back to the source domain in a rollback. New computer accounts are created in the new domain, but the old computer accounts are disabled for rollback purposes. There are two combinations of objects that need to be migrated together. This is referred to as, closed sets.

# Users and Global Groups

Global groups allow only users and other global groups from the same domain. When the user changes domains, it can't be a member of its original group. When a group is moved, the members from the original domain are dropped as well. These need to be migrated together to maintain access within the limits of global group membership rules.

# Resource Computers and Domain Locals

Resources cannot assign permissions to domain locals from other domains. If the computer is migrated without the assigned domain local groups, the computer will not be able to "see" the group's SID on the user's security token to provide it access. As an alternative, you can opt to change the scope of the domain local group to universal, but this will impact the global catalog size.

# HANDLING PERMISSIONS WITH THE NEW DOMAIN

Suppose you decide to go the C&P route. Since there will be an intermediate phase, you can expect that the users of the organization will be members of old domains or the new one. This will require users in the new domain to be able to access files and other resources in an old one. Straddling the two domains, the organization will be heavily dependent on the trusts between the domain controllers until all servers that hold the resources are on the same side as the others.

How will the users maintain access to resources in the new domain as they did in the old domain? Business continuity is a big-ticket item for management; they need to ensure their people will be able to get to data. A seamless migration will minimize any access outages.

There are two approaches to maintain access: re-ACL and SID histories. ACL stands for access control list, a techie for the security tab of a shared folder. The SID is the security identifier, which is the unique number assigned to accounts to identify it within the permission structure. If you don't blink after opening the security tab of a file, you may see the SID listed on the ACL before the computer resolves the SID to a friendly name.

# Real World Scenario

# THE RANDOM HORDE AND THEIR JUNK

A group of venture capitalists acquired two IT firms. The management of the newly formed corporation wanted to merge the two firms' Active Directory forests into one to provide a unified message system from Exchange and reduce the administrative overhead.

The network environment of one firm seemed to be held together with duct tape and Super Glue. Unexpected downtime was common, and performance slowed down after a few days of operations between restarts.

You might think that an IT firm would be able to apply its expertise to its own environment. They had the know-how to deliver a top-of-the-line example of their services. However, they did not have the time and money to do so No.

As employee employee, the environment was the result of a random horde. To address issues in an aging and piecemeal environment, part-time administrators and IT professionals faced stop-gap measurements. These in turn became the long-term solutions. Similar solutions existed in Active Directory. The number of user accounts tripled the number of actual computers as well. The undocumented VPN solution that relied on the original domain controller could not be reconfigured. (They lost the admin password.) Thus, an upgrade or swing migration would potentially collapse the remote users' tunnel into the network. A C&P approach was must.

# Re-ACLing the Server

One approach is the obvious (somewhat laborious) way: just walk over all those old servers and add Joe's new account to the permissions lists on those servers. This is called re-ACL because the other name for a list of permissions on a network service is the access control list. It can be a real pain, but some migration tools will do that for you automatically.

# CLEAN AND PRISTINE MIGRATION: PROS AND CONS

Here are C&P's advantages:

- C&P lets you do gradual upgrades.
- C&P copies user accounts; it doesn't move them. The old accounts are still there if something goes wrong.
- C&P lets you create DCs from clean installs, avoiding the extra complexity and potential bugs of an in-place upgrade.
- C&P lets you consolidate domains, collapsing a morass of many domains into one or just a few.

Although we said that C&P has the advantage of reversibility, helping you manage your risk, it's not without costs:

- You need more machines than you were just upgrading. You'll need machines to act as domain controllers in the new domain.
- Most migration tools cannot copy passwords. ADMT provides a separate service to install on the source domain for. Otherwise, the users will have to create new passwords the first time they log into the new AD domain. This isn't a showstopper, but for a large workforce, this would cause headache.
- You have to use ADMT, but it's really intended for small-scale migrations of 1,000 users at best. These tools aren't cheap, starting somewhere in the neighborhood of $10 per user.
- You cannot create an Active Directory domain with the same NetBios name or FDN as the original domain, because that would require you to be able to create two domains with the same name (since you don't decommission the domains when you do to create a clean and pristine migration).

- It's more work. You have to worry about when moving any set of users and groups, you may have to re-ACL or translate local profiles, and so on.
