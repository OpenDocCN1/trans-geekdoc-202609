
## 14.2 Terrain generation and the evolutionary process

When you watch the video [here](https://www.youtube.com/watch?v=RE3Lz559aM0), you may think that the two images at the top – especially the one on the right side – are not changing, compared to the two at the bottom. This is an optical illusion, caused by the fact that transitions are very smooth when morphing alone takes place. The evolutionary transitions at the bottom seem to happen much faster, because they are chaotic and involve both backward and forward steps. But in the end, the transformation between the first and last frame in the video, is just as dramatic for the slow-moving scene.

Now I discuss the three main components of my method.

### 14.2.1 Morphing and nonlinear palette operations

Morphing is straightforward. But there is something interesting in the way I do it. It is accomplished using numpy arrays in Python, both for the palette `M` and the terrain `W`. Both `M` and `W` are matrices. The elements of `M` are between 0 and 1. The morphing involves element-wise operations [[Wiki](https://en.wikipedia.org/wiki/Hadamard_product_(matrices))]. For instance, the terrain at time `t` is computed with one line of code: `W[t] = (1 - r[t]) * W[0] + r[t] * W[T]`![Image](images/B9780443218576000187/si5.png), where `r[t] = t / T`![Image](images/B9780443218576000187/si6.png), `W[0]`![Image](images/B9780443218576000187/si7.png) is the initial terrain configuration corresponding to `t = 0`![Image](images/B9780443218576000187/si8.png), and `W[T]`![Image](images/B9780443218576000187/si9.png) is the final, target configuration corresponding to `t = T`![Image](images/B9780443218576000187/si10.png).

To obtain better results, I use a nonlinear morphing for the palette, `M[t] = M[0]^(1 - r[t]) * M[T]^(r[t])`![Image](images/B9780443218576000187/si11.png). Again, this element-wise operation is accomplished with just one line of code, thanks to the way numpy arrays work. The resulting intermediary palette `M[t]`![Image](images/B9780443218576000187/si12.png) is a valid one, with all elements between 0 and 1.

### 14.2.2 The diamond-square algorithm

I use the **diamond-square** algorithm [[Wiki](https://en.wikipedia.org/wiki/Diamond-square_algorithm)] for terrain generation. My implementation is adapted from a recent version published in 2022 by Philipp Janert, [here](https://janert.me/blog/2022/the-diamond-square-algorithm-for-terrain-generation/). The main difference is that I use Gaussian rather than uniform deviates whenever I need random numbers in the blending method. The reason is that the blending method in the evolutionary process preserves Gaussian distributions and thus results in a **stable distribution** [[Wiki](https://en.wikipedia.org/wiki/Stable_distribution)] over time, while uniform distributions (and all non-Gaussian distributions with finite variance) do not have this property.

The diamond-square algorithm successively populates an array (the terrain), at increasing levels of detail. Initially, only the corners need to be initialized; the remaining cells in the array are then populated by averaging over the four nearest populated neighbors, and adding a small random amount. At each step, the amplitude of the random noise initially set to `s`, is reduced by some factor `ds`. This factor controls the roughness of the terrain. The number of points being updated (and thus number of calls to the random number generator) exponentially increases with each subsequent step, by a factor close to 4. So very few steps are needed. Here `s` and `ds` are the names of the variables in the Python code.

There are two ways to improve the algorithm. First, instead of averaging values across nearest neighbors, use a median value. Then, in the evolutionary process, do not update the random deviates in the early steps corresponding to small `s`, but only in the final steps. This may eliminate rare but abrupt transitions over time, especially when using the mixture method. Unless you really want these rare, unpredictable “cataclysms” of various amplitudes (the larger the rarer): after all, they are present in real-life situations such as the evolution of life on Earth. The parameter `jump` in the code also controls how frequently they occur.

### 14.2.3 The evolutionary process

The terrain at time `t` is an image represented by an `n × n`![Image](images/B9780443218576000187/si13.png) matrix of pixels `W[t]`![Image](images/B9780443218576000187/si14.png), each pixel representing a level or elevation on a map. Here `n = 1 + 2^9`![Image](images/B9780443218576000187/si15.png). The diamond-square algorithm requires `n` to be a power of two, plus one. The time is represented by the integer variable `frame` in the code. The total number of (video) frames is denoted as `Nframes`. The terrain is stored as a numpy array named `d`.

Initially, at time `t = 0`![Image](images/B9780443218576000187/si8.png), the terrain is built incrementally using a few number of steps, with each subsequent step being more granular and updating about 4 times more pixels than the previous step, with exponentially decreasing noise amplitudes from one step to the next. This is performed by the function `make_terrain` in the code. At step `s`, let `W[0](s)`![Image](images/B9780443218576000187/si16.png) be the partially built terrain. It is a function of some random numbers `u[0](s, 1)`, `u[0](s, 2)`![Image](images/B9780443218576000187/si17.png), and so on, generated either with the function `random.gauss(0, s)` or `random.uniform(-s, s)` depending on whether the global parameter `distribution` is set to `'Gaussian'` or `'Uniform'`. The step `s` is represented by the variable `s` in the code.

A time `t + 1`![Image](images/B9780443218576000187/si18.png), the new terrain `W[t + 1]`![Image](images/B9780443218576000187/si19.png) is a function of `W[t]`![Image](images/B9780443218576000187/si14.png). The only quantities that are updated are the numbers `u[t](s, 1)`, `u[t](s, 2)`![Image](images/B9780443218576000187/si20.png), and so on, at each step `s` during the construction of `W[t + 1]`![Image](images/B9780443218576000187/si19.png). Two options are offered to update these numbers, via the global parameter `mode`. This parameter can be set either to `'Blending'` or `'Mixture'`. I now describe these two options:

*   **The mixture option.** We either have `u[t+1](k, s) = u[t](k, s)`![Image](images/B9780443218576000187/si21.png) with probability `p`, or `u[t+1](k, s)`![Image](images/B9780443218576000187/si22.png) is a new deviate with probability `1 - p`![Image](images/B9780443218576000187/si23.png), generated from a `Uniform[-s, s]`![Image](images/B9780443218576000187/si24.png) or `Normal(0, s)`![Image](images/B9780443218576000187/si25.png) distribution depending on the parameter `distribution`, for `k = 1, 2`![Image](images/B9780443218576000187/si26.png), and so on. Typically, `p` is small and represented by the global parameter `jump` in the code.

*   **The blending option.** It is allowed only when `distribution` is set to `'Gaussian'` in the code. Again, either `u[t+1](k, s) = u[t](k, s)`![Image](images/B9780443218576000187/si21.png) is unchanged with probability `p`, or `u[t+1](k, s)`![Image](images/B9780443218576000187/si22.png) is updated with probability `1 - p`![Image](images/B9780443218576000187/si23.png). When an update takes place, it is performed as follows: `u[t+1](k, s) = u[t](k, s) + ω * z`![Image](images/B9780443218576000187/si27.png), where `ω` is a weight, and `z` is a `Normal(0, s)`![Image](images/B9780443218576000187/si25.png) deviate. Either way, by construction, `u[t+1](k, s)`![Image](images/B9780443218576000187/si22.png) is a Gaussian deviate with zero mean. The weight `ω` is represented by the global parameter `weight` in the code.
