

## 33.3 属性：上下文与方法之间的抽象

回顾第 33.1.2 节中的术语和框架，上下文和终端任务决定了解释所需的属性。例如，在高风险场景中——例如为不稳定患者提供干预建议——解释完整且准确地反映模型（保真度）可能很重要。相比之下，在以发现为导向的场景中，解释允许高效的迭代优化，并依次揭示模型的不同方面（交互性）可能更重要。并非所有上下文和终端任务都需要所有属性，关键属性的缺失可能导致下游性能不佳。

尽管研究仍在发展中，但关于属性如何作为方法与上下文之间的抽象，已逐渐形成一种非正式的共识。第 33.2 节中的许多可解释性方法共享相同的属性，且具有相同属性的方法在特定的终端任务和上下文中可能具有相似的下游性能。如果两个上下文和终端任务需要相同的属性，那么对一个有效的方法可能对另一个也有效。一个在某个上下文中属性匹配良好的方法，在另一个上下文中可能惨败。

**如何找到所需的属性？** 当然，确定特定上下文和终端任务中哪些属性很重要并非易事。事实上，确定哪些属性对哪些上下文、终端任务和下游性能指标很重要，是可解释机器学习的重大挑战之一。目前，识别正确属性的过程可能需要通过用户研究进行迭代。然而，对属性进行迭代的空间仍远小于对方法进行迭代。例如，如果有人想测试解释的稀疏性是否是良好下游性能的关键，可以故意创建不同稀疏性水平的解释来测试该假设。这比穷举地尝试不同超参数的不同解释方法要精确得多。

接下来，我们首先描述可解释机器学习文献中讨论过的属性示例。其中许多属性是纯计算性的——也就是说，它们可以仅根据模型和解释来确定。少数属性包含一些以用户为中心的元素。接着，我们列出认知科学（关于人与人之间的解释）和人机交互（关于机器与人之间的解释）中的属性示例。这些属性中的一些在机器学习列表中有对应项，而另一些则可能作为正式化领域的灵感来源。

### 33.3.1 可解释机器学习中的解释属性

已编制了许多关于可解释机器学习模型潜在重要属性的列表，有时针对相似概念使用不同术语，有时针对不同概念使用相似术语。下面我们列出一些常见的解释属性，并意识到随着该领域的发展，此列表会随时间演变。

**忠实性，保真度**（例如，如[JG20; JG21]中所述）。当解释只是模型的部分视图时，它与模型匹配得如何？有很多方法可以使这一概念精确化。例如，假设使用模仿（简单模型）来对更复杂的模型提供全局解释。忠实性的一个可能衡量标准是模仿给出与原始模型相同输出的频率。另一个可能是模仿与原始模型具有相同一阶导数（局部斜率）的频率。在包含预测“关键”特征的局部解释的背景下，可以通过翻转被认为重要的特征来查看预测是否改变，从而衡量忠实性。另一个衡量标准可以检查，确保如果翻转被认为不重要的特征，预测不会改变。适当的形式化将取决于上下文。

**紧凑性，稀疏性**（例如，如[Lip18; Mur+19]中所述）。一般来说，解释必须足够小，以便用户可以在任务约束内处理它（例如，做出决定需要多快）。稀疏性通常对应于某种小性概念（少量特征、少量参数、L1 范数等）。紧凑性通常还包含不包含任何无关内容的额外概念（也就是说，即使解释足够小，也可以进一步缩小）。每个都必须针对上下文进行形式化。

**完整性**（例如，如[Yeh+19b]中所述）。如果解释不是模型本身，是否仍包含所有相关元素？例如，如果解释由预测的重要特征组成，是否包含所有这些特征，还是遗漏了一些？此外，如果解释使用的不是原始输入特征的派生量——例如，某种高级概念——它们是否足够表达，以解释可能改变预测的所有可能变化方向？请注意，一个人可以在某种方面拥有忠实的解释，但在其他方面不完整：例如，解释可能在翻转被认为重要的特征会翻转预测，而翻转被认为不重要的特征不会翻转预测这一意义上是忠实的。但是，解释可能未能包含翻转一组不重要的特征确实会改变预测这一事实。

**稳定性**（例如，如[AMJ18a]中所述）。对于相似的输入，解释在多大程度上相似？请注意，底层模型自然会影响解释是否可以稳定。例如，如果底层模型具有高曲率，而解释的表达能力有限，那么可能无法获得稳定的解释。

**可操作性**（例如，如[Kar+20b; Poy+20]中所述）。可操作性意味着过滤解释的内容，只关注用户可能能够干预的模型方面。例如，如果患者被预测为心脏病高风险，可操作的含义可能只包括可变特征（如运动），而不包括年龄或遗传等不可变因素。补救概念在司法环境中对应于可操作性。

**模块化**（例如，如[Lip18; Mur+19]中所述）。模块化意味着解释可以分解为可理解的部分。虽然模块化不能保证用户能够解释整个系统，但对于更复杂的模型，模块化解释——用户可以检查每个部分——可以提供对模型工作原理合理洞察的有效方式。

**交互性**（例如，[Ten+20]）。解释是否允许用户提出问题，例如解释如何随相关输入变化，或者输出如何随输入变化而变化？在某些情况下，一开始就提供用户可能想要或需要知道的一切可能会让人感到不知所措，但可能可以提供一种方式，让用户以自己的方式浏览关于模型的信息。

**半透明性**（例如，如[SF20; Lia+19]中所述）。解释是否清楚地说明了其局限性？例如，如果线性模型在特定输入处局部拟合深度模型，是否存在一种机制来报告，如果该输入周围存在强特征交互，则此解释可能受到限制？我们强调，半透明性是关于暴露解释中的局限性，而不是模型。与所有问责方法一样，解释的目的是暴露模型的局限性。

**可模拟性**（例如，如[Lip18; Mur+19]中所述）。如果用户可以获取模型和输入并计算输出（在任何时间和认知约束内），则该模型是可模拟的。可模拟解释是可模拟模型的解释。例如，特征列表是不可模拟的，因为仅特征列表本身并不告诉我们如何计算输出。相比之下，决策树形式的解释确实包含一个计算过程：用户可以遵循树的逻辑，只要它不太深。这个例子还指出了紧凑性和可模拟性之间的一个重要区别：如果解释太大，可能不可模拟。但是，仅仅因为解释是紧凑的——例如，简短的特征列表——并不意味着人可以使用它来计算模型的输出。

可模拟性可能看起来与其他属性不同，因为其定义涉及人类输入。然而，在实践中，我们通常知道哪些类型的解释对人们来说易于模拟（例如，路径长度短的决策树、公式小的规则列表等）。这种知识可以转化为纯计算训练约束，其中我们寻求可模拟的解释。

**与用户词汇和心智模型对齐。**（例如，如[Kim+18a]中所述）。解释的内容是否为用户的词汇而设计？例如，解释可以以用户了解的语义给出，例如医疗状况与原始传感器读数。这样做可以帮助用户更轻松地将解释与其知识和现有决策准则联系起来 [Clo+19]。当然，合适的词汇将取决于用户：以参数方差和有影响点的术语给出的解释可能对调试贷款模型的工程师来说可以理解，但对贷款申请人来说可能不可以理解。

与可模拟性一样，心智模型对齐更加以人为中心。然而，与之前一样，我们可以想象从用户那里提取词汇和心智模型（即确定他们如何定义术语以及如何思考）与确保解释与所提取的用户词汇和心智模型保持一致之间存在一种抽象。

一旦确定了所需属性，我们需要将其操作化。例如，如果稀疏性是所需属性，使用 L1 范数是否足够？或者需要设计一个更复杂的损失项？这个决定必然是以人为中心的：解释需要多小，或者以何种方式变小，是一个需要考虑人们将如何使用解释的决定。一旦操作化，大多数属性都可以在计算上优化。也就是说，属性应与上下文、终端任务、模型和所选解释方法一起评估。评估后，可以重新考虑解释和模型的选择。

最后，我们强调，实现特定属性的能力将取决于模型的**固有**特征。例如，具有输入之间交互的高度非线性模型的行为，通常比线性模型更难理解。无论我们如何尝试解释，如果我们试图解释某个复杂的东西，用户就会更难理解它。
