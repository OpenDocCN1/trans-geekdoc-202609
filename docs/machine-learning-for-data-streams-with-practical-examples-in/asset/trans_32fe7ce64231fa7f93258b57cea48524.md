
[图 4.6](#chapter_4.xhtml#fig4-6) 展示了 `SPACESAVING` 的伪代码。它在内存中维护一组至多 *k* 个（项目，计数）对，用前 *k* 个不同元素及其计数进行初始化。当新的流项目到达时，如果该项目在集合中已有条目，则其计数加 1。如果没有，则该项目替换计数最低的项目，后者的计数随后加 1。非直观的部分在于，该项目继承了它所驱逐元素的计数，即使这是它的首次出现。然而，正如以下断言所示，误差永远不会太大，既不会让稀有元素看起来过于频繁，也不会让真正的重击者看起来过于不频繁。

[**图 4.6**](#chapter_4.xhtml#rfig4-6)

SPACESAVING 概略图。

令 *f*[*t,x*] 为前 *t* 个流元素中项目 *x* 的绝对频率，若 *x* 在时刻 *t* 位于概略图中，令 *count*[*t*](*x*) 为其关联的计数；当从上下文中清楚时，我们省略下标 *t*。以下对于每个项目 *x* 且在所有时间 *t* 均成立：

1.  最小计数器 *min* 的值至多为 *t/k*。
2.  若 *x* ∉ *S*，则 *f*[*x*] ≤ *min*。
3.  若 *x* ∈ *S*，则 *f*[*x*] ≤ *count*(*x*) ≤ *f*[*x*] + *min*。

（1）和（2）蕴含了每个频率高于 *t/k* 的 *x* 都在 *S* 中，即概略图包含所有（1*/k*）重击者。（3）表明 *S* 中元素的计数既不低估真实频率，也不高估超过 *t/k*。*t/k* 的值可视为最小分辨率：计数仅对远大于 *t/k* 的频率是良好的近似，而频率为 1 的项目可能刚进入概略图，其关联计数高达 *t/k*。

文献 [175] 中提出的 `Stream-Summary` 数据结构实现了该概略图，确保了每次更新的摊还常数时间。对于概略图中存在的每个计数值 *c*，都会创建一个包含 *c* 以及指向所有具有计数 *c* 的项目的双向链表指针的桶。桶保存在一个按其值 *c* 排序的双向链表中。项目链表中的节点都包含指向其父桶的指针，还有一个哈希表，给定一个项目，可提供指向包含它的节点的指针。细节留作练习。

总而言之，取 *k* = ⌈1*/*𝜖⌉ 时，`SPACESAVING` 可找到所有 𝜖–重击者，其频率近似正确至 𝜖，使用 *O*(1*/*𝜖) 个内存字和常数摊还时间。

`SPACESAVING`、`FREQUENT`、`Lossy Counting` 和 `Sticky Sampling` 均为确定性算法；除哈希表内部可能用于搜索集合的哈希函数或随机化外，它们不使用哈希函数或随机化。很容易将 `SPACESAVING` 适配为形式为 (*x,c*) 的更新，其中 *x* 为项目，*c* 为任意*正*权重，该对代表赋值 *f*[*x*] ← *f*[*x*] + *c*，对内存或更新时间无显著影响。但它无法模拟项目删除，或等价地，无法处理带*负*权重的更新。

## 4.6.2 CM-Sketch 算法

*Count-Min sketch*（计数-最小概略图）或 *CM-sketch* 由 Cormode 和 Muthukrishnan [81] 提出，可用于解决与项目频率相关的多个问题，其中包括重击者问题。与 `FREQUENT` 和 `SPACESAVING` 不同，它是概率性的，并大量使用随机哈希函数。对某些应用更重要的是，它能处理具有正负权重的更新，特别是项目的添加和减去。

我们首先描述概略图能实现什么，然后是其实现。我们考虑形式为 (*x,c*) 的元素流，其中 *x* 为项目，*c* 为对 *f*[*x*] 的任意正或负权重更新。我们用 *F* 表示给定时刻的总权重 ![](images/pg51-in-1.png)。

可见 `Update` 和 `Query` 操作均执行 *O*(*d*) 次操作。我们不正式证明不等式（[4.1](#chapter_4.xhtml#eq4-1)）中的近似界，但提供一些关于其为何成立的直观解释。首先观察到，对于第 *i* 行第 *j* 列，*A*\[*i,j*\] 包含该行中所有满足 *h*[*i*](*x*) = *j* 的项目 *x* 在流中的权重之和。仅此一点就保证了 *f*[*x*] ≤ *A*\[*i,h*[*i*](*x*)\]，因此 *f*[*x*] ≤ `Query`(*x*)。但如果有其他项目 *y* 恰好被映射到该行的同一单元格，即 *h*[*i*](*x*) = *h*[*i*](*y*)，则 *A*\[*i,h*[*i*](*x*)\] 可能会高估 *f*[*x*]。需分配给该行 *w* 个单元格的总权重为 *F*，因此落在任意特定单元格上的期望权重为 *F/w*。可以证明，任何单元格接收远超该期望值的权重的可能性不大。直观上，这可能发生在特别重的项目被映射到该单元格时，但重项目数量有限，所以这种情况很少发生；或者太多轻项目被映射到该单元格，但这也不太可能，因为哈希函数将项目或多或少均匀地分布在该行的所有 *w* 个单元格中。马尔可夫不等式在证明中起核心作用。

回到重击者问题，CM-sketch 为重击者元素的频率提供了合理的近似，但没有明显的方法从数据结构中定位它们。对所有可能的 *x* 调用 `Query`(*x*) 的暴力搜索对于大型项目全集是不可行的。解决方案使用了所谓的*区间求和查询* 的高效实现，这在许多情况下具有独立的研究价值。

区间求和查询定义在可与 {1, . . . , |*I*|} 中的整数对应的项目集合上。参数为 \[*x,y*\] 的区间求和查询返回 *f*[*x*] + *f*[*x*+1] + ⋯ + *f*[*y*−1] + *f*[*y*]。例如，考虑一个处理发往 IP 地址数据包的路由器。路由器的一个区间求和查询可能是：“你见过多少发往 IPv4 地址范围 172.16.aaa.bbb 的数据包？”我们期望比遍历该范围内的 2^(16) 个地址更快地解决此查询。
