

两种分析系统的类型是 `data warehouses` 和 `online analytical processing (OLAP)` 系统。`Data warehouses` 作为企业内不同功能领域的单一真实数据源。优秀的 `data warehouses` 整合多个异构数据源，并针对数据读取进行了优化，使其成为报告应用程序的理想数据源。`Data warehouses` 通常是关系型数据存储，例如 `Azure Synapse Analytics dedicated SQL pool` 或 `Azure SQL Database`。`OLAP` 模型通常是商业智能 (`BI`) 模型，它们将业务逻辑和预聚合应用于数据仓库数据，以在数据仓库和报告平台之间创建一个抽象层。`Azure Analysis Services` 和 `Power BI` 表格模型是可以创建此类数据模型的 `OLAP` 技术示例。

典型的数据仓库和 `OLAP` 表格模型将使用星型架构存储数据。由于数据的非规范化方式，星型架构使数据易于报告。度量和指标汇总在事实表中。它们连接到包含每个度量描述性属性的表，也称为维度表。例如，互联网销售事实表可以关联到多个维度表，其中包括提供购买日期详细信息的日期维度、包含购买客户特定信息的客户维度，以及描述所售产品不同属性的产品维度。星型架构设计的固有简单性使分析人员能够轻松地在事实表上创建聚合，同时连接必要的维度表来回答关于数据的不同业务问题。

## 非关系型数据存储

有大量数据不适合关系型模型。非关系型数据，也称为 `NoSQL` (`Not Only SQL`)，是指不适合关系型模型的数据。某些解决方案需要比关系型数据库更灵活的数据模型，并可以牺牲 ACID 合规性来换取速度和水平扩展。`NoSQL` 数据库比关系型数据库更能处理快速写入和读取的易失性数据，因为它们不强制数据符合特定结构。

二进制对象，如图像、视频和 PDF，也被视为非关系型数据。虽然像 `SQL Server` 这样的关系型数据库可以使用 `FILESTREAM` 等功能存储本书的 PDF 副本等文件，但这并不是文件存储的最优解决方案。对象存储针对二进制文件存储进行了优化，可以轻松访问以将这些文件提供给应用程序。它们还可用于为大数据处理解决方案创建高度可扩展的数据湖生态系统。

### NoSQL 数据库

`NoSQL databases` 不会对其存储的数据强加架构，允许数据在摄入过程中保持其自然格式。事实上，主要优势之一是设计 `NoSQL` 数据库解决方案的用户不需要提前定义架构。这种灵活性使 `NoSQL` 数据库成为需要毫秒级响应时间并需要能够快速扩展的解决方案的理想选择。`NoSQL` 数据库可能比关系型数据库更好的场景包括摄入和分析来自 IoT 传感器的突发数据、为电子商务网站的 Web 搜索功能存储产品目录数据，以及为 Web、移动和社交媒体应用程序存储用户生成的内容。

与关系型数据库中将数据存储为表格行不同，数据作为实体存储在集合或容器中。与表格中的行不同，同一集合中的实体可以具有不同的字段集。这种灵活性允许根据解决方案要求实现多种不同的 `NoSQL` 数据库实现。通常，这些实现分为以下四类：

* `Key-value stores` 是插入和查询数据的最简单类型的 `NoSQL` 数据库（参见 [图 1.1](#c01.xhtml#c01-fig-0001））。每个数据片段包含一个键和一个值。键作为数据片段的唯一标识符，值包含数据。值可以是标量值或复杂结构，例如 JSON 数组。当应用程序从键值存储中查询数据时，它们会发出指定键以检索值的查询。[图 1.1](#c01.xhtml#c01-fig-0001) 是一个电话目录示例，在键值存储中为每个人存储一个或多个电话号码。键值存储的示例包括 Python 字典对象、`Azure Table storage` 和 `Azure Cosmos DB Table API`。

    ![FIGURE 1.1 Key-value store](images/c01f001.png)

    [图 1.1](#c01.xhtml#R_c01-fig-0001) 键值存储

* `Document databases` 是最常见的 `NoSQL` 数据库类型（参见 [图 1.2](#c01.xhtml#c01-fig-0002））。数据片段定义为文档，通常以 JSON、XML、YAML 或 BSON 格式存储。每个文档包含一个文档键，用作管理和查询查找的唯一标识符。与只能通过键搜索来检索数据的键值存储不同，查询文档数据库的应用程序可以对文档的键和/或一个或多个字段进行查找，以检索特定的数据集。此功能使文档数据库成为需要更具选择性的应用程序的更好选择。[图 1.2](#c01.xhtml#c01-fig-0002) 说明了文档数据库中存储为文档的客户订单示例。文档数据库的示例包括 `MongoDB` 和 `Azure Cosmos DB Core (SQL)` API。

    ![FIGURE 1.2 Document database](images/c01f002.png)

    [图 1.2](#c01.xhtml#R_c01-fig-0002) 文档数据库

* `Columnar databases` 在概念上类似于关系型数据库（参见 [图 1.3](#c01.xhtml#c01-fig-0003)）。它们将数据组织为行和列，但对数据进行非规范化，使其分为多个列族。每个列族包含一组逻辑相关的列。[图 1.3](#c01.xhtml#c01-fig-0003) 是自行车公司产品信息以列式格式存储的示例。列式数据库的示例是 `Azure Cosmos DB Cassandra API`。

    ![FIGURE 1.3 Columnar database](images/c01f003.png)

    [图 1.3](#c01.xhtml#R_c01-fig-0003) 列式数据库

* `Graph databases` 将数据存储为实体，并关注这些实体之间的关系（参见 [图 1.4](#c01.xhtml#c01-fig-0004)）。实体定义为节点，而它们之间的关系定义为边。查询图数据库的应用程序通过遍历节点和边的网络来实现，分析实体之间的关系。虽然关系型数据库可以实现类似目标，但大型图数据库可以非常快速地遍历关系，无需对许多表执行多个联接操作。[图 1.4](#c01.xhtml#c01-fig-0004) 说明了存储组织人员图表的图数据库示例。实体代表不同的职位和部门，而边代表每个实体之间的关系。图数据库的示例包括 `Neo4j` 和 `Azure Cosmos DB Gremlin API`。

 ![FIGURE 1.4 Graph database](images/c01f004.png)

[图 1.4](#c01.xhtml#R_c01-fig-0004) 图数据库
