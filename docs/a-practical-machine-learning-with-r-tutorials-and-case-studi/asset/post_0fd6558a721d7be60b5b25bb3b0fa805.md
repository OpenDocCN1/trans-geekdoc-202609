You might have noticed that the select() and the mutate() commands were used right after the data was loaded with import() — before the recipeWine was defined. This raises the question:

# When should we use select() and mutate(), and when should we use recipe to pre-process data?

Here are some suggestions:

- 1. Generally, using a recipe is advisable because we can reuse a recipe of other data frames.
- 2. It is good practice to use select() before to reduce the columns of an original frame to only those columns (variables) for the analysis. This allows us to use the notation in the formula argument of the recipe() command.
- 3. When transforming outcome variables, it is advised to do this outside of a recipe. For example, in the R code above, we used mutate() to convert the outcome variable WineColor from a char to a factor data type outside the recipe. If a recipe is later used on another dataset for prediction, this dataset might contain a column for the outcome variable. More about why recipes should not be used on outcome variables in Kuhn and Silge (2022), Section 8.4.

## 4.7.4 Creating a Model-Design

A model design determines which machine learning model from which R package be used for the analysis.

To define a model design within the tidymodels environment, only three commands (connected with |>) are required. The following code shows how to generate a learning design for a k-Nearest Neighbors model:

```
ModelDesignKNN=nearest_neighbor(neighbors=4,
  set_engine("knn") |>
  set_mode("classification")
```

As you see, the k-Nearest Neighbors model is designed with only three commands:

> If the dataset contains the outcome variable, such as the testing data, some step, including step_normalize(), ignore the outcome variable to avoid data leakage. Data Leakage occurs when information from the training process is used (often inadvertently) in the testing phase of the model. This can lead to poor prediction quality when the model is used in the production phase.

## 4.7 Using Tidymodels for k-Nearest Neighbors

- 1. A command determining the name of the machine learning algorithm (in this case nearest_neighbor()) and optionally hyperparameter for the model. Here we used neighbors=4 to determine the value for k (number of neighbors), and weight_function=rectangular to ensure that the original k-Nearest Neighbors algorithm is used.
- 2. A set_engine() command to provide the name of the package that performs the machine learning algorithm (in this case, set_engine("knn")). Note there is no need to load the package by library() because this is done internally by set_engine(), but the package must be installed before you use it.
- 3. A set_model() command that indicates if we perform a classification or a regression.

The model design is stored in an R object (ModelDesign). As the name suggests, ModelDesignKNN is only a design for a model, like a blueprint. A model design like ModelDesignKNN only contains a model description, and no data are fitted to the model at this point of the development. Consequently, ModelDesignKNN in its current state cannot be used for predictions.

When we print the model design, we get some basic information about the model design.

```
print(ModelDesignKNN)

## K-Nearest Neighbor Model Specification (classification)
##
## Main Arguments:
## neighbors = 4
## weight_func = rectangular
##
## Computational engine: knn
```

To detailed information about how k-Nearest Neighbors is implemented through the knn package, we refer to Hochnlicher and Schlieper (2004). To find more details about model design in tidymodels by Kuhn and Silge (2022), Chapter 6.

## 4.7.5 Creating and Training a Workflow

In the two previous sections, we defined a recipe and a model design. In this section, we will put it together in a workflow. A workflow combines a recipe for data pre-processing with a model design into a workflow. Afterward, the workflow needs to be fitted (calibrated) to the training data before it can be used to predict (more about fitted vs. unfitted machine learning models will be covered in Section 5.4.2).

In the code block below, we start with the workflow() command, and we add the recipe add_recipe(RecipeWine) and the model design add_model(ModelDesignKNN) to the workflow. Then we fit the workflow to the training data with fit(DataTrain) and save the fitted workflow model into the R object WFModelWine. We decided to build the object name with WFModelWine to indicate that this R object is a workflow model ready to be used for predictions.

```
WFModelWine<-workflow()
add_recipe(RecipeWine)
add_model(ModelDesignKNN)
fit(DataTrain)
```

## 4.7.6 Predicting with a Fitted Workflow Model

In this section, we will use the fitted workflow model from the previous section to predict the WineColor for the observations of the testing dataset DataTest.

We use testing rather than training dataset because we want to assess the model's prediction quality rather than how well the model can approximate the training data.

To predict the wine color of different wines based on their acidity and sulfur dioxide content, we can use the predict() command. As you can see in the code block below, the predict() command only requires two arguments: the name of the trained workflow WFModelWine and the name of the testing dataset DataTest.

```
predict(WFModelWine, DataTest)
```

The predict() command pre-processes the data and uses the fitted workflow to predict the WineColor. You can see the predictions for the first six in the printout:

```
head(predict(WFModelWine, DataTest))
```

The output of the predict() command is a tibble like this:

| WineColor | Acidity | Sulfur | .pred_class | .pred_red |
| :--- | :--- | :--- | :--- | :--- |
| 1 | white | 90 | white | 0.82 |
| 2 | red | 190 | red | 0.25 |
| 3 | white | 220 | white | 0.67 |
| 4 | red | 131 | white | 0.78 |
| 5 | white | 161 | white | 0.7 |
| 6 | red | 41 | red | 0.99 |

The augment() command also calculates the probabilities for each observation to be a red or a white and stores them in the variables _pred_red and _pred_white, respectively. These probabilities result from the voting process of the k-Neighbors. Remember, we considered the four neighbors. Therefore, the vote for the red could be either 25%, 50%, 75%, or 100%, which is reflected in the variable _pred_red. The probabilities for white wine follow _pred_white = 1 - _pred_red.

## 4.7.7 Assessing the Predictive Quality with Metrics

The tidymodel package provides several commands to calculate metrics. Most of these compare the estimate with the truth and calculate the related metrics.

For example, we can use the conf_mat() command from tidymodel to create a confusion matrix. The command requires two arguments:

- 1. the name of the data frame that contains the estimate and the truth (e.g., DataTestWithPred).
- 2. The variable that contains the truth (e.g., Wine)
- 3. The variable that contains the estimate (e.g., pred_class)

The code below uses conf_mat() in combination with the data frame DataTestWithPred to generate a confusion matrix:

```
ConfMatrixWine=conf_mat(DataTestWithPred, truth=WhiteColor, estimate=.pred_class)

print(ConfMatrixWine)

## Truth
## Prediction red white
## red 436 46
## white 44 434
```

The sum of the counts of the main-diagonal elements of the confusion matrix (the counts of correctly predicted wines) is very high, compared to the sum of the counts of the off-diagonal elements (the counts of the falsely predicted wines). This is the first indicator for a good prediction quality. However, as the following section will show, we have to analyze the matrix in more depth to gain an accurate, objective assessment about the prediction quality.
