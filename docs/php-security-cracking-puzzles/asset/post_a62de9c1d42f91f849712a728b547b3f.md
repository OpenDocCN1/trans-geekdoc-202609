Now, to sweep away the tracks you left during the break-in, all you must do is upload and run the upload.php file again: neither the upload.php file nor the 1.php file will be left on the server.

Besides structured query language (SQL) injection, this is the most common break-in technique, typical for forums, chats, photo galleries, or any other Web application allowing users to upload files to the server.

The best method for protecting against this type of break-in is to impose a blanket prohibition on loading files, and then allow only certain types of files to be uploaded. This defense can be implemented by analyzing file extensions using a script like the one shown in Listing II.3.3.

```php
<?php
// The HTML form handler
if(!empty($_FILES['filename']['tmp_name']))
{
    // Extracting the file's extension
    $ext = strtolower(strrchr($_FILES['filename']['name'], "."));
    // Allowing only files of certain
    // formats to be uploaded
    $extensions = array(".jpg", ".gif");
    // Checking the file's extension against
    // the list of the allowed extensions
    if(in_array($ext, $extensions)) {
        // Saving the file in the current directory
        if(copy($_FILES['filename']['tmp_name'],
            $_FILES['filename']['name'])) {
            echo "File upload successful: <a href=" .
                $_FILES['filename']['name'] . ">" .
                $_FILES['filename']['name'] . "</a>";
        }
    } else {
        // The file's extension is not in the allowed list.
        echo "Only images can be uploaded!";
    }
}
?>
```

Right after the $file is uploaded to the server, the script extracts its extension and places it in the $ext variable. The file extensions permitted for uploading are stored in the $extensions array. If the extension of the uploaded file matches one of those stored in the $extensions array, the file is copied from the temporary directory to the destination directory. Otherwise, the file is ignored.

Although it is possible to upload a malicious script by changing its extension to, for example, .gif, once uploaded it cannot be executed. To execute a file with such an extension, this extension must be associated with an interpreter, which cannot be done.

## II.3.4. Download Counter

All download counters are based on the principle that users are given a link not to the file itself but only a link to the script that registers the download and sends the file to the user.

The script for solving the posed problem, counting the number of times a file is downloaded, constructed so that the link to the file to download is implemented as a link to the current page with the file name passed as a parameter: for example, index.php?down=archive.zip. The script checks whether the down parameter was passed and, if it was, registers the download in the filecount.txt file. Every time the page is loaded, the counter value for each archive is extracted from this file and displayed in the browser window. The requested file is made available for downloading by sending the user an HTTP header named that contains a link to the archive to download. The actual file download script may look like the one shown in Listing II.3.6.

> NOTE It is more convenient to store statistical information for industrial and large systems in a file.

### II.3.6. A file download counter

```php
<?php
// Registering the file names in an array
$file_name = array('archive1.zip', 'archive2.zip', 'archive3.zip');

// The name of the file that stores statistics
$countname = "filecount.txt";
// If the file exists, reading the
// current statistics into the array.
if (file_exists($countname)) {
    $fd = fopen($countname, "r");
    $content = fread($fd, filesize($countname));
    fclose($fd);
    // Unpacking the array
    $count = unserialize($content);
}
```

The names of the downloaded files are stored in the $file_name array; when a new archive for downloading is added, it is automatically registered in the system. The advance registration is necessary for several reasons. First, when a file name is passed in the down parameter, it must be checked against allowed for downloading. Second, processing files in an array is much easier than processing them individually. Thus, the $count array, which stores the number of the file downloaded, is automatically created on the $file name array. For convenience, the $count array is converted into a byte-stream representation string using the serialize() function and back into the value using the unserialize() function.

> to remember that all headers can only be sent before the main content is sent. Sending them in a different order is impossible; the PHP interpreter will issue the following warning message: "Warning: Cannot modify header information— already sent by." This is because HTTP sends headers first and sends the contents of the document. Thus, any initial output into the browser window is interpreted as headers with the document body expected to. If it is impossible to avoid sending the contents before the buffers, output control functions should be used to place the output into a buffer and then send it to the browser window at the end of the script's execution.

When the script is run for the first time, the filecount.txt file does not exist. It is created when the page is loaded for the first time. The creation process is initiated by the 0 value for each file from the $file name array.

## II.5. Saving Text and Graphics Files

A browser can only interpret a file if it knows its contents. The browser learns about the file’s contents from the server, because each file is accompanied with HTTP headers telling the client about the file’s contents, its size, and other service information, such as having to set a cookie. If the type of the file is unknown, it is sent as a binary stream.
