# 6.6.3.1 Rejoin and Replacement

Because processes fail over time, it is important to repair or replace replicas that have become faulty to ensure the long running of a fault tolerance system. As we have argued before, when a replica rejoins the system, it must first obtain the latest state of the system before it can participate in the Paxos algorithm again. This mechanism negates the need for logging Paxos-related information (promises and votes, etc.) on persistent storage. As reported in Chubby [5], local hard drives cannot be used as true persistent storage and hence, a rejoining replica is not allowed to immediately take part in the Paxos algorithm. A replacement replica would assume the replica id of the replaced one, and it joins the system by first requesting a state transfer, exactly the same as a rejoining replica.

# 6.6.3.2 Membership Expansion

When expanding the membership, two replicas should be added at a time. Assuming the current membership consists of 2f + 1 replicas, after adding the two replicas, the new membership would be able to tolerate f + 1 faulty replicas, thereby, increasing the failure resiliency of the system. To join the system, a replica multicasts a join request to all existing members of the system. The join request is totally ordered with respect to all other application requests. The execution of the join request is a membership change.
