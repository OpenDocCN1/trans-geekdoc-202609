
# Storage System Fault Tolerance and Data Replication

## Physical Disks and Fault Tolerance

An underlying number of physical disks in a virtual volume also determines fault tolerance level. For example, if a single RAID 5 volume is configured on 10 physical disks, the probability of volume failure is higher due to any two disks failing together, compared to having two RAID 5 volumes each having 5 physical disks. Of course, in scenario 2, there would be total two disks' space lost due to parity, whereas in scenario 1 only one disk's space is lost.

## Spare Disk Configuration

Spare disk configuration within a storage system adds greater value in fault tolerance and data protection. It prevents the system from going into a degraded state. Upon failure of a disk, the rebuild process uses the spare disk to generate data that was on the failed disk and make the virtual volume return to a healthy state.

A storage system without a spare disk configured goes into a degraded state upon failure of a disk. Depending on the RAID level, subsequent failure of another disk can result in data loss. Therefore, it is recommended to have multiple spare disks configured to avoid any data loss due to disk failures. Whenever a spare disk gets consumed by the rebuilding process, it is also important to have the failed disk replaced with a working one and have it configured as a spare disk.

## Recovery Point Objective and Recovery Time Objective

In any data protection solution, recovery point objective (RPO) and recovery time objective (RTO) are two important parameters that drive how to deploy the solutions.

- **RPO**: The maximum allowable threshold time of the data that is needed to restore in the event of a disaster. For example, if your RPO is 6 hours, you want to be able to restore systems back to the state they were in as of no longer than 6 hours ago.
- **RTO**: The time needed to recover from a disaster—usually determined by how long you can afford to be without your systems.

## Data Replication

There are multiple terminologies for data replication. Replication of data is nothing but making a copy of data. The primary purpose of replication is to recover data in the event of data corruption or data loss. Replication features enhance fault tolerance and data protection aspects of a storage system. Primarily, there are two types of replications implemented.

### Local Replication

Technologies that copy data locally to the same storage system are called local replication. Snapshot and clone are examples of such technologies.

Data on a production virtual volume keeps changing; an application constantly accesses it for read or write operations. Therefore, there is a need to have a point-in-time copy of data on a virtual volume that can be used for taking an offline backup, accessing data to generate reports, and so on.

#### Snapshot Technology

A snapshot is a point-in-time (PIT) copy of data on a virtual volume. For example, if a host accesses a snapshot that was created at 9:00 AM, it reflects the data of the primary production volume at that point in time. Some storage systems allow restoring snapshot data back to the primary volume. In case of accidental deletion of data on the primary volume, data corruption, or virus infection, data on the latest snapshot can be restored back onto the primary volume to recover the data. Data of the snapshot can also be used for other purposes like generating an offline report, analytics, test, or development.

The primary volume is also referred to as the parent volume of a snapshot volume. Immediately after the creation of a snapshot, all blocks of the snapshot point to its parent volume, but as and when data on the parent volume changes, old data gets copied to the snapshot and the occupancy of the snapshot increases. Blocks that are not changed since the creation of the snapshot will continue to have the reference to the parent volume.

#### Example: Snapshot Creation and Updates

At the time of snapshot creation, the volume had data A, B, and C. The snapshot would also have the same data, but all data is just a reference to the actual location of data on the volume.

![Figure 7.7: Snapshot: After creation](images/Fig_7.7.png)

Figure 7.7: Snapshot: After creation

When a block of data is changed, let us say from C to D, data C is first copied to the snapshot and then updated in the parent volume from C to D. The reference from the snapshot to the parent volume for this data is also removed. The allocated size of the snapshot grows by the size of data C. More writes in the parent volume cause more updates and increase the allocated size of the snapshot. In this process, the snapshot continues to have the data at the time of creation of the snapshot. Updated ones are physically located, and unchanged ones still maintain references to corresponding blocks in the parent volume.

![Figure 7.8: Snapshot: After writing or updating data on primary volume](images/Fig_7.8.jpg)

Figure 7.8: Snapshot: After writing or updating data on primary volume

In the above method, before every write operation, the data block in the parent volume is copied to the snapshot. This method of data update is commonly used by most vendors and is called **copy on write (COW)**.

There is another popular method of data update implementation in snapshot technology called **redirect on write (ROW)**.

![Figure 7.10: After writing or updating data on primary volume](images/Fig_7.10.png)

In ROW, after the creation of a snapshot, all blocks referred to by the snapshot are frozen. As shown in the above figure, upon any new update for C, the new data D is simply written in a new location in the storage and the parent volume refers to it, instead of C. Whereas the snapshot continues to refer to C. Therefore, in this method, a copy operation from parent to snapshot is saved, but data in the parent volume may get fragmented.

#### Copy on Write (COW) vs Redirect on Write (ROW)

| Copy on write | Redirect on write |
| --- | --- |
| More write overhead | Less write overhead |
| Makes data contiguous | Makes data noncontiguous |
| Commonly implemented in storage systems | Few storage vendors implement it |

#### Snapshot Limitations

A snapshot does not provide protection of data against physical media failures of the parent volume. For example, if a storage volume has snapshots and due to multiple underlying disk failures, data on the parent volume is no longer accessible, in that case, snapshots associated with it would also not be accessible. However, for logical errors such as accidental data deletion or modification from the host server or virus infection, previous data can be recovered from the snapshot.

#### Read-Only and Read-Write Snapshots

There are two types of snapshots: read-only (RO) and read/write (RW). An RW snapshot allows the host to update data on it. If a copy of production data is required for test or development of an application or some other purposes, an RW snapshot can be created as a copy of the original data and then update data further on it.

#### Snapshot of Snapshot

Before making any change on an RW snapshot, another snapshot of it can be created to keep a copy of it before the application writes data onto it. A snapshot of an RO snapshot can also be created to have a second copy of the data.

If an application is continuously writing onto an RW snapshot, a snapshot of this snapshot can be scheduled if the administrator wants to protect data of the snapshot at regular intervals.
