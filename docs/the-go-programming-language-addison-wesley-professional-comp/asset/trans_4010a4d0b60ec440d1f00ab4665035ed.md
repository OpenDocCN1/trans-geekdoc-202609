

## 7.5 接口值

通常情况下，我们无法在编译时知道接口值的动态类型是什么，因此通过接口的调用必须使用*动态分发*。编译器不生成直接调用的代码，而是生成从类型描述符中获取名为 `Write` 的方法地址，然后对该地址进行间接调用的代码。调用的接收者参数是接口动态值的副本，即 `os.Stdout`。其效果等同于我们直接进行了如下调用：

[点击此处查看代码图像](#part0137_split_029.html#id183pro02_r)

```
os.Stdout.Write([]byte("hello")) // "hello"
```

第三条语句将一个 `*bytes.Buffer` 类型的值赋给接口值：

```
w = new(bytes.Buffer)
```

现在动态类型是 `*bytes.Buffer`，动态值是指向新分配缓冲区的指针（[图 7.3](#part0065.html#id-figures-iface3)）。

![包含 *bytes.Buffer 指针的接口值。](images/00027.jpeg)

**图 7.3。** 包含 `*bytes.Buffer` 指针的接口值。

对 `Write` 方法的调用使用与之前相同的机制：

[点击此处查看代码图像](#part0137_split_030.html#id183pro03_r)

```
w.Write([]byte("hello")) // 将 "hello" 写入 bytes.Buffer
```

这一次，类型描述符是 `*bytes.Buffer`，因此调用了 `(*bytes.Buffer).Write` 方法，接收者参数的值是缓冲区的地址。该调用将 `"hello"` 追加到缓冲区中。

最后，第四条语句将 `nil` 赋给接口值：

```
w = nil
```

这将其两个组成部分都重置为 `nil`，使 `w` 恢复到声明时的状态，如[图 7.1](#part0065.html#id-figures-iface1)所示。

接口值可以容纳任意大的动态值。例如，表示时间点的 `time.Time` 类型，是一个包含若干非导出字段的结构体类型。如果我们从它创建一个接口值，

```
var x interface{} = time.Now()
```

结果可能如[图 7.4](#part0065.html#id-figures-iface-time)所示。从概念上讲，动态值总是能放入接口值中，无论其类型多大。（这只是一个概念模型；实际的实现截然不同。）

![包含 time.Time 结构体的接口值。](images/00028.jpeg)

**图 7.4。** 包含 `time.Time` 结构体的接口值。

接口值可以使用 `==` 和 `!=` 进行比较。如果两个接口值都为 nil，或者它们的动态类型相同且动态值根据该类型 `==` 的常规行为相等，则这两个接口值相等。因为接口值是可比较的，所以它们可以用作 map 的键或 switch 语句的操作数。

然而，如果比较的两个接口值具有相同的动态类型，但该类型不可比较（例如切片），则比较会失败并引发 panic：

[点击此处查看代码图像](#part0137_split_031.html#id184pro01_r)

```
var x interface{} = []int{1, 2, 3}
fmt.Println(x == x) // panic: comparing uncomparable type []int
```

在这方面，接口类型比较特殊。其他类型要么是安全可比较的（如基本类型和指针），要么完全不可比较（如切片、map 和函数），但在比较接口值或包含接口值的聚合类型时，我们必须意识到可能发生 panic 的风险。将接口用作 map 键或 switch 操作数时存在类似风险。只有当你确定接口值包含可比较类型的动态值时，才比较它们。

在处理错误或调试时，报告接口值的动态类型通常很有帮助。为此，我们使用 `fmt` 包的 `%T` 动词：

[点击此处查看代码图像](#part0137_split_032.html#id184pro02_r)

```
var w io.Writer
fmt.Printf("%T\n", w) // "<nil>"

w = os.Stdout
fmt.Printf("%T\n", w) // "*os.File"

w = new(bytes.Buffer)
fmt.Printf("%T\n", w) // "*bytes.Buffer"
```

内部实现上，`fmt` 使用反射来获取接口动态类型的名称。我们将在[第 12 章](#part0111.html#id-reflection)中探讨反射。

### 7.5.1 警示：包含空指针的接口非空

空接口值（不包含任何值）不同于包含恰好为 nil 的指针的接口值。这个微妙的区别制造了一个陷阱，每个 Go 程序员都曾踩中过。

请看下面的程序。当 `debug` 设为 `true` 时，main 函数在 `bytes.Buffer` 中收集函数 `f` 的输出。

[点击此处查看代码图像](#part0137_split_033.html#id185pro01_r)

```
const debug = true

func main() {
    var buf *bytes.Buffer
    if debug {
        buf = new(bytes.Buffer) // 启用输出收集
    }
    f(buf) // 注意：微妙的错误！
    if debug {
        // ...使用 buf...
    }
}

// 如果 out 非空，将向其写入输出。
func f(out io.Writer) {
    // ...做些事情...
    if out != nil {
        out.Write([]byte("done!\n"))
    }
}
```

我们可能期望将 `debug` 改为 `false` 会禁用输出收集，但实际上这会导致程序在 `out.Write` 调用时 panic：

[点击此处查看代码图像](#part0137_split_034.html#id185pro02_r)

```
if out != nil {
    out.Write([]byte("done!\n")) // panic: nil pointer dereference
}
```

当 `main` 调用 `f` 时，它将一个 `*bytes.Buffer` 类型的空指针赋给 `out` 参数，因此 `out` 的动态值是 `nil`。然而，其动态类型是 `*bytes.Buffer`，这意味着 `out` 是一个包含空指针值的非空接口（[图 7.5](#part0065.html#id-figures-iface4)），所以防御性检查 `out != nil` 依然为真。

![包含空指针的非空接口。](images/00029.jpeg)

**图 7.5。** 包含空指针的非空接口。

和以前一样，动态分发机制确定必须调用 `(*bytes.Buffer).Write`，但这次接收者的值是 nil。对于某些类型（如 `*os.File`），`nil` 是合法的接收者（[§6.2.1](#part0055.html#id-nilrecv)），但 `*bytes.Buffer` 不在其中。方法被调用了，但当它试图访问缓冲区时发生了 panic。

问题在于，虽然空的 `*bytes.Buffer` 指针拥有满足接口所需的方法，但它不满足接口的*行为*要求。具体来说，该调用违反了 `(*bytes.Buffer).Write` 的隐式前置条件——其接收者不能为 nil，因此将空指针赋给接口是一个错误。解决方法是将 `main` 中 `buf` 的类型改为 `io.Writer`，从而避免一开始就将这个有缺陷的值赋给接口：

[点击此处查看代码图像](#part0137_split_035.html#id186pro01_r)

```
var buf io.Writer
if debug {
    buf = new(bytes.Buffer) // 启用输出收集
}
f(buf) // 正确
```
