
# 13.1 内存布局与对齐

`Sizeof` 仅报告每个数据结构固定部分的大小，如字符串的指针和长度，但不包括间接部分，如字符串的内容。下表展示了所有非聚合 Go 类型的典型大小，尽管确切大小可能因工具链而异。为保证可移植性，我们以字（word）为单位给出了引用类型（或包含引用的类型）的大小，其中在 32 位平台上一个字为 4 字节，在 64 位平台上为 8 字节。

## 类型大小

| 类型 | 大小 |
|------|------|
| `bool` | 1 字节 |
| `intN`, `uintN`, `floatN`, `complexN` | `N` / 8 字节（例如 `float64` 为 8 字节） |
| `int`, `uint`, `uintptr` | 1 字 |
| `*T` | 1 字 |
| `string` | 2 字（data, len） |
| `[]T` | 3 字（data, len, cap） |
| `map` | 1 字 |
| `func` | 1 字 |
| `chan` | 1 字 |
| `interface` | 2 字（type, value） |

## 对齐与填充

计算机在值正确**对齐**时能最高效地从内存加载和存储值。例如，两字节类型（如 `int16`）的值的地址应为偶数；四字节值（如 `rune`）的地址应为 4 的倍数；八字节值（如 `float64`、`uint64` 或 64 位指针）的地址应为 8 的倍数。即使对于 `complex128` 等较大类型，更高倍数的对齐要求也很少见。

因此，聚合类型（结构体或数组）的值的大小至少是其字段或元素大小之和，但由于存在**空洞**，实际大小可能更大。空洞是编译器添加的未使用空间，用于确保后续字段或元素相对于结构体或数组的起始位置正确对齐。

语言规范不保证字段声明顺序即内存布局顺序，因此理论上编译器可重排字段，尽管目前尚无编译器这样做。如果结构体字段类型大小不同，按紧凑顺序声明字段可能更节省空间。下面三个结构体字段相同，但第一个比后两个多占用高达 50% 的内存：

```go
// 64-bit    32-bit
struct{ bool; float64; int16 }   // 3 words   4 words
struct{ float64; int16; bool }   // 2 words   3 words
struct{ bool; int16; float64 }   // 2 words   3 words
```

对齐算法细节超出本书范围，无需为每个结构体担心，但高效打包可使频繁分配的数据结构更紧凑、更快。

## `unsafe.Alignof` 与 `unsafe.Offsetof`

`unsafe.Alignof` 函数报告其参数类型所需的对齐值。同 `Sizeof` 一样，它可应用于任意类型的表达式，并产生一个常量。通常，布尔和数值类型按其大小对齐（最大 8 字节），其他类型按字对齐。

`unsafe.Offsetof` 函数的操作数必须是字段选择器 `x.f`，它计算字段 `f` 相对于其外层结构体 `x` 起始位置的偏移量（含空洞）。

```go

    a bool
    b int16
    c []int
}
```

尽管名字中带 "unsafe"，这些函数实际上并不 unsafe，在为空间优化而理解程序原始内存布局时可能有帮助。

# 13.2 `unsafe.Pointer`

大多数指针类型写作 `*T`，意为“指向类型为 `T` 的变量的指针”。`unsafe.Pointer` 是一种特殊指针，可持有任意变量的地址。当然，我们不能通过 `*p` 间接引用 `unsafe.Pointer`，因为不知道该表达式应有何类型。同普通指针一样，`unsafe.Pointer` 可比较，并可与 `nil`（该类型的零值）比较。

普通 `*T` 指针可转换为 `unsafe.Pointer`，`unsafe.Pointer` 也可转回普通指针，不必是同类型 `*T`。例如，将 `*float64` 指针转为 `*uint64` 可检查浮点变量的位模式：

```go
package math

func Float64bits(f float64) uint64 { return *(*uint64)(unsafe.Pointer(&f)) }

fmt.Printf("%#016x\n", Float64bits(1.0)) // "0x3ff0000000000000"
```

通过结果指针也可更新位模式。这对浮点变量无害（任何位模式均合法），但总体而言，`unsafe.Pointer` 转换允许向内存写入任意值，从而颠覆类型系统。

`unsafe.Pointer` 还可转为 `uintptr`，后者持有指针的数值，允许对地址执行算术运算（回顾 [第 3 章](#part0029.html#id-integers)，`uintptr` 是足以表示地址的无符号整数）。此转换也可逆向应用，但同样，从 `uintptr` 转 `unsafe.Pointer` 可能颠覆类型系统，因为并非所有数字都是有效地址。

许多 `unsafe.Pointer` 值因此成为将普通指针转为原始数字地址再转回的中介。下例取变量 `x` 的地址，加上其 `b` 字段的偏移量，将结果地址转为 `*int16`，并通过该指针更新 `x.b`：

```go
var x struct {
    a bool
    b int16
    c []int
}

// equivalent to pb := &x.b
pb := (*int16)(unsafe.Pointer(
    uintptr(unsafe.Pointer(&x)) + unsafe.Offsetof(x.b)))
*pb = 42

fmt.Println(x.b) // "42"
```

尽管语法繁琐——或许这并非坏事，因为这些特性应谨慎使用——但不要试图引入 `uintptr` 类型的临时变量来拆分行。以下代码是错误的：

```go
// NOTE: subtly incorrect!
tmp := uintptr(unsafe.Pointer(&x)) + unsafe.Offsetof(x.b)
pb := (*int16)(unsafe.Pointer(tmp))
*pb = 42
```

原因非常微妙。某些垃圾收集器会在内存中移动变量以减少碎片或记账开销，这类收集器称为**移动 GC**。变量移动时，所有持有旧地址的指针都必须更新为指向新位置。从垃圾收集器角度看，`unsafe.Pointer` 是指针，其值必须随变量移动而改变，但 `uintptr` 只是数字，其值不应改变。上述错误代码在非指针变量 `tmp` 中向垃圾收集器**隐藏了一个指针**。等到第二条语句执行时，变量 `x` 可能已移动，`tmp` 中的数字不再是 `&x.b` 的地址。第三条语句会用值 42 破坏任意内存位置。
