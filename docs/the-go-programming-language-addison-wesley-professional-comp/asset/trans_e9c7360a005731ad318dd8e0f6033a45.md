
## 13.4 bzip2 Writer 和 cgo

### `Close` 方法

```go
// Close flushes the compressed data and closes the stream.
// It does not close the underlying io.Writer.
func (w *writer) Close() error {
    if w.stream == nil {
        panic("closed")
    }
    defer func() {
        C.BZ2_bzCompressEnd(w.stream)
        w.stream = nil
    }()
    for {
        inlen, outlen := C.uint(0), C.uint(cap(w.outbuf))
        r := C.bz2compress(w.stream, C.BZ_FINISH, nil, &inlen,
            (*C.char)(unsafe.Pointer(&w.outbuf)), &outlen)
        if _, err := w.w.Write(w.outbuf[:outlen]); err != nil {
            return err
        }
        if r == C.BZ_STREAM_END {
            return nil
        }
    }
}
```

完成后，`Close` 调用 `C.BZ2_bzCompressEnd` 以释放流缓冲区，使用 `defer` 确保这在所有返回路径上都会发生。此时 `w.stream` 指针不再安全解引用。为了防御性编程，我们将其设为 `nil`，并为每个方法添加显式的 nil 检查，以便如果用户在 `Close` 后错误地调用方法，程序会 panic。不仅 `writer` 不是并发安全的，而且对 `Close` 和 `Write` 的并发调用可能导致程序在 C 代码中崩溃。修复此问题见[练习 13.3](#part0125.html#id-bzipmutex)。

### `bzipper` 程序

下面的程序 `bzipper` 是一个使用我们新包的 bzip2 压缩命令。它的行为类似于许多 Unix 系统上存在的 `bzip2` 命令。

[点击此处查看代码图像](#part0143_split_020.html#id365pro01_r)

`gopl.io/ch13/bzipper`

```go
// Bzipper reads input, bzip2-compresses it, and writes it out.
package main

import (
    "io"
    "log"
    "os"

    "gopl.io/ch13/bzip"
)

func main() {
    w := bzip.NewWriter(os.Stdout)
    if _, err := io.Copy(w, os.Stdin); err != nil {
        log.Fatalf("bzipper: %v\n", err)
    }
    if err := w.Close(); err != nil {
        log.Fatalf("bzipper: close: %v\n", err)
    }
}
```

### cgo 讨论

我们演示了将 C 库链接到 Go 程序中。反过来，也可以将 Go 程序编译为静态归档文件以链接到 C 程序，或编译为共享库以便被 C 程序动态加载。这里我们只是浅尝辄止地介绍了 `cgo`，关于内存管理、指针、回调、信号处理、字符串、`errno`、终结器，以及 goroutine 与操作系统线程之间的关系，还有很多内容要说，其中大部分非常微妙。特别是，正确地在 Go 和 C 之间传递指针的规则很复杂，原因类似于我们在[第 13.2 节](#part0123.html#id-unsafepointer)中讨论的，且尚未有权威规范。欲了解更多，请从 `https://golang.org/cmd/cgo` 开始阅读。

## 13.5 再次警示

我们在上一章结束时警告了反射接口的缺点。这一警告对本章描述的 `unsafe` 包适用得更为强烈。

高级语言不仅将程序和程序员与各个计算机指令集的晦涩细节隔离开来，还将它们与那些无关紧要的细节隔离开来，比如变量在内存中的位置、数据类型的大小、结构体布局的细节，以及其他大量实现细节。由于这层隔离，可以编写出安全、健壮且无需修改即可在任何操作系统上运行的程序。

`unsafe` 包让程序员穿透隔离层，以使用某些关键但原本无法访问的特性，或者为了获得更高的性能。代价通常是牺牲可移植性和安全性，因此使用 `unsafe` 需自担风险。我们关于如何以及何时使用 `unsafe` 的建议，与我们在[第 11.5 节](#part0109.html#id-profiling)中引用的 Knuth 关于过早优化的评论不谋而合。大多数程序员永远不需要使用 `unsafe`。尽管如此，偶尔会有一些关键代码使用 `unsafe` 编写最为合适。如果仔细的研究和测量表明 `unsafe` 真的是最佳方法，请将其限制在尽可能小的范围内，以便程序的大部分不受其影响。

暂时将最后两章放在脑后。编写一些实质性的 Go 程序。避免使用 `reflect` 和 `unsafe`；只有在必须时才回过头来看这些章节。

同时，祝你 Go 编程愉快。我们希望你像我们一样享受编写 Go 的乐趣。
