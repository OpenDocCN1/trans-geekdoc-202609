Caffe's tool-set is written in python with pyc interfacing and only requires Caffe's prototxt and caffodel as inputs. First, Ristretto is used to analyze and generate static or dynamic fixed-point quantization schemes for each layer. The quantization results are used to generate modified CNN weights which are transferred once to FPGA board DRAMs. A parser extracts layer attributes from the prototxt which are used by architecture optimizer along the quantization results from Ristretto. Following this, the OpenCL compiler takes over and generates the FPGA binary. Finally, the same binary can be used to accelerate specific or multiple networks accordingly.

## 8.9 Performance evaluation

To verify the computation model, we implement FICaffe on a DE5-Net board with a Stratix V GXA7 FPGA, 4 GB DDR3 DRAM @ 800 MHz and PCI-E Gen3 x8 interface with the host PC. Our host is a 6-Core Intel's Xeon CPU E5-2603 v3 @ 1.60 GHz, with 16 GB RAM. Intel's OpenCL SDK v16.0 is used to synthesize the libraries. The board uses the PCI-E port along with an external power supply.

### 8.9.1.2 Exploration strategy

To choose optimum values of design, we perform design space exploration to estimate resource usage and runtime. We allow Tn to vary as powers of two, Tm takes values as well to improve DSP usage. Performance scales linearly with DSPs to some power of two due to the nature of feature map used in CNNs, after which the gain is nominal. Designs that do not satisfy DSP and BRAM requirements of FPGA board are rejected. We then check logic usage of designs in descending order of highest performance and select the first one that satisfies logic resource. This reduces the total exploration time.

### 8.9.1.3 Design variable optimization

The runtime and resource optimization for VGG and GoogleNet are shown in Figure 8.11. 8.11(a) and (d) show how the runtime latency varies with sweep of Tn and Tm for values that satisfy resource constraints of FPGA. Optimal pairs of these tiling factors are obtained with the least latency. Furthermore, Tr also has impact on performance along BRAM usage. For a network with large layer dimensions like VGG, i.e., with large, Tr can only be increased to a relatively lower extent as the buffer depth quickly saturated BRAM resources. This is seen in Figure 8.11(b) as Tr has a maximum sweep up to 18. On the other hand, GoogleNet layer dimensions are relatively smaller and Tr can be made as large as 68 but buffer initializations start dominating for on-chip buffers and best performance occurs at 13, i.e., visible in Figure 8.11(e). To provide higher on-chip bandwidth, buffer depths, the burst length needs to be sacrificed, leading to poor off-chip memory performance. To keep from stalling, we give higher preference to the on-chip bandwidth by instantiating as wide on-chip buffers as needed and then optimize the performance by using the Tr values. Figure 8.11(c) and (f) show how used BRAMs change in incremental steps for VGG and GoogleNet, respectively. If the value of Tr at a step in Figure 8.11(f) falls inside the monotonic region BRAM requirement can be reduced by reducing Tr by 1 with marginal no reduction in performance. This can result in simplified routing leading to higher operating frequency.
