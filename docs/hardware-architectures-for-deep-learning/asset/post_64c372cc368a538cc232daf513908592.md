### 8.6.2 Unifying off-chip and on-chip memory

FPICache takes advantage of on-chip, off-chip bandwidth matching. We allow the unmatched bandwidth impact to factor into the predicted performance which gives us better runtime estimates and independence from the underlying FPGA platform used.

### 8.6.21 Impact of unmatched system

To determine access latency for a memory system, suppose the accelerator runs at freq. If number of data elements stored/from to the memory is num\_data\_elem and DW is the data width in number of bits, then the number of cycles spent in memory access is given by

```
$num\_cycles = mem\_latency \times freq \quad (8.7)$
```

```
$mem\_latency = \frac{data\_size}{mem\_bw} \quad (8.8)$
```

```
$data\_size = num\_data\_elem \times DW \quad (8.9)$
```

where mem\_bw is the bandwidth of the memory system. The effective bandwidth mem\_bw can be determined in the following way.

Let us denote off\_chip\_bw as the theoretical bandwidth specification of DRAMs and on\_chip\_bw as the total bandwidth provided by BRAM buffers as defined later.

It is often not possible to fully use the DRAM device bandwidth without wide data requests and sequential accesses for burst transfer [6]. As a result, the number of independent parallel on-chip buffer ports affects off-chip bandwidth usage. For example, IFM buffer banks have $Tn$ independent ports to supply parallel pixels every cycle. Accordingly, IFM tiles are loaded with $Tn$ elements every cycle, even though off-chip memory might be able to provide more.

Figure 8.6 shows achieved bandwidth with DDR3 DRAMs operating at 800 MHz for different on-chip buffers with small burst lengths of 128. Maximum capable performance of the memory used is 25 GB/s and the memory controller provides a 1024 bit wide interface. As we can see, to cache data in a 64 bit wide on-chip buffer, the requests have to be 64 bits per cycle which achieved only 1.32 GB/s, a fraction of the available off-chip memory performance. By increasing the on-chip bandwidth, per cycle requests can be widened correspondingly and better off-chip bandwidth usage. It is just enough to make widths equal to interface width of 1,024, as even more wider requests can also improve the burst average. Further improvement requires longer access of sequential data. For feature maps, the burst length is represented by depth of the buffer. For example, OFM buffers maximum possible burst is $Tr \times max$. The burst access effects of on-chip memory are incorporated in the runtime model presented in the next section by assuming that all accesses within maximum off-chip bandwidth do not encounter any stalls.

### 8.6.2.2 Effective bandwidth latency

We need to consider both the maximum bandwidth $off\_chip\_bw$ and the request bandwidth $on\_chip\_bw$, to study memory latency. Hence, (8.10) yields the effective bandwidth $mem\_bw$, visible to the accelerator as

```
mem_bw = min(off_chip_bw, on_chip_bw) (8.10)
on_chip_bw = vector_size × DW × freq (8.11)
```

where vector\_size is the number of data elements accessed every cycle as shown in (8.6). For stall-free operation, we want the $on\_chip\_bw$ to be as close to $off\_chip\_bw$ as possible.

Lower on\_chip\_bw would mean that off\_chip\_bw is used and there is room for memory performance improvement. On the other hand, higher on\_chip\_bw would mean that performance is memory bound and is restricted by off\_chip\_bw. As the architecture scales, on\_chip\_bw requirement subsequently surpasses off\_chip\_bw and the DRAM bandwidth becomes the bottleneck. FICCaffe's architecture optimizer considers impacts of this unmatched off\_chip\_bw and on\_chip\_bw and tries to adjust the design parameters accordingly. We express (8.7)-(8.10) into a single expression as follows:

```
num_cycles = num_data_elem \times DW\min(off\_chip\_bw, on\_chip\_bw) \times freq
= num_data\_elem \times avg\_cycles\_per\_elem  (8.12)
```

where we represent the factor avg\_cycles\_per\_elem as ACPE for brevity. This is calculated accordingly with on\_chip\_bw of the buffers as it is used for, represented as ACPE$_i$, ACPE$_o$ and ACPE$_w$ for IFM, OFM and weight buffers, respectively.

### 8.6.3 Analyzing runtime

We categorize runtime cycles, total\_cycles, and into the following stages:

- ifm\_pl\_cycles: number of cycles to preload the first IFM file
- wt\_ld\_cycles: total weight cycles
- conv\_cycles: total number of convolution
- mem\_ld\_cycles: total number of load/store IFM files
- ofm\_ps\_cycles: number of cycles to store the last OFM

Cycles by stages 1, 2, 4 and 5 are overheads that need to be minimized. The rest of this section is dedicated to these variables. Before computation, the IFM filters are loaded. As IFM dimensions are determined by Tr, shown here, they are:

```
ifm\_pl\_cycles = N_{itr} \times N\_C \times (R_{itr}) \times Tn \times ACPE\_i  (8.13)
```

Weight filters are loaded onto chip-buffers as they are discarded from IFM and brought back from global memory. This overlap is not significant for CLs with large IFM.. traffic:

```
wt\_ld\_cycles = M\_C \times M\_R \times N_{itr} \times Tm \times ACPE\_w + bias\_cycles  (8.14)
```

```
bias\_cycles = M_{itr} \times Tm \times ACPE\_o  (8.15)
```

If on\_chip\_bw cycles of 8.5 do not incur any stalls, then the total cycles for convolution can be expressed as:

```
conv\_cycles = M\_C \times M\_R \times N_{itr} \times M_{iter} + R_{itr} \times M_{iter} \quad (8.16)
```

where the second term is added to the tiling loop. It is possible to potentially hide IFM loads and OFM stores inside convolution cycles. But for accurate estimates, we remove the last OFM store memory traffic:

```
mem\_ld\_cycles = ifm\_ld\_cycles + ofm\_st\_cycles \quad (8.17)
```

Details of each of these follows. Since convolution filters can have strides less than IFM dimensions, IFM rows tend to slightly overlap. For smaller IFMs in deeper layers of CNNs, IFM sizes become smaller but not require tiling if Tr is large enough. This presents another trade-off in Tr. As IFM traffic is complex, we instead calculate number of IFM elements required by every IFM row:

```
rows1 = \begin{cases} 0, & \text{if } R_{itr} = 1 \\ K\_R + S \times (M\_R - (R_{itr} - 1)) \times Tr) \times (R_{itr} - 2), & \text{otherwise} \end{cases} \quad (8.18)
```

```
rows2 = K\_R + S \times (M\_R - (R_{itr} - 1)) \times Tr \quad (8.19)
```

```
ifm\_ld\_cycles = N_{itr} \times N\_C \times (rows1 + rows2) \times Tn \times ACPE \quad (8.20)
```

```
ofm\_ld\_cycles = M\_C \times M\_R \times M_{itr} \times (N_{itr} - 1) \times Tm \times ACPE \quad (8.21)
```

```
ofm\_st\_cycles = M\_C \times M\_R \times M_{itr} \times N_{itr} \times Tm \times ACPE \n- ofm\_ps\_cycles \quad (8.22)
```
