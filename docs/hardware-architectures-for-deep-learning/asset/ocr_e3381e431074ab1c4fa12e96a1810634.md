# 6.4.2 Supporting activation sparsity

Cvlut optimized DaDianAo architecture by enabling skipping zero activation [23]. In every cycle, DaDianAo computes multiplication of a $16\times16$ matrix (of synapses) and a $16\times1$ vector (ofNeurons), in each tile. DaDianAo showed that such operations suffice to support both CNN and FC layers. In this architecture, $16\times16$ synaptic values are loaded from a wide ERAM bank (also called synapse buffer or SB) to an array of $16\times16$ multipliers, while the other operands come from broadcasting 16 neuron values from the input neuron buffer or NBin (see Figure 6.3(a)). Hence, if a neuron value is zero, it causes 16 multiply-by-zero operations. In order to avoid underutilizing the multipliers, Cvlut decomposes the multiplier array to sixteen $16\times1$ multiplier vectors (or subunits). Thus, all the multipliers in a subnet share the same neuron values. In addition, Cvlut breaks 1 ERAM bank to 16 banks, one for each subnet. (however, they cannot be fully independent to be synchronized in every cycle (as they should still contribute to the output numbers). Due to the loose independence, each subnet can now skip steps (see Figure 6.3(b)). To end, Cvlut stores only nonzero input neurons with their offset. The index is used to fetch the appropriate weights from SB. Cvlut also uses format (ZNAF). In this format, data are decomposed into bricks, that is 16 indexed neurons in 16 consecutive input feature maps. Each brick is compressed, separately, by storing only its nonzero values. For each brick, Cvlut stores the offsets in a different storage unit next to the central unit. Cvlut does not leverage ZNAF to save capacity in order to simplify locating bricks. Hence, each brick of data occupies 16 positions whether it is compressible or not. Dispatch reads the required bricks from the central buffer in ZNAF format and distributes them to the tiles. The result of the computation is also encoded in ZNAF because it is passed through ReLU, before storing it in the central buffer. Cvlut reported $1.37\times$ improvement in the throughput with $4.5\%$ area overhead (measured for 65 nm technology). This low area overhead is due to two main reasons. First, it works with 16-bit values, as the metadata overhead and control is marginal, and second, most of the area is occupied by large ERAM banks.
