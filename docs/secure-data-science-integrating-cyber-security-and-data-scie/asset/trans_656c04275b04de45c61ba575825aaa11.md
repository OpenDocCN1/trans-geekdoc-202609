

# 视图作为安全机制

视图作为安全机制已被广泛研究，既用于自主安全也用于强制安全。例如，可能不想授予对整个关系的访问权限，特别是当它有 25 个属性时，如医疗记录、薪资、差旅信息、个人数据等。因此，DBA 可以定义视图并授予用户对视图的访问权限。同样，在强制安全的情况下，视图也可以被分配安全级别。

视图也存在相关问题，包括视图更新问题（参见 [DATE1990](#ch02.xhtml#ref2_7)）。也就是说，如果更新了视图，则需要确保基本关系也被更新。因此，如果视图被 John 更新，而 John 没有访问基本关系的权限，那么基本关系还能被更新吗？也就是说，我们是为不同用户创建不同的视图，然后由 DBA 将视图上的更新合并为对基本关系的更新？[图 2.7](#ch02.xhtml#fig2_7a) 说明了用于安全的视图。

### 2.3.1 用于安全的 SQL 扩展

本节讨论策略规范。虽然重点将放在用于安全策略规范的 SQL 扩展上，但我们也将简要讨论一些新兴语言。请注意，SQL 是为关系系统的数据定义和数据操纵而开发的。已经开发了各种版本的 SQL，包括面向对象的 SQL、面向多媒体的 SQL 和面向 Web 的 SQL。也就是说，在过去 30 年里，SQL 对数据操纵和数据定义产生了巨大影响（参见 [SQL3](#ch02.xhtml#ref2_16)）。

正如我们所说，SQL 是一种数据定义和数据操纵语言。安全策略可以在数据定义期间指定。SQL 具有用于指定授予和撤销用户访问权限的 `GRANT` 和 `REVOKE` 结构。也就是说，如果用户 John 对关系 `EMP` 具有读取访问权限，则可以使用 SQL 指定类似 `GRANT JOHN EMP READ` 的内容，如果要撤销访问权限，则需要类似 `REVOKE JOHN EMP READ` 的内容。SQL 还通过更复杂的约束进行了扩展，例如授予 John 读取关系中元组的访问权限，以及授予 Jane 写入关系中元素的访问权限。

在 [THUR1989](#ch02.xhtml#ref2_19) 中，我们指定了用于安全断言的 SQL 扩展。这些断言用于多级安全。我们可以使用类似的推理来指定自主安全策略。例如，考虑这样一种情况：John 没有读取 `EMP` 中姓名和薪资组合在一起的访问权限，但他可以分别读取姓名和薪资。可以用类 SQL 语言指定如下：

```
GRANT JOHN READ
EMP.SALARY
GRANT JOHN READ
EMP.NAME
NOT GRANT JOHN READ
Together (EMP.NAME, EMP.SALARY)
```

如果要授予 John 读取薪资低于 30K 的员工的访问权限，则该断言指定如下：

```
GRANT JOHN READ
EMP
Where EMP.SALARY < 30K
```

请注意，我们指定的断言尚未纳入任何标准。这些是我们的一些想法。我们需要探索将这些断言纳入标准的方法。也有人提出了用于基于角色的访问控制的 SQL 扩展。事实上，像 Oracle 的 Trusted 数据库产品这样的产品就实施基于角色的访问控制。访问控制规则是用类 SQL 语言指定的。

请注意，还有许多其他已开发的规范语言。这些包括用于 Web 和语义 Web 的 XML、RDF 及相关语言。语义 Web 本质上是一个智能 Web。已经为 XML 和 RDF 指定了类 SQL 语言。例如，为 XML 开发了 XML-QL，它后来演变成了一种称为 XQuery 的语言。SPARQL 现在是 RDF 的查询语言（参见 [THUR2007](#ch02.xhtml#ref2_25)）。我们将在 [第 IV 部分](#part_04.xhtml#part4) 讨论的系统中使用此类语言。[图 2.9](#ch02.xhtml#fig2_9a) 说明了安全策略的规范方面。

### 2.3.2 查询修改

查询修改（现称为查询重写）最早是在加州大学伯克利分校的 INGRES 项目中提出的（参见 [STON1974](#ch02.xhtml#ref2_17)）。其思想是根据约束条件修改查询。我们已成功设计并实现了基于强制安全的查询修改（参见 [DWYE1987](#ch02.xhtml#ref2_8)、[THUR1987](#ch02.xhtml#ref2_18)、[THUR1993](#ch02.xhtml#ref2_20)）。然而，本节的大部分讨论将集中在基于自主安全约束的查询修改上。我们通过一些示例来说明要点。

考虑 John 检索 `EMP` 中所有元组的查询。假设 John 只有读取薪资低于 30K 且员工不在安全部门的元组的访问权限。那么查询

```
Select * from EMP
将被修改为
Select * from EMP
Where salary < 30K
And Dept is not Security
```

其中我们假设 `EMP` 的属性为，例如 `name`、`salary`、`age` 和 `department`。

本质上发生的情况是，查询的 "where" 子句包含与该关系关联的所有约束。我们也可以有跨越多个关系的约束。例如，我们可以有两个通过 `Dept #` 连接的关系 `EMP` 和 `DEPT`。那么查询修改如下：

```
Select * from EMP
Where EMP.Salary < 30K
And EMP.D# = DEPT.D#
And DEPT.Name is not Security
```

我们使用了一些简单的示例来说明查询修改。详细算法可以在 [DWYE1987](#ch02.xhtml#ref2_8) 和 [STON1974](#ch02.xhtml#ref2_17) 中找到。高层算法如 [图 2.10](#ch02.xhtml#fig2_10a) 所示。

### 2.3.3 自主安全与数据库功能

在 [第 2.3.2 节](#ch02.xhtml#sec2_003_002) 中，我们讨论了查询修改，这本质上是在查询操作期间处理安全约束。查询优化也会受到安全约束的影响。也就是说，一旦查询被修改，就必须构建查询树。其思想是将选择和投影下推到查询树中，并在稍后执行连接操作。

其他功能也会受到安全约束的影响。让我们考虑事务管理。Bertino 等人开发了用于事务管理中完整性约束处理的算法（参见 [BERT1989](#ch02.xhtml#ref2_3)）。我们已经研究了他们的技术，用于事务管理期间的强制安全约束处理。这些技术可以改编用于自主安全约束。其思想是确保在事务执行期间不违反约束。
