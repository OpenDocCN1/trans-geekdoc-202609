
1. **Policy Engine**: CAISS 使用基于 RDF 的策略引擎，其表达能力有限。RDF 的目的是为描述资源提供结构（或框架）。OWL 构建在 RDF 之上，专为需要处理信息内容而非仅向人类用户呈现信息的应用程序设计。OWL 通过提供描述属性和类的额外词汇以及形式语义，比 RDF 具有更强的机器可解释性。OWL 有三种表达能力递增的子语言：OWL Lite、OWL DL 和 OWL Full，可根据应用需求自由选择合适的子语言。在 CAISS++ 中，我们计划使用比 RDF 表达能力强得多的 OWL，通过特定于组织的领域本体以及系统级的上层本体来建模安全策略。（注：CAISS++ 将复用组织现有的领域本体，或在不存在时促进新领域本体的创建。此外，我们还必须设计集中式 CAISS++ 组件将使用的上层本体。）此外，CAISS++ 将利用分布式推理算法，借助本体来强制执行安全策略。

2. **Hadoop Storage Architecture**: CAISS 使用静态存储模型，用户仅在初始化步骤中向系统提供一次 RDF 数据。此后，不允许用户更新现有数据。另一方面，CAISS++ 试图为用户提供灵活的存储模型。在 CAISS++ 中，允许用户将新数据追加到存储在 HDFS 中的现有 RDF 数据中。注意，仅允许追加新数据而不允许删除/修改现有数据，源于 HDFS 强制执行的文件仅追加限制。

3. **SPARQL Query Processor**: CAISS 仅支持使用基本图模式（BGP）的简单 SPARQL 查询。在 CAISS++ 中，将增加对其他 SPARQL 查询算子（如 `FILTER`、`GROUP BY` 和 `ORDER BY`）的支持。此外，CAISS 使用启发式查询优化器，旨在最小化回答查询所需的 MapReduce 作业数量。CAISS++ 将采用基于成本的查询优化器，以最小化查询执行过程中访问的三元组数量。

### 16.2.4 Design of CAISS++

CAISS++ 克服了 CAISS 的局限性。CAISS++ 的详细设计及实现将在第 2 阶段进行。CAISS 的经验教训也将推动 CAISS++ 的详细设计。我们假设数据已使用适当的 DoD 加密技术进行加密，因此本项目不研究加密。CAISS++ 的操作概念如 [Figure 16.4](#ch16.xhtml#fig16_4a) 所示，展示了其与多个参与机构的交互，多个组织在单一云中共享数据。

CAISS++ 的设计基于基于 OWL 的策略引擎与 RDF 处理引擎的新颖组合。因此，该设计由多个任务组成，每个任务分别求解，随后集成为单一框架。

(1) **OWL-based policy engine**：策略引擎使用一组特定于机构的领域本体以及一个上层本体来构建用于 AIS 任务的策略。强制执行策略的任务可能需要使用分布式推理器；因此，我们将评估现有的分布式推理器。

(2) **RDF processing engine**：处理引擎需要构建复杂的存储架构以及高效的查询处理器。

(3) **Integration Framework**：最后的任务是将策略引擎与处理引擎结合成一个集成框架。CAISS++ 的初始设计将基于设计简洁性与其可扩展性和效率之间的权衡。第一种设计备选称为集中式 CAISS++，选择简洁性作为权衡；第二种设计备选（称为去中心化 CAISS++）选择可扩展性和效率作为权衡。最后，我们还提供了一种混合 CAISS++ 架构，试图结合集中式和去中心化 CAISS++ 的优势。由于 CAISS++ 遵循需求驱动设计，我们前面为实现 AIS 而概述的任务划分存在于我们接下来介绍的每种方法中。

#### 16.2.4.1 Centralized CAISS++

[Figure 16.5](#ch16.xhtml#fig16_5a) 展示了两个机构通过集中式 CAISS++ 进行交互。集中式 CAISS++ 由用于存储共享数据的共享云存储组成。所有参与机构存储其各自的知识库，包含领域本体及相应的实例数据。集中式 CAISS++ 还包含一个上层本体、一个查询引擎（QE）和一个分布式推理器（DR）。上层本体用于捕获参与机构领域间通用的领域知识，而领域本体捕获特定于给定机构或领域的知识。注意，给定机构的领域本体将受到保护，不被其他参与机构的领域本体访问。策略可以根据其适用范围，在上层本体或任意领域本体中捕获。注意，给定机构的领域本体将受到保护，不被其他参与机构的领域本体访问。
