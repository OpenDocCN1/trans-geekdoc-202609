
# 15.4.3 使用谓词进行分割

在第一步中，我们根据谓词对数据进行划分。这种划分能立即让我们缩减任何不包含变量谓词的 SPARQL 查询的搜索空间。对于此类查询，我们只需为每个谓词选取一个文件，并仅在这些文件上运行查询。为求简化，我们使用谓词命名文件，例如，所有包含谓词 `p1:pred` 的三元组都存入名为 `p1-pred` 的文件中。然而，如果三元组模式 [W3e] 中存在变量谓词，且我们无法确定对象的类型，则必须考虑所有文件。如果我们能确定对象的类型，则考虑所有包含该类型对象的文件。我们将在 [第 15.5 节](#ch15.xhtml#sec15_5) 中进一步讨论这一点。在真实的 RDF 数据集中，不同谓词的数量通常不大 [[STOC2008](#ch15.xhtml#ref15_45)]。不过，也存在拥有许多谓词的数据集。在这种情况下，我们的系统性能不会变化，因为我们只选择与 SPARQL 查询中指定的谓词相关的文件。

### 15.4.4 使用对象的显式类型信息进行分割

在下一步中，我们处理 `rdf_type` 文件中的显式类型信息。谓词 `rdf:type` 在 RDF 中用于表示某资源是某个类的实例。`rdf_type` 文件首先被分割成与 `rdf:type` 谓词拥有的不同对象数量相同数量的文件。例如，如果在本体中，类层次结构的叶子节点是 `c[1]`、`c[2]`、…、`c[n]`，那么我们将为这些叶子节点中的每一个创建文件，文件名将类似于 `type_c[1]`、`type_c[2]`、…、`type_c[n]`。请注意，对象值 `c[1]`、`c[2]`、…、`c[n]` 不再需要存储在文件内部，因为它们可以轻松地从文件名中获取。这进一步减少了存储数据所需的空间。我们为谓词 `rdf:type` 的每个不同对象值生成这样一个文件。

### 15.4.5 使用对象的隐式类型信息进行分割

我们根据对象的类型对剩余的谓词文件进行划分。并非所有对象都是 URI（统一资源标识符）；有些是字面值。字面值保留在以谓词命名的文件中；它们不需要进一步处理。URI 对象的类型信息未在这些文件中提及，但可以从 `type_*` 文件中检索。URI 对象会移入以“谓词_类型”命名的相应文件中。例如，如果一个三元组具有谓词 `p`，且 URI 对象的类型为 `c[i]`，则主语和对象将在文件 `p_c[i]` 中以一行的形式出现。为了进行这种分割，我们需要将谓词文件与 `type_*` 文件进行连接，以检索类型信息。

我们的 MapReduce 框架（详见 [第 15.5 节](#ch15.xhtml#sec15_5)）包含三个子组件。它接收用户的 SPARQL 查询并将其传递给输入与计划生成器。该组件使用我们在 [第 15.5 节](#ch15.xhtml#sec15_5) 中描述的算法选择输入文件，决定需要多少个 MapReduce 作业，并将信息传递给连接执行器组件，后者使用 MapReduce 框架运行作业。随后，它将来自 Hadoop 的查询结果返回给用户。

### 15.4.6 访问控制模型

我们在 RDF 数据系统之上开发了一种基于令牌的访问控制机制以及一种基于 XACML 的访问控制模型。运行架构的右侧展示了 XACML 策略是如何实施的。也就是说，当数据从优化组件（左侧）到达时，根据 XACML 模型在数据上强制执行策略。具体流程为：请求被提交给 PEP（策略执行点）。PEP 执行一些检查，然后将其交给 PDP（策略决策点）进行决策。PDP 随后咨询 PAP（策略接入点）和 PIP（策略信息点），然后决定应如何强制执行策略。最后，PEP 强制执行该决策。值得注意的是，基于 XACML 的框架可以被任何访问控制模型替代，因此我们也实现了基于令牌的访问控制模型。这些安全模型将在 [第 15.7 节](#ch15.xhtml#sec15_7) 中讨论。

## 15.5 MapReduce 框架

### 15.5.1 概述

MapReduce 框架是我们云计算工作的核心。在本节中，我们将讨论如何在我们的 MapReduce 框架组件中回答 SPARQL 查询。

[第 15.5.2 节](#ch15.xhtml#sec15_005_002) 讨论了我们用于选择输入文件以回答查询的算法。[第 15.5.3 节](#ch15.xhtml#sec15_005_003) 描述了生成回答 SPARQL 查询计划所需的成本估算。它介绍了我们在后续讨论中使用的一些术语。我们还描述了我们应遵循的用于估算计划成本的理想模型，并介绍了我们在实践中使用的基于启发式的模型。[第 15.5.4 节](#ch15.xhtml#sec15_005_004) 展示了我们基于启发式的贪心算法，用于生成使用 [第 15.5.3 节](#ch15.xhtml#sec15_005_003) 中介绍的成本模型的查询计划。在某些生成计划的情况下，我们会面临平局情况。在 [第 15.5.5 节](#ch15.xhtml#sec15_005_005) 中，我们将讨论如何处理这些特殊情况。[第 15.5.6 节](#ch15.xhtml#sec15_005_006) 通过一个示例查询展示了我们如何在 Hadoop MapReduce 作业中实现连接。

### 15.5.2 输入文件选择

在确定作业之前，我们选择需要输入到作业中的文件。我们在此查询处理步骤中应用一些查询重写能力。我们获取用户提交的查询并遍历三元组模式。我们可能会遇到以下情况：

1.  在一个三元组模式中，如果谓词是变量，我们选择所有文件作为作业的输入，并终止遍历。

2.  如果谓词是 `rdf:type` 且对象是具体的，我们选择具有该特定类型的类型文件。例如，对于 LUBM 查询 9（清单 1），我们可以选择文件 `type_Student` 作为输入集的一部分。然而，这引出了一个有趣的场景。在我们的数据集中，实际上不存在名为 `type_Student` 的文件，因为 Student 类在本体树中不是叶子节点。在这种情况下，我们参考 LUBM 本体 [[LEHI](#ch15.xhtml#ref15_30)] 来确定正确的输入文件集。我们添加文件 `type_GraduateStudent`、`type_UndergraduateStudent` 和 `type_ResearchAssistant`，因为 GraduateStudent、UndergraduateStudent 和 ResearchAssistant 是以 Student 为根节点的子树的叶子节点。

3.  如果谓词是 `rdf:type` 且对象是变量，那么如果该变量的类型由另一个三元组模式定义，我们选择具有该特定类型的类型文件。否则，我们选择所有类型文件。

4.  如果谓词不是 `rdf:type` 且对象是变量，那么我们需要确定该对象的类型是否由查询中的另一个三元组模式指定。在这种情况下，我们可以重写查询并消除一些连接。例如，在 LUBM 查询 9（清单 1）中，Y 的类型被指定为 Faculty，Z 的类型被指定为 Course，这些变量被用作最后三个三元组模式中的对象。如果我们选择文件 `advisor_Lecturer`、`advisor_PostDoc`、`advisor_FullProfessor`、`advisor_AssociateProfessor`、`advisor_AssistantProfessor` 和 `advisor_VisitingProfessor` 作为输入集的一部分，则第 2 行的三元组模式变得不必要。同样，如果选择文件 `takesCourse_Course` 和 `takesCourse_GraduateCourse`，则第 3 行的三元组模式变得不必要。因此，我们得到清单 2 所示的重写查询。然而，如果未指定对象的类型，则我们选择该谓词的所有文件。

5.  如果谓词不是 `rdf:type` 且对象是具体的，那么我们选择该谓词的所有文件。
