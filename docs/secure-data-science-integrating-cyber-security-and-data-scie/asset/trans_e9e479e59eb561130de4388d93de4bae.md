
假设框架接收到以下管理员请求：`{Bob, SWRL[2]}`，其中 `SWRL[2]` 如下：

`SWRL[2] : Video(?targetObject) ^ ParentOf(Bob,?controlled) ⇒ PRead(?controlled,?targetObject)`

然后，系统可以修改提交的 SWRL 为：

`New_SWRL[2]: PRead(?p) ^ Grantor(?p,Bob) ^ Controlled(?p,?controlled) ^ TargetObject(?p,?targetObject) ^ Video(?targetObject) ^ ParentOf(Bob,?controlled) ⇒ PRead(?controlled,?targetObject)`

其求值效果是仅当存在管理员禁止策略（`Bob, *c, o*, Read`）时，才插入 `PRead` 属性实例（即读取禁止），其中 `c` 是 Bob 的子女，`o` 是视频资源。注意，即使提交的 SWRL 显式指定了受控用户的名称（例如 `…. ⇒ PRead(Alice,?targetObject)`），这也是有效的。

### 17.6.3 访问请求求值

一般来说，访问请求可以建模为一个三元组（`u`, `p`, `URI`），表示用户 `u` 请求在位于 `URI` 的资源上执行权限 `p`。为了评估该请求，框架必须验证是否存在访问控制授权，将 `URI` 上的权限 `p` 授予请求者 `r`。然而，由于所提系统也支持过滤策略，此类授权的存在并不一定意味着 `r` 被授权访问 `URI`，因为可能存在一条禁止策略拒绝该用户访问该资源。因此，要评估是应授予还是拒绝访问请求，有必要对 SAKB 执行两个查询。第一个用于检索授权，第二个用于检索禁止。更确切地说，如果 `u` 需要读取权限 `Read`，系统必须查询对象属性 `Read` 和 `PRead` 的实例。特别是，这两个查询都寻找实例 `<u, URI>`（即 `<u, URI> : Read` 和 `<u, URI> : PRead`）。如果第一个查询返回实例且第二个查询返回空集，则授予访问；否则拒绝。

再次考虑 [17.3 节](#ch17.xhtml#sec17_3) 和 [17.4 节](#ch17.xhtml#sec17_4) 中的示例，并增加一个名为“Susan”的人。Susan 是 Jane 的朋友，并发布了一个她允许所有朋友查看的视频。然而，Jane 的父亲禁止她观看视频。当 Jane 请求查看 Susan 的视频时，将执行授权和禁止查询。授权查询返回 `Read` 权限，但禁止查询返回 `PRead`。这意味着 Jane 将无法观看该视频。

## 17.7 访问控制框架的实现

在前几节中，我们提供了一个使用语义 Web 技术的社交网络访问控制框架。在这里，我们展示了在合成数据上对该框架的初步实现结果。如前所述，我们设计了一个基于语义 Web 技术的可扩展、细粒度的 OSN 访问控制模型。我们的主要思想是通过本体编码社交网络相关信息。具体而言，我们建议使用语义 Web 本体对 OSN 的以下五个重要方面进行建模：（1）用户配置文件，（2）用户间关系（例如，Bob 是 Alice 的密友），（3）资源（例如，在线相册），（4）用户与资源间的关系（例如，Bob 是相册的所有者），（5）动作（例如，在某人的墙上发布消息）。通过构建此类本体，我们对社交网络知识库（SNKB）进行建模。然后，我们的访问控制执行机制通过利用这些知识来实现。具体而言，思路是将安全策略定义为规则，其前件陈述 SNKB 上的条件，后件指定授权动作。我们假设由社交网络管理器托管的集中式参考监视器将强制执行所需策略。我们的架构具有可扩展性，因为我们可以添加模块来执行诸如推理控制之类的功能。此外，我们还可以扩展策略以包含信息共享策略，而不仅仅是访问控制策略。有关语义技术在在线社交网络中应用的详细讨论，请参阅我们的工作文献 [CARM2009a]。在这里，我们将讨论局限于那些影响我们在在线社交网络中实现资源访问控制机制的特定主题。

在最近的过去，Facebook 对其定义网络上朋友关系的方法进行了重大更改。以前，如果我们有两个是朋友的 Facebook 用户，例如 John 和 Jane，他们中的任何一方都可以选择 Facebook 允许的预选友谊类型之一，另一方则需要确认或拒绝这一友谊标签。随后，John 或 Jane 的任何朋友都能看到应用于这段友谊的定义。然而现在，每个人都有能力创建有意义的列表，而不是定义对他人可见的链接类型。然后，朋友可以被添加到用户选择的任意数量的列表中。这些列表随后可用于控制状态更新、墙贴等的可见性。但是，无法定义这些列表的层次结构。例如，如果创建了“高中同学”列表和“大学同学”列表，则无法创建“同学”列表，除非将每个人单独添加到该第三个列表中。

我们使用 W3C [WWW1999] 指定的 n 元关系模式来表示友谊。这意味着每个友谊都是一个类的实例，我们称之为 `FriendshipRelation`。这使我们能够维护关于每个友谊的独立信息。具体而言，我们为每个友谊维护一个 `TrustValue`。这使我们能够确定友谊的特定强度，即使与同一类中的友谊相比也是如此。我们的实现支持访问控制策略，以调节在线社交网络成员如何访问资源。特别是，支持的访问控制策略是基于我们之前的工作 [CARM2009b] 定义的。在这里，授权用户是根据网络中节点间关系的类型和/或信任级别来表示的。例如，访问控制策略可以规定，唯一被授权访问给定资源的 OSN 参与者是那些与资源所有者具有直接友谊关系的人，前提是该关系也具有特定的信任级别。

然而请注意，使用语义推理可以带来一些超出 [CARM2009b] 中讨论能力的改进。这一优势源于我们能够针对 OSN 中的语义概念指定访问控制策略。例如，作为默认设置，Facebook 可能规定照片只能由直接朋友查看。在个别用户未定义策略的情况下，推理将默认采用这一通用策略。我们为 OSN 提供安全性的方法设计在 [第 19 章](#ch19.xhtml#chapter19) 中讨论。主要方面包括过滤策略、安全规则执行、管理策略评估和访问请求评估。在下一节中，我们将描述我们的实现框架。
