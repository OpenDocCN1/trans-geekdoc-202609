

# 18.7.2.1 患者生成器

患者生成器从一组网页中提取一个人的属性。[算法 18.1](#ch18.xhtml#alg18_1) 详细描述了患者生成器的工作。

```
http://www.yellowpages.com/findaperson?fap_terms%5Bfirst%5D="fname"
&fap_terms%5Blast%5D=" Lname "
&fap_terms%5Bstate%5D=" State "
&page=1"
```

[图 18.10](#ch18.xhtml#fig18_10a) 显示了当 `fname`=`John`、`lname`=`Smith` 和 `State`=`CA` 时的结果。然后我们从结果页面中提取地址和电话号码。[图 18.11](#ch18.xhtml#fig18_11a) 显示了当基础 URI 为 `www.whitepatges.com`、参数为 `fname`=`John`、`lname`=`Smith` 和 `State`=`CA` 时执行算法 18.1 的结果。然后我们从结果页面中提取地址和年龄。[图 18.12](#ch18.xhtml#fig18_12a) 是我们在溯源知识库中为每位患者收集的属性列表。

# 18.7.3 杂项生成器

该模块使用 `www.webMD.com` 来确定疾病、药物、检查和治疗之间的关系。因此，这使我们能够将这些实体之间的语义关联添加到我们的知识库中。由于这些关系是任何用户也可获取的背景信息，我们构建了规则，在披露溯源信息时将这些语义关系纳入考量。

# 18.7.4 工作流生成器

我们构建了一组标准工作流，这些工作流取自现有程序（例如 `mercyhealthcom`）。由于这些程序免费可用，我们构建规则以保护生成的工作流中的某些敏感组件。此外，这些工作流中实体之间的关系可以是显式的，也可以是隐式的。因此，我们的推理控制器利用策略和推理规则的混合来保护这些工作流中的信息。

# 18.7.5 标注工作流

我们使用背景生成器产生的数据来标注我们的工作流。因此，患者属性之间的关联是从 `www.yellowpages.com` 和 `www.whitepages.com` 收集的。同样，医院和医生的属性实际上是从 `www.yellowpages.com` 和 `www.ratemd.com` 收集的。

# 18.7.6 生成工作流

如前所述，在我们的玩具医院示例中，为每位患者发起更新患者记录的工作流。记录的溯源是我们在系统中假设的唯一机密数据。其目的是给查询用户一个机会，去猜测与记录相关的患者疾病、药物或检查。溯源带来的挑战比传统数据更大。控制器不仅要预测涉及用户先验知识的推理，还要考虑数据项之间因果关系以及溯源实体相关的推理（[算法 18.2](#ch18.xhtml#alg18_2)）。

# 18.7.7 数据库中的不完整信息

我们从各种网页生成数据，每个网页为知识库贡献了一部分。这代表了我们的知识库包含部分或不完整信息的一个典型案例。

不完整数据库由一组约束和一个部分数据库实例定义。在不完整数据库上回答结合查询是一项重要的计算任务，它是信息集成、数据交换和数据仓储等许多问题的核心。关系数据库上部分信息的一个常见例子是视图。视图可以被定义为隐藏底层数据库中的重要数据，从而限制用户的访问。这通常是为了满足某些约束而进行的；例如，财务部门的员工可以查看会计记录，但不能查看人力资源记录。给定一个查询和一个不完整数据库，任务是计算确定答案的集合。确定答案是在符合部分实例并满足约束的每个数据库实例中都满足查询的元组。在一般约束下回答查询是不可判定的。因此，通常会限制所考虑的约束语言的表达能力，以实现可判定性。数据库中不完整信息的一个类比是 OWL 本体。在 OWL 本体中，TBox 可以被视为包含约束集合的概念模式，而 ABox 则可以被视为模式的某些部分实例。

不完整数据库具有一项重要特性，推理控制器在回答 RDF 数据库上的查询时可以利用该特性。当查询返回否定响应时，用户必须判断该查询是试图访问机密信息，还是该查询在 RDF 数据库中并不蕴含。
