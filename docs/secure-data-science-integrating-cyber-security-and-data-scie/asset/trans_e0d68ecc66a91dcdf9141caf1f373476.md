
[图 16.11](#ch16.xhtml#fig16_11a) 展示了混合布局的存储模式。该布局是垂直分区布局的扩展，因为除了为 RDF 图中的每个唯一谓词创建单独的文件外，它还创建了一个单独的三元组文件，包含采用 `SPO`（主语、谓语、宾语）格式的所有三元组。拥有此类文件的优势在于，它能直接提供属于特定主语或宾语的所有三元组。回想一下，在垂直分区布局中，此类搜索操作需要扫描多个文件。由于增加了三元组文件，该布局的存储空间效率不如垂直分区布局。然而，使用该布局可以更高效地执行查找属于特定主语或宾语的所有三元组的 `SPARQL` 查询。

### 16.2.4.7 SPARQL 的分布式处理

`CAISS++` 中的查询处理包含多个步骤（[图 16.12](#ch16.xhtml#fig16_12a)）。第一步是查询解析和转换，给定的 `SPARQL` 查询首先被解析以验证语法正确性，然后构建与输入查询对应的解析树。解析树随后被转换为 `SPARQL` 代数表达式。由于给定的 `SPARQL` 查询可以有多个等价的 `SPARQL` 代数表达式，我们用关于如何评估该表达式中每个操作的指令来标注每个此类表达式。此类带标注的 `SPARQL` 代数表达式对应于查询评估计划，作为优化器的输入。优化器选择一个使查询评估成本最小化的查询计划。为了优化查询，优化器必须知道每个操作的成本。为了计算每个操作的成本，优化器使用一个元存储，其中存储与 `RDF` 数据相关的统计信息。给定查询评估计划的成本也可以用 `MapReduce` 作业的数量或作为查询执行一部分将被访问的三元组数量来衡量。一旦选定查询计划，将使用该计划评估查询并输出查询结果。由于我们使用以云为中心的框架来存储 `RDF` 数据，评估引擎需要将 `SPARQL` 代数算子转换为底层存储布局（前文所述）上的等价 `MapReduce` 作业。因此，在 `CAISS++` 中，我们将为每个 `SPARQL` 代数算子实现一个 `MapReduce` 作业。此外，评估引擎使用分布式推理器来计算查询评估所需的推论。

### 16.2.4.8 框架集成

我们概述的作为 `CAISS++` 一部分的组件需要集成以协同工作。此外，这一集成过程取决于用户对 `CAISS++` 提供的三种可能设计选择之一的选择，即集中式 `CAISS++`、分散式 `CAISS++` 或混合 `CAISS++`。迄今为止提出的 `CAISS++` 各个部分的集成需要考虑若干问题。首先，我们需要确保本体工程过程已成功捕获机构的需求，并且本体可以存储在 `Hadoop` 存储架构使用的存储模式中。其次，我们需要确保分布式 `SPARQL` 查询处理器能够高效地评估底层 `RDF` 存储上的查询（即用户生成的 `SPARQL` 查询以及评估策略的 `SPARQL` 查询）。最后，我们需要对 `CAISS++` 进行性能评估，以验证其是否满足各参与机构的性能要求，以及与 `CAISS` 相比是否带来显著的性能优势。

### 16.2.4.9 策略规范与实施

`CAISS++` 的用户可以使用他们选择的语言（例如 `XACML`、`RDF` 和 `Rei`）来指定其信息共享策略。这些策略将使用现有的或定制的转换器转换为 `OWL` 的合适子语言。我们将扩展 `CAISS` 的策略引擎以处理用 `OWL` 指定的策略。除了 `RDF` 策略外，我们当前的策略引擎还可以处理用于实现基于角色的访问控制、推理控制和社会网络分析的 `OWL` 策略。

## 16.2.5 设计扩展

### 16.2.5.1 形式化策略分析

我们的框架适用于各种关键任务、高保障的应用，这些应用跨越多个可能相互不信任的组织。为了在这类环境中提供最大程度的安全保障，建立关于系统正确性及其所执行策略的强有力形式化保证非常重要。为此，我们研究了为我们的系统构建重要系统属性和策略分析的形式化、机器可检查证明的基础设施。虽然对于许多大型软件系统，构建机器可检查证明可能非常困难且耗时，但我们选择 `SPARQL`、`RDF` 和 `OWL` 作为查询、本体和策略语言，为在逻辑编程环境中优雅地构建此类证明提供了独特的机会。我们将把策略、策略重写算法和安全属性编码为 `Prolog` 中基于规则的逻辑推导系统，并应用模型检查和定理证明系统（如 `ACL2`）生成机器可检查的证明，以证明系统遵守这些属性。我们打算在模型中考虑的属性包括可靠性、透明性、一致性和完整性。我们的形式化策略分析结果将驱动 `CAISS++` 的详细设计和实现。据我们所知，以往的研究中没有专注于针对 `SPARQL`、`RDF` 和 `OWL` 的此类形式化策略分析。我们关于带内联参考监视器的形式化策略分析的广泛研究在相关工作中讨论。

通过将高级安全策略规范和系统模型降低到其二进制级实现的指称语义和操作语义层面，我们过去的工作为各种复杂软件系统开发了形式化的、机器可认证的安全实施机制，包括用 [.NET](http://in.NET) 实现的系统 \[HAML2006b\]、`ActionScript` \[SRID2010\]、`Java` \[JONE2010\] 和本地代码 \[[HAML2010b](#ch16.xhtml#ref16_30)\]。在二进制级工作提供了极高的形式化保证，因为它允许生成关键任务软件组件的工具链保持不可信；工具链生成的二进制代码可以直接被认证。该策略非常适合 `CAISS++`，因为诸如 `XACML` 和 `OWL` 等数据安全规范语言可以通过具有 `XML` 感知的系统应用程序编程接口（`API`）（如 `Java` 字节码）优雅地映射到字节码语言的二进制级。我们过去的工作应用了二进制插桩（例如内联参考监控）以及二进制类型检查 \[HAML2006b\]、模型检查 \[SRID2010\] 和自动定理证明（例如通过 `ACL2`）的组合，在上述领域实现了二进制软件的完全自动化机器认证。
