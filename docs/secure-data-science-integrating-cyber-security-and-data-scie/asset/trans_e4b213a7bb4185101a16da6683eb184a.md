

第一种授权是由访问控制策略蕴含的。一般来说，访问控制授权可以建模为一个三元组（`u`，`p`，`o`），表明主体 `u` 拥有在对象 `o` 上执行权限 `p` 的权利。因此，在某种程度上，访问控制授权表示 `u` 和 `o` 之间的一种关系 `p`，意味着 `u` 可以在 `o` 上行使 `p`。因此，我们决定将权限 `p` 的访问控制授权编码为一个 OWL 对象属性的实例，该属性命名为 `p`，定义在被授权人和被授权资源之间。为了对所有可能的访问控制授权建模，我们必须为 OSN 中支持的每个动作引入一个不同的对象属性（参见[第 17.3 节](#ch17.xhtml#sec17_3)）。值得注意的是，通过妥善定义编码访问控制授权的对象属性，我们可以根据动作间定义的分类自动传播授权。

让我们以动作 `Post` 为例，假设它已被定义为动作 `Write` 的子类。在访问控制方面，如果向用户授权了发帖权限，则也授权了写入权限。在所提框架中，只要对象属性 `Post` 被定义为对象属性 `Write` 的子属性，访问控制授权就可以自动推断出来。我们要注意，这种层级可能不同于传统的访问控制系统。当我们使用 SWRL 时，为超类定义的任何内容也将为其子类定义。然而，反之则不然。因此，当我们允许某个体 `Write` 时，并不会自动赋予其 `Post` 权限。

#### 17.5.2.2 禁止策略

过滤策略规定目标用户无权访问某个对象（在受监管过滤策略的情况下），或者目标用户倾向于不访问（在过滤偏好的情况下）。与访问控制授权类似，禁止指定了用户与其无权访问或倾向于不访问的资源之间的关系。因此，禁止也可以表示为 `Person` 和 `Resource` 类之间的一个对象属性。更确切地说，针对 Read 权限的禁止被定义为 OWL 对象属性 `PRead`。该对象属性的一个实例 `<John, URI1>:`PRead` 表明 Bob 不得读取资源 URI1。与访问控制授权类似，只需定义子属性，即可指定禁止如何传播。

让我们再次考虑三个基本动作：`Read`、`Write`、`Delete`，以及它们被禁止的版本：`PRead`、`PWrite`、`PDelete`。我们再次希望按逻辑顺序形成一个动作层级。也就是说，如果某个体被禁止 `读取` 资源，则她也应被禁止 `写入` 和 `删除` 该资源。为此，我们只需定义 `PRead` 为 `PWrite` 的子类型，而 `PWrite` 又是 `PDelete` 的子类型。

#### 17.5.2.3 管理员授权

管理员授权是由管理员策略蕴含的授权，回顾一下，其目的是授权用户指定访问控制或过滤策略。因此，管理员策略蕴含两类授权：指定访问控制策略的授权，我们简称为 `管理员授权`；以及指定过滤策略的授权，即 `管理员禁止`。一般来说，管理员授权可以表示为一个三元组（`u`，`p`，`o`），表明用户 `u` 被授权为对象 `o` 上的权限 `p` 指定访问控制策略。因此，与授权和禁止类似，管理员授权也可以表示为 `Person` 和 `Resource` 类之间的一个对象属性。根据这种建模，我们可以定义对象属性 `AdminRead`，其实例表明给定用户被授权表达授予特定对象读取权限的访问控制策略。考虑实例 `<Bob,URI1>:`AdminRead`，它表明 Bob 被授权指定授予 URI1 对象读取权限的访问控制策略。

与访问控制授权类似，只需定义子属性，即可指定管理员授权如何传播。让我们声明前面提到的属性 `AdminRead`，并进一步创建属性 `AdminWrite` 和 `AdminAll`。我们声明 `AdminAll` 为 `AdminWrite` 和 `AdminRead` 两者的子属性。考虑我们的运行示例，Alice 拥有一张照片。假设这授予了她该照片的 `AdminAll` 授权。如果 Alice 试图允许 Bob 读取该照片，而该动作仅限拥有 `AdminRead` 属性的个体执行，则通过 `AdminAll` 属性即可允许此操作。

相反，管理员禁止可以表示为一个元组（`s`，`t`，`o`，`p`），这意味着用户 `s`（监管者）被授权为目标用户 `t` 和对象 `o` 上的权限 `p` 指定过滤策略。与之前的授权不同，管理员禁止不能表示为属性，因为它们不表示二元关系。因此，我们决定将管理员禁止建模为一个 OWL 类 `Prohibition`。这使我们能够将禁止的所有组成部分指定为类属性。更确切地说，给定一个管理员禁止（`s`，`t`，`o`，`p`），我们可以将授权监管者建模为 `Prohibition` 和 `Person` 类之间的一个对象属性 `Supervisor`。类似地，目标用户可以表示为 `Prohibition` 和 `Person` 类之间的一个对象属性 `TargetUser`，目标对象表示为 `Prohibition` 和 `Resource` 类之间的一个对象属性 `TargetObject`。相反，监管者被授权声明过滤策略的权限不表示为对象属性。确实，为了自动传播管理员禁止，我们倾向于直接将权限指定为类名。因此，作为示例，`ProhibitionRead` 类的实例表示授权为读取权限指定过滤策略的管理员禁止。通过妥善定义子类，可以自动推断新的管理员禁止。

假设，我们有一个通用的 `Prohibition` 类，带有子类 `PRead` 和 `PView`。然后我们为它们各自创建另一个子类 `PAll`。假设我们有两个个体，John 和 Jane，John 是 Jane 的父亲。在这种情况下，John 应被允许过滤其女儿能观看的视频。即，我们有一个禁止（“John”，“Jane”，Video，`PAll`）。现在，对于任何视频和任何权限，John 都可以禁止他希望禁止的内容。

### 17.5.3 安全规则

所提框架将每个安全策略转换为一条 SWRL 安全规则，其中前件编码策略中指定的条件（例如，表示主体和对象规范的条件），而后件编码蕴含的授权或禁止。特别地，由于我们将安全规则建模为 SWRL 规则，SWRL 规则体陈述了针对 SNKB 的策略条件，即[第 17.3 节](#ch17.xhtml#sec17_3)中引入的本体上的条件，而 SWRL 规则头蕴含 SAKB 的新实例，即[第 17.3 节](#ch17.xhtml#sec17_3)中引入的本体的实例。因此，SWRL 安全规范的制定严格受限于 OSN 为建模 SN 和 SA 知识库所支持的本体。这意味着无法提供通用 SWRL 规则的形式化，因为这些规则会因所考虑的本体而异。相反，在本节中，我们旨在展示一些基于我们框架中采用的本体定义的有意义的 SWRL 安全规则示例。
