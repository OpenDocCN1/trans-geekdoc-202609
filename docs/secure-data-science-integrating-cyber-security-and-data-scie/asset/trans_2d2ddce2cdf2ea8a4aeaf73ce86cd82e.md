

# 混合 CAISS++

某机构的本地 CAISS++ 用于接收并处理针对位于该机构的实例数据的联邦查询。参与组是由来自多个机构、希望相互共享信息的用户组成的群体。组成员将就采用集中式还是分散式方法达成共识。如果需要，其他用户稍后也可以加入该组。混合 CAISS++ 将设计为同时支持一组参与组。此外，一个用户可以同时属于多个参与组。我们描述几个用例场景来说明其操作。

1.  第一种情况对应这样一种场景：一组希望安全地相互共享信息的用户选择了集中式方法。假设机构 1 的用户想与机构 2 的用户共享信息，反之亦然，那么这两个机构都将包含领域本体和实例数据的知识库存储在全局 CAISS++ 所在的共享云存储上。集中式 CAISS++ 方法通过让参与机构就使用中央云存储达成相互信任来工作。随后，信息共享按集中式 CAISS++ 的方式进行。

2.  第二种情况对应这样一种场景：一组用户选择了分散式方法。例如，机构 3、4 和 5 希望相互共享信息，并共同选择分散式方法。这三个机构都将各自的领域本体存储在中央云存储中，且该信息仅对该组成员可访问。后续的信息共享过程按前文所述的分散式 CAISS++ 方法进行。

3.  第三种情况对应这样一种场景：某机构的用户属于多个参与组，其中一些组选择集中式共享方法，另一些选择分散式方法。由于该用户属于一个使用集中式方法共享的组，他/她需要将数据传送到中央云存储，以使其数据可供该组使用。此外，由于该用户也属于一个使用分散式方法共享的组，他/她需要借助位于其机构的本地 CAISS++ 来响应联邦查询。

在 [图 16.9](#ch16.xhtml#fig16_9a) 中，我们展示了基于 Hadoop 的 RDF 存储与检索框架的架构概览。我们使用 `Store`（存储）的概念，为存储在底层 HDFS 中的 RDF 图提供数据加载和查询功能。一个存储代表单个 RDF 数据集，因此可以包含多个 RDF 图，每个图拥有自己独立的布局。随后，对 RDF 图的所有操作都隐式转换为对底层布局的操作，包括以下内容：

*   **布局格式化器**：该模块执行格式化布局的功能，即删除 RDF 图中的所有三元组，同时保留用于存储该图的目录结构。
*   **加载器**：该模块执行将三元组加载到布局中的操作。
*   **查询引擎**：该模块允许用户使用 SPARQL 查询来查询布局。由于我们的框架运行在底层 HDFS 上，因此对布局的查询机制涉及将 SPARQL 查询转换为可能的 MapReduce 作业流水线，然后在布局上执行该流水线。
*   **连接**：该模块维护与底层 HDFS 所需的连接和配置。
*   **配置**：该模块维护配置信息，例如组成存储的每个 RDF 图的图名。

由于 RDF 数据将作为我们存储模式的一部分，存储在不同的 HDFS 文件夹下的单独文件中，我们需要为这些文件夹和文件采用特定的命名约定。

## 16.2.4.4 命名约定

在我们的框架中，一个 Hadoop 存储可以由多个不同的 RDF 图组成。因此，将在 HDFS 中为每个此类 Hadoop 存储创建一个单独的文件夹。该文件夹的名称将对应于为给定存储选定的名称。此外，在我们的框架中，根据所选的存储布局，一个 RDF 图被划分为多个文件。因此，将在 HDFS 中为每个不同的 RDF 图创建一个单独的文件夹。默认 RDF 图的该文件夹名定义为 `default`，而对于命名 RDF 图，则使用该图的统一资源标识符 (URI) 作为文件夹名称。我们在框架中使用存储的抽象，原因是这将简化属于不同机构的数据的管理。我们框架支持的两种布局将在后面讨论。这些布局使用数量不等的 HDFS 文件来存储 RDF 数据。

## 16.2.4.5 垂直分区布局

[图 16.10](#ch16.xhtml#fig16_10a) 展示了垂直分区布局的存储模式。对于 RDF 图中包含的每个唯一谓词，该布局在底层 HDFS 中使用谓词名称作为文件名创建一个单独的文件。请注意，文件名中仅使用谓词 URI（统一资源标识符）的本地名称部分，且文件名与谓词 URI 之间存在单独的映射。给定谓词的文件为包含该谓词的每个三元组包含单独的一行。该行存储构成三元组的主语和宾语值。因为将谓词名称移至文件名完全消除了该谓词值的存储，所以这种模式将带来显著的存储空间节省。然而，相同的资源 URI 或字面值的多次出现将在所有文件中以及文件内部被多次存储。此外，SPARQL 查询可能需要查找多个文件，以确保向用户返回完整的结果，例如，查找属于特定主语或宾语的所有三元组的查询。
