
According to Ref [[21](#ch20.xhtml#r362)], retrieval-augmented generation (RAG) refers to the retrieval of relevant information from external knowledge bases before answering questions with LLMs. RAG has been showcased to significantly enhance model performance for knowledge intensive task. Since ranking lecture material is a knowledge intensive task, `Gemini Pro` is provided with context retrieved using RAG from a pdf containing topics present in DSA and OOPs coursework, stored in chunks in `Chroma DB` (a vector database). The context obtained has content related to the topic asked in query, and `Gemini Pro` is prompted to use this context to judge the lecture material in terms of context. This choice of exploring `Gemini Pro` with RAG as a content evaluator is backed by the attribution aspect of factuality of `Gemini API` models, that is, if grounded to a given context. The `Gemini API` models generate a response with the highest degree of faithfulness to the context as mentioned in [[20](#ch20.xhtml#r361)].

### 10.5.2 Test dataset composition and query distribution

Test set has been generated using demonstration data set (see Section 10.3). As discussed, the demonstration dataset consists of five query types: ST, TC, PQ, CQ, and OCQ. Test set is not chosen randomly to ensure a balanced representation of each query type. An equation-based approach is employed to determine the number of queries for each category as shown in Equation (10.1).

$$CQ \times x + OCQ \times x + TC \times x + PQ \times x = 50 \tag{10.1}$$

Count of queries in the demonstration dataset is fixed. Using those same count of queries of each category in the demonstration dataset (see Section 10.2 and [Table 10.1](#ch20.xhtml#t38)), Equation (10.1) is transformed to Equation (10.2).

$$11x + 7x + 70x + 138x + 48x = 50 \tag{10.2}$$

In above Equation (10.2), `x` represents the scaling factor, and their respective constants represent the count of queries belonging to a particular query type in demonstration dataset. For example, in the term `11x`, 11 represents the count of comparison queries in the demonstration dataset.

### 10.5.3 Evaluation

This section highlights the evaluation of our proposed technique through rule-based and human evaluation methods. Rule-based evaluation utilizes predefined rules and metrics to measure the performance of LLMs. Human evaluation relies on human judges to assess the quality of the LLM outputs. Combining both rule-based and human evaluation methods allows for a more comprehensive and precise assessment of LLM performance.

#### 10.5.3.1 Rule-based evaluation

In this phase, the generated LPM are evaluated on the basis of a predefined structural criteria which focuses on finding specific keywords, within the generated content, like topic identification, objectives, theory explanation, code implementation, complexity analysis, applications, conclusion, quiz, and references which should be a header in an ideal LPM. For the presence of each component, the generated material is rewarded a score of 1 and conversely, the absence results in a score of 0. Finally, all scores are added and since there are total 10 headings, a score out of 10 is assigned to each lecture material. The results obtained depicts that for the 50 queries in test dataset, the score of LPM generated using template-based prompting (`TB_score`) ranges between 9 and 10, for the LPM generated using few-shot, the score (`FS_score`) ranges between 6 and 10, and for the LPM generated using zero shot (`ZS_score`), the score ranges between 0 and 5, as shown in [Figure 10.7a](#ch20.xhtml#f77). It can also be observed, in [Figure 10.7b](#ch20.xhtml#f77), that count of value of TB score and FS score as 10 is similar but TB score is not below 9 for any query which is the case in zero shot and few shot. Therefore, it can be concluded that according to rule-based evaluation technique, TB prompt technique performed as good as FS prompt technique or better in terms of structural criteria.
