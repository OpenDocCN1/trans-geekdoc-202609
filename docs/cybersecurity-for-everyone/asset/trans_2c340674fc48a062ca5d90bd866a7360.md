
# 协议层级与网络通信

定义流量外观及流动方式的规则集称为**协议**。它们构成了每根管道所连接节点的交战规则。

人类交谈时也存在类似的交战规则。在最底层，语音只是一系列振动。在更高一层，我们将短时振动片段归类为音素。再往上，将音素组合归类为单词。最上层则涉及语言、演讲或对话等概念。电话能传输语音，但它仅将语音视为振动。语音识别系统（如许多自动话务员）必须在音素和单词的更高层级理解语音。智能代理或聊天机器人则必须将语音理解为对话。

同理，协议按层级排列，对应不同抽象层次。通信底层仅通过光纤、导线或无线电信号将比特从一端移动到另一端（比特流本身不包含任何揭示其“含义”的结构）。上一层理解比特集合作为通信单元的含义。更高层管理更复杂的通信过程（类似对话），包括处理两端不同步的情况。

## 5.1 IP 协议

在最底层（仅移动比特之上）是一种描述数据如何以单元移动的协议，但仅限简单单元。这就是**互联网协议**，即 `IP`。它负责将单个信息块（以**数据包**为单位）从源 `IP` 地址（发送计算机）传递到目标 `IP` 地址（接收计算机）。

这两台计算机通常不会直接相连，因此该协议不仅负责将数据从管道一端移至另一端，还负责通过一系列管道将其导向正确位置。它利用每个中间节点的路由表引导每个数据包，使其在每一步都更接近目的地。

现实类比是寄送实体邮件。邮局在一地收到信件，尽力投递到另一地。途中会经过分拣办公室，每个办公室将其发往旅程的正确下一阶段。

正如实体邮件一样，`IP` 传递是尽力而为的，发送方不会收到数据包已送达的通知。

在 `IP` 中，每个数据包独立于其他所有数据包处理，因此即使从同一来源发往同一目的地的数据包，也不一定遵循相同路径，也不保证按发送顺序到达。实体邮件也存在这种情况。

某个数据包在旅程各阶段可能经过的管道，其容量不一定相同。特别是数据包可能遇到只能处理较小数据包尺寸的管道（类似开车走捷径却遇到限高桥）。`IP` 拥有将大数据包分割成小数据包并在目的地重组的机制。这类似于将包裹切成薄片，使其看起来像一堆信件即可发送。遗憾的是，`IP` 拆分和重组数据包的机制过于简陋——它依赖每个片段仅记录其距原始数据包开头的距离——这给轻易篡改创造了机会。

## 5.2 TCP 协议

尽管我们使用实体邮政服务已超一个世纪，但它作为网络空间数据传输模型有明显缺陷。两个更抽象的协议构建在 `IP` 之上。使用这些高层协议的流量被分割成 `IP` 数据包并通过 `IP` 传输，但它们无需知晓具体实现方式。它们不再将管道视为简单的比特移动连接器，而是视为 `IP` 流量传输器。这些高层协议提供了 `IP` 缺失的功能，如保证交付和流速管理。

最重要且作为互联网标准的协议是**传输控制协议**，即 `TCP`。它太常见了，以至于常与 `IP` 连用称为 `TCP/IP`。`TCP` 提供了 `IP` 缺失的以下功能：

*   **端点间的有状态连接，创建会话**（而非单向单数据包投递）。会话类比对话：有始有终，存在期间双方均负责管理。
    
    建立连接要求一端发送控制**段**。
*   **数据包到达确认**，以便通过超时检测丢失的段，并由会话另一端的发送方重发。
    
    因双方知晓会话存在，均预期来自对方的流量。段到达后，接收方必须在约定时间内确认（双方可协商调整）。若发送方未收到确认，则假定段丢失并重传。
*   **按发送顺序向目标节点交付数据**，利用每个段携带的**序列号**。当某段延迟或丢失时，目标节点接收到的后续段会被保留，直到缺失片段到达。因此，目标端必须预留大量空间用于重组。
*   **拥塞控制**，通过信号告知发送方何时停止发送以便接收方追赶进度。
*   **更复杂的寻址方案**，发送方和接收方均使用 `IP` 地址和**端口号**的组合。节点上运行的每个预期与外界交互的软件使用特定端口。某些常用软件的端口号预先确定且广为人知——例如 Web 流量用端口 `80`，邮件用端口 `25`，域名服务用端口 `53`。其他软件每次启动时选择端口号。这些 `IP` 地址和端口号的组合标识了节点及其上运行的特定软件，确保数据来自并送达正确位置。

`TCP` 为互联网上两设备提供稳健通信，但若路径上某些管道较小、发生拥塞、或两端传输时间长，速度会相对较慢。

## 5.3 UDP 协议

在交付速率至关重要的场景下，还有一种可用的高层协议。它称为**用户数据报协议**，即 `UDP`，提供与 `IP` 同类功能——尽力而为交付，无排序或错误控制——但具备 `IP` 地址 + 端口寻址。因此 `UDP` 以牺牲可靠交换换取快速端到端交付。

`UDP` 用于延迟比偶尔丢包更重要的应用。此类应用通常主要单向流式传输数据。例如网络电话（`VOIP`）、视频传输（`Skype`、`Netflix`）。有时也用于可假设高可靠性的局域网（如远程桌面协议），因其避免了 `TCP` 的开销。
